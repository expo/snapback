# Clique build diary

## M1 — identity and profiles

I built the sessions-backed account entry, durable web session restoration, logout, unique user profiles, avatar persistence, profile editing, and live profile projection into a second signed-in client. The canonical M1 starter log is parsed and replayed through the generated `profiles.save` mutation rather than loaded into SQLite directly. The standalone acceptance runner covers every suite-required M1 assertion, and the frozen choreography passed all three required checks. An iOS Hermes bundle is retained under `artifacts/m1-ios`.

The familiar profile made the authoring core pleasantly legible. A flat `schema.ts`, a top-level `profiles.ts`, generated `api` references, `query`/`mutation`, `v.doc`, `ctx.db`, and React `useQuery`/`useMutation` all map closely to the Convex-shaped mental model. Once booted, the cross-client profile update was fast and the schema/index intent was easy to audit.

The work around that core fought hard. Published codegen could not bootstrap a `v.doc` function result until the schema had first been generated alone; the documented `_generated` directory is actively refused in favor of `generated`; and a mutation returning `v.doc("profiles")` passed codegen but failed at runtime. The sessions store also pins its exact function carrier, so a low-level restart after the correction required preserving and reseeding the partial store. On web, the published supervised environment ignored the provider's explicit binding override and demanded the unavailable supervisor IPC exchange. I kept the package's platform adapters but supplied a narrow local admission seam for the exact generated binding. Finally, the editor initially exposed default form state before its live profile snapshot arrived, allowing late hydration to overwrite user input; gating the form on hydration fixed the actual choreography failure.

What remained specifically Snapback-shaped was carrier construction, binding/admission evidence, auth-context-bound mutation identities, deployment pinning, first-party bootstrap state, and live-subscription custody. The missing diagnostic was a direct statement that the default Expo environment ignores an explicit binding when no supervisor exchange is installed. Codegen also needed a precise diagnostic for the schema-first `v.doc` bootstrap and the mutation document-result runtime incompatibility; both currently look like application contract errors.

## M2 — posts and the follow graph

I added directed, idempotent follow edges; text, image, video, and reply posts; live likes and reposts; Global and Following projections; author identity and avatars; linkified text without unfurling; thread-only replies; 20-item client pagination; and implicit self-membership without self-follow edges. The M2 starter segment is replayed after M1 through the same generated mutations. The acceptance runner covers all 22 suite-required M2 assertions, and the choreography passed all seven implemented required checks. Its two media-live checks remained the frozen harness's declared optional skips. The milestone's Hermes export is under `artifacts/m2-ios`.

The familiar profile continued to pay off in the normal data work: table/index definitions, ID validators, ordered queries, and set-state mutations were concise. Live broad-table queries plus deterministic client joins made the feed projection easy to inspect, and live counts generally converged in roughly 110–350 ms in choreography.

The rough edges were storage and custody. A media URI array first hit my undersized element limit, then revealed Snapback's independent 32 KB ceiling for an entire structured stored value; I moved up to four media values into scalar columns while keeping the public mutation input array-shaped. A more serious audit found that multiple headless clients share Node auth custody, so retained actor clients all drifted to the last signed-in principal. Re-authenticating the named actor before each fixture action made replay correct but much slower. Optional fields also decode as `null` even though their generated TypeScript shape reads as optional/`undefined`, which initially emptied the top-level feed. On the UI side, the web Stack retained an inactive feed composer in the DOM, producing a strict selector collision on the thread screen; rendering root controls only on the active path fixed it.

What I wanted from documentation was a stored-structured-value sizing page that distinguishes child limits from the 32 KB canonical aggregate ceiling, an explicit Node auth-custody warning for multi-persona replay, and generated types that reflect `null` for optional SQLite fields. A diagnostic that reports “actual string exceeds maxBytes” instead of “expected string, actual string” would also have shortened the media correction loop.

## M3 — conversations and presence

I added direct and group conversations, membership-aware message queries, ordered live messages, stable client IDs, quoted replies with an excerpt and jump target, sender identity, and expiring typing presence. The third starter segment is replayed after M1 and M2 through the same generated mutation path, including membership changes and quoted-message references. Acceptance covers all seven suite-required M3 assertions. The final two-client choreography passed both required checks and the implemented optional quoted-reply check; four optional checks remained explicit frozen-harness skips. The iOS Hermes export is retained under `artifacts/m3-ios`.

The core conversation model felt straightforward in the familiar profile. Tables for conversations, memberships, messages, and typing leases translated directly into indexed lookups and small authenticated functions. `v.doc`, generated IDs, `useQuery`, and `useMutation` kept the server/client boundary readable, while Snapback's live invalidation made cross-client messages work without a separate socket protocol in application code. The required live message check regularly arrived well inside a second.

The hard parts sat at the observation boundary. A group preview mentioning Bob made an otherwise honest browser check choose the wrong row, so the group summary had to remain semantically generic. The frozen message component also separates the whole bubble, content, quote action, and quote preview across test IDs; wrapping it without altering its contract was necessary for exact message selection. Quoted-message navigation first exposed a ScrollView offset mismatch on web and then an animation race, both fixed with a synchronous centered DOM jump and a native offset fallback. Typing presence initially refreshed its lease every 400 ms during sequential input, queuing enough mutations to miss the two-second visibility ceiling. A two-second refresh cadence preserved a three-second lease without flooding the write path and brought all three observed attempts under the ceiling.

The familiar profile saved the most work in authorization and reactivity: membership guards live beside the mutation, indexes express the intended access path, and the UI consumes generated function references rather than hand-written endpoints. The Snapback-specific remainder was still substantial: carrier replacement for an additive schema, exact deployment identity, repeated schema-only generation before `v.doc` functions, session-bound replay custody, and a lease implemented as durable rows because the platform exposes no first-class ephemeral presence primitive in this profile. The missing documentation was practical guidance for high-frequency presence writes—client mutation ordering, live-query invalidation latency, and whether a supported ephemeral channel exists. A latency diagnostic separating mutation queue time, commit time, and subscriber delivery would have made the typing correction direct instead of empirical.

# Lane essay (verbatim)

# Familiar, but not invisible: building Clique on Snapback

The Familiar TypeScript profile succeeds at its most important promise: once inside the application model, it feels recognizably like Convex. I could think in tables, indexes, validators, queries, mutations, authenticated principals, and live React hooks. The generated `api` object made function references concrete, and the data model stayed close enough to the source schema that moving between server code and UI code rarely required translation. For a social product, that is a strong fit. Profiles, follow edges, feed objects, conversations, memberships, messages, and typing leases all want transactional writes and reactive reads. The profile made those ideas easy to express without inventing an HTTP resource layer, cache keys, or a socket protocol.

That resemblance was most valuable during ordinary product work. A follow toggle could be an idempotent mutation guarded by an index. A message query could assert membership and return an ordered collection. A second browser could observe a committed profile edit or message through the same query hook the first browser used. Compared with building this on a conventional REST backend, there was much less duplicative machinery: no controller/request-schema/DTO/client-wrapper chain, no manual cache invalidation, and no separate event fan-out path. Compared with GraphQL, I did not have to coordinate schema resolvers, a normalized client cache, and subscription infrastructure. The familiar surface made the code compact and, more importantly, auditable.

Convex still feels more cohesive as a development experience. In Convex, the function model, deployment loop, generated bindings, database, authentication integrations, and reactive client tend to feel like one product. Snapback exposed more of the machinery between those layers. The application had to carry an exact descriptor identity, a carrier had to admit that identity, the Expo provider needed a binding and an environment, and sessions belonged to the running store. Those concepts are defensible—especially for a local-first or supervised runtime—but they were not incidental details. They shaped restarts, schema changes, browser boot, fixture replay, and diagnostics.

That explicitness has a good side. Snapback made provenance and deployment identity visible in a way many hosted backends obscure. The generated app descriptor and the server's carrier are evidence that the client and backend agree about the contract. A production system can benefit from that precision. It is easier to reason about which functions a process is actually serving, and a benchmark can preserve a store and a matching artifact rather than relying on mutable hosted state. The sessions model also provided real backend-mediated authentication instead of a UI-only mock. Snapback's architecture appears to value custody and reproducibility, and those values are meaningful.

The cost is that the boundary currently leaks too often. Additive schema work required a schema-only code-generation bootstrap before functions returning documents could be generated. The published tool rejected the requested `_generated` spelling and required `generated`. A document validator was accepted for a query result but failed when used as a mutation result. The default supervised Expo environment disregarded the provider's explicit binding when its supervisor exchange was unavailable. None of these problems belonged to Clique's domain, yet each demanded careful investigation. Convex has its own deployment and schema constraints, but its common path is better paved: the conceptual surface and the operational surface line up more reliably.

The database model was similarly strong at the center and rough at the edges. Indexed reads, transactions, and live invalidation were natural. Stored structured values, however, had an aggregate size ceiling that was separate from the validators on their children, and the error text did not identify the actual oversized value. Optional persisted fields came back as `null` while their generated TypeScript shape suggested absence. These are exactly the small mismatches that make a typed backend feel less typed under pressure. PostgreSQL with a mature query builder is more verbose and leaves reactivity to the application, but its storage limits, nullability, migrations, and inspection tools are more predictable. Supabase inherits much of that operational clarity, though its row-level security and realtime behavior can distribute product rules across SQL, policies, triggers, and client code.

Firebase offers the opposite trade. It makes realtime synchronization and client writes exceptionally approachable, but complex authorization and relational projections can become difficult to review. Snapback's server-function boundary is a better place for Clique's membership and mutation invariants. The function declares authentication, reads, writes, refusals, arguments, and return validation in one source file. That is safer than allowing clients to compose arbitrary document-store operations. The familiar profile therefore lands in an attractive architectural region: more application-centric than SQL services and more server-governed than Firebase.

Fixture replay revealed another Snapback-specific seam. Multiple headless clients in one Node process shared authentication custody, so retaining one client per actor did not retain one principal per actor. Correct replay required explicitly restoring the intended principal before each actor run. That behavior is understandable if auth state is process-scoped, but surprising when the objects look independent. Convex scripts usually make server-side seeding or per-client identity more explicit; traditional databases make the transaction identity an argument to the seeder. Snapback needs a prominent explanation of custody scope and a purpose-built replay pattern, because event-log replay is precisely where silent principal drift is dangerous.

Presence showed the difference between database reactivity and ephemeral collaboration. Durable live queries were excellent for messages. Typing indicators worked when modeled as expiring rows, but an eager refresh cadence queued enough writes to affect the visibility target. Slowing refreshes while keeping a lease solved the product requirement, yet it felt like fitting an ephemeral concern into a durable transaction system. Firebase and dedicated realtime systems expose presence primitives; many Postgres stacks add a separate broadcast service; Convex applications also commonly model presence above durable storage. Snapback would benefit from either a documented ephemeral channel or explicit guidance on mutation cadence and subscriber-delivery latency.

My overall judgment is positive about the authoring model and cautious about the current product boundary. The Familiar TypeScript profile did not merely rename an unfamiliar system; it removed a great deal of application ceremony and let the domain model stay central. The resulting Clique code is small, reactive, and understandable. What remained was not generic backend work but Snapback work: code-generation staging, carrier lifecycle, admission evidence, auth custody, structured-value limits, and platform binding. Better diagnostics and a more continuous local development loop would turn those from recurring investigations into occasional advanced concepts. Today, Snapback feels like a promising Convex-shaped programming model wrapped in an explicit runtime architecture that has not yet made its common path as familiar as its TypeScript surface.
