## 2026-06-27 — Building v2 to exercise LLP 0021 Phase 0

### What I built

I added `demos/todo-v2/` alongside the original todo demo. It keeps the same
basic app shape but adds a `priority` field and a `setPriority` mutation, then
uses those from both the required headless surface and the optional Contract
surface. The v2 headless suite also asserts the LLP 0021 wrong-native-server
diagnostic:
`SNAPBACK_CAPABILITY_EXACT_NATIVE_ARTIFACTS_UNAVAILABLE`.

The shared `demos/_kit/snapback-contract-boundary.mjs` bridge is now less
hardcoded: it derives query and mutation runtime links from the generated
Contract data manifest and exposes `declaredQueries` / `declaredMutations`.
Todo v2 verifies that `setPriority` appears there and works through Contract
actions and the provider seam.

### What helped from LLP 0021

- **The inventory doc changed the task shape.** Starting from
  `docs/contract-exact-integration.md` made it obvious that a second demo should
  not copy another bridge. The right move was to generalize the shared bridge a
  little, then let v2 prove whether that helped.
- **The product/prototype split stayed visible.** The bridge improvement is
  useful, but it still lives in `demos/_kit/`, and v2 still needed hand-written
  `.contract-meta.ts` sidecars. That is exactly the prototype glue LLP 0021 says
  should disappear later.
- **The new wrong-server diagnostic is real product value.** Adding a headless
  assertion for `/_snapback/admin/__exact/platform-manifest.json` against the
  embedded browser console was straightforward, and the failure was structured
  enough to test without prose scraping.
- **The manifest-derived runtime links caught the right thing.** The v2 Contract
  acceptance checks `surface.declaredMutations` and `surface.links.setPriority`.
  That directly targets the silent failure LLP 0021 names: a Contract surface
  compiling while the runtime bridge exposes only a subset of mutations.

### What still felt bad

- **Descriptor sidecars are still manual.** Adding `setPriority` required
  `setPriority.mutation.ts`, `setPriority.mutation.contract-meta.ts`, import
  semantics in the acceptance harness, and a runtime-links type update. That is
  not product-quality codegen yet.
- **The copied browser dev script was wrong for the current Exact checkout.**
  The package script launched Vite through Node and failed resolving Exact TS
  source as `.js`. Running Vite through `bun --bun` matched the acceptance
  toolchain and brought the browser surface up on port 5175. This is exactly the
  kind of recipe detail LLP 0021 says should become a preset instead of demo
  folklore.
- **The bridge is more generic but not an adapter package.** It now reads the
  manifest, but it still assumes one boundary collection, one authoritative
  query, online-only reconciliation, and hand-written optimistic reducers by
  mutation name.
- **Exact headless log noise remains.** The Contract acceptance still prints
  repeated `Missing exact.dispatch during protocol flush` warnings. Tests pass,
  but the output remains noisier than an agent validation lane should be.
- **HostPlan limits still shape the demo.** Priority works because it is a
  simple string field and patch mutation. Anything more semantic, like sorting
  by priority or filtering incomplete todos without a second query primitive,
  would run into the current v0 authoring limits.

### Snapback observations

The headless side stayed strong. Deterministic reset/seed, explicit
capability gaps, stable diagnostic codes, and the current-value-plus-subscription
seam made v2 quick to validate. The newer generated API/capability artifacts
also gave the original and v2 headless suites a more useful inspection target,
even though v2 intentionally kept its acceptance calls string-based to focus on
the LLP 0021 bridge behavior.

### Contract/Exact observations

Contract handled the richer row shape without drama: `todo.priority`, ternary
styling, priority buttons, and extra actions compiled and mounted. The real
friction was not Contract expressiveness; it was still packaging and generated
binding glue.

### Compared to React + Convex / Supabase

Convex would make the typed function-reference and generated-client parts feel
more finished today. Snapback is still catching up there. Where Snapback felt
better for this exercise was diagnostics: the native Exact wrong-shape case and
artifact-version mismatch were structured facts, easy to assert in a headless
suite. Supabase would make simple table CRUD fast, but the Contract action plus
server-authoritative mutation flow here stayed more agent-checkable than direct
client table writes.

### Net

Todo v2 was useful. It did not prove LLP 0021 is implemented beyond Phase 0, but
it did prove the Phase 0 work helped: the inventory prevented bridge copying,
the new diagnostic became a testable acceptance fact, and the second demo forced
the shared bridge to expose the full generated mutation set instead of a
handwired subset.

## 2026-06-27 — Extending v2 into LLP 0021 Phase 1

### What I built

I extended `demos/_kit/codegen.mjs` so the demo codegen now emits
`snapback/generated/contract/` modules alongside the JSON manifests:
`runtime-links.ts`, one ordinary query or mutation module per generated
function, and one `.contract-meta.ts` sidecar per binding. Todo v2 now imports
those generated modules directly from its `.contract` file and no longer has a
demo-local `surfaces/contract/data/` sidecar directory.

The v2 Contract acceptance now checks that every imported binding points at
`../../snapback/generated/contract/`, that the generated manifest declares the
query/mutation set, and that no ordinary demo-local Contract sidecars remain.

### What helped from LLP 0021

- **The Phase 1 wording gave a clear target.** The useful distinction was
  "Snapback owns the projection, Exact owns the manifest shape." That kept this
  slice focused on generated modules and descriptors instead of inventing a new
  Contract schema.
- **Generated imports removed a real copy step.** Adding a mutation no longer
  requires creating local `.query.ts` / `.mutation.ts` and `.contract-meta.ts`
  files under the Contract surface. That was one of the most obvious integration
  glue seams from the first v2 pass.
- **The result is easier for agents to inspect.** The `.contract` file now says
  exactly which generated Snapback binding it imports, and the acceptance suite
  can assert that path mechanically.

### What still felt bad

- **The bridge is still a prototype.** Runtime hydration, optimistic reducers,
  provider lifecycle, and reconciliation still live in
  `demos/_kit/snapback-contract-boundary.mjs`, not an adapter package.
- **The compiler check still uses manual `importSemantics`.** The browser path
  resolves generated modules through Vite/Exact, but the headless Contract
  acceptance still supplies semantics directly. That means it proves path
  discipline and generated artifacts, not full Exact project-check conformance.
- **Only v2 moved.** The original todo surface and admin UI still have
  hand-written descriptor sidecars, so this is a foothold rather than a cleanup
  across all surfaces.
- **Staleness diagnostics are not done.** The generated files carry the same
  `inputsHash` lineage through the manifests, but a deliberately stale
  descriptor module does not yet produce a standardized structured diagnostic.

### Net

This made LLP 0021 materially more useful than the first pass. Phase 0 reduced
confusion and caught wrong-server-shape failures; this Phase 1 slice removed a
real duplicated artifact path from Todo v2. The remaining friction is now more
clearly adapter and conformance work, not "every demo has to hand-copy sidecar
files."

## 2026-06-27 — Moving the bridge into a package-equivalent adapter

### What changed

I moved the shared Contract bridge out of `demos/_kit/` and into
`packages/snapback-contract/` with a private `@snapback/contract` package shape.
Todo v2 now imports `createSnapbackContractSurface` from that package-equivalent
module, and its browser surface resets generated runtime links on HMR dispose.

The original todo demo also moved to generated Contract binding modules, so both
todo demos now have the same pattern: generated sidecars under
`snapback/generated/contract/`, no local `surfaces/contract/data/`, and a shared
adapter outside demo-local kit code.

### Was this easier?

Yes, but in a narrow way. The second move was easier than the first: once v2 had
proved generated modules, converting the original todo surface was mostly import
rewriting plus an acceptance assertion. The package-equivalent adapter also made
the product/prototype line less fuzzy: tests now import from
`packages/snapback-contract/`, not from a demo helper with a bridge-shaped name.

### What still is not done

This is still not the full LLP 0021 finish line. The adapter has no Exact-owned
provider conformance suite yet, the optimistic reducers are still mutation-name
based, stale generated Contract descriptors do not emit a standardized
structured diagnostic, and the admin UI still has its own bridge and sidecars.
The work did remove demo-local sidecar copying for both todo demos, though, which
was one of the concrete frictions this diary was meant to test.

## 2026-06-27 — Stale Contract artifact diagnostics

### What changed

I added `validateSnapbackContractArtifacts` to the shared adapter. Browser boot
and acceptance now pass the generated `artifacts.json`, schema manifest, and
function manifest alongside the Contract data manifest, so the adapter can
compare `inputsHash`, schema hash, bundle hash, manifest version, and descriptor
artifact coverage before it mounts a Contract surface.

The Todo v2 Contract acceptance suite now corrupts the generated Contract data
manifest `inputsHash` on purpose and expects
`SNAPBACK_STALE_CONTRACT_DATA_INPUTS_HASH` with
`details.target_surface = "Contract/Exact"`.

### What felt better

This was one of the places where LLP 0021 helped directly. Because Phase 1 had
already forced the generated Contract projection to share lineage with the
Snapback artifact index, adding the diagnostic was mostly comparison code in the
adapter instead of another surface-specific workaround.

### What is still not done

This does not replace the Exact-owned provider conformance suite, and it does
not prove that Exact project checks validate descriptor module contents. It does
mean stale generated Contract data no longer waits for a browser smoke test to
fail opaquely.

## 2026-06-27 — Provider conformance discovery

### What changed

I added `packages/snapback-contract/exact-conformance.mjs`, a Snapback-side probe
for the Exact-owned provider conformance gate from LLP 0021 / Exact 0263. It
resolves the local Exact checkout, inspects `exact-verify.json` for
`data-provider-conformance`, searches known candidate suite paths, and reports
`SNAPBACK_CAPABILITY_EXACT_PROVIDER_CONFORMANCE_MISSING` while the suite is not
there.

### Was this useful?

Yes, but as honesty plumbing rather than ergonomics. The probe makes the missing
Exact suite a structured fact instead of a vague TODO. It also keeps me from
declaring victory based on the todo provider seam tests, which are useful
Snapback acceptance coverage but not the canonical Exact conformance suite.

### What still felt bad

The real integration-glue friction is still upstream of this probe: Exact has
runtime DataProvider primitives and mock-boundary tests, but not the reusable
provider-conformance target Snapback can import or run. The Snapback side can
now discover and fail that absence cleanly, but it cannot turn local provider
behavior checks into Exact-owned conformance without the Exact artifact.

### Net

LLP 0021 helped by naming the ownership boundary sharply. The right move was a
small discovery/reporting tool, not another local harness. Phase 2 remains open
until Exact lands the reusable suite and Snapback wires a real adapter fixture
through it.

## 2026-06-27 — Passing Exact-owned provider conformance

### What changed

Exact now has a registered `data-provider-conformance` check and reusable
conformance helpers under `packages/exact-contract/src/conformance/`. I updated
Todo v2 with `tests/acceptance/provider-conformance.mjs`, which starts a live
Snapback server, creates the package-owned Contract provider, and calls Exact's
`assertDataProviderConformance` with a `snapback-todo-v2-provider` fixture.

The Snapback discovery probe now passes in both modes:
`node packages/snapback-contract/exact-conformance.mjs --require` sees the Exact
check, and `--run` invokes Exact's own `bun scripts/exact-verify.mjs --check
data-provider-conformance --json` lane.

### What felt better

This was the first LLP 0021 Phase 2 task where the ownership boundary paid off
directly. I did not need to invent a Snapback-local provider harness or decide
what Exact "should" test. The fixture work was mostly translating Todo v2's
live server state into the generic Exact fixture shape: one primary query, one
successful mutation, one failed mutation, row sync state, force-state behavior,
and disposal.

The adapter work from the previous passes also helped. Because Todo v2 already
used generated runtime links and the package-equivalent provider seam, the
conformance runner could exercise product-shaped code instead of another demo
copy of the bridge.

### What still felt bad

The fixture has to adjust expectations dynamically because Snapback owns row
ids, timestamps, and versions on the server. That is correct behavior, but it
adds a little glue around the generic fixture: after `createTodo` and
`setPriority`, the runner re-queries Snapback and fills the expected rows with
the authoritative server values.

The other friction is still packaging. The runner imports Exact's TypeScript
source from a sibling checkout. That is acceptable for this local integration
gate, but it is not a stable installed-package story yet.

The conformance fixture also reflects the current adapter shape: one live query,
one boundary collection, Online capabilities, and server-authoritative
reconciliation. It is a real Exact-owned provider pass, not a claim that the
adapter is Parity/local-first or generalized beyond the current manifest shape.

### Net

This made LLP 0021 materially easier to continue. The earlier discovery work
prevented a false local victory, and once Exact landed the suite, the next step
was clear: wire a Snapback fixture into the Exact-owned gate and document the
remaining glue. The concentrated friction is now narrower and more concrete:
stable Exact package consumption, generated descriptor validation by Exact
project checks, and the remaining admin-specific client/view-model shaping.

## 2026-06-27 — Exact descriptor project checks

### What changed

Todo v2 now has a descriptor-only acceptance runner:
`bun demos/todo-v2/tests/acceptance/contract-descriptors.mjs`. It imports Exact
through `@exact/contract` package exports when possible, falls back to the local
Exact checkout package root, resolves generated query and mutation descriptor
modules through Exact static import semantics, and runs Exact's data doctor
against Snapback's generated Contract data manifest.

The generated query descriptor sidecars now include a `result` type and a
generated row shape. Exact uses that result descriptor while analyzing `async
ready` rows, so changing the Contract template from `todo.priority` to
`todo.notAField` fails with `shape_unknown_member` before any browser smoke or
live server test runs.

### Was this easier?

Yes. LLP 0021 made the next move obvious: validate the generated Contract import
surface with Exact, not with another Snapback-local artifact check. The code
ended up small once Exact had a single place to preserve a query descriptor's
`result` and inject it into the ready-slot row environment.

The package-export resolver also reduced one bad kind of glue. Provider
conformance and descriptor checks no longer import Exact helper files by
absolute `packages/exact-contract/src/...` paths. That is not the same as
stable installed-package consumption yet, because this checkout still falls
back to a sibling Exact package root, but the boundary now follows Exact's
`package.json` export map.

### What still felt bad

The server-backed provider conformance runner is still sensitive to local Ibex
Hermes setup. The vendored Snapback Ibex tree has headers, an iOS xcframework,
and `hermesc`, but not the macOS framework that `vendor/ibex/build.rs` requires
for Cargo tests. Pointing the runner at the peer
`/Users/ccheever/projects/ibex` artifacts first got through compile preflight
but exposed a runtime dyld failure: Cargo could compile, then the server process
exited looking for `hermesvm.framework`.

I patched the shared server helper to carry the resolved Hermes framework
directory into `DYLD_FRAMEWORK_PATH` for spawned Cargo runs. After that,
server-backed provider conformance and the full Contract acceptance both passed
with only the peer `HERMES_INCLUDE_DIR`, `HERMES_LIB_DIR`, and `HERMESC`
overrides. That is better, but it is still too much local setup for ordinary
agents; the descriptor-only Exact gate remains the cleaner no-server check for
generated descriptor correctness.

### Net

This pass made Phase 1 meaningfully less hand-wavy. Generated descriptors are
now checked as Contract modules by Exact, and row-shape mistakes are caught by
Contract analysis before the browser path. The remaining LLP 0021 friction is
mostly packaging and lifecycle work: installed Exact package consumption, the
full LLP 0012 race-handling adapter contract, and a deliberate decision about
whether admin-specific client/view-model shaping becomes a package or remains
the system-app exception.

## 2026-06-27 — Adapter rollback and pending semantics

### What changed

I tightened `packages/snapback-contract` so runtime-link mutations return their
tracked promise and provider mutations use the same pending set. That gives the
adapter one combined `pendingCount()` across Contract actions and provider
calls, instead of only counting action-link background work.

I also added `demos/todo-v2/tests/acceptance/adapter-semantics.mjs`, a no-server
runner that uses Exact runtime plus an in-memory Snapback-like client. It holds
a rejected `createTodo` mutation open long enough to observe the optimistic row,
then releases the rejection and verifies the adapter republishes authoritative
rows and records `SNAPBACK_CONTRACT_MUTATION_FAILED`. The same runner holds one
runtime-link mutation and one provider mutation at once and verifies
`pendingCount()` reports both.

### Was this easier?

Yes. LLP 0021's checklist made it obvious which parts of the race contract were
actually reachable in the current adapter. Rejected optimistic rollback and
combined pending counts are adapter-owned today, so they got a tight no-server
test. Pre-subscribe delta buffering, auth buffering, and reconnect resync are
wire-level behaviors for a future live WebSocket provider path, so I left those
open instead of pretending a mock-boundary test proved them.

### What still felt bad

The server-backed Contract runner is slower and depends on the local Ibex/Rust
tree being coherent. While writing this slice I briefly hit dirty-tree Rust
compile errors in `src/runtime.rs` around `CapturedReadDependency` initializers;
after the tree was coherent again, the full Contract and provider conformance
runners passed. The no-server runner still earned its keep because adapter
semantics can be tested cheaply and deterministically without involving local
server startup.

### Net

This reduced the LLP 0021 Phase 2 gap without overclaiming. The adapter now has
explicit coverage for rejected mutation rollback/republication and combined
pending counts. The remaining Phase 2 work is the live-wire race contract:
pre-subscribe delta buffering, auth buffering, reconnect resync, and
empty-array-on-subscription-error behavior in the path that will actually own
those events.

## 2026-07-09 — ENG-23899 Stage 1: todo-v2 becomes the LLP 0328/0329/0051 program demo

### What I did

Todo-v2 is now Stage 1 of the program proof app (Exact LLP 0329 / snapback
LLP 0051 / Exact LLP 0328, tracker ENG-23890): a Contract UI todo app backed
by snapback mutations authored on the `define.mjs` builder, verified
end-to-end. Concretely:

- Added a `contract` block to `surfaces/contract/todo.contract` claiming the
  core behaviors: `has`/`press`/`change` on the input and Add button, a
  dynamic `count item testId="^todo-row-" = todos.length`, `when`-gated
  enabled/disabled state claims, plus the statically enforced
  `action submit writes draft` and `derive canSubmit depends only on draft`.
  Compiles clean against the generated descriptors (all 9 clauses in the IR).
- Migrated the browser surface off the deleted `SNAPBACK_EXACT_ROOT`
  source-alias bridge to the ENG-22480 registry model (all-aboard shape):
  npm alias deps on `@ccheever/exact-*@0.1.0`, committed `bun.lock` as the
  pin, `exact.pin.json` deleted, the exact-devtools patch carried over.
- Adopted all-aboard's direct-API-origin pattern (`__SNAPBACK_API_ORIGIN__`
  define) after re-hitting the bun-vite proxy bug: a hung `/snapback` live
  WebSocket upgrade wedges *subsequent proxied HTTP* too — boot works, then
  every mutation fails with `Failed to fetch`.

### Verification

- `contract.mjs` acceptance 14/14 against a live server (compile, mount,
  optimistic add, server-authoritative priority, toggle/reprioritize/delete,
  provider seam, rejected-mutation diagnostics, pending counts);
  descriptors 2/2, adapter semantics 2/2, provider conformance PASS,
  headless 16/16; production `vite build` passes.
- Real-browser round-trip via CDP on the dev surface: type + Add (3 → 4
  rows, optimistic then settled), toggle (○ → ✓), delete (back to 3),
  server-side rows confirmed authoritative afterwards.

### What felt good / bad

Good: the generated-descriptor path held up — adding a contract block
required zero backend or codegen changes, and the compile-time
`shape_unknown_member` analysis plus `writes`/`depends only on` enforcement
give real claims for free. The registry migration was mechanical because
all-aboard had paved it.

Bad: the surface silently broke when Exact deleted the source-alias
machinery the pin pointed at — pin-file drift detection can't catch "the
consuming mechanism is gone". Registry + lockfile is structurally better.
The bun-vite WS proxy wedge cost the most time; the failure smells like a
data bug (mutations fail, queries fine) when it is actually transport-order
(boot's HTTP preceded the WS upgrade; everything after it wedged). The
plain-browser tab also does not register as an Acto target
(`NO_REGISTERED_TARGET` on the relay), so agent-API verification of the
*live* page still goes through CDP; the exact_tree / contract-witness loop
applies once the demo graduates onto an Exact host (Stage 2+).
