## 2026-07-29 — staged Linux package and external Todo confirmation

This was a clean external confirmation rather than another source-tree run. I
built frozen commit `4e5da63c33064082c73359f0ee02efcd11e360ff` in a detached
Linux worktree, staged the seven-package host closure as
`0.1.1-llp0102.1` with the publisher's dry-run mode, ran the official staged
cold-install proof, and then copied the frozen Todo work directory outside the
repository. The external copy generated and built offline and ran on assigned
ports `33101` and `43101` with an isolated HOME, XDG roots, npm cache, runtime
directory, browser state, and receipt directory.

The result was 11 passes, 3 declared gaps, and no failures across all 14
expected checks. Authenticated membership reads, outsider refusal, CRUD,
native push, concurrent conflict handling, ordering, logout, revocation,
performance sampling, backup evidence, and exact cleanup all passed. The three
gaps are product gaps rather than harness skips: the shipped protected Todo
query is not locally runnable or retainable, the React Online surface has no
durable offline mutation outbox, and reconnect therefore has no queued work to
settle. It does return to the 100-row authoritative view without creating the
attempted offline row.

What felt good:

- The staged package closure is capable of carrying the full app loop. The
  official cold proof passed offline codegen, packaged CLI introspection,
  runtime doctor, scaffold/generate, deploy build, managed dev lifecycle, and
  browser bundling without a sibling source checkout.
- The package-only server produced strong provenance. Both the original start
  and restart reported the exact frozen commit, clean source, and release
  profile, and `/inspect` matched the generated app and bundle hashes.
- Snapback's executable-artifact permission check correctly refused a
  group-writable startup carrier. That is the right safety result.
- The Todo semantics remained substantial after externalization: sessions,
  membership enforcement, server-owned writes, durable live updates,
  concurrent mutation behavior, revocation, and cleanup all exercised the real
  installed backend rather than a substitute wrapper.

What felt bad or frustrating:

- Linux bootstrap was much harder than package consumption. No prepared binary
  matched the frozen pinned Hermes revision. A prepared older Hermes tree was
  correctly rejected by provenance, but reaching a valid build required the
  exact Hermes patch stack plus lane-local ICU and curl development files.
  The safety was good; the amount of host surgery was not.
- The first package dry run under isolated HOME could not find Volta's Node
  until `VOLTA_HOME=/home/ccheever/.volta` was bound explicitly. The packaging
  path is sensitive to tool-manager state in a way a clean-machine workflow
  should make obvious.
- `@snapback/client/online` is an exported runtime path but the staged client
  package ships no declaration for it. The external TypeScript build failed
  with TS7016. I had to add a receipt-tracked declaration shim that changes no
  runtime behavior. Snapback should ship types for every public export.
- The startup-carrier refusal reported only that the artifact could not be read
  safely. The cause was the worker's `0002` umask creating a group-writable
  file; an explicit `0022` fixed it. The refusal should retain its security
  posture while naming the failed mode/ownership/ACL predicate.
- Raw `/inspect` on a sessions target requires
  `x-snapback-auth-client-protocol: 1`. The returned diagnostic was excellent,
  but package-owned lifecycle/provenance helpers should make the correct probe
  available so external harnesses do not have to rediscover protocol headers.
- Installed `snapback stop` closes the server and removes the ready and
  impersonation files, but it leaves the owner-only `.secret-read-root` file
  until the arm removes its scoped runtime directory. Final cleanup was exact
  and proved the file absent, but `stop` alone does not provide a complete
  lifecycle cleanup.
- The frozen performance receipt hardcodes `Mac17,3 arm64` even though this run
  executed on Minisforum Linux x86_64. The raw samples are retained with a
  companion correction, but they must be scored at reduced confidence or
  regenerated by a centrally corrected evidence path.

Compared with Convex or Supabase, the strongest Snapback-specific feeling here
was how much authority, bundle identity, and cleanup detail can be proven
locally from installed artifacts. The weak side is that packaging and host
lifecycle still expose internal seams that a mature default backend should
hide. The biggest product gap remains offline behavior: an online Todo is
solid, but this frozen surface does not yet make a resilient offline Todo feel
native.

Improvement candidates for synthesis:

1. Ship TypeScript declarations for every exported client subpath, starting
   with `@snapback/client/online`.
2. Provide a package-owned external acceptance/lifecycle API that starts,
   provenance-checks, and stops the installed runtime without demo-kit or
   source-tree knowledge.
3. Make secure startup-artifact diagnostics state the rejected inode predicate.
4. Have `snapback stop` retire every process-bound secret sidecar it created,
   or return a structured cleanup plan naming deliberate retained state.
5. Make the Linux runtime/package preparation reproducible without manual
   dependency extraction and tool-manager environment repair.
6. Add a protected-query retention policy and durable offline mutation outbox
   to the primary React surface.
7. Derive performance environment metadata at runtime; never hardcode a machine
   profile in an acceptance runner.
