# Knockoff

Knockoff is an Expo SDK 57 social app with a live feed, profiles, posts,
replies, likes, Apple login, and Google login. It uses Snapback's own sessions
and application custody. Clerk, Firebase Auth, and Supabase Auth are not
dependencies.

## What the demo proves

The checked acceptance path proves the current local broker seam:

1. A server-only broker verifies an Apple or Google identity fixture.
2. The broker derives a stable opaque email from immutable issuer and subject.
3. Snapback issues a one-time email-code exchange through its local capture
   path.
4. `signInWithExternalCode` installs the resulting session through the
   application Auth facade and its ordinary coordinator custody.
5. `ensureProfile`, `createPost`, and `toggleLike` derive the actor from
   `ctx.auth.userId`. The client never submits an author or liker identity.
6. Repeating Google login returns the same Snapback principal.

The default `auto` profile needs no provider account. It opens Snapback
Development Auth in the system browser and uses hermetic Apple and Google
identities behind the same one-use completion protocol intended for the hosted
shared broker. The local broker does not claim to authenticate a real Apple or
Google account.

After app-owned provider configuration and the installed native build both
verify, `auto` selects the native Adapter. A native runtime error is final for
that attempt. Knockoff never falls back to shared credentials after native auth
starts.

## Run the proof

From the repository root, the catalog commands are:

```sh
bun run --cwd demos/knockoff start
bun run --cwd demos/knockoff test
```

Generate the backend, typecheck the Expo app, and run the social-auth witness:

```sh
cd demos/knockoff
bun install
bun run generate
bun run typecheck
SNAPBACK_RUNTIME_BINARY=/path/to/qualified/snapback bun run test
```

The witness starts an isolated sessions-mode server and a server-only identity
broker. It signs in with both provider fixtures, creates principal-bound
profiles, writes a post, checks the live feed, signs out, and proves stable
repeat login.

## Run the app locally

Use three terminals. Start Snapback without the Expo supervisor's automatic
development session so that the app opens on its login screen:

```sh
cd demos/knockoff
node ../../packages/snapback-cli/cli.mjs dev snapback \
  --ready-file .snapback/dev.ready.json
```

Start the server-only broker:

```sh
cd demos/knockoff
SNAPBACK_KNOCKOFF_READY_FILE=.snapback/dev.ready.json bun run broker
```

Start Expo:

```sh
cd demos/knockoff
EXPO_PUBLIC_KNOCKOFF_DEPLOYMENT_PROFILE=development \
EXPO_PUBLIC_KNOCKOFF_AUTH_ORIGIN=http://127.0.0.1:3777 \
bun run start:dev-client
```

Tap either provider button. The browser page is visibly branded Snapback
Development Auth and returns only a one-use completion code to
`knockoff://auth/shared`.

The loopback broker origin works from the iOS simulator and web on the same
Mac. Android emulators and physical devices need a reachable development
origin. Do not put the Snapback admin token or impersonation capability in an
`EXPO_PUBLIC_*` variable.

## How profile selection works

Knockoff calls one controller for both providers. The resolver freezes one
Adapter before sign-in:

- tests use the synthetic Adapter;
- local development uses shared browser auth until native readiness passes;
- owner-authenticated previews require an expiry and use at most 100 rehearsal
  users;
- staging and production refuse shared credentials; and
- app-owned configuration plus a matching native-build probe selects native
  auth.

The broker enforces shared-profile admission again from server-only deployment
configuration. The client resolver is UX, not the security boundary. Preview
admission needs a server-side owner authorization flag and unexpired timestamp;
staging and production never construct the shared Adapter.

The build probe uses native URL schemes generated by `app.config.ts`. Changing
provider configuration in Metro cannot forge the probe. Rebuild the development
client to activate a newly configured native Adapter.

Shared and app-owned identities use separate provider installations. Switching
profiles signs out incompatible custody. It does not merge accounts by email.

## Configure real Apple login

Real Apple login requires an app-owned Apple Developer registration. Set:

- create an explicit App ID whose bundle identifier is
  `com.snapback.knockoff`, enable its Sign in with Apple capability, and rebuild
  the development client after the registration is active;
- `KNOCKOFF_APPLE_CLIENT_ID` on the broker to the app's bundle identifier;
- `EXPO_PUBLIC_KNOCKOFF_APPLE_CREDENTIALS=auto` or `app-owned` in Metro;
- `EXPO_PUBLIC_KNOCKOFF_APPLE_NATIVE_CONFIGURED=1` in Metro only after the
  Apple Developer registration above is active;
- `KNOCKOFF_BROKER_IDENTITY_SECRET` on the broker to at least 32 random
  characters.

The app uses `expo-apple-authentication` on iOS. It sends the identity token,
authorization code, nonce, and first-login name to the broker. The broker
verifies the token signature, issuer, audience, expiry, and nonce against
Apple's JWKS.

This demo does not retain an Apple refresh token or implement provider
revocation during account deletion. LLP 0151 requires that behavior before an
Apple provider can become a production Snapback capability.

## Configure real Google login

Real Google login uses `@react-native-google-signin/google-signin`. Create the
platform client and server client registrations, then set:

- `EXPO_PUBLIC_KNOCKOFF_GOOGLE_CREDENTIALS=auto` or `app-owned`;
- `EXPO_PUBLIC_KNOCKOFF_GOOGLE_IOS_CLIENT_ID` on iOS;
- `EXPO_PUBLIC_KNOCKOFF_GOOGLE_ANDROID_CONFIGURED=1` after Android package and
  signing-certificate registration;
- `EXPO_PUBLIC_KNOCKOFF_GOOGLE_SERVER_CLIENT_ID` in the app;
- `KNOCKOFF_GOOGLE_CLIENT_ID` on the broker, with the same server client id;
- `EXPO_PUBLIC_KNOCKOFF_GOOGLE_IOS_URL_SCHEME` in Metro on iOS;
- `KNOCKOFF_GOOGLE_IOS_URL_SCHEME` at build time, with the same reversed client
  id scheme;
- `KNOCKOFF_BROKER_IDENTITY_SECRET` on the broker; and
- a rebuilt development client.

The native SDK returns an ID token to the app. The app sends it to the broker,
which verifies the Google signature, issuer, audience, and expiry before
issuing the Snapback exchange. Expo web can use the app-owned browser code and
PKCE Adapter when `EXPO_PUBLIC_KNOCKOFF_GOOGLE_WEB_CLIENT_ID` is set.

## Security boundary

Provider tokens stay in the broker process. The app receives only a short-lived
Snapback exchange object. The broker alone holds the local capture authorities.
The stable provider mapping uses issuer and subject, never mutable email.

This is still a local demo. The shared browser page uses hermetic identities,
and the broker uses Snapback's non-production capture mailbox to enter an
ordinary session. It proves profile resolution, server-side deployment
admission, and completion mechanics, not hosted owner authentication or
Snapback-owned Apple or Google credentials. It does not claim hosted Auth,
account linking, Apple revocation, or production challenge delivery.
