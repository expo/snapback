# Review: LLP 0015 Demo Application Suite

**Reviewed:** `llp/0015-demo-application-suite.plan.md`
**Round:** 1
**Date:** 2026-06-26
**Reviewer:** Codex / AGENTS
**Outcome:** Revised in place

## Overall Assessment

This is a good Plan and it answers the user's main design question correctly:
Snapback should not make ordinary core development depend on an undeclared local
Exact checkout, and it should not force Exact into the repo as a mandatory
submodule. Exact should be an optional, capability-probed external toolchain
until a specific CI or release need justifies a vendored/pinned form.

The document's strongest idea is treating demo apps as acceptance fixtures with
one shared backend and multiple thin surfaces. That aligns with LLP 0010 and
LLP 0012, and it avoids repeating the Valet pattern where every demo had its
own bridge, aliases, and local priming code.

## Strengths

- Separates shared Snapback backend facts from framework-specific surfaces.
- Keeps headless validation runnable without Exact installed.
- Makes Contract/Exact the intended primary product surface without blocking
  early Snapback core acceptance on external Exact readiness.
- Chooses capability-based Exact resolution over path-based resolution.
- Names the todo demo as a real floor app, not a marketing sample.

## Concerns

- The original draft blurred staging: it said Contract/Exact was the primary
  surface but did not say when it becomes required versus expected-missing.
  Without that, CI could accidentally treat a skipped Contract surface as a
  passing integration.
- The demo manifest fields were too light compared with LLP 0012's artifact and
  capability vocabulary. A manifest needs target profile, artifact schema
  version, surface requirement level, staleness policy, and expected diagnostic
  codes if agents and CI are supposed to reason about it.
- The Exact resolver had good source precedence but not enough skip/fail
  semantics. A stale peer checkout and a missing checkout should produce
  different facts, but a required Contract surface must still fail on either one
  if the capability is absent.

## Revisions Applied

- Added **Phase Gates**: headless core, first visual surface, Contract/Exact
  surface, and cross-surface integration.
- Strengthened `demo.snapback.json` requirements with artifact schema version,
  target profile, surface requirement levels, generated-artifact staleness
  policy, and expected diagnostics.
- Added Contract/Exact capability and version requirements to the Exact
  dependency policy.
- Added explicit skip validity rules and made required-surface capability
  absence a failure.
- Clarified that V0 todo requires headless or React, with Contract/Exact
  becoming required at Phase 2.

## Suggestions Not Applied

- A concrete JSON schema for `demo.snapback.json` would be useful, but it should
  probably land with the first demo implementation rather than in this Plan.
- A named diagnostic code family for demo/toolchain gaps would be useful, but
  the exact code names should be coordinated with the LLP 0012 diagnostic schema.

## Open Questions

- Should the first implementation include a `demo.snapback.schema.json` file, or
  should the manifest schema be generated from Rust/TypeScript types?
- What is the first stable name for the Exact capability that means
  "Contract data binding can mount a Snapback query cell"?
- Should the Exact integration pin live in the demo manifest, CI config, or a
  separate lockfile generated by the resolver?
- When Contract/Exact reaches Phase 2, should React remain required for the
  cross-surface check or become optional?

## Status Recommendation

Keep LLP 0015 in `Draft` until the first `demos/todo` directory lands. After the
demo manifest and resolver shape exist in code, move the document to `Review`.

The LLP process also recommends a GPT review unless this Codex/AGENTS review is
the GPT review the author wanted.
