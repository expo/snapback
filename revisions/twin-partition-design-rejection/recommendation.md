The strongest source evidence is the second executable-store construction. `TwinStore.sync` builds a new `ClientStore`, then replays the carrier's rows, overlays and answers into it (`twin-store.ts:59–111`). Its `row` and `answer` paths reconstruct effective images, negative receipts, member pools and issuing-key callbacks (`:131–210`). `ClientStore` separately owns tables, indexes, coverage, directories and prediction rollback (`evaluator/src/store.ts:20–122`). The carrier already owns current rows and receipt/proof membership, with a live fact index (`carrier-index.ts:17–47,136–183`). This is real cross-layer materialization, even after the successful immutable image/range sharing.

The proposed replacement would let Runner read a committed prepared partition directly, plus an indexed sparse overlay for affected prediction rows. Standalone ClientStore would construct the same kernel in memory; PersistentRangeStore would supply its persistence transaction. Twin would retain public revisions, freshness and cursor behavior as a facade. Generic custom sources would enter through the existing isolated JSON boundary, and format5 snapshots/changes would remain exact boundary outputs. All implementation and adapters stay in the five-root measurement. No native offload, lazy code loading or omitted export is involved.

**What must actually disappear:** Twin's second snapshot-to-store population and row/answer admission bridge; a second ownership/update pipeline for the same current rows; and a substantial part of the two receipt-owner maintenance paths. Replacing those methods with callbacks into the same old bodies does not count. Durable contradiction facts and query completeness must remain distinct fields/views, with their separate sequence, owner and authority rules. This proposal does not flatten `applyCoverage` or move network retry/epoch/outbox orchestration into a universal reducer—the earlier source analysis correctly found those phases necessary.

There is enough gross code to ask the question, not to promise the answer. Historical minified contributions are range-store 26,896; ClientStore 7,708; TwinStore 7,295; CarrierIndex 6,238; CoverageIndex 5,561. Those five total **53,698 minified bytes**, not removable bytes or additive gzip. Eliminating only TwinStore is plainly too small a basis for a >10 KB gzip claim. The opportunity requires removing whole ownership/materialization paths across several layers while adding much less replacement code.

The decisive uncertainty is that much apparent duplication is necessary temporal state. Current rows, immutable historical facts and predicted rows cannot simply share one membership. FactIndex already reuses HeldIndex code and already shares its live/sequence trees (`fact-index.ts:13–17,41–45`); fewer index instances alone saves **zero copies of that implementation**. Coverage's expected issuing positions, losses and exhaustion summaries are not interchangeable with CarrierIndex's complete-extent contradiction evidence. A sparse overlay also needs ordered merge, scope-authority invalidation and bounded reclamation, which can consume the supposed savings. Historical ~52 MB carrier/~79.5 MB Twin heaps do not establish removable gzip or current resident improvement.

My recommended next deliverable is therefore a short **elimination proof**, not code: one retained-state/ownership diagram, exact old methods/fields to delete, every replacement operation and custom/standalone adapter, and a walkthrough of FULL/replay, split-swap movement, denied/partial/exhaustion, prediction rollback and cold reopen. Reject that design before implementation if it merely moves the existing three stores behind an interface, requires history scans, or can delete only the ~7.3 KB minified Twin layer. A promising plan would still need the original exact-output, 524,286-absence, movement, authority/GC/isolation controls and one unchanged full measure later; none is newly authorized or executed here.
