# Clique on Quarry — M1: Accounts and profiles (media-free)

```schema
-- Milestone 1 baseline (first milestone: no NEW/CHANGED marks yet).

use identity
  -- email+password credentials (minimum password length 8 configured on the
  -- kind), expiring session tokens, server-side logout revocation; provides
  -- `viewer` to every program. Duplicate email is refused by the kind at
  -- signup. Credentials and tokens never appear in declared tables.

table users:
  displayName: text <=50
  handle: text <=20
  bio: text <=200 ?
  location: text <=50 ?
  link: text <=200 ?                 -- one URL; well-formedness is client-validated
  unique handle
  read r <- public                   -- declared disclosure: profiles are world-readable
  insert r <- r.id = viewer          -- you may only create your own profile row
  update (old, next) <- old.id = viewer   -- own-profile editing only
  -- no delete rule: profile deletion is not in this product; deletes refuse
```

```programs
-- Sign-up flow: the identity kind creates the account (email+password) and
-- issues the session; the client then claims the profile row. `viewer` may
-- dangle (no users row yet) until claimProfile commits; reads through it
-- propagate absence and the client routes to the claim screen.

mutation claimProfile(displayName: text <=50, handle: text <=20,
                      bio: text <=200 ?, location: text <=50 ?,
                      link: text <=200 ?) -> users:
  require displayName != '' else EMPTY_NAME
  require matches(handle, '^[a-z0-9_]{3,20}$') else BAD_HANDLE  -- INVENTED: no length/charset predicate exists in the language
  +users { id: viewer, displayName, handle, bio, location, link }
  -- duplicate handle -> unique-key refusal at commit (client shows the error);
  -- claiming twice -> implicit-id uniqueness refusal. No check-then-insert.

mutation updateProfile(displayName: text <=50 ?, handle: text <=20 ?,
                       bio: text <=200 ?, location: text <=50 ?,
                       link: text <=200 ?) -> users:
  u = users[viewer]! else NO_PROFILE
  require (displayName ?? 'x') != '' else EMPTY_NAME
  require matches(handle ?? 'aaa', '^[a-z0-9_]{3,20}$') else BAD_HANDLE  -- INVENTED: same predicate as claimProfile
  ~users[u] {
    displayName: displayName ?? .displayName,   -- absent argument = keep current value
    handle:      handle ?? .handle,
    bio:         bio ?? .bio,
    location:    location ?? .location,
    link:        link ?? .link,
  }
  users[viewer]! else NO_PROFILE     -- result: the row as edited (re-read; patch result is unspecified)

query me():
  users[viewer] { * }                -- absent until claimed; client routes to the claim screen on absence

query profile(u: users):
  users[u]! else NOT_FOUND { * }

query profileByHandle(handle: text <=20):
  users[handle = handle] { * }       -- point read by the unique key; absent -> client renders not-found
```

```boundary
identity: `use identity` — signup/sign-in with email+password (min length 8 is kind config), expiring sessions, server-side logout revocation, duplicate-email refusal; provides `viewer`; the data plane never sees credentials or tokens.
live transport: queries are live subscriptions — the engine pushes changes (acceptance 5's cross-client profile edit); no polling or refresh logic in the data plane.
client custody: session-token persistence across reloads (acceptance 3) belongs to the identity kind's client SDK; logout invalidation (acceptance 4) is the kind's server-side revocation.
client validation: handle charset/min-length and URL well-formedness are mirrored client-side; the server-side charset check rests on the single INVENTED `matches` predicate.
schedules / channels / effects: none needed in M1 (session expiry is the identity kind's own).
```

```notes
1. Profiles ARE the users table — one row per principal, inserted with `id: viewer` ("id minted unless given"), so profile identity and auth identity never diverge.
2. Max lengths are native (`text <=N`); minimums are not: nonempty falls out of `!= ''`, but handle's 3-char floor and `[a-z0-9_]` charset are inexpressible — one INVENTED `matches(...)` per use site.
3. Handle uniqueness is `unique handle` with commit-time refusal — no racy check-then-insert, exactly as the reference advises.
4. updateProfile takes all-optional args and patches with `arg ?? .col`; consequence: a field can be cleared only to '' (empty string), never back to absent. Acceptable for bio/location/link.
5. The language does not say what a patch evaluates to, so updateProfile ends with an explicit re-read; assumes a transaction reads its own writes.
6. Duplicate-email rejection (acceptance 2) has no data-plane surface at all — it is the identity kind's refusal.
7. No timestamps on users: the brief says profile fields are "exactly these" and no M1 screen needs one.
8. Acceptance 3 and 4 (session persistence, server-side logout) are entirely boundary; the data plane's only contribution is that `viewer`-keyed reads stop resolving when the kind revokes the session.
```
