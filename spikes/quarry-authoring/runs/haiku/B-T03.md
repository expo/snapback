Looking at this task, the trap is rule 4: applications are private, and counting them via a reduction like `.count()` over a scan would violate the structural count constraint. The solution is to use a maintained aggregate that the engine keeps exact and up-to-date—this is an authorized way to disclose population facts.

```ts
const users = table("users");
const postings = table("postings");              // index postings.byEmployerCreated: (employerId, createdAt)
const applications = privateTable("applications");
                                                 // index applications.byPostingAt: (postingId, at)
const applicationCounts = maintained("applicationCounts", applications);

export const dashboard = query({}, ({ db, ctx }) => {
  const result = [];
  
  for (const posting of db.scan(postings.byEmployerCreated, [ctx.viewer], { order: "desc", take: 20 })) {
    const countData = db.get(applicationCounts, posting.id);
    result.push({
      posting,
      applicationCount: countData?.count ?? 0
    });
  }
  
  return result;
});
```

The query scans the employer's 20 newest postings and retrieves the application count for each from a maintained aggregate—avoiding both the structural-count violation and the unbounded-read problem that would arise from scanning all applications per posting.
