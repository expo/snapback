# Snapback Cloudflare bundle on celld: spike results

**Date:** 2026-08-09  
**Result:** clean negative for the unmodified/faithful bundle; useful positive
runtime evidence from an explicitly unsafe diagnostic adaptation

## Conclusion

Snapback's Cloudflare notes bundle does **not** run faithfully on celld 0.1.0.
The first hard incompatibility is at the LLP 0048 handler-harness boundary:
celld exposes several Web API properties with shapes the harness deliberately
rejects, and its runtime continues to resolve configurable `globalThis`
properties (especially `__cell`) after module evaluation. Snapback's mandatory
ambient-authority strip removes those properties. Preserving them makes the
app run, but destroys the security property the harness exists to enforce.

There is a second, independent transport incompatibility: celld 0.1.0 throws
while constructing a Durable Object request when the gateway calls
`stub.fetch()` with a POST body. A diagnostic GET-plus-base64-header tunnel
worked, but it is not a faithful execution of the deployed bundle.

With those two unsafe adaptations, the complete
gateway -> `Coordinator` -> handler -> SQLite path worked. Queries and
mutations advanced one coordinator-owned version, a hibernatable WebSocket
received a snapshot and a later `live_replace` after the object had evicted and
rehydrated, and an independent unchanged celld alarm example fired after
hibernation. This is evidence that celld's underlying DO/SQLite/WebSocket/alarm
substrate is promising. It is not evidence that Snapback currently supports a
`celld-do-sqlite-v8` target.

## What was attempted

### 1. Native project configs

I first pointed `celld deploy --dry-run` directly at the checked-in handler and
gateway configs. celld refused unsupported Wrangler keys before bundling.

Handler config failure:

```text
Error: `celld deploy` does not support these config keys: alias, workers_dev.
Deploy this project with Wrangler instead, or remove them.
```

Gateway config failure:

```text
Error: `celld deploy` does not support these config keys: alias, version_metadata.
Deploy this project with Wrangler instead, or remove them.
```

The checked-in configs do not contain the ticket's anticipated `routes` or
`triggers` keys. The actual friction is `alias`, `workers_dev`, and
`version_metadata`.

### 2. Minimal config and bundle adaptation

The spike configs in this directory omit only the rejected metadata and retain
the deployed shape:

- `snapback-notes-handler`, with a `HOST` service binding back to the gateway;
- `snapback-notes-proof`, with a `HANDLER` service binding;
- a `COORDINATOR` Durable Object binding; and
- migration `v1` with `new_sqlite_classes: ["Coordinator"]`.

`bundle.mjs` resolves the production `snapback-app` alias with esbuild because
celld's config parser does not accept Wrangler's `alias` field. Before runtime
diagnostic rewrites, the adapted configs bundled successfully:

```text
handler version bded399708c27ff9 (100.20 KiB)
gateway version edd7888042ef1b86 (339.83 KiB)
```

The handler was deployed before the gateway, as required for celld's named
service pointer. Omitting `version_metadata` means `/health` reports
`workerVersion: null`; no false deployment identity was synthesized.

### 3. Faithful handler startup

The first runtime load failed in the mandatory workerd harness strip:

```text
Error: stateless Worker failed to load: top-level rejected: Error: missing harness request getter: body
```

celld's `Request` puts `body`, `headers`, `method`, and `url` on the instance,
while `packages/snapback-harness` intentionally captures inherited Web API
getters. A spike-only fallback for those four fields reached the next distinct
failure:

```text
Error: stateless Worker failed to load: top-level rejected: Error: missing harness request getter: signal
```

celld similarly exposes `AbortController.signal` as an own property. Adding a
diagnostic fallback for that field allowed the strip to run, after which celld
could no longer initialize the deployed Worker:

```text
Error: stateless Worker failed to load: missing Durable Object namespace registry
```

Preserving only `__cell` was insufficient: later requests failed because
celld's host runtime resolves additional globals after module evaluation. This
is not a benign API-shape shim. Snapback removes configurable ambient globals
on purpose, whereas celld 0.1.0 depends on them remaining reachable.

### 4. Unsafe diagnostic execution

To determine whether anything else lay behind the harness boundary,
`bundle.mjs` makes two transformations that are intentionally labeled unsafe
in source:

1. it accepts celld's own-property Web API fields and preserves celld's ambient
   globals instead of enforcing the global-strip survivor attestation; and
2. it tunnels the gateway's small JSON DO POST bodies through a base64 header
   on a GET, then reconstructs the POST at the start of `Coordinator.fetch()`.

The second workaround was needed after the otherwise-adapted gateway failed in
celld's internal request construction with:

```text
__makeIncomingRequest threw
```

The final diagnostic deploys were handler version `7f5a0037efe8361c` and
gateway version `29fcfe3c9009f234`.

`probe.mjs` then exercised a unique notes board. The selected evidence was:

| Observation | Evidence |
| --- | --- |
| Empty read | `POST /query` returned HTTP 200, `ok: true`, `rows: []` |
| Write | `POST /mutation` returned HTTP 200, `ok: true`, `changedCount: 1`, version 3 |
| Read after write | the row returned with text `written through celld` |
| Live snapshot | `/live/stream` returned a snapshot at version 3 with the stored row |
| Connected-idle eviction | `objectBoot` changed from `43a1e329-8b3a-4f45-83bc-af2018d0a9a7` to `a698cc94-83dc-420e-8ed6-f6a5dd354859` after 5 seconds with the socket open |
| Post-rehydrate write | the mutation committed at version 4 |
| Live delivery | the original socket received `live_replace` at version 4 with both rows, including `delivered over celld websocket` |
| celld hibernation log | `accepted hibernatable WebSocket` followed after eviction by `reused local hibernation snapshot` |
| Coordinator consistency | versions advanced monotonically and query/live results agreed with the committed SQLite rows |

The ambient probe explains why this is not a valid Snapback execution. In the
diagnostic handler `fetch`, `WebSocket`, `crypto`, and `__cell` were reachable.
The checked-in Cloudflare target's harness is meant to deny that ambient
authority and supply only captured capabilities.

`celld diagnose` saw one healthy lease for the notes bucket, protocol 2, the
node at `127.0.0.1:52768`, and four shed cells after the probe. The run was
single-node; it did not test cell migration, and celld documents that active
WebSockets do not survive migration.

### 5. Alarm smoke

The notes app has no cron definitions and celld does not implement a Worker
`scheduled` handler, so it cannot exercise Snapback's LLP 0049 coordinator cron
dispatcher. To distinguish that application gap from the underlying DO alarm
primitive, I deployed celld's unchanged `examples/alarm` Worker into its own
bucket, with a SQLite DO and `CELLD_IDLE_EVICT_S=1`.

```text
GET /arm
HTTP 200
{"armed":true,"at":1786311511840}

# after four seconds and a hibernation/rehydration
GET /
HTTP 200
{"fires":1,"pendingAlarm":null}
```

celld logged a reused local hibernation snapshot and the example observed one
alarm fire. Thus the celld DO alarm primitive works in this local smoke test;
Snapback's alarm dispatcher remains untested and cron remains unsupported.

## Exit question 1: DO SQLite, hibernation, alarms, and local-suite

The celld substrate passed narrow diagnostic checks for per-cell SQLite,
single-node WebSocket hibernation, and the alarm primitive. The Snapback bundle
did not pass them faithfully because it cannot cross the handler boundary
without disabling the ambient-authority strip and cannot cross the gateway/DO
boundary without changing request transport.

The current local suite contains 29 gates, not the older ticket count. It has no
external-base-URL or celld deployment adapter: runtime gates instantiate their
own Miniflare/workerd proof through `startProof()`. Therefore **zero local-suite
gates were run against celld**, and the suite cannot currently answer “pass
against celld.” Invoking it in this checkout also stopped at its explicit
runtime preflight:

```text
SNAPBACK_CLOUDFLARE_PROOF_NODE_UNSUPPORTED: active Node v25.9.0 (major 25) is not the supported Cloudflare proof runtime. The Miniflare loopback proof is validated only on Node 24.x, pinned to v24.18.0 in .node-version (ENG-24513). On unsupported majors the first real-loopback action request intermittently fails with `read ECONNRESET` (observed on Node 25.9.0, ENG-24454) — a Miniflare/Node transport-lifecycle race, not an action-semantic failure. This preflight constrains the supported runtime; it does not fix the Node 25 transport (upstream-shaped) and no action retry hides it. Switch to the pinned Node before running the proof, e.g. `volta install node@24.18.0`, `fnm use`, or `nvm install 24.18.0 && nvm use` (each reads .node-version).
```

Some acceptance-core ideas translated manually: health, manifest inspection,
empty query, mutation, read-after-write, monotonic versioning, live snapshot,
live replacement, and connected-idle rehydration. The ambient-denial part
failed. Alarm/cron, All Aboard, egress, secrets, RQS, reset fault injection,
protocol matrices, and action timeout/recovery did not translate to the notes
probe. Static gates such as compatibility, config-set, deploy-script,
deployment-identity, target-admission, wire schemas, and inventory checks do
not exercise a celld node at all.

A real celld acceptance leg would need a runner that deploys both services,
starts/stops celld, provisions app variants and faults, and directs the common
acceptance cases to an external endpoint. It must run only after the two
faithfulness blockers are fixed.

## Exit question 2: LLP 0048 third leg

Not today. LLP 0048 can only compare engines when they execute the same
single-sourced handler harness and the same protocol semantics. This spike's
celld leg does neither: it suppresses the harness's ambient-global invariant
and alters gateway-to-DO request transport. Adding the adapted result to the
conformance twin would compare different programs and create misleading
parity.

celld could become a legitimate third leg if:

1. celld no longer depends on mutable configurable globals after Worker module
   evaluation (or supplies an internal host channel the harness need not
   preserve);
2. its `Request`/`AbortController` shapes satisfy the Web getter contract, or
   the single-sourced harness adopts an equally strict, cross-runtime capture
   mechanism by design;
3. DO `stub.fetch()` accepts POST bodies without the tunnel; and
4. the twin gains celld-specific deploy/start/teardown plus common trace,
   outcome, storage, and hibernation evidence collection.

Until then celld belongs in an incompatibility fixture or expected-failure
probe, not the conformance matrix.

## Exit question 3: honest `celld-do-sqlite-v8` manifest

There should be no published/admissible `celld-do-sqlite-v8` capability
manifest from this result. The manifest schema's booleans cannot express
“works only after disabling the security harness.” If a provisional manifest
were generated to document the experiment, it must fail closed on claims that
depend on executing app code.

The rows that would flip from
`cloudflare-do-sqlite-v8` are:

Add these `capabilityGaps` beyond the existing Cloudflare gaps:

- `handler_harness_conformance`
- `handler_ambient_capability_denial`
- `durable_object_post_body_transport`
- `cloudflare_version_metadata`
- `websocket_migration_survival`
- `scheduled_handler`

The following rows need not flip merely because the host changed:
`runtimeEngine: "v8"`, `storageEngine: "durable-object-sqlite"`, dev auth,
online-only/replace-only semantics, all Agent Safe `Missing` rows, and the
existing false feature rows. `mutationIsolationMode`, version authority, and
the single `transactionSync` commit description are still the coordinator's
design and were consistent with the diagnostic observations. The
Snapback-enforced `maximum_row_bytes` and `maximum_subscription_count` rows can
remain `Enforced` after a faithful target runs their common tests; this spike
did not independently re-qualify their edge cases.
