## Changes by file

- `packages/snapback4/src/writes.ts`: preserve the first unpersisted terminal
  outcome when another receipt is offered for the same id. Register that custody
  before awaiting storage, retain it on failure, and expose a persistence barrier
  and synchronous pending-custody check. Recovery can distinguish actual
  delivery receipts from local admission-storage errors whose intent is still
  recoverable.
- `packages/snapback4/src/local-receipts.ts` (new): persist and settle a known
  receipt locally, using its original sequence for success or original refusal
  for failure. Reading a known volatile receipt alone does not prove persistence:
  the explicit save must succeed before settlement or transport can advance.
  A correlated outbox acknowledgement also proves success.
- `packages/snapback4/src/local.ts`: protect every known terminal outcome in the
  keepalive callback, not only sent. A failed ordinary receipt save returns the
  known result to its caller without falling through to sync or later entries.
  A retry recovers and settles existing receipt custody before another POST.
  Sync, page application, store observation/adoption and exit refusal handling
  cross the persistence barrier; page-hide dispatch cannot send an unpersisted
  terminal id. Recheck after asynchronous barrier completion before dispatching
  a device operation. Ordinary transport also handles acknowledgements that
  arrive during preflight. An already reflected acknowledgement needs no
  redundant sync that would withdraw acquisition freshness. The file remains
  1,498 lines.
- `packages/snapback4/src/web.ts`: the serialized final send check returns
  committed acknowledgement custody for local settlement instead of sending
  again. Exit transport omits acknowledged entries. An ordinary settlement
  that performs no POST does not block a successor's exit opportunity.
- `packages/snapback4/src/local-sync.ts`: moved the unchanged response-size
  refusal classifier out of local.ts to keep it below the source-file ceiling.
- `packages/snapback4/test/web-admission-review.test.mjs`: add both NOT_ADMIN
  response orders with two aborted receipt transactions; the actual abort/retry
  timer sequence against replacement B; and independent sent_seq/observed_seq
  custody with absent terminal history. Record actual retry callbacks and sync
  entry in the test bundle without changing their scheduling. Add fall-through,
  replay, persistence-barrier and sequence-custody mutants.
  The aborted keepalive control counts each actual exit completion and retries
  only callbacks explicitly declined by settlement ownership, after that owner
  releases. Its reopened page starts visibly, so the test controls the hide.
- `packages/snapback4/test/acquisition.test.mjs`: verify first sent and first
  failed outcomes survive repeated failed saves even if another terminal outcome
  is offered to WriteHistory for the same id.
- `packages/snapback4/test/client-lifecycle.test.mjs`: update the wasm/native
  lost-response and held-sync expectations. Once sync has established a terminal receipt,
  reopen settles it locally and does not POST again; the original one-increment

- `packages/snapback4/test/navigation-model.test.mjs`: after eviction and failed

## Forms and behavior

No new Quarry form, client signature or refusal code. Existing calls compile
and run unchanged:

```ts
const write = await app.mutate(api.removeMember, { room, principal });
const receipt = await app.client.write(write.id);
```

If the original outcome is sent, a receipt-storage failure cannot cause a later
replacement to change it. A retry persists that same receipt and settles with
its sequence locally. If the original outcome is failed / NOT_ADMIN, later
replacement handling preserves NOT_ADMIN. Reopen recovers the original outcome
without allocating a replacement id or reposting a known terminal write.

Unknown outcomes still retain their durable intent and original binding for
same-id recovery. Storage failure does not manufacture a terminal outcome.

## Decisions and open problems

No deviation from the requested rule and no known open scoped problem. A local
E_STORE error describing an unknown admission outcome is not a known server
refusal; its synchronous journal still owns recovery. Repair
uses existing receipt and settlement operations; a persistence failure holds
known custody until a later retry. Terminal receipt retention stays bounded.
The shared transport queue and per-id settlement ownership remain in place.
No authorization/disclosure relaxation, engine-meter change, storage ceiling
increase or receipt-window expansion. No new language forms or acquisition
retuning, and no new cold-acquisition performance claim.

The changed acknowledgement expectations are intentional consequences of the rule:
recover known terminal receipts locally rather than requesting historical reply
values from the server. Failed saves still report the known caller outcome;
unknown response loss still uses the original durable id.
