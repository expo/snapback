## One rule fixes both Medium findings

A measured RTT of at most 1,000 ms uses the midpoint. A longer response uses
`serverNow - received` and is provisional, just like a streaming final-body
stamp. It can update both estimated server time and the offset used by issued
device time; any short measured sample outranks it. The 60-second/32-sample
window, newest ties, monotonic issued floor, epoch ordering, durable admission
floor, wall freshness and server-authoritative settlement remain intact.

Receipt dating avoids adding half a server wait to either clock. It can lag
true server time by the delay after stamping, while a later short sample refines
it. This replaces the round-2 rule that ignored slow responses for issued time.
The stored `issuedOffset` remains readable for compatibility; a regression also
covers correcting a round-2 store where the two offsets differed.

- **Slow negative-offset startup:** the actual native JSON/SQLite client starts
  against dev `--clock-offset -31d`, with both `/auth/refresh` and `/schema`
  delayed 1,500 ms before the real server responds. The thirty-day session has
  an expiry before device wall time, yet startup succeeds and performs zero
  credential deletions. Offline prediction, cold reopen and expiry handling
  continue on the learned server time.
- **Buffered polls:** the actual `changeFeed`, with streaming capability absent,
  requests `wait=2` without `heartbeat`. Three controlled two-second responses
  carry only end-stamped headers after a +120 s advance. Both clocks learn the
  advance; both delays for a deadline 500 ms ahead remain 500 ms, and a short
  response refines the estimate without an overshoot left in the floor.

## When each endpoint stamps

The audited clock stamp is separate from the server execution `now` used to
authorize work or stamp confirmed rows. No server accepts the client's clock.

| Response path | Stamp site and dating |
|---|---|
| `/sync`, snapshot and stream-page modes | `serve_sync.rs` calls `respond_with_sync(..., Some(shared))`; headers are stamped after page execution and JSON serialization in `serve.rs`. Slow samples use receipt. |
| `/q/<op>` | `respond_timed` after query execution and serialization; slow samples use receipt. |
| `/m/<op>` | `respond_timed` after admission/execution or replay lookup and serialization; slow samples use receipt. Confirmed row timestamps still come from server execution. |
| Session endpoints: guest, signup, login, refresh, logout, logout-all, custom session, revoke | `auth.rs` or `serve.rs` finishes identity work, then `respond_timed` stamps headers after serialization. Refusals use the same path. Slow samples use receipt. |
| `/schema`, `/probe`, `/auth/config` | The same final `respond_timed` header path. `/schema` is part of the slow-startup regression. |
| Buffered `/changes`, or a poll finishing before any heartbeat | `PollResponse.finish` calls `respond_timed` after the hold and final authorization/read; the header stamp is created after serialization. Slow samples use receipt, including the native two-second polling path. |
| Streaming `/changes` after a heartbeat | **End stamp only.** Early heartbeat headers now omit clock fields. The final JSON gets `serverNow` and `clockRevision` after the hold and final authorization/read, before bounded serialization; `sampleChanges` dates it at receipt. Overflow refusals retain those fields. |

For streaming polls, I chose the requested **stamp at the end** option rather
than dating an early header at request send. This also handles transports that
buffer a streaming response: there is no start stamp to mistake for an end stamp.
The final-body clock fields already existed; buffered responses retain their
existing headers. The real 25-second streaming test asserts the absence of an
early time header and bounds issued time after the final body and a short reply.
