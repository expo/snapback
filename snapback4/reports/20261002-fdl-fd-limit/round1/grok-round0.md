## Findings

**1. Bug — a failed socket clone tight-loops the accept thread.** In vendored tiny_http, `accept()` still returns a live socket when one descriptor is free. `ConnectionState::new`, `RefinedTcpStream::new`, or `ClientConnection::new` then fails the next `try_clone` with `EMFILE`, and the new `Err(_) => continue` drops that socket and goes straight back to `accept()`. With a non-empty listen backlog the free slot is the same one `accept()` just consumed, so the thread repeats with no sleep, no log, and no refusal counter. When the backlog drains, `accept()` blocks and the CPU stops; when descriptors free up, the next clone succeeds. The old spare-2 and spare-3 behavior killed the thread with `try_clone().unwrap()`. The new behavior keeps the listener alive and pegs one core while resetting clients. `http_emfile` queues one connection, checks that `num_connections()` returns to 0, then retries after descriptors are restored, so it cannot see this. `accept()` itself still logs, pushes `Message::Error`, and `break`s, which is the pre-existing death when zero descriptors are free. Add a backoff and one log before `continue`. Counting or writing the existing refusal is optional; the spin is the defect.

**2. Suggestion — a container with soft and hard both at 1024 is silent.** `adjust()` sets `target` to `soft.max(hard.min(65536).min(ceiling))` and calls `setrlimit` only when `target > soft`. The hard limit is never raised. If soft and hard are both 1024, nothing is called, `startup.error` stays empty, and `describe()` emits `E_HTTP_LIMIT` only when the current soft limit is **below** 1024. The startup line is `startup soft=1024 target=1024` with no hint. Soft and hard both at 256 do warn and tell the operator to raise the hard limit. Soft 256 and hard 1024 raise to 1024 and the warning disappears. One server’s steady footprint is about 563 descriptors, so 1024 can hold it; 1,197 is the unit suite, not one server. This is also the ceiling where finding 1 is the only fallback. Warn when the soft limit is at the cap and was not raised, including equality with 1024.

**3. Nit — the test raise is not a harness hook before every server test.** `prepare_tests()` is a `Once` around `initialize()`, called from `Host::with_evidence` before `Server::http_with_limits`, and from the listed server-test sites. That covers the paths that exhausted descriptors. It is not a process-wide constructor. `tests/latency/duration.rs` binds its constrained sockets without calling it, and the integration binary `tests/http.rs` does not either. Both use a handful of descriptors and are not the original failure. Libtest can start another unit-binary test before the first `Once` runs. `many_servers` also returns success without the workload when the hard limit is below 2048, so a tight container records a pass it did not exercise.

## Claims

**1. Peak 1,197 is demand, not a lasting leak. Confirmed for the measured suite.** `baseline-4096.json` records `peak_fds` 1197 on unmodified main at soft 4096, during overlapping serve and adoption tests in one libtest process (this host has 96 CPUs). The serial baseline peaks at 249 and returns to 3 descriptors in quiet gaps. `many_servers` runs three cycles of 8 hosts by 32 connections and asserts the count returns to baseline. After this change a connection holds four descriptors: the accepted socket, the deadline clone, the read half, and one abort socket. The per-request abort `try_clone` is gone; `ConnectionAbort` is an `Arc<Mutex<Stream>>`. The admission cap is 128, so connection descriptors top out near 512 plus sqlite, the listener, and pipes. Idle and header timeouts default to 5 seconds, so an idle keep-alive drops those four descriptors together. Request workers are a thread pool of `FnOnce` jobs and do not retain sockets. No multi-hour soak was run; nothing in the suite samples shows a one-descriptor-per-request leak.

**2. Startup raises the soft limit, logs failure, and does not fail startup. Confirmed on Linux by code and the `adjust()` tests. The macOS formula matches the written policy and was not executed.** `MAX_DESCRIPTORS` is 65536. A soft limit already above the target is kept, including both limits unlimited, and the setter is not called. A refused `setrlimit` stores `setrlimit(RLIMIT_NOFILE): {error}` in a `OnceLock`, logs once, and continues. `serve()` calls `initialize()` before the witness listener and before `DevWorker`. `dev` reaches that only after project and bind validation, through `lifecycle::run`. The internal watchdog returns in `main` before `initialize()`. The one exception is `witness_socket::take` at process entry: an inherited listener descriptor can exist before the raise. It was opened by the parent. The accept thread and workers still start after the raise.

On macOS, `platform_ceiling()` reads `kern.maxfilesperproc` as an `int` and otherwise uses `OPEN_MAX` (10240). The target is `min(hard, 65536, that ceiling)`. `sysconf(_SC_OPEN_MAX)` is not used as the cap; it reports the current soft limit. Unit tests cover `(256, u64::MAX)` → 65536, the same with cap 10240 → 10240, `(256, 512)` → 512, an already-high soft limit preserved, unlimited left untouched, and `EPERM` leaving soft at 256 with the OS cause. `macos-typecheck.log` only typechecks `host_limits.rs` for `aarch64-apple-darwin`. There was no live `setrlimit` or sysctl.

Children inherit the raised soft limit and the unchanged hard limit. `setrlimit` is process-wide and crosses fork/exec. Node and the watchdog are spawned after `initialize()` on the normal path, so they see the new soft limit. Nothing here sets the hard limit or `RLIM_INFINITY`. A child could already raise its own soft limit up to the hard limit; Node doing that on its own is not a new bypass. An operator soft cap of 1024 is lifted for the whole tree, up to `min(hard, 65536)` on Linux. That is the intended effect of the raise, not a privilege change. The watchdog’s `pre_exec` only toggles `FD_CLOEXEC` on the owner flock.

**3. Tests raise the limit before any server test. Mostly true, and overstated.** See finding 3. The common `Host` path raises before its own listener. There is no before-all-tests hook.

**4. A failed clone is closed instead of panicking, and admission accounting of the old paths is unchanged. Confirmed, with finding 1.** The lease is taken before `ConnectionState::new`. If that constructor’s `try_clone` or a timeout call fails, the lease is dropped on the error return and `fetch_sub` runs once. The new `continue` drops the `state` `Arc` the same way. There is no leak and no double-free. Over-cap refusal is untouched: it still writes the fixed 503 body and increments `http_written` / `http_failed` / `tls_closed`. The EMFILE close does not. The client sees a TCP close, not an HTTP refusal. During the spin, `num_connections()` can flicker by one; that is not a leaked permit. Spare 1 already continued before this diff. Spare 2 and 3 used to panic the thread, which also would not have counted a refusal.
