## Security

Tokens are not printed, not stored (only the SHA-256), and not put on argv. Doctor status is name, source, mode, state, counts, and pid (`dev_worker.rs:286`). The Node `--version` probe uses `env_clear` (`dev_worker.rs:373-378`). Stdout and stderr go through a longest-match redactor that holds a strict prefix, including the JSON-escaped form (`worker_environment.rs:52-60`); the supervised test splits a token across two writes and across stderr. Deploy copies regular-file bytes from `O_NOFOLLOW` fds into a new stage directory and does not copy the environment. Discovery is only `snapback/workers/<service>.{mjs,mts,ts}`. `node_modules` is not walked. A dependency cannot become a worker unless something writes a file there, and that file is trusted application code, same as `snapback/worker.ts`. The ledger file is created beside the store; dev, fresh, and deploy directories are `0700`, so a `0644` ledger file is not traversable by other users.

Crash, rotation, and spawn failure do not mint a second bearer while the old row remains. Reload bumps `worker_revision` before close (`serve_adoption.rs:220`), and `current_service_tx` rejects a supervised family whose meta revision does not match (`identity.rs:51-52`). Effect claim, effect settle, action claim, and `/auth/session` use that fence. Manual `token --service` seats have no `worker:family:` row and are left alone. Startup `clear_child_session` (`serve.rs:294`, `dev_worker.rs:22-29`) deletes supervised families; `substr(key, 15)` matches the `worker:family:` prefix.

**Medium.** A removed worker’s bearer stays usable on every door that uses `identity::resolve`. `dev_worker.rs:78` drops a worker that disappeared from the tree. `Drop` (`dev_worker.rs:331-335`) calls `close_child_session` once, ignores `false`, and still writes status `stopped`. Nothing retries. `resolve_digest` (`identity.rs:187-191`) never looks at `worker:family:` or the supervisor revision. `/m/` and `/q/` (`serve.rs:1079`), `/a/` (`actions.rs:58`), and `/auth/refresh` (`auth.rs:238-243`) all use that path. `/auth/refresh` keeps the same family and starts the one-day lifetime over, so expiry is not a bound.

Failing scenario: `dev` is running with `snapback/workers/push.mjs`. The worker has already copied `SNAPBACK_SERVICE_TOKEN` out (the regression worker writes it to a file). An external `BEGIN IMMEDIATE` is held longer than the store’s 5 s busy timeout, or the delete hits a disk error. A schema or worker edit adopts, `worker_revision` increments, and `push.mjs` is gone. Close fails once. Doctor shows `push` stopped. `POST /effects/claim` with the old token is 401, because the meta row still carries the old revision. `POST /m/send` (the fixture mutation, which only emits) and `POST /auth/refresh` still succeed. Refresh can be repeated for as long as that dev process stays up. `serve` does not hot-remove; the next process start clears these rows. This is a dev-server hole, and it is the removal case the retirement rule misses.

Smallest fix: do not drop the `DevWorker` until `close_child_session` returns true, and apply the same family/revision check inside `resolve` and `rotate_session`, passing `shared.worker_revision`. Test it by holding the write lock, removing the worker under a watch, and asserting 401 on `/m/send` and `/auth/refresh` while the lock is held, not only 401 on `/effects/claim` after rollback.

A mutation that survives the current revocation test: delete `identity.rs:51-52`. That test 401s only after the row is deleted.

## Supervision

`dev` and `serve` share `Supervisor`. Both launch every declared entry with its own service session, token, ledger path, and 250 ms–5 s backoff, and both close every watchdog stdin before waiting. `serve` sets `explicit_env`, so it does not reload on `worker_revision`; `dev` does, and a successful adoption restarts changed entries. The host’s `SIGINT`/`SIGTERM`/`SIGHUP` handler closes those pipes. The watchdog is in its own process group (`worker_process.rs:6`, `22`), so a signal to the host pid does not hit it; stdin EOF then `SIGTERM`s the Node group and `SIGKILL`s it after 2 s (`worker_process.rs:49-56`), including host `SIGKILL`. `waitid(WNOWAIT)` holds the leader pid until that kill. Backoff is capped at 5 s and resets after 30 s uptime, so a crash loop is not a 250 ms storm. Workers do not bind ports of their own; the shared ledger lock is the only cross-worker lock, and it is the one documented above.

**Medium.** The watchdog dies on `SIGTERM` and then cannot kill the group. `main.rs:61` dispatches `--internal-worker-watchdog` before `lifecycle::install`, and `watchdog` (`worker_process.rs:19`) never ignores `SIGTERM`/`SIGINT`/`SIGHUP`. Default disposition kills that process. `pkill snapback4` or `killall snapback4` signals every `snapback4` process and not Node. The watchdog exits inside the poll loop. Node and a helper that ignores `SIGTERM` are reparented and keep running, including a `BEGIN IMMEDIATE` held across a provider call. The next server’s workers retry that lock forever (`worker-ledger.ts:44-49` has no attempt cap). systemd `KillMode=control-group` is milder: the cgroup `SIGKILL` still arrives after `TimeoutStopSec`, so the orphan window is that timeout instead of the watchdog’s 2 s. `worker-regressions.test.mjs:160` only signals the host pid, so this stays green.

Smallest fix: at the top of `watchdog()`, ignore `SIGTERM`, `SIGINT`, and `SIGHUP`, and keep shutdown exclusively on stdin EOF or Node exit. Add a test that `SIGTERM`s the watchdog pid (the parent of the Node pid in the start record) and asserts the `SIGTERM`-ignoring helper is dead within the grace period.

`SIGKILL` of both host and watchdog still orphans the group. That cannot be fixed from userspace.

**Low.** A new declaration that fails `start_named` is dropped on the floor. `dev_worker.rs:81-83` logs and does not insert. Only the next `worker_revision` change tries again. Workers already in the map retry spawn from `tick`. Scenario: the adoption that first sees `snapback/workers/push.mjs` runs while `node` is not v24. One log line, no status row, no backoff. Restoring Node does not start it until another file change. Smallest fix: insert the `DevWorker` anyway, or remember the failed name and retry it from the 100 ms loop with the same backoff.

## Ledger

The ledger does not record a failed handler, a `GiveUp`, or a commit that did not succeed. Handler failure sets `handlerFailed`, rolls back, and rethrows (`worker-ledger.ts:57-67`); `perform` then settles a failure (`worker.ts:189-198`). `COMMIT` is the completion. A crash before that releases the lock and the handler runs again. That is the documented at-least-once window, not suppression. Two processes cannot both pass `BEGIN IMMEDIATE` for one key; the executed two-process test performs the handler once and replays the receipt twice. Corrupt files, a wrong table, a non-JSON receipt, and a non-directory parent fail open before claim (executed). Disk full and a failed commit/rollback close the connection, settle nothing, and leave no row (executed). `meta.idempotencyKey` is the outbox primary key assigned at emit (`runner.rs:570`). Claim, settle, and lease expiry update other columns and do not change `id` (`effects.rs:274`, `509`). `worker.test.mjs:281` and `:835` assert the same id across a real lease expiry and a lost settlement. Replacing the store changes `store_id`, so the ledger filename changes. Moving the store without the ledger file loses deduplication; the guide says the file has to travel with backups.

Initialization failure suspends polling until abort (`worker.ts:293-298`) and does not consume an attempt. That matches the spec. The supervisor still shows `running`, because the process has not exited. Repair the file, then restart the process.

## Verdict

**READY WITH CHANGES.**

The retirement gate, the no-follow snapshot, the store-scoped ledger, secret subsetting, and the host-pid shutdown path are sound, and the ledger does not suppress an incomplete delivery. Do not treat it as done until a removed worker’s token is refused by `resolve` (not only by effect claim), and until the watchdog ignores terminal signals so only stdin EOF reaps the group.
