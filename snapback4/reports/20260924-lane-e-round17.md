# Lane E round 17 — consistent outcomes when receipt saves fail

Online custody now returns and notifies the known server outcome even when its
receipt cannot be saved. Receipt lookup cannot turn that outcome back into
pending. The original durable intent stays available for same-id restart replay.

## File-by-file changes

- `packages/snapback4/src/app-online.ts`: mutation, lookup and background
  settlement failures retain a receipt summary in memory, finish the wrapper's
  reservation and notify subscribers. Lookup retries persistence and returns
  that summary even if the raw client's receipt has expired or the journal read
  fails. Successful persistence retires the memory entry; pause/close clears
  retained summaries. The summaries omit historical results and refusal details.
- `packages/snapback4/src/app.ts`: an additional local-model finding required
  provisional opening cancellation to use the existing cleanup/publication path
  when its scope was fenced by a peer but its auth operation is still current.
  Restoration retries instead. Explicit close and superseding local operations
  retain their existing cancellation path.
- `packages/snapback4/test/app-online.test.mjs`: six focused cases cover sent
  and failed outcomes learned by mutate, lookup or background notification.
  Receipt saves keep failing during lookup. Tests remove the raw receipt, fail
  journal reads, repair storage, and check one notification, durable custody,
  successful retirement, receipt redaction and closed-client fencing.
- `packages/snapback4/test/app-receipts.test.mjs`: two real-server regressions
  cover a committed mutation and an input refusal. Three lookups run while
  receipt saves still fail. Restart replays the original id and leaves exactly
  one accepted row or no refused row.
- `packages/snapback4/test/react.test.mjs`: Chromium exercises the actual
  AppProvider/usePendingWrite lifecycle with failed receipt saves. A pending
  hook settles by notification; remount recovers sent while saves still fail;
  neither step submits a new id.
- `packages/snapback4/test/helpers/app-session-model.mjs`: add persistent
  receipt-store outage/repair and captured-handle lookup operations. I13 compares
  mutation results, receipt lookups and notifications with independently modeled
  server receipts. The prior 25 operations and I1–I12 checks remain.
- `packages/snapback4/test/app-session-model.test.mjs`: require I13 coverage for
  sent and failed outcomes on both tiers, add four fixed consistency cases and
  retain the reduced provisional-opening failure as a local regression.
- `packages/snapback4/CLIENT-AND-OPERATIONS.md`: document I13, receipt summaries,
  notification, retry and same-id restart custody.
- `llp/3000.013-quarry-states-intent.rfc.md` §6: record the same implemented
  contract and the expanded model.
- `JOURNAL.md`: one dated append. This report records scope and qualification.

## Existing forms

No new API or Quarry form was added:

```ts
const result = await app.mutate(api.add, { body: "one row" }, { id });
const receipt = await app.client.write(id);
// Receipt storage can still be failing: both outcomes remain sent (or failed).
```

```ts
const stop = app.client.onWrite(write => updatePendingWrite(write));
// The known terminal result is notified even when its receipt save fails.
```

`usePendingWrite(api.add, id)` recovers the same terminal state after a component
remount. A deliberate new `run()` remains a new mutation; the fix removes the
incorrect pending state that could induce an accidental second submission.

## Additional defect found by the model

Local seed 3168 reduced to this sequence: A signs up; B replaces that session,
closes and restores; hold a store write; allow A to observe the superseding
session and begin private cleanup; queue A's guest opening and B's next signup;
release the held write. B fences A's provisional opener before it becomes owner.
The old early return reported E_CLOSED without either finishing auth publication
or entering the restoration retry path. A stayed restoring with no remaining
operation. The fixed model case includes the original fault settings, though
instrumentation showed this reduced schedule did not need an injected failure.

More simulated time did not fix the reproduction. The attempted timing change
was removed. Provisional cancellation now throws the existing epoch/restoration
signal through the existing cleanup path when its operation is still current.
The original model timing limits remain; no assertion or invariant was relaxed.

Scope decisions: notify on background settlement failures as well as mutate and
lookup failures, since a caller may already have received pending. Retain receipt
summaries, not result payloads, to preserve the existing recovery disclosure
contract. Lookup retries persistence; no new timer or admission path was added.
The additional provisional-opener cleanup is justified by the reduced model
failure and preserves the existing epoch/refusal design. The attempted model
wait-bound change was removed, not used to conceal the failed invariant.
