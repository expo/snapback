# Lane V round 15 — settlement never reads a shared correction

Date: 2026-09-26. Branch: `sb4-intent/v-web-start`, based on round 14
`b650375a9`. Intended integration: 0.4.3. The supervisor wrote this round, as it
did round 14, because the lane's codex session could not authenticate. Grok's
round-14 review (`v-r14.grok.md`, READY WITH CHANGES) was read in full.

## The finding

**Grok (Medium): the round-14 overlay reached settlement** (`web.ts:346`).
Round 14 applied `lookupReceipts` to every `meta write-history` reply.
`WriteHistory.acknowledged` reads the same reply, so a shared `NOT_ADMIN` or
`sent` hid this device's own `E_STORE_REPLACED` from the qualified-success
repair. Three consequences followed:

- A qualified success was reported as the shared refusal and never kept.
- A qualified success over a shared `sent` was reported but not kept.
- A legacy sequence could be settled against the overlay.

## The fix

The overlay is now a separate, caller-only read:

- `web.ts`: an ordinary `write-history` read is local-first again, as before
  round 14. Only a request with `lookup: true` applies `lookupReceipts`.
- `writes.ts`: `WriteHistory.lookup(id)` consults the host's `lookup()` only
  when the device's own receipt is a durable `E_STORE_REPLACED`. It keeps and
  settles nothing it returns.
- `local.ts`: `client.write(id)` uses `lookup` only when this device holds no
  outbox entry for the id. Settlement (`acknowledged`) and exit commits keep
  reading the local-first history.

Devices read only `key` from a `meta` request, so the extra field is inert on
both the native and the wasm device.
