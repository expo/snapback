This report supersedes the earlier treatment of offset metadata's `last`.

## Findings and changes

**Non-admission `last` cannot override startup samples.** `ServerClock.attach`
now ignores `last` in offset metadata, regardless of whether it is zero or
nonzero, whether the offset is positive or negative, or the stored issued offset.
Offset validation and persistence no longer include that field. No migration or
special-case repair of unpublished round-2 metadata is needed.

The live clock still issues monotonically. Across reopening, the only restored
floor sources are the atomic `server-clock-floor` admission record and queued
`entry.now` values. The admission transaction, synchronous web journal capture,
settlement durability, pending-entry recovery and epoch guard are unchanged.

The native regression creates an actual SQLite store with
`{offset: -31 days, issuedOffset: 0, last: Date.now() - 5000}` after the two
1,500 ms startup responses but before clock attachment. It first verifies that
there is no admission floor or queued write. Opening succeeds, the valid
thirty-day session is retained, and credential deletions remain zero. The fresh
`-31d` startup case remains separate. Both subsequently exercise offline writes
and cold reopening through the real native JSON bridge.

**Provisional samples are now distinguishable.** The slow competitor is 500 ms
behind the streaming stamp. Both arrival-order tests require the streaming
estimate to survive and a deadline 100 ms ahead to stay 100 ms away, rather than
being postponed to 600 ms. Production selection was already correct.

**RTT ties explicitly prefer the newest sample.** New measured and streaming
cases lower the estimated offset while the issued floor stays frozen. They check
the unfloored estimate and refetch delay, so the monotonic floor cannot hide an
incorrect older-sample selection.

## Tests and intentional expectation changes

Focused checks: **38 clock/regression tests** and **9 browser/wire/native tests**
passed. New unit cases cover both `issuedOffset: 0` and an already-negative
issued offset, so the fix cannot merely special-case round 2's zero value.

Three deliberate mutations were rejected and restored:

- Restoring `Math.max(this.last, state.last)` for any nonzero `last`: both
  negative-startup unit cases fail.
- Using `<` instead of `<=` for RTT ties: both measured and streaming cases fail.
- Always preferring the newest provisional sample: the stream-first case fails
  because the later slow sample shifts the estimate by 500 ms.

The old offline restart unit expected a readonly `now()` call to supply a durable
floor. It now supplies an admission record, as the clarified rule requires.
The two browser crash tests previously inspected serialized `last`; they now
require its absence while retaining pending/settled admission recovery checks.
These are deliberate expectation changes, not removed durability coverage.

No new Quarry form, API or refusal code. Existing examples remain covered:
`at: time default now`, `expire at .expiresAt`,
`return clockMessages where .conversationId = conversationId last 20 by .at`,
`query heldTyping(conversationId: conversations) held:`, `client.now()` and
`useNow(deadline)`. Endpoint stamp timing remains exactly as audited in the
[round-3 report](20260925-lane-y-r3.md).

Full `scripts/test.sh`, exit 0: **`== 0 failure(s) in 408 s`**.
Regular clients: **1,555 passed**, 10 existing skips; all **78 model tests**
