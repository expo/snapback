## Findings and changes

**Recovery after attachment preserves the admission floor.** The source audit
found two production outbox insertion sites (`admit_with_replay` and `enqueue`)
and one upsert site (`predictions::enqueue`, used by replay and receipt recovery).
All three now call the same `keep_issued_floor` helper inside their existing
writer transaction. It raises `server-clock-floor` to at least the entry's `now`
and skips unchanged metadata writes. A failed floor write rolls back the outbox
write too. The storage adapters merely implement or forward those operations;
there is no separate production insertion path bypassing this rule.

This covers ordinary admission, journal recovery through admission, orphan
transfer through `enqueue`, and replay/receipt upserts. The earlier atomic
attachment backfill remains for old records already in the store. No additional
queue scan was added to these writers: the floor update is constant work per
outbox write. Synchronous web journal capture remains unchanged.

**Backfill refusal blocks startup.** Production already checked `pending.denied`.
A new test injects a transient refusal through the actual client's `DeviceCore`
wrapper and requires startup rejection with no mutation request, settlement,
dequeue or apply. The legacy entry remains byte-for-byte durable and the floor
remains absent. Clearing the fault allows startup, one send, settlement and a
persisted floor. Removing the existing guard now fails this test.

**Backfill must inspect the whole queue.** Rust fixtures now use
`[1001000, 1004000, 1003000]`, putting the maximum in the middle. Taking only
the first entry fails on memory and SQLite.

## Tests and measurements

Focused checks: **9 Rust clock tests**, **40 clock/regression tests**, and
**14 browser/wire/native tests**, all passing.

The new real-Wasm orphan test holds a sibling's legacy store while the
destination attaches with an empty queue and no floor. It releases the sibling
and triggers ordinary orphan recovery through `observe_store`. The recovered
outbox entry and `1004000` floor must appear in the same persistence batch.
After settlement empties the queue, the test closes only the core, rolls wall
time from `1004000` to `1000000`, reopens and still issues `1004000`.

Rust recovery tests cover memory and SQLite, including legacy receipt upserts.
The new recovery batch test requires both the outbox row and floor in one
committed batch. An invalid floor forces a failure after insertion and must
leave neither a new entry nor a partial committed batch.

Four deliberate mutations were rejected and restored:

- Fold to the first queued time: two Rust failures, `1001000` versus `1004000`.
- Omit the recovered enqueue's floor update: three Rust recovery failures.
- Omit the replay/receipt upsert's floor update: two Rust recovery failures.
- Ignore `pending.denied`: the real client test fails with a missing expected
  startup rejection.

The old bridge fixtures used current `enqueue` to simulate a pre-floor store.
They now insert the old serialized outbox record directly through host memory
persistence or SQLite, and still assert that the floor is absent before attach.
Rust backfill fixtures reset the constructed queue's floor to the intended
legacy value; zero models absence for that test. The bridge tests retain actual
absent-record coverage. No durability assertion was removed or weakened.

No new Quarry form, public client API or refusal code. Existing examples remain
covered: `at: time default now`, `expire at .expiresAt`,
`return clockMessages where .conversationId = conversationId last 20 by .at`,
`query heldTyping(conversationId: conversations) held:`, `client.now()` and
`useNow(deadline)`. Endpoint stamp timing remains as audited in the
[round-3 report](20260925-lane-y-r3.md).
