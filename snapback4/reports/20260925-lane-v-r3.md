**Open High: Web Locks do not make the next holder's localStorage read current.**
The unchanged `storeLock` / `sameAdmissionAuthority` protocol assumes that a
locked localStorage read sees the previous holder's write. Chromium on this
host violates that assumption. The standalone reproduction reported:

```json
{"iteration":239,"captured":{"principal":"test:alice","snapback4Epoch":"239"},"seenUnderLock":{"principal":"test:alice","snapback4Epoch":"239"},"after":{"snapback4Logout":"239"}}
```

The writer held the same Web Lock, wrote the exact same-epoch tombstone used by
`restoringStore.delete`, then released the lock. The reader acquired it and saw
the old signed-in value matching its captured principal and epoch. Its next
read saw the tombstone. Thus even the intact `logoutEpoch` rejection cannot
reject the stale value. Reproduce from `snapback4/`:

```sh
node reports/20260925-lane-v-r3-evidence/storage-lock-repro.mjs
```

The probe stops with exit 1 on a stale authorized read, or reports that it did
not reproduce in 10,000 handoffs. The iteration varies. There are no task sleeps
or arbitrary timing thresholds. This is a counterexample, not a passing gate.
The existing real app test independently exposed the consequence: in
`targeted-final.log`, `session-locked journal refuses stale authority: principal`
returned `sent` rather than `failed`, and the audit advanced from 3 to 4. The
following epoch/recovery assertions failed on that already-incremented audit.
The review had already reported an intermittent same-epoch tombstone failure;
a later mutant run here reproduced that symptom too. Instrumented repetitions
can pass (150 handoffs did), so retrying the suite cannot prove this safe.

This protocol predates the round-3 source delta. It is a **pre-existing product
defect newly demonstrated here**, not an environmental timeout or a failure
listed in the recorded baseline. Per the brief, I stopped this part instead of
adding delays, weakening tests, or redesigning authority storage in this lane.
A coherent authority source and its durability/compatibility rules need the
supervisor's design decision. The lane must not be integrated as satisfying
cross-tab logout authorization until that is resolved.

Engineering decisions and limits:

- An unreachable probe retains the established offline custody, as explicitly
  allowed by the review. A received but rejected/malformed probe never grants
  exit transport. This does not make keepalive delivery reliable while offline.
- Replay checks cover every unsent entry (`sent_seq == null`), matching the exit
  sender's set, including entries with an observed receipt.
- A successful initial sync plus a healthy device capture enables exit after
  backend adoption. It does not make a second redundant network probe: that
  initially introduced a hang in an existing held-probe compatibility test and
  was corrected before final qualification.
- `onSuspend` remains web-specific. Native startup retains its existing
  snapshot/receipt ordering. No meters, bucket limits, durability modes,
  disclosure checks, snapshot sizes or wasm budgets changed.
- Cold acquisition was not remeasured in this round, which changes neither
  snapshot processing nor persistence. The latest measurements remain round 2:
  13.298 / 15.825 / 18.703 s bounded, versus 70.716 s fresh per-row; median
  **4.47×**, with all 65,180 rows retained after offline reopen. These are prior
  measurements, not new round-3 performance claims.
- No package version bump, push, publication or new language form.
