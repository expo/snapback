
## M1 — accounts and profiles
Built password signup/login, persisted web/native sessions, server-owned profiles and unique handles, fixture avatar upload/render, and an idempotent eight-person seed. The suite and two-client choreography pass; an iOS Hermes export is retained. Quarry's built-in identity and asset placement were easy to express. React form payload hygiene and retained Expo stack routes fought me: two agent errors, both fixed without a backend workaround. Familiarity with React and Expo helped; no prior Snapback code was consulted. The guide's result shapes and generated API made refusals understandable. Compared with Supabase, there was less session/storage-policy assembly; compared with Convex, the local replica was part of the default client rather than a separate cache design. Setup required fixing the actual shell's Node version and the read-only copied harness permissions. No platform gap established at this milestone.

## M2 — posts and follow graph
Built text/image/video posts, direct reply threads, counts, likes/reposts, profile post lists, public and Following feeds, and fixture segment M2. Both verification gates pass, with Hermes export. The union activity view and materialized Following view expressed the feed without hand-built fan-out. Built-in owned-key coverage supports future offline set-state interactions. The main fight was navigation: the frozen choreography clicks feed tabs directly from profile routes, so those routes now expose the same feed navigation. This was an agent integration error rather than a backend defect. Familiarity with declarative query systems helped with source/derived separation. Compared with SQL, the Following view avoids substantial materialization machinery; compared with Convex, Quarry is less general but communicates its plan and copy costs directly. The guide also states its 1,000-event per-author history window, which remains a candid scaling limitation beyond this fixture's author histories.

## M3 — messaging core
Built deduplicated DMs, group creation and administration, text messages, quoted replies with paging/jump, expiring typing, and sent/delivered/read receipts. The suite and full multi-client choreography pass, including slowest group recipient and removed-member retained history. The receipt declaration removed a large amount of application accounting; the SDK reports fetched positions and the screen reports viewed positions. My first membership update policy blocked non-admin receipt updates, a useful reminder that generated behavior still composes with application authorization. Named composite lookup briefly produced a bound diagnostic while the equivalent positional key compiled; this is retained as ambiguous diagnostic evidence. React experience helped with stable screen ownership. Compared with Convex/Supabase, there is much less receipt/replica code here, but the receipt family's mapping vocabulary takes study and query decorations need deliberate separation from retained history.

## M4 — message media and interactions
Built picker uploads, inline photos, playable video, arbitrary emoji set-state reactions, caption/text editing, and delete-for-everyone with asset release. Server windows come from the shortened fixture JSON via generated Quarry helpers. Both suite and choreography pass; real elapsed-time probes also produced EDIT_WINDOW_EXPIRED and DELETE_WINDOW_EXPIRED. The asset home model made revocation straightforward. UI integration fought me more: viewer container/close semantics, scrolling while opening actions, and a reaction toggle incorrectly treating a revalidating query as empty. A focused two-client reproduction separated server success from the stale local toggle decision. The final UI preserves explicit caller intent through query transitions. Compared with Supabase storage URLs, policy-bound bytes remove a separate revocation mechanism; compared with Convex, the first-class local prediction needs more care about unknown versus empty than a purely online UI.

Declarative expiry and asset placement made revocation unusually direct. ## M6
Built a supervised push seam, token-client API and demo, the full action-log adapter, and visible durable pending sends. Suite and choreography pass; Hermes exported; an additional web probe verifies cold offline history and ordered sends after reload. The 50-action sample exercises every verb and passes final-state checks. Scale is on a separate recorded clock and fresh store, not the acceptance store. The integrated outbox and worker ledger saved substantial plumbing. Media retries fought me: a fresh upload is a different argument even when the message ID is unchanged, so replay now resolves existing messages first. Familiarity with idempotency keys helped explain that refusal. Compared with Convex or Supabase, local durability is much more directly supported here, though prediction horizons still require honest fallback UI. The API needs an explicit normalized wrapper because generated rows are backend-shaped. No simulator execution is claimed; the required native build artifact exists.

## M8
Built maintained lifetime and daily Insights, server-ranked Trending, shared unread counts, and a scheduled digest using recipient-authorized reads and once-per-period admission. The suite and live choreography passed, and the isolated digest emitted the exact expected counts with every client closed, then emitted nothing in an inactive period after a server restart. Cold-offline media and search also passed a separate browser probe. Maintained aggregates were easy to add without manual counter updates. The live-store lock prevented an unsafe old-post test; a separate clock-controlled instance made that proof clean. A root-route assumption in the harness required the home chat rail. Dual-offline settlement exposed unstable list rendering: keeping IDs and ordinals while giving each message its own authorized subscription resolved it without keeping protected content copies. Prior React subscription experience helped more here than database familiarity. Compared with a hand-built Postgres or Supabase stack, the biggest saving was keeping authorization, aggregate maintenance, expiry and scheduling in one backend language. Compared with Convex, I appreciated the replica and receipt declarations, but spent more attention on local read availability and row lifetimes. No simulator proof is claimed; Hermes exports and browser proofs are distinct evidence. Scale continues on its own clock.

## Replay protocol correction after M8
The first replay overlapped M8 schema adoption and had imported a probe module before the aggregate queries existed. I retained its two successful checkpoints and all receipts as diagnostic evidence, stopped its recorded server, and started a new empty store after the app was frozen. This is an agent protocol correction, not a platform capability failure. The final replay includes the full backend and aggregate probes from the outset. A separate scale web build points at that store; the acceptance app remains separate. Historical choreography npm metadata also had a hard-coded version error; original evidence is preserved with an explicit erratum rather than silently rewritten.

## Scale closure and unread-count correction

The full fresh-store replay settled every fixture action, but its final inbox paging probe exposed my raw unread scan exceeding the returned-shape meter. The guide's row-keyed count was the direct remedy. I adopted it, retained the original failed checkpoint, and re-verified the full corpus without replaying or skipping fixture actions; the clock includes the correction. This is not an unchanged-generation performance curve. Counts, grouped invariants, named fixtures and full busy-chat paging pass. The maintained count changes prediction eligibility, so I rebuilt the client/native artifact and reran the affected suite/choreography and durable offline proof. Those passed. The published diagnostic and example reduced diagnosis time; knowing ordinary aggregate patterns helped, but the row-keyed expiry and replica semantics were platform-specific. A SQL backend would also need a deliberate unread strategy; this system made the supported strategy explicit and bounded the unsafe query instead of letting it grow silently.

Two verification mistakes also mattered: a repeated quote test assumed the starter quote would remain in the newest history window, and I briefly overlapped an idempotency comparison with choreography writes to the same fixture accounts. The corrected test sends a fresh quote to the original source and asserts navigation to its actual message element. The comparison then passed sequentially. The scale browser export additionally needed a clean Metro cache to honor its different backend URL. These are author/test-environment corrections, not platform capability failures.
