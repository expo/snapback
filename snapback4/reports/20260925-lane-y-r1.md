## Findings and fixes

1. **Astra: shrinking-offset expiry refetch loop.** `estimatedServerNow()` is
   unfloored; `serverDelay()` uses it. `issuedDeviceNow()` is monotonic;
   `deviceDelay()` uses that floor for device deadlines. Online server answers
   use the first delay. Local fallback results now carry `serverExpiry`
   separately from the device's `nextExpiry`; mixed results retain both and
   schedule the earlier delay. Rendering and device execution still use issued
   time. Controlled online, fallback and composition tests each hold their
   request count at one across 120 ms while the issued floor is ahead of the
   server deadline, then prove the real server deadline still refetches.

2. **Astra: admission floor missing after a crash.** Before issuing any device
   time, `ServerClock.attach()` restores the maximum safe issued time from the
   durable pending entries as well as clock metadata. The admission entry already
   carries its issued time in the outbox and synchronous web journal. No await
   was inserted before that journal capture. The real Chromium/IndexedDB witness
   advances wall time by four seconds, admits offline, verifies the synchronous
   journal record and an older clock metadata floor, and reloads without either
   `close()` or a subsequent client query. After rolling wall time back, its first
   issued time is at least the pending entry's time and the predicted row survives.

3. **Astra: render-to-effect deadline/correction gap.** `useNow` captures the
   issued time used during render, subscribes and schedules in its effect, then
   compares current issued time with that render. A difference requests one
   catch-up update. Tests execute the actual hook with controlled effect
   installation: an elapsed deadline, a forward correction across the deadline,
   and a correction while the deadline is still ahead. Each requests one update;
   the last installs the corrected 50 ms timer, and cleanup removes it.

4. **Grok: half-poll streaming overshoot.** Final streaming stamps are dated at
   receipt, not the midpoint of a request that the server held. They are marked
   provisional and cannot beat any real RTT sample in the current bounded window.
   This applies to every final streaming stamp, including a revision change:
   the stamp always describes the end of the hold. A controlled 20-second hold
   proves no ten-second overshoot, and a following 40 ms sample refines the offset.
   The actual 25-second HTTP poll now has both lower and upper bounds, then checks
   issued time again against the following short query's server time.

5. **Grok: reordered responses across restart and fork.** Adopting another epoch
   records the current request-order high-water mark. A different epoch on any
   request issued at or before that mark is rejected. Same-epoch revision checks
   remain in force. A fork copies both the counter and barrier. The regression
   has two requests in flight when the first adopts NEW, then delivers OLD on
   the later-issued request, verifies parent and fork reject it, and verifies a
   newly issued request can adopt NEWER.

6. **Grok: freshness timestamps changed clock domains.** Successful sync writes
   wall `Date.now()` into `syncedAt`; remembered server answers also record wall
   time. All existing `since` paths inherit those stamps. `ReadObservation` keeps
   its wall-time behavior, now documented in code. At +25h, the regression checks
   the persisted sync stamp, local offline `since`, remembered server `since`,
   and retained fresh observation `since` all equal wall time while device time
   remains 90,000,000 ms ahead.

7. **Both: tests did not enforce their claims.** A controlled-scheduling held
   observation test asserts publication within 16.7 ms. Injecting a 500 ms delay
   into the built client made this test fail; the original artifact was restored
   immediately. The real-browser timing measurement remains separate from that
   deterministic scheduling assertion. The wire test reads the committed
   `/m/media.sendClock` row back, requires `at !== 1` for the submitted `now: 1`,
   and checks that it is near the actual +25h server time.
