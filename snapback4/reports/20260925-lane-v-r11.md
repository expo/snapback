# Lane V — round 11

The round-10 Grok and Astra findings are addressed. Refused `_ops` idempotency
records no longer acknowledge execution. The client preserves a known authored
refusal even when an older server already supplied acknowledgement evidence.
Positive acknowledgement still repairs an unknown-outcome `E_STORE_REPLACED`.

## Implementation, file by file

- `crates/snapback4-core/src/engine/mod.rs`: restrict the existing bounded,
  principal-scoped acknowledgement lookup to stored `sent` outcomes. This
  applies to both covered receipts and `committed_above`.
- `packages/snapback4/src/writes.ts`: return a known failure other than
  `E_STORE_REPLACED` from acknowledgement selection without saving success.
- `packages/snapback4/src/local.ts`: return the recovered receipt from final
  send preflight. It must not discard a preserved refusal and publish the
  original preflight success instead. The file remains 1,496 lines.
- `crates/snapback4-core/tests/stream_receipts.rs`: exercise real successful and
  refused mutations, stored refusal outcomes, replay, and both receipt ranges.
- `packages/snapback4/test/acquisition.test.mjs`: assert that a known authored
  refusal survives acknowledgement lookup without any save of a success.
- `packages/snapback4/test/web-admission-review.test.mjs`: add the three real
  Chromium regressions below and two client fault variants. The file remains
  1,171 lines.
- `packages/snapback4/CLIENT-AND-OPERATIONS.md` and
  `../llp/3000.013-quarry-states-intent.rfc.md`: document that refusal idempotency
  is not success evidence and that older acknowledgement data cannot replace
  a known authored refusal.
- `JOURNAL.md`: append-only qualification entry. This report and its evidence
  directory record the measurements, failure accounting and reproductions.

Implementation and regression commit: `7df63b7d1`.

## Forms and behavior

No new Quarry form, public API or refusal code. Existing calls retain their
signatures:

```ts
const result = await app.mutate(ops.remove, args, { id });
const receipt = await app.client.write(id);
```

When the server refuses `NOT_ADMIN`, both calls return that failed outcome,
including after a lost response, sync, and reopening. When a stored
`E_STORE_REPLACED` has a matching outbox `sent_seq: 7`, lookup returns
`{ state: "sent", id, seq: 7, replayed: true }` and persists the repair before
catch-up can remove the outbox entry.

## Tests and negative controls

The three new browser cases use real servers, Chromium and IndexedDB:

1. Lose the actual `NOT_ADMIN` response, sync while the refused ID is pending,
   verify it is absent from both acknowledgement maps, then verify the original
   mutation, lookup and reopened lookup all return `NOT_ADMIN`. Inspect the
   actual SQLite `_ops` row and require no audit increment.
2. Retain the real refused `_ops` outcome and sequence as legacy durable outbox
   evidence. A same-ID mutation and lookup, including reopening, must preserve
   `NOT_ADMIN`. This independently tests the client guard against older data.
3. Store `E_STORE_REPLACED` with `sent_seq: 7` and no `observed_seq`. Hold startup
   before flushing; lookup must repair durable history immediately. Apply a
   covering page to remove outbox custody, reopen offline and require `sent`.

The core test also splits successful and refused IDs across the event cut and
image head, so both `acknowledged` and `committed_above` reject refusal records.
The history unit test requires zero success-persistence calls for `NOT_ADMIN`.

Negative controls fail their intended assertions:

- The pre-fix round-10 server acknowledges the refused `_ops` row as sequence
  3. The new browser test requires that ID to be absent.
- Removing the known-authored-refusal guard returns `sent` from `mutate` where
  the legacy-data test requires `failed` / `NOT_ADMIN`.
- Removing `await this.keep(sent)` leaves durable history `failed` where the
  lookup-only test requires `sent`, before flush or catch-up can mask the bug.

## Decisions, deviations and failure accounting

No design deviation. The server change is the explicitly requested outcome
filter; principal scoping, pending-ID bounds and meter limits remain intact.
Final send preflight additionally propagates the guarded receipt so another
existing call site cannot publish a discarded success. No authorization,
disclosure, storage limit or receipt-window change. No acquisition retuning or
cold-acquisition remeasurement in this receipt-only round.

One initial full browser run exposed a test-fixture error, classified as ours:
the shared server had advanced beyond sequence 7, so the synthetic catch-up
page correctly returned `E_STORE_RESTORE`. The fixture now uses
`max(7, current watermark)` for that page while retaining precisely
`sent_seq: 7` with no `observed_seq`. The durability assertion still precedes
all flushing and catch-up. The corrected complete browser file passes.
The old-server control and both deliberately faulty clients are expected
failures, preserved with their reproductions in the evidence directory.

The supplied baseline tail (`== 1 failure(s) in 276 s`, cargo test) was inspected
