## Findings and changes

**Legacy admission floors outlive retirement.** Clock attachment now requests
`queued` with the internal `restore_clock_floor: true` option. The device reads
the complete queue and the existing `server-clock-floor` under one writer
transaction, raises the record to their maximum, and commits before returning.
An unchanged floor causes no metadata write. Ordinary queue reads remain read
transactions. Attachment awaits this operation before reading the floor or
allowing startup replay; an error aborts attachment rather than letting replay
retire the only durable evidence.

The operation uses the queue traversal attachment already needed. The choice of
an internal option on `queued` avoids a separate queue scan or a JavaScript
read/modify/write race. Memory/Wasm and SQLite use the same implementation and
their existing transaction and persistence paths. Synchronous web journal
capture is unchanged. New admissions still commit their floor with their outbox
entry, and offset metadata's non-admission `last` remains untrusted.

**Legacy offset fallback is protected.** A unit test attaches offline with
`{offset: -31 days, last: wall - 5000}`, no `issuedOffset`, no admissions and no
sample. A native integration test writes the old metadata shape into a real
SQLite store after close, cuts transport, and reopens a valid thirty-day session.
It requires zero credential deletions and the restored negative offset.

**Future non-admission `last` is protected.** A separate unit test sets
`last = wall + 120000`, an issued offset of -31 days, and a distinct estimated
offset. It requires issued time to equal `wall + issuedOffset`, while estimated
time follows its own offset.

## Tests and measurements

Focused checks: **6 Rust clock tests**, **40 clock/regression tests**, and
**12 browser/wire/native tests**, all passing. The three new Rust tests establish
the maximum over every queue entry and the existing floor on both stores,
survival after retirement and reopening, no changes on a failed backfill, and
no writes on repeated attachment with an unchanged floor.

The two bridge tests create legacy entries through `enqueue`, verify the floor
record is absent, reopen and attach, and require `1004000` to be persisted before
settlement. They retire the entry, close only the core (no clock flush), roll
wall time back to `1000000`, and reopen: issued time remains `1004000`.

Three deliberate generated-code mutations were rejected and restored:

- Removing `?? state?.offset`: the offline legacy-offset unit fails, issuing
  wall time instead of wall minus 31 days.
- Restoring `last` only when it exceeds wall time: the future-`last` unit fails,
  issuing wall plus 120 seconds instead of its negative issued offset.
- Disabling `restore_clock_floor`: both real bridge upgrade tests fail because
  the durable floor is still absent before retirement.

No existing test expectations were weakened or removed. No new Quarry form,
public client API or refusal code. Existing examples remain covered:
`at: time default now`, `expire at .expiresAt`,
`return clockMessages where .conversationId = conversationId last 20 by .at`,
`query heldTyping(conversationId: conversations) held:`, `client.now()` and
`useNow(deadline)`. Endpoint stamp timing remains as audited in the
[round-3 report](20260925-lane-y-r3.md).
