## Invariants and the commit boundary

The client reference and implementation state I1–I5:

1. **I1:** every revocation path compares the currently stored bearer. A
   successful explicit logout first commits a noncredential tombstone.
2. **I2:** a failed auth operation preserves session bytes and epoch, or leaves
   the documented logout tombstone. Failed opening preserves the previous
   runtime and its session, including a guest without another recovery method.
3. **I3:** issued tokens remain owned by a live runtime, the saved session or
   retirement custody. Displacement is journaled before commit; replay waits
   for displacement and removes acknowledged entries.
4. **I4:** observing a newer epoch fences the prior principal's client. This
   includes wire operations, device reads, cached observations and retained
   media access through the client.
5. **I5:** epochs advance only in the atomic record that commits replacement or
   logout. A failed session write cannot leave a separately advanced epoch.

The session record now carries `snapback4Epoch` and `snapback4Backend` alongside
its ordinary Session fields. The old separate `.epoch` remains a readable
migration floor. A replacement prepares its client and retirement journal,
then performs one atomic session-key set containing both bearer and epoch.
The previous client remains live until commit. Automatic refresh, local sync,
local outbox replay and online journal replay start after commit. Successful
commit retires the previous client; failure retires only provisional tokens.
No fallible device constructor follows the commit. The local startup/acquisition
barrier still completes before sign-in returns; a post-commit transport failure
reports auth.why without rolling identity back.

Logout atomically replaces that value with a backend-bound tombstone containing
its epoch and retirement obligations. It can shrink a full store without
allocating a new key. A failed write leaves the old bytes untouched. A later
sign-in copies the tombstone's epoch into its atomic session record. Retirement
is separate maintenance: it removes acknowledged journal entries and clears
acknowledged tokens from the noncredential tombstone. Every replay rechecks the
stored bearer, including stale peers, close, failed open and successful barriers.

## Forms and fixed regressions

No new Quarry or public authoring form. Existing calls retain their syntax:

```ts
const app = createApp({ url, device, sessionStore });
await app.auth.guest();
await app.auth.login(email, password);
await app.client.refreshSession();
await app.auth.logout();
await app.client.signOut(); // same atomic boundary as app.auth.logout()
```

The new focused cases prove:

- A fourth-session-save fault either leaves the original guest intact or is
  eliminated by the single-commit implementation; it cannot lose both accounts.
- A failing device constructor preserves the original guest and its live token.
- A failed bearer commit preserves epoch zero; a peer can still refresh the
  original session instead of logging it out.
- Acknowledged retirement removes both journal and tombstone entries.
- After observing replacement, an old local client refuses query, mutation,
  cached observation and asset access, even if remote logout is offline.
- A provisional online login does not replay pending writes; successful retry
  replays the original mutation ID after commit.
- A failed near-expiry local restoration does not start rotation before device
  opening succeeds, so the original guest remains usable.
- A foreign tombstone cannot dispatch credentials or be relabeled by logout.
- Storage comparison failures return typed query/write/action/media refusals,
  preserve the stored session, and allow a later read to recover.
- Class-based SessionStore adapters retain their prototype methods and receiver.
- Public Client signOut/logoutAll use the app's atomic logout boundary; a
  retained old client cannot log out the newly selected account.

All round 6–9 scenarios remain. Assertions that deliberately change: epoch and
bearer now share one write; tombstone promotion needs no separate marker;
auth-refusal cleanup does not silently commit logout; the near-expiry constructor
now defers its refresh until opening commits. Failure injection targets the new
atomic commit instead of a removed second save or delete. The poll observing
late revocation retries UND_ERR_SOCKET from an aborted pooled connection while
still requiring the server's E_AUTH within the original bound.

## Model, coverage and discoveries

The model uses actual createApp/Client instances, three slots with distinct
runtime identities across close/reopen, one store and one mock identity server.
The server tracks live tokens and refresh ancestry independently. Store get,
set and delete failures are injected before arbitrary numbered operations;
individual writes are atomic. Auth replies can be held after server commit,
including signup, login, guest, refresh and logout replies. Query checks exercise
principal isolation. The oracle checks I1 at remote revocation, I5 at every
store write, failed-operation I2 at quiescent boundaries, I4 at wire dispatch
and public state, and I3 ownership and eventual retirement after fair recovery.
Overlapping operations may linearize independently; they are not compared as
one isolated failed transaction.

The default suite runs seeds **1–2,000**, each with two setup commands and 24
random commands: **52,000 commands**. The 120-sequence sweep injects each of
get/set/delete failures at positions 1–40 after a rotation whose persistence
read failed. Four reduced model discoveries also run as named regressions.
The test prints the seed and a deletion-minimal reproducer on failure. It checks
that every operation, each fault kind and each held-reply type was exercised.

Beyond findings 1–3, the model found:

1. **Stored-token revocation after a read failure.** A failed get during signup
   reached cleanup that could POST logout for the still-stored token. Initial
   baseline seed 1 reduced to signup with get #11 failing.
2. **Late guest response after close.** Closing while guest issuance was held
   discarded the returned token without retirement. Reduced to held guest,
   then close.
3. **Unpersisted refresh successor lost on replacement.** A failed persistence
   read left the successor in the raw client; replacement detached that client
   without retaining its token. Reduced to guest, refresh with get #5 failing,
   then held guest.
4. **Repair during failed replacement changed storage.** An initial round-10
   implementation retried the old client's save during release. The systematic
   sweep found get #10 and set #4 could then fail the replacement after the
   previous session bytes had changed. Keeping the previous owner until commit
   removes that premature release/repair.
5. **Closed runtime returned to restoring.** A late epoch observation during
   queued sign-ins and close fenced an already closed app, whose cleanup could
   no longer publish completion. Seed 104 supplied the fixed seven-command
   sequence. Closed apps now stay signed out.

One later I4 failure was an **oracle defect**, not a product defect: the model
attributed a closed runtime's late retirement reads to a reopened runtime in the
same slot. Runtime identities are now distinct. No failing oracle was waived.

Negative controls all fail with reduced counterexamples:

- Removing stored-bearer protection: I1 fails.
- Writing the epoch separately before the bearer: I5 fails at the store boundary.
- Disabling retirement cleanup: the acknowledged-journal assertion fails.

## Required limit / stopped part of the absolute guarantee

Literal unconditional I3 cannot be implemented with the existing server/store
interfaces. Concrete counterexample: server refresh consumes T and commits S;
the response carrying S never reaches the app; every store write/revocation is
unavailable; the process is killed. No client record contains S, and T cannot
revoke its already-rotated family. A new runtime cannot reconstruct S. Even a
received successor cannot be made durable while every store set fails and the
process is forcibly lost. I did not weaken custody, claim that case passes, or
add an unapproved server issuance-recovery protocol. The implemented/modelled
liveness guarantee assumes eventual response delivery and storage/network
recovery while an owner survives, with lifecycle retries to drain retirement.
This limitation is explicit in the reference and LLP; the model ends by
delivering held replies, repairing faults and retrying logout.

Atomicity also assumes a rejected individual set did not mutate its key, and
cooperating runtimes share the session lock (Web Locks across browser tabs;
within one JavaScript runtime on other hosts). These interfaces cannot promise
transactions across arbitrary noncooperating external writers or processes.
The durable format and deferred startup are intentional changes required by
I1–I5. README stays unchanged at 296/300 lines. No authorization/disclosure rule,
engine meter, Quarry form, asset policy or native ABI changed.
