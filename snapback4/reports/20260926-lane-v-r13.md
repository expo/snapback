## Running examples and evidence

No new language or API forms were added. The existing forms now keep their
meaning through the reviewed upgrade paths:

- `await client.write(id)` for a legacy row with
  `{ observed_seq: 3, receipt_store: { id: A } }` remains bound to A after the
  device adopts B. Both transports send `{ id, args, newIds, store_id: A }` to
  the endpoint; B refuses `E_STORE_REPLACED` before execution. Both real-server
  audit queries remain **0**, and the refusal survives an offline reopen.
- `await client.write(id)` after an orphan's same-ID replay recovers
  `{ state: "failed", why: { code: "NOT_ADMIN", ... } }`. After the adopter
  closes and its database is removed by another recovery, lookup and an offline
  reopen still return `NOT_ADMIN`. The shared order stays
  `[before, id, after]`; conflicting later input cannot change the authored
  refusals or their positions.
- An old `apply` page with `acknowledged: { [id]: seq }` and no `sent` records
  only a decision. `await client.mutate(op, {}, { id })` and lookup remain pending
  with no terminal history until same-ID replay returns `NOT_ADMIN`. Both stores
  replay once, preserve the original binding, leave the audit at **0**, and
  retain the failure after reopening.

## Additional review Low: stopped pending a design decision

Grok also proposes invalidating previously stored `sent` history whenever the
remaining legacy outbox lacks `success_seq`. This was not one of the three
numbered round-13 changes. I stopped that part under the lane's instruction to
report a design conflict instead of weakening durability. Round 9 and the current
LLP §6 explicitly make known `sent` immutable and forbid another POST for it;
only unknown-outcome `E_STORE_REPLACED` is correctable.

Concrete counterexample: an old client receives a genuine successful response,
saves `{ state: "sent", id, seq }`, then its outbox-settlement transaction aborts.
An old stream observation leaves `{ observed_seq: seq, receipt_store: { id: A } }`
with no success qualifier. On offline reopen, these bytes have the same shape as
the older bug's manufactured success for an actual `NOT_ADMIN`. Invalidating all
such history makes the genuine durable success pending and requires a POST,
contrary to the existing guarantee. The history format does not record how that
old `sent` was established.

Reproduction from `snapback4/`:

```sh
node reports/20260926-lane-v-r13-evidence/stored-sent-ambiguity.mjs
```

It uses the Wasm device over memory persistence and two real-server scenarios:

| Original server outcome | Upgrade history | Offline lookup | Audit | Replay POSTs |
| --- | --- | --- | --- | --- |
| `NOT_ADMIN` | Old manufactured `sent`, unqualified legacy outbox | `sent` (open defect) | 0 | 0 |
| Committed success | Real saved `sent`, unsettled legacy outbox | `sent` (existing guarantee) | 1 | 0 |

The reviewer’s stored-false-success case therefore remains open. It requires a
supervisor ruling about historical `sent` custody, distinct from a sequence with
no terminal history. I have not weakened the latter's new qualification rule or
changed the known-terminal policy. No other open scoped problem is known.
