`posts` contains only original posts. Its body is bounded to 1,000 characters, an authoring choice because the task did not give an original-post bound. `replies.postId: posts` references an original; reply body is `text <=100`. `by byPostId: postId, id` supplies the requested order and `cap 10 by postId` enforces the per-original limit. `after insert <- exists posts[.postId]` requires the original to exist by the end of a reply insertion. Both tables have public read rules. No write operations were requested, so no write API or write grants were added; omitted write rules deny ordinary writes. Table references alone do not ensure existence or delete cascades.

`openReply(replyId: replies)` reads `replies[id = replyId]`: one reply row or null for an absent target. `optionalReply(replyId: replies ?)` uses the same point spelling and also admits null or an omitted input. `thread(postId: posts)` reads `replies[postId = postId] by byPostId`: an ascending page of at most 10 reply rows using the schema cap. An empty thread is an empty page, not null.

The diagnostic `positionalPostReference(k: posts)` returns `replies[k]`. `why` confirms `byPostId (postId = k)`, result page, with reason `single exact positional type match`. The argument matches the declared type of `replies.postId`, so this is a thread read, not an open-reply-by-ID operation. `explicitPostReference(k: posts)` spells that same meaning as `replies[postId = k] by byPostId`. To open a reply, the caller must instead supply a replies reference, as `explicitReplyReference(k: replies)` and `replies[id = k] by byId` demonstrate. No posts-to-replies conversion or generic-ID helper is used.
