## Data structures and complexity

`partition::pending::PendingEvents` owns an ordered `Vec<Option<Event>>`.
Two hash maps hold vectors of live positions: `(table, id)` for Put/Del,
`(partition, table, id)` for Join. Their lengths are the earlier-event
counts, with expected O(1) lookups. All four log helpers go through `push`;
Scope occupies its original slot without contributing to either count.

A withdrawal drains only the positions after that key's preserved prefix,
drops those event images, and leaves empty slots. Preserved positions are
not revisited. Every event is added once and withdrawn at most once. Taking
the buffer resets its maps and flattens the live slots in insertion order,
once per commit consumer. Inductively, a push appends the same event, and
a withdrawal clears precisely the matching live positions after the old
retained prefix; neither operation changes the relative order of survivors.
Birth maps also use hash maps, removing ordered
map overhead from this bookkeeping; their iteration order is never used.
Expected bookkeeping cost is linear in generated events, with storage
linear in generated events and distinct keys. Empty slots persist until
the commit is taken; withdrawn row images are released immediately.

`key_has_row` is byte-for-byte unchanged, including index probes. This
change makes no claim about the complexity of those probes or about the
store, schema traversal, and append/coalescing outside event bookkeeping.
All meter calls remain at their previous locations with the same arguments.

## Consumers

| Consumer | Preserved view |
| --- | --- |
| `partition::account_row_change` | Counts and withdrawals use live per-key positions, equivalent to filtering/retaining the previous Vec. |
| `engine/mod.rs`: activation rebuild, expiry sweep, mutation, seed, seed-delete, normal load, stored-row load | Each of the seven former `mem::take` sites calls `events.take()` and receives the same dense event sequence. |
| `engine/postgres/mod.rs`: mutation, load, seed | The three equivalent handoffs also take the dense sequence. |
| `engine/job.rs`: Quarry job chunks | Dense sequence before the unchanged empty-event commit condition and append. |
| `engine/native.rs`: native job chunks | `ChunkOutcome.events` remains `Vec<Event>`; downstream job commit and append are unchanged. |
| `partition::append` | Unchanged. Receives only live events, preserving last-row-event coalescing and join/scope ordinals. |
| Mutation outcome event counts | Continue to use the compact vector's length at the same point, before append coalescing. |
| Meter | No meter reads the event slots. Partition charge sites and outcome meter capture remain unchanged. |
| `engine/recorded.rs` activation test | Test-only `is_empty()` ignores tombstones. |
| New equivalence test | Test-only iteration ignores tombstones; final take is also compared with the reference Vec. |

Other `events` collections (snapshots, stream pages, native outcomes) keep
their public types and are not this runner buffer. The entire new buffer
and both birth maps remain under `cfg(feature = "sqlite")`; logless WASM
hosts do not construct them.

## Equivalence and mutation proof

`partition/born_reference.rs` copies the old log helpers, accounting
function and retain-based withdrawal from the base. Only the event-vector
parameter is separated from `Runner`. A scripted source comparison checked
those copies and the unchanged `key_has_row`.

`randomized_commits_match_original_events_and_meter` uses 64 fixed seeds,
eight sequential commits each and 128 random writes per commit, plus
explicit renewal/revoke/rebirth, delete/reinsert and row-id/group-id
collision prologues. It exercises
public and principal row audiences, multiple content dependents, synced
and online-only grant targets, changing keys, expiry, predecessors and
siblings. Each implementation sees the same post-write store and has its
own birth maps and meter. It compares every event and its position after
every change, both birth maps, the meter, and the final compact vector.
The generator exercises the accounting boundary directly: it writes images
to real SQLite rows/indexes, then invokes both functions, including overlapping
physical grant siblings. The existing interpreter, disclosure and device
suites separately cover admitted writes and the wire contract.

The first equivalence run passed all 512 commits. The mutation probe removed
the Join position update in `PendingEvents::push`: event equivalence failed
at seed 1, commit 0, step 1, leaving two joins where the oracle had none.
The source was restored byte-for-byte in a `finally` block; SHA-256
`fc19790f9283adaf555145ff52407a7c6d9e54890100a88a48921ab65d5cbc94`
matched the original bytes. The full core suite passed after restoration,
including the final equivalence test with typed canonical row/group IDs.

## Measurements

All five original targets passed. Baseline executables were built from the
base and saved under `/tmp/born-perf-before-{timing,sim,device}` before any
fixed code was compiled. Direct test-binary runs exclude compilation and
use `--nocapture --test-threads=1`.

| One commit making 5,000 grants | 2.301138 s | 0.613283 s | 1.2 s |
| `w13c2_five_thousand_lanes_cut_without_cursor` | 11.44 s | 1.44 s | — |
| `following_is_full_and_complete_at_the_envelope` | 396.87 s | 31.41 s | — |
| `w8b_wired_calibration_acquisition_on_server_and_both_stores` | 2,437.60 s | 49.58 s | — |

The guards are approximately twice the observed after times; both original
measurements exceed their guard. The full core run passed both guards with
its normal test concurrency. Each fixture asserts exactly one commit; the
grant fixture also checks that all 5,000 join transitions reached the log.

The two commit measurements surround `Engine::seed_at`, including append
and commit; row construction and schema compilation are outside the timer.
The three existing targets use the Rust harness's full-target elapsed time,
including seeding. Before whole-process times were respectively 8.836, 2.381,
13.727, 396.973 and 2,439.816 seconds; startup is not included in the table.
After whole-process times for the three existing targets were 3.819,
31.500 and 51.156 seconds. All three passed before and after. The measured
speedups are 7.9× (lanes), 12.6× (Following) and 49.2× (w8b).

The named targets were built with:

```sh
cargo test -p snapback4-sim --test clique --no-run --message-format=json
```

Their saved executables were run separately, with the full test-name
