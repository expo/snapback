## Existing forms exercised

After both tabs restore the same account, the ordinary API now handles a saved
peer rotation:

```ts
await tabA.client.refreshSession();
await tabB.auth.logoutEverywhere(); // Revokes A's successor and external siblings.
```

The in-flight variant may initially return E_AUTH because the server consumed the
only available bearer. Its committed global obligation remains durable; when the
held successor arrives, it receives logout-all, including after the requesting
tab closes. E_AUTH alone is never treated as proof of global removal.

```ts
const captured = app.client;
const result = await app.auth.logoutEverywhere();
// If the tombstone write failed: result.ok === false, auth.why describes it,
// auth remains signed-in and captured remains the current, usable client.
// Once the tombstone commits: signed-out, and captured is permanently refused.
```

There are no new Quarry forms or refusal codes. README and starters did not need
changes in this round; the public forms already exist.

## Invariants and model coverage

I1–I8 retain stored-bearer protection, atomic failure/epoch commits, retirement
custody, principal isolation, coherent public identity, refused-session exclusion
and permanent fencing of hidden handles. The deliberate change is **when global
logout hides the account**: after its durable fence, not before a fallible write.

**I9:** acknowledged global logout removes every session of that principal at
the server's revocation point, including external siblings and committed refresh
successors with undelivered responses. A deliberate new sign-in after that point
is a new session, not evidence that global logout failed. No client-only logout
can prevent future password sign-ins; the model checks descendants of covered
sessions separately from newly issued login sessions.

The standalone affected run passed **117 tests**, including **5,000 seeded
sequences (seeds 1–5,000), 130,000 commands, 20 fixed model regressions and a
120-sequence indexed fault sweep**. The model uses three real createApp runtimes,
one mock server and one shared atomic-key store. Its **23 operations** are signup,

## Discoveries and regression strength

The widened model found two additional product defects during implementation:

1. **Seed 104, retirement:** guest in C; B restores; C globally logs out;
   stale B globally logs out. B recreated the already acknowledged token's
   global retirement. An existing principal/generation fence now serves that
   request; a completed fence never promotes the consumed credential again.
2. **Seed 1961, I6:** guest; hold the global tombstone write; queue login; release
   the write. The newer revision suppressed the old call's signed-out
   publication while its client was retired. A committed logout always hides
   its retired view before the queued login runs.

Both deletion-minimal sequences are retained. The final 5,000-sequence affected
run found no additional defect.

Six negative controls each failed their targeted regression: selecting the
caller's stale token; disabling late global promotion (both real-server and I9
model cases); removing the principal check; publishing before tombstone commit;
and ignoring the completion watermark. Mutations were applied only to generated
dist files, restored afterward, and never committed.

The initial local held-rotation test was too strict about a harmless ordinary
logout *after* acknowledged global revocation. It now requires that the first
retirement request for the successor is logout-all and that external siblings
die. This still fails when global promotion is removed.

Two existing failed-fence tests caught a temporary implementation regression:
an attempted journal write blocked discarded login/refresh retirement while all
writes failed. Live-runtime custody and successful comparison reads now allow
that retirement; both regressions pass. The other changed old assertion pinned
the superseded precommit signed-out behavior and was updated intentionally.
These development failures were ours, not baseline or environmental exceptions.

## Decisions, deviations and open limits

The persisted global fence is an engineering choice for the brief's silent
storage representation. It binds principal, epoch and retry credentials; completed
watermarks hold no bearer. Keeping a compact watermark is necessary to distinguish
a late old response from a new login after global acknowledgement.

Round 13 explicitly supersedes round 12's behavior on a failed global fence.
Those tests and the living documentation were changed; earlier reports/journal
entries remain historical. No requested work was omitted. No server protocol,
engine authorization/disclosure rule, meter, public export, package version,
starter, offline-shell implementation or README changed. No push or publication.

There is no unresolved reproduction from this round. Previously documented
protocol limits remain: hold a minted response, fail all persistence/revocation,
then kill its only runtime; its unknown token cannot be recovered without a
server issuance receipt. Likewise, lose a successful logout-all acknowledgement
and its runtime before local cleanup: a consumed bearer cannot prove global
success on retry. Complete refusal-fence failure followed by process loss cannot
exclude the indistinguishable old bytes during offline reopen. These cases
require server receipts or recovered durable storage, not weaker client checks.
