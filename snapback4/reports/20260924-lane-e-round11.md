# Lane E round 11 — refusal fencing, global logout, and the wider model

Round 11 fixes the three review findings and extends the executable session
model from I1–I5 to I1–I7. No new public API or Quarry spelling was introduced.

## Implementation, file by file

- `packages/snapback4/src/app.ts`: a confirmed refusal conditionally commits a
  logout tombstone for the still-stored bearer, with one retry of a transient
  storage failure. A different stored successor is untouched. Refusal cleanup
  cannot wait behind a held sign-in. Epoch observation fences every older scope,
  including rollback candidates, before any retirement callback. Auth and client
  notifications expose a coherent view; public client close routes through app
  close. Global logout blocks new rotations, awaits the existing one, and
  atomically places its latest bearer in private global-revocation custody.
  Revision guards cover queued, superseded and closed operations. Close retries
  retained acknowledgement cleanup without sending a new global revocation.
- `packages/snapback4/src/app-revocations.ts`: backend-bound journals and
  tombstones carry global obligations separately from ordinary retirement.
  Ordinary logout cannot consume a global retry bearer. Only successful
  logout-all acknowledges a global obligation; E_AUTH does not prove that the
  other sessions were revoked. Received acknowledgements survive local cleanup
  failures in the live runtime, retry idempotent cleanup, and clear on close.
- `packages/snapback4/src/client-start.ts`: private registration/waiting for a
  client's current rotation; no new public exports or rotation is initiated.
- `packages/snapback4/src/client.ts`, `src/local.ts`: register each tier's
  existing rotation promise with that private coordination mechanism.
- `packages/snapback4/test/app-state.test.mjs`: 14 focused cases: 13 against the real
  server and one isolated foreign-backend credential test, described below.
- `packages/snapback4/test/helpers/app-server.mjs`: extract the existing real
  server fixture and bounded polling helper so both app test files share them.
- `packages/snapback4/test/app.test.mjs`: use that helper and replace the test
  that incorrectly expected a refused bearer to remain restorable. Earlier
  round 6–10 regressions remain.
- `packages/snapback4/test/helpers/app-session-model.mjs`: add global logout,
  external revocation, held storage writes, offline reopen and public client
  close; observe I6 inside both auth and client callbacks and I7 on restoration.
  Track actual runtime identities, private retry custody, pending storage values
  and global journal custody. Recovery also verifies acknowledged entry removal.
- `packages/snapback4/test/app-session-model.test.mjs`: default 5,000 seeds,
  coverage requirements, 13 reduced fixed sequences and the existing 120-point
  storage-failure sweep. Failure output includes a deletion-minimal sequence.
- `packages/snapback4/CLIENT-AND-OPERATIONS.md`: document I1–I7, refusal and
  notification boundaries, global retry custody, acknowledgements and limits.
- `llp/3000.013-quarry-states-intent.rfc.md` §6: record these implemented

- `JOURNAL.md`: one dated append with implementation, measurements and limits.

Existing forms now exercise these guarantees:

```ts
await app.client.refreshSession(); // E_AUTH tombstones its still-stored bearer.
await app.auth.logoutEverywhere(); // Waits for rotation; retains failed retry custody.
await app.client.close();          // Auth becomes signed-out; kept session survives.
const reopened = createApp({ url, device, sessionStore, fetch: offlineFetch });
await reopened.ready;             // Known-refused bearer opens no replica.
```

## Invariants and test coverage

- **I1:** compare the stored bearer before every retirement dispatch; never
  revoke it while it is the stored session.
- **I2:** failure preserves session bytes and epoch, or commits the documented
  logout tombstone.
- **I3:** minted tokens have live or durable custody, and retirement drains
  after displacement; fair recovery leaves no live mock-server tokens.
- **I4:** observing the stored epoch fences all superseded principals and
  rollback candidates before further reads, writes or publication.
- **I5:** epoch and session change atomically only at replacement/logout commit.
- **I6:** published auth state, viewer and current client agree, including
  inside raw-client notifications and after public-client close.
- **I7:** a server-refused bearer is not restored by a later online/offline open;
  the informed runtime and replica lose access. Durable exclusion assumes the
  refusal fence can be stored before the last informed runtime is lost.

The real-server cases prove: online/local refusal excludes offline reopening
and local replica acquisition (2); held Charlie replacement cannot roll back to
Alice (1); online/local global logout waits for a committed refresh response and
retains a failed retry both in-process and across restart (4); schema-acquisition
refusal prevents offline replica reopening (1); global logout owns a successor
whose ordinary session save failed (1); foreign global credentials never dispatch
(1); online/local client notification boundaries preserve I6 during held
refusal cleanup (2); online/local public-client close preserves I6 and the saved
session (2).

The standalone model ran **5,000 sequences, seeds 1–5,000**, each with two setup
commands and 24 generated commands: **130,000 commands** over three actual
createApp runtimes and a mock server/store. Its 14 commands are signup, login,
guest, refresh, logout, logoutEverywhere, close, closeClient, reopen,
reopenOffline, query, server revoke, holdStore and release. Server revocation is
followed by either refresh or query. It holds committed signup/login/guest/
refresh/logout/logout-all responses and pre-commit store sets while peers act.
Faults target get/set/delete positions 1–12; the separate 120-sequence sweep
covers positions 1–40 for each kind after an unpersisted rotation.

Measured standalone coverage: **3,487 get, 356 set, 94 delete faults**;
**4,630 held storage writes**, **24,723 peer commands while storage was held**;
**4,773 external revocations**, **9,007 offline fetch attempts**. Held responses:

## Additional defects discovered and fixed

Beyond the three incoming findings, the widened model found:

1. A transient refusal-tombstone failure allowed later offline restoration
   (seed 32): retry the conditional commit under the same lock.
2. Refusal cleanup queued behind held sign-in left rejected bytes restorable
   (seed 125): begin conditional cleanup outside the auth/network queue.
3. An older queued global logout advanced revision after a newer logout and
   suppressed its completion (seed 79): capture revision at invocation.
4. Auth calls on a closed app changed revision and stranded a held logout in
   restoring (seed 183): closed operations return without revision changes.
5. A queued global retry with no owner retained a restoring public view
   (seed 1024): complete the signed-out view on that path.
6. A late refusal republished restoring after close (seed 1630): closed apps
   always publish signed-out while cleanup continues.
7. Global success followed by failed journal deletion retried a consumed
   bearer instead of cleanup (seed 441): keep the acknowledgement until cleanup.
8. Epoch retirement emitted client callbacks before hiding the old signed-in
   view (seed 1 with client observers): fence all scopes, publish, then retire.
9. A retiring runtime lost its global acknowledgement after cleanup's session
   read failed (seed 4288): retry local cleanup and flush acknowledgements on close.

I6-directed real-server probes additionally found and fixed credential-loss
notifications preceding the app view change, and `app.client.close()` leaving
a signed-in auth snapshot. A model-inspired real-server probe found global
logout comparing an unpersisted successor against storage; it now compares the
last kept bearer while retaining the successor as the global retry credential.
Every item has a fixed regression; the randomized test also observes client
notification boundaries and generates public-client close.

Oracle refinements distinguish a restoration already started before a refusal
from a *later* open; include tokens owned by held store writes and global retry
records; preserve runtime identities across reopened slots; and test orphaned
custody only when responses and storage are quiescent. The final fair-recovery
phase releases all held operations, repairs faults, retries logout, closes and
reopens. It requires zero live tokens and removes acknowledged journal entries.
These are explicit liveness assumptions, not claims about crashes during an
unavailable store.

## Limits / stopped part of an unconditional guarantee

**I7 with total storage failure and process loss cannot be guaranteed by the
current interfaces.** Reproduction: store T and its replica; the server refuses
T; every attempt to store a refusal tombstone fails; kill every informed runtime;
open offline on the same old bytes. The new runtime has no evidence of the
refusal. Denying that case unconditionally would also deny ordinary supported
offline restoration. The informed runtime denies access and reports the storage
failure. I documented this counterexample rather than claiming a nonexistent
durable fence or changing the server protocol.

The round-10 I3 limit remains: refresh consumes T and creates S, its response
never arrives, no persistence/revocation succeeds, and the process dies. The
client cannot reconstruct unknown S with the existing protocol. Global logout
has an analogous receipt limit: a successful response/acknowledgement is lost
before durable cleanup and process loss; a later E_AUTH with the consumed bearer
cannot establish whether all other sessions were revoked. The obligation remains
and refusal is reported. Stronger guarantees require recoverable server issuance
and revocation receipts; that protocol work was not undertaken in this lane.

Atomicity assumes rejected individual writes leave their key unchanged and
cooperating runtimes share the lock. Model liveness assumes eventual response
delivery and storage/network recovery while an owner survives. No authorization
rule, disclosure rule, engine meter, public export, asset policy, native ABI,
package version, guide form or starter changed. No push or publication.
