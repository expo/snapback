## Behavior and implementation choices

`ServerClock.raiseIssued(time)` raises the monotonic issued floor without
changing estimated server time. Valid increases notify subscribers and force
deadline rescheduling, including a one-millisecond crossing that would otherwise
be ignored as sample noise. Invalid or lower values cannot change the floor.
The floor is already durable in the admission transaction; this method adds no
offset save and never restores a non-admission `last`.

Orphan adoption reports the maximum transferred `entry.now` only after the
destination persistence batch commits. The local client registers its listener
before clock attachment and therefore before the first post-attach
`observe_store`. The listener immediately raises issued time; flushing waits
until client initialization has established its machinery.

A mutation may already have synchronously captured its journal entry while
recovery holds the serialized web device chain. At execution, the shared journal
admission helper stamps it with `max(requested.now, server-clock-floor)`.
This is the engineering choice for serializing recovered time with waiting
admissions: custody still happens synchronously before the first await; admission
and prediction use the committed floor after earlier recovery. Journal replay
uses the same helper. The client also adopts the actual admitted entry's time.
No additional queue scan is needed, only a metadata read per web admission.

The Rust floor writer already raises a nonzero floor correctly. Its tests now
start recovery at `1002000`, import `1004000`, retire the entry and reopen after
rollback, on memory and SQLite. Receipt recovery is covered too. The web transfer
test now includes two increasing timestamps, checks the maximum on the existing
live clock, and retains its atomic-batch and retirement/reopen assertions.

## Tests and measurements

Focused checks: **44 clock/live/regression tests**, **14 browser/wire/native
tests**, and **9 Rust clock durability tests**, all passing.

The two new live tests keep wall time fixed at `1000000` and import orphan times
`1002000` and `1004000`. One transfers during the first post-attach observation,
before startup returns. The other transfers after startup, deliberately holding
the destination persistence commit while another mutation captures its journal
entry at `1000000`. The journal record must already exist before the held commit
is released; the admitted entry must use at least `1004000`. Both require the
existing client's clock and a subsequent admission to reach `1004000` without
reopening.

The controlled deadline test first raises time to one millisecond before expiry,
then recovers the final millisecond. It requires the held answer to drop the row
without advancing wall time or delivering a timer. The unit test additionally
requires the server estimate and server-answer delay to remain unchanged.

Five deliberate mutations failed and were restored:

- Write a floor only when its previous value is zero: both Rust store cases fail
  with `1002000` instead of `1004000`.
- Register the recovery listener after initial sync: startup recovery leaves the
  live clock behind, failing the first-observation test.
- Use the captured timestamp without clamping at execution: the waiting mutation
  remains at `1000000`, failing the serialized-admission assertion.
- Suppress floor notifications: the held answer retains the expired typing row.
- Report only the first transferred timestamp: the live clock misses the maximum.

Initial development checks caught two lane-owned issues, corrected before full
qualification: `Queued.now` is optional in the compatibility type, and the new
test fixture initially supplied invalid caller write IDs (`E_WRITE_ID`, which
also left its waiting-admission barrier untriggered). The production guard now
uses zero for an absent timestamp, and the fixture uses `mintId()`.
