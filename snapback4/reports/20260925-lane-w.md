# Lane W: Following after unfollow and the periodic read stall

2026-09-25, `expo-build-1000`, branch `sb4-intent/w-following-device`, base
`2c595ed6c`. Tests and measurements only: no runtime fix is justified by the
reproductions below. No push, publication, version bump or budget change.

## Findings

### d-02: the intended sequence passes; the frozen harness has a missing precondition

The explicit follow → unfollow → repost sequence, repeated three times in one
device session, passes on native SQLite, memory, and the release-built Wasm
device. The server and device have identical Following pages after settlement
and publication. A repost predicts its own inbox copy; follow and unfollow
queue without prediction. Unfollow removes the original without removing the
viewer's independent repost.

There is a concrete counterexample to the grader's attribution. The frozen
`repost-following-feed-surface` choreography:

1. Creates a new Alice post.
2. Samples Bob's Following projection with `() => true` as its wait predicate.
3. Calls `toggleFollow` only if that new post is already rendered as a direct card.
4. Reposts from Global, then fails if Following has a direct card too.
5. Ends a successful attempt by following Alice again.

On attempts 2–3, Bob can still follow Alice while the newest event is not yet
delivered. Step 2 returns an absent card immediately, so step 3 skips unfollow.
Once delivery arrives, both cards are correct. Inspectable source:
`~/clique-cmp-20260925/instrument/choreography/choreography.mjs:1488`
(the wait implementation is at line 935). The repository's frozen copy has the
same logic at `benchmarks/tools/social-messenger/choreography/choreography.mjs:1541`.
Neither copy was changed.

The SDK test reproduces precisely this faulty inference with delivery held:
the new original is absent locally, while an authorized `exists follows`
query is **true on both server and device**. Skipping unfollow and then
allowing delivery/reposting yields the two cards. Explicitly unfollowing then
leaves exactly the repost. This is reproducible on Wasm and native SQLite.
It distinguishes delivery lag from stale edge images, stale inbox filtering,
or a prediction that survived settlement incorrectly.

This establishes a harness race capable of producing the reported symptom,
not a retrospective proof of every failed browser attempt. The original
browser app and instrument were not rerun; the copied calibration directory
lacks its installed dependencies and populated stores. The supervisor should
rerun after making the follow state an explicit acknowledged precondition
(query the edge, unfollow if present, wait for the acknowledged change).
Absence of a just-created card cannot establish absence of an edge.

### d-09: not reproduced; checkpoint I/O remains a candidate

The supplied grader trace already distinguishes the receipt's stalls from its
independent macOS remeasurement (`~/cal20-grading/trace.md`, phase 3h): all ten
independent probe p95s are below 5 ms and the 500-follow/5-follow ratio is 1.09×.
The 27–31 ms signature belongs to the builder's scale receipt. That distinction
does not explain the stalls, but rules out treating them as a reproduced
invariant of every read batch on that host.

Generated a disk fixture using the accepted Clique target's actual Quarry
program: 1,000 profiles, 50,000 original posts, 505 follows (readers with 5 and
500 follows), 1,000 memberships and 100,000 messages, including a 10,000-message
chat. Posts, follows and derived inboxes are produced by ordinary engine
mutations/delivery; other source rows use the engine's seed path. The resulting
SQLite file is approximately 477 MiB. This is a controlled scale fixture,
**not calibration #20's full 167,157-action replay**: its store was not copied
to this host. The fixture's source is the checked-in acceptance target
`crates/snapback4-sim/tests/fixtures/intent-clique.q`.

Each probe does 20 warmups and **1,000 sequential measured reads**. The same
unchanged production binary is used throughout, built with Rust 1.97.0 and
`LIBSQLITE3_FLAGS=-USQLITE_ENABLE_MEMORY_MANAGEMENT`; Node is 24.13.1.
Binary SHA-256:
`bcd59a02a45012eb2c0bf11c83b4254f5129377084866cf7e88d91b6fd992244`.

The first explicit checkpoint can drain accumulated WAL work and exceed a
slice. That is a concrete slow-I/O candidate, not evidence connecting it to
the calibration's repeated 27–31 ms HTTP samples. Ordinary idle maintenance,
the watcher, keep-alive and schedules did not reproduce that signature.
There was no macOS host available in this lane's configuration; the advertised
fleet file is absent. No macOS timings or emulation claims are made.

LLP 3000.013 §4 explicitly allows indivisible row and commit I/O to extend a
cooperative slice. A hard request-latency bound below 5 ms would be false if a
FULL commit takes 28 ms while a request waits for the engine. Neither weakening
FULL nor starving maintenance is a permitted fix. Without the original store,
host and concurrent-work trace, the periodic stall remains unresolved.

No new Quarry form or refusal code was added. Existing forms exercised include:

```quarry
view activity:
  posts where .parentId = null and not .removed { post: .id, actor: .authorId, at, repost: false }
  reposts { post: .postId, actor: .actorId, at, repost: true }
view feed: activity where .actor = viewer or exists follows[viewer, .actor]
query cards(c: cursor ?):
  return feed last 20 by .at after c { *, post: posts[.post] }
mutation unfollow(actor: principal):
  delete follows[viewer, actor]
mutation repost(postId: posts):
  return insert reposts { actorId: viewer, postId, at: now } if absent
```

device change was made. The harness counterexample is retained instead. The
periodic macOS stall was not reproduced, so no performance fix or sub-5-ms hard
bound is claimed. The synthetic scale fixture and lack of macOS access are
explicit scope/evidence deviations. No frozen harness, package or shared
