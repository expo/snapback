# E_REFERENCED

E_REFERENCED means a delete would leave a live row referencing the deleted one through an `on delete restrict` reference — the default for a reference that declares no action. The message names the referencing column (`comments.task`); nothing about the row itself (its id, owner or count) is disclosed, and when several references are occupied the first in schema order is named. A delete reaches every row its `on delete cascade` references reach, so a hidden comment on a cascaded task refuses the project delete too; rows the same delete removes never hold each other back.

Choose what deleting the target should do, on the referencing column: `task: tasks on delete cascade` deletes the referencing rows in the same transaction (with `cap N by task`); `task: tasks ? on delete set null` clears an optional reference that no rule reads; `task: tasks on delete keep` keeps them, naming a deleted row (the behavior before 0.5); `on delete restrict` keeps this refusal and silences `N_DELETE_RESTRICTED`. Or delete the referencing rows first in the same mutation, or mark the target (`archived: true`) and delete in a job.

Two things changed in 0.5 with this code: a delete that consults referencing rows needs read authority on the row it deletes (a caller who may delete but not read gets NOT_FOUND), and a restrict refusal tells the deleter that some row references the target — `restrict` exists to block, so the blocked party sees that it is blocked. A reference other principals create to your rows (a like, a bookmark, an RSVP) should be `cascade`, or anyone can hold your row. A read-through child refuses with E_PARENT_HAS_CHILDREN instead. guide writes.
