# N_REQUIRE_HIDDEN

A program `exists` sees only the rows its caller may read; a rule probe sees every row. So `require exists clinicians[principal = specialist, role = 'specialist'] else UNKNOWN_SPECIALIST` over a roster whose read rule is `.principal = viewer` passes only when `specialist` is the caller: every other clinician's row exists but is hidden, and the require refuses your code, at the require line, with no hidden-row hint. `check` notes N_REQUIRE_HIDDEN when every disjunct of the probed table's read rule admits only the row whose pinned column is the caller and the probe pins that column to something else. Let the callers who run the check read those rows: `read <- .principal = viewer or exists clinicians[viewer]` (a roster its members read), or a role (`… or exists staff[viewer]`). If only the caller's own row is meant, write `principal = viewer`. A read rule with any other disjunct (a grant, a public row) is not noted.

The same note covers a read-rule role arm incompatible with the caller role established by earlier path guards on the same total-unique roster key. A composite principal/role key does not prove roles disjoint; unknown or overlapping arms remain unproved. Explicit service-principal read exceptions are named as exceptions: an ordinary admitted caller can still see false for the hidden target even when the service could read it. Do not broaden a private roster accidentally; use the smallest readable membership projection or move the check to an authorized service mutation.
