# E_CASCADE_BOUND

E_CASCADE_BOUND means a delete's cascade has no fixed bound that fits its program. `on delete cascade` and `on delete set null` write every referencing row in the deleting transaction, so they need `cap N by <column>` on the referencing table: a product limit on how many rows one target can have. A delete then reserves the cascade's whole worst case — every cap along the chain — whether or not those rows exist, so its cost never depends on rows the caller cannot see; `check` refuses a delete whose reservation cannot fit a mutation (or a job chunk). For an unbounded relation: lower the cap if the domain has a smaller limit; keep `on delete restrict` and delete the referencing rows first in a job (`chunk`), then the target; mark the target (`archived: bool`, filtered by readers) and sweep it in a job; or declare `on delete keep` when the rows should outlive the target. guide writes.
