# Essay: Clique on Snapback 4.0.4.12, against Convex, Supabase, and earlier Snapback

This run built Clique as a single-author, timed product: schema, Expo Router client, acceptance, two-client choreography, a custom-client demo, and a 167k-action scale replay. The backend pin was `snapback4@0.4.12` from the public npm registry, plus `snapback4-expo@0.4.12`. I did not read a Snapback source tree. What follows is the experience of that published surface, compared with Convex, Supabase, and the Snapback generations I already know as a product engineer — not a claim that this pin is faster or slower than those systems in production.

## Where the backend reduced friction

The largest reduction is that the backend *is* the schema. Clique's data, rules, live queries, mutations, expiry, receipts, jobs, and the push seam all live in `snapback/schema.q`. There is no parallel migrations folder, no RLS policy file that can drift from the TypeScript types, no "remember to update the Convex validator." `npx snapback4 check` writes `snapback/generated/api.ts`, and the client imports those names. When a mutation is wrong, the compiler names a code (`HANDLE_TAKEN`, `EDIT_WINDOW`, `NOT_ADMIN`) and `npx snapback4 why CODE` explains it. That loop is tighter than Convex's "run the mutation and read the thrown Error" and much tighter than Supabase's "open SQL, open RLS, open the client, discover they disagree."

Three language features carried whole milestones:

Receipts. `receipts chat by .conversation, .ordinal from .sender to members` with watermarks and a `messageReceipts` query is WhatsApp ticks as a table annotation. In Convex I would store per-member high-water marks and compute `sent|delivered|read` in a query. In Postgres I would do the same with triggers or a receipts table and then fight RLS so a user cannot forge another member's watermark. Here the clause is the implementation. M3 choreography passed on that path. I spent time aligning `after insert` membership with the conversation row, which is real work, but it is compiler work rather than production-bug work.

Expiry and once-media. `expire at .expiresAt` plus `image once` is the brief's disappearing and view-once story without a cron I have to prove ran while no client was open. Convex scheduled functions can delete rows; they do not, by themselves, prove that an unopened client cannot resurrect the bytes. Supabase Storage plus a `deleted_at` column is worse: the object can outlive the row unless you also write a storage policy. Snapback 4 treats both as data-model. That changed the shape of M5 from "build a sweeper and a cache policy" to "declare the field and render the kit's unopened/opened states."

Feeds as views. `view activity` unioned with `view following` is the follow graph's read model. I did not maintain a fanout table. I did not write a Convex `homeFeed` that joins `follows` on every call and then add an index later when it hurts. The view is the join, `home` pages it, both browsers observe it. Insights in M8 were the same move: `view postCount`, `view likesReceived`, `day(.at)` buckets, `trending … last 10 by .likeCount, .at`. Those would be three Convex query functions and a cron, or three SQL views and a materialized rollup. Here they are ten lines next to `posts`.

Auth and replay also shrank. `use identity password` plus unique handle is M1. The scale replay is the same `signup` / `mutate` path as the app, with `--replay` holding schedules and suppressing new effects so 100k notification side effects do not define the run. Convex has no equivalent one-flag "this is a fixture replay, do not fire the scheduler." Supabase has SQL COPY, which is faster and also not the product's write path. The brief required the product's write path. Snapback 4 made that requirement cheap enough that 167157 actions finished in 263 seconds on this machine and the store matched `invariant-manifest-combined.json` on every count I checked.

The Expo arm is a product decision that paid off: `createApp({ device: webDevice() | nativeDevice, assets: { keep: "viewed" } })` is the replica. M6/M8 offline choreography is that replica plus queued mutations, not a hand-rolled IndexedDB queue. I still had to wrap SecureStore and a small intent store. I did not have to invent sync.

## Where the backend added friction

Quarry is a language. Optional `image ?` fields need bounds. `!` needs `else CODE`. Receipts need the member row to exist in the same insert. `expiresAt` must be immutable if another table reads through it. Reactions need a legal sync path. Message search cannot pair `matching` with `byConversationOrdinal`. Each of those is a compile error with a useful code, and each is still a stop that a TypeScript-first Convex mutation would not have imposed in that form. I did not treat them as correction loops — they failed before I claimed done — but they are the tax on "the schema is the backend."

The worker story is the clearest published-surface gap I hit. Supervised workers run from a private copy under `.snapback4/worker-*/scope/scope/…`. A log path derived from `import.meta.url` writes beside that copy, not in the lane's `data/push-log.jsonl`. The M6 suite then cannot see the push payload. The workaround is `resolve(process.cwd(), "data/push-log.jsonl")` or an env var. I found this by inspecting the process command line after the suite missed the file. That is a documentation defect of this pin: the guide should say the worker's files are not the project's files. I labeled the loop `snapback-defect` / `knowledge-gap`. A second, environmental, failure: symlinking `node_modules` into `scale-run/` made the worker copy throw `Too many levels of symbolic links`. `--replay` saved the scale instance because it does not need the worker.

Live queries and the frozen UI kit interacted badly with Playwright. Snapback is not at fault for `FlatList` unmounting rows, or for `sm-chats-item` living on `/chats` while choreography starts on `/`. Those loops are mine. They ate more wall clock than Quarry did. A backend that ships a replica encourages a client that renders from local projections; a harness that uses `hasText` on mounted DOM punishes virtualization. Convex-online-only apps sometimes dodge this by always rendering the current query page. The replica made me greedy about local lists, and the harness billed me for it.

`connected[p]` is correct and sharp-edged. If Bob's Expo tab is still open, Alice's message does not emit `notify`. That is the right product behavior and it failed the first M6 push assertion until I used a third persona with no browser. The guide mentions connectedness; the suite implication (close the target's clients, including the one you are looking at) should be in the social card in bold.

SQL inspection is intentionally narrow. `npx snapback4 sql` will not select from `sqlite_master` (`E_SQL_INTERNAL`). Application tables work and were enough to verify the scale store. I wanted `\dt`. I used `data profiles --limit 2` and then `SELECT COUNT(*) FROM messages`. Fine, once.

Sync windows are easy to misread. `sync to members[.id] last 500 by byConversationOrdinal` is the replica's working set, not the server's history. The busy group `g0001` has 10,000 messages in the store and a replica that will not keep all of them. History queries with cursors still page. If I had verified scale only through a connected replica without SQL, I might have under-counted. The pin gives you `sql` for a reason.

## How the shape of the work changed

On Convex, Clique is a TypeScript program that happens to have a database. You think in functions: `sendMessage`, `listHistory`, `markRead`, `expireJob`. Auth is a product you wire. Files are a product you wire. Realtime is `useQuery`. Offline is not in the box. The work is familiar. The risk is that receipts, expiry, and view-once exist only as comments in those functions.

On Supabase, Clique is a relational database with a TypeScript costume. You think in tables, policies, storage buckets, and Realtime publications. The work is SQL you already know, plus a long RLS session, plus a local-store problem you pretend not to have. Scale replay is a SQL load or a REST loop. Digest is pg_cron. You will get the counts right and the client wrong.

On earlier Snapback generations I remember a smaller language, a closer coupling to source checkouts, and more "the template is the docs." This pin is a published npm package with an optional host binary, `npx snapback4 guide` cards, `why CODE`, `new --template social`, `--replay`, `sql`, and an Expo device arm. The authoring surface is Quarry-first rather than checkout-first. That is a different job: you learn the language from the cards, you take compile errors as the spec, and you are not allowed to peek at the compiler. When the cards and the compiler agree, the work is fast. When a worker isolation rule lives only in process layout, you pay a correction loop the older source-checkout runs would have skipped by reading the code.

The work that remained, after Quarry did its job, was application-shell work: Expo Router depth, kit testIDs, Playwright's need for mounted nodes, upload-then-send races, DOM video versus RN video, identity strings of the form `dm:bob`. That is the same work I would have on Convex or Supabase once the backend existed. Snapback 4 moved the backend through M8 without a second datastore, a second auth vendor, or a hand-rolled replica. It charged for a language and for a few unpublished operational facts (worker copies, connectedness versus push tests, SQL's refused catalogs).

If I were choosing a backend for a production Clique tomorrow, I would still want this receipts/expiry/once/replica combination. I would also want the worker cwd contract and the search-index pairing rules written on the first social card, not discovered at M5/M6. The pin is already a product. The remaining friction is discoverability, which the protocol correctly counts as part of the product under test.
