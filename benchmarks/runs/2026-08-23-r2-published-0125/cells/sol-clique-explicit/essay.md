# Building Clique on Snapback explicit: a qualitative comparison

Snapback's explicit authoring profile feels closest to writing a small, strongly reviewed application server, but with the deployment and subscription machinery compressed into generated artifacts. The central experience is not “declare some tables and call a client SDK.” It is “state the application contract precisely enough that codegen can challenge it, then consume only the references generated from that contract.” That distinction shaped nearly every good and frustrating moment in Clique.

Compared with Convex, Snapback asks for more ceremony and rewards it with a clearer security story. In Convex I would also write server functions, derive the authenticated identity inside them, and get live query invalidation almost for free. The productive loop would be faster at first: schema declarations are compact, handlers have fewer posture fields, and React hooks are familiar. Snapback's explicit reads, writes, refusals, result validators, and generated surface bindings take longer to author. In exchange, the finished function advertises much more of its authority and failure envelope before I read its body. For social features—especially membership removal and receipt obligations—that is valuable. Convex's ergonomics win for exploration; Snapback's reviewability wins when the question is “what can this operation touch, and how can it refuse?”

Supabase starts from the opposite direction. Its center of gravity is Postgres: normalized relations, unique indexes, row-level security, SQL queries, Storage, and Realtime. Clique's follow graph, unique DM pair, membership rows, and receipt obligations map naturally onto Postgres. I would expect Supabase to be excellent for reporting and ad hoc server-side joins, and its operational model is easier to explain to a team already fluent in SQL. But the application contract would be distributed across migrations, policies, database functions, edge functions, generated database types, and client query code. Realtime behavior can be made solid, yet the invalidation model is less application-shaped than a live function that returns exactly the feed projection. Snapback kept the projection and its authority in one authored module, at the cost of writing bounded joins manually and receiving N+1 advisories where SQL would simply optimize a join plan.

Firebase would get the first demo running fastest and would make presence feel familiar. Authentication, offline-capable clients, snapshot listeners, and a document model are a proven match for chat. The hard part would arrive when the demo becomes the product. Following feeds, repost attribution, uniqueness of a DM pair, aggregate receipts, and historical access after membership removal all require careful denormalization, transactions, security rules, and often Cloud Functions. Firebase rules are powerful but can become a second program whose relationship to client-visible projections is indirect. Snapback made these invariants server functions over ordinary rows. It was slower to begin and easier to reason about at the point where Firebase designs often acquire counters, fan-out documents, and compensating repair jobs.

Hand-rolled Postgres plus Express offers the most freedom and the least help. I could express Clique's relational invariants elegantly, tune feed queries, expose REST or RPC endpoints, and choose a mature session library. I would also own migration tooling, validation, authorization conventions, websocket fan-out, subscription invalidation, offline semantics, idempotency, typed client generation, process supervision, and acceptance integration. A good team can build that platform, but it is an organizational commitment disguised as an app backend. Snapback's explicit profile resembles the disciplined version of that stack: handler contracts and database operations remain visible, while runtime loading, client references, live updates, and session plumbing are supplied. The trade is accepting a younger framework's sharper edges and narrower documentation instead of absorbing years of infrastructure work.

The strongest part of Snapback here was the generated identity chain. The schema, functions, application descriptor, client binding, and exact references agree on one build. I did not pass arbitrary function names from Expo or trust client-supplied user IDs. That reduced a whole class of integration and authorization ambiguity. Replay idempotency also benefited from the separation between a fixture's domain mutation identity and the transport's per-client mutation identity: once modeled correctly, repeat installation was boring, which is exactly what seed replay should be.

The weakest part was the development carrier. The fixed-port benchmark constraint exposed assumptions in supervised Expo web startup: Metro uses internal public/process arms and a bootstrap exchange, while the CLI does not offer caller-selected ports for them. The provider types permit an explicit binding, but the default supervised environment is exchange-first and does not consume that override. Solving the mismatch required shipped type and implementation inspection and a custom explicit environment, not a served-Guide recipe. This is the kind of seam mature platforms have usually sanded down. It did not undermine the backend model, but it made “open the app” harder than “implement live authorization-safe messaging,” which is the wrong difficulty gradient.

My overall impression is that Snapback explicit is unusually honest. It refuses to pretend that validation, authority, mutation outcomes, offline custody, and realtime presence are one simple database call. The resulting code is longer, but much of that length is executable review material. I would choose it over Firebase for a collaboration product with complex invariants, and over a hand-rolled Express stack unless the organization already owns a realtime platform. Against Convex, the decision is temperament and maturity: Convex is the smoother product surface, while Snapback explicit provides more declared evidence. Against Supabase, it is application-shaped live functions versus the power and ecosystem of SQL. Clique made the case for the explicit model; it also made clear that the surrounding Expo development workflow and pattern documentation need to catch up with the quality of the core contract.
