# Familiar, but not invisible: building Clique on Snapback

The Familiar TypeScript profile earns its name. For the ordinary application layer, working in it felt much closer to Convex than to learning a new backend from first principles. A table is a table declaration, an index is attached to it, a query or mutation is a top-level TypeScript export, and the React side consumes generated references with live hooks. That shape matters under time pressure. It kept attention on Clique's actual invariants—unique handles, authenticated authorship, one DM per pair, idempotent fixture identities—instead of forcing a translation into a builder DSL or manually synchronized client protocol.

The Convex comparison is strongest in the feedback loop. Change a schema or function, regenerate, and the client receives a typed reference whose arguments and result follow the backend declaration. Queries become subscriptions in React without standing up a separate socket protocol. Server handlers have an authenticated context and a database object with indexed reads and transactional writes. In both systems, this makes “write the invariant once, render the subscribed result everywhere” the natural design. Clique's cross-client profile edits, reactions, posts, and messages all benefited from that model.

Snapback is less permissive than Convex inside the handler, and that was both helpful and surprising. Familiar TypeScript looks like general TypeScript, but codegen lowers an admitted subset into a controlled runtime. A relational read ceiling, static table access, closed validators, declared read/write sets, and restrictions around authority tables are enforced before deployment. Convex functions generally feel like JavaScript running in a managed transaction; Snapback handlers feel like TypeScript-shaped source for a compiler with a security model. The practical consequence is that diagnostics are part of the programming language. When they are good—as with a bounded `take` violation—they are better than discovering a cost or correctness problem in production. When the documented recovery is incomplete—as with bootstrapping a declared membership from a new resource—the apparent familiarity can become misleading.

Authentication felt more explicit than Convex's typical external-provider setup. Snapback's sessions mode, durable custody requirement, fixed external origin, generated app binding, recovery-code policy, and auth-context-bound mutation identity made the security boundary visible during local development. That visibility caught a real replay-tool mistake: a transport mutation identity cannot simply be reused under another session, even if the domain write is idempotent. The right design became two-layered—fresh transport identities, durable unique fixture source identities—which is a sound production distinction. The built-in password path also avoided inventing credential storage, a place where a small benchmark app could otherwise become dangerously fake.

Compared with Supabase, Snapback made live application data easier and relational exploration harder. Supabase exposes familiar SQL, row-level security, storage, and a broadly hosted operational story; its database is inspectable with the entire PostgreSQL ecosystem. But a client author must deliberately align schema, policies, generated types, realtime publication, and application queries. Snapback's generated graph makes those pieces one artifact and gives the React client a narrower paved road. Conversely, Snapback's table visibility and authority declarations are not interchangeable with RLS, and the local ephemeral system explicitly does not claim a hosted multi-instance topology. Supabase would make a production membership policy and ad hoc analytics more conventional today, while requiring more care to achieve the same cohesive client subscription contract.

Compared with Firebase, Snapback encourages stronger server-owned domain operations. Firebase can produce an extraordinarily fast first live UI, but document paths and security rules often become a second program that must agree with client write shapes. Clique's follow toggles, repost projection, DM uniqueness, and quoted-message validation belong naturally in authenticated mutations rather than client-authored document writes. Snapback's declared function surface and generated references made that boundary hard to bypass accidentally. Firebase remains more mature as a globally hosted product and has a simpler mental model for presence, but its denormalization and rule-testing burden would become more prominent as Clique's graph grows.

Compared with a traditional TypeScript service over PostgreSQL, Snapback removed an enormous amount of glue: route handlers, request schemas, client DTOs, cache invalidation, websocket fan-out, auth middleware, and optimistic subscription bookkeeping. The trade is platform grammar. In a conventional service I could express a resource-and-membership bootstrap transaction directly in SQL, place a constraint around it, and expose exactly one endpoint. In Snapback, declaring the roster as authority changes which writes are legal and expects a declaration-owned transition workflow. That is a principled design—authority data should not be writable through generic calls—but the complete Familiar path needs to be as easy to find as the prohibition.

Ephemeral typing was the most distinctive part of the experience. Snapback treats presence as typed, scoped, TTL-bounded latest state with explicit publication and subscription policies. The Expo activity-presence hook owns idle withdrawal, renewal, cleanup, and lifecycle behavior. That is substantially safer than hand-rolling a “typing” row plus timers, and more integrated than bolting a second realtime provider onto a Convex-style data layer. It also revealed the platform's current maturity line: the feature is local-target only, and the strongest authorization mode depends on canonical declared membership. Clique uses the ephemeral transport and lifecycle correctly, but its fallback public room policy is a genuine privacy gap, not something a passing browser receipt should conceal.

The served Guide was valuable because it was bound to the running binary. That avoided a common framework problem where web documentation describes a newer release than the installed CLI. Package types filled in exact signatures well. Still, the experience was uneven: the Familiar profile says generated output lives in `snapback/generated` and that `_generated` is retired, while the benchmark request used the older name; scaffold relocation left an opaque absolute-path reservation; and advanced recipes sometimes showed an explicit-profile or demo seam without the complete Familiar application workflow. The best documentation improvement would be a set of vertical packets—schema, generated operations, app mutation, React hook, acceptance probe—for the authority-heavy cases.

My overall impression is positive but qualified. Familiar TypeScript dramatically reduces the novelty tax for a Convex-aware engineer and makes ordinary live application work fast, typed, and coherent. Snapback's stricter compiler and explicit authority model can prevent classes of mistakes that a more permissive backend leaves to review. Yet those benefits depend on paved recovery paths being complete. Where the path is paved—sessions, ordinary live queries, mutations, generated hooks, activity presence—the system feels unusually cohesive. Where it is not—authority-table lifecycle composition—the abstraction boundary becomes the work. That is not a reason to loosen the model; it is a reason to finish the Familiar story all the way through the security-sensitive workflows it is designed to protect.
