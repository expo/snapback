# Clique build diary

## M1 — identity, sessions, and profiles

I built the sessions-mode Snapback foundation, email/password signup and login, durable browser session custody, logout, recovery-code presentation, unique handles, editable public profiles, fixture avatars, and a deliberately small authenticated home surface. The starter log is replayed in order through the same generated mutation references used by the app. The acceptance runner then checks the replayed documents and drives negative cases through the backend. The frozen two-client harness confirmed that Alice's profile edits reached Bob live, survived an Alice reload, and that logout remained logged out across another reload. An Expo iOS export also produced a Hermes bytecode bundle.

The easy part was wiring the generated app identity into the Familiar provider and using the frozen UI components as the visible interaction boundary. Familiar queries and mutations read like ordinary TypeScript modules, and the generated API references made both hooks and the replay tool straightforward. That profile saved most of the conceptual translation normally spent learning a backend-specific declaration language: schema fields, indexes, arguments, return validators, queries, and mutations remained close to the Convex-shaped mental model the profile promises.

The work that fought me was mostly at the edges. Moving the generated starter out of its temporary scaffold directory left runtime reservation files containing the old absolute path, so the first backend restart failed until I isolated those stale files. TypeScript 6 surfaced a stale compiler option and a query-state union needed explicit narrowing. React Native web also lacks the `Image.resolveAssetSource` shape I first assumed, which caused the first Metro render to fail until fixture asset resolution was made platform-safe. Finally, the in-app browser controller had no available browser session, so the authoritative Playwright choreography became the end-to-end diagnostic as well as the milestone proof.

The Familiar profile saved boilerplate around operation definitions, generated references, validators, auth access, and React subscriptions. What remained Snapback-specific was substantial but bounded: the codegen policy, external-origin admission, runtime binding, session-storage partitioning, auth recovery behavior, table write posture, and the CLI/runtime split. One notable documentation mismatch is that the published 0.1.25 Familiar guide says `snapback/generated` is authoritative and `_generated` is retired, while the benchmark request still names `_generated/`. I followed the running binary and published codegen rather than manufacturing a second generated tree.

The most useful missing diagnostic would have been an error that explicitly connected a relocated scaffold to the stale absolute runtime reservation and offered the safe cleanup target. The guide also could state more prominently that public-read tables with authenticated server mutations trigger migration-posture warnings even when the mutation itself derives the principal. A compact web-safe asset-resolution example in the Expo packet would have prevented the only browser runtime crash.

## M2 — posts, reactions, reposts, threads, and the follow graph

I added the social graph and feed model as four live document sets: follow edges, posts (including direct replies), likes, and reposts. Every write derives the acting user from the authenticated context. The UI combines those subscriptions with profiles to render Global and Following projections, implicit self-membership, attributed reposts, live counts, threads, and deterministic 20-item pagination. The M2 starter replay settled all 52 new actions through those mutations. The acceptance entrypoint covered all 22 suite-owned assertions; the frozen browser harness then passed text-post delivery, follow/unfollow projection, author identity, like/unlike, repost attribution, followed-reposter projection, and live reply threads. Its two media-live checks remained the harness's declared optional skips because the frozen contract has no drivable feed media picker selector.

The schema and basic mutations felt easy. Familiar indexes and the generated `v.doc`/`v.id` validators made identity-safe edges and set-state reactions concise. The client-side projection also stayed pleasantly ordinary: the live hooks supply canonical rows, while small `Set` and `Map` transforms express Global versus Following without a bespoke backend query language. The replay format was regular enough that one parser could preserve line order and fixture timestamps.

What fought me was app-shell choreography. The harness deliberately carries each browser forward between assertions. A profile follow therefore needed to settle and return to a surface where feed tabs remained reachable. The own-profile component's first visible line was the frozen Edit action, while the observation expected the display name; I added an outer contracted profile surface whose first line is the name and passed a distinct test ID into the unchanged frozen component. Finally, Expo Router keeps the outgoing stack screen mounted during a push. That briefly exposed both the Global composer and thread composer under the same frozen selector, so the old composer now unmounts before the route transition. These were three correction loops around navigation state, not data liveness; the final run was green.

Familiar saved the most time in the mutation layer: authenticated context, indexed reads, typed IDs, return validation, generated API references, and live hooks all remained uniform as the model expanded from one table to five. Snapback-specific constraints still shaped the result. Inline Familiar handlers cap relational `take` at 1024, generic table writes produce explicit-authority migration warnings, mutation IDs are bound to auth context, and development briefly closes app-data admission while a new schema is loading. Unique durable `sourceId` values handle fixture idempotency while each transport attempt now gets a fresh mutation ID.

The codegen error for the 1024 ceiling was excellent and directly actionable. The missing diagnostic was for `SNAPBACK_AUTH_STALE_RESULT`: it should say that a replay tool must not reuse a client mutation identity under a new session even when the domain operation is idempotent. The client mutation return shape also deserves one short Familiar example; querying the settled document by its unique source ID was reliable, but the mistaken return-envelope assumption cost a loop. A guide note about Expo Router retaining an outgoing web screen during stack transitions would also help authors using globally unique test selectors.

## M3 — conversations, messages, groups, quotes, and typing

I added idempotent one-channel-per-pair DMs, distinct same-roster groups, owner/member rosters, owner-only member removal, membership-checked message reads and writes, chronological live messages, sender identity, quoted replies, and jump-to-original behavior. The authenticated home now exposes conversation rows without displacing the feed. Conversation typing uses Snapback's generated ephemeral reference and the Expo activity-presence hook, so a keystroke touches the lease and idle activity withdraws it. The starter replay composes M1 and M2 before installing the conversation stream, and the suite repeats that entire installed replay to prove source-level idempotency.

The easy part was again the live data path. Once conversation IDs and authenticated membership checks existed, `messages.forConversation` and `messages.send` were small, legible Familiar operations. The hook-driven UI saw new messages without a polling layer. Quoting was also clean: the durable message stores a typed reference to another message in the same conversation, while the frozen bubble renders the excerpt and the route owns scroll position.

The part that fought me exposed a meaningful boundary in the current profile. I first modeled the roster as Snapback's canonical membership declaration and bound the typing collection with `allow.members`, following the served recipe. Codegen correctly refused every generic `ctx.db.insert/delete` targeting that authority table. Familiar handlers cannot casually bootstrap or transition a declared authority table; the declaration-owned workflow must own those writes. Building conversation creation around that generated workflow would have expanded this milestone considerably, so I corrected to an ordinary durable roster with explicit server-side checks for all conversation and message operations. Typing remains genuinely ephemeral and session-connected, but its collection uses `allow.all` and the UI filters entries against the durable roster. That is green for the frozen M3 observations, but it is not a production privacy boundary if an outsider learns a conversation ID. It is the clearest remaining security gap.

Familiar saved almost everything on the ordinary application-data side: flat TypeScript modules, generated branded IDs, validators, auth context, familiar database calls, and hooks all scaled naturally. The ephemeral feature was more Snapback-specific. Its generated reference, connection-owned entry key, TTL, dispatch policy, activity touch/withdraw lifecycle, and local-only hosting claim are concepts an author must learn. The activity-presence hook itself was excellent; it removed the timer and lifecycle footguns the guide warned about, and the isolated browser contexts observed clean expiry.

The missing documentation is a Familiar-specific, end-to-end example of “create a resource and bootstrap its declared membership, then add and remove members” using only the public generated workflow. The recipe shows the declaration and the runtime behavior, but not the complete flat-TypeScript application write path needed by a new app. Codegen's refusal was precise; the recovery path was not. A second missing diagnostic is a warning when `allow.all` ephemeral scope values look like private resource IDs while an ordinary roster table exists—it cannot prove intent, but it could point directly to the membership recipe.
