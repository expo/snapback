
## M1 — Accounts and profiles

Built password accounts, profile onboarding and editing, durable sign-in, server logout, protected avatar uploads, the Expo Router shell, and web/native local-client selection. The suite and two-client choreography passed; the iOS Hermes export succeeded. Built-in identity and typed profile writes were easy. The largest orientation cost was the broad published README, which made the auth/asset/replica responsibilities explicit. A retained navigation stack duplicated active forms; replacing it with Slot fixed my client mistake. Copying the frozen harness preserved read-only permissions, and its missing snapshot JSON-schema helper needed a disclosed AJV dependency adapter in a lane-contained layout. No choreography check was rewritten. Prior React and Expo familiarity saved the basic UI wiring; no earlier Snapback implementation was consulted. Compared with Supabase, this needed less session and storage authorization glue; compared with Convex, the local replica is more explicit at startup. Neither comparison is a measured result.

## M2 — Posts and the follow graph

Built text, multi-image and video posts, reply threads, idempotent likes/reposts, profile counts, Following/Global feeds and twenty-row pagination. All suite mappings and the complete choreography passed, with a Hermes export. The generated feed recipe removed considerable fan-out design work, though it adds many explicit tables and acquisition costs. The first browser run mixed suite writes with choreography; those independent-looking tasks actually shared a changing corpus. I stopped that invalid overlap and ran them serially. The frozen harness assumes feed tabs are available from profiles and threads, so I made those navigation controls persistent. Media tests needed to await picker/form settlement. Quarry itself compiled this increment on the first check. Public aggregates and full post sync simplify offline reads but carry a cold-sync cost to measure at scale. Convex would make this server-side query composition familiar; Supabase would require SQL projections and a separate offline design. Here the read model is authored explicitly but reused on device.

## M3 — Messaging core

Built DMs, groups, member administration, typing, chronological history, quoted replies and monotonic per-account receipt watermarks evaluated against each message's original recipients. The full choreography passed, including removal with retained pre-removal history and a later delivery witness. The suite and Hermes export passed. Schema rules and `retain delivered-history` made the difficult authorization/retention split straightforward. My client code caused two correction loops: clearing a draft after awaiting a send could erase the next draft, and a lazy web-device import failed if connectivity dropped during reload. A focused two-browser proof identified the latter as a return to sign-in, not a receipt-aggregation failure; static platform imports fixed it. The package's server/device agreement saved writing a second history implementation. Compared with Supabase realtime, membership-scoped replica acquisition and revocation are substantial built-in work. Compared with Convex, offline lifecycle setup demands more attention, but the backend operation shape remains declarative. No unsupported platform capability was found here.

## M4 — Media messages, reactions, edit/delete

Built image/video messages, a native/web media viewer, arbitrary emoji reactions with replacement and clear intents, editing with an edited label, and deletion with a shared tombstone and cleared asset homes. Window values come from the fixture config and are checked against Quarry `now`. The suite, all choreography checks and Hermes export passed. Asset placement and revocation were easy because storage reads follow row authority. The friction was client composition: a dev warning toast covered the bottom attachment button. I first removed import cycles, then the screenshot exposed the actual remaining warning—empty string children from error conditionals under React Native View. Boolean conditions fixed it. This was my mistake, not a backend defect. Compared with independent object storage plus database rows, home-bound assets avoid a separate URL revocation design. Native video playback still needs Expo UI work regardless of backend.

## M5
Built chat appearance, scoped and held-message search, expiring messages, and view-once media. Both suite and choreography passed. Server time and asset authority were easy to reuse; cold offline search needed an explicit replica proof. The UI kit uppercases group headings, which required correcting the test, not the app. Prior knowledge of retained replicas helped separate held history from current membership. The published search guide explains bounded merge costs; global held search avoids unbounded server scans. Compared with Supabase, the server expiry and asset revocation relationship needed less custom infrastructure; compared with Convex, explicit query bounds remained more visible. The supplemental offline proof uses a Node replica, not an iOS simulator.

## M6
Built the durable push seam, documented custom-client operations, complete replay adapter, exact checkpoint verification and builder performance probes. Suite and choreography passed; the iOS Hermes bundle exported. A Node replica proved offline cold history/media/search, pending rows across restart, ordered exact-once delivery and read receipts; simulator assertions remain instrument-skipped, not proved. Effects-only presence was easy once variable-cost profile reads moved outside the guard. Adapter retries fought me: reuploading assets changed arguments under a stable write ID, correctly rejected by E_ID_REUSED. I also corrected my pagination assumption to the documented Read.next. Familiarity with idempotency and cursor APIs helped, but trusting an assumed property name cost a loop. Compared with Convex and Supabase, one Quarry operation covers both prediction and authoritative commit; the cost is attending closely to eligibility diagnostics. Replay verification is builder-authored and does not claim the hidden grader's sampling or scores.

## M8
Built six server-computed lifetime totals, seven UTC activity buckets including zero days, immediately maintained Trending scores with server-time expiry, and the config-driven scheduled digest. Verified closed-client execution, exact counts, quiet users and periods, private-chat and tombstone exclusion, and restart idempotency. Account-shared watermarks and the replica outbox supplied multi-device convergence. Choreography first exposed its home-screen chat-row assumption, then one intermittent missing offline bubble. An independent reproduction passed; I added durable view metadata for queued-without-row writes without taking ownership of submission. The final suite, choreography and Hermes export passed. Prior familiarity helped separate read models from authorization and provider delivery. Schedule syntax required converting seconds from the fixture config into supported minute units. The immediate Trending index required explicit source-write maintenance; the published scheduled recipe permits score lag and therefore did not meet this brief's load-time freshness. Compared with Supabase I wrote less plumbing for expiry and outbox recovery; compared with Convex I spent more attention on static bounds and prediction eligibility. A second fresh replay measures the M8 read models through the growth curve. No M7 work was attempted.
