# Building Clique with a schema that is also the backend

This cold build made Snapback 4 feel most valuable where a conventional application would accumulate several implementations of the same policy. Message membership, local availability, expiry, and media access were related parts of one model. Quarry described the rows, the rules, the sync audience, and the operations. The Expo client consumed generated operations and rendered the resulting state. That arrangement reduced the number of places where I had to remember what a message meant.

The difference was especially tangible after the basic chat existed. Adding disappearing messages did not require inventing a client timer as the authority. Adding a view-once photo did not require treating an ordinary permanent URL as secret. Adding offline text messages did not require writing my own authoritative retry loop. Those facilities still required careful application work and separate proofs, but they were available as backend concepts rather than conventions scattered across components.

This is an experience report about the exact published packages used in this lane. I did not inspect another implementation or an earlier benchmark. Comparisons with Convex, Supabase, and conventional application servers below are architectural judgments based on general familiarity, not measured alternate builds. I cannot turn this single experience into a credible claim about comparative development speed or production reliability.

The first productive constraint was that the backend could not quietly become a collection of arbitrary JavaScript handlers. I had to express authorization, bounds, and business changes in Quarry. That made membership and attribution visible during design. A direct conversation was a unique pair. A reaction was one actor's set-state intent. A message carried a snapshot of its recipients, while receipt calculation stopped waiting for people who had left. The distinctions were straightforward to audit because they sat next to the schema and indexes.

A typical Convex implementation would let me express most of those operations in TypeScript transactions and build reactive views around them. I would expect that to feel familiar sooner, particularly for branching application logic. Here, the unfamiliar language initially demanded more attention, but it also made local prediction an explicit property of the same operation. The compiler's eligibility notes were unusually useful. When I put a profile lookup inside a presence-controlled branch, it explained why the send operation would no longer predict. Moving the lookup outside the branch restored the intended relationship: presence selected the notification effect, while message creation remained independent of it.

With Supabase, I would normally think in terms of PostgreSQL constraints, row-level security, transactional functions, storage policy, and a separate offline-client design. Those are powerful and familiar tools. The cost for this particular brief would be connecting them into one coherent mobile behavior. Snapback's sync declarations and replica runtime supplied much of that connection. I did not have to invent a second data model just to let the mobile client read its own held history. The distinction between retained history and current authorization was nevertheless real work; a retained message is not permission to keep downloading revoked media.

The language also made cost visible earlier than a permissive application server would. Bounded pages, explicit indexes, merge widths, and completeness were not optional optimization notes. The global server search could name too many lanes to fit the normal read ceiling, and the diagnostic said so. The app's ordinary global search therefore uses the held-message index. The server API remains bounded and reports incompleteness rather than disguising a partial scan as exhaustive. This is useful discipline, although a product engineer must still translate it into a sensible interface.

The feed recipe was another example of helpful specificity. It offered a published hybrid delivery model, with a different path for highly followed authors. I could use the installed package's generated recipe and connect my own post cards to it without discovering a private implementation. That saved design work. It did not remove the need to test the intended envelope, check the exact fixture graph, or distinguish a fast query from a query over an accidentally smaller corpus.

The replay work exposed ordinary application mistakes rather than a dramatic platform failure. On a repeated media action, my adapter uploaded a new asset but reused the original mutation ID. The backend rejected the changed arguments. That was the right refusal. The repair was to recover the authoritative asset reference and preserve the original intent. I also assumed the wrong pagination property before returning to the published Read contract. Those errors are reminders that concise APIs still need careful reading; familiarity with other SDKs can be a source of incorrect shortcuts.

Offline behavior changed the shape of the UI work. The SDK owned the outbox, prediction, retries, and terminal outcomes. My responsibility was to show a truthful pending state even when a write could be queued without a predicted row. One repeat choreography run missed an offline bubble while an independent dual-client reproduction passed. I could not honestly call that a proven platform defect. I added durable view metadata for that case, with an important boundary: it observes SDK write IDs and never submits a message itself. That leaves one authority for retry and ordering.

The strongest supplemental offline evidence came from reopening a real process replica with networking deliberately unavailable, then reconnecting it. History, viewed media, and held search remained available. Pending messages survived restart, delivered once in order, and reached read. Likes and reactions retained set-state behavior. Those are meaningful checks of the replica contract, but they are not iOS simulator evidence. Producing a Hermes bundle establishes that the native application can be bundled with the pinned native arm; it does not establish every behavior of an installed iPhone app.

M8 put pressure on a different part of the model. Lifetime totals and calendar buckets were a good fit for maintained aggregates. They kept the client from downloading the corpus to count it. Trending was less automatic. The published scheduled ranking recipe explicitly permits lag, while this brief asks for fresh results at load. I used a ranking row maintained in the source write transaction, expiring with the post's rolling window, and made the read depend on server time. This required more application design than the aggregate totals, but the resulting query did not grow into a corpus-wide sort.

The digest was where backend ownership paid off again. A scheduled Quarry job computed the period's activity and emitted a durable effect. The worker only recorded the already-authorized payload. Closing every client did not stop the schedule. Restarting the backend mid-period did not require a client to repair missed work. The isolated proof also checked quiet periods, private chats, and tombstones. In a PostgreSQL-based stack I would likely assemble a scheduler, transactional aggregation, and an outbox worker explicitly. In a general application server I would own even more of the restart bookkeeping. Snapback supplied that bookkeeping, while I still owned the definition of “activity.”

The hardest boundary to keep honest was measurement. The frozen choreography needed a lane-contained import-layout repair because a referenced helper was absent from the supplied snapshot. I kept the checks unchanged and disclosed the adapter. The environment's advertised Node selection also differed from the initial shell resolution, so later commands used the supplied absolute toolchain path. These details do not describe the product's backend quality, but hiding them would make the run harder to interpret. The same applies to unavailable native token accounting and unrun simulator checks: neither can be reconstructed from a pleasant-looking application.

I have no independently established earlier-generation Snapback result from this cold session, so an empirical generational comparison would be speculation. What this release demonstrably offered was an integrated Quarry program, generated client types, local and native replica arms, asset authority, effect delivery, schedules, and concrete diagnostics. If earlier approaches require an engineer to coordinate more separate layers, these facilities explain where a reduction in friction could come from. They do not prove that reduction across generations, nor do they justify importing an old limitation into this release.

The experience left me with a clear tradeoff. Snapback reduced the amount of application-owned infrastructure around offline state, authorization-aware sync, expiry, and durable scheduled work. It added a language and a set of bounded-execution rules that had to be learned precisely. Convex would offer a more familiar transaction-programming surface; Supabase would offer the breadth and portability of PostgreSQL-centered tools. For this messenger, the integrated replica contract was the most distinctive benefit. The remaining engineering burden was making every visible state, every retry, and every measurement agree with that contract.
