# Clique on Snapback 4: an interrupted accounts milestone

This is an account of an incomplete cold build, not an evaluation of the full social-messenger workload. I built and tested accounts and profiles, produced an iOS Hermes bundle, and then stopped at the benchmark's first evidence gate. The frozen choreography could not load a schema-validation module absent from the supplied instrument. Its browser checks never ran. The milestone therefore has no green receipt, and the dependency graph blocks the remaining continuous milestones. That boundary matters to every comparison below: I experienced authentication, profile modeling, avatar storage, client setup, and part of the verification workflow. I did not experience messaging, large feeds, offline message replay, scheduled digests, or schema evolution in this run.

The most encouraging part of the backend was the distance between a profile's product requirements and its declaration. A Quarry table describes bounded fields, a unique handle, a principal identity, an avatar, and the read and write rules. Public profile synchronization is another line in that declaration. The save operation is an upsert under the caller's principal; the avatar operation changes one column. The first authored schema compiled without a repair. That is useful compression of several concerns that would otherwise live in separate places. It also gives a reviewer a compact place to inspect whether the client is actually allowed to update the profile it displays.

My conceptual comparison with Convex is strongest here. In the Convex model I know, I would expect TypeScript functions and validators around the profile operations, with explicit authorization inside those functions. Snapback instead puts substantial authority at the table and index layer, while the mutations describe the allowed application operations. That changes how I would review a patch: I would inspect both the mutation and the declarative rule, then inspect the compiler's account of which reads can execute locally. I have not run a contemporary Convex comparison in this session, so this describes familiar architectural differences rather than a measured advantage over a particular release.

Compared with the Supabase architecture I know, Quarry combines concerns that I would normally distribute across SQL definitions, row-level security, storage policy, and the application's client integration. A unique handle feels conventional in either world. Binding an uploaded image directly to a typed profile column is less conventional and was convenient in this implementation. The client uploads bytes and gives the resulting reference to a mutation. The storage lifetime and access policy then follow the row. I did not have to create a separate object naming scheme, expose a public bucket, or add a second profile-image authorization implementation. The test established that a fixture image uploaded and rendered on the profile. It did not establish every later revocation scenario in the brief; delete-for-everyone and view-once belong to milestones I did not reach.

Built-in password authentication also fit this narrow product. I enabled password identity and used the package's signup, login, and session APIs. There was no reason to author a password hash, token format, or identity service. The app uses a local client, explicitly persists sessions in the browser, and supplies a secure-store adapter for native. The documentation explains the default memory session store and the opt-in needed for reload continuity. That explicit distinction saved a likely failure: treating a successful login as proof that a page reload would stay authenticated. Profile onboarding is separate from credential signup, so a user whose handle is rejected keeps the authenticated session and can choose another handle.

The client contract asks the application to distinguish loading, denied, and ready reads, as well as pending, sent, and failed writes. This is more vocabulary than a minimal request-and-response tutorial, but it corresponds to states the product eventually needs. In a local-first messenger, a returned promise is not necessarily a committed server write. A predicted row is not proof that the server accepted it. The published documentation makes those distinctions prominent. In this run I used them on the profile form and did not replace the replica with a hand-written cache. I cannot yet say whether the same vocabulary remains pleasant across every message action, media viewer, and restart case; that would require completing the later milestones.

The documentation was extensive. The README continues into client and operations documentation, and the CLI supplies keyword cards and diagnostic explanations. Reading the whole published surface was a substantial part of orientation, but it exposed important constraints before implementation. Bounded reads, completeness, synchronization horizons, and the difference between source rows and derived aggregates are central concepts rather than incidental tuning notes. For a full feed and search implementation I would need to design around them early. Familiarity with SQL indexes and authorization helped me understand the model, but ordinary SQL intuition alone would not establish a complete local partition or a safe predicting write. The compiler's generated API explicitly records operation placement and prediction eligibility, which makes those claims inspectable rather than implicit.

Setup had two distinct kinds of friction. The exact native package initially returned registry errors, while the backend package installed immediately. A later installation resolved the required native version, and the final manifest again makes it a required exact dependency. The Hermes export succeeded with that pin. The record preserves both the initial diagnostic and the recovery; it would be incorrect to publish the initial failure as an unresolved native-platform limitation. I cannot determine from those observations alone whether the initial cause was publication timing or registry propagation. No alternative Snapback version or source checkout was used.

The second problem remained unresolved and was outside the product implementation. Copying the choreography directory alone did not preserve its surrounding dependency layout. I supplied its metering siblings from the allowed instrument and arranged them inside the lane, then found an import of a schema validator that the instrument did not contain. A complete invocation still failed at module loading. Supplying my own validator or modifying the frozen harness would create a different evidence mechanism. I retained the exact failure instead. This is frustrating because it prevents a green milestone even when the independent suite passes, but that is preferable to treating an application test as an attested choreography run.

Some of the friction was mine. I initially used an unsupported route filename and had to replace it with Expo Router's index and catch-all files. I also supplied the wrong prop name to the kit's feed tabs; typechecking identified that mistake. The initial duplicate-handle test exercised a profile edit, which was weaker than the manifest's signup wording. I revised it to attempt the duplicate during onboarding and then recover with a different handle. None of these problems demonstrates a Snapback defect. Recording them separately is necessary if this run is later used to reason about developer effort.

I cannot make a responsible empirical comparison with earlier Snapback generations from this session. I deliberately read no old implementations, run diaries, or source repositories. The published current docs describe a backend and a device executing the same Quarry programs, with explicit synchronization and durable write state. That is the current model I worked with. Any statement that it improved over an earlier generation would require independent, comparably gathered evidence. The same caution applies to mature hosted backends: I did not deploy this application, operate backups, measure scale, or compare hosted latency.

The narrow experience suggests a promising integrated model for the first account screen: schema, authorization, generated operations, replica reads, and avatar storage fit together with little backend glue. It also shows that a benchmark's packaging is part of whether that promise can be evaluated. The app artifacts remain useful for diagnosis and continuation, but this run does not demonstrate the requested production-shaped messenger. The unbuilt scope is substantial, and the missing green receipt must stay visible alongside the passing tests.
