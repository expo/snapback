# Clique build diary

## M1 boundary — 1789223151.296

Built password accounts, persistent sessions, server logout revocation, the five textual profile fields, unique handles, public synced profiles, frozen-kit profile/auth screens, the real-action starter seed, acceptance coverage, two-browser choreography, and an iOS Hermes export. M1 is green.

The small Quarry schema felt easy: bounded strings, uniqueness, ownership, and public sync fit in one readable file. Built-in password auth removed the most consequential hand-rolled security work. Generated operation types were immediate.

The difficult part was the interaction of the local client and the app shell. Rejected predicted writes caused an unhandled IndexedDB abort; profile writes now use the documented online client. Default long polling coincided with server stalls; one-second waits restored responsiveness in the passing run. My own route/session lifetime mistakes and accidental extra mutation fields also cost correction loops. A server E_INPUT became “server unreachable” at the client, slowing the distinction between those causes.

Prior familiarity with React, Expo, HTTP, and database uniqueness saved time. I had no prior implementation to borrow. The published surface was pleasantly short, but its `public 'reason'` example did not parse, and neither the client error mapping nor the poll behavior was explained. The copied instrument also needed a missing dependency shim and path relocation; that is environment work, not backend work.

Compared with Convex, the declarative schema plus sync is smaller than writing functions and subscriptions, but the runtime is much less mature in error recovery. Compared with Supabase, having an integrated local replica avoids designing a second storage/sync layer. I cannot make an empirical Snapback 2 comparison from this cold run; conceptually this version puts more backend behavior into a constrained language rather than general-purpose server code.

## M2 boundary — 1789223695 (receipt carries exact first-green)

Built original text posts, follow/unfollow, implicit self-membership, Following and Global pagination, likes, attributed reposts, direct replies and threads, profile post lists, link handling, maintained counts, and M2 fixture replay. The suite covers server state and browser pagination/thread behavior. All non-struck choreography passes; the two media checks are explicitly skipped under the environment overlay. iOS Hermes and TypeScript verification pass.

Quarry's merge query was the strongest moment so far. An explicit viewer lane plus dynamically enumerated follow lanes expressed Following directly, and a shared entry table made repost attribution natural. Maintains removed hand-updated counters. Public sync made the UI live without subscription plumbing.

I initially treated aggregate point reads as value rows; generated types clearly showed they are numbers. That was my mistake. The frozen harness assumed feed tabs remain accessible from profiles; I adapted the shell rather than pretending the failed navigation passed. More seriously, its unstruck code still attempted media and crashed on a filechooser promise. The lane copy now emits honest strike skips; the original failure is preserved. I also invalidated a run by concurrently adding suite posts that displaced choreography fixtures. Subsequent runs are sequential and suite receipts are immutable.

Familiarity with relational indexes and feed modeling helped. Missing indexed search and effects have not yet been exercised. Compared with Convex, maintaining counters and merging feed lanes required fewer imperative functions. Compared with Supabase, the public local replica removes realtime-to-cache glue, though syncing the complete public corpus may become expensive at scale. Compared conceptually with earlier Snapback architectures, this language makes the audience and query costs more visible; I have no cold-run evidence to quantify that comparison.

## M3 boundary — 1789225200.019 (attested in evidence/m3-choreo.jsonl)

Built canonical DMs, distinct groups, membership administration, private messages and full history on join, recipient snapshots, monotonic receipts, typing, quoted replies, chat lists, new-chat/group flows, and M3 replay. The suite and every implemented choreography check pass; the default DM layout's optional avatar check remains an explicit skip. iOS Hermes exports were produced through the correction loop.

The server model remained compact and readable. Atomic send plus a bounded member loop made recipient snapshots straightforward; the DM-pair unique index worked in either ordering. The type checker accepted the intended membership audience and the public guide explained the needed indexes.

The client fought much harder. Per-keystroke durable typing created a backlog, which was my design mistake. Throttling fixed timing. Rejected or overlapping predictions also raised unhandled IndexedDB aborts, and concurrent local calls sometimes returned pending despite a healthy HTTP connection. Operation-level logging and a small two-browser quote probe exposed the difference between correct data and an Expo error overlay blocking clicks. I serialized local mutation calls, moved typing and receipt acknowledgements online, and retained the package queue for user-authored writes. Concurrent tabs also needed separate IndexedDB store slots; the package exports an IndexedDB adapter even though the README only illustrated the native custom-store path. Finally, delivered-history rows became hidden by local membership evaluation after removal. I added a disclosed archive of actually rendered authorized history, backed by IndexedDB on web and SQLite on native.

Familiarity with browser lifecycle, HTTP keepalive, IndexedDB, and Web Locks saved this milestone. A bare declarative retain flag was not enough for the visible retention guarantee in this run. Compared with Convex, the backend is smaller but client integration is much more fragile. Compared with Supabase, I still avoided writing the main sync protocol, but the archive and tab isolation are exactly the kind of glue a local-first platform should ideally own. Relative to my conceptual knowledge of Snapback 2, this release's narrowed language helps state the model; I cannot claim its newer runtime reduced total effort without comparable cold-run evidence.

## M4 boundary — 1789225879.636 (attested in evidence/m4-choreo.jsonl)

Built per-user reactions with replacement/clear, arbitrary emoji input, edited labels, server-authoritative configurable edit/delete windows, and delete-for-everyone text tombstones. The suite, all non-struck choreography, iOS export, and real elapsed shortened-window probes pass. Photo/video checks remain skips; a plain text prerequisite lets the unchanged reaction choreography run.

Time comparisons and author checks were easy to express in Quarry. The configuration is compiled from an actual JSON file into server operations, and the client reads the same resulting values. Waiting through one- and two-minute windows provided concrete evidence without a privileged timestamp seam.

The difficult new defect was a schema that passed `check` but made every sync return `503 E_SCHEMA`: the reactions table lacked an index leading with its conversation audience. The client silently presented a fresh=false empty partition, so the visible symptom looked like routing. Direct inspection of the documented sync endpoint revealed the exact issue. The diagnostic's `why` text said `check` would identify the line, but it had not. Adding the index fixed the suite. A copied fixture's read-only mode also broke production-config restoration; the script now reads/writes bytes rather than copying modes.

Familiarity with HTTP probes and database indexes was more useful than UI debugging here. Compared with Convex or Supabase, windows are not inherently harder, and declarative uniqueness helps reactions. The missing compile-time index check and degraded error presentation are maturity costs. Media is struck, so this milestone provides no comparison evidence for storage or uploads in any backend, including Snapback 2.

## M5 boundary — 1789227308
Built settings, palette validation, three search scopes, captured message TTL, guarded reads, client-triggered purge, archive cleanup, and the Hermes export. Local search over synced data was straightforward, and the frozen kit made consistent settings easy. Time-dependent authorization fought the platform: rule syntax rejects greater-than, so the strong expiry guarantee remains unmet despite a passing UI expiry choreography. A second friction was stale hooks after switching between components using the same query; a distinct settings operation resolved the reproduced navigation failure. Familiarity with React lifecycles and local persistence helped isolate this from correct server state. Missing indexed word search means scanning retained rows, with scale limits still unproven. Compared with backends with programmable server handlers, Quarry makes schema-level ownership concise but leaves less room to enforce time-dependent reads. Suite and non-struck choreography pass; the server-read gap is explicitly separate from that authoring green.

## M6 boundary — 1789228291
Built the token-based API documentation and dependency-free demo, push outbox/provider sink with per-device leases, durable offline message/like/reaction validation, bootstrap schema caching, replay adapter and independent manifest verifier. The sample and full replay use the actual auth/mutation path. The successful fresh replay passed both checkpoints and final entity, relationship, and named-content checks; a prior attempt was stopped by my own verifier field-name mistake and is retained. The plain JSON protocol and stable mutation IDs were easy to use, and the sequential replay was pleasantly fast. Cold boot fought me because startup fetched schema despite a durable replica; caching that public response through the documented fetch option fixed it. Shaped queries also dropped pending metadata, requiring an unshaped companion query. Familiarity with offline stores, idempotency, and lease-based presence saved time. Compared with Supabase's usual client assembly, the local queue is substantially less work; compared with a mature offline stack, these bootstrap and hook edge cases demanded more app scaffolding. Push is a durable outbox seam with a 15-second abrupt-disconnect lease, not an external effect system. The final browser suites/choreography and Hermes export pass; native runtime behavior is not claimed.

## M8 boundary — 1789229406
Built maintained server Insights totals, UTC activity buckets, paged indexed Trending, refresh controls, and same-account offline convergence. Existing dev and scale stores were backfilled through deterministic server mutations. The supplied suite and choreography pass; a separate browser probe proves pending messages survive page destruction, restore offline, flush once, and reach read, plus live same-account edits/reactions through the real UI. Maintained counts made server reads compact and fast on the installed corpus. The work fought me in undocumented arithmetic and sum spellings, ambiguous unique-index diagnostics whose suggested upsert spelling was invalid, and a catalog-adoption race while a data CLI opened the fresh scale store. A two-column metric key and an exact-PID restart resolved those. My own pending-row sort also caused a transient dual-offline order failure; raw authoritative timestamps plus pending-at-end ordering fixed it. Familiarity with materialized read models, cursor merging, and optimistic UI state was valuable. Compared with SQL I wrote more explicit denormalization, while compared with function-oriented backends I wrote less aggregation read code. Scheduled digests remain struck, and M7's message-count migration remains untouched. Full-corpus analytics API checks pass; a native runtime proof and hidden performance growth curve remain unclaimed.
