# Building Clique with Snapback 4

Snapback 4 made the center of this application unusually compact, then made several edges unusually demanding. The most valuable part was having the data model, ownership rules, sync audience, and mutation intent in one Quarry program. I could read a conversation table and its membership relationship together and understand why a user should receive a row. The hardest part was discovering where that attractive model stopped matching the client’s observable behavior. This was a cold build from the published package, not a continuation of a familiar codebase. My comparisons with other backends are architectural judgments from model knowledge, not claims that I ran equivalent implementations alongside this one.

The early work benefited from the small surface. Profiles, follow edges, posts, and direct messages translated naturally into tables with unique keys and explicit mutations. A follow or reaction could be a set-state intent, backed by a uniqueness constraint, without a separate resolver layer. The generated operation types kept the frontend attached to the authored schema. I particularly liked being able to express a conversation’s membership audience beside the table instead of rediscovering it in every subscription handler. That reduced the number of places where I had to remember the product’s authorization story.

Convex is the closest comparison in the way an application developer thinks about queries and mutations. In a function-oriented system, I would normally put input validation, membership checks, and the write sequence into a server function, then subscribe to its result. Quarry moves more of that work into a constrained language and its table rules. That is a useful reduction when the operation fits. The cost is that a familiar programming technique is not necessarily available when the operation stops fitting. Immutable local bindings, restricted rule expressions, and explicit bounded reads changed how I designed the solution, rather than merely changing its syntax.

Expiry was the clearest example. The requirement was stronger than hiding a message in the interface: every server read had to refuse expired content. The compiler rejected a time comparison in a table read rule. A query could compare server time and refuse, so I built a guarded point read. That did not make ordinary history or raw replication safe before purge. I verified the difference with both conversation clients closed and retained the evidence. In a programmable query handler, a time guard is ordinary control flow; in SQL, time-dependent predicates are familiar tools. Here the rule language’s restriction left an actual product guarantee unmet. A passing UI expiry test cannot erase that distinction.

Supabase suggests a different tradeoff. A relational design would make these relationships and aggregates familiar, and SQL offers a broad vocabulary for filtering, grouping, and ranking. It would also leave me with more work to assemble the offline replica, durable intent queue, optimistic updates, and reconciliation behavior required by this brief. Snapback supplied those pieces as one client model. The benefit was real: messages, likes, and reactions could use the same durable mutation path. I did not have to invent a general synchronization protocol before building the messenger.

The offline work nevertheless required more scaffolding than the package’s simplicity initially suggested. Cold restoration attempted a schema fetch even when the session and message rows were already durable. Caching the public schema response through the documented fetch option made the browser cold-start probe pass. Shaped history rows omitted the pending metadata that an unshaped query exposed, so the UI needed a companion query. Separate browser tabs also needed separate durable replica-store slots. These were tractable fixes, but they moved responsibilities back into application code that I had expected the client abstraction to cover.

The subscription lifecycle was another revealing edge. A color update was correct on the server and in an explicit local query, yet the settings screen stayed stale after navigation from a conversation. Opening settings directly worked. Giving settings a distinct query avoided the apparent shared-subscription teardown problem. That distinction took a focused reproduction to uncover; the first visible symptom looked like failed sync. A mature reactive backend’s greatest convenience is not merely delivering events. It is making the relationship between an event, a query snapshot, and a rendered component dependable enough that the developer rarely has to investigate that boundary.

Retained history also changed the shape of the app. The product wanted a removed member to retain previously delivered history while losing access to future messages. The package’s local rule evaluation hid the retained rows after membership removal. I added a supplemental archive of history actually rendered while authorized. That met the visible retention behavior, but it created another store whose expiry and deletion semantics needed attention. I would treat that archive as a debt requiring careful review before production deployment, particularly for tombstones delivered after removal. A simple schema declaration did not completely discharge the application’s obligation.

The published documentation helped most when a diagnostic supplied a concrete, valid next step. It helped less when the next step was itself rejected. The README’s maintained-sum spelling did not compile, and an index-disambiguation rewrite was not accepted in the upsert position that needed it. A missing sync index had also passed the static check before failing at runtime. None of these problems made the underlying design impossible, but each forced an extra experimental loop. In a constrained language, canonical examples and trustworthy diagnostics carry more weight because ordinary language intuition is a less reliable fallback.

Insights showed the upside of those constraints once the model was settled. I introduced per-post facts, maintained totals, and UTC-day aggregates. The client received a small server-computed result rather than paging through content to invent totals. Trending used two indexed day partitions, ordered by likes and timestamp, with cursor paging past candidates outside the precise trailing window. This resembles the explicit read models I would build in a document database or a function-oriented backend under load. SQL would likely make the initial expression shorter, but the maintained representation made the read cost and update obligations easy to identify.

The replay was a useful counterweight to the debugging. The plain JSON protocol and stable mutation IDs made a sequential adapter straightforward. Registration used the real auth path; each write settled before the next. I made a verifier mistake at the first checkpoint, preserved the failed attempt, corrected the field names, and started another fresh instance. The successful run matched the non-media invariant state through both checkpoints and the final corpus. That gives me confidence in the basic write and storage machinery. It does not substitute for the hidden performance grader or prove every client path at the envelope.

The push seam required a similarly explicit boundary. Quarry could append an immutable notification payload transactionally, so I used a durable outbox and a reference polling sink. Per-device leases approximate whether the recipient has a connected UI. That is a reasonable seam for this build, but abrupt disconnect detection has a grace period and no external notification service is integrated. An effects-oriented backend would offer a more direct home for provider invocation. Scheduled work was struck from this run, so I cannot use the absence of a digest implementation as evidence for or against the experience of implementing one.

For Snapback 2, the evidence boundary is narrower. I did not inspect its source, documentation, previous implementations, or benchmark runs, and I do not have grounded runtime observations from it in this session. I therefore cannot honestly claim that a particular Snapback 4 behavior is a regression or an improvement over version 2. The comparison I would want is concrete: the same expiry authorization rule, the same cold bootstrap, the same navigation subscription lifecycle, and the same replay. This run establishes those questions and Snapback 4’s observed answers; it does not establish an upgrade recommendation from Snapback 2.

My preference after this build is conditional. I would value this backend for a relational application whose authorization and synchronization rules fit Quarry, especially when offline writes are central. I would budget engineering time for client lifecycle validation and read the release’s unsupported surface as a design constraint, not a footnote. I would prefer a more programmable server boundary when temporal authorization or external effects are core requirements. Clique reached the requested authoring green checks, but the expiry gap is enough that I would not describe the result as production-ready. The experience reduced the amount of routine backend glue while making the remaining escape hatches more consequential.
