I inherited the app without its builder context and added group polls using the frozen composer and display components. Questions and options are validated in Quarry. A vote is one principal-scoped row, replaced by an explicit option choice, with the existing Snapback local client supplying durable mutation IDs, offline prediction, and replay. Poll messages reuse receipts, expiry, and deletion. Settings now wait for an authoritative count read rather than showing a cached value while expiry cleanup is pending.

The client extension felt straightforward. The generated types and the existing reaction path supplied a useful model, and the kit already expressed selection, tallies, and pending state for the browser harness. The first full poll choreography passed without a custom queue or synchronization service. The inherited code was compressed and carried several documented platform workarounds, so reading the API, tests, and report mattered more than guessing the original intent.

Migration fought me. The published package said new maintained aggregates were backfilled; hot adoption announced a rebuild, but existing conversation groups read zero while new messages counted correctly. A semantic no-op update did not repair them. I used an explicit authenticated, paged migration that creates an idempotent count contribution for every visible existing message. Snapback maintains the count of those contributions afterward. Sends, polls, tombstones, and expiry update the contribution in the same mutation. Exact custom-client snapshots proved the migration preserved the inherited message fields, reactions, and receipt states; subsequent test clients legitimately advanced receipts.

This is a working starter-state evolution, not evidence of unrestricted production scale. Count reads scan bounded history to enforce server-time expiry and refuse beyond their bound. The inherited general history/raw-sync expiry security gap is still present. I did not repair it under this phase. Native evidence is a Hermes bundle, not a simulator session. Temporal count testing used a disclosed development seed adjustment of expiresAt after a real send; it did not wait a full production disappearance interval.

Compared with SQL migrations I know, Quarry made the additive schema and authorization concise and avoided hand-written aggregate triggers, but the misleading rebuild report forced an application-level migration ledger. Compared with function-based backends such as Convex, the fixed Quarry execution forms reduced backend code while making bounded traversal and read-time maintenance less flexible. Those comparisons are architectural judgments from prior knowledge, not measurements against another lane, checkout, or benchmark run.
