# Clique: where the backend changed the work

*Written after M8's green boundary, before tallying this run's quantitative results. The scale replay is still running. This is a qualitative account of this cold build, not a comparative benchmark of other products. I used only the installed Snapback 4 release and its published surface; I did not inspect earlier implementations or source checkouts.*

## One language carried more of the product

The strongest impression from building Clique is how much behavior belongs in the backend definition. Profiles, membership, send-time recipients, receipt positions, asset placement, disappearance, view-once access, aggregate counts, notification effects and schedules all live in Quarry. The client mostly turns those results into the supplied presentational kit. That concentration mattered more than the shortness of any individual query. When a message expired, its read authority, delivery state and asset access were tied to a server-owned row rather than separate cleanup promises scattered through the application.

The simple social features were straightforward. Creating a profile, returning a shaped post, and maintaining counts felt like writing the product model directly. The generated API then gave the client a concrete contract. Quarry still required learning: row references, optional fields, principal types and page completeness are real distinctions, and JavaScript habits did not always translate. I initially tried a convenient string construction for a DM identity and later tried notification fanout over a derived list. The compiler rejected both. The fixes followed the model it actually supports: sorted principal columns for the former, the original capped membership page for the latter.

This is different from how I would ordinarily approach Supabase. With PostgreSQL, SQL and row-level security provide a familiar, flexible foundation. I would expect to distribute Clique's remaining behavior among database functions, triggers, storage policies, scheduled execution and client synchronization code. Those are powerful building blocks, but the connections between them become application work. Here, asset authority and expiry were part of the same declared system. The tradeoff was giving up familiar SQL freedom and accepting a more constrained language with explicit bounds.

## Offline behavior was architectural, not a final embellishment

The local client changed the shape of the app early. The browser uses the package's persistent device and the native build uses the separately installed Expo arm. The same queries read synchronized state, and writes have pending, sent or failed outcomes. A process-device proof could close the client, reopen the same device offline, observe pending messages and cached history, then reconnect and verify the server's settled identities. That is materially less application plumbing than building a durable queue and replication protocol by hand.

It did not mean every mutation could optimistically manufacture a result. Public-feed delivery involves server-side state, and exact Trending ranking introduced server-owned reads into the like transaction. Those writes can queue while the UI shows that they are pending. I had to distinguish “the user's intent is durable” from “the device has enough evidence to predict its result.” That distinction is useful, but it also needs careful product language. A permanently vague spinner would squander the platform's richer outcome model.

Against the Convex programming model I know, Snapback's local database is the largest difference for this brief. Convex's reactive query and mutation model is an attractive fit for live social interfaces, with ordinary TypeScript carrying much of the domain logic. For this build's deeper offline requirements, I would still need to examine and implement the durable offline behavior explicitly rather than equating reactivity with persistence. Snapback supplied that arm directly, while asking me to learn its replication coverage and prediction boundaries. I did not build the alternative here, so this is an architectural comparison rather than a claim about elapsed time.

The implementation also exposed a mundane integration lesson. An early conversation navigation loaded the web replica through a lazy import. The tightly timed network transition could arrive before that dependency was ready. Static platform-specific device modules made readiness more predictable. That was my integration mistake, not evidence of a broken backend. The live receipt proof only became convincing after testing the actual navigation and offline sequence.

## Media and time justified the integrated model

Media tends to make otherwise neat messaging demos incomplete. Clique needs real uploads, inline images and video, deleted-media revocation, disappearance with no client open, and one-view photos that cannot quietly become an ordinary cached asset. The platform's image/video fields and dedicated one-view column gave those requirements a place in the schema. The client still had responsibilities: fetch a one-view image only on explicit opening, revoke the temporary URL when closing, and render the opened state without fetching it again.

The server clock controls edit, delete and disappearance windows. The shortened fixture configuration could therefore exercise the same logic as production values. An isolated server proved expiry without relying on an open browser. Another isolated server advanced beyond a day to distinguish an actual rolling Trending window from a convenient UTC-day approximation. The guide explicitly called out that difference. That was valuable documentation: it described the semantic trap rather than merely listing syntax.

Earlier Snapback generations are not directly represented in this run. I have no cold-build evidence here that supports a numerical improvement over them, and I did not use an older checkout as a crib. The relevant contrast is conceptual: a smaller backend or an earlier generation without this integrated local, asset and scheduling surface would push more of these responsibilities into client code or external workers. This release exposed those responsibilities as one published package family. Whether that represents an improvement over a particular earlier release requires a separate comparable run.

## Bounds are both assistance and work

The published feed recipe was especially helpful because the workload includes a celebrity and a user following many accounts. Its private delivery and shared broadcast paths provided a concrete starting design. I did not have to invent fanout storage entirely from memory. At the same time, caps, indexes, membership prefixes and cursor ownership became part of ordinary authoring. A page without a cursor can be incomplete even when the interface only wants a fixed number of visible rows. That needs understanding; pretending an incomplete answer is a total would be a serious analytics bug.

For Insights, maintained lifetime and calendar groups produced small server answers without client corpus paging. For Trending, I chose a separate ranked table, updated transactionally and expired after the post's trailing-day lifetime. That preserved zero-like candidates and exact ordering on load. The design was more explicit than a casual sort over whichever posts happened to be cached, and it made the correctness argument inspectable.

The digest is where I deliberately favored a clear implementation over an elaborate incremental one. It uses resumable server sweeps: initialize each user's period counts, examine eligible messages and current memberships, then emit at most one payload for each nonempty period. No external cron or browser callback drives it. The restart and quiet-period proof passed. It does scan message history, so I would revisit that cost for a production workload beyond this exercise. The platform removed scheduler infrastructure; it did not choose the application's optimal digest data model for me.

## What I would carry forward

The successful pattern was to treat generated types, compiler diagnostics and complete read results as evidence. I also learned to keep proof infrastructure honest. An isolated test store needs its own service token; a guessed health endpoint is not a documented readiness check; a Hermes export demonstrates a compiled artifact, not native interaction. The frozen browser harness also depended on a missing external schema helper, which required an explicitly recorded environment repair in the lane. None of those issues should be relabeled as product capability results.

A PostgreSQL/Express implementation would offer maximal freedom, and Supabase would package much of that foundation. Convex would keep more application behavior in a broadly familiar language with a reactive server model. Snapback 4's distinctive benefit in this build was that offline state, authorization, media lifetime and scheduled work were available through one coherent authoring surface. Its distinctive cost was learning the exact boundaries of that surface and designing around explicit completeness and structural constraints. For a messaging app with this much offline and temporal behavior, that was a consequential trade: less glue to maintain, but more backend semantics to understand before the interface could honestly claim success.
