# PocketBase after building Clique

PocketBase was at its best whenever Clique could be expressed as a collection
of durable records plus a small amount of local product logic. The first useful
backend was almost comically compact: one executable, one data directory, an
auth collection, and a handful of base collections. There was no account
provisioning ceremony, cloud project, deployment wait, or service boundary to
debug. Being able to inspect the server help, create the superuser, author the
schema through the same API that manages it, and immediately use password auth
made the beginning of the build feel direct and legible.

That directness continued through the social core. Posts, follows, likes,
reposts, conversations, and messages all fit comfortably as records. File
fields made fixture avatars and media pleasantly mundane. Explicit indexes and
autodate fields kept reverse-chronological projections fast and deterministic.
The JavaScript SDK was small enough that the browser and headless tooling could
share nearly identical calls. A custom-client API did not require inventing a
second protocol: documenting the native collection protocol, auth token, sort,
filter, and paging behavior was credible and testable.

The friction appeared where Clique stopped being a record CRUD application and
became a coordination system. PocketBase realtime is record-oriented, but the
app needed typing leases, connected-device knowledge, monotonic delivery/read
state, membership-at-send recipient sets, ordered offline mutations, and
per-device convergence. I represented these as more records and used frequent
portable polling for the web proof. That worked, but it is application
infrastructure, not a backend capability I received. Presence and typing in
particular feel heavier than they should because a transient signal becomes a
durable row plus an expiry convention.

Offline was the clearest dividing line. The SDK persists auth, not application
data or mutation intent. The durable snapshot, ordered set-state queue,
reconnect flush, pending UI, and conflict posture were all mine to build. The
result handled the web choreography cleanly, including two offline contexts for
one account, but it did not magically become a complete native sync engine.
PocketBase offers a good local server; it is not a client database with a sync
protocol.

Authorization had a similar shape. Simple authenticated reads and owner edits
fit collection rules. Group history, removed-member cutoff, promoted admins,
view-once assets, and server-time edit/delete windows demand hooks or custom
routes. The hook runtime is genuinely useful: it let the backend own push-log
emission and scheduled digest work without adding Express. Yet the complexity
has merely moved into embedded JavaScript. The protected-file and one-time
asset story especially needs more than a permissive file field and a viewed-by
array.

The scale run exposed both sides of the product. A single local SQLite-backed
binary accepted the entire deterministic envelope and reproduced every
published invariant exactly. That is an impressive operational result for such
a small deployment. Indexed conversation history stayed stable deep into the
busy chat, cold conversation sync remained quick, and high-follower post
creation did not slow down because the design avoided fan-out on write. On the
other hand, a very large author predicate exceeded the practical query surface,
and unindexed global text search grew too sharply. Server-maintained search and
aggregate read models were not optional at that point. The autogenerated
migrations also revealed a sharp edge: collections created within the same
second received filename ordering that did not preserve relation dependencies
on a fresh instance. The collections API remained reliable, but the generated
migration artifact did not.

Compared with Snapback, PocketBase feels smaller and more immediately
inspectable, but less opinionated about the cross-client state machine Clique
needs. Snapback's appeal in this comparison is the possibility of making local
data, mutation ordering, and synchronization part of one explicit application
contract. PocketBase instead gives me an excellent compact server and asks me
to design the client convergence layer.

Compared with Convex, PocketBase has far less deployment and platform magic.
The database is a file I can retain, the server is a process whose PID I own,
and the protocol is visible. Convex would likely make reactive queries and
server functions feel more native, especially for feed and message updates,
but at the cost of a hosted runtime and a more proprietary execution model.
PocketBase's polling solution was more work, though its custody story was much
clearer.

Compared with Supabase, PocketBase wins decisively on local provisioning and
operational surface area. Supabase brings stronger PostgreSQL querying,
full-text search, relational joins, and row-level security, all of which would
matter at the scale boundary. It also brings a larger stack and more services
to understand. PocketBase was easier until the query became genuinely
relational or aggregate-heavy; then PostgreSQL's mature planner and index types
would have paid back the complexity.

Compared with Firebase, PocketBase felt more transparent and portable. I could
inspect the SQLite data, run the whole service offline, and avoid vendor account
setup. Firebase would provide a more established mobile offline story and push
ecosystem, but its authorization/query constraints and document-model tradeoffs
would still make Clique's group semantics and analytics careful work.

Compared with hand-rolled Postgres plus Express, PocketBase removed an enormous
amount of scaffolding: password hashing, token issuance, CRUD endpoints, file
storage, migrations machinery, dashboard, filters, and scheduled jobs were
already present. The hand-rolled stack would be more work at the beginning but
more comfortable when implementing custom SQL aggregates, transactional group
authorization, revocable sessions, protected media issuance, and indexed
search. PocketBase postpones that custom-server moment remarkably well; Clique
eventually reached it, but much later than it would with Express.

My lasting impression is affectionate but qualified. PocketBase is a superb
production-shaped backend for a small team that values custody, simplicity,
and understandable operations. It can carry a surprising amount of product.
For a messenger whose hardest requirements are offline convergence,
authorization-rich group state, ephemeral assets, and large-corpus analytics,
I would treat it as a strong server foundation rather than a complete backend
platform. The build was enjoyable precisely because the foundation stayed
visible—even when the missing layers became mine to own.
