# Convex lane reflection

This run felt less like using Convex and more like failing to cross the line between a React prototype and a backend-integrated product. I pinned `convex@1.45.0`, authored a Convex schema and functions, and used the package as the intended backend dependency. However, I did not establish an anonymous local Convex deployment in the available build interval. That matters: the resulting app stored its state in browser storage and used BroadcastChannel for a tiny same-origin live-update experiment. It is not an honest substitute for Convex, especially under the fixture’s two-context, authentication, revocation, and scale requirements.

The strongest part of the experience was the instrument. The fixture logs, compact action grammar, assertion IDs, and choreography selector contract make a remarkably precise product definition. Instead of guessing what “messaging” means, I could see exact expectations such as one DM per pair, server-time edit windows, group receipt aggregation, and view-once non-durable caching. The frozen harness also did its job: M1 navigated into the app and failed profile live visibility; M2 reached actual posting then found the absent media chooser; M3–M8 exposed missing conversation, offline, and insights behavior. Those are better signals than a handwritten checklist.

Convex would have been attractive here if initialized early: reactive queries fit the live-feed, presence, read-state, and multi-device portions naturally, and typed functions plus schema validation would reduce the amount of ad-hoc API plumbing. Compared with a self-hosted SQL backend, its subscription model is probably the most ergonomic fit for the choreography. Compared with Snapback-style local development, though, the need to establish a deployment/auth runtime is a meaningful early hurdle when the benchmark explicitly asks for anonymous/local development. I found the package pin and function authoring straightforward, but I did not obtain the operational feedback loop needed to trust mutation/auth behavior.

The build also highlights what a backend cannot make free. Even with Convex connected, this benchmark still needs a durable offline mutation queue, deterministic seed/replay adapter through real writes, media storage and revocation, push/digest seams, and rich client state. Those are product work. The most useful next iteration would start with Convex dev deployment and fixture replay before UI breadth: use backend identities, replay M1–M3 into authoritative data, then make the first M1 choreography pass before adding feeds. That sequence would turn the very clear harness from a failure report into a development guide.
