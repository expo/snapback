# Building Clique on Supabase: a qualitative comparison

Supabase was a comfortable backend for building Clique because the product is fundamentally relational. Profiles, asymmetric follow edges, posts, reposts, direct-message pairs, group memberships, per-recipient receipt state, and reaction uniqueness all wanted ordinary tables, constraints, and transactions. I rarely had to translate the product into an alien storage model. When a rule mattered, I could usually point to one durable place that enforced it: a unique index for one direct conversation per pair, a composite key for one reaction per person per message, a foreign key for quote targets, or a security-definer function for an atomic state transition. That directness made the backend feel production-shaped early.

The strongest part of the experience was the combination of Postgres and the published JavaScript client. The client was enough for Auth, table reads, RPC calls, Storage, and Realtime, while SQL remained available for invariants that should never depend on a browser behaving well. The same function surface worked from the Expo app, the fixture adapter, and the custom client demo. Row-level security also made the trust boundary concrete. Conversation history, recipient rows, and private media were not merely hidden by the interface; access was decided at the backend and at Storage URL creation.

That strength came with a cost: Supabase is several coordinated systems, not one uniform programming model. Auth, PostgREST, Realtime, Storage, and the Management API each have slightly different error behavior and policy implications. A private message image, for example, involved an owner upload policy, an upsert-specific SELECT requirement, a message/member authorization policy, and a separate rule for chat backgrounds that happened to live in the same bucket namespace. The initial failure said only that row-level security rejected the operation. The useful explanation emerged from inspecting the actual lifecycle, not from the error itself.

Realtime was similarly capable but deliberately low-level. Postgres Changes delivered the durable mutations and Broadcast handled typing well, but the application still owned projection settlement. A table notification is not a ready-to-render feed or message bubble. My first implementation refreshed complete projections after each event, which was correct in a quiet single-client test and too slow or racy at the frozen observation boundary. The eventual design used immediate payload insertion for messages, optimistic set-state projection for reposts, authoritative request generations, and background reconciliation. Supabase supplied the signals; Clique had to supply the synchronization semantics.

Compared conceptually with Snapback, Supabase felt less integrated around the benchmark workflow and more like assembling a proven database platform. Snapback’s attraction for this kind of exercise is a single backend-shaped development loop: schema, mutation behavior, local runtime, replay custody, and evidence can be designed as one system. Supabase gave me mature independent surfaces instead. That made ordinary product data work familiar, but it also meant the scale fixture crossed a hosted Auth quota before the database envelope was reached. A local, lane-owned runtime with Auth configuration under the same process boundary would have made the replay more controllable and the failure more attributable to the application rather than the service posture.

The contrast is clearest around iteration. With Supabase, changing a function was easy and changing an RLS policy was expressive, but applying broad schema text while live clients were connected could contend with unrelated Storage locks. I learned to make narrow Management API changes for narrow defects. Snapback, as I understand its intended shape, can make that migration/runtime relationship more explicit and keep the authoring feedback loop inside the repository. The trade is ecosystem maturity: Postgres constraints, SQL inspection, and Supabase’s published client behavior were already familiar and powerful, while a newer integrated backend asks the builder to trust more bespoke machinery.

Compared with Convex, Supabase gave me more database-native leverage and less end-to-end reactive abstraction. In Convex I would expect queries and mutations to be TypeScript functions with reactive query invalidation as the central mental model. That can remove much of the manual subscription and projection plumbing that consumed time here. It also tends to make client-visible state follow server functions naturally, which is appealing for feeds, unread counts, and live message lists.

On the other hand, Clique’s dense relational rules were pleasant to express in Postgres. Partial unique indexes, transactional advisory locks, full-text indexes, server-time expiry predicates, and set-based aggregate queries were all close at hand. In Convex, I would expect more of those guarantees to be encoded through application functions, indexed access patterns, and careful denormalization. That may produce an excellent reactive product, but the proof that two concurrent callers cannot violate a pair-unique or one-row-per-recipient invariant feels especially crisp in SQL.

Supabase’s operational posture was the main source of ambivalence. For day-to-day feature work I liked it: the data was inspectable, failures were usually diagnosable, and the final API did not need a custom server process. For a deterministic benchmark replay, the hosted boundary was restrictive. Real signup was correctly part of the workload, yet its quota prevented the workload from reaching the part of the system whose scale behavior I wanted to observe. The platform did the safe hosted-service thing; the benchmark needed disposable infrastructure with adjustable limits.

My overall qualitative impression is therefore positive but conditional. Supabase is a strong fit when the team values Postgres semantics, wants a broad managed backend, and is willing to design projection settlement explicitly. It is less effortless when one workflow spans Auth load generation, private Storage, high-frequency realtime state, offline reconciliation, and reproducible local replay. Snapback’s integrated custody could be better for that controlled loop, while Convex’s reactive functions could be better for reducing client synchronization code. Supabase’s advantage is that none of its individual pieces felt mysterious once isolated: the hard part was composing them into one precise product contract.

M8 sharpened that conclusion. The Insights and Trending queries were terse, legible SQL, and a second same-account browser received messages and unread-state changes without any new backend abstraction. The difficult edge was entirely projection settlement: when two warm-offline Alice clients reconnected one after the other, a committed Realtime payload could coexist for a few milliseconds with the same locally queued ID. Deduplicating by the durable message ID made all three clients converge in server-arrival order and preserved read receipts. That is a fair picture of Supabase at its best and its most demanding: the database makes identity and order crisp, but the client remains responsible for turning asynchronous signals into one coherent render.
