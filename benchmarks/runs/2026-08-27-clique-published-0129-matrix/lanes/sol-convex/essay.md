# Building Clique on Convex

Convex was at its best when Clique behaved like the product it is: a collection of live, related views over shared social state. Once a message, reaction, follow edge, or post mutation settled, the second browser generally converged without application-authored subscription plumbing. That changed the character of the work. Instead of designing a transport, invalidation protocol, and cache-key scheme for every screen, I could spend more attention on the authority rules: who may read retained history after group removal, when an edit window has expired, whether a view-once asset is still authorized, and which aggregate receipt state should be shown. The reactive function boundary was a good fit for feeds, chat timelines, unread projections, and profile counts.

The schema and function model was also comfortable for a production-shaped prototype. Tables and indexes were explicit, while mutations provided a natural place to enforce handle uniqueness, direct-message deduplication, membership, and idempotent fixture identifiers. Compared with a conventional SQL backend such as Supabase, this traded declarative relational constraints and ad hoc query power for a more cohesive TypeScript authority layer. I missed database-level unique constraints and occasionally wrote more lookup-and-check code than I would in Postgres, but I also avoided splitting policy among migrations, row-level-security expressions, generated client types, and server functions. For this timed build, having one language and one authorization path was a material advantage.

The comparison with a small record server such as PocketBase is similar but sharper. PocketBase can make CRUD and local administration extremely quick, and its SQLite-shaped operational story is wonderfully legible. Clique's requirements, however, are dominated by derived state and synchronized transitions rather than simple forms. Receipt aggregation, retained-history cutoffs, view-once authorization, disappearance, and celebrity/feed probes all benefited from transactional server functions. Convex felt more natural there. The cost was operational opacity: I had less immediate visibility into raw data and query plans than I would with SQLite or Postgres, so bounded diagnostic functions became part of the build.

Snapback's appeal, from the published product shape and my general familiarity rather than any inspected implementation, is a tighter offline-first abstraction. Clique's hardest cross-cutting requirement was not realtime delivery; Convex handled that cleanly. It was durable offline intent and the distinction among cached, pending, sent, delivered, and read states across reloads and devices. On Convex web I built that bridge explicitly with a local durable queue, deterministic client IDs, cached query projections, and idempotent server mutations. That worked for the frozen web choreography, but it remains application machinery. A backend whose central abstraction includes durable local state and sync semantics should make this portion feel more native and should offer a stronger native proof. Conversely, the explicit Convex implementation made every authority boundary inspectable and kept conflict behavior under application control.

Authentication was workable rather than luxurious. Implementing password signup, login, revocable sessions, and expiry in functions was straightforward, and bcrypt was ordinary TypeScript. It was still infrastructure I owned. A hosted auth system attached to Supabase, or a backend bundled with an established auth product, would provide recovery, email verification, abuse controls, and provider integrations that this benchmark did not exercise. Convex did not obstruct the custom model, but the pleasant local function experience should not be mistaken for a complete production identity system.

Local development had two distinct faces. The anonymous local backend was genuinely useful: no account dependency, reactive behavior representative enough for the web proof, and a real headless client surface. The public path to that setup was less polished. Exact noninteractive startup controls, isolated storage, admin-key derivation, and deployment to a second local instance were discoverable in the published package source rather than from an obvious stable CLI workflow. The CLI also rewrote the application environment file when aimed at the scale instance, requiring a careful restore. A local-first benchmark should not demand this much archaeology to create a second clean database.

The scale replay exposed both strengths and limits. Convex accepted the complete deterministic action stream through real auth and mutation functions, and exact checkpoint and final invariants conformed. Indexed paging, large-follow feeds, cold sync, receipt writes, and celebrity read/write probes stayed bounded. The single recorded degradation miss was subtler: Trending at the midpoint landed above the frozen line between the small and full samples even though all measurements were only a few milliseconds. The result must remain a failure under the instrument's exact banding. Technically, it also illustrates how a very fast colocated cache-backed query can make ratios sensitive to sub-millisecond noise. I would want server-side profiling and a frozen absolute ceiling before drawing broader performance conclusions; the published snapshot promised such ceilings but still contained placeholders.

The largest implementation friction was actually above the backend. The frozen React Native UI kit and React Native Web did not preserve every expected accessibility semantic, and web images rendered through CSS backgrounds where the browser choreography expected loaded image elements. I kept the kit's component contracts unchanged and adapted the application shell. That experience is not a Convex flaw, but it matters to the overall feel: the backend made live data easy while the cross-platform presentation boundary consumed several correction loops.

M8 reinforced the backend-side strengths. Insights totals, daily buckets, and Trending remained server-derived; same-account browser contexts received live messages and shared read-state clearing; independently queued offline messages reconciled exactly once and converged on both senders and the recipient. The only choreography corrections were missing web accessibility attributes, not aggregate or convergence defects. That distinction matters: Convex carried the synchronized product semantics while the adapter repaired observability at the presentation edge.

At the end of M8, my qualitative view is positive but measured. Convex made realtime application state, transactional authorization, deterministic headless replay, aggregates, and multi-context convergence unusually direct. It asked me to own offline durability, identity completeness, media persistence choices, and more operational diagnostics than a SQL-first backend would. Relative to Snapback's presumed offline-first center of gravity, Convex feels server-reactive first; relative to Supabase it feels more cohesive and less declarative; relative to PocketBase it feels more capable for synchronized domain logic and less transparent as a local database. For Clique's web run, that was a good trade, though not an effortless one.
