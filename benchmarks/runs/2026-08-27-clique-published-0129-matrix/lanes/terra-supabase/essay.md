# Qualitative backend experience

Supabase was a pleasant fit for the first half of Clique. The Management API made it possible to create a completely lane-namespaced schema without installing a local database, while `@supabase/supabase-js@2.112.4` gave the same client a credible auth, data, and Realtime surface. Seeding the named fixture accounts through `auth.admin.createUser` then writing profiles and social data was compact and easy to inspect. The browser client’s `postgres_changes` subscription also made the basic “another client changed something” loop natural.

The less pleasant part was the distance between a permissive prototype and the benchmark’s server-authoritative requirements. Rich authorization rules (membership-scoped messages, view-once revocation, edit windows, idempotency keys, scheduled digest) want RPCs, policies, storage policies, and likely Edge Functions. A broad authenticated RLS policy is enough to keep this short build moving, but it is not the production boundary Clique needs. Realtime change subscriptions refresh broad client state here as well; a production design would need scoped channels, indexes, paged queries, and server-side aggregates.

Compared with a Snapback-shaped integrated product surface, Supabase felt more explicit and composable: every table, policy, publication and function is a decision. That makes data ownership tangible, but it costs momentum when the product needs many coordinated invariants. Compared with Convex-style application data APIs, relational SQL is especially comfortable for follows, counts, histories, and future analytics, while live application workflows need more plumbing. I would happily use Supabase for Clique with time to design the RPC/policy layer; for a timed full-stack benchmark, it rewarded schema fluency but made the hard lifecycle semantics expensive.

The run was also constrained by the frozen fixture delivery: the committed scale log required by O5 was not present, only `scale-log.sha256`, so a valid full replay could not be attempted. The supplied choreography package declares Playwright but lives in the read-only instrument tree, preventing dependency installation there. Those are harness/fixture constraints rather than Supabase behavior, and they should not be mistaken for successful product proof.
