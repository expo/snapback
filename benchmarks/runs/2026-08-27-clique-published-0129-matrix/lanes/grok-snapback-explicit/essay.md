# Closing essay — Snapback explicit 0.1.29, Clique web lane

This sitting was one backend, end to end: published Snapback 0.1.29, default explicit `schema.mjs` / `functions.mjs`, generated Exact references, one supervised `snapback dev` owner, Expo Router on web. I am comparing that sitting to backends I already know how to finish an app on — Convex, Supabase, Firebase, and a hand-rolled Postgres + Express API — not to a later Snapback.

The part that felt most like Convex was the live-query core. Declaring `defineLiveQuery` over `posts`, `follows`, and then a scoped `messagesByConversation` with `limit: 80`, and wiring `useSnapbackQuery`, produced two-client feed and chat updates without a socket protocol of my own. M1 and M2 went green that way. M4’s photo/video/reaction/edit/delete choreography went green the same way. M3’s live DMs, typing (v2 boundary), group receipts, membership cutoff, and quoted replies went green once the query was scoped and pending sends were flushed into the DOM before the network round-trip. Additive schema in a running lifecycle (M1→M2 kept accounts and sessions; M2→M3 added chat tables without a reseed) is closer to Convex’s “push a new schema, keep the data” than to a migration night with Postgres. The explicit profile’s generated `api.sendMessage` handles are fussier than Convex’s `api.foo.bar` strings, but once they existed the client did not care about SQL.

Where Snapback fought like early Firebase is the gap between “the row is in the backend” and “Playwright can see the contract.” Headless `sendMessage` plus `markDelivered` wrote a delivered receipt in tens of milliseconds. The same transition in two Chromium contexts after `context.setOffline` did not, until I mounted a document reload *outside* the auth gate. React Native Web still does not map the frozen kit’s `accessibilityValue={{ text }}` onto `aria-valuetext`; an observability bridge had to lift those values. Convex and Supabase do not make you do that. They also do not ship a frozen UI kit that a harness reads as the API. The tax was real, and it was not a data-layer tax.

Supabase is still the backend I would reach for if the job was “password auth, Postgres constraints, storage buckets, and a REST/JS client by Friday.” Snapback’s built-in password sessions were closer to that than Firebase’s email-link maze: `signUpWithPassword`, unique handle index, `ctx.refuse('HANDLE_TAKEN')` mapped to a visible error, durable web custody. That is a B2 win. What Supabase would have given me for free and Snapback made me assemble: membership-scoped reads that hide rows from a removed group member without a client-side `recipientIds` CSV; a search index instead of NFC word-prefix over a retainable `allMessages` (M5 warm-offline search still missed the starter “Coffee after work?” row); a chat background that *did* upload and live-sync in a debug sitting, but whose RN-web `Image` host is a `div` without `src`, so the harness’s `observableState` never saw Carol’s preview change.

Hand-rolled Postgres + Express would have made receipts and disappearing messages easier to reason about (one SQL function, server time, done) and everything else slower. I would have spent M1 on session cookies instead of fighting Metro’s port range and `snapback dev` dying on pipe EOF. Snapback’s lifecycle receipt (`snapback.application-ready.v1`) is better than my usual “the server printed a URL.” It is worse when generation fails: handlers in a sibling module were unserializable until they lived inline in `functions.mjs`; Action auth is a closed set; `elevatedReads` is illegal on inline queries. Those errors named codes, which is better than Express stack traces, and they still ate a deployment identity rotation.

Offline is the comparison that stung. Convex has optimistic mutations and a cache story; Firebase has persistence; I have written outboxes on Express. Snapback advertises retainable live queries and a default mutation that “settles or queues.” Using `useSnapbackSettledMutation` required connectivity, so Playwright offline could not click `sm-convo-send` without the button oscillating through re-renders. Switching send to the default (queueable) mutation plus `flushSync` pending made *online* DMs live; it did not make the send control stable while the browser was offline (M6 and M8 dual-offline). I did not get to a place where I trusted the outbox, which is the opposite of “it fell out of the platform.”

Scale was a documentation and lifecycle bind, not a speed contest. The instrument’s `generate.mjs scale` produced 167,159 lines whose sha256 matched `scale-log.sha256`. A second `snapback start` on port 48103 with a fresh sqlite bound as `local-app` with no Clique schema, because this lane forbids `snapback start --startup-artifacts`. The combined invariant manifest therefore cannot conform on a schema-less instance. That is an O5 0, honestly, and it is not Snapback being slow.

The honest summary: I liked the explicit profile’s generated references, unique indexes, refuse codes, HostPlan `limit`, and additive successor in a running owner. I did not like authoring a production-shaped messenger against a contract that lives in Playwright semantic values on RN-web, or discovering that reconnect after `setOffline` is a document reload outside the auth gate rather than a client API. If the product were “a live social feed with password accounts and a scoped chat thread,” I would use this backend again. If the product were “WhatsApp-shaped receipts after a browser went offline, view-once revocation, and a 167k-action envelope on a second instance,” I would still start on Snapback for the live queries, and I would budget a week of platform-edge work that Convex or a thin Express API would have made me write anyway — just with fewer surprise codes and a documented way to stage a second sqlite.
