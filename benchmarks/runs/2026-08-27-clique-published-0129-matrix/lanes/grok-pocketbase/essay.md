# Essay: building Clique on PocketBase

This run was a cold PocketBase build: one local binary, no hosted account, JS SDK from npm, schema and behavior authored as migrations plus hooks. The product shape is a full social messenger. What follows is the qualitative comparison the brief asks for, against Snapback, Convex, Supabase, Firebase, and a hand-rolled Postgres+Express stack, using only what this lane actually felt like.

PocketBase’s pitch as a single self-hosted binary is not marketing. Download, unzip, `serve --http` on a loopback port, `superuser upsert`, and there is an app. That is closer to “open a folder and run” than Snapback’s explicit runtime, Convex’s cloud project, or Supabase’s linked project+keys. Firebase is also a console-and-credentials dance. Postgres+Express is a compose file, a migrator, and a process manager before the first route exists. For a timed lane that must provision inside itself, the binary is the best five minutes I had all day.

Built-in password auth on an auth collection is the other early gift. Registration, bcrypt-class hashing, JWT issuance, and “login returns a token plus a record” mapped onto M1 without inventing a users table. That is Firebase-shaped (Auth as a product) and better than hand-rolling argon2 in Express. Snapback and Convex also want you to use their auth story; the difference is PocketBase’s story is the same process as the database. Logout-as-revocation is the first crack: tokens are stateless JWTs, so “logout revokes server-side” is not a row you delete. Rotating `tokenKey` works and is documented if you already know to look. It is not a first-class session table. Firebase session invalidation and a custom Express session store both have a clearer “this token is dead” place to point at. I paid that cost in a hook, not in the dashboard.

Schema work is where PocketBase feels like a small Supabase: collections, fields, list/view/create rules, indexes as SQL strings. Relation fields and unique indexes made follow edges, likes, and “one DM per pair” natural. The autodate gotcha is real and unfriendly — a hand-authored collection does not grow `created`/`updated` for you, and `sort=created` then fails with a generic 400. Supabase/Postgres would have made that a migration error with a column name. Convex would not have a SQL sort in the first place. Once autodate fields are explicit, reverse-chronological feeds and keyset-ish cursors are ordinary.

Realtime is record-oriented SSE. Live posts, likes, and new messages “just subscribe.” That is the Convex/Firebase feeling, not the Express one. It is also not a presence or typing primitive. Typing became durable rows, an expiry timestamp, a sweep cron, and client-side hide. Receipts became a second collection plus an aggregate over a frozen recipient set. Group authorization — promoted admins, self-leave, removed-member history, membership-at-send — overflowed the rule DSL immediately. PocketBase can host that logic in JSVM hooks; the dashboard rules cannot express it. That is the same shape as “Supabase RLS is not a group-chat language” and the opposite of a backend that ships membership as a first-class object.

Files are the other place the product is obviously a BaaS. File fields, size/mime limits, protected files, and `/api/files/...` URLs made avatars and post images easy. View-once and delete-for-everyone are not a checkbox. They are `onFileDownloadRequest` plus a views table. Firebase Storage rules can say “only if not viewed”; they still need Cloud Functions for the one-view bit. Express would be an authz middleware on `/media`. PocketBase did not save that work. It did save the upload and serving.

The JSVM is the relationship. Official examples use file-scope helpers inside `routerAdd` callbacks. In 0.39.9 those callbacks do not close over file scope; they run as isolated functions (the stack says `pb.js:2`). Cron jobs have the same isolation. The fix — `eval` a factory from `api.js` inside each handler — is a builder-experience wound. Convex functions and Express route modules do not do this to you. Snapback’s function surface is also just functions. I burned a large correction loop discovering that PocketBase’s hook pool is not a Node module.

There is no offline SDK. Durable cache, ordered write queue, restart-survival, and “purge view-once from the cache” are all hand-rolled `localStorage`. That is Express-level work on a BaaS. Firebase has persistence. Convex and Snapback have their own sync stories. Supabase does not magically queue writes either, but the expectation is clearer. M6/M8 offline was the heaviest part of the run and the least PocketBase-native.

Push is a log I wrote. Detecting “no connected client” is a presence row plus a realtime flag, not a subscription registry I could actually call. Scheduled digest, though, is a real `cronAdd` against server time. That is more scheduler than Firebase client SDKs give you for free, and more honest than a “run it on read” fake. Compared with a Postgres job table or Cloud Scheduler, it is small and local and good enough for the shortened two-minute period.

Scale is SQLite in-process. The envelope is plausible if you index and avoid deep OFFSET. This lane’s scale replay against a fresh instance reached the ten-percent checkpoint and then died mid-posts; probes at that checkpoint already erroring. I would not sell PocketBase as “the thing that eats a celebrity with 900 followers” without proving the read path. Convex and hosted Postgres have a different failure mode (you pay, it stays up). The local binary’s failure mode is “the process is gone.”

Versus Snapback: PocketBase is less of a product for sync and more of a product for “I have an HTTP API and files.” Versus Convex: no reactive query language, no hosted durability, much simpler to run. Versus Supabase: same Postgres-shaped instincts, worse SQL, better one-binary story, similar “rules are not a chat ACL.” Versus Firebase: auth and files feel familiar; presence/typing/offline do not. Versus Express+Postgres: I still wrote a lot of Express, just inside goja, with worse debugging.

I liked the binary, auth, files, and cron. I did not like teaching hooks to see their own helpers, inventing offline, or pretending collection rules were a group-messaging authorization language. I would use PocketBase again for a small realtime app with password users and uploads. I would not start a WhatsApp-shaped product here without planning to outgrow the rule DSL on day one.
