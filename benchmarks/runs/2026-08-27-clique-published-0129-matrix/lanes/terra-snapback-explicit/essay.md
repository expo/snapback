# Notes on building Clique with Snapback

This run made Snapback feel most like a strongly guided application platform rather than a database with a client library. The `expo-chat` scaffold immediately gave me a real session program, explicit schema, generated operation references, a surface that joined a conversation's live data, a typed upload intent, and a supervised Expo web route. That is a richer first five minutes than hand-rolled Postgres plus Express, where I would have written migrations, password hashing, session middleware, websocket wiring, and a development launcher before I could even inspect a live message. The application-ready receipt was especially good: it named the exact Linux runtime package, schema/function identities, origin, and owned processes. This is the kind of operational provenance that usually gets added to a bespoke backend too late.

The explicit profile is both the virtue and the friction. `schema.mjs` and `functions.mjs` are readable declarations rather than magical file conventions, and generated references remove an entire class of stringly typed client mistakes. The scaffold's `conversation` surface also makes a useful statement: these live reads, mutations, commands, assets, and presence state belong together. Compared with Firebase, it is easier to see where server authority should live. Compared with Supabase, it front-loads the joining and authorization design instead of inviting a client to assemble rows and RLS policies piecemeal. Compared with Convex, it is more overtly declarative; that improves reviewability, but it also makes rapid exploration feel heavier.

Clique exposed the problem with that tradeoff. A social messenger is not just five tables. It needs profiles, a directed graph, posts and reply trees, per-conversation roles, read receipts, reactions with idempotent state, media lifecycle, revocations, scheduled jobs, aggregate insights, search, and a replayable fixture adapter. The starter was excellent evidence that a narrow chat works, but it did not provide a short, product-shaped path from that chat to the canonical social schema. I could infer how to add tables and live queries, but the authoritative docs workflow intentionally asks for one lookup at a time, and the benchmark requires dozens of interconnected decisions. That pacing is defensible for safety, yet it is expensive under a timed build.

Convex would likely have been faster for this particular benchmark because arbitrary server functions and reactive queries can be sketched quickly, then hardened. Supabase would make aggregate analytics and SQL-style graph queries familiar, though realtime and offline conflict handling still need deliberate design. Firebase would get a prototype on screen quickly, but complex permissions, relational feeds, and exact server-authoritative expiry would be less pleasant. A hand-rolled Postgres service would offer maximal flexibility and clear query plans, but it would be the slowest path to polished live/offline behavior. Snapback sits in an appealing middle: more constrained and traceable than a custom service, more product-oriented than a raw database, but currently demanding enough in its explicit declarations that it rewards a prepared schema plan.

The strongest moment was receiving the supervised application-ready receipt with a pinned published runtime and generated binding identity; it made the development environment trustworthy. The hardest moment was recognizing that the chat template's data model is not a substitute for the benchmark's full social domain. I would use Snapback again for a bounded collaborative application where its surface model matches the product. For an ambitious greenfield social product, I would want a canonical relational-social recipe, schedule/aggregate examples, and a migration guide that begins with the product model rather than individual API symbols.
