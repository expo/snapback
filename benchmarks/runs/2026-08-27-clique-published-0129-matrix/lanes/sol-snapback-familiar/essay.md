# Familiar Snapback after three Clique milestones

The most accurate short description of this experience is that Snapback's familiar profile succeeds at making backend code look ordinary, but does not yet make backend behavior feel ordinary. Through accounts, profiles, feeds, social actions, and the first messaging model, I could usually express product rules in straightforward TypeScript. The sharp edges appeared one layer below that syntax: lifecycle-issued identity, an inline-handler subset, durable client custody, authorization barriers, subscription behavior, and storage constraints. Those are not cosmetic differences. They determined a large share of the actual engineering time.

Compared with Convex, the authoring surface is recognizably close. A schema contains named tables, validators, and indexes. Top-level modules export queries and mutations. React components consume generated references through familiar hooks. That shape helped materially. For example, the unique DM invariant was naturally a unique pair-key index, the group membership check lived beside its mutation, and the M2 feed could join posts, profiles, follows, likes, and reposts in one readable handler. There was no separate controller, repository, transport DTO, or handwritten client API. When the path was green, the loop was pleasant: edit TypeScript, let the supervised lifecycle generate and rotate the binding, then observe the UI update.

Convex still has an advantage in how predictable that loop feels. In Convex, a mutation of data read by a subscribed query normally implies that the query will update everywhere it is subscribed. During M3 here, an Alice message settled and appeared after a fresh query, but remained absent from Bob's already-open live hook. A stored conversation revision made the initiating surface update, yet cross-client fanout remained stale. That gap is especially costly because it breaks the most valuable assumption behind a reactive backend: the dependency between transactional writes and subscribed reads. Once that assumption failed, I was debugging authorization custody, hook stability, subscription connection limits, and document reload timing rather than messaging behavior.

Snapback's diagnostics are stronger than many young backends in some places. The schema compiler precisely rejected structured IDs inside arrays. It identified a clock-dependent protected result when a live query filtered typing leases with runtime time. It warned about repeated exact lookups and unstable hook arguments. The lifecycle also reported exact old and new deployment identities and explicitly attested that the database, accounts, sessions, and stores were preserved. Those are excellent production-shaped affordances. Supabase or a custom Postgres service would require much more work to achieve equivalent typed deployment and continuity evidence.

The diagnostics were weaker at causal joins. A cross-client live query could stay stale without a receipt explaining which write it observed, which dependency invalidation it skipped, or whether its realtime handle had stopped advancing. Likewise, `SNAPBACK_OUTBOX_AUTHORIZATION_SUSPENDED` was explained well by the served auth-transition recipe, but discovering that a background React effect was contending with foreground gestures required reading logs and progressively removing writers. A production tool needs a single trace that connects the hook, current authority generation, mutation admission, server commit, invalidation publication, and subscriber revision. Without that, precise individual diagnostics still leave the engineer reconstructing the system narrative manually.

Against Supabase, PocketBase, or a conventional REST/Postgres stack, Snapback bought a lot. Sessions, generated types, local supervision, live-query declarations, and transactional functions arrived together. I did not have to configure row-level SQL policies, write cache invalidation code, define REST resources, or reconcile client DTOs. On the other hand, those conventional stacks are easier to reason about when something fails: a SQL row either changed, a request either returned it, and realtime is usually an explicitly separate channel. Snapback combines storage, authorization, local outbox custody, optimistic behavior, and subscriptions. The combination is powerful, but a failure crosses more layers.

The sessions model also felt more opinionated than Convex's typical authentication integration. Durable-required custody, single-writer outbox ownership, session-scoped mutation identities, and authority transitions were meaningful constraints throughout the run. They prevented unsafe cross-principal replay, which is a real correctness benefit. They also made an ordered fixture replay surprisingly delicate: stable transport IDs could conflict across fresh auth contexts, a refused attempt could still leave durable identity state, and two external clients for the same actor could contend even with distinct store IDs. The correct solution was to separate domain idempotency from transport identity and close authority owners before isolated replay. That is robust once understood, but it is not familiar merely because the handler was written in TypeScript.

The supervised development lifecycle was one of the better ideas. One owner controlled the backend, generated binding, Metro projection, and readiness receipt. Additive schema changes retained sessions and application state, and every successor named its identities. This is stronger than the casual “dev server restarted” experience common in app backends. The cost was sensitivity to generation and bundler timing: code edits could briefly leave TypeScript or Metro looking at a predecessor reference, and the React Native DevTools helper repeatedly failed its Linux sandbox setup even though the product server remained healthy.

The frozen UI kit provided a useful reminder that backend ergonomics do not end at data. React Native Web dropped `accessibilityValue` from the DOM, so semantic values needed a web projection bridge even though the kit contract was correct. Media also exposed a planning trap: storing fixture bytes as strings hit Snapback's structured-value ceiling, and the served Guide recommended typed asset intents only after the single M1-to-M2 schema transition was already active. The final web build uses the supervised asset projection and carries typed asset custody as a gap. Convex storage or Supabase Storage would also require an explicit asset path, but their limits and primitives are more widely known.

My qualitative verdict after M3 is mixed. I liked writing the schema and functions. I liked the exact lifecycle receipts, preservation facts, validators, and server-side refusal boundaries. I disliked how quickly a realtime messaging task turned into an investigation of hidden client authority and subscription machinery. The familiar profile removed declaration noise and made the application code approachable; it did not remove the need to understand Snapback-specific semantics. For CRUD and feed-style work, that trade looked promising. For multi-client messaging—the point where a reactive backend should feel most compelling—the observed behavior was not yet trustworthy enough.
