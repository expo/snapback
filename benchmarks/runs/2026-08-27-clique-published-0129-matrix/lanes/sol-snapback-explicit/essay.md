# Building Clique on Snapback’s explicit profile

Snapback’s explicit profile feels closest to a strongly typed application protocol that happens to own a database. The productive center of the experience was not “make a table, then expose an endpoint,” but “declare the stored fact, declare exactly how code may read and write it, and consume a generated reference.” That framing was unusually effective for Clique’s trust boundaries. Sender identity always came from `ctx.auth.userId`; group authority was centralized in membership helpers; unique rows captured follows, reactions, receipts, and view-once opens. When those pieces worked, the backend was easy to audit in a way that a rapidly built Express application rarely is.

Compared with Convex, Snapback asks for much more ceremony. Convex also encourages server functions over an authoritative database and has a similarly pleasant TypeScript client story, but its common query/mutation loop is less verbose. Snapback required argument validators, result validators, declared read sets, write sets, bounded query limits, and sometimes conflict or opaque-write posture. That cost time, especially while the data model was changing quickly. The benefit was that mistakes appeared as named generation failures before they became vague runtime behavior. The explicit declarations made it harder to accidentally trust a client-supplied principal or return an unbounded result. For a benchmark dominated by authorization invariants, that trade was often favorable.

The reactive experience was less consistent than Convex. Root message delivery and counters could feel magical in the good sense: one client wrote, another client’s generated query changed, and the UI updated. Child reaction rows and custom JavaScript projections were much less predictable. Several committed reaction changes were immediately visible to a fresh query but did not wake an already subscribed projection. I eventually used connection-owned ephemeral state only as an invalidation signal and then performed a fresh authoritative query. That preserved correctness, but it was application machinery I would not expect to write in Convex. A live-query dependency trace would have saved a great deal of time.

Compared with Supabase, Snapback kept more business policy in one language and one generated surface. Supabase’s Postgres foundation makes ad hoc aggregation, indexes, SQL inspection, scheduled jobs, and operational diagnosis familiar. Row-level security can express strong boundaries, but coordinating RLS, RPCs, triggers, storage policies, and Realtime publications often scatters the reasoning. In Snapback, the membership checks and mutation logic remained together. Conversely, I missed SQL badly for Insights-shaped aggregation, corpus verification, and expiry maintenance. Snapback’s bounded JavaScript queries are explicit and portable, but repeatedly fetching related rows is verbose and raised N+1 warnings. Supabase would have made those aggregations and background schedules more conventional.

Firebase is the closest comparison for the client-retention and offline ambition. Snapback’s generated references and explicit schema give it a much stronger review surface than a loosely structured Firestore project. Firebase’s mature offline write queue, cache semantics, and listener behavior are easier to rely on, however. Clique’s warm-offline search and pending message UI needed application-owned retained state, and the supervised web bootstrap did not always recover cleanly when the browser was taken offline at a navigation boundary. Snapback exposes thoughtful vocabulary around custody, outboxes, and local-first behavior, but the paved application recipe was not always as complete as the vocabulary suggested.

Against hand-rolled Postgres plus Express, Snapback saved the most on protocol consistency. There was no opportunity to forget that the web client, headless client, asset client, and live client needed compatible authentication; generated exact references kept them on the same contract. Typed media attachment and delivery were safer than inventing signed-URL conventions under time pressure. The lifecycle’s additive successors also preserved the same accounts, sessions, and store while the schema grew, which felt substantially better than manually coordinating migrations and restarting an Express server during a live acceptance run.

The cost was opacity at the edges. A hand-rolled stack gives direct access to SQL logs, request traces, and the exact scheduling mechanism. Here, a stale live projection or bootstrap failure required inference across generated references, served Guide pages, and client diagnostics. The diagnostics were usually specific once they appeared—clock-dependent protected visibility, invalid result contracts, unsupported media validators—but there was no equally good explanation for why a valid committed dependency did not invalidate a subscription. The published Guide was valuable, particularly the start packets, asset patterns, multi-persona recipe, and headless-client custody guidance. Its biggest weakness was discoverability: broad searches frequently returned no result even when a relevant page existed.

The explicit profile’s best moment was the view-once invariant. A recipient could open a photo exactly once because the server checked membership, checked that the message targeted the authenticated principal, checked the typed media row, and inserted a unique message/recipient open fact. The UI could be wrong without weakening that write boundary. Its hardest moment was making the same sort of authority feel live and offline across multiple React Native Web contexts. Snapback gave me strong tools for the durable half, but the last mile still demanded careful application state, semantic DOM projections for the frozen kit, and recovery logic around route changes.

At this point in the run, I would choose Snapback over an improvised Express backend for a local-first product whose authorization model matters and whose team values generated contracts. I would choose Convex for faster reactive product iteration, Supabase when SQL aggregation and operational familiarity dominate, and Firebase when proven mobile offline behavior is the primary constraint. Snapback’s distinctive promise is compelling: strict server authority plus one generated protocol across Expo and headless clients. The run also showed that the promise is not yet uniformly paved, especially for live invalidation, scheduled work, and debugging retained/offline state.

M8 sharpened both sides of that judgment. The cron model was excellent once I found the served page: a declared schedule invokes a public action, which invokes a durable mutation, and the operator ledger showed an autonomous succeeded run. That is more explicit than a Firebase scheduled function and more application-cohesive than wiring an external scheduler to Express. Period identity, zero suppression, and replay suppression remained ordinary stored invariants. At the same time, read-only analytical handlers had to masquerade as mutations with a declared table they did not write, because the explicit JavaScript mutation contract rejected an empty write set. Supabase SQL or a Postgres view would be materially simpler for six totals, seven buckets, and top-ten ranking.

The three-context browser proof exposed the least mature edge. Two independently authenticated Alice contexts repeatedly triggered `SNAPBACK_CLIENT_AUTH_COMMIT_REENTRANT`; an authenticated custom projection could return instantly through the headless client yet never settle in one React provider. Getting to green required bounded table-native projections, retained snapshots, optimistic sender state, atomic receipt facts, and idempotent retry. Convex and Firebase have had much longer to harden same-user multi-tab behavior, and a hand-rolled HTTP client would at least make the failed request directly observable. Snapback did provide a precise error code, but not a causal trace or prescribed recovery boundary. The explicit profile made the workaround's security surface impossible to ignore, which is valuable, but I would not want every product team inventing that recovery path.

So my final qualitative view is more differentiated than it was after M6. I liked authoring durable invariants, exact generated references, typed assets, and cron jobs on Snapback. I disliked fighting client custody coordination and having no SQL-grade aggregate path. The backend feels promising and unusually principled, but this run crossed enough sharp edges that I would currently adopt it for a team willing to co-design with the platform, not for a deadline-sensitive social product expecting mature multi-tab and offline behavior out of the box.

The scale replay made the operational contrast sharper. Snapback's published ordered runner was far better than the custom client loop I began with: it bounded the actor pool, preserved ordered terminal receipts, projected settled identifiers into later actions, and resumed exactly across lifecycle rotations. That is a strong primitive, closer to a purpose-built event-ingestion protocol than anything bundled with Firebase or Supabase. Yet the earlier adapter's lost custody acknowledgements permanently saturated a global 10,000-record mutation ledger. Even custody-free, application-idempotent replay could continue only because Clique's explicit write model already had stable external IDs or set-state mutation IDs; ordinary mutation-backed probes stayed blocked. Postgres would offer lower-level repair tools, while a managed platform should offer a safe authority-recovery or ledger-compaction path.

The workload itself remained semantically sound: all actions through the retained prefix settled, and both reached invariant checkpoints matched the frozen manifest. Throughput was simply too low to finish within four hours. That result leaves my qualitative preference intact but less enthusiastic. The system's contracts and diagnostics are unusually thoughtful, and I enjoyed the explicit backend when authoring correctness. I enjoyed it much less when diagnosing custody state that was durable, global, and intentionally opaque. Snapback is strongest today as a correctness framework; it still needs equally mature operational escape hatches before I would prefer it to established managed backends for a high-volume social workload.
