# Building Clique on the published Snapback 4 surface

This build changed where I spent engineering effort. I wrote a social feed, private messaging, media handling, offline behavior, and reporting in one continuous session. The most useful part of Snapback was that authorization, replication, expiry, and ordinary writes shared one model. The hardest part was learning to express that model precisely enough that the compiler could prove what would run on a device. This was a cold build from the published package, not a continuation of an earlier application. I did not inspect earlier Snapback implementations or competitor implementations. My comparisons below are architectural judgments based on general familiarity, not results from equivalent timed builds of those products.

The first benefit appeared in messaging. A conversation membership rule could govern both access to server data and which rows arrived on a device. That removed an entire category of coordination code that I would normally expect to write around a database, an API, and a subscription channel. The distinction between retaining previously delivered history and admitting new deliveries was explicit. A removed member could keep history already delivered while losing access to future messages. This is a product policy that can become scattered across SQL policies, socket subscription filters, client caches, and object-storage signing code. Here, much of it stayed near the table declaration.

The asset model was similarly consequential. Normal photos and videos were uploaded through the client and referenced by authorized rows. Deleting media from a message revoked subsequent server reads. View-once photos used a separate once asset field and explicit user-triggered fetching, so the application did not accidentally consume them while rendering previews. Server expiry was a declaration, not a timer in an open chat window. I verified expiry after closing the clients and waiting on real time, including the loss of history, search results, and asset access. That experience is materially different from merely hiding an old message in React. It moved the central correctness obligation into a place the backend could enforce.

Offline writes provided the clearest reduction in application code. The app used the published local client and its web or native device arm rather than inventing a second mutation language. Predicted rows carried pending state; durable admission kept intent IDs and arguments through a restart; reconnect handled ordered submission. The two-device choreography demonstrated that independent offline messages converged without duplicates and continued through normal receipt states. I also tested a production web shell reload while offline. The queued message reappeared as pending and later settled. These are useful observations, but they should not be inflated into simulator proof: the native deliverables were Hermes exports, as the environment permitted.

In the database-plus-API systems I know, I would normally build or choose another subsystem for that offline contract. With Supabase, the PostgreSQL foundation would make aggregates, migrations, and administrative inspection familiar, while I would expect to coordinate row-level security, storage authorization, realtime delivery, and an offline queue. That is not an assertion that such an application cannot be built cleanly there. It is a statement about where the integration burden usually lands. In this run, Snapback made many of those pieces one authoring problem. The price was less freedom to write an arbitrary loop and deal with its cost later.

Convex is the closer conceptual comparison for reactive application development. Typed functions and reactive queries are a comfortable way to make a UI follow authoritative state. I associate that approach with short feedback loops and ordinary TypeScript control flow. Quarry was less immediately improvisable. I had to learn its bounded scans, authorization prefixes, shapes, helper return rules, and residency diagnostics. The compiler sometimes told me that a query was incomplete or that a mutation would queue without a predicted row. Those messages interrupted authoring, but they exposed issues that a more permissive stack could leave latent until an offline interaction or a large dataset exercised them.

One small mistake captures that tradeoff. I initially read the sender profile inside a presence-conditioned push arm. The compiler stopped treating the send as predictable because the guard now controlled a potentially fallible read. Moving the profile lookup outside the guard left presence responsible only for emitting the effect, and prediction returned. This was useful feedback about the shape of the computation, not just its syntax. It also required understanding a rule that was unfamiliar at the start of the build. The published guide explained the intended form and the presence grace interval, so I could correct the application without examining implementation source.

The feed was where backend design mattered more than ordinary CRUD. I used the published feed recipe, which separates ordinary recipient fan-out from shared delivery for popular authors. That generated substrate was not hand-authored application code, and it should not be counted as such. It saved design time while making the delivery strategy visible enough to integrate with Clique's own posts, likes, and replies. The scale replay then exercised the actual authenticated write paths, including uploads and all action verbs. Its checkpoints checked stored counts and public API behavior rather than trusting that the replay loop had reached its final line. The hidden scored performance probes were unavailable, so my measurements remain unscored evidence rather than a claimed benchmark score.

Reporting fit the declarative model well. Maintained counts supplied lifetime totals and UTC daily buckets without paging the corpus into the client. The trending recipe indexed like counts into hour lanes and applied an exact trailing-day filter. This avoided an application-level full scan and sort. Adding the facts needed by that index still required a real backfill for existing records. There was no escape from migration thinking simply because the schema language was compact. I also hit a database-lock error when I started a post-replay backfill concurrently with schema adoption. That was a sequencing error in my tooling; retrying after startup was the appropriate correction.

The daily digest exposed another valuable boundary. A scheduled job, durable contribution rows, and a per-user period marker made the work independent of connected clients. An initial per-membership count still exceeded the 16 MiB heap ceiling in a busy chat at full scale. Narrowing the projection did not fix it. I changed the job to sweep individual period messages, accumulating per-chat totals with per-message idempotency markers. The published guide explicitly warned that a busy single chat needs message paging; I had not taken that warning far enough in the first implementation. The isolated proof restarted the backend during a period, checked exact payloads, reran the same period, and waited through a quiet following period. The effect queue served as the durable push seam, with a small worker adapter available for logging or provider integration. Real APNs or FCM delivery was not part of this proof. Provider idempotency remains something an integration must honor even when effect admission is atomic.

Compared with a traditional Express and PostgreSQL implementation, this backend had less glue and more constraints. Express would let me write nearly any query shape immediately, but I would own pagination correctness, transaction boundaries, websocket policy, cache invalidation, upload grants, scheduled work, and durable client retries. Quarry made some of those obligations declarations and made other obligations compiler-visible. The result felt particularly well matched to a messaging application whose difficult behavior lies between the server and a disconnected device. It felt less familiar when I wanted a quick diagnostic query or a one-off shape transformation.

I cannot make a measured comparison with earlier Snapback generations from this session. Their source and previous runs were deliberately outside the evidence boundary. What I can say is that the installed generation exposed an unusually broad published surface: guide cards, diagnostics, generated types, feed recipes, replica clients, assets, effects, and scheduling. I did not encounter a confirmed platform defect that forced a scoped feature to be removed. Several failures were plainly mine: invalid write-ID formatting, overly broad source replacement, a ranking test that assumed earlier test likes would not change its fixture, and navigation that did not match a frozen choreography route. Metro also served stale development transforms, requiring explicit restarts. These should not be blended into a claim that the backend was unreliable.

The experience leaves me with a qualified positive judgment. Snapback reduced friction where the application needed one coherent answer to authorization, local state, durable intent, and revocation. It added friction where the compiler required proof of bounded work or where I had to learn a new authoring construct. The published examples were most valuable when they explained the reason for a pattern, especially prediction, feed delivery, and digest chunking. For this application, those constraints changed the implementation toward explicit delivery and cost models early enough to test them. The remaining uncertainty is operational: a successful local scale replay and bundle export are strong development evidence, but they are not a production deployment, provider qualification, or native simulator run.
