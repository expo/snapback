# Building Clique with Snapback 4

This was a cold build of a social feed and private messenger through the full continuous milestone sequence. I used the pinned public packages, their published reference material, CLI guide cards, diagnostics and generated API. I did not inspect a Snapback source checkout or another implementation. The comparisons below are engineering judgments based on this build and my general knowledge of other backend approaches, not a controlled implementation of the same app on each alternative. In particular, I have no direct earlier-generation Snapback run in this session from which to claim a measured improvement.

The most consequential choice in Snapback was making the device a host for the backend's model. I authored message reads, membership rules, mutations, expiry and search in Quarry, then connected the Expo screens to the replica client. The client did not need a second handwritten model of which messages belong to a conversation, how to predict a send, or which indexed search should run offline. That changed the work more than any individual API convenience. The application still had plenty of UI and protocol details, but a large category of reconciliation code never became an application file.

Messaging showed the benefit clearly. Sending a message captures its recipient memberships and advances a server arrival ordinal. Delivery and read watermarks are monotonic per membership, and the same account's devices observe the same state. While disconnected, the local client admits a durable intent and can render its predicted row with a pending marker. Reconnection settles the intent through the server. The browser proof went further than leaving a tab open: it reloaded while offline and found both the queued message and saved search results. That outcome relied on the SDK's durable outbox and interpreter, while the application supplied its own cached HTML and JavaScript shell. The division of responsibility was sensible, but easy to miss without reading the full client reference.

Convex is the closest comparison in the ordinary screen-authoring loop. Typed functions, authenticated queries and reactive UI bindings encourage a similarly direct path from backend operation to component. In a Convex-shaped design I would expect much of the online live-update work to feel familiar. The larger difference here was the offline requirement: prediction and indexed reads ran against the acquired device partition under the authored model. I did not have to approximate that model in a separate JavaScript cache. This is not a claim about every current Convex integration or offline library; it is the architectural advantage I actually used in this build.

Supabase would have offered a familiar relational foundation: tables, indexes, constraints, row-level policies, storage and application functions. Its SQL flexibility would be attractive for reporting and ad hoc inspection. I would expect more separate moving pieces to satisfy this particular brief's offline behavior: a local database, an outbox, receipt reconciliation, storage invalidation and a way to keep local search behavior aligned with server search. Snapback let the schema declarations and sync audience carry much of that relationship. The tradeoff was giving up the open-ended expressiveness of SQL for a deliberately bounded language. Quarry wanted explicit indexes, bounded pages, known audiences and typed helper parameters. That was useful pressure, but it was pressure.

The media lifecycle was another strong point. Uploads returned server-validated references, ordinary viewed media could be retained by the SDK, and view-once assets had a distinct server-enforced consumption rule. Expiring a message made it absent to reads and ultimately revoked its asset access without an open client doing cleanup. The closed-client disappearing-message choreography passed. The view-once test also checked an actual second server fetch, rather than trusting an opened badge in the interface. With a generic object store and database, those features usually demand careful coordination between application rows, signed URLs, client caches and deletion jobs. Here the relationship between the row and its media was part of the backend surface.

That did not make application mistakes disappear. I initially treated a newly uploaded asset as interchangeable with the reference from an earlier replay attempt. Reusing the same mutation ID with that different reference was correctly refused. The fix was to persist upload receipts and settled actions as separate replay state. I also confused globally named effects with module-qualified operations when wiring the provider worker. These were my mistakes, not demonstrated platform defects. The diagnostics made the fixes concrete, although the naming distinction was easier to overlook than I would like in a first encounter.

The published guide was unusually valuable when it explained semantics rather than merely listing syntax. The details about held search, acquisition, session rotation, cache revocation, presence grace and schedule admission affected real implementation decisions. Generated types caught the shape of the client contract, and the compiler pointed directly at invalid declarations. On the other hand, discovering the full practical surface required moving among the README, client reference, keyword cards and generated API. A reader who stopped after the starter example could easily build an online app and mistakenly believe that installing the local client alone had solved cold-offline startup. The shell still belonged to me, and I had to verify it.

Reporting and scheduled work made the backend feel more database-like. Maintained totals and UTC calendar buckets gave Insights bounded server reads without transferring the post corpus to the client. Trending used a like-ranked table updated through the authored mutations and an expiry deadline tied to post time, so on-load ranking could be immediate rather than waiting for a periodic rescore. The digest used server-owned sweeps and a persisted period ledger, then emitted through the same provider seam as message notifications. Its proof closed the clients, restarted the backend mid-period, checked authorization and deduplication, and observed a following quiet period. The useful simplification was not just having a scheduler: it was keeping its writes, progress and emitted effects within the same backend execution model.

A more general backend would give me more ways to implement those reports, and sometimes that freedom would be faster. Quarry's bounds make it important to distinguish a page, an exact total and an incomplete answer. I had to think about which operations should use maintained data and which could safely walk a bounded group. That is a different development rhythm from writing an unrestricted SQL aggregate and later examining its query plan. It front-loads some design work. It also gives a natural explanation for why a query cannot be treated as complete, which is preferable to silently returning a plausible subset.

The UI work remained ordinary product engineering. A fixed component kit reduced visual decision-making, but it did not choose navigation, pagination, receipt semantics or when to mount a media player. Choreography exposed problems that compilation could not: a lazy startup chunk blocked an offline transition, an inline video appeared too late for the intended interaction, and the home screen lacked the chat rows needed to demonstrate cross-device unread state. A later directory improvement hid an expected member behind a first-page boundary. These were useful reminders that backend ergonomics do not substitute for testing the whole path a person takes through an application.

Compared with earlier Snapback generations, the defensible observation is about the surface available here. This release exposed an integrated Quarry schema, local and native client arms, asset lifetimes, word indexes, maintained calendar aggregates, jobs, presence-aware effects and a replay mode through the published package. I could use those facilities without borrowing a prior checkout or inferring that an older limitation still applied. I cannot honestly turn that into a numerical historical comparison. The larger conceptual contrast is with approaches where a server framework gains offline behavior through an additional client-side layer: here the device interpreter is central to the design.

The remaining tradeoff is operational and structural, not just syntactic. Public replication and retained chat history make local reads straightforward, but acquisition has a real byte and row cost. The scale replay therefore matters independently of small-fixture correctness. I have kept its clock, exact invariant audit, API paging checks and unscored measurements separate from milestone completion; hidden scored probes remain the grader's work. My overall judgment is that Snapback reduced friction most where authorization, offline state and lifecycle rules would otherwise have been duplicated. It added friction where a general-purpose language or SQL would have let me improvise. For this application, that constraint was often productive: it kept the hard behavior close to the data, while leaving the interaction mistakes visibly mine to fix.

The completed fresh-instance replay matched its invariant manifest at both checkpoints and at the final corpus, including the fully paged busy conversation and named media, reaction and quote checks. Cold acquisition also completed at the full corpus. That supports the correctness of this implementation at the supplied envelope; it does not substitute for the grader’s hidden performance or trust-boundary probes.
