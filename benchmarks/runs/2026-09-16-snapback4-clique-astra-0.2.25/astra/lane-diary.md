## M1 — Accounts and profiles
Built built-in password identity, persistent web and secure native sessions, live public profiles, unique handles, six-field editing and avatar upload. The schema and generated operations were straightforward; the web replica opened and streamed profile edits without custom subscription plumbing. The first suite and browser segment passed. The Expo starter also exported Hermes successfully. The environment fought more than the backend: PATH differed from the Node overlay, copied fixtures retained read-only permissions, and choreography lacked its shared JSON-schema module. The lane supplies real AJV validation for that omitted dependency and discloses the repair. Prior familiarity with React/Expo and browser automation saved time; no prior Snapback implementation was consulted. Compared with Convex this moves rules and shape validation into one compact language; compared with Supabase it avoided separate identity, RLS and realtime wiring. The long published reference is substantial orientation work, but the needed primitives were documented.
## M2 — Posts and follow graph
Built text, image and video posts, profiles with follow counts, likes, attributed reposts, chronological direct replies and 20-entry feeds. Used the published prefixed feed recipe with application media joins; expanded backfill to its declared full author cap. The suite and isolated choreography passed, with a Hermes bundle. Maintains made counters easy and the typed-reference diagnostic correctly identified my mistaken repost bridge. The difficult parts were client composition: an RN-only image helper crashed the web export, and choreography expected feed navigation from profiles. Both were my errors. A further verification mistake ran write-heavy acceptance alongside choreography and displaced its retained witness; isolated rerun passed. Familiarity with feed models helped understand the recipe, but its full public card replication has a meaningful cold-sync cost to measure later. Convex or SQL would express more flexible read joins; this platform instead exposes the local acquisition tradeoff and supplies a reusable fan-out recipe. No source checkout or previous implementation was consulted.
## M3 — Messaging core
Built unique DMs, distinct groups, admin membership management, full retained delivered history, message paging, quoted replies, expiring typing indicators and monotonic receipts over the send-time membership instances. All suite and choreography checks passed after fixing one client startup race; Hermes exported. Quarry accepted the first messaging schema, including the sorted pair key, capped roster iteration and private sync audience. The receipt model was easier than manually maintaining subscriptions in Supabase, though still application logic rather than a messaging primitive. A failing delivered-state check initially looked like sync trouble; a focused browser reproduction showed my lazy web-device import failed during reload plus immediate connectivity loss. A platform-specific static import fixed it. The docs' retained-history caveat mattered: history has no membership require, so devices can answer from previously delivered rows after removal while the server refuses further content. React/Expo experience helped diagnose the bundler issue. No missing backend capability identified at this milestone.
## M4 — Media, reactions, edit/delete
Built inline photo and video messages, native video playback, arbitrary emoji reactions, caption/text edits and delete tombstones with asset clearing. Window constants are generated from the fixture config and compared only to server time. All suite/choreography checks and Hermes export passed. The backend additions were direct: image/video columns own their asset authorization, and clearing the home column refused the recipient's next fetch without a separate storage ACL. The two correction loops were mine: the suite read before a predicted write settled, and the video player mounted only after its URL arrived, causing the harness to take its alternate viewer path. Compared with an object-storage-plus-SQL stack, asset placement and revocation reduced integration work considerably. The kit is intentionally presentational, so genuine video playback still needed app composition. Generated types caught my wrong reaction callback prop before runtime. No platform capability gap identified.

## M5
Built server-expiring text/media, view-once assets with an ephemeral viewer, shared accent/background settings, and indexed scoped/held search. Expiry and once semantics were unusually direct declarations, including cache revocation. JSX callback syntax fought me briefly; TypeScript caught it. Familiarity with React helped the UI, but I used the published guide for Quarry search and lifecycle semantics. The docs supplied concrete offline/expiry guarantees. Compared with SQL plus a custom cache, this eliminated substantial invalidation code; compared with Convex, the held search ran on the same authored query without a parallel client index. Suite and all implemented choreography checks passed, including no-client expiry.

## M6
Built a durable offline web shell around the replica, transactionally emitted push payloads with a logged idempotent provider, a documented headless API and demo, and the full replay adapter with checkpoint verification. The offline queue itself was already supplied by the local client; reload with a pending write and cold search passed. The worker effect name and stable upload retry identity caused two correction loops. Prior experience with idempotent APIs helped separate application IDs, write IDs, and upload receipts. Published docs explained these distinctions, though global effect naming was easy to confuse with module operation names. Compared with Supabase or a hand-built API, replica persistence saved significant plumbing; the headless path remained a normal small SDK client. Full-scale execution is still pending on its separate clock after M8. Suite, choreography, and Hermes export passed.

## M8
Built six maintained lifetime totals, seven UTC daily buckets, exact like-ranked 24-hour Trending, the two-minute scheduled digest, and deeper multi-device/offline checks. Aggregates and schedule cursors made the server model compact. The digest proof closed every proof client, restarted the backend mid-period, checked authorized counts and exactly-once emission, and observed no new payload in the next quiet period. UI choreography exposed a missing home inbox surface and a pagination regression in member selection; both were corrected, with M3 rerun green. Familiarity with indexed rank tables and idempotent jobs helped, but Quarry's maintained calendar groups and resumable sweeps supplied the mechanics. Compared with Convex's reactive-function approach this felt more declarative and constrained; compared with Supabase it avoided triggers plus a separate local reconciliation layer. Full public replica acquisition remains a deliberate cost to measure at scale. The suite, M8 choreography, membership regression, digest proof and Hermes export all passed.
