# Building Clique on the published Snapback 4 surface

This was a cold build using the published Snapback 4 package, its README and guide cards, diagnostics, and generated types. I did not consult another Snapback checkout or an earlier Clique implementation. My comparisons below describe architectural differences and prior general knowledge of other backends; they are not controlled measurements of those systems, and they do not imply that I implemented this application on them during this run. I wrote this account after the M8 boundary, before tallying the final numbers. The separate scale replay is still in progress, so its result does not inform the judgments here.

The strongest part of the experience was the continuity between the backend model and the local application. A chat message, its membership visibility, its retained history, its expiry, and its sync audience can be described together in Quarry. That made several difficult product obligations feel like variations of the same modeling task. The application still had plenty of state to manage—composers, navigation, media viewers, pending indicators—but I did not have to invent a second persistence protocol for every optimistic interaction. Once the membership and message model was correct, the local client could execute the same operations and reconcile them with server authority.

This changes where engineering effort goes. In a conventional Supabase application, I would expect to spend more time coordinating Postgres policies, realtime subscriptions, local SQLite or IndexedDB, an outbox, conflict behavior, and asset access. Postgres gives very mature tools and an exceptionally broad query language, but those tools do not by themselves settle the complete offline lifecycle. Convex offers a cohesive reactive backend and a comfortable TypeScript authoring environment; for the deeper offline requirements here I would still need to be explicit about durable client storage and replay. Snapback made that local durability part of the installed client surface. The extra web proof was useful: two queued messages survived an offline reload and later flushed in order. That is actual web evidence, not a substitute for native evidence. Producing an iOS Hermes bundle only establishes that the native dependency graph bundles successfully.

Quarry was simultaneously the main simplification and the main learning cost. A small declaration such as an expiry field or a maintained count replaces quite a lot of incidental code. Rules live close to the data, and a generated API connects their operation names and argument types to the client. But ordinary-looking values have distinctions that matter: an identifier referring to a post is not interchangeable with an identifier referring to a ranking row. I initially used one where the other was required. The compiler's diagnostic led me to a unique post-reference index, which expressed the relationship more accurately. In TypeScript backed by a permissive JSON API, that mistake might instead become a runtime bug or an implicit convention nobody checks.

The bounded-work model also demands a different habit. My first push implementation iterated an accumulated recipient list. The compiler refused it because the list no longer preserved the provenance of one complete, bounded membership page. Moving the effect branch into the original membership-page loop resolved the refusal. This was useful feedback, although it interrupted a pattern that would be routine in general-purpose application code. The cost is not just learning syntax. The author must learn which operations preserve completeness, which reads can predict, and where a page is only a page rather than a complete set. Those are worthwhile concerns in any distributed application, but Snapback puts them directly in the authoring loop.

The generated feed recipe saved substantial design work. Following feeds are not a simple global query with an author filter at the required envelope: fan-out, celebrity routing, ordering, repost identity, and removal all matter. Starting from the published recipe gave those concerns a coherent structure and explicit capacities. I still had to connect product cards, reaction state, profiles, and the fixture's idempotent actions. The recipe did not make the whole social product automatic. It did reduce the likelihood that a superficially working small dataset would hide a completely different scale strategy. Whether this implementation meets the full envelope remains a question for the separately recorded replay and its verification, rather than something a recipe alone proves.

Media illustrated the value of backend-owned semantics particularly clearly. Ordinary uploads, authorization, once-only retrieval, and expiry were available through one asset model. I did not build a bespoke signed-URL issuance service or a separate garbage-collection policy to make the initial product behavior work. Nevertheless, the client had responsibilities the backend could not discharge: a view-once viewer must revoke its object URL on close, the UI needs to remember that it has been opened, video needs an actual playable rendering path, and deleted content must stop rendering. An integrated platform reduces glue; it does not remove the need to inspect the complete user-visible lifecycle.

The reporting milestone exposed a different strength. Six totals and seven UTC day buckets were natural maintained aggregates. That is much clearer than paging a user's entire corpus in the browser, and it makes the performance intent visible in the backend. Trending was more involved because the requirement is a rolling interval, not a calendar-day bucket, and ranking must reflect current likes. I used explicit ranking rows with an expiry time and updated their score in the like mutation. This is a read model, comparable in spirit to a Postgres projection table or a Convex materialized counter. Snapback supplied expiry and indexing, while the application supplied the relationship and its update discipline.

The digest combined scheduled execution, authorization, aggregation, and effects. A scheduled Quarry job computes each user's period, records the durable emission boundary, and emits through the same provider seam as ordinary message notifications. A separate proof instance demonstrated that this runs with no client open, tolerates a mid-period restart, excludes a foreign chat, and remains silent in the next inactive period. This is more cohesive than wiring a scheduler, a database query service, and a push queue independently. It still needs operational judgment: a bounded job must be checked against the largest relevant memberships and message ranges, and a logged provider seam is not an APNs or FCM deployment. Real push delivery was outside this brief.

The frozen harness was an important source of product feedback, but it also introduced assumptions that were independent of the backend. One check expected chat rows on the application's home route. My original home route was a feed with a separate Chats screen; I added an inbox alongside the feed. Several failed suite attempts were my own mistakes: navigating before authentication settled, observing a predicted message before the server receipt, using a stale display-name assumption, or checking the wrong test identifier. Those failures belong to the implementation and verification process, not to a platform-defect count. Keeping diagnostic evidence separate from conclusions made that distinction easier to preserve.

I cannot responsibly turn this into a version-by-version claim about earlier Snapback generations. I did not read or run them here. The observable characteristic of this release is that schema, rules, sync, mutations, expiry, maintained aggregates, jobs, and effects form one authored backend, with a generated client surface and local execution. Compared with systems where those concerns live in separate libraries and services, that consolidation clearly changed the shape of the work. The remaining friction came from learning its completeness and reference rules, choosing correct read models, and verifying the real product lifecycle. For an application whose hardest requirements are authorization plus offline continuity, that is a promising trade. For workloads needing unrestricted SQL exploration or broad ecosystem integrations, the narrower language and runtime would deserve their own evaluation rather than an assumption that this successful path generalizes.
