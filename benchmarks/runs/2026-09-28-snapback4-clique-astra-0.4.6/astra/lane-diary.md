The suite and all four implemented frozen choreography checks passed. A separate pair of isolated users closed every client for 182 real seconds; the server then refused the message, both clients purged on reopen, and offline search excluded it. The iOS Hermes export is retained.

Expiry felt unusually direct: one nullable deadline and an `expire at` clause cover server reads, replicas, assets, and search. The `once` asset column likewise removed the need to invent signed URLs and consumption races. What fought me was my own adapter assumption that every send returned the same shape, and my initial interpretation of the uploader's one-view allowance. Generated types and a direct fetch test corrected both; neither is evidence of a platform defect. I also initially sent an empty optional URL in the isolation probe, correctly rejected by validation.

Prior React and browser media familiarity helped with owning the transient handle above a paginated list and cancelling late fetch results. The distinction between a complete server search and a retained device horizon required explicit UI text and separate held queries. The compiler warned that the time-ordered search and ordinal-ordered sync windows differ; I kept the promised search ordering and disclosed incomplete offline coverage. No missing M5 capability was established. Compared with a conventional Supabase implementation, substantially less authorization and cache-expiry glue was needed. Compared with Convex's reactive queries, the durable local search is a useful addition, with a larger coverage vocabulary to learn. These comparisons are conceptual familiarity, not parallel measurements.

## M6 — Durable writes, notification seam, custom API, replay adapter

Built the provider seam as a Quarry effect and a logged service worker, a token-only HTTP demo and complete message-field API documentation, durable queue recovery UI from SDK pending-write custody, offline likes/reactions, and the full action-log adapter. The frozen 50-action validator and actual-state verification pass. The suite also reloads the browser while offline, recovers two pending messages, retains ordinary media, refuses previously opened one-view media, searches locally, and flushes messages, a reaction, and a like. The matching choreography and iOS Hermes export pass. Full scale execution is deliberately after M8 so its two checkpoints include Insights and Trending; the adapter, verifier, and sequential probe runner were authored here.

Durable mutation custody was easy to reuse; there is no application resend loop. Exposing pending writes even when prediction is impossible was essential. The native online-fallback journal uses SQLite for large arguments while credentials remain in SecureStore. The generated types caught my initial async-versus-sync storage adapter mistake. Other self-inflicted errors were the raw HTTP query envelope, a hardcoded original display name after choreography had edited it, and treating pending as a receipt enum rather than the kit's separate flag.

The difficult part was negative knowledge offline. A bounded raw likes/reposts window could not answer missing compound keys, so it withheld the entire composed post card even on an acquired device. A standalone process-replica probe isolated this from UI state and pending writes. Fully synced maintained summaries over the already-public interaction sources fixed the reads. I tried narrowing those aggregate audiences; the compiler correctly explained that maintains inherit their source's sync and rejected mismatched public delivery. Keeping public summary semantics adds replica rows, a cost the scale cold-sync probe will expose. This is an authoring tradeoff, not an established missing requirement.

Prior protocol and idempotency experience saved time on the adapter: each action waits for a real receipt, timestamps are never backdated, media is uploaded, and verification reads actual state independently. Compared with Supabase, the transactionally admitted effect and replica custody avoid substantial custom plumbing. Compared with Convex, the API is straightforward but its HTTP envelope and optional historical results need precise documentation. Earlier offline systems I know often obscure whether absence is known; this backend is more explicit, at the cost of more query-shape decisions. No source or historical benchmark implementation informed those comparisons.
