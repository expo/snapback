# Building Clique on the published Snapback 4 surface

This essay is written after the final M8 acceptance boundary and before the final quantitative tally. The full scale replay has started on an empty instance; its results are deliberately not assumed here. My evidence is this cold build, its published package documentation, diagnostics, generated types, and the tests I ran. Comparisons with Convex, Supabase, and other systems are conceptual engineering judgments from general familiarity, not matched implementations or measured rankings. I did not inspect another lane, an earlier Clique implementation, or any Snapback source checkout.

The most consequential feature of this backend was the concentration of responsibility. Quarry held the schema, authorization, synchronization, retention, mutations, queries, expiry, effects, and schedules. That changed the work from assembling several services into making a coherent data contract. A disappearing message could carry a deadline and an expiry clause that also governed reads, replicas, search, and assets. A view-once image could be a distinct asset type. Those declarations displaced substantial glue that I would otherwise expect around storage URLs, object deletion, background workers, cache invalidation, and client reconciliation.

That concentration did not make the application automatic. The difficult part was often understanding when the client had enough information to render a truthful answer. An acquired replica is not synonymous with complete knowledge of every relation. The distinction surfaced sharply when a bounded likes window could not prove that a particular compound key was absent. A composed post query consequently remained incomplete offline. Fully synchronized maintained summaries over public interaction data resolved it, but that choice has a replica cost. The useful lesson was that synchronization design is part of query design, and both are product decisions.

## What reduced work

Authentication, typed assets, generated client operations, and maintained counts were productive foundations. I could express unique handles, canonical direct-message pairs, one reaction per person per message, and monotonic conversation ordinals directly. Feed totals did not require a separate web of application counter updates. The compiler's cost and residency feedback gave me actionable information while authoring queries rather than leaving every concern to a production profiler. Generated types caught real adapter mistakes, including differing mutation return shapes and synchronous native storage expectations.

Media was the strongest example of reduced cross-layer work. Image and video size/type constraints belonged beside the data that referenced them. Duration validation used server facts. Tombstones removed media references, and authorization could then refuse fetches. One-view photos required careful ownership of transient handles in React, but I did not implement a separate consumption ledger or signed-URL race. Server expiry worked with every application client closed; that test is more meaningful than a disappearing bubble driven only by a browser timer.

The durable write boundary also mattered. The application did not invent a retry queue. It displayed SDK-owned pending intents, recovered them after a browser reload, and let the platform settle them. A mutation can be durably accepted without being locally predictable. Once I treated those as separate states, the UI could show honest pending rows even when an online-only effect prevented prediction. That is a more useful contract than optimistic rendering that silently assumes every server action is reproducible locally.

The notification seam and digest benefited from the same ownership. A transaction admitted a deduplicated effect, and a service worker delivered it to a local log. The digest used server time and a schedule, with shortened configuration for testing. Exact count checks, absence of empty deliveries, and restart behavior were all testable without adding application cron state. This run demonstrates the provider seam, not an APNS or FCM deployment.

## What added work

The largest source of rework was my React lifecycle handling. I initially let transient query loading unmount a conversation route and its composer. I also mixed paginated content with a page-wide scroll container, split related caller state across reads, and treated auxiliary profile or quote loading as if it should hide the main content. Those are agent mistakes, not evidence that the backend cannot express messaging. Nevertheless, the backend's explicit local coverage and revalidation states made those mistakes more visible and demanded more careful ownership than a simple request-response screen.

Receipts were another substantial piece of application reasoning. Delivered state depends on what the device actually holds, not merely on a live subscription being open. Read state depends on visibility and a monotonic watermark. Retained history after membership removal must coexist with refusal of new messages and current media authorization. The published receipt recipe saved design effort, but an index prefix and an equivalent-looking filter had different local coverage consequences. Reading the guide and inspecting a standalone process replica was more effective than adding retries to a screen whose data contract I had misunderstood.

Typing exposed a different boundary: ephemeral online hints should not become durable offline work. I used the package's online arm for both typing reads and writes, while messages remained on the replica arm. This is a reasonable split, but it belongs in a practical application recipe because a developer can otherwise accidentally inherit durable semantics for data that should disappear.

Diagnostics were generally precise. Rejected query bounds, inherited aggregate synchronization policy, and invalid optional values led to concrete corrections. The challenge was integrating many small contracts: historical optional results, HTTP envelopes, maintained-view audiences, held queries, and asset-handle lifetimes. A single polished social application example would reduce that discovery cost. I found no established expressibility gap for the requested milestones, but that is a narrower claim than saying the documentation made every correct design obvious.

## Comparison with other backends

Convex is the closest conceptual comparison for reactive queries, transactional application operations, scheduled work, and typed client calls. Those ideas are familiar and reduce the distance between a product action and its backend implementation. Snapback moves more local-replica and asset semantics into the authored data model. In this build, that avoided inventing offline persistence and reconciliation, but it also required learning coverage, retention, and prediction as first-class concepts. I would not infer a performance or productivity ranking from this one run. The important difference is where the complexity lives: in explicit contracts here, versus additional client architecture when an application needs comparable offline behavior on a conventional reactive server.

Supabase offers a familiar relational foundation and a broad ecosystem around SQL, authorization, storage, authentication, and realtime delivery. A team with established PostgreSQL practices may value that transparency and operational familiarity. For this particular brief, however, a conventional Supabase implementation would still need to coordinate local storage, outbox recovery, delivery intervals, asset consumption, expiry propagation, and notification effects. Those are feasible engineering tasks; the advantage I experienced here was having several of their guarantees participate in one model. The corresponding cost is dependence on Quarry's authoring and diagnostic surface rather than the much wider SQL toolchain.

Compared with a custom PostgreSQL service or a document database plus a local cache, this backend offered fewer seams to get subtly out of sync. That did not eliminate the need for an independent replay verifier or real browser tests. A replay adapter that waits for settled writes, uploads actual media, and verifies actual state is still necessary. Compiler acceptance cannot prove that a screen preserves a draft, that a removed member loses access at the right moment, or that two offline devices converge in the order the product promises.

I cannot make an empirical comparison with earlier Snapback generations from this session. I intentionally did not read their source, examples, diaries, or results, and I will not project remembered limitations onto this release. The defensible observation is that this published generation exposes a unified Quarry backend and several client arms through one pinned package family. Any claim that it improved a specific older failure requires a separately controlled historical comparison. General familiarity with earlier local-first designs helped me ask about durable custody and known absence; it did not supply an implementation to reuse.

The resulting application feels production-shaped because its important behaviors have explicit owners: the server owns time, authorization, expiry, and effect admission; the replica owns durable pending work and retained data; React owns drafts, navigation, visibility, and transient media handles. Most friction appeared when I blurred those boundaries. Snapback reduced infrastructure assembly and made guarantees easier to express, while adding a vocabulary that must be understood before the UI can use those guarantees correctly. The final report will distinguish completed proofs, scale observations, native build artifacts, and remaining evidence limitations rather than flattening them into a single score.
