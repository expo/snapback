# Building Clique with the published Snapback 4 surface

This run changed where the hard work lived. I built a social feed and messenger with profiles, ordinary and view-once media, membership authority, receipts, expiring messages, search, offline writes, insights, and scheduled digests. The backend remained Quarry declarations and operations. That removed a considerable amount of application plumbing, but it made the exact relationship between an authoritative answer, a local answer, a pending intent, and a mounted React component central to the work. The most persistent problems were at those boundaries.

These are observations from one cold build using the published 0.4.4 packages, their documentation, diagnostics, and generated API. I did not inspect another implementation or earlier Snapback source. My comparisons with Convex and Supabase draw on their familiar programming models, not a controlled implementation of this same brief on those products. They should not be read as current feature inventories or comparative performance results. In particular, I cannot substantiate a release-to-release improvement over earlier Snapback generations from this run.

The strongest part of the experience was keeping authority near the data. Conversation membership, sender ownership, edit and delete windows, immutable expiry times, and asset access were expressed in the backend. The client could ask to act without becoming the source of truth about whether the action was allowed. Once the shape was right, the same policy served the normal app, custom HTTP client, replay adapter, and independent probes. The no-client expiry proof was particularly valuable: closing every client and observing the server remove both the message and its accessible asset established something a countdown in the UI could not.

That differs from the work I would expect with a Postgres-centered Supabase design. SQL constraints, row-level security, triggers, scheduled work, and storage policies can provide strong authority, but I would need to keep their boundaries aligned and add an explicit client synchronization strategy. Here the schema, policy, synchronization audience, query, and asset relationship occupied one authored surface. The advantage was coherence. The cost was that Quarry is a specific language with specific admissible plans; SQL intuition helped with the goal but did not reliably supply the syntax or the execution model.

Compared with the TypeScript function model I associate with Convex, the restrictions were more visible. I could not casually turn a mutation into an arbitrary scan and loop. The compiler rejected structural fanout and explained when an operation could predict locally, when it would only enter durable custody, and when a read could be incomplete. This was useful pressure. It also meant that a superficially reasonable implementation often needed a different data shape. Delivery acknowledgements, for example, required bounded progress and explicit treatment of expired ordinal holes. A general-purpose function would feel more familiar initially, but would leave more of that boundedness argument to the author.

The guide and operation diagnostics were practical tools rather than incidental documentation. The receipt recipe saved real design effort, and I adapted it with attribution. The search correction illustrated why recipes matter: a query that compiled and returned correct results on the starter corpus later returned an incomplete empty global search on a larger corpus. The published scoped-search form already showed the right membership-lane shape. Moving to that form restored a complete page, and avoiding repeated group rosters reduced the response payload. This was my query-shape error, not proof of a missing search capability. It was also evidence that a compiler success is not a substitute for checking a meaningful result at scale.

Offline support reduced infrastructure work while expanding the UI state model. The public client owned durable pending writes and a replica, and cold browser tests could load history and execute a new local search. I did not build an IndexedDB command queue, write retry protocol, or a second hand-maintained cache of the backend. However, an admitted write did not always produce a predicted message row. The first UI treatment effectively equated those things and therefore failed to show a pending bubble. The pending-write hook was the proper way to expose custody independently. That distinction is a useful product concept: the app can truthfully say that a user's intent is safe without pretending the server has accepted its final row.

The same separation affected live rendering. Receipt changes and query replacement could briefly withdraw an answer, causing a composer, media viewer, or action menu to lose state if it lived under the affected row. I moved user interaction state to stable owners, kept appropriate public observations, and added a short, bounded history display buffer. That buffer holds presentation metadata while a replacement loads; it does not confer asset authority, advance receipts, survive a denial, or make an expired message live again. This was careful work that a declarative backend did not remove. A conventional React app with a different reactive backend could face related component-lifetime problems, but Snapback's answer lifecycle made them unusually prominent in this build.

Media was another place where the platform did more than a basic upload endpoint. Ordinary viewed media could remain available offline, while a view-once source stayed outside that cache and required an explicit server opening. Membership removal, deletion, expiry, and identity changes had to revoke the displayed source as well as affect the next request. Using the public asset arm let the app preserve those semantics without inventing its own signed-URL lifetime scheme. The remaining client work was substantial: previewing uploads, separating video posters from video bytes, keeping the viewer stable, and closing it on revocation. Expo's web video component also required a wrapper to expose the frozen observation ID; that was renderer integration work, not a backend defect.

The reporting features were comparatively straightforward. Maintained author-keyed aggregates supplied the lifetime totals and daily buckets without transferring the corpus to the browser. Trending was a bounded, ordered server query. The digest was a scheduled job with durable progress and an idempotent effect key. A real-clock test closed clients, restarted the backend during the period, and checked both the expected notification and silence in the next inactive period. In a Supabase design I would expect to choose among SQL aggregation, materialized data, and scheduled functions; in a function-oriented backend I would expect explicit counter maintenance and scheduled orchestration. Here those concerns were close enough together that the application code was compact and the proof could focus on semantics.

Operational documentation was less uniformly smooth. Minting the worker service token while the development store was open failed with the store-lock diagnostic, although the guide sequence suggested doing so after starting the service. Stopping, minting, and restarting worked. I recorded that discrepancy as ambiguous rather than inferring an underlying implementation defect. The published-package fence was otherwise workable: the compiler, generated types, guide cards, and public client APIs supplied enough information to complete the required product scope. I did not need a source checkout to get unstuck.

The replay adapter also imposed discipline that was useful beyond benchmarking. Every action used the application write path, preserved its intent ID, and waited for an authoritative settlement before continuing. Independent verification paged actual state instead of treating a count of HTTP requests as proof that content existed. The exploratory replay was intentionally stopped when search was wrong; its receipts remain separate from the fresh final attempt. That is more cumbersome than declaring a small demo complete, but it exposed a real correctness issue and prevented a fast empty response from being presented as good performance.

I would choose this approach with a clearer understanding of the trade. It substantially reduced the amount of custom authority, replica, asset, and durable-write infrastructure I had to own. In return, it required learning a constrained query language and treating local answer completeness and pending custody as first-class UI states. Familiarity with transactions, idempotency, pagination, SQL aggregates, and React state ownership transferred well. Familiarity with JavaScript alone would not have been enough. The earlier Snapback generations remain an unmeasured comparison here; the defensible conclusion concerns this published release and this run.

Finally, the evidence has boundaries. Every milestone produced an iOS Hermes export, but a bundle export is not a simulator or physical-device offline proof. The deeper restart and multi-device behavior was exercised in web browsers. The push seam is a durable provider hook with a logging provider, as the brief allows, not a live APNs deployment. The scale probes are local viability measurements and do not establish cross-backend speed or internet deployment latency. Those limits leave a production-shaped application and a substantial set of behavioral proofs, while still leaving real deployment, mobile runtime validation, and operational hardening for a subsequent engineering phase.
