# M7 diary

Built group polls as a real message type (question, 2–4 options, one changeable vote per member as an idempotent set-state intent with a client mutation id, live tallies, offline queue) and a backfilled visible-message count on every conversation, shown in chat settings. The count is a Snapback `maintain` grouped by conversation and tombstone flag; expired rows drop when the engine sweeps them; polls are rows in `messages`, so they count. Existing starter DMs and the Weekend Plans group survived the schema change with the same messages, media, receipts, and reactions as the pre-M7 custom-client snapshot.

What felt easy: once the Quarry compiled, `snapback4 dev` re-adopted the live in-memory store as generation 2 in 13 ms and classified the change Additive. The maintain rebuilt over the fifteen starter messages without a hand-written UPDATE. Live two-client tallies passed on the first choreography run. The kit already had PollCompose, PollDisplay, and the settings message-count slot, so the UI was wiring, not pixels.

What fought: the compiler. A poll-options sync horizon had to lead with `conversationId`, and optional option-three/four labels would not go into a non-optional column until they were narrowed. The online client's in-memory write queue *does* hold a vote while the link is down, but my first PollMessage implementation wiped options on `E_OFFLINE` and rebuilt the buttons every 300 ms, so Playwright could see `m7-option-b` and still never get a stable click. Choreography also refused to start on the host's Node 25 because setup-identity had pinned 24.18.0.

A migration on this backend, compared to the alternatives I know: there is no numbered SQL migration to author. You change `schema.q` and the running `dev` process re-adopts, or `deploy` classifies additive / rule-change / narrowing / destructive against the current release. That is closer to a live schema push (Convex, some hosted document stores) than to Rails/Django/Prisma migrate. The honest backfill was the maintain: adding it forced the engine to walk existing message rows. The cost is that a maintain grouped on a membership-audience table plus `deleted`, marked `online only`, moved the conversation query to the server. You do not get a free local replica of the new field unless you sync it. Destructive changes are a flag, not a rewrite of history; existing data either still fits or queued writes start refusing, typed. For Day-2 work on a small starter corpus this was the pleasant version of that contract. I would not want to discover a destructive classification against a 100k-message store in the same afternoon.
