# Building Clique with a shared server and device language

This build made Snapback 4 feel less like a hosted database client and more like a small application runtime. I authored Clique’s data model, authorization, synchronization, mutations, queries, expiry and scheduled work in Quarry, then connected an Expo Router interface to the generated API. That division mattered most when the application went offline. The same program that admitted a message on the server could produce its pending local row, and the replica could answer history and search queries after reopening. I did not have to invent an outbox schema and a second implementation of the message model. That was the clearest reduction in friction in this session.

The comparison here is qualitative. I built only this lane, with the exact published Snapback packages specified for it. I did not inspect another implementation or run current versions of Convex, Supabase, Firestore, or an earlier Snapback release beside it. My comparisons with those systems concern architectural patterns from prior knowledge, not a contemporary feature matrix or measured speed ranking. In particular, I cannot honestly turn this cold build into a version-by-version comparison of earlier Snapback generations. No earlier source, diary, or benchmark was consulted. The defensible observation is that this published generation exposes an unusually unified authoring surface; whether a particular older release delivered more or less of that needs separate evidence.

Authorization and replication fit together well for a messenger. Membership rows governed access to conversations, messages, reactions and read state, and the same audience declarations selected what reached each device. That is a useful place to put the contract: the client does not separately guess which chat rows to retain or whom to notify of a mutation. Schema caps also expressed real product limits, such as group membership size. The compiler could reject an unbounded or structurally unsuitable iteration before I had a workload large enough to expose it. The cost of that protection was learning precisely which source page preserved a complete capped group. A list accumulated from an otherwise valid page was not always an equivalent program to the classifier.

Against a Convex-shaped design, the tradeoff is familiarity versus shared semantics. A TypeScript server-function surface would make many ordinary transformations easier for me to express immediately. I would already know the language’s collection operations, debugging conventions and package ecosystem. Quarry instead required regular consultation of its guide and diagnostics. But translating a server function into an optimistic client update is another opportunity for divergence. Here, a successful predictable mutation supplied that local behavior through the runtime. The actual cold-offline and durable-restart proofs made that benefit concrete. I would be cautious about claiming that every current Convex application needs a hand-built queue; the narrower point is that this build received one directly from its chosen Snapback client arm.

Supabase and PostgreSQL suggest a different comparison. SQL is a more familiar and expansive language for reporting, joins and migrations. For lifetime totals and daily activity I naturally thought in SQL first, and I used independent read-only SQL inspection to check the maintained results. Quarry’s maintained counts made the application queries small, however, and kept count updates in the same transaction as their source rows. A conventional PostgreSQL application could achieve the same invariants with suitable constraints, triggers, views or application transactions. The extra design work would be deciding how those invariants, authorization and an offline device’s state correspond. Snapback made that correspondence part of the backend declaration rather than a separate integration project.

Media was another substantial reduction in application plumbing. Ordinary asset fetching, retained viewed bytes, view-once consumption and server expiry were related parts of the same model. I uploaded actual image and video bytes, rendered them, checked consumption per recipient, and verified that an expired message disappeared from history and search while its asset URL stopped serving content. The expiry proof closed the browser clients. It did not depend on a screen waking up to delete a row. That is more reassuring than an attractive disappearing-message animation with no server guarantee. It also leaves a clear limitation: the published upload operation is online-only, so picking a new media file offline does not become a durable upload job in this app.

The unified surface did not eliminate platform surprises. Delivered-history retention failed when combined with the message sync horizon in the configuration I tested; removing the horizon restored retained history after removal. That workaround preserves behavior by accepting more cold-sync work. An eligible reaction upsert returned pending without producing the expected local reaction, while explicit existence, update and insert branches behaved correctly and survived reopening. Presence was another disagreement: the guide described a conservative prediction value for connected clients, but the compiler classified a send reading presence as non-predictable. I separated durable notification candidates from service-only Quarry dispatch. That preserves message prediction, with the candid tradeoff that connection eligibility is checked at dispatch rather than exactly at the original commit.

These incidents changed the shape of debugging. I was not just asking whether a query returned the right answer on the server. I had to ask whether it ran locally, whether its inputs were held, whether its mutation was eligible to predict, and whether its predicted rows actually appeared. This is more vocabulary than an ordinary request-response CRUD application needs. The reward is that offline behavior becomes inspectable rather than an accidental cache effect. A Firestore-style document architecture offers another familiar route to local interaction, but a relational messenger with memberships, quoted messages and aggregate receipts would still require careful choices about denormalization and authorization. Quarry made those relationships explicit, while making residency an equally explicit engineering concern.

The scheduled digest was pleasantly concrete. Its configuration generates a real server schedule, and its chunked job accumulates authorized activity before emitting through the provider seam. The schedule ledger and chunk cursor survive restart. The proof checked exact counts, a quiet account, a quiet following period, and a restart before the boundary. The worker only relays or records provider work; the business decision stays in Quarry. This is more verbose than a single well-chosen SQL aggregation, and a full-corpus sweep is an operational choice that deserves attention as data grows. Still, I did not have to assemble a separate cron service, lease mechanism and retry ledger to establish the basic scheduled guarantee.

Several difficult loops were plainly my own. Adding required fields did not retroactively populate existing rows, so I had to stage a backfill. A modal retained its image node during a close animation until I made its lifetime explicit. Tests assumed an old fixture message remained in the newest history page. Most significantly, timestamp-plus-UUID ordering did not preserve server arrival when concurrent messages shared a millisecond. A burst probe demonstrated the error. I added a transactional conversation arrival clock and precise read watermarks, then checked partial reads within that ordering. A shared interpreter cannot choose the correct domain invariant for its author. It can faithfully execute a mistaken invariant on both server and device.

The native artifact boundary also deserves precision. Every requested milestone produced an iOS Hermes export using the pinned native package, and the final application also exported for web. The additional restart and media proofs ran in a browser replica. They are useful evidence about application behavior and durability, but they are not simulator evidence. Similarly, a working local development binary and a logged provider seam are not claims about a hardened public deployment or actual APNs delivery. Those distinctions let the build be production-shaped without inflating what the instrument actually exercised.

My strongest impression is that Snapback moved work from assembling subsystems into specifying their shared contract. That paid off for this messenger’s authorization, offline queue, media lifecycle and scheduled jobs. It added friction when the classifier’s boundaries or local prediction behavior were surprising, and it required explicit evidence rather than trust in a generated eligibility label. I would carry forward the server/device unity, the declarative expiry and the transactionally maintained aggregates as the compelling parts of this experience. I would also budget time to test residency, migration and replay behavior early. The separate full-scale run was still in progress when I wrote this essay; its measurements belong in the report, rather than being used to retrofit this account of the authoring experience.

The completed replay subsequently verified the combined fixture state. Its cold-browser measurements made the cost of retaining full chat history visible, while still completing the tested loads. A separate replica-client check returned complete, paged global search results at the full corpus. The direct HTTP global-search query was incomplete, so its recorded timings cannot establish a successful search curve. That distinction reinforces the essay’s main practical point: understanding where a query runs is part of correctness and measurement in this backend, not just a performance annotation.
