# Building Clique on the published Snapback 4 surface

Clique made the backend choice visible in the shape of the application. This was not simply a database exercise with a React interface added afterward. Messages had to survive offline work, receipts had to mean something precise, media had to become unavailable after revocation, and scheduled work had to continue with no client present. Snapback 4 supplied primitives for those obligations that I would otherwise have expected to assemble across a database, storage service, local store, transport, and worker. It also made the boundaries between those primitives unusually important.

The strongest reduction in friction was the small distance between a product rule and its server representation. A profile's owner, a conversation's membership, a message's expiry, and an asset's single-view policy all had visible declarations in Quarry. The same schema informed generated types and device behavior. That was particularly useful for disappearing messages. I did not write a client timer that pretended to be deletion, or a polling cleanup function whose absence would leave private content accessible. I declared the deadline on the row, calculated it from server time when sending, and verified the server refusal after the clients had closed. The physical sweep and the client purge followed that declaration.

Assets were another substantial saving. Uploading a file and placing it on an authorized row gave the file a home and an access rule. Deleting the message's media reference made the old asset inaccessible. A single-view column made the second fetch fail for the same principal and avoided durable caching. That is a meaningful simplification compared with my usual Supabase-shaped design, where I would think separately about storage object paths, bucket policies, signed URLs, cache retention, and what revocation can actually promise. It did not eliminate application work: the UI still had to own transient handles correctly, close viewers, avoid consuming a photo during ordinary rendering, and cope with late asynchronous results.

The media viewer illustrated the distinction. A video worked when opened from a settled message, yet failed during live choreography. Keeping the viewer inside a row whose lifetime followed live query replacement was the wrong arrangement. Moving ownership above the list fixed the observed interruption. The package guide contained that lifetime advice. My React familiarity helped recognize its relevance, but the first implementation did not follow it sufficiently. This was application error, not evidence that the asset primitive was defective.

Compared with a Convex-shaped implementation, Quarry moved more work into declarations and more reasoning into query shape. My default Convex design would use TypeScript query and mutation functions, with explicit authorization checks and reactive subscriptions around their results. Here, table rules and sync declarations were part of the model from the start. That made several trust boundaries easy to inspect together. It also meant that two superficially equivalent queries were not necessarily equivalent for local coverage, authorization proofs, or performance. Returning bare message hits enabled the documented current-and-retained search behavior; adding presentation joins too early changed the planner's guarantees. I had to treat generated types and compiler notes as part of design feedback, rather than as a final validation step.

The compiler was helpful without being a substitute for understanding. It refused an invalid use of the `once` modifier and explained why the modifier belonged on the owning column. It exposed shape and execution-mode mistakes during receipt work. It warned about query order, incomplete discovery, and bounded work. Those diagnostics let me continue using the published package instead of guessing at implementation details. Some corrections were entirely mine: the first daily Insights query treated `day()` as an epoch timestamp when it was a bucket number. The schema compiled, but the seven-day test exposed the semantic mistake immediately. Strong types did not remove the need for a small, independent expectation about the result.

Offline behavior changed the client architecture more than the visible screens suggest. An operation could be admitted durably without producing a predicted row. A pending notification could describe dispatch rather than authoritative settlement. A retained answer could remain useful while revalidating, yet still be withdrawn when its authority or deadline changed. The app therefore needed to render the outbox itself for some messages, likes, and reactions, rather than assuming every optimistic write would appear in a query. Once that distinction was explicit, ordered offline messaging and restart recovery were straightforward to exercise. The supplementary browser check showed a queued message surviving an offline reload and settling once after reconnection. The native artifacts are Hermes exports; they do not stand in for simulator evidence that was not collected.

This is where Snapback saved the largest amount of infrastructure work relative to my usual plans for other backends. With a conventional hosted SQL design, I would budget a durable client queue, entity reconciliation, account-scoped storage, retry ordering, and a way to retire revoked content. With a reactive function backend, I would still budget explicit durable-offline behavior unless I had separately established that the chosen client supplied it. In this build, those concerns were part of the published client and replica surface. That saving came with a larger vocabulary of local states and a requirement to preserve its semantics in the UI. A pending marker was easy; making it mean the right thing across custody, restart, settlement, and read receipts took deliberate work.

Receipts also resisted the tempting simplification of treating connection as delivery. The model used per-conversation ordinals, actual delivered intervals, and a separate seen watermark. Removing a member did not claim that the member had read anything. Expiry introduced holes, so the delivery mutation needed a read phase that found live blockers before it changed interval state. That is more application code than a boolean `read` flag, but it implements the brief rather than a convenient approximation. The shared roster and bounded group size made the proof manageable. The published receipt and sequence cards were useful because they explained the invariant, not merely the syntax.

Insights and the digest showed a different advantage. Maintained counts expressed totals without downloading a corpus to the client, and the daily job had a real scheduler, server clock, and durable emission key. The notification worker was a small provider seam rather than an independent scheduler with its own checkpoint table. I verified the digest with fresh activity, closed clients, a server restart during the period, and a following idle period. Exact counts and authorization still belonged to the application: a system job cannot rely on ordinary viewer rules to decide whose unread messages contribute. The job explicitly walked each recipient's memberships and excluded old, read, own, tombstoned, and expired messages.

The main source of friction was interaction between correctness and observation cost. The initial dual-device run briefly lost visible messages during convergence even though the messages had appeared. Consolidating per-message reaction reads and making ordinal assignment server-only each produced passing runs, but later regression passes exposed the race again. A repeated navigation probe finally captured the history page withdrawing and returning, without message loss in storage. The published client contract allows that withdrawal when a change cannot be revalidated within one second. My screen also ran empty searches and an inbox observation when no one was searching. Removing that unnecessary work produced six consecutive independent convergence passes and another complete choreography pass. I also stopped issuing typing writes while offline and removed unused subscription linger. I regard the unnecessary observations as application error; the exact cause of the earlier deadline misses remains ambiguous. The retained failures matter because one green run would have overstated confidence. A platform can provide a sound local model while an application's observation pattern still makes the experience unstable. The guide's recommendation to batch list reads mattered in practice.

This was a cold build against the published 0.4.10 packages. I did not inspect earlier Snapback implementations or previous benchmark work, so I cannot honestly claim a measured improvement over an earlier generation. The comparison I can support is architectural: this generation exposes local execution, expiry, media ownership, effects, maintained views, and schedules as one authoring surface. Whether an earlier generation lacked or implemented any particular feature is not established by this run. The same limit applies to treating these impressions as a current-release benchmark against Convex or Supabase; those comparisons describe how I would structure the work with those systems, not a controlled timing result.

My overall impression before the numerical tally is that Snapback reduced the amount of infrastructure I had to invent, while increasing the importance of understanding its precise contracts. The best moments were declarations that removed an entire secondary subsystem. The hardest moments were boundaries: transient assets and live rows, retained data and current authority, pending intent and settled history, bucket keys and timestamps. The production lesson is to keep those boundaries visible in code and tests. The full replay subsequently matched the state manifest. Its endpoint degradation ratios passed, but the strict midpoint bounds for search, Insights, and Trending did not. Concurrent work may explain some noise; it does not justify replacing the failed measurements. The 50-member browser test delivered every message, yet its roughly four-second p95 was visibly slow. State correctness and scale safety remain separate conclusions.
