# M7 diary

I picked up this lane without the builder's context. The README, API wrapper, Quarry schema, frozen tests, and inherited report were enough to find the seams. I started a new persisted backend inside this lane, replayed the three starter logs through the application's own seed command, and exported each persona's M6 message manifest before editing the schema. I did not read the prohibited diaries, essays, sibling lanes, or a Snapback source checkout.

I added group polls as ordinary messages with optional typed question/options. Poll creation shares the existing message sequence, receipts, notification seam, expiry and tombstone lifecycle. A unique message/principal vote row implements changeable set-state intent. The existing durable message transport now handles poll creation and voting, preserving submission order and original wire envelopes. The frozen compose/display components made the UI straightforward. Live voting, replacement, exact retries, and offline reconciliation worked through the actual UI and API.

The migration itself was easy to adopt. Snapback classified the final change from the inherited schema as additive and rebuilt the new count aggregate. The inherited schema already had messageSequence and receipt/unread aggregates, but no visible-message count. Exact snapshots taken immediately around adoption preserved the starter manifest. A separate proof added real photo/video messages, reactions, a read receipt and a tombstone under the inherited schema, then adopted the final schema and compared again. The uploaded bytes still matched their source fixtures.

The count semantics fought me. A plain maintained count still includes an expired source row until the physical sweep, although history already hides it. Quarry's immutable locals and limited aggregation expressions ruled out the first read-time corrections I tried. Its published sum(page, .field) example does not match the compiler. An unsupported maintain expiry property and the diagnostic's readable hint did not solve the problem. I ended with maintained buckets grouped by conversation, deletion and expiry; the server marks eligible buckets at read time, the custom-client API pages and sums them into conversation.messageCount, and settings sum the synced buckets while respecting expiry. This is an aggregate-backed projection rather than a new integer column in the conversation source row. It avoids counting or transferring message bodies and avoids imposing a fixed conversation-size cutoff.

The inherited regression bar stayed red. The M1 duplicate-email test gets stuck waiting for the signup toggle after logout. It fails with the pre-M7 schema as well. I preserved that behavior rather than spending M7's budget repairing authentication. M4 also exposed an inherited optimistic-bubble/server-observation race in some runs; an unchanged retry passed, and the final run passed without retry. The phase report does not convert either earlier failed attempt into a pass.

Compared with migrations I know on SQL-backed systems, schema adoption and aggregate backfill required much less deployment choreography. I did not write a migration runner or manually update every conversation. The tradeoff was a smaller expression language and an expiry/aggregate semantic gap that needed explicit design work. A SQL view could usually express this filtered sum directly; a document backend might require a transactional counter and an expiry reconciliation job. Here the final bucket projection is understandable, but more involved than the concise maintain declaration initially suggested.

I built an iOS Hermes artifact and verified web interactions. I did not claim a new simulator runtime proof, scale migration, push-provider delivery, or a repair of the inherited scale failures. Later browser activity advanced some starter delivery receipts normally; the exact immediate migration snapshots are preserved separately, and final-state receipt deltas are disclosed instead of being reset.
