
## M1 — Accounts and profiles
Built password signup/login, durable sessions, revocation, editable unique profiles, avatars, Expo Router web and SQLite-native client wiring. Schema constraints and asset uploads were easy; the first successful seed required very little backend code. Direct-route loading and post-login navigation fought me because I initialized the form too early and preserved the Settings route after authentication. Existing React knowledge helped isolate those mistakes. The default polling setting coincided with server stalls; the documented one-second setting produced responsive verification. The published auth surface avoided writing security-sensitive password code. Relative to familiar Convex/Supabase patterns, the integrated local replica removed subscription/cache setup, while the new language required learning even an empty scan's syntax. The harness snapshot omitted a generic validator dependency; its original failure is retained and an AJV import shim enabled unchanged assertions. No prior Snapback implementation was read.

## M2 — Posts and follow graph
Built text/photo/video posts, original and repost feed entries, follow edges, likes, threads, profile post lists, link opening, and cursor pagination. Quarry's merge over follow prefixes expressed the Following feed directly and kept self membership implicit. The main friction was runtime aggregate shape: lookups returned scalars, while I had read the aggregate documentation as row-shaped. I corrected both UI and tests. Asset bytes and authorization were straightforward, but inspecting normalized video duration inside the insertion body failed with E_FIELD; the missing server-side 60-second validation remains explicit. Familiar relational modeling helped with unique set-state relationships. Unlike a SQL service plus an offline cache, this needed no client reconciliation layer. Unlike TypeScript-first backends, generated shaped query results provided less guidance about aggregate values. An overlapping suite/choreography run was my mistake: fixture writes moved a live-test post off its initial page. The successful rerun was sequential.

## M3 — Messaging core
Built DMs, distinct groups, admin lifecycle, membership-scoped message sync, quoted replies, sender identity, typing and monotonic receipts. The partition audience matched membership directly, and delivered-history retention passed the removal proof without a custom cache. The hard part was separating ephemeral traffic from durable writes: initially I queued typing and repeatedly acknowledged idle receipts. Those choices caused typing timing failures and unnecessary traffic. Reactive receipt work and immediate ephemeral typing requests fixed them. Membership writes also needed keepalive requests across the harness's immediate full-page navigations. A direct API probe proved removal itself worked; the precise interrupted-queue boundary remains ambiguous. Familiar browser lifecycle knowledge helped more than backend familiarity here. Against server-only subscription systems, the built-in history retention is unusually useful. Against TypeScript application servers, immutable local bindings and query diagnostics required a different style of bounded aggregation.

## M4 — Media messages, reactions, edit/delete
Added photo/video picker flows, inline asset rendering, playback, set/replace/clear reactions, editing and tombstones. The fixture window config generates server-side Quarry limits; the caller has no timestamp seam. Clearing asset columns revoked serving immediately in the API test. This was the smoothest extension so far: the existing local client handled live reaction and edit propagation without new sync infrastructure, and all required choreography passed on its first M4 run. Existing web media knowledge supplied video poster extraction and playback. Compared with a backend that separates blob storage from rows, row-owned media made revocation noticeably simpler. The unresolved video-duration insertion limitation from M2 still applies.

## M5 — Ephemeral content, customization, search
Built server-enforced disappearing messages, view-once photos, synchronized chat name/description/color/background, and three search scopes. The one-view asset path was concise and correctly returned E_ASSET_VIEWED on a second fetch. Server-only expiry refused both the message and asset with no client opened for that test conversation; the frozen closed-client relaunch proof also passed. The guide's conditional-expression shorthand did not compile. Explicit conditional updates within the insert transaction preserved atomicity and the server expiry rule. Search required ordinary JavaScript normalization and prefix matching because the release explicitly lacks served word indexes. That is coherent online/offline behavior over the replica, but it is not an indexed search claim at scale. Compared with SQL-backed search services, search is weaker; compared with separately authorized storage, one-view and expiry revocation are substantially easier to express. No familiarity with another Snapback checkout was used.

## M6 — offline, push seam, custom client, replay
The local client supplied durable storage and predicted writes with very little glue. The custom client uses the same authenticated HTTP mutations and queries as the UI; all 50 sample actions settled through real operations, including uploaded media. The first scale checkpoint independently matches the frozen manifest. The scale replay continues on its own clock.

Offline UI failures were mostly mine: an unhandled ephemeral typing request raised Expo's error overlay, and waiting for settlement unnecessarily held the composer. A later ordering miss did not reproduce in the independent two-browser probe or final choreography; retained as ambiguous rather than silently discarded. Connection presence is a four-second server lease, which leaves a detection interval for abrupt losses. Public row sync makes broad offline search straightforward but is a poor substitute for a served search index at scale. Prior HTTP/session and SQLite familiarity saved time. Compared with Convex this client carries more of the local-first lifecycle; compared with Supabase it supplies substantially more prediction and sync machinery. Neither comparison constitutes a measured alternative-backend run.

## M8 — aggregates, schedule, and devices
I built six server-maintained Insights totals, seven UTC activity buckets, an expiry-backed top-ten ranking, the daily/shortened digest job, cross-device unread counts, and restart verification. Derived activity facts keep Insights reads independent of corpus size. A server backfill job handles data written before this milestone. The digest uses a per-profile transactional tally because the documented sum form was rejected. It passed an unattended two-period proof with a backend restart and a private conversation excluded from the target's counts.

The local replica made same-account convergence easy, but my proof plumbing fought me. Replaying a cached Expo shell triggered Chromium's loopback permission boundary; I initially blamed queue recovery, then proved that even a direct HTTP fetch was blocked. I removed the unnecessary outbox workaround. Waiting for local mutation admission before clearing the composer fixed a separate queue ordering race. Three sequential restart proofs retained pending messages, flushed in order, and reached read. These are web IndexedDB proofs with a replayed bundled shell, not simulator evidence; the native SQLite path is compiled into Hermes artifacts.

The scale corpus verified exactly, including media. Maintained aggregate reads stayed small. The broad following merge and cold replica initialization did not meet the scale envelope. This is the cost of my chosen sync shape, especially broadcasting per-recipient receipts to the whole conversation. It remains a delivery limitation, not a reason to redefine the benchmark. Familiarity with transaction boundaries, materialized counters, browser CORS and async lifecycle debugging saved time; unfamiliar Quarry arithmetic and collection syntax caused avoidable loops. Convex would let me express the digest's arithmetic in ordinary application code; Supabase would offer familiar SQL aggregation but leave much more local-first machinery to assemble. Snapback 4 concentrates both the benefit and the constraint in its one authored backend language.

### M8 final regression correction
Late M6 regressions disproved the admission-only ordering diagnosis. I inspected only the installed npm client's relevant queue code and declarations. Its outbox sorts operation IDs; the ID builder shifts the timestamp out of the encoded range. The final application FIFO guard persists submission order, reads the original envelopes through the exported replica store interface, and preserves their prediction IDs. An initial guard omitted those IDs and left local receipt predictions unmatched despite server read state; that agent error was corrected. The final guard passed repeated M6 choreography, the full M8 segment, and a cold browser restart through read. This is a pinned-package compatibility workaround, not a patch to the installed package. Expo's optional peer resolver also required explicit pins matching its bundled native-module recommendations; the final native export was rebuilt.
