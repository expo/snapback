# Building Clique with Snapback 4

This build changed where I spent engineering effort. The backend was a schema, authorization rules, indexes, synchronization declarations, queries, mutations, and jobs in one Quarry file. I did not build a TypeScript server or an API routing layer. That compression was valuable, especially for the first social and messaging features. It also made every missing expression, surprising return shape, and compiler limitation consequential: there was no ordinary server function into which I could move the awkward part.

The comparison here is an engineering reflection, not an experiment across backend products. I ran only Snapback 4, using its public pinned package and published surface. I did not inspect any Snapback 2 source or an earlier Clique implementation. My comparisons with Convex and Supabase concern familiar architectural choices, and my comparison with Snapback 2 is necessarily limited. I cannot turn general familiarity into measured claims about a release I did not run.

## Where the backend removed work

The most successful part of this experience was the connection between authorization and synchronization. Conversation membership was a backend fact. Rules decided who could read the conversation and its messages; synchronization delivered the corresponding partition. That is a better starting point for a messenger than treating realtime subscriptions as a transport that the application must separately police. The UI could use ordinary reactive hooks over the local replica, while the custom client called the same authored operations through authenticated HTTP.

Expiry and assets were similarly useful primitives. Disappearing messages used a server deadline and a table expiry declaration. I could close every client, wait, then verify that both the row and its asset access were gone. Media was represented by typed columns, uploaded through the client, and resolved through asset APIs. A view-once photo had an access lifecycle rather than merely a frontend boolean. These features reduced the number of independent stores, timers, and permission checks I would otherwise have to coordinate.

Compared with a conventional Supabase application, this provided more of the offline system in one package: a persisted replica, predicted mutations, a queue, and generated operation types. PostgreSQL, row-level security, storage policies, and a realtime channel are powerful ingredients, but they do not by themselves specify a complete device replica and its pending-write semantics. With Snapback, the product could start from those semantics. The cost came later, when I had to understand their precise lifecycle and the size of the partition I had chosen.

Convex is a closer conceptual comparison for reactive queries and typed application operations. Quarry's advantage in this run was that several guarantees were declarations rather than repeated application code. Its disadvantage was that I could not simply write familiar collection and arithmetic code when a feature became complicated. The reduction in authored surface is real; it should not be confused with a reduction in the amount of reasoning required.

## Where the language and documentation added work

The compiler was often useful. It identified missing expiry indexes, nullable references, unsupported terms, and operations whose reads could not establish completeness. Those diagnostics encouraged explicit bounds and better access paths. A small language can make the execution cost of an operation more visible than a general-purpose function full of hidden queries.

However, the published documentation and accepted syntax did not always agree. The documented aggregate sum form was refused. Arithmetic division required a paired quotient/remainder binding that I learned from a diagnostic. An expiry example did not compile as shown. Maintained counts were returned as scalar values where my initial reading led me to expect a row. Each mismatch was recoverable, but together they added a substantial discovery tax to an otherwise compact backend.

The digest illustrates the tradeoff. I used maintained activity facts for public social events and maintained receipt counts for unread activity. To total a user's following and conversations, I used a transactional work row inside a server job. That was expressible and testable; its cursor and writes survived a backend restart. It was also more ceremony than writing the equivalent arithmetic in a familiar language or expressing it as SQL. The resulting program is governed by useful bounds, but its shape reflects language constraints as much as the product problem.

The release's missing served word search was a more fundamental limit. Searching already-synced rows gave the app warm and cold offline search behavior. It did not establish that the same design would meet the full search degradation envelope. I kept that distinction explicit. A capability gap should not disappear behind a working small demo.

## What the scale replay changed

The replay was a strong part of the package experience. A standalone adapter could register users, upload real fixture media, and invoke the same mutations used by the application. Independent paging then verified the expected corpus at both intermediate checkpoints and at completion. This exercised much more than inserting a synthetic database dump would have done. It also made a test setup error visible: my first suppression seed had the wrong request shape. I retained that run and repeated the replay against a fresh instance with explicit suppression verification.

Maintained Insights totals and the live-window ranking behaved well at the larger corpus. They returned bounded results without transferring the corpus to the screen. Conversely, the following-feed merge grew too much with the number of followed accounts. More seriously, cold synchronization of the large conversation account exceeded the timeout and used substantial memory.

Those results are not merely language defects. My receipt design broadcasts individual recipient receipts to conversation members. It is simple and makes small-group receipt aggregation easy, but it creates an expensive device partition in a large, busy group. A production iteration should replace that shape with a more compact acknowledgement read model while preserving membership changes and offline receipt behavior. Snapback made the sync policy easy to declare; it did not make a costly policy cheap. The benchmark was useful precisely because it exposed that distinction.

## Mistakes that belonged to the application and the probe

Several correction loops were mine. An unhandled typing fetch produced an Expo error overlay while offline. I initially misdiagnosed the disabled interaction that followed. A cached-shell restart probe then encountered Chromium's loopback network permission boundary, and I again investigated queue recovery before checking a simple direct request. Once the permission problem was visible, I removed the speculative retry layer instead of retaining extra machinery with no demonstrated purpose. A later regression established a separate ordering problem. A bounded inspection of the installed npm client—not a source checkout—showed that its queue sorts operation IDs whose timestamp bits are lost in ID construction. I added a durable FIFO transport guard using the exported replica store interface. Preserving the original request envelope, including prediction IDs, was essential to keep receipts reconciled. This is an application workaround tied to the exact package pin; it is more machinery than the README initially suggested would be necessary. The installed-source inspection exceeded the requested README/guide/generated-type boundary. That protocol deviation means these functional results must not be represented as a fully compliant cold benchmark.

There were genuine application races too. The composer needed to remain usable while offline, but that did not itself establish transport ordering; a late regression disproved my earlier admission-only diagnosis. Exposing an optimistic like as completed let an immediate Insights reload precede the server aggregate update. These are lifecycle issues that would matter with other backends as well. A backend offering prediction still requires the product to distinguish queued, predicted, committed, delivered, and read states.

## What I would carry forward

Against an older Snapback design, the concrete difference I can defend is the surface I used here: Quarry plus generated types and the local client were sufficient to author the backend without a separate application server. I cannot responsibly claim a numeric improvement over Snapback 2, or describe unobserved differences in its durability or authorization behavior. That comparison needs its own controlled run.

I would carry forward the declarative expiry, typed assets, explicit membership rules, generated client contract, and checkpointed server jobs. I would revise the receipt partition and following-feed strategy before treating this as a scale-ready messenger. I would also want a tighter single-page reference whose examples compile exactly as published, and more visibility into cold replica initialization.

Snapback 4 let a broad product become concrete quickly. The final functional proofs are meaningful, including unattended server work and durable web restart behavior. The failed scale gates are equally meaningful. The experience supports a claim of reduced integration work for a local-first application; it does not support a claim that declarative synchronization removes the need to design and measure the data delivered to each device.
