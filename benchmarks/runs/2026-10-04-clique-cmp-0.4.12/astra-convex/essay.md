Clique on Convex: what changed the work

Convex made the connected version of this app feel unusually direct. The same function that described the data a screen needed also described what that screen would keep observing. A message send, a reaction replacement, a membership change, and a read acknowledgement could each be a small transaction, followed by a query result that changed in the other browser. That was the clearest benefit of this build. I spent comparatively little time inventing a transport protocol for the primary interface. I spent considerably more time deciding what the application had to remember when that transport disappeared.

This is an account of one independent Convex build. I did not inspect another lane, a Snapback checkout, or a previous Clique implementation. I did not run Supabase or Snapback 4 alongside this app. Comparisons with those systems therefore concern architecture and prior model knowledge, not measured authoring speed or a claim that the same implementation would have taken a particular amount of time elsewhere. That distinction matters especially for Snapback 4: this session gives me direct evidence about Convex and no fresh operational evidence about Snapback. A plausible alternative design is useful to discuss, but it is not a substitute for a second run.

The schema was easy to make concrete. Conversations, memberships, messages, reactions, posts, and follows fit naturally into separate tables with explicit indexes. Stable fixture keys and mutation-intent keys made retries understandable. A DM's sorted participant pair gave the application a single identity to protect in its creation transaction. Handle uniqueness and one reaction per person were similarly straightforward to enforce in the mutation path. The tradeoff is that these guarantees live in functions and indexed lookups rather than in declarative unique constraints. I could keep them coherent, but a reviewer has to inspect the write paths to understand the full model.

Compared with a PostgreSQL-backed design, that shifts effort from a database definition toward application transactions. For a SQL implementation I would expect unique constraints, foreign keys, and carefully scoped procedures to express much of this model. Supabase's documented row-level security is a natural place to enforce per-user visibility, while this Convex app enforces it explicitly inside every public function. Neither approach removes the need to decide what a removed group member may still see, or what a quote should reveal after its source is deleted. Those were product authorization decisions before they were database decisions. The advantage I felt here was having those decisions close to the transaction and return shape. The cost was repeated authorization plumbing. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

Authentication was less automatic than the connected data path. I used the published Convex Auth password provider rather than writing password hashing or JWT signing myself. The surprising part was signup behavior: submitting existing credentials did not initially produce the duplicate-email behavior the brief required. I had to inspect the published provider implementation and wrap the actual authorization option, then verify the result through the UI. Immediate logout revocation also needed an explicit session-record check in application functions and media grants. Supabase documents a comparable distinction between access tokens, refresh tokens, and session identity; a token's signature alone does not answer every application revocation requirement. I would preserve that explicit reasoning in either stack. [Supabase session documentation](https://supabase.com/docs/guides/auth/sessions).

Realtime behavior was the part where the backend most clearly reduced friction. Read state was account data, while initial-sync cursors were device data. Keeping those separate meant a second device could clear its unread badge without losing the ability to fetch messages it had never stored. The later same-account choreography largely reused the model already built for two different users. Typing and presence were less elegant: I used short-lived rows, leases, and scheduled cleanup. They worked, but I would not describe that as a purpose-built ephemeral-state experience. The durable reactive core was stronger than the presence abstraction I authored around it.

Offline support changed the shape of the application. Convex's optimistic-update documentation describes temporary local query changes that reconcile with a mutation result. That is useful connected interaction behavior, and it is different from the durable store this brief needed. I built a per-device outbox, stable operation keys, ordered replay, persisted sync cursors, cold-start account and conversation metadata, a message store, and media retention. I also had to connect tombstone and expiration updates to local deletion. The browser restart check was valuable precisely because a warm screen can hide missing persistence. Later review moved browser messages to IndexedDB and made delivery acknowledgements wait for durable commit. [Convex optimistic updates documentation](https://docs.convex.dev/client/react/optimistic-updates).

This is the strongest architectural comparison I can make with a local-first alternative, including the role Snapback 4 is intended to play in this comparison. If an alternative supplies durable queries, an ordered persistent mutation log, and documented revocation semantics as one integrated client model, it could remove a substantial portion of the code I wrote here. This lane does not establish that Snapback 4 supplies all of those guarantees, nor that its edge cases would be easier. It establishes what Convex's server-centric reactive model left to this application. A conventional Supabase client would also need a deliberately chosen local persistence and synchronization layer for this contract; changing the hosted database would not itself implement a cold-start outbox.

Media had a similarly sharp split between the happy path and the guarantee boundary. Uploading fixture images and video to storage was easy. Validating video duration and ownership, serving message assets through session-bound grants, consuming a view-once grant once, and refusing a previously issued URL after deletion required real application logic. The important design choice was to avoid exposing a durable public message-media URL. Once that boundary existed, expiration, logout, deletion, and group removal could share it. Offline media added another boundary: ordinary files could be retained, while view-once bytes had to remain transient. These guarantees were expressible without a separate service, but they were not merely a storage configuration toggle.

Search also exposed a mismatch between a convenient product feature and the exact query contract. The brief wanted word-prefix matching with newest-first ordering and authorization across conversations. I chose indexed token postings and a prefix vocabulary rather than pretend a relevance-ranked result was the requested ordering. Offline search then needed the same normalization rules over locally stored messages. This was workable, and the explicit indexes made the access pattern reviewable, but it was a second substantial application subsystem. SQL would offer a different set of text-search and index tools, although I would still have to prove prefix, ordering, and offline semantics rather than assume the defaults matched.

The scale replay then supplied a concrete search failure: at its middle checkpoint, scanning global postings before filtering conversation membership exceeded the server's operation budget. I changed the read plan to start from authorized conversation indexes and resumed the acknowledged log prefix. This was my query-plan error, not evidence of a Convex defect. It also illustrates the extra care required when the application owns the join strategy. SQL would provide more planning machinery, but I would still need to inspect its plan. I retained the failure rather than reporting only the repaired query.

Insights and digests brought the transactional model back into favorable territory. I maintained user totals and UTC-day buckets in the same mutation paths that changed posts and reactions, and backfilled existing post entities through an idempotent accounting flag. Trending used a rolling eligible set with scheduled removal. The digest used a server schedule and a persisted per-user period record, so a retry or backend restart did not create another notification. A closed-client test checked the payload, an unauthorized chat, a zero-activity user, and a later quiet period. I did catch my own mistake in using a deployment-relative interval for an anchored UTC schedule. Convex provided the scheduling primitive; selecting the correct schedule remained my responsibility. [Convex cron documentation](https://docs.convex.dev/scheduling/cron-jobs).

Local operations were useful but imperfect under this environment's restrictions. Anonymous development avoided a hosted-project dependency, and the local binary gave the replay a genuinely fresh database. The CLI also started a dashboard on its hardcoded default port, which violated this lane's assigned range before I noticed and corrected it. That is recorded as my setup error, not concealed as successful confinement. Running the backend explicitly made the process and port boundary clear. The package source was valuable for discovering behavior that was less obvious from the command line. A more direct headless local mode with all listening ports configurable would have reduced this friction.

The replay and evidence work altered what I was willing to call success. A count of acknowledged actions alone was insufficient, so verification also read the backend independently, checked per-user and per-chat totals, inspected named entities, and paged the busy chat through the public API. Checkpoint snapshots allow the later Insights and Trending diagnostics to use the same verified workloads without mutating the authoritative replay. The retained receipts also expose mistakes in my own evidence handling: early suite files were overwritten before I switched to immutable receipt names. Later regression runs repair the current proof chain, but they do not recreate the missing historical bytes. That is an evidence gap, not a reason to invent a clean history.

The environment also sets a firm limit on the result. Hermes exports show that the iOS JavaScript bundles build. The browser checks show the behavior they actually exercised. Neither demonstrates a native simulator run. The simulator attempts are recorded as unavailable on Linux, and I would not transfer the browser restart result into a native score. This makes the build production-shaped rather than a claim of production readiness: there are real authorization boundaries, schedules, persistence, and repeatable tests, together with explicit limits on what was executed.

My lasting impression is that Convex made server-authoritative, connected collaboration easy to express and inspect. It made the application functions a productive center of gravity. It did not make durable offline behavior disappear, and the strict media and search contracts still required specialized code. A SQL-based stack would change where constraints and aggregations live; an integrated local-first stack could change how much synchronization code the client owns. The most useful comparison is therefore about which guarantees the platform supplies and which the application must construct. This build gives concrete examples of both, without turning one timed lane into a universal ranking.

Two late checks sharpened that distinction between convenient reactivity and explicit freshness. Convex's React client's one-shot query can reuse an existing subscription result. That is excellent for ordinary reads, but a refresh of a server-time window needs a new query key if no data changed. I added a nonce that affects caching only; the server still owns calendar time. Separately, keeping multi-gigabyte local replay databases inside the authorized workspace made Metro's file watching an operational concern. Explicit crawler exclusions and a recorded server restart restored responsiveness. These were integration responsibilities in this build, not evidence that the database's transaction model was defective.

The last browser-scale check was also useful precisely because the API probes were already green. A durable browser bootstrap adds storage work and subscription invalidation that a headless fetch does not measure. A larger bounded bootstrap batch and no-op receipt suppression reduced that work without weakening persist-before-acknowledge semantics. I also had to account for Expo 55's development virtual environment module, which merges dotenv files over shell values: two frontends against different local instances needed an explicit dotenv exclusion in the scale bundler. Those failures belonged in the build record even though neither was a Convex invariant failure.
