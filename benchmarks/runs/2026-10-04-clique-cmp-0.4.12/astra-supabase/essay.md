# Building Clique on Supabase: the boundaries I had to own

This run made Supabase feel like a capable collection of infrastructure services around a database I already understood. It let me express the social graph, conversation membership, receipts, ephemeral access, and aggregate read models directly. It also left the shape of synchronization largely in my hands. The app that emerged has an Expo Router client, a Node API, hosted Supabase Auth and Storage, PostgreSQL transactions, a local cache, and a durable client queue. That is a familiar architecture, and familiarity reduced the time needed to choose an implementation. It also made it easy to underestimate how many boundaries that architecture creates.

This is one cold build, not a controlled comparison of finished products. I did not inspect another lane, any Snapback checkout, or an earlier Clique implementation. I did not operate Snapback 4 or Convex in this session. My Convex comparison combines general familiarity with its public documentation; my Snapback 4 comparison is necessarily limited to the integration questions this benchmark exposes. I cannot honestly attach a measured advantage to Snapback 4 from this evidence. Where I describe what an integrated synchronization system could remove, that is a counterfactual about architecture, not a claim that an untested product automatically satisfies the brief.

Accounts were straightforward once I separated the hosted Auth identity from the lane's application profile. Password handling stayed on the managed Auth path. The difficulty was provisioning: the hosted project already contained some fixture identities, while this lane's namespaced profile tables were fresh. A successful login did not initially imply a profile existed. Email confirmation settings also differed from the assumption in my first signup implementation. Those were application integration mistakes, not evidence of broken password storage. The eventual code verifies a real session, creates the lane profile where appropriate, and persists a server-side session revocation record so logout has immediate meaning at the API boundary. The cost was extra glue between identity and application state.

PostgreSQL was most helpful when an invariant had a crisp relational form. One DM per sorted participant pair, one reaction per actor and message, one recorded view per recipient, unique mutation intent IDs, and transactional recipient snapshots all fit naturally. I could make “retrying this request does not toggle it again” a database-backed property. Conversation locks let sending and membership changes agree on a recipient snapshot. This resembles a conventional PostgreSQL service more than an application built chiefly around client database access. My API uses a trusted database connection after authenticating the caller; the application tables have RLS enabled without client policies. That is a deliberate trust boundary, with the corresponding responsibility to check authorization in every endpoint.

Convex offers a different default boundary. Its documentation describes dependency-tracked query subscriptions and automatically updated query results. That would move some of the feed, profile, receipt, and unread invalidation work out of this client's polling loops. It would not, by itself, decide the product rule for a removed member's historical access or a late-added member's receipt obligation. Those rules still need to be represented correctly. The likely benefit is less manual plumbing around changing results, not the disappearance of domain modeling. This is an inference from the documented model, not an observed time saving in this run. [Convex Realtime documentation](https://docs.convex.dev/realtime)

My transaction code is also visibly more operational than a deterministic mutation function. I acquire a connection, begin, lock where needed, insert an intent, perform changes, commit, and release. There are opportunities for both mistakes and optimization in that sequence. Convex documents atomic mutations, conflict detection, and retries based on deterministic execution. That could reduce explicit retry and lock management for some of these operations. It would still require choosing the correct read and write set, especially for group membership and once-only access. I found SQL constraints reassuring because I could inspect and independently query them; another engineer may prefer having more of those mechanics inside a typed function runtime. [Convex transaction documentation](https://docs.convex.dev/database/advanced/occ)

The largest amount of application-owned behavior appeared at the network boundary. Live updates here use polling. I had to guard against overlapping requests, keep feed projections from briefly showing another tab's rows, isolate caches by account, hydrate state before rendering a cold session, and reconcile revoked or expired content. Supabase has a documented Postgres Changes subscription facility; I did not use it in this lane. Consequently, the polling code is evidence about the architecture I chose, not proof that Supabase requires polling or lacks live delivery. Subscribing to changes would still leave decisions about local query projections, durable storage, and media invalidation. [Supabase Postgres Changes documentation](https://supabase.com/docs/guides/realtime/postgres-changes)

Offline behavior made that distinction concrete. Persisting message metadata was easy. Preserving intent order, keeping stable IDs, classifying retryable failures, showing pending receipts, and resuming the same queue after process death were separate tasks. Ordinary media needed durable bytes as well as metadata. View-once content needed the opposite treatment: an atomic server gate and transient viewing bytes, with no durable received-media cache. Expiration required a local check while disconnected and authoritative reconciliation after reconnect. These are the places where I would most want to compare Snapback 4 against this implementation: exactly which of these responsibilities its published client/runtime contract owns, which it exposes as application hooks, and what survives restart. I cannot substitute an attractive local-first mental model for that missing empirical answer.

The media work also exposed an important weakness in my own workflow. The development instance's bucket update path accepted video, while fresh bucket creation still carried the earlier image-only allowlist. The isolated scale replay therefore failed during starter seeding. The small development conformance run could not catch that difference because it reused an already updated bucket. Correcting the source afterward does not turn the recorded replay into a full workload. There is no valid large-corpus latency or degradation claim here. The lesson is about deployment reproducibility: a successful mutation path in an evolved development instance is weaker evidence than successful provisioning and replay from an empty instance.

Insights and digest brought the work back toward Supabase's strengths. I used maintained counters and daily buckets rather than making the client page content to derive totals. Triggers keep those read models in the same transaction as their source rows. The digest worker uses server time, a persisted period cursor, and unique emission keys; the cursor and logged payloads commit together. A real restart during a period exercised that state, and an inactive following period checked suppression. This is still an API-process worker, not a managed deployment with a demonstrated service uptime guarantee. It shows that the scheduling logic can recover, while leaving the operational obligation to run that worker explicit.

Several visible setbacks had little to do with the backend. The frozen UI kit's React Native accessibility values did not always become the DOM attributes the web harness reads. An Expo Router stack retained hidden screens and duplicated selectors. A missing harness import required a narrow schema-validator loader. My later Metro restart used CI mode and therefore stopped watching source changes. These distinctions matter: blaming Supabase for them would be misleading, but ignoring them would also misdescribe the engineering experience. A timed build is a whole toolchain exercise. The reports retain those retries rather than presenting only the eventual passing receipts.

I would choose this shape of Supabase application when relational invariants, SQL inspection, and explicit service boundaries are valuable, and when the team is prepared to own synchronization and operations. Compared with a conventional PostgreSQL-plus-REST stack, managed Auth and object storage reduced what I had to provision. Compared with Convex's documented reactive model, I authored more client coordination. Compared with Snapback 4, this run identifies the questions a fair follow-up must answer rather than supplying an unsupported ranking. The web milestones, Hermes exports, scheduled digest proof, and offline browser checks are useful evidence. The unavailable Apple simulators and failed fresh-instance replay are equally important limits on what this app has demonstrated.
