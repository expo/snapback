# Building Clique on the published Snapback 4 surface

The strongest part of this experience was that the backend remained one description of the product. Profiles, follows, public posts, conversations, membership, assets, receipts, expiry, search, and scheduled work all lived in Quarry. I did not have to introduce a second storage authority for media, a separate cache schema for offline use, or an application-maintained receipt protocol. That reduced the number of places where a change could be correct in isolation and wrong in combination. A disappearing photo, for example, was not merely a message hidden by a timer: its row deadline also governed search visibility and permission to fetch its bytes.

This was an independent build from the installed public packages. I read no Snapback source checkout and reused no prior Clique implementation. My comparisons below concern engineering patterns I know, not a controlled measurement of contemporary Convex or Supabase releases. I also have no fresh empirical comparison with earlier Snapback generations. It would be misleading to turn expectations about earlier designs into claims about releases I did not run. The meaningful observation is what this published generation let me express and what I had to discover while building it.

## Where the declared model paid off

The schema did useful work immediately. Unique handles, per-author writes, private conversation membership, bounded media types, and explicit sync audiences were close to the concepts in the brief. The same declarations produced generated client operations. Many familiar backend tasks became choosing the right relationship and predicate rather than writing transport handlers. Public feed activity could combine original posts and reposts while retaining their different identities. A direct-message pair could be deduplicated atomically with the creation of its two memberships. The generated receipt family supplied server arrival order and account watermarks, leaving the UI responsible for reporting what was actually visible.

Media was especially cohesive. Uploading created a handle; placing it on a row established its authorization home. Clearing the column, deleting its home, or expiring the row revoked access. A distinct once-only image column supplied a server-enforced consumption rule. The UI still had real obligations: opening explicitly, keeping the viewer above a recycled list, revoking its handle on close, and never treating metadata as permission to display bytes. But those obligations did not require an independently designed storage policy system. The closed-client expiry and direct asset-refusal tests gave stronger evidence than a disappearing bubble alone could provide.

Against the Supabase patterns I know, this avoided coordinating relational constraints, row-level policies, realtime subscriptions, storage ownership, cleanup work, and a separate offline synchronization layer. SQL would have felt more familiar for inspecting and joining data, and a large ecosystem of ordinary database tools is valuable. Here the benefit came from fewer independent mechanisms. It is not that those mechanisms cannot be built elsewhere; it is that this brief exercises their seams repeatedly, and Snapback made several seams engine responsibilities.

Compared with the Convex-style reactive application functions I know, Quarry asked for more up-front learning and less imperative implementation. Typed functions in a familiar language would have been faster to start writing. However, a backend function by itself is not a durable offline store, a receipt collection protocol, or an asset lifetime. Snapback's integrated client and server contract changed the shape of that work. The client still needed deliberate state ownership, but it did not need a new reconciliation algorithm invented for this app.

## Where the friction moved

The work was not frictionless. Quarry's types and rule language are small enough to learn, but they are not interchangeable with TypeScript or SQL. A reference is not a row. A nullable lookup is still nullable after a nearby human-obvious membership argument. A relationship expression valid in a query may not be valid in a write rule. Early corrections came from treating those distinctions too casually. The diagnostics usually named the source location and a concrete rewrite, and the served guide cards were useful because they addressed the exact construct I was authoring.

Prediction and completeness required more attention than ordinary CRUD development. The compiler could tell me that an operation remained eligible to predict, that it might queue outside acquired coverage, or that receipt-derived unread maintenance prevented prediction. These are different outcomes. The right UI response was not to force a local row into existence. The durable intent helpers let a pending message remain visible without assigning it a server ordinal, claiming membership authority, or presenting a fabricated receipt. That distinction became important when the unread model was added late in the build.

Search had a similar lesson. A word-prefix query could run against server-authorized data and acquired device history, but a finite sync window could not justify a claim to complete lifetime history. The app labels offline and partial results. This is a more demanding contract to explain than a simple loading/data/error hook. It is also more honest. The documentation exposed those boundaries instead of presenting offline behavior as a universal promise.

Several failures were ordinary product-engineering mistakes rather than evidence against the backend. Route-local feed selection reset across remounts until selection moved into the URL. A media viewer's test target appeared too late for the harness's element classification. A composer cleared a newer draft when an older asynchronous send completed. A notification preview initially read optional fields that were absent from an insert result. Tests assumed profile names and unique text that earlier choreography legitimately changed. Distinguishing these errors from platform limitations mattered; otherwise the diary would measure my first implementation choices as backend defects.

## Scheduled work and evidence

The digest was a useful test of whether the system remained coherent beyond live screens. A schedule invoked a job without a client. The job computed activity under each recipient's read authority, and a user/period emission key prevented duplicate admission. The worker used a completion ledger and an idempotent local provider receipt. Those are separate protections: admitting an effect once is not identical to delivering an external side effect once. Keeping that distinction explicit made the restart test understandable.

The scale adapter added another kind of discipline. It registered real users, uploaded real fixture media, submitted one action at a time, and waited for authoritative success. It did not count a pending local write as a settled replay action. A failed write receipt remained failed after I corrected the program; recovery required an explicit new intent rather than silently treating a retry as a fresh operation. Checkpoint verification compared fixture accounting with independent reads, and read probes paused the replay clock. These details are not attractive UI features, but they are essential to knowing what a large replay actually proves.

Relative to what I would hope to see improve across Snapback generations, this release's most valuable quality was the breadth of the published contract: generated types, focused diagnostic cards, ordinary offline search, receipt helpers, durable intent presentation, row-owned media, and supervised effects. I cannot attribute that breadth to a particular historical change without violating the cold-build evidence boundary. I can say that a package able to compile a declaration is only part of an application platform; this build depended equally on documentation explaining what an incomplete read, an unpredicted write, a consumed asset, and an external-effect retry mean.

The final scale verification also exposed an operational tradeoff: adding the completed aggregate model to the populated replay store required an atomic derived-state rebuild. The resulting read paths were fast in the local probes, but activating them was visibly longer work. This is a reason to plan deployment and adoption separately from ordinary request latency, especially where writes must wait for the new generation. It also distinguishes the convenience of a maintained declaration from a promise of cost-free evolution.

I would leave this build with confidence in the architectural fit and a cautious view of the surrounding product work. Snapback reduced backend coordination, but it did not remove the need for careful React lifecycle ownership, accurate tests, explicit offline presentation, and operational evidence. The resulting app is production-shaped, with real authorization and persistence, rather than a set of optimistic screen demos. That is the most important qualitative result. Performance and completion claims belong to the separate receipts and final report, including any limitations those artifacts reveal.
