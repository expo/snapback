All four tasks passed the full fresh-server acceptance using the installed published snapback4 0.2.29 pin. No package implementation, external backend, SQL, native code, raised ceilings, or other agent was used.

Run `npm run check -- --cost --residency`, `SNAPBACK_URL=http://127.0.0.1:PORT npm run seed:hub`, or `npm run acceptance`. Acceptance starts its own fresh in-memory dev server on an available port and terminates its recorded process group. Seed only talks to the supplied running URL. HTTP requests use `{args: ...}`; the transport preserves the native query envelope and rejects failed mutations.

The server returns all 99,090 hub matches in 50 membership pages and the sparse result in five membership pages, including empty groups. Each page has at most 20 groups. Nested matches are newest first. Membership rules exclude outsider rooms. Following returns 250, 25,000 and 250 posts for small, wide and celebrity in 13, 1,250 and 13 pages. Roster returns all 50 members in three pages. Unread is exact for hub (50,000), sparse and outsider. Every tested query page was complete, with no meter cuts.

Trending merges 25 hourly post-index lanes. Negative like counts and negative timestamps give descending likes and time while keeping logical keys ascending. Zero-like posts are present in the same index. Like changes update the source pair and post count in one transaction; repeated add/remove is idempotent. Acceptance verifies the initial top ten, excludes the old popular post, checks a zero-like window, adds 20 distinct likes to p000011, and removes one. The initial top-ten query examined 34 rows. Posting writes one source row regardless of follower count.

The only correction cycle was transport setup: an early request preceded readiness, and the initial raw argument body needed the documented/generated operation arguments inside the wire `args` envelope. The corrected client waits for readiness and checks denied/failed responses. The first compile passed; its complete cost and residency output is preserved in `evidence/checks/001.log`. No failed check output was discarded.

Chosen constraints and anticipated limits: each chat has a 256-message cap, permitting a complete nested collection; longer chats need another continuation design. Seed batches contain at most 128 inputs. Keys are limited to 80 characters, bodies to 4,000 and search terms to 100. Unread uses per-room maintained counts minus each membership's readOrdinal, relying on the brief's contiguous 1..N ordinal contract; deletion or sparse ordinals would require another model. Its membership walk is metered and has no continuation. Following rediscovers author lanes on every page and can exceed the opening meter at larger fanout. Search retains the engine's word, heap and output limits. Trending can spend its examined budget rejecting posts in the boundary hour. Cursors are live, not snapshots.

Stored derived facts are messageCounts.value, posts.negAt and posts.negLikes. Posts are publicly readable and have permissive update authority to permit likes from other viewers. Only the declared like operation updates negLikes; no operation takes a caller-supplied score. This is an application-maintained counter, not an engine-maintained aggregate. Seed mutations require the seed persona. Chat and author identities are represented through their fact rows rather than redundant identity tables.
