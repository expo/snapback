# Building Clique with the published Snapback 4 surface

The strongest impression from this build is that Snapback 4 moved work away from coordinating separate subsystems and toward describing the lifetime of data. A message was not merely a row with a text field. Its membership rules, receipt family, expiry deadline, media home, and replica policy were part of the backend declaration. That made several difficult product requirements surprisingly small in application code. It also made the distinctions between a submitted intent, an authoritative write, a held row, and a complete query answer central to everyday frontend work. This was an independent build from the public 0.4.13 packages, the published guide, and generated types. I did not inspect an earlier implementation or another backend checkout. The comparisons below are qualitative judgments informed by general backend knowledge, not measurements of competing builds.

Accounts and profiles established the pattern. Password identity, unique handles, owner-only mutations, and avatars fit together without a separate storage authorization service. The same pattern carried into messages: an uploaded image belonged to a typed column, and clearing that column revoked access to the bytes. In a Supabase-shaped implementation I would expect to coordinate table policies, object storage policies or signed URLs, and a local cache's invalidation behavior. A custom Postgres and Express service would make those boundaries even more explicit. Here the media home did much of that coordination. The application still had to own file selection, upload errors, playback, and the lifetime of visible handles. The platform reduced the number of contracts I had to invent; it did not remove the need to understand the remaining ones.

The messaging model showed this advantage most clearly. The receipt declaration supplied conversation ordinals, membership-at-send accounting, delivery progress, and read watermarks. The app had to report what was actually visible and foregrounded, but it did not need a bespoke receipt table and reconciliation algorithm. Expiry similarly began with an immutable captured deadline and an `expire at` declaration. It worked without an open client. View-once photos used a server-enforced bytes-once asset contract, while the client kept an explicit viewer above recycled message rows. These were product requirements that could otherwise consume a large fraction of a small team's implementation effort. In a Convex-style design, I would be comfortable expressing their server logic in TypeScript, but I would still need to design much of the device persistence, asset invalidation, and receipt behavior around those functions.

That convenience came with a learning cost. Quarry was readable, but it was not TypeScript with a different database client. I had to learn its reference types, module qualification, rule-hop restrictions, bounded lists, and query completeness model. Early mistakes included assuming a list lower bound was supported, using a rule traversal in the wrong form, and treating another file as though it did not qualify operation names. The compiler generally gave actionable feedback. Consolidating the backend into one schema module reduced namespace friction for this build, although a larger team would want a deliberate module structure. Familiarity with relational keys helped me model canonical DMs and unique reaction intents; familiarity with React helped me keep a draft and screen shell stable. Neither familiarity was a substitute for reading the current platform's contracts.

The local replica changed the shape of frontend engineering. A missing value could mean absence, incomplete acquisition, revalidation, or a denied read. Treating all of those as an empty array or a false toggle would create a deceptively simple UI. I had to keep pending state separate from protected read results, retain the composer through transient reads, and make already-submitted intent references survive a restart without creating a second outbox. The generated starter was useful here. Its account-scoped intent journal was a small, comprehensible example of UI bookkeeping that left replay ownership with the SDK. This was less application machinery than I would normally associate with a durable offline queue layered over a conventional server API, but it demanded more precise state handling than an online-only application.

The cold-media test made that precision tangible. Seeing an optimistic upload preview was not yet proof that the image had a download-confirmed durable home. My first test cut connectivity too early. Waiting for authoritative settlement and an ordinary online reopen produced a meaningful cold-start proof. Another test checked for history as soon as the shell and composer appeared, before replica hydration had supplied rows. Those were test and application-boundary mistakes, not evidence that media caching or durable history was absent. They are still real costs of using the system: the developer needs vocabulary and observability that explain why an apparently visible piece of content is not yet the same thing as durable acquired content.

I also encountered the bounded behavior of imperative replica reads. A one-shot read can decline to settle after several rounds of concurrent replica change. That is a useful fail-closed contract, but it was the wrong tool for my snapshot-style Trending screen. I switched Insights and Trending to the published online client arm, borrowing the account owner's current bearer. The server then owned the snapshot's freshness, while messaging and offline interactions retained their local-first path. Compared with Convex's reactive-query mental model, this involved more explicit choice of client arm and read lifetime. Compared with assembling a local database, transport, and cache independently around Supabase, the available choices were more integrated and better connected to the backend's authorization model.

Insights and the scheduled digest were a favorable second test of the backend. Maintained counts covered lifetime totals and UTC calendar buckets. Trending required a finite lower and upper time bound; the diagnostic explained why omitting the upper bound left a residual scan. The digest job could enter each recipient's read authority, page their inbox, and compute counts that excluded inaccessible, expired, tombstoned, own, and already-read messages. A committed period cursor and effect idempotency key made restart behavior explicit. The provider worker only logged the payload and deduplicated delivery. I did not need to add a client-triggered cron substitute or an administrator query whose authorization had to be reimplemented in JavaScript. This is where the declarative backend felt most cohesive.

Supabase remains an attractive mental model when the team's center of gravity is SQL, existing Postgres tools, and interoperability. Convex remains attractive when sharing TypeScript conventions across client and server matters more than minimizing bespoke offline behavior. A plain Postgres service offers still more freedom, at the cost of owning nearly every lifecycle described above. In this build, Snapback's advantage was the correspondence among rules, synchronization, media, receipts, expiry, and scheduled work. Its friction was concentrated in learning and correctly composing that correspondence. I would not translate those observations into a general speed ranking from one timed build, particularly because the frozen UI and choreography, browser startup costs, and my own test mistakes affected the elapsed experience.

My comparison with earlier Snapback generations is necessarily narrower. I did not run an older release, inspect its source, or reuse a previous build. The current guide contains migration-era distinctions, but those do not establish what a predecessor could or could not implement. What I can say about this release is that the published surface was sufficient to build the required behavior without opening a source repository. The README, keyword cards, `why` explanations, generated contract, and generated starter formed a usable development path. The least direct part was headless password registration documentation: the replay adapter used real browser signup and then the public typed client. That was valid and concrete, but less convenient than a clearly documented headless registration example would have been.

The scale replay is a separate empirical obligation. The adapter was exercised on the full action vocabulary before the fresh instance was started, and its execution records authoritative settlement, exact manifest checks, and public continuity probes. Hidden grader probes are deliberately not available to the builder, and native bundle export is not a simulator behavior proof. Those boundaries matter when interpreting success. The application milestones demonstrate that the composition works on the required fixtures and choreography; they do not erase execution limits such as the Following backfill horizon or prove every performance property at every workload. I would carry this project forward with the same distinction: keep the integrated backend contracts that reduced coordination, improve the compact timed-build source for maintainability, and investigate measured limits through explicit evidence rather than optimistic empty states or inferred guarantees.
