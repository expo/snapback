# Clique build diary

## M1 orientation notes (boundary entry follows verification)

The cold start began with the frozen instrument, then the whole published package README and the relevant served cards. I did not inspect another lane or backend checkout. The package supplied an Expo Router starter and a compact password/profile recipe. I replaced the starter product screens with the frozen UI kit, retaining its Metro/Wasm setup and documented app/device opener.

The schema was straightforward: built-in password identity, a public discoverable profile, owner-only writes, a unique handle, and an image whose access follows its home row. That removes the separate storage ACL work I would expect with a custom object-store integration. My initial friction was mostly self-inflicted: overlapping npm installation with scaffolding replaced dependency entries, and spreading a read row into mutation arguments carried unwanted fields. The latter was caught by the avatar acceptance case and fixed with explicit argument construction.

Published knowledge was enough for the initial UI. Prior React/Expo and relational-schema familiarity helped with screens, state ownership, and constraints; it did not establish any Snapback guarantee. I relied on current docs for those. The guide is terse about headless password-client setup, so the first seed driver deliberately uses the real browser signup and profile paths. The harness copy also needs adjacent metering files, which were not part of copying its directory alone.

Neither comparison measures a competing implementation. Hermes export and native execution remain distinct proofs here; only export is required and claimed.

## M6 — offline writes, push seam, and public API

Built durable queued-send presentation, queued like/reaction state, a real notification provider log, a token-only documented client and clean-install demo, and a 13-verb replay adapter. The adapter's 50-action conformance run used real signup and authoritative write receipts, then checked actual profiles, graph, posts/media, memberships, messages/quotes, and reaction state. The scale runner was authored here, with independent clocks, exact manifest checks, public continuity probes, and resumable receipt accounting; execution is deferred until M8 so its aggregate queries exist on the fresh instance.

The SDK's outbox, own-key interaction coverage, asset retention, and receipt helpers did the heavy work. The generated starter's account-scoped intent journal saved time: UI references could survive restart without inventing a second replay queue. The push worker needed little code; the absence-of-connected-client guard and durable effect delivery stayed in the backend. The clean Node demo worked with a bearer and the generated contract.

The test boundary fought more than the product path. An imperative read hit the documented four-round settlement limit during receipt synchronization. A cold-start assertion initially raced replica hydration. An image viewed optimistically was not yet a download-confirmed durable home; waiting for authoritative settlement and a normal online reopen made the cold-media proof meaningful. Those corrections are recorded, not treated as platform capability failures. Both cold restart and queued interactions now pass, as do suite and frozen choreography.

Prior familiarity with local-first state helped distinguish a pending intent, a server-accepted write, and a replicated row. The package explains those distinctions well, although its auth documentation led the replay adapter through the real browser signup surface rather than a documented headless signup call. Compared with Convex, the offline queue and media cache require much less application machinery. Compared with Supabase, receipt state, revocation-aware asset storage, and idempotent local writes are substantially more integrated. The cost is learning the SDK's acquisition and settlement model. Native evidence remains an iOS Hermes export, as requested; these extra cold-start behavior proofs ran on web, not a simulator.

## M8 — Insights, scheduled digest, and multiple devices

Built maintained lifetime totals and UTC daily activity buckets, a server-ranked finite 24-hour Trending query, visible account-wide unread state, and a scheduled digest with recipient-authorized reads, committed per-user period progress, and idempotent notification effects. The suite verified aggregates against independent read-only SQL, seven days including zero days, ranking and age/tie behavior, same-account edits/reactions, and a digest run with every client closed. The digest proof included expired/tombstoned and outsider-chat exclusions, inactive users, an idle next period, and a mid-period server restart. All frozen M8 choreography checks passed, including live same-account messages, cross-device read clearing, dual-offline order/no-duplication, and receipts. Hermes exported.

Maintained aggregates and `as recipient` inside the scheduled job were the easy parts. The guide gave an almost directly usable authorization shape, and the scheduler handled durable period boundaries without a client trigger. The harder part was choosing the correct client arm for a snapshot screen: a one-shot replica read of Trending could exhaust its bounded settlement rounds while the replica changed. Borrowing the current bearer for the documented online arm made freshness explicit. I also stopped unknown interaction state from appearing as an unliked/unreposted fact.

Most correction work was mine: a test raced account restoration after navigation, and a repeatability adjustment tried CLI `run --now` while a live server owned the store. The refusal was precise and admitted no work. The final age test verifies/reuses its real old fixture, creating and advancing one only when necessary. Prior SQL and job-processing familiarity helped design an independent count oracle and a restart-safe digest cursor. Current documentation supplied UTC bucket semantics and the finite ranked-window requirement; adding the upper time endpoint removed the sparse-window diagnostic.

Compared with Convex, I gave up TypeScript familiarity but obtained maintained counts, authority-scoped jobs, and the same durable replica model already used for messaging. Compared with Supabase or a custom Postgres service, I wrote less explicit orchestration among aggregates, schedules, notification work, and client invalidation. This does not establish comparative speed: no alternative was built in this session. The remaining empirical question is behavior at the full fixture envelope. The core replay adapter and its conformance proof were completed in M6; additional read-only roster/profile verification was added while preparing the M8-complete replay. Hidden grader probes remain outside builder custody.
