# Building Clique on the published Snapback 4 package

This was a cold build of a fairly demanding social messenger using the published `snapback4@0.4.7` and `snapback4-expo@0.4.7` packages. I used the package README, served guide, compiler diagnostics, and generated API types. I did not inspect another implementation or a Snapback source checkout. The comparison below therefore distinguishes what this lane demonstrated from general familiarity with other backend models. It is not a controlled performance comparison with Convex, Supabase, or an older Snapback release.

The strongest impression is that Snapback changed the unit of backend work. A table declaration described data, access, and the audience that could hold a local replica. A mutation described the authoritative transaction and, where local evidence justified it, the same operation's prediction. That connection mattered more than saving a few lines of CRUD. Clique needed private memberships, messages, receipt positions, disappearing content, and offline writes to agree. Having those concerns meet in one backend definition reduced the number of separate systems I had to make consistent.

That benefit was most visible late in the build. Insights totals, daily buckets, and per-member unread counts became maintained views. Message expiry became a server deadline on the row, rather than a timer owned by an open client. Notifications became transactionally recorded effects, with a small provider worker responsible only for logging delivery. The digest was a scheduled Quarry job that walked each user's memberships, counted the period's authorized activity, updated progress, and emitted with a recipient/period key. I did not write a separate application server to duplicate those rules.

The reduction in backend plumbing did not make the app automatically correct. The longest difficult stretch was media and reaction UI behavior. A transient read could unmount a row that owned an open viewer or picker. An earlier asynchronous mutation could finish and close a newly opened picker. Those were application lifecycle mistakes. Moving ownership to the conversation screen, using the documented retained-read option carefully, and closing the picker at submission addressed them. It would be misleading to attribute that entire stretch to the backend simply because it happened during a backend evaluation.

At the same time, the replica model made those lifecycle mistakes easier to encounter than a simplistic fetch-once screen would. Loading, held data, prediction, pending custody, and authoritative success are different states. A write can be durably queued without producing a local row. A list can contain useful held data without proving a complete answer. The UI has to honor those distinctions. Once I used the pending-write list directly, the offline interface became clearer: it could show an admitted message even when the local database could not predict it, without inventing another outbox or resubmitting an uncertain operation.

## Compared with Convex

From general familiarity, Convex's attraction for this kind of application is a familiar TypeScript function model combined with reactive queries and transactional mutations. I would expect the initial social graph and messaging functions to be comfortable to express there. Query-driven React rendering is also a familiar mental model. Snapback's Quarry syntax imposed more learning overhead: nullable lookups, reference paths, aggregate keys, cursor modifiers, and audience inference all have specific spellings and constraints.

The trade became more favorable as Clique's requirements moved beyond an online reactive app. Here the published Snapback client provided local replica storage, durable mutation custody, ordered reconnection, asset retention policy, and a native arm. I could define the backend behavior and then ask whether a device had enough evidence to execute it locally. In another stack, I would need to assess and assemble the corresponding offline pieces explicitly. This is a comparison of the work exposed by the chosen surfaces, not a claim that another product cannot support offline applications.

Snapback's aggregate declarations also changed how I thought about reporting. I asked for a count by author or UTC day, and read that maintained value. I did not have to place counter updates beside every application write. The cost is that the compiler's supported forms become part of the design space. My first grouped reaction scan was refused because the source inherited a private parent's audience. The eventual solution used bounded message-local reaction rows and complete aggregate keys. A TypeScript implementation might look more flexible at that point, but would leave more of the authorization and maintenance argument to the author.

## Compared with Supabase and SQL-centered backends

Supabase's SQL and row-level-security model offers a language and tool ecosystem many engineers already know. Independent verification in this lane was easiest when I could use the published read-only SQL command over my own application tables. It let me compare UI totals with stored relationships without trusting the same aggregate query twice. SQL familiarity also helped explain the backend structure: unique edges, membership joins, keyset pagination, and transactional updates were recognizable even when Quarry used a different syntax.

For a Supabase-shaped implementation, I would expect to make more explicit decisions about database functions, storage authorization, scheduled execution, realtime subscriptions, and offline persistence. Those decisions can be desirable. A team already operating Postgres may value direct control over schema evolution and operational tooling more than a unified authoring language. In this run, however, every integration boundary would have been additional timed work. The package's asset types, expiry rules, effect queue, and replica client removed several such boundaries.

The resulting control surface is narrower. Quarry is not arbitrary SQL, and its reference types do not imply general foreign-key cascades. I had to read the documented rules rather than assume familiar database behavior. I also hit the live-store writer exclusion while constructing an old-post test. The diagnostic was precise: no work had been admitted, and the owned server needed to stop before the offline CLI mutation. That was a useful operational guard, but it cost a correction loop because I had assumed a developer command could write alongside the running process.

## Offline systems and earlier Snapback generations

Firebase-style client SDKs are another familiar reference point: local observations and queued writes can make an app feel responsive before the network responds. Snapback's distinctive experience here was the connection between the backend's declared rules and what the replica could justify. The compiler explained when an operation would queue without a predicted row, and the client exposed custody separately from terminal settlement. Those are valuable distinctions for a messenger, where a premature “sent” label is a product bug rather than a cosmetic issue.

I cannot honestly claim a measured improvement over earlier Snapback generations. The cold-build restriction excluded their implementations and prior run notes, and I did not install them. The current documentation mentions compatibility spellings, such as older aggregate syntax, but that is not evidence of comparative reliability or effort. What I can say is that this published version exposed a coherent path across schema, rules, sync, assets, expiry, jobs, effects, and Expo. Any claim about how much better that is than a previous generation would need a separate comparable run.

The documentation was unusually useful when it supplied complete, relevant patterns: receipt ranges, expiring unread counts, provider idempotency, and scheduled digest sweeps. Exact diagnostics often led directly to the relevant guide card. Discoverability still mattered. I guessed an expiry keyword incorrectly, assumed a pagination property that TypeScript rejected, and initially treated a configurable choreography timeout as fixed. Those were author errors, but they illustrate why a concise public surface and navigable examples are important under time pressure.

## What the completed app establishes

The authoring milestones reached their required suite and choreography bar. Additional checks demonstrated server expiry without an open client, a browser restart with queued offline messages, and scheduled digest delivery across a backend restart with a quiet next period. Every required milestone produced an iOS Hermes export. An export is not a simulator proof, and this lane makes no such claim.

The separate full-scale replay is recorded on its own clock and fresh instance; its outcome belongs in the final report, not inside an authoring-green claim. A retryable transport refusal interrupted the first 50% verification attempt while the backend remained alive. Re-verifying the unchanged store passed, and the retained action journal allowed continuation without repeating workload mutations. I corrected the runner to distinguish verification failures from rejected actions and to keep the original clock through recovery. The adapter uses real password registration and settled authenticated operations. Its checkpoint verification compares stored counts and named fixtures independently, and its builder probes are distinct from hidden grader probes. This separation matters: a compact backend and a pleasant authoring path do not establish a scale envelope by themselves.

My overall judgment is that Snapback reduced the amount of backend coordination code substantially while increasing the importance of understanding evidence and coverage at the client boundary. It did not eliminate frontend engineering, test discipline, or operational care. For this app, the strongest advantage was that private data, local custody, expiry, and maintained state were parts of one model. The principal friction was learning that model precisely enough to avoid treating every temporary absence, queued operation, or partial answer as an ordinary online fetch result.

The completed replay ultimately matched every final invariant, and a fresh 100-conversation browser account acquired complete offline inbox and newest-page history coverage. The performance evidence is less categorical: endpoint ratios passed the builder checks, but search and Insights missed their interpolated mid-curve ceilings. Those small absolute timings came from a limited local sample, yet they remain failures of those measurements rather than results to discard. Correctness at the full corpus is established by this run; a clean performance-envelope claim is not.
