# Building Clique with the published Snapback 4 package

Clique made Snapback 4 feel like a system for placing application rules, rather than a database with a client attached. The strongest example was messaging. Membership, send-time recipients, receipt watermarks, expiry, local retention, and asset access lived together in Quarry. The React application still had substantial work to do, but it did not implement a second version of the backend in order to keep working offline. That changed where I spent my attention. I spent less time connecting services and more time proving that my data model gave the compiler enough information to make the right decision.

This is a qualitative account of this cold build, written before the report's numerical tally. I used the exact published packages and their documentation. I did not inspect another implementation or a Snapback source checkout. The comparisons below draw on general architectural familiarity with Convex, Supabase, and conventional server stacks; they are not timings from equivalent runs of those systems. I also cannot turn this session into empirical evidence about earlier Snapback versions. Where I compare generations, the comparison is about the shape of the authoring surface, not a claim that I reran an older release.

The initial schema was pleasantly direct. Password identity was a declaration, profile constraints were visible in the table, and a uniqueness failure could carry an application-facing message. The public profile and social graph were straightforward to expose. Having generated operations gave the client an obvious catalog. With a Postgres-and-HTTP stack, I would expect to separately wire credential handling, route validation, subscriptions, upload authorization, and a local storage strategy. Supabase supplies several of those pieces, but the application still has to decide how they compose. Here the common schema, rules, and sync declarations made that composition the default starting point.

That compactness did not remove modeling decisions. A timeline wants original posts separated from replies. A repost is an attributed event, not a copied post. Read receipts must refer to the intended recipient set, not whichever members happen to exist when a screen renders. Group removal must stop future delivery while retaining the allowed history. Those distinctions would matter with any backend. Snapback helped by making them executable in a single language, but it also exposed the consequences of a wrong choice earlier. A typed reference could select a parent-key scan when I intended an id lookup. A rule that was obvious to me could still be undecidable from a particular local key.

The diagnostics were most useful when they explained a structural reason and offered a concrete rewrite. I initially put a profile lookup inside the presence condition around a push emission. The compiler told me that this made sending ineligible for prediction. Moving the payload reads outside the guard restored the intended effect-only dependency. That is better feedback than discovering, after a mobile UI is finished, that a supposedly optimistic write has no local result. The cost of this feedback is that the author must understand the compiler's vocabulary: a bounded prefix, a held query, a maintained value, a source horizon, and a query that is incomplete are different things. They cannot safely be treated as synonyms for an ordinary array read.

Offline behavior was the clearest reduction in application plumbing. The device arm retained rows, ordinary viewed media, and ordered mutations. The same operations used online could be queued offline, and receipt state converged after reconnect. I still had to make the UI respect that lifecycle. One real failure was entirely in my composer: the predicted first bubble appeared before the send promise completed, and clearing the input afterward could erase the next draft. Changing the input timing fixed it. A backend that supplies durable prediction cannot make a component's asynchronous state transitions correct on its own.

Web cold start added another boundary. A replica stores data, not an HTML application shell. I exported the Expo web app and added a service worker for its own static assets. The cold-offline check then exercised restoration, queued messages, and synced search through the actual browser application. Native used the published Expo arm and produced Hermes bundles. I did not install and prove the native application in a simulator, so the native claim remains a build artifact rather than a demonstrated device lifecycle. That distinction matters more than whether an import or a bundler command succeeded.

Media also benefited from integrated policy. Ordinary assets, expiring references, and once-only photos could be modeled at the row where they belong. I did not need a separate presigned-URL service and a parallel database of permissions just to enforce the fixture's behavior. But a once-only fetch is not the whole UI contract. An already-open viewer must close when its message is deleted or its membership is revoked. I added that cleanup explicitly. Likewise, server expiry had to be checked with clients disconnected; a countdown on a screen would have produced a superficially convincing demonstration without establishing the required guarantee.

For analytics, maintained aggregates and recorded one-hop attribution were a substantial advantage. Lifetime totals and UTC day buckets became reads of server-owned summaries. Trending used a score on the original post and a merge of hour ranges, including zero-like posts and an exact trailing-window filter. This made the query's scaling argument inspectable. In a SQL system I would recognize the same underlying problems, but would choose among aggregate queries, materialized summaries, triggers, scheduled refreshes, or an additional read model. Convex would let me express the logic in familiar application code; I would still need to choose and maintain the aggregate strategy. Quarry's maintained forms made the strategy concise while narrowing the acceptable shapes.

That narrowing is a tradeoff. My separate reply table needed explicit attribution for engagement on nested replies. Treating every reference as though it reached an original post would have silently lost part of the total. The diagnostic and administrative inspection surfaces helped expose that mistake, but the correction was still application work: add the appropriate reference, backfill existing development rows through a Quarry job, and include those contributions. The convenience of a maintained counter does not absolve the author from deciding exactly what the counter means. I documented that the Posts total counts originals, while received engagement includes authored replies.

The scheduled digest brought several concerns together. The schedule had to come from the fixture configuration, the period and bucket anchor had to agree, unread counts had to respect current membership and expiry, and a retry could not emit another period's notification. Durable marker rows and the effect commit boundary made this understandable. The worker was deliberately small: it logged the payload and deduplicated a business key. During verification I made an operational mistake by restarting the backend while an intermediate schema edit was invalid. The new process correctly refused to start. Repeating the proof with a stable schema and a readiness check separated my orchestration error from the scheduling behavior.

The replay exercise was useful for a different reason than the UI tests. It forced stable mutation identities, authoritative settlement after each action, and independent reads of the resulting state. A queued promise could not count as acceptance. The published replay mode also supplied a clear notification boundary: application writes remain, new effects are suppressed, and schedules are held. I preserved an initial replay of the M6 program and started another fresh replay of the completed M8 program so the analytics reads could be measured at the fixture checkpoints. Those runs are evidence to inspect, not permission to make a broad performance claim from how responsive the starter app felt.

Compared with earlier, more SDK-centered ways of thinking about Snapback, this published surface puts much more of the application's behavior into a compiled backend language. That reduced the temptation to hide a rule in a React handler or a worker. It also made authoring less like unrestricted TypeScript and more like designing a small, bounded relational program. I would not infer any particular missing feature or improvement in an older release from this experience alone. The defensible observation is about this version: schema, authorization, replication, maintenance, and scheduling are close enough together that a change in one can be checked against the others.

The experience left me with a fairly specific preference, rather than a universal winner. For a product whose core is private realtime data, offline continuation, and media tied to row lifetimes, Snapback's integrated model removed important coordination work. For a team deeply invested in SQL tooling and a broader ecosystem of database integrations, Supabase's familiar foundation would still be attractive. For a team wanting server functions in its primary application language with reactive client reads, Convex would remain an appealing authoring model. A conventional custom server offers still more freedom, along with responsibility for every boundary shown here. In this build, Snapback's value was that those boundaries were visible and often shared between server and device. Its friction was the precision required to stay within that model, plus the ordinary frontend and operational mistakes that no backend can eliminate.
