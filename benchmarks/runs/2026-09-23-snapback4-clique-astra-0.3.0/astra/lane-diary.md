
## M1 — Accounts and profiles (2026-09-23 22:43 UTC)
Built password signup/login, session restore and server-confirmed logout, public live profiles, unique handles, every profile field, avatar upload and render, Expo Router shell, fixture segment replay, browser acceptance and Hermes export. The server model and its generated client types were straightforward. The same declared read rule governs avatar access, which removed a separate storage-policy task. The local client and React hooks made the other-client profile update work without authored polling.

Setup fought me more than the feature: shell Node differed from the overlay, a latest react-dom install conflicted with the starter's pinned React, copied choreography kept read-only modes and required sibling instrument dependencies, and setup identity required paths beneath its own directory. Familiarity with Expo, React and Playwright helped with these; no prior Snapback implementation was used. The published README's complete password/profile path was sufficient for M1. Compared with Convex or Supabase as I know them, built-in password auth plus media placement under the row rule felt compact; Quarry added a language-learning cost but very little server code. This is an experience comparison, not a measured competing build.

## M2 — Posts and follow graph (2026-09-23 22:55 UTC)
Built public posts with images/video, inline cards and media viewers, follow counts, likes, reposts, direct reply threads, Following and Global pagination, profile post lists, and idempotent M2 seeding. The declared timeline handles self membership, follow projection, and celebrity promotion; this is substantially less application machinery than I would normally write around a relational database. Global events still needed an application table because I initially guessed an unsupported cross-table merge. Replies remain separate from timeline originals.

The docs were unusually concrete about scale ceilings and replication cost. Generated types and accurate reference-type errors helped catch my accidental attempt to use a repost ID as an events reference. React/Expo knowledge helped more than backend familiarity in this milestone: retained Stack screens confused strict selectors, async navigation briefly exposed the previous feed, and Metro served stale content while CI was a truthy string. Slot composition and shared immediate tab state resolved navigation. Copied fixture-path assumptions required the documented input-only adapter. No missing backend capability has been established yet. Compared with Convex's ordinary indexed functions, Quarry asks for more explicit shape and bound declarations; compared with Supabase, policy and derived-feed behavior are more integrated, at the price of a specialized language and a capped timeline model.

## M3 — Messaging core (2026-09-23 23:04 UTC)
Built deduplicated DMs, distinct groups, membership management, send-time recipient sets, server-arrival ordinals, delivered/read watermarks, typing expiry, quoted replies and jump, and retained history. The entire backend remains Quarry. The published ordinal and typing examples supplied useful design guidance; membership-scoped sync and delivered-history retention saved a substantial amount of custom client filtering and cache logic. The complete two-client choreography passed, including group receipts and removed-member cutoff.

I tripped over a reserved column name, nullable membership reads, and using empty word search as a people browser. The compiler explained the first two; choreography exposed the empty picker. Metro's missed new routes continued to require an explicit restart. The tricky work was deciding receipt semantics and when a client counts as having fetched versus viewed content, not writing a transport. Relative to Supabase I avoided a separate realtime channel protocol; relative to Convex I got durable local history from the platform, while still having to author the application-level receipt model. No prior repository implementation or earlier benchmark helped this build.

## M4 — Media, reactions, edits and deletion (2026-09-23 23:10 UTC)
Built image/video messages with inline recipient rendering and playback, reaction set/replace/clear, caption/text editing, and delete-for-everyone. JSON configuration is compiled into Quarry helper constants; the server compares its own commit time with the original message time. Clearing the asset reference on deletion immediately denied a fresh recipient asset fetch. A real 61.5-second wait also produced EDIT_WINDOW_CLOSED, independently of UI affordances. Browser choreography and the Hermes export passed.

Assets were the easiest part: upload facts are validated once and placement carries the row's policy. I did not need a separate signed-URL service or revoke list. Reaction maintains inherited the membership audience when that key survived grouping, with a diagnostic explaining the replication cost. One suite mistake treated an optimistic rendered image as proof of remote settlement; I changed it to wait for the receiver's authoritative history. This distinction is valuable but asks the author to understand the client contract. Against the alternatives I know, the integrated policy/asset path is attractive; Convex/Supabase familiarity did not remove the need to learn Quarry's prediction versus settlement boundary.

## M5 — Privacy, appearance, and search
Built chat color/background/name controls, administrator-managed disappearance, one-fetch photos, scoped and global message search, and held-replica offline search. Both acceptance and choreography pass; a separate client-free timer verified authoritative expiry and search removal. The expiry declaration and one-fetch asset column made the privacy mechanism concise. Search needed an explicit local held query and empty-prefix people browsing required a separate branch. Familiarity with server-owned TTLs helped avoid relying on a screen timer. I initially missed a private-sync index and corrected it from the diagnostic. Compared with Supabase, the local search and TTL contract is much more integrated; compared with Convex, declaring replica retention and asset policy beside the table is a meaningful difference. Native behavior is bundled, not simulator-proven.

Built authenticated Node API documentation/demo, the durable logged push effect, all 13 action-log verbs, deterministic retry ids, sample state verification, and a separate fresh replay host. The scale run has its own fresh store and clock; its result is still pending at this boundary.

## M8 — Insights, scheduled digest, and two devices
Built server-maintained lifetime and UTC-day statistics, a bounded hour-lane Trending merge with exact rolling-window filtering, and a config-driven scheduled digest. The digest uses the same membership authority as chat history, live expiry-aware reads, durable per-user/period markers, and provider-side deduplication. Added online snapshots and pull-to-refresh for analytics, cross-device unread rows on Home, and explicit transient-viewer cleanup on deletion or membership loss. The suite, choreography, full earlier-suite regression, and real-clock digest restart/empty-period proof pass. The native Hermes export is rebuilt.

Maintained fields and one-hop recorded attribution made the aggregate work unusually short. The difficult part was understanding when a typed reference selects a parent index rather than an id lookup, and accounting for nested replies stored outside the original-post table. I added an explicit reply target and a Quarry backfill for existing development data. That is analytics attribution, not M7's intentionally deferred message-count migration. A restart test overlapped an invalid intermediate edit and failed to start the host; that was my orchestration error, and the rerun held the schema steady and checked readiness.

Familiarity with SQL indexes, idempotent scheduled work, and replica queues saved design time. The package examples were helpful but needed adaptation to the actual application's tables; copying a recipe without following its invariants would have been unsafe. Compared with Supabase, fewer moving parts were needed for sync and expiry. Compared with Convex, the compiler makes work bounds and on-device eligibility much more explicit. This also created more opportunities to choose the wrong prefix or confuse an aggregate's scalar with its page. The final-program scale replay remains on its separate clock so Insights and Trending can be measured at the same fixture checkpoints. No native simulator or independent grader result is claimed.
