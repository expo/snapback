# Building Clique on Snapback 4

This was a cold build from the published packages and their public documentation. My strongest impression is that Snapback changes where application complexity lives. Accounts, authorization, synchronized data, maintained counts, asset ownership, expiry, and scheduled effects can be expressed close to the data model. That removed a substantial amount of glue I would normally expect in a social messenger. The complexity returned at the boundary between that model and a mobile interface: what the device knows, what a local mutation can predict, what has actually entered the durable queue, and what should stay visible while those states change.

I am writing this after the continuous application milestones, before tallying the final numbers. The full replay is executing separately against a fresh instance. This essay is about the engineering experience, not a claim that this run establishes a performance ranking. I did not build the Convex or Supabase versions alongside it, and I did not inspect another implementation. Comparisons below come from my general knowledge of their programming models. Native runtime behavior also remains outside the evidence available here: Hermes exports succeeded, but the Linux host cannot execute the requested Apple simulator witnesses.

The initial account and profile work felt unusually compact. A Quarry identity declaration, a profile table, uniqueness, validation, and asset fields gave me a coherent backend boundary. I could use the same declared operations from the app and a headless fixture client. I did not have to invent an upload proxy or write a second ownership system for stored avatars. With Supabase I would expect to make those decisions across SQL schema, row security, auth integration, and storage policies. Those are familiar, individually useful tools, but the joins between their guarantees still belong to the application engineer. Snapback made more of those joins part of a single declaration.

Convex is a closer comparison in the feeling of an integrated application backend. Its reactive query model and server functions offer a familiar place to put business rules. Quarry asks for a more declarative expression of those rules, and it rewards knowing its access paths. A nested roster predicate that looked natural to me did not bind the conversation the way I intended; an explicit helper did. I also guessed at syntax more than once and received accurate refusals. These were not evidence of broken semantics. They were evidence that fluency in TypeScript and SQL does not immediately become fluency in Quarry.

The compiler's explanations were a significant benefit. It told me when a query could never claim completeness, when a mutation would not predict locally, and when maintained values would stream a whole parent row. Those messages made costs and limitations visible before they became mysterious production behavior. The distinction between a row missing from a local horizon and a row absent on the server is especially valuable. An application that quietly treats both as the same thing can appear correct on small data and fail later. Snapback makes the distinction harder to ignore, although the interface still has to translate it into something a person can understand.

Feeds and counters illustrate the tradeoff well. Maintained Following delivery and aggregate counts kept bookkeeping out of my mutation handlers. I did not write a chain of increment/decrement code for every screen that displays a count. In a Supabase implementation I would likely choose between SQL aggregation, triggers, materialized structures, and application fan-out according to the workload. In Convex I would still need to choose explicit data structures and update them in server functions where appropriate. Here the backend could derive much of that work from declarations. The price was learning the materialized delivery shape and accepting the compiler's warning that convenient count columns have streaming consequences.

Messaging exposed more of the distributed system. A sent message needed a send-time recipient set, monotonic account receipt watermarks, and current membership checks. A removed group member also needed to retain already delivered history without regaining access to new messages. That was more precise than simply subscribing to a messages table. The held-query facility was useful because it described the retained local state honestly, without pretending that the ordinary authorized server query still applied. I had to separate that shape from a richer query whose receipt calculation depended on membership information the removed person could no longer read.

The local replica was the most valuable capability and the largest source of integration work. Offline search and queued mutations were available without my choosing another local database and synchronization protocol. But an interface cannot treat every local result as an ordinary settled server response. Temporary query states unmounted interactive message bubbles until I retained valid results. Pagination needed explicit accumulation. A direct-message route originally tried to create or resolve its conversation through an online operation after every load, which stranded an offline reload on an opening screen. Resolving the held membership locally fixed the application mistake.

My most instructive error was in pending-send presentation. A required time-window test advanced server time far beyond device time. Locally predicted messages could then fall outside the latest chronological page even though the user had just sent them. I added small persistent presentation references so those intents stayed visible while Snapback continued to own the durable queue. I initially used UUIDs as SDK write IDs where the published contract required minted IDs. The package correctly rejected them. Worse, my UI briefly treated failed references as pending. The eventual correction was to make admission and recovery explicit through the actual write receipt and journal. The extra browser cold-restart proof was worthwhile because it caught a misleading interface that simpler same-session tests had not exposed.

This is an area where an integrated offline backend changes the work rather than eliminating it. With Supabase alone I would expect to choose or build an offline write queue, local storage model, conflict policy, and reconnect protocol. With Convex, I would also need to consider the particular persistence and offline guarantees supplied by the chosen client architecture. Snapback brought those mechanisms into the package, but I still had to represent their states correctly. The right comparison is not just how many server functions disappear. It is whether the whole application has a clear, testable story for an intent before admission, during disconnection, after restart, and after server refusal.

Media and lifecycle rules were comparatively pleasant. Permission-bound asset serving, expiry, and one-view consumption had useful backend support. View-once was enforced at the asset endpoint, not merely by hiding a button. Normal viewed media could use the package cache while once-only bytes stayed out of durable storage. The browser proof itself needed care: an image element being visible did not mean its bytes had decoded before I disconnected the device. That failure belonged to my test synchronization. The final proof distinguished a retained normal image from unavailable once media after an offline reload.

Scheduled digest work made the integrated approach look especially strong. The job could read authorized account-related facts, compute the period's useful changes, and emit an effect with a durable once key. I then used an isolated backend and worker to cross a real schedule boundary after a restart, verify recipients, retry the job, and observe an idle next period. In a conventional PostgreSQL and Express stack, I would own more decisions about job scheduling, leases, the transactional outbox, retry identity, and provider delivery. Those tools offer flexibility, but keeping their failure boundaries aligned is work. Snapback provided a narrower path that matched this requirement well.

The surrounding tooling was less frictionless than the backend declarations. The frozen browser harness lacked a helper module, so I supplied a documented loader shim without changing its assertions. React Native Web omitted some neutral accessibility values expected by the UI contract, requiring a model-driven presentation bridge. Static web exports were more dependable for this run than the development bundler behavior I encountered. These issues matter to the total experience, but they should not all be attributed to the database. Likewise, the native witness refusal is an environment limitation, not a passing native test and not evidence of a Snapback runtime defect.

I would leave this build with confidence in the value of the integrated data model and with more respect for the client-state discipline it requires. Quarry reduced the amount of imperative backend plumbing, and its diagnostics often explained the relevant constraint clearly. It also introduced concepts that I had to learn rather than approximate from neighboring systems. The result is attractive for an application whose offline and authorization requirements fit those concepts. The remaining decision for a production team would include operational experience, deployment requirements, native testing, and measured behavior at its own workload. This single cold build offers concrete evidence about authoring and verification; it does not settle those broader choices.
