
## M1 boundary
Built password accounts, expiring/revocable sessions, profile validation and unique handles, fixture avatars, live public profiles, Expo Router screens, and the browser acceptance suite. Quarry's identity declaration and asset ownership removed substantial server plumbing. The compiler accepted the first profile schema. The UI fought me: an optimistic row unmounted onboarding before a refusal could render, and CI Metro served stale code. Stable editor navigation and static exports resolved those agent mistakes. The instrument snapshot also lacked its JSON-schema helper; an explicit AJV loader supplies validation without changing assertions. Prior React familiarity helped with state lifetime; no prior Snapback implementation was used. Compared with Supabase, there was less session and storage-policy wiring; compared with Convex, the local replica made optimistic lifecycle behavior more visible. No native simulator claim is made. The iOS Hermes export exists.

## M2 boundary
Built text, multi-image and video posts, direct replies, likes, reposts, public profiles with counts, Following and Global, and scrolling pagination. The schema compiled without a correction; the maintained feed and counts reduced application bookkeeping. Web UI integration was considerably harder: picker behavior, omitted accessibility values, persistent navigation assumptions, and accumulated pagination all required correction. One test run was contaminated by my concurrent suite execution and was discarded. The final suite and choreography passed sequentially. Explicit accumulation over local-client queries works where my usePage integration stalled; this remains ambiguous rather than an asserted platform defect. Published diagnostics clearly disclosed whole-parent streaming for maintained counts. Familiarity with relational feeds helped, but Quarry's materialized Following shape required its own guide. Compared with Supabase, automatic delivery avoids application fan-out plumbing; compared with Convex, the declarative shape is more constrained and the local query layer adds another place to diagnose UI behavior.

## M3 boundary
Built unique DMs, groups, roles, membership lifecycle, messages, quoted replies, typing and monotonic per-account receipt watermarks over send-time recipient sets. Suite and choreography passed, including sender identities, removed-member cutoff and retained history. The declaration language gave useful prefix/cap diagnostics: a nested roster predicate needed an explicit helper binding. Two sync lines were my unsupported guess. Typing through a durable queue was the wrong application choice; throttled ephemeral requests solved the timing problem. Membership writes needed keepalive across hard page navigation. Retained history required a separate held query because the ordinary receipt shape depended on no-longer-readable membership. Prior messaging experience helped with recipient-set semantics; the distinction between held and authoritative reads was new. Compared with Convex, there is more local-replica reasoning; compared with Supabase, authorization and sync stay close together in one schema. These benefits did not remove the need for careful UI lifecycle handling.

## M4 boundary
Built image/video messages, captions, emoji replacement/removal, author-only edits and tombstones with server windows generated from the supplied config. Native Hermes and web exports succeed; suite and all five choreography checks pass. Asset sniffing and permission-bound serving were straightforward. UI lifecycle fought me: draft clearing raced later input, asynchronous media viewers needed stable containers, and transient query states could unmount interactive bubbles. Retaining valid results and paging fewer initial messages resolved the observed failures. Familiarity with async forms helped; the local query state lifecycle required more care than expected. Compared with Supabase, there is much less asset authorization plumbing. Compared with Convex, the local replica has more states to handle. I have not proven every transient timing failure was caused by one issue, so ambiguous failures remain labeled that way.

## M5 boundary
Built server expiry, one-view photos, member-synced chat color/background and group identity, plus three indexed search scopes. All required suite assertions and all four implemented choreography checks pass. An additional direct API check and a warm-offline search check confirm expired content disappears. One-view consumption is enforced at the asset endpoint, not a client flag. The published expiry and search cards mapped closely to the brief and saved substantial implementation work. React Native Web observability again fought the integration: selection and a nested image source needed neutral semantic attributes. Background bytes and colors had synced correctly before those corrections. Prior relational authorization experience helped with group-admin gates. Relative to Supabase, built-in local indexed search is a major reduction in separate infrastructure; relative to Convex, the same query on server and device is attractive, with additional coverage/horizon states to expose honestly. Native behavior remains unproven on this host.

## M6 boundary
Built the logged push provider seam, a documented headless API and working demo, replay support for every frozen verb with authoritative per-action receipts, checkpoint verification and probe orchestration, and offline queue behavior using the package's persistent device arm. The suite and browser choreography pass. The 50-action sample was also checked against actual profiles, posts, media, memberships, message counts, quotes and final set/clear state. A retry exposed my incorrect assumption that an idempotency key would tolerate newly uploaded asset IDs: E_ID_REUSED was correct and helpful. Keeping the original media reference fixed it. Removing the redundant reaction key made its insertion predictable. Worker effects and built-in replay suppression were easier than maintaining a separate trigger/outbox stack in Supabase. Compared with Convex, the local queue and prediction are additional built-in capability, but require understanding which unique keys prove local authorization. The native witness explicitly refused Linux; no native offline guarantee is claimed. Full scale execution remains on its own later clock against the completed schema.

## M8 boundary
Built account insights with six server totals, seven zero-filled UTC days, rolling ranked trending posts, and a scheduled per-user digest with durable once keys. The final suite and two-client choreography pass. An isolated backend/worker proof crossed a real scheduled boundary after a backend restart, verified every active recipient and an idle account, retried the same job, and observed no next-period idle emission. A separate browser proof survived offline reload with two admitted pending sends, normal cached media, excluded once media, and queued likes/reactions that settled after reconnect. Native witness again reported unavailable on Linux; these browser checks are not native proof.

Maintained aggregates and scheduled effects felt easy and kept computation off the screen. Offline presentation fought me. The handle route needed a held local membership lookup; pending intents needed visible references when a deliberately advanced server clock put locally stamped predictions outside the current history page. I initially supplied UUIDs where the SDK required minted write IDs, then let failed references look pending. The package correctly refused that mistake. Recovery now consults the actual SDK journal, and the small app journal only preserves presentation references. Media proof also needed to wait for decoded bytes rather than merely an image element. Prior experience with durable queues and React lifecycle helped once the states were explicit. Compared with Convex and Supabase, the integrated replica reduces infrastructure but demands more knowledge of local coverage, prediction eligibility, and queue admission. Documentation for those concepts existed, though it took several readings to turn it into correct UI behavior. Full scale replay starts next on its own fresh-instance clock.

## Replay and closing evidence
The full fresh-instance replay settled every frozen action and matched the combined invariant manifest at both checkpoints and at completion. Exact public-API paging and application-table counts agreed. My first attempt omitted the probe warm-ups/deadlines, so I retained it and restarted from an empty instance. Reporting also uncovered an overwritten M5 suite receipt; a fresh passing choreography run restored the hash linkage.

The full-data browser exposed an important limit that the smaller milestone fixtures did not. A fresh user could render the feed, but initial replica acquisition exceeded the thirty-second observation deadline. The residency tool made the reason concrete: the public sources and engine-owned Following structures form a large acquired partition. The published feed guide says a small page does not bound acquisition, and an isolated attempt to add a source horizon was correctly refused with E_TIMELINE_SHAPE. I have kept that performance failure visible rather than marking a longer wait green or changing the verified corpus. This materially qualifies the convenience described in the earlier essay: the built-in materialized feed shape couples efficient server reads to broad device residency. I did not prove that every alternative feed architecture is impossible, and I have not labeled the documented constraint a runtime defect. Native performance remains unknown on this host.
The separate longer cold-sync observation also timed out. I retained its failure and heap samples, and left the thirty-second criterion unchanged. This remains a concrete scale limitation in the delivered build, despite passing corpus invariants and API probes. A separate Expo export-cache issue initially pointed the scale browser at the wrong backend; clean exports corrected that environmental mistake before the real cold-sync observations.
