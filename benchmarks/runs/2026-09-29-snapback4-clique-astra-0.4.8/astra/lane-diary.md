
## M1 boundary
Accounts, exact profile fields, unique handles, replaceable avatars, persistent sessions and logout now work through the Expo Router client and frozen kit. The suite and two-client choreography passed, and the iOS Hermes export exists. Built-in password auth and asset placement were straightforward; no password code was needed. My profile form initially passed a whole generated row into a narrower mutation, correctly rejected as E_INPUT. Tightening the URL column after seeding also met an explicit adoption refusal, resolved by validating at the mutation boundary. The copied read-only harness and shell's unexpected Node version added environment work. Familiarity with React controlled forms and Expo helped; Quarry was learned from this package. Compared with a typical Supabase app, row rules and sync live in one declaration; compared with Convex, the client ownership and local replica require more deliberate setup. No conclusion about later messaging/offline behavior is warranted yet.

## M2 boundary
Posts now support text, two/four-image compositions, uploaded video with browser-generated poster and playback, follows, likes, reposts, direct replies, and paged feeds/profile posts. The suite and complete choreography segment are green; the Hermes export includes native video playback. Schema authoring was direct, especially engine-owned counts and asset lists. The harder work was publication timing: separate author reads briefly exposed incomplete cards, a state-loading branch dropped button presses, and Expo's preserved routes exposed duplicate automation surfaces. Those were application mistakes. The published materialized Following contract is asynchronous; the instrument's immediate baseline observation exposed that distinction. I switched the UI reader to the published planned current-state query and retained its N_SPARSE_FILTER certificate as a scale risk, not a proven scale failure. Familiar React experience helped diagnose the route/controlled-state bugs, while the feed guide supplied the backend model. Convex would also require careful UI readiness, but its server query model would make the immediate projection simpler; Supabase would require explicit joins, counters, and a subscription invalidation policy. Here the unified local interpreter removed hand-built caching, while its coverage/publication boundaries required more attention than a simple remote query.

## M3 boundary
DM deduplication, three-person groups, admin membership changes, retained history after removal, typing, ordered messages, quoted replies, unread state and delivered/read receipts are implemented. The suite and required choreography passed; an optional avatar probe skipped in the final run after passing earlier runs. The iOS Hermes export succeeded. The published social starter and receipt recipes saved substantial design work, especially the interval-based delivery reports. Local query loading was the difficult boundary: one-shot route resolution mistook loading for absence, and reactive resolution then remounted the conversation during refresh. Keeping a resolved route ID stable fixed drafts and retained-history continuity. A repeated quote test also needed its own unique origin. These were application mistakes rather than demonstrated platform defects. React familiarity helped isolate them; I had no previous Quarry messaging code. Compared with Convex, the receipt protocol is more elaborate but supplies local delivery semantics; compared with Supabase, the declarative membership partitions remove much custom subscription and cache invalidation work. The docs had the ingredients, though a complete route-resolution example would have prevented friction.

## M4 boundary
Photo/video messages, editable captions, one-per-member reactions with replace/remove, server-time edit/delete windows, tombstones and byte revocation are implemented. The suite (including a real 60-second edit refusal) and every choreography check passed, with a fresh Hermes export. Built-in asset ownership made revocation easy: clearing the column was sufficient. The generated Quarry constants preserve both production and shortened fixture configs. My first reaction grouping was unbounded; the compiler correctly required pagination. I chose full reaction acquisition per held chat after windowed decorations produced repeated incomplete reads, recording that residency tradeoff for scale. UI lifetime ownership fought me again: selected media and reaction pickers belonged above transient rows. A harder failure came from global row action buttons: the harness's long-press fallback selected an older message and the server correctly rejected its expired delete window. A proper selected-message action menu fixed that. These were mostly application errors, not evidence of an asset or timing defect. React and browser event knowledge helped; the media and read-through guides supplied the backend semantics. Convex would need explicit storage authorization/revocation wiring; Supabase would need storage policy and object lifecycle coordination. Here those were declarations, while local publication and interaction ownership demanded careful UI work.

## M5 boundary
Disappearing settings capture immutable server deadlines on future messages, one-view photos use per-principal asset consumption, chat name/description/color/background settings are wired, and people/in-chat/global grouped search works online and warm-offline. Both the suite's three-minute closed-client expiry test and the choreography's independent five-minute cycle passed; previously served bytes were refused and durable/offline search purged the message. The Hermes export is confirmed bytecode. This milestone was noticeably easier: expire-at, once assets, and indexed normalized prefixes directly matched the product. The published sequence guide supplied a server-only initial blocker read so delivery prefixes can cross expired ordinal gaps. The primary correction was my persistent-browser test racing hydration and missing sign-in. A minor React Native type change required moving pointerEvents onto a View. Familiarity with component lifetime cleanup helped keep viewers and quote/edit state safe through expiry. Compared with Supabase, the deadline and byte lifecycle avoid hand-built cleanup jobs and storage revocation logic; compared with Convex, client-local expiry/search are part of the same query contract rather than a separate cache. The remaining tradeoff is honest incomplete coverage: offline search reports device holdings rather than pretending it has the full server corpus. No required M5 platform capability was missing in this run.

## M6 boundary
Built a live push effect worker, documented custom-client API and standalone demo, durable send references, and the complete replay adapter with fresh-instance execution driver. The 50-action sample and stored-state checks pass, as do the suite, offline choreography, and Hermes export. Explicit mutation IDs made replay accountability easy, but the avatar retry taught me that identity includes the exact asset argument. Offline membership loading fought the composer until I stopped treating temporary uncertainty as permission denial. Familiarity with outboxes and idempotency helped; the published starter supplied the native SQLite custody and settlement recipe. Compared with Convex or Supabase, owning queue replay in the SDK saves considerable application infrastructure, while explicit read completeness requires more careful UI state handling. Full scale execution remains on its separate clock after M8, so aggregate probes can run at all checkpoints.

## M8 boundary
Built server-maintained lifetime and UTC-day Insights, ranked trailing-window Trending, a real two-minute digest schedule with an idempotent worker, and deeper multi-device/offline behavior. Suite and choreography pass, including a separate persistent-browser offline restart and isolated real-clock digest restart/quiet-period proof; the native artifact is an iOS Hermes export. Aggregates and jobs were pleasantly direct in Quarry. The difficult parts were UI boundaries: a DM alias depended on an online-only key, the home needed an inbox surface, transient reads cleared rows, and predicted like state raced a fresh Insights read. The documented keep option and explicit server-settled like state resolved those cases. General distributed-state experience helped more than framework familiarity. Compared with Supabase, the maintained read models and scheduling avoided trigger/worker glue; compared with Convex, the server model felt less general but the replica and asset lifecycle were much more integrated. I have no cold-run evidence for an earlier Snapback generation, so that comparison remains architectural rather than empirical. Additional replay-adapter hardening happened in this M8 interval and is recorded as such.
