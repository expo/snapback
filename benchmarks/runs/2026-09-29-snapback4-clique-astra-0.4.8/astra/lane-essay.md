# Building Clique with the published Snapback 4 surface

This was a cold build against `snapback4@0.4.8` and `snapback4-expo@0.4.8`. I used the published README, generated starter, CLI guide, diagnostics, and generated application API. I did not inspect a Snapback source checkout or another lane. The comparisons below are architectural judgments informed by general model knowledge of other backends, not measurements from a parallel Convex or Supabase implementation. The milestone application is complete; the separately timed scale replay was started before this essay, and its quantitative result belongs in the final report. I wrote this assessment before tallying the run's numbers.

The strongest feature of this backend is how much behavior can be expressed in the same place. A message is a row with a membership rule, an ordinal, an expiry time, a sync policy, and references to assets. Those declarations participate in server execution, local reads, pending writes, and media authorization. That made it possible to build a messenger without independently designing a server database, a local database schema, a replication protocol, a media ACL service, and an offline outbox. Those are usually separate engineering projects, even when the initial application is small.

That integration also changed where the hard work appeared. A substantial part of this build was learning exactly what a read result meant. A missing local row could mean absence, incomplete acquisition, a history boundary, a pending write, or an unavailable server fact. Treating those states as interchangeable caused real defects: a transient lookup unmounted a composer; an unavailable membership disabled an offline send; an online-only DM lookup prevented an otherwise durable conversation from reopening offline. The application needed stable ownership of drafts and routes, while displayed protected rows needed to follow the SDK's read lifecycle. The result was better than a collection of ad hoc caches, but it demanded more care than an ordinary fetch-and-render prototype.

Convex is the closest conceptual comparison for the reactive server portion. Both approaches encourage describing application reads and writes as operations and then letting the client subscribe to the resulting state. With Convex, I would expect to spend much of the authoring time in familiar TypeScript functions and indexes. Quarry substitutes a smaller language with explicit rules, bounds, maintained views, and replication declarations. For the relationships in this brief, that smaller language was often productive: membership checks, set-state reactions, follow edges, and aggregate counters are concise and inspectable. The compiler could explain why a read or prediction was unsafe instead of leaving the mistake to an integration test.

The tradeoff is that familiar programming habits do not always translate. A nested projection needs the right parent scope. A convenient upsert on a read-through child can be server-only even when the source rows are locally held. A filtered feed that is acceptable for a small corpus can have a very different scale certificate from the materialized reader view. These are not incidental syntax issues. They are part of the platform's execution model. Convex's general-purpose function surface would make some rewrites feel more familiar, while requiring more application decisions about local persistence and offline replay. In this run, Snapback provided much more of that client machinery, but the developer had to understand when it could safely operate.

Supabase would offer a different set of strengths. The public social graph, unique identities, membership tables, and analytics all fit a relational database well. SQL, constraints, indexes, row-level policies, and ordinary inspection tools would give a broad and familiar foundation. The cost would be assembling the rest of the system: realtime subscriptions into a coherent screen state, a durable client outbox, conflict handling across devices, receipt progression, media revocation, and scheduled work with idempotent delivery. It is possible to build all of that, but the consistency story is spread across database definitions, application code, and client storage. Here, Quarry put much of that story beside the schema.

Media made that difference especially visible. The brief required real uploads, inline images and video, expiring content, and one-view photos. A storage URL alone is not enough to meet those requirements. The application must distinguish acquiring a handle from viewing once, close viewers when the row changes, and avoid retaining a protected snapshot just because a component has a local state variable. Snapback's asset references and one-view primitive reduced the amount of custom backend code. I still had to lift viewer ownership above recycled rows, implement the native and web picker paths, and test actual byte refusal. The important reduction was in backend mechanisms, not in the need for lifecycle-aware UI code.

The scheduled digest was another clear reduction in glue. It is a Quarry job sweeping profiles and counting through each recipient's current memberships. The schedule supplies the period, the job records the emission key with its work, and a small worker logs the payload through the same seam used for message pushes. An isolated test closed all clients, restarted the backend within a period, checked the emitted counts, and then waited through an inactive period. That is a more convincing test than invoking a digest function from an open page. In a Supabase-shaped implementation I would expect to arrange database scheduling and a worker or function boundary; in a Convex-shaped implementation I would expect scheduled functions and an external delivery action. Snapback made the database side unusually compact, though the worker still needed provider-level deduplication and operational supervision.

Insights were straightforward once I found the maintained aggregate forms. Lifetime totals and UTC-day buckets do not require the client to page all posts. Trending uses the post's maintained like count and a server-time window. The more interesting difficulty was the boundary between optimistic interaction state and an explicitly fresh Insights read. A predicted like icon could change before the server had accepted the mutation, and the choreography immediately reloaded Insights. I made likes visibly queued until acceptance and stopped rendering unknown interaction state as false. That was an application correction, not a missing aggregate capability. It illustrates how a local-first client can expose timing mistakes that a server-only prototype happens to avoid.

The tools were useful when they gave a concrete rewrite. `check`, generated types, operation explanations, and the focused guide cards kept the backend authoring loop short. The generated social starter was valuable for the online presence arm, one-view media ownership, saved send references, and native SQLite custody. Diagnostics were less useful when repeated `EMPTY_READ` messages had no actionable explanation. Some correction loops also came from my own choices: using a live-store CLI write for a time fixture, assuming a one-shot lookup was stable enough to own a route, and reusing a mutation ID after creating a different asset argument. The log distinguishes those mistakes from unresolved platform behavior.

I cannot honestly claim an empirical improvement over earlier Snapback generations from this run. I did not open their source or prior benchmark records. What I can say is that this published release presents an integrated authoring surface rather than just a database client: rules, local replicas, maintained views, jobs, effects, asset lifetimes, and generated contracts are all part of the documented workflow. Any comparison with an earlier generation should test those capabilities against that generation's actual published surface instead of importing remembered limitations. The same caution applies to claiming a speed advantage over Convex or Supabase from this single lane.

The production shape is therefore credible but bounded by the evidence. The application has real authorization, durable state, revocable media, offline writes, and scheduled server work. The iOS exports demonstrate that the Expo Router client and pinned native arm bundle to Hermes; they do not demonstrate a simulator or physical-device execution. The web choreography and the extra persistent-browser restart proof cover different facts and should stay separate. The full replay also has its own fresh instance, clock, invariant verification, and performance probes. A pleasant authoring experience cannot substitute for that scale evidence.

My overall judgment is that Snapback removes a large amount of infrastructure work for an application whose difficult requirements are local persistence, authorization-aware sync, and media lifetime. In exchange, it asks the product engineer to become precise about read completeness, custody, prediction, and presentation during revalidation. The backend declarations were often the easy part. Getting the product's visible behavior to respect those declarations was where most of the judgment went. That is a promising allocation of responsibility, provided the team treats the published execution model as part of the product architecture and tests the failure states as carefully as the happy path.
