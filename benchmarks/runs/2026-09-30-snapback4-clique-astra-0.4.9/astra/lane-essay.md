# Building Clique with the published Snapback 4 package

This build made the backend feel less like an application server and more like an executable data contract. Clique needed social feeds, private conversations, media, receipts, offline writes, reporting, and scheduled work. In Quarry, the schema did more than describe columns. It also described who could read and change rows, which rows belonged on a device, how long messages lived, and where uploaded bytes acquired their authority. That concentration was the most distinctive part of the experience. It reduced the number of separately authored systems whose behavior had to agree.

The comparison here is a product engineer's account of this cold build, not a benchmark of competing products. I did not run Convex or Supabase alongside it, inspect another implementation, or inspect an older Snapback checkout. My comparisons with them use architectural familiarity. I also cannot turn one local run into a claim about relative performance or release-to-release improvement. The retained receipts and source describe what this implementation actually did; broader judgments below are qualitative.

Authentication and ordinary social data were straightforward once I learned the package's authoring surface. A profile's handle constraint, ownership rule, query, and synchronization declaration lived together. Likes and follows were set-state mutations with unique keys, which made retries easier to reason about than toggles. Feed pagination and generated operation types gave the client a concrete contract. I did not have to maintain a parallel REST routing layer, transport DTOs, and authorization middleware. Those omissions mattered because the app had many small operations, each of which would otherwise have repeated a similar amount of infrastructure.

Convex is the closest conceptual comparison in my familiar vocabulary: server queries and mutations form a typed boundary, and React consumes reactive answers. A TypeScript-oriented backend would have been more immediately familiar to author. Quarry demanded learning its own expressions, rules, index syntax, and prediction constraints. In exchange, facts that normally spread across handlers were available to the compiler together. Accurate diagnostics frequently pointed toward a repair. The unfamiliar language was a real cost, but it was not simply a second way to write a handler; it let the platform reason about properties that ordinary application code leaves implicit.

Supabase suggests a different comparison. Its SQL and policy model are familiar tools for relational constraints and authorization. I would expect that familiarity to help with joins, aggregates, migrations, and operational inspection. For this app, however, database rules alone would not settle browser persistence, offline custody, retained conversation history, read receipts, and media revocation. Those behaviors would still need a coherent application design. Snapback placed more of that design in one published contract. The benefit was fewer boundaries to reconcile; the cost was accepting the platform's particular definitions of acquisition, completeness, retention, and refusal.

Media showed this integration most clearly. Uploading an object did not automatically make it usable by everyone. An authorized asset column gave it a home, and removing that home revoked access. The message deletion proof could check both a visible tombstone and a subsequent refusal to fetch the bytes. Disappearing messages used a server deadline rather than a timer in an open screen. View-once images required explicit consumption and a transient handle, with cleanup on close, deletion, or expiry. Compared with stitching together database rows, signed storage URLs, and a cleanup worker, these primitives removed a substantial amount of application glue.

The browser still required careful ownership of effects. Early versions attached a media viewer or reaction picker too closely to disposable message rows. Query withdrawal could remove those rows and thereby close the user's interaction. A late completion from one reaction could also close a newly opened picker. These were my React mistakes, and the published client guide described the relevant lifetime rules. Moving transient interaction state above the page was the repair. It would be misleading to count those failures as backend defects merely because a replica made them easier to encounter.

Offline work changed the shape of the client more than any individual feature. I did not build a replacement outbox or invent a second message identifier system. The SDK accepted custody, exposed pending writes, persisted them, and reconciled them when the connection returned. The application still had to present unknown, pending, refused, and confirmed states honestly. A loading answer was not an empty conversation. A partial search result was not proof that no other result existed. Retained history after membership removal was not permission to fetch new history. These distinctions are valuable, but they demand more discipline than a screen that treats every missing value as an empty array.

That discipline was tested again by multi-device convergence. The server accepted the messages, yet the browser briefly withdrew the history while many overlapping subscriptions revalidated. Removing mounted feed subscriptions from the conversation screen improved the interaction. A controlled revert showed that paged reaction/receipt decorations also mattered for convergence, so the final client retains them. The lesson was not that every query must be collapsed into one enormous read. Raw history still needed an independent lifetime from receipt and reaction decorations. The better structure kept history, decorations, and interaction state independently owned. A simpler built-in diagnostic view of subscription pressure would have saved time. A later edit regression also showed why an admitted pending message should retain its own action controls: hiding them made a fallback action select an older message. Keeping the controls available let subsequent edits use the existing ordered queue.

Receipts also deserve a distinction between convenience and capability. The package supplied the delivery-reporting seam, but I still modeled ordinals, delivered runs, read positions, membership boundaries, and gaps left by expired content. The compiler required the documented server-only repair for one receipt scan. That was more explicit data modeling than an application developer might expect from the word “messenger.” It remained feasible, and the resulting semantics were inspectable. I would welcome a higher-level recipe or reusable schema for this common pattern, provided it preserved the underlying authority rules.

Reporting and scheduled work fit the data-oriented model well. Lifetime totals and daily buckets were maintained on the server; the client rendered a compact result instead of paging the corpus to count it. Trending combined a server-time window with like-count ordering. The digest used a genuine schedule, an explicit period, server-side eligibility, and an idempotent effect. Its isolated proof closed every client, restarted the server inside the period, then checked provider receipts at the boundary and the next empty period. This was a stronger demonstration than clicking a “send digest” button. The worker seam kept external delivery replaceable without moving application authorization into the worker.

The development environment produced a separate, avoidable lesson. An alternate web export for scale measurement changed the baked backend URL. Metro then reused that transform in a main-client export. The invariant check rejected the first replay because test messages had reached the scale database. That failure was useful evidence: a fresh instance and exact manifest caught contamination that a successful replay exit would have missed. I preserved the failed attempt, made export URLs explicit, cleared the transform cache, and restarted from fresh state. This is an authoring/build-isolation error, not evidence that Quarry cannot maintain the required counts.

I cannot responsibly claim that this run proves Snapback 4 is faster to build with than earlier Snapback generations. No earlier generation was installed or tested here. The generational comparison I can make is narrower: this release's published surface asks the engineer to express a large portion of application behavior declaratively, and its client contract makes replica knowledge explicit. Whether earlier generations achieved similar behavior with more or less code is outside this evidence. I deliberately did not import assumptions about older limitations into the current build.

My overall impression is that Snapback reduced backend plumbing most strongly where authority, offline storage, and media custody intersected. It added friction where the application needed to understand replica answer lifetimes and where familiar JavaScript instincts did not translate directly into Quarry. Convex remains the more familiar mental comparison for reactive application code; Supabase remains the more familiar comparison for relational operations and database tooling. Snapback's distinctive bargain was to make more behavior part of the same contract. For this app, that bargain was useful, but it did not eliminate engineering judgment, browser lifecycle work, or the need for independent evidence.
