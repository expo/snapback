# Clique / Convex diary

## M1 — accounts and profiles (boundary pending)
Built Expo Router authentication and profile screens using the frozen kit, Convex Auth's Password provider with scrypt, reactive profile queries, server validation, logout session-record checks, storage uploads, and an idempotent starter segment replay. The iOS Hermes export works.

Reactive profile delivery and transactional handle checks were straightforward. Setup fought me: the anonymous CLI had a hardcoded extra dashboard listener, Expo required a dependency alignment and a route-cache restart, and I initially assumed the Password profile callback could be async. The published provider returns its operative configuration inside options, which made my first authorization wrapper ineffective. Those were my implementation mistakes, not evidence that Convex cannot support the requirements. Password signup also deliberately accepted an existing account with matching credentials; this brief needs an explicit rejection.

General React and transactional database familiarity helped. Convex's precise validation errors located malformed callback output, but included the synthetic fixture password in the error payload; the benchmark credential exception applies, and these diagnostics are not a production logging design. I used only published package code and public docs. No competing implementation was inspected. Compared with my general knowledge of Supabase, auth composition here is more application-visible; unlike SQL uniqueness declarations, the handle invariant is a transaction query plus write. I have insufficient first-hand Snapback evidence in this cold run to assert a comparative result.

## M2 — posts and the follow graph
Text/image/video posts, transactional counters, follows, likes, reposts, direct replies, author profiles, and keyset-paged feeds now pass the suite and choreography. Feed membership includes the caller without storing a self-edge. Set-state intents are deduplicated server-side. Storage URLs and reactive queries made media delivery simple; the kit needs a separate video poster and the app owns playback.

The surprising friction was outside data modeling: the copied choreography defaults refer to its original repository layout, and its helpers require feed-tab navigation even while viewing profiles or threads. Metro served an old shell after edits until a cache-clear restart. The resulting browser failures were useful concrete evidence, not a reason to weaken checks. General React familiarity saved time; no backend-specific feed implementation was reused. Convex's transaction model makes counters and edge transitions concise; the Following merge remains app code. A SQL backend would express that join more directly, while this implementation explicitly merges indexed per-author streams. Scale behavior remains unproven until M6.

## M3 — messaging core
DM pair deduplication, group identity, membership management, historical access, text messages, quoted replies, typing, and receipts pass both test layers. The seed now installs all three segments. Membership cursors let receipt aggregation avoid per-message writes on each read; the send-time recipient array preserves the specified aggregate semantics as members leave.

Convex's scheduler made typing expiry a small server mutation, and live query invalidation carried the change without a polling channel. Its ordinary transactions were sufficient for DM uniqueness and admin checks. I fixed a JSX brace and an acceptance locator that selected an older identical fixture message; neither required a backend workaround. Prior knowledge of cursor-based messaging models saved more time than platform familiarity. Unlike a backend with a dedicated presence primitive, typing here is durable data plus a scheduled cleanup. Compared with SQL realtime wiring, the reactive query result is pleasant to consume because the complete derived state updates together. Large-history and offline guarantees are still future work.

## M4 — media, reactions, edits, deletion
Photo/video messages, single-per-user reactions, editable text/captions, and delete-for-everyone pass the suite and choreography. The server parses uploaded MP4 duration and validates size/type. The asset endpoint authenticates and rechecks the message on each request; deleting a message deletes its storage object as well. A direct fetch passed before deletion and returned forbidden afterwards. Native video support and another Hermes export are present.

Storage upload itself was easy. Revocable delivery required deliberately avoiding public storage URLs for messages and constructing a protected HTTP action. That is more application plumbing than a storage policy attached directly to relational membership. Convex mutations still made reactions and window checks simple. The config uses the supplied shortened grading durations, alongside the production config. General media/container knowledge helped validate MP4 duration without transcoding. No missing capability surfaced; the work changed shape from storage convenience to explicit authorization at the serving boundary.

## M5 — ephemeral content, customization, search (verification in progress)
Expiry is a scheduled server mutation, with read-time denial as a second check. One-view photos consume a per-user view transaction before bytes are served; their decoded viewer contents stay only in memory. The kit now exposes group details, colors, background, and disappearing options. Synced histories are persisted for warm-offline search.

A source review found an important search design mistake: sorting a limited relevance-ranked full-text candidate set cannot guarantee newest-first results. I replaced it with normalized token postings and a prefix dictionary, maintained within message transactions, so time ordering is explicit. That costs schema and write amplification. Convex's native search was quick to integrate but its result ordering did not directly match this brief. Offline search still needs a separate local predicate. The scheduler and mutation-based one-view claim, by contrast, fit well. Prior understanding of authorization and information retrieval mattered more here than UI work.

M5 boundary: final suite and browser choreography passed, including group background/color sync, first/second view behavior, warm-offline search, and disappearing-message purge after closed-client expiry. The final run uses 190 seconds against the supplied 180-second TTL. The original five-minute run also passed; the repeat binds the final search change to an immutable suite receipt. No instrument checks were skipped.

## M6 — offline writes, push, API, replay adapter
The web offline queue choreography passed: two pending messages flushed in order and reached read. The suite checks the notification seam, the complete documented Node client demo, and all 50 sample actions with final-state validation over every verb. The adapter uses real password signup and the app's public authenticated writes; it records one settle receipt before proceeding. Its checkpoint callback is an execution hook for the separate scale run. Web and iOS Hermes exports are retained; no simulator claim is made.

Offline behavior required substantial application code: AsyncStorage snapshots and ordered queues, IndexedDB/native-file media caching, revocation purging, and a service worker for the web shell. Convex reconnects subscriptions and retries in-memory writes, but that is not the required durable offline product. Presence likewise became a short lease and delayed push evaluation rather than a built-in disconnect event. These are real costs that a sync-first backend could potentially reduce; I cannot claim a measured Snapback comparison from this cold lane.

I revisited the Following feed before scale: merging 500 per-author streams would make the published envelope expensive. Per-viewer projections are now scheduled in bounded fan-out batches, keeping the original post acknowledgement small. A regression suite passes. This is explicit backend design work, not free reactive behavior. The typed function surface and transaction semantics helped keep the public Node API small, while the custom offline layer was the largest effort so far.

## M8 — Insights, digest, and multi-device offline
I built transactional lifetime/daily counters, a scheduled 24-hour trending projection, and a scheduled per-user digest ledger under the two-minute fixture configuration. The two-client live/read/offline choreography passed. Convex's transaction boundary made maintaining counters straightforward, and scheduled mutations fit expiry and digest work well. The application still owns every definition of an activity period and every offline queue/cache rule. Familiarity with materialized views saved a late full-table aggregate design. The docs supplied primitives, not a complete durable offline model. Relative to PostgreSQL/Supabase, this favors maintained read models instead of ad hoc GROUP BY queries; relative to a database with built-in local replication, this requires considerably more client persistence code. First green is recorded; independent digest/restart and full-scale checks are still running and may expose additional corrections.

### M8 final verification corrections
The final pass found application mistakes beyond the first green: a video viewer raced the harness while asynchronously loading cached bytes, group routes needed stable IDs instead of names, cold-offline search needed the persisted account identity, and post video duration needed server validation rather than only picker validation. Each correction was followed by affected suite/choreography checks. The independent digest proof survived a mid-period backend restart and produced no extra quiet-period payload. A browser process restart preserved the pending queue and cold-offline search, then converged and advanced receipts. These are web proofs; I did not turn them into native simulator claims. The long replay also forced me to add durable resume, renew authenticated sessions, eliminate a redundant text-post read, and record actual mutation acknowledgement timing. Those adapter corrections remained on the original replay clock and are attributed to my implementation, not to Convex.

### Scale-driven maintenance review
The scale replay exposed high wall time despite small application execution time and no reported transaction conflicts. I replaced one long-lived Trending timer per post with indexed periodic retirement and batched independent fanout/index writes and obsolete timer cancellation within their transactions. Throughput improved substantially after the timer cleanup, but the experiment changed more than one factor and ran on a shared host, so I record ambiguous attribution rather than a Convex defect. I also finished people pagination and live older-history pages, moved large web history snapshots to IndexedDB, and caught an immediate-navigation race that could drop an unacknowledged membership removal. Membership intents now use the same durable ordered queue as subsequent text sends.

### M8 close
The complete fresh-instance replay and its final invariant verification passed. Independent recomputation matched every user's maintained totals, and the named public and protected media hashes matched their fixture bytes. The final web regression receipts have exact suite hash linkage, and every requested milestone retains a real iOS Hermes export. What remained easy was expressing transactional ownership and derived counters; what fought me was designing durable client state, authenticated media, and bounded projections under the larger workload. Familiarity with database indexes and idempotent queues saved time, while there was no single Convex guide that supplied the entire offline messenger contract. Compared with the other backends I know, Convex reduced transaction/subscription plumbing but left the application responsible for offline durability and most read-model design. The timing probes are useful diagnostics, not a substitute for the independent grader's full browser performance audit.
