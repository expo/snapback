# Building Clique on Convex

This was an independent build against a fixed product contract, not an attempt to reproduce another implementation. I used the published Convex package and its CLI, public documentation, and the supplied instrument. I did not inspect a Snapback checkout, another Clique implementation, or another lane. The comparisons below distinguish what I observed here from architectural comparisons with systems I know. In particular, this is not a measured claim that this implementation beat or lost to Snapback or Supabase.

Convex reduced the distance between a product interaction and a working live screen. A query was both a server function and the source of a React subscription. Mutations could read the relevant records, check authorization, update several related records, and return a result in one transaction. That made the early application feel unusually direct. Following someone, liking a post, changing a group setting, or advancing a read cursor did not require a separate event publication layer to make another browser update. The same functions were callable from the headless client, so the custom-client API was a real product interface rather than a second backend assembled for the benchmark.

The useful boundary was the transaction, not just TypeScript on both sides. Message creation records the sender, chat, recipient snapshot, expiry, search entries, and scheduled notification work together. Like and follow mutations maintain the underlying edge and the corresponding totals together. The server owns the authoritative time and membership checks. These are the places where an optimistic interface otherwise makes it easy to look correct while storing contradictory state. Convex gave me a good place to express those invariants. It did not write them for me: I still had to make every public function check the session and every chat operation check membership.

Authentication was less immediate than the first live data screen. Anonymous local development was available, but local deployment setup, signing keys, and the authentication provider still needed explicit work. A particularly instructive correction was duplicate-email signup. The password provider's existing-account behavior did not match this product's expected visible rejection. My first wrapper also misunderstood where the provider's effective authorization callback lived. Reading the installed package resolved that. This was an integration mistake on my part, not evidence of a Convex database defect. It did show that a high-level auth package does not remove the need to understand its lifecycle when the product contract is precise.

The local CLI also exposed an operational mismatch with this environment. Its anonymous dashboard listener had a hardcoded default outside the lane's allocated ports. I stopped that listener and used a narrow launcher shim to remap the dashboard and keep CLI state inside the lane. The database and application semantics were unchanged. The resulting local workflow was useful, but this is extra ceremony that matters in a cold, isolated build. A backend that starts entirely inside the application's existing process would avoid some of this setup. A hosted Supabase project would exchange it for project provisioning, credentials, and network dependence; a local PostgreSQL stack would introduce its own installation and lifecycle work. These are different operational costs rather than a universal winner.

The largest change in the shape of the work came with offline behavior. Convex's live client state was not the durable application store required by this contract. I built an ordered intent queue, persisted conversation snapshots, a media cache, an offline web shell, and reconciliation on reconnect. The queue uses stable mutation IDs so a lost acknowledgement can be retried without duplicating the effect. Cached data is scoped to the account, and revocation synchronization removes expired or deleted media. View-once bytes take a separate path and are never persisted. This is application code with its own failure modes, even though the server mutation underneath it is transactional.

That is the most meaningful contract-level comparison with a local-first backend such as the Snapback alternative contemplated by this benchmark. If the backend provides durable local queries, queued writes, and a defined convergence model, much of this responsibility can move below the application. In this Convex build it remained above the backend. I cannot infer how complete or ergonomic Snapback's implementation is without using it in this run, which I deliberately did not do. The concrete observation is the amount of persistence and reconciliation code this lane needed. Relative to a conventional Supabase browser client, the same offline requirement would also call for an explicit local store or replication layer; SQL and realtime notifications alone do not define restart-safe pending messages.

Media made that ownership boundary especially visible. Uploading bytes to storage was easy. Deciding who may fetch them later was the actual feature. Public profile and post images can use storage URLs, but conversation assets need authorization on every fetch. Delete-for-everyone and expiry must revoke the source and clear synchronized caches. View-once requires an atomic claim before serving bytes, and a retry after the claim cannot silently serve the image again. I used an authenticated HTTP action for these assets. A late review also caught a duration check that was present in the post composer but not enforced by the post mutation. The correction added a server validation certificate for uploaded video. This was a useful reminder that a successful picker demonstration is weaker evidence than an adversarial direct API call.

Scheduled work was a strong fit for Convex. Disappearance does not depend on a browser being open: creation schedules the authoritative cleanup, and reads also filter by expiry. The digest similarly runs from the scheduler, with a persisted per-user period marker and a deduplication key. A controlled test closed the clients, restarted the backend during the activity period, and checked both the active period and a following quiet period. The scheduler provided the execution mechanism; the ledger, authorization rules, and definition of each count remained application decisions. Compared with arranging database cron, functions, and a notification seam separately, keeping this work next to the mutations was convenient.

Scale moved the design away from straightforward queries toward maintained read models. My initial Following feed design merged per-author results. That made the number of followed accounts part of the read cost, so I replaced it with a projected feed and asynchronous fanout. Insights uses transactional totals and daily buckets. Trending has its own indexed projection and scheduled retirement. This makes the reads small and predictable, but it adds more write paths and background work. PostgreSQL would offer expressive joins, grouped aggregates, and query-plan tools for exploring alternative designs. It would not make every such aggregate cheap at this envelope; materialized views or counters might still be the right answer. Convex encouraged me to make those choices earlier and express them as application functions.

Search was another place where a convenient first implementation was insufficient. The contract requires prefix matching with normalization, authorization, chronological results, and offline behavior. I built an indexed posting representation and a separate search over the durable client cache. One correction removed a bounded candidate shortcut that could miss a rare second prefix behind many occurrences of the first. Another made cold-offline search load its account identity from durable storage. These are not glamorous features, but they are the difference between a search box that works in a demonstration and a specified search behavior. A SQL implementation could use different indexing tools; it would still need the same semantic agreement between server and offline client.

The replay also challenged my maintenance design. One long-lived retirement timer per post was unnecessary when a periodic indexed sweep and an exact read-time predicate could express the same behavior. Replacing those timers, and batching independent database operations within transactions, coincided with a substantial throughput improvement. I changed multiple factors on a shared host, so this is evidence for the revised design, not a clean diagnosis of a backend defect. It made background maintenance a visible part of the product architecture rather than an afterthought.

Finally, the evidence workflow changed my confidence more than any single framework feature. The suites, multi-browser choreography, headless API demo, restart proof, and replay checked different failure classes. The replay required its own resumable adapter and token renewal; treating a long run like a short script would have made session expiry an avoidable failure. I retained the original replay clock across a controlled interruption rather than pretending the continuation was a new clean start. Direct API timing samples are useful diagnostics, but I distinguish them from the instrument's hidden rendering and subscription probes. Native Hermes exports establish that the client bundles for iOS; they do not establish simulator behavior.

My conclusion from building this app is that Convex made transactional live application state and scheduled server work pleasant to compose. It added less value at the durable offline and media-revocation boundaries, where the application still needed a substantial model of its own. Its query model also rewarded explicit projections rather than postponing all read decisions to a relational query layer. Those tradeoffs are coherent. The successful parts of the experience came from using those strengths directly; the corrections came from assuming a convenient primitive already supplied a stronger product guarantee than it actually did.
