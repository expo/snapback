# Building Clique against the published Snapback 4 surface

Snapback 4 changed where I spent engineering effort. The difficult part was less often implementing a mechanism and more often expressing the mechanism in a form the compiler could prove safe, bounded, and reproducible on a device. Clique needed authorization, live data, media lifecycle, offline writes, receipts, aggregates, and scheduled work. Those concerns usually cross several libraries and services. Here, many of them were declarations attached to the same schema. That coherence was the strongest benefit of the experience. It did not make the work effortless: it made the cost of understanding the backend unusually visible at authoring time.

This was a cold build from the exact public packages and their published documentation. I did not inspect another lane, a Snapback checkout, or a prior Clique implementation. My comparisons with Convex and Supabase are therefore comparisons with their familiar architectural models, not measurements from parallel implementations. I also do not have an independently qualified earlier-Snapback baseline in this session. That limits what I can honestly say about improvement between releases. The observations below describe the installed release, the code I wrote, and the behavior I actually checked.

The clearest reduction in friction was the relationship between a message, its audience, and its media. Membership determined who could read a row and which devices received it. An image placed on that row inherited its access boundary. Clearing the image reference or expiring the message made subsequent asset access fail. A view-once image used a dedicated declaration, with consumption enforced per principal. I still had to build the picker, preview, viewer, and close behavior, but I did not implement a parallel signed-URL authorization system or a bespoke server-side view counter. These were important guarantees to obtain from one model rather than several loosely coordinated subsystems.

With a conventional Supabase design, I would expect to express the relational model and row policies in PostgreSQL, then separately coordinate object storage policies, deletion jobs, and device caching. PostgreSQL would be a more familiar and more broadly flexible query language for me. The extra integration work would appear around the database, especially for offline behavior. Convex's reactive query and mutation model is closer to the application's live behavior, and TypeScript would avoid much of the syntax discovery I experienced here. But a durable local replica with a predictable outbox is a distinct capability from a live online client. Snapback made that distinction central instead of leaving me to add it after the online product worked.

A sender-side media edge case also needed care: an optimistic bubble could fetch an unplaced upload preview before commitment. That fetch did not provide a retained offline copy. Gating media access until the placement committed made the ordinary-image cold-reload proof pass, while view-once bytes remained unavailable. This was an integration boundary worth testing directly.

The offline implementation was consequential. A browser could reopen without connectivity, show synced history, search it, preserve a newly queued message across another reload, and flush it when connectivity returned. The application did not maintain its own second message database. The same operations and the package's device runtime supplied the behavior. This is where I felt the greatest difference from an ordinary hosted backend plus a frontend cache. A cache answers questions about data fetched earlier; this device model also executes admitted reads and predicts writes, with explicit coverage and pending-state semantics.

That advantage came with a stricter authoring discipline. A push notification initially prevented message prediction because I looked up the sender's profile inside a presence-dependent branch. The branch looked harmless to a JavaScript programmer: it only constructed a notification payload. The compiler could not classify it as an effects-only decision because the nested read could fail or vary in cost. The diagnostic explained this, and moving the lookup before the guard restored prediction. Similarly, reaction uniqueness and its cap had to carry the chat key so the compiler could establish the membership scope. These were small code changes, but they required a precise mental model of what the engine was proving.

I would not call those episodes platform defects. The eventual diagnostics were useful and specific. They are examples of friction that a more permissive backend would defer until runtime, performance testing, or an authorization review. The trade is attractive when the proof protects an important guarantee. It is less pleasant when the programmer only discovers the relevant rule after assembling several features. The published guide is unusually rich, but its breadth also creates an orientation cost. A smaller end-to-end product recipe connecting auth, replica retention, membership, effects, and aggregates would have reduced the number of separate cards I needed to reconcile.

One gap in the high-level composition stood out. The ordinary application controller handled authentication and client replacement, but its published options did not expose the viewed-media retention option documented on the lower-level local client. I used the documented auth helpers and local-client constructor directly. The capability was available, so this was not an inability to satisfy the brief. It nevertheless moved lifecycle responsibility into application code: restoring sessions, opening clients, switching accounts, and clearing state on logout. An integrated option would have kept more of that behavior in the package. In a TypeScript-centric backend ecosystem, I would usually expect such composition to be the default form of customization; in this product, it felt like stepping off the simplest path to combine two supported features.

Feeds exposed a different concern. Public activity, follows, and maintained engagement counts were compact to express. The first interaction with a materialized Following feed was harder to reason about under the choreography's immediate observation window. A just-published event could be committed before the asynchronous materialized result was visible. A direct filtered activity query initially solved the observed interaction, while the compiler explicitly warned that sparse follows could make the query incomplete at larger sizes. The scale probe then exhausted the read heap for sparse readers, confirming that warning. Returning to the documented materialized feed and waiting for the author’s terminal write and replica sync in the composer passed the original choreography. The important lesson is that a UI lifecycle mistake can tempt an engineer into an expensive backend workaround, even when the intended backend design already supplies the necessary guarantee. Concise declarations can still hide meaningful delivery timing and scan-cost choices. They deserve product-level scrutiny, not just a green compiler invocation.

The busy-chat scale probe also caught an unnecessary exact unread count over expiring receipts. Replacing it with an indexed existence query preserved the required unread indication and avoided scanning the whole unread group. That was an application design correction, not a reason to weaken the query meter.

Aggregates and the digest were more satisfying once the query model was understood. Lifetime totals and UTC buckets were maintained from source contributions. Received likes and replies used recorded attribution to the referenced author's identity. The scheduled job walked each recipient's own memberships, computed authorized period activity, and emitted through a persistent once-per-user-and-period key. A real-time test closed the clients, restarted the backend during the period, and then checked both the active period and the following quiet one. This combined scheduling, idempotent admission, and authorization in a small amount of backend code. I would expect more explicit counter maintenance or transaction logic in a general-purpose function backend, and more coordination between SQL, scheduler, and provider worker in a typical PostgreSQL service arrangement.

The job language still had a surprise. Moving loops into a helper made carried values look like state crossing automatic sweep chunks. Inlining the recipient computation inside the outer profile sweep made the intended transaction boundary clear to the compiler. I kept the query preview and job body generated from one template so their business logic would not drift. This is a good illustration of the broader pattern: the backend reduced infrastructure code while making execution placement and boundedness part of everyday application design.

The comparison with earlier Snapback generations needs restraint. The current published documentation includes historical migration notes, including native media-cache repairs. Those notes show an evolving product, but they do not establish a measured earlier-release baseline for this build. I cannot attribute today's successful offline or media behavior to a particular generational improvement without testing the older artifact, which this run deliberately forbids. What I can say is that the installed package presents a broad, integrated authoring surface: compiler diagnostics, generated operations, device runtimes, protected assets, effects, and schedules. Its value should be assessed from that present surface rather than assumptions carried forward from an older run.

The overall experience favors a backend that treats authorization, replication, and lifecycle as one design problem. It also rewards an engineer willing to learn a constrained language and interpret its execution proofs. Convex would offer a more familiar application-language workflow; Supabase would offer familiar SQL and a larger conventional database toolbox. Snapback reduced the amount of glue needed to connect several difficult guarantees, while adding compiler-oriented reasoning and some integration seams of its own. The milestone evidence demonstrates a working web product and exported native bundles. It does not substitute for simulator execution, hidden trust-boundary probes, or an independently operated production deployment. Those limits matter when turning an effective cold-build experience into a claim about operational maturity.
