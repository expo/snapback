# Building Clique on hosted Supabase

Written after M8's final passing verification and before aggregate timing, correction-loop, dependency, or source-line tallies. The scale replay is still running on its separate clock. This essay describes one cold build and the engineering choices made within it, not a controlled ranking of backends.

Supabase made the durable, relational part of Clique feel familiar. Profiles, follows, conversations, memberships, reactions and receipts fit tables with foreign keys and uniqueness constraints. I could express a unique DM pair, a one-reaction-per-user rule and monotonic receipt updates directly. The late features also fit SQL: seven UTC buckets, top posts over a time window, and digest counts did not require inventing a separate aggregation model. That familiarity was valuable, but it is a source of bias. I arrived knowing PostgreSQL and HTTP, and used that knowledge to choose an architecture I could reason about quickly.

The actual application is Supabase plus a substantial application server. It uses the published Supabase JavaScript client for real Auth and private Storage, and a direct PostgreSQL connection for application data and transactions. Browser updates travel through my PostgreSQL LISTEN/NOTIFY-to-SSE bridge; native updates use an authenticated WebSocket. They are not Supabase Realtime subscriptions. This distinction matters to the comparison. The experience measures what I built on hosted Supabase, including my decision to own that server, rather than the shortest possible application using every managed Supabase feature.

Authentication was initially easy because passwords, sessions and signed tokens were already provided. Immediate logout revocation required a more specific contract than merely checking a JWT signature. I checked the live Auth session row as well, so a locally revoked session could not keep using its unexpired access token. That added a database dependency to request authentication, and high-frequency writes eventually combined the session check and mutation inside one SQL transaction. The resulting rule is understandable, but it is extra integration work that a more integrated application backend might conceal behind its session abstraction. The custom-client documentation also exposes the current limitation honestly: clients authenticate again after token expiry; I did not ship a refresh endpoint.

Private media changed the shape of the work more than basic CRUD did. A file upload is easy; a file that is readable only while its message remains authorized is a different feature. I chose an authenticated proxy that checks message membership, deletion and expiry on every read, including byte-range reads for video. View-once photos use an atomic recipient claim and return bytes only through that operation. This avoids giving a client a durable URL that outlives the intended permission. It also means the Node server participates in every media download. Supabase Storage removed the need to run an object store, but did not remove the need to define the application's access lifecycle.

PostgreSQL was particularly useful for server-time rules. Edit and delete windows compare database time with the stored creation time. Disappearing messages receive an expiry timestamp when sent; history, search and asset reads exclude expired content independently of any open client. A server sweep clears expired text and emits invalidation. I initially made that sweep issue an UPDATE even when nothing matched. My statement-level notification trigger still fired, creating a refresh storm. The fix was small, but the lesson was architectural: a database trigger plus a generic invalidation stream is not automatically a carefully designed reactive query system. That mistake belongs to my implementation, not to Supabase.

The clearest contrast with Convex is this reactive layer. Convex documents dependency-tracked queries that update subscribed clients and maintain a consistent view across subscriptions. That is precisely the category of work I implemented manually here: deciding what a notification means, refreshing the right screens, recovering after disconnects and avoiding an older response replacing a newer view. SQL remained pleasant for the underlying joins and constraints, but the client/server update protocol consumed attention that an integrated subscription model could reduce. This is a comparison of documented capabilities and the responsibilities visible in my code, not a measured claim about another Clique build. [Convex realtime documentation](https://docs.convex.dev/realtime)

Offline behavior widened that gap. I built a per-account ordered mutation queue, stable operation IDs, retry handling, cached history and local prefix search. Web data moved to IndexedDB, media bytes to CacheStorage, and the application shell to a service worker. Native uses AsyncStorage and the filesystem. None of those pieces is individually exotic, but their interactions are where the work accumulates. A reconnect must reconcile receipts, preserve ordering, refresh the sender as well as recipients, and remove content that was revoked elsewhere. The client needs to distinguish a pending local action from a server-acknowledged one without treating an optimistic UI transition as proof that a write committed.

Firestore offers a useful comparison here. Its documented offline persistence supports cached reads, writes, queries and listeners, then synchronizes local changes after reconnection; Apple and Android enable persistence by default, while web persistence requires configuration. That would remove some scaffolding I wrote. It would not, by itself, specify Clique's slowest-recipient receipt rule, per-recipient view-once claim, expiring media access or account-specific purge semantics. Those remain product rules. The distinction is between receiving a durable offline data substrate and receiving a finished messenger. Supabase gave me excellent server primitives, but this particular build supplied its own offline substrate. [Firestore offline documentation](https://firebase.google.com/docs/firestore/manage-data/enable-offline)

Verification exposed both real client faults and faults in my tests. The most instructive late investigation started with an offline-media probe that used an async Playwright polling predicate. The installed implementation treated the returned Promise as truthy, so the probe advanced before caching was complete. I initially read those failures as evidence of persistence races; that diagnosis was not justified. After correcting the probe to await each evaluation, it exposed a real bug: a generic array conversion had changed string revocation IDs into objects, preventing cache deletion. The final probe verifies actual cold rendering and byte removal. This episode is a warning against attributing friction to a backend when the test and the application both contain agent-authored plumbing.

The digest was comparatively straightforward once the data model existed. A transactional cursor, an advisory lock and unique period keys made restart catch-up and duplicate suppression explicit. The independent probe crossed the shortened scheduling boundary with no browser open and checked quiet-user suppression and the next period. The server must stay running for this scheduler, just as it must for notification forwarding and the logged push worker. This is a production-shaped service arrangement, not a claim that I deployed a managed scheduling fleet or integrated APNs. A backend with built-in scheduling and subscription lifecycle management could reduce those operational responsibilities; a conventional PostgreSQL/Express stack would leave roughly the same ones with the application.

Scale also showed why deployment posture matters. The replay uses real signup, media upload and ordinary authorized write paths, settling one action before advancing. Hosted Auth imposed its signup token bucket, and the adapter now preserves and backs off on 429 responses. The published rate-limit documentation describes this behavior; I did not bypass it with privileged account provisioning or modify the shared project's limits. Database network round trips also motivated consolidated SQL functions. These are different observations: a documented admission policy, the cost of hosted network calls, and my initial number of calls per mutation. None establishes a provider defect, and no complete scale-envelope claim is available while the replay remains unfinished. [Supabase Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits)

I cannot offer an equally concrete Snapback comparison from this session. I inspected no Snapback source, checkout, prior implementation or run diary, and I have no verified hands-on Snapback result to substitute for that absence. The useful comparison is therefore a set of responsibilities an independent Snapback run can test: how much of my session handling, reactive invalidation, durable queue, media lifecycle and scheduler remains application code there, and how observable its failure modes are. Claims that Snapback would have been faster, slower, more local-first or less reliable here would exceed the evidence I have. That limitation is preferable to inventing familiarity in a comparative essay.

What I would carry into another Supabase project is confidence in its relational foundation and greater care about the boundary around it. Constraints and transactions made the durable rules easy to inspect. Auth and Storage avoided building two substantial services. The expensive parts were the application-owned synchronization protocol, offline media lifecycle, and verification machinery. Some of that cost follows from Supabase's composable shape; some follows from choosing SQL plus a custom Node API; and some was plainly my error. Keeping those causes separate is the most useful result of this build. A later cross-backend comparison should compare preserved evidence and equivalent behavior, not credit one backend for work silently omitted by another.
