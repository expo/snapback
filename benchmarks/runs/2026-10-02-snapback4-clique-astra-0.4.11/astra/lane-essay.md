# Building Clique on the published Snapback 4 surface

I finished the requested application milestones before writing this essay, and I am writing it before tallying milestone times, correction counts, or source lines. The separate scale replay is still running. This is an account of one cold build, not a controlled comparison of simultaneous Convex, Supabase, or earlier Snapback implementations. I did not inspect another lane, an older implementation, or a Snapback source checkout. My comparisons to other systems come from general engineering familiarity; the concrete observations here come from the installed 0.4.11 packages, their public documentation, diagnostics, and this application's tests.

The most consequential difference was that the backend was a single declarative authoring surface. Tables, authorization, synchronization, assets, receipt bookkeeping, expiry, aggregates, queries, mutations, jobs, and schedules lived together in Quarry. That changed where I spent attention. I was rarely deciding which external subsystem should own a behavior. I was deciding whether the schema expressed the right audience and whether the client could make an honest statement from the data currently available. For a social messenger, that is a substantial change in the work: membership, offline history, unread state, and asset access are not independent features that can safely be assembled without considering one another.

The early profile and feed work felt familiar. Typed query and mutation handles connected backend operations to React components, and a real password flow supplied user principals. I made ordinary application mistakes: passing row metadata back into an edit mutation, allowing hidden routed screens to duplicate selectors, and placing navigation where the frozen UI expected it elsewhere. Those were my mistakes, not evidence that the backend was incapable. The compiler was useful because it narrowed many problems to a specific declaration or argument. Some diagnostics were more helpful than others: receipt functions needed a row rather than an ID, and a captured expiry deadline had to be immutable. Both requirements made sense after I saw the diagnostic and the relevant guide.

Convex is the closest conceptual comparison in the query-driven parts of the app. My general expectation from that style of backend is that reactive reads and transactional writes relieve the client of much manual invalidation. Snapback provided that experience, but its local replica added another dimension. A query could be loading, partial, stale, or locally answerable under a particular coverage horizon. Treating every temporarily missing value as an empty value was wrong. A reaction toggle demonstrated the cost of that mistake: I needed to preserve the user's explicit set-state intent while the query revalidated. Familiar React state patterns helped, but a generic loading spinner was not sufficient reasoning.

Supabase and a conventional Postgres application are the other useful comparisons. I would normally expect to reason separately about database policies, client caching, change delivery, object storage, background jobs, and an offline queue. I could certainly build this product from those components, but their boundaries would be part of my application design and test burden. Here, putting an image reference on an authorized row made storage access part of the same model. Clearing a message's references on deletion, or expiring the message, also removed the corresponding read access. View-once images were especially valuable as a platform primitive: my client still had to release its temporary handle correctly, but it did not invent a second-fetch protocol or a durable secret-media cache.

The receipt family was another place where backend machinery displaced application machinery. Conversation ordinals, join floors, recipients, delivered watermarks, and seen watermarks are easy to describe casually and surprisingly easy to get subtly wrong. The generated operations made the intended model explicit. I still had to author member-management rules carefully. Initially I made membership updates admin-only, which also blocked a member from updating their own receipt watermark. Correcting that rule while keeping promotion and removal gated was a reminder that a compact schema does not eliminate authorization design. It makes the design visible in fewer places.

Offline behavior was the most demanding client work. A write could be accepted into durable custody without producing a predicted row. That required a visible pending fallback based on the SDK's pending arguments. Cold restart and reconnection then had to preserve order without an application resend loop. The browser probes confirmed restored history, viewed ordinary media, search over synced messages, and queued sends surviving reload. I kept native proof separate: every milestone exported an iOS Hermes bundle using the exact published Expo arm, but I did not execute the simulator. A bundle is evidence of build compatibility, not evidence that every native lifecycle behavior was exercised.

The two-device tests exposed a second client issue that an online happy path would not have revealed. Both offline messages reached all three clients, yet a rendered-list assertion could observe an empty transition during settlement. I changed the history presentation to retain only message IDs and ordinal order while each message rendered through its own current authorized subscription. I did not retain a second copy of protected message content. That distinction mattered because disappearing messages and revocation were in scope. This was more demanding than wiring a list to a query, but it was also a useful pressure toward explicit ownership of read state. The public guide's emphasis on honest availability was relevant to the actual failure rather than an abstract warning.

The scheduled digest was compact in a way I would not expect from a fully hand-built backend. The job swept profiles, selected the recipient's read authority, computed period activity and unread counts, and admitted an effect once for that recipient and period. The worker used the published durable ledger and a stable provider key. In an isolated instance with every client closed, the scheduled result had the expected counts, excluded a private chat and a deleted message, and did not repeat in the following inactive period after a restart. The provider seam here is a local log, as requested. It is not a claim about real mobile push delivery or general exactly-once network effects.

Insights also benefited from the same schema vocabulary. Lifetime and UTC day counts were maintained views, not totals assembled by paging records into React. Trending was a server query over original posts and their maintained like counts. The compiler made those choices visible and warned about coverage or scan properties. This resembles the discipline I would want around SQL materialized summaries or application-maintained counters, but I did not have to write a separate counter-update path for every mutation. I still needed independent count checks, an old-post test on a separate clock-controlled instance, and tie-order tests. Declarative maintenance reduced code; it did not remove the obligation to verify meaning.

The replay adapter was deliberately ordinary application code. It registered real accounts, uploaded actual fixture media, and waited for authoritative settlement before submitting the next action. Retrying a media action caught an important error: a new upload reference is a different argument even when the message ID is unchanged. Resolving an existing message before uploading again made retry semantics explicit. The scale store was separate from acceptance residue, and replay suppression prevented the notification workload from turning into a different benchmark. The available checkpoint probes are diagnostic; the instrument's secret rotated probes and seeded grader sample are not available to the builder. I will report those boundaries rather than manufacture a grading result.

I cannot honestly give a measured comparison with earlier Snapback generations from this run. The independence rules deliberately removed prior implementations and documentation from my evidence. What I can say is that this published generation exposed a coherent path for the demanding features in this brief: device state, receipts, expiring assets, effect workers, maintained aggregates, and scheduled jobs were all discoverable through the package's guide. A comparison that attributes a current success or failure to an older release would need separate evidence. I did not need a source build or source inspection to complete the milestone proofs.

My overall impression is that Snapback reduced backend integration work and increased the importance of precise client read semantics. That trade was favorable for this product because the difficult guarantees crossed so many traditional subsystem boundaries. The friction was real: coverage horizons, generated receipt ownership, live-store exclusion, and transient query states all required learning. The strongest result was not that the implementation became effortless. It was that the hardest product rules could be expressed in one backend model and then tested through the same public client path. The remaining assessment should rest on the recorded artifacts, the completed replay verification, and independent grading, rather than the appeal of that model alone.


The last scale checkpoint supplied a useful correction to this impression. I had left the inbox unread badge as a raw scan, which was cheap on the starter data but exceeded a returned-shape meter on the busy conversation. The diagnostic named the shape and the guide supplied the exact row-keyed maintained-count pattern, including expiry and offline coverage. Replacing the scan made the full corpus readable. This was an authoring mistake with a documented remedy, not evidence that the platform could not express the feature. It also shows why the smaller milestone proofs were insufficient: the schema remained legal while the chosen query composition stopped fitting at scale. The repaired count changed prediction eligibility, so I returned to the offline proof instead of assuming that a server-side optimization had no client consequences.
