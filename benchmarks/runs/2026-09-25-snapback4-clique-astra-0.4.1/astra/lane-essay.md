# Building Clique with the published Snapback 4 surface

This build made the backend feel like a description of the application's durable facts and obligations. That was its strongest quality. A conversation was a row, membership was the authority to see it, a sync declaration distributed it, and an expiry declaration ended its visibility. I did not have to invent a different account of the same relationship for an HTTP handler, a subscription service, a device database, and a cleanup worker. The result still required substantial application engineering. The difficult work moved toward understanding exactly when the device knew something, when a write had been admitted, and what a derived value was allowed to retain.

This is a qualitative account of one cold build, written before the final metric tally. I used only the pinned public Snapback packages, their README and guide, diagnostics, and generated types for platform knowledge. I did not inspect another lane, an older application, or a Snapback source repository. The Convex and Supabase comparisons below are comparisons with architectural approaches I know, not measurements of current competing releases. My comments on older Snapback styles come from the compatibility material in this release's guide; this session provides no independent evidence about how an older release would perform on this brief.

Accounts and public profiles established the basic pattern quickly. Quarry let the schema state ownership, uniqueness, read access, and synchronization together. Generated operations made the client call sites concrete. With a conventional Supabase application, I would normally reason separately about table definitions, row policies, storage rules, and the client subscription path. Those are familiar and useful boundaries, especially for a team comfortable with PostgreSQL. Here, having one declaration govern more of the lifecycle reduced the chance that an avatar was public through one path but inaccessible through another. With the Convex style of typed server functions and reactive queries, I would expect the function language to feel more familiar immediately. Quarry exchanged some of that familiarity for a smaller, more restrictive vocabulary.

The restrictions helped when they expressed an obligation clearly. Message timestamps came from the server. Membership constrained reads and writes. Edit and delete windows used generated helpers from the selected configuration files, so the shortened grading windows did not become independent UI guesses. The same model expressed monotonic read and delivered watermarks. Those watermarks were still my responsibility: I had to decide what a sender should see when recipients left and rejoined, and which recipients belonged to a particular message. A backend cannot remove the need to specify product semantics. It can make those semantics easier to keep consistent once they are specified.

Media was where the integrated model paid off most visibly. Clearing an asset placement revoked subsequent access without an application download endpoint. Disappearing messages used server-enforced expiry, and a once-only photo had a server-enforced consumption boundary. In a design assembled from a relational database, object storage, and a client cache, I would plan additional state and tests for placement, access grants, consumption, deletion, and cleanup. It is possible to build those guarantees there, but each additional boundary creates room for disagreement. In this build, much of that work was already a platform contract. The remaining important work was on the client: a once-only image must not be fetched by the ordinary thumbnail hook or left in the normal viewed-media cache.

The platform did not protect me from a derived-data leak of my own making. I initially copied a last-message body into a conversation preview. Expiring the message would not necessarily erase that independent copy. Replacing the copied preview with a read of the latest live message made preview and unread behavior follow the source lifecycle. That episode is more instructive than a claim that declarative expiry solves every privacy problem. The declaration governs what it owns. The application must avoid creating other durable copies that escape it. I would apply the same reasoning with Convex document fields or a PostgreSQL denormalized summary.

Offline work changed the shape of development more than ordinary live queries did. A returned pending receipt is not a server commit. A restored session is not a fully acquired partition. A locally visible row is not necessarily a row that another client has received. These distinctions were explicit in the public documentation, and I repeatedly had to make my UI and tests respect them. My first edit flow navigated before terminal success. A later administrative action could lose the race against hard navigation before asynchronous admission, so I added a small synchronous intent handoff with a stable retry ID. The message queue itself used the platform's durable machinery. This combination was much less code than designing an outbox, replay protocol, local query mirror, and conflict policy from scratch, but it was not a substitute for understanding those concepts.

The replay adapter exposed the same lesson in a different form. A stable mutation ID only works as a retry key when the arguments remain stable. Re-uploading the same fixture produced a different asset reference, and my initial retry path then supplied changed arguments under an existing write ID. The server refused that inconsistency. Persisting the original upload binding under the backend's identity fixed the adapter. That was an application mistake, not evidence of a broken retry mechanism. It also showed why an exact diagnostic can teach a contract more effectively than a broad promise of idempotency. Once the binding was correct, the full action replay could settle writes, retain receipts, and verify its independent state model without special access to the database.

Feeds and scale exposed a less comfortable tradeoff. The maintained Following declaration was concise and saved application fan-out bookkeeping. Its published contract also includes a bounded historical backfill per newly followed author and requires fully synchronized public source tables. The compiler explicitly refused my attempt to give posts a bounded acquisition horizon. That is a real limitation of this particular serving model, not a conclusion imported from an older benchmark. The source posts still exist and remain queryable, but a full public corpus has a cold-device cost. My initial screen-wide acquisition gate made that cost the user's entire startup experience. The final client waits initially, then permits documented online fallback reads while clearly indicating that offline access is still being prepared.

That compromise deserves continued attention in a production rollout. Immediate online usefulness and a complete local working set are different readiness conditions. Removing the initial wait entirely made the seeded dual-offline choreography get ahead of acquisition; restoring a bounded wait and waiting for a conversation's roster fixed the final behavior. A conventional server-query-first application often hides this distinction because it does not promise the same local data model. A local-first application should expose it honestly and test both warm offline use and truly cold startup. The populated scale instance rendered correct profile and Insights data, but its cold acquisition behavior should not be confused with the much faster direct server query measurements.

Insights and the digest fit the language particularly well. Maintained views expressed the six totals and UTC day buckets without asking the client to count its way through the corpus. They also adopted onto the populated scale store. The scheduled job received period boundaries, computed authorized counts, and admitted once-per-user/per-period effects. The provider worker only logged delivery and deduplicated the stable effect identity. Closing every client and restarting the backend in the middle of a period was a useful proof because it removed the temptation to mistake a live screen's query for scheduled work. Relative to the database-plus-worker designs I know, fewer pieces had to agree on the period and retry identity. Relative to function-oriented backends, the declarative form was concise, though the helper namespace and job syntax required learning.

The published guide was usable as an external customer's surface. The complete-chat example, asset lifecycle explanations, acquisition contract, and Following example were more valuable than a large collection of disconnected snippets would have been. Diagnostics usually supplied a concrete rewrite. I still spent time on guessed spellings, confusing an imperative asset result with its React wrapper, and test selectors that targeted the wrong row. Those belong to the agent's learning and integration cost. The guide's compatibility discussion suggests that the newer Following declaration reduces older recipe and sizing ceremony, but I cannot turn that observation into a measured claim about earlier generations. The remaining documentation opportunity is a single realistic account of cold acquisition, navigation, online fallback, and durable admission under a large partition.

Some friction was ordinary tooling rather than backend design. A stale Metro graph initially served an earlier UI, and later Metro cached an environment-substituted backend URL across exports for separate instances. Explicit clean exports made that boundary reproducible. A broken host FFmpeg installation led me to extract the fixture's video poster through Chromium. These are relevant to the experience of shipping an app, but blaming the backend for them would make the comparison less useful. The same applies to tests that needed unique text, exact row targeting, or a wait for a rendered pagination result.

My conclusion is that this release reduced the amount of infrastructure I had to invent, especially for privacy-sensitive media lifecycle, membership sync, retained history, durable writes, and scheduled effects. It added a new language and a more demanding model of client knowledge. Convex's function-oriented approach and Supabase's SQL-centered approach remain easier starting points for teams whose existing skills align with them; their flexibility can also be valuable when the prescribed Following model is a poor fit. In this build, the strongest reason to choose Snapback was the coherence of its guarantees across server and device. The main caution is to budget for proving the boundaries between those guarantees, rather than treating a compact schema or a green small-data UI as sufficient evidence. The requested Hermes exports exist, while the runtime restart proofs here are web proofs. That distinction, and the separate scale evidence, are part of the result rather than qualifications to hide.
