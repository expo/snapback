
## M1 — accounts and profiles (2026-09-24)
Built real password accounts, persistent sessions, public owner-editable profiles, unique handles, and uploaded avatars, using Quarry and the published Expo client. Both required browser evidence paths passed; an iOS Hermes export exists. The compact schema and generated operations were easy. Most friction was mine: mutation IDs have a defined format; pending is not terminal; a profile form must not submit the whole returned row. Expo screen retention and a stale Metro graph complicated the tests. Existing React and browser-test familiarity helped, but no prior Snapback implementation was consulted. The README offered a directly useful account example and the guide explained receipt semantics. Relative to Convex, this felt like learning a smaller declarative server language rather than writing TypeScript handlers; relative to Supabase, auth plus assets plus public profile sync required less separate policy plumbing. No platform defect is established by this milestone.

## M2 — posts and follow graph (2026-09-24)
Built text, multi-image and video posts; Following and Global feeds; likes, reposts, direct replies, profile counts, and infinite pagination. The suite and all required choreography passed, with a refreshed Hermes export. The feed guide was unusually concrete: its public activity union and Following declaration compiled directly. Maintained row counts removed application counter bookkeeping, while diagnostics disclosed full-parent streaming costs. The main fights were frontend integration and test precision: the harness expects feed tabs accessible from profiles, initial replica acquisition could reset a scrolled page, and a test accidentally selected a media post sharing its text. The system FFmpeg was broken; Chromium decoded the fixture frame instead. General React and test experience helped; previous backend-specific implementation was not available. Compared with Supabase, the joined live data and aggregate maintenance required less coordination; compared with Convex, Quarry constrained the design more, and Following brings an explicit 1,000-event backfill window and full public replica acquisition tradeoff to revisit at scale.

## M3 — conversations, receipts, typing, and groups
Built deduplicated DMs, distinct groups, membership roles, quoted replies with paged history navigation, delivered/read watermarks, slowest-member receipts, and retained history after leaving. The final suite and choreography pass, and the iOS Hermes export is refreshed. Membership-scoped sync and retained-history declarations were concise; the guide clearly explained why retained reads must pin the group and avoid mixed authorization. Most friction came from the client lifecycle: a hard navigation could beat asynchronous mutation admission, so admin clicks now keep a synchronous tab-local intent and retry the same mutation ID after navigation. Isolated probes separated that issue from the retention engine, which retained history correctly. Typing needed throttling plus the guide's render-deadline filter. Repeated tests grew history beyond a page and exposed a missing quote-jump pagination path. General distributed-systems knowledge helped with monotonic receipts and rejoin positions; no other implementation was inspected. Compared with Convex, replica acquisition and navigation durability require more explicit thought; compared with Supabase, membership fanout and retained local data need far less custom replication code. No Snapback defect is established here.

## M4 — media messages, reactions, and edit/delete
Added fixture image/video messages and recipient playback, optional captions, one set-state reaction per person, caption/text editing, edited labels, and delete-for-everyone tombstones. The suite, choreography, and Hermes export pass. Asset placement and revocation were especially easy: clearing the row's asset column made the old asset fetch fail without an application download handler. Config-generated helpers enforce edit/delete windows using server time; an old seeded message is refused through the API. Quarry's unfamiliar helper namespace and `count(text)` spelling caused two quick diagnostic corrections. I also initially confused the React asset state with the imperative client's url-or-denied result. General schema and UI experience carried most of this milestone. Compared with Supabase, fewer independent storage policies were needed; compared with Convex, the asset lifecycle is more declarative and less flexible. The published package expressed the required behavior without a platform gap.

## M5 — ephemeral content, customization, and search
Added disappearing-message settings, once-only photos, admin chat identity editing, accent/background customization, and people/in-chat/grouped message search. Suite and all implemented choreography checks pass, including the five-minute close/reopen expiry check; the Hermes export is current. A separate Henry/Grace proof closed both accounts before expiry and verified message, asset, search, preview, and unread removal. Declarative `expire at` and `once` were the largest friction reducers so far. Search used the same indexed word-prefix engine online and offline, including NFC and case handling. The main application correction was removing a copied last-message preview that would outlive its source; preview and unread counts now read live messages. One repeated view-once UI click missed without a demonstrated cause; an unchanged rerun passed, so it is logged as ambiguous. TypeScript/JSX corrections were ordinary authoring mistakes. Existing security reasoning helped identify derived-data revocation leaks. Compared with Supabase, this eliminated a storage-consumption table, cleanup scheduler, and local-search mirror; compared with Convex, expiry and asset lifecycle were more concise, while understanding replica completeness remains additional work.

## M6 — offline writes, push seam, API, and replay
Completed durable offline sends, a logged provider worker driven by Quarry presence-guarded effects, a field-complete custom-client history API and standalone documented demo, and the full 13-verb replay adapter. Required suite and choreography pass; a web cold-relaunch proof restored history, cached media, and indexed search. An iOS Hermes bundle is exported without claiming simulator proof. The adapter's first sample run passed, but a retry exposed my changed-upload-ID bug: original upload references now persist under backend identity, and retry sends identical arguments. Stable write IDs and transactional effects made the final design straightforward. API history deliberately separates richer server receipt/reaction reads from retained device history. The fresh scale replay is running on its own clock, with its 10% checkpoint already verified; its final result will be recorded independently. Compared with Convex and Supabase, the integrated replica/outbox removes substantial queue and conflict code; understanding admission versus terminal success, schema acquisition, and asset retry identity is additional cognitive load. Published docs covered those distinctions, though the server's explicit changed-argument refusal was clearer than the prose suggesting replay simply returns an existing record.

## M8 — insights, scheduled digests, and multiple devices
Built the six server totals, seven UTC day buckets, Trending's rolling window and tie break, and a scheduled digest with transactional once-per-person/period effects. The suite and required choreography pass, with a final Hermes export. Separate proofs cover same-account live edits and reactions, offline queue persistence across page closure, and a real scheduled digest with every client closed and the backend restarted mid-period. The full scale replay completed and its invariant checks passed on its independent instance and clock; the final web client also displayed the populated scale profiles and Insights.

Maintained views were easy to add, including adoption onto the populated scale store. Scheduled job arguments already included period boundaries, so the backend owned the clock and idempotency. The difficult part was the boundary between online usefulness and completed local acquisition. My original whole-screen acquisition gate took too long with the full public post corpus; I kept a bounded initial wait and allowed documented server reads afterward, with an explicit offline-preparation notice. Following rejected a bounded post horizon with E_TIMELINE_SHAPE, so that restriction is a real published-model tradeoff. An intermediate removal of the wait broke the immediate dual-offline choreography; the final wait and roster-readiness handling restored it. A separate apparent scale-login failure was my Metro cache carrying the other instance's URL into an export; clean target-specific exports corrected it.

General experience with aggregate read models, idempotent consumers, and async UI state helped. No previous implementation or source repository was used. The docs supplied the required jobs, schedule, maintained-view, and fallback contracts; a clearer end-to-end cold-acquisition budget would have helped. Relative to Convex, the job and aggregate declarations were compact but less familiar than ordinary functions. Relative to Supabase, there was much less separate replication, storage-revocation, and outbox infrastructure. Native runtime confidence remains limited to the requested Hermes exports; the restart proofs executed on web. Final regressions of earlier affected milestones are running as handoff validation, without changing their original first-green timestamps.
