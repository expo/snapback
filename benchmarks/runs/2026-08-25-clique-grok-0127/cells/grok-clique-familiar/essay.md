# Essay — familiar Snapback versus Convex (and the rest)

I came into this lane with a Convex-shaped muscle memory: a schema, a handful of `query` / `mutation` modules, generated `api.*` handles, and React hooks that subscribe live. The familiar TypeScript profile (`snapback-familiar-ts-v1`) is explicitly aiming at that groove. After building Clique M1–M3 on published Snapback 0.1.27, the honest comparison is that the *spelling* is Convex-like and the *operating system around the spelling* is not.

## What felt like Convex

`defineSchema` / `defineTable` / `v.string()` / `v.id("posts")` is immediately readable if you have written Convex. Top-level function files exporting `query({ args, returns, handler })` and `mutation({ ... })` are the same grain of module. `useQuery` / `useMutation` from `@expo/snapback-react/familiar` collapse the live-query and settled-mutation stories into the names a Convex app already uses. Idempotent writes via client-supplied ids (`clientId` on posts and messages, `mutationId` on likes and follows) are the same pattern I would use on Convex to make a fixture log replayable. Indexes are declared next to the table, not in a separate migration DSL. Once a function actually committed, live updates across two browser contexts just showed up — feed cards, follow projection, DM bubbles — without me wiring a socket.

That last point matters. Clique's two-client proof is not a fake: Alice posts, Bob's Following tab updates; Alice types, Bob's conversation shows `…`. Convex's live queries would have given me the same qualitative feeling. Snapback's familiar hooks delivered it.

## What was Snapback-specific, and not a thin coat of paint

Every function carries `auth`, `reads`, and (for mutations) `writes` and `refusals`. Convex infers much of this, or treats it as a runtime concern; Snapback makes it a codegen-time contract. `ctx.refuse("HANDLE_TAKEN", {})` is not `throw new ConvexError`. Assets are first-class (`v.assetRef({ upload: "media.avatarUpload" })`, `ctx.assets.attach`) rather than "upload somewhere and store a URL." Auth is not a separate Clerk/Auth0 bolt-on and not Convex's "it just has users": it is `defineAuth` with password/recovery/guest policy, `auth: { mode: "sessions" }`, durable custody as the default, and a principal type on the table. Ephemeral typing is its own subsystem (`defineEphemeral`, `ephemeral.collection`, `useSnapbackActivityPresence` with `idleMs` and `touch`/`withdraw`), not a table you poll.

The codegen policy is an actual fork in the road. This lane had to opt into `"authoringProfile": "snapback-familiar-ts-v1"` in `snapback/codegen.policy.json`. The older brief still says `_generated/`; 0.1.27 refuses that directory and emits `generated/`. Getting this wrong is not a warning, it is a different backend. I did not fall back to `schema.mjs` / `functions.mjs`, and I would not describe that explicit profile as "the same thing with uglier files." It is a second authoring universe sharing a runtime.

The client provider story is the sharpest divergence from Convex. Convex's `ConvexProvider` is one object. Snapback on supervised Expo web injects `EXPO_PUBLIC_SNAPBACK_SUPERVISOR_ORIGIN`, mints an ambient session, and does **not** inline `EXPO_PUBLIC_SNAPBACK_URL`. Adopting the mint hid the auth form; signing it out crashed the provider with `SNAPBACK_AUTH_SESSION_EXPIRED`. The working landing was URL-first `SnapbackProvider` using the supervisor bootstrap's `binding.target.origin` and ignoring the minted bearer. That is not a Convex problem. It is also not documented on the familiar profile page in a way that would have saved the first hour.

Activity presence has the same split personality. `@expo/snapback-expo`'s `useSnapbackActivityPresence` refuses to run without an Expo application lifecycle context. A URL-first familiar provider does not provide one. The hook that actually works is the one from `@expo/snapback-react` (not the Expo facade), which defaults lifecycle to active. Convex has nothing like this layering.

## Operational texture versus Firebase, Supabase, and a hand-rolled Node API

Firebase would have given me auth and a realtime document tree on day one, and I would have spent M2 fighting security rules and fan-out for following feeds. Snapback's server-authoritative queries (following feed computed on the server from `follows` + `posts` + `reposts`) are closer to "I wrote the join" than to "I denormalized into the client's listener graph." That is a win versus RTDB. Versus Firestore it is closer to Convex than to collections-plus-rules.

Supabase would have been Postgres, RLS, and a realtime plugin. I would have been faster on "a table exists" and slower on "the following feed is a live, paginated, self-follow-aware projection with repost attribution." Snapback's `reads`/`writes` sets are more pedantic than RLS and less expressive; they did catch a missing `profiles` read on the chat list, which RLS would have expressed as a policy instead of a codegen field.

A hand-rolled Node API plus Postgres plus a websocket fan-out would have made M3 typing my problem in the worst way. Snapback's ephemeral collection is the right primitive: TTL, routing key, publish rate, `latest` delivery. I still had to learn that `touch()` on every keystroke starts a new generation and can cancel the in-flight publish, and that re-rendering the whole chrome on each character makes Playwright's `pressSequentially` blow a 2-second budget. Those are still better problems than inventing presence.

## The lifecycle is the product

Convex `npx convex dev` is a quiet companion. Snapback `snapback dev snapback --expo --expo-platform web` is an owner: it mints the application-ready receipt, supervises Metro, binds the Expo web origin, and is the only process I was allowed to start. When codegen wrote a `.tmp-*` directory, Metro's watcher threw ENOENT and the owner died (`SNAPBACK_EXPO_METRO_EXITED`). Restarting against the same `dev.sqlite3` without reseeding was required by the ruled lifecycle and happened to work; the account rows survived. That is closer to "a local Cloud" than to "a dev server." It is also closer to a product you can fail by starting twice.

I did not miss Convex's dashboard. I missed Convex's boringness. The familiar profile saved me from inventing a functions bundle format, and it did not save me from learning Snapback's identity binding, supervised Expo rendezvous, or ephemeral generation fence. If the pitch is "Convex-shaped on a different substrate," the substrate is doing more work than the shape admits — some of it (live queries, sessions, assets) in a way I would take again, and some of it (silent missing `EXPO_PUBLIC_SNAPBACK_URL`, Metro death on generate, presence hook split across packages) in a way I would not call familiar yet.
