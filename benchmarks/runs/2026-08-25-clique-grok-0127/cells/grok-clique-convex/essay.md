# Essay

Building Clique on Convex as a cold Expo Router web app felt like pairing a reactive database with a product that is mostly “live lists plus a few uniqueness rules.” That is a better fit than it first appears. Convex’s default posture is: declare tables, write queries and mutations, subscribe from the client, and let the runtime push diffs. For a social messenger whose M1–M3 bar is “the other browser sees it without refresh,” that posture is the product. I did not design a websocket protocol, a cache invalidation matrix, or a feed fan-out job. I wrote `feed.list` and `messages.list` and watched Alice’s screen update when Bob mutated. Compared with backends I know that treat realtime as an add-on—REST plus polling, or a separate pub/sub fabric you must remember to emit into—this was the main reason Convex felt like a first-class social-app backend rather than a datastore with extras.

Snapback, as I know it from prior work and public description, is the opposite kind of aid. It is an authoring environment: schema, clients, and a lot of generated surface so a lane can spend clock on product instead of glue. This lane forbade Snapback packages and Snapback scaffolds, so the comparison is experiential rather than a head-to-head of two Clique implementations. What I missed from that world was not magic sync. It was the boring path from zero to a running typed client: a known Expo+backend template, a documented port story, and a replay adapter that already spoke the fixture verbs. On Convex I had published docs, a CLI that really will run anonymously, and codegen that is good once `convex dev` is up. I did not have a Clique-shaped example. Every route, every `sm-*` wiring, and every seed replay line was hand-authored against the frozen kit. That is the competitor-control point of the exercise, and it showed: M1’s cost was mostly “get the runtime to exist,” M2’s cost was “make the kit’s feed tabs survive navigation,” and M3’s cost was “ephemeral typing under a stopwatch.”

Auth is the other axis where backends diverge. Convex does not ship password credentials as a built-in the way some BaaS products do. The brief is honest about that: use built-in if it fits, otherwise a named KDF. I used bcryptjs in a `"use node"` action, sessions as server rows, logout as a revoke flag. That is not glamorous, and it is not Convex Auth (which is oriented toward OAuth/OTP providers). It *is* the brief. Relative to Firebase Auth or Clerk, I spent more time on the password path and less time fighting redirect URIs. Relative to a hand-rolled Express+JWT stack, I spent almost no time on token plumbing in queries—every function takes a session token and looks it up. The gap I felt was not security; it was error transport. A thrown `Error` from an action arrives as a redacted “Server Error.” Duplicate handle and duplicate email are user-visible suite assertions. They needed `ConvexError`. That is a docs/ergonomics miss, not a capability miss: the platform can pass application errors, but the default looks like a crash.

Uniqueness and DMs were the schema fights I expected. Convex indexes are not unique constraints. Handle uniqueness, one-DM-per-pair, and idempotent seed IDs are “query then insert” in a mutation. Occupancy control makes that safe enough for sequential replay; it is not the same as a database unique index. Snapback-style systems and classic SQL both make “unique handle” a declaration. Here it is a convention. For Clique’s starter graph that is fine. I would not want to learn occupancy the hard way at a thousand concurrent signups.

Realtime durable data was easy; ephemeral typing was not. Live queries re-run when documents change, not when time passes. A typing row with `lastTypedAt` does not automatically disappear five seconds later. I scheduled a `runAfter` clear and also expired on the client. That is the workaround every Convex chat tutorial eventually writes. Compared with a presence channel (Ably, Firebase `onDisconnect`, a dedicated ephemeral bus), it is more table and less primitive. Compared with polling, it is still live. The choreography then asked for appearance within two seconds *including* the time Playwright spends typing a forty-five-character UUID. That is where the platform comparison ends and the instrument begins. Convex delivered the DM in a few hundred milliseconds. The typing assertion’s clock starts before a long `pressSequentially`. I could not make Playwright type a UUID in under two seconds on this host.

Media and storage were uneventful in the M1–M3 envelope: `generateUploadUrl`, POST bytes, `storage.getUrl`. No CDN policy language, no signed-cookie ceremony. Access is URL-bearer, which is the documented model and is acceptable until view-once/delete (out of this reduced run). Search was a client-side prefix filter over a small user table; I did not need Convex’s search index yet.

What I would take from this run: Convex is a strong default for “the other client should just see it,” a workable default for password auth if you accept Node actions and `ConvexError`, and a weak default for time-expiring ephemeral state unless you schedule it. Snapback’s value, from this side of the fence, looks like time-to-first-route and a frozen authoring loop—not a different consistency model. SQL’s value looks like constraints. Convex’s value is the subscription that comes with every query. Clique M1 and M2 spend that value immediately. M3 spends it on messages, then trips on a stopwatch that is mostly the harness’s typing loop.
