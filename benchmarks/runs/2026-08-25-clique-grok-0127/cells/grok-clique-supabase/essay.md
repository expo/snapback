# What this backend felt like

This lane was a cold build of Clique on hosted Supabase, Expo Router web only, using the frozen UI kit and the published JS client. I am writing this before totaling wall clocks. The comparison is to how I already understand Snapback and Convex as product-shaped backends, not to a checkout I opened.

Supabase’s best moment was also its most Postgres-shaped one. Handle uniqueness, one DM per pair, and “set this follow/like/repost, do not flip it” all wanted a unique index and an idempotent write. I could declare that in SQL, wrap it in a `SECURITY DEFINER` function, and have the Expo client and the replay adapter call the same RPC. That is a real authoring advantage: the mutation path is one place, and the constraint fails closed. Built-in password auth similarly absorbed M1 instead of forcing a hand-rolled KDF. I spent time on RLS recursion and replica identity, not on hashing.

Where it felt worse than Convex is liveness. Convex’s default posture is “subscribe to the query you already wrote.” Here, live profile edits, feed likes, and DM delivery were assembled from `postgres_changes`, a namespaced broadcast channel for typing, and short poll fallbacks when the hosted Realtime path was silent or slow. That combination works, and the M1/M2/M3 choreography greens used it, but it is not one primitive. Typing in particular is client-side expiry on top of broadcast. Convex would have made me argue with occupancy or a mutation table; Snapback, as I understand the instrument’s own stack, would have given me a subscription that already meant “this conversation.” I did not get that for free from Supabase.

Storage was closer to fine than to painful. Public buckets under `grokclq25_avatars` and `grokclq25_media`, path-in-the-row, URL on the client. Avatar rendering on RN-web was a DOM surprise (the `testID` sits on a wrapper `div`, the bytes are an inner `img`), not a policy surprise. I would not call this Convex-level “just put a blob in the document,” and I would not call it a CORS death march either.

The Expo web host fought me in ways that are not backend-shaped but still ate the authoring clock. Metro-plus-DevTools tried to launch a sandboxed Chrome helper and died; the working proof is `expo export` plus a static server on 48300. `expo-router`’s `Link asChild` crashed RN-web with a CSSStyleDeclaration error, so navigation is `router.push`. Playwright `fill` on kit `TextInput`s sometimes wrote the DOM and not React state, which disabled Send in DMs until I bridged `input` events. None of that is Supabase’s fault. All of it is the cost of “Expo Router web on Linux without a native toolchain.”

Relative to Snapback: I missed having a stack that was designed for this exact brief. Snapback’s pitch, as I carry it, is that Clique’s subscriptions, identity, and test IDs are the product, not an integration. On Supabase I was translating the brief into Postgres. That translation is honest and often elegant (DM keys, feed unions of originals and reposts). It is also a pile of policies, publication grants, and RPC signatures that PostgREST will reject if you omit a named argument. I never wondered whether last-write-wins would work; I did wonder whether a table was in `supabase_realtime`.

Relative to Convex: I missed reactive queries and in-code schema that does not drift from the client types. I did not miss Convex’s weaker story for “declare this unique or the write is wrong,” which is exactly where SQL earned its keep. Auth on Convex, in my prior picture, is more glue; Auth on Supabase was a built-in that matched the brief’s password rule. File storage on Convex is a separate product conversation; here it was a bucket name and a policy.

If I had to name the texture of the run in one line: Postgres let me say the data model; Realtime and Expo web made me assemble the experience. That is a fair deal for M1–M3, and it left a visible seam wherever the brief wanted ephemeral state or native proof.
