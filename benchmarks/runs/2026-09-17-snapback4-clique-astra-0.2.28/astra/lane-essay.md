# Building Clique with the published Snapback 4 surface

The most consequential property of this build was that the backend program also described what the client could know and predict. Clique needed more than ordinary CRUD: it needed an offline message queue, receipts across devices, membership-sensitive history, consumable images, expiring content, public feeds and scheduled work. In a conventional stack I would expect several implementations of the same idea to appear along that path. There would be server validation, client optimism, cache invalidation and background processing, each with its own vocabulary. Quarry brought those concerns into one declared model. That reduced duplication, while making the declarations themselves a larger part of the engineering task.

This is a cold-build comparison based on the work in this lane and my general knowledge of the alternatives. I did not run Convex or Supabase alongside it, inspect an earlier Snapback checkout, or consult a previous Clique implementation. I therefore cannot make comparative speed claims or attribute a measured improvement to a particular older Snapback release. Familiarity with React, relational modeling, indexing and idempotent distributed operations helped; familiarity with this application's prior source did not. Where earlier Snapback generations enter the comparison, the useful question is what this published surface made possible without reaching into an implementation repository.

The first stages were relatively ordinary product engineering. Password accounts, editable profiles, unique handles and public social content fit a concise relational schema. The strict generated API gave the Expo Router client a concrete set of operations. It was useful that an image field represented a managed asset rather than an arbitrary URL: avatar upload and rendering used the same asset mechanism that later supported messages and revocation. UI composition still took real work. Routing, retained screens, file pickers and accessible identity values produced several of the early mistakes. Those mistakes did not become more interesting merely because they occurred beside a novel backend.

Convex is a useful comparison at this stage because its transactional functions and reactive queries also let a product engineer move quickly without building a conventional API server. I would expect its TypeScript function surface to be more immediately familiar than Quarry. In this build, however, the unfamiliar language forced me to state indexes, permissions and synchronization before assuming that a query would behave well. A successful check was more than syntax validation: it could explain residency, prediction and bounded work. That information changed implementation choices while the application was still small.

Supabase offers a different kind of familiarity. Postgres constraints, indexes and SQL are a strong foundation for profiles, follows and content. An experienced SQL engineer can express much of the same data model comfortably. For this particular application, the additional work would accumulate around the browser/native replica: which rows belong on a device, how offline mutations are represented, how their predictions are reconciled, and what should happen to retained bytes after authorization changes. Supabase provides building blocks for authentication, storage and realtime updates, but those building blocks do not by themselves define this app's complete offline protocol. Snapback's local client and managed assets supplied a more integrated answer here.

Messaging made that distinction concrete. The server assigns an ordinal in the same mutation that inserts a message. Recipients are captured at send time, while receipt calculation consults current membership and monotonic delivered/read watermarks. The same mutation can predict a pending row on a device and later settle with the authoritative order. I did not write a second client-only message reducer with subtly different validation. A browser proof eventually showed pending messages surviving a cold offline reload and arriving in order after reconnect. That is a meaningful reduction in the amount of application-owned synchronization code. It is also a claim with a boundary: the native deliverables here are Hermes exports, not simulator execution evidence.

The backend did not eliminate offline design work. A dynamic web import initially requested a chunk after a network cut; the fix was a static platform-specific device import. Later, opening an existing DM still went through the online pair-deduplication mutation, so a cold offline route could not resolve its conversation even though its history was stored locally. Adding a replica-readable lookup fixed the navigation boundary. These were useful reminders that an offline-capable database does not automatically make every surrounding application path offline-capable. The application shell, credentials, routing and managed-byte lifecycle all have to cooperate.

Media and disappearance were among the clearest places where the integrated model helped. Expiry was a server field and index policy, rather than a timer in an open screen. A separate proof closed its clients, waited for the configured deadline, and then found both the message and its asset unavailable. View-once access was enforced by the asset door, with UI state preventing an accidental second opening and explicit revocation of the viewer's object URL. In a hand-built Express/Postgres stack I would expect to own the expiry worker, access-token or signed-URL policy, asset deletion logic and local cache invalidation contract separately. Those pieces are manageable, but their interaction is exactly where a messenger becomes expensive to make trustworthy.

Scheduled work was similarly direct. The digest walks each target's memberships, counts activity for the configured period, writes an emission marker and emits through a durable provider seam. The TypeScript worker only logs the emitted payload; it does not select recipients or implement business rules. The isolated digest proof covered a restart mid-period, an unauthorized conversation, a user with no activity and an empty following period. This felt closer to adding another part of the backend program than provisioning another service. Convex's scheduling model can provide a similarly cohesive experience; with Supabase I would expect to choose a combination of SQL functions, scheduling and an external or hosted function boundary. The tradeoff here is that Quarry's job envelopes and available expression forms become constraints the application must understand.

Aggregation exposed both the strengths and the rough edges of the language. Lifetime counts and UTC-day buckets were compact maintained views. They avoided turning Insights into client-side pagination of a corpus. Trending needed a more deliberate index: hour, score, timestamp and id, with an exact time predicate and explicit hour lanes. A maintain lookup returns a scalar when its group is fully specified, something I initially handled incorrectly in the scale verifier. Merge lanes could not be generated from a range, so they had to be written out. Schedule syntax accepted minute/hour/day periods rather than the seconds notation I first generated. These were documented constraints, and the diagnostics pointed toward repairs, but they were real cognitive costs.

The Following feed was the largest change in the shape of the work. A direct merge over followed authors was straightforward and passed functional tests. The published hybrid recipe offered a stronger large-account path: ordinary authors deliver references to private inboxes, while promoted authors use a bounded broadcast merge. Adopting it added routing tables, explicit caps, atomic bridges from application mutations and a migration for existing records. The recipe reduced algorithm design work, but it did not make integration free. A regression caught my accidental removal of the previous projection's `post` alias. I also kept original and repost identities distinct so self-repost attribution could coexist with the original event. This is the sort of work that a framework can structure well without making it disappear.

The compiler's warnings encouraged a broader view of performance than server latency alone. Public source rows, maintained counts and feed projections all contribute to what a cold device acquires. A fast query can sit on top of an expensive replica. The public corpus remains a material cost in this implementation, even after improving the Following read path. That is an advantage of having residency described in the backend surface: the cost is visible and discussable. It is not evidence that the cost has vanished. The replay and its independent invariant checks are intended to keep that distinction honest.

The published documentation was sufficient to complete the product work without reading Snapback source. It was also substantial. I moved among the package README, client and operations reference, guide cards, diagnostics and generated types. Working examples were especially valuable for presence-gated effects, jobs and fan-out. A compiler diagnostic that explained why a profile read inside a presence branch disabled prediction saved a much harder offline debugging session. Conversely, the conventional worker entry and Node module mode produced avoidable setup loops. A single correct example often carried more practical value than a broad promise about what the platform supports.

Compared with earlier-generation backend abstractions, the distinctive result is the explicit connection among authorization, replication, prediction, expiry and durable effects. I cannot claim a measured generation-over-generation improvement from this run. I can say that the pinned published package expressed those parts of Clique, and that I did not need to introduce a TypeScript business-logic server as an escape hatch. The costs moved toward schema design, bounded-query reasoning, published-recipe integration and careful client lifecycle work. For an application whose defining requirements include durable offline interaction and revocable media, that was a useful trade. For a simpler online application, the additional language and residency concepts would have a less obvious payoff.

The scale run supplied a useful final check on those distinctions. An older replay instance reached its halfway invariant check with one missing self-repost: my event key had conflated an original publication with its author reposting it. The finished schema already represented those separately. I preserved the failed instance and restarted the fixture on a fresh final-schema instance, rather than repairing the measured dataset with an extra write. The compiler could prove the key was unique; only a workload that exercised both meanings revealed that I had chosen the wrong identity. That boundary between language guarantees and product semantics remains familiar across all these backends.

A final deployment check also caught a misleading timeout: a cached Expo web bundle still pointed to the development backend, so a scale-only account could not authenticate. That was an export-cache mistake, not evidence about replication speed. Recording the actual page error before assigning blame mattered as much as the backend diagnostics.

The correctly targeted cold client then revealed a real cost: unbounded social source rows, original event rows, and private feed copies had all been declared resident. Published sync horizons let me bound those overlapping social views without deleting server data. The full fixture invariants, offline queue proof, and browser flow passed afterward. Cold acquisition still exceeded the brief's probe timeout. This is the most concrete remaining performance gap: fast server queries do not compensate for an expensive initial replica, and declarative synchronization still requires a deliberate residency budget.
