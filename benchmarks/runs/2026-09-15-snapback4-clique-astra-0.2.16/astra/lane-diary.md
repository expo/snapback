# M1 — Accounts and profiles

Built password signup/login, persisted expiring sessions, server logout, public profiles, unique handles, all profile fields, avatar upload and live views. The schema and asset placement were easy: one public table and two mutations suffice, and the React/local client handles observation. Setup fought me in ordinary tooling ways: read-only copied harness directories, a missing sibling harness import, and Node selection contrary to the environment overlay. My general React and Expo familiarity saved navigation work; I had no prior Snapback implementation to reuse. The README was unusually comprehensive and the compiler's unbounded-sync note was clear. Compared with Convex this makes local replicas explicit much earlier; compared with Supabase it avoids separately wiring SQL, auth and storage policies. This milestone does not establish scale or offline messaging behavior.

# M2 — Posts and follow graph

Built original/media posts, feed pagination, follow counts and projection, likes, attributed set-state reposts, direct replies and profile post lists. Built-in uploads made image and video storage straightforward; generated operation types and mechanical index disambiguation helped. Most friction came from my UI assumptions: a native-only image helper, navigation that did not expose tabs from profile screens, and a broken host ffmpeg dynamic-library dependency. The documented harness adapter corrected its original-repository fixture path. I extracted a real fixture video frame with Chromium after ffmpeg failed.

Prior React/Expo knowledge helped, but also caused the native-only helper error. Quarry's wide-merge note makes the cost of Following explicit; I retained the simple read merge pending the scale measurement rather than claiming performance. Compared with SQL, the required index prefixes are less forgiving but more visible. Compared with Convex, counters need little code; local query completeness is an extra concept to understand. No Snapback platform defect has been established so far.

# M3 — Messaging core

Built unique DMs, separate groups, membership administration, quoted replies, typing, monotonic delivery/read receipts, sender avatars, retained removed-member history and the starter chat replay. Per-chat ordinals establish server arrival order; they are sequence numbers, not a maintained visible-message count. The backend compiled on the first pass. Keeping a recipient snapshot in each message and per-member receipt watermarks avoided a receipt row for every recipient/message pair.

The local client made live delivery and expiring typing simple. The difficult boundary was an administrative click immediately followed by document navigation: the removal had not reached the server, although a direct mutation worked. A synchronous-start authenticated keepalive request resolved this for administration. Attribution remains ambiguous between the application’s navigation contract and the replica lifecycle; no server authorization defect was observed. A suite start also raced Metro readiness, which I fixed in the launcher. Compared with Supabase, the membership rule doubles as an explicit delivery partition; compared with Convex, retained local history is a declared policy instead of separate cache bookkeeping. Native playback and Hermes exports exist, but there is no simulator proof claim.

# M4 — Media, reactions, edit/delete

Added image/video messages, caption edits, arbitrary emoji reactions, edited labels and delete-for-everyone tombstones. The shortened fixture config generates Quarry constants; mutation checks use server `now`, never caller timestamps. Clearing the asset column made deletion denial automatic, and the suite independently fetched before deletion and confirmed denial afterward. Both the suite and required two-client checks passed, with a Hermes artifact.

The reaction query initially used a message-only prefix although authorization depended on conversation. The compiler named that completeness problem; adding a conversation/message index resolved it before verification. This explicit relationship between index shape and authorization is different from ordinary SQL or Convex and useful once understood. General frontend familiarity handled media players and picker wiring; the backend’s asset-placement model saved storage-policy plumbing. A supplementary real-time edit-window probe was launched after green and is separately recorded, outside the green claim.

# M5 — Expiry, view-once, customization and search

Built disappearing messages, server one-view photos, chat colors/background/name/description, and people, in-chat and grouped global message search. The same indexed queries serve warm-offline search. Both the choreography and an independent Erin/Frank probe waited real shortened-config time with clients closed; expired history vanished and the asset endpoint denied access. View-once bytes stay temporary, with explicit viewer cleanup on tombstone/unmount.

Expiry and one-view enforcement were notably easier than building scheduler cleanup plus signed-URL revocation on a conventional storage service. The engine owns row expiry and asset placement. Quarry’s shape-after-filter syntax caught me once, and I initially guessed colors before reading the frozen palette; both were author errors. Reviewing starter bookkeeping also exposed my local receipt ledger’s credential-bearing keys and instance ambiguity. I removed it and moved receipts into private backend rows containing only action ordinals. Re-running each installed segment now performs no new actions. General SQL/search familiarity helped with prefixes, but the explicit device-completeness contract remains different from the alternatives. No cold-offline proof is claimed yet.

## M6 — Offline, public API, and replay adapter
Built the push logging seam, authenticated custom-client example and protocol documentation, complete 13-verb settled replay adapter, checkpoint invariant checker, and offline app-shell caching. The published local client made the basic outbox straightforward. A redundant message-existence guard prevented prediction; the diagnostic led to removing it and relying on stable mutation IDs for retry idempotence. Static web export plus a narrow service worker made a cold offline launch possible without caching private asset responses indiscriminately. The sample replay settled all 50 actions and all 13 verbs, with actual-state assertions. Full scale execution follows M8 so its checkpoint probes include the final read models. Prior knowledge of HTTP idempotency and service workers helped; no familiarity with an earlier Snapback implementation was used. Compared with Supabase, durable local writes required less custom queue code; compared with Convex, the explicit replica completeness and prediction contract demanded more attention. Native Hermes export succeeded; device execution is not claimed.

## M8 — Insights, scheduled digest, and multiple devices
Built server-maintained lifetime, UTC-day and period engagement facts, a ten-row indexed trending read whose entries expire after a day, and the frozen kit screens. The digest is a Quarry schedule with resumable per-membership work and per-user emissions. It records each period atomically and the logging worker deduplicates effect IDs. The no-client test checked counts, a genuinely quiet next period, private-chat exclusion, tombstones and backend restarts. Browser choreography proved account-wide read state and two offline writers; a separate persistent-browser restart proved queued writes survived relaunch. The iOS Hermes bundle was exported, without claiming simulator execution.

Maintains and expiry made the aggregate screens unusually direct. The difficult part was choosing the right shape for work: an initial 500-lane Following merge failed the relative scale rule despite being fast in absolute milliseconds. The published feed recipe gave a concrete alternative. The optimized checkpoint uses a small celebrity merge and indexed delivery rows; those rows contain only public follow/post data. A first scale attempt also exhausted loopback ephemeral sockets, so the adapter now paces actions and retries transport failures with the same operation ID. These are different failure classes and are logged separately.

Prior knowledge of database indexes, outboxes, at-least-once effect delivery and service-worker scope saved time. Quarry's structural read-rule checks required learning its proof model: an OR rule was insufficient for a cleanup sweep even after adding an actor prefix. I changed the projection's public read policy to match its entirely public inputs. No competitor implementation was consulted. Compared with Convex, the daily job and materialized counters ask for more explicit bounded-work planning; compared with Supabase, the replica and time-based asset revocation remove substantial glue. I cannot make a measured claim about earlier Snapback generations from this cold build. The important difference in this published surface is that rules, prediction, expiry and scheduled work share the same executable schema. The scale replay and its remaining full-corpus checks continue on their separate clock.

Final M8 review: the native session-store wrapper initially omitted the SecureStore-safe key normalization shown in the generated starter. I restored it, removed unused scaffold entry points, expanded typechecking to include all Router files, and exported the final Hermes bundle again. This was my integration error. Native execution remains unclaimed; an export cannot establish device behavior.
