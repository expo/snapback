# Build diary

## M1 — Accounts and profiles

Built password accounts, public profiles, unique handles, editable profile fields, policy-bound avatar uploads, browser session restoration, logout, and the Expo Router shell. The native arm uses the exact published Expo module and exports Hermes. The README's complete account recipe made the backend small; built-in Argon2 and asset authorization removed security plumbing I would otherwise need to assemble.

My frontend state timing fought me: the edit form mounted before the profile arrived, and login initially retained the Settings route. These were my errors, surfaced by the browser suite and choreography. Copying a read-only harness also copied its permissions, and its sibling metering imports needed to be retained. Familiarity with React and ordinary HTTP made those fixes straightforward; no prior Snapback implementation was consulted. Compared with Supabase, I wrote fewer separate policies and storage rules; compared with Convex, the declarative profile mutation is shorter, though learning a new language and several completeness states adds orientation cost. No backend capability gap established in M1.

## M2 — Posts and follow graph

Built both feeds, follow counts, self-feed membership, likes, reposts, direct reply threads, profile posts, image/video composition and playback, and pagination. The activity/Following recipe and maintained counts were concise and the compiler gave useful bounded-cost statements. Generated hooks made live counters straightforward.

The surprising failure was asset placement inside a list: the schema compiled and stored image IDs, but authorized recipient downloads returned E_ASSET_UNKNOWN. Four scalar asset columns fixed it while a helper reconstructs the client list. This is a platform defect candidate retained with a direct HTTP probe; the backend can still express the product. My own errors included using a native-only image resolver on web, omitting persistent feed tabs that choreography expected after profile visits, and running a mutation-heavy suite concurrently with choreography. That overlap displaced the harness target past page one and wasted retry time. SQL/Supabase familiarity suggested normalized media rows; this app instead uses its pinned maximum of four scalar slots. Convex would make arbitrary list processing familiar TypeScript, while storage authorization would need more explicit server code. Snapback's feed maintenance saved substantial application code, but compiler acceptance did not establish asset-list runtime behavior.

## M3 — Messaging core

Built unique DMs, independent groups, membership administration, text and quoted messages, background delivery acknowledgement, monotonic read marks, aggregate receipts, and ephemeral typing. The published rules/receipts/ephemeral cards made these concepts expressible without a separate realtime service. The compiler's self-equality diagnostic caught a nested-scope error with the exact replacement.

This milestone demanded more frontend discipline than the backend syntax suggested. A DM route accidentally selected a group containing the counterpart. Unnecessary delivery writes delayed ephemeral publication while the replica caught up. A loading account query could remount settings. A content query that joined live receipt state hid retained messages after removal; separating content from receipt state fixed it, verified by an isolated removal probe and full choreography. Recipient records now bind to a membership identity so rejoining cannot revive old obligations. These are mostly application design errors, not evidence that the backend lacks the features.

Compared with familiar Convex patterns, Quarry makes authorization and replica residency visible in the schema instead of embedding them in functions. Compared with Supabase, the app did not need separate channel plumbing or a custom durable message cache. The tradeoff is learning which composed reads remain locally answerable after authorization changes. Prior React knowledge helped diagnose remounts; database knowledge helped model recipient identity. No prior app implementation was read.

## M4
Built photo/video messages, one reaction per member, edit and delete windows driven by config, and asset revocation. Quarry mutations and server asset authorization were easy to extend. UI optimistic completion races fought me: a completed send could clear a later draft; conditional clearing fixed it. Prior React familiarity helped find that race. The asset docs were sufficient for scalar placements; list asset placement from M2 remains the workaround. Compared with Supabase, expiry and byte authorization require less infrastructure; compared with Convex, generated operations and optimistic writes shift more responsibility into the declarative schema. Both suite and choreography passed, with an iOS Hermes export.

## M5
Built server-declared message expiry, per-principal view-once photos, synchronized color/background and group metadata, and three search scopes. The served guide made these straightforward: `expire at`, `once`, and indexed `matching` map closely to the product requirements. Optional-value narrowing required a local TTL binding; the diagnostic gave the exact rewrite. React media handles must still be explicitly released on close. Familiarity with browser lifecycle and access-controlled assets helped. Compared with SQL backends, eliminating a purge scheduler and a custom one-time download ledger saved substantial plumbing. The cost is learning Quarry syntax and the distinction between retained history and live membership-dependent metadata. Both acceptance and every choreography check passed; real-time unattended expiry also returned an absent row and HTTP 404 bytes.

## M6
Built the push worker with durable logged payloads, a raw-HTTP third-party API guide and demo, a complete action-log adapter, and an exported offline web shell. All 50 sample actions settled and their resulting state passed conformance. The 10% scale checkpoint also matched its manifest. Offline history and search worked through a cold reload, but sends queued without a predicted row: eligible does not mean every call predicts. A small durable view-state record, keyed by account and SDK intent, fills that UI gap while the SDK remains the sole transport queue. I initially used UUIDs for SDK intent IDs; its diagnostic correctly required mintId. Prior offline-app experience helped separate transport authority from presentation. Compared with Convex or Supabase, the built-in outbox and replica remove large subsystems; incomplete prediction still forces explicit UX. Native Hermes export, suite and choreography passed. No simulator claim is made.

## M8
Built maintained lifetime and daily Insights, fresh Trending, a server-scheduled digest through the logged push seam, and same-account offline convergence. The counters and UTC bucket functions were easy once I read the maintains card. The digest helper initially crossed an automatic-sweep boundary; moving its locals and inner loops into the documented recipient sweep made transaction ownership explicit. An unattended proof crossed two real schedule periods and a backend restart: exact authorized counts, no inactive-user digest, and no following-period repeat. Same-account message/read convergence and dual offline queues passed choreography. A final M3 regression then exposed another UI completion race around quoted replies; conditional cleanup fixed it. Prior knowledge of transactional outboxes helped reason about emission versus provider delivery. Compared with SQL plus a cron worker, the schedule/once-key combination reduced glue; compared with general TypeScript backends, the Quarry sweep rules are an extra language constraint with useful diagnostics. Native Hermes export is present; simulator behavior remains unclaimed.
