# Building Clique with Snapback 4

Clique exposed the parts of a backend that a small CRUD demonstration can hide. The difficult work was deciding what a device knows, what it may retain after losing access, what a queued operation means before the server accepts it, and who owns time. Snapback 4 supplied unusually direct answers to several of those questions. It also made me learn a new set of boundaries rather than letting me treat every operation as ordinary application code.

The strongest part of this experience was the proximity between the product specification and the backend program. A message has a membership audience, a limited acquisition horizon, an optional expiry deadline, and media whose authorization follows the message. Quarry can state those properties near the fields. Disappearing content did not require me to invent a separate purge service. A view-once image did not require an application table of download tickets and consumed flags. The server refused an expired row and its bytes without a client causing the cleanup. That is a substantial reduction in the number of mechanisms I had to coordinate.

The schema was also the program. Mutations assigned message order, checked edit windows, changed reactions, and admitted notifications. Queries described pages and shaped the related profile information. Jobs and schedules handled the digest. This was useful under time pressure because there was one place to inspect authorization and data transitions. It was less comfortable when I brought habits from JavaScript into Quarry. Optional expressions needed explicit narrowing, list construction had its own rules, and a helper containing a loop was not interchangeable with a loop inside a job's recipient sweep. The compiler usually supplied a concrete rewrite. Those diagnostics were more useful than a broad claim that something was unsupported.

The replica changed the client architecture. I used the same declared queries for online and held data, and the published web shell made the exported client available after an offline reload. Ordinary viewed images and videos came back from retained storage. View-once bytes did not. The transport outbox survived a restart. These are expensive subsystems to build carefully in an application, especially when account changes, revocation, and uncertain network outcomes must agree. Having them behind the client contract freed me to spend time on product behavior.

That did not eliminate optimistic UI work. My first implementation assumed that a mutation eligible for prediction would always produce a pending message row. It did not. The client returned an explicit pending receipt explaining that local data did not justify a prediction. The guide distinguishes eligibility from a guarantee, so the assumption was mine. I added durable presentation metadata keyed by account, conversation, and the SDK's saved intent ID. The backend client still owns transport, ordering, and settlement; the additional record gives the user something visible when there is no predicted row. This distinction matters. A second application transport queue would have created competing authorities and made restart behavior harder to explain.

The optimistic surface also exposed ordinary React mistakes quickly. A send could finish after the user had selected the next attachment or reply target. Unconditional cleanup then erased that newer draft state. Conditional cleanup fixed the text, attachment, and quote cases. Those were application races, not backend failures. A good platform cannot prevent a component from clearing the wrong state. It can, however, make the distinction between submission, durable admission, and authoritative settlement clear enough that the engineer can diagnose the race. Snapback's pending and terminal receipts provided that vocabulary.

The most concrete platform problem I encountered involved media placement. The compiler accepted a list of image values on a post, but authorized recipients could not fetch the stored images through that representation. Four scalar image columns, projected back into a list for the client, worked. I retained the diagnostic evidence rather than treating the workaround as proof that the original surface was sound. The cost was modest for this product because its image limit is fixed, but the lesson is broader: a type that compiles must still be tested at the byte-serving authorization boundary. An upload response and an attractive preview are not enough.

Private history required a separate modeling decision. A removed member should retain already delivered message content while losing new delivery and current membership-dependent information. Initially I shaped retained content together with live receipt data. The live dependency disappeared on removal and obscured the history that the device was entitled to retain. Splitting the content query from live receipt state restored the intended behavior. A later regression also showed that a media viewer should outlive its refreshing message row; moving it to an account-level modal made that lifecycle explicit. This is a case where the platform's explicit retention model helped, but only after I respected the different lifetimes of the related facts.

The reporting and scheduling work was reassuringly server-shaped. Insights totals came from maintained counts, including reference-based attribution and UTC day buckets. The client did not page through a post corpus to invent totals. Trending used a bounded ranked query over original posts in the current time window. The digest walked each recipient's memberships before counting private messages, excluded tombstones and expired content, and used a business key to deduplicate emission for a period. The provider seam separately deduplicated its logged effect IDs. The unattended test included a backend restart and a quiet subsequent period. Keeping schedule admission, transactional emission, and provider execution separate made the result easier to audit.

Compared with the Convex architecture I would normally reach for, Quarry gives up the familiarity and generality of TypeScript in exchange for more declarative information about residency, bounded reads, expiry, and prediction. With Convex I would expect to be comfortable expressing the business transitions immediately, while treating offline durability and media retention as explicit architectural work to investigate and integrate. Here those facilities were already part of the installed client. The trade was learning when a query is complete, when a row is actually held, and why an otherwise eligible write cannot predict. This is an architectural comparison from my existing knowledge, not a timed Convex implementation or a claim about every current Convex integration.

Compared with a Supabase design, the reduction in coordination was even more visible. My usual SQL approach would combine tables and row-level policies with storage authorization, subscriptions, client persistence, a synchronization protocol, and scheduled work. PostgreSQL would give me familiar inspection and aggregation tools and wide freedom to express transformations. Snapback supplied a more integrated path from membership rules to device holdings and asset lifetime. The cost is that a familiar SQL-shaped idea may need a different declared query or sweep. I still used the package's documented read-only SQL inspection to verify replay state independently; I did not use it to import or bypass the fixture's mutation path.

I cannot honestly claim an experiential speed comparison with earlier Snapback generations from this run. I did not inspect their implementations or prior benchmark diaries. The published guide mentions older storage formats, which establishes a compatibility boundary, not a measurement of earlier capability. What I can say is that this release presents schema, rules, sync, queries, mutations, effects, jobs, and schedules as one authoring surface, with generated client types and runnable recipes. That integrated surface is the property worth comparing in a future controlled generation-to-generation run. Reusing recollections of an older limitation would have been a poor substitute for trying the installed version.

The remaining caution is about proof. A Hermes export establishes that the native bundle builds; it does not establish simulator behavior. Browser offline tests establish browser behavior, even when the native arm shares the contract. A successful replay and complete query answers at named checkpoints are useful evidence, but they are not a repeated latency study or a secret holdout score. I kept those claims separate. The final impression is of a backend that removes several difficult distributed-client mechanisms from application ownership, while demanding unusually precise thinking about what the device can prove. That is a worthwhile change in the shape of the work, provided the application treats incompleteness and pending-without-prediction as normal product states.
