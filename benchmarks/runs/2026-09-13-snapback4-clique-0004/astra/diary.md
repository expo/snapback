Prior React/Expo and HTTP familiarity saved time assembling navigation and tests; no prior Snapback implementation was consulted. Relative to Convex's reactive server queries, the replica adds an explicit device boot but makes offline continuity part of the client choice. Relative to Supabase, this profile slice needed fewer separately configured auth, policy, storage, and realtime pieces. These are architectural comparisons from model knowledge, not comparative timings.

M8 boundary — Aggregates, scheduled work and deeper offline

Built the six server-maintained Insights totals and seven UTC day buckets, authoritative refresh screens, a like-ranked expiring Trending index, and the fixture-configured daily digest. The digest is a Quarry job with resumable chunks and transactional effect emission, not a client timer. A closed-client test created fresh personas and scoped activity, restarted the backend mid-period, observed exact follower/post/unread counts once per active user, excluded a private chat from a non-member's counts and excluded a tombstone, then observed no digest in the next empty period. A synthetic historical post on an isolated development instance proved that an old popular post is absent; its five likes and fresh control used normal mutations, and no replay timestamp was changed.

The five M8 choreography checks passed: Insights refresh after another user's like, same-account live delivery, shared read-state clearing, dual-offline convergence and normal receipts. An additional two-client test proved live edit/reaction convergence and two pending writes surviving page destruction and cold reopening with the backend blocked, then flushing in order. This is web evidence; the native deliverable is a fresh Hermes export, not a simulator claim. The M2 suite and all nine choreography checks were rerun successfully after the feed changes.

The feed read model required the most design work. A direct fan-out loop both violated Quarry's complete-group certificate when uncapped and would have made a 900-follower author's write much larger than a small author's. I changed it to one pending delivery on the write path plus a resumable materialization job. Following reads merge the pending lane with the reader's materialized lane. A newly changed follow graph temporarily uses the authorized catalog until the job has covered that graph; query incompleteness is explicit. This keeps immediate visibility without making the author wait for every follower's row. Scale measurements will determine the real cost, rather than treating the architecture as a performance result.

Other corrections were ordinary compiler feedback: exact sync audiences, jobs' top-level chunk grammar, optional-value narrowing, module job naming, and a missing ID tie-break for cursor paging. I kept the rejected designs and diagnostics. The compiler consistently left the previous valid generation serving while an edit failed.

SQL familiarity made maintained aggregates, calendar buckets and ranking keys easy to reason about. Convex's general-purpose transaction functions would have allowed the first fan-out loop without this early structural refusal; Supabase would give more direct aggregate/range syntax but need more separately coordinated policy, scheduled-job and realtime plumbing. Snapback reduced the number of synchronization mechanisms I had to invent, while its bounded language made read-model design more deliberate.
