# M7 diary

I inherited a working Quarry backend and Expo application without the builder's context. I read the lane's code, API documentation, acceptance scripts, and factual run reports. I first installed the starter action segments into a new deployment and exported authenticated per-persona snapshots. That made preservation a concrete comparison rather than an assumption about what a schema activation ought to do.

I added polls as message rows with bounded option lists, plus a membership-scoped votes table keyed by message and principal. Votes are upserts expressing a selected option, sent through the existing durable mutation client. The frozen poll composer/display components fit the existing chat shell easily. The first real browser test could create a poll and cast a vote without a custom queue, polling loop, or tally service. The two-client harness subsequently observed the live changes and an offline pending vote that settled after reconnect.

The count migration required more thought. The old conversation sequence counter measures arrivals, so it cannot represent currently visible messages. I added a contribution field to each message and summed it by conversation. Sends and polls contribute one, tombstones contribute zero, and expiry removes the contribution when the engine sweeps the row. The count is exposed on conversation reads and displayed in settings. The required contribution field also makes an omitted forward write visible as a validation error instead of silently drifting the count.

The awkward part was reaching the deployment's data with the backfill. I first tried the published local job command from a release directory. Before serving that release, it created an empty development store; after serving established the deployment link, it refused the deployment store. I archived the accidental empty store and used a temporary scheduled Quarry job instead. I also had to move that job into the root schema because my attempted module schedule references did not compile. These were my integration corrections, not demonstrated backend defects.

The final migration followed expand, backfill, and contract stages. The compiler classified optional-int to required-int as destructive, so I retained the stopped expanded deployment and explicitly accepted that classification only after observing the successful backfill. The resulting aggregate was rebuilt by schema activation, and the custom-client snapshots matched exactly afterward. This felt less direct than an explicit SQL migration transaction and migration runner, where I would normally see the backfill and constraint change together. It also meant I did not have to maintain a separate trigger implementation for the sum or a separate client interpretation of a vote. The tradeoff was operational clarity around which CLI commands work on a development store versus a deployed store.

The inherited regression suites were useful and mostly straightforward to reuse. Their first failures came from my fresh-instance setup: a replay cache still held the old database's tokens, and the isolated historical-content helper was not running. I preserved those failures, supplied the fixtures, and reran the unchanged suites. A final review also caught that the old caption-edit endpoint could mutate a poll question beyond its new limit; I guarded that path and removed the unsupported Edit affordance from poll messages.

The remaining limits are explicit. The mandated starter message fixture has no populated message-media or reaction rows and no read/delivered history, so comparing those fields proves their preservation at that actual starting state. Populated post/avatar assets were hash-compared. Counts inherit the engine's small expiry-sweep interval. Native evidence is a Hermes export, not a simulator session. I did not inspect another lane's files or a Snapback source checkout; an overly broad process diagnostic did accidentally display unrelated command text, and I restricted subsequent process inspection to owned PIDs.
