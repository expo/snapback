# Building Clique on Snapback 4

The strongest part of this experience was how many product rules could stay next to the data they governed. Accounts, public profiles, membership, message history, protected media, expiry, reactions, aggregate counts and scheduled work all lived in Quarry. I did not have to choose a different authorization vocabulary for the database, the realtime connection and the asset server. That reduced coordination work substantially. It did not make the application effortless: device initialization, navigation, ordinary media caching and the interaction between query shapes and pending state still required careful client engineering.

This is an architectural comparison, not a head-to-head timing study. I built this app on the pinned public Snapback packages, without consulting another implementation or a source checkout. My comparisons with Convex, Supabase and older Snapback approaches draw on model knowledge and the current package's published migration notes, with the alternatives' current official policy and client documentation checked during the final review. I did not run equivalent applications on those alternatives during this session. The distinction matters most around performance: a plausible design is not a measured result, and a local development binary is not comparable to a remote hosted service merely because both report milliseconds.

The initial account and profile slice was unusually compact. A profile's unique principal and handle, text limits, ownership rules and public synchronization were declarations rather than four separate integration tasks. The React arm then exposed a small set of hooks over that definition. In a Supabase-shaped implementation, I would think separately about the relational schema, row-level policies, authentication, storage policies and change subscriptions. Those pieces can be excellent individually, but the boundaries between them become application work. In a Convex-shaped implementation, reactive queries and transactions already reduce much of that glue; Snapback's additional distinction here was that the same query definition also participated in a device replica. The relevant baseline mechanisms are documented in [Supabase row-level security](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase Realtime](https://supabase.com/docs/guides/realtime), and [Convex optimistic updates](https://docs.convex.dev/client/react/optimistic-updates).

That replica was the major change in the shape of the work. Messaging could use ordinary mutations and still acquire a durable outbox, ordered reconciliation and local queries. The final browser tests exercised pending messages, ordered flush, shared read state, two offline devices and reopening a device with pending writes. I did not write a second messaging database or a custom message transport to obtain those behaviors. Against a server-first design, that saves a substantial amount of synchronization code. It also moves responsibility toward a reliable device bootstrap: a web client that needs to download its runtime before opening its offline store is not actually cold-offline capable. Persisting the pinned WASM bytes was a small but necessary part of making the promise real.

The hardest offline correction taught me something more specific than “offline is difficult.” I had added an existence check before inserting a caller-named message. It looked like harmless extra idempotency. Beyond the device's synchronized horizon, however, the replica could not prove absence, so it queued the mutation without predicting the new row. Removing that redundant guard and using the platform's write-ID idempotency restored prediction. This is a useful discipline: uncertainty about data outside a partition should not silently become a false fact. But it means the programmer must understand how apparently equivalent transactions differ in their ability to predict.

A second correction was less satisfying. The decorated history shape omitted pending metadata that the raw-row query retained. The message existed locally, yet its receipt looked sent. Reading the raw metadata beside the decorated history fixed the display without introducing another outbox. I would want that behavior either made consistent or explained prominently in the published surface. The ID-only video argument produced a similar surprise: local prediction reported a missing duration, while the same wire mutation succeeded. Supplying the full asset metadata returned by upload worked. These were the two clearest places where the shared server/device model still exposed a seam to application code.

Media authorization was otherwise a clear advantage. One typed home column established ownership and serving authority. Clearing that home on deletion revoked the asset; expiry removed the message and access; a once-photo column enforced one view per principal. Those are useful product concepts to have directly in the backend model. In a more conventional storage stack I would expect to coordinate object identifiers, database rows, signed access and cleanup. Here, the timed probe could verify the edit deadline, delete deadline and expired asset refusal against the actual server clock. The one-view client only needed to keep its temporary URL in memory and revoke it when the viewer closed.

Ordinary offline media remained application work because asset responses intentionally used private, no-store semantics. I added an explicit per-principal cache, then expanded it beyond message attachments to avatars, post media and chat backgrounds. A reconnecting client checks cached homes and removes revoked entries, including content whose screen is closed. View-once photos never enter that cache. This is more code than an optimistic reading of “local-first” might suggest, but the division is understandable: the platform owns authorization and one-view consumption; the application owns which ordinary bytes it retains and how it presents them. I also removed message and reaction horizons to preserve the full authorized history required by this brief, accepting that the scale cold-start probe must measure that larger replica.

Quarry's constraints were most valuable during the feed work. My first materialization attempt involved a mutation looping over a partially selected, uncapped group. The compiler refused it. That was friction, but it also prevented a casual implementation from hiding an arbitrary truncation or an uncontrolled write fan-out. I moved toward a pending delivery lane plus a reader lane populated by a resumable job. New posts remain visible before materialization, and the author does not wait for hundreds of follower rows. A changed follow graph temporarily reads the authorized catalog until the job has covered it. This design is more elaborate than a free-form transaction loop, and its incompleteness signals must remain honest, but its cost model is explicit.

This is where general-purpose backend languages have an advantage in expressiveness. With SQL or ordinary transaction code, I would have more familiar filtering and aggregation options immediately available. Quarry instead asks me to choose indexes, narrow optional values and express bounded work in its own forms. I made several ordinary mistakes while learning that surface: unsupported filtering syntax, a missing cursor tie-break, an invalid module schedule reference and a job-level binding outside a chunk. The diagnostic-and-rewrite loop was usually fast. Keeping the previous valid generation serving while the edited one failed was especially helpful; a compiler error did not turn every browser session into collateral damage.

The aggregate and digest work showed the benefit of staying inside one backend model. Lifetime totals and calendar buckets became maintained values, and Trending became a small ranking index with a server-enforced expiry. The UI re-queries those authoritative values on refresh; it never pages the corpus to manufacture a total. The digest used resumable server chunks, with emission and its sent marker committed together. The closed-client test restarted the backend mid-period, observed one correctly scoped payload per active user, excluded a tombstone and a non-member's private chat, and observed no digest for a quiet user or an empty following period. That is stronger evidence than a button that invokes a scheduled-looking function.

The scale workload adds an important qualification to the otherwise quick authoring loop. Registration runs through the real password path, and the public runtime's identity admission limits visibly pace that phase. I left those controls intact. The replay uses the actual app mutations, uploads each placed asset and waits for authoritative settlement before the next action. Its clock includes that cost. Checkpoints verify named fixtures before running probes, and the database is separate from development and choreography residue. This distinction between application correctness, controlled replay and performance measurement is necessary; a fast replay against an underfilled or specially imported database would not demonstrate the requested application.

Compared with the older declaration vocabulary described in the current guide, Snapback 4 presents a more consolidated authoring surface around tables, rules, sync lines, operations and jobs. I cannot honestly turn that observation into a measured claim about previous generations. What I can say from this build is that the current published package was sufficient to build and exercise the requested product without reading its implementation. The remaining friction was concrete rather than mysterious: prediction certificates, metadata preservation, explicit media durability, bounded fan-out and a few missing conveniences in the documentation. I would choose this model when durable local behavior and policy-aware synchronization dominate the application. For ad hoc relational reporting or integrations that depend on unrestricted server code, the narrower language would deserve a deliberate evaluation first.

The completed scale replay changed my assessment in a useful way. A repost count maintained over all feed entries also produced a counter for each original post, and the public aggregate inherited synchronization. That accidental replication overwhelmed the cold-start budget before the corpus was complete. The snapshot protocol made the cause visible without reading implementation source. A repost-only source removed those unnecessary counters, while every message remained in the authorized partition. The first timeout, the same-store resume and the original clock are retained. A server exit during the schema transition had no diagnostic, so its cause remains ambiguous.

The full action replay and independent entity counts eventually passed, as did the final cold startup and the isolated group send/render and celebrity-write probes. That does not make the performance result uniformly green. Insights and Trending failed the strict midpoint interpolation predicates, and the implementation changed between checkpoints. I have kept those results as diagnostics rather than claiming a uniform-code benchmark or adjusting a threshold after seeing the measurements. This is the main qualification I would carry into another project: Snapback made durable behavior and shared rules unusually compact, but an inherited synchronization decision still needed the same scrutiny I would give a SQL query plan or a Convex subscription's dependencies. The smaller language reduced some categories of work; it did not remove the responsibility to measure the resulting application.
