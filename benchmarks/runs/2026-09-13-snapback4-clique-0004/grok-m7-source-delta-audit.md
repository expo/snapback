# Grok M7 source-delta audit

Audit date: 2026-09-14

Scope: bounded read-only static comparison of the completed canonical lane `lanes/grok-snapback4` with the retained pre-M7 source archive and grading custody. I did not run tests or probes, inspect private model reasoning, or modify the lane, instrument, prompts, or pins. This note audits source and retained public records; it does not independently reproduce runtime outcomes or grade M7.

## Verdict

The additive schema evolution and same-store re-adoption are real, the generated API matches the evolved schema, vote writes are set-state and one-per-user, and the maintained message count has the required tombstone and logical-expiry semantics on Snapback 4 0.2.6. The M7 browser choreography records live tallies and offline settlement green.

There are two material app defects in the delivered M7 source: the unpaged conversation-wide vote query can truncate a later poll's tallies after 200 retained vote rows, and native has no affordance that opens the poll composer. The verification record also overstates several M7 mappings and cannot rehabilitate the inherited suites that the pre-M7 grader already adjudicated dishonest. Smaller app issues are a lost pending indicator after an offline-vote remount and a duplicated poll question on native.

## Schema addition and re-adoption lineage

`m7/pre-m7-schema.q` hashes to `1c0cd8576cc94e83ec0b4a08cb3b9d70cb1889d5040e8596e05c19c1c971b54a`, exactly matching the pre-M7 canonical schema. The public M7 run log (SHA-256 `770da005cb095aeb1d6f477efd6d704702832d52095ad88d9223d3989e2078f7`) records a fresh pre-replay store seeded with the starter logs, a custom-client snapshot, an additive `snapback4 check --cost`, termination of only the pre-evolution PID, and restart of `snapback4 dev --port 49300 --no-watch` on the same store (`m7/run-log.md:13-22`). The retained check output hashes to `768d5fab611dc58b870dde1451b4b435a35bee66c6cf102e166818e4e39addbf` and reports 40 tables, 61 operations, and no problems.

The final schema adds optional poll columns to `messages`, a `pollVotes` table, the `visibleMessageCounts` maintain, member-scoped projections/queries, and `createPoll`/`setPollVote` (`snapback/schema.q:205-206,257-286,372-387,478-522,856-894`). Published Snapback 4 0.2.6 at repository commit `342c53d306d7484cd64e820ee27a151e02eb4b0b` rebuilds a new or redefined maintain from every existing source row during schema installation (`snapback4/crates/snapback4-core/src/engine/mod.rs:375`; `engine/write.rs:426-464`). This makes the count projection a real backfill over the seeded rows; a release-tree deploy was not required by the M7 instrument. The run log's post-adopt 6-message DM and 9-message group observations support that path.

The pre/post comparator reports no mismatch after the M7 suite (`m7/snapshot-compare.json`, SHA-256 `d4fa8a08e1ef4274b8845df21d3aed295392689096eccabab1879efae3f6ab2e`). Its evidence boundary is narrow: the snapshot manifest (SHA-256 `fd01c832f28f6830cc4cb507723dd770a47d9e20231ef9a718e80a27b56a95cf`) contains 15 Alice, 15 Bob, and 9 Carol message observations but zero media messages, receipts, or reactions. The comparator proves those existing message fields and recipient-visible conversations survive; it cannot demonstrate preservation of populated media, receipt, or reaction specimens.

## Poll and maintained-count semantics

The server shape enforces group-only creation, a 1–200 character question, two required 1–50 character options, at most two more optional 1–50 character options, and ordered optional slots (`snapback/schema.q:856-872`). `pollVotes` is unique and capped at 50 by `(messageId, principal)`/message, matching the 50-member conversation cap (`snapback/schema.q:230-245,372-387`). `setPollVote` validates membership, poll liveness, and option existence, then inserts or updates the viewer's one row (`snapback/schema.q:874-894`). Replaying one mutation envelope is therefore transport-idempotent, while a new intent sets the current option.

`visibleMessageCounts` groups by `(conversationId,tombstoned)` and both inbox and `conversationOf` read the `false` bucket (`snapback/schema.q:205-206,478-491`). Text, media, and poll writes start `tombstoned:false`; deletion moves the row to `true` and clears its content (`snapback/schema.q:798-867`). Contrary to the builder's stated approximately one-second count lag (`m7/final-report.md:108`), published 0.2.6 logically recomputes a maintained read whose source expires, excludes every source row expired at the query clock, and reports its next live expiry (`snapback4/crates/snapback4-core/src/engine/read.rs:83-136` at `342c53d…`). The closed expiry ticket records this exact guarantee. Thus the delivered server query has the required tombstone and expiry semantics before physical sweep; the M7 test simply does not exercise expiry.

The React integration uses the ordinary `useMutation(api.setPollVote)` path, so offline writes use the Snapback durable outbox, and local `pollVotes`/`myVote` projections provide optimistic state (`components/ConversationView.tsx:41-53,201-242`). The unchanged choreography records all three live-tally attempts passing and one offline vote settling in 1,790.7 ms; the receipt hashes are listed above. This supports one visible poll with its small fixture population.

### Material app defects

1. **Tallies truncate after 200 conversation vote rows.** `convPollVotes` returns `first 200 by byConv` for the entire conversation, with no cursor, while each poll may retain 50 rows and the conversation may contain arbitrarily many polls (`snapback/schema.q:372-387,520-522`). The UI performs this query once and derives every visible poll's counts only from that slice (`components/ConversationView.tsx:41-46,201-227`). Four fully voted earlier polls can occupy all 200 returned rows, causing a fifth poll to show zero or incomplete live tallies. Tombstoning a poll leaves its `pollVotes` rows, so four tombstoned polls are a deterministic instance. The one-poll suite/choreography never reaches this bound. The query needs per-message paging/aggregation or a conversation query that the client fully pages.
2. **Native cannot open poll composition.** `showPoll` begins false and the only state toggle is passed to the web-only `WebConvoSurface` (`components/ConversationView.tsx:72,375-408`). The native branch renders messages and a normal `Composer`, but no native control calls `setShowPoll`; `PollCompose` is therefore unreachable on native (`components/ConversationView.tsx:409-534`). Native can render/vote on a poll but cannot create one.

Two smaller integration defects remain. First, a pending vote restored after a component remount is represented by `msg.myVote.pending`, but `pollView` uses that row only for selection and sets the busy/pending flag solely from ephemeral React `pendingVotes` (`components/ConversationView.tsx:95,102-109,211-242`). The durable vote still queues and settles, but its pending marker disappears after remount. Second, `createPoll` stores `body: question`; native passes that body to `MessageBubble` and then passes the question again to `PollDisplay`, so native renders the question twice (`snapback/schema.q:867`; `components/ConversationView.tsx:623-664`). The web overlay explicitly substitutes the poll question once and renders only options below it (`components/WebConvoSurface.tsx:117-128,172-187`).

The supplied kit is not the source of those defects. `ui/src/PollCompose.tsx` and `PollDisplay.tsx` byte-match both the 228-file pre-M7 archive and `instrument/ui/src` at SHA-256 `5a143045095ae1bae8e640317799fbbed49db436594a0dd72226b9620f525054` and `bb5dfffb85a55184a5b9e1aafdd611c8b64eb94500015bf63a5f33f4d07fc4ec`. Grok's new integration also filters blank optional inputs before it calls `createPoll` (`components/ConversationView.tsx:245-257`), so the frozen kit's permissive blank-optional submit behavior does not reach the server here. The missing native toggle, duplicate question, pending remount behavior, web overlay, and conversation-wide tally read are newly authored integration choices.

## Verification truth and inherited failures

The new M7 suite contains substantive tests for two/four-option creation plus group-only/long-question refusal, vote changes, mutation-id replay, starter counts, forward text/poll/tombstone counts, and regression invocation (`scripts/acceptance.mjs:566-719`). Its retained six-result receipt is green. The mapping is still broader than the exercised observations:

- `m7-a01` does not test the 50-character option bound or explicit one/five-option refusals (`scripts/acceptance.mjs:566-605`). The schema enforces the bounds, but the suite receipt does not.
- `m7-a06` compares the aggregate to at most twenty 50-row history pages for the small starter conversations; the fixture contains no tombstoned or expiring message (`scripts/acceptance.mjs:524-543,664-678`). It therefore does not cover the assertion's tombstone/expiry clauses.
- `m7-a07` proves the `conversationOf.messageCount` payload equals the queried aggregate but never renders chat settings (`scripts/acceptance.mjs:680-706`). Static app source does pass `conv.messageCount` into the supplied `ChatSettingsForm` (`components/ChatSettingsScreen.tsx:110-131`), but this is not suite observation.
- `m7-a09` really invokes all 58 inherited M1-M6/M8 test functions in process and fails if any throws (`scripts/acceptance.mjs:708-719`). The pre-M7 portion of `acceptance.mjs` is byte-identical at SHA-256 `e8a9c959dce14707275716a4ed6cb513c687dc1ba76ee512430f799c17e38336`, and every individual old `suite-*`, `coverage-*`, and `suite-status-m*` receipt is byte-identical. However, the M7 receipt records only the parent `m7-a09`, not the 58 child outcomes. More significantly, the pre-M7 grader report had already adjudicated M2, M3, M4, M5, M6, and M8 coverage dishonest because of tautologies and tests that never observe their mapped behavior (`grading/grader-report.json:770-806`). Re-executing those unchanged bodies does not cure that finding. The inherited `suite-m2.json` remains a zero-result pass.

The generic `receipts/suite-status.json` was overwritten by the M7-only run and now marks M1-M6/M8 false with null receipts (`scripts/acceptance.mjs:721-775`); the separate `suite-status-m7.json` is correct. The original milestone-specific receipts remain present, but consumers of the generic file see a false regression picture. The known M3 choreography failure is preserved byte-for-byte (`receipts/choreo-m3.jsonl` SHA-256 `a8b231ddc21171e4dfc99d4d968f0b2ff4732690e53483ca8cb3ea3fcb24314d`), and the M7 report explicitly says it was not repaired or rerun.
