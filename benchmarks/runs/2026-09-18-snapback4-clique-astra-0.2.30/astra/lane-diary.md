# Build diary

## M1 boundary — accounts and profiles
Built password signup/login, persistent sessions, revoking logout, live public profiles, ownership checks, unique handles, all textual fields, and uploaded avatars. Both the browser suite and frozen choreography pass; an iOS Hermes export exists.

Quarry made the schema and ownership rules compact. The built-in password path removed KDF and session infrastructure work; avatar placement attached serving authority to the profile. Reading the full published surface took real orientation work: the main README is long and continues into a second reference. The generated types made operation naming unambiguous.

The friction so far was mostly mine: the initial Expo navigation stack retained duplicate semantic nodes during transitions, and CI mode disabled Metro watching. The frozen harness also needed its sibling metering module after copying. General React, Expo, and Playwright familiarity helped with those issues; no prior Snapback implementation was consulted. Compared with Supabase, the profile rule and sync declaration avoid wiring a separate subscription cache. Compared with Convex, the explicit local replica is an additional setup decision, but password auth and asset policy are already integrated. Native execution has not been proven; only Hermes compilation is claimed.

## M2 boundary — social posts
Built image/video/text posts, direct replies, unique set-state likes and reposts, profile counts, Global and Following feeds, own-feed membership, and cursor-backed scrolling. The suite and frozen choreography pass. The native Hermes export was rebuilt.

The supplied Following recipe saved designing a hybrid delivery system from scratch. Its integration guidance was specific about app post IDs versus feed event IDs, atomic follow bridging, and keeping media in the original home row. Maintains made counts straightforward. The cost is a substantial recipe module and broad public replication; acquisition at scale remains unmeasured here. The recipe's documented 32 pulled-author cap is a product bound, even though the supplied celebrity fixture needs only one.

Web asset resolution and profile-to-feed navigation fought me. The harness's default fixture directory also required an explicit adapter. A browser navigation interruption was retried rather than hidden. General Expo knowledge helped, but assuming native Image.resolveAssetSource existed on web was my error. Compared with Convex or Supabase, this moves more read projection decisions into schema-time sync and bounded-query design. The compiler's typed result exposed a mismatch between two feed row shapes, which I resolved by selecting the same card fields.

## M3 boundary — messaging core
Built pair-deduplicated DMs, distinct groups, admin membership controls, send-time recipient sets, server-arrival ordering, monotonic delivery/read cursors, expiring typing, and quoted replies with history paging. All required choreography passes, including removal cutoff witnessed by a later DM and retention of old history. The harness records its optional sender-avatar skip on a sender-owned bubble; recipient bubbles do render avatars. Hermes export and the suite pass.

The membership audience and delivered-history retention matched the product unusually directly. Typing expiry was a schema field plus a local display timer. Receipt semantics were application work, but ordinary queries and mutations were enough. A send-time recipients list avoids accidentally making a newcomer a recipient of old messages. The compiler clearly identified the name-based group lookup's incomplete server scan; fixture navigation uses stable IDs.

The Reply action's initial placement outside the contracted bubble and a smooth-scroll timing mismatch caused two failed choreography iterations. These were UI authoring mistakes, not backend defects. I also made old quote targets load earlier pages. Prior familiarity with React refs and monotonic receipt cursors helped. Convex would make live queries similarly natural but require separate offline retention logic; Supabase would require more explicit subscription and local-cache coordination. Here removal retention came from the backend declaration, and the browser proof actually exercised it.

## M4 boundary — media and message actions
Photo and video messages, captions, inline images, playable videos, single per-user reactions, edits and deletion tombstones now work across clients. The suite, first choreography run and Hermes export pass. Additional API proofs reject edits and deletes of old fixture messages and prove cleared media becomes unfetchable.

Assets were the easiest part: an upload is attached to a typed image/video column, and clearing its only home revokes access. This saves the storage-policy bookkeeping I would expect with Supabase or a separate object store. React composition and arbitrary emoji selection were routine. I guessed three language forms incorrectly (len, a namespaced helper, durationMs); exact diagnostics supplied the corrections. No platform defect was required to explain those errors. The membership-leading reaction index improved completeness after the compiler explained why a message-only scan could not prove authorization. Compared with Convex, backend functions are more constrained but asset ownership and local projections are more integrated.

## M5 boundary — ephemeral messages, configuration and search
Implemented server expiry, per-principal view-once images, group settings, shared backgrounds and color, three search scopes, and warm-offline search. The suite, all implemented choreography checks, Hermes export and separate no-client expiry proof pass. The real three-minute expiration happened with API clients closed; subsequent message, search and asset requests all refused the expired content. Choreography used its full five-minute wait before reopening clients.

Expiry and one-view assets were pleasantly declarative. The SDK also owns ordinary viewed-media retention and purges bytes when the owning reference disappears. This avoids a substantial custom offline cache policy. Search required thinking in membership scopes; the documented grouped query avoids treating a partial global scan as complete. It feels less like writing arbitrary backend code and more like choosing executable data contracts.

The compiler corrected my use of a column-only once modifier in an argument and an unsupported membership operator. These were author mistakes. I also expanded TypeScript checking to Router files and fixed a conditional generic hook it exposed. Prior familiarity with authenticated object access helped me test the actual second fetch, rather than merely disable a UI button. Supabase would need storage policy plus view-consumption transaction and cache invalidation; Convex would still need a custom durable offline story. I have not validated other backend versions in this run, so these are architectural comparisons, not measured speed claims.

## M6 boundary — offline, provider seam and third-party API
Built the provider seam worker, documented user-token API, standalone polling demo, 13-verb replay adapter, sample conformance checks and application-shell caching. The suite, final choreography and Hermes export pass. Extra browser proofs cold-reload history, viewed images and search offline, and retain a pending write across reload. Native proof is the required Hermes artifact, not a simulator claim. Full scale replay has started on a fresh store with replay mode and a separate clock; its verification is still in progress at this boundary.

The package's effect declaration made push admission transactional with message insertion, and the worker is only the external logging seam. The explicit replay flag is useful: it suppresses effects without changing mutation, receipt or feed behavior. Authenticated online clients made the replay adapter straightforward; each action awaits authoritative writes before advancing. I initially passed fixture intent names directly as mutation IDs, and the diagnostic required the documented Crockford form. The adapter now deterministically encodes their identities while preserving entity IDs.

The most revealing bug was mine: a DM route required its online pair-dedup mutation even when an existing room was cached. A membership lookup fixed cold startup. The backend had retained the data correctly. One send-control timeout on a later choreography run did not reproduce in the separate durable-queue proof or final rerun; attribution remains ambiguous. Compared with Supabase or an ordinary REST backend, the durable outbox removes a major application subsystem. Compared with Convex, the offline interpreter changes what the client can do without a connection. Those advantages still require attention to application navigation and shell caching.

## M8 boundary — insights, trending, digest and multiple devices
Built the six server-computed totals, a seven-day UTC breakdown including zero days, and exact trailing-day trending with score then creation-time order. Ranking rows are maintained in each like/post transaction, with a rules-validated score and hour-leading index. A bounded backfill handles the existing app corpus. The scheduled digest walks profiles, then period messages, then emission totals, so a busy chat is not silently truncated to a fixed message sample. It checks current membership before accumulating unread activity, excludes tombstones and expired rows, and writes durable user-period emission markers. The provider seam test passed with users closed, a restart mid-period, correct counts, an unrelated private chat, an inactive user, and a silent following period.

Same-account send/edit/reaction observations, cross-device read state, dual-offline convergence and a two-message offline close/relaunch proof all pass. The final suite, choreography and Hermes export are green. I also finished native attachment preview plumbing, scroll-triggered feed paging and visible queued-write failures. The full replay remains on its separate clock at this boundary; its first checkpoint is verified and later checkpoints are still pending.

The aggregate declarations made ordinary insights concise. Exact trending ties needed an explicit ranked table rather than pretending a maintained-group identifier was creation-time ordering. The language rejected direct scalar aggregate expressions in rules and an explicit id inside upsert; the correct forms were existence probes and a key-owned row. These were useful corrections, though I had to compose several primitives rather than find one ready-made feature.

The digest was the biggest change in shape from a conventional SQL-backed service. A Supabase implementation could express much of this with SQL joins and an external scheduler; a Convex implementation would likely use scheduled functions and denormalized counts. Quarry required explicit bounded sweeps and atomic chunk progress. That made the operational limits visible, and the scheduled no-client proof was more convincing than invoking a handler manually. The public docs explained the distinction between one scheduled run and exactly-once provider delivery, so I preserved both emission markers and provider idempotency. No prior implementation or previous lane was consulted.

## Final verification boundary — full replay and populated-store adoption
The full replay completed and its final invariant verification passed. Both earlier checkpoints had passed too. Applying the final M8 schema to that populated store and backfilling ranked rows/reply attribution then passed every profile's six totals and seven UTC buckets, exact top-ten trending, the heavy user's complete delivery targets, and unchanged original entity counts. No M7 work was attempted.

The final scale audit found my inbox-first-page delivery mistake; a dedicated bounded membership query and a 60-chat proof fixed it, followed by green M6/M8 regressions and the final Hermes export. The populated-store backfill initially raced the development host's derived rebuild and received E_STORE database is locked. I stopped only the recorded scale processes, ran the backfill offline, and restarted replay mode. Both corrections were application/operational responsibility rather than demonstrated platform defects. Familiarity with transaction boundaries helped identify the safe handoff; the missing piece in my procedure was explicit single-writer coordination. Compared with a hosted SQL migration workflow, the local CLI/store lifecycle needed more care; compared with maintaining a separate client data engine, the shared schema still saved substantial work. The essay was completed before the final numeric inventory.
