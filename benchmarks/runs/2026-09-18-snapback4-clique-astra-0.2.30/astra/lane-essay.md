# Building Clique through the published Snapback 4 surface

This build changed where I spent engineering effort. The visible application was an Expo Router social messenger, but the important backend work lived in the relationships among schema, authorization, synchronization, mutation prediction and bounded reads. Those were not separate integration projects. A message table could declare its membership audience, its retained history and its expiry, and the same declaration influenced the server and the device. That cohesion was the strongest part of the experience.

This is an account of this cold build, not a benchmark of competing products. I used the exact published Snapback packages supplied in the brief and their published authoring surfaces. I did not inspect another Snapback checkout, an earlier Clique implementation or another lane. Comparisons with Convex, Supabase and other architectures draw on model knowledge of their programming models, not fresh installations or measurements. The quantitative report follows this essay; the independent full replay was still progressing when I wrote the initial qualitative account.

## The friction that disappeared

The most substantial saving was the local data system. Ordinary application code did not need to implement a durable mutation queue, a cache invalidation protocol, a per-chat synchronization subscription, or a second hand-written model of optimistic updates. The local client and its interpreter handled those responsibilities. I still had to make operations eligible to predict, and sometimes a write deliberately queued without a predicted row. But “what happens offline?” was usually answered by the schema and operation, rather than a new subsystem in the application.

Media showed the same integration. An upload became a typed image or video reference attached to a row. The row's authorization determined access to the asset. Clearing a message's reference made its media unfetchable, and expiry removed both the message and its accessible asset. A once-only image column supplied server-enforced consumption per principal. The client had a separate policy for retaining ordinary viewed media and explicitly excluded once-only responses from durable storage. I verified actual subsequent fetches, not just an “opened” label or a hidden image.

With a conventional object store alongside Postgres, I would expect to spend more time joining these pieces: storage policies, metadata rows, signed URL lifetimes, consumption transactions, local byte eviction and authorization changes. Supabase gives useful building blocks for that architecture, but the application still has to make their boundaries agree. Here, asset ownership was part of the data model. That removed a class of accidental disagreements between what the database permits and what an old media URL or device cache still exposes.

Convex is a closer comparison for live application work. Reactive queries and transactional mutations make the online experience straightforward in both models. The distinctive part of this run was keeping the application useful across disconnected and restarted clients. In Clique, persisted data, a pending write and its eventual authoritative result belonged to one client abstraction. I did not have to build a bespoke queue beside an online query cache and then reconcile their competing versions of a message.

## The friction that moved into authoring

Quarry is not simply a familiar language with a database library. I repeatedly reached for a plausible spelling that was not in its surface: a length function, a namespaced helper call, an asset duration field, a membership operator, or a row ID inside an upsert. The compiler usually gave a precise replacement or a relevant guide card. That was helpful, but it was still a correction cycle caused by transferring habits from other languages too casually.

The more consequential learning concerned completeness. An index can find rows while still being unable to prove that a reader has seen the entire authorized answer. A message-only reaction scan did not pin the conversation needed by its membership rule. Adding the conversation prefix made the authorization scope explicit. A name-based group lookup remained potentially incomplete; stable IDs were the appropriate navigation contract. These diagnostics encouraged a better design than silently treating every returned array as exhaustive.

This is a different tradeoff from writing an arbitrary server function in TypeScript or issuing a SQL query. Those environments offer a broader vocabulary immediately. Quarry makes the cost and authorization shape more visible and refuses some convenient-looking forms. That can reduce operational surprises, but it asks the application engineer to understand the execution model earlier. I benefited most when I treated diagnostics as explanations of the model, rather than merely instructions for making the current line compile.

Exact trending illustrates the distinction. Lifetime counts and calendar buckets were compact maintained aggregates. The product's ranking rule was more specific: recent original posts, ranked by likes, then newest first. I did not assume a maintained group identifier was an adequate time tie-breaker. I added a ranked row with explicit score and timestamp ordering, updated transactionally with the source mutations and checked against the maintained like count. Hour-leading lanes bounded the trailing-window read. It was more backend design than a short “order by count” expression, but the resulting ordering and work were explicit.

## Application responsibility did not disappear

The cold-offline test found a useful counterexample to any claim that the backend makes an app automatically local-first. The device had retained the conversation, yet the route tried to run the online pair-deduplication mutation before opening it. An existing-membership lookup fixed the route. The storage system was doing its job; application control flow was preventing the user from reaching the data.

The browser also needed its own cached application shell. Retained backend data cannot execute JavaScript that the browser cannot load. I added a same-origin service worker for that shell while leaving authenticated data and media retention to the SDK. Native builds used the published Expo arm and produced Hermes artifacts. I did not substitute simulator claims for the artifact requirement, and I did not claim that a browser page-lifetime test was a native process test.

The frozen UI kit and choreography exposed ordinary frontend mistakes. A reply action was initially outside the bubble scope expected by the contract. Smooth scrolling did not satisfy an immediate quote-target visibility observation. One push test assumed a fixture display name that an earlier UI test had legitimately edited. These were application and test-authoring errors. They should not be counted as backend defects merely because they occurred while evaluating a backend.

## Scheduling and scale made the boundaries concrete

The digest was a useful test of whether the platform could own work without an open app. Its implementation used several bounded sweeps: initialize user-period activity, visit messages in the period, and emit completed totals. This avoided counting only the first fixed-size sample of a busy chat. Authorization was structural: unread contributions required a current membership, and deleted or expired content did not contribute. Durable emission markers and provider effect IDs addressed different retry boundaries.

Compared with a SQL-oriented implementation, the job required more explicit staging. Compared with a general server-function scheduler, it made chunk progress and limits part of the authoring surface. That extra structure paid for itself in a meaningful proof: users were closed, the backend restarted within the period, the schedule emitted the expected payload, and the next inactive period stayed silent. Manually calling a digest function would not have established the same thing.

The full replay was deliberately separate from development state. It used real authentication and application mutations, awaited each authoritative settlement, preserved fixture entity IDs and recorded action receipts. Push and schedules were suppressed through the documented replay mode. Checkpoint verification combined independent application-table counts with ordinary authorized API reads and full history paging. The feed recipe also made its acquisition tradeoff visible: bounded following reads can coexist with a substantial replicated public corpus. A small query result is not evidence of a small initial device synchronization.

I cannot make a defensible measured claim about earlier Snapback generations from this session. No earlier version was installed or inspected, and prior implementation familiarity supplied no shortcut. What I can say is that this generation's published package exposed a coherent path from Quarry declarations to generated types, local execution, native packaging, effects and scheduled work. That coherence mattered more than any isolated syntactic convenience. Its remaining costs were the need to learn a constrained language, reason about completeness and bounds, and finish the application-level details around those capabilities.

I would describe the experience as integrated rather than effortless. Snapback reduced the number of independent systems I had to make agree, especially for offline writes and media authorization. It added explicit reasoning about scope, residency and chunked computation. Convex remains a useful mental comparison for reactive transactional app code; Supabase for relational flexibility and SQL-centric operations; an ordinary REST stack for the amount of offline infrastructure this build avoided writing. The practical result here rests on the retained proofs and artifacts, not on assuming that one programming model universally wins.

The completed replay and populated-store verification strengthened that account. The same declared aggregates produced correct per-user insights after the large corpus was adopted, and the exact ranking agreed with an independent query over the source rows. The handoff also exposed an operational boundary: an explicit CLI backfill raced the development host's derived rebuild and received a database-lock diagnostic. Stopping that host, backfilling offline, and restarting in replay mode resolved it. That was a coordination mistake in my procedure, not evidence of a wrong aggregate result. It is the kind of operational detail that belongs in the handoff alongside the otherwise concise backend declarations.
