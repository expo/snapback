# An account slice at the edge of Snapback 3

This experience ended at a product boundary rather than at a performance or implementation boundary. Clique asks for an avatar in its first milestone. The installed Snapback 3 package admits persisted Quarry queries and mutations, but rejects media columns. The public documentation disclosed that limitation; the actual worker confirmed it with `S3_CAPABILITY_UNAVAILABLE`. The result is a working textual account/profile slice and an incomplete application. Any comparison that treats this as a completed social messenger would lose the most important observation of the run.

I wrote this account before the final numerical tally. Comparisons below are qualitative comparisons with backend approaches I know from model knowledge, not measured results from sibling lanes or earlier benchmark runs. I inspected none of those implementations. In particular, I have no firsthand Snapback 2 build from this session to contrast with this one. The permitted public S3 README describes inherited Quarry/compiler/engine foundations and a new client and development server. That is the basis for discussing the relationship, not a claim that I tested the predecessor here.

Within the supported slice, the separation of responsibilities felt coherent. Quarry described the profile record, its unique owner and handle, and its write authority. The client consumed generated operation references. React subscribed to the same resource store through a provider and hooks. I did not author a transport protocol, manually invalidate caches after saving, or open a parallel subscription just to keep another profile view current. The browser choreography edited Alice on one client and observed the new name and bio on another. That is a small but real demonstration of reduced integration work.

The resource contract also asks the application to be more honest than a plain loading flag. A resource distinguishes completeness from freshness, and the guide warns that a complete page does not imply a fully downloaded dataset. I used completeness to avoid treating an unknown profile as an absent profile. I could see how this would help prevent misleading offline screens later. But this run did not reach offline messaging, durable multi-device queues, or the scale envelope. Those are promising properties of the documented model, not outcomes I can infer from a live profile edit.

The mutation interface was similarly explicit. An operation has local durability and a terminal server receipt. The simple profile form only needed the settled receipt, while the same shape appears designed to expose pending and recovery states for more demanding clients. This changes application authoring: a mutation call is an object with a lifecycle, not merely a request promise. That seems useful for avoiding accidental resubmission, but it also means the author must read the receipt and handle rejection correctly. I initially showed only the constraint code. The server had supplied a more useful explanation, and preserving it fixed the visible duplicate-handle error. That friction belonged to my adapter code rather than to server enforcement.

Authentication was a good fit for the first milestone. I used the built-in password methods rather than implementing hashing, token generation, or session storage. The browser restored its session after reload and stayed signed out after logout. A separate direct probe checked that a short password was denied, the issued session carried a future expiry, and the old token stopped working after logout. Those observations made the account core credible without inflating them into an independent audit of the password implementation. The framework owned those critical pieces; this application used its public path.

Against a Convex-shaped approach, the strongest similarity is the compact connection between backend operations, generated types, and live React reads. The main difference I felt was language acquisition. I know the TypeScript mental model well; Quarry required discovering the exact grammar before I could state a very small data model. The installed README described where files belong but did not give a complete account example. The supplemental guide directed readers to an example whose source was outside this experiment's permitted doorway. I therefore read the installed compiler parser. This is legitimate package API discovery here, but it is not the experience I would want a new product engineer to need for their first table and upsert.

Compared with a Supabase/Postgres-shaped approach, Quarry put authorization and schema near each other and made generated client operations the front door. In SQL I would expect to spend more visible effort deciding how row policies, a profile table, and the application API fit together. Familiar SQL would also make the underlying uniqueness and lookup model immediately legible to me. S3's implicit ids and implicit byId index were economical after discovery, but my first attempt redundantly declared them. The compiler told me exactly what to remove. Economy in the final schema and familiarity on the first attempt are different advantages, and this run illustrated both sides.

Storage is where comparing ergonomics stops being useful. In backend stacks with an available object-storage facility, avatar work is usually an integration and policy task: select a file, upload it, retain a reference, and render it. Here the relevant runtime slice does not exist. I could have encoded a fixture image in a text field or added an application-owned file server. Either would make a screenshot look more complete while evading the restriction against replacing missing S3 behavior. I chose to retain the failing media schema and leave the avatar requirement red. The application names the limitation visibly. The starter replay also stops rather than silently dropping its avatar argument.

The relationship with Snapback 2 should be judged with the same care. Sharing compiler and engine foundations does not mean S3 serves every declaration the compiler can recognize. The image type was syntactically valid; admission then refused it. The S3 README expressly cautions that inherited exports do not imply served capabilities. That honesty helped me attribute the failure correctly, but the layered surface still required two discoveries: how to express the desired schema and whether the selected runtime could actually own it. A concise capability matrix beside a complete minimal example would make those two questions easier to answer without reading installed implementation code.

Expo added a separate boundary. The Router and React Native shell compiled for web, and the iOS Hermes bundle exported successfully on Linux. That is evidence about source compatibility and bundling, not evidence of a usable native offline client. S3 documents browser IndexedDB as its default persistence and describes another host as needing a storage adapter. I left native storage explicitly ephemeral in this partial shell and did not claim native session persistence. A finished mobile product would have to resolve that obligation even if media admission were available. The host also cannot run Apple's simulator, independently of the package's native-client maturity.

Operationally, a single packaged local owner was convenient. I installed the hash-qualified tarball, ran its checks, started one server on the assigned port, and served the built Expo web files from that same owner. There was no managed-project provisioning or second backend to coordinate. This is a useful development posture, but I did not test deployment, recovery, backup, or migration operations. A short account build gives no evidence about their readiness. The API's explicit admission refusal was more informative than a half-working upload endpoint would have been, even though it ended the intended product run.

The broader lesson is about scope alignment. Snapback 3 reduced code in the slice it actually owns: auth, typed operations, resource reads, and live profile propagation fit together with little adapter machinery. It added learning cost at the authoring boundary and stopped the product at the media boundary. The dependency DAG made that stop decisive: no later milestone could legally establish green after M1 failed. I therefore cannot score its messaging, search, push, digest, or scale experience from this session. The final artifact is useful as a precise diagnostic of an experimental package, not as a production messenger or a general ranking of backends.
