# Building Clique with a backend that also lives on the device

Clique changed shape as the session progressed. The first profile and feed screens looked like a conventional application: authenticate a person, write rows, query lists, and attach media. Messaging made the backend choice much more consequential. Membership had to govern delivery, a removed member could retain permitted history without gaining future access, and a pending message had to remain an actual durable intent when the application disappeared. Snapback 4's most useful contribution was keeping those concerns close to the data model. The schema, rules, sync declarations, and operations described both the server and the replica. I did not author a second message database or a second mutation queue in React.

This is an account of one build, not a comparative benchmark of several backends. I used the exact published Snapback packages, their README and guide, diagnostics, and generated API. I did not inspect another implementation, an earlier run, or a source checkout. My comparisons with Convex, Supabase, and conventional server stacks are architectural judgments from general familiarity. They are not measured claims that one alternative would have taken a particular number of hours or lines. I have even less basis for a measured comparison with earlier Snapback generations, and I will not invent one.

The strongest reduction in friction appeared at the transition from online messaging to offline messaging. Once the conversation and membership partitions were declared, the published client could acquire them, run local reads, retain ordinary viewed assets, and durably admit writes. React did not need a hand-written retry coordinator. The same message operations could settle on the server after reconnection, with authoritative ordinals providing arrival order. The exported web application eventually survived an entire browser-process restart while disconnected: history and viewed media remained, search worked, pending messages rendered, and reconnect delivered them in order. That is stronger evidence than a successful optimistic animation, although it is still web evidence rather than an iOS simulator demonstration.

A design built around Supabase and Postgres would give me familiar SQL, constraints, transactions, indexes, and row-level authorization. Those are substantial strengths. For this brief, however, I would also need to choose and integrate a durable local database and synchronization strategy, decide how its authorization boundaries correspond to database policy, and reconcile its pending queue with media revocation. A plain Postgres/Express design exposes those same decisions even more directly. They are all solvable engineering problems; the relevant difference is that Snapback gave me one published model spanning several of them. That reduced the number of application-owned mechanisms whose failure modes I needed to keep consistent.

Convex is a closer conceptual comparison for typed server functions and reactive queries. Its familiar TypeScript surface would remove the cost of learning Quarry's syntax, and generated client types would feel natural in this Expo project. Snapback's distinction in this session was the explicit device replica and the compiler's account of what that replica can justify. I could not assume that a write which works online will produce a useful local prediction. The compiler explained when a table was online-only, when a bounded group justified fanout, and when local evidence was insufficient. Some operations therefore queued without a predicted row. Exposing that distinction honestly in the interface was real product work, not an implementation detail the library could erase.

The diagnostics were usually useful. Several early mistakes were plainly mine: JavaScript-style optional access in Quarry, an expiry declaration without its required index, a wrong fixture filename, and an omitted React Native import. Their fixes were local. A more interesting refusal occurred when I assembled recipients into a filtered list and then emitted notifications over it. Iterating the membership group directly let the compiler see the finite bound. That is a different authoring habit from writing arbitrary server JavaScript and relying on tests or production measurements to discover expensive loops. It sometimes interrupts flow, but it puts an important cost argument where the operation is authored.

The same philosophy helped with the scale fixture. The published feed recipe offered an explicit hybrid between per-reader delivery and shared celebrity activity. I had to read it, understand its caps, and adjust capacities for the actual fixture. The result handled the full action log through real authentication and application mutations. Independent persisted-state checks matched the manifest at the checkpoints and at completion. That does not prove unlimited scalability or a good cold-start experience for every user. In particular, I kept full public source synchronization in several places to preserve straightforward offline semantics. Warm indexed queries can be fast while initial replica acquisition is large. A production review must keep those two facts separate.

Media was another area where a unified model paid off. Uploaded assets were placed on rows with ownership and visibility rules. Clearing a placement revoked access; expiring messages ceased to serve content even with no client open. View-once was a backend property rather than merely a disabled button. The client still had work to do: present an inline photo or video, avoid retaining a view-once image, close its viewer cleanly, and use the correct platform video component. But the critical authorization decision did not live in that presentation code. In a more loosely assembled stack I would be especially concerned about signed URLs that outlive the row state which originally authorized them.

M8 exposed both the elegance and the constraints of the approach. Maintained counts made six lifetime totals and seven UTC-day buckets compact server operations. The client rendered totals rather than paging the corpus to count it. Trending required a more deliberate read model. A periodically rebuilt ranking would introduce a freshness delay, so I used an indexed expiring ranking table updated with engagement changes. That made ranking immediate but moved those writes outside local prediction. The pending-write hook was necessary. This was a concrete example of one product requirement changing another feature's offline presentation through the data dependencies.

The digest was pleasantly small in infrastructure terms. Quarry's scheduled, chunked job traversed activity, checked membership, and emitted the same notification effect used for messages. The effect worker only logged and acknowledged payloads. Its backend-owned cursor and period identity provided a coherent restart story. I verified that story against a separate fresh instance with every user client closed: a restart did not duplicate delivery, inactive users received nothing, private and tombstoned activity did not leak into another user's counts, and the next inactive period produced no digest. I would still review long-running-job snapshot semantics and retention before operating this indefinitely. The successful fixture test is evidence for its stated scenario, not a substitute for an operations design.

There was friction outside the backend as well. The frozen harness copy needed its neighboring metering files and an omitted JSON-schema helper supplied inside the lane. Expo Router retained-screen behavior initially created duplicate test surfaces until the layout was simplified. A lazily loaded web device module broke an offline navigation path; importing the web arm statically resolved it. These should not all be charged to Snapback. Nor should my test mistakes: concurrent activity can bury a reference post or change unread state, and a test that races the login screen is simply a bad test. The run log distinguishes those corrections from platform uncertainty.

One platform interaction remains worth calling out. After a local job adopted the evolved schema against the scale store, the already-running host returned E_GENERATION and asked for its engine to be reopened. Restarting the owned host fixed the supplementary probes. I did not need to modify the package, but I would want that operational boundary to be especially prominent in a production workflow. More generally, this build produced a compiled release and native Hermes bundles, not a deployed service with TLS, backups, push-provider credentials, or a signed mobile distribution. The native code path is implemented through the pinned Expo package; native execution itself was not proved in a simulator.

Earlier Snapback generations are a limit on my comparison rather than a convenient foil. I can say that the current published surface expresses this application through Quarry and provides the local, React, and native arms used here. I cannot honestly say which earlier release lacked a capability, how much a prior implementation cost, or that this session improved on an old benchmark. The useful comparison is the shape of responsibility: this version let me place more synchronization, expiry, authorization, and scheduling responsibility in the backend definition, while making me reason explicitly about bounded work and prediction. For Clique's combination of private messaging and durable offline behavior, that was a meaningful benefit. It also left clear obligations around acquisition size, operational tooling, and the proof still needed on a real native runtime.
