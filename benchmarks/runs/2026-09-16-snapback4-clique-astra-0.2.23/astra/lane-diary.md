## M1 boundary
Built real password signup/login, persisted expiring sessions and logout, public live profiles with unique handles and the exact profile fields, plus uploaded avatars. The Quarry model compiled on the first check. Built-in auth and policy-bound images made the backend small. The work that fought me was Expo navigation keeping hidden screens mounted and the copied instrument's dependency layout. Familiar React and Playwright knowledge helped diagnose those issues; no prior Snapback checkout or implementation was used. The README was unusually comprehensive, although long enough to dominate initial orientation. Compared with Convex, the schema carries more behavior and generates client operations; compared with Supabase, no separate RLS/storage integration was needed here. Native evidence is an iOS Hermes export, not a simulator claim.

## M2 boundary
Built public original posts, four image slots or one video, direct replies, set-state likes/reposts, profile counts and author posts, and paged Following/Global feeds. The published feed recipe saved designing celebrity delivery from nothing: private inboxes and shared celebrity events were explicit Quarry. I adjusted its sample author-count cap for 1,008 fixture users and its last-200 backfill to cover the full capped history. The type checker correctly rejected passing an application table reference into a different table's helper; using the shared ID parameter resolved it. Browser navigation and running write-heavy acceptance concurrently with choreography caused my correction loops. Snapback's media placement was straightforward; React rendering was most of the client work. Compared with SQL/RLS or Convex functions, the recipe puts distribution and bounds in the model, but it is substantial application code to understand, with real caps and cold-sync costs. These are design choices, not an unlimited-feed guarantee.

## M3 boundary
Built DM deduplication, independent groups and admin membership operations, full prior history on join, retained history after removal, text and quoted messages, typing expiry, and sent/delivered/read indicators. Recipient lists capture membership at send time; current membership removes departed recipients from the aggregate. Query shapes and bounded lists expressed this directly. The first schema check passed. A browser offline transition exposed my lazy-loaded device module: navigation could need another network chunk. Statically importing the platform-selected device fixed the receipt reconnect check, and the complete suite/choreography rerun passed. Compared with Convex or Supabase, durable device history and group removal retention were schema declarations instead of a separate sync implementation. Receipt semantics still required careful application modeling; the backend did not invent them. No missing backend primitive blocked this milestone.

## M4 boundary
Built image/video messages with captions, inline images and playable video, reactions with replacement/removal, edited labels, and delete-for-everyone tombstones. Window durations come from the copied JSON configuration and compile to server-side Quarry constants. Clearing an asset column revokes its URL without a separate object-storage policy. Media and reaction choreography passed immediately. My acceptance exposed a predicted-send UI race: a bubble appeared before the pending mutation settled, then late draft clearing erased newer input. Conditional draft clearing fixed the product issue. The diagnostic needed browser observations rather than backend internals. The backend's distinction between prediction and authoritative settlement is useful, but requires the UI to respect both. Compared with a purely online backend, that is additional client-state reasoning in exchange for offline capability.

## M5 boundary
Built disappearing messages with server-enforced expiry, one-view photos, group metadata/color/background configuration, and people/in-chat/all-message search including warm-offline results. The no-client expiry check passed; a read-only server inspection found zero remaining expiring rows before the harness reopened the clients. View-once uses the platform's asset refusal, and the suite saw HTTP 410 on a repeat fetch. Expiry and asset access fit much more directly than the separate scheduled deletion and signed-URL invalidation I would expect to assemble with Supabase or an object-store integration. Search reused the same device interpreter. The docs explicitly warned that an unscoped server search cannot claim completeness and that very wide server merges can hit the meter. The app uses the fully synced device index for its UI. The main missing convenience was configuration-file ingestion by Quarry; a small generator reads the JSON windows and emits constants. I also corrected my own seed ledger to retain digests rather than credential-bearing action lines.

## M8 — 1789524531
Built six maintained lifetime totals, seven UTC day buckets, exact current top-ten ranking with time expiry, and the configured scheduled digest. Added the profile Insights route, frozen summary/bar/ranking components, explicit refresh, a home chat rail, and narrow-screen stacking. Two same-account contexts converged live and after simultaneous offline composition. A real browser process restart retained pending messages, history, media, and search; reconnect reached read. A separate fresh digest instance emitted exact counts with all clients closed, survived a mid-period restart, excluded private/deleted activity, and emitted nothing in the quiet next period. Native Hermes export and compiled backend release are complete.

Maintains and server-owned chunk cursors made aggregates and restart-safe scheduling pleasantly direct. Current ranking needed an application-owned expiring table; the scheduled recipe's lag would not satisfy immediate refresh. That choice made likes queue without predicted rows, so the UI now uses the package's pending-write hook. The local-job/schema adoption interaction returned E_GENERATION and required reopening the scale host. Familiarity with indexes, attribution columns, and bucketed aggregates helped; JSX nesting and test login timing were ordinary agent mistakes. Compared with Postgres/Supabase, I avoided separately wiring row-change replication and a queue; compared with Convex, the durable device store is the unusual advantage. The public full-sync cost and custom language remain tradeoffs. No alternative was run, and I cannot make a measured comparison to earlier Snapback generations.
