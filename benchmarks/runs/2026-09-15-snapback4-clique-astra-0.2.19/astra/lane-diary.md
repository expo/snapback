
## M1 boundary — accounts and profiles
Built password signup/login with the built-in identity provider, session persistence and revoking logout, public live profiles, validated unique handles, complete profile editing, avatar uploads, Expo Router web shell and native image picking. Acceptance and the frozen two-client segment pass; the corrected native Hermes export is retained.

Quarry's unique index and asset column were easy. Password hashing and session lifetime required no application server code. The hardest work was my own React lifecycle wiring: initializing an edit form before the profile arrived, then using a shared pathname inside retained routes. Moving the persistent application shell above empty Router routes fixed duplication. Choreography also needed sibling instrument support directories, and the actual PATH Node differed from the overlay's promise. Those are separately recorded, not platform defects.

Prior general React, SQL and authentication familiarity helped identify lifecycle and uniqueness concerns. No prior Snapback checkout or earlier implementation was used. Reading the whole long README took effort but supplied the relevant APIs, including deliberate browser token persistence. There is no established platform gap from M1. Against Convex or Supabase, the asset field tying read authorization to the row felt unusually direct; UI and navigation still cost ordinary application work. This comparison is conceptual, not a measured competing build.

## M2 boundary — posts and follow graph
Built text/image/video posts, profiles listing authored posts, Following and Global feeds, likes, attributed reposts, direct reply threads, link tapping, and cursor pagination. Backend writes use set-state operations and stable create IDs. The M2 suite and all required choreography checks pass; an iOS Hermes export is retained.

The language made indexed queries and derived counts concise. Its `check --fix` resolved an explicitly diagnosed ambiguous index without guessing. I chose a server-side indexed merge for Following to avoid per-follower write fanout. The compiler accurately warns about the wide merge; the scale comparison still needs actual measurement. Likes retain a viewer-owned replica for future offline writes, while aggregate counts stay server-side.

Navigation and verification discipline fought me more than Quarry: the harness assumes feed tabs reachable from other screens, and concurrent suite writes displaced a choreography target beyond the first page. Both were my integration mistakes. A fixture adapter was also needed because the copied harness's default path assumes its original repository layout. No check was waived. The suite and choreography now run serially.

General SQL indexing and React familiarity saved time. The published feeds and prediction cards exposed the architectural alternatives clearly. Compared conceptually with Supabase, application query code is less split between SQL, authorization and client caching. Compared with Convex, Quarry feels more constrained but makes query residency and work bounds explicit. Those bounds are useful warnings, not yet evidence of scale success.

## M3 boundary — messaging core
Built unique DMs, distinct group entities, member/admin lifecycle, text messages and quoted replies, four-second typing expiry, monotonic delivery/read watermarks, and send-time recipient sets. Conversation ordinals establish server-arrival ordering. The native replica retains delivered history after removal. All suite assertions and all implemented choreography checks pass, including the removed-member cutoff after an independent DM progress witness. Hermes export retained.

Membership-scoped sync and server/device execution of the same history query were the strongest parts. A single expiry column handled typing cleanup and UI invalidation. Derived receipt state needed deliberate modeling, but per-member ordinal watermarks avoided per-message receipt fanout.

The first removal proof failed because a full-page navigation overtook the local client's asynchronous durable admission. A standalone probe showed the actual mutation and authorization were correct when allowed to settle. The README explicitly states the admission boundary. I used the published online arm with keepalive for membership controls; messages remain local-first. This was my integration error, not evidence that Snapback delivers rows after an effective revocation. The corrected proof passed.

Prior knowledge of replicated high-water marks and React effects helped. The writes guide supplied the exact per-conversation ordinal recipe and the sync guide spelled out retained-history behavior. Compared with familiar hosted backends, putting retention and expiry next to the schema significantly reduces custom cache policy code. Browser lifecycle boundaries still require application judgment; a local-first API does not make an unawaited UI action automatically durable.

Built photo/video messages, inline media and video viewer playback, per-user set/replace/clear reactions, editable text/captions, and deletion tombstones that clear asset placement. Window constants are compiled from the copied shortened fixture config into Quarry; the checks use server `now`, never caller time. All required suite and choreography checks pass, including actual recipient video playback. Hermes export retained.

Asset upload and home-row revocation remain compact. Adding optional media fields and literal defaults adopted existing messages cleanly. Reaction aggregation was a short maintained view. The compiler documents that the inherited reaction counts increase device residency, which remains a scale consideration.

Two UI errors needed correction: a completed send cleared a subsequent draft after a predicted bubble appeared, and the video viewer mounted its observable root too late for the harness's initial selector choice. Draft clearing now compares submitted state; the viewer has a persistent wrapper. Neither required backend changes or an instrument waiver.

Prior React async-state experience helped diagnose the draft race. Quarry's asset and adoption documentation supplied the rest. Compared conceptually with Supabase storage policies or application-managed signed URLs, clearing a typed asset column is easier to connect to revocation. Against Convex, the constrained schema language provides fewer escape hatches, but this feature set fit without one.

## M5 — Ephemeral content, customization and search

Built per-chat disappearance, one-view photo placement, durable per-viewer opened state, admin-owned group details, the pinned color palette and background uploads, plus people/in-chat/all-chat indexed search. The suite and all four browser choreography checks passed. An isolated backend also lost its message and denied its image after 185 real seconds with no clients open.

Expiry felt unusually direct: one timestamp column, one `expire at` declaration, and the existing query/sync machinery removed the content. Once-assets likewise put the trust boundary in the backend rather than in a modal's state. Search reused the same scoped query offline without a second JavaScript search implementation. I still had to distinguish ordinary asset prefetch from deliberate first-view acquisition.

The friction was mainly my integration: a test expected title case while the frozen kit uppercased headings, and an isolated test initially omitted required profiles. Browser navigation can overtake asynchronous settings admission, so the explicit online keepalive path already used for membership controls also handles settings. Prior familiarity with React lifetimes and HTTP asset semantics helped; no earlier Snapback implementation was inspected. The docs supplied the exact expiry and once semantics; no missing platform capability was established here.

Compared with Supabase I avoided a storage authorization route plus client cache invalidation policy and a separate expiry worker. Compared with Convex I avoided writing application cleanup scheduling and a separate local search model. Those comparisons describe implementation shape from general knowledge, not measured builds. The first-party local evaluator is doing substantial work, but its horizons and asset-lifetime rules must be read carefully.

## M6 — Offline writes, notification seam and external clients

Built a durable notification effect in the send transaction, a pinned replay-mode config, a dependency-free HTTP client and documented field manifest, and the complete 13-verb adapter. The sample's 50 authoritative receipts were syntax-validated by the frozen validator and independently checked against expected profiles, follows, posts/media/counts, memberships, quotes and reactions. The custom-client demo traversed two real history pages, sent and polled a message. Web choreography observed two pending offline messages, ordered flush and read receipts. The milestone's native Hermes export succeeded; simulator execution is not claimed.

The easy part was reusing the same mutations in browser, HTTP demo and replay. There is no privileged import path in the adapter. Stable mutation IDs give retries the intended set-state semantics. The difficult part was knowing which local facts are complete: an existence guard on a brand-new message ID was unnecessary and blocked optimistic evaluation past the history horizon. Removing it left idempotency with the wire protocol, where it belongs. The compiler also rejected iterating a filtered recipient list for notification effects and prescribed the original bounded membership page. My first text replacement placed that effect in the wrong mutation; that was an authoring mistake, not a platform defect.

A second suite run correctly saw no push immediately after Bob's browser closed: the published 35-second presence grace was still active. Waiting for the stated grace fixed the test. General HTTP and distributed-systems familiarity helped with retry IDs and bearer revocation. The docs covered all required seams, although the effect guide's suggestion to hold effect claims is not equivalent to the brief's requirement to suppress emissions; I used an explicit app replay flag.

Compared with Supabase, durable device evaluation and ordered outbox settlement removed a substantial client subsystem. Compared with Convex, the explicit plain-JSON protocol made a small third-party client straightforward, while query completeness and predicted writes needed more attention than a server-only reactive client. The public release met this milestone's web bar without source inspection. Full scale execution remains on its own clock after M8 so aggregate checkpoints can be included.

## M8 — Insights, scheduled digest and multiple devices

Built six server-maintained lifetime totals, seven UTC-day activity buckets including zero days, exact trailing-24-hour Trending with zero-like candidates and newest-first ties, and a scheduled digest. The digest uses a per-user period ledger and bounded message/member sweeps, excludes tombstones and unauthorized chats, and emits through the same durable seam. A real two-period isolated test with no browsers produced the expected two active-user payloads, none for inactive accounts, none in the next empty period, and no duplicate across a backend restart. Two Alice devices passed live delivery, cross-device unread clearing, dual-offline ordering and normal receipts. The suite and native export also passed.

Maintained counts and calendar groups were easy to express. Attribution for replies and reposts needed explicit fields and a bounded backfill for the earlier milestones' data; the platform did not pretend that a join-derived author appeared automatically. Trending needed its own expiring candidate table because a simple daily bucket is not a rolling day and a count maintain omits zero-like posts. That online ranked side effect means likes queue without local prediction; the UI now exposes a pending-change indication.

The largest interruption came from development tooling: long-running Node25 Metro hit a graph error, repeated logs and memory exhaustion during choreography. I restarted under the environment's intended Node24 and excluded artifacts and isolated backend directories from its watcher. I also removed literal JSX spaces that generated React Native warnings and broke avoidable import cycles. Those were client/tooling corrections, not evidence of a Snapback defect. A reload assertion initially counted rows before hydration and was corrected to wait for the screen.

Prior knowledge of aggregate attribution, period ledgers and restart-safe job cursors helped. The published maintain and jobs cards covered the required backend mechanisms; compiler diagnostics correctly rejected JavaScript optional chaining and gave the Quarry replacement. Relative to Supabase, this avoided a separate cron runtime and explicit aggregate trigger installation. Relative to Convex, the overall scheduled-transaction shape felt familiar, while the bounded sweep discipline was more explicit. Full-corpus performance remains the next independent measurement rather than a claim inferred from these small tests.

## Post-green verification and refinement

The complete corpus was replayed through 167,243 starter-plus-scale actions. The final attempt passed both checkpoint manifests and the combined final manifest, with exact per-user/per-chat counts, named public-API checks and all 10,000 busy-chat messages paged. All measured degradation gates passed after changing dense Following readers to an indexed global-event filter. A separate five-page equivalence proof preserved feed order and membership semantics. Sparse-follow readers retain the original merge. The compiler's sparse-filter notice is an honest bound on workloads unlike the measured envelope.

Two unsuccessful replay attempts remain in evidence: an idle pooled HTTP connection reset during checkpoint verification, and a verifier's reply/media-type mapping error after a fully settled corpus. Neither was a demonstrated server defect. Final checks also found two authoring/test issues: receipt obligations now bind to membership seats so a rejoin cannot regress an old receipt, and the initial online UI waits for the replica sync barrier before exposing a composer. Isolated single/dual writes passed while a full-route regression was flaky; the sync barrier resolved the full choreography. Seed-idempotence checks now exclude independently expiring test messages rather than treating a correct expiry as a duplicate-seed failure.

A supplemental published process-device test acquired the full-envelope account, reopened offline, returned history and search results, preserved a queued write across process restart and flushed it. That strengthens confidence in the shared interpreter and durable queue. It remains distinct from iOS application execution; the iOS evidence here is the requested Hermes bundle exports.

The final review caught ordinal subtraction masquerading as an unread count. A bounded Quarry query now drives a truthful New indicator, excluding own and tombstoned messages and inheriting server expiry. Direct read/delete tests passed. This was application logic, not a platform gap. The full-envelope replica proof was repeated against this final query on a disposable replay copy.
