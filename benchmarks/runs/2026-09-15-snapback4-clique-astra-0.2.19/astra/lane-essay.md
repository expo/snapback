# Clique on the published Snapback 4 surface

This build changed where I spent my attention. I still had to build an application: authentication screens, navigation, composers, media affordances, settings, query states and a usable API. Snapback did not remove that work. It did remove several backend/client seams that normally become separate projects. A Quarry table's authorization rule, sync audience, expiry rule and indexes described behavior that the server and the device both understood. The benefit was clearest when the brief asked for behavior that crosses those boundaries: disappearing content, offline search, durable queued messages and revocation of locally viewed media.

This was a cold build from the pinned public packages and their documentation. I did not inspect an earlier Clique implementation, a Snapback repository or a previous benchmark run. Comparisons below draw on general familiarity with other backend architectures, not fresh side-by-side measurements. The native artifacts are successful Hermes exports. They are not evidence that this particular app was exercised in a simulator.

## The ordinary application work remained ordinary

Profiles and the social graph were straightforward to model. Built-in identity gave me a real password authentication path, session persistence and revocation without inventing an account system. Posts, follows, likes and reposts were normal relational entities. The interesting part was deciding which relations should reach a device. Public profiles could be synced wholesale at this envelope, while a viewer's private likes could be synced only to that viewer. Public feeds could remain online projections. That is a useful distinction: the public nature of data does not require sending the whole corpus to every phone.

The client still exposed my own mistakes. I initially mounted route content in a way that retained duplicate screens. A form initialized before its profile arrived. An asynchronous send cleared a newer draft. A media-viewer root appeared too late for a consumer looking for its contracted selector. Literal JSX whitespace generated a remarkable amount of React Native logging. None of these problems became easier merely because the backend was declarative. The frozen UI kit reduced design decisions, but integrating it correctly still required careful ownership of state and lifecycle.

This matters when comparing authoring effort. A backend can be excellent while a run spends substantial time on navigation or browser tooling. Conversely, a green UI does not establish that the server enforces its apparent behavior. I kept direct API checks beside browser checks for precisely that reason.

## The device was the largest difference

With a conventional Supabase architecture, I would expect PostgreSQL and row-level security to own the authoritative data, then a separate client system to cache rows, search them offline, queue intents and reconcile receipts. Storage authorization and cache revocation would add another boundary. Those systems are buildable, but they need an explicit design and usually application-specific code. Here, the same scoped word-prefix query ran online and over already-synced rows. The message mutation that ran on the server also described the predicted offline rows.

That reuse is powerful, but it has a condition: the device must know that the facts it is using are complete. My original send mutation checked whether the new message ID already existed. It looked like a sensible idempotency guard. Past a retained history horizon, however, absence of that ID was not known locally. The guard prevented the pending bubble from being predicted. Removing it, and using the protocol's stable mutation ID for retries, was both simpler and more correct. The published prediction material explained the distinction. General distributed-systems intuition helped, but it was not enough to guess the local evaluator's knowledge model.

Convex is a closer comparison for reactive queries and transactional functions. In a typical server-centered reactive client, I think first about the authoritative mutation and then about optimistic presentation. Snapback made local execution and incomplete knowledge part of the backend design itself. It reduced duplicated implementation while making query horizons, sync audiences and unknown local bases more visible. That is a trade: less handwritten reconciliation, more responsibility to understand what a device can safely conclude.

## Lifetimes and trust boundaries were unusually compact

Disappearing messages were the strongest example of reduced friction. The message received a server timestamp for expiry, and the table declared that timestamp as its lifetime. The server refused the expired row and its asset without a browser being open. Reconnected browsers purged the content. Search did not need a separate cleanup implementation. An isolated real-time test confirmed the row was absent and the image unavailable after the shortened deadline.

One-view photos used an asset placement with one-fetch-per-principal semantics. That moved the important rule away from a disabled button and into the server. The UI still had to avoid prefetching a once-photo, mount a stable viewer, record an opened affordance and keep those bytes out of any application-created durable cache. A second authenticated asset request returned the documented refusal. The mechanism was compact; using it correctly still required respecting acquisition as the actual view event.

In a Supabase-style stack, I would likely implement a mediated asset endpoint or equivalent token consumption, plus client cache controls. In a Convex-style application, I would still need to decide how file access, consumption and local retention compose. Snapback's placement semantics gave those decisions a common enforcement point. The confidence comes from this run's API and browser checks, not from treating a product label such as “local first” as proof.

## Aggregates and schedules exposed useful constraints

Insights was a good fit for maintained counts and calendar buckets. The client received six totals and seven day rows instead of downloading posts and counting them. Replies and reposts needed explicit author attribution, followed by a bounded backfill for the earlier milestones' data. The engine did not silently turn a join into an aggregate key. That explicitness added a little schema work and made the source of each total understandable.

Trending needed more thought. A UTC day bucket is not a trailing 24-hour window, and a like-count aggregate has no row for an unliked post. I used an expiring ranked candidate for every original post, with a score and timestamp ordering. It preserves zero-like candidates and removes old popular posts from consideration. The online ranked side effect also means a like can queue without predicting a local row. The client therefore needs a pending indication and terminal receipt handling; it cannot assume every durable offline intent is also optimistically executable.

The digest used the same durable effect seam as message notifications. A scheduled job initialized per-user period records, swept bounded message/member pages and emitted each nonempty payload with an emitted marker. A real two-period test ran with no browsers, restarted the backend between boundaries and verified no duplicate or empty-period emission. This felt familiar in the broad shape of scheduled transactional work I associate with Convex. Compared with a separate cron process calling a PostgreSQL application, the job cursor, schedule identity and writes lived closer together and required less external coordination.

## Performance required measurement, not declarations

The first implementation merged one feed lane per followed author. It was correct on small tests, but the early scale probe showed the 500-follow reader exceeding the published ratio against the five-follow reader. I changed dense readers to filter the indexed global event timeline while preserving lane merging for sparse readers. Five pages were identical before and after the change, and the early dense-reader measurement improved substantially. The compiler's sparse-filter notice remains relevant: a high follow count does not guarantee a dense recent timeline in every possible workload. This is an envelope-tested choice, not a universal feed architecture.

The replay also tested my tooling. A pooled HTTP connection reset after a blocking inspection pause; bounded transport retries with unchanged mutation IDs addressed that. A verifier incorrectly compared a fixture reply category with a wire media type; that was a test bug. I preserved those failed attempts rather than describing the eventual result as a clean first pass. Every action used the real application path, including registrations and media uploads. Disposable stopped copies allowed write probes without polluting the canonical corpus.

Earlier Snapback generations are a limited comparison here. I did not use an older release in this session and cannot attribute current behavior to a historical improvement curve. The published generation I actually used expresses the backend through Quarry and supplies a shared server/device interpreter. My meaningful observation is about that present authoring surface: it can make lifetime, authorization and offline execution one design problem rather than several loosely connected implementations. Any claim about how much better it is than a particular earlier release would need a controlled run of that release.

Overall, the backend reduced friction most when one rule had to remain true on the server, in a live client and in a disconnected device. It added friction when I guessed unfamiliar syntax or treated local absence as authoritative absence. The diagnostics were often concrete enough to correct the mistake immediately, but reading the guide first would have saved some of those loops. The result is a substantial application with unusually little backend glue. Its remaining confidence limits—especially unexecuted native lifecycle proofs and workload-dependent feed behavior—should stay visible alongside the successful builds and tests.

A final supplemental test exercised the published process device at the full envelope: cold acquisition, offline history and search, and a queued message surviving process restart before flushing. It strengthens the shared-engine evidence while leaving the iOS UI lifecycle unmeasured. Final browser regression also reinforced the same lesson as the earlier prediction guard: an online answer is not a substitute for completed local acquisition. Waiting on the public sync barrier made that boundary explicit.
