## M1 — Accounts and profiles

Built password signup/login, persistent sessions, server revocation on logout, public live profiles, unique handles, all profile fields, and uploaded avatars using the frozen kit in Expo Router. Built-in identity and a single profile table were easy: the first Quarry check passed, and asset placement used the profile's read rule without a separate URL policy. The kit reduced UI decisions substantially.

The friction was mostly mine: an Expo Stack retained hidden duplicate contract nodes, CI mode disabled Metro's reloads, and an empty CI variable was not accepted by Expo. The copied read-only choreography directory needed owner-write permissions, and its relative metering import needed the matching instrument directory copied alongside it. These were not backend defects. The documented Node24 path also differed from the actual shell PATH, so I selected it explicitly.

Prior React and browser-test familiarity helped separate stale-bundle behavior from backend behavior. I had no prior implementation source. The published client reference was unusually detailed; reading the whole published surface took more orientation than the small M1 backend required. Compared with familiar Convex or Supabase designs, identity plus row-controlled assets avoided custom auth and storage plumbing. That comparison is model knowledge, not a fresh competitor run. Suite and two-client choreography passed; Hermes export exists, without a simulator claim.

## M2 — Posts and the follow graph

Built text/image/video posts, attributed reposts, set-state likes and follows, direct reply threads, profile post lists, and paginated Global/Following feeds. The published prefixed feed recipe installed without conflicts; the app's post mutation calls its helper in the same transaction. The compiler accepted the app schema on its first pass, with useful aggregate residency notes. Starter actions used real credentials and mutations; per-user installed-segment markers now prevent reinstallation from changing later user activity.

The recipe saves invention but is a substantial serving model: private copies, shared author routing, slot counts, tombstones, and cleanup. Its public docs describe limits plainly. This differs from the simple indexed-query model I would initially reach for in Convex or Postgres, and trades server fan-out choices for explicit replica residency. I have not measured the scale envelope yet. The public post cards and aggregate groups are currently fully synced; their cost remains a real risk to measure.

The main correction was app navigation: choreography expects feed tabs to remain reachable from profiles. A fixture-poster helper also assumed a native Image API that RN Web lacks; Expo Asset fixed it. Suite, choreography, and Hermes export passed. An Expo web event-dispatch console exception appeared during navigation despite passing observations; it remains a diagnostic to investigate rather than an invented backend defect.

## M3 — Messaging core

Built DMs, distinct groups, admin membership lifecycle, quoted replies, expiring typing rows, receipt aggregation over the send-time recipient set, and retained delivered history after removal. Browser choreography passed twice, including the final server-ordinal version. Every installed seed segment is verified idempotent; the native Hermes export passed.

Quarry's audience declarations did substantial work: membership removal and local history retention are schema policies rather than app cache surgery. The compiler accepted the messaging schema directly and identified the typing page's missing cap. Receipt aggregation was ordinary bounded application code, with per-member delivery/read high-water marks. The ordering guide explicitly warned that millisecond timestamps plus client IDs do not prove server arrival order; adopting its ordinal recipe was a useful correction before closing the milestone.

React familiarity saved time wiring route resolution and component lifetime, but the app still owns delivery acknowledgements, read acknowledgements, typing render timers, and navigation. The platform did not pretend those UI facts could be inferred automatically. Compared with SQL/realtime subscriptions, partition revocation and delivered-history retention felt materially more integrated. Compared with Convex live queries, the local query card adds meaningful completeness/freshness obligations. No missing backend capability was established at this step.

## M4 — Media messages, reactions, edit/delete

Built photo/video messages, a video viewer, emoji reactions with replace/clear intents, caption/text editing, and delete-for-everyone tombstones. Server window constants are generated from the checked config file, with production defaults retained alongside the shortened grading profile. Deletion clears the asset-bearing columns, which uses the platform's ordinary asset revocation path.

The media and reaction schemas compiled directly. The most useful abstraction was one upload placed in one authorized row: there was no separate signed-URL lifecycle to reconcile. The app still needs explicit upload failure handling and a proper video viewer; the kit deliberately supplies only a poster/play surface.

One suite check raced a predicted row against server acknowledgement. Correcting the test to wait for authoritative settlement made the distinction concrete; it was my test error, not data loss. The first choreography run passed its UI checks but remained non-green because it was correctly bound to that failed suite receipt. A new linked run passed after the suite repair. Compared with familiar hosted databases, the local/server boundary adds testing discipline while reducing hand-built optimistic state. No platform capability gap was established here.

## M5 — Ephemeral messages, customization, search

Built disappearing-message settings, server expiry, one-view photos, group/DM customization, background uploads, and people/in-chat/all-message prefix search. Search over the held partition passed warm-offline choreography. The unattended expiry choreography passed after closing and reopening the clients. An independent backend proof also verified deleted asset denial, server-side edit-window refusal, and message/asset expiry with no client open at the deadline. Hermes export passed.

Expiry and one-view enforcement were remarkably direct: a nullable deadline plus `expire at`, and an asset column's `once` modifier. I initially put `once` on a mutation argument; the diagnostic named exactly where it belongs and supplied the rewrite. That was an authoring error against a clear diagnostic. The client still must avoid fetching a one-view asset before the user opens it, revoke its transient URL on close, and render an opened state.

The search guide makes two costs explicit: full local history makes held search simple, while server-wide history needs a two-cursor membership/result walk. I chose complete local acquisition for this app and added the bounded server operations for the API. This is more unified than maintaining separate SQL full-text and ad-hoc offline substring algorithms, but acquisition is not free. The compiler's completeness words remain important; the group-title discovery query is locally useful and cannot claim complete server enumeration. No demonstrated capability gap at this boundary.

M6 boundary — Custom API, offline outbox, push seam, and replay adapter. The typed client made a standalone messenger and a sequential 13-verb fixture adapter straightforward. Fifty actions were settled and independently checked, and the generic push worker logged authorized payloads without introducing another domain backend. A process-backed replica survived an offline close/reopen with ordinary media, search, and two pending messages, then flushed them in order. The exported web shell has a service worker; the iOS artifact is a Hermes export, not a simulator proof.

The hardest loop was a plain UI mistake: I supplied “pending” as a ReceiptState instead of using the kit's receiptPending boolean. That yielded a zero-size receipt and repeated choreography failures despite correct durable writes. I initially blamed reconnect timing; application diagnostics disproved that. Reading the kit props earlier, or typechecking sooner, would have saved time. Queue lifecycle familiarity helped build the independent reproduction, but it did not excuse that misdiagnosis. Compared with a typical Supabase client, considerably less queue/reconciliation code was necessary; compared with Convex, offline restart is more directly part of this client contract. The scale adapter and fresh-instance invariant verifier are authored before starting their separate replay clock. Actual scale results remain to be measured.

M8 boundary — Insights, trending, daily digest, and multi-device offline are implemented. The final suite and choreography pass. Server maintains supply the six totals and UTC buckets. A dedicated expiring rank table keeps trailing-day trending exact without scanning an old high-score tail. The digest's resumable sweeps gather per-period public activity and authorized unread messages, revalidate candidates, emit through the push seam, and commit the emitted marker atomically. An isolated real-clock proof passed an active period, restart mid-period, restart after emission, inactive-user silence, inactive-next-period silence, private-chat exclusion, and tombstone exclusion with every client closed.

The aggregate syntax felt concise and automatic adoption rebuilt maintains. Digest job design fought the language's deliberate constraints: a rule cannot dereference an arbitrary joined field, and a mutation cannot scan an expiring table. The diagnostics led to an exists rule and a nonexpiring staging table whose candidates are revalidated by the job. That was a workaround in my design, not an omitted requirement. I also added an inbox on the root screen for the cross-device unread interaction and resolved existing DMs from held membership rows for cold-offline navigation. The web shell now passes an offline reload proof; the separate process-backed replica proof covers cached media, search, likes, reactions, durable messages, ordered flush, and read receipts. Native evidence remains the required Hermes export, without a simulator claim.

Compared with Convex's familiar TypeScript model, Quarry needed more up-front thought about what a scan can prove, but fewer independently authored sync and expiry mechanisms. Compared with Supabase, the difficult work stayed within one backend language instead of crossing SQL policies, triggers, storage rules, realtime, and a queue library. My prior database/index and offline-outbox familiarity helped; it did not prevent several ordinary integration errors. The full M6 scale replay passed its exact manifest at all checkpoints.
