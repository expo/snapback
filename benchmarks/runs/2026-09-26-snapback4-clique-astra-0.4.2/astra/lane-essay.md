# Building Clique on the published Snapback 4 surface

This was an independent cold build using the public 0.4.2 packages, their documentation and generated API. I did not read another implementation or a Snapback source checkout. The comparison below is qualitative: I built only the Snapback lane. My descriptions of Convex, Supabase and older backend patterns come from model knowledge, not a timed competitor build or a claim about their latest releases.

The most distinctive reduction in work was that schema, authorization, replication and asset lifetime could be written together. A message belonged to a conversation; membership governed its rows and bytes; an expiry field made it absent when the server clock crossed a deadline. The no-client expiry test showed the message disappearing and its asset returning 404 without a browser doing cleanup. A view-once field similarly moved the decisive check to the byte-serving boundary. Those are features for which a conventional database plus object storage design usually needs several cooperating pieces. Here the important policy was visible beside the field.

That mattered more than saving a few endpoint functions. Media revocation, membership removal and offline copies are places where individually plausible subsystems can disagree. I could express retained delivered text separately from current membership and let the backend enforce byte access. I still had to write product logic—the UI, receipt semantics, windows, membership administration and error handling—but I did not write a second storage authorization service or an offline database engine. In a Supabase-shaped design I would expect to coordinate SQL policies, storage access, subscriptions and a separate client persistence strategy. There is considerable power and familiarity in those primitives. This run illustrated the appeal of having their relationship specified by one program instead.

Quarry was compact for the social graph and feeds. Uniqueness constraints and idempotent set-state writes fit follows, likes and reposts. Maintained counts avoided application-managed increment/decrement races. The activity union and Following projection were a concise statement of which activity belongs in a feed. In the insights milestone, immutable reference paths let likes be grouped by the original post’s author; calendar buckets supplied the seven-day breakdown without transferring posts to the client to count. The daily digest could iterate each recipient’s current memberships under a server schedule. That is a useful shape: public activity totals can be summarized cheaply while private unread counts still follow an explicitly authorized path.

Compared with the application-function style I associate with Convex, the trade is vocabulary. Ordinary TypeScript is familiar and flexible; Quarry makes more structural decisions visible to the compiler. I had to learn the forms it accepts rather than translate arbitrary JavaScript literally. A failed attempt to use a conditional focal expression inside an aggregate became a bounded helper loop. A multi-column sync ordering was refused, so I used the documented conversation ordinal. Those corrections were small, but they were real learning costs. The helpful part was that the diagnostics usually pointed to a rewrite or a guide card rather than merely identifying a syntax error.

The greatest friction was at the client boundary, not in the schema. This is not simply a remote query hook with a cache. The app observes a device replica that can be acquiring, can have incomplete coverage, can predict a write, or can queue an intent without a predicted row. I initially treated temporary lack of data as a reason to tear down routes and rows. That caused repeated acknowledgement effects and, more visibly, caused a view-once image to vanish after it had already been consumed. The fix was to give the media viewer an appropriate UI lifetime above the refreshing list. Nothing in the backend could recover the bytes on a second fetch; the server was correctly refusing it.

Offline messaging exposed another version of the same mistake. Holding the composer busy until settlement prevented composing another message when the connection was absent. A durable pending-intent view, keyed by the SDK’s write ID, made the UI honest about an accepted local queue entry even when there was no predicted row. The installed outbox remained responsible for dispatch and recovery. I did not substitute a home-grown retry transport. A browser proof later showed history after a cold offline reload, the pending message after another reload, and settlement on reconnect. That proof is useful, but it is not an iOS simulator proof: the native deliverables in this lane are Hermes bundle exports.

Ordering and read coverage were particularly educational. A two-message choreography initially reported an order failure even though a server inspection showed the right acceptance order. The message list could become temporarily unavailable while its query refreshed. The `why` diagnostic exposed that the query’s ordering and the sync horizon did not match. Aligning them on a per-conversation ordinal, and computing receipt progress from bounded membership state, made the repeated browser probe stable. The ordinal also solved the genuine problem of timestamp ties: milliseconds alone cannot express total server-arrival order. I would recognize that problem in PostgreSQL or a function backend too, but the replica made the consequences of an index mismatch unusually immediate.

The replay adapter produced a different useful refusal. Its first media retry uploaded new bytes under an old write ID. The platform rejected the changed arguments with `E_ID_REUSED`. That was an adapter defect, not a backend inability to retry. Persisting the upload references made the same intent actually identical. The sample then exercised all thirteen fixture verbs through real authentication, uploads and writes, with an authoritative receipt before the next action. This is a good example of a strict interface making a sloppy test implementation visible rather than quietly accepting duplicate or divergent work.

I cannot make a measured claim about earlier Snapback generations from this lane. I did not inspect their packages, source, prior runs or diaries. The useful comparison is with the older architectural idea I knew: a backend whose rules and synchronization model are part of the same program. In this published generation, that idea is concrete enough to cover media, real accounts, effects, schedules, aggregate views and device-owned writes. Whether any earlier release supplied a particular capability is outside the evidence of this build. The current package’s compiler and guide, rather than remembered limitations, determined what I attempted.

There are limits to what the green bars establish. They establish the suite assertions and the implemented choreography checks at each milestone, together with the exported native artifacts. They do not turn a loopback development server into a hardened deployment, establish simulator behavior, or replace hidden grader probes. The scale replay has its own receipts, clock and invariant verification. I began it on a fresh store with notifications suppressed, independently of the development data accumulated by acceptance tests. Its final outcome belongs in the report, not in a retrospective claim that small functional tests proved scale.

My practical assessment is that Snapback reduced the number of independently maintained systems, while increasing the importance of understanding the one integrated system. The backend declarations were often shorter and more inspectable than the coordination code I would expect with separate database, storage and offline layers. The price was learning precise local-read, prediction and lifetime contracts. Once I treated those as product states rather than incidental loading behavior, the later milestones became easier. This is promising for an engineer willing to reason about replication explicitly; it is less forgiving of an app that assumes every absent answer is empty data and every write immediately produces a row.

The final scale work sharpened that assessment. The full replay verified its prescribed state, but a stronger browser check found that my unread-count helper could exhaust the read meter on a ten-thousand-message conversation. Small passing tests had not justified that query shape. Maintained counts over ordinal blocks, with a short boundary scan, fixed the server query. Then a cold offline reload exposed a separate issue: an expiry-aware aggregate could require source coverage outside the device's retained window. Separating locally available conversation identity from an optional unread badge kept the list and routing usable. I would need to consider count cost and offline freshness with other backends too; here, the integrated system made those constraints explicit through a diagnostic rather than silently returning a plausible incomplete count. The price was another round of schema work and UI design.

There was also friction outside the data model. An Expo transform cache retained the previous backend URL until I cleared it; one replay connection reset required recovery from exact settled receipts; and concurrent hot adoption and a CLI backfill contended on the large SQLite store. Those are distinct failures and should not be collapsed into a single verdict about Snapback. The corrected scale account acquired and survived a cold offline reload, but browser memory was substantial. The final report keeps the failed attempts, recovery clock and measurements. My confidence is strongest in the tested behavior and declared invariants, not in a claim that an integrated backend removes the need for load testing or careful client lifetimes.

One final offline regression made that lesson concrete: a predicted local message appeared before server settlement, and my UI mislabeled it as sent. Retaining the pending intent until the SDK's terminal write event fixed it. That was my state-model error, not a transport failure. An integrated outbox removes transport work, but it cannot decide what the application means by “sent.”
