## M1 — Accounts and profiles
Built password accounts through the built-in identity, persistent local-client sessions, public profiles with unique handles, avatar uploads, and Expo Router screens using the frozen kit. Schema validation and the first avatar path were straightforward; the policy attached to the asset's home row avoided a separate storage service. My row-to-form spread accidentally forwarded metadata and the accurate E_INPUT diagnostic exposed it. Copied harness permissions and adjacent harness dependencies needed local setup corrections. An overlapping acceptance run also overwrote its newer result; serial execution fixed the evidence linkage. Familiarity with React and Expo helped the shell; Quarry knowledge came from the package README and guide. Compared with general SQL stacks, auth and media authorization needed less integration code. Compared with Convex-style TypeScript functions, learning a new language and its read-card semantics was additional orientation. No M1 platform gap established. Browser suite and choreography green; Hermes exported.
## M2 — Posts and follow graph
Built original/reply media posts, likes, reposts, unique follow edges, chronological threads, profile posts, and paged Following/Global feeds. Used the published prefixed feed recipe and joined application cards rather than copying media. The schema compiled on its first check; generated types and helper integration were clear. Public replicated aggregates make the live UI convenient but increase cold acquisition, so this is a conscious scale tradeoff. React Native Web's asset resolver differed from native, and I repaired the platform branch. The harness's default fixture path needed an adapter. The hardest correction was a transient stale Following projection: a nonpredicting unfollow finished before the replica caught up. Waiting for explicit sync before feed navigation fixed the observable race. Familiarity with React helped; no prior Snapback implementation was consulted. Compared with Supabase I wrote fewer subscription/cache glue layers, but compared with ordinary server queries I had to reason more carefully about acquisition and freshness. Suite, all required choreography, typecheck and Hermes export passed.
## M3 — Messaging core
Built canonical DMs, distinct groups, admin membership lifecycle, text messages, quoted excerpts and jumps, live typing, and monotonic delivered/read watermarks. Each message captures its recipient set; current membership drops removed recipients from the aggregate. A conversation ordinal makes server arrival order explicit without relying on timestamp ties. Quarry compiled the model and its rules immediately. Retained-history sync made removed-member history much simpler than a hand-maintained cache. The UI needed stable group-id routes because names need not be unique, and direct counterpart routes now create canonical DMs. The initial choreography group route failed before those adapter/navigation corrections. The final suite and all required two-client checks passed, including the ordered delivery-progress witness after removal. The exported Hermes bundle and typecheck passed. Relative to Convex, the sync retention policy replaces substantial client cache work; relative to Supabase, aggregate receipt logic is more explicit application code but remains shared between server and replica. No M3 platform defect established.

## M5 — Expiry, one-time media, chat settings, search

I built server-timed disappearing messages, per-viewer once-only photos, synchronized chat colors/backgrounds, admin-controlled names and descriptions, and case-insensitive prefix search in a chat, across chats, and over people. The frozen window configuration generates Quarry constants; callers cannot supply time. An isolated server proof closed every client before advancing past expiry and then checked server reads, asset denial, replica resynchronization, and offline search removal. The native Hermes artifact contains the same local client and media policy.

Asset lifetime and expiry were unusually direct: a typed `once` image and an `expire at` declaration expressed guarantees that otherwise need endpoint authorization, cleanup jobs, and cache invalidation. Search also stayed in the backend language and ran against the replica. The awkward part was a browser view-once miss: the first harness pass stored an ordinary photo, but an independent UI reproduction sent `once=true`, and the unchanged retry passed. I have left the attribution ambiguous rather than inventing a platform explanation. The harness's expiry proof takes a real five-minute wait even though the configured short lifetime is three minutes.

Prior familiarity with React state, browser file choosers, and database retention rules helped more than any familiarity with this backend. I needed the published asset/search cards to understand the distinction between a viewed ordinary asset and a once asset. Compared with a conventional Supabase implementation, the server-to-replica revocation path removed several moving parts. Compared with Convex, the main difference here was the durable local query engine sharing the query definition; the tradeoff remains learning a new query language and its bounded traversal rules. These are experience-based architectural comparisons, not claims from a head-to-head run.

## M6 — Offline writes, provider seam, and external clients

I added a Quarry push effect and a provider worker that only durably logs payloads. The sender, recipient, absence condition and preview are decided transactionally in Quarry. The headless API demo signs in, lists conversations, pages history, sends, and polls for the new message. API.md explains tokens, expiry, logout, pagination, field mappings and raw HTTP. The replay adapter covers all thirteen frozen verbs and persists the mapping from fixture intent IDs to minted write IDs; its 50-action sample passed syntax validation and authenticated state verification. The scale driver was authored here, with fresh-instance startup, separate clocks, checkpoint verification, exact manifest counts, named API checks, full busy-chat paging and sequential probes.

The existing local-client configuration did most of the offline work. Browser choreography passed without an offline-specific UI queue, and a process-device proof retained pending messages across close/reopen, returned cached ordinary media and search results, refused viewed-once bytes offline, then flushed in order and reached read. That was the clearest reduction in application machinery so far. I initially suspected the explicit message ID might prevent prediction; the published residency guidance and the actual process proof showed that this schema's fully acquired partitions were sufficient. No workaround was needed.

The provider seam is more explicit than a conventional server callback: effects commit with data, presence can defer them, and the worker must deduplicate. That is useful, but understanding why a recently disconnected account may wait 35 seconds requires reading the presence card. The main missing convenience was accepting arbitrary fixture mutation IDs directly; the documented minted-ID contract required a small adapter ledger. My familiarity with token APIs and retry semantics helped keep the distinction between entity IDs and write IDs clear. Relative to Convex or Supabase plus a mobile cache/outbox, the surprising part was how little app-specific offline machinery I needed. This remains a bundle plus process/browser proof, not a claim of simulator execution.

## M8 — Insights, scheduled digest and multiple devices

I built the six server-computed lifetime totals, seven UTC day buckets with explicit zeros, and a top-ten Trending feed. Insights uses maintained aggregates. Trending uses a small public rank projection updated in the like transaction, indexed by score and original creation time and expired after a day. That choice makes the brief's newest-first tie rule explicit. The published maintain-based ranking recipe was useful, but its documented maintained-ID tie order did not express the rule as directly.

The digest is entirely scheduled Quarry work. It accumulates unread activity in small message chunks, emits per user with membership-aware inputs, persists a period marker, and tracks completed progress so coalesced periods recover activity after downtime. The provider adapter adds external-delivery deduplication. An isolated clock proof covered positive counts with all user clients closed, private and removed-member authorization, expired/deleted exclusions, silent empty periods, restart/manual retry, and catch-up across skipped boundaries. The existing replica and shared read watermarks handled the same-account live and dual-offline choreography; no second queue implementation was necessary.

What fought me was language precision: schedule units are minutes/hours/days, text needs a bound, a text lookup can be ambiguous with byId, and row-rule terms cannot directly compare an aggregate expression. Those were my authoring mistakes, and diagnostics were specific enough to correct them quickly. The rank projection retains an aggregate-copy note; there is no public mutation accepting an arbitrary score, and the helper computes it from the maintained count. The fixed top-ten query also deliberately has no pagination cursor. I documented these rather than suppressing the notes.

Familiarity with indexed ranking, materialized counts, UTC buckets, and resumable jobs mattered here. Compared with a SQL backend, Quarry made the live counters and replica consequences explicit but required more syntax learning. Compared with a function backend, its job chunks made transaction boundaries visible instead of leaving batching implicit in application code. I did not need a cron process in JavaScript: the only JavaScript worker performs the provider seam. The scale replay continues on a frozen M6 copy with its own clock; its first checkpoint passed before this boundary. Hidden grader probes and simulator execution remain outside the evidence I have produced.

### Final integration audit

After the first M8 green, the scale probe exposed the documented broad-prefix word-expansion cut. I added truthful partial-result messaging and corrected people search to newest-first, then reran the full M5 segment. I also found that quote jumps assumed the original was already in the loaded page and used a DOM-only scroll method. The final client requests an indexed context window around an unloaded original and routes scrolling through the web/native container, keeping the rendered window bounded at the busy-chat envelope. These are later integration corrections, retained in the log and final timing, rather than silently treating the earlier green as proof of every edge case. The scale replay's first and second checkpoints have independently verified their manifests.
