# Building Clique with Snapback 4

The most consequential part of this build was sharing the data model and query language between the server and a durable client replica. That changed where I spent effort. I still had to build screens, choose indexes, define authorization, and make media interactions behave correctly. I did not have to invent a second representation of a message for an offline database, a separate optimistic reducer, or an application-specific retry queue. By the time the brief reached offline messaging, much of the machinery was already present because the earlier milestones had used the local client consistently.

This is a cold-build account based on the published Snapback 4 package, its documentation and diagnostics, the generated API, and this lane's tests. I did not inspect earlier Snapback implementations or runs. Comparisons with Convex, Supabase, Firebase, and conventional API stacks draw on general architectural knowledge, not matched experiments performed here. In particular, I cannot claim a measured improvement over earlier Snapback generations. The useful comparison is between the responsibilities this release took on and the responsibilities I would otherwise expect to implement.

The initial authoring experience was less familiar than TypeScript functions or SQL migrations. Quarry is a real language with its own rules, rather than a thin wrapper around expressions I already know. A missing text bound, an ambiguous key, or an unsupported expression in a row rule can stop compilation. I encountered each of those. The compiler usually supplied an actionable location and rewrite, which made the correction inexpensive, but it did not eliminate the need to learn the language's distinctions. The distinction between an operation being eligible to predict and a particular call having enough acquired facts was especially important. That is a valuable distinction, but not one most product engineers carry into their first database-backed screen.

The published documentation helped most when it presented a complete design. The feed recipe gave me a concrete way to handle ordinary fan-out and celebrity delivery without pretending that one naive query would suit every account. The asset, presence, prediction, and job cards similarly described operational behavior, not just syntax. I could ask what a refusal meant and connect it to a design change. The weaker moment was moving from a recipe to a slightly different product rule. Trending required newest-first ties, so I chose an explicit score/time projection rather than rely on a maintained-ID tie order. That left a documented aggregate-copy note and another projection to maintain. A backend can make a common case easy while still requiring careful judgment around the boundary of its example.

Compared with Convex's function-oriented model, Quarry made locality and traversal constraints more prominent. In a TypeScript server function, I would expect to express a transaction in a familiar language and reason about reactive reads around it. Here, the same declaration also influenced what a disconnected device could answer or predict. That coupling reduced duplication, but it made schema design more consequential early. Whether a table was fully synced, windowed, or online-only could change an interaction from an immediately visible pending row to a queued write without one. I had to reason about the client's evidence, not just the server's transaction. Once those choices were correct, the benefit was tangible: the web choreography and the process-device restart proof exercised the same message operations without a special offline implementation.

Supabase would offer a more familiar SQL-centered starting point for the aggregates and reporting. Joins, counts, ranking indexes, and explicit migrations are well understood tools. The part I would expect to assemble separately is the complete mobile replica story: durable queryable local data, a mutation outbox, replay ordering, optimistic presentation, asset retention, and revocation after reconnect. Realtime delivery alone does not describe those responsibilities. In this build, the server's rules and sync declarations carried much of that policy into the local client. The tradeoff is that I accepted Quarry's expressiveness and budgets instead of reaching for arbitrary SQL or server code whenever a query became awkward.

Media made that trade particularly visible. Ordinary viewed assets, once-only photos, deleted references, and expired messages need different lifetimes. The typed asset fields and expiry declaration let the backend enforce those differences. I still had to avoid opening a once-only asset through a generic eager image hook, release viewer URLs, and wire the file chooser correctly. Those are application responsibilities. But the backend could refuse the second view and revoke an expired reference while every client was closed. The isolated proof then checked that a replica synchronized the removal and could no longer find or open the content offline. That was stronger evidence than hiding an expired bubble with a client timer.

There was also a useful reminder that not every failure belongs to the backend. One choreography run sent an ordinary image where a once-only image was intended. An independent browser reproduction sent the correct flag, and an unchanged retry passed. I did not find enough evidence to identify the cause, so the log keeps it ambiguous. Other mistakes were clearly mine: a browser-only image-resolution assumption, UI navigation races, and language syntax errors. A comparison that attributes all of those to the platform would be misleading. Conversely, a final green receipt should not erase the effort spent diagnosing them.

The notification seam felt closer to a durable transactional outbox than a casual callback. Quarry decided recipients, presence eligibility, and payloads in the message transaction. A separate worker only logged the provider payload. Presence also had a grace interval: an apparently connected recipient could defer a notification, and a subsequent poll could satisfy it. The digest extended the same design with scheduled chunks, emission markers, provider deduplication, and a progress watermark for coalesced periods. I did not need a JavaScript cron service to supply the business logic.

For reporting, maintained aggregates were a good fit for the lifetime totals and UTC day buckets. They let the Insights screen ask for a small result instead of paging the corpus and calculating totals in the client. Trending needed a more deliberate choice. I used a projection whose score is derived inside the like mutation and whose ordering includes original server time. There is no caller-facing operation that accepts an arbitrary score. Expiring the rank rows gives an indexed trailing window. This is a design I could also build in SQL or a transactional function backend; Snapback's contribution was keeping the projection, expiry, authorization surface, and replica consequences in the same authored backend. Its diagnostic about copying an aggregate was useful precisely because it forced me to state why this projection existed.

Firebase and a custom REST-plus-SQLite stack are helpful additional reference points. Client SDKs with offline persistence can remove substantial work, so offline support by itself is not a unique idea. What stood out here was applying the authored backend operations to a local query engine with explicit sync coverage and server replay. A custom stack would offer the most control over wire formats, storage, and query semantics, but it would also make me responsible for reconciling those layers. Snapback reduced that integration surface. It did not remove the need to test loss of connectivity, restart, duplicate intents, shared read watermarks, or authorization changes.

The scale adapter was another boundary where familiar engineering discipline mattered more than framework convenience. Fixture registration went through real auth, every action waited for authoritative settlement, and arbitrary fixture intent IDs were mapped to the SDK's minted write-ID form. The replay uses a fresh instance with notification suppression, not the development database polluted by acceptance activity. At the time of writing this essay, replay is still progressing; the first checkpoint's exact counts and named fixtures have passed. I have not yet tallied timings or claimed the final envelope. The deliberate serialization makes the workload reproducible, and it also exposes costs that a burst of unacknowledged requests could conceal.

There are limits to what this run establishes. Each milestone has an iOS Hermes export, but a bundle export is not simulator execution. Browser choreography and a published process replica provide useful functional and durability evidence; they do not prove every native integration detail. The app also uses full public post and like replication, which simplifies offline prediction at the cost of a larger cold store. The development instance and shortened fixture configuration are intentional testing posture, not a completed production deployment. I would carry those facts into an operational review instead of treating “production-shaped” as “ready for arbitrary production traffic.”

A later envelope probe exposed a concrete search limitation: a broad first-term prefix can exhaust the published word-expansion bound and return a partial answer without a continuation. An exact handle lookup still completed. I recorded that as a platform gap and made the UI disclose incompleteness rather than imply an exhaustive result. This is an important qualification to the pleasant search authoring experience: using the same query on server and replica does not make the query unbounded. The backend's explicit refusal and completeness vocabulary helps diagnose the limit, but the product still has to account for it.

The experience ultimately shifted effort from synchronization plumbing toward schema and evidence design. Snapback 4 was most effective when a feature could be stated as a rule, a sync partition, an aggregate, or a scheduled bounded traversal. It added friction when I tried to use a familiar expression where Quarry required a more specific construct, or when a recipe's semantics differed slightly from the brief. Relative to earlier Snapback generations, the only defensible conclusion from this cold run is that the published surface here was sufficient to build and test the continuous-session features without reading implementation source. A stronger historical comparison would require another controlled run. For this app, the practical result was a small, coherent backend definition and fewer independently implemented client/server behaviors to keep aligned.

Postscript after replay, before the final tally: the complete fresh-instance replay and invariant manifest passed. Applying the M8 schema to that corpus also completed: the bounded backfill finished, named users’ aggregate totals matched independent counts, and the exact trending list matched. This strengthens the corpus-specific evidence without removing the search bound or the native-execution qualification above.
