Clique on the published Snapback 4 package felt most distinctive when the application crossed from ordinary CRUD into offline behavior. The backend was a collection of Quarry files, but those files did more than define remote functions. They also determined which rows a device held, which operations it could predict, how permissions affected local reads, and when assets stopped being readable. That changed the shape of the work. I spent less time building a second client-side data system, and more time checking whether each backend expression preserved the guarantees the client needed.

The early milestones benefited from that integration. Profiles, follows, posts, conversations, and memberships fit naturally into tables with indexes and rules. The generated API connected the Quarry declarations to the Expo client without a separate hand-maintained transport schema. The React hooks supplied observable reads and paged collections. Uploads returned typed asset references, so the same authoring surface covered avatars, post images, videos, chat backgrounds, and message media. I did not need to invent storage URLs, a parallel media-permission service, or a separate native queue. That was a meaningful reduction in architectural work, even though the application still required substantial UI composition and verification.

Convex is the closest alternative in my prior architectural vocabulary for the reactive part of this experience. Server functions and client subscriptions can make a live application feel cohesive, with fewer seams between a mutation and its visible result. Snapback added an unusually direct relationship between backend declarations and the device replica. A `sync` line was a deployment decision about local data, not just a subscription convenience. For this brief, that distinction mattered: messages had to remain available without a connection, queued writes had to survive process restart, and read state had to converge across two devices belonging to the same account. The published local client provided those mechanisms. I would expect more explicit offline-layer work in an application built around an online reactive service, although this run did not test any current Convex offline integrations.

Supabase brings a different set of strengths to mind: PostgreSQL, familiar relational tools, explicit row-level security, and the ability to use mature database facilities when a query grows complicated. Quarry's tables, keys, and server-maintained counts were comfortable from that perspective. However, Quarry is not a general SQL console with a thin SDK around it. The compiler and runtime constrain the programs that can be evaluated safely and locally. That narrower surface made some decisions clearer and some rewrites less obvious. With PostgreSQL I would have more ways to express an aggregate or a migration, but I would also have to join more components to deliver the same offline replica, asset revocation, and predicted-write experience.

The most instructive friction was prediction. A message-send mutation initially worked online and passed live interaction checks. Adding a presence-dependent notification path then made it non-predictable. The offline queue still existed, but the user had no predicted message bubble to see. The published presence text suggested a device would treat recipients as connected during prediction; the operation diagnostic instead classified the presence read as server-only. I resolved that mismatch by splitting delivery into two durable stages. The send transaction emits a notification request, and a service-only Quarry mutation checks presence and emits the final payload. The worker transports effects; the business decision remains in Quarry. This is a familiar outbox pattern, but discovering that it was necessary here took a correction loop.

A separate existence check showed how easily a harmless-looking guard can affect offline behavior. Reading a message ID that was outside the replica's history horizon prevented a predicted row. Removing that redundant lookup restored prediction; stable mutation IDs already supplied retry deduplication. The follow-up regression mattered: the starter seeder had relied on that guard when replaying old messages. I changed seed installation to record completion explicitly and to check existing starter messages during a partial installation. The lesson was practical rather than philosophical. A shared server/device program reduces duplicate implementation, but it makes residency assumptions part of ordinary mutation review.

The scale run uncovered a second surprising interaction. The database contained the full busy-group history, yet a shaped history response returned no continuation cursor. A diagnostic query with only basic fields paged correctly. The receipt helper's early return was the isolating difference. Rewriting the helper to accumulate the same state restored the outer cursor. I also retained a compact reaction summary to avoid nested page work in each message projection. These were small source changes with large behavioral consequences. A compiler warning about the lost continuation would have saved more time than another general example of cursor syntax. The generated classifications and `why` output were useful, but not every runtime interaction was visible in them.

Insights and Trending were more pleasant. Maintained counts and sums gave the six lifetime totals without sending the corpus to the client. Explicit day and digest-period buckets made the reporting semantics inspectable. Trending used an indexed ranking table, updated with the social mutations and expired by the server, rather than scanning and sorting the entire recent corpus. That is a conventional materialized read model, expressed within the same language as the application. The main cost was denormalization and backfill work. The benefit was a small, predictable read path that did not grow with the total post count.

The digest was another place where the integrated backend reduced friction. A schedule drove a system job, the job computed authorized per-user activity, and a durable effect carried the payload to the logging seam. Transactional period receipts made the intended idempotence visible in the schema. The proof used a real shortened schedule, closed clients, and a backend restart; it did not call the job to simulate the acceptance condition. The following quiet period emitted nothing for the controlled users. In a PostgreSQL-centered application I would expect to assemble scheduler, transaction, and delivery pieces explicitly. In a function-centered backend I would look for the equivalent scheduled-function and outbox facilities. Here they were part of the published Quarry surface.

Native support also changed the tradeoff. The exact Expo package supplied the native device arm, and every milestone produced an iOS Hermes export. A separate process-device test demonstrated durable pending writes, offline search, restart, ordered flush, and final read receipts. That is useful evidence about the shared replica, but it is not a simulator proof, and I do not treat it as one. Similarly, the successful web choreography is evidence about the implemented interaction paths, not proof of arbitrary production networking conditions. Keeping those boundaries explicit is important when a platform unifies so much of the stack.

I cannot responsibly give a release-by-release comparison with earlier Snapback generations from this run. I did not inspect an earlier package or checkout, and no earlier implementation was used as a template. The architectural comparison I can support is that this published version makes the schema, authorization, synchronization, operations, and scheduled work one authored backend. Whether an earlier generation exposed fewer of those facilities, or required more application glue, would need separate evidence. This session demonstrates both the attraction and the cost of the current approach: a small number of declarations replace entire client subsystems, while language and runtime edge cases can influence behavior far from the edited line.

The result is encouraging with concrete limits. The requested milestone suites and implemented choreography are green, the full replay reached the exact invariant state, and full API paging now traverses the busy chat. The measured search curve missed its strict middle-checkpoint bound, and I have preserved that result rather than interpreting a low absolute latency as a pass. The application also remains a local, production-shaped build with a provider seam, not a deployed notification service. Relative to the alternatives I know, Snapback reduced the amount of infrastructure I had to invent. It concentrated the remaining difficulty in understanding, validating, and occasionally working around the consequences of making one backend program serve both the server and the device.
