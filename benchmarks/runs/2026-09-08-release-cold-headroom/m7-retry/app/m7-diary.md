# M7 Author Diary

This was a fresh, bounded day-2 continuation over the exact assigned pre-replay starter state. I used the supervisor timestamp as the clock origin rather than treating my first shell command as time zero. No excluded lane, assessment, prior report, diary, transcript, baseline, or grader finding was supplied or accessed.

The first important discovery was that this was not a blank count migration. The pre-M7 schema already maintained `messageCounts`, and chat settings already exposed it. Its semantics were wrong for the new requirement: it counted every message row by conversation, including tombstones, and only ceased counting expired rows after their scheduled deletion. I therefore recorded `preExistingCountStructures=true` and changed the model to a stored `conversations.visibleMessageCount` backed by a tombstone-aware aggregate, an explicit backfill job, and forward updates on sends, polls, tombstones, and expiry.

I deliberately avoided rewriting the existing message discriminator. A first direct widening of `messages.kind` compiled, but the owner correctly demanded an explicit successor migration, and the reviewed apply was refused before changing data. The safer design added an optional logical `messageType`; old rows project through their unchanged legacy `kind`, while every new message writes both the legacy-compatible kind and the logical type. Poll details live in their own bounded query after an attempt to nest them into every history row exceeded certified bounds.

The backfill visited the three existing conversations and wrote the observed counts of six, one, and nine. Immediately after the final required-field transition—and before acceptance fixtures—the immutable snapshot was run under the required Node runtime. Its semantic payload matched the supplied pre-M7 snapshot once capture timestamps were ignored. All baseline message IDs remained intact. That proves preservation for the values actually populated: text/quote structure and receipts. The starter image, video, reaction, edit, tombstone, and view-once classes were empty, so I do not treat them as populated-value migration proof.

The authored journeys caught two useful issues. Advancing time inside the first M7 journey contaminated a later digest journey, so expiry became its own journey after the digest scenario. A malformed vote test also used an operator combination the quarry language rejected; I corrected the assertion rather than weakening it. The final journey set covers poll bounds and group-only creation, one changeable set-state vote, exact retry idempotence, poll/text count increments, tombstone decrement, and scheduled expiry decrement.

The first complete M7 suite passed, but browser work exposed behavior the headless API suite could not. Two fresh tabs could contend on the web-specific IndexedDB store name and remain at “Restoring Clique…”. Giving every tab a durable, session-scoped namespace fixed concurrent startup. The next choreography run showed that the frozen poll kit’s `accessibilityValue` was not emitted by this React Native Web version. I added an app-side semantic bridge for stable option IDs, numeric tallies, selected state, pending state, and total; the frozen kit and harness remained untouched.

The final offline failure was subtle and came directly from the installed offline contract. `useOutbox().entries` includes settled ledger entries until they are dismissed, so it is not a truthful busy indicator. `useMutation(api.polls.setVote).pending` contains only queued intents. Switching the UI to that source made the pending marker appear while offline and clear only after reconnect settlement.

I retained the compile, migration, suite, export, setup, hydration, semantic, and offline failures rather than reporting only the best result. I also retained command-entry mistakes, including accidental Node 26 inspection/snapshot attempts, malformed flags, and malformed shell/tool invocations. Each authoritative qualification command was rerun with Node 24.18.0 and the assigned environment.
