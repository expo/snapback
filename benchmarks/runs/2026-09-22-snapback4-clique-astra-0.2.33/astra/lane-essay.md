# Building Clique on the published Snapback 4 surface

This build changed where the hard work lived. The most useful parts of Snapback 4 were not individual conveniences such as a query helper or a generated type. They were the fact that the same authored backend described server authority, device residency, prediction, expiry, and aggregate maintenance. A chat message could be inserted by a Quarry mutation, arrive through the replica, appear as a pending local row while disconnected, and later acquire an authoritative receipt without an application-specific synchronization service. That is a substantial reduction in the number of systems an engineer must make agree.

I built against the pinned public packages and their published documentation, without consulting another Snapback checkout or an earlier Clique implementation. This matters to the interpretation of the result. The mistakes in this lane were often mistakes of discovery or application design, rather than evidence that a feature was unavailable. The scale fixture's self-repost was a particularly clear example: I had invented a product restriction, the fixture exercised it, and the server correctly enforced my wrong rule. Removing that restriction and separating original and repost identities fixed the problem. Blaming the backend would have concealed the actual correction.

The first account and profile work felt conventional. Password signup, sessions, unique handles, and generated client operations were direct. Avatars forced the more interesting question: an asset is not just a public URL. The reference belongs to an authorized row, and the client obtains a handle whose lifetime matters. That model initially adds concepts compared with uploading a file to an object store and putting its URL in a table. It pays back later when a message expires or is deleted. The authorization relationship already exists; it does not have to be retrofitted into separate storage policies and cache invalidation code.

Media also revealed the boundary of what the backend can simplify. Expo Web's image behavior, a browser file chooser, video posters, and a React Native warning overlay remained ordinary application engineering. The overlay that obstructed an attachment action came from stray JSX text, not a broken upload service. Metro's stale transformed modules caused another correction loop. Restarting the owned development server with a cleared cache resolved it. A product engineer still has to distinguish a rendering failure, a stale build, a failed write, and a refused asset fetch. Good backend semantics do not remove that diagnostic work.

Messaging was where the unified model did its best work. Membership rules and sync declarations expressed who could receive new messages. Retained delivered history was distinct from continuing membership. Reactions, edits, tombstones, and receipt markers fit into the same data model. Disappearing messages used server expiry, and view-once photos used the asset's once policy. I verified expiry with the relevant clients closed, rather than trusting a timer in a screen. I also reopened a durable device store offline: ordinary viewed media remained available, a consumed once photo did not, and queued messages survived. Those tests exercised relationships that are easy to promise and much harder to implement consistently in an app-owned cache.

The comparison with Convex is closest around authored server functions, reactive reads, and transactional application logic. In a Convex-shaped implementation I would expect the server mutation and subscription story to be comfortable, while the durable offline store, prediction, queue recovery, and media-cache lifecycle would require more explicit application decisions. In this build those were part of the installed runtime. Conversely, Quarry was less permissive than a general-purpose function body. It refused an expiry-table page inside a mutation, required proof around nullable values, and explained when a write could not predict. Familiar TypeScript habits did not always transfer. The advantage was that these constraints were encountered before silently shipping an unsafe or unbounded operation.

Supabase offers a different familiar starting point: SQL, PostgreSQL constraints, authentication, storage, row-level security, and additional services. That ecosystem gives an engineer broad freedom and familiar operational tools. For this particular app, the cost would be coordinating policies and change delivery with an offline database and outbox, plus jobs that revoke media and process expiry independently of open clients. Snapback concentrated that coordination in fewer authored files. The tradeoff was giving up arbitrary SQL as the application language and learning the engine's indexes, bounds, maintains, and residency rules. Neither tradeoff is universally better. A team already invested in PostgreSQL analytics would evaluate it differently from a team whose central problem is disconnected mobile collaboration.

The aggregate milestone made the distinction concrete. Lifetime totals and calendar buckets became maintained declarations. The screen fetched a small server-computed result; it did not page through the corpus to count it. Trending required more thought. A calendar day is not a rolling twenty-four-hour window, and a ranked list of liked posts does not include zero-like candidates automatically. The published guide addressed both problems with hour-scoped ranking and a zero-like fill. This was useful documentation because it exposed the design's reasoning and boundaries, rather than offering a deceptively short example that only worked on a small dataset.

The scheduled digest was similarly revealing. I used the fixture's shortened schedule, closed the test clients, restarted the backend during a period, and checked the emitted payloads. The job traversed each recipient's memberships, excluded tombstoned content, and wrote a period marker in the same transactional work as the effect. Repeating the same period did not duplicate delivery; a quiet following period emitted nothing. In a more assembled backend stack I would expect a scheduler, a worker, idempotency storage, and authorization-aware counting to be separate pieces. Here they were still separate responsibilities, but the backend supplied their execution model and their failure boundaries.

There was a learning cost in those boundaries. An effect guarded by presence must keep its branch safe for prediction. A paged index needs a stable cursor suffix. A lookup can be nullable even when the surrounding application logic makes existence seem obvious to a human. I corrected several such mistakes from the diagnostic and guide, and also caught mistakes in my tests: an incorrect generated argument name, an un-awaited write-receipt lookup, and a compiler output I initially overlooked. The useful distinction is between friction that clarifies a real invariant and friction that merely makes authoring verbose. Much of this run's Quarry friction was the former, although a competent newcomer still needs time to acquire the model.

The public surface was unusually important to progress. The README led to a substantial client reference, keyword guide cards, generated operation types, and diagnostics with suggested rewrites. I did not need repository archaeology to discover expiry, the push worker seam, replay suppression, server-arrival ordinals, or scheduled jobs. The guides also warned about broad feed merges and incomplete reads. Those warnings were worth measuring rather than either ignoring or treating as automatic failure. One scale probe caught a query that returned the correct ten Trending rows but had discarded the page metadata; preserving the shaped page fixed the incomplete-result flag. That distinction between plausible data and a complete answer is part of the backend contract, not merely a display concern. Scale replay was a different workload from clicking through a friendly starter fixture; it exposed an application assumption and forced exact state verification and retained evidence.

I cannot make a measured version-by-version comparison with earlier Snapback generations from this cold build. No earlier checkout, diary, benchmark, or source repository was inspected, and inventing a historical experience would undermine the comparison. What this release demonstrably offered here was a published, installable server/device/client system with explicit policies for offline writes, asset lifetime, effects, and maintained data. The meaningful comparison with an earlier local-first approach is the amount of that policy now available as an authored backend contract, rather than as application glue. Whether a particular older release had each capability is outside this run's evidence.

The experience leaves me with a specific engineering preference rather than a universal winner. For an app whose defining requirements are private shared state, disconnected writes, server-enforced lifecycle, and convergence across devices, this backend reduced the amount of coordination code I had to own. It added a language and a proof model that had to be learned carefully. The successful tests are evidence for this implementation and this pinned release, not a claim that all native behavior is proven by a bundle export, or that every possible scale shape is safe. The strongest part of the result is that the difficult behaviors could be made executable and reviewable without escaping into a separate application backend.
