## M1 — Accounts and profiles
Built password signup/login, persisted sessions and logout, live public profiles, unique handles, all profile fields, and uploaded avatars. Quarry's profile rules and generated operations were easy: the first schema compiled. The shell took more care: React version matching, copied harness permissions/imports, and Expo Stack's retained DOM complicated proofs. Familiarity with React and browser automation helped; no prior Snapback implementation was consulted. The README was unusually actionable, although write-ID formatting only became concrete after E_WRITE_ID and the writes card. Compared with Convex or Supabase, built-in password identity and policy-bound assets reduced the number of separate integrations. The local interpreter and acquisition state add concepts those ordinary online paths do not have. Suite and frozen choreography passed; iOS Hermes exported.
## M2 — Posts and follows
Built media posts, text links, follows, implicit self-feed membership, live counts, repost attribution, direct reply threads, and paged feeds. Maintained counts and nested Quarry shapes were concise. I initially guessed shape syntax and corrected it from the shapes card; that was my error. React Native Web image APIs and stale Metro transforms fought harder than the data layer. Persistent feed navigation was needed by the frozen choreography. Repeated runs have explicit logs, including an accidentally overlapping pair whose shared receipts are not green evidence. The final isolated choreography passed. A compiler warning makes the current read-time Following merge's scale cost explicit; small-data correctness is proven, scale safety is not yet. Compared with SQL joins and realtime subscriptions, typed shaped reads are pleasant; compared with Convex TypeScript, learning a second language has a visible initial cost.
## M3 — Messaging core
DMs, distinct groups, admin add/promote/remove/leave, bidirectional messages, typing, quoted replies and sender avatars are implemented. A small recipient snapshot plus monotonic member receipt positions gives group receipts; removed members leave the receipt requirement. The retained-history sync policy avoided writing a second historical cache. The suite and all eight choreography checks passed, including removal cutoff, retained history and timing boundaries. Pair identity needed two principal columns rather than text concatenation: Quarry correctly refused treating principals as strings. Familiarity with relational membership models transferred well. The backend handled realtime and authorization without a channel server; a conventional Supabase implementation would have needed more explicit delivery and cache policy. Typed rules still require careful thought about how query completeness interacts with membership scoping. Native export succeeded. M7's visible message count is not present.
## M4 — Media, reactions, edits and deletion
Photo and video messages render from authorized uploaded assets; reactions are set-state intents with one row per actor/message; captions/text edit and media deletion are server-authoritative. Durations come from JSON configuration compiled into Quarry helpers; grading uses the shortened values. Suite and all choreography checks passed, with a fresh native bundle. The hardest loop was mine: a literal JSX space caused React Native warning overlays that intercepted clicks. A screenshot exposed it. A second suite error read server state immediately after optimistic rendering; authoritative polling fixed the test. Asset revocation itself was easy: clearing the home column made a fetch fail without implementing signed-URL expiry. This is materially less glue than storage buckets plus independent SQL policies, while familiar React Native debugging still dominates the client side.

## M5 boundary
Built synchronized chat colors/backgrounds, config-driven disappearing messages, view-once photos, indexed online and held offline search. The once asset modifier and table expiry made server enforcement unusually direct: an independent real-time test closed every relevant client, then confirmed message disappearance and asset revocation. The frozen choreography also passed its longer timer. Search was easy once the held-query distinction was understood. Media viewer lifetime and native/web image differences required application care. Familiarity with local-first caches helped separate durable ordinary media from transient once media. No platform gap was found here. Compared with Supabase, expiry and asset authorization required less infrastructure; compared with Convex, device-local search came with the runtime rather than an additional cache design.

## M6 boundary
Built the logged push provider seam, token-only documented custom client, complete fixture replay adapter, and explicit server-arrival ordering. Existing local-client integration passed the frozen two-message offline queue and receipt choreography without an application outbox. Push presence grace and service token ownership were clearly documented. Quarry rejected an expiry-table page inside a mutation and a variable-cost presence branch; moving the profile read outside the guard and passing receipt ordinals solved both. The sample's 50 actions, all 13 verbs, and resulting media/reactions/quotes/membership passed. An initial test used the wrong generated argument name, corrected as agent error. Native bundle exported; simulator proofs are deliberately not claimed. Compared with Convex or Supabase, the durable replica and at-most-once writes saved substantial application plumbing. The cost is learning the engine's proof rules, not merely TypeScript. Scale replay starts on its own clock, fresh instance, with push/schedules suppressed and exact checkpoint audits.

## M8 boundary
Built the six maintained lifetime totals, seven UTC day buckets, rolling 24-hour like-ranked Trending with zero-like fill, scheduled digest, and multi-device read/arrival handling. Used the frozen Insights and Trending kit. Exact totals were independently compared with paged source cards and edges in acceptance, rather than only checking nonnegative numbers. The frozen multi-device choreography passed. A Node process-device proof (not claimed as an iOS simulator proof) reopened offline with pending messages, searched durable history, retained ordinary viewed images but not once images, then flushed messages, likes and reactions without duplicates. Every milestone has its iOS Hermes export.

The digest was a real server schedule using the fixture's 120-second config: all relevant clients closed, backend restarted mid-period, one correct payload per active user, tombstone and membership exclusions, exact-period retry deduplicated, and the following quiet period emitted nothing. Calendar maintains and the documented digest recipe made the aggregate work straightforward. Rolling time windows required more care than a simple daily group. Compiler diagnostics caught a nullable timestamp, a seconds-versus-minutes schedule unit, and a missing id suffix on a cursor index. I also forgot to await the asynchronous write-receipt accessor in my offline test; the replica had already done the right thing.

Compared with Convex, the difficult boundary moved from application-maintained counters/cache/outbox code into declarative aggregate and residency rules. Compared with Supabase, very little infrastructure glue was necessary, but SQL instincts were sometimes counterproductive because Quarry insists on bounded and provable operations. There is no demonstrated platform defect in this run so far. The scale replay exposed my unjustified restriction on self-reposts; I removed it and preserved the failed attempt. Final scale evidence and the persistent dataset are being completed on their separate clock.

### Post-boundary verification corrections
The persistent scale probe caught a real application query mistake: rebuilding Trending's full ranked page as an ordinary array discarded continuation metadata and returned `complete:false`. The guide explicitly preserves the full page; I changed that branch to return a shaped page and retained the zero-like fill only for a short page. A parser error in the first correction and an over-hasty readiness diagnosis were both recorded and corrected. The app never promoted the incomplete response into a complete claim. The final replay also independently audits every entity count and runs the full warmup/sample protocol. Earlier in-memory replay evidence is retained, but the deliverable scale store is now persistent.

Regression tests exposed an evidence-management weakness rather than an application failure: stable suite filenames were overwritten, while prior frozen receipts referenced their hashes. Most exact historical payloads were recoverable by hash from unchanged test results and their timestamp; the original M2 suite payload was not. Final choreography reruns bind the retained current files, and future acceptance writes immutable timestamped receipts. This limits the reproducibility of that historical first-green snapshot, not the final green result.
