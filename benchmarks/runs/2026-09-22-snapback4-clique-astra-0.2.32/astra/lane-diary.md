
## M1 — accounts and profiles
Built password signup/login, persistent sessions, server logout, public profiles with unique handles, image upload and live profile edits. Suite and frozen choreography passed; iOS Hermes export exists. Quarry schema and avatar policy were compact; the first compile passed. My Expo route setup fought me: optional catchall and stale Metro route manifest caused an unmatched root until corrected and restarted. Fixture IDs also are not valid SDK mutation IDs; the diagnostic supplied the correct mintId idiom. Copied harness permissions and an undeclared sibling metering import required local environment repairs. Familiarity with React and auth flows saved time; no previous Snapback implementation was consulted. Compared with known Convex patterns, schema, auth and media policy live closer together. Compared with SQL/Supabase, unique ownership and sync were unusually concise, but understanding the new client result vocabulary required careful reading. No platform capability gap established in M1.

## M2 — posts and follow graph
Built text, image and video posts, links, profiles with live follow counts, likes, reposts, direct replies, and paged Following/Global feeds. The public Following recipe saved designing promotion and removal from scratch. Its typed event/app-reference boundary caused two first-pass compile refusals; the manual integration example resolved them. Choreography passed after fixing profile/feed navigation and adapting the fixture directory. The SDK did the live invalidation with little application wiring. The recipe adds many tables and public replicated reference rows; this is more explicit machinery than a typical small Convex query or SQL join, but designed to bound reads for the 500-follow fixture. Familiar React composition helped; no prior Snapback code was read. The docs were unusually candid about the acquisition cost. No proven platform defect or capability gap yet.

## M3 — messaging core
Built DM uniqueness, groups and administration, quoted replies, expiring typing, captured recipient sets and monotonic delivered/read watermarks. Removed members retain delivered history through the platform policy. All suite and choreography checks now pass; the Hermes export is retained. The table/rule/sync model made the membership boundary understandable and compact. The UI add-member picker exposed my mistaken assumption that empty word search enumerates rows; a separate empty-query branch fixed it. Existing knowledge of relational membership and high-watermark receipts helped. Compared with Convex, receipt and typing tables feel familiar; compared with Supabase realtime, there is less subscription/filter/cache plumbing. The difficult question was retained history versus current membership, and the published retain policy handled that directly. No simulator claim is made.

Built photo/video messaging with real uploads and playback, per-user reaction set/replace/clear, caption/text edits, and tombstones that clear assets. ## M5 — expiry, one-view media, customization, search
Built server-enforced disappearance from the config, one-view image placement, chat backgrounds/colors and group identity editing, and people/scoped/global prefix search over the replica. Suite and every implemented choreography check passed. An independent proof closed Dave and Erin and verified expired history and asset denial after 185 seconds. The frozen choreography independently waited five minutes with Alice and Bob closed and verified purge on reopen. The platform's expiry and one-view asset types removed a significant amount of scheduler and cache-invalidation code. Search used the same indexed query path offline. Metro served stale generated API exports once; a cache-clearing restart fixed it, attribution remains ambiguous between bundler/environment and generated-file watch behavior. The login shell's Node25 override was discovered and commands now use the intended Node24. Compared with hand-built SQL plus client caching, the authority/cache linkage is substantially less work; the tradeoff is having to understand the platform's exact held/complete/pending vocabulary.

## M6 — offline queue, push seam, custom API and replay
Built the durable notification seam, a headless authenticated client demo, an idempotent 13-verb fixture adapter, and independent SQL invariant verification. The published SDK made ordinary headless mutations and subscriptions straightforward; the local replica gave the web client optimistic offline writes without a second data model. One repeat of offline choreography timed out after a previous pass, then passed unchanged; this is unresolved intermittency, not a proven repair. Expo Hermes export passes. Prior familiarity with stateful browser tests helped separate durable writes from UI receipts, but provided no Quarry shortcuts. Feed recipe and replay suppression are useful public surfaces; a complete fixture adapter and scale verifier still had to be authored. Compared with Supabase this avoids designing an outbox and replication protocol; compared with Convex, the predictable/offline distinction is a more explicit part of the application contract. Scale execution follows on its own clock.

## M8 — insights, trending, scheduled digests and multiple devices

Built six server totals, seven explicit UTC day buckets, a like-ranked trailing-day top ten, the two-minute grading digest schedule generated from configuration, and cached DM resolution for cold offline starts. Maintains made the totals and ordering compact; the published trending example supplied the right bounded hour-lane design. Jobs and effect admission let the schedule operate with every client closed, retain period markers through restart, and omit an empty next period. A fresh-instance proof confirmed the payload and authorization rather than relying on a UI trigger.

What fought me was the distinction between eligible prediction and an acquired device. Frozen choreography intermittently timed out on otherwise simple live/offline actions; small focused multi-device tests passed. I gated the composer on acquisition and used cached conversation identity instead of waiting for a server mutation reply during a cold start. The full choreography then passed; the earlier intermittency is retained and not presented as conclusively diagnosed. One generated nullable-array type was ambiguous in TypeScript; requiring the referenced post before shaping it avoided that surface. Suite mistakes included looking for a React Native button role the rendered control did not expose and checking a read receipt before the stream settled.

Familiarity with SQL verification, service workers and lifecycle races saved time. Quarry syntax still required its own documentation, especially rule terms, system jobs and time-bucket ordinals. Compared with Convex, maintained aggregates and durable local execution move more policy into declarations; compared with Supabase, I wrote much less synchronization plumbing but had to learn a new bounded-query discipline. The inherited public sync footprint is an important tradeoff, not a free optimization. The full-corpus replay and additional M8 probes remain independently clocked evidence, separate from the authoring green bar. No simulator claim is made; the requested native artifacts are Hermes bundles.
