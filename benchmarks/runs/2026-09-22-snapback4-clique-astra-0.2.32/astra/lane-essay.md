# Building Clique on the published Snapback 4 surface

This was a cold build against a pinned public package. I did not consult another implementation or a Snapback source checkout. My comparisons with Convex, Supabase and earlier Snapback generations are based on general model knowledge, not parallel implementations or measurements made during this run. The most useful question is therefore where the backend changed the work I actually had to do.

The defining difference was that the schema was executable application policy. Tables, read and write rules, maintained counts, replication declarations, jobs and mutations lived together in Quarry. A chat message was not just a database row that another service later decided how to distribute. Its membership rule, replicated audience, expiry and media ownership were part of the same authored backend. That shortened several features which usually spread across a database, an API server and a client cache. It also meant that a mistake in a rule or index could affect authorization, query completeness and prediction at once.

Profiles and ordinary social writes were the easy introduction. The generated API removed hand-maintained operation strings from the application, while the headless client could exercise the same writes for fixtures and a third-party example. Authentication did not require me to invent an identity system. The harder part was choosing a social feed representation. The published feed recipe had real machinery: private delivery, public celebrity broadcasts, pull subscriptions and removal markers. Using it gave me a credible fan-out design quickly, but the result was larger and more constrained than the phrase “follow a user” suggests. I had to understand its budgets and delivery modes, not merely paste it.

Convex offers a familiar programming-language environment for this kind of work. TypeScript functions, reactive queries and transactional mutations make many product operations feel direct. In this build, Quarry traded that flexibility for a compiler-visible account of reads, rules, bounds and prediction. The diagnostics often told me precisely which lookup prevented local execution or why a page could not prove completeness. That is useful feedback before a user experiences a problem. The cost was a separate language-learning loop: an expression that felt ordinary in TypeScript or SQL was sometimes not a legal rule term. I repeatedly needed the installed guide or an exact diagnostic rather than intuition.

Supabase would have given me SQL, database tooling and a broad ecosystem immediately. Maintained counters could be implemented with triggers or carefully written transactions, authorization with row-level security, and scheduled work with database or worker facilities. Those are familiar pieces. The work that would remain is integrating those pieces with an Expo client's durable offline queue, local search, prediction, retained membership history and media revocation. Snapback's local client made those aspects part of the backend model. I did not author a second offline database schema or a transport that reconciled it with a separate REST layer.

That advantage needs qualification. “Eligible for prediction” is not a promise that every call instantly creates a local row. A device first needs the relevant partition and backend. The documentation exposes acquisition as a separate condition, and this application now uses it before offering a conversation composer that depends on immediate offline prediction. A cached DM also has to be opened by its cached identity. Waiting for a fresh mutation result to discover an already-existing conversation works online and fails as a cold-offline navigation strategy. These were application lifecycle decisions, not features that a replication engine could guess for me.

The frozen multi-client tests were valuable precisely because a pleasant one-browser demo missed those transitions. Some live and offline choreography runs timed out while focused reproductions passed. I retained the failed receipts and described the uncertainty. The later complete pass followed acquisition and routing changes, but I do not have evidence that every earlier timeout had the same cause. A production team would want longer lifecycle stress tests and telemetry around queued-without-prediction outcomes. The successful browser restart proof establishes a concrete durable-queue behavior; it does not substitute for an iOS simulator proof, which this run did not require or claim.

Media was another area where the backend reduced the number of moving parts. Uploading an asset, attaching it to a typed field, reading it under the owning row's rule, expiring that row and handling a one-view field were connected capabilities. A conventional object-storage stack needs careful coordination between upload authorization, database references, signed URLs, retention and cached bytes. Here the client and backend already shared that vocabulary. I still had to build the actual image and video experience, select files in Expo, provide posters, release viewer URLs and avoid retaining view-once bytes. Backend support removed infrastructure work, not product work.

Insights and trending made the distinction between a reactive application and a scalable read model visible. Lifetime totals and UTC day buckets were concise maintains. Trending needed a more deliberate design: group likes by the original post's time, keep the score order transactionally, merge bounded hour lanes, and fill zero-like originals when necessary. The public guide explained that construction well. Copying a post's timestamp into a like also required preserving its trust boundary and backfilling existing data. The compiler did not make that migration disappear. One generated nullable-object array type caused a TypeScript problem; a required point lookup before shaping the result avoided it without editing generated code.

The digest was the strongest demonstration of server-owned work. A scheduled job could walk recipients, prove membership by walking their own memberships, count period activity, emit through the same notification seam, and commit a durable period marker. The fresh-instance proof closed every client and let the configured schedule fire, then restarted the backend and observed the next empty period. There was no client-triggered substitute. This is a coherent design, but it remains bounded: a recipient's complete live digest must fit one chunk's documented execution envelope. The guide is commendably explicit about the difference between durable effect admission and exactly-once delivery through an external provider. This application logs the seam; it does not claim APNs delivery.

Compared with earlier Snapback generations as I understand them conceptually, this published surface places much more emphasis on explicit acquisition, delivery policy, prediction diagnostics and operational envelopes. I cannot turn that impression into a release-to-release performance claim because I did not run or inspect an earlier generation. The useful evidence here is narrower: the current package supplied an Expo arm, a shared local interpreter, generated types, system jobs, media lifetime behavior and detailed guide cards that were sufficient to build and exercise this application. Remaining limitations should be judged from this run's exact refusals and receipts, not inherited folklore about older releases.

The overall experience was neither simply less code nor simply more abstraction. It shifted engineering effort away from synchronization infrastructure and toward declaring a sound data model, understanding bounded reads, and presenting durable states honestly in the client. The scale replay, invariant checks and degradation probes are separate evidence because a green product workflow cannot establish an envelope by itself. I would choose this approach for a product whose offline and authorization semantics are central, provided its team accepts the language and budget model. For a primarily online application with an existing PostgreSQL estate, Supabase's familiarity may matter more; for a TypeScript-heavy team optimizing reactive online iteration, Convex may offer a shorter initial learning curve. Clique benefited most where these requirements intersected: membership, media, server time, offline state and scheduled work.
