## Commission

Charlie ratified LLP 0146's D1–D3 first tranche for implementation at
author decision sitting #2. Scope, exactly as the RFC defines the three
decisions:

1. **D1 — declaration/observation conformance**, with the sitting's OQ1
   ruling applied: **strict mode is opt-in for newly generated apps** —
   a newly generated app does not opt in by default; strict-mode
   authoring is the opt-in surface for new and legacy apps alike.
2. **D2 — `snapback verify`, the done-oracle**, as the RFC defines it
   (CLI-orchestrated; not the pinned `acceptance.run` host operation).
3. **D3 — the agent digest**, as the RFC defines it.

The sitting also ruled OQ8: the Cloudflare fan-out stays **conservative
widening** for now — no hosted claim in this tranche is gated on
recovering fan-out precision.

## Boundary — OQ7 was NOT ruled

The sitting deliberately did not rule OQ7 (the CV-14 custody trigger in
the 0062 family). Implementation of this tranche **must not claim CV-14
custody satisfaction** without the custody owner's ratification. Any
D4-adjacent digest/verify work that would imply CV-14 custody stops at
an honest nonclaim.

## Exit

- D1 (strict-mode opt-in authoring), D2, and D3 implemented per LLP
  0146's decision text, with their acceptance obligations as tests.
- Capability/GAP rows updated honestly; no claims for the unratified
  D4–D7 remainder.
- Dated implementation-record amendment in LLP 0146 at landing.

## Progress log

### 2026-08-03 — D1 landed (report + strict-mode opt-in), first slice

**Landed.**

- **D1 surface 1 (report, v0):** `src/conformance.rs` —
  `DeclarationConformance` with the four class-tagged deltas
  (`missingReads`/`missingWrites`/`extraReads`/`extraWrites`) and per-class
  `readProvenance`/`writeProvenance` (`complete`/`incomplete`/`unsupported`),
  scoped to application tables (auth/permission captures and reserved
  projections excluded). Attached to the admin runner's `FunctionRunResult`
  on every arm (queries/mutations `complete` on success, `incomplete` on
  failure and pre-invocation refusals; actions `unsupported` always), to the
  `function.run` host-op envelope (`data.conformance`), and to the
  `app.inspect` recent-invocation ring — **scoped to host-op invocations**,
  the RFC's stated v0 fallback.
- **D1 surface 3 (strict mode, opt-in per app):**
  `defineSchema(tables, { strictDeclarations: true })` →
  `strictDeclarations` on the schema manifest (absent unless true; rides the
  schema hash via the schema evaluation) → enforcement at the two shared
  Ibex runtime seams (`run_ibex_query_with_reads_prepared`,
  `execute_ibex_mutation_prepared`), which every fresh/staged/nested/
  detached invocation path passes through, before result handoff and before
  any commit. Refusals: `SNAPBACK_HANDLER_UNDECLARED_READ` /
  `SNAPBACK_HANDLER_UNDECLARED_WRITE`, details naming function, table,
  declared set, and the declaration's source span. OQ1 ruling honored:
  default off for newly generated apps (test-pinned). HostPlan runtimes are
  exempt by construction (declared sets derive from the plan); declaration
  facts ride `PreparedInvocation` immutably.
- **Tests:** `tests/conformance_v0.rs` (8 tests: undeclared-read report
  with complete provenance; read/write swap reports both classes; action
  `unsupported`; strict read refusal with named code + span; strict write
  refusal with no durable-version advance; declared-conformant handler
  serves under strict; default posture stays evidence) and the
  `strictDeclarations` authoring block in
  `packages/snapback-codegen/authoring-validation.test.mjs`.
- **Docs:** dated implementation record in LLP 0146's Revised header +
  Status note; `operating.declaration-conformance` capability row (partial,
  GAP page, owner ccheever, review 2026-08-31).
- **Toolchain rotation:** editing `define.mjs` rotated every committed
  demo/fixture review manifest (inputsHash/bundleHash/schemaHash) — all
  regenerated via `scripts/check-generated-artifacts`; `schemas/*` Rust
  JSON-schema goldens regenerated via `snapback-schemagen`.

**Honest residue inside D1 (not exit-blocking for D1, recorded):**

- The `function.run` **mutation** envelope reports `incomplete` provenance:
  the recording/settlement mutation path does not hand captured sets back to
  the envelope seam. The authoritative mutation report lives on the admin
  runner result. Follow-up: plumb captured deps through
  `invoke_mutation_recording_*` so the host-op envelope can carry a
  `complete`-provenance mutation report.
- App-data-plane invocations are not in the recent-invocation ring (the
  RFC's admissible scoping; wiring the plane in is open).
- The per-dependency-class escape hatch ("explicitly conservative or
  unobservable classes, never a blanket disable") is specified but its class
  vocabulary is not — see Questions for the author. Not implemented.
- Cloudflare arm: the manifest flag rides through but nothing enforces it
  there and no captured-set authority exists (OQ14 open; OQ8 ruling keeps
  conservative widening). Stated in the capability row as a nonclaim.
- Strict enforcement covers the shared Ibex seams; the asset upload-intent
  authorizer (its own declared-reads surface, LLP 0044) is out of D1's
  function scope and unenforced.

**Remaining in the tranche (precise next steps):**

1. **D2 `snapback verify`** — CLI orchestration (not `acceptance.run`):
   artifact freshness/identity → runtime readiness receipt → admission +
   D1 conformance **coverage** (the aggregate over-declaration judgement,
   which is D1 surface 2 and deliberately not built here) → capability
   resolution → registered acceptance profiles; `--json` receipt binding
   profile identity, test-bytes digest, target/data identity, authority
   context, seed identity; `recommendedNext` only when mechanically unique.
   Start in `packages/snapback-cli` (new `verify` command) + a receipt
   schema; reuse the LLP 0010 readiness receipt verifier.
2. **D3 agent digest** — extend LLP 0062's
   `snapback-app introspect --changed-since` (packages/snapback-app-cli)
   with the two-section digest (static keyed by `envelopeHash`, dynamic by
   a `digestCursor` embedding it), byte/item budgets, stable ordering,
   honest elision markers; unknown/expired cursor degrades to full digest
   with a named reason. OQ10 custody: pick nothing silently — surface the
   coarse-resolution fallback (dynamic section sent whole) as the v0 and
   record it, since it needs no retention decision.
3. **Strict-flag refusal on non-enforcing targets** (added 2026-08-04 per
   the sitting #3 ruling below): load/ensure-time refusal with a named
   `SNAPBACK_*` code when `strictDeclarations` is present on a target that
   cannot enforce it (Cloudflare arm today), plus a test pinning the
   refusal. The flag must never ride through unenforced. This belongs to
   the tranche's continuation, not to the sitting's recording commit.
4. Then close the ticket with the LLP 0146 record extended to D2/D3 and
   capability rows updated.

**Questions accumulated for the author — RULED 2026-08-04, author decision
sitting #3 (`issues/closed/20260804-author-decision-sitting-3.md`):**

- D1's strict-mode escape hatch ("per-dependency-class... explicitly
  conservative or unobservable classes" — vocabulary undefined).
  **RULED: no hatch in v1.** The boolean strict-mode opt-in ships as-is;
  the per-dependency-class vocabulary gets defined only when a real app
  hits a conservative or unobservable class (evidence-driven). Nothing to
  build here until that evidence arrives.
- Should the strict-mode manifest flag be refused at load on targets that
  cannot enforce it? **RULED: REFUSE AT LOAD with a named code** — the
  flag must never ride through unenforced. Implementation item added as
  next-step 3 above. Partially resolves LLP 0146 OQ14 in the refuse
  direction (the broader capture-authority question stays open).

**Boundary check:** nothing in this slice claims or implies LLP 0115 CV-14
custody satisfaction (OQ7 unruled); D4 remains untouched.
