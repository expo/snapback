# P4 bucket verification — all 40 rows reach a durable or outbound effect

Status: open  
Date: 2026-08-24  
Systems: snapback-auth, snapback-sync, snapback-engine, snapback-kernel, snapback-server  
Related: `issues/20260824-liveness-row-bucket-assignment.md`, LLP 0283, LLP 0303

## Result

The P4 bucket is substantially mis-assigned: **all 40 rows fail the stated P4 criterion**.

The original bucket grouped duplicate or lower-layer sites. Duplication does not establish that no durable effect is reachable. Every row reaches either a durable database/file/blob write or an outbound effect. Eight are currently bounded by exact production callers and belong in P3; the remaining 32 expose a correlation decision covered by LLP 0303 and belong in P2.

No row can be closed as `CONFIRMED-P4`.

## Method and limitations

I inspected commit `5cae72b2b554e6ca9e5ce53e017bc5989e2ac8aa`, dated 2026-08-24 15:05:46 -0700. All cited declaration lines were checked against that tree. Every assigned row was located.

For each row I:

1. Located the current declaration and transcribed its complete signature. Signature whitespace below is normalized, but no parameter or return component is elided.
2. Followed the returned carrier, callback, plan, permit, ticket, or authority through its current consumers.
3. Continued until reaching:

   - a write, update, or deletion in `_snapback_*` or `_auth_*`;
   - a durable clock, counter, ledger, epoch, or watermark update;
   - a file or blob write; or
   - an outbound effect such as an email, credential/secret disclosure, signed invalidation, websocket publication, push delivery, or external asset PUT.

4. Distinguished process-local state from the later effect. An in-memory plan, fence, registry entry, or permit was not treated as durable by itself.
5. Applied LLP 0303’s provenance corollary: a type-correct or value-equal artifact is not a correlation unless the consumer verifies the exact producing instance. This is material to F115/F227 and F264/F265.
6. Used `PROMOTE-P3` where a durable/outbound effect exists but current production structure supplies the value only through an exact checked caller. `PROMOTE-P2` means LLP 0303 requires derivation or an instance-bound artifact and the row remains implementation work. No row exposed a current P1-style mismatch with an already available predicate at the same production seam.

What this analysis might have missed:

- It is static analysis; I did not run tests, inject mismatches, or read back databases.
- I did not inspect unenumerated JavaScript, FFI, generated, CLI, or unrelated authority surfaces.
- I did not verify whether a newer remote commit exists beyond the inspected checkout.
- Dynamic callbacks were followed through every installed production implementation I found. The public callback factories remain P2 because another in-crate installer can supply a different callback.
- Ordinary process-local mutation is not counted as durable. Where an in-memory carrier later gates a durable or outbound effect, the row is promoted on that concrete downstream path.

## Is the P4 criterion sound?

Yes, with two qualifications.

First, the criterion must be applied to the complete reachable graph, not the declaration body. A method that only allocates an in-memory plan is not P4 when that plan is the mandatory input to a later SQLite commit, blob PUT, credential disclosure, or websocket publication. That distinction invalidates most of this bucket.

Second, a P4 closure is a statement about current consequence, not a statement that the authority/subject API is well designed. If an authority is only live-checked and its subject remains independently supplied, the row is fragile even when its current result has no effect. Such a genuine no-effect row should be tagged `P4-FRAGILE` and reclassified immediately if a durable or outbound consumer is added.

The criterion itself is therefore sound. The original proxy—“duplicates another row”—is not. On the inspected tree, **40 of 40 duplicate rows reach effects, so the entire assigned P4 bucket must be reopened.**
