# Root-identity mechanism survey — what could supply a same-UID-proof root

**Status:** Open
**Systems:** Auth, Security, Storage
**Date:** 2026-08-26
**Related:** LLP 0303, LLP 0313, LLP 0284,
`issues/20260826-landing-a-cannot-establish-file-wide-authority.md`,
`issues/20260826-step-up-claimant-root-requires-new-ceremony.md`

## Why this exists

Two independent LLP 0283 F-1 workstreams stalled against the same wall: LLP 0303's
DERIVE rule terminates only at a root the caller cannot author, and Snapback has
no such root. Landing A could not establish file-wide authority; the step-up
claimant lane found a caller could mint a fresh valid identity and install it
first. This survey enumerates and costs every mechanism that could supply that
root, so the Landing C boundary decision is made against the real option set
rather than an assumed one.

Produced by codex `gpt-5.6-sol` at `xhigh` in a read-only sandbox against
`origin/main` at `ae106cdfb`. Its four load-bearing repository claims were
verified independently by the supervisor before landing: `keyring_path` resolves
to `<db>.auth-keyring.json`, `EncodedKeyEntry` serializes encoded key material
into it, `ProcessBoundIdentity::new()` is constructed fresh on every open, and
LLP 0057 backup step 5 writes the captured keyring bytes into the backup — so a
restored copy carries the same root and cannot establish device identity.

Claims about OS behaviour that could not be executed from a read-only sandbox are
marked UNVERIFIED in the survey and rest on linked primary platform
documentation. They should be executed before any mechanism is adopted.

---

## Bottom line

Snapback cannot provide a portable, transparent same-UID-proof root in its current local-development shape. It can obtain that property only by adding a boundary the caller does not share—such as a separately isolated service identity, signed-code/Keychain machinery on macOS, workload attestation, or Cloudflare’s platform capabilities. Otherwise the strongest honest guarantee is the repository’s existing one: protection applies to Snapback-controlled APIs and registered connections, not arbitrary native code or another process with the same UID and raw SQLite/filesystem access.

That follows directly from DERIVE: a forgeable root derives nothing, and the regress must terminate at something the caller cannot author ([LLP 0303:28](../llp/0303-subject-authority-correlation-policy.decision.md:28), [LLP 0303:843](../llp/0303-subject-authority-correlation-policy.decision.md:843)). Landing C therefore must choose either the trusted-native boundary or an external OS/service/cryptographic boundary ([LLP 0313:254](../llp/0313-authority-creation-chokepoint.spec.md:254), [LLP 0313:280](../llp/0313-authority-creation-chokepoint.spec.md:280)).

### Deployment shapes used below

- **M:** local CLI/server on Apple-silicon macOS—the packaged target is explicitly Darwin arm64 ([package.json:2](../packages/snapback-runtime-darwin-arm64/package.json:2), [package.json:28](../packages/snapback-runtime-darwin-arm64/package.json:28)).
- **L:** local CLI/server on x86-64 Linux ([package.json:2](../packages/snapback-runtime-linux-x64/package.json:2), [package.json:28](../packages/snapback-runtime-linux-x64/package.json:28)).
- **S:** the same native Rust/SQLite server operated long-running; its canonical architecture is one Rust process owning one SQLite database ([LLP 0003:43](../llp/0003-local-code-hosting-and-storage-core.rfc.md:43)).
- **CF:** the checked-in Cloudflare Worker/Durable Object target, presently a narrow proof rather than a general hosted product ([targets/cloudflare/README.md:1](../targets/cloudflare/README.md:1), [README.md:386](../README.md:386)).

Evidence notation: I locally verified that this machine is an Apple-M4 Mac, that `/usr/bin/security` exposes trusted-application `-T` controls, and that no `/dev/tpm0` or `/dev/tpmrm0` is present. The read-only constraint prevented end-to-end security probes. Anything marked **UNVERIFIED locally** rests on the linked primary platform documentation, not an execution test here.

## Ranked mechanisms

Ranked by suitability as Snapback’s product policy—not simply by cryptographic strength.

| Rank | Precise mechanism | Shapes and attacker boundary | Adoption, restore, and failure cost | Safe degradation |
|---:|---|---|---|---|
| **1** | **Explicit security profiles: no local root by default.** Define `trusted-same-uid` and `externally-rooted`; this is a policy mechanism, not secret storage. | **M/L/S/CF.** The weak profile does **not** stop arbitrary same-UID native code, direct SQLite, file replacement, or a caller invoking legitimate tooling. It can claim only encapsulation against unsupported construction through Snapback APIs and registered connections. That is already the documented boundary: same-user processes and evasive native code are excluded ([LLP 0165:436](../llp/0165-proof-domains-and-checkpoints.spec.md:436), [LLP 0284:395](../llp/0284-workspace-security-gate-threat-model.spec.md:395)). | **Medium.** New persistent profile/readiness state, receipts and health output carrying the profile, tests preventing accidental weak-mode claims, and an explicit operator ceremony to enable a strong backend. Weak restores remain weak; strong restores/forks require re-enrollment. | **Safe only if explicit.** Never silently fall back from strong to weak. In strong mode, absence of the root rejects every root-derived mint/transition. An explicitly selected weak local profile may authorize normal development operations but emits no same-UID-resistance claim. |
| **2** | **Different security principal owning both database and root, with a closed broker API.** Linux: system `systemd` service with `User=`/`DynamicUser=`, `LoadCredentialEncrypted=`, private `0700` state, and optionally `SO_PEERSEC`/SELinux labels. macOS: root LaunchDaemon registered with `SMAppService.daemon(plistName:)`, communicating over XPC. | **Best for S; possible but ceremonious for M/L; not CF.** Moving the database under a dedicated service UID stops the ordinary developer UID. It does **not** stop code executing as the service UID. A daemon that exposes `sign(caller_message)` is only an oracle; it must reload the protected state and perform the complete closed ceremony. UID/PID credentials alone do not distinguish two same-UID processes; Linux `SO_PEERCRED` supplies only PID/UID/GID, while `SO_PEERSEC` can supply an SELinux label ([unix(7)](https://www.man7.org/linux/man-pages/man7/unix.7.html)). **Linux policy effectiveness is UNVERIFIED locally.** | **Very high.** Root/admin install, service user, system directories, IPC protocol/versioning, daemon upgrade/rollback, SELinux/AppArmor policy where used, operational logging, and migration from user-owned databases. A machine move or disaster restore must register a new custodian/root; a declared faithful relocation could preserve it only through a separate operator procedure. Apple requires administrator approval for LaunchDaemons ([Service Management](https://developer.apple.com/documentation/servicemanagement), [SMAppService registration](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29)). | Root-dependent transitions refuse if the broker is missing, unreachable, or cannot authenticate its peer. Root-independent reads may continue. Never fall back to direct local signing. |
| **3** | **Cloudflare-native object/service capability.** Use the `DurableObjectNamespace` binding and a fixed object identity, with claimant state in private Durable Object storage; prefer this over a plaintext Worker secret. | **CF only.** It stops external HTTP callers and the stripped handler Worker because bindings are injected by the platform and the current handler has only `HOST`, no storage/env/public route ([wrangler.handler.jsonc:1](../targets/cloudflare/wrangler.handler.jsonc:1)). The gateway currently possesses the `COORDINATOR` binding ([wrangler.jsonc:24](../targets/cloudflare/wrangler.jsonc:24)); the coordinator owns SQLite and handlers never receive storage or env ([coordinator.js:29](../targets/cloudflare/src/coordinator.js:29)). It does **not** stop malicious gateway/coordinator code, a deployer able to replace that code, or platform compromise. Same-UID is inapplicable. [Cloudflare bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/) and [Durable Object storage](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/) are **UNVERIFIED locally**. | **Medium for CF, nonportable.** Add durable claimant generation/store binding, define object clone/reset semantics, and ensure a copied app or new environment receives a new object/root. A Worker secret is easier but is readable by trusted Worker code; current coordinator code already reads secrets from `env` ([coordinator.js:2255](../targets/cloudflare/src/coordinator.js:2255), [Cloudflare secrets](https://developers.cloudflare.com/workers/configuration/secrets/)). | Missing binding should make deployment/startup fail. Missing claimant state disables root-derived authority. The existing admin surface already follows this pattern: no configured token means no admin surface ([coordinator.js:2248](../targets/cloudflare/src/coordinator.js:2248)). |
| **4** | **Code-signed macOS XPC helper plus Secure Enclave signing key.** Generate with `SecKeyCreateRandomKey`, `kSecAttrTokenIDSecureEnclave`, and `SecAccessControlCreateWithFlags(...privateKeyUsage...)`; require an exact peer signature with `xpc_connection_set_peer_code_signing_requirement`. | **M and macOS S only.** Apple silicon includes a Secure Enclave, matching Snapback’s arm64 Mac target. It can stop another same-UID unsigned or differently signed process from using the root, while the private key is nonextractable. It does **not** stop compromised authorized Snapback code, a confused-deputy operation exposed by that code, or a user deliberately approving an otherwise denied action. [Secure Enclave key protection](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave), [XPC peer-signature requirement](https://developer.apple.com/documentation/xpc/xpc_connection_set_peer_code_signing_requirement%28_%3A_%3A%29), and [Apple hardware availability](https://support.apple.com/guide/security/hardware-security-overview-secf020d1074/web). API availability is local; enforcement is **UNVERIFIED locally**. | **Very high.** Stable Developer ID signature/designated requirement, hardened release pipeline, helper bundle and installer, XPC protocol, a schema containing public key/root generation/store binding, and a closed—not raw-signing—operation. Local source builds and ad-hoc binaries cannot automatically inherit the production identity. Secure Enclave keys do not migrate; restore or machine move requires a new key and explicit re-anchoring. | Fail closed for authority creation if the helper, signature requirement, key, or user-presence policy is unavailable. No file-secret fallback in the strong profile. |
| **5** | **External KMS/HSM with isolated workload identity.** Example: asymmetric AWS KMS `SIGN_VERIFY` key via `Sign`, or PKCS#11 `C_Sign`; stronger variant decrypts a root only inside an attested Nitro Enclave and runs the closed ceremony there. | **Primarily S; technically callable from M/L/CF, but not a strong local answer when the same user owns the cloud credentials.** It stops offline database/keyring copying and callers lacking KMS/IAM authority. Plain KMS does **not** stop a same-UID caller who can reuse the process’s AWS credentials—it becomes a remote oracle. Measured-enclave attestation can distinguish the approved workload from the parent host. It does not stop the KMS administrator or compromised attested code. [AWS KMS Sign](https://docs.aws.amazon.com/kms/latest/APIReference/API_Sign.html), [Nitro attestation](https://docs.aws.amazon.com/enclaves/latest/user/set-up-attestation.html). **UNVERIFIED locally.** | **Very high.** External account/IAM lifecycle, network latency/outages/cost, key ID and public-key schema, anti-replay generation/nonces, audit logging, and explicit fork/restore semantics. A restored copy using the same KMS key is still the same logical instance unless an external registry assigns a new identity—the repository already records that complete authenticated copies are indistinguishable without such a root ([LLP 0293:840](../llp/0293-authority-transition-chokepoint.spec.md:840)). | KMS outage rejects root-derived operations; verification using the cached public key may continue. Never cache an exportable fallback root. |
| **6** | **macOS Keychain generic-password item with application ACL.** `SecItemAdd`/`SecItemCopyMatching`, `kSecAttrAccess`, `SecAccessCreate`, or operationally `security add-generic-password -T /path/to/signed/snapback`. | **M and macOS S only.** Unlike file permissions, Keychain ACLs can distinguish trusted applications from another same-UID application; an untrusted app is denied or prompts, and “Always Allow” adds it. It does not stop the already authorized binary, an attacker who tricks the user into approval, or extraction after the legitimate process has copied a symmetric root into its memory. Unsigned/user-replaceable dev binaries are a weak identity. `SecAccessCreate` is deprecated, another adoption risk. [Apple Keychain ACLs](https://developer.apple.com/documentation/security/access-control-lists), [SecAccessCreate](https://developer.apple.com/documentation/security/secaccesscreate%28_%3A_%3A_%3A%29). CLI presence is local; ACL enforcement is **UNVERIFIED locally**. | **High.** Signing identity, prompt behavior, headless-agent policy, account/service naming, rotation, and tested backup/sync accessibility. A migratable item preserves identity on machine move; a nonmigratable policy forces re-enrollment. Snapback’s earlier secrets design rejected Keychain as the default because Linux/CI/headless prompts and directory mobility suffer ([LLP 0036:330](../llp/0036-app-secrets-and-config.rfc.md:330)). | Keychain locked/missing/denied means no root-derived operations. An explicit weak profile may continue; automatic fallback may not. |
| **7** | **TPM 2.0 sealed or nonmigratable key.** `TPM2_Create`/`TPM2_Unseal` or TPM signing, with an `authPolicy` such as `TPM2_PolicyPCR`; practical Linux integration could use `systemd-creds encrypt` and `LoadCredentialEncrypted=`. | **L/S only when a real TPM2 and supporting service manager are present; not M or CF.** TPM prevents offline extraction and can bind use to machine/boot measurements. PCRs describe platform state, not which same-UID process requested the operation: another process with device/object authorization under the same PCR state can use it. `systemd` filesystem namespacing and a distinct service identity can close that gap, but that becomes mechanism 2. [Linux TPM subsystem](https://www.kernel.org/doc/html/latest/security/tpm/index.html), [`tpm2_createpolicy`](https://tpm2-tools.readthedocs.io/en/latest/man/tpm2_createpolicy.1/), [systemd credentials](https://systemd.io/CREDENTIALS/). Linux target availability is **UNVERIFIED**; this Mac exposes no TPM device. | **High.** Enrollment, ownership/auth policy, PCR selection, firmware/boot-update recovery, vTPM policy, hardware inventory, and emergency recovery. Moving to another machine normally loses the root; restore must re-enroll. PCR brittleness creates avoidable outages. | TPM missing, policy mismatch, or unseal failure rejects root-derived operations. Falling back to a software file destroys the claimed property. |
| **8** | **Linux desktop Secret Service or kernel keyrings.** `org.freedesktop.Secret.Service` methods such as `SearchItems`, `Unlock`, and `GetSecret` through libsecret; or `keyctl(KEYCTL_GET_PERSISTENT)`/persistent user keyrings. | **L desktop only reliably; poor fit for headless S; not M/CF.** The Secret Service specification does not mandate application access control and explicitly permits an unlocked item to become accessible to any client. Linux persistent/user keyrings are associated with the UID. These protect against other users, locked-session/offline access, and accidental exposure—not the required same-UID caller. [Secret Service specification](https://specifications.freedesktop.org/secret-service/latest-single/), [Linux keyrings](https://man7.org/linux/man-pages/man7/keyrings.7.html). **UNVERIFIED locally.** | **Medium/high.** Desktop D-Bus service dependency, unlock prompts, session availability, differing GNOME/KDE implementations, headless boot behavior, and uncertain migration. Implementation-specific app ACL extensions would require separate qualification. | Service absent or locked rejects strong operations. A promptless fallback is unsafe. |
| **9** | **POSIX file and directory permissions.** File `0600`, parent directory `0700`, `O_NOFOLLOW|O_EXCL`, owner/effective-UID checks, and advisory `flock`. | **M/L/S; not CF.** Stops other unprivileged UIDs and many pathname races. It categorically does **not** stop the same UID: `0600` grants that owner read/write, `0700` grants traversal, and on Linux the owner can change mode with `chmod`. [Linux ACL access algorithm](https://man7.org/linux/man-pages/man5/acl.5.html), [`chmod(2)`](https://man7.org/linux/man-pages/man2/chmod.2.html); OS enforcement was **UNVERIFIED locally** because no writes were allowed. Snapback currently stores base64 key material in `<db>.auth-keyring.json` ([keyring.rs:125](../crates/snapback-kernel/src/auth/keyring.rs:125), [keyring.rs:528](../crates/snapback-kernel/src/auth/keyring.rs:528)) and strictly validates owner-only files ([secure_file.rs:133](../crates/snapback-kernel/src/secure_file.rs:133)). The server takes a `flock` before opening ([cli.rs:8554](../crates/snapback-cli/src/cli.rs:8554), [instance_lock.rs:1208](../crates/snapback-kernel/src/instance_lock.rs:1208)), but a lower-level open reaches SQLite directly ([engine.rs:8021](../crates/snapback-engine/src/local/engine.rs:8021), [storage.rs:3488](../crates/snapback-kernel/src/storage.rs:3488)). | **Already adopted; low incremental cost, zero value for this threat.** Current backup deliberately copies exact keyring bytes into another `0600` file ([LLP 0057:1416](../llp/0057-auth-provider-protocol.spec.md:1416)); therefore backup/machine move carries the same root and cannot establish device identity. | Current missing-keyring behavior disables email-code issuance while existing session resolution remains available ([LLP 0057:708](../llp/0057-auth-provider-protocol.spec.md:708)). For a claimant root, that is too permissive: every operation deriving claimant authority must refuse, and startup must never silently mint a replacement. |
| **10** | **Derive from an existing ephemeral/platform identity rather than storing a secret.** Examples: current `ProcessBoundIdentity`, pointer/CSPRNG identity; Linux `SO_PEERCRED`; macOS code-signing identity; Cloudflare object/binding identity. | The macOS and CF variants can work only with mechanisms 3/4. `SO_PEERCRED` returns the same UID for attacker and legitimate process, so it fails. Process/pointer identity stops some cross-handle reuse during one lifetime but not restart; current storage creates a fresh process identity during every open ([storage.rs:3508](../crates/snapback-kernel/src/storage.rs:3508)). The stalled claimant lane found that a caller could mint a fresh valid identity and install it first rather than forge one ([claimant-root issue:23](../issues/20260826-step-up-claimant-root-requires-new-ceremony.md:23), [claimant-root issue:54](../issues/20260826-step-up-claimant-root-requires-new-ceremony.md:54)). | **Low implementation cost, but disqualified alone.** Persisting it makes it caller-readable; regenerating it loses continuity. Restart must either require external re-enrollment or recreate first-writer-wins. | Safe degradation is to refuse after restart until a real external ceremony rebinds the instance. Automatically minting a replacement authorizes the attacker and is not degradation—it is failure. |

## Recommendation

Adopt the explicit two-profile design in rank 1: keep ordinary local development under a deliberately named `trusted-same-uid` profile, require a deployment-provided root and fail-closed behavior for an `externally-rooted` profile, and implement that strong root independently per target—service isolation for native servers, signed XPC/Keychain or Secure Enclave where macOS operators choose it, and Durable Object/service capabilities on Cloudflare.

**Threat statement:** In `trusted-same-uid`, Snapback protects authority construction only through its supported APIs and Snapback-controlled connections and does not resist arbitrary code or processes running as the database-owning OS user with raw filesystem/SQLite access, while `externally-rooted` may claim same-UID resistance only when its deployment root is present and every root-derived operation fails closed without it.

## Strongest arguments against this recommendation

1. It deliberately leaves the most common local experience without the property that motivated F-1. Landing C could no longer make one universal “durable forgery cut” claim; every proof, receipt, guide page, and review would need to preserve the profile qualification, and an accidental production launch in `trusted-same-uid` would be a serious configuration hazard.

2. Multiple roots create a permanent semantic and operational matrix. macOS signing and prompts, Linux service/LSM policy, KMS outages, Cloudflare object lifecycle, and target-specific restore/fork ceremonies could diverge enough that maintaining one authorization protocol over them costs nearly as much as selecting and enforcing one strong service-hosted deployment model everywhere.
