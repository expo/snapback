# Authority-minting factory inventory

Date: 2026-08-24
Branch/commit surveyed: `lane/factory-inventory` at `8ded451f8f7949e5c508734f3aa39604f1f25dff` (`origin/main` at the start of the survey)
Deliverable posture: static inventory only; no production change is proposed here

## Result

The sealed `AuthDatabasePlan` protocol is not an authority boundary. Its seal
prevents downstream implementations, but several sanctioned factories capture a
caller-selected subject and a later public executor runs the closure against the
engine's private database. `AuthAdmission::record_authenticated_use_plan` is the
smallest verified instance. It is not unique.

This inventory uses the four requested classes exactly:

- **OWNERSHIP-CHECKED** — before the minted value can be honored, the factory's
  own validation path proves that the presented caller authority owns, authenticates,
  or is the exact opaque predecessor for the named subject. The row cites that check.
- **LIVENESS-ONLY** — the factory checks only process/admission/epoch/lease
  liveness and permits a caller-selected subject. A factory which performs **no
  caller-authority check at all** is placed here, marked `zero-check`; that is
  strictly weaker than the class name, but the requested taxonomy has no
  `NO-AUTHORITY-CHECK` class.
- **NO-SUBJECT** — the value names no caller-selected subject. This includes
  transformations whose subject is already fixed inside one opaque input and
  factories for global/process/database authority with no subject axis.
- **UNCLEAR** — the inspected code did not establish either ownership or a
  structural impossibility. The row states what would settle it.

“Opaque,” “sealed,” “private fields,” and “I found no current abusive caller” are
not ownership checks. Conversely, “the current caller passes matching values” is
not a structural block when the signature accepts the values separately.

## Boundary and search method

The positive inventory covers production Rust authority protocols in
`snapback-auth`, `snapback-sync`, `snapback-engine`, `snapback-kernel`,
`snapback-server`, and the authority-bearing portions of `snapback-services`,
`snapback-types`, and `snapback-activation`. “Production-reachable” includes
`pub`, `pub(crate)`, and private functions called by non-test code. It excludes
items gated by `cfg(test)` or `feature = "test-support"`, ordinary mutex/file
guards that protect only memory safety or singleton execution, read-only data
transfer objects, and declaration/configuration/query plans that no later
runtime authorization or commit path trusts.

The search was deliberately redundant:

1. Enumerate authority-shaped types (`Authority`, `Plan`, `Ticket`, `Handle`,
   `Witness`, `Permit`, `Lease`, `Guard`, `Reservation`, `Capsule`, `Carrier`,
   `Origin`, `Admission`, `Fence`, `Proof`, `Credential`, `Token`,
   `Invitation`, `Binding`, `Publication`, `Commit`, and `Participant`).
2. Enumerate functions whose return signatures contain those terms, including
   multiline signatures and `impl Trait`; this produced 1,317 syntactic
   candidates before semantic exclusions.
3. Independently enumerate factory-like names (`new`, `from_*`, `prepare_*`,
   `plan_*`, `mint_*`, `issue_*`, `admit*`, `bind*`, `reserve*`, `acquire*`,
   `resolve*`, `register*`, `begin*`, `claim*`, and `retain*`); this produced
   2,790 name candidates before semantic exclusions.
4. Enumerate `Default`, `From`, `Into`, and `TryFrom` implementations and every
   sealed trait. Follow each included value to at least one later consumer.
5. Read signatures and bodies at the cited revision. Doc comments were used
   only to locate intended protocols, never as proof of a classification.
6. Compare the result with
   `issues/20260824-uncorrelated-staging-entry-point-inventory.md` so staging
   carriers, asset tickets, stream origins, and terminal plans were not lost by
   an auth-only search.

The decisive question in each row is: **can a caller choose the subject named by
the newly minted value independently of the caller authority the factory checks?**
For a sealed closure, checks performed when the closure is executed are part of
the factory validation path; a mere lookup that the selected row is live is not
ownership.

## Completeness limits and disposition rules

This is an enumeration within the stated boundary, not a proof that the whole
repository has a closed authority mint. In particular, an omitted module family
listed at the end cannot be used to make a “closed” claim. Within the examined
families, I included zero-check factories, private production leaves, public
wrappers, conversions, `Default`, opaque splits/joins, and authority-transfer
accessors when they create another independently held value. I did not duplicate
every trivial forwarding accessor when it borrows rather than mints, and I did
not count a type declaration itself among function rows.

The largest false-negative risks are:

- macros or generated impls whose expanded signature is absent from source;
- a generic return such as `String`, tuple, closure, `Value`, or `Self` which is
  later treated as authority but has no authority-shaped type/name nearby;
- authority stored directly into state and honored later without being returned;
- feature-gated production combinations not active in the source configuration;
- transfer through `Clone`, serialization, or enum construction without an
  explicit named factory (partially exposed by C001–C014);
- JavaScript/TypeScript handler-side capabilities and non-Rust FFI surfaces.

“Not included” therefore means “outside the semantic boundary or in an
explicitly unexamined family,” never “proved safe.” The raw candidate files
described next are the audit trail for re-triage; a future change should diff
those files as well as this table.
