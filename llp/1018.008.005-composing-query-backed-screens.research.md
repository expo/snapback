## Problem

A builder can declare a conversation view with messages, a count, and a preview
in Quarry. Making that view paginated, predictive, and useful offline still
requires several client declarations that do not compose as one ordinary
screen resource. The application must connect query shape, row identity,
pending writes, page membership, and independent downloaded history.

Adding a count or preview can increase the work needed to keep already
downloaded messages visible. Adding pagination can require another rendering
path. These are routine changes to one screen, yet their integration demands
knowledge of multiple client mechanisms.

This document defines the problem and desired outcomes. It selects no API,
compiler inference, companion-query synthesis, or implementation sequence.
Charlie requested problem statements on 2026-09-11, with solution sub-LLPs to
follow. The source inspection baseline is `b47337b26`; no new application
benchmark was run for this document.

## Evidence and current strengths

- The [shared chat binding](../snapback2/packages/snapback2/templates/chat/shared/thread.ts)
  combines `defineItems`, semantic mutation targets, wrapper selectors, ordering,
  create membership, draft contents, and `withHistory`. Some of these are
  essential product choices; their presence alone does not prove redundancy.
- [ClientPages](../snapback2/packages/snapback2/src/client-pages.ts) accepts array
  results and flattens each page's `data`. Its constructor does not accept the
  item/history options used by the composite thread observation.
- The current [pagination guide](../snapback2/packages/snapback2/guide/pagination.md)
  and [history contract](./1018.006-declared-partial-custody.decision.md#2-the-published-record)
  already preserve certified continuation and separate history authority. The
  old blanket claim that a returned record cannot carry a cursor is obsolete.
- [LLP 1018.008.001](./1018.008.001-derived-query-presentation.rfc.md#implementation-selection-2026-09-10)
  implemented typed original-row identity selection. It deliberately retained
  wrapper selectors and explicit policy; generalized derivation was deferred
  after review because a useful net application deletion was not established.

Confidence is high in the API mismatch and current source shape. The amount of
application code that can safely disappear is unmeasured. In particular,
original-recipient history and live history available to a later joiner are
different product permissions, not equivalent spellings to collapse.

## Desired outcomes

1. A screen can combine a paginated collection, pending item actions, and
   downloaded history without maintaining parallel rendering/reconciliation
   systems for them.
2. Adding a scalar summary does not require the builder to rediscover how to
   preserve available messages. An unknown count remains unknown.
3. Loading older messages retains opaque continuation, stable item identity,
   and correct ordering through live inserts, edits, deletion, and prediction.
4. The same declared relationships serve React, Expo, and headless observations.
5. Total application responsibilities fall, counting root observers, shared
   bindings, selectors, fallback queries, and helper files as application work.

These are outcome criteria for a future proposal, not new blocking checks or
an assertion that every existing declaration can be inferred.

## Constraints and unresolved questions

The applicable contracts remain [LLP 1001 §3](./1001-query-engine.spec.md#3-read-and-write-states-no-silent-states),
[LLP 1018.006](./1018.006-declared-partial-custody.decision.md), and
[LLP 1012 §§5–7](./1012-local-first-v1.spec.md#5-retention-revocation-and-the-fence).
Missing authority cannot become a scalar value or continuation. A fallback's
receipt cannot certify the primary composite. A committed mutation is not
evidence that its image has reached a particular view. Account changes and
revocation remain authority boundaries.

Future solution work should answer:

- Which repeated relationships are mechanically known, and which express
  product intent? What does eliminating each one actually save?
- Can the existing pagination and item contracts compose without another
  public query model or independently maintained metadata graph?
- Which page owns a summary while live page boundaries move? What remains
  renderable when only some history is held?
- How do original recipients, later joiners, and revoked members differ?
- What are the runtime bytes, subscription, evaluation, and check-time costs?

The four-problem [parent](./1018.008-elegance-after-the-corrections.research.md#11-problem-statements-and-papercuts-2026-09-11)
