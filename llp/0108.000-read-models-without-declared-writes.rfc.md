## Commission status

This document commissions a design; it does not add an operation kind or
authorize implementation. Existing queries and mutation write declarations
remain normative. Under LLP 0317.000 P7, acceptance routes O13's read-model
sub-obligation but does not close it.

- **Design owner:** the LLP 0108 inline-handler/result-contract owner.
- **Implementation owner:** the codegen/runtime/client-retention maintainers
  named by the accepted design.
- **Publication owner:** the Snapback package-family release maintainer after

The author must replace those role descriptions with accountable named owners
before accepting this RFC.

## Summary

Decide whether analytical, multi-source server reads need a first-class
operation/result shape that declares no writes and consumes no durable client-
mutation retention record. The design must distinguish this need from the
scalar/document result contracts already available to ordinary queries.

## Motivation

The 0.1.29 scale lane authored Insights and Trending as mutations because the
needed analytical shape could not honestly satisfy the mutation contract's
non-empty write set. Those read-shaped mutations then consumed the global
durable client-mutation ledger and were refused when it saturated. Tuning that
ceiling would preserve the category error. LLP 0317 C5 asks whether a separate
read model removes the coupling by construction.

## Questions the design must settle

1. What concrete analytical shape is impossible or materially misleading as
   an existing query with `results.document(...)` or `results.value(...)`?
2. Is a new operation kind necessary, or can LLP 0108's query contract be
   extended without weakening bounded reads, authorization, or replay?
3. What read sets, bounds, result contracts, cache/live behavior, and
   authorization invalidation must be declared?
4. Must execution be side-effect-free and replay-free, and how is that proven
   across HostPlan and Ibex?
5. How do clients submit/subscribe without allocating a durable mutation ID or
   client-mutation ledger record?
6. What identical Explicit and Familiar authoring forms lower to the new
   normalized operation, if one exists?

## Required acceptance evidence

Before acceptance, the design must include an inventory proving why current
query result contracts do or do not suffice. If it proposes a new surface, it
must require executable witnesses for multi-table analytics, bounded result
validation, authorization/invalidation, live and one-shot use, offline
behavior, HostPlan/Ibex agreement, and Explicit/Familiar parity. A saturation
test must prove the operation neither allocates nor depends on a durable
client-mutation record, while an actual mutation remains refused at the same
ledger ceiling.

## Non-goals

- Raising or purging the mutation-retention ceiling.
- Allowing mutations with dishonest empty write declarations.
- Creating an unbounded arbitrary server action.
- Assuming a new primitive is needed before the existing query inventory is
  complete.

## Open questions

The necessity and exact shape of a new operation remain open. Review must
prefer an extension of existing query/result machinery if it meets the
acceptance witnesses without lying about writes.
