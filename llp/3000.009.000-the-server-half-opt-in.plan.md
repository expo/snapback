## Summary

LLP 3000.009's server half is partly shipped and partly planned.

- **Shipped:**
  - `action` declarations, with TypeScript handlers and durable steps;
  - `route` declarations, including webhooks;
  - schedules that name an action;
  - OIDC and trusted-profile helpers;
  - action-bound session minting;
  - a managed-organization and invitation recipe, built from ordinary tables
    and TypeScript.
- **Planned, and not current forms:**
  - application SQL reads, projections and database-owned tables;
  - production Postgres, which is an opt-in experiment and not a deployable
    target.

The shipped part sits on the same default surface as the local-first core, and
core cards carry its vocabulary.

This plan puts the existing server-half declarations behind one project-wide
directive, `use server`, following `use identity` and `use personas`. Without
the directive, three things change:

- `action` and `route` declarations, and schedules that name an action, refuse
  with a rewrite that adds the line;
- `guide` lists the core cards;
- the core cards teach the core.

The shared work machinery stays core, because effects already use it:
generated contexts, secrets, deadlines, durable steps and parked outcomes.
OIDC and managed-policy material moves to `SERVER.md` as documentation, not as
a gate. Planned capabilities will require the directive when they ship.

The plan keeps LLP 3000.010 §7's two constraints:

- service credentials stay on the core path;
- the capabilities stay integrated in one binary, one language and one release
  (LLP 3000.007 §3.4).

It leaves §14.7's post-Workroom retain/remove pass where it is.

This is a product change, not a score lever. The record holds one step that
happened while the guide grew (LLP 3000.010 §3), and one pre-registered
reduction that moved `setup_and_docs` (W14b). This plan predicts no score
effect either way.

## 1. The line

| Class | What | Without `use server` |
|---|---|---|
| **Gated declarations** | `action` declarations, including `returns` and their work settings; `route` declarations, including webhooks; schedules that name an action | Refused, with the directive as the rewrite |
| **Shared work capabilities** (core) | Generated `EffectContext`; declared secrets; retry, backoff, deadline and cancellation clauses; durable `ctx.step`; parked outcomes; declaration-contract checks; `snapback4/server`, through which generated effect handlers run; `snapback4/worker`'s effect claim and settle, `mintSession` and `revokeSessions` | Available, unchanged |
| **Core, unchanged** | Tables, rules, `sync`, retention, `expire at`, assets, search; maintains and LLP 3000.007.003's derived forms; queries, mutations, helpers, shapes, merges; `use identity` guests and passwords; personas; presence; jobs, chunks and schedules of jobs; `effect` and `emit`; service seats (`token --service`) | Available |
| **Documentation placement** (no gate) | OIDC helpers and trusted profiles; managed organizations and invitations; action-bound session minting | Documented in `SERVER.md`, not on core cards |
| **Future admission policy** | Application SQL reads, projections, database-owned tables; the Postgres store; channels, which the parser refuses today | Not current forms; when they ship, they require the directive |

So schedules and jobs stay core, and so do effects with every capability they
share with actions. Actions and routes move behind the gate, and a schedule that
names an action moves with them.

Native jobs (LLP 3000.005) and the witness verbs stay core (ruling 51).

## 2. Evidence

The evidence is LLP 3000.012 §2.6:

- **Diagnostic codes.** By prefix, 32 of 151 codes belong to families specific
  to the server half (`E_ACTION`, `E_ROUTE`, `E_OIDC`). `E_STEP` and
  `E_SERVER` are shared with effects, and `E_SQL` concerns the developer
  inspection verb.
- **Documents and cards.** `SERVER.md` is 46,564 B. The `actions` and `routes`
  cards total 25,397 B.
- **The core cards carry server-half forms.**
  - The language card's first sentence names routes, and its compiled program
    declares two actions and two routes.
  - The app card's opening paragraph lists actions.
  - The services card follows the service seats with action-bound minting and
    OIDC.
- **What calibration #16's builder did.** It opened the services and effects
  cards for its push seam, and made no authored import of `snapback4/worker`
  or `snapback4/server`.

The actions card also contradicts the effects card on `ctx.step`
([ticket](../issues/20260922-snapback4-actions-card-denies-effect-steps.md)).

## 3. The mechanism

- **The directive.**
  - `use server` is declared once in `schema.q` and applies to every module,
    as `use identity` does.
  - Without it, each gated declaration refuses with one code whose rewrite is
    the directive line, so a builder who needs an action is one step from it.
    The implementation chooses the code's spelling.
  - `why` explains every code whether or not the directive is present.
  - There is no `use identity oidc`. OIDC is TypeScript helpers and actions.
- **Generated output.**
  - Without the directive, `api.ts` carries no action or route types.
  - The generated `server.ts` and `snapback4/server` keep serving effect
    handlers either way.
- **The guide.** Bare `guide` lists the core cards, then one line naming the
  server cards and the directive. `guide actions` still answers.
- **The cards.**
  - The language and app cards list action and route forms only in a section
    headed by the directive.
  - The services card keeps service seats and application-minted sessions.
    Action-bound minting and OIDC move to `SERVER.md`.
  - The effects card keeps its full effect surface, including steps and
    parking, because that surface is core.
  - The actions card's stale sentence on effect steps is corrected.
- **The package.**
  - `snapback4/worker` and `snapback4/server` keep every export.
  - `worker`'s action types are documented under the server half.
  - The README's reference map keeps one row for the server half.
- **`init`.** The default, `--expo` and `--online` templates write no action or
  route. A template that needs one writes the directive.
- **The binary.** Unchanged. This plan adds no cargo feature and no second
  package (§6).

## 4. Relationship to §14.7 and Workroom

The two are orthogonal:

- Workroom's application adds the directive.
- Whatever the post-Workroom pass removes leaves from behind the gate.
- Whatever it retains stays there.

The gate needs no Workroom result and can land first.

## 6. Alternatives

| Alternative | Disposition |
|---|---|
| A separate npm package and a binary feature | A stronger boundary, with more publication machinery; revisit if the directive leaks |
| A documentation-only split | Leaves action and route declarations and their types reachable with no signal |
| Gating the shared work machinery too | Would remove capabilities effects need (LLP 3000.010 §7) |
| Removing the server half now | Would pre-empt §14.7; the author's call, not this plan's |
| A fence so builders "never learn it exists" | Withdrawn by LLP 3000.010 §7 |
| Leaving things as they are | Leaves LLP 3000.010 §8.4's question open |
