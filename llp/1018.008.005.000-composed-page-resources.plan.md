## Outcome and scope

Make a paginated conversation view use the same item binding and rendering
loop as its single-page form. A count/preview remains tied to the primary
query; independently authorized downloaded history can supply paginated items
when that query is partial. React, Expo, and headless consumers share the same
page-resource implementation.

This implements the [composition problem](./1018.008.005-composing-query-backed-screens.research.md).
The proposed implementer is Codex; planning date 2026-09-11, implementation start
2026-09-11 under the author's delegated post-panel commission. API spellings
below describe the selected implementation contract. Original source baseline was `b47337b26`; implementation baseline is `bf8450849`.

Use the existing `ClientPages`, `client.observe`, `Items`, and `ItemsWithHistory`
contracts. General companion-query synthesis, table inference, a client query
planner, and per-field partial values remain deferred. Explicit selectors,
product membership, draft contents, and recipient-history policy stay authored.

## Proposed public shape

Extend `usePage` with the item/history overloads already familiar from
`useQuery`; expose the same lazy resource as `client.observePages`. Keep the
existing array-without-items form returning raw rows. An explicit item binding
returns `QueryItem<Row, Draft>` values with exact inferred types.

Implemented use:

```tsx
const thread = usePage(api.messages.conversationView, { conversationId }, {
  items: conversationItems,
});
const summary = thread.head.data;
// Render thread.items; show summary only when this primary result is usable.
// thread.loadMore() follows the active source's certified continuation.
```

For the item form, expose `head` (the primary first-page snapshot), `items`,
`pages`, `itemsFrom`, `loadMore`, `hasMore`, `status`, and `reason`. `pages` holds
the active source's original per-page snapshots, typed with the source
discriminant. It is not a combined receipt. `itemsFrom` is `query`, `history`,
or `drafts`, as in the existing history vocabulary. No aggregate `seq` or
whole-collection completeness claim is introduced.

`head.data` supplies the count/preview only when the primary is usable. Pages
can have different execution sequences, as existing live pagination does;
the API must not imply one transaction across them. Do not infer a summary by
counting visible items or borrowing history's receipt.

## Page and history lifecycle

Use one page-chain implementation for primary and history sources. The primary
head remains observed while a history chain is active. Apply the existing
`composeHistory` eligibility law once at the resource boundary, rather than
attaching the same history fallback to every primary page.

| Primary head | Active collection | Continuation and lifetime |
| --- | --- | --- |
| Complete/capped with usable data | Primary query pages | Follow only primary `next`; release history |
| Partial and declared history is readable | History pages | Start from authored history arguments, then follow history `next` |
| Partial with unavailable history | Current-account drafts only | No fabricated cursor; retain truthful primary/history reasons |
| Loading, denial, refusal, or reset | Existing permitted draft/loading presentation | Release history and dependent pages as the current authority contract requires |

The raw head observation must not itself start another automatic history
chain. Share the existing lower-level observations and reuse the history
eligibility/composition functions, with an internal separation of the binding
from its fallback declaration. No new wire query is generated.

Keep the sources' cursor arguments and desired page counts separate. Resolve
each cursor name from its own operation metadata, including custom cursor
names and omitted/null normalization. The authored history mapping runs from
the primary base arguments; a primary cursor is never passed to history by
analogy. When a source becomes inactive, release its page subscriptions;
rebuilding it later uses its current root and valid returned cursors, not stale
tokens. A missing cursor on a partial is not exhaustion. On source handover, preserve
the requested depth as an integer, rebuild valid continuations for the new
source, and release the old source immediately. Temporary shorter visibility
is a loading state; keeping ineligible history rows for visual continuity
would change the authority contract.

Account, backend, operation, argument, and binding identity changes retire the
resource's old observations. Generation/coverage reset invalidates dependent
page chains. Late frames cannot republish an abandoned chain. Multiple handles
reuse the existing query-sharing layer; no new persisted page cache is needed.

The resource's `status` describes acquisition availability; it is distinct from
`head.status` and does not gate the permitted `items`. In draft-only mode it
retains primary and eligible-history loading/unavailable reasons, including a
pending history observation. Drafts still render during that acquisition.
This explicit interpretation resolves the late Grok status recommendation;
[the received review and disposition](./reviews/1018.008-four-implementations.grok-pages.md)
are retained without changing the source-selection law.

For an active chain, a refused/unavailable tail makes status `unavailable`;
otherwise any loading replacement makes it `loading`, while a usable prefix
remains renderable. A partial tail retains its reason and only its actually
returned cursor. `hasMore` means the active tail has a certified cursor, not
that the collection is complete when it is false. Refusal takes precedence
in the exposed reason; preserve the primary `head` and history-head reason
separately so missing authority is inspectable without app reconstruction.

## Ordering and pending work

The collection uses the source's certified scan order. For each active page,
consider selected row items in acquisition order and choose the first whole
item for each table/key. A materialized row always wins over a draft-only
candidate, including when the row occurs on a later page. Preserve every
chosen item's own pending actions, image, and observation evidence; never
union proofs or retire an action merely because its ID appears elsewhere.

`Items.order` is absent or `"reverse"`; it supplies no comparator or order key.
Undo the existing per-page presentation reversal before choosing the unique
scan sequence, then reverse that whole row sequence once for `"reverse"`.
Collect draft-only candidates across the entire valid loaded prefix, choose
one whole candidate per key in acquisition order, and exclude keys already
represented by a selected row. Emit them once in the existing durable FIFO
draft area, using the client-owned outbox ordering/alias index where needed.
A head's post-commit selection can exclude a create whose deeper page has not
yet observed it: restricting drafts to the head would drop that still-pending
work. Conversely a page-one draft cannot hide its page-three selected row.
Keep candidate evidence separate; an absent loaded-prefix row is not deletion.

Reuse the existing pure item projection. Factoring a single `attachItems`
pass is appropriate only if it preserves each selected image's original
observation and selection evidence; it must not require a synthetic combined
receipt. An absent row in the loaded prefix is neither proven absent from
the collection nor deleted.

When a parent's certified continuation changes, retire its dependent suffix
before publication and expose the valid prefix while replacements load.
An edit with unchanged continuation does not rebind unrelated pages. Accept
replacement frames only for the current lifecycle, source, and link identity.
Repeated loadMore while a replacement is loading does not multiply requests.
Pin three-page forward/reverse vectors, conflicting duplicate images, a create
materializing on page three, commit-before-observation, a changed boundary
with a late suffix frame, a head excluding a committed create while a valid
deeper page still carries it, and unrelated queued edits/removals. For concrete
reverse vectors, raw pages [9,8,7], [6,5,4], [3,2,1] render [1,2,3,4,5,6,7,8,9]
followed by distinct drafts. Per-page reversal plus head-first concatenation
would incorrectly produce [7,8,9,4,5,6,1,2,3].

## Implementation record (2026-09-11)

C1–C4 are implemented in the integration worktree. `ClientPages` owns a shared
`PageChain` algorithm for arrays, primary item pages, and independent history
pages. `ClientQueries.observePages` captures the existing identity fence and
uses its existing query-sharing owner. The public client and both React arms
delegate to that resource. Stable history-free primary declarations avoid
nested fallback subscriptions. Private item inputs follow each original item
snapshot so the shared outbox alias/order index can place drafts without a
second ledger or a combined receipt.

Projection/notification stays inside the same reentrant refresh loop: a
headless subscriber can call `loadMore` from a capped publication without
waiting for another frame. Pure getters cannot consume a listener's pending
notification. Cursor changes retire the old suffix before publication, and
metadata resolution cannot acquire a retired source.
The focused review's reentrant-loadMore correction is covered by the complete
page/history file: 20/20 pass after the final package rebuild.

### Full-script screen follow-up

The complete script exposed two additional fixture assumptions. The Expo
recovery witness expected raw transport text inline; it now checks the saved-work
advice, opens Details, and checks the original refusal before continuing recovery.
That native Thread control passes with its bubble and owner-removal assertions.

The cold React lost-response witness assumed settlement could count only its
two message sends. A held-response reproduction showed the exact third entry:
an ordinary queued `_delivery.deliveries.ack` earned by the first send's
independent live disclosure, while both sends stayed unchanged. The fixture now
settles initial acknowledgements, then holds the real commit response until
the accepted delivery event, sequence, and acknowledgement match that message.
It asserts exactly the two original send intents followed by that acknowledgement
and `remaining: 3`; no count or settlement semantics were relaxed. The full
transition file passes 6/6, preserving exact retry bytes, two pinned bubbles,
FIFO execution, one owner row per send, and eventual acknowledgement settlement.
The temporary timing probe was removed in favor of this evidence barrier.
This first follow-up changed two existing test files only (+29/−5 lines), with
no runtime change or new gate.

A later integrated screen run exposed the documented source-handover exception
to DOM continuity. The same resource and auth generation published a settled
row under a capped primary, then a partial primary with its newly reacquired
history still loading, then readable history. The middle publication correctly
hid the settled row: it had no current draft, the partial primary could not
authorize its image, and the previous history subscription had been released.

The exact baseline `useQuery` screen control reached a capped primary but did
not reproduce the later partial during that run; no baseline DOM failure is
claimed. Deterministic controls over both `observe` and `observePages` now pin
the same required redaction and restoration from the new history's own receipt.

lost-response witness retains its original node assertion through cold auth
