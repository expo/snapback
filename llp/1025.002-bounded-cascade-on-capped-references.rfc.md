## Commission disposition — 2026-09-12

The user delegated evaluation, refinement and implementation of worthwhile
changes in this family. This proposal is **not selected for implementation**.
The digest needs a conditional last-unread transition as well as deletion:
a cascade cannot remove `periodChats` only when its last contribution goes
away. It therefore would not eliminate the authored pairing that motivates
it. LLP 1025.000 will keep each capped cleanup in the same transaction as
the eligibility change.

Before reopening, supply a customer whose full invariant is expressible by
bounded deletion and settle the following design costs. A cap on
`(membershipId, periodStart)` does not bound all dependents of one membership;
the admission proof must use a cap on a subset of the lookup prefix.
Multiple cascade paths can reach the same row; pricing and deletion order
must cover overlaps, maintained values, delivered removals and rollback.
Local prediction must conservatively handle an unheld dependent population.
Changing cascade behavior changes the meaning of future deletes, even when
no stored rows need conversion; successor compatibility is not established
by calling that change additive. Depth two is not justified by this digest.

No implementer or delivery date is assigned while shelved. The design below
is retained for future evaluation and does not bind code. Its references to
a diagnostics registry are not an implementation request: Snapback 2 forbids
new registries (`rules/NOT-DOING.md`). Reuse its existing diagnostic families
and guide if the feature is commissioned later.

## Summary

Add one schema line, `cascade <reference columns>`, meaning: when the row a
listed column references is deleted, delete this row in the same
transaction. It is admitted only where the fan-out is bounded by an existing
`cap` or unique index on that column, it is executed as an engine write like
`_timers` maintenance, and it is priced on every program that deletes from
the referenced table. It turns "every writer that deletes a message or a
membership must also delete its custody rows" from a reviewed discipline
into a certified fact, and it lets `schedule … at .expiresAt: delete .`
clean custody with no target mutation.

## Motivation

Every eligibility hole the digest assessment found was an unpaired writer: a
purge that nulled `body` and `expiresAt` without touching `periodUnread`; an
admin removal that left an old-incarnation row. The guide's rule is "deny any
unpaired writer", which a reviewer enforces by reading every mutation. The
engine already maintains three things this way for the author (`_timers`,
maintains, `deliver` custody); the missing one is the existence of dependent
rows. Today a reference column is validated when written and nothing happens
when its target is deleted; the referencing row stays and reads through it
yield absence.

## Design

### D1 — Grammar

A table-level line, parallel to `immutable`:

```q
table periodUnread:
  messageId: messages
  membershipId: memberships
  …
  cap 50 by messageId
  cap 50 by recipient, conversationId, membershipId
  cascade messageId, membershipId
```

Each listed column must be a reference column (`col: table`);
`E_CASCADE_COLUMN` otherwise. The alternative spelling `messageId: messages
cascade` on the column is recorded as open question 1.

### D2 — Admission

For each cascade column `c` on table `T` referencing `P`:

- `T` has an index whose first column is `c`, so the engine can find the
  dependents by prefix (`E_CASCADE_INDEX`, rewrite: `by byC: c, id`).
- The dependents per `P` row are bounded: `cap N by c` on `T`, or a unique
  index on `c` alone (`N = 1`). Otherwise `E_CASCADE_UNBOUNDED`, rewrite
  `cap N by c` with the same wording LLP 1017.000 gives every cap: a data
  constraint, never a platform maximum.
- Chains are allowed to depth 2 (`P ← T ← U`); deeper refuses
  `E_CASCADE_DEPTH`; a cycle refuses `E_CASCADE_CYCLE`.

`cap 50 by recipient, conversationId, membershipId` does not bound
`membershipId` alone (a membership's rows span messages), so the fixture
adds `cap 50 by membershipId, periodStart` or, more simply, cascades only on
`messageId` and keeps the membership cleanup authored. The RFC does not
decide the fixture's choice; 1025.000 §3 does.

### D3 — Engine semantics

When any program deletes a `P` row (a mutation, a job chunk, a `delete .`
schedule target, a nested cascade), the engine deletes up to `N` `T` rows
through the prefix index inside the same transaction, taking the same paths
an authored `delete T[row]` takes: maintains update, `_timers` rows for `T`'s
scheduled columns cancel, `deliver` removal events append if `T` is
delivered, and `T`'s own cascades run. `T`'s delete rule is not consulted;
the cascade is an engine write certified as `engineWrites: [T]` on the
deleting program, exactly as `_timers` and `_outbox` are today.

### D4 — Pricing

Each delete of a `P` row is priced with `N` additional `T` deletes and their
per-row write cost (maintain updates, derived-index removal), transitively
to the depth bound. `write_rows` (ceiling 2,048) bounds the chain; a 50 × 50
depth-two chain refuses at `check` with the term named
`cascade T by c × N`, and the rewrite is a job. `check --cost` prints the
term on admitted and refused programs alike (LLP 1020 A4).

### D5 — Successors

Adding or removing a `cascade` line is additive: no stored row changes.
Pre-existing dependents of already-deleted parents are not swept; the
successor report counts nothing (that would be a scan) and pastes a purge
job whose chunk deletes `T` rows whose parent read is absent. Dropping `P`
in a destructive plan lists `T`'s cascade as a consequence.

### D6 — Diagnostics

`E_CASCADE_COLUMN`, `E_CASCADE_INDEX`, `E_CASCADE_UNBOUNDED`,
`E_CASCADE_DEPTH`, `E_CASCADE_CYCLE`, each with a site and a rewrite, added
to the registry with `check-inventories` run.

## What it changes for the digest

- `schedule expireMessage on messages at .expiresAt: delete .` removes the
  message's ≤ 50 custody rows with no authored target.
- Unsend is `delete messages[id]` under the tombstone contract
  (LLP 1018.007.004 "Final message custody correction"), and custody follows.
- Membership removal cascades rows keyed by `membershipId` when the fixture
  chooses to bound that column.
- The `periodChats` "last row" transition (delete the chat row when the
  chat's pending count reaches zero) is conditional and stays authored; a
  cascade cannot express it. If `unreadChats` is dropped (1025.000 open
  question 1), nothing authored remains.

## Acceptance

1. Engine tests: parent delete removes dependents, updates maintains,
   cancels their timers, appends their delivery removals; the cap bounds the
   count; depth and cycle refusals; a `delete .` schedule target cascades.
2. Certificate tests: the cascade term appears on every deleting program;
   `write_rows` refusal at the depth-two 50 × 50 case with the job rewrite.
3. Successor tests: additive add/remove; the pasted purge job compiles.
4. Fixture: `quarry-schedules` with cascade replacing the authored unsend
   and expiry loops; the 1025.000 witnesses for unsend and expiry pass
   unchanged.
5. Rust/TypeScript parity for the twin's local prediction of a cascading
   delete (the client predicts the dependent rows' absence, or marks them
   `partial`); LLP 1012's prediction rules decide which.

## Non-claims

No `on update` cascade, no set-null, no cross-generation or cross-store
semantics, no garbage collection of pre-existing orphans, no change to
`deliver` (which stays engine-derived custody with its own words), no
relaxation of `write_rows`.

## Open questions

1. Table-level `cascade a, b` (parallel to `immutable`) versus column-level
   `a: table cascade`.
2. Depth 2 versus 1. Depth 1 covers every case in the digest and the chat
   template; 2 covers a poll's options under a message.
3. Whether the twin predicts cascaded absence locally or reports `partial`
   until the owner answers.
4. Whether `deliver`'s custody should be documented as a built-in cascade so
   the guide teaches one idea.
