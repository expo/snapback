# LLP 3000.038: File assets — documents beside images and videos

**Type:** RFC
**Status:** Implemented
**Systems:** Snapback 4 language (`snapback4-lang`: the `file` type, its allow-list, the TypeScript emitter, the guide), core (`snapback4-core`: the asset ledger, verification, placement), the HTTP host (`crates/snapback4`: `POST /assets`, `GET /assets/<id>`), the device (`snapback4-device`: upload facts and retained media), the TypeScript client (`packages/snapback4`: `upload`, `asset`, `useAsset`, `saveAsset`)
**Author:** Claude Opus 5.5 (for Charlie Cheever)
**Date:** 2026-10-12
**Revised:** 2026-10-16 (§11: SURF3 shared immutable evidence and fail-closed scanning); 2026-10-12 (implemented as written on branch `sb4-ws-file`; one addition: a `file` argument given an image upload, or the reverse, refuses E_ASSET_TYPE before the program runs, and the device declines to predict it); 2026-10-12 (draft, accepted by the author as briefed: a `file` type with a MIME allow-list, a size bound, image rules and lifetime, no transcoding)
**Related:** [LLP 3000](./3000-snapback4.explainer.md) §7 ("one asset, one home"; "assets are staged, bounded and viewer-private"), [LLP 1006](./1006-assets.rfc.md) §13a (the deferred `file` design this lands), §5 (column-less upload), [LLP 3000.019](./3000.019-what-the-builder-still-wrote.rfc.md) §3.5 (retained media follows its download receipt), [LLP 3000.033](./3000.033-read-only-client-mode.rfc.md), [LLP 3000.037](./3000.037-app-farm-new-project-friction.research.md) (the app farm)

## Summary

App-farm builders of receipts, contracts, sheet music, data rooms and lab
results needed PDFs and other documents and were refused: Snapback 4 took
JPEG, PNG, WebP and MP4 and nothing else. This RFC adds a third asset kind,
`file`, landing LLP 1006 §13a with one change the author approved: a column
may narrow the accepted media types with an allow-list. Everything an image
already means — one asset, one home, serving by the home row's read rule,
release on delete/clear/expiry, the unclaimed sweep, `private, no-store` —
holds for a file unchanged. Snapback never transcodes, renders or strips a
file; it verifies that the bytes are what the uploader declared and serves
them as a download.

## 1. The type

```quarry
table receipts:
  owner: principal
  scan: file <=10000000 ('application/pdf', 'image/jpeg', 'image/png')
  notes: file <=2000000 ?                  -- the default allow-list
  read <- .owner = viewer
  insert <- .owner = viewer
```

- `file <=N` takes the default allow-list; `file <=N ('type', ...)` narrows
  it. Each listed type must be one Snapback can verify (§2); anything else is
  a compile error naming the verifiable types. HTML, SVG, XML, JavaScript and
  other script-bearing types are never verifiable: the error says to upload
  them as `text/plain` or inside a `zip`.
- The word `file` is a type only before `<=`; a table named `file` still
  works as a reference type.
- `once` is refused on a file column: a download is saved by the browser,
  so "one view, never cached" would be a promise the platform cannot keep.
- The value a row carries is `{ id, type, bytes, name }`. `type` is the
  verified media type, `bytes` the stored size, `name` the sanitized
  filename (§4). These are the server's facts; a client-supplied fact is
  replaced at placement, exactly as for images. In Quarry `doc.name` is
  `text <=255`, `doc.type` text, `doc.bytes` int.
- Lists and optionals work as for images: `[file <=10000000] <=8`.
- Mutation and action arguments take `file <=N (...)` the same way; the
  argument carries the server's facts inside the mutation.

## 2. Verifiable types and verification

The default allow-list is the whole verifiable set:

| Type | Verified by |
|---|---|
| `application/pdf` | starts with `%PDF-` |
| `text/plain`, `text/csv`, `text/markdown` | valid UTF-8 (BOM allowed), no NUL byte |
| `application/json` | valid UTF-8 that parses as JSON |
| `image/png`, `image/jpeg`, `image/webp` | the image sniffer's header (no pixel bounds: nothing decodes it) |
| `image/gif` | `GIF87a` / `GIF89a` |
| `application/zip` | `PK\x03\x04` or the empty-archive `PK\x05\x06` |
| `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `…spreadsheetml.sheet`, `…presentationml.presentation` | the zip header |

**Declared plus sniffed.** The upload declares a type (its `Content-Type`,
parameters dropped, lowercased). The type must be verifiable and the bytes
must pass that type's check; a mismatch is `E_ASSET_TYPE` naming both. A
spoofed `application/pdf` without `%PDF-` is refused; an HTML page declared
`application/pdf` is refused. When the declaration is absent or
`application/octet-stream`, the server names the type from magic numbers
for the binary types (PDF, PNG, JPEG, WebP, GIF, zip); text types must be
declared. Text verification is deliberately loose about content: an HTML
document declared `text/plain` is accepted *as text/plain* and is served
as such (§5), never as HTML.

The magic-number check is a type check, not a safety scan: a PDF with
JavaScript, a zip with an executable and a DOCX with macros pass. They are
downloads, never rendered by Snapback's origin. Metadata is stored byte
for byte; a file carries no privacy claim (LLP 1006 §13a).

## 3. Upload

`POST /assets?as=file&name=<filename>` with `Content-Type: <type>` and the
bytes as the body. Without `as=file` the route is the media upload,
unchanged. The upload stays column-less (LLP 1006 §5 and §12): placement
checks the column, as for images.

- **Admission.** The declared (or named) type must be accepted by at least
  one file column of the current schema; otherwise `E_ASSET_TYPE` says
  which column types exist. Size: the largest file column bound that
  accepts this type, refused with `E_ASSET_TOO_LARGE`.
- **Streaming bound.** For `as=file` the host computes the largest file
  bound in the schema *before reading the body* and reads at most that
  many bytes plus one (a declared `Content-Length` over it is refused
  before reading, 413). The media path keeps the 64 MiB ceiling.
- **Placement** (the mutation) checks kind `file`, the column's
  allow-list, and its bound: `E_ASSET_TYPE` / `E_ASSET_TOO_LARGE`. An
  image upload cannot be placed in a file column and vice versa: a JPEG
  meant as an attachment is uploaded with `as=file` (LLP 1006 §12's one
  record per column).
- The reply is `{ asset: { id, type, bytes, name, width: null, height:
  null, duration: null } }`.

## 4. The filename

The one client-supplied fact. The `name` query parameter (percent-encoded
UTF-8) is sanitized once at upload and stored on the ledger (`_assets.name`,
added in place to older stores):

1. keep the last segment after any `/` or `\`;
2. drop control characters (C0, DEL, C1) and bidirectional overrides and
   isolates (U+202A–U+202E, U+2066–U+2069), which disguise extensions;
3. trim surrounding whitespace and leading dots (no hidden files, no `..`);
4. truncate to 255 bytes on a character boundary;
5. if nothing is left, `file`.

The name never decides the type and never reaches a filesystem path:
stored bytes live under the asset id.

## 5. Download

`GET /assets/<id>` authorizes exactly as for images. A file is served with:

- `Content-Type: <verified type>` (`; charset=utf-8` for text types);
- `Content-Disposition: attachment; filename="<ASCII fallback>";
  filename*=UTF-8''<percent-encoded name>` — the fallback replaces
  non-ASCII, quotes, backslashes and separators with `_`;
- `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`;
- `Content-Security-Policy: default-src 'none'; sandbox` so that even a
  browser told to navigate to the URL renders nothing active;
- `Accept-Ranges: bytes`; ranges work as for ordinary images (resumable
  downloads and PDF viewers), 416 when unsatisfiable;
- `Content-Disposition` is in `Access-Control-Expose-Headers`.

There is no stored-XSS path: no verifiable type is script-bearing, text is
always `text/*` with a charset, every file response is an attachment under
`nosniff` and a sandboxing CSP. Images and videos keep inline delivery.

## 6. Lifetime, rules, view-once

Identical to images (LLP 3000 §7): uploader-only until placed, claimed
once, served by the home row's read rule on the row as it stands, released
by delete/clear/expiry/list removal, swept with unclaimed uploads after an
hour, generation-checked commit, two concurrent uploads, disk writes
outside the engine mutex. Read-only sessions download files (no view is
consumed). `once` does not apply (§1).

## 7. Clients

- `client.upload(bytes, { file: { type?, name? } })` uploads with
  `as=file`; a `File`/`Blob` supplies its own `type`/`name` when omitted.
  Without the option, `upload` is the media upload. The reply's `asset`
  carries `name`.
- `client.asset(id)` returns `{ url, type, bytes, name, revoke }`; `name`
  comes from the `Content-Disposition` header. `useAsset(id)` exposes
  `name` when ready.
- `saveAsset(client, id, name?)` (`snapback4/client`) fetches under the
  viewer's credentials and saves through a temporary download link, then
  revokes it: documents download on demand rather than on render.
- The local client keeps upload facts for prediction and retains viewed
  files under `assets: { keep: "viewed" }` like ordinary images, with the
  filename on the retained home.
- Generated types: a `file` column is `{ id: string; type?: string; bytes?:
  number; name?: string | null }`.
- Expo: `upload` and `asset` work with React Native Blobs; a native file
  picker and a "save to Files" helper are deferred to the Expo package.

## 8. Testing support

Fixture rows load file cells as the system: `{"scan": {"id": "r1", "type":
"application/pdf", "bytes": 1234, "name": "r.pdf"}}`. Like an image fixture,
such a cell has no bytes behind it (the download answers 404); an
acceptance script that needs real bytes uploads them (`POST
/assets?as=file`) and places the returned id with a mutation.

## 10. Not in this change

Transcoding, previews or thumbnails; per-column upload routing; content
scanning; HEIC; audio types; inline rendering of any file.

## 11. Shared immutable evidence and fail-closed scanning (SURF3)

The chosen composition for snapshots, approvals and evidence is a shared
immutable **home row**, with ordinary nominal row references from consumers.
This uses the existing engine semantics; it adds neither multiple asset homes
nor a clone endpoint. The home keeps the file/image column immutable, along
with the fields identifying its owner and content. Business snapshots copy
business fields separately. Copying an asset value into another media column
continues to refuse E_ASSET_PLACED. An independently authorized copy with its
own lifetime is an ordinary authorized download followed by a fresh upload.

Every byte read remains authorized by the original home's current read rule;
reading a referencing row never grants bytes. Removing a reference leaves the
home intact. Deleting/expiring the home removes access through every reference.
The recipe explicitly declares `on delete keep`: these references are not
retention roots or independent lifetime captures. The ordinary default
`restrict` refuses deletion while live references remain; `cascade` deletes
them. Authors
must retain the home for the longest needed retention period and deliberately
align its audience with consumers. Shared evidence excludes view-once assets.

`guide assets` executes a concrete recipe: immutable document/owner, pending
by default, scanner-only status update, shared access only after a clean
verdict; snapshots contain an evidence-row reference. The scanner seat reads
the immutable stored bytes and sends those exact bytes through an application
adapter. Only an explicit clean verdict bound to their SHA-256 may call the
approval mutation. Infected content, scanner errors, timeout, HTTP errors,
invalid JSON, missing/mismatched digest and unknown verdict all leave the home
pending. The scanner is trusted configuration and its transport/authentication
are the application's responsibility. Snapback's type verifier is not a
malware scanner. A handler completes the effect only after a sent approval;
redelivery can scan and approve the same immutable bytes again.

Verification: `snapback4-core/tests/file_assets.rs` executes the published
schema, proves pending outsiders cannot fetch, forged scanner approval fails,
two consumers can reference the approved home, reference deletion preserves
bytes, second placement refuses, and home deletion revokes every consumer.
`asset-scan-recipe.test.mjs` executes the published adapter for the clean,
infected, unknown, unavailable, malformed and wrong-digest cases.
