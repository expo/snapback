## Summary

[LLP 0329.008](./0329.008-coterie-plan-expressibility.research.md) classified
`coterie`'s 25 mutations statically and named the remaining gap: *"the 25 plans were
not authored and run through codegen."* This document runs that experiment on the
first mutation and reports two results — one confirming, one new.

1. **Confirming.** `coterie`'s `editProfile`, translated to a declarative plan with
   its uniqueness check removed, **compiles** (`generate()` → `ok: true`). The
   ownership guard, the point `get`, and the `patch` are all expressible. The
   non-key read is the sole reason that mutation is a JS handler, as
   LLP 0329.006 F4 predicted.
2. **New.** The natural workaround for the missing read — passing a non-id field to
   `get()` — **also compiles**, silently. Filed as
   `issues/20260828-plan-get-accepts-untyped-id-expression.md`.

## Method

`generate(backendDir)` from `packages/snapback-codegen/index.mjs` was run against a
scratch backend at `/tmp/plan-exp` containing a `profiles` table (`by_owner`,
`by_handle`) and one authored mutation. Workspace dependencies had to be installed
first (`bun install`) — the checkout had none linked after the 2,373-commit
fast-forward, so `@expo/snapback-client` was unresolvable and codegen could not run
at all. Verified against `main` at `d23666d12`.

## Findings

### G1 — The expressible portion compiles

```js
export const editProfile = defineMutation({
  args: { profileId: v.id('profiles'), displayName: v.string(), bio: v.string() },
  plan: [
    get('profiles', arg('profileId'), 'profile', { elseError: 'PROFILE_NOT_OWNED' }),
    guard(eqv(field(bindingRef('profile'), 'ownerId'), authUserId()), 'PROFILE_NOT_OWNED'),
    patch('profiles', arg('profileId'), { displayName: arg('displayName'), bio: arg('bio') }),
  ],
  refusals: ['PROFILE_NOT_OWNED'],
  result: results.value(v.object({ profileId: v.string() })),
  returns: returnExpr(record({ profileId: arg('profileId') })),
});
```

`ok: true`. This upgrades LLP 0329.008's rung-A classification for `editProfile`
from static inference to demonstration: everything except
`requireAvailableIdentity`'s `by_handle` lookup is plan-expressible today.

It does not upgrade the other 24. Rungs B, C, and D remain unproven in both
directions, because the steps they need do not exist to be tried.

### G2 — The natural workaround compiles silently wrong

`get` is declared `get(table: string, id: ValueExpr, bindAs: string, opts?)`
(`define.d.ts:313`). Nothing relates `id`'s type to the table's document-id domain.

An author needing the missing lookup reaches for `get` with the field they have:

```js
args: { profileId: v.id('profiles'), handle: v.string(), … },
plan: [ …, get('profiles', arg('handle'), 'byHandle'), … ]
```

`ok: true`, and the artifact carries it:

```json
{"Get":{"bind_as":"byHandle","else_error":null,"id":{"Arg":"handle"},"table":"profiles"}}
```

At runtime it seeks a `profiles` row whose `_id` equals a handle string, binds
`null` for every input, and any guard built on it never fires. The step also
propagates into the optimistic-prediction metadata:

```json
{"binding":"byHandle","idArg":"handle","kind":"point","requiredFields":["_id"],"table":"profiles"}
```

The first attempt at this test was unfair — it typed `profileId` as `v.string()`, so
there was no type distinction to detect. Retyping it to `v.id('profiles')` while
leaving `handle` as `v.string()` produced the same `ok: true`.

**Why this matters.** The case for declarative plans over handlers is that plans are
*checkable*. Here a check the schema plainly supports is not performed at the point
in the loop where an agent would see it — and it sits precisely where an agent lands
when working around LLP 0329.006's missing step. The missing capability and the
silent failure compound: the agent is pushed toward a workaround the toolchain then
fails to reject.

### G3 — Codegen could not run on the checkout as found

Worth recording because it is the same class of finding as LLP 0310's dev-loop
cluster. After the fast-forward, no workspace package was linked; `generate()` failed
at import with `Cannot find package '@expo/snapback-client'`. A `bun install` fixed
it in under a second. Nothing surfaced this until a tool tried to run — the failure
appears as a module-resolution stack trace rather than a diagnostic naming the
repair.

## Consequences

1. LLP 0329.008's method is sound where it can be tested, and its rung-A verdict for
   `editProfile` is now demonstrated rather than inferred.
2. LLP 0329.006's F4 causal chain has its first end-to-end confirmation on a real
   mutation: remove the non-key read and the plan compiles; the rest of the handler
   was never the obstacle.
3. A new defect exists independent of the rebuild question, and it makes the missing
   step worse rather than merely absent.

## Confidence

High on G1 and G2 — both are executed results with the emitted artifact quoted, and
G2 was re-run after correcting an unfair first attempt.

G2's scope is bounded: established that **codegen accepts and emits it**; not
established whether activation or the runtime refuses it later. Even so, the agent's
fast loop does not catch it, which is what LLP 0010's feedback-loop philosophy is
about.

Low on generalizing G1 to the other 24 mutations. One mutation was translated. The
honest statement is that the method works and the first case confirms the prediction.

## Open questions

1. Translate the remaining rung-A mutations (8 more) — they need no new step, so they
   are testable today, unlike B/C/D.
2. Does server activation refuse the G2 plan? If it does, the defect is a
   feedback-latency problem; if it does not, it is a correctness problem.
3. Should `get`'s id expression be typed against the table's id domain, as
   `bounded-children.v1` already requires for its child foreign key (LLP 0110 §1.1)?
