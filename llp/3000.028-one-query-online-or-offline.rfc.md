## 1. Decision

Let an application declare a read once. The platform should select an
authorized server plan for complete online coverage and a device plan for
offline coverage. A device page may be incomplete; an unknown Boolean must
not become false. Neither condition should require a second query body or
an application branch on network state.

Calibration #24 scored queries/live and client integration 85, data modeling
87, against 95. Its builder wrote `historyHeld` beside `history`, selected
`searchHeld` versus `searchNewest` and `searchInHeld` versus `searchIn`,
and invented public interaction-key aggregates to prove offline absence.
It also had to learn that aggregate residency and readability are independent,
and that a helper's query callers
inherit stricter bounds than its job callers.

This RFC accepts three design changes:

1. Keep ordinary retained history as the supported contract, with the exact
   calibration program in its regression and integrated guide example.
   Give the proved leading equality equivalent prefix coverage with an
   explicitly selected index. The later UI failure does **not** reproduce
   with the bracket body after a completed leave sync; this is not evidence
   for replacing that working routing mechanism.
2. Give the ordinary bare all-chat search an inferred server audience plan
   and a device plan that includes authorized retained images. Define bounded
   composition for a mixture of live and departed chats inside the platform,
   and use one unguarded pinned body for per-chat search.
3. Add an explicit owner-key coverage policy on a windowed source. The
   platform maintains a horizon-free, viewer-partitioned key projection;
   the application keeps its ordinary `exists` expression. Make this the
   social recipe's default, rather than silently expanding every existing
   windowed table.

Improve the two diagnostics at their failing source sites, and show all of
this in one compiled social-app example with exercised React/Expo witnesses.
This accepts the design; this round authorizes document changes only, with
no product implementation, ceiling increase or publication. The experiment
contains no replacement query engine.

The scope addresses query selection and offline coverage. Transient media
ownership, online typing and route/composer lifetime remain client work;
these proposals do not eliminate those client-integration charges. §8 requires
recipes and exercised witnesses for them. A fresh builder/scorer run is needed
before claiming the target score of 95.

### 2.1 Former member: the server loses authority, the device keeps history

The earlier `run-log.md:55` incident is a concrete coverage-spelling failure,
distinct from the later line-91 UI symptom. With the explicitly selected
`byHistory` index, `messages where .conversation = conversation last 20 by
byHistory` kept the equality as a residual filter and selected `byHistory ()`.
The bracket form selected `byHistory (conversation = conversation)`, pinning
the audience group and its horizon/retained coverage. The saved
`evidence/m3-history-why.txt` and `evidence/m3-history-why-2.txt` show these
different plans; the run log records server fallback and lost retained local
rendering before the bracket correction. The current planner's
`bind/intent.rs::read` returns before intent normalization when an index is
already selected. The guide's `where` form with inferred `by .at` does not
take that path. P19's runtime experiment used the corrected bracket body;
it did not rerun the earlier `where` body. §3.2 requires equivalent coverage
for this narrowly proved equality case.

The final builder already has the P12 form:

```quarry
query history(conversation: conversations, c: cursor ?):
  return messages[conversation = conversation] last 20 by byHistory after c
```

`messages` retains delivered history, syncs to `members[.conversation]`,
and acquires its last 500 on the same `byHistory` index. `conversations`
also retains history. There is no membership `require`, join, profile,
receipt or other decoration in this body. `historyHeld` differs only in
its header. Thus P12's old explanation about a guarded or decorated history
does not diagnose this final program.

After the reader acquires one message and its leave tombstone, **both arms**
observe:

| Read | Result |
| --- | --- |
| Online-only `history` | `data: []`, `complete: true`; no currently readable rows |
| Online-only `progress` | `NOT_MEMBER` from its explicit required member lookup |
| Local ordinary `history`, online | The retained row; `complete: true`; no server request |
| Local `historyHeld`, online | The same retained row; no server request |
| Either history, offline | The same row, `fresh: false`; no post-leave message |
| Ordinary history after rejoin and sync | Both messages via server fallback from the rejoined range |

The raw departed device answer has `retained: true, unknown: false`.
`device/history.rs` persists the `Left` group; `device.rs::query_observation`
propagates retained-only coverage. `local-query.ts` asks the server for
unknown coverage **unless retained**, and keeps this page. The server does
not reject the bare query: it returns an authorized empty page. It refuses
the guarded progress operation. Keeping those outcomes distinct matters.

The later historical record is real but weaker than a routing diagnosis.
`run-log.md:91` calls the cause ambiguous and records the switch after a
transient retained-history count failure. `m4-m3-regression-5.log:2` says

route-unmount investigations before the held workaround.

**Why it wrote the branch:** `src/receipts.ts` treats a `NOT_MEMBER` progress
answer as archived, then selects `historyHeld`. That excludes a possible
server fallback while the screen settles. It was an understandable defensive
response to an unresolved UI symptom, but neither the retained artifacts nor
P19 establish that this corrected bracket query incorrectly replaced these
retained rows in that later incident.
P19 does not claim to have reproduced that historical UI failure. Capturing
the failing observation/interleaving remains necessary before diagnosing it.

### 2.2 All-chat and per-chat search: deleting `held` is insufficient

The final builder has two different predicates, not just two headers:

```quarry
query searchHeld(q: text <=100, c: cursor ?) held:
  return messages matching q where not .tombstone last 20 by .at after c
query searchNewest(q: text <=100, c: cursor ?):
  return messages matching q where exists members[.conversation, viewer] and not .tombstone last 20 by .at after c
```

`src/Search.tsx` selects between them using `useLink`, and remounts its
results by link state. The search card itself instructs this split: held for
device holdings; grouped/newest online for full history. That is the guidance
the builder followed at `run-log.md:100`.

On `u0500`, `q: 'coffee'`, **both runtimes** produce:

| Operation | Server | Local online | Local offline |
| --- | --- | --- | --- |
| `searchNewest` | 20 hits, complete | Same via fallback | 20 held hits, incomplete |
| `searchHeld` | `E_QUERY_HELD` | 20 held hits, incomplete, no request | 20 held hits, incomplete |
| Bare held body made ordinary | Empty, incomplete | Server replaces 20 device hits with empty, incomplete | 20 held hits, incomplete |

The explicit membership form already answers both modes for **current**
chats. Its server meter is examined 141, index entries 141, probes 140,
heap 433,439 B, output 8,251 B, steps 1,619. The unscoped ordinary form
returns an empty incomplete answer with logical examined 1, index entries
33, probes 55, heap 36 B, output 12 B, steps 19. These latter counters
do not measure all hidden authorization work. LLP 3000.024 §2 describes
the hidden-prefix exhaustion in this corpus; the observable result and
current plan inspection agree with that explanation. P19 did not add an
internal physical-counter instrument.

There is a second difference. On the departed reader, searching the unique
retained token gives `searchNewest: []` with `complete: true`: the explicitly
required current membership no longer exists. Held search finds the retained
message with `complete: false`. The bare ordinary body also finds it offline,
but its unscoped coverage is unknown. Explicit application predicates cannot
be erased just because they exclude retained data.

**Why it wrote two bodies:** the author must currently supply the server's
audience-discovery predicate; that predicate changes which retained rows
the device can return. Removing only `held` exposes the unscoped server
plan, and using only `searchNewest` drops former chats. A full first page
offline is still incomplete when the horizon cannot prove the global word
order; twenty hits alone are not evidence of coverage.

There is also a second network-selected pair at `src/Search.tsx:10` for
“This chat.” The final program's `searchIn` (`builder.q:428`) has
`require exists members[conversation, viewer] else NOT_MEMBER` before
`messages[conversation = conversation] matching q where not .tombstone`.
`searchInHeld` has the same pinned page without that `require`. A former
member's retained match can therefore be available through the held body
offline while the ordinary guarded body refuses `NOT_MEMBER` online.
This follows from the supplied bodies and selector; P19 did not run this
pair in its experiment. Replacing only the all-chat pair leaves this branch
and mode-dependent meaning intact. §3.3 proposes an explicitly authored
unguarded per-chat body; it does not remove guards from existing queries.

### 2.3 “Did I like this post?”: acquired does not prove an absent key

The original relations have public windows of 2,000 likes and 1,000 reposts
by time. A unique `(post, principal)` or `(actor, post)` miss cannot prove
absence from those windows. The missing row might be older. Uniqueness
proves at most one row, not that this device would hold it.

The reconstructed original state query is:

```quarry
query p19RawState(post: posts):
  return { liked: exists likes[post, viewer], reposted: exists reposts[viewer, post] }
```

On both versions, a newly created post with neither interaction answers
`{liked: false, reposted: false}`, complete, online via `/q/p19RawState`.
Offline it returns `{loading: true}`. The composed post does too. The
device marks the unknown derived value speculative/unavailable; that term
does not mean a pending write exists. The pending list is empty. Adding
both keys, syncing, then going offline gives true/true, complete. This
matches the original and corrected offline logs named at `run-log.md:135`.

The builder's solution is `view ownLikes: count likes by .principal, .post`
and the corresponding repost view. Their source audience is public, and
the inherited sync drops the source horizon. A complete missing group
lookup returns zero. The final `postState` therefore returns false/false,
complete, offline. “own” in a view name does not restrict its audience.

At initial acquisition the independent reader receives **5,008 ownLikes
rows / 1,121,792 row bytes** and **1,004 ownReposts rows / 220,880 row bytes**,
including other viewers' keys. Those are logical stored row bytes from
`residency()`, not transfer bytes or standalone SQLite allocation.
The counts precede P19's interaction insertions.

**Why it wrote maintained summaries:** there was no source-level way to
request full coverage of its own keys while retaining a bounded public
window. A horizon-free public aggregate was an available coverage proof,
but replicated every reader's interaction keys to every device.

### 2.4 M6 inherited audiences and M8 helper bounds

All three compiler corrections reproduce against the full builder program
on both versions; the original diagnostics are retained as historical
excerpts and the reconstructed runs as JSON.

**M6.** An explicit `sync to .principal` on `ownLikes` gives
`E_QUARRY_SYNTAX`: a maintain inherits sync, or opts out with `online only`.
Removing that line while keeping `read <- .principal = viewer` gives
`E_SYNC`: inherited `sync public` requires a public read rule. A narrower
read rule does not re-infer the inherited residency. The second rewrite
says to match audiences but does not name that the public sync came from
`likes`, nor a viable offline alternative. The first rewrite's `online only`
alternative would undo the reason for this view: offline absence.

**M8.** Adding the recorded experimental viewer preview calling
`digestCounts(viewer, periodStart, periodEnd)` gives `E_QUARRY_BOUND` at
`schema.q:504:17`, the helper's `members[principal = reader]` loop.
`members` is readable by conversation membership; fixing the principal
does not pin that deciding conversation. A job can walk the domain as the
system under its chunk meter. A query cannot reuse that uncapped,
non-uniform loop as a complete total. Passing `viewer` to `reader` does
not change the rule's structural proof. The helper is checked in its
callers' execution contexts; a function is not a system-authority grant.

The current rewrite suggests `first 50`, or pinning conversation. Fifty
would change a full digest into a truncated total on the 100-chat fixture.
The builder removed the unused preview and kept the scheduled job; its
second check passed. It did not need an arbitrary cap on the job. This is
the specialized knowledge charged by the scorer, not a request to make
viewer queries run with job authority.

## 3. Proposed ordinary-query contract

### 3.1 One operation, explicit truth about coverage

Keep `Read<T>` and the existing query declaration. A known complete local
answer may satisfy an online read. Otherwise the platform uses the original
operation and arguments with an authorized server plan. Complete means
the declared page or scalar was answered within its coverage and work
limits; it does not promise an unbounded result or bypass meters.

Offline, return known non-speculative rows with `complete: false` when
coverage is insufficient, `fresh: false` and the existing `since` where
available. A derived scalar whose truth is not known remains loading;
`{liked: false, complete: false}` is not a substitute for a missing fact.
Fully acquired owner-key coverage makes that scalar answerable (§3.4).
Existing prediction, expiry, identity and delivery-publication fences still
govern every answer. Network state is not itself an authorization proof.

An online server may still refuse or return an honest cut. Complete online
coverage is the successful outcome when the authorized plan fits, not an
unconditional promise for arbitrary data size. No automatic retry may reset
the logical or physical meter to conceal unfinished work.

### 3.2 Retained history

The builder keeps its ordinary `history` and removes the UI's
history/query selection. A known departed range uses its acquired retained
images even online. The server cannot restore pre-leave rows the device
never acquired, cannot send post-leave messages, and need not be contacted
to prove an already certified local retained answer.

Do not broaden this into “ignore a server refusal.” An explicit application
`require`, a changed identity, ended lifetime, or invalidated retained
authority still wins. A retained text row does not authorize downloading
its former media. Decorations retain independent availability and must not
replace or unmount the message list. P12's current implementation is the
starting point. The line-55 plan evidence justifies the following targeted
normalization change, not a replacement of retained routing.

Normalize a safe, non-optional equality on the selected index's leading
column into that index's prefix, even when `by byHistory` is explicit.
For this builder, `.conversation = conversation` must lower to the same
conversation prefix as `messages[conversation = conversation]`, with the
same horizon selection, `Left` certification and completeness. Prove the
value is safe in the read's binding context; retain every other residual
predicate, existing key constraint, order, limit and cursor. Do not reorder
the index or infer unsafe, optional or conflicting equalities into a prefix.

Until implemented, the proposed guide text must state: “With an explicitly
selected `byHistory` index, write `messages[conversation = conversation]`.
Today `messages where .conversation = conversation ... by byHistory` leaves
the equality as a residual filter and does not establish the conversation's
local coverage. The inferred-order `where ... by .at` form has a different
planning path.” `check` should note a residual leading equality that prevents
this coverage and point to the bracket spelling while the limitation remains.

The integrated example explains that `complete` applies to the declared
read over its known domain, and freshness describes observation/sync state,
not a new membership grant. It must not label a retained page as newly
fetched server history just because the network is online.

### 3.3 One body per search scope and two platform plans

Make this the ordinary authoring form:

```quarry
query search(q: text <=100, c: cursor ?):
  return messages matching q where not .tombstone last 20 by .at after c
```

For the exact invertible non-expiring membership audience in this builder,
the binder derives the server membership discovery from `messages.read` and
its sync audience. It lowers to the authorized compact plan of LLP 3000.024,
without requiring the application to repeat `exists members[...]`.
The original source read rule still runs. This optimization is initially
limited to a single bare ordered page with a proved audience; arbitrary
joins, non-uniform extra rules and opaque native functions receive no
completeness promise from it and keep today's evaluator. `check --cost`
names the inferred audience and retains the grouped rewrite when opening
all scopes cannot fit.

On the device, the same query searches authorized current holdings and
lawfully retained images. It does not add an application membership predicate
that deletes retained hits. Horizon coverage, word expansion, expiry, filters
and meter limits all contribute to completeness. Existing explicit
membership predicates keep their literal meaning and their current behavior;
the compiler does not rewrite them away.

For a mixed set of current and departed chats while online, the platform
needs a narrowly proved ordered merge: the server's current authorized
stream plus the device's certified `Left` scopes. This is future work beyond
P12's whole-result routing and LLP 3000.001's component-record composition.
Never append arbitrary retained rows to an already limited server page.

The eligible plan must establish a head or proven exhaustion in every live
and retained lane before claiming a globally ordered prefix. Both sides use
the same `(at, id)` order, source identity and tombstone/expiry predicates.
Apply the page limit after union and deduplication. Reobserve departure,
rejoin and identity state before publication. A rejoined scope cannot appear
simultaneously as authoritative current data and a stale retained duplicate.
Keep the server's error authoritative; a typed loss of a scope can trigger
replanning only after sync establishes that transition.

The SDK owns buffering and cursor translation; there is still one declared
query and one application call. The initial online mixed-host implementation
makes **one server invocation of the original operation per requested combined
page**, plus a device scan on its separate local read ledger. It makes no
additional server request to fill the page or finish a constituent cut.
A server drain cut ends this combined page, preserving its incompleteness
and only the continuation the consumed prefix can safely support. Opening
cuts/refusals and undisclosed cut reasons remain authoritative; incomplete
or uncertain constituent work cannot become a complete combined answer.

A continuation must bind query arguments, identity/generation, ordering and
the relevant membership epoch, and advance each source **only through its
consumed prefix**.
Consumption means emission into the combined page or a proved safe discard
such as deduplication, not merely fetching a row. If retained rows fill the
page, a fetched but unconsumed server page must not advance to its response's
`next`. Bound and retain that unconsumed work with its ownership and validity
checks, or recompute from the consumed position on a later requested page,
charging the repeated work. Do not introduce a durable search session.

The coordinator's budget comes from the **same existing per-page device read
allowance as the local scan**, with no third allowance or reset after scanning.
Charge merge comparisons, deduplication, server-result decoding, buffering,
retained state, output and cursor construction before work/allocation; carried
state occupies that allowance on resume. Server work keeps its own unchanged
invocation ledger and physical authorization bound. Exhausting either side
preserves the appropriate cut/refusal, never a fabricated full page.

No hidden-row key, unauthorized scope or private cut reason may enter the
continuation. Stay within the existing cursor bound; refuse/reset rather than
accumulate unbounded lane state. A link transition invalidates a cursor whose
plan cannot continue
with equivalent coverage; the SDK restarts the observation without asking
the application to choose a second operation.
Any broader multi-request protocol must go through LLP 3000.024 §5 and its
Decision process, including consistency, disclosure and state-lifetime review.

The domain is deliberately explicit: current authorized server history plus
the images that **this device** may retain. It is not all historical messages
from a former chat. Missing retained acquisition ranges make the combined
answer incomplete where they could change its requested prefix. The online
client with no device has only the current authorized domain. Offline a
device has its current and retained holdings and reports coverage honestly.

For “This chat,” explicitly author one pinned ordinary operation:

```quarry
query searchChat(conversation: conversations, q: text <=100, c: cursor ?):
  return messages[conversation = conversation] matching q where not .tombstone last 20 by .at after c
```

It has no membership `require`. Table rules still protect server reads;
a departed conversation keeps only its certified retained images locally,
online or offline, while a current conversation may use the server below
the acquisition horizon. Missing acquired history stays incomplete. The
example uses this body for both link states and drops `searchInHeld` from
its selection, just as it drops `searchHeld` for all-chat search. Existing
guarded `searchIn` operations remain unchanged and still refuse `NOT_MEMBER`;
the compiler must never strip their explicit guard.

This merge and cursor protocol are not prototyped here. Their proof and
costs are implementation prerequisites, not claimed consequences of renaming
`searchHeld`. Land the inferred current-scope plan independently only if
its narrower scope is stated; do not announce this whole RFC as implemented.

### 3.4 Viewer-owned keys: a partition proof, not a cached miss

Recommend a platform-maintained owner-key partition, selected explicitly on
the source. Illustrative **new syntax, not supported today**:

```text
-- within likes
sync public last 2000 by .at with own keys .principal
-- within reposts
sync public last 1000 by .at with own keys .actor
```

The exact spelling is for language review. The design decision is explicit
coverage policy, one source and one ordinary query body. Existing declarations
keep their existing sizes and meanings. The new social recipe uses this policy
by default; no heuristic recognizes a field just because it is called owner.

Initially admit only non-expiring public sources with a total unique key
containing the declared principal column, immutable key/owner fields, and
structurally proved caller-owned writes, as in these two builder tables.
The compiler checks those conditions and supplies the source owner index.
More complex row rules, inherited lifetimes and mutable ownership require
their own proof before this policy can accept them. `online only` opts out;
the compiler must not silently sync such a table.

For each principal, maintain every extant unique key in that principal's
partition, without a time horizon. No post body, media, timestamp or another
principal's key is needed. Reuse whole-partition snapshot/catch-up/watermark
publication. A complete empty partition is an affirmative proof of no keys;
a partial snapshot, reset, gap, failed persistence or missing generation is
not. Inserts/deletes of source and key projection commit together. Deletion
of the last key must still publish whole empty coverage.
The complete marker is principal-scoped, and sign-out or viewer change
withdraws it in the same device commit that drops its keys. A subsequent
viewer cannot inherit either the keys or their absence proof.

An `exists likes[post, viewer]` can then consult this coverage when its raw
point is outside the public window. A present key proves existence; a missing
key proves absence only in the complete owner partition at its acquired
watermark. An offline answer remains stale relative to unseen remote writes.
This owner-key proof covers only the viewer's own keys: the owner expression
must be proved equal to the caller. `exists likes[post, other]` for another
principal retains today's unknown-outside-the-public-window result, even
when this device's own partition is complete. Neither presence nor absence
for another principal follows from the viewer's partition.
This proof certifies **existence only**: it cannot supply a row image, public
count, arbitrary predicate, retained media grant or mutation precondition
that needs fields the device lacks. Predictions overlay/invalidate the key
facts transactionally under the existing publication fences; an unpredicted
write stays a pending intent, never a fabricated settled key.

The compiler may implement the projection as a hidden table. It is platform
custody, so the builder removes `ownLikes`/`ownReposts` and restores the
original raw `postState` and `postCard` expressions. Schema adoption builds
keys from the existing store before publishing coverage; interrupted adoption
never exposes an empty completed owner set. The new capability must be fenced
from older device implementations rather than quietly yielding false answers.
Ordinary older applications and their explicit summaries continue compiling.

Alternatives considered:

| Alternative | Decision and reason |
| --- | --- |
| Remove the raw public horizons | Works for absence after whole acquisition, but sends every user's full rows everywhere; reject as the default. |
| Sync all viewer-owned raw rows as well as the public window | Sufficient and useful when offline row fields are needed; more payload/index/storage than this Boolean question needs. Consider a later explicit row policy. |
| Cache a server absence proof for each queried `(post, viewer)` | Reject here: arbitrary unseen posts remain unknown; introduces per-query negative facts, invalidation and cache custody excluded by NOT-DOING. |
| Complete viewer-key partition | Preferred. One watermark/coverage domain, all own keys, no request-shaped receipts; answers arbitrary keys, including never queried posts. |
| Automatically infer extra sync from every `exists` | Reject silent expansion of existing apps. Offer a checked schema policy and make it the recipe/scaffold default. |

The [owner-key pilot](../snapback4/experiments/p19-one-query/own-keys.q)
uses ordinary private horizon-free tables populated from `u0500`'s actual
keys on a copied store. Both runtimes return complete offline true and false,
keep an offline pre-delete true marked stale, then return false after syncing
the deletion. Three like keys and one repost key occupy **426 + 142 = 568
row bytes**. This shows that an ordinary private whole partition can answer
these Booleans; it is not evidence for the proposed public-source projection.
It does not exercise dual distribution, empty coverage publication, source
maintenance, automatic lowering, adoption, pending-write interaction or a
new wire capability.

## 4. Put the rules where the builder meets them

For M6, retain the refusal but replace generic repair text with the source
chain: “`ownLikes` inherits horizon-free public sync from `likes`; its new
owner-only read rule conflicts with that audience. A maintained view cannot
declare a separate sync audience. Keep the public rule to retain this public
offline summary, or use `online only` and lose offline absence coverage.”
Once §3.4 exists, offer its source owner-key policy for this exact use case.

## 5. What stays and what needs a deliberate extension

Authorization, expiry, server disclosure, the physical authorization-work
bound and logical meters are unchanged. A device's retained history cannot
grant server access. Server replies never echo client claims as authorization.
No current-membership predicate or explicit query refusal is bypassed.
Unknown scalars remain loading. `held` remains the instruction that a read
must never reach the server, including a cut or failed local proof, and
server execution still refuses it with `E_QUERY_HELD`.

Existing `historyHeld`, `searchHeld`, `searchInHeld`, guarded `searchIn`,
explicit `searchNewest` and maintained interaction summaries remain valid.
No forced source migration or new application-owned online/offline query
branch is introduced. The new owner-key
capability needs an ordinary coordinated upgrade; backward source compilation
does not mean an old device can interpret a new coverage proof.

The bare membership-audience word search deliberately changes behavior:
today's empty incomplete server answer becomes the compact membership page
for the admitted audience class, subject to the existing meters and cuts.
Any audience outside that class keeps today's plan and completeness behavior.
This is a result change, even though existing source keeps compiling.

This RFC does propose extensions to current boundaries: §3.3's ordered
mixed page composition and §3.4's platform projection with a narrower
distribution than its public source. Before implementation, record the
corresponding NOT-DOING move and account for schema, index, sync and custody
costs. Do not quietly call it existing support for multiple sync audiences.
Per-query result caches, durable search sessions, unbounded cursor state,
new authorization grants and JavaScript query execution remain excluded.

| Cost | Measure before accepting an implementation |

Do not multiply the four-key result into a universal saving. |

Do not use two independent query requests to reset meters and relabel their
union as one successful original server query. The initial SDK-side two-host
merge makes one server invocation per requested combined page; a constituent
cut or uncertainty ends the attempt without extra requests to complete it.
The coordinator shares the device scan's existing read allowance (§3.3),
not a fresh allowance after that scan. Measure retained unconsumed work and
charge recomputation; fetching ahead never advances a source's consumed prefix.
Any broader multi-request protocol returns to LLP 3000.024's decision process.
