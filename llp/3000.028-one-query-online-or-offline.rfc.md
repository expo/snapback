## 1. Decision

Let an application declare a read once. The platform should select an
authorized server plan for complete online coverage and a device plan for
offline coverage. A device page may be incomplete; an unknown Boolean must
not become false. Neither condition should require a second query body or
an application branch on network state.

Calibration #24 scored queries/live and client integration 85, data modeling
87, against 95. Its builder wrote `historyHeld` beside `history`, selected
`searchHeld` versus `searchNewest` and `searchInHeld` versus `searchIn`,
and invented public interaction-key aggregates to prove offline absence.
It also had to learn that aggregate residency and readability are independent,
and that a helper's query callers
inherit stricter bounds than its job callers.

This RFC accepts three design changes:

1. Keep ordinary retained history as the supported contract, with the exact
   calibration program in its regression and integrated guide example.
   Give the proved leading equality equivalent prefix coverage with an
   explicitly selected index. The later UI failure does **not** reproduce
   with the bracket body after a completed leave sync; this is not evidence
   for replacing that working routing mechanism.
2. Give the ordinary bare all-chat search an inferred server audience plan
   and a device plan that includes authorized retained images. Define bounded
   composition for a mixture of live and departed chats inside the platform,
   and use one unguarded pinned body for per-chat search.
3. Add an explicit owner-key coverage policy on a windowed source. The
   platform maintains a horizon-free, viewer-partitioned key projection;
   the application keeps its ordinary `exists` expression. Make this the
   social recipe's default, rather than silently expanding every existing
   windowed table.

Improve the two diagnostics at their failing source sites, and show all of
this in one compiled social-app example with exercised React/Expo witnesses.
This accepts the design; this round authorizes document changes only, with
no product implementation, ceiling increase or publication. The experiment
contains no replacement query engine.

The scope addresses query selection and offline coverage. Transient media
ownership, online typing and route/composer lifetime remain client work;
these proposals do not eliminate those client-integration charges. §8 requires
recipes and exercised witnesses for them. A fresh builder/scorer run is needed
before claiming the target score of 95.

### 2.1 Former member: the server loses authority, the device keeps history

The earlier `run-log.md:55` incident is a concrete coverage-spelling failure,
distinct from the later line-91 UI symptom. With the explicitly selected
`byHistory` index, `messages where .conversation = conversation last 20 by
byHistory` kept the equality as a residual filter and selected `byHistory ()`.
The bracket form selected `byHistory (conversation = conversation)`, pinning
the audience group and its horizon/retained coverage. The saved
`evidence/m3-history-why.txt` and `evidence/m3-history-why-2.txt` show these
different plans; the run log records server fallback and lost retained local
rendering before the bracket correction. The P19 baseline planner's
`bind/intent.rs::read` returns before intent normalization when an index is
already selected. The guide's `where` form with inferred `by .at` does not
take that path. P19's runtime experiment used the corrected bracket body;
it did not rerun the earlier `where` body. §3.2 requires equivalent coverage
for this narrowly proved equality case.

The final builder already has the P12 form:

```quarry
query history(conversation: conversations, c: cursor ?):
  return messages[conversation = conversation] last 20 by byHistory after c
```

`messages` retains delivered history, syncs to `members[.conversation]`,
and acquires its last 500 on the same `byHistory` index. `conversations`
also retains history. There is no membership `require`, join, profile,
receipt or other decoration in this body. `historyHeld` differs only in
its header. Thus P12's old explanation about a guarded or decorated history
does not diagnose this final program.

After the reader acquires one message and its leave tombstone, **both arms**
observe:

| Read | Result |
| --- | --- |
| Online-only `history` | `data: []`, `complete: true`; no currently readable rows |
| Online-only `progress` | `NOT_MEMBER` from its explicit required member lookup |
| Local ordinary `history`, online | The retained row; `complete: true`; no server request |
| Local `historyHeld`, online | The same retained row; no server request |
| Either history, offline | The same row, `fresh: false`; no post-leave message |
| Ordinary history after rejoin and sync | Both messages via server fallback from the rejoined range |

The raw departed device answer has `retained: true, unknown: false`.
`device/history.rs` persists the `Left` group; `device.rs::query_observation`
propagates retained-only coverage. `local-query.ts` asks the server for
unknown coverage **unless retained**, and keeps this page. The server does
not reject the bare query: it returns an authorized empty page. It refuses
the guarded progress operation. Keeping those outcomes distinct matters.

The later historical record is real but weaker than a routing diagnosis.
`run-log.md:91` calls the cause ambiguous and records the switch after a
transient retained-history count failure. `m4-m3-regression-5.log:2` says

**Why it wrote the branch:** `src/receipts.ts` treats a `NOT_MEMBER` progress

P19 establish that this corrected bracket query incorrectly replaced these
retained rows in that later incident.
P19 does not claim to have reproduced that historical UI failure. Capturing
the failing observation/interleaving remains necessary before diagnosing it.

### 2.2 All-chat and per-chat search: deleting `held` is insufficient

The final builder has two different predicates, not just two headers:

```quarry
query searchHeld(q: text <=100, c: cursor ?) held:
  return messages matching q where not .tombstone last 20 by .at after c
query searchNewest(q: text <=100, c: cursor ?):
  return messages matching q where exists members[.conversation, viewer] and not .tombstone last 20 by .at after c
```

`src/Search.tsx` selects between them using `useLink`, and remounts its
results by link state. The search card itself instructs this split: held for
device holdings; grouped/newest online for full history. That is the guidance
the builder followed at `run-log.md:100`.

On `u0500`, `q: 'coffee'`, **both runtimes** produce:

| Operation | Server | Local online | Local offline |
| --- | --- | --- | --- |
| `searchNewest` | 20 hits, complete | Same via fallback | 20 held hits, incomplete |
| `searchHeld` | `E_QUERY_HELD` | 20 held hits, incomplete, no request | 20 held hits, incomplete |
| Bare held body made ordinary | Empty, incomplete | Server replaces 20 device hits with empty, incomplete | 20 held hits, incomplete |

The explicit membership form already answers both modes for **current**
chats. Its server meter is examined 141, index entries 141, probes 140,
heap 433,439 B, output 8,251 B, steps 1,619. The unscoped ordinary form
returns an empty incomplete answer with logical examined 1, index entries
33, probes 55, heap 36 B, output 12 B, steps 19. These latter counters
do not measure all hidden authorization work. LLP 3000.024 §2 describes
the hidden-prefix exhaustion in this corpus; the observable result and
current plan inspection agree with that explanation. P19 did not add an
internal physical-counter instrument.

There is a second difference. On the departed reader, searching the unique
retained token gives `searchNewest: []` with `complete: true`: the explicitly
required current membership no longer exists. Held search finds the retained
message with `complete: false`. The bare ordinary body also finds it offline,
but its unscoped coverage is unknown. Explicit application predicates cannot
be erased just because they exclude retained data.

**Why it wrote two bodies:** the author must currently supply the server's
audience-discovery predicate; that predicate changes which retained rows
the device can return. Removing only `held` exposes the unscoped server
plan, and using only `searchNewest` drops former chats. A full first page
offline is still incomplete when the horizon cannot prove the global word
order; twenty hits alone are not evidence of coverage.

There is also a second network-selected pair at `src/Search.tsx:10` for
“This chat.” The final program's `searchIn` (`builder.q:428`) has
`require exists members[conversation, viewer] else NOT_MEMBER` before
`messages[conversation = conversation] matching q where not .tombstone`.
`searchInHeld` has the same pinned page without that `require`. A former
member's retained match can therefore be available through the held body
offline while the ordinary guarded body refuses `NOT_MEMBER` online.
This follows from the supplied bodies and selector; P19 did not run this
pair in its experiment. Replacing only the all-chat pair leaves this branch
and mode-dependent meaning intact. §3.3 proposes an explicitly authored
unguarded per-chat body; it does not remove guards from existing queries.

### 2.3 “Did I like this post?”: acquired does not prove an absent key

The original relations have public windows of 2,000 likes and 1,000 reposts
by time. A unique `(post, principal)` or `(actor, post)` miss cannot prove
absence from those windows. The missing row might be older. Uniqueness
proves at most one row, not that this device would hold it.

The reconstructed original state query is:

```quarry
query p19RawState(post: posts):
  return { liked: exists likes[post, viewer], reposted: exists reposts[viewer, post] }
```

On both versions, a newly created post with neither interaction answers
`{liked: false, reposted: false}`, complete, online via `/q/p19RawState`.
Offline it returns `{loading: true}`. The composed post does too. The
device marks the unknown derived value speculative/unavailable; that term
does not mean a pending write exists. The pending list is empty. Adding
both keys, syncing, then going offline gives true/true, complete. This
matches the original and corrected offline logs named at `run-log.md:135`.

The builder's solution is `view ownLikes: count likes by .principal, .post`
and the corresponding repost view. Their source audience is public, and
the inherited sync drops the source horizon. A complete missing group
lookup returns zero. The final `postState` therefore returns false/false,
complete, offline. “own” in a view name does not restrict its audience.

At initial acquisition the independent reader receives **5,008 ownLikes
rows / 1,121,792 row bytes** and **1,004 ownReposts rows / 220,880 row bytes**,
including other viewers' keys. Those are logical stored row bytes from
`residency()`, not transfer bytes or standalone SQLite allocation.
The counts precede P19's interaction insertions.

**Why it wrote maintained summaries:** there was no source-level way to
request full coverage of its own keys while retaining a bounded public
window. A horizon-free public aggregate was an available coverage proof,
but replicated every reader's interaction keys to every device.

### 2.4 M6 inherited audiences and M8 helper bounds

All three compiler corrections reproduce against the full builder program
on both versions; the original diagnostics are retained as historical
excerpts and the reconstructed runs as JSON.

**M6.** An explicit `sync to .principal` on `ownLikes` gives
`E_QUARRY_SYNTAX`: a maintain inherits sync, or opts out with `online only`.
Removing that line while keeping `read <- .principal = viewer` gives
`E_SYNC`: inherited `sync public` requires a public read rule. A narrower
read rule does not re-infer the inherited residency. The second rewrite
says to match audiences but does not name that the public sync came from
`likes`, nor a viable offline alternative. The first rewrite's `online only`
alternative would undo the reason for this view: offline absence.

**M8.** Adding the recorded experimental viewer preview calling
`digestCounts(viewer, periodStart, periodEnd)` gives `E_QUARRY_BOUND` at
`schema.q:504:17`, the helper's `members[principal = reader]` loop.
`members` is readable by conversation membership; fixing the principal
does not pin that deciding conversation. A job can walk the domain as the
system under its chunk meter. A query cannot reuse that uncapped,
non-uniform loop as a complete total. Passing `viewer` to `reader` does
not change the rule's structural proof. The helper is checked in its
callers' execution contexts; a function is not a system-authority grant.

The current rewrite suggests `first 50`, or pinning conversation. Fifty
would change a full digest into a truncated total on the 100-chat fixture.
The builder removed the unused preview and kept the scheduled job; its
second check passed. It did not need an arbitrary cap on the job. This is
the specialized knowledge charged by the scorer, not a request to make
viewer queries run with job authority.

MP round 1 makes the job-preserving diagnostic conditional: “if this viewer
query is unused, remove `<name>`”. A compiler cannot infer whether a screen
outside the Quarry program calls that viewer query. The paged-preview and
complete-job alternatives remain explicit.

## 3. Proposed ordinary-query contract

### 3.1 One operation, explicit truth about coverage

Keep `Read<T>` and the existing query declaration. A known complete local
answer may satisfy an online read. Otherwise the platform uses the original
operation and arguments with an authorized server plan. Complete means
the declared page or scalar was answered within its coverage and work
limits; it does not promise an unbounded result or bypass meters.

Offline, return known non-speculative rows with `complete: false` when
coverage is insufficient, `fresh: false` and the existing `since` where
available. A derived scalar whose truth is not known remains loading;
`{liked: false, complete: false}` is not a substitute for a missing fact.
Fully acquired owner-key coverage makes that scalar answerable (§3.4).
Existing prediction, expiry, identity and delivery-publication fences still
govern every answer. Network state is not itself an authorization proof.

An online server may still refuse or return an honest cut. Complete online
coverage is the successful outcome when the authorized plan fits, not an
unconditional promise for arbitrary data size. No automatic retry may reset
the logical or physical meter to conceal unfinished work.

### 3.2 Retained history

The builder keeps its ordinary `history` and removes the UI's
history/query selection. A known departed range uses its acquired retained
images even online. The server cannot restore pre-leave rows the device
never acquired, cannot send post-leave messages, and need not be contacted
to prove an already certified local retained answer.

**Publication ordering (RH, 2026-10-04).** An ordinary unknown-coverage
fallback can start while the device still calls a group current and return
after the server has revoked it. Its authorized empty page must not replace
the history that the pending leave will retain. This is independent of whether
the first device answer already carried retained components or row masks.

For a locally evaluated fallback whose possible dependencies include a synced
`delivered-history` table, compare the server answer's sequence with the applied
watermark returned by that evaluation's read transaction. Unknown branches
keep static dependencies; opaque native reads cover every table. A later
transport capture is not this evidence: another process can commit to the
same SQLite store without advancing this reader's in-memory authority revision.
The engine reads the watermark and rows in one transaction, on both hosts.
The whole-server covered-evidence exception in LLP 3000.023 §10 excludes
these retained-sensitive routes: a newer server cut cannot certify an older
local routing decision. Disjoint-input progress separately proves that the
local inputs stayed unchanged and requires a covering cut for each external
component; it does not replace the transaction-bound routing proof.
OP round 1 keeps that proof live after routing: every checkpoint and the final
publication proof compare the evaluation watermark against this client's maximum
observed published device watermark. Published apply records the floor in its
commit callback, before later metadata/media waits; sync then records the actual
published watermark too. If publication advances past the evaluation cut, the
candidate is retired and its watch reruns, even for an empty table footprint and
a server cut that already covers the catch-up. Missing evaluation metadata may
survive only without floor advancement since attempt capture. Equal-watermark
repetitions coalesce. This floor adds no query await, certifies no local rows and
cannot observe another owner's unreported commits; the existing shared-store
transaction checks below remain necessary.
Equal/older server cuts therefore need no extra device call. Missing or invalid
evaluation metadata conservatively takes the ahead-cut path. Known complete local answers and queries with no possible
retained dependency keep their existing route and await count.

For a whole-server candidate whose cut is ahead (or whose ordering evidence
is absent), read the
actual device watermark once. A caught-up device is evaluated again, and that
observation decides whole-local, whole-server or independent-component routing.
New row-level retention without a requested server provenance envelope keeps
the permitted local subtree; it invents no pairing or second server request.
While the device is still behind, an empty server page must not replace its
permitted non-speculative history. Publish that local value with
`complete: false, fresh: false`, or loading if it has no publishable value.
A positive server array may be published with those same provisional flags:
this preserves useful reads before acquiring a new conversation and current
page decorations. Structured answers keep the local value so empty nested
history cannot sneak through. No provisional answer enters remembered whole
answers or conveys a delivery manifest; the server cut still orders cache
retirement when that result is accepted. A positive provisional page retains
its server value/answer deadlines.

Already-known retained compositions keep their existing second observation,
source-identity pairing, stale metadata and value deadlines. They can combine
retained device rows with current server rows while sync is behind. If the
second observation instead selects a whole-server answer, that candidate must
pass the same evaluation-cut/applied-watermark check. That second decision is
bound to the second evaluation's watermark; another owner committing before a
later state read cannot validate the earlier decision. If that evaluation is
behind, keep its permitted value provisional. A still-retained sibling likewise cannot validate emptying an unknown sibling
array at an ahead cut: keep that sibling's non-speculative device rows with
provisional metadata, or withhold speculative rows. Explicit retained routing
stays owned by the device; a provisional server page is never a fresh, complete substitute.

This adds no catch-up wait, polling loop or new retention budget. Sync wakes
retained-sensitive observations and reroutes from applied state, even when a
published page advances only the watermark and touches no local rows. Selection
includes purely local watches with no server-read flag or pending change cut,
and uses static plus observed dependencies (all tables for opaque programs). Existing notified-cut
and scope fences may prevent the older partial value from replacing a watch;
the ordinary one-second revocation bound then withdraws it to loading if sync
stalls. A one-shot returns permitted partial data promptly, or settles through
its existing bounded retry/refusal procedure (LLP 3000.023 §11). Every new await
uses the existing session, incarnation, authority, prediction, credential and
expiry checks. Explicit original-query refusals win immediately. No retention
metadata grants server authority, changes the horizon or changes `Read<T>`.

One-shots, observations, plain cursors and page chains all use this routing
procedure. Non-blank ordinary search has its own metered coordinator and
must meet the equivalent rule in §3.3. Blank search uses the ordinary local
router. A query that cannot execute in the current device partition still
uses Rule 3 and the store/adoption identity fences: it cannot select retained
images from an invalidated partition. A cold bypass is restricted to an
already server-answered, unacquired watch; a provisional retained-sensitive
fallback is not eligible. Ephemeral reads remain whole-server queries under
LLP 3000.017 §2.3, with their own incarnation/expiry fences; durable retained
history is a separate query under that contract.

The held-apply regressions on wasm and process reproduce the captured order
without load; the real server still returns zero while the device holds 25.
The [RH report](../snapback4/reports/20261004-rh-retained-history-order/REPORT.md)
records the causal controls, contention repetitions and latency measurements.

Do not broaden this into “ignore a server refusal.” An explicit application
`require`, a changed identity, ended lifetime, or invalidated retained
authority still wins. A retained text row does not authorize downloading
its former media. Decorations retain independent availability and must not
replace or unmount the message list. P12's current implementation is the
starting point. The line-55 plan evidence justifies the following targeted
normalization change, not a replacement of retained routing.

Normalize a safe, non-optional equality on the selected index's leading
column into that index's prefix, even when `by byHistory` is explicit.
For this builder, `.conversation = conversation` must lower to the same
conversation prefix as `messages[conversation = conversation]`, with the
same horizon selection, `Left` certification and completeness. Prove the
value is safe in the read's binding context; retain every other residual
predicate, existing key constraint, order, limit and cursor. Do not reorder
the index or infer unsafe, optional or conflicting equalities into a prefix.

**Lane EQ implementation, 2026-09-28.** The selected plain-index path now
extends an explicitly indexed page's contiguous prefix using a single
explicit `=` equality per next column, with the existing binding-context
safety proof and a non-optional source column. Round 1 restricts extraction
to leading conjuncts: it never skips an earlier predicate that could refuse
or fail arithmetic. Existing seeks keep their original binder path (an
invalid seek must not become valid); extraction stops before the index's
final component. Unpaged reads remain unchanged, preserving both
scan admission and result kind.
It does not change the index, order, limit, existing keys or remaining
predicates. Duplicate/conflicting equalities, optional/fallible values, gaps,
computed columns, bare Boolean predicates and selected word indexes remain
outside this normalization. Unchanged predicates keep their original source

### 3.3 One body per search scope and two platform plans

**Publication cut (RH round 1, 2026-10-04).** `search_state` returns the
applied watermark and acquired current scopes from the same read transaction
as its retained membership observation. The closing state still verifies the
existing delivery/epoch fences. Stable fences alone do not prove that a newer
server leave has been applied. When the server cut exceeds the opening cut
(or ordering metadata is absent), its complete authorized `searchScopes`
opening may prove that every acquired current scope is still current. This
proof uses the shared search ledger and adds no device call or HTTP request.
It preserves ordinary current edits, unrelated writes and valid continuations.

Without that proof, the merged positive page is provisional (`complete: false`,
`fresh: false`), with its existing value/answer deadlines and no continuation.
If the server and retained scan produced no hits, evaluate the ordinary device
query once at the caller's consumed position, including still-current acquired
matches. Resume the same meter and return its permitted matches provisionally,
or loading when it supplies no usable value. Do not infer fresh absence from
the empty server lane, reset the meter, request another server page, remember a
whole answer, or issue a cursor that skips an unresolved retained head. Normal
publication fences and bounded one-shot retries still apply; published sync
progress wakes served observations. Explicit original-query refusals win.
An existing combined cursor whose audience/identity changed is withdrawn by
the existing binding check and restarts its root; this rule does not relax it.


Make this the ordinary authoring form:

```quarry
query search(q: text <=100, c: cursor ?):
  return messages matching q where not .tombstone last 20 by .at after c
```

For the exact invertible non-expiring membership audience in this builder,
the binder derives the server membership discovery from `messages.read` and
its sync audience. It lowers to the authorized compact plan of LLP 3000.024,
without requiring the application to repeat `exists members[...]`.
The original source read rule still runs. This optimization is initially
limited to a single bare ordered page with a proved audience; arbitrary
joins, non-uniform extra rules and opaque native functions receive no
completeness promise from it and keep today's evaluator. `check --cost`
names the inferred audience and retains the grouped rewrite when opening
all scopes cannot fit.

On the device, the same query searches authorized current holdings and
lawfully retained images. It does not add an application membership predicate
that deletes retained hits. Horizon coverage, word expansion, expiry, filters
and meter limits all contribute to completeness. Existing explicit
membership predicates keep their literal meaning and their current behavior;
the compiler does not rewrite them away.

For a mixed set of current and departed chats while online, the platform
uses a narrowly proved ordered merge: the server's current authorized
stream plus the device's certified `Left` scopes. This extends
P12's whole-result routing and LLP 3000.001's component-record composition.
Never append arbitrary retained rows to an already limited server page.
**Decision, 2026-09-28 — supervisor ruling, lane OS round 7.**
A page's retained candidates (at most its size plus lookahead) send only their
IDs in that same server invocation. Before evaluating the page, the server
point-reads those IDs through the ordinary row/field/expiry authorization
boundary, in the page's transaction and existing meter. It returns only which
supplied IDs currently have readable rows. The SDK suppresses those retained
candidates: the current lane owns a readable current ID even if its new image
no longer matches, was filtered out, or lies before the consumed position.
This covers both a scope update and delete/reinsert replacement of the same ID.
The round-5 immutable-scope admission is removed: `immutable` constrains updates,
not the ID's whole lifetime, and point overlap supplies the needed proof.

**Disclosure argument.** Every returned ID was supplied by this viewer. A
positive answer says no more than a point read of that ID already says; hidden,
absent and expired current images all produce the same negative answer. The
check returns no newly discovered IDs, scope names, bodies, order keys or hidden
counts. It does not enumerate the server's other IDs. Ordinary point admission,
private-field handling, expiry dependencies and authorization work remain in
force. Its proof and page use one transaction; the captured store/generation,
audience and device delivery fences still gate publication. Retained text grants
no server or media authority. Malicious oversized candidate lists refuse before
point work; a capped check refuses rather than treating unknown as absence.

Suppression is a safe consumed discard. When a bounded candidate prefix is all
suppressed, the coordinator may return an empty page with a progress cursor at
its last discarded retained key. It cannot fetch a second device or server page
to fill that request. A short prefix ends before any unproved next retained head;
subsequent explicit requests recompute and pay again. This preserves one server
invocation, bounded memory and cursor size, and no empty non-progressing answer.
The overlapped point work is bounded by page size and spends the server's
existing query allowance, so an envelope that formerly drained may now refuse
while opening. Candidate serialization, reply decoding and suppression also
spend the existing shared device/coordinator allowance.

The eligible plan must establish a head or proven exhaustion in every live
and retained lane before claiming a globally ordered prefix. Both sides use
the same `(at, id)` order, source identity and tombstone/expiry predicates.
Apply the page limit after union and deduplication. Reobserve departure,
rejoin and identity state before publication. A rejoined scope cannot appear
simultaneously as authoritative current data and a stale retained duplicate.
Keep the server's error authoritative; a typed loss of a scope can trigger
replanning only after sync establishes that transition.

The SDK owns buffering and cursor translation; there is still one declared
query and one application call. The initial online mixed-host implementation
makes **one server invocation of the original operation per combined-page
publication attempt**, plus a device scan on its separate local read ledger. It makes no
additional server request to fill the page or finish a constituent cut.
A server drain cut ends this combined page, preserving its incompleteness
and only the continuation the consumed prefix can safely support. Opening
cuts/refusals and undisclosed cut reasons remain authoritative; incomplete
or uncertain constituent work cannot become a complete combined answer.

**One-shot settlement, 2026-09-30 — QS.** LLP 3000.023 §11 now bounds the
outer `query()` call. A retired attempt may be discarded and evaluated again;
a ready partial page or authoritative refusal ends the call without draining
or combining work from another attempt. Thus the one-invocation statements
below apply per publication attempt; one-shot retries can pay that cost up to
four times within their shared deadline. Cursor/authority fences and each
attempt's meters remain unchanged. An invalid old continuation that cannot
settle refuses `E_QUERY_RETRY`; the caller may need sync or a fresh first page.
Observed page-chain recovery keeps its existing root/suffix procedure.

A continuation must bind query arguments, identity/generation, ordering and
the relevant membership epoch, and advance each source **only through its
consumed prefix**.
Consumption means emission into the combined page or a proved safe discard
such as deduplication, not merely fetching a row. If retained rows fill the
page, a fetched but unconsumed server page must not advance to its response's
`next`. Bound and retain that unconsumed work with its ownership and validity
checks, or recompute from the consumed position on a later requested page,
charging the repeated work. Do not introduce a durable search session.

**Decision, 2026-09-28 — supervisor ruling, lane OS round 6.**
Continuation is keyset pagination over (order key, id), evaluated at each page
request, across the combined domain. Each page is the next rows after the
consumed position among the rows each lane can see at that request: the server
lane over current scopes, and the device lane over retained rows. This is the
contract every single-source ordinary search already has. A traversal is not a
snapshot. Between pages, a row whose order key changes, whose match status
changes, or which is inserted before the consumed position may repeat or be
skipped, exactly as a server-only traversal would treat it. Exactly-once holds
for every row whose order key, match status, scope and readability stay stable
across the traversal. An application that needs exactly-once over edits declares
the order column `immutable` (message `at` usually is). Reactive page ranges are
a possible future design, not part of this contract.

The combined consumed position bounds both source requests. An unconsumed
fetched hit after that position stays eligible; a newly visible hit before it
does not enter a later page just because its source has not emitted any rows.
SDK page accumulation uses source row identity only when query metadata proves it,
and keeps the newest observed image. Generated source-row page handles carry
`rowKey: "id"`; arbitrary projections preserve list semantics, including fields
named `id` that are computed from another column. Existing cut and coverage
limits still apply; `complete` certifies a page, and terminal completeness is
judged against the remaining keyset domain at that request.

The coordinator's budget comes from the **same existing per-page device read
allowance as the local scan**, with no third allowance or reset after scanning.
Charge merge comparisons, deduplication, server-result decoding, buffering,
retained state, output and cursor construction before work/allocation; carried
state occupies that allowance on resume. Server work keeps its own unchanged
invocation ledger and physical authorization bound. Exhausting either side
preserves the appropriate cut/refusal, never a fabricated full page.

No hidden-row key, unauthorized scope or private cut reason may enter the
continuation. Stay within the existing cursor bound; refuse/reset rather than
accumulate unbounded lane state. A link transition invalidates a cursor whose
plan cannot continue
with equivalent coverage; the SDK restarts the observation without asking
the application to choose a second operation.
Any broader multi-request protocol must go through LLP 3000.024 §5 and its
Decision process, including consistency, disclosure and state-lifetime review.

The domain is deliberately explicit: current authorized server history plus
the images that **this device** may retain. It is not all historical messages
from a former chat. Missing retained acquisition ranges make the combined
answer incomplete where they could change its requested prefix. The online
client with no device has only the current authorized domain. Offline a
device has its current and retained holdings and reports coverage honestly.

For “This chat,” explicitly author one pinned ordinary operation:


### 3.3.1 Point decorations preserve the search page

A pinned ordinal page may name its plain unique conversation/ordinal index
(LLP 3000.007 §18.1, IS). It lowers to the same words scan as `by .ordinal`;
that spelling does not widen composition admission or change the decoration,
coverage or cursor guarantees below.

The ordinary all-chat and pinned-chat forms may return presentation fields:
`messages matching q last 20 by .at after c { *, chatTitle: conversations[.conversation].title,
senderName: profiles[principal = .author].name }`. Reference traversal (including multiple
hops) and total unique-key point reads are decorations. The compiler separates
the original bare page from its one-to-one projection. The bare plan alone owns
hit identity, order, completeness, cut, continuation and freshness. No missing,
unreadable or unavailable decoration drops its hit: its value is `null`.

A decoration deadline is a **value deadline**, never an availability condition.
This applies to composed local and online-only clients, remembered answers,
watches and one-shots. Passing or not knowing it never blocks, withdraws or
blanks the page, returns `E_QUERY_RETRY`, or changes hits, order, `complete`,
`cut`, `next` or freshness. A one-shot returns the page. Only the bare page's
own deadlines may withdraw it; authority and publication fences still apply.

At or after a known deadline, or when its freshness cannot be proved, no
pre-expiry decoration value may remain visible, including during an in-flight
refresh. This implementation conservatively nulls **every point-dependent
leaf across the page** when either authority's value deadline is due or
unknown. Nested object constructors retain their shape; source fields and
point-independent outputs at every depth stay intact. A whole point-read
value is itself a nullable leaf. Generated client types mark exactly those
maskable values nullable, not the enclosing constructed objects or stable
siblings. A masked decoration is a placeholder, not proof of absence. Page
freshness does not prove that every decoration is current. A refresh restores
values once a later deadline is proven.

The existing page-wide deadline does not identify individually expired
rows/fields. The online reply names static output paths once per page; local
clients derive the same paths from their compiled program. There are no per-row
or per-field deadlines. Both value deadlines are required on internal local,
search and online query results, through the final publication wrappers and
scheduler inputs; `undefined` is rejected rather than silently losing a refresh.
Every composition carries the earliest device
and server deadline separately; an unknown deadline dominates that authority's
merge. Loading/refusal results explicitly carry no value deadlines. Byte costs
and every result return site are recorded in the SJ Round 3 report; Round 4
closes the final local wrapper's compiler-enforcement gap and adds permanent
negative compile checks.
Explicit `null` means the evaluator proved
no upcoming decoration expiry; a missing deadline on a decorated reply means
unknown, not permission to retain its values.

Online watches continue value refreshes with bounded backoff (25 ms growing
to at most 1 second), without a give-up count. A server reply is accepted as
authority for its own clock: a past client estimate never rejects its page,
and a reply with no upcoming expiry ends the value retry. While the estimate
still makes a returned future server deadline uncertain, publish its page
with nulled decorations and keep refreshing. A successful reply can restore
values when their freshness is proved. Offline remembered answers recover
exactly like their bare form, retaining their cached confirmation age and
nulling expired/uncertain decorations. Local evaluation, timers, synchronous
snapshot access and approved facade holds apply the same value rule. Each
refresh uses a new attempt's meter and one server invocation, never a
constituent refill.

Source order keys use exact signed-i64 comparisons. Internal ordering hints and
source-key replies carry integers outside JavaScript's safe range as canonical
decimal strings; the SDK compares them with `BigInt` and writes canonical
numeric i64 cursor tokens without converting through `Number`. This does not
widen the public signed-53-bit numeric value domain. Storage-level and protocol
regressions cover larger keys defensively. Ordinary device query replies do not
build unused `searchRows`; retained candidate replies carry their exact source
keys in the already required bare rows.

Evaluate decorations only after selection. Share each distinct point key within
a page and authority domain, including misses; repeated fields and hops share
that read. This is request-local execution scratch, never a result cache or
search session. Source rules, field visibility, expiry and physical authorization
admission apply exactly as for ordinary point reads. Current server hits read
server rows; current device hits read under device authority. Departed hits use
only this device's lawfully held images, including retained decoration images.
Deleting a retained image makes its decoration null; a server deletion unseen
by a departed device cannot erase an image that its retention policy preserves.
No retained image grants server authority or causes a decoration server request.

The current page and its decorations use the page's one server invocation.
The SDK still applies the existing overlap suppression and consumed-prefix merge.
For lifted projections only, the bounded overlap request also carries each
candidate's source ordering value and whether another retained page exists.
These hints select which current projections to evaluate; they confer no read
authority. The server returns source identity/order separately from presentation,
so even a projection omitting those fields cannot change merge order or cursors.
It can leave unconsumed current projection slots empty. The device decorates only
retained hits emitted by the merge, in the existing final state-fence call.
That fence validates delivery/epoch after the point reads. New descriptors on
an old server fail explicitly rather than silently losing retained behavior.
A short page remains short; decorating it never refills either lane. Decoration
work is charged after page selection on the existing meter. Resource refusal
is explicit; exhaustion cannot masquerade as a missing row, trim the page or
manufacture a different successful completeness/cursor result.

Only point projections lift. Cross-hit aggregates, predicates or ordering that
read decoration values, and per-hit non-key subqueries keep the existing
evaluator. `N_SEARCH_SHAPE` identifies the unliftable portion; it does not imply
a retained/current guarantee for that shape. Explicit guards and membership
predicates keep their authored semantics. The bare form remains valid.

### 3.4 Viewer-owned keys: a partition proof, not a cached miss

Recommend a platform-maintained owner-key partition, selected explicitly on
the source. Lane OK implements this explicit syntax (see §3.4.1):

```text
-- within likes
sync public last 2000 by .at with own keys .principal
-- within reposts
sync public last 1000 by .at with own keys .actor
```

The exact spelling is for language review. The design decision is explicit
coverage policy, one source and one ordinary query body. Existing declarations
keep their existing sizes and meanings. The new social recipe uses this policy
by default; no heuristic recognizes a field just because it is called owner.

Initially admit only non-expiring public sources with a total unique key
containing the declared principal column, immutable key/owner fields, and
structurally proved caller-owned writes, as in these two builder tables.
The compiler checks those conditions and supplies the source owner index.
More complex row rules, inherited lifetimes and mutable ownership require
their own proof before this policy can accept them. `online only` opts out;
the compiler must not silently sync such a table.

For each principal, maintain every extant unique key in that principal's
partition, without a time horizon. No post body, media, timestamp or another
principal's key is needed. Reuse whole-partition snapshot/catch-up/watermark
publication. A complete empty partition is an affirmative proof of no keys;
a partial snapshot, reset, gap, failed persistence or missing generation is
not. Inserts/deletes of source and key projection commit together. Deletion
of the last key must still publish whole empty coverage.
The complete marker is principal-scoped. Local sign-out preserves the replica,
outbox and the owner's proof, as required by LLP 3000.011.003.000 §2. Reopening
offline as the same principal can still use that acquired proof. A different
caller cannot use another principal's partition to prove absence: its own
whole partition must have been durably acquired. Ordinary SDK store names
include the principal; even a custom opener reusing the same store cannot
lend the prior owner's proof. An explicit replica reset drops keys and markers
atomically; sign-out is not a replica reset.

An `exists likes[post, viewer]` can then consult this coverage when its raw
point is outside the public window. A present key proves existence; a missing
key proves absence only in the complete owner partition at its acquired
watermark. An offline answer remains stale relative to unseen remote writes.
This owner-key proof covers only the viewer's own keys: the owner expression
must be proved equal to the caller. `exists likes[post, other]` for another
principal retains today's unknown-outside-the-public-window result, even
when this device's own partition is complete. Neither presence nor absence
for another principal follows from the viewer's partition.
This proof certifies **existence only**: it cannot supply a row image, public
count, arbitrary predicate, retained media grant or mutation precondition
that needs fields the device lacks. Predictions overlay/invalidate the key
facts transactionally under the existing publication fences; an unpredicted
write stays a pending intent, never a fabricated settled key.

The compiler may implement the projection as a hidden table. It is platform
custody, so the builder removes `ownLikes`/`ownReposts` and restores the
original raw `postState` and `postCard` expressions. Schema adoption builds
keys from the existing store before publishing coverage; interrupted adoption
never exposes an empty completed owner set. The new capability must be fenced
from older device implementations rather than quietly yielding false answers.
Ordinary older applications and their explicit summaries continue compiling.

Alternatives considered:

| Alternative | Decision and reason |
| --- | --- |
| Remove the raw public horizons | Works for absence after whole acquisition, but sends every user's full rows everywhere; reject as the default. |
| Sync all viewer-owned raw rows as well as the public window | Sufficient and useful when offline row fields are needed; more payload/index/storage than this Boolean question needs. Consider a later explicit row policy. |
| Cache a server absence proof for each queried `(post, viewer)` | Reject here: arbitrary unseen posts remain unknown; introduces per-query negative facts, invalidation and cache custody excluded by NOT-DOING. |
| Complete viewer-key partition | Preferred. One watermark/coverage domain, all own keys, no request-shaped receipts; answers arbitrary keys, including never queried posts. |
| Automatically infer extra sync from every `exists` | Reject silent expansion of existing apps. Offer a checked schema policy and make it the recipe/scaffold default. |

The [owner-key pilot](../snapback4/experiments/p19-one-query/own-keys.q)
uses ordinary private horizon-free tables populated from `u0500`'s actual
keys on a copied store. Both runtimes return complete offline true and false,
keep an offline pre-delete true marked stale, then return false after syncing
the deletion. Three like keys and one repost key occupy **426 + 142 = 568
row bytes**. This shows that an ordinary private whole partition can answer
these Booleans; it is not evidence for the proposed public-source projection.
It does not exercise dual distribution, empty coverage publication, source
maintenance, automatic lowering, adoption, pending-write interaction or a
new wire capability.

## 5. What stays and what needs a deliberate extension

Authorization, expiry, server disclosure, the physical authorization-work
bound and logical meters are unchanged. A device's retained history cannot
grant server access. Server replies never echo client claims as authorization.
No current-membership predicate or explicit query refusal is bypassed.
Unknown scalars remain loading. `held` remains the instruction that a read
must never reach the server, including a cut or failed local proof, and
server execution still refuses it with `E_QUERY_HELD`.

Existing `historyHeld`, `searchHeld`, `searchInHeld`, guarded `searchIn`,
explicit `searchNewest` and maintained interaction summaries remain valid.
No forced source migration or new application-owned online/offline query
branch is introduced. The new owner-key
capability needs an ordinary coordinated upgrade; backward source compilation
does not mean an old device can interpret a new coverage proof.

The bare membership-audience word search deliberately changes behavior:
today's empty incomplete server answer becomes the compact membership page
for the admitted audience class, subject to the existing meters and cuts.
Any audience outside that class keeps today's plan and completeness behavior.
This is a result change, even though existing source keeps compiling.

This RFC does propose extensions to current boundaries: §3.3's ordered
mixed page composition and §3.4's platform projection with a narrower
distribution than its public source. Before implementation, record the
corresponding NOT-DOING move and account for schema, index, sync and custody
costs. Do not quietly call it existing support for multiple sync audiences.
Per-query result caches, durable search sessions, unbounded cursor state,
new authorization grants and JavaScript query execution remain excluded.

### Starter routes — Lane SR round 0, 2026-09-29

Calibration #26's essay and M3/M6/M8 diary identified an offline composer
blocked by unknown membership, transient resolver remounts and an online-only
DM alias. The changes here implement the author's SR commission; they do not
change SDK retention, delivery reporting, typing, media authorization or the
existing conversation/member/send rules. Failed send settlements explicitly say
“Not sent” with their saved text, Edit and Dismiss.

**DM identity.** The starter adds `directChats(owner, peer, conversation)` with
an immutable unique `(owner, peer)` index, `read <- .owner = viewer`, and
horizon-free `sync to .owner`. One atomic `openDirect(id, other)` transaction
first checks the caller's key, then inserts a conversation, its two memberships
and both directional keys if absent. The reverse participant therefore finds
the same ID. Server serialization and the unique index cover simultaneous
opens; the transaction never commits only one direction. The new table's insert
rule requires a conversation created in that transaction and the caller as
owner or peer. It has no update/delete operation.

Two directional keys are deliberate: they give a complete private viewer-keyed
partition without a public principal-pair directory, union sync audience, ordered
principal comparison, membership-dependent coverage proof or online-only key.
The cost is two small rows per pair. They survive leave and contain only IDs;
knowing the route does not restore membership or grant conversation/media access.
The existing invite/leave rules still govern memberships. No rejoin is implicit
in opening an existing DM. Conversation and history queries keep their existing
rules and delivered-history behavior.

`openDirect` is prediction-eligible with acquired coverage (LLP 3000.022 §14.3,
RY round one). Scope creation, memberships and directional keys predict together
on process and wasm devices; the server still selects the canonical winner.
Without the required coverage, durable custody keeps the proposed route until
settlement. The UI requires a complete,
non-revalidating absent lookup before creating, so an unacquired/slow/withheld
lookup never starts an attempt. An explicit `SELF_DM` refusal rejects self pairs.
No profile-existence read adds a horizon-dependent input to creation.

**Resolution and ownership.** Profile's Message action opens the DM resolver.
A current complete positive lookup navigates straight to its conversation ID;
a complete miss submits one minted conversation ID and one mutation ID with
`waitSeconds: 0`, then navigates at custody. Reopening a pending pair
recovers its original opening ID from `usePendingWrites` even without a
predicted lookup row. Before creating, it also awaits `client.pendingWrites()`;
the hook's initial empty snapshot does not prove an empty queue. A delayed
restoration therefore recovers the original opening rather than submitting
another. No effect resends an unknown write.
The conversation route carries `opening` (the write ID) and `other` while it
observes settlement and the replicated key. Recovered receipts can have no
historical result, so the ready non-pending key is the recovery path. The screen
uses Router `setParams` to replace the URL's conversation ID without replacing
its navigation entry; the opening ID keeps composer ownership stable. History
is keyed to the current conversation, and selected media/seen progress reset
when that ID changes. Backend/account reset still fences the owner. No protected
query answer is saved in application state or a ref. A draft and its attachment
stay through canonical-ID settlement; a send already queued against the losing
ID is not rewritten or resent, and may settle as Not sent with editable text.
When saving a send against a proposed ID, the starter atomically saves that ID
and peer with the intent in backend/account-scoped storage, before dispatch.
Opening and navigation alone need no journal association; the SDK and Router
already own their lifetimes. Thus successful, failed or abandoned openings without
sends leave no journal entries. A ready non-pending private key associates all
saved proposals for that peer with the canonical ID. A conversation screen mounts
at most one indexed `directPeer(conversation)` lookup to recover its own peer,
including on a bare canonical route after Profile, inbox navigation or reload.
It never mounts a lookup for every unresolved peer. Unrelated pending/recoverable
sends keep their associations until their own route is recovered or dismissed.
Every journal save prunes associations with no saved send; mounting a conversation
also prunes orphan entries left by older starters. Dismissing or observing success
of the last send removes its association, and an empty journal removes its storage
key. No age or count limit evicts an association still needed by a pending, failed,
restoring or unknown intent. These are route references only, never rewritten
admitted arguments or a resend loop. Canonical settlement does not interrupt an
admission already in flight.
The opening ID remains in navigation, including reload; it is a UI reference,
not a second outbox or a routing-authority grant.

transaction. There is no raw client insert operation. Any future writer must

returned IDs and a raw-store assertion that the losing conversation does not exist.
Leave/reopen checks current membership, inbox, protected content and send refusal;
the identity key survives without restoring access.
