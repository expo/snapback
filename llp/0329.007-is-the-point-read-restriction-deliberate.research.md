## Summary

[LLP 0329.006](./0329.006-why-writes-escape.research.md) established that a
declarative mutation plan can only read rows by primary key, and that this forces
74% of writes into JS handlers, forfeiting optimistic prediction and cold retention.
It left one question, which decides whether the finding is actionable:

> Is the point-read restriction a deliberate property of the atomic
> single-transaction host-plan model (LLP 0032 Phase 2, docket DK-1 leg E3), or is it
> simply unbuilt?

**Verdict: unbuilt.** No governing decision forbids a non-key read in a mutation
plan, and the executor already performs one — it just spends it on a delete instead of
binding the rows.

Confidence: high on E1–E4 (quotation and source), medium-high on the verdict, which
is an argument from absence of prohibition plus presence of machinery. I did not find
a document forbidding it; I cannot prove one does not exist somewhere in a 353-document
corpus.

## Findings

### E1 — The E3 ruling constrains read *timing*, not read *shape*

LLP 0032 Phase 2, leg E3, records the finding that produced Option A:

> host-plan `MutationPlan`s are *unconditional* write sequences that execute reads and
> writes in **one transaction** (`execute_mutation`) under the global instance mutex,
> so a server-captured read cannot be stale relative to the commit — there is no
> read-then-commit window to validate.

The argument is entirely about *when* a read happens relative to the commit. It holds
identically whether the read is a point lookup or an index scan: both execute inside
the same transaction, and neither can be stale relative to it. **Nothing in E3
distinguishes read shapes**, and Option A ("the client-supplied `read_set` is the
isolation mechanism") is a statement about who supplies the optimistic *baseline*, not
about what a plan may read.

### E2 — E3's premise has since drifted, unrevisited

E3 calls host-plan mutations "*unconditional* write sequences." That was accurate on
2026-07-02. The `guard` step and `get(..., { elseError })` first appear in
`packages/snapback-codegen/define.mjs` on **2026-07-09**, one week later, and a plan
carrying `guard(cond, elseError)` is conditional by construction.

E3 itself named the alternative it was choosing against:

> Detecting the intended conflict … needs a *client-supplied baseline* …, **or a
> redesign where host-plan mutations carry conditional read predicates.**

Conditional refusal arrived without that redesign being taken up, so the corpus
contains a ruling whose stated premise its own vocabulary has outgrown. This does not
invalidate Option A — the baseline argument stands on its own — but it does mean E3
cannot be cited as settling anything about conditional or non-key reads.

### E3 — LLP 0264 contemplates new step variants rather than closing the set

LLP 0264 §D-classification states the shipped `MutationStep` classification is closed,
and classifies `Get`, `Guard`, `Let`, `AssertCurrentRelation`, and
`AssertSourceChanged` as **non-writers**. Its rule for growth is procedural, not
prohibitive:

> A future `MutationStep` variant cannot inherit generic write authority from a
> wildcard/default match; it must be exhaustively classified or fail with
> `SNAPBACK_TABLE_WRITE_UNCOMPOSED_SURFACE`.

A read-into-binding step would be a non-writer, so it inherits no write authority and
satisfies the rule by being classified. LLP 0264 also confirms plan reads are already
transactional: "the executor then stamps/checks within the same transaction that
evaluates **plan reads**, guards, and writes."

### E4 — The executor already runs a filtered query inside a mutation

This is the decisive evidence. `crates/snapback-kernel/src/storage.rs`, executing
`MutationStep::DeleteWhere`:

```rust
MutationStep::DeleteWhere { table, filter } => {
    enforce_identity_binding_write_seal(&schema, table)?;
    let table = schema_table(&schema, table)?;
    let owner_field = generic_owner_write_field(table, GenericTableWriteFormV1::DeleteWhere)?
        .map(str::to_owned);
    // Reuse the query WHERE builder so DeleteWhere filters share
    // matcher/SQL semantics with reads (empty filter = clear).
    let scan_plan = QueryPlan {
        table_visibility: owner_field.map(|field| TableVisibilityV1::Owner { field }),
        table: table.name.clone(),
        filters: filter.clone(),
        membership_filters: Vec::new(),
        order: Vec::new(),
        limit: None,
        indexed_by: None,
    };
```

A mutation step constructs a **`QueryPlan`** — the read path's own type, carrying
`filters`, `membership_filters`, `order`, `limit`, and `indexed_by` — applies table
visibility, and evaluates it inside the authoritative transaction. The comment states
the reuse is deliberate: filters "share matcher/SQL semantics with reads."

Two consequences:

1. **Non-key access inside a mutation is not a new capability.** It ships. The only
   thing absent is a step that binds the matched rows for later steps instead of
   deleting them.
2. **Bounded work cannot be the rationale.** This scan runs with `indexed_by: None`
   and `limit: None` — an unbounded, unindexed table scan, already permitted inside a
   mutation. A bounded, indexed read would be *strictly cheaper* than what is allowed
   today.

### E5 — The conflict-validation machinery also exists

LLP 0032 leg E4 ("Predicate-granularity validation") **landed 2026-07-01**: the
Query-kind arm of read-set validation reuses the live matcher's
`query_dependency_change_may_affect`, so a captured query-shaped read is validated
predicate-granularly rather than at table granularity. A bound index read in a
mutation would capture a Query-kind dependency, which is the arm that already exists.

## What would actually be new

Being fair to the restriction, one obligation is genuinely new and is not discharged
by E4's `DeleteWhere` precedent.

`DeleteWhere` never returns row values. A read-into-binding does: the bound rows flow
into later step expressions and possibly into the mutation's return value. So a read
step needs the **read-side visibility composition**, not merely the owner-field write
check `DeleteWhere` applies — otherwise a mutation could exfiltrate rows the caller
may not read. That machinery exists on the read path (`table_visibility`,
`membership_filters`, and the generated visibility declarations of LLP 0080), but
wiring it into the mutation path and proving noninterference is real work.

That is a design obligation, not a prohibition, and it is the same obligation any read
plan already discharges.

> **Correction, 2026-08-28 — this section overstates the work.**
> [LLP 0329.010](./0329.010-cost-of-a-mutation-step.research.md) H5 traced the
> `DeleteWhere` arm past the `QueryPlan` construction quoted in E4 above: it calls
> `build_query_sql(...)` — the read path's own SQL builder, which calls
> `build_table_visibility_sql`, which handles **all four** `TableVisibilityV1` kinds
> including `Membership` and `AnyOf` — then `tx.prepare(&sql)` and **materializes
> rows** inside the transaction. So the visibility composition is not new machinery
> to be wired in; it is already present and already invoked from a mutation step.
> `DeleteWhere` passes `Owner` only because an owner write field is what a delete
> needs. What remains genuinely open is the *policy* — which visibility a bound read
> should compose, and the noninterference contract — not the mechanism.

## Consequences

1. **The restriction is unbuilt, not forbidden.** Every prerequisite ships: filtered
   evaluation inside the mutation transaction (E4), predicate-granular conflict
   validation (E5), a governance path for new step variants (E3), and an isolation
   ruling that is silent on read shape (E1).
2. **The highest-leverage fix in this family is therefore available.** LLP 0329.006
   measured the cost of the restriction at 74% of writes, a 19% optimistic-prediction
   ceiling, and the loss of cold retention for every application with a non-key
   invariant.
3. **E3 should be re-examined on its own terms.** Its premise — unconditional plans —
   is no longer true, and it explicitly named conditional read predicates as the
   alternative it was deferring.

This document proposes no design and authorizes nothing. The next step is an RFC under
LLP 0004's frame specifying a bound read step, its visibility composition, its work
ceiling, and its read-set capture — or a decision recording why the restriction should
stand, which the corpus does not currently contain.

## Open questions

1. ~~Should the bound read be a general `lookup(table, filter, bindAs)` or the narrower
   `unique(table, index, key, bindAs)`…~~ **Answered 2026-08-28 by
   [LLP 0329.008](./0329.008-coterie-plan-expressibility.research.md): the narrow
   form.** Measured against all 25 of `coterie`'s mutations, `unique` alone closes
   40% — not a majority. The general bounded read closes 56%, and adding a
   `count(binding)` expression and letting `insertEach` iterate a binding reaches
   100%. All four are the same primitive at different `take` values, so the narrow
   form is an increment rather than the fix.
2. Does binding read rows into a mutation's return value create an authorization
   surface distinct from the read path's, given that mutation results are not
   subscribable?
3. Does lifting the restriction move the measured escape rate? LLP 0329.006 F2 shows
   that widening the plan vocabulary in July did *not*, so the prediction that this
   change would is itself a claim requiring a rerun rather than an assumption.
