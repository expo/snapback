## 2. Retain by default

Every release activation (deploy and rollback) retains removed durable application tables, columns and index definitions in SQLite-owned dormant storage within the same activation transaction. The active r/i image remains an exact projection of the active schema. Dormant data is outside that namespace and unavailable to programs, rules, references, queries, sync, SQL application projections and clients. Operator inspection may enumerate it. Reintroducing a dormant name deliberately reactivates its data, after full validation under the candidate schema. This applies to deployments as well as rollback; a rename remains two names, without an inferred data move.

Dormant whole tables store their row images; dormant columns store values keyed by table/column/row id and their definitions. Capture interpreted literal defaults and optional nulls when a column becomes dormant, preserving the value existing rows actually saw. Keep index definitions as history; preserve their data logically and rebuild physical keys on reactivation from current rows. Dormant indexes are never consulted for active writes, uniqueness or caps. Thus a new duplicate under the older release can precisely refuse forward activation. Derived rows are caches and are rebuilt, not authoritative history. Retention must precede existing derived-state retirement. An unsupported durable-to-ephemeral conversion refuses rather than silently discarding stored data.

Restoration, candidate validation, derived rebuild, catalog/generation/programs and current release commit together. Any error rolls all of them back. Retained values overwrite no explicit candidate writes: restoration precedes activation builders. Incompatible name reuse must pass candidate types and constraints; no flag bypasses validation.

## 3. Older writes and incompatible values

Updating an active row while its newer columns are dormant preserves those dormant values. Deleting that row deletes its dormant column values in the same transaction: forward never resurrects a deleted row, including when its id is reused. New rows written under the older schema have no dormant value. On forward they receive the candidate literal default or optional null; required columns without such a default refuse with exact missing-row counts and up to five ids. Contextual now/viewer defaults do not invent historical values. Existing required-column backfill rules still apply.

Enum narrowing with values in use REFUSES. Hiding a row could hide an authorization parent or membership, change cap/unique populations, or leave a surviving reference without its target. No silent fallback, row hiding or coercion is sound generally. E_ADOPT must report table.column, incompatible values, total affected rows, at most five ids and the exact repair/inspection command. Repair using the current release's authorized operation, then retry rollback; --allow-destructive never bypasses enum validation. An unused newer enum variant remains in immutable release/history definitions and is available again on forward.

For every data-dependent refusal, aggregate count and bounded samples at the failed column/index/constraint, without unbounded row retention. Include actual conflicting values for column failures, index name and conflicting keys for unique failures, and actionable command or schema repair. No claim that a green read-only preview freezes later writes: adoption rechecks under its transaction.

## 4. Explicit pruning and audit

snapback4 prune <dir> lists dormant tables, columns and indexes with counts and at most five ids; it changes nothing without --allow-destructive. With that flag it permanently deletes exactly the currently dormant storage in one writer transaction, records a durable prune event, and leaves active rows/programs untouched. It releases dormant asset homes for the ordinary collector. Deploy/rollback --allow-destructive do not prune; direct users to the separate command. After prune, reintroducing the schema gets empty tables and normal required-column/default behavior. Pruning is an irreversible operator action; the command output names every item dropped.

Release activation events live in the database transaction with release/previous/generation, timestamp and retained/restored summary. Prune records its item summary in that transaction. Existing releases.jsonl and current remain checked convenience copies; post-commit filesystem errors explicitly say activation succeeded. History is never edited or rewound. Rollback picks an earlier immutable source, not a historical data snapshot.

Dormant asset homes remain live in the asset ledger but are unreadable because the active schema has no home. Active-row deletion also retires any associated dormant asset home. Dormant rows do not run old expiry or jobs while dormant; candidate liveness applies again upon reactivation. Explicit application deletion and ordinary active expiry still mean deletion, not an undo archive.

## 5. Hot activation and ownership

serve owns the database sidecar for its lifetime and publishes a Unix-domain release-control socket in the private deployment directory (directory 0700, socket 0600). Only the host filesystem owner has this capability; it is not an HTTP door, browser origin, bearer service seat or remote endpoint. Check filesystem objects before replacing a stale socket; never follow symlinks or replace a regular file. Commands hold a separate private command flock while allocating/staging immutable release source. They acquire the store owner when stopped; E_STORE_BUSY with a running serve uses the local socket instead of opening another writer. Dev and an older/unreachable server continue to refuse with an exact stop/retry command.

A bounded command message identifies the owned database inode/canonical identity, candidate release id, expected current release, operation and explicit flags. The server compiles only its own immutable release directory, prepares native module/worker prerequisites before commit, then holds its existing engine writer guard for activation and in-memory publication. The server verifies expected current release inside the activation transaction. Concurrent commands serialize on the command flock; out-of-band stale commands fail compare-and-swap. No request may choose arbitrary filesystem source. Compilation/validation failure leaves the previous engine, bound schema, native module, worker revision and reader factory unchanged.

A query already running in a pinned SQLite read transaction finishes on its old snapshot and reports that generation. A writer already executing finishes before activation obtains its engine guard. Queued writers recheck current generation and authority; they may refuse E_GENERATION and must never execute old IR against new storage. Fresh requests after publication use the new engine; a stale pooled reader not yet pinned retries through the replacement factory. Swap bound/generation in the existing /schema guard order, retire pooled readers, rebind ephemeral state, invalidate change answers, wake sync/polls and update worker revision while holding the writer guard. Workers restart using the candidate packaged source and native continuation hashes keep the existing conservative parking policy. Long validation can pause writes; hot means no process restart, not an unbounded zero-pause latency promise.

The database is authoritative at crash or lost socket reply. Timeout/EOF after sending a command reports an ambiguous result and instructs inspection of current and durable history; never silently resend as a new release or claim failure left the old release active. Restart attaches the database-selected release even if current's convenience copy is stale. After database commit, publication is infallible in-memory assignments; fallible native/worker preparation happens before commit. Filesystem-copy failures report the committed result.

## 6. Devices and partitions

Every changed activation including A→B→A gets a fresh monotone semantic generation, never reuses a release number as a generation. Program/schema hash equality retains the current generation under the existing protocol. Rollback and forward use the same generation replacement and full partition reacquisition already used by adoption: /schema advertises the exact active shape, sync rejects old watermarks, devices clear obsolete base/index state and rebase or refuse their queued intents under the existing authority/operation contract. Store id remains unchanged; this is not a store replacement. No dormant rows or fields enter snapshots, partition logs, online answers or device stores. Never combine old-generation pages with a new backend. A late old read remains tagged old and cannot overwrite a newly observed generation. Simulate rollback/forward across a delayed sync page and audience changes; retained data changes server storage only, not device persistence formats.
