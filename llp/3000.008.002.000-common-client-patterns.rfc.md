## Summary

Make the ordinary client implementation preserve a user's draft, admitted
write, navigation and media interaction through temporary read gaps,
reconnects and component remounts. Do this without retaining unauthorized
results, inventing successful settlement, or building a second outbox.

Revision 1 was right about the principles and the responsibility split, and
wrong about three facts that would have aimed the work at the wrong place
(§10 records the reviews). First, its one concrete receipt rule inverted the
benchmark brief. Second, most of the "temporary read gaps" were produced by the
client's own prediction fence, not by the network. Third, the builder in the
evidence worked from the package README, `CLIENT-AND-OPERATIONS.md` and the
`guide` cards on the Expo tier, and several of its mistakes were copied from
those published examples. The web starter the first revision targeted already
has most of these patterns.

So the increment is: correct the paved docs and add the missing `guide client`
entry point; name the fence where it bites (the `reads` card, and a `check`
note where one can be precise); give admission its own boundary in the SDK;
and bring the Expo starter up to the web starter's per-intent outcomes. Runtime
guarantees stay in the SDK, presentation in starters, receipt policy in the
application schema. No read-retention law changes here.

## 2. What already exists, and what must not change

Orientation snapshot: `origin/main` at `0badac9872`, plus LLP 3000.017 on
`sb4/eph-integrate`. The paved client surface is
[CLIENT-AND-OPERATIONS](../snapback4/packages/snapback4/CLIENT-AND-OPERATIONS.md).
It already exposes `useMutation`, `usePendingWrite(op, id)`, `client.write(id)`,
`onWrite`, `useAcquisition()` and `useNow(deadline)`. Same-id retries with
changed input are refused (`E_WRITE_ID_REUSE`), and a missing aggregate is
already `loading`, never zero. `createApp` owns admission/recovery journals;
the local device owns its outbox. Predicted rows carry `pending: true`. The web
starter (`init --web`) already saves write ids before dispatch, observes each
intent separately, distinguishes unknown outcomes and opens rooms by a held
lookup instead of creating them.

These laws stay: `sent` with `replayed: true` carries no historical result; an
evicted receipt is unknown, never failed; no fresh id to recover a lost
acknowledgement; account isolation; loading is not empty; no protected-result
cache. The query publication rules of LLP 3000.016 §2.2 (Rules 1–5 in
`local-query.ts`) are documented here, not relaxed (§4, §9).

## 3. Submit once, then let the user continue

The composer separates three events: durable local admission (custody),
authoritative settlement, and observation in the authorized read.

- **Admission is its own boundary.** A device's `mutate()` returned only at
  settlement or after 4 s online, although admission took milliseconds (Astra's
  probe: admitted at 2 ms, returned at 4,002 ms), so a composer that awaited it
  stalled on a slow link. `MutateOptions.waitSeconds` (0–25, clamped like
  `ActOptions`) bounds that wait; `0` returns at custody with `pending` or with
  the refusal that prevented custody. Omitted keeps each tier's default.
  Custody is the device outbox, `createApp`'s online intent journal, or the
  online client's memory queue. The React write hooks take the same options:
  `run(args, { waitSeconds: 0 })`, and `run(args, { id })` for an id saved first.
- Clear the field at submit, as chat apps do, so the submitted text never
  remains and text typed meanwhile is plainly new. If the outcome is `failed`
  (nothing was kept), give the text back: into the field when it is still empty,
  otherwise on the refusal row with **Edit**, which appends rather than
  overwrites. A save that fails before dispatch says "Not sent: could not save it
  on this device; your draft is kept." (Revision 2's "clear exactly the
  submitted revision after custody" deleted a retyped draft that happened to
  start with the same text — Astra's code review; §10.) Send is disabled only
  while that submission is being admitted — never because an earlier write is
  `pending`, which lasts until terminal settlement.
- Display the admitted intent immediately. Predicted rows carry `pending: true`
  ("Sending…"). A write that queues without a row has a `reason`; show a
  labelled pending item, never a fabricated server row.
- **Per-intent outcomes.** `useMutation`'s `last` is the latest call's outcome
  by design, so a refusal of an earlier send disappears (Astra reproduced it in
  Chromium against the Expo starter's single `usePendingWrite(api.send)`). The
  paved form saves `{ id, … }` in account-and-backend-scoped storage before
  dispatch and observes each with `usePendingWrite(op, savedId)`: `failed` shows
  the refusal with the saved text to edit; a retry is a new intent with a new id;
  `sent` leaves the list, and the row carries it. `usePendingWrite` reports
  `restoring` while it looks up a saved id's recorded outcome, so a row reads
  "Saving…" while its own submission is admitted and "Checking…" while it is
  looked up; only then is a missing receipt shown as unknown — with its text and
  Dismiss, never resent.
- Correlate presentation by a declared identity, never by matching text or
  time. Pending presentation and saved drafts follow the account/store isolation
  contract; an account switch cannot display another account's text.

This remains composition plus one SDK boundary and one hook field
(`restoring`). An SDK view over the durable outbox (pending and refused intents
with their arguments) would remove the saved-intent journal from every app; LLP
3000.019 P3(4) proposes it (§9); it is not built here.

## 4. Stable UI ownership, honest read boundaries

**The client's own fence produces most read gaps.** While this device holds a
predictable pending write to a table a query reads — or a write whose predicted
footprint is unknown, which blocks every query — the query asks no server
(`local-query.ts` `blocked()`/`recover()`). What the screen then shows depends on
the device's own answer. An answer the device **withholds** stays `loading`
(test "rule 3: engine-withheld prediction"); a **partial** answer stays local
partial data (`complete: false`). What makes the device withhold a whole answer
was measured on real devices (lane L3, §7): a streaming total or extremum
(`count`, `sum`, `min`, `max` over a domain or a page) whose input crosses the
sync horizon, and a point read — a quoted message, a joined row — that misses
past the horizon. An order that differs from the window's order alone yields
partial data. Writes to unrelated tables hold nothing. A local observation
keeps its previous answer only during a server fetch, and drops it at any local
commit; every local commit also re-runs live reads from `loading` (LLP 3000.019
§3.3). `usePage` then returns `items: []`. So an app's own typing,
acknowledgement and send writes blanked its own screens, and effects in list
rows re-fired. The `reads` card said the opposite ("an unavailable ordinary
device read asks the server while online even with pending writes"), and
`check` named no affected query. This RFC does not relax the fence — LLP
3000.019 P3 proposes keeping answers across same-authority commits — and ranks
prevention above survival:

1. **Prevent.** Keep a screen's query one the device can complete: no total,
   extremum or point lookup over data past the sync horizon inside it (check with
   `snapback4 why <query>`). Put a server-needing decoration — an unread total
   over history past the horizon, a quoted message older than the horizon — in
   its own query, so the screen's list never waits on it. The `jobs` card's own
   `inbox` example embeds such a total; it changes with this RFC. A `check` note
   naming these queries is feasible (L3 found sound risk predicates) but was not
   shipped: it would truthfully fire on that card, so the card changes first.
2. **Survive.** The signed-in tree follows session validity (`useAuth().state`),
   not a profile query: decide the first route once; after that a `loading` read
   never unmounts the signed-in tree, a route or a draft. Keep headers and
   composers mounted through `loading`; rows follow the current read — never a
   previous answer. Keep effects out of list rows.
3. **Stay honest.** Loading and authority loss differ. Revocation and sign-out
   still hide protected content and fence late responses; preserving a component
   is not permission to retain its last protected result. A missing unread total
   says unknown, not zero, and does not remove the conversation. A business
   decision that needs one consistent authorized snapshot stays one query.

## 5. Acknowledgements are schema and recipe, not an SDK hook

**Receipts follow the brief.** For Clique the recipient set is membership at
send time, and "members who leave or are removed before reaching a state drop
out of the aggregate requirement" (`benchmarks/briefs/social-messenger.md`
~500–507); members who join later never enter it. The calibration app
implements exactly that. Grader d-01 quoted only the first clause; revision 1
followed the grader and is withdrawn here. Removing someone from aggregate
eligibility is not recording that they read.

The paved recipe is `main`'s `receipts` card (`snapback4 guide receipts`),
reviewed in its own program: per-member ordinals and runs, `delivered` and
`seen` mutations, and a `useReceipts` hook that owes what it fetched. The client
card points to it and keeps only the lifecycle rules below; an earlier draft of
the client card's own receipt recipe was withdrawn so the guide has one.

- Progress is server-owned, monotonic and per member (an ordinal written by an
  authorized, idempotent mutation); the aggregate is the minimum over the
  remaining recipients. An acknowledgement from a non-member is refused, not
  silently ignored (grader d-02).
- "Read" means the recipient viewed the conversation: acknowledge when the
  conversation is open and the app is foregrounded — not per rendered row. A
  per-message-visibility policy, where one exists, must not advance across
  unloaded or unread gaps; the SDK cannot infer either policy from a maximum id.
- Remember the progress you sent only after `run` returned a non-failed outcome,
  in a ref above the list keyed by account, backend and room, so a refetch or
  remount never re-sends it. Across reload, rely on server progress and the
  existing write recovery.
- Start background delivery reporting (the receipts card's hooks with
  `visible: false`) only after `useAcquired()` is true; deferring them took
  calibration 21's cold acquisition from 69.9 s to 5.6 s at 100 conversations.
  LLP 3000.019 P7 would make delivery a server fact and retire this.

No SDK visibility or watermark hook is built. A reusable hook is extracted only
if the recipe, once published, is still repeated machinery in a cold build.

## 6. Ephemeral activity and media interactions

Typing uses [ephemeral tables](./3000.017-ephemeral-tables.rfc.md), which own the
wire, authority, renewal and coalescing, and bypass the outbox and prediction —
which also removes the largest fence source in §4. Carry through its
separate-query rule: joining typing into the inbox would move the whole inbox to
the server and break cold-offline behavior. The binding stops on idle, route
exit, account change and host backgrounding; offline activity is dropped, never
replayed.

A one-view media viewer owns its `client.asset(id)` handle above transient list
rows, keyed by account, message and asset, so refetching or recycling a row
cannot consume or lose it. Lifting it must not drop the revocation coupling that
unmounting used to provide: Astra's probe showed a held one-view blob still
readable after the server revoked it, until `revoke()`. So the viewer observes
its message row and closes and revokes when the row is gone (`data: null`),
denied, tombstoned or past its deadline — not on `loading`. It revokes on
unmount and account change, and never fetches a one-view asset twice. The
existing media API suffices; no media cache or handle extension is proposed.

**2026-09-29, AV: ordinary author avatars and hook ownership.** A DM/group
bubble may read `profileById(message.sender)` and pass `profile.avatar.id` to
`useAsset`, independently of a feed or chat list resolving the same id. The
profile's home-row rule authorizes serving (LLP 3000 §7); neither the observation
nor the message carries an additional grant. Profile replacement releases the
old upload. Leaving a conversation does not revoke a public profile's avatar;
it still revokes private message media. Retention remains receipt-bound under
LLP 3000.019 §3.5, and one-view assets keep the explicit-open ownership above.

The hook binds every resolved outcome to one selection of client identity,
the signed-out bit and asset id. A change hides the preceding outcome in the render itself, before
effect cleanup; reselecting an id after clearing it starts a new selection.
In-place sign-out returns actionable `E_AUTH` without fetching and releases the
held URL. Late obsolete downloads release their handles and never publish.
The live client owns one credential scope: app account changes replace its
facade, and a raw client ends that scope on sign-out. An online bearer may have
`viewer() === null` before its first query discovers the principal; that is not
sign-out. The hook follows the explicit `signed-out` link state, so discovering
the viewer or going offline cannot consume another one-view fetch.
No promise or URL is shared between hook mounts, and no new asset grant or
client-contract field is introduced. Round 1 adds the bounded retries below. A controlled React
regression first fails on the old code's commit of the old URL under a new id.

Round 0: calibration #26 d-02's claim of permanent `loading` did **not** reproduce with
the supplied seven-file Quarry program: both published 0.4.8 and this checkout
resolve and paint the exact profile/avatar pattern on online, process and wasm.
The supplied frozen Expo export also paints DM/group avatars with recorded
`ready` hook states. Thus the render-time ownership fix is a separately proved
defect, not an established explanation or closure of d-02. The original failing
store/browser trace is needed to establish that report's cause. `guide media`
now gives the complete author-avatar pattern and distinguishes profile loading,
empty assets and actionable refusals instead of concealing all with initials.
Evidence and qualification limits:
[`AV report`](../snapback4/reports/20260929-av-asset-resolution/REPORT.md).

**2026-09-29, AV round 1: transient failure recovery.** The supervisor's
mechanism reproduces on published 0.4.8: one reset or admission 503 leaves
`useAsset` denied permanently for that selection; a hung download stays loading
past thirty seconds. A later mount can resolve the same id. The builder hides
all non-ready states as initials. Current main's FU admission retries repair
an isolated 503, but not a reset or hung request; a forty-request burst can
still exhaust them. This reproduces the mechanism and visible symptom, not
proof that those failures occurred in the original grader session.

A full-file `Range: bytes=0-` request is safe to retry: the server authorizes
each attempt and refuses any Range on a once asset before consumption. No
schema guess, copied id or stale device fact establishes retry safety. An
explicit `E_ASSET_RANGE` switches to the one non-range fetch; only an explicit
retryable admission refusal proves that fetch may be replayed. An ambiguous
once failure has `retryable: false`, including a failed body or Blob conversion.
Missing, revoked, consumed and authorization refusals stop immediately.

Safe downloads have four attempts, exponential backoff from 250 ms with up to
25% positive jitter and ten seconds maximum backoff. Round 3 separates observable
streaming inactivity from opaque transfer time. After headers, five seconds
without bytes ends a streaming attempt; only nonempty chunks renew it. Healthy
streams have no total-duration deadline. A streamless Blob instead allows
60,000 ms plus Content-Length / 32 KiB/s, rounded up to milliseconds. Missing or
invalid length uses 64 MiB (the server upload ceiling), and larger lengths are
clamped there: at most 2,108,000 ms (35 min 8 s). A generic fetch may expose
headers only after buffering the whole body. Before that promise resolves,
its capability and size are unknown, so it receives the same maximum allowance.
This deliberately also delays detecting a fetch that never produces headers;
a five-second first-response bound cannot distinguish those hosts from healthy
opaque downloads. No native progress API or native-device qualification is
claimed. Refusal bodies remain bounded to five seconds once headers arrive.

Queue/backoff time has a separate cumulative thirty-second allowance, excluding
active transfer time; real byte progress replenishes it. Empty chunks replenish
neither timer. Calls remain bounded even when a host ignores abort, and explicit
client/session cancellation interrupts opaque waits immediately. Regression
coverage requires real six-second buffered HTTP images to reach ready and paint
for ordinary and once hooks, both completion-only fetch and streamless Blob.
Size-aware deadlines are checked with virtual time past thirty and sixty seconds;
empty-chunk streams must cancel and exhaust exactly four attempts.
Retry-After is captured as an absolute deadline at response headers, before
reading refusal JSON. A stalled or malformed body preserves that deadline and
HTTP status, without inventing an explicit admission refusal that could replay
a one-view transfer. Valid E_RATE_LIMIT envelopes keep their admission meaning.
Guidance exceeding the wait budget ends the call and suppresses early hook
recovery. Credential rotation returns that same refusal and deadline; it cannot
recurse into a fresh admission budget, including rotation during backoff.
Permitted recovery uses current credentials. Local queued calls that stopped
before dispatch may retry E_AUTH after rotation, without invalidating retained
bytes or handles. Completed bytes remain usable across bearer rotation for the same known
principal, without another GET; a local facade has one fixed principal. Unknown
principal, sign-out, close, store replacement or restoration still fence obsolete
results. Local downloads wait for an active refresh after media reconciliation,
before capturing credentials, so an intermediate revision cannot send the old
bearer or invalidate retained bytes. An ambiguous once failure never replays. Each client admits six transfers through body completion;
no handle, response or authority is shared between callers. Close aborts queued
and active work; retries recheck session/store lifetime. Local calls reconcile
media expiry before waiting on network/backoff. Late host responses
are disposed. A host fetch ignoring abort can outlive the SDK deadline, but
cannot publish or retain its result. SDK queue/transfer deadlines are E_CLIENT,
not evidence that the network is offline; they neither drop the local link nor
invalidate retained media. An actual socket failure remains E_OFFLINE and permits
the existing offline cache fallback. If the shared queue/backoff budget ends,
the preceding refusal and its absolute Retry-After survive unchanged. Post-body
retention or display failures are E_CLIENT too, retryable only after a ranged
(non-consuming) transfer. One-view construction failures remain non-retryable.

`client.asset` preserves `{ denied: why }`. `useAsset` distinguishes transport
and local construction `error` (with code/message) from authorization/revocation
`denied`. Only safely retryable errors restart on reconnect, browser online,
refocus or visible-document return; ready handles and terminal refusals never
restart. A recovery event before Retry-After schedules one attempt at the
deadline; one received while busy waits for the outcome and retries only a safe
failure. Events coalesce; cleanup cancels the timer. No event means no new
automatic retry loop. Raw callers may invoke `asset` again after connectivity returns.
`assetSource` remains a host-managed URI and has no SDK transfer queue.
Ordinary full-file 206 responses may enter the existing receipt-bound cache
only when Content-Range covers exactly the body and total length; partial
ranges confer no retention authority (LLP 3000.019 §3.5).

Review corrections: outcomes also carry an effect-lifetime token invalidated
on cleanup, so React Activity cannot reveal a revoked handle. Dispatch is
microtask-deferred and checks liveness, avoiding StrictMode's discarded initial
setup consuming a view. Tests resolve the current request before the obsolete
one to prove a late completion cannot overwrite readiness. A one-view viewer
still belongs above transient/hidden rows and explicitly owns its open lifetime.
Evidence: [round-1 report](../snapback4/reports/20260929-av-asset-resolution/round1/REPORT.md).
