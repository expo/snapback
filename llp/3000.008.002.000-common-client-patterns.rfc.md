## Summary

Make the ordinary client implementation preserve a user's draft, admitted
write, navigation and media interaction through temporary read gaps,
reconnects and component remounts. Do this without retaining unauthorized
results, inventing successful settlement, or building a second outbox.

Charlie requested this proposal after discussing the 0.4.2 Clique diary.
The proposal extends the implemented client and starter work rather than
reopening their guarantees. This commission is to author the RFC; it does
not accept the design or commission implementation, publication or reviews.
No API name below is a promised new export.

The hypothesis is that the remaining common mistakes can be removed mainly
by better composition of existing APIs, with focused SDK additions only
where an application cannot safely own the lifecycle. Success is fewer
application workarounds with the same authority and durability guarantees,
not fewer visible states at the cost of truth.

## 2. What already exists, and what must not change

Orientation snapshot: `origin/main` at `0badac9872`. The current paved client
surface is [CLIENT-AND-OPERATIONS](../snapback4/packages/snapback4/CLIENT-AND-OPERATIONS.md),
especially its write, acquisition, session, expiry and pending-write sections.
It already exposes `useMutation`, `usePendingWrite(op, id)`, `client.write(id)`,
`onWrite`, `useAcquisition()` and `useNow(deadline)`. `createApp` already owns
admission/recovery journals; the local device owns its outbox. This proposal
must not announce those mechanisms as missing or add competing retries.

The parent's §2 preserves execution-only replay: `sent` with `replayed: true`
does not carry a historical result. Receipt eviction or lost evidence can
leave an outcome unknown. Never infer success from an empty pending list or
mint a fresh ID merely to recover a lost acknowledgement.

The starter LLP §2 binds intent metadata to backend and principal and
separates settlement from replica observation. The Following contract may
withhold a whole shaped query when a required card is unavailable. This RFC
does not change that contract, treat loading as empty, or create a stale
protected-result cache. A newer unpublished branch must be assessed against
these requirements before duplicating work already in progress.

## 3. Submit once, then let the user continue

The default messenger composer separates three events: durable local
admission, authoritative settlement, and observation in the authorized read.

- Before admission succeeds, preserve the draft. Failed storage or admission
  leaves it editable with a retryable error; a click alone is not durability.
- After admission, clear only the submitted draft revision and allow another
  send. Text entered while admission was pending must survive. Repeated clicks
  on that same revision refer to one intent; a deliberate next send is new.
- Display the admitted intent immediately. Prefer the actual predicted row;
  if no row exists, show a clearly labeled local pending item, not a fabricated
  server row or predicted return value. It grants no media or data authority.
- Correlate pending display and observed row by a declared stable identity,
  never matching text/time. If the current API cannot supply the mapping,
  choose an explicit application key in the recipe or design the minimal SDK
  support before claiming duplicate-free presentation.
- Preserve terminal refusal with retry/edit affordances. A transport retry
  uses the same write ID and arguments through the SDK. Edited content is a
  new intent only after the old outcome is resolved or its uncertainty is
  explicitly presented; never silently resubmit a possibly committed send.
- On reopen, observe the original ID through existing recovery. Do not promise
  indefinite terminal receipt history. When the receipt is unknown, present
  that fact and use a newly authorized lookup where the app has a stable key.

This is initially a composer/starter composition, not a generic replacement
mutation API. Add an SDK primitive only for a reproduced lifecycle gap.
Pending presentation and saved drafts follow the existing account/store
isolation contract; account switching cannot display another account's text.

## 4. Stable UI ownership, honest read boundaries

Keep route identity, draft state, selection and viewer ownership above the
read boundaries that can temporarily become unavailable. An authentication
boundary responds to session validity; it must not interpret a temporarily
loading profile query as sign-out or replace the entire navigation tree.
A route to a locally known conversation should use the starter's existing
held-navigation path, not rerun a create operation on every visit.

Loading and authority loss are different. Keep generic layout and permitted
user-owned state during a read gap; render protected content only from a
currently permitted read state. Revocation and sign-out still hide protected
content and fence late responses. Preserving the component is not permission
to retain its last protected result. Offline authorization limits remain the
engine's existing limits, not a new promise of instantaneous offline revocation.

Independent decorative reads belong behind their own boundaries. A missing
unread count should say unavailable, not zero, and should not remove the
conversation. This does not mean automatically splitting every query: a
business decision that requires one consistent authorized snapshot stays one
query. The recipe distinguishes decoration from required data and exposes
`complete` and `fresh` where they affect a user action.

## 5. Acknowledgements follow visibility, not rendering

Provide one tested visibility-to-acknowledgement recipe, then extract a hook
only if it removes repeated lifecycle machinery. A mounted row is not proof
of visibility or reading. Foreground state, actual visibility and the app's
receipt policy decide when a read acknowledgement is eligible. Delivery and
read receipts remain separate.

For an application with a monotonic server-defined ordering, coalesce a
contiguous observed prefix into a watermark. Do not advance across unloaded
or unread gaps. For sparse visibility or unordered data, use explicit IDs
instead. The SDK cannot infer that a maximum visible ID means all earlier
messages were read. Never use wall-clock timestamps as a total-order shortcut.

The reusable lifecycle remembers admitted progress for its backend, viewer,
room and policy, preventing remount/refetch loops from generating equivalent
writes. Across reload it uses existing write recovery and server progress,
not another durable queue. Server operations remain authorized, monotonic
and idempotent under retries and multiple devices.

The server schema must state whether aggregate receipts use recipients at
send time or current membership. The helper cannot silently change that set.
For Clique, test the send-time contract from the brief; leaving must not
magically count as reading. This requirement follows the grader's finding,
not the earlier diary's provisional interpretation of retained history.

## 6. Ephemeral activity and media interactions

Typing uses the proposed [ephemeral tables](./3000.017-ephemeral-tables.rfc.md),
not a durable expiring-table recipe presented as equivalent. That RFC owns
the wire, authority, renewal proof and coalescing rules. In particular, do
not coalesce arbitrary mutations as though all were replaceable state.

The activity binding stops on idle, route exit, account change and host
backgrounding where the host exposes it. A withdrawal is best effort; TTL
handles abrupt death. Offline activity is dropped, never replayed. Reconnect
requires current activity rather than replaying a stale typing flag. Test
that an in-flight old renewal cannot resurrect activity after a newer stop
within the ordering guarantees chosen by LLP 3000.017. Until implemented,
the guide must identify the durable workaround's different semantics.

A media viewer owns its interaction above transient list rows. Refetching,
reordering or recycling a row must not reopen or lose the viewer. Use the
existing media custody API and its permitted handle lifetime; do not copy
one-view bytes into a general cache or fetch them again on remount. Expiry,
revocation, consumption and sign-out continue to apply. Offline expiry and
cache behavior must be tested under the existing contract, not inferred from
component survival. If the current media API cannot sustain a legal viewer
session across list invalidation, propose that narrow extension separately.

## 7. Delivery sequence and ownership

1. Reproduce the diary scenarios with the existing client and latest starter.
   Record which now pass; concurrent receipt/presence work may already fix them.
2. Correct the default chat starter and its guide together using current APIs:
   composer admission, stable route boundaries, optional counts and viewer
   ownership. Keep one canonical example instead of competing recipes.
3. Extract only demonstrated reusable lifecycle code for acknowledgements or
   submission. Specify any missing durable identity/receipt boundary before
   adding a hook. Preserve headless behavior and generated types.
4. Adopt LLP 3000.017's activity binding after its implementation is qualified.
   Do not duplicate its ephemeral engine work in this proposal.
5. Exercise a cold builder on the published package and starter, including one
   subsequent change to the app. Record required workarounds and their causes.

Runtime guarantees belong in the SDK; layout and intent presentation belong
in starters; receipt product policy belongs in the application schema. No
new global readiness gate, query-result cache, retry queue, router framework
or second client state machine is proposed. API names and implementation
ownership remain open until the concrete gaps in step 1 are established.

## 8. Acceptance and measurement

Use the simulator for ordering, loss, retries and multiple owners; use an
actual browser for IndexedDB, route reload, visibility and list lifetimes.
Native backgrounding, process death and viewer behavior require a native
witness; a Hermes export alone is not runtime proof. Add scenarios to the
existing suites, not a new standing gate or registry.

| Scenario | Required outcome |
| --- | --- |
| Storage rejects admission while the user keeps typing | Submitted and newly typed content survive; no falsely durable pending item |
| Three offline sends, then reload and reconnect with a lost acknowledgement | Three distinct intents; one authoritative execution each; stable pending-to-row presentation; no draft loss |
| Hard navigation immediately after admission | Existing recovery observes the same ID; no application resend loop |
| Repeated read gaps during typing and receipt updates | Route and permitted draft survive; protected content follows actual read state; no duplicate acknowledgement storm |
| Sparse visible messages, then remount and scroll | No watermark crosses an unread gap; equivalent admitted progress is not resent indefinitely |
| Recipient leaves without reading | Aggregate follows declared recipient policy, including Clique's send-time set |
| Cold offline conversation with unavailable aggregate | Conversation remains usable where authorized; badge is unknown rather than zero |
| List invalidation while viewing a one-view image | Legal viewer session survives; no second consumption or unauthorized byte retention |
| Sign-out/account switch with callbacks and admitted work in flight | No cross-account draft/result exposure or stale callback adoption |
| Typing burst, disconnect, idle, reconnect | Durable outbox does not grow; no historical typing replay; expiry/renewal ordering follows LLP 3000.017 |

Keep the instrument and app requirements fixed for the before/after comparison.
Record application-owned workaround code, correction loops by cause, time to
working behavior, redundant acknowledgements, admitted-intent loss/duplication,
visibility-to-receipt latency and added persistent state/resource cost.
Acceptance requires every applicable scenario above to pass with no additional
application outbox or protected-result cache. A fresh builder should need no
custom acknowledgement sets, settlement wiring or acquisition timers for these
paved patterns. If it still does, record the gap rather than relabeling it an
agent mistake. One successful build is evidence, not a universal ergonomic claim.

## 9. Decisions still open

- Which gaps remain after current receipt and presence lanes land? Inventory
  their exports and witnesses before assigning implementation.
- Can a small starter component supply submission recovery using current
  pending-write APIs, or is a reusable lifecycle helper justified?
- Which applications admit contiguous watermark acknowledgements, and what
  minimal explicit policy selects that recipe safely?
- Does the current media handle already provide the necessary viewer lifetime?
  Do not create a new media-cache abstraction without a failing witness.
- Which supported starter is the first qualification target? Recommend the
  existing chat starter on web, with native-specific claims held for the native
  witness; retain the same product contract across both.
