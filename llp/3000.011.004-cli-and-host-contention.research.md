# LLP 3000.011.004: Development commands contend with the running host

**Type:** Research
**Status:** Active
**Systems:** Snapback 4 CLI, dev host, SQLite writer ownership, schema adoption, backfills
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (reviewed evidence and scoped remedies)
**Related:** [Parent](./3000.011-recent-builder-friction.research.md), [Improvement proposal](./3000.011.004.000-coordinated-development-commands.rfc.md), [LLP 3000.000](./3000.000-atomic-schema-and-release-activation.research.md)

## 1. Problem

A builder can save a schema, start a development host and run a backfill or
job as individually reasonable steps, yet overlap two writers to the same
store. The current development loop can turn that overlap into a low-level
store refusal and require the builder to discover the correct sequencing.

## 2. Evidence

The final boundary of the [0.2.30 diary](../benchmarks/runs/2026-09-18-snapback4-clique-astra-0.2.30/astra/lane-diary.md)
records a populated-store backfill racing the host's derived rebuild and
receiving `E_STORE database is locked`. The builder stopped its recorded scale
processes, ran the backfill with the host stopped, then restarted.

The [0.2.31 M8 follow-through](../benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/astra/lane-diary.md)
records another concurrent CLI/startup attempt waiting on adoption and
returning E_STORE; a sequential retry succeeded. The
[run synthesis](../benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/README.md)
identifies the repeated class as a candidate issue without attributing a
runtime defect.

These reports establish contention and a manual workaround. They do not
establish lost data, non-atomic activation, corruption or a need for online
zero-downtime schema migration.

## 3. Existing guarantees

[LLP 3000.000's implementation follow-up](./3000.000-atomic-schema-and-release-activation.research.md#implementation-follow-up)
records atomic activation, generation checks and read-only inspection that
does not adopt working source. Those repairs remain in force.

The [current operations reference](../snapback4/packages/snapback4/CLIENT-AND-OPERATIONS.md#5-development)
already documents automatic retry of dev adoption after writer-lock or
generation failure, `doctor` adoption health, and the need to restart a
`--no-watch` host after another process adopts. `run` executes against the
local store; jobs run as the system and are refused through the public
application operation wire.

The residual is user-facing command coordination across cooperating local
processes, not the absence of transactional activation or any retry mechanism.

## 4. Interpretation and confidence

SQLite serialization is expected. Requiring each builder to manually arrange
process timing is avoidable if commands can identify a busy adoption, wait
within a known deadline and either proceed against the right generation or
give a specific next step. A raw store error contains too little lifecycle
context for that routine case.

The repeated symptom makes this a strong usability candidate. Root-cause
reproduction is still required: an error from unrelated I/O or invalid data
must not be relabeled contention, and a lock retry must not repeat a committed
mutation whose response was lost.

## 5. Desired outcome

Cooperating development commands should have an explicit, bounded sequence
around adoption and execution. They should preserve process ownership, show
what they are waiting for and report the actual generation and job outcome.
A stopped-store command should still work without a running daemon.

The [child RFC](./3000.011.004.000-coordinated-development-commands.rfc.md)
selects bounded typed retry before admission, retaining SQLite and generation
checks as the correctness boundary. A new coordinator and a public system-job
endpoint are outside this increment.

## 6. Review disposition

Review scope correction: the host already retries typed contention and supports watching after external adoption. The concrete CLI asymmetry is a one-shot open/adopt before run admission. Bounded retry and precise lifecycle reporting are selected before any new coordination primitive.
