## 1. Why

The receipts card (`guide receipts`) computes sent, delivered and read
correctly, but a React hook reports delivery, one mounted conversation at a
time. Two Grok comparatives charged it:

- **0.4.1:** receipts "never advanced without open conversation".
- **0.4.3:** "receipts stay `sent` until the client calls `delivered`". That
  builder mounted a `DeliveryAck` on the signed-in shell, and it acknowledged
  every position through `lastOrdinal`, including messages it never fetched.

The client knows exactly which rows reached it. This RFC moves the reporter
into the platform and keeps the card's data model.

Revision 0 bound a confirmation query that the SDK read after each report.
Review found that the only reason a successful call was not already coverage
is one line of the card: its 65th run succeeds without being stored. A
confirmation read then needs its own binding, its own progress loop and its
own fences. Revision 1 removes the cause instead: the card refuses what it
cannot record, so a successful call *is* coverage.

## 2. The contract

### 2.1 The clause

```quarry
mutation delivered(conversation: conversations, from: int, through: int)
  reports delivery of messages by .conversation, .ordinal
```

It names the tracked table, its group column and its position column. The
compiler checks, with `E_DELIVERY_CLAUSE` and a rewrite otherwise:

- the mutation's parameters are exactly the group (a reference to the table
  the group column references) and then two `int`s, the first and last
  position of a run;
- the group and position columns are `immutable`, and `(group, position)` is
  `unique`;
- one clause per tracked table.

### 2.2 What the mutation promises

The compiler cannot check a mutation's body, and does not try to. The
clause's contract is documented in the card, the guide and
`snapback4 why reports`:

- **Success is coverage.** When a call succeeds, every position from `from`
  through `through` in that group is recorded as delivered to the caller.
- **What cannot be recorded is refused**, with a coded refusal.
- **Replays** of a write id return its recorded outcome, as for every
  mutation.

A mutation that breaks the contract gives wrong receipts, as a wrong hook
does today. The platform's own guarantees do not depend on it:

- the SDK reports only positions that reached the client (§3);
- it retires a position only on the server's committed success;
- the server still decides membership and range.

### 2.3 The card, changed in one place

The end of `delivered` (`receipts.rs:136–140`) becomes:

```quarry
  if low <= prefix + 1:
    update members[me] { deliveredOrdinal: high }
  else:
    require count(runs where .conversation = conversation and .principal = viewer) < 64 else RUNS_FULL
    insert runs { conversation, principal: viewer, fromOrdinal: low, throughOrdinal: high }
  return null
```

Today the last branch inserts only when there is room and otherwise returns
`null` without storing anything.

- **The merge loop cannot lose coverage.** It deletes the runs it merges
  before the count, so a merge that deleted any run always has room. Only a
  disjoint 65th run is refused.
- **What stays:** everything else, including `runs`, `members.deliveredOrdinal`
  and `joinedOrdinal`, the early `return null` for a covered run, `progress`
  and `seen`.
- **Beyond 64 holes.** A run with more than 64 permanent holes below it stays
  unrecorded, as the card says today; now the refusal says so.

`delivered` checks, as today:
- that the caller is a member (`NOT_MEMBER`);
- that the conversation exists (`NOT_FOUND`);
- that `0 < from <= through <= chat.lastOrdinal` (`NOT_A_RUN`,
  `PAST_LAST_MESSAGE`).

That is the allocation bound, not an existence check. Every tracked row is
assumed to exist, and the card meets that because it never deletes messages.

## 3. What a client collects

**Positions are exact integers in JavaScript's safe range**
(|n| ≤ 2^53 − 1). A tracked row whose position lies outside it is never
collected, on either client, and stays `sent`: a rounded position could claim
a row that never arrived.

A client collects the positions that reached it. It collects them into a
**debt**, the positions owed less those already reported and those refused
(§4). Debt is kept per store, viewer, **binding** (the tracked table and its
mutation) and group. So position 41 of `c1` in two tracked tables are two
debts, and every limit in §4 counts per binding and group.

**The device (the local client) collects the rows a publication transaction
leaves published.** The hooks below gather **candidate** identities. Before
`predictions::replay` (`device.rs:870`), after every authoritative effect of
the page, membership change and clock publication, the transaction keeps
only the candidates whose final image is:
- present;
- row-level `Held`;
- not provisional;
- not expired at the device's effective time.

The same final check applies to a settlement. So a deferred row installed at
`device.rs:856` and deleted by the same page's events (`deferred.rs:237`) is
never collected. Neither is a staged row that a text-only delivered-history
scope event kept without clearing `acquired` (`snapshot.rs:102`), nor a put
that is already expired. The hooks:

| Path | What it collects |
|---|---|
| An ordinary sync page | Event puts that pass `boundaries.accept` (`deferred.rs:231`), not every incoming put. Horizon rejects are not stored and not collected. |
| A deferred ordinary page | Nothing while it is staged (`device.rs:756–761`). Its accepted images are collected when `deferred::install` installs them, inside a later page's transaction (`device.rs:856`, `deferred.rs:86–112`). |
| Snapshot pages, catch-up and promotion | Nothing while staged (`device.rs:804–808`). At promotion (`device.rs:825–871`), the promoted `Staged` rows with `acquired: true`. Rows with `acquired: false` are retained local copies (`snapshot.rs:8–19`), not a new delivery. |
| A prediction's settlement or withdrawal | The confirmed images left visible after `replay`, because a confirmed image under a pending edit was never collected (see Durability). |

- **Predictions.** They are restored before publication and replayed after
  it, so collection before `predictions::replay` sees only authoritative
  images. A provisional position is never collected.
- **Durability.** On a publication, debt is written to device meta in the
  publication transaction:
  - after `deferred::install`, the page's `events` and any promotion puts
    (`device.rs:830–859`), and before `predictions::replay`
    (`device.rs:870`) and the commit (`device.rs:871`);
  - on a replacing publication too, after `clear_rows` (`device.rs:826`),
    which deletes rows and indexes but not `_meta` (`sqlite.rs:90–95`).
  On wasm, debt shares the host persistence batch that `web.ts:190`
  completes before the commit is observable.
- **Settlement is its own transaction.** `restore` puts back every
  prediction base and `replay` reapplies the still-active predictions
  (`device.rs:1048–1057`, `predictions.rs:25–45`, `:265–297`). `withdraw`
  does the same (`device.rs:974–977`). Before `restore`, the transaction
  remembers the row ids the predictions wrote. After `replay`, it checks
  only those ids whose prediction was not reapplied: the confirmed images
  left visible because their prediction ended. It never scans the table,
  which after `replay` would be every non-provisional row, on each
  settlement. They pass the final check above, and the debt is
  written in the `settle` or `withdraw` commit (`device.rs:1058`, `:978`).
  Nothing scans the table between `restore` and `replay`, where every
  pending base is visible.
- **Every committing restore and replay path collects what it confirms.**
  Publication's own replay can retarget a prediction or withdraw it without
  a separate `settle` (`device.rs:824`, `:870`; the retargeted case is
  `prediction_write_set.rs:46`), and `dequeue` restores and replays in its
  own transaction (`device.rs:1099`). Each such path keeps the identities
  it restored. It collects those left confirmed, `Held` and unexpired after
  replay, from those identities and never from a table rescan, and writes
  the debt before the same commit.

**From answers (both clients).** A client also collects the manifest entries
(§5) of answers accepted under the current credential, including the local
client's fallback answers, which are not installed in the store. The local
client persists them after acceptance, subject to the final fences on every
collection attempt (§4).

**Left groups.** When a group becomes `Left`, its debt is dropped.

**First activation.** A store that holds tracked rows but no delivery record
(a device upgraded from 0.4.4) enumerates its held rows once, as if they had
just been published. It is built on `history::Reading` and walks the tracked
table's `(group, position)` index. `history.rs:151` delegates raw scans, so
it applies each filter explicitly. It takes rows:
- whose row-level `coverage_state` is `Held` (a redelivered row after a
  rejoin, not a retained one);
- that are not provisional;
- that are not expired at the device's effective time.

A confirmed image under a pending edit is collected at its settlement
(above). Enumeration keeps one persisted cursor and one `done` marker **per
binding**, so a second tracked table is enumerated too. It reads pages of at
most 500 raw rows (`Reading::scan` is a raw scan, `history.rs:151`), and the
cursor is the last raw `(group, position)` examined, including rows the
filter drops, so a page that yields nothing still advances. It schedules its
next page until `done` is written, and never runs again for that binding.

**The online client** collects from manifests only, into memory. Rows lost
with the process stay `sent`.

A row that expires after collection is still reported, because it was
delivered.

## 4. How it reports

**One acceptance point.** An answer is accepted when a watch publishes it or
one-shot `query` resolves with it, synchronously after its final expiry,
incarnation, authority, credential and `unavailable()` fences. Acceptance
never waits for collection persistence and never fails because of it. The
local client then persists the collection in a CAS whose every attempt
rechecks that the answer is current, including at the host's commit point.
A stale attempt writes nothing. An already accepted answer stays accepted;
uncollected rows stay `sent`. A crash or a change before commit only
under-reports. Nothing is collected from an unaccepted or stale answer.
Hosts without a conditional commit omit supplementary answer collections;
device publication collection still shares its ordinary row transaction.

**Scheduling**
- **Runs.** Per group, the queue takes owed intervals in ascending order.
  Each call reports one maximal interval `[a, b]`, and every integer in it is
  owed.
- **Slots.** Four calls may be in flight per client, at most one per group.
  When a slot frees, the ready group that has waited longest takes it, so a
  busy group cannot starve another. A call in backoff, and a parked group,
  hold no slot.
- **Deadline.** A call has a 15-second deadline. A call past its deadline
  is uncertain, like a transport failure.
- **The outbox first.** The delivery scheduler dispatches only while the
  local client's serial network chain (`local.ts:189`) holds no outbox
  work. It never queues a delivery request ahead of one. Running requests
  still share the server's single writer.
- **When it flushes.**
  - on new debt, debounced 250 ms (on the online client too, so a manifest
    accepted while the user stays on the home screen is sent then);
  - on reconnect;
  - on start (persisted debt is flushed first).

  It never uses the outbox's suspend path (`local-device.ts:20`, web only,
  outbox entries only). Debt is persisted, so a closed tab reports at its
  next session.
- **The request.** Each call is a direct `POST /m/<mutation>` with the body
  `client.mutate` sends, `{ id, args, store_id }`, named by the binding's
  argument names (§5). The local client persists the attempt's id and
  arguments before dispatch, so an uncertain attempt is retried with the
  same id after a restart. Responses pass the existing store-identity and
  head observation (`client.ts:348`, `store_identity.rs:89`) before
  anything retires. `store_id` fences a replaced store (`E_STORE_REPLACED`,
  `serve.rs:798–803`). A restored store with the same id executes the call
  and answers `sent` with a lower `head`. Only the client names that
  `E_STORE_RESTORE`, so:
  - **Each call is judged by its own floor.** Each call records the floor
    it was dispatched with (online, the client's `minimumReadSeq`,
    `client.ts:466`), and only that floor judges its response, as
    `observeStore` does (`client.ts:348–363`). Responses to four calls can
    return out of order.
  - **The local client** does not dispatch until `witnessRestore`
    (`local.ts:294–301`) has accepted the server in this session. It judges
    heads the way `observe_store` does, not with a session counter.
  - **A missing or non-numeric `head`** neither retires anything nor counts
    as a restore.
  - **A detected restore** retires nothing, drops the queue, and deletes
    this viewer's delivery meta in the device store, so the next session
    cannot flush it.

| Outcome | What the queue does |
|---|---|
| Success, fresh or replayed | Moves `[a, b]` to reported. |
| `RUNS_FULL` | Parks `[a, b]` and continues with the group's next interval. |
| `NOT_MEMBER` or `NOT_FOUND` | Drops the group's debt. |
| `E_AUTH` (a 401 `denied`, `serve.rs:1010–1012`) from an obsolete credential | Keeps `[a, b]` and retries with the same id after the refresh, as the clients already do (`client.ts:438`, `local.ts:530`). |
| `E_AUTH` from the current credential | Keeps `[a, b]`, stops the queue, and keeps the viewer's persisted debt. |
| A replaced store (`E_STORE_REPLACED`), or a detected restore (a `head` below that call's own dispatch floor, whatever the body says) | Retires nothing, drops the queue and every in-flight call, and deletes the viewer's delivery meta. Recovery is a fresh device store, whose debt starts empty. |
| `NOT_A_RUN` or `PAST_LAST_MESSAGE` (the card's range refusals, which an honest client never provokes) | Moves `[a, b]` to the group's refused set and reports it through `onDeliveryRefused`. While that entry is retained, a later manifest cannot recreate it. |
| Any other non-retryable refusal (`E_OP`, `E_INPUT`, an unknown code) | Parks `[a, b]` until start, and reports it through `onDeliveryRefused`. |
| A transport failure, a deadline, or an uncertain store failure (no recorded outcome) | Keeps `[a, b]` and retries with the **same** id, backing off from 1 s and doubling to 60 s, at most 8 times. Then it parks `[a, b]` until reconnect or start. |
| A **recorded** retryable refusal (such as `E_CONFLICT`, `error.rs:349`, which the engine records, `engine/mod.rs:1082`, `:1104`) | Keeps `[a, b]` and retries with a **new** id on the same backoff and budget, since replaying the old id returns the same refusal. |
| `E_BOUND` | First replay the **same** id: `state: "sent"` retires the interval, while a bare `denied` without a failure receipt remains uncertain on that id. Only a replay returning `state: "failed"` with `why.code === "E_BOUND"` permits a new id on the 1 s–60 s backoff, debiting an **in-memory counter per binding fingerprint and group key**, at most **eight mints per queue session**; the counter survives all interval/park transitions, merges, splits, eviction and recollection, resets only with a new queue on app start or sign-in, and when spent parks the interval as `start` until the next session, with no terminal refusal, refused entry or `onDeliveryRefused`. |
| Offline (`E_OFFLINE`) | Keeps everything and sends nothing until reconnect. It does not spend the retry budget. |

The named refusals are matched before the generic non-retryable row, in
both the `why` and the `denied` envelopes, except that the `E_BOUND` new-id
branch requires the replayed failure receipt stated above. The HTTP layer can
answer `denied: E_BOUND` after a committed mutation whose JSON reply exceeds
16 MiB; its stored receipt is success. Replaying protects that committed report
from executing twice. No bound counters, spending coverage or wake allowance
are persisted, and success does not replenish the session counter. If pressure
loses an id awaiting a bound replay, an in-memory pending-id marker delays the
group until the next session rather than minting fresh initial ids around the
limit; it neither restores evicted debt nor creates a refusal. Every `E_BOUND`
outcome records that session marker, even when stale or without a usable head;
only a validated current outcome can retire debt or mint a replacement.
Abandoned persistence reservations consume the allowance even if no replacement
request is dispatched.
Retired records carry their binding fingerprint; removal and restoration match
that fingerprint, not merely the table and mutation.
An attempt after a definitive
outcome takes a new id, because the old refusal is recorded.

**Waking a parked run.** A parked `RUNS_FULL` interval can succeed after
another device merges runs, and nothing tells this device.
- Wake events set one pending flag per group, so a burst of manifests is
  one wake.
- At a wake, the group retries **one** parked interval, the one that has
  waited longest, with a new id. It does so only if the group has no call
  in flight, and never sooner than 30 seconds after that interval's last
  attempt.
- Owed intervals take a free slot before any parked retry, so a wake never
  delays a new message's report.

The wake events are:
- after the next success in its group;
- when the device publishes a tracked row of its group, or the online client
  accepts a manifest from it;
- on reconnect and on start;
- on a slow timer, every 10 minutes while online, with at most one minute of
  jitter.

This replaces LLP 3000.021 §3.2's "retry when the confirmed prefix or runs
change", which needed a confirmation read to observe. It needs none. A group
with more than 64 permanent holes pays one call per wake.

**Stale callbacks.** Every attempt captures its group state's
**incarnation**. A leave, an eviction or a recreation of the group's state
starts a new incarnation.
- An outcome for an older incarnation releases its slot and changes no
  debt, reported or refused state. So a `NOT_MEMBER` that executed during a
  leave cannot drop debt collected after a rejoin, and the group is never
  wedged with a stale call holding its only slot.
- A viewer change and a sign-out start a new incarnation too, so a late
  outcome never lands on debt collected after a new sign-in.
- The online client cannot observe membership. There, a group-dropping
  refusal drops only debt collected at or before the attempt's captured
  collection version.

**Fences**
- A viewer change or sign-out stops the queue at once. Debt is persisted in
  the viewer's device store (`local-device.ts:35` names the store per server
  and viewer), and a same-viewer credential refresh keeps it.
- `signOut` on the online client waits at most one second for calls already
  in flight, on a signal it has not yet aborted. Anything still queued is
  lost and stays `sent`.

**A rejoin.** A report executes against the caller's membership at commit.
- A report dispatched before a leave that lands after a rejoin records
  against the new membership. The card's join floor
  (`max(deliveredOrdinal, joinedOrdinal)`) covers every earlier position,
  so it changes nothing.
- A coverage model without a join floor must refuse positions before the
  join. The contract says so. The platform does not fence it.

**Bounds**
- **Per group.** Owed intervals are capped at 256, and past that the lowest
  are dropped and stay `sent`. Reported intervals are capped at 256, and
  dropping them costs at most a redundant report. Refused intervals are
  capped at 64.
- **Groups with state.** The local client keeps at most 4,096 and the online
  client 1,024. Past that, the least recently collected group's state is
  evicted, and its positions stay `sent`.
- **Refused intervals.** Only `NOT_A_RUN` and `PAST_LAST_MESSAGE` enter
  the refused set. Every other refusal keeps the
  interval, parks it, or drops the whole group (`NOT_MEMBER`, `NOT_FOUND`)
  or queue (store).
- **The refused set** holds at most 64 intervals per binding and group, and
  never evicts. An honest client never provokes these refusals. If one
  still fills it, the group is **saturated**:
  - a persisted marker is written;
  - collection and dispatch stop for that binding and group;
  - the owed intervals still queued are dropped without adding refused
    entries, and stay `sent`.

  The marker, the refused set and the group's other delivery state are
  cleared only with a new group incarnation (a leave and rejoin) or a new
  device store, not merely by a start. Evicting a group's state under the
  4,096 and 1,024 caps keeps its refused set and marker, so a refused
  interval is never reported again after its group is recreated.
- **Retries.** They are bounded by the backoff schedule and the wake events.

## 5. The manifest

Every successful `/q/` answer that read a tracked table carries a manifest:
the tracked rows the answer delivered, nested images included, deduplicated,
under the binding that reports them.

```json
"delivery": [{ "table": "messages", "mutation": "delivered", "args": ["conversation", "from", "through"],
               "fingerprint": "…", "rows": [["c1", 41], ["c1", 42]] }]
```

**Self-describing.** Each binding names its tracked table, its mutation, and
its argument names in order (group, first, last), because HTTP arguments are
named (`validate.rs:150`).

**Fingerprinted.** Each binding also carries a `fingerprint`: a digest of its
table, group column, position column, mutation and argument names, as the
compiled schema states them. Every report sends the fingerprint of the
binding it was collected under, and the server checks it under the writer,
before the body runs.
- **A mismatch.** If a later generation rebound the mutation (for example to
  another tracked table), or removed its clause, the server refuses
  `E_DELIVERY_BINDING`, which is not retryable. The queue then drops that
  binding's state.
- **Why the server checks.** Without it, a report dispatched under
  `messages` could execute under a rebinding to `photos`, and record a
  position that never reached the client. Fencing the callback cannot undo
  a server execution; the check must run where the body does. The pair `(table, mutation)` is the binding's
identity in every queue key (§3). When a new backend generation changes a
binding, for example a mutation name reused for another table
(`client.ts:740`), the binding's state starts a new incarnation, and
callbacks for the old binding are fenced. The SDK needs no registry, no codegen hook and no
`/schema` fetch. An answer touching two tracked tables carries two bindings.
The device learns the clauses from the compiled backend it already holds.

**What qualifies** is as LLP 3000.021 §3.2 specifies.
- A row qualifies when the answer carries at least one of its stored fields,
  in an image stamped with its source identity.
- It never qualifies through:
  - an empty shape;
  - a shape that replaces every field;
  - an extracted scalar;
  - a copied `.ordinal`;
  - a count or a filter.
- Denied, loading and overflowed rows are absent.

**How it is built**, over existing provenance: `Runner::stamp_source`,
`SourceIdentity`, shape propagation and the provenance reservation.
- **Coordinates.** `SourceIdentity` gains the row's delivery coordinates,
  captured from the authorized source image when it is stamped
  (`provenance.rs:6`), never from projected JSON.
- **Stamping.** For a tracked source it is automatic, independent of the
  request's `provenance` flag (`serve.rs:1086`).
- **Origin, per field.** Each projected field carries its origin: a triple
  `(table, id, column)` naming a stored column of one row, or nothing. It
  is copied through aliases and spreads, into every successive projection;
  replacement clears it. An image qualifies only when some surviving field's
  origin names **its own** source row (its `SourceIdentity`). One bit per
  image would not do:
  - `{text: .text, ordinal: 0}` then `{ordinal}` carries no stored field;
  - `{alias: .text}` then `{alias}` still carries one;
  - `{ preview: quote.text }` on a message carries the quoted row's field,
    not its own, so it does not qualify the outer message. It qualifies the
    quoted row only if its own image survives.
  - An origin whose column is the binding's **position** column never
    qualifies. So `{ ordinal: .ordinal }` and `{ text: "x", ordinal:
    .ordinal }` do not report the row, as §3.2 requires of a copied
    `.ordinal`.
- **Where origins live.** Beside the value, as `SourceIdentity` does: they
  are not part of `retained_heap` or `expression_heap` (`value.rs:224–238`,
  `runner.rs:733`) and not part of the answer's bytes (`runner.rs:1064`).
  They are charged to the manifest ledger below, and never cross the wire.
- **Survivors only.** The manifest is built from the output images that
  survive, never from the read set. Stamping happens before filtering
  (`read.rs:1008`).
- **The gate.** An answer whose `tables` exclude every tracked table carries
  no manifest and is not walked; an inbox of conversations pays nothing. An
  answer that reads messages but returns only a count is still walked, and
  yields nothing.
- **Its own ledger, stated as an amendment (§8).** The alternative, residual
  room under the existing ceilings, would let the manifest's work consume
  capacity the answer needs later in its own evaluation. So the manifest is
  funded separately and the answer is never touched. Delivery stamping,
  origin tracking, the output walk,
  deduplication and the manifest's bytes are charged to a manifest ledger of
  their own. It holds a quarter of each of the query's step, heap and output
  allowances, and at least 128 bytes of output, reserved incrementally
  before each operation. So an answer with a manifest may use up to 125% of
  today's per-query ceilings, and never more (§8). The ledger's use is
  reported with the answer's meter under `dev`, as `delivery` beside the
  answer's `ReadMeter`.
  - **The answer is untouched.** It never draws on the answer's meters, and
    never calls `meter.step`, `meter.heap` or `charge` in a way that returns
    `Bound` (`meter.rs:214–229`) or sets `capped_at` (`meter.rs:145–149`).
    So the manifest can never cut, fail or change an answer: not its
    `complete`, its `cut` or its `capped_at` (`engine/mod.rs:917–918`),
    and never turn it into `loading` or `null` (`runner.rs:341–345`).
  - **Filtered candidates.** Their stamping heap is released when the
    candidate is dropped (`read.rs:1016`).
  - **Budget exhausted during evaluation.** Coordinates are not recorded
    for later rows, which the manifest omits.
- **Overflow.** When the next reservation would exceed the budget,
  construction stops. The manifest keeps what it has, and is marked
  `partial`. The envelope's fixed overhead (binding names, argument names,
  framing and the `partial` marker) is reserved first. The 128-byte floor
  always holds the minimal form, `"delivery": "partial"` with no bindings,
  which is what the answer carries if even one binding's envelope does not
  fit. A partial
  manifest only under-reports, and the missing rows stay `sent`.

## 6. The engine: a no-op report advances nothing

Today a mutation that writes nothing still records a commit, advances the
sequence and wakes the global change stream. For a mutation with a clause, a
successful execution that writes no row and emits no effect keeps its
**receipt** but advances nothing:
- **Kept.** The receipt records the outcome and the argument binding
  (`record_applied`, `bind_applied`, `engine/mod.rs:1099`). So replaying a
  write id still returns its recorded outcome before any program lookup
  (`engine/mod.rs:983`), exactly as §2.2 promises.
- **Its sequence is the last committed one,** `next_seq() - 1`, the value a
  refusal already stores (`engine/mod.rs:1102`). It is never the
  unallocated `next_seq()` assigned at `engine/mod.rs:1075` (SQLite) and
  `postgres/mod.rs:249`, which the next real commit will take. The
  response's `seq` and `head` are both that value, so the online client,
  which treats `seq` as a watermark (`client.ts:763–765`), never raises its
  floor past the real head.
- **Skipped.** `record_commit`, the partition append and effect recording;
  the host's `durable_committed` notification (`serve.rs:1197`); and the
  waiter wake-up (`serve_ephemeral.rs:77`).

The transaction is still the writer's, short and receipt-only. No device
syncs anything for it, and no change stream wakes. The same rule applies on
the SQLite and Postgres stores (`engine/mod.rs:1073–1107`,
`postgres/mod.rs:265–298`).

## 7. Costs

| Case | Requests | Commits |
|---|---:|---:|
| A new message to an online local-client recipient | 1 report (plus the sync page it already receives) | 1 |
| A device restarting with 1,000 held conversations and no owed debt | 0 | 0 |
| A device restarting with owed debt in `k` groups | `k` or more, four at a time, flushed first | only for new coverage |
| First activation after upgrade, 1,000 conversations with one owed run each | 1,000, four at a time | only for runs not already covered |
| A fresh online client whose inbox shows 20 conversations' last messages | ≤ 20 | only for new coverage |
| A group parked at `RUNS_FULL` | at most 1 per wake (§4); each interval at most once per 30 s; the 10-minute timer when idle | only if a slot freed |

"Commits" counts sequence advances. A no-op report still takes the writer
for a receipt-only transaction (§6), and every real report is a commit that
wakes the global change stream, as the card's hook does today.

**Trust.** Delivery is the recipient client's word, as with the card. The
server checks membership and the allocation bound.

## 8. Amendment to LLP 3000.021 §3.2

This RFC departs from five requirements, and §3.2 is revised with it:

- **"Confirmation is the member row, authoritatively … a later read."** It is
  replaced by *success is coverage* (§2.2–2.3).
  - The mutation's committed outcome is the server's authoritative answer
    at its commit.
  - The card's silent 65th run was the only reason it was not, and it now
    refuses.
  - Review of revision 0 showed a confirmation read needs its own binding,
    which a return type cannot give; its own progress loop; and its own
    fences.
- **"It also scans that local read at flush, as recovery."** It is replaced
  by collection at publication into persisted debt (§3), plus one bounded
  enumeration at first activation.
- **The clause binds no confirmation reader.**
- **"Its bytes count as output."** The manifest's work and bytes are
  charged to a supplemental ledger (§5), a quarter of each allowance with a
  128-byte output floor, not to the answer's meters. A query with the
  clause may therefore use up to 125% of today's ceilings. The ceilings stay
  explicit and bounded, and the answer can never be cut or changed by the
  manifest.
- **"Retries a refused remainder when the confirmed prefix or runs change."**
  It is replaced by §4's wake events. A parked run retries on the group's
  next success, a publication or manifest from the group, reconnect, start,
  and a slow timer, so another device's merge is found without a
  confirmation read.
