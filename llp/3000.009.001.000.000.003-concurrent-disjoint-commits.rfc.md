### 2.2 What a strict W4/A win requires

With 32 clients at the edge of capacity, Little's law sets the bar: a mean of
at most 32/4,525 = **7.07 ms**, about 6.4 ms with the margin three passing
repetitions need (G7.0's arm C passed at 6.93 ms, worst intended p99 84 ms
against 100). HTTP 0.45–0.63 ms, 0.56 ms of link per flight, the flush (2.64
ms sync, 2.70 ms PG commit) and release 0.25–0.35 ms are fixed, so **one
flight leaves about 3 ms for CPU, server work, phasing and the flush residual;
a second leaves 2.5.**

- **Supabase is flush-bound too**: one `set_config` and one SECURITY DEFINER
  RPC per transaction; at 3,200/s ≈98% of the device, p50 8.02 ms; it fails
  4,525. The contest is everything else.
- **The shapes** (G7.0, SQL only): arm C at N=16 on two connections, 6.93 ms
  at 4,525/s, sync/batch 1.003; E2, early release at N=16, 7.01–7.03 ms,
  **though product arm E qualified only 1,600/s** (§3.5); N=8 on four merged
  flushes (0.705) was slower, 7.74 ms; ordered S at N=32, 8.39–8.73 ms. The
  product adds HTTP, interpretation and authority CPU, a slower P1, phasing
  and release.
- **The ordered lane's limit.** At depth d a request spans about d chains
  (≈4.7 ms after G7.3), so depth two cannot pass 4,525; at depth one with N≈32
  the per-member tail matters as much as concurrency. The then-modelled batched floor,
  every term low, was ≈6.8 ms (rev 4's budget); the raw-PG token reference measures p50
  5.43 ms on W5 mix/B at 4,525/s ([one-host
  final](../snapback4/experiments/scale-controls/results-20261024-s1-onehost-final/README.md)).

### 3.2 Stage P: Postgres per-batch server cost

Stage P replaced repeated inline checks with provisioned checks, compact typed
arrays and shape-specialised set-based tails, and moved evidence pruning off
application batches. WF supplies the combined raising final, cumulative
pre-COMMIT budget and notified ordered release. Their reports distinguish
root-statement clocks, process CPU, flush and request residence; P did not
fully attribute the old fitted 2.4 ms intercept. The batch-granular commit
index and typed-layout proposals were **not** demonstrated savings. N=1 R
keeps one **enriched `_commits` record, also the attempt record**, and one
evidence row per reservation (§4.4); it does not remove their consumers or
introduce an internal unkeyed result receipt.

R adopts Stage P's **digest-named, create-only lifecycle** for cached PL/pgSQL
write bodies as well as check functions. Names bind signature, body and
execution attributes; qualified relations and pinned `pg_catalog`, invoker
security and VOLATILE statement snapshots are required. Generic plans cache
code, never authority or an execution result. Provision new shapes only at a
drained, fenced opening/maintenance boundary under the head lock; bound their
number and memory. A new shape may first fall back to O. Validate **every
admitted digest**, including versions unknown to this binary, at open,
lease/reacquisition, reconnect and doctor. Missing or incompatible admitted
functions refuse and are never recreated as a repair. Retain old functions
until fenced takeover permits removal; clear prepared caches on replacement
sessions or schema/code changes. Preserve namespace/output/`array_nulls`
guards on every flight, including caller namespace capture before the helper
pins its path. Privileged mid-lease DDL remains outside the supported boundary.

### 3.3 L′: one flight on validated warm facts

This accepted O-lane design is also R's warm-fact contract. The slot
interprets each member before any flight, in parallel, on a bounded mirror and ingress-carried session facts; the final message validates every
consumed fact inside the fenced transaction, and any failure **raises and
aborts the attempt**, the batch rerunning two-flight. **L′ is built only with
the freshness protocol below** (astra); without it the two-flight path stays.

- **Mirror:** images this committer published plus **validated read facts**
  (S1 never writes `memberships`; Fable), dropped at every barrier, lane
  change, unknown outcome and ownership event; rows an unresolved batch writes
  are cold, and a stale entry costs only a miss.
- **Targets: a locked probe** classifies each row (absent, hidden, rule
  refusal, image mismatch, ok) against the predicted class, so a changed row
  never commits as `NOT_FOUND` (grok).
- **Reads:** points and absences by key; **a span only if re-read whole under
  a phantom-rejecting lock** (grok: the O lane's ticket or an R phase's frozen
  `i`), such as `exists memberships[.room, viewer]`, a `key::encode` prefix
  over `i.k` (`rows.rs:156`) asserted with count and ids as `k >= $p AND k <
  $p_next` (Fable), one row by uniqueness.
- **Stored authority facts:** generated from every `SessionFacts` field the
  shared resolver consumes (`identity/facts.rs:7`), absent metadata asserted
  absent; `ordinary` kinds only, others taking the two-flight resolver; a
  census fails on any unasserted input.
- **Host authority inputs** (astra). The resolver also consumes `ServiceSample`:
  `now` and the in-memory **supervisor revision** (`identity/facts.rs:33`;
  sampled at ingress, `crates/snapback4/src/auth.rs:192`), which failed worker
  retirement advances with database facts unchanged
  (`crates/snapback4/src/dev_worker.rs:822–831`, `fence_revision` at `:331`).
  **The slot resamples it (an Acquire load) after interpretation, immediately
  before writing the final message, and a member resolved under another value
  misses**, keeping the order of the two-flight path's in-transaction sample
  (`mutation.rs:65`); a fence after it linearizes after the request, as today.
- **Time: an absolute deadline** (astra). Relative SQL timeouts start only when
  PostgreSQL runs the message and `at` can lag the authority clock (committer
  §3.6), so a message sent before expiry could execute after it against
  unchanged facts. **The message's last authority command raises a named
  SQLSTATE unless `clock_timestamp()` precedes a bound**: the earliest
  authority deadline consumed (session and read-cap expiry, claim windows),
  mapped to the server's clock by a measured offset, minus a margin ε for its
  uncertainty and drift. Run after every assertion, a pass proves validation
  preceded each deadline on committer §6's clock while the mapping holds
  within ε. **ε is qualified:** an RTT-bounded offset sample at lease
  acquisition and every renewal, ε = 50 ms to start; L′ falls back to two
  flights while the sample is stale or wider than ε, or after a clock step
  outside G6's bounds. A deadline passed at dispatch, or a raise, is a **miss
  resolved afresh** on two flights, where an expired session refuses as
  today. Rows' lifetime edges keep committer §6's rule (`at` before B).
- **Keyed members join on the O lane** (Fable: the SDK always sends `{id,
  args}`, `packages/snapback4/src/client.ts:1013`): receipt absence is a point
  assertion after the head CAS (round-trip §3.5). R starts unkeyed; keyed R
  needs §6.7, with O as the complete fallback.

**Cost and keep rule.** Rev 4's preparation anchor was 0.146 ms/member;
its proposed 20–30 µs/member and 0.12–0.15 ms validation at N=16 were targets,
not new measurements. R uses measured per-request CPU (§8). Ordered L′ retains

## 4. Stage R — per-request concurrent one-flight commits (Accepted 2026-10-27, §23)

### 4.1 Two lanes, the phase rule and the drain

**R** has up to K concurrently executing, independent, synchronous transactions,
each exactly one semantic member. **O** is the existing ordered pipeline with
P/WF and, when qualified, L′. Ineligible and hot-key work stays O. N=1 removes
batch collection, cohort holds, per-batch result vectors and predecessor
folding from R; it does not remove serial history, publication or recovery.
A reservation is **open until W covers it**, even if its SQL has committed.
No O writer overlaps an open R reservation. Administrative barriers drain R
and all O transactions before writing.

**R→O (the former C→O drain):** stop R dispatch; resolve every reservation,
void and outcome; settle every catch-up (confirmed reply, or its original
backend proven ended); advance W and install publication. One fenced,
synchronous transaction then verifies the prior `_head` attempt and H≤W,
writes `_head=(W.r,W.s,fresh attempt)` with exact counts, and confirms it.
Only then may the first O head CAS proceed. A lost drain commit is reconciled,
never guessed. This prevents an O head from leaping a hole or a late catch-up
from racing an O CAS. O sequences resume at W.s+1.

**O→R:** drain O's original transactions and publication even if asynchronous
polling has already emptied its queue; read its durable head afresh and reseed
both counters. Invalidate warm facts, or refresh the complete bounded changed
image set in one coherent snapshot only when immutable index addresses and
unchanged schema/code/authority binding prove selective refresh sound. Unknowns,
activation and unclassified producers always clear it. A no-op preserves the
cache only if revision and engine binding did not change. The spike's re-entry
bug is why an empty queue alone cannot authorize reseeding.

### 4.2 Footprints and eligibility

Keep rev 4's complete bounded closure: rows read **or examined**, hidden rule
probes, absent keys, alternative paths and writes. Dependent keys not known
before dispatch become whole-table entries; unsupported closure routes O.
R requests commute only if neither writes a dependency the other reads or
writes. Logical locks live in the owner process; the lifetime database fence
excludes a second owner, so no external managed writer bypasses this index.

| Dependency / operation | Initial R disposition |
| --- | --- |
| Existing row points, bounded rule probes, row images ≤2 KiB | Admitted with complete canonical locked validation; validation of a written old image may fuse into its counted UPDATE |
| Absent keys and ranges | Recorded even when no row exists; admitted only with L′'s complete, phantom-safe re-read under frozen `i`, otherwise O |
| Dependent reads | Conservative table entries until a bounded complete finer footprint is proved |
| Row writes | Existing, index-stable updates only; hard-check actual deltas before dispatch and in apply |
| `i`, inserts, deletes, maintains, caps, `_sequences` allocations | O; frozen `i` is an enforced invariant, not an inference from W4 |
| Session, identity, generation, code/schema metadata | Shared authority reads; every writer is a drained barrier |
| Receipts | Initially O, including receipt-only/refusal writes; keyed R requires §6.7 |
| Outbox/effects, claimers, presence, time-dependent programs/lifetimes | O; ordinary sync events for eligible updates still persist atomically |
| Engine entropy and minted ids | O initially, as in the spike; any widening needs the serial oracle and revision-keyed entropy, never a shared speculative stream |

Freezing `i` makes scans' membership and uniqueness stable. Every payload use
still selects the correct image (§5); `i` stability cannot excuse predicates
on a new `r.data`. SQL locks validate facts, while the router proves the
absence of conflicting open writers. A late unsupported family aborts before
COMMIT and falls back after drainage with fresh facts, never with stale images.

### 4.3 Routing, hot keys and lane switching

The **open-footprint index U** has key and table read/write holders, retained
through publication, not merely until SQL confirmation as in the spike. A
lookup examines only the bounded request footprint and its table summaries:
expected **O(1) per point / O(footprint size) per request**, independent of the
number of flights; never scan every open request for each arrival. A hard
closure bound makes routing bounded; unbounded plans use O. Principal FIFO
prevents a later member bypassing its held predecessor.

A disjoint eligible arrival dispatches as soon as it has admission and physical
session custody, with **no N>1 fill timer**. A collision is held to its blocker
or triggers a drained O phase; it is never sent to contend on a hot SQL row.
Maintain bounded counters from actual collected footprints to detect hot keys.
The spike's initial rule (at least four members, at least half sharing a key,
100 ms O dwell) is a starting sensitivity, not a qualified constant. **One
collision must not pin disjoint traffic in O**: the isolated-collision witness
and sustained 1% mix must pass §10.3's measured recovery/rate gate. In a
proved hot phase, route to O **before** interpretation, identity hashing or
repeated eligibility work. O→R uses hysteresis and measured conflict/eligibility rates; no timer
can bypass §4.1's drain. Exact-key latency, low-rate singleton service and
re-entry decide the thresholds; the batch-controller repair is measured apart.

### 4.4 Reservations, sequence allocation and the attempt record

One sequencer shared by O and R assigns **one revision and one public sequence
per R reservation**, in dispatch order, with fresh `(owner token, monotone
attempt counter)`, store incarnation, effective `at=max(T,pin)` and generation.
The mapping starts from the last drained head; within an R phase r and s
advance in lockstep, even for a void. Never confuse them: O receipt-only and
authority revisions can make their bases differ. Allocate only when dispatch
can proceed. A reservation abandoned before send is still resolved/voided if
it could have become visible to another dispatch; never rewind past an open
reservation. Attempts never repeat or reseed downward.

At N=1, **fold the attempt record into an enriched `_commits`**, rather than
adding rev 4's separate `_batches` relation. Keep its existing unique public
`seq` key and commit fields; add revision, incarnation, owner token/attempt
counter, generation and immutable `state=committed|void`. R requires all these
bindings and a one-to-one r/s mapping. Legacy/O rows remain distinguishable
from R descriptors; conversion/opening and every compatible writer/consumer
must honor the format, including O revisions that produce no new sequence.
The candidate's outcome and commit fields are fixed before dispatch, so the
complete row can be inserted **first after the fencing/settings boundary**,
before any images or other tails. Exactly one such insert is counted; there
is no second commit insert at the end. Its evidence and images/logs/receipts
commit atomically with it. A void inserts the same sequence key with its
no-op commit fields and explicit empty evidence (§6.1).

The existing sequence primary key (`postgres/store.rs`'s `_commits` DDL) already
provides the required arbitration: original commit and void cannot both win;
an abort rolls back the first insert along with every image. The enriched
identity supplies recovery and exact-outcome checks, so a separate descriptor
would duplicate that work without adding a guarantee. This adopts sol #2's
representation, **not a measured saving**; measure its wider row/index and
first-insert placement in R0. `_change_evidence`, `_ops` and `_log` remain
distinct, with their own retention contracts. The merged row survives the
longest applicable commit-cursor, evidence, recovery and tombstone horizon
(§6.4); folding records cannot shorten any of them.

No reservation fsync or extra steady flight is required: after exclusion,
a hole between durable neighbours is reconstructible one singleton at a time
from the two bases. A lost trailing
reservation with no durable successor leaves no state and can be reused only
by a new fenced owner with a fresh attempt identity. A committed highest
record survives as a recovery scan bound even when `_head` lags.

The record stores history identity, not an unkeyed result receipt. Do not
infer an xid epoch from `xmin::text`; xid status, if used diagnostically, needs
a captured full xid8 and database continuity identity. The unique attempt
record and key race (§6) are the primary resolution evidence.

### 4.5 The publication watermark W and durable `_head`

**W=(W.r,W.s)** is the largest contiguous prefix of resolved reservations:
synchronously committed and confirmed (or later certified), or synchronously
voided. It is in memory, sampled atomically. A publication lock advances it
while installing G5/G6 invalidations, ordered replies, continuations and
`/changes` wakeups. **Invalidations happen-before W:** a prefix's G5/G6
invalidations are installed before the new W is stored with release ordering,
and every reader acquires W before any cache lookup, so no reader that observes
W can hit a cache generation W already invalidates (lock-free readers included).
**Publication is one release sequence:** (1) install invalidations; (2) install
cache entries, each immutable and tagged with the `(identity, W)` it was filled
at — a hit requires the entry's W to equal the reader's acquired W, and an
install fails if W moved since its fill was read, so no in-place replacement
can show a reader holding an older W a newer payload; (3) release-store W;
(4) only then send ordered replies, run continuations and fire `/changes`/live
wakeups. Every waiter re-acquires W after arming and before sleeping, so a
wakeup can never be consumed by a waiter that still sees the old W. A committed singleton above a hole is durable but
**unpublished**. R keeps rev 4's ordered acknowledgement rule: unlike the
spike, it releases no success reply or continuation above W. Mutation `seq`
and head therefore agree with published history. This restoration cost must
be measured; per-client gates are not permission for early success (§5.1).

`H=_head` is a **durable low-water mark**, not a row on each R request's
critical path. O, barriers, recovery, the drain and bounded catch-ups write it.
A fenced synchronous catch-up CAS writes a **captured** prefix ≤W and a fresh
attempt, with pruning behind that head (§6.4). Only one catch-up is outstanding;
its lost reply is settled before another head writer. Initial cadence is
100 ms or 1,000 resolutions, with priority for a control loan in the unified
pool; voids have priority too. At 4,525 writes/s this is about 10 catch-up
transactions/s, not 4,525 extra publisher fsyncs/s. Both their CPU and flushes
are charged. No dedicated connection is outside the cap.

Invariant: **H.r≤W.r**, equality at every drain, and durable records plus H
can reconstruct a prefix at least W. Publication is not a durability proof;
it advances only after such proof. If maintenance cannot progress within its
bounded interval plus flight allowance, stop admission before retention grows
without bound (§6.6). A due control task cannot starve behind data loans.

### 4.6 Two-image rows: how a commit stays hidden above W

R adopts rev 4's two-image mechanism. `r` gains nullable unindexed `orev`,
`owm`, `odata`: the last R writer's revision, dispatch W.r and prior image.
A counted R UPDATE saves old `data` to `odata`, installs the canonical next
image, stamps its revision/watermark, and requires
`orev IS NULL OR orev<=dispatch_W.r`. Its old-image predicate also validates
the interpreter's input. All separate read facts keep their locked assertions.

For a row x last written at r, `odata` is x's image at every revision in
`[owm,r)`: U excluded every competing writer until the prior writer was
published, and all earlier open reservations are footprint-independent.
**This is why U must retain committed-above-W footprints.** Letting a second
same-key request overwrite the old image while the first is unpublished,
as the spike's writer cache can do, would need more than two versions.
R neither folds above-W confirmations into a usable writer base nor releases
their footprint holds. The tripwire detects a committed conflicting writer
but does not replace the router when that writer is still uncommitted.

O writes after a complete drain and advances H atomically, so old R stamps
are below every new reader's V and harmless. O/schema conversion must preserve
that relationship, or clear stamps in the stopped conversion. Wide/TOAST rows
stay O initially. Extra tuple/WAL bytes, vacuum and stale-snapshot restarts
are production costs, not measured away by N=1.

### 4.7 The flight of a C batch

R keeps C's guarded final-flight protocol, with exactly one member per batch.
Interpret a warm bounded base in Rust. Under exclusive session custody send
one message: BEGIN READ COMMITTED READ WRITE; explicit synchronous commit;
Stage P's guards; valid session-fence capability (§6.6); first-write enriched
`_commits` attempt/commit insert; complete stored-authority assertions, locked
program-fact validation, generation/store binding and absolute authority
deadline (§3.3); counted two-image updates and evidence/log/qualified receipt
rows; cumulative invocation-budget assertion; timeout resets and **uncancellable COMMIT**.
The cached VOLATILE PL/pgSQL body preserves required command snapshot order.
No still-pending client decision can be placed after COMMIT. Require complete
expected results/tags, COMMIT and idle ReadyForQuery without warnings, as WF
does; a generic zero-count tag is not proof of COMMIT.

Cold, unqualified-clock or validation-miss attempts take fresh two-flight/O
execution after known abort and the phase drain; the one-flight claim applies
to warm eligible requests only. A socket replacement never replays a flight.
The session fence removes per-request `_owner` key shares and their MultiXact
work only after the complete compatible-owner protocol qualifies (§6.6).

### 4.8 Why the committed history is serial-equivalent

For request c interpreted at W_c, each lower revision was either in W_c or
open and independent of c's complete footprint. Its validated facts therefore
equal the serial state just before c. Its interpreter, rules, meter and image
encoder are the reference execution at that revision. A void is a no-op;
no surviving R request read it, so an abort causes no R cascade. Refused or
aborted requests use the existing bounded fresh-fact fallback, with no reply
before that decision. O phases keep the ordered argument and phases meet
only at drains. The oracle replays singleton records and voids in revision
order, rather than treating confirmation order as history.

## 5. Visibility on every reader path

### 5.1 The reader rule

Every reader binds atomic W immediately before opening its statement or
snapshot. In that snapshot use:

```sql
V.r = GREATEST($w_r, (SELECT revision FROM _head WHERE singleton))
image(x) = CASE WHEN x.orev IS NULL OR x.orev <= V.r THEN x.data
                WHEN x.owm <= V.r THEN x.odata
                ELSE sb4_stale(x.orev) END
```

V.s is the paired sequence at the same selected boundary, never an independent
maximum mixing two samples. `_head` revision/sequence/attempt are read in one
snapshot. A reader cannot bind new W to an older existing snapshot; REPEATABLE
READ binds once at open. `sb4_stale` is a stamp-dependent STABLE raising function,
not constant-folded. All predicates, joins, closure keys, hidden probes and
projections consume `image`, not raw `data`.

Every reservation ≤W was durable and visible before W advanced, and the reader
snapshot follows its W sample. O images are covered by the H in the snapshot;
R images above V use `odata`. Thus all returned data/authority/metadata is at
**one prefix V**. A delayed reader seeing a row outside `[owm,orev)` restarts
the **whole** snapshot, discarding accumulated rows, probes, fills and partial
response; **each restart re-acquires W and binds a fresh V before opening the
new snapshot** (reusing the old V would fail identically); at most three
restarts then retryable `E_STORE`. Streams restart before emission or
terminate retryably, never splice prefixes.

Replace the spike's **global drain-before-every-read** with a bounded
**per-client minimum sequence**. The SDK carries the maximum acknowledged
write sequence and observed read sequence for the same incarnation; subsequent
online query, change and sync requests wait only until the serving prefix
covers that minimum, then open their V snapshot. Authentication and store
binding precede using it; it grants no authority. Reset on store replacement,
revalidate generation and retain normal expiry. A wait holds no database loan,
never stops newer writes and never forces `_head` catch-up. Timeout refuses
retryably rather than serving below the minimum. A fresh client without a
minimum reads current W; a new owner serves only after reconciliation. All
first-party arms carry the fence automatically; raw protocol clients have the
same declared consistency contract without an app-managed lane choice.

With prefix-ordered ACKs the minimum is normally already satisfied; it also
prevents regression across retained readers, reconnect and SDK rebase. This
preserves existing acknowledgement semantics. **An early ACK above W would
be a separate consistency/API decision requiring the author and new evidence**,
not an implicit part of R or a budget saving here. The spike's reads paid
≈4.28 ms A / 4.67 ms B in global gate waits; that is motivation to remove the
global drain, not a predicted saving for every production read.

### 5.3 Cost on reads, and raw SQL

Qualify the image expression, wider rows, plan effects, vacuum, restarts and
pool competition on all six read cells, alone and under writes. No global
reader lock remains. Compare EXPLAIN plans for W1–W3, closure and fallback
paths; a change needs explanation and matched evidence, not a free pass.

Generated inspect views bind `_sb4_prefix()` once per snapshot: H plus the
contiguous committed records above it, with the same image expression and
whole-snapshot stale handling. They show a coherent **committed prefix**, not
process-local W. A record can be visible before synchronous flush confirmation;
`pg_xact_status` alone does not certify durability. Therefore direct SQL views
cannot promise the runtime's durable-publication point. Snapback's own `sql`
and doctor's application-data reads use the owner's W-bound snapshot while
serving, or require stopped fenced reconciliation first; catalog-only doctor
checks need no application prefix. Do not invent a zero-flight durable-prefix
oracle for an independent SQL connection.

Direct raw `r` access can additionally observe physically committed rows above
W out of order, even before flush confirmation. It is not the prefix inspection
surface. Document these raw-SQL boundaries, keep managed SQL writes forbidden,
and disclose them alongside S1 configurations. Restore reconciles; graduation
exports one reconciled, certified snapshot. A future stronger direct-SQL
contract needs an explicitly reviewed WAL-position protocol, not a visible
certificate row assumed already flushed.

## 6. Holes, outcomes and recovery

### 6.1 The void and the key race

A void is a fenced synchronous transaction inserting the **same `_commits.seq`
key** as the original, with the reserved revision, exact resolution identity,
state `void`, no-op commit fields and empty-footprint evidence, with raising
counts. This one row is also the attempt record (§4.4); it prunes nothing. The
unique-key insert waits if the original inserted but is still running:
commit makes the void lose with 23505; abort lets it win. If the original
has not inserted yet, a won void makes its late insert fail **before images**.
Read the exact store/sequence/attempt/state after a collision: arbitrary
23505, absent record, a reused numeric revision or a timeout proves nothing.
A previously won void resolves idempotently. A void meeting a committed
record certifies that commit only after §6.3's durability step.

**Tombstones outlive every possible late message.** Retain the void until H
covers it and the original backend (PID **and start time**, role/store/token)
is gone, has demonstrably finished that message via a later transaction on
that same backend, or is excluded by a completed takeover fence. Reconnecting
another socket proves nothing. No record above H is pruned; removing it
would recreate a recovery gap atop already existing tail rows. Bound a void's
wait; termination rechecks exact identity and the whole blocker set. If safe
termination cannot be established, pause and reacquire, never skip the hole.

### 6.2 Outcome table

| Original-transaction evidence | Caller and history treatment | Publication |
| --- | --- | --- |
| Complete asserted results, COMMIT, idle ReadyForQuery, no warning | Confirmed synchronous commit; retain result until ordered release | Resolve, release only when W covers it |
| Explicit pre-COMMIT raising/validation/deadline error with original transaction acknowledged aborted | Known abort; durable void; bounded fresh-fact O fallback within the original deadline, or return the named failure | No R cascade; advance only after void confirmation |
| Lost/incomplete reply, transport loss, COMMIT warning or undecidable result after final dispatch | Unknown; §6.3 key race and certificate may decide while the result is held; otherwise metadata-free `E_COMMIT_OUTCOME_UNKNOWN`, no automatic rerun | Stalls at the hole; cap further dispatch |
| Lease lost before dispatch | Unsent intent refuses ownership; an assigned hole belongs to new-owner reconciliation if the old fence is gone | No stale-owner void |
| Lease lost after dispatch | Actual confirmed result, else unknown; new owner excludes old sessions and reconciles | Old process publishes nothing new after loss |
| Continuation/result processing fails after proven commit | Preserve history; never call it an abort or reapply | Exactly one terminal completion claim |

### 6.3 Unknown outcomes, durability and lost replies

The key race settles **whether** the original can commit. A void winner
proves it cannot; R3 permits a bounded rerun only after all its witnesses pass,
with the same invocation identity, fresh facts and original deadline. A
committed-record winner proves the original committed and **must never rerun**.
A lost void reply repeats the same key race. Absence alone never permits retry.

A visible committed record need not yet have completed its synchronous wait,
especially after cancellation/termination warnings. Before treating an
unconfirmed original as durable, end/exclude its backend and perform a later
**WAL-bearing fenced synchronous certificate**, checking its write count and
COMMIT. Its WAL follows the original visible commit, so the confirmed flush
covers it. A lost certificate remains unresolved and is retried/reconciled;
`pg_xact_status` without that durability evidence is insufficient. This is an
exceptional-path flight, not per-request publisher work.

A proven committed request may return its exact retained Rust result once W
covers it and only while its single completion claim remains unconsumed. If
the response was already lost/returned unknown, no later contradictory reply
is sent. After process loss an ordinary unkeyed request has no persisted
result: recovery retains its commit but never reconstructs a result or replays
the HTTP invocation. A new unkeyed HTTP retry is a new invocation and can apply
again. Keyed retry uses its bound durable receipt (§6.7), including across
owners. No fresh-cluster xid-epoch assumption survives into production.

### 6.4 Evidence retention and pruning

Keep rev 4's **head-bound pruning proof**, but replace its fixed sequence
floor: **1,000 / 4,525 ≈221 ms at N=1**, too short for a B round trip plus
delivery/re-entry. A new point snapshot at V≥H cannot repair a lost delta
interval for `/changes`, G5 validation or sync.

Qualify an evidence duration **T≥5 seconds**, increased if the measured worst
admitted polling/transport/processing gap plus catch-up allowance needs more.
At the qualified maximum aggregate sequence rate q, retain at least
`E=max(1000, ceil(q*T)+burst allowance)` sequences below H, **and retain until
every admitted cursor passes**. Count voids and O public sequences in q;
include the bounded dispatch burst, not just a window's mean. At 4,525/s the
five-second term alone is **22,625 records**. Increase E before admitting a
higher rate; shrinking it is a separately qualified policy change. Report
retained time, records and bytes, including the cost on mixed readers.

Let F be the durable **pruned-through** sequence, co-published with H. **No R
request, void or reservation prunes.** A fenced synchronous catch-up may move
F monotonically only up to `min(max(0,H.s−E), oldest admitted cursor)` (or
`max(0,H.s−E)` with no cursor), deleting evidence only in `(F_prev,F]` in that
same transaction.
Ordered maintenance follows the same rule. Cursor admission/progress and prune
selection are serialized: pin a cursor c≥F before admitting its snapshot and
keep the pin until it advances or its declared lease ends. Include in-flight
readers, held polls, G5 validation bases and sync consumers; a pin cannot
expire while its admitted snapshot is still running. Bounded cursor count,
lease/progress and byte limits stop admission if necessary, rather than
evicting valid cursors just to make pruning pass. Disconnected/expired clients
below F get explicit resync under the existing contract; such resyncs are
counted, never reported as passing live delivery.
Pins that may outlive the serving process need durable cursor leases, or a
takeover prune hold through their lease/re-admission window; restart cannot
silently forget an admitted retention obligation. Charge that mechanism too.
Conversion records the actual existing F and cannot recreate pruned evidence:
hold pruning and accumulate the qualified window before advertising it or
raising the admitted rate. Legacy gaps still require explicit resync/refusal.

A delayed reader opening after prune sees the co-committed H/F, chooses V≥H
and can check its cursor against F; an earlier snapshot retains old evidence
through MVCC. Every admitted interval `(c,V.s]` therefore has contiguous
commit and evidence rows; void evidence is explicitly empty, never missing.
Retention alone is insufficient if consumers silently cap the interval:
the current `revocation::footprint_between` 500-record limit and Postgres
`change_evidence`'s `LIMIT 501` must be replaced for R by bounded chunked
consumption covering the **whole pinned interval in one V snapshot**. Compose
footprints conservatively, charge work and deadlines, and retry/refuse on an
incomplete interval; no truncated scan certifies preservation. That cost and
the W1–W3-plus-writer no-revocation-storm gate belong to qualification (§10).

Keep enriched `_commits` attempt rows above H and tombstones still needed by
a live backend. Below H they must also survive as long as their commit-cursor
and evidence consumers need them: the merge takes the **longest** horizon,
not the shortest. Prune in bounded steps only when every applicable floor and
tombstone condition permits. `_ops` keeps its replay horizon, `_log` its sync
horizon and continuations their reconciliation horizon independently. Missing
evidence never means no change. Catch-up lag, retained bytes, open attempts
and tombstones have admission limits; when safe pruning cannot progress,
retain and pause rather than delete proof.

### 6.5 Crash recovery and takeover reconciliation

Before serving reads **or** writes after restart, takeover, failover or
unreconciled ownership loss:

1. In **one transaction**, claim the expired lease under store-port §5.2's
   database-clock protocol, start the `pg_blocking_pids` watcher, obtain the
   store's **`pg_advisory_xact_lock`**, take the owner-row `FOR UPDATE`, then
   update the token/holder/lease and commit. Exclusion is held **through the
   token commit**: acquire/unlock/update is forbidden. Keep the watcher looping
   while the exclusive request waits, including through bounded savepoint
   retries, so newly granted shared locks that barge ahead of the waiting
   exclusive request are still observed as blockers. Terminate only the
   verified whole set of prior-token blockers (§6.6). A restart likewise
   excludes its old-token sessions. Keep the owner-row fence for O/legacy
   transactions, and confirm takeover before reconciling or admitting work.
2. Under the new fence and correct database continuity/incarnation, read H/F
   and all retained singleton records above H through the highest visible
   committed record (certified in step 4). Check r/s mapping and identities;
   reconstruct each interior hole from its neighbours and synchronously void
   it. Old qualified backends are gone, so no missing original can later
   commit. Unrecorded trailing intent has no
   durable effect; do not persist/replay the dead queue or reuse an attempt.
3. Verify exact commit counts for every reserved sequence, exact evidence
   above the persisted retained floor F (§6.4), no tail record above H outside an
   attempt, matching log/receipt references, no row stamp in a void and
   consistent two-image bounds. Receipt-only revisions use their creating
   revision. A mismatch refuses with a named R-reconciliation error, never
   fills evidence by guessing. Records below the floor are not required to
   have pruned evidence.
4. In the **certificate transaction**, re-read the maximum retained attempt
   row's **revision/sequence and full identity** from enriched `_commits`,
   after all exclusion and hole resolutions, and recheck exact coverage through
   it. A scan bound captured before the fence or before that transaction is
   insufficient. An unexpected higher/changed maximum refuses and restarts
   reconciliation; it cannot be certified as a lost trailing reservation.
   Write a fresh-attempt, WAL-bearing synchronous head/certificate covering
   the reconciled prefix, **never below prior H** (retain H if no attempt
   extends it), preserving F, and confirm it. **Only then** set W=H, install
   fresh G5/G6 state, reseed sequences/effective time and serve. A lost recovery
   reply repeats fenced reconciliation; no output trusts a visible head alone.

A committed original's images and records are atomic; a missing attempt left
neither, so a reconstructed void is a no-op. Exclusion prevents resurrection;
the final certificate makes every preserved record durable. Every previously
acknowledged request was in W and durably represented, so reconciliation
cannot lose it. PostgreSQL recovery/failover still obeys store-port §5.4's
HA/continuity contract: an async history rewind is not repaired by R.

### 6.6 Session fencing, deadlines, back-pressure and connections

**Session fence.** Each R-capable physical data session first completes
`pg_advisory_lock_shared` on the store key, for its **lifetime**. Only **after
the grant**, in a **later READ COMMITTED command with a fresh snapshot**, may
it validate the current holder/token, store incarnation, generation and every
admitted digest against its expected owner binding. If it waited across
takeover it must see the **new** binding and refuse the old token; a snapshot
from the lock-wait command cannot qualify it. "Later" means a separate
statement whose snapshot is taken after the lock call has returned: the check
may not run inside the locking statement, a CTE or multi-statement simple-query
string evaluated against an earlier snapshot, or a `REPEATABLE READ`/
`SERIALIZABLE` transaction (or session default) whose snapshot predates the
grant; R sessions pin `default_transaction_isolation=read committed` and the
session-reset path re-establishes it. No R body runs before that
qualification completes. No transaction pooling.

Qualification belongs to that exact backend and uninterrupted lock lifetime.
**`DISCARD ALL`, advisory unlock/unlock-all, backend replacement or disconnect
clears it**. A backend whose post-grant qualification **fails** releases its
shared lock (or disconnects) before reuse, so takeover's watcher never mistakes
an unqualified holder for the renewed owner and wait on it forever; along with prepared/warm state; even on the same socket, reacquire
the shared lock and revalidate all bindings/settings/catalogs before any R
body. Failed admission stays pending. Never silently resume under a cached
token. The owner watchdog latches lease loss and rejects unstarted work.

Every compatible successor, **including flag-off owners**, must unconditionally
obtain the matching **exclusive transaction** advisory lock and publish the
token **in the same transaction**, holding exclusion until its commit (§6.5).
Do not condition this on an R marker: an old owner can create its first shared
session **after** the successor's lease claim. The watcher uses the existing
whole-set role/store/token and PID/start checks to terminate blockers; it is
already running before the exclusive request and keeps polling that waiting
backend, including barging shared holders. Foreign or unkillable blockers
make takeover fail closed. Shared acquisition is not assumed FIFO: a session
granted before exclusion may finish an old-token body, which reconciliation
must include, or be terminated and roll back/become ambiguous; a session
granted **after** exclusion waits through the token commit, then its later
validation sees the new token and refuses the old binding. There is no
unlocked old-token interval between exclusion and publication. This replaces
per-transaction R key shares without permitting an old-token commit after
takeover. O writers retain fence-first row locking; session acquisition
precedes application/head locks to avoid
cycles. Hash collisions cost availability, never cross-store authority.

**Spike check:** `git diff 9ee365bbd6 a450/spike-r -- snapback4/crates` shows
`postgres/ownership.rs::StoreLease::claim` already starting `Watcher` before
the fence request; its materialized CTE takes `pg_advisory_xact_lock` in the
same `tx` that later updates `_owner` and commits. `Watcher` loops over
`pg_blocking_pids` while acquisition waits. `postgres/pipeline.rs` acquires
the shared session lock before a later `DO` checks token/store id. Thus the
spike is stricter than rev 5's prose on atomic token publication. It does
**not** establish the full protocol here: the exclusive path is flag-gated,
mixed flag-off owners are excluded, full incarnation/generation/digest and
qualification-reset coverage are unqualified, and recovery/max-row
certification is deferred. The pre-token trigger/first-session-after-claim
tests are useful evidence, not a witness of every barging interleaving (§10.2
item 5). This is a source inspection, not a new executed test result.

**Mixed versions.** Production cannot inherit the spike's exclusion of
flag-off owners. First deploy a fence/format-aware release to **every potential
owner**, with R off; persist the compatibility requirement, and ensure old
binaries are refused by their previously deployed opening check. An old binary
that ignores a new marker is not fenced by the marker: an installation lacking
that check needs a stopped, all-owner upgrade before R. Compatible flag-off
owners honor exclusion, image readers and recovery even while serving only O.
Turning R off requires the drain; downgrade requires stopped reconciliation
and a supported format conversion, never merely unsetting the flag.

**Deadlines/admission.** Preserve 32 executing mutation workers and the spike's
bounded **32-request handoff queue**, not 64 executing writers. The extra cohort
absorbed response/permit-return overlap and removed its measured 503s. Intake
keeps its original 100 ms deadline and any earlier body deadline; independent
expiry must run with all workers blocked. Queued work opens no DB connection.
Pool waits, footprint holds, preparation and fallback consume original budgets;
never reset them. Invocation deadline and absolute authority expiry are distinct:
retain §3.3's qualified clock bound/dispatch supervisor resample and WF's
cumulative pre-COMMIT budget including delivery reserve. R has no regular
opener sample, so qualify a conservative reserve from same-transport control
flights, else use fresh two-flight execution; do not invent a zero reserve.
Relative SQL timeouts or the spike's >5 s session headroom cannot replace the
absolute authority assertion. Reset statement/lock and PG17 transaction timeout
only after all raising checks; COMMIT remains uncancellable, possibly past the
invocation deadline. No cancellation converts unknown into abort.

**Back-pressure.** Cap running flights by actual K session loans, total open
reservations at 512, queued requests/bytes and retained result/footprint memory.
Stop dispatch if H lags over four catch-up intervals; reserve progress for
voids, reconciliation, lease renewal and catch-up. A 250 ms unresolved void
stall pauses admission and surfaces retryable store failure; a lost lease
refuses immediately. Waiters hold no session while waiting for W. Saturation
is a retained capacity failure, not grounds to widen SLOs or connections.

**One ≤32 budget.** All owner, lease, control, O, R, reader, setup/reconnect and
maintenance sessions count, including openings and retiring sockets until gone.
Round 2 restored this with exclusive writer/control loans from the reader pool
(29 data connections plus owner, lease and optional second O writer); the
35-total sensitivity is non-comparable. Reads may pipeline only outside any
exclusive transaction custody. A loan lasts through confirmed COMMIT/ROLLBACK
or disposal of the ambiguous backend; no read can enter a writer transaction.
K is elastic, readers reclaim idle loans, and a measured mixed-read floor and
control priority prevent starvation. No permanent K=32 reservation plus readers.

Round 3 may fold owner/lease/control duties into data sessions to recover
capacity **only if its evidence preserves independent lease progress, session
lock lifetime, notifications, exclusive transaction custody and total-session
accounting**. A saturated pool must still renew or stop. Until witnessed, use
the restored round-2 allocation and charge its pool wait. Driver placement is
measured, never a reason to block the one mutable Engine or let concurrent
workers mutate it without the sequencer/publication boundaries.

### 6.7 Keyed/receipted writes

The SDK normally sends keyed operations: an unkeyed benchmark is not full
product qualification. Initially keyed and receipt-only/refusal members route
to O **after R drains**, preserving bound preflight, replay-before-judgment,
wrong-store refusal before replay and post-lock serial receipt re-check.
This is complete behavior, with its measured cost, not an R speed claim.
It is also a **default-on gate**: keyed W4 and SDK 1% mix, including every
R→O drain they cause, must meet §10.3's same A/B rungs. If fallback cannot,
build and qualify keyed R or seek the author's explicit **unkeyed-only,
opt-in** ruling; an unkeyed headline cannot enable R by default for SDK users.

A later keyed R slice must lock `(principal,op id)` in U, retain the full
operation/raw-argument/store binding, validate receipt absence in the final
transaction, and insert the receipt atomically with its creating revision.
`_ops.rev NOT NULL DEFAULT 0` keeps old receipts visible; all compatible
writers explicitly stamp new receipts, even if their result carries an old
public sequence. Preflight uses `rev≤V.r`, waits on an open same key and then
reopens its authenticated snapshot; duplicates cannot execute over a hidden
receipt. A binding mismatch is `E_ID_REUSED`, not permission to execute again.
Lost replies replay exact stored outcomes after publication/recovery, including
renamed operations and narrowed arguments. Same-key copies in O and R never
overlap phases. Gate this slice on HTTP/SDK duplicate, expiry, takeover and
replay witnesses. Effects, unbounded writes and other excluded families remain
fully supported on O; admitting them to R requires new complete footprints
and publication/claim proofs, not removal of their tail records.

## 7. Interactions

- **G5/G6:** invalidate/install only with W; G6 reads at installed W under its
  separately qualified grant, fresh authority and clock contract. R's hidden
  writes need no global read drain or per-request G6 gate closure. Ownership
  uncertainty invalidates grants; session write fencing alone cannot authorize
  a paused old process's CPU-only reads. R does not make G6 default-on.
- **Maintenance/schema evolution:** authority/time writers, activation, adoption,
  index changes, backfill selections, restore and graduation are barriers.
  Stop admission, drain, confirm H=W, then perform the existing fenced
  conversion and generation change. Rebuild plans, helpers, mirror and reader
  bindings before R resumes. Renewal must remain live; bounded head-bound
  pruning/vacuum may run during R only within their proved invariants.
  An online schema conversion overlapping R is outside the initial scope.
- **E/ordered C:** mutually exclusive with R; one durability/publication rule per
  owner. Existing P/WF ordered fallback keeps its own guarded final protocol.
- **SQLite:** R is **Postgres-only**. SQLite uses the existing single ordered
  writer, `BEGIN IMMEDIATE`, batching and ordinary WAL snapshots; it gets no
  advisory session fence, R reservations or two-image columns. It remains a
  serial semantic oracle, with explicit mapping of PG voids to no-ops. No SQLite
  concurrency gain or new format is claimed.
- **Agent ergonomics:** lane choice, client minima, handoff and retries belong
  to the engine/SDK. Quarry rules, metering, typed states and the common path
  remain; doctor/check explain fallback and incompatible deployments. No app
  author must choose a lane, manage a watermark or guess whether to retry an
  unkeyed unknown. Publication is a separate qualified path, not this RFC edit.

### 23.1 The competitive gate (replaces §8.2's authorizing gate and §13 Q3)

**Where and how.** The campaign runs on expo-build-450b with the §10.3
one-host runner and the real ≤32 pool, under unchanged SLOs. It interleaves:
- the candidate;
- flag-off main of the same commit;
- the Supabase advocate;
- the Convex-on-Postgres advocate.

Each measurement gets a fresh service. Arm order rotates. Every run is
10 s warm-up plus 20 s measured, on a quiet host with the contamination
census and fixed durable settings. Advocates may re-tune only before the
window. Other hosts can stop the program but cannot pass this gate.

**Deciding rungs.** Use five predeclared repetitions at the qualifying
ceiling and at the first failing rung above it; three-repetition scouts may
find the bracket. Every repetition must pass:
- write intended-arrival p99 ≤100 ms, or read p99 ≤50 ms;
- measured errors ≤0.1%;
- exact durable counters against all acknowledgements, including warm-up.

A 4/5 fails. Every failure is retained.

**Ladder and tie-break.** The headline ladder is 100·2^(k/2). §9's quarter
rung is used only when the candidate and the best competitor share a
headline rung and fail the next one. If both pass or both fail the quarter
rung, the cell is a tie. A quarter rung never reverses a headline-rung loss.
Quarter-rung wins are reported beside the headline tie, with §9's
adoption-after-results disclosure. Latency, sent mean, CPU and WAL never
break a tie. An unrun next rung leaves the cell untested. A shared pass at
the harness's 128,000/s limit is a tie with the upper frontier untested.

**Win, tie and untested.** A cell is a **strict win** when the candidate's
qualifying rate is strictly above both Supabase's and Convex's in that
campaign. A tie or an untested cell fails the gate.

**Pinned competitor rungs** (Grok). These are the latest accepted
same-method passes. If a competitor fails one of them, the cell is
inconclusive; one disclosed advocate check and one full rerun are allowed,
and the second result stands.

### 23.2 Postgres CPU (replaces the +30% stop and §13 Q2)

The +30% PG CPU stop and the ≤0.35 ms/write threshold are withdrawn as
blocking rules. ≤0.35 remains a non-blocking optimization target. PG
CPU/write, WAL bytes, syncs and maintenance are published for every cell,
with aligned accounting windows.

**Evidence correction (Sol).** Round 4's 0.146 ms/write and 104 B/ACK
comparator is raw Postgres. Flag-off main in that window was about
0.185 ms/write and 616 B/ACK, against R0's 0.474 and 811. Cost ratios must
match identities, loads and windows.

**Why a one-CPU profile.** CPU decides the outcome when Postgres has about
one core: a small managed instance, or many tenants on one server. The
**one-CPU profile** reproduces that. It changes S1 in only one way: the
private Postgres process family, background workers included, runs on one
predeclared logical CPU with an aggregate quota of one CPU-second per
wall-second, with identical placement for every system. App/proxy and
generator placement, memory, `shared_buffers`, storage, connection limits,
durability, fixture and A/B delays stay as published. The report records
CPU pressure or throttling at the disjoint-write frontier. If the
constraint is never exercised, the qualification is incomplete.

**What the profile gates** (scope from Sol, timing from Grok). All six
write cells and the six read cells must be strict wins under the one-CPU
profile:
- before default-on;
- before any “every scenario” sentence.

It does not block the start of R1–R5. The restored-R0 campaign measures the
profile's write cells for information, so a loss there is known early.
A one-CPU loss limits any claim to the dedicated S1 CPU grant.

If every system fails every rung down to 100/s, the cell is inconclusive
and the universal sentence waits.
