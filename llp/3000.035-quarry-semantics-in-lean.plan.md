## 0. What this records

Tudor wrote a prompt for Opus 5.5 that asks for a formal semantics of the
Contract language and a differential test of Contract's Rust interpreter
against it. Charlie asked for the prompt to be recorded and then adapted to
verify Quarry instead of Contract.

§1 is the prompt verbatim. §2 lists what has to change for Quarry, with the
reason for each change. §3 is that adaptation in full. §4 assesses whether it
is worth doing, and concludes that the full scope is not. §5 is the plan
adopted instead. §6 lists what is left open.

Nothing here has been run yet. This is a plan, not a result.

## 1. The original prompt (verbatim)

Recorded 2026-10-07 as Charlie relayed it. Contract lives
outside this repository.

> Here's the prompt for Opus 5.5
>
> Write an axiomatic and operational semantics for the Contract language.
> Then write a code generator backend for the compiler that emits an
> embedding in those semantics of any user code. Then write a differential
> random testing library that can do large-scale testing of the generated
> code (using the operational semantics) against the Rust interpreter
> version. Then add a large number of test scripts to the repo and update CI
> to do differential random testing between the lean and rust versions

The prompt has four steps, and the adaptation keeps all four:

1. axiomatic and operational semantics (in Lean, per the last sentence);
2. a compiler backend that embeds any user program in those semantics;
3. a differential random tester, Lean against Rust;
4. a large test corpus and CI that runs the differential test.

## 2. What changes for Quarry, and why

**Which program the semantics describes.** Quarry has two candidate
objects: the checked surface program the binder receives, and the IR it
emits (`snapback4-core/src/ir.rs`). The server and device interpreters
already share that IR. A semantics of the IR alone would compare one IR in
two interpreters, so the binder would never be tested. Two of the
disagreements LLP 3000.003 reproduced were binder defects:
`identity(1) + identity(2)` returned 4, and a null assertion ran in the
skipped right side of `true or …`. The adapted prompt therefore defines the
meaning of the checked surface program. An IR-level embedding is optional
and serves to localize failures. It is not the reference.

**What an outcome is.** The original prompt does not say what an outcome
is. A Quarry read or operation returns more: data, completeness, cut sites,
cursors, meter fields, the tables touched, the next expiry, and refusals
with their sites. LLP 3000.009 §11.1 already lists these fields as the
outcome every host must agree on, so the comparison uses the same list. A
differential test that compares only returned rows would miss most of what
Snapback 4 promises.

**Authority is part of the meaning.** Rules decide what a principal can read
and write, and disclosure is the property the simulator's exhaustive test
checks against a model. The semantics must include principals and rules.
That makes disclosure and write authority axioms, not test fixtures.

**The value model is specific.** Integers are i53 and overflow refuses.
There is one total order over values (text compares by code point, not by
UTF-16 unit), one canonical JSON, and one digest. Each of these produced a
reproduced cross-host bug. The Lean model must state them exactly.

**There is more than one Rust executor.** The reference is compared with the
engine over SQLite, the engine over Postgres (on a schedule, as
`scripts/test-postgres.sh` runs today), and the device interpreter over its
memory store. Prefetch on and off, and a meter cut forced at each charge
position, are part of the same comparison (§11.1).

**CI follows this repository's verification law.** The blocking suite
(`scripts/test.sh`) has a 60-second budget. LLP 3000.009 §11 says no new
blocking gate follows from these obligations, and LLP 0189 puts the complete
battery on a schedule, with reds becoming fix-forward tickets. Large-scale
random runs therefore go on a schedule. At most a small fixed-seed smoke
check joins the fast path, and only if it fits the budget. "Update CI"
becomes "schedule the large runs and file what they find."

**Disagreements need a ruling, not a winner.** When Lean and Rust disagree,
the semantics is not automatically right, because it is new and unreviewed.
Each disagreement is ticketed. The ruling (Rust bug, semantics bug, or an
underspecified point the language must decide) is recorded in the governing
LLP.

**Existing assets seed the corpus.** The repository already has the
conformance corpus (`snapback4/corpus/`, 327 JSON cases), the guide's cards
(every card's Quarry is compiled by `crates/snapback4-lang/tests/guide.rs`),
the apps under `snapback4/apps/`, the simulator's rules model, and Kani
proofs of the key encoding. The large test corpus starts from these.

## 3. The adapted prompt (full scope; not adopted)

This is the faithful adaptation of §1. It is kept as the record of what was
considered. §4 explains why it was not adopted, and §5 replaces it. It has
one known flaw beyond its scope. It tells the agent to read the binder and
the interpreter before writing the semantics, which invites a model that
copies the code's mistakes (§4).

> Write an axiomatic and an operational semantics for Quarry, Snapback 4's
> data language, in Lean 4. Put them in a Lake project at `snapback4/lean/`
> with a pinned `lean-toolchain`. Avoid Mathlib unless a proof needs it,
> because build time matters for the scheduled runs. Read `snapback4/AGENTS.md`,
> LLP 3000, LLP 3000.003, LLP 3000.007 and LLP 3000.009 §11 first. Then read
> the language card (`snapback4 guide language`), the binder
> (`crates/snapback4-lang/src/bind/`), the IR (`crates/snapback4-core/src/ir.rs`),
> the value model (`crates/snapback4-core/src/value.rs`) and the interpreter
> (`crates/snapback4-core/src/engine/`).
>
> **1. Semantics.** Define the meaning of a checked Quarry program: the
> parsed and type-checked surface program, before the binder lowers it to
> IR. Cover:
>
> - the value model exactly as `value.rs` states it: i53 integers with
>   refusing overflow, nominal ids, bytes, rows, arrays and maps, the one
>   total order (text by code point), the canonical JSON and the digest;
> - expressions, including short-circuit evaluation, null assertions and
>   pure helper calls with independent evaluation of each call;
> - schema, keys and key order, and point reads, scans, counts, bounded
>   reads and pages, with completeness and cursors;
> - writes, operations, jobs and their at-most-once identity;
> - principals and rules: what a principal may read, what it may write, and
>   which refusal it receives otherwise;
> - the meter: what each step charges, where a budget cuts a read, and what
>   a cut reports;
> - expiry, ephemeral tables and maintained columns, at the level of
>   observable outcomes.
>
> The operational semantics must be executable: a Lean function from
> (schema, store state, principal, program, arguments, meter budget, clock)
> to an outcome record with the fields LLP 3000.009 §11.1 lists. Those are
> data, completeness, cut sites, cursors, every meter field, tables touched,
> next expiry, refusals and their sites. The axiomatic semantics gives
> Hoare-style rules for statements and the system's invariants as theorems
> over the operational semantics. At minimum, prove:
>
> - determinism;
> - that the value order is total and agrees with the key encoding;
> - that no read discloses a row its rules hide from the principal;
> - that no write succeeds without write authority;
> - that `complete: true` is never reported for a read that omitted a
>   qualifying row.
>
> Where the language is underspecified, do not guess silently. List each
> point in an `OPEN.md` beside the Lean project, with the Rust engine's
> current behaviour.
>
> **2. Backend.** Add a Lean emitter to `snapback4-lang` beside the
> TypeScript and Rust emitters (`src/emit.rs`, `src/emit/rust.rs`). Expose
> it through `snapback4 check` (for example `--emit-lean <dir>`). For any
> app's `snapback/*.q`, it emits a Lean module that embeds the schema, the
> rules and every query, operation and job as terms of the §1 semantics. The
> emitted module must elaborate with no `sorry`. Optionally, also emit the
> bound IR as Lean terms, with an IR-level evaluator, so that a disagreement
> can be localized to the binder or the interpreter. The surface semantics
> remains the reference.
>
> **3. Differential random testing.** Build a harness (a crate, for example
> `snapback4-difftest`, plus a compiled Lean executable that reads cases and
> writes outcomes as canonical JSON) that:
>
> - generates well-typed Quarry programs, schemas with rules, store states,
>   principals, arguments, meter budgets and clocks from a seed;
> - runs each case through the Lean reference and through the Rust engine on
>   SQLite and on the device's memory store, and on Postgres when one is
>   available;
> - runs the Rust side with prefetch on and off, and with a meter cut forced
>   at every charge position;
> - compares every outcome field after the documented normalization (none
>   for data and refusals);
> - shrinks each disagreement to a minimal Quarry source file plus store
>   state, and writes it as a replayable case that names its seed.
>
> A named unsupported case never counts as a pass. Report counts of
> supported, unsupported and disagreeing cases separately.
>
> **4. Tests and scheduled runs.** Add a large corpus of differential cases:
>
> - every case in `snapback4/corpus/` that the semantics covers;
> - every guide card's Quarry;
> - the apps under `snapback4/apps/`;
> - each reproduced disagreement in LLP 3000.003 as a named regression case;
> - shrunk counterexamples as they are found.
>
> Add a fixed-seed smoke run to `scripts/test.sh` only if it fits that
> suite's 60-second budget, and leave the Lean build outside it if the build
> does not fit. Put the large randomized runs on a schedule, in the same way
> as the Postgres suite and the drift backstops. Large means at least 10^6
> cases per run across a seed range that rotates. File each new
> disagreement signature as a ticket under `issues/` without duplicating an
> open one. Do not add a blocking gate (LLP 3000.009 §11, LLP 0189).
> Document every command in `snapback4/AGENTS.md`.
>
> When Lean and Rust disagree, neither wins by default. Classify each
> disagreement as a Rust defect, a semantics defect, or an open language
> question. Fix the first two with a regression case, and bring the third to
> Charlie with both behaviours stated. Write up what was built, what is
> proved, what is only tested, and what is not yet covered, as an LLP under
> 3000 with the evidence attached.

## 4. Assessment: is this worth doing?

Charlie asked whether this verification makes sense. The answer recorded
here is that it does, in a narrower form than §3.

**Why it is worth doing.**

- **The bug classes are real here.** LLP 3000.003 reproduced every class
  this method targets:
  - integer overflow handled differently on the device;
  - text ordered by UTF-16 unit instead of code point;
  - `identity(1) + identity(2)` returning 4;
  - a null assertion running in the skipped side of `or`;
  - a JSON 1.25 decoded as zero.

  A filed ticket also records an id/text equality divergence in rules
  (`issues/20260913-snapback4-rule-equality-id-string-divergence.md`). Random
  differential testing finds these classes well. Hand-written cases mostly
  do not.
- **There is a close precedent.** AWS's Cedar is, like Quarry's rules, an
  authorization language with a Rust implementation. Its published method
  is a Lean model, proofs of the security properties, and large-scale
  differential random testing of the Rust code against the model, which
  found real defects. Tudor's prompt reads like that recipe. This record
  cites the precedent from memory and has not re-verified its details.
- **Some claims need proof.** "No read discloses a row its rules hide,"
  proven absence (LLP 3000.031) and a certifiable unread count
  (LLP 3000.020) are claims where a proof over a model means much more than
  a passing test.

**Why the full scope is poor value.**

- **The language moves too fast for a full model.** In the 30 days to
  2026-10-07, `snapback4/crates/snapback4-lang` received about 1,170
  commits and `snapback4-core/src/engine` about 510; `value.rs` received 18.
  A Lean model of the whole language would trail it every week. Cedar's
  method worked partly because its language was small and stable. Quarry's
  value model is close to stable; its reads, residency, meter and derived
  data are not.
- **Most of the bug-finding value does not need Lean.** LLP 3000.009 §11.1
  already asks for comparisons with no reference model: SQLite against
  Postgres, server against device, prefetch on against off, and a meter cut
  forced at every charge position. Each executor is the oracle for the
  others. Meaning-preserving rewrites of a program (`a + b` against `b + a`,
  a value against `identity(value)`, `true or e` against `true`) are
  oracles too, and would have caught both of 3000.003's binder bugs. In
  every version, the hard part is a generator of well-typed Quarry
  programs, schemas, rows and principals, not the Lean.
- **A model written from the code copies the code.** §3 tells the agent to
  read the interpreter first. A model derived that way shares the
  interpreter's mistakes, and the comparison then finds nothing. The model
  must be written from the language card and the LLPs. The engine is
  consulted only to resolve a disagreement or an underspecified point.
- **It does not reach the costliest risks.** Real-host behaviour, sync at
  scale and builder ergonomics are outside it. LLP 3000.009 §11.6 already
  says simulation is not proof of a real host.

**Recommendation.** Build the generator and the Rust-against-Rust
comparisons first (Stage 1). They are useful immediately and already owed
under §11.1. Then add a small Lean core for the security claims (Stage 2),
compared against Rust through the same generator. Leave the meter, expiry,
ephemeral tables, maintained columns and residency out of Lean until they
stop moving.

## 5. Plan

### 5.1 Stage 1: a generator and Rust-against-Rust comparison

**Build on what exists.** Snapback 4 already has:

- schema-driven covering matrices (`snapback4-core/tests/disclosure/generated.rs`);
- paired worlds for disclosure (`tests/paired_worlds/`);
- the conformance corpus, run on SQLite and, through
  `scripts/test-postgres.sh`, on Postgres;
- device-side differentials of the codec and components
  (`snapback4-device/tests/codec.rs`, `components.rs`).

None of them generates random programs, and none compares one case across
every executor. Stage 1 adds those two things and reuses the rest.

**Where it lives.** A new workspace crate, `snapback4-difftest`, with three
parts: the generator and harness as a library, a runner binary for
scheduled runs, and a fixed-seed test target. It adds no dependency to the
shipped crates or to the wasm device.

**The generator.** From a seed, it produces Quarry source text, not IR, so
that the parser and binder are under test. Each program comes with its
schema, rows, principals, arguments, clock and meter budget. It starts with
a core fragment and widens later:

- tables with int, text, id, bool and nullable columns; unique keys and
  indexes;
- rules: allow, deny, owner equals viewer, and an `exists` witness;
- residency: public sync, sync to owner, and online only;
- point reads, index scans with filters and order, bounded reads and pages,
  counts and simple aggregates;
- insert, upsert, update and delete operations;
- expressions with integers near the i53 bounds, text outside the Basic
  Multilingual Plane, short-circuit operators, null assertions and pure
  helper calls.

Every generated program must compile. A generated program the binder
refuses is either a generator bug, or a refusal the generator records as
intended.

**The oracles.** Each case is compared on the full outcome record of LLP
3000.009 §11.1: data, completeness, cut sites, cursors, every meter field,
tables touched, next expiry, and refusals with their sites. It is compared
across:

1. the engine on SQLite against the engine on Postgres, with prefetch on
   and off (Postgres runs where a cluster is available, as
   `scripts/test-postgres.sh` provides one);
2. the uncut run against a run with a meter cut forced at each charge
   position. Each cut must report a cut, and continuing from its cursor must
   reach the uncut answer;
3. the program against meaning-preserving rewrites of itself;
4. the server against a device that has acquired the same rows, on reads
   the device reports complete. This is a later slice: it needs the
   simulator's acquisition path.

**Failures.** Each disagreement shrinks to a minimal `.q` file, rows and
seed, which replays with one command. A disagreement is a defect until
shown otherwise. Each one is ticketed under `issues/`, one ticket per
normalized signature, never duplicating an open one. Fixed defects keep
their shrunk case as a regression case in the repository. Cases the harness
cannot run count as unsupported, never as a pass, and the report gives
supported, unsupported and disagreeing counts separately.

**Cadence.** A fixed-seed smoke run joins `scripts/test.sh` only if it fits
that suite's 60-second budget. The large randomized runs (at least 10^6
cases per run, over a rotating seed range) run on a schedule on a fleet
machine, beside the Postgres suite. No blocking gate follows
(LLP 3000.009 §11, LLP 0189).

**Stage 1 is done when:**

- the core fragment generates;
- oracles 1–3 run;
- shrinking and replay work;
- one scheduled run of at least 10^6 cases has been recorded, with its
  findings ticketed.

**Status (2026-10-07): slice A landed.** `snapback4/crates/snapback4-difftest`
contains:

- the seeded source generator;
- the exact-repeat oracle;
- five rewrite oracles: commute, declarations, identity helper, lazy `and`,
  lazy `or`;
- a let binding;
- the meter-boundary continuation oracle on SQLite;
- structural shrinking and `replay`.

Its fixed-seed tests run in the suite in about 1–2 s.

**The first run.** Seeds 0–99,999 ran on a Linux fleet host in 266 s:

- 3,153,140 engine calls;
- zero disagreements and zero unexpected refusals;
- resumable cuts on 67.6% of pageable reads.

Both shapes from LLP 3000.003 pass: `identity(1) + identity(2)` returns 3,
and a skipped null assertion does not run. The two disagreements found along
the way were harness defects. Their cases stay under `cases/found/` as
regression tests.

**Negative controls.** Two faults were planted in the engine, one at a time,
and each was caught by the oracle aimed at it:

- an order-dependent `+`: `rewrite-commute` reported 252 disagreements in
  2,000 cases;
- a cursor that skips or repeats a row on resume: the continuation oracle
  reported 1,105.

**What slice A does not cover.** Generated programs have one operation and
one varying table. They never declare expiry. They never write enough for
`index_entries` or `rows_written` ceilings to cut, and the public API does
not expose every charge position. Slice B (Postgres with prefetch on and off,
scheduled runs of at least 10^6 cases, ticket filing) and slice C (server
against device) remain, as do generator widening and a list of the fields
the API does not expose.

**Status (2026-10-07): slice B landed.** The harness now runs each case on
the engine over SQLite and over Postgres, with prefetch on and with it off.
It compares the complete outcome record exactly, with no store-specific
exceptions.

**What changed in the harness:**

- Each worker reuses one Postgres schema, restored to the seeded state
  between attempts. A test shows a restored schema gives byte-identical
  outcomes to a fresh one.
- On writes, Postgres checks a reproducible sample of meter positions plus
  the first and last; SQLite checks every position.
- `scripts/difftest-scheduled.sh` runs a calibrated rotating seed window on
  a private non-durable cluster, and files one `issues/` ticket per stable
  signature (`scripts/difftest-tickets.py`). It runs nightly at 02:00
  CEST on the Hetzner host `expo-build-450a` (cron, 8 workers, a 3-hour
  calibrated window). It uses Postgres 17.10 built under
  `~/quarry-difftest`, and pushes tickets with a write deploy key scoped to
  this repository.

**Throughput** is 37,256 cases an hour on an M-series Mac with 8 workers,
below the 100,000 aim. Enumerating SQLite memory allowances on writes
dominates the cost.

**The first finding.** At low `heap_bytes` ceilings, SQLite and Postgres
disagree on about 3.9% of attempts: different cut charges, reads cut on one
store only, and writes committed on one store and refused on the other.
Their scratch reservations differ, and the reported meter does not show the
difference. This conflicts with LLP 3000.009 §11.1. Charlie ruled on 2026-10-08
that the engine charges `heap_bytes` identically on every store, from encoded
value sizes, with a separate internal memory guard per store; the fix follows
slice C
(`issues/closed/20261007-snapback4-heap-accounting-differs-between-sqlite-and-postgres.md`; fixed, see below).

**Negative controls:**

- A planted tie-order fault in the Postgres scan was caught: 725 additional
  disagreements per mode in 2,000 seeds.
- A planted prefetch fault was caught by a targeted test but not by the
  random corpus, because the generator emits no reads that use prefetch
  (`issues/closed/20261007-quarry-store-oracle-prefetch-coverage-gap.md`;
  closed by the widening below).

**The first long run** (unchanged engine, seeds 2,000–295,766, 3 hours, 8
workers on the same Mac) covered 293,767 cases at about 98,000 cases an
hour, with 1.39 billion engine calls. It had no setup errors, no unsupported
cases and no new signatures. Each Postgres mode had 4,597,924 attempts and
195,175 disagreements (4.2%), all under the six known heap and step
signatures above. The SQLite write-repeat oracle passed all 274,096,035 of
its checks. The two prefetch modes gave identical counts. That agreement
says nothing about prefetch while the coverage gap stands. The run reached
293,767 of the 1,000,000 cases requested in 3 hours. It was faster than the
pilot because shrinking new signatures dominated the pilot's time.

**The engine drops Postgres error details** from `E_STORE` refusals, so the
harness carries a wire relay to recover them
(`issues/20261007-snapback4-postgres-store-errors-lose-their-detail.md`).

**Status (2026-10-08): slice C landed.** Oracle 4 runs as
`run-devices` against both device stores: native SQLite and memory. Each device
acquires its rows the client's way: the `/schema` backend, then one
`local.ts::syncRound` of `/sync` snapshot and catch-up pages through
`call_text`. Reads the device publishes without the server compare on the whole
outcome record, except the device's `seq`. Every other read is counted by
reason (all `online-only-*` in this generator). Low ceilings reach the device
only through `call`'s `spent` ledger. Writes compare at three points:
`admit`'s refusal, the predicted row, and convergence after `settle` and a
sync round.

**The run.** 100,000 cases took 875 s:

- **Reads:** zero disagreements on 58,499 compared reads per store, including
  every meter field at the default ceilings.
- **Low ceilings:** 16,920 SQLite-device and 29,632 memory-device disagreements
  among 757,317 positions each, all heap or step accounting. They are the
  device half of the heap ruling: an ~18 KB per-candidate reservation on
  device reads of non-uniform-rule tables, and memory-store pricing without
  SQLite's page scratch.
- **Writes:** 56 per store, a prediction of an insert whose caller-supplied id
  belongs to an unheld row
  (`issues/closed/20261008-snapback4-device-predicts-insert-over-an-unheld-id.md`).
  Charlie ruled on 2026-10-08 to keep these predictions and document the typed refusal; the oracle counts them as the named outcome `predicted-then-refused-unheld-id`, never a pass (11 per store in seeds 0–19,999).

Planted device faults were each caught: reversed memory-scan ties, a dropped
last row reported complete, and refused predictions.

**Status (2026-10-08): the heap fix landed (lane HU, LLP 3000.007 §20.24.5).**
Every store and the device charge `heap_bytes` from one logical ledger; store
scratch moves to a per-store guard (`E_STORE_MEMORY`). On seed 0 with 20,000
cases, the store oracle went from 13,350 disagreements in 312,282 attempts per
prefetch mode to 0 in 309,513, and the device cut oracle from 3,599 (SQLite)
and 6,197 (memory) in 152,124 positions to 0 in 151,057 on each store. The
ten heap found cases (nine device, one Postgres) are retired and the pinned signature sets are empty; the
prediction ticket's write signature remains.

**Status (2026-10-08): the generator is widened (lane GW).** What slice A
did not cover is now generated, by `src/widen.rs`, from a stream independent
of the base generator. A seed it leaves alone is the base case byte for byte.
Frequencies are over seeds 0–19,999:

- **Prefetch-reachable reads** (21.8%): pages projecting `tags[.tag]` and
  `tags[name = .label]`, a `Get` and a unique `Lookup` whose keys vary across
  the page's rows, and loops reading `tags[row.tag]` (2.2%). `tags` mostly has
  an owner read rule.
- **Mutation blocks** (12.3%): lets and let chains, `require`, `if`/`else`,
  several writes to `key` and a second key `k2` (8.2% multi-write), and reads
  after writes (`items[k].score ?? 0`, `exists items[k]`).
- **A prelude** (17.1%): one to three further mutations run in order on the
  same store before `run`, 8.9% as the other viewer. Every oracle compares
  their outcomes, and `observe` reads both keys.
- **Expiry** (16.8%): `expire at .until`, rows expiring before, at and after
  each operation, a clock advancing between operations (28.5% of cases),
  sweeps (6.7%) and `until: now + ttl` writes.
- **Unique clashes** on the upsert insert path (OPEN W4): block writes put a
  seeded row's `tag`.

Shrinking reduces each new shape structurally (a test plants a predicate and
checks the minimum). The report counts each feature under `coverage`.

### 5.2 Stage 2: a small Lean core

**Scope.** It starts after Stage 1's generator covers the core fragment.
The core is the value model, expressions, point reads and scans in key
order, the four rules, and the completeness flag. It is a Lake project at
`snapback4/lean/` with a pinned toolchain and no Mathlib unless a proof
needs it.

**The proofs:**

- determinism;
- the value order is total and agrees with the key encoding;
- no read discloses a row its rules hide;
- no write succeeds without write authority;
- `complete: true` is never reported for a read that omitted a qualifying
  row.

**Independence.** The model's author works from the language card
(`snapback4 guide language`), LLP 3000.007 and the value-model LLPs, and
does not read the binder or the interpreter. Underspecified points go to an
`OPEN.md` beside the model and are resolved there, with the engine's
behaviour stated, before they are encoded.

**The emitter and the comparison.** A Lean emitter in `snapback4-lang`
(beside `emit/rust.rs`) embeds programs in the core fragment, and reports
any other program as unsupported. The Stage 1 harness gains the Lean model
as a further oracle on that fragment. The model is not normative: when it
and the engine disagree, the disagreement is classified as a Rust defect, a
model defect, or an open language question, and an open question comes to
Charlie with both behaviours stated.

**Widening.** The model grows to a further area (the meter, expiry,
ephemeral tables, maintained columns or residency) only when that area has
been stable long enough for the model to keep up. This record leaves "long
enough" to a later revision, which should measure it from the area's own
commit history.

**Status (2026-10-08): the model and its proofs are built.** The model is a
Lake project at `snapback4/lean/`, pinned to Lean 4.34.1, with no Mathlib.
`./check.sh` runs `lake build` (about 15 s cold). It refuses any `sorry`,
`admit`, `native_decide` or `axiom`, audits 38 headline theorems for
standard axioms only, and runs 30 hand-written examples from the guide
cards. All 30 agree.

The model was written under the independence rule. It is an executable
big-step semantics of the core fragment:

- values and their one order;
- expressions, with short-circuit evaluation, null assertions and helpers;
- point reads, pages with `complete` and `next`, `count` and `exists`;
- the four rules, with exact-key `exists` probes;
- insert, upsert, update and delete, with their refusal codes.

Its only meter is an abstract ceiling on the visible candidates examined.

**What is proved:**

- the value order is total, and agrees with an order-preserving key encoding
  (`encKey_agrees`);
- scan order is determined by key order (`pageRead_perm`);
- noninterference: a query's whole outcome is a function of the viewer's
  visible rows (`query_noninterference`). Pages return only readable rows
  (`page_rows_readable`), `count` is exactly the number of visible matches
  (`countRead_eq`), and a hidden insert changes no query
  (`query_ignores_hidden_insert`);
- write authority, per write and per mutation (`applyWrite_authorized`,
  `mutation_authorized`);
- completeness soundness (`pageRead_complete`);
- oracle 2 as a theorem: a cut page's rows, followed by its continuation's,
  equal the uncut page (`cut_continuation`);
- the two LLP 3000.003 shapes (`or_true_skips`, `identity_sum`);
- sound Hoare rules for every statement form.

Four planted model faults each broke the build.

`snapback4/lean/OPEN.md` records 30 open points, with the model's choice
for each. The engine has not been consulted on any of them. The points most
likely to disagree with the engine are:

- whether rule probes see hidden rows (R1);
- which images an unnamed `update` rule judges (R2);
- where null sorts (V2);
- `next` on an exactly filled page (C2);
- the precedence among refusal codes (W1–W4).

**Status (2026-10-08): the emitter and the Lean oracle are built.**

- **The emitter** (`snapback4-lang/src/emit/lean.rs`) translates a checked
  program's surface tree, not the binder's IR, so the binder stays under
  test. It takes the few types it needs (literal typing beside ids,
  positional keys) from the declarations the checker accepted. Anything
  outside the fragment is a named unsupported reason, never a partial
  translation. `snapback4 check --emit-lean <file.q>` prints one file.
- **The runner** is `quarry-oracle` (`snapback4/lean/Oracle.lean`): one JSON
  case per line in, one tagged outcome per line out, one process per worker.
  The model's semantics were not changed for I/O.
- **The oracle** is `snapback4-difftest run-lean`. It compares the engine
  (SQLite, default ceilings) with the model on kind, refusal code, tagged
  data, `complete` and `next` presence. Each side then continues from its own
  cursor, and a mutation's `observe` reread runs on each side's resulting
  store. Meter fields and sites are not compared. Lean-only generator
  variants (`lean::generate`) aim at `OPEN.md`: per-effect and named update
  rules, a probe target hidden by its read rule, nullable and id orders, and
  residual filters.
- **The nightly runner** builds `quarry-oracle` before its campaigns and
  fails if `lake` is missing. Host setup is in `snapback4/AGENTS.md`.

**Negative controls.** Two faults were planted, one at a time, and reverted
with `git checkout`. The engine and binder were confirmed unchanged
afterwards. Each was run on seeds 0–1,999 with the final harness. The
unplanted baseline has 44 disagreements, under three known signatures.

- **`or` evaluates its right side.** A first plant in the interpreter's
  `Binary` short-circuit was not reached, because the binder lowers `or` to
  an `If`. Planted instead in the binder's lowering
  (`bind/program/expr.rs`), it was caught: 241 cases of
  `lean--kind--NULL_ASSERT~bool`.
- **`items`' read rule skipped.** A first plant in `read_authority_inner`
  was not reached by server reads. Planted in `check_rule`, it was caught:
  79 cases under five new signatures.
  - Point reads leaked rows (`data--row~null`, `post-data--row~null`).
  - Non-uniform scans returned hidden rows (`data--arr~arr`).
  - Write refusals changed (`code--E_RULE~NOT_FOUND`,
    `code--E_CONSTRAINT~E_RULE`).

**The run.** 60,000 cases (seeds 0–59,999), 8 workers, release build:

- 54,598 cases supported (91.0%). The 5,402 unsupported are the unpaged
  `sum`, `min` and `max` the model does not have.
- 53,277 passed and 1,321 disagreed, under four signatures. There were no
  harness errors.
- 137,680 engine and model calls; 5,109 reads were followed page by page
  to their end.
- 62 s (about 960 cases a second) on an M-series Mac. A repeat under heavy
  host load took 129 s.

**What the disagreements were:**

- **R2, an open question.** The engine judges an unnamed `update <- R`
  against the next image only (`lean--kind--committed~NOT_FOUND`, 69;
  `…~E_RULE`, 8). The model judges both images, as `OPEN.md` R2 chose. Under
  `update <- .owner = viewer`, a viewer can take over another principal's
  row with a blind `upsert` or `update` that sets `owner: viewer`. Named
  `(old, next)` rules agree.
  - `why NOT_FOUND` and LLP 3000.007 §8 item 7(a) lean toward the model.
  - The rules card does not decide the unnamed form.
  - This needs Charlie's ruling, and it is security-relevant.
  - **Status (2026-10-08, revision 11): an engine defect, fixed.** The
    orchestrator classified it from the documents: the rules card and
    `why NOT_FOUND` say "the update rule judges old and next". A direct
    probe confirmed the takeover on `Engine::memory`, with `read <- allow`
    and with `read <- .owner = viewer`. The engine now judges an unnamed
    `update <- R` as `R[old] and R[next]`
    (`snapback4-core/src/schema/update_images.rs`, applied in `check_rule`),
    on the server's SQLite and Postgres stores and in the device's
    prediction, which share that evaluator. A rule that reads only `id`
    and immutable columns is still judged once. Both shrunk cases now
    replay as agreeing and stay as regressions. A 20,000-case `run-lean`
    has no `lean--kind--committed~*` signature. LLP 3000.007 §8 item 7(a)
    records the rule. This is a security fix and must be published.
- **C2, an open question.** On non-uniform pages and pages with a residual
  filter, a full page carries `next` even when no candidate follows
  (`lean--next--next~no-next`, 799; `lean--continuation-next--…`, 445).
  Following that cursor returns an empty page. Uniform pages without a
  residual filter agree with the model's lookahead. The reads card permits
  both behaviours.
- **A model defect, fixed.** The model gave a cursorless filled page a
  `next` (108 cases). LLP 3000.027 §1 says "a cursorless top-N answer has no
  `next`". The model was corrected, and `./check.sh` passes with 31
  examples. The point is recorded as `OPEN.md` C9 (confirmed).

Apart from R2 (an engine defect, fixed above), no engine or binder defect was confirmed. The oracle also observed the
engine agreeing with the model's choices on R1, V2, V3, V5, C1, C8, W1, W3
and W7. Each is recorded in `OPEN.md` as an observation, not a ruling.

**Not yet compared.** Cuts, under OPEN M1 with `cut_continuation` as the
property. Unique-key clashes on absent upserts (W4). The unpaged
aggregates.
