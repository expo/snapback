# LLP 0327.000: Integration-test target consolidation

**Type:** RFC
**Status:** Draft
**Systems:** Testing, Rust core, Build, Developer experience, Proof/gates,
Project
**Author:** Charlie Cheever / Codex
**Date:** 2026-08-28
**Revised:** 2026-08-28 (initial Draft)
**Related:** LLP 0175, LLP 0189, LLP 0225, LLP 0232, LLP 0276, LLP 0287,
LLP 0325, LLP 0327, `issues/20260820-debug-binary-symbol-bloat.md`

## Summary

Consolidate Snapback's Rust integration tests from 83 separately linked Cargo
test targets toward LLP 0276's goal of no more than 12 workspace targets,
without converting integration tests to unit tests and without placing tests
that require process isolation into one process.

LLP 0327 supplies the measurement LLP 0175 required before this decision:
linking one integration target costs about five seconds even when its
dependencies are warm. The checkout measured for this Draft has 83 integration
targets, 79 under `crates/snapback/tests/`, so target proliferation accounts for
roughly 6.9 minutes of link work and a large share of the 126 GB
`target/debug` tree.

The consolidation unit is a stable **test case**, identified by today's target
stem. Cases move beneath a small number of aggregate target files. A checked
case map preserves targeted execution and records the isolation disposition of
every predecessor target. The target-count goal is subordinate to semantics: a
case that genuinely needs its own process remains separate and is recorded as
an exception rather than being made flaky to satisfy a number.

This RFC does not authorize implementation while it and parent LLP 0327 remain
Draft.

## 1. Evidence and problem shape

### 1.1 Current inventory

`cargo metadata --no-deps --format-version 1` on 2026-08-28 reports:

| Package | Integration targets |
| --- | ---: |
| `snapback` | 79 |
| `snapback-sync` | 2 |
| `snapback-engine` | 1 |
| `snapback-harness` | 1 |
| **Workspace** | **83** |

The 79 `crates/snapback/tests/*.rs` files contain 72,186 lines. Their size is
not the link-cost driver: LLP 0327 measured a 20-line target at 4.8 seconds and
a 42-line target at 5.3 seconds. Every new top-level integration-test file adds
another crate and another link.

The population has also grown from 57 targets when LLP 0175 was written to 83
now. Without a structural rule, improvements to linker or debug settings would
only make continued target growth less visible.

### 1.2 Consolidation changes execution semantics unless it is audited

Separate integration targets are separate processes. Modules inside one
aggregate target share:

- process environment and current directory;
- process-global statics and runtime singletons;
- the test harness's thread pool and panic process;
- inherited file descriptors and signal handlers; and
- one compiled crate-level `cfg` and lint context.

A lexical first pass over the 79 `snapback` targets found these lower-bound
signals:

| Signal | Files |
| --- | ---: |
| environment mutation | 7 |
| listeners or sockets bound in-process | 11 |
| child-process launch | 24 |
| crate-level attributes | 6 |
| platform-specific `cfg` | 9 |
| process-global statics | 4 |
| ignored tests | 1 |

These counts are routing evidence, not an isolation verdict. A listener using
an operating-system-assigned port is often safe to colocate; an environment
mutation guarded only within one source file may be unsafe once another case
runs in the same process. Conversely, a case that launches a child process is
not automatically isolation-sensitive.

### 1.3 Target names are an operator surface

Current LLPs, issues, fixture receipts, comments, and reproduction commands use
forms such as:

```sh
cargo test -p snapback --test graph_corpus_v1 paired_worlds
```

Moving the source without a compatibility surface would make those commands
fail even when the test still exists. Historical evidence must not be rewritten
to pretend it used a new command, while current operator instructions need a
stable way to address the same logical case after its aggregate target changes.

## 2. Decision

### 2.1 Keep integration semantics; reduce only the link units

Tests stay integration tests compiled against public crate surfaces. Do not
move them into product modules merely to avoid a link. Unit tests continue to
live inline per LLP 0276 and LLP 0325; this RFC changes only the physical Cargo
target boundary of existing integration tests.

Under `crates/snapback/tests/`, retain no more than eight ordinary aggregate
targets, leaving four workspace target slots for the currently separate
`snapback-sync`, `snapback-engine`, and `snapback-harness` targets:

1. `artifacts_and_contracts`
2. `server_and_cli`
3. `auth_and_authority`
4. `runtime_and_execution`
5. `data_queries_and_migrations`
6. `realtime_and_sync`
7. `fork_replication_and_storage`
8. `security_network_and_platform`

The names express test ownership, not product crate rank. Stage 0 may merge two
buckets when the measured case map makes one empty or tiny, but it may not add a
ninth ordinary `snapback` aggregate without amending this RFC or recording a
semantic-isolation exception.

Each aggregate is a top-level Cargo integration target. Existing case files
move beneath non-target-bearing directories:

```text
crates/snapback/tests/
  auth_and_authority.rs
  cases/
    auth_and_authority/
      auth_bypass_v1.rs
      auth_invalidation_boot_replay_v1.rs
      ...
```

The aggregate file attaches any required module-level `cfg` and imports each
case with a deterministic module name. Moving a file must preserve its `@ref`s,
helpers, fixtures, ignored markers, and platform conditions. A crate-level
attribute that cannot be translated faithfully to a module attribute blocks
that case's move.

### 2.2 Every predecessor receives an isolation disposition

Before moving a case, the implementation-time census assigns exactly one:

- **mergeable** — no process-shared state or all such state is already
  collision-safe;
- **mergeable after repair** — inject configuration, allocate unique resources,
  scope environment mutation, or move the sensitive operation into a child
  process before consolidation;
- **serialized in aggregate** — shared state is intentional and an explicit
  aggregate-owned lock preserves semantics without relying on test order; or
- **process-isolated** — the test requires a separate Cargo target.

Serialization is not a cheap substitute for process isolation. In particular,
an environment variable read by other concurrently running modules cannot be
made safe by a lock known only to the mutating case. Such a case must either
remove the ambient dependency, use an aggregate-wide guard adopted by every
reader, execute the sensitive leg in a child, or remain process-isolated.

Every `process-isolated` disposition names the exact property that requires the
boundary and the failed alternative. The target-count metric reports these
exceptions separately. LLP 0276's “≤12” remains a goal, not authority to erase
semantic isolation.

### 2.3 Stable case identity is separate from aggregate target identity

Introduce one checked data record, initially
`scripts/rust-test-cases.v1.json`, containing for every predecessor:

- stable case id (the old Cargo target stem);
- package, source path, aggregate target, and module name;
- isolation disposition and evidence note;
- platform and ignored-test facts;
- current targeted command; and
- predecessor target name for migration lookup.

The record is exhaustive against `cargo metadata` plus the declared
`tests/cases/` roots. It is not a second test inventory: before LLP 0287's
cutover it is a Rust-specific migration/lookup view checked against the current
proof mechanisms; after that cutover it becomes a generated view of LLP 0287's
canonical proof inventory.

Provide a stable operator façade:

```sh
scripts/rust-test-case graph_corpus_v1 paired_worlds -- --nocapture
```

The façade resolves the case id to package, aggregate target, and
module-qualified filter, prints the exact Cargo command, then `exec`s it. It
does not hide Cargo output or normalize failure. A bucket move therefore does
not break the targeted operator command again.

Historical LLPs, closed issues, and retained receipts keep the commands they
actually ran. Current guides, open tickets, code comments, and active LLP
acceptance commands migrate to the stable façade or the new exact Cargo target.

### 2.4 Preserve test-set and harness behavior exactly

For each migration slice, compare the old and new `cargo test -- --list`
projections after normalizing only the new module prefix. The following are
invariants:

- every predecessor test function appears exactly once;
- ignored, measured, and platform-inapplicable dispositions agree;
- no `#[should_panic]` or async-runtime behavior changes;
- the workspace proof retains `--no-fail-fast` and its current test-thread
  policy;
- aggregate modules do not depend on execution order; and
- a targeted case run executes only that logical case unless the operator asks
  for a wider filter.

Module-name collisions fail the case-map check. Shared `common` modules move to
an explicit helper owner rather than being copied into several buckets without
a declared reason.

### 2.5 Selection follows logical ownership, not the new coarse binary

Affected verification must not broaden every edit to an entire 10,000-line
bucket merely because Cargo links one binary. The proof inventory owns logical
case/path relationships independently of the aggregate compile unit. It may
choose the aggregate target for execution while passing a module-qualified
filter when the selected cases are safely filterable.

If a bucket has aggregate-level setup or a case declares a cross-case
invariant, the inventory marks the bucket indivisible and affected selection
runs it whole. Silent widening is acceptable for safety; silent narrowing is
not.

## 3. Migration

### Stage 0 — freeze the exact case and reference census

Generate the initial case map from `cargo metadata`, enumerate test functions
and ignored/platform facts, and inventory current tracked references to
`cargo test --test <old-id>`. Record:

- target count by package;
- no-op and marginal link metrics from LLP 0327;
- compiled artifact bytes;
- old test-list output; and
- the lexical isolation signals in §1.2, followed by human/agent inspection of
  each signaled case.

No target moves in Stage 0.

### Stage 1 — prove the aggregate mechanism on low-risk cases

Choose small `mergeable` cases with no ambient mutation, crate-level `cfg`, or
special ignored command. On the implementation branch, compare old and new
test lists and run both forms before removing the predecessor target. Land the
case map, stable façade, checker, and first aggregate together so no test lacks
an owner.

### Stage 2 — move ordinary semantic families

Move one bucket at a time. Each slice:

1. refreshes the case/reference census;
2. repairs every `mergeable after repair` case before or with its move;
3. compares normalized old/new test membership;
4. runs the affected bucket and the case-map fixtures;
5. updates current operator references; and
6. records target count, link wall, and artifact bytes.

Main's ordinary optimistic-landing rule applies: affected evidence binds the
slice; the complete battery runs on LLP 0189's scheduled cadence.

### Stage 3 — audit the isolation remainder

Move cases marked `serialized in aggregate` only after stress execution at the
normal workspace test-thread setting demonstrates the guard. Retain every
`process-isolated` target with its disposition in the case map.

If the workspace remains above 12, file one bounded filesystem ticket per
isolation reason family. Do not extend a migration indefinitely or weaken a
boundary to make the scalar green.

### Stage 4 — make proliferation mechanically visible

Add a report-only target census to LLP 0327's standing build-loop record. The
case-map checker refuses an unclassified new top-level integration target and
requires a new case to join an aggregate unless it declares and tests a
process-isolation reason.

The ratchet is an affected proof check, not a complete-battery or publication
veto. A deliberate exception is reviewable data, not an undocumented bypass.

## 4. Acceptance

1. Every pre-migration Cargo integration target maps to exactly one stable case
   or one documented retained process-isolated target.
2. Normalized old/new test membership, ignored status, and platform disposition
   are equal for every slice.
3. The complete workspace has no more than 12 integration targets, or every
   excess target has a semantic-isolation disposition and an open burn-down
   ticket; no correctness claim depends on the scalar alone.
4. `scripts/rust-test-case <old-target-id>` runs the intended logical case after
   consolidation and rejects unknown or ambiguous ids.
5. Active operator documentation contains no stale direct command for a moved
   target. Historical evidence remains unchanged.
6. A new top-level target or an unowned file under `tests/cases/` fails the
   inventory check.
7. The normal `rust-tests` proof passes with the existing thread and
   no-fail-fast semantics, followed by one scheduled complete-battery result.
8. LLP 0327's standing metric records before/after link wall, target count, and
   artifact bytes. Keep the consolidation only if the measured developer loop
   improves without a material test-runtime or flake regression.

## 5. Non-goals

- No test deletion or cadence demotion.
- No conversion of integration tests into unit tests to hit the count.
- No adoption of `cargo-nextest`, `mold`/`lld`, remote caching, or a different
  debug profile; LLP 0175/0327 keep those as separate experiments.
- No merging source files into giant authored files. Cases remain separate
  modules governed by LLP 0325.
- No product crate-boundary change and no reopening of LLP 0225/0276's rank
  decisions.
- No rewriting of retained historical evidence to use commands that were not
  run.
- No exact-HEAD complete-proof landing protocol; LLP 0189 and LLP 0232 continue
  to govern cadence and optimistic landing.

## 6. Open questions

- **OQ1 — Exact bucket membership.** Stage 0 owns the checked mapping. The eight
  names are decided here; individual case placement remains evidence-driven.
- **OQ2 — Aggregate-wide serialization primitive.** Prefer removing ambient
  state or using child processes. If a shared guard remains necessary, decide
  whether the existing test support can own it without adding another runtime
  dependency.
- **OQ3 — Retained target budget.** The current lexical audit cannot prove how
  many cases truly need process isolation. The ≤12 result is plausible but not
  claimed until Stage 0 dispositions exist.
- **OQ4 — Proof-inventory sequence.** If LLP 0287 implementation starts first,
  put stable case identity directly in its canonical inventory and generate
  `rust-test-cases.v1.json`; do not create a temporary authored authority.

## 7. Why this is a child of LLP 0327

LLP 0175 deliberately required evidence before target consolidation. LLP 0327
provides that evidence and explicitly leaves the design out of scope. This
document consumes the measurement, decides the missing isolation and operator
contracts, and returns before/after metrics to its parent. Keeping the decision
as `0327.000` makes that dependency visible and avoids a second top-level build-
economics programme.
