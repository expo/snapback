# LLP 3000.008.003: Whole-application performance

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 application startup; device acquisition and persistence; query and write latency; HTTP; SQLite; memory; synchronization; package size; performance measurements
**Author:** Codex (for Charlie Cheever)
**Date:** 2026-09-14
**Revised:** 2026-09-14 (initial; fourth gap in the holistic assessment)
**Related:** [LLP 3000.008](./3000.008-holistic-product-excellence.rfc.md), [LLP 3000.002](./3000.002-end-to-end-resource-bounds.research.md), [LLP 3000.008.001](./3000.008.001-understandable-data-placement.rfc.md), [LLP 3000.008.002](./3000.008.002-complete-client-experience.rfc.md), [LLP 3000 §3](./3000-snapback4.explainer.md#3-the-bakeoff-protocol)

## Summary

Optimize the complete application path and its sustained operating costs.
Faster individual interpreter, database or transport stages are valuable when
they improve those outcomes without moving disproportionate cost elsewhere.

Snapback 4 has measured fast paths and important improvements. Its current
records also show workload-dependent latency, expensive full-browser startup,
payload costs and experiments that trade one case's speed for another's.
This child organizes that work without inventing a new benchmark framework,
raising a ceiling or treating every microbenchmark loss as a release veto.

## 1. What the existing measurements establish

| Evidence | Supported observation | Limit |
| --- | --- | --- |
| [Full Clique run](../benchmarks/runs/2026-09-13-snapback4-clique-0004/README.md) | The completed 0.2.6 application replay settled 167,157 actions; full-corpus browser startup passed in 21.446 s. | One builder artifact; startup includes authentication, navigation and rendering; two midpoint predicates failed and code changed between checkpoints. |
| [Startup audit](../benchmarks/runs/2026-09-13-snapback4-clique-0004/replica-startup-audit.md) | Removing unnecessary application counters reduced snapshot work, alongside improved whole-startup observations. | No device-apply span; no demonstration of quadratic scaling in the replacement store. |
| [HTTP and membership record](../benchmarks/runs/snapback4-public-catalog-20260913/README.md) | There are repeatable narrow improvements, cached-query differences, concurrency costs and retained regressions. | Warm local HTTP workloads do not establish hosted, device, realtime or matched-durability write performance. |
| [Client](../snapback4/metrics/client.jsonl), [wasm](../snapback4/metrics/wasm.jsonl) and [publication](../snapback4/metrics/publish.jsonl) records | The shared Rust device has a separately measured payload, and publication records identify actual packaged artifacts. | Different revisions and optimization settings cannot be combined into one invented shipped-size number. |

The later 0.2.8 Office membership runs had higher p50 case medians in 32 of
39 cases than the earlier 0.2.5 runs, while improving several wide-feed tails.
Those are different time windows and include intervening changes. They justify
investigation, not causal attribution to one compiler flag or a current
controlled win over another backend.

## 2. Measure what the application experiences

| Journey | User-visible endpoint | Costs recorded alongside it |
| --- | --- | --- |
| First visit | First useful authorized screen. | Shell/auth, runtime transfer and compilation, initial query, render. |
| Acquire for offline use | Required content, thread and search work with the server unreachable. | Rows, bytes, requests, device apply/persistence, indexes, peak and retained memory. |
| Reopen offline | Useful screen from already durable state in a new process/realm. | Runtime availability, store open, query and rendering; no warm-module shortcut. |
| Send | Local visible admission and authoritative settlement, measured separately. | Device persistence, prediction, server transaction, stream, reconciliation and render. |
| Reconnect after work | Required observations converge and queued writes settle correctly. | Backlog size, replay work, retries, bandwidth and sustained memory. |
| Concurrent use | Useful point, thread, feed and search interactions while other clients are active. | p50/p95/p99, failed requests, throughput, fan-out and resource saturation. |

First useful content may arrive before acquisition is complete. That is a
good product outcome when coverage and freshness remain truthful. Report both
endpoints; do not improve a startup number by relabeling partial readiness as
full offline availability.

## 3. Budgets and comparison rules

Preserve [LLP 3000 §3's bakeoff bars](./3000-snapback4.explainer.md#3-the-bakeoff-protocol),
including acquisition within 2× the measured floor and the existing loop bar.
Interaction targets remain descriptive where the root says they are.

For an additional journey, agree its device, fixture, timing boundary and
target before measuring a candidate. Until that happens, report observations
without calling them a pass against an unstated product budget. Keep all
required history, membership and offline behavior in the fixture. A smaller
but semantically incomplete result is a failure, not a faster equivalent.

Use paired or interleaved comparisons on the same source/toolchain and
equivalent state when attributing a change. Retain losses and errors, choose
representative hot and changing inputs, and distinguish stage timing from
the complete request. Name instrumentation overhead and cache history.

For writes, match or explicitly distinguish durability and failure guarantees.
SQLite process-crash behavior and physical power-loss durability are different
claims. An unsafe persistence setting cannot count as an equivalent speedup.
Keep publication's SQLite build input distinct from an ordinary developer or
native framework build when comparing their numbers.

## 4. Optimization order

### Data and work before lower-level tuning

First remove unnecessary application facts from device partitions through
the residency child's recipes. Measure source rows, derived rows, indexes and
log work separately. Preserve the required result domain and explain any
write amplification introduced by a materialized projection.

Then locate repeated queries, serial startup waits, redundant observation
work, excessive boundary serialization and unnecessary persistence operations.
Use the actual client path: a fast engine behind a costly initialization or
transport path can still produce a slow screen.

Only then choose changes to indexed scans, merge planning, rule probes, reader
connections, allocation, HTTP dispatch or package representation based on the
identified bottleneck. Retest the complete affected journey and a small set
of meaningful adjacent cases. A smaller stage interval does not guarantee
lower concurrent request latency.

### Total resource behavior

The runtime meter bounds an operation's logical work. It does not alone bound
all live HTTP work, whole-commit materialization, device memory, historical
partition logs or replay of a large outbox. LLP 3000.002 remains the owner of
those resource questions; resolve them where a measured path demonstrates the
need, including fair progress under concurrent activity.

Acquisition horizons do not enforce exact long-lived holdings. Exercise an
aging device and a server with write churn, including retained history and
queued work, before claiming bounded storage. Retention changes require an
explicit offline/replay contract; silently deleting deduplication or history
state is not a storage optimization.

### Runtime bytes and memory

Keep the shared interpreter while testing a measured device diet. Report
shipped JavaScript, wasm, native linked size, compression, download,
initialization, peak memory and local-query cost with their exact builds.
Evaluate the [existing diet proposal](../issues/20260913-snapback4-wasm-device-diet.md)
against its correctness controls; its early number is not the size of every
later package. Do not count only JavaScript when comparing a wasm-backed client.

## 5. Evidence using existing tools

Extend the existing storage measurement, browser/native witnesses and retained
Clique probes only where they lack the timing boundary needed for the next
decision. Keep raw results in their existing records, alongside input and
artifact identity. No new monitoring product, frozen registry or blocking
matrix is proposed.

Long experiments run separately from the affected test loop. Verification
binds the changed semantic inputs and measured artifact; a moving main does
not require rerunning expensive work whose inputs did not change. Publication
continues through its existing qualification path.

## 6. Acceptance and stop conditions

1. A complete browser and native application record distinguishes first
   usefulness, offline acquisition, reopen, send and reconciliation. Missing
   coverage is visible rather than filled by a related microbenchmark.
2. The hub's required thread and search content is durably usable offline
   within the existing acquisition bar on the stated host. Comparison floors
   cover equivalent required data and persistence work.
3. A claimed optimization improves its named whole-application target while
   reporting adjacent concurrency, memory, size and correctness tradeoffs.
   An unresolved material regression is explicitly dispositioned.
4. A published-pin run preserves the full product requirements and exact
   result checks; authentication refusals, lost writes and truncated answers
   do not count as successful throughput.
5. Reopen, backlog replay and write churn expose the actual lifetime resource
   costs and limits. Any promised bound has a defined workload and retention
   contract rather than being inferred from a request meter.

After three unsuccessful correction rounds, use the existing loop rule to
escalate or narrow the experiment. A result may conclude that a workload needs
a different projection or lies outside the intended scope. It must not raise
the ceiling or redefine the required data to manufacture a win.

## 7. Open decisions

Choose the first complete journey and its reference device for focused work;
recommend browser hub startup followed by concurrent feed/send/reconnect.
Decide any missing journey targets before measuring the candidate. Broader
claims about hosted conditions, physical devices and durability wait for
their own evidence. This child commissions no new fleet run by being written.
