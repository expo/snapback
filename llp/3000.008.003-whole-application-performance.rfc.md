## Summary

Measure the application path before choosing an optimization. This accepted
increment is one browser acquisition/offline-reopen experiment using existing
witnesses, with honest boundaries and artifact identities. It is not a new
benchmark framework or a promise to tune every subsystem.

## 1. What the existing measurements establish

The [0.2.12 calibration](../benchmarks/runs/2026-09-14-snapback4-clique-astra-0.2.12/README.md)
records 634 ms for a cold 100-conversation replica. It does not replace the
older [21.446-second full-corpus browser startup](../benchmarks/runs/2026-09-13-snapback4-clique-0004/README.md).
The old audit attributes neither number to the retired JavaScript store.

The [HTTP record](../benchmarks/runs/snapback4-public-catalog-20260913/README.md)
retains wins, losses and non-adopted experiments. Its current
[membership-feed follow-up](../issues/20260914-snapback4-membership-feed-query-cost.md)
requires requalification after intervening source changes. That is a separately
owned investigation, not a license to tune from old results.

Client, wasm and publication records refer to different artifacts/toolchains.
Their byte numbers must not be combined into an invented current shipped size.

## 2. Measure what the application experiences

| Endpoint | Evidence needed |
| --- | --- |
| First useful content | Authorized query/render after the actual client opens; identify any shell/auth work outside the measurement. |
| Durable acquisition | Required seeded data is usable with server requests blocked, with actual transferred rows/bytes and persistence work accounted for. |
| Offline reopen | New JavaScript realm, retained runtime/backend/store, server unavailable; useful local query and exact result checks. |
| Send and recovery | Distinguish visible durable admission from authoritative settlement and any later replay receipt. |

The existing constructor waits for initial sync. Name that boundary rather
than calling it progressive first content. Do not relabel a partial local
result as full offline acquisition or an online warm reopen as offline reopen.

## 3. Budgets and comparison rules

Preserve [LLP 3000 §3](./3000-snapback4.explainer.md#3-the-bakeoff-protocol),
including acquisition within 2× the measured equivalent floor. The new witness
observations are descriptive unless they use that actual fixture, host and
floor; a different seed or hardware cannot claim that bar by analogy.

Choose the fixture, host and timing boundary before candidate measurements.
Use paired/interleaved runs with equivalent required data to attribute an
optimization. Retain errors and adjacent costs. Logical/process-crash durability
and physical power-loss durability are different claims; do not substitute
weaker persistence for an equivalent speedup.

## 4. Optimization order

### Data and work before lower-level tuning

Measure transferred facts, repeated queries, serial waits, boundary encoding
and persistence before choosing engine or transport tuning. Source/projection
changes preserve the product's required history and result domain. A smaller
but incomplete answer is not an optimization win.

### Total resource behavior

A per-operation meter does not bound all HTTP work, lifetime device memory,
partition history or outbox replay. Those questions remain owned by LLP
3000.002 and specific measured follow-ups. This increment adds no retention
policy and does not silently delete deduplication or history state.

### Runtime bytes and memory

Record the actual runtime artifact/toolchain used by the witness, including
wasm rather than JavaScript alone. A comprehensive wasm diet or concurrent
storage campaign is deferred until a measured cost justifies it.

## 5. Evidence using existing tools

Extend `witness/scale.mjs`, `witness/idb.mjs` and their existing helper only
where a selected endpoint is missing. Retain results in the existing metrics
and a readable run record. Use a headless fleet browser to avoid disturbing
the control machine. Measurements on Linux are not Apple/native qualification.

Long experiments stay outside the affected test loop. Main advancing without
semantic input changes does not require repeating expensive measurements.
Publication uses its existing qualification path.

## 6. Acceptance and stop conditions

1. One browser record distinguishes cold client/acquisition, useful local
   query and fresh-realm offline reopen, with exact seeded-result checks,
   source/toolchain/runtime identity and rows/bytes.
2. Failed or partial acquisition is reported truthfully; no ready flag or
   missing rows can manufacture a fast successful run.
3. A claimed optimization improves the named whole path on equivalent data,
   and reports relevant memory/concurrency/correctness costs. Otherwise the
   result is a diagnosis, not an improvement claim.
4. A separate native/physical-device or full-hub gap is stated explicitly.
   No new gate or universal target follows from this experiment.

After three unsuccessful correction rounds, apply the existing loop rule:
narrow or escalate the experiment rather than redefine required data.

## 7. Open decisions

The selected first journey is browser acquisition plus offline reopen. Broader
feed/send concurrency, aging-device storage, power-loss durability and native
budgets remain future evidence. Keep the existing membership-feed owner and
consume its current-source findings rather than duplicate that lane.

## 8. Measured correction and completion evidence

The [execution record](../benchmarks/runs/2026-09-14-snapback4-excellence/README.md)
separates the labeled baseline debug witness from the integrated production
observation. At 40 groups × 500 messages × 10 members, the latter transfers
20,480 replica events in six snapshot pages plus catch-up, reaches its first
useful local result in 11,658.4 ms, and reopens in a fresh offline realm in
621.9 ms with the compared IDs/content intact and no runtime fetch. The clock
includes per-page response cloning and JSON decoding. No equivalent full-hub
floor or uninstrumented optimization comparison is claimed.

The existing native pending-ID regression also exposed a concrete transport
cost: all 273 writes eventually settled, but response-body waits consumed
11.09 s and exceeded the original 15 s assertion. TCP_NODELAY on accepted
sockets reduced body-read median from 40.7 to 0.3 ms and the same complete
drain from 20.25 to 4.61 s. The test and deadline are unchanged. This bounded
correction follows the measured-cost rule in §4; it does not reopen a general
transport or concurrency campaign. Compiler and binary receipts identify the
Linux debug counterfactual separately from the production browser run.
