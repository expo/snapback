## 0. Summary

Quarry has no editor support. A `.q` file renders as plain text in VS Code,
on GitHub, on npmjs.com and in any diary or review that quotes one. The
compiler, by contrast, already produces everything an editor needs for
diagnostics: every refusal carries a `file:line:col` site, a code, a
message, a rewrite and a guide pointer, and `check --json` prints them.

This RFC proposes the smallest editor investment that is worth keeping
green under a language that changes weekly:

1. **A TextMate grammar and a tree-sitter grammar whose keyword tables are
   generated from the parser's reserved-word lists**, with a fence that
   fails the affected battery when the grammar and the parser disagree or
   when any `.q` file in the tree produces an unknown token.
2. **A VS Code extension** that ships the grammar, the comment and
   indentation rules, and a problem matcher that turns `snapback4 check`
   output into inline diagnostics with the rewrite text. No server process.
3. **Registration of the `quarry` fence name** with the highlighters the
   guide and the docs site use, so the 91 Quarry blocks in the guide cards
   and the README stop rendering as plain text where a renderer can be told
   otherwise.

It explicitly **does not** propose a language server (§6). Hover,
go-to-definition and completion would need span-carrying symbol tables the
binder does not keep, and the users who write most Quarry today, agents,
never see an editor. The trigger that would reopen that question is stated.

The claim is modest and is not a calibration claim: this changes how Quarry
*reads* to a human, not how it is *learned* by a builder. §7 says what is
measured and what is not.

The cost is credibility and reading speed for humans. It is not a cost the
calibration series records, because the calibration builders are agents and
run `check` directly. §7 keeps that distinction.

## 2. What is proposed

### 2.1 One source of truth: the token classes come from the parser

The grammar never carries a hand-typed keyword list. A generator,
`snapback4/scripts/generate-editor-grammar.mjs`, reads the parser's
reserved-word constants and writes the keyword tables into both grammars.
To make that readable from JavaScript without parsing Rust, the lang crate
exposes the lists through one small `#[test]`-free entry point:

```text
snapback4 grammar --json
```

printing the lexical facts the grammar needs, all of which already exist
in the lexer and `reserved.rs`:

| Field | Source | Example |
| --- | --- | --- |
| `comment` | `lexer.rs`: lines beginning `--` | `"--"` |
| `two_character_symbols` | `TWO_CHARACTER` | `["<-", "->", "<=", ">=", "!=", "??"]` |
| `symbols` | `SYMBOLS` | `":(),[]{}.?!+-~*/%=<>"` |
| `hyphenated_words` | `HYPHENATED_WORDS` | `["until-revoked", "delivered-history"]` |
| `table_words` | `TABLE_WORDS` | `after by cap delete …` |
| `binding_words` | `BINDING_WORDS` | `and as break commit …` |
| `declaration_words` | a new constant, `DECLARATION_WORDS`, naming the words that open a top-level declaration (`table`, `query`, `mutation`, `view`, `job`, `effect`, `fn`, `shape`, `use`, `schedule`, `maintain`, `sequence`, `channel`, `action`, `proc`, …) | listed once, in the parser, beside the two existing lists |
| `type_words` | a new constant, `TYPE_WORDS`, the scalar and column types (`text`, `int`, `bool`, `time`, `decimal`, `money`, `json`, `bytes`, `principal`, `image`, `video`, `file`, `enum`, …) | the same |
| `builtin_words` | the contextual builtins (`viewer`, `now`, `commit`, `new`, `device`) | already in `BINDING_WORDS`; split out so they can be colored as values, not keywords |
| `duration_units` | the unit words the parser accepts after a number (`ms`, `s`, `m`, `h`, `d`, `w`, `mo`, `y` and their long forms) | listed once, in the parser |

The two new constants and the unit list are the only parser changes. They
do not alter parsing; they name, in one place, classes the parser already
recognizes by string comparison at scattered sites. Adding a keyword to the
language without adding it to its class list becomes a fence failure
(§2.4), which is the mechanism that keeps the grammar honest.

The verb is `grammar`, not a flag on `check`, because it is a lexical fact
dump with no project input. `check --audit` already takes `--json`; the new
verb follows `cli_flags.rs`'s help and validation conventions.

### 2.2 The TextMate grammar and the VS Code extension

`snapback4/editors/vscode/` holds:

- `syntaxes/quarry.tmLanguage.json`, generated. Scopes follow the TextMate
  conventions so every existing theme colors it: `keyword.declaration`,
  `keyword.control`, `keyword.other.table-line`, `storage.type`,
  `variable.language` for the builtins, `comment.line.double-dash`,
  `string.quoted`, `constant.numeric` with a `keyword.other.unit` suffix
  for durations, `keyword.operator` for `<-` and the rest, and
  `entity.name.type` for the identifier that follows a declaration word.
  Field access (`.authorId`) and index reads (`todos[viewer]`) get their
  own scopes so a rule reads as a rule.
- `language-configuration.json`: `--` line comments, bracket pairs,
  auto-closing quotes, indentation rules (a line ending in `:` indents the
  next line), and `onEnterRules` that keep the lexer's one convention, that
  a deeper line beginning `{`, `and` or `or` continues the line above.
- `package.json` contributing the `quarry` language id for `.q`, the
  grammar, and a **problem matcher** named `$snapback4-check` whose regex
  reads the `file:line:col` site, the code and the message from
  `snapback4 check` output, with the rewrite as the message's second line.
  A contributed task runs `snapback4 check` on save when the workspace has
  a `snapback/` directory with `.q` files. Inline diagnostics appear in the
  Problems pane and as squiggles with no server process.

The extension is published to the VS Code marketplace and Open VSX under the
`snapback4` publisher only after one release has carried it through the
fence; until then it installs from the repository as a `.vsix` built by the
generator.

### 2.3 The tree-sitter grammar

`snapback4/editors/tree-sitter-quarry/` holds a tree-sitter grammar whose
`grammar.js` keyword tables are generated from the same `grammar --json`
output. It covers Zed, Neovim, Helix and GitHub's Linguist, which requires
a tree-sitter or TextMate grammar in a public repository before a language
can be registered (§5).

The tree-sitter grammar is a **highlighting** grammar: it recognizes
declarations, table lines, statements, expressions, shapes and literals
well enough to color and fold them. It is not a second parser of record.
The parser of record is `snapback4-lang`, and the fence (§2.4) checks the
tree-sitter grammar only for the absence of `ERROR` nodes on the corpus,
not for structural agreement with the Rust AST. That bound is deliberate:
structural agreement would make the tree-sitter grammar a conformance
obligation on every language change, which is the cost this RFC refuses.

### 2.4 The fence

`snapback4/scripts/check-editor-grammar.mjs`, registered in
`scripts/affected.mjs` so it runs when `snapback4-lang/src/lexer.rs`,
`parser/**`, or `editors/**` change:

1. Runs `snapback4 grammar --json` and regenerates both grammars into a
   temporary directory; fails if the committed grammars differ
   (the same freshness pattern as `check-generated-artifacts`).
2. Tokenizes every `.q` file under `snapback4/` (excluding `target/` and
   `node_modules/`) with the TextMate grammar through `vscode-textmate` and
   fails on any token that falls to the default scope outside a comment or
   string. Every word the parser accepts must land in a named scope.
3. Parses the same corpus with the tree-sitter grammar and fails on any
   `ERROR` or `MISSING` node.
4. Compiles the 91 guide fences and the README's examples through the
   same two steps, so a card cannot show a form the grammar does not color.

The fence runs in the affected battery, not at every landing (LLP 0189).
A language wave that adds a keyword lands with its grammar regeneration in
the same commit, the way a diagnostics move lands with its registry
regeneration today.

### 2.5 The `quarry` fence name in renderers

- **The guide verb** prints to a terminal and does not highlight; nothing
  changes there.
- **npmjs.com** renders the README with GitHub's highlighter and therefore
  depends on Linguist registration (§5). Until then the README's fences are
  plain, as now.
- **Any docs site that renders the guide cards** (Shiki, Prism or
  highlight.js based) is given the TextMate grammar as a custom language.
  The Snapback 1 docs site at snapback.expo.app is out of scope; this RFC
  binds Snapback 4's own surfaces only.

## 3. What this is not

- **Not a language server.** §6.
- **Not a formatter.** Quarry is indentation-significant with one line
  continuation rule; `check --fix` already applies the spelling repairs
  the compiler can prove. A formatter would be a third opinion on layout.
- **Not a second grammar of record.** The Rust parser remains the only
  definition of the language. Both editor grammars are derived artifacts,
  and the fence enforces that they are.
- **Not a learning-cost intervention.** LLP 3000.011.000's finding is that
  the recurring cost is discovering which ordinary expression changes
  completeness, authority or prediction. Coloring does not touch that, and
  §7 does not claim it does.
- **Not GitHub rendering on day one.** Linguist has usage thresholds that
  Quarry does not meet (§5).

## 5. GitHub and Linguist

Linguist requires, for a new language, a grammar under a permissive
license in a public repository and evidence of use across many
repositories, measured by its own search. Quarry's `.q` files live almost
entirely in this repository and in builders' private apps. The `.q`
extension is also shared with other languages in Linguist's registry,
which means registration would need a heuristic (the `--` comment and a
leading `table`/`query`/`mutation` word suffice) on top of the usage
threshold.

So GitHub rendering is a consequence of adoption, not a lever for it. The
tree-sitter grammar of step 4 is the prerequisite that can be prepared
early; the registration itself waits.

## 6. Why no language server

The case for an LSP is hover showing `why`, go-to-definition from a rule to
a table, completion of column names and keywords, and diagnostics without
saving. Against it:

- **The binder keeps no span-indexed symbol table.** Diagnostics carry a
  `Site` at emission; there is no map from an arbitrary cursor position to
  the bound entity under it. Building one touches `bind/` across a crate
  that lands language changes weekly and is the subject of the difftest and
  Lean programs (LLP 3000.035). That is the opposite of a leaf change.
- **The primary users do not see editors.** The calibration builders are
  agents that run `check` and read the same diagnostic the matcher would
  show. Nothing in eighteen calibrations records a cycle an editor would
  have saved.
- **Diagnostics-on-save already gives most of the value.** The problem
  matcher in §2.2 shows the site, code, message and rewrite inline. The
  delta an LSP adds is latency between keystroke and squiggle. The
  measurement step 2 required (§10) corrected this document's first
  draft: a **debug** `check` on `apps/chat` took 57–94 s under build load,
  not the sub-second figure the draft assumed. That is a compile-and-analyze
  run of the unoptimized binary on a loaded host, and the on-save task
  coalesces saves and allows five minutes, so the editor loop works; but
  the honest statement is that an LSP would not make `check` faster, and
  the `check` latency itself is a compiler concern outside this RFC.
- **It is a surface that must stay green.** LLP 3000.007's calibration
  series shows added capability carrying comprehension cost; an LSP adds
  maintenance cost without touching the measured bottleneck.

**What would reopen it:** humans authoring Quarry by hand in volume, or a
registered experiment showing an agent with editor-resident diagnostics
through Claude Code's LSP tool converges in fewer compiler cycles than one
running `check`. If either arrives, the binder's `Site` and the
`Diagnostic` shape already match what `tower-lsp` publishes, and the
grammar and matcher of this RFC are what the server would sit beside, not
what it would replace.

## 7. What is measured, and what is not claimed

**Measured, by the fence:** every `.q` file in the tree and every guide
fence tokenizes into named scopes with no fallthrough; the committed
grammars equal the generated ones; the tree-sitter grammar parses the
corpus without `ERROR` nodes.

**Observed, once, and recorded in `snapback4/JOURNAL.md`:** a screenshot of
the chat reference app's `schema.q` before and after in VS Code with the
default dark and light themes, and the Problems pane showing one refusal
with its rewrite. This is evidence the thing exists, not a measurement.

**Not claimed:** any movement in the calibration series. The pre-registered
expectation is **null** on every category. If a later calibration note
credits highlighting, that is a surprise to record, not a result this RFC
predicted.

## 8. Risks

| Risk | Mitigation |
| --- | --- |
| The grammar lags the language | Generated from the parser; the fence fails the affected battery on drift; a keyword added without a class is a parser unit-test failure before it is a grammar failure |
| Tree-sitter's indentation handling needs a hand-written external scanner that drifts from the lexer | The scanner implements only `Indent`/`Dedent`/`Newline` with the lexer's grouping rule; fence step 3 runs it over 1,136 files; step 4 is optional |
| The problem matcher's regex breaks when `check` output changes | The matcher is generated beside the grammar from one `check` fixture that the fence asserts matches; or `check --json` becomes the matcher's input through a tiny wrapper task, which is the more durable choice and the one step 2 should take |
| The `.q` extension collides in Linguist and in VS Code with other registrations | VS Code: the extension declares `.q` and a first-line pattern; users with Q/kdb+ tooling can disambiguate per workspace. Linguist: a heuristic, §5 |
| Publishing to a marketplace creates an ongoing publication obligation | Publication follows the repo's rapid-publish posture (LLP 0041); the extension version tracks the `snapback4` version it was generated from, and the README states which |

## 10. Implementation record

**Chunk A, 2026-10-30** (codex `gpt-6-astra` xhigh, lane
`~/projects/snapback-quarry-grammar`, report
`snapback4/reports/20261030-editor-grammar/REPORT.md`): steps 1–3 and 5.
Departures from §2.1, each with the reason the parser gave:

- `TABLE_WORDS` and `BINDING_WORDS` are *reservation* sets, overlapping on
  the write words and containing the builtins; removing entries would change
  name admission. They stay intact. The editor classes are a projection:
  `CONTEXTUAL_WORDS` names the 100-odd clause words the parser accepts by
  position (`first`, `by`, `where`, `every`, …) without reserving them, and
  `editor_binding_words()` is binding ∪ contextual minus table words minus
  builtins. `grammar --json`'s `binding_words` is that projection.
- `DECLARATION_WORDS` has 19 entries read from the parser's top-level
  table, not the RFC's illustrative list: `proc` and `channel` are refused
  forms and `sequence` is a column type, so they are not declaration words.
- `DURATION_UNITS` is `ms s m h d` plus `month(s)`/`year(s)`, which the
  parser accepts only in calendar schedules; the long forms the draft listed
  are not accepted.
- The keyword-drift test scans the parser sources at test time for the
  three idioms the parser uses to compare a `Word` token (`"w" =>` match
  arms, `== "w"`, and the `at`/`take`/`maybe` helpers) and asserts each
  word has exactly one editor class or sits on a short commented exception
  list. A runtime census fails the test if a parser module is added without
  being included in the scan.
- The three compiler-owned pre-expansion templates (`bind/receipts.q`,
  `bind/timeline.q`, `recipe/bridge.q`) carry `@NAME@` and `$name`
  placeholders. They get two template scopes rather than an exclusion, so
  the corpus enumeration stays total.
- The problem matcher is driven by `check --json` through
  `editors/vscode/scripts/check-problems.mjs`, the durable choice §8 named.
- The fence is not in `scripts/test.sh`: measured 2.9–16.5 s depending on
  build load, against that suite's 60 s budget.

Measured: fence 2,905 ms over 1,136 `.q` files and 215 fences on an idle
host; `check` on `apps/chat`, debug binary, three runs: 57.0 / 94.5 / 70.6 s
(§6 corrected). Chunk A committed on the lane branch as `2d45b71e0e`.

**Chunk B, 2026-10-30** (codex `gpt-6-astra` xhigh, same lane; report
`snapback4/reports/20261030-editor-grammar/REPORT-B.md`): step 4.
`editors/tree-sitter-quarry/` holds a hand-written structural `grammar.js`
importing `keywords.generated.js`, which the same generator emits from
`grammar --json`; an external scanner `src/scanner.c` implementing the
lexer's layout rules with a rule-by-rule mapping table in the report and
19 layout tests (CRLF, tabs, Unicode whitespace, the `{`/`and `/`or `
continuation, grouping across lines, EOF dedent flush, incremental
re-parse); `highlights`/`folds`/`indents` queries; a 12-case corpus taken
from `apps/chat/snapback/schema.q`, three fixtures and the language card.
Generated `parser.c`, `grammar.json`, `node-types.json` and build outputs
are ignored; the fence regenerates them. The fence's default run now
includes the tree-sitter pass: regenerate and diff, `tree-sitter generate`
into a temp dir with a C-compilation probe, `tree-sitter test`, then a
census of every `.q` file and guide fence reporting every `ERROR`/`MISSING`
site. `expected-errors.txt` lists exactly the three pre-expansion
templates; a fixture exception would require a `syntax E_QUARRY_SYNTAX:`
reason that the fence verifies against the Rust CLI, and none is listed.
One explicit editor limit: the scanner serializes 251 nested block levels
(tree-sitter's 1,024-byte state cap) and refuses beyond that rather than
truncating. Measured on the orchestrator's run: both passes 7,019 ms, the
tree-sitter pass 2,410 ms of that.

**Review fixes, round 1, 2026-10-30** (report
`snapback4/reports/20261030-editor-grammar/REPORT-R1.md`): all eleven distinct
findings reproduced and fixed without changing Rust parser admission. The
comparison census now includes literal-left equality, `matches!` patterns and
literal slices used by `.contains`, including cross-module uses. The thirteen
text-pattern words reuse the parser's existing constant in the refusal-only
allowlist; they are not advertised as accepted operators. Both grammars are
regenerated; the tree-sitter scanner's small hyphenated-word header and VS Code
`firstLine` are generated and freshness-checked too.

Located security notes, refuted invariant sites and pending review dispositions
reach the Problems matcher; unlocated errors remain on stderr. Nonzero/unknown
task exits notify the editor user. Template exceptions now declare substitution
only: equal-length identifiers replace placeholders in temporary copies, which
must parse cleanly. A syntax-fixture exception is checked from a real temporary
project. The corpus includes `.snapback/` and refuses symlinks loudly. Unicode
whitespace is scoped only on ignored blank/comment lines.

The scanner persists logical CR/LF line starts and follows the lexer's recovered
layout for tabs and off-stack dedents. Unclosed groups get a local
`missing_delimiter` node so surrounding structure survives; highlights and the
fence query it as an error alongside native `ERROR`/`MISSING`. The 20-byte scanner
header leaves room for 250 nested blocks (251 stored levels including root).
The complete fence now runs regression self-tests for the wrapper, extension,
manifest, corpus walk and exception fault probes. The report carries the
red/green evidence and corrected layout mapping; no publication or GUI claim.

**Review fixes, round 2, 2026-10-30** (report
`snapback4/reports/20261030-editor-grammar/REPORT-R2.md`): all six lane items
are fixed without changing Rust parser admission. The comparison-idiom scan
is replaced by an intentionally over-inclusive census of every production Rust
string literal with a Quarry-word spelling, including raw/escaped strings and
macro bodies. Two reviews exposed more idioms each time; enumerating literals
removes that unbounded maintenance problem. Each candidate needs exactly one

and rename suggestions. Templates substitute only their expanders' vocabularies;
the scanner preserves completed layout across ignored extras within its existing

default debug binary. Only reachable authored/generated fixture refutations
produce invariant errors; acknowledged security notes disappear by disposition
index. A real successful synthetic-refutation envelope and red/green regressions
cover the corrections. No publication or GUI claim is added.
