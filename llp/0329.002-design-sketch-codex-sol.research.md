# The thesis

**The right foundation is one small, total, authorization-aware relational transaction language: an author writes a data program once, and the system either derives server execution, local execution, realtime maintenance, persistence, authorization dependencies, and optimistic settlement from that same program, or rejects the program at its definition.**

This is a language-design decision, not an API-consolidation exercise. Renaming thirteen query constructors to one constructor while retaining opaque handlers underneath would preserve the bug. The important property is that two spellings of the same computation cannot receive different capabilities, because there is only one semantic representation and it has no opaque spelling.

# Part 1 — The theory

## 1. The core abstraction is an admitted data program

The unit an author writes is an **operation** over a typed relational database. An operation may only read, or it may produce a transaction. That distinction is inferred from its effect; the author does not choose among “live query,” “offline query,” “JS query,” “server mutation,” and “optimistic mutation.” A read operation is observable continuously by default. A write operation is replayable and predicted locally by default.

The language is a bounded relational algebra plus transactions:

- keyed lookup, selection, projection, joins, `exists`, ordering, bounded windows, and a deliberately small set of aggregates;
- pure scalar expressions and conditionals;
- insert, update, and delete over key-bounded sets, composed atomically;
- modeled authority values such as the authenticated principal and commit time;
- no I/O, process state, ambient time, randomness, reflection, or arbitrary JavaScript during data execution.

TypeScript is only the notation used to assemble this program. Builder callbacks run at build time and construct an immutable typed AST; row values are expression objects, not JavaScript values. A callback cannot branch on a row with a JavaScript `if`, call a package, inspect `process.env`, or hide a loop in a helper. Reusable helpers are fine when they merely compose AST nodes.

The compiler lowers every admitted operation and every authorization rule to the same portable logical IR. From that IR it derives:

- read and write sets, including authorization reads;
- whether authentication is required;
- a minimal materialization and policy-witness closure for local execution;
- query invalidation dependencies and a realtime update plan;
- the optimistic patch, rollback information, and server settlement shape;
- input, output, and error types;
- persistence and eviction keys;
- required indexes and an explainable cost bound;
- SQLite and Postgres physical plans;
- a generated client operation and a capability certificate.

The author never writes `reads`, `writes`, `retainable`, `authorityIndependent`, an invalidation list, or a second optimistic implementation. If the compiler can know it, asking the agent to repeat it creates a new opportunity for contradiction.

The IR, rather than TypeScript or a particular SQL dialect, is the product contract. SQLite is the first execution backend. Postgres is another lowering of the same transaction and isolation semantics, not another authoring mode. The common semantic floor should be explicit: foreign keys, portable scalar types, deterministic collation, well-defined null ordering, and serializable operation outcomes. SQLite may implement this with a single writer; Postgres may use serializable transactions and retry. Programs cannot rely on either engine's accidents.

## 2. Make the language total by making it smaller

I would choose refusal: every admitted core operation gets every core capability, and programs that cannot get them are not core operations.

“Every capability” means the compiler can produce all of these artifacts for the same semantics:

1. an authoritative server plan;
2. a local plan over retained materialization;
3. a realtime maintenance plan, even if the first implementation is conservative rerun-and-diff;
4. a durable intent representation for writes;
5. an optimistic result and inverse/settlement description;
6. a dependency-complete authorization plan.

It does not mean an offline device knows data it has never received, can learn that it was revoked while disconnected, or can predict an authoritative commit timestamp exactly. Those are information limits, not program capabilities. The runtime reports them as state: `hydrating`, `fresh`, `stale`, or `partial` for a read; `predicted`, `queued`, `committed`, or `rejected` for an intent. It never silently substitutes “unsupported.”

This distinction matters. A bounded message query that has completed once can reopen from encrypted local storage with its last acknowledged result. An offline send can update that result immediately if its policy witness and affected window are present. A query never hydrated cannot manufacture messages. If deleting the last retained row would require an unseen row beyond a pagination boundary, the local result becomes explicitly `partial` until reconnection. All operations obey these rules; no constructor or auth spelling changes them.

The price of totality is real:

- Arbitrary server JavaScript is not a database operation.
- Unbounded loops, recursive application code, dynamic table names, runtime code loading, ambient reads, and network calls are impossible in the core.
- Some queries that are easy to write in SQL will be refused until the IR and local materializer can support them.
- Boundedness is part of the typecheck. A collection operation needs a key bound, cursor, or maximum result window.
- Server-authoritative time is a modeled value. Locally it is provisional and settles at commit. Random IDs are generated by a defined client-safe ID primitive, not `Math.random()`.
- Sophisticated incremental maintenance can be expensive to build. Correct rerun-and-diff on the server is an acceptable first lowering; silently dropping realtime or offline is not.

This will lose applications to a general server framework. That is preferable to claiming local-first behavior and making it conditional on an invisible subset of the language. The intended product is an unusually reliable server-authoritative data plane, not a general-purpose application runtime.

There can still be an escape boundary, but it must be a strict capability subset and impossible to confuse with an operation. A worker may consume a committed event, call an external service, and submit a normal operation later. It is never client-callable, live, offline, or optimistic; it cannot introduce a second way to read or mutate tables. Its connected-only nature is present in its name, type, generated output, and diagnostics. There is no `unsafeRawSql`, “turn off analysis,” or handler fallback in an application package.

## 3. Authorization is a relational input to every plan

Authorization belongs beside the schema, expressed in the same relational language, and is compiled into every read and write plan. It is neither an annotation on an endpoint nor an imperative check inside a handler.

Each table is deny-by-default for each effect. A rule is a predicate over the authenticated principal, the affected row, and other policy-visible relations. Reads are relationally filtered, so unauthorized rows do not exist from the operation's point of view. Writes are checked against both the current database and the proposed row inside the authoritative transaction. The client receives only authorized materialization plus the minimum non-secret witness needed to evaluate a prediction.

For a message, the normal rule is “the principal has a membership whose conversation matches this row.” That exact predicate serves four purposes: server read filtering, server write validation, derivation of the local membership witness, and revalidation when membership changes. The operation itself does not say `auth: 'public'`, opt into an authorized lease, or repeat the membership test.

Public access must be an explicit security decision, not the absence of a rule. An unconditional predicate is rejected. Publishing requires a conspicuous `publicData(reason)` construct and produces a security-impact item in the build receipt. Most importantly, public access unlocks no data capability whatsoever. Changing a membership rule to public cannot fix retention, offline execution, or realtime, so the system gives an obstacle-routing agent no reward for doing it.

The offline authorization contract must be stated honestly:

- The server authorizes disclosure when it sends a materialization.
- A per-principal local store persists that disclosed data encrypted with an OS-protected key. Signing out destroys the local principal key and store.
- While disconnected, the client can show the last authorized snapshot and labels it stale. The server cannot retroactively undisclose data, and no system can learn about a membership revocation without communication.
- On reconnection, an authorization epoch and dependency recheck remove newly unauthorized materialization before it is exposed as fresh. Queued writes are always reauthorized in the server transaction and may be rejected and rolled back.
- A product may impose a maximum offline age, but that is a deployment security policy applied uniformly to the principal's cache, not an eligibility switch attached to query syntax.

This is genuine offline behavior, with the unavoidable revocation limit made visible. A design that promises immediate offline revocation is either not offline or is hiding a lease-expiry availability failure.

Rules also need non-interference discipline. Read denial should normally look like absence; write denial should return a stable authorization category without disclosing which hidden membership or row failed. Detailed policy traces are available in local development using synthetic data, but production clients do not receive secret-bearing traces.

## 4. Realtime and offline are two executions of the same dependency graph

Realtime is not a special query flavor. A completed read operation creates a materialization identified by its operation version, principal, and canonical input. The server records the compiler-derived dependency graph. Committed changes either update that materialization incrementally or trigger a bounded rerun and result diff. The client applies monotonically sequenced deltas and persists acknowledged state.

Offline prediction is not a handwritten imitation of the server mutation. The client interpreter runs the exact same transaction IR against its retained authorized snapshot. Authority-only values become typed provisional slots. The resulting local delta is tagged with a durable intent ID and base epoch. The server later runs the same IR against current authoritative state and returns one of three meaningful outcomes:

- the prediction matches and becomes committed;
- the operation commits with a settlement delta, for example a final commit time;
- the operation is rejected, and the generated inverse removes or repairs the prediction.

A stale membership witness may permit a prediction after the user has been removed. That is acceptable because prediction is a user-interface claim, not authority. The authoritative transaction rejects it. The client must make pending state visible and must never tell application code that a predicted write is committed.

This model needs a small local relational store, not merely an opaque result cache. But it does not require a general client replica. The compiler materializes the rows, boundary facts, and authorization witnesses needed by active or retained operations. The client cannot issue ad hoc local SQL. Partial materialization and completeness are first-class values, so a local answer is never presented as complete when the necessary closure is missing.

## 5. The agent is a bounded optimizer, not a reader

An agent author searches, edits, runs, and reacts to the nearest result. It has strong local synthesis ability and weak awareness of distant, delayed consequences. When blocked, it tends to minimize the current error, even if that means widening authorization and leaving a comment about the compromise. This is predictable optimizer behavior. The platform has to make the locally easiest path globally safe.

That implies five design rules.

**One canonical path.** There is one package, one profile, one schema form, one operation form, one client arm, and one development command. No aliases are kept for discoverability. Search results should converge on the same answer.

**Consequences at the edit site.** The editor and compiler show the operation's inferred effects, auth dependencies, local materialization bound, and capability certificate beside its definition. A security policy change shows which operations and rows become newly visible. Nothing important is discoverable only in a guide page about another subsystem.

**Fast, executable feedback.** `snap check --json` should typecheck and plan a small app in roughly a second. `snap dev` should perform schema application, code generation, server start, identity binding, and client handshake as one generation-tracked transaction. It emits one acceptance receipt. A web or Metro client from an earlier generation receives a precise reload response, not a mysterious second app identity.

**Refuse dangerous progress.** Unsupported constructs, unbounded reads, implicit public access, schema/client generation skew, and unverifiable authorization are hard errors. A warning is permission to an agent. The diagnostic gives a safe local repair when one exists, but never recommends weakening authorization to regain a capability.

**A small error algebra.** Keep typed refusal, but not thousands of public codes. There should be perhaps twenty stable machine categories—language, bound, authorization, schema, migration, generation, sync, and settlement—with structured fields, source spans, and nested causes. Prose can improve without changing the category. Every failure includes the violated invariant and the capability proof that could not be constructed.

The documentation should fit the retrieval behavior: a one-page grammar, a generated schema/operation index for the current app, a short cookbook of complete patterns, and compiler diagnostics that link to a single canonical repair. The test fixture behind each cookbook entry is more valuable than another conceptual page.

The primary product metric is median time from an empty directory to a green acceptance receipt, followed by correction-loop count on private offline tasks. Feature count and the best run's ceiling are secondary. Every release should be tested by fresh agents whose context contains only the task and the small index.

## 6. What earns its keep

Keep:

- a Rust authority with SQLite, near-zero idle work, and a portable logical IR;
- server authority, ordered durable intents, explicit pending-versus-settled state, and honest conflict/rejection outcomes;
- private partial materialization, encrypted per-principal persistence, and reconnect repair;
- declared reviewable authorization, expressed as executable relational policy;
- precise refusal and machine-readable green receipts;
- the real-agent benchmark and retained correction diaries;
- MIT licensing.

Remove or postpone:

- an embedded JavaScript engine in the authoritative request and transaction path; the Rust IR interpreter is enough. A JS worker runtime may cold-start only for out-of-band effects;
- multiple client arms and authoring profiles. Ship one TypeScript client and one React/Expo adapter only after the framework-neutral contract is stable;
- arbitrary user code in live reads or mutations;
- cron as a first-class data-program feature. A scheduler can submit an ordinary operation as a service principal;
- asset transformation in the core. Store blob metadata in the database and use a narrow signed-blob service;
- admin UI, generalized extension points, clever query aliases, and generated reference forests before the private-chat benchmark is routinely one-shot green;
- automatic acceptance of expensive plans. The compiler should refuse a materialization beyond configured bounds and explain the cardinality path.

I would also set a public-surface budget before implementation: two top-level exports for definition, fewer than thirty language terms including scalar operators, and four generic client state concepts. A new term must remove one or demonstrate that it cannot be represented compositionally.

## 7. Where the diagnosis is incomplete

I agree with the diagnosis's central claim and with its sequencing conclusion. The capability-by-authoring-form split explains the sprawling names, declared facts, insecure workaround, and much of the client machinery.

I do not think it is the only root cause. “Offline” was also missing a compact semantic contract for incomplete local knowledge, revocation, provisional authority values, and settlement. Without that contract, even a perfect single constructor can accumulate leases, custody modes, and exceptions as engineers encounter the information limits one at a time. The total language and the explicit runtime states above are both necessary.

Likewise, generation identity and dev-loop races are not merely API consequences. They require one generation protocol across schema, server, generated client, Metro/web bundle, and local cache. I am confident the proposed language removes the architectural capability holes; I am less confident that it alone would achieve the desired benchmark without treating that lifecycle protocol as a co-equal product.

My assumptions are that applications will accept bounded retained windows rather than an unlimited offline replica; that showing previously disclosed private data while offline is within the threat model; that most interactive backend logic can be expressed as relational transactions; and that connected workers cover the remainder. Confidence is high on the single total IR, derived capabilities, deny-by-default policy, and automatic prediction. Confidence is medium on the exact materialization budget and the proposed cut between core operations and workers; only corpus-driven prototypes will locate that boundary reliably.

# Part 2 — The concrete API

The following is the complete backend definition for the relevant slice of a group chat. `op` has no read/live/mutation variants. The compiler infers whether an operation is read-only or transactional.

```ts
import { app, t } from "@snapback/backend";

export default app(({ table, principal, rule, op }) => {
  const users = table("users", {
    id: t.id,
    displayName: t.text({ min: 1, max: 80 }),
  });

  const conversations = table("conversations", {
    id: t.id,
    title: t.text({ min: 1, max: 120 }),
    ownerId: t.ref(users),
  });

  const memberships = table(
    "memberships",
    {
      conversationId: t.ref(conversations),
      userId: t.ref(users),
      joinedAt: t.commitTime,
    },
    { key: ["conversationId", "userId"] },
  );

  const messages = table("messages", {
    id: t.id,
    conversationId: t.ref(conversations),
    senderId: t.ref(users),
    body: t.text({ min: 1, max: 4_000 }),
    createdAt: t.commitTime,
  });

  // `sub` is verified by the configured auth adapter. Request input cannot set it.
  const actor = principal({ userId: t.claim("sub").asRef(users) });

  const isMember = (userId, conversationId) =>
    memberships.exists(
      (m) =>
        m.userId.eq(userId).and(m.conversationId.eq(conversationId)),
    );

  const sharesConversation = (leftUserId, rightUserId) =>
    memberships.exists((left) =>
      left.userId.eq(leftUserId).and(
        memberships.exists((right) =>
          right.userId.eq(rightUserId).and(
            right.conversationId.eq(left.conversationId),
          ),
        ),
      ),
    );

  // Every omitted effect is denied.
  rule(users, {
    read: ({ row }) => sharesConversation(actor.userId, row.id),
    update: ({ old, next }) =>
      old.id.eq(actor.userId).and(next.id.eq(old.id)),
  });

  rule(conversations, {
    read: ({ row }) => isMember(actor.userId, row.id),
    insert: ({ next }) => next.ownerId.eq(actor.userId),
    update: ({ old }) => old.ownerId.eq(actor.userId),
  });

  rule(memberships, {
    read: ({ row }) => isMember(actor.userId, row.conversationId),
    insert: ({ next, db }) =>
      db.conversations
        .byId(next.conversationId)
        .ownerId.eq(actor.userId),
    delete: ({ old, db }) =>
      old.userId.eq(actor.userId).or(
        db.conversations.byId(old.conversationId).ownerId.eq(actor.userId),
      ),
  });

  rule(messages, {
    read: ({ row }) => isMember(actor.userId, row.conversationId),
    insert: ({ next }) =>
      next.senderId
        .eq(actor.userId)
        .and(isMember(actor.userId, next.conversationId)),
    delete: ({ old }) => old.senderId.eq(actor.userId),
  });

  const messagesInConversation = op(
    { conversationId: t.ref(conversations) },
    ({ db, input }) =>
      db.messages
        .where((m) => m.conversationId.eq(input.conversationId))
        .orderBy((m) => [m.createdAt.desc(), m.id.desc()])
        .take(100),
  );

  const sendMessage = op(
    {
      id: t.id,
      conversationId: t.ref(conversations),
      body: t.text({ min: 1, max: 4_000 }),
    },
    ({ db, input }) =>
      db.messages.insert({
        id: input.id,
        conversationId: input.conversationId,
        senderId: actor.userId,
        body: input.body,
        // createdAt is a schema-defined commitTime. Locally it is provisional;
        // the authoritative value arrives in the settlement delta.
      }),
  );

  return { messagesInConversation, sendMessage };
});
```

The live query is private and offline-capable without any retention or auth option. Its compiled dependency closure includes the matching messages, the actor's membership witness, the ordered-window boundary, and the relevant policy epoch. Once hydrated, it cold-opens from the per-principal store. Online changes stream as result deltas. Revocation invalidates and purges it on the next contact.

The mutation's optimistic implementation is also absent because it is generated from the operation:

```ts
import { openClient } from "@snapback/client";
import { api } from "./snapback.generated";

const chat = await openClient({ api });

const live = chat.read(api.messagesInConversation, { conversationId });
// live.value: Message[]
// live.state: "hydrating" | "fresh" | "stale" | "partial"

const intent = chat.run(api.sendMessage, {
  id: chat.newId(),
  conversationId,
  body: "Are we still on for five?",
});

// The row is in live.value immediately when the retained membership witness is
// sufficient. Its metadata is `predicted`; commitTime is provisional.
// intent.state: "predicted" | "queued" | "committed" | "rejected"
await intent.settled;
```

If the user lost membership while offline, `run` may still predict from stale authorized state. The server re-evaluates the message insert rule atomically, rejects the intent, and the generated inverse removes the message. The client receives `AUTH_DENIED` and a non-secret message; it never receives the hidden membership trace.

Here is the exact workaround the system must reject:

```ts
rule(messages, {
  // Wrong: an agent tries to make private messages public to “fix” offline.
  read: () => true,
});
```

`snap check` responds at that line:

```text
AUTH_PUBLIC_IMPLICIT: an unconditional read rule would disclose every `messages` row.

Offline, persistence, and realtime do not depend on public access. For private
conversation data, use a membership predicate such as:
  isMember(actor.userId, row.conversationId)

If this table is intentionally public, acknowledge the data-boundary change with
  read: publicData("reason shown in the security receipt")

No client or deployment artifact was emitted.
```

An opaque program fails similarly and locally:

```ts
const broken = op({ conversationId: t.ref(conversations) }, ({ db, input }) => {
  return db.messages.toArray().filter((m) => customAcl(m, input));
});
```

```text
LANG_OPAQUE_VALUE: `toArray()` would move database rows into JavaScript.
The server plan is derivable, but local execution and incremental dependencies are not.
Capability certificate: server=yes, local=no, realtime=no, prediction=n/a — rejected.
Use relational `where`, or move external work to a connected worker.
```

The generated client contains the two app-chosen operation names and their inferred input/output types. It does not generate table clients, query-flavor variants, transport variants, hook variants, retention APIs, or authorization modes. The framework-neutral client has four verbs/concepts: `read`, `run`, `state`, and `settled`; `newId` is the one authority-safe utility. A React/Expo adapter can provide one `use` hook over the same generated operation objects without creating another backend surface.

The definition package exports only `app` and `t`. The callback introduces five definition constructs: `table`, `principal`, `rule`, `op`, and the deliberately conspicuous `publicData`. The complete relational grammar should be held below roughly twenty additional verbs and operators. An author of this chat uses about twenty platform names total, not hundreds of constructors or thousands of generated symbols. More important than the exact count, each name denotes an orthogonal semantic concept; none selects a hidden capability bundle.
