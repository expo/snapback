## Outcome and scope

Reduce the work needed to make a populated account useful, keep foreground
interaction responsive during history acquisition, and make already acquired
knowledge cheap to reopen. Preserve exactly the same authorized data, retained
history, pending work, search results, and asset custody.

This plan addresses [affordable offline acquisition](./1018.008.007-affordable-offline-acquisition.research.md).
Implementer: Codex; planning and implementation date 2026-09-11, runtime start
after commission. The design baseline `b47337b26` includes earlier schema-identity
and collector optimizations; their old cost is not the new baseline. The dated
implementation record below uses current `bf8450849` product inputs.

Proceed with local data-path improvements under the current wire/storage
contracts. Multi-page transport responses, broad notification suppression,
eviction/retention changes, and a second replica remain outside this plan.
Use the existing measurement/witness entry points and ordinary retained run
artifacts. Add no benchmark service, registry, gate, or runtime configuration.

retained heap by owner; measure durable bytes independently of JavaScript heap.

Deliver a short attribution record and select the dominant measurable cost.
Use at least ten alternating matched baseline/candidate browser samples for

Report medians and tails as observed; do not infer a population p95 from a
handful of runs. Native results need their own paired sample set and pinned

Record the exact first-useful predicate (the chosen screen's rows/results and
required authority), and compare checkpoints by equivalent durable acquired

## A2 — Remove unnecessary traversal and preparation

The first concrete candidate is `store/row-values.ts::collectRefs`. It calls
the transforming `mapRowValues` only to collect references, discarding the
arrays/objects that traversal constructs. Replace it with a read-only collector
that visits the same canonical markers and escaped application objects, preserves
first-seen reference order and deduplication, and materializes only the final
reference list. Keep `mapRowValues` for callers that actually transform values.

This extends the earlier `hiddenRefs` cleanup; it must not be credited again
as the same optimization. Pin empty, nested, duplicated, escaped `$row`, null,
asset-bearing, and maximum-depth cases. Preserve malformed-input behavior at
the same validation boundary. A mutable caller object must not acquire trusted
identity because a collector inspected it.

Then inspect `OfflineRuntime.commitMany` in `src/offline.ts` and the
`prepareClosureReceipt` path. If A1 shows repeated preparation of identical
immutable images in one accepted group, prepare that exact row version once
within the group. Key any reuse by actual validated content and current
authority/generation scope, never by row ID alone. Keep receipts, selection,
disclosure, and observation evidence per query. Do not cache dynamic permission
by schema hash or suppress separate verdict/absence checks.

Prefer reuse of existing prepared-row objects/markers to a new long-lived cache.
If durable carriers or the twin copy an already immutable image again, identify
who needs ownership of each copy before changing it. An optimization must
preserve escaped-value isolation, rollback, revocation, and physical byte leases.

Ship the collector independently when its scoped allocation/work improvement
is proved. Select at most one further dominant preparation/materialization fix
at a time; retain a record of which A1 cost it addresses.

## A3 — Preserve incremental commits and foreground opportunities

Inspect `drain.ts`, `client-offline.ts`, `offline.ts`, `image-runtime.ts`,
`store/canonical.ts`, `store/swap-journal.ts`, and the IndexedDB/SQLite carriers
along the measured path. The revision journal and prepared changes already
exist: use them; do not rebuild a full store per page or create another journal.

Two conditional changes are in scope:

1. Where the same accepted store revision causes duplicate materialization or
   evaluation, reuse the revision's prepared result and publish each affected
   observation once. Preserve existing no-op behavior. Do not batch away
   distinct clock, refusal, reset, commit, or terminal transitions.
2. If A1 identifies long CPU runs or serial acquisition monopolizing foreground
   work, yield between fully committed pages before asking for the next page.
   Recheck lifecycle/generation after the yield. Reuse existing serial owners;
   do not interrupt an atomic transaction or reorder admitted FIFO intents.

Do not hold an open store transaction or a short mutation critical-section
mutex across a transport wait. The long-lived ownership lease enforcing one
writer per account stays effective throughout network work. Current
`commitMany` already releases its store transaction and runtime queue before
FullRevalidationRequired transport; preserve that boundary. A yield is justified only by measured foreground benefit; unconditional
per-page delays can worsen acquisition. A foreground mutation that requires
missing authority still waits/refuses according to the existing contract.

If network round trips dominate after these changes, record the result against
LLP 1018.008.004's deferred transport proposal. Do not smuggle batching or larger
envelopes into this implementation. Likewise, excessive durable retention is
a separate policy decision, not permission to evict promised offline knowledge.

## A4 — Verify equal knowledge and user-visible improvement

Before comparing speed, compare the actual acquired dataset and facts. On each
carrier, verify thread pages, never-opened held search, maintained reads, pending
predictions, delivery changes/removals, and eligible asset bytes. At intermediate
checkpoints, cut transport and reopen the physical store; compare answers and
availability against the same baseline checkpoint.

Adversarial controls include persistence failure before commit, interruption
after commit but before publication, repeated pages, superseded generation,
account change during acquisition, revocation, clock reset, and writer takeover.
Failed work cannot advance the durable watermark or lose admitted intent bytes.
The real IndexedDB and Expo SQLite paths matter; an in-memory carrier alone
does not qualify physical recovery behavior.

Use existing `offline-store`, `store-review`, delivery, offline-resume-tail,
and owner/browser/native witnesses. The proposed performance objective is a
clear improvement in the A1-selected user-visible metric; target at least 20%
on the matched full workload, with no unexplained regression in first useful
data, foreground latency, reopen, or memory. This is a planning target, not a
new gate or an existing SLA. Record results even when they miss it. A local
allocation win can land on its own merits but cannot close the end-to-end goal.

Keep the complete runtime at or below 90,000 gzip bytes, with the 80,000 target
and current package-growth guard. Measure integrated bytes; do not relocate
required input or change the measurement roots. Long comparative and physical
restart runs use the existing nonblocking verification path on an appropriate
warm fleet lane. Fast affected checks remain the normal landing work.

## Implementation record — 2026-09-11

Two bounded changes are implemented. `collectRefs` now visits canonical markers
and escaped application fields without constructing discarded parent objects or
arrays. The existing transforming walker remains for its transforming callers.
A separate 1,000-row diagnostic produces the same 1,000 distinct references from
3,000 markers while removing 5,000 `Object.fromEntries` materializations and
12,000 copied field entries. These counts exclude other allocations and say
nothing by themselves about end-to-end latency or retained heap.

The one additional measured change is in `compactSuccesses`: an unchanged
answer can extend evidence only for an existing, positively observed row image.
When `rowObservation` finds no such image, every answer-specific call necessarily
returns no positive evidence. Skip that impossible scan and retain the existing
explicit-negative check. No row, answer, receipt, watermark, outbox entry, byte
lease, or authority transition is omitted. There is no cache, batch, scheduler,
or revision-only notification suppression.

The clean current full-size CPU diagnostic attributed 2,646 ms of a 30-second
sample to success compaction, including 2,562 ms in its effect filter. Its
physical IndexedDB snapshot contained 4,500 messages and 31 committed delivery
acknowledgements retaining 1,550 unseen receipt-row effects. The 4,550 network
rows received at that point were not its durable prefix. This is source-linked
attribution from one truncated profile, not a full-workload performance result.

The collector's affected suite passed 298 tests. After the compaction change,
291 tests passed across `store-review`, `store-review-custody`, `outbox`, and
`offline-resume-tail`. New controls cover escaped literals, encounter order,
duplicates, caller mutation, null/assets, sparse/deep values and malformed
marker boundaries; compaction controls cover missing images/sequences, explicit
removal, older negatives, exact unchanged proofs, retained/clock-only/denied
answers, wrong images and atomic alias/watermark outcomes. Existing carrier
tests cover partial effect discharge, reopen, program replacement and rollback.

### Completed comparison and remaining qualifications

The [retained measurement](../snapback2/metrics/acquisition-20260911.json)
records all ten alternating pairs, exact source/runtime/owner/compiler hashes,
host load, dataset hashes, setup failures and controls. All ten candidates
completed the full 10,008-message acquisition: median **67.414 seconds**, range
66.970–69.953 seconds. All ten baselines were right-censored at 120 seconds,
with 9,500–9,700 physically durable messages. The baseline median therefore
exceeds 120 seconds; the observed candidate median gives a **greater than
43.8% median-time reduction lower bound**. This is not an estimated baseline
median or p95. It clears the scoped 20% planning target, while both versions
remain unqualified for the original 30-second goal.

First-inbox medians were 1,072.5 ms baseline and 1,118.1 ms candidate: a 45.5 ms
increase (+4.25%), retained without inferring either a significant regression
or a first-render improvement from ten shared-host samples. Single clean
baseline CPU/heap diagnostics at 100 and 1,000 messages completed in 1.172 and
4.049 seconds, with post-GC used heap 12.02 and 23.53 MB. These are instrumented
diagnostics, separate from the full-size primary comparison.

All full candidate snapshots have the same 10,008-message content hash.
Post-timing owner-cut thread and never-opened search queries return the held
data. Physical Chromium reopen through public queries passed on all eight
attempts using that protocol, preserving the exact dataset, 50-row history,
and seed search hit; total reopen/control time ranged 8.738–9.853 seconds.
The first two samples instead waited for the template Auth UI and timed out:
the development persona has no held bearer binding. That UI limitation is
preserved, no authentication check was bypassed, and the query controls do
not qualify bearer-authenticated or native UI reopen. Baselines did not finish,
so a full-size matched reopen comparison is unavailable.

Both variants also passed the separate physical checkpoint control. The
existing correctness barrier stopped the next transaction at 1,000 messages;
closing Chromium left exactly 950 durable messages. Reopen preserved that
prefix's content hash and held queries. An offline send and its reserved IDs
survived a second physical reopen, then committed after a successful 200
`/api/resume` response with no reset. At that identical reopened prefix,
diagnostic post-GC used heap was 19.163 MB baseline / 19.159 MB candidate and
IndexedDB usage 6.001 / 5.993 MB. This does not establish full-size memory gains.

The separate foreground probe opened useful thread rows at about 1.5 seconds
and filled the input, but both variants awaited the public online mutation
until the external 90-second harness timeout. No admission, commit or receiving
latency was obtained. The [bounded follow-up](../issues/shelved/20260911-snapback2-full-acquisition-and-foreground-send.md)
keeps that result and the full-size 30-second goal open. There is no foreground
latency verdict or closure of the broader incident from the bulk improvement.

The root's matched canonical five-root runtime measurement is 88,008 gzip bytes
for pristine `bf8450849` and 88,053 bytes for the integrated four-plan change
(+45), below the 90,000 ceiling and above the 80,000 target. The previous
accepted 84,580-byte growth baseline already fails on pristine `bf8450849`;
that inherited growth-guard result is separate from this matched delta. The
integrated byte change is not attributed to acquisition alone. No runtime
measurement input was moved or omitted. The bounded implementation is complete;
the broader affordable-acquisition and foreground goals remain open.

### Follow-up implementation — 2026-09-11

The author commissioned the next diagnostic and repair pass. The
[retained follow-up](../benchmarks/runs/2026-09-11-snapback2-followup-diagnostics/README.md)
records stage traces, matched fixture profiles and source-bound verification.
The send repair removes repeated same-scope writer activation and pre-admission
whole-queue draining, then returns each caller's own durably settled terminal.
A coverage-change guard prevents a skipped carrier swap from resolving that
terminal. FIFO replay, immutable admitted bytes and whole-queue `settled()`
semantics stay intact; LLP 1018.003.000 §4 and LLP 1018.004 §2 govern them.

A second measured change replaces deep copying every retained acknowledgement
with a detached pending key→sequence projection (LLP 1019 §6). It preserves
retry/redelivery, receipt retention and partition custody. The exported custom
`OutboxStore` method changes from `deliveryAcks()` to `pendingDeliveryAcks()`;
custom carriers supporting receipts must implement the new projection.
The full instrumented fixture goes from 66.342 to 53.634 seconds, still above
30 seconds; neither single profile establishes clean performance qualification.
No larger transport batch, retained-data deletion, new index, scheduler or gate
was introduced. The next work is the remaining accumulated-state traversal,
with final profile attribution retained in the follow-up record.
