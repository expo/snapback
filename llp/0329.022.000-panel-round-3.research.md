## Codex — round 3

# Panel round 3 — Codex

## Revised position

The product is smaller than I described in round 2, but the architectural split from that round holds.

I explicitly withdraw the breadth of my earlier “conforming server-side adapter or gateway” language. For a mutable foreign domain, conformance includes control of the authoritative commit order and participation of every write in versioning, OCC, index/aggregate maintenance, and reconciliation. A gateway that merely reads a Rails-owned database while Rails keeps writing it is not a weaker strong path; it is unsound. For the migrated domain, this is Snapback adoption, not backend integration.

P5 does not reverse my round-2 position that a client cast cannot promote remote data into receipt-backed data. It makes the reason sharper and closes the remaining client-side loophole: rows are only positive holdings. The facts that turn omission into absence, a prefix into a complete range, and a policy result into an authorization verdict all require an authority.

So the round-2 conclusions remain: Snapback owns the receipt-backed store and state machine; foreign resources have a separate, non-coercible contract; Aquifer, if retained, coordinates lifecycle and binding rather than data semantics. P2 and P5 eliminate the broad compatibility story around that design.

## 1. Client-side Snapback over a foreign backend

As a general product path, it is dead. It should not become a third public resource family.

A client that has received rows can honestly compute over those bytes. It cannot infer that an unheld row does not exist, that a range is complete, that its copy is current, or that the current principal may see a row. Consequently:

- a positive-only calculation can be a useful projection or lower bound, but it is not an authoritative query result;
- an empty result, `exists == false`, uniqueness check, exhausted range, or negative authorization decision must be `Partial` or go online;
- prediction over known rows may remain a UI speculation, but it cannot decide a guard or inherit Snapback's reconciliation guarantees unless the authority runs the same mutation contract.

Calling that construction “client-side Snapback” would give a row cache the spelling and expectations of the receipt-backed path. The foreign resource already has the honest vocabulary for it: cached, stale, pending, failed, and server-required—not `Fresh`, covered absence, or locally authorized.

There are narrow placements where the embedded engine remains legitimate:

1. device-owned/local-only data, where the device actually is the authority;
2. computation over an explicitly sealed finite snapshot whose completeness and version were supplied by an authority;
3. the ordinary client half of a Snapback client/server pair.

The second case does not rescue arbitrary foreign integration: the source has implemented the missing authority protocol. For mutable shared application data, the product should standardize on Snapback client plus Snapback server. Everything else is remote fetch-and-cache unless and until an authority supplies versioned coverage and verdict evidence.

## 2. What P2 does to Grok's §4

P2 kills the *integration reading* of §4, not the deployment topology.

“Put Snapback in front of Rails” survives only if it means that Snapback is the transaction authority for the selected data domain: Rails submits commands through it or is read-only there. If Rails can still write the same rows directly, the server cannot safely mint receipts. Being physically in front of the read path is irrelevant; ownership of the commit path is the condition that matters.

For the selected domain, that is not meaningfully different from adopting Snapback. It can still be operationally incremental: keep Rails for other bounded domains, UI, jobs, and endpoints; move one set of tables and mutations at a time; even retain an existing physical database if ownership boundaries are enforced. But each migrated domain has one authoritative write protocol. The product should call this **incremental migration/adoption**, not an adapter, bridge, or generic backend integration.

The fundamental constraint is slightly more precise than “one process may write.” Every write must participate atomically in one authoritative order and all required invariants. A source-native transaction hook could theoretically do that without routing HTTP through a Snapback process, but once it advances the Snapback version, validates preconditions, maintains derived state, and emits the protocol's commit record, the source has adopted Snapback's write contract in substance. That is a possible migration technique, not an exception that preserves an unmodified foreign backend.

## 3. CDC is a partial read escape, not a full P2 escape

Plain asynchronous CDC does not restore the full contract. A WAL event arrives after the foreign transaction has committed, so Snapback cannot retroactively validate that transaction's baseline, reject a stale guard, or make a source-side maintained update atomic. If Snapback issues ordinary `Fresh` while committed source transactions are still between the source and its consumer, P2's silent window remains.

CDC is not useless, however, and it does not necessarily recreate every ordering problem. A database WAL already supplies a transaction order. With a consistent bootstrap snapshot, gapless ordered consumption including deletes and relevant schema/policy changes, atomic application of each source transaction, and a receipt tied to the applied source watermark, a trusted replica can establish complete positive and negative knowledge **as of that watermark**. It can also update its own indexes and aggregates atomically with each replicated transaction. In that narrow sense, CDC can support an exact, versioned read snapshot rather than mere “not in my copy.”

That design needs a different state contract—such as `Snapshot(v)` and `Lagging(v)`—unless it performs a source catch-up barrier before issuing `Fresh` and has a sound invalidation stream afterward. It must never issue coverage beyond its applied watermark. Authorization additionally requires authoritative policy inputs and epochs, or verdicts from the source.

CDC therefore has three honest uses:

| Use | Honest outcome |
| --- | --- |
| Bootstrap and cutover | Migration aid; Snapback becomes exclusive writer after cutover |
| Complete WAL-fed read replica | Exact reads as of a named watermark, with lag explicit; no local mutation authority by itself |
| Full Snapback mutation semantics | Requires synchronous source cooperation for preconditions and commit identity; adoption of the write protocol in substance |

I would not put the second row on the core Exact 2 path now. It is a substantial replication product with source-specific failure modes. More importantly, it does not solve the mutation guards highlighted by P5. Treat CDC as future read-replica or migration machinery, not as permission to advertise shared-write Snapback.

## 4. Concrete Exact 2 data story

Exact 2 should expose three deliberately distinct sources of data:

1. **`snapback resource` — the local-first path.** A Snapback server is authoritative and owns writes for a bounded domain. It executes against one commit order and issues versioned rows, absences/ranges, and verdicts. The Snapback client persists those facts, re-executes programs, predicts mutations, submits the baseline for OCC, and reconciles the authoritative result. `Fresh`, `Predicted`, covered absence, and offline authorization exist only here.
2. **`remote resource` — the existing-backend path.** Rails, GraphQL, or another API owns reads and writes. Exact may fetch, cache, retry, and queue commands, but its nominal result type exposes cached/stale/online-required states. Existence, uniqueness, membership, and authorization guards execute at that backend. There is no conversion to a Snapback result based on a provider assertion.
3. **`local resource` — optional device-authoritative state.** This is for genuinely local data, not a replica of mutable foreign data. Its authority and synchronization limits should be explicit.

Aquifer may schedule these resources, scope them to routes/principals, and bind their unchanged states into views if that shared machinery earns its cost. It does not store Snapback rows, normalize the three state vocabularies, mint completeness, or run a second optimistic layer.

For an existing Rails app, the supported journey is concrete: start with remote resources; choose a bounded domain that needs certified offline execution; use snapshot/CDC tooling to bootstrap and shadow-check it if helpful; cut its writes over to Snapback; then declare that domain receipt-backed. There is no moment when the same declaration silently acquires stronger meaning.

The pitch should become:

> Exact 2 has a first-class local-first backend. Adopt Snapback for the domains that need certified offline execution, prediction, and reconciliation; use explicit remote resources for existing backends; migrate domain by domain.

It should stop promising local-first behavior “regardless of backend.” The honest differentiator is not that Exact turns every API into Snapback. It is that the strong end-to-end path is unusually complete, while the boundary to ordinary remote data remains visible and safe.

## Source-check notes

The point-read implementation supports P5 exactly: a visible hit contributes a client row; a hidden hit produces `Null` and only a point trace for that lookup; a true miss contributes an absence to trace and receipt. Scans likewise emit receipt range closure only when every examined candidate is visible. The engine also confirms that its writes, reindexing, and maintained deltas occur within its transaction. The commit-version/OCC portion of P2 is not implemented in this particular file, and LLP 0329.021 correctly labels P2 a design-level argument rather than an observed external-writer test.

One separate spike-hardening issue surfaced in the check: `assert_bounds` validates receipt rows, ranges, and verdicts against the trace/certificate, but does not similarly validate `receipt.absences` against `trace.absences`. Normal internal generation inserts both together, so this does not alter P5, but the invariant should be made explicit before receipts can cross an untrusted boundary.

## Grok — round 3

# Panel round 3 — Grok

**Position:** Round 2’s architecture holds. P2 and P5 do not reopen the tier, the type split, or Aquifer-as-store. They collapse the remaining *foreign* story I left standing.

I already refused a client-side bridge. P5 is why that refusal is soundness, not taste: a client cannot issue the knowledge that makes `Fresh` mean `Fresh`. I already required a Snapback server in front of foreign storage. P2 is why that requirement was still too cheap: a Snapback server that does not exclusively write is not a weaker Snapback. It is a machine that mints silent `Fresh`.

**Move, stated first:** §4 as an integration path is dead. “Runs or embeds Snapback 2” survives only as *adoption* — exclusive writer, migrated write path, or Rails-as-read-only. The product should stop saying “integration.” Round 1’s recoverability clause (“wrong about the word ‘bridge,’ not about the client”) is retracted: a Snapback server sharing a database with another writer is the defect in the silent direction, worse than a client that merely cannot prove coverage.

---

## 1. Is the client-side / embedded placement dead?

**Yes, as a product path over a foreign backend.** The only honest configuration is Snapback client + Snapback server, and that server is an exclusive writer. Everything else is fetch-and-cache. Do not build a third placement.

P5 is not a missing feature. It is the factoring of the receipt:

| Component | Who may issue it | What a foreign client can actually say |
|---|---|---|
| `rows` | the holder | “I was sent these” |
| `absences`, complete `ranges` | an authority | cannot distinguish missing-from-subset from missing-from-the-world |
| `verdicts` | an authority | cannot |

Absence is also what separates `Fresh` from `Partial`. A client-side Snapback pointed at Rails can hydrate `rows` it was given. It cannot honestly answer “is this handle taken,” “are there no unread messages,” or any `exists`-shaped guard. LLP 0329.008 measured those as the largest class of real mutations. A store that cannot speak to that class is not a degraded Snapback. It is a row cache.

**Three placements, so this is not ambiguous:**

- **Snapback client against a Snapback server.** Alive. This is the product. The client does not self-issue absences; it re-executes against a receipt the authority minted. `receipt ⊆ trace ⊆ certificate` stays intact.
- **Snapback engine in the client, pointed at foreign HTTP.** Dead. P5. It can only issue `rows`. If it issues absences, it lies. If it never issues absences, it can never be `Fresh`, and authors will still write uniqueness checks against it.
- **Snapback server embedded in the Rails process.** Alive only as exclusive writer (see §2). That is not client-side placement. It is a write-path migration colocated with the old app.

**Is there a design still worth building?** A “positive-knowledge-only” Snapback — always `Partial`, never absences, never `Fresh` on an `exists` guard — is honest and not worth a product. The foreign type already means “I hold these rows.” Building it inside Snapback’s client is how uniqueness checks acquire Snapback’s spelling. Do not staff it.

Embedded, then, means: embed the *writer*, or do not embed.

---

## 2. Does P2 kill §4?

**It kills the product reading. It does not kill the technical necessity of a Snapback server.**

§4 said: local-first is true only if “backend” means storage behind a Snapback 2 server; a foreign system that wants Exact’s client properties runs or embeds Snapback 2. That sentence had two readings. I intended the first. People would ship the second.

- **Intended:** Snapback is the write authority. Rails is a disk, a read model, or a process that *calls* Snapback.
- **Shippable:** put a Snapback server in front of the existing Rails database and keep ActiveRecord.

P2 says the shippable reading does not degrade guarantees. It breaks them in the direction the client cannot see: commit version does not move, OCC does not run, `maintain.count` / `maintain.sum` drift, and the client is told `Fresh`. LLP 0007 already named this the exclusive single-writer profile. I treated that as an operational note. It is a soundness constraint.

**Is “Rails writes through Snapback” meaningfully different from adopting Snapback?** On the data plane, no. Who advances the commit version *is* the system of record. On the application process, yes: you can keep Rails as HTML, as an admin UI, or as a client of Snapback mutations. That is integrating an *app*, not a *backend*. Product language should follow the data plane.

So:

- Stop describing this as integration, bridge, or adapter.
- Call it migration / adoption.
- The remaining honest shapes are exactly three: (1) Snapback is the only writer; (2) Rails is read-only against Snapback-owned data; (3) Rails is not in this path at all — fetch-and-cache.

Round 1 said founder-wrong was recoverable if the “bridge” was a Snapback server in front of foreign storage. **Retract that.** Server-in-front with a second writer is worse than a client-side bridge. The client bridge fails *openly* (it cannot mint absences, so it cannot claim `Fresh`). The dual-written server fails *closed to the author and open to the bug*: it mints receipts. Silent `Fresh` is the incident.

Does this move me off Snapback-as-tier? No. It moves me off the claim that the tier can be pointed at someone else’s database without taking their writes.

## 3. CDC is not an escape

**Do not consume the foreign WAL in order to share write ownership.** That reintroduces the problem the commit version exists to avoid: two clocks, a lag between them, and read-set validation against the wrong one.

The design is a single monotonic commit version, advanced in the same transaction as the write, against which read-sets and maintained-aggregate deltas are applied. CDC gives you a second clock (LSN / WAL position) and a delay.

- A receipt minted at Snapback version `V` while a Rails write is committed but not consumed is `Fresh` against a version that did not move. Same silent direction as P2.
- OCC on Snapback’s stream cannot see a mutation that has not been applied yet. Uniqueness and membership — P5’s largest class — lose to exactly this race.
- `maintain.count` / `maintain.sum` cannot be applied “in the same SQLite transaction” as a write that already committed elsewhere. Recompute-after-CDC is a different consistency model. Drift windows are receipts you should not have issued.
- Catching up before every Snapback commit (stall on WAL tail) abandons local-first and turns Snapback into a lock on someone else’s log. Treating CDC as a peer that can abort Snapback commits makes Snapback a replica that sometimes writes. Dual-writing *and* consuming the WAL is the classic exactly-once hole.

CDC remains legitimate for two jobs that are **not** this product:

- **Cutover ingest:** copy Rails into a Snapback-owned store, then cut writes. One-time. Exclusive writer after the cut.
- **Read replica with a watermark:** “as of LSN *n*, lag may be *t*.” That is asserted data with a clock. It must not construct a Snapback receipt. An absence in a lagged replica means “not in my copy,” which P5 already forbade the client from saying.

A replica that issues `Fresh` absences is a client-side Snapback with extra machinery. Forbidden for the same reason.

## 4. How an Exact 2 app gets data

Smaller than the pitch. Here is the whole recommendation.

**Default, and the only local-first path.** Author Snapback programs. The client is the Snapback 2 client. The server is a Snapback 2 server. That server is the exclusive writer of its database. Hydration is `ClientStore::hydrate` plus `install_verdicts`. Outcomes are `Fresh | Predicted | Partial(site ids)`. Offline, prediction, local auth, OCC live here. Persistence and restoration of these facts live here. Aquifer does not.

**Foreign systems (Rails, GraphQL, raw HTTP).** A separately named type. Fetch and maybe cache. Writes are calls to that system. States are `Cached | Stale | Failed` — never `Fresh`, never `Predicted`, never an absence that means “does not exist.” No uniqueness guard, no `exists` that authorizes a mutation, no local auth. Aquifer may coordinate this as non-receipt data. It does not grow a completeness case.

**Existing Rails app that wants the first path.** Migrate the write path onto Snapback, or stay on the second path. There is no adapter. There is no CDC dual-write. Rails may remain as a process that *reads* Snapback or *submits mutations* to it. At that point Rails is an Exact client, not a backend.

**Non-server UI state, route coordination, identity isolation.** Aquifer, shrunk, as in round 2. Unchanged.

**What the pitch should become**

Drop: “local-first regardless of backend,” “Snapback in front of Rails,” “bridge,” “embed the client,” “one `useQuery`.”

Keep: Exact 2 is local-first on Snapback, end to end. The client is a replica of the program, not a cache of the last JSON. That is true of Snapback’s database, with Snapback exclusively writing. Other backends are fetch-and-cache and look like it.

That is a smaller story than the founder’s, smaller than my own §4, and still larger than “Aquifer with two provider grades.” I would rather have a visible hole than a receipt over a database someone else writes, or a `Fresh` that cannot tell absence from omission.

If Exact cannot staff write-path migrations, it does not staff connectors instead. It ships the Snapback pair and the foreign type, and it does not apologize for the second one looking like a second one.

## What moves, what does not

P2 and P5 earn a change on **foreign placement and product language**. They do not earn a change on **who owns receipt-backed facts**.

They make Fable’s shared cell more dangerous, not less: a completeness field over dual-written storage or client-issued absences is silent `Fresh` with a respectable name. They do not move me toward Codex’s public Aquifer tier. A binder that must not mint absences, must not advance commit versions, and must not predict is still a binder. P5’s authority split is more evidence that the result type cannot be a projection.

The strongest new objection to round 2 is not “then how do we talk to Rails.” It is “then the local-first product is Snapback-shaped apps on Snapback-owned data, and the rest of the market is the other type.” That is correct. Treat it as scope, not as a defect in the type split.

| Claim | Round 3 |
|---|---|
| Snapback 2 client is the tier for receipt-backed data | **Hold** |
| Aquifer is not that tier; shrink, keep coordination | **Hold** |
| Foreign backends are not providers of that tier; non-coercible types | **Hold** |
| Client-side Snapback over a foreign backend | **Hold rejection; P5 is the reason** — not worth a positive-only salvage |
| Snapback client + Snapback server is the only honest pair | **Hold, now load-bearing** |
| §4: foreign storage behind a Snapback server as *integration* | **Move — dead.** Exclusive writer or read-only. Call it migration. |
| Round 1 recoverability: server-in-front saves founder-wrong | **Retract.** Dual-write server-in-front is silent `Fresh`. |
| CDC as shared-write escape | **Reject.** Reintroduces two clocks. Ingest-for-cutover or watermarked replica only; replica does not issue receipts. |
| Pitch: local-first regardless of backend | **Move — smaller.** Local-first on Snapback-owned data; else fetch-and-cache. |
| Type split / no unified spelling | **Hold; P5 strengthens** — absences and verdicts are not a field a foreign type can grow |
| Codex compose-with-Aquifer-as-public-tier | **Hold rejection** |

The next time someone proposes Snapback in front of Rails, ask who advances the commit version. If the answer is “both,” the receipts are unsound. If the answer is “we will CDC the gap,” they have rebuilt the gap. If the answer is “Rails will write through Snapback,” they are adopting Snapback and should say so.
