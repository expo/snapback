## Review finding (0.0.16 baseline)

The runtime meter bounds selected interpreter operations, while several large
physical operations occur before a charge or outside that meter entirely.
The HTTP host also spends its four workers waiting for changes. Consequently,
four ordinary idle clients can stall unrelated requests, and a query can send
more than its configured output budget while merely reporting incomplete.
Resource accounting needs an end-to-end design that preserves the chosen
runtime-meter substrate.

This research extends [LLP 3000 §9](./3000-snapback4.explainer.md#9-architecture-and-code-review-2026-09-12).
It does not raise a ceiling, add a resource certificate, or assess security
holes; those are outside this review's updated scope.

## Evidence and confidence

**Measured:** with four `/changes?wait=2` requests already waiting, an ordinary
health request took 1,904 ms. The server has four blocking worker loops, and
all four were occupied until the waits expired. The normal client uses long
polling, so this is a small-client-count capacity problem.

**Reproduced:** with a five-byte output ceiling, the core returns the complete
26-character string `abcdefghijklmnopqrstuvwxyz` and marks the read capped.
`charge_output` runs after evaluation, and its false return is not used to
limit the returned data. The configured bound is not an output bound.

**Code traced:** the following physical work is not covered by the public
operation meter in a way that limits peak request cost:

- POST bodies are read into an unbounded string before argument bounds apply.
- `/sync` constructs a full snapshot or page, serializes it and responds while
  holding the shared engine lock. Network response progress can occupy the
  database owner after its computation is complete.
- Cold snapshots materialize all acquired groups. Stream selection reads up
  to a page per group before the global selection, and join expansion can
  make an atomic commit much larger than the nominal page limit.
- Partition logs and applied-operation records have no retention/compaction
  lifecycle. Group-keyed logging removes recipient fanout but does not bound
  accumulation over time.
- Query heap accounting follows selected allocations rather than owning all
  live values, copies, decoded rows and response buffers. It is not presently
  a peak-heap guarantee.
- The TypeScript interpreter omits several axes of the Rust meter, including
  output bytes and heap bytes.

The paths are [serve.rs](../snapback4/crates/snapback4/src/serve.rs),
[partition.rs](../snapback4/crates/snapback4-core/src/partition.rs),
[store.rs](../snapback4/crates/snapback4-core/src/store.rs),
[meter.rs](../snapback4/crates/snapback4-core/src/meter.rs),
[runner.rs](../snapback4/crates/snapback4-core/src/engine/runner.rs) and the
historical `src/replica/interpreter.ts`. That TypeScript interpreter was later
replaced by the shared Rust runner over the
[device store](../snapback4/crates/snapback4-device/src/store.rs); its old
meter omissions above are historical, not a claim about the current device.
This review did not run a large-scale soak or measure a slow-reader stall.
The two measured examples are small deterministic probes, not throughput
benchmarks or a claim about production hardware.

## Boundaries that need owners

| Boundary | Question to answer |
|---|---|
| Receive and decode | What bounds admitted bytes and time before a Quarry argument exists? |
| Storage acquisition | Who bounds physical rows, decoded bytes and temporary results when a semantic read is small? |
| Evaluate and construct | Does the meter reserve before growth, and which live allocations belong to it? |
| Encode and send | What is charged: tagged canonical values, wire JSON, or both? What happens before an oversized result escapes? |
| Acquire a partition | How can a large snapshot or whole commit be delivered atomically without requiring an unbounded memory buffer? |
| Retain history | When can logs and deduplication outcomes be reclaimed, and what do old devices do then? |
| Wait for work | How many idle clients fit without consuming all request executors? |

The public meter also has constraints inherited from the existing design;
physical admission should not be implemented by casually exposing additional
internal work counters. Preserve those constraints while deciding where
physical cost is limited. The separate security review owns any assessment
of disclosure properties.

## Alternatives worth evaluating

A bounded synchronous serving owner can remain viable if waits and network
writes release it, work is admitted before large allocation, and expensive
acquisition is incremental. An asynchronous HTTP layer is another option,
but replacing the transport alone leaves materialization and global-lock
costs unchanged. Adding more worker threads only moves the current failure
threshold.

For replication, compare staged snapshot/commit application with an explicit
maximum admitted partition/commit size. Staging can preserve whole-commit
visibility while transmitting bounded chunks; a fixed admitted size is
simpler but must be discoverable before a device or write reaches the wall.
Neither requires exact horizon eviction, which remains out of scope. Log
compaction likewise needs a minimum resumable watermark and a reset path;
deduplication retention needs its own replay contract before records vanish.

## Focused next work

Fix the clear output and worker-starvation bugs first. Then measure cold
acquisition across group count, rows per group, commit size and retained
history independently; include the temporary server allocations, not only
steady-state SQLite bytes or client heap. Determine which existing ceiling
owns each operation before introducing another counter. Keep these examples
inside existing measurements and tests, without another registry or blocking
suite. The review's HTTP/body/output tickets can proceed while the partition
acquisition and retention choices are researched.

## Implementation follow-up

The concrete R17–R19 and R36 corrections were implemented on the author's
2026-09-13 request. An indivisible query result above the output ceiling now
refuses `E_BOUND`; mutation output overflow aborts the transaction. Canonical
tagged output is counted through a writer without allocating another full
JSON buffer. The response no longer disguises an oversized value as an
incomplete successful query.

The HTTP host admits ordinary JSON up to 1 MiB, seed JSON up to 16 MiB and
asset bodies up to 64 MiB; it limits encoded responses to 16 MiB. Exact-limit
bodies are admitted, malformed/truncated input is diagnosed, and oversized
responses return a bounded refusal. Guards protecting the engine and bound
programs are released before socket response work. Upstream 0.1.1 already
replaced the four waiting workers with one thread per request; the regression
now exercises many waiting change polls beside ordinary traffic.

The HTTP library's fixed-length reader also needed correction: its drop
path allocated the entire declared unread remainder. The pinned vendored
`tiny_http` 0.12.0 patch drains through a fixed 8 KiB buffer and terminates
on EOF/error. Provenance and patch scope are in
`snapback4/vendor/tiny_http/SNAPBACK-PATCH.md`. This is a bounded allocation
correction, not a claim of bounded socket lifetime or thread count.

Publication builds the `production` profile and uses Cargo's reported
executable path, including a configured target directory. The existing
installed-consumer proof checks the packed binary's version and SHA-256
against that executable, then records its actual byte size and profile.
The incremental `release` profile remains an edit-loop choice.
The subsequent compiler comparison selects optimization level 3 for this
production server profile, retaining the bounded output writer. The separate
wasm profile and native xcframework invocation keep their size setting;
LLP 3000 §7 records the latency/size trade and its limits.

Remaining research is explicit: request concurrency and read/write deadlines,
server-side snapshot/whole-commit materialization, total live heap and the
TypeScript meter's missing axes, and partition/deduplication retention.
The current fixes do not establish a global physical resource ceiling. No
ceiling was raised, new blocking gate added, or security verdict made.

## 2026-09-16 review: progress, physical work, and native memory

The new review is pinned to `a0d48a4e6b660e2bfca3de3ef3470ef7787f3d15`
(0.2.26). The earlier HTTP starvation/body-buffer findings are historical:
current serving has separate bounded admission classes and socket deadlines.
This section replaces the remaining-work inventory above where it describes
those mechanisms as absent. Independent Sol and Muse reports and lead
validation are preserved in the dated review record. No whole-system rewrite
is justified by those findings alone.

### A response bound must permit sync progress

`partition::snapshot_page` chooses a row count; `stream` chooses events and
then preserves complete commits; `expand_joins` materializes a historical
group before taking its horizon. None of those counts bounds encoded bytes.
The local client requests 4,000 rows, while HTTP returns `E_BOUND` above
16 MiB. A set of legal wide rows, or one large join, therefore can refuse
acquisition forever; the client makes a nonretryable sync refusal terminal.
Lead reproduction seeded 45 legal rows with 400000-byte bodies, then granted
one membership. `stream(alice, 9, 1)` returned 45 events, watermark 10,
more:false and 18006410 serialized bytes, already over the 16777216-byte
HTTP ceiling. This is a bounded functional probe, not a throughput or soak
measurement.
See [the sync ticket](../issues/20260916-snapback4-sync-indivisible-join-progress.md).

The strongest candidate is byte-bounded staged acquisition: send a stable
snapshot/commit identity and continuation over bounded chunks, stage them on
the device, and publish the watermark/holding only when the complete unit is
present. A restart must resume or discard incomplete staging atomically.
Membership revocation during transfer must invalidate authority before
publication. Both memory and SQLite devices must implement the same state
machine. This touches the partition protocol, store history interface,
device persistence and client transport; it is a component redesign.

An alternative is an admission-time maximum for every indivisible holding
and commit, diagnosed before accepting the write that creates it. That is
simpler but restricts applications, and checking it can itself scan large
holdings. Lowering page size alone helps cold snapshots but cannot split a
single join or commit. Raising 16 MiB only moves the failure threshold.
Do not implement a partial split that advances a watermark before all rows
of the unit are durable.

### Physical work and private logical work have different contracts

Expired siblings in rule probes can require repeated physical batches even
when the public rule cost is one. Maintained existence can walk the expired
source group. Sync reconstructs current memberships plus complete transition
history before its page selection. These are code-traced unbounded axes;
[the physical-work ticket](../issues/20260916-snapback4-physical-rule-probe-work.md)
requires measurements varying expiry backlog and membership churn separately.
LLP 3000.007 §17 deliberately prevents private cardinality from leaking via
logical cost; charging those siblings to the visible meter is not a repair.

Evaluate live candidate indexes maintained transactionally, bounded
maintenance debt, and resumable private acquisition with a refusal policy
whose observable shape preserves uniformity. SQL progress interrupts or a
wall-clock timeout can protect availability but do not establish that privacy
contract or deterministic interpreter semantics. The meter remains the
logical contract; document separately which allocations and physical work
are admitted. Guest-principal rows, operation receipts, logs, request/step
receipts and retained membership history need a coordinated lifetime model;
automatically deleting a principal because its last session expired can
orphan application data and durable work.

### Native wasm adds an unmetered allocation boundary

The bridge allocates guest-supplied lengths before checking memory ranges,
instantiates without a memory/table limiter, and keeps every log string.
Fuel limits guest instructions, not these host allocations. The immediate
repair can be local: validate ranges before copying, enforce existing heap
and output ceilings at every entry point (including metadata exports), and
bound retained logs. The [native memory ticket](../issues/closed/20260916-snapback4-native-host-memory-bounds.md)
requires tiny hostile wasm fixtures, not a host-exhaustion experiment.
Those guards do not turn all peak process memory into a proven bound: wasm,
JSON copies, interpreter values and concurrently admitted responses still
need a measured aggregate envelope. Muse's 16 MiB-times-concurrency concern
belongs here; lowering the wire ceiling without fixing acquisition progress
would make the first problem worse.

### Decision and validation status

These remain research alternatives. The local bridge safeguards and
byte-aware snapshot improvements can proceed independently. A protocol
redesign needs tests for interrupted chunks, restart, revoke/regrant, restore,
large rows, large commits and a single oversized row, plus peak-memory and
forward-progress measurements on existing test machinery. No new gate,
ceiling increase, or replacement of SQLite/the synchronous owner is selected.

The 2026-09-16 repair candidate adds the localized native guards described in
LLP 3000.005 §4 and adaptive client snapshot/stream page reduction at the same
cursor. Real-server wide-row acquisition is covered on wasm and process
devices. A limit-one refusal remains terminal: this is intentionally not a
claim that an indivisible oversized join or commit can now make progress.
The staged-transfer, physical-work, aggregate-memory and retirement designs
above remain open research.

Counted across classes, `BTreeMap`/`BTreeSet` code is 505,002 B in roughly
960 generic items — one full copy of the node-balancing machinery per
distinct key/value pair — and slice sorting is another 107,923 B, most of it
reached through `collect()` into a map. `.rodata` holds about 40 KB of
text; the rest is tables, chiefly Unicode normalization.

Five findings follow, and none was available to the first proposal:

1. **JSON is 41% of the module, not two thirds, and removing all of it does
   not reach the target.** The no-codec probe is an upper bound on what any
   codec redesign can save inside the device crate: 384,443 B gzip remains,
   2.6 times the target, before a single byte of replacement codec is added
   back. Codec replacement is necessary and cannot be sufficient.
2. **Half of the serde cost is duplication, not representation.** Every
   wire and durable type is decoded through both `from_str` (the kept
   backend, stored rows, metadata) and `from_value` (the dispatcher), and
   encoded through both `to_string` and `to_value`. Routing both directions
   through one family saves 61,680 B gzip for about fifteen lines — more
   than the rejected 1,531-line decoder saved (60,609), with no format, wire
   or protocol change and no hand-maintained mirror of the derive.
3. **Ordered-map monomorphization is the second largest class and appears
   in no earlier plan.** It is as large as the interpreter and the device
   together. Almost every one of those maps is small (a row's columns, a
   table's indexes, a program's arguments) and built once.
4. **The NFC tables cost 60,005 B gzip**, a ninth of the module, for one
   call in `words.rs`. Tables compress badly.
5. **The rejected lane failed by drift, and the first proposal would have
   repeated its risk at three boundaries at once.** A hand-written decoder
   is a second definition of every serde attribute on the IR (`default`,
   `rename`, `skip_serializing_if`, custom `deserialize_with`), maintained
   against a `main` that changes `ir.rs` and `schema.rs` daily. Whatever
   replaces JSON must keep the derive as the single definition.

### Recommended architecture: a measured ladder, cheapest certain bytes first

Keep the shared Rust `Runner`, value semantics, key and cursor order, rules
and meter, as the first proposal did. Change what surrounds them in the
order of bytes saved per unit of risk, measuring each rung on the same
script before starting the next. Estimates are labelled; everything else is
measured.

| Stage | Change | Wire, store or semantics change | Gzip after, as estimated before any rung was built |
| --- | --- | --- | ---: |
| S0 | Instrument: land the attribution script beside `measure-wasm.sh`; record the baseline; print the budget on every suite run | None | 520,557 |
| S1 | One serde family in each direction on the web artifact; no whole-page clone before decoding; programs shared by reference instead of cloned per call | None | about 455,000 (scratch A measured 458,877) |
| S2 | Small ordered maps: a sorted-vector map with the `BTreeMap` method names for the small, build-once maps (row columns, schema and IR maps, runner environments); B-trees stay where a large map is range-scanned (the memory store); one shared sort helper where a generic sort is instantiated per element type | None: same iteration order, same serialized form | about 350,000 (estimate: B-tree and sort code is a third of the no-codec probe's raw bytes; a sorted vector keeps roughly a fifth of it) |
| S3 | Unicode folding from the host on the web: `normalize("NFC")` and `toLowerCase()` imported instead of linked tables | **Semantic — needs the author's ruling**, below | about 295,000 (the probe measured −60,005) |
| S4 | The codec stage, below, in three independently landable parts | Durable format (S4a), then wire (S4b, S4c) | about 210,000 (bounded by the probe: at most 74,434 from the device crate's entry points after S1, plus the core's residual) |
| S5 | Reachability: keep server-only engine paths out of the web build (static admission analysis, Postgres prefetch planning, partition-log helpers, effect, action, job and step statements as refusals); drop float formatting if no device value prints one | None on the device's contract | about 180,000 (estimate) |
| S6 | Decide with the numbers in hand | — | — |

The ladder does not reach 150,000 on its estimates — and the first two rungs
showed those estimates were themselves optimistic; the measured results and
the restated ladder follow this subsection — and the plan says so now rather
than after the expensive stages. What it establishes is how far
representation and reachability go before the executor itself is the
remainder — the evidence the first proposal wanted before commissioning a
shared compact execution representation, obtained for a fraction of the
work. S6 is the author's: accept a measured budget, commission the compact
execution representation of the first proposal (lowered ahead of time, shared
by every host; never a browser-only interpreter, which would reverse LLP 3000
§7), or split the device by feature. The target stays missed until measured
otherwise, and is not raised here.

**A diet without a ratchet is undone within a week.** S0 adds one number,
`metrics/wasm-budget.json`, lowered in the same commit as each rung. The
suite's existing wasm build step prints the measured gzip against it and
marks an overrun loudly; publication records it. Whether an overrun *fails*
the step is a new blocking gate, which `NOT-DOING.md` forbids without the
author; until ruled, it reports. The budget is a byte count beside a build
the suite already performs, not a registry, an inventory or a frozen record.

**S3 needs a ruling because it trades a principle for bytes.** LLP 3000 §7
says one implementation on every host; importing the host's normalization
makes the browser's ICU the web device's tokenizer. Unicode's stability
policy guarantees the NFC form of every *assigned* character never changes,
so skew between the Rust crate's Unicode version and a browser's is confined
to code points unassigned in the older of the two; `toLowerCase()` and Rust's
`to_lowercase` both implement default case conversion with the final-sigma
rule. The recommendation is to adopt it for the web only, behind a
differential witness over the Unicode `NormalizationTest` corpus in Chromium,
and to say on the search card that a device's word index follows its host's
Unicode version. It is built on a branch and not landed without the ruling.

**The candidate exists and is measured (2026-09-17, branch
`sb4/diet-s3-host-unicode`, `a98aa62eb0`).** On wasm32/web only, the word
tokenizer's NFC comes from the host through `js-sys`, with an ASCII fast path;
every other host is byte-for-byte unchanged. Importing NFC alone takes the
device from 466,618 to 407,786 B gzip (−58,832; the glue grows 185 B gzip).
Importing the tokenizer's lowercase as well saves nothing further; importing
`lower()` saves 4,307 more but changes a value queries return and predictions
write, and is not recommended. Over the pinned `NormalizationTest` 17.0.0
corpus plus every lowercase and `SpecialCasing` mapping — 57,848 folds — the
host and the Rust crate agree exactly in Node 24.18 (ICU 78.3) and in Chromium
153, run by the lead. The implementing lane corrected this section's argument:
Unicode's stability policy guarantees the NFC form of assigned characters and
makes **no** such promise for case mappings, which is a second reason to
import NFC only. What a disagreement could cost is a local search miss, an
extra local hit or a different local index key for text containing code
points one side's Unicode version lacks; the index is rebuilt in memory and
is neither persisted nor sent to the server, and authoritative execution is
unchanged. **The ruling asked of the author:** may the web device take NFC
from its host, with the search card saying that a device's word index follows
its host's Unicode version? If yes, the branch is narrowed to NFC only and
goes through the two-family review like every other rung.

**De-duplication is worth about a third of what a raw attribution suggests.** S2's estimate was −100,000 B gzip from removing about 450,000 raw bytes of B-tree and sort monomorphization. The first cut removed 228,209 raw bytes and saved 35,525: near-identical function bodies compress at roughly 0.15, against about 0.33 for the interpreter's own logic and 0.5 for tables (the NFC tables: 122,089 raw for 60,005 gzip). The warning was already on the page — `wasm-opt -Os` shrinking the raw module while inflating its gzip — and the estimate ignored it. Every remaining estimate below is restated on that basis, and no further rung is estimated from an attribution table: a scratch build takes half a minute.

**A sorted vector is only safe where data cannot size it.** Both review families found that three of S2's conversions were sized by data rather than program text — a viewer's held-and-left groups, the principals an effect reads, and a per-row `$filter` binding that shifted the whole runner environment — turning metered linear passes into unmetered quadratic ones that a remote party could drive; the fix round's audit found a fourth (dynamic JSON maps). With those restored the saving was 27,271, the value-and-environment family was net negative, and server tail latencies could not be shown neutral. The lead narrowed the rung rather than landing it: `SmallMap` is for compiled, build-once structures fixed by authored schema or program text — the schema's maps, the IR's maps, the static plans — and never for runtime state, whatever bounds it. Narrowed that way it measured 500,660 alone — 19,897 saved, under 4% — with server, device and HTTP timings within about 10% of base on the workloads measured and no stronger claim available on a loaded machine. The lead shelved it rather than landing it: a custom container in the core's public schema and IR types, and a rule every later contributor must apply correctly or reintroduce an unmetered quadratic pass, is a permanent cost, and four percent does not change where this ladder ends. The candidate, its three rounds of measurements and both review records are kept (branch `sb4/diet-maps`, `metrics/smallmaps-20260917/` on that branch); it is cheap to revive if a later rung makes four percent decisive.

**The ladder, restated.** S1 is worth 59,000 and S2, had it landed, 20,000 more — not the 165,000 first estimated for the pair. S3 (host Unicode, still needing its ruling) is a measured 60,000 because tables do not compress. The codec stage is bounded by the no-codec probe at about 74,000 beyond S1 and will keep some of that as its own decoder. Reachability (S5) removes non-redundant logic, which compresses worst, so its roughly 100,000 raw bytes of server-only code — the structural admission check that `validate_inputs` runs on every device query and prediction, the prefetch planner that `Runner::run` invokes over a memory store that never prefetches, and the partition-log event derivation a device's predictions compute and discard — measured 26,315 in a scratch build that simply removed the three calls (466,171 → 439,856; raw −97,091), which is this plan's own lesson applied: the estimate was made from a build, not from the attribution table. Summed honestly the ladder ends near **300,000 B gzip, twice the ticket's target**, not the 180,000 this section first estimated. The executor and the device logic themselves are about 390,000 raw bytes of non-redundant code, roughly 130,000 gzip before any runtime support. S6 therefore arrives with its answer mostly known: 150,000 needs either a compact shared execution representation or a web device that does less; representation work alone will not reach it.

**The codec stage's order changes with the evidence.** By type, the serde bytes are the backend — `Stmt` 73 KB, `ColumnType` 54, `Expr` 40, `ArgType` 40, `RuleExpr` 28, `Constraint` 24 — and row values are 4% (33 KB). A durable-row codec would buy about 8,000 B gzip for a store-format migration, so it is no longer first and may never be worth doing. The backend image is the stage: the server emits the compact image and the identity digest it already computes; the device decodes the image with derived visitors instantiated once for a non-self-describing format, keeps the image bytes it received rather than re-encoding them, and takes the identity from the server, so the web artifact needs no `Serialize` for the IR or schema and no typed JSON decode of them at all.

### The codec stage (S4)

The first proposal's three boundaries are right; the mechanism and the order
change. **The derive stays the only definition of every type.** The core gains
one small non-self-describing serde format (`compact`: varints,
length-prefixed text and sequences, numeric variant indexes, a presence byte
written from `skip_field` so `skip_serializing_if` cannot shift a position,
and a tagged escape for the few `serde_json::Value`-typed fields). Derived
visitors are then instantiated once, for a format that never calls
`visit_map`, so field-name matching and the JSON parser fall out of every
typed path without a handwritten decoder. Lengths are checked against the
remaining input before allocation; a malformed tag, length, depth or
reference refuses before state is published. A property test round-trips
every corpus program, every reference app's backend and generated pages,
rows and outbox entries through both `compact` and JSON and requires equal
values: drift between the two is a test failure on the day it is introduced,
not an acquisition failure in a browser.

The JavaScript host never parses or builds the binary forms; it carries
opaque bytes between the server, the device and IndexedDB. Small dynamic
envelopes — a call's request and reply, a drained change's `{s, k, v}` —
stay JSON, handled as a tree by code that is not generic over types.

| Part | Work | Boundary touched |
| --- | --- | --- |
| S4a: backend image | The server answers `GET /schema` in `compact` on request, with the identity digest it already computes; the device opens and adopts from the image, keeps the image bytes it received for offline reopen instead of re-encoding them, and takes the identity from the server, so the web artifact needs no `Serialize` for the IR or schema and no typed JSON decode of them; the host keeps fetching the JSON it reads itself, and the double transfer is measured and reported | Wire, negotiated; JSON stays the default |
| S4b: stream pages | `/sync` answers a small JSON envelope the host reads beside an opaque `compact` page the device applies | Wire, negotiated |
| S4c: durable rows | Row, confirmed-image and staged-snapshot values (`r`, `b`, `s`) as `compact` bytes the host stores unread; metadata, outbox and transfer markers (`m`, `o`, `j`), which `web.ts` reads, stay JSON | The device's own store format — a migration for about 8,000 B; last, and only if the measurements after S4a still want it |

Each part is measured and lands alone. The backend image is first because
the backend is where the serde bytes are: the first draft of this section put
durable rows first on the argument that they need no server, before anyone had
attributed serde by type, and row values turned out to be 4% of it. If S4a
recovers less than half of the probe's bound, stop and record the attribution
rather than building S4b.

### Persistence and format lifetime

Unchanged in substance from the first proposal. The host may acknowledge a
mutating device call only after its complete batch is durable, and discards
and reopens the in-memory device after a failed save, preserving the last
committed image. One batch owns rows, metadata, watermark and outbox changes
together. Snapshots remain privately staged until their existing publication
point; decoding a chunk does not make the partition acquired. Exclusive
store claims, orphan adoption, synchronous admission journals and
server-decided replay-candidate recovery carry forward from
[LLP 3000.007 §20.4](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md#20.4);
the localStorage journal keeps its small textual format.

Wire, backend-image and durable-store format versions are separate from
schema generation and `store_id`, and the runtime cache identity includes
the codec version. A store written before S4a is converted once, inside its
exclusive claim, by reading each old row through the dynamic JSON tree and
the existing non-generic `wire::row_from_json` path — a few dozen lines, not
a retained typed decoder — and published atomically with the old records
preserved on failure. Deletion and reacquisition is not an upgrade: left
history and the images beneath unresolved predictions cannot be reacquired.
An unsupported format refuses recoverably. Cached-old-runtime with a new
backend, and a new runtime over an old store, are both exercised.

### Acceptance, stop conditions and unresolved choices

Every rung: the device scenarios on memory and SQLite, the client suite on
the wasm and process devices, actual Chromium acquisition and offline
fresh-realm reopen (`witness/idb.mjs`), and a journal record with source,
toolchain, features, artifact identities and total byte accounting — glue,
SDK JavaScript, backend image and cold transfer reported separately, none
hidden in another bundle. The earlier lane's rejected reduction makes actual
acquisition mandatory evidence at every rung, including the ones that change
no format. S1 and S2 add paired cold-open and cold-acquisition timings on the
existing scale witness, because one serde family adds an intermediate tree on
the open path and a sorted vector changes insertion cost; a repeatable
regression is investigated before the rung lands. A byte win alone is
insufficient.

Closure is the first proposal's: the complete default web module strictly
below 150,000 gzip bytes with the scenarios, witnesses and differential checks
green. Three unsuccessful correction rounds on a rung use the existing stop
rule. Open choices are S3's ruling, whether the budget overrun blocks, how
much double transfer S4b may cost, and S6. Keep this work separate from
staged large-commit transfer, physical-work privacy and log retirement, which
share only its atomic publication requirements. The composition plan in
[LLP 3000.001](./3000.001-durable-replica-and-write-lifecycle.research.md#proposed-composition-of-retained-and-authoritative-reads)
no longer tracks per-value provenance, so it spends none of these bytes.


<a id="staged-sync"></a>
## Proposal: byte-bounded staged sync

**Proposal status:** Draft, 2026-09-17; authored by Codex / GPT-6 at Charlie
Cheever's request. This section proposes a protocol change, not an implemented
contract or an acceptance of the research document.
**Ticket:** [indivisible join progress](../issues/20260916-snapback4-sync-indivisible-join-progress.md).

### Problem and current evidence

The September 16 probe above produced 18,006,410 bytes from a limit-one stream
request. The repair delivered in `e96d0fe1d` reduces ordinary page counts, but
cannot divide that atomic join. Source inspection at `70a663c22285dc3a5278ca9ac13db01bbe05446b`
still finds `stream` fetching a complete oversized commit and `expand_joins`
materializing and sorting `group_at` before taking the horizon. This proposal
has not been implemented or newly benchmarked.

The relevant owners are [partition.rs](../snapback4/crates/snapback4-core/src/partition.rs),
[PartitionRows](../snapback4/crates/snapback4-core/src/partition/storage.rs),
[store.rs](../snapback4/crates/snapback4-core/src/store.rs), the shared Rust
[device](../snapback4/crates/snapback4-device/src/device.rs), and
[local.ts](../snapback4/packages/snapback4/src/local.ts). The existing snapshot
staging and catch-up transaction are useful starting points. The protocol must
also cover a large ordinary commit, large holding metadata and an individual
encoded row; fixing joins alone is insufficient.

### Recommendation and invariants

Transfer an atomic application unit in byte-bounded fragments into a durable,
invisible device stage. Publish its rows, holding metadata, acknowledgement
correlations and watermark together only after the unit and its authority
reconciliation are complete. Keep one interpreter, one partition watermark and
the existing public Read/Write card. Transport continuation is internal.

1. A fragment never advances the visible watermark or becomes queryable.
2. Redelivery of an identical fragment is idempotent. A different payload at
   the same transfer position refuses and invalidates that stage.
3. Every server page includes its complete encoded envelope within the existing
   HTTP response ceiling; the server reserves envelope space before payload.
4. A continuation identifies a store incarnation, schema generation, principal,
   base watermark, transfer unit and position. It conveys no authorization.
5. Every send and finalization authenticates current authority. A prior grant
   or a retained server spool never grants access to newly requested bytes.
6. Outbox intents retain their IDs and order across restart, stage replacement,
   schema refusal and storage failure. Publication rebases predictions once.
7. With stable authority, finite admitted data and sufficient device storage,
   transfer progresses despite ordinary concurrent writes. It never requires
   a quiet server. Storage or protocol refusal leaves a recoverable old base.

### Server acquisition and wire shape

Use a fixed source cut for the logical unit and keyset iteration over its
historical rows/events. The historical access path must enumerate by a stable
key with a bounded decoded batch; placing a limit around today's full
`group_at` vector or SQL window scan does not establish this bound. A persisted
historical image/index or checkpoint-plus-version index is the recommended
storage change. Its build and update costs belong in the measurements below.

For a join, select the horizon using the historical ordering at the join's
commit, then apply current visibility before sending each row. This preserves
the existing distinction between eligibility at the join and permission to
retrieve an image now. Pin the necessary history for the transfer's bounded
lifetime, integrating with the [retention proposal](#durable-retention).
Do not hold a database transaction or the engine lock across network requests.

Proposed internal records, with final names left to implementation:

| Record | Required information |
| --- | --- |
| Transfer descriptor | Protocol version, store incarnation, generation, principal, base watermark, source cut, unit ID, authority fence, expiry |
| Fragment | Unit ID, monotonically ordered position, bounded payload, payload digest, next continuation |
| End of unit | Final position/digest and tentative target watermark; never permission to publish by itself |
| Publication record | Completed reconciliation cut, generation/authority fence, holding changes and acknowledgement correlations |
| Restart/refusal | Reason sufficient to restart safely; never an instruction to discard admitted outbox work |

Rows, event collections and holding metadata use the same fragment framing.
An individual row crossing a fragment boundary is reassembled outside the
visible store, checked against existing value/schema limits, then admitted
atomically. This changes transport representation, not the permitted value
size. A row that violates the existing value limits receives a bounded refusal.
Encoded-byte counting includes JSON escaping, framing, digests and metadata.

The server must make repeats deterministic without retaining the whole transfer
in RAM. Recommend a small durable spool of already issued, unacknowledged
fragments, with authenticated acknowledgement and incremental deletion. Bound
spool bytes and transfer lifetime using measured storage budgets; a stopped
client cannot pin history forever. Authentication and authority checks occur
before replaying even an identical spooled response. If authority invalidates
it, abort the unit instead of returning old bytes. No new public registry,
operator command or independent service is required.

### Device publication, concurrent changes and revocation

Persist descriptor, fragment position and staged rows atomically per fragment.
Queries continue using the prior committed base and its existing freshness
state; a first acquisition stays loading. A crash before a fragment commit
retries it; a crash after it resumes from the persisted position. Duplicate
finalization is a no-op only when the complete publication identity matches.
SQLite and the web memory-plus-persistence host implement this same state
machine in the Rust device.

Once initial acquisition finishes, choose a finite catch-up cut and stage
subsequent commits through that cut. Commits newer than the cut remain for the
next ordinary sync. Do not repeatedly move the cut to the current head.
Reconciliation must include deletions, changes to ordering/horizons under the
existing acquisition rules, scope tombstones and outbox acknowledgements.
A final server transaction checks current generation and relevant authority
fences and emits the publication record. An authority change requires another
bounded reconciliation or an explicit restart; ordinary unrelated data writes
do not invalidate an otherwise complete transfer.

A generation or authority fence is scoped to what affects the transferred
partition, including row-rule dependencies, grant expiry and revoke/regrant.
It cannot be just a token's expiry or a membership row's ID. This dependency
mapping is a required design proof before implementation of finalization.
A revocation learned while staging invalidates the stage before publication;
apply the existing until-revoked versus delivered-history policy to the old
base. If the old base cannot yet be safely reconciled, affected reads cannot
be reported ready/fresh merely because staging still has rows. Previously
visible delivered-history may survive according to policy; unseen stage rows
never become delivered-history merely by having reached disk.

The guarantee is relative to the server publication cut and revocations the
device has observed. It does not promise recall of already authorized bytes or
instant knowledge of a revocation while a device is offline. A later scope
must still remove until-revoked rows when applied, as today.

### Alternatives and rollout

Raising the response ceiling fails again at a larger group and violates the
current budget. Rejecting a write or membership whose resulting holding is too
large is a coherent alternative, but changes the application model and can
require scanning that holding during admission. Partial application with an
advanced watermark loses atomicity and is rejected.

First add the bounded historical iterator and fragment codec with executable
scenarios in the existing core/device suites. Then implement invisible stage
persistence, restart and final reconciliation on both device hosts. Finally
switch transport and update the sync receipt/version negotiation. An older
client must receive an actionable unsupported-protocol refusal before it
mistakes a fragment for a complete commit. No parallel long-lived compatibility
protocol is proposed. Deploy clients/server coherently; retain recovery data
until pending work is accounted for. The public application card stays fixed.

### Validation and decisions to make before implementation

Reproduce the original 45-row join through real HTTP and prove forward progress
with every encoded response below 16 MiB. Also cover a multi-table large commit,
a large holding manifest, boundary-length escaped strings and a row crossing
fragment boundaries. Check that each intermediate query sees the old complete
state and that publication produces one coherent new state.

Run simulator faults at fragment persistence, acknowledgement and publication:
loss, duplication, reordering, restart, quota failure and final-response loss.
Add revoke/regrant, logical grant expiry, generation change, sign-out, pending
writes and delivered-history tests. Physical IDB/SQLite crash witnesses cover
only behavior the simulator cannot establish. Compare peak server memory,
spool/device bytes, writer-lock duration and hub acquisition time with the
current implementation; record the actual supported storage envelope.

Before coding finalization, resolve the authority-dependency fence, historical
index layout, exact protocol version and measured spool/lifetime budgets. The
recommendation is staged atomic publication, not authorization to invent new
ceilings. Stop if progress depends on quiescence, replay sends newly unauthorized
bytes, or a stage can publish without complete authority reconciliation.

<a id="physical-work"></a>
## Proposal: bounded physical work behind private rule probes

**Proposal status:** Draft, 2026-09-17; authored by Codex / GPT-6 at Charlie
Cheever's request. Measurements and disclosure review remain prerequisites to
claiming this implemented.
**Ticket:** [physical rule-probe work](../issues/20260916-snapback4-physical-rule-probe-work.md).

### Problem and recommendation

At `70a663c22285dc3a5278ca9ac13db01bbe05446b`,
[rule_probe_exists and lookup_live](../snapback4/crates/snapback4-core/src/engine/read.rs)
can scan expired siblings while charging one logical probe. Maintained existence
can inspect its source population; `partition::intervals` reconstructs complete
membership histories before returning a small sync page. The code establishes
the unbounded paths. No fresh scaling measurement is claimed here.

Recommend two coordinated changes: storage witnesses that answer supported
private boolean probes without scanning expired populations, and checkpointed,
paged authority history for sync. Keep the logical meter unchanged. A hidden
population must not decide whether an otherwise identical public operation
returns E_BOUND, capped, a cursor or a different receipt.

This targets dependence on expired backlog and historical churn. It does not
promise constant database cost, constant timing, or bounded total work for an
unbounded amount of legitimately visible output. Index traversal may still
scale logarithmically; visible acquisition is incremental.

### Private existence witnesses

For a supported equality probe, maintain an ordered private index over the
exact probed key and effective expiry, with the row ID as a tie-breaker.
Non-expiring rows sort as infinite lifetime. A seek for the greatest lifetime
answers whether any eligible row survives at the invocation's captured time;
an all-expired prefix needs no sibling walk. Insert, update, delete, expiry
column changes and schema adoption maintain it in the same transaction as the
row. Clock passage requires no write to make expired rows logically absent.

For maintained existence, materialize the source's *eligibility*, not just the
existence of the stored aggregate row. A candidate witness combines the source
selection predicate, computed group key and source expiry. Its boolean must
match the existing interpreter over that exact group. This is not a license
to substitute an arbitrary maximum-expiry row for the current ordered lookup.

The binder/storage planner must prove equivalence for each admitted probe
shape. Plain positional existence and a fully resolved unique key are initial
candidates. Extra equalities, computed predicates, maintained values and
multiple source lifetimes need explicit cases. A probe that returns a row or
whose result depends on the first row retains its ordering semantics; a boolean
witness cannot implement that lookup. Do not silently change `exists` or expand
its authoring surface to make the index convenient.

Equivalence includes the probe's expiry observation (`note_expiry`/`nextExpiry`),
not only its boolean. Current code records the first live ordered witness's
expiry; selecting the longest-lived witness can change invalidation behavior.
The maximum-lifetime seek above is therefore only the boolean component. The
chosen structure must also recover the same ordered live witness/expiry without
a backlog-linear scan, for example through an augmented ordered index with
subtree lifetime summaries. A fully resolved unique key avoids that ambiguity.
Until this complete equivalence and physical access bound are demonstrated,
the general prefix witness is a candidate, not an implementation-ready plain
expiry index. Any intentional change to expiry observation needs a separate
semantic decision rather than being hidden in an optimization.

Prefer derived indexes in the existing store, generated with the schema, over
a second cache service. Derivation follows the shared IR on SQLite and the
currently supported Postgres paths. Device behavior uses the same logical
expiry semantics, while partial local coverage still returns the existing
unknown/online fallback rather than claiming absence.

### History acquisition and maintenance

Use the [retention proposal's](#durable-retention) complete authority checkpoint
at a committed floor, plus keyset-paged transitions after it. A complete
checkpoint records live intervals, expiry and the state needed for historical
grant boundaries; current membership rows alone cannot reconstruct a revoke
and regrant. Reconstruction keeps its private continuation outside the public
rule meter and completes before it authorizes any content page.

A bounded page is also required for present memberships and historical group
images: truncating a vector or adding SQL LIMIT after a complete window/sort
is not sufficient. Measure database steps/rows visited, decoded bytes and peak
memory, not only round-trip count. Large visible partitions may take multiple
internal pages with an authenticated cursor. No content is released from an
incomplete authority ledger.

Expiry sweeping reclaims dead physical rows in bounded background batches.
The witness supplies correct logical answers even when sweeping falls behind.
Index backfill builds a replacement privately at a fixed cut, catches up
transactionally and switches atomically; it never exposes partial answers.
Maintenance resource exhaustion must not turn one secret prefix's population
into a query-specific refusal. Operator-visible aggregate maintenance state
belongs in existing `doctor`/`why`/measurements, not in ordinary responses.

### Resource protection and disclosure boundary

Measure the physical envelope first, then reserve work before accessing private
candidates where a public, population-independent bound exists. A timeout or SQL
progress interrupt can be a last availability defense, but cannot establish
logical uniformity merely by returning the same error spelling. Refusal versus
success is itself observable. Global overload behavior also needs an explicit
threat-model discussion; it is not called constant-time protection here.

The proposed normal path avoids private backlog-dependent scans rather than
metering them publicly. Where an exact witness is not yet proved, retain the
current semantics and leave that shape's physical bound unresolved. If an
implementation proposes refusing a formerly supported shape, that is an
explicit language/product change for author decision and compiler diagnostics,
not a hidden runtime cutoff. No ticket closes on a partial witness subset
without listing the remaining supported unbounded shapes.

### Alternatives, delivery and validation

An eager sweep before every read moves the unbounded work into the request.
A TTL cache can answer stale authority. Charging each expired sibling publicly
violates LLP 3000.007 §17. These are rejected. A more general augmented ordered
index can preserve first-live-row selection efficiently, but should follow
measurements showing that boolean witnesses leave a material hot path.

Sequence the work as: measure current paths; enumerate and prove exact probe
shapes; implement transactional witnesses and their backfill; add authority
checkpoints/pages; qualify supported stores and device fallback. Keep the
existing interpreter and tests. This does not wait for every retention class
to be reclaimable, but must share its checkpoint format and floor contract.

Use paired worlds that differ only in hidden expired populations, at sizes
0, 1, 1,000 and 100,000, with one fixed visible result. Compare the full public
observation: result/refusal, completeness, cursor, nextExpiry/invalidation, all
logical meters, receipt,
replay, writes, maintained rows, effects and sync output. Exercise expiry
boundaries, rolling clocks under the invocation-time rule, updates/deletes,
rollback, maintained selection changes and generation adoption. Independently
vary membership churn with fixed current holdings. Repeat on the actual store
interfaces; a mock with constant lookups proves nothing about physical work.

Success requires elimination of backlog-linear request acquisition for the
covered shapes, bounded incremental history reconstruction, unchanged public
observations and measured write/storage overhead within existing budgets.
Numerical baselines and acceptable overhead must be recorded before selecting
index layout. Before implementation lands, use the two blind disclosure reviews
already called for by LLP 3000 decision 4; this draft is not such a review.

<a id="durable-retention"></a>
## Proposal: coordinated history, receipt and principal retention

**Proposal status:** Draft, 2026-09-17; authored by Codex / GPT-6 at Charlie
Cheever's request. This is a proposed lifetime contract, not permission to delete
existing durable records or a statement that storage is now bounded.
**Ticket:** [durable-record retention](../issues/20260916-snapback4-durable-record-retention.md).

### Evidence and governing choice

The review traced retained partition/membership history, `_ops` receipts and
guest principals. Current [store.rs](../snapback4/crates/snapback4-core/src/store.rs)
replays an operation by principal and ID, checking its recorded name/argument
digest; [identity.rs](../snapback4/crates/snapback4-core/src/identity.rs) also now
contains bound session issuance/recovery for action claims. Work, step and
identity records therefore have dependencies beyond their own terminal flags.
The source baseline is `70a663c22285dc3a5278ca9ac13db01bbe05446b`; sustained
storage measurements remain to be run.

Recommend independent retention classes under one transactionally enforced
lifecycle. First compact reconstructible history and bulky terminal payloads
while retaining the identities that prevent replay. Give old sync cursors an
explicit reset path that preserves queued writes. Reclaim only provably unused
guest identities. **Do not introduce a blanket age-based deletion job.**

Finite total receipt storage, arbitrary offline duration and permanent
principal-plus-ID deduplication cannot all be guaranteed without a different
admission contract. This proposal preserves permanent deduplication in the
first implementation and explicitly leaves the small identity-key population
unbounded. That tradeoff is part of the recommendation, not a claim that the
entire ticket is solved by log compaction.

### Record classes and deletion preconditions

| Class | Live dependency | First recommended reclamation rule |
| --- | --- | --- |
| Partition events and commit times | Resumable cursors, staged transfers, historical joins | Complete checkpoint plus committed resume floor; retain every dependency of a still-valid transfer |
| Membership transitions | Historical authorization and grant expiry | Fold into an equivalent checkpoint before advancing the same floor; never prune independently of content history |
| Mutation identity and result | Same-ID retries and changed-input detection | Compact terminal payload only under a defined collection contract; retain principal, ID, operation binding, digest and terminal marker |
| Action/effect/job work | Pending attempts, cancellation, leases, unknown external outcomes | Retain nonterminal/uncertain work; compact terminal payloads only after all children, consumers and collection obligations are accounted for |
| Step and session-issuance bindings | Provider deduplication, lost-result recovery, session-family fences | Retain while parent recovery is possible; no plaintext token retention; terminal identity survives payload removal |
| Guest principal | Sessions, rows, grants, work, receipts and external application references | Automatically reclaim only a principal proven never used outside its expired session; otherwise retain until explicit application cleanup |

A compacted result needs a typed collection outcome that says its body is no
longer retained. It must not look like an unexecuted operation, a successful
empty result or an authentication failure. Exact spelling/public vocabulary is
an acceptance choice; retain payloads until it is settled. Replay must never
re-execute merely because the response body was compacted. Keep existing
sanitization and authority checks before returning retained metadata.

### Resume floor and crash-safe checkpoints

Introduce a store-incarnation-bound minimum resumable sequence `F`, atomically
paired with a complete checkpoint. A cursor below `F`, from another incarnation,
or requiring an expired transfer receives an explicit reset response. It is
never treated as an empty, caught-up stream. A checkpoint plus suffix must
reconstruct all historical row/authority states still promised at or above `F`,
including ordering, expiry and revoke/regrant boundaries.

Build at a fixed committed cut without holding the writer for the whole scan;
catch up to a finite cut, validate completeness, then atomically publish the
checkpoint and floor. Delete obsolete pages afterward in bounded batches.
Crashing before publication leaves the old floor valid; crashing afterward can
leave extra old pages, but cannot expose a floor without its reconstruction
state. Checkpoint correctness is semantic, not just a row count or checksum.

Transfers created by [staged sync](#staged-sync) pin only the required history
for a finite lease. Ordinary disconnected clients do not pin global history
indefinitely. Persist the pin/floor decision under the same storage owner so
compaction cannot race transfer creation. Compaction includes the physical
membership-history work addressed in the [probe proposal](#physical-work).

On reset, retain outbox entries, IDs, original order, cancellation records and
schema bindings. Stage a fresh current-authority snapshot and reconcile each
pending operation through its existing receipt/admission contract. Never mint
replacement IDs automatically. Keep the existing delivered-history policy:
reset does not authorize downloading revoked history or automatically erasing
retained device-only history. Unsupported generation changes remain explicit.

### Receipts, guest cleanup and the unavoidable policy boundary

Recommend permanent compact deduplication tombstones for already admitted
mutation IDs in the first phase. A terminal tombstone must still distinguish
an identical retry from changed name/arguments and preserve the fact of prior
execution. Work/step tombstones similarly keep external effects from being
started again. A parked or uncertain step is live recovery state even if old.
Bound session mint/replacement bindings cannot be removed while a recovered
claim could otherwise create another session family.

If tombstone growth itself later becomes unacceptable, the next design must
select a finite deduplication/admission horizon and enforce it *before* treating
an absent receipt as a new operation. Merely trusting client `minted_at`, a
cleanup timestamp or an arbitrary request epoch is insufficient: an old retry
can arrive without its receipt or be mislabeled as new. A server-verifiable,
non-relabelable intent lifetime would change the admission/wire contract and
must account for offline writes and legacy IDs. No such protocol is selected
here; server ID grants/slices remain outside current scope. Retaining compact
keys is safer than claiming a bound that quietly weakens at-most-once behavior.

For guest cleanup, maintain a monotone "has been used" fact at every engine
path that can establish a durable dependency, including row data, grants,
admitted operations, work and issuance. A newly created guest whose only
history is an expired session may be reclaimed after a measured grace period
and a transactional final dependency check. Legacy or incompletely accounted
principals are retained. Arbitrary text fields and external systems make
universal referential inference impossible; a used guest is application-owned
until the application explicitly retires it. Removing identity metadata never
cascades through user rows by accident and never makes a revoked session live.

### Rollout, alternatives and acceptance

Implement in four increments: (1) measure retained bytes/counts by existing
internal tables and classify dependencies; (2) shadow-build and compare history
checkpoints; (3) enable resume-floor/reset semantics on both device hosts before
log deletion; (4) implement narrowly justified payload/unused-guest cleanup.
Use existing inspection and measurement facilities. A new scheduler framework,
policy registry or blocking gate is unnecessary. SQLite and any shipped
Postgres path must agree before shared claims are made.

Deleting everything older than a fixed duration is rejected. Keeping everything
forever remains a valid baseline for measuring benefit but does not meet the
storage goal. Application-owned cleanup alone cannot safely know engine work
and replay dependencies. A finite offline/retry horizon is a viable future
product alternative, with an explicit compatibility decision, rather than an
implicit consequence of a cron job.

Run long-history fixtures with fixed live holdings, guest creation/expiry and
repeated operations. Compare checkpoint-plus-suffix reconstruction against the
uncompacted implementation for every tested cursor at/above `F`; below it must
reset. Kill at each checkpoint/floor/delete boundary. Exercise lost mutation
responses before/after compaction, changed-input retries, stale/future IDs,
parked external steps, cancellation, bound-session replacement, pending offline
writes and principal references in rows/work. Measure disk reclamation, index

Acceptance of the first phase requires zero lost admitted intents, no duplicate
execution, no unauthorized history reacquisition, useful storage reduction and
an honest residual count of permanent tombstones and application-owned guests.
Closing the whole ticket requires an explicit decision accepting that residual
or a separately proved finite-admission design. Default resume age, transfer
lease/grace periods and terminal-result collection duration remain author-facing
choices informed by these measurements; no arbitrary deletion defaults are
introduced by this draft.
