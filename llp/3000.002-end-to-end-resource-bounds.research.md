**Type:** Research

**Author:** Codex / GPT-6 (review requested by Charlie Cheever)

**Related:** [LLP 3000](./3000-snapback4.explainer.md), [LLP 2000.000](./2000.000-keep-the-core-flip-two-substrates.rfc.md), [review record](./reviews/3000-architecture-code-review-20260912.md)

## Review finding (0.0.16 baseline)

The runtime meter bounds selected interpreter operations, while several large
physical operations occur before a charge or outside that meter entirely.
The HTTP host also spends its four workers waiting for changes. Consequently,
four ordinary idle clients can stall unrelated requests, and a query can send
more than its configured output budget while merely reporting incomplete.
Resource accounting needs an end-to-end design that preserves the chosen
runtime-meter substrate.

This research extends [LLP 3000 §9](./3000-snapback4.explainer.md#9-architecture-and-code-review-2026-09-12).
It does not raise a ceiling, add a resource certificate, or assess security
holes; those are outside this review's updated scope.

## Evidence and confidence

**Measured:** with four `/changes?wait=2` requests already waiting, an ordinary
health request took 1,904 ms. The server has four blocking worker loops, and
all four were occupied until the waits expired. The normal client uses long
polling, so this is a small-client-count capacity problem.

**Reproduced:** with a five-byte output ceiling, the core returns the complete
26-character string `abcdefghijklmnopqrstuvwxyz` and marks the read capped.
`charge_output` runs after evaluation, and its false return is not used to
limit the returned data. The configured bound is not an output bound.

**Code traced:** the following physical work is not covered by the public
operation meter in a way that limits peak request cost:

- POST bodies are read into an unbounded string before argument bounds apply.
- `/sync` constructs a full snapshot or page, serializes it and responds while
  holding the shared engine lock. Network response progress can occupy the
  database owner after its computation is complete.
- Cold snapshots materialize all acquired groups. Stream selection reads up
  to a page per group before the global selection, and join expansion can
  make an atomic commit much larger than the nominal page limit.
- Partition logs and applied-operation records have no retention/compaction
  lifecycle. Group-keyed logging removes recipient fanout but does not bound
  accumulation over time.
- Query heap accounting follows selected allocations rather than owning all
  live values, copies, decoded rows and response buffers. It is not presently
  a peak-heap guarantee.
- The TypeScript interpreter omits several axes of the Rust meter, including
  output bytes and heap bytes.

The paths are [serve.rs](../snapback4/crates/snapback4/src/serve.rs),
[partition.rs](../snapback4/crates/snapback4-core/src/partition.rs),
[store.rs](../snapback4/crates/snapback4-core/src/store.rs),
[meter.rs](../snapback4/crates/snapback4-core/src/meter.rs),
[runner.rs](../snapback4/crates/snapback4-core/src/engine/runner.rs) and the
historical `src/replica/interpreter.ts`. That TypeScript interpreter was later
replaced by the shared Rust runner over the
[device store](../snapback4/crates/snapback4-device/src/store.rs); its old
meter omissions above are historical, not a claim about the current device.
This review did not run a large-scale soak or measure a slow-reader stall.
The two measured examples are small deterministic probes, not throughput
benchmarks or a claim about production hardware.

## Boundaries that need owners

| Boundary | Question to answer |
|---|---|
| Receive and decode | What bounds admitted bytes and time before a Quarry argument exists? |
| Storage acquisition | Who bounds physical rows, decoded bytes and temporary results when a semantic read is small? |
| Evaluate and construct | Does the meter reserve before growth, and which live allocations belong to it? |
| Encode and send | What is charged: tagged canonical values, wire JSON, or both? What happens before an oversized result escapes? |
| Acquire a partition | How can a large snapshot or whole commit be delivered atomically without requiring an unbounded memory buffer? |
| Retain history | When can logs and deduplication outcomes be reclaimed, and what do old devices do then? |
| Wait for work | How many idle clients fit without consuming all request executors? |

The public meter also has constraints inherited from the existing design;
physical admission should not be implemented by casually exposing additional
internal work counters. Preserve those constraints while deciding where
physical cost is limited. The separate security review owns any assessment
of disclosure properties.

## Alternatives worth evaluating

A bounded synchronous serving owner can remain viable if waits and network
writes release it, work is admitted before large allocation, and expensive
acquisition is incremental. An asynchronous HTTP layer is another option,
but replacing the transport alone leaves materialization and global-lock
costs unchanged. Adding more worker threads only moves the current failure
threshold.

For replication, compare staged snapshot/commit application with an explicit
maximum admitted partition/commit size. Staging can preserve whole-commit
visibility while transmitting bounded chunks; a fixed admitted size is
simpler but must be discoverable before a device or write reaches the wall.
Neither requires exact horizon eviction, which remains out of scope. Log
compaction likewise needs a minimum resumable watermark and a reset path;
deduplication retention needs its own replay contract before records vanish.

## Focused next work

Fix the clear output and worker-starvation bugs first. Then measure cold
acquisition across group count, rows per group, commit size and retained
history independently; include the temporary server allocations, not only
steady-state SQLite bytes or client heap. Determine which existing ceiling
owns each operation before introducing another counter. Keep these examples
inside existing measurements and tests, without another registry or blocking
suite. The review's HTTP/body/output tickets can proceed while the partition
acquisition and retention choices are researched.

## Implementation follow-up

The concrete R17–R19 and R36 corrections were implemented on the author's
2026-09-13 request. An indivisible query result above the output ceiling now
refuses `E_BOUND`; mutation output overflow aborts the transaction. Canonical
tagged output is counted through a writer without allocating another full
JSON buffer. The response no longer disguises an oversized value as an
incomplete successful query.

The HTTP host admits ordinary JSON up to 1 MiB, seed JSON up to 16 MiB and
asset bodies up to 64 MiB; it limits encoded responses to 16 MiB. Exact-limit
bodies are admitted, malformed/truncated input is diagnosed, and oversized
responses return a bounded refusal. Guards protecting the engine and bound
programs are released before socket response work. Upstream 0.1.1 already
replaced the four waiting workers with one thread per request; the regression
now exercises many waiting change polls beside ordinary traffic.

The HTTP library's fixed-length reader also needed correction: its drop
path allocated the entire declared unread remainder. The pinned vendored
`tiny_http` 0.12.0 patch drains through a fixed 8 KiB buffer and terminates
on EOF/error. Provenance and patch scope are in
`snapback4/vendor/tiny_http/SNAPBACK-PATCH.md`. This is a bounded allocation
correction, not a claim of bounded socket lifetime or thread count.

Publication builds the `production` profile and uses Cargo's reported
executable path, including a configured target directory. The existing
installed-consumer proof checks the packed binary's version and SHA-256
against that executable, then records its actual byte size and profile.
The incremental `release` profile remains an edit-loop choice.
The subsequent compiler comparison selects optimization level 3 for this
production server profile, retaining the bounded output writer. The separate
wasm profile and native xcframework invocation keep their size setting;
LLP 3000 §7 records the latency/size trade and its limits.

Remaining research is explicit: request concurrency and read/write deadlines,
server-side snapshot/whole-commit materialization, total live heap and the
TypeScript meter's missing axes, and partition/deduplication retention.
The current fixes do not establish a global physical resource ceiling. No
ceiling was raised, new blocking gate added, or security verdict made.

## 2026-09-16 review: progress, physical work, and native memory

The new review is pinned to `a0d48a4e6b660e2bfca3de3ef3470ef7787f3d15`
(0.2.26). The earlier HTTP starvation/body-buffer findings are historical:
current serving has separate bounded admission classes and socket deadlines.
This section replaces the remaining-work inventory above where it describes
those mechanisms as absent. Independent Sol and Muse reports and lead
validation are preserved in the dated review record. No whole-system rewrite
is justified by those findings alone.

### A response bound must permit sync progress

`partition::snapshot_page` chooses a row count; `stream` chooses events and
then preserves complete commits; `expand_joins` materializes a historical
group before taking its horizon. None of those counts bounds encoded bytes.
The local client requests 4,000 rows, while HTTP returns `E_BOUND` above
16 MiB. A set of legal wide rows, or one large join, therefore can refuse
acquisition forever; the client makes a nonretryable sync refusal terminal.
Lead reproduction seeded 45 legal rows with 400000-byte bodies, then granted
one membership. `stream(alice, 9, 1)` returned 45 events, watermark 10,
more:false and 18006410 serialized bytes, already over the 16777216-byte
HTTP ceiling. This is a bounded functional probe, not a throughput or soak
measurement.
See [the sync ticket](../issues/20260916-snapback4-sync-indivisible-join-progress.md).

The strongest candidate is byte-bounded staged acquisition: send a stable
snapshot/commit identity and continuation over bounded chunks, stage them on
the device, and publish the watermark/holding only when the complete unit is
present. A restart must resume or discard incomplete staging atomically.
Membership revocation during transfer must invalidate authority before
publication. Both memory and SQLite devices must implement the same state
machine. This touches the partition protocol, store history interface,
device persistence and client transport; it is a component redesign.

An alternative is an admission-time maximum for every indivisible holding
and commit, diagnosed before accepting the write that creates it. That is
simpler but restricts applications, and checking it can itself scan large
holdings. Lowering page size alone helps cold snapshots but cannot split a
single join or commit. Raising 16 MiB only moves the failure threshold.
Do not implement a partial split that advances a watermark before all rows
of the unit are durable.

### Physical work and private logical work have different contracts

Expired siblings in rule probes can require repeated physical batches even
when the public rule cost is one. Maintained existence can walk the expired
source group. Sync reconstructs current memberships plus complete transition
history before its page selection. These are code-traced unbounded axes;
[the physical-work ticket](../issues/20260916-snapback4-physical-rule-probe-work.md)
requires measurements varying expiry backlog and membership churn separately.
LLP 3000.007 §17 deliberately prevents private cardinality from leaking via
logical cost; charging those siblings to the visible meter is not a repair.

Evaluate live candidate indexes maintained transactionally, bounded
maintenance debt, and resumable private acquisition with a refusal policy
whose observable shape preserves uniformity. SQL progress interrupts or a
wall-clock timeout can protect availability but do not establish that privacy
contract or deterministic interpreter semantics. The meter remains the
logical contract; document separately which allocations and physical work
are admitted. Guest-principal rows, operation receipts, logs, request/step
receipts and retained membership history need a coordinated lifetime model;
automatically deleting a principal because its last session expired can
orphan application data and durable work.

### Native wasm adds an unmetered allocation boundary

The bridge allocates guest-supplied lengths before checking memory ranges,
instantiates without a memory/table limiter, and keeps every log string.
Fuel limits guest instructions, not these host allocations. The immediate
repair can be local: validate ranges before copying, enforce existing heap
and output ceilings at every entry point (including metadata exports), and
bound retained logs. The [native memory ticket](../issues/closed/20260916-snapback4-native-host-memory-bounds.md)
requires tiny hostile wasm fixtures, not a host-exhaustion experiment.
Those guards do not turn all peak process memory into a proven bound: wasm,
JSON copies, interpreter values and concurrently admitted responses still
need a measured aggregate envelope. Muse's 16 MiB-times-concurrency concern
belongs here; lowering the wire ceiling without fixing acquisition progress
would make the first problem worse.

### Decision and validation status

These remain research alternatives. The local bridge safeguards and
byte-aware snapshot improvements can proceed independently. A protocol
redesign needs tests for interrupted chunks, restart, revoke/regrant, restore,
large rows, large commits and a single oversized row, plus peak-memory and
forward-progress measurements on existing test machinery. No new gate,
ceiling increase, or replacement of SQLite/the synchronous owner is selected.

The 2026-09-16 repair candidate adds the localized native guards described in
LLP 3000.005 §4 and adaptive client snapshot/stream page reduction at the same
cursor. Real-server wide-row acquisition is covered on wasm and process
devices. A limit-one refusal remains terminal: this is intentionally not a
claim that an indivisible oversized join or commit can now make progress.
The staged-transfer, physical-work, aggregate-memory and retirement designs
above remain open research.
