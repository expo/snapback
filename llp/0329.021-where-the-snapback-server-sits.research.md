# LLP 0329.021: Where the Snapback server sits, and splitting the receipt

**Type:** Research
**Status:** Draft
**Systems:** Client, Sync, Storage, Authorization, Runtime, Contract integration
**Author:** Charlie Cheever / Claude
**Date:** 2026-08-29
**Related:** LLP 0329, LLP 0329.018, LLP 0329.019, LLP 0329.020, LLP 0002,

## Summary

[LLP 0329.020](./0329.020-where-the-client-data-tier-lives.research.md) §Open
question 4 recorded grok's proposal as the most useful uncosted idea in the panel:
*"'backend' means 'storage/source behind a Snapback 2 server.' A foreign system
that wants Exact's client properties runs (or embeds) Snapback 2. Rails is
persistence or a source the **server** compiles into programs and receipts."*

This document costs it. Two results:

1. **A constraint the panel missed dominates the server-side placement:
   exclusive write ownership.** "Put a Snapback server in front of Rails" is not
   an adapter; it is "Rails writes *through* Snapback, or Rails is read-only."
2. **The client-side placement is coherent, but only if the closure receipt is
   split.** Coverage is a claim about what a client *knows* and is self-issuable.
   Authorization is a claim about what a client is *permitted* and is not. Today
   `install_verdicts` fuses them, which is why the client cannot be repointed
   without losing both at once.

## Findings

### P1 — "Storage or source" hides two very different designs

**A1 — Snapback owns the database.** The foreign system's Postgres *is* Snapback's
storage. Index-served reads, real transactions, OCC, commit versions. This is
LLP 0046's Postgres graduation aimed at someone else's schema.

**A2 — Snapback fetches from the foreign system's HTTP API.** This largely does not
work for bounded programs. A program's read is
`scan table.index [prefix] take=N` **served by an index**, with an examined-entry
ceiling and a static work bound. An HTTP endpoint cannot be an index: there is no
predicate pushdown, no transaction spanning the reads of one program, and a network
round trip inside every loop iteration whose cost the ceiling was supposed to
bound. Building A2 means building a query planner over REST.

Grok's phrasing — "persistence **or** a source" — treats these as alternatives of
equal standing. They are not. **A1 is the proposal; A2 is a different and much
weaker product.**

### P2 — Exclusive write ownership is the dominating constraint

This is the finding, and no panelist raised it.

If the foreign system also writes to the database Snapback owns, Snapback's
guarantees do not degrade — they break:

- an external writer mutates rows **without advancing the commit version**, so
  read-set validation compares against a version that did not move;
- it does not participate in OCC, so a Snapback mutation's baseline can be stale in
  a way the protocol cannot detect;
- it does not apply the maintained-aggregate delta that `SPEC.md` specifies is
  applied "in the same SQLite transaction," so `maintain.count`/`maintain.sum`
  targets silently drift from their sources.

A receipt minted over a database another party is writing is unsound, and unsound
in the silent direction — the client is told `Fresh` about rows that moved.

LLP 0007 already records the shape of this: LLP 0081's migration workflow v1 is
"the **exclusive single-writer profile**." The assumption is present in the corpus;
it has simply never been stated as a constraint on *integration*.

**So A1's real cost is a migration, not an adapter.** Either the foreign
application is rewritten to write through Snapback, or it is demoted to read-only
against tables Snapback owns. Both are large. Neither is what "put a server in
front of Rails" sounds like, and the difference should be stated before anyone
sells it as integration.

### P3 — The client-side placement, and why it is not absurd

The founder asked whether the Snapback server could sit on the client. That is less
strange than it sounds: [LLP 0002](./0002-canonical-local-target.decision.md) makes
the canonical target "the whole server — code hosting *and* data store — running
locally on your machine." Snapback already ships a full server that runs on a
developer's laptop.

Placed on a user's device, in front of a foreign backend, it would execute programs
locally, maintain a store, and produce prediction — all of which work.

**What it cannot do is authorize.** A client-side server is not an authority. A
malicious client controls it, so any verdict it issues is the client's own
assertion about itself. Enforcement must remain at the foreign backend's boundary,
and Snapback's local verdicts become presentation-only — the exact degradation
LLP 0329.020 C4 says must be visible in the result type rather than hidden.

### P4 — Therefore: split the receipt

The line through P3 is clean and, as far as this family's documents go, new:

| Claim | About | Who can issue it |
|---|---|---|
| **Coverage** — which rows and ranges this store holds, which absences are known, what the program's trace touched | what the client **knows** | the client itself, honestly |
| **Authorization** — which rows this principal may see, under which epoch | what the client is **permitted** | only an authority |

`ClientStore::hydrate(schema, receipt)` seeds rows *and* calls
`install_verdicts(&receipt.verdicts)`. The two are fused in one artifact, so a
client can only obtain both together, from a Snapback server, or neither.

**Splitting them makes the placement space describable:**

- a **coverage receipt** is self-issuable, so an embedded or client-side Snapback
  can honestly produce one, and offline rendering, partiality by site id, and
  local prediction all remain sound;
- an **authorization receipt** requires an authority, so a client-side placement
  simply does not have one, and the result type says so by having no verdict case
  to read — satisfying C4's non-coercible-type rule by construction rather than by
  discipline.

This also sharpens LLP 0329.020's C1. The panel said Snapback's client is the tier
"for receipt-backed facts." With the split, the sentence becomes more precise:
**coverage-backed facts can be local; authorization-backed facts require a
server.** A client-side deployment is not a lesser Snapback — it is Snapback with
one of the two receipts absent, and the type can say which.

## The honest menu

| Placement | Offline + prediction | Local authorization | Real cost |
|---|---|---|---|
| Foreign app writes **through** a Snapback server | yes | yes | a migration of the foreign app's write path |
| Foreign app read-only; Snapback owns writes | yes | yes | halves the foreign app |
| Snapback embedded **client-side** over a foreign backend | **yes** | **no** | adapter, plus the P4 receipt split |
| Fetch-and-cache, separately typed | no | no | grok's "smaller and truer" story |

Rows 1 and 2 are P2's migration. Row 3 is the one the founder's instinct was
reaching for, and P4 is what makes it expressible rather than a silent
degradation.

## Confidence

High on P2. The three break modes are read from `SPEC.md`'s maintained-aggregate
rule and the corpus's OCC/commit-version design, and LLP 0007's "exclusive
single-writer profile" is quoted. I have **not** tested an external writer against
the spike; this is a design-level argument, not an observed failure.

High on P1's characterisation of what a bounded-program read requires.

Medium on P4. The coverage/authorization distinction is clean in principle, but I
have not checked whether the spike's `ClosureReceipt` factors cleanly — whether
coverage evidence is computable without the verdict set, or whether the two are
entangled in the trace. That is a code question and I did not answer it.

Medium-low on P3's security claim being the whole story. "A client-side server is
not an authority" is correct, but there may be deployments — a trusted device, an
enterprise-managed client — where a weaker assumption is acceptable, and I have not
thought about them.

## Open questions

1. **Does `ClosureReceipt` factor?** Can coverage be computed and verified without
   the verdicts, or does the trace entangle them? P4 depends on the answer.
2. Is there a middle placement — a Snapback server in the same trust domain as the
   client but not on it (a user's home server, a per-tenant instance) — where
   authorization is real but latency is local?
3. If the foreign app must migrate its write path anyway (P2), is that materially
   different from adopting Snapback outright? If not, the honest pitch may be
   migration rather than integration.
4. Does P2 have an escape via change-data-capture — Snapback consuming the foreign
   system's WAL to advance its own version stream — or does that reintroduce every
   ordering problem the commit-version design exists to avoid?
