**Archetype:** hierarchical document workspace (Notion / Google Drive / Confluence).

## 0. The short version

The model does **not** survive contact with this app, and it fails in a place the
ladder does not have an axis for. Four results, in descending order of how much I
think they matter:

1. **The ladder measures reads; this app's hard problem is a set-oriented *write*.**
   `deleteWhere(table, filter)` exists — an unbounded, predicate-selected delete.
   There is no `patchWhere`. Every structural operation in a workspace (move,
   trash, restore, re-key a materialized path) is a predicate-selected *patch* over
   a subtree whose cardinality nobody authored. Rung D (`insertEach` over a
   binding) does not reach it, because D is bounded by a `take` and this is not.
   **Rung E is `patchWhere` / a subtree update, and the IR is already asymmetric
   about it in a way that is visible in `define.mjs`.**

2. **Finding 3's count rule cannot express an integrity check, and on this app that
   turns a refusal into a silent pass.** LLP 0329.011 S5 open question 3 asked
   whether "visibility-filtered counts never turn a refusal into a silent pass."
   In coterie that was a hypothetical about non-members. Here it is the *normal
   operating case*: partial visibility into a subtree is the entire point of the
   product, so a mover who can see 40 of a folder's 3,000 descendants computes a
   depth/size/cycle check over 40 rows and gets `ok` for a move that is structurally
   illegal. Rule (a) — "filtered by the caller's declared read visibility" — is
   sound as a *disclosure* rule and wrong as a *correctness* rule, and the app needs
   both kinds of count. See §5.2.

3. **Recursive permission is not a rung; it is a second axis.** A0/A/B/C/D vary
   *how many rows one read binds*. Hierarchy varies *how many reads*, with each
   read's key depending on the previous read's output, to unbounded depth. No value
   of `take` buys a loop. The escape is denormalization (a materialized ancestor
   path), which converts the recursion into a single indexed read — and then
   immediately runs into two smaller walls: the expression algebra has no
   prefix/containment predicate (`PINNED_FUNCTIONS` is `len trim lower abs min max
   round floor ceil coalesce`), and maintaining the path is exactly the unbounded
   `patchWhere` from result 1. **Rung F is a containment/prefix predicate; it is
   cheap and it unblocks the single most dangerous mutation in the app.**

4. **The authority table has no declarative writer at all.** Membership writes go
   through `ctx.membership.<decl>.{insert,setRole,remove,patch,bootstrap}`, a
   JS-tier bridge (`guide/auth/scoped-roles.md`); no plan step writes a membership
   row, and LLP 0264 rule 3 says `membership` is not a generic write grant. In
   coterie, granting access is incidental — add a member to a chat. In a workspace,
   **granting access is the product**. So every share, grant, revoke, and link
   redemption is JS-tier by construction, before the ladder gets a vote. The
   escape-rate measurement inherits coterie's assumption that ACL churn is rare.

And one product-shaping result: **revocation is enforceable and expiry is not.**
Revoking a share link is a row write, so it rides the authorization-invalidation
barrier and drops live sessions. Expiry is a clock event with no data event, and
`SNAPBACK_AUTH_CLOCK_DEPENDENT_VISIBILITY` refuses ambient time in protected live
evaluation. The only shipped enforcement is a cron sweep flipping `status`, so
"expires at 5:00" is really "expires within one cron period of 5:00." §7 says when
that is a fine product change and when it is not.

## 1. The invariants, in plain language, before any code

These are the things Vellum must not violate. I wrote these first and then found
that three of them are inexpressible.

**I1 — Effective access is a path property.** A principal may read a node iff, on
the walk from that node to the workspace root, the nearest node carrying an entry
for that principal grants a role ≥ the required role, and no node between them
carries a denial. There is no single row that answers this.

**I2 — The tree is a tree.** No node is its own ancestor. Depth ≤ `maxDepth`.
Every non-root node's parent exists, is a folder, and is in the same workspace.

**I3 — A move is a permission event.** After `move(F → G)`, every descendant of F
has the effective access it would have had if it had always been under G. Nothing
is grandfathered. No open subscription continues to deliver a row the subscriber
just lost.

**I4 — Trash hides, it does not delete, and restore is its exact inverse.**
Restoring node N un-hides exactly the set that trashing N hid — no more (a node
independently trashed while inside N stays trashed) and no less.

**I5 — Removing access removes access.** If the UI says "Alice can no longer read
this," then Alice can no longer read it, by whatever mechanism, and the mechanism
is not "we removed the grant you were actually inheriting from a folder 4 levels
up, which also cut off 300 other documents."

**I6 — A share link is a delegation, and a delegation cannot outlive its
delegator's authority.** If Bob mints a viewer link to /Eng/Specs/D and then loses
edit access to /Eng, the link stops working. If D is moved to /Legal where Bob has
nothing, the link stops working.

**I7 — Structural refusals must not depend on what the caller can see.** Whether a
move creates a cycle is a fact about the tree, not about the mover.

**I8 — The audit log is append-only.** Who had access to this document on March 3
must be answerable after the tree has been rearranged.

## 2. The hard invariant: name it

Coterie's trap was *active-versus-historical membership*: a naive schema stores one
boolean `isMember`, and that boolean cannot answer "was this person in the room
when this message was sent." The disease was **collapsing a time-indexed relation
into a scalar**.

Vellum's trap is the same disease with a different index. Here it is:

> ### The overlooked transition is `restore`, and the disease is storing derived state as intrinsic state.

Everyone models `trash`. It is one patch: `trashedAt = now`. Almost nobody models
`restore` correctly, because **restore needs to know what trash hid, and trash only
wrote one row.**

The counterexample, which a naive design fails on the first day of real use:

```
/Eng                              (folder)
  /Eng/Specs                      (folder)
    /Eng/Specs/api-v2.md
    /Eng/Specs/api-v3.md
```

1. Alice trashes `/Eng/Specs/api-v2.md`. Row gets `trashedAt = T1`.
2. Bob trashes `/Eng`. Row gets `trashedAt = T2`. `Specs` and `api-v3.md` are now
   hidden — but they carry no `trashedAt`, because they were not trashed.
3. Bob restores `/Eng`.

A design with one `trashedAt` boolean per node has two implementations and both are
wrong. If restore clears `trashedAt` on the subtree, `api-v2.md` comes back from
the dead — Alice's deletion is silently undone. If restore clears `trashedAt` only
on `/Eng`, that is correct *here* but only by luck: it breaks as soon as anyone
implements "empty trash" (which must purge `api-v2.md` but not `api-v3.md`, and
cannot tell them apart because `api-v3.md` is in the trash view too), and it breaks
"restore `api-v2.md` while `/Eng` is still trashed" (the row un-trashes into a
folder nobody can see, so it vanishes from every view including trash).

The fix is to stop pretending "in the trash" is a property of a node. It is a
property of a *(node, trash event)* pair:

- `trashedAt` / `trashEventId` — **intrinsic**. Set only on the node the user
  actually chose. Cleared only by restoring *that* node.
- `hiddenByEventId` — **derived**. The id of the trash event whose root is the
  nearest trashed ancestor. Maintained by the same subtree write that does moves.

Restore(N) = clear N's intrinsic trash, then clear `hiddenByEventId` on exactly the
descendants where `hiddenByEventId == N.trashEventId`. That predicate is what makes
the operation the exact inverse: a node independently trashed at T1 carries its own
event id, not Bob's, so it is untouched.

**And the same distinction is the whole app.** Three instances of one bug:

| Derived thing | Intrinsic thing | Naive collapse | Breaks at |
|---|---|---|---|
| hidden-because-ancestor-trashed | trashed-in-its-own-right | one `trashed` flag | restore |
| inherited grant | explicit grant | one `role` column on the node | "remove access" |
| effective path / depth / workspace | `parentId` | recomputing on read | move (cost) or move (staleness) |

All three are written by the same operation shape: **a write to one node that
changes the derived state of a whole subtree.** That shape is result 1 in §0, and
it is the reason this app is a good instrument.

### 2.1 The direct temporal analogue

Coterie's "was she a member when this message was sent" has an exact Vellum
counterpart, and it is the one that is a security bug rather than a UX bug:

> **A share link is authorization frozen at mint time, evaluated at redeem time,
> against a tree that has moved underneath it.**

Bob has edit on `/Eng`. He mints a viewer link to `/Eng/Specs/D`. Carol moves
`/Eng/Specs` into `/Legal`, where Bob has nothing and the link's recipients have
nothing. The naive link row says `{ nodeId: D, role: 'viewer' }` and keeps working
forever. This is not exotic — it is the default outcome of storing a link as a
capability on a node id, and it is the exact structure of the historical-membership
trap: the row records a decision, the world changes, and nothing re-derives it.

The fix is that a link is not a capability, it is a *cached delegation* that must
be re-validated against (a) the minter's current effective role at the node, and
(b) the node's current path. Which means every redemption is a full recursive
authorization walk, twice. See `redeemShareLink` in §4.

```js
import {

export const workspaces = defineTable({
  name: v.string(),
  // The tree's root folder. Optional only because bootstrap seats the owner
  // membership before the root node exists.
  rootNodeId: v.optional(v.id('nodes')),
  // Structural ceilings. These are integrity limits, not product limits — see §5.2
  // for why that distinction is the one Finding 3 cannot express.
  maxDepth: v.integer(),
  maxNodes: v.integer(),
  nodeCount: v.integer(),
  createdAt: v.integer(),

  .visibility({

    resourceField: '_id',
    roles: ['owner', 'editor', 'viewer'],
  })
  .index('by_name', ['name'])
  .sync();

// not the ACL: it says "you are in this workspace at all." Every per-node decision
// below is handler-side, because the visibility grammar is single-hop and node
// permission is a path property (I1). This is coterie's S4 fallback repeating one
// level up: coterie fell back to `public-read`; Vellum can at least declare a
// perimeter, but the interior is still unenforced.
export const workspaceMemberships = defineTable({
  workspaceId: v.id('workspaces'),
  principal: v.principal(),
  role: v.string(),
  joinedAt: v.optional(v.integer()),
})
  .visibility({ kind: 'owner', field: 'principal' })
  .index('by_workspace', ['workspaceId'])
  .index('by_principal', ['principal'])
  .index('by_workspace_principal', ['workspaceId', 'principal'], { unique: true })
  .membership({
    id: 'workspaceMemberships',
    principal: 'principal',
    resource: 'workspaceId',
    role: 'role',
    roles: ['owner', 'editor', 'viewer'],
    pendingRoles: ['invited'],
    bootstrapRole: 'owner',
    lastHolder: { protect: 'owner' },
    provenance: 'full',
    transitions: [
      { op: 'insert',  by: ['owner'],  target: 'other', to: ['invited'], fields: ['joinedAt'] },
      { op: 'setRole', by: ['self'],   target: 'self',  from: ['invited'], to: ['viewer'] },
      { op: 'setRole', by: ['owner'],  target: 'other', from: ['viewer'], to: ['editor'] },
      { op: 'setRole', by: ['owner'],  target: 'other', from: ['editor'], to: ['viewer'] },
      { op: 'setRole', by: ['owner'],  target: 'other', from: ['editor', 'viewer'], to: ['owner'] },
      { op: 'remove',  by: ['owner'],  target: 'other', from: ['editor', 'viewer', 'invited'] },

    name: 'workspaceMemberships',

  parentId: v.optional(v.id('nodes')),   // null exactly for the workspace root
  kind: v.string(),                      // 'folder' | 'doc'
  title: v.string(),

  // materialPath is '/' + every strict ancestor id, root-first, '/'-terminated:

  materialPath: v.string(),

  hiddenByEventId: v.optional(v.id('trashEvents')),

  // --- INTRINSIC trash state. Set only on the node the user actually chose.
  trashedAt: v.optional(v.integer()),
  trashEventId: v.optional(v.id('trashEvents')),

  parentAtTrash: v.optional(v.id('nodes')),

    declaration: 'workspaceMemberships',
    resourceField: 'workspaceId',
    roles: ['owner', 'editor', 'viewer'],

  .index('by_workspace_path', ['workspaceId', 'materialPath'])
  .index('by_workspace_depth', ['workspaceId', 'depth'])
  .index('by_hidden_event', ['hiddenByEventId'])
  .index('by_trash_event', ['trashEventId'])
  // Sibling name uniqueness. This is load-bearing far beyond tidiness — §5.4
  // argues it is the ONLY host-enforced, unfiltered, sealed-refusal integrity
  // check the platform has, and the thing rung E/F should be modelled on.
  .index('by_parent_title', ['parentId', 'title'], { unique: true })
  .sync();

// Bodies are split from metadata so a folder listing does not carry document

export const docBodies = defineTable({
  nodeId: v.id('nodes'),
  workspaceId: v.id('workspaces'),
  body: v.string(),
  revision: v.integer(),
  updatedBy: v.principal(),
  updatedAt: v.integer(),

    kind: 'membership',
    declaration: 'workspaceMemberships',
    resourceField: 'workspaceId',
    roles: ['owner', 'editor', 'viewer'],
```

## 4. The hard operations

Twelve. I skipped `renameNode`-as-CRUD and everything else that is a `patch`.

Shared helper, used by almost all of them. Its existence is the finding: this is
`guide/auth/protecting-data.md`'s "sanctioned multi-hop handler pattern in **every**
named function," but the multi-hop is a *loop*, so no amount of care makes it
declarative.

```js
// functions.mjs — the recursive authorization walk.
//
// @ref guide/auth/protecting-data.md#authorize-first-then-elevate-the-exact-handler-read
// Every read below is elevated because the ACL rows for ancestors the caller cannot
// read are exactly the rows that decide whether the caller can read. That is the
// definition of hierarchical permission and it is why caller-visibility-by-default
// cannot be the contract for this app.
const ROLE_RANK = { none: 0, viewer: 1, commenter: 2, editor: 3, owner: 4 };

async function effectiveRole(ctx, node, principal, workspace) {
  // Workspace owners short-circuit; nothing below can deny them (I5 escape hatch,
  // and the reason `lastHolder: { protect: 'owner' }` matters).
  const wsRole = await ctx.permissions.workspaceMemberships
    .roleOrNull(node.workspaceId);
  if (wsRole === 'owner') return 'owner';
  if (wsRole === null) return 'none';

  // The walk. `materialPath` gives us the ancestor id list without N point reads,
  // but the ORDER is load-bearing: nearest ancestor wins, so we must iterate from
  // the node outward and stop at the first entry. There is no plan step that
  // iterates, and no expression that indexes an array.
  const chain = [String(node._id), ...ancestorIdsFromPath(node.materialPath).reverse()];
  const grants = await ctx.db.elevated
    .query('nodeGrants')
    .withIndex('by_principal_workspace')
    .eq('principal', principal)
    .eq('workspaceId', node.workspaceId)
    .take(512)
    .collect();
  const byNode = new Map(grants.map((g) => [String(g.nodeId), g.role]));

  for (const nodeId of chain) {
    const role = byNode.get(nodeId);
    if (role === undefined) continue;
    // 'none' is a DENIAL and it stops the walk. This is what makes the predicate
    // non-monotonic: adding a row reduces access. §6.3.
    return role;
  }
  // Fall back to the workspace-wide role.
  return wsRole;
}

function ancestorIdsFromPath(path) {
  return String(path).split('/').filter(Boolean);
}

async function requireNodeRole(ctx, nodeId, minRole) {
  const node = await ctx.db.elevated.get('nodes', nodeId);
  if (!node) ctx.refuse('NODE_NOT_FOUND');
  // Every elevated read below is scoped to this node's workspace; the caller's
  // workspace membership is checked inside effectiveRole before anything returns.
  const workspace = await ctx.db.elevated.get('workspaces', node.workspaceId);
  if (node.trashedAt != null || node.hiddenByEventId != null) {
    ctx.refuse('NODE_NOT_FOUND');   // trashed rows are indistinguishable from absent
  }
  const role = await effectiveRole(ctx, node, ctx.auth.userId, workspace);
  if (ROLE_RANK[role] < ROLE_RANK[minRole]) ctx.refuse('NODE_NOT_FOUND');
  return { node, workspace, role };
}
```

### M2 — `moveSubtree` — the operation the whole app is about

One user gesture. Cycle check, depth check, quota check, two independent
authorization walks, a materialized-path rewrite over an unbounded set, and an
authorization change to thousands of rows none of which are written.

```js
export const moveSubtree = defineJsMutation({
  auth: 'authenticated',
  args: {
    nodeId: v.id('nodes'),
    newParentId: v.id('nodes'),
    // Optimistic-concurrency token: the mover saw this parent. Without it, two
    // concurrent moves can each individually pass the cycle check and jointly
    // create a cycle. §5.5.
    expectedParentId: v.optional(v.id('nodes')),
  },
  reads: ['nodes', 'nodeGrants', 'workspaces', 'workspaceMemberships'],
  writes: ['nodes', 'accessEvents'],
  refusals: [
    'NODE_NOT_FOUND', 'PARENT_NOT_FOUND', 'PARENT_NOT_FOLDER', 'CROSS_WORKSPACE',
    'WOULD_CYCLE', 'DEPTH_LIMIT', 'SUBTREE_TOO_LARGE', 'STALE_PARENT', 'ROOT_IMMOVABLE',
  ],
  trackedRefusals: ['STALE_PARENT'],
  result: results.value(v.object({ moved: v.integer(), depthDelta: v.integer() })),
  outgrewIr: 'general-iteration',
  handler: async (ctx, args) => {
    const { node, workspace } = await requireNodeRole(ctx, args.nodeId, 'editor');
    if (node.parentId == null) ctx.refuse('ROOT_IMMOVABLE');
    // Two walks: you must be able to take it out AND put it in. Drive gets this
    // wrong in the "move to a shared folder you can write but not read" case.
    const { node: target } = await requireNodeRole(ctx, args.newParentId, 'editor');
    if (target.kind !== 'folder') ctx.refuse('PARENT_NOT_FOLDER');
    if (String(target.workspaceId) !== String(node.workspaceId)) ctx.refuse('CROSS_WORKSPACE');
    if (args.expectedParentId != null
        && String(node.parentId) !== String(args.expectedParentId)) {
      ctx.refuse('STALE_PARENT', { actual: node.parentId });
    }

    // --- I2, cycle. The whole check, in one line, ONLY because materialPath is
    // denormalized. Note what it is: a string prefix test. §5.3 / rung F.
    const selfPrefix = `${node.materialPath}${node._id}/`;
    if (String(target._id) === String(node._id)) ctx.refuse('WOULD_CYCLE');
    if (`${target.materialPath}`.startsWith(selfPrefix)) ctx.refuse('WOULD_CYCLE');

    // --- I7, structural counts over the UNFILTERED subtree. Elevated is not an
    // optimization here; a caller-scoped read gives a WRONG answer, not a partial
    // one — it returns `ok` for an illegal move. §5.2.
    const subtree = await ctx.db.elevated
      .query('nodes')
      .withIndex('by_workspace_path')
      .eq('workspaceId', node.workspaceId)
      .gte('materialPath', selfPrefix)
      .lt('materialPath', `${selfPrefix}￿`)
      .take(5001)
      .collect();
    if (subtree.length > 5000) ctx.refuse('SUBTREE_TOO_LARGE', { limit: 5000 });
    const maxDescendantDepth = subtree.reduce((m, r) => Math.max(m, r.depth), node.depth);
    const depthDelta = (target.depth + 1) - node.depth;
    if (maxDescendantDepth + depthDelta > workspace.maxDepth) {
      ctx.refuse('DEPTH_LIMIT', { limit: workspace.maxDepth });
    }

    // --- The write. THIS is the part with no declarative form. It is a patch over
    // a predicate-selected set whose cardinality is not authored — not insertEach
    // over a bound array, not deleteWhere. See §5.1 / rung E.
    const newPath = `${target.materialPath}${target._id}/`;
    const now = ctx.runtime.now();
    await ctx.db.patch('nodes', node._id, {
      parentId: target._id,
      materialPath: newPath,
      depth: target.depth + 1,
      updatedAt: now,
    });
    for (const row of subtree) {
      await ctx.db.patch('nodes', row._id, {
        materialPath: newPath + String(node._id) + '/'
          + row.materialPath.slice(selfPrefix.length),
        depth: row.depth + depthDelta,
        updatedAt: now,
      });
    }

    // --- I3. This is the honest part: the permission of every row in `subtree`
    // just changed, and NOT ONE of them is a membership row. I do not believe the
    // invalidation barrier fires for these. §6.4.
    await ctx.db.insert('accessEvents', {
      workspaceId: node.workspaceId, nodeId: node._id, kind: 'move',
      actor: ctx.auth.userId, subject: null,
      fromValue: String(node.parentId), toValue: String(target._id),
      affectedCount: subtree.length + 1, at: now,
    });
    return { moved: subtree.length + 1, depthDelta };
  },
});
```

### M3 — `grantAccess`

An explicit grant at a node. The subtlety: a grant that is *weaker* than what the
principal already inherits is a silent no-op under a naive "nearest ancestor wins"
walk — the user clicks "make Bob a viewer," Bob keeps editing, and the UI shows
viewer. So a downgrade must be refused with an explanation, or written as a
denial-style override. Both require knowing the inherited role, which is the walk.

```js
export const grantAccess = defineJsMutation({
  auth: 'authenticated',
  args: { nodeId: v.id('nodes'), principal: v.principal(), role: v.string() },
  reads: ['nodes', 'nodeGrants', 'workspaces', 'workspaceMemberships'],
  writes: ['nodeGrants', 'accessEvents'],
  refusals: ['NODE_NOT_FOUND', 'ROLE_INVALID', 'NOT_A_WORKSPACE_MEMBER',
             'CANNOT_GRANT_ABOVE_SELF', 'WOULD_BE_NOOP_INHERITED',
             'NODE_GRANT_LIMIT'],
  result: results.value(v.id('nodeGrants')),
  outgrewIr: 'filtered-read-guards',
  handler: async (ctx, args) => {
    if (!(args.role in ROLE_RANK) || args.role === 'none') ctx.refuse('ROLE_INVALID');
    const { node, workspace, role: myRole } =
      await requireNodeRole(ctx, args.nodeId, 'owner');
    // You cannot grant more than you hold.
    if (ROLE_RANK[args.role] > ROLE_RANK[myRole]) ctx.refuse('CANNOT_GRANT_ABOVE_SELF');

    // The subject must already be inside the perimeter; a node grant does not
    // create workspace membership. This ordering matters: it means "share with
    // someone outside the workspace" is a two-step ceremony, not one write.
    const wsRow = await ctx.db.elevated
      .query('workspaceMemberships')
      .withIndex('by_workspace_principal')
      .eq('workspaceId', node.workspaceId).eq('principal', args.principal)
      .take(1).collect();
    if (wsRow.length === 0) ctx.refuse('NOT_A_WORKSPACE_MEMBER');

    // The no-op trap.
    const inherited = await effectiveRole(ctx, node, args.principal, workspace);
    if (ROLE_RANK[inherited] >= ROLE_RANK[args.role]) {
      ctx.refuse('WOULD_BE_NOOP_INHERITED', { inherited, inheritedFrom: node.materialPath });
    }

    const existing = await ctx.db.elevated
      .query('nodeGrants').withIndex('by_node_principal')
      .eq('nodeId', node._id).eq('principal', args.principal).take(1).collect();
    const now = ctx.runtime.now();
    if (existing.length === 1) {
      await ctx.db.patch('nodeGrants', existing[0]._id, {
        role: args.role, origin: 'direct', originNodeId: null,
        grantedBy: ctx.auth.userId, grantedAt: now,
      });
      return existing[0]._id;
    }
    // Capacity check keyed to the NODE resource: Finding 3 admits this one cleanly.
    const onNode = await ctx.db.elevated
      .query('nodeGrants').withIndex('by_node').eq('nodeId', node._id)
      .take(201).collect();
    if (onNode.length >= 200) ctx.refuse('NODE_GRANT_LIMIT', { limit: 200 });

    return await ctx.db.insert('nodeGrants', {
      nodeId: node._id, workspaceId: node.workspaceId, principal: args.principal,
      role: args.role, origin: 'direct', originNodeId: null,
      grantedBy: ctx.auth.userId, grantedAt: now,
    });
  },
});
```

### M4 — `revokeAccessAt` — "remove access" when the grant came from an ancestor

The one that breaks naive designs from the product side. Bob can read
`/Eng/Specs/api-v3.md` because of a grant on `/Eng`. Alice clicks "Remove Bob."
There is no row to delete.

Four possible semantics, and the backend forces the choice:

| Option | Effect | Cost |
|---|---|---|
| (a) delete the ancestor grant | cuts Bob off from 300 unrelated docs | violates I5's spirit |
| (b) write `role: 'none'` at this node | correct and local | requires **negative grants**, which the visibility grammar cannot express (§6.3) |
| (c) push the ancestor grant down to every sibling, then delete it | preserves everything, purely positive | **unbounded fan-out write** — rung E again, and it explodes the grant table |
| (d) refuse: "access is inherited from /Eng" | honest | users hate it; Confluence does roughly this |

I implement (b) with an audited fallback to (d) when the node is not the right
place for a denial, and I note that (c) is what you'd want if you were forbidden
negative grants — which is exactly the position Snapback's grammar puts you in.

```js
export const revokeAccessAt = defineJsMutation({
  auth: 'authenticated',
  args: {
    nodeId: v.id('nodes'),
    principal: v.principal(),
    // 'here'      — deny at this node only (option b)
    // 'at-origin' — delete the ancestor grant (option a), requires confirmation
    //               because it is not local; caller must have seen the count.
    scope: v.string(),
    acknowledgedAffected: v.optional(v.integer()),
  },
  reads: ['nodes', 'nodeGrants', 'workspaces', 'workspaceMemberships'],
  writes: ['nodeGrants', 'accessEvents'],
  refusals: ['NODE_NOT_FOUND', 'NO_ACCESS_TO_REMOVE', 'SCOPE_INVALID',
             'AFFECTED_COUNT_STALE', 'CANNOT_REVOKE_WORKSPACE_OWNER',
             'DENIAL_UNSUPPORTED_AT_ROOT'],
  result: results.value(v.object({ mode: v.string(), affected: v.integer() })),
  outgrewIr: 'conditional-writes',
  handler: async (ctx, args) => {
    const { node, workspace } = await requireNodeRole(ctx, args.nodeId, 'owner');
    const current = await effectiveRole(ctx, node, args.principal, workspace);
    if (current === 'none') ctx.refuse('NO_ACCESS_TO_REMOVE');
    const wsRole = await ctx.permissions.workspaceMemberships
      .roleOrNullFor(node.workspaceId, args.principal);
    if (wsRole === 'owner') ctx.refuse('CANNOT_REVOKE_WORKSPACE_OWNER');

    // Where does the access actually come from?
    const chain = [String(node._id), ...ancestorIdsFromPath(node.materialPath).reverse()];
    const grants = await ctx.db.elevated
      .query('nodeGrants').withIndex('by_principal_workspace')
      .eq('principal', args.principal).eq('workspaceId', node.workspaceId)
      .take(512).collect();
    const byNode = new Map(grants.map((g) => [String(g.nodeId), g]));
    const source = chain.map((id) => byNode.get(id)).find((g) => g !== undefined) ?? null;
    const now = ctx.runtime.now();

    if (args.scope === 'here') {
      if (node.parentId == null) ctx.refuse('DENIAL_UNSUPPORTED_AT_ROOT');
      if (source && String(source.nodeId) === String(node._id)) {
        await ctx.db.delete('nodeGrants', source._id);
        // Deleting the local grant may re-expose an ancestor grant. If it does,
        // the delete alone is NOT a revocation and we must also write a denial.
        const after = await effectiveRole(ctx, node, args.principal, workspace);
        if (after === 'none') {
          await ctx.db.insert('accessEvents', {
            workspaceId: node.workspaceId, nodeId: node._id, kind: 'revoke',
            actor: ctx.auth.userId, subject: args.principal,
            fromValue: current, toValue: 'none', affectedCount: 1, at: now,
          });
          return { mode: 'deleted-direct', affected: 1 };
        }
      }
      await ctx.db.insert('nodeGrants', {
        nodeId: node._id, workspaceId: node.workspaceId, principal: args.principal,
        role: 'none', origin: 'direct',
        originNodeId: source ? source.nodeId : null,
        grantedBy: ctx.auth.userId, grantedAt: now,
      });
      await ctx.db.insert('accessEvents', {
        workspaceId: node.workspaceId, nodeId: node._id, kind: 'revoke',
        actor: ctx.auth.userId, subject: args.principal,
        fromValue: current, toValue: 'none', affectedCount: 1, at: now,
      });
      return { mode: 'denied-here', affected: 1 };
    }

    if (args.scope === 'at-origin') {
      if (!source) ctx.refuse('NO_ACCESS_TO_REMOVE');
      // Count what the caller is about to break, over the UNFILTERED subtree —
      // and require them to have acknowledged that exact number. A filtered count
      // here would understate the blast radius of a destructive operation. §5.2.
      const originNode = await ctx.db.elevated.get('nodes', source.nodeId);
      const prefix = `${originNode.materialPath}${originNode._id}/`;
      const affected = await ctx.db.elevated
        .query('nodes').withIndex('by_workspace_path')
        .eq('workspaceId', node.workspaceId)
        .gte('materialPath', prefix).lt('materialPath', `${prefix}￿`)
        .take(5001).collect();
      const n = affected.length + 1;
      if (args.acknowledgedAffected !== n) ctx.refuse('AFFECTED_COUNT_STALE', { actual: n });
      await ctx.db.delete('nodeGrants', source._id);
      await ctx.db.insert('accessEvents', {
        workspaceId: node.workspaceId, nodeId: originNode._id, kind: 'revoke',
        actor: ctx.auth.userId, subject: args.principal,
        fromValue: source.role, toValue: 'none', affectedCount: n, at: now,
      });
      return { mode: 'deleted-at-origin', affected: n };
    }
    ctx.refuse('SCOPE_INVALID');
  },
});
```

Note `AFFECTED_COUNT_STALE`. It is the analogue of `assertSourceChanged` for a
blast radius: the caller must prove they were shown the true number. This is the
only mechanism I could find that makes a destructive fan-out honest, and it is
hand-rolled.

```js
export const trashSubtree = defineJsMutation({
  auth: 'authenticated',
  args: { nodeId: v.id('nodes') },
  reads: ['nodes', 'nodeGrants', 'workspaces', 'workspaceMemberships'],
  writes: ['nodes', 'trashEvents', 'shareLinks', 'accessEvents'],

    const subtree = await ctx.db.elevated
      .query('nodes').withIndex('by_workspace_path')
      .eq('workspaceId', node.workspaceId)
      .gte('materialPath', prefix).lt('materialPath', `${prefix}￿`)

      workspaceId: node.workspaceId, rootNodeId: node._id,

      hiddenCount: subtree.length, trashedBy: ctx.auth.userId, trashedAt: now,
      restoredAt: null, purgedAt: null,
    });

      trashedAt: now, trashEventId: eventId, parentAtTrash: node.parentId,
    });

    // descendant that already carries its own trashEventId keeps it and is not
    // touched — its independent deletion survives this one.
    for (const row of subtree) {
      if (row.hiddenByEventId != null) continue;   // already hidden by an inner event
      await ctx.db.patch('nodes', row._id, { hiddenByEventId: eventId });
    }
    // Links pointing into the trashed subtree stop working now, not at expiry —
    // this is a row write, so it rides invalidation. §7.
    const links = await ctx.db.elevated
      .query('shareLinks').withIndex('by_node').eq('nodeId', node._id)
      .take(200).collect();
    for (const link of links) {
      if (link.status !== 'active') continue;
      await ctx.db.patch('shareLinks', link._id, { status: 'revoked', revokedAt: now });
    }
    await ctx.db.insert('accessEvents', {
      workspaceId: node.workspaceId, nodeId: node._id, kind: 'trash',
      actor: ctx.auth.userId, subject: null, fromValue: null, toValue: null,
      affectedCount: subtree.length + 1, at: now,
    });
    return { trashEventId: String(eventId), hidden: subtree.length };
  },
});
```

### M6 — `restoreSubtree` — the overlooked transition

```js
export const restoreSubtree = defineJsMutation({
  auth: 'authenticated',
  args: {
    trashEventId: v.id('trashEvents'),
    // Where to put it if the original parent is gone or is itself trashed.
    // The caller must decide; the mutation refuses rather than guessing.
    fallbackParentId: v.optional(v.id('nodes')),
  },
  reads: ['nodes', 'nodeGrants', 'trashEvents', 'workspaces', 'workspaceMemberships'],
  writes: ['nodes', 'trashEvents', 'accessEvents'],
  refusals: ['TRASH_EVENT_NOT_FOUND', 'ALREADY_RESTORED', 'PURGED',
             'RESTORE_PARENT_GONE', 'RESTORE_PARENT_TRASHED',
             'NOT_EDITOR_OF_RESTORE_PARENT', 'TITLE_CONFLICT_AT_DESTINATION',
             'DEPTH_LIMIT'],
  result: results.value(v.object({ restored: v.integer(), relocated: v.boolean() })),
  outgrewIr: 'general-iteration',
  handler: async (ctx, args) => {
    const ev = await ctx.db.elevated.get('trashEvents', args.trashEventId);
    if (!ev) ctx.refuse('TRASH_EVENT_NOT_FOUND');
    if (ev.purgedAt != null) ctx.refuse('PURGED');
    if (ev.restoredAt != null) ctx.refuse('ALREADY_RESTORED');
    const root = await ctx.db.elevated.get('nodes', ev.rootNodeId);
    if (!root || String(root.trashEventId) !== String(ev._id)) {
      ctx.refuse('TRASH_EVENT_NOT_FOUND');
    }

    // --- Restore-into-a-hole. The original parent may have been deleted, trashed,
    // or moved somewhere the restorer cannot write. Drive silently relocates to
    // "My Drive"; that is a product decision to paper over a backend fact, and it
    // is the wrong default for a permissioned workspace because it can move a
    // document OUT of a restricted folder into an open one.
    let destId = ev.restoreParentId;
    let relocated = false;
    let dest = destId ? await ctx.db.elevated.get('nodes', destId) : null;
    if (!dest || dest.trashedAt != null || dest.hiddenByEventId != null) {
      if (args.fallbackParentId == null) {
        ctx.refuse(dest ? 'RESTORE_PARENT_TRASHED' : 'RESTORE_PARENT_GONE',
                   { originalParentId: ev.restoreParentId });
      }
      dest = await ctx.db.elevated.get('nodes', args.fallbackParentId);
      relocated = true;
    }
    // The restorer must be able to write where it lands — checked NOW, against the
    // current tree, not against the ACL as it stood when the trash happened.
    const { node: destNode, workspace } =
      await requireNodeRole(ctx, dest._id, 'editor');

    // Sibling-title collision: something may have taken the name while we were away.
    const clash = await ctx.db.elevated
      .query('nodes').withIndex('by_parent_title')
      .eq('parentId', destNode._id).eq('title', root.title).take(1).collect();
    if (clash.length > 0) ctx.refuse('TITLE_CONFLICT_AT_DESTINATION', { title: root.title });

    const now = ctx.runtime.now();
    const newPath = `${destNode.materialPath}${destNode._id}/`;
    const oldPrefix = `${root.materialPath}${root._id}/`;
    const depthDelta = (destNode.depth + 1) - root.depth;

    // Exactly the set this event hid — no more, no less. This predicate IS I4.
    const hidden = await ctx.db.elevated
      .query('nodes').withIndex('by_hidden_event').eq('hiddenByEventId', ev._id)
      .take(5001).collect();
    const maxDepth = hidden.reduce((m, r) => Math.max(m, r.depth), root.depth);
    if (maxDepth + depthDelta > workspace.maxDepth) ctx.refuse('DEPTH_LIMIT');

    await ctx.db.patch('nodes', root._id, {
      trashedAt: null, trashEventId: null, parentAtTrash: null,
      parentId: destNode._id, materialPath: newPath,
      depth: destNode.depth + 1, updatedAt: now,
    });
    for (const row of hidden) {
      await ctx.db.patch('nodes', row._id, {
        hiddenByEventId: null,
        materialPath: newPath + String(root._id) + '/'
          + row.materialPath.slice(oldPrefix.length),
        depth: row.depth + depthDelta,
        updatedAt: now,
      });
    }
    await ctx.db.patch('trashEvents', ev._id, { restoredAt: now });
    await ctx.db.insert('accessEvents', {
      workspaceId: ev.workspaceId, nodeId: root._id, kind: 'restore',
      actor: ctx.auth.userId, subject: null,
      fromValue: String(ev.restoreParentId ?? ''), toValue: String(destNode._id),
      affectedCount: hidden.length + 1, at: now,
    });
    return { restored: hidden.length + 1, relocated };
  },
});
```

### M7 — `mintShareLink`

```js
export const mintShareLink = defineJsMutation({
  auth: 'authenticated',
  args: {
    nodeId: v.id('nodes'), role: v.string(),
    ttlMs: v.integer(), maxUses: v.optional(v.integer()),
    tokenHash: v.string(),   // client-hashed; the raw token never reaches the DB
  },
  reads: ['nodes', 'nodeGrants', 'workspaces', 'workspaceMemberships', 'shareLinks'],
  writes: ['shareLinks', 'accessEvents'],
  refusals: ['NODE_NOT_FOUND', 'ROLE_INVALID', 'CANNOT_SHARE_ABOVE_SELF',
             'TTL_OUT_OF_RANGE', 'LINK_LIMIT_FOR_NODE'],
  result: results.value(v.id('shareLinks')),
  outgrewIr: 'filtered-read-guards',
  handler: async (ctx, args) => {
    if (!(args.role in ROLE_RANK) || args.role === 'none' || args.role === 'owner') {
      ctx.refuse('ROLE_INVALID');
    }
    // Server-clamped TTL. Never trust a caller-chosen deadline for a security
    // window — guide/recipes/time-windowed-live-reads.md says the clock argument
    // "is not trusted for authorization, billing, or a security deadline."
    if (args.ttlMs < 60_000 || args.ttlMs > 30 * 86_400_000) ctx.refuse('TTL_OUT_OF_RANGE');
    const { node, role: myRole } = await requireNodeRole(ctx, args.nodeId, 'editor');
    if (ROLE_RANK[args.role] > ROLE_RANK[myRole]) ctx.refuse('CANNOT_SHARE_ABOVE_SELF');

    const existing = await ctx.db.elevated
      .query('shareLinks').withIndex('by_node').eq('nodeId', node._id).take(51).collect();
    if (existing.filter((l) => l.status === 'active').length >= 50) {
      ctx.refuse('LINK_LIMIT_FOR_NODE', { limit: 50 });
    }
    const now = ctx.runtime.now();
    return await ctx.db.insert('shareLinks', {
      workspaceId: node.workspaceId, nodeId: node._id, tokenHash: args.tokenHash,
      role: args.role, minterPrincipal: ctx.auth.userId,
      // Frozen evidence, re-derived at redeem (§2.1).
      minterRoleAtMint: myRole, pathAtMint: node.materialPath,
      status: 'active', expiresAt: now + args.ttlMs,
      maxUses: args.maxUses ?? null, useCount: 0, revokedAt: null, createdAt: now,
    });

});
```

### M8 — `redeemShareLink` — the delegation re-check

```js
export const redeemShareLink = defineJsMutation({
  auth: 'authenticated',
  args: { tokenHash: v.string() },
  reads: ['shareLinks', 'nodes', 'nodeGrants', 'workspaces', 'workspaceMemberships',
          'linkRedemptions'],
  writes: ['shareLinks', 'linkRedemptions', 'accessEvents'],
  // Every failure collapses to LINK_INVALID on purpose: a distinguishable
  // "expired" vs "revoked" vs "target moved" vs "no such token" is an oracle over
  // a secret URL. This is the sealed-refusal shape from LLP 0329.011 §S3.
  refusals: ['LINK_INVALID', 'LINK_EXHAUSTED'],
  result: results.value(v.object({ nodeId: v.string(), role: v.string(),
                                   leaseExpiresAt: v.integer() })),
  outgrewIr: 'filtered-read-guards',
  handler: async (ctx, args) => {
    const now = ctx.runtime.now();
    const found = await ctx.db.elevated
      .query('shareLinks').withIndex('by_token').eq('tokenHash', args.tokenHash)
      .take(1).collect();
    if (found.length === 0) ctx.refuse('LINK_INVALID');
    const link = found[0];
    if (link.status !== 'active') ctx.refuse('LINK_INVALID');
    // Belt AND braces: the cron sweep flips status, but a redemption inside the
    // sweep window must still refuse. This comparison is safe HERE (a mutation
    // materializing server time as a fact) and refused in a live query.
    if (link.expiresAt <= now) ctx.refuse('LINK_INVALID');
    if (link.maxUses != null && link.useCount >= link.maxUses) ctx.refuse('LINK_EXHAUSTED');

    const node = await ctx.db.elevated.get('nodes', link.nodeId);
    if (!node || node.trashedAt != null || node.hiddenByEventId != null) {
      ctx.refuse('LINK_INVALID');
    }
    // --- I6, the temporal analogue (§2.1). Two re-derivations, both required.
    // (1) The node has not been moved out from under the delegation.
    if (node.materialPath !== link.pathAtMint) ctx.refuse('LINK_INVALID');
    // (2) The minter still holds at least what they delegated. A link cannot
    //     outlive its delegator's authority.
    const workspace = await ctx.db.elevated.get('workspaces', node.workspaceId);
    const minterNow = await effectiveRole(ctx, node, link.minterPrincipal, workspace);
    if (ROLE_RANK[minterNow] < ROLE_RANK[link.role]) ctx.refuse('LINK_INVALID');

    const prior = await ctx.db.elevated
      .query('linkRedemptions').withIndex('by_link_principal')
      .eq('shareLinkId', link._id).eq('principal', ctx.auth.userId).take(1).collect();
    const leaseExpiresAt = Math.min(link.expiresAt, now + 3_600_000);
    if (prior.length === 1) {
      if (prior[0].revokedAt != null) ctx.refuse('LINK_INVALID');
      await ctx.db.patch('linkRedemptions', prior[0]._id, { leaseExpiresAt });
      return { nodeId: String(node._id), role: link.role, leaseExpiresAt };
    }
    await ctx.db.patch('shareLinks', link._id, { useCount: link.useCount + 1 });
    await ctx.db.insert('linkRedemptions', {
      shareLinkId: link._id, workspaceId: node.workspaceId, nodeId: node._id,
      principal: ctx.auth.userId, role: link.role, leaseExpiresAt,
      revokedAt: null, redeemedAt: now,
    });
    return { nodeId: String(node._id), role: link.role, leaseExpiresAt };
  },
});
```

```js
export const revokeShareLink = defineJsMutation({
  auth: 'authenticated',
  args: { shareLinkId: v.id('shareLinks') },
  reads: ['shareLinks', 'nodes', 'nodeGrants', 'workspaces', 'workspaceMemberships',
          'linkRedemptions'],
  writes: ['shareLinks', 'linkRedemptions', 'accessEvents'],
  refusals: ['LINK_NOT_FOUND', 'NOT_LINK_OWNER', 'TOO_MANY_REDEMPTIONS'],
  result: results.value(v.integer()),
  outgrewIr: 'general-iteration',
  handler: async (ctx, args) => {
    const link = await ctx.db.elevated.get('shareLinks', args.shareLinkId);
    if (!link) ctx.refuse('LINK_NOT_FOUND');
    const { role: myRole } = await requireNodeRole(ctx, link.nodeId, 'editor');
    if (String(link.minterPrincipal) !== String(ctx.auth.userId)
        && ROLE_RANK[myRole] < ROLE_RANK.owner) {
      ctx.refuse('NOT_LINK_OWNER');
    }
    const now = ctx.runtime.now();
    await ctx.db.patch('shareLinks', link._id, { status: 'revoked', revokedAt: now });
    // Revoking the LINK is not revoking the ACCESS. Everyone who already redeemed
    // holds a redemption row, and that row — not the link — is what a live
    // subscription's authorization reads. Killing the link without killing the
    // redemptions is the mid-session leak, and it is the single most likely bug
    // in this whole app.
    const reds = await ctx.db.elevated
      .query('linkRedemptions').withIndex('by_link').eq('shareLinkId', link._id)
      .take(1001).collect();
    if (reds.length > 1000) ctx.refuse('TOO_MANY_REDEMPTIONS');
    let n = 0;
    for (const r of reds) {
      if (r.revokedAt != null) continue;
      await ctx.db.patch('linkRedemptions', r._id, { revokedAt: now });
      n += 1;
    }
    await ctx.db.insert('accessEvents', {
      workspaceId: link.workspaceId, nodeId: link.nodeId, kind: 'link-revoke',
      actor: ctx.auth.userId, subject: null, fromValue: 'active', toValue: 'revoked',
      affectedCount: n, at: now,
    });
    return n;
  },
});
```

## 5. Testing the model, operation by operation

### 5.1 The table

Q1 = can it be a declarative plan today? Q2 = rung. Q3 = does the count rule hold?

| # | Operation | Plan today? | First missing construct | Rung |
|---|---|---|---|---|
| M1 | `createDocument` | No | recursive ancestor-grant read | **E′** (recursion) → A after path denormalization + F |
| M2 | `moveSubtree` | No | predicate-selected **patch** over an unbounded subtree | **E** (new) + **F** (prefix predicate) |
| M3 | `grantAccess` | No | membership/ACL write has no plan step; then recursive read | **G** (new) + E′ |
| M4 | `revokeAccessAt` | No | data-dependent branch on the walk result | **E′**, plus `conditional-writes` (already named out-of-profile) |
| M5 | `trashSubtree` | No | predicate-selected patch over unbounded subtree | **E** |
| M6 | `restoreSubtree` | No | same, plus a *second* predicate-selected patch keyed by event id | **E** |
| M7 | `mintShareLink` | No | recursive read for the minter's role | **E′**; capacity count is fine (C) |
| M8 | `redeemShareLink` | No | recursive read ×1, indexed read by token ×1 | **A** for the token lookup, **E′** for the walk |
| M9 | `revokeShareLink` | No | fan-out **patch** over redemptions | **E** (bounded variant — could be `patchEach` over a binding) |
| M10 | `expireDueShareLinks` | No | indexed range read + fan-out patch | **B** + **E** |
| M11 | `readDocument` (query) | n/a (queries) | recursive read | **E′** |
| M12 | `listFolder` (query) | n/a | N recursive reads, one per child | **E′** nested |

Rung usage:

- **A/B/C/D reach nothing on their own here.** Not one of these twelve becomes a
  plan if you land the full ladder as specified. The closest is M8's token lookup,
  which is a textbook rung A — and it is one step of a mutation whose other step is
  off the ladder entirely.
- **E** — set-oriented *patch* selected by predicate. Six of twelve.
- **E′** — recursion, or its denormalized stand-in. Nine of twelve.
- **F** — prefix/containment predicate. Two, but one of them is `moveSubtree`.
- **G** — a declarative writer for the authority table. Three.

### 5.2 Q3: the count rule does **not** hold, and the failure is a silent pass

Finding 3 says a count may drive a refusal only when the counted domain is (a)
filtered by the caller's declared read visibility and (b) keyed to a resource.

This app has counts of two different species and the rule only fits one:

**Policy counts** — product limits. `LINK_LIMIT_FOR_NODE` (50 links per node),
`NODE_GRANT_LIMIT` (200 grants per node). Both are keyed to a node resource the
caller holds `owner` on. Both are fine filtered or unfiltered, because a caller
with owner on the node can enumerate the domain anyway. **Rule holds. No
complaint.**

**Integrity counts** — structural invariants of the tree. `SUBTREE_TOO_LARGE`,
`DEPTH_LIMIT`, `WORKSPACE_NODE_LIMIT`, and the `WOULD_CYCLE` containment test
(which is a count-zero check in disguise). These are facts about the data, and
**every one of them must be computed over rows the caller cannot see.**

Concretely. Alice has `editor` on `/Eng`. Inside it, 2,900 of 3,000 documents carry
`nodeGrants` rows denying her. She drags `/Eng` into `/Archive/2024/Q3/legacy`,
already at depth 17 of a `maxDepth` of 20.

- Compute `maxDescendantDepth` over what Alice can see (100 shallow docs): 3. New
  depth 18. **Passes.**
- Compute it over the true subtree: 9. New depth 24. **Should refuse.**

The move commits. The tree now violates I2. Nothing detected it, and no future
operation will, because every future operation computes the same filtered answer.
This is not a disclosure bug — it is the *opposite* of one. **Rule (a) makes the
answer safe and wrong.** LLP 0329.011 S5 open question 3 asked exactly this
("worth confirming that visibility-filtered counts never turn a refusal into a
silent pass") and the answer on this app is: they do, routinely, because partial
visibility into a subtree is the product's normal state rather than an edge case.

The rule as written cannot be repaired by adding an exception, because the two
species need opposite treatment:

| | Policy count | Integrity count |
|---|---|---|
| Domain | must be filtered | must **not** be filtered |
| Refusal code | may be specific and caller-observable | must be **sealed** — indistinguishable from other failures — or it is a channel |
| Who may compute it | the caller's authority | the **host**, not the caller |

So the honest statement is: **Finding 3 is a rule about policy counts, and the
model currently has no category for an integrity count at all.** An integrity
count is not a caller's question; it is the host's. Which brings us to §5.4.

### 5.3 Rung F, and why it is cheap

`moveSubtree`'s cycle check, with a materialized path, is:

```
target.materialPath.startsWith(node.materialPath + node._id + '/')
```

The expression algebra has `concat` and `PINNED_FUNCTIONS = len trim lower abs min
max round floor ceil coalesce`. There is no `startsWith`, `contains`, `slice`, or
`indexOf`. With a JSON ancestor array instead of a string, there is no array
membership operator either. So the check is inexpressible.

Two honest escapes:

1. **Bounded unrolling.** Store ancestors as declared columns `a0…a19` and write a
   20-term disjunction of `eqv`. It works, it caps depth at a schema constant, and
   it is grotesque. But its existence is informative: **recursion over a
   *declared-bounded* depth is already expressible; what's missing is a way to say
   the bound once.** A `maxDepth` in the schema plus a compiler that unrolls is a
   much smaller ask than general recursion.
2. **Add `startsWith` / `contains` to `PINNED_FUNCTIONS`.** Growing the library is
   described as "a profile-version event, not an app-side extension," so it is not
   free — but it is one entry, and it converts the app's most dangerous mutation's
   safety check from handler code into a `guard`.

I'd take (2) and keep (1) in reserve.

**Incidental correction, worth propagating.** Brief 3 says "there is **no
string-length operator**," and LLP 0329.008 §"Two smaller gaps" says the same and
lists it as a residual blocking `ensureMyProfile`/`editProfile` even after the read
step lands. That is now false:

```js
// packages/snapback-codegen/define.mjs:3227
export const PINNED_FUNCTIONS = Object.freeze([
  'len', 'trim', 'lower', 'abs', 'min', 'max', 'round', 'floor', 'ceil', 'coalesce',
]);
```

`call('len', ...)` ships. `handle.length >= 3 && handle.length <= 20` is
`and(gte(call('len', arg('handle')), lit(3)), lte(call('len', arg('handle')),
lit(20)))` today. So one of 0329.008's two named residuals is closed, and — more
usefully for §5.3 — **the precedent for a string predicate in the pinned library is
already set**, which makes `startsWith` a smaller ask than the "profile-version
event" framing suggests when read cold.

### 5.4 The unique index is the mechanism the model should generalize

The one integrity check in this app that is enforced correctly, unconditionally,
over the unfiltered domain, with a sealed refusal, is sibling-title uniqueness —
and it is enforced by `.index('by_parent_title', ['parentId','title'], { unique:
true })`.

Look at what that declaration buys, against the §5.2 table:

- computed by the **host**, not the caller;
- over the **unfiltered** domain, so it is correct;
- discloses nothing selective, because the refusal is a platform code identical
  whether the colliding sibling is visible to you or not;
- and it is **declarative**, so an analyzer can see it.

That is precisely the contract an integrity count needs, and it already ships for
exactly one predicate class. **My strongest constructive suggestion is that rung E
and the integrity-count category should be designed as generalizations of the
unique index — a declared, host-evaluated, unfiltered structural constraint with a
sealed refusal — rather than as generalizations of the bounded read.** The bounded
read is a caller-authority construct and it is the wrong parent class for
`WOULD_CYCLE`.

The obvious first two members of that family, both of which this app needs:

```js
.tree({ parent: 'parentId', path: 'materialPath', depth: 'depth',
        maxDepth: 20, maxSubtree: 5000 })
```

— which would make cycle-freedom, depth, and path maintenance host-enforced, and
would make `moveSubtree` a plan; and

```js
.appendOnly()
```

— for `accessEvents`, which I8 requires and which today is enforced only by my
having not written a patch.

### 5.5 Two things I could not classify at all

**Concurrency on a shape invariant.** Two simultaneous moves: `move(A → B)` and
`move(B → A)`. Each individually passes the cycle check against the pre-state.
Both commit. The tree now has a detached cycle, and every path-prefix query
silently misses it. Snapback's read-set conflict validation should catch this
*if* each mutation's read set includes the other's written rows — `moveSubtree`
reads both `A` and `B` by id, so I believe OCC does save us here. But I want to
flag it as the shape of thing the ladder has no vocabulary for: **an invariant
whose violation requires no individual writer to be wrong.** `AssertCurrentRelation`
in the brief's step list smells like it was built for exactly this class and I did
not find its documentation; if it generalizes, it may be more important than any
rung.

**The blast-radius acknowledgement.** `AFFECTED_COUNT_STALE` in M4 is my
hand-rolled way of making a destructive fan-out require the caller to have seen its
true size. There is no construct for "this refusal exists to make the user's
consent informed." It is neither a permission, nor a limit, nor a conflict. It is
worth a category name because every ACL product needs it and every one implements
it by hand.

## 6. Where the model breaks, ranked

### 6.1 (Highest) The set-oriented write vocabulary is asymmetric

From `define.mjs`, the step constructors are: `insert`, `patch`, `del`, `get`,
`guard`, `letBind`, `deleteWhere`, `insertEach`, `assertSourceChanged`,
`allocateSequence`. So:

| | one row | bounded set | predicate-selected set |
|---|---|---|---|
| insert | `insert` | `insertEach` (rung D extends it) | — |
| delete | `del` | — | **`deleteWhere`** |
| patch | `patch` | — | **missing** |

`deleteWhere` already accepts an unbounded predicate-selected domain — the guide
explicitly discusses `deleteWhere(table, [])` as a deliberate clear-table. So the
IR is not philosophically opposed to unbounded set writes; it just has exactly one
and it is the destructive one. A workspace needs the other one: a move, a trash, a
restore, and a link-revocation cascade are all `patchWhere`.

**Rung E: `patchWhere(table, filter, values)` — a predicate-selected update whose
values may reference the matched row.** With it, `moveSubtree`'s write half becomes
two steps. Without it, six of my twelve operations are JS by construction.

The obvious objection is the work ceiling. But `deleteWhere` has the same problem
and shipped anyway, and the ceiling has an obvious authored form (`maxRows`, refuse
above it) which is exactly what my handlers do by hand with `take(5001)`.

### 6.2 (High) Recursion is an axis, not a rung — and the fix is a schema feature

The ladder's four rungs are `take(1)`, `take(N)`, `count(binding)`, `insertEach
over binding`. All four are the same read at different widths. **Depth is
orthogonal to width.** No `take` gives you a loop whose next key depends on the
last row read.

I do not think the answer is recursive plans. The answer this app actually wants is
what every real workspace ships: **denormalize the closure and let the platform
maintain it.** The `.tree(...)` declaration in §5.4 is the whole feature:
materialized path maintained by the host on every parent change, host-enforced
acyclicity and depth. That turns E′ into rung A — one indexed read on
`by_workspace_path` — and simultaneously solves E and F for this app, because the
one operation that needs the unbounded patch is the one the platform is now doing
itself.

That is a bigger swing than a plan step. It is also the only version of this I
would actually ship, because a hand-maintained materialized path where every
`moveSubtree` bug silently corrupts every future authorization decision is a worse
outcome than the JS tier.

### 6.3 (High) The visibility grammar cannot express a denial, which silently picks a product side

`TABLE_VISIBILITY_KINDS` is `public-read | owner | membership | any-of`, `any-of`
is 2–8 non-nesting arms of `owner`/`membership` only, and there is no negation
anywhere. So `nodeGrants.role = 'none'` — the denial that makes M4 option (b)
possible — can never be part of a declared boundary. It is handler-only forever.

This is not a small gap. Drive, Notion, SharePoint, and Confluence disagree with
each other about whether denials exist and whether "deny wins," and the answer
drives the whole sharing UI. Snapback's grammar makes exactly one of those products
declarable (the no-denials one) and forces the other three entirely into handlers.

Worth stating plainly because it is the kind of thing that reads as a modelling
detail and is actually a product-scope decision.

### 6.4 (High, lower confidence) A move changes authorization without touching an authorization table

`protecting-data.md`: "A membership-containing policy records all membership
dependencies and uses the conservative live-replace lane on relationship insert or
delete." And: "A settled membership removal or allowed-to-disallowed role change is
therefore an authorization boundary on all three surfaces."

`moveSubtree` writes `nodes.parentId` and `nodes.materialPath`. It writes no
membership row and no grant row. Every descendant's effective permission changes.
I do not see the mechanism by which an open live subscription to a moved document
would be re-authorized — the dependency graph is over the membership declaration,
and the membership declaration knows nothing about `parentId`.

**In coterie, every authorization change was a membership write, so this could not
arise.** That is the structural reason this archetype is a better instrument, and
it is the finding I'd most want someone with the invalidation code in front of them
to check. If it holds, it is more serious than any missing rung: the platform's
authorization-invalidation guarantee is conditional on the app's authorization
being *declared*, and an app whose authorization is handler-side gets a
guarantee-shaped hole rather than a documented absence.

I am marking this **inference, not measurement.** I read the guide, not
`crates/snapback-auth/src/auth/invalidation.rs`.

### 6.5 (Medium) No declarative writer for the authority table; no append-only

Membership writes are `ctx.membership.<decl>.{insert,setRole,remove,patch,bootstrap}`
— JS only. LLP 0264 rule 3 confirms `membership` is not a generic write grant. So
grant/revoke can never be a plan, and the escape-rate metric will keep counting
these as JS forever no matter what happens to the read ladder. **Rung G: plan steps
for declared membership transitions** — the transition grammar is already
declarative and analyzable, which makes this a smaller ask than it sounds.

Similarly, `accessEvents` needs `.appendOnly()` and has no way to say it. LLP
0329.008 listed "append-only or immutability constraints" as an untested candidate;
this app needs it and I could not express it.

### 6.6 (Medium) Expiry is not enforceable; revocation is

`SNAPBACK_AUTH_CLOCK_DEPENDENT_VISIBILITY` refuses ambient time in protected live
evaluation, and the recipe says the pinned client clock "is not trusted for
authorization, billing, or a security deadline." LLP 0053.000 commissions a design
and explicitly ships nothing.

So there are exactly two enforcement paths for a share link:

- **Revocation** — a row write. It rides the invalidation barrier. Enforceable,
  immediate, correct. This is why M8 mints a `linkRedemptions` row instead of
  treating the link itself as the capability: it converts the security question
  from "what time is it" into "does this row exist," which is a question the
  platform can answer.
- **Expiry** — a clock event with no data event. The only mechanism is the cron
  sweep in M10 flipping `status` and revoking redemptions, which turns the deadline
  into a row write after the fact. The window of over-grant is one cron period.

The design consequence is that **an expiry should be implemented as a scheduled
revocation, not as a comparison.** That is a good pattern and I'd recommend it
generally. It is also a real weakening, and §7 says when it is not acceptable.

---

## 7. Verdict

**The model does not survive.** Not because the ladder is wrong — A/B/C/D look
correct for what they measure — but because they measure the wrong dimension for
this application. On coterie the question was *how wide is the read*. On a
workspace the question is *how deep is the read* and *how wide is the write*, and
the ladder has an axis for neither.

Concretely: **landing all four rungs exactly as specified converts zero of my
twelve operations to plans.** That is the headline. The ladder was derived from an
app where authorization is a single-hop membership fact and permission changes are
single-row writes; both assumptions fail here, and they fail structurally rather
than incidentally.

### Ranked, what it misses

1. **`patchWhere`** — rung E. Predicate-selected update. The IR already has the
   destructive twin (`deleteWhere`); this is the constructive one. Six of twelve
   operations.
2. **A tree/closure schema feature** (`.tree({ parent, path, depth, maxDepth })`)
   — host-maintained materialized path with host-enforced acyclicity. This is not
   a rung; it is the thing that makes the rungs sufficient. It converts recursion
   into rung A and removes the need for the app to ever write a subtree by hand.
3. **A category for integrity constraints** — host-evaluated, unfiltered, sealed
   refusal. Generalize the unique index, not the bounded read. Finding 3's count
   rule is a *policy*-count rule and should be renamed as one, because as written
   it silently endorses a filtered structural check, which is a correctness bug
   (§5.2), not just an incomplete feature.
4. **A prefix/containment predicate** — rung F. One entry in `PINNED_FUNCTIONS`.
   Cheapest item on this list and it unblocks the most dangerous mutation.
5. **Plan steps for declared membership transitions** — rung G. Without it, ACL
   apps stay on the JS tier permanently regardless of the read ladder, and the
   escape-rate metric will not move for this whole archetype.
6. **Negation in the visibility grammar** — or an explicit decision that Snapback
   apps do not have denials, documented as a product constraint rather than left
   as a discovery.
7. **`.appendOnly()`** — small, needed, named as untested in 0329.008 and now
   tested: needed.

### Rungs E and F, stated

> **E — set-oriented update.** `patchWhere(table, filter, values)`, with values
> able to reference the matched row, and an authored `maxRows` ceiling that refuses
> above it. The bounded sibling `patchEach(table, source, itemAs, values)` over a
> binding is rung D's mirror and closes M9/M10; the predicate form is what closes
> move/trash/restore.
>
> **F — structural predicates over materialized relationships.** A containment or
> prefix test (`startsWith`, `contains`) in the expression algebra, and/or a
> declared bounded ancestor depth the compiler can unroll. This is what makes a
> hierarchy's safety check expressible without recursion.

And the thing I want to say most loudly, because I think it is a category error in
the current framing:

> **E and F are not further rungs on the same ladder.** The ladder's rungs are all
> the same primitive at different `take` values, which is why LLP 0329.008's result
> was so satisfying. E and F are not. E is a write construct; F is an expression
> construct; both are orthogonal to read width. If they get appended to the same
> list, the list stops being "one primitive at four settings" and becomes an
> unordered wish list, and the elegance of the original finding — which is real —
> gets used to justify a shape it does not have. The honest presentation is **two
> ladders**: read-width (A–D, one primitive, coterie-derived) and write-shape
> (single row → bounded set → predicate set, `deleteWhere`-derived, half-built).

### Where the product requirement should change instead

**Change it: share-link expiry.** "This link expires at 5:00pm" should become "this
link stops working within a few minutes of 5:00pm, and you can revoke it instantly
at any time." Implement expiry as scheduled revocation (§6.6). Almost every product
can accept this; Drive's own link expiry is not instant either. The engineering
benefit is large — you stop needing clock-dependent protected visibility, which is
a genuinely hard primitive that LLP 0053.000 is right not to have rushed.

**Do not change it in three cases.** (a) The deadline is a *legal* boundary —
litigation hold, an embargoed filing, a data-residency window. "Within a few
minutes" is not a defensible answer to a regulator, and the fix is not a better
sweep, it is to not use link-expiry as the control at all. (b) The link is the
*only* control — no workspace membership behind it, so a stale link is unauthenticated
public access to private content rather than a redundant grant to someone already
inside. My schema deliberately avoids this by requiring workspace membership before
`grantAccess` and by minting a revocable redemption row rather than treating the
link as the capability. (c) The window is longer than the exposure it protects: a
5-minute cron on a link whose whole purpose was a 60-second one-time view is not a
weakened requirement, it is an unimplemented one.

**Change it: "3 items you can't see."** Do not ship the hidden-child count in
`listFolder`. It is a genuine feature and a genuine disclosure over protected rows,
and unlike coterie's withdrawn S1 it would be live, because `nodeGrants` is
actually protected here. Ship "this folder may contain items shared only with
others" as a static string if you must, with no count.

**Do not change it: inherited-grant removal.** The temptation is to ship option (d)
— refuse, tell the user to go remove it at the ancestor — because it is the only
option the backend makes easy. That is the backend choosing the product, and it is
the wrong choice: it makes the most common safety action in the product ("stop this
person from seeing this document") into a multi-step operation with an over-broad
blast radius, which is how people end up not doing it. Either negative grants or
pushdown must be supported, which means either §6.3 or rung E must land.

### Confidence

**High** on §6.1 (read directly from `define.mjs`; the asymmetry is a fact),
§6.3 (read from `TABLE_VISIBILITY_KINDS` and the `anyOf` arm constraints), §6.5
(read from `scoped-roles.md` and LLP 0264 §V1 rule 3), and §5.3 (read from the
pinned function list).

**High** on §5.2's mechanism, **medium-high** on its severity. The silent-pass
argument is sound given filtered reads, but I have not run it; the specific claim
that a caller with partial subtree visibility computes a passing depth check is a
consequence of the design, not an observation.

**Medium** on §6.2's rung classification. I am confident recursion is not on the
ladder; I am less confident that `.tree(...)` is the right shape rather than, say,
a recursive read step with a declared depth bound.

**Low-to-medium** on §6.4, the invalidation gap, which is the highest-value item if
true. It is an inference from the guide's description of the membership dependency
graph. It should be checked against
`crates/snapback-auth/src/auth/invalidation.rs` before anyone acts on it, and if
someone does check it, that check is worth more than the rest of this document.

**Not established at all:** I did not author a single plan and run codegen, so
every "cannot be a plan" verdict here is static classification of the same kind
LLP 0329.008 flagged in its own Confidence section — with the same caveat, and one
additional one: my app is designed, not shipped, so unlike coterie there is no
independent evidence that these twelve operations are the ones a real workspace
needs. I believe they are; I chose them; that is a weaker warrant than measuring
an app someone else wrote.
