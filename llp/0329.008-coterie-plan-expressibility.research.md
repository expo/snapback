**Status:** Draft
**Systems:** Authoring surface, Code generation, Engine, Storage, Developer

**Author:** Charlie Cheever / Claude

## Summary

[LLP 0329.007](./0329.007-is-the-point-read-restriction-deliberate.research.md)
established that the mutation point-read restriction is unbuilt rather than
forbidden, and proposed a narrow `unique(table, index, key, bindAs)` step on the
grounds that the measured demand is uniqueness and membership checks.

This document tests that proposal against all 25 `defineJsMutation` handlers in
`coterie` — the largest and most realistic application in the corpus (14 tables,
zero declarative mutations). **The proposal is partly wrong**, and the corrected
answer is cleaner:

> The four missing constructs are all the *same primitive* — a bounded, indexed read
> into a plan binding — plus two small extensions. One new step and two extensions
> make all 25 mutations plan-expressible; the narrow `unique` form alone reaches 40%.

## Method

Each mutation's handler body was expanded with the transitive closure of the 52
module-local helper functions it calls, then classified by the first construct it
needs that no `MutationStep` provides. Classification is static and regex-assisted
over that closure; see [Confidence](#confidence) for what that does and does not
establish.

## Findings

### The ladder

| Rung | Construct | Mutations closed | Cumulative |
|---|---|---|---|
| A0 | already plan-shaped | 1 | 1 (4%) |
| A | single-row indexed read (`unique`) | 9 | **10 (40%)** |
| B | bounded set read into a binding (roster) | 4 | **14 (56%)** |
| C | count over a bound set | 8 | **22 (88%)** |
| D | fan-out write over a bound set | 3 | **25 (100%)** |

Per-mutation assignment:

- **A0** — `attachMyAvatar`
- **A** — `ensureMyProfile`, `editProfile`, `createPost`, `setLike`, `setRepost`,
  `ensureFixtureLike`, `ensureFixtureRepost`, `leaveChat`, `markReceiptsThrough`
- **B** — `removeMember`, `promoteAdmin`, `markDelivered`, `markRead`
- **C** — `setFollow`, `ensureFixtureFollow`, `openDm`, `createGroup`, `addMember`,
  `ensureFixtureDm`, `ensureFixtureGroup`, `ensureFixtureMember`
- **D** — `ensureFixturePost`, `sendMessage`, `ensureFixtureMessage`

### The four rungs are one primitive

This is the useful result. They are not four features:

- **A** is the `take(1)` case of a bounded indexed read. `markDelivered`/`markRead`
  literally spell it `.take(2).collect()` then `receipts[0]`, overfetching by one to
  detect duplicates.
- **B** is the same read with `take(51)` — the conversation roster, read via
  `by_current_conversation` with `isCurrent: true`.
- **C** is **B plus an expression that counts a binding**. Every instance is a
  capacity check of the form `rows.length >= limit → ctx.refuse(...)`:
  `requireChatEnvelopeCapacity` (chat envelope), `insertMessageCore` (message
  envelope), `setFollowCore` (following-set capacity).
- **D** is **B plus `insertEach` iterating a binding rather than only an
  argument-supplied array**. `insertMessageCore` reads the roster, computes
  `recipients = activeMembers.filter(...)`, inserts the message, then
  `for (const recipient …)` inserts one receipt per recipient.

So the minimal change set is:

1. **one new step** — a bounded indexed read binding rows (`take` required, so the
   work ceiling is authored, exactly as `bounded-children.v1` does for reads);
2. **a `count(binding)` expression** — closes rung C, which is the largest single
   rung at 32%;
3. **`insertEach` over a binding** — today the guide defines its `source` as "the
   argument-supplied array"; admitting a bound read set closes rung D.

Every read involved is already bounded by an authored `take` in the JS original —
`take(1)`, `take(2)`, `take(51)`, `take(limit)` — so the bounded-work story is
inherited rather than invented.

### The narrow proposal was wrong in a useful direction

LLP 0329.007 §Open question 1 proposed `unique(...)` over a general `lookup` because
it "has a trivial work ceiling (`take + 1`) and a simpler noninterference story."
That reasoning still holds, but the measurement says `unique` alone leaves 60% of
coterie on the JS tier — not a majority, and short of the threshold that would make
the escape rate move.

The general bounded read has the same ceiling story as long as `take` is required and
literal. Its noninterference story is harder only because more rows are exposed to
later expressions, which is the LLP 0329.007 §"What would actually be new" obligation
either way.

### Two smaller gaps, noted for completeness

- **String-length validation.** `ensureMyProfile` and `editProfile` validate via
  `handle.length >= 3 && handle.length <= 20`. The expression vocabulary
  (`add sub mul div mod eqv ne lt lte gt gte and or not neg cond concat coalesce
  record field`) has no string-length operator, so these two need one even after the
  read step lands. Small, and unrelated to the read restriction.
- **`normalizedProfile` throws bare `Error`** for validation rather than using
  `ctx.refuse`, which is an application-side choice, not a platform gap.

## Consequences

1. **Ship the bounded read, not the narrow `unique`.** `unique` is its `take(1)`
   special case and reaches 40%; the general form plus two extensions reaches 100% on
   this application. Shipping `unique` first would be a defensible increment but
   should not be described as closing the gap.
2. **Rung C is the biggest single win** (32%) and is an *expression*, not a step —
   likely the cheapest item in the set once a bound set exists.
3. **The bound is already authored.** Every JS original passes an explicit `take`.
   The step can require it and inherit the existing effect-ceiling machinery rather
   than designing a new one.

## Confidence

Medium-high on the ladder shape and rung membership. The classification is static:
it identifies the first missing construct in each mutation's transitive closure. It
does **not** prove that a plan encoding exists — I did not author 25 plans and run
codegen against them. That translation is the experiment that would make this high
confidence, and it is now the obvious next step.

Explicitly low confidence on the specific 40/56/88/100 percentages as a prediction
about other applications. This is one application, chosen because LLP 0329.006 F1
identified it as the corpus's largest and most realistic — which also makes it
atypical.

Three detector defects were found and corrected during this family's analysis; this
document's first pass had the third. A loose `\.length` pattern classified 17 of 25
mutations as needing a count, because it matched `handle.length >= 3` — string
validation inside `normalizedProfile`, not a query count. The corrected detector
tracks only `.length` on variables bound from a `.collect()` call. The uncorrected
figure is not reported anywhere except here, as a caution about this method.

## Open questions

1. **Author the 25 plans.** Which ones fail codegen, and on what? This is the
   remaining gap between "expressible in principle" and "expressible."
   **Started 2026-08-28 in [LLP 0329.009](./0329.009-plan-translation-experiment.research.md):**
   `editProfile` minus its uniqueness check compiles (`ok: true`), so its rung-A
   verdict is demonstrated rather than inferred and the non-key read is confirmed as
   the sole blocker for that mutation. The other 24 remain untranslated, and rungs
   B/C/D cannot be tried at all because the steps they need do not exist.
2. Does the bound read need `order`, or is an unordered bounded set sufficient? Rungs
   A–D as measured never order the bound rows — `markDelivered` takes `receipts[0]`
   from a 2-row overfetch, and the roster reads filter rather than rank. If ordering
   is genuinely unnecessary, the step is materially simpler than a read query.
3. Does closing all four rungs actually move the escape rate? LLP 0329.006 F2 is the
   standing caution: widening the vocabulary in July did not. A published rerun on a
   fresh Clique pin is the only thing that answers this.
