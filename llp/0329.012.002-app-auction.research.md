# Sealed-bid auction marketplace: where the ladder breaks

## Product contract and invariants

Amounts below are integer cents and times are Unix milliseconds. An auction has at
most 128 distinct bidders and 512 maximum-bid revisions. The target design uses an
internal wallet ledger: placing a maximum bid moves that amount from `available` to
`held`; closing should atomically capture the winner's clearing price and release
every other cent. That target exposes a current Snapback write-authority
impossibility, made explicit below. A real card processor changes the settlement
conclusion again.

The numeric caps are product bounds, not measured Snapback hosted-target limits. I
am assuming one JS mutation can perform the resulting bounded write set. If the
actual target ceiling is lower, the bidder/revision caps must be lowered to fit;
chunking the close would violate the stated atomic reveal-and-settlement invariant.

The auction is a sealed proxy auction:

- A bidder may only raise their maximum. Their current maximum ranks for the
  auction; revisions remain as immutable history.
- Highest maximum wins. Ties go to the earliest `rankedAt`; a server-minted
  `rankKey` is the stable final tie-breaker when two commits receive the same
  millisecond. A timestamp-only rule is not a total order.
- The clearing price is `max(reserve, min(winnerMaximum,
  runnerUpMaximum + increment))`. With one bidder it is the reserve.
- A bid accepted with `0 < closesAt - now <= antiSnipeWindowMs` advances
  `closesAt` by `extensionMs` and increments `closeGeneration`.
- Before close, a principal can read only their own commitments and revisions.
  After the close transaction commits, public copies of every revision, the final
  standings, and compressed proxy runs exist. The protected source rows never
  change visibility.

The non-negotiable invariants are:

1. No buyer, including the eventual winner, learns another buyer's amount before
   the close transaction commits. The seller cannot read them either.
2. A client clock is never an authorization input. Bid admission uses one frozen
   `ctx.runtime.now()` inside the mutation.
3. A close job for an obsolete deadline can never close or reveal the auction. The
   auction row's current `(closeGeneration, closesAt)` is canonical.
4. A close is idempotent and has one deterministic winner and price for its frozen
   commitment set.
5. `bidRevisions` is append-only history; `bidCommitments` is the current ranking
   projection. Updating one without the other is forbidden.
6. Every active maximum is fully held. Wallet available and held balances never go
   negative, and increasing a maximum reserves only the delta.
7. The close commit atomically writes the winner, wallet debits/releases, hold
   states, settlement, public reveals, and in-app notices. There is no interval in
   which bids are public but the winner is undecided.
8. Every set is explicitly bounded. A 129th bidder or 513th revision refuses at bid
   time; a close never silently truncates.
9. Proxy history is a deterministic fold over ordered maximum revisions. It is
   stored as compressed runs, not one database row per price increment.
10. An auction may be logically past its bid deadline while still awaiting its
    close worker. During that interval new bids refuse, rows remain sealed, and the
    public state is still `open`; clients may display “closing” from `closesAt`, but
    cannot treat that display as authority.

### The overlooked temporal transition: stale close incarnations

This is the auction analogue of coterie's active-versus-historical membership
trap. A queued close job is a fact about a **historical deadline incarnation**.
The auction row is the **active deadline incarnation**. Anti-sniping creates a new
incarnation without cancelling the already durable old job.

A naive job carrying only `auctionId` fires at the old deadline and closes the
auction early. Checking “my scheduled time has arrived” does not help: that time is
precisely the superseded one. Every job must carry `closeGeneration`; the close
transaction must reread the auction and require all of:

```text
state == "open"
job.closeGeneration == auction.closeGeneration
ctx.runtime.now() >= auction.closesAt
```

The bid mutation must patch the new deadline/generation and enqueue its replacement
job in the same transaction. An old job then becomes a harmless no-op. A periodic
repair sweep handles a current-generation job that exhausts its retries.

The public notice table is acceptable only because this product publishes bidder
identities and standings at close. If bidder identities must remain private after
close, this table needs a different authorization model; filtering a public table
by `recipientId` in a query is not authorization.

### A second head-on collision: the scheduler cannot settle owner rows

`wallets` and `fundingHolds` must be owner-visible or they disclose private financial
state. Snapback's owner write boundary permits a generic patch only when the old
row's owner equals the effective user principal. A scheduled action has system
authority and no user principal. `ctx.db.elevated` deliberately elevates **reads
only**; there is no elevated write form or system-owner stamping mode.

Consequently, the close handler below is the exact desired atomic transaction in
real JS authoring syntax, but current Snapback makes each cross-owner wallet or hold
patch an owner-scoped no-op (`false`). The handler must detect that and abort; if it
ignored the return, it could publish a false settlement. Making those tables
`public-read` is not a fix: it exposes balances and public read is not a generic write
grant. Running one nested mutation “as each bidder” is also unavailable: current
one-off jobs run as system, not under a captured arbitrary-principal grant.

The literal scheduled, atomic internal-ledger settlement requirement is therefore
not deployable today. The code is retained because it precisely locates the missing
capability; silently replacing it with a multi-transaction loop would violate the
stated invariant.

## The eight hard operations (`functions.mjs`)

The snippets use current Snapback authoring constructs. The bounded indexed-read

### 1. Publish and transactionally schedule the first close

```js
import {
  arg,
  asc,
  authUserId,
  defineAction,
  defineCron,
  defineJsLiveQuery,
  defineJsMutation,
  defineLiveQuery,
  eq,
  lit,
  results,
  v,
} from '@expo/snapback-codegen/define';

export const publishAuction = defineJsMutation({
  auth: 'authenticated',
  args: { auctionId: v.id('auctions') },
  refusals: [
    'AUCTION_NOT_FOUND', 'AUCTION_NOT_DRAFT',
    'AUCTION_TIME_INVALID', 'AUCTION_PROXY_RANGE_TOO_LARGE',
  ],
  reads: ['auctions', 'auctionRoles'],
  writes: ['auctions'],
  result: results.value(v.object({ closesAt: v.integer(), generation: v.integer() })),
  handler: async (ctx, args) => {
    const auction = await ctx.db.get('auctions', args.auctionId);
    if (!auction) ctx.refuse('AUCTION_NOT_FOUND');
    await ctx.permissions.auctionRoles.requireRole(args.auctionId, 'seller');
    if (auction.state !== 'draft') ctx.refuse('AUCTION_NOT_DRAFT');

    const now = ctx.runtime.now();
    const delayMs = auction.closesAt - now;
    // One-off jobs currently have a 30-day horizon.
    if (delayMs <= 0 || delayMs > 30 * 24 * 60 * 60 * 1000) {
      ctx.refuse('AUCTION_TIME_INVALID');
    }
    // Bounds the total number of conceptual proxy increments. The close writes
    // compressed runs, but this also prevents pathological arithmetic/history.
    const possibleSteps = Math.ceil(
      (auction.maxBidAmount - auction.reserve) / auction.increment,
    );
    if (auction.reserve < 0
        || auction.increment <= 0
        || auction.maxBidAmount < auction.reserve
        || auction.antiSnipeWindowMs < 0
        || auction.extensionMs <= 0
        || auction.extensionMs > 30 * 24 * 60 * 60 * 1000
        || possibleSteps > 4096) {
      ctx.refuse('AUCTION_PROXY_RANGE_TOO_LARGE');
    }

    const generation = auction.closeGeneration + 1;
    await ctx.db.patch('auctions', auction._id, { state: 'open', closeGeneration: generation });
    await ctx.jobs.enqueue(
      'closeAuctionAtGeneration',
      { auctionId: auction._id, generation },
      {
        delayMs,
        maxAttempts: 3,
        idempotencyKey: `close:${auction._id}:${generation}`,
      },
    );
    return { closesAt: auction.closesAt, generation };
  },
});
```

### 2. Place or raise a sealed maximum, reserve funds, and auto-extend

The auction row serializes bidder/revision counters and deadline changes. The wallet
row serializes competing reservations by the same buyer. The unique commitment and
hold indexes close the concurrent first-bid race.

```js
export const placeMaximumBid = defineJsMutation({
  auth: 'authenticated',
  args: {
    auctionId: v.id('auctions'),
    walletId: v.id('wallets'),
    maximumAmount: v.integer(),
  },
  refusals: [
    'AUCTION_NOT_FOUND', 'AUCTION_NOT_OPEN', 'AUCTION_CLOSED',
    'SELLER_CANNOT_BID', 'BID_OUT_OF_RANGE', 'MAXIMUM_MUST_INCREASE',
    'WALLET_NOT_FOUND', 'WALLET_NOT_OWNED', 'INSUFFICIENT_FUNDS',
    'BIDDER_LIMIT', 'REVISION_LIMIT',
  ],
  reads: ['auctions', 'wallets', 'bidCommitments', 'fundingHolds'],
  writes: ['auctions', 'wallets', 'fundingHolds', 'bidCommitments', 'bidRevisions'],
  result: results.value(v.object({
    commitmentId: v.id('bidCommitments'),
    closesAt: v.integer(),
    generation: v.integer(),
  })),
  handler: async (ctx, args) => {
    const now = ctx.runtime.now();
    const auction = await ctx.db.get('auctions', args.auctionId);
    if (!auction) ctx.refuse('AUCTION_NOT_FOUND');
    if (auction.state !== 'open') ctx.refuse('AUCTION_NOT_OPEN');
    if (now >= auction.closesAt) ctx.refuse('AUCTION_CLOSED');
    if (auction.sellerId === ctx.auth.userId) ctx.refuse('SELLER_CANNOT_BID');
    if (args.maximumAmount < auction.reserve || args.maximumAmount > auction.maxBidAmount) {
      ctx.refuse('BID_OUT_OF_RANGE');
    }
    if (auction.revisionCount >= 512) ctx.refuse('REVISION_LIMIT');

    const wallet = await ctx.db.get('wallets', args.walletId);
    if (!wallet) ctx.refuse('WALLET_NOT_FOUND');
    if (wallet.ownerId !== ctx.auth.userId) ctx.refuse('WALLET_NOT_OWNED');

    const existing = await ctx.db.query('bidCommitments')
      .withIndex('by_auction_bidder')
      .eq('auctionId', args.auctionId)
      .eq('bidderId', ctx.auth.userId)
      .first();
    if (!existing && auction.bidderCount >= 128) ctx.refuse('BIDDER_LIMIT');
    if (existing && args.maximumAmount <= existing.maximumAmount) {
      ctx.refuse('MAXIMUM_MUST_INCREASE');
    }

    const delta = args.maximumAmount - (existing?.maximumAmount ?? 0);
    if (wallet.availableCents < delta) ctx.refuse('INSUFFICIENT_FUNDS');
    await ctx.db.patch('wallets', wallet._id, {
      availableCents: wallet.availableCents - delta,
      heldCents: wallet.heldCents + delta,
      updatedAt: now,
    });

    let holdId;
    let commitmentId;
    let revisionNo;
    const rankKey = ctx.runtime.id();
    if (existing) {
      const hold = await ctx.db.get('fundingHolds', existing.holdId);
      if (!hold || hold.state !== 'active' || hold.walletId !== wallet._id) {
        throw new Error('active commitment/hold invariant violated');
      }
      holdId = hold._id;
      commitmentId = existing._id;
      revisionNo = existing.revisionNo + 1;
      await ctx.db.patch('fundingHolds', hold._id, {
        authorizedAmount: args.maximumAmount,
        updatedAt: now,
      });
      await ctx.db.patch('bidCommitments', existing._id, {
        maximumAmount: args.maximumAmount,
        rankedAt: now,
        rankKey,
        revisionNo,
      });
    } else {
      holdId = await ctx.db.insert('fundingHolds', {
        auctionId: auction._id,
        walletId: wallet._id,
        authorizedAmount: args.maximumAmount,
        capturedAmount: 0,
        state: 'active',
        updatedAt: now,
        // bidderId is host-stamped by the owner write policy.
      });
      commitmentId = await ctx.db.insert('bidCommitments', {
        auctionId: auction._id,
        walletId: wallet._id,
        holdId,
        maximumAmount: args.maximumAmount,
        rankedAt: now,
        rankKey,
        revisionNo: 1,
        // bidderId is host-stamped.
      });
      revisionNo = 1;
    }

    await ctx.db.insert('bidRevisions', {
      auctionId: auction._id,
      commitmentId,
      holdId,
      revisionNo,
      maximumAmount: args.maximumAmount,
      submittedAt: now,
      rankKey,
      // bidderId is host-stamped.
    });

    const extendsAuction = auction.closesAt - now <= auction.antiSnipeWindowMs;
    const closesAt = extendsAuction
      ? auction.closesAt + auction.extensionMs
      : auction.closesAt;
    const generation = extendsAuction
      ? auction.closeGeneration + 1
      : auction.closeGeneration;
    await ctx.db.patch('auctions', auction._id, {
      bidderCount: auction.bidderCount + (existing ? 0 : 1),
      revisionCount: auction.revisionCount + 1,
      closesAt,
      closeGeneration: generation,
    });

    if (extendsAuction) {
      await ctx.jobs.enqueue(
        'closeAuctionAtGeneration',
        { auctionId: auction._id, generation },
        {
          delayMs: closesAt - now,
          maxAttempts: 3,
          idempotencyKey: `close:${auction._id}:${generation}`,
        },
      );
    }
    return { commitmentId, closesAt, generation };
  },
});
```

`ctx.runtime.now()` is legal and necessary in a mutation. This operation is not safe for
offline optimistic execution: an offline client cannot know whether its bid beat the
deadline, reserved a concurrently spent wallet balance, or extended the auction.

```js
export const bidsByClock_DO_NOT_SHIP = defineJsLiveQuery({
  args: { auctionId: v.id('auctions') },
  auth: 'authenticated',
  result: results.documents('bidRevisions'),
  reads: ['auctions', 'bidRevisions'],
  handler: async (ctx, args) => {
    const auction = await ctx.db.get('auctions', args.auctionId);
    if (ctx.runtime.now() < auction.closesAt) {
      return ctx.db.query('bidRevisions')
        .withIndex('by_auction_bidder_time')
        .eq('auctionId', args.auctionId)
        .eq('bidderId', ctx.auth.userId)
        .collect();
    }
    return ctx.db.elevated.query('bidRevisions')
      .withIndex('by_auction_time')
      .eq('auctionId', args.auctionId)
      .collect();
  },

```

It receives `SNAPBACK_AUTH_CLOCK_DEPENDENT_VISIBILITY`, correctly. Passing a pinned
client `clockMs` would make the subscription deterministic but would let an
untrusted client ask for post-close authority early. Pinned clocks are suitable for
presentation windows, not for releasing sealed bids.

### 7. Close, rank, replay proxy bids, and settle atomically

These helpers are ordinary top-level function declarations so current Snapback can
splice them into the inline handler.

The body shows the required single transaction. Its protected-set reads are
available through `ctx.db.elevated`; its cross-owner `ctx.db.patch` calls are the
current runtime blocker described above. No successful execution is claimed.

```js
function compareRankKeys(a, b) {
  return a < b ? -1 : (a > b ? 1 : 0);
}

function rankCommitments(rows) {
  return rows.slice().sort((a, b) =>
    (b.maximumAmount - a.maximumAmount)
    || (a.rankedAt - b.rankedAt)
    || compareRankKeys(a.rankKey, b.rankKey));
}

function replayProxyRuns(revisions, reserve, increment) {
  const ordered = revisions.slice().sort((a, b) =>
    (a.submittedAt - b.submittedAt) || compareRankKeys(a.rankKey, b.rankKey));
  const maxima = new Map();
  const runs = [];
  let price = reserve;
  let previousLeader = null;

  for (const revision of ordered) {
    maxima.set(revision.bidderId, {
      bidderId: revision.bidderId,
      maximumAmount: revision.maximumAmount,
      rankedAt: revision.submittedAt,
      rankKey: revision.rankKey,
    });
    const ranked = Array.from(maxima.values()).sort((a, b) =>
      (b.maximumAmount - a.maximumAmount)
      || (a.rankedAt - b.rankedAt)
      || compareRankKeys(a.rankKey, b.rankKey));
    const leader = ranked[0];
    const runnerUp = ranked[1];
    const target = runnerUp
      ? Math.max(reserve, Math.min(leader.maximumAmount, runnerUp.maximumAmount + increment))
      : reserve;
    if (target > price || leader.bidderId !== previousLeader) {
      const increase = Math.max(0, target - price);
      runs.push({
        causedByRevisionId: revision._id,
        leaderId: leader.bidderId,
        fromAmountExclusive: price,
        toAmountInclusive: target,
        increment,
        stepCount: increase === 0 ? 0 : Math.ceil(increase / increment),
        ordinal: runs.length + 1,
      });
      price = target;
      previousLeader = leader.bidderId;
    }
  }
  return { runs, price };
}

export const closeAuctionTx = defineJsMutation({
  // Scheduler-compatible, and therefore also client-callable. The lack of an
  // internal-only system callee is discussed below.
  auth: 'public',
  args: { auctionId: v.id('auctions'), generation: v.integer() },
  refusals: ['CLOSE_NOT_DUE', 'CLOSE_SET_TOO_LARGE'],
  reads: [
    'auctions', 'bidCommitments', 'bidRevisions',
    'fundingHolds', 'wallets', 'settlements',
  ],
  writes: [
    'auctions', 'fundingHolds', 'wallets', 'settlements',
    'revealedBids', 'revealedProxyRuns', 'auctionNotices',
  ],
  result: results.value(v.object({ outcome: v.string() })),
  handler: async (ctx, args) => {
    const auction = await ctx.db.get('auctions', args.auctionId);
    if (!auction || auction.state === 'closed') return { outcome: 'unchanged' };
    // This is the load-bearing stale-incarnation fence.
    if (auction.state !== 'open' || auction.closeGeneration !== args.generation) {
      return { outcome: 'stale-generation' };
    }
    const now = ctx.runtime.now();
    if (now < auction.closesAt) ctx.refuse('CLOSE_NOT_DUE');

    // Every elevated row is scoped back to the public resource argument. The
    // handler returns no secret rows; after the trusted deadline its purpose is to
    // materialize exactly those rows as public facts.
    const commitments = await ctx.db.elevated.query('bidCommitments')
      .withIndex('by_auction_max_time')
      .eq('auctionId', args.auctionId)
      .take(129)
      .collect();
    const revisions = await ctx.db.elevated.query('bidRevisions')
      .withIndex('by_auction_time')
      .eq('auctionId', args.auctionId)
      .take(513)
      .collect();
    if (commitments.length > 128 || revisions.length > 512) {
      ctx.refuse('CLOSE_SET_TOO_LARGE');
    }

    const ranked = rankCommitments(commitments);
    if (ranked.length === 0) {
      await ctx.db.patch('auctions', auction._id, { state: 'closed', closedAt: now });
      return { outcome: 'closed-no-bids' };
    }
    const winner = ranked[0];
    const runnerUp = ranked[1];
    const clearingPrice = runnerUp
      ? Math.max(auction.reserve,
          Math.min(winner.maximumAmount, runnerUp.maximumAmount + auction.increment))
      : auction.reserve;
    const proxy = replayProxyRuns(revisions, auction.reserve, auction.increment);
    if (proxy.price !== clearingPrice) {
      throw new Error('proxy fold/ranking projection drift');
    }

    let releasedAmount = 0;
    for (const [index, commitment] of ranked.entries()) {
      const hold = await ctx.db.elevated.get('fundingHolds', commitment.holdId);
      const wallet = await ctx.db.elevated.get('wallets', commitment.walletId);
      if (!hold || !wallet || hold.state !== 'active'
          || hold.authorizedAmount !== commitment.maximumAmount) {
        throw new Error('commitment/hold/wallet invariant violated');
      }
      const isWinner = index === 0;
      const released = isWinner
        ? hold.authorizedAmount - clearingPrice
        : hold.authorizedAmount;
      releasedAmount += released;
      const walletPatched = await ctx.db.patch('wallets', wallet._id, {
        availableCents: wallet.availableCents + released,
        heldCents: wallet.heldCents - hold.authorizedAmount,
        spentCents: wallet.spentCents + (isWinner ? clearingPrice : 0),
        updatedAt: now,
      });
      const holdPatched = await ctx.db.patch('fundingHolds', hold._id, {
        capturedAmount: isWinner ? clearingPrice : 0,
        state: isWinner ? 'captured' : 'released',
        updatedAt: now,
      });
      // Owner writes return false for a not-owned row. Never ignore that result:
      // doing so could publish a settlement whose money movement was a no-op.
      if (!walletPatched || !holdPatched) {
        throw new Error('SYSTEM_SETTLEMENT_WRITE_UNAVAILABLE');
      }
      await ctx.db.insert('revealedBids', {
        auctionId: auction._id,
        rowKind: 'standing',
        bidderId: commitment.bidderId,
        sourceId: `standing:${commitment._id}`,
        revisionNo: commitment.revisionNo,
        maximumAmount: commitment.maximumAmount,
        submittedAt: commitment.rankedAt,
        finalRank: index + 1,
      });
      await ctx.db.insert('auctionNotices', {
        auctionId: auction._id,
        recipientId: commitment.bidderId,
        kind: isWinner ? 'won' : 'lost',
        createdAt: now,
      });
    }
    for (const revision of revisions) {
      await ctx.db.insert('revealedBids', {
        auctionId: auction._id,
        rowKind: 'revision',
        bidderId: revision.bidderId,
        sourceId: `revision:${revision._id}`,
        revisionNo: revision.revisionNo,
        maximumAmount: revision.maximumAmount,
        submittedAt: revision.submittedAt,
        finalRank: 0,
      });
    }
    for (const run of proxy.runs) {
      await ctx.db.insert('revealedProxyRuns', { auctionId: auction._id, ...run });
    }

    const settlementId = await ctx.db.insert('settlements', {
      auctionId: auction._id,
      winnerId: winner.bidderId,
      winnerHoldId: winner.holdId,
      chargeAmount: clearingPrice,
      releasedAmount,
      state: 'settled',
      createdAt: now,
    });
    await ctx.db.patch('auctions', auction._id, {
      state: 'closed',
      winnerId: winner.bidderId,
      winnerMaximum: winner.maximumAmount,
      clearingPrice,
      closedAt: now,
      settlementId,
    });
    return { outcome: 'closed' };
  },
});

export const closeAuctionAtGeneration = defineAction({
  auth: 'public',
  args: { auctionId: v.id('auctions'), generation: v.integer() },
  result: results.value(v.object({ outcome: v.string() })),
  handler: async (ctx, args) => ctx.runMutation('closeAuctionTx', args),
});
```

`auth: 'public'` is not an internal-only declaration. An anonymous client can invoke
`closeAuctionTx`; the generation and server-time guards prevent an early reveal, but
the call still reaches a bounded elevated-read/work path after the deadline. On the
current platform its cross-owner patches then refuse, as do the scheduler's. If a
future system-write capability made those patches legal, it must also distinguish a
scheduled system invocation from this public caller—or explicitly declare
permissionless finalization. Merely changing an action to `public` never makes its
nested mutation internal-only.

The final auction patch is not a later commit: all handler writes settle together.
If any wallet, reveal, notice, or settlement write fails, none of them commit and
the auction remains open-but-past-deadline for retry.

On current Snapback the owner-write check is exactly such a failure: system authority
cannot patch the winner's or losers' owner rows. Moving the loop into an action does
not repair it because actions provide neither transactional database writes nor
principal impersonation.

The proxy “cascade” is real but compressed. One revision may move the virtual price
through hundreds of increments; one `revealedProxyRuns` row records the leader,
range, increment, and step count. Requiring one durable row per virtual increment
would require data-dependent recursive fan-out and make the write budget depend on
currency magnitude. That is a bad product/storage requirement unless each virtual
step is a legally required signed event.

Because this auction exposes no intermediate price, replaying that deterministic
proxy fold inside close is behaviorally equivalent to generating the invisible steps
when each maximum arrives. It would not be equivalent in an open ascending auction,
or where every derived bid needs an immediate external timestamp; those versions
really require F's stateful cascade during `placeMaximumBid`.

### 8. Repair a missing or dead current-generation close job

One-off jobs are at-least-once and have finite retry budgets. A low-frequency cron
does a bounded range scan and enqueues fresh idempotent repair attempts. It does not
decide visibility itself.

```js
export const enqueueOverdueClosures = defineJsMutation({
  auth: 'public',
  args: {},
  reads: ['auctions'],
  writes: ['auctions'], // upper-bound declaration; durable job enqueues are the effect
  result: results.value(v.object({ enqueued: v.integer(), hasMore: v.boolean() })),
  handler: async (ctx) => {
    const now = ctx.runtime.now();
    const minuteBucket = Math.floor(now / 60_000);
    const due = await ctx.db.query('auctions')
      .withIndex('by_state_close')
      .eq('state', 'open')
      .lte('closesAt', now)
      .order('closesAt', 'asc')
      .take(9)
      .collect();
    for (const auction of due.slice(0, 8)) {
      await ctx.jobs.enqueue(
        'closeAuctionAtGeneration',
        { auctionId: auction._id, generation: auction.closeGeneration },
        {
          delayMs: 0,
          maxAttempts: 3,
          idempotencyKey:
            `repair-close:${auction._id}:${auction.closeGeneration}:${minuteBucket}`,
        },
      );
    }
    return { enqueued: Math.min(due.length, 8), hasMore: due.length > 8 };
  },
});

export const runOverdueClosureSweep = defineAction({

  args: {},
  result: results.value(v.object({ enqueued: v.integer(), hasMore: v.boolean() })),

export const auctionClosureCron = defineCron({

    schedule: { everyMs: 60_000 },
```

The repair idempotency key includes a minute bucket, so it can create a new job after
a prior minute's identity became terminal while repeated direct or cron calls within
one minute deduplicate. Regardless, `closeAuctionTx` is the final idempotency and
generation fence.

### Finding 3's count rule

No protected-row count drives a buyer-visible refusal in this design.
`bidderCount` and `revisionCount` are intentionally public fields on the auction
resource and are updated in the same transaction as the protected rows. The limit
refusal therefore reveals only an already-readable resource fact.

Trying to replace `bidderCount` with `count(myVisibleCommitments)` is wrong: owner
visibility gives the buyer only zero or one row, so a globally full auction appears
not full. An elevated count of all commitments is keyed to an auction resource, but
the bidder has no declared permission over that resource that authorizes reading
other bidders' protected rows. Finding 3 should refuse that plan. A public
denormalized counter is the honest product choice when bid count itself is not
secret.

The close path does read and count protected sets and may also be invoked by an
anonymous finalizer, but it emits no secret-derived capacity decision during normal
operation. Its over-limit refusal is an invariant alarm made unreachable by public
resource counters. Every elevated row is scoped to `auctionId`, and the desired
handler would reveal it only after the trusted deadline as part of the atomic public
transition.
Finding 3's elevated-read contract does not quite describe this case: the caller has
neither a seller role nor private-row visibility; the product grants a public,
state-and-server-time-gated **transition**, not general read authority. A first-class
system-only scheduled transition would avoid needing this carefully hand-audited JS
exception.

## Verdict

The model does **not** survive this application as a claim that A–D closes realistic
hard mutations. The bound read remains necessary and useful, but the auction adds
several independent dimensions.

The next two data rungs should be:

- **E — bounded ordered/range reduction:** indexed interval predicates, explicit
  stable multi-key ordering, and reductions such as `argMax`/`topK` (with tie keys).
  `highest bid wins` is not a count.
- **F — bounded stateful set transformation:** fold an ordered binding into state and
  derived rows, plus `patchEach`/`deleteEach` as well as `insertEach`. Settlement
  updates each hold and wallet; proxy bidding makes each derived state depend on the
  prior state. Row-independent D fan-out cannot express either.

Transactional job enqueue and scheduled system authority are not honestly “rung G”:
they are an orthogonal execution axis. So is clock-driven visibility. The latter
should not be added as a permissive visibility grammar feature. The safe pattern is
to keep authorization time-independent and turn the deadline into a durable state
transition that invalidates live queries.

Ranked by product impact, the missing capabilities are:

1. A resource-scoped system settlement primitive (or equivalent declared write
   authority) that may atomically patch the bounded owner rows selected by a
   scheduled close. Read elevation alone cannot settle.
2. A first-class, analyzable scheduled transition with transactional enqueue,
   generation fencing, system-only invocation, and repair semantics.
3. E's protected `argMax`/ranking and interval scans.
4. F's stateful fold and fan-out patch, needed by both proxy replay and settlement.
5. An analyzer-enforced, resource-scoped public finalization transition—or an
   internal system-only callee—rather than a hand-audited public JS handler using
   `ctx.db.elevated`.
6. A declarative idempotent effect/outbox model if “notify” means push/email rather
   than the atomic in-app notice row.

### Product changes are part of the correct answer

Three apparent backend requirements should be changed rather than papered over:

1. **Change “bids become visible at exactly `closesAt`” to “bids stop being accepted
   at `closesAt` and become visible when the fenced close commit succeeds, never
   before.”** This preserves secrecy through scheduler outages. It is not acceptable
   to make this change when a statute or exchange rule requires dissemination at an
   exact instant; current Snapback cannot meet that requirement with authenticated
   live queries.
2. **Store compressed proxy runs, not one row per virtual increment.** The final
   outcome and an exact reconstructible audit remain. This is not acceptable if each
   derived bid must carry its own external signature or legal timestamp; that product
   needs a bounded event count or a different execution substrate.
3. **Choose between stronger backend authority and weaker settlement semantics.**
   An internal wallet can be truly atomic only after Snapback gains a declared,
   bounded system write capability over the affected owner rows. Current Snapback's
   alternatives are buyer-claimed releases (not atomic at close) or an external
   payment saga. A card-network capture/release and a Snapback commit cannot be one
   atomic transaction: close must write idempotent capture, release, and notification
   intents; workers execute them at least once and a settlement state machine reports
   pending/failed/succeeded. Claiming cross-system atomicity would be false.

The collision with `SNAPBACK_AUTH_CLOCK_DEPENDENT_VISIBILITY` is therefore a useful
refusal, not a defect. The application then exposes the missing positive half: a
durable scheduled transition and a bounded system settlement authority that make the
secure alternative analyzable and executable.
