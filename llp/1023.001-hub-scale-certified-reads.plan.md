## Outcome and owner

A builder finds a compiling, complete form for Following, grouped message
search, rich thread history and scheduled digest. The form retains the required
population, content, authorization and ordering within current certified
limits. Refusal text explains the actual expensive term and a tested repair.

Implementer: Codex / Astra, existing Snapback 2 compiler/core lane, under the
parent's 2026-09-12 commission. The first slice is a requirement and cost
audit, followed by the smallest demonstrated product repair. There is no
decision to freeze 500, 100 or 10 as universal platform limits.

## B — Turn reported refusals into costed reproductions

Recover the exact Quarry shapes, declared field widths, rules, caps and
diagnostics from the report's retained artifacts. Preserve them as evidence,
then minimize without changing the term that caused refusal. Record package/
source, operation, arguments and `check --cost --json` output.

The report's approximate 6–7 MiB closure, 16–32 MiB search closure and 18.5 MiB
thread heap are certificate bounds for particular programs. They are not
measured allocations or a table of universal lane limits. The 256 live-shape
limit is a separate client subscription admission limit, not a row or
certifier heap limit. Diagnose the failed operation before associating it with
one of these numbers.

Compile and execute the required forms in existing compiler/core/consumer
test surfaces. Test current main before changing prices: LLP 1020's diagnostic
terms and recent client/page work may already change the right repair.
Do not make the initial log's admitted/refused outcome an immutable oracle.

## C — Choose a complete form, in this order

1. **Existing single bounded query.** Try the documented indexed/lazy merge
   with the actual schema, visibility, lane discovery and output. Retain all
   required lanes. If an overcount is demonstrated, repair the accounting
   with Rust/TS parity and adversarial bound tests. Heap, closure, output,
   rule probes and steps all remain sound.
2. **Existing complete composition.** If the honest single-query bound still
   refuses, use cursor pages, smaller rich pages or complete chunk jobs only
   where they preserve the screen contract. Ship the compiling code and its
   integration in the package's existing guide/examples, not prose that asks
   each builder to invent a merge engine.
3. **Unresolved capability.** If neither form can express the requirement,
   retain the gap and the failing consumer case. No new index/read model,
   query-composition mechanism, grammar or client-side N-way merge is selected
   in this program. Such a redesign is a separately scoped decision. A bounded
   lane exit is not complete hub support; lowering the population, raising
   ceilings or documenting a refusal cannot mark that product outcome complete.

Output projection alone may not reduce full-row custody. Narrowing a schema
field bound changes accepted application data. Neither is an accounting fix
unless the original contract is preserved. `check --cost` should explain
these distinctions on both admitted and refused programs.

### Following and search

A `first 500` lane discovery covers at most those selected follows; it does
not page the omitted lanes. Keep the baseline feed correct at its required
500-follow population, including self, duplicates, timestamp ties and hidden
rows. An exploratory 1,000-follow case may improve; do not require it to
refuse after a sound optimization.

For global search, cover the hub's entire 1,000-conversation membership set.
A 100-chat slice alone fails. Before choosing a composition, specify:

- How membership continuation reaches every chat and how each result page
  continues. Preserve opaque cursor ownership; a message cursor is not a
  membership cursor.
- The required ordering: Clique groups results by chat. Do not silently add
  a globally ranked top-K promise; if a chosen presentation does promise a
  global order, prove it across all participating lanes before publishing it.
- Empty early slices, matches only in the last membership slice, ties,
  duplicate messages, argument changes, membership changes, revocation and
  boundary invalidation. Smaller pages cannot falsely signal exhaustion.
- Warm/cold offline search of held data. Preserve exact held/partial states;
  separate pages do not acquire one combined receipt or a common server
  snapshot. The existing page resource owns only continuations it supports.
- Bounded subscriptions and work. Do not mount one live query for every chat
  or fetch the corpus into JavaScript to reconstruct a server answer.

Compile the proposed recipe before teaching it. `held_search` and dynamic
array-merge spellings from a failed builder attempt are not evidence that
either is an intended API. Prefer an existing legal spelling; do not accept a
guess as a new language feature just to improve a diagnostic.

### Rich thread

Qualify a smaller composite page with the original author, quote, reaction
and receipt fields; reach at least the original 50 messages through valid
continuation and onward into busy history. Use existing `usePage` /
`observePages` and declared history where appropriate. Verify insertion,
editing and removal across page boundaries without duplicates or lost rows.

A separate raw-history query may supply authorized items under the existing
fallback contract; it cannot supply the composite's count or preview.
Independent detail reads observe independent snapshots. Do not describe that
composition as one atomic 50-row result, or drop enrichments without an
explicit screen-policy decision.

### Digest and backfill

Bounded jobs are already a product form, not inherently a workaround. Ship
one concise recipe for compact contributions plus complete chunk processing
only if it satisfies the original digest: fixed period boundaries, correct
counts, current authorization/expiry exclusions, no output for zero activity,
and one logical emission per user/period across retry and restart.

Use the existing job cursor/progress transaction and effect seam. Do not emit
a final total from a partial chunk or count a chat the target cannot read.
State how membership/content changes during a multi-chunk run affect the
recipe; a job does not promise one snapshot spanning all chunks.

Authorization and expiry are evaluated at the final per-user emission. A
system-owned job bypasses viewer read rules; filtering each earlier chunk is
insufficient if eligibility can change before emission. Use an existing bounded
recipe whose contributions remain correct under those changes or whose final
operation can validate the necessary facts. Do not assume an unbounded final
rescan. Qualify accumulation followed by membership revocation, content deletion
or expiry before emission, then repeat the final chunk across restart. If no
supported bounded form satisfies those obligations, retain a specific digest
gap rather than weakening the requirement to per-chunk authorization.

Backfill size 25 versus 100 is an implementation choice when all rows are
processed with bounded progress and restart safety. Include that reproduction
only if it improves the same repair guidance; it is secondary to read coverage.

## D — Diagnostics that teach the verified repair

Keep `E_BOUND` / `E_STEPS` tied to the operation's priced term. Where a
unique, semantics-preserving local edit is known, return that compiling edit.
Otherwise name the mechanism and the relevant executed guide example; do not
paste an arbitrary `first 100` as if it preserves population.

Read `guide merge`, `bounds`, `pagination`, `fanout`, `shape` and
`job`; some already warn that smaller lane bounds narrow the population.
Replace insufficient examples instead of expanding a second guide. Test
examples through the existing snippet/consumer checks. Stable diagnostic
family/site/repair coverage matters; exact prose substring tests alone do
not prove a repair compiles.

## Acceptance

| Case | Required result |
| --- | --- |
| Baseline Following | 500-follow + self enriched feed certifies and returns correct ordered pages |
| Hub search | A shipped compiling form reaches a match only in the final slice of 1,000 chats; paging, permission and offline controls pass |
| Rich history | Full fields and required history remain reachable through smaller pages; live boundaries preserve identity and continuation |
| Digest | Full-population scheduled result is correct with every client closed; restart/retry and authorization cases pass |
| Refusals | Honest over-budget cases still refuse; their recommended fixture compiles and preserves the stated contract |
| Cost | Sound accounting and existing limits; measure actual fixture latency separately from static bounds |

Use affected tests in the existing suite. Full-scale browser/probe runs use
existing scheduled/qualification machinery; they are not a new landing gate.
No forced refusal for 1,000 lanes or 50 composite rows: sound future admission
is welcome. No ceiling increase, benchmark reduction or unsupported client
merge recipe is selected. Completion requires a working published-consumer
form, not just clearer failure wording.
