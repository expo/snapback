## 2. What the builder wrote by hand

The builder's final report lists ten candid gaps (`final-report.md:165–176`).
This RFC takes five of them:

1. **A server `history` beside a held `historyHeld`, merged in the client**
   (`schema.q:319–324`; the M8 merge of "live + held + queued",
   `run-log.md:38`). A `held:` history compiled, then live DMs showed no
   bubble (`diary.md:37`), and the HTTP acceptance suite got `E_QUERY_HELD`
   (`diary.md:59`). Search kept the same kind of pair: `searchInChat` on the
   server for one conversation, `searchHeld` on the device over every
   holding (`schema.q:345–353`). Those two are not the same query.
2. **A shell-wide delivery acknowledgement.** `DeliveryAck` on the signed-in
   shell (`app/_layout.tsx:57`) acknowledges each inbox row's `lastOrdinal`
   (`src/InboxStrip.tsx:62–75`). That shows the mounting problem: the card's
   hook runs only per mounted conversation. It is not a correct reporter,
   since it acknowledges messages it never fetched. The 0.4.1 comparative
   charged the same thing, and it is LLP 3000.019's P7.
3. **`SNAPBACK4_BIN`.** npm has no Linux binary, so a Linux installation needs
   an externally supplied one (`final-report.md:114`, `167`). The harness
   supplied it.
4. **A client snapshot of a conversation after removal.** `messages` declares
   `retain delivered-history`; `conversations` does not
   (`schema.q:120–130`, `198`), and the thread screen unmounted.
5. **The first-account path.** The README's first account path shows no
   `mintId()`, `held` or `retain` (`packages/snapback4/README.md:6–73`).
   The builder wrote `src/ids.mjs` to convert fixture tokens into accepted
   ids.

§6 names the other scorer charges and what answers them.

## 3. Proposals

### 3.1 P12: a history is an ordinary query

**What the builder hit.** The builder declared `history` `held:` to keep
retained history after removal. A held query is device-only: the server
refuses it (`E_QUERY_HELD`), and the local client never asks the server
(`local-query.ts`: `held` blocks the external answer). The builder's
`history` also read `reactions` (`online only`, so always unknown on a
device), `members` and `runs` through `receipt`, `profiles` and quoted
messages, and `require`d current membership (`schema.q:228–240`,
`319–324`). No change to `held` makes that one body right in all three
places the builder needed it.

**What already works.** For a bare page of one conversation, an *ordinary*
device-capable query already does what the builder wanted from `held`:

- The local client answers it on the device, on wasm and native devices
  alike (`call.rs::query`, `Device::query_observation`).
- A `Left` group is not unknown, so its retained rows stay local, online and
  offline (`wantsServer` is `unknown && !retained`).
- Any other unknown answer is replaced by the server's whole result, behind
  the prediction fence (`local-query.ts:207`). That covers missing coverage,
  presence, any unsynced read, and a `Rejoined` range, whose old images are
  not marked retained. A membership-synced page is never merged with the
  server's. The two exceptions lie outside this history:
  - LLP 3000.001's proved component record, which keeps a retained field
    beside server fields;
  - LLP 3000.014's retained `read through` rows, which `keepRetainedRows`
    appends to the server's page (`local-query.ts:219`).
- `dev` and `serve` answer it for the online client and the HTTP suite
  under current authorization.

What breaks this in the builder's program is the body, not the routing:

- a `require` of current membership refuses once the member row is gone;
- a parent without `retain delivered-history` disappears (P15);
- an online-only decoration (`reactions`) or an unsynced nested read keeps
  the device answer unknown. The whole query then takes the server's
  answer, and for a departed member that is a refusal or an empty page
  (`local-query.ts:207`).

**Change.**

- **The guide.** The app, sync and receipts cards show the thread as a bare
  page: `messages where .conversation = c last N by` the horizon's index,
  ordinary, not `held`, with no membership `require`. Receipts, profiles,
  quotes and reactions are their own queries, rendered beside it, so a
  decoration that loads or refuses never takes the page with it. The cards
  already say "put server-needing decorations in their own query"; they now
  show it for a thread, and say that `held` is only for a read the server
  cannot answer, such as a word search over every chat.
- **One note.** `N_HELD_UNKNOWN` is a conservative may-read check. It fires
  when a held query's lowered read sites include a table or view that no
  device holds: one with no `sync`, whatever the reason. The walk covers
  expanded helpers and shapes, nested reads, point reads and `exists`. It
  names that site: "this query may read data unavailable on a device; when
  that read is needed, `held` prevents server fallback". The rewrite is to
  move the read to its own query, or drop `held`. It does not fire for a
  horizon or a word index, and fires on none of the guide's own held
  examples.
- **Nothing else changes.** `held` stays device-only, and `E_QUERY_HELD`
  stays.

**Acceptance tests,** on the builder's program with `history` and
`historyHeld` replaced by the guide's ordinary bare `history(conversation)`
and separate decoration queries:

- on the local client, a DM another member sends appears before this device
  has acquired the conversation, through the ordinary fallback;
- the HTTP acceptance suite calls `history` through `createClient({ url })`.
  Its assertions and the app's rendering move with the decorations: `m3-a10`
  asserts `quoteRow` on `history` (`scripts/acceptance.mjs:372–373`), which
  now comes from its own query. The other history assertions stand;
- a removed member's `history` answers retained rows on the local client,
  offline and online, with no refusal;
- a queued send that does not predict is listed by `pendingWrites` (LLP
  3000.019 §3.3 part 4) while offline;
- `searchHeld` stays held; its note does not fire, since a word search reads
  no online-only table.

**Implementation (2026-09-27, lane GN).** The app, sync and receipts cards
now use ordinary bare history and separate decorations. `N_HELD_UNKNOWN`
walks lowered read sites, including helpers, shapes, nested points and
`exists`, and names unsynced sources without changing dispatch. The held
word search's generated empty-needle branch no longer gets history-order
advice; ordinary mismatched pages still do. The search card now uses a
horizon, removing its historical note exception from the guide test.
`held_unknown.rs` checks the note and the note-free comparative messaging
excerpt (`tests/history/comparative.q`). `ordinary-history.test.mjs`
runs cold-DM fallback, HTTP history and separate quote/receipt/profile/reaction
reads, retained history and nonpredicting queued sends on wasm and process
devices. The excerpt preserves the builder's messaging rules and writes;
its horizon uses the same named unique index as history, progress uses the
current descending interval recipe, and reactions expose a cursor.

### 3.2 P13: delivery the SDK reports (P7, revision 3)

Revisions 0–2 of P7 were reviewed NOT READY. Both families recommended
keeping the receipts card's data model and moving only the reporter into the
SDK. Revision 3, its own RFC, must meet these requirements.

- **A clause, not a proof.** The clause on the card's `mutation delivered(
  conversation: conversations, from: int, through: int)` binds, by name:
  - the mutation, its group argument and its `from`/`through` pair;
  - the tracked table (`messages`) and its group and position columns
    (`.conversation`, `.ordinal`);
  - the confirmation reader: the member row (`members`, keyed by group and
    principal), its prefix as `max(.deliveredOrdinal, .joinedOrdinal)` (the
    join floor keeps messages from before the join unacknowledged), and the
    runs table, selected by `runs.conversation` and `runs.principal` matched
    to the member row's own group and principal, with endpoints
    `runs.fromOrdinal` and `runs.throughOrdinal`. The card's runs name their
    member by those two fields; there is no member-reference column.

  Revision 3 chooses the syntax. The compiler checks every name and type,
  and requires no `sequence by`.
- **Position identity.** The group and position columns are immutable and
  unique within the group. The compiler checks both; the card's unique key
  and immutable fields meet them. That a deleted position is never issued
  again is a documented contract of the application's allocator, which the
  card meets because it never deletes. No analysis proves it.
- **What a run claims.** A run `[a, b]` claims every ordinal from `a` through
  `b`, as the card's prefix and stored runs do. So the reporter sends `[a,
  b]` only when every integer in it is a row it holds.
- **What a device holds.** It holds published rows whose coverage state is
  `Held` and which are not `pending`; expired rows are absent. That excludes
  staged snapshot pages, `Left` groups, pre-rejoin images in a `Rejoined`
  group, and rows dropped below a horizon floor. The reporter collects when
  rows are published, when an answer is accepted, and on reconnect. It also
  scans that local read at flush, as recovery. It reports positions that the
  confirmed prefix and runs do not already cover. A row that expires, is
  deleted or is replaced before collection stays `sent`, as the card accepts
  today.
- **Confirmation is the member row, authoritatively.** A successful call is
  not coverage: `delivered` returns `null`, and the confirmation is a later
  read. Only an authoritative confirmation retires debt: a server-confirmed
  member row and runs, for the current member row. A predicted, retained or
  unknown member row confirms nothing, and a locally predicted
  acknowledgement never confirms itself. Incomplete confirmation never
  establishes saturation or an unchanged coverage set. The reporter merges
  a fitting subset, and retries a refused remainder when the confirmed
  prefix *or* runs change.
  After a confirmed saturation no-op, a new attempt takes a new write id,
  because replaying the old id returns its recorded outcome. More than 64
  permanent holes stay unrecorded, as the card says today.
- **The manifest.** Every successful `/q/` answer of a program with the
  clause carries a manifest of the tracked rows it delivered, nested images
  included, deduplicated. A tracked row qualifies when the answer carries at
  least one of its stored fields in an image stamped with the row's source
  identity: the row itself, a wildcard, or a field-only shape such as
  `{text: .text}`. It does not qualify through an empty shape, a shape whose
  every field is replaced, an extracted scalar, a new object that copies
  `.ordinal`, a count, or a filter. Rows denied, loading or replaced by an
  overflow are absent. Group and position come from the engine row, not the
  projected JSON. Building the manifest is metered as provenance is:
  traversal, deduplication and allocation are charged before they happen,
  and its bytes count as output. Both clients, including the local client's
  fallback answers, enqueue only from a manifest on a response accepted
  under the current credential. Watches' refreshes post `/q/`, so they carry
  it too.
- **Transport.** The queue calls the mutation directly, with backoff, apart
  from the ordered outbox and never through `client.mutate`. Its size,
  concurrency and retries are bounded. It is bound to the viewer, the store
  incarnation (`device:store_id`) and the member row's id. On rejoin the
  member row is a new row, so a late callback for a previous id is dropped. The local client
  flushes on its suspend callback, on published sync, on accepted answers
  and on reconnect. The online client's queue is memory: it flushes before
  `signOut` aborts, and rows lost with the process stay `sent`. Sign-out
  keeps the device store, so the next session for that viewer derives again.
- **The card** keeps `runs`, `delivered`, `progress` and `seen`. Its hook
  stops reporting delivery; `seen` and its retry debt stay.

### 3.3 P14: a Linux binary on npm

- **The binary** is `x86_64-unknown-linux-musl`, statically linked, with
  `sqlite.c` built by the musl C compiler and `publish.mjs`'s
  `LIBSQLITE3_FLAGS` unchanged. It links bundled SQLite, `wasmi` and
  `argon2`; no OpenSSL, no PostgreSQL. An ELF check records that it has no
  interpreter and no shared-library dependencies. The harness's 0.4.3 glibc
  build needs `GLIBC_2.39` and does not start on Ubuntu 22.04 or Debian 12.
- **The package** is `snapback4-linux-x64`, with `os` and `cpu` set, as an
  optional dependency of `snapback4` at the same version. `resolveBinary`
  already selects `snapback4-${platform}-${arch}` and honors
  `SNAPBACK4_BIN`. Its unsupported-platform error, which today names only
  `darwin-arm64` and suggests a build, names `darwin-arm64` and `linux-x64`
  once that package ships. Its `target/` search finds nothing in a clean
  container, so the proof runs outside any checkout. `linux-arm64` ships only once an arm64 host qualifies it.
- **Qualify on each platform; publish by digest.** The order is:
  1. The publisher builds the device wasm from the release source
     (`scripts/build-wasm.sh`), because the package build only copies the
     generated wasm. It then builds the common client with today's clean
     build (`publish.mjs` removes and rebuilds `dist`), and packs it once, after its `optionalDependencies` name both platform
     packages at the version. It records the tarball's sha512 SRI and
     inspects the packed manifest for exactly those names and versions.
  2. The Linux host builds the platform tarball and runs the suite at the
     release commit. It then runs the consumer proof in clean Ubuntu 22.04
     and Alpine containers, with a pinned Node and `SNAPBACK4_BIN` unset.
     The proof installs that client tarball and the platform tarball, then
     runs `npx snapback4 --version`, `init`, `check`, `dev` and a client
     round trip. Containers establish userspace compatibility, not a kernel
     baseline.
  3. The Linux host writes a receipt: source, target, toolchain, flags,
     suite result, proof result, the ELF check (no interpreter, no `NEEDED`
     entries), the platform tarball's sha512 SRI, the binary's sha256, and
     the client SRI it proved with. It does not sign,
     pack the client or call `verifyDeveloperId`. It performs no
     authenticated registry write, and exits if `NPM_TOKEN` or
     `NODE_AUTH_TOKEN` is set.
  4. On the Mac, the publisher builds and signs the darwin tarball, runs the
     suite, and runs the installed-binary signature and hash check and the
     consumer proof against the same client SRI.
  5. The publisher accepts the Linux tarball only when its SRI matches the
     receipt, and only when the receipt proved the same client SRI. It never
     rebuilds, repacks or executes it, and requires no Developer ID for it.
  6. The publication receipt lists one artifact per platform plus the client.
     Resume re-runs only the darwin check. It re-reads the Linux receipt,
     verifies every artifact's SRI and registry integrity, and never executes
     the Linux binary. Platform tarballs publish first, then the client.

  Only artifacts and receipts move between hosts; credentials stay where
  they are. `scripts/publish.mjs` changes accordingly: its one-platform
  stage, its global signing fields and its per-stage client pack all become
  per-artifact.

**Implementation (2026-09-27, lane LX).** `publish.mjs --prepare-client`
builds wasm and a clean client once; cross-host preparation names both
platform packages at the release version. A new run without a Linux receipt
packs a Darwin-only client from a private package copy. Prepared clients and
resumed stages must name exactly their staged platforms; an existing
two-platform preparation is refused for a Darwin-only run. Format-3
publication stages hold
per-platform qualification, preserve format-2 Darwin resumes, and import
Linux bytes with `--linux-receipt` and `--linux-tarball`. Resume rereads the
copied receipt and checks every digest, requalifies Darwin only, then
converges platform packages before the client. After proof, upload copies
all artifacts into a private snapshot and verifies every copy against the

### 3.4 P15: a removed member keeps the screen

`retain delivered-history` on a membership-synced parent already keeps its
row. `crates/snapback4-device/tests/retained_history.rs` declares it on
`conversations`. The screen unmounts for other reasons: the cards do not
retain the parent, and their thread query `require`s membership. This is a
guide gap:

- the receipts and app cards put `retain delivered-history` on
  `conversations`, and on `messages` where the receipts card lacks it;
- they show a parent-only screen query that pins the conversation with no
  membership `require`, beside P12's bare history. They say that the inbox
  query, which reads memberships, drops the row when the member row is
  deleted;
- a test runs those two guide queries after leave, remount and reopen,
  offline and online, on the local client. An online-only client cannot
  recover a departed member's retained row; retention grants no server
  authority.

**Implementation (2026-09-27, lane GN).** Both cards retain the conversation
and its messages and expose a parent-only `conversationScreen` beside bare
history, with no membership `require`. The local-client acceptance test
extracts those exact card programs and checks leave, watch remount, and device
reopen offline and online on wasm and process hosts. Their inboxes drop the
deleted membership; server reads still return no departed-member data. The
comparative excerpt separately tests removal by an administrator. It preserves
the original `retain delivered-history` on members, so the inbox-drop assertion
belongs to the guide programs, whose memberships are until-revoked.

### 3.5 P16: the first-account path says what builders trip on

The README's first-account path adds these. Explicit write ids must be in the
accepted form: omit the id normally, or `mintId()` once for an intent you
keep. It shows P12's ordinary history, and P15's `retain delivered-history`
on the conversation and its messages. It shows `held` only on the all-chat
word search. It links the receipts card. It also
distinguishes product limits (`cap`) from engine-chosen bounds, and names the
Following view/query name collision the scorer cited under setup.

**Implementation (2026-09-27, lane GN).** The README's first-account path
now teaches accepted write IDs and one `mintId()` per kept intent, ordinary
history, retained parent/messages, held all-chat search, separate decorations,
the linked receipts card, product caps versus engine bounds, and the Following
view/query name collision. Duplicate notes/jobs and feed examples give way to
their existing tested cards so the README stays within its unchanged 300-line
budget. Every README Quarry block compiles without a diagnostic or note.

## 6. Charges this RFC does not take

- **Optimistic bubbles offline** (`offline_sync`; `essay.md:58–61`,
  `run-log.md:33–34`). A `sendText` that does not predict leaves no row on a
  server `history` page. P12 does not change that. 0.4.4's `pendingWrites`
  (LLP 3000.019 §3.3 part 4) is the platform's answer: the queued write is
  visible without a second queue. The acceptance rerun checks the builder's
  program renders its queued sends from `pendingWrites`.
- **`dmEdges cap 200`** (overall, `scale_and_limits`). The builder wrote that
  cap and raised it to 2000 at scale. There is no platform default. P16's
  caps paragraph is the only change.
- The final report's other candid gaps are environment or agent attributed.
