## Summary

Establish that the implemented pieces compose reliably through the published
clients, their real persistence boundaries and the supported operating tools.
Then test whether the product remains ergonomic in an application whose data
and integration requirements differ from Clique's.

Passing the current suite, repairing a set of findings and completing one
application are valuable evidence. None individually establishes every
client lifecycle, sustained operation or general backend suitability. This
child specifies the next evidence without commissioning an unlimited test
matrix or treating already repaired defects as open.

## 1. Current evidence and its boundary

The [review correction record](./reviews/3000-review-corrections-20260913.md)
and [security remediation record](./reviews/3000-security-remediation-20260913.md)
document substantial implemented fixes and qualification. The earlier research
children retain unresolved architectural questions beside their implementation
follow-ups. References to the retired TypeScript interpreter in those histories
are not descriptions of the current single-interpreter device.

The deterministic simulator runs the server core under faults. Its
[Replica host](../snapback4/crates/snapback4-sim/src/replica.rs) also has its own
replica lifecycle and chat-specific prediction behavior. It therefore does
not, by itself, execute every behavior in the published TypeScript client,
React hooks, browser opener and native boundary. Existing actual-client tests
and browser/native witnesses cover parts of that gap; their evidence should
be identified precisely rather than conflated with model coverage.

The [three-builder Clique record](../benchmarks/runs/2026-09-13-snapback4-clique-0004/README.md)
is still incomplete at this assessment. Its successful builder, incomplete
builder and pending independent grades are retained separately. A reported
toolchain failure is not automatically a Snapback defect; an authoring
limitation that follows the documentation can still be product friction.

## 2. Reuse the model and exercise the shipped behavior

Keep deterministic simulation as the primary mechanism for exploring ordering
and faults. Prefer sharing production device/lifecycle code at a controlled
clock, transport and persistence boundary over teaching another model to
imitate each repaired bug.

Where the JavaScript lifecycle cannot be hosted directly in the Rust simulator,
replay a compact deterministic event trace through the actual client using its
existing injectable boundaries. Assert observable invariants independently of
the code under test. A trace passed by the model and rejected by the shipped
client is useful disagreement to investigate, not permission to count both as
the same proof. No embedded JS engine is required by this proposal.

Use real browser and native witnesses for the semantics those adapters cannot
simulate: IndexedDB commit/abort and quota, web locks and separate realms,
native module lifetime, application termination and reopening. State whether
a witness uses a simulator or physical device and what it actually interrupts.

## 3. A small set of composed journeys

| Journey | Required observation |
| --- | --- |
| Queue offline, terminate, reopen, reconnect | Durable admission survives within the stated persistence boundary; submission identity/order survive and each write reaches its authoritative outcome. |
| Commit, lose acknowledgement, receive stream, retry | No duplicate authoritative application, no second optimistic application of an already observed write, and a consistent terminal result. |
| Queue, revoke or expire membership, reconnect | Server authority decides the write; device rows obey the declared retention policy once the relevant revocation is applied. |
| Rotate credentials while reads and writes are delayed | Obsolete replies neither end the new session incorrectly nor settle its durable writes or strand observations. |
| Change schema/rule with old client and queued work | Activation is atomic; the old operation is accepted compatibly or refused with a typed explanation; supported recovery remains available. |
| Fail persistence during prediction, snapshot or runtime installation | No acknowledged durable admission is fabricated; confirmed state and the prior usable generation remain recoverable as promised. |

Each journey exercises related properties together. It does not require a
Cartesian product of all applications, transports and faults at every commit.
Begin with the boundaries changed by the other children and expand only when
a failure or unsupported claim warrants it.

Revocation is not retroactive erasure of bytes an offline device already
received. `delivered-history` has an intentional leave policy, and a device
cannot learn a remote revocation before communication. Bind assertions to the
declared policy and applied stream position, not an impossible instant global
erasure promise. One-view asset rules also do not prevent a viewer from
recording content outside the platform.

## 4. Operational completeness on the supported target

The current release boundary already supports transactional activation,
classification and rollback; [LLP 3000.000's implementation follow-up](./3000.000-atomic-schema-and-release-activation.research.md#implementation-follow-up)
states both the delivered behavior and the remaining long-rebuild/power-loss
limits. Build operational evidence on those tools instead of proposing a new
hosting platform or admin console.

Demonstrate one supported deploy, restart, schema change and rollback with
real clients attached. Include a queued old-generation write and a refused
candidate release. Record interruption and recovery behavior during a changed
maintain rebuild; a writer transaction that takes time is not a zero-downtime
migration guarantee.

Define and exercise a backup/restore procedure whose consistency boundary
includes schema/program identity, database state, necessary asset files,
deduplication and queued jobs/effects. State its recovery point and what an
attached device must do after restoring an older snapshot. Restoring a backup
can also restore old deduplication state: replaying an external effect or a
previously acknowledged write requires an explicit policy, not an assumed
exactly-once guarantee. Missing procedure or semantics is a named gap; this
draft does not invent an implemented backup command.

Exercise disk or quota exhaustion, interrupted asset operations and backlog
recovery on disposable state. Distinguish process termination from physical
power loss. State the actual SQLite and host durability configuration. Existing
`doctor`, `data`, `why` and logs should explain how the operator proceeds;
additional permanent observability remains governed by the scope fence.

## 5. Complete application evidence

Finish the already commissioned independent grading and fresh M7 work before
turning the current run into a holistic success claim. Preserve the 119-ID
result and comparable 101-ID subtotal, skipped coverage and capability failures
as the instrument requires. A shortened or source-assisted repair run has its
own scope; it does not replace a cold published-package build.

After the product changes are published, repeat the affected complete journeys
with fresh builders under the existing protocol. Record both time to a working
artifact and time to required verified behavior. Retain total correction loops
and categorize causes without assuming every self-attributed agent mistake is
irrelevant to ergonomics. Record custom transport, stores, duplicate queries,
metadata joins and runtime-caching code that the app needed to add.

Three model families provide useful coverage of different builder behavior,
but one run per family remains calibration. Improvement requires consistent
results and honest remaining costs; a selected best run is insufficient.

## 6. Test a different application demand

[Interview](./3000.004-feeds-and-the-interview-reference-app.rfc.md#8-interview-as-the-second-reference-application)
is the existing candidate for a real second application. It adds a product
owner, native integration, external model workers and identity-adapter needs.
Its feed remains related to Clique's, so name the additional generality claim
carefully.

Recommend combining that application with a bounded server-heavy workflow,
such as its invitation/moderation administration or an import/reporting task.
Keep detailed source rows online, expose only the appropriate device facts,
and require ordinary integrations through the supported worker and service
boundaries. If that workflow does not fit Interview's product, select a small
field-work or administrative application with the author before implementation.

The outcome is not necessarily that Quarry fits everything. Record whether
ordinary business logic needs excessive work tables, native code for trivial
operations, a parallel API or inaccessible diagnostic knowledge. A clearly
stated scope limit is preferable to changing the application requirement to
make the platform appear general.

## 7. Acceptance and remaining decisions

1. The six composed journeys have evidence from the actual affected client and
   device paths, with deterministic reproduction where possible and explicit
   real-host limits. No model-only pass is presented as shipped-client coverage.
2. Deployment/evolution and a defined backup/restore boundary are exercised on
   the supported target with attached clients. Any interruption, loss or
   replay limits are stated, and recovery uses supported procedures.
3. The complete Clique grading and day-two record is available, including
   failures and unrun assertions. A follow-up published pin demonstrates the
   claimed improvements without hidden application repairs or source access.
4. A second application and the chosen server-heavy workflow preserve their
   product requirements, expose the measured friction and identify the actual
   scope in which Snapback 4 is excellent.
5. Longer device and operating experiments run outside the existing fast
   landing loop; the evidence adds no new exact-HEAD battery requirement.

The author still decides the second application commission, operational
recovery targets and the final promotion claim. Implementation custody and
scope exclusions remain those of LLP 3000. This document is an evidence and
product proposal, not a claim that the experiments have run or authority to
perform destructive operations against a live deployment.
