## Summary

Establish dependable composition through the actual client and persistence
boundaries changed by this program. Preserve broader usefulness as a question
until a concrete second application is commissioned. This is a bounded
completion increment, not a new test matrix or hosting platform.

## 1. Current evidence and its boundary

Current client-lifecycle, client-seams, retained-history and release-activation
tests already exercise substantial shipped behavior. The
[IndexedDB witness](../snapback4/witness/idb.mjs) covers a successful offline
reload. The Rust simulator remains the primary ordering/fault model; its
chat-specific replica does not by itself execute the TypeScript lifecycle or
host persistence.

The [0.2.12 Astra grade](../benchmarks/runs/2026-09-14-snapback4-clique-astra-0.2.12/README.md)
is complete for that artifact: 101/119 passed, 18 not run. This does not finish
missing native or fresh M7 evidence, or regrade every older builder cell.
Historical repair records remain regression evidence, not reopened defect lists.

## 2. Reuse the model and exercise the shipped behavior

Use existing injectable clock, transport and persistence boundaries to
reproduce a fault through the actual client. Prefer a small deterministic
sequence to another imitation of repaired behavior. Use real IndexedDB/native
witnesses for semantics an in-memory adapter cannot establish. No embedded JS
engine or new cross-product harness is required.

## 3. A small set of composed journeys

| Journey | Required observation | This increment |
| --- | --- | --- |
| Queue, close/reopen, reconnect | Durable identity/order and authoritative settlement survive | Exercise alongside acquisition/persistence repairs |
| Commit, lose acknowledgement, stream, retry | One application and truthful execution-only replay | Replay contract regression |
| Queue, revoke/expire, reconnect | Authority decides; applied retention policy holds | Preserve existing regressions |
| Rotate credentials with delayed work | Old replies cannot corrupt the new session | Preserve existing lifecycle tests beside new outcomes |
| Change generation with queued work | Typed compatible/refused operation and truthful readiness | Acquisition-reset regression; stopped release exercise |
| Fail persistence or runtime installation | No falsely durable admission; old committed state recoverable | Actual wasm and IndexedDB fault/reopen witness |

An applied revocation follows declared retention. An offline device cannot
learn a remote revocation instantly, and delivered history is intentional.
Never assert impossible retroactive erasure or physical-device behavior from
an in-memory test.

## 4. Operational completeness on the supported target

Deployment/rollback currently require the serving process to stop; the
[release tests](../snapback4/packages/snapback4/test/release-activation.test.mjs)
assert that a live deployment refuses both. Clients may survive that supported
interruption; this is not zero-downtime activation.

Select one **disposable, stopped-server** recovery exercise using existing
release/store tools. A consistent backup contains the whole release identity,
database and required asset files, including authentication, deduplication and
queued job/effect state wherever stored. Stop all writers/workers before the
copy and preserve all necessary SQLite state; copying only a live main database
file is not the procedure. Verify restart, a permitted schema change, a refused
candidate and rollback without pretending rollback restores historical rows.

Restore of an older backup is a new recovery boundary. It may rewind server
watermarks, deduplication and external-effect records. Do not automatically
attach old device stores/outboxes or replay externally completed work. The
bounded exercise restores to an isolated endpoint with fresh device state and
external effect workers disconnected, states its recovery point and demonstrates
current reads and asset availability. Serving resumes built-in jobs and
schedules; the exercise parks a real job and controls its schedule boundary
so preserved work can be checked without claiming those executors are disabled. A production continuation policy for outstanding devices
and external effects remains unimplemented; no seamless restore claim or new
backup command is commissioned.

No live deployment is stopped or overwritten for this experiment. Distinguish
process interruption from physical power loss and report actual durability
configuration rather than infer it.

## 5. Complete application evidence

Retain the existing 119-ID grade, comparable subtotal, failures and unrun
assertions. New affected journeys demonstrate only what they execute.
A source-assisted regression is not a cold published-package build; a newer
single-family calibration is not a completed independent three-family cell.

Record correction costs and application workarounds honestly. Neither a selected
best run nor a changed not-run classification establishes holistic excellence.
Missing native/M7 and broad independent application evidence remain follow-ups,
not a newly invented landing battery.

## 6. Test a different application demand

Interview is a design and compiled sketch with native/worker fixtures; it is
not a completed independent reference application in this repository. Its
future concrete feature may exercise identity, external model workers and
server-heavy administration. A product brief must name requirements and
acceptance before that build is commissioned.

This program defers the second app, general reporting and SQL application
reads. Do not weaken a future app's requirement to make the platform look
general, or add a parallel API merely to satisfy an unbounded slogan.

## 7. Acceptance and remaining decisions

1. The changed replay, acquisition and persistence boundaries have actual-client
   evidence. Existing rotation/revocation coverage remains intact; real-host
   gaps are explicit.
2. One disposable stopped-release lifecycle and isolated restore exercise has
   a reproducible procedure, named recovery point and correct device/worker
   limitations. No new command or production restore promise is inferred.
3. The current app-grade scope is reconciled, and absent native/M7/second-app
   coverage is recorded separately from this increment's completion.
4. Longer experiments add no exact-HEAD battery or new blocking matrix.

The [umbrella's delegated ruling](./3000.008-holistic-product-excellence.rfc.md#8-panel-disposition-and-authorized-program)
authorizes this increment. Production recovery targets, a concrete second
application and promotion remain future decisions.

## 8. Reproduced recovery defect and procedure

A stopped full-directory copy reproduced two failures: its absolute generated
store link read post-backup rows from the original, and a dangling legacy link
refused startup. Serving now creates a relative link to the selected
deployment's own database and reconciles existing symlinks under the deployment
lock. An unexpected regular file refuses without being overwritten.

The [package procedure](../snapback4/packages/snapback4/README.md#stopped-backup-and-isolated-restore)
uses new paths and `cp -a` after all writers stop. Twelve release tests and
30 CLI tests passed on Linux. The restore test preserves actual sessions,
stable mutation deduplication, a queued effect, a parked scheduled job,
release/program identity and asset bytes, and reads through a fresh process
device while the original deployment still exists with newer rows. It also
checks widening, refused destructive activation and rollback without row
rewind. External delivery, old-device continuation and physical power loss
remain outside that evidence.
