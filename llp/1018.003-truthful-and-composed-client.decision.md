## Summary

The client tells the whole truth and makes every screen pay for it. This
decision keeps every fact the client publishes today and changes how they are
arranged. One snapshot record with orthogonal axes — value, receipt,
freshness, local overlay, refusal — replaces the seven-state view union. A
three-way `status` and at most one `reason` are *derived* from those axes by
one SDK function and never stored. Write readiness is derived the same way.
The thread's display projection moves into a certified Quarry query. The
rows that tombstone other rows are declared in the schema, carried in the
Rust schema and its hash, and read by engine and twin alike, instead of being
injected by an application callback. The witness is the chat template's
thread screen and composer on React and Expo. The shared delivery-log reducer
and tombstone callback are removed; authored send and account-recovery helpers
retain their separate mutation-custody responsibilities.

This page is short on purpose: the decision is small and the code is the
witness. It does not reopen LLP 1018.000 §4's coherence boundary or ownership
model; it fixes the shape of the snapshot that boundary publishes.

## Context

**The scores.** LLP 1018 §2 records Snapback 2 winning where the work is a
primitive and losing where it is composition: client integration 63 against
Convex's 83 in the Astra assessment, queries and live 60 against 85 across
three scorers. Muse's notes name the discovery half ("grants/outbox/drain/lease
semantics came only from probes"); Astra's name the composition half.

**The surface as it stands.** `QueryView` (`types.ts:389`) is a union of seven
sibling states: `complete`, `capped`, `partial`, `denied`, `refused`, `stale`,
`hydrating`, the first four carrying `live`, `stale`, `retained`, `caughtUp`,
`watermark`, and `predicted` facts. Those states answer three different
questions — what the certificate said, how current the answer is, what this
device added — and the union makes them compete: a stale-but-complete answer
is state `stale` and loses its receipt. Six overlapping unions describe the
same delivery on its way to a screen (`ServerQueryResult`,
`OfflineQueryResult`, `QueryResult`, `SubscriptionDelivery`, `QueryView`,
`QueryHookResult`). `OutboxStatus` enumerates seven mechanism reasons
(`ready`, `sealed`, `grant-missing`, `grant-expired`, `ids-exhausted`,
`program-missing`, `follower`), four actions, and the fence.
`OfflineClientOptions.onTombstone` (`types.ts:283`) asks the application to
tell the client which stored rows tombstone which others; `offline.ts:638`
calls it on every fresh row.

**The template is the evidence.** The shipped chat app's `App.tsx` renders
its inbox with `"data" in inbox && Array.isArray(inbox.data) ? inbox.data : []`;
the Expo thread screen has the same line. The React thread screen is 130 lines
and needs a 131-line `shared/log.ts` to turn the delivery log and the outbox
into bubbles (event-kind filtering, message-id deduplication, tombstone
hiding, pinned-id merge, chronological sort) and a 32-line
`shared/offline.ts` that maps the seven outbox reasons to sentences and
declares which delivery kinds tombstone which message. Both the React and
the Expo composer import it. Anything both platform templates must share
identically is SDK, not application, and a reducer over the log that runs
in application TypeScript is one the certificate cannot vouch for and the
twin cannot share.

**What is already commissioned, and what the lane already did.** LLP
1018.000 §4 moves query reduction into one shared entry exposed as
`client.observe`, read by React and Expo through `useSyncExternalStore`, with
one immutable snapshot owning value, completeness, freshness, predictions,
continuation, and refusal, and it says "preserve value identity with
`reduceQueryState`", so the record it publishes is the current union. §7 adds
expression-only `fn` helpers. The unlanded lane branch
(`llp-ship/20260907-1018-architecture/client`) has implemented that hook
rewrite, adds a `held` answer state meaning "data from custody, server
coverage unknown", mints local search continuations, and adds the durable
follower-forwarding outcomes of §8: readiness reasons `writer-discovery`,
`writer-capacity`, `writer-unresponsive` and a fourth `run` outcome
`{ state: "admission-unknown", recovery }`. Its templates have grown to a
279-line thread screen with two more helper modules. None of this is on
`main`. This decision is implemented on `main` first; the lane adopts the
record when it rebases, and its additions have rows in the tables below.

**Retention.** LLP 1012 §5 rule 3 reads: "a fresh log row of kind `removed` or
`expired` evicts the body it names." The rule is stated in the chat recipe's
own vocabulary, and the client learns those kinds only through the
application's callback. The spec knows something the certificate does not.

## Options

**For the view.** (a) Keep the union and document it better. Rejected: the
cost is paid per screen, not per reader. (b) Convex's shape, `T | undefined`.
Rejected: it is composed by lying — a denied query and a loading query look
the same, and the twin's prediction has nowhere to go. (c) Orthogonal axes
with a derived summary. Chosen: every fact stays, each consumer touches one
axis, the common case is the default.

**For write readiness.** (a) The application maps reasons to actions, as the
template does. (b) The SDK derives `can` once. Chosen: (b); the mapping is the
same for every application.

**For the thread projection.** (a) Keep an application reducer over delivery
events. Rejected: uncertifiable and duplicated per platform. (b) A composite
record query. Not on `main`, and LLP 1018.000 §4's composite still returns
delivery events. (c) A kind-scoped index so the certified page already
contains only live message events, leaving one null filter and one reversal
to the screen. Chosen: (c); it is expressible in today's Quarry and the twin
evaluates it.

**For tombstones.** (a) Keep the callback. (b) Infer from enum member names.
Rejected: a heuristic in the eviction path. (c) One schema declaration in the
Rust schema, hashed, certified, and read by engine, twin, and client alike.
Chosen: (c).

**For settlement of committed intents.** (a) The runtime dismisses a committed
intent when its row arrives. Rejected: LLP 1012 §7 rules that arrival retires
prediction custody and does not dismiss, and `overlay-retirement.test.ts`
pins it. (b) The hooks retire it. Rejected: their notification can precede
the row's render and unmount its pending element. (c) The screen dismisses
a committed, arrived intent after rendering its pinned row and retiring its
remaining prediction custody. Chosen: (c),
recorded in §4 below.

## Decision

### 1. The snapshot record

Hooks and `client.observe` publish one record.
Every field below exists today under some state name; none is new
information except the row identities of predicted rows, which the twin
already holds and now publishes.

```ts
type Snapshot<T> = {
  data: T | undefined;
  /** What a certified evaluation said about this value, and whose evaluation it was. */
  receipt?: {
    outcome: "complete" | "capped" | "partial" | "denied";
    source: "server" | "twin";
    seq: number; next: Cursor | null; reason?: string; rule?: string;
    sites?: readonly { site: string; reason: string }[];
  };
  /** How current it is. Transport truth, independent of the receipt. */
  freshness: { live: boolean; staleSince?: number; connection: ConnectionState };
  /** What this device added. Offline truth. */
  local: {
    predicted: readonly { table: string; id: string; intent: string }[];
    retained: boolean; caughtUp?: boolean; watermark?: Cursor | null;
  };
  refusal?: RefusalEnvelope;
  /** Derived by `summarize`, never stored. `detail` is the rule a denial named or the reason a partial gave. */
  status: "loading" | "ready" | "unavailable";
  reason?: { code: "refused" | "denied" | "partial" | "stale" | "offline" | "predicted" | "held"; message: string; detail?: string };
};
```

A partial receipt also carries the twin's `sites` (the uncovered sites and
their reasons, LLP 1012 §6), so no fact the offline runtime publishes is
dropped on the way to a screen.

`receipt.source` is the provenance axis: `server` for an owner receipt,
`twin` for the client evaluator's certified evaluation over held rows, which
also owns any locally minted continuation. A shared query's local refresh
carries that source explicitly even while its transport stays live;
connection-only reprojection never changes who evaluated the value.
An equal local reevaluation may retain the existing owner receipt when its
certified outcome, sequence, and effective value are unchanged. A different
sequence, completeness outcome, or local uncertainty still publishes; equal
data alone does not justify retaining an obsolete receipt.
The lane's `held` state maps to
`data` present with no `receipt`; that row of the table below exists so the
lane needs no new field. `data` keeps value identity across snapshots when
the value is unchanged, as `reduceQueryState` does today. `QueryView` remains
the reducer's type and `summarize`'s input for headless code that reads
`client.subscribe` events; `QueryViewState` and `QueryHookResult` leave the
public surface. `SubscriptionDelivery` and `QueryResult` remain the event and
wire types; screens never see them.

### 2. Derive, never add

`status` and `reason` are computed by one exported pure function,
`summarize(view)`, used by every hook and available to headless code. Its
table is the whole summary contract:

| Axes | `status` | `reason` |
| --- | --- | --- |
| `refusal` present | `unavailable` | `refused` (the envelope's `rewrite`, else `message`) |
| `receipt.outcome = denied` | `unavailable` | `denied` (the rule) |
| `receipt.outcome = partial` and no `data` | `unavailable` | `partial` (the receipt's reason) |
| no `data`, no `receipt`, the twin reported nothing held, and the transport is not `connected` | `unavailable` | `offline` |
| the same "nothing held" marker while `connected` (a fetch is in flight) | `loading` | none |
| `data` present with a non-denied receipt, fresh or stale or retained | `ready` | the first of `partial`, `stale`, `predicted` that applies, else none |
| `data` present with no receipt (the lane's `held`) | `ready` | `held` |
| otherwise | `loading` | none |

**`ready` means readable data.** It does not mean server confirmation, drain
completion, or a usable composite. A composite record (LLP 1018.000 §4) is
usable only when `receipt.outcome` is `complete` or `capped` and its data has
all three fields. A partial with data is `ready`; a partial without data is
`unavailable`. Both screens select fallback from the partial receipt itself,
then read the independently authorized history with count and preview
unavailable, exactly as §4 rules. Derived `status` and `reason` grant no
authority. A usable composite releases the fallback subscription.

A test enumerates the cross product of the axes and asserts the table. The
rule this encodes: **a summary is a projection of facts, never a fact.**

**Transition invariants** the shared reducer keeps, so the table above is
applied to a coherent view:

- A stale event keeps the last receipt and marks `freshness.staleSince` when
  it names no other sequence; a stale event that names another sequence
  carries held data the receipt does not describe, so the receipt is dropped
  and the data reads as `held`. A stale event never invents an outcome, and
  a kept denial keeps no data.
- A denied or refused event scrubs `data`; a reset forgets the snapshot.
- A row kept under `retain delivered-history` (LLP 1012 §5 rule 4) marks
  `local.retained` and keeps the outcome that delivered it.
- A drain may expose readable data before `caughtUp`; `caughtUp` is a fact,
  not a precondition of `ready`.

Write readiness follows the same rule. `useMutation(op)` returns
`{ run, inFlight, can, pending, last, detail }`. `run` and its outcomes are
unchanged on `main` (`committed | queued | rejected`); the lane's fourth
outcome `admission-unknown` with `recovery` is carried through `last`
untouched. `can` is derived by one function with three inputs, because the
sentences depend on all three: `readiness(status, connection, queued)`, where
`queued` is the op-scoped count the hook already computes, not the status's
partition-wide `remaining`:

| `OutboxStatus` | `can.send` | `can.action` | `can.reason.code` |
| --- | --- | --- | --- |
| ready, fence inside, `queued = 0` | true | — | — |
| ready, fence inside, `queued > 0` | true | `connect` | `pending` (connected: "waiting for the server"; else "waiting for connection") |
| ready, fence past | true | `connect` | `fence` |
| `sealed` | false | `sign-in` | `sealed` |
| `grant-missing`, `grant-expired`, `ids-exhausted`, `program-missing` | false | `connect` | that reason |
| `follower` | false | `other-tab` | `follower` |
| lane: `writer-discovery`, `writer-capacity`, `writer-unresponsive` | false | `wait` | that reason |

`connect` means the app offers `client.online()`, because reconnect alone
replays nothing (`guide/offline.md`). The sentences the template's
`sendingStatus` produces today become `can.reason.message`, the way a
refusal's `rewrite` is already the SDK's; the SDK also exports them as a map
keyed by code, and the outbox entry label (`intentLabel`) the same way. An
application that wants its own copy switches on `code`. `detail` carries the
full `OutboxStatus` and the last retryable transport refusal; `ready`,
`status`, and `transport` are folded into `can` and `detail`. `useOutbox()`
keeps `entries` and `dismiss` and exposes the same `can` and `detail`.

### 3. Tombstones are declared, certified, and shared

The table whose rows are the log declares which of its rows tombstone which
target, on the table itself, with the predicate spelling row schedules
already use:

```q
table deliveries:
  …
  tombstones messages[.messageId] if .kind = 'removed' or .kind = 'expired'
```

The target column must be a column of this table whose type is a reference
to the target table; an optional reference that is null tombstones nothing.
The predicate reuses the rule-expression parser and is restricted after
parsing to `.column` reads of this table's `enum`, `bool`, and `text` columns,
literals, `=`, `!=`, `and`, `or`, `not`, and parentheses; a null column
compares false. `check` refuses anything else at the authored site. Several
lines per table union.

**Custody.** The declaration is a field of the Rust `Table` in `schema.rs`,
validated with the schema, omitted from serialization when empty so every
existing schema's canonical bytes and `Schema::hash()` are unchanged, and
included when present, so a schema that declares it has a new hash and new
certificate and resume-validator identities bound to it (LLP 1012 §8). The
evaluator's hasher knows the field and produces the same canonical form; a
golden proves parity. The owner serves it in the program from
`GET /api/program`, and LLP 1012 §5 rule 3 is amended to fire on rows the
held program declares. `OfflineClientOptions.onTombstone` is removed, with
every consumer: `src/test.ts` and `types/test.d.ts`, the provider's
`throughRef` wrapper, the chat template's React entry and Expo `App.tsx` and
`Witness.tsx`, the generic React scaffold's `main.tsx`, the browser witness's
generated entry, and `tests/offline-store.test.ts`. `retain
delivered-history` and rules 1, 2, and 4 are unchanged. What is unchanged is
query execution and the existing protocol algorithms; certificate
identities are not.

### 4. Pending rows: attribution, settlement, and failure

**Historical implementation:** §§4–6 record Claude's landed pass. The current
follow-on in §§8–10 replaces their screen-owned joins and automatic dismissal.
The record/receipt and mutation-readiness contracts in §§1–3 remain unchanged.

A thread shows only rows the certificate or the twin vouches for, plus the
intents that could not be predicted.

- **Attribution.** A queued write the twin predicted appears in `data` under
  its pinned ids and is listed in `local.predicted` by table, row id, and
  intent. The pinned first id is the id the server row will carry, so the
  row's key is the same before and after settlement and the mounted element
  does not remount; the pending presentation is "Sending…" with no time.
- **Unpredicted intents.** A queued write the twin did not predict, for any
  cause — no held program, the fence past, uncovered or refused local
  evaluation — and every rejected or expired intent are outbox entries. The
  screen selects the ones that belong to it by the intent's own arguments
  (`entry.args.conversationId` for a post, `entry.args.messageId` against the
  rows it shows for an edit or an unsend); that attribution is application
  presentation and stays in the screen. Their label is the SDK's
  `intentLabel(entry)`; rejected and expired entries stay until dismissed.
- **Settlement.** The runtime does not dismiss on arrival (LLP 1012 §7). It
  records `arrived` on a committed intent when a delivered row carries one of
  its pinned ids or its predicted overlay is confirmed by arrival, judged
  after the swap's outbox puts so a settlement that lands with its own tail
  counts. Neither the runtime nor the hooks dismiss on that fact, because the
  outbox notification precedes the subscription delivery that puts the row on
  screen: a hook that retired the entry then would unmount the bubble one
  render before the row mounts. The screen that renders the row retires the
  intent — one effect: a committed, arrived intent whose pinned id is among
  the rendered rows and whose `predicted` custody has cleared is dismissed.
  Arrival of an ordinary message can precede its maintained count; automatic
  dismissal must not delete that remaining overlay. The existing `predicted`
  fact clears after full confirmation or the bounded retirement rule, and
  bounded retirement does not claim confirmation. Explicit dismissal remains
  available for terminal entries. Thus a write that was never predicted keeps
  its "Sent" label until its row is on screen and the element never remounts.
  A call that settles its own write answers from the drain's recorded terminal
  outcome when something retired the entry first; that record is held only
  for calls that are waiting on their own intent. This amends LLP 1012 §7's
  presentation guidance, not its runtime rule.

### 5. The certified thread projection

The delivery log returns events. A thread wants live messages, oldest first.
Today an application reducer filters event kinds, deduplicates message ids,
hides tombstoned bodies, and sorts. The certified replacement is one index
and one query in the chat recipe:

```q
  by byRecipientConversationKindAt: recipient, conversationId, kind, at, id
```

with the thread query reading
`deliveries[viewer, conversationId, 'message'] after c last 50 by byRecipientConversationKindAt`.
The page then holds exactly one event per live message; a deleted or evicted
body is a null nested `message`, on the server because the row is gone and
on the device because rule 3 evicted it. The screen keeps one null filter
and one reversal (the page is newest-first, a thread reads oldest-first),
and an edit changes the message row in place, so no edit event is needed
for display. The twin evaluates the same query over the same held log. The
inbox's per-conversation grouping is application presentation and stays in
the inbox screen of each platform; it is not a shared module.

### 6. The witness

The initial upstream chat template's React `Thread.tsx` landed at 78 lines
(the original 60-line bound was missed), reading the kind-scoped `thread`
page, with `shared/log.ts` and `shared/offline.ts` deleted. Integration with
LLP 1018.000 keeps those deletions and adds its composite/history boundary
and account-scoped forwarding recovery. The resulting thread is larger;
the shared recovery helper remains the custody owner defined in LLP 1018.000
§8, rather than a delivery-log reducer. The Expo thread uses the same query
and settlement conditions with native primitives. Its composite's partial
receipt, even without data, enables an independently observed history page;
denial, refusal and reset do not. Both platform screens release that fallback
subscription once the composite is usable, and retain no count or preview from
a partial composite. The inbox
and search reading `view.data` directly; both composers gating on `can.send`
and showing `can.reason.message` and the `connect` action. The existing
browser and Expo witnesses pass with assertions changed only where they name
attributes or query shapes, not behavior — including the step that a message
revoked while offline is gone after the resume, which now depends on the
declaration rather than the deleted callback, and the pending bubble's
"Sending…" with no time under a stable key. The complete local runtime is
measured after the change, including the tombstone interpreter, and reported
against the current 82,500 gzip ceiling of LLP 1018.000 §2. The upstream lane's
80,524-byte result is historical; the merged runtime's source-bound
measurements and failures are recorded in LLP 1018.000 §10. Removing
TypeScript unions saves no runtime bytes. Expo parity is claimed for the shared hooks and the Node-level
Expo tests; native rendered identity is a simulator-witness claim and is
made only when that witness runs.

## Consequences

- Breaking for `snapback2/react` and `snapback2/react-native` hook return
  types, for `OfflineClientOptions`, and for `OfflineFacts.predicted`.
  Snapback 2 is pre-1.0 with no compatibility lanes (`rules/NOT-DOING.md`),
  and the templates and witnesses are the only known consumers.
- A schema that declares tombstones has a new schema hash, so its
  certificates and resume-validator identities change; existing schemas do
  not.
- The guide's first pages teach `data`, `status`, `reason`, and `can`. Grants,
  fences, drains, leases, and partitions stay real and reachable under
  `receipt`, `local`, and `detail`, and move to a "how it works" section of the
  offline page. The `live-query` page that will carry this contract still
  opens with a TypeScript `query({...})` example from the authoring surface
  deleted on 2026-09-02; that example is replaced in the same landing.
- Nothing in LLP 1012 §5–§8's protocol algorithms changes except the input to
  rule 3 and the presentation guidance of §7. Receipts, the wire, resume, and
  the twin's evaluation are untouched. The composite query's coherence and
  its lack of a page continuation remain §4's.
- The six delivery fan-out loops in the chat recipe remain. They need a
  statement-level helper or a declared fan-out, which LLP 1018.000 §7
  explicitly defers; this page does not solve them in the client.

### 7. One list, with the query's truth preserved

The proposed screen reads:

```tsx
const thread = useQuery(api.deliveries.thread,
  { conversationId, c: null }, { items: threadItems });

return <>
  {thread.reason && <p role="status">{thread.reason.message}</p>}
  {thread.items.map(item => <Message
    key={item.key}
    message={item.data}
    draft={item.draft}
    pending={item.pending}
    predicted={item.predicted}
  />)}
</>;
```

React and Expo use the existing `useQuery`; headless code uses
`client.observe(api.deliveries.thread, args, { items: threadItems })`.
The optional projection runs inside that query entry before its immutable
publication. There is no `useCollection`, `observeCollection`, or separate
collection subscription lifecycle. The implementation adds this option to
both existing APIs. A pure internal `attachItems(spec, args, data, inputs)` performs the
join; calling a pure function over two independently changing hook results
would not establish this publication contract.

The result retains the underlying query's `data`, `status`, `reason`,
`receipt`, `freshness`, `local` and `refusal`, and adds `items`. `data` is still
the named query's result; the receipt describes that result. `items` is its
presentation with attributed intents, never a second certified result. A
pending-only item cannot turn an unavailable query into `ready`, count as a
server row, or grant completeness to a composite. An empty `items` list does
not mean the query is loaded or exhausted.

An item has one stable `key`, `data` when there is a readable selected row,
`draft` when there is a separately labeled submitted create payload,
`predicted` for a contributing local overlay, and `pending`, an ordered list
of its unresolved actions. Each action carries its intent ID, operation,
state, SDK label, optional refusal, and whether explicit dismissal is
available. The same action can be displayed by several observations;
dismissal addresses its durable intent, not a row or component instance.

Never construct a fake message to fill a row type. A submitted body is a
draft; it has no server timestamp, author assertion, media custody or read
permission. `Message` renders the readable row or the labeled draft and the
attached actions. It does not search another collection. The outer keyed
element persists when a draft becomes a predicted or server row. A predicted
create shows no timestamp; an existing message can keep its authoritative
timestamp while an edit is pending.

### 9. Attribute and publish at the shared entry

The client's existing account session owns one current outbox projection and
indexes its associations from the raw durable entries. Collection joins use
those entries, not an already filtered global pending list: an action that
is complete for another presentation may still lack this view's target
evidence. The existing query entry owns the optional item projections.
It retains at most one derived publication per attached spec identity, with
one shared underlying query/value/transport. Different specs add pure
projection work, not subscriptions to a second source or new query lifecycles.
They leave when their last attachment leaves; an inactive spec keeps nothing
alive. The ordinary query's first/last-subscriber lifecycle stays LLP
1018.000 §4's. This is derived output memoization, not another authoritative
result cache or durable queue.

**Input-frame contract.** The architecture lane already has `StoreRevision`
(`incarnation`, `revision`), atomic `StoreChange` batches, `TwinStore.sync`,
and shared-entry epoch fencing. Reuse those. A private frame captures the
query value, exact selected-row evidence, effective overlay attribution, and
raw outbox entries. Local evaluation captures these synchronously from one
synchronized twin image. Actual immutable `RowImage` objects survive evaluator
aliases and nested point reads; a copied object with the same ID cannot borrow
their provenance. A private WeakMap binds the frame to its event. Publication
clones the public value and rebinds witnesses to the cloned row objects;
equality reuse rebinds them to the equal objects the reducer preserves. Immutable
captured ledger records are shared, not cloned afresh for every query. The twin
reuses its ordered ledger until outbox records change. A spec/ledger index maps
targets and intent IDs once and orders creates by their unresolved sequence cut.
Warm pages inspect their targets and unresolved creates, not every old send.
The outbox observer compares history once per client update, independently of
its distinct operation-status slots.

For a direct server delivery, only its own returned `$row` references inherit
its sequence. A later pool read cannot upgrade an older returned body. The
admitted delivery is joined with the current ledger under the existing authority
and entry fences. If a local evaluator is unavailable, or a one-shot query keeps
its original value, newer ledger entries may attach work to that value while its
original row witnesses stay fixed. This refines the first draft's unnecessarily
strict same-revision requirement: the value and its proof are inseparable;
ledger progress may only attach work or resolve it against that proof. It never
supplies a newer row observation.

The shared entry's publish operation replaces the base snapshot and all its
attached item projections together, then notifies readers. A refresh can
retain the previous publication while computing its successor. Reset invalidates both
immediately. Authority/program and entry-epoch fences reject obsolete
completions. Keep one refresh in flight and coalesce later requests as the
existing entry does; no cross-query barrier or global matching of commit
numbers. The required internal frame is not exposed as another public
snapshot type. Qualifying this capture against the integrated lane remains
required: merely adding an option to `observe` does not make its inputs atomic.

For each committed input revision, the SDK:

1. Selects readable rows, preserving their identity and specified display
   order, and indexes their `(table, id)` addresses.
2. Attaches contributing prediction references by that exact address, using
   the same local revision as the value. A partition-wide prediction list
   cannot mark unrelated query rows. `predicted` does not mean every pending
   action on the row was predicted, and its absence does not mean fresh or
   server-confirmed.
3. Attaches declared create/update/remove actions, in durable FIFO order.
   Several edits to one row remain several actions. A failed earlier edit
   does not hide a later queued edit. An overlay and a declared binding for
   the same intent produce one attachment, not two. The displayed body is
   exactly the selected query/twin value: the presenter never reapplies edit
   arguments or chooses an older draft over the twin's FIFO overlay result.
   The row's prediction mark denotes a contributing effective overlay, not
   that every attached action was predicted or confirmed. Masked overlays
   cannot supply that mark.
4. Adds matching creates with no readable row as explicitly labeled
   intent-only items, in an unsorted pending tail. Uses the bound pinned ID
   as their key when it is known. When that row becomes readable, publishes
   one item at its query-defined position under the same key.
5. Publishes once after the source query value, prediction attribution and
   outbox inputs are consistent. A row cannot appear once as a prediction
   and once as a pending bubble in the same publication.

No callback from a render, `getSnapshot`, selector, or subscriber writes the
outbox. Store changes arrive after their atomic swap, not from intermediate
reads. Fence async work by account/session, program and source revision;
matching server sequence numbers alone are insufficient. Preserve item and
array references when their values and attached work are unchanged. Do not
make every row scan every intent; index once and join in work proportional
to the page and relevant associations.

On a denied/refused query, the reducer clears query-origin data. A scoped
create may still display the current account's own submitted draft, explicitly
labeled, while `status` remains unavailable and the denial/refusal remains
visible. Unavailable/offline with no held answer can likewise show an owned
draft. This is not permission to retain a previously read body. Target-less
updates/removals remain reachable through the account outbox surface.
Account replacement/reset invalidates the derived snapshot before successor
values publish; none of the retired account's drafts escape that fence.
Delivered-history results retain exactly the reducer's existing permitted
data and retained/stale facts; do not reinterpret a permitted retained result
as a fresh denial. Item labels accompany the query's reason and never override
its completeness, provenance or freshness.

### 10. Retirement is a read-model decision, dismissal is a write

**Implementation rule, 2026-09-07.** A mutation's terminal response proves
that it committed. A row observation proves that a particular readable
image includes that commit or a later state. These are separate facts:

```
committed(intent, s) + observed(table, id, through >= s)
    => this item's successful action no longer needs a pending indicator
```

`through` is the owner's read sequence for that exact row image, not the
row's last-change version and not the client's highest sequence. The
evidence travels with the query value that uses it. Matching requires the
declared target, the current partition and authority, and fresh evidence
beyond the intent's admission. A retained answer or an unchanged admission
baseline cannot acquire a newer stamp from another row's arrival. The
direct server path derives it from accepted row references; local reads use
the authoritative base actually used by the twin, beneath any still-valid
later prediction. Absence is explicit negative evidence, never a row
missing from a capped page or a local predicted deletion.

For example, an edit commits at 41. A message body still read through 40
keeps its "Sent" indicator even if an unrelated delivery advances the
client to 80. The message read through 42 resolves that edit. It need not
equal the submitted body: another authorized edit may already have
superseded it. A second local edit can still predict over that confirmed
base and keeps its own action attached. No minted ID or write-set inference
is required for an in-place edit that creates no rows.

The corresponding lifetime rule removes the online special case:
`run()` returns its terminal response without dismissing the durable entry.
Online and offline admission therefore share one ledger and one lifetime.
Item projection is read-only; neither a subscription nor rendering schedules
deletion. The same keyed publication replaces a draft with its readable row
and removes a resolved indicator. Zero, one, or four readers cause exactly
zero automatic dismissals. Explicit dismissal remains a user action, as in
LLP 1012 §7; failures remain recoverable after the issuing call returns or
the component unmounts.

This deliberately retains successful terminal history until explicit
dismissal, matching the existing queued-write contract. It makes no bounded
history or automatic storage-compaction claim, and does not add a second
queue, acknowledgment ledger, timer, or per-screen settlement effect. The
account recovery surface exposes dismissal, including committed entries.
Any later automatic compactor must be specified separately and must not
erase unresolved work or use mounted-reader count as delivery evidence.

Remove the hook-owned `retired` sets and their calls to `dismiss`. Prefer
zero automatic dismissal actions: the client's one derived outbox/collection
projection stops showing a completed action when existing settlement
evidence says it is no longer awaiting delivery. Headless observation,
React and Expo use that same projection, even when no React hooks exist.
The runtime's durable `entries()` and explicit `dismiss(intent)` contract
remain available. This requires auditing **all** cleanup callers, including
`client-outbox.ts::settledResult`, which currently dismisses terminal entries
before returning `run()`'s result. Removing hook cleanup alone cannot preserve
an online placeholder through delivery, nor retain every online failure.

Expose the shared outbox read model through `client.outbox.observe()` and
have `useOutbox` and `useMutation` read it. Its scoped summaries share the
session's immutable input rather than issuing one status read per hook per
notification. This is the outbox counterpart of the existing query observer,
not a general resource framework.

This revises §4's hook-only policy. It is not automatic deletion moved one
layer down. A subscriber changes neither replay bytes nor storage lifetime.
Rejected and expired entries stay actionable until explicit dismissal;
queued entries cannot be dismissed. **Proposed terminal rule:** a `run()`
result reports settlement, not acknowledgment of its presentation. For a
store-backed write, return the terminal result without `settledResult`'s
implicit deletion; retain it through the same explicit-dismissal path as a
write that first returned queued. No-store writes keep their ordinary direct
result. Change the corresponding tests and LLP 1012 guidance together if this
rule is implemented. This intentionally changes online terminal retention;
the original follow-on's claim of unchanged storage lifetime was too broad.

The shared outbox snapshot exposes the raw terminal history, with one status
projection per distinct operation and one source subscription per client.
The templates expose it in **Changes on this device**, including explicit
dismissal of committed records and changes whose target is absent. Only query
items hide resolved indicators. This replaces the initial proposal for a
globally filtered outbox: each view owns its own observation evidence, so the
ledger needs no second definition of successful presentation. Retained
terminal records are a storage cost, not a bounded-history claim. Automatic
successful-record compaction is a separate policy decision and cannot hide in
this read projection. Qualify retained-history costs and indexed lookup in the
implementation; a material unbounded cost requires resolving that policy
before calling the default complete, not moving the scan into a hook.

Distinguish settlement from visibility when deriving an item's presentation:

| Evidence | Item/action presentation |
| --- | --- |
| Queued, with a contributing preview | One preview and its pending action; no create timestamp |
| Queued, without a preview | One labeled submitted draft if scoped here |
| Committed, no sufficient arrival evidence | Committed / awaiting delivery; no second send and no invented row |
| Readable authoritative target supersedes the action | One readable row; the completed indicator leaves |
| Current-authority target absence/removal at or after the commit | No invented visible-row claim; the completed action can leave the projection |
| Overlay retirement by generic cursor progress or another reserved ID | Custody progress only; it cannot settle this item's delivery indicator |
| Patience alone drops a prediction | No proof of row arrival; preserve the committed outcome for recovery |
| Rejected or expired | Failed action remains, with explicit dismissal |

**Target-evidence rule.** For an in-place edit, delivery is resolved by the
selected target's authoritative base at or after the commit, or an explicit
current-authority negative/tombstone for that target at or after the commit.
For a removal, only the corresponding negative/removal resolves absence;
a still-present target does not. Match `(table, id)`, partition, authority
and program identity. The evidence must be bound to the image used by this
frame: a newer global `seq`, a halo row, an unrelated fan-out ID, equality of
body strings, or `receipt.source = twin` is insufficient. A subsequent queued
edit may still overlay that base; it remains attached after the older committed
edit's indicator retires. Successful writes need not leave their old value
unchanged forever to count as observed/superseded.

Use the store's existing row/negative sequence facts and the admitted query's
selected-row provenance where sufficient; a receipt's overall sequence must
not be assigned to each retained/overlaid row. The integration may need a
private selected-row evidence sidecar during resolution. Establish that small
seam before promising per-item retirement, not a new wire field or compiler
declaration by assumption.

**Page-membership rule.** Whether to synthesize an unplaced create is a
separate question from whether a displayed row reflects a write. A complete or
capped owner answer to this exact query, freshly observed through the commit,
can select a page that omits the target. That committed create then belongs only
in device history; it must not return as a draft when a page advances or the
store reopens. This is a membership decision, not a claim of row arrival or
absence. A newer pool, sibling-query delivery, or halo cannot advance the old
page. Partial, denied, retained, clock-only and invalidated held answers provide
no new membership proof. Identical envelope replay does not manufacture fresh
observation order. Each stored answer privately retains its last qualified
membership observation as `{ through, order }`. This constant-size metadata
advances within the existing carrier commit, survives a partial or denied
replacement and later coverage invalidation, and travels in the query's private
frame. It never enters the wire or public answer. A legacy complete answer
records its existing order before losing coverage; migration cannot mint a
new observation. Cold reopen therefore preserves the same decision without
per-intent retirement records or a read-side write. An owner partial frame may
carry this query's earlier membership observation, never a later concurrent
answer's evidence. Coverage reset clears it with the stored answer.
Retained, clock-only and invalidated answers likewise cannot upgrade an old
point absence with fresh observation order. In-place indicators still require the selected row's own
proof even when this query's membership sequence is newer.

A pending create also retains its submitted `draft` alongside a selected `data`
row. During a composite-to-history authorization transition the screen can show
that owned draft while the independent history observer reattaches; it renders
query-origin data only from a usable composite or authorized history. This
preserves the key without borrowing uncertain row contents, author, or time.
No new lifecycle or collection cache is needed for the handoff.

The current `arrived` flag is not a per-item proof. The existing overlay
retirement includes negatives and cursor-chain progress; the pinned-ID
arrival loop also recognizes any reserved ID, including a fan-out row. Do
not read those as "this displayed message was returned by this query."
Use them for their existing custody meaning and require the selected target
to be readable before a draft becomes a row. A negative must not resurrect
the submitted body; a committed unpredicted edit, which may mint no IDs,
must not wait for a nonexistent inserted ID.

The implemented private frame supplies that evidence without changing the
wire. The no-ID edit tests advance an unrelated row first, then the displayed
target, and retain a once-only view of the old image. The live item resolves
only on its target update; the once-only item keeps its action. Both retain
the terminal intent. Missing proof keeps the action visible.
