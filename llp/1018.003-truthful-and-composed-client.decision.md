## Summary

The client publishes one record with independent data, receipt, freshness,
local changes and refusal facts. Pure `summarize` and `readiness` functions
provide the common status, sentence and action. Schema-declared tombstones
are hashed into the certificate and shared by the owner and twin.

Read this page for those implemented contracts. Read
[LLP 1018.003.000](./1018.003.000-items-and-observation.decision.md) for composed query items, their observation
proof and current outbox retention. Read
[LLP 1018.003.001](./1018.003.001-client-follow-ups.plan.md) for the commissioned follow-ups.
The [implementation record](./reviews/1018.003-implementation-record.md) preserves superseded
alternatives, actual reviews, failed runs and qualified results.

**The elegance target remains unmet.** At `e6c89816b`, the React thread is
179 lines and the Expo thread 68. The original 60-line goal was missed.
Composed items remove the joins, but recovery custody, positional target
bindings and indefinite successful history remain. This is a qualified
implementation of its stated contracts, not a completed elegance claim.

## Context

The earlier seven-way query union made each screen reconstruct readability,
provenance and offline state. Hook-owned or screen-owned outbox retirement
also made mounted consumers responsible for durable lifetime. The record
keeps those facts independently inspectable and gives their common
presentation one shared implementation. The item decision owns the later
outbox-to-row composition; its storage policy remains explicit.

## Decision

### 1. The snapshot record

Hooks and `client.observe` publish one record.
Every field below exists today under some state name; none is new
information except the row identities of predicted rows, which the twin
already holds and now publishes.

```ts
type Snapshot<T> = {
  data: T | undefined;
  next: Cursor | null;
  partial: boolean;
  /** What a certified evaluation said about this value, and whose evaluation it was. */
  receipt?: {
    state: "complete" | "capped" | "partial" | "denied";
    source: "server" | "twin";
    seq: number; next: Cursor | null; reason?: string; rule?: string;
    sites?: readonly { site: string; reason: string }[];
  };
  /** How current it is. Transport truth, independent of the receipt. */
  freshness: { live: boolean; staleSince?: number; connection: ConnectionState };
  /** What this device added. Offline truth. */
  local: {
    predicted: readonly { table: string; id: string; intent: string }[];
    retained: boolean; caughtUp?: boolean; watermark?: Cursor | null;
  };
  refusal?: Refusal;
  /** Derived by `summarize`, never stored. `detail` is the rule a denial named or the reason a partial gave. */
  status: "loading" | "ready" | "unavailable";
  reason?: { code: "refused" | "denied" | "partial" | "stale" | "offline" | "predicted" | "held"; message: string; detail?: string };
};
```

A partial receipt also carries the twin's `sites` (the uncovered sites and
their reasons, LLP 1012 §6), so no fact the offline runtime publishes is
dropped on the way to a screen.

`receipt.source` is the provenance axis: `server` for an owner receipt,
`twin` for the client evaluator's certified evaluation over held rows, which
also owns any locally minted continuation. A shared query's local refresh
carries that source explicitly even while its transport stays live;
connection-only reprojection never changes who evaluated the value.
An equal local reevaluation may retain the existing owner receipt when its
certified outcome, sequence, and effective value are unchanged. A different
sequence, completeness outcome, or local uncertainty still publishes; equal
data alone does not justify retaining an obsolete receipt.
Held data maps to `data` present with no `receipt`. `data` keeps value identity across snapshots when
the value is unchanged, as `reduceQueryState` does today. `QueryView` remains
the reducer's type and `summarize`'s input for opt-in inspection; `QueryViewState` and `QueryHookResult` leave the
public surface. `SubscriptionDelivery` and `QueryResult` remain the event and
wire types; screens never see them.

### 2. Derive, never add

`status` and `reason` are computed by one exported pure function,
`summarize(view, connection)`, used by every hook and available to headless code. Its
table is the whole summary contract:

| Axes | `status` | `reason` |
| --- | --- | --- |
| `refusal` present | `unavailable` | `refused` (the envelope's `rewrite`, else `message`) |
| `receipt.state = denied` | `unavailable` | `denied` (the rule) |
| `receipt.state = partial` and no `data` | `unavailable` | `partial` (the receipt's reason) |
| no `data`, no `receipt`, the twin reported nothing held, and the transport is not `connected` | `unavailable` | `offline` |
| the same "nothing held" marker while `connected` (a fetch is in flight) | `loading` | none |
| `data` present with a non-denied receipt, fresh or stale or retained | `ready` | the first of `partial`, `stale`, `predicted` that applies, else none |
| `data` present with no receipt (`held`) | `ready` | `held` |
| otherwise | `loading` | none |

**`ready` means readable data.** It does not mean server confirmation, drain
completion, or a usable composite. A composite record (LLP 1018.000 §4) is
usable only when `receipt.state` is `complete` or `capped` and its data has
all three fields. A partial with data is `ready`; a partial without data is
`unavailable`. The former screen-owned selection and usable-composite guard
are superseded by the plain tier: declared history hides unusable composite
`data` and selects items without granting count or preview authority. Derived `status` and `reason` grant no
authority. A usable composite releases the fallback subscription.

A test enumerates the cross product of the axes and asserts the table. The
rule this encodes: **a summary is a projection of facts, never a fact.**

**Transition invariants** the shared reducer keeps, so the table above is
applied to a coherent view:

- A stale event keeps the last receipt and marks `freshness.staleSince` when
  it names no other sequence; a stale event that names another sequence
  carries held data the receipt does not describe, so the receipt is dropped
  and the data reads as `held`. A stale event never invents an outcome, and
  a kept denial keeps no data.
- A denied or refused event scrubs `data`; a reset forgets the snapshot.
- A row kept under `retain delivered-history` (LLP 1012 §5 rule 4) marks
  `local.retained` and keeps the outcome that delivered it.
- A drain may expose readable data before `caughtUp`; `caughtUp` is a fact,
  not a precondition of `ready`.

Write readiness follows the same rule. `useMutation(op)` returns
`{ run, inFlight, last, can }`. The former hook-owned `pending` and `detail`
fields are superseded by the plain tier below. LLP 1018.004 makes every
outcome terminal or durable: `committed | queued | rejected`. A follower
queues an inbox row; it has no unknown-admission token. `can` is derived by one function with three inputs, because the
sentences depend on all three: `readiness(status, connection, queued)`, where
`queued` is the op-scoped count the hook already computes, not the status's
partition-wide `remaining`:

| `OutboxStatus` | `can.send` | `can.action` | `can.reason.code` |
| --- | --- | --- | --- |
| ready, fence inside, `queued = 0` | true | `none` | — |
| `ready`, fence inside, `queued > 0`, `draining` | true | `wait` | `pending` ("waiting for the server") |
| `ready`, fence inside, `queued > 0`, paused | true | `connect` | `pending` (connected: "sync to resume delivery"; else "waiting for connection") |
| ready, fence past | true | `connect` | `fence` |
| `sealed` | false | `sign-in` | `sealed` |
| `grant-missing`, `grant-expired`, `ids-exhausted`, `program-missing` | false | `connect` | that reason |
| `follower` | false | `other-tab` | `follower` |
| `forwarding`, fence inside, `queued = 0` | true | `none` | — |
| `forwarding`, fence inside, `queued > 0` | true | `wait` | `pending` ("waiting for the sending tab") |
| `writer-unresponsive` | true | `wait` | that reason |
| `inbox-full` | false | `wait` | that reason |

`connect` means the app offers `client.online()`, because reconnect alone
replays nothing (`guide/offline.md`). The shared sentences are `can.reason.message`, the way a
refusal's `rewrite` is already the SDK's; the SDK also exports them as a map
keyed by code, and the outbox entry label (`intentLabel`) the same way. An
application that wants its own copy switches on `code`. `useOutbox().detail` carries the full `OutboxStatus`. `useMutation().last`
carries the latest result, including a retryable transport refusal.
`useOutbox()` keeps `entries`, `dismiss`, and `can`. A
follower's `detail.writer` contains the announced writer status separately
from the inbox status used to derive `can`.

The existing drain owner publishes `draining` independently of mounted hooks
or connection state. [LLP 1018.003.001 §1](./1018.003.001-client-follow-ups.plan.md#1-readiness-actions)
records its implementation and qualification on the durable inbox.

### 3. Tombstones are declared, certified, and shared

The table whose rows are the log declares which of its rows tombstone which
target, on the table itself, with the predicate spelling row schedules
already use:

```q
table deliveries:
  …
  tombstones messages[.messageId] if .kind = 'removed' or .kind = 'expired'
```

The target column must be a column of this table whose type is a reference
to the target table; an optional reference that is null tombstones nothing.
The predicate reuses the rule-expression parser and is restricted after
parsing to `.column` reads of this table's `enum`, `bool`, and `text` columns,
literals, `=`, `!=`, `and`, `or`, `not`, and parentheses; a null column
compares false. `check` refuses anything else at the authored site. Several
lines per table union.

**Custody.** The declaration is a field of the Rust `Table` in `schema.rs`,
validated with the schema, omitted from serialization when empty so every
existing schema's canonical bytes and `Schema::hash()` are unchanged, and
included when present, so a schema that declares it has a new hash and new
certificate and resume-validator identities bound to it (LLP 1012 §8). The
evaluator's hasher knows the field and produces the same canonical form; a
golden proves parity. The owner serves it in the program from
`GET /api/program`, and LLP 1012 §5 rule 3 is amended to fire on rows the
held program declares. `OfflineClientOptions.onTombstone` is removed, with
every consumer: `src/test.ts` and `types/test.d.ts`, the provider's
`throughRef` wrapper, the chat template's React entry and Expo `App.tsx` and
`Witness.tsx`, the generic React scaffold's `main.tsx`, the browser witness's
generated entry, and `tests/offline-store.test.ts`. `retain
delivered-history` and rules 1, 2, and 4 are unchanged. What is unchanged is
query execution and the existing protocol algorithms; certificate
identities are not.

## The plain tier

Revised 2026-09-08. The following delegated rulings implement the author's
2026-09-08 elegance commission. They supersede the earlier `receipt.outcome`,
`RefusalEnvelope`, thrown public `SnapbackRefusal`, `as` client option,
`client.subscribe`, `useSubscription`, and mutation `pending`/`detail` contracts.
The composed-item observation and custody proofs remain binding; `data` is now
undefined on the `history` and `drafts` branches. The screen line-count claim
belongs to lane A2, so the summary's elegance target remains unmet.

A1. `useMutation(op).run(args)` never throws. `MutationResult` stays `committed | queued | rejected`. `rejected` is `{ state: "rejected" } & Refusal` whether the cause was a program `require … else CODE` (family `rule`, `code` = the CODE), a platform refusal (its family), or a transport failure (family `transport`, code `E_TRANSPORT`, `retryable: true`). The thrown `SnapbackRefusal` class and `isSnapbackRefusal` leave the public surface; no ordinary path on `snapback2/react` or `snapback2/client` throws. The headless client's `mutation()` returns the same union; `query()` returns the wire union (never throws either: transport failures are `{ state: "refused" }` with the same `Refusal` fields).
A2. One refusal shape: `Refusal = { code; family; message; rewrite?; guide?; site?; rule?; retryable?; reason? }`. `RefusalEnvelope` is renamed `Refusal` (delete the old name). `Snapshot.refusal?: Refusal`. No second envelope type anywhere in `src/`.
A3. One vocabulary: `state` is a verdict (the server's, or the twin's) on an answer or a write: `complete | capped | partial | denied | refused` for reads, `committed | rejected | queued` for writes. `status` is a hook's lifecycle: `loading | ready | unavailable`. Therefore `receipt.outcome` becomes `receipt.state`; the word `outcome` disappears from `src/`. One action set for "what can the user do": `Action = "sign-in" | "connect" | "other-tab" | "wait" | "none"`; `OutboxStatus.action` uses it (`login`→`sign-in`, `resume`→`connect`, `load-program`→`connect`), `Readiness.action` uses it. `createClient({ persona })` and `<SnapbackProvider persona=…>` replace `as` (the test runner's `as("alice")` verb stays; the CLI `--as` stays).
A4. Plain reading of a snapshot: `data`, `status`, `reason`, `items` (when bound), `next` (the continuation cursor, hoisted from the receipt; `null` when there is none), `partial: boolean` (true when `items` come from declared history rather than the observed query). `data` is `undefined` whenever the observed composite is not usable, so no screen reads `itemsFrom`. The truthful axes (`receipt`, `freshness`, `local`, `refusal`, `history`, `itemsFrom`) remain on the snapshot, documented as the opt-in tier on `guide/live-query.md`. Query args omit the cursor: `useQuery(api.messages.inbox, {})` is the paved form; `{ c: null }` still works; items bindings treat a missing and a null cursor the same.
A5. `usePage(op, args, options?)` for ops whose result is an array: `{ items, pages, loadMore(), hasMore, status, reason }`; each page is its own live query keyed by the previous page's `next`; the cursor argument is `c` unless `options.cursor` names another; pages reset when args change. Exported from `snapback2/react` (and the native entry).
A6. `ResultOf<Op>` and `ArgsOf<Op>` exported from `snapback2/client`; templates use them; the `__result` phantom-inference hack in templates is deleted.
A7. `useMutation` returns `{ run, inFlight, last, can }`; the SDK clears `last` when the client's auth generation changes or the hook's op changes, so a screen renders `last` inline and app code never holds a generation guard. `useSnapbackSnapshot().authGeneration` stays available (truthful tier) but no template imports `useSnapbackClient` or `useSnapbackSnapshot`.
A8. Public surface: `snapback2/client` no longer exports `Coverage, HeldAnswer, HeldProgram, OverlayRow, StoreSwap, LocalAnswer, Prediction, PartialSite` or `SnapbackClient.sharedConsumers()`; `useSubscription` is deleted (it was an alias); `client.subscribe` becomes internal and `client.observe` is the one read API. Internal modules import from source paths. Anything a witness or `snapback2/test` still needs is re-exported from a `snapback2/internal` entry that the guide never mentions — the lane lists what and why.
A9. Expo parity: the Expo template uses `<SnapbackProvider url persona offline>` from `snapback2/react-native` with the same props as web; no `useEffect`/`useState<SnapbackClient>` client construction in app code.
A10. Bytes: the five-root complete local runtime (`build.mjs --measure-twin`) must not exceed its base-commit value (83,999) after this lane; the deletions in A1/A2/A8 pay for `usePage`. Report before/after.

Implementation: `client.query` and `client.mutation` catch at the client boundary;
`useMutation.run` also catches supplied-client failures. Internal transport
errors stay inside the SDK. Owner require rejections are identified by their
explicit `E_REQUIRE:CODE:` message and mapped to `family: "rule"`. Resume-only
wire details remain internal; published refusals have only the one shape.

`snapback2/internal` is a small static entry for first-party journeys and
witnesses: `subscribe` inspects raw deliveries, `sharedConsumers` measures shared
readers, and their symbol keys keep those methods off the named client surface.
The entry uses the existing client and adds no bundler configuration. Internal
SDK modules import source paths; the guide does not mention this entry.

Pagination returns the individual `Snapshot`s in `pages`. Changing a page's
continuation releases and rebinds its successors; an account, operation, cursor
name or argument change resets the hook. The native provider configures Expo
fetch, SQLite and secure token custody, then uses the shared provider lifetime.
