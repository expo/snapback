# LLP 1018.003: A truthful and composed client — the snapshot record, derived status, and schema-declared tombstones

**Type:** Decision
**Status:** Draft
**Systems:** Snapback 2 client snapshots and hooks (`snapback2/client`, `snapback2/react`, `snapback2/react-native`), the outbox surface, the chat and todos templates, the `offline` and `live-query` guide pages, one Quarry schema declaration, the certificate and the twin
**Author:** Claude Fable 5.1, commissioned by Charlie Cheever in session
**Date:** 2026-09-07
**Revised:** —
**Related:** LLP 1018 (parent), LLP 1018.000 §4 and §7, LLP 1012 §5 and §7, LLP 1013, LLP 1002 §9, LLP 1004, `rules/NOT-DOING.md`

## Summary

The client tells the whole truth and makes every screen pay for it. This
decision keeps every fact the client publishes today and changes how they are
arranged. One snapshot record with orthogonal axes — value, receipt,
freshness, local overlay, refusal — replaces the seven-state view union. A
three-way `status` and at most one `reason` are *derived* from those axes by
one SDK function and never stored. Write readiness is derived the same way.
The rows that tombstone other rows are declared in the schema and certified,
not injected by an application callback. The witness is the chat template's
thread screen and composer, rebuilt with no helper modules on React and Expo.

This page is short on purpose: the decision is small and the code is the
witness. It does not reopen LLP 1018.000 §4's coherence boundary or ownership
model; it fixes the shape of the snapshot that boundary publishes.

## Context

**The scores.** LLP 1018 §2 records Snapback 2 winning where the work is a
primitive and losing where it is composition: client integration 63 against
Convex's 83 in the Astra assessment, queries and live 60 against 85 across
three scorers. Muse's notes name the discovery half ("grants/outbox/drain/lease
semantics came only from probes"); Astra's name the composition half.

**The surface as it stands.** `QueryView` (`types.ts:389`) is a union of seven
sibling states: `complete`, `capped`, `partial`, `denied`, `refused`, `stale`,
`hydrating`, the first four carrying `live`, `stale`, `retained`, `caughtUp`,
`watermark`, and `predicted` facts. Those states answer three different
questions — what the certificate said, how current the answer is, what this
device added — and the union makes them compete: a stale-but-complete answer
is state `stale` and loses its receipt. Six overlapping unions describe the
same delivery on its way to a screen (`ServerQueryResult`,
`OfflineQueryResult`, `QueryResult`, `SubscriptionDelivery`, `QueryView`,
`QueryHookResult`). `OutboxStatus` enumerates seven mechanism reasons
(`ready`, `sealed`, `grant-missing`, `grant-expired`, `ids-exhausted`,
`program-missing`, `follower`), four actions, and the fence.
`OfflineClientOptions.onTombstone` (`types.ts:283`) asks the application to
tell the client which stored rows tombstone which others; `offline.ts:638`
calls it on every fresh row.

**The template is the evidence.** The shipped chat app's `App.tsx` renders
its inbox with `"data" in inbox && Array.isArray(inbox.data) ? inbox.data : []`;
the Expo thread screen has the same line. The React thread screen is 130 lines
and needs a 131-line `shared/log.ts` to turn the delivery log and the outbox
into bubbles (tombstone hiding, pinned-id merge, chronological sort) and a
32-line `shared/offline.ts` that maps the seven outbox reasons to sentences
and declares which delivery kinds tombstone which message. Both the React and
the Expo composer import it. Anything both platform templates must
share identically is SDK, not application, and a reducer over the log that
runs in application TypeScript is one the certificate cannot vouch for and
the twin cannot share.

**What is already commissioned.** LLP 1018.000 §4 moves query reduction into
one shared entry exposed as `client.observe`, read by React and Expo through
`useSyncExternalStore`, with one immutable snapshot owning value, completeness,
freshness, predictions, continuation, and refusal. It also says "preserve value
identity with `reduceQueryState`", so the record it publishes is the current
union. §7 adds expression-only `fn` helpers for the repeated reads. Neither
changes what a screen receives. That consumer rewrite is in flight, which is
why this page exists now rather than after it.

**Retention.** LLP 1012 §5 rule 3 reads: "a fresh log row of kind `removed` or
`expired` evicts the body it names." The rule is stated in the chat recipe's
own vocabulary, and the client learns those kinds only through the
application's callback. The spec knows something the certificate does not.

## Options

**For the view.** (a) Keep the union and document it better. Rejected: the
cost is paid per screen, not per reader. (b) Convex's shape, `T | undefined`.
Rejected: it is composed by lying — a denied query and a loading query look
the same, and the twin's prediction has nowhere to go. (c) Orthogonal axes
with a derived summary. Chosen: every fact stays, each consumer touches one
axis, the common case is the default.

**For write readiness.** (a) The application maps reasons to actions, as the
template does. (b) The SDK derives `can` once. Chosen: (b); the mapping is the
same for every application.

**For tombstones.** (a) Keep the callback. (b) Infer from enum member names.
Rejected: a heuristic in the eviction path. (c) One schema declaration,
certified, read by engine-served program and twin alike. Chosen: (c).

## Decision

### 1. The snapshot record

Hooks and `client.observe` publish one record. Every field below exists today
under some state name; none is new information.

```ts
type Snapshot<T> = {
  data: T | undefined;
  /** What the certificate said about this value. Authoritative, per named query. */
  receipt?: { outcome: "complete" | "capped" | "partial" | "denied"; reason?: string; rule?: string; seq: number; next: Cursor | null };
  /** How current it is. Transport truth, independent of the receipt. */
  freshness: { live: boolean; staleSince?: number; connection: ConnectionState };
  /** What this device added. Offline truth. */
  local: { predicted: readonly string[]; retained: boolean; caughtUp?: boolean; watermark?: Cursor | null };
  refusal?: RefusalEnvelope;
  /** Derived by `summarize`, never stored. */
  status: "loading" | "ready" | "unavailable";
  reason?: { code: "refused" | "denied" | "partial" | "stale" | "offline" | "predicted"; message: string };
};
```

`data` keeps value identity across snapshots when the value is unchanged, as
`reduceQueryState` does today. The record is produced by the §4 shared entry
and consumed by `snapback2/react`, `snapback2/react-native`, and headless
`client.observe`. `QueryView`, `QueryViewState`, and `QueryHookResult` leave the
public surface. `SubscriptionDelivery` and `QueryResult` remain the event and
wire types the entry consumes; screens never see them.

### 2. Derive, never add

`status` and `reason` are computed by one exported pure function,
`summarize(snapshot)`, used by every hook and available to headless code. Its
table is the whole contract:

| Axes | `status` | `reason` |
| --- | --- | --- |
| `refusal` present | `unavailable` | `refused` (the envelope's `rewrite`, else `message`) |
| `receipt.outcome = denied` | `unavailable` | `denied` (the rule) |
| `receipt.outcome = partial` and no `data` | `unavailable` | `partial` (the receipt's reason) |
| no `data`, no `receipt`, `connection = offline` | `unavailable` | `offline` |
| `data` present, any outcome but denied, fresh or stale or retained | `ready` | the first of `partial`, `stale`, `predicted` that applies, else none |
| otherwise | `loading` | none |

A test enumerates the cross product of the axes and asserts the table. The
rule this encodes: **a summary is a projection of facts, never a fact.** Only
`unavailable` and `loading` are distinct at the top level because that is the
minimum a screen needs to be honest; everything finer is one property down.

Write readiness follows the same rule. `useMutation(op)` returns
`{ run, inFlight, can, pending, last, detail }`. `run` and its
`committed | queued | rejected` result are unchanged. `can` is derived from
`OutboxStatus` by one function, `readiness(status)`:

| `OutboxStatus` | `can.send` | `can.action` | `can.reason.code` |
| --- | --- | --- | --- |
| ready, fence inside, nothing queued | true | — | — |
| ready, fence inside, queued > 0 | true | — | `pending` |
| ready, fence past | true | `connect` | `fence` |
| `sealed` | false | `sign-in` | `sealed` |
| `grant-missing`, `grant-expired`, `ids-exhausted`, `program-missing` | false | `connect` | that reason |
| `follower` | false | `other-tab` | `follower` |

The sentences the template's `sendingStatus` produces today become the SDK's
`can.reason.message`, the way a refusal's `rewrite` is already the SDK's. An
application that wants its own copy switches on `code`. `detail` carries the
full `OutboxStatus` and the last retryable transport refusal; `ready`,
`status`, and `transport` are folded into `can` and `detail`. `useOutbox()`
keeps `entries` and `dismiss` and exposes the same `can` and `detail`.

### 3. Tombstones are declared, certified, and shared

The table whose rows are the log declares which of its rows tombstone which
target, on the table itself:

```q
table deliveries:
  …
  tombstones messages[.messageId] when .kind in ('removed', 'expired')
```

The target column must be a reference to a table; the predicate is a
conjunction of `.column = literal`, `.column != literal`, and
`.column in (literals)` over this table's `enum`, `bool`, and `text` columns,
evaluated per row with no reads. `check` refuses anything else at the authored
site. The compiler carries the declaration in the program the owner serves
from `GET /api/program`, so the twin and the client read the same fact. LLP
1012 §5 rule 3 is amended to fire on rows the held program declares, and
`OfflineClientOptions.onTombstone` is removed, with `snapback2/test`'s copy
and the provider's `throughRef` wrapper. `retain delivered-history` and rules
1, 2, and 4 are unchanged. The engine executes nothing new; eviction remains a
client rule, now over a certified input.

### 4. One product rule for pending rows

A thread shows only rows the certificate or the twin vouches for. A queued
write the twin predicted appears in `data` under its pinned id and is marked
by `local.predicted`. A queued write the twin could not predict, because no
program is held, is reported by the composer as a count through `pending` and
never invented as a row. This closes the pinned-id merge in `threadBubbles`.

### 5. The witness

The chat template's React `Thread.tsx` at most 45 lines, reading the composite
`conversationView` of LLP 1018.000 §4 (the `thread` page until it lands), with
`shared/log.ts` and `shared/offline.ts` deleted; the Expo thread the same
shape with native primitives; the inbox and search reading `view.data`
directly; both composers gating on `can.send` and showing `can.reason.message`
and the `connect` action. The existing browser and Expo witnesses pass with
assertions changed only where they name attributes, not behavior — including
the step that a message revoked while offline is gone after the resume, which
now depends on the declaration rather than the deleted callback. The complete
local runtime is measured after the change and reported against the 82,000
gzip ceiling of LLP 1018.000 §2; the SDK gains two small pure functions and
their sentences and loses the union handling.

## Consequences

- Breaking for `snapback2/react` and `snapback2/react-native` hook return
  types and for `OfflineClientOptions`. Snapback 2 is pre-1.0 with no
  compatibility lanes (`rules/NOT-DOING.md`), and the templates are the only
  known consumers.
- The guide's first pages teach `data`, `status`, `reason`, and `can`. Grants,
  fences, drains, leases, and partitions stay real and reachable under
  `receipt`, `local`, and `detail`, and move to a "how it works" section of the
  offline page. The `live-query` page that will carry this contract still
  opens with a TypeScript `query({...})` example from the authoring surface
  deleted on 2026-09-02; that example is replaced in the same landing.
- Nothing in LLP 1012 §5–§8's protocol changes except the input to rule 3.
  Receipts, certificates, the wire, resume, and the twin's evaluation are
  untouched. The composite query's coherence and its lack of a page
  continuation remain §4's.
- The six delivery fan-out loops in the chat recipe remain. They need a
  statement-level helper or a declared fan-out, which LLP 1018.000 §7
  explicitly defers; this page does not solve them in the client.

## Open questions (author)

1. When both `partial` and `stale` apply to a ready snapshot, the table picks
   `partial`. Is that the right sentence for a user to see first?
2. `follower` yields `other-tab` rather than a takeover action. LLP 1018 §3's
   policy is that the second tab follows and inherits on close; a takeover
   affordance waits for a product that asks.
3. `summarize` and `readiness` are exported so headless and test code can use
   the same table. Should the sentences be exported as a map keyed by code, so
   an application can replace one without replacing the function?
