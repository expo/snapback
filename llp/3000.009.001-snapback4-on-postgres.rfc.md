## Summary

The author asked for Snapback 4 to work on Postgres, in three parts:

1. **The port.** A Snapback 4 server can keep its store in Postgres in
   production: `serve`, `deploy`, identity, durable work, assets, release and
   recovery, not only the data plane the evaluation adapter runs today.
2. **Graduation.** An application that outgrows SQLite moves to Postgres with
   as little disruption to its users as possible: no application change, no
   client release, devices keep their replicas, sessions stay valid, and
   writes are unavailable for seconds rather than for the length of a copy.
3. **Scale.** We find out, by measurement against Supabase, raw Postgres and
   Convex self-hosted on Postgres, whether Snapback 4 on Postgres has scale
   limits those systems do not, and we attribute each limit to its cause.

This RFC keeps LLP 3000.009's accepted direction: one interpreter over both
stores, the generic row and index layout, no lowering of Quarry to SQL, one
commit order per store, the same wire. It adds four decisions of its own:

- **A store is a logical identity, not a file** (§3.1). Its `store_id`,
  commit sequence, principals, sessions, receipts and work records belong to
  the logical store. Moving it to another engine keeps that identity; restoring
  an earlier point creates a new one. Graduation is seamless because of this.
- **The port is a semantic contract for all durable state** (§3.2). It is not
  a SQL abstraction and not only `Rows`. `serve` and `deploy` compile against
  it, and nothing above it reaches a SQLite connection.
- **The commit path is the first scale risk** (§3.3). Today a writer holds
  the store's single head across every round trip its program makes. That
  cannot reach a production write rate over a network. The port defines a
  committer seam. Its first committer is a serial batch, which is correct by
  construction and amortizes the flush on both stores. An optimistic
  committer is designed beside it, to remove the round-trip term on Postgres.
  The scale program's first cells measured the ceiling: 120 commits/s at a
  0.5 ms round trip, against 5,700/s and more for raw Postgres. The serial
  batch barely helps, so the author commissioned the optimistic committer.
  It is built once its execution stage is sized.
- **Postgres earns its place through operations and more than one process**
  (§3.4). Read latency is not the reason. The first production target is one
  serving process with a fenced standby. More than one serving process is the
  second target, and the first must not foreclose it.

Each part has a child. This document holds the decisions they share, the
sequence and the scope changes that need the author's ruling (§7).

The SQLite engine has kept growing beside the adapter. 23 files and about
10,000 lines of `snapback4-core` use `rusqlite` directly, and the SQLite store
owns 31 internal tables: assets, dormant evolution state, release events,
credentials, time audiences, effect steps and more. Asset bytes are files
beside the store. The server holds one `FairMutex<Engine>`, and serving code
reaches `engine.store().conn()` directly. A sidecar file lock gives a store its
one owner. The ephemeral hub, presence, held change polls and commit wakeups
live in that process's memory. No non-test code deletes from `_log` or
`_commits`.

So the evaluation adapter proved that the **semantics** transfer. It did not
prove that the **product** transfers. Most of the remaining work lies outside
`Rows`.

## 2. Why an application moves to Postgres

The answer decides what "work on Postgres" has to mean. An application
outgrows SQLite for some of these reasons:

| Reason | What it asks of Snapback on Postgres |
| --- | --- |
| Operator trust: managed backups, point-in-time recovery, replicas, failover, a provider's SLA | The production port with fencing (child A); restore as a new incarnation |
| More than one serving host: rolling deploys, availability through a host failure, more CPU for reads and sync | A fenced standby first; then several serving processes over one store (child A, P2) |
| A larger store than one disk or one file comfortably holds | Layout and retention that stay healthy at 10⁸–10⁹ rows; log retention (child C) |
| Write concurrency | A commit path whose ceiling is set by the database rather than by round trips (§3.3) |
| The SQL ecosystem: reporting, extensions, BI tools | Projections and SQL reads (LLP 3000.009 §6, increment D), outside this RFC |

None of these reasons is read latency. The evaluation shows Postgres is slower
per operation, as expected for a network database under an interpreter that
makes several calls per operation. This RFC therefore does not promise lower
latency. Child C measures the cost and decides whether it is acceptable.

## 3. Decisions

### 3.1 A store is a logical identity

A logical store has:

- its `store_id`;
- its commit sequence and partition log;
- its generation and release history;
- its principals, credentials, sessions and read sessions;
- its receipts and work records (requests, jobs, effects, steps, schedules);
- its asset ledger, with the bytes held in a blob store;
- its release artifacts (the release tree, by digest) and activation record;
- its worker completions (today a ledger file beside the store);
- its change evidence, cap occupancy, dormant evolution state, time
  audiences and sequences.

A physical store is one engine holding one logical store: a SQLite file or a
Postgres schema.

- **Graduation moves a logical store.** The target starts at the source's
  exact head and keeps its `store_id`. A device's watermark, a session token
  bound to the store, an outbox entry awaiting its receipt and a worker's
  lease all remain valid (child B).
- **Restore creates a new incarnation.** Restoring an earlier point makes a
  new `store_id`, as LLP 3000.009 §9 already requires. Old resumes are fenced,
  sessions bound to the old identity end, and uncertain work is quarantined.
- **Failover in a lossless HA mode keeps the incarnation** (child A §5.4;
  the author's ruling, §7). A failover that loses acknowledged transactions
  is dangerous for two reasons:
  - lost commits can be refilled under the same sequence numbers;
  - revocations commit without advancing the head and can vanish without
    trace.

  No asynchronous mechanism can repair that. Revision 4 tried and round 4
  showed why it fails (§9). So the store declares its HA mode:
  - **Lossless modes keep the incarnation.** `storage-sync` covers RDS
    Multi-AZ instances, Cloud SQL HA, Aurora, AlloyDB and Neon.
    `streaming-sync` covers a strict-synchronous HA manager. A failover in
    either is a reconnect: nobody is logged out and no device re-acquires.
    Each provider is qualified by live failover witnesses.
  - **`async` makes the operator choose.** `new-incarnation`, the default,
    recovers as a restore. `continue` keeps serving with the loss stated, as
    Supabase or raw Postgres applications would.
  - **A hash-chain checkpoint is a tripwire,** not a proof. It catches a
    lossless mode whose contract was violated.
  - **Graduation requires a lossless mode.**

- **No physical store is ever "the same store" as another by accident.**
  Exactly one physical store may serve a logical store at a time. The store
  holds that fence itself (§3.4). A copy is a new incarnation unless
  graduation's cutover protocol hands the identity over.

The code already binds sessions and sync to `store_id`
(`store/authority.rs`, `serve_sync.rs`). This decision makes the binding a
contract across engines, rather than a property of one SQLite file.

### 3.2 The port is a semantic contract for all durable state

The port has three layers (child A §3):

1. **Access**: `Rows` and `PartitionRows` as today, with batching (C1).
2. **Durable state**: typed operations by family — identity, work, assets,
   release and evolution, receipts, sequences, time audiences. Each runs
   inside a store transaction that a backend implements. This generalizes the
   C3.2 authority policy, which is already store-neutral with a SQLite and a
   Postgres adapter.
3. **Host coordination**: what one process does in memory today and several
   processes must share. That is commit notification, ownership and fencing
   leases, the ephemeral and presence hub, and blob storage.

The rule: **only an adapter touches a database connection.** The `sql`
inspection verb gets an implementation for each store. A test refuses any
`rusqlite` or `postgres` use in `crates/snapback4` outside the adapters.
Snapback 1's graduation path (LLP 0046) found the seam had to be extracted
before Postgres could plug in. Snapback 4 is at the same point, with a larger
non-row surface.

Each family has one conformance suite run against both adapters, as the
corpus is today. A schema or feature that `check` accepts runs on both stores,
or `check` names the store it requires. There is no silent Postgres subset:
maintained columns, `not before`, assets, jobs and schedules must reach parity
before Postgres is called a production target.

### 3.3 The commit path is the first scale risk

Today's protocol takes the head lock first, then runs the whole program, then
commits. The SQLite writer and the evaluation adapter's `Serialized` mode both
work this way. On Postgres the lock is a row lock, held across every call the
program makes and across the commit's flush. One store's write ceiling is
then roughly

```
commits/s ≤ 1 / (calls_in_program × RTT + execution + commit_flush)
```

- At the evaluation's Unix-socket RTT this gave about 450 commits/s.
- At a managed database's in-region RTT of 0.3–1 ms, with the measured 15
  calls per increment, the bound falls to roughly 60–200 commits/s, before
  the flush.
- **S0 confirmed it.** The engine's serial time fits
  `2.05 ms + 11.98 × RTT`, where 12 is exactly the round trips held under
  the head lock. That is 120 commits/s at 0.5 ms, against 5,700/s for raw
  Postgres with four writers and 89,000/s with 64. **This is the first
  measured structural limit of Snapback 4 on Postgres.** Whether it is the
  largest waits on child C's W6, because table-granular live invalidation
  (H3) may bind first.

Raw Postgres and Supabase serialize only conflicting rows, and Postgres
group-commits their flushes. Convex orders commits through one committer.
Its functions run against a snapshot, outside that committer
([How Convex Works](https://stack.convex.dev/how-convex-works)).

On SQLite the same bound applies with `k·RTT ≈ 0`. On S0's host,
`serve`'s single connection reached 3,700–4,200 commits/s, where execution
cost (about 160 µs) outweighs a 77–79 µs flush. Disks whose flush costs
milliseconds would be flush-bound instead. The first draft's 165/s figure
probably came from such a disk (child C §2).

The directional decision: **the port defines the commit path as a
`Committer` seam, with today's lock-first protocol as the reference.** The
candidates are in child A §6:

- **(0) The serial batch.** N queued mutations run back to back in one store
  transaction, each under its own savepoint, with one head update and one
  flush. It is correct by construction: the same serial order, no read sets,
  no overlay. S0 showed it recovers only the flush's share: about 130/s on
  Postgres at 0.5 ms within the write SLO, against the reference's 120, and
  an estimated 1.46× on a fast-flush SQLite disk.
  It stays as the hot-key fallback, the qualification reference for (a),
  and a SQLite improvement on slow-flush disks. It lands at child A's P0.
- **(a) An optimistic single committer.** It executes at a snapshot with
  sequence-derived values as placeholders. It validates complete read sets,
  including authority facts, against an internal revision that every
  durable write advances, serially within each batch, then group-commits.
  This is the only candidate that removes `k·RTT` from the serial section.
  Its commit stage is bounded at 15,700/s at 0.5 ms. **The decision rule
  fired on S0's evidence, and the author commissioned (a)** (§7). It is built once child C's S1
  sizes its execution stage, which is bounded by `connections / (k·RTT +
  exec)`.
- **(b) Per-mutation database transactions with an ordering stage.** The
  first draft's version broke exact snapshots. A correct version is a
  different protocol, and it is held in reserve.

Round 2 noted that H1's formula had already predicted the rule's outcome.
S0 confirmed the prediction, and its value lies in the measured constants.
They size (a) and rule out (0) as the Postgres answer. Every candidate must
keep the invariants of LLP 3000 §7 and LLP 3000.009 §4.4:

- one total commit order per store;
- a published watermark has no gaps below it;
- a snapshot at watermark W contains exactly the commits at or below W;
- an infrastructure retry repeats the whole operation and rereads every fact;
- the authority clock is monotone in commit order;
- every durable transaction is fenced by the owner token.

Shipping production Postgres on the lock-first reference is the one outcome
this RFC rules out.

### 3.4 Operations and more than one process

| Phase | Topology | What it gives |
| --- | --- | --- |
| P1 | One serving process per store over Postgres, plus an optional warm standby. The store holds the ownership lease on the database clock and the fencing token. Every durable transaction checks the token, and takeover terminates a paused owner's sessions. Asset bytes and release trees go to an S3-compatible blob store. | Managed backups, PITR, database failover, larger stores, a host failure survived by promoting the standby |
| P2 | Several serving processes over one store. Queries, sync pages and change polls are served anywhere. Commits go through one committer, the lease holder; other processes forward mutations to it or submit their executions to it. Commit notification and the ephemeral hub cross processes. | Read and sync capacity beyond one host; rolling deploys without a stopped activation |

P1 is the parity target. It is what a SQLite deployment does, plus the
operator benefits of §2. P2 is commissioned from child C's evidence, but P1
must not foreclose it:

- every in-process coordination point is named in child A §4 with its P2
  mechanism;
- no new one is added without such a mechanism.

Multi-region execution, sharding one store across databases, and placing
several applications in one commit order stay out of scope. Their absence is
part of what child C measures against the controls: Supabase and raw Postgres
also start from one primary, and so does a Convex deployment.

## 6. Verification

The obligations of LLP 3000.009 §11 apply unchanged. This RFC adds:

1. **One meaning on every store, for the whole product.** Every durable-state
   family runs one conformance suite against both adapters. The HTTP host
   suite runs with the store as a parameter, not only the corpus.
2. **Identity across engines.** A graduated store answers every recorded
   device resume, session, outbox replay and worker lease exactly as the
   source would have. A restored store refuses them.
3. **Fencing of every durable transaction.** A partitioned or paused former
   owner can commit nothing after its lease is taken, including writes that
   publish no sequence (sessions, claims, receipts, asset views,
   time-audience pins). This is tested by pausing the process (SIGSTOP),
   then resuming it, not only by killing it.
4. **No performance claim without child C's ledger.** No public statement
   says Snapback 4 on Postgres scales, or scales like a named competitor,
   without a row of that ledger behind it.

No new blocking gate follows. The Postgres suites keep running on their
schedule, as `scripts/test-postgres.sh` and the difftest runner do today.

## 7. Scope changes and the author's decisions

`NOT-DOING.md` currently says: "One hosted target, SQLite in the production
CLI … A separately enabled Postgres evaluation adapter is not a
hosted/deployable target." Enacting this RFC needs a Moves line for each of
the following:

1. **Production Postgres in the CLI** (child A, P1). LLP 3000.009 ruling 7
   commissioned C3 and admitted Postgres as a production target; this line
   enacts that ruling.
2. **Graduation** (child B). It is new: LLP 3000.009 §4.5 named an "explicit
   export and import", not a live move.
3. **The scale program and its controls** (child C), including a Convex
   self-hosted deployment and a self-hosted Supabase stack on fleet machines.
4. **The optimistic committer (a)**, commissioned by the author on S0's
   evidence (§3.3). It changes the SQLite writer too. The serial batch (0) is part of
   P0 and needs no separate line.
5. **More than one serving process** (P2), when commissioned.
6. **Log retention**, when commissioned. It follows LLP 3000.002's proposal
   for coordinated history, receipt and principal retention (an authority
   checkpoint plus a floor), not deletion below a floor (child A §7.3).
   Until then both stores keep the whole log.

Questions for the author:

- **Is P1's single serving process with a fenced standby enough to call
  Postgres a production target?** This RFC says yes for the topology. But
  §3.3 rules out production on the lock-first reference, so the label in
  practice waits on (a) landing, or on your restating the write bound
  (round 3, Fable). P1b alone is not the production milestone.
**The author's rulings (2026-10-19):**

- **Failover: "every promotion is a new incarnation" is rejected.** The
  author called it silly and asked for a fix.
  - Revision 4's first fix, an asynchronous proof of continuity with narrow
    repair, did not survive round 4.
  - Revision 5's fix: in the lossless HA modes, which every recommended
    managed configuration provides, failover keeps the incarnation and is a
    reconnect. Only an `async` deployment faces the choice, and its operator
    makes it.
  - Making `async` both safe and seamless would need a synchronous external
    anchor on every commit. That is recorded as a separate path (child A
    §5.4.4).
- **The optimistic committer (a) is commissioned**, "unless there are
  realistic alternatives". The alternatives were weighed against S0's
  measurements. None reaches 1,000 commits/s and 25% of raw Postgres at a
  managed RTT:
  - *Cut `k`, the round trips inside the lock.* Prefetch-style batching and
    a one-statement tail plausibly take 12 round trips to about 4, which is
    about 500/s at 0.5 ms. It is worth doing anyway, and (a) benefits from
    it.
  - *Co-locate the server with Postgres.* About 990/s over a Unix socket,
    but managed Postgres does not allow it.
  - *Run the interpreter inside Postgres as an extension.* One round trip
    per mutation, but managed providers do not allow custom extensions, and
    the head stays serialized.
  - *(b), database concurrency with a correct ordering protocol.* Comparable
    complexity to (a). It still needs the contiguous-prefix publication and
    exact-snapshot design that no one has written.
  - *Ship P1 with a documented ceiling and defer (a).* About 120–220
    commits/s at in-region RTT, which is enough for many applications. It
    is the fallback if (a) slips; it is not the plan.

  The build follows child C's S1a sizing.
- **Restate child C's sizing bound?** It is 1,000 commits/s and 25% of raw
  Postgres at 0.5 ms with a 2× margin. You may restate it before S1a runs,
  not after.
- **Should child C's controls be built by fresh agents under the benchmark
  protocol, or by the lead with each control's design reviewed by an advocate
  for that system?** Child C §4 recommends the second, because this is a
  measurement of systems, not of builders.

## 8. Not proposed

- Lowering Quarry to SQL, typed physical layouts for managed data, or SQL
  writes to managed tables (LLP 3000.009 §12 stands). Child C names the
  evidence that would reopen the first two.
- Postgres on a device.
- Logical replication or WAL decoding as the source of the partition log.
  Child A §6 records it as an alternative for commit ordering and sets it
  aside.
- Multi-region, sharding, or several logical stores in one commit order.
- A claim that Snapback 4 on Postgres is faster than on SQLite.
