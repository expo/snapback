**Author:** Codex (for Charlie Cheever)
**Date:** 2026-09-14

**Related:** [LLP 3000.008](./3000.008-holistic-product-excellence.rfc.md), [LLP 3000.001](./3000.001-durable-replica-and-write-lifecycle.research.md), [LLP 3000.007 §8](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md#8-the-client-seams-the-runs-hit), [LLP 3000.008.001](./3000.008.001-understandable-data-placement.rfc.md), [the client contract](../snapback4/packages/snapback4/src/contract.ts)

## Summary

The ordinary client should carry the information and lifecycle guarantees an
application needs from the underlying system. A builder should not add a
second query to recover a mutation result, join raw rows just to show pending
state, or discover that downloading the device runtime is a prerequisite for
opening an otherwise durable offline store.

LLP 3000.007 already proposes several repairs. This child supplies their
composition rules and acceptance cases. A small card remains the goal; small
vocabulary alone does not establish a complete product contract.

## 1. Evidence and attribution

| Observation | Evidence and interpretation |
| --- | --- |
| A server mutation returns a value that the client does not expose | `Client.mutate<A, R>` returns `Promise<Write>` and `Write` has no result field. The [Grok attribution audit](../benchmarks/runs/2026-09-13-snapback4-clique-0004/grok-client-attribution-audit.md) identifies a documented limitation, including the DM-reuse workaround. |
| A decorated history row loses `pending` | The [shape audit](../benchmarks/runs/2026-09-13-snapback4-clique-0004/m6-pending-shape-audit.md) finds behavior consistent with schema-column projection. It still forced extra application composition. |
| Offline reopen depended on runtime bytes being available | The [Astra essay](../benchmarks/runs/2026-09-13-snapback4-clique-0004/astra/essay.md) records application persistence of the pinned wasm. `webDevice({ wasm })` accepts bytes, but the default opener does not durably cache them. |
| An id-only video argument fails during local prediction | The [P1 report](../issues/20260913-snapback4-video-id-only-prediction-refuses.md) records local `E_FIELD` versus authoritative success. This is a received reproduction, with its independent-validation limit retained. |

Session rotation, stale-response handling, observation recovery and repeated
prediction have already received substantial fixes. Their resolved tickets
are regression evidence, not a new list of open defects. The objective is
to make these behaviors compose through the public client and real hosts.

## 2. Authoritative mutation results

Recommend a typed authoritative result on a successful `sent` outcome,
propagated through `mutate`, React's `run`/`last`, and the terminal notification
path for a write that initially returned pending. The generated mutation's
result type must reach the caller instead of being discarded.

A predicted result, if exposed, is explicitly provisional. It may contain a
client-minted ID while the authoritative operation returns an existing entity,
as in create-or-reuse DM. Navigation or irreversible follow-up actions must be
able to distinguish those results without querying around the client.

An acknowledgement lost after commit must not cause a rerun with a fresh ID
or a different authoritative result. Replay and deduplication must reproduce
the admitted operation's recorded outcome under the existing access policy.
Keep result size, storage cost, retention and principal ownership explicit.
Do not expose a previous viewer's result after a session switch.

This requires a deliberate card change, not just a React convenience method.
The exact generic `Write<R>` and listener shape remain a decision. Discovering
an outcome long after its outbox entry has retired remains the broader open
question in LLP 3000.001; this first change must state its retrieval window
without promising an unbounded result history.

## 3. Pending state through useful projections

Provide a first-party way for a row-based projection to preserve the originating
row's pending state. The normal decorated-message query should be sufficient
to render both content and local settlement state.

Recommend compiler-tracked row provenance for a projection that keeps a base
row, with inferred client metadata attached through that provenance. Settle
whether `*` includes it or an explicit projection form requests it. Keep the
existing distinction between schema columns and device-owned metadata clear.

The rule cannot be mechanical propagation to every object. A joined author's
pending state is not the message's state. An aggregate, a flattened object
assembled from several rows, or a scalar has no single obvious originating
row. Define these cases, field-name collisions and generated types explicitly;
do not silently choose whichever row happened to be visited last.

No application mutation may forge authoritative settlement by writing a
`pending` column. Refusal restores the confirmed base and replays surviving
writes; the resulting metadata follows those actual predictions. Snapshot
replacement and delayed acknowledgements must not cause an already observed
authoritative write to become pending again.

## 4. Startup and package ownership

The browser opener should retain the compatible device runtime needed to
reopen its persisted backend, with version/content identity and atomic
installation. On reconnect, a new backend and its runtime cannot leave the
store requiring a half-installed or unavailable module. Cache failure or
eviction must produce an understandable startup failure without deleting
queued writes or claiming an offline capability that is absent.

Test reopening in a new JavaScript realm with the network blocked, not only
reusing an already initialized module. Test failed downloads and an interrupted
upgrade. Measure download, compilation, opening persisted rows and first query
separately through the performance child.

The platform can own its device module; an application still owns making its
web shell available offline. The published recipe must make that division
explicit. Caching a wasm module alone is not proof that a browser can load
the application's HTML and JavaScript with no network.

For native clients, keep startup compatibility checks against the actual
installed module, clear rebuild guidance and cleanup of failed opens. A
JavaScript refresh cannot replace an installed native binary. Reference
templates should exercise supported web and native package combinations.

## 5. Asset arguments and media lifetime

After a successful upload, a mutation accepting the documented `{ id }` form
must reach authoritative validation even if prediction lacks duration,
dimensions or other server-established facts. Recommend safe degradation to a
durable unpredicted write when those facts are not held. Predicting from
authenticated cached upload facts is an optional optimization.

Caller-supplied extra fields never become authority for ownership, kind, size,
placement or dimensions. The server resolves those facts and rejects forged
or unauthorized assets as today. A local missing fact is not evidence that a
valid server mutation should fail before being sent.

Ordinary media caching has a different lifetime from one-view consumption.
Keep authenticated access, home removal, revocation and principal cleanup
explicit in the recipe. This proposal does not make one-view content durable,
weaken `private, no-store`, or infer that caching the data replica caches every
media byte. A general asset-cache API is a separate design choice if repeated
application work demonstrates the need.

## 6. Session and observation composition

The normal provider and hooks should survive Strict Mode replay, late opens,
close during work, pagination changes, credential rotation and sign-out.
Returned mutation outcomes, observation state and native asset headers must
refer to the same current session or to a clearly retired request.

Use the existing corrected paths and regression tests. Expand them only for
interactions introduced by the proposed result, provenance and startup changes.
An obsolete bearer response must not settle a durable write incorrectly or
leave a live observation permanently denied after successful rotation.

Development persona ergonomics and safer diagnostic explanations can be
improved through the existing tools. Do not relax deployed auth admission
limits or disclose a hidden unique key to make a benchmark easier.

## 7. Acceptance examples

1. Create-or-reuse DM returns the authoritative ID through the ordinary hook,
   including a delayed acknowledgement and a retry of the same write ID.
2. One decorated history query renders pending state, then settlement or
   refusal, without a raw-row companion query. Nested joins do not misattribute
   another row's state; generated types match the chosen provenance rule.
3. A fresh browser realm opens an already initialized device offline using
   retained runtime bytes. An unavailable app shell is separately identified;
   interrupted runtime installation preserves the old usable state and outbox.
4. Id-only image and video arguments are admitted and authoritatively judged
   on browser and native clients. Forged metadata cannot bypass asset rules.
5. The new outcome and metadata paths preserve the corrected rotation,
   sign-out, close, pagination and overlapping-write behaviors. Assertions use
   the actual client, hooks and device implementations.
6. A cold application builder uses the supported template and these APIs
   without introducing its own outbox, mutation-result polling or module cache.
   The application's remaining shell and media responsibilities are documented.

## 8. Open decisions

Decide the minimal typed result extension, whether to expose predicted values
in the first change, the row-provenance projection form, and result/runtime
retention limits. Coordinate the offline non-value with LLP 3000.008.001.
Extend LLP 3000.007 §8 with the accepted choices and current-surface examples
when implementation is commissioned. No public contract changes in this draft.
