## Summary

The client should carry the information and durability boundaries the
application relies on. Fresh mutation results, shaped pending metadata,
runtime caching and id-only media support already shipped. The selected
residuals are truthful replay results and verified recovery from browser
persistence or startup failure.

## 1. Evidence and attribution

The [contract](../snapback4/packages/snapback4/src/contract.ts),
[client seams tests](../snapback4/packages/snapback4/test/client-seams.test.mjs)
and [IndexedDB witness](../snapback4/witness/idb.mjs) establish those delivered
mechanisms. The original missing-result/cache/video observations describe an
older package; they are not new open defects.

The remaining [replay type defect](../issues/closed/20260914-snapback4-write-result-type-omits-replay-state.md)
is different: the accepted server receipt withholds a result, while `Write<R>`
and both clients promise one. Browser source also exposes hypotheses about
drain-before-save, failed-open cleanup and invalid runtime installation;
those require reproduction before repair.

## 2. Authoritative mutation results

A fresh successful `sent` outcome carries the server's typed result, including
a legitimate null. A successful replay carries execution identity and
`replayed: true`, **without** a historical result. Represent these as a
minimal discriminated union and preserve the distinction through both clients,
`onWrite` and React `run`/`last`. A caller narrows result availability before
using a returned ID. Pending outcomes expose rows, not predicted results.

[LLP 3000.007 §17](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md#17-the-second-blind-pass-the-implementation-of-87-and-59-2026-09-14)
is authoritative: the at-most-once record cannot grant historical read
access, including scalar values. Never restore a cached result after revocation
or rerun with a fresh write ID to recover a lost acknowledgement. The original
wish to always recover the same DM ID is withdrawn; after an execution-only
receipt the application may make a newly authorized read.

Live terminal notifications are not unbounded result history. Stable operation
identity and no duplicate authoritative effect are required; value recovery
beyond that boundary is not promised.

## 3. Pending state through useful projections

Row-based shapes already preserve originating pending metadata through spreads
and further shapes. Retain that rule, its generated types and corrected replay
behavior. A joined author's pending state must not replace the message's.
Aggregates and unrelated objects do not acquire an invented origin.

Add a regression if a concrete misattribution is found; do not build a new
provenance algebra merely because the old draft proposed one. Application
columns cannot forge authoritative settlement.

## 4. Startup and package ownership

`webDevice()` already owns durable runtime bytes keyed by digest. The app owns
its offline shell. A fresh JavaScript realm with network blocked, not a warm
module reused in one test, establishes offline-runtime availability.

A failed persistence transaction must not leave the live wasm device reporting
uncommitted state as durable. Recover from the last persisted backend and rows,
or fail explicitly if they cannot be reopened. Previously acknowledged outbox
entries remain intact. Successful calls should not copy the entire store to
prepare for a hypothetical failure.

Failed initialization releases its device and lock, including failure during
initial persistence or orphan adoption. An orphan's durable source is removed
only after its destination admission commits. Validate a runtime before
promoting its bytes/pointer atomically; an invalid or interrupted installation
must not replace a known usable entry or erase queued work. Cache eviction is
an explicit offline-startup limit, not authority to destroy the outbox.

Native clients retain installed-module compatibility checks and rebuild
guidance. Reloading JavaScript cannot replace their binary.

## 5. Asset arguments and media lifetime

Id-only images/videos and cached upload facts are already exercised by the
current client-seams tests. Preserve safe unpredicted admission when facts are
missing and authoritative server validation of caller-supplied metadata.
Ordinary viewed-media retention stays separate from one-view consumption,
revocation and principal cleanup. This increment adds no media-cache API.

## 6. Session and observation composition

Use the actual client and hooks to verify the new replay and persistence paths
beside corrected rotation, sign-out, close and overlapping-write behavior.
An old bearer response cannot settle a new session's writes. Recovery must
serialize concurrent calls and must not make `close()` race a reopened device.

## 7. Acceptance examples

1. Fresh object and null results are distinguishable from execution-only
   replay in both runtime values and generated TypeScript use. Same-ID retry
   after a lost acknowledgement applies once; hooks/notifications retain the
   replay distinction and existing revocation tests stay green.
2. An injected failed save on the actual wasm device produces no falsely
   durable outcome; a subsequent call/reopen uses the last committed state.
   Earlier durable queued writes survive, including concurrent calls/close.
3. Failed initial save or orphan adoption releases owned resources and leaves
   recoverable source data. Invalid runtime or failed cache promotion cannot
   poison a prior usable installation.
4. A real browser exercises the relevant IndexedDB abort/lock boundary and a
   fresh-realm offline reopen. Report adapter-only evidence separately.
5. Current pending projection and asset regressions remain intact; the package
   documents replay availability and app-shell/runtime ownership together.

## 9. Implementation evidence

Four online/process and immediate/queued replay regressions failed before the
union correction; 25 focused runtime, TypeScript, hook and disclosure tests
passed afterward. Fresh null remains a value, replay has no result property,
and neither client restores historical read access.

Actual wasm fault tests reproduced uncommitted state after a failed save and
startup resource leaks. Recovery discards the live device on failure and
restores only from persisted rows on the next serialized call. The Chromium
IndexedDB witness aborts transactions, checks lock release, preserves earlier
durable outbox entries and reopens offline in a fresh realm.

A further cache-retry reproduction used a real runtime with one incompatible
import: wasm-bindgen's initialized-instance shortcut could otherwise accept
uncached replacement bytes without linking them. The installer now retains
the initialized content identity after a failed cache save. Identical content
can retry; a different runtime requires page reload before installation. Six
wasm durability tests and the browser witness pass, including zero runtime
fetches on fresh offline reopen. No extra device instance or whole-store copy
was added to a successful call.

The native acquisition repair ships in `snapback4-expo@0.2.5`; rebuild the
native application to include it. The existing receipt-protocol probe checks
wire compatibility, not whether every bug fix is present in an older module.
A JavaScript-only upgrade cannot change that older Rust implementation.
