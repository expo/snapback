## 1. Summary

A pre-executed member's outcome depends only on what it read. Suppose no
member committed after its snapshot wrote anything it read. Then executing
it now, at its commit position, would read the same values and produce the
same outcome. That is backward validation in the style of Kung and Robinson.
It makes the committed history serializable in revision order, which is
exactly the replay oracle of the parent RFC's §3.5.

This RFC defines four things:

- what a **read set** records;
- what a **footprint** records;
- how the two are **intersected**;
- how the result is qualified.

The same read sets later let live queries be invalidated by key rather than
by table.

## 2. Where reads are recorded

Reads are recorded **at the boundary**, inside the recording wrapper the
overlay uses, not in the `Runner`. Today `Runner::read_tables` keeps only
table names (`runner.rs:131`), and the interpreter reaches the store from
many sites. Every read that can influence an outcome passes through one of
three places:

- `Rows`;
- `PartitionRows`;
- a durable-state family operation (parent RFC §3.2), such as the
  authority facts an operation is admitted under.

Recording there is complete by construction for those calls. Completeness
is also checked, not assumed (§6).

Every fact a member depends on is read **inside its snapshot S**, through
the recorder (parent RFC §3.6). That includes the admission facts the
reference reads before its program today: session validity, principal
generation, the receipt's absence, asset-intent placement, and the clock
floor. None is carried in from an earlier snapshot.

The pre-execution handle exposes only the recorded interfaces, so a
raw-SQL read cannot compile into a pre-executed path. Members that frame
their work in raw SQL run in place until they are decomposed (parent RFC
§3.2).

A few inputs are **transcript inputs, not reads**, recorded for replay
(parent RFC §3.5):

- ids minted at admission;
- presence observations, which never commit (parent RFC §4.6);
- chunk and yield decisions;
- the schema generation, which is checked, and whose change conflicts with
  everything.

## 3. Read sets and footprints

All keys are in the store's order-preserving encoded key space, per
`(table, index)`, so intervals compare as bytes. Two kinds of dependency are
kept separate (round 1: Astra F1, Grok F2):

- **Membership**: which keys exist in an interval;
- **Content**: what an observed row's image is.

| Read | Read-set entries | Conflicts with a footprint that… |
| --- | --- | --- |
| `get(table, id)`, present or absent | `Row(table, id)` | writes or deletes that row |
| `lookup(table, index, key)` | `Span(table, index, prefix interval of the logical key)` for membership, because stored keys append the row id. Plus `Row(table, id)` for the image it returned | adds or removes any key in the interval; or writes the returned row, including a non-key update that leaves every index entry untouched (`store.rs:678–688`) |
| `scan(…, bounds, dir, limit)`, `scan_metered`, `scan_selected` | A **directional span**: from the bound the walk started at, through the last key examined, plus the one successor position past it in the walk direction. For an ascending walk that is `[lo, next(k_stop)]`; for a descending walk, `[prev(k_stop), hi)`. An unstopped walk covers its whole bound. Plus `Row` for **every row image the walk examined**: returned rows, and rows a rule or expiry check examined and then hid or filtered. Their sizes also decide a meter cut | adds or removes a key inside the span, which covers phantoms on the side the walk crossed; or writes any examined row |
| `count_prefix(…, limit)` | `Span` of the prefix up to the limit-th key, or the whole prefix if the count did not saturate | adds or removes a key in it |
| `index_head(…, dir)` | `Span` from the walk's starting bound **through** the head (round 1: Grok F1, Fable): a new key between the bound and the head changes the head | adds a key in that span, or removes the head |
| `sequence_value(parent, id)` | `Seq(parent, id)`, unless it is an allocation (parent RFC §4.5), which is not a read | sets that sequence |
| `cap_count`, and maintained totals read only to compare | `Pred(kind, key, predicate, my delta)`: a predicate read, re-evaluated at validation against the current value plus the batch's accepted deltas (parent RFC §4.5) | makes the predicate false |
| `cap_count`, read otherwise | `Cap(table, key)` by value | changes that occupancy |
| `effect_once(effect, key)` | `EffectKey(effect, key)` | claims that key |
| Receipt check for `(principal, op id)` | `Receipt(principal, op id)`, absent (round 1: Grok, Fable, Muse) | records that receipt |
| Admission facts: session by digest, principal generation, family member, work record, asset-intent placement | `Auth(kind, key)`, `Intent(id)` | invalidates, mints, revokes, or places under that key |
| Clock floor, time-audience pending or published | `Time(clock)`, `Time(audience, key)` | advances the floor past the member's effective time, or publishes under the key |
| Asset reads | `Asset(id)` | claims or releases it |

**Footprints.** A member's footprint lists everything it wrote:

- each written or deleted row, as `Row`, including non-key updates;
- each index key it added or removed, old and new keys alike, as `Key`;
- each sequence, cap, effect key, authority fact, time-audience and asset
  record it changed, under the same names.

Monotone time-audience pins are excluded (parent RFC §6). A schema
generation change is a wildcard. Footprints come from the overlay's write
set for pre-executed members, and from the adapter's recorded writes for
in-place members, so every member has one.

**Precision rules.**

- **Coarsening is always safe.** Replacing an entry with a superset, such
  as a whole index or a whole table, can only add conflicts. A read set that
  exceeds its size bound coarsens per table. Meters bound reads, so this is
  rare.
- **Hidden rows count.** Rows a rule reads and then hides, or a scan
  examines and filters, still determine the outcome. They are recorded like
  any other.
- **Prefetch is physical.** A prefetch fill is not a read. Only the
  interpreter's logical calls are recorded.

## 4. The window and the intersection

The committer keeps, for revisions newer than the oldest live snapshot:

- per `(table, index)`, an ordered map from encoded key to the latest
  revision that added or removed it;
- per row, a map from `(table, id)` to the latest revision that wrote it;
- similar maps for each other footprint kind.

Validating a member with snapshot S and read set R:

- a point entry (`Row`, `Seq`, `Receipt`, `Auth` and the rest) looks up its
  key and conflicts if the latest revision is greater than S;
- a span entry runs an ordered range query over its directional interval,
  and conflicts if any key in it has a revision greater than S;
- a predicate entry re-evaluates its predicate against the current value,
  meaning the committed value plus the deltas of the members already
  accepted in this batch;
- the members already accepted into the current batch are folded into the
  same maps before the next member is validated (parent RFC §3.4), so a
  batch is one serial image.

The cost is `O(|R| · log n)` plus the matched keys. The window is bounded by
snapshot age (parent RFC §4.4); older revisions are pruned.

## 5. Reuse: live invalidation by key

Today a watched query re-runs whenever a commit touches a table it read
(LLP 3000.009 §7.1). Child C predicts this is the limit that will bind
chat-shaped workloads (H3).

A watched query's read set has the same shape as a member's. So the server
can keep each live observation's read set and notify only observations
whose read sets intersect a commit's footprint.

- Read sets and footprints stay on the server, because a key can name a
  hidden row.
- The client still learns only "re-run this query".

This is increment E. It reuses this RFC's machinery, but it is commissioned
separately on child C's W6 evidence.

## 6. Qualification

1. **Recording completeness: a census of sites, not methods** (round 1:
   Muse F1).
   - A static census enumerates every outcome-influencing read site
     reachable from a pre-executed member, including raw SQL. The store-port
     ratchet's matcher (P0-S0) finds the direct-SQL sites.
   - Every trait method, defaulted ones included (`holds_assets`,
     `time_audience_published`, `acquired_boundary` and the rest), must
     either map to an entry kind or be refused on the pre-execution handle.
   - An instrumented build asserts that every call crossing the handle
     produced an entry.
   - A new site or method without a mapping fails the build.
2. **The validation adversary.** For each read kind in §3, the generator
   produces a mutation whose outcome depends on that read, and a second
   mutation that changes it. The second commits between the first's
   snapshot and its validation, and the first must fail validation. A
   control pair whose writes miss the read must pass. Kinds covered:
   - present and absent;
   - in range and just outside it, on **both sides** of a directional
     span;
   - ascending and descending walks cut by their limit, and cut by the
     meter;
   - a non-key update of a looked-up or scanned row;
   - a change to a hidden row;
   - `index_head` from both sides;
   - receipts;
   - each admission fact;
   - the clock floor;
   - predicates exactly at the cap boundary.

   This runs on both stores.
3. **The replay oracle** (parent RFC §8.1) checks the end-to-end property
   under random concurrency.

## 7. Alternatives

- **Table-granular read sets.** Simple, but every concurrent reader of a
  busy table would conflict. That defeats pre-execution exactly where it
  matters, and it is what round 2 rejected.
- **Database-side conflict detection.** Postgres SSI detects phantoms
  through predicate locks. But execution would then happen in read-write
  serializable transactions, which need write connections. It would not
  exist on SQLite. On Snapback's generic layout it sees physical index
  ranges rather than the interpreter's logical reads, and it would also
  conflict on prefetch's over-reads.
- **Recording in the `Runner`.** The `Runner` misses the reads that rules,
  maintains, constraint checks and family operations make through other
  paths.
