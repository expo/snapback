# Roomwright — a multi-tenant resource booking system, and what it does to the ladder

**Archetype:** resource booking and scheduling. Organizations own resources (rooms,
equipment, clinicians); members book them; bookings can be cancelled, rescheduled,
waitlisted, and recurred.

**Answer in one line:** the ladder survives as far as it goes, but it is calibrated on
the wrong axis. Its four rungs vary *how many rows you read* (`take` at 1, N, N+count,
N+fan-out). Every hard mutation in this app varies *how you address them* — by range
and by rank, not by key — and half of them are blocked on a **write** shape the ladder
does not discuss at all. Rung A and my hardest read are both `take(1)`. One is
reachable and the other is not.

**The most useful individual finding is §2.3**, and it is good news rather than bad: I
predicted that the overlap check races under row-granular read-set capture, checked the
kernel, and found the opposite — range-granular capture is shipped and
predicate-complete, and plan steps execute *inside* the commit transaction, so a
declarative range read would be serializable by construction where the JS handler doing
the same job needs conflict validation to be safe. That is a concurrency-correctness
argument for the declarative read tier that the corpus has not made, and it makes rung E
cheaper than `ANSWER.md` §5 costs it. It also required withdrawing my own headline; see
Confidence.

Sources checked, not assumed: `guide/backend/declarative-plans.md` (the complete step
and expression vocabulary), `packages/snapback-codegen/define.mjs`,
`crates/snapback-kernel/src/storage.rs`, `crates/snapback-kernel/src/live_matcher.rs`,
`crates/snapback-types/src/storage.rs`, `demos/messaging-snapback/snapback/schema.mjs`,
`packages/snapback-codegen/ctx.d.mts`. Where I am guessing I say so.

# Part 0 — Two corrections to the brief, made before the argument depends on them

**(a) There is a string-length operator.** BRIEF3 and LLP 0329.008 both say the
expression vocabulary has none. `guide/backend/declarative-plans.md` §"The pinned
function library" lists `call(name, ...)` admitting exactly `len, trim, lower, abs,
min, max, round, floor, ceil, coalesce`. `call('len', arg('handle'))` is available.
The two `coterie` mutations 0329.008 flags for this reason are not blocked on it. This
does not change the ladder; it does mean one of the two "smaller gaps" is already
closed, and it is the kind of error that comes from reading the census instead of the
generated vocabulary.

**(b) The mutation IR already contains a range-predicate, visibility-composed,
multi-row scan.** `deleteWhere(table, filter)` is not an equality construct.
`crates/snapback-kernel/src/storage.rs:6344` executes it by building a full
`QueryPlan { table_visibility, filters, membership_filters, order, limit, indexed_by }`
and handing it to `build_query_sql` — the same builder the read path uses — with the
comment *"Reuse the query WHERE builder so DeleteWhere filters share matcher/SQL
semantics with reads."* The filter vocabulary is therefore the query filter
vocabulary: `eq`, `ltFilter`, `lteFilter`, `gtFilter`, `gteFilter`.

So today a plan **can** say "delete every booking for this series starting after now"
as one range-filtered, visibility-composed set operation. It **cannot** say "is there a
booking for this resource overlapping this interval." The IR can range-delete but not
range-read. The proposed bound read (`unique(table, index, key, bindAs)`, LLP 0329.007
§Open question 1, carried forward by 0329.008) would ship with a **strictly weaker
predicate language than the delete step that already ships**. That is not a
feature-gap argument, it is an incoherence argument, and it is the cheapest thing on
my list to fix.

Note also that this `QueryPlan` is constructed with `limit: None`, `order:
Vec::new()`, `indexed_by: None`. The set-oriented step that exists today is unbounded,
unordered and unindexed — which is worth knowing before "every bound is authored" is
used as a cost argument.

# Part 1 — The app, its invariants, and the trap

## 1.1 Invariants, in plain language, before any code

- **I1 — No double booking.** For one resource, no two *calendar-live* bookings may
  have overlapping **exclusion intervals**. The exclusion interval is the occupancy
  interval widened by the resource's setup and teardown buffers. Half-open: `[s, e)`
  overlaps `[s', e')` iff `s < e' ∧ s' < e`.
- **I2 — Cancellation frees, but does not erase.** A cancelled booking stops blocking
  the calendar *immediately and in the same commit as the cancellation*, and its row
  survives forever with the reason, the actor, and whether it was late.
- **I3 — The cancellation cutoff is not gameable.** Whether a cancellation is "late" is
  decided against a start time that the holder cannot move. Rescheduling a booking must
  not launder a late cancellation into a free one.
- **I4 — Calendar-liveness is a fact about the clock, not only about the stored state.**
  A hold whose expiry has passed does not block, whether or not anyone has written to
  it. A confirmed booking whose end has passed is history, not a future commitment.
- **I5 — Waitlist promotion is atomic with the release that caused it, and is in
  order.** When a slot frees, the *earliest-positioned entry that actually fits the
  freed window* is offered it, exactly once, in the same commit. Two concurrent
  cancellations must never promote the same entry twice, and must never skip an entry.
- **I6 — Quotas count live things only.** "At most 5 concurrent bookings per member"
  counts confirmed and unexpired-held future bookings — not cancelled ones, not past
  ones.
- **I7 — Penalty history is append-only and is the input to a suspension rule.** Three
  late cancellations or no-shows in 90 days suspends booking. Ledger rows are never
  patched or deleted; a reversal is a compensating row.
- **I8 — A recurring series is a rule *and* its materialized occurrences, and the two
  must not disagree.** Cancelling one occurrence must not end the series; ending the
  series must not erase past occurrences or the individual cancellation reasons already
  recorded on future ones.
- **I9 — Policy is frozen onto the booking at write time.** Changing a resource's
  cancellation cutoff, fee, or buffers must not retroactively change the terms of
  bookings already made.
- **I10 — Authorization is org-scoped; occupancy is resource-scoped.** Every read must
  be scoped by org membership; every overlap check is keyed by resource. These are
  different keys on the same row and both must hold.
- **I11 — A booking outlives the membership that authorized it.** Removing a member
  from an org must leave no booking that occupies a resource while being invisible to,
  and uncancellable by, its holder.
- **I12 — Waitlist position is a rank, and ranks do not renumber.** Withdrawing entry
  #3 must not rewrite entries #4…#40.

## 1.2 The trap — five of them, ranked

The brief asks for the analogue of `coterie`'s active-versus-historical membership.
`coterie`'s problem was that **visibility became a function of time** — "can you see
this message" depends on when you joined and when you left — and the single-hop
membership grammar can only express *current* membership.

Booking has the same shape one level deeper, and I found five. **T1 is the real
analogue** and it is the one I did not expect.

### T1 — The clock is a writer that nobody declared

Six states: `held → confirmed → completed`, with `cancelled`, `no_show`, `released` as
exits. **Three of the transitions have no writer.**

| Transition | Caused by |
|---|---|
| `held → expired` | `holdExpiresAt` passing. No row is written. |
| `confirmed → completed` | `end` passing. No row is written. |
| `confirmed → no_show` | `end` passing with `checkedInAt` still null. No row is written. |

A naive design stores `state` and treats it as authoritative. It is not. Between the
instant a hold expires and the instant a sweep job notices, the row says `held` and
`blocksCalendar: true` while the truth is that the slot is free. Every read of
`state` is **stale by construction**, and the staleness window is however long your
cron interval is.

This is worse than `coterie`'s cutoff in one specific way. `coterie`'s trap made a
*visibility* predicate time-dependent, and the failure mode was a wrong screen. Here it
makes the **write invariant** time-dependent, and the failure mode is a room that is
occupied by nothing, or a booking that is refused for no reason.

Three consequences that bite the model directly:

1. **The overlap check cannot be `take(1)`.** It should be — the invariant I1 makes the
   nearest predecessor sufficient (proof in §2.1). But because expired holds still carry
   `blocksCalendar: true`, the first row returned may be a corpse, and so may the second.
   You must overfetch by however many corpses you are willing to tolerate, and **that
   number is not derivable from anything in the schema.** LLP 0329.008's cost argument —
   *"the bound is already authored… inherited rather than invented"* — does not hold here.
   The bound is a guess about garbage-collection lag.
2. **The equality-keyed read the ladder proposes returns rows the app must then
   re-filter by a clock comparison.** So even the reads that *are* equality-keyed are
   followed by a range predicate over a binding, which no expression in the vocabulary
   can apply as a filter (`cond` selects a value, it does not select rows).
3. **The honest fix is to stop storing the derived fact.** Do not store `state`; store
   the facts that cause it (`confirmedAt`, `cancelledAt`, `holdExpiresAt`,
   `checkedInAt`, `end`) and *derive* liveness in the predicate. But indexes name
   authored fields only (`guide/backend/queries.md`: "Indexes name authored table fields
   only"), so a derived liveness cannot be an index prefix, so the overlap read cannot
   use an index. You are forced back to materializing the derived value and maintaining
   it by hand. **The schema language makes the correct design unindexable.**

### T2 — Reschedule launders the cancellation window

The exploit, which is real and which I have seen in production systems:

1. Booking starts in 30 minutes. The cutoff is 24 hours. Cancelling now costs the fee.
2. Instead, **reschedule** the booking to a date three months out. At the moment of the
   reschedule, is that late? If you check the cutoff against the *new* start, it is not
   — the new start is 90 days away.
3. Next week, cancel the rescheduled booking. It is 83 days out, comfortably outside the
   cutoff. Free.

The late cancellation has been laundered through a reschedule. The fix is that the
cutoff must be measured against a **frozen policy anchor** that a reschedule can only
advance when the reschedule itself was outside the cutoff:

```js
policyAnchorStart: wasLate ? b.policyAnchorStart : args.newStart
```

Which means the booking row carries a start time that is *not* its start time, exists
only to answer a policy question, and must be immutable-except-under-a-condition.
Nothing in the schema language can express "immutable except under a condition,"
and nothing can express "immutable" at all.

### T3 — "Cancelled must not block" becomes a derived boolean in an index prefix

I1 says only calendar-live bookings block. So the overlap index must exclude cancelled
rows. Snapback indexes are ordered field lists and the range column must be last, so
the state discriminator has to sit in the prefix:

```
.index('by_resource_blocking_exclusion', ['resourceId', 'blocksCalendar', 'exclusionStart'])
```

It cannot be `state` directly, because **two** of the six states block (`held` and
`confirmed`) and an index prefix is one equality value. So the app must carry a derived
column `blocksCalendar` whose only definition is `state ∈ {held, confirmed}`, and must
maintain it by hand on every one of the six transitions. There is no `.derived()`, no
check constraint, and no way to declare the relationship. **The single most
safety-critical column in the app is an unenforced denormalization of another column in
the same row.**

The same gap appears in uniqueness. `messaging-snapback` dedups reactions with
`.index('by_message_user_emoji', [...], { unique: true })` — the trick works because a
reaction never enters a dead state. Every uniqueness constraint in *this* app is
partial: "one **waiting** waitlist entry per (resource, holder)," "one **live**
check-in per booking." `{ unique: true }` is total. Postgres would write
`CREATE UNIQUE INDEX … WHERE state = 'waiting'`. Snapback cannot, so partial uniqueness
falls back to read-then-check — the exact `filtered-read-guards` class that
`defineMutation` refuses.

### T4 — A booking outlives the membership that authorized it (the `coterie` analogue proper)

Alice books Room 3 for next Tuesday. On Friday she leaves Acme. On Tuesday the room is
occupied by a booking that:

- **still blocks the calendar** — the overlap read is keyed by `resourceId` and knows
  nothing about org membership;
- is **invisible to Alice** if `bookings` uses `{ kind: 'membership', resourceField:
  'orgId' }`, because her membership row is gone;
- is **uncancellable by Alice**, because `ctx.permissions.orgMemberships.requireRole`
  refuses her;
- and still accrues a **no-show penalty** to a principal who has no way to act on it.

A ghost booking. The visibility half is fixable with `any-of` (verified available:
`define.mjs:441`, 2–8 arms, each `owner` or `membership`):

```js
.visibility({ kind: 'any-of', arms: [
  { kind: 'owner', field: 'holderId' },
  { kind: 'membership', declaration: 'orgMemberships', resourceField: 'orgId',
    roles: ['owner', 'manager', 'member'] },
]})
```

**But the authority half is not fixable**, and this is the residue worth naming.
`any-of` lets Alice *see* the booking; `requireRole` still refuses her *cancel*. Read
visibility and mutation authority are two separate declarations over the same
relationship, and `any-of` only exists on one of them. Alice can watch her ghost
booking and cannot do anything about it. `removeOrgMember` therefore has to release the
departing member's future bookings *in the same commit as the removal* — an unbounded,
range-selected, set-oriented **patch**, which is precisely the one set-oriented step the
IR does not have (§2.11).

### T5 — Promotion is conditional, ordered, and the eligible entry is usually not the first

Waitlist entry #1 wants a two-hour block. The cancellation frees one hour. Entry #1 is
not eligible; entry #2, who wants one hour, is. So promotion is **"the first entry in
position order whose desired window is contained in the freed window and whose desired
duration fits"** — an ordered scan with a residual predicate that compares three of the
row's own fields against a runtime interval. Not an index predicate at any prefix.

And then, if nobody is eligible, **nothing is written**. The cancellation must still
commit. That is a data-dependent write, and `guide/backend/declarative-plans.md` is
explicit: *"General iteration, data-dependent step skipping, and cross-step control flow
are permanently outside the profile."* `guard` cannot help — it aborts the whole
mutation, so "cancel, and promote if anyone is waiting" would roll back the
cancellation whenever the waitlist is empty.

**Cancellation-with-promotion is inexpressible as a plan for a reason that has nothing
to do with reading.** No amount of climbing the ladder reaches it. That is the finding I
think is worth the most.

## 1.3 Schema

```js
// snapback/schema.mjs — Roomwright.
//
// Eight durable tables. The design decisions worth reading are marked with the
// trap they defend against (T1–T5) and the invariant they carry (I1–I12).

import {
  allow, defineEphemeral, defineSchema, defineTable, ephemeral, v,
} from '@expo/snapback-codegen/define';

export const organizations = defineTable({
  slug: v.string(),
  name: v.string(),
  // Recurrence expands in this zone. A weekly 09:00 series crossing a DST
  // boundary is 09:00 local on both sides, which is not a fixed millisecond
  // offset — so occurrences must be materialized, not computed from a period.
  timezone: v.string(),
  createdAt: v.integer(),
})
  // Deliberately narrow: name and slug only, so an invite link can render
  // before the invitee is a member. Everything else is membership-scoped.
  .visibility({ kind: 'public-read' })
  .index('by_slug', ['slug'], { unique: true });

export const orgMemberships = defineTable({
  orgId: v.id('organizations'),
  principal: v.principal(),
  role: v.string(),
  joinedAt: v.integer(),
})
  .visibility({ kind: 'owner', field: 'principal' })
  .index('by_org', ['orgId'])
  .index('by_principal', ['principal'])
  .index('by_org_principal', ['orgId', 'principal'], { unique: true })
  // Current-only, exactly as messaging-snapback's is. Roomwright does NOT try
  // to model historical membership in this declaration — see I11 and §2.11 for
  // where that decision is paid for.
  .membership({
    id: 'orgMemberships',
    principal: 'principal',
    resource: 'orgId',
    role: 'role',
    roles: ['owner', 'manager', 'member'],
    bootstrapRole: 'owner',
    lastHolder: { protect: 'owner' },
    provenance: 'full',
    transitions: [
      { op: 'insert', by: ['owner', 'manager'], target: 'other', to: ['member'], fields: ['joinedAt'] },
      { op: 'setRole', by: ['owner'], target: 'other', from: ['member'], to: ['manager'] },
      { op: 'setRole', by: ['owner'], target: 'other', from: ['manager'], to: ['member'] },
      { op: 'remove', by: ['owner', 'manager'], target: 'other', from: ['manager', 'member'] },
      { op: 'remove', by: ['self'], target: 'self', from: ['manager', 'member'] },
    ],
  })
  .authorityProfile({
    name: 'orgMemberships',
    hierarchy: { owner: ['manager', 'member'], manager: ['member'], member: [] },
    roster: { visible: ['principal', 'role'] },
  });

export const resources = defineTable({
  orgId: v.id('organizations'),
  name: v.string(),
  kind: v.string(), // 'room' | 'equipment' | 'clinician'

  // Policy. Every one of these is copied onto each booking at write time (I9),
  // because a booking's terms must not move when the resource is edited.
  setupMs: v.integer(),
  teardownMs: v.integer(),
  minDurationMs: v.integer(),
  maxDurationMs: v.integer(),
  maxAdvanceMs: v.integer(),
  cancellationCutoffMs: v.integer(),
  lateCancelFeeCents: v.integer(),
  waitlistCapacity: v.integer(),
  holdTtlMs: v.integer(),

  // Retired, never deleted. A decommissioned room keeps its history, and its
  // future bookings must be released deliberately rather than orphaned.
  retiredAt: v.optional(v.integer()),
  // Bumped on any policy edit; stamped onto bookings so an audit can tell which
  // terms applied.
  policyVersion: v.integer(),
  createdAt: v.integer(),
})
  .visibility({
    kind: 'membership', declaration: 'orgMemberships',
    resourceField: 'orgId', roles: ['owner', 'manager', 'member'],
  })
  .index('by_org', ['orgId'])
  .sync();

export const bookings = defineTable({
  // Denormalized from `resources` solely so single-hop membership visibility can
  // key on it. Nothing in the schema language enforces
  // booking.orgId === resource.orgId. This is the multi-hop tax
  // (LLP 0329.006 §4.2), paid on every child table below.
  orgId: v.id('organizations'),
  resourceId: v.id('resources'),
  holderId: v.principal(),
  // May differ from holderId: a manager books on behalf of a member. The
  // cancellation penalty follows holderId, the audit follows bookedBy.
  bookedBy: v.principal(),

  // 'held' | 'confirmed' | 'cancelled' | 'completed' | 'no_show' | 'released'
  state: v.string(),
  // T3. MUST equal (state === 'held' || state === 'confirmed'). Unenforced.
  // It exists only because an index prefix is one equality value and two states
  // block. This is the most safety-critical column in the app and the schema
  // language cannot say what it means.
  blocksCalendar: v.boolean(),
  // T1. Only meaningful while state === 'held'. A hold past this instant does
  // not block, but no row is written when it lapses, so every reader of
  // blocksCalendar must re-test this against the clock.
  holdExpiresAt: v.optional(v.integer()),

  // Occupancy — what the product shows.
  start: v.integer(),
  end: v.integer(),
  // Exclusion — occupancy widened by the resource's buffers at write time.
  // exclusionStart = start - setupMs; exclusionEnd = end + teardownMs.
  // Materialized rather than computed because indexes name authored fields only,
  // and the overlap read must be indexed. Cost: changing a resource's buffers is
  // an unbounded rewrite of every future booking (§2.10).
  exclusionStart: v.integer(),
  exclusionEnd: v.integer(),

  // T2. Frozen at creation; advanced by a reschedule ONLY when that reschedule
  // was itself outside the cutoff. This is what a late cancellation cannot be
  // laundered through.
  policyAnchorStart: v.integer(),
  // I9: terms frozen at write time.
  cancellationCutoffMs: v.integer(),
  lateCancelFeeCents: v.integer(),
  policyVersion: v.integer(),

  seriesId: v.optional(v.id('bookingSeries')),
  occurrenceIndex: v.optional(v.integer()),

  createdAt: v.integer(),
  confirmedAt: v.optional(v.integer()),
  cancelledAt: v.optional(v.integer()),
  cancelledBy: v.optional(v.principal()),
  cancelReason: v.optional(v.string()),
  wasLateCancel: v.optional(v.boolean()),
  checkedInAt: v.optional(v.integer()),
  rescheduleCount: v.integer(),
  promotedFromWaitlistId: v.optional(v.id('waitlistEntries')),
})
  // T4: the owner arm is what keeps a departed member's booking visible to them.
  // It does not make it cancellable by them — see §2.11.
  .visibility({ kind: 'any-of', arms: [
    { kind: 'owner', field: 'holderId' },
    { kind: 'membership', declaration: 'orgMemberships',
      resourceField: 'orgId', roles: ['owner', 'manager', 'member'] },
  ]})
  // THE index. I1 lives or dies here. Range column last; derived boolean in the
  // prefix because two states block and a prefix is one value.
  .index('by_resource_blocking_exclusion', ['resourceId', 'blocksCalendar', 'exclusionStart'])
  .index('by_holder_start', ['holderId', 'start'])
  .index('by_series_start', ['seriesId', 'start'])
  .index('by_org_state_start', ['orgId', 'state', 'start'])
  .sync();

export const waitlistEntries = defineTable({
  orgId: v.id('organizations'),
  resourceId: v.id('resources'),
  holderId: v.principal(),

  // The window the party will accept, and the length they need inside it. A
  // freed slot is offered only if [windowStart, windowEnd) contains it AND the
  // freed length is at least desiredDurationMs. Interval containment, three
  // fields, no index can express it (T5).
  windowStart: v.integer(),
  windowEnd: v.integer(),
  desiredDurationMs: v.integer(),

  // I12: allocated from a scoped sequence and never renumbered. Gaps are normal
  // and are what makes withdrawal O(1) instead of O(queue).
  position: v.integer(),

  // 'waiting' | 'offered' | 'promoted' | 'withdrawn' | 'expired'
  state: v.string(),
  // T1 again: an offer that lapses returns the entry to the front of the queue,
  // and nothing writes the row when it lapses.
  offerExpiresAt: v.optional(v.integer()),
  promotedBookingId: v.optional(v.id('bookings')),
  createdAt: v.integer(),
})
  .visibility({ kind: 'any-of', arms: [
    { kind: 'owner', field: 'holderId' },
    { kind: 'membership', declaration: 'orgMemberships',
      resourceField: 'orgId', roles: ['owner', 'manager'] },
  ]})
  .index('by_resource_state_position', ['resourceId', 'state', 'position'])
  .index('by_holder_state', ['holderId', 'state'])
  // NOTE what is NOT here: a unique index on (resourceId, holderId). It would be
  // wrong — withdrawing and rejoining is legal. The constraint the app actually
  // needs is partial ("one WAITING entry per resource per holder") and
  // { unique: true } is total. So this invariant is enforced by a read-then-check
  // in joinWaitlist, which is why joinWaitlist cannot be a plan (§2.5).
  .sync();

export const bookingSeries = defineTable({
  orgId: v.id('organizations'),
  resourceId: v.id('resources'),
  holderId: v.principal(),

  weekdayMask: v.integer(), // bitmask, Sun=1 … Sat=64
  startMinuteOfDay: v.integer(),
  durationMs: v.integer(),
  seriesStart: v.integer(),
  // I8 + the recurrence product decision: a series is materialized to a bounded
  // horizon, never "forever". A cron extends the horizon. See Part 3 for when
  // this product constraint is and is not acceptable.
  horizonEnd: v.integer(),
  materializedThrough: v.integer(),

  state: v.string(), // 'active' | 'ended'
  endedAt: v.optional(v.integer()),
  // Ending a series is effective from an instant, not retroactive. Occurrences
  // before this stay exactly as they are, including ones already individually
  // cancelled with their own reason.
  endedEffectiveFrom: v.optional(v.integer()),
  createdAt: v.integer(),
})
  .visibility({ kind: 'any-of', arms: [
    { kind: 'owner', field: 'holderId' },
    { kind: 'membership', declaration: 'orgMemberships',
      resourceField: 'orgId', roles: ['owner', 'manager', 'member'] },
  ]})
  .index('by_resource_state', ['resourceId', 'state'])
  .index('by_holder', ['holderId'])
  .sync();

export const cancellationLedger = defineTable({
  orgId: v.id('organizations'),
  holderId: v.principal(),
  bookingId: v.id('bookings'),
  resourceId: v.id('resources'),
  kind: v.string(), // 'late_cancel' | 'no_show' | 'early_cancel' | 'waiver'
  feeCents: v.integer(),
  occurredAt: v.integer(),
  // Denormalized so the 90-day suspension rule is one range read on one index
  // rather than a join back into bookings.
  bookingStart: v.integer(),
  // A waiver is a compensating row referencing the row it offsets. I7: nothing
  // in this table is ever patched or deleted.
  offsetsLedgerId: v.optional(v.id('cancellationLedger')),
  createdAt: v.integer(),
})
  .visibility({ kind: 'any-of', arms: [
    { kind: 'owner', field: 'holderId' },
    { kind: 'membership', declaration: 'orgMemberships',
      resourceField: 'orgId', roles: ['owner', 'manager'] },
  ]})
  .index('by_holder_occurred', ['holderId', 'occurredAt'])
```

### M1 — `createBooking`: the overlap check

```js
const HOLDER_CONCURRENT_LIMIT = 5;
const NINETY_DAYS = 90 * 24 * 60 * 60 * 1000;
// T1: how many lapsed holds we are willing to step over. Not derivable from
// anything; a function of how often sweepExpiredHolds runs.
const CORPSE_SLACK = 8;

export const createBooking = defineJsMutation({
  args: {
    resourceId: v.id('resources'),
    holderId: v.optional(v.string()),
    start: v.integer(),
    end: v.integer(),
  },
  auth: 'authenticated',
  outgrewIr: 'filtered-read-guards',
  refusals: [
    'RESOURCE_NOT_FOUND', 'RESOURCE_RETIRED', 'BAD_INTERVAL',
    'DURATION_OUT_OF_RANGE', 'TOO_FAR_IN_ADVANCE', 'SLOT_UNAVAILABLE',
    'HOLDER_QUOTA_EXCEEDED', 'HOLDER_SUSPENDED',
  ],
  reads: ['resources', 'bookings', 'orgMemberships', 'cancellationLedger', 'resourceCounters'],
  writes: ['bookings', 'resourceCounters'],
  result: results.value(v.id('bookings')),
  handler: async (ctx, args) => {
    const resource = await ctx.db.get('resources', args.resourceId);
    if (!resource) ctx.refuse('RESOURCE_NOT_FOUND');
    if (resource.retiredAt !== undefined) ctx.refuse('RESOURCE_RETIRED');

    // I10: authority is org-scoped even though occupancy is resource-scoped.
    await ctx.permissions.orgMemberships.requireRole(
      resource.orgId, 'owner', 'manager', 'member');

    const now = ctx.runtime.now();
    const me = ctx.auth.userId();
    const holderId = args.holderId ?? me;
    if (holderId !== me) {
      await ctx.permissions.orgMemberships.requireRole(resource.orgId, 'owner', 'manager');
    }

    if (!(args.end > args.start)) ctx.refuse('BAD_INTERVAL');
    const duration = args.end - args.start;
    if (duration < resource.minDurationMs || duration > resource.maxDurationMs) {
      ctx.refuse('DURATION_OUT_OF_RANGE');
    }
    if (args.start - now > resource.maxAdvanceMs) ctx.refuse('TOO_FAR_IN_ADVANCE');

    const exclusionStart = args.start - resource.setupMs;
    const exclusionEnd = args.end + resource.teardownMs;

    // ---- I1. THE predicate. ----------------------------------------------
    // Two equalities (resourceId, blocksCalendar) and one RANGE on the last
    // index column, read in DESCENDING order. Order is load-bearing for
    // correctness, not presentation: ascending would truncate from the wrong
    // end of an unbounded prefix.
    const predecessors = await ctx.db.query('bookings')
      .withIndex('by_resource_blocking_exclusion')
      .eq('resourceId', args.resourceId)
      .eq('blocksCalendar', true)
      .lt('exclusionStart', exclusionEnd)
      .order('exclusionStart', 'desc')
      .take(CORPSE_SLACK)
      .collect();

    for (const p of predecessors) {
      // T1: blocksCalendar is stale for lapsed holds. Skip corpses.
      if (p.state === 'held' && (p.holdExpiresAt ?? 0) <= now) continue;
      // First LIVE predecessor decides, by the disjointness argument in §2.1.
      if (p.exclusionEnd > exclusionStart) {
        ctx.refuse('SLOT_UNAVAILABLE', { freeAt: p.exclusionEnd });
      }
      break;
    }

    // ---- I6. Quota over the caller's own live future bookings. ------------
    // Note the shape: range-selected set, then counted THROUGH a predicate.
    // Not count(binding) — count(binding WHERE clock-dependent-predicate).
    const mineAhead = await ctx.db.query('bookings')
      .withIndex('by_holder_start')
      .eq('holderId', holderId)
      .gte('start', now)
      .take(HOLDER_CONCURRENT_LIMIT + CORPSE_SLACK)
      .collect();
    const liveMine = mineAhead.filter((b) =>
      b.state === 'confirmed' || (b.state === 'held' && (b.holdExpiresAt ?? 0) > now));
    if (liveMine.length >= HOLDER_CONCURRENT_LIMIT) ctx.refuse('HOLDER_QUOTA_EXCEEDED');

    // ---- I7. Suspension: 3 strikes in 90 days, net of waivers. ------------
    const recent = await ctx.db.query('cancellationLedger')
      .withIndex('by_holder_occurred')
      .eq('holderId', holderId)
      .gte('occurredAt', now - NINETY_DAYS)
      .take(64)
      .collect();
    const waived = new Set(recent.filter((r) => r.kind === 'waiver')
      .map((r) => r.offsetsLedgerId));
    const strikes = recent.filter((r) =>
      (r.kind === 'late_cancel' || r.kind === 'no_show') && !waived.has(r._id)).length;
    if (strikes >= 3) ctx.refuse('HOLDER_SUSPENDED', { strikes });

    const bookingId = await ctx.db.insert('bookings', {
      orgId: resource.orgId,
      resourceId: args.resourceId,
      holderId,
      bookedBy: me,
      state: 'confirmed',
      blocksCalendar: true,          // T3: paired by hand with `state`.
      start: args.start,
      end: args.end,
      exclusionStart,
      exclusionEnd,
      policyAnchorStart: args.start, // T2: frozen here.
      cancellationCutoffMs: resource.cancellationCutoffMs,
      lateCancelFeeCents: resource.lateCancelFeeCents,
      policyVersion: resource.policyVersion,
      createdAt: now,
      confirmedAt: now,
      rescheduleCount: 0,
    });

    const counter = await ctx.db.query('resourceCounters')
      .withIndex('by_resource').eq('resourceId', args.resourceId).first();
    if (counter) {
      await ctx.db.patch('resourceCounters', counter._id, {
        confirmedFutureCount: counter.confirmedFutureCount + 1, updatedAt: now });
    }
    return bookingId;
  },
});
```

```js
export const cancelBooking = defineJsMutation({
  args: { bookingId: v.id('bookings'), reason: v.optional(v.string()) },
  auth: 'authenticated',

  refusals: ['BOOKING_NOT_FOUND', 'NOT_CANCELLABLE', 'ALREADY_ENDED', 'NOT_PERMITTED'],

  handler: async (ctx, args) => {
    const b = await ctx.db.get('bookings', args.bookingId);
    if (!b) ctx.refuse('BOOKING_NOT_FOUND');
    const now = ctx.runtime.now();
    const me = ctx.auth.userId();

    if (b.holderId !== me && b.bookedBy !== me) {
      // T4: for a departed holder this refuses even though `any-of` lets them
      // SEE the row. Visibility and authority disagree and only one of them
      // has an any-of.
      await ctx.permissions.orgMemberships.requireRole(b.orgId, 'owner', 'manager');

    if (b.state !== 'confirmed' && b.state !== 'held') ctx.refuse('NOT_CANCELLABLE');
    if (now >= b.end) ctx.refuse('ALREADY_ENDED');

    // T2: measured against the FROZEN anchor, never against b.start.

    await ctx.db.patch('bookings', b._id, {
      state: 'cancelled',
      blocksCalendar: false,
      cancelledAt: now,
      cancelledBy: me,
      cancelReason: args.reason ?? '',
      wasLateCancel: late,
    });

    // I7. Conditional write #1.
    if (late) {
      await ctx.db.insert('cancellationLedger', {
        orgId: b.orgId, holderId: b.holderId, bookingId: b._id,
        resourceId: b.resourceId, kind: 'late_cancel',
        feeCents: b.lateCancelFeeCents, occurredAt: now,
        bookingStart: b.start, createdAt: now,
      });
    }

    // I5 + T5. Conditional write #2, ordered, same commit.
    const promoted = await offerFreedWindow(ctx, b, now);

    const counter = await ctx.db.query('resourceCounters')

        confirmedFutureCount: Math.max(0, counter.confirmedFutureCount - 1),
        waitingCount: promoted ? Math.max(0, counter.waitingCount - 1) : counter.waitingCount,
        updatedAt: now,
      });
    }
    return { late, promoted };
  },
```

### M3 — `offerFreedWindow`: ranked selection with a residual interval predicate

```js
// Same-file helper; spliced into the handler closure by codegen.
const WAITLIST_SCAN = 25;
const OFFER_TTL_MS = 30 * 60 * 1000;

async function offerFreedWindow(ctx, freed, now) {
  const freedLen = freed.end - freed.start;

  // Ordered by rank. The winner is NOT necessarily position 0: entry #1 may
  // want two hours when one just freed. So this is
  //   argmin over position of { entries satisfying an interval-containment test }
  // and the test compares three of the row's own fields against a runtime
  // interval. No index prefix expresses it; no expression in the plan
  // vocabulary filters rows out of a binding.
  const candidates = await ctx.db.query('waitlistEntries')
    .withIndex('by_resource_state_position')
    .eq('resourceId', freed.resourceId)
    .eq('state', 'waiting')
    .order('position', 'asc')
    .take(WAITLIST_SCAN)
    .collect();

  const winner = candidates.find((w) =>
    w.windowStart <= freed.start &&
    w.windowEnd >= freed.end &&
    w.desiredDurationMs <= freedLen);

  // I5: if nobody fits, NOTHING is written and the cancellation still commits.
  // `guard` cannot express this — it would roll the cancellation back.
  if (!winner) return false;

  // Atomicity: the entry is consumed in the same commit that frees the slot, so
  // two concurrent cancellations cannot both promote this row — the second
  // fails OCC on the row-version dependency for the entry it read. M1's overlap
  // check gets equivalent protection by a different route: its zero-row read
  // registers a captured *query-range* dependency, so a concurrent conflicting
  // insert fails validation too. See §2.3 — I expected this to be a hole and it
  // is not.
  await ctx.db.patch('waitlistEntries', winner._id, {
    state: 'offered', offerExpiresAt: now + OFFER_TTL_MS,
  });

  const resource = await ctx.db.get('resources', freed.resourceId);
  const bookingId = await ctx.db.insert('bookings', {
    orgId: freed.orgId,
    resourceId: freed.resourceId,
    holderId: winner.holderId,
    bookedBy: winner.holderId,
    // A promotion is a HOLD, not a confirmation. The waitlisted party must
    // accept. T1 immediately applies: this hold expires by the clock.
    state: 'held',
    blocksCalendar: true,
    holdExpiresAt: now + OFFER_TTL_MS,
    start: freed.start,
    end: freed.start + winner.desiredDurationMs,
    exclusionStart: freed.start - resource.setupMs,
    exclusionEnd: freed.start + winner.desiredDurationMs + resource.teardownMs,
    policyAnchorStart: freed.start,
    cancellationCutoffMs: resource.cancellationCutoffMs,
    lateCancelFeeCents: resource.lateCancelFeeCents,
    policyVersion: resource.policyVersion,
    createdAt: now,
    rescheduleCount: 0,
    promotedFromWaitlistId: winner._id,
  });
  await ctx.db.patch('waitlistEntries', winner._id, { promotedBookingId: bookingId });
  return true;
}
```

### M4 — `rescheduleBooking`: two overlap checks, self-exclusion, and the anchor rule

```js
export const rescheduleBooking = defineJsMutation({
  args: { bookingId: v.id('bookings'), start: v.integer(), end: v.integer() },
  auth: 'authenticated',
  outgrewIr: 'filtered-read-guards',
  refusals: [
    'BOOKING_NOT_FOUND', 'NOT_RESCHEDULABLE', 'RESCHEDULE_WINDOW_CLOSED',
    'BAD_INTERVAL', 'DURATION_OUT_OF_RANGE', 'SLOT_UNAVAILABLE', 'RESCHEDULE_LIMIT',
  ],
  reads: ['bookings', 'resources', 'orgMemberships'],
  writes: ['bookings'],
  result: results.value(v.id('bookings')),
  handler: async (ctx, args) => {
    const b = await ctx.db.get('bookings', args.bookingId);
    if (!b) ctx.refuse('BOOKING_NOT_FOUND');
    if (b.state !== 'confirmed') ctx.refuse('NOT_RESCHEDULABLE');
    const now = ctx.runtime.now();
    const me = ctx.auth.userId();
    const isManager = b.holderId !== me;
    if (isManager) {
      await ctx.permissions.orgMemberships.requireRole(b.orgId, 'owner', 'manager');
    }
    if (now >= b.end) ctx.refuse('NOT_RESCHEDULABLE');
    if (b.rescheduleCount >= 3) ctx.refuse('RESCHEDULE_LIMIT');

    // T2, the whole point. A move inside the cutoff is as expensive as a
    // cancellation, so it cannot be used to escape one.
    const lateMove = now > (b.policyAnchorStart - b.cancellationCutoffMs);
    if (lateMove && !isManager) ctx.refuse('RESCHEDULE_WINDOW_CLOSED');

    if (!(args.end > args.start)) ctx.refuse('BAD_INTERVAL');
    const resource = await ctx.db.get('resources', b.resourceId);
    const duration = args.end - args.start;
    if (duration < resource.minDurationMs || duration > resource.maxDurationMs) {
      ctx.refuse('DURATION_OUT_OF_RANGE');
    }

    const exclusionStart = args.start - resource.setupMs;
    const exclusionEnd = args.end + resource.teardownMs;

    // The overlap check must EXCLUDE THIS ROW. There is no not-equal in an
    // index key, so take(1) is unsound here — it would return the booking
    // itself and refuse. The overfetch-by-one trick LLP 0329.008 observed in
    // markDelivered is not incidental; it is what you always do when the read
    // must exclude a known row.
    const predecessors = await ctx.db.query('bookings')
      .withIndex('by_resource_blocking_exclusion')
      .eq('resourceId', b.resourceId)
      .eq('blocksCalendar', true)
      .lt('exclusionStart', exclusionEnd)
      .order('exclusionStart', 'desc')
      .take(CORPSE_SLACK + 1)
      .collect();
    for (const p of predecessors) {
      if (p._id === b._id) continue;                                     // self
      if (p.state === 'held' && (p.holdExpiresAt ?? 0) <= now) continue;  // corpse
      if (p.exclusionEnd > exclusionStart) ctx.refuse('SLOT_UNAVAILABLE');
      break;
    }

    // Release-and-acquire in one commit. As two commits there is a window in
    // which the resource is free and someone else takes it, and the reschedule
    // then fails with the original booking already gone.
    await ctx.db.patch('bookings', b._id, {
      start: args.start,
      end: args.end,
      exclusionStart,
      exclusionEnd,
      // T2: the anchor advances only when the move was free. A manager override
      // moves the booking but keeps the penalty exposure — the favour does not
      // launder the lateness.
      policyAnchorStart: lateMove ? b.policyAnchorStart : args.start,
      rescheduleCount: b.rescheduleCount + 1,
    });
    return b._id;
  },
});
```

### M7 — `createSeries`: bounded fan-out with N overlap checks

```js
const MAX_OCCURRENCES = 26; // ~6 months of weekly. See Part 3 on the horizon.

export const createSeries = defineJsMutation({
  args: {
    resourceId: v.id('resources'),

    durationMs: v.integer(), seriesStart: v.integer(), horizonEnd: v.integer(),
    conflictPolicy: v.string(), // 'all-or-nothing' | 'skip-conflicts'
  },

  outgrewIr: 'general-iteration',
  refusals: ['RESOURCE_NOT_FOUND', 'HORIZON_TOO_LONG', 'SERIES_CONFLICT', 'BAD_RULE'],
  reads: ['resources', 'bookings', 'organizations', 'orgMemberships'],
  writes: ['bookingSeries', 'bookings', 'resourceCounters'],

    seriesId: v.string(), created: v.integer(), skipped: v.integer() })),
  handler: async (ctx, args) => {
    const resource = await ctx.db.get('resources', args.resourceId);
    if (!resource) ctx.refuse('RESOURCE_NOT_FOUND');

      resource.orgId, 'owner', 'manager', 'member');
    const org = await ctx.db.get('organizations', resource.orgId);
    const now = ctx.runtime.now();
    const me = ctx.auth.userId();

    // Expanded in the ORG's timezone, so a 09:00 weekly series is 09:00 local
    // across a DST boundary and the occurrences are not a fixed period apart.
    // This is why occurrences are materialized rather than derived.
    const instants = expandWeekly(org.timezone, args.weekdayMask,
      args.startMinuteOfDay, args.seriesStart, args.horizonEnd);
    if (instants.length === 0) ctx.refuse('BAD_RULE');
    if (instants.length > MAX_OCCURRENCES) ctx.refuse('HORIZON_TOO_LONG');

    const seriesId = await ctx.db.insert('bookingSeries', {
      orgId: resource.orgId, resourceId: args.resourceId, holderId: me,
      weekdayMask: args.weekdayMask, startMinuteOfDay: args.startMinuteOfDay,
      durationMs: args.durationMs, seriesStart: args.seriesStart,
      horizonEnd: args.horizonEnd, materializedThrough: args.horizonEnd,
      state: 'active', createdAt: now,
    });

    // N overlap checks — one per occurrence, each the range read from M1, each
    // of which must also see the rows this same loop has already inserted.
    let created = 0, skipped = 0;
    for (let i = 0; i < instants.length; i += 1) {
      const start = instants[i];
      const end = start + args.durationMs;
      const exclusionStart = start - resource.setupMs;
      const exclusionEnd = end + resource.teardownMs;

      const predecessors = await ctx.db.query('bookings')
        .withIndex('by_resource_blocking_exclusion')
        .eq('resourceId', args.resourceId).eq('blocksCalendar', true)
        .lt('exclusionStart', exclusionEnd)
        .order('exclusionStart', 'desc').take(CORPSE_SLACK).collect();

      let conflict = false;
      for (const p of predecessors) {
        if (p.state === 'held' && (p.holdExpiresAt ?? 0) <= now) continue;
        conflict = p.exclusionEnd > exclusionStart;
        break;
      }
      if (conflict) {
        if (args.conflictPolicy === 'all-or-nothing') {
          ctx.refuse('SERIES_CONFLICT', { occurrenceIndex: i, start });
        }
        skipped += 1;
        continue; // 'skip-conflicts': the series is sparse, deliberately.
      }
      await ctx.db.insert('bookings', {
        orgId: resource.orgId, resourceId: args.resourceId, holderId: me, bookedBy: me,
        state: 'confirmed', blocksCalendar: true,
        start, end, exclusionStart, exclusionEnd,
        policyAnchorStart: start,
        cancellationCutoffMs: resource.cancellationCutoffMs,
        lateCancelFeeCents: resource.lateCancelFeeCents,
        policyVersion: resource.policyVersion,
        seriesId, occurrenceIndex: i,
        createdAt: now, confirmedAt: now, rescheduleCount: 0,
      });
      created += 1;
    }
    return { seriesId, created, skipped };
  },
});
```

```js
    if (s.state === 'ended') ctx.refuse('ALREADY_ENDED');
    const me = ctx.auth.userId();
    if (s.holderId !== me) {
      await ctx.permissions.orgMemberships.requireRole(s.orgId, 'owner', 'manager');
    }
    const now = ctx.runtime.now();
    const from = args.effectiveFrom ?? now;

    // I8: FUTURE occurrences only. Past ones are history; already-cancelled
    // future ones keep their own reason and must not be overwritten.
    const future = await ctx.db.query('bookings')
      .withIndex('by_series_start').eq('seriesId', args.seriesId)
      .gte('start', from).order('start', 'asc').take(MAX_OCCURRENCES + 1).collect();
    if (future.length > MAX_OCCURRENCES) ctx.refuse('TOO_MANY_OCCURRENCES');

    let cancelled = 0, lateCount = 0;
    for (const b of future) {
      if (b.state !== 'confirmed' && b.state !== 'held') continue; // keep its reason
      const late = now > (b.policyAnchorStart - b.cancellationCutoffMs);
      await ctx.db.patch('bookings', b._id, {
        state: 'cancelled', blocksCalendar: false, cancelledAt: now, cancelledBy: me,
        cancelReason: 'series_ended', wasLateCancel: late,
      });
      if (late) {
        lateCount += 1;
        await ctx.db.insert('cancellationLedger', {
          orgId: b.orgId, holderId: b.holderId, bookingId: b._id,
          resourceId: b.resourceId, kind: 'late_cancel',
          feeCents: b.lateCancelFeeCents, occurredAt: now,
          bookingStart: b.start, createdAt: now,
        });
      }
      await offerFreedWindow(ctx, b, now);
      cancelled += 1;
    }
    await ctx.db.patch('bookingSeries', args.seriesId, {
      state: 'ended', endedAt: now, endedEffectiveFrom: from });
    return { cancelled, lateCount };
  },
});
```

Cancelling **one** occurrence is just `cancelBooking` on a materialized row — nothing
special, because the occurrence is a real row. That asymmetry is the argument for
materializing: the cheap operation stays cheap and the expensive one is expensive
exactly once. If occurrences were derived from the rule, cancelling one would require
an *exception* row — a negative record — and every overlap check would have to subtract
exceptions from a generated set, which nothing in this system can do.

### M10 — `changeResourceBuffers`: an edit that can retroactively violate I1

```js
export const changeResourceBuffers = defineJsMutation({
  args: { resourceId: v.id('resources'), setupMs: v.integer(), teardownMs: v.integer() },
  auth: 'authenticated',
  outgrewIr: 'general-iteration',
  refusals: ['RESOURCE_NOT_FOUND', 'WOULD_CREATE_CONFLICTS', 'TOO_MANY_FUTURE_BOOKINGS'],
  reads: ['resources', 'bookings', 'orgMemberships'],
  writes: ['resources', 'bookings'],
  result: results.value(v.object({ rewritten: v.integer() })),
  handler: async (ctx, args) => {
    const r = await ctx.db.get('resources', args.resourceId);
    if (!r) ctx.refuse('RESOURCE_NOT_FOUND');
    await ctx.permissions.orgMemberships.requireRole(r.orgId, 'owner', 'manager');
    const now = ctx.runtime.now();

    // Widening a buffer widens every future booking's exclusion interval, which
    // can make two previously-legal neighbours overlap. So this edit must
    // (a) rewrite a denormalized column on an unbounded set, and (b) re-verify
    // I1 across the whole rewritten set before committing any of it.
    const future = await ctx.db.query('bookings')
      .withIndex('by_resource_blocking_exclusion')
      .eq('resourceId', args.resourceId).eq('blocksCalendar', true)
      .gte('exclusionStart', now - r.setupMs)
      .order('exclusionStart', 'asc')
      .take(501).collect();
    if (future.length > 500) ctx.refuse('TOO_MANY_FUTURE_BOOKINGS');

    const live = future.filter((b) =>
      !(b.state === 'held' && (b.holdExpiresAt ?? 0) <= now));
    const rewritten = live.map((b) => ({
      ...b,
      exclusionStart: b.start - args.setupMs,
      exclusionEnd: b.end + args.teardownMs,
    })).sort((a, b) => a.exclusionStart - b.exclusionStart);

    // Pairwise disjointness over the rewritten set. This is the invariant the
    // engine ought to hold and instead the application re-derives, in JS, once.
    for (let i = 1; i < rewritten.length; i += 1) {
      if (rewritten[i].exclusionStart < rewritten[i - 1].exclusionEnd) {
        ctx.refuse('WOULD_CREATE_CONFLICTS', {
          a: rewritten[i - 1]._id, b: rewritten[i]._id });
      }
    }

    await ctx.db.patch('resources', args.resourceId, {
      setupMs: args.setupMs, teardownMs: args.teardownMs,
      policyVersion: r.policyVersion + 1,
    });
    for (const b of rewritten) {
      await ctx.db.patch('bookings', b._id, {
        exclusionStart: b.exclusionStart, exclusionEnd: b.exclusionEnd });
      // NOTE what is deliberately NOT patched: cancellationCutoffMs,
      // lateCancelFeeCents, policyAnchorStart. I9 — the terms a booking was
      // made under do not move. Only the physical exclusion does.
    }
    return { rewritten: rewritten.length };
  },
});
```

```js
export const removeOrgMember = defineJsMutation({
  args: { orgId: v.id('organizations'), principal: v.string() },

      // 'cancelled' would charge a departing member for their own removal.
      await ctx.db.patch('bookings', b._id, {

      });

      await offerFreedWindow(ctx, b, now);
    }

      .withIndex('by_holder_state').eq('holderId', args.principal).eq('state', 'waiting')
      .take(64).collect();
    let withdrawn = 0;
    for (const w of waiting) {
      if (w.orgId !== args.orgId) continue;
      await ctx.db.patch('waitlistEntries', w._id, { state: 'withdrawn' });

    }

    const membership = await ctx.db.query('orgMemberships')
      .withIndex('by_org_principal').eq('orgId', args.orgId).eq('principal', args.principal)

    if (!membership) ctx.refuse('NOT_A_MEMBER');
    await ctx.db.delete('orgMemberships', membership._id);
```

### Q1 — `availabilityForDay`: the complement of a set of intervals

```js
export const availabilityForDay = defineJsQuery({
  args: { resourceId: v.id('resources'), dayStart: v.integer(), dayEnd: v.integer() },
  auth: 'authenticated',
  reads: ['resources', 'bookings'],
  result: results.records(v.object({ start: v.integer(), end: v.integer() })),
  handler: async (ctx, args) => {
    const r = await ctx.db.get('resources', args.resourceId);
    if (!r) return [];
    const now = ctx.runtime.now();
    // Overlaps-the-day, not starts-in-the-day: a booking that began yesterday
    // evening still occupies this morning. So the lower bound must be
    // dayStart - maxDurationMs - teardownMs, which is why maxDurationMs exists
    // as a schema constraint at all. Without a declared maximum duration there
    // is no finite lower bound on this scan.
    const rows = await ctx.db.query('bookings')
      .withIndex('by_resource_blocking_exclusion')
      .eq('resourceId', args.resourceId).eq('blocksCalendar', true)
      .gte('exclusionStart', args.dayStart - r.maxDurationMs - r.teardownMs)
      .lt('exclusionStart', args.dayEnd)
      .order('exclusionStart', 'asc')
      .take(256).collect();

    // Interval complement — a left fold over an ordered set producing a
    // variable-length result. Not an aggregate, not a projection, not a join.
    const gaps = [];
    let cursor = args.dayStart;
    for (const b of rows) {
      if (b.state === 'held' && (b.holdExpiresAt ?? 0) <= now) continue;
      if (b.exclusionStart > cursor) gaps.push({ start: cursor, end: b.exclusionStart });
      cursor = Math.max(cursor, b.exclusionEnd);
    }
    if (cursor < args.dayEnd) gaps.push({ start: cursor, end: args.dayEnd });
    return gaps.filter((g) => g.end - g.start >= r.minDurationMs);
  },
});
```

# Part 2 — Testing the model against it

## 2.1 The overlap check is `take(1)`, and rung A cannot reach it

This is the central result, so I will state the mathematics.

**Claim.** If the existing calendar-live bookings for a resource are pairwise
exclusion-disjoint (which is I1, the invariant we are maintaining), then a candidate
interval `[s, e)` overlaps some existing booking **iff** it overlaps the *single*
booking `P` with the greatest `exclusionStart` among those with `exclusionStart < e`.

**Proof.** Suppose some live `B` overlaps: `B.exclusionStart < e` and `B.exclusionEnd >
s`. `P` exists (B is a candidate) and `P.exclusionStart ≥ B.exclusionStart`. If
`P.exclusionStart ≥ s` then, with `P.exclusionStart < e`, `P` overlaps. Otherwise
`P.exclusionStart < s`, so `B.exclusionStart ≤ P.exclusionStart < s`; if `B ≠ P` then
disjointness forces `B.exclusionEnd ≤ P.exclusionStart < s`, contradicting
`B.exclusionEnd > s`; so `B = P` and `P` overlaps. ∎

So double-booking prevention is a **one-row read**. Not `take(51)`, not a roster, not a
count. It is the same cardinality as rung A, and it is unreachable by rung A's
primitive, because:

| | Rung A (`unique(table, index, key, bindAs)`) | The overlap read |
|---|---|---|
| Predicate on the last index column | equality | **strict inequality** |
| Direction | irrelevant (one row matches) | **descending, load-bearing** |
| Result if unbounded prefix | n/a | truncated from the wrong end without `order` |
| Exclude a known row | n/a | **required** by `rescheduleBooking` |

**The ladder measures cardinality. This app varies addressing mode.** Rung A and my
hardest read are both one row. The rungs are `take = 1, N, N+count, N+fan-out` — a
single axis. What the census would have found in a booking app is that the axis is at
minimum two-dimensional: `{1, N} × {key, range+order}`.

And this is not a hypothetical extension. LLP 0329.008 open question 2 asks *"Does the
bound read need `order`, or is an unordered bounded set sufficient?"* and reports that
rungs A–D as measured never order the bound rows. **For this app the answer is that
ordering is a correctness prerequisite for the single most important write in the
system.** That question was asked and answered against one app; a second app inverts it.

## 2.2 The `take` bound is not "already authored" here

LLP 0329.008's cost argument is that the bounded read inherits its work ceiling from
the JS original: *"Every JS original passes an explicit `take` … the bounded-work story
is inherited rather than invented."*

In Roomwright the `take` is a guess about garbage-collection lag (T1). `CORPSE_SLACK =
8` is not a product fact; it is a bet that the hold sweeper never falls more than eight
lapsed holds behind on one resource. If it does, the overlap check returns eight
corpses, finds no live predecessor, and **confirms an overlapping booking**. The take
is not a ceiling on work; it is a *correctness parameter with no principled value*.

The general form of the problem: **an authored `take` is only a sound work bound when
every row read is semantically meaningful.** When the clock invalidates rows that no
writer has updated, the read is polluted by an unbounded number of them and the bound
becomes an availability/correctness tradeoff rather than a cost ceiling. Any app with
expiring state has this; booking, sessions, invitations, holds, offers, locks, and
reservations all do.

## 2.3 Concurrency: I predicted a hole, checked, and found the opposite — which is a better argument for rung E than the hole would have been

My first draft of this section claimed that the overlap check races: it *succeeds by
reading nothing*, so row-granular read-set capture would record no dependency, two
concurrent `createBooking` calls would both pass, and I1 would be violated in durable
storage. That is the negative-dependency hole from `ANSWER.md` §1 — *"a viewer denied
because no membership row exists reads no row, so row-granular capture records no
dependency"* — relocated from live delivery into the write path, where its consequence
is corruption rather than a stale screen.

**I checked the kernel and the claim is wrong. Both halves of the defence already
exist, and the second half is stronger than a defence.**

**(1) Range-granular capture is shipped, on the handler path.**
`CapturedReadKind` (`crates/snapback-types/src/storage.rs:401`) has variants `Row,
MissingRow, Query, Auth, Permission, GraphNode`. The `Query` variant carries the
executed `predicate` as a serialized `QueryPlan`. `validate_captured_read_set`
(`storage.rs:16119`) validates it by finding every change to that table since the
captured version and asking `live_matcher::query_dependency_change_may_affect` whether
the change could alter *this query's* result. That matcher evaluates the full filter
vocabulary — `filter_matches_expected` (`live_matcher.rs:3234`) handles `Eq, In, Lt,
Lte, Gt, Gte` with SQL three-valued NULL semantics — and composes table visibility
first (`row_matches_query_filters`, `live_matcher.rs:3158`).

So M1's overlap check, as a JS handler, is already correctly protected: it registers a
`Query` dependency for `(resourceId = R, blocksCalendar = true, exclusionStart < e)`,
and a concurrent insert matching that predicate fails validation at commit. Zero rows
returned is a first-class captured dependency, not an absence of one.

**This is a direct correction to `ANSWER.md` §5**, whose cost table lists
*"Range-granular capture | new machinery; a correctness prerequisite, so not optional |
[confidence] low."* On the mutation handler path it is not new machinery. It is built,
predicate-complete, and visibility-composing. That line should be struck or narrowed to
whichever path actually lacks it.

**(2) A plan-side range read would not need OCC at all — it would be serializable by
construction.** This is the part worth the most. `storage.rs:5454` explains the
asymmetry in the plan commit path:

> "plan `Get` reads execute inside this same transaction (they can never be stale
> relative to the commit, so they need no conflict validation) … Ibex handlers still
> differ: they read → await → commit across an async window, so their reads are
> captured server-side and validated in `commit_buffered_writes`."

A JS handler reads, suspends on `await`, and commits later; the window between is the
race, and captured-read validation exists to close it. **A plan has no such window.**
Its steps execute inside the commit transaction — and `deleteWhere` demonstrates that a
full range-filtered scan can already run there (`storage.rs:6344`, building its
`QueryPlan` against `&tx`).

So moving `createBooking`'s overlap check from a handler to a plan step would convert a
race that must be *detected and retried* into one that **cannot occur**. For an app
whose central invariant is pairwise interval disjointness, that is not a tidiness
argument; it is the difference between an invariant enforced by conflict-retry and one
enforced by isolation.

**And this is a new argument for the declarative read that the corpus has not made.**
LLP 0329.011 argues for declarative bound reads entirely on *disclosure* grounds —
making the noninterference question answerable. The concurrency argument is independent
and, for interval-keyed apps, stronger: the plan tier is not merely more analyzable
than the handler tier, it is more *serializable*. Rung E should be sold on this, not
only on plan coverage.

Two honest caveats. First, this rests on the source comment plus `deleteWhere`'s
execution against `&tx`; I did not run a concurrent test. Second, it assumes a new read
step would be implemented in the transaction the way `Get` and `DeleteWhere` are — very
likely, but it is an assumption about unwritten code.

One residual hole survives all of this, and it is T1's: **the clock is not a row
change.** A hold that lapses writes nothing, so no capture and no matcher can notice
it. Isolation protects the overlap check against concurrent *writers*; nothing protects
it against the passage of time. That is why `CORPSE_SLACK` exists and why §2.2 stands.

## 2.4 Rung C does not close a single count in this app

Rung C is `count(binding)`. Every capacity check in Roomwright is
`count(binding **where** predicate)`, and the predicate is a clock comparison:

| Check | Bound set | Residual predicate |
|---|---|---|
| Holder concurrent quota (M1) | `holderId = H, start ≥ now` | `state = 'confirmed' ∨ (state = 'held' ∧ holdExpiresAt > now)` |
| Suspension strikes (M1) | `holderId = H, occurredAt ≥ now − 90d` | `kind ∈ {late_cancel, no_show} ∧ ¬waived` |
| Waitlist capacity (M5) | `resourceId = R, state = 'waiting'` | — (this one is clean) |

Two of the three are unreachable, and for a reason the ladder does not name. The
expression vocabulary has `cond`, which selects a *value*; it has nothing that selects
*rows from a binding*. So even given a bound set, you cannot count the live subset of
it. `count(binding)` counts what the index prefix gave you, and the index prefix cannot
carry a clock comparison because the range column is already spent on the interval.

The fix is small and I would propose it: **`count(binding, predicateOverItem)`**, with
the predicate drawn from the existing expression algebra over the item binding — the
same shape `insertEach(table, source, itemAs, values)` already uses for its `itemAs`
binding. If `insertEach` can evaluate expressions per item, `count` can too, and the
work is already bounded by the read's `take`.

## 2.5 Finding 3's count rule: does not hold, and fails in the worse direction

**No.** Two independent failures.

**Failure 1 — a visibility-filtered count is silently wrong, not refused.**

"How many people are ahead of me on the waitlist" is a universal product requirement
(every waitlist UI shows it). Apply the rule:

- (b) *keyed to a resource, not a third-party principal* — **passes.** The domain is
  `waitlistEntries where resourceId = R ∧ state = 'waiting' ∧ position < mine`. That is
  a resource key.
- (a) *filtered by the caller's declared read visibility* — **"passes," and destroys the
  answer.** `waitlistEntries` is `any-of [owner:holderId, membership(roles: owner,
  manager)]`. To a plain member, the visible domain is their own rows. The count returns
  0 or 1. **The count is admitted and returns a wrong number.**

LLP 0329.011's own open question 3 gestures at exactly this — *"Worth confirming that
visibility-filtered counts never turn a refusal into a silent pass"* — and this is the
answer: **they do, and it is not even a refusal-shaped failure; it is a wrong integer
delivered with full confidence.** That is the silent-degradation class `ANSWER.md` §2
identifies as disqualifying, arriving through the noninterference rule that was
supposed to prevent it.

S5's summary sentence — *"protection makes counting safer, not riskier"* — is true for
disclosure and false for correctness, and the rule as written does not distinguish
them. What rule (a) actually guarantees is that the count is **safe**. It guarantees
nothing about whether it is **the count the product asked for**. A rule that silently
substitutes a different question is worse than one that refuses.

**The sharpened rule I would propose:**

> A count may drive a refusal or a displayed value only when the counted domain is
> keyed to a resource the caller is authorized for **and the caller's read visibility
> over that domain is not strictly narrower than the domain itself.** When it is
> narrower, the count must refuse at generate time and the author must supply a
> maintained aggregate owned by the same authority as the domain.

The third clause is the one that makes it actionable, and it is codex's
maintained-exact aggregate from `ANSWER.md` §2 arriving as a *necessity* rather than an
availability preference. Roomwright's `resourceCounters.waitingCount` is exactly that:
an authority-owned aggregate, maintained in the same commits that change the domain,
readable by anyone who can see the resource. Q2 uses it and never counts.

**Failure 2 — the app needs sums, and sums are not counts with a different operator.**

A paid-resource variant needs "this org has 40 booked hours left this month," which is
`SUM(end − start)` over the org's confirmed bookings this month. The ladder has
`count(binding)` only. Extending it to `sum(binding, expr)` looks like a one-line
change and is not, for a disclosure reason:

A count over `n` invisible rows discloses `n`. A **sum** over invisible rows discloses a
*value*, and combined with a probe (book one more unit, observe whether the refusal
fires) it is an exact oracle on a third party's consumption at whatever granularity the
attacker chooses to bisect. The count rule's (a)+(b) conditions do not address
magnitude-vs-cardinality at all. I would not extend Finding 3 to sums without a
separate analysis; I flag this as **reasoned, not measured** — I did not construct the
attack against a running system.

## 2.6 The blocker is often a *write* shape, and the ladder is entirely about reads

Six of eleven mutations are blocked on something the ladder does not discuss:

- **Conditional writes.** `cancelBooking` promotes *if* someone is waiting; charges a
  fee *if* the cancellation was late. `guard` aborts the whole mutation, so it cannot
  express "do this optionally." `guide/backend/declarative-plans.md` names
  `conditional-writes` as a permanently-out-of-profile class. **Every cancellation in
  every booking product in the world is a conditional write.** This is not an exotic
  shape.
- **Set-oriented patch.** `endSeriesFrom` and `removeOrgMember` want "patch every row
  matching this range predicate." `deleteWhere` exists — and is exactly wrong, because
  the entire cancellation trap (T3/I2) is that you must **not** delete. **The one
  set-oriented write step the IR has is the destructive one, in an app whose central
  invariant is that history survives.** `patchWhere(table, filter, values)` is the same
  machinery, the same `QueryPlan`, the same `build_query_sql`, with `UPDATE` instead of
  `DELETE`.
- **Even `withdrawFromWaitlist` (M6), which is nearly plan-shaped, breaks** — not on
  the patch, but on needing the counter row's id, which is only reachable by an indexed
  read. It is a rung-A read blocking an otherwise-trivial plan.

I would name these as one rung because they share a property that makes them
admissible: **the write set stays statically bounded.** `insertIf(cond, table, values)`
writes 0 or 1 rows. `patchWhere(table, filter, values)` writes 0..N where N is the same
bound `deleteWhere` already tolerates. Neither introduces loops, data-dependent step
*sequences*, or unbounded fan-out. The out-of-profile class `conditional-writes` is
currently all-or-nothing, and a *bounded* conditional write is strictly weaker than
what it forbids.

## 2.7 What the schema language cannot say, and why that is the highest-leverage gap

Four declarations Roomwright needs and cannot write:

1. **Exclusion constraint.** `EXCLUDE USING gist (resourceId WITH =, tsrange(exclusionStart,
   exclusionEnd) WITH &&) WHERE (blocksCalendar)`. This is I1, in one line, enforced by
   the storage engine, immune to a forgetful author and immune to the OCC race in §2.3.
   Without it, I1 holds only as long as every present and future writer remembers to
   check — which is LLP 0310 P18's posture verbatim, reproduced at the level of the
   application's single most important invariant.
2. **Partial uniqueness.** `{ unique: true, where: [eq('state', 'waiting')] }`. Every
   uniqueness constraint in this app is conditioned on a live state. `messaging-snapback`'s
   reaction dedup works only because reactions never die.
3. **Derived column.** `blocksCalendar` is `state ∈ {held, confirmed}`, hand-maintained
   across six transitions, sitting in an index prefix, load-bearing for I1. A
   `.derived('blocksCalendar', expr)` that codegen maintains would eliminate the entire
   T3 class.
4. **Append-only.** `cancellationLedger` (I7) can be patched or deleted by any plan or
   handler. `.appendOnly()` is a one-bit declaration that makes a whole class of
   tampering inexpressible.

Every one of these converts "the author must remember" into "the engine enforces." That
is the pit-of-success standard LLP 0310 disposed P18 under. And note the shape: **these
are not plan steps.** The ladder is a list of things a mutation should be able to *do*.
Half of what this app needs is things the schema should be able to *forbid*. A census
that only classifies mutations cannot see this axis at all, which is a methodological
finding about the census as much as about the ladder.

## 2.8 Per-mutation classification

`plan?` = expressible as `defineMutation` with today's steps. Rung = where it lands on
A0/A/B/C/D, or the new rung it needs.

| # | Operation | Plan today? | First missing construct | Rung |
|---|---|---|---|---|
| M1 | `createBooking` | No | **range predicate + descending order on a bound read** | **E** (then C′ for the quota, F for nothing — the writes are fine) |
| M2 | `cancelBooking` | No | **conditional insert** (`insertIf` for the ledger row) | **F** — and E via M3 |
| M3 | `offerFreedWindow` | No | **ordered read + first-match over a binding** (`find`, not `count`) | **E′** (ranked selection) then **F** (conditional write) |

| M6 | `withdrawFromWaitlist` | No | indexed equality read (fetch the counter row by `resourceId`) | **A** |

**One mutation of eleven is a plan today (M9, 9%).** With the full ladder as specified
(A+B+C+D), **two more become plans (M5, M6 — both rung A)**, taking the app to 27%.
That is the measurement that matters: on `coterie` the ladder claims 100%; on
Roomwright it claims 27%, and the nine it misses include every operation the product is
actually about.

I want to be careful about that number. It is a static classification by first missing
construct, the same method as 0329.008, with the same limitation: I did not run codegen
on any of these. M9 is the only one I would defend as verified-by-inspection against the
step table.

## 2.9 What `coterie` would have had to be to surface this

Worth stating, because it explains why one app was not enough and predicts which
*third* app to write.

`coterie` is a **point-keyed** application. Every read is "rows where `X = k`,"
optionally paginated by an opaque `pageKey`. Its hardest temporal feature — the
active/historical membership cutoff — is expressed as a *stored* `cutoffPageKey`
compared to a *stored* `pageKey`, so even the time-dependent part reduces to a
comparison between two columns the app already materialized. `coterie` never has to ask
"is there anything in this interval."

Roomwright is an **interval-keyed** application. Its central object is a range, its
central predicate is range intersection, and its central invariant is pairwise
disjointness. Nothing about that is exotic — calendars, reservations, rate limits,
leases, shift rosters, subscriptions, and pricing periods are all interval-keyed — but
none of them are in the corpus.

**The prediction:** the ladder derived from `coterie` will hold up on any app whose
domain model is a graph of entities related by identity, and will fail on any app whose
domain model is a set of intervals or an ordered queue. The corpus has five instances
of the first kind and none of the second. That is a sampling problem, not a modelling
one, and it is fixable by choosing the third app deliberately.

# Part 3 — Verdict

## 3.1 Does the model survive?

**Partly. The ladder is correct and incomplete, and the incompleteness is structural
rather than incremental.**

What survives intact:

- **The diagnosis.** "A declarative mutation plan can only read rows by primary key" is
  exactly right and is the first blocker in 9 of my 11 mutations too. Finding 1 is not
  in question.
- **The direction.** A bounded, indexed, visibility-composed read into a plan binding is
  the right primitive, and §Part 0(b) shows its machinery is already in the executor
  with a *richer* predicate vocabulary than the proposal asks for.
- **Rung A is real.** Two of my eleven mutations are blocked on exactly it, and one of
  them (M6) is otherwise a complete plan.
- **The platform's concurrency story survives contact with a range invariant, which I
  did not expect.** §2.3: range-granular capture is shipped and predicate-complete on
  the handler path, and plan steps run inside the commit transaction, so a plan-side
  overlap check would be serializable by construction. This is a *stronger* position
  than the corpus currently believes it is in.

What does not survive:

- **"All four are the same primitive at different `take` values."** They are the same
  primitive at different `take` values *along one axis*. My hardest read is `take(1)`
  and unreachable. Cardinality is not the variable that matters.
- **"The bound is already authored."** Only where the read has no clock-invalidated
  rows in it. In an app with expiring state the take is a correctness parameter.
- **"100% of mutations become plans."** 27% of mine do, and the 73% split roughly evenly
  between a read-addressing gap and a write-shape gap.
- **Finding 3's count rule.** It admits a count that returns a wrong number (§2.5).

## 3.2 Ranked: what the model misses

**1. Rung E — interval addressing.** A bound read whose last index column takes a range
predicate and a direction:

```js
readRange('bookings', 'by_resource_blocking_exclusion', {
  eq: { resourceId: arg('resourceId'), blocksCalendar: lit(true) },
  range: ltFilter('exclusionStart', bindingRef('newExclusionEnd')),
  order: 'desc',
  take: lit(8),
  bindAs: 'predecessor',
})
```

Sub-parts, in dependency order: (E1) range on the last index column; (E2) `order`,
which E1 is unsound without; (E3) not-equal against a bound id, for self-exclusion;
(E4) `count(binding, predicate)` and `find(binding, predicate)` over the result.

E4's `find` is worth separating: **ranked selection** — first item in an ordered
binding satisfying a predicate — is a different aggregate from `count`, it is what
every queue in every product needs, and no proposal in the corpus has it. If you prefer
to split the rungs, call E the range read and **E′ the ranked selection**.

Rung E is first on this list partly because §2.3 makes it cheaper than it looked. The
predicate vocabulary exists in the filter type; `deleteWhere` already executes a
range-filtered, visibility-composed `QueryPlan` inside the commit transaction; the
capture-and-validate layer already evaluates range predicates. E is largely an
*exposure* problem — bind the rows instead of deleting them, and add `order`, `take`,
and `indexed_by`, which the existing `QueryPlan` struct already has fields for.

**2. Rung F — bounded conditional and set-oriented writes.** `insertIf(cond, table,
values)`, `patchIf`, and `patchWhere(table, filter, values)`. All three keep the write
set statically bounded. `patchWhere` is `deleteWhere` with `UPDATE`, reusing the same
`QueryPlan` and `build_query_sql` path (`storage.rs:6344`), and it is the step this app
needed most often. Note that F is not on the ladder's axis at all — the ladder is four
rungs of *reading* and six of my eleven mutations are blocked on *writing*.

**3. Rung G — declared constraints (schema language, not plan steps).** Exclusion
constraints, partial unique indexes, derived columns, append-only tables (§2.7). This is
the highest-*leverage* item even though it is third in urgency, because each of these
converts a hand-maintained invariant into an enforced one, and because a constraint
that the engine holds cannot be forgotten by the next mutation someone writes. G is
also the only item that would have made `coterie`'s missing scope checks impossible
rather than merely absent.

**4. Sums, and their disclosure profile.** `sum(binding, expr)` is needed and is not a
trivial extension of `count` (§2.5, failure 2). Flagged as reasoned, not measured.

**5. A note on what is *not* on this list, and should be struck from `ANSWER.md`.**
Range-granular capture, listed there as uncosted new machinery and a blocking
correctness prerequisite, is shipped on the mutation handler path (§2.3). I put it at
the top of my own list before checking, which is the same error in the same direction.

Two things I deliberately did **not** put on the list, having considered them: general
iteration (M7's per-occurrence read loop is genuinely out of profile and should stay
there — the right answer is that `createSeries` is a JS handler forever), and the
interval complement in Q1 (a fold producing a variable-length result is a query-shape
problem, not a mutation-IR problem, and `defineJsQuery` is the correct home for it).

## 3.3 Where changing the product requirement is the right answer

**Yes, in two places, and they are good trades.**

**(a) Waitlist standing: display a maintained rank, never a computed count.** The
product asks "you are #4." Computing it needs a count over other members' private rows
— the exact shape Finding 3 exists to police, and §2.5 shows the rule mishandles it.
The product answer is a maintained `waitingCount` on the resource plus the entry's own
`position`, which is exact, discloses nothing but an aggregate the resource's own
members are entitled to, and needs no new primitive. **This is strictly better product
engineering, not a concession.** It is also the only design that stays correct under
concurrent withdrawals, since a computed rank is stale the moment someone ahead leaves.

**(b) Recurrence: a bounded materialization horizon, not "forever."** `MAX_OCCURRENCES
= 26` with a cron extending the horizon. This makes the whole recurrence feature
tractable — occurrences are real rows, so overlap checks see them, cancelling one is a
one-row patch, and ending a series is a bounded range patch. The alternative (store
only the rule) makes the overlap predicate range over a *generated* set, which nothing
in this system can do, and forces exception rows that every reader must subtract.

**When (b) is not acceptable, precisely:**

- **A clinic or university publishing a full academic year or a physician's 12-month
  schedule.** The horizon *is* the product; a patient booking 8 months out is the normal
  case, not an edge case. A 6-month materialization horizon means the calendar is
  visibly empty past a rolling boundary and bookings silently become possible in a slot
  that a recurring seminar will later claim.
- **Anything where the recurring series must *win* against ad-hoc bookings.** With a
  horizon, an ad-hoc booking placed past the horizon takes a slot the series will need,
  and extending the horizon then fails. The series's priority claim has to exist
  independently of materialization — which is a second, sparser kind of blocking row
  ("reserved for series S") and a genuinely harder design.
- **Any regulated context that must show the full committed schedule on demand.** A
  horizon means the answer to "what is booked in March" depends on when you ask.

In those cases you must either raise the horizon to cover the real planning window
(cheap, and probably right — 52 occurrences is not 26 occurrences' worth of hard) or
build the sparse priority-claim row. What you must not do is keep the horizon and
pretend the calendar past it is empty.

**Where changing the requirement is *not* available at all:** T2, the reschedule
laundering. "Let users move a booking" and "charge for late cancellations" are both
non-negotiable in every real booking product, and their interaction is the exploit. The
frozen policy anchor is the only fix, and it needs a schema-level immutability
declaration to be safe (rung G). Similarly T3 — "cancelled bookings must not block, and
must not disappear" is the definition of the product, and the derived-boolean-in-an-
index-prefix workaround it forces is exactly the kind of unenforced denormalization
that LLP 0310 P18 was filed about.

## 3.4 The one-sentence version

The ladder correctly identified that plans cannot read by index and correctly proposed
one primitive to fix it — but it derived the *shape* of that primitive from an
application whose every key is an identity, and a booking app's every key is an
interval, so the same `take(1)` that closes rung A leaves this app's central invariant
inexpressible in a plan and unenforceable in the schema, even though every mechanism it
would need is already sitting in the kernel one layer down.

## Confidence

**High, read from source rather than inferred:** the step and expression vocabulary
(`guide/backend/declarative-plans.md`, `define.mjs`); `deleteWhere`'s range-filter
capability and its `QueryPlan`/`build_query_sql` reuse (`storage.rs:6344`); the
existence and predicate-completeness of range-granular captured reads
(`CapturedReadKind::Query` at `snapback-types/src/storage.rs:401`,
`validate_captured_read_set` at `storage.rs:16119`, `filter_matches_expected` at
`live_matcher.rs:3234`); the JS query builder's `.lt/.gte/.order/.take` surface
(`ctx.d.mts`, used throughout `demos/coterie`); `any-of`'s 2–8-arm owner-or-membership
constraint (`define.mjs:441`); the `call('len', …)` correction. The disjointness proof
in §2.1 is mathematics and stands on its own.

**Medium-high:** the per-mutation classification in §2.8. Same method and same
limitation as LLP 0329.008 — first missing construct by inspection, no codegen run. M9
is the only one I would call verified. Also medium-high: §2.3's claim that a plan-side
range read would need no conflict validation, which rests on the source comment at
`storage.rs:5454` plus `deleteWhere` executing against `&tx`. I did not write a
concurrent test, and it assumes a new step would be built the way `Get` and
`DeleteWhere` are.

**Medium:** the claim that Finding 3's rule admits a silently-wrong count (§2.5). The
logic follows from the rule as written plus `waitlistEntries`' visibility, but it
assumes rule (a) is implemented as "filter the domain by caller visibility, then count"
rather than "refuse if the caller's visibility is narrower than the domain." If the
latter was intended, my objection becomes a specification-clarity point rather than a
defect — which is still worth fixing, because 0329.011 S5's own summary ("protection
makes counting safer") reads as the former.

**Reasoned but unmeasured:** the sum-disclosure argument in §2.5, and the assertion in
§2.9 that interval-keyed apps are a systematically absent corpus category (I checked the
demo directory names, not the demos).

**Withdrawn before publication, and worth recording as method.** My first draft's
lead finding was that the overlap check races because a zero-row read captures no
dependency — the negative-dependency hole moved into the write path. I wrote it as the
top-ranked item in §3.2 and flagged it "low confidence, check this first." I then
checked it, and it is false: range-granular capture is shipped and predicate-complete,
and plan steps execute inside the commit transaction so a plan-side read would not need
it at all. The retained §2.3 is the corrected finding, which is *more* favourable to the
model than the error was. This is the same failure mode as LLP 0329.011's withdrawn S1
— asserting a concurrency or disclosure defect from the shape of an application without
reading the layer that would prevent it. The general lesson for this family of
documents: **claims of the form "the platform fails to X" require reading the code that
does X, and the prior should be that a mechanism this central already exists.**
