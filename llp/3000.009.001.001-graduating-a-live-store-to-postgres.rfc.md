## 1. Summary

An application on SQLite moves to Postgres with one command, while it
serves. Its users notice at most a pause of a few seconds in writes. The move
is identity-preserving (parent §3.1). The Postgres store starts at the
SQLite store's exact head, with its `store_id`, sessions, receipts, work and
leases. So:

- no device re-acquires;
- no session ends;
- no outbox write applies twice or is lost;
- no worker loses its lease;
- no client release or application change is needed.

The mechanism follows the shape that online schema and table movers converged
on, such as Vitess `MoveTables` and gh-ost:

1. Arm change capture.
2. Copy in short chunks, replaying captured changes alongside under a
   per-key ordering rule.
3. Verify range by range while the source serves, and keep re-verifying
   changed keys until what remains fits the pause budget.
4. Fence the source under its write lock and a durable marker.
5. Verify the small remaining tail, and hand off ownership through a
   durable commit-or-abort decision.
6. Keep a reverse path open for a while.

The same format and tool run in reverse, Postgres to SQLite, to pull a
production store into a local `dev` or to roll a graduation back.

## 2. What "seamless" means

| Property | Target | How |
| --- | --- | --- |
| Application code | Unchanged | Same release, same schema and programs; only the store binding changes |
| Clients | No release, no re-acquisition | Same `store_id`, head and partition log window; resumes continue |
| Sessions and tokens | Valid throughout | Identity family copied; tokens are bound to `store_id`, which is preserved |
| Offline writes in an outbox | Applied exactly once | `_ops` receipts copied; a resend after cutover finds its receipt |
| Durable work | Continues | Requests, steps (`_effect_steps`, `_action_steps`), leases and schedules copied; tokens preserved; workers reach the same URL. Until the worker slice of child A §4.3 lands, preflight and cutover refuse while any effect is `running` or any local completion exists for an effect that is not terminal, because the worker's ledger stays on the source host. An expired lease returns an effect to `queued`, so "claimed" alone would miss that case |
| Asset URLs | Unchanged | Served by the server at `/assets/<id>` as today; bytes moved to `BlobStore` by digest before cutover |
| Write unavailability | Seconds, within a stated budget | The fence is entered only when the unverified tail fits the budget (§6). The pause scales with what changed since the last verification round, not with the store. If verification cannot outrun writes, cutover refuses rather than pausing longer |
| Read availability | Continuous, except connection drops at the switch | Reads keep being served from the source until the switch |
| Reversibility | Until the operator finalizes | Reverse capture on the target (§7) |
| Ephemeral state | Lost, as on any restart | LLP 3000.017: ephemeral rows are empty after a store replacement |
| Crash at any point | No lost or doubled writes, never two writable stores | The state machine plus a durable commit-or-abort decision per attempt; nothing reopens the source except a written abort (§5) |
| Release | Unchanged | The deployed release tree is uploaded to `BlobStore` by its artifact digest before cutover; the target's activation record names it (child A §4.2) |
| Authority clock | Monotone | `_meta.time_audience_clock` is copied. The target's writers use `max(wall clock, pinned clock)`, so a target host whose clock lags the source never pins an earlier time |

Not promised: no pause at all, two live writers, a schema or release change
during graduation, or graduation between different releases.

## 3. Preflight: `snapback4 graduate check`

Preflight is read-only against both sides. It refuses with named codes:

- **Target.** Postgres version, roles (child A §8), TLS, an empty target
  schema, no extensions required. It reports the pooler mode, replication
  mode and `max_connections`.
- **Release.** The running binary supports graduation. The target will be
  created by the same binary and release. Every feature the schema uses has
  Postgres parity (child A §9). A not-yet-ported feature refuses and names it.
- **Data portability.** Existing index entries over the portable 2,048-byte
  bound are allowed to remain on SQLite. They cannot move, so preflight
  counts them per index with the existing refusal and its rewrite. The same
  goes for label bounds and for any row image that fails to decode under the
  current schema.
- **Assets.** A `BlobStore` is configured and reachable. Preflight reports
  the byte total and checks the ledger against the files: a missing file is a
  refusal, an orphan file a warning.
- **Estimate.** Rows, index entries, log window, assets and bytes, with a
  copy-time estimate from a sampled chunk rate. Preflight also predicts the
  capture lag at the current write rate.

## 4. Copy and capture

### 4.1 Capture first

`graduate start` arms change capture on the source before any row is copied.

- **Mechanism: triggers on the SQLite store.** For the copy's duration the
  adapter installs `AFTER INSERT/UPDATE/DELETE` triggers on every table of
  every durable family. Each writes `(jid, table, key, op, image)` into
  `_graduation_journal`. `jid` is an `INTEGER PRIMARY KEY` and SQLite has one
  writer, so `jid` is a total order of every durable write, including writes
  that never advance the commit head: session mints, claims, lease renewals,
  sweeps.
- **Why triggers rather than engine instrumentation.** A trigger cannot be
  forgotten by a code path. A missed write would be the worst failure here: a
  silent divergence found weeks later. Instrumenting each writer would need
  every present and future write site to cooperate. The triggers are
  generated from the family registry and checked against `sqlite_master`, so
  a table without a trigger refuses `start`.
- **Cost.** One extra insert per row write during graduation only. Preflight
  measures it.
- **Mapping.** Triggers journal SQLite's physical tables (`r` keyed by catalog number, `i` by index number, internal tables). So the replayer carries a per-table mapping from each SQLite table to its family's logical record. That is table translation for the capture path only. The copy and the target still go through the family contracts.
- **Recursive triggers.** Capture runs with `PRAGMA recursive_triggers = ON`. Otherwise an `INSERT OR REPLACE` that resolves a non-key `UNIQUE` conflict (for example `_credentials.email`) deletes another row without firing its `DELETE` trigger.
- **Disarm.** Finalizing or abandoning the graduation drops the triggers and
  the journal.

### 4.2 Chunked logical copy

The copier reads each family through its logical export (child A §4.1) in
chunks of bounded rows and bytes. Each chunk is a short SQLite read
transaction, so there is no long-lived snapshot holding back WAL checkpoints
on a large store. It writes to Postgres with `COPY … FROM STDIN (FORMAT
binary)` through the family's import.

- **Managed rows.** Imported through the Postgres adapter's put path, which
  computes index entries with the shared key encoding. Index entries are
  then compared by digest (§6), not copied. This proves the two adapters
  encode the same keys from the same rows.
- **The partition log.** Copied whole, with `_commits` and the
  change-evidence window. Sync reconstructs authority from the whole
  membership history, and no re-acquisition path exists for a device behind
  the head (child A §7.3). Once retention exists, graduation copies its
  checkpoint plus the suffix, and the digest covers the checkpoint.
- **Release tree.** The deployed tree is uploaded by its artifact digest, as `deploy` does on Postgres (child A §4.2).
- **Asset bytes.** Uploaded to `BlobStore` by digest, verified by re-hashing,
  idempotent. A new upload during graduation goes to both: the source keeps
  its local file, and the ledger row's capture carries the digest the
  replayer uploads.

### 4.3 Replay and per-key ordering

The replayer applies journal entries to the target in `jid` order. Copy and
replay run at the same time, so that a large store's journal does not grow
for the whole length of the copy. Running them together needs a per-key
ordering rule, because a chunk can read key K at source point p, the source
can then write K at `jid` j > p, and the replayer can apply j before the
chunk's older image lands. Without a rule, that stale image would win
(round 2, §11).

- **Per-key version.** During graduation every target record carries the
  `jid` it reflects. A chunk's records carry the journal's maximum `jid` read
  in the same short source transaction as the chunk; a replayed entry
  carries its own `jid`. A write applies only if its `jid` is at least the
  stored one. Replayed deletes leave tombstones with their `jid` until
  `finalize`, so a later-landing chunk image cannot resurrect a deleted
  row. Applying writes this way is idempotent and commutative per key.
  Each key converges to its latest journaled image, or to its chunk image if
  the journal never touched it, whatever order chunks and entries land in.
- **Positions.** The replayer records its position in the target in the same
  transaction as each applied batch, so a crash resumes without a gap.
- **Rate.** The replay rate must exceed the source's write rate. Preflight
  predicts the lag, and a lag that stays large refuses cutover rather than
  growing the pause.

Convergence holds per key. The target is never taken as a consistent image
at an arbitrary `jid`. Only verified positions (§6) are used for comparison
and cutover.

### 4.4 Consistent points without long snapshots

A *consistent point* is a source point aligned with transactions:

1. Take SQLite's write lock (`BEGIN IMMEDIATE`).
2. Record the journal's maximum `jid`, which is now a transaction boundary.
3. If a source snapshot is needed, open a read transaction on a second
   connection **and read from it** while the lock is still held, so its
   snapshot is actually pinned.
4. Release the lock. The pause lasts milliseconds.

Graduation never holds a source snapshot for the length of an O(store)
operation. That would pin SQLite's WAL checkpoint for the whole operation,
which is the reason §4.2 copies in short chunks. Verification (§6) therefore
works range by range, each range under its own short consistent point.

## 5. Cutover

Round 1 showed that an admission-list fence leaks, because read paths
commit. Round 2 showed that reopening the source after reading "not live"
from the target is unsafe: a handoff that is delayed or ambiguously
acknowledged can still commit after the read (§11). The cutover is therefore
a state machine with an explicit, durable, mutually exclusive decision per
attempt.

**Records.**

- The source and the target each keep `_graduation`, with states `copying`,
  `prepared`, `handed-off` and `live`.
- The target also keeps `_graduation_attempts(attempt, decision)`, where
  `decision` is null, `commit` or `abort`. A decision, once set, never
  changes.
- The target is created **sealed**: `serve` refuses to open a target whose
  state is not `live`.
- Every writing `StoreTx` on the source refuses while the source is
  `prepared` or `handed-off`. It checks this as it checks the owner token
  (child A §5.1).

`graduate cutover` with a pause budget (default 10 s):

1. **Insert the attempt row** with a null decision, before any fence.
2. **Hold** new durable requests. Reads that cannot commit continue.
3. **Lock** SQLite (`BEGIN IMMEDIATE`). Every source write, including
   read-triggered commits (time-audience pins, one-view asset views), has
   now finished or waits behind the lock.
4. **Prepare the source.** In the locked transaction, record `prepared` with
   the attempt id and the final `jid`, the journal's maximum, then commit.
   From this commit on, nothing can write the source or append to the
   journal.
5. **Catch up and verify** through the final `jid` (§6, the in-pause step).
6. **Hand off.** In one Postgres transaction:
   - `UPDATE _graduation_attempts SET decision = 'commit' WHERE attempt = $a
     AND decision IS NULL`, which must affect one row;
   - take `_owner` and its token;
   - arm reverse capture: the target's triggers on every family table, so
     its first application write is already journaled;
   - set `_graduation.state = 'live'`.
7. **Release.** Mark the source `handed-off`. `serve` opens the target.
   Held requests are admitted against Postgres, and held change polls close
   with a reconnect hint.

**Abort.** To abort, whether because the budget ran out, verification
failed or an operator asked, the coordinator commits `UPDATE
_graduation_attempts SET decision = 'abort' WHERE attempt = $a AND decision
IS NULL` on the target. Only after that commit succeeds does the source
return from `prepared` to `copying` and admit held requests on SQLite. The
handoff's conditional update and the abort's take the same row lock, so
exactly one of them can win. A delayed handoff that arrives after the abort
affects no row and rolls back.

**Recovery,** run at every process start on either store, and by
`graduate` itself:

- **Target decision is `commit`.** The target is live. A source still in
  `prepared` moves to `handed-off`.
- **Target decision is `abort`.** The source may return to `copying`.
- **Decision is null, or the target is unreachable.** The source stays
  `prepared`, fail-closed. Recovery may *write* the abort decision, which
  then wins. It may not infer one from a read. Lacking a reply, a timeout,
  or a read showing "not live" is not knowledge that the handoff aborted.
- **Target permanently lost before a decision.** The only way out is
  `graduate abandon --target-destroyed`. The operator attests that the
  target database no longer exists, and the command reopens the source.
  It is documented as the one manual override.

Reversal (§7) runs the same machine in the opposite direction, with the
attempt row on the SQLite side.

## 6. Verification

Verification advances a **verified position** while the source keeps
serving. The pause then only covers what changed after the last verified
position, and that is kept within the budget before the fence is entered
(round 2, §11).

1. **Range verification, outside the pause.** Each family's export defines
   a canonical record order. The verifier walks it in key ranges. For each
   range it:
   - takes a short consistent point (§4.4) and reads the range's source
     records under it;
   - waits until the replayer has passed that point's `jid`;
   - compares the range on the target. Records whose per-key `jid` is newer
     than the point are deferred to the delta.

   Derived state (index entries, cap occupancy) is recomputed for the range
   and compared too.
2. **Shadow comparison, outside the pause.** The store oracles' machinery
   (`snapback4-difftest`, LLP 3000.035 §5.1) runs a sample of the
   application's compiled queries, plus sync snapshot and stream pages for
   sampled principals and partitions. They run against a pinned consistent
   point on both stores. Pinning both target and source for a sample is
   short, because the sample is bounded. One disagreement refuses cutover.
3. **Delta rounds, outside the pause.** The journal names every key changed
   since its range was verified. The verifier re-verifies those keys, row
   and derived state, in rounds. Each round advances the verified position.
   The fence is entered only when the unverified tail fits the pause budget:
   keys, bytes, and the verifier's measured rate. If verification cannot
   outrun the write rate, cutover refuses and reports both rates. It never
   enters a pause it cannot finish.
4. **The in-pause step.** After the source is `prepared`, the remaining tail
   is verified: changed keys with their derived state, plus the head,
   `store_id`, generation and family counters. Every asset and
   release-artifact digest in the ledger must be present in the blob store
   and must re-hash correctly; digests added since the last round are
   checked here.
5. **After cutover.** The target's complete digest is recomputed at leisure
   and recorded in the graduation report.

Graduation time and its limits are child C's W13 cell. It measures
verification throughput against the write rate, source WAL growth, the
delta size at the fence, and the pause, not only the pause.

## 7. Reversal and the reverse direction

- **Revert window.** Reverse capture is armed in the handoff transaction
  (§5 step 5), so every target write is journaled. It uses **triggers**, the
  same fail-closed mechanism as §4.1. Family writers would reintroduce the
  missed-site risk that capture exists to remove. `graduate revert` replays
  the journal onto the retained SQLite source and materializes every blob
  written since cutover back into `<store>/assets/`, because SQLite serves
  bytes from there. It cuts back through the same state machine, with the
  same identity, barriers, delta comparison and pause budget, in the
  opposite direction. `graduate finalize` ends the window, drops the
  journals and releases the source file. The window has a default length
  (for example 7 days), and the source refuses writes throughout.
- **The reverse direction as a product.** `snapback4 data pull` (Postgres to
  SQLite, from a barrier) uses the same families, format and blob
  materialization to bring a production store into `dev`. The copy is
  always a **new incarnation**, never the production identity, so a pulled
  copy cannot be mistaken for the store.
- **Backup.** The logical export at a barrier is also a portable backup
  format that does not depend on the engine. It does not replace provider
  PITR (LLP 3000.009 §9).

## 8. What graduation does not handle

- A release change during graduation. Graduation refuses an activation, and
  an activation refuses during graduation.
- Several serving processes on the source. SQLite has one, by construction.
- A source that cannot reach the target at the required rate. That is a
  preflight refusal, with the measured lag.
- Stores above the size the scale RFC measures. The cell is graduation time
  against store size, and the report states the largest store qualified.

## 10. Alternatives considered

- **Stop, export, import, start** (LLP 3000.009 §4.5's "explicit export and
  import"). Simple and safe, but the downtime grows with the store, which is
  exactly when an application is large enough to graduate. It stays, as G0's
  `data pull` and as a fallback mode (`graduate --offline`).
- **Copying SQLite WAL frames or pages** (Litestream or LTX style, as in
  Snapback 1's LLP 0188). Pages are SQLite's physical format and cannot be
  applied to Postgres.
- **Dual writes from the engine during the copy.** Each commit would need to
  succeed on both stores, putting Postgres's latency and availability on the
  source's commit path before the operator has chosen it. Capture plus replay
  keeps the source's commit path unchanged except for the trigger insert.
- **Re-acquiring every device after the move.** This is what a new
  incarnation forces, and the reason identity preservation is the central
  decision. For a store with many devices, re-acquisition is a thundering
  herd that the scale RFC would measure as a load spike.
- **Hosted graduation only** (a managed service moves the store). It may come
  later. The self-hosted command comes first because the self-hosted binary
  is the target LLP 3000.009 ruling 5 names.

## 11. Panel revision

The one-round panel (Astra max, Fable xhigh, Grok 4.7 xhigh; parent §9)
judged this document sound with major issues. Revision 1 changes:

- **§5:** the fence had been an admission list, and read paths that commit
  (time-audience publication, one-view asset reads) escaped it. The fence is
  now the source's write lock plus a durable `prepared` marker that every
  writing transaction checks. The cutover is a state machine with
  crash-safe recovery and a sealed target. Reverse capture is armed in the
  handoff transaction itself.
- **§4.3–§4.4, §6:** a replay position was not a consistent snapshot, and
  the digest that gated the pause was O(store). Verification now runs at
  transaction-aligned barriers against a held source snapshot, and the
  pause compares only the keys changed since the barrier. Blob presence is
  gated.
- **§4.2:** the log is copied whole, because retention by deletion would
  break authority reconstruction (child A §7.3).
- **§4.1, §2:** the capture mapping and recursive triggers are stated, and
  worker completions are constrained until child A §4.3 lands.

### Round 2 (revision 2)

Round 2 (Astra, Fable and Grok as deltas; Muse fresh) found the remaining
cutover and verification defects:

- **Recovery reopened the source on a read of "not live"** (Astra N1, Grok
  N1, both FUNDAMENTAL; Fable note 1). A delayed handoff could commit after
  that read, leaving both stores writable. Each attempt now has a decision
  row on the target; handoff and abort are conditional updates of that row,
  and the source reopens only after a written abort (§5).
- **The pause still grew with the store** (Grok N2, FUNDAMENTAL; Astra N2;
  Muse F4; Fable note 2). Changes kept accumulating during the O(store)
  comparison, and the held snapshot pinned the WAL. Verification now works
  range by range under short consistent points and keeps re-verifying
  changed keys outside the pause, entering the fence only when the tail fits
  the budget (§4.4, §6).
- **Concurrent copy and replay could land a stale chunk image after its
  replay** (Fable N2). Per-key `jid` ordering with tombstones (§4.3).
- **Smaller items:**
  - snapshots are pinned by reading under the lock (Astra);
  - derived state is verified in the delta, and the release tree is
    uploaded (Grok);
  - the interim worker fence covers expired leases (Grok N6);
  - the authority clock is carried (Muse).
