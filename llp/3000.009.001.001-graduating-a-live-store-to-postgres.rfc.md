## 1. Summary

An application on SQLite moves to Postgres with one command, while it
serves. Its users notice at most a pause of a few seconds in writes. The move
is identity-preserving (parent §3.1). The Postgres store starts at the
SQLite store's exact head, with its `store_id`, sessions, receipts, work and
leases. So:

- no device re-acquires;
- no session ends;
- no outbox write applies twice or is lost;
- no worker loses its lease;
- no client release or application change is needed.

The mechanism follows the shape that online schema and table movers converged
on, such as Vitess `MoveTables` and gh-ost:

1. Arm change capture.
2. Copy in short chunks.
3. Replay the captured changes until the target is close behind.
4. Fence writes briefly.
5. Drain, verify, and switch the store binding.
6. Keep a reverse path open for a while.

The same format and tool run in reverse, Postgres to SQLite, to pull a
production store into a local `dev` or to roll a graduation back.

## 2. What "seamless" means

| Property | Target | How |
| --- | --- | --- |
| Application code | Unchanged | Same release, same schema and programs; only the store binding changes |
| Clients | No release, no re-acquisition | Same `store_id`, head and partition log window; resumes continue |
| Sessions and tokens | Valid throughout | Identity family copied; tokens are bound to `store_id`, which is preserved |
| Offline writes in an outbox | Applied exactly once | `_ops` receipts copied; a resend after cutover finds its receipt |
| Durable work | Continues | Requests, steps, leases and schedules copied; tokens preserved; workers reach the same URL |
| Asset URLs | Unchanged | Served by the server at `/assets/<id>` as today; bytes moved to `BlobStore` by digest before cutover |
| Write unavailability | Seconds, independent of store size | Bounded by the capture tail at the fence, not by the copy |
| Read availability | Continuous, except connection drops at the switch | Reads keep being served from the source until the switch |
| Reversibility | Until the operator finalizes | Reverse capture on the target (§7) |
| Ephemeral state | Lost, as on any restart | LLP 3000.017: ephemeral rows are empty after a store replacement |

Not promised: no pause at all, two live writers, a schema or release change
during graduation, or graduation between different releases.

## 3. Preflight: `snapback4 graduate check`

Preflight is read-only against both sides. It refuses with named codes:

- **Target.** Postgres version, roles (child A §8), TLS, an empty target
  schema, no extensions required. It reports the pooler mode, replication
  mode and `max_connections`.
- **Release.** The running binary supports graduation. The target will be
  created by the same binary and release. Every feature the schema uses has
  Postgres parity (child A §9). A not-yet-ported feature refuses and names it.
- **Data portability.** Existing index entries over the portable 2,048-byte
  bound are allowed to remain on SQLite. They cannot move, so preflight
  counts them per index with the existing refusal and its rewrite. The same
  goes for label bounds and for any row image that fails to decode under the
  current schema.
- **Assets.** A `BlobStore` is configured and reachable. Preflight reports
  the byte total and checks the ledger against the files: a missing file is a
  refusal, an orphan file a warning.
- **Estimate.** Rows, index entries, log window, assets and bytes, with a
  copy-time estimate from a sampled chunk rate. Preflight also predicts the
  capture lag at the current write rate.

## 4. Copy and capture

### 4.1 Capture first

`graduate start` arms change capture on the source before any row is copied.

- **Mechanism: triggers on the SQLite store.** For the copy's duration the
  adapter installs `AFTER INSERT/UPDATE/DELETE` triggers on every table of
  every durable family. Each writes `(jid, table, key, op, image)` into
  `_graduation_journal`. `jid` is an `INTEGER PRIMARY KEY` and SQLite has one
  writer, so `jid` is a total order of every durable write, including writes
  that never advance the commit head: session mints, claims, lease renewals,
  sweeps.
- **Why triggers rather than engine instrumentation.** A trigger cannot be
  forgotten by a code path. A missed write would be the worst failure here: a
  silent divergence found weeks later. Instrumenting each writer would need
  every present and future write site to cooperate. The triggers are
  generated from the family registry and checked against `sqlite_master`, so
  a table without a trigger refuses `start`.
- **Cost.** One extra insert per row write during graduation only. Preflight
  measures it.
- **Disarm.** Finalizing or abandoning the graduation drops the triggers and
  the journal.

### 4.2 Chunked logical copy

The copier reads each family through its logical export (child A §4.1) in
chunks of bounded rows and bytes. Each chunk is a short SQLite read
transaction, so there is no long-lived snapshot holding back WAL checkpoints
on a large store. It writes to Postgres with `COPY … FROM STDIN (FORMAT
binary)` through the family's import.

- **Managed rows.** Imported through the Postgres adapter's put path, which
  computes index entries with the shared key encoding. Index entries are
  then compared by digest (§6), not copied. This proves the two adapters
  encode the same keys from the same rows.
- **The partition log.** Copied for the retained window only (child A §7.3).
  Resumes below that floor would re-acquire after graduation exactly as they
  would have before.
- **Asset bytes.** Uploaded to `BlobStore` by digest, verified by re-hashing,
  idempotent. A new upload during graduation goes to both: the source keeps
  its local file, and the ledger row's capture carries the digest the
  replayer uploads.

### 4.3 Replay

The replayer applies journal entries in `jid` order to the target. Each entry
is a full image or a delete, and applying one is idempotent. So applying the
journal from before the first chunk over the chunked copy converges, per
key, to the source's latest state:

- a key not written after its chunk was copied keeps the copied value;
- a key written afterwards ends at its last journal image.

An older journal entry can briefly regress a key the copy had already taken
newer. A later entry restores it, and the target is consistent only at a
replayed `jid`, which is the only point verification and cutover use. The
replayer records its position in the target in the same transaction as each
applied batch, so a crash resumes without gaps.

The replay rate must exceed the source's write rate; preflight's lag
prediction checks this. The replayer batches entries into one Postgres
transaction per batch. A long, slow-moving lag refuses cutover rather than
growing the pause.

## 5. Cutover

`graduate cutover` with a pause budget (default 10 s):

1. **Fence.** The source stops admitting durable writes. Mutations, action
   admissions, claims, mints and uploads are held for up to the remaining
   budget, not refused. Reads, sync pages and change polls continue against
   the source, which no longer changes. Schedules and sweeps stop.
2. **Drain.** In-flight transactions finish, and the journal's final `jid`
   is fixed.
3. **Catch up.** The replayer applies through the final `jid`.
4. **Verify.** The quick digest (§6) must match: head `seq`, `store_id`,
   generation, row and entry counts and rolling digests per family. On a
   mismatch, unfence the source and refuse. Nothing has switched.
5. **Transfer ownership.** In one Postgres transaction, take the store's
   `_owner` token and set `_graduation.state = 'live'`. Mark the source
   `graduated(to, at, final_jid)`; from now on it refuses to open for writes
   except through `graduate revert`.
6. **Switch.** `serve` reopens on the Postgres binding. In P1 the same
   process does this; with a fresh process, the old one hands off held
   requests by closing them with a retryable status. Held requests are then
   admitted against Postgres. Held change polls are closed with a reconnect
   hint, and clients resume at the same `store_id` and head.
7. **Arm reverse capture** on the target (§7).

Steps 1 through 6 bound the user-visible write pause. Two things are
deliberately excluded from it: the copy, and the complete digest, which runs
before cutover at a replayed `jid` and again afterwards. If the pause budget
expires before step 5, the cutover aborts, the source unfences, and held
requests are admitted on the source. They pause, but none is lost.

## 6. Verification

- **Quick digest.** Each family's export defines a canonical record order and
  a rolling SHA-256 over canonical bytes. Managed rows are digested per table,
  index entries per index, and the log over the retained window. Identity,
  work, receipts and the rest are digested per family. Both adapters compute
  it, and it gates cutover (§5 step 4).
- **Complete comparison before cutover.** The copier runs the store oracles'
  machinery (`snapback4-difftest`, LLP 3000.035 §5.1) as a shadow comparison.
  A sample of the application's own compiled queries, plus sync snapshot
  pages for sampled partitions and principals, run against both stores at the
  same replayed `jid`. The comparison is exact over the full outcome record,
  as the difftest compares it, and a single disagreement refuses cutover.
- **After cutover.** The complete digest is recomputed on the target at its
  first head and recorded in the graduation report beside the source's final
  digest.

## 7. Reversal and the reverse direction

- **Revert window.** After cutover the target captures changes into its own
  journal, through the same store-neutral capture on Postgres: triggers, or
  the adapter's family writers. `graduate revert` replays them onto the
  retained SQLite source, fences Postgres and cuts back, with the same
  identity, digests and pause budget. `graduate finalize` ends the window,
  drops the journals and releases the source file. The window has a default
  length (for example 7 days), and the source stays read-only throughout.
- **The reverse direction as a product.** `snapback4 data pull` (Postgres to
  SQLite, from a stopped copy or a capture) uses the same families and format
  to bring a production store into `dev`. The copy is always a **new
  incarnation**, never the production identity, so a pulled copy cannot be
  mistaken for the store.
- **Backup.** The logical export at a replayed point is also a portable
  backup format that is independent of the engine. It does not replace
  provider PITR (LLP 3000.009 §9).

## 8. What graduation does not handle

- A release change during graduation. Graduation refuses an activation, and
  an activation refuses during graduation.
- Several serving processes on the source. SQLite has one, by construction.
- A source that cannot reach the target at the required rate. That is a
  preflight refusal, with the measured lag.
- Stores above the size the scale RFC measures. The cell is graduation time
  against store size, and the report states the largest store qualified.

## 9. Increments and evidence

| Increment | Delivers | Evidence |
| --- | --- | --- |
| G0. Format | Logical export and import for every family; quick digest on both adapters; `data pull` as a stopped copy | Round trip SQLite → Postgres → SQLite gives byte-identical digests on the corpus, fixtures and a seeded Clique store; a pulled copy is a new incarnation |
| G1. Live copy | Capture triggers with registry check; chunked copy; replayer with a resumable position; preflight | Under a write load, a crash and restart of the copier and of the replayer converge to matching digests; a deliberately untriggered table refuses `start` |
| G2. Cutover | Fence, hold, drain, verify, ownership transfer, switch | A live Clique or Workroom store graduated under load with devices and workers attached. Records zero re-acquisitions, zero ended sessions, zero duplicate or lost outbox writes, zero lost leases, and the measured pause. Cutover is aborted at each step and loses nothing |
| G3. Reversal | Reverse capture, `revert`, `finalize` | Graduate, write, revert, compare digests; a revert under load |

## 10. Alternatives considered

- **Stop, export, import, start** (LLP 3000.009 §4.5's "explicit export and
  import"). Simple and safe, but the downtime grows with the store, which is
  exactly when an application is large enough to graduate. It stays, as G0's
  `data pull` and as a fallback mode (`graduate --offline`).
- **Copying SQLite WAL frames or pages** (Litestream or LTX style, as in
  Snapback 1's LLP 0188). Pages are SQLite's physical format and cannot be
  applied to Postgres.
- **Dual writes from the engine during the copy.** Each commit would need to
  succeed on both stores, putting Postgres's latency and availability on the
  source's commit path before the operator has chosen it. Capture plus replay
  keeps the source's commit path unchanged except for the trigger insert.
- **Re-acquiring every device after the move.** This is what a new
  incarnation forces, and the reason identity preservation is the central
  decision. For a store with many devices, re-acquisition is a thundering
  herd that the scale RFC would measure as a load spike.
- **Hosted graduation only** (a managed service moves the store). It may come
  later. The self-hosted command comes first because the self-hosted binary
  is the target LLP 3000.009 ruling 5 names.
