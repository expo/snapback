## 1. Summary

An application on SQLite moves to Postgres with one command, while it
serves. Its users notice at most a pause of a few seconds in writes. The move
is identity-preserving (parent §3.1). The Postgres store starts at the
SQLite store's exact head, with its `store_id`, sessions, receipts, work and
leases. So:

- no device re-acquires;
- no session ends;
- no outbox write applies twice or is lost;
- no worker loses its lease;
- no client release or application change is needed.

The mechanism follows the shape that online schema and table movers converged
on, such as Vitess `MoveTables` and gh-ost:

1. Arm change capture.
2. Copy in short chunks.
3. Replay the captured changes until the target is close behind.
4. Verify completely at a barrier aligned with transactions.
5. Fence the source under its write lock and a durable marker.
6. Catch up, compare only what changed since the barrier, and hand off
   ownership through a crash-safe state machine.
7. Keep a reverse path open for a while.

The same format and tool run in reverse, Postgres to SQLite, to pull a
production store into a local `dev` or to roll a graduation back.

## 2. What "seamless" means

| Property | Target | How |
| --- | --- | --- |
| Application code | Unchanged | Same release, same schema and programs; only the store binding changes |
| Clients | No release, no re-acquisition | Same `store_id`, head and partition log window; resumes continue |
| Sessions and tokens | Valid throughout | Identity family copied; tokens are bound to `store_id`, which is preserved |
| Offline writes in an outbox | Applied exactly once | `_ops` receipts copied; a resend after cutover finds its receipt |
| Durable work | Continues | Requests, steps (`_effect_steps`, `_action_steps`), leases and schedules copied; tokens preserved; workers reach the same URL. Until the worker-completion slice of child A §4.3 lands, preflight and cutover refuse while any effect is claimed but unsettled, because the worker's completion ledger stays on the source host |
| Asset URLs | Unchanged | Served by the server at `/assets/<id>` as today; bytes moved to `BlobStore` by digest before cutover |
| Write unavailability | Seconds, independent of store size | Bounded by the capture tail at the fence, not by the copy |
| Read availability | Continuous, except connection drops at the switch | Reads keep being served from the source until the switch |
| Reversibility | Until the operator finalizes | Reverse capture on the target (§7) |
| Ephemeral state | Lost, as on any restart | LLP 3000.017: ephemeral rows are empty after a store replacement |
| Crash at any point | No lost or doubled writes, never two writable stores | The `_graduation` state machine on both stores, resolved at every process start (§5) |

Not promised: no pause at all, two live writers, a schema or release change
during graduation, or graduation between different releases.

## 3. Preflight: `snapback4 graduate check`

Preflight is read-only against both sides. It refuses with named codes:

- **Target.** Postgres version, roles (child A §8), TLS, an empty target
  schema, no extensions required. It reports the pooler mode, replication
  mode and `max_connections`.
- **Release.** The running binary supports graduation. The target will be
  created by the same binary and release. Every feature the schema uses has
  Postgres parity (child A §9). A not-yet-ported feature refuses and names it.
- **Data portability.** Existing index entries over the portable 2,048-byte
  bound are allowed to remain on SQLite. They cannot move, so preflight
  counts them per index with the existing refusal and its rewrite. The same
  goes for label bounds and for any row image that fails to decode under the
  current schema.
- **Assets.** A `BlobStore` is configured and reachable. Preflight reports
  the byte total and checks the ledger against the files: a missing file is a
  refusal, an orphan file a warning.
- **Estimate.** Rows, index entries, log window, assets and bytes, with a
  copy-time estimate from a sampled chunk rate. Preflight also predicts the
  capture lag at the current write rate.

## 4. Copy and capture

### 4.1 Capture first

`graduate start` arms change capture on the source before any row is copied.

- **Mechanism: triggers on the SQLite store.** For the copy's duration the
  adapter installs `AFTER INSERT/UPDATE/DELETE` triggers on every table of
  every durable family. Each writes `(jid, table, key, op, image)` into
  `_graduation_journal`. `jid` is an `INTEGER PRIMARY KEY` and SQLite has one
  writer, so `jid` is a total order of every durable write, including writes
  that never advance the commit head: session mints, claims, lease renewals,
  sweeps.
- **Why triggers rather than engine instrumentation.** A trigger cannot be
  forgotten by a code path. A missed write would be the worst failure here: a
  silent divergence found weeks later. Instrumenting each writer would need
  every present and future write site to cooperate. The triggers are
  generated from the family registry and checked against `sqlite_master`, so
  a table without a trigger refuses `start`.
- **Cost.** One extra insert per row write during graduation only. Preflight
  measures it.
- **Mapping.** Triggers journal SQLite's physical tables (`r` keyed by catalog number, `i` by index number, internal tables). So the replayer carries a per-table mapping from each SQLite table to its family's logical record. That is table translation for the capture path only. The copy and the target still go through the family contracts.
- **Recursive triggers.** Capture runs with `PRAGMA recursive_triggers = ON`. Otherwise an `INSERT OR REPLACE` that resolves a non-key `UNIQUE` conflict (for example `_credentials.email`) deletes another row without firing its `DELETE` trigger.
- **Disarm.** Finalizing or abandoning the graduation drops the triggers and
  the journal.

### 4.2 Chunked logical copy

The copier reads each family through its logical export (child A §4.1) in
chunks of bounded rows and bytes. Each chunk is a short SQLite read
transaction, so there is no long-lived snapshot holding back WAL checkpoints
on a large store. It writes to Postgres with `COPY … FROM STDIN (FORMAT
binary)` through the family's import.

- **Managed rows.** Imported through the Postgres adapter's put path, which
  computes index entries with the shared key encoding. Index entries are
  then compared by digest (§6), not copied. This proves the two adapters
  encode the same keys from the same rows.
- **The partition log.** Copied whole, with `_commits` and the
  change-evidence window. Sync reconstructs authority from the whole
  membership history, and no re-acquisition path exists for a device behind
  the head (child A §7.3). Once retention exists, graduation copies its
  checkpoint plus the suffix, and the digest covers the checkpoint.
- **Asset bytes.** Uploaded to `BlobStore` by digest, verified by re-hashing,
  idempotent. A new upload during graduation goes to both: the source keeps
  its local file, and the ledger row's capture carries the digest the
  replayer uploads.

### 4.3 Replay

The replayer applies journal entries in `jid` order to the target. Each entry
is a full image or a delete, and applying one is idempotent. Applying the
journal from before the first chunk over the chunked copy therefore
converges, per key, to the source's latest state.

Convergence is a property of the end, not of every point along the way:

- chunks come from different source snapshots, so a target key can be
  newer than the replay position;
- `jid` numbers individual trigger records, not transactions.

The target is therefore treated as consistent only at a **barrier** (§4.4),
never at an arbitrary `jid`. The replayer records its position in the target
in the same transaction as each applied batch, so a crash resumes without
gaps.

The replay rate must exceed the source's write rate, and preflight's lag
prediction checks this. The replayer batches entries into one Postgres
transaction per batch. A lag that stays large refuses cutover rather than
growing the pause.

### 4.4 Barriers

A barrier is a source point that is aligned with transactions and comes
after every chunk:

1. Take SQLite's write lock (`BEGIN IMMEDIATE`). No source transaction is
   then in progress, so the journal's maximum `jid` is a transaction
   boundary.
2. Record that `jid` as the barrier.
3. Open a read transaction on a second connection. Its snapshot is exactly
   the barrier state.
4. Release the write lock. The pause lasts milliseconds.
5. Once the replayer reaches the barrier `jid`, the target and the held
   source snapshot describe the same state.

Verification (§6) runs only at barriers, against that held snapshot. A
barrier taken before the last chunk completed is invalid, and the copier
refuses to verify at it.

## 5. Cutover

The first draft fenced writes by holding a list of request kinds, which
made it an admission list rather than a lock. Several paths it called reads
still commit:

- `advance_time_audiences` on `/changes`, `/sync`, `/q/` and `/m/`;
- held change polls when an opening comes due;
- a query that materializes a pending opening;
- a one-view `GET /assets/<id>` recording its view.

The first draft also had no crash-safe handoff between the two stores, and
armed reverse capture after the target had already accepted writes (§10).
The cutover is now a durable state machine, with the source's write lock as
the fence.

**States.** Both stores record the graduation in a `_graduation` row:
`copying` → `prepared` → `handed-off` → `live`, with the same graduation
id on both sides. The target is created **sealed**: `serve` refuses to open
a target whose state is not `live`, even though the partial copy already
carries the production `store_id`.

`graduate cutover` with a pause budget (default 10 s):

1. **Hold.** New durable requests are held, not refused. Reads that cannot
   commit continue.
2. **Lock.** Take the SQLite write lock (`BEGIN IMMEDIATE`). Every source
   write, including the read-triggered commits above, has now either
   finished or waits behind the lock. Waiters past the budget fail as
   retryable.
3. **Prepare the source.** In that locked transaction, record
   `_graduation.state = 'prepared'` with the final `jid`, which is the
   journal's maximum, and commit. From this commit on, every writing
   `StoreTx` on the source refuses, from any process. It checks
   `_graduation` the same way it checks the owner token (child A §5).
   Nothing can append to the journal after the final `jid`. A source in
   `prepared` stays fenced across restarts until recovery (below) resolves
   it. This is the fail-closed marker that a token held in Postgres could
   not provide.
4. **Catch up and verify.** The replayer applies through the final `jid`.
   The cutover verification of §6 must pass: the barrier digest plus the
   delta comparison, and every ledger digest present in the blob store.
5. **Hand off.** In one Postgres transaction:
   - take `_owner` and its token;
   - arm reverse capture, the target's own triggers on every family table,
     so the target's first application write is already journaled;
   - set `_graduation.state = 'live'`.
6. **Release.** Mark the source `handed-off`. `serve`
   reopens on the Postgres binding. Held requests are admitted against
   Postgres. Held change polls close with a reconnect hint, and clients
   resume at the same `store_id` and head.

If the budget expires before step 5 commits, the cutover aborts: the source
returns from `prepared` to `copying`, and held requests are admitted on the
source. They pause, but nothing is lost.

**Recovery** from a crash at any point:

- **Target is `live`.** The target wins. A source still in `prepared` moves
  to `handed-off` and refuses writes.
- **Target is not `live`, source is `prepared`.** The step-5 transaction
  either committed or it did not. An ambiguous commit (the connection was
  lost) is resolved only by reading the target's `_graduation` row, never by
  the coordinator's lack of a reply. If the target is not `live` after that
  read, the source returns to `copying` and may serve.
- **Source is `handed-off`.** The source refuses writes except through
  `graduate revert`.

Recovery runs at every process start on either store, not only inside the
`graduate` command.

## 6. Verification

The first draft gated the pause on a rolling digest over every family. That
is an O(store) computation, and it contradicted the promise of a pause
independent of size (§10). Verification now splits by when it runs:

- **At a pre-cutover barrier, outside the pause: the complete comparison.**
  - Each family's export defines a canonical record order. Both adapters
    compute a digest over canonical bytes: managed rows per table, derived
    state (index entries and cap occupancy) per index, the whole log, and
    each durable family.
  - The source side reads the barrier's held snapshot.
  - The copier also runs the store oracles' machinery (`snapback4-difftest`,
    LLP 3000.035 §5.1) as a shadow comparison. A sample of the
    application's compiled queries, plus sync snapshot and stream pages for
    sampled principals and partitions, runs against the held source
    snapshot and the target at the barrier. The comparison is exact over
    the full outcome record, and one disagreement refuses cutover.
- **At cutover, inside the pause: the delta comparison.** The journal
  between the last verified barrier and the final `jid` names every key that
  changed. The cutover compares exactly those keys' images on both stores,
  plus the head, `store_id`, generation and the family counters. This takes
  O(delta), not O(store).
- **Blob bytes.** Every asset and release-artifact digest in the ledger must
  be present in the blob store and re-hash correctly. New digests since the
  barrier are checked in the delta.
- **After cutover.** The target's complete digest is recomputed at its first
  head and recorded in the graduation report beside the barrier digest and
  the delta.

## 7. Reversal and the reverse direction

- **Revert window.** Reverse capture is armed in the handoff transaction
  (§5 step 5), so every target write is journaled. It uses **triggers**, the
  same fail-closed mechanism as §4.1. Family writers would reintroduce the
  missed-site risk that capture exists to remove. `graduate revert` replays
  the journal onto the retained SQLite source and materializes every blob
  written since cutover back into `<store>/assets/`, because SQLite serves
  bytes from there. It cuts back through the same state machine, with the
  same identity, barriers, delta comparison and pause budget, in the
  opposite direction. `graduate finalize` ends the window, drops the
  journals and releases the source file. The window has a default length
  (for example 7 days), and the source refuses writes throughout.
- **The reverse direction as a product.** `snapback4 data pull` (Postgres to
  SQLite, from a barrier) uses the same families, format and blob
  materialization to bring a production store into `dev`. The copy is
  always a **new incarnation**, never the production identity, so a pulled
  copy cannot be mistaken for the store.
- **Backup.** The logical export at a barrier is also a portable backup
  format that does not depend on the engine. It does not replace provider
  PITR (LLP 3000.009 §9).

## 8. What graduation does not handle

- A release change during graduation. Graduation refuses an activation, and
  an activation refuses during graduation.
- Several serving processes on the source. SQLite has one, by construction.
- A source that cannot reach the target at the required rate. That is a
  preflight refusal, with the measured lag.
- Stores above the size the scale RFC measures. The cell is graduation time
  against store size, and the report states the largest store qualified.

## 10. Alternatives considered

- **Stop, export, import, start** (LLP 3000.009 §4.5's "explicit export and
  import"). Simple and safe, but the downtime grows with the store, which is
  exactly when an application is large enough to graduate. It stays, as G0's
  `data pull` and as a fallback mode (`graduate --offline`).
- **Copying SQLite WAL frames or pages** (Litestream or LTX style, as in
  Snapback 1's LLP 0188). Pages are SQLite's physical format and cannot be
  applied to Postgres.
- **Dual writes from the engine during the copy.** Each commit would need to
  succeed on both stores, putting Postgres's latency and availability on the
  source's commit path before the operator has chosen it. Capture plus replay
  keeps the source's commit path unchanged except for the trigger insert.
- **Re-acquiring every device after the move.** This is what a new
  incarnation forces, and the reason identity preservation is the central
  decision. For a store with many devices, re-acquisition is a thundering
  herd that the scale RFC would measure as a load spike.
- **Hosted graduation only** (a managed service moves the store). It may come
  later. The self-hosted command comes first because the self-hosted binary
  is the target LLP 3000.009 ruling 5 names.

## 11. Panel revision

The one-round panel (Astra max, Fable xhigh, Grok 4.7 xhigh; parent §9)
judged this document sound with major issues. Revision 1 changes:

- **§5:** the fence had been an admission list, and read paths that commit
  (time-audience publication, one-view asset reads) escaped it. The fence is
  now the source's write lock plus a durable `prepared` marker that every
  writing transaction checks. The cutover is a state machine with
  crash-safe recovery and a sealed target. Reverse capture is armed in the
  handoff transaction itself.
- **§4.3–§4.4, §6:** a replay position was not a consistent snapshot, and
  the digest that gated the pause was O(store). Verification now runs at
  transaction-aligned barriers against a held source snapshot, and the
  pause compares only the keys changed since the barrier. Blob presence is
  gated.
- **§4.2:** the log is copied whole, because retention by deletion would
  break authority reconstruction (child A §7.3).
- **§4.1, §2:** the capture mapping and recursive triggers are stated, and
  worker completions are constrained until child A §4.3 lands.
