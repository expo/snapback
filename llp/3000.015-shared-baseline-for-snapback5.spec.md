## Summary

LLP 4000 judges Snapback 5 against a Snapback 4 that carries the same
additions, so that the only difference between the arms is derived
residency. This spec is those additions, landed in Snapback 4 as ordinary
language and engine work, each reviewed on its own. Three of them are here;
`through .ref` is LLP 3000.014 revision 2 and is not part of this baseline.

1. **`written by .col`** on a column: field-level write authority, with
   private projection by default and `readable by audience` to opt out.
2. **`sequence by <ref>`** on a column: an engine-assigned, dense,
   per-parent integer, assigned at commit, provisional under prediction.
3. **A maintained view keyed by another table's row:** `view name: count T
   by U u where <predicate over T's fields and u's fields>`, maintained per
   `U` row, with a bounded background recount when a `u` field the predicate
   reads changes by more than the meter allows in the writer's transaction.

Together they let Clique's read marks, unread counts and message ordering
leave the application's hand-written helpers without a per-message receipt
row. The receipt table itself stays (LLP 4000 §3.3).

## 1. `written by`

```quarry
table members:
  conversationId: conversations
  principal: principal
  readUpTo: int default 0 written by .principal
  read <- exists members[.conversationId, viewer]
  update (old, next) <- exists members[conversationId = old.conversationId, principal = viewer, role = 'admin']
                     and next.readUpTo = old.readUpTo
```

- **Authority.** The value of a `written by .p` column may be written only
  by the principal named in column `p` of the same row. An insert sets it
  to its declared default; a supplied value is refused with
  `E_FIELD_AUTHORITY` unless the inserter is that principal. A patch that
  touches the column is authorized for that column by that principal, and
  for every other field by the row's `update` rule. The owner may patch the
  column alone with no row `update` rule; the row's `update (old, next)`
  rule may still constrain the transition (monotonic marks), as above.
- **Projection.** By default the column is **private to its owner**: it
  never appears in a log image, a query row, a shape, a cursor or a write
  result delivered to any principal other than the owner. The owner sees
  it on every device. `readable by audience` on the column makes it an
  ordinary column for reads. The implementation must deliver the private
  value to the owner's devices through the owner's own partition, not by
  filtering the group image per reader, because group images are shared
  by audience.
- **Prediction.** A write to an own `written by` column is a point write to
  a held row and predicts under the existing rules.
- **Diagnostics.** `E_FIELD_AUTHORITY` (a non-owner supplied or patched
  the column), with a rewrite naming the owner column; a `check` line per
  such column stating its visibility.

## 2. `sequence by`

```quarry
table messages:
  conversationId: conversations
  ordinal: sequence by conversationId
table members:
  conversationId: conversations
  joinedAt: sequence by conversationId
```

- **Assignment.** One counter per parent row (here, per `conversations`
  row), shared by every column in any table that declares `sequence by`
  that parent. The engine assigns the next value at commit, dense and
  monotonic per parent, inside the write's transaction, in every store
  (memory, SQLite, Postgres) with the same transactional discipline as cap
  occupancy counts. A client-supplied value is refused with
  `E_SEQUENCE_SUPPLIED`. The column is immutable by construction.
- **Prediction.** A predicted insert carries a **provisional** value
  (greater than every settled value the device holds for that parent); the
  settled write replaces it, and any page ordered by the column reorders
  when the settled image arrives. The device never publishes a provisional
  value as settled.
- **Ordering.** `last N by .ordinal` over a sequence column is a total
  order per parent, which `by .at` is not.
- **Diagnostics.** `E_SEQUENCE_SUPPLIED`; `E_SEQUENCE_PARENT` when the
  parent reference is missing or not a table reference.

## 3. A maintained view keyed by another table's row

```quarry
view unread: count messages by members m
  where .conversationId = m.conversationId and .ordinal > m.readUpTo
    and .senderId != m.principal and not .tombstone
```

- **Meaning.** One maintained value per `members` row: the number of
  `messages` rows satisfying the predicate against that row. Readable under
  the `members` row's read rule (the count is about the member, and
  discloses nothing the member could not count).
- **Maintenance on `T` events** (insert, update, delete, expiry of a
  `messages` row): the delta is applied to every `U` row whose predicate
  the event affects. For the shapes the predicate admits (an equality on a
  reference to `U`'s parent plus comparisons against `u`'s fields and `T`'s
  own fields), the affected `U` rows are found by the reference equality
  (the conversation's members), bounded by the parent's cap.
- **Maintenance on `U` field changes** (`m.readUpTo` moves): the delta is
  the count of `T` rows in the range the change uncovers or covers. When
  that range fits the writer's meter (an index range scan on
  `(conversationId, ordinal)`), it is applied in the writer's transaction.
  When it does not, the write commits the field change, the view's value
  for that row is marked **pending** (`complete: false` on reads of it),
  and a bounded background recount (self-chunking, as LLP 3000.013's
  streaming aggregates and delivery work) settles it. The writer is never
  refused for opening a large chat.
- **Admitted predicate shape.** Exactly one equality between a `T`
  reference and a `U` reference to the same parent (the key), any
  comparisons between `T` fields and `u` fields, and `T`-only conditions.
  Anything else refuses with `E_VIEW_KEY` and a rewrite.
- **Prediction.** A device holding the `U` row and the covered `T` range
  predicts the value; otherwise it reads the settled value.
- **Diagnostics.** `E_VIEW_KEY`; a `check` line stating the key and the
  bound on the writer-side recount.

## 4. Verification

Each addition lands with: language tests (parse, bind, diagnostics with
rewrites, `explain_code`), engine tests on memory and SQLite (and Postgres
where the store is touched), device tests for prediction and projection
(no wire message to a non-owner carries a private value; a provisional
sequence never publishes as settled), a guide card, a JOURNAL entry, and
the wasm measurement with a ratchet reason if the budget moves. Two blind
reviews (Astra, Grok) per addition before landing.

## Non-claims

This spec does not define `through` (LLP 3000.014), engine-derived
delivery receipts (withdrawn from LLP 4000 to a future LLP), or any
residency change. It adds three forms to Snapback 4 that stand on their
own product merit whatever Snapback 5's outcome.
