## Commission status

This document commissions a design; it does not select server-authored
buckets, declared clock quantization, scheduled purge, or any other mechanism.
It does not weaken `SNAPBACK_AUTH_CLOCK_DEPENDENT_VISIBILITY`, add a
capability, or authorize implementation.

## Summary

Decide whether Snapback should add a deterministic primitive for protected
live visibility that changes with server time, and if so define its authority,
invalidation, bounds, and generated authoring form. The current pinned-client-
clock recipe remains the only paved behavior until such a design is accepted,
implemented, and published.

## Motivation

Trending windows, expiring links, and durable typing leases all need a result
whose membership changes as time advances. The current guard correctly
refuses ambient runtime time in authorization-sensitive live evaluation.
Authors can pass a load-pinned clock and re-issue at a chosen boundary, but
independent benchmark lanes repeatedly rediscovered that pattern. LLP 0317 F3
therefore commissions a design evaluation rather than relaxing determinism.

## Questions the design must settle

1. Is the intended product shape still the existing pinned-clock recipe, or a
   primitive? If a primitive, why is scheduled purge or explicit client
   refresh insufficient?
2. If time is admitted, who authors it, what quantization is allowed, and what
   exact instant is authoritative across retries and resumed subscriptions?
3. What event advances authorization and query membership when no data row
   changes, and how is that event bounded and coalesced?
4. How do offline retention, reconnect, clock skew, and old clients interpret
   the result without treating local wall time as authority?
5. What static declaration makes cost visible before activation, and what
   ceilings/refusals prevent timer cardinality from becoming hidden work?
6. How do Explicit and Familiar source lower to one normalized contract?

## Required acceptance evidence

The design must require executable witnesses for a trending window, expiry,
and typing lease; exact boundary inclusion/exclusion; restart and reconnect;
offline stale/unknown behavior; authorization loss at a time boundary; skewed
client clocks; timer coalescing and capacity refusal; and compatibility with a
client that lacks the primitive. Every witness must preserve the current
guard for undeclared ambient time.

## Non-goals

- Weakening deterministic authorization evaluation.
- Treating client wall time as server authority.
- Claiming the existing recipe is broken.
- Choosing a mechanism in this commission.

## Open questions

All mechanism, granularity, and cost questions remain open. Review should
prefer retaining the explicit recipe if no bounded primitive is materially
safer or simpler.
