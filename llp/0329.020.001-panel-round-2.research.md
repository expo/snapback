## Codex

# Panel round 2 — Codex

## Revised position

Grok moves me on scope. I withdraw my round-one formulation that “Aquifer stays the public data tier” if *data tier* means one public query surface and one state machine for all server-derived facts.

For receipt-backed resources, the Snapback client should be the authoritative store and execution tier. A foreign fetch/write integration should be a separately declared resource family with different result and state types. Aquifer may survive above both as framework infrastructure—dependency scheduling, route and component lifetime, principal-scoped construction, cancellation, and view binding—but it must not normalize their semantics or own a second copy of their data behavior.

That is composition only after a substantial shrink. It is closer to Grok's position than my round-one label suggested.

## 1. Does the evidence channel answer Grok's charge?

An evidence channel by itself does not. If authors write the same `useQuery`, a provider is selected ambiently, and a field later says `complete` or `unknown`, Grok's charge lands completely. That is the old capability-by-form defect with better telemetry. Fable's backend grade also puts the cut in the wrong place: a Snapback execution can be partial, while a particular non-Snapback operation can have stronger app-specific guarantees than its neighboring operations.

Three things have to remain distinct:

1. The authoring declaration states the semantic contract it requires.
2. Admission checks whether an implementation can supply that contract.
3. Runtime evidence reports what happened in this particular execution.

The third cannot substitute for the first two. A receipt-backed declaration and a remote declaration therefore need different constructors and non-coercible result types. The remote result must not have Snapback's `Fresh`, `Predicted`, verdict, or covered-absence cases. A receipt-backed result may still report partial coverage by exact site because provider capability does not guarantee that every execution succeeds completely.

This is where Grok's and my positions are indeed close. We agree on the semantic split and on making it unavoidable at the authoring site. The remaining disagreement is architectural: Grok treats separate package/API identity as the safeguard; I think separately named, nominal contracts may share a compiler, scheduler, subscription mechanism, and generic cell container without sharing meaning. A generic container is harmless if it carries `SnapbackResourceState<T>` unchanged; a generic data API that projects both paths into `Rows<T> + completeness` is not.

So my per-operation evidence proposal defeats the charge only together with the type split already implicit in my round-one “different declarations” requirement. Presented as a widened provider seam under one public query API, it would be Grok's objection with extra steps.

Fable's proposed completeness field should therefore not be the seam. An internal capability manifest can help admission, and runtime evidence is still necessary, but neither is a public backend grade. “Receipt-backed” should name the strong contract; “asserted complete” remains metadata on the remote contract and cannot unlock receipt-backed behavior.

## 2. Should the foreign path deliberately feel worse?

Ergonomic asymmetry is a legitimate warning device, but “worse” is not a durable correctness mechanism. Teams under delivery pressure will wrap an ugly API, alias the convenient hook, or add a default that hides `unknown`. Taste loses to the first important Rails customer.

The durable mechanism is semantic asymmetry:

- different declaration names;
- different nominal types and state vocabularies;
- no implicit conversion from remote/asserted data to receipt-backed data;
- components that require receipt-backed behavior reject remote resources before execution;
- promotion requires a conforming Snapback server or gateway, not a client-side cast.

The foreign API can be pleasant for the job it actually does. Fetching, caching, retrying, and queueing writes need not be punitive. It should feel less powerful precisely where facts are missing: an author must handle cached/stale/server-required states, and APIs for local authorization, exact replay, and prediction simply do not exist. That consequential asymmetry will survive ergonomic polish; intentional ugliness will not.

Grok is right, however, that using the same spelling is itself a product signal. Even perfect internal types will be undermined if docs and examples teach “one `useQuery`, choose a backend later.” The paved road should be Snapback and should say Snapback. The remote road should be visibly named remote.

## 3. Aquifer composes only where it has stopped competing

Grok is right about the overlapping scope. Two owners cannot independently manage the same server-derived materialization. My round-one ownership rule was directionally right but left Aquifer too much semantic territory, especially “the view-visible state machine.” I revise that claim: the provider-specific store owns that state, and Aquifer may only transport and bind its typed representation without translating it into a common freshness model.

The ownership split should be:

| Concern | Sole owner |
| --- | --- |
| Receipt rows, verdicts, coverage, local re-execution, prediction, OCC, persistence/restoration, and reconnect reconciliation | Snapback client store |
| Fetch cache, remote freshness, retry, and any foreign outbox | The remote resource implementation |
| Dependency scheduling, route/component lifetime, cancellation, and typed view binding | Aquifer, if this shared framework layer earns its keep |
| Meaning exposed to application code | The provider-specific nominal resource type, never an Aquifer-normalized status |

Consequently Aquifer must have no generic optimistic overlay for Snapback data, no independent row eviction or persistence policy, no generic completeness bit, and no authority to turn connectivity into semantic freshness. Principal scoping can be coordinated at the framework level, but each store must enforce isolation for its own retained material.

Under that boundary, Aquifer is not a second state machine; it is closer to a resource graph and binding substrate. If the remaining implementation is merely a pass-through wrapper around Snapback subscriptions, it should be removed from that path. “Aquifer composes” is not a reason to preserve a name or abstraction that no longer performs a distinct job.

Thus, for the same scope, the answer is **shrink**: Snapback owns receipt-backed server data. Composition applies only to the adjacent framework concerns left after that shrink.

## 4. The strongest argument against my round-one position

The strongest argument is institutional rather than theoretical: calling Aquifer the public tier creates pressure to make its resources substitutable. Once it owns the hook, documentation, persistence knobs, and view state, every “internal” distinction tends to be projected into a common denominator. The word *provider* itself invites swapping implementations after authoring. My proposed ownership rule could then become a diagram respected by neither caching code nor product ergonomics, and the evidence channel would legitimize the abstraction instead of containing it.

That argument moves me. I no longer support a universal Aquifer query contract with Snapback behind it. I support two public, typed resource families, with Snapback directly visible as the receipt-backed one, and only a narrower shared framework layer underneath or around them.

What would move me the rest of the way to deleting Aquifer from server-derived data entirely is evidence that, after removing storage, prediction, persistence, freshness, and semantic state, its remaining binding/scheduling role is trivial or forces Snapback through translation points. Then direct Snapback integration is simpler and safer. What would justify keeping the narrow layer is the opposite evidence: multiple resource families demonstrably need the same lifecycle and dependency machinery, it can be parametric over their unaltered state types, and it introduces no second policy owner.

What would permit a foreign system onto the receipt-backed path is not a more persuasive completeness assertion. It is a server-side adapter or gateway that satisfies the Snapback protocol and conformance obligations, including authoritative coverage and verdict evidence. At that point it is another implementation of the strong contract, not an exception that weakens it.

The resulting direction is: make Snapback the first-class receipt-backed data tier; give foreign data a separate honest surface; retain per-operation evidence inside the strong path; and keep Aquifer only for demonstrably non-semantic composition. Shared infrastructure is acceptable. Shared meaning is not.

Your fallback — one grade everywhere, no proofs, uniformly weaker — is honest. I would take it over the proposal. I would not take it over a type split. Uniform weakness is how you avoid the defect when you refuse to have two computational models in one spelling. Exact 2 can have two models. It cannot have one spelling for both.

On cost: the asymmetry you weight is real only if “the tier” must be singular for every kind of app data. That is the premise I refuse. Route loaders, secure storage, pooled sessions, window restoration, and cross-runtime transport are not receipt-backed row stores. ## Directly to Codex

We agree on more of the *defect* than Fable and I do. We disagree on who is allowed to own the public type.

You reject rich-versus-thin backend grading. So do I. You want capabilities per operation, static requirements in the declaration, admission before execution, and a value type that cannot pretend asserted complete is receipt-backed coverage. So do I. You prefer receipt-backed / trace-certified to “proved.” I adopt that. A closure receipt is protocol evidence under a schema, verdict set, and authorization epoch. It is not a cryptographic proof and it is not eternally current. I was using “proved” as a contrast with “asserted,” and that word is doing harm if it inflates the claim.

You also correctly separate static capability from dynamic outcome. A Snapback result can be `Partial`. A thin adapter must not grow a `complete` case because one resource was mirrored carefully. Proof is a property of a result, not of a vendor. That part of round 1 stands, and you stated it more cleanly than I did.

None of that makes Snapback a provider behind Aquifer.

### 1. Does your evidence channel defeat the charge?

No. It defeats the charge against Fable’s field. It does not defeat the charge against seam-widening.

The charge was not “you forgot to split completeness into five axes.” It was: **a shared public type whose meaning depends on which provider is bound is capability-by-form, even when the runtime can see the difference.** LLP 0329’s three properties were implicit boundary, incidental determination, silent degradation. A typed channel with `requires`, admission, and separate axes can fix *silent* and *implicit* at the declaration site. It does not fix the third once Aquifer is the thing you author.

If Exact 2 apps write Aquifer resources, and Snapback is a rich execution provider that preserves evidence and *projects* verified outcomes into cell axes, the app-facing object is still an Aquifer cell. Coverage, prediction, and authorization provenance become cell state. That is the translation layer. “Aquifer need not understand the receipt internally” is exactly the loss: sites, verdicts, and `Fresh | Predicted | Partial(site ids)` survive only as whatever the projection kept. The next policy — offline launch, restoration, retry — will be written against the projection, because that is the public type.

Your `local resource` / `remote resource`, or a `requires` clause that fails to bind a row-only provider, is my type split wearing Aquifer’s grammar. If those are truly different types with no implicit coercion, and asserted complete cannot unlock receipt-backed rendering, prediction, or local auth, then you have accepted the load-bearing part of my position. What you have not accepted is the consequence: **the public tier for receipt-backed data is the type that only constructs from a compiled program plus a receipt-shaped contract.** Calling that type an Aquifer resource with a Snapback provider is packaging. Packaging is not composition of two engines. It is one engine’s API in front of the other.

So: closer than Fable, not my objection with extra steps. The extra steps (per-operation axes, admission, no normalization of asserted-complete) are right, and I take them. They are what you do *after* you refuse a shared seam. Done *as* the seam, they are how the defect becomes respectable.

Your own warning is the tell: a narrow rows-only Aquifer seam that strips receipts and rebuilds store, completeness, and prediction is the worst of both directions. A rich-provider amendment that projects Snapback into cell axes is the same maneuver with better types. The ownership rule — do not evict what a receipt still holds; do not compute a second prediction — is a confession that Aquifer must not run a store for these facts. A tier that must not materialize, must not evict, must not predict, and must not authorize is not the data tier. It is a shell. Shells that own the public types still lock authoring. That is the Draft window I said we would burn.

### 2. “It should feel worse”

This is not taste. It is the only mechanism that survived the last defect. Convenience at the call site is how 74% of writes escaped. If Rails support is wanted badly enough that the same hook is demanded, that demand *is* the defect proposing itself. Yielding to it is not pragmatism. It is repeating the incident.

Codex (and Fable’s essay, not Fable’s proposal) are right about a different point: **aesthetic friction erodes; type incompatibility does not, or not as cheaply.** People will wrap an ugly foreign API until it looks like `useQuery`. They cannot wrap away a type that has no `Predicted` and no receipt-backed `Fresh` without writing an explicit adapter that changes the type. I already required that adapter. Round 1’s slogan, “it should feel worse,” overstated the means.

**Refinement, not a change of architecture:** the mechanism is different names, different types, no implicit coercion. Ugliness is a byproduct of honesty, not a tax we levy to shame Rails users. A pretty `remote resource` that cannot be passed to a component that requires receipt-backed data is acceptable. A pretty `remote resource` that can, with a completeness field or a capability badge, is not.

Will product pressure still flatten the split? Yes. That is why the split has to live in types the compiler owns, not in guidelines, provider grades, or cell-axis documentation. If someone later unifies the spelling because a customer wants Rails to “feel the same,” that decision should be visible as deleting a type boundary, not as widening a seam.

### 3. Compose or shrink — not the same scope, and Codex is describing shrink under a compose label

Codex lists as Aquifer’s: authored cells/resources, identity and principal isolation, dependency scheduling, request lifecycle, route/server integration, replay into views, view-visible state machine.

Split that list.

**Actually backend-independent, and I was too willing to say “dies”:** identity and principal isolation, dependency scheduling, request lifecycle, route/server integration, view subscription. Aquifer (or a binding layer of that shape) can own those without being a second store. Round 1’s “shrink or die” overstated the leftover. **Move:** Aquifer does not have to die. It has to lose the job of being the store, the predictor, the completeness authority, and the authoring grammar for receipt-backed facts.

**Not backend-independent when the facts are Snapback-derived:** authored resources that are bounded programs; replay that is program re-execution; the view-visible machine `Fresh | Predicted | Partial(sites)`; optimistic overlays that are Snapback predictions. Those are the store. Codex’s ownership rule assigns them to Snapback. That is shrink. Calling the remainder “the public data tier” keeps the diagram in which Exact’s knowledge of any backend ends at whatever Aquifer’s cell can project.

Both cannot be right about the *same* scope. If the scope is “who materializes server-derived rows, who proves coverage, who predicts, who authorizes locally,” Snapback owns it and Aquifer must shrink. If the scope is “who schedules requests and binds views,” they can compose. Codex’s write-up mixes the two scopes and concludes compose. The ownership rule, applied without protecting Aquifer’s public-tier status, concludes shrink.

I will not fight a coordination layer. I will fight a coordination layer that owns the resource type.

The founder’s “one data story” is the thing that forces the mix. Non-server state, foreign fetch, and receipt-backed programs are three kinds of fact. One spelling for all three is how you get two state machines and a projection. Exact 2 can have one *local-first* story — Snapback client, Snapback wire, foreign storage behind a Snapback server — and a second, narrower story for fetch-and-cache. That is smaller than the pitch. It is the true one.

Codex’s gateway that implements the Snapback contract and issues real receipts is my §4. We agree. Codex’s thin path is acceptable only as the other type. Under Aquifer, as a provider that reports `unknown` on the same cell axes, it is Fable’s proposal with more fields.

## 4. Strongest argument against round 1 — and whether it moves me

**Fable’s cost argument, sharpened by Codex’s prototype note.**

If Snapback’s client is the public tier for receipt-backed data, something still has to own route integration, identity isolation, persistence, subscriptions, and restoration. `ClientStore` as inspected is a compact prototype: hydrate, verdicts, re-execution. It does not already contain the app-facing surface. Either Snapback grows those concerns — Fable’s late rewrite, excellent for one backend — or Exact 2 apps author *two* surfaces (Snapback for programs, Aquifer for everything else), and the pressure to unify spelling returns from inside the company rather than from Rails customers.

That is the best objection. It says my type split is correct and my packaging is incomplete: I have named the store and not the application grammar.

**Does it move me? Only on leftover Aquifer, not on the tier.**

It moves me to this: Aquifer survives as coordination and as the home of facts that are not receipt-backed. Exact 2 will have more than one authoring surface, on purpose. The product cost of that split is lower than the category error of one surface. The engineering cost of growing Snapback into a full app runtime is avoided by *not* asking it to. Persistence and restoration of receipt-backed data live in Snapback’s store; Aquifer must not layer a second eviction/prediction policy on top. That is Codex’s ownership rule, which I take as a shrink rule.

It does **not** move me to “Aquifer stays the public data tier, Snapback is a rich provider.” That is how the incomplete packaging gets “fixed” by putting the wrong name on the public type. The incomplete packaging gets fixed by teaching Exact 2 apps to author receipt-backed resources as Snapback programs, and to use a different type for foreign fetch.

**What would actually move me to Codex’s architecture:**

- Receipt-backed resources are a closed type: they only construct from program + receipt contract; they cannot be bound to a rows-and-writes provider; their result type is Snapback’s state machine, not a projection into generic cell axes.
- Aquifer, for those resources, has no store, no overlay, no completeness of its own — a binder only.
- The default tutorial never shows a remote/thin resource as the local-first path.
- And — this is the real bar — someone shows that screen-level authoring *cannot* be Snapback-shaped without reinventing Aquifer’s grammar, because views, routing, and identity are inseparable from the data declaration.

Until that last showing, “apps will want one resource grammar” is the founder’s pitch restated as inevitability. It is not evidence. ClientStore being a prototype is evidence of work, not of who should own the type.

**What would move me toward Fable’s proposal:** nothing that keeps a shared cell and a completeness field. Uniform asserted-everywhere, if Exact is unwilling to staff the type split. That is retreat, not composition.
