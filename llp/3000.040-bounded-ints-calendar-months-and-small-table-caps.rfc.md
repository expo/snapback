## 0. Summary

The app farm's six waves (LLP 3000.037) asked for three things that Quarry
answered with idioms: a range on an `int`, a calendar month, and a small
lookup table that every query could read whole. Each idiom cost builders
time, and each became a targeted diagnostic or a guide paragraph. This RFC
replaces the idioms with language. The brief was "the ideal end-game
solution", not the smallest patch.

| § | addition | surface | where it is enforced |
|---|---|---|---|
| 1 | bounded integers | `int 1..5`, `int 0..`, `int <=100`, `int -10..10`, also as list items and arguments | wire input (`E_INPUT` naming the bound), every stored write on the server and both device stores, fixtures and `/seed`, adoption of a tightened bound |
| 2 | calendar months and years | `month(t)`, `year(t)`, `monthStart(m)`, `yearStart(y)`; `month(.at)`/`year(.at)` as index and view keys; `schedule … every 1 month at day 1 09:00` and `every N months`/`every 1 year` | the shared interpreter (server and devices), computed index keys, the scheduler and the dev clock, the Lean model |
| 3 | caps for small tables | `cap N` with no `by` (one group: the whole table) | already in the engine (LLP 3000.007 §20.3); this RFC names it, fixes its refusal text, proves it on both devices and through adoption, and documents it |

Decisions in one line each:

1. A bounded int is a **new column and argument type**, `IntRange`, with
   optional inclusive bounds. An out-of-range value is `E_INPUT` naming the
   bound, wherever it enters. A range is not a separate `check`.
2. `month(t)` is the **month ordinal since 1970-01** (UTC): 681 is 2026-10.
   It is ordered and continuous, so `month(now) - 1` is last month, as
   `day(t)` counts days. `year(t)` is the calendar year (2026).
   `monthStart(m)` and `yearStart(y)` go back to a `time`.
3. A monthly schedule's boundaries are **calendar months**. A schedule that
   was down coalesces missed boundaries into one run, the same rule as fixed
   periods.
4. `cap N` without `by` stays as it is in the engine. Its refusal now reads
   `categories holds at most 50 rows`.

## 1. Bounded integers

### 1.1 What the farm met

Eleven wave-5 lanes wrote `n: int 1..10` (LLP 3000.036 §15.7). The parser
said "expected the end of the line, got 1". Wave 5 replaced that message with
a targeted `E_QUARRY_SYNTAX` whose rewrite is a `require` in every mutation
that writes the column, plus an insert rule and an update rule (optional
columns add `x = null or …`). That is three to five lines for one fact about
a column, repeated in every writer. A missed writer is a silent hole. The
analysis's 5a.1 called this the language's job. §15.7 recorded why it was
not done: a new scalar kind reaches the schema, wire validation, both device
stores, the generated types and the Lean model. This RFC does that work.

### 1.2 Surface

```quarry
table reviews:
  author: principal
  stars: int 1..5
  helpful: int 0.. default 0
  delta: int -10..10 ?
  scores: [int 0..100] <=8
  read <- .author = viewer
  insert <- .author = viewer

mutation rate(stars: int 1..5, note: text <=200):
  return insert reviews { author: viewer, stars, scores: [] }
```

- `int M..N`: M ≤ value ≤ N, both inclusive, both written. This is text's
  spelling, `text M..N`.
- `int M..`: at least M. `int 0..` is the non-negative int.
- `int <=N`: at most N, with no lower bound. Text's `<=N` means `0..N`
  because a length is never negative. An int can be negative, so `int <=N`
  has no implied zero. The guide says this in one line beside the type.
- Bounds are integer literals, optionally negative, within ±(2^53 − 1).
  M > N is a syntax error, and so is a fractional bound.
- `int >=M`, `int <N`, `int >N` and `int ..N` have one spelling each. A
  targeted `E_QUARRY_SYNTAX` gives the canonical form with the author's
  bound: `int >=1` becomes `int 1..`, and `int <10` becomes `int <=9`. This
  is the house rule: one spelling, and the refusal prints it.
- An optional bounded int is `int 1..5 ?`. A bounded list item is
  `[int 1..5] <=8`. Helper (`fn`) parameters accept the bound as well.
  Inside the program the value is an ordinary `int`, as `text 1..80` is
  ordinary text.

### 1.3 Representation

`ColumnType::IntRange { min: Option<i64>, max: Option<i64> }` and
`ArgType::IntRange { min, max }` are new variants. `Int` is unchanged. Two
other representations were considered:

- *Change `Int` into `Int { min, max }`.* Every stored schema serializes
  `"Int"`, and old backends, corpus cases and kept device stores would all
  need a decoder shim. Refused.
- *A table constraint, as text's minimum is (`Constraint::Text`).* That
  bounds only top-level columns: list items and arguments would need a
  second mechanism. It would also report `E_CONSTRAINT` for a value the
  caller supplied. Refused.

A new enum variant fails closed on an older decoder, as `ListRange` does
(LLP 3000.007 §5.4): an older device or server cannot decode the schema or
program at all, so it never accepts a value it cannot check. A schema
capability, `int-range`, also turns that decode failure into the named
`E_SCHEMA_CAPABILITY` at schema open, the way every other new semantics is
fenced.

Every place that treats `Int` as "an integer column" (ordering, key
encoding, key budgets, sums and maintained totals, insert-rule ordering,
`sql`, cost tables, the Rust emitter, cursor decoding, the SQL catalog)
treats `IntRange` the same way through one helper, `ColumnType::is_int()`.
Sites that need the exact unbounded `Int` keep it: engine-assigned
sequences, delivery positions and calendar keys. The binder's value type
stays `Ty::Int`, because a bound is a fact about the slot, not the value.

### 1.4 Where the bound is enforced

A value meets the bound wherever it crosses into a declared slot. It is not
checked on intermediate arithmetic.

| entry | check | refusal |
|---|---|---|
| a call's arguments (HTTP, `run`, the client, a device's predicted call) | `validate_arg` | `E_INPUT: rate.stars must be int 1..5, not the number 7` |
| a stored write: insert, update, upsert patch, default, the engine's row images | `validate_column`, at the same trust boundary as text's maximum | `E_INPUT: reviews.stars must be int 1..5, not the number 0` |
| fixtures and `/seed` rows | the same row validation | the fixture loader's existing `E_INPUT` line |
| a literal `default` | the binder | `E_QUARRY_TYPE` at the default |
| an `int` literal stored into a bounded column (`insert reviews { stars: 9 }`) | the binder, when the literal is a constant | `E_QUARRY_TYPE` naming the bound (a computed value is checked at run time) |
| adoption of a tightened bound | the adoption walk (§1.6) | `E_ADOPT` |

Text's maximum, an oversized list and a bounded int are all `E_INPUT`. A
bounded int is about what a value *is*, not about a relation between rows.
That is why it is not `E_CONSTRAINT`. The message says the type with its
bound, `int 1..5`, so the caller sees the range without opening the schema.

Devices share the interpreter and `validate.rs`. A predicted write that
would put 0 in `stars` refuses `E_INPUT` on the device, exactly as the
server does, and the write is never queued. This is the existing
argument-validation path, so the server, the SQLite device and the memory
device give the same outcome by construction. The parity tests (§5) prove
it for arguments, stored writes, list items, optional values and computed
values.

### 1.5 Generated TypeScript

A bounded int is `number` in `api.ts`. The bound is documented in two
places:

- In `Rows`, a JSDoc line above the column: `/** int 1..5 */`.
- In each operation's comment, after the arguments: `Bounds: stars: int 1..5.`
  The same `Bounds:` clause already lists list minimums.

Branded types (`number & { __range: '1..5' }`) were considered and refused.
A literal `5` would not typecheck without a cast or a constructor, every
form helper and test would need that constructor, and it would not catch
the common error, a computed value out of range. The server's `E_INPUT` is
the guarantee; the comment is the documentation.

### 1.6 Schema evolution

`column_change` classifies an int bound change:

- `int` → `int 1..5`, or a tighter range: **Narrowing**. The adoption walk
  checks every stored row with `validate_column` (the path text's maximum
  already uses). If every row fits, the step becomes Additive with "existing
  rows satisfy it". Otherwise it is refused `E_ADOPT`, with the rewrite
  "keep stars's previous type and default, or repair existing values before
  adopting stars: int 1..5".
- `int 1..5` → `int`, or a wider range: **Additive**, applied in place.
- `int ?` ↔ `int 1..5 ?` follow the existing optional rules (optional to
  required narrows).
- `int 1..5` → `text`, and similar changes, stay Destructive, as any change
  of kind is today.

A device holding rows for a schema whose bound tightened receives the
narrowed schema only after the server has adopted it, and the server adopts
only if every row fits. A held row therefore cannot violate the new bound.

### 1.7 `check`, rules and the meter

The bound is the range. `check` neither infers nor reports ranges through
arithmetic. Two uses come free and are in scope:

- An insert or update rule that only restates the bound
  (`insert <- .stars >= 1 and .stars <= 5`) becomes redundant. It is still
  accepted, with no note.
- A `require stars >= 1 and stars <= 5` in a mutation whose argument is
  already `int 1..5` is harmless. It is not flagged; the lints do not add
  noise for belt-and-braces code.

Using an argument's bound as a static page size (`first n` with
`n: int 1..50`) would let a client choose its page within a declared
ceiling. Today `first` takes a literal, and making it dynamic changes the
IR, the meter's prepay and the cursor. That is **deferred** (§7).

### 1.8 The Lean model

Column types are outside the Lean model's fragment (README "Out of scope":
text bounds and formats), and an int bound is the same kind of fact. The
Lean emitter reports `int-range` as unsupported with a reason, exactly as it
reports `text-minimum`. The differential harness's server-against-device
oracle (`run-devices`) is the parity oracle for bounds.

### 1.9 What this replaces

`Parser::int_range`'s targeted refusal becomes the parser of the type. The
wave-5 test that pinned the refusal now pins acceptance, plus the one-spelling
refusals. LLP 3000.036 §15.7 gains a pointer to this section: the decision is
reversed, and the analysis's 5a.1 is implemented. The cheatsheet's "`int`
has no range" line becomes the type.

## 2. Calendar months and years

### 2.1 What the farm met

`guide time` says there is no `month(t)` and gives an idiom. The client
computes `202610`, stores it in an `int` column and passes the month's first
and next instants as `time` arguments, which the mutation checks against
`now`. Billing, quotas, "this month's leaderboard" and monthly digests all
repeat the idiom. A schedule cannot fire monthly at all: `every 30d`
drifts.

### 2.2 Builtins

| builtin | type | meaning |
|---|---|---|
| `month(t)` | `time → int` | months since 1970-01, UTC. 2026-10 is 681, and 1969-12 is -1. |
| `year(t)` | `time → int` | the UTC calendar year: 2026 |
| `monthStart(m)` | `int → time` | the first instant of month ordinal `m`, UTC: `monthStart(681)` is 2026-10-01T00:00Z |
| `yearStart(y)` | `int → time` | the first instant of year `y`, UTC |

Identities, all half-open like every range in Quarry:

- `monthStart(month(t)) <= t < monthStart(month(t) + 1)`;
- `yearStart(year(t)) <= t < yearStart(year(t) + 1)`;
- `month(t) / 12 + 1970 = year(t)`, and `month(t) % 12` is the zero-based
  month of the year (`/` and `%` floor, so this holds before 1970 too).

**Why an ordinal, not `yyyymm`.** The farm's idiom stored `202610`. That is
readable, but arithmetic on it is wrong at year ends: `202612 + 1` is not
January. `day(t)` and `hour(t)` are ordinals since the epoch, and `month(t)`
follows them. Last month is `month(now) - 1`. A three-month window is
`month(.at) >= month(now) - 2`. A month's length is
`monthStart(m + 1) - monthStart(m)`. JavaScript converts both ways in one
expression each: `Date.UTC(1970, m)` is the month's start (Date.UTC
normalizes month overflow and negative months), and
`(d.getUTCFullYear() - 1970) * 12 + d.getUTCMonth()` is the key. `year(t)`
is the calendar year itself. Year arithmetic is already continuous, and
"2026" needs no explanation.

**Why `monthStart(m)`, not `monthEnd(t)` or `addMonths(t, n)`.** A
month's end is the next month's start, `monthStart(m + 1)`, and Quarry's
ranges are half-open. `monthEnd` would invite the off-by-one
`.at <= monthEnd(t)`. `addMonths(t, n)` needs a rule for clamping the 31st,
which billing systems disagree on. Taking the ordinal makes "the same day
next month" something the author writes deliberately:
`monthStart(month(t) + 1) + (t - monthStart(month(t)))`, clamped by the
author if needed.

**Errors.** `monthStart` and `yearStart` refuse `E_OVERFLOW` when the
result leaves the i53 time range. Inputs reach about ±285,000 years, so
only an absurd argument does this. All four builtins are total on their
domains, deterministic, and read no clock.

**No offsets in this RFC.** `day(t, 8h)` shifts a day's boundary by a
non-negative offset smaller than the period. For months that convention is
wrong for zones east of UTC: Tokyo's month starts at 15:00 UTC on the *last
day of the previous month*, which an offset in [0, 1d) cannot express. A
signed offset is a different convention from `day`'s. It waits for a
time-zone design rather than being half-solved here (§7).

### 2.3 Index keys, views and windows

`month(.at)` and `year(.at)` join `day`, `hour` and `bucket` wherever a
calendar key is accepted:

```quarry
table checkins:
  person: principal
  at: time default now
  unique person, month(at) else ALREADY_THIS_MONTH
  read <- .person = viewer
  insert <- .person = viewer

view checkinsByMonth: count checkins by .person, month(.at)
  read <- .person = viewer
```

`CalendarKey` gains the two functions, with `millis = 0` and `offset = 0`
(the duration fields are meaningless for a calendar month). An older
engine's `validate` already refuses a function it does not know, and a
non-positive `millis`, so the key fails closed. The capability
`calendar-month` names the failure. Key values are plain ints in the
existing key encoding: ordering, prefix scans, sync windows over a calendar
key (`last N by month(.at)`), maintained views and adoption need nothing
new.

### 2.4 Monthly and yearly schedules

```quarry
schedule billing every 1 month at day 1 09:00: bill
schedule quarterly every 3 months: report
schedule renewals every 1 year at day 1 00:00: renew
```

- `every N month[s]` fires at the start of every month whose ordinal is
  divisible by N, so quarters begin in January, April, July and October.
  `every N year[s]` is `every 12N months` and fires in January.
- `at day D HH:MM` moves the boundary to day D (1–28) at HH:MM UTC. `at
  HH:MM` alone means day 1. Days 29–31 are refused: not every month has
  them, and silent clamping is the drift this feature exists to remove. The
  rewrite is `day 28`, or a daily schedule whose job checks
  `month(now + 1d) != month(now)` for "the last day".
- `periodStart` is the previous calendar boundary and `periodEnd` is this
  one. For a monthly bill at 09:00 on the 1st, `month(periodStart)` is the
  month being billed.
- **Catch-up is the documented coalescing rule, unchanged** (`guide time`).
  A schedule fires once per boundary and never twice. Boundaries it missed
  (the server was down, or `clock advance` jumped) coalesce into one run for
  the latest period, and `periodStart`/`periodEnd` describe that period
  only. `clock advance` reports `skippedPeriods` by counting calendar
  boundaries, not milliseconds. A job that must not lose a skipped month
  sweeps back, as the fixed-period recipe does. The billing recipe (§6) keys
  invoices by `(subscription, month)` and bills every unbilled month up to
  the period's, so a two-month outage bills both months once.
- `Schedule` gains `months: u32` (0 for a fixed period). A calendar schedule
  has `every_ms = 0`. An older engine refuses that at load (it already
  rejects a zero period), and the capability `calendar-schedule` names the
  refusal.
- `doctor`, `dev` status and the schedule line print `every 1 month at day 1
  09:00 UTC` and the next boundary as a date.

Schedules run only on the server, so a device has nothing to do for §2.4.
The builtins of §2.2 run on devices through the shared interpreter.

### 2.5 The Lean model

Calendar builtins enter the model's fragment. `Expr` gains
`cal (f : CalFn) (args : List Expr)` for `day`, `hour`, `bucket` (period and
offset), `month`, `year`, `monthStart` and `yearStart`. The civil calendar is
the days-from-civil algorithm over `Int` (Hinnant's, proleptic Gregorian),
written from the documents rather than from `value.rs`. The model proves:

- `monthStart_month_le`: `monthStart (month t) ≤ t`;
- `lt_monthStart_succ`: `t < monthStart (month t + 1)`;

and the same two facts for years, on the full i53 domain. The emitter
(`emit/lean.rs`) translates the seven calls. The oracle generator draws them
in scalar bodies over `now`, over time arguments that include the month,
year and leap-day edges, and over their round trips. `run-lean` compares the
engine with the model on at least 100,000 cases.

## 3. Caps for small tables

### 3.1 What exists

`cap N` with no `by` has parsed since LLP 3000.007 §20.3 (the Following
feed's public broadcast projection). It is one group, the whole table:

- the bounds checker accepts an unfiltered scan, or a filter over the whole
  table, when the cap is at most the examined ceiling (8,192). Above it, the
  checker refuses with "above the 8192 examined ceiling";
- the server's insert path counts the table with `count_prefix` over an
  empty group and refuses at the cap;
- adoption's constraint walk counts the one group;
- a device predicts a capped insert only when it holds the whole group
  (E_NOT_PREDICTABLE's "a whole-table cap needs the whole public table").

The farm did not find it. No card shows it, the types card says
`cap N by cols`, and `E_QUARRY_BOUND`'s rewrite says "declare `cap N`"
without an example. The refusal text is wrong for it:
`categories holds at most 50 rows per group by ` (an empty column list).

### 3.2 Changes

- **Refusal text.** A whole-table cap refuses `E_CONSTRAINT: categories
  holds at most 50 rows`, and the dev refusal trace names the clause as
  `cap 50`. A grouped cap keeps its text.
- **Docs.** `guide types` (constraints), `guide bounds` (a small lookup
  table read whole) and the cheatsheet show `cap N` beside `cap N by cols`,
  with the categories example. `E_QUARRY_BOUND`'s rewrite for an uncapped
  whole-table read leads with `cap 100` on the table when the read has no
  cursor.
- **Adoption.** Adding `cap N`, or lowering it, on a populated table is
  Narrowing. Adoption counts the table and refuses `E_ADOPT` when it holds
  more than N rows. Raising the cap is Narrowing in classification and
  passes the count. The machinery exists, and tests now pin it.
- **Devices.** Insert refusal at the cap, and prediction over a fully held
  public table, get parity tests on both stores. A capped table that the
  device does not hold whole queues the write (`E_NOT_PREDICTABLE`), as
  today.

Nothing about the cap's meaning changes. It is a product constraint ("at
most 50 categories") that also serves as an execution bound. A table that
can legitimately grow keeps paging with `first N` and a cursor.

## 4. Fences and compatibility

| semantics | fence |
|---|---|
| `IntRange` in a column | capability `int-range` and the new enum tag |
| `IntRange` in an argument | the new `ArgType` tag (a program an older device cannot decode is refused whole) |
| `month`/`year` calendar keys | capability `calendar-month`, and `validate`'s function list |
| `month`/`year`/`monthStart`/`yearStart` in programs | new `Builtin` tags |
| monthly schedules | capability `calendar-schedule`, and `every_ms = 0` |
| whole-table caps | none new (existing semantics) |

Schemas that use none of these serialize byte for byte as before, so the
conformance corpus and kept stores are unaffected.

## 7. Deferred, and open questions for review

- **Deferred: `first n` with a bounded argument** (§1.7).
- **Deferred: time zones and signed calendar offsets** (§2.2).
- **Deferred: branded TypeScript ranges** (§1.5).
- **Open: should `int <=N` exist at all?** It is the one spelling where an
  int and text differ (text's `<=N` implies 0). The alternative is `int ..N`
  for "at most N", with `<=N` refused. This draft keeps `<=N` because it
  mirrors the spelling builders already know from text and lists, and the
  guide states the difference in one line.
- **Open: the month ordinal versus `yyyymm`** (§2.2). This draft chooses
  the ordinal for arithmetic and for consistency with `day`. A reviewer who
  weighs readability in `snapback4 sql` and in fixtures higher should say
  so.

## 8. Review record

Reviews are saved verbatim under `llp/reviews/` with their provenance. This
section records each review's verdict and the disposition of each point.
