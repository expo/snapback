## 0. Summary

The app farm's six waves (LLP 3000.037) asked for three things that Quarry
answered with idioms: a range on an `int`, a calendar month, and a small
lookup table that every query could read whole. Each idiom cost builders
time, and each became a targeted diagnostic or a guide paragraph. This RFC
replaces the idioms with language. The brief was "the ideal end-game
solution", not the smallest patch.

| § | addition | surface | where it is enforced |
|---|---|---|---|
| 1 | bounded integers | `int 1..5`, `int 0..`, `int ..100`, `int -10..10`, also as list items and as operation arguments | wire input (`E_INPUT` naming the bound), every stored write on the server and both device stores, fixtures and `/seed`, constant writes at `check`, adoption of a tightened bound |
| 2 | calendar months and years, UTC | `month(t)`, `year(t)`, `monthStart(m)`, `yearStart(y)`; `month(.at)`/`year(.at)` as index and view keys; `schedule … every 1 month at day 1 09:00`, `every N months`, `every 1 year` | the shared interpreter (server and devices), computed index keys, the scheduler and the dev clock, the Lean model |
| 3 | caps for small tables | `cap N` with no `by` (one group: the whole table) | already in the engine (LLP 3000.007 §20.3); this RFC names it, fixes its refusal text, makes raising it additive, proves it on both devices and through adoption, and documents it |

Decisions in one line each:

1. A bounded int is a **new column and argument type**, `IntRange`, with
   optional inclusive bounds. An out-of-range value is `E_INPUT` naming the
   bound, wherever it enters. The spellings are `M..N`, `M..` and `..N`.
2. `month(t)` is the **month ordinal since 1970-01** (UTC): 681 is 2026-10.
   It is ordered and continuous, so `month(now) - 1` is last month, just as
   `day(t)` counts days. `year(t)` is the calendar year (2026).
   `monthStart(m)` and `yearStart(y)` go back to a `time`.
3. A monthly schedule's boundaries are **calendar months, anchored at
   1970-01**. Missed boundaries coalesce into one run, the same rule as for
   fixed periods.
4. The whole feature is **UTC**. Local-time months wait for a time-zone
   design (§7).
5. `cap N` without `by` keeps its engine semantics. Its refusal now reads
   `categories holds at most 50 rows`.

## 1. Bounded integers

### 1.1 What the farm met

Eleven wave-5 lanes wrote `n: int 1..10` (LLP 3000.036 §15.7). The parser
said "expected the end of the line, got 1". Wave 5 replaced that message with
a targeted `E_QUARRY_SYNTAX` whose rewrite is a `require` in every mutation
that writes the column, plus an insert rule and an update rule (optional
columns add `x = null or …`). That is three to five lines for one fact about
a column, repeated in every writer, and a missed writer is a silent hole.
The analysis's 5a.1 called this the language's job. §15.7 recorded why it
was not done: a new scalar kind reaches the schema, wire validation, both
device stores, the generated types and the Lean model. This RFC does that
work.

### 1.2 Surface

```quarry
table reviews:
  author: principal
  stars: int 1..5
  helpful: int 0.. default 0
  delta: int -10..10 ?
  budget: int ..1000 ?
  scores: [int 0..100] <=8
  read <- .author = viewer
  insert <- .author = viewer

mutation rate(stars: int 1..5, scores: [int 0..100] <=8):
  return insert reviews { author: viewer, stars, scores }
```

- `int M..N` means M ≤ value ≤ N. Both bounds are inclusive and both are
  written. This is text's spelling, `text M..N`.
- `int M..` means at least M. `int 0..` is the non-negative int.
- `int ..N` means at most N, with no lower bound.
- Bounds are integer literals, optionally negative, within ±(2^53 − 1).
  M > N is a syntax error that prints the swapped range. A fractional bound
  is a syntax error. `int ..` bounds nothing and is a syntax error.
- **One spelling.** `int <=N`, `int >=M`, `int <N` and `int >N` refuse
  `E_QUARRY_SYNTAX`, and the rewrite is the canonical form with the
  author's number: `int ..N`, `int M..`, `int ..N-1`, `int N+1..`. `int
  <=N` is refused on purpose. Text's `<=N` means 0..N because a length is
  never negative. An int's at-most has no implied zero, so the same
  spelling would mean two things. The refusal says this in one clause.
- An optional bounded int is `int 1..5 ?`. A bounded list item is
  `[int 1..5] <=8`.
- **A helper (`fn`) parameter cannot be bounded.** It refuses
  `E_QUARRY_TYPE`. A helper is inlined at its call, so no value crosses a
  boundary where the bound could be checked. The rewrite moves the bound to
  the operation's argument or to the stored column. Text bounds on helper
  parameters are unchanged; they are static.
- Inside a program the value is an ordinary `int` (`Ty::Int`), the way
  `text 1..80` is ordinary text. Arithmetic is not range-checked; a value is
  checked when it enters a slot.

### 1.3 Representation

`ColumnType::IntRange { min: i64, max: i64 }` and
`ArgType::IntRange { min, max }` are new variants. `Int` is unchanged. An
unwritten end is the i53 limit itself (`int ..N` is `-(2^53 − 1)..N`), which
means the same thing because every int is i53; it is omitted from the
serialized form, and it keeps `ColumnType` at its previous size, so the heap
meter's per-column cursor charge does not move. A raw catalog or program
whose range is reversed or leaves i53 is refused at load
(`columns::validate`, `ArgType::bounds_valid`). Two other representations
were considered:

- *Change `Int` into `Int { min, max }`.* Every stored schema serializes
  `"Int"`, and old backends, corpus cases and kept device stores would all
  need a decoder shim. Refused.
- *A table constraint, as text's minimum is (`Constraint::Text`).* That
  bounds only top-level columns: list items and arguments would need a
  second mechanism. It would also report `E_CONSTRAINT` for a value the
  caller supplied. Refused.

Every site that treats `Int` as "an integer column" also accepts
`IntRange`: ordering, key encoding and key budgets, insert-rule ordering,
`sum` sources, the wire codec, cursor decoding, `sql`, cost tables and the
Rust emitter. `ColumnType::is_int()` and `ColumnType::unbounded()` name
this. Sites that need the exact unbounded `Int` keep it, and a bounded
column there is a binder or schema refusal: engine-assigned sequences,
delivery positions, maintained columns and calendar keys.

### 1.4 Where the bound is enforced

There is one check, `validate.rs::fits`. Its `IntRange` arm requires the
value to lie in the i53 range and inside the bound. Every path that admits
a value into a declared slot already calls `fits`:

| entry | path | refusal |
|---|---|---|
| a call's arguments (HTTP, `run`, the client, a device's predicted call, a job run by hand) | `validate_arg` → `fits` through `arg_as_column`, recursing into list items and optionals | `E_INPUT: stars must be int 1..5, not the number 7` |
| a stored write (insert, update, upsert patch, engine-filled defaults, the stored image) | `validate_row`/`validate_column` → `fits` | `E_INPUT: reviews.stars must be int 1..5, not the number 0` |
| fixtures and `/seed` rows | the same row validation | the row is refused and not stored; the load path currently reports any invalid row as `NOT_FOUND`, for text bounds too (`issues/20261012-snapback4-seed-refusal-reports-not-found.md`) |
| a literal `default` | the binder runs `validate_column` on the literal | `E_QUARRY_TYPE` at the default |
| a constant written into a bounded column (`insert reviews { stars: 9 }`) | the binder | `E_QUARRY_TYPE: reviews.stars is int 1..5; 9 is outside it` |
| adoption of a tightened bound | the adoption walk (§1.6) | `E_ADOPT` |

**Aggregates erase the bound.** A `sum` view over a bounded column, and a
`sum` maintained column, total into an unbounded `int`: two contributions
of 5 to `int 1..5` total 10. The binder gives the total `Int`, and
`maintain_target` maps an `IntRange` source to `Int`. A count is `Int`. A
maintained column's type comes from its aggregate, never from a
declaration, so no engine-maintained slot is bounded, and the engine's
direct writes (`apply_aggregate`, `mirror_column`) never meet a bound. A
view's group key copied from a bounded column keeps that column's values,
which already fit.

**Why `E_INPUT`, not `E_CONSTRAINT`.** Text's maximum, an oversized list
and a bounded int are all facts about what a value *is*, not relations
between rows. There is no hidden row whose existence the refusal could
disclose, so the message can name the bound and the offending value. The
message gives the type with its bound, `int 1..5`, so the caller sees the
range without opening the schema.

Devices share the interpreter and `validate.rs`. A predicted write that
would put 0 in `stars` refuses `E_INPUT` on the device, exactly as on the
server, and is never queued. The parity tests (§5) prove this on both stores
for arguments, stored writes, list items, optional values and computed
values.

### 1.5 Generated TypeScript

A bounded int is `number` in `api.ts`. The bound is documented in two
places:

- In `Rows`, a JSDoc line above the column: `/** int 1..5 */` (also for
  optional and list columns, which print as `int 1..5 ?` and
  `[int 0..100] <=8`).
- In each operation's comment, after the arguments: `Bounds: stars: int 1..5.`
  The same `Bounds:` clause already lists list minimums.

Branded types (`number & { __range: '1..5' }`) were considered and refused.
A literal `5` would not typecheck without a cast or a constructor, every form
helper and test would need that constructor, and it would still not catch
the common error, a computed value out of range. The server's `E_INPUT` is
the guarantee; the comment is the documentation.

### 1.6 Schema evolution

`successor.rs::column_change` classifies an int bound change:

- `int` → `int 1..5`, or a tighter range: **Narrowing**. The adoption walk
  (`store/successor.rs`) checks every stored row with `validate_column`,
  the path text's maximum already uses. If every row fits, the step becomes
  Additive with "existing rows satisfy it". Otherwise it is refused
  `E_ADOPT`, with the rewrite "keep stars's previous type and default, or
  repair existing values before adopting stars: int 1..5".
- `int 1..5` → `int`, or a wider range: **Additive**, applied in place.
- A list whose item type widens (`[int 1..5]` → `[int 0..9]`) is Additive.
  The list rule now compares items with `column_change` rather than with
  equality.
- `int ?` ↔ `int 1..5 ?` follow the existing optional rules (optional to
  required narrows).
- `int 1..5` → `text` and similar changes stay Destructive, as any change
  of kind is today.

**Devices.** An adopted schema is a new generation. A device adopting it
(`Device::adopt_captured`) resets its watermark and, unless the change only
adds literal defaults, drops its held images and reacquires them from the
server, which has validated every row. A stale image (`stars = 0`, held from
before the server repaired the row) is therefore never read under the new
bound. Pending writes stay in the outbox. A pending write whose value no
longer fits is refused `E_INPUT` by the server when sent, like any write
that loses a race with a schema change.

### 1.7 `check`, rules and the meter

The bound is the range. `check` neither infers nor reports ranges through
arithmetic. An insert or update rule that restates the bound
(`insert <- .stars >= 1 and .stars <= 5`) becomes redundant but stays
accepted, with no note. So does a `require` that restates an argument's
bound. The lints do not add noise for belt-and-braces code.

Using an argument's bound as a static page size (`first n` with
`n: int 1..50`) would let a client choose its page within a declared
ceiling. Today `first` takes a literal, and making it dynamic changes the
IR, the meter's prepay and the cursor. That is **deferred** (§7).

### 1.8 The Lean model

Column types are outside the Lean model's fragment (README "Out of scope":
text bounds and formats), and an int bound is the same kind of fact. The
Lean emitter reports `int-range` as unsupported, with a reason, exactly as
it reports `text-minimum`. The parity oracle for bounds is the
server-against-device harness (`run-devices`). Because the server and the
devices share `fits`, that harness cannot catch a defect in `fits` itself.
Direct tests pin `fits` against the declared range: every boundary, one
past each boundary, and the i53 ends.

### 1.9 What this replaces

`Parser::int_range` was a targeted refusal; it now parses the type. The
wave-5 test that pinned the refusal now pins acceptance, plus the
one-spelling refusals. LLP 3000.036 §15.7 gains a pointer to this section:
the decision is reversed, and the analysis's 5a.1 is implemented. The
cheatsheet's "`int` has no range" line becomes the type.

## 2. Calendar months and years

### 2.1 What the farm met

`guide time` says there is no `month(t)` and gives an idiom. The client
computes `202610`, stores it in an `int` column and passes the month's first
and next instants as `time` arguments, which the mutation checks against
`now`. Billing, quotas, "this month's leaderboard" and monthly digests all
repeat the idiom. A schedule cannot fire monthly at all: `every 30d` drifts.

### 2.2 Builtins

| builtin | type | meaning |
|---|---|---|
| `month(t)` | `time → int` | months since 1970-01, UTC. 2026-10 is 681; 1969-12 is -1. |
| `year(t)` | `time → int` | the UTC calendar year: 2026 |
| `monthStart(m)` | `int → time` | the first instant of month ordinal `m`, UTC: `monthStart(681)` is 2026-10-01T00:00Z |
| `yearStart(y)` | `int → time` | the first instant of year `y`, UTC |

The calendar is the proleptic Gregorian calendar with astronomical year
numbering. Year 0 exists, the year before it is -1, and 1900 is not a leap
year. One implementation, `snapback4_core::calendar` (Hinnant's
days-from-civil and civil-from-days over `i128` intermediates), serves the
server, both device stores, the index keys and the scheduler.

**Identities.** These hold over the integers, without bounds. They are the
model's theorems (§2.5):

- `monthStart(month(t)) <= t < monthStart(month(t) + 1)`;
- `yearStart(year(t)) <= t < yearStart(year(t) + 1)`;
- `month(t) / 12 + 1970 = year(t)`, and `month(t) % 12` is the zero-based
  month of the year. `/` and `%` floor, so this holds before 1970 too.

**Representability.** A Quarry `time` is an i53 millisecond. `month` and
`year` are total on every time. `monthStart` and `yearStart` refuse
`E_OVERFLOW` when the instant they would return falls outside ±(2^53 − 1):

- `monthStart(m)` for m > 3,425,121 or m < -3,425,121 (the earliest time
  lies inside month -3,425,122, whose start precedes it);
- `yearStart(y)` for y > 287,396 or y < -283,456.

So the executable form of the first identity holds whenever both starts are
representable. At the two extreme months one side refuses `E_OVERFLOW`;
neither side ever returns a wrong instant.

**Why an ordinal, not `yyyymm`.** The farm's idiom stored `202610`. That is
readable, but arithmetic on it is wrong at year ends: `202612 + 1` is not
January. `day(t)` and `hour(t)` are ordinals since the epoch, and `month(t)`
follows them. Last month is `month(now) - 1`. A three-month window is
`month(.at) >= month(now) - 2`. A month's length is
`monthStart(m + 1) - monthStart(m)`. In JavaScript, `Date.UTC(1970, m)` is
the month's start (Date.UTC normalizes month overflow and negative months),
and `(d.getUTCFullYear() - 1970) * 12 + d.getUTCMonth()` is the key. A JS
`Date` covers ±8.64e15 ms, narrower than i53, so the extreme times render
as `Invalid Date`; the guide says so. `year(t)` is the calendar year
itself, because year arithmetic is already continuous.

**Why `monthStart(m)`, not `monthEnd(t)` or `addMonths(t, n)`.** A
month's end is the next month's start, `monthStart(m + 1)`, and Quarry's
ranges are half-open. A `monthEnd` would invite the off-by-one
`.at <= monthEnd(t)`. `addMonths(t, n)` needs a rule for clamping the 31st,
and billing systems disagree on that rule. Taking the ordinal makes "the
same day next month" something the author writes deliberately.

All four builtins are deterministic and read no clock. They charge the
ordinary expression step.

### 2.3 Index keys, views and windows

`month(.at)` and `year(.at)` join `day`, `hour` and `bucket` wherever a
calendar key is accepted:

```quarry
table checkins:
  person: principal
  at: time default now
  unique person, month(at) else ALREADY_THIS_MONTH
  read <- .person = viewer
  insert <- .person = viewer

view checkinsByMonth: count checkins by .person, month(.at)
  read <- .person = viewer
```

`CalendarKey` gains the two functions, with `millis = 0` and `offset = 0`
(a duration means nothing for a calendar month), and `CalendarKey::value`
calls the same `calendar` functions as the builtins. A key read
(`checkins[viewer, month(now)]`) and a stored key are equal by
construction. Key values are plain ints in the existing key encoding:
ordering, prefix scans, sync windows over a calendar key, maintained views
and adoption need nothing new. `month` and `year` take no offset (§7).

### 2.4 Monthly and yearly schedules

```quarry
schedule billing every 1 month at day 1 09:00: bill
schedule quarterly every 3 months: report
schedule renewals every 1 year: renew
```

- **The anchor.** `every N month[s]` fires at the start of every UTC month
  whose ordinal since 1970-01 is a multiple of N. The anchor is the epoch,
  not the moment the schedule is declared, just as fixed periods are
  multiples of `every_ms` since the epoch. Quarters therefore begin in
  January, April, July and October, and a bimonthly schedule declared in
  June first fires in July. `every N year[s]` is `every 12N months` and
  fires in January. N is from 1 to 1,200 months.
- **The day.** `at day D HH:MM` moves the boundary to day D (1–28) at HH:MM
  UTC, and `at HH:MM` alone means day 1. Days 29–31 are refused, because not
  every month has them and silent clamping is the drift this feature exists
  to remove. The rewrite names `day 28`, or a daily schedule whose job tests
  the *period*, not the clock: `month(periodEnd) != month(periodStart)`
  holds exactly for the daily period that crosses a month's end. Because
  missed boundaries coalesce, such a job must also sweep back (the general
  rule below). `at day D` on a fixed-period schedule is refused.
- **Periods.** `periodStart` is the previous calendar boundary and
  `periodEnd` this one. For a monthly bill at 09:00 on the 1st,
  `month(periodStart)` is the month being billed.
- **Catch-up is the documented coalescing rule, unchanged** (`guide time`).
  A schedule fires once per boundary and never twice. Boundaries it missed,
  because the server was down or `clock advance` jumped, coalesce into one
  run for the latest period, and `periodStart`/`periodEnd` describe that
  period only. `clock advance` reports `skippedPeriods` by counting calendar
  boundaries (`Schedule::periods_between`), not milliseconds. A job that
  must not lose a skipped month sweeps back with durable progress, as the
  billing recipe (§6) does.
- **Representation.** `Schedule` gains `months: u32`, serialized only when
  non-zero (`skip_serializing_if`), so every existing schedule keeps its
  bytes, its schema hash and its `schedule-shape` digest. A calendar
  schedule has `every_ms = 0` and `offset_ms < 28 days`. `Schedule::valid`
  accepts exactly one of the two shapes. `boundary`, `previous`, `next`,
  `periods_between` and `describe` are the only arithmetic. The scheduler,
  the dev clock and `doctor` call them rather than adding `every_ms`
  themselves.
- `doctor`, `dev` status and `clock advance` print `every 1 month at day 1
  09:00 UTC` and the next boundary as a date.

Schedules run only on the server, so devices have nothing to do for §2.4.
The builtins of §2.2 run on devices through the shared interpreter.

### 2.5 The Lean model

Calendar builtins enter the model's fragment. `Expr` gains a calendar
builtin form for `day`, `hour`, `bucket` (period and offset), `month`,
`year`, `monthStart` and `yearStart`. The civil calendar is days-from-civil
over `Int`. It is written from this RFC and the guide, not from
`calendar.rs`. The model's `monthStart` and `yearStart` are total on `Int`.
The checked i53 conversion is a separate step that refuses `E_OVERFLOW`, as
`+` and `*` already do in the model. The model proves the identities of §2.2
over `Int`:

- `monthStart (month t) ≤ t` and `t < monthStart (month t + 1)`;
- the same two facts for years;

and the examples pin the shared vectors (§5) with their expected outcomes.

The Lean emitter refuses `now` today, so oracle cases pass times as
arguments. The generator draws calendar builtins over time arguments chosen
from the vectors, from the month, year and leap-day edges, and from random
times. It also draws their round trips. These are calendar-only scalar
cases, so no bounded column makes them unsupported. `run-lean` reports how
many cases the model supported, and the run fails if the calendar cases
were not drawn.

## 3. Caps for small tables

### 3.1 What exists

`cap N` with no `by` has parsed since LLP 3000.007 §20.3 (the Following
feed's public broadcast projection). It is one group, the whole table:

- **Bounds.** The checker accepts an unfiltered scan, or a filter over the
  whole table, when the cap is at most the ordinary examined ceiling (8,192).
  A larger cap is legal as a product constraint, but it does not bound a
  read ("above the 8192 examined ceiling"). A cap removes no other meter:
  steps, heap and output still cut.
- **Insert.** The server counts the group with `count_prefix` over a
  plain index, which is the implicit id index when none is declared, and
  refuses at the cap. A
  cap on an **expiring** table counts live rows: physical occupancy is a
  cheap upper bound, and at the cap a bounded scan skips expired rows. So
  expired, unswept rows can make that scan longer than N.
- **Private tables.** A cap on a table whose read rule is not uniform counts
  rows the writer may not read. At the cap, the refusal is the generic
  `E_RULE` when an occupant is unreadable (guide writes, "two limits"),
  never a count.
- **Devices.** A device predicts a capped insert only when it holds the
  complete current group. For a whole-table cap that means `sync public`
  with no horizon. A private partition, or `sync public last N`, queues the
  write (`E_NOT_PREDICTABLE`). An expiring cap always queues, because only
  the server knows physical occupancy.
- **Adoption.** The constraint walk counts physical rows, including
  expired, unswept ones. That is stricter than the runtime's live count. It
  is kept, because adoption must not depend on when the sweeper last ran.

The farm did not find it. No card shows it, the types card says
`cap N by cols`, and `E_QUARRY_BOUND`'s rewrite says "declare `cap N`"
without an example. The refusal text is wrong for it:
`categories holds at most 50 rows per group by ` (an empty column list).

### 3.2 Changes

- **Refusal text.** A whole-table cap refuses `E_CONSTRAINT: categories
  holds at most 50 rows`, and the dev refusal trace names the clause as
  `cap 50`. A grouped cap keeps its text.
- **Raising a cap is Additive.** A constraint change whose only difference
  is a cap with the same grouping and a maximum at least as large cannot
  invalidate a stored row. It is now classified Additive, with no walk.
  Adding a cap, or lowering one, stays Narrowing: adoption counts the group
  and refuses `E_ADOPT` when it holds more than N rows.
- **Docs.** `guide types` (constraints), `guide bounds` (a small lookup
  table read whole) and the cheatsheet show `cap N` beside `cap N by cols`,
  with the categories example and the limits of §3.1.
- **Tests.** Insert refusal at the cap and prediction over a fully held
  public table get parity tests on both stores, along with adoption for
  adding, lowering and raising a cap on a populated table.

Nothing about the cap's meaning changes. It is a product constraint ("at
most 50 categories") that also serves as an execution bound. A table that
can legitimately grow keeps paging with `first N` and a cursor.

## 4. Fences and compatibility

| semantics | what an older engine or device does | capability recorded |
|---|---|---|
| `IntRange` in a column | refuses to decode the schema (unknown `ColumnType` tag) | `int-range` |
| `IntRange` in an argument | refuses to decode the program (unknown `ArgType` tag) | — |
| `month`/`year` builtins | refuses to decode the program (unknown `Builtin` tag) | — |
| `month`/`year` calendar keys | refuses `E_SCHEMA_CAPABILITY: unsupported engine capability calendar-month` (every binary since the capability fence); without the carrier, `CalendarKey::validate` refuses | `calendar-month` |
| monthly schedules | refuses `E_SCHEMA_CAPABILITY` naming `calendar-schedule`; without the carrier, admission refuses `every_ms = 0` | `calendar-schedule` |
| whole-table caps | unchanged semantics | — |

The capabilities are recorded in the schema's carrier, as every new
semantics is. Every binary since the capability fence checks the declared
names after decoding the schema's structure and refuses an unknown one with
`E_SCHEMA_CAPABILITY`. So a schema with calendar keys or a calendar schedule
gets the named refusal from an older binary. A schema with an `IntRange`
column fails earlier, in structural decoding (an unknown `ColumnType` tag),
before the capability check is reached; it still fails closed, but with the
decoder's own message. Programs carry no capability: an unknown `ArgType` or
`Builtin` tag refuses the program's decode.
Detection recurses through optional and list columns, index components and
maintain keys.

Schemas that use none of these features serialize byte for byte as before,
including their schedules, so the conformance corpus, schema hashes,
schedule progress and kept stores are unaffected.

## 7. Deferred, and open questions

- **Deferred: time zones and local-time months.** A fixed offset cannot
  express a zone east of UTC: Tokyo's month starts at 15:00 UTC on the last
  day of the previous month, which a non-negative offset smaller than a day
  (the `day(t, 8h)` convention) cannot name. DST changes the offset
  twice a year. A local-time design needs a zone name, a
  zone database on every host (server, wasm device, native device), and a
  rule for keys stored under one zone and read under another. It is a
  separate RFC. Everything here is labelled UTC, so nothing has to migrate
  later. A UTC month key stays a correct UTC month key, and a zoned key
  will be a different function.
- **Deferred: `first n` with a bounded argument** (§1.7).
- **Deferred: branded TypeScript ranges** (§1.5).
- **Deferred: days 29–31 for calendar schedules** (§2.4), until there is a
  demonstrated need and a clamping rule the author chooses.
