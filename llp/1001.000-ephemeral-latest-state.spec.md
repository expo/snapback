## Summary

Make `channel` a typed, scoped, observable latest-state resource. Keep its
durable rule expressions and generated reference; replace its untyped event
pipe. The user commissioned deciding this direction, writing the LLPs,
obtaining the two named sanity reviews, and implementing the resulting design.
That commission authorizes these design documents and the implementation;
the reviews advise the delegated decision, not accept on the user's behalf.

The asset surface already converges with durable data at its useful boundary
(LLP 1006.002). This change concentrates on ephemeral state.

## Declaration and value

```q
channel typing(conversationId: conversations):
  value: { typing: bool }
  publish <- exists memberships[conversationId, viewer]
  subscribe <- exists memberships[conversationId, viewer]
  ttl 4s
```

`value` is a required closed record declaration whose fields use existing Quarry argument
types, including bounded text, scalars, enums, lists and optionals. Missing
required fields, extra fields and invalid bounds/types refuse. Optional fields
normalize to null as ordinary arguments do. The first slice excludes asset,
byte and cursor types recursively: channels own no asset custody, streaming
bytes or durable cursor. Bounded `json` remains an explicitly unstructured
field, not the default value type. Empty record declarations, duplicate declared
fields and duplicate channel properties refuse at Quarry parse time. Wire JSON
parsing follows ordinary durable arguments; it adds no raw duplicate-key parser.
An all-optional declaration may accept `{}` and normalize fields to null.
The IR contains `value: BTreeMap<String, ArgType>` and `ttl_ms`.

`ttl` is an integer 1–30 seconds, required and checked by both the compiler and
core generation admission. Payloads are validated server-side with the same
argument value/type checks as durable programs; TypeScript inference is not
validation. Generation admission also rejects invalid value descriptors.

The compiler emits `Channel<Args, Value>` under `api.channels.typing` and the
existing unambiguous short alias `api.typing`. The old payload-`unknown`
declaration and `publish` client method are removed. Existing channel fixtures
and the chat template move in the same landing.

## Ownership and lifetime

One **logical subscribed channel connection** owns at most one entry. Opening
it creates a random public `key` and a separate unguessable `lease`, both minted
by the owner. The lease is returned only on that connection's frames, never
in another entry. It binds the exact channel name, normalized scope args,
authenticated principal/session epoch, and the live subscription. Each command
checks all those bindings against its authenticated request, compares the lease
in constant time, and requires a live receiver. Tokens have at least 128 bits
of CSPRNG entropy with collision retry. The lease is not independent bearer
authority. Foreign, missing and closed leases share one invalid-lease refusal.
The lease is the sole locator; URL name/body scope are equality checks and
never relocate a command. Scope arguments reject extra fields before
normalization. Clients
cannot choose a key, impersonate another principal, or resurrect a closed
lease. Two tabs for one principal have separate entries. There is one key mode;
principal keys and arbitrary authored keys wait for a demonstrated need.

Opening requires subscribe admission. `set` additionally requires publish
admission. A publish-only participant is deliberately outside this first
surface: a writable handle is a subscribed room handle. Readers need not pass
publish admission. The entry's `from` is the owner-derived principal.

The key and lease survive value TTL; a later set on that still-live handle
reinserts the same key. An admitted `set(value)` replaces that connection's whole value and renews its
expiry to server-now + TTL. There is no automatic value renewal: heartbeats
keep the transport alive, not an old typing indicator. Applications renew
presence explicitly. `clear()` removes only the caller's entry and is
idempotent, including after TTL expiry. It releases state even if publish
permission has since disappeared, provided the lease is still owned.

Disconnect/unsubscribe, session expiry/revocation, explicit clear, TTL expiry,
reset and owner restart remove entries. Detected disconnect removes promptly;
an undetected partition is bounded by TTL. Reconnect can briefly leave old
and new connection entries; applications may group by `from` when they want
people rather than connection counts. Expiry is swept on the owner's
background turn (target <=1 second), and synchronously before snapshot or set
so expired values are never admitted into a new delivery. Wall-clock metadata
is informational. Store a monotonic deadline for authority/expiry decisions
and a wall-clock `expiresAt` for display; wall-clock rollback cannot extend the
lease. The sweep interval is a best-effort latency target, not a hard deadline.

Subscribe admission traces retain the existing commit-triggered revocation
fence. Stored values also retain the publish verdict's dependencies: losing
publish permission removes that value even when subscribe remains allowed.
All affected admission checks and removals happen before the next room frame.
An authorization refusal replaces any buffered state and terminates the child.
Schema succession clears entries and terminates old channel children with a
typed reconnect instruction; new subscriptions use the active declaration.

## Snapshot and transport

The first delivery and every subsequent delivery are complete bounded
replacement snapshots. A frame contains:

```ts
{ state: "snapshot", key: string, lease: string,
  entries: readonly { key: string; from: Principal; value: Value;
                      expiresAt: number }[] }
```

Entries use a stable key order. Empty rooms deliver `entries: []` immediately.
The owner serializes admission, snapshot selection, publication and expiry,
so there is no subscribe/snapshot race. Snapshot creation and fanout first
exclude expired or revoked entries. Lease data is internal transport state;
the public snapshot exposes `key` and entries but never the lease.

Both server and client multiplexing coalesce a slow consumer's pending channel
frame to the newest whole snapshot **per subscribed handle**, including its
own key/lease. Terminal refusals supersede the replaceable pending frame
and cannot be overwritten by a later snapshot. Bytes already handed to a
transport cannot be retracted. This reuses the bounded query
handoff and avoids a delta-merging protocol. Delta frames are a future wire
optimization only if measured full-frame traffic warrants them. A reconnect
always opens a fresh lease and receives a fresh snapshot. No durable commit
sequence, Last-Event-ID replay, missed-event recovery or room history is used.

The transport uses an internal `ChannelFrame<Value>`; the public
`ChannelSnapshot<Value>` and callbacks are a separate projection with no lease.

`POST /api/channel/<name>/set` takes `{ args, lease, version, value }`;
`/clear` takes `{ args, lease, version }`. Both return `{ ok: true }` or the
ordinary complete refusal envelope. The routes use ordinary mutation
authentication (Bearer session or development persona) and origin/CORS
handling, with no new cookie carrier. `version` is a positive safe integer,
strictly increasing per lease. The client allocates from 1 at invocation time;
the server accepts any version greater than the previous watermark (initially
0), allowing 2 to arrive before 1 without losing the newer intent.
The owner refuses stale/equal versions rather
than allowing an old delayed set to undo a newer clear. A validated command
consumes its version after scope, lease ownership and value shape validation,
but before publish admission, so an admitted caller's denied command still
fences older commands. Malformed and foreign commands cannot burn versions;
stale commands leave the watermark unchanged. A new lease resets
the sequence. The old `/publish` route is removed.

Limits are fixed runtime bounds, not new authored knobs: 4 KiB per canonical
JSON value, 1 KiB per normalized scope, 64 logical handles per exact room, and
1,024 channel handles per owner. Existing shared-stream child limits still
apply. A room is the normalized `(name, args)` pair. Room/owner capacity refuses new
subscriptions with the ordinary refusal envelope and terminates only the
refused child, without truncating a snapshot; expired values alone do not release connected handles. The server handoff retains
one replacement snapshot. Each client child allows two already-enqueued stream
chunks plus one replaceable pending frame; terminal refusal replaces that
pending frame and follows already-enqueued bytes. Closed and failed receivers release their entries
and handles. These are memory bounds, not a throughput or anti-abuse claim.

## Observable client surface

```ts
const typing = useChannel(api.typing, { conversationId })
typing.entries
typing.status // loading | ready | unavailable
await typing.set({ typing: true })
await typing.clear()

const room = client.channel(api.typing, { conversationId })
const observation = room.subscribe(snapshot => render(snapshot))
room.getSnapshot()
await room.set({ typing: true })
observation.close()
room.close()
```

`ChannelSnapshot<Value>` has immutable `entries`, optional own `key`, `status`,
optional `reason` (`reconnecting | offline | refused | closed`) and refusal.
It is an ephemeral snapshot, not a durable query receipt. React web and Expo
share this headless resource and `useSyncExternalStore` semantics.

Constructing a handle is inert. First observation or set opens a channel.
Once opened it stays open until `room.close()`, even with no observers.
An observation's close only detaches that listener. `clear()` with no live
lease is a local idempotent success and opens no connection; it also cancels
older sets still waiting for the initial snapshot, so a cold clear cannot be
undone by its own pending set. Closed handles cannot be reopened.
React owns and closes its handle on cleanup; a cancellable deferred cleanup
supports Strict Mode setup/cleanup/setup. Argument/account changes create new
handles. Independent handles own independent entries; listeners on one handle
share its snapshot/lease.

Until its first snapshot the resource is loading with no entries. Transport
loss immediately empties entries and key, exposes unavailable/reconnecting or
offline, and invalidates the lease. Fresh server state returns it to ready.
Terminal refusal, account change and close also erase state; delayed old
responses must not publish into the new account or reconnect incarnation.

Calls waiting for the initial snapshot are bounded by the existing 30-second
subscription timeout. A write already bound to an old lease never rebinds to
a new one. Writes while reconnecting/offline refuse locally. Versions are
allocated per invocation; a delayed/ambiguous request cannot win over a newer
one. No retry, offline queue, value prediction or automatic republish occurs.
A cold clear succeeds locally without claiming an owner effect. Other
successes mean the owner applied the state command, not that another
consumer observed it or that the value survives restart. An ambiguous network
outcome is reported and settles naturally through snapshots/TTL.

## Diagnostics and exclusions

Use existing `quarry`, `schema`, `input`, `rule`, and `op` families, with a
site, rewrite and the existing live-query guide page. Distinguish malformed
values, invalid/closed leases, stale versions, room/owner capacity and
authorization refusal. Ordinary durable mutations never read/write a channel.
No queries, joins, arbitrary filtering, transactions, prediction, offline
storage, history, signal API, maintained room aggregates or durable presence
are added. `connected` keeps its separate transport-count meaning.
