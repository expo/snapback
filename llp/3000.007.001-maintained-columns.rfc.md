# LLP 3000.007.001: Maintained columns — an aggregate on the row it describes

**Type:** RFC
**Status:** Review
**Systems:** Snapback 4 Quarry parser and binder; schema; the maintain evaluator; the write path and partition log; adoption; the TypeScript emitter; residency and disclosure notes; guide cards. Device prediction of the column is out of the first build (§3.7)
**Author:** Claude Fable 5.1 (for Charlie Cheever)
**Date:** 2026-09-17
**Revised:** 2026-09-17 (revision 2, after the first blind round — GPT NOT READY, Grok READY WITH CHANGES, both "build this form": an unconditional hidden-parent reservation; limbo aggregates make a parent's birth population-independent; an in-place rebuild that never deletes a parent and rewrites on redefinition; activation as a generation barrier; no device prediction of the column in the first build; a resolved dependency walk for the refusals; §10 records the round and its dispositions); 2026-09-17 (initial: the design ruling 30 commissioned; nothing is built)
**Related:** [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) (§20.9 maintains, §20.20, §21.3 P2 and P5, §14 ruling 30), [LLP 3000](./3000-snapback4.explainer.md), [LLP 2000.000](./2000.000-keep-the-core-flip-two-substrates.rfc.md), [LLP 3000.004](./3000.004-feeds-and-the-interview-reference-app.rfc.md)

## Summary

A `maintain` keeps a count or a sum in a table of its own, keyed by group. When the group
*is a row* — the likes of a post, the replies to a post, the members of a room — that
placement is the source of every caveat LLP 3000.007 §20.20 had to attach to it, and of
the hand-kept `posts.score` with `update <- allow` that three consecutive Clique builders
wrote instead. This RFC proposes the same aggregate, by the same evaluator, **stored as a
column of the row it describes**:

```quarry
table posts:
  authorId: principal
  body: text <=500
  at: time
  likeCount: count likes by postId                      -- proposed
  replyCount: count posts where .parentId != null by parentId
  by byLikes: likeCount, at, id
```

The engine writes it in the source row's transaction; no program, principal, job, native
job or seed can; it is zero from the row's birth, dies with the row, rides the row's
audience and arrives with `*`. *If the group is a row, the aggregate is a column; if the
group is a tuple, it is a `maintain`.*

The author ruled this **yes in direction** on 2026-09-17 (LLP 3000.007 §14, ruling 30):
the design and a two-family blind review first; nothing is built before READY from both.
First scope, from the ruling: the group is a reference to this table, the source does not
expire, the cascade is acyclic — read here at its narrowest, **no cascade in the first
build** (§3.9). Both families of the first round would build this form rather than
`maintain … over posts`; neither found it ready as first written (§10).

LLP 3000.007 §21.3's P5 is restated for this form: *ordinary fields keep their writer
class; each maintained field has exactly one declared engine derivation.* The writer
class is per column, and the compiler knows it.

## 1. Motivation

Evidence, all in LLP 3000.007 §21 and its record
(`benchmarks/runs/2026-09-17-snapback4-derived-probes/`):

- The 0.2.27 builder keeps `posts.score: int default 0` with `by byScore: score, at, id`,
  sets it in `like` from `likeCounts[postId]`, and so had to give **`posts` itself**
  `update <- allow`. The 0.2.25 and 0.2.26 builders did the same on a ranking table. The
  count on the row is what builders reach for first; the language offers no safe way to
  have it.
- §20.20's caveats on maintain-as-ranking: a group with no contribution has no row; ties
  break by maintained id, not by anything about the entity; a target can neither expire
  nor be capped, so groups outlive their entity; every shape needs a nested
  `likeCounts[.id]` read. Each follows from the aggregate living apart from its entity.
- A maintain "that groups by something other than its source's audience … reaches no
  device as a value" (feeds card). Likes are private to their principal and posts are
  public: the natural count cannot sync as a maintain. On the row it syncs as the row does.

## 2. The form

Inside a table block, a column line whose type position holds an aggregate:

```
<name>: count <source> [where <predicate>] by <column>
<name>: sum <source> of <column> [where <predicate>] by <column>
```

- `<source>` is an **ordinary table** — not a maintain's generated target (an engine write
  to a target does not fan out, so a column over one would go stale). It may be this
  table (`replyCount` above). **First scope: it has no `expire at`** (§3.10).
- `by <column>` names one column of the source whose type is a reference to **this**
  table (`postId: posts`), optional or not. A source row whose reference is null
  contributes to nothing. One `by` column; computed keys and tuples are the `maintain`
  form's.
- `<predicate>` is the maintain predicate grammar unchanged. `sum … of` takes what a
  maintain's `sum` takes.
- The column's type is `int` for `count`, the summed column's type for `sum`. It is
  required, never optional; its value is never null.

It **is** a column: present in `*`, shapes, `where`, `sort`, `group`; in `by` indexes at
any position; in `api.ts` (`Rows.posts.likeCount: number`; the emitter walks
`schema.tables[..].columns` and emits no insert or patch types).

It may **not** be depended on by anything that decides authority, identity, lifetime or
delivery. The check is one **resolved dependency walk**, shared by the binder and the
core's schema validation (hand-serialized schemas are checked too), over: every rule of
every table — terms on the row itself, **`exists` and `created` probes' keys and extra
equalities, positional probes of any index that contains the column, and `old`/`next`
terms**; every constraint — `unique`, `cap … by`, `immutable`, `after insert`'s final
exists; `expire at`; `default`; the `sync` line and its audience; `words(..)`; the `of`,
the predicate and the `by` of any other aggregate, table form or column form (§3.9). Each
refusal names the column, the dependent declaration and the rewrite. `RuleExpr::fields`
is not that walk (it collects only this-row terms). Two things are deliberately
**allowed**: a `by` index over the column — though a job's chunk index stays excluded by
the existing immutable-index rule — and an `append only` parent, whose constraint governs
program updates, not the engine's.

## 3. Semantics

### 3.1 Value

For a parent row P that exists and has not expired: the aggregate over the source rows S
with `S.<by> = P.id` that satisfy the predicate. Zero when there are none. With a
non-expiring source the physical value is the live value.

### 3.2 The write, and who may make it

`Runner::maintain` (`crates/snapback4-core/src/engine/maintains.rs`) fans a source row
change out to the maintains of that source, computes the old and new images'
contributions with `Maintain::selected`, `source_key` and `delta`, and coalesces equal
groups. A maintained column reuses that evaluator and ends differently: look the parent up
**with `tx.get` and `Table::expired` — never `fetch` or `get`**, which consult rules and,
on a device, record an unknown fact; if the parent is present and live, write the same
image with the one field changed — `tx.put(parent_table, table, new, Some(old))` — and
`row_changed(.., Origin::Maintained)`; if it is absent or expired, write the limbo row
instead (§3.3). An expired parent is absent: it is never `put`, so it is never
resurrected into the stream.

- **No rule is consulted** for the engine's write. The source write is judged by the
  source's own rules; that is the only authority involved.
- **No constraint is run** for the engine's write: none can involve the column (§2), and
  `append only` does not apply to it.
- **The reservation is unconditional.** Today's `reserve_maintains` returns early when the
  source is uniformly readable or the maintain has no filter, computed key or expiry, and
  `maintain_scratch` leases heap that it refunds — neither protects a *hidden parent*. For
  every maintained column and on **every** source-write path — insert, update (old and new
  parent), delete, both arms of `upsert`, and `insert … if absent` including the arm that
  does nothing — the engine prepays, before it resolves anything about the parent, the
  schema-bounded worst case of two parent attempts: the lookups, the row copies, every
  index entry of every index containing the column, rows written, partition work and heap;
  the actual charges are then suppressed through the prepaid path (`maintain_prepaid`,
  `charge_maintain`), and partition work is charged by the write's **origin**, not by
  whether the table is classified as a maintain target. A present parent, an absent
  parent and a parent with any non-overflowing value then cost the source writer the same
  on every meter, at ample and at just-insufficient budgets.
- **The named exception is overflow.** A sum near the 53-bit endpoint can refuse with
  `AggregateOverflow` naming the table and column, never a value (LLP 3000.007 §17, the
  rules card). The paired tests exclude it from equality and test it by itself.
- **Programs cannot write it.** The refusal is on the fields a caller **submits** — in an
  insert image, a patch, an upsert's either arm, an `insert … if absent` that would do
  nothing, an explicit `0` — before defaults, merging or no-op resolution; an internally
  materialized zero, and a field retained by `merge_patch`, are not submissions. It holds
  under the system context: jobs, **native jobs** (which reach `runner.update` with any
  declared column) and seeds are refused like any program. The binder refuses with the
  wording of today's maintain-target refusal, naming the column; the engine refuses
  beside `refuse_engine_owned` for hand-serialized IR.
- **`Engine::load`** (fixtures; it writes images as given and skips maintains) ignores a
  supplied value and runs the column's rebuild (§3.11) after loading, so a fixture cannot
  carry a lying count. The Postgres evaluation store's loader does the same or refuses
  tables with maintained columns; it gives no parity evidence otherwise.

### 3.3 Birth, death and limbo — population-independent

Counting a parent's pre-existing contributions at its insert would make the work — and
`E_BOUND` — depend on how many source rows name that id, including rows the predicate
excludes and rows the creator cannot read, and a delete-and-recreate could repeat the
experiment. So the engine never counts at birth. For each maintained column it keeps an
internal **limbo** table, keyed by parent id, holding the aggregate for ids that have
**no live parent row**: never readable, never synced, in no rule, absent from `api.ts`
and `sql` views by default, a row only while its value is not zero.

- A contribution whose parent is absent or expired updates the limbo row — one engine row
  write, as the present-parent case is, under the same reservation.
- **Birth:** inserting a parent takes the limbo value for its id (one `get`, one `delete`)
  or zero. O(1), whatever names the id.
- **Death:** physically removing a parent — a delete, or the expiry sweep — adds its
  column's value to the limbo row (one `put`) when that value is not zero. Between a
  parent's expiry and its sweep, contributions go to limbo; the sweep adds the stale
  stored value to them. An insert over an expired, unswept id performs that removal
  bookkeeping first, then the birth.
- Same-commit order is therefore immaterial: a reply inserted before its parent goes to
  limbo and the parent is born with it; a parent inserted first is born at zero and then
  incremented. A self-referential source contributes exactly once either way.

Refusing contributions to a missing parent was considered and rejected by both families:
it breaks forward references, seeding order and a like written while its post is not
held, and it would make parent existence an outcome channel.

### 3.4 Deleting source rows, and re-creation

Deleting a source row subtracts from the parent or from limbo, wherever the aggregate
lives. A parent re-created under an id takes limbo's value: the right count, at O(1).

### 3.5 Stream and log — the cost to be honest about

The engine's write is a `Put` of the **whole parent image** to each of the parent's
partitions (`partition::row_changed`), coalesced to one event per row per commit
(`partition::append`). Each contributing commit therefore logs and streams one full image
of the parent per destination partition: a like on a 500-byte public post is about 500
bytes of log and a row event for every holder. That is what the hand-kept `posts.score`
costs today, and more than an `online only` maintain, which streams nothing.

Rule of thumb for the card: *a count the row's readers want with the row is a column; a
counter that changes far more often than its row is read stays a `maintain … online
only`.* A note, `N_MAINTAINED_COLUMN_STREAM`, fires on the **parent** table's sync line
(not through a generated target's `inherited_from`, and not folded into
`N_MAINTAIN_SYNCED`'s envelope). Coalescing a stream page to the latest image per row is
a separate, measured follow-up.

### 3.6 Rows a device never acquired

A device stores every `put` it is streamed (`snapback4-device`, `device.rs`, `apply`) and
the stream applies no horizon (`partition.rs` uses it for acquisition only), so under
`sync public last 2000 by byTime` a like on an old post makes every device acquire that
post. The families disagreed: Grok would filter at the device (ignore a `put` for an id
not held whose horizon key sorts before the group's acquired boundary); GPT would accept
and measure, because a sound filter needs durable per-group acquisition boundaries, the
full ordering tuple, generation state, and event provenance the ordinary `put` does not
carry. **First build: accept and measure** (§7, item 2, a briefing gate). If the growth is
material on the Clique fixture the filter becomes its own reviewed device design before
this form ships on a horizoned public table; NOT-DOING's "exact horizon maintenance" stays
refused either way.

### 3.7 On a device: the first build does not predict the column

A device **never writes a maintained column**. A source write predicts exactly as it does
today — its own rows — and the count changes when the server's image of the parent
arrives. Nothing is lost against today: the hand-kept `score` is set from an `online
only` maintain, so `like` never predicted it.

The reason is a sync-protocol defect the first review found and execution confirmed
(`issues/20260917-snapback4-stream-page-serves-images-newer-than-its-watermark.md`): a
stream page serves the *current* image of a row under an older watermark, so a device can
hold an image that already contains its own unacknowledged write and replay that write on
top of it. "Holding the row is knowing the base" is false until that is repaired.

Predicting the column is a **later increment**, and these are its obligations, from the
first round: the ticket above is fixed; a prediction that skipped an unheld parent stays
skipped on every replay of that entry, or the source is required to be delivered in the
parent's commit (an `online only` source refused); replay's affected rows are recorded
and returned so watches over the parent are invalidated on failure and withdrawal, not
only on success; an engine-only predicted write does not add `pending` to the parent and
**preserves** a marker an ordinary prediction already put there (the asset path hides
pending rows' media); a device predicts a parent's birth at zero only for an id minted in
that mutation, and otherwise queues the insert without a row.

### 3.8 Rules, audience and disclosure

A maintained column is a dependency of no rule (§2), so an engine write never changes any
row's audience and the parent's partitions before and after are identical.

What it discloses, stated once: to every reader of the parent row, the **count** of source
rows naming that parent (or their **sum**); with a predicate, how many of them satisfy it
— a predicate-dependent fact about rows the reader may not be able to read; with an index,
the parents' relative order by that value; and, to a source writer, the overflow bit of
§3.2. A missing parent is absence, not a readable zero. Birth and death disclose nothing
more (§3.3).

`check` prints this as a note wherever parent readers are **not proven** able to read the
contributing source rows. That is a different proof from `N_MAINTAIN_DELTA`'s, which is
silent when a source's *write* rules imply its read rule: private likes on public posts
satisfy that and must still be noted here. When in doubt, the note prints.

### 3.9 No cascade in the first build

A maintained column cannot be the `of`, the predicate or the `by` of another aggregate,
and a column form cannot take a maintain's generated target as its source (§2). Reason:
writes under `Origin::Maintained` do not fan out to maintains (`engine/write.rs`,
`row_changed`), so either would go stale; an ordered, budgeted, cycle-refusing cascade is
its own design. The ruling's acyclic cascade is the ceiling, not the first build. A
self-referential *source* (`replyCount`) is not a cascade and is admitted.

### 3.10 Expiring sources: refused in the first build

The source may not have `expire at`: its live value would change with no write, the stored
column would be stale until the sweep, and an index over it would order stale values (LLP
3000.007 §20.9.3, §20.21). The refusal points at the `maintain` form, which recomputes
live contributions at read time. An expiring **parent** is fine (§3.2, §3.3).

### 3.11 Adoption

- **Images without the field read 0.** The engine gives a maintained column an implicit
  literal `0` for `materialize_optional_fields`, for old-image validation during
  activation's walk, and for index builds — an engine interpretation; authors still cannot
  write `default` on it. Today's `materialize_optional_fields` fills only optionals and
  authored literal defaults, and `classify` marks a required column added without a default
  `Narrowing`; both gain a named exception for "required maintained column added", which is
  `Additive`. `Additive` here means recomputable derived data is added — **not** that no
  parent row changes — and a column target must not enter `classify`'s whole-maintain-
  table bypass (`successor.rs`, the target short-circuit).
- **The rebuild is in place and never deletes a parent.** `rebuild_maintain_inner` deletes
  every row of its target before folding the source; for a column the target is the
  application's table, and reusing that loop would delete every post. The column rebuild
  folds the source's contributions by parent id and `put`s each existing parent's image
  with the one field changed; ids with no live parent go to limbo.
  - *Initial addition:* only parents whose aggregate is not zero are written; the rest
    read the implicit 0.
  - *Redefinition* (kind, source, predicate, `by`, a dependency's literal default): every
    parent whose stored value differs from the recomputed one is rewritten, **including
    nonzero to zero**, preserving all ordinary fields and other maintained columns; limbo
    is rebuilt with it.
  - *Removal* follows the ordinary column-removal path; limbo is dropped.
- **Activation is a generation barrier, not a stream of rows.** Rewriting 100,000 public
  parents in one commit would exceed the response ceiling, and a client that cannot decode
  the page cannot learn the generation it needs to discard its images. So the rebuild's
  row writes emit **no partition row events**; the activation commit names the table as
  touched (so server-run watches re-run), the generation changes, and every device
  re-acquires by snapshot — which it must already do, because
  `successor::keeps_literal_default_images` is false when maintains differ. Rebuild and
  generation publish in one transaction; a failed rebuild rolls back; a snapshot page that
  crosses a generation is already refused.
- The Postgres evaluation store has no activation API: no adoption parity is claimed.

### 3.12 Residency and classification

A read of the column is a read of its row: `held`, `horizon` or `server` by the parent's
sync line, with no new class. A source write keeps its prediction class.

## 4. What it replaces

| Today (0.2.27 lane, `snapback/social.q`, `trending.q`) | With this |
| --- | --- |
| `posts.score: int default 0`, `update <- allow` on `posts` | `likeCount: count likes by postId`; no update rule for it |
| `update posts[postId] { score: likeCounts[postId] }` in `like` | nothing: the engine keeps it |
| `maintain likeCounts` + nested `likeCounts[.id]` in every post shape | the count arrives with `*` |
| `trendingPosts` table, its expiry, its `insert/update <- allow`, the upsert in `like` and the backfill job | `by byHourLikes: hour(at), likeCount, at, id` (ruling 29) read through hour lanes (ruling 28); zero-like posts and post-time ties included |

## 5. Alternatives considered

- **Fix maintain tables instead** (`maintain … over posts carrying at`). Keeps table-level
  writer separation and could stream less; still needs parent-domain zeros, parent
  lifetime and audience, tie-break fields and a projection story, and the count still
  does not arrive with the row. Put to the author beside ruling 30 and not chosen; both
  review families would build the column form.
- **Computed columns as one family** (`postedHour: int = hour(.at)`): put to the author
  beside ruling 29 and not chosen. Nothing here depends on it.
- **`system update`, privileged helpers, triggers.** Closed by LLP 3000.007 §20.20.
- **Do nothing; ship the note** (ruling 31). Makes the footgun visible; does not give
  builders the count on the row.
- **Count at birth; or refuse contributions to a missing parent.** §3.3.

## 6. What changes where

- `snapback4-lang`: the column-line grammar; the binder (reference resolution, the
  resolved dependency walk of §2, the refusals, the two notes); the language, maintains,
  rules, indexes and feeds cards; `guide::CODES`.
- `snapback4-core`: the declaration on `Schema` (a `Maintain` whose target is a column —
  evaluator, predicate and dependency machinery reused, not copied) and the same walk in
  schema validation; `Runner::maintain` and a sibling of `apply_aggregate`; the
  unconditional reservation and origin-keyed partition charging; limbo; the submitted-
  field refusal on every write arm; `load`; `successor.rs`, the store's assessment and
  activation (implicit 0, the named `Additive` exception, the in-place rebuild, the
  event-free activation commit); the sweep's removal bookkeeping.
- `snapback4-device`: nothing writes the column (§3.7); both stores read it as a column.
- `snapback4` verbs: `check --cost` and `why` for the column; `test --residency` rows.
- No wire change, no new `Read` or `Write` field, no card word beyond the column form.

## 7. Measurements owed before a lane is briefed

Items 1, 2 and 5 are gates: no lane is briefed without them.

1. Log and stream bytes per like — **serialized HTTP bytes** as well as log rows — for a
   500-byte and a 4,000-byte parent, against the `online only` maintain and the hand-kept
   `score`; durable log growth over 100,000 likes.
2. Rows a device gains per day under `sync public last 2000 by byTime` on the Clique scale
   fixture when likes fall on old posts (§3.6).
3. Index churn: entry writes per change with one and with three indexes over the column.
4. Limbo: the cost of a contribution to an absent parent, of a birth and of a death,
   against the present-parent write, on every meter.
5. Activation: elapsed time, **peak memory** and whether a **real device completes
   adoption over HTTP**, for 100,000 parents and 1,000,000 source rows, beside the same
   maintain's rebuild; retry and contention behaviour while it runs.

## 8. Acceptance (tests a lane must bring)

- **Oracle.** An independent model, not the evaluator: inserts, predicate-flipping
  updates, reference-moving updates (old parent down, new parent up, one commit), deletes,
  rollback, sums, several maintained columns on one table, a self-referential source
  including same-commit parent-and-child in both orders, deletion and re-creation of a
  parent, expiry of a parent with contributions before and after the sweep; on the server
  and on both device stores as readers; after a rebuild; on the Postgres evaluation store
  for ordinary mutations.
- **Refusals.** Every write arm — insert, update, both upsert arms, a no-op `insert … if
  absent`, an explicit `0`, native and system writes, seeds, raw IR — and every dependency
  of §2's walk, including a probe's extra equality (`exists posts[id = .postId, likeCount
  != 0]`), a positional probe of an index containing the column, `old`/`next` terms,
  `after insert`, a maintain target as a source, and a raw schema that violates them.
- **Paired observations** in §17's method, at ample and at just-insufficient budgets: two
  worlds differing only in the parent — absent, present, present with another value,
  expired-unswept — give the source writer an identical HTTP body, receipt, retry, every
  meter field, stream and snapshot; likewise a parent's creator against limbo populations
  of none and of 100,000 filtered-out source rows. Overflow is asserted separately as the
  declared exception.
- **Rebuild.** Never deletes a parent (assert the row count and every ordinary field);
  initial addition leaves zero parents untouched and reading 0; redefinition rewrites
  nonzero to zero; limbo matches the oracle afterwards.
- **Activation.** No row events in the activation commit; a device on the old generation
  learns the new one and re-acquires; 0 is never served from a pre-generation held image
  or from a snapshot page that crossed the activation.
- **Device.** No device path writes the column; a like predicts its own row and the count
  follows the server's image; watched results, not only stored rows, are asserted.
- **Index and cursor.** Paging an index over the column while counts move asserts the
  maintains card's moving-key contract explicitly.
- **Notes.** Private source with a public parent whose write rules imply source
  readability still prints the disclosure note; filtered sums and indexed order are named;
  neither note fires on the existing cards, recipes and templates (a census, asserted).
- **Published examples.** Wave 12's assertion that no published document ships a ranking a
  principal can write stays green, beside executable attempts to write the column and to
  move it through the source outside the source's authority.

## 9. Questions the first round settled, and what stays open

Settled: a rule-free column is right for the first build (both); leaving `pending` unset
on an engine-predicted parent is right and restore never depends on the marker (both) —
moot until §3.7's later increment; counting at birth is wrong and refusing contributions
is worse (§3.3); an implicit 0 plus a generation barrier close the zero-as-fact window
(§3.11). The first extension after the first build is parents addressed by a total unique
key (`profiles.followerCount: count follows by followedId`), before any cascade (GPT).

Open: §3.6's acceptance is a measured bet; §3.7's later increment waits on the sync
protocol.
