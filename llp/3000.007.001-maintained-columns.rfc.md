# LLP 3000.007.001: Maintained columns — an aggregate on the row it describes

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 Quarry parser and binder; schema; the maintain evaluator; the write path and partition log; device prediction; adoption; the TypeScript emitter; residency and disclosure notes; guide cards
**Author:** Claude Fable 5.1 (for Charlie Cheever)
**Date:** 2026-09-17
**Revised:** 2026-09-17 (initial: the design ruling 30 commissioned; nothing is built; goes to two model families blind before any lane is briefed)
**Related:** [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) (§20.9 maintains, §20.20, §21.3 P2, §14 ruling 30), [LLP 3000](./3000-snapback4.explainer.md), [LLP 2000.000](./2000.000-keep-the-core-flip-two-substrates.rfc.md), [LLP 3000.004](./3000.004-feeds-and-the-interview-reference-app.rfc.md)

## Summary

A `maintain` keeps a count or a sum in a table of its own, keyed by group. When the group
*is a row* — the likes of a post, the replies to a post, the members of a room — that
placement is the source of every caveat LLP 3000.007 §20.20 had to attach to it, and of
the hand-kept `posts.score` with `update <- allow` that three consecutive Clique builders
wrote instead. This RFC proposes the same aggregate, by the same evaluator, **stored as a
column of the row it describes**:

```quarry
table posts:
  authorId: principal
  body: text <=500
  at: time
  likeCount: count likes by postId                      -- proposed
  replyCount: count posts where .parentId != null by parentId
  by byLikes: likeCount, at, id
```

The engine writes it in the source row's transaction; no program, principal, job or seed
can; it is zero from the row's birth, dies with the row, rides the row's audience and
arrives with `*`. *If the group is a row, the aggregate is a column; if the group is a
tuple, it is a `maintain`.*

The author ruled this **yes in direction** on 2026-09-17 (LLP 3000.007 §14, ruling 30):
the design and a two-family blind review first; nothing is built before READY from both.
First scope, from the ruling: the group is a reference to this table, the source does not
expire, the cascade is acyclic. This design takes the narrowest reading of the last — **no
cascade at all in the first build** (§3.9).

## 1. Motivation

Evidence, all in LLP 3000.007 §21 and its record
(`benchmarks/runs/2026-09-17-snapback4-derived-probes/`):

- The 0.2.27 builder keeps `posts.score: int default 0` with `by byScore: score, at, id`,
  sets it in `like` from `likeCounts[postId]`, and so had to give **`posts` itself**
  `update <- allow`. The 0.2.25 and 0.2.26 builders did the same on a ranking table. The
  count on the row is what builders reach for first; the language offers no safe way to
  have it.
- §20.20's caveats on maintain-as-ranking: a group with no contribution has no row; ties
  break by maintained id, not by anything about the entity; a target can neither expire
  nor be capped, so groups outlive their entity; every shape needs a nested
  `likeCounts[.id]` read; and a device cannot predict a count whose base it does not hold
  ("the affected aggregate value or its absence is not known locally; queued without a
  predicted row", `engine/maintains.rs`, `apply_aggregate`). Each follows from the
  aggregate living apart from its entity.
- A maintain "that groups by something other than its source's audience … reaches no
  device as a value" (feeds card). Likes are private to their principal and posts are
  public: the natural count cannot sync as a maintain. On the row it syncs as the row does.

## 2. The form

Inside a table block, a column line whose type position holds an aggregate:

```
<name>: count <source> [where <predicate>] by <column>
<name>: sum <source> of <column> [where <predicate>] by <column>
```

- `<source>` is a table (it may be this table: `replyCount` above). **First scope: it has
  no `expire at`** (§3.10).
- `by <column>` names one column of the source whose type is a reference to **this**
  table (`postId: posts`), optional or not. A source row whose reference is null
  contributes to nothing. One `by` column; computed keys and tuples are the `maintain`
  form's.
- `<predicate>` is the maintain predicate grammar unchanged (maintains card: scalar
  comparisons of the source row's own columns, `and`/`or`/`not`, literals; no tables,
  `viewer`, `now`, helpers or arithmetic). `sum … of` takes what a maintain's `sum` takes.
- The column's type is `int` for `count`, the summed column's type for `sum`. It is
  required, never optional; its value is never null.

It **is** a column: present in `*`, shapes, `where`, `sort`, `group`; in `by` indexes at
any position; in `api.ts` (`Rows.posts.likeCount: number` — the emitter walks
`schema.tables[..].columns`, `crates/snapback4-lang/src/emit.rs`, and there are no insert
or patch types for it to be excluded from).

It may **not** appear: as a field of any `insert`, `update`, `upsert` or seed row (§3.2);
in any rule of any table (§3.8); in `unique`, `cap … by`, `immutable`, `expire at`,
`default`, a `sync` line or a `words(..)` index; as the `of`, the predicate or the `by` of
another aggregate (§3.9). Each refusal names the column and says what to do instead.

## 3. Semantics

### 3.1 Value

For a parent row P that exists: the aggregate over the source rows S with `S.<by> = P.id`
that satisfy the predicate. Zero when there are none. With a non-expiring source the
physical value is the live value; there is no live recompute path.

### 3.2 The write, and who may make it

`Runner::maintain` (`crates/snapback4-core/src/engine/maintains.rs`) already fans a source
row change out to every maintain of that source, computes the old and new images'
contributions with `Maintain::selected`, `source_key` and `delta`, coalesces equal
groups, and calls `apply_aggregate`, which gets one target row, adds the change, checks
the 53-bit range, and `tx.put`s the row followed by `row_changed(.., Origin::Maintained)`.

A maintained column is the same fan-out with a different last step: look the parent up by
id in **its own table**; if it is absent or expired, do nothing; otherwise write the same
image with the one field changed — `tx.put(parent_table, table, new, Some(old))` — and
`row_changed(parent_table, Some(old), Some(new), Origin::Maintained)`. Under
`Origin::Maintained` the row change charges the maintain meter, records the written table
and emits the partition events, and does **not** place assets or fan out to further
maintains (`engine/write.rs`, `row_changed`) — which is the behaviour wanted (§3.9).

- **No rule is consulted** for the engine's write, exactly as for a maintain target. The
  source write is judged by the source's own rules; that is the only authority involved.
- **No constraint can involve the column** (§2), so `check_constraints` is not run for the
  engine's write. Overflow keeps `AggregateOverflow`, naming the table and column and never
  a value (LLP 3000.007 §17).
- **Reservation.** A source write reserves the maintain's worst case before it inspects
  anything hidden (`maintain_scratch`, `reserve_target_resolution`). The reservation for a
  maintained column is the parent row's copy ceiling times its index count, by the formula
  `Runner::maintain` already uses for a target table — with the parent table's numbers.
  Hidden-target discipline is unchanged: a source write's outcome may not depend on
  whether the parent exists or on its value, except through the overflow bit the rules
  card already names.
- **Programs cannot write it.** The binder refuses the field in any write's patch or
  insert image with the wording of today's maintain-target refusal
  (`bind/program.rs`: "… is a maintained aggregate; write its source rows instead"),
  naming the column; the engine refuses it for hand-serialized IR beside
  `refuse_engine_owned`. Seeds (`POST /seed`) and jobs are programs for this purpose: a
  seeded parent row that carries the field is refused; seeded source rows maintain it.
- **An ordinary update of the parent** by a program keeps the column: `merge_patch` merges
  a patch that cannot name it.

### 3.3 Birth

On a parent's insert the column is the aggregate of the contributions that already exist
for that id — normally none. References do not enforce existence, so a source row may
precede its parent. The engine counts them through an index on the source that leads with
the `by` column; the binder requires one and names it in the refusal when it is missing
(as `expire at` requires its index). The count is charged to the maintain meter; a parent
inserted over a very large orphaned population can abort `E_BOUND`. That cost is paid at
most once per parent, and zero contributions cost one index probe.

### 3.4 Death

Deleting or expiring the parent removes the column with the row. Source rows are
untouched, and a later source write for a missing parent does nothing. A parent re-created
under the same id recounts (§3.3).

### 3.5 Stream and log — the cost to be honest about

The engine's write is a `Put` of the **whole parent image** to the parent's partitions
(`partition::row_changed`), coalesced to one event per row per commit
(`partition::append`). So each contributing commit streams and logs one full image of the
parent: a like on a 500-byte post costs about 500 bytes of log and a row event to every
holder of that post. This is exactly what the hand-kept `posts.score` costs today, and
more than an `online only` maintain, which streams nothing.

Rule of thumb for the card: *a count the row's readers want with the row is a column; a
counter that changes far more often than its row is read stays a `maintain … online
only`.* A note, `N_MAINTAINED_COLUMN_STREAM`, prints the consequence where a maintained
column sits on a synced table, in `N_MAINTAIN_SYNCED`'s manner. Coalescing a stream page
to the latest image per row is a separate, measured follow-up, not part of this design.

### 3.6 Rows a device never acquired

A device applies every `put` it is streamed (`crates/snapback4-device/src/device.rs`,
`apply`), including one for a row older than its acquisition horizon. Ordinary updates to
old rows are rare; an engine-written count makes them common (a like on an old post), so
a device under `sync public last 2000 by byTime` would slowly acquire every old post that
is liked. **Open for the reviewers and for measurement** (§7): either accept and measure
the growth on the Clique fixture, or have a device ignore a `put` for a row it does not
hold that sorts before its group's acquired boundary. The second is a device change with
its own review; NOT-DOING's "exact horizon maintenance" stays refused either way.

### 3.7 On a device

Prediction runs the same program through the same runner with real writes marked
`pending`, the confirmed image of each touched row remembered first; the server's image
later restores, applies and replays (`device/predictions.rs`). For a maintained column:

- the parent's table is not synced → skip, as a device skips an unsynced maintain today;
- the parent row is not held → **skip silently**. Nothing local can show a wrong count for
  a row that is not there, so this is *not* a prediction failure. It removes, for this
  form, the "aggregate base is not known locally" class that makes a maintain over a
  partly held group queue without a row;
- the parent row is held → write the image with the changed count, remembering its base
  first. **The engine's predicted write does not set `pending` on the parent**: the post
  is not pending, only a number on it is provisional, and restore works from the base
  image, not from the marker. (A hand-kept `update posts[..] { score }` marks the whole
  post pending today.)

So a like predicts its count when the post is held and simply predicts the like when it
is not; no read of the column ever costs a mutation its prediction, because a program
never reads a fact it cannot already read from the row.

### 3.8 Rules, audience and disclosure

A maintained column appears in no rule. Therefore an engine write never changes any row's
audience, the parent's partitions before and after are identical, and sync inference is
untouched.

The count is readable by every reader of the parent row. Where the source's readers are
fewer than the parent's (private likes, public posts) that is a declared channel — the
author declared it by writing the column — and `check` prints it as `N_MAINTAIN_DELTA`
prints a readable maintain over a hidden source: the column, the source, and the facts it
discloses (how many source rows match the predicate for this parent; relative values when
indexed). It is silent when every parent reader can read the source rows anyway.

### 3.9 No cascade in the first build

A maintained column cannot be the `of`, the predicate or the `by` of another aggregate
(`profiles.likesReceived: sum posts of likeCount by authorId` is refused, with the
rewrite: count the source directly — `count likes by authorId` with the fact carried on
the like). Reason: engine writes do not fan out to maintains today, and an ordered,
budgeted, cycle-refusing cascade is its own design. The ruling's scope — an acyclic
cascade — is the ceiling, not the first build.

### 3.10 Expiring sources: refused in the first build

The source may not have `expire at`. Its live value would change with no write, the stored
column would be stale until the sweep, and an index over it would order stale values
(LLP 3000.007 §20.9.3, §20.21). The refusal points at the `maintain` form, which recomputes
live contributions at read time. An expiring **parent** is fine.

### 3.11 Adoption

Adding, changing or removing a maintained column is a derived rebuild of that column at
activation, classified `Additive` as a maintain's rebuild is (`successor.rs`, `classify`),
and dry-run for fit by the store's assessment. It is the one case where a required column
is added to a populated table without a literal default and is not `Narrowing`: rows
written before it read **0** (through `materialize_optional_fields`, as a literal default
reads), and the rebuild writes only the parents whose aggregate is not zero. A new index
over the column is an ordinary index build over those images. A generation that adds or
redefines one invalidates devices' held images of that table, as a changed maintain
already does (`successor::keeps_literal_default_images` returns false when maintains
differ); they re-acquire.

### 3.12 Residency and classification

A read of the column is a read of its row: `held`, `horizon` or `server` by the parent's
sync line, with no new class. A source write keeps its prediction class: the engine's
side effect never costs prediction (the maintains card's rule for an online-only
aggregate, unchanged).

## 4. What it replaces

| Today (0.2.27 lane, `snapback/social.q`, `trending.q`) | With this |
| --- | --- |
| `posts.score: int default 0`, `update <- allow` on `posts` | `likeCount: count likes by postId`; no update rule for it |
| `update posts[postId] { score: likeCounts[postId] }` in `like` | nothing: the engine keeps it |
| `maintain likeCounts` + nested `likeCounts[.id]` in every post shape | the count arrives with `*` |
| `trendingPosts` table, its expiry, its `insert/update <- allow`, the upsert in `like` and the backfill job | `by byHourLikes: hour(at), likeCount, at, id` (ruling 29) read through hour lanes (ruling 28); zero-like posts and post-time ties included |
| a like's count visible only after the server answers | predicted on a device that holds the post |

## 5. Alternatives considered

- **Fix maintain tables instead** (`maintain … over posts carrying at`): zero groups seeded
  from the parent, lifetime and audience from the parent, carried columns for ties. Keeps
  "a user row is written only by programs" true per table. Rejected as the primary form:
  four features to reach one outcome, and the count still does not arrive with the row.
  Put to the author as an alternative to ruling 30; not chosen.
- **Computed columns as one family** (`postedHour: int = hour(.at)`): put to the author as
  an alternative to ruling 29; not chosen. Nothing here depends on it.
- **`system update`, privileged helpers, triggers.** Closed by LLP 3000.007 §20.20: an
  imperative statement that borrows authority cannot be analysed for disclosure or bounded
  per write; a declared aggregate can.
- **Do nothing; ship the note.** Ruling 31's note flags the hand-kept copy and offers the
  invariant rule. It makes the footgun visible; it does not give builders the count on the
  row, and `update <- allow`-with-a-pin is still three lines of rule per copy.

## 6. What changes where

- `snapback4-lang`: the column-line grammar; the binder (reference resolution, the source
  index requirement, every refusal of §2, the two notes); the language, maintains, rules,
  indexes and feeds cards; `guide::CODES`.
- `snapback4-core`: `Schema` gains the declaration (a `Maintain` whose target is a column —
  the evaluator, predicate and dependency machinery are reused, not copied);
  `Runner::maintain` and a sibling of `apply_aggregate`; the per-column write refusal;
  birth (§3.3); `successor.rs` and the store's assessment; `rebuild` for a column.
- `snapback4-device`: the skip rules of §3.7 and the unmarked predicted write; both stores.
- `snapback4` verbs: `check --cost` and `why` for the column; `test --residency` rows.
- No wire change, no new `Read` or `Write` field, no card word beyond the column form.

## 7. Measurements owed before a lane is briefed

1. Log and stream bytes per like for a 500-byte and a 4,000-byte parent, against the
   `online only` maintain and against the hand-kept `score`; the chat fixture's
   `messages`-parent case (a room's `messageCount`).
2. Rows a device gains per day under `sync public last 2000 by byTime` on the Clique scale
   fixture when likes fall on old posts (§3.6).
3. Index churn: entry writes per change with one and with three indexes over the column
   (wave 12 measured two per value change for a maintain's value index).
4. Birth over an orphaned population of 0, 1,000 and 100,000 source rows.
5. Activation time of the rebuild for 100,000 parents and 1,000,000 source rows, beside the
   same maintain's rebuild.

## 8. Acceptance (tests a lane must bring)

- The column equals an oracle after inserts, predicate-flipping updates, reference-moving
  updates (old parent down, new parent up, one commit) and deletes; on the server and both
  device stores; after a rebuild; after adoption onto a populated store (zero parents
  untouched and reading 0).
- Every refusal of §2, each by code and rewrite, and the engine-side refusal for
  hand-serialized IR that names the field in a patch, an insert image and a seed row.
- Paired observations in §17's method: two worlds differing only in a parent the writer
  cannot read (absent, hidden, hidden with another value) give the source writer an
  identical outcome, receipt, retry, every meter field, stream and snapshot.
- Device: a like on a held post shows the new count at once with no `pending` on the post,
  survives restore–apply–replay, and converges to the server's image; a like on a post that
  is not held predicts the like and writes no parent; an unsynced parent is skipped.
- An index over the column pages correctly while counts move between pages (the cursor
  promise is the maintains card's, no stronger).
- The two notes fire where §3.5 and §3.8 say and nowhere on the existing cards, recipes and
  templates (a census, asserted).
- Wave 12's assertion that no published document ships a ranking a principal can write
  stays green, and the feeds card's Trending moves to the column only when rulings 28 and
  29 are built.

## 9. Open questions for the reviewers

1. §3.6 — accept the device's gradual acquisition of old parents, or filter at the device?
2. §3.7 — is leaving `pending` unset on an engine-predicted parent right, or does any
   client path rely on the marker to find rows to restore?
3. §3.3 — is counting at birth right, or should a parent start at 0 and a contribution to a
   missing parent be refused (which would make references enforce existence for these
   sources only)?
4. §3.8 — is a rule-free column too strict? (`read <- .memberCount != 0` is conceivable; it
   would let an engine write change an audience.)
5. §3.11 — reading 0 for images written before the column exists: is there any path
   (a device's held image, a snapshot in flight across activation) on which that 0 is
   presented as fact for a parent whose aggregate is not zero?
6. First extension after the first build: parents addressed by a total unique key rather
   than an id (`profiles.followerCount: count follows by followedId` via `byPrincipal`),
   or the acyclic cascade?
