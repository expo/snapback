**Type:** RFC
**Status:** Review

## Summary

A `maintain` keeps a count or a sum in a table of its own, keyed by group. When the group
*is a row* — the likes of a post, the replies to a post, the members of a room — that
placement is the source of every caveat LLP 3000.007 §20.20 had to attach to it, and of
the hand-kept `posts.score` with `update <- allow` that three consecutive Clique builders
wrote instead. This RFC proposes the same aggregate, by the same evaluator, **shown as a
column of the row it describes**:

```quarry
table posts:
  authorId: principal
  body: text <=500
  at: time
  likeCount: count likes by postId                      -- proposed
  replyCount: count posts where .parentId != null by parentId
  by byLikes: likeCount, at, id
```

No program, principal, job, native job or seed can write it; it is zero from the row's
birth, dies with the row, rides the row's audience and arrives with `*`. *If the group is
a row, the aggregate is a column; if the group is a tuple, it is a `maintain`.*

**The mechanism (revision 3): a private maintain plus a mirror.** The declaration is a
`maintain` the author cannot see — the authoritative total for every parent id, live,
absent or expired, kept by today's maintain machinery unchanged — and an engine step that
copies the total onto the parent row whenever that row is present and live. Every hard
case the first two rounds found in keeping the total *only* on the row (what to do while
the parent is absent or expired, how to be born, how to die, where overflow is checked,
what a redefinition reconciles) has one answer: the private total is the truth, and the
column is its mirror.

The author ruled this **yes in direction** on 2026-09-17 (LLP 3000.007 §14, ruling 30):
the design and a two-family blind review first; nothing is built before READY from both.
First scope: the group is a reference to this table, the source does not expire, **no
cascade** (§3.9). Both families, in both rounds, would build this form rather than
`maintain … over posts`.

LLP 3000.007 §21.3's P5 is restated for this form: *ordinary fields keep their writer
class; each maintained field has exactly one declared engine derivation.*

## 1. Motivation

Evidence, all in LLP 3000.007 §21 and its record
(`benchmarks/runs/2026-09-17-snapback4-derived-probes/`):

- The 0.2.27 builder keeps `posts.score: int default 0` with `by byScore: score, at, id`,
  sets it in `like` from `likeCounts[postId]`, and so had to give **`posts` itself**
  `update <- allow`. The 0.2.25 and 0.2.26 builders did the same on a ranking table. All
  three apps *also* declare `maintain likeCounts: count likes by postId`: they already pay
  for the aggregate's own row; what they lack is a safe way to have it on the post.
- §20.20's caveats on maintain-as-ranking: a group with no contribution has no row; ties
  break by maintained id; a target can neither expire nor be capped; every shape needs a
  nested `likeCounts[.id]` read. Each follows from the aggregate living apart from its
  entity.
- A maintain "that groups by something other than its source's audience … reaches no
  device as a value" (feeds card). Likes are private to their principal and posts are
  public: the natural count cannot sync as a maintain. On the row it syncs as the row does.

## 2. The form

Inside a table block, a column line whose type position holds an aggregate:

```
<name>: count <source> [where <predicate>] by <column>
<name>: sum <source> of <column> [where <predicate>] by <column>
```

- `<source>` is an **ordinary table** — not a maintain's generated target. It may be this
  table (`replyCount`). **First scope: it has no `expire at`** (§3.10).
- `by <column>` names one column of the source whose type is a reference to **this**
  table, optional or not. A null reference contributes to nothing — the private lowering
  **excludes null references before any delta is evaluated** (a plain maintain would
  aggregate a `[null]` group, which could overflow for rows that contribute nowhere), and
  it maps the group to a collision-free internal field, so a reference column that happens
  to be called `value` or `id` is an ordinary source column. One `by` column; computed keys
  and tuples are the `maintain` form's.
- `<predicate>` is the maintain predicate grammar unchanged. `sum … of` takes what a
  maintain's `sum` takes.
- The column's type is `int` for `count`, the summed column's type for `sum`; required,
  never null.

It **is** a column for reading: in `*`, shapes, `where`, `sort`, `group`; in `by` indexes
at any position; in `api.ts` row types. **A write's result never carries it** (§3.2).

It may **not** be depended on by anything that decides authority, identity, lifetime or
delivery. The check is one **resolved dependency walk**, shared by the binder and the
core's schema validation and made over *resolved* index definitions (raw schemas
included): every rule of every table — terms on the row itself, `exists` and `created`
probes' keys and extra equalities, positional probes of any index that contains the
column, `old`/`next` terms; every constraint — `unique`, `cap … by`, `immutable`, `after
insert`'s final exists; `expire at`; `default`; the `sync` line, its audience **and its
horizon index** (`sync … last N by <an index containing the column>` would let a like
change which rows a device acquires); `words(..)`; the `of`, the predicate and the `by` of
any other aggregate (§3.9). Each refusal names the column, the dependent declaration and
the rewrite. `RuleExpr::fields` is not that walk. A rule *probe* and a program *read* are
different forms (`RuleExpr::Exists` against `Scan`/`Get`), so an index `likeCount, at, id`
stays fully readable and pageable; a job's chunk index stays excluded by the existing
immutable-index rule; an `append only` parent is allowed, its constraint governing program
updates, not the engine's.

## 3. Semantics

### 3.1 Value

For a parent row P that exists and has not expired: the aggregate over the source rows S
with `S.<by> = P.id` that satisfy the predicate. Zero when there are none.

### 3.2 The mechanism: a private maintain, and its mirror

**The private maintain.** The declaration generates a maintain — same kind, source,
predicate and `by` — whose target is an engine-named table the author cannot spell (its
name is not a Quarry identifier). It is a `Maintain` in `Schema.maintains` with a
`private` mark and the owning `(table, column)`; its target is **not** the parent table,
so `maintain_for(parent)` stays `None` and neither `classify`'s maintain-target bypass nor
`refuse_engine_owned` ever sees the application's table as engine-owned. It has no read
rule and is never synced. Everything else is today's maintain, unchanged:
`Runner::maintain`, `apply_aggregate`, the 53-bit check on **the one authoritative
value**, `rebuild_maintain`. It holds the total for every parent id that has one —
whether the parent is live, absent, expired or deleted.

**"Private" is operational, not a naming convention.** An unspellable name and a denied
read rule stop neither a hand-serialized rule probing the target's `byGroup` (a probe does
not consult the probed table's read rule), nor a native job, which names tables as strings
and runs as the system. So:

- *One predicate*, `visible`, decides every enumeration, and a private target and its
  `Maintain` fail it: both emitters (`api.ts` and the Rust module), `GET /` and **`GET
  /schema`**, `check`'s counts and listings, `check --residency`, `why`, `data` (including
  its suggestions), `sql`'s views, `/changes` — ordinary commit metadata **and** its
  saturated-page fallback, which today lists every schema table — and adoption
  diagnostics, which attribute the private table's steps to the owning column instead of
  reporting "a table is added". `doctor` keeps honest physical row and byte totals and
  says they include engine-internal storage.
- *A public schema projection.* `GET /schema` is the device's `Backend` today and sends the
  whole `Schema`. The device and every client receive a projection with **no private
  tables and no private maintains**; it carries, per maintained column, what a device
  needs — that the column is unwritable, that a missing value reads 0, and a **derivation
  identity** (a digest of kind, source, predicate and `by`) so that a changed derivation
  still changes what `keeps_literal_default_images` compares. The server keeps the
  complete schema.
- *A core invariant.* No program, native call, rule, constraint, seed, fixture or
  hand-serialized IR or schema can address a private target — `Get`, `Scan`, an `exists`
  or `created` probe, or any write — **including under the system context**. Core
  validation refuses the schema or program; the runtime refuses the access; only the
  engine's own birth, mirror and rebuild path reaches the table. Every refusal and every
  diagnostic names the owning `(table, column)`, never the private name.

**The mirror.** After **every** `apply_aggregate` return that changed the private total
for id X — a `put`, or the delete-to-zero that today returns without one — the engine
re-reads the parent's **current** image with **`tx.get` and `Table::expired`** (never
`fetch` or `get`, which consult rules and, on a device, record an unknown fact; and never
an image captured earlier in the commit, so two maintained columns changed in one commit
compose instead of clobbering each other). If P is present and live, it writes P's image
with the one field set to the new total — `tx.put(parent_table, table, new, Some(old))`,
`row_changed(.., Origin::Maintained)`. If P is absent or expired, it does nothing: an
expired parent is never `put`, so it is never resurrected into the stream, and nothing is
owed later, because the truth is not on the row.

- **Birth:** a parent's insert sets the field to the private total for its id — one
  `tx.get` on the private table, always made and always charged, whatever it finds — after
  the submitted-field refusal and the defaults and **before `validate_row`**, which would
  otherwise refuse the required column as missing (Quarry and native inserts alike). Zero
  when none. A reply inserted before its parent is already counted; a parent inserted
  first is born at zero and mirrored on the next contribution; a self-referential source
  contributes once because the row's own `put` precedes its `maintain`, as today.
- **Death, expiry, the sweep, re-creation:** nothing to do. A re-created parent is born
  with the right total.
- **No rule and no constraint** is consulted for the mirror write: the source write is
  judged by the source's rules, and no constraint can involve the column (§2).
- **One new, always-on reservation per source-write attempt, at the outermost boundary.**
  It is **not** `reserve_maintains`, whose early returns — a uniformly readable source,
  the system context, a maintain with no filter, computed key or expiry — skip exactly the
  Clique case (public, unfiltered likes) and would put the first round's finding back on
  the default app. For each maintained declaration the write can affect it reserves,
  before inspecting the private row or the parent, the schema-bounded worst case of **the
  private aggregate's work and the mirror's**: both the old and the new group; the private
  row created, changed in place or deleted (`0→1`, `n→m` and `1→0` differ in index work, so
  the private maintain's cost is *not* the same across hidden totals unless it is
  reserved); scratch; and two mirror attempts — lookups, row copies, every index entry of
  every index containing the column and `byId`, rows written, partition steps, heap. It
  has `target_attempt`'s lifetime — set once, restored on every exit — which `insert_mode`
  and the `insert … if absent` arm that does nothing gain, and an `upsert` reserves once,
  not once per arm. Exactly the reserved work is suppressed on the prepaid path
  (`maintain_prepaid`, `charge_maintain`); a separately declared `maintain` on the same
  source is not suppressed unless its work is inside the ceiling; and
  `partition::row_changed` is told the write's **origin**, charging `Origin::Maintained`
  steps there rather than by whether the table is a maintain target. So a present, absent,
  expired or differently valued parent, and any hidden total, costs the source writer the
  same on **every meter field**, at ample and at just-insufficient budgets. This is
  equality of reserved ceilings, not of SQLite work, and the card says so.
- **The parent table is always named as touched.** A source write that feeds a maintained
  column records the **parent table** in the commit's touched set whether or not a parent
  row was written, and the private table's name never enters commit metadata. `/changes`
  reports touched tables to every principal; without this a writer who cannot read the
  parent would learn from its own next poll whether the parent exists.
- **The named exception is overflow**, checked on the private total alone: a sum near the
  53-bit endpoint refuses with `AggregateOverflow` naming the **owning table and column** —
  never the private target, never a value. The paired tests assert it, and its text,
  separately.
- **Programs cannot write the column.** The refusal acts on the fields a caller
  **submits** — an insert image, a patch, either arm of an upsert, an `insert … if
  absent` that would do nothing, an explicit `0` — before defaults, merging or no-op
  resolution; a materialized zero or a field `merge_patch` retains is not a submission. It
  holds under the system context: jobs, native jobs and seeds are refused like any
  program. The binder refuses with the wording of today's maintain-target refusal, naming
  the column; the engine refuses for hand-serialized IR.
- **A write's result never carries a maintained field.** An insert's result today is the
  image prepared *before* the engine writes (`bind/program.rs`), and an insert rule need
  not grant read: returning the stored total would disclose it to a creator who cannot
  read the row, and returning the prepared image would fabricate a zero. So the result
  of `insert`, `insert … if absent`, `upsert` and `update` — Quarry and native — is a
  **table-branded result type: the row without its maintained columns, `id` kept**. It
  still works as a write key (`update (insert posts {..}) {..}`), a wildcard expands the
  reduced shape, the optional and unit outcomes of if-absent, update, upsert and the
  native APIs are unchanged, and asking a result for the maintained field is refused at
  `check` with the rewrite "read the row". The binder omits the column from the prepared
  insert image, the engine strips it where a write re-reads the row, and the generated
  native result types carry the same distinction. To see the count, read the row, under
  the read rule.
- **`Engine::load`** (the server's fixture import) ignores a supplied value, then rebuilds
  the private maintain and mirrors **with ordinary row events**, or refuses unless the
  store is not being served; it never uses activation's event-free mode (§3.11).

### 3.3 Why not keep the total only on the row

Revision 2 did, with a *limbo* table for ids that had no live parent. The second round
showed what that costs: an expired-but-unswept parent holds part of the total while limbo
holds the rest, so the overflow check has two halves, the sweep can be poisoned by an
addition that no longer fits, a redefinition has to decide which half it rewrites, and a
changed `expire at` can revive a row whose debt is stranded; birth and death move a value
and must be prepaid separately. One authoritative total removes all of it. The price is
one small private row per parent with a nonzero total, written beside the parent's row —
what all three Clique apps already pay for the `maintain likeCounts` they declare.

### 3.4 Deleting source rows

Deleting a source row lowers the private total and mirrors it, like any other change.

### 3.5 Stream and log — the cost to be honest about

The mirror is a `Put` of the **whole parent image** to each of the parent's partitions
(`partition::row_changed`), coalesced to one event per row per commit
(`partition::append`). Each contributing commit logs and streams one full image of the
parent per destination partition: a like on a 500-byte public post is about 500 bytes of
log and a row event for every holder. That is what the hand-kept `posts.score` costs
today, and more than an `online only` maintain, which streams nothing.

Rule of thumb for the card: *a count the row's readers want with the row is a column; a
counter that changes far more often than its row is read stays a `maintain … online
only`.* A note, `N_MAINTAINED_COLUMN_STREAM`, fires on the **parent** table's sync line,
not folded into `N_MAINTAIN_SYNCED`'s envelope. Coalescing a stream page to the latest
image per row is a separate, measured follow-up.

### 3.6 Rows a device never acquired

A device stores every `put` it is streamed and the stream applies no horizon
(`partition.rs` uses it for acquisition only), so under `sync public last 2000 by byTime` a
like on an old post makes every device acquire that post. Round 1's families disagreed
(filter at the device; accept and measure); round 2's both found accept-and-measure
defensible **with a threshold stated before the measurement**: the first build ships on a
horizoned public table only if, on the Clique scale fixture, a device's held rows of that
table grow by no more than 10% a day beyond its horizon; past that, a device-side filter
is designed and reviewed first. NOT-DOING's "exact horizon maintenance" stays refused
either way.

### 3.7 On a device: the first build does not derive the column

A device **never derives a maintained column and never accepts an application's
assignment to one**. Its schema is the public projection of §3.2, which contains no
private maintain at all, so `Runner::maintain` has nothing to run there (today it overlays
any synced target, which is why absence, not a skip flag, is the mechanism); the
projection's column metadata is what tells it the column is unwritable and reads 0 when
missing. It stores the column as it stores any
field of a server image: applying a stream or snapshot page, and **restoring its own
persisted rows** (`MemoryStore::load` and its SQLite counterpart are restoration, not
fixture import), keep the server's value verbatim.

A source write predicts exactly as it does today — its own rows — and the count changes
when the server's image of the parent arrives; nothing is lost against today, where the
hand-kept `score` is set from an `online only` maintain and never predicted. A parent a
device *inserts* is predicted without the field and reads the implicit 0 of §3.11 on a row
marked `pending`: a provisional value, stated as such on the card, replaced by the
server's image (which carries the private total, if one existed for that id).

The reason the column is not predicted is a sync-protocol defect the first review found
and execution confirmed
(`issues/20260917-snapback4-stream-page-serves-images-newer-than-its-watermark.md`):
"holding the row is knowing the base" is false while a stream page can serve an image
newer than its watermark. Predicting the column is a **later increment** with these
obligations: that ticket fixed; a prediction that skipped an unheld parent stays skipped on
every replay, or the source is required to arrive in the parent's commit; replay's
affected rows are recorded and returned, so watches over the parent are invalidated on
failure and withdrawal; an engine-only predicted write adds no `pending` marker and
preserves one already there; birth at zero only for an id minted in that mutation;
persistence reopen and interrupted catch-up are in its tests.

### 3.8 Rules, audience and disclosure

A maintained column is a dependency of no rule and of no delivery decision (§2), so a
mirror write never changes any row's audience.

What it discloses, stated once: to every reader of the parent row, the **count** of source
rows naming that parent (or their **sum**); with a predicate, how many satisfy it — a
predicate-dependent fact about rows the reader may not be able to read; with an index, the
parents' relative order by that value; to a source writer, the overflow bit. A missing
parent is absence, not a readable zero. Birth, death, the touched-table set and every
meter disclose nothing more (§3.2).

`check` prints this as a note wherever parent readers are **not proven** able to read the
contributing source rows — a different proof from `N_MAINTAIN_DELTA`'s, which is silent
when a source's write rules imply its read rule; private likes on public posts satisfy
that and must still be noted. When in doubt, the note prints.

### 3.9 No cascade in the first build

A maintained column cannot be the `of`, the predicate or the `by` of another aggregate,
and neither form can take a generated target — private or not — as its source. Reason:
writes under `Origin::Maintained` do not fan out to maintains (`engine/write.rs`,
`row_changed`), so either would go stale. The ruling's acyclic cascade is the ceiling, not
the first build. A self-referential *source* (`replyCount`) is not a cascade.

### 3.10 Expiring sources: refused in the first build

The source may not have `expire at`: the live total would change with no write, the
mirrored column would be stale until the sweep, and an index over it would order stale
values (LLP 3000.007 §20.9.3, §20.21). The refusal points at the `maintain` form, which
recomputes live contributions at read time. An expiring **parent** is fine (§3.2).

### 3.11 Adoption

- **Images without the field read 0 — and that is not a literal default.** The engine
  special-cases a required maintained column in `materialize_optional_fields`, **in
  `validate_row`** (activation's first walk and the store's assessment both validate old
  images, and would refuse the generation), in index builds and in `sql`'s projection,
  which today synthesizes literal defaults only. It is **not** stored
  as `ColumnDefault::Literal`: that would make `successor::keeps_literal_default_images`
  true and a device would keep its pre-generation rows reading 0. Authors cannot write
  `default` on it. `classify` gains a named `Additive` exception for "required maintained
  column added"; because the private maintain's target is not the parent,
  `classify`'s maintain-target bypass never applies to the application's table, and an
  ordinary narrowing of another column on it is still reported.
- **Rebuild = today's maintain rebuild, then a mirror pass.** The private maintain is
  rebuilt by `rebuild_maintain` as any maintain is — its delete-all-then-fold loop is
  correct here, because the target is the private table. The **mirror pass** then walks
  the parent table and `put`s, in place, every live parent whose stored field differs from
  the private total — *including nonzero to zero* — preserving every ordinary field and
  other maintained columns. It has no delete in it; the row adapter asserts none occurs.
  On an initial addition the pass writes only parents whose total is not zero. **Triggers
  are defined over the resolved interpretation, not the declaration's text.** The private
  maintain is rebuilt when the column is added or redefined (kind, source, predicate,
  `by`) or when the type, optionality or default of any **source** column it depends on
  changes. The mirror pass runs after any rebuild, and whenever the parent's liveness can
  change with no write: a changed `expire at` line, **or a change to the type, optionality
  or default of the column it names** — widening a defaulted `expiresAt` to optional makes
  a missing value read null, which never expires, so a parent the mirror had skipped as
  expired becomes live with nothing else having changed. Both happen before the generation
  publishes.
- **Removal** follows the ordinary destructive column projection, and **drops the private
  table**, so re-adding the declaration cannot recover stale totals.
- **Activation is a generation barrier, not a stream of rows.** The mirror pass under
  activation — and only there — emits **no partition row events**; the activation commit
  **always** names the parent table as touched, even when no parent row was rewritten
  (today's rebuild commit is skipped when nothing was written), so server-run watches
  re-run; the generation changes, and every device re-acquires by snapshot, because
  `keeps_literal_default_images` is false when maintains differ and the column has no
  authored default. Successful stream and snapshot replies carry the generation and the
  client adopts it before applying rows; `Device::apply` rejects a mismatched page.
  A maintain's own rebuild emits events today; the difference here is deliberate — a
  100,000-row `Put` of an application table is not a decodable generation signal.
- **A prerequisite outside this design:** a sync response that exceeds the HTTP ceiling is
  replaced by a bare `E_BOUND` body with no generation, and the client only halves its page
  (`issues/20260917-snapback4-oversized-sync-page-hides-generation.md`). Adding a column
  enlarges the *current* images a stream page re-materializes, so a page that fitted can
  stop fitting. The first build requires that ticket fixed — generation discovery must not
  depend on a row page being deliverable.
- The Postgres evaluation store has no activation API: no adoption parity is claimed.

### 3.12 Residency and classification

A read of the column is a read of its row: `held`, `horizon` or `server` by the parent's
sync line, with no new class. A source write keeps its prediction class.

| --- | --- |
| `posts.score: int default 0`, `update <- allow` on `posts` | `likeCount: count likes by postId`; no update rule for it |
| `update posts[postId] { score: likeCounts[postId] }` in `like` | nothing: the engine keeps it |
| `maintain likeCounts` + nested `likeCounts[.id]` in every post shape | the private maintain is generated; the count arrives with `*` |

## 5. Alternatives considered

- **The total only on the row, with limbo for absent parents** (revision 2). §3.3.
- **Fix maintain tables instead** (`maintain … over posts carrying at`). Keeps table-level
  writer separation; still needs parent-domain zeros, parent lifetime and audience,
  tie-break fields and a projection story, and the count does not arrive with the row. Put
  to the author beside ruling 30 and not chosen; both families, twice, would build the
  column form.
- **Computed columns as one family**: put to the author beside ruling 29 and not chosen.
- **`system update`, privileged helpers, triggers.** Closed by LLP 3000.007 §20.20.
- **Do nothing; ship the note** (ruling 31). Makes the footgun visible; does not give
  builders the count on the row.
- **Count at birth; or refuse contributions to a missing parent.** The first leaks hidden
  population work; the second breaks forward references, seeding order and a like written
  while its post is not held, and makes parent existence an outcome channel.

## 6. What changes where

- `snapback4-lang`: the column-line grammar; the binder (reference resolution, generating
  the private maintain, the resolved dependency walk, the refusals, write-result types
  without maintained fields, the two notes); `emit.rs` (private targets excluded); the
  language, maintains, rules, indexes and feeds cards; `guide::CODES`.
- `snapback4-core`: `Maintain` gains the private mark and its owning `(table, column)`;
  the same walk in schema validation; the mirror step after `apply_aggregate`; birth in
  the insert path; the per-attempt reservation and origin-keyed partition charging; the
  always-touched parent table and the exclusion of private names from commit metadata;
  the submitted-field refusal on every write arm and the stripped write result (Quarry and
  native); `load`; `successor.rs`, the store's assessment and activation (the special-
  cased 0, the named `Additive` exception, the mirror pass with its event-free activation
  mode and its unconditional commit); `sql`/`data` exclusion.
- `snapback4-device`: `Runner::maintain` skips private maintains and mirrors on a device;
  restoration and page application keep stored values; both stores read it as a column.
- `snapback4` verbs: `check --cost` and `why` for the column; `test --residency` rows.
- No new `Read` or `Write` field and no card word beyond the column form. (The sync
  ticket of §3.11 adds a field to one error body; it is that ticket's change.)

## 7. Measurements owed before a lane is briefed

Items 1, 2 and 5 are gates, each with its acceptance stated now.

1. Log and stream bytes per like — serialized HTTP bytes and log rows — for a 500-byte and
   a 4,000-byte parent, against the `online only` maintain and the hand-kept `score`;
   durable log growth over 100,000 likes. *Gate: no worse than the hand-kept `score` it
   replaces, within 10%.*
2. Rows a device gains per day under `sync public last 2000 by byTime` on the Clique scale
   fixture when likes fall on old posts. The workload is pinned before it is measured: the
   fixture's recorded like stream, unmodified; a device that acquires at the replay's 50%
   checkpoint; growth counted over the replay's final simulated day; the denominator is the
   rows of that table the device held at acquisition. *Gate: §3.6's 10%.*
3. Index churn: entry writes per change with one and with three indexes over the column.
4. The private row: storage and write cost per contribution beside today's declared
   `maintain likeCounts` (expected equal) and beside revision 2's limbo (expected one extra
   small row per live, nonzero parent).
5. Activation: elapsed time, peak memory and whether a **real device completes adoption
   over HTTP**, for 100,000 parents and 1,000,000 source rows, including a device that is
   behind by a large pre-activation page. *Gate: the device adopts; no response exceeds
   the ceiling because of this form.*

## 8. Acceptance (tests a lane must bring)

- **Oracle.** An independent model: inserts, predicate-flipping updates, reference-moving
  updates (old parent down, new parent up, one commit), deletes, rollback, sums, several
  maintained columns on one table, a self-referential source with same-commit
  parent-and-child in both orders, deletion and re-creation of a parent (born with the
  total), a parent that expires with contributions arriving before and after the sweep
  (never resurrected; re-created right), a changed parent `expire at` that revives a row;
  on the server and on both device stores as readers; after a rebuild; on the Postgres
  evaluation store for ordinary mutations.
- **Refusals.** Every write arm — insert, update, both upsert arms, a no-op `insert … if
  absent`, an explicit `0`, native and system writes, seeds, raw IR — and every dependency
  of §2's walk, including a probe's extra equality, a positional probe of an index
  containing the column, `old`/`next` terms, `after insert`, a **sync horizon** over such
  an index, a generated target as a source, and raw schemas that violate them. Reads and
  pages of an index over the column are admitted.
- **Paired observations** in §17's method, at ample and at just-insufficient budgets, for a
  source writer in four parent worlds — absent, present, present with another value,
  expired-unswept: **the HTTP body, the receipt, the retry, every meter field and the
  `/changes` touched tables are identical** (the parent table always named, the private
  table never). Stream and snapshot are identical **when the parent is outside the
  writer's partitions**; for a readable parent they differ by the parent's image, which is
  the feature. Likewise for a parent's creator against private totals of zero and of
  nonzero for that id, a creator who cannot read the row included. An `upsert`'s insert
  arm reserves once. Overflow is asserted separately as the declared exception.
- **Write results.** Full-row and scalar results of insert, `insert … if absent`, upsert
  and update, Quarry and native, never carry the column — typed so, and stripped — for
  creators with and without read permission.
- **Rebuild and mirror.** The mirror pass performs no delete (asserted at the row adapter,
  not by counting rows); initial addition leaves zero parents untouched and reading 0;
  redefinition rewrites nonzero to zero; an expired-unswept parent is not written and is
  right after its sweep and re-creation; removal drops the private table and a re-added
  declaration recounts from the source.
- **Activation.** No row events in the activation commit; the commit exists and names the
  parent table even when every total is zero; `classify` still reports an ordinary
  narrowing on the parent table and `maintain_for(parent)` is `None`; adding the column
  does not satisfy `keeps_literal_default_images`; a device on the old generation
  re-acquires and **never serves the implicit 0 from a pre-generation image**; a
  server-run watch over the parent re-runs.
- **Device.** Predicting a like writes no parent on either store; applying pages and cold
  offline restoration preserve the server's value; a predicted parent insert shows 0 on a
  `pending` row and converges; watched results, not only stored rows, are asserted.
- **Index and cursor.** Paging an index over the column while counts move asserts the
  maintains card's moving-key contract explicitly.
- **Notes.** Private source with a public parent whose write rules imply source
  readability still prints the disclosure note; filtered sums and indexed order are named;
  neither note fires on the existing cards, recipes and templates (a census, asserted).
- **Visibility.** The private table appears in none of `api.ts`, `sql`, `data`, `check`
  listings, `why`, commit metadata or any schema enumeration a principal can reach.
- **Round 3's cases.** A public, unfiltered source (the Clique shape) and a system-context
  write in the paired observations, since those are what `reserve_maintains` skips;
  `0→1`, `1→0` and `n→m` hidden totals under each ceiling; the prepaid state restored after
  `insert_mode` and after a no-op `insert … if absent`; the last unlike on a live post
  stores 0; two maintained columns changed in one commit both match the oracle; a failure
  injected after the private write and between two mirrors rolls everything back; a
  defaulted `expiresAt` widened to optional, and a defaulted source reference widened to
  optional, each leave column and oracle equal; null references, a null-to-parent move,
  and two large sums with null references that must not overflow anything; a reference
  column named `value`; a raw schema whose rule probes the private target, raw IR that
  reads it, and a native job that names it — all refused, each naming the owning column;
  the device's schema payload contains no private table or maintain and still makes the
  column unwritable and zero-when-missing; `/changes`' saturated fallback lists no private
  name; `sql` shows 0 for a parent without the field; an insert's result works as a write
  key and refuses `{ likeCount }`; watched results compared after an interrupted catch-up
  and a reopen.
- **Published examples.** Wave 12's assertion that no published document ships a ranking a
  principal can write stays green, beside executable attempts to write the column and to
  move it through the source outside the source's authority.

## 9. What three rounds settled, and what stays open

Settled: build this form, not `maintain … over posts` (both families, every round); a
rule-free, delivery-free column for the first build; no counting at birth and no refusing
contributions; one authoritative total, mirrored (revision 3, from GPT's round-2
alternative; both families in round 3: the right mechanism, limbo's findings dissolved);
write results without maintained fields; the event-free activation and the special 0; the
split of the two protocol prerequisites; no device derivation in the first build;
accept-and-measure for §3.6 with a pinned workload and a threshold. The
first extension afterwards is parents addressed by a total unique key
(`profiles.followerCount: count follows by followedId`), before any cascade.

Open: two prerequisites in the sync protocol (the stream-image ticket for the later
prediction increment; the oversized-page ticket for the first build); §3.6's measured bet.
