## Summary

The three sketches in [LLP 0329.000](./0329.000-three-family-design-sketches.research.md)
agree unanimously on "admitted implies every capability — refuse, do not degrade."
That position has an unstated precondition, and
[LLP 0120](./0120-relational-composition-and-aggregation.research.md) already
measured the evidence against it.

**The precondition:** refusal is only viable if the admitted language can express
the query shapes real applications need. If it cannot, "refuse" means "refuse to let
anyone build a real app," and an opaque escape hatch regrows under a new name —
which is what happened the first time.

This document records that constraint, the causal chain it establishes, and a fourth
architecture none of the three sketches considered. It reorders LLP 0329's open
questions; it proposes no design.

## Findings

### F1 — composition is where every recent comparison was lost, for one reason

LLP 0120 §Summary records that relational composition and aggregation is "the one
authoring area where every recent comparison — the seven-backend Linear bakeoff
(Diary 0029) and the 2026-07-30 seven-app rerun (Diary 0039) — scored Convex ahead
for the same structural reason."

The stable Snapback relational surface is a deliberately closed two-source
unique-join (LLP 0080). The better-fitting bounded-children and
write-with-activity profiles are experimental and publication-gated
(LLP 0110/0113). LLP 0120 keeps three distinct exclusion mechanisms separate:
grouped counts and multi-table derivation are enumerated Non-goals of both
relational documents; multi-child fan-out is an LLP 0110 Non-goal but LLP 0080's
*deferred* open question 1; sequence allocation is an LLP 0110 §2.1 admission
refusal and the subject of its open question 4.

### F2 — the causal chain the sketches did not have

LLP 0120: "the shapes that actually dominate the rerun apps all fall outside the
generated surface," so those apps "stay on imperative inline handlers — fixed
fan-out (Relay), N+1 (Split), and unbounded-scan (Campfire) shapes."

This changes the standing of the capability bifurcation described in
[LLP 0329](./0329-agent-native-rebuild-diagnosis.research.md). It is not a design
smell surviving on inertia. **Authors reach for the opaque handler because the
declarative surface cannot express what their application needs.** The bifurcation
is load-bearing in practice.

LLP 0120 is careful about what the fallback proves: those handler-shaped apps
"passed their retained acceptance checks and are snapshot-consistent but carry none
of the bounded-work or declared-reach evidence the generated profiles exist to
provide." The escape hatch is not broken. It is untyped with respect to the
properties the platform sells.

> **Correction, 2026-08-28 — F2 as written is too strong.**
> [LLP 0329.005](./0329.005-authoring-shape-census.research.md) measured the whole
> demo corpus (105 backend files) rather than LLP 0120's felt-loss set. Across that
> corpus, **45% of inline JS read handlers use no capability the declarative surface
> lacks** — several are a single indexed `take` with no JavaScript logic at all — and
> of the 13 that genuinely need composition, **12 are the single "k independent
> bounded reads" shape** and one is nested N+1. LLP 0120's felt losses are real and
> its Finding 1 stands, but the inference *"therefore the opaque handler is
> load-bearing"* does not generalize from them to the corpus. The honest statement is
> that the handler is **load-bearing for a minority of read shapes and habitual for
> the rest**, which makes the escape substantially a discoverability and defaulting
> problem rather than an expressiveness one. LLP 0329.005 also relocates the
> question: the escape rate is **35% on reads and 74% on writes**, so the read
> language this document is about is not where the corpus actually leaves the paved
> path.

### F3 — a fourth architecture, absent from all three sketches

LLP 0120 §What Convex does: Convex's model is "a query is just code over the
database" — an ordinary TypeScript function inside one serializable transaction,
performing any sequence of point reads, index scans, and in-memory joins, with the
result type inferred. Two properties follow (LLP 0120 marks this paragraph as
general background, not diary-measured): the runtime **records the read set of each
execution after the fact**, which powers both optimistic-concurrency validation and
reactive re-execution; and because the function runs at one snapshot, any composed
object graph is automatically snapshot-consistent.

So reactivity does not require a statically analyzable language. It can be obtained
by *dynamic* read-set recording plus re-execution. All three sketches assumed static
derivation was the only route to reactivity, and each therefore accepted a
restricted language as the price.

The trilemma this exposes:

| Approach | Expressive | Reactive | Genuine offline |
|---|---|---|---|
| Convex — dynamic read-set recording | yes | yes | no — an arbitrary server function cannot be re-executed on a client that lacks the data |
| LLP 0329.000 sketches — static derivation | limited | yes | yes |
| Snapback as built — both forms side by side | yes | partly | partly, and invisibly |

The "genuine offline: no" cell for Convex is **[inferred]** from the architecture —
local re-execution of an arbitrary server function requires data the client does not
have — and is not a measured claim about any Convex release.

Snapback's row is the worst of the three, which is LLP 0329's thesis intact. But the
sketches purchase offline by paying in expressiveness, and F1 measures that price as
losing every recent head-to-head on authoring.

## Consequence for the open questions

LLP 0329 listed planner affordability of row rules first. This document moves the
expressiveness question ahead of it, because it determines whether the unanimous
design is implementable at all rather than merely whether it is fast.

The question, stated so it can be answered: **can an analyzable read language
express bounded fan-out, grouped counts, multi-table derivation, and bounded graph
traversal — the shapes LLP 0120 found dominating real applications — while
preserving static read-set derivation, retention eligibility, and local
re-execution?**

If yes, the LLP 0329.000 consensus is buildable and LLP 0155 move 1 is the route.
If no, then either offline is bought at a price the benchmark has already shown is
lost, or the design must adopt a hybrid the three sketches did not consider — for
instance dynamic read-set recording for server-side reactivity with a separately
admitted, narrower class for locally re-executable queries. That hybrid reintroduces
two capability classes and would need to answer LLP 0329 F1 to be admissible at all.

## Confidence

High that F1 and F2 report LLP 0120 and its cited diaries accurately. High that the
precondition in the Summary follows from them. Medium-high on F3's characterization
of Convex, which LLP 0120 itself labels general background rather than measured.
The trilemma table is a framing device, not a measurement; the Convex offline cell
is explicitly inferred.

This document was written after the three sketches and was not available to them.
It should not be read as a refutation of any of them, only as a constraint each
would have had to address.

A subsequent design analysis of that constraint —
[LLP 0329.012](./0329.012-bound-carrying-algebra-as-the-only-language.research.md)
— argues the restricted language *can* be the only language if the restriction
is on computational class rather than operator poverty, and proposes a
bound-carrying algebra as the architecture that satisfies both sides. That
analysis is research; it does not ratify a rebuild. A second analysis,
[LLP 0329.013](./0329.013-one-read-language-proposals.research.md), written
independently in the same hour, reaches the same answer by a different route
— only local prediction forces restriction; static derivation is not required
for reactivity; the Supabase lane is a measured existence proof for SQL-shaped
reads — and records where the two disagree (static ceilings versus
index-served rules, who decides aggregate maintenance, the client evaluator,
recursion and time). A three-family panel then argued the question for three
rounds ([LLP 0329.014](./0329.014-bounded-data-programs-panel-synthesis.research.md))
and converged on bounded data programs, with the trace as the closure.

## Open questions

1. What is the smallest admitted node set that covers the LLP 0120 shape census?
   LLP 0120 lays out seven paths and deliberately makes no call, deferring to
   LLP 0080's open question 7 under LLP 0115 CV-8. That decision is still open and
   is now upstream of the whole rebuild question.
2. Is dynamic read-set recording compatible with Snapback's authority model, or does
   it require the trusted-execution posture LLP 0009 refuses for hosted code?
3. Would a two-class design (reactive-everywhere, retainable-on-a-subset) be
   materially different from the current defect, or is it the same matrix with
   better-chosen boundaries and honest naming?
