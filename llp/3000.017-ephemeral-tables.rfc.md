## Summary

Snapback 4 has no ephemeral state. `NOT-DOING.md` says so: "no typing
indicators, last-seen storage, multi-server presence or a presence stream."
Builders therefore write typing indicators as durable tables with
`expire at .expiresAt`. Every keystroke becomes a durable mutation: minted
id, device outbox, at-most-once record, partition log entry, fsync, replay.
The outbox sends its oldest write first and never skips a blocked head, so a
burst of keystrokes arrives late and the indicator outlives its window.
Queries do not tick, so peers also need a render-deadline filter. This is the
most repeated Snapback 4 failure in the Clique record from 0.2.25 to 0.4.2
(§1).

This RFC adds one table modifier:

```quarry
table typing:
  roomId: rooms
  principal: principal
  unique byRoomPrincipal: roomId, principal
  cap 50 by roomId
  read <- exists members[.roomId, viewer]
  insert <- .principal = viewer and exists members[.roomId, viewer]
  update <- .principal = viewer
  delete <- .principal = viewer
  ephemeral 4s
```

An **ephemeral table** keeps its rows in server memory only. They never reach
the store file, the partition log, `_commits`, the at-most-once record,
backups, `sql`, `data`, a device replica or an outbox. Each insert, upsert
or update sets the row's deadline to the server's `now` plus the declared
life. A row past its deadline is absent to every reader, before any rule,
as `expire at` rows are today. Everything else is an ordinary table: typed
columns, unique keys, caps, rules, and queries that join it to durable
tables.

A mutation that writes an ephemeral table writes only ephemeral tables. The
compiler classifies it as an **ephemeral mutation**. It runs on the server
and only online. It is never predicted, queued, recorded or replayed, and it
does not take the store's writer lock. On the client, calls coalesce: at most
one request per operation and argument set is in flight, a newer call
replaces a waiting one, and a call made offline resolves at once with
`E_OFFLINE` instead of waiting. Its commit bumps an in-memory **ephemeral
epoch**, which wakes the `/changes` long polls of clients watching a query
that reads that table. Those clients re-run the query; a device never holds
ephemeral rows, so it falls back to the server as it already does for
server-only reads. Each answer's `nextExpiry` already makes clients re-fetch
when a row's deadline passes, so an indicator disappears on time with no
application timer.

This enacts LLP 3000.009 §12's standing line ("Presence beyond polls →
ephemeral channels, if the brief charges for them"). The brief charges for
them: rubric B3 scores 60 for "a durable workaround (tables + expiry jobs)"
and 90 for "purpose-built primitives". The author asked on 2026-09-26 for
this state to be added back. Snapback 1 and Snapback 2 both had it, and
Snapback 2's typing indicator appeared 23–30 ms after the keystroke.

The design choice is **a table, not a channel**. Snapback 2's `channel` was
a separate object with its own scope arguments, publish/subscribe rules, hook
and wire. Here the author writes the table they already write and adds one
line. Rules, joins, generated row types, `useQuery` and `useMutation` all
carry over. §7 weighs the channel port.

## 2. The authoring surface

### 2.1 Declaration

`ephemeral <life>` is a line in a table body, beside `expire at`, `sync` and
`online only`. `<life>` uses the duration units that schedules already
accept (`500ms`, `4s`, `1m`). It is required and must be between 1 second
and 60 seconds inclusive. Outside that range the compiler refuses with
`E_QUARRY_EPHEMERAL`, and the message states the range.

The table keeps the ordinary body grammar: columns, `unique`, `by`, `cap`,
`immutable`, `read`/`insert`/`update`/`delete` rules and `after insert`. The
implicit `id` column and `byId` stay. `default now` columns are allowed.
Some clauses cannot appear in an ephemeral table, because each would make
durable state depend on memory. The compiler refuses them with
`E_QUARRY_EPHEMERAL`, and the message names the clause and the fix:

| Refused on an ephemeral table | Why | Fix the message gives |
| --- | --- | --- |
| `sync …`, `online only`, `sync public`, a horizon | The rows never reach a device | Delete the line; devices read ephemeral rows from the server |
| `expire at .col` | Its life is the declaration | Delete it; `ephemeral <life>` sets every row's deadline |
| `sequence by`, `through`, `words(..)` indexes, asset columns (`image`, `video`), `once` | Durable custody | Keep that data in a durable table |
| Being the source of a `maintain`, a Following view or a feed | Durable derived data | Count or rank durable rows |

Durable declarations may not depend on ephemeral rows. The compiler refuses
each of these with `E_QUARRY_EPHEMERAL`:

- a durable table's rule or `after insert` that probes an ephemeral table
  (`exists typing[..]`);
- a durable table column whose type is an ephemeral table (a reference);
- `sync to typing[..]`;
- a durable mutation, job or schedule that reads an ephemeral table.

Queries may read both kinds. This follows LLP 3000.009 §7: "Ephemeral state
never decides a durable invariant."

### 2.2 Ephemeral mutations

The binder classifies each mutation by the tables it writes:

- **Durable:** writes no ephemeral table. Unchanged.
- **Ephemeral:** writes only ephemeral tables. It may read durable tables,
  for example with `require exists members[roomId, viewer] else NOT_MEMBER`,
  and it may use `insert`, `upsert`, `update`, `delete`, `if absent`,
  `require`, `let` and `return`, as any mutation may. It may not `emit`.
  It may not call a native job.
- **Mixed:** writes both kinds. Refused with `E_QUARRY_EPHEMERAL`: "split
  this into two mutations; call the ephemeral one from the client after the
  durable one".

Jobs, schedules and actions cannot write ephemeral tables in this revision;
they are refused with the same code. A job-maintained scoreboard of who is
online stays out of scope.

The classification appears in three places:

- `check`'s program listing, as `ephemeral`;
- `check --residency`, where each ephemeral table is listed as
  `ephemeral <life>: server memory, never on a device`;
- the generated operation, as `ephemeral: true` (§2.4).

An ephemeral mutation's semantics:

- **Life.** Each insert or upsert-insert of an ephemeral row stamps the
  deadline `now + life`. Each update, and each upsert that patches an
  existing row, stamps it again, even with an empty patch. That renewal is
  what a heartbeat means. A delete removes the row.
- **Rules.** Read, insert, update and delete rules are checked exactly as
  for durable tables. Durable tables are read at the store's head at
  execution. Ephemeral tables are read at the memory store's state under its
  lock.
- **Failure.** The mutation applies completely or not at all. A refusal
  leaves the memory store exactly as it was.
- **Result.** The result is the program's return value. There is no `seq`,
  no replay and no id-based idempotence. The client-minted `id` is only a
  correlation token.
- **Unique keys, caps and constraints** apply within the memory store. An
  expired row does not collide, as with `expire at`.

### 2.3 Queries over ephemeral tables

A query reads an ephemeral table like any other:

```quarry
query typingIn(roomId: rooms):
  return typing where .roomId = roomId and .principal != viewer by .principal { principal }
```

The query runs on the server. On a device, a read that touches an ephemeral
table is `unknown`. The client's existing server fallback answers it, in both
tiers and in `held` and ordinary queries alike. A `held` query that reads an
ephemeral table is refused at `check` with `E_QUARRY_EPHEMERAL`, because
held means answered by the device. Answers carry `nextExpiry`, the earliest
deadline among the ephemeral rows the answer read. That is the mechanism
already used for `expire at` rows.

The guide's `ephemeral` card includes a compiled query for the chats list
that answers "who is typing in each of my conversations" in one read. The
lane chooses the spelling the language accepts (a nested read per
membership, or a scan admitted by the read rule) and the suite compiles and
runs it.

### 2.4 The client

Generated code marks the operation:

```ts
export const setTyping: Ephemeral<{ roomId: Id<"rooms"> }, null> =
  { kind: "mutation", name: "setTyping", runs: "server", predicts: "never", ephemeral: true };
```

`contract.ts` gains `Ephemeral<A, R> = Mutation<A, R> & { readonly ephemeral: true }`
and a result type with no pending state and no sequence:

```ts
export type Signal<R = unknown> =
  | { readonly state: "sent"; readonly id: string; readonly result: R }
  | { readonly state: "failed"; readonly id: string; readonly why: Refusal };
```

`client.mutate(api.setTyping, args)` and `useMutation(api.setTyping)` return
`Promise<Signal<R>>` for an ephemeral operation. They still return
`Promise<Write<R>>` for a durable one. That is one overload, so application
code does not change. `usePendingWrite` refuses ephemeral operations at the
type level.

Calls travel the ordinary `POST /m/<name>` route, but they bypass everything
durable:

- the device outbox and its admission journal;
- the online tier's pending queue;
- `app-online.ts`'s durable journal;
- the browser admission path in `app-client.ts`;
- prediction.

The client applies three rules per client instance.

1. **Coalescing.**
   - The key is the operation name plus the canonical JSON of its arguments.
   - With no request in flight for the key, the call is sent at once.
   - With one in flight, the call becomes the key's single *waiting* call,
     replacing any earlier waiting call. The replaced call's promise
     resolves with whatever the call that replaced it resolves with.
   - When the in-flight request settles, the waiting call is sent.
2. **Renewal window.**
   - A call is not sent if all of these hold:
     - it has the same key as the last *successfully sent* call;
     - that call was sent less than a quarter of the shortest life among
       the tables the operation writes ago;
     - no other ephemeral operation has been sent by this client since.
   - Such a call resolves at once with the previous result.
   - The row that call wrote is still alive for at least three quarters of
     its life.
   - A keystroke-per-call typing indicator therefore sends about once per
     `life / 4`, and its row expires between `0.75 × life` and `life` after
     the last keystroke.
   - The window can only hide a call that would have rewritten the same
     row. Any intervening ephemeral call closes it; `stopTyping` is one.
3. **Offline.**
   - While the client's link is not `online`, a call resolves at once with
     `{ state: "failed", why: E_OFFLINE }`. It is never queued or retried.
   - `E_OFFLINE`'s card text gains that sentence: an ephemeral write is
     dropped, not held.

Watches need no new API. A watched query that the server answered, and that
read an ephemeral table, is re-run when a `/changes` answer names that table
(§3.3). It is also re-run at its `nextExpiry`. In the local-first tier this
re-run never triggers a `/sync`: ephemeral changes are not commits.

The recipes the cards will teach:

```ts
const setTyping = useMutation(api.setTyping);
const stopTyping = useMutation(api.stopTyping);
<Composer onChangeText={text => text ? setTyping({ roomId }) : stopTyping({ roomId })}
          onSend={() => stopTyping({ roomId })} />
const typing = useQuery(api.typingIn, { roomId });
<TypingIndicator visible={(typing.data?.length ?? 0) > 0} />
```

For presence in a scope ("who has this chat open"), declare
`table viewing … ephemeral 30s`. The card's heartbeat helper upserts the row
on mount and every 10 s, and deletes it on unmount.

## 3. Semantics

### 3.1 Time

- Deadlines use the server clock (`Shared::now`). That is the development
  clock under `dev`, so `dev clock advance` expires ephemeral rows as it
  expires `expire at` rows.
- A row is absent at `now >= deadline`, through the same `expired` check the
  runner already applies to expiring tables. The engine gives ephemeral
  tables a hidden `$deadline` column and an `$expiry` index, like
  `through`'s hidden deadline (`schema/through.rs`).
- Answers never expose `$deadline`. `recorded.rs`'s public image strips
  engine fields, and generated row types omit them.

### 3.2 Authorization and revocation

- Ephemeral rows are read under their table's read rule, like any row.
- Rules are evaluated at read time, and ephemeral rows are never cached on a
  device. So a principal who loses membership sees nothing on their next
  read of that room.
- A durable commit to a table a watched query probes invalidates that
  query, as today.
- A departed member's own row can outlive the departure by at most its life.

### 3.3 Change notification

- The memory store keeps an **epoch**, a `u64` that each ephemeral mutation
  commit increments.
- It also keeps an **incarnation**: a random id reset by restart, adoption
  and generation change.
- A bounded ring records `(epoch, tables written)`.
- Deadline expiry does not bump the epoch, because clients already re-fetch
  at `nextExpiry`. Sweeping expired rows only reclaims memory.

`GET /changes` takes three optional parameters:
- `eph=<epoch>`;
- `ephi=<incarnation>`;
- `ephTables=<comma-separated ephemeral tables the client's server-answered
  watches read>`.

A commit or ephemeral mutation wakes the poll. It answers, as today, when:
- the store's sequence moved past `since`;
- the store identity changed;
- a table in `ephTables` was written after `eph`;
- the incarnation differs from `ephi`;
- or the wait expired.

A wake caused only by an ephemeral write to a table outside `ephTables`
keeps waiting; it neither answers nor restarts the heartbeat. If the ring no
longer covers `eph`, the answer names every table in `ephTables`.

The answer gains `"ephemeral": { "epoch": n, "incarnation": "…", "tables": [...] }`.
A poll with no `eph` parameters behaves exactly as before, and its answer
omits the field.

A query answer that read an ephemeral table carries
`"ephemeral": { "epoch": n, "incarnation": "…" }`. The client discards an
answer older than the epoch it has already observed for that watch. This
mirrors `minimumReadSeq` for durable answers.

### 3.4 Restart, adoption and generation change

Ephemeral rows do not survive any of these:
- a server restart;
- schema adoption under `dev`;
- a generation change;
- a store replacement.

Each clears the memory store and changes the incarnation, so every client
watching an ephemeral table re-runs its queries.

Day-two classification (`successor.rs`):
- making a durable table ephemeral is **Destructive**, because its rows are
  deleted;
- making an ephemeral table durable is **Additive** (a new, empty table);
- adding, removing or changing an ephemeral table is **Additive**.

When a durable table becomes ephemeral, activation deletes its stored rows
and index entries (`store/activation.rs`), so they cannot return if it later
becomes durable again.

### 3.5 Bounds

| Bound | Value | Refusal |
| --- | --- | --- |
| Life | 1 s – 60 s | `E_QUARRY_EPHEMERAL` at `check`; generation admission re-checks |
| Rows in memory, all tables | 100,000 | `E_EPHEMERAL_FULL`, retryable, with no row detail |
| Bytes in memory, all tables (row images + index keys) | 64 MiB | `E_EPHEMERAL_FULL` |
| Ephemeral mutations per session | 20 per second sustained, burst 40 | `E_RATE_LIMIT` (the existing code; its card text gains ephemeral writes), retryable |
| Rows per group | the table's `cap … by …` | the existing cap refusal |
| Work per mutation and per query | the existing meter | unchanged |

The client's coalescing and renewal window keep an ordinary typing indicator
near one request per second per typist, far below the rate bound. Memory
refusals are values: they never degrade to a durable write or a silent drop.
The card recommends a `cap` on every ephemeral table that is grouped by a
room.

### 3.6 What does not change

- A schema with no ephemeral table serializes byte-identically. Its wire,
  its device and the published-0.2.33 capability fences are unchanged.
- A new capability name, `ephemeral`, makes an older device refuse a schema
  that has one, instead of queuing its writes.
- `connected[p]` keeps its meaning and its grace.
- Durable mutations, their prediction, the outbox, replay and the partition
  log are unchanged.
- Presence-guarded effects are unchanged.

### 4.3 Engine

A new `engine/ephemeral.rs`, gated on the `sqlite` feature like the server
engine, adds three things.

- **`Hub`** is shared by `Arc` between the serving engine and its reader
  engines. `Engine::reader` hands the same `Arc` to each reader. It holds:
  - `rows: Mutex<MemoryRows>`, the existing in-memory `Rows`
    implementation (`rows.rs:282-425`) with indexes, prefix scans, heads
    and counts;
  - the byte and row counters of §3.5;
  - `epoch`, `incarnation` and the `(epoch, tables)` ring;
  - `sweep(now)`, which reclaims memory;
  - `clear()`, which also changes the incarnation.
- **`Layered<'a> { durable: &dyn Rows, eph: &MemoryRows, journal }`**
  implements `Rows` by routing on the table name. Row gets, lookups, scans,
  heads, counts, puts and deletes of an ephemeral table go to `eph`, and
  every mutation of `eph` is journaled. Everything else goes to `durable`:
  - durable tables;
  - sequences;
  - `effect_once`;
  - assets;
  - prefetch.
- **Queries.** Every query runner, on the serving engine and on readers,
  runs over a `Layered` whenever the schema has an ephemeral table. Queries
  never write.

`Engine::mutate` checks the operation's `ephemeral` fact right after its
kind checks, at around line 963 of `engine/mod.rs` (946-1058). It then
re-checks at runtime with `ir::write_tables`, and branches to
`mutate_ephemeral`, which:

1. opens a **read** transaction on the durable store; a reader engine can
   do this, so the serving engine's writer lock is not needed;
2. locks the hub and runs the program over `Layered`, stamping each
   ephemeral write's `$deadline` in `write.rs`: at insert after defaults
   (58-62, before validation at 127) and at update beside
   `recompute_deadline` (281);
3. on refusal, undoes the journal in reverse; on success, checks §3.5's
   capacity, bumps the epoch and records the written tables;
4. writes nothing to `_commits`, `_log`, `_outbox` or `_ops`.

It returns the result, the epoch and the written tables.

The sweeps:
- `sweep_expired_for` (`engine/mod.rs:780-820`) skips ephemeral tables;
- the hub's `sweep` runs from the maintenance loop.

`seed_at`, `load` and `/seed` refuse ephemeral tables. `snapback4 run` and
`snapback4 test` use the in-process hub: rows written inside one process are
visible to later calls in that process. That lets `test` exercise the
typing recipe.

The Postgres store's `supported()` (`postgres/mod.rs:396-421`) refuses a
schema with an ephemeral table until increment C3.

### 4.4 Server (`crates/snapback4`)

- `serve.rs` `/q/` and `/m/` (930-1087):
  - before the replay lookup (947), an ephemeral operation takes a pooled
    reader (as `/q/` does at 995-1015) and calls `mutate_ephemeral`;
  - it does not touch `seq`, and notifies `shared.committed`;
  - it replies `{ state: "sent", ephemeral: true, id, result, ephemeralEpoch }`;
  - the per-session token bucket of §3.5 is checked first.
- Query answers that read an ephemeral table carry the `ephemeral` field of
  §3.3.
- `serve_changes.rs` (29-55): §3.3's parameters, wake filtering and answer
  field. The loop records the hub epoch on entry. A wake with an unchanged
  `seq` and no relevant ephemeral change keeps waiting.
- `serve_maintenance.rs` (116-137): the hub sweep on every pass.
- `serve_adoption.rs` (157-190): adoption clears the hub.
- `verbs.rs`: `data` and `sql` skip ephemeral tables and say why.

### 4.5 Device (`crates/snapback4-device`)

`admit_with_replay` (`device.rs:952`) refuses an ephemeral operation with
`E_QUARRY_EPHEMERAL`, as a guard. The client never sends one there.

Reads of an ephemeral table are already `unknown`, because the table has no
`sync` (`require_acquired`, `device.rs:320-333`). The lane confirms that the
device's wasm grows by less than the ratchet's headroom
(`metrics/wasm-budget.json`: 578,207 B against 577,207 B measured). If it
cannot, it raises the budget in the same commit and records the reason.

## 5. How we will know

- **Mechanism, before publication:** §4.7's end-to-end test passes. First
  sight is at most 500 ms after the first call; disappearance is at most
  life + 500 ms. The durable-typing control is recorded beside it.
- **Benchmark, after publication:** in the calibration run on the new pin,
  `m3-a06` and `m3-a07` pass. The builder uses `ephemeral`, found through
  the guide, and no typing correction loop in the run log attributes
  lateness to the backend.
- **Rubric:** B3's scorer note names a purpose-built ephemeral primitive.
  N=1 cannot show a score change; the calibration series is fitted, not
  compared pairwise.
- **Failure:** if the builder does not find the card, or writes a durable
  `expire at` table anyway, discoverability failed, not the mechanism. The
  next revision then goes to the cards and diagnostics. A candidate: a
  `check` note on a durable table named `typing`, `presence` or `viewing`
  that has `expire at` and a sub-minute default life.

## 6. Non-goals and non-claims

The revised `NOT-DOING.md` line will read: "No multi-server presence, no
presence history or last-seen storage, no broadcast event stream, no
connection-bound rows."

- **No connection-bound rows (`while connected`).**
  - The online tier polls only while it watches something.
  - `connected[p]` keeps a 35 s grace.
  - A writer's liveness is therefore not a precise signal today, and a
    heartbeat under a 30 s life is simpler and honest.
- **No delivered receipts.** The brief's `delivered` (fetched by the
  recipient's client) is a durable fact. A platform delivered-receipt fact
  is a separate candidate, still open in the 0.4.1 comparison record.
- **No key-range invalidation.** Invalidation stays table-granular. A typing
  write re-runs every watched query that read `typing`, in any room. The
  renewal window keeps this near one per second per typist. LLP 3000.009
  §7.1's narrower invalidation is the fix and is not in scope.
- **No multi-process hub.** One `serve` process owns the memory. The hub is
  a trait boundary so a Postgres host can later use `UNLOGGED` tables and
  `LISTEN`/`NOTIFY`. Postgres refuses ephemeral schemas until then.
- **No device-side ephemeral state or prediction.** A device never shows an
  ephemeral row it did not read from the server.
- **No claim of scale.** Rows are bounded at 100,000 and 64 MiB per
  process. Invalidation cost is linear in watchers per table.

## 7. Alternatives considered

- **Port Snapback 2's `channel`.**
  - A channel is a separate declaration: scope arguments, a `value` record,
    `publish`/`subscribe` rules and `ttl`. It has its own hook
    (`useChannel`), connection-owned leases, version fencing and a
    snapshot stream.
  - It is proven, and its engine surface is smaller, because it never
    touches the runner.
  - But it is a second model beside tables. It cannot join a profile, so
    values duplicate names. Its rules are a second grammar over scope
    arguments. It needs its own held connection per client, and this server
    admits only 32 held polls (`serve.rs:370-372`). It also teaches a hook
    and object that agents have looked for under the wrong name before.
  - The table form reuses every concept an author already has, and the
    engine already runs over a pluggable row store with an in-memory
    implementation. Rejected for authoring cost.
- **Keep durable `expire at` and make its writes skip the outbox.**
  - The writes would still be logged, fsynced, replayed and synced to
    devices. Every keystroke would still invalidate every durable watcher,
    and devices would still hold rows that expire.
  - It fixes F1 and none of F2–F4. Rejected.
- **Store ephemeral rows in the SQLite file, in tables cleared at startup.**
  - SQLite has no unlogged tables, so every keystroke would pay an fsync
    and the writer lock.
  - The rows would leak into backups, `sql` and activation walks.
  - An attached shared-cache memory database hits `SQLITE_LOCKED` outside
    the busy timeout, and every reader would need to attach it.
  - Rejected for the in-process `MemoryRows` store.
- **Connection-bound rows now.** Deferred (§6).
