## Summary

Snapback 4 has no ephemeral state. `NOT-DOING.md` says so: "no typing
indicators, last-seen storage, multi-server presence or a presence stream."
Builders therefore write typing indicators as durable tables with
`expire at .expiresAt`. Every keystroke becomes a durable mutation: minted
id, device outbox, at-most-once record, partition log entry, fsync, replay.
The outbox sends its oldest write first and never skips a blocked head, so a
burst of keystrokes arrives late and the indicator outlives its window.
Queries do not tick, so peers also need a render-deadline filter. This is the
most repeated Snapback 4 failure in the Clique record from 0.2.25 to 0.4.2
(§1).

This RFC adds one table modifier:

```quarry
table typing:
  roomId: rooms
  principal: principal
  unique byRoomPrincipal: roomId, principal
  cap 50 by roomId
  read <- exists members[.roomId, viewer]
  insert <- .principal = viewer and exists members[.roomId, viewer]
  update <- .principal = viewer and exists members[.roomId, viewer]
  delete <- .principal = viewer
  ephemeral 4s
```

An **ephemeral table** keeps its rows in server memory only. They never reach
the store file, the partition log, `_commits`, the at-most-once record,
backups, `sql`, `data`, a device replica or an outbox. Each insert, upsert
or update sets the row's deadline to the server's `now` plus the declared
life. A row past its deadline is absent to every reader, before any rule,
as `expire at` rows are today. Everything else is an ordinary table: typed
columns, unique keys, caps, rules, and queries that join it to durable
tables.

A mutation that writes an ephemeral table writes only ephemeral tables. The
compiler classifies it as an **ephemeral mutation**. It runs on the server
and only online. It is never predicted, queued, recorded or replayed, and it
never opens a SQLite write transaction. On the client, calls go through one ordered
lane per client. A renewal such as `setTyping` coalesces with an identical
waiting call and is sent about once per quarter of the table's life, and a
call made offline resolves at once with `E_OFFLINE` instead of waiting. Its commit bumps an in-memory **ephemeral
epoch**, which wakes the `/changes` long polls of clients watching a query
that reads that table. Those clients re-run the query; a device never holds
ephemeral rows, so it falls back to the server as it already does for
server-only reads. Each answer's `nextExpiry` already makes clients re-fetch
when a row's deadline passes, so an indicator disappears on time with no
application timer.

This enacts LLP 3000.009 §12's standing line ("Presence beyond polls →
ephemeral channels, if the brief charges for them"). The brief charges for
them: rubric B3 scores 60 for "a durable workaround (tables + expiry jobs)"
and 90 for "purpose-built primitives". The author asked on 2026-09-26 for
this state to be added back. Snapback 1 and Snapback 2 both had it, and
Snapback 2's typing indicator appeared 23–30 ms after the keystroke.

The design choice is **a table, not a channel**. Snapback 2's `channel` was
a separate object with its own scope arguments, publish/subscribe rules, hook
and wire. Here the author writes the table they already write and adds one
line. Rules, joins, generated row types, `useQuery` and `useMutation` all
carry over. §7 weighs the channel port.

## 2. The authoring surface

### 2.1 Declaration

`ephemeral <life>` is a line in a table body, beside `expire at`, `sync` and
`online only`. `<life>` uses the duration units that schedules already
accept (`500ms`, `4s`, `1m`). It is required and must be between 1 second
and 60 seconds inclusive. Outside that range the compiler refuses with
`E_QUARRY_EPHEMERAL`, and the message states the range.

The table keeps the ordinary body grammar: columns, `unique`, `by`, `cap`,
`immutable`, `read`/`insert`/`update`/`delete` rules and `after insert`. The
implicit `id` column and `byId` stay. `default now` columns are allowed.
Some clauses cannot appear in an ephemeral table, because each would make
durable state depend on memory. The compiler refuses them with
`E_QUARRY_EPHEMERAL`, and the message names the clause and the fix:

| Refused on an ephemeral table | Why | Fix the message gives |
| --- | --- | --- |
| `sync …`, `online only`, `sync public`, a horizon | The rows never reach a device | Delete the line; devices read ephemeral rows from the server |
| `expire at .col` | Its life is the declaration | Delete it; `ephemeral <life>` sets every row's deadline |
| `sequence by`, `through`, `words(..)` indexes, asset columns (`image`, `video`), `once` | Durable custody | Keep that data in a durable table |
| Being the source of a `maintain`, a Following view or a feed | Durable derived data | Count or rank durable rows |

Nothing may depend on ephemeral rows except a query's own reads. The
compiler refuses each of these with `E_QUARRY_EPHEMERAL`:

- **any** table's rule or `after insert` that probes an ephemeral table
  (`exists typing[..]`), durable or ephemeral. An ephemeral row's
  visibility then depends only on its own deadline and on durable rows,
  which is what lets deadline expiry stay silent (§3.3);
- a column of any table whose type is an ephemeral table (a reference);
- `sync to typing[..]`;
- a durable mutation, job, schedule or action that reads or writes an
  ephemeral table;
- a `held` query that reads an ephemeral table (held means answered by the
  device).

This follows LLP 3000.009 §7: "Ephemeral state never decides a durable
invariant."

### 2.2 Ephemeral mutations

The binder classifies each mutation by the tables it writes and reads,
using an **exhaustive effect visitor**. `ir::write_tables` is not one: it
misses writes inside expressions such as `Expr::Block` (reviewed probe). The
visitor walks statements, nested expressions, loop domains and inlined
helpers.

- **Durable:** writes no ephemeral table and reads none. Unchanged.
- **Ephemeral:** writes only ephemeral tables. It may read durable tables,
  for example with `require exists members[roomId, viewer] else NOT_MEMBER`,
  and it may use `insert`, `upsert`, `update`, `delete`, `if absent`,
  `require`, `let` and `return`. It may not `emit`, call a native job, use a
  sequence, or write a durable table.
- **Mixed:** writes both kinds. Refused with `E_QUARRY_EPHEMERAL`: "split
  this into two mutations; call the ephemeral one from the client after the
  durable one".

A runtime boundary backs the classification. While an ephemeral mutation
runs, the layered row store (§4.3) refuses any durable write with an
internal refusal and rolls back. A durable mutation's store has no catalog
entry for an ephemeral table, so it cannot write one either.

The binder also marks an ephemeral mutation **`renews`** only when it can
prove that running it twice in a row has the same effect and result as
running it once. The proof is conservative:

- the program makes exactly one write, an `upsert` or `update` of an
  ephemeral table;
- that write's key and every patch value are built only from arguments,
  `viewer`, literals and `now`, never from a read (for example, no
  `n: old.n + 1`);
- anything before the write is a `require` guard, or a `let` used only by
  guards; those guards may read durable tables only, since an ephemeral
  write may invalidate an ephemeral guard;
- the program returns nothing.

`setTyping` renews. None of these does: `stopTyping`, an insert of a
reaction burst, a counter or toggle, or any operation that returns a value.
(Revision 3: Astra's delta probe compiled an upsert keyed by `viewer` that
patched `n: old.n + 1`. It met revision 2's key-only criterion but was not a
renewal.) Only `renews` operations are coalesced or suppressed by the
client (§2.4). All others are sent once per call, in order.

The classification appears in three places:

- `check`'s program listing, as `ephemeral` or `ephemeral, renews`;
- `check --residency`, where each ephemeral table is listed as
  `ephemeral <life>: server memory, never on a device`;
- the generated operation (§2.4).

An ephemeral mutation's semantics:

- **Life.** Each insert or upsert-insert of an ephemeral row stamps the
  deadline `now + life`. Each update, and each upsert that patches an
  existing row, stamps it again, even with an empty patch. That renewal is
  what a heartbeat means. `$deadline` is stamped as its own assignment:
  `recompute_deadline` returns early without `through`, and `merge_patch`
  copies the old deadline. A delete removes the row.
- **The renewal law.** Any write that stamps `$deadline` must pass the
  table's **insert** rule on the new image, in addition to whatever rule
  the write already needs (update, or insert on the insert arm). Extending a
  row's life re-admits it. So a principal who loses the right to insert,
  for example a removed member, cannot keep a row alive past one life,
  whatever the update rule says. Refusal is the update's ordinary refusal
  (`E_RULE` / `NOT_FOUND` per the writes card's table).
- **Rules.** Read, insert, update and delete rules are checked exactly as
  for durable tables. Durable tables are read at the reader's snapshot.
  Ephemeral tables are read at the memory store's state under its lock
  (§3.4 fixes the order).
- **Failure.** The mutation applies completely or not at all. A drop guard
  undoes the journal on every exit that is not a completed commit, including
  refusals, store errors and panics.
- **Result.** The result is the program's return value. There is no `seq`,
  no replay and no id-based idempotence. The client-minted `id` is only a
  correlation token. The server mints any new row ids itself and ignores
  `newIds`.
- **Unique keys, caps and constraints** apply within the memory store. An
  expired row does not collide, as with `expire at`.

### 2.3 Queries over ephemeral tables

A query reads an ephemeral table like any other:

```quarry
query typingIn(roomId: rooms):
  return typing where .roomId = roomId and .principal != viewer by .principal { principal }
```

The query runs on the server. On a device, a read that touches an ephemeral
table is `unknown`, and the client's existing server fallback answers it.
Answers carry `nextExpiry`, the earliest deadline among the ephemeral rows
the answer read.

**An ephemeral read is always its own query.** Reading `typing` inside a
query makes the whole query server-answered: a table without `sync` gives a
server site (`bind/residency.rs:209`), and any server site makes the query
`runs: "server"` (`residency.rs:122`). Joining typing into the chats list
would take the list off the device, so M6's cold-offline chats list would
break, and every typing write would re-run every user's chats list on the
server. `check` therefore prints a note, `N_EPHEMERAL_SERVER`, when a query
that would otherwise run on the device runs on the server only because it
reads an ephemeral table. The note's rewrite is: split the ephemeral read
into its own query and render it next to the device-held one.

The `ephemeral` card teaches the chats-list hint as a separate query,
rendered beside the device-held list:

```quarry
query typingInMyRooms():
  return typing where exists members[.roomId, viewer] and .principal != viewer first 100 by .roomId { roomId, principal }
```

The lane chooses the exact spelling the language accepts (an indexed scan
admitted by the read rule, or a nested read per membership). The suite
compiles the card and runs it.

### 2.4 The client

**Generated facts.** For an ephemeral mutation, the generated operation
carries:
- `ephemeral: true`;
- `renews: true` when the binder marked it;
- `renewMs`: a quarter of the shortest life among the tables it writes, in
  milliseconds.

For every query, the generated operation carries `ephemeralReads`: the
static list of ephemeral tables its read closure can touch (read sites,
helpers, and native reads treated conservatively), omitted when empty.

The same facts appear on the operation entries of `/schema`.

```ts
export const setTyping: Ephemeral<{ roomId: Id<"rooms"> }, null> =
  { kind: "mutation", name: "setTyping", runs: "server", predicts: "never", ephemeral: true, renews: true, renewMs: 1000 };
export const typingIn: Query<{ roomId: Id<"rooms"> }, { principal: Principal }[]> =
  { kind: "query", name: "typingIn", runs: "server", ephemeralReads: ["typing"] };
```

**Types.** Durable and ephemeral mutations are disjoint types over a common
base, so widening cannot pick the wrong overload:

```ts
export type Mutation<A, R> = Op<A, R> & { readonly kind: "mutation"; readonly ephemeral?: false };
export type Ephemeral<A, R> = Op<A, R> & { readonly kind: "mutation"; readonly ephemeral: true;
  readonly renews?: true; readonly renewMs: number };
export type Signal<R = unknown> =
  | { readonly state: "sent"; readonly id: string; readonly result: R }
  | { readonly state: "failed"; readonly id: string; readonly why: Refusal };
```

`client.mutate(op, args)` resolves to `Signal<R>` for an `Ephemeral` and to
`Write<R>` for a `Mutation`. It takes no `MutateOptions` for an ephemeral
operation. `useMutation(op)` keeps its `{ run, last, inFlight }` shape and
types `run`'s result the same way. `usePendingWrite` accepts only
`Mutation`. Negative type tests pin all of this.

**Transport.** Calls travel the ordinary `POST /m/<name>` route, but they
bypass everything durable:

- the device outbox and its admission journal;
- the online tier's pending queue;
- `app-online.ts`'s durable journal;
- the browser admission path in `app-client.ts`;
- prediction.

**The ephemeral lane.** Each client has one ephemeral lane. It keeps at most
one request in flight and sends calls in call order. Keeping calls in order
means a `stopTyping` can never be overtaken by an earlier `setTyping`.

1. **Coalescing, `renews` operations only.**
   - The key is the operation name plus the canonical JSON of its arguments.
   - A new `renews` call whose key matches a call still waiting in the lane
     removes that waiting call and joins the end of the lane. The removed
     call's promise resolves with the new call's outcome.
   - A call that is already in flight is never replaced.
   - Non-`renews` operations are never coalesced.
2. **Renewal window, `renews` operations only.**
   - A call is not sent, and resolves at once with the previous result, if
     all of these hold:
     - its key equals that of the lane's last successfully sent call;
     - that call was sent less than `renewMs` ago;
     - the lane has sent no other call since, and none is waiting.
   - The rule is applied both when the call is made and when it reaches the
     head of the lane.
   - The skipped call's row is still alive for at least three quarters of
     its life.
   - A keystroke-per-call typing indicator therefore sends about once per
     `renewMs`, and its row expires between `0.75 × life` and `life` after
     the last keystroke.
3. **Offline.**
   - While the client's link is not `online`, a call resolves at once with
     `{ state: "failed", why: E_OFFLINE }`. It is never queued or retried.
   - When the link goes offline, every waiting call fails the same way.
   - `E_OFFLINE`'s card text gains that sentence: an ephemeral write is
     dropped, not held.
4. **Bounded.**
   - The lane holds at most 256 waiting calls.
   - Beyond that, a new call fails locally with `E_RATE_LIMIT` and is not
     sent.
5. **Refusals do not change the link.**
   - Every refusal of an ephemeral write arrives as HTTP 200 with
     `{ state: "failed", why }`: rule, capacity, rate, generation.
   - The lane changes the client's link state only on a transport failure:
     no response, or a response that is not this route's JSON.

**Watches need no new API.**
- A query with `ephemeralReads` joins the client's ephemeral interest set
  when it is observed, before its first answer.
- When that set grows, the held `/changes` request is aborted and re-issued
  at once. Shrinking never restarts it.
- A watch is re-run when a `/changes` answer names one of its ephemeral
  tables, and at its `nextExpiry`.
- In the local-first tier, this re-run never triggers a `/sync`, because
  ephemeral changes are not commits.
- §3.3 has the exact parameters and the fencing.

The recipes the cards will teach:

```tsx
const typing = useQuery(api.typingIn, { roomId });
const setTyping = useMutation(api.setTyping);
const stopTyping = useMutation(api.stopTyping);
<Composer onChangeText={text => text ? setTyping.run({ roomId }) : stopTyping.run({ roomId })}
          onSend={() => stopTyping.run({ roomId })} />
<TypingIndicator visible={"data" in typing && (typing.data?.length ?? 0) > 0} />
```

The lane compiles this snippet against the real `Read<R>` union and adjusts
the narrowing to whatever the union requires. The card shows the compiled
form.

For presence in a scope ("who has this chat open"), declare
`table viewing … ephemeral 30s` with a `renews` `markViewing` operation. The
card's snippet calls it on mount and every 10 s, and calls a delete
operation on unmount.

## 3. Semantics

### 3.1 Time

- Deadlines use the server clock (`Shared::now`). That is the development
  clock under `dev`, so `dev clock advance` expires ephemeral rows as it
  expires `expire at` rows.
- A row is absent at `now >= deadline`, through the same `expired` check the
  runner already applies to expiring tables. The engine gives ephemeral
  tables a hidden `$deadline` column and an `$expiry` index, like
  `through`'s hidden deadline (`schema/through.rs`).
- **`$deadline` never reaches the wire.**
  - `recorded.rs` `public_image` returns a row unchanged when the table has
    no recorded fields, no `through` and no timeline slots. Ordinary
    ephemeral tables have exactly that shape. That fast path must also
    check for engine fields.
  - `value/disclosed.rs` `Disclosed::visible` must hide `$deadline` as it
    hides recorded fields.
  - Wire tests cover unshaped point reads, scans, and rows returned by
    mutations.
- Generated row types omit engine fields (`emit.rs:24`).

### 3.2 Authorization and revocation

- Ephemeral rows are read under their table's read rule, like any row.
- Rules are evaluated at read time, and ephemeral rows are never cached on a
  device. So a principal who loses membership sees nothing on their next
  read of that room.
- A durable commit to a table a watched query probes invalidates that
  query, as today.
- By the renewal law (§2.2), a departed member's rows outlive the departure
  by at most one life, whatever the update rule says.
- **Disclosure.** The `/changes` answer names ephemeral tables that were
  written. That is the same class as today's table-granular durable
  invalidation, which names every table a commit touched (`serve_changes.rs:80-94`).
  It adds no new leak class. Capacity refusals depend only on the writer's
  own rows (§3.5), except for the global backstop, which reveals only a
  server-wide aggregate, like HTTP admission.

### 3.3 Change notification

**Server state.**
- The memory store keeps:
  - an **epoch**, a `u64` that each committed ephemeral mutation
    increments;
  - an **incarnation**, a random id that changes whenever the store is
    cleared (§3.4);
  - a bounded ring of `(epoch, tables written)`.
- Deadline expiry does not bump the epoch.
  - For a **complete** answer this is safe. No rule probes an ephemeral table
    (§2.1), so expiry can change the answer only by removing rows the answer
    read. Those rows' deadlines are in its `nextExpiry`, and clients
    re-fetch at it.
  - An **incomplete** answer (`complete: false`, for example a scan cut by
    the authorization walk allowance behind hidden rows) can become more
    complete when hidden rows expire, and their deadlines cannot be
    exported. So a watched query with `ephemeralReads` whose latest answer
    is incomplete is re-fetched on a fixed, content-independent 1 s cadence
    while it stays incomplete. (Revision 3: Astra's delta probe put 8,192
    hidden rows ahead of a live row.)
  - The sweep only reclaims memory.

**Wake state, and no lost wakeups.**
- Polls get their own wake state: `Shared.wake: Mutex<Wake { seq, store_identity, generation, eph_incarnation, eph_epoch, ring_tail }>`,
  with a `polls: Condvar`.
- A durable commit updates `seq` under that mutex and notifies `polls`. It
  also notifies `committed` as today, for maintenance.
- An ephemeral commit publishes `(incarnation, epoch, ring tail)` into the
  wake state **while still holding the hub**, taking the wake mutex last
  (hub, then wake), and notifies `polls` only. `clear_and_rebind` publishes
  its new incarnation and hub binding (store identity, generation) together
  under that mutex. Wake publication therefore follows
  commit order. (Revision 3: publishing after releasing the hub let a paused
  commit 1 overwrite commit 2's wake. Astra's protocol model reproduced it.)
- A poll reads its wake snapshot under the wake mutex before `wait_timeout`,
  and re-reads it under the same mutex after a wake.
- On a wake where `seq` is unchanged, a poll takes no engine lock. Only a
  moved `seq` takes the engine for the store check, as today.
- Lock order is: engine mutex, then hub, then wake mutex. Nothing takes the
  hub or the engine while holding the wake mutex. Nothing takes the engine
  while holding the hub.

**`GET /changes` parameters.**
- `eph=<epoch>`.
- `ephi=<incarnation>`.
- `ephTables=<comma-separated table names>`:
  - absent means "wake me for every ephemeral commit";
  - present, possibly empty, means "wake me only for these tables".
- Clients send all three when the backend declares an ephemeral table.
  A client with no ephemeral interest sends `ephTables=` (empty). A
  durable-only backend keeps the old wire: clients omit all three, with no
  initial incarnation reset (§3.6).
- An online client without schema facts learns support from
  `X-Snapback-Ephemeral: 1` on ordinary responses/heartbeats, present only for
  ephemeral backends and exposed through CORS. It loads `/schema` and reissues
  any legacy discovery poll immediately. Generated read facts can enable the
  parameters before discovery. This preserves the entire durable-only request
  flow, including clients whose transport has no `/schema` endpoint.

**When the poll answers.** Exactly as today, plus two conditions:
- the store's sequence moved past `since`;
- the store identity changed;
- the generation differs from the generation at poll entry;
- the wait expired;
- a table in its interest was written after `eph` (new);
- the incarnation differs from `ephi` (new).

**Wake filtering and pacing.**
- A wake caused only by an ephemeral write outside the interest keeps
  waiting. It neither answers nor restarts the heartbeat.
- If the ring no longer covers `eph`, the answer names every table in the
  interest.
- An answer caused only by ephemeral writes is not sent sooner than 100 ms
  after the poll began. That bounds each client to 10 ephemeral-only
  re-polls a second, however fast a session writes.

**What the answer carries.**
- It gains `"ephemeral": { "epoch": n, "incarnation": "…", "tables": [...] }`.
- A poll with none of the three parameters answers exactly as before (the
  field omitted), apart from waking for ephemeral commits. A schema with no
  ephemeral table has none, so for it this is byte-identical to today.

**Re-issuing a poll.**
- Backend adoption reconciles every mounted watch against the adopted
  operation facts, including additions and removals. The client re-issues its
  held poll whenever its ephemeral interest set grows (§2.4).
- The re-issued poll's `eph` is the smallest epoch among the current
  incarnation's latest answers of its ephemeral watches.
- A watch with no answer yet contributes the client's last `/changes`
  epoch.
- A write that lands between an answer and the new poll is therefore always
  after `eph`, and the new poll answers at once.

**Query answers.**
- A query answer that read an ephemeral table carries
  `"ephemeral": { "epoch": n, "incarnation": "…" }`.
- The epoch is read under the hub lock, in the same critical section as the
  memory rows.

**Fencing.**
- The client keeps an **ephemeral revision**, a counter it tags onto every
  ephemeral query request and `/changes` poll it sends.
- Accepting a new incarnation advances the revision. The client then
  invalidates its outstanding ephemeral queries and its poll, and re-issues
  them.
- A response tagged with an older revision is dropped before its
  incarnation is looked at. So `A:50 → B:1 → delayed A:50` cannot reinstate
  the retired incarnation A. (Revision 3: under revision 2's rule, a
  different incarnation was always accepted. Astra's protocol model
  reproduced the resurrection.)
- Within the current revision, each watch remembers its own
  `(incarnation, epoch)` floor.
- An answer from a different incarnation is accepted, advances the
  revision, and replaces the floor.
- An answer from the same incarnation is accepted only if its epoch is at
  least the floor.
- This is independent of durable `seq` fencing (`minimumReadSeq`), and the
  two are never folded together.
- It applies in the online tier's `currentRead`, in `local-query.ts`'s
  publication path, and to `/changes` answers before they are judged stale.

**Presence re-polls.** Poll entry today runs `presence_reconnected`, which
opens an IMMEDIATE transaction (`engine/effects.rs:287-291`). With this
change, it first checks without a write transaction whether the principal
has a pending presence deferral. It opens the write transaction only if it
has one. The effect semantics are unchanged; ephemeral re-polls stop paying
a writer transaction each.

### 3.4 Generation fence, restart, adoption

The memory store is bound to the `(store identity, generation)` it serves.

- Every hub access runs under the hub lock, for mutations and for queries.
  It compares the durable snapshot's `(store identity, generation)`, which
  its read transaction has already established, with the hub's binding:
  - **hub older:** clear it, rebind to the snapshot's pair, and change the
    incarnation;
  - **snapshot older:** refuse with the store's retryable generation
    refusal. The request retries on a fresh reader.
- Adoption (`serve_adoption.rs`) holds the engine mutex, then takes the hub,
  clears it and rebinds it. So does every engine replacement
  (`open_engine_at`).
- A reader loaned before adoption can therefore never write under the old
  generation's indexes into the new store, nor read new rows under old
  rules.

Ephemeral rows do not survive any of these:
- a server restart;
- schema adoption under `dev`;
- a generation change;
- a store replacement.

Each changes the incarnation, so every client watching an ephemeral table
re-runs its queries (§3.3 fencing).

Day-two classification (`successor.rs`):
- **Destructive:** a durable table gaining `ephemeral`. Activation deletes
  its stored rows and index entries even though the table name remains
  (`store/activation.rs` today deletes only disappeared names).
- **Additive:**
  - an ephemeral table becoming durable, as a new, empty table;
  - adding an ephemeral table;
  - removing one;
  - changing one.

The ephemeral case must be decided before the generic "removed; its rows
are lost" branch (`successor.rs:65-69`). The `$deadline` engine-field
branch is not the only step.

### 3.5 Bounds

| Bound | Value | Refusal |
| --- | --- | --- |
| Life | 1 s – 60 s | `E_QUARRY_EPHEMERAL` at `check`; generation admission re-checks |
| Live rows written by one principal | 1,000 | `E_EPHEMERAL_FULL` |
| Declared bytes written by one principal | 4 MiB | `E_EPHEMERAL_FULL` |
| Live rows, all principals (backstop) | 100,000 | `E_EPHEMERAL_FULL` |
| Declared bytes, all principals (backstop) | 512 MiB | `E_EPHEMERAL_FULL` |
| Ephemeral mutations per session | 20 per second sustained, burst 40 | `E_RATE_LIMIT` |
| Waiting calls in a client's lane | 256 | `E_RATE_LIMIT` (local) |
| Rows per group | the table's `cap … by …` | the existing cap refusal |
| Work per mutation and per query | the existing meter | unchanged |

Every refusal in this table is retryable, carries no row detail, and
arrives as HTTP 200 `{ state: "failed", why }` (§2.4 rule 5).

**How capacity is counted.**
- The hub records each row's writing principal.
- A row is charged its **declared maximum image size**, computed from the
  schema's bounds for its columns and index keys, never its actual bytes.
- Per-principal admission therefore depends only on the writer's own rows
  and on the schema. Another principal's private payload cannot flip it
  (Astra F3).
- The global backstop reveals only a server-wide aggregate. That is the
  same residual class as HTTP admission being full.

**When capacity is checked.**
- Capacity counts live rows only. The hub sweeps expired rows before it
  refuses.
- The check runs under the hub lock, after the program and before the epoch
  bump. A refusal undoes the journal: the row is absent and the epoch does
  not move.

**The rate bucket is new.**
- It is a new per-session token bucket, checked before the mutation runs.
- It applies under `dev` and `serve` alike.
- It shares nothing with the login and upload counters that `E_RATE_LIMIT`
  names today. The code is reused, its card text is extended, and its
  family stays `auth`.

The lane's coalescing and renewal window keep an ordinary typing indicator
near one request per second per typist. That is far below these bounds.

### 3.6 What does not change, and what the lock claims are

**What does not change.**
- A schema with no ephemeral table serializes byte-identically. Its wire,
  its device and the published-0.2.33 capability fences are unchanged.
- A new capability name, `ephemeral`, makes an older device refuse a schema
  that has one, instead of queuing its writes.
- `connected[p]` keeps its meaning and its grace.
- Durable mutations, their prediction, the outbox, replay and the partition
  log are unchanged.
- Presence-guarded effects are unchanged.

**The lock claims.** An ephemeral mutation:
- never opens a SQLite write transaction;
- never holds the serving engine's mutex while it executes;
- takes that mutex only for the short sections a query takes: session
  resolution and reader checkout.

Only queries and mutations whose static read closure includes an ephemeral
table take the hub lock, and only for their metered run. Message pages and
other durable queries never wait on it. `MemoryRows` is `!Sync`, so this is
a `Mutex`, not an `RwLock`; the programs that take it are small.

### 4.3 Engine

A new `engine/ephemeral.rs` (gated on the `sqlite` feature, like the server
engine) adds three things.

- **`Hub`** is shared by `Arc` between the serving engine and its readers.
  It holds:
  - `Mutex<HubState>`, containing:
    - `MemoryRows` (`rows.rs:282-425`);
    - the `(store identity, generation)` binding;
    - per-row writer and declared size;
    - per-principal and global counters;
    - `epoch`, `incarnation` and the ring;
  - `sweep(now)`, which reclaims memory;
  - `clear_and_rebind(identity, generation)`, which also changes the
    incarnation.
- **`Layered<'a> { durable: &dyn Rows, eph: &MemoryRows, journal, mode }`**
  implements `Rows` by routing on the table name.
  - Ephemeral tables go to `eph`, and every mutation of `eph` is
    journaled.
  - Everything else goes to `durable`: durable tables, sequences,
    `effect_once`, assets and prefetch.
  - In ephemeral-mutation mode, any durable write is an internal refusal.
  - A drop guard undoes the journal unless the commit completed (§2.2).
- **Queries.** Only a query whose static `ephemeralReads` is non-empty runs
  over `Layered` and takes the hub lock. It holds the lock for its metered
  run. All other queries run exactly as today.

**`mutate_ephemeral`.** `Engine::mutate` checks the operation's `ephemeral`
fact right after its kind checks (`engine/mod.rs` 946-1058). It then
branches to `mutate_ephemeral`, which:

1. Opens a **read** transaction on the durable store (`read_transaction`,
   deferred), never `transaction()`. A pooled reader engine does this, and
   the serving engine's mutex is not held while it runs.
2. Locks the hub and applies §3.4's generation check.
3. Runs the program over `Layered`, stamping `$deadline` and applying the
   renewal law in `write.rs`:
   - at insert, after defaults (58-62, before validation at 127);
   - at update, as its own assignment beside `recompute_deadline` (281).
4. On success, checks §3.5's capacity (undoing and refusing if exceeded),
   bumps the epoch and records the written tables. On any other exit, the
   drop guard undoes the journal.
5. Publishes the wake while still holding the hub (hub, then wake mutex;
   §3.3), then releases the hub.
6. Writes nothing to `_commits`, `_log`, `_outbox` or `_ops`.

It returns the result, the epoch, the incarnation and the written tables.

**Sweeps.** `sweep_expired_for` (`engine/mod.rs:780-820`) skips ephemeral
tables. The hub's `sweep` runs from the maintenance loop.

**Other paths.**
- `seed_at`, `load` and `/seed` refuse ephemeral tables.
- `snapback4 test` uses the in-process hub, so `test` can exercise the
  typing recipe.
- `snapback4 run` of an ephemeral mutation prints a note: the row lives in
  this process only, and a running `dev` server's clients will not see it.
- The Postgres store's `supported()` (`postgres/mod.rs:396-421`) refuses a
  schema with an ephemeral table until increment C3.

## 6. Non-goals and non-claims

The revised `NOT-DOING.md` line will read: "No multi-server presence, no
presence history or last-seen storage, no broadcast event stream, no
connection-bound rows."

- **No connection-bound rows (`while connected`).** The online tier polls
  only while it watches something, and `connected[p]` keeps a 35 s grace.
  A writer's liveness is therefore not a precise signal today. A heartbeat
  under a 30 s life is simpler and honest.
- **No delivered receipts.** The brief's `delivered` ("fetched by the
  recipient's client") is a durable fact. A platform delivered-receipt fact
  is a separate candidate, still open in the 0.4.1 comparison record.
- **No key-range invalidation.**
  - Invalidation stays table-granular: a typing write re-runs every watched
    query that read `typing`, in any room.
  - The renewal window keeps this near one per second per typist, and the
    100 ms pacing bounds each client to 10 re-polls a second.
  - LLP 3000.009 §7.1's narrower invalidation is the fix, and it is not in
    scope.
- **No multi-process hub.** One `serve` process owns the memory. The hub
  sits behind a trait boundary, so a Postgres host can later use `UNLOGGED`
  tables and `LISTEN`/`NOTIFY`. Until then, Postgres refuses ephemeral
  schemas.
- **No device-side ephemeral state or prediction.** A device never shows an
  ephemeral row it did not read from the server.
- **No rule may probe ephemeral state.** A "muted while typing" rule, or any
  other rule that reads an ephemeral table, is out of scope. Allowing it
  would require notifying clients when a denied answer becomes readable at
  a hidden witness's expiry.
  - The same gap exists today for durable `expire at` witnesses probed
    negatively (Astra F6).
  - That durable case is ticketed separately. This RFC does not widen it.
- **No claim of scale.** Rows are bounded as in §3.5. Invalidation cost is
  linear in the number of watchers of each table.

## 7. Alternatives considered

- **Port Snapback 2's `channel`.**
  - A channel is a separate declaration: scope arguments, a `value` record,
    `publish`/`subscribe` rules and `ttl`. It has its own hook
    (`useChannel`), connection-owned leases, version fencing and a snapshot
    stream.
  - It is proven, and its engine surface is smaller, because it never
    touches the runner.
  - But it is a second model beside tables:
    - it cannot join a profile, so values duplicate names;
    - its rules are a second grammar over scope arguments;
    - it needs its own held connection per client, and this server admits
      only 32 held polls (`serve.rs:370-372`);
    - it teaches a hook and an object that agents have looked for under the
      wrong name before.
  - The table form reuses every concept an author already has, and the
    engine already runs over a pluggable row store with an in-memory
    implementation. All three reviewers agreed with the table.
  - Rejected for authoring cost.
- **Keep durable `expire at` and make its writes skip the outbox.**
  - The writes would still be logged, fsynced, replayed and synced to
    devices.
  - Every keystroke would still invalidate every durable watcher, and
    devices would still hold rows that expire.
  - It fixes F1 and none of F2–F4. Rejected.
- **Store ephemeral rows in the SQLite file, in tables cleared at startup.**
  - SQLite has no unlogged tables, so every keystroke would pay an fsync
    and the writer lock.
  - The rows would leak into backups, `sql` and activation walks.
  - An attached shared-cache memory database hits `SQLITE_LOCKED` outside
    the busy timeout, and every reader would need to attach it.
  - Rejected in favour of the in-process `MemoryRows` store.
- **Connection-bound rows now.** Deferred (§6).
