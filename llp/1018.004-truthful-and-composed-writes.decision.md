# 1018.004 Truthful and composed writes: the durable inbox

**Type:** Decision
**Status:** Implemented (2026-09-08; revision 3 after the Sol implementation review)
**Systems:** snapback2 client SDK (`packages/snapback2/src`), the IndexedDB carrier (`src/store/indexeddb.ts`), the outbox ledger (`src/store/outbox.ts`), tab sessions and forwarding (`src/client-sessions.ts`, `src/client-forwarding.ts`), React and Expo hooks, the chat templates, the test fake (`tests/fake-indexeddb.ts`), the browser witness
**Author:** Claude (Fable 5.1), with the author; implementer: the same agent, 2026-09-08
**Date:** 2026-09-08
**Revised:** 2026-09-08 (revision 3)
**Related:** LLP 1018.003 (the snapshot record; items carry their work), LLP 1018.000 §8 (account sessions and durable follower admission), LLP 1012 §7 (writes offline), LLP 1002 §9 (a 503 after a commit is never a rejection)

## Summary

Reads became truthful and composed in LLP 1018.003: one `Snapshot` record,
derived status, screens that read axes. Writes did not. A write from a
browser tab that is not the account's writer is forwarded over a
`BroadcastChannel` to the writer tab, and when the writer's answer is late or
lost the SDK returns a fourth mutation outcome, `admission-unknown`, with an
opaque recovery token. The application then owns the retry identity, a
custody slot, an auth-generation guard, and the copy, in memory. On main that
costs the chat template two shared modules and about ninety lines of the
thread screen, repeats one guard four times, is imported by the Expo composer
that can never be a follower, and loses both the draft and the fact that a
send may have happened if the tab reloads.

The unknown outcome is an artifact of the transport, not of the problem. The
follower and the writer are tabs of one browser profile and already share
the partition's IndexedDB database; the Web Lock decides who may mutate the
range image, not who may write a row. This decision replaces the forwarded
command with a **durable inbox row in that database**: the follower's `run()`
resolves once its row is durable, the writer admits inbox rows through the
same ledger serial as its own writes, in the same transaction as the entry it
creates, and the follower reads the ledger's persisted entries directly for
everything that happens afterwards. There is no unknown state to recover
from, so there is no recovery token, no two-second timeout, no five-minute
command lifetime, no receipt table, no clock floor, and no application
custody. `MutationResult` returns to three outcomes, all of them either
terminal or durable. `OutboxEntry` stays the one write record on both tabs.
The chat templates delete `shared/send.ts` and `shared/recovery.ts`.

Revision 2 corrects the draft on the points the Astra review established:
connection lifecycle and wipe ordering, admission ordering by durable
insertion rather than wall clock, the record contract for unadmitted rows
and the intent alias, reload visibility through the runtime's item inputs,
liveness without a channel, takeover placement, durable dismissal, the
readiness and settlement contracts, the test fake's fidelity, and the
composer guards that were never about recovery.

## Context

### What a write looks like on main

Three records describe one write at three moments, and they do not share a
vocabulary:

| Record | Where | States | Only here |
| --- | --- | --- | --- |
| `MutationResult` | the `run()` call site | committed, rejected, queued, admission-unknown | `admission-unknown`, `recovery` |
| `OutboxEntry` | the durable ledger, `useOutbox`, `useMutation.pending` | queued, committed, rejected, expired | `expired`, `arrived`, `predicted`, `reason: "fence"` |
| `ItemAction` | a row's `pending` list from `defineItems` | the entry's state | `label`, `dismissible` |

A screen that asks "what happened to the thing I sent" holds the intent id
and consults all three; the thread on main reads a state from each.

The fourth outcome is the one that leaks. LLP 1018.000 §8 forwards a
follower tab's mutation to the writer as a command over `BroadcastChannel`,
the writer admits it into its ledger with a durable request receipt, and
answers. If no answer arrives within two seconds, or the writer stops, or
the five-minute command lifetime expires, the follower's `run()` resolves
`{ state: "admission-unknown", recovery }`. The token binds request identity
and scope but carries no arguments, so `client.recoverMutation(op, sameArgs,
recovery)` needs the application to keep the arguments, the token, and the
draft. The template does that in `useAccountRecoveryCustody`, a `useRef`
cell keyed by client and auth generation, and in `useSendController`:

| File | Lines | Content |
| --- | ---: | --- |
| `templates/chat/react/src/Thread.tsx` | 179 | about ninety lines are recovery plumbing, repeated for edit, unsend, and recover |
| `templates/chat/shared/send.ts` | 155 | the send controller the Composer delegates to |
| `templates/chat/shared/recovery.ts` | 102 | custody slot, tokens, generation guard |
| `templates/chat/react/src/Composer.tsx` | 43 | thin only because of the two files above |

The `visit` capture and its `current(captured)` guard appear four times
across those files. The Expo composer imports the same controller although
the SQLite carrier refuses to follow and native has no second tab.

### Why this is a truthfulness gap and not only a composition gap

The custody cell is memory. A reload during an unknown admission loses the
token, the arguments, and the draft. If the writer had admitted the command,
the message is durable in the writer's ledger and will be sent; the follower
simply stops knowing about it. If the writer had not admitted it, the
message is gone with no trace on the device. The screen that showed "Send
confirmation was lost. Check this send" is telling the truth for exactly as
long as the tab lives. That is the write-side version of a screen that
claims more than it knows.

### What the tabs already share

`indexedDbRangeStore` opens one database per principal partition
(`${prefix}${partition}`), with object stores keyed by `key`, and commits
every swap in one `readwrite` transaction spanning all of them
(`src/store/indexeddb.ts`, LLP 1012 §4). The writer holds the Web Lock
`snapback2:${partition}`; a follower waits on that lock (`follow()` in
`src/offline.ts`) and meanwhile reads live queries from the server. The lock
protects the range image and its swap discipline. It is not what makes the
database private: IndexedDB permits overlapping connections from other tabs
and serializes conflicting transactions across them by object-store scope,
so a writer transaction that spans `inbox` and `outbox` is atomic with
respect to a follower transaction on `inbox` (the specification's
transaction-scheduling rules; Astra review finding 1). What one open
connection does block for another is a version upgrade or a database
deletion, which fires `versionchange` on the other connections first.

LLP 1018.000 §8 solved cross-tab writes as remote procedure calls to a
writer service, and then had to solve everything an unreliable RPC brings:
request identity, payload digests, bounded receipts that survive dismissal,
expiry encoded in the identity, a monotonic clock floor against rollback,
capacity per follower and per partition, timeouts, and a public unknown
outcome. Its witness is thorough for that design. The observation this
decision rests on is that the two ends of the RPC share a durable medium,
and a durable queue between them has none of those problems by construction.

## Options

**A. Keep the forwarded command; make its custody durable and SDK-owned.**
Add a follower-side durable ledger of outstanding commands, extend
`OutboxEntry` with an `unconfirmed` state, run re-confirmation from the SDK
on writer discovery, `online()`, and takeover, and have the writer broadcast
settlements of forwarded intents so the follower's record reaches
`committed` or `rejected`. This composes the application side and closes the
reload gap. It keeps every mechanism of §8 and adds a second durable ledger,
a settlement protocol, and a third state that exists only to describe the
transport's uncertainty. The unknown outcome stays in the public record as a
state a screen has to explain.

**B. Replace the forwarded command with a durable inbox row.** The follower
inserts its mutation as a row in an `inbox` object store of the partition's
database before `run()` resolves. The writer admits inbox rows through the
ledger serial, in the same transaction as the outbox entry it creates. The
follower reads the persisted ledger for the rest of the write's life. No
unknown state exists. This reverses §8's transport, keeps its ownership
model unchanged, deletes most of `client-forwarding.ts`, the receipt table,
the token, the timeout, the lifetime, and the clock floor, and adds one
object store, one version bump, a second connection with a defined
lifecycle, and an admission loop. Its costs are the lifecycle work in §2,
one rekey of a forwarded create's item when the writer assigns its pinned
ids, and a follower `run()` result without ids.

**C. Keep application custody.** The status quo. Composition and the reload
gap remain; every application that can have two tabs reimplements the
custody hook.

**Decision: B.** A is the shape I proposed before reading the carrier, and
it is the wrong shape: it manages a state that the medium does not require.
B is the same move LLP 1018.003 made for reads, one level down. The review
confirmed the premise and refuted the risk that the old RPC's scenarios
return (findings 1 and 16); what it found were contracts the draft had left
implicit, and revision 2 states them.

## Decision

### 1. The write record

`OutboxEntry` is the one write record. Its state axis is unchanged,
`queued → committed | rejected | expired`, and every `run()` result for a
store-backed write corresponds to one durable record with the same public
intent. `MutationCommitted` and `MutationRejected` are exactly a ledger
entry's `response`; `MutationQueued` is `{ intent, ids }`. `ItemAction`
remains the entry's state plus a label and dismissibility. Nothing about a
write is representable at the call site and not in the ledger or the inbox.
Submitting a semantic target also captures its selected table as `presentation`
on the inbox row and admitted entry. The writer derives addresses from its
certified program at admission; the follower never supplies a reserved-ID
offset (LLP 1018.003.001 §3).

**Unadmitted rows are distinguishable.** A follower's `entries()` lists an
unadmitted inbox row as an `OutboxEntry` whose `state` is `queued`, whose
`ids` is empty, whose `grant`, `offset`, `count`, and `issuedSeq` are the
empty values `""`, `0`, `0`, `0`, and which carries `inbox: <key>`. Nothing
replays it: `queuedIntents()` on the writer excludes rows, `replayEnvelope`
is never built from one, and `attachItems` treats it as a create with no
key, so its item falls back to the intent key exactly as an unkeyed create
does today (finding 11). Item retirement never consults it, because
retirement requires `committed`.

**The intent alias.** A follower's `run()` resolves
`{ state: "queued", intent: "inbox:<key>", ids: [] }`. When the writer
admits the row, the ledger entry it creates records `inbox: <key>`, and
from then on the row's public name `inbox:<key>` is an alias every ledger
operation resolves to that entry: `dismiss("inbox:7")` dismisses the entry
whose `inbox` is `7`, on the writer and on a follower that has since taken
over, and `entries()` lists the entry once, under its ledger intent, with
`inbox` set. The alias holds across roles and reloads because it is stored
on the entry (finding 9). A screen that kept `run().intent` finds its entry
by `entry.inbox`; the templates do not need to, because items carry the
work.

Removed from the public surface: `MutationAdmissionUnknown`,
`MutationRecovery`, `client.recoverMutation`, and the `admission-unknown`
member of `MutationResult`. A `run()` on a follower that cannot make its
row durable refuses, with a code, before anything leaves the tab; it never
resolves a state the device does not hold.

### 2. The inbox

The partition database gains one object store, `inbox`, in database version
4, with an **auto-incrementing integer key**. IndexedDB assigns those keys
in transaction-commit order across every connection, so the key order is
the durable insertion order of the device, not any tab's wall clock, and one
follower's rows are in its submission order because its inserts commit in
sequence (finding 8). The writer admits rows in key order, and a local
write on the writer is admitted behind every row durable before it (§4), so
the ledger order is the device's durable order.

```ts
interface InboxRow {
  key: number;                 // auto-increment; the public intent is `inbox:${key}`
  kind: "mutation" | "dismiss";
  scope: string;               // canonical backend url + carrier namespace + principal, as the channel scope today
  principal: string;
  authEpoch?: number;          // the follower's established epoch; absent for a dev persona
  followerId: string;          // diagnostic; not an ordering or ownership key
  op?: string;                 // mutation rows
  args?: unknown;              // mutation rows; JSON-representable, validated at insertion
  target?: string;             // dismiss rows: the ledger intent or an `inbox:` alias to dismiss
  state: "queued" | "rejected";
  admitted?: string;           // the ledger intent, once admitted
  ids: string[];               // empty until admitted
  response?: unknown;          // a rejection at admission
  createdAt: number;
  updatedAt: number;
}
```

**Insert-only from followers.** A follower inserts rows with `add`, never
`put`, and never modifies a row afterwards; only the writer marks a row
admitted or rejected, and only the writer or the row's own rejection path
deletes one. Arguments are validated at insertion against the ledger's JSON
representation, the same canonical form `enqueue` stores, so a value that
IndexedDB can clone but the ledger cannot persist is refused before the row
exists (finding 13). Capacity is 256 rows in `queued` state per partition,
counted and inserted in one `readwrite` transaction on `inbox`, which
IndexedDB serializes across followers; at capacity `run()` refuses
`E_OFFLINE_INBOX_FULL` with no row written.

**The follower's connection.** A following runtime opens the partition
database on its own connection, held in its own field, never in the field
the writer path uses, so `giveBack()` and `open()` keep their meaning
(finding 1). The connection opens when `follow()` begins and reads the
inbox and the persisted ledger once before any network request, so a
reloaded tab shows its device's queued rows from durable state (finding
10). It installs `versionchange`, and so does the writer's connection: on
`versionchange` a connection closes itself at once, so an upgrade or a
deletion elsewhere never waits on it. A follower whose connection closed
this way marks its inbox route ended and refuses new rows with the follower
code until its wait resolves or the client reopens the partition; it does
not reopen the database, because reopening a deleted database would
recreate it. An `onblocked` on open or delete no longer rejects and
abandons the request: the request stays attached with handlers that close
whatever it eventually yields, and the caller waits a bounded time for the
blocker to close on its `versionchange` before refusing (finding 2).

**Wipe holds the lock through deletion.** `wipe()` closes the writer's own
connection, deletes the database while still holding the Web Lock, and
releases the lock only after the deletion completes or times out. A waiting
follower therefore cannot open the partition between the release and the
deletion, which is a race the current carrier has with the range image as
well; the follower's inbox connection has already closed on
`versionchange` (finding 2). Rows die with the database. The scope written
into each row, not the database name, is what binds a row to a backend: two
clients with different backends and the same prefix and principal share a
database and a lock today, and the writer refuses a row whose `scope` is
not its own with `E_OFFLINE_FORWARDING_IDENTITY` (finding 5).

**Admission is one serial operation and one swap.** The writer's admission
loop reads the rows in key order and, for each `queued` mutation row without
`admitted`, runs one operation inside the ledger serial that re-reads the
row, checks custody as `ClientForwarding.admit` does today (the client is
not closed, the operation fence is unchanged, the partition, scope,
principal, and epoch match), and calls `enqueueNow` with an extra swap
fragment that puts the row back with `admitted`, `ids`, and `state:
"queued"`. Grant consumption, the entry, the prediction overlay, and the
row's admission land in one carrier transaction whose scope includes
`inbox` for that swap; the inbox delta is explicit per key and never a
replacement of the store, so a row another follower inserted meanwhile is
untouched (finding 4). Admission is idempotent: a row with `admitted` set is
skipped, so a crash between the transaction and the nudge, or a takeover
mid-loop, cannot admit twice.

**Temporary and terminal refusals at admission.** A grant that is missing,
expired, or exhausted, a bound not yet recorded while no program is held,
or the partition sealed, leaves the row `queued` and stops the loop, because
rows behind it must not overtake it; the next trigger retries. A mismatched
scope, principal, or epoch, an operation the held program does not declare,
or arguments the ledger cannot persist, settles the row `rejected` with the
refusal in `response`, creates no entry, and is dismissible (finding 13).
An unadmitted row from an older epoch is rejected this way; an admitted
row is a ledger entry and replays under the principal's grant exactly as a
local intent does after re-login (finding 5).

**The follower reads the ledger.** After admission the row's write is a
ledger entry, and the follower reads entries from the persisted `outbox`
object store on its own connection, in a readonly transaction, whenever the
writer nudges or a poll fires. There is no mirroring of settlement into the
inbox row: the entry is the record, on both tabs. A follower's `entries()`
is the persisted entries plus its partition's unadmitted or rejected rows;
the writer's `entries()` is the ledger plus unadmitted rows. "Changes on
this device" is the device's on either tab, and an admitted row appears
once (finding 10).

**Dismissal is a durable command.** A follower dismisses by inserting a
`dismiss` row naming the target; the writer's loop consumes it by running
the ledger's serial dismissal and deleting the command row in one swap,
so a dismissal survives a lost nudge, a writer closing, and a takeover, and
a dismissed entry cannot reappear (finding 14). A follower deletes a
`rejected` row of its own partition directly, because that row never
entered the ledger. Queued rows and queued entries cannot be dismissed.

**Amendment 2026-09-10 (LLP 1020 A2, fix rounds r2/r3):** the implemented
state union above is now `queued | rejected | done`. Dismissal atomically
removes an eligible entry and its alias and retains the command as `done`,
with the original entry in `response` (null when ineligible). The follower
consumes that result and deletes the command; after takeover or cold reopen,
the writer also recovers it once by scoped target, including the original
alias, and deletes it under the same ledger lock. A queued entry is eligible
only after its last replay received a non-retryable input/schema refusal;
starting replay clears eligibility durably before transport, so in-flight
or unknown outcomes cannot be dismissed. Unadmitted queued rows remain
ineligible. This supersedes immediate command deletion and the blanket
queued-entry exclusion above; `dismiss` returns the refused intent's
operation, arguments and refusal so re-authoring can unblock the FIFO.

### 3. Readiness on a follower

A follower can make a row durable whenever it has a connection and
capacity, so `readiness()` reports `send: true` for a healthy follower with
a status whose `reason` is `forwarding`: this tab's writes are admitted by
another tab. Two facts remain observable on a ready status:

- `forwarding` with queued rows composes the pending sentence
  "N queued · Waiting for the sending tab."
- `writer-unresponsive`, raised when this tab's oldest queued row has drawn
  no admission for five seconds after a nudge, keeps `send: true` and
  `action: "wait"` with the existing sentence; the rows are durable and
  FIFO, and a frozen writer either wakes or loses the lock. `readiness()`
  gains the branch for a ready status with this reason (finding 12).

What is not sendable stays unsendable: the inbox at capacity
(`inbox-full`, `ready: false`), the inbox connection ended or storage
unavailable (`follower`, the hard refusal), and a bearer follower whose
authority is not established or whose partition is sealed (`sealed`).
`writer-discovery` and `writer-capacity` are gone. A follower's
`detail.status` is this follower status; the writer's grant state, when the
writer has announced it, is exposed beside it as `detail.writer` rather than
folded into `can`, so `useOutboxState` keeps deriving `can` from the status
it exposes (finding 12).

The writer's status also carries `draining: true` during its existing serialized
replay. Its queued work then offers `wait`; a paused queue offers sync even if
a successful read has restored the connected transport. The writer-only ledger
subscription announces both transitions, including a stop that changed no
durable entry. On a follower this remains `detail.writer.draining`; it neither
blocks durable inbox admission nor changes the sending-tab sentence. This
implements [LLP 1018.003.001 §1](./1018.003.001-client-follow-ups.plan.md#1-readiness-actions)
on the inbox's ownership model.

`outbox.settled()` on a follower resolves when every row of its partition
is admitted and every entry it can read is terminal, and otherwise stops
with `{ stopped, remaining }` where `stopped` is `fence`, `offline`, or
`pending` from the writer's announced status when one is known, or the new
member `writer-unresponsive` when the writer has not admitted for five
seconds; it never hangs on an offline writer (finding 12).

### 4. Liveness: nudges, polls, and where admission runs

The follower posts a one-word nudge after every insertion; the writer posts
one after every swap that admitted, rejected, settled, or dismissed. Neither
side depends on it. The writer reads the inbox on: a nudge; partition open,
including takeover; every successful resume or grant change; **before every
local enqueue of its own**, so a local write is admitted behind the rows
durable before it and the existing sessions witness's writer-first,
follower-middle, writer-second order holds by construction; and a
thirty-second safety poll while it holds the partition, which becomes a
five-second poll when `BroadcastChannel` is unavailable. The empty-to-
nonempty transition is therefore always discovered (finding 6). Every
admission that creates an entry schedules a drain through the client's
existing `drainNow`, which already respects forced-offline. The follower
reads its rows and the ledger on its own insertion, on a nudge, and on a
two-second poll while it holds non-terminal rows. Inbox changes reach the
runtime's input listeners, so query items and `outbox.observe` republish
under the same authority fencing as any store change (finding 10).

**Takeover.** The follower session's sequence today is acquire and open,
reauthenticate, `takeover()` (which performs the first resume), clear the
follower marker, activate the writer, drain. Admission of inherited rows is
a new host step between reauthentication and `takeover()`, run with the
wait's cancellation checks and against the open partition while the
follower marker is still set, so the runtime helper must not require the
writer role. It attempts the rows; rows that need the grant or metadata the
resume will fetch stay queued and are retried by the post-resume triggers
(finding 7).

### 5. Hooks and templates

`useMutation` and `useOutbox` do not change shape. `run()` on a follower
resolves `queued`; `pending` includes unadmitted rows; `can` follows §3.
`intentLabel` for a queued unadmitted row is the existing "Sending… ·
Awaiting confirmation".

The chat templates delete `shared/send.ts` and `shared/recovery.ts` on both
platforms. What those modules did that was not recovery stays in the
composer, because it was never about recovery: it captures the conversation
and account it was submitted from and ignores a completion that lands after
navigation, refuses a second submit while one is in flight, clears the
draft only if it is still the text that was sent, and shows a thrown refusal
as a note, since `useMutation.last` holds results and not exceptions
(finding 15). That is about fifteen lines, and the React composer is about
fifty in total. The thread's edit and unsend become short handlers with the
same capture. The Expo composer is the same without the form. The items
declaration in `shared/thread.ts` is unchanged.

Two presentational consequences are accepted and documented. A create sent
from a follower is keyed by its inbox alias until the writer assigns ids,
then by `ids[0]`, so its bubble remounts once at admission; keeping the
alias as the presentation key through admission would need a second
identity beside `item.key`, which the thread uses as the mutation target,
and this decision does not add one. And a follower's `run()` result carries
no ids, so an application that references a newly created parent right
after `run()` must do so from the writer tab or await admission; the
writer and native paths are unchanged.

### 6. The test fake and the witness

`tests/fake-indexeddb.ts` snapshots the whole database per transaction and
replaces it wholesale on a readwrite completion, ignores scope, treats
`close()` as a no-op, deletes under open connections, and never blocks an
upgrade. Under this design's concurrency it erases a writer swap that
overlapped a follower insertion (finding 3). Slice 0 repairs it: a
transaction snapshots only its scope, a readwrite transaction waits for
earlier readwrite transactions whose scope overlaps, `add` refuses an
existing key and `autoIncrement` assigns keys in commit order, `close()`
ends the connection and later transactions throw, `deleteDatabase` and a
version upgrade fire `versionchange` on other connections and stay blocked
until they close. Tests of the carrier's own lifecycle then mean something.

`scripts/witness-web.mjs --sessions` replaces the lost-acknowledgment step
with, in real Chromium:

1. The writer's admission loop is paused by the witness hook. The follower
   sends two messages. Each resolves `queued` at once, both bubbles show
   "Sending…" in send order, the composer stays enabled, and
   `outbox.entries()` on the follower lists two queued rows with empty ids.
2. The follower tab reloads. Both bubbles are back from the inbox before any
   network request.
3. The writer's loop resumes. Both rows are admitted in key order, one swap
   each, the follower's entries show them as ledger entries with ids and
   `inbox` set, and the server stores exactly one row per message.
4. The writer sends a message while one follower row is unadmitted; the
   ledger order is the follower's row first.
5. The writer tab closes with one unadmitted follower row outstanding. The
   follower takes over, admits its own row before its first resume, drains
   it, and the server stores exactly one row.
6. A follower dismisses a settled entry; the writer's history loses it and
   it does not return after a takeover.
7. Lifecycle: with a third tab following, the writer's partition is wiped
   (a persona app has no sign-out; sign-out takes the same path). The
   deletion completes beneath the third tab's open inbox connection because
   that connection closes on `versionchange`; the third tab's wait then wins
   the freed lock and it becomes the writer of a fresh partition whose ledger
   is empty, which is the proof that the old database was deleted rather
   than reopened.

The Expo template's changes are covered by the Expo harness suites
(`expo.test.ts`, `expo-harness.test.ts`, `expo-witness.test.ts`), which
bundle the changed screens; the simulator lane was not rerun for this
landing, because its clip step is blocked by the CoreMedia refusal ticketed
on 2026-09-07, and native has no follower to exercise.

   the lock. Nothing else lands on a fake that erases writes.

before landing.

## Consequences

- A write from any tab is durable on the device before `run()` resolves,
  and stays visible across a reload. That is the truthfulness property
  reads already had.
- The application never sees a transport state. `MutationResult` has three
  members, and every one of them is either terminal or durable.
- The chat templates lose two modules and most of the screens' recovery
  code; the SDK loses the receipt table, the token codec, the timeout and
  lifetime machinery, and most of an 820-line module. The review's estimate
  is 1,200 to 1,400 production lines removed and 600 to 1,000 added, plus
  fixture and test changes; this is a net deletion but not a large one, and
  the claim is measured after slice 3, not assumed.
- A forwarded create's bubble remounts once at admission, and a follower's
  `run()` result has no ids.
- A follower's rows admitted by a frozen writer wait as long as the freeze;
  today they would have surfaced as unknown after two seconds. The user is
  told the sending tab is not responding and that the message is saved,
  which is true.
- The IndexedDB database version rises to 4. A deployment where an old tab
  holds version 3 open makes the new tab's follower writes refuse with the
  follower code until the old tab closes, since the old carrier has no
  `versionchange` handler to close on.
- The carrier's wipe changes order to delete under the lock, which also
  closes a pre-existing race between a wipe and a waiting follower's open.

## Non-claims

- No follower-side prediction: a follower has no held rows and no twin, so
  its create shows the submitted draft until the server row arrives, as
  today.
- No asset uploads or channel publication from a follower; they keep the
  existing explicit refusal.
- No follower grant; the writer allocates every id.
- Nothing cross-device. Two devices remain two partitions and two queues.
- No automatic compaction of terminal history; LLP 1018.003 §10 stands.
- The SQLite carriers cannot follow and are unchanged; the shared
  projection changes are covered by the existing native suites.
- No change to the wire, the engine, or the server's intent ledger; server
  replay and its thirty-day expiry are untouched.
- No dependency-aware outbox, cancellation, or device-to-device sync
  (`rules/NOT-DOING.md`).

## Open questions

1. Whether a follower's `run()` should wait a bounded time for admission so
   the common case returns real ids and never rekeys. The draft answer stays
   no: the row is already published to the follower's entries, and a
   delayed `run()` would make the hook's `inFlight` disagree with the
   ledger. If the rekey proves visible in practice, a bounded wait is a
   one-line change in the follower path, and the record contract above does
   not depend on it.
2. Whether 256 queued rows per partition is the right bound. It matches the
   old receipt bound and is only a guard against a runaway follower; the
   writer's grant capacity governs what can actually be admitted.

**Slice 0, the fake.** `tests/fake-indexeddb.ts` was rewritten: a
