# 1018.004 Truthful and composed writes: the durable inbox

**Type:** Decision
**Status:** Draft
**Systems:** snapback2 client SDK (`packages/snapback2/src`), the IndexedDB carrier (`src/store/indexeddb.ts`), the outbox ledger (`src/store/outbox.ts`), tab sessions and forwarding (`src/client-sessions.ts`, `src/client-forwarding.ts`), React and Expo hooks, the chat templates, the browser witness
**Author:** Claude (Fable 5.1), with the author
**Date:** 2026-09-08
**Revised:** 2026-09-08
**Related:** LLP 1018.003 (the snapshot record; items carry their work), LLP 1018.000 §8 (account sessions and durable follower admission), LLP 1012 §7 (writes offline), LLP 1002 §9 (a 503 after a commit is never a rejection)

## Summary

Reads became truthful and composed in LLP 1018.003: one `Snapshot` record,
derived status, screens that read axes. Writes did not. A write from a
browser tab that is not the account's writer is forwarded over a
`BroadcastChannel` to the writer tab, and when the writer's answer is late or
lost the SDK returns a fourth mutation outcome, `admission-unknown`, with an
opaque recovery token. The application then owns the retry identity, a
custody slot, an auth-generation guard, and the copy, in memory. On main that
costs the chat template two shared modules and about ninety lines of the
thread screen, repeats one guard four times, is imported by the Expo composer
that can never be a follower, and loses both the draft and the fact that a
send may have happened if the tab reloads.

The unknown outcome is an artifact of the transport, not of the problem. The
follower and the writer are tabs of one browser profile and already share
the partition's IndexedDB database; the Web Lock decides who may mutate the
range image, not who may write a row. This decision replaces the forwarded
command with a **durable inbox row in that database**: the follower's `run()`
resolves once its row is durable, the writer admits inbox rows through the
same ledger serial as its own writes, and every later transition of that
write is mirrored to the row in the same swap. There is no unknown state to
recover from, so there is no recovery token, no two-second timeout, no
five-minute command lifetime, no receipt table, no clock floor, and no
application custody. `MutationResult` returns to three outcomes, all of them
either terminal or durable. `OutboxEntry` stays the one write record on both
tabs. The chat templates delete `shared/send.ts` and `shared/recovery.ts`.

## Context

### What a write looks like on main

Three records describe one write at three moments, and they do not share a
vocabulary:

| Record | Where | States | Only here |
| --- | --- | --- | --- |
| `MutationResult` | the `run()` call site | committed, rejected, queued, admission-unknown | `admission-unknown`, `recovery` |
| `OutboxEntry` | the durable ledger, `useOutbox`, `useMutation.pending` | queued, committed, rejected, expired | `expired`, `arrived`, `predicted`, `reason: "fence"` |
| `ItemAction` | a row's `pending` list from `defineItems` | the entry's state | `label`, `dismissible` |

A screen that asks "what happened to the thing I sent" holds the intent id
and consults all three; the thread on main reads a state from each.

The fourth outcome is the one that leaks. LLP 1018.000 §8 forwards a
follower tab's mutation to the writer as a command over `BroadcastChannel`,
the writer admits it into its ledger with a durable request receipt, and
answers. If no answer arrives within two seconds, or the writer stops, or
the five-minute command lifetime expires, the follower's `run()` resolves
`{ state: "admission-unknown", recovery }`. The token binds request identity
and scope but carries no arguments, so `client.recoverMutation(op, sameArgs,
recovery)` needs the application to keep the arguments, the token, and the
draft. The template does that in `useAccountRecoveryCustody`, a `useRef`
cell keyed by client and auth generation, and in `useSendController`:

| File | Lines | Content |
| --- | ---: | --- |
| `templates/chat/react/src/Thread.tsx` | 179 | about ninety lines are recovery plumbing, repeated for edit, unsend, and recover |
| `templates/chat/shared/send.ts` | 155 | the send controller the Composer delegates to |
| `templates/chat/shared/recovery.ts` | 102 | custody slot, tokens, generation guard |
| `templates/chat/react/src/Composer.tsx` | 43 | thin only because of the two files above |

The `visit` capture and its `current(captured)` guard appear four times
across those files. The Expo composer imports the same controller although
the SQLite carrier refuses to follow and native has no second tab.

### Why this is a truthfulness gap and not only a composition gap

The custody cell is memory. A reload during an unknown admission loses the
token, the arguments, and the draft. If the writer had admitted the command,
the message is durable in the writer's ledger and will be sent; the follower
simply stops knowing about it. If the writer had not admitted it, the
message is gone with no trace on the device. The screen that showed "Send
confirmation was lost. Check this send" is telling the truth for exactly as
long as the tab lives. That is the write-side version of a screen that
claims more than it knows.

### What the tabs already share

`indexedDbRangeStore` opens one database per principal partition
(`${prefix}${partition}`), with object stores keyed by `key`, and commits
every swap in one `readwrite` transaction spanning all of them
(`src/store/indexeddb.ts`, LLP 1012 §4). The writer holds the Web Lock
`snapback2:${partition}`; a follower waits on that lock (`follow()` in
`src/offline.ts`) and meanwhile reads live queries from the server. The lock
protects the range image and its swap discipline. It is not what makes the
database private: a second connection to the same database from another
tab is ordinary IndexedDB, transactions are atomic and isolated per object
store scope, and a version upgrade is the only operation that one open
connection blocks for another.

LLP 1018.000 §8 solved cross-tab writes as remote procedure calls to a
writer service, and then had to solve everything an unreliable RPC brings:
request identity, payload digests, bounded receipts that survive dismissal,
expiry encoded in the identity, a monotonic clock floor against rollback,
capacity per follower and per partition, timeouts, and a public unknown
outcome. Its witness is thorough for that design. The observation this
decision rests on is that the two ends of the RPC share a durable medium,
and a durable queue between them has none of those problems by construction.

## Options

**A. Keep the forwarded command; make its custody durable and SDK-owned.**
Add a follower-side durable ledger of outstanding commands, extend
`OutboxEntry` with an `unconfirmed` state, run re-confirmation from the SDK
on writer discovery, `online()`, and takeover, and have the writer broadcast
settlements of forwarded intents so the follower's record reaches
`committed` or `rejected`. This composes the application side and closes the
reload gap. It keeps every mechanism of §8 and adds a second durable ledger,
a settlement protocol, and a third state that exists only to describe the
transport's uncertainty. The unknown outcome stays in the public record as a
state a screen has to explain.

**B. Replace the forwarded command with a durable inbox row.** The follower
writes its mutation as a row in an `inbox` object store of the partition's
database before `run()` resolves. The writer admits inbox rows through the
ledger serial, in the same transaction as the outbox entry it creates, and
mirrors every later transition to the row. The follower's `run()` resolves
`queued` once the row is durable. No unknown state exists. This reverses
§8's transport, keeps its ownership model unchanged, deletes most of
`client-forwarding.ts`, the receipt table, the token, the timeout, the
lifetime, and the clock floor, and adds one object store and one version
bump. Its costs are a second database connection from the follower, a
per-row admission loop in the writer, and one rekey of a forwarded create's
item when the writer assigns its pinned ids.

**C. Keep application custody.** The status quo. Composition and the reload
gap remain; every application that can have two tabs reimplements the
custody hook.

**Decision: B.** A is the shape I proposed before reading the carrier, and
it is the wrong shape: it manages a state that the medium does not require.
B is the same move LLP 1018.003 made for reads, one level down. It also
removes more code than it adds.

## Decision

### 1. The write record

`OutboxEntry` is the one write record. Its state axis is unchanged,
`queued → committed | rejected | expired`, and every `run()` result for a
store-backed write corresponds to one durable entry with the same `intent`.
`MutationCommitted` and `MutationRejected` are exactly that entry's
`response`; `MutationQueued` is its `{ intent, ids }`. `ItemAction` remains
the entry's state plus a label and dismissibility. Nothing about a write is
representable at the call site and not in the ledger.

Two fields change:

- `ids` may be empty on a queued entry. A forwarded write does not know its
  pinned ids until the writer admits it. Item bindings that key a create by
  `ids[0]` fall back to the intent key until then, as `attachItems` already
  does for any create without a key.
- `admitted?: string` names the writer's ledger intent for a forwarded row
  once admission has happened. Before admission it is absent. Screens do not
  need it; the shared outbox projection and takeover reconciliation do.

Removed from the public surface: `MutationAdmissionUnknown`,
`MutationRecovery`, `client.recoverMutation`, and the `admission-unknown`
member of `MutationResult`. A `run()` on a follower that cannot make its
row durable refuses, with a code, before anything leaves the tab; it never
resolves a state the device does not hold.

### 2. The inbox

The partition database gains one object store, `inbox`, in database version
4. A row is:

```ts
interface InboxRow {
  key: string;             // `${followerId}:${sequence}`, the entry's `intent` on the follower
  followerId: string;      // random per follower tab session
  sequence: number;        // per follower, monotonic
  issuedAt: number;        // follower wall clock, for cross-follower ordering only
  principal: string;
  authEpoch: number;       // the follower's established auth epoch, or absent for a dev persona
  op: string;
  args: unknown;           // structured-cloneable; asset inputs are refused before the row exists
  state: OutboxState;      // queued until admitted; then mirrors the ledger entry
  admitted?: string;       // the ledger intent
  ids: string[];           // empty until admitted
  response?: unknown;      // mirrored on settlement
  createdAt: number;
  updatedAt: number;
}
```

**The follower's write path.** `performMutation` on a following runtime
opens the partition database without the lock, on a connection that touches
only `inbox`, and puts the row in its own `readwrite` transaction. The row's
`principal` and `authEpoch` are the follower's own established authority,
captured exactly as LLP 1018.000 §8 captures them today; no bearer token is
written. When the transaction completes, `run()` resolves
`{ state: "queued", intent: row.key, ids: [] }` and the follower posts a
one-word nudge on the existing channel. Capacity is 256 unsettled rows per
partition; at capacity `run()` refuses `E_OFFLINE_FORWARDING_CAPACITY` with
no row written. If the database cannot be opened at this version because an
older tab still holds a lower-version connection, or IndexedDB is
unavailable, `run()` refuses with the existing follower refusal; that is the
only remaining hard refusal, and it is known non-admission.

**The writer's admission path.** The writer reads unadmitted inbox rows in
`(issuedAt, followerId, sequence)` order and admits each through
`OutboxLedger.enqueue` inside the ledger serial, so a forwarded write and a
local write never interleave inside one enqueue. Admission checks the row's
`principal` against the partition and its `authEpoch` against the writer's
current epoch; a mismatch settles the row `rejected` with
`E_OFFLINE_FORWARDING_IDENTITY` and creates no entry. The outbox entry and
the row's `admitted`, `ids`, and `state` land in one swap, because `inbox`
joins the stores the writer's commit transaction spans. Admission is
idempotent: a row with `admitted` set is skipped, so a crash between the
transaction and the nudge, or a takeover mid-loop, cannot admit twice. A
row the writer cannot admit yet because the partition holds no grant, or no
bound for the op, stays `queued` and is retried on the next trigger; the
fence never discards a queued write (LLP 1012 §7), and a row is a queued
write.

**Mirroring.** `settle()` in the writer includes the mirrored row in the
same `commitMany` swap as the entry it settles, so the follower's record and
the writer's are never observed in different states after the same commit.
Dismissal is a device action: the writer's `dismiss(intent)` deletes the
entry and its mirrored row; a follower's `dismiss(key)` deletes the row and
posts a dismiss request the writer honors for the entry. Queued rows cannot
be dismissed, as queued entries cannot.

**Wipe and takeover.** Logout deletes the partition database, and the inbox
goes with it; a follower whose connection points at a deleted database gets
a transaction error and refuses. On takeover the new writer opens the
partition, reloads custody, and runs the admission loop before its first
resume, so rows a dead writer left are admitted in order behind the intents
it inherited. A follower that becomes the writer therefore admits its own
rows. The partition incarnation of §8 is no longer needed to fence recovery,
because there is no recovery; it is retained only where the sessions module
still uses it for takeover fencing.

### 3. Readiness on a follower

A follower can always make a row durable, so `readiness()` returns
`send: true` for it. The status reasons `writer-discovery`,
`writer-capacity`, and `follower` as a soft state are gone. Two facts
remain observable:

- `forwarding`, a ready status meaning this tab's writes are admitted by
  another tab. The pending sentence for a follower reads
  "N queued · Waiting for the sending tab." instead of naming the server.
- `writer-unresponsive`, a ready status raised when a nudge has drawn no
  admission of this follower's oldest queued row within five seconds. Its
  message is the existing one, "The sending tab is not responding. Your
  message stays saved.", and it is a reason on a sendable status, not a
  block: the rows are durable and FIFO, and a frozen writer either wakes or
  loses the lock.

`follower` stays as the hard refusal only when the inbox is unavailable.

### 4. Automatic admission and observation

The writer runs the admission loop on: a nudge; every commit of its own;
every successful resume or grant change; partition open, including
takeover; and, when `BroadcastChannel` is unavailable, a five-second timer
while its last inbox read found unadmitted rows. The follower reads its
rows on: its own write; a writer nudge, which the writer posts after any
swap that touched `inbox`; and, without `BroadcastChannel`, a two-second
timer while it holds non-terminal rows. The writer's existing announcement
keeps carrying its `OutboxStatus` so a follower's `detail.status` reflects
the grant state that will govern admission.

`outbox.entries()` on a follower returns its inbox rows as entries. On the
writer it returns the ledger entries plus any unadmitted inbox rows, so
"Changes on this device" is the device's, not the tab's, and an admitted row
appears once, as its entry. `outbox.settled()` on a follower resolves when
its rows are terminal or the writer is unresponsive, with the same
`{ stopped, remaining }` shape.

### 5. Hooks and templates

`useMutation` and `useOutbox` do not change shape. `run()` on a follower
resolves `queued`; `pending` includes unadmitted rows; `can` follows §3.
`intentLabel` for a queued unadmitted row is the existing "Sending… ·
Awaiting confirmation".

The chat templates delete `shared/send.ts` and `shared/recovery.ts` on both
platforms. The React composer becomes: a controlled input, a submit that
calls `post.run` and clears the draft on any result that is not `rejected`,
the readiness sentence from `post.can`, and the Sync now action when
`post.can.action === "connect"`. A rejection's rewrite renders from
`post.last`. The thread's edit and unsend become two-line handlers. The Expo
composer is the same without the form. The items declaration in
`shared/thread.ts` is unchanged.

One presentational consequence is accepted and documented: a create sent
from a follower is keyed by its row key until the writer assigns ids, then
by `ids[0]`, so its bubble remounts once at admission. On the writer, and
on native, nothing changes. If a reviewer finds a key-stable alternative
that does not delay publishing a durable row, take it.

### 6. The witness

`scripts/witness-web.mjs --sessions` replaces the lost-acknowledgment step
with:

1. The writer's admission loop is paused by the witness hook. The follower
   sends two messages. Each resolves `queued` at once, both bubbles show
   "Sending…" in send order, the composer stays enabled, and
   `outbox.entries()` on the follower lists two queued rows with empty ids.
2. The follower tab reloads. Both bubbles are back from the inbox before any
   network request.
3. The writer's loop resumes. Both rows are admitted in order in one swap
   each, the follower's entries gain ids and `admitted`, and the server
   stores exactly one row per message.
4. The writer tab closes with one unadmitted follower row outstanding. The
   follower takes over, admits its own row, drains it, and the server stores
   exactly one row.
5. A follower row written under an earlier auth epoch settles `rejected`
   with the identity code and creates no entry.

The Expo witness is unaffected in behavior and reruns to prove the deleted
modules are not missed.

## Sequencing

1. Store and ledger: the `inbox` store and version bump, the follower
   connection, the admission loop and mirroring in `OutboxLedger` and

2. Client and types: remove the fourth outcome and the recovery surface,
   reduce `client-forwarding.ts` to announcement, nudges, and dismiss

3. Templates, hooks, guide, and corpus: delete the shared modules, rewrite

## Consequences

- A write from any tab is durable on the device before `run()` resolves,
  and stays visible across a reload. That is the truthfulness property
  reads already had.
- The application never sees a transport state. `MutationResult` has three
  members, and every one of them is either terminal or durable.
- The chat templates lose two modules and about 130 lines of screen code;
  the SDK loses the receipt table, the token codec, the timeout and lifetime
  machinery, and most of an 820-line module, and gains an object store and
  an admission loop.
- A forwarded create's bubble remounts once at admission.
- A follower's rows admitted by a frozen writer wait as long as the freeze;
  today they would have surfaced as unknown after two seconds. The user is
  told the sending tab is not responding and that the message is saved,
  which is true.
- The IndexedDB database version rises to 4. A deployment where an old tab
  holds version 3 open makes the new tab's follower writes refuse with the
  follower code until the old tab closes.

## Non-claims

- No follower-side prediction: a follower has no held rows and no twin, so
  its create shows the submitted draft until the server row arrives, as
  today.
- No asset uploads or channel publication from a follower; they keep the
  existing explicit refusal.
- No follower grant; the writer allocates every id.
- Nothing cross-device. Two devices remain two partitions and two queues.
- No automatic compaction of terminal history; LLP 1018.003 §10 stands.
- The SQLite carriers cannot follow and are unchanged.
- No change to the wire, the engine, or the server's intent ledger.

## Open questions

1. Should a follower's `run()` wait a bounded time for admission so the
   common case returns real ids and never rekeys? The record would be
   durable either way; the question is only whether to delay resolution.
   The draft answer is no, because the row is already published to the
   follower's entries and a delayed `run()` would make the hook's `inFlight`
   disagree with the ledger.
2. Is 256 unsettled rows per partition the right bound, given that the
   writer's ledger has its own grant capacity?
3. Whether the dismiss request from a follower should be durable (a row
   flag the writer consumes) rather than a channel message.
