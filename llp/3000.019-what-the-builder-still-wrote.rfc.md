## 1. Why

Calibration #21 (0.4.2, Astra builder, Astra score, Claude grade) scored
`data_modeling` 90, `queries_and_live` 88, `client_integration` 86 and
`scale_and_limits` 89, with `background_work` at 98. The grade found no blocker
or major defect: M1–M5 passed 79 of 79 assertions and M8 16 of 18. The scorer's
notes, and the builder's own essay, diary and run log, name what still cost the
builder. This RFC lists each cost, with the builder's workaround, and proposes
the platform change that removes it. The goal is 95 in each of those five
categories at the next calibration.

The scorer's words, per category:

- `data_modeling` 90: "conditional aggregate expressions and multi-column sync
  ordering required bounded helpers and a documented ordinal design".
- `queries_and_live` 88: "explicit query/sync ordering requirements; an offline
  coverage limitation for expiry-aware unread aggregates".
- `client_integration` 86: "substantial explicit acquisition, prediction and
  settlement handling, including durable intent presentation; native evidence
  consists of Hermes exports".
- `scale_and_limits` 89: "cold acquisition reached 5.602 seconds, with
  substantial browser RSS of 1,213.5 MiB".

## 2. What the builder wrote by hand

1. **Counting past a watermark.** An unread badge is `count(messages where .chat
   = c and .ordinal > readOrdinal and .sender != viewer and not .deleted)`. On a
   10,000-message conversation it hit the 8,192-row read meter. The builder
   replaced it with a stored `block` column set by both send paths, two
   maintained views, a backfill job and `whole - own + edge` arithmetic.
2. **Aggregates that go missing offline.** Expiry-aware aggregates recompute from
   a horizon-limited source on the device, so the cold offline inbox lost its
   unread counts, and one withheld field withholds the whole row. The builder
   duplicated `inbox` as `inboxLocal` without counts and merged the two in a
   hook with a `useRef` cache.
3. **Sync windows order by one column.** `sync … last 10000 by .at, .ordinal`
   is refused (`E_QUARRY_SYNTAX`), and a query ordered by `.at, .ordinal`
   against a window ordered by `.at` alone went unavailable offline, with no
   `check` note naming the mismatch. The builder adopted the guide's ordinal
   recipe, which rewrites the synced conversation row on every message.
4. **Reads fall back to loading.** A transient reload unmounted routes, lost
   typed input and receipt observers, and made a view-once image vanish. The
   builder latched first answers in refs across four components.
5. **No list of queued writes.** To show an honest pending state for a queued
   send with no predicted row, the builder wrote a 105-line `Pending.ts`
   mirroring the outbox into local storage.
6. **Delivery needs client acknowledgements.** The builder's `Deliveries`
   component observed `thread` for all 100 inbox conversations to acknowledge
   delivery, which made cold acquisition take 69.9 s until it was deferred
   (5.6 s after).
7. **Typing goes through the durable outbox.** Per-keystroke upserts queued
   behind other writes kept the indicator past its 5-second limit. The builder
   throttled to 500 ms and shortened expiry to 3 s.
8. **No row binding inside an aggregate.** `min(deliveries where …, .state)`
   could not state a conditional per-member value, so the receipt became a
   loop.
9. **Residency is invisible.** The 1,213.5 MiB figure summed every Chromium
   process; the builder had no way to see rows and bytes per table.
10. **Contention.** A CLI backfill and the dev server's hot adoption contended
    on the SQLite store (`E_STORE database is locked`).

## 3. Proposals built here

### 3.1 P1: sync windows by several columns, and a note when a query's order cannot be served

**Today.** `parse_sync` (`crates/snapback4-lang/src/parser.rs`) reads `last N
by` and then one word: `.column` or an index name. A comma after it is
`E_QUARRY_SYNTAX`. `.column` becomes a generated index `[audience prefix…,
column, id]` (`bind/intent.rs`). The core already accepts any plain index that
leads with the audience columns (`schema.rs` `Horizon`). The device's window
boundary is the full index key of the window's last delivered row
(`device/boundary.rs`), so it has no one-column limit either. A named index
with several columns (`sync last 500 by byConvTime` over `conversationId, at,
id`) already works; only the `.column` spelling is limited.

Offline, a read of a windowed table is known only when it scans the window's
own index, newest first (`engine/read.rs`, `by_boundary`). Any other order is
unknown on the device, and the query falls back to the server. The compiler
notes this only for mutations (`N_NO_HORIZON`); a query gets no note.

**Change.**

- `sync … last N by .a, .b[, …]` is accepted and generates the index
  `[audience prefix…, a, b, …, id]`, exactly as a named index would. A column
  named twice, or one of the audience columns, is `E_QUARRY_SYNTAX` with the
  rewrite.
- A query that may run on the device and reads a windowed table in an order the
  window cannot serve (another index, or ascending) gets a note,
  `N_SYNC_ORDER`, naming the window's order, the query's order and two
  rewrites: order the page by the window's columns, newest first; or mark the
  query `online only`. The note is a note, not a refusal: the query still runs,
  and falls back to the server offline exactly as today. `check` prints it; the
  guide's `why N_SYNC_ORDER` explains it.
- The sync card shows a two-column window (`last 500 by .at, .id`) and says what
  the device answers from it. The writes card's ordinal section keeps `sequence
  by` for server-arrival order, and stops recommending an ordinal where the
  engine can order by existing columns.

**Evidence.** Parser and binder tests for the new spelling and its refusals; a
device test that a two-column window answers its own order offline and an
ascending read falls back; the note on the builder's shape (window by `.at`,
query by `.at, .ordinal`) and its absence once the window is `.at, .ordinal`;
the guide's compiled blocks.

### 3.2 P2: `min` and `max` of an expression of the row

**Today.** `count` and `sum` take any predicate, and `sum` evaluates a value
expression with the row bound (`bind/program/expr.rs`, the `$filter` row).
`min` and `max` accept only a literal `.field` (`bind/program/extrema.rs`), and
the IR's `Builtin::Extremum` carries a field name, read by `row.field(field)` in
`engine/extrema.rs`. A conditional per-row value cannot be stated, so the
builder's receipt became a loop.

**Change.** `min(t where p, e)` and `max(t where p, e)` accept any scalar
expression `e` of the aggregate's row, written with `.field` as in `sum`, and
with Quarry's conditional (`2 if .seenOrdinal >= m.ordinal else 1`). A literal
`.field` keeps today's plan: an index ordered by that field is a one-row seek.
Any other expression folds over the metered scan, like `sum`, and the scale
certificate prices it as that scan (constant under a declared `cap`, growing
otherwise). An expression that could bind an enclosing shape's row keeps
today's refusal. The IR gains `Builtin::ExtremumOf { value, max, domain }`
beside `Extremum`, so existing programs and generations keep their encoding.

**Evidence.** Binder tests for the forms and the ambiguity refusal; engine
tests that the fold matches a loop over the same rows, with nulls; device and
server agreement; the receipts card's aggregate written this way, if it reads
better; the certificate for a capped and an uncapped source.

### 3.3 P3: answers stay on screen, and the outbox is visible

**Today.** Every `apply`, `admit`, `settle`, `settle_exit` and `clear_rows` on
the local client calls `invalidateAnswers` (`packages/snapback4/src/local.ts`),
which resets every watch to `{ loading: true }` (`LocalReads.clear`) before
re-running it. So each incoming sync page and each local write makes every live
read flash `loading` for at least a frame. A screen that renders a spinner for
`loading` unmounts its children, which is the builder's "transient reload".
Closing a watch deletes it, so a remount starts from `loading` too. `usePage`
makes the whole read `loading` while any page is not ready. Nothing lists the
queued writes: `Write` carries only an id and an optional reason, and
`usePendingWrite(op, id)` needs the id.

**Change.**

1. **Re-evaluation keeps the answer.** A commit on the same store under the same
   authority (`apply`, `admit`, `settle`) marks every watch dirty, fences its
   in-flight publication (the revision already does), and re-runs it, keeping
   the published answer until the new one replaces it. Only a change that can
   withdraw what the viewer may see resets to `loading`: `clear_rows`,
   `settle_exit`, a store replacement (`observeIncarnation`), adoption, and a
   credential or authority change. This is the rule the online client already
   follows for a refetch (`retain`), and the rule LLP 3000.018 applies to a
   presence refresh.
2. **A remount starts from the last answer.** When a watch's last subscriber
   leaves, the client keeps its last answer for 30 seconds, keyed by operation,
   arguments, viewer and store incarnation. A new watch of the same key starts
   from it, marked `fresh: false` with its `since`, and re-runs at once. The
   same resets as in (1) discard kept answers.
3. **Pages stay while more load.** `usePage` keeps the pages it has while a
   further page is loading; `loading` is only the first page's.
4. **The outbox is visible.** `client.pendingWrites()` lists queued writes,
   oldest first, as `{ id, op, args, state, reason?, predicted }`, where
   `state` is `queued` (not yet sent), `sent` (sent, outcome unknown) or
   `held` (a retryable refusal holds the queue), and `predicted` names the
   rows its prediction wrote. `usePendingWrites(op?)` is the hook. A settled
   write leaves the list and still reaches `onWrite`. The online client lists
   its in-memory queue the same way.

**Evidence.** For (1): a test that a watch never publishes `loading` across
`apply`, `admit` and `settle`, on the wasm and process devices, and still does
across each reset in the list; the in-flight fence (an answer read before a
commit never lands after it). For (2): remount within and after the keep window,
and each reset discarding kept answers. For (3): `usePage` in the React harness.
For (4): the list's states through queue, send, a retryable hold and settle,
across a reload, on both clients; a React case.

### 3.4 P8: residency you can see, and a CLI that does not fight the dev server

**Change.**

- `client.residency()` returns rows and bytes per table on the device, with
  the store's total bytes and, on the web, the wasm heap. The guide's residency
  card shows it next to the sync windows that bound it.
- `snapback4 run <job>` and the other store-writing CLI commands detect a live
  dev server on the same store (its lifetime lock file) and either run the work
  through that server or refuse with `E_STORE_BUSY`, naming the server's
  address, instead of failing with `database is locked`. Which of the two is
  the lane's first finding.

**Evidence.** Residency on a fixture with known rows; the CLI against a running
dev server, both ways.

## 4. Proposals that need their own RFC

- **P4. Counted ranges** (item 1). [LLP 3000.015](./3000.015-shared-baseline-for-snapback5.spec.md)'s
  row-keyed views, on `main` and shipping in 0.4.3, answer the builder's case
  directly: `view unread: count messages by members m where .conversationId =
  m.conversationId and .ordinal > m.readUpTo and .senderId != m.principal`
  keeps one count per member, maintained by writes and synced with the member
  row (`guide maintains`, "A value per member: Clique unread"). A general
  counted range over an index is not proposed until a builder needs one the
  view cannot state.
- **P5. Expiry on the device** (item 2; its own RFC). A row-keyed count over
  expiring rows is a private cache the device cannot recompute without the
  source rows, so offline past an expiry it reports pending. The RFC decides
  whether the server ships the count with its next-expiry deadline and the
  expiring contributions, so the device can decrement locally, and lets a shape
  mark a field optional so one withheld field no longer withholds the row. It
  meets `issues/20260925-snapback4-remembered-answer-row-expiry.md`, which asks
  for row-expiry and authorization deadlines to be told apart.
- **P6. Ephemeral signals** (item 7). [LLP 3000.017](./3000.017-ephemeral-tables.rfc.md)
  (ephemeral tables, in review) answers this; this RFC takes it as given.
- **P7. Delivery as a platform fact** (item 6; its own RFC). The server records
  what each principal's devices received, so a receipt needs no client
  acknowledgement. The device's `/sync` request names its transfer watermark,
  which proves receipt of every event of its partitions below it; the server
  keeps no such position today. [LLP 0008.000](./0008.000-fetch-observed-delivery.rfc.md)'s
  questions apply: which serving cuts count (snapshot, stream, query pages),
  identity per principal or device, bounded retention, and authorization loss.
  It would replace the receipts card's runs, catch-up and owing hook.

## 5. Lanes

Each lane implements one proposal on its own branch, with a journal entry, and
gets a blind delta review by both families, as in 0.4.3:

| Lane | Proposal | Surface |
|---|---|---|
| S | P1 | `snapback4-lang` parser and binder, `engine/read.rs`, the sync and writes cards |
| M | P2 | `snapback4-lang` extrema binding, core IR and `engine/extrema.rs`, the certificate |
| K | P3 (1)–(3) | `local.ts`, `local-reads.ts`, `read-observation.ts`, `client.ts`, `react.tsx` |
| O | P3 (4) | the device's `queued` op, `local.ts`, `client.ts`, `react.tsx`, contract |
| R | P8 | device store statistics, `client.ts`, the CLI's store commands |

Lanes K and O start after 0.4.3 lands, because 0.4.3's live presence rewrote
`local-query.ts` and `local-reads.ts`.

## 6. Acceptance

The release that carries these is qualified as 0.4.3 was, then measured by
calibration #22 on the same frozen instrument. Its target is 95 or better in
`data_modeling`, `background_work`, `scale_and_limits`, `queries_and_live` and
`client_integration`.
