## 1. Why

Calibration #21 (0.4.2, Astra builder, Astra score, Claude grade) scored
`data_modeling` 90, `queries_and_live` 88, `client_integration` 86 and
`scale_and_limits` 89, with `background_work` at 98. The grade found no blocker
or major defect: M1–M5 passed 79 of 79 assertions and M8 16 of 18. The scorer's
notes, and the builder's own essay, diary and run log, name what still cost the
builder. This RFC lists each cost, with the builder's workaround, and proposes
the platform change that removes it. The goal is 95 in each of those five
categories at the next calibration.

The scorer's words, per category:

- `data_modeling` 90: "conditional aggregate expressions and multi-column sync
  ordering required bounded helpers and a documented ordinal design".
- `queries_and_live` 88: "explicit query/sync ordering requirements; an offline
  coverage limitation for expiry-aware unread aggregates".
- `client_integration` 86: "substantial explicit acquisition, prediction and
  settlement handling, including durable intent presentation; native evidence
  consists of Hermes exports".
- `scale_and_limits` 89: "cold acquisition reached 5.602 seconds, with
  substantial browser RSS of 1,213.5 MiB".

## 2. What the builder wrote by hand

1. **Counting past a watermark.** An unread badge is `count(messages where .chat
   = c and .ordinal > readOrdinal and .sender != viewer and not .deleted)`. On a
   10,000-message conversation it hit the 8,192-row read meter. The builder
   replaced it with a stored `block` column set by both send paths, two
   maintained views, a backfill job and `whole - own + edge` arithmetic.
2. **Aggregates that go missing offline.** Expiry-aware aggregates recompute from
   a horizon-limited source on the device, so the cold offline inbox lost its
   unread counts, and one withheld field withholds the whole row. The builder
   duplicated `inbox` as `inboxLocal` without counts and merged the two in a
   hook with a `useRef` cache.
3. **Sync windows order by one column.** `sync … last 10000 by .at, .ordinal`
   is refused (`E_QUARRY_SYNTAX`), and a query ordered by `.at, .ordinal`
   against a window ordered by `.at` alone went unavailable offline, with no
   `check` note naming the mismatch. The builder adopted the guide's ordinal
   recipe, which rewrites the synced conversation row on every message.
4. **Reads fall back to loading.** A transient reload unmounted routes, lost
   typed input and receipt observers, and made a view-once image vanish. The
   builder latched first answers in refs across four components.
5. **No list of queued writes.** To show an honest pending state for a queued
   send with no predicted row, the builder wrote a 105-line `Pending.ts`
   mirroring the outbox into local storage.
6. **Delivery needs client acknowledgements.** The builder's `Deliveries`
   component observed `thread` for all 100 inbox conversations to acknowledge
   delivery, which made cold acquisition take 69.9 s until it was deferred
   (5.6 s after).
7. **Typing goes through the durable outbox.** Per-keystroke upserts queued
   behind other writes kept the indicator past its 5-second limit. The builder
   throttled to 500 ms and shortened expiry to 3 s.
8. **No row binding inside an aggregate.** `min(deliveries where …, .state)`
   could not state a conditional per-member value, so the receipt became a
   loop.
9. **Residency is invisible.** The 1,213.5 MiB figure summed every Chromium
   process; the builder had no way to see rows and bytes per table.
10. **Contention.** A CLI backfill and the dev server's hot adoption contended
    on the SQLite store (`E_STORE database is locked`).

## 3. Proposals built here

### 3.1 P1: sync windows by several columns, and a note when a query's order cannot be served

**Today.** `parse_sync` (`crates/snapback4-lang/src/parser.rs`) reads `last N
by` and then one word: `.column` or an index name. A comma after it is
`E_QUARRY_SYNTAX`. `.column` becomes a generated index `[audience prefix…,
column, id]` (`bind/intent.rs`). The core already accepts any plain index that
leads with the audience columns (`schema.rs` `Horizon`). The device's window
boundary is the full index key of the window's last delivered row
(`device/boundary.rs`), so it has no one-column limit either. A named index
with several columns (`sync last 500 by byConvTime` over `conversationId, at,
id`) already works; only the `.column` spelling is limited.

Offline, a read of a windowed table is known only when it scans the window's
own index, newest first (`engine/read.rs`, `by_boundary`). Any other order is
unknown on the device, and the query falls back to the server. The compiler
notes this only for mutations (`N_NO_HORIZON`); a query gets no note.

**Change.**

- `sync … last N by .a, .b[, …]` is accepted and generates the index
  `[audience prefix…, a, b, …, id]`, exactly as a named index would. A column
  named twice, or one of the audience columns, is `E_QUARRY_SYNTAX` with the
  rewrite.
- A query that may run on the device and reads a windowed table in an order the
  window cannot serve (another index, or ascending) gets a note,
  `N_SYNC_ORDER`, naming the window's order, the query's order and two
  rewrites: order the page by the window's columns, newest first; or mark the
  query `online only`. The note is a note, not a refusal: the query still runs,
  and falls back to the server offline exactly as today. `check` prints it; the
  guide's `why N_SYNC_ORDER` explains it.
- The sync card shows a two-column window (`last 500 by .at, .id`) and says what
  the device answers from it. The writes card's ordinal section keeps `sequence
  by` for server-arrival order, and stops recommending an ordinal where the
  engine can order by existing columns.

**Evidence.** Parser and binder tests for the new spelling and its refusals; a
device test that a two-column window answers its own order offline and an
ascending read falls back; the note on the builder's shape (window by `.at`,
query by `.at, .ordinal`) and its absence once the window is `.at, .ordinal`;
the guide's compiled blocks.

### 3.2 P2: `min` and `max` of an expression of the row

**Today.** `count` and `sum` take any predicate, and `sum` evaluates a value
expression with the row bound (`bind/program/expr.rs`, the `$filter` row).
`min` and `max` accept only a literal `.field` (`bind/program/extrema.rs`), and
the IR's `Builtin::Extremum` carries a field name, read by `row.field(field)` in
`engine/extrema.rs`. A conditional per-row value cannot be stated, so the
builder's receipt became a loop.

**Change.** `min(t where p, e)` and `max(t where p, e)` accept any scalar
expression `e` of the aggregate's row, written with `.field` as in `sum`, and
with Quarry's conditional (`2 if .seenOrdinal >= m.ordinal else 1`). A literal
`.field` keeps today's plan: an index ordered by that field is a one-row seek.
Any other expression folds over the metered scan, like `sum`, and the scale
certificate prices it as that scan (constant under a declared `cap`, growing
otherwise). An expression that could bind an enclosing shape's row keeps
today's refusal. The IR gains `Builtin::ExtremumOf { value, max, domain }`
beside `Extremum`, so existing programs and generations keep their encoding.

**Evidence.** Binder tests for the forms and the ambiguity refusal; engine
tests that the fold matches a loop over the same rows, with nulls; device and
server agreement; the receipts card's aggregate written this way, if it reads
better; the certificate for a capped and an uncapped source.

### 3.3 P3: answers stay on screen, and the outbox is visible

**Today.** Every `apply`, `admit`, `settle`, `settle_exit` and `clear_rows` on
the local client calls `invalidateAnswers` (`packages/snapback4/src/local.ts`),
which resets every watch to `{ loading: true }` (`LocalReads.clear`) before
re-running it. So each incoming sync page and each local write makes every live
read flash `loading` for at least a frame. A screen that renders a spinner for
`loading` unmounts its children, which is the builder's "transient reload".
Closing a watch deletes it, so a remount starts from `loading` too. `usePage`
makes the whole read `loading` while any page is not ready. Nothing lists the
queued writes: `Write` carries only an id and an optional reason, and
`usePendingWrite(op, id)` needs the id.

**Change.**

1. **Answers stay during a bounded re-read.** Revised and implemented by
   [LLP 3000.023](./3000.023-answers-stay-on-screen.rfc.md): omission retains
   for one non-renewable second after the client processes an invalidation,
   marked `revalidating: true`, with `fresh` and `since` unchanged.
   `keep: false` preserves immediate withdrawal; `keep: true` retains without
   that episode cap and adds the linger in item 2. Every option withdraws on
   failure, refusal, row expiry or a scope reset. Lane K's revocation finding
   still applies: membership loss by `apply`, predicted leave by `admit`,
   and owner transfer can revoke an ordinary displayed row. The default now
   bounds that exposure; actions can gate on `isReady(read) && !read.revalidating`.

   The facade keeps the last approved answer under its own row deadlines and
   inherited episode deadline, including across clock corrections. Every
   source withdrawal clears the hold and remount peeks synchronously. Held
   expiry fences delayed HTTP writes to remembered answers before callbacks
   can roll the clock back, preserving newer unexpired memory. Deadline
   accessors work without timer delivery, and shared notifications reach
   opening remounts. Implemented in `read-observation.ts`, `read-episode.ts`,
   `read-approval.ts`, `read-expiry.ts` and `guardClient` (KG round 1).

   Ordinary ephemeral refreshes defer to each watch's retention policy;
   expiry retries explicitly withdraw. The guide's existing `keep: true`
   typing examples still compile, with the separate revalidating mark.

2. **A remount can start from the last answer.** With `keep: true`, a watch
   lingers for 30 seconds after its last subscriber leaves. It stays the live
   observation it was, so every reset, expiry, ephemeral adoption and schema
   installation reaches it as it reaches any watch. A new `keep: true`
   subscriber of the same operation, arguments, viewer and store incarnation
   joins it and sees its current snapshot. A reset that ends its scope ends it
   at once. There is no separate store of retired answers (revision 5: three
   review rounds of lane K found a stored answer outliving an expiry across a
   clock move, an ephemeral adoption and a first schema installation).
3. **Pages stay while more load.** `usePage` keeps the pages it has while a
   further page is loading; `loading` is only the first page's.
4. **The outbox is visible.** `client.pendingWrites()` lists queued writes,
   oldest first, as `{ id, op, args, state, reason?, predicted }`, where
   `state` is `queued` (not yet sent), `sent` (sent, outcome unknown) or
   `held` (a retryable refusal holds the queue), and `predicted` names the
   rows its prediction wrote. `usePendingWrites(op?)` is the hook. A settled
   write leaves the list and still reaches `onWrite`. The online client lists
   its in-memory queue the same way.

**Evidence.** For (1): a test that a watch never publishes `loading` across
`apply`, `admit` and `settle`, on the wasm and process devices, and still does
across each reset in the list; the in-flight fence (an answer read before a
commit never lands after it). For (2): remount within and after the keep window,
and each reset discarding kept answers. For (3): `usePage` in the React harness.
For (4): the list's states through queue, send, a retryable hold and settle,
across a reload, on both clients; a React case.

### 3.4 P8: residency you can see, and a CLI that does not fight the dev server

**Change.**

- `client.residency()` returns rows and bytes per table on the device, with
  the store's total bytes and, on the web, the wasm heap. The guide's residency
  card shows it next to the sync windows that bound it.
- `snapback4 run <job>` and the other store-writing CLI commands detect a live
  dev server on the same store (its lifetime lock file) and either run the work
  through that server or refuse with `E_STORE_BUSY`, naming the server's
  address, instead of failing with `database is locked`. Which of the two is
  the lane's first finding.

**Evidence.** Residency on a fixture with known rows; the CLI against a running
dev server, both ways.

**2026-09-27 — Darwin ownership correction (lane OW).** Ownership now locks
`<database filename>-owner` beside the canonical database, a regular 0600 file
opened with `O_NOFOLLOW`: exclusive for backend writers, shared for devices
including the native C ABI. On macOS/iOS, a flock on the database itself
conflicts with SQLite's POSIX locks, preventing startup adoption and device
commits. Database identity remains `(dev, ino)`, checked with stat alone;
only a missing database is created and closed before SQLite opens it. The
guard holds the sidecar, never a database descriptor whose close could discard
SQLite's locks. Sidecars persist after unlock and move with the database's
other sidecars; symlinks, hard links and nonregular ownership files are refused.
`serve.lock` remains an address hint, and `E_STORE_BUSY` keeps its meaning.

**2026-09-27 — round-1 file-mutation hardening (lane OW).** Both ownership
and address-file opens lstat the database and candidate before opening and
compare the opened inode again before any lock, read, write or chmod. A
post-open alias or uncertain descriptor is deliberately forgotten, never
closed or unlocked: either operation could discard SQLite's POSIX locks.
Ownership sidecars must be empty, and address records at most 128 bytes;
these stat-only bounds also refuse a SQLite database renamed to either name
when its original path is absent. Lock the sidecar before creating a missing
database; an `E_STORE_BUSY` probe creates no database or address record.
Database hard links are refused with `E_STORE` and “copy the store, do not
hard-link it,” including on an existing owner's path check.

**2026-09-27 — round-2 exclusion boundary (lane OW, option b).** Exclusion
holds while `<database>-owner` is left in place. Deleting or replacing it while
a process runs ends exclusion: a second owner can create and lock a new sidecar
while the first can continue reading and writing. Removal does not revoke a
running process or cancel its transactions. The retained descriptor still locks
the old inode, which no longer coordinates new opens. Stop all owners before
moving a store and move its sidecars with it; leave `-owner` in place for the
whole ownership lifetime.

This replaces round 1's partial fail-closed claim and removes its live sidecar
checks. `Store::conn()` exposes a raw SQLite connection: auth autocommit writes,
auth and worker transactions, and effect/action/job/timeline reads bypass the
store's transaction helpers. There is no single existing fallible interception
point; changing that accessor's return type would change the connection API and
its callers, and an accessor check cannot revoke a previously borrowed
connection. No single-digit-microsecond transaction-cost claim is made. The
database inode, hard-link and acquisition-time sidecar checks remain. Unit,
native-device and two-process regressions label unlink/replacement as this
documented boundary and prove a second owner can start while old work continues.

**2026-09-27 — live token mutual proof (lane TK, round 1).** A busy
`token` command asks the announced owner to mint through its existing writer.
The per-run 0600 `<canonical database>-token` secret never crosses HTTP:
BSD wildcard listeners need not own the specific loopback address the CLI
dials. Both rounds require an actual loopback socket peer, one literal
loopback Host, no Origin and single protocol headers. IPv4-mapped IPv6 peers
fail closed, including mapped loopback; native `::1` remains usable.

The client sends a fresh 32-byte OS nonce and the request. The server issues a
fresh 32-byte nonce and HMAC-SHA256 over `snapback4-token-server`, client nonce,
server nonce and request binding. Only after verifying it does the client send
HMAC-SHA256 over `snapback4-token-client`, server nonce, client nonce and the
same binding. Nonces are fixed-width raw bytes within the MAC, hex on the wire;
the HMAC key is the exact 64 ASCII hex bytes in the private file. The binding
is UTF-8 JSON of `[1, service, days, storeIdentity]`; days bind before clamping.
The identity hashes JSON of `[hex(canonicalPathBytes), device, inode]`, avoiding
`/var` versus `/private/var` aliases and lossy path encoding. Different stores
also have independent per-run secrets.

The server holds at most 128 pending nonces, expiring after 10 monotonic seconds;
completion atomically removes the nonce before verifying its MAC or minting.
Both sides use RustCrypto HMAC's constant-time `verify_slice`, never string
comparison of tags. Malformed/expired/wrong proofs and boundary failures have
one 403 refusal, no CORS, no secret/token diagnostics. Body/reply limits stay
4,096/8,192 bytes; there is no automatic retry or offline fallback after live
failure. A lost final reply can leave one unused session until expiry.

Mutual MACs alone would let an active impostor forward the handshake and read
the final bearer. Thus the one final reply (including authenticated validation
errors) uses ChaCha20-Poly1305, with a key derived by HMAC under the separate
`snapback4-token-reply` domain, client nonce, server nonce and binding, the
first 12 server-nonce bytes as its AEAD nonce, and binding as associated data.
The single-use server nonce permits exactly one encryption under this derived
key. A relay can forward the caller's one intended mint or deny delivery;
it cannot read the resulting bearer or mint another by replay. Offline
validation, session storage and wall-clock expiry remain the same identity
routine. These dependencies belong only to the server/CLI, outside the device.

**2026-09-26 — Darwin qualification (lane DQ).** Residency counters and
triggers join successful device installation's transaction. Reopening an
unchanged legacy backend computes missing counters in SQLite temp storage;
it does not upgrade the old database before a later adoption can refuse.
Temp triggers maintain this connection's writes; another owner's commit
invalidates the cache through `data_version` and the next inspection rebuilds
it in one read snapshot. Repeated inspections without peer commits do not
scan the partition. A successful new installation or backend adoption
promotes counters to durable storage and removes the temp triggers. Neither
capability refusal nor inspection changes the legacy SQLite bytes.

### 3.5 P9: a list of media is a column

Calibration #22 wrote a bounded list of images that compiled but was never
placed: the server inspected only scalar cells. The M5 image-list fix on
`main` (`94789877f`, `1b7baad4d`, `dc6a3bb40`) now resolves element facts,
places and serves bounded image/video lists through `engine/asset_columns.rs`.
Optional and list wrappers are recursive, homes identify table/row/column
rather than list position, and row-wide releases precede claims. Its existing
reservation and legacy non-placement semantics remain the server authority.

The device half ports lane A's reviewed retention design onto that server.
Confirmed sync records acquisition of each media-bearing row and its generation,
never custody of an id merely referenced by a row. The authorized download
captures the ledger home and store identity in the same transaction; the
CORS-exposed `X-Snapback-Asset-Home` header carries percent-encoded JSON
`{ store_id, table, row, column }`. Upload previews have no home receipt.

The marker is sparse: a row whose media cells are all null or recursively empty
lists needs no marker. A confirmed clear removes its old marker; a later
confirmed image containing media creates it again. Existing extra markers on
empty rows remain harmless because the ordinary authorized read must still
find that asset in the receipt's named column. This avoids one metadata write
per text-only message without changing download or retention authority.

Before keeping or reading ordinary bytes, the device checks that receipt's
store, acquired row and generation, reads the row through the ordinary metered
local interpreter, and checks current membership in the named media column.
The traversal follows the landed server's optional/list shape, without copying
the list or bringing server placement into wasm. Read rules, field authority,
pending rows, expiry and partition leave keep their existing fences. Removal,
clear, deletion, expiry, generation change and leave retire cached bytes;
reorder preserves them. Delivered text history does not retain media authority.
`once` elements remain uncached. A delayed old-store response can finish its
already-authorized transfer but cannot retain bytes in a replacement store.
Entries without a confirmed store-bound receipt are purged on reopen.

**Upgrade and delayed delivery (A5 round 1).** An absent media-index format
stamp requests one normal snapshot reacquisition, even when the server's rows,
store identity, generation and watermark have not changed. The device preserves
the published watermark, private restore evidence, retained history and outbox;
only the transfer request restarts at zero. Until confirmed snapshot/catch-up
publication, media authority remains unavailable. An interrupted upgrade restarts
on reopen. Publication stamps the format and creates markers only for reacquired
rows; retained left-history images do not become media authority. Subsequent
opens resume ordinary incremental sync. Older bytes still need a download receipt.

An invalid download receipt removes an entry only if it is unconfirmed or bound
to the same store, table, row and column. A held old-store response delivered
after a new-store download leaves the newer bytes and live URL intact.

**Restore evidence (A5 round 4).** A same-store restore is a fresh response
head strictly below the maximum published cut, private cut and image head
captured before its request. An explicit image head supplies head evidence. Without it, a terminal stream
watermark or fresh first snapshot page supplies the head. A stream rewind below
its requested cursor is independent proof even if an image head is higher.
A snapshot continuation's watermark never supplies head evidence: it is pinned
to the first page, even when terminal. An explicit image head, if supplied,
retains its meaning on a snapshot. No subsequently staged private
progress is borrowed to condemn an older response. A legacy response without
capture echoes attests only its requested cursor; missing evidence does not
permit borrowing the shared published watermark either. Fresh first snapshots below
captured private image heads now halt as well as those below published progress,
including nonterminal upgrade pages requested from zero without `images_at`.
The refusal persists and stops follow and outbox sends; equal heads remain healthy.

Before observation or application, a continuation must match the current staged
owner, next cursor and snapshot cut. Superseded continuations return `E_GENERATION`
whether the other owner staged or published, with no durable restore halt.
The running client preserves its own captured backend-adoption requirement when
metadata observation supplies a narrower flag, adopts the other owner's published
identity and resumes acquired offline reads without reopening.
The format stays unstamped through the terminal snapshot until
catch-up publishes; reopening there restarts from zero with the same queued
intent. A `once` response parses its receipt before invalidation and checks the
current cache entry inside serialization: a foreign store cannot revoke the
confirmed entry or its live URLs. The current store's `once` response still
invalidates ordinary bytes, including when its receipt is absent, malformed or missing home coordinates,
and no `once` body is retained.

There is no new authoring or public client spelling. For example,
`photos: [image <=10000000] <=4 ?` with
`assets: { keep: "viewed", maxBytes: 67108864 }` keeps viewed list elements
under the same byte limit and eviction policy as scalar media. No server
placement policy, runtime meter, wasm budget or server-side legacy repair is changed.

**Evidence.** `snapback4-device/tests/asset_lists.rs` runs image, video and
nested-list reorder/removal/clear/expiry/deletion/leave/reopen plus generation
and reset checks on memory and SQLite. Existing scalar, delivered-history and
deferred-publication tests now validate the receipt. The client's
`asset-lists.test.mjs` exercises real HTTP grants and native/wasm offline bytes,
legacy bare/copied references, delayed store replacement, expiry and generation
change. Blob lifecycle tests reject malformed/unbound receipts and purge old
bytes on read, reconciliation and reopen. The lane report records the complete
suite and before/after wasm measurements. Round 1 adds persisted scalar/list
upgrades with unchanged server rows, interrupted acquisition and preserved outbox,
newer-download-before-old-response ordering, nested `[[a], [b]]` and `[[], [b,a]]`
across offline reopen, and a same-row placed `photo` plus legacy `refs` copy whose
surviving id cannot replace the cleared ledger home. Round 3 adds the two-owner
overtaken-continuation ordering on both stores and through real HTTP initial
acquisition, including terminal continuation and reopen checks. Restored first
pages cover empty and nonempty events at different watermarks; receipt-less
`once` cases prove ordinary-byte removal, live-handle revocation and no body
retention. Round 4 adds unpublished staging, both continuation terminalities,
open-owner offline recovery, a fresh first snapshot below captured private head,
and valid JSON lacking home coordinates. The report records the failing mutations.

### 3.6 P10: adding a view never stalls reads

Calibration #22's M8 read waited 74,978 ms while adoption held the serving
engine. A reproducible engine fixture at the reported source populations has

**Implemented.** Activation compares the persisted predecessor inside its

This uses the brief's allowed old-program read instead of chunking publicly

Writes submitted during the build wait and execute once under the adopted

remains open. A reconnect acknowledged before its durable write followed
by a crash could leave a pending presence-loss notification eligible despite the

correct chunking is impossible is made.

### 3.7 P11: the server knows its own p95

Calibration #22 scored `scale_and_limits` 88: all 167,157 scale actions settled,
but repeated p95/degradation testing was unclaimed. Its checkpoint probes timed
each named read once. A percentile would have required a custom load harness.
The server now keeps count, refusals and total/wait/engine/CPU latency distributions for
each named query, mutation and action, plus `/sync`, `/changes`, and asset
upload/download, since process startup or an explicit development reset.

**Bound and meaning.** Each operation has four fixed 480-counter logarithmic
histograms (15,432 bytes of statistics per operation, plus its lock, Arc, name and map entry;
no samples retained). Integer bucket
edges grow by at most 10%; their midpoint is within 5% of any sample in that
bucket. The range includes 10 µs through 10 minutes and extends to every `u64`
nanosecond value, including an exact zero bucket; maxima are exact. Percentiles
use nearest rank, bounded by the observed maximum; empty distributions are zero.
`n` and `refused` count requests; `cpu_n` counts requests with a supported CPU
clock sample. With `n = 0`, CPU has an empty distribution (zero percentiles,
`cpu_n = 0`) and doctor prints `cpu n=0`. With `n > 0` and `cpu_n = 0`,
JSON has `cpu: null` and doctor prints `cpu unavailable`; a request without a
CPU clock sample omits `cpu` from its timing header. Names are HTTP paths,
including fixed `/assets (upload)` and `/assets (download)` entries. Invalid
names share three fixed `<unknown>` entries. Successful hot adoption retains
surviving names and removes retired ones, bounding memory by the active program.

Acceptance is the HTTP parser's accepted request, after headers and before
small-body prebuffering or listener/worker admission. Total ends after the
response write/flush (or failed transport), before disposing of or draining the
request reader. Checked tiny_http responses invoke a completion hook immediately
after the final flush; held polls stamp after the final frame, before reader
disposal. A request-owned fallback guard stamps an unanswered/panicking handler
as refused before automatic response/reader cleanup, only if no stamp exists.
When the common JSON path consumes the request into a writer, the guard follows
that writer and drops before its transport cleanup. Wait sums actual reader checkout (including connection opening and failed
attempts) and writer lock acquisition intervals, including authentication and
later acquisitions. Before lane SE it meant acceptance to first acquisition;
that included unrelated request work and missed later waits. Engine time is
wall time owning a reader/writer, including authentication and response-head
reads; nested ownership counts once and reader acquisition suspends any
enclosing engine span so its interval is wait only. Detached reader loans end on return to
the pool or drop, including refusal paths. Held-poll sleeping is outside those
spans. CPU is this request thread's consumed CPU since worker start, from
`CLOCK_THREAD_CPUTIME_ID` on Linux/macOS when available, never process CPU.
It excludes listener/background work and overlaps engine/serialization work;
it is not additive to wall durations. Requests without a worker have no CPU
sample. Requests that never try an acquisition have zero wait/engine. Action pending
responses and long polls describe HTTP request latency, not asynchronous work
completion. Refusals include top-level `denied`, failed write/action envelopes,
HTTP errors and aborted/failed transports; nested user data and ordinary pending
or incomplete reads are not refusals. The request uses thread-local timestamps
and captures the registry topology by cloning one Arc under a short mutex, then
records under that operation's mutex; recording never acquires the engine.
Snapshots capture topology in O(1), clone one operation's fixed histograms at a time
under its operation lock, and scan percentiles outside all locks. They are
consistent per operation, not a simultaneous cut across every operation.
Adoption and reset build replacement topology outside the recording mutex;
reset publishes a new window and excludes already accepted in-flight requests.
Concurrent snapshots may retain the preceding topology until they finish.

**Inspection.** `GET /dev/latency` returns `{ since, storeId, operations }`, with
Unix milliseconds for `since` and millisecond `p50`, `p95`, `p99`, `max` under
`total`, `wait`, `engine` and optional `cpu` for every operation, plus its `n`,
`refused` and `cpu_n`. Development
inspection uses the existing loopback/persona fence and never acquires the
engine. `serve` authenticates the same live service credential as other worker
admin doors before exposing the snapshot; that existing credential check still
acquires the engine. `POST /dev/latency/reset` is dev-only. No application row,
argument, principal, result or meter is recorded or disclosed here.

Ordinary `doctor` shows the three slowest observed operations by total p95 and
the worst observed wait. `doctor --latency` shows every operation; with `--json`
it prints the snapshot. `doctor --latency --reset` starts a fresh dev window.
Persisted dev is discovered through lane R's `serve.lock` address beside the
resolved database, with the existing store identity check. Symlinked
`.snapback4` paths retain lane R's existing startup and ownership behavior.
For `dev --fresh` or `dev --memory`, use the address dev printed at startup:
`doctor --latency --url http://127.0.0.1:4400`, with `--json` and `--reset`
as needed. `doctor --url` also supports ordinary health/summary inspection.
Only loopback HTTP origins are accepted: literal IPv4/IPv6 loopback or
`localhost`, without credentials, paths, queries or fragments; localhost is
mapped directly to IPv4 loopback without DNS. No server is selected by recency.
When no persisted host is found, doctor explains how to pass the printed URL.

The server remembers its canonical project and temporary-store status and
returns both from `/dev/status`. Both address sources require the **server's**
project to match doctor's canonical project before any latency read or reset;
a mismatch names the other project and stops. The **server's** temporary flag
selects the health path. Ordinary doctor reports temporary-store identity and
latency without claiming persisted-store health. An explicit URL chooses a
listener; its status checks are consistency checks, not process authentication.
Reset carries the inspected store identity to that listener before mutating
the window. No extra per-project discovery file or cleanup lifecycle is used.
Doctor requests HTTP/1.0 so snapshots above the server's 32-KiB chunk
threshold remain length-delimited for its bounded close-only reader.
The bounds card owns the executable growth-curve recipe; its entire shell/Node
block is extracted and run by the real-process guide/latency test, while all
Quarry blocks remain under the whole guide suite. The aliases `latency`,
`performance`, `p95`, `benchmark` and `load test` all resolve to bounds.

**Per-response development evidence (lane SE).** Responses passing the existing
loopback peer/Host/Origin dev fence on a loopback-bound listener add the standard
`Server-Timing` header independently of CORS, including refusals and pending replies,
with `total`, `wait`, `engine` and optional `cpu` durations in milliseconds,
rounded to 0.001 ms. Other dev routes receive the header without creating new
histogram names. Production never adds it; production aggregate inspection
retains its live-service-token check. No timing header is sent for an aborted
admission (no response) or a request rejected by the loopback fence.
The same thread-local measurements drive header and histogram. Header total
ends at header construction, after JSON encoding on the ordinary query path;
this cannot include a future socket flush. Stream/heartbeat headers describe
only time before streaming. Doctor's completed total still includes the final
write/flush; request-body cleanup and later asset-view bookkeeping are excluded.
CPU and engine histograms stop at that same completion stamp.
The header contains no rows, counters, operation names, arguments or identities.
Phase and CPU timings reveal more than total elapsed time: CPU can distinguish
hidden-row payload work even with identical results and meters, and wait separates
contention from request work. Doctor also aggregates other principals’ requests.
Per-response timing is acceptable only on loopback-bound dev, where the developer
already holds the store; serve never emits it. Production aggregate inspection
remains restricted to a live service credential. This is no constant-time claim. The meter and disclosure rules are unchanged. No new diagnostic code or execution meter is introduced.

**Evidence.** Histogram tests compare nearest-rank percentiles against 200,000
deterministic random samples across linear, logarithmic, sub-10-µs and bimodal
distributions, plus every edge and the full representable range. HTTP tests
cover operation counts, typed/reflected refusals, fixed routes, reset, a held
engine with independent dev inspection, old requests spanning reset, and
service-only production inspection. The real CLI test exercises ordinary,
all-operation, JSON and reset forms against a running dev server, including
300 additional operations taking the snapshot past the HTTP chunk threshold.
Round 1 adds 500/300-ms withheld-body drain cases for changes/assets, a query
with 150 ms of held engine work, a heartbeat poll held at least 180 ms and then
drained for another 300 ms, and a 32-MiB asset whose socket reads are held for
200 ms. All three review mutations fail these duration assertions. A
10,000-operation snapshot test proves an unrelated record finishes while the
snapshot is deliberately blocked on one operation (100-ms timeout), then
bounds observed record wait plus work below 10 ms during three full snapshots.
These shared-host wall-clock bounds are regression witnesses, not scheduling
guarantees. Real CLI regressions cover persisted discovery, explicit URLs for
both temporary spellings, simultaneous persisted and temporary servers,
non-loopback refusal, stale store identity and project mismatch before read or
reset. Ordinary doctor takes temporary status from the server and prints an
unquoted store identity. Persisted dev reopens and serves an existing database
through a symlinked `.snapback4`; fresh and memory starts work with that directory
alias too. All three modes write no extra discovery file.
A panicking handler withholds a
2-KiB body for 300 ms without adding its cleanup to total. A 16-KiB JSON reply
uses constrained TCP buffers and withheld reads to pin its final-write stamp;
a client reset during a 32-MiB asset proves exactly one sample and one refusal.
Moving the JSON stamp before its write and forcing successful classification
on the asset callback each fail their respective new test.
Round 3 pins the held poll's final write: a real heartbeat poll wakes with a
17-KiB table invalidation frame on constrained TCP buffers, then the client
withholds reads for 200 ms. Total must include that blocked write. Moving the
stamp before `write_response_frame` compiles and fails the regression.
Measurement and full-suite results are recorded in the lane's journal entry.

## 4. Proposals that need their own RFC

- **P4. Counted ranges** (item 1). [LLP 3000.015](./3000.015-shared-baseline-for-snapback5.spec.md)'s
  row-keyed views, on `main` and shipping in 0.4.3, answer the builder's case
  directly: `view unread: count messages by members m where .conversationId =
  m.conversationId and .ordinal > m.readUpTo and .senderId != m.principal`
  keeps one count per member, maintained by writes and synced with the member
  row (`guide maintains`, "A value per member: Clique unread"). A general
  counted range over an index is not proposed until a builder needs one the
  view cannot state.
- **P5. Expiry on the device** (item 2; shipped in 0.4.4 as [LLP
  3000.020](./3000.020-an-unread-count-the-device-can-certify.rfc.md), device
  range certification over existing indexes). A row-keyed count over
  expiring rows is a private cache the device cannot recompute without the
  source rows, so offline past an expiry it reports pending. The RFC decides
  whether the server ships the count with its next-expiry deadline and the
  expiring contributions, so the device can decrement locally, and lets a shape
  mark a field optional so one withheld field no longer withholds the row. It
  meets `issues/20260925-snapback4-remembered-answer-row-expiry.md`, which asks
  for row-expiry and authorization deadlines to be told apart.
- **P6. Ephemeral signals** (item 7). [LLP 3000.017](./3000.017-ephemeral-tables.rfc.md)
  (ephemeral tables, in review) answers this; this RFC takes it as given.
- **P7. Delivery as a platform fact** (item 6; its own RFC). The server records
  what each principal's devices received, so a receipt needs no client
  acknowledgement. The device's `/sync` request names its transfer watermark,
  which proves receipt of every event of its partitions below it; the server
  keeps no such position today. [LLP 0008.000](./0008.000-fetch-observed-delivery.rfc.md)'s
  questions apply: which serving cuts count (snapshot, stream, query pages),
  identity per principal or device, bounded retention, and authorization loss.
  It would replace the receipts card's runs, catch-up and owing hook.
  Revisions 0–2 were reviewed NOT READY by both families, who recommended
  keeping the card's data model and moving only the reporter into the SDK.
  Revision 3's requirements are [LLP 3000.021](./3000.021-what-the-comparative-builder-still-wrote.rfc.md)
  §3.2 (P13), for 0.4.5.
