## Review finding (0.0.16 baseline)

The shipped local client stores predictions directly over confirmed rows and
uses an outbox that mostly records touched ids. That representation cannot
reconstruct the last confirmed state after a refused update or delete, nor
reliably preserve overlapping predictions. Snapshot replacement, stream
application and adapter transactions also lack a shared atomicity contract.
The vocabulary on the card is small, but the state transitions behind it are
not yet one coherent durable protocol.

This is a focused extension of [LLP 3000 §9](./3000-snapback4.explainer.md#9-architecture-and-code-review-2026-09-12),
not a proposal to return to per-query receipts or a second public client model.

## Evidence and confidence

At the review's 0.0.16 baseline, independent probes reproduced:

- A failed snapshot replacement clears rows but retains the old watermark.
- Two simultaneous syncs can apply watermark 3 followed by watermark 2.
- A SQLite write can resolve successfully, then disappear when an unrelated
  overlapping write rolls back. The memory adapter does not roll back at all.
- A refused update deletes a previously confirmed row locally. A subsequent
  successful sync leaves the row missing because the refusal made no server
  commit to replay. The local read nevertheless reports complete and fresh.
- The id mint drops its timestamp; sorting the outbox by these ids does not
  preserve admission order.
- A transient HTTP 503 leaves a pending write unsent after transport recovery
  and an explicit successful sync.

These are tested outcomes, not simulated possibilities. Additional concerns
below follow from code paths and need focused execution during implementation.
The original review examined `src/replica/{replica,store,sqlite,interpreter}.ts`.
Those historical TypeScript files were subsequently replaced. Current owners are
[local.ts](../snapback4/packages/snapback4/src/local.ts), the Rust
[device](../snapback4/crates/snapback4-device/src/device.rs), its
[store interface](../snapback4/crates/snapback4-device/src/store.rs),
[SQLite adapter](../snapback4/crates/snapback4-device/src/sqlite.rs), and shared
[interpreter](../snapback4/crates/snapback4-core/src/engine/runner.rs).

## A state model to make explicit

Five things have different lifetimes: the last committed partition, its
watermark/generation, admitted writes in a durable order, the visible result
of applying those writes speculatively, and terminal write outcomes. The
current representation collapses the first and fourth, and retains terminal
outcomes only in memory after removing outbox entries.

That is particularly problematic when write A and write B touch the same row.
Acknowledging A can overwrite B's prediction. Refusing A can remove B's row.
A maintain's speculative updates are not all represented in the touched-row
list used for failure cleanup. Generation reset clears predictions, while
startup replay and ordinary catch-up have different reapplication behavior.
A write admitted offline returns `pending`, but the card exposes no durable
way to find its eventual refusal after the submitting call or process is gone.
These code-traced cases need a deliberate policy, not more cleanup branches.

## Alternatives worth evaluating

| Representation | What it makes easy | Main tradeoff |
|---|---|---|
| Confirmed base plus ordered operation overlays | Drop one refused operation and deterministically replay survivors; incoming sync cannot erase the base needed for rollback | Replay cost and dependency semantics must be bounded; maintains must share the overlay transaction |
| Confirmed base plus undo/rebase records | Cheap simple rollback and incremental updates | Overlapping writes, deletes and maintains require complete before-images and careful rebase logic |
| Durable outbox with prediction only where eligibility is proven | Smaller first implementation; server remains available for ineligible operations | Some writes have pending state without an immediate row prediction; UI must explain that state using the existing card |

The third option can be combined with either of the first two. Keeping the
confirmed base recoverable is more important than predicting every mutation.
No option should make a local refusal final merely because the device lacks
an online-only row or data beyond its horizon.

## Required decisions

- Define the store transaction contract for rows, indexes, metadata and side
  tables. Separate asynchronous callers are never nested transactions merely
  because they share a driver object. Snapshot replacement and generation
  reset must use that same contract.
- Define one owner or compare-and-apply rule for stream application. A
  response is checked against the persisted current state when it commits,
  not only the watermark captured before its request began.
- Give admitted writes a durable sequence independent of random ids and wall
  clocks. Specify dependencies, terminal versus retryable refusal, and retry
  scheduling across restart.
- Decide how a caller observes the eventual result of a write admitted while
  offline. The present `Promise<Write>` and in-memory settlement map cannot
  provide durable outcome discovery alone.
- Specify admission failure: transaction failure must leave neither partial
  prediction nor a false `pending` acknowledgement. A caught-up replica does
  not establish freshness of a prediction or restore lost confirmed rows.
- Define rebase order around snapshots, schema generations, acknowledgements
  and multiple outstanding writes, including maintained values and deletes.

## Verification that addresses this gap

The Rust simulator's replica serializes sync requests, uses an ordered
counter for operation ids, stores snapshots atomically as a blob, and keeps
ack/failure state that the shipped TypeScript client does not. Its seven
invariants establish useful properties of that model, but do not establish
that the adapters and lifecycle above implement it.

Use the same transition examples against the actual TypeScript lifecycle and
memory/IndexedDB/SQLite adapters: fail admission; crash between replacement
steps; reorder two responses; acknowledge A after predicting B; refuse A;
retry after 503; reopen with pending writes; change generation. Preserve the
small existing test entry point. [LLP 3000.003](./3000.003-one-semantics-and-credible-verification.research.md)
considers how to share those scenarios without adding a parallel model that
silently supplies the missing safeguards.

## Implementation follow-up

The author's request to fix the tickets produced a confirmed-base and ordered
replay implementation in both shipped device arms. These are implemented
choices for R05–R15, R28–R29, R31 and R37, not acceptance of all the broader
outcome-discovery proposals above.

A store transaction now owns rows, indexes, metadata and side tables.
Independent SQLite/Expo callers queue; Expo uses its transaction-owned
connection when available. Memory transactions use copy-on-write containers
and isolate mutable values, so a failed transaction cannot alter committed
rows or metadata without copying the entire store for each small write.
IndexedDB waits for transaction completion.

Snapshots stage in a separate table while queries continue to see the old
committed partition. Snapshot rows stay staged through a log catch-up to a drained watermark;
only its final transaction replaces rows and watermark. This repairs rows
read on either side of a concurrent server commit without waiting for a
quiet server.
A persisted owner, generation, watermark and send revision bind continuations;
repeated final pages, competing owners and stale continuations are refused.
Stream responses check persisted state when applied, and same-client sync
requests coalesce. Backend/schema adoption also uses the store queue.

Prediction records include confirmed before-images for source rows and
maintains, a durable submission order, admitted IDs, viewer and time. A
refusal restores the base and replays surviving writes in order in one
transaction. Replay cannot invent extra IDs after the request's ID supply
has been fixed; an expanded prediction is withdrawn while its durable write
remains queued. Snapshots, deltas and acknowledgements share this rebase
path. Native and TypeScript tests include updates, deletes, aggregate changes,
overlapping writes and reopening before settlement.

A bounded `/sync` correlation of pending IDs to committed operation sequences
prevents a received authoritative write from being predicted a second time
while its mutation response is delayed or lost. The write remains queued
until its full outcome is known. A drained stream advances through the
current commit even when a no-op or online-only write has no viewer events,
so those terminal entries can retire too. Network ordering covers same-client sends
versus sync, while a durable send revision detects another store owner's
intervening send inside the apply transaction. Capturing pending IDs and that
revision is atomic. This guard matters even when the admitted write was absent
from the original sync request. Long-lived outcome discovery after the outbox
entry is removed remains an open API question.

Transient failures retry the same IDs with bounded backoff without requiring
an observer. Close waits for owned work and stops retries. Online query
responses retain dependencies; denied observations retain conservative
dependencies, and poll progress is separate from a query's observed sequence.
Missing online-only data or uncertain horizon coverage routes work to the
server when reachable, or returns the existing typed unknown/refusal offline.
An unavailable row is not sufficient evidence for a terminal local mutation
refusal. A supplied token can establish the viewer from authority.

React resources survive Strict Mode's setup/cleanup replay. A changed page
boundary recreates dependent pages to the requested depth; combined results
use the conjunction of completeness/freshness and the oldest observation time.
Concurrent mutations track their separate lifetimes. Reference apps dispose
late-opened clients and preserve independently edited drafts on settlement.

Native startup probes the read-only sync receipt before starting queries,
followers or outbox work, including an offline reopen. An older Expo 0.1.14
module can otherwise open a store but refuse the newer protocol while its
JavaScript client appears online. An unsupported or malformed receipt now
fails startup with `E_NATIVE_VERSION` and update/rebuild guidance; every probe
failure closes the native handle, and operational errors retain their original
diagnostic. Reloading JavaScript cannot replace an installed native binary.
The actual current-core online/offline control and incompatible-core cleanup
cases pass in the client suite; native publication still requires rebuilding
the generated XCFramework and application binary.

The actual TypeScript clients and Memory/SQLite/IndexedDB adapters, native
SQLite device and React development runtime have focused regressions in the
existing test entry points. This is not a process-kill or physical iOS disk
failure experiment. Durable terminal outcomes, limits on replay work and a
more compact representation of large outboxes remain research.

## 2026-09-16 review: ownership and lifecycle guarantees

The current review is pinned to `a0d48a4` (0.2.26). Current web writes have
transactional admission plus a bounded synchronous localStorage journal
when an exclusive Web Lock is held. The old pagehide-loss hypothesis is
therefore too broad. Muse's supplemental pass confirms the remaining split:
without `navigator.locks`, `web::claim` opens the shared persistence name
with `exclusive:false`, disabling journal capture/recovery and orphan
adoption while allowing multiple memory devices to mutate one IDB database.
See [the ownership ticket](../issues/closed/20260916-snapback4-web-store-without-locks.md).

Choose one durable ownership contract. The smallest safe change requires a
usable cross-context lock for built-in browser persistence and returns an
actionable opening refusal when unavailable. A portable implementation could
instead use a transactionally fenced owner in IndexedDB; a timed lease alone
is insufficient because suspended tabs can wake and write stale state.
Per-tab stores without an adoption/ownership protocol avoid direct collisions
but can strand admitted work permanently. A SharedWorker owner is another
component-level redesign, with its own platform and lifetime constraints.
No browser-storage rewrite is selected here. Qualify two simultaneous tabs,
suspension/revival, closing during admission and reopening after a crash.

The online asset path separately demonstrates a small lifecycle hole: a
fetch admitted before `close()` can resolve afterward with a new usable blob
URL. Lead reproduction delayed a 13-byte response across close. Fence both
success and refusal completion on current client/credential state and revoke
obsolete object URLs; the local tier already follows that shape. This does
not promise recall of media already delivered to an authorized viewer.

Client IDs also mix ordering with time: each mint increments the timestamp
by at least a millisecond, so a burst creates future `minted_at` values. Order
can instead advance the 80-bit entropy suffix at a fixed logical timestamp.
Clock rollback still requires monotonic logical time, but throughput must not
invent one extra millisecond per ID. Missing secure entropy is a distinct
platform decision: browser/Node and native Expo need an explicit supported
source, not silent Math.random. The [ID ticket](../issues/20260916-snapback4-client-id-clock-and-entropy.md)
tracks both with separate validation obligations.

The 2026-09-16 repair candidate implements the explicit ownership contract:
built-in IndexedDB requires Web Locks, and custom Persistence providers must
supply claim(name, alternate) for both opening and orphan recovery. The memory
provider supplies a provider-local owner set. It also fences late online asset
completion and increments client ID entropy within one logical millisecond.
Secure entropy on hosts without Web Crypto remains open; these IDs must not be
treated as secret capabilities. Portable durable ownership without Web Locks
remains a separate design and platform-qualification question.

Follow-up qualification exposed recovery against stale cached rows. A surviving
executable journal record now uses replay-candidate admission: successful local
prediction remains, while a local refusal leaves an unpredicted durable intent
for server decision. Primary and orphan recovery share this rule; it preserves
offline custody without a new device API. Custom alternate claims are also
validated for the documented `:tab-` namespace and discovery/removal methods.
Invalid claims release ownership and refuse before device admission. The living
contract and cancellation limits are in LLP 3000.007 §20.4.

## Proposed composition of retained and authoritative reads

**Planning status, 2026-09-17:** rewritten the day after the first proposal
and commissioned for implementation by the author's request of 2026-09-17
("rewrite them if you think you have a better plan, then carry out
execution"). The first proposal (`68ac50852`) planned per-value data, absence
and control provenance in the shared runner, a compiler component plan, a
server sidecar of component outcomes and client composition. This rewrite
keeps its result, its eligibility boundary and its consistency rules, and
removes the provenance machinery and the sidecar: the first slice the
proposal itself chose never needs either. The
[ticket](../issues/20260914-snapback4-mixed-left-held-query-loses-retained-rows-online.md)
stays open until the acceptance below is met; the accepted fallback behavior
in [LLP 3000.007 §18.2](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md#18.2)
changes only when the implementation lands, and says so there.

### The result the design must make possible

Unchanged. The regression has two groups of 26 messages and an acquisition
horizon of 25; after leaving one group neither host can produce the desired
value alone:

| Observation | Current result | Result for an independently composed query |
| --- | --- | --- |
| Online | `{left: 0 rows, held: 26 rows}` from the server | `{left: 25 retained rows, held: 26 authoritative rows}` |
| Offline | `{left: 25 rows, held: 25 rows}` from the device | The same useful local value, incomplete |
| Reconnect or watch rerun | Left rows disappear again | Left rows remain while the held component refreshes |

The online result is still incomplete: nothing recovers the 26th left row,
which was never delivered. Row counts abbreviate arrays; exact ids and
content define the acceptance fixture. The source-backed baselines are
[r2_n3_mixed_returned_history_uses_whole_server_or_device_answer](../snapback4/crates/snapback4-device/tests/search_merge/round2.rs)
and [the actual-client regression](../snapback4/packages/snapback4/test/retained-history.test.mjs).

### What changed from the first proposal, and why

The first proposal chose the right first slice — "compiler-proven
independent, cursor-free components, each replaced as a unit" — and then
planned the infrastructure of a slice it excluded. Per-value provenance with
interned dependency sets, a propagation rule for every operation, dynamic
execution identities, bounded provenance growth and new meter charges are
what *general* composition over joins and aggregates would need. For
statically independent components, which read site feeds which component is
a fact the binder can state, and "what did this component's reads cover" is
the runner's existing coverage flags, scoped. Three consequences:

- **No provenance in the runner, so no bytes and no meter delta.** The first
  proposal asked the device diet to measure provenance's wasm cost and to
  report its charges as a semantic delta. Coverage frames are a few dozen
  lines that save, reset and merge flags the runner already keeps.
- **No server change and no new disclosure surface.** The first proposal's
  server attached per-component outcomes to the reply and rightly flagged
  them as a disclosure channel "even when it contains only booleans". Here
  the server answers the original query exactly as today. Per-component
  coverage is computed only by the device, from the device's own state, and
  never leaves it.
- **The contract is one sentence, and it is the documented recipe.** *Each
  independent component of a returned record is answered by the host that
  would have answered it as its own query.* That is the separate-query
  workaround, performed by the client in one observation and one
  publication, so its semantics are already specified and already tested
  per component.

What is given up: the server's whole-query `complete` stands in for the
server components' coverage, so a composed read can report `complete: false`
because of a component the client discarded. That is conservative and
sound; a sidecar can refine it later behind its own disclosure analysis.
Shadow provenance as groundwork for general composition is not built; that
design, if an application ever needs it, starts from a residual-evaluation
proposal and not from annotations added now.

### Eligibility: the binder's component plan

A query is composable when the binder proves all of the following on the
lowered program, and records the plan with the operation's other compiled
execution facts:

1. It is a query, not native, not declared `held` (an explicit `held` query
   never acquires server fallback), takes no cursor and contains no scan
   that can mint or consume one; the first slice is cursor-free.
2. Its top level is bind-once `let`/`const` statements and `require` guards
   followed by one `return` of a record literal with at least two fields.
   No top-level branch, loop, assignment or early return.
3. Every top-level binding whose expression performs a read — a point read,
   `exists`, a scan, a merge, a page or recursive loop, a presence or capped
   count — is used, transitively, by exactly one returned field, which owns
   it. Bindings that read nothing may be shared.
4. No nested statement assigns, pushes or sinks a remainder into a top-level
   local: a block may mutate only what it declares.

The plan is the list of returned fields with the top-level statements each
owns. Guards belong to no component. Anything unproven — dependent branches,
cross-component values, mixed-origin joins and aggregates — has no plan and
keeps whole-query behavior and the separate-query recipe. `check --residency`
names a query's components so an author can see which shape was proven.

### Runtime: coverage frames on the device

With a plan, the device runner evaluates each owned statement and each
returned field inside a coverage frame: the flags that decide `complete`,
`unknown` and retained-only incompleteness are saved, cleared, observed for
that component, and merged back. Whole-query `data`, `complete`, `unknown`,
`retained`, `cut`, dependencies and meter outcomes are byte-for-byte what
they are today; the merge is the same union. A meter cap is monotone: a
component evaluated after the cap is incomplete. The device's reply adds
`components: {field: {complete, unknown, retained}}` only when a plan exists
and the guards' own frame is complete; an incomplete or unknown guard
withholds the plan and the query behaves as today. Helpers called from a
component are attributed by the active frame, not by their static site, so a
helper shared by two components needs no dynamic identity. Both stores run
the same frames.

### One client observation, with explicit consistency limits

The client applies to each component the routing rule it applies to a whole
query today, through one shared predicate, so a later change to that rule
(the bounds program proposes keying fallback on `unknown`) moves both:

1. Evaluate locally. If no component would route to the server, or none is
   retained, nothing changes: the local answer, or the whole server answer.
   Composition is never entered while a predictable write is unobserved; the
   local answer stands until it settles, as today.
2. Otherwise request the **original query** under its ordinary authorization
   and guards. The client submits no fragment, bypasses no `require`, and
   sends no retained row as authority. A refused original query remains
   refused; a reply that cannot be bound to the current incarnation is
   discarded by the existing check.
3. When the reply arrives, evaluate locally **again** and compose from that
   second observation: retained components from the device, every other
   component from the one server transaction. If the second observation no
   longer has a retained component, the server answer stands whole; if it no
   longer needs the server, the local answer stands. Either way there is a
   publishable value and no retry loop to bound.
4. Publish one `Read<T>` atomically, to a query caller or a watch, never a
   sequence of field patches.

The composed value is a product of two observations, **not one server
snapshot**, so it reports `fresh: false` and omits `since` until a sound
common meaning exists — deliberately more conservative than a caught-up
standalone retained read, and an explicit acceptance choice for the author.
`complete` is the conjunction of the server's whole-query word and the
retained components' frames; being retained is not proof of completeness.
`cut` is the server's: a retained-only frame has no meter or word cut by
definition, and no private site is named. `next` is absent. Offline, or when
the request fails, the client returns the whole local incomplete answer,
preserving left history; it never substitutes a remembered whole server
answer for an operation it would compose. Watch dependencies are the union
of both evaluations' tables plus held/left state, acquisition, link and auth
changes, with the earlier expiry scheduled.

### Authority, lifetime and disclosure

Unchanged in substance. Retained data stays under the delivered-history
policy: it grants no server access after leave, until-revoked rows are never
resurrected, and applied deletions, expiry, rejoin snapshots and store
replacement invalidate the local contribution because the second local
evaluation sees them. Composed results are ephemeral observations: no
durable per-query cache, receipts, range-coverage store or new sync
audience. The server's request pattern for a composable query is the
request pattern of today's fallback — one `POST /q/<name>` with the original
arguments — so worlds differing only in unreadable data remain
indistinguishable on the wire by construction rather than by analysis; the
qualification still compares them.

| Stage | Work | Exit evidence |
| --- | --- | --- |
| M0: specify the example | Pin exact expected ids, metadata and reconnect behavior for `both()`; add shapes that must stay ineligible | The before/after contract as tests that fail only on the composed rows |
| M1: plan and frames | Binder plan in the compiled execution facts; runner frames; the device reply's `components`; `check --residency` names them | Both-store differential: whole-query outputs and meter outcomes identical with and without a plan across the device suite and the corpus; adversarial shared helpers, discarded reads, guards, caps |
| M2: client composition | The shared routing predicate; the two-observation compose; watches | The ticket example through actual wasm and process queries and watches, online, offline and across reconnect, with the chosen `complete`/`fresh` words |

Acceptance covers zero rows and missing points, retained-derived scalars,
shared guards, mixed joins and aggregates declared ineligible, meter, page
and search cuts, pending-write settlement, and browser and SQLite reopen,
on the existing device tests, retention and client suites and the real
IndexedDB witness. Do not close the ticket because frames exist or the Rust
example passes: the composed query must preserve 25 exact left rows and
provide 26 exact held rows online through both client arms, and watches must
keep history across reconnect. The README sync paragraph and the sync card
change only when the behavior exists, and keep the separate-query recipe for
every shape without a plan.

Open decisions are whether `fresh: false` without `since` is the right card
for a composed read, and whether fixed independent components satisfy an
actual application — no independent builder has yet shown the recipe
inadequate, which limits priority, not correctness. Stop after three
unsuccessful correction rounds, or if qualification requires arbitrary
distributed evaluation; never broaden the slice silently.

## Proposal: secure client ID sources on every supported host

**Proposal status:** Draft, 2026-09-17; authored by Codex / GPT-6 at Charlie
Cheever's request. This is a focused client/host proposal, not an implemented
specification. No change to identifier authority or the server namespace is
proposed.
**Ticket:** [client ID clock and entropy](../issues/20260916-snapback4-client-id-clock-and-entropy.md).

### Evidence and recommendation

At `70a663c22285dc3a5278ca9ac13db01bbe05446b`,
[client.ts](../snapback4/packages/snapback4/src/client.ts) correctly increments
the 80-bit suffix within one logical millisecond and preserves monotonic order
through clock rollback. `freshEntropy` still uses `Math.random` if Web Crypto
is absent. The [Expo opener](../snapback4/packages/snapback4-expo/src/index.ts)
provides device/storage operations, not a randomness source; Expo Go intentionally
uses the online client without that custom device module.

Recommend a synchronous, explicitly bound ID minter with a cryptographically
secure host source, and an actionable refusal when that source is unavailable
or fails. Remove the silent fallback. Keep the existing 128-bit format, 26-digit
encoding, synchronous mint API and caller-supplied retry IDs. No server round
trip, new ID grant, reserved slice or seeded application PRNG is needed.

A secure random initial suffix reduces accidental collision risk. Incrementing
that suffix makes neighboring IDs predictable; IDs remain names, never bearer
capabilities or session secrets. This proposal does not promise unguessability
or global ordering across processes.

### Proposed SDK seam

Extract the current algorithm into a small minter whose state and byte supplier
are fixed at construction. Conceptual API names below are proposed, not exported
by the current package:

```ts
type FillRandom = (bytes: Uint8Array) => void;
type IdMinter = (now?: number) => string;
// One private timestamp/suffix state per returned minter.
createIdMinter(fillRandom: FillRandom): IdMinter;
```

The existing `mintId(now?)` export delegates to one module-default minter backed
by the host's Web Crypto. Existing browser/Node callers keep the same signature
and shared sequence. Client options gain one optional `ids: IdMinter` host seam;
the online and local tiers use it for every implicit intent and row ID. An app
that mints an explicit ID uses the same minter instance. Default clients share
the default instance; a host adapter exports one reusable instance rather than
constructing a new sequence per call or per component render.

Monotonicity is within a minter. Explicitly constructed independent minters do
not gain a shared clock or ordering promise. Durable FIFO remains the outbox's
job. Generated helpers, React hooks, actions, local prediction ID supplies and
fixtures must all use the selected source; a single stray imported global mint
would leave the native failure path open. Caller-provided IDs are validated by
the existing wire contract and never replaced because the host RNG is missing.

A byte supplier is trusted host code, not a security boundary against the app
itself. The SDK cannot statistically prove a callback is cryptographically
secure. First-party suppliers have pinned implementation/provenance and host
tests; deterministic suppliers are explicit test fixtures, never selected from
a production environment variable.

### Host choices and the Expo distinction

| Host | Recommended supplier | Qualification required |
| --- | --- | --- |
| Supported browser and worker | Bound `globalThis.crypto.getRandomValues` | Real realm with success, missing API and provider exception paths |
| Supported Node runtime | Its Web Crypto implementation | Pinned Node runtime and packaged import paths |
| Expo Go and native Expo builds | An Expo-specific adapter around `expo-crypto.getRandomValues` | Actual supported SDK/runtime combinations, independent of custom device availability |
| Other headless/custom hosts | Explicit secure supplier | Host owns its cryptographic provenance; missing supplier refuses |

The [Expo Crypto documentation](https://docs.expo.dev/versions/latest/sdk/crypto/#cryptogetrandomvaluestypedarray)
documents `getRandomValues` as synchronous secure filling, and the package as
included in Expo Go. Its nearby `getRandomBytes` documentation explicitly
permits a development-time `Math.random` fallback. The
[upstream implementation](https://github.com/expo/expo/blob/main/packages/expo-crypto/src/Crypto.ts)
shows these distinct paths. These sources were checked on 2026-09-17; the
implementation must pin and inspect the actual supported SDK package, rather
than infer a release guarantee from upstream main.

Put the Expo source in an Expo-only entry point, with an SDK-compatible declared
`expo-crypto` dependency/peer and a clear install diagnostic. Do not pull native
imports into the browser/Node entry or mutate `globalThis.crypto` as a side
effect. Templates pass that same adapter to both the native-device client and
the Expo Go online fallback, and import its minter for explicit IDs. A missing
custom Snapback device module must not disable secure ID minting in Expo Go.
The minimum supported Expo pin and dependency placement are implementation
choices to resolve from the template/package compatibility check.

An asynchronous entropy pool is unnecessary for the selected synchronous API.
If a supported host actually has only asynchronous secure randomness, it needs
an explicit asynchronous setup step and exhaustion behavior before admission;
it must not refill with weak bytes. That host extension is outside the first
implementation.

### Failure and state guarantees

Obtain new randomness into a temporary array before updating timestamp/suffix
state. Copy provider-owned data into minter-owned storage; a retained mutable
buffer cannot later change the sequence. Provider failure, invalid time,
reentrant minting or 80-bit exhaustion leaves the prior valid state intact.
Never advance the logical clock merely to conceal entropy exhaustion.

Expose one stable SDK-local failure for unavailable/failed secure randomness,
with host setup guidance and no byte values. The exact diagnostic name must be
chosen with the existing refusal vocabulary. A direct `mintId` throws it before
returning an ID. An SDK write that cannot mint must fail before prediction,
localStorage journal capture, durable admission or network send, with no pending
acknowledgement and no partial side effect. Reads, authentication and retries
of already identified intents need not depend on fresh randomness from this
minter. Server/session-token generation remains on its existing secure source.

### Alternatives, rollout and validation

Keeping `Math.random` and documenting it fails the ticket. A global polyfill
creates import-order coupling; requiring the custom Snapback native module
breaks Expo Go's supported online tier. Server-minted IDs break offline admission.
Changing the wire format or treating IDs as secrets solves a different problem.
The explicit host source is the smallest compatible architectural change.

Implement the extraction and state tests first, then thread the optional source
through every implicit mint site. Add the Expo adapter and template wiring,
qualify both Expo client tiers, and remove the fallback in the same delivered
change. Update the client card/package documentation with the required provider
and failure behavior. Existing IDs, journals, receipts and outboxes require no
migration; package publication follows the normal qualified path later.

Acceptance includes deterministic tests for same-millisecond bursts, rollback,
maximum timestamp, suffix carry/exhaustion, thrown/partially written buffers,
reentrancy and failure followed by successful retry. Spy on `Math.random` to
prove it is never called, including development mode. Confirm no local/device/
network admission after an RNG failure, and that replay of an existing ID still
works. Run import/bundle checks so browser consumers acquire no Expo dependency.

Qualify browser, Node, Expo Go online, and supported native Expo builds with the
actual selected source; include development/debug modes that previously induced
weak fallback. A mocked crypto object alone does not qualify those hosts. Record
bundle-size cost against existing budgets and measure burst mint latency. Close
the remaining ticket only after every advertised host has secure minting or an
explicit supported failure path. The choice of secure source is recommended;
its exact host/package qualification remains work, not evidence claimed here.
