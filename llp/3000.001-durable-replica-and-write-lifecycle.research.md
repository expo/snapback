## Review finding (0.0.16 baseline)

The shipped local client stores predictions directly over confirmed rows and
uses an outbox that mostly records touched ids. That representation cannot
reconstruct the last confirmed state after a refused update or delete, nor
reliably preserve overlapping predictions. Snapshot replacement, stream
application and adapter transactions also lack a shared atomicity contract.
The vocabulary on the card is small, but the state transitions behind it are
not yet one coherent durable protocol.

This is a focused extension of [LLP 3000 §9](./3000-snapback4.explainer.md#9-architecture-and-code-review-2026-09-12),
not a proposal to return to per-query receipts or a second public client model.

## Evidence and confidence

At the review's 0.0.16 baseline, independent probes reproduced:

- A failed snapshot replacement clears rows but retains the old watermark.
- Two simultaneous syncs can apply watermark 3 followed by watermark 2.
- A SQLite write can resolve successfully, then disappear when an unrelated
  overlapping write rolls back. The memory adapter does not roll back at all.
- A refused update deletes a previously confirmed row locally. A subsequent
  successful sync leaves the row missing because the refusal made no server
  commit to replay. The local read nevertheless reports complete and fresh.
- The id mint drops its timestamp; sorting the outbox by these ids does not
  preserve admission order.
- A transient HTTP 503 leaves a pending write unsent after transport recovery
  and an explicit successful sync.

These are tested outcomes, not simulated possibilities. Additional concerns
below follow from code paths and need focused execution during implementation.
The original review examined `src/replica/{replica,store,sqlite,interpreter}.ts`.
Those historical TypeScript files were subsequently replaced. Current owners are
[local.ts](../snapback4/packages/snapback4/src/local.ts), the Rust
[device](../snapback4/crates/snapback4-device/src/device.rs), its
[store interface](../snapback4/crates/snapback4-device/src/store.rs),
[SQLite adapter](../snapback4/crates/snapback4-device/src/sqlite.rs), and shared
[interpreter](../snapback4/crates/snapback4-core/src/engine/runner.rs).

## A state model to make explicit

Five things have different lifetimes: the last committed partition, its
watermark/generation, admitted writes in a durable order, the visible result
of applying those writes speculatively, and terminal write outcomes. The
current representation collapses the first and fourth, and retains terminal
outcomes only in memory after removing outbox entries.

That is particularly problematic when write A and write B touch the same row.
Acknowledging A can overwrite B's prediction. Refusing A can remove B's row.
A maintain's speculative updates are not all represented in the touched-row
list used for failure cleanup. Generation reset clears predictions, while
startup replay and ordinary catch-up have different reapplication behavior.
A write admitted offline returns `pending`, but the card exposes no durable
way to find its eventual refusal after the submitting call or process is gone.
These code-traced cases need a deliberate policy, not more cleanup branches.

## Alternatives worth evaluating

| Representation | What it makes easy | Main tradeoff |
|---|---|---|
| Confirmed base plus ordered operation overlays | Drop one refused operation and deterministically replay survivors; incoming sync cannot erase the base needed for rollback | Replay cost and dependency semantics must be bounded; maintains must share the overlay transaction |
| Confirmed base plus undo/rebase records | Cheap simple rollback and incremental updates | Overlapping writes, deletes and maintains require complete before-images and careful rebase logic |
| Durable outbox with prediction only where eligibility is proven | Smaller first implementation; server remains available for ineligible operations | Some writes have pending state without an immediate row prediction; UI must explain that state using the existing card |

The third option can be combined with either of the first two. Keeping the
confirmed base recoverable is more important than predicting every mutation.
No option should make a local refusal final merely because the device lacks
an online-only row or data beyond its horizon.

## Required decisions

- Define the store transaction contract for rows, indexes, metadata and side
  tables. Separate asynchronous callers are never nested transactions merely
  because they share a driver object. Snapshot replacement and generation
  reset must use that same contract.
- Define one owner or compare-and-apply rule for stream application. A
  response is checked against the persisted current state when it commits,
  not only the watermark captured before its request began.
- Give admitted writes a durable sequence independent of random ids and wall
  clocks. Specify dependencies, terminal versus retryable refusal, and retry
  scheduling across restart.
- Decide how a caller observes the eventual result of a write admitted while
  offline. The present `Promise<Write>` and in-memory settlement map cannot
  provide durable outcome discovery alone.
- Specify admission failure: transaction failure must leave neither partial
  prediction nor a false `pending` acknowledgement. A caught-up replica does
  not establish freshness of a prediction or restore lost confirmed rows.
- Define rebase order around snapshots, schema generations, acknowledgements
  and multiple outstanding writes, including maintained values and deletes.

## Verification that addresses this gap

The Rust simulator's replica serializes sync requests, uses an ordered
counter for operation ids, stores snapshots atomically as a blob, and keeps
ack/failure state that the shipped TypeScript client does not. Its seven
invariants establish useful properties of that model, but do not establish
that the adapters and lifecycle above implement it.

Use the same transition examples against the actual TypeScript lifecycle and
memory/IndexedDB/SQLite adapters: fail admission; crash between replacement
steps; reorder two responses; acknowledge A after predicting B; refuse A;
retry after 503; reopen with pending writes; change generation. Preserve the
small existing test entry point. [LLP 3000.003](./3000.003-one-semantics-and-credible-verification.research.md)
considers how to share those scenarios without adding a parallel model that
silently supplies the missing safeguards.

## Implementation follow-up

The author's request to fix the tickets produced a confirmed-base and ordered
replay implementation in both shipped device arms. These are implemented
choices for R05–R15, R28–R29, R31 and R37, not acceptance of all the broader
outcome-discovery proposals above.

A store transaction now owns rows, indexes, metadata and side tables.
Independent SQLite/Expo callers queue; Expo uses its transaction-owned
connection when available. Memory transactions use copy-on-write containers
and isolate mutable values, so a failed transaction cannot alter committed
rows or metadata without copying the entire store for each small write.
IndexedDB waits for transaction completion.

Snapshots stage in a separate table while queries continue to see the old
committed partition. Snapshot rows stay staged through a log catch-up to a drained watermark;
only its final transaction replaces rows and watermark. This repairs rows
read on either side of a concurrent server commit without waiting for a
quiet server.
A persisted owner, generation, watermark and send revision bind continuations;
repeated final pages, competing owners and stale continuations are refused.
Stream responses check persisted state when applied, and same-client sync
requests coalesce. Backend/schema adoption also uses the store queue.

Prediction records include confirmed before-images for source rows and
maintains, a durable submission order, admitted IDs, viewer and time. A
refusal restores the base and replays surviving writes in order in one
transaction. Replay cannot invent extra IDs after the request's ID supply
has been fixed; an expanded prediction is withdrawn while its durable write
remains queued. Snapshots, deltas and acknowledgements share this rebase
path. Native and TypeScript tests include updates, deletes, aggregate changes,
overlapping writes and reopening before settlement.

A bounded `/sync` correlation of pending IDs to committed operation sequences
prevents a received authoritative write from being predicted a second time
while its mutation response is delayed or lost. The write remains queued
until its full outcome is known. A drained stream advances through the
current commit even when a no-op or online-only write has no viewer events,
so those terminal entries can retire too. Network ordering covers same-client sends
versus sync, while a durable send revision detects another store owner's
intervening send inside the apply transaction. Capturing pending IDs and that
revision is atomic. This guard matters even when the admitted write was absent
from the original sync request. Long-lived outcome discovery after the outbox
entry is removed remains an open API question.

Transient failures retry the same IDs with bounded backoff without requiring
an observer. Close waits for owned work and stops retries. Online query
responses retain dependencies; denied observations retain conservative
dependencies, and poll progress is separate from a query's observed sequence.
Missing online-only data or uncertain horizon coverage routes work to the
server when reachable, or returns the existing typed unknown/refusal offline.
An unavailable row is not sufficient evidence for a terminal local mutation
refusal. A supplied token can establish the viewer from authority.

React resources survive Strict Mode's setup/cleanup replay. A changed page
boundary recreates dependent pages to the requested depth; combined results
use the conjunction of completeness/freshness and the oldest observation time.
Concurrent mutations track their separate lifetimes. Reference apps dispose
late-opened clients and preserve independently edited drafts on settlement.

Native startup probes the read-only sync receipt before starting queries,
followers or outbox work, including an offline reopen. An older Expo 0.1.14
module can otherwise open a store but refuse the newer protocol while its
JavaScript client appears online. An unsupported or malformed receipt now
fails startup with `E_NATIVE_VERSION` and update/rebuild guidance; every probe
failure closes the native handle, and operational errors retain their original
diagnostic. Reloading JavaScript cannot replace an installed native binary.
The actual current-core online/offline control and incompatible-core cleanup
cases pass in the client suite; native publication still requires rebuilding
the generated XCFramework and application binary.

The actual TypeScript clients and Memory/SQLite/IndexedDB adapters, native
SQLite device and React development runtime have focused regressions in the
existing test entry points. This is not a process-kill or physical iOS disk
failure experiment. Durable terminal outcomes, limits on replay work and a
more compact representation of large outboxes remain research.

## 2026-09-16 review: ownership and lifecycle guarantees

The current review is pinned to `a0d48a4` (0.2.26). Current web writes have
transactional admission plus a bounded synchronous localStorage journal
when an exclusive Web Lock is held. The old pagehide-loss hypothesis is
therefore too broad. Muse's supplemental pass confirms the remaining split:
without `navigator.locks`, `web::claim` opens the shared persistence name
with `exclusive:false`, disabling journal capture/recovery and orphan
adoption while allowing multiple memory devices to mutate one IDB database.
See [the ownership ticket](../issues/closed/20260916-snapback4-web-store-without-locks.md).

Choose one durable ownership contract. The smallest safe change requires a
usable cross-context lock for built-in browser persistence and returns an
actionable opening refusal when unavailable. A portable implementation could
instead use a transactionally fenced owner in IndexedDB; a timed lease alone
is insufficient because suspended tabs can wake and write stale state.
Per-tab stores without an adoption/ownership protocol avoid direct collisions
but can strand admitted work permanently. A SharedWorker owner is another
component-level redesign, with its own platform and lifetime constraints.
No browser-storage rewrite is selected here. Qualify two simultaneous tabs,
suspension/revival, closing during admission and reopening after a crash.

The online asset path separately demonstrates a small lifecycle hole: a
fetch admitted before `close()` can resolve afterward with a new usable blob
URL. Lead reproduction delayed a 13-byte response across close. Fence both
success and refusal completion on current client/credential state and revoke
obsolete object URLs; the local tier already follows that shape. This does
not promise recall of media already delivered to an authorized viewer.

Client IDs also mix ordering with time: each mint increments the timestamp
by at least a millisecond, so a burst creates future `minted_at` values. Order
can instead advance the 80-bit entropy suffix at a fixed logical timestamp.
Clock rollback still requires monotonic logical time, but throughput must not
invent one extra millisecond per ID. Missing secure entropy is a distinct
platform decision: browser/Node and native Expo need an explicit supported
source, not silent Math.random. The [ID ticket](../issues/20260916-snapback4-client-id-clock-and-entropy.md)
tracks both with separate validation obligations.

The 2026-09-16 repair candidate implements the explicit ownership contract:
built-in IndexedDB requires Web Locks, and custom Persistence providers must
supply claim(name, alternate) for both opening and orphan recovery. The memory
provider supplies a provider-local owner set. It also fences late online asset
completion and increments client ID entropy within one logical millisecond.
Secure entropy on hosts without Web Crypto remains open; these IDs must not be
treated as secret capabilities. Portable durable ownership without Web Locks
remains a separate design and platform-qualification question.

Follow-up qualification exposed recovery against stale cached rows. A surviving
executable journal record now uses replay-candidate admission: successful local
prediction remains, while a local refusal leaves an unpredicted durable intent
for server decision. Primary and orphan recovery share this rule; it preserves
offline custody without a new device API. Custom alternate claims are also
validated for the documented `:tab-` namespace and discovery/removal methods.
Invalid claims release ownership and refuse before device admission. The living
contract and cancellation limits are in LLP 3000.007 §20.4.

## Proposed composition of retained and authoritative reads

**Planning status, 2026-09-16:** proposed, not accepted or implemented.
Charlie requested a plan for the
[mixed left/held query](../issues/20260914-snapback4-mixed-left-held-query-loses-retained-rows-online.md).
This extends the replica/read lifecycle here; the accepted fallback behavior
remains in [LLP 3000.007 §18.2](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md#18.2).
The completed placement increment,
[LLP 3000.008.001 §4](./3000.008.001-understandable-data-placement.rfc.md#4-read-and-write-outcomes),
explicitly deferred this mechanism. Source inspection used `18c8f5daf`;
no new runtime experiment or application requirement is claimed.

### The result the design must make possible

The existing regression has two groups with 26 messages each and an
acquisition horizon of 25. After leaving one group, neither host can
produce the desired combined value alone:

| Observation | Current result | Proposed result for the independently composed case |
| --- | --- | --- |
| Online | `{left: 0 rows, held: 26 rows}` from the server | `{left: 25 retained rows, held: 26 authoritative rows}` |
| Offline | `{left: 25 rows, held: 25 rows}` from the device | The same useful local value, incomplete |
| Reconnect/watch rerun | Left rows disappear again | Left rows remain while the held component refreshes |

The desired online result is still incomplete: it cannot recover the 26th
left-group row that was never delivered. Row counts abbreviate message arrays,
not proposed Quarry syntax. Exact IDs/content, rather than lengths alone,
must define the future acceptance fixture.

The source-backed baseline is
[r2_n3_mixed_returned_history_uses_whole_server_or_device_answer](../snapback4/crates/snapback4-device/tests/search_merge/round2.rs)
and [the actual-client regression](../snapback4/packages/snapback4/test/retained-history.test.mjs).
The [local runner](../snapback4/crates/snapback4-core/src/engine/local.rs)
returns query-wide unknown/retained flags; the
[client](../snapback4/packages/snapback4/src/local.ts) substitutes one whole
server answer. OR-ing a retained flag would mask missing held coverage;
merging lists by row ID would corrupt arbitrary derived results.

### Alternatives and recommended first scope

| Approach | What it resolves | Remaining cost |
| --- | --- | --- |
| Keep separate queries | Today's supported workaround; each has honest coverage and cursor ownership | Application coordinates the two observations |
| Mark the entire query `held` | Keeps the device's view online and offline without server fallback | Cannot supply the held group's missing 26th row |
| Compose compiler-proven independent return components | Resolves the ticket's record-shaped example using per-value provenance | New runtime metadata, server/client coordination and disclosure analysis |
| General distributed query execution over retained and current facts | Could evaluate mixed joins, aggregates and control flow | A substantially larger language/execution/consistency contract |

Recommend the third as a bounded first proposal. A screen showing retained
history beside a current held conversation is a concrete acceptance example,
but no independent application has yet demonstrated that the separate-query
recipe is inadequate. That limits priority, not the usefulness of a design.
Do not equate solving that example with arbitrary transparent composition.

The first candidate accepts a fixed returned record with independently
computed, cursor-free components. The compiler must prove that replacing a
component cannot change another component's data, control flow, guard,
cardinality or position. A component may be a whole list or a derived scalar;
its provenance describes the computation, not merely its returned row IDs.
Data-dependent record shape, cross-component dependencies, opaque native
reads and unproven cases retain whole-query behavior and the documented
separate-query recipe. Explicit `held` queries never acquire server fallback.

### Provenance must include computation and absence

Use internal annotations alongside the shared Rust values, not application
row fields. Intern compact dependency sets per evaluation so copying a value
does not copy an ever-growing graph. Each contributing read records its
semantic source, invocation and coverage. Backend/program identity, viewer,
device revision and observed server state bind the evaluation as a whole.
Provenance is evidence about how a value was computed, never a grant to read.

| Operation | Required propagation |
| --- | --- |
| Field projection, assignment, helper return, shape construction | Carry the producing value's dependencies; retain field structure where independence is proved |
| Scan/page, empty list, absent point read, false `exists`, zero count | Carry coverage and the deciding read even when no row is returned |
| Filter, branch, early return, `require`, loop bounds and dynamic keys | Carry control dependencies into every affected output; a discarded value may still control a visible result |
| Sum/count/group, concatenation, sort, distinct and join | Union source, membership/order and control dependencies; replacing input rows requires recomputation, not grafting |
| Repeated helper/loop execution of one site | Identify each dynamic execution; a static site ID alone cannot match occurrences across hosts |
| Time, expiry, pending values, unknown native/server facts | Carry the dependency or conservatively make the component ineligible |

The compiler's component plan supplies stable result-slot identities. It must
not match dynamic reads between server and device by ordinal occurrence:
different holdings can take different branches and loop counts. Initial
composition operates only at statically proven independent slots, each
replaced as a unit. Mixed-origin aggregates and joins are one dependent
component and remain unsupported in that first slice.

Bound provenance growth before allocating it. In shadow mode, account for
its cost separately and stop tracking at the bound without changing existing
results or meter outcomes. In active composition, charge the work to existing
resource ceilings. A tracking overflow makes composition unavailable; it
never silently drops a dependency and certifies independence. Adopting these
new charges is a separately reported semantic delta, with deterministic
behavior on both stores and a measured WASM cost.

### One client observation, with explicit consistency limits

For an eligible operation:

1. Evaluate locally and freeze its candidate data/provenance under the
   current viewer, auth/client incarnation, store identity, generation,
   acquisition revision, held/left map, prediction revision and clock.
   A never-acquired or reset store contributes no authoritative local facts.
2. If a component needs current coverage, request the **original query**
   under its ordinary server authorization and guards. The server may attach
   internal component outcomes for the compiler's plan. The client cannot
   submit arbitrary fragments, bypass a `require`, or send retained rows
   back as authority. A refused original query remains refused.
   The reply must identify its store, generation, program/component-plan
   version and server observation, and belong to the captured operation and
   arguments. A matching local capture alone cannot establish that a remote
   reply came from the same backend incarnation.
3. Select a whole local component only when its dependencies are valid held
   facts/retained history and it has no independent unresolved input. Select
   a whole server component only when the plan proves that substitution
   cannot change retained siblings. Constants may be shared. The first
   implementation composes no pending prediction with an authoritative
   component; it preserves the current local answer while prediction settles.
4. Before publication, revalidate the captured identities and relevant device
   revision. Revoke/regrant, reset, adoption, sign-out, prediction or expiry
   during the request invalidates the candidate. Publish one complete
   `Read<T>` value atomically to a query caller or watch, never a sequence
   of in-place field patches.

Server components come from one server query transaction. Retained components
come from the frozen device observation. Together they are a product view
across two observations, **not one server snapshot**. The first proposal
therefore reports `fresh: false` whenever it composes retained and current
components; it cannot truthfully claim that the whole result reflects the
server now. This is deliberately more conservative than a caught-up standalone
retained read. Do not assign the server reply's time to the retained component
or fabricate a single `since`; omit it until a sound common meaning exists.
Whether this conservative card is sufficient is an explicit acceptance choice.

Bound discarded attempts rather than spinning until writes stop. Retry once
on a changed capture; a watch remains dirty for its next ordinary rerun.
After churn or a transport failure, return the current whole local incomplete
answer if usable (or the existing loading/refusal outcome), preserving left
history. Do not return the destructive whole-server answer for an operation
already selected for composition. Obsolete-session data is never reused.

Whole-result `complete` is the conjunction of selected components' actual
coverage and all governing control/guard obligations, including independent
meter, non-uniform, page-loss and word-search reasons. Being retained is not
proof of completeness. `cut` may expose only the current card's permitted
reason; it must not identify a private contributing site. Keep the first
slice cursor-free: a single outer `next` cannot advance two unrelated
collections. Cursor composition needs its own design bound to operation,
arguments, identity, generation, component and observation.

Dependencies for watch invalidation include all relevant tables from both
evaluations, including absent inputs and control reads, plus held/left state,
acquisition, link/auth changes and expiry. Schedule the earliest applicable
expiry and revalidate before publishing a delayed reply. Server-dependent
components use the existing change-observation path even if their tables are
not synced. An unobservable dependency makes the operation ineligible.

### Authority, lifetime and disclosure

Retained data stays under the existing delivered-history policy. It grants
no server access after leave; until-revoked rows are never resurrected by
composition. Applied deletions, expiry, rejoin snapshots and store replacement
invalidate the relevant local contribution. Computed results remain
ephemeral observations, with no durable per-query result cache, receipts,
range coverage store or new sync audience.

Additional component coverage is a potential disclosure channel even when
it contains only booleans. Begin with eligible uniform, scope-pinned reads
and keep private traces, costs, site IDs and hidden cardinalities off the
wire. Qualify pairs of worlds differing only in unreadable data, comparing
the entire exposed outcome, fallback/request pattern, cursor behavior and
expiry scheduling. Do not infer safety from the current whole-query
`complete` contract. A scope guard or a native dependency the plan cannot
model prevents composition.

### Implementation sequence and acceptance

| Stage | Work | Exit evidence |
| --- | --- | --- |
| C0: specify the example | Preserve the current regression and define exact expected identities, metadata and reconnect behavior | Before/after contract and a fixed eligibility boundary, including `held` |
| C1: shadow provenance | Track values, absence and control without changing fallback | Both-store differential; adversarial repeated sites, helpers, discarded reads and branches; resource/byte overhead |
| C2: independent components | Compiler plan, ordinary server query sidecar and atomic client publication for the fixed-record slice | Ticket example through actual wasm and process queries/watches, with correct incomplete/stale words |
| C3: qualify interleavings | Delay/reorder server replies across lifecycle and persistence events | No old-identity publication, retained loss, false completeness or missed invalidation; actual offline reopen |

Acceptance covers online/offline/reconnect and watch transitions; zero rows
and missing points; retained-derived scalars; reversed evaluation order;
shared guards; mixed joins/aggregates that must be declared ineligible;
meter/page/search cuts; expiry and revoke/regrant while a response is delayed;
pending-write settlement; interrupted acquisition; generation/store reset;
sign-out/rotation; and browser/SQLite reopen. Use existing device tests,
retention/client suites, simulator and real IDB witness. Extend the current
sync/read/residency cards only when the new behavior exists.

Do not close the ticket merely because provenance is stored or the Rust
example passes. The supported composed query must preserve 25 exact left
rows and provide 26 exact held rows online through both client arms; watches
must preserve history across reconnect; coverage and consistency must match
the chosen card contract. Document remaining unsupported query shapes.
General joins/aggregates require a later residual-evaluation design and
cannot be claimed by this acceptance.

Open decisions are whether fixed independent components satisfy an actual
application, whether the conservative freshness word is sufficient, and
whether provenance fits the device's resource/byte budget. Stop after three
unsuccessful correction rounds or if qualification requires arbitrary
distributed query execution. Preserve separate queries as the supported
recipe; do not silently broaden the first slice or accept a different
fallback contract on the author's behalf.
