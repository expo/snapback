## Implementation selection (2026-09-10)

The user commissioned revision and feasible implementation after independent
review. Implementer: Codex, 2026-09-10. The first slice is **inert presentation
defaults only**: identity selection for typed original rows. An array's element,
or a composite's explicitly selected `rows` element, must extend `ItemRow` to
omit `select`. The exact row type is preserved; wrappers, nullable elements, and
non-row sources still require their explicit selector. The default returns the
same object, never a copy; existing query-image provenance still decides whether
that object can supply observation or prediction proof.

Explicit tables, selectors, ordering, membership, drafts, and `withHistory`
remain available and own their existing meaning. Table inference from consistent
authored mutation targets was considered and deferred: the current shared chat
declaration already names its table once, so inference would delete one app line
while adding target-ambiguity rules and runtime bytes. The shipped query sources
still contain `{ message: Row | null }` wrappers; their explicit selectors are
load-bearing, not identity boilerplate. This slice claims no template deletion.
Never guess table ownership from an `id` string or a runtime row's fields.

Do not synthesize companion queries, change certification, add subscriptions,
or emit a new runtime metadata graph in this implementation. Generated `Op`
references are currently inert name proxies, not descriptor objects; therefore
the review suggestion to simply read table/order metadata from them is not an
existing implementation path. The initial design below is retained as deferred
research, not the scope commissioned for this pass. Reopen compiler derivation
only with post-1019 examples demonstrating substantial net app-code deletion
and an independently reviewed authorization-preserving derivation. The existing
chat `belongs` callbacks and fallback mapping to `{ conversationId, c: null }`
remain explicit and unchanged; the fallback head is not the primary cursor.

Selected-slice verification (2026-09-10): all 44 checks in `client-items`,
`client-history`, and packaged `typing` passed. These cover raw and composite
identity selection, exact row/draft inference, compile-time refusals for missing
tables/selectors, explicit null filtering and reverse order, original-image
proof versus computed lookalikes, and the unchanged history/cursor lifecycle.
The package build passed; its guide uses 79,078 of the existing 98,304 bytes.
The fixed five-root local runtime remains 84,994 gzip bytes on this lane's
baseline (item presentation is outside those roots); the packaged
`client-runtime.mjs` grows by 3 gzip bytes, 90,740 → 90,743. Measurements used
Node 24.18.0, esbuild 0.25.9 and gzip level 9. Integration measures its own total.
An earlier concurrent rebuild removed the generated declarations while the
typing tests were reading them; the complete rerun after the build passed.
That was test orchestration error, not a product behavior change.

## 1. Outcome and scope

Adding a count or preview to a message query should preserve the ordinary
downloaded-message presentation without requiring the author to write another
history query and repeat its table/selector/order relationship in TypeScript.
The compiler can propose those relationships where its checked graph proves
them. Product-specific draft contents and ambiguous page membership remain
explicit application choices.

The initial design is a Draft amendment to LLP 1018.006's authored fallback,
not an admission of partial scalar values. Design author: Codex, 2026-09-10;
the selected implementation and its narrower scope are recorded above. LLP 1019
retains delivery-schema ownership.
Common item labels already belong to LLP 1018.003.001 §5 and are not assigned
again here. No new per-field `unheld` type, public query builder, or client
query planner is proposed.

## 2. Current work that can disappear

`templates/chat/shared/thread.ts` repeats the message table, row path, reverse
order, create scope, and a thread fallback around `conversationView`.
`guide pagination` records why: missing count authority makes the composite
partial. LLP 1018.006 correctly selects an independent history snapshot and
never copies its receipt onto the unusable composite.

Retain that semantic boundary. Remove authored repetition by deriving a
normal companion query and a finite correspondence from the same bound graph.
The entire online composite still executes atomically and publishes one
receipt. The fallback remains a separate evaluation with separate authority.

## 3. Derivation and certification

### One supported shape first

Recognize a composite with exactly one returned, cursor-bearing page, possibly
under a fixed record path. That page must preserve original row identity or
select one original joined row through a statically known path. Order and
cursor provenance come from the existing certifier, not object inspection.

Starting at the selected row expression, derive a closed executable slice:

1. Keep all transitive argument, binding, key, branch, and read dependencies
   needed to evaluate that page, preserving evaluation order and single
   evaluation of authored bindings.
2. Preserve every authored `require`, refusal, and control dependency that
   gates reaching that return. A requirement involving the unavailable count
   cannot disappear merely because count is not displayed in the fallback.
3. Include table/rule checks and the selected joined row's read authority.
   A row path is not permission to disclose it.
4. Refuse derivation when the slice is ambiguous, depends on unsafe effectful
   setup, has multiple candidate pages, or cannot preserve the guards. Keep
   the explicit existing `withHistory` path with a sourced explanation.

Lower the slice ahead of time to an ordinary read-only program in the existing
generation and independently certify it in Rust. Its internal name is compiler
owned and excluded from authored-name collisions. "Internal" supplies no
privilege: serving it uses ordinary session admission, rules, ceilings, trace,
and receipt production. No new control route or hidden-row access exists.
Bind the primary/companion relation and its derived descriptors into certified
generation metadata. A client cannot supply or edit the relation as authority.

The companion returns the eligible page and receives its own cursor contract.
It is not extracted from a failed twin execution's partial memory and does not
copy the primary's sequence or completeness label. Its query code and types
live in the existing ignored build output, never committed generated source.

### Presentation facts

The same relation can supply the table, original-row selector path, and order
to `defineItems`. Build the actual selector once from validated descriptors;
do not search arbitrary returned JSON or match a computed lookalike by `id`.
Existing per-image observation and semantic mutation-target proofs still
decide pending action retirement.

Create membership is derived only when the target table, query prefix, and
mutation's inserted key expressions establish an exact argument relationship.
An unknown branch, computed key, multi-target write, or unresolved relation
requires the current explicit `belongs` callback. Do not guess from operation
names or from whichever row happens to match at runtime. Available mutation
targets are still chosen by the author when several operations could create,
edit, or remove the same rows. Draft content is presentation and stays authored.

Proposed source example, not current syntax or a working guide snippet:

```ts
const conversationItems = defineItems(api.messages.conversationView, {
  create: { target: messageWrites.create, draft: args => ({ body: args.body }) },
  update: { target: messageWrites.update },
  remove: { target: messageWrites.remove },
});
```

The omission of `table`, `rows`, `select`, `order`, `belongs`, and `withHistory`
is legal only for independently proven relationships above. The generated
types require explicit fields when derivation is unavailable. This is one
entry point with checked defaults, not a second automatic client profile.

## 4. Snapshot law and lifecycle

Apply LLP 1018.006's eligibility exactly: only a primary receipt marked partial
can activate history. Denial, refusal, reset, account change, and unsupported
primary execution do not become fallback permission. Loading and raw held
composite data without a receipt keep their existing meaning.

Observe the companion through the existing shared subscription owner. On a
usable primary, release fallback activity. On transition to eligible partial,
reuse any independently acquired companion answer, otherwise evaluate/query it
normally. Do not add an always-mounted fallback for every query in the app.
Late answers cannot revive history after denial or an account transition.

`data` is the whole usable primary result or undefined. History can supply
items, never the count or preview. Its receipt, freshness, and continuation
belong to history. Root `next` is never copied from a different snapshot. If
the common UI needs history pagination, it follows history's own continuation
through that existing observation; it cannot make a partial primary complete.
Retained-owner-page rules and predicted-overlay invalidation remain unchanged.

One companion generation binds one primary generation. A successor replaces
the relation through existing generation reset/revalidation. Matching numeric
sequences do not establish coherence between independently evaluated queries,
especially when their clocks differ.

## 5. Acceptance and limits

Prototype on the final LLP 1019 chat query shape, and on a non-chat list with
an independently authorized aggregate. Compare full React and Expo application
work, including bindings, fallback queries, root observers, and draft code.
Remove the authored duplicate fallback only when the generated relation proves
the same behavior. No reducer, copied array, or hidden extra UI cache may replace it.

Required controls: partial count authority; absent versus hidden aggregate;
guard depending on count; nested record and aliases; branch-dependent page;
clock-dependent read; optional joined row; denial after readable history;
successor while history is in flight; account switch and offline cold restart;
multiple candidate pages; computed objects with an original row's ID; capped
page omission without target observation; predicted create/edit/removal; primary
and history continuations with different provenance. Compare against explicit
`withHistory` under the same real-owner/carrier journeys.

Record compiler/check latency, generated program size, number of live requests,
complete runtime bytes, and application decisions removed. A common query must
not acquire an unconditional second subscription. If safe slicing brings no
material application reduction, retain authored history and limit the change
to proven table/selector/order defaults.

Before implementation, independent review must verify that keeping all gating
requirements is sufficient for the supported slice. Any proposal to drop a
guard or publish individual fields from an incomplete evaluation is a different
authority design and remains outside this RFC and the current NOT-DOING scope.
