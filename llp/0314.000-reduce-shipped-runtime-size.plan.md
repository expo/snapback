# LLP 0314.000: Reduce the shipped runtime size

**Type:** Plan
**Status:** Draft
**Systems:** Packaging, Build, Runtime, Distribution, Developer experience
**Author:** Charlie Cheever / Grok
**Date:** 2026-08-25
**Related:** LLP 0314 (parent), LLP 0000, LLP 0010, LLP 0041, LLP 0126,
LLP 0141, LLP 0189, LLP 0232, LLP 0276

## Summary

LLP 0314 found the npm runtime is large because the ship path does not
use the ship profile, does not strip the symbol table, and compiles the
Guide into the server — on top of a genuinely large Rust program.

This plan is the size program. It does **not** shrink the debug
developer binary (LLP 0010 stays report-only). It does **not** become a
landing veto (LLP 0189 / LLP 0232). It does **not** replace Hermes.

The work is four phases. Phases 1–2 are packaging and carriage; they
should move the Darwin server from **~159 MB** toward **~90–110 MB**
without deleting product. Phases 3–4 need a bloat ranking first and may
not pay. Split-binary and `opt-level = "z"` stay optional.

## Standing constraints

- **Debug stays fat.** LLP 0010’s qualified developer binary keeps full
  split debug. Do not strip `target/debug/snapback`. Do not fold ship
  size into `scripts/binary-size-metrology.mjs`’s debug baseline.
- **Publish path only.** Fat LTO belongs on the artifact people
  download, not on the in-window `cargo build --release` edit loop
  (LLP 0276). Ordinary release remains incremental.
- **Optimistic landing stays the default.** Size drift on main is
  fix-forward. A new ship-path size check may refuse a *publication*
  ceremony; it may not refuse an unrelated landing.
- **Ibex/Hermes stays.** LLP 0000’s local runtime choice is not on the
  table. The packaged Darwin framework is ~9.4 MB.
- **npm remains the distribution path.** LLP 0141’s crates.io limit
  still holds. Shrinking the binary does not make a crates.io server
  crate viable until Hermes carriage changes, which this plan does not
  do.
- **No current users depend on stability** (LLP 0041 publication
  posture). Stripping symbols and moving the Guide out of the binary
  are allowed to change on-disk layout. They are not allowed to change
  ready-file, health, or Guide *URL* semantics.

## Non-goals

- Beating PocketBase (~13 MB). That is a smaller product in a language
  that does not monomorphize this hard. 64 MB of `__text` is mostly
  real code.
- `opt-level = "z"` or size-at-all-costs on the query engine as a first
  move.
- Replacing V8/workerd on Cloudflare, or unifying VM weight across
  targets.
- Deleting search Unicode tables, SQLite, auth, or live queries to
  make a better screenshot of `ls -lh`.
- A complete-proof-at-exact-HEAD size gate.

## Measurement (do this before claiming crate-level wins)

Ship-path size is a **publication** signal, sibling to LLP 0010’s debug
signal, not an extension of it.

Retain, for Darwin arm64 and Linux x64, on the binary that
`prepare-runtime.mjs` actually copies:

1. File bytes, Mach-O/ELF section sizes (`__text`, `__const`,
   `__LINKEDIT` / `.symtab`, unwind).
2. `nsyms` / symbol-string bytes (Darwin `LC_SYMTAB`).
3. Package `unpackedSize` and tarball bytes.
4. After Phase 0: `cargo bloat --profile production --crates` and a
   `bloaty` (or `llvm-nm --size-sort`) compile-unit view, committed
   under `scripts/` or `benchmarks/records/` as a dated snapshot, not
   as a claim digest.

Budgets, once a production-profile stripped baseline exists, belong in
a small JSON next to the packager — analogous to
`scripts/binary-size-baseline.json` but keyed on
`SNAPBACK_BUILD_DISTRIBUTION=public-package` and
`--profile production`. Publication may refuse a regression past
tolerance. Landings may not.

Until that baseline exists, the expected ranges below are planning
numbers, not gates.

## Phase 0 — Rank the bytes

**Goal:** turn LLP 0314 F6 from a dependency list into a crate ranking.

- Build `cargo build --profile production -p snapback --bin snapback`
  with `SNAPBACK_BUILD_DISTRIBUTION=public-package` on Darwin arm64.
  Do not publish it.
- Run `cargo bloat` (crates and functions) and `bloaty` on that
  binary, before and after a `strip -x` (or equivalent).
- Record Guide-blob size inside `embedded-guide.v1.bin` (`OUT_DIR`)
  as its own line, so F4 is not mixed with Rust rodata.

**Exit:** a committed ranking that can falsify “jsonschema is the next
cut” or confirm it. No product change.

## Phase 1 — Ship the ship profile and strip it

**Goal:** use the compiler flags and symbol policy we already designed.

1. **Pack `--profile production`, not `--release`.** Point
   `prepare-runtime.mjs` (both Darwin and Linux) at
   `target/production/snapback`. Change the public-package command
   pinned in `tests/ci_workflows_v0.mjs` and LLP 0041’s runtime
   assembly notes to
   `SNAPBACK_BUILD_DISTRIBUTION=public-package cargo build --profile production --bin snapback`.
   Leave `[profile.release]` incremental for humans and agents in the
   window.
2. **Strip the packaged binary only.** Cargo
   `[profile.production] strip = "symbols"` and/or `strip -x` in the
   packer. Keep dynsyms needed to load Hermes. If open question 4 of
   LLP 0314 is “yes, we want crash stacks,” emit a `.dSYM` / ELF
   debuginfo next to the receipt in CI; do not leave 241k names in
   the npm file.
3. **Do not strip debug developer builds.** LLP 0010 baseline remains
   the qualified `target/debug/snapback`.

**Expected:** `__LINKEDIT` ~34 MB largely gone (strip). `__text` 15–25
MB smaller (fat LTO, wide range — Phase 0 will replace the range).
Darwin file **~110–130 MB** after this phase alone is a success;
**~90–110 MB** if LTO pays the top of the range. Compile time on the
publish machines gets worse; that is the trade LLP 0276 already
accepted. Do not run fat LTO on every agent `cargo test`.

**Docs to amend when this lands:** LLP 0041 runtime assembly (the
copied binary is `target/production/snapback`); LLP 0276 (the ship
command is no longer aspirational).

## Phase 2 — Stop compiling the Guide into the server

**Goal:** same URLs, sidecar files, like admin.

Admin already lives under `packages/snapback-runtime-*/admin/`. Serve
the Guide corpus the same way: package files next to the binary,
opened at process start, identity still bound by the existing
content-hash / build-commit headers.

- Keep `crates/snapback-server/src/guide.rs` as the decoder and HTTP
  surface. Stop `include_bytes!` of `embedded-guide.v1.bin` on the
  public-package build.
- Contributor-source / in-tree `cargo run` may keep embedding, or
  may read `guide/` from the checkout. Pick one and pin it; do not
  silently fall back.
- Public-package identity must fail closed if the sidecar corpus is
  missing or its hash does not match the receipt — same class of
  refusal as a missing admin snapshot (LLP 0041).
- `guide/` edits must not rebuild `snapback-server` on the publish
  path.

**Expected:** most of the ~20 MB Guide corpus leaves `__const`. Some
Rust string overhead stays. Combined with Phase 1, Darwin **~90–110
MB** is the planning target for “we did the obvious carriage work.”

**Do not** change `/_snapback/guide/…` routes or the MCP guide
surface’s external contract in this phase. Carriage only.

## Phase 3 — Align the crate graph with a ship graph

**Goal:** the binary people download is not the test binary.

Depends on Phase 0’s ranking. Do not cut by folklore.

In priority order, *if the ranking agrees*:

1. **Drop `test-support` and `benchmark-support` from
   `crates/snapback` `[dependencies]`.** Keep them on
   `[dev-dependencies]` / `cfg(test)`. Kernel already documents this
   rule; the umbrella crate currently violates it for
   `snapback-server` and `snapback-services`. Likely small, but it is
   the wrong graph even at 0 MB.
2. **`jsonschema` only where Ask needs it.** Tests that compile
   schemas already can (and in kernel, already do) use it as a
   dev-dependency. If bloat says the crate is tens of megabytes in
   `__text`, consider a smaller runtime validator; that is a later
   RFC, not this plan’s default.
3. **`image` + exif behind an assets feature** if a meaningful
   fraction of installs never decode uploads. Default-on is allowed
   if the ranking says it is cheap.
4. **One KDF in the default binary (argon2).** bcrypt/scrypt as a
   compat feature if stored hashes exist. Do not strand existing
   local DBs.
5. **Trim `tokio` `full` and `rusqlite` features** to what the ship
   path uses. Easy to get wrong; Phase 0 first.
6. **`panic = "abort"` on `[profile.production]` only.** Recovers
   some unwind info. Do not expect the full 11 MB of `__eh_frame` +
   `__gcc_except_tab` — a chunk is C++.

**Expected:** maybe another 5–20 MB if the ranking is kind; maybe
almost nothing if `__text` is mostly Snapback’s own crates. Phase 0
decides. This phase may split into tickets rather than one landing.

## Phase 4 — Optional structure (do not start here)

Only after Phases 1–2 are in a published closure and Phase 0 is
retained:

- **Two binaries:** `snapbackd` (listen, no clap, no MCP, no Guide
  embed) and `snapback` (CLI). Local-dev npm still ships both;
  hosted/sidecar can ship only the daemon. This is an RFC-sized
  split, not a packer flag.
- **`opt-level = "s"` experiment** on production, measured against
  the query/live path, not against `ls -lh` alone.
- **Linux ICU carriage:** whether the extra ~60 MB vs. Darwin is
  unstripped ELF, duplicated ICU, or something else. Measure, then
  trim.

## Expected outcome (planning, not a gate)

| Artifact | 0.1.27 (LLP 0314) | After Phases 1–2 (plan) |
|---|---:|---:|
| Darwin `bin/snapback` | ~159 MB | ~90–110 MB |
| Darwin runtime tarball | ~52 MB | ~30–40 MB |
| Darwin unpacked package | ~178 MB | ~110–130 MB |
| Debug `target/debug/snapback` | ~500 MB | unchanged policy |
| Hermes framework | ~9.4 MB | unchanged |

Linux should move in proportion once strip + production profile apply
there too; the ICU `.so` remainder is Phase 4.

A 50 MB *download* was already acceptable. The point of this plan is
disk, dyld, and not lying about `[profile.production]`.

## Open questions

1. Does any published support path need symbolized stacks from the
   npm binary (LLP 0314 OQ4)? If yes, Phase 1 keeps a debuginfo
   sidecar.
2. Contributor-source Guide carriage: keep embedding for `cargo run`,
   or always read files? Phase 2 must pick one.
3. Publication-only size gate: which ceremony (fast-path vs. qualified
   staging) grows the check, and what tolerance? Default proposal:
   fast-path pack refuses a regression past 15% of the committed
   production baseline, matching LLP 0010’s debug tolerance but on a
   different file.
4. Is `jsonschema` load-bearing for Ask’s product semantics, or could
   a smaller validator preserve the same refusals? Out of scope until
   Phase 0.
