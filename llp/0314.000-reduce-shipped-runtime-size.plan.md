## Summary

LLP 0314 found the npm runtime is large because the ship path does not
use the ship profile, does not strip the symbol table, and compiles the
Guide into the server — on top of a genuinely large Rust program.

This plan is the size program. It does **not** shrink the debug
developer binary (LLP 0010 stays report-only). It does **not** become a
landing veto (LLP 0189 / LLP 0232). It does **not** replace Hermes.

The work is four phases. Phases 1–2 are packaging and carriage; they
should move the Darwin server **binary** from **~159 MB** toward
**~90–110 MB**. The unpacked *package* moves less — Phase 2 relocates
the Guide, it does not delete it. Phases 3–4 need a bloat ranking first
and may not pay. Split-binary and `opt-level = "z"` stay optional.

## Standing constraints

- **Debug stays fat.** LLP 0010’s qualified developer binary keeps full
  split debug. Do not strip `target/debug/snapback`. Do not fold ship
  size into `scripts/binary-size-metrology.mjs`’s debug baseline.
- **Publish path only.** Fat LTO belongs on the artifact people
  download, not on the in-window `cargo build --release` edit loop
  (LLP 0276). Ordinary release remains incremental.
- **Optimistic landing stays the default.** Size drift on main is
  fix-forward. A new ship-path size check may refuse a *publication*
  ceremony; it may not refuse an unrelated landing. Each phase lands
  with its affected checks green, publishes promptly through the
  existing qualified path, and gates any capability claim on scoped
  post-landing evidence plus the LLP 0189 D-6 battery reference;
  unrelated complete-battery reds are ticketed, never retroactive
  blocks.
- **Ibex/Hermes stays.** LLP 0000’s local runtime choice is not on the
  table. The packaged Darwin framework is ~9.4 MB.
- **npm remains the distribution path.** LLP 0141’s crates.io 10 MB
  limit is the immediate blocker, and 0141’s path-dependency, artifact
  custody, qualification, and publication-metadata requirements also
  stand — shrinking the binary does not make a crates.io server crate
  viable, and this plan does not change Hermes carriage.
- **No current users depend on stability** (LLP 0041 publication
  posture). Stripping symbols and moving the Guide out of the binary
  are allowed to change on-disk layout. They are not allowed to change
  ready-file, health, or Guide *URL* semantics.

## Non-goals

- Beating PocketBase (~30 MB executable, ~13 MB download). That is a
  smaller product in a language that does not monomorphize this hard.
  67 MB of `__text` is mostly real code.
- `opt-level = "z"` or size-at-all-costs on the query engine as a first
  move.
- Replacing V8/workerd on Cloudflare, or unifying VM weight across
  targets.
- Deleting search Unicode tables, SQLite, auth, or live queries to
  make a better screenshot of `ls -lh`.
- A complete-proof-at-exact-HEAD size gate.

## Measurement (do this before claiming crate-level wins)

Ship-path size is a **publication** signal, sibling to LLP 0010’s debug
signal, not an extension of it.

Retain, for Darwin arm64 **and** Linux x64, on the binary that
`prepare-runtime.mjs` actually copies:

1. File bytes, Mach-O/ELF section sizes (`__text`, `__const`,
   `__LINKEDIT` / `.symtab`, unwind).
2. `nsyms` / symbol-string bytes (Darwin `LC_SYMTAB`; ELF symtab).
3. Package `unpackedSize` and tarball bytes.
4. Binary digest plus raw `size`/`otool -l` (or `readelf`) output with
   each dated snapshot, so later passes do not trust prose.
5. After Phase 0: `cargo bloat --profile production --crates` and a
   `bloaty` (or `llvm-nm --size-sort`) compile-unit view, committed
   under `scripts/` or `benchmarks/records/` as a dated snapshot, not
   as a claim digest.

**Baseline custody.** Once a production-profile stripped baseline
exists, it lives in a small committed JSON next to the packager —
analogous to `scripts/binary-size-baseline.json` but keyed on
`SNAPBACK_BUILD_DISTRIBUTION=public-package` +
`--profile production`, per platform. Custody follows LLP 0189 D-4:
the baseline declares its semantic input closure and carries its own
registered drift coverage rather than living inside claim digests, and
baseline updates (including intentional growth) are an authorized,
recorded operation, not a silent rewrite. **One shared validator** runs
in every publication ceremony — fast-path pack *and* EAS qualified
staging — over the final immutable tarballs publication accepts, so no
lane bypasses the check; it is never wired into pre-push or landing
gates. The tolerance, initial-baseline bootstrap, and update authority
(with its durable authorization record) are settled before the first
Phase 1 publication (open question 3). Publication may refuse a
regression past tolerance. Landings may not.

Until that baseline exists, the expected ranges below are planning
numbers, not gates.

## Phase 0 — Rank the bytes

**Goal:** turn LLP 0314 F6 from a dependency list into a crate ranking.

- Build `cargo build --profile production -p snapback --bin snapback`
  with `SNAPBACK_BUILD_DISTRIBUTION=public-package` on Darwin arm64.
  Do not publish it.
- Run `cargo bloat` (crates and functions) and `bloaty` on that
  binary, before and after Cargo `strip = "symbols"` — the same
  transform Phase 1d ships (`strip -x` may be recorded as an optional
  extra measurement row, not the primary).
- Record Guide-blob size inside `embedded-guide.v1.bin` (`OUT_DIR`)
  as its own line, so F4 is not mixed with Rust rodata.
- Crate ranking may stay Darwin-only, explicitly scoped; Linux gets
  its own measured pre/post baseline in Phase 1, and the ICU/unpacked
  remainder stays Phase 4.

**Exit:** a committed ranking that can falsify “jsonschema is the next
cut” or confirm it. No product change.

## Phase 1 — Ship the ship profile and strip it

**Goal:** use the compiler flags and symbol policy we already designed.

The packers copy; they do not build. Switching a packer default without
switching every producer strands publication lanes on the wrong
artifact (`SNAPBACK_RUNTIME_BINARY_MISSING`) or breaks source repair.
Phase 1 is therefore two **closed inventories** plus an attestation and
a strip rule, landed together:

**1a. Manufacture switches to `--profile production` /
`target/production/snapback`** — every producer, receipt, and pin in
one landing:

- Both packer defaults, their error strings, and both env overrides
  (`SNAPBACK_RUNTIME_SOURCE_BINARY`,
  `SNAPBACK_RUNTIME_LINUX_X64_SOURCE_BINARY`).
- `.github/workflows/linux-runtime-package.yml`: the cargo build
  **and** both `--binary …/target/release/snapback` receipt-issue
  paths.
- `.eas/workflows/qualified-package-staging.yml`: both `darwin_runtime`
  and `linux_runtime` cargo commands (these are not currently pinned by
  `tests/ci_workflows_v0.mjs`; pin them when changed).
- `tests/ci_workflows_v0.mjs`: both existing pins — the public-package
  cargo string and the Linux receipt-binding assertion.
- `scripts/build-linux-runtime-release`.
- `scripts/packaged-store-qualification.mjs`: its direct-entry default
  binary (`SNAPBACK_RUNTIME_BINARY` or `target/release/snapback`)
  retargets to the production path, with its help text and tests.
- `scripts/path-migration-manifest.v1.json`: every `verify-unchanged`
  row whose `currentPathExpression` is the **public-package** ship
  command or names `target/release/snapback` as the public-package
  binary — `s01-r013`, `s01-r024`, `s01-r025`, `s07-r004` — changes
  intentionally, not silently. `s01-r005` is **not** in this set: its
  consumer is `scripts/assemble-runtime-package:63`, source-repair
  custody under 1b, and it stays verify-unchanged on `--release`.
- The Linux lane split, with a named home:
  `linux-runtime-package.yml` keeps a **second** ordinary `--release`
  build plus its sibling receipt solely for the existing
  source-checkout custody assertion (LLP 0010 resolution coverage);
  production is the pack/seal path. `package.test.mjs` splits so the
  public-package lane asserts installed-package custody only, and
  Darwin’s `package.test.mjs` gains the Linux-style installed-custody
  form (a forced package root) instead of bare source-topology
  `resolveRuntimeBinary()`.
- LLP 0041 runtime assembly notes and LLP 0276 (the ship command is no
  longer aspirational).

**1b. Source-checkout custody stays on ordinary `release`** — must
NOT be retargeted:

- `packages/snapback-cli/index.mjs` source-checkout selection and
  repair (`target/release/snapback`, `release` identity).
- `scripts/assemble-runtime-package` — the contributor source-repair
  command (`--source-test-staging --strict-clean-release`). It keeps
  its ordinary-release build and, once packer defaults move, passes
  its release binary explicitly rather than inheriting the production
  default.
- `packages/snapback-runtime-linux-x64/package.test.mjs`
  source-checkout resolution assertion (see the lane split in 1a).
- `[profile.release]` stays incremental; LLP 0010 debug metrology and
  `scripts/binary-size-metrology.mjs` untouched.

**1c. Profile attestation.** `BinaryIdentity.build_profile` reports
only `debug`/`release` via `cfg!(debug_assertions)`, so a production
binary reports `release`, and `assertRuntimePackageBuildIdentity`
requires exactly `release`. Do **not** change `buildProfile` in this
phase — emitting `production` refuses every public package. Instead add
a distinct verifiable build-recipe fact whose **authority is the build,
not the ceremony**, stated implementably: Cargo hands a build script
`PROFILE` but not the resolved `lto`/`codegen-units`/`incremental`/
`strip` tuple, so `build_identity.rs` (already the `cargo:rustc-env`
emitter) stamps `PROFILE` **plus the `[profile.production]` recipe as
declared in root `Cargo.toml`**, and policy closes the ambient override
channels that could falsify the declaration: the
`CARGO_PROFILE_PRODUCTION_*` family, `CARGO_INCREMENTAL`,
`RUSTFLAGS`/`CARGO_ENCODED_RUSTFLAGS` touching `-C lto`/`-C strip`/
`-C codegen-units`/`-C opt-level`, `cargo --config`, and rustc
wrappers — with negative tests for an ordinary-release binary and for
each override class, plus cross-host attestation transport. Receipts,
seals, Linux attestation, staging receipts, ledgers, and publication
validators *copy* the stamp; none may originate it (a workflow-written
line would be as spoofable as the `SNAPBACK_BUILD_DISTRIBUTION` env).
Public-package assembly reads the fact from the bytes being packed and
requires `PROFILE=production` with the declared recipe values. Without
this, an env-overridden ordinary-release binary passes while the
ceremony claims production.

**1d. Strip at one deterministic pre-receipt point.** Use Cargo
`[profile.production] strip = "symbols"` so the compiler output *is*
the final bytes: CV-2 loader qualification (LLP 0123), source receipts
(Linux CI issues one on the pre-pack file), seals, and measurement all
bind the stripped binary. Never strip in the packer after a receipt or
seal exists — that desyncs digests. Keep the dynamic symbols Hermes
loading needs. If open question 1 is “yes, crash stacks”: build with
split debug info, emit and UUID/build-id-bind the `.dSYM`/debuginfo
sidecar **before** stripping, archive it outside npm. Phase 0 and this
phase use the same strip policy (Cargo `strip = "symbols"`), or Phase 0
records both it and `strip -x` — they are not the same transform.
Before sealing, confirm the stripped binary still loads
`hermesvm.framework` (Darwin) / `libhermesvm.so` (Linux).

**1e. Do not strip debug developer builds.** LLP 0010 baseline remains
the qualified `target/debug/snapback`.

**Expected:** `__LINKEDIT` ~35 MB largely gone (strip). `__text` 15–25
MB smaller (fat LTO, wide range — Phase 0 will replace the range).
Darwin binary **~110–130 MB** after this phase alone is the success
band (~90–110 MB is LTO upside, not a second success line — the
outcome table’s stacked bands govern). Compile time on the
publish machines gets worse; that is the trade LLP 0276 already
accepted. Do not run fat LTO on every agent `cargo test`.

**Exit evidence, both platforms:** pre/post section+symbol tables,
binary/package/tarball bytes, and a green qualified path — runtime
qualification, attestation, seal verification, cold install.
“Proportional movement” on Linux is not an exit criterion.

## Phase 2 — Move the Guide out of the binary (a governed amendment)

**Goal:** same URLs, sidecar carriage, like admin — while keeping every
property LLP 0061 §4a decided embedding for.

Embedding is a settled design, not drift: LLP 0061 §4a chose
*embedded-in-binary, always served* (server as structural version
authority; HTTP and MCP re-serve one build-matched corpus), LLP 0041
binds “the runtime binary and its embedded Guide,” and LLP 0284’s
security design leans on the inert artifact, committed decoder, and
directly-included manifest, and LLP 0123’s live package-seal contract
enumerates only the binary and Hermes header/runtime. So this phase
**amends LLP 0061 §4a/OQ3, LLP 0041’s embedded-Guide language, the
affected LLP 0284 rows, and LLP 0123’s seal member set on the same
landing that changes carriage** (testing Guide drift through both
package-seal reopening and `runtime-qualify --persist/--verify`),
preserving by name:
always-available packaged discovery, build/source binding, one
validated corpus across HTTP and MCP, inert bounded decoding, and the
closed path table (no serving a loose file tree).

**Pinned shape:**

- The sidecar is the existing closed-table `embedded-guide.v1.bin`
  format, shipped as a **sealed package member** at
  `guide/embedded-guide.v1.bin`, next to `admin/` — not a raw `guide/`
  tree. `crates/snapback-server/src/guide.rs` remains the decoder and
  data-access layer; the small `include_str!` guide-manifest stays
  compiled in as the trust anchor the decoded blob must hash-match.
  The consumers beyond it — the HTTP routes in `server.rs`,
  `guide_artifact.rs`, `guide_reference.rs`, and the native/MCP Guide
  carriers — all read through the same loader and share its refusal
  semantics; sweep remaining “embedded Guide” wording with the LLP
  amendments.
- **Producer:** `build.rs::emit_embedded_guide` is today the only
  producer, into Cargo’s `OUT_DIR`. Extract it into a shared
  deterministic encoder with two callers: `build.rs` (contributor
  embedding, unchanged) and a pack-time producer running inside
  non-`--native-artifact-staging` `prepare-runtime.mjs` on both
  platforms. The pack-time producer **refuses with a coded assembly
  failure** when package-input pathspecs are dirty or `HEAD` does not
  equal `identity.binary.gitCommit` — runtime wrong-revision refusal
  is a backstop, not the gate. Gate only the Rust *inclusion* off for
  public packages (a `cfg` on the `include_bytes!` path) — never
  artifact production.
- **Discovery:** a dedicated environment seam (a new variable — do not
  reuse `SNAPBACK_ADMIN_DIST`) injected by the CLI with the
  package-relative `guide/embedded-guide.v1.bin` after seal membership
  checks, fail closed — never the process cwd, never a loose `guide/`
  tree, and **no compile-time `CARGO_MANIFEST_DIR` probe** (admin’s
  `default_admin_dist()` fallback is exactly the checkout-tree
  discovery this phase forbids).
- **Assembly modes (three, explicit — the admin seam alone is not
  enough):** (1) native-artifact staging omits the sidecar (CV-2
  qualification and `build-identity` succeed without it; the native
  tars gain no member); (2) public-package final assembly requires and
  seals it as a member of both runtime packages’ `files` manifests,
  `swapStagedAssembly` lists, and seal candidates — plus the adjacent
  pins that red otherwise: both packages’ `.gitignore` gain `/guide/`
  (CI fails closed on a dirty prepared tree) and both
  `package.test.mjs` `manifest.files` / exact-ignore assertions gain
  the member, mirroring `admin/`; (3) contributor
  source-test assembly (`assemble-runtime-package
  --source-test-staging`) omits it — the contributor binary carries
  embedded bytes, and shipping both copies is a defect, so swapping
  into contributor mode removes any stale `guide/` member. Test all
  three transitions. A packaged process missing its sidecar starts,
  passes the handler-VM probe, and refuses the Guide HTTP/MCP surfaces
  with a coded `SNAPBACK_*` diagnostic — same refusal class as a
  missing admin snapshot (LLP 0041).
- **Load validation (split by what exists):** every load validates the
  compiled-in manifest `contentHash` **and** binary `gitCommit`
  against the sidecar’s stamped revision — `contentHash` alone does
  not bind every record (LLP 0284 §3.7), and a same-content
  wrong-revision sidecar must be refused so HTTP and MCP identity
  cannot diverge. `artifactSha256` is checked wherever a package seal
  exists; a bare-binary launch (no seal) validly loads an env-injected
  sidecar on the two binary facts alone. External loading keeps the
  bounded inert decoder: total-size and record-count/length ceilings,
  regular-file (no symlink) source, read-once semantics. Amend LLP
  0010’s packaged readiness artifact set to include the sidecar.
- **Tests:** installed CLI, bare binary launch, HTTP, MCP, and native
  `snapback guide`, each against missing, tampered, oversized, and
  wrong-revision sidecars; publication tarball reopening and
  cold-install cover presence and seal membership.

**Build-graph split:** on the public-package path, gate off the blob
`include_bytes!` and the `cargo:rerun-if-changed=../../guide` walk, and
split `scripts/runtime-build-inputs.txt` into binary-input vs
package-input closures — carried into that file’s consumers (the
`build_identity` dirty probe among them). The split scopes the
binary-side `gitDirty` bit: uncommitted package-only Guide edits stop
dirtying binary identity, while any *committed* Guide change still
advances `HEAD` and restamps commit identity — that is correct, and
the pack-time producer’s clean-source refusal is the package-side
gate. The honest benefit is a smaller embedded/link
payload, not rebuild immunity: the compiled-in manifest remains a
binary input, so a guide edit still recompiles that unit, and fat LTO
relinks regardless.

**Expected:** most of the ~20 MB Guide corpus leaves `__const`, so the
**binary** falls toward **~90–110 MB** combined with Phase 1. The
unpacked package barely moves (the corpus still ships as files, like
admin), and the tarball is roughly neutral. Phase 2’s wins are the
executable/dyld image and the smaller link payload — not package
bytes.

**Do not** change `/_snapback/guide/…` routes or the MCP guide
surface’s external contract in this phase.

## Phase 3 — Align the crate graph with a ship graph

**Goal:** the binary people download is not the test binary.

Depends on Phase 0’s ranking. Do not cut by folklore.

In priority order, *if the ranking agrees*:

1. **Drop `test-support` and `benchmark-support` from
   `crates/snapback` `[dependencies]`.** Keep them on
   `[dev-dependencies]` / `cfg(test)`. Kernel already documents this
   rule; the umbrella crate currently violates it for
   `snapback-server` and `snapback-services`. Likely small, but it is
   the wrong graph even at 0 MB.
2. **`jsonschema` only where Ask needs it.** Two normal-dep sites:
   `snapback-engine` and the `snapback` crate (the kernel and
   `snapback-types` copies are already dev-only). If bloat says the crate is
   tens of megabytes in `__text`, a smaller runtime validator is a
   later RFC, not this plan’s default.
3. **Trim `tokio` `full` and `rusqlite` features** to what the ship
   path uses. Easy to get wrong; Phase 0 first.

**Explicitly not routine cuts** (single prebuilt npm binary; a Cargo
feature cannot vary per install):

- **KDFs.** Dropping bcrypt/scrypt strands imported credentials —
  LLP 0227 requires bounded bcrypt/scrypt verification with
  upgrade-on-verify. Any argon2-only shape needs its own design
  (migration story or runtime variants), not graph trimming.
- **`image`/exif behind an assets feature.** Same one-binary problem:
  installs that decode uploads cannot opt back in. Only viable with a
  separate runtime-variant design.
- **`panic = "abort"`.** Production correctness relies on
  `catch_unwind` (commit-capsule commit-uncertainty preservation and
  reconciliation, writer boundaries). Requires a separate
  durability/safety decision with a complete `catch_unwind`/`Drop`
  audit and crash/restart reconciliation proof — a size ranking cannot
  establish semantic safety.

**Expected:** maybe another 5–20 MB if the ranking is kind; maybe
almost nothing if `__text` is mostly Snapback’s own crates. Phase 0
decides. This phase may split into tickets rather than one landing.

## Phase 4 — Optional structure (do not start here)

Only after Phases 1–2 are in a published closure and Phase 0 is
retained:

- **Two binaries:** `snapbackd` (listen, no clap, no MCP) and
  `snapback` (CLI). The daemon retains Guide HTTP loading/validation —
  or the RFC amends LLP 0061’s always-available property. Local-dev
  npm still ships both; hosted/sidecar can ship only the daemon. This
  is an RFC-sized split, not a packer flag.
- **`opt-level = "s"` experiment** on production, measured against
  the query/live path, not against `ls -lh` alone.
- **Linux ICU carriage:** whether the extra ~60 MB unpacked vs. Darwin
  is unstripped ELF, duplicated ICU, or something else. Measure, then
  trim.

## Expected outcome (planning, not a gate)

| Artifact | 0.1.27 (LLP 0314) | After Phase 1 | After Phases 1–2 |
|---|---:|---:|---:|
| Darwin `bin/snapback` | ~159 MB | ~110–130 MB | ~90–110 MB |
| Darwin runtime tarball | ~52 MB | ~30–40 MB | ~30–40 MB (Guide bytes stay in the tarball) |
| Darwin unpacked package | ~187 MB | ~140–160 MB | ~140–160 MB (corpus moves next to the binary, ~28 MB non-binary content + ~20 MB Guide) |
| Debug `target/debug/snapback` | ~500 MB | unchanged policy | unchanged policy |
| Hermes framework | ~9.4 MB | unchanged | unchanged |

Binary and tarball savings come from Phase 1 (strip + LTO); Phase 2’s
gain is the executable image and rebuild isolation, not package bytes.
Linux gets its own measured pre/post baseline in Phase 1; the ICU
`.so` remainder is Phase 4.

A 50 MB *download* was already acceptable. The point of this plan is
disk, dyld, and not lying about `[profile.production]`.

## Open questions

1. Does any published support path need symbolized stacks from the
   npm binary (LLP 0314 OQ4)? If yes, Phase 1d keeps a debuginfo
   sidecar, bound before stripping.
2. ~~Contributor-source Guide carriage~~ — resolved in Phase 2:
   in-tree builds keep embedding; public-package builds use the sealed
   sidecar; fail closed both ways.
3. Publication-only size gate: exact tolerance and baseline-update
   authorization ceremony. Default proposal: the shared validator
   refuses a regression past 15% of the committed production baseline
   (matching LLP 0010’s debug tolerance, different file), in both
   fast-path pack and qualified staging; baseline custody per
   Measurement above.
4. Is `jsonschema` load-bearing for Ask’s product semantics, or could
   a smaller validator preserve the same refusals? Out of scope until
   Phase 0.
5. Which documents persist the copy of the Phase 1c compiler-derived
   recipe stamp (receipt field, seal line, or both) — decided at
   implementation. The authority question is settled in 1c: the stamp
   originates in `build-identity` from Cargo’s profile facts; ceremony
   documents only copy it, and `buildProfile` is not repurposed.
