# LLP 3000.011.003: Offline capability still leaves application traps

**Type:** Research
**Status:** Active
**Systems:** Snapback 4 local clients, application navigation, shell caching, acquisition, pending writes
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (reviewed evidence and scoped remedies)
**Related:** [Parent](./3000.011-recent-builder-friction.research.md), [Improvement proposal](./3000.011.003.000-offline-ready-application-starters.rfc.md), [LLP 3000.001](./3000.001-durable-replica-and-write-lifecycle.research.md), [LLP 3000.008.001](./3000.008.001-understandable-data-placement.rfc.md), [LLP 3000.008.002](./3000.008.002-complete-client-experience.rfc.md)

## 1. Problem

A durable replica and outbox do not by themselves produce an application that
opens and behaves correctly offline. Routes can require online work before
showing cached data; a browser can lack its shell; a pending write can have no
predicted row; a retained page can be useful without covering all history.
The application must compose those boundaries deliberately.

## 2. Evidence

The [0.2.30 M6 diary](../benchmarks/runs/2026-09-18-snapback4-clique-astra-0.2.30/astra/lane-diary.md)
records a DM route that ran an online pair-deduplication mutation before
opening an already cached room. A membership lookup fixed startup; the backend
had retained the data correctly. Its essay also describes separately adding
a same-origin service worker for the app shell.

The [0.2.29 M2 diary](../benchmarks/runs/2026-09-18-snapback4-clique-astra-0.2.29/astra/lane-diary.md)
found a stale Following projection after a nonpredicting unfollow settled;
explicit synchronization before navigation repaired that particular flow.
This is evidence that authoritative settlement and replica freshness are
different boundaries, not advice to block every route on synchronization.

The [0.2.31 diary](../benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/astra/lane-diary.md)
successfully proved web offline reload and dual-offline convergence. It also
notes that offline search covers acquired history, and that broad public post
and aggregate replication is a scale tradeoff. Its
[report](../benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/astra/lane-final-report.md)
explicitly leaves native acquisition latency and memory unmeasured.

## 3. Current contract

The [README](../snapback4/packages/snapback4/README.md),
[sync card](../snapback4/crates/snapback4-lang/src/guide/sync.rs) and
[prediction card](../snapback4/crates/snapback4-lang/src/guide/prediction.rs)
already state these distinctions. `client.acquired`, `useAcquired()`,
`usePendingWrite`, `complete`, `fresh` and terminal write states exist. The
read card is not missing a new collection of application-specific states.

LLP 3000.001 owns replica lifecycle and retained-read composition. The
implemented LLP 3000.008 client increment is not undone by an application
route choosing the wrong prerequisite. Likewise, a missing native measurement
does not invalidate earlier reference-app measurements on their own fixtures.

## 4. Interpretation

The remaining friction is concentrated at the starter/application boundary.
The substrate supplies facts and durable behavior, but common examples can
still invite an online-first control flow. Each app then rediscovers shell
delivery, route resolution and how to display writes without predicted rows.

Replica placement is a separate deliberate choice: public does not mean that
every row must be acquired, and a small rendered page does not prove small
startup work. Choosing a horizon can also remove the negative knowledge a
mutation needs for prediction. Automatic blanket horizon insertion would
trade one surprise for another.

## 5. Desired outcome and confidence

A generated app should reopen held content without an online precondition,
preserve pending intent, render incomplete history honestly and make its
acquisition workload visible. It should leave the established client contract
and retention policy intact.

The route and shell observations are concrete application errors; whether a
better starter prevents them is testable. The latest diary establishes a
need to measure its residency choice, not a finding that current acquisition
is necessarily slow. The [child RFC](./3000.011.003.000-offline-ready-application-starters.rfc.md)
proposes a starter improvement plus one named real-client residency exercise.

## 6. Review disposition

Review scope correction: default init is schema-only, while Expo init copies a real application. The selected deliverable reuses the existing Vite chat reference and exposes that one output through init; it does not assume a web starter already exists.
