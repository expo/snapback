## Summary

[LLP 0329.004](./0329.004-composition-expressiveness-constraint.research.md)
asks whether an analyzable read language can express bounded fan-out, grouped
counts, multi-table derivation, and bounded graph traversal while preserving
static read-set derivation, retention eligibility, and local re-execution. If
yes, the LLP 0329.000 consensus is buildable. If no, offline is bought at a
price the bakeoffs already scored as a loss.

**The answer is yes**, provided the restriction is on *computational class*,
not on *operator poverty*. The 0329.004 trilemma is a false one: it treats
"static derivation" as implying "a language too small for real apps." That
implication only holds for the language Snapback actually shipped — a closed
two-source unique-join plus an opaque handler — not for every closed language.

The category error, visible in [LLP 0157](./0157-composition-algebra-and-completeness.spec.md)
as clearly as in the withdrawn 0318–0320/0323 batch, is that Snapback specified
*shapes as products* (capability ids, each with its own cursor, live class,
refusal grammar, and maturity) rather than *operators in one algebra*. Adding
grouped counts then means another 1,700-line profile. A rebuild that repeats
that move will re-lose LLP 0120 even with "admitted ⇒ every capability" painted
on the door.

The design that solves both sides:

> One bound-carrying relational algebra. Cardinality is part of the type.
> Unbounded collections cannot be executed, only bounded or maintained.
> Authorization is a predicate in the same language. Named operations are the
> sync unit; composition is compile-time inlining, not a client query engine.
> Anything that still will not fit is an *effect* that writes a table, which
> is a different kind, not a second query class.

That is not Convex (dynamic read-set of Turing-complete functions). It is not
Zero (ad-hoc local ZQL over a replica). It is not Snapback-as-built (two
forms, capability by spelling). It is the 0329.000 sketches with the operator
set they omitted, and with LLP 0157's "algebra" rebuilt as operators instead
of as a registry of profiles.

This document proposes several architectures, argues them, and names a
preferred one. It authorizes no rewrite.

## Findings

### F1 — the trilemma's static-derivation cell is the wrong dual of Convex

LLP 0329.004's table:

| Approach | Expressive | Reactive | Genuine offline |
|---|---|---|---|
| Convex — dynamic read-set recording | yes | yes | no |
| LLP 0329.000 sketches — static derivation | limited | yes | yes |
| Snapback as built | yes | partly | partly, and invisibly |

The middle row's "limited" is an artifact of identifying static derivation with
the current admitted surface (LLP 0080's two-source unique-join; LLP 0110's
one-parent/one-child page; LLP 0157's node-class registry with aggregates and
traversal as Non-goals). Static derivation does not require that poverty. It
requires that every term of the language have a *statically known bound or a
declared maintenance lowering*, and that no term be an opaque function.

Convex's mechanism — record the read set after the fact — is the right tool
for a language that *cannot* be analyzed. It is the wrong dual of a closed
algebra. The dual of a closed algebra is:

- **static:** the *shape* of the read set (tables, indexes, prefix arities,
  per-stage cardinality ceilings, authorization witnesses) and the *bound*;
- **dynamic:** the *windows actually touched this execution*, used to
  invalidate precisely and to populate a materialization closure.

Snapback's generated profiles have (a coarse) static shape and almost no
dynamic window. Convex has dynamic windows and no static bound. Both halves
are wanted. Neither requires JavaScript in the data plane.

The Convex offline cell remains inferred, as LLP 0329.004 labeled it: an
arbitrary server function cannot be re-executed on a client that lacks the
data, because the function does not describe what data it needs.

### F2 — the four LLP 0120 shapes are operators, not products

Restated as operators, with the bound each one actually needs:

| Shape | Diary demand | Operator | Bound |
|---|---|---|---|
| Bounded fan-out | Relay `boardView`: board + columns + cards + activity at one snapshot | `nest` along a declared ref or index, each child with `take n` | product of parent card and per-child `n` |
| Grouped counts | Relay `boardSummary`: counts by column | `group` + `count` / `sum` | if the source is already a page, the page bound; if the group is data-unbounded, the *read* bound is 1 only as a **maintained** row |
| Multi-table derivation | Split ledger: per-participant reductions over four tables | the same nest/join/group, over more sources | same as grouped counts |
| Bounded graph traversal | not in the rerun, but Linear-class (folder trees, issue deps, recursive membership) and recursive authorization | `recurse(along, depth D, fanout F)` | geometric: `(F^{D+1}−1)/(F−1)`, refused if it exceeds the global examined-entry ceiling |

Sequence allocation is **not a query shape**. It is a write-side primitive
(`alloc` on a named scope). LLP 0135 already decided that. Campfire `send`
and Relay `moveCard` are consumers of it.

None of these operators is exotic. They are SQL `LATERAL` + `LIMIT`,
`GROUP BY`, multi-way equijoin, and `WITH RECURSIVE` with an iteration cap —
or the Datalog equivalents. What Snapback forbade was not "analysis"; it was
these operators.

### F3 — LLP 0157 proves the category error in writing

[LLP 0157](./0157-composition-algebra-and-completeness.spec.md) calls itself
a composition algebra. What it is: a static tuple of 2–8 already-admitted
*profile nodes*, with growth "only through owners," and with aggregates,
free predicates, and traversal as Non-goals. Author-facing syntax is
"compilation sugar over the algebra" that "admits no predicate, traversal,
aggregate, or data-dependent invocation the algebra lacks."

That is an algebra of *products*. It is why `snapshot-batch.v1` can assemble
Relay's fan-out from existing nodes (LLP 0120 option 3a, decided in LLP 0135)
and still have nothing to say about `boardSummary` or Split. A third profile
for counts would be another product. The 2026-08-27 batch (LLP 0318–0320,
0323) tried to collapse products from the outside and was withdrawn because
the premises were false of the surface as built.

A from-scratch algebra of *operators* does not grow a capability id per
shape. It grows a term. The cursor, live class, and refusal grammar are
properties of the term's bound and of the runtime states (fresh / stale /
partial), not of a registry row.

### F4 — Convex's bakeoff win and Zero's bakeoff win are different

LLP 0120 measured **server-side object-graph assembly in one snapshot**
(Linear issue detail, Relay board, Split ledger). Agents preferred Convex
because a TypeScript function could do that without a generated contract
block and without being told the paved surface refused the shape.

[LLP 0155](./0155-local-sync-product-direction.rfc.md) / LLP 0138 measured
**client-side composable queries over a local row store** (Zero's ZQL), plus
completeness and inspection. Grok's sketch in LLP 0329.003 attacked that
architecture: a local engine you can invent new joins against *and trust* is
a second query planner, a second permissions evaluator, and the
completeness-proof machine that grew `snapback-client` to ~212k lines.

These are not the same demand. Covering LLP 0120 does **not** require Zero's
client query engine. It requires that a *named* operation may nest, group,
and (bounded-)recurse. Fable's sketch already wrote this as compile-time
inlining of view expressions; Grok wrote it as named SQL. They agree on the
sync unit (a named operation) and disagree on spelling. The 0329.004 question
is the Convex/0120 question. Treating it as the Zero question smuggles in a
client architecture that LLP 0329 F3 says is the complexity sink.

Zero's own current direction is relevant and **[inferred]** from public docs
rather than from a Snapback bakeoff: custom named queries with server-side
filtering are being recommended over the compiled-permissions path. That is
movement toward named operations, not toward a richer local engine.

### F5 — "refuse, do not degrade" survives if and only if the operator set covers the census

The unanimous 0329.000 rule is right, and LLP 0329.004 is right that it has a
precondition. The way the precondition fails in Snapback-as-built is
mechanical: the paved surface cannot say `boardView`, so the author writes a
JS handler, and the handler cannot carry the closed-inputs proof, so
retention becomes a flag, so `auth: 'public'` unlocks a capability, so P18
happens.

If the operator set covers the census, the handler is not load-bearing, and
the escape hatch does not have to exist *as a query*. Effects still exist
(HTTP, Stripe, embeddings, `now()`-relative trending). They write tables.
Views read tables. That is Fable §2 and Grok §1, and it is the only hybrid
that is not a second query class.

If the operator set does *not* cover the census, an opaque query-shaped
escape hatch will be reinvented, because that is what the rerun apps did
when faced with Non-goals. Covering the census is therefore not a nicety. It
is the load-bearing test of the unanimous design.

## The restriction that actually buys analysis

Five constraints, and not a sixth:

1. **No Turing-complete per-row computation.** Builder callbacks (if the
   spelling is TypeScript) run at *build time* and construct an immutable
   AST; a callback cannot `if` on a row value, hide a loop in a helper, or
   call `fetch`. SQL spelling: no UDFs, no PL/pgSQL, no `json_each` of
   attacker-controlled text.
2. **Every collection that executes is bounded or maintained.** See §Cardinality
   as a type.
3. **Schema-closed.** No dynamic table or column names, no `eval` of
   predicates.
4. **Deterministic given (snapshot, args, viewer).** No `now()`, no
   `random()`, no I/O in the data plane. Time and identity are modeled
   values (`viewer()`, `commitTime`) with declared provisional/authoritative
   behavior.
5. **Authorization is in the language**, as row predicates compiled into
   every plan. A query cannot widen a table rule. Public unlocks nothing.

The sixth constraint Snapback actually used — **few operators, each a
separately specified product** — is not on this list. It is what made the
language lose the census. Drop it.

What this still cannot express, honestly, and must not pretend to:

- ranked-by-model-score feeds (effect materializes `rank`);
- `now() - 5 minutes` live windows (pass `since` as an arg, or materialize);
- unbounded "the whole org chart" as a single callable (paginate the walk,
  or maintain a closure table);
- exact `min`/`max` under deletion without rescan or an ordered auxiliary
  structure (LLP 0120 option 5 already refused silent min/max);
- client-invented joins with a completeness guarantee.

Those stay effects or refusals. They are not the LLP 0120 census.

## Cardinality as a type

This is the mechanism that makes "restricted" and "expressive" compatible
instead of sequential.

Collections in the builder (or in the SQL type of a subquery) occupy one of
four states:

| Type | Meaning | Can execute? | Can `count`/`sum`? |
|---|---|---|---|
| `Unbound<T>` | a filtered table, no window | no | no — type error |
| `Page<T, N>` | at most N rows, index-served, ordered | yes | yes, exact over the page |
| `Row<T>` | at most one (`byId`, `.one()` along a unique ref) | yes | n/a (it's a row) |
| `Maintained<T>` | a derived row updated in the same commit as its sources | yes (point read) | it *is* the aggregate |

`messages.where(conversationId)` is `Unbound<Message>`. It is a legitimate
*intermediate*. It is not a query. `.order(at.desc).take(200)` is
`Page<Message, 200>`. That is a query. `.with({ author: m => m.author.one() })`
is `Page<{message, author: Row<User>}, 200>` — bounded fan-out of cardinality
1, along a ref, so indexed by construction.

`cards.where(boardId).count()` is a type error: `Unbound` has no `count`.
The repairs the diagnostic offers are the three honest aggregate semantics
from LLP 0120, as methods, not as constructors:

```text
Unbound<Card> has no count.
  .take(1000).count()              — exact over a page; at-cap if you also want a flag
  .countCapped(1000)               — min(count, 1000), work bound 1000
  .maintainCount({ by: columnId }) — Maintained<number> per group; read bound 1
```

Exact-over-an-arbitrarily-growing-group is **only** the maintained form.
That is LLP 0120 result-semantics variants 1–2 versus 5, pulled into the
type system so an agent cannot write the Convex-looking scan and be
surprised when the compiler asks it to pick. Split's ledger, if it requires
exact current balances for unbounded groups (LLP 0120 OQ8, still open as a
product fact), is `maintainSum`. If a declared page of participants is
acceptable, it is `Page` then `sum`.

The global examined-entry ceiling `G` (a compile-time constant, e.g. 10_240)
is applied to the *worst-case* product of page bounds. A plan whose static
ceiling exceeds `G` is refused at `check`, at the nest/recurse that blew it,
with a rewrite that shrinks a `take` or a recurse fanout. This is not a
query optimizer. **Admission is not optimization.** Every filter must be
index-served or a ref traversal; otherwise refuse with "add index
`cards(board_id)`" or "traverse along the declared ref." Snapback should not
grow a general planner. The 0080/0110 experience is what that costs when
each shape is a product; it would cost more as a general optimizer.

### Bound calculus, sketched

- `byId` / unique lookup: card ≤ 1, examined ≤ 1.
- `where(index-prefix).take(n)`: card ≤ n, examined ≤ n + 1 (has-more).
- unique-join (LLP 0080): card ≤ card(left).
- `nest(parent, child, take n)`: examined ≤ card(parent) · (n+1).
- `exists(page)`: examined ≤ examined(inner), result card 1.
- `group(page).count/sum`: examined ≤ examined(page), result card ≤ card(page).
- `maintain(group, agg)`: read examined = 1; write path is +1/−1 on the
  source change, in the same commit. Delete needs the preimage. Sum overflow
  is a declared write refusal. min/max not in v1.
- `recurse(start, along, depth D, fanout F)`: examined ≤ Σ_{k=0..D} F^k.
  Cycles: visited-set, specified, not optional. If the sum > `G`, refuse.
- Row rules: inlined as `exists`/`filter` of the same calculus. Recursive
  authorization ("visible if any ancestor grants") is `recurse` or a
  `Maintained` closure; it is not a JS walk and it is not free.

Visibility-before-aggregation and visibility-before-traversal are the
defaults. A count never includes rows the viewer cannot read; a walk never
steps through an edge the viewer cannot read. Existence leakage via overflow
refusals is closed by making the ceiling a compile-time fact of the plan,
not a function of invisible-row counts (LLP 0120 §Noninterference).

### Local re-execution without a replica engine

The materialization closure of an admitted operation `P(args)` for viewer
`V` at snapshot `S` is the finite set of source rows, maintained rows, and
authorization witnesses the bound calculus says `P` may examine. The server
sends that closure (or a result fragment plus the subset of the closure the
client still needs). The client stores it keyed by operation identity.

Local evaluation is the **same IR** run against the closure. It is not SQL
and it is not ad-hoc. Completeness is a property of `(P, args, V, S)`: the
closure is either present or it is not. Runtime states, uniform across
every operation (Codex's names, which are the right ones):

- reads: `hydrating | fresh | stale | partial`
- intents: `predicted | queued | committed | rejected`

`partial` is what happens when a nested window would need a row beyond the
retained page — an information limit, not a program limit. No constructor
changes this. `stale` is a disconnected last-authorized snapshot. Revocation
while disconnected is not observable; reconnect re-evaluates rules and
purges. That is Grok's offline-auth honesty and Codex's information/program
cut, and it deletes authorized leases as a user-facing object.

This is DK-9's original slogan — "result cache, never a replica" — reached
by refusing ad-hoc completeness rather than by punching holes in a replica.
The cache happens to contain rows, because the IR needs them to predict
writes and to re-run `P`. The client still cannot issue a query the model
did not name. Cross-query canonical-row reuse is a later, separately
admitted optimization (LLP 0155 Move 2's gated half), not a v1 requirement.

Dynamic read-set recording, used as Convex uses it — *as the evidence* —
is refused. Used as a debug assertion that the derived shape covered the
rows actually touched, it is cheap insurance and would have caught compiler
bugs. That is LLP 0120 finding 5 (capture and declaration are complements).

## Proposals

The proposals below are alternative architectures for the *same* product
question, not sequenced implementation steps. Several share parts.

### P0 — Keep iterating profiles (the current path)

Specify `grouped-count.v1`, promote `bounded-children` and
`snapshot-batch`, leave JS handlers as the undocumented remainder.

**Good.** No rewrite. LLP 0135/0157 machinery exists. Sequence allocation
already has a spec.

**Bad.** This is the path LLP 0120 option 6 already scored: even at full
promotion the admitted shapes miss `boardView` (three children — now
partly addressed by snapshot-batch), `boardSummary`, Split, and sequence
derivation-as-query. A new profile for counts re-enters the 0113
experimental terminus and is bypassed by ordinary artifacts, which is why
the rerun never selected 0110. The capability matrix remains, because the
handler remains. The withdrawn 0318–0323 batch is the existence proof that
you cannot collapse this from the outside.

**Verdict.** Not an answer to 0329.004. It is how we got here.

### P1 — Convex clone: JS is the language, dynamic read-set is the evidence

Queries and mutations are TypeScript functions. The runtime records read
sets, re-runs on overlap, and infers result types. Offline is "best-effort
cache of last result" with no local re-execution of the function.

**Good.** This is what won Clique authoring. Snapshot-consistent graphs are
free. No planner. Agents already write it. Fastest path to "one
constructor."

**Bad.** Genuine offline of private data is the product requirement
(0329.003's assumption, 0329's canonical local-first app). An arbitrary
function does not describe its closure, so the client cannot know what to
retain in order to re-run it. Bounds are theatrical. Hosted untrusted JS in
the data plane re-opens LLP 0009's whole VM story (the Ibex/Hermes
contract, DK-4 pooling, the 0314 binary). Capability-by-form is gone only
because *everything* is the form that cannot be retained honestly — which
is totality by degradation, the thing the sketches rejected.

**Verdict.** Right competitor to steal DX from; wrong substrate. Taking it
as the data plane abandons the half of Snapback the bakeoffs did *not*
lose (authority, settlement, idle, inspectability).

### P2 — Hybrid two-class queries (0329.004's fourth architecture)

Reactive-everywhere via dynamic read-set; a separately admitted narrower
class is retainable and locally re-executable.

**Good.** Honest about the information-theory cut if the classes are
*named* as information states. Lets a Convex-shaped function exist for
"I need a one-shot admin report."

**Bad.** If both classes are query-shaped (`defineLiveQuery` /
`defineJsLiveQuery` under new names), this *is* Snapback-as-built, and
LLP 0329 F1 applies. Agents will write the general class. The retainable
class becomes the hole, and P18-class incentive design returns ("make it
the retainable spelling").

The only version of P2 that is not the current defect is the one the
sketches already have: the general class is **not a query**. It is an
effect. It cannot be subscribed. It writes tables. That is P4's escape
hatch, not a second query class.

**Verdict.** Reject as a query/query split. Accept as query/effect.

### P3 — The sketches as written, operator set not extended

Fable's views with `.one()` and `.limit` and a small aggregate set; Codex's
bounded relational algebra "deliberately small aggregates"; Grok's
restricted SQL with `LIMIT` required, no `GROUP BY` story, no `RECURSIVE`.

**Good.** Totality, row rules, derived facts, effects as a different kind,
dev-loop as co-equal — all of that should survive. Private chat works.
Relay `boardView` works in Fable (nest along refs) and in Codex if nest is
in the "small" algebra; it does not work in a Grok reading that refuses
ad-hoc composition *and* does not nest inside a named query.

**Bad.** Grouped counts over growing domains, Split's four-table
derivation, and bounded graph walks are either "small aggregates, maybe"
or Non-goals again. Fable is the closest: it wrote `.count()` on a
range-indexed nest and admitted the live-aggregate cost. It did not pin
exactness (LLP 0120's five variants) and did not include `recurse`. Codex
named aggregates without pinning maintenance versus scan. Grok's named-SQL
can *add* `GROUP BY` and `WITH RECURSIVE` — the sketch just didn't, because
0329.004 did not exist yet.

**Verdict.** Right shape, incomplete operator set. Completing it is P4/P6,
not a different architecture.

### P4 — Bound-carrying algebra, cardinality as type, derived lowerings (preferred)

One language. Operators, not profiles. Cardinality types as in the section
above. Compiler-visible lowering for aggregates (`Page`-fold vs
`Maintained`). Named operations are the sync unit; views compose by
inlining at `check`. Effects are a different kind and write tables. The
authoritative interpreter is Rust over the IR; JS is not in the data plane.
The client interprets the same IR over materialization closures. Row rules
in the same language, deny-by-default, public is loud and buys nothing.
Runtime states are information, not constructors.

Spelling is deliberately not decided here (see P4a/P6). Semantics are.

**Good.**

- Covers the LLP 0120 census without a second query class, so
  "admitted ⇒ every capability" is implementable rather than sloganeering.
- Static shape + bound for admission, retention, and local re-execution;
  dynamic windows for invalidation. The trilemma's middle cell becomes
  "expressive enough, reactive, offline" instead of "limited."
- Does not grow a capability id per shape. Cursor identity is plan-hash +
  args + window; live class is "all admitted operations"; refusal grammar
  is the small error algebra the sketches wanted.
- Deletes the incentive that produced P18.
- Client stays a closure cache plus outbox plus an IR interpreter, not a
  replica engine. Addresses LLP 0329 F3 without giving up local prediction.
- Matches DK-9's intent (no ad-hoc local SQL, no client-owned auth) while
  allowing the DK-9 dated amendment's local plan evaluation over retained
  fragments, because the fragment *is* the closure of a named plan.
- Planner affordability of the common rule (`exists` membership) is a
  semi-join plus an index, not a recursive walk. Recursive auth is
  `Maintained` or `recurse`, chosen in the type system.

**Bad.**

- It is a language, and languages have a specification cost. The claim is
  that specifying ~12 structural operators *once* is cheaper than specifying
  the next three profiles, and that the 0080/0110 line counts measure
  product-specification, not operator-specification. That is a judgment,
  not a measurement.
- Maintained aggregates couple the write path to every reader of the count.
  Hot-key increment contention replaces scan contention (LLP 0120 option 5's
  named empirical expectation). Split-style four-table maintenance is a
  real spec (preimage, group-move as −1/+1, overflow, idempotent replay).
- `recurse` plus row rules can still leak existence if overflow or visited-set
  behavior is data-dependent; the ceiling must stay a compile-time fact.
- Agents who want a `for` loop will hit a type error. The diagnostic has to
  be as good as Diary 0114 says today's diagnostics are, or they will look
  for an effect-shaped back door and we will have to refuse that too.
- Does not by itself fix the Clique losses that were not the query language
  (Metro races, identity rebind, media). Those stay co-equal, as both
  two-against-one findings in LLP 0329.000 said.
- First implementation still has to pick exactness defaults. If we default
  to `Maintained` for every `count`, write-path cost surprises authors; if
  we default to "must `.take` first," exact ledgers surprise them. The type
  error forces a choice; it does not make the choice.

**Verdict.** This is the architecture that satisfies both sides of
0329.004. The sketches already described its surrounding product (row
rules, derived facts, effects, runtime states, small error algebra). They
did not describe this operator/type core, which is what makes the
precondition hold.

#### P4a — TypeScript build-time builder as the spelling of P4

Codex's notation: callbacks construct AST, row values are expression
objects. Fable's nested `.with({ author: m => m.author.one() })` is the
fan-out spelling. Instant's InstaQL and Zero's ZQL are cousins; the
difference is that P4a's builder cannot emit `Unbound` as an executable
query and cannot run on the client against a replica.

**Good.** Agents write TypeScript. Inferred result types (the other half of
the Convex DX gap, CV-4/6) fall out of the builder. One ecosystem with the
app.

**Bad.** The "looks like JS but isn't" hazard is real: an agent *will* write
`rows.filter(r => …)` and the type error has to fire. Build-time evaluation
of the module must be sandboxed (this is a compiler, not a handler). The
IR, not TypeScript, is the product contract — same as Codex said — or we
grow a second dialect.

### P5 — Datalog / differential dataflow as the semantics, any spelling

Stratified Datalog with bounded recursion and stratified aggregation.
Authorization is more rules. Incremental maintenance is the native
execution (Differential Datalog, Materialize, Noria). Instant's *client*
engine is Datalog over triples; Materialize's server is SQL compiled to
differential dataflow, including `WITH MUTUALLY RECURSIVE` with an
iteration cap.

**Good.** Recursion and incremental aggregates are the well-studied core,
not an add-on. Recursive authorization is a program in the same language.
IVM is the execution of P4's `Maintained`, not a special case. If Snapback
ever needed true incremental nested queries rather than rerun-and-diff,
this is the literature.

**Bad.** Agents do not currently write Datalog well, and Clique would
become a Datalog tutorial. A differential-dataflow runtime fights the idle
and SQLite-first story: Materialize is a dataflow cluster, not a
scale-to-zero SQLite process. Using Datalog as the *IR* while spelling P4
in TS or SQL is coherent; using Datalog as the *authoring* language is an
agent-experience bet the scoreboard does not support. min/max, negation,
and stratified aggregation have subtle semantics that become 3,934 codes if
we are not careful.

**Verdict.** Steal execution ideas (rerun-and-diff is acceptable v1, IVM
for `count`/`sum`/`exists`, iteration caps on recursion). Do not author in
Datalog. P4's `Maintained` *is* the IVM subset, named so an agent can see
it.

### P6 — Restricted SQL as the spelling of P4

Grok's `app.model.sql`, extended with the operators P3 omitted: `LATERAL`
(or nested `SELECT` in `json_object` / a documented nest syntax) for
fan-out, `GROUP BY` with the same cardinality rules (a `LIMIT` on the
source, or `CREATE MAINTAINED VIEW`), `WITH RECURSIVE … CYCLE … LIMIT`
with required depth. Row rules are SQL booleans. Mutations are SQL DML plus
`ASSERT`.

**Good.** One artifact an agent greps. Diagnostics can paste the rewrite in
the language the file is already in. SQLite and Postgres are lowerings of
the same SQL subset, which matches the portable-IR goal. `EXISTS (SELECT 1
FROM memberships …)` is the membership template Grok wanted in the error
message.

**Bad.** SQL is huge; the subset must be specified by what is *admitted*,
not by what is forbidden, or agents will use the next clause (`WINDOW`,
`GENERATE_SERIES`, `json_each`) and we will play whack-a-mole. Nested
object graphs are awkward in SQL (this is why Convex won on inferred
TypeScript shapes). Result types need an extra mapping layer. SQL's
three-valued logic and collation are footguns LLP 0080 already refused to
import (`localeCompare` is an observable migration).

**Verdict.** Viable spelling of P4, not a different architecture. Prefer it
if the primary author is an agent that pastes DDL; prefer P4a if the
primary author is an agent that pastes TypeScript next to React. The IR is
the same. This choice is LLP 0329.000 D1 (genuine disagreement, "spelling
matters least") and should stay that.

### P7 — Local replica + client SQL/ZQL (Zero / Electric / Instant)

Sync *shapes* or triples to the client; run queries locally; permissions
either compile into the local query (Zero) or post-filter (Instant CEL).
Offline is free because the data is here. Expressiveness is whatever the
local engine can do.

**Good.** Instant and Zero both show that nested graph queries plus
optimistic local eval are a product people like. Electric shows that
shape-based partial replication can be small. This is the local-first
end-state many users describe when they say "offline."

**Bad.** Client-side permissions, completeness for ad-hoc queries, and a
second engine are the architecture LLP 0155 said not to copy and the
complexity LLP 0329 F3 measured. Instant's permissions are a *second
language* (CEL), which is the matrix in miniature: queries in InstaQL,
auth in CEL, and the two can disagree. Zero originally compiled ZQL
permissions into the replica path and is publicly walking some of that
back toward named server queries. Snapback already tried to be more
honest about authority than Zero, then grew the client implementing holes
so it could approximate Zero anyway.

**Verdict.** Copy the outcome (query-driven partial materialization, useful
local rows, shared mutators, inspection). Do not copy the local engine.
P4's closure cache is the copy.

## What I would actually do

Pursue **P4**, with spelling picked by a one-week agent bakeoff between P4a
and P6 on the private-chat + Relay-board + Split-ledger census — not by
taste. Surround it with the sketches' unanimous product, which is not in
dispute:

- row rules in the same language, deny-by-default, public is conspicuous
  and buys nothing;
- derived read/write sets, retention, indexes, invalidation — never
  authored;
- mutation text is the predictor;
- effects are a different kind;
- runtime states are information limits;
- small closed vocabulary and a small error algebra;
- dev loop as co-equal (generation identity, one `check` / `dev` /
  `verify`);
- no JS in the authoritative data path (unevaluated against DK-5 for
  *actions*, which still need a sandbox; evaluated enough against queries
  and mutations).

Do not retrofit this onto `define.mjs`. The 2026-08-27 withdrawals are the
evidence that the current surface cannot converge. A from-scratch data
plane that keeps the Rust+SQLite idle profile, the settlement/intent
machinery, the diagnostic honesty, the schema-source-of-truth rule, and
the benchmark loop is the "start over" that is actually a start-over of
the *authoring and client* layers, not of the process.

A spike that would falsify P4 cheaply, before a rebuild:

1. Write the operator grammar and the cardinality types on one page.
2. Hand-compile three named operations — Relay `boardView`, Relay
   `boardSummary` as `maintainCount`, Split `ledger` as `maintainSum` — to
   IR, no product surface.
3. Execute them in a Rust interpreter against SQLite at one snapshot,
   with membership rules inlined, and persist a closure that a second
   in-process interpreter re-runs.
4. If step 3 cannot be done without inventing a thirteenth special case,
   P4 is wrong. If it can, the sketches' precondition holds and the
   rebuild has a kernel.

## Answers to LLP 0329.004's open questions

**1. Smallest admitted node set that covers the census?**

Wrong unit, if starting over. The smallest *operator* set:

lookup, index-prefix filter, order, take, nest (bounded children), exists,
project/with along a unique ref, equijoin on a declared unique index,
group + count/sum on a Page, maintain(count|sum), recurse(depth, fanout),
insert/update/delete, assert, alloc-sequence; plus scalars, `viewer()`,
`commitTime`.

That is the census plus the traversal the census did not happen to
exercise but every authorization-recursive app will. Snapshot-batch as a
*node class* disappears: it is `nest` of several children in one named
operation.

If forced to answer in LLP 0157's unit, the set is: current relational +
bounded-children + an aggregate node + a recurse node + sequence
allocation (already LLP 0135). That is P0 with more products, and I would
not.

**2. Is dynamic read-set recording compatible with the authority model?**

As the *sole* evidence for hosted untrusted JS: no. That is Convex's
posture plus LLP 0009's threat model, and it is why DK-5 exists. As a
runtime assertion on a derived shape, yes, and useful. If JS is not in the
data plane, the interesting form of the question mostly vanishes for
queries and mutations. It remains for effects, which should not be
reactive.

**3. Is a two-class design (reactive-everywhere, retainable-on-a-subset)
materially different from the current defect?**

If the classes are query/query: no. It is the current defect with better
names. If the classes are query/effect: yes — that is P4. If the "classes"
are runtime states of one query (`fresh`/`stale`/`partial`): also yes —
that is information, not authoring form, and is required either way.

## What starting over would keep
