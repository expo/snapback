# LLP 3000.011.005: The latest applications lack native and production evidence

**Type:** Research
**Status:** Active
**Systems:** Snapback 4 native witness, Expo packaging, deployment, provider delivery, benchmark interpretation
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (reviewed evidence and scoped remedies)
**Related:** [Parent](./3000.011-recent-builder-friction.research.md), [Improvement proposal](./3000.011.005.000-qualify-the-built-application.rfc.md), [LLP 3000.003](./3000.003-one-semantics-and-credible-verification.research.md), [LLP 3000.009](./3000.009-general-purpose-backend.rfc.md)

## 1. Problem

Recent Clique builds have substantial real browser and local-server evidence,
but their native deliverable is a Hermes export. An export establishes that
the application bundles; it does not establish SQLite persistence, cold
offline startup, process restart or the native module's runtime behavior.
Similarly, a logged effect seam is not provider delivery, and a local replay
is not operation of a deployed service.

This is an evidence gap. It is not a finding that these capabilities are
missing or that their implementations fail.

## 2. Evidence

All three latest diaries explicitly distinguish Hermes exports from simulator
proof. The [0.2.31 final report](../benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/astra/lane-final-report.md)
claims no native simulator, device installation, APNs/FCM delivery or hosted
deployment. It also says its scale probes measured authenticated server
queries rather than native acquisition latency or memory.

The [independent grade](../benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/astra/grader-report.json)
found the native artifacts absent. The run's
[README](../benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/README.md)
explains that different graders labeled the same absence differently; changing
`failed` to `not-run` did not execute the scenarios. The latest run also had no
committed secret holdout probe set. These are separate coverage limitations.

## 3. Existing capability and obligations

The [published witness card](../snapback4/crates/snapback4-lang/src/guide/witness.md)
already supplies `witness ios`, installed Release-app operation, backend
stop/restart, app relaunch, receipts, video and a hashed run manifest. It builds
no app; the application must integrate its own assertions. The development
reference documents this path. A second simulator harness is unnecessary.

[LLP 3000.009 §11](./3000.009-general-purpose-backend.rfc.md#11-verification-obligations)
already names real-host, external-provider and restore obligations. The
[operations reference](../snapback4/packages/snapback4/CLIENT-AND-OPERATIONS.md#6-release)
documents stopped backup and isolated restore, including limitations around
old devices, unsettled effects and physical power loss.

Earlier reference apps and core tests retain their own evidence. They do not
fill the missing application/package/host cells in the latest benchmark, and
the latest benchmark's absence does not erase those earlier results.

## 4. Interpretation and confidence

The missing evidence is certain from the run artifacts. Benchmark scope
explains an important part: the retained calibration-15 builder prompt says
“simulator proofs are not required,” while its environment lists simulators
as available. Root inspected those retained primary files on M5 on 2026-09-22
under `~/clique-sb4-20260920-astra-cal15/`. The cold builder was required to
export Hermes bundles; installed native execution is additional qualification,
not an unexplained missing feature or an established discoverability failure. Do not infer a product
defect from an unattempted scenario or design another framework before trying
the existing tool on the built application.

The practical cost is uncertainty for someone choosing Snapback for native
offline use or deployment. Confidence should be specific to the tested host,
application, package versions, scenario and external integration.

## 5. Desired outcome

The next built application should have an explicit evidence map: what was
executed on browser, native simulator, deployed server and provider; what
passed or failed; and what was unavailable. Reuse existing run records and
witness manifests. Long execution belongs in a scoped qualification run,
not every code-edit gate.

The [child RFC](./3000.011.005.000-qualify-the-built-application.rfc.md)
proposes a sequence beginning with the missing native witness, followed by
isolated deployment/restore and an explicitly selected provider path. It
does not claim that performing one smoke test proves production readiness.
