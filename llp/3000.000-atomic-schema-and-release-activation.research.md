## Review finding (0.0.16 baseline)

Schema activation currently has several independent owners and several commit
points. The classifier describes a successor but does not enforce it against
stored data. A release number also serves as a replica generation, although
rollback and process restart do not preserve the meaning of that identity.
These are structural correctness problems in the implemented day-two surface.

This research refines [LLP 3000 §9](./3000-snapback4.explainer.md#9-architecture-and-code-review-2026-09-12).
It proposes questions and directions, not an accepted migration protocol.

## The atomic object to define

An active generation needs an agreed relationship between source identity,
bound programs, schema, row projection, indexes, maintained values, and the
replica reset identity. A successful activation must publish a mutually
consistent set. An unsuccessful activation must leave the previous set usable.
Source rollback is a new activation of old source, not reuse of an old device
history. Release identifiers and activation generations therefore serve
different purposes.

The current `_generations` table is created but does not provide this protocol.
Another ledger alone would not solve the ownership problem. First establish
which process may install a schema, and how other open engines detect or refuse
a stale generation before reading or writing.

## Alternatives worth evaluating

| Approach | Advantage | Cost or unresolved point |
|---|---|---|
| One serving owner serializes activation with requests | One place publishes programs and storage together; easiest state model | Long validation/rebuilds can stall serving; crash recovery still needs a durable activation boundary |
| Prepare a candidate, then activate through the serving owner | Preparation can happen without replacing live programs | Must bind candidate validation to the rows it checked and handle intervening writes |
| Explicit stop, migrate, restart for H0 | Smallest implementation if downtime is acceptable | Every writer, including CLI inspection verbs, must respect the stop/ownership rule; commands must state the required sequence |

The third approach may fit the current H0 scope best. That is a candidate for
the owner to choose, not a new requirement for a control plane or online
migration machinery. Whichever approach wins, inspecting data should not
silently install the working directory's schema.

## Decisions still needed

1. Is downtime an acceptable H0 activation contract? What exactly does
   `deploy` promise to an already-running `serve` process?
2. Which changes validate all existing rows, and which apply an explicit
   projection? What does a failed validation report without partially changing
   the store?
3. Are removed tables erased immediately, or retained outside the active
   namespace? Reintroducing a name must not silently resurrect old data.
4. How are maintains rebuilt and published with their source schema? How are
   changed maintain definitions distinguished from already-built ones?
5. What durable monotone identity invalidates device state on every changed
   activation, including rollback and restart? How is an old process stopped
   from writing using a previous catalog?
6. Which filesystem failures are fatal, and when may `deploy` announce success?
   Immutable release directories and atomic pointer publication need to agree
   with the database activation, not merely each other.

## Implementation follow-up

Release removal and stop-to-deploy behavior in this historical implementation record is superseded by [LLP 3000.000.000](./3000.000.000-retained-storage-and-hot-release.rfc.md): release activations retain dormant storage and the admitted server owns hot adoption. Development/device projection behavior remains scoped as recorded.

On 2026-09-13 Charlie requested that the review tickets be fixed. R01–R04
now have an implemented local SQLite activation boundary. This records the
code's contract; it does not accept every migration alternative above.

`Store::activate` owns a `BEGIN IMMEDIATE` transaction. Candidate row
projection, index replacement, changed maintain rebuilds, stored-data
validation, schema/program identity and the monotone generation publish
with the release pointer. A failed validation, derived rebuild, SQL commit
or release compare-and-swap leaves the previous activation intact. The
in-memory catalog and identity are published only after commit. Removed
columns disappear, optional columns materialize null, and removing then
reintroducing a table does not resurrect its rows. Asset narrowing checks
the upload ledger; removed homes become collectable in the activation
transaction. Row validation walks seekable 500-row pages. Program-only
changes do not walk rows or rebuild unchanged maintains.

Every engine transaction checks the identity it opened, including job
admission, chunk parking and schedule advancement. An old engine refuses
`E_GENERATION`; switching A → B → A still invalidates the first owner.
The four identity keys share one cached prepared statement. Every call still
reads all four values from its current transaction; no metadata value is
cached across transactions or substituted for the persisted identity check.
`Engine::open` reads the persisted schema/program pair without adopting
working source. Serving attaches to that active release; `data` and
`doctor` do not compile and install local edits. `dev` and `run` refuse to
adopt source into a store with a deployed release.

Release directories are reserved monotonically above every existing number,
including incomplete attempts. Rollback changes activation, never reuses an
immutable directory. Required preparation I/O precedes activation. The
SQLite release pointer is authoritative; failures updating the filesystem
convenience pointer or ledger after commit explicitly report that activation
already succeeded. Serving verifies the selected source matches the stored
schema/programs.

The regressions in `snapback4-sim/tests/review_corrections.rs` and
`packages/snapback4/test/release-activation.test.mjs` exercise narrowing,
projection, rollback, competing owners, failed SQL/maintain work, release
I/O, stale source and read-only inspection on disposable stores. They do
not establish a power-loss or online zero-downtime migration guarantee.
Long changed-maintain rebuilds still hold the writer transaction. Choosing
an online handoff or bounded background migration remains research.

**2026-10-04, AP (round 1):** index construction stages admitted keys in a temporary
SQLite table keyed by `(ti,k)` and inserts them in key order inside that same
transaction. A duplicate refuses at its original walk step, with the original
`E_STORE: UNIQUE constraint failed: i.ti, i.k` message, before later validation
or meter work. The clustered staging key supplies the final order without a
separate sorter. Server activation's combined main/temp cache target defaults
to 64 MiB, half for each. `SNAPBACK4_ADOPTION_CACHE_MIB` selects 0–512 MiB (0 preserves the caller setting),
and larger caller settings are retained. Linux reduces the target to one quarter
of both the finite address-space limit and the remaining mapped-address headroom
when procfs supplies those values. This is conservative headroom, not a memory
ceiling; other platforms use the explicit target. Restore both caller settings
after each attempt. On SQLite `NOMEM` after an enlargement, roll back fully,
release cached workspace and retry once at the caller setting with the same candidate and time.
Recheck the predecessor identity; never retry a still-open transaction or another
error. The failed attempt is a separate reported phase, never a partial commit.
The internal server builder owns only transactional work and can be replayed;
one-shot device preparation is never retried. Neither native device installation nor
wasm changes its path. A server-activation-only serialized read-ahead page has
its own 128 KiB admission and retains the ordinary per-row decoder and logical
meter charges. It never decodes future rows, is discarded on writes/raw access
(including activation's projection and staging SQL) and savepoint rollback,
and falls back for a row too large for the buffer. Capture and sparse-image
semantics are unchanged. Counts sharing a source reuse its validated image
assessment when the entire population fits the count range; wide sums keep
their per-group cancellation check. Rebuilds and final validation still run.

`check`, dev and deploy expose population-based write-pause advice using measured
eb1000 rates, explicitly not a latency SLO for another host/load. Retirement-only
and mixed changes count predecessor rows/index entries selected for clearing,
once per physical catalog name, and warn that this extra pause is unestimated.
**AP round 2** includes surviving timeline-owned names and dependent targets,
changed aggregate/private targets, row-view recount/basis state, and replaced
indexes. Tables selected by `Retirement::affects` (read-through changes or
inherited-expiry field/default changes) warn about retirement/recapture: their
deletion subset depends on activation time, so the stored population is not an
exact deletion count. On a schema change, an unaffected read-through table
separately rewrites every stored row, including expired rows, to recompute
deadlines. These deadline rewrites are counted exactly, not as a deletion
subset; their pause remains unestimated. Preview never evaluates the later
activation clock. Maintained-column
mirrors, cap occupancy resets/rebuilds and asset-home ledger retirement also
warn when unpriced. Legacy live-sum and cap-occupancy repairs are covered even
without a schema delta. Unpriced populations may overlap modeled source work
and supply no extra seconds to add to the model. Memory advice names the cache control and measured RSS.
The completed activation reports disjoint phases and nested table/capture/rebuild details;
nested timings must not be added twice. The [AP report](../snapback4/reports/20261004-ap-adoption-pause/REPORT.md)
records reproduction, equivalence and qualification. Online publication remains
design-only under [LLP 3000.026 §8.6](./3000.026-following-over-a-populated-store.rfc.md#86-general-derived-state-adoption-after-calibration-30-ap-2026-10-04).

## 2026-09-16 review: executable identity and durable continuations

At `a0d48a4` (0.2.26), immutable release directories and database-owned
activation repair the old split-publication issues above. Two executable
identity gaps remain. A temporary app build reproduced `check` selecting an
old `zzz_old.wasm` after the crate was renamed to `aaa_new`: the directory
scan chooses its lexicographically last artifact. Cargo's reported artifact
must identify the candidate before validation and replacement.

At the reviewed baseline, native jobs intentionally hashed only their Quarry
declaration (the original LLP 3000.005 §4). Their saved `Again` JSON is nevertheless an ABI owned by a particular
module implementation. Replacing Rust code without changing the declaration
can resume a partially committed run with incompatible state or different
business meaning. This is documented behavior with a correctness cost,
not an undiscovered claim that module bytes were already in the digest.

The minimal repair is content-bound admission: store a digest covering the
native declaration plus installed module bytes, compare before every chunk,
and park an old or unbound run with `E_JOB_GENERATION`. Newly queued runs use
the new module. Previously committed chunks remain committed; operators must
not be told that enqueueing a replacement undoes or safely repeats them.
Scheduled admission and restart must use the same identity. Conservative
parking of legacy runs is safer than silently guessing their state ABI.

A richer alternative retains immutable module versions until their admitted
runs finish. It permits continuation through deployment but adds artifact
retention, rollback ownership and security-update policy. Explicit state
migrations are a third alternative and need application-owned compatibility
semantics; a hash cannot infer them. Prefer conservative parking for the
present system rather than introducing a module registry.

See [artifact selection](../issues/closed/20260916-snapback4-native-build-selects-stale-artifact.md)
and [continuation identity](../issues/closed/20260916-snapback4-native-job-continuation-code-identity.md).
These localized fixes do not require rearchitecting the whole backend.
The admitted server-action/step contract has its own capability and receipt
identity (LLP 3000.009); do not equate a native job continuation with an
idempotent external action or silently share their replay rules.

The 2026-09-16 repair candidate implements conservative parking, including
manual admission, schedule boundaries, restart and legacy hashes. The current
contract is recorded in LLP 3000.005 §4. Cargo artifact selection uses the
current manifest's reported cdylib and validates before atomic replacement.
Retained module versions and continuation migration remain research.
