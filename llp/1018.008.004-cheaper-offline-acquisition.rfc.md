# LLP 1018.008.004: Acquire the same offline knowledge with less work

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 2 log drain and resume, carrier transactions, query evaluation, receipt/index materialization, offline memory accounting
**Author:** Codex, commissioned by Charlie Cheever
**Date:** 2026-09-10
**Revised:** 2026-09-10 (initial proposal and measurement boundaries)
**Related:** LLP 1018.008, LLP 1018.007.002, LLP 1012 §4–§8 and §11, LLP 1018.000, LLP 1018.003.001 §4, LLP 1018.006, LLP 1019, LLP 1020

## 1. Outcome and baseline

Reduce network round trips, repeated preparation/evaluation, and duplicate
retained representations needed to acquire a fixed authorized offline dataset.
Preserve the same rows, authorization evidence, cursors, pending work, and
restart behavior. This is a performance follow-up to the completed cold-sync
correction, not a reopening of that work or a new replica model.

The [qualified cohort](./1018.007.002-bounded-cold-sync.plan.md#current-black-cold-series-qualification)
drained 10,008 inbox rows in 201 responses with p95 22,465.823 ms on a contended
host. The [separate final diagnostic](./1018.007.002-bounded-cold-sync.plan.md#final-candidate-operation-counts-and-post-gc-heap)
recorded 207 carrier commits, 613 query evaluations, one full twin snapshot,
20,484 row preparations, and 127,619,872 post-GC heap bytes. Those preparations
include more than delivery rows. The diagnostic was one instrumented run, not
comparative heap metrology; its counts do not prove an asymptotic bound.

Design author: Codex, 2026-09-10; implementation owner/date await commission.
The proposals below are conditional on attributed costs. No current latency,
heap, throughput, or total-store-budget promise changes when this Draft lands.

## 2. Establish which work dominates

Reuse the retained workload and existing benchmark/journey machinery. Preserve
the frozen fixture; run copies against the actual post-1019/1020 implementation
as both baseline and candidate so new delivery semantics are not mistaken for
an optimization. Record the compiler, package, carrier, host/load, fixture size,
and whether the native engine is present.

Separate at least these costs in existing instrumentation/evidence:

| Work | Record | Avoid confusing it with |
|---|---|---|
| Transport | HTTP requests, logical pages, bytes, time waiting on network | Per-page execution time |
| Authority | Certification identity, receipt validation, rule/hash work | Ordinary row decoding |
| Persistence | Accepted delivery groups, durable commits, journal work | Query observer notifications |
| Materialization | Unique rows, row images prepared, index updates | Distinct messages or physical copies |
| Evaluation | Actual query executions by operation and reason | Notifications or sampled stack frames |
| Memory | Peak, settled and post-GC JS heap; durable carrier bytes separately | A claim that the whole store is bounded |

Record the existing 10/50/100-percent checkpoints and cold restart. Test small,
medium, and the full corpus. Instrumentation may be a temporary local change
to current probes; do not add a registry, standalone metrology framework, or
required gate. Keep counts and failures with the experiment they explain.

## 3. First slice: remove duplicate work within existing contracts

Optimize the measured dominant path first, using the existing atomic swap,
metadata selectors, incremental indexes, and shared subscription owner:

- Validate/cache immutable program and schema identities at their existing
  generation boundary. Do not cache dynamic authority by schema identity.
- Within one already accepted delivery group, prepare a canonical row image
  once where its exact content and authority/provenance agree. Sharing a row
  value never merges different query-selection or observation evidence.
- Publish affected query refreshes after their atomic swap, coalescing repeated
  invalidations within that swap. A publication that will not occur need not
  trigger a second identical evaluation, but clock/read-time, refusal, reset,
  and terminal transitions retain their distinct meaning.
- Release obsolete execution scratch and source images after current custody
  owners no longer reference them. Reuse immutable values and existing indexes
  rather than holding equivalent whole-store representations. Do not discard
  authorization facts or outbox evidence to reduce a heap number.

These are implementation candidates, not a claim that today's code duplicates
each item. Retain only changes whose measured operation counts and end-to-end
results establish a benefit. Whole-query execution remains the reference;
this does not commission arbitrary incremental execution inside every query.

## 4. Conditional slice: several certified pages per transport response

If transport/commit overhead remains material after section 3, prototype bounded
acquisition of consecutive pages through the existing resume path. This is an
extension for certified ascending append logs, not an arbitrary query batch API.
It does not introduce a new CLI verb, route, worker, or log cursor kind.

Keep the current per-page shape and bound (at most 50). The server may return
several consecutive ordinary page envelopes inside one response, subject to
the existing one-MiB resume response ceiling and a bounded writer-turn work
allowance. Each page is independently executed and authorized under the current
session, generation, and clock context and has its own receipt. The aggregate
work of all pages, not just each page, is subject to the turn allowance.
Stop at the byte/work bound with the last completed continuation; if one page
cannot fit, use the existing refusal rather than silent truncation.

Do not parallelize guesses at future cursors. Page `n+1` follows the actual
`next` of page `n`. Preserve the authoritative order of edits and tombstones,
including a sequence shared by several events. No new cross-page snapshot
claim is made. If the generation or authority changes, stop/reject the affected
portion under the existing reset/auth rules; never blend generations into one
coverage extent.

On the client, validate the ordered envelopes, then use `commitMany` only when
their existing swap rules admit that group. Persist the accepted facts and its
last accepted watermark atomically. A malformed later page cannot advance the
watermark past durable accepted state. Decide all-or-nothing acceptance of the
response in the prototype first; the preferred first slice is one atomic
accepted group, replayable from its predecessor watermark after failure.

A served page is not received data. LLP 1019 acknowledgements, if enabled,
are created only after the corresponding content is durably accepted, under
its final contract. Connect the live tail from the accepted continuation using
the existing no-gap handshake. Tail progress, acquisition progress, and
receipt acknowledgement remain different facts.

The existing single-page path is the behavior oracle during implementation.
This pre-promotion change should end with one product protocol, not a permanent
compatibility profile. If the prototype cannot stay within existing writer and
response budgets, retain section 3 and report that transport batching did not
justify its complexity. No increase in page size or ceilings is assumed.

## 5. Retained data is a separate decision

Successful outbox compaction already has a discharge proof in LLP 1018.003.001.
Reuse it. Do not replace it with TTL deletion. Unresolved successes, rejected
work, pending inbox aliases, and queued envelopes may remain indefinitely.

This RFC measures durable storage by category, including receipts/extents,
indexes, cached answers, rows, outbox/inbox, and asset bytes. It makes no total
storage-bound claim. The current asset byte-cache limit is a different budget.

An eventual total-store budget needs a product retention decision: which
downloaded history may become unavailable; what backs off at a full store;
which facts/absences and cursors must be invalidated atomically with evicted
rows; and which unresolved work can never be evicted. Pinning all such work
can exceed any hard cap, so a cap additionally needs admission/backpressure.
NOT-DOING and LLP 1012 §11 defer that feature. Gather a named brief's storage
requirement and actual category costs before proposing its scope trade.
Do not silently implement row eviction, per-field unheld values, hold sets, or
per-row delta resume under this performance RFC.

## 6. Acceptance and tradeoffs

Run paired baseline/candidate series on the same host/toolchain/workload and
interleave them to reduce load bias. Use three warm-ups and twenty measured
runs for end-to-end timing as in the retained qualification; keep instrumented
count/heap runs separate. Record raw failures and peak plus post-GC values.
Fleet measurements are appropriate; no primary-machine browser disruption is
required by this drafting task.

Before the experiment, choose the dominant measured cost and a proposed
materiality threshold. The default proposal is at least a 20% reduction in
end-to-end p95 or post-GC retained heap, with no material regression in the
other dimension and no regression of ordinary live-send behavior. That is an
experiment's decision rule, not a new fixed product limit or check. An operation
count improvement without an application benefit is reported as such.

Correctness controls cover interruption before/after durable commit, corrupted
later pages, revocation midway, generation change, repeated and backward
cursors, equal-sequence events, member removal, old-message edit/unsend/expiry,
held search, a never-opened thread after process kill, acquired feed pages,
unchanged queued bytes, writer takeover, and once-media nonretention. Use the
actual post-1019 audience and receipt semantics, including dropped responses.
Native and both first-party carriers retain their current evidence obligations.

Measure full local-runtime bytes against the unchanged 85,000 ceiling and
80,000 target. If batching adds representation machinery, name the redundant
path removed and include its parsing/index/state bytes in the measurement.
Do not move required code out of the measured roots. End with one acquisition
owner and one custody model; omit a proposed optimization if its savings do
not justify its ongoing code and protocol cost.
