## 1. Summary

On Postgres, every database call `serve` makes is a network round trip.
RT-A counted them for public `serve` over a Unix socket, warm, by
protocol capture:

| Warm request | Postgres dependent exchanges | SQLite statements |
| --- | ---: | ---: |
| Tiny counter increment | 57 | 79 |
| One-membership mutation | 58 | 80 |
| W1 point read | 23 | 31 |
| W2 newest 20 | 23 | 31 |

The committer RFC modeled about 12 round trips per execution and S1b got
execution down to 2. That model covered the program and its commit. It
did not cover the **request envelope** around them: four session
resolutions per mutation, two response-head snapshots, and three
post-commit snapshots that re-read what the commit had just written. The
envelope is 43 of the 57 exchanges.

At the measured 0.56 ms ping, 57 serial waits cost about 32 ms before any
work. K3 batching shares only the seven framing exchanges, so it improves
a member by about 1.13×. Pre-execution (K3/K4) moves the envelope off the
serial section, so throughput scales with connections, but latency and
connection-time per request stay at 57 waits.

This RFC makes round trips a budgeted, tested quantity:

- **B1, the structural budget:** a warm read waits on at most **6**
  exchanges, a warm mutation on at most **8**. It is reached by removing
  repeated work, not by caching authority.
- **B2, the pipelined budget:** reads **3**, mutations **4**, by
  pipelining independent statements and folding guarded setup and finish.
- **B3, the raw-control budget (not adopted):** 2 for both, which is
  within 2× of the one-statement raw-Postgres control. It needs each
  admitted program lowered into one server-side atomic operation. §8 says
  why it waits, and what would decide it.

A counted-driver ratchet enforces whichever budget is current, per request
class, in the test suite.

## 2. Where the exchanges go

From RT-A's per-flight attribution of the tiny increment:

| Stage | Exchanges | Why it is there |
| --- | ---: | --- |
| Ingress authentication, before the body | 6 | Refuse unauthenticated requests before buffering a body |
| Route authentication, after the body | 6 | Same resolution again: `principal_of` after decoding |
| First writer-queue admission | 6 | Same resolution again, before queueing |
| Preflight response identity and head | 4 | Built for replay/refusal metadata even when unused |
| Executing writer admission | 6 | The check that counts: fresh after the queue wait |
| Durable transaction | 14 | BEGIN, owner fence, head lock, generation, four savepoint frames, two program reads, one write, tail, SET + COMMIT |
| Post-commit publication head, id, evidence | 11 | Three snapshots re-reading the sequence, store id and change evidence the commit produced |
| Final response identity and head | 4 | Fourth snapshot for the response metadata |

Each authority resolution is its own read-only transaction: BEGIN,
generation/head, session union, two worker-family metadata reads,
ROLLBACK. The reads are W1/W2 with the same shape: two resolutions (7
each, because a detached reader also checks store identity), a response
snapshot (4), and the query snapshot (3 framing + 1–2 reads).

None of this is a retry loop. They are separate callers, each correct in
isolation, each opening its own snapshot because the port's read API
opens one per call (`store/port/lifecycle.rs`, `engine/postgres/handle.rs`).
On SQLite each costs microseconds, so it never showed.

## 3. Principles

### 3.1 Two authority boundaries, not four

A request has at most two places where authority is resolved:

1. **Ingress**, before reading the body. It may refuse early. It never
   authorizes: it only lets the request proceed to be read.
2. **The final check, inside the snapshot the outcome depends on.** For a
   read, that is the query snapshot. For a mutation run in place, it is the
   durable transaction, after the owner fence and the head lock. For a
   pre-executed member, it is snapshot S plus the serial admission re-check
   against a fresh authority clock (committer §3.6).

The route check after the body and the first queue-admission check are
removed: they decide nothing the final check does not decide again. The
final check stays **after every wait** (body upload, queue), so a session
revoked or expired while the request waited refuses, exactly as today
(`serve_identity.rs:58–60`).

A carried *capability* is allowed between the two boundaries: the parsed
bearer digest, the principal, the family and generation seen at ingress,
and a validity deadline. It saves parsing and lets the final check be a
point comparison. It is never treated as proof of current authority.

### 3.2 One statement per authority resolution

The session row, its principal generation, expiry and read cap, the
worker-family marker and revision, and the store generation/incarnation
are resolved in **one parameterized, bounded SELECT**. On Postgres a
single statement sees one snapshot, so the result is as consistent as
today's six-statement transaction. Inside the final snapshot, it is one
statement within that snapshot, not a transaction of its own.

The §9.1 rules apply to it as to any adapter statement: NUL refusal,
total `ORDER BY` under any `LIMIT`, no `SELECT *`, typed arguments, a
statement error ends the transaction. Legacy optional storage (an absent
`_read_sessions`) is resolved at attach, not probed per request.

### 3.3 Borrow the snapshot, never open another

Read APIs take a borrowed snapshot handle instead of opening their own.
The response's identity and head, the query's generation check, and the
query's reads all come from the one query snapshot. The port keeps a
snapshot-opening call for callers that need a fresh boundary, and the
ratchet (§5) makes a new one show up as a counted regression.

### 3.4 What the commit produced is carried, not re-read

The durable transaction returns its committed sequence, the store
incarnation, the generation, and the exact change evidence it wrote. The
committer's publication continuation and the response use those values.
Today `continue_durable_publication` says it "never opens a transaction"
(`engine/committer.rs:374`), but `seq()` and store identity dispatch to
Postgres wrappers that each open one. After this change the statement is
true.

The values are handed over only after a durable COMMIT. An outcome-unknown
COMMIT carries nothing and keeps today's classification. A response
contract that needs a head newer than the acknowledged sequence still
reads it. Wakeups keep their order.

### 3.5 Guarded setup and finish are one flight each (B2)

The writer's setup is BEGIN, the owner fence (`FOR KEY SHARE`, the first
lock of every writing transaction, §5), the head lock, the generation check,
and the member and program savepoints. The finish is the releases, the
tail, the SET LOCALs and COMMIT. B2 sends each as one pipelined flight.

The constraint is the guard. A token mismatch must stop everything after
it on the server, not merely be noticed in Rust after the fact. So the
fence is written to **raise** on mismatch, and the server aborts the rest
of the pipelined transaction. Setup statements are locks and reads, never
writes, so an aborted flight leaves nothing behind. COMMIT returning
ROLLBACK never acknowledges success, and the uncancellable COMMIT and
outcome-unknown classification of S10d-2 are unchanged.

### 3.6 Independent reads are pipelined (B2)

tokio-postgres can send several statements before reading any result.
Reads that do not depend on each other's results go in one flight: the
authority statement with a program's first read, or a membership probe
with a page query when the program's plan already fixes both addresses.
Results are all validated before anything is disclosed or written. A
data-dependent read, or anything past a guard, is not pipelined.

### 3.7 SQLite gets the same structure

The changes are structural, so they apply to both stores. On SQLite they
remove statements rather than round trips: RT-A's isolated savings for
the tiny increment are 8 (preflight head), 11 (post-commit re-reads) and
20 (duplicate authority snapshots), taking 79 statements to about 40. SQLite's transaction modes do not change:
`BEGIN IMMEDIATE` for writers, WAL read transactions for readers.

## 4. The budgets

Budgets count **dependent waits** of a warm request: driver operations
whose result must arrive before the next can be sent. A pipelined flight
is one wait however many statements it carries. Cold costs (first
reader construction, first prepare) are tracked separately, per physical
connection, and are not part of the request budget.

| Request class | Today | B1 | B2 | B3 (not adopted) |
| --- | ---: | ---: | ---: | ---: |
| Point read (W1) | 23 | 6 | 3 | 2 |
| List read (W2) | 23 | 6 | 3 | 2 |
| Mutation, in place | 57–58 | 8 | 4 | 2 |
| Mutation, pre-executed (K3/K4), serial section | (model 7) | 3 | 1 | — |

**B1, a read:** ingress authority (1); then the query snapshot: BEGIN, one
authority + generation + identity + head statement, up to two dependent
program reads, ROLLBACK (5).

**B1, a mutation:** ingress authority (1); setup flight with fence, head and
generation (≤ 2); the final authority statement inside the transaction
(1); up to three program read/write flights (≤ 3); tail and COMMIT (1).
Post-commit SQL is zero.

**B2** pipelines the read's BEGIN with its combined statement and the first
program read, and folds the mutation's setup, final authority and finish
into the flights of §3.5.

These are network budgets. CPU, log amplification, locking, durability
and queueing are measured by the S1 cells, not budgeted here.

## 5. The ratchet

A counted driver wrapper, compiled only under `cfg(test)` or a test
feature and costing nothing otherwise, counts dependent waits per
request. A test suite drives each request class through the real `serve`
HTTP path on a private cluster and asserts:

- the count is at most the current budget for that class;
- the count is recorded in a checked-in table, so a change that lowers it
  must lower the table too, and one that raises it fails.

The ratchet starts at today's counts and moves down with each increment.
It is the same idea as the C1 call-count ceilings S10c already asserts
for the engine, extended to the whole request. On SQLite the same suite
counts statements, against its own table.

## 6. Increments

Each increment is a small landing, reviewed blind by two families. It
names its predicted count, from RT-A's isolated-savings arithmetic, and the
ratchet proves the measured one.

| Increment | Delivers | Tiny mutation | Read |
| --- | --- | ---: | ---: |
| RT0 | The counted driver and the ratchet at today's counts, for the four classes | 57 | 23 |
| RT1 | Commit metadata and evidence carried into publication and the response (§3.4) | 42 | 23 |
| RT2 | Response head built only when used, from the borrowed snapshot (§3.3) | 38 | 19 |
| RT3 | Two authority boundaries (§3.1), each one statement (§3.2); the final one inside the query snapshot or the durable transaction | 16 | 7 |
| RT4 | Read APIs borrow the query snapshot; one snapshot per read request (§3.3) | — | 6 |
| RT5 | Setup and finish folded into one flight each; savepoint frames joined to them; generation check joined to the head lock | 8 | — |
| B2 | Pipelined flights (§3.5, §3.6) | 4 | 3 |
| RT6 | Per-connection: cache the lease UPDATE; pre-open and warm serving readers within the connection budget | — | — |

RT1, RT2 and RT4 are independent and can land in any order. RT3 depends on
the committer's admission point (K0-Q). B2 waits for B1 and for the S1
cells measured at B1.

## 7. Correctness constraints

- **Authority freshness.** A revocation or expiry committed before the
  final check refuses. One committed after it is caught by validation for a
  pre-executed member, and is the same race as today for an in-place one.
  Tests: revoke during body upload; revoke while queued; expiry while
  queued; supervisor-family change while queued.
- **No authority cache across requests.** Bearer sessions are not tied to
  HTTP or Postgres connections, and a TTL or best-effort notification is
  not an invalidation protocol. RT-A found no safe positive saving from one.
  If one is ever proposed, it needs an authoritative version protocol with
  loss and reconnect handling, and its own RFC.
- **Snapshot consistency.** Within each snapshot, generation, head, rules
  and rows agree, as today. A snapshot is never held across a body upload
  or a queue wait and then treated as current.
- **Ownership (parent §5).** The owner fence remains the first lock of
  every writing transaction. A cached token or a live lease is not
  continuing proof of ownership. Folding changes the flight, not the lock
  order.
- **Commit outcomes.** Unknown-outcome COMMITs carry no metadata and keep
  their classification. Carried metadata is never published before the
  COMMIT is durable.
- **Same outcomes on both stores.** Store oracles and difftest compare
  outcomes for every increment, as for any adapter change (parent §9).

## 8. The raw-control budget, and why it waits

The raw-Postgres control does W1, W2 and W4 in **one prepared autocommit
statement each**, with membership authorization inside it and token
verification outside the database. Matching it within 2× means two waits
per request: early live authority, then one statement that is the whole
request.

For a read, that statement is a composed, authorized point or page query
that also returns authority, generation, head and store identity. For a
mutation, it is a **server-side atomic operation**: final authority, owner
fence, head and generation, rule checks, row changes, the complete commit
tail, and returned metadata, committed by the statement's implicit
transaction. That means lowering each admitted program into SQL or a
generated function, with all failure semantics and differential
qualification. It is a second executor in a new form, which LLP 3000.009
§4 (one executor) argues against, and S10e is retiring the last one.

So B3 is not adopted here. The decision is made on measurements, not
argument:

- run the S1 Postgres cells at B1, and again at B2;
- if, at B2, Snapback's W1 p50 is within 2× of raw PG at 0.5 ms RTT
  (parent H2's rule) and W4 throughput clears the §8 rule of LLP
  3000.009.001.002 with pre-execution on, B3 is closed;
- otherwise, B3 is opened as its own RFC, scoped first to reads, where a
  composed query is a smaller step than a mutation lowering.

## 9. What this changes in the sibling plans

- **The committer.** K3 keeps its value: it removes the serial section's
  per-member framing. It is not the fix for request latency, and K3's
  sizing (committer §7) uses B1/B2 counts for the execution stage instead
  of S1b's engine-only 2.
- **The scale study.** The S1 Postgres cell reports its count per request
  class next to its throughput and latency. It runs first at the current
  counts (after maintained columns land, P1-MC), then at B1 and B2, so the
  ledger shows what each step bought.
- **The port.** The read API's snapshot-per-call shape (§3.3) is a port
  change. It is recorded in the parent's §3 when RT4 lands.

## 10. Alternatives considered

- **Do nothing until K3/K4.** Pre-execution scales throughput with
  connections, but each request still holds a connection for 57 waits, and
  p99 latency at 1 ms RTT would be above the 100 ms SLO with any queueing.
- **Cache authority per connection or per bearer.** Rejected in §7.
- **Pipelining only.** Pipelining today's statements reaches about 49
  waits for a mutation and 17 for a read (RT-A). The repeated work is the
  larger term.
- **Lower everything server-side now (B3).** Deferred, §8.

## 11. Open questions

1. Does ingress need a database round trip at all, or can it check only
   the bearer's form and a signature, leaving the final check as the only
   live one? It saves one wait per request, but an unauthenticated client
   could then make the server buffer bodies. The answer may differ for
   `/q` (no body) and `/m`.
2. Should the response head be omitted for successful unkeyed mutations
   when the client did not ask for it, rather than built from the
   snapshot?
3. Is `REPEATABLE READ READ ONLY` needed for a read that makes one
   statement? A single statement is already one snapshot under READ
   COMMITTED, which would save BEGIN and ROLLBACK for such reads.
