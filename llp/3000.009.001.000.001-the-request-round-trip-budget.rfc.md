## 1. Summary

On Postgres, every database call `serve` makes is a network round trip.
RT-A counted them for public `serve` over a Unix socket, warm, by
protocol capture:

| Warm request | Postgres dependent exchanges | SQLite statements |
| --- | ---: | ---: |
| Tiny counter increment, no operation id | 57 | 79 |
| One-membership mutation, no operation id | 58 | 80 |
| W1 point read | 23 | 31 |
| W2 newest 20 | 23 | 31 |

The committer RFC modeled the program and its commit: about 12 round
trips per execution, which S1b cut to 2. It did not model the **request
envelope** around them: four session resolutions per mutation, two
response-head snapshots, and three post-commit snapshots that re-read what
the commit had just written. The envelope is 43 of the 57 exchanges, and
none of it is inside the durable transaction.

At the measured 0.56 ms ping, 57 serial waits cost about 32 ms before any
work. K3 batching shares the seven framing exchanges of the durable
transaction, so an unkeyed member would get about 1.13× from it (only
keyed members share a batch, §9). Pre-execution (K3/K4)
reads admission facts inside its snapshot (committer §3.6), which already
collapses the four resolutions on that path; it leaves the response heads,
the post-commit re-reads and the framing.

This RFC makes round trips a budgeted, tested quantity:

- **B1, structural:** remove repeated work. A warm read waits on **6**
  exchanges, a warm unkeyed mutation on **16**.
- **B2, flights:** send ordered statements as one flight where the store
  already allows it. With ordered SimpleQuery flights: reads **3**,
  unkeyed mutations **8**, keyed first attempts (the common first-party
  path) **9**, replays **2**; with typed envelope functions, 5, 11 and 12. The mechanism is chosen by a correctness difftest and by
  measurement over the real network path (§3.6).
- **B3, a composed statement per request (not adopted):** 2 for both,
  which is within 2× of the one-statement raw-Postgres control. It needs
  rule checks and writes evaluated by the database, which LLP 3000.009
  §4.1 does not allow. §8 gives the rule that would reopen it.

Keyed mutations and replays get their own derived budgets, which RT0
confirms (§4). A ratchet that counts dependent flights per request class enforces
the current budget on both stores (§5).

## 2. Where the exchanges go

From RT-A's per-flight attribution of the tiny increment:

| Stage | Exchanges | Why it is there |
| --- | ---: | --- |
| Ingress authentication, before the body | 6 | Refuse unauthenticated requests before buffering a body |
| Route authentication, after the body | 6 | Same resolution again: `principal_of` after decoding |
| First writer-queue admission | 6 | Same resolution again, before queueing (`serve.rs:1172`) |
| Preflight response identity and head | 4 | Built for replay/refusal metadata even when unused |
| Executing writer admission | 6 | The check that counts: fresh after the queue wait (`serve.rs:1407`) |
| Durable transaction | 14 | BEGIN, owner fence, head lock, generation, four savepoint frames, two program reads, one write, tail, SET + COMMIT |
| Post-commit publication head, id, evidence | 11 | Three snapshots re-reading the sequence, store id and change evidence |
| Final response identity and head | 4 | Fourth snapshot for the response metadata |

Each authority resolution is its own read-only transaction: BEGIN,
generation/head, session union, two worker-family metadata reads,
ROLLBACK (`authority.rs:219–240`, `identity.rs:205–217`). Reads have the
same shape: two resolutions (7 each, because a detached reader also checks
store identity), a response snapshot (4), and the query snapshot (3 framing
plus 1–2 reads).

None of this is a retry loop. They are separate callers, each correct in
isolation, each opening its own snapshot because the port's read API opens
one per call (`store/port/lifecycle.rs`, `engine/postgres/handle.rs`). On
SQLite each costs microseconds, so it never showed.

**What RT-A did not measure.** RT-A sent no operation ids, and first-party
clients send them. A keyed first attempt adds, by code inspection:

- a replay snapshot in preflight (`serve.rs:1177`): BEGIN, generation/head,
  the `_ops` lookup, ROLLBACK;
- a second replay snapshot inside `Engine::mutate`, before program
  resolution (`engine/mod.rs:946`);
- a third, fenced replay check inside the durable transaction
  (`engine/mod.rs:963`);
- the receipt INSERT and bind UPDATE before COMMIT (`engine/mod.rs:1082–1083`);
- when the client sends `store_id`, an `intent_store` snapshot in preflight
  and again before execution (`serve.rs:1176`, `:1417`).

That is on the order of ten more exchanges, at least two of them the
duplicate kind this RFC removes. A replay hit returns from the preflight
section (`serve.rs:1192`) and never reaches the executing writer. Action
sessions walk their claims (`authority.rs:237`), which is a data-dependent
read outside the guest resolution RT-A counted. Refusals (unauthenticated,
rate-limited, ownership lost) were not counted either. RT0 measures all
of these before any budget is set for them. **RT0 follow-up:** the keyed
first attempt is 77 flights, **20** more than the 57-flight unkeyed path;
the rough ten-exchange estimate above understated it. Replay is 30;
action-session W1 is 29; metadata-bearing mutation refusals are 26.
Ownership-loss refusals and deeper delegation chains remain unmeasured.
The full reconciliation and SQLite counts are in the
[RT0 report](../snapback4/reports/20261022-rt0-ratchet/REPORT.md).

## 3. Principles

### 3.1 Authority boundaries

A request has up to three places where authority is resolved, and each
outcome is produced behind a fresh one:

1. **Ingress**, before reading the body. It may refuse early, and its
   refusal discloses nothing but the refusal. It never authorizes: it only
   lets the request proceed to be read. It runs on a reader connection.
   Today a non-detached `/m` ingress resolves on the writer
   (`serve_identity.rs:86`), so ingress is itself a queue wait.
2. **The preflight snapshot**, after the body, on a reader connection:
   read-only, and taking no owner fence. It is opened only when the
   request needs it, and it is the final check for every outcome it
   returns:
   - **A keyed request always opens it.** In one snapshot: the authority
     facts statement; the store id, head and generation; the **bound**
     receipt lookup for `(principal, op id)` with the requested operation
     name and the digest of the raw wire arguments (`replay_bound`,
     `receipts.rs:48–54`; the wire JSON is available before decoding).
     Then, in memory and in this order: the `intent_store` comparison of
     the client's `store_id` against this snapshot's store id, which on a
     mismatch is `E_STORE_REPLACED` and never returns a receipt (LLP
     3000.013, store binding; today `intent_store().and_then(replay)`,
     `serve.rs:1176`); then the receipt: a bound hit returns the stored
     outcome, and a row with a different name or digest is `E_ID_REUSED`,
     both with this snapshot's head. Only on a miss do the program lookup,
     the delivery check, ephemeral diversion and argument decoding run.
     A hit returns before any of those can re-judge a historical write. That is
     the replay-before-judgment contract (LLP 3000.022 §6;
     `engine/mod.rs:931–936`): a committed write whose response was lost
     still replays after its operation is renamed, its arguments narrowed,
     or it becomes ephemeral. Because the snapshot takes no fence, a
     process that has lost its lease still answers a replay, as today.
   - **A refusal that carries store metadata opens it.** An unkeyed request
     runs the in-memory checks first. If one refuses with metadata
     (`operation_refusal`, `argument_refusal`, a delivery mismatch,
     `E_STORE_REPLACED`), the refusal opens this snapshot, authenticates in
     it, and takes its head from it. A request that is not refused never
     opens it.
3. **The final check for execution, inside the snapshot the outcome
   depends on.**
   - For a read: the query snapshot.
   - For a mutation run in place: the durable transaction, after the owner
     fence and the head lock. Every Postgres identity write takes the head
     fence (`lifecycle.rs:158`, `store.rs:173`), so a revocation cannot
     commit between this check and the mutation's COMMIT. The in-place race
     closes, which is stronger than today, where the check precedes the
     transaction. The in-transaction authority statement also returns the
     store id, and the `intent_store` comparison is repeated against it in
     memory, because the store may have been replaced while the request was
     queued (today `serve.rs:1417`). The owner fence compares this
     process's token, not the client's `store_id`, so it does not replace
     this check. A keyed mutation re-checks its bound receipt here as its
     own command after the head lock (§3.5), because a concurrent copy may
     have committed after the preflight miss. A hit aborts the member's
     savepoint and returns the stored outcome.
   - For a pre-executed member: snapshot S plus the serial admission
     re-check against a fresh authority clock (committer §3.6). Receipt
     absence read at S is an early check. The serial receipt re-check at
     admission into the batch is the one that counts. A hit there aborts
     only that member's savepoint, and its stored outcome is acknowledged
     with the batch, after the durable COMMIT (committer §3.4, §3.7).

**Why a keyed request always pays the preflight flight.** Keyed requests
are the common first-party mutation (§2), so this costs the common path one
flight (§4: 9 rather than 8 under (a)). The alternative puts the bound
receipt lookup first in the durable transaction, ahead of the in-memory
judgment, and reads the receipt unfenced only on a fence failure. It saves
that flight on a miss, but serves every replay from the writer's serial
section and makes in-place keyed execution differ from pre-execution. The
preflight keeps replays and wrong-store refusals off the writer entirely,
and it has the same shape as K3's read at S plus serial re-check. RT6
measures both forms on the keyed class and keeps the preflight unless the
conditional form is faster at the S1 cells' load without moving replays
into the serial section's tail.

The route check after the body and the first queue-admission check are
removed: on every path, a later check (2 or 3) decides the same question
after the same waits. A session revoked or expired while the request was
uploading or queued still refuses, as today (`serve_identity.rs:58–60`).
The existing test that a replay waiting while its session expires or is
revoked gets 401 (`tests/serve_adoption/authority.rs`) stays, and is
extended to each class.

**Ownership loss is not a verdict on the operation.** For a keyed request
that missed in preflight, an `E_STORE_OWNERSHIP` from the durable
transaction means "not applied by this process", never "failed". It maps
to a retryable outcome, and the parent's retry table (§5.2) gets the row.

A carried *capability* is allowed between boundaries: the parsed bearer
digest, the principal, and the family and generation seen at ingress. It
saves parsing. It is never proof of current authority. The session scope
that selects the delivery manifest (`serve.rs:1152`) comes from the most
recent check; if the final check's scope differs from the scope a decision
used, the request refuses as stale and the client retries.

### 3.2 One statement fetches a guest session's authority facts

The SQL fetches facts; the shared Rust resolver still decides. For a guest
or ordinary session, the facts the resolver needs (the session row, its
principal generation, expiry and read cap, the worker-family marker and
revision, and the store generation and incarnation) are fetched by **one
parameterized, bounded SELECT**, and the resolver evaluates them exactly as
it does today. No authority policy moves into SQL, and SQLite and Postgres
keep one resolver. On Postgres a single statement sees one
snapshot, so the result is as consistent as today's six-statement
transaction. Inside the final snapshot, it is one statement within that
snapshot.

An action session also validates its claims: work state, lease and
deadline, and admission authority, possibly across several delegation
families (`authority.rs:114`, `:237`). Those reads depend on rows the
first statement returns. For action sessions and any other credential kind
the fast path does not name, the complete shared resolver runs inside the
borrowed snapshot, as many statements as it needs, and the class gets its
own row in the ratchet.

The §9.1 rules apply as to any adapter statement: identity NUL refusal, total
`ORDER BY` under any `LIMIT`, no `SELECT *`, typed arguments, a statement
error ends the transaction. Optional storage (an absent `_read_sessions`)
is resolved at attach, and the flag is updated when storage is installed
lazily (LLP 3000.033 §1.3). If that flag is false and the facts statement
finds no session, probe the catalog once in the same snapshot (`sqlite_schema`
or `pg_catalog.to_regclass('_read_sessions')` under the adapter's pinned schema
search path). On presence, set transaction availability and rerun with the read
arm. Full-session hits retain one statement; independently opened readers can
discover another handle's committed first install on their next snapshot.
Completed fixture backups initialize their independent flag from the copied
catalog. A raw NUL digest is an absent optional lookup key on both adapters,
returned without a query; admitted/stored identity strings still fail closed.

The in-transaction check needs a typed authority method on the Program
member's facade, as K0d added for Direct members. Members still get no
path to raw SQL (K0c).

### 3.3 Borrow the snapshot, never open another

Read APIs take a borrowed snapshot handle instead of opening their own.
The response's identity and head, the query's generation check and the
query's reads all come from the one query snapshot. The port keeps a
snapshot-opening call for callers that need a fresh boundary, and the
ratchet (§5) makes any new one show up as a counted regression.

### 3.4 What the commit produced is carried, not re-read

The durable transaction returns its committed sequence, the store
incarnation and the generation. Request publication and the response carry
those values without another transaction. Non-request publishers without
commit facts still use `continue_durable_publication`, whose `seq()` and
store-identity calls take fresh snapshots, as its comment now states.

The values are handed over only after a durable COMMIT. An outcome-unknown
COMMIT carries nothing and keeps today's classification. A response
contract that needs a head newer than the acknowledged sequence still
reads it. Wakeups keep their order.

A confirmed durable commit answers HTTP 200 `sent` with that commit's
`seq`, `head`, `generation` and `store_id` (incarnation), even if a foreign
activation, a Postgres takeover retiring the connection, or SQLite ownership
loss occurs between COMMIT and publication. Subscribers are woken with that
committed head and identity, except for a receipt-only success (a covered
delivery report that writes no rows), which still skips the wake as §6 states. Before RT1, the response re-read could instead
turn this confirmed write into a 503 `denied` with `E_GENERATION` or an
ownership error. Retrying that apparent refusal without an operation id could
apply the write twice. The committed result therefore remains successful;
the next request observes the changed activation or ownership through the
existing refusal/handoff boundary. This does not authorize any later request.

Change evidence needs care. The Postgres tail writes no `_change_evidence`
(`tail.rs:62–76`), so today's preservation read returns *unknown* on
Postgres. Carrying keeps that answer, and it must not be mistaken for
evidence. Recording the evidence in the tail is a parity item of its own
(parent §9).

### 3.5 Each command keeps its own place

Folding statements into fewer flights must not change what each one sees
or locks:

- **The owner fence is its own command and comes first.** It is the first
  lock of every writing transaction (parent §5.1). A single statement that
  joins `_owner` and `_head` can let the planner take the head lock first,
  which parent §5.1 changed because that order deadlocks with takeover.
- **The receipt re-check is its own command, after the head lock,** for
  the same reason as the generation check below: the receipt a concurrent
  copy committed while this transaction waited for the lock is visible only
  to a later command.
- **The generation check is its own command, after the head lock.**
  Writers run READ COMMITTED (`store.rs:98–101`). Adoption locks `_head`
  and then publishes `_backend.generation` (`opening.rs:105–125`). A
  statement that both locks `_head` and reads `_backend` takes its
  snapshot before it waits for the lock, so it can miss an adoption it
  waited on. A separate later command takes a new snapshot and sees it.
- **A failed fence stops everything after it on the server.** A
  `SELECT … FOR KEY SHARE` that returns no row raises nothing. The fence
  takes the key-share lock and then raises explicitly on a token mismatch,
  for example through an attach-installed function. The commands after it
  are locks and reads, never writes, so an aborted flight leaves nothing
  behind.
- **Every check that decides whether to commit happens before COMMIT is
  sent.** Some are statement errors the server raises: the fence, unique
  and check constraints, deferred-rule failures. Others are results the
  client inspects: the tail's committed-row count must be exactly one
  (`tail.rs:62`, `:80`), released savepoints and member dispositions must
  match the frame, and the program's outcome must be a commit. A flight
  that folds any of these either makes the server raise on it, or ends at
  that check and lets the client inspect the result before the next
  flight. The count includes that wait. Fault tests cover a zero-row tail,
  a statement failure inside each folded flight, and an ambiguous COMMIT.
- **COMMIT is its own flight.** Today a failure before COMMIT is sent is a
  definite abort (`ownership.rs:129–131`). If COMMIT shared a message with
  earlier statements, a lost message would be outcome-unknown even when
  the server never saw COMMIT. Folding COMMIT needs that wider window
  accepted in the parent's retry table first (§5.2), and this RFC does not
  propose it.

### 3.6 How a flight is sent is decided by measurement

S1b measured ways of sending several statements over the Hetzner pair's
SSH path (`experiments/postgres-commit-path/README.md`, full window, C=32):

| Form | Flights | Executions/s |
| --- | ---: | ---: |
| Extended-protocol pipelining (k3p; k1 likewise) | 2 | 381; fails the sizing rule at every C; stall root cause not isolated |
| One SimpleQuery message per flight with `EXECUTE` of prepared statements (k3) | 2 | 9,544 |
| One composed `UNION ALL`/`unnest` statement per level (k2) | 4 | 6,969 |

S1b's forms were read-only `REPEATABLE READ` executions. A READ COMMITTED
writer whose later command must see a commit made during its lock wait is
a different case, which RT5 qualifies.

The adapter uses the synchronous `postgres` crate (parent §8), which
cannot pipeline independently prepared calls (`tail.rs:58`). So B2 does
not assume extended-protocol pipelining. Two candidates are qualified on
the path S1b used, for correctness and for latency, before B2 lands. They
reach different counts, and §4 gives both:

- **(a) Ordered SimpleQuery flights.** One message holds several commands
  in order. An error stops the rest of the string, which gives §3.5's
  guard, and each READ COMMITTED command takes its own snapshot.
  Arguments travel as literals to `EXECUTE` of statements prepared with
  typed parameters. There is no Bind, so the adapter's pre-bind NUL guard
  (`Tx::query`, `Tx::execute`) never runs. The **literal encoder** becomes
  the chokepoint instead: one encoder, used for every flight, that refuses
  NUL with the same typed `E_INPUT` and transaction-poisoning semantics
  (rule 1), and encodes every port value type (NULLs, numeric bounds, text,
  bytes, and arrays, including the tail's eighteen array parameters,
  `tail.rs:62–78`). Rows come back as text and are decoded against the
  prepared types. Adopting (a) amends parent §9.1 rule 5 to: values reach
  the server either as Bind parameters, or through that encoder into
  statements prepared with typed parameters. RT5 qualifies the encoder and
  the text decode by difftest against the binary path for every type.
- **(b) Attach-installed envelope functions,** in `VOLATILE` PL/pgSQL only.
  A small fixed set, installed and shape-validated at attach like any other
  DDL (rule 6), for example `sb4_open(token, store_id, digest, now, op)`:
  fence that raises on mismatch, head lock, generation check, authority
  facts and receipt re-check, as separate statements, returning the head,
  generation, authority facts and any receipt. Arguments are Bind
  parameters, so rule 5 holds as written. Each statement inside a
  non-inlined `VOLATILE` PL/pgSQL body takes its own snapshot under READ
  COMMITTED, so the later statements see commits the head lock waited on.
  A SQL-language function can be inlined into the calling statement, and
  then shares that statement's snapshot, so SQL-language functions are
  excluded. A function cannot contain `BEGIN`,
  `SAVEPOINT`, `RELEASE` or `ROLLBACK`, so framing stays in separate
  argument-free simple messages. These functions read the store's own
  tables and evaluate no program, rule or expression, which keeps them
  within what LLP 3000.009 §4.1 lets the store take.

RT5 adopts (a) if its encoder passes the difftest and its latency holds;
otherwise B2 is (b)'s counts. Extended-protocol pipelining is excluded
unless its S1b stall is explained and removed.

### 3.7 SQLite gets the same structure

The changes are structural, so they apply to both stores. On SQLite they
remove statements rather than round trips: RT-A's isolated savings for the
tiny increment are 8 (preflight head), 11 (post-commit re-reads) and 20
(duplicate authority snapshots), taking 79 statements to about 40.
SQLite's transaction modes do not change: `BEGIN IMMEDIATE` for writers,
WAL read transactions for readers. SQLite's first lock is `BEGIN
IMMEDIATE`, not a row fence; the fence and envelope functions of §3.5 and
§3.6 belong to the Postgres adapter.

## 4. The budgets

Budgets count **dependent flights** of a warm request: messages whose
response must arrive before the next can be sent (a Sync or a simple Query,
through ReadyForQuery). Cold costs (first reader construction, first
prepare) are tracked separately, per physical connection, and are not part
of the request budget.

| Request class | Today | B1 | B2 (a) | B2 (b) | B3 (not adopted) |
| --- | ---: | ---: | ---: | ---: | ---: |
| Point read, one dependent row (W1) | 23 | 6 | 3 | 5 | 2 |
| List read, addresses fixed by arguments (W2) | 23 | 6 | 2 | 2 or 4 | 2 |
| Unkeyed mutation, in place, three program flights | 57–58 | 16 | 8 | 11 | 2 |
| Keyed first attempt, same program, id + store_id | 77 | 21 | 9 | 12 | — |
| Replay hit, id + store_id | 30 | 5 | 2 | 2 | — |
| Action session, W1, one parent family | 29 | RT0 | RT0 | RT0 | — |
| Unauthenticated / rate-limited refusal | 0 / 0 | RT0 | RT0 | RT0 | — |
| Unknown-token refusal | 5 | RT0 | RT0 | RT0 | — |

## 5. The ratchet

A counted wrapper around the driver, compiled only under `cfg(test)` or a
test feature, counts dependent flights per request. It can start from the
adapter's existing call counter (`Store.calls`, `engine/postgres/store.rs:81`),
which counts exchanges the way the synchronous driver makes them. A
test suite drives each request class of §4 through the real `serve` HTTP
path and asserts the count against a checked-in table. A change that lowers
a count must lower the table; one that raises it fails.

There are two tables:

- **SQLite statements, on every landing.** This is the guard that runs
  everywhere, because it needs no cluster.
- **Postgres flights,** in `scripts/test-postgres.sh` on a private cluster,
  as for every other Postgres case. They are named ignores without one.

Both start at RT0's measured counts and move down with each increment. It
is the same idea as the C1 call-count ceilings S10c already asserts for the
engine, extended to the whole request and to every class, including keyed
attempts, replay hits, action sessions and refusals.

## 7. Correctness constraints

- **Authority freshness.** A revocation or expiry committed before the
  final check refuses. For an in-place mutation one cannot commit after it
  (§3.1). For a pre-executed member it is caught by validation, as
  committer §3.6 specifies. Tests: revoke during body upload; revoke while
  queued; expiry while queued; supervisor-family change while queued; each
  for a first attempt and for a replay.
- **Store binding before replay.** A keyed retry that names a replaced
  store gets `E_STORE_REPLACED`, not another store's receipt, in preflight
  and when the store is replaced while queued (the existing wrong-store
  regression, `tests/serve_store/mod.rs`). A resent id with another
  operation or other wire arguments gets `E_ID_REUSED`.
- **Replay before judgment.** A resent id replays its stored outcome after
  its operation is renamed, its arguments narrowed, or it becomes
  ephemeral; a replay during ownership loss still answers; two concurrent
  copies of one id apply once (the in-transaction re-check); in a batch, a
  member's hit aborts only that member.
- **No authority cache across requests.** Bearer sessions are not tied to
  HTTP or Postgres connections, and a TTL or best-effort notification is
  not an invalidation protocol. RT-A found no safe saving from one. A
  proposal for one needs an authoritative version protocol with loss and
  reconnect handling, and its own RFC.
- **Snapshot consistency.** Within each snapshot, generation, head, rules
  and rows agree, as today. A snapshot is never held across a body upload
  or a queue wait and then treated as current.
- **Ownership (parent §5).** The owner fence remains the first lock of
  every Postgres writing transaction, as its own command. A cached token or
  a live lease is not continuing proof of ownership.
- **Commit outcomes.** COMMIT stays its own flight; unknown-outcome COMMITs
  carry no metadata and keep their classification.
- **Same outcomes on both stores.** Store oracles and difftest compare
  outcomes for every increment, as for any adapter change (parent §9).

## 8. B3, and the rule that would reopen it

The raw-Postgres control does W1, W2 and W4 in **one prepared autocommit
statement each**, with membership authorization inside it and token
verification outside the database. Matching it within 2× means two
flights per request: early live authority, then one statement that is the
whole request. For a mutation that statement would evaluate the program's
rule checks and writes in the database. LLP 3000.009 §4.1 lets the store
take batched reads and the commit tail, and does not let it evaluate a
rule, an expression or a filter. B3 would be a second executor, and S10e
is retiring the last one.

Reads and mutations are separate questions. A bounded read such as W2
can be one composed statement that fetches the authority facts, the
membership and the page, with the Rust interpreter still evaluating rules,
metering and building the outcome. That is access batching, which §4.1
allows, and B2 already counts W2 at 2. Lowering a *mutation's* semantics
into the database is what §4.1 forbids.

So B3 is not adopted. The rule that governs the next step is LLP
3000.009.001.002 §8: if W1–W3 p50 still exceed **3×** raw Postgres at
0.5 ms RTT after B2, commission the next **access-boundary** step: batch
the program's same-level reads into one flight (S1b's k2/k3), keeping all
semantics in the Rust executor. Lowering stays declined unless that step
also fails the same rule. B2's read count is about 3× raw's network floor
whenever RTT dominates, so the access step, not lowering, is the likely
next move.

The follow-up is chosen from the measured bottleneck, not from which
workload missed. A W4 or W5 miss whose time is in commit serialization or
durability goes to the committer track (K3/K4), not to read composition.
A latency miss is first checked against a matched transport and locality
comparison where one is deployable, before it is attributed to the
interpreter.

## 9. What this changes in the sibling plans

- **The committer.** K3 keeps its value as the serial-section win: it
  shares the durable transaction's framing across members. It is not the
  fix for request latency. Only keyed members share a batch (committer
  §3.4), so the 1.13× figure above is an illustration for an unkeyed
  shape, not a sizing result; K3 is sized on the keyed classes RT0
  measures. Whole-request latency, reader-connection occupancy and serial
  commit work are sized separately. Its sizing keeps S1b's form: the execution stage
  is the program's flights plus the one authority statement this RFC moves
  inside snapshot S; the commit stage is the batch's framing. The whole
  request budget is not substituted for `k_exec`; that would count the
  commit stage twice.
- **The scale study.** The S1 Postgres cell reports its flight count per
  request class next to its throughput and latency. It runs first at the
  current counts (after maintained columns land, P1-MC), then at B1 and B2,
  so the ledger shows what each step bought.
- **The port.** The read API's snapshot-per-call shape (§3.3) is a port
  change, recorded in the parent's §3 when RT4 lands.

## 10. Alternatives considered

- **Do nothing until K3/K4.** Pre-execution scales throughput with
  connections and collapses the four resolutions, but each request still
  pays the response heads, the post-commit re-reads and the framing, and
  holds connections while it does.
- **Cache authority per connection or per bearer.** Rejected in §7.
- **Pipeline today's statements.** About 49 flights for a mutation and 17
  for a read (RT-A), and S1b measured extended-protocol pipelining stalling
  on the real path. The repeated work is the larger term.
- **Co-locate `serve` with Postgres.** A Unix socket on the same host
  (about 0.05 ms) shrinks every flight, and that is the right deployment
  where it is possible. It is not available on managed Postgres, which is
  the target, and the scale study treats the co-located cell as a reference
  only. It does not replace the budget.
- **Lower each request server-side now (B3).** Not adopted, §8.

## 11. Open questions

1. Does ingress need a database round trip at all, or can it check only
   the bearer's form, leaving the final check as the only live one? It
   saves one flight per request, but an unauthenticated client could then
   make the server buffer bodies. The answer may differ for `/q` (no body)
   and `/m`.
2. Should the response head be omitted for successful unkeyed mutations
   when the client did not ask for it?
3. Can a read that is one statement skip `REPEATABLE READ` framing, since a
   single statement is one snapshot under READ COMMITTED? Under B2 the
   framing rides in the flight, so the saving is CPU, not a round trip.
