## Summary

The parent RFC moves applications that outgrow SQLite to Postgres. Its own
measurements show that Postgres is slower per operation: a page costs about
5× SQLite, and today's commit path reaches about 120 commits/s at a 0.5 ms
round trip, against about 4,000/s for SQLite under `serve`. The reasons to
move are operational. A reviewer asked whether **replicated SQLite** —
SQLite kept as the store, with streaming replication, point-in-time
recovery, fenced failover and perhaps read replicas — would meet most of
those needs for much less work. This note answers that question from
primary sources and from Snapback's own prior art.

The findings:

- **Asynchronous LTX streaming to an object store is mature, cheap, and
  meets the backup and PITR need.** Litestream 0.5 is the reference.
  Snapback 1 already vendored a Rust port and ran a fenced asynchronous
  lane through a kill drill (LLP 0188). Snapback 4 today has only a
  stopped `cp -a` backup.
- **Asynchronous replication cannot give lossless failover.** It is
  disaster recovery, not high availability. It maps exactly onto child A's
  `async` HA mode, whose default is a new incarnation.
- **Lossless replicated SQLite exists, but no maintained library offers it
  in a form Snapback can embed.** Cloudflare's Durable Objects, Turso Cloud
  and celld each acknowledge a write only after it is replicated, and each
  is a platform rather than a component. dqlite does it with Raft but
  replaces the in-process connection. rqlite and Hiqlite replicate
  statements and cannot run an interactive program. Building it into
  Snapback means owning a replication and takeover protocol.
- **Replicated SQLite is better where Postgres is weakest,** in per-store
  write rate and read latency, and weaker where Postgres is strongest:
  provider-run failover with an SLA, a separate database host, very large
  stores, and organizations that require Postgres. Neither store serves
  the SQL ecosystem directly, because both hold the generic layout.

**Recommendation** (§8): both, in sequence. Give every SQLite store
continuous LTX backup and PITR first (tier R1). It is the cheapest large
gain and makes replicated SQLite the default production durability for
single-host deployments. Keep Postgres P0 and P1 as commissioned, as the
high-availability and managed-operations path. Hold synchronous replicated
SQLite (R2) as the named alternative that child C's evidence can trigger.
Confidence is moderate; §9 lists what would change it.

## 2. Evaluation axes

### 2.1 The needs (parent §2)

| # | Need | What it means concretely |
| --- | --- | --- |
| N1 | Operator trust | Continuous backups, point-in-time recovery, a replica, failover without loss, ideally someone else's SLA |
| N2 | More than one serving host | Survive a host failure; rolling deploys; more CPU for reads, sync and polls |
| N3 | A larger store | More than one disk or one file comfortably holds; restore and reseed times that stay bounded |
| N4 | Write concurrency | A per-store commit ceiling set by the database, not by round trips |
| N5 | The SQL ecosystem | Reporting, BI tools, extensions, familiar operations tooling |

### 2.2 Snapback constraints

Any store, replicated or not, must keep these (LLP 3000 §7, parent §3):

| # | Constraint | What it rules out |
| --- | --- | --- |
| K1 | One total commit order per store | Leaderless or multi-writer replication |
| K2 | Exact snapshots: a snapshot at watermark W holds exactly the commits at or below W, with no gaps below a published watermark | Replicas that apply partial transactions, or that publish a watermark the failover can lose |
| K3 | Store-held fencing: a deposed owner commits nothing that counts, including writes that advance no head (revocations, sessions, receipts, pins) | Fencing by host clock or by a file lock that two hosts cannot both see |
| K4 | The store is a logical identity; a copy is never the same store by accident; restore is a new incarnation | Physical copies that carry `store_id` without a rule about when they may serve |
| K5 | Devices hold replicas and watermarks; a lost acknowledged commit can be refilled under the same sequence | Lossy failover under the same incarnation |
| K6 | Durable work: effects, attempts, leases and worker completions survive with the store, and no handler runs twice unnoticed | Dispatching work before its claim is durable |
| K7 | The one-process `serve`: one `FairMutex<Engine>`, in-process hubs, the interpreter calling `Rows` many times per operation | Designs that put a network hop under every `Rows` call |

K7 is why the commit path dominates the Postgres plan. It is also why
statement-replicated systems fit badly (§3.2).

### 3.2 What the survey shows

The systems fall into four classes. Only two of them fit Snapback.

1. **Physical, asynchronous** (Litestream, LiteFS, Verneuil, celld-ltx in
   async mode). They keep K1, K2 and K7 intact, because the engine still
   commits to a local SQLite file and replicas apply whole transactions.
   They lose the tail on failover.
2. **Physical, synchronous** (celld, Durable Objects, Turso Cloud, dqlite,
   regional disks). They keep acknowledged writes. All but dqlite and
   regional disks are platforms. dqlite holds the write lock across the
   quorum round trip and moves the connection out of process.
3. **Statement replication** (rqlite, Hiqlite). The replicated unit is a
   SQL batch. Snapback's unit is a program that reads, decides and writes,
   so it would have to replicate whole mutations as deterministic commands.
   That would be a new state-machine-replication design, not an adoption.
4. **Leaderless or CRDT** (Marmot, cr-sqlite). They violate K1.

Two facts recur across the classes. First, **every lossless system gates
its output on replication**, not only its commits: Durable Objects' output
gates, celld's acknowledgement rule, and Postgres holding a waiting
transaction's locks "until the transfer is confirmed"
([Postgres §26.2.8.3](https://www.postgresql.org/docs/current/warm-standby.html)).
Second, **every fenced system puts the fence where durability lives**:
in the bucket (celld's epoch), in the quorum (Raft terms), or in the disk
attachment (force-attach).

## 4. Snapback's own prior art

Snapback 1 accepted LLP 0188 on 2026-08-06 and built most of its
self-hosted lane in three days:

- **Vendored** celld's `crates/ltx` at `553ae73f` into `vendor/celld-ltx`.
  It is a Rust port of Litestream v0.5, format-pinned to LTX v0.5.1, and
  its conformance suite ran 172 tests, including 5 byte-for-byte
  differential cases against the Litestream v0.5.11 binary
  (`issues/closed/20260806-llp-0188-ltx-implementation-g1.md`).
- **Landed the G2 async lane** (`6c90c98b5`,
  `crates/snapback-services/src/replication.rs`, 2,664 lines): the
  replicator as sole checkpoint owner, a restorable frontier, encrypted
  keyring snapshots, refusal fencing through a sidecar incarnation and a
  conditionally updated head, `snapback replicate status|checkpoint|restore`,
  and a MinIO SIGKILL drill under load.
- **Found a real defect on the way.** The port had omitted Litestream's
  persistent-WAL setting. Another connection's close-time checkpoint then
  wedged capture. Every connection that touches a replicated database must
  set it.
- **Shelved the hard parts**: succession, the full fencing matrix (G2f)
  and the hosted lane (G3) wait for demand
  (`issues/shelved/20260810-llp-0188-*`).

So the asynchronous lane is a known quantity with a known trap. Snapback 1
never built synchronous replication.

## 5. Fitting replicated SQLite into Snapback 4

### 5.1 Three tiers

| Tier | What it is | Meets |
| --- | --- | --- |
| **R1** | Continuous asynchronous LTX shipping to an operator's bucket; PITR restore; a warm standby that restores from the bucket | N1's backup and PITR. Failover loses the tail |
| **R2** | Synchronous replication: each durable write reaches a follower's disk or the bucket before anything that reveals it leaves the process; fenced takeover that first recovers the acknowledged tail (celld's design) | N1's lossless failover; N2's host-failure survival |
| **R2b** | The SQLite file on a synchronously replicated regional disk, with force-attach takeover | The same as R2 on one cloud, with the provider doing the replication |
| **R3** | Read replicas: LTX streamed to further hosts that serve queries, sync pages and polls at their applied watermark, with mutations forwarded to the owner | N2's read capacity; the analogue of the parent's P2 |

### 5.2 The output gate makes R2 correct, and it is also R2's throughput story

A SQLite commit is visible to every later reader in the process before any
replica has it. R2 therefore needs the rule celld and Durable Objects use:

- **Nothing leaves the process until the replicated frontier covers what it
  reveals.** That covers mutation responses, query and sync responses, held
  change polls, effect claims handed to workers, refusals that read state,
  and asset grants. Each response records the internal revision it read or
  wrote, and waits until the frontier passes it.
- **The internal revision already exists in the plan.** Child A §6.3 gives
  every durable write, including writes that advance no head, a revision in
  the committer's stream. The gate reuses it. A revocation that has not
  replicated has not been acknowledged, so losing it is safe; the revoker
  retries.
- **Losing a suffix is then safe.** Replication ships in commit order, so a
  failover loses only a suffix. Nobody outside saw that suffix, so it may
  be refilled under the same sequence numbers (K5). Worker claims are
  gated too, so no handler starts on a claim that a failover can erase
  (K6).

Because the gate holds output rather than the write lock, commits pipeline.
The single writer keeps committing locally while earlier commits replicate.

### 5.3 Fencing and identity

- **The fence lives at the durability target** (K3). A deposed owner can
  still write its local file, but nothing it writes becomes acknowledged:
  in R2 the followers reject an older epoch, and a bucket proof re-reads
  the ownership record, as in celld. Child A's principle, that ownership
  belongs to the store, carries over with "the store" meaning where
  acknowledged history lives.
- **Clocks.** Litestream's lease judges expiry by host time. Child A §5.1
  forbids that for safety. R2 must take celld's approach (epochs, CAS and
  re-reads) and use time only for liveness.
- **Copies carry `store_id`** (K4). A physical replica or restored file
  contains the same identity row. LLP 0188 kept the replication incarnation
  in a sidecar and the bucket head for exactly this reason. R1 and R2 must
  mint a new incarnation on every restore to an earlier point, as LLP
  3000.009 §9 requires, and allow the same incarnation only for a takeover
  that recovered the whole acknowledged tail.
- **HA modes map one to one** onto child A §5.4.1: R1 is `async`, with
  `new-incarnation` as the default and `continue` as the operator's
  choice; R2 and R2b are lossless modes. Devices, sessions and graduation
  rules need no new semantics.

### 5.4 Predicted throughput

From S0's constants on its host: SQLite execution about 160 µs, flush
77–79 µs, and 3,700–4,200 commits/s under `serve` (child C §2). Let `R` be
the round trip to a follower and `F′` its flush.

| Design | Per-store commit ceiling | At R = 0.5 ms |
| --- | --- | --- |
| Local SQLite today | `1/(exec + F)` | about 4,000/s (measured) |
| R1 | Unchanged; replication runs beside the writer | about 4,000/s (predicted) |
| R2 with the output gate | Unchanged; latency rises by `R + F′` plus batching | about 4,000/s, with about 0.6 ms more latency (predicted) |
| R2 holding the write lock (dqlite's shape) | `1/(exec + F + R + F′)` | about 1,200/s (predicted) |
| Postgres, reference committer | `2.05 ms + 11.98 × RTT` serial time | 120/s (measured) |
| Postgres, optimistic committer (a) | Sizing target | ≥ 1,000/s and 25% of raw Postgres (target, not yet built) |

Reads stay in process on R1 and R2, so a page keeps SQLite's cost rather
than the 5.22× of Postgres (W9). These are predictions for an idle
single-region pair. Disks whose flush costs milliseconds would move every
SQLite row down; the `450b` host's 165/s (child C §2) is the warning.

Two needs are met only by Postgres: a provider's SLA, and an organization
that requires Postgres. Two favor SQLite: write rate and read latency. The
rest are met by either, at different costs.

## 7. The work in Snapback 4

**Shared by both paths** (already commissioned or required by either):

- P0's extraction: the durable-state contract, the rule that only an
  adapter touches a connection, the fenced `StoreTx`, and the `Committer`
  seam. R2's gate attaches to the same seam.
- `BlobStore` for asset bytes and release trees (child A §4.2). A standby or
  replica cannot see local files on either path, and PITR must cover them.
- Worker completions moved into the store (child A §4.3).
- The declared HA mode, identity checks at acquisition, and `doctor`.
- An ownership lease with fencing tokens. Postgres keeps it in `_owner`;
  replicated SQLite keeps it in the bucket or the quorum.

**Postgres only:**

- Adapters for every durable-state family: about 10,000 lines of
  `rusqlite` across 23 files of `snapback4-core` (parent §1), plus parity
  for the refused features.
- The optimistic committer (a), which Postgres needs to reach a production
  write rate.
- Layout v1, roles and connections, and the P2 `Notifier`.
- Live graduation (child B), because a move between engines needs a
  logical copy.

**Replicated SQLite only:**

- R1: the replication lane on the Snapback 4 store. Snapback 1's lane is
  the template, and the vendored crate is already in the repository.
  The persistent-WAL rule applies to every connection the store opens,
  short-lived ones included. Restore mints a new incarnation;
  `doctor` checks the bucket's conditional writes, as celld's storage test
  does. Size: comparable to Snapback 1's G2 lane.
- R2: the output gate over every response path; a follower receiver with
  epoch fencing; takeover that seals the predecessor and recovers its
  acknowledged tail; witnesses for SIGSTOP, partition and crash windows.
  Size: large, and its risk sits in a distributed protocol. Four review
  rounds on child A §5 found their most serious defects in each round's
  newest mechanism (parent §9). R2 would be more mechanism of that kind,
  with no provider sharing the burden.
- R2b: mostly qualification, with a measured flush cost; one cloud only.
- R3: replica serving at a watermark, mutation forwarding, and replica
  reseed. Comparable to P2.

A store moving from R1 SQLite to Postgres still needs child B, and a move
between SQLite hosts under R2 is a takeover. Replicated SQLite therefore
does not make graduation unnecessary for applications that later need
Postgres. It does defer it, perhaps indefinitely, for applications whose
only need was N1's backup.

## 8. Recommendation

**Both, in sequence.**

1. **Commission R1 now**, beside P0. Every SQLite store gets continuous LTX
   shipping to an operator's bucket, PITR restore as a new incarnation,
   and a warm standby that restores from the bucket under child A's `async`
   semantics. Reasons:
   - Snapback 4 has no continuous backup at all today (LLP 3000.008.004
     §8), and SQLite remains the default store.
   - It meets the most common reason in parent §2 for a fraction of
     Postgres's work. The format is standard, the Rust crate is vendored,
     and the lane has been built once.
   - It changes nothing on the commit path, so the ~4,000/s ceiling and
     in-process reads survive.
   - It needs a Moves line in `NOT-DOING.md`.
2. **Keep Postgres P0 and P1 as commissioned,** as the path for lossless
   failover run by a provider, a separate database host, very large
   stores, an SLA, and organizations that require Postgres. Those needs
   are real and replicated SQLite cannot meet them without Snapback
   owning a replication protocol.
3. **Do not commission R2 now.** Record it, with the output gate of §5.2 and
   celld's protocol as its starting design, as the alternative that child
   C's evidence triggers (§9). If it is built, Postgres remains the
   ecosystem and managed-operations path.

In short: replicated SQLite becomes the default production durability for
single-host deployments, and Postgres is the high-availability path,
unless Postgres's measured write ceiling makes lossless replicated SQLite
the better high-availability path too.

**Confidence: moderate.** About 75% that R1 is worth doing first, because it
rests on mature components and Snapback's own prior run. About 60% that
Postgres rather than R2 should be the high-availability path, because that
judgment rests on predicted throughput, an unbuilt committer (a), and an
estimate of protocol risk rather than a measurement.

## 9. What would change the recommendation

| Evidence | Effect |
| --- | --- |
| Child C S1a: the sized (a) misses the bound of ≥ 1,000 commits/s and 25% of raw Postgres at 0.5 ms, or S1 shows page latency binding for a named workload | Raise R2 to the high-availability path for throughput-bound applications; Postgres keeps N1-SLA, N3 and N5 |
| A bounded R2 prototype: one follower and the gate reach ≥ 2,000 commits/s at 0.5 ms, and takeover passes child A's SIGSTOP, partition and crash witnesses | Cuts R2's risk estimate; R2 becomes a candidate alongside P1 |
| celld publishes its replicator and ownership logic as a separate crate, or Litestream ships synchronous replication with epoch fencing | Cuts R2's cost toward R1's |
| Applications that outgrow SQLite cite mostly backup and restore | Postgres's priority drops after P1 |
| They cite an SLA, a managed provider or an organizational mandate | Postgres only, as planned; R1 still stands for small deployments |
| A measured regional-disk flush cost keeps SQLite above 1,000 commits/s | R2b becomes a cheap lossless mode on that cloud |
| A store-size study finds reseed time binding well below Postgres's comfortable sizes | Strengthens Postgres for N3 |

## 10. Unverified and open

- **UNVERIFIED:** whether celld's replication and ownership logic can be
  used outside the `celld` crate; dqlite's Rust bindings and its users;
  libSQL server's failover semantics; Hiqlite's transaction model beyond
  its README; regional-disk flush latency; how long Litestream retains
  restore points under compaction on real buckets.
- **Not measured:** every replicated-SQLite figure in §5.4, and reseed
  time against store size.
- **Open for R1's design:** whether the warm standby continuously restores
  (as Litestream's VFS hydrates) or restores on takeover; and how blob and
  release-tree retention matches the bucket's PITR window (child A §4.2's
  rule applies unchanged).
