**Author:** Codex for Charlie Cheever
**Date:** 2026-10-16
**Revised:** 2026-10-16 (revision 1)
**Related:** [LLP 3000.014](./3000.014-a-child-reads-through-its-parent.rfc.md), [LLP 3000.036.000.000](./3000.036.000.000-union-sync-audiences.rfc.md), [LLP 3000.039](./3000.039-a-reference-declares-what-deleting-its-row-does.rfc.md)

## 1. Intent and authority

Wave 14 lanes 007, 032 and 085 need a child readable by its parent's
**current** department roster. An immutable copy means creation-time access;
an application-maintained copy means the builder must maintain the invariant.
Neither is the intended language end game.

Propose `read through live .parent` as the child's entire read rule. Its
required immutable reference names one ordinary application table, with no
default. For a live child C and viewer V, the rule means: C's referenced
parent P is live, and P's complete read rule currently admits V. It does not
mean a bare existence test. Missing, dormant, expired, or unknown parents
never grant authority, including underneath negation. Service grants remain
on P and do not create device audiences. No conjunction or alternate child
read rule is accepted. Existing captured `read through` is unchanged.

The first implementation is commissioned to RULES4 on 2026-10-16, conditional
on both independent reviews marking the same revision READY. The user directs
a recipe fallback if the design has not converged after two review rounds.
This RFC is a proposal, never an implementation claim.

## 2. Evaluation and lifetime

Add a distinct live-through rule IR node naming the reference and parent.
Evaluate it against the current transaction on every read and asset access;
it invokes the parent's rule, including all conjuncts, rather than copying
policy fields. All live-through edges and captured-through edges form one
acyclic graph. Bound nesting by the schema, with a fixed authorization
reservation per node and per syntactic probe; denied/missing parents restore
the same caller-visible charge. Private parent field values never appear in
child outputs, cursors, or public refusals.

An inserted child still needs a live readable parent, plus its insert rule.
On updates/deletes the table's write rule remains independent; hidden denied
targets keep NOT_FOUND. The parent reference cannot change. An ordinary
reference has the existing nominal-id contract; a live-through edge adds
parent existence/readability at insertion. A parent delete retains the
captured-through physical-child restriction (unless an explicitly admitted
cascade deletes its complete closure). Sweeps remove children first. Parent
id reuse is blocked while any physical child remains. Thus an old child
cannot acquire authority from an unrelated replacement parent.

Live children use the current minimum of their own expiry and every current
ancestor expiry. Changing a parent deadline hides or reveals descendants
according to that current deadline, without trusting a stored capture. A
physical retirement remains irreversible and a later deadline cannot restore
physically removed rows. The query answer's next-expiry includes necessary
parent authorization witnesses. A child not-before or finite deadline cannot
be combined with live sync until the protocol below carries its time witness;
explicit online-only tables remain supported.

## 3. Completeness and invalidation

A page pinning `.parent = p` resolves p once. An admitted parent establishes
uniform read authority for that scope; a known absent/denied parent yields a
complete empty page. Unknown parent coverage on a device yields unknown,
never an invented empty complete page. Completion additionally requires the
child range, horizon and lifetime coverage under the ordinary rules. A page
not pinning the parent stays per-row filtered and may be capped. An aggregate
by the parent key may inherit that scope; an aggregate across parent keys
cannot claim uniformity without covering all of them. No copied-field
complete proof may apply to a live edge. LANG3 owns other completeness notes;
this proposal owns the live edge's proof and diagnostic.

Dependency analysis follows the full ancestor rule graph, all probed roster
rows, parent fields, lifetimes, child reference and selected child fields.
A mutation to a parent's department invalidates subscribed child reads even
when no child row changes. A roster revoke invalidates the same reads.
Broad table dependencies are a correct conservative implementation; stale
answers are not. A transaction's own later read observes its earlier policy
writes. Held device queries follow the same dependencies.

## 4. Sync without child fanout

For the initial invertible case, P's device rule must be exactly one existing
public, principal, or membership audience (after removing whole service
branches); child unions, retained history, timelines, row views and private
field owners are refused until separately designed. `sync` on C uses a
**parent-keyed scope**, not the parent's mutable department value copied into
every child. `sync ... last N by .index` bounds acquisition per parent scope.
This avoids a policy edit rewriting an unbounded population of children.

The server's scope grant is `(child table, parent id, parent policy epoch)`.
It computes viewer admission from the current parent rule and roster. An
ordinary child write appends to its parent scope. A parent policy change
increments the parent's epoch in the same transaction and changes its grants;
old recipients lose the scope and new recipients acquire it. The grant
resolver uses the parent audience index and a parent-to-child-scope registry,
not a walk of all child rows. Membership changes use that same resolver.
The work is proportional to the existing grant changes and number of schema
edges; it must not reserve a mutation allowance from hidden child counts.
Log compaction and bootstrap must preserve the latest epoch and its grant.

Delivery atomically applies a parent-authority descriptor, child scope grants,
revocations and their watermark in one response batch. A device can expose a
child only under a matching current authority descriptor; a newer child epoch
without that descriptor queues/falls back, while an older epoch is discarded.
Scope revocation removes all until-revoked child rows before observers run.
Ordinary offline staleness remains the existing last-applied-server-state
contract: no claim to learn a revocation while disconnected. At reconnect,
no response may mark fresh while retaining an obsolete grant. Ordered batches
must handle a revoke/regrant of the same parent before acquisition completes.

This is a protocol change. Old devices must refuse that generation and follow
the existing upgrade path, never evaluate the node as captured-through.
Prediction requires current parent and child coverage and all rule witnesses;
otherwise it queues. Predicted parent policy changes suspend affected child
completeness until authoritative grants arrive. Authority descriptors and
scope transitions are persisted atomically in both memory/IndexedDB and
SQLite device stores. A duplicate or out-of-order batch cannot resurrect an
obsolete epoch. Reused ids remain prohibited by §2.

## 5. Adoption

Captured-to-live, live-to-captured and edits of parent binding/rules are
generation changes. Activation validates all physical child links, refuses
missing parents by table/count in operator output, rebuilds the scope registry
and grant descriptors and replaces affected device generations. It does not
copy mutable policy into historical child fields. Dormant rows remain dormant
under the existing adoption closure. A live-to-captured change requires every
captured policy input to be immutable and recaptures it under LLP 3000.014.
Rollback revalidates the destination's invariants rather than trusting old
captures, and atomically restores its protocol/generation contract. No partial
adoption may publish new grants with old child descriptors.

## 6. Qualification and remaining design risks

Tests must cover: parent transfer with old/new overlapping rosters; roster
revoke/regrant; two-level policy chains; missing/expired/dormant parents;
parent deletion and id reuse; time boundaries; fixed hidden charges; uniformly
pinned and nonuniform pages and aggregates; assets; same-transaction policy
changes; held watch invalidation; memory and SQLite device stores; reorder,
duplicate, disconnect during bootstrap, revoke during acquisition and crash
between descriptor/grant/data persistence; adoption and rollback in both
directions; mixed old/new clients. Guide examples execute against a packed
consumer. Run the 100-schema census before/after and the differential oracles.

The principal risks needing review are whether the existing grant machinery
can index and meter parent-keyed scope admission without hidden-population
leaks, whether one atomic delivery batch suffices for multi-partition polling,
and whether mutable expiry can safely share existing sweep/retirement logic.
The proposal requires those properties; it does not claim they already exist.
A reviewer should mark NOT READY if an executable algorithm or a bounded
representation is missing. The recipe fallback keeps this RFC in Review and
records the exact unresolved questions rather than shipping partial authority.
