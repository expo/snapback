## Summary

Calibration #20 (0.4.1) charged three of its five weakest categories for the same thing: the Following view.

| Category | Score | The scorer's charge |
|---|---:|---|
| `queries_and_live` | 82 | "Following's 1,000-event backfill limit and full-source-sync requirement; `E_TIMELINE_SHAPE` rejected bounded acquisition" |
| `scale_and_limits` | 78 | "cold multi-route browser flow took 42.324 seconds; required full public sync and rejected acquisition bounds remain material" |
| `client_integration` | 83 | "acquisition, admission and online fallback as demanding integration boundaries" |

The view requires its sources to declare `sync public` with no horizon. Its generated event table does the same. So every cold device acquires every public post, repost and event before a Following page is complete offline. At the scale fixture that is 50,228 posts and as many events.

This RFC changes only **acquisition**. Delivery, the inbox's contents, the history window and prediction of an author's own post are unchanged.

1. **Sources may be bounded, and events follow them.** `posts` and `reposts` may declare `sync public last N by .at` or `online only`. The owned event table follows its sources: a device holds the event of every post and repost it holds, exactly while that event exists (§2.1a). The application's `follows` may take any public residency.
2. **The inbox may be bounded per reader.** The reader's owned inbox syncs with a per-reader floor of the newest M copies. By default, M equals the history window.
3. **A page never shows a hole.** On a device, a Following page, or any query that shapes it with cards, is either answered from held rows or withheld. Online, the withheld page is answered by the server. Offline, it is `loading`. A null card is never published as data.

## 2. What changes

### 2.1 Admission (`bind/timeline.rs`)

| Table | 0.4.1 | This RFC |
|---|---|---|
| posts (originals) | public, `sync public`, no horizon | public, and `sync public`, `sync public last N by .at`, or `online only` |
| reposts | the same | the same as posts |
| follows (edges) | public, `sync public`, no horizon | public, with any residency a public table has: `sync public`, `sync public last N by …`, or `online only`. A device filters a Following page by the reader's owned edges (`@T@Edges`), which sync to the reader, and edge transitions are server sites. So the view never reads the application's follows on a device. Application queries and rules that read follows inherit its residency, as for any table |
| owned events (`@T@Posts`) | `sync public` | each kind follows its source row (§2.1a): full sync while that source is fully synced; otherwise a device holds the event of every source row it holds, exactly while it exists. The table carries no horizon |
| owned tombstones (`@T@RemovedEvents`) | `sync public` | unchanged: full sync, because removal must always reach a device (§3) |
| owned inbox (`@T@Feed`) | `sync` to its reader | `sync` to its reader, with a floor of the newest M copies over `byReaderPage`, the index the Following scan uses. M defaults to the history window, 1,000, as one merged suffix per reader, not per author |

- **A floor is global and non-sliding.** `sync public last N by .at` makes a cold device acquire the newest N rows of the whole table, whoever it follows. Nothing evicts a row after acquisition, and the floor is fixed at acquisition time; this is how horizons already behave.
- **A source horizon's index must be the source's mapped time column plus `id`.** This applies to `posts` and `reposts` only. An `id`-ordered or other index is refused, with a rewrite, because the floor must be the newest events. The inbox floor is always on `byReaderPage`, because a horizon page is locally known only when the floor's index is the scan index.
- **Everything else is unchanged:** owner write authority, immutable mapped fields, one-way removal, the unique pairs, and no expiry on sources.

### 2.1a Owned events follow their source rows

An owned event is a function of its source row:
- **An original's event** has the post's id, author and time. It exists exactly while the post passes the originals filter and has not been removed.
- **A repost's event** has the repost's actor and time, and the original's post and author. It exists exactly while the repost row exists. Removing the original leaves it, as today.

So a device needs an event only when it holds the event's source row.

- **Each source row records its own event.** The engine keeps an **event slot** on every post and repost row, **one per Following declaration and source role**. Two declarations may share a source table, and each has its own originals filter and its own event ids. A slot is an engine column, like LLP 3000.014's captures and like maintained columns: the application cannot declare, write or read it.
  - On a post, a declaration's slot says whether that declaration's original event is live. The event's id is the post's id.
  - On a repost, it holds that declaration's repost event id, or null.

  The transition that inserts or deletes an event sets or clears its own slot **in the same commit and in the source row's own image**.
  - The slot is prepared before the source row's write and its log accounting, so it rides that write rather than following it as a second update.
  - For an insert or a removal's update, the image written already carries the slot.
  - An upsert's insertion preflight skips engine slots just like an ordinary
    insert. Full row validation runs after the slots are prepared; a required
    slot without a default cannot refuse an otherwise authorized insertion.
  - An unrepost is the source row's delete, which removes the slot with the row. The server reads the event id from the pre-delete image.

  So the slot is part of the source row's image. The ordinary machinery logs it, normalizes it, snapshots it, stages it, catches it up and syncs it with that image. Deleting a source row deletes its slots. Replacing an image, including under a reused source id, replaces them atomically. Removing one declaration drops its slots and leaves the others'.
- **Residency.** Each kind of event takes its source's residency:
  - with a fully synced source, that kind is fully synced;
  - with a floored source, the kind is **partial**: a device holds the event state of exactly the source rows it holds, in their event columns. The source rows held are exactly those the source's horizon admits: the acquired floor's rows and every later row the horizon accepts, which is every later row while the floor is `whole`. That set is never re-derived by comparing times;
  - with an `online only` source, that kind is **online only**, and a device holds no event state for it.

  A kind is **not fully synced** when it is partial or `online only`. Every rule below that names such a kind applies to both.
- **A device keeps no owned event rows of a kind that is not fully synced.** On a device, the owned event table holds only fully synced kinds' events, and their raw log entries apply as today. Raw entries of a kind that is not fully synced are not stored.
  - The server does not pair anything at serving time. Nothing depends on raw-entry order, a raw delete's kind, or event ids never being reused.
  - Three traps the revision-7 to revision-9 reviews found all dissolve. Birth accounting logging an event before its source's final image: the final image carries the column. A normalized put carrying a later removal: its column is already cleared. A repost deleted and recreated, or deleted before catch-up serves its insert: the source row's own put or delete carries it.
- **The mechanism is constrained.** The owned table stays `sync public` with no horizon, so its log serves the fully synced kinds. The horizonless snapshot walk filters out kinds that are not fully synced on `repost`. Do not set `sync.horizon` on the owned table, and do not clear its `sync`.
- **Activation.** Adopting event slots fills them from owned events inside one activation transaction at a pinned time. An already-declared Following preserves those events; a first-use Following over populated sources constructs them with [LLP 3000.026 §4](./3000.026-following-over-a-populated-store.rfc.md#4-atomic-launch-adoption)'s atomic **start this feed now** contract: all retained own events and newest 1,000 live events per current follow, no refill on removal. Original ids stay post ids; repost ids and edge epochs are fresh, with no reconstruction of delivery history. Dev launches automatically; deploy requires `--allow-feed-adoption`; above 5,000,000 copies it refuses before activation. `check` uses the same runtime preflight, retirement plan and predecessor-expiry predicate at a pinned time. It excludes exactly the affected rows activation retires, writes no rows or work tables, and reports `N_TIMELINE_ADOPT` at the declaration with the contract, copies, estimated lock time and deployment flag, or `E_TIMELINE_ACTIVATE` with the refusal and planned `home` alternative. Writes and syncs wait during launch; detached readers retain the predecessor. Each post receives its live bit and each repost its event id, or null when `byActorPost` misses, before generation publication. This retains LLP 3000.014 §7's atomic scan-and-fill boundary.
  - **A slot has no literal default.** A slot not yet filled is never event absence. The fill runs before `assess` and before row validation, and it does not log, as maintained-column activation does not.
  - **The shapes are fixed.**
    - A post's slot is a **required bool with no default**. False means "filled, and not live". A missing slot is not false. It is not a maintained column either, because a missing maintained field reads as 0. Activation fills it before validation, so the server never holds a post without it.
    - A repost's slot is an **optional id**. Null means "filled, and no event".
  - **Any generation that adds either slot makes `keeps_literal_default_images` false**, even when the same generation also adds a literal default on any table. So `adopt` clears the device's source images and its acquisition, and the device answers nothing from these tables until it has applied the snapshot that carries the filled slots. A device therefore never holds a source row whose slot was not filled. Otherwise an unfilled optional slot would materialize as null, meaning event absence, and a device would refuse `FEED_POST_NOT_FOUND` for every post whose snapshot page had not arrived yet.
- **No time boundary.** Event state is never acquired by time. "Every event of that kind at or after the floor's oldest time" can overfetch without bound on timestamp ties, and a repost event's minted id sorts independently of its repost's.
- **The three transition lookups read the witness's event column,** so they are decidable on a device. Revision 2 floored events by their own count. A held post's event could then lie outside the event floor (Grok's scenario A), and a miss could not tell "never admitted" from "outside the floor" (scenario B). Here each lookup reads the event column of a source row the device holds:
  - **repost insertion** reads the original post, then its event column. The event is live, or it is absent because the post is a reply, was removed, or fails the filter. A known absence refuses `FEED_POST_NOT_FOUND` on the device, as full sync does today;
  - **removal** reads the post's old image's event column. Its event id is the post's id;
  - **unrepost** reads the repost's pre-delete image's event column, which holds the event id to delete and tombstone;
  - **a lookup through a source row the device does not hold is unknown,** and the write queues without a row. The source row's own read already misses first.

  On the server, the same transitions may read either the slot or `byActorPost`; they must agree, and a test holds them to it.

  A predicted transition on a device stamps the slot on the row it writes, using the same minted id as the server. For a kind that is not fully synced, it never inserts into or deletes from the device's owned table: a delete of a row the device does not hold would be `NOT_FOUND`. It tombstones the id read from the slot.
- **A synced aggregate over the owned events stops prediction for a kind that is not fully synced.** An application may maintain an aggregate over the owned event table (`view totals: count followingPosts by .actorId`) and sync it. The server's event write updates that aggregate. A device's prediction writes a slot, not an owned row, so it cannot. It may also lack the original's `authorId`, which the aggregate groups by.
  - When the owned table has a synced dependent aggregate and a kind is not fully synced, the transitions that insert or delete that kind's events **do not predict**. They queue without a row.
  - `check` says so, naming the aggregate, and the runtime enforces it. Otherwise a device could refuse definitively, from a stale total, a mutation the server accepts.
  - An `online only` aggregate is unaffected.
- **Every other device read of the owned table is unknown while either kind is not fully synced.** An application query or a rule probe may read the owned event table as an ordinary public table. On a device, that table holds only fully synced kinds. Most of its keys (`byId`, `byTime`, `byActorTime`) do not name the kind. So while either kind is not fully synced:
  - a point read by any key, and any rule probe, is unknown on a miss, unless its key names a fully synced kind (`byActorPost` with that kind's flag);
  - a hit, which can only be a fully synced kind's row, is returned;
  - any scan that could return a kind that is not fully synced is unknown.

  An unknown read here is a **withheld trigger** (§2.2), not an ordinary horizon result: the query publishes the withheld value, never a null, a false probe or a short page. `check` classifies it as a horizon site. The generated Following page reads no owned events: it reads the inbox, the owned edges and the tombstones. Backfill, delivery, cleanup and purge run on the server.

### 2.2 Device reads

The paved Following page is the **inbox projection**: event id, post, actor, author, repost flag and time. It reads the reader's inbox, the follows filter and the tombstones. It needs no posts. A page has **known inbox coverage** when its scan stays within the acquired inbox floor. Such a page is answered on the device, whatever the posts horizon. Pending backfill or cleanup, and meter cuts, keep their existing `complete: false` meaning: they do not make a page unavailable.

A **card** is the application's shape, for example `{ *, card: posts[.post] }`. It is a separate point read.

**The withheld result.** Two cases make a query's local answer **withheld**:
- an **unknown card:** any horizon miss of `posts` or `reposts`. A by-id read has no time key, so the engine does not try to prove that the missing row is under the floor. A known null on a fully synced source stays a null card;
- an **inbox scan that crosses the inbox floor**, meaning the page needs copies older than the acquired floor;
- a **required card read of an `online only` source**, which is unknown on a device even when it hits;
- a **device read of the owned event table that §2.1a makes unknown**: a miss or a scan while either event kind is not fully synced.

A withheld query publishes exactly one result: `{ loading: true }`, with no `data` and no `next`. It never publishes a page with a null card, a short page, or a continuation. The client routes it in this order, before any other loading or server-run shortcut:
1. **Offline** → publish the withheld result.
2. **Online, with a predictable, unobserved outbox entry** (an own post that predicted, `observed_seq == null`; a repost that queued without a row does not count) → publish the withheld result until that entry is observed. The rule that a predicted row never disappears under a server answer holds.
3. **A `held` query** → publish the withheld result, online or offline, until the page is locally answerable. A `held` query never falls back to the server, as today.
4. **Otherwise** → call the server with the query's **original arguments**, cursor included. A transport failure publishes the withheld result.

This precedence applies before any server-run routing or remembered-answer recovery. That includes a query that shapes an `online only` source: offline, or while an own post is pending, it is withheld rather than answered from a remembered answer or refused with `E_OFFLINE`.

The existing local-commit invalidation fence still retires earlier in-flight answers.

What stays as it is:
- **Pending backfill or cleanup** keeps its published `complete: false` page. It is data, not withheld.
- **The unshaped inbox page** reads no posts. It is withheld only when its scan crosses the inbox floor.
- **Meter cuts** stay as they are. A scan cut by the examined meter above the floor is a known, resumable prefix: it is published partial with its continuation, as today. Heap and scalar exhaustion are already unavailable. The coverage calculation must use the actual cut position, so that a cut above the floor is never mistaken for crossing it. A full page at the floor whose `next` leads past the floor is published. Its next page is the one withheld.
  A point read of an owned event with partially held source kinds is withheld
  as unknown even when its examined admission fails before lookup. The
  schema and key determine this classification without fetching a candidate;
  the owned table's lack of its own horizon does not establish absence.

So the promise is precise. A device answers a Following page offline when the rows it shows are held: the copies within the inbox floor, and every card the application shapes within the posts and reposts floors. A quiet followed author's older post, or a new repost of an old original, can put a page past those floors, and then the server answers it.

With `online only` sources, cards are never held. A shaped Following page is answered by the server, under the precedence above.

### 2.3 Prediction

- An author's own post predicts as today: the local row is the card, and the author's own inbox copy is written.
- These are **necessary** conditions for a repost to predict: its source post, the original's event, and the tombstone probe must all be known. On a device, the original's event is the held post's event slot (§2.1a), and it is known whenever the post is held. The ordinary uniqueness proof of a paved `insert … if absent` also applies, and a new insertion into a horizoned `reposts` table can still queue. Otherwise the repost queues without a local row.
- **`check` classifies each transition's implicit inputs by what that transition reads,** so a mutation's summary says when it may queue:

  | Transition | Implicit reads | Class |
  |---|---|---|
  | own post insert | no owned-event read: it writes a new event and its own inbox copy; it reads the tombstone (`RemovedEvents.byEvent`) for the new id | tombstone Held (fully synced); nothing else added |
  | removal (post update to removed) | the old post, its original event, the tombstone | the posts class; tombstones fully synced |
  | repost insert | the original post, its original event, the tombstone | the post and its event: the posts class; the tombstone: Held |
  | unrepost (repost delete) | the old repost, its repost event | the reposts class; no original-post read |
  | follow, unfollow | owned edges and work | server sites, whatever the owned work table's sync, because the transition is server-owned |

  The owned event input is never classified from a horizon on the event table, which has none.
- **`online only` sources do not predict.** A write to an `online only` source is a server site, so the mutation is `predicts: never` and queues without a local card or inbox copy, as residency already classifies it. The own-post guarantee above is for synced sources, full or horizoned.
- Follow and unfollow already queue without prediction.

### Own edge publication

A reader's own follow or unfollow changes a Following read's input before the
server's edge and copied events reach the replica. The 50-event immediate copy
is in the **server transaction**, not a promise that the device has published
those rows when the call starts or its receipt arrives. Calibration #26's
empty baseline was reproduced on real wasm and process clients: admission and
settlement each allowed a complete, fresh empty answer before sync.

The SDK marks affected mounted answers revalidating synchronously when the
mutation is called (`keep: false` withdraws). Before publishing any data answer,
including a server fallback, it checks the existing durable outbox for this
viewer's unobserved mutations whose compiled inputs include that declaration's edge
source. Such answers report `complete: false`. This is conservative at the
operation level: a branch that reads the edge without changing it can also
qualify the answer. Unknown/native operation footprints cover every declaration;
query dependencies cover the declaration's owned Feed, Edges and Work tables.
Disjoint reads keep their own completeness. Posts, likes and removals do not
qualify merely because they can affect a feed. No operation names are special.

Custody can also enter through orphan adoption, journal replay or restoration
of a committed image whose save reply was lost. Browser hosts report the
committed entries synchronously, before pending-write notification or delivery;
the SDK invalidates only the affected declaration's observations at that boundary.
Both main-thread and worker hosts report restored entries even when recovery
writes no new outbox change. Initial process recovery has no mounted answer yet;
its first publication uses the same durable check. Another principal's retained
entry neither invalidates nor gates this viewer, including after sign-out and
explicit reuse of a backing store.

An in-memory call marker covers the interval before durable admission and while
the call is unsettled; it is not another write queue. Recovered and zero-wait
writes use the outbox. A sent receipt does not clear this condition: the outbox
must record observation with the published effects or retire the entry. A
terminal refusal clears it without inventing an edge. Admission and completion
invalidate in-flight reads using the existing publication revision. Sync publication
also wakes qualified reads when an idempotent edge write retires without changing
any row, so no polling or retry timer is needed to restore completeness. The final
check crosses the same session, incarnation, expiry and authority fences as any
other answer. Loading, denial, missing-card withholding and prediction fallback
rules keep their precedence; this condition only qualifies data already eligible
to publish. Freshness retains its existing meaning independently of completeness;
the derived `existence` is recomputed when completeness changes. After observation,
an author with no posts gives a complete, fresh empty page, without waiting for
a copied row. Overlapping follow/unfollow retains both intents through observation.

Rendered sequence: previous answer marked revalidating (or loading), then
incomplete old or newly delivered data, then the observed Following page. A
screen checks loading, revalidating and incompleteness before displaying an
empty-state message. Unfollowed events disappear on the next read of the observed
edge. Backfill/cleanup can keep that page incomplete independently. A refused
follow can legitimately return to a complete empty page. Authorization, source
and inbox floors, fixed 1,000-event history, immediate 50-event server copy,
event identity, and nonprediction of edge transitions are unchanged.

Evidence and causal real-device regression:
[`FW round 0`](../snapback4/reports/20260929-fw-follow-window/REPORT.md).
The compiler/device wire, replica storage and wasm artifact are unchanged.

### 2.4 Adoption

- Changing a source between full sync, a horizon and `online only` is an ordinary generation change. The device clears its acquisition and re-snapshots the partition, as it does for any sync change. A device never trims in place.
- Changing from a horizon to full sync re-acquires the whole table.
- The inbox floor is the same kind of change.
- A source's residency change carries its events' residency in the same generation change. A change to the application's follows is an ordinary sync change; the view is unaffected.

## 3. Semantics worth stating

- **Delivery is unchanged.** Copies are made on the server for every follower, whatever any device holds.
- **Removal is unchanged.** The owned tombstone table stays fully synced. A copy is hidden by `not exists RemovedEvents[eventId]`, whether or not its post is held.
- **Nothing is disclosed.** Sources, events and tombstones stay public, and the inbox stays private to its reader. A floor changes what a device holds, never who may read it.
- **The history window stays.** Charlie ruled on 2026-10-03 that a follow keeps the actor's newest 1,000 events at follow time plus new events afterward; older posts belong on the actor's profile. [LLP 3000.016.000 §0](./3000.016.000-older-following-history.rfc.md#0-ruling) shelves the all-history prototype with its measurements: followers × history storage, whole-feed withholding during backfill, more catch-up traffic with the same device floor, and no demonstrated builder demand. The prototype stays on `origin/sb5/f-follow-history-prototype-parked` (0936b660f0). Any future older Following support should read pages on demand under its own design, covering enumeration, fairness, completeness, existing follows and storage. The feeds card states the product boundary and profile recipe.

## 4. Increments

1. **Admission** of source horizons and `online only` on `posts` and `reposts`, and the per-reader inbox floor. Tombstones stay fully synced, whatever the sources' residency.
2. **The withheld result and its routing precedence** (§2.2), on the device and in the client, before any other loading or server-run shortcut.
3. **Repost prediction** gated on a held original, and its horizon-site classification.
4. **The card:** the bounded form first, the global-floor wording and the window. `check --cost` lines. A measured inventory.
5. **Events follow their source rows** (§2.1a), and the application's follows admit any public residency. `check` classifies per transition (§2.3), and the card says so. The inventory is measured again.

## 5. How we will know

- **A whole-partition inventory at the scale fixture,** before and after, in rows and bytes, with the cold acquisition time on the web device: posts, reposts, events, tombstones, follows, the inbox, profiles and work. The target is at least 5× less over the view's own tables: sources, follows, events, tombstones, inbox, work and edges. The whole partition is reported too; the application's other tables are its own. Say what dominates afterward.
- **Device tests:**
  - a page with known inbox coverage and held cards is answered offline;
  - a page whose scan reaches past the inbox floor is withheld offline and answered online;
  - a page with a repost of an original past the floor is withheld offline and answered by the server online, from the original cursor;
  - a pending predicted post is never replaced by the server page before it is observed;
  - a quiet author's old post is answered online;
  - a repost of a held original, a reply and a removed post predict or refuse on the device exactly as with full sync, under every synced source residency, subject to §2.3's uniqueness proof;
  - a post removed **after** acquisition: its event's delete reaches the device with the post's update, and a repost of it then refuses locally;
  - a repost unreposted on the server after acquisition, then reposted again on the device: the stale event is gone, and the new repost predicts;
  - an unrepost and a removal of held rows predict; through an unheld row they queue;
  - an application query reading the owned event table on a device, with a floored kind, is withheld, never a known null or a complete page;
  - a source inserted or removed between snapshot pages, and an interrupted acquisition resumed, end with every held source's event column exactly as the server has it;
  - a post inserted and updated in one mutation, delivered in the stream: the device holds it with its event column set;
  - a stream split between commit A (a body update) and commit B (removal), with A's put normalized to B's state: the post arrives with its column already cleared;
  - a repost deleted after its snapshot page and before catch-up serves its insert; a repost deleted and recreated under the same id for another post; an original's event id reused by a later repost: in each, the device's event state for every held source equals the server's, and no orphan event survives;
  - activation on a populated store fills every source row's slots to agree with `byActorPost`. The device reacquires, and answers no repost or removal from an unfilled slot, including when the same generation adds `pinned: bool default false` elsewhere. An upgrade interrupted before the source pages arrive leaves reads unavailable and mutations queued. A server test holds the transitions' slot and index reads in agreement;
  - two Following declarations over the same reposts: an offline unrepost tombstones both declarations' events, and removing one declaration leaves the other's slots;
  - a synced `count followingPosts by .actorId` with posts floored: a post insert does not predict, `check` names the aggregate, and with the aggregate `online only` the insert predicts again;
  - a `whole` source floor, then a backdated source insert: the device holds the source and its event, and a repost of it predicts;
  - with posts fully synced and reposts floored, an application `byId` read of an unheld repost event, and a `byTime` scan, are withheld offline, and a rule probe of either queues the mutation without a local refusal;
  - the same with reposts `online only`: no repost event is ever acquired, a `byId` read of one is withheld even though the server has it, and a `byActorPost` miss of an original (fully synced) is still a known null;
  - an event id reused after purge (a repost deleted, its tombstone purged, and a later repost supplied the same minted id), in either order of delivery: the device's event state follows each source row's image;
  - `check` on a plain post insert under a posts horizon stays `predicts: eligible`, with no event site; an unrepost under full-synced reposts has no posts site.
- The bounded feeds program compiles without refusal, and the next calibration does not charge the full-source-sync requirement.

## 6. Non-claims

This RFC does not bound tombstones or the reader's owned edges on a device, choose a residency for the application's follows, change delivery or the history window, or make a Following page complete offline beyond the floors. Its claim is smaller acquisition, and a page that is never shown with a hole.

### Revision 5, measured: the owned events dominate

Lane U's round 1 implemented revision 5 and measured the scale fixture's whole partition for one reader in a real browser. The rows went from 171,330 to 98,543, the row bytes from 35.9 MB to 15.1 MB, and cold acquisition from 281 s to 118 s: 2.4× in time, short of the 5× target. The fully synced owned events were half of what remained, at 49,228 rows and 7.8 MB. The lane's counterexample: even with no posts, reposts or inbox rows at all, 95,543 rows remain, so revision 5 cannot reach the target.

Revision 6 answers the objection that sent events back to full sync in revision 3, "a horizon cannot say this event is absent", by construction. An event lookup on a device goes through a held source row, and the device holds that row's event (§2.1a). The follows relaxation removes a second corpus-sized table the view never reads on a device.
