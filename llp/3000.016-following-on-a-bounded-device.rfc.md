## Summary

Calibration #20 (0.4.1) charged three of its five weakest categories for the same thing: the Following view.

| Category | Score | The scorer's charge |
|---|---:|---|
| `queries_and_live` | 82 | "Following's 1,000-event backfill limit and full-source-sync requirement; `E_TIMELINE_SHAPE` rejected bounded acquisition" |
| `scale_and_limits` | 78 | "cold multi-route browser flow took 42.324 seconds; required full public sync and rejected acquisition bounds remain material" |
| `client_integration` | 83 | "acquisition, admission and online fallback as demanding integration boundaries" |

The view requires its sources to declare `sync public` with no horizon. Its generated event table does the same. So every cold device acquires every public post, repost and event before a Following page is complete offline. At the scale fixture that is 50,228 posts and as many events.

This RFC changes only **acquisition**. Delivery, the inbox's contents, the history window and prediction of an author's own post are unchanged.

1. **Sources may be bounded, and events follow them.** `posts` and `reposts` may declare `sync public last N by .at` or `online only`. The owned event table follows its sources: a device holds the event of every post and repost it holds, exactly while that event exists (§2.1a). The application's `follows` may take any public residency.
2. **The inbox may be bounded per reader.** The reader's owned inbox syncs with a per-reader floor of the newest M copies. By default, M equals the history window.
3. **A page never shows a hole.** On a device, a Following page, or any query that shapes it with cards, is either answered from held rows or withheld. Online, the withheld page is answered by the server. Offline, it is `loading`. A null card is never published as data.

## 2. What changes

### 2.1 Admission (`bind/timeline.rs`)

| Table | 0.4.1 | This RFC |
|---|---|---|
| posts (originals) | public, `sync public`, no horizon | public, and `sync public`, `sync public last N by .at`, or `online only` |
| reposts | the same | the same as posts |
| follows (edges) | public, `sync public`, no horizon | public, with any residency a public table has: `sync public`, `sync public last N by …`, or `online only`. A device filters a Following page by the reader's owned edges (`@T@Edges`), which sync to the reader, and edge transitions are server sites. So the view never reads the application's follows on a device. Application queries and rules that read follows inherit its residency, as for any table |
| owned events (`@T@Posts`) | `sync public` | each kind follows its source row (§2.1a): full sync while that source is fully synced; otherwise a device holds the event of every source row it holds, exactly while it exists. The table carries no horizon |
| owned tombstones (`@T@RemovedEvents`) | `sync public` | unchanged: full sync, because removal must always reach a device (§3) |
| owned inbox (`@T@Feed`) | `sync` to its reader | `sync` to its reader, with a floor of the newest M copies over `byReaderPage`, the index the Following scan uses. M defaults to the history window, 1,000, as one merged suffix per reader, not per author |

- **A floor is global and non-sliding.** `sync public last N by .at` makes a cold device acquire the newest N rows of the whole table, whoever it follows. Nothing evicts a row after acquisition, and the floor is fixed at acquisition time; this is how horizons already behave.
- **A source horizon's index must be the source's mapped time column plus `id`.** This applies to `posts` and `reposts` only. An `id`-ordered or other index is refused, with a rewrite, because the floor must be the newest events. The inbox floor is always on `byReaderPage`, because a horizon page is locally known only when the floor's index is the scan index.
- **Everything else is unchanged:** owner write authority, immutable mapped fields, one-way removal, the unique pairs, and no expiry on sources.

### 2.1a Owned events follow their source rows

An owned event is a function of its source row:
- **An original's event** has the post's id, author and time. It exists exactly while the post passes the originals filter and has not been removed.
- **A repost's event** has the repost's actor and time, and the original's post and author. It exists exactly while the repost row exists. Removing the original leaves it, as today.

So a device needs an event only when it holds the event's source row.

- **Residency.** Each kind of event takes its source's residency:
  - with a fully synced source, that kind is fully synced;
  - with a floored source, the kind is **partial**: **for every source row a device holds, it holds that row's event exactly while the event exists**. The source rows held are exactly those the source's horizon admits: the acquired floor's rows and every later row the horizon accepts, which is every later row while the floor is `whole`. That set is never re-derived by comparing times. "Never evicts" means a live event is never dropped to keep a count. A deleted event is always deleted;
  - with an `online only` source, that kind is online only.
- **The owned event table carries no horizon.** Its one lookup index, `byActorPost`, has no time key, so a horizon on it cannot mean "newest", and a horizon would make every miss unknown. The partial residency is the kind's own state, recorded with the source's acquisition.
- **A partial kind's event state travels with its source.** Every image of a source row a device receives, whether in a snapshot page, in snapshot catch-up or in the ordinary stream, carries that source's **event state**: its event row, or the authoritative absence of one. The server reads it from the **same server state** as the delivered source image.
  - The device applies the source image and its event state in one transaction, source first.
  - Deleting a held source row deletes its event, found by the source's key: an original's by `(author, post, false)`, whose id is the post's id, and a repost's by `(actor, post, true)`.
  - A repost's event id is minted, so its row is transferred, never reconstructed.
  - Raw event puts in the log do not decide a partial kind's state on a device. A raw event delete may still apply unconditionally, because an event id is never reused.

  This is what makes the state consistent. Two traps defeat an ordering of raw entries:
  - a mutation that inserts a post and then updates it logs the post's final image *after* its event, because birth accounting withdraws the earlier put;
  - the stream re-reads a put at the serving transaction's current state, so an update from commit A can carry commit B's `removed: true` while B's event delete sits on the next page.

  With the event state paired to the delivered image, neither leaves a removed source beside a stale event, or a held source without its event.
- **The mechanism is constrained.** The owned table stays `sync public` with no horizon, so its puts and deletes remain in the public log for any fully synced kind. A partial kind is left out of the horizonless snapshot walk: its events arrive paired with their sources. Do not implement a partial kind by setting `sync.horizon` on the owned table, which would make the three lookups unknown, or by clearing its `sync`, which would stop the log. The partial state is recorded with the source's acquisition and shares its staging and publication lifetime.
- **No time boundary.** "Every event of that kind at or after the floor's oldest time" is not used. Timestamp ties can make it overfetch without bound: 50,000 originals sharing one time would all be acquired for a floor of 1,000. Comparing a repost event's full `(at, id)` key with the floor's is also wrong, because its minted id sorts independently of the repost's id.
- **The three transition lookups through a held source row are decidable.** Revision 2 floored events by their own count. A held post's event could then lie outside the event floor (Grok's scenario A), and a miss could not tell "never admitted" from "outside the floor" (scenario B). Here each lookup goes through a source row the device holds, and that row's event is held exactly while it exists. The three device lookups are the timeline transitions' `byActorPost` point reads, each with its witness:
  - **repost insertion** reads the original post, then the original's event. With the post held, the event is present, or it is absent because the post is a reply, was removed, or fails the filter. A known absence refuses `FEED_POST_NOT_FOUND` on the device, as full sync does today;
  - **removal** reads a held post's own event, with the post's old image as the witness;
  - **unrepost** reads the repost's event, with the repost's pre-delete image as the witness;
  - **a lookup through a source row the device does not hold is unknown,** and the write queues without a row. The source row's own read already misses first.

  These are the only device reads that may treat a missing owned event as absent. The engine decides them from the witness, not from `get_inner`'s table-level horizon state, which the table does not have.
- **Every other device read of the owned table is unknown while either kind is partial.** An application query or a rule probe may read the owned event table as an ordinary public table. Most of its keys (`byId`, `byTime`, `byActorTime`) do not name the kind, so a miss cannot tell a missing original from a repost outside the floor. While either kind is partial:
  - only the three transition lookups may treat a missing event as absent;
  - a point read by any other key, and any rule probe, is unknown on a miss, unless its key names a fully synced kind (`byActorPost` with that kind's flag);
  - any scan that could return a partial kind is unknown;
  - a hit of a row the device actually holds may be returned.

  An unknown read here is a **withheld trigger** (§2.2), not an ordinary horizon result: the query publishes the withheld value, never a null, a false probe or a short page. `check` classifies it as a horizon site. The generated Following page reads no owned events: it reads the inbox, the owned edges and the tombstones. Backfill, delivery, cleanup and purge run on the server.

### 2.2 Device reads

The paved Following page is the **inbox projection**: event id, post, actor, author, repost flag and time. It reads the reader's inbox, the follows filter and the tombstones. It needs no posts. A page has **known inbox coverage** when its scan stays within the acquired inbox floor. Such a page is answered on the device, whatever the posts horizon. Pending backfill or cleanup, and meter cuts, keep their existing `complete: false` meaning: they do not make a page unavailable.

A **card** is the application's shape, for example `{ *, card: posts[.post] }`. It is a separate point read.

**The withheld result.** Two cases make a query's local answer **withheld**:
- an **unknown card:** any horizon miss of `posts` or `reposts`. A by-id read has no time key, so the engine does not try to prove that the missing row is under the floor. A known null on a fully synced source stays a null card;
- an **inbox scan that crosses the inbox floor**, meaning the page needs copies older than the acquired floor;
- a **required card read of an `online only` source**, which is unknown on a device even when it hits;
- a **device read of the owned event table that §2.1a makes unknown**: a miss or a scan while either event kind is partial.

A withheld query publishes exactly one result: `{ loading: true }`, with no `data` and no `next`. It never publishes a page with a null card, a short page, or a continuation. The client routes it in this order, before any other loading or server-run shortcut:
1. **Offline** → publish the withheld result.
2. **Online, with a predictable, unobserved outbox entry** (an own post that predicted, `observed_seq == null`; a repost that queued without a row does not count) → publish the withheld result until that entry is observed. The rule that a predicted row never disappears under a server answer holds.
3. **A `held` query** → publish the withheld result, online or offline, until the page is locally answerable. A `held` query never falls back to the server, as today.
4. **Otherwise** → call the server with the query's **original arguments**, cursor included. A transport failure publishes the withheld result.

This precedence applies before any server-run routing or remembered-answer recovery. That includes a query that shapes an `online only` source: offline, or while an own post is pending, it is withheld rather than answered from a remembered answer or refused with `E_OFFLINE`.

The existing local-commit invalidation fence still retires earlier in-flight answers.

What stays as it is:
- **Pending backfill or cleanup** keeps its published `complete: false` page. It is data, not withheld.
- **The unshaped inbox page** reads no posts. It is withheld only when its scan crosses the inbox floor.
- **Meter cuts** stay as they are. A scan cut by the examined meter above the floor is a known, resumable prefix: it is published partial with its continuation, as today. Heap and scalar exhaustion are already unavailable. The coverage calculation must use the actual cut position, so that a cut above the floor is never mistaken for crossing it. A full page at the floor whose `next` leads past the floor is published. Its next page is the one withheld.

So the promise is precise. A device answers a Following page offline when the rows it shows are held: the copies within the inbox floor, and every card the application shapes within the posts and reposts floors. A quiet followed author's older post, or a new repost of an old original, can put a page past those floors, and then the server answers it.

With `online only` sources, cards are never held. A shaped Following page is answered by the server, under the precedence above.

### 2.3 Prediction

- An author's own post predicts as today: the local row is the card, and the author's own inbox copy is written.
- These are **necessary** conditions for a repost to predict: its source post, the original's owned event row in `byActorPost`, and the tombstone probe must all be known. The event row's presence or absence is known whenever the source post is held (§2.1a). The ordinary uniqueness proof of a paved `insert … if absent` also applies, and a new insertion into a horizoned `reposts` table can still queue. Otherwise the repost queues without a local row.
- **`check` classifies each transition's implicit inputs by what that transition reads,** so a mutation's summary says when it may queue:

  | Transition | Implicit reads | Class |
  |---|---|---|
  | own post insert | no owned-event read: it writes a new event and its own inbox copy; it reads the tombstone (`RemovedEvents.byEvent`) for the new id | tombstone Held (fully synced); nothing else added |
  | removal (post update to removed) | the old post, its original event, the tombstone | the posts class; tombstones fully synced |
  | repost insert | the original post, its original event, the tombstone | the post and its event: the posts class; the tombstone: Held |
  | unrepost (repost delete) | the old repost, its repost event | the reposts class; no original-post read |
  | follow, unfollow | owned edges and work | server sites, whatever the owned work table's sync, because the transition is server-owned |

  The owned event input is never classified from a horizon on the event table, which has none.
- **`online only` sources do not predict.** A write to an `online only` source is a server site, so the mutation is `predicts: never` and queues without a local card or inbox copy, as residency already classifies it. The own-post guarantee above is for synced sources, full or horizoned.
- Follow and unfollow already queue without prediction.

### 2.4 Adoption

- Changing a source between full sync, a horizon and `online only` is an ordinary generation change. The device clears its acquisition and re-snapshots the partition, as it does for any sync change. A device never trims in place.
- Changing from a horizon to full sync re-acquires the whole table.
- The inbox floor is the same kind of change.
- A source's residency change carries its events' residency in the same generation change. A change to the application's follows is an ordinary sync change; the view is unaffected.

## 3. Semantics worth stating

- **Delivery is unchanged.** Copies are made on the server for every follower, whatever any device holds.
- **Removal is unchanged.** The owned tombstone table stays fully synced. A copy is hidden by `not exists RemovedEvents[eventId]`, whether or not its post is held.
- **Nothing is disclosed.** Sources, events and tombstones stay public, and the inbox stays private to its reader. A floor changes what a device holds, never who may read it.
- **The history window stays.** A follow copies the author's newest 1,000 events, as today. Removing it needs a design of its own: a fixed enumeration domain, fairness between background tasks, per-page completeness, an upgrade for existing follows, and a stated storage cost. The reviews of revision 1 laid all of that out. It is not in this RFC. The feeds card states the window plainly.

## 4. Increments

1. **Admission** of source horizons and `online only` on `posts` and `reposts`, and the per-reader inbox floor. Tombstones stay fully synced, whatever the sources' residency.
2. **The withheld result and its routing precedence** (§2.2), on the device and in the client, before any other loading or server-run shortcut.
3. **Repost prediction** gated on a held original, and its horizon-site classification.
4. **The card:** the bounded form first, the global-floor wording and the window. `check --cost` lines. A measured inventory.
5. **Events follow their source rows** (§2.1a), and the application's follows admit any public residency. `check` classifies per transition (§2.3), and the card says so. The inventory is measured again.

## 5. How we will know

- **A whole-partition inventory at the scale fixture,** before and after, in rows and bytes, with the cold acquisition time on the web device: posts, reposts, events, tombstones, follows, the inbox, profiles and work. The target is at least 5× less over the view's own tables: sources, follows, events, tombstones, inbox, work and edges. The whole partition is reported too; the application's other tables are its own. Say what dominates afterward.
- **Device tests:**
  - a page with known inbox coverage and held cards is answered offline;
  - a page whose scan reaches past the inbox floor is withheld offline and answered online;
  - a page with a repost of an original past the floor is withheld offline and answered by the server online, from the original cursor;
  - a pending predicted post is never replaced by the server page before it is observed;
  - a quiet author's old post is answered online;
  - a repost of a held original, a reply and a removed post predict or refuse on the device exactly as with full sync, under every synced source residency, subject to §2.3's uniqueness proof;
  - a post removed **after** acquisition: its event's delete reaches the device with the post's update, and a repost of it then refuses locally;
  - a repost unreposted on the server after acquisition, then reposted again on the device: the stale event is gone, and the new repost predicts;
  - an unrepost and a removal of held rows predict; through an unheld row they queue;
  - an application query reading the owned event table on a device, with a floored kind, is withheld, never a known null or a complete page;
  - a source inserted or removed between snapshot pages, and an interrupted acquisition resumed, end with every held source's event exactly as the server has it;
  - a post inserted and updated in one mutation, delivered in the stream: the device holds it with its event;
  - a stream split between commit A (a body update) and commit B (removal), with A's put normalized to B's state: the device never holds the removed post beside its event;
  - a `whole` source floor, then a backdated source insert: the device holds the source and its event, and a repost of it predicts;
  - with posts fully synced and reposts floored, an application `byId` read of an unheld repost event, and a `byTime` scan, are withheld offline, and a rule probe of either queues the mutation without a local refusal;
  - `check` on a plain post insert under a posts horizon stays `predicts: eligible`, with no event site; an unrepost under full-synced reposts has no posts site.
- The bounded feeds program compiles without refusal, and the next calibration does not charge the full-source-sync requirement.

## 6. Non-claims

This RFC does not bound tombstones or the reader's owned edges on a device, choose a residency for the application's follows, change delivery or the history window, or make a Following page complete offline beyond the floors. Its claim is smaller acquisition, and a page that is never shown with a hole.

### Revision 5, measured: the owned events dominate

Lane U's round 1 implemented revision 5 and measured the scale fixture's whole partition for one reader in a real browser. The rows went from 171,330 to 98,543, the row bytes from 35.9 MB to 15.1 MB, and cold acquisition from 281 s to 118 s: 2.4× in time, short of the 5× target. The fully synced owned events were half of what remained, at 49,228 rows and 7.8 MB. The lane's counterexample: even with no posts, reposts or inbox rows at all, 95,543 rows remain, so revision 5 cannot reach the target.

Revision 6 answers the objection that sent events back to full sync in revision 3, "a horizon cannot say this event is absent", by construction. An event lookup on a device goes through a held source row, and the device holds that row's event (§2.1a).
