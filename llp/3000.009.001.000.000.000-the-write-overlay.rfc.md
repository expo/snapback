## 1. Summary

A pre-executed mutation runs at a read-only snapshot, so its writes cannot
go to the store. They go to an **overlay**: a `Rows` implementation layered
over the snapshot.

- It answers every read as the store would answer it after those writes.
- It raises every error at the point and in the order the store would.
- It produces a **write set**, which the committer applies at batch commit.

LLP 3000.009 §4.2 named this need as C2:

- maintains read totals the same transaction just changed;
- final-existence checks read the program's result;
- unique checks read earlier inserts.

The overlay must make a program's execution indistinguishable from in-place
execution at the same snapshot: the same outcome, refusals, meter
observations, cut sites and final state. That property, not a proof, is
what qualifies it (§6).

## 2. The rule: same calls, same answers

The interpreter's sequence of logical `Rows` calls must not change. Each
answer from the overlay must equal the answer the store would give inside a
transaction that already contains the overlay's writes.

This mirrors prefetch's contract (LLP 3000.009 §4.2): the interpreter stays
the only executor, and the overlay changes where an answer comes from,
never which questions are asked.

The overlay must not evaluate expressions, run rules, charge the meter, or
reorder calls. The meter charges what the interpreter charges for each
call. So, given identical answers, the charges are identical.

## 3. State

The overlay holds:

- **Rows:** `(table, id) → Some(image) | None`, the latest image or a
  deletion.
- **Index deltas** per `(table, index)`: encoded keys added and removed.
  They are computed by the shared `stored_index_keys` preparation every
  store uses (`rows.rs`), so keys are byte-identical to the store's, and the
  2,048-byte bound and label bound are checked at the same point.
- **Sequences:** `(parent, id) → value`, written by `set_sequence`.
- **Caps:** `(table, key) → delta`.
- **Effect keys** claimed by `effect_once`.
- **Time-audience records,** asset claims and releases, and change-footprint
  widening.
- **Placeholders** (parent RFC §5): the sites where a sequence-derived value
  entered a row, key or outbox entry.
- **A savepoint journal.** The program-level savepoint (`SAVEPOINT program`
  and its rollback on refusal), and the conflict reread's
  `rollback_program`, need nested undo. `Layered` already journals undo for
  ephemeral rows, and the overlay generalizes that journal to every field
  above.

## 4. Reads over the overlay

| `Rows` call | Answer |
| --- | --- |
| `get(table, id)` | The overlay's row or deletion if present, else the snapshot's |
| `lookup(table, index, key)` | Removed keys hide snapshot entries; added keys answer with their id; otherwise the snapshot. Uniqueness is whatever the merged view shows |
| `scan(table, index, bounds, dir, limit)` and `scan_metered` / `scan_selected` | An ordered merge: the snapshot's entries in key order, minus removed keys, plus added keys in their encoded order, in direction `dir`, up to the limit. It yields the same sequence of rows the store would yield over its transaction, so physical examination counts and cut sites match |
| `count_prefix` | The snapshot count + added − removed within the prefix |
| `index_head` | The extreme of the merged view |
| `sequence_value` | The overlay's value, else the snapshot's |
| `cap_count` | The snapshot count + delta |
| `effect_once` | False if the overlay already claimed the key; otherwise the snapshot's answer, which then claims it in the overlay |
| `time_audience_pending` / `published`, `asset`, `holds_assets` | The overlay's records over the snapshot's |
| `walk_adoption`, `rewrite_sequence_ids`, the `restored_*` calls | Not supported. Administrative members run in place (parent RFC §3.2) |
| `prefetch` | Passes through to the snapshot for keys the overlay does not shadow. A prefetched answer for a shadowed key is never used |

**Writes** (`put`, `delete`, `set_sequence`, caps, effect keys, asset
claims, time-audience tracking) update the overlay only. They run the
store's own pre-write checks first: key preparation, bounds, the oversized
existing-entry rule, and unique-constraint checks against the merged view.
So a refusal is raised at the same call, with the same error.

## 5. Rollout by operation family

The overlay is qualified family by family. Until a family qualifies, a
program that touches it is not eligible, and runs in place (parent RFC
§4.1). The order follows what the reference applications use:

1. rows, indexes and counts: queries, inserts, updates, deletes, unique
   checks;
2. sequences and caps;
3. maintains and live aggregates (their reads of just-written totals);
4. effect keys and outbox;
5. time audiences and assets.

Administrative operations never pre-execute.

## 6. Qualification: the overlay differential

For every generated program in `snapback4-difftest`, using its widened
generator with preludes, mutation blocks, expiry and placeholders:

1. Build two identical stores at the same state.
2. On store A, run the program in place, as the reference does.
3. On store B, run it pre-executed through the overlay at a snapshot of the
   same state, then apply its write set in a one-member batch.
4. Compare:
   - the full outcome record: data, completeness, cursors, cut sites, every
     meter field, dependency tables, next expiry, refusal sites;
   - the final state, byte for byte, of rows, index entries, sequences,
     caps, outbox, receipts and the log.

This runs with prefetch on and off on Postgres, on SQLite, and at every
forced meter cut position, as the store oracles do today. One disagreement
is a defect. A named unsupported operation is recorded as a skip, never as
a pass.

## 7. Costs and limits

- **Memory.** The overlay grows with a mutation's writes, which the meter
  already bounds through the write ceilings.
- **CPU.** Merged scans cost a merge per scan. Mutations' scans are bounded
  pages, so the cost is bounded.
- **Placeholders** are resolved at commit, not by the overlay (parent RFC
  §5).

## 8. Alternatives

- **Write into a real database transaction, then roll it back.** Execute in
  a read-write transaction, capture the writes, roll back, then re-apply at
  commit. This needs no overlay. But every pre-execution then takes write
  locks: on SQLite the single writer lock, which serializes again; on
  Postgres, row locks that block other executions. It also cannot run on
  reader connections.
- **Flush buffered writes before a read that could observe them**
  (LLP 3000.009 §4.2's second option). That would need a write connection
  during execution, which brings back the serialization the committer
  exists to remove.
