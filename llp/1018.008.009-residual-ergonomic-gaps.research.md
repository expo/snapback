## 1. Summary

On 2026-09-12 the author asked whether Snapback 2 is beautiful, elegant, and
ergonomic, what holds it back, and what needs improvement. The answer given
named eight uneven areas. This document expands each one as a research
finding — then-state, what the 2026-09-11 four-plan implementation changed,
and the residual gap. The review baseline is local main `3b7f51564a`,
inspected 2026-09-12 UTC. Four-plan measurements below are historical
checkpoints; later acquisition and Insights repairs are called out separately.
A source landing is not a published-package or full Clique qualification.

This consolidates observed friction and proposed priorities. Each section
points at its implementation owner and distinguishes measurements, source
findings and hypotheses. The read/scale/write follow-up is now proposed in
[LLP 1023](./1023-clique-builder-jump.rfc.md); this assessment does not
commission a second program. No section authorizes runtime, grammar,
budget, or scope changes; the governing
constraints remain LLP 1001 §3, LLP 1012 §§5–7, the 90,000-byte runtime
ceiling with its 80,000 target, one data language, and no runtime code
generation.

## 2. G1 — Composing query-backed screens still costs a second description

**Then.** Adding a count to a thread changed what the author had to declare
to keep existing messages visible offline; the shared thread bindings
described table identity, row selection, order, membership, drafts, mutation
targets, and an independent history query — some product policy, some a
second description of executable relationships (LLP 1018.008 §F2).

**Now.** The composed-page-resources plan is implemented: one SDK owner for
raw pages, item pages, and independently authorized history; real-owner
50→100→105 history, live edit/insert/remove, search 20→40; cold held
history without fabricated count/preview; 22 focused source/lifecycle cases
(LLP 1018.008 §§13–14).

**Residual.** The whole chat TypeScript corpus moves 27 files / 1,718 lines
→ 28 files / 1,751 lines: no total line-count win. The concrete deletion is
four client-hook sites, both Composer `online()` compositions, and the
duplicate ledger lookup — against added pagination controls and product
advice. A real loss of eligible source can still unmount a settled row until
history requalifies it; stable identity covers continuous visibility, never
retention of an unauthorized row. The open edit-draft ticket below is the
sharpest remaining instance: editor state lives in the row, so a transient
absence destroys it.

**Confidence:** high in the friction and the measured outcome; medium that
further derivation (compiler-inferred presentation) is the right next
mechanism rather than more hand-owned bindings. Owner: the composition plan
line; this document adds nothing.

## 3. G2 — Synchronization needs ordinary one-client usage

**Then.** Connected use asked the user to replenish a finite resource: 23
sends committed, then admission stalled with 85 IDs remaining against a
certified 352-ID slice on a fixed 8,192-ID grant (LLP 1018.008 §F1).

**Now.** Shared recovery, work lookup and readiness are implemented, including
per-caller bounded waits and account/takeover/offline fences. Admission and
a subscribed selected operation acquire missing capacity automatically;
snapshot/readiness reads themselves perform no I/O. Explicit recovery is the
path for stopped work, not a required call before every ordinary online write.

Subsequent acquisition work repaired foreground admission waiting behind
general recovery. The Insights fix in `3b7f51564a` also withholds unheld
maintained totals and preserves narrowly qualified owner answers. The original
complete-looking local zero is no longer an unimplemented repair.

**Residual.** The exact timed Insights load/refresh, online once-image
publication and browser navigation/offline-vote replay still need their
specific qualification. A stale held total may remain readable; a screen
requiring current owner data needs a working load/refresh path on the same
client. Simplify that path where measured app code still reconstructs
mechanism, while preserving explicit recovery for refused/stopped work.

**Confidence:** high in the landed contracts, limited in broader browser/
native qualification. Owners: the implemented recovery plan and
[LLP 1023.000](./1023.000-one-query-story.plan.md) /
[LLP 1023.002](./1023.002-web-writes-that-survive-the-browser.plan.md).

## 4. G3 — Acquisition improved; the current target is two to three seconds

**Then.** The original collector and success-compaction work measured ten
candidate runs at median 67.414 seconds against baselines censored at 120
seconds. Follow-up profiles reached 53.634 seconds. Those observations
explain the work's history; they are not the latest performance.

**Now.** Incremental work subsequently measured 56.458 → 32.554 seconds in
a qualified ten-pair development-build cohort. The author then tightened the
objective to **2–3 seconds** including durable full content, all earned
acknowledgement terminals and first offline thread/search queries
([LLP 1018.008.007.002](./1018.008.007.002-bounded-bulk-acquisition.plan.md)).
The earlier 30-second criterion is historical.

Bounded transport batches, four-page atomic carrier groups, grouped receipt
work and preparation reductions are implemented. The later production V4
cohort's descriptive medians are **33.788 → 28.434 seconds**. All 20 content,
receipt, first-query and reopen oracles pass, but two owner-stop failures
keep strict cohort qualification false. First mounted inbox regresses
1.105 → 1.616 seconds. The separate final V6 smoke passes all its checks
in **28.509 seconds**; it does not replace the V4 cohort.

**Residual.** The 2–3-second objective remains open by a wide margin.
Current profiles point to client preparation and ordinary receipt mutation
execution; larger transport batches alone are insufficient. The latest
foreground repair admits three observed sends in 596–686 ms and returns
committed in 2.50–3.09 seconds, but one control fails cleanup. Preserve that
failure and distinguish admission, settlement and view responsiveness.

Do not compare these successive cohorts as one continuous controlled
speedup: source, renderer, owner and endpoint changed. Full-size heap,
bearer-authenticated UI, native timing and broader foreground qualification
remain scoped open work. Store eviction remains a separate NOT-DOING
decision, not an incidental performance repair.

**Confidence:** high in the retained observations and target miss, limited
in general latency and shutdown attribution. Canonical owner/tracker:
[acquisition ticket](../issues/20260911-snapback2-full-acquisition-and-foreground-send.md)
and `boundedBulk20260911` in the
[measurement record](../snapback2/metrics/acquisition-20260911.json).

## 5. G4 — Application changes still have wider consequences than the edit

**Then.** `Schema::rule_hash` binds the complete schema; an optional
message-column addition left queued rule-verdict conflicts, and the audit
found only a conservative disconnected-table candidate (LLP 1018.008 §F3,
via LLP 1018.002).

**Now.** The locality plan's bounded work is implemented: declared field
widths, full-row/projected custody, multiplicity, and search metadata are
explained; 495 operation certificates across nine retained variants are
equal except diagnostic terms; no schedule-target cascade after a real bound
refusal; existing repair families and hot-regroup controls retained — with
no price or hash-domain relaxation.

**Residual.** Any narrowing of the evidence identity (the LLP 1018.002 §7
experiment) is still unproven against real application evidence, and the
L4/hash experiments stop without it. Enum widening and maintain regrouping
are covered by LLP 1020's implementation record, not new work commissioned
by this assessment. The practical cost a builder still pays: touching a
table can invalidate and re-price more of the app than the edit suggests,
and the explanation, however accurate, is documentation rather than a
smaller blast radius.

**Confidence:** high in the broad invalidation; limited in the safe useful
scope of any narrowing — the experiment is designed to produce exactly that
evidence. Owner: LLP 1018.002 §7 and LLP 1020.

## 6. G5 — Delivery and effects: declarations landed, authoring costs adjacent

**Then.** The authored delivery table, fan-out calls, tombstones,
original-audience semantics, and durable received acknowledgements were all
application responsibility; effect authoring rejected ordinary imported
helpers and no-network bodies still required a grant (LLP 1018.008 §F5).

**Now.** LLP 1019 records all its lanes implemented: `deliver` derives
per-recipient custody in the engine, and the `tombstones` declaration, authored
log, fan-out proc, seven calls, delivery seeds, and purge mutation were
deleted as the offset. The empty-grant slice (explicit no-network effects,
dummy-origin advice removed) is implemented. Per-recipient writes and
storage remain — declaration removed responsibility, not cost, as predicted.

**Residual.** Imported effect helpers stay deferred under LLP 1018.008.003;
their demand and runtime/lifetime work must be justified separately. Node/npm
SDK compatibility is explicitly not promised. Effect visibility, real execution
witnesses, provider stand-ins, stopping, staged-argument disposal, and
reset/seed fixes belong to LLP 1021. Confidence in the current restriction
is high; implementation and size benefits of closure assembly are
unmeasured.

**Confidence:** high; this area has the cleanest ownership split of the
eight. Owners: LLP 1019, LLP 1021, LLP 1018.008.003.

## 7. G6 — Proof boundaries still shape data modeling

**Then.** LLP 1001 §3 deliberately gives a nonuniform scan one opaque capped
outcome: a long hidden run can yield an empty capped page with no
continuation though readable rows exist later. Separately, a bounded page
cannot generally be projected into a stored or passed list
(`issues/closed/20260904-quarry-no-list-from-range.md`), and the `fn`/`proc`
distinction is friction with an explicit rationale in LLP 1018.005
(LLP 1018.008 §F4).

**Now.** No language implementation was selected for bounded collection
composition — the demand gate (an independent use case surviving LLP 1019)
was not met, and the working-set link was removed while the document
remains. Indexing a uniform visible scope remains the documented escape for
the capped-scan shape.

**Residual.** Authorization structure is still part of physical query
planning: the builder must learn which shapes of question get answers and
which get an honest `capped`. The page-to-list gap has no commissioned
form. The `fn` (expression-only, read-pure) vs `proc` (statement helper)
split stands until new evidence arrives; no merger is proposed.

**Confidence:** high that the boundaries are load-bearing rather than
accidental; medium that documentation and the two-site repair style (as used
for the refused `where`) can carry them without new grammar. Owner: no active collection-language mechanism. The complete query/job
forms at the existing limits are now proposed in LLP 1023.001; this does not
reopen the collection or `fn`/`proc` design.

## 8. G7 — Starter papercuts: four closed, two resolved in follow-up, one new

**Then.** Seven assessment rows: search with no continuation, no
older-message navigation, media placeholders, refused edits losing state,
recovery/dismissal reconstruction, index/log-flavored status copy, plus
successor and journey-type residuals (LLP 1018.008 §11).

**Now.** Four are closed (search continuation, older-message navigation,
recovery/dismissal duplication, status language); React thread media and
refused-edit preservation were resolved on the page-resource Thread in the
follow-up; the successor-residuals and journey-type items were updated
without duplication. The 60-line Thread budget is preserved, which constrains
where fixes can live.

**Residual.** One new Open P3 directly in this area:
`issues/20260911-snapback2-starter-edit-draft-across-page-shifts.md` — the
edit draft lives in row component state, so when a message transiently
leaves `snapshot.items` (e.g. a head-window slide after "Load older
messages"), the draft is lost and every other Edit button stays disabled
while `ui.editing` remains set. Requested outcome: keep draft/base/note per
`[account, messageId]` outside the row. This is G1's residual at starter
scale and the best next papercut to close.

**Confidence:** high in the row-local state and written acceptance; the
page-shift trigger is source-inferred and still needs a controlled UI
reproduction. Moving draft custody must preserve account isolation and
revocation; it cannot keep an unauthorized row visible.

## 9. G8 — Loop and package costs are constraints, not background noise

**Then.** The four-plan record includes a roughly 68-second full test pass,
consumer smoke 13.35 seconds, project check 0.461 seconds and incremental
rebuild 2.34 seconds. Other retained contexts have slower consumer/check and
first-launch doctor results. These are different observations, not one
qualified full-loop measurement.

**Now.** The later bounded-bulk V6 full test script passes in 105.234 seconds,
over the 60-second budget. Its earlier 54.79-second V5 pass did different
rebuild work and cannot prove the whole five-check budget. Source test
success and time-budget success must be recorded separately. Slower scoped
qualification belongs on the existing schedule; calling an overrun intended
behavior does not satisfy `rules/RULES.md`.

The latest Insights record measures the complete local runtime at **89,999
gzip bytes** against the unchanged **90,000 ceiling / 80,000 target**.
There is effectively no implementation headroom. Its smaller published-entry
growth guards remain separate; being below the complete-runtime ceiling
does not waive them. The one-time release exception in the
[package-growth ticket](../issues/20260911-snapback2-package-growth-after-four-plans.md)
is scoped to that release, not all future additions.

**Residual.** Fund further SDK work through measured deletion or
simplification and check the integrated entries. The loop bar still requires
a fresh agent building reduced Clique on the published package under its
stated time/correction limits. Neither fast individual verbs, builder-green
milestones nor a holistic score establishes that bar.

**Confidence:** high in those recorded costs; limited in attribution across
different hosts/build states. Owners: existing loop/package follow-ups,
`rules/RULES.md` and the publication path. No additional gate or budget
increase is proposed.

## 10. Recommended order and decision criteria

Priorities are hypotheses about removed builder work, not score predictions.

| Work | Why it is next | Owner and useful exit |
| --- | --- | --- |
| Qualify the existing query/admission fixes; reproduce the remaining browser cases | Avoid spending another lane on code already landed; remove the reason for an auxiliary client | LLP 1023.000/.002: same-client screen and custody matrices pass |
| Ship complete query/job forms at the real fixture envelope | Smaller lane bounds currently risk hiding data; wording alone cannot fix missing coverage | LLP 1023.001: compiled and executed full-population recipe |
| Continue attributed acquisition work | About 28.5 seconds is far from the 2–3-second objective; this remains material even if client ergonomics improve | LLP 1018.008.007.002 and its open ticket, including first-view and cleanup failures |
| Fix the starter edit-draft issue as a small independent task | Source suggests a concrete loss of user work; a bounded reproduction can justify the fix | Existing G7 ticket; draft survives a page shift without retaining unauthorized content |
| Run the scoped invalidation experiment when a real edit exercises it | The potential benefit is smaller blast radius; evidence has not yet established a safe useful change | LLP 1018.002 §7 |

The first two tracks need not wait for the acquisition target, but their
success cannot close it. Do not make papercut work the sole strategy or
dismiss its value without evidence. Compare correction loops and removed
application work at fixed requirements; use holistic scores as descriptive
feedback. The 0.0.24/0.0.25 run records include shared-host and cross-lane
incidents and do not establish independent graded success for this program.

Compiler-generated fallback queries, collection lineage analysis, helper
module assembly, new policy identities and retention eviction remain
unselected. **Bounded multi-page transport is already implemented** under
LLP 1018.008.007.002; it is no longer a hypothetical forbidden optimization.
That narrow drain/acknowledgement protocol does not authorize arbitrary query
batching, a second cache or relaxed proof prices. Further changes must fit the
current byte/loop constraints and their existing owners.
