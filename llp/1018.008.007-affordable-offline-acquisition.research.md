## Problem

Snapback's local evaluator, held authorization evidence, durable outbox, and
offline search become useful after the client acquires and prepares the
relevant data. For a populated account, that acquisition can dominate startup
time and memory, making the platform's strongest capabilities feel expensive.

A short total sync time alone is insufficient. The first useful screen,
foreground input and sending while history downloads, and the cost of reopening
an already populated account all shape whether offline support feels ordinary.
The user should not have to wait for unrelated historical work before the
available part of the application is useful.

## Why initial sync is still expensive — 2026-09-11

The author commissioned this architectural research and a new implementation
plan after comparing the current 53.634-second acquisition with specialized
offline synchronization systems. The [child plan](./1018.008.007.001-acquisition-with-incremental-work.plan.md)
addresses the remaining work amplification. This extends the existing research;
it does not count earlier repairs as new work or supersede their evidence.

### Observed work

The [current profile](../benchmarks/runs/2026-09-11-snapback2-followup-diagnostics/profile-projected-comparison.md)
acquires exactly 10,008 distinct messages in 53.634 seconds. It records 201
inbox requests, 200 acknowledgement mutations, 202 groups queries, and 612
IndexedDB write transactions. Renderer thread CPU is 47.687 seconds. Sampled
GC is 10.449 seconds; acknowledgement cleanup is 6.109 seconds inclusive,
other detached outbox reads 5.960, React root work 4.874, and coverage application
4.751. Inclusive categories overlap. Network request-to-header and transaction
lifetimes also overlap CPU; neither is an independently subtractable blocker.
The 604 MB endpoint heap is neither post-GC retained memory nor measured peak.

This is an instrumented, shared-host diagnostic. It establishes expensive local
paths, not a clean latency distribution or the cause of every allocation. In
particular, asynchronous stacks do not identify which outbox selector caused
all copying. The 202 groups queries are observed; their complete causal chain
must be established before claiming a specific invalidation repair removes them.

### Architectural comparison

Ordinary cloud query latency and complete durable offline acquisition measure
different tasks. Convex's ordinary synchronization description explicitly does
not promise full offline sync; its live result delivery is therefore not our
full-history comparison ([Convex](https://www.convex.dev/sync)).

PowerSync is the more relevant comparison. Its service consumes source changes
and prepares authorized subsets in bucket storage. Client catch-up streams
those stored changes without directly querying the source database for every
batch. This moves work ahead of client connection and pays for a separate
replication service and stored representation ([service architecture](https://docs.powersync.com/architecture/powersync-service)).
The client maintains SQLite data and sync metadata, with ordered operations,
checkpoints, checksums and reconnect positions. Initial and incremental sync
use the same protocol; this is not a claim that its fast path omits correctness
or uses a separate bulk protocol ([protocol](https://docs.powersync.com/architecture/powersync-protocol),
[client architecture](https://docs.powersync.com/architecture/client-architecture)).

PowerSync's January 2025 vendor benchmark reports mean initial sync for 10,000
rows of 0.36 seconds on native Linux, 1.4 on a Pixel 8a, and 2.5 on Flutter web
with IndexedDB; OPFS is about 0.6 seconds. It averages ten runs with a local
server. These are different records, hardware, clients, and completion criteria;
our messages additionally entail delivery events, joined bodies, coverage and
application delivery acknowledgements. No exact competitive multiple follows
([benchmark and setup](https://powersync.com/blog/how-fast-is-powersync-performance-benchmarks-for-flutter)).

Snapback currently drains certified application queries of at most 50 events.
Each accepted page updates durable rows and query knowledge; receipt admission
and settlement then use the ordinary outbox. Mounted queries observe changes
through the shared client. This reuses correct machinery but incurs many
full lifecycle operations during catch-up. A 50-row query bound need not forever
determine transport, persistence, or observer granularity, but changing those
boundaries is a separate design decision with authority and failure semantics.

### Necessary knowledge versus avoidable implementation work

Snapback keeps enough authorized knowledge to execute supported Quarry queries
offline and distinguish incomplete results from empty ones. Delivery custody
also preserves original-recipient history and only acknowledges durably
accepted event/body disclosure. These are useful semantic differences. They do
not require repeatedly scanning historical acknowledgement records, copying
an unchanged complete program for a small target projection, or refreshing
unaffected UI work after every bookkeeping change.

For illustration, scanning the accumulated prefix after each 50-record batch
visits `50 + 100 + ... + 10,000 = 1,005,000` records, versus 10,000 for one
pass. That arithmetic is not a measured count. The corresponding baseline source pattern
exists: `pendingDeliveryAcks` enumerates retained marks, and
`applyDeliveryAcknowledgements` scans all marks during every store commit.
Multiple lifecycle commits can amplify it further. The prior pending-only
projection removed deep copying but retained the enumeration.

The carrier already journals changed records and writes them incrementally;
it does not rewrite the entire database on every page. The next repair should
use that journal to maintain derived pending/intent indexes, and project only
the small data an internal consumer needs. JavaScript versus native SQLite
affects constants, but language replacement does not repair repeated work and
WASM remains outside scope.

### Confidence and next decision

At the start of this commission, confidence was high that the named scans
existed and the local profile was CPU-heavy.
Moderate confidence: eliminating them and narrowing copying/invalidation will
materially improve full acquisition. Unmeasured: the attainable minimum latency,
exact competitive ratio, and how much residual time demands transport changes.
The 30-second goal remains an interim target; lower latency is desirable, not
an unsupported promise. The child plan measures the resulting implementation
before deciding whether transport batching earns its complexity.

This is the 2026-09-11 problem-definition commission. It prescribes no batching
protocol, scheduler, representation, storage policy, or performance budget.
The initial problem definition used source baseline `b47337b26`. The subsequent
dated implementation record uses current product inputs and new measurements.

## Evidence and limits

The retained [cold-sync cohort](./1018.007.002-bounded-cold-sync.plan.md#current-black-cold-series-qualification)
acquired 10,008 inbox rows in 201 responses, with p95 22,465.823 ms and maximum
23,753.609 ms on a contended BLACK host. Timing included navigation, auth, and
sync; those rows are not a count of distinct messages.

A [separate instrumented diagnostic](./1018.007.002-bounded-cold-sync.plan.md#final-candidate-operation-counts-and-post-gc-heap)
took 16,737.659 ms and retained 127,619,872 JavaScript heap bytes after GC. It
recorded 207 carrier commits, 613 query evaluations, 20,484 row preparations,
and one whole twin snapshot installation. This is a single diagnostic, not
controlled comparative heap evidence or proof of an asymptotic bound.

Since that baseline, [LLP 1018.008.004](./1018.008.004-cheaper-offline-acquisition.rfc.md)
implemented validated immutable schema-identity reuse, stable native sorting,
and removal of discarded recursive collections. The named collector diagnostic
fell from 1,504,500 copied entries to 3,000. These are meaningful local results;
they do not establish a new end-to-end cold-sync latency. LLP 1019 also changed
delivery representation, so comparisons must identify the delivery semantics
and package under test rather than attributing all differences to optimization.

Confidence is high in the retained observations and landed local changes.
The current dominant end-to-end cost, the memory amplification ratio, and
whether background work delays current foreground requests remain questions.

## Desired outcomes

1. A populated account reaches a useful, truthful first screen promptly while
   further history is acquired.
2. Interaction and ordinary foreground writes remain responsive during
   acquisition without violating replay order or admission guarantees.
3. Already acquired knowledge survives restart and becomes useful without
   repeating the entire network and preparation workload.
4. Work and retained representations are proportionate to the data and evidence
   needed for the promised offline behavior, with measured costs explained.
5. Improvements preserve exactly which rows, search results, pending changes,
   and media are available under the same authorization and retention policy.

Evidence for later solution proposals should distinguish time to useful data,
time to catch-up, foreground interaction/send latency, warm and cold reopen,
peak and settled JavaScript memory, and durable bytes. Request, transaction,
preparation, and evaluation counts can explain a result; reducing a count alone
does not demonstrate improved user experience. Future proposals should choose
scoped workloads and targets using the existing measurement machinery.

## Constraints and unresolved questions

[LLP 1012 §§4–9](./1012-local-first-v1.spec.md#4-the-range-store) and
[LLP 1019](./1019-derived-delivery-custody.rfc.md) govern evidence, persistence,
retention, and delivery. Sharing row values cannot merge different authority
or observation evidence. Progress cannot precede durable acceptance. Required
revocation, reset, clock, and terminal transitions cannot be skipped merely to
reduce notifications.

The [current scope limits](../rules/NOT-DOING.md) remain: the complete local
runtime has a 90,000-byte gzip ceiling and 80,000-byte target; broad store
eviction and retention redesign remain deferred. This commission changes no
budget, client arm, gate, or service.

Future solution work should answer:

- What dominates on the current package, separately for browser and Expo?
- How much retained memory is unique content, authority, indexes, or duplicate
  materialization? Which owners require each representation?
- Does foreground work wait on background acquisition, and which waits are
  necessary for correctness?
- How much useful offline behavior exists at intermediate checkpoints and
  after restart, with identical acquired data?
- What real latency or memory benefit survives after accounting for load,
  compiler/package version, carrier, and changed delivery semantics?

LLP 1018.008.004 remains the earlier mechanism and measurement record. This
document broadens the evaluation to user-visible acquisition and responsiveness;
it does not reopen the completed LLP 1018.007 correction or accept that RFC's
deferred transport and retention alternatives. Later solution sub-LLPs should
reference and extend existing work where it fits.

## Bounded implementation — 2026-09-11

The commissioned [implementation record](./1018.008.007.000-incremental-acquisition-performance.plan.md#implementation-record--2026-09-11)
removes discarded `collectRefs` parent materializations and one measured,
impossible success-compaction answer scan. Authority, byte custody, transport,
retention, and publication semantics remain unchanged. The collector diagnostic
proves its scoped work reduction, and affected carrier/outbox tests pass.

The current derived-delivery fixture was populated through supported mutations
with 100 conversations and 10,008 distinct messages. A clean 30-second Chromium
profile reached 4,500 durable messages and attributed 2,646 ms to success
compaction. Earlier samples with the correctness witness's complete-snapshot
hook are explicitly excluded from timing claims. The old frozen cohort remains
historical evidence rather than the baseline for these changes.

The [retained matched measurement](../snapback2/metrics/acquisition-20260911.json)
now contains ten alternating pairs. All candidates completed in 66.970–69.953
seconds (median 67.414); every baseline was incomplete at the 120-second cutoff.
The censored median improvement lower bound exceeds 43.8%. All candidates
acquired the same 10,008-message dataset, and eight physical owner-cut browser
reopens preserved it through public held queries. The first two Auth UI reopen
timeouts remain a development-persona limitation, not a bearer/native UI
qualification. Both variants preserved the same 950-message interrupted
checkpoint and pending write/IDs across physical restarts, then resumed and
committed the write.

The 30-second acquisition goal remains unmet. The separate foreground online
mutation probe timed out after 90 seconds on both variants; it yields no
admission or receiving-latency verdict. A [focused follow-up](../issues/20260911-snapback2-full-acquisition-and-foreground-send.md)
retains these open outcomes. Full-size matched memory, foreground responsiveness,
bearer UI reopen and native performance remain unqualified. The bounded
implementation improves current bulk acquisition; the broader goals in this
research document remain open.

## Follow-up diagnosis and bounded repairs — 2026-09-11

The [follow-up record](../benchmarks/runs/2026-09-11-snapback2-followup-diagnostics/README.md)
now attributes the foreground stall to repeated writer activation/admission and
waiting for the whole FIFO to drain before admitting a new send. Writer
activation is idempotent per scope, admission appends before replay, and a caller
can receive its own durable terminal while later work continues. Controlled
tests preserve FIFO, session custody and coverage-change settlement guards.
Three alternating instrumented controls had no baseline send admission at the
15-second cut; repaired sends admitted in 148–398 ms and returned committed in
560–1,689 ms. This is a small diagnostic cohort, not p95 qualification.

Full source-mapped acquisition profiles then identified repeated acknowledgement
history copying: 13.54 seconds inclusive after the send fix. The store now
returns only detached unbound event keys and scalar sequences to admission,
while all retained/retry marks persist. The next full profile completed the same
10,008-message fixture in 53.634 seconds versus 66.342 seconds before that
projection. These are single instrumented observations, not a clean causal
timing distribution. Key enumeration and lifecycle cleanup still grow with held
state. The 30-second goal, native timing, full-size retained memory and broader
foreground qualification remain open.


## Incremental work implementation and residual — 2026-09-11

The [reviewed child plan](./1018.008.007.001-acquisition-with-incremental-work.plan.md)
implements incremental acknowledgement cleanup and pending selection, small
certified target/queued projections, guarded removal of empty-effect ack tail
fetches, and item refresh without unrelated query reevaluation. Grok, Muse,
Astra and Gemini reviewed two plan rounds; fresh Codex and Grok implementation
reviews cleared the repaired source. The durable receipt and query-authority
semantics remain those of LLP 1012 and LLP 1019.

The clean ten-pair cohort reaches complete durable content **and** settled
acknowledgements in a median **32.554 seconds**, versus **56.458 seconds** for
the matched baseline (42.34% less). Candidate range is 32.087–33.126 seconds;
baseline range is 55.055–57.502. Content-only medians are 32.219 and 55.885
seconds. All 20 runs pass full-row content hashes, local acknowledgement state,
the post-stop owner receipt oracle and physical owner-cut browser reopen;
none fail or reach the 180-second cutoff. Frozen-input and source manifests
remain unchanged through the run. This meets the child's 30% improvement
criterion while every candidate remains above the 30-second product goal.

The selector diagnostic establishes the relevant source attribution. Full
outbox copies fall from 6,819 calls / 7.438 seconds to 2,080 / 1.939 seconds;
the new queued selector takes 0.116 seconds for 5,411 calls. Full program
copies fall from 206 / 0.715 seconds to 5 / 0.014 seconds; 201 small target
projections take 0.0018 seconds. Groups queries fall from 203 to 114, matching
89 acknowledgements whose actual effects are empty. Inbox pages and ack
mutations remain 201 each, and IndexedDB writes remain 613. These are single
instrumented diagnostics, with the initial candidate preceding the later
error-path-only repair; they explain mechanisms rather than qualify latency.

A separate final candidate control retains **172,781,080 bytes after GC**, versus
209,027,476 for its clean baseline control (about 17% less). Physical owner-cut
reopen takes 8.927 seconds versus 9.024 seconds in those controls. The interrupted
950-message prefix and the exact pending envelope/IDs survive physical restart,
then resume successfully. These are scoped browser controls, not distributions.
Foreground durable admission is 10.3 ms during acquisition and 24.7 ms after;
the corresponding public mutation returns committed after 1.213 and 0.661
seconds. Baseline controls are 38.1/52.2 ms and 1.652/1.840 seconds. Broader
foreground, bearer-authenticated UI and native qualification remain open.

The final profile still spends sampled time on canonical image construction
(2.344 seconds inclusive), JSON state preparation (1.660 seconds self), posting
tree changes (2.871 seconds inclusive), and IndexedDB replacement (1.275 seconds
inclusive). Sampled GC falls from 10.198 to 2.721 seconds self. IndexedDB
transaction lifetimes occupy a 9.027-second union and request-to-header spans
10.067 seconds; these overlap CPU and each other. They are neither additive
savings nor a proven minimum latency. Removing more repeated preparation and
examining per-page transaction/request overhead are evidence-backed next
investigations. A larger transport or batching design still needs its own plan
for authority, durable partial progress and replay; this result does not select
or implement one.

All exact controls, profile scope, failed setup attempts and final paired timing
are retained under the `incrementalWork20260911` field in the
[acquisition record](../snapback2/metrics/acquisition-20260911.json). The fixture
starts with 4,450 received and 5,558 unreceived application receipts, so this is
not qualification of a fixture whose every receipt is initially unreceived.
