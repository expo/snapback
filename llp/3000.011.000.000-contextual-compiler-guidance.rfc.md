# LLP 3000.011.000.000: Contextual compiler guidance for common authoring mistakes

**Type:** RFC
**Status:** Accepted
**Systems:** Snapback 4 binder, check, why, guide examples, generated types
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (selected scope after independent reviews; parent §7)
**Related:** [Problem](./3000.011.000-quarry-learning-cost.research.md), [Umbrella](./3000.011-recent-builder-friction.research.md), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md)

## 1. Recommendation

Extend the existing `check` and `why <op>` explanations for the three recurring
structural mistakes: row/reference confusion, authorization-prefix omissions,
and a presence-controlled fallible read that prevents prediction. Reuse the
binder's existing facts. Do not add a second analyzer or weaken those facts.

The proposed increment is contextual presentation, with narrowly safe fixes;
it is not a new language or a claim that existing diagnostics lack root
causes. First capture their current output and retain
only improvements that remove a demonstrated extra inference by the builder.

## 2. Proposed behavior

| Case | Context the diagnostic should provide |
| --- | --- |
| Wrong reference kind | Expected table reference, actual row/reference kind, the helper parameter and call site; show a valid expression only when the actual typed value contains that exact reference. Never suggest casting one table's id to another. |
| Incomplete membership-scoped read | The rule probe, the missing conversation equality, and an existing compatible index if one exists. If an index must be declared, show its actual column order and the query change together. |
| Lost prediction through an effect guard | A short dependency path from mutation to guard to fallible read, with source sites. Distinguish server data, unknown horizon facts and guarded fallibility so they do not all look like the same fix. |

Keep the first refusal short. `why <op>` can expand the same explanation;
`check --json` should preserve stable codes and expose any new detail as
additive diagnostic data. Deduplicate shared causes. The normal success path
must not grow a catalog of hypothetical concerns.

Every proposed snippet uses names from the user's bound program. A snippet
must pass the same parser, binder and affected checks before it is presented
as a working rewrite. If that cannot be established, present the dependency
and a link to the tested card rather than invent code.

## 3. Safe fixes and author decisions

The existing `check --fix` remains restricted to unambiguous mechanical
changes. Qualifying an unambiguous name can qualify; moving a potentially
fallible read across a guard cannot. Hoisting may make the mutation refuse
when the original branch would not execute, so it needs an explicit behavior
comparison and remains an author choice.

Likewise, changing read rules, making a table public, removing a horizon,
increasing a cap or inserting an index with new uniqueness semantics must
never be presented as a semantics-preserving fix. The diagnostic should
state the trade when a rewrite changes acquisition or the answer's domain.

For feed references, prefer the typed bridges in the
[feed proposal](./3000.011.002.000-simpler-feed-integration.rfc.md) over adding
special conversions to the language. For maintained columns, consume the
owning RFC's implementation and diagnostics when qualified.

## 4. Scope and implementation sequence if accepted

1. Recreate the three diary cases as small programs beside the existing
   language/diagnostic tests, recording today's explanations and correction steps.
2. Add only missing contextual fields to the existing diagnostic producer;
   render them through the current terminal and JSON paths.
3. Update the relevant guide paragraph and test corrected examples. Keep
   unsupported or ambiguous rewrites advisory and out of automatic fixes.
4. Give fresh builders the same three tasks on control and candidate packages.
   Vary task order and retain every correction, refusal and policy change.

## 5. Acceptance and rejection

The candidate must preserve acceptance/refusal, authority and prediction
classification for the original programs. Tests should verify actual fixes
compile, and ambiguous/semantics-changing edits are not auto-applied.

For a small pilot, target one correction cycle or less for each of the three
cases and no policy weakening. Record lookup count, output volume and time
beside correctness; the pilot is descriptive. Existing subsecond `check`
expectations remain; do not add expensive whole-program recompilation to
every successful check merely to generate unused suggestions.

Reject the added output if the current messages already meet the task or the
candidate produces longer reading with the same errors. Ordinary TypeScript
functions, a synonym for every guessed spelling, and another documentation
index are broader alternatives with costs this evidence does not justify.

## 6. Reviewed implementation boundary

The binder already retains helper source sites. Reuse them without an inlined
stack IR. Expected/actual helper types, uniform-prefix explanations and
prediction root deduplication also already exist. Record current output first;
leave sufficient cases unchanged. Prefer an existing compatible index and
explain a missing dependency only where the reduced cases demonstrate value.
This is the accepted narrow increment under the parent §7; a larger diagnostic
redesign and a new pilot harness are not part of implementation.

## 7. Implementation record — 2026-09-22

The unchanged producers were run first against three reduced programs in
`crates/snapback4-lang/tests/builder_guidance.rs`. Their actual terminal,
serialized diagnostic and `why` output is retained in
`tests/fixtures/builder-guidance-control.txt`. Both control tests passed on
the warm M5 lane; no compiler guidance had changed during that execution.

The reference case already reports `E_QUARRY_TYPE` at `schema.q:11:18`:
`deliver's event is a events reference; got a posts row`, followed by
`pass a events reference for event`. That producer and its output remain
unchanged. The companion case still accepts a same-table row through the
intentional helper coercion. No cast or synthetic `.id` fix is introduced.

The membership case already names `exists members[.conversationId, viewer]`
and the unpinned `.conversationId`. Its old rewrite proposed a new
`byConversationId: conversationId, id`, despite an existing
`byConversationMessage: conversationId, messageId, id`; it also dropped the
original message equality from the proposed index order. The candidate
prefers an existing plain index with the required column order and retains
the original equality columns when suggesting a new order. The text says to
pin the missing rule columns while retaining the old equality prefix, and
that choosing a scope narrows the answer. It does not guess which argument
is the intended scope. The corrected query and the fallback declaration
plus query are compiled by the regression tests. Matching-search guidance
keeps its existing separate recipe path.

The presence case already explains the fallible arm and evaluation, with
`connected[p]` at `schema.q:10:17`. The actual `notes[1]` at
`schema.q:11:23` was separately listed as a held read, leaving the reader to
connect the two. The candidate retains those causes and their existing keys,
attaching the already-bound read consumer to the fallible-evaluation cause.
The existing source-location pass resolves it for both `why` and JSON. There
is no new dependency analyzer, inlined stack, diagnostic envelope or change
to prediction eligibility. Repeated causes still use the existing grouping;
multiple distinct consumers retain their actual sites.

All guidance remains non-mechanical. The tests compile an author-chosen
hoist to demonstrate eligible prediction, while the prediction card explains
that the hoist can introduce a refusal on a branch that previously did not
read. `check --fix` gains no permission to move that read, alter a rule or
change an index's uniqueness. A fresh-builder pilot remains unrun and is
not represented by these compiler regressions.

Fleet verification passed all 102 affected language tests: four builder-guidance
cases, 38 frontend regressions, 49 guide tests, nine presence cases and two
search-guidance cases. The initial guide execution exposed an unrelated new
starter-document link omission; the starter lane fixed that link, and the
complete affected rerun passed. The control and candidate transcripts are
retained by the integration run. No policy, acceptance or prediction
classification changed in these cases.
