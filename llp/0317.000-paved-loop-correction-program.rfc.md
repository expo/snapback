## Summary

LLP 0317 inventories 3 fixed-or-plausibly-fixed rows, 20 not-our-problem rows,
and **46 prevention-backlog rows** from eight autonomous lanes that built the
same social app on published Snapback 0.1.29. This RFC decides how that
backlog gets worked.

Its central claim is that **the backlog is not a queue**. Three structural
facts make naive top-down execution wasteful or wrong:

1. **Reproduction debt.** Several rows name a cause that is unestablished, and
   four of them — O10, O12, O34, O42 — prescribe repairs that **already exist
   in the version the lanes ran**. Implementing against the inventory as
   written would produce changes that fix nothing, and in O10's case would
   remove working API.
2. **A retrieval multiplier.** O44 records that broad guide searches return
   nothing even when the right page exists. Roughly half the backlog's
   interventions are documentation, and three of the four already-shipped
   repairs above were *findable in principle and not found in practice*.
   Retrieval is not one row among many; it is the mechanism behind several.
3. **A profile-parity discount.** O31/O32 record that Familiar has no template
   and one documentation page. Every guide fix authored Explicit-only is worth
   half of what it appears to be worth.

The plan is six waves, sequenced so each raises the value of the next:
**truth repair → diagnosis → retrieval and parity policy → prevention →
primitives → requalification.** Waves 0 and 2's policy half are cheap and
unblock everything; Wave 4 commissions run beside Wave 3 rather than after it;
Wave 5 is the only thing that can honestly close the parent.

This RFC plans work. It does not authorize a new primitive: rows needing one
are commissioned in Wave 4 and named here as commissions, not designs.

## Goals and non-goals

**Goals.**

- Give every LLP 0317 **obligation** — not merely every row — exactly one
  wave, owner, and gate. §Obligation map is the single normative assignment;
  the wave narratives describe it and never contradict it.
- Refuse to implement against an unestablished cause. A reproduction is
  cheaper than a wrong fix plus its revert, and four rows have already proved
  the failure mode.
- Make the closure claim measurable in the terms `benchmarks/protocol.md` and
  LLP 0186/0198 already define, against a baseline that actually exists.
- Produce lanes that independent agents can run in parallel without
  colliding, per LLP 0232's optimistic-landing default.

**Non-goals.**

- Designing any new primitive. Wave 4 commissions RFCs; it contains no designs,
  and no Wave 3 lane may design one either.
- Routing the whole diagnostics registry. LLP 0193 owns that program; this RFC
  touches only the codes its own evidence names (§L8).
- Fixing the benchmark instrument beyond what Wave 5 requires to measure.
- Reaching parity with Convex/Supabase/Firebase on any axis.
- Blocking any wave on `main` being quiet.

## Design principles

**P1 — Reproduction precedes implementation for any obligation whose cause is
unestablished.** Gating is per *obligation*, not per row: O10's 1,024 ceiling
is established while its empty-projection failure is not, and only the latter
is gated. Every Wave 1 lane lands a **repro harness** — a runnable artifact
that exercises the reported shape — and one of three verdicts:

- **confirmed** — the harness fails on current main; the mechanism is named.
- **not reproducible** — the harness passes across the declared negative-evidence
  standard (§Wave 1). The row closes with its evidence retained.
- **inconclusive** — the harness cannot be made to exercise the reported shape,
  or the result is nondeterministic. The obligation stays open and says why.

A harness lands in all three cases. "Not reproducible" is a real outcome; a
single passing attempt is not one.

**P2 — Prefer the cheapest intervention that makes the next agent avoid the
loop**, in this order: make the bad shape impossible → refuse it at generate
time with the exact repair → **route the existing page** → write the page →
write the recipe. The third rung is listed explicitly because four rows in
this program are failures of it. Move up only when the cheaper rung cannot
carry the fix.

**P3 — Every documentation intervention is authored for both authoring
profiles or explicitly scoped to one.** No new page may silently assume
Explicit.

**P4 — Every diagnostic code *this program touches* gets a guide route, and
the route is checked.** Scoped deliberately: the registry holds 3,580 codes
against 456 guide-anchored rows, and closing that gap is LLP 0193's program,
not this one. This RFC owns the codes its own lane evidence names, plus the
non-`SNAPBACK_*` vocabulary the registry extractor cannot see at all.

**P5 — Silent degradation is a defect class, not a papercut**, and it holds
priority inside its wave. O29 (successor silently retains the old value), O35
(asset hook returns empty; live query goes silent) and the O14 family share
one property: nothing is emitted, so nothing can be looked up.

**P6 — Claims are scoped to their evidence.** The F2 correction in LLP 0317 r2
exists because a Node-only mechanism was generalized to browser evidence.
Every closure claim names the platform, profile, and client arm it was proven
on.

**P7 — An accepted design is not closure.** A Wave 4 commission that produces
an accepted RFC has routed the row, not prevented the loop. Only implemented,
published behaviour counts in §Measurement.

### Wave 5 — Requalification (the only real closure)

**Entry contract — all three are hard gates, before any rerun:**

1. **L17 — instrument and harness repair.** Owns N7 (the M3 Dave
   contradiction, which cost `sol-snapback-familiar` its entire M4–M8
   remainder and hit `grok-snapback-familiar` independently), the broken scale
   fixture (only `scale-log.sha256` shipped, leaving the deepest Snapback lane
   unscored), and N20 (the OpenCode hang that destroyed three glm cells). N20
   gates only if glm cells are included, which the plan intends.
2. **L18 — baseline construction.** The 0.1.29 parent is an inventory of
   *distinct causes with retries folded together*. That is not a correction-loop
   count. `benchmarks/protocol.md` defines a loop precisely — a done-claim,
   contrary evidence, and revision of already-produced work, with three
   attempts against one defect counted as one loop — and LLP 0201 registers the
   per-milestone fields a comparison needs. L18 retrospectively annotates the
   retained 0.1.29 lane evidence under that schema, marking cells
   **inapplicable** where the evidence cannot support the measure rather than
   estimating them. Without L18 there is nothing to compare against.
3. **Scale-tail classification.** The parent's own exit criterion requires it;
   see §Exit criterion for how this RFC scopes that.

**Then:**

4. Publish, per the repository's rapid-publication posture.
5. Rerun the matrix against the published pin with **matched cells**: same
   instrument version, same model roster at the same efforts, recorded as a
   snapshot tuple. `gpt-5.6-terra` produced zero signal in all five cells; if
   it is dropped or re-run at a different effort, its cells are excluded from
   the comparison rather than compared across a changed condition.
6. Record, for every obligation exercised, the five facts LLP 0317
   §Proposed proof specifies.

**Exit:** a dated comparison of Snapback-attributable correction loops per
milestone against the L18 baseline, on matched cells, split by authoring
profile.

## Ticket and LLP policy

- Wave 1 lanes are **not** tickets. Each lands a harness plus a verdict, and
  the verdict updates the parent row in LLP 0317.
- Wave 2, 3, and 5 obligations become filesystem tickets under `issues/`, one
  per obligation or tightly coupled group, each citing its O-row. Check the
  four pre-existing tickets named in LLP 0317 open question 1, plus the two
  closed ones this RFC identifies, before opening a duplicate.
- Wave 4 commissions become `llp-create` RFCs numbered under their named
  governing LLP, not under 0317 — they are subsystem designs this program
  requested, not sub-parts of it. Each names its implementation owner at
  commission time (P7).
- Wave 0 lands directly with its evidence.
- Anything that grows PM state graduates to Linear in the Exact project with a
  Snapback label; the filesystem ticket records the pointer and closes.

## Measurement

Progress is reported as four **disjoint** obligation states. An obligation
occupies exactly one at a time:

1. **Diagnosed** — a Wave 1 verdict landed: confirmed, not reproducible, or
   inconclusive. Diagnosis alone never counts as closure.
2. **Prevention landed** — a Wave 2/3 change is on `main`, naming which rung
   of the P2 ladder it used. A row closed at "wrote a page" when "refuse it at
   generate time" was available is recorded as a **partial**, and a row closed
   at "route the existing page" is recorded as a **retrieval fix**, which is
   what four of this program's rows turn out to be.
3. **Routed** — assigned to another owner (instrument, kit, host) or to an
   accepted Wave 4 design that is not yet implemented. Per P7 this is not
   closure.
4. **Proven** — Wave 5 evidence on the published pin, on a matched cell.

A row is **not** counted as closed because a ticket was closed on `main`. That
is the failure mode LLP 0186/0198 already names. This program's Wave 5 bar is
*fewer Snapback-attributable loops than the L18 baseline on matched cells*,
which is weaker than LLP 0186's standing absolute bar; the report states both.

## Risks

- **Wave 1 returns "not reproducible" or "inconclusive" for several
  obligations.** Likely for at least one of O10/O12, and correct if so, but it
  means the parent's row count overstates the defect count. The program reports
  that rather than reclassifying rows as documentation work to keep the number
  up.
- **Four rows already turned out to be retrieval failures** (O10, O12, O34,
  O42). There are probably more. If L8's retrieval-eval work finds that a
  large fraction of the backlog is findability rather than capability, the
  program's shape should change — and that is a finding, not a failure.
- **The evidence is N=1 per cell.** LLP 0201 scopes this. Cross-lane
  recurrence, recorded per row in LLP 0317 r2, is the only frequency signal;
  rows with a single sighting from a lane that later hung (O29, O40) are the
  thinnest.
- **Wave 5 cannot isolate this program's effect** if instrument, roster, and
  product all change. L17 changes the instrument by necessity; L18's matched-cell
  rule and the recorded snapshot tuple are how that stays legible.
- **Wave 3 is large enough to starve Waves 1 and 4.** It is the most legible
  work and the least valuable per obligation. The gates and C1's precedence
  rule exist to stop that.
- **A Familiar template (L9b) is new surface** and generates its own
  correction loops. It ships through template-portfolio qualification. It
  deliberately gates nothing.

2. Should the Familiar template (L9b) be a new `expo-chat-familiar` or a
   `--profile familiar` flag on the existing templates? The flag is less
   surface but makes every template dual-profile to maintain.
3. Is O33 the mechanism behind O6? If L5 confirms it, one obligation closes for
   free and the lifecycle story simplifies.
4. Should non-`SNAPBACK_*` emitted codes like `CODEGEN_POLICY_INVALID` join the
   LLP 0193 registry, or get a parallel route check? L8 decides; the answer
   affects LLP 0193's program, so it needs that document's owner.
5. Does the sealed scale tail add a wave? Its visible items already include a

## Exit criterion

This RFC moves from Review to Accepted when the author agrees the wave
sequencing, the obligation map, and the gates are right.

It moves to Implemented when every obligation in §Obligation map carries a
terminal state under §Measurement — proven, routed to another owner, or closed
as not reproducible — **and** Wave 5 has published its matched-cell comparison
against the L18 baseline.

**Scope boundary:** this RFC governs the obligations enumerated in
§Obligation map, which are those of LLP 0317 r2. The unsealed sol-explicit
scale tail is explicitly **outside** it. Completing this RFC therefore does not
by itself satisfy the parent's exit criterion 2, which requires the tail to be
classified; that classification is a parent-document revision, and if it adds
obligations they need an amendment here or a sibling RFC.
