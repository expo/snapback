## Summary

LLP 0317 inventories 3 fixed-or-plausibly-fixed rows, 20 not-our-problem rows,
and **46 prevention-backlog rows** from eight autonomous lanes that built the
same social app on published Snapback 0.1.29. This RFC decides how that
backlog gets worked.

Its central claim is that **the backlog is not a queue**. Three structural
facts make naive top-down execution wasteful or wrong:

1. **Reproduction debt.** Nine rows name a cause that is unestablished, and
   two of them (O10, O12) prescribe repairs that already shipped in the exact
   published version the lanes ran. Implementing against the inventory as
   written would produce changes that fix nothing and remove working API.
2. **A retrieval multiplier.** O44 records that broad guide searches return
   nothing even when the right page exists. Roughly half the backlog's
   interventions are documentation. Landing them behind a broken lookup buys
   a fraction of their value.
3. **A profile-parity discount.** O31/O32 record that Familiar has no template
   and one documentation page. Every guide or template fix authored
   Explicit-only is worth half of what it appears to be worth, because half
   the authoring surface cannot use it directly.

The plan is therefore six waves, sequenced so that each one raises the value
of the next: **truth repair → diagnosis → retrieval and parity → prevention →
primitives → requalification.** Waves 0–2 are cheap and unblock everything
else; Wave 5 is the only thing that can honestly close the parent document.

This RFC plans work. It does not itself authorize a new primitive: rows that
need one are routed to their own RFC in Wave 4 and named here as
commissions, not designs.

## Goals and non-goals

**Goals.**

- Give every LLP 0317 row exactly one disposition: a wave, a gate, and an
  artifact type. Nothing is left implicitly assigned.
- Refuse to implement against an unestablished cause. A reproduction is
  cheaper than a wrong fix plus its revert.
- Make the closure claim measurable in the terms LLP 0186/0198 already use —
  correction loops on a fresh published pin — rather than as tickets closed.
- Produce lanes that can be run in parallel by independent agents without
  colliding, per LLP 0232's optimistic-landing default.

**Non-goals.**

- Designing any new primitive. Wave 4 commissions RFCs; it does not contain
  designs.
- Fixing the benchmark instrument. LLP 0317 §2 rows N1–N20 are routed to their
  owners in §7 and are otherwise out of scope here.
- Reaching parity with Convex/Supabase/Firebase on any axis. The measured
  target is Snapback-attributable correction loops, not a competitive ranking.
- Blocking any wave on `main` being quiet. Per the repository's standing
  ruling, lanes land promptly and verify against the landed commit.

## Design principles

**P1 — Reproduction precedes implementation for any row whose cause is not
established.** The gate is a runnable artifact that fails before the fix and
passes after, checked into the repository. A row that cannot be reproduced is
closed as *not reproducible on current main* with its evidence retained — that
is a real outcome, not a failure.

**P2 — Prefer the cheapest intervention that makes the next agent avoid the
loop**, in this order: make the bad shape impossible → refuse it at generate
time with the exact repair → route the diagnostic to a page → write the page
→ write the recipe. Move up this ladder only when the cheaper rung genuinely
cannot carry the fix. This is LLP 0310's author standard restated as an
ordering.

**P3 — Every documentation intervention is authored for both authoring
profiles or explicitly scoped to one.** No new page may silently assume
Explicit. This is the O32 discount applied as a rule.

**P4 — Every emitted diagnostic code that an agent can hit has a guide route.**
The registry already tracks this; the gap becomes a checked invariant rather
than a periodic audit.

**P5 — Silent degradation is a defect class, not a papercut.** O29 (successor
silently retains the old value), O35 (asset hook returns empty, live query
goes silent) and the O14 family share one property: nothing is emitted, so
nothing can be looked up. These are prioritized above louder failures of
similar size.

**P6 — Claims are scoped to their evidence.** The F2 correction in LLP 0317 r2
exists because a Node-only mechanism was generalized to browser evidence.
Every closure claim this program produces names the platform, profile, and
client arm it was proven on.

## The waves

### Wave 0 — Truth repair (no code, blocking)

Three artifacts assert that the matrix's cross-client fanout reports were a
test-harness artifact and not a Snapback defect. LLP 0317 r2 withdrew that
claim: the mechanism is Node-gated by construction, while the broadest
evidence is same-client and browser-to-browser. Until they are corrected, the
repository's own benchmark record argues against investigating O14.

documentation gap that made it look like a defect).

### Wave 4 — Primitive commissions

Rows that cannot be closed by a diagnostic, type, page, or template. Each
becomes its own RFC under its governing subsystem LLP. **This wave commissions;
it does not design.** Sizing here is deliberately absent — that is the
commissioned RFC's first job.

| Commission | Rows | Governing LLP | Question the RFC must answer |
|---|---|---|---|
| **C1 — causal subscription receipt** | O15 | LLP 0219 | What minimal receipt lets an agent trace hook → authority generation → commit → invalidation publication → subscriber revision without reading source? This is open question 5 of the parent and the row the whole authority bundle turns on. |
| **C2 — membership-scoped authorization** | O34 | authorization LLP | Is membership-scoped read/ephemeral authorization expressible today? Three lanes each **widened visibility to ship**; if it is expressible this is a routing failure, and if it is not this is a primitive gap with a security cost. | **C3 — server-observed delivery** | O43 | LLP 0219 / live queries | Should delivery be observable server-side when a principal's live query fetches, or is client-ack the supported answer? Either is defensible; the current state — no primitive and no stated pattern — is not. |
| **C4 — time-window primitive** | F3 open half | clock ticket | Can a protected query depend on server time without the clock-dependent-visibility refusal, or is scheduled purge the intended shape? `grok-snapback-familiar` states it precisely: "disappearing expiry cannot be a server query filter without a scheduled purge." |

### Wave 5 — Requalification (the only real closure)

Per LLP 0186/0198, closure is measured as fewer Snapback-attributable
correction loops on a fresh published pin, not as tickets closed on `main`.

1. Publish, per the repository's rapid-publication posture.
2. Rerun the Clique matrix against the published pin, with the four lanes r1
   omitted included by default and with `gpt-5.6-terra` either dropped or run
   at an effort that produces signal — its five cells produced none.
3. Fix the two instrument defects that cost the most lane-time first, or the
   rerun re-buys them: the M3 Dave contradiction (N7, which cost
   `sol-snapback-familiar` its entire M4–M8 remainder and hit
   `grok-snapback-familiar` independently) and the broken scale fixture (which
   left the deepest lane unscored). Neither is Snapback's defect; both are
   Snapback's measurement problem.
4. Record, for every row exercised, the five facts LLP 0317 §Proposed proof
   already specifies.

**Exit:** a dated comparison of Snapback-attributable correction loops per
milestone against the 0.1.29 baseline, with per-row disposition.

## Instrument and harness routing

LLP 0317 §2 correctly places these outside Snapback, but two of them are
measurement blockers for Wave 5 and must be owned, not merely classified:

- **N7 (the M3 Dave contradiction)** — blocking for Wave 5. The frozen
  instrument contradicts its own send-time-recipient invariant, and a lane
  that honors the product invariant cannot pass the harness check. Fix and
  version the instrument; preflight starter state against choreography
  preconditions.
- **The broken scale fixture** (only `scale-log.sha256` shipped, not the
  actual scale log) — blocking for Wave 5's O5/scale evidence, and the reason
  the matrix's deepest Snapback lane is unscored.
- N1–N6, N18, N19: instrument packet, launcher credential validation, and
  acceptance-code fixes. Not blocking.
- N8–N11: the social UI kit or the choreography contract owes a web adapter.
  Not blocking, but four lanes each rebuilt the same bridge, so the cost is
  paid every run.
- N12–N15, N17, N20: host image and runner. The OpenCode hang (N20) cost
  three glm cells and should be fixed before the rerun.

## Ticket and LLP policy

- Wave 1 lanes are **not** tickets. Each is a reproduction plus a verdict,
  landed together, and the verdict updates the parent row in LLP 0317.
- Wave 2 and Wave 3 rows become filesystem tickets under `issues/`, one per
  row or per tightly coupled group, each citing its O-row. Check the four
  known pre-existing tickets named in LLP 0317 open question 1 before opening
  a duplicate.
- Wave 4 commissions become `llp-create` RFCs numbered under their governing
  subsystem LLP, not under 0317 — they are subsystem designs that this program
  requested, not sub-parts of it.
- Wave 0 and Wave 5 are landed directly with their evidence.
- Anything that grows PM state — assignment, cycles, cross-repository
  coordination — graduates to Linear in the Exact project with a Snapback
  label, and the filesystem ticket records the pointer and closes.

## Measurement

The program claims closure only on Wave 5 evidence. Interim progress is
reported as three counts, not one:

1. **Rows retired by cause** — Wave 1 verdicts: confirmed defect fixed,
   not reproducible, or working-as-designed with the doc gap closed.
2. **Rows retired by prevention** — Wave 2/3 landings, each naming which rung
   of the P2 ladder it used. A row closed at the "wrote a page" rung when the
   "refuse it at generate time" rung was available is recorded as a partial.
3. **Correction loops on the rerun** — Wave 5, per milestone, against the
   0.1.29 baseline, split by authoring profile.

A row is **not** counted as closed because a ticket was closed on `main`.
That is the failure mode LLP 0186/0198 already names.

## Risks

- **Wave 1 returns "not reproducible" for several rows.** Likely for at least
  one of O10/O12, and it is the correct outcome, but it means the parent
  document's row count overstates the defect count. The program reports that
  honestly rather than reclassifying the rows as documentation work to keep
  the number up.
- **The evidence is N=1 per cell.** LLP 0201 already scopes this. Cross-lane
  recurrence, now recorded per row in LLP 0317 r2, is the only frequency
  signal available, and rows with a single sighting from a lane that later
  hung (O29, O40) are the thinnest.
- **Wave 5 cannot isolate this program's effect** if the instrument, the model
  roster, and the product all change between runs. Hold the instrument and the
  roster fixed except for the two blocking instrument fixes, and record both.
- **Wave 3 is large enough to starve Waves 1 and 4.** It is the most legible
  work and the least valuable per row. The gate in §Waves exists to stop that;
  if lanes are contended, Wave 1 and the C1 commission take precedence.
- **A Familiar template (L9) is new surface**, and new surface generates its
  own correction loops. It must ship through template-portfolio qualification
  like any other template.

## Open questions

1. Does C2's pre-step retire the commission? If membership-scoped
   authorization is already expressible, three lanes widened visibility for a
   routing failure, which would make it an L8 row and a much cheaper fix.
2. Should the Familiar template (L9) be a new `expo-chat-familiar` or a
   `--profile familiar` flag on the existing templates? The flag is less
   surface but makes every template dual-profile to maintain.
3. Is O33 the mechanism behind O6? If L5 confirms it, one row closes for free
   and the lifecycle story simplifies.
4. Does the sol-explicit scale tail, once sealed, add a wave? Its
   already-visible items include a general successor defect
   (`SNAPBACK_SCHEMA_FIELD_RETYPED` on a widened bound) and a saturated
   mutation ledger refusing reads — neither is a scale-only concern.
5. Should Wave 5 rerun on more than one platform? Every 0.1.29 lane was Linux
   web-only, so the native and macOS legs of the parent's evidence are empty,
   and O26's capability skew was platform-specific.

## Exit criterion

This RFC can move from Review to Accepted when the author agrees the wave
sequencing and the gates are right. It moves to Implemented when Wave 5 has
published its comparison and every LLP 0317 row carries a terminal disposition
— fixed and proven, not reproducible, routed to another owner, or superseded
by a Wave 4 design.
