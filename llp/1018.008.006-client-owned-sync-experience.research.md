## Problem

Snapback owns durable mutation admission, replay, account custody, and query
freshness. Applications still inspect those mechanisms to explain whether a
message is saved, whether useful work is underway, and what a user can do next.
The same integration is repeated in the React and Expo composers.

The problem is the gap between correct internal facts and an easy, correct
application experience. A connected transport does not establish that queued
work is progressing; readable cached data does not establish current server
confirmation. The ordinary UI needs to express those distinctions without
becoming another synchronization coordinator.

Charlie commissioned this problem statement on 2026-09-11. It selects no new
hook, status vocabulary, retry policy, scheduler, or recovery protocol. Source
inspection uses `b47337b26`; execution evidence below belongs to its cited runs.

## Evidence and current strengths

- [LLP 1018.008.000](./1018.008.000-client-owned-recovery.rfc.md#selected-implementation-2026-09-10)
  already implements bounded account-owned recovery and capacity acquisition.
  The historical requirement to manually replenish every exhausted grant is
  not the current default. Explicit recovery still matters when work stops.
- [Snapshot summaries](../snapback2/packages/snapback2/src/snapshot.ts) already
  derive status, reasons, readiness, and labels from orthogonal facts. The
  remaining problem is their consumption and composition, not their absence.
- The [React composer](../snapback2/packages/snapback2/templates/chat/react/src/Composer.tsx)
  and [Expo composer](../snapback2/packages/snapback2/templates/chat/expo/src/Composer.tsx)
  inspect queue entries and forwarding state, call `online()`, await
  `outbox.settled()`, and maintain separate recovery messages.
- The [September 11 triage](../issues/closed/20260910-snapback2-clique-0021-findings.md)
  reproduced a held complete zero that was explicitly twin-sourced, stale,
  and not live, before convergence to the current count. It did not reproduce
  a false live/server zero. The original multi-aggregate Insights report and
  offline vote-flush stall remain open; they must not be relabeled as solved
  presentation issues.

Confidence is high in the repeated source-level integration. The remaining
benefit of a smaller public surface needs an application comparison. An
additional helper that merely moves the same branching elsewhere is not yet
evidence of a simpler product.

## Desired outcomes

1. A composer can present admission, durable progress, refusal, and the useful
   recovery action through the client surface without reading queue internals.
2. React, Expo, and headless callers share recovery ownership. Mounting more
   consumers does not create more retry loops or independent progress state.
3. Cached readable data can stay visible while its freshness is understandable;
   the UI does not present an unknown value as zero or stale data as live.
4. Account restoration, follower takeover, reconnection, and stopped replay
   have usable default explanations and actions with fewer application decisions.
5. Failure preserves the user's draft or durable intent, with an explicit way
   to resolve work that cannot proceed automatically.

Success should be assessed across the complete client application: ordinary
send, brief disconnection, an explicit offline cut, stopped replay, follower
admission, account switch, and a cold reopen. Exact acceptance scenarios and
implementation sequencing belong in later proposals.

## Constraints and unresolved questions

[LLP 1012 §7](./1012-local-first-v1.spec.md#7-writes-offline),
[LLP 1018.004](./1018.004-truthful-and-composed-writes.decision.md), and the
[current recovery guide](../snapback2/packages/snapback2/guide/offline.md#recovery)
continue to govern. Preserve FIFO custody and admitted intent bytes. Explicit
offline mode forbids automatic networking until the user reconnects. Refused
non-admitted writes cannot be silently resubmitted. In-flight or unknown
outcomes cannot be discarded as ordinary failures.

Future solution work should answer:

- What is the smallest public action/progress contract that removes both
  composers' coordination while retaining operation-specific readiness?
- Which statements are SDK facts and which are product copy? When is a
  freshness label sufficient, and when does an action need confirmed data?
- How does an explicit recovery action report stopped work and cancellation,
  especially across account changes and unmounts?
- Can existing outbox/item decisions serve both the device-work list and
  message bubbles without parallel eligibility predicates?
- Which reported stalls are correctness defects, and which are correctly
  reported pauses that the UI makes difficult to understand?
