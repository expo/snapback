## 2. What the current rule protects

| State | Actual mechanism | What retained sources can prove |
|---|---|---|
| Original event | `crates/snapback4-core/src/engine/timeline.rs:84–100`: event id = source post id; immutable actor/time and originals filter determine its projection | The current live event, with its original id |
| Repost event | `engine/timeline/slots.rs:16–25` mints an independent id during insertion, using `Context::mint` (`engine/mod.rs:210–216`); source id and event id are different allocations | A never-materialized source has no event id. **An existing declaration's source does retain it**, in its engine slot |
| Event consumers | `engine/timeline.rs:168–211`: delivery work names event id; inbox identity is `(reader,event,epoch)`; removals address event id; `bind/timeline.rs:165` orders and filters those copies | Reassigning an id changes list keys, equal-time order, cursor position and potentially the 1,000-event cut |
| Follow admission | `engine/timeline.rs:156–160`, `engine/timeline/online.rs:6–18`: edge epoch = transaction sequence + write ordinal, independent of source id or `.at` | Current follows prove membership, not the lifetime or admission order of that membership |
| Backfill/delivery | `engine/timeline/work.rs:61–93`: backfill copies births before the epoch; delivery copies births after it | A source timestamp cannot decide either side of the admission boundary |
| Removal/cleanup | `engine/timeline/slots.rs:78–82`, `engine/timeline/work.rs:95–132`: tombstone first, delete event, purge copies, cancel delivery, then retire tombstone; unfollow cleanup addresses only the old epoch | Current rows cannot recover deleted repost incarnations, pending copies, old edge epochs, work cursors or already-retired tombstones |

Here and below, paths abbreviated `engine/...` are under
`crates/snapback4-core/src/`; `bind/...` is under `crates/snapback4-lang/src/`.

A new follow **does backfill**: newest 50 live events synchronously, then up to
950 more, in descending `(at,eventId)` order. Later births do not consume that
history allowance. Conversely, an early follow can accumulate arbitrarily many
later deliveries; 1,000 is not an inbox eviction cap. Own copies are not capped
by this per-follow history window. The work record of a delivered event remains
with `status=done` so a future backfill can still compare its birth order
(`engine/timeline/work.rs:120–125`). Delivery alone does not make a page
incomplete; pending reader backfill/cleanup does (`engine/timeline.rs:279–283`).

For cleanup, compare never-followed with unfollowed-after-1,000-deliveries:
both have no source edge, but the latter still has old-epoch copies and queued
cleanup after its immediate 256-copy deletion. For removal, compare never
reposted with repost-deleted-before-purge: neither has the source repost, but
the latter needs a tombstone to suppress held copies and cancel old delivery.
The existing `timeline_background` tests for epochs and last-chunk purge
exercise these cases; their 17 tests and the admission-order regression pass
in the attached [baseline log](../snapback4/experiments/following-adoption/baseline-following.log).

Two executable counterexamples in
[`following_adoption_research.rs`](../snapback4/crates/snapback4-lang/tests/following_adoption_research.rs):

1. Follow, then 1,001 posts: 1,001 foreign copies after delivery. The same current
   posts/follows with follow after those posts: 1,000. Source rows alone cannot
   distinguish the histories. Refollow with a reused application edge id also
   starts a fresh engine epoch; delayed old cleanup must not delete new copies.
2. Identical visible repost source rows, supplied different event mint inputs:
   different Following ids. LLP 3000.016 slots differ too. Thus the diagnostic
   “source rows do not retain event identities” needs qualification: **existing
   declaration-specific slots do retain live identities**. For reposts it is
   accurate for a new declaration, or after retirement projected its slots away;
   originals always retain their post ids.
   Even intact live slots do not supply the missing edge/copy/work history.

The original refusal lived in `engine/timeline/activation.rs`; unchanged
declarations still skip launch, redefinition stays refused, and the withdrawn
experimental builder stays fenced. `store/timeline_launch.rs` now admits a
first-use launch. Populated profiles do not affect its source/copy count.

### Device acquisition is a separate boundary

LLP 3000.016 stays intact. Source floors are global, fixed at acquisition and
non-sliding. Each reader acquires the newest 1,000 **merged inbox copies**, not
1,000 per actor (`bind/timeline.rs:126`). Held source slots carry partial-kind
event state; fully synced kinds retain owned event rows. Edges and removal
records retain their existing audiences. A card miss or an inbox scan crossing
the acquired floor withholds the whole local answer; it does not prove absence.

For example, a device that acquired 1,000 copies and then received 500 new
copies holds 1,500; a cold device at the same server state acquires 1,000.
The source state does not identify either device's floor.

Adoption does not let a server reconstruct a device's old floor, watermark,
held delivered history or pending predictions from source rows. It need not:
adding slots already requires a new generation and reacquisition
(`crates/snapback4-core/src/successor.rs:222–225`). Fill every source slot before
publishing that generation, as required by LLP 3000.014 §7 and LLP 3000.016
§2.1a. A required post slot cannot default to false, nor an unfilled repost slot
to known absence. The proposed adoption publishes no unfinished device schema.

## 3. Launch contract

The proposed materialized program remains:

```quarry
view activity:
  posts where .parent = null and not .removed { post: .id, actor: .author, at, repost: false }
  reposts { post, actor, at, repost: true }
view following: activity where .actor = viewer or exists follows[viewer, .actor]
query home(c: cursor ?):
  return following last 20 by .at after c { *, card: posts[.post] }
```

No application replay. Use a **first-use owned and slot namespace**: catalog
numbers survive retirement, so reused owned names refuse even if empty. A fresh
name forces reacquisition; a same-name re-add beside a literal default can
preserve stale device images (`successor::keeps_literal_default_images`).

S is the committed source state when the activation acquires the writer lock;
P is its one commit. No source writer changes S between those points.

1. Preserve all public/owner/immutable/unique/non-expiry prerequisites. Orphan
   reposts and self-follows refuse; invalid input is never silently omitted.
2. Keep qualifying live originals with their post ids. Keep every retained
   repost with an existing card, including removed or filtered-out originals;
   future repost insertion still requires a live original. Mint repost identities
   from framed `(domain, fresh incarnation, declaration, source role, source id)`.
   Insert, never overwrite on collision. A retry gets a fresh incarnation.
3. Initialize retained births directly `done` at `(sequence,0)` and existing
   edges at `(sequence,1)`. Record the activation commit so future admissions
   compare strictly later. No redundant delivery work runs.
4. Each actor gets **all** their own retained events. Each existing follow gets
   exactly that actor's newest 1,000 live events in S, descending `(at,eventId)`.
   The edge window does not cap later live deliveries or own retention.
5. Fill the declaration's source slots and publish all copies with the new
   generation at P. The first page is already complete; there are no launch
   tasks or partially published pages. Future delivery/backfill/cleanup retain
   their ordinary completeness rules. Removal prunes copies and **does not refill**
   the launch window. Refollow starts the ordinary new admission window.

This is not historical equivalence. An early follower may have accumulated more
than 1,000 later deliveries; fresh launch loses that older delivered history.
New repost ids can reorder ties and change boundary membership. Launch can also
**add older events never delivered before**: follow after 2,000 posts, receive
newest 1,000, then remove those 1,000. The historical inbox is empty; launch
copies the older 1,000 still live. It also differs from a recomputed window after removal: E2…E1001 loses
E1001 and yields 999, whereas a new launch after removal can include E1 and yield
1,000. The card states pruning without refill. Current source content and membership survive, but saved feed
positions, notifications and historical reconciliation need a separate import.
Own retention and the device's merged 1,000-copy acquisition floor stay distinct.

## 4. Atomic launch adoption

**AP follow-up (2026-10-04).** General schema adoption now reports disjoint
phase times and nested index/capture details, and gives population-based
`N_ADOPTION_PAUSE` advice before activation (see the [AP report](../snapback4/reports/20261004-ap-adoption-pause/REPORT.md)).
AP round 2 also counts retirement of owned tables and transitive maintain
targets when their names survive, without counting a target twice if rebuilt.
Read-through retirement omitted from launch-copy counts still receives a
separate unestimated-pause warning. This advice complements the feed-specific estimate below; it does not alter
feed launch admission, its copy ceiling, or its deployment opt-in. All work
continues to share the existing atomic publication transaction.

**Scope and guarantees.** `store/timeline_launch.rs` constructs §3 inside the
existing `Store::activate_at_with_launch` transaction (`store/activation.rs:65`;
preflight/admission/build in `store/timeline_launch.rs:58`, `:44`, `:158`), before `event_slots::fill`,
source projection/index validation, dependent aggregate rebuild and generation
publication. One writer lock; no chunks, application fence, staging image,
reservations, manifest, roster or roster tasks. Meter pages are scratch scopes
inside that same transaction and never checkpoints. A crash before commit rolls
back slots, catalog, rows, indexes, sequence and generation; the next start
recounts and retries from scratch. Existing declarations' slots are preserved.
Ordinary later follows read the initialized done birth records normally.

**Isolation.** SQLite WAL readers retain the committed predecessor snapshot.
Candidate slot bytes are never committed separately, so predecessor queries,
snapshot pages and normalization of older log puts cannot observe them. The
commit-hook test reads all three with candidate slots already filled. The HTTP
test holds the activation immediately before commit: 32 syncs wait on the
ordinary serving-engine lock while `/q/home` and `/schema` still succeed against
the predecessor. Sync has its own bounded 32-request admission pool, separate
from queries/discovery and mutations, including when launch begins after dispatch.
It authenticates through a detached reader before waiting where available and
rechecks bearer authority after the wait; expiry or revocation refuses. A sync
then receives the generation change and reacquires; an admitted mutation executes
once on the current engine. There is no new reservation state. Existing devices'
backend adoption drops images, with native and memory-store tests for reacquisition.
An already pinned predecessor snapshot may finish after P; a new stale-engine
transaction refuses its generation identity rather than exposing candidate bytes.

**Admission and diagnostic.** Dev needs no flag. `deploy` (and rollback if it
would add a first-use feed) needs `--allow-feed-adoption`, independent of the
existing retirement `--allow-destructive` flag. `serve` only attaches to an
already committed release; it cannot implicitly adopt edited release source.
Before activation, print counts of source rows, retained events, follows,
**rows to copy**, the expected lock duration at the measured rate in §5, and the
ceiling. Without opt-in, `E_TIMELINE_ACTIVATE` includes that estimate, the flag
and this alternative: `query home(c: cursor ?): return activity where .actor =
viewer or exists follows[viewer, .actor] last 20 by .at after c` (`guide feeds`).
First-use name collisions, self-follows and orphan reposts use the same code
with the offending name/source and recovery. Invalid candidates never publish.

`check` and both runtime admission points call the same read-only preflight.
It uses activation's pinned-time retirement predicate, so expired rows that a
read-through change retires do not inflate launch counts or orphan checks.
`check` reports `N_TIMELINE_ADOPT` at each populated new declaration, including
the launch contract, source/copy estimate, expected lock time and deployment
flag. It succeeds for automatic dev launch and refuses over the ceiling or for
invalid launch sources/names. Its database and WAL stay unchanged. Runtime
rechecks under the writer lock with the same pinned time. Regression matrices
compare CLI/API/runtime verdicts and actual copy counts, including inherited
expiry changes; any divergence fails the tests.

Every mapped source read uses the candidate schema's materialized image:
event rows, a repost's original card, edges in both estimate and construction,
and slot-fill inputs. Ordinary adoption can leave literal defaults absent from
retained bytes. These sparse rows have the same launch meaning as fully stored
images. Slot filling materializes a clone for actor/post lookups and writes only
the original source image plus its new slot. Literal defaults remain absent,
including on excluded replies, so later default edits reinterpret those bytes.
Tests create sparse rows through actual schema adoption, then compare `check`
and launch, copy contents, author attribution, source slots and later reads
under changed defaults.

**Bounds and costs.** The whole activation may create at most **5,000,000 inbox
copies**, summed across new declarations. Read-only preflight counts qualifying
originals plus retained reposts by actor, then sums all own events plus
`min(1000, events(actor))` per retained edge. Its actor-count map and source
walks are metered, not unbounded row collections. A known over-ceiling copy count
refuses **before the activation transaction starts**, with the estimate and
planned-query alternative. Recheck counts under the writer lock before candidate
writes, covering a writer between preflight and lock acquisition. No ceiling or
device budget is raised. The regression observes zero SQLite writes on ceiling
refusal. Two declarations estimating 3,001,001 copies each must refuse their
combined 6,002,002 before any write; an individually admissible declaration
cannot hide the aggregate cost. A deterministic SQLite authorizer pause before
the writer transaction admits one more follow of a full actor after the unlocked
5,000,000-copy estimate. The in-lock 5,001,000-copy estimate refuses before any
candidate write, preserving the generation, post-follow sequence, source slots
and owned catalog. A later validation or meter failure rolls the transaction back.

All retained row decoding, source-slot rewriting, copy writes and indexes use
activation meters. Construction holds at most a source page and a 32-event page;
no per-reader all-actor merge is needed because no partial feed is published.
Work and disk scale with source rows, event/birth/edge records and the sum of
copies; the transaction, WAL and device reacquisition can be expensive. Counts
predict the measured fixture's cost, not a hardware/load SLO. Large or live stores
can use planned `home` now or await the separately reviewed online design. This
explicit long-lock contract supersedes LLP 3000.019 §3.6's short adoption pause
for this opt-in operation only; detached query behavior remains unchanged.

## 8. Future: online adoption

**Unbuilt, NOT READY in both round-1 reviews.** The following records the online
design and its requirements, not the atomic implementation or its shipping gates.
It would extend §3 with a pending interval after P: actor rosters freeze the newest
1,000 foreign members and all own members in S, keeping event ids/birth tokens.
A shared server-private roster body is referenced by versioned `backfill` cursors,
never embedded in the 4,096-byte cursor. Each task binds readerId/viewerId to its
reader; own tasks have null edge epoch. New events deliver live after P without
consuming the retained window. Retire a roster only after every referencing task
finishes or is validly cancelled. Missing rosters never mean completion.

### 8.1 Fence custody and fair admission

Persist the candidate digest, predecessor generation, incarnation A, phase,
cursor, fenced tables/epochs and expected per-table live high-waters before
initialization. Bump the server store version for this manifest so an old binary
cannot ignore it. Restore must contain the entire manifest and candidate or refuse.

**Reserve each accepted client mutation id durably before waiting**, keyed by
store/principal/id and bound to operation, raw arguments, submission generation
and authority lineage. A duplicate joins that reservation; changed input refuses.
A reservation is pending, never a success receipt. After release, recheck live
authority and the current generation and claim/execute/settle under the writer
transaction; effects and outcome commit together. Crash before commit leaves the
reservation retryable; after commit, every retry returns the same outcome.
Expired/revoked authority cannot execute. Queue saturation rejects before accepting
custody, explicitly retryably; it cannot silently drop an accepted write.

Each fenced table has a durable **fence epoch**. The commit path, including jobs,
sweeps, indirect maintained-column writes, imports and every writer entry point,
refuses any commit touching it without that epoch's initializer capability.
Existing readers see predecessor semantics. The fence wait holds **neither
`shared.engine` nor a SQLite write transaction**; every chunk releases both.
An initializer's own physical writes advance the manifest's expected high-water
in the same commit. Any other live high-water change fails publication.

The current shared 32-slot `Mutation` admission class (`serve.rs:376–420`) is
insufficient. Fence waiters must release its permits and use a separately bounded
wait queue. Keep executable capacity for identity writes, ephemeral writes and
authenticated receipt/reservation replay even when that queue is full. Independent
durable presence reconnects must also get turns. Do not bypass authority to replay.
A blocked maintenance job defers its turn and yields **without waiting**,
so the same loop can advance initialization. A parked candidate must not consume
all request or maintenance capacity.

Replace `work.rs:149`'s restart-at-first-declaration selection with round-robin
across nonempty runnable declarations, remembering the last selected declaration
across invocations and recovery. With D continuously runnable declarations each
gets a bounded chunk within D successful selections. Rotate work within a
declaration too: launch, delivery and cleanup each retain turns under continuous
arrivals; parked or fenced tasks release theirs. A runnable finite roster advances
at least one examined member per granted chunk; a meter refusal parks visibly; frontier construction must itself make durable
progress before a copy can be selected (§8.4).
This bounds **turns**, not disk fsync latency. FIFO engine-lock admission alone
cannot guarantee it. Regression: continuously replenish declaration 1's delivery
while declaration 2 launches; assert the selection bound, launch completion and
continued delivery/cleanup, including restart and a parked task.

### 8.2 In-place initialization and publication

Initialize the new owned event/index/birth state and rosters in metered,
checkpointed chunks; patch **only the new slots** on existing source rows.
No application `mutate` replay, effects or other declarations' slot reminting.
Preparation writes are unlogged, or logged under private names the predecessor
cannot stream. Existing engine columns, source fields and other declarations'
slots are copied unchanged. Until P the predecessor schema projects only its own
columns; neither query/sync nor an old client may observe a half-filled slot.
Candidate owned names remain inaccessible. If that isolation cannot be proved,
do not use in-place chunking; the replacement-image alternative below remains.

The publication transaction creates one task for **every** retained edge and
an own task for every nonempty own roster, then recounts and verifies exact keyed
coverage against S: no missing, duplicate, wrong-epoch or wrong-reader task;
every event has its initialized slot and `done` birth; every required roster is
present; indexes and dependent aggregates agree. A persisted init cursor is not
this proof. A zero-task reader is complete only if the completed recount proves
zero obligations. The transaction publishes the generation, coverage record and
work together, then releases the fence. Table high-waters must equal the manifest,
or publication fails. No success can erase a receipted source write.

Task creation/recount costs O(F + U), for F retained edges and U readers with
own events, not a constant-time swap. Use the existing
metered activation walk, charging every examined/written row and index; do not
replace it with unmetered SQL or raise ceilings. Its transaction and recovery
pause must be measured. If it cannot meet the pause requirement, a reviewed
atomic publication of prebuilt task coverage is needed; discovering tasks after
publication is not an acceptable shortcut.

Every read of a reader's Feed depends on launch coverage and that reader's work,
including point misses, `byReaderActor`, other indexes, scans, joins and folds,
on server and device. The check cannot be restricted to `Cut::Cap` or the two
paved indexes (`engine/timeline.rs:279–283`). Partial pages stay `complete:false`;
absence/probes without a sound partial result withhold instead of proving absence.
Writes cannot use unfinished absence as authority. Pending metadata has the
reader's private audience, participates in invalidation and survives device sync;
unknown metadata withholds. Only schemas using launch require device support for
this expanded pending check; older devices refuse that schema until upgraded.
Ordinary feeds gain no enum/schema change merely from installing the new binary.
Before P, new/changed dependent queries answer `loading:true, complete:false`,
including a replaced `home`; unrelated predecessor
queries and sync use detached WAL readers. At P replace reader factories,
invalidate obsolete loans and force source reacquisition through new slot names.

Crash before P restores predecessor plus fence/cursor and resumes; explicit
cancellation removes only candidate slots/state before releasing its fence.
Crash after P resumes work. Parked work keeps its reader pending; cancellation
cannot masquerade as completion. Serialize competing adoptions; compatible
successors preserve published work. Keep store identity, receipts, monotone
sequences and `synchronous=FULL`. Do not promise shorter `/changes` waits without
the signed-in test: LLP 3000.019 §3.6 records the existing stall.

Device regression: acquire halfway through a reader's multi-actor roster, with
at least 1,000 copies, tied times and a quiet actor. Interleave removal, live
births, refollow and a crash. At every read the device must either retain the
work/pending witness or hold **every surviving roster copy above its fixed floor**
when claiming complete. Below-floor pages still withhold. Deleting work cannot
race ahead of its copies in snapshot/stream application.

### 8.3 What the simpler design saves and still costs

`online.rs:10–18` and `work.rs:61–93,127–172` already handle ordinary concurrent
writes safely: admission tokens divide live delivery from backfill, a chunk
rechecks the edge and commits cursor/copies atomically, and removals/unfollows
cannot change mid-transaction. No long application fence is needed for copying
**after** P. But unmodified backfill scans live `byActorTime`: continuous new
backdated births can remain ahead of its cursor, get skipped without spending
`remaining`, and prevent completion. It can refill after removals too. A separate frozen-roster walker with the skip/advance rules in §8.4 is required;
calling the unchanged task alone does not.

Slot fill is real O(posts + reposts) work, including filtered-out originals. Today's
`store/event_slots.rs:23–49` walks every source row, looks up its owned event,
decodes and rewrites its whole serialized image, charges scratch/writes, and
logs nothing. There is no constant-time lazy default: a missing required slot
cannot mean false. A new feed additionally needs event indexes, retained birth
records, edge enumeration and finite rosters. The atomic measurements do not qualify the online roster preparation
or publication pause. Own and foreign **copies** can move after P; event identity and slots
cannot. Slot fill can be chunked durably only behind the fence, with manifest
progress and predecessor-column isolation; today's single activation transaction
is not resumable chunking. Concurrent writes through partially filled slots
would need a new snapshot/delta protocol, not just shorter transactions.

**The round-1 in-place recommendation is deferred.** It removes
a replacement copy of source images/indexes and catalog-map swapping. Compared
with round 0 it loses immediate retained own copies at P and cheap cancellation
(discarding a private image); in-place cancellation must clean candidate slots.
It keeps a finite launch window but still pauses source writers for the full
initialization. Space is O(posts + reposts + follows + sum_edges min(1000, events(actor))),
plus ordinary indexes/logs and uncapped own copies. It makes no short-pause claim.

If predecessor-column isolation rules it out, corrected round-0 staging must
follow §§8.1–8.2 too: private unlogged replacement tables, other slots preserved,
no `mutate` replay, exact task creation/recount and live table high-water comparison
**in the swap transaction**, then deferred reclamation after WAL readers release.
A slipped removal after S must fail the swap, never install its old row over a
success receipt. That alternative buys source isolation and cheap discard at the
cost of extra disk, catalog custody and recovery cases. Neither publisher exists.

### 8.4 Additional round-1 requirements (both full reviews retained)

- **Merge progress (Astra High).** 16,385 heads exceed the 16,384-examination
  chunk. Persist metered head-discovery/frontier progress, then advance the

  park a finite launch forever. Reads must cost O(page), not O(follows).
- **Reservation across generations (Grok High).** A queued mutation executes
  once against the newly live engine and fills its slots. Generation mismatch
  is not a terminal `_ops` refusal: the same id must remain retryable/joinable.
  Only a real application/authority refusal is terminal. Crash/retry tests
  prove one outcome and effect on both sides of publication.
- **Committed slot isolation (both).** Current `public_image` and `project_fields`
  do not strip candidate fields absent from the predecessor schema. Before any

  this cannot be proved, use replacement images rather than in-place chunks.
- **Frozen walker (Grok High).** A roster cursor must branch on its version
  **before** hex/key decoding. It is not a `byActorTime` continuation. Removed

  corrupt roster state/meter cuts park. Unfollow cancels only the old epoch.
- **Unlogged writes (Grok).** `_commits`/partition sequence is not a table
  high-water. A per-table counter must advance with every `Tx::put/delete` and

- **First useful page (Grok).** Hash-ordered task draining can copy 1,000 old

- **Device schema and fairness.** Roster bodies are private server rows for the

- **Whole publication cost (Astra).** Task insertion O(F+U) excludes verification
  of every source/event/slot/birth, index, roster and dependent aggregate. Name
  and measure every traversed population; any durable preparation proof checked
  at publication must cover all of them. A cursor alone is insufficient.

### 8.6 General derived-state adoption after calibration 30 (AP, 2026-10-04)

digest, predecessor generation, time basis, phase and cursor. Retain a complete

crash-safe chunks, then briefly hold the writer for the last tail, validation of
the candidate's bound high-waters, and one atomic catalog/generation switch.
The existing audience partition log alone is insufficient: it does not contain
every unlogged capture, source rewrite, private recount, expiry or loader change.
Every relevant write path must participate, with a retention floor owned by the
candidate. A sequence cursor alone is not a coverage proof.

Historical captures are the hard boundary. An activation-time fact must agree

expired since S. Capturing once at S would silently change today's meaning.

replacement storage, so existing readers, sync normalization and cancellation

generation must also preserve the existing row-keyed settled/pending contract,
maintained-column mirrors, wide-sum cancellation and exact index semantics.

only after old readers release it. Test crashes before/after every checkpoint and

revocation, device reacquisition, skew and admission saturation. Compare with a
serial atomic oracle at P, including receipts and effects. These requirements
exceed a safe optimization patch; this lane implements no online protocol.

### 9.1 Evidence and approved online/offline split

repost time indexes, with a residual follow predicate. It is not a k-way merge.
On the D0 50,000-post sparse fixture it exhausts 16 MiB heap at 5,789 charged
examinations, returning unavailable/incomplete with no continuation. The default
8,192-examination ceiling is an independent bound. An existing actor-index

continue discovery. There is no product follow cap (LLP 3000.013 §4).

The materialized inbox copies 50 events immediately and at most 950 additional
pre-follow events; first-use adoption copies the newest 1,000 per edge. Later

**Online:** every history page comes from the exact per-author merge, including

Open all eligible author heads or prove their ends before publishing ordered

### 9.2 Frozen domain, identity and current authority

At opening, capture the store incarnation, schema generation and the committed
admission upper bound B in one read transaction. Births are the engine's
`Work.admitted` tokens (commit sequence plus write ordinal), not application
`at` values. B includes the last committed transaction's ordinals. Tokens and
birth probes remain engine-internal. Delivery Work is actor-private; use only
the narrowly addressed delivery witness, under a fixed reservation, never a
system-context execution of an ordinary query.

The domain is the viewer's lane plus edges whose epoch is ≤ B, and live owned
events admitted ≤ B. Discover the viewer's own edge range by `(reader,actor)`;
a new follow after B does not enter this session or restart it. A refollow,
including source-ID reuse within one transaction, has a new epoch. Capture that
epoch, not the application edge id. No self-follow lane is duplicated.

Order is `(at,eventId)` descending, with declaration-specific event ids.
Originals keep their post id; independent repost events keep their minted id.
A card id, copy id or planned-activity branch cursor is not a history cursor.
The sole event source is the existing owned `Posts.byActorTime` index. There
is no new index, birth column or change to Timeline v2 catalog serialization.

The current predicate is exactly the inbox's: actor is viewer, or its captured
edge epoch still exists, and the event is not tombstoned. Older events must also
be live in owned Posts and have a valid admission witness ≤ B. Birth existence
alone does not prove liveness. Removal of an original removes its own event;
its retained card and independent reposts remain. Repost deletion removes its
own event. A tombstone retained while Work remains, or a later purge, cannot
resurrect an event. No history-only block filter is introduced.

Before publishing a selected event, and on replay, check that predicate in the
publication transaction. Unfollow of another unselected lane only removes
possible competitors; it cannot create an earlier eligible key. Reject a stale
head and refill its lane before choosing another winner, or retire the lane if
its captured edge no longer exists. If a selected/staged/replayed event has
lost authority, restart the revision rather than rewriting that unit's page.
A new follow or an unrelated store commit does not restart it. Round 2 applies source/private
field authorization while shaping and rechecks each disclosed card point/field
before publishing and on replay; the metadata predicate alone cannot qualify it.

The SDK also withdraws already-mounted revoked events. Current authorization
is not a promise to undo bytes disclosed while authorized. The history epoch
never expands B. Later births, including backdated ones, and new follows'
recent deliveries arrive through the existing live path as a **live prepend**.
Their older events wait for the next history session. This is an explicit live
layer above the frozen history, not a claim that post-B timestamps belong to
its ordered prefix.

### 9.3 Units, replay and custody

The only progress phases are `preparing`, `page`, `stalled`, `restart` and
`refused`. Preparation is distinct from an empty page. No progress document
contains counts of lanes, candidates, rejections or examinations, private
revision counters, unpublished heads, epochs or birth tokens. Operator meter
instrumentation is separate from the serializable response.

An opaque token names **one unit**, which may be preparation or a page. Its
successor names the following unit. Checkpoint advancement and the pinned
response become visible together; a lost response cannot consume another page.
Replay returns those shaped bytes after rechecking current authority. It never
substitutes freshly chosen events or a new card image under an old token.
Authority loss restarts explicitly. Restarts are never empty success.

Bind every request to viewer, store incarnation, schema generation, declaration,
page size, argument values and consumer opening identity. Malformed, forged,
cross-binding and stale tokens cannot evict a valid consumer. Expiry, process
loss, detected restore/rewind or a changed binding restarts. Keep B separate from
the latest committed head observed by accepted work or authorized replay; a
lower later head restarts. Replacing a store with the same incarnation and an
equal/higher sequence is not detectable from these values: the host must
invalidate its controller on such a restore. The internal controller
mints opaque opening ids containing a random controller-incarnation prefix;
even a lost opening reply cannot silently reopen at a new B after a crash.
The controller registers each opening against viewer, declaration and page size
before issuing it. This separately metered registration occupies one session
slot and charges its lifecycle records. Acceptance atomically replaces it with
the traversal; an unknown or reclaimed opening always restarts. Unused openings
also expire and require bounded reclaim. There is no unbounded spent-token list.
The host/SDK uses a separate bounded `open` registration RPC, then requests the
first unit without a token. Registration is custody admission, not a history
progress response; the first unit publishes immediately when it fits. A lost
registration response leaves its slot charged until idle reclamation. Subsequent
unit retries reuse exactly the same opening and token. Registration never freezes
B or traverses author heads; the first unit does. Measurements count this extra
RPC separately from preparation units.

Keep the current and immediately preceding accepted units for replay. Requesting
a successor implicitly acknowledges older units; a token outside the retained
window restarts and never consumes the pending unit. A refused admission/unit
is not accepted and advances nothing; its token can be retried after resource
availability changes. Duplicate/reordered SDK results are owned by an opening
and revision, and obsolete responses are discarded. Mounted-page authorization
must not depend on the replay window remaining resident.

Choose **four independent sessions per viewer and declaration**: two tabs, a
second device and one replacement/recovery session can coexist. A fifth gets
`E_FOLLOWING_QUOTA`; it does not evict or share another consumer's continuation.
Idle expiry is **five minutes** since accepted work or authorized replay. Expiry
restarts the feed, not ends it. Cancellation only abandons that consumer.

The initial controller is **volatile and process-owned**, matching the explicit
crash-restart contract. It adds no persisted engine table, catalog capability,
application commit, sync row or sidecar file. An old engine continues to open
the unchanged store; there is no new persistent format requiring an old-engine
refusal in this milestone. If a later implementation introduces durable state,
its unsupported-engine refusal test is mandatory before landing.

### 9.4 Algorithm and resource model

1. Discover the viewer lane, then frozen eligible edges in key order. Seek the
   next candidate in each actor's existing time index. Check birth, liveness
   and current captured epoch; checkpoint a lane's key after each rejection.
2. Once discovery is complete, select the greatest head. Reauthorize it, stage
   the event and finish that lane's refill before selecting another head.
   No unknown replacement competes with known heads.
3. Shape a selected card under its own fixed reservation when staging it. Before
   publication, reauthorize every staged event and every disclosed card point/field
   in one read transaction. Card bodies remain the staged images; body edits do
   not rewrite them. A revoked staged image restarts. Commit the pinned response
   and successor atomically with frontier advancement.

Every lane head is an upper bound on all remaining eligible keys in its lane.
The greatest valid head is therefore the next global event. Immutable ordering
keys, captured edge epochs and the admission bound prevent a later insertion
from adding an eligible key behind discovery. Removal only shrinks the domain.
This proves **each published prefix**, not just equality of the eventual set.

A fixed finite domain does not imply a finite physical scan under continuous
post-B backdating. Keep skip-and-checkpoint now; do not add a retained snapshot
or birth-fenced enumeration. When a resource slice is obstructed by such later
births, return `stalled` with its exact successor and retained key progress.
It may resume; it is never exhaustion. Once that workload settles, continuation
terminates, subject to admission, resource quotas and session lifetime. A finite
batch may also produce `stalled`; the phase reports the obstruction, not a
prediction that the author will insert forever.

**Approved round-2 ruling:** `Edges.byPair` discovery also visits post-B
follows in its unscanned key range. Continuous additions there use `stalled`
exactly like backdated births: checkpoint strict actor-key progress, never a
false end or perpetual `preparing`, and terminate after additions stop. Only
the viewer's own follows extend this range. This closes the round-1 liveness
finding; new follows still do not join the frozen domain.

Let F be eligible lanes, D the viewer's physical edge rows visited during
discovery (including post-B follows), N the requested event count, X lawful
event-candidate rejections, and E the relevant index population. Discovery
costs O(D+F), then merging costs O((F+N+X) log F); each storage seek additionally
costs O(log E).
D can grow under the stalled follow-churn case above. Unrelated actors' row images
are never scanned; physical B-tree I/O/latency need not be identical as E grows.
Later retained-frontier pages do O((N+X) log F) selection. A fast page without
retained frontier rediscovers at its consumed position.

The initial transactional frontier uses ordered records of at most **64 heads**.
A request copies the record map and copy-on-writes only changed head records;
refusal or error leaves the prior unit intact. That implementation adds
O(F/64) record-map work per retained request, explicitly metered, rather than
claiming the ideal O(N log F) total. Its record copies and published payloads
are preflighted. A small one-request page discards its temporary heads without
writing a frontier checkpoint. Persisted-in-controller record updates count
against the ordinary rows-written allowance even though they are volatile.

All seven ceilings stay: 8,192 examinations, 16,384 index entries, 8,192 probes,
1,000,000 steps, 16 MiB request heap, 1 MiB output, 1,024 records written.
A reservation tests all dimensions before charging any. Failed reservations
change no ledger or state, and no head seeks occur after discovery cuts.
Reserve publication, response retention and checkpoint cost before more work.
Meter fixed reusable decoding scratch; engine-owned metadata has an independent
64 KiB stored-row/index-key envelope checked before SQLite payload loads and decoding. Birth/epoch/tombstone probes
use fixed reservations rather than disclosing private witness size or status.

Controller-owned allocations have a **32 MiB per-session / 128 MiB total**
accounted quota. Prices conservatively include strings, vectors, ordered-map
nodes, head records, staged events, pinned replies and lifecycle metadata.
The transaction's additional allocations remain under the request heap ceiling.
This is not a claim to cap process RSS, SQLite caches, allocator arenas, HTTP
buffers or client-retained responses (LLP 3000.002). The volatile controller has
no WAL or on-disk index overhead. Measure its allocated-state high-water mark
separately from engine/store and eventual transport costs.

Abandoned and expired state counts until physically reclaimed. Reclaim a bounded
number of records under a fresh ordinary meter; never drop an unbounded
frontier on cancellation or expiry. Count lifecycle indexes and reply retention,
and refuse quota admission without evicting another session. Opening,
cancellation and each reclaimed record reserve 64 KiB of lifecycle scratch
before cloning keys or changing ordered trees. The 128 MiB controller quota and
16 KiB retained session base bound lifecycle maps to at most 8,192 entries; the
scratch covers worst-case split paths across those maps. It is charged per
reclaimed record, so default heap permits at most 256 such records per reclaim
request even when the write allowance would permit more. The host must
schedule reclaim fairly along with foreground requests. The server invokes one
bounded reclaim slice each second under a 1 MiB temporary heap allowance; source
work uses its existing fair engine lock before the controller lock.

A shaped row that cannot fit the page output/heap envelope yields the named
ordered omission `E_FOLLOWING_ROW_TOO_LARGE` and continues past its event key.
If even its omission/control envelope cannot fit, refuse the request explicitly.
Normal rows that fit alone shorten the page at its consumed boundary; they are
not omitted merely because an earlier row used the remaining space. The metadata
milestone tested this rule on metadata. Round 2 also tests actual card shaping,
private-field revocation, immutable replay across body edits, oversized-card
continuation, and maps of many small fields against object custody prices.

### 9.5 Qualification and claim gate

The oracle is an independent full scan of owned event rows, delivery admissions,
tombstones and captured/current edge epochs. Freeze viewer plus edges at B,
keep live events born ≤ B, and sort descending by `(at,eventId)`, including ties.
Do not use the planned `activity` scan or production lane/head helpers. Compare
every published page with the next oracle prefix, including across preparation.

Required server cases: originals/reposts; original removal retaining reposts;
tombstone plus surviving Work; purge; no self lane duplication; reused edge
ids and same-transaction refollow; empty/all-rejected lanes; removal of a head,
last staged row and entire staged page; post-B and backdated births; new follows
without restart; current unfollow; more than 8,192 follows; all meter cuts,
publication/checkpoint reservations and absence of failed charges; unrelated
post density; named oversized omissions; continued key progress and stalled
phase under continuing backdating; paired hidden-row worlds and opaque tokens;
forged/cross-viewer/store/schema/declaration/argument/page-size tokens; lost
opening/page/replay responses; replay reclamation; expiry; process loss; two
tabs/devices; cancellation storms, quotas, bounded cleanup and fairness.
Blocks in the reviews' matrices are replaced by parity with the unchanged
inbox predicate, not a new history filter.

Required integration cases: authenticated `serve` route; real card projection
and authority; one generated Following hook from the declared view; sparse
online exhaustion; large-roster preparation; offline inbox plus the device fact;
live prepend and backdated arrival; mounted unfollow/withdrawal; pending own-post
and own-edge fences; lost/reordered replies; expiry restart and two consumers.
The SDK owns polling, retries, cancellation, revision reset and identity. It is
not `usePage`, and the builder never stitches cursors or author lists.

Measure first-page engine latency, preparation requests, later-page latency,
total work, allocated frontier/replay storage and reclaim on the 1,000-user /
50,000-post sparse corpus and the 8,200-follow corpus. Displayed-page and HTTP
latency claims wait for those layers. Run the full suite and Linux wasm with
the 130 B macOS allowance; enumerate every persisted-byte change. The user runs
the Darwin capability fence separately.

**No guide or certificate may call public Following history exact until the
real reader, shaping, route and SDK pass these cases.** The approved intended
wording is: each page is a correct prefix of the frozen domain; requests have
bounded work and continuation terminates when post-B backdated rows and new
follow additions stop obstructing unscanned ranges (within session lifetime,
admission and resource quotas). `Stalled` is explicit and never
a false end. Device execution and general resumable queries remain deferred.

### 9.9 Round 2 discovery ruling (approved 2026-10-07)

The author-delegated decision closes Round 1 finding R3: continuous post-B
follow additions obstructing roster discovery use the same `stalled` phase as
backdated post-B births. Discovery checkpoints its actor key, never claims an
end and never reports `preparing` indefinitely for this obstruction. Once the
additions stop, continuation terminates against the frozen oracle. Only the
viewer's own follows can extend this range. No new follow joins the frozen
domain, and no follow cap is introduced.


### 9.10 Round 2 transport, projection and SDK

`POST /following/<operation>` accepts authenticated `open`, `unit`, `refresh`
and `cancel` actions. It checks identity before its 64 KiB body allowance and
rechecks the bearer under the source engine lock. Unit responses are the stored
bytes, with `Cache-Control: private, no-store`; no fresh head, birth, epoch, work
count or frontier is appended. Existing auth/input infrastructure refusals remain
named refusals. Controller refusals are `E_FOLLOWING_INPUT`,
`E_FOLLOWING_DECLARATION`, `E_FOLLOWING_PAGE_SIZE`,
`E_FOLLOWING_REQUEST_TOO_SMALL` and `E_FOLLOWING_QUOTA`.

Bindings are derived from the existing compiler collector for a descending
Following page of 1–100 events and one-for-one scalar/object projections with
ordinary non-expiring unique point reads. General scans, maintained aggregates,
effectful/control-flow collectors and authored predicates are not admitted to
this binding. Other ordinary query programs remain usable through their existing
API; they receive no exact-history certificate. No IR/schema/program encoding is
added to identify a history reader. The emitter supplies an additive TypeScript
`FollowingQuery` descriptor and `useFollowing` consumes it.

Shaping uses the ordinary authorized point path. Its fixed reservation allows
64 examinations, 128 index entries/probes, 32,768 steps, 8 MiB temporary heap and
128 KiB card output. These are slices of unchanged request ceilings. Price JSON
object/map nodes, vector capacities, strings, witnesses and serialization before
materialization, not merely JSON length. A retained card above 1 MiB is a named
omission. A page reserves 256 KiB encoded payload and about 1 MiB staged card
custody (a fitting first card may occupy the remaining wrapper allowance); fitting
cards start a shorter next page when space runs out. Replay checks current policy
inputs and disclosed private-field owners, without reloading edited body fields.

The SDK owns one opening per hook consumer and advances only after accepting its
unit. Lost responses retry the same token; late responses fail the credential,
store/input and mutation-admission fences. Mounted cards keep internal authorized
row/field identities, never unpublished heads or birth tokens. `refresh` checks
up to 100 mounted identities per bounded request and obtains new live items from
the existing inbox path. The hook publishes the composed list only after every
batch is authorized. A nonrenewable one-second withdrawal deadline bounds a
pending remote revalidation; own-post/edge admission withdraws synchronously.
Public progress remains a phase with no work counts. SDK-held row identities are
already readable card identities; submitted witnesses can only perform ordinary
authorized point checks, and cannot access private engine tables.

New-event and post-B-follow deliveries prepend as live events, deduplicated by
engine event id (including repost identities); they never enter the frozen
historical traversal. Mounted authority loss withdraws those identities. A
revision restart clears the old list and explicitly reports `restart` before
preparing again. Offline delegates to the original inbox pager and retains its
read status, together with the device fact. The hook never evaluates author heads
on wasm or native devices and never substitutes an inbox page online.

The new certificate is a separate `followingHistory` entry in `check --json`
and a separate `Following history (useFollowing, server)` line in cost reports.
The existing `scale` certificate object and persisted inbox program do not change.
