## 2. What the current rule protects

| State | Actual mechanism | What retained sources can prove |
|---|---|---|
| Original event | `crates/snapback4-core/src/engine/timeline.rs:84–100`: event id = source post id; immutable actor/time and originals filter determine its projection | The current live event, with its original id |
| Repost event | `engine/timeline/slots.rs:16–25` mints an independent id during insertion, using `Context::mint` (`engine/mod.rs:210–216`); source id and event id are different allocations | A never-materialized source has no event id. **An existing declaration's source does retain it**, in its engine slot |
| Event consumers | `engine/timeline.rs:168–211`: delivery work names event id; inbox identity is `(reader,event,epoch)`; removals address event id; `bind/timeline.rs:165` orders and filters those copies | Reassigning an id changes list keys, equal-time order, cursor position and potentially the 1,000-event cut |
| Follow admission | `engine/timeline.rs:156–160`, `engine/timeline/online.rs:6–18`: edge epoch = transaction sequence + write ordinal, independent of source id or `.at` | Current follows prove membership, not the lifetime or admission order of that membership |
| Backfill/delivery | `engine/timeline/work.rs:61–93`: backfill copies births before the epoch; delivery copies births after it | A source timestamp cannot decide either side of the admission boundary |
| Removal/cleanup | `engine/timeline/slots.rs:78–82`, `engine/timeline/work.rs:95–132`: tombstone first, delete event, purge copies, cancel delivery, then retire tombstone; unfollow cleanup addresses only the old epoch | Current rows cannot recover deleted repost incarnations, pending copies, old edge epochs, work cursors or already-retired tombstones |

Here and below, paths abbreviated `engine/...` are under
`crates/snapback4-core/src/`; `bind/...` is under `crates/snapback4-lang/src/`.

A new follow **does backfill**: newest 50 live events synchronously, then up to
950 more, in descending `(at,eventId)` order. Later births do not consume that
history allowance. Conversely, an early follow can accumulate arbitrarily many
later deliveries; 1,000 is not an inbox eviction cap. Own copies are not capped
by this per-follow history window. The work record of a delivered event remains
with `status=done` so a future backfill can still compare its birth order
(`engine/timeline/work.rs:120–125`). Delivery alone does not make a page
incomplete; pending reader backfill/cleanup does (`engine/timeline.rs:279–283`).

For cleanup, compare never-followed with unfollowed-after-1,000-deliveries:
both have no source edge, but the latter still has old-epoch copies and queued
cleanup after its immediate 256-copy deletion. For removal, compare never
reposted with repost-deleted-before-purge: neither has the source repost, but
the latter needs a tombstone to suppress held copies and cancel old delivery.
The existing `timeline_background` tests for epochs and last-chunk purge
exercise these cases; their 17 tests and the admission-order regression pass
in the attached [baseline log](../snapback4/experiments/following-adoption/baseline-following.log).

Two executable counterexamples in
[`following_adoption_research.rs`](../snapback4/crates/snapback4-lang/tests/following_adoption_research.rs):

1. Follow, then 1,001 posts: 1,001 foreign copies after delivery. The same current
   posts/follows with follow after those posts: 1,000. Source rows alone cannot
   distinguish the histories. Refollow with a reused application edge id also
   starts a fresh engine epoch; delayed old cleanup must not delete new copies.
2. Identical visible repost source rows, supplied different event mint inputs:
   different Following ids. LLP 3000.016 slots differ too. Thus the diagnostic
   “source rows do not retain event identities” needs qualification: **existing
   declaration-specific slots do retain live identities**. For reposts it is
   accurate for a new declaration, or after retirement projected its slots away;
   originals always retain their post ids.
   Even intact live slots do not supply the missing edge/copy/work history.

The original refusal lived in `engine/timeline/activation.rs`; unchanged
declarations still skip launch, redefinition stays refused, and the withdrawn
experimental builder stays fenced. `store/timeline_launch.rs` now admits a
first-use launch. Populated profiles do not affect its source/copy count.

### Device acquisition is a separate boundary

LLP 3000.016 stays intact. Source floors are global, fixed at acquisition and
non-sliding. Each reader acquires the newest 1,000 **merged inbox copies**, not
1,000 per actor (`bind/timeline.rs:126`). Held source slots carry partial-kind
event state; fully synced kinds retain owned event rows. Edges and removal
records retain their existing audiences. A card miss or an inbox scan crossing
the acquired floor withholds the whole local answer; it does not prove absence.

For example, a device that acquired 1,000 copies and then received 500 new
copies holds 1,500; a cold device at the same server state acquires 1,000.
The source state does not identify either device's floor.

Adoption does not let a server reconstruct a device's old floor, watermark,
held delivered history or pending predictions from source rows. It need not:
adding slots already requires a new generation and reacquisition
(`crates/snapback4-core/src/successor.rs:222–225`). Fill every source slot before
publishing that generation, as required by LLP 3000.014 §7 and LLP 3000.016
§2.1a. A required post slot cannot default to false, nor an unfilled repost slot
to known absence. The proposed adoption publishes no unfinished device schema.

## 3. Launch contract

The proposed materialized program remains:

```quarry
view activity:
  posts where .parent = null and not .removed { post: .id, actor: .author, at, repost: false }
  reposts { post, actor, at, repost: true }
view following: activity where .actor = viewer or exists follows[viewer, .actor]
query home(c: cursor ?):
  return following last 20 by .at after c { *, card: posts[.post] }
```

No application replay. Use a **first-use owned and slot namespace**: catalog
numbers survive retirement, so reused owned names refuse even if empty. A fresh
name forces reacquisition; a same-name re-add beside a literal default can
preserve stale device images (`successor::keeps_literal_default_images`).

S is the committed source state when the activation acquires the writer lock;
P is its one commit. No source writer changes S between those points.

1. Preserve all public/owner/immutable/unique/non-expiry prerequisites. Orphan
   reposts and self-follows refuse; invalid input is never silently omitted.
2. Keep qualifying live originals with their post ids. Keep every retained
   repost with an existing card, including removed or filtered-out originals;
   future repost insertion still requires a live original. Mint repost identities
   from framed `(domain, fresh incarnation, declaration, source role, source id)`.
   Insert, never overwrite on collision. A retry gets a fresh incarnation.
3. Initialize retained births directly `done` at `(sequence,0)` and existing
   edges at `(sequence,1)`. Record the activation commit so future admissions
   compare strictly later. No redundant delivery work runs.
4. Each actor gets **all** their own retained events. Each existing follow gets
   exactly that actor's newest 1,000 live events in S, descending `(at,eventId)`.
   The edge window does not cap later live deliveries or own retention.
5. Fill the declaration's source slots and publish all copies with the new
   generation at P. The first page is already complete; there are no launch
   tasks or partially published pages. Future delivery/backfill/cleanup retain
   their ordinary completeness rules. Removal prunes copies and **does not refill**
   the launch window. Refollow starts the ordinary new admission window.

This is not historical equivalence. An early follower may have accumulated more
than 1,000 later deliveries; fresh launch loses that older delivered history.
New repost ids can reorder ties and change boundary membership. Launch can also
**add older events never delivered before**: follow after 2,000 posts, receive
newest 1,000, then remove those 1,000. The historical inbox is empty; launch
copies the older 1,000 still live. It also differs from a recomputed window after removal: E2…E1001 loses
E1001 and yields 999, whereas a new launch after removal can include E1 and yield
1,000. The card states pruning without refill. Current source content and membership survive, but saved feed
positions, notifications and historical reconciliation need a separate import.
Own retention and the device's merged 1,000-copy acquisition floor stay distinct.

## 4. Atomic launch adoption

**Scope and guarantees.** `store/timeline_launch.rs` constructs §3 inside the
existing `Store::activate_at_with_launch` transaction (`store/activation.rs:65`;
preflight/admission/build in `store/timeline_launch.rs:42`, `:74`, `:145`), before `event_slots::fill`,
source projection/index validation, dependent aggregate rebuild and generation
publication. One writer lock; no chunks, application fence, staging image,
reservations, manifest, roster or roster tasks. Meter pages are scratch scopes
inside that same transaction and never checkpoints. A crash before commit rolls
back slots, catalog, rows, indexes, sequence and generation; the next start
recounts and retries from scratch. Existing declarations' slots are preserved.
Ordinary later follows read the initialized done birth records normally.

**Isolation.** SQLite WAL readers retain the committed predecessor snapshot.
Candidate slot bytes are never committed separately, so predecessor queries,
snapshot pages and normalization of older log puts cannot observe them. The
commit-hook test reads all three with candidate slots already filled. The HTTP
test holds the activation immediately before commit: detached queries proceed;
sync requests and mutations wait on the ordinary serving-engine lock. A sync
then receives the generation change and reacquires; an admitted mutation executes
once on the current engine. There is no new reservation state. Existing devices'
backend adoption drops images, with native and memory-store tests for reacquisition.
An already pinned predecessor snapshot may finish after P; a new stale-engine
transaction refuses its generation identity rather than exposing candidate bytes.

**Admission and diagnostic.** Dev needs no flag. `deploy` (and rollback if it
would add a first-use feed) needs `--allow-feed-adoption`, independent of the
existing retirement `--allow-destructive` flag. `serve` only attaches to an
already committed release; it cannot implicitly adopt edited release source.
Before activation, print counts of source rows, retained events, follows,
**rows to copy**, the expected lock duration at the measured rate in §5, and the
ceiling. Without opt-in, `E_TIMELINE_ACTIVATE` includes that estimate, the flag
and this alternative: `query home(c: cursor ?): return activity where .actor =
viewer or exists follows[viewer, .actor] last 20 by .at after c` (`guide feeds`).
First-use name collisions, self-follows and orphan reposts use the same code
with the offending name/source and recovery. Invalid candidates never publish.

**Bounds and costs.** The whole activation may create at most **5,000,000 inbox
copies**, summed across new declarations. Read-only preflight counts qualifying
originals plus retained reposts by actor, then sums all own events plus
`min(1000, events(actor))` per retained edge. Its actor-count map and source
walks are metered, not unbounded row collections. A known over-ceiling copy count
refuses **before the activation transaction starts**, with the estimate and
planned-query alternative. Recheck counts under the writer lock before candidate
writes, covering a writer between preflight and lock acquisition. No ceiling or
device budget is raised. The regression observes zero SQLite writes on ceiling
refusal. A later validation or meter failure rolls the transaction back.

All retained row decoding, source-slot rewriting, copy writes and indexes use
activation meters. Construction holds at most a source page and a 32-event page;
no per-reader all-actor merge is needed because no partial feed is published.
Work and disk scale with source rows, event/birth/edge records and the sum of
copies; the transaction, WAL and device reacquisition can be expensive. Counts
predict the measured fixture's cost, not a hardware/load SLO. Large or live stores
can use planned `home` now or await the separately reviewed online design. This
explicit long-lock contract supersedes LLP 3000.019 §3.6's short adoption pause
for this opt-in operation only; detached query behavior remains unchanged.

## 8. Future: online adoption

**Unbuilt, NOT READY in both round-1 reviews.** The following records the online
design and its requirements, not the atomic implementation or its shipping gates.
It would extend §3 with a pending interval after P: actor rosters freeze the newest
1,000 foreign members and all own members in S, keeping event ids/birth tokens.
A shared server-private roster body is referenced by versioned `backfill` cursors,
never embedded in the 4,096-byte cursor. Each task binds readerId/viewerId to its
reader; own tasks have null edge epoch. New events deliver live after P without
consuming the retained window. Retire a roster only after every referencing task
finishes or is validly cancelled. Missing rosters never mean completion.

### 8.1 Fence custody and fair admission

Persist the candidate digest, predecessor generation, incarnation A, phase,
cursor, fenced tables/epochs and expected per-table live high-waters before
initialization. Bump the server store version for this manifest so an old binary
cannot ignore it. Restore must contain the entire manifest and candidate or refuse.

**Reserve each accepted client mutation id durably before waiting**, keyed by
store/principal/id and bound to operation, raw arguments, submission generation
and authority lineage. A duplicate joins that reservation; changed input refuses.
A reservation is pending, never a success receipt. After release, recheck live
authority and the current generation and claim/execute/settle under the writer
transaction; effects and outcome commit together. Crash before commit leaves the
reservation retryable; after commit, every retry returns the same outcome.
Expired/revoked authority cannot execute. Queue saturation rejects before accepting
custody, explicitly retryably; it cannot silently drop an accepted write.

Each fenced table has a durable **fence epoch**. The commit path, including jobs,
sweeps, indirect maintained-column writes, imports and every writer entry point,
refuses any commit touching it without that epoch's initializer capability.
Existing readers see predecessor semantics. The fence wait holds **neither
`shared.engine` nor a SQLite write transaction**; every chunk releases both.
An initializer's own physical writes advance the manifest's expected high-water
in the same commit. Any other live high-water change fails publication.

The current shared 32-slot `Mutation` admission class (`serve.rs:376–420`) is
insufficient. Fence waiters must release its permits and use a separately bounded
wait queue. Keep executable capacity for identity writes, ephemeral writes and
authenticated receipt/reservation replay even when that queue is full. Independent
durable presence reconnects must also get turns. Do not bypass authority to replay.
A blocked maintenance job defers its turn and yields **without waiting**,
so the same loop can advance initialization. A parked candidate must not consume
all request or maintenance capacity.

Replace `work.rs:149`'s restart-at-first-declaration selection with round-robin
across nonempty runnable declarations, remembering the last selected declaration
across invocations and recovery. With D continuously runnable declarations each
gets a bounded chunk within D successful selections. Rotate work within a
declaration too: launch, delivery and cleanup each retain turns under continuous
arrivals; parked or fenced tasks release theirs. A runnable finite roster advances
at least one examined member per granted chunk; a meter refusal parks visibly; frontier construction must itself make durable
progress before a copy can be selected (§8.4).
This bounds **turns**, not disk fsync latency. FIFO engine-lock admission alone
cannot guarantee it. Regression: continuously replenish declaration 1's delivery
while declaration 2 launches; assert the selection bound, launch completion and
continued delivery/cleanup, including restart and a parked task.

### 8.2 In-place initialization and publication

Initialize the new owned event/index/birth state and rosters in metered,
checkpointed chunks; patch **only the new slots** on existing source rows.
No application `mutate` replay, effects or other declarations' slot reminting.
Preparation writes are unlogged, or logged under private names the predecessor
cannot stream. Existing engine columns, source fields and other declarations'
slots are copied unchanged. Until P the predecessor schema projects only its own
columns; neither query/sync nor an old client may observe a half-filled slot.
Candidate owned names remain inaccessible. If that isolation cannot be proved,
do not use in-place chunking; the replacement-image alternative below remains.

The publication transaction creates one task for **every** retained edge and
an own task for every nonempty own roster, then recounts and verifies exact keyed
coverage against S: no missing, duplicate, wrong-epoch or wrong-reader task;
every event has its initialized slot and `done` birth; every required roster is
present; indexes and dependent aggregates agree. A persisted init cursor is not
this proof. A zero-task reader is complete only if the completed recount proves
zero obligations. The transaction publishes the generation, coverage record and
work together, then releases the fence. Table high-waters must equal the manifest,
or publication fails. No success can erase a receipted source write.

Task creation/recount costs O(F + U), for F retained edges and U readers with
own events, not a constant-time swap. Use the existing
metered activation walk, charging every examined/written row and index; do not
replace it with unmetered SQL or raise ceilings. Its transaction and recovery
pause must be measured. If it cannot meet the pause requirement, a reviewed
atomic publication of prebuilt task coverage is needed; discovering tasks after
publication is not an acceptable shortcut.

Every read of a reader's Feed depends on launch coverage and that reader's work,
including point misses, `byReaderActor`, other indexes, scans, joins and folds,
on server and device. The check cannot be restricted to `Cut::Cap` or the two
paved indexes (`engine/timeline.rs:279–283`). Partial pages stay `complete:false`;
absence/probes without a sound partial result withhold instead of proving absence.
Writes cannot use unfinished absence as authority. Pending metadata has the
reader's private audience, participates in invalidation and survives device sync;
unknown metadata withholds. Only schemas using launch require device support for
this expanded pending check; older devices refuse that schema until upgraded.
Ordinary feeds gain no enum/schema change merely from installing the new binary.
Before P, new/changed dependent queries answer `loading:true, complete:false`,
including a replaced `home`; unrelated predecessor
queries and sync use detached WAL readers. At P replace reader factories,
invalidate obsolete loans and force source reacquisition through new slot names.

Crash before P restores predecessor plus fence/cursor and resumes; explicit
cancellation removes only candidate slots/state before releasing its fence.
Crash after P resumes work. Parked work keeps its reader pending; cancellation
cannot masquerade as completion. Serialize competing adoptions; compatible
successors preserve published work. Keep store identity, receipts, monotone
sequences and `synchronous=FULL`. Do not promise shorter `/changes` waits without
the signed-in test: LLP 3000.019 §3.6 records the existing stall.

Device regression: acquire halfway through a reader's multi-actor roster, with
at least 1,000 copies, tied times and a quiet actor. Interleave removal, live
births, refollow and a crash. At every read the device must either retain the
work/pending witness or hold **every surviving roster copy above its fixed floor**
when claiming complete. Below-floor pages still withhold. Deleting work cannot
race ahead of its copies in snapshot/stream application.

### 8.3 What the simpler design saves and still costs

`online.rs:10–18` and `work.rs:61–93,127–172` already handle ordinary concurrent
writes safely: admission tokens divide live delivery from backfill, a chunk
rechecks the edge and commits cursor/copies atomically, and removals/unfollows
cannot change mid-transaction. No long application fence is needed for copying
**after** P. But unmodified backfill scans live `byActorTime`: continuous new
backdated births can remain ahead of its cursor, get skipped without spending
`remaining`, and prevent completion. It can refill after removals too. A separate frozen-roster walker with the skip/advance rules in §8.4 is required;
calling the unchanged task alone does not.

Slot fill is real O(posts + reposts) work, including filtered-out originals. Today's
`store/event_slots.rs:23–49` walks every source row, looks up its owned event,
decodes and rewrites its whole serialized image, charges scratch/writes, and
logs nothing. There is no constant-time lazy default: a missing required slot
cannot mean false. A new feed additionally needs event indexes, retained birth
records, edge enumeration and finite rosters. The atomic measurements do not qualify the online roster preparation
or publication pause. Own and foreign **copies** can move after P; event identity and slots
cannot. Slot fill can be chunked durably only behind the fence, with manifest
progress and predecessor-column isolation; today's single activation transaction
is not resumable chunking. Concurrent writes through partially filled slots
would need a new snapshot/delta protocol, not just shorter transactions.

**The round-1 in-place recommendation is deferred.** It removes
a replacement copy of source images/indexes and catalog-map swapping. Compared
with round 0 it loses immediate retained own copies at P and cheap cancellation
(discarding a private image); in-place cancellation must clean candidate slots.
It keeps a finite launch window but still pauses source writers for the full
initialization. Space is O(posts + reposts + follows + sum_edges min(1000, events(actor))),
plus ordinary indexes/logs and uncapped own copies. It makes no short-pause claim.

If predecessor-column isolation rules it out, corrected round-0 staging must
follow §§8.1–8.2 too: private unlogged replacement tables, other slots preserved,
no `mutate` replay, exact task creation/recount and live table high-water comparison
**in the swap transaction**, then deferred reclamation after WAL readers release.
A slipped removal after S must fail the swap, never install its old row over a
success receipt. That alternative buys source isolation and cheap discard at the
cost of extra disk, catalog custody and recovery cases. Neither publisher exists.

### 8.4 Additional round-1 requirements (both full reviews retained)

- **Merge progress (Astra High).** 16,385 heads exceed the 16,384-examination
  chunk. Persist metered head-discovery/frontier progress, then advance the
  newest head (including own events) and update the frontier atomically. Turns
  can construct the frontier without copying. Aggregate follow count cannot
  park a finite launch forever. Reads must cost O(page), not O(follows).
- **Reservation across generations (Grok High).** A queued mutation executes
  once against the newly live engine and fills its slots. Generation mismatch
  is not a terminal `_ops` refusal: the same id must remain retryable/joinable.
  Only a real application/authority refusal is terminal. Crash/retry tests
  prove one outcome and effect on both sides of publication.
- **Committed slot isolation (both).** Current `public_image` and `project_fields`
  do not strip candidate fields absent from the predecessor schema. Before any
  chunk commits, explicitly remove candidate slots before query pricing/results,
  snapshots and normalization of an older log put; test cancellation too. If
  this cannot be proved, use replacement images rather than in-place chunks.
- **Frozen walker (Grok High).** A roster cursor must branch on its version
  **before** hex/key decoding. It is not a `byActorTime` continuation. Removed
  members, changed birth tokens and changed edge epochs skip and advance in the
  same commit; they cannot park `FEED_EVENT_REMOVED` forever. Only missing or
  corrupt roster state/meter cuts park. Unfollow cancels only the old epoch.
- **Unlogged writes (Grok).** `_commits`/partition sequence is not a table
  high-water. A per-table counter must advance with every `Tx::put/delete` and
  raw row UPDATE/DELETE, including initializer writes. Reservation rows are
  outside those tables. Publication validates these counters, not log sequence.
- **First useful page (Grok).** Hash-ordered task draining can copy 1,000 old
  foreign events before the reader's newest own event. Select the newest
  persisted roster head per reader turn; keep prefix withholding as a backstop.
  Bound hot-actor retained-own time to first useful page and completion. Do not
  call `timeline_follow` in publication and add 50 live copies per edge there.
- **Device schema and fairness.** Roster bodies are private server rows for the
  new declaration, never a new Work column/kind/type or a suffix added to all
  old declarations. Keep the declaration scheduler cursor durable across
  restart so a crash loop cannot starve declaration 2.
- **Whole publication cost (Astra).** Task insertion O(F+U) excludes verification
  of every source/event/slot/birth, index, roster and dependent aggregate. Name
  and measure every traversed population; any durable preparation proof checked
  at publication must cover all of them. A cursor alone is insufficient.

### 8.5 Online gates proposed by the reviewers

Astra's gate is **at most five seconds of normal-operation fence in every
measured supported fixture and offered-load case, including publication**.
Fix hardware/load/scale before measurement; count admission refusals/timeouts,
and require accepted queues to drain under load sustained by the no-adoption
control. Lost writes, duplicate effects, false completeness and stale above-floor
device images have zero tolerance. Failure means redesign online preparation
and short drain/publication; never relax the threshold after observing results.

Also retain Grok's proposed bars: whole publication writer lock ≤1 s (worst of
three); skewed 1× queued mutation p99 ≤2 s, max ≤5 s; 10× p99 >5 s rejects the
fence; signed-in query/sync p99 ≤max(2 s, twice control); unrelated declarations'
oldest-work age within one round-robin cycle of control; one outcome/effect in
the crash matrix. These are unqualified future online gates, not acceptance bars
for §4's explicitly long atomic launch. The skew/load/recovery plan in §5 still
applies to any future online implementation.
