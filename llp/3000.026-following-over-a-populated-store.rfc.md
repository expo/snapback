## 1. Finding

The empty-source rule prevents an invented **history**, not an unauthorized
projection. For a first declaration, its old event ids and edge epochs never
existed; adoption need not pretend to restore them. A new Following view can
soundly start from retained public sources
if adoption means **start this view now**: own copies of all retained live events,
and the newest 1,000 per followed actor at the adoption boundary. With no
intervening changes this is exactly a new follow's completed backfill. It cannot
promise the inbox of a view declared from the start. Recommend this semantics
for a genuinely new declaration, while retaining the redefinition and incomplete
restore refusals. The code changes needed for crash-resumable, staged activation
are larger than deleting the refusal; the branch contains a construction probe,
not a production implementation.

## 2. What the current rule protects

| State | Actual mechanism | What retained sources can prove |
|---|---|---|
| Original event | `crates/snapback4-core/src/engine/timeline.rs:84–100`: event id = source post id; immutable actor/time and originals filter determine its projection | The current live event, with its original id |
| Repost event | `engine/timeline/slots.rs:16–25` mints an independent id during insertion, using `Context::mint` (`engine/mod.rs:210–216`); source id and event id are different allocations | A never-materialized source has no event id. **An existing declaration's source does retain it**, in its engine slot |
| Event consumers | `engine/timeline.rs:168–211`: delivery work names event id; inbox identity is `(reader,event,epoch)`; removals address event id; `bind/timeline.rs:165` orders and filters those copies | Reassigning an id changes list keys, equal-time order, cursor position and potentially the 1,000-event cut |
| Follow admission | `engine/timeline.rs:156–160`, `engine/timeline/online.rs:6–18`: edge epoch = transaction sequence + write ordinal, independent of source id or `.at` | Current follows prove membership, not the lifetime or admission order of that membership |
| Backfill/delivery | `engine/timeline/work.rs:61–93`: backfill copies births before the epoch; delivery copies births after it | A source timestamp cannot decide either side of the admission boundary |
| Removal/cleanup | `engine/timeline/slots.rs:78–82`, `engine/timeline/work.rs:95–132`: tombstone first, delete event, purge copies, cancel delivery, then retire tombstone; unfollow cleanup addresses only the old epoch | Current rows cannot recover deleted repost incarnations, pending copies, old edge epochs, work cursors or already-retired tombstones |

Here and below, paths abbreviated `engine/...` are under
`crates/snapback4-core/src/`; `bind/...` is under `crates/snapback4-lang/src/`.

A new follow **does backfill**: newest 50 live events synchronously, then up to
950 more, in descending `(at,eventId)` order. Later births do not consume that
history allowance. Conversely, an early follow can accumulate arbitrarily many
later deliveries; 1,000 is not an inbox eviction cap. Own copies are not capped
by this per-follow history window. The work record of a delivered event remains
with `status=done` so a future backfill can still compare its birth order
(`engine/timeline/work.rs:120–125`). Delivery alone does not make a page
incomplete; pending reader backfill/cleanup does (`engine/timeline.rs:279–283`).

For cleanup, compare never-followed with unfollowed-after-1,000-deliveries:
both have no source edge, but the latter still has old-epoch copies and queued
cleanup after its immediate 256-copy deletion. For removal, compare never
reposted with repost-deleted-before-purge: neither has the source repost, but
the latter needs a tombstone to suppress held copies and cancel old delivery.
The existing `timeline_background` tests for epochs and last-chunk purge
exercise these cases; their 17 tests and the admission-order regression pass
in the attached [baseline log](../snapback4/experiments/following-adoption/baseline-following.log).

Two executable counterexamples in
[`following_adoption_research.rs`](../snapback4/crates/snapback4-lang/tests/following_adoption_research.rs):

1. Follow, then 1,001 posts: 1,001 foreign copies after delivery. The same current
   posts/follows with follow after those posts: 1,000. Source rows alone cannot
   distinguish the histories. Refollow with a reused application edge id also
   starts a fresh engine epoch; delayed old cleanup must not delete new copies.
2. Identical visible repost source rows, supplied different event mint inputs:
   different Following ids. LLP 3000.016 slots differ too. Thus the diagnostic
   “source rows do not retain event identities” needs qualification: **existing
   declaration-specific slots do retain live identities**. It is accurate for
   a newly added declaration, or after retirement has projected its slots away.
   Even intact live slots do not supply the missing edge/copy/work history.

The refusal is at `engine/timeline/activation.rs:44–57`; unchanged declarations
are skipped. Redefinition remains refused at lines 34–37, and the withdrawn
experimental builder is explicitly fenced at lines 14–25. Populated profiles
are irrelevant: only the three mapped source tables are checked.

### Device acquisition is a separate boundary

LLP 3000.016 stays intact. Source floors are global, fixed at acquisition and
non-sliding. Each reader acquires the newest 1,000 **merged inbox copies**, not
1,000 per actor (`bind/timeline.rs:126`). Held source slots carry partial-kind
event state; fully synced kinds retain owned event rows. Edges and removal
records retain their existing audiences. A card miss or an inbox scan crossing
the acquired floor withholds the whole local answer; it does not prove absence.

For example, a device that acquired 1,000 copies and then received 500 new
copies holds 1,500; a cold device at the same server state acquires 1,000.
The source state does not identify either device's floor.

Adoption does not let a server reconstruct a device's old floor, watermark,
held delivered history or pending predictions from source rows. It need not:
adding slots already requires a new generation and reacquisition
(`crates/snapback4-core/src/successor.rs:222–225`). Fill every source slot before
publishing that generation, as required by LLP 3000.014 §7 and LLP 3000.016
§2.1a. A required post slot cannot default to false, nor an unfilled repost slot
to known absence. The proposed adoption publishes no unfinished device schema.

## 3. Proposed semantics: first materialization at a fresh epoch

The builder adds the same program to a populated product:

```quarry
view activity:
  posts where .parent = null and not .removed { post: .id, actor: .author, at, repost: false }
  reposts { post, actor, at, repost: true }
view following: activity where .actor = viewer or exists follows[viewer, .actor]
query home(c: cursor ?):
  return following last 20 by .at after c { *, card: posts[.post] }
```

No author-written replay, resource cap or special deployment spelling. `check`
and the feeds card must say what first materialization means. It is a new
view, not a restoration of any prior incarnation. Restrict this populated-store
path to a first-use owned namespace; a conservative proof is that none of its
owned catalog names existed before staging (catalog numbers survive retirement).
Same-name redefinition and populated re-addition of a retired namespace continue
to refuse. To intentionally launch a different feed over retained sources,
choose a fresh view name, which also gives it fresh slot names and a mandatory
device reacquisition. A re-added feed beside a literal-default addition can pass the existing
image-preservation check on an offline device that missed retirement; the
probe contrasts this with a fresh slot namespace. Retirement remains destructive and requires
its existing deploy flag. The consumer is
`crates/snapback4-device/src/device.rs:567–586`; its public-table check at line
381 compares names, not incarnation identities.

Define a finite source state S at a durable adoption fence A:

1. Check the current public/owner/immutability/unique-key/non-expiry prerequisites
   unchanged. Refuse owned-name collisions. Preflight all retained repost targets
   and self-follow edges before publication. A repost needs a retained original
   card; an already-removed card or one excluded from the originals branch is
   allowed. The retained reposts branch is unfiltered in the authored union.
   A missing card or self-follow requires reconciliation, not silent omission.
2. Create an event for each qualifying, unremoved original. Keep its source id.
   Create an independent event for each retained repost, including a repost of
   an original subsequently removed or a reply excluded from the originals
   branch. This grandfathers retained state; future repost insertion still
   requires a live original under the existing rule. Preserve source actor/time/reference and
   the original's author. Do not replay the ordinary repost operation: that
   operation requires a *currently live* original (`engine/timeline.rs:123–127`).
3. For these new repost events, derive an id from a framed tuple
   `(domain, durable adoption incarnation A, declaration, source role, source id)`.
   Persist A before work; retries use the same id. Check collisions through the
   ordinary unique insertion path and refuse instead of overwriting. A hash
   domain alone does not prevent a supplied original id from equalizing the
   chosen string. Later ordinary reposts continue to mint fresh ids.
4. Give each retained event a durable birth token before every adopted edge
   epoch, with a `done` delivery record retaining that token. Give every current
   non-self edge an epoch at A. The concrete ordinal encodings may differ, but
   all retained births must precede all adopted epochs, and all post-publication
   births/edges must follow them. A reserved `(A,0)` birth and `(A,1)` edge
   token suffice; edge identity still includes the reader/actor pair. Preserve
   the engine sequence high-water mark.
5. Make every actor's own copies. Freeze one shared roster per actor containing
   its newest 1,000 live event identities in S, ordered as ordinary backfill.
   Queue one adoption-backfill task per retained edge, bound to that edge's A
   epoch and this roster. Foreign copies may be made **after publication**.
   Own copies are not capped, and new delivery never trims the inbox. There are
   initially no old cleanup tasks or old-view tombstones to replay.
6. Fill all declaration/role-specific source slots. Publish once source images,
   events, own copies, edges, rosters and queued work are complete and their
   indexes/aggregates agree. Preserve other declarations' slots and owned state.
   Each affected reader stays `complete: false` through their ordinary Work
   dependency until their adoption tasks finish. Normal source writes resume
   at publication; ordinary new follows keep their existing backfill contract.
7. A task advances only through its frozen roster. Before copying, require the
   current edge's A epoch, a live current event with the frozen birth token,
   and the usual removal check, in the copy transaction. Removal prunes this
   fixed launch window; it does not refill from older-than-window events.
   A deleted/recreated repost with a reused event id has a later birth and is
   skipped. Unfollow/refollow cancels the old epoch's work. Delete completed
   tasks, then retire the shared roster only when none can still use it.

The observable loss relative to a hypothetical view declared from the start is
precise: an existing long-time follower can have fewer than that hypothetical
inbox's copies older than the newest 1,000; new repost ids can reorder tied times
and change membership at that cut; unfinished historical delivery may instead
be supplied by adoption backfill. No current source content or current
follow is lost. An already-following reader could notice the older history
missing, and an app requiring historical notification delivery would care.
For a newly introduced social feed this is a reasonable launch contract, not a
historical equivalence claim. The supervisor must accept that product judgment.

## 4. Background execution and publication

Use two phases: a resumable initialization with LLP 3000.019's writer fence,
then published, metered adoption backfill alongside ordinary writes. This
avoids pausing mutations for the dominant foreign-copy phase. Fully concurrent
source writes during initialization remain outside this first increment; the
probe does not measure the integrated initialization pause.

- Persist one candidate manifest: adoption incarnation, predecessor generation,
  candidate schema/program digest, frozen source boundary, phase, cursor and
  private staging catalog. Persist a new server store-format version with the
  manifest: old binaries must refuse rather than ignore a pending writer fence
  (`crates/snapback4-core/src/store.rs:99,258`). A trusted restore must include
  the whole candidate and its manifest, or reject it. Freeze application durable mutations before fixing
  S; submitted writes use bounded admission and wait without a success receipt.
  Recheck authority when they execute. Do not hold the serving mutex or a SQLite
  write transaction while waiting. Permit durable identity/presence writes and
  genuinely independent maintenance between chunks; otherwise signed-in
  `/changes` repeats the known 0.4.4 stall. The fence also covers jobs/sweeps
  that could change application rows being staged, including indirect
  maintained-column writes; allowing such a writer would lose its changes.
- Build private physical tables/indexes for the new events, own copies, edges,
  queued work, shared frozen rosters and replacement images of affected sources,
  under job meters and the existing fair work scheduler. The replacement source
  rows contain filled slots. The roster is server-private adoption metadata,
  at most one entry per retained event, not a per-edge copy of the corpus. Each chunk
  commits its cursor with its writes under WAL `synchronous=FULL`; no meter or
  authorization override is introduced. Do not run arbitrary application
  mutations, effects or maintained side effects again to reconstruct a row.
- Keep the predecessor's source/catalog rows active throughout. Existing query
  and sync snapshots use the detached reader factory. A new or changed query
  depending on the pending view returns the established pending response:
  `loading: true, complete: false`, no data or continuation. A reader with no
  discovered edge task is still pending. Neither an empty inbox nor a missing
  control row proves completion. Unchanged operations keep their old meaning;
  do not answer a replaced `home` with its former Global-feed program.
- Swap the affected physical catalog mappings and generation metadata in one
  short transaction after validation. Do **not** rewrite N source slots or copy
  N staged rows at publication: stage replacement physical tables instead.
  Staging names cannot be application-readable, exported by sync, or confused
  with occupied owned names. Keep the store identity, existing log/receipt
  lineage and monotone sequence. Invalidate obsolete reader loans, replace the
  backend reader factory, and reacquire through the existing generation path.
  Release the application writer fence in this same durable publication.
  Reclaim old physical rows later; readers already in WAL snapshots remain valid.
- After publication, adoption tasks use the existing copy, authorization,
  metering, epoch and tombstone primitives, with a **frozen roster walk** rather
  than the ordinary backfill's live-event scan. This needs a server work kind;
  its `readerId` and `viewerId` both name the affected reader, so the work
  row participates in the existing completeness probe and private device sync.
  Extend the generated Work kind enum; device acquisition and read algorithms
  still use the same rows and pending predicate. Cursor and copies commit together. A later live birth
  is delivered normally and cannot consume or extend the launch roster. Reads
  can return partial inbox data while the affected reader's task remains.
- Before publication, process death restores the predecessor, persisted writer
  fence and candidate cursor before accepting mutations. Resume committed work.
  Invalid input or meter refusal parks with a reason; old reads keep working.
  Explicit cancellation discards this unpublished candidate and releases its
  fence. After publication, ordinary durable work recovery applies: a parked
  adoption task keeps its reader incomplete, and cannot be discarded as though
  it had finished. Retirement retains its existing destructive-operation rules.
  A competing adoption must first finish or cancel an unpublished candidate;
  published adoption work must survive compatible schema changes.

This needs a staged catalog implementation; the current `Store::activate_at`
uses one transaction (`crates/snapback4-core/src/store/activation.rs:78–145`).
Simply yielding its loop does not make progress durable. The prototype below
does **not** implement the catalog swap, writer admission, HTTP pending-query
routing or device handoff. Do not claim this complete design is measured or
ready to ship. Existing two-connection reads are evidence for the mechanism,
not proof of every HTTP path; §3.6 explicitly still records `/changes` waiting.

Initialization is finite because S is frozen; later copy work is finite because
its roster is frozen, even under continuous backdated inserts. Space is
`O(P + R + F + sum_edges min(1000, live_events(actor)))`, plus own copies,
replacement source images/indexes, a shared roster no larger than P + R, and
the existing log/metadata costs. Peak
worker heap is a chunk, not that total. A queue chasing continuously appended
source ids has no such termination proof. Even the ordinary backfill scan can
keep encountering later, backdated births that it skips without spending its
remaining-copy allowance. The frozen roster prevents that adoption-specific
starvation. Fully online initialization still needs a separate finite snapshot
and metered delta protocol; it is not hidden in the word “background.”

## 5. Prototype and measurements

The branch-only [probe](../snapback4/crates/snapback4-lang/tests/following_adoption_research.rs)
settles the historical counterexamples, the actual planned-read fallback and
the construction cost of the existing metered copy machinery. It changes no
production source, schema format, client contract or ceiling.

It builds a retained-source SQLite store without Following, then constructs a
separate candidate through real engine transitions. A private progress row
commits with each source batch; the existing worker drains delivery/backfill.
Retained repost ids use the proposed adoption-key derivation. Its reader facade
forces `complete=false` until global construction completes. An actual child
process exits without destructors after a committed chunk; reopening finds
both the cursor and its events and resumes without duplicate insertion.
The benchmark also reopens once mid-build and retains concurrent detached WAL
readers. This is a construction measurement, **not end-to-end adoption**. It keeps
sources frozen through all foreign copies and uses ordinary follow previews,
not the proposed early publication or frozen-roster worker. The shared roster
would add bounded initialization work; the measured foreign-copy phase could
then run with application writes admitted.

Release-profile construction results (single samples on the shared host):

| Measurement | 1× | 10× |
|---|---:|---:|
| Wall time, seconds | 127.835 | 1,699.416 |
| Logical rows written | 557,886 | 5,579,689 |
| Final inbox copies | 340,697 | 3,407,033 |
| Observed Rust heap peak, MiB (estimate) | 1.306 | 4.780 |
| Process peak RSS, MiB | 17.250 | 21.000 |
| Candidate read p95 / max, ms | 1.783 / 13.787 | 1.953 / 19.494 |
| Source read p95 before / during, ms | 0.147 / 0.460 | 0.088 / 0.488 |

Exact counters, phases, read sample counts and reproduction are in
[the experiment record](../snapback4/experiments/following-adoption/README.md).
The fixture has 48,000 public original posts (200-byte bodies), 1,000 reposts,
6,000 follows and 1,008 distinct principals; 10× scales all four populations.
It is count-shaped like calibration #22, not its full application database:
no replies, removed originals, attachments, profiles, hot-author distribution
or concurrent application writes. Every actor has fewer than 1,000 events.
The 1,001-event counterexample separately exercises the history cutoff.

The probe includes source copying, indexes, partition logs, durable commits,
checkpoint writes and completion of the existing event tasks. A production
adopter could write retained birth records directly as `done`, avoiding the
probe's redundant delivery walks. It also needs validation and atomic generation
publication absent here. These opposing differences preclude labeling the
number an upper or lower bound on integrated adoption. SQLite C allocations
are outside the Rust allocator peak; the record reports process RSS separately.
A subsequently corrected concurrent-realloc counter makes the recorded Rust
peaks observational estimates, not exact high-water bounds; RSS is independent.
Heap growth includes the retained read-timing samples (11,182 versus 145,210);
it is not all worker state. No HTTP, wasm or device acquisition latency claim
follows from these numbers. The full 10× process took 1,856.17 seconds including
setup and post-timer size queries; the table isolates construction. Four research
tests pass, with the crash child and benchmark deliberately ignored by the
default invocation; both benchmark sizes were executed separately.

## 6. The existing planned alternative and rejected options

The current package already accepts this **query**, over retained sources:

```quarry
query home(c: cursor ?):
  return activity where .actor = viewer or exists follows[viewer, .actor] last 20 by .at after c
```

The single-line `view following: activity where ...` is parsed as a feed
(`crates/snapback4-lang/src/parser/views.rs:13–19`); a read predicate on the
planned union instead reaches its sources (`bind/intent_views.rs:81–99`). It
needs no event adoption. Its ids are source ids distinguished by branch, and it
has current-membership semantics over all retained history, no materialized
history window or independent delivered-copy history.

The feeds card mentions “a planned view” at lines 230 and 248 without showing
this program. Its main example at lines 34–92 directs the builder to the
materialized form. The calibration diary confirms the builder followed those
instructions. **Cheapest immediate improvement:** show the concrete query and
its tradeoff next to the refusal; qualify the statement about event slots.
This fixes a hidden option, but cannot make sparse, large feeds equivalent.

| Rejected option | Counterexample / reason |
|---|---|
| Delete the empty-source check and claim historical reconstruction | Identical current sources yield 1,001 versus 1,000 copies depending on follow admission; ordinary repost sources can have different minted event ids (§2) |
| Infer admission from source `.at`, source ids or current edge ids | Two writes can have equal or backdated times; delete/refollow can reuse its application id. Delayed delivery then crosses the history boundary or old cleanup deletes new copies. Admission uses commit order for this reason |
| Hash only the repost source id, and reuse it across adoption incarnations | Delete/recreate or retire/re-add the same source identity: stale tombstones, old saved ids or old work can name the new event. Use a durable adoption incarnation; ordinary later reposts still mint ids |
| Replay today's ordinary post/repost mutations as the general importer | A retained independent repost of a removed original is valid existing state, but ordinary repost insertion refuses it. Replaying arbitrary application operations can also re-emit effects; the probe handles only its all-live fixture |
| Reconstruct only source events, skipping birth records or epochs | A later backfill explicitly requires each event's retained delivery admission record; a missing record parks `FEED_APP_NOT_FOUND` (`engine/timeline/work.rs:87`). Guessing birth order can make delayed delivery exceed 1,000 |
| Re-add a populated retired view beside an unrelated literal-default addition | A device that missed retirement has the same old slot names; `keeps_literal_default_images` returns true. A fresh slot namespace returns false (executable probe). Schema shape does not identify a feed incarnation |
| Copy all retained events to every current follower | An actor with 1,001 pre-adoption events gives a newly adopted edge more history than a new follow. It changes the existing contract and increases storage without a bound per edge |
| Copy only the sources' newest global 1,000 | A quiet followed author's only event can precede 1,000 unrelated posts. Device acquisition floors are not server history windows |
| Treat undiscovered readers or unfilled slots as complete/absent | The first chunk has not reached reader B's edge, or its old post. B sees a falsely complete empty inbox, or a held repost is falsely refused. Global pending and pre-publication slot filling are required |
| Chase live sources with a last-id cursor | Continual inserts ahead of the cursor can prevent termination; inserts behind it can be omitted. Deletion/reuse of a repost id changes the incarnation being copied |
| Use ordinary live backfill scans for the adoption worker | Continuous backdated inserts after A can remain ahead of its cursor; they are skipped by birth order without consuming its remaining-copy budget. A frozen launch roster gives a finite enumeration domain |
| One atomic rebuild transaction behind detached readers | Reads can work, but a crash near the end loses all build progress. It also retains the existing unbounded wait for durable presence reconnect if that path uses the writer |
| Treat the planned fallback as a full replacement | One followed old post behind 9,000 unrelated newer posts yields `unavailable=true`, `complete=false`, `next=null`: 5,764 examinations and a 16 MiB heap cut in the tested build. Bounded device sources also cannot establish the missing history |

## 7. Open questions for review

1. Is a fresh 1,000-event-per-existing-follow launch contract acceptable as the
   default for a genuinely new view, with later removals pruning its fixed
   launch roster without refilling older events? Apps requiring historical
   delivery need a separate import contract.
2. Is a writer fence for initialization acceptable? Foreign backfill should run
   after publication with writes admitted. Measure that actual split before
   deciding; the prototype's full construction time is not its write-pause time.
   If even initialization must be fully online, a snapshot/delta design is needed.
3. Accept this RFC's grandfathering of every retained repost with a retained
   card, even when that card is excluded from the originals branch? The union
   says to include it, whereas ordinary future repost insertion still refuses.
   Should orphan/self-follow inputs be reported as a table/count refusal or an
   operator reconciliation report?
4. Does the staging catalog swap preserve every store-identity, receipt,
   generation and reader-loan invariant? Require process-death tests before,
   during and after publication, two declarations sharing sources, independent
   aggregates, auth expiry while queued, signed-in `/changes`, and devices
   holding predicted posts before approval to build beyond the probe.
5. Can retained birth records be initialized directly as `done` under the same
   authority and meters, avoiding the measured redundant delivery walk? Obtain
   integrated and skewed-load measurements before making a latency promise.
