## 0. Evidence and the author's ruling

Every app-farm wave since 0.4.16 has asked for a browser app that writes
without the device. LLP 3000.013 §6.2 records the first waves: ten lanes in
wave 1, twelve in wave 2, twenty-one in wave 3 (twelve "fix first" votes, the
largest group), and 26–29 lanes per wave since. A bare browser
`createClient()` and a device-less `createApp` refuse every mutation with
`E_ADMISSION`, so an app with no synced table ships `webDevice()`: 2,147,888 B
of wasm (648,672 B gzip, measured on this branch's `scripts/build-wasm.sh`),
a 24 KB worker and 56.7 KB of device glue, to hold no rows.

§6.2 assessed four paths and named path 2, "a synchronous online journal with
its own replay, held to §20.4's navigation witness and §6's epoch and store
fences", as the real fix. The author ruled on 2026-10-12:

> (b) a small JS-only write journal for schemas with no synced tables — same
> at-most-once guarantee, no offline queries — as a reviewed design.

This RFC is that design. It adds no wire form, no server change and no new
web artifact. The device path (`createApp({ device: webDevice() })`) is
unchanged.

## 1. What exists, and the one gap

A device-less `createApp` already owns a durable **online intent journal**
(`app-online.ts`, `app-journal.ts`): one JSON value per (backend, account),
`storeKey("writes", url, viewer)`, kept in the app's `sessionStore`. In a
browser with `localStorageSessionStore()` that store is IndexedDB (the session
authority, `session-authority.ts`) with a localStorage mirror, and every journal
transaction runs under a Web Lock on the journal key (`storeLock`). The journal
already provides, and this RFC keeps unchanged:

- **Admission before dispatch.** An intent (id, operation, JSON arguments,
  owner, store identity) is committed before the online transport may send it
  (`ownDispatch.before` binds and marks it dispatched first).
- **Same-id replay.** Reopening replays every pending intent of this account
  with its original id; `start()` initiates the replays in recorded order and
  the journal lock admits them in that order. The server returns
  `replayed: true` for an id it already executed and never re-executes it
  (LLP 3000.007 §17; `engine/receipt.rs`). Server ids are scoped by principal.
- **Store binding.** Each intent is bound to the store identity it was
  admitted under; every mutation request carries `store_id`, and the server
  refuses a replaced store with `E_STORE_REPLACED` before execution or
  idempotency lookup. A journal that saw a replacement retires its unbound
  intents with an unknown-outcome refusal.
- **One known outcome per id** (I13), receipts without historical values (the
  journal keeps 256), retirement ids that are never admitted again, and
  damaged-record preservation.
- **Waiting before identity.** A call on an unidentified client waits in
  memory (15 s of identity I/O) before admission, as on the device
  (LLP 3000.007 §20.4, EA round 3). No intent exists before identity.

The gap is the commit. The journal transaction is asynchronous: a Web Lock,
then IndexedDB. `mutate` returns its promise before that commit, so a
same-turn navigation, a tab close or a renderer crash in that window loses the
click. Losing it never duplicates it, but "a web client never loses a click"
(LLP 3000.013 §13.3) is a stated guarantee, so a device-less browser app
refuses instead (`app.ts` `admit()`, `client.ts`'s `!dispatch.owner` refusal).

The device closes the same window with W4a's synchronous localStorage
journal (`web-journal.ts`), whose recovery admits into the device's IndexedDB
outbox. This RFC gives the online journal the same front end: a synchronous
localStorage capture whose recovery admits into the online journal.

## 2. The guarantee

For a `createApp` in a browser, without a device, whose writes this journal
admits (§3):

- **G1 — capture before return.** When `mutate` returns a promise whose
  `state` is not `"failed"`, the id, operation, arguments, account, store
  identity and session authority stamp are already in localStorage, written
  synchronously in the calling stack. (A call made before store
  identification waits in memory first, exactly as today and as on the
  device; G1 applies from the moment that wait ends.)
- **G2 — no loss across page loss.** After G1, a same-origin navigation, a
  reload, a tab close, or a renderer crash after the write reached the
  browser's storage service, leaves the intent recoverable. The next app that
  opens the same backend and account under the same session authority, in
  this tab or another, admits it into the online journal and sends it with its
  original id. The only cancellation is G5's: the session that captured it
  has ended. A record that cannot be admitted for any other reason stays in
  localStorage and is reported (§4.4).
- **G3 — at most once.** *Execution:* every send of an intent uses its
  captured id and its captured store identity, and the server executes an id
  at most once per (store, principal), answering a repeat with the stored
  receipt (`replayed: true`, no result values). This holds whatever the
  client's local state. *Admission:* while the online journal is intact, a
  localStorage record is admitted into it at most once: an IndexedDB transfer
  marker, committed in the same transaction as the admission, is consulted by
  live admission and by recovery and is dropped only by the runtime that
  removed the record (the device's rule). G3 assumes the server keeps its
  receipts; §5 lists what is outside it.
- **G4 — same replay semantics as the device path.** A recovered intent
  settles as `sent` with `replayed: true` (or the stored refusal), without
  historical result values; `write(id)`, `onWrite`, `usePendingWrites` and
  `pendingIntents` see it exactly as an intent the online journal admitted
  directly.
- **G5 — session fences.** A record is admitted only if, under the session
  lock, the IndexedDB session authority still names the capturing principal in
  the capturing epoch from the same authority source. Otherwise it is
  cancelled: a live caller receives `E_AUTH`; a recovered record from an ended
  session is cancelled and counted in a console warning. A later sign-in
  never revives it (the device's rule, LLP 3000.013 §13.3). A record from a
  different authority source is never judged by this one (§4.4).
- **G6 — refuse loudly.** If custody cannot be acquired synchronously the
  call is refused with `E_ADMISSION` in the calling stack (a fulfilled failed
  promise that also exposes `state`, `id` and `why`), with a site and a
  rewrite; nothing was admitted and nothing was sent, and retrying the same id
  after repair is allowed. (Identity-wait refusals keep their own rules,
  `E_ADMISSION_STORE`/`E_ADMISSION_TIMEOUT`, which ask for a new id.) No path
  removes a captured record without a refusal to its live caller, a recovery
  admission, or G5.

G2's limits are the device's limits, because the capture mechanism is the
same: localStorage survives navigation, close and renderer crash once the
browser's storage service has the write (Chromium's renderer forwards
`setItem` to it without waiting for a reply); it does not survive clearing
site data, and it gives no promise across an operating-system crash or power
loss before the browser flushes its storage. Private windows keep
localStorage for the life of the private session only.

## 3. Selection

`AppOptions` gains one field:

```ts
/** Browser writes without a device: journal each click in localStorage and
 * send it through the server (no offline reads, no predictions). Chosen
 * automatically when the backend syncs no table; "online" also chooses it when
 * tables sync. Requires sessionStore: localStorageSessionStore(). */
readonly writes?: "online";
```

A browser `createApp` without `device` and without `readOnly` decides, once
per signed-in scope, before it publishes `signed-in`:

1. `writes: "online"` → the journal. No extra request.
2. Otherwise the scope reads `GET /schema` once with its own bearer. A schema
   in which no table has a `sync` clause → the journal. One or more synced
   tables → **refuse writes** with `E_ADMISSION` naming the synced tables and
   both rewrites: `device: webDevice()` for offline reads and predictions, or
   `writes: "online"` to write through the server only.
3. If that read fails or answers malformed (offline, refused), the decision is
   unknown: writes refuse `E_ADMISSION` with `retryable: true` ("the backend
   has not said whether tables sync"), and each such refusal starts one new
   read (single flight). The decision is not cached across reloads;
   `writes: "online"` avoids the read entirely.

The decision binds the scope and only gates **new** captures. Recovery of
existing records (§4.4) runs whatever the decision. A schema that starts
syncing while the scope is open keeps the journal: the server stays
authoritative, and the only thing the app lacks is what it chose not to ship.

Preconditions, each refused synchronously with `E_ADMISSION` and a rewrite
when missing at the call: a session store with a synchronous reader and an
IndexedDB session authority (`localStorageSessionStore()`; the memory default
and custom asynchronous stores refuse, as on the device), and
`navigator.locks` (the journal's cross-tab serialization and runtime
liveness). `writes: "online"` together with `device` or `readOnly`, or any
other value, is a configuration error (`E_CLIENT` at `app.writes`, through
`ready`, like invalid `assets`).

Unchanged: the device path; Node and native online apps (no capture, their
existing journal); a bare browser `createClient()` (still refuses: it has no
session authority or journal; its refusal now names both `createApp` forms);
persona apps (§8).

## 4. Mechanism

### 4.1 Capture (synchronous)

`mutate` on the app's client reaches, synchronously and in order:

1. the app facade's existing synchronous session check (`app.ts` `admit()`:
   the mirror's epoch and principal, the scope's validity), now also the
   selection decision of §3;
2. `MutationIds.run` (id shape, JSON snapshot, input reuse within this
   runtime);
3. if the store is identified (the ordinary case after opening; otherwise the
   §20.4 wait runs first and the capture happens when it ends), **capture**.

Capture writes one localStorage record and returns:

```
key:   snapback4-online-admission:<hex url>:<hex authority source>:<hex principal>:<id>
value: { v: 1, key, nonce, runtime, seq, id, op, args, viewer, url, storeId,
         authority: { key, epoch, principal, source }, at }
```

The key names the authority source and principal because server ids are
scoped by principal: two accounts may use the same id, and two authority
namespaces may hold the same account. `nonce` is minted per capture; every
removal and cancellation compares the stored text with the text it wrote or
read (compare-and-remove), so cleanup never deletes another capture's record.
`runtime` names this custody lifetime (§4.5). `seq` is one more than the
largest `seq` among this backend's records and this runtime's last capture.
`authority` is the stamp the device journal records (`AdmissionAuthority`:
session key, epoch, principal, authority source).

If a record already exists at the key (an explicit id reused across tabs, or
a same-id retry of a capture still waiting for its commit): the same operation
and arguments reuse that record, unchanged, as this call's capture; different
input refuses with `E_WRITE_ID_REUSE`; a non-executable cancellation is
replaced. Before writing, capture enforces the device journal's bounds over
this backend's records: at most 32 records, 256 KiB of UTF-8 keys and values,
and 64 KiB for one record. Any exception (`localStorage` unavailable or
throwing, `QuotaExceededError`) or bound refuses the call with `E_ADMISSION`
(G6).

Ids this runtime already holds durably in memory (intents restored from the
journal at opening, records it recovered) are not captured again; their
replays go straight to the journal. A same-id call this runtime has not seen
is captured; the admission branches of §4.2 make that harmless.

### 4.2 Admission (asynchronous, under both locks)

The existing journal transaction becomes, for a captured call:

```
storeLock(journalKey):              // Web Lock, as today
  storeLock(sessionKey):            // Web Lock on the session custody key
    if !sameAdmissionAuthority(stamp, authority, viewer): cancel record; E_AUTH
    journal = read(journalKey)      // IndexedDB, raw store
    if id in journal.captured and not pending:  E_WRITE_RECEIPT_EXPIRED
    ...the existing admission body (previous intent, receipt, retired id,
       store observation, push pending)...
    journal.captured += id          // transfer marker, same transaction
    collect markers (below)
    set(journalKey, journal)        // one IndexedDB commit, strict durability
compare-and-remove record           // after the commit
```

The authority check is the device's (`sameAdmissionAuthority`: a fresh
IndexedDB read of the session and epoch under the session lock; the mirror is
never authority). All I/O under the two locks uses the raw store and
`authority.read`, never the app's locking `sessionStore` wrapper: `storeLock`
is not reentrant. Lock order is always journal, then session; no existing
path takes the session lock and then the journal lock (session replacement,
logout, revocation and authority checks take the session lock alone, through
the app's `persist` queue, and touch no journal), so the order cannot
deadlock across tabs.

The commit sees the same branches as today: an id already pending continues
to dispatch (the server deduplicates), an id with a receipt or a retirement
id returns it. New: an id known only by its marker (its intent settled and its
receipt left the journal) returns `E_WRITE_RECEIPT_EXPIRED`, as a retired id
does. In every branch the marker is added.

**Markers.** `journal.captured` lists ids whose records may survive. A marker
is dropped only by the runtime that removed that record itself: its
compare-and-remove returned without an exception and its own `getItem` then
read `null`. That runtime drops it at its next journal transaction. A peer's
`getItem() === null` proves nothing (a Web Lock does not order Chromium's
localStorage between renderer processes, LLP 3000.013 §13.3), so absence
alone never drops a marker. Recovery removes any surviving record whose id the
journal knows and drops the marker in the same commit. Markers are capped at
1,024; beyond that the oldest is dropped (the residual case in §5).

**Commit failure.** If the commit throws (IndexedDB refused or aborted), the
record stays and the call does not fail: it resolves `pending` with the
reason "journaled in this browser; waiting for the write journal to commit".
`write(id)` and `usePendingWrites` report it pending while its record exists,
and a same-id retry joins it. The runtime marks itself stale and recovers its
own records (§4.4) before its next admission and on a backoff timer (1 s,
doubling to 60 s) until one recovery commits. A recovered id this runtime
already reserved is released from `MutationIds` before its replay, so the
replay admits and dispatches it. Its outcome reaches `onWrite` like any
other.

**Session ended.** If the authority check fails, the record is
compare-and-removed, or replaced by a non-executable cancellation if removal
fails (`{ key, cancelled: true }`), and the caller gets `E_AUTH`; the app then
rechecks its scope after the locks release, as the device path does.

### 4.3 Dispatch and settlement

Unchanged. Once admitted, the intent belongs to the online journal: dispatch
binds it to its store, the raw online client sends it with its id and
`store_id`, and settlement commits a receipt (no historical values) and
retires the pending entry. The capture adds no transport and no settlement
path.

### 4.4 Recovery

Custody construction installs a **recovery gate** before the app exposes the
signed-in client: every captured admission awaits it before taking the journal
lock. `custody.start()` (after the session commit and the `signed-in`
publication) runs recovery and then opens the gate; pausing a custody that
never started opens it too, so a waiting call reaches its own (refusing)
admission. A stale runtime (§4.2) runs the same recovery behind the same gate.

```
storeLock(journalKey):
  records = this backend's records under this scope's authority source and
            session key, valid shape, not cancelled,
            not in flight in this runtime, and, for another runtime's records,
            whose runtime lock is not held or pending (§4.5); in seq order
  storeLock(sessionKey):
    journal = read(journalKey)
    for each record:
      if the journal knows the id (pending, receipt, retired id, marker):
        compare-and-remove it; drop its marker if this removal is observed
      else if record.viewer != this account:
        if sameAdmissionAuthority(stamp, authority, record.viewer) fails: cancel
        else leave it                                      // not ours to admit
      else if sameAdmissionAuthority(stamp, authority, viewer) fails: cancel
      else if the journal's retirement ids are saturated: leave it; report
      else: push pending { owner, id, op, args, storeId: record.storeId,
                           dispatched: false }; add marker
    commit once
  compare-and-remove admitted records; drop their markers at the next commit
release this runtime's reservations of recovered ids; replay them with
client.mutate(op, args, { id }) in seq order; then open the gate
```

Partitioning by authority source and session key matters: custom
`localStorageSessionStore(mirror, namespace)` adapters are supported, and a
record captured under namespace A can still be valid there while a scope under
namespace B runs. Records of another source are never read as "ended".
Within one source, a record of another account can be cancelled by anyone:
epochs only increase and every account change advances the epoch, so a failed
stamp check never becomes true again. Authority read errors (IndexedDB
unavailable) cancel nothing; they are reported through `auth.why` and the
records wait. A saturated retirement list (4,096 ids, which already fences
every new online admission) leaves the record in place and reports it through
`auth.why` on every open, rather than cancelling it.

Ordering: recovered replays are initiated, in seq order, before the gate
opens, so their journal transactions are queued before any admission this
runtime captured after its custody was built; each replay hands its intent to
the online transport as soon as its own transaction commits. Recovered
intents therefore reach the transport before this runtime's new ones, and in
capture order among themselves. There is no ordering promise across two live
tabs, as today.

### 4.5 Many tabs

Each custody lifetime holds a Web Lock named
`snapback4-online-runtime:<runtime>` from before the client is exposed (the
custody awaits the grant) until it pauses (sign-out, account change, close,
store refusal). Recovery treats another runtime's record as live, and skips
it, while `navigator.locks.query()` lists that lock as held or pending. A
closed, crashed or reloaded tab releases its lock with the document, so its
records become adoptable by the next tab or reload that opens this backend and
account. Two live tabs never adopt each other's in-flight clicks.

All journal and recovery transactions in every tab serialize on the journal's
Web Lock, so at most one transaction can observe a record as unknown and admit
it. If a runtime pauses with a commit in flight, another runtime may adopt the
same record concurrently; the journal lock orders them, the second sees the
intent or its marker, and both dispatch paths use the same id (the server
deduplicates; the journal's existing `previous` branch keeps one pending
entry).

### 4.6 Session and epoch changes

- **Logout or account change after capture, before commit.** The commit's
  locked check fails; the record is cancelled; the caller gets `E_AUTH`. This
  is the device's rule (a logout cancels an unadmitted record).
- **Logout after commit.** The intent is in the account's online journal and
  is retained through sign-out, replaying at that account's next sign-in, as
  online intents always have (CLIENT-AND-OPERATIONS, "Online `app.mutate` …
  retains uncertain writes through restart and sign-out").
- **A stale mirror** (Chromium can show a stale localStorage mirror after
  granting a Web Lock): the synchronous check may pass and the click be
  captured; the locked IndexedDB check refuses it before admission or
  transport.
- **Rotation** keeps the epoch, so it never cancels a record.

### 4.7 Store changes

Capture records the store identity the call saw (G1 needs an identified
store). Recovery admits the intent bound to that identity; the existing
dispatch guard retires it with `E_STORE_REPLACED` (unknown outcome, never
retried automatically) if the server now has another store. A record is never
rebound.

## 5. Why at most once holds

Write K for the localStorage record, P/R/T/M for the journal's pending
intents, receipts, retirement ids and markers (one IndexedDB value, one atomic
commit), S for the server's per-store receipt table. The life of one id:
(1) K written; (2) commit {P += id, M += id}; (3) K compare-and-removed by
runtime r; (4) dispatch binds P[id] to its store; (5) the server executes once
and records S[id]; (6) settle {R += id, P −= id}; (7) r's next commit drops
M[id], only if (3) observed K gone.

- **Loss.** From (1) the intent is in K or P until (6), which requires a
  server terminal outcome. K is removed only after (2) committed, after the
  journal is found to know the id, or by G5's locked refusal. A failed commit
  keeps K and keeps the call pending; a crash at any point leaves K, P, or
  both; recovery admits K only when P/R/T/M do not know the id, and replays P.
- **Duplicate admission.** K is admitted only under the journal lock when
  P/R/T/M do not know the id, and live admission also consults M. M is added
  in the same commit that adds P and is dropped only by a runtime that itself
  saw K removed, so after (2) no copy of K is admitted again, even after R
  evicts the receipt or T saturates, unless one of the residual cases below
  holds.
- **Duplicate execution.** Every send of the id, from the live call, the
  journal's replay or a peer tab, carries the same id and the store identity
  captured at (1). The server checks the store before execution or lookup and
  executes an id at most once per (store, principal). This is the primary
  guarantee; the markers keep the client from presenting a settled id as new.
- **Residual cases (admission).** (a) A damaged online journal is preserved
  aside and replaced with an empty one, losing its markers. (b) A runtime's
  own removal is visible to it but never reaches storage (the renderer dies
  first), after which it drops M. (c) More than 1,024 markers are outstanding.
  In each, a surviving K can be admitted a second time; its send carries the
  same id to the same store and settles as `replayed`. The device journal has
  (a) and (b) too.
- **Outside G3 (execution).** A server restored from a backup keeps its store
  identity but loses every receipt recorded after the backup, so a replay of
  such an id executes again. This is true of today's online journal, which
  persists no server-head floor (the device persists one and refuses a
  regressed head on reopen). The operations guide already requires fresh
  client stores and pending outboxes after a restore ("Stopped backup and
  isolated restore"); a durable online head floor is deferred (§8).

## 6. Failure modes

| Condition | When | Result |
|---|---|---|
| `localStorage` getter or `setItem` throws (blocked storage, `QuotaExceededError`) | capture | `E_ADMISSION` in the calling stack; nothing admitted or sent; retry the same id after repair |
| 32 records, 256 KiB, or a 64 KiB record | capture | `E_ADMISSION` naming the bound |
| same id, different input, still captured | capture | `E_WRITE_ID_REUSE` |
| memory or asynchronous-only `sessionStore` | call | `E_ADMISSION` naming `localStorageSessionStore()`; construction also warns once |
| no `navigator.locks` | call | `E_ADMISSION` (no cross-tab serialization) |
| schema syncs tables, no `writes: "online"` | call | `E_ADMISSION` naming the tables and both rewrites |
| sync decision unknown (offline at opening) | call | `E_ADMISSION`, `retryable: true`; a new read starts |
| IndexedDB unavailable or failing (some private modes, quota) | sign-in | sign-in fails with `auth.why`; the signed-out client refuses writes |
| IndexedDB commit fails after capture | commit | the call stays `pending`; K stays; own recovery before the next admission and on a backoff timer; at the next open otherwise |
| record removal fails after commit | cleanup | marker kept; record never admitted again; removed by a later recovery |
| session ended between capture and commit | commit | `E_AUTH`; record cancelled; scope rechecked |
| session ended before a recovery | recovery | record cancelled; one console warning with the count |
| record under another authority source | recovery | untouched |
| authority read fails during recovery | recovery | nothing cancelled; `auth.why`; retried at the next open |
| retirement ids saturated | recovery | record kept; `auth.why` on every open |
| site data cleared, OS crash before flush | — | out of scope (G2's limits; same as the device) |

## 7. What is not supported

- **Offline reads and predictions.** Reads are the online client's: live
  queries over `/changes`, one-shots over `/q`, with its existing offline
  behavior (`loading`/`E_OFFLINE`). There is no replica, no prediction, no
  local interpreter and no `sync` behavior. A write is visible when the server
  confirms it.
- **New writes after an offline reload**, until the sync decision is known,
  unless `writes: "online"`. Admitted intents wait for the link as they do
  today.
- **Page-hide keepalive sends.** The device sends its outbox head on
  `pagehide`; this journal does not. A click recovers at the next open
  instead.
- **Personas** (§8), **custom asynchronous session stores**, and **bare
  `createClient()`** writes in a browser.

## 8. Deferred

- **Persona apps.** A device-less `createApp({ url, persona })` has no session
  store, so it has neither the online journal nor an authority stamp. It keeps
  refusing browser writes, naming the device. A persona journal would bind
  records to (url, persona) with no epoch; it is a separate, small change.
- **A durable online head floor** that refuses replay into a restored server
  (§5), for this journal and today's online journal alike.
- **Expo web.** The Expo starter selects `webDevice()` on web; an online-only
  Expo schema could omit it there too. The starter is unchanged here.
- **A cached sync decision** across offline reloads.

## 9. Testing

- **Unit (Node, a simulated window with an in-memory `Storage` and Node's Web
  Locks):** capture order and bounds; refusal on throwing and full storage;
  same-id reuse and `E_WRITE_ID_REUSE`; selection by schema (zero, some,
  unknown, explicit); markers consulted by live admission and kept when a
  peer only observes absence; a failed commit stays pending and recovers in
  its own runtime, with a same-id retry joining it; recovery admits once
  across two runtimes; other-account and other-source records; saturation
  keeps the record; the recovery gate orders recovered before new intents,
  including a click made from a `signed-in` listener; unchanged behavior with
  no window.
- **Browser (the Chromium witness, `witness/lib.mjs` `launch`):** a click
  followed by a same-turn `location.assign`, and a click followed by a reload
  while the mutation POST is held, each recover with one server execution; a
  reload after commit but before removal does not re-admit; two tabs: a live
  tab's records are never adopted, a closed tab's are adopted once; storage
  refusal (full localStorage) refuses synchronously and sends nothing; logout
  between capture and commit cancels; the page fetches no `.wasm`.
- **Fault instrumentation:** the journal's new awaits are classified in the
  delivery await census (`delivery-await-boundary.json`,
  `delivery-fault-instrument.mjs`); none of them is on the device's delivery
  path, so the census records them with this RFC's tests as their coverage.
- **Bytes:** a Vite production build of the same online-only page with and
  without `webDevice()`, recorded here.

## 10. Alternatives

- **Path 1 (journal through the session store only):** the gap itself.
- **Path 3 (lazy wasm on the first write):** defers custody past the click.
- **Path 4 (a journal-only wasm):** a second web artifact with its own budget,
  census and qualification, to do what a few hundred lines of JavaScript over
  the existing journal do.
- **Capture before identity:** withdrawn in EA round 3 (LLP 3000.007 §20.4)
  after three review rounds; this design keeps the wait.
- **Automatic selection regardless of `sync`:** an app whose schema syncs and
  forgets the device would silently lose offline reads; the author scoped the
  journal to schemas with no synced tables, with `writes: "online"` as the
  explicit choice.
