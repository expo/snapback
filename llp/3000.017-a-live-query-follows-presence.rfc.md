# LLP 3000.017: A live query follows presence

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 — presence (`connected[p]`), the server's held change polls, the clients' live-query invalidation, the presence card
**Author:** Claude Opus 5.5 (for Charlie Cheever)
**Date:** 2026-09-26
**Revised:** 2026-09-26 (revision 5: a presence answer re-runs on the server's interval, keeping its answer; the follow tokens of revisions 1–4 are deferred, §6); 2026-09-26 (revision 4: query tokens); 2026-09-26 (revision 0)
**Related:** [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) §19.1 (presence that decides effects), [LLP 3000.013](./3000.013-quarry-states-intent.rfc.md) §6 (one procedure publishes every read), [`issues/20260926-snapback4-live-presence.md`](../issues/20260926-snapback4-live-presence.md), [`snapback4/NOT-DOING.md`](../snapback4/NOT-DOING.md) ("Presence beyond the server's own polls")

## 1. The defect

`connected[p]` is the number of change polls the server holds open for `p`,
plus a 35-second grace after the last one answered. The presence card says "a
query reads it for an online mark". A live query that reads it does not follow
it, however:

- the engine records no dependency when a query reads `connected[p]`;
- the server's presence map changes on poll entry and exit and signals nothing;
- a client re-runs a watch only when a `/changes` answer names a table the
  watch read.

So an online mark refreshes only when some table the same query reads happens
to change. A supervisor probe measured it on 0.4.2 source. Alice watches
`presenceOf(bob)` (`{ online: exists connected[p], count: connected[p] }`),
and Bob opens a client and holds a watch:

| Tier | One-shot query after 3 s | Alice's live snapshot after 3 s | …after 60 s |
|---|---|---|---|
| online | `online: true`, count 1 | `online: false`, `fresh: true`, `complete: true` | `online: false` |
| web | `online: true`, count 1 | `online: false`, `fresh: true`, `complete: true` | `online: false` |

The read also reports itself fresh and complete, which contradicts §6 of LLP
3000.013. The 0.4.1 Grok comparative's builder polled `memberPresence` from the
client to work around it.

## 2. Decision

A live query that reads `connected[p]` re-runs every 5 seconds while it is
observed, keeping its answer on screen as it does. The server tells the client
to, on the answer itself: `refresh: 5000`. Presence changes without a commit, so
no change feed can name it; a short, stated refresh is the simplest thing that
keeps an online mark current and says nothing a re-run of the query would not.

So Alice's mark for Bob turns within about 5 seconds of Bob's client starting
to poll, and within about 5 seconds of his grace ending. An application writes
no polling of its own.

This moves one item off `NOT-DOING.md`'s "Presence beyond the server's own
polls": a live query of `connected[p]` is now kept current, still only from the
server's own polls. There is still no presence stream API, no last-seen
storage, no typing indicators and no multi-server presence.

## 3. Design

### 3.1 The answer asks for its refresh

In a query evaluated on a server, `Builtin::Connected` reads each principal
once per run and memoizes the count, so every read of `connected[p]` in one
answer agrees. `QueryOutcome.presence` records which principals a run read, for
the server alone. When it is not empty, the `/q/` reply carries
`refresh: <milliseconds>` (`PRESENCE_REFRESH`, 5 seconds), in both the ready
and the loading shape. The reply names no principal and no count.

A device does not know presence. Its queries that read `connected` already run
on the server, and a composed local answer carries the server's `refresh`.
Effects keep their own presence path (LLP 3000.007 §19.1).

### 3.2 The client re-runs, keeping the answer

Both clients arm one timer per watch when an answer carries `refresh`, and
re-run the watch when it fires (never sooner than 250 ms, whatever a server
asks). The online client re-runs with the answer retained: the snapshot keeps
its data, marked `fresh: false`, until the new answer replaces it, so the mark
never falls back to loading. The local tier publishes only the new answer. A
server's successful answer that carries no `refresh` stops the refresh. A
refresh that fails, is refused, or is answered from the device keeps the
interval, so it retries. Closing a watch clears its timer, and a table change
still re-runs the watch at once, as before.

### 3.3 Freshness

An answer is `fresh: true` when it arrives, as before; between refreshes it can
lag presence by up to the interval, and the docs say so. While a refresh is in
flight the kept answer reads `fresh: false`.

### 3.4 Cost

One re-run per observed presence query per 5 seconds, each under the query's
own meter, and nothing for a watch that is not observed. The server keeps no
state for it and wakes no poll. A thousand clients each watching one member
list add about 200 small queries a second.

### 3.5 What a client learns

Only what re-running its own query shows it, which the application authorized:
the refresh is the client's own `/q/` read, as its viewer, under current
authority. The interval is the same for every presence answer, so its presence
on a reply says only that the query read presence, which its code already
does.

## 4. Compatibility

- **An older client** ignores `refresh`, and behaves as before: its presence
  watches refresh when a table they read changes.
- **A newer client with an older server** receives no `refresh`, and behaves
  the same way.
- **Effects** keep their own presence semantics (LLP 3000.007 §19.1).
  Prediction eligibility is unchanged: a query that reads `connected` already
  runs on the server.

## 5. Tests and evidence

- **Server** (`serve_tests`): `a_presence_answer_asks_its_client_to_refresh`.
  An answer that reads presence, directly or through an aggregate, carries the
  interval and names no principal; one that reads none carries nothing.
- **Clients:**
  - `presence-refresh.test.mjs`, on a controlled transport: the online client
    re-runs after the named interval, never publishing loading, with the kept
    answer marked not fresh meanwhile. A plain answer never re-runs, the client
    floors the interval, and a closed watch stops. A refresh that fails, and
    one that is refused, keep the interval and retry.
  - `presence-live.test.mjs`, on the online, native and web tiers: Alice's mark
    turns true within one interval of Bob's client starting to watch, and false
    within one interval of the clock passing his grace, with no loading
    snapshot in between.
- **Docs:** the presence card; `CLIENT-AND-OPERATIONS.md`, for `refresh`;
  `NOT-DOING.md`.

## 6. Not decided here: following presence as it changes

Revisions 1 to 4 had the server follow presence for a held change poll
instead, answering within about 20 ms. Each round closed its predecessor's
defects, and each review found new ones:

- **Revision 1** sent each principal's connected bit with the answer, a
  disclosure beyond what the query showed.
- **Revision 3** replaced the bits with opaque tokens bound to the viewer. But a
  token still moved when a count the answer hid moved, outlived its viewer's
  access, and could fill memory.
- **Revision 4** made a token stand for its query and report only a changed
  answer, with a bounded table. Astra's fourth review (NOT READY) then found
  these:
  - clock-dependent answers reopened the hidden-count oracle;
  - retirement made a revocation observable at a presence change;
  - retained arguments outgrew their charge;
  - count reads and poll restarts between two clients fed each other, at 65
    polls a second.

Following presence exactly, without saying more than a re-run would, is
possible. It needs a double evaluation at one instant, delivery-latched
reports, conservative memory accounting and restart-free polling, and every
one of those is a new surface to review. For an online mark, five seconds is
enough, so this RFC ships the refresh. The token design stays recorded in
revision 4 of this document's history and in the review records
(`pl-r0` to `pl-r4`), and can return as an acceleration over the same `refresh`
fallback if a measured need appears.

Also not decided here: last-seen times, which would be storage and remain
not-doing, and presence across servers.
