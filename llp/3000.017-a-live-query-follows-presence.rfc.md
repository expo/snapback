## 1. The defect

`connected[p]` is the number of change polls the server holds open for `p`,
plus a 35-second grace after the last one answered. The presence card says "a
query reads it for an online mark". A live query that reads it does not follow
it, however:

- the engine records no dependency when a query reads `connected[p]`;
- the server's presence map changes on poll entry and exit and signals nothing;
- a client re-runs a watch only when a `/changes` answer names a table the
  watch read.

So an online mark refreshes only when some table the same query reads happens
to change. A supervisor probe measured it on 0.4.2 source. Alice watches
`presenceOf(bob)` (`{ online: exists connected[p], count: connected[p] }`),
and Bob opens a client and holds a watch:

| Tier | One-shot query after 3 s | Alice's live snapshot after 3 s | …after 60 s |
|---|---|---|---|
| online | `online: true`, count 1 | `online: false`, `fresh: true`, `complete: true` | `online: false` |
| web | `online: true`, count 1 | `online: false`, `fresh: true`, `complete: true` | `online: false` |

The read also reports itself fresh and complete, which contradicts §6 of LLP
3000.013. The 0.4.1 Grok comparative's builder polled `memberPresence` from the
client to work around it.

## 2. Decision

A live query that may read `connected[p]` re-runs 5 seconds after each of its
answers while it is observed, and the answer on screen stays until the new one
replaces it. The server tells the client to, on each reply: `refresh: 5000`.
Presence changes without a commit, so no change feed can name it; a short,
stated refresh is the simplest thing that keeps an online mark current and says
nothing a re-run of the query would not.

So Alice's mark for Bob turns about 5 seconds after Bob's client starts to
poll, and about 5 seconds after his grace ends, plus the time a query takes. An
application writes no polling of its own.

This moves one item off `NOT-DOING.md`'s "Presence beyond the server's own
polls": a live query of `connected[p]` is now kept current, still only from the
server's own polls. There is still no presence stream API, no last-seen
storage, no typing indicators and no multi-server presence.

## 3. Design

### 3.1 The query, not the run, asks for the refresh

A query may read presence when `connected[p]` appears anywhere in it or in a
helper it calls. The binder already records this as the query's `presence`
residency site (the device cannot answer such a read), and rules cannot read
`connected` at all. The `/q/` reply for such a query carries
`refresh: <milliseconds>` (`PRESENCE_REFRESH`, 5 seconds) on every answer:
ready, loading, and an authored refusal, since a refusal can depend on presence
too. Which branch a run took never decides it, so the field discloses nothing
about the data. It comes from the schema of the engine that evaluates the
query, so a schema adopted mid-request cannot pair one query with another's
answer. A reply names no principal and no count, and a query that
cannot read presence never carries the field.

In a query evaluated on a server, `Builtin::Connected` reads each principal
once per run and memoizes the count under the heap meter, so every read of
`connected[p]` in one answer agrees. A device evaluates `connected` as
unknown, so a query that reads it is answered by the server, whole or composed
with rows or fields the device retained; both composed forms carry the server's
`refresh`. Effects
keep their own presence path (LLP 3000.007 §19.1).

### 3.2 The client refreshes in the background

Both clients keep one timer per watch. When it fires, the client reads the
query in the background, as a one-shot read. What it does with the reply:

- **Overtaken.** Something else published, or another read began, while it
  ran. The reply decides nothing: neither the answer nor the timer, which the
  newer read set.
- **Accepted.** The server's reply is published whatever it says, a loading
  or a refusal included, and sets the interval, or clears it when it carries
  none.
- **Failed.** A transport failure, or an answer the device gave, keeps the
  answer on screen and the interval, and retries. A background failure says
  nothing about the link: the change feed notices a real outage on its own.

Everything else keeps its own behavior, and wins:

- a table change or an expiry re-runs the watch and withdraws the answer
  immediately, as before, and a background answer that arrives after it is
  discarded;
- on the local client, a server's answer or refusal replaces what a later
  recovery may show for its query only if it is not older. A reply below the
  highest store cut any reply for the query has named, whether that reply was
  kept or not, is older. Otherwise a later cut than the remembered one wins,
  and at the same cut, or when either reply names no cut, the read that began
  later wins. Every refetch counts anew: a retry after a store or authority
  change, a refetch after the credentials change, and an expired device answer
  re-routed to the server. A refusal names the cut its own evaluation read,
  not the head taken before it. A composed read remembers no whole answer,
  but its cleanup and its reply, refused or composed, take their place in the
  same order with the server's cut; only the cleanup of an expired answer
  forgets it outside the order. So an answer
  remembered with a cut is always at the highest cut named for its query, an
  overtaken reply never outranks the read that overtook it, and no reply
  below a cut already named replaces what recovery shows. A reply without a
  cut, such as an authentication refusal, is ordered only by its read;
- a dead session, closing the watch, and replacing the local store clear the
  timer, and on either client a read that settles after the session died arms
  none.

The client never refreshes sooner than 250 ms, nor waits longer than a timer can
hold, whatever a server asks.

### 3.3 Freshness and latency

A presence answer is a sample. It keeps the `fresh` it arrived with, `true`
for a server's whole answer and `false` for a local answer that composes
retained rows, until a newer answer replaces it. While refreshes succeed, a
change to presence shows within the rest of the read in flight when it
happened, plus the interval, plus the next read's evaluation and transport: the
timer starts when the previous read settles. Failed refreshes and a suspended
client remove that bound: the sample stays on screen, with the same freshness
flag, until a refresh succeeds. `contract.ts` says so beside
`fresh`.

### 3.4 Cost

One background read per observed presence query per 5 seconds, each under the
query's own meter, and nothing for a watch that is not observed. The server
keeps no state for it and wakes no poll. A thousand clients each watching one
member list add about 200 full evaluations of that query a second,
unstaggered.

### 3.5 What a client learns

Only what re-running its own query shows it, which the application authorized:
the refresh is the client's own `/q/` read, as its viewer, under current
authority. Whether a reply carries `refresh` depends only on the query's text,
never on the data or on which branch ran.

## 4. Compatibility

- **An older client** ignores `refresh`, and behaves as before: its presence
  watches refresh when a table they read changes.
- **A newer client with an older server** receives no `refresh`, and behaves
  the same way.
- **Effects** keep their own presence semantics (LLP 3000.007 §19.1).
  Prediction eligibility is unchanged: a query that reads `connected` already
  runs on the server.

## 5. Tests and evidence

- **Server** (`serve_tests`): `a_presence_answer_asks_its_client_to_refresh`.
  Every reply of a query that may read presence carries the interval. That
  holds directly, through an aggregate, on a branch that did not run, through
  a helper, and on a presence-controlled refusal. No reply names a principal,
  and a query that cannot read presence carries nothing.
- **Clients:**
  - `presence-refresh.test.mjs`, on a controlled transport, covers these:
    - the background refresh never publishes anything but an answer;
    - a successful answer without `refresh` stops it, and a plain answer never
      starts it;
    - a failed refresh and a refused presence query keep refreshing;
    - an invalidation during a held refresh withdraws at once, and the late
      refresh is discarded, and does not touch the newer interval;
    - an accepted loading answer is published; a background 503 keeps the
      answer on screen and the link online;
    - a background reply older than a commit the client observed is not
      published;
    - the interval is floored and clamped, and a closed watch stops.
  - `presence-local.test.mjs`, on the wasm and process devices: a failed
    background refresh keeps the answer and the link; an accepted loading
    answer or refusal is published, and a later outage's recovery never brings
    back the answer it replaced; a reply overtaken by an expiry's re-run
    changes neither the answer, the interval, nor what recovery shows; an
    accepted background reply is what recovery shows, and replaces an older
    one-shot answer that landed while it ran; an older refusal landing later
    does not erase it; it yields to a newer one-shot answer, to a newer
    deletion of an answer that was never remembered, to a refusal read at a
    later store cut, and to a read retried after its store changed.
  - `remembered-answers.test.mjs`: a reply below a cut already named loses
    through a reply without a cut, and when the reply that named the cut had
    itself lost on its read; a composed read's refusal and its own cleanup
    leave a later read's answer at the same cut, and its refusal at a later
    cut removes it; a composed answer, of retained rows or of a retained
    field, outranks an older answer that lands later; a composed read's whole
    answer is not remembered; a refusal is ordered by its evaluation's
    cut, not an older head beside it; each refetch renews the read's place.
  - `serve_tests.rs`, `a_refusal_names_the_cut_its_evaluation_read`: a commit
    between a reply's metadata and the query's own read makes the refusal's
    cut one past its head.
  - `presence-refresh.test.mjs` also holds a completed online read behind a
    barrier while the credentials end, and requires that it arm no timer.
  - `presence-live.test.mjs`, on the online, native and web tiers: Alice's mark
    turns within one interval of Bob's client starting to watch, and of the
    clock passing his grace. No notification in between carries anything but
    an answer.
  - `presence-composed.test.mjs`, on the wasm and process devices: an answer
    composed of retained history and the server's presence refreshes and turns.
    Dropping the composed copy of `refresh` fails it.
  - `read-through.test.mjs`, "an unheld parent falls back without losing
    retained rows": a query that reads `connected[viewer]` beside retained
    rows is composed row by row, and keeps refreshing. Dropping that copy of
    `refresh` fails it.
- **Docs:** the presence card; `CLIENT-AND-OPERATIONS.md`, for `refresh`;
  `NOT-DOING.md`.

## 6. Not decided here: following presence as it changes

Revisions 1 to 4 had the server follow presence for a held change poll
instead, answering within about 20 ms. Each round closed its predecessor's
defects, and each review found new ones:

- **Revision 1** sent each principal's connected bit with the answer, a
  disclosure beyond what the query showed.
- **Revision 3** replaced the bits with opaque tokens bound to the viewer. But a
  token still moved when a count the answer hid moved, outlived its viewer's
  access, and could fill memory.
- **Revision 4** made a token stand for its query and report only a changed
  answer, with a bounded table. Astra's fourth review (NOT READY) then found
  these:
  - clock-dependent answers reopened the hidden-count oracle;
  - retirement made a revocation observable at a presence change;
  - retained arguments outgrew their charge;
  - count reads and poll restarts between two clients fed each other, at 65
    polls a second.

Following presence exactly, without saying more than a re-run would, is
possible. It needs a double evaluation at one instant, delivery-latched
reports, conservative memory accounting and restart-free polling, and every
one of those is a new surface to review. For an online mark, five seconds is
enough, so this RFC ships the refresh. The token design stays recorded in
revision 4 of this document's history and in the review records
(`pl-r0` to `pl-r4`), and can return as an acceleration over the same `refresh`
fallback if a measured need appears.

Also not decided here: last-seen times, which would be storage and remain
not-doing, and presence across servers.
