# LLP 3000.017: A live query follows presence

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 — presence (`connected[p]`), the server's held change polls, the clients' live-query invalidation, the presence card
**Author:** Claude Opus 5.5 (for Charlie Cheever)
**Date:** 2026-09-26
**Revised:** 2026-09-26 (revision 0)
**Related:** [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) §19.1 (presence that decides effects), [LLP 3000.013](./3000.013-quarry-states-intent.rfc.md) §6 (one procedure publishes every read), [`issues/20260926-snapback4-live-presence.md`](../issues/20260926-snapback4-live-presence.md), [`snapback4/NOT-DOING.md`](../snapback4/NOT-DOING.md) ("Presence beyond the server's own polls")

## 1. The defect

`connected[p]` is the number of change polls the server holds open for `p`,
plus a 35-second grace after the last one answered. The presence card says "a
query reads it for an online mark". A live query that reads it does not follow
it, however:

- the engine records no dependency when a query reads `connected[p]`;
- the server's presence map changes on poll entry and exit and signals nothing;
- a client re-runs a watch only when a `/changes` answer names a table the
  watch read.

So an online mark refreshes only when some table the same query reads happens
to change. A supervisor probe measured it on 0.4.2 source. Alice watches
`presenceOf(bob)` (`{ online: exists connected[p], count: connected[p] }`),
and Bob opens a client and holds a watch:

| Tier | One-shot query after 3 s | Alice's live snapshot after 3 s | …after 60 s |
|---|---|---|---|
| online | `online: true`, count 1 | `online: false`, `fresh: true`, `complete: true` | `online: false` |
| web | `online: true`, count 1 | `online: false`, `fresh: true`, `complete: true` | `online: false` |

The read also reports itself fresh and complete, which contradicts §6 of LLP
3000.013. The 0.4.1 Grok comparative's builder polled `memberPresence` from the
client to work around it.

## 2. Decision

A live query that reads `connected[p]` follows `p`'s connected bit,
`exists connected[p]`. It re-runs within a second of `p`'s first poll, and at
the end of `p`'s grace when the last connection is gone. The count is read
along with each refresh and is not followed on its own.

This moves one item off `NOT-DOING.md`'s "Presence beyond the server's own
polls". A live query of `connected[p]` is now followed, but still only through
the server's own polls. There is still no presence stream API, no last-seen
storage, no typing indicators and no multi-server presence. The author gave
standing authorization for reworks that make queries excellent (2026-09-25:
"I'm not attached to things being the way they are now"). The process section
of `NOT-DOING.md` records the change with this LLP.

## 3. Design

### 3.1 A query answers a token for the presence it read

In a query evaluated on a server, `Builtin::Connected` reads each principal
once per run and memoizes the count. So every read of `connected[p]` in one
answer agrees, and the recorded bit matches the data.

`QueryOutcome.presence` carries principal → bit for the server alone. The
`/q/` reply returns only an opaque follow token, `presence: "<token>"`, in both
the ready and the loading shape. The bits stay on the server, bound to the
viewer.

A device does not know presence. Its outcomes carry nothing, and its queries
that read `connected` already run on the server. Effects keep their own
presence path (LLP 3000.007 §19.1) and record nothing here.

### 3.2 The poll follows those tokens

A client lists the tokens its live watches hold on its held change poll,
`follow=<token>,…`, at most 64. The server keeps only tokens its own viewer was
issued, and resolves each to the bits it recorded. It then compares every
principal's current bit with those bits, and answers at once if any differs.
While waiting, the poll also wakes in two cases:

- **A principal enters.** Poll entry that moves a principal from 0 to
  connected, outside its grace, bumps a presence generation under the change
  lock and notifies, if some held poll follows that principal. A client that
  re-polls within its grace never produces it.
- **A grace ends.** For each followed principal with no open poll but inside
  its grace, the poll sets a wake deadline at the end of that grace.

A poll reads the generation before its checks, and looks again instead of
sleeping if the generation moved. So a wake that lands between its checks and
its wait is never lost.

A presence wake answers only a poll whose own tokens moved. Every other wake,
such as a commit, answers as before. So a presence change does not end
unrelated polls, and cannot disturb absence-guarded effects.

The answer keeps the store's `seq` when only presence moved, and carries
`presence: ["<token>", …]`, the tokens that moved. A token that lapsed while
the poll waited is dropped, never reported.

A held poll sent before a watch's first answer does not follow that watch's
token. When an answer changes the follow list, the client ends its held poll
with a restart reason and polls again at once. The restart is not a lost link.
A token that moved re-runs exactly the watches holding it, and each re-run
receives a new token.

### 3.3 What is not followed

Some reads of presence cannot be followed:

- principals beyond a poll's 64;
- answers from a server older than this LLP, which report no `presence`;
- reads a device answers from memory while it is offline.

These behave as before: they refresh when a table they read changes. Marking
such an answer `fresh: false` after the 5-second confirmation window is not
implemented.

### 3.4 Cost

Every commit already wakes every held poll, and each rechecks its own store
head. Presence adds occasional wakes. An entry after an absence, of a
principal some held poll follows, notifies the same condition a commit does,
and every held poll answers. That is no worse than a commit, and it happens
only when a followed principal returns after its grace. A grace deadline wakes
only the polls that follow that principal. A steady
client re-polls inside its grace and produces neither. Rechecking a poll's
followed bits costs at most 64 map lookups under the presence lock. Per-poll
wait conditions, which would wake only the followers, are deferred until
change notification in general needs them.

### 3.5 Tokens, not principals or bits

Presence is server knowledge. A client that could name principals, or receive
their bits, could learn presence the application's queries never showed it.
For example, the bits behind `connected[bob] + connected[carol]` would show
more than the sum.

So a query answers only an opaque token. The token is bound to the viewer the
query ran for, and stands for the bits that query read. A poll's answer says
which of its tokens moved, and nothing else. The client learns a principal's
presence only by re-running its own query, which the application authorized.

A token lives 10 minutes. A client re-runs its presence-reading watches every
5 minutes, so an honest live watch never lapses. The token table holds at most
100,000 tokens; past that, lapsed tokens are pruned, and a read issues none
until room frees. A token is unique but not secret, since it resolves only for
its own viewer.

## 4. Compatibility

- **An older client** sends no `follow`. The server treats its polls as before,
  and the client ignores the additive `presence` fields.
- **A newer client with an older server** receives no `presence` field. It
  follows nothing, so it behaves as before (§3.3).
- **Effects** keep their own presence semantics (LLP 3000.007 §19.1) and add no
  dependencies. Prediction eligibility is unchanged: a query that reads
  `connected` already runs on the server.

## 5. Tests and evidence

**Server** (`serve_tests`):

- `a_held_poll_follows_the_token_its_query_issued`:
  - `/q/online` answers a token and names no principal it read;
  - a poll that follows the token waits, and Bob's first poll wakes it with
    `[token]`, while `seq` is unchanged;
  - an already-moved token answers at once;
  - a fresh read issues a fresh token, and the end of Bob's grace answers it;
  - a plain poll has no `presence` field, and no followers are counted once
    polls end.
- `a_token_follows_only_for_its_viewer_and_discloses_no_principal`: an
  aggregate over two principals answers its sum and one token. Alice's token
  in Carol's poll, and an unknown token, follow nothing. Alice's own token
  answers.
- `a_followed_grace_ends_on_its_own_deadline_and_lapsed_tokens_stay_quiet`:
  - a clock advance that leaves about 2 s of grace does not answer the poll;
    the grace's own deadline does. Deleting that deadline arm fails the test;
  - a bystander poll that follows nothing runs its own deadline;
  - a token that lapses while its poll waits is never reported.
- `follow_parses_tokens_and_stops_at_the_limit`.

**Clocks** (`clock.rs`): an open poll survives clock advances.

**Clients** (`presence-live.test.mjs`, on the online, native and web tiers):

- Alice's observed mark turns true about 20 ms after Bob's client starts
  watching.
- It turns false within about 4 s of Bob closing and the clock passing his
  grace. The server ends his held poll at its next heartbeat.
- Every such answer is `fresh: true`.

## 6. Not decided here

- A count that is followed per change. It flickers when one of several devices
  re-polls.
- Last-seen times. They would be storage, and remain not-doing.
- Presence across servers.
