# LLP 3000.017: A live query follows presence

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 — presence (`connected[p]`), the server's held change polls, the clients' live-query invalidation, the presence card
**Author:** Claude Opus 5.5 (for Charlie Cheever)
**Date:** 2026-09-26
**Revised:** 2026-09-26 (revision 4: a token stands for its query and reports only a changed answer; bounded token table; follow keeps tokens live); 2026-09-26 (revision 0)
**Related:** [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) §19.1 (presence that decides effects), [LLP 3000.013](./3000.013-quarry-states-intent.rfc.md) §6 (one procedure publishes every read), [`issues/20260926-snapback4-live-presence.md`](../issues/20260926-snapback4-live-presence.md), [`snapback4/NOT-DOING.md`](../snapback4/NOT-DOING.md) ("Presence beyond the server's own polls")

## 1. The defect

`connected[p]` is the number of change polls the server holds open for `p`,
plus a 35-second grace after the last one answered. The presence card says "a
query reads it for an online mark". A live query that reads it does not follow
it, however:

- the engine records no dependency when a query reads `connected[p]`;
- the server's presence map changes on poll entry and exit and signals nothing;
- a client re-runs a watch only when a `/changes` answer names a table the
  watch read.

So an online mark refreshes only when some table the same query reads happens
to change. A supervisor probe measured it on 0.4.2 source. Alice watches
`presenceOf(bob)` (`{ online: exists connected[p], count: connected[p] }`),
and Bob opens a client and holds a watch:

| Tier | One-shot query after 3 s | Alice's live snapshot after 3 s | …after 60 s |
|---|---|---|---|
| online | `online: true`, count 1 | `online: false`, `fresh: true`, `complete: true` | `online: false` |
| web | `online: true`, count 1 | `online: false`, `fresh: true`, `complete: true` | `online: false` |

The read also reports itself fresh and complete, which contradicts §6 of LLP
3000.013. The 0.4.1 Grok comparative's builder polled `memberPresence` from the
client to work around it.

## 2. Decision

A live query that reads `connected[p]` follows its own answer. When a
connection count it read moves, the server re-runs it for its viewer, and the
client re-runs the watch if, and only if, the published answer changed. A
count moves on `p`'s first poll after an absence, when another of `p`'s devices
connects or leaves, and when the grace after `p`'s last poll ends. An answer
that hides a count, such as `connected[p] > 1`, moves only when its own value
does.

This moves one item off `NOT-DOING.md`'s "Presence beyond the server's own
polls". A live query of `connected[p]` is now followed, but still only through
the server's own polls. There is still no presence stream API, no last-seen
storage, no typing indicators and no multi-server presence. The author gave
standing authorization for reworks that make queries excellent (2026-09-25:
"I'm not attached to things being the way they are now"). The process section
of `NOT-DOING.md` records the change with this LLP.

## 3. Design

### 3.1 A query answers a token for its own answer

In a query evaluated on a server, `Builtin::Connected` reads each principal
once per run and memoizes the count, so every read of `connected[p]` in one
answer agrees.

`QueryOutcome.presence` carries principal → count for the server alone. When
it is not empty, the `/q/` reply returns an opaque follow token,
`presence: "<token>"`, in both the ready and the loading shape. The token
stands for the query: its name, arguments and viewer, a digest of the answer
it published, and, kept on the server, the counts and tables it read and the
head it read them at. An answer the server will not follow (§3.3) carries an
empty token, `presence: ""`.

A device does not know presence. Its outcomes carry nothing, and its queries
that read `connected` already run on the server. Effects keep their own
presence path (LLP 3000.007 §19.1) and record nothing here.

### 3.2 The poll follows those tokens

A client lists the tokens its live watches hold on its held change poll,
`follow=<token>,…`, at most 64. A token its viewer was not issued, or one that
lapsed, is reported at once in the answer's `presence`, so its watch re-runs; a
foreign token reads exactly as an unknown one.

For each live token, the poll compares the counts the token read with the
counts now. When one moved, it re-runs the token's query as the token's viewer,
the way `/q/` does, and compares the digest of what it would publish. The
token is reported only if the digest differs. Either way the token's baseline
moves to the re-run, so a change is reported once, and a count its answer hides
is not looked at again until it moves again.

While waiting, the poll also wakes:

- **A count moves.** A poll entry after an absence, a second device's entry,
  or an exit that leaves another poll open, moves a principal's count. If some
  held poll follows that principal, the generation moves and polls are told,
  both under the change lock.
- **A grace ends.** For each followed principal whose only connection is its
  grace, the poll sets a wake deadline at the end of that grace.

Every wake is one more look from the top of the poll's loop: only a change seen
there answers it. A notice meant for another waiter, such as an effect worker
or an action, a late presence notice, and a spurious wake all wait again. A
poll reads the generation before its checks and looks again, rather than
sleeping, if it moved; since the notice is sent under the change lock the poll
holds until it waits, no presence change is slept through.

The answer keeps the store's `seq` when only presence moved, and carries
`presence: ["<token>", …]`. The client drops a reported token from its follow
list and re-runs each watch holding it; the re-run's answer brings the next
token. A held poll sent before a watch's first answer does not follow that
watch's token: when an answer changes the follow list, the client ends its
held poll with a restart reason and polls again at once. The restart is not a
lost link.

### 3.3 What is not followed

- An answer that read more than 1,024 principals, or whose token would take
  more than 256 KiB, gets an empty token; its watch re-runs every 30 seconds
  instead.
- Answers from a server older than this LLP report no `presence`, and reads a
  device answers from memory while offline follow nothing.

These refresh when a table they read changes, as before.

### 3.4 Cost

A re-run happens only when a count a followed token read moved, once per such
token per held poll that follows it, and each is one evaluation under the
query's own meter. A steady client re-polls inside its grace, which moves no
count. A move wakes every held poll, as a commit does, and each re-checks its
own tokens' counts: at most 64 tokens, each a few map lookups. Per-poll wait
conditions, which would wake only the followers, are deferred until change
notification in general needs them.

The token table is bounded: 100,000 tokens and 64 MiB in all, and 256 tokens
per viewer. Past a bound the least recently followed token makes room, the
viewer's own first. A token lives while a poll follows it and lapses 120
seconds after the last. An evicted or lapsed token is reported at its next
follow, and its watch re-runs for a new one.

### 3.5 A token reports only what its query would show

Presence is server knowledge. A client that could name principals, or receive
their counts, could learn presence the application's queries never showed it:
the counts behind `connected[bob] + connected[carol]` show more than the sum.
Nor may a token's report say more than its query would. So:

- **A token names nothing.** It is opaque and resolves only for its viewer.
- **A token moves only when its query's answer does.** The re-run runs as the
  viewer, and the report is one bit per token: the digest changed.
- **A token that no longer answers its viewer retires silently.** If a commit
  after the token's answer touched a table its query read, the client re-runs
  that watch for the commit anyway, and a report at a presence change could owe
  something to data. If the re-run is refused, for example because access was
  withdrawn, the token follows nothing. Either way the next follow reads it as
  lapsed.

So what a client learns from following is what re-running its own query at
that moment shows, which the application authorized.

## 4. Compatibility

- **An older client** sends no `follow`. The server treats its polls as before,
  and the client ignores the additive `presence` fields.
- **A newer client with an older server** receives no `presence` field. It
  follows nothing, so it behaves as before (§3.3).
- **Effects** keep their own presence semantics (LLP 3000.007 §19.1) and add no
  dependencies. Prediction eligibility is unchanged: a query that reads
  `connected` already runs on the server.

## 5. Tests and evidence

**Server** (`serve_tests`):

- `a_held_poll_follows_the_token_its_query_issued`: a token names no principal;
  Bob's first poll answers it with `seq` unchanged; a reported token does not
  report the same change twice; the end of Bob's grace answers a fresh token; a
  plain poll has no `presence`, and no followers remain.
- `a_token_follows_only_for_its_viewer_and_discloses_no_principal`: an
  aggregate answers its sum and one token; Alice's token in Carol's poll and an
  unknown token both read as lapsed, at once.
- `a_token_reports_only_a_changed_answer`: `connected[p] > 1` stays quiet at
  Bob's first connection, reports at his second, and reports again when one of
  the two ends.
- `a_token_retires_when_its_query_stops_answering_its_viewer`: withdrawn
  access, a data change behind the answer, and a refused re-run each report
  nothing at the presence change, and the token then reads as lapsed.
- `the_token_table_keeps_its_bounds`: the per-viewer and byte bounds evict the
  least recently followed token; idle tokens lapse; an answer that read too
  many principals gets an empty token.
- `a_notice_without_a_change_does_not_end_a_poll`: notices for other waiters
  and presence notices for unfollowed principals leave a bystander waiting.
- `a_presence_change_before_the_wait_is_not_slept_through`: a connection
  between a poll's look and its wait is answered at once.
- `a_followed_grace_ends_on_its_own_deadline_and_lapsed_tokens_stay_quiet`:
  the grace's own deadline answers; a bystander runs its deadline; a token that
  lapses mid-wait is never reported, and reads as lapsed at the next poll.
- `follow_parses_tokens_and_stops_at_the_limit`.

Eight mutants of the server fail these tests: dropping the pre-wait generation
look, answering every wake, reporting without comparing digests, dropping the
table check, not retiring a refused token, not waking on an exit that leaves a
poll open, not registering followers, and not moving the baseline.

**Clocks** (`clock.rs`): an open poll survives clock advances.

**Clients:**

- `presence-follow.test.mjs`, on a controlled transport: a moved token is not
  followed while its watch re-runs, where round 3 polled in a loop; an empty
  token is never followed and re-runs after 30 seconds; the follow list holds
  each token once, up to 64, less the moved.
- `presence-live.test.mjs`, on the online, native and web tiers: Alice's mark
  turns true about 20 ms after Bob's client starts watching, and false within
  about 4 s of Bob closing and the clock passing his grace, every answer
  `fresh: true`.

**Docs:** the presence card; `CLIENT-AND-OPERATIONS.md`, for `follow` and
`presence`; `NOT-DOING.md`.

## 6. Not decided here

- A query that presence makes refuse, such as `require not exists
  connected[p]`, stops being followed once it refuses: a refusal carries no
  token. Its watch refreshes when a table it read changes.
- A count that is followed per change. It flickers when one of several devices
  re-polls.
- Last-seen times. They would be storage, and remain not-doing.
- Presence across servers.
