## Summary

Eighteen Clique calibrations sit on a plateau: holistic 88–92, with
`data_modeling`, `queries_and_live` and `scale_and_limits` at the bottom in
every window (LLP 3000.012 §2.1). Every `data_modeling` note charges the cost
of learning Quarry's execution model, and most charge a read model the
application maintains or a capacity number the author chose. 0.3.0 moved
three derived forms into the engine and the calibration did not move
(`data_modeling` 87, `queries_and_live` 90).

The remaining cost is the surface itself. A query names the index it scans
(`by byAuthorTime`), hand-merges lanes (`[h] for h in range(hour(now) - 24,
hour(now) + 1)`) and states bounds the engine could choose (`first 10001`,
`size authors 2000, edges 20000`, `cap 60000`). Each derived form has its own
grammar and its own limits. A typed reference can silently select a parent
scan instead of the row it names. The builder has to learn the engine's cost
model to state what the product means.

Charlie authorized significant rework (2026-09-23: "if you need to try making
*significant* architectural reworks in order to make the data modeling,
queries, and scalability be excellent and elegant, you can experiment with
that. I'm not attached to things being the way they are now."). This RFC
decides that rework:

1. **Reads state intent; a planner chooses how.** `posts where .authorId =
   owner last 20 by .at after c`. The compiler chooses or synthesizes every
   index. Queries, rules, sync lines, caps and expiry never name one.
   Time-window rankings become bucketed lane merges without authored lanes.
2. **One derived-data declaration, `view`.** The engine picks the strategy:
   filters, projections and unions are planned at read time; aggregates are
   maintained in the writing transaction; Following is materialized per
   reader.
3. **Following without caps.** Delivery to followers becomes engine-owned
   background work, so a post acknowledges in constant time. Reads hide
   unfollowed authors immediately. Promotion, pull routes, broadcast lanes and
   every author-visible cap leave the design.
4. **Work without bounds.** Aggregates over reads stream instead of
   materializing pages. Job loops chunk themselves. `emit … once` replaces
   marker tables.
5. **A paved client.** One app object owns sign-in, restore and the durable
   outbox. One command gives a web export an offline shell.

The engine, rules, partitions, prediction, metering and IR stay. The rework
is a planner and desugarer in front of the binder, three engine additions
(merge-lane projection, background delivery, streaming aggregates), and the
client.

**Interpretation.** The strongest categories (media 98, authorization 97)
are the ones where a declaration on a table does the whole job. The weakest
are the ones where the author must also say *how*. The fix is to let the
author say only *what*, everywhere, and to move the *how* into a planner and
the engine.

## 2. Reads state intent

### 2.1 Predicate reads

```quarry
query userPosts(owner: principal, c: cursor ?):
  return posts where .authorId = owner last 20 by .at after c postCard
query thread(postId: posts, c: cursor ?):
  return replies where .postId = postId first 20 by .at after c
query trending():
  return posts where .at > now - 1d and .at <= now last 10 by .likeCount, .at postCard
```

A read is `T where P`, optionally followed by `matching q`, a page clause
(`first N` ascending or `last N` descending), `by K1, K2, …` and `after c`,
then an optional shape. Order keys are columns (`.at`), including
engine-maintained columns. `id` is always the final tiebreak in the same
direction. Without `by`, the order is `id`. Ids are time-ordered, so
`last N` is newest first. Without a page clause the read is a domain: the
whole matching set, bounded as today by a schema cap or the meter, and
chunked in a job (§5.2).

Supervisor ruling (2026-09-24): in a table order, every key after `id` is
redundant because `id` is unique within that table. The planner truncates the
order at `id`: `by .id, .at` plans exactly as `by .id`, using the existing id
index without a duplicate component or new index. View orders are not
truncated: ids may coincide across branches, and branch identity breaks any
remaining tie after the projected order keys.

The planner splits `P` into top-level conjuncts:

| Conjunct | Plan |
|---|---|
| `.c = e`, with `e` independent of the row | an equality pin on `c` |
| `.c < e`, `<=`, `>`, `>=` on the first order key | a seek |
| a range on a `time` column other than the first order key, with finite lower and upper bounds (`now - D` and `now`, `D` constant) | bucketed lanes over every intersecting bucket: `hour` for a window ≤ 48h, `day` for ≤ 92d; the exact endpoints stay as filters, so the page is exact. With only one bound the window is not finite, and the read is an ordinary residual scan with a note that adds the missing bound |
| `.c in e`, with `e` a bounded list or one column of a read (`members where .principal = viewer`)`.conversationId` | one lane per value |
| anything else | a residual filter, evaluated after the read rule, under the meter |

The 0.4.1 Workroom ruling (2026-09-24) makes ordering comparisons on nullable
scanned-row columns inside `where` false on null. A seek on such a column
excludes nulls: an upper-only seek has an exclusive null lower bound.
Equality and inequality with null remain total. Nullable arguments/locals and
comparisons outside predicates keep their presence checks.
Seek extraction, including an explicitly ordered page, requires a present,
infallible endpoint before the predicate runs. Required bindings and literals
qualify; arithmetic qualifies only with a proof against overflow. Division and
optional bindings guarded within the predicate stay residual, preserving
short-circuit evaluation and narrowing.

Required enums of at most eight variants plan `!=` a literal or stable bound
value as membership in the remaining variants. Nullable enums and larger
enums remain residual; nullable inequality retains null rows. Fallible
exclusion expressions remain under their original predicate guards.
Value lanes require a proof that every lane prefix decides the source read
rule, including any nullable fallback lane. Otherwise membership and enum
inequality stay residual on an ordinary scan, preserving its continuation
through visible rows without claiming completeness for a non-uniform rule.
Certificates render residual membership as membership, not its lowered
boolean initializer; fully extracted predicates have no residual clause.

The optional-filter ruling (2026-09-24) recognizes `(a = null or C)` in
either disjunct order (also accepting `==` in this idiom). `a` must be an
optional argument or a local derived only from arguments. `C` must be a
pinnable equality, bounded membership, or range with a safe endpoint that
uses `a` and no other optional input. Up to three distinct inputs receive
presence alternatives; additional conjuncts remain residual and are named
by `N_OPTIONAL_FILTER_LIMIT`. Each alternative uses ordinary index planning
and admission. The runtime selects it before the scan, removing an absent
input's conjunct and narrowing a present input. Streaming aggregate
consumers remain streaming on each alternative. Certificates describe each
presence combination; any growing alternative makes the operation grow.

Presence alternatives share a logical page site and carry a fixed-size
128-bit identity in their opaque cursor scope. Changing presence refuses
with `E_CURSOR_INDEX`, including when alternatives share an index. A search
needle folding to no terms is another absence alternative: browse using the
ordinary pins and order. Evaluate the needle once and meter its fold before
choosing. This is Quarry lowering; serialized raw words-index IR keeps its
existing behavior when no word lanes exist. Server and device interpret
the same conditional reads. Generated browse normalization touches only its
outer leaf; nested point reads and needle expressions retain their own keys.
For an explicitly selected words index, the browse leaf reuses the
lexicographically first plain index with the identical effective ordering and
computed-key definition, or synthesizes its ordinary index. This generated
choice does not relax ambiguity checks on authored predicate reads. A unique
key with any nullable component is not a total cursor order: null ties are
legal. Browse alternatives and ordinary reads with cursors reuse an index
without a declared id only when every unique component is required (including
validated calendar keys). Otherwise they synthesize or choose a separate id
ordering, preserving the unique constraint. Explicit unsafe cursors refuse
with `E_CURSOR_INDEX` and a column-ordered read rewrite. Reads without cursors
may keep their existing physical-prefix indexes; merge cursors and internal
sweep/aggregate positions already carry the physical id tiebreak. The generated
Following inbox keeps its existing unique constraints and reads through a
separate `byReaderPage` index ending in id; pending-work completeness and
live-query dependencies apply to both old and new reader indexes.

Presence-selected reads cannot supply mutation population loops or top-level
job sweeps in this implementation. Bind those as an ordinary capped loop or
stable sweep and put the optional condition in its body. Mutation admission
retains conditional scan provenance even for emit-only loops. The runtime
validates every top-level loop before running any chunk and parks stored
non-native jobs with no recorded sweep or any unsupported work loop as
`E_JOB_SWEEP`. Mixed valid/invalid sweeps cannot skip work or commit a valid
chunk first. Bounded setup loops before a recorded sweep are supported when
both their bodies and domain expressions are write-free and emit-free;
compiler-generated prefix setup, such as a list `sum`, replays under each
chunk's meter. Inner loops keep their execution. A trailing setup loop with
no following sweep is unsupported because no chunk would execute it.

A keyed `exists` in a predicate is always an ordinary authorized point
probe when it covers a total unique key. Driving from that table is only
an optimization: if its discovery prefix cannot decide its read rule,
retain the point probe per candidate and explain the skipped-row growth.
The source rule, disclosure policy, scan admission and meter are unchanged.

The index is the pins in canonical order, then any bucket key, then the order
keys, then `id`. A declared index with exactly those leading components is
used. Otherwise the compiler synthesizes one and adds it to the schema. Its
identity derives from its complete canonical descriptor: components,
computed-key parameters, words fields and uniqueness. It is independent of
declaration and program order. `check --cost` prints
every chosen and synthesized index with the read that needs it. Index
synthesis changes nothing at run time. The engine builds indexes on adoption
exactly as it does for a declared `by` line.

A predicate read that the planner can only serve as a sparse residual scan
keeps today's note (`N_SPARSE_FILTER`), with a rewrite to a pin, a view
(§3), or an order key.

### 2.2 Point reads have one meaning

`T[e]` reads the row whose id is `e`. `T[a, b]` reads by the table's
*declared* unique key of that arity, in declared column order. If no declared
unique key has that arity, or more than one does, the read is refused and
must name its columns. Synthesized indexes never take part in resolving a
positional key, so adding a read can never change another read's meaning. `T[col = e, …]` reads by named
columns; named equalities that cover a unique key check any extra columns on
that one row. A positional read that would select a non-unique prefix
without an explicit `by <index>` is refused, with the `where` rewrite. This
removes type-directed selection between a row and a parent scan. The
explicit `by <index>` forms remain accepted for existing programs.

### 2.3 No index names anywhere

`by` lines on tables become optional tuning. The compiler synthesizes what
each of these needs:

- rule probes (`exists members[.conversationId, viewer]`, named probes);
- sync audiences and horizons: `sync to members[.conversationId] last 500 by .at`;
- `cap N by col`;
- `expire at .expiresAt`, whose sweep index is synthesized;
- word search. A table line `search displayName, handle` declares the words,
  and `matching q` reads synthesize the words index for their pins and order.

`unique` takes an optional name: `unique handle else HANDLE_TAKEN 'That
handle is taken.'`, `unique postId, principal`.

### 2.4 Durations

`500ms`, `30s`, `15m`, `24h` and `7d` are integer milliseconds in any
expression, not only in `bucket` and `schedule`.

## 3. One derived-data form: `view`

A view is a named query. The engine decides whether to plan it at read time,
maintain it, or materialize it. `maintain … : timeline` and `maintain
name: count …` remain accepted as older spellings, and `check --fix` rewrites
them.

### 3.1 Planned views: filter, projection, union

```quarry
view activity:
  posts where not .removed { post: .id, actor: .authorId, at, repost: false }
  reposts { post: .postId, actor: .actorId, at, repost: true }

query global(c: cursor ?):
  return activity last 20 by .at after c { *, post: posts[.post] postCard, actor: profiles[principal = .actor] }
```

Each branch is `T [where P] { fields }`. Every branch yields the same field
names with compatible types. A view row's identity is its branch and its
source row's `id`: ids are unique within a table, not across tables. So two
branches never collapse into one row, and cursors carry the branch.
A view is read like a table. A pin or range on a view field becomes a pin or
range on each branch's source column. A pin on a constant field selects the
matching branches. Order keys must be source columns in every branch.

The plan is one merge lane per branch, and per `in` value or bucket. Each lane
scans its own table under that table's read rule, applies the branch filter,
then projects. The merge orders by the projected order keys, then source id
if absent from those keys, then branch identity. The cursor carries those
values. Source ids may coincide across branches; branch identity keeps those
rows distinct, with no duplicates or gaps across tables. Nothing is stored.
Live queries, devices and prediction behave exactly as for the source tables.

**Engine addition:** `MergeLane` gains an optional projection, evaluated per
row after the read rule and filter, before merging. Lanes may name different
tables. The merge key is read from the projected row. The existing
cross-table cursor translation (LLP 3000.007 §20.3) generalizes to
projected lanes.

### 3.2 Maintained views: aggregates

```quarry
view followerCount: count follows by .followedId
view receivedLikes: count likes by .postId.authorId
view dailyPosts: count posts where not .removed by .authorId, day(.at)
view revenue: sum orders of .amount by .shopId

table posts:
  likeCount: count likes
```

These have exactly the semantics of today's maintains: the same engine, the
same recorded attribution, and maintained columns for the in-table form.
`followerCount[p]` reads the number, 0 when absent. Two defaults remove the
boilerplate lines:

- **Readability is derived.** A uniformly readable source gives a readable
  aggregate. A source whose read rule uses only bare group keys gives the same
  rule over the aggregate's key. Anything else needs an explicit `read <-`.
- **In-table columns find their reference.** A column is counted by the one
  column of the source that references the table. If there are several, use
  `count likes by .postId`.

### 3.3 Materialized views: Following

```quarry
view following: activity where .actor = viewer or exists follows[viewer, .actor]

query home(c: cursor ?):
  return following last 20 by .at after c activityCard
```

The planner recognizes this shape and materializes one inbox per reader. It
does so only when materializing discloses nothing the sources do not already
disclose. The originals, reposts and edges must be explicitly public and
fully `sync public`, with owner rules and immutable mapped columns, as the
0.3 timeline requires. Structure alone is not permission; private feeds
would need their own per-recipient authorization design.

- a planned union with an originals branch (`post: .id`, a principal actor
  column, a time column, an optional one-way removal flag);
- a reposts branch (`post:` a reference to the originals table);
- filtered by the viewer plus an edge table whose unique key is `(follower,
  followed)` of principals.

The declaration contains no sizes, no author table and no caps. Any other view
that mentions `viewer` is planned at read time.

## 4. Following without caps

The 0.3 timeline copies events inside the writer's transaction. To keep that
work under the 1,024-write mutation ceiling, it promotes authors past 50
followers to a shared broadcast lane. It merges at most 32 such lanes on
read, and it caps follows, followers, authors and events. Each of those
numbers exists only because the fan-out runs synchronously.

This RFC makes delivery engine-owned background work:

| Transition | In the writing transaction | Afterward |
|---|---|---|
| Post or repost | the source row, the author's own inbox copy, one durable delivery record | copies to followers, 256 per chunk |
| Follow | the edge, plus copies of the author's newest 50 events | older events, chunked |
| Unfollow | the edge delete | deletion of that author's copies, chunked |
| Remove (one-way flag) | a public tombstone | purge of copies |

Reads filter the inbox by the view's own predicate: the actor is the viewer
or is still followed. That is one point probe per candidate row. Unfollow
therefore takes effect on the next read. It also deletes up to 256 stale copies
in its own transaction, so an ordinary unfollow leaves nothing to skip.
Removal hides through the tombstone, as today.

Every task is durable and idempotent:

- Delivery, backfill, cleanup and purge are enqueued in the transaction that
  causes them.
- A task's progress commits with the rows it writes.
- SQLite disk transactions use WAL `synchronous=FULL`, including background
  work. A chunk also publishes partition-log watermarks: replaying lost copies
  would not repair a watermark already observed by a device. `NORMAL` is
  therefore insufficient even for idempotent delivery.
- Copies are admitted by their (reader, event) identity.
- Tasks are bound to the incarnation of their edge and event. An old cleanup
  never deletes copies made by a refollow. Delivery revalidates the event and
  each edge in every chunk. A tombstone outlives any task that could still
  publish its event.

Background delivery runs on the server promptly after the commit that
enqueued it, not on a minute schedule. Followers normally see a new post
within a second; the author sees it immediately. Following pages over
*delivered* inbox contents:

- A page read during an unfinished delivery may lack the newest foreign
  events.
- `complete` is false for a reader while a backfill or cleanup task for that
  reader is pending.
- Nothing the predicate excludes is ever shown.
- `doctor` lists pending tasks.

There are no author modes, pull routes, pull counts, broadcast lane or
author-visible caps. The per-chunk meters bound engine work. Devices hold the
reader's private inbox and the public edges, and apply the same read filter
locally.

The server admits requests and maintenance through a FIFO. Maintenance may
wait for 1 ms without request activity, but takes its ticket after at most
5 ms of deferral, so sustained traffic cannot starve it. If requests are already
queued behind the active request, it joins the queue immediately. It uses a 250 µs
cooperative work slice when contended and 2 ms otherwise, in addition to the
count and meter bounds. These slices end between atomic rows; commit I/O can
extend the lock hold. A request already queued precedes the next chunk.

Removing a materialized view retires its owned rows, indexes and delivery work
in the activation transaction. Dependent aggregates are reset or retired there
too, including when their table names survive as ordinary tables. Source rows
and unrelated views survive. Dev needs no flag; deploy requires
`--allow-destructive`, as for removing a maintained aggregate.

Redefinition is refused with `E_TIMELINE_REDEFINE`; there is no sound historical
builder for a new view over populated event or edge tables either
(`E_TIMELINE_ACTIVATE`). For example, repost event ids are minted when the
original mutation runs and cannot be recovered from the repost source row;
rehashing that row changes tie order, saved ids and the history-window cut.
The withdrawn experimental reconstruction also could chase a growing source
indefinitely or park on an orphan repost. It is not a product execution path.
An unfinished experimental reconstruction refuses to open or resume; removal
can still retire it. The rewrite is to remove the view and deploy, then add the
new definition over empty event and edge tables. For retained populated sources,
use a planned view. Removing and re-adding over the same populated sources is
not a historical reconstruction mechanism.

## 5. Work without bounds

### 5.1 Streaming aggregates

`count(R)`, `sum(R, .col)` and `exists R`, where `R` is a predicate read
without a page clause, examine rows under the examined and steps meters.
Each decoded row is charged transiently, and exactly that charge is released
when the row is dropped. Retained state stays charged.

A streaming consumer keeps the underlying scan's admission, authorization,
expiry and coverage checks. Calling a scan `count` does not make it a safe
probe; LLP 3000.007 §21.9's expiring-mutation counterexample stands.
Unpaged aggregate reads retain ordinary streaming scans: membership, enum
complements and window predicates do not become bounded merge pages. Their
residual filters fold the entire admitted domain, or return null on a cut.
Streaming aggregation across planned lanes is not implemented.

The busy-chat digest claim (LLP 3000.011.001.000's 16 MiB stop) holds only
if the retained recipient-heavy fixture passes.

An inferred aggregate seek must preserve predicate short-circuiting: its
endpoint must already be present and must not fail when evaluated before the
whole predicate. Otherwise the comparison stays a residual filter. Selecting
one safe endpoint must not extract an unsafe sibling bound on the same column.
A named prefix pinning intrinsic `id` keeps its single-row access path; remaining
comparisons filter that row rather than introducing an order after the id pin.

### 5.2 Self-chunking jobs

A top-level `for x in R:` in a job, over a stable domain, is a chunked sweep.
A stable domain orders by `id` or by immutable columns; a row could otherwise
move behind the cursor. The engine commits every K iterations, with the cursor
and the evaluated domain bounds, as `chunk` does today.

K adapts: it starts at 64, and a meter refusal retries the same uncommitted
work with K halved. Rule, constraint and generation refusals park at once.
A job parks on a meter only when a single iteration alone is refused.

Locals declared in the loop body are per-iteration; loop-carried state
across a commit is refused. `chunk … first N` remains the explicit spelling.

### 5.3 Effects keyed once

`emit notify { … } once [p.principal, periodEnd]` records at most one effect
per effect name and key, forever. A repeat is a no-op, not a refusal, and
survives restart and retry. Keys are stored apart from the outbox, so a
replay-suppressed emit still records its key. `once` deduplicates emission,
not completion: an iteration that emits nothing records no key.

## 6. A paved client

- **The app object.** `snapback4/app` exports `createApp({ url, device?,
  sessionStore? })`. It returns `{ client, auth }`, where `auth.state` is
  `restoring`, `signed-out` or `signed-in`, and `auth` has `signup`,
  `login`, `logout` and `guest`. It persists the session and reopens the
  local outbox. Pending writes keep their ids across restarts without
  authored intent storage. In React, `<AppProvider app>` and `useAuth()`
  compose with the existing hooks. Client opening is provisional; the prior
  owner remains live until success. Replacement journals retirement, then
  commits the bearer and epoch in one atomic store write under the session
  lock. Automatic rotation and outbox replay start after that commit.
  Restoration and rotation retain their epoch; replacement of a live bearer
  advances it. Logout atomically writes a noncredential tombstone carrying
  the epoch and retirement obligations. In the browser, IndexedDB is the
  authoritative session state (2026-09-25 ruling): every session replacement or
  logout awaits its strict transaction commit inside the session Web Lock.
  localStorage mirrors that value and synchronously captures mutation intent;
  it is not authority for a locked admission or recovery check. Chromium's
  renderer caches can remain stale across Web Lock holders. A stale mirror may
  capture a click, but admission checks IndexedDB under the lock and returns
  `E_AUTH` instead of admitting or sending it after logout. Legacy mirror-only
  sessions require sign-in, and unadmitted records without the new authority

### 11.1 Keyed writes on expiring tables (0.4.1, Lane P)

The 0.4.0 cap check scanned the whole physical cap group to count live rows.
With `unique conversationId, ordinal`, `cap 200000` and `expire at .expiresAt`,
9,000 sequential sends stopped at insert 8,193 even when every expiry was null.
The unique lookup already pinned the complete key; the cap scan caused the
live-population cost.

Cap checks on expiring tables now read a maintained **physical occupancy**
counter, per table or declared cap group. This is conservative: unswept expired
rows occupy capacity until removed. Inserts, deletes, group moves, inline
cleanup and background sweeps update the counter transactionally; failed writes
and device withdrawals restore it. Store adoption or legacy-store upgrade
builds counters once; reopening an unchanged store does not scan to count.
The memory device rebuilds them with its indexes from persisted row images.
Counter transitions are charged as index bookkeeping under the existing meter.
Non-expiring tables retain their existing cap path.

Every unique constraint on an expiring write probes only its complete key.
Expired collisions are skipped under the examined meter; unrelated keys do
not contribute. `if absent`, secondary unique keys, and unique-key upserts
retain this behavior. Update, upsert and alternate-key delete accumulate
target-resolution expiry work privately and charge it only after write
authority. A denied target and an absent target have the same refusal and
meter, including past the examined ceiling. Resolution stops after the
remaining examination allowance plus one expired sibling: an unresolved
update/delete refuses `NOT_FOUND`; an upsert cannot use this cut as an absence
proof, because its insert arm must pay the over-ceiling debt after insert
authority and before any write. Authorized upserts with excessive backlogs
therefore refuse `E_BOUND` and roll back until swept. This private limit keeps
denied resolution bounded too. Server rule probes retain their existing
population-independent accounting. Alternate-key delete retains its read gate
but resolves inside the engine instead of through an author-visible `Get`.

**Deferred cleanup (round 1 review decision):** secondary unique collisions
remain physical until the background sweep. The ordinary deletion tail emits a `scope` and row id when
retiring a membership inserted already expired, disclosing a group that the
recipient never held. The existing
`a_never_live_grant_stays_silent_across_watermarks` regression demonstrates this
with two already-expired grants for the same group/principal. Physical rows
carry no birth-visibility provenance, so this needs a reviewed lifecycle design;
Lane P does not weaken disclosure to implement it. Existing by-id replacement
and background expiry behavior are unchanged. With a full physical cap, a
secondary-key replacement refuses `E_CONSTRAINT` until the sweep removes its
predecessor. The refusal includes its write site and a rewrite naming the
one-second tick and 2,000-row pass limit. Immediate secondary removal is no
longer a landing requirement under the round 1 ruling.

**Integration with commit-end retirement (2026-09-24):** main's reviewed
LLP 3000 §7 fix retires a program's already-expired births before commit.
That removal uses the same transactional counter deltas as the sweep, so
both table and group occupancy are released before the next write. Born-row
events are withdrawn and born grants reveal no scope; a replacement beside

program births from becoming the backlog described above. Seed/load rows and
older physical rows retain the deferred-cleanup limitation. Devices still

The certificate describes constant work in the live population plus only the

### 12.1 Scale: background work never stalls a request

- **Requests come first.** The engine lock is FIFO. Background work (delivery, jobs, sweeps, leases) runs in time slices (1–2 ms, 250 µs under contention) and takes a ticket only when no request is waiting, deferring at most 5 ms. A post by an author with 900 followers acknowledges within 1.5× of an ordinary post's p95; on 0.4.0 it was 120×.
- **Every disk transaction is `synchronous=FULL`.** Under `NORMAL`, a lost commit could rewind a watermark a device had already observed, and the device would refuse the store for good (`E_STORE_RESTORE`).
- **A populated materialized view can be removed.** Its owned data and dependent aggregates retire in the activation transaction; `deploy` requires `--allow-destructive`. Redefining one is refused: the repost event ids cannot be rebuilt soundly.
- **Expiring tables keep O(1) writes.** Cap enforcement uses a maintained physical occupancy, so it is conservative until the sweep runs. Unique checks are point lookups. Expiry work is charged only after authorization, and the reservation precedes the lookup, so a refusal is identical at any hidden backlog. A device defers prediction of occupancy-increasing writes on an expiring cap.

### 12.2 Reads and the client

- **An unavailable answer is never data.** It is `loading`, or `denied` where a refusal explains it. `usePage` never throws.
- **Retention is bounded.** Only the local client keeps an answer, and only across the server fallback it started for an unavailable device rerun. Any local commit clears it. The online client retains nothing.
- **Online reads are monotonic** within a store, and a response older than an acknowledged write is refetched.
- **A store identity change or a sequence regression is terminal** (`E_STORE_REPLACED`, `E_STORE_RESTORE`) for every entry point: reads, writes, actions, uploads, assets, refresh. `createApp` reopens after a replacement. Pending writes are durably retired, and a retired or displaced id is never admitted again.
- **No request whose server effect may have committed is aborted.** The caller's wait is cancelled, adoption is fenced, and an unkept result is revoked.
- **`createApp` session custody is modelled.** Invariants I1–I13 are checked over 5,000 seeded interleavings on each of the online and local clients. The interleavings mix sign-in, refresh, logout, logout-everywhere, reopen, held responses and injected storage failures. Among the invariants:
  - a stored bearer is never revoked by another runtime;
  - a failed operation leaves the store as it was;
  - a refused bearer is never restored;
  - no handle outlives its principal;
  - a dispatched write's known outcome is never replaced.

  The online client's invariants R1–R6 are checked over 3,000 more.
- **`close()` never waits on the network.** A write or action whose response has not arrived when close completes is `pending`, never a failure. The durable intent settles it on the next open, where the server's idempotency record answers `replayed: true`. A response that arrived before close completed keeps its known outcome.
- **A known result survives a failed receipt save, and replay goes only to the store that acknowledged it.**
  - Each durable online intent records the store it was dispatched against, before dispatch.
  - A repost after restart goes only to that store, where it is deduplicated.
  - An intent recorded against a replaced store retires with an unknown-outcome refusal.
  - The server checks the requested store identity under its engine lock before it executes a mutation or an action.
  - If storage cannot record the intent's store at all, the write is not admitted.
- `createApp` forwards the local client's options (`assets`, `waitSeconds`). Uploads snapshot their bytes once, across realms and on React Native, and retry bounded admission refusals.

### 12.3 Language: forms a builder writes on the first try

**Lane S (2026-09-24, shipped in 0.4.1):** an infallible point read whose value flows
only into effect arguments does not cost prediction, including below a
presence guard and through local bindings. The compiler retains every shared
use (condition, write, refusal, return, loop domain or unrelated binding), and
the device skips only the proven exclusive payload work. The server executes
the original program with its ordinary authorization, durable emission and
meters; these reads are charged on the server only. `why` names them as
"server-only, feeds an effect". Nullable fields, coalescing and proven total
text/arithmetic expressions qualify; unwrap/require, unproved division,
overflowing arithmetic and live sums over expiring sources remain fallible.
The existing presence rule still governs all other work. This accepts the
server/device charge difference already allowed for effect arms.

- **Spread.** `{ ...p, extra }` is the shape `p { *, extra }`: fields combine left to right, and a result is `pending` if any spread row is. A conditional that joins different row kinds (spread object, shape, row) is refused with an explanation. A pasteable rewrite is offered only where it is proved.
- **An explicit field replaces the column `*` brought in.**
- **Bare `text` is `text <=10000`.** An index that needs a bound says so, naming the read or `unique` line.
- **A positional key, then named tests,** in rules and reads. Write targets still name one row by its key; the rewrite tests the extra columns with `require exists` first.
- **Schedule periods take any duration unit** of one minute or more.
- **Diagnostics speak the builder's terms:** rule-keyword synonyms, source-quoting certificates, synthesized indexes named by their columns, and constraints across hidden rows explained with the per-unit `unique` pattern.

### 12.4 The planner

- **Optional filters.** `(a = null or C)` plans as argument-presence variants, at most 2³.
- **An empty search browses.**
- **A keyed `exists` never refuses.**
- **Complement and value lanes are planned only where the prefix decides the rule.**
- **Seek endpoints are extracted only when safe to evaluate first.**
- **A page cursor totally orders its rows,** so no nullable unique index substitutes for one.
- **Presence conditionals cannot be sweep domains,** and a job never reports done without running its domain.

### 12.5 Evidence and tooling

- **`snapback4 witness ios --smoke`** proves an Expo app's native runtime (prime, offline relaunch, restart) with no application code.
- **The README names `check --cost` as the structural proof** for degradation rules.
- **Guide cards lead with what the feature is.** Every refusal excerpt carries the facts a client needs, pinned to executed writes.

### 12.5a What the macOS publication run found

The first 0.4.1 dry run on the M5 stopped on failures that the Linux suite does not run:
- Node's bundled Undici threw outside the fetch promise, surfacing `setTypeOfService EINVAL` from `mutate`. The Node transport now uses a private Undici dispatcher, and every rejection after dispatch is `pending`.
- A refused adoption created `_cap_counts` and its marker in the old store. Counter initialization now happens only inside a successful activation or upgrade.
- Canonical printing lost four `[]` pairs. Canonical origins restore the pinned 2,950-byte capability-free backend.

The published-0.2.33 fences run on darwin-arm64 only, so every publication's dry run is where they are enforced.

### 12.7 Review of the ruled close and replay code

The blind reviews of integration part h ([Astra](./reviews/3000.013-integration-part-h.astra.md), [Grok](./reviews/3000.013-integration-part-h.grok.md), both NOT READY) found narrow defects. Integration round 6 fixed them before 0.4.1 was published:
- Two concurrent calls with the same id, both answered during close cleanup, can swap or drop their known outcomes.
- `close()` still awaits a held `/auth/refresh`.
- A response delivered during the app's own session cleanup returns `pending` rather than its known outcome.
- A duplicate caller of an overlapping write can receive `E_WRITE_RECEIPT_EXPIRED` at close.
- The session model's oracle compared outcome kinds, not full refusals.
- An intent admitted but not yet bound to a store when the process died is bound to a replacement store on reopen, instead of retired (Grok).

trades synchronous follower visibility for constant-time writes; that trade
