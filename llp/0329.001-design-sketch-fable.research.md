# One language, three kinds, no flags

**Thesis:** liveness, offline retention, and authorization are not features to be
requested — they are *static properties of a program*. Snapback's error was to make
them authoring modes. Make the read/write language analyzable by construction, make
the analysis total, and put the escape hatch at a different *kind* rather than a
different *spelling*.

---

# Part 1 — Theory

## 1. The core abstraction

An author writes exactly three kinds of thing:

| Kind | What it is | Guaranteed properties |
|---|---|---|
| **view** | a bounded relational expression over tables | live, retainable offline, authorized, cacheable |
| **transition** | a bounded write sequence over tables | locally predictable, durably replayable, atomic |
| **effect** | arbitrary JavaScript | none of the above, by definition |

Views and transitions are written in one small analyzable language and compile to
IR. Effects are ordinary JS that may call out to the world, and may only change data
by applying a transition.

Everything else is derived. The system computes, and the author never writes:

- the read set (for invalidation) — from the view's plan
- retention eligibility — from the plan plus the schema's visibility rules
- the authorization predicate — from the schema, not the query
- the optimistic prediction — by running the transition IR against the local store
- the replay envelope — the transition IR *is* the queued intent

`reads:`, `writes:`, `retainable:`, `authorityIndependent:`, `auth: 'public'`,
`defaultLive:` all disappear. Not because they stop mattering, but because asking
the author for a fact the compiler can prove is how you get a matrix with holes:
the author can answer wrong, and the answer silently changes what they get.

## 2. Avoiding the capability matrix

The brief's question is the right one: either every program gets every capability,
or the language refuses to express programs that can't have them. **I choose refusal,
and I think the choice is forced.**

If capability is optional, capability becomes a mode; modes multiply
combinatorially (this is literally where 13 query flavors came from); and the author
cannot see which mode they are in. The only way capability can be invisible — which
is what you want, since the author should be thinking about their app — is for it to
be *uniform*. Uniform means total. Total means restricted.

So: **anything expressible as a view is live, retained, and authorized. There is no
view that isn't.**

### The honest cost

The view language is not Turing-complete. Things that are genuinely hard or
impossible in it: aggregations beyond an admitted set, recursive traversal,
ranked full-text search, "top N by a score computed in JS," anything reading the
clock or randomness, anything calling out.

I do not think you can wish this away, and I think the systems that pretend
otherwise are where the holes come from. The resolution is **not** an escape hatch
at the same layer. It is:

> Anything inexpressible as a view becomes an effect that *materializes a table*,
> which a view then reads.

Want a trending feed ranked by a model score? An effect computes it on a schedule
and writes `trending_rank`. A view reads `trending_rank`. The view is live,
retained, and authorized like everything else. Generality is preserved; totality is
preserved; the cost is a materialization step and staleness the author chose
explicitly.

This is the same move Snapback's own LLP 0155 reaches for ("composition of admitted
bounded plan nodes as the primary read-authoring surface") — but taken all the way,
so there is no second-class alternative sitting beside it.

### Why the escape hatch must be a different *kind*

`defineJsQuery` sits in the same position in the program as `defineQuery`, takes
similar arguments, and has different capabilities. That is the whole disease in one
API. An author choosing between them is choosing capabilities without knowing it.

An `effect` is a different kind of thing — a background job that calls Stripe or
resizes an image. Every programmer already knows a background job isn't reactive.
The capability boundary now coincides with a *conceptual* boundary the author
already holds, instead of a syntactic one they must be taught.

**Design rule:** capability boundaries must fall on concept boundaries. When they
fall on spelling boundaries, authors — human or agent — cannot see them.

## 3. Where authorization lives

This is the part I feel strongest about, because it is where the current design
actively produces insecure applications.

**Authorization is a property of rows, declared in the schema, and it is written in
the view language.**

```js
export const messages = table({ ... })
  .readable(m => memberOf(m.conversation))
```

Consequences, all of which follow mechanically:

- **There is no `auth:` option on a query.** A view is exactly as visible as the
  rows it returns. Visibility is not something a query can widen.
- **Therefore widening visibility buys nothing.** The P18 failure — an agent setting
  chat tables to `public-read` because `auth: 'public'` was the predicate that
  unlocked retention — cannot occur, because retention does not depend on it. The
  incentive that produced the insecure choice is gone, not merely discouraged.
- **The private case is the paved case.** `memberOf(...)` is the ordinary spelling.
  Public data is the degenerate rule `.readable(() => true)`, i.e. the *special case*,
  which is the right way round.
- **Revocation is just a write.** Deleting a membership row changes the rule's
  result, which the same invalidation machinery already tracks. Authorization
  invalidation stops being a separate subsystem with its own epochs and leases.
- **Retention is provably sound.** The client's retained rows are exactly the rows
  whose rule held for that viewer; when the rule stops holding, the row is
  invalidated like any other.

Because rules are written in the view language, they are bounded joins, so the
planner can push them into the query rather than post-filtering — which is what
makes this affordable rather than merely correct.

**What this does not fix.** Rules must be bounded, so recursive authorization
("visible if any ancestor folder grants it") needs a materialized closure table.
Retained-then-revoked data on a disconnected device is still a real problem — you
still need a bounded lease before a client may render rows it cannot revalidate. I
am not claiming the hard problems vanish. I am claiming they become **one
mechanism applied uniformly** instead of a matrix of special cases with different
eligibility rules. That is the entire win.

## 4. The agent as author

Four properties of agents, and what each demands:

**Agents retrieve; they do not read.** A 178-page guide is not a documentation
problem, it is a *surface area* problem wearing a costume. You do not fix it with
better retrieval; you fix it by having less to retrieve. Target: the complete
authoring vocabulary fits on one screen and in the system prompt. If the guide must
be large, the design failed upstream.

This is measured, not asserted. The 2026-08-21 retrieval-eval runs in
`guide/eval-runs/` are all PASSes — and the passing agents spent **7, 11, and 12 of
a 15-tool-call budget just reaching the right page**, before doing any work. The
static checker is now at **73 seed cases**, governed by a standing rule that every
replicated discoverability miss must add a case that would have caught it. That is
a treadmill: the surface generates misses faster than seeds absorb them, and each
seed is a permanent tax. A design whose retrieval eval must grow monotonically is
telling you its vocabulary is too large.

Two of those seed cases are worth quoting, because they are the thesis in
miniature. Case 4 fails the agent if its plan "hand-writes the join in
`defineJsLiveQuery`" — an eval case that exists solely to stop agents from falling
into the capability-losing form. Case 10 fails the plan if it "claims
`authScopeField` alone enforces the filter" rather than restating the
`authUserId()` predicate in the query. Both are the system asking documentation to
compensate for a surface that made the wrong thing natural.

**Agents cannot see consequences distant from the edit site.** Every consequence of
a choice must surface *at the choice, at author time*. A property that manifests
three subsystems away at runtime is invisible to an agent, and agents are the ones
you said you're optimizing for. This is the strongest argument for deriving
capability rather than declaring it: a derived property can be reported at the
declaration site; a declared one is only checked where it's used.

**Agents route around obstacles and document the compromise.** This is the finding I
would put on the wall. A refusal an agent can satisfy by widening permissions is not
a refusal — it is a funnel toward the insecure configuration. So: **a refusal must
have exactly one repair, and that repair must not be "reduce safety."** If your
error message has two ways out and one is `public-read`, you have shipped a
vulnerability with a helpful hint attached.

**Agents validate by running.** So the loop must be one command with a verdict, and
as much as possible must fail at generate time rather than run time. Snapback got
this right and should keep it.

On errors specifically: 3,934 distinct codes is a corpus, not a language. An agent
cannot hold it, so it greps — which only works if it already knows the term. Aim for
a closed set in the low dozens, each naming its single repair. Precision of
diagnostics is the most-praised thing in Snapback's diaries; the problem is
cardinality, not quality.

## 5. What earns its keep

**Keep:** server authority; Rust + SQLite + embedded JS engine; the measured idle
profile (~13 MiB, zero idle writes — genuinely rare, and the honest core of
scale-to-zero); typed refusals that name the repair; the green-receipt-or-it's-a-claim
discipline; and above all the benchmark/diary loop — running real agents building
real apps against real competitors is the best instrument in the project and should
exist in week one.

**Cut:** two authoring profiles; declared `reads`/`writes`; per-query auth switches;
JS handlers as a read/write authoring form; separate retention classes; committed
generated artifacts (the single highest-churn path in the repo); optimistic reducers
authored by the app (derive them from the transition IR); and a client that has
grown to ~212k lines implementing a capability matrix. Under this design the client
is a row cache, a cursor, and an outbox — which is what DK-9 said it should be all
along.

**Confidence.** High (0.85) that capability-by-authoring-form is the root defect and
that uniformity requires restriction. Medium (0.6) that row-rule authorization is
affordable at the planner level for the general case — that is the load-bearing
engineering risk in this design and I would prototype it before anything else. Low
confidence on the exact vocabulary below; treat it as shape, not spelling.

# Part 2 — The API

## Schema — group chat, private by default

```js
import { table, text, time, ref, exists, viewer } from 'backend'

export const users = table({
  handle: text().unique(),
}).readable(() => true)                       // profiles are public: the special case

export const conversations = table({
  title: text(),
}).readable(c => memberOf(c.id))

export const memberships = table({
  conversation: ref(conversations),
  user: ref(users),
}).readable(m => memberOf(m.conversation))

export const messages = table({
  conversation: ref(conversations),
  author: ref(users),
  body: text(),
  at: time(),
})
  .readable(m => memberOf(m.conversation))
  .index('byConversation', ['conversation', 'at'])

// A rule is an ordinary bounded view expression.
const memberOf = (conversation) =>
  exists(memberships, m => m.conversation.eq(conversation).and(m.user.eq(viewer())))
```

## The view

```js
export const threadMessages = view({
  args: { conversation: ref(conversations) },
  body: (a) => messages
    .where(m => m.conversation.eq(a.conversation))
    .order('at', 'desc')
    .limit(200),
})
```

This is live. It is retained offline. It is authorized to members only. **There are
no flags on it.** That is the entire proposal: this is the code that is hard to write
correctly today, and here there is only one way to write it.

## Composition — the thing Zero actually won on

A view that returns only `messages` is useless; you want the author's handle, and
you want to build bigger views out of smaller ones. LLP 0155 records that Zero beat
Snapback on "composable relational queries" and "query completeness," so the one
language has to earn that, or the restriction argument collapses.

```js
export const threadMessages = view({
  args: { conversation: ref(conversations) },
  body: (a) => messages
    .where(m => m.conversation.eq(a.conversation))
    .order('at', 'desc')
    .limit(200)
    .with({ author: m => m.author.one() }),      // bounded 1:1 traversal along a ref
})

export const myConversations = view({
  body: () => conversations
    .where(c => memberOf(c.id))
    .with({
      members:  c => memberships.where(m => m.conversation.eq(c.id)).with({ user: m => m.user.one() }),
      latest:   c => messages.where(m => m.conversation.eq(c.id)).order('at', 'desc').limit(1),
      unread:   c => messages.where(m => m.conversation.eq(c.id).and(m.at.gt(lastRead(c.id)))).count(),
    }),
})
```

Three rules keep this analyzable, and they are the whole trick:

1. **Traversal only along declared `ref`s.** No ad-hoc join predicates. The schema's
   reference graph is the join graph, so every join is indexed by construction.
2. **Every nested node is bounded** — `.one()`, `.limit(n)`, or an admitted
   aggregate (`count`, `sum`, `min`, `max`). No unbounded nesting, so a view's cost
   and its invalidation set are both statically known.
3. **Views compose as expressions, not as calls.** `myConversations` inlines
   `memberOf`; the compiler sees one plan. There is no opaque function boundary for
   the analysis to fail at — which is precisely the boundary `defineJsQuery`
   introduces today.

Nested authorization composes automatically: `members` returns only memberships the
viewer may read, because `memberships.readable` applies to the nested node like any
other read. The author does not re-state the rule at each level, and cannot forget
to.

**Cost, honestly:** `unread` above is a per-viewer aggregate over a per-conversation
range, and keeping it live is the expensive case in any system that offers it —
Zero included. It is affordable here only because the aggregate is admitted and
range-indexed. If you want an aggregate the planner has no incremental maintenance
strategy for, you are back in effect-plus-materialization. I would ship the admitted
aggregate set deliberately small and grow it on measured demand rather than
promising general aggregation.

## The transition

```js
export const send = transition({
  args: { conversation: ref(conversations), body: text() },
  body: (a, tx) => {
    tx.require(memberOf(a.conversation))
    tx.insert(messages, {
      conversation: a.conversation,
      author: viewer(),
      body: a.body,
      at: tx.now(),
    })
  },
})
```

`tx.now()` is a declared nondeterminism point: the server stamps it, the client
predicts with its own clock and reconciles on settle. Because the body is IR, the
same definition predicts locally and decides on the server. The author writes no
optimistic reducer.

## The client

```jsx
const thread = useView(threadMessages, { conversation: id })
const send   = useTransition(sendMessage)

// thread.rows
// thread.status: 'live' | 'retained' | 'loading'   (retained = offline, from local store)

await send({ conversation: id, body })   // optimistic by construction; queued when offline
```

## Failure modes

**Reading the clock in a view** — the trending/expiry case that costs Snapback lanes
today:

```js
export const trending = view({ body: () => posts.where(p => p.at.gt(now() - HOUR)) })
```
```
✗ views.js:12  A view cannot read the current time.
  now() makes this result change with no write, so it can be neither kept live
  nor retained.
  Repair — take the boundary as an argument:
    view({ args: { since: time() },
           body: a => posts.where(p => p.at.gt(a.since)) })
  and pass a refresh boundary from the client.
```

One repair. It does not involve reducing safety.

**Widening visibility** — the P18 move. It is still expressible, because sometimes
you mean it. But it no longer *buys* anything, and it is loud:

```
⚠ schema.js:14  messages.readable is unconditional, but messages references
  conversations, whose rule is membership-scoped. This publishes data otherwise
  reachable only to members.
  If intentional: .readable(() => true, { public: 'intentional' })
```

**Arbitrary JS in a read** — not a diagnostic, because it is not expressible.
`view()` takes an expression builder, not a function body. If you need JS, you need
an effect, and an effect is visibly a different kind of thing:

```js
export const summarize = effect({
  args: { conversation: ref(conversations) },
  run: async (a, ctx) => {
    const rows    = await ctx.read(threadMessages, { conversation: a.conversation })
    const summary = await ctx.fetch(MODEL_URL, { ... })
    await ctx.apply(saveSummary, { conversation: a.conversation, summary })
  },
})
```

Not live. At-least-once. Writes only through a transition.

## Surface size

The complete authoring vocabulary:

```
table  view  transition  effect
text  int  bool  time  ref  json
index  unique  readable  writable
exists  viewer  with  one  count
useView  useTransition
```

**Twenty-one names.** Today: 140 exported from `define.mjs`, 31 `define*`
constructors, 13 of them query flavors, 4,248 published symbol identities.

The generated client is one typed module per view and per transition, and the
runtime is a row cache, a cursor, and an outbox — nothing else.
