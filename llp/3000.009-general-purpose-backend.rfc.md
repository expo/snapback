## Summary

The author set the goal: "Nearly every ordinary application can use Snapback
as its application backend, while specialist systems can access
Postgres-compatible server-only facilities when needed" — a backend chosen
consistently over Convex and Supabase, agnostic to whether its server keeps
data in SQLite or Postgres.

Snapback 4 already has the distinctive half: one data language with static
authorization and runtime metering, maintained values, durable writes,
partition sync and prediction. For ordinary applications it lacks the server
half — declared action results, HTTP routes and webhooks, a supervised
runtime, identity and file services, operations — and a Postgres story. This
RFC designs both around five decisions:

1. **One executor, two stores.** The Rust interpreter remains the only
   executor of Quarry: on the server over SQLite or Postgres, and on every
   device. The storage boundary pushes down *access* — seeks, bounded scans,
   counts, batches of point reads and rule probes, a pipelined commit tail —
   and never *semantics*. Rules, expressions, shapes, completeness and the
   meter stay in the interpreter. Quarry is not lowered to SQL.
2. **Postgres is a persistence target.** A Postgres-backed server keeps the
   generic row and index layout, one commit order and the same wire. It adds
   operations (a managed database, point-in-time recovery, failover) and
   database capabilities, not a second query engine for Quarry.
3. **Database capabilities reach managed data only through projections.**
   The engine maintains a typed, natively indexed table from a managed table
   inside the managed commit. SQL reads see projections and database-owned
   tables only through inputs the caller may read; only the engine writes
   managed rows. On SQLite the same projection gives SQL reporting its
   indexes.
4. **The server half is TypeScript outside the transaction.** Quarry declares
   an action's or route's arguments and result; TypeScript implements it
   against a generated, typed context; authority is bound when work is
   admitted; `serve` supervises the runtime; one release carries both.
5. **Applications choose the retained surface.** An online-only brief, built by fresh
   agents on the published package beside Convex and Supabase controls,
   measures the gap. The author's 2026-09-16 commission (§14.7) starts the
   service baseline before that record and uses the completed Workroom record
   to remove services rather than waiting to add them. Postgres remains a
   parallel, measured lane, not the critical path.

"Native" already names LLP 3000.005's Rust modules hosted as wasm, so this
document says *database capabilities* where the first draft said native
capabilities.

The author accepted this direction on 2026-09-15 (§14). A one-round panel then
found it sound and five of its contracts too loose; §15 records the
disposition, and the sections below carry the revised contracts. Spellings
remain illustrative until a language-card trial. No production Postgres,
performance or replacement claim follows from this document. LLP 3000.008's
Implemented status covers its bounded repair program, not this architecture.

## 1. What this revision changes

The first draft (Codex, the same day) drew the right boundaries: Quarry for
managed data, TypeScript outside transactions, no SQL writes into managed
tables, one commit order until a replacement earns its guarantees, and durable
work without a fictional exactly-once. Those survive. Four directions change.

| First draft | This revision | Reason |
| --- | --- | --- |
| Lower data fragments to backend-specific plans; qualify each against the interpreter; fall back where equivalence is unproven. | One executor. The boundary batches access through transaction-scoped prefetch (§4.2). | The measured cost is a per-row loop: 68 calls for a 32-room inbox, 5 for a 20-row page. Batching removes it without a second implementation of rules, expressions, completeness and meter charges in two SQL dialects. |
| Postgres "should evaluate typed per-table columns"; managed data read natively through a qualified read adapter. | The generic layout for managed data on both stores; typed tables only as projections (§4.3, §6.1). | Typed managed layouts make every schema successor DDL and every index component a dialect question. Projections pay that cost only where an application asks, and stay live-invalidatable because only the engine writes them. |
| Six increments, with a substantial application last. | An online-only comparison brief that measures the gap, rerun after increments; Postgres in parallel (§10). | "Chosen over Convex and Supabase" is a comparison. Snapback 4 has improved fastest when a builder record chose the work (LLP 3000.007 §10). |
| General obligations stated for every boundary. | Concrete declarations, a prefetch contract, a projection contract and one instrument; the durable-work, webhook, restore and verification obligations kept in compressed form. | A concrete form can be trialled, reviewed and refused; a general obligation cannot. |

## 2. The goal and the evidence

### 2.1 What the comparison says so far

The last comparison with Convex and Supabase controls was the Snapback 2
Clique wave of 2026-09-05 (LLP 3000.007 §2.4): Convex 81, Snapback 2 66,
Supabase 62. Snapback 2 won authorization and offline; it lost queries and
live (60 against 85), client integration (59 against 79), setup and docs (55
against 79), operations (53 against 76) and scale (62 against 80). Supabase's
best dimension was data modeling (88). Snapback 4's Clique calibrations since
(Astra medium, N = 1 per pin, same-family scoring) run holistic 86 to 91, on
the application its model was designed around. Snapback 4 has no record of an
ordinary online-only application, and none with a Convex or Supabase control.

### 2.2 What exists, and what an ordinary application still misses

| Area | Snapback 4 today | Missing |
| --- | --- | --- |
| Data programs | Quarry queries and mutations with rules, maintains, seeks, `group`, helpers and `where`; jobs; native jobs and reads (LLP 3000.005, 3000.007) | Reporting over whole populations; application SQL reads admitted on 2026-09-16 (§14.4), implementation pending in D |
| Server code | Worker actions with durable admission, leases, retries and request-principal sessions ([actions card](../snapback4/crates/snapback4-lang/src/guide/actions.rs)) | Declared results (today `unknown`), authority bound at admission, a server context, HTTP routes, webhooks, scheduled actions, production supervision |
| Identity | Guests, password accounts, service seats, sessions a service mints | OIDC and OAuth sign-in, email verification and recovery, an organizations recipe |
| Files | Image and video assets (JPEG, PNG, WebP, MP4) with one home row | Arbitrary files, resumable upload, processing |
| Live and realtime | The online client re-runs a watched query when a commit touches a table it read; `connected[p]` | Invalidation narrower than a table; ephemeral channels |
| Search | Word-prefix `words()` and `matching`, on server and device | Relevance full-text, vector, geo |
| Operations | `deploy` and `rollback` on a stopped server; `sql` inspection; a stopped-copy restore procedure (LLP 3000.008.004 §8) | A managed database, point-in-time recovery, failover |
| Storage | SQLite, one server process | Postgres |

### 2.3 What the Postgres experiment established

The [experiment](../snapback4/experiments/postgres/README.md) runs compiled
Quarry, rules, maintains, receipts, whole-commit sync and the unchanged device
over Postgres 16, with ten passing tests. Medians from its 1,000-iteration run
on one Apple M5, over a Unix socket:

| Workload | SQLite | Postgres adapter | Postgres calls |
| --- | ---: | ---: | ---: |
| Rule-filtered point read | 0.0057 ms | 0.117 ms | 5 |
| Ordered 20-row page | 0.0248 ms | 0.164 ms | 5 |
| 32-room inbox with maintained totals | 0.138 ms | 1.894 ms | 68 |
| Increment, receipt and sync commit | 0.054 ms | 0.441 ms | ~18 |

A hand-written relational join over separately seeded tables returns the
inbox's values in 0.082 ms without Snapback's rules, meter or completeness: a
lower bound, not a Snapback query. Four writers committed about 2,500
operations per second on serialized Postgres and 14,000–15,000 on SQLite in
the same cell (1,800–2,400 and 4,700–7,800 in the shorter run); serializable
Postgres execution retried on the shared commit head and was slower. These
settings do not establish identical durability, so no number here is a
cross-store ranking. A 6,000-byte indexed text fits SQLite's layout and
exceeds Postgres's B-tree entry limit.

Read as causes:

1. **The semantics transfer.** Nothing in the application contract had to
   change for Postgres.
2. **The cost is a loop of round trips, not the storage format.** The inbox's
   68 calls are BEGIN, the sequence read, one page scan, 32 maintained-total
   lookups, 32 rule-probe lookups and ROLLBACK.
3. **Postgres buys neither read latency nor write throughput as built.**
4. **The shared key layout has a physical limit SQLite lacks.**

So Postgres's value to an ordinary application is not speed. It is operator
trust (a managed database, point-in-time recovery, replicas and failover), the
extension ecosystem, SQL tools, and eventually more than one server process
over one store. None of those requires Quarry to execute as SQL.

### 2.4 A production design point

Convex runs its own query engine over indexes it maintains, and a single
committer assigns commit order ([How Convex
Works](https://stack.convex.dev/how-convex-works)). Its Postgres persistence
keeps serialized documents and encoded index keys in two shared tables with no
per-application relational DDL, with columns for a key's prefix, suffix and
hash
([`crates/postgres/src/sql.rs`](https://github.com/get-convex/convex-backend/blob/main/crates/postgres/src/sql.rs)).
Its subscriptions re-run a query when a commit overlaps the query's read set.
That shows the shape proposed in §4 is viable for a general-purpose backend.
It does not show that the shape is right for Snapback, and nothing here relies
on how Convex orders long keys; the measurements of §10 decide.

## 3. The application model

| Operation | Meaning | Where it runs |
| --- | --- | --- |
| Query | A read of one consistent snapshot, with truthful completeness | Server; a device when every read site is held |
| Mutation | One atomic change to managed state, judged by the server | Server; predicted on a device when eligible; queueable offline |
| Action | Ordinary TypeScript that may perform I/O, with no transaction | The server runtime; never queued by the SDK |

An action calling two mutations performs two transactions. A job remains an
atomic, chunked data program; a scheduled action is an action.

A restriction applies only where its reason applies. Device execution
restricts what runs on a device; audience inversion restricts what syncs;
authorization and the meter restrict everything (LLP 3000.007 §3.1). The
language remains one spelling, and where an operation runs is computed, not
chosen (LLP 3000.007 §4). An operation runs as its caller unless it is
declared to run as a service seat: running on the server is not running
trusted.

| Owner | Owns | Never owns |
| --- | --- | --- |
| Core (Rust) | Values, schema, rules, Quarry semantics, the meter, atomic commits, receipts, commit order, the partition log, work records and their authority, projection writes | Provider calls, application JavaScript, object bytes |
| Store adapter (SQLite, Postgres) | Transactions, physical layout, access pushdown and batching, durability settings, projection and database-owned DDL | Rules, expressions, completeness, meter charges |
| Server runtime (Node) | Action and route handlers, provider SDKs, invocation leases, streaming responses | Any write to managed data except through a mutation; any credential for managed tables |
| Device (Rust, native or wasm) | Acquired partitions, the same interpreter, the outbox, local observation | Authoritative admission, effects, server-only facts |

The four ship as one release and need not share a process. An online-only
client loads no device runtime (`createClient`), as today. Imports and repairs
of managed data use managed writes or an explicit maintenance procedure that
rebuilds derived state; a database connection is never an application write
path.

## 4. One executor, two stores

### 4.1 Push down access, never semantics

The boundary beneath the interpreter (`Rows`, `PartitionRows`) may give a
store more to do at once: a batch of point reads, a batch of rule probes,
several bounded scans, a count, a mutation's commit tail in one flight. A
store answers with whatever SQL it likes. A store never evaluates a rule, an
expression, a shape, a filter, a completeness class or a meter charge.

This keeps LLP 3000 §7's "one implementation, in Rust" true on the server. No
dialect's null, collation, overflow or error order enters the data plane. The
conformance corpus, the simulator and the device suites qualify Quarry once.
An adapter is qualified by a small access contract — the rows a seek, scan or
batch returns, in key order, at the transaction's snapshot — testable against
`MemoryRows`.

### 4.2 Transaction-scoped prefetch

Prefetch is a physical cache in front of the store. It never caches the answer
to a Quarry read.

1. **Marking.** A compiler pass beside the page plan (`engine/pages.rs`)
   marks, for each page-producing loop, the point reads in its body whose keys
   are *total* expressions of the row: field paths of the loop binding,
   literals, `viewer`, arguments, and aliases of those that are never
   reassigned. In the inbox, `totals[.room]` lowers to
   `Get(totals.byGroup[$row.room])`. The pass also marks the read-rule probe
   each marked read will make when the probe's key terms are pinned the same
   way. The first cut does not mark:
   - arithmetic, calls, or anything that can fail or allocate;
   - reads keyed on another read, and reads inside `where` filters;
   - word lanes (`matching`), merges, and reads of tables with `expire at`.

   The plan is a side table keyed by read site, so the serialized IR and the
   corpus do not change.
2. **Filling.** After the interpreter fetches a page and before it runs the
   loop body, the runner hands the store the marked key sets. The store
   answers the exact `Rows::get` and `Rows::lookup` calls those keys would
   make — row image and stored key, at the transaction's snapshot — in one
   flight (`= ANY`, `unnest` joins, or a pipeline). The flight runs under a
   savepoint, so a failed fill is rolled back and leaves the cache empty.
   Filling evaluates no expression, runs no rule, charges no meter, attributes
   no site and raises nothing.
3. **Reading.** The interpreter then runs exactly as it does today. Every
   read, rule check, expiry walk, live aggregate and meter charge happens where
   and when it happens now. A `Rows` call whose exact arguments are cached
   gets the cached answer; any other call goes to the store. A cut leaves
   filled entries unread and uncharged.

The cache belongs to one transaction. It is dropped at commit and rollback,
cleared at every savepoint rollback (the conflict re-read included), never
held by a pooled connection, never shared across principals and never logged.
A write to a table drops that table's entries. The cache has a byte budget of
its own, and a fill that would exceed it is skipped. SQLite and the device
keep prefetch off.

Results, refusals, cursors, completeness, meter observations and cut sites are
the same with prefetch on and off. The interpreter's sequence of logical reads
does not change, and each cached answer is the store's answer at the same
snapshot. Physical work may exceed logical work by one page of marked reads,
within the byte budget. Hidden rows are read physically and never returned by
the interpreter, as today; Snapback claims no constant-time behavior (LLP
3000.007 §8.7). Qualification is a differential run on Postgres, not an
inference from SQLite (§11.1).

The inbox should fall from 68 calls to under ten. That is an estimate. C1
measures it against SQLite's 0.138 ms and the 0.082 ms lower bound (§10.2).

**Writes.** A mutation's writes cannot all wait for its end. Maintains read
totals the same transaction just changed; final-existence checks read the
program's result; unique checks read earlier inserts (`engine/write.rs`,
`engine/maintains.rs`). Batching program-time writes therefore needs one of
two things:

- a read-your-writes overlay over point reads, index scans, counts, deletions
  and constraints that preserves the order of errors and charges; or
- a flush of buffered writes before the next read that could observe them.

That is increment C2, taken only if C1 shows program-time writes dominate. The
commit tail needs neither: the head update (using the sequence the head lock
already returned), commit record, log events, effect admissions and receipt
follow the program's last read. C1 sends them as one pipelined flight.

### 4.3 Layout

- Managed data keeps the generic layout on both stores: canonical row images
  and order-preserving index keys, the bytes a device scans (LLP 3000 §7, "one
  key encoding"). Schema successors stay logical; none becomes DDL on a live
  table. The Postgres adapter may partition its row and entry tables by
  logical table for vacuum and maintenance.
- **Long keys.** Postgres limits a B-tree entry to a fraction of a page;
  SQLite does not. Every index key has one portable bound, checked by `check`
  on both stores so a schema stays portable. The bound covers the encoded
  composite of its components and the id, word entries included. A column that
  could exceed it needs a declared length, and `check` prints that rewrite;
  the tokenizer caps an indexed word's length on every host.

  C1 sets the bound from Postgres's limit with a margin and keeps the
  counterexample test. A representation that stores over-long keys another
  way (a prefix with a hash, say) is admitted only with a proof, against
  `MemoryRows`, that it preserves full key order. None is proposed.
- Typed, natively indexed tables exist only as projections (§6.1).

### 4.4 One commit order

A watermark is a position in one total order of commits per store, and no
earlier commit may appear below a position a device has passed. Both stores
keep that order. A Postgres sequence allocation is not commit order; the
transactional head is (LLP 3000 §7).

Throughput comes first from making each ordered commit cheaper: prefetched
reads, the pipelined commit tail, and group commit where durability settings
allow. Whole-commit atomicity does not by itself rule out publishing by scope
— the log already records one commit as rows per partition. So a
commit-ordered publication stage, or ordering per scope, remains an open
design. It is taken up when a named workload's measured commit rate needs it:
- the brief's write mix;
- a disjoint-writer mix;
- the busiest application store a managed deployment hosts.

C1 measures serialized and serializable execution against those mixes. Group
commit does not remove the head lock, so more than one server process over
one store still serializes writers. An infrastructure retry repeats the whole
operation with its ids and deterministic inputs, and rereads every fact.

### 4.5 What the abstraction gives up

The author asked what large wins an abstraction over SQLite and Postgres
loses. On this design there are two:

1. **Cost-based planning of Quarry.** Quarry reads are metered, bounded pages
   by design, where a batch recovers most of the round-trip cost. The read
   that needs a planner — an unbounded join or aggregate for a report — is
   written as SQL over authorized projections (§6.2) or computed by a job.
2. **Write parallelism beyond one committer.** One ordered committer on SQLite
   measured 14,000–15,000 commits per second in the experiment's longer
   four-writer run, and Convex serves general-purpose applications through
   a single committer. §4.4 names the path past it.

Operations, extensions and SQL tools survive the abstraction.

`dev` stays zero-install on SQLite unless the application requires Postgres
(§6.4). A store moves between SQLite and Postgres by an explicit export and
import of rows and log, never by a configuration change.

## 5. The server half

### 5.1 Declared actions and routes, typed handlers

Increment A spellings:

```quarry
action summarize(doc: documents, revision: int) returns { summary: summaries }
route billing: post "/hooks/billing" as service:billing secrets [BILLING_SIGNING_KEY] wait 5s
```

```ts
// snapback/server.ts; model and billing are the application's provider SDKs
import { GiveUp, Retry } from "snapback4/worker";
import { api } from "./generated/api";
import { server } from "./generated/server"; // built by check and dev, never committed

export default server({
  actions: {
    async summarize({ doc, revision }, ctx) {
      const source = await ctx.query(api.documentAt, { doc, revision }); // the caller's rules, at the requested revision
      if ("denied" in source) throw new GiveUp(source.denied.message);
      const text = await ctx.step("model", { doc, revision }, (key) =>
        model.summarize(source.data.text, { idempotencyKey: key })); // outcome persisted; a rerun returns it
      const saved = await ctx.mutate(api.saveSummary, { doc, revision, text },
        { id: ctx.writeIdFor("save") }); // one write id per durable step
      if (saved.state !== "sent") throw new GiveUp("the summary was not saved");
      return { summary: saved.result.id }; // an id: current rules decide who reads the row
    },
  },
  routes: {
    billing: {
      async verify(req, { secrets, signal }) {
        return billing.verify(await req.rawBody(), req.headers,
          secrets.BILLING_SIGNING_KEY, { signal }); // exactly true or false; no database context
      },
      async handle(req, ctx) {
        const event = billing.decode(await req.rawBody());
        const saved = await ctx.mutate(api.applyBillingEvent, event,
          { id: ctx.writeIdFor("apply") }); // the mutation deduplicates event IDs and checks revisions
        if (saved.state === "pending") throw new Retry("the write is uncertain");
        if (saved.state !== "sent") throw new GiveUp("the event was refused");
        return new Response(null, { status: 204 });
      },
    },
  },
});
```

- **One declaration, three uses.** Quarry declares argument and result types.
  `check` generates the client's typed `Action<A, R>` and the handler's
  signature from that declaration. Admission validates arguments and
  settlement validates the result. A result that fails validation fails the
  invocation terminally: its effects may already have happened, so it is never
  retried automatically.
- **The context.** `ctx.query` and `ctx.mutate` run under the invocation's
  authority and return the card's `Read` and `Write` states, replay-aware as
  LLP 3000.007 §8.1 requires. No transaction spans two calls. The context also
  offers `ctx.principal`, `ctx.invocation` (id, attempt, deadline,
  cancellation), `ctx.secrets`, `ctx.step`, `ctx.writeIdFor` and, later,
  `ctx.files` (§7). There is no `ctx.sql` in increment A.
- **Authority is bound at admission.** A caller-authorized invocation records
  the session that admitted it, that session's refresh chain and its deadline.
  - A claim runs only while that authority stands. Revoking the session,
    logging out everywhere or revoking the principal fails the invocation with
    a typed refusal instead of minting a new session.
  - A lease never outlives the originating session.
  - Service-authorized work names its seat, and a scheduled action runs as a
    declared service seat, never as a caller.

  At the proposal baseline, claims minted sessions from stored principals,
  so queued work could outlive revocation. A1 now binds admission authority
  and fences claims/collection; A2 also fences transitive delegated chains
  and scheduled service seats. The qualification is recorded in §10.2.
- **Results.** Collecting a settled result requires the originating authority
  to stand. A result is data the handler chose to return to that caller.
  Content derived from protected data belongs in a managed row, returned by
  id, so current rules decide who may read it later.
- **Ids are bound to what they admit.** Admission binds an id to its operation
  and a digest of its arguments, for actions and mutations alike. Reusing an
  id for another operation or other arguments refuses with a typed code.
  A1 replaced the proposal baseline's principal/operation-only action replay
  and principal/id-only mutation replay with these payload bindings on
  SQLite. C3.1 now binds mutation replay in the Postgres evaluation executor;
  this is not yet a production-Postgres work-record claim.
  `ctx.writeIdFor(label)` derives a write id
  deterministically from the invocation and the label, in `mintId()`'s form.
- **Steps.** `ctx.step(name, input, fn)` persists each external step's outcome
  under the invocation, with a digest of its input and a stable idempotency
  key.
  - A rerun returns a completed step's outcome.
  - A changed input for the same step refuses.
  - A step with no recorded outcome reconciles through its key or parks
    (§5.2).

  It is a record per step, not a workflow engine.
- **Routes.** A route is declared and bound to a handler; exporting a function
  never publishes one. It authenticates by session, or runs as a declared
  service seat whose separate verifier checks a provider signature over raw
  bytes, without delegated database authority. Each delivery verifies afresh,
  including retries of settled work; an invalid request cannot reserve a body
  digest or collect a prior response. False returns 403; unavailable verification
  returns 503. Unverified tickets are bounded and ephemeral, not work records.
  - After authentication the core admits a route request durably before its handler runs, keyed by
    route and a digest of its body. A provider's retry of the same delivery
    therefore joins the same invocation. Session routes additionally scope the
    id to principal and originating family. Changed declarations or revoked
    service generations refuse old same-body work rather than re-keying it.
    The first verified envelope is retained, with Authorization,
    Proxy-Authorization, Cookie and development-persona headers removed before
    durable storage and handler dispatch. Other headers and body bytes are work
    payloads; only the body is byte-exact.
  - When the invocation settles within the route's wait, the core returns the
    handler's response. Otherwise it answers 503, and the provider's retry
    collects the settled response.
  - Plain `GiveUp` application refusals are recorded and acknowledged with a
    bare 204. Infrastructure failures answer 5xx; explicit handler 5xx responses
    retry under the work policy, never settle as successful cached responses.
    Invalid/oversized responses fail terminally after possible external I/O.
  - A stream is not a completion receipt, and a disconnect does not undo
    admitted work.
  - Under `dev`, declared routes accept a non-loopback peer, and only declared
    routes do. The default listener stays loopback; explicit `--bind` uses the
    same cleartext acknowledgement as `serve`. Core development doors keep
    their loopback Host, Origin and peer requirements.
  - A3 is bounded static POST, with no query strings/captures or streaming
    forwarding: 64 KiB request/response bodies, 64 headers/16 KiB, a default
    5s route wait (1ms–25s, including verification), and at most 10s to buffer a
    handler Response, shortened by invocation cancellation. Sixteen ingress
    waits cannot consume the 4 verification-poll, 4 generated-registry-poll,
    32 legacy worker/long-poll or 32 short-request slots. Generated actions
    share one name-set poll loop grouped by session lifetime; it and the
    verifier loop rotate through chunks of at most 128 names, with at most
    1s waits when there are multiple chunks. Idle named handlers cannot
    occupy the capacity needed to verify or execute admitted route work.
- **Secrets.** A release declares the secret names each action and route may
  read. `serve` resolves them from its environment or secret store and passes
  only those to the runtime; logs redact them. The runtime's environment is
  constructed explicitly, never inherited from the core's process.
- **Coupling.** The runtime reaches the core only through the claim protocol,
  over HTTP, so a hosted pool can replace the supervised process.
- **Correlation.** `why <id>` follows one invocation from request through
  admission, claims, attempts and commits to settlement, without protected
  row contents.

### 5.2 Schedules and durable work

- A schedule may name an action as well as a job; the action runs as the
  schedule's declared service seat. An effect `emit`ted by a mutation remains
  the transactional way to start external work.
- Actions, effects and scheduled actions share one lifecycle. Each carries a
  stable id bound to its operation and payload, release version, authority,
  due time, attempts, a fenced lease and an outcome, and `doctor` and `why`
  inspect it.
  - Retries, backoff, deadlines and cancellation are per-operation settings;
    §12 records the scope change.
  - Retention and deduplication windows are documented, and an expired id is
    never silently accepted again.
- A provider request uses the step's stable idempotency key, never an attempt
  number. Suppose a worker dies after a provider accepted a request and before
  the step's outcome was recorded. The lease fences the old attempt, and the
  successor reconciles through the key. Work whose provider can neither
  deduplicate nor be queried parks for an operator instead of repeating.
- Long workflows are persisted state and resumable steps, never checkpointed
  JavaScript stacks. Cancellation is cooperative for work in flight;
  compensation is application logic.
- A report too large for a request reads a declared cutoff over immutable or
  append-only rows, or says it is approximate. A job that pages across commits
  does not freeze mutable sources.

### 5.3 Supervision and isolation

`serve` supervises the runtime as `dev` does today: start, restart with
backoff, correlated logs, stop with the server. A hosted worker pool may
implement the same claim protocol later. Application TypeScript is trusted
application code in its own process, isolated from the core and never a
sandbox for end-user programs. A declared capability list is not proof that it
cannot reach the network. It receives no credential for managed tables.

## 6. Database capabilities

### 6.1 Projections

```quarry
table places:
  name: text <=200
  latE6: int
  lngE6: int
  read <- public
  project places_geo { id, name, lat_e6: .latE6, lng_e6: .lngE6 }   -- proposed
```

```sql
-- snapback/sql/migrations/0001-places-geo.sql, applied at activation (Postgres with PostGIS)
ALTER TABLE places_geo ADD COLUMN location geometry
  GENERATED ALWAYS AS (ST_SetSRID(ST_MakePoint(lng_e6 / 1e6::float8, lat_e6 / 1e6::float8), 4326)) STORED;
CREATE INDEX places_geo_location ON places_geo USING gist (location);
```

- A projection maps each row of one managed table to one row of scalar
  columns computed by Quarry expressions of that row. The interpreter computes
  the values; the adapter writes them.
- **Maintenance.** The engine writes a projection inside every managed commit
  that changes a projected column of the source — insert, update, delete,
  expiry sweep — and backfills it with a job when it is first declared.
  - A projection write that fails aborts the commit. At every commit, a
    projection is exactly its source.
  - Projection writes are charged to the mutation that causes them.
  - A commit that writes a projection names its source table as touched, so
    observations over the projection are invalidated with the source.
- The engine keeps each projected row's lifetime beside it, even when the
  projection does not select the `expire at` column.
- **Migrations.** Database migrations may add generated columns, non-unique
  indexes and extension types to a projection table. They may not add unique
  or exclusion constraints, triggers, rules, foreign keys or write grants.
- A projection is as sensitive as its source. It is server-only, never syncs,
  and changes nothing a device holds.
- It exists on both stores: a typed SQLite table (with FTS5 where wanted) or a
  typed Postgres table.

### 6.2 SQL reads

```quarry
query nearby(latE6: int, lngE6: int): sql reading places_geo returning places   -- candidates over a public projection
query revenue(org: orgs): sql channel reading orders_facts returning list { month: time, cents: int }
  require exists memberships[org, viewer, 'admin'] else FORBIDDEN               -- a declared channel
```

```sql
-- snapback/sql/nearby.sql
SELECT id FROM places_geo
ORDER BY location <-> ST_SetSRID(ST_MakePoint(:lngE6 / 1e6::float8, :latE6 / 1e6::float8), 4326)
LIMIT 50;

-- snapback/sql/revenue.sql
SELECT date_trunc('month', placed_at) AS month, sum(cents) AS cents
FROM orders_facts WHERE org = :org GROUP BY 1 ORDER BY 1;
```

- **Scope.** A SQL read is a server-only query in the store's dialect. It
  never reads the managed row and entry tables, the log or receipts. It
  declares the relations it reads, and the store enforces the declaration: a
  per-operation grant on Postgres, SQLite's authorizer. It runs read-only,
  with bound parameters, a statement timeout and a row limit — guardrails,
  labelled as such, not the meter (LLP 3000.002).
- **Authorized inputs.** A SQL read sees only rows its caller may read, before
  it selects, orders or limits anything.
  - It reads a projection of a public table directly.
  - It reads a projection of a rule-filtered table only through a per-viewer
    view the compiler generates from a read rule it translates exactly:
    `.col = viewer`, or `exists t[.a, viewer]` over a projection of `t`. The
    view is tested differentially against the interpreter's rule.
  - It reads a database-owned table only through the declared key that ties
    it to a managed table (§6.3), joined to that table's authorized view.

  Anything else is refused unless the read is a declared channel. "Nearest
  50" therefore means the nearest 50 rows the viewer may see, never 50 rows
  filtered afterwards. Filtering candidates after SQL has run would let
  selection and ordering disclose hidden rows.
- **Results.** A read returns either ids of one managed table, or computed
  values. Ids are read under that table's read rule in one prefetched batch
  and returned in the SQL's order, as a page that says `complete: false`,
  since its extent is the SQL's rather than a prefix Snapback decides.
- **Declared channels.** A read whose inputs are not all authorized that way
  must say `channel`.
  - `check` refuses it unless every parameter its `require` prelude guards is
    bound in the SQL text.
  - `check` lists every channel beside readable maintains (LLP 3000.007 §8.7
    (g)).

  The compiler cannot prove that the SQL stays within what the prelude
  guarded; the marker, the listing and cross-principal leak tests make that
  responsibility explicit. Channels ship after candidates.
- **Expiry.** Views hide rows past their lifetime by the operation's clock,
  passed to the transaction as a parameter. They never use the database's
  `now()` or the activation time.
- **Liveness.** A SQL read is live only when its whole dependency set is known
  and invalidatable:
  - the source tables behind its relations;
  - the rule tables behind its views;
  - its prelude's reads;
  - the read rules of the rows it returns;
  - the next expiry among them.

  It must also use only functions the host lists as stable. Any other SQL
  read is one-shot, and the host refuses to observe it. Reads of
  database-owned tables are one-shot, since no managed commit writes them.
- **Portability.** A Postgres-only function or extension requires §6.4's
  declaration. A SQLite-backed application writes SQLite's dialect. Moving an
  application between stores ports its SQL reads explicitly.

The author admitted LLP 3000.007 §10.3's recommendation for application SQL
reads on 2026-09-16 (§14.4). Its §9.1 named three costs, and this form answers each:
- Generated views could not use the secondary index; projections carry
  native indexes.
- Authorization needed a second translation; views are generated only for
  rules that translate exactly, and are tested against the interpreter.
- The SQLite instruction meter was approximate; the limits are labelled
  guardrails.

This is the admitted form on both stores; implementation remains increment D.

### 6.3 Database-owned tables

- They are created by database migrations in a separate schema and written
  only by actions, through `ctx.sql`, under a role that can write nothing
  else. SQL reads read them.
- A database-owned table that holds data derived from a managed table declares
  that table as its key, for example `owned document_vectors keyed by
  documents` (proposed). SQL reads see it only joined to the viewer's
  authorized view of the keyed table; an undeclared database-owned table is
  readable only by declared channels.
- They are never managed: no rules, sync, maintains or receipts. Whatever
  clients should see live or offline is published into a managed table by a
  mutation carrying a source version, eventually and explicitly.
- A database write followed by a mutation is two transactions. No bridge that
  writes managed rows from SQL is proposed; one would have to capture every
  trigger and cascade and enforce rules, maintains, receipts and whole-commit
  sync inside the database.
- For example, an action computes embeddings with a model provider and stores
  them in a pgvector table keyed by `documents` and revision. A SQL read
  returns the candidate documents the viewer may read, ordered by similarity,
  as a one-shot answer.

### 6.4 Requirements and credentials

```quarry
requires postgres >= 16 with postgis, vector   -- proposed
```

- `check` knows the declared target and refuses a Postgres-only construct
  against SQLite, naming the requirement. `dev` runs such an application
  against a configured local Postgres. `deploy` checks the server version,
  extensions, roles and migrations before activation.
- Only the core holds the role that writes managed tables and projections. SQL
  reads use per-operation read grants over authorized views; `ctx.sql` uses
  the database-owned write role. The `sql` inspection verb (LLP 3000.007 §8.8)
  is never an application surface.

### 7.1 Observation narrower than a table

Today a watched online query re-runs whenever a commit touches a table it
read. That is correct but coarse: every write to `messages` re-runs every
watched query over `messages`.

The interpreter knows each read's table, index and key range. The server can
keep an observation's read set and notify a client only when a commit's
changed keys overlap it, as Convex's subscriptions do. Key ranges stay on the
server, because a key can name a hidden row.

Measure invalidation fan-out on the brief's workload before building it
(increment E, not A or C). With more than one server process, commit
notification and presence must also cross processes, through Postgres
`LISTEN`/`NOTIFY` or a polled commit table.

## 8. Locality stays optional

- A table without `sync` is online-only, and an online client loads no device
  runtime.
- A `sync` line requests an authorized replica with a horizon. `check
  --residency` computes where each operation runs and whether a mutation
  predicts (LLP 3000.007 §6); queueable, predicted and accepted remain
  distinct.
- Actions, routes, SQL reads, projections, database-owned tables and presence
  never run on a device. Nothing in §4–§7 changes what a device holds or how
  its writes are judged; the experiment's device already acquires, predicts
  and settles from Postgres pages (§2.3).
- A rule or capability change that would make an existing replica unsafe is
  refused or requires an explicit transition. A device learns of revocation
  on reconnect; retroactive secrecy is not promised.

## 9. One release, evolution and recovery

- **The release** carries the schema and programs, handlers and routes, SQL
  reads, database migrations, requirements and secret names; secret values
  are references. The candidate is validated before admission switches, and
  the stopped activation model remains the first target (LLP 3000.008.004
  §4).
- **Activation fencing** belongs to the store, as a lock held in the database,
  not a lock file in a deployment directory. Two hosts or directories that
  target one Postgres store therefore cannot activate at once.
- **Queued work** records its handler contract. A deploy drains it, keeps a
  compatible executor, migrates it explicitly, or refuses; it never feeds an
  old payload to new code. Leases and credentials are fenced across
  activation.
- **Projections.** A projection added to an existing table backfills in a job
  before its SQL reads are admitted. A removed projection's table is dropped
  at activation.
- **Backup and restore** cover the database, release identity, database-owned
  schema, object bytes, durable work and deduplication state. Restoring an
  earlier point creates a new store incarnation: old device resumes are
  fenced, uncertain work is quarantined, and provider effects are reconciled
  before redelivery. Point-in-time recovery neither restores object bytes nor
  unsends an email.
- **Correlation.** One path runs from request to operation, commit, work
  attempt and delivery, without protected row contents by default; waits,
  contention and refusals are diagnosable.
- **The managed service** gives each application store its own Postgres
  database until its child LLP decides otherwise. No two applications then
  share a commit head, a role or a projection namespace.

## 11. Verification obligations

These carry forward LLP 3000.003's open cross-host questions. Its historical
defects are not reopened by being cited.

1. **One meaning on every host.** The corpus, simulator and device suites run
   on both stores. Prefetch is qualified by a differential run on Postgres,
   not by leaving SQLite without it. Every outcome field must be identical
   with prefetch on and off, with a meter cut forced at every charge position:
   - data, completeness, cut sites and cursors;
   - every meter field, the tables touched and the next expiry;
   - refusals and their sites.

   The run covers hidden rows, early cuts, unmarked expiring maintains and
   values past the byte budget.
2. **The access contract.** Every seek, scan, count and batch on Postgres
   returns SQLite's rows in key order at the snapshot. The cases include keys
   at the portable bound, nulls and word entries. A named unsupported case
   never counts as a pass.
3. **Atomic commits and ordered publication.**
   - Fail after every durable write.
   - Contend on related and disjoint rows.
   - Repeat operation ids.
   - Delay an earlier commit while later ones finish.
   - Have two hosts activate one store.

   No change may be skipped, duplicated or reordered through a real database
   restart, and a restore fences old resumes.
4. **Authorization across boundaries.**
   - Revocation, logout-all and expiry between admission and claim.
   - Result collection after revocation.
   - Id reuse with other arguments or another operation.
   - Generated views checked against the interpreter's rules.
   - Cross-principal leak attempts through channels, views, expiry and errors.
   - SQL roles that cannot read managed tables or write projections.
5. **Durable external work.**
   - Crash before a provider accepts a request, and between its acceptance
     and a step's recorded outcome.
   - Acknowledge webhooks only after admission.
   - Distinguish a retry from new intent.
   - Park what a provider can neither deduplicate nor be queried about.

   Test doubles are labelled, and a real-provider path precedes advertising an
   adapter.
6. **Real hosts.** Actual browser and native reopen, session replacement and
   persistence, as LLP 3000.008.004 requires. Simulation is not proof of a
   real host.
7. **Evolution and restore.** Deploy with pending work and old clients;
   migrations and projection backfills; an isolated restore with files,
   database-owned data, and fenced workers and devices.
8. **Generality.** The brief's records, not demos: workaround code,
   infrastructure the builders invented, correction loops, and the controls'
   results.

No new blocking gate, exact-HEAD battery or performance ratchet follows. The
Postgres suites run on a schedule, as `scripts/test-postgres.sh` runs today.

Revisit this design if any of these happen:
- the brief's builders still need a second backend for ordinary features;
- prefetch leaves Postgres page workloads outside the stated multiple of
  SQLite;
- generated views cannot be kept equal to the interpreter's rules;
- routine reporting keeps moving to SQL for want of Quarry forms rather than
  for database facilities;
- one commit order limits a named workload.

## 13. Alternatives considered

- **Lower Quarry fragments to SQL** (the first draft). This gains planning for
  joins and aggregates. Each lowering reimplements rules, expressions, null,
  collation and overflow behavior, completeness and meter charges in two
  dialects, qualified against the interpreter or abandoned to the fallback.
  The meter's charges and cut are defined in interpreter order, which a
  cost-based planner does not follow. Snapback's reads are bounded pages by
  design, where batching recovers the round trips; the read that needs a
  planner is better written as SQL over authorized projections. Reconsider if
  prefetch fails on a measured workload.
- **A typed per-table layout for all managed data on Postgres.** Better for
  SQL tools and planning, at the cost of DDL for every schema successor and a
  dialect question for every index component. Projections provide it where an
  application asks.
- **Postgres as the only server store.** One server store, with the ecosystem
  by default. It gives up the zero-install binary behind `dev`, the loop bar
  and small deployments, and the author asked for both stores.
- **SQLite only, with Postgres as an external database the runtime calls.**
  The cheapest path. Specialist data stays outside the managed commit, and an
  operator who wants a managed database has no target. It is the fallback if
  increment C stalls.
- **TypeScript queries and mutations.** Familiar to agents, but it reopens
  JavaScript in the transaction and on the device, which the scope fence and
  the security review refuse. LLP 3000.007's relaxation is the measured
  answer; the brief will show whether data-program authoring is still the
  loss.
- **Build the platform, then an application.** This risks services no builder
  needed. The brief measures the gap first.

## 16. Code review 2026-09-16: worker credential trust (research)

This section records the current implementation and an unresolved direction,
not a new author ruling or expansion of the accepted increments. At `a0d48a4`
the server authenticates any service token for action/effect claims, provider
verification and account session mint/revoke. The generated supervised runtime
uses `service:worker` even when a route is declared `as service:billing`.
Tests deliberately exercise that combination. Delegated data access still
uses the admitted principal and its standing authority.

Grok classified cross-seat verification/claims as defects; Sol identified the
same paths but recognized the deliberate worker contract. Lead adjudication:
there is no implemented per-seat worker ACL to bypass. The current credential
is deployment-trusted, while the seat name governs the principal of direct
or admitted data operations. Documentation must say that plainly. Issuing such
a token to a partially trusted provider would grant more authority than its
row-rule principal suggests. See [the trust-boundary ticket](../issues/20260916-snapback4-service-worker-trust-boundary.md).

If isolated integrations become a requirement, separate worker execution,
route-verification, identity-administration and data-plane capabilities. Scope
claims and cancellation to declared operations; scope session mint/revoke
independently; bind delegated leases to both caller and worker standing.
Changing only the route comparison to `worker == route.service` breaks the
supported shared runtime and leaves broader authority paths intact. A single
trusted application worker remains the smallest current model; separate
worker processes alone do not narrow credentials.

This choice can require redesign of service-token provisioning, generated
runtime registration and every worker/admin endpoint. It does not require
replacing the interpreter or SQLite. Preserve the existing authority tests
and add wrong-capability claim/verify/cancel/mint cases before claiming
least-privilege worker isolation. The review has not selected or implemented
that new model. The experimental Postgres receipt-binding gap remains a
separate concrete parity defect, not evidence for replacing SQLite.
