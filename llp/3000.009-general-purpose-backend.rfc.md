# LLP 3000.009: A general-purpose backend with optional locality

**Type:** RFC
**Status:** Accepted in direction (2026-09-15: the author's rulings are §14; one panel round precedes implementation)
**Systems:** Snapback 4 product architecture; the interpreter's storage boundary; SQLite and Postgres persistence; the TypeScript server runtime (actions, routes, webhooks, schedules); durable work; database capabilities (projections, SQL reads, database-owned tables); integrated services; optional locality; release and recovery
**Author:** Codex (first draft) and Claude Opus 5 (revision), for Charlie Cheever
**Date:** 2026-09-15
**Revised:** 2026-09-15 (rewritten after a directional review: one executor over both stores with transaction-scoped prefetch instead of lowering Quarry to SQL; Postgres as a persistence target; projections as the only database-native form of managed data; an online-only brief with Convex and Supabase controls first); 2026-09-15 (initial design, grounded in the current authoring surface and Postgres evaluation prototype)
**Related:** [LLP 3000](./3000-snapback4.explainer.md), [LLP 2000.000](./2000.000-keep-the-core-flip-two-substrates.rfc.md), [LLP 3000.002](./3000.002-end-to-end-resource-bounds.research.md), [LLP 3000.003](./3000.003-one-semantics-and-credible-verification.research.md), [LLP 3000.005](./3000.005-native-jobs.rfc.md), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md), [LLP 3000.008](./3000.008-holistic-product-excellence.rfc.md), [LLP 3000.008.004](./3000.008.004-dependable-composition-and-generality.rfc.md), [Postgres evaluation](../snapback4/experiments/postgres/README.md)

## Summary

The author set the goal: "Nearly every ordinary application can use Snapback
as its application backend, while specialist systems can access
Postgres-compatible server-only facilities when needed" — a backend chosen
consistently over Convex and Supabase, agnostic to whether its server keeps
data in SQLite or Postgres.

Snapback 4 already has the distinctive half: one data language with static
authorization and runtime metering, maintained values, durable writes,
partition sync and prediction. For ordinary applications it lacks the server
half — declared action results, HTTP routes and webhooks, a supervised
runtime, identity and file services, operations — and a Postgres story. This
RFC designs both around five decisions:

1. **One executor, two stores.** The Rust interpreter remains the only
   executor of Quarry: on the server over SQLite or Postgres, and on every
   device. The storage boundary pushes down *access* — seeks, bounded scans,
   counts, batches of point reads and rule probes, write flights — and never
   *semantics*. Rules, expressions, shapes, completeness and the meter stay
   in the interpreter. Quarry is not lowered to SQL.
2. **Postgres is a persistence target.** A Postgres-backed server keeps the
   generic row and index layout, one commit order and the same wire. It adds
   operations (a managed database, point-in-time recovery, failover) and
   database capabilities, not a second query engine for Quarry.
3. **Database capabilities reach managed data only through projections.**
   The engine maintains a typed, natively indexed table from a managed table
   inside the managed commit. SQL reads query projections and database-owned
   tables; only the engine writes managed rows. On SQLite the same projection
   gives SQL reporting its indexes.
4. **The server half is TypeScript outside the transaction.** Quarry declares
   an action's or route's arguments and result; TypeScript implements it
   against a generated, typed context; admission is durable; `serve`
   supervises the runtime; one release carries both.
5. **Applications choose the sequence.** An online-only brief, built by fresh
   agents on the published package beside Convex and Supabase controls, comes
   first and is rerun after each increment. Postgres is a parallel, measured
   lane, not the critical path.

"Native" already names LLP 3000.005's Rust modules hosted as wasm, so this
document says *database capabilities* where the first draft said native
capabilities.

This is a Draft design, not an accepted program or a description of the
shipped product. Spellings are illustrative until a language-card trial. No
production Postgres, performance or replacement claim follows from it.
LLP 3000.008's Implemented status covers its bounded repair program, not this
architecture.

## 1. What this revision changes

The first draft (Codex, the same day) drew the right boundaries: Quarry for
managed data, TypeScript outside transactions, no SQL writes into managed
tables, one commit order until a replacement earns its guarantees, and durable
work without a fictional exactly-once. Those survive. Four directions change.

| First draft | This revision | Reason |
| --- | --- | --- |
| Lower data fragments to backend-specific plans; qualify each against the interpreter; fall back where equivalence is unproven. | One executor. The boundary batches access through transaction-scoped prefetch (§4.2). | The measured cost is a per-row loop: 68 calls for a 32-room inbox, 5 for a 20-row page. Batching removes it without a second implementation of rules, expressions, completeness and meter charges in two SQL dialects. |
| Postgres "should evaluate typed per-table columns"; managed data read natively through a qualified read adapter. | The generic layout for managed data on both stores; typed tables only as projections (§4.3, §6.1). | Typed managed layouts make every schema successor DDL and every index component a dialect question. Projections pay that cost only where an application asks, and stay live-invalidatable because only the engine writes them. |
| Six increments, with a substantial application last. | An online-only comparison brief first, rerun after each increment; Postgres in parallel (§10). | "Chosen over Convex and Supabase" is a comparison. Snapback 4 has improved fastest when a builder record chose the work (LLP 3000.007 §10). |
| General obligations stated for every boundary. | Concrete declarations, a prefetch contract, a projection contract and one instrument; the durable-work, webhook, restore and verification obligations kept in compressed form. | A concrete form can be trialled, reviewed and refused; a general obligation cannot. |

## 2. The goal and the evidence

### 2.1 What the comparison says so far

The last comparison with Convex and Supabase controls was the Snapback 2
Clique wave of 2026-09-05 (LLP 3000.007 §2.4): Convex 81, Snapback 2 66,
Supabase 62. Snapback 2 won authorization and offline; it lost queries and
live (60 against 85), client integration (59 against 79), setup and docs (55
against 79), operations (53 against 76) and scale (62 against 80). Supabase's
best dimension was data modeling (88). Snapback 4's Clique calibrations since
(Astra medium, N = 1 per pin, same-family scoring) run holistic 86 to 91, on
the application its model was designed around. Snapback 4 has no record of an
ordinary online-only application, and none with a Convex or Supabase control.

### 2.2 What exists, and what an ordinary application still misses

| Area | Snapback 4 today | Missing |
| --- | --- | --- |
| Data programs | Quarry queries and mutations with rules, maintains, seeks, `group`, helpers and `where`; jobs; native jobs and reads (LLP 3000.005, 3000.007) | Reporting over whole populations; the SQL-reads ruling (LLP 3000.007 §10.3) |
| Server code | Worker actions with durable admission, leases, retries and request-principal sessions ([actions card](../snapback4/crates/snapback4-lang/src/guide/actions.rs)) | Declared results (today `unknown`), a server context, HTTP routes, webhooks, scheduled actions, production supervision |
| Identity | Guests, password accounts, service seats, sessions a service mints | OIDC and OAuth sign-in, email verification and recovery, an organizations recipe |
| Files | Image and video assets (JPEG, PNG, WebP, MP4) with one home row | Arbitrary files, resumable upload, processing |
| Live and realtime | The online client re-runs a watched query when a commit touches a table it read; `connected[p]` | Invalidation narrower than a table; ephemeral channels |
| Search | Word-prefix `words()` and `matching`, on server and device | Relevance full-text, vector, geo |
| Operations | `deploy` and `rollback` on a stopped server; `sql` inspection; a stopped-copy restore procedure (LLP 3000.008.004 §8) | A managed database, point-in-time recovery, failover |
| Storage | SQLite, one server process | Postgres |

### 2.3 What the Postgres experiment established

The [experiment](../snapback4/experiments/postgres/README.md) runs compiled
Quarry, rules, maintains, receipts, whole-commit sync and the unchanged device
over Postgres 16, with ten passing tests. Medians from its 1,000-iteration run
on one Apple M5, over a Unix socket:

| Workload | SQLite | Postgres adapter | Postgres calls |
| --- | ---: | ---: | ---: |
| Rule-filtered point read | 0.0057 ms | 0.117 ms | 5 |
| Ordered 20-row page | 0.0248 ms | 0.164 ms | 5 |
| 32-room inbox with maintained totals | 0.138 ms | 1.894 ms | 68 |
| Increment, receipt and sync commit | 0.054 ms | 0.441 ms | ~18 |

A hand-written relational join over separately seeded tables returns the
inbox's values in 0.082 ms without Snapback's rules, meter or completeness: a
lower bound, not a Snapback query. Four writers committed about 2,500
operations per second on serialized Postgres and 14,000–15,000 on SQLite in
the same cell (1,800–2,400 and 4,700–7,800 in the shorter run); serializable
Postgres execution retried on the shared commit head and was slower. A
6,000-byte indexed text fits SQLite's layout and exceeds Postgres's B-tree
entry limit.

Read as causes:

1. **The semantics transfer.** Nothing in the application contract had to
   change for Postgres.
2. **The cost is a loop of round trips, not the storage format.** A page is
   one scan; the inbox evaluates `{ room, total: totals[.room] }` once per
   row, and each of those reads is a separate call.
3. **Postgres buys neither read latency nor write throughput as built.**
4. **The shared key layout has a physical limit SQLite lacks.**

So Postgres's value to an ordinary application is not speed. It is operator
trust (a managed database, point-in-time recovery, replicas and failover), the
extension ecosystem, SQL tools, and eventually more than one server process
over one store. None of those requires Quarry to execute as SQL.

### 2.4 A production design point

Convex runs its own query engine over indexes it maintains, and a single
committer assigns commit order ([How Convex
Works](https://stack.convex.dev/how-convex-works)). Its Postgres persistence
keeps serialized documents and encoded index keys in two shared tables with no
per-application relational DDL, storing a long key as a prefix, a suffix and a
hash
([`crates/postgres/src/sql.rs`](https://github.com/get-convex/convex-backend/blob/main/crates/postgres/src/sql.rs)).
Its subscriptions re-run a query when a commit overlaps the query's read set.
That shows the shape proposed in §4 is viable for a general-purpose backend.
It does not show that the shape is right for Snapback; the measurements of §10
decide that.

## 3. The application model

| Operation | Meaning | Where it runs |
| --- | --- | --- |
| Query | A read of one consistent snapshot, with truthful completeness | Server; a device when every read site is held |
| Mutation | One atomic change to managed state, judged by the server | Server; predicted on a device when eligible; queueable offline |
| Action | Ordinary TypeScript that may perform I/O, with no transaction | The server runtime; never queued by the SDK |

An action calling two mutations performs two transactions. A job remains an
atomic, chunked data program; a scheduled action is an action.

A restriction applies only where its reason applies. Device execution
restricts what runs on a device; audience inversion restricts what syncs;
authorization and the meter restrict everything (LLP 3000.007 §3.1). The
language remains one spelling, and where an operation runs is computed, not
chosen (LLP 3000.007 §4). An operation runs as its caller unless it is
declared to run as a service seat: running on the server is not running
trusted.

| Owner | Owns | Never owns |
| --- | --- | --- |
| Core (Rust) | Values, schema, rules, Quarry semantics, the meter, atomic commits, receipts, commit order, the partition log, effect and work admission, projection writes | Provider calls, application JavaScript, object bytes |
| Store adapter (SQLite, Postgres) | Transactions, physical layout, access pushdown and batching, durability settings, projection and database-owned DDL | Rules, expressions, completeness, meter charges |
| Server runtime (Node) | Action and route handlers, provider SDKs, invocation leases, streaming responses | Any write to managed data except through a mutation |
| Device (Rust, native or wasm) | Acquired partitions, the same interpreter, the outbox, local observation | Authoritative admission, effects, server-only facts |

The four ship as one release and need not share a process. An online-only
client loads no device runtime (`createClient`), as today. Imports and repairs
of managed data use managed writes or an explicit maintenance procedure that
rebuilds derived state; a database connection is never an application write
path.

## 4. One executor, two stores

### 4.1 Push down access, never semantics

The boundary beneath the interpreter (`Rows`, `PartitionRows`) may give a
store more to do at once: a batch of point reads, a batch of rule probes,
several bounded scans, a count, all of a mutation's writes in one flight. A
store answers with whatever SQL it likes. A store never evaluates a rule, an
expression, a shape, a filter, a completeness class or a meter charge.

This keeps LLP 3000 §7's "one implementation, in Rust" true on the server. No
dialect's null, collation, overflow or error order enters the data plane. The
conformance corpus, the simulator and the device suites qualify Quarry once.
An adapter is qualified by a small access contract — the rows a seek, scan or
batch returns, in key order, at the transaction's snapshot — testable against
`MemoryRows`.

### 4.2 Transaction-scoped prefetch

1. The compiler marks, for each page-producing read, the point reads and rule
   probes in its per-row shape or filter whose keys are pure functions of the
   row. In the inbox these are `totals[.room]` and the probe that `totals`'
   read rule makes.
2. After fetching a page, the runner sends the adapter one prefetch: the key
   set for each marked read. Postgres executes it in one flight (`= ANY`,
   `unnest` joins, or a pipeline) into a cache scoped to the transaction.
3. The interpreter then evaluates exactly as it does today. Its reads hit the
   cache; the meter charges each read when the interpreter performs it, in the
   same order; a cut leaves the remainder unread and uncharged.

Results, refusals, cursors and meter observations are unchanged by
construction: prefetch only moves physical reads earlier within one snapshot.
Physical work may exceed logical work by one page of marked reads. Hidden rows
are read physically and never disclosed, as SQLite's page cache already reads
them. A write invalidates its table's cached entries. A prefetch failure is an
infrastructure failure of the operation, like any store failure. SQLite and
the device need no prefetch and may keep it off.

A mutation's writes — row images, index entries, projection rows, the commit
record, log events, effect admissions and the receipt — are all known when its
program ends, so the adapter sends them as one pipelined flight before commit.
The measured increment made about 18 calls.

Reads whose keys come from an earlier read in the same row prefetch one level
at a time. The inbox should fall from 68 calls to a handful. That is an
estimate; measuring it against SQLite's 0.138 ms and the 0.082 ms lower bound
is the Postgres lane's first step (§10.2).

### 4.3 Layout

- Managed data keeps the generic layout on both stores: canonical row images
  and order-preserving index keys, the bytes a device scans (LLP 3000 §7, "one
  key encoding"). Schema successors stay logical; none becomes DDL on a live
  table. The Postgres adapter may partition its row and entry tables by
  logical table for vacuum and maintenance.
- Long keys: either the schema bounds every indexed text so its encoded key
  fits both stores (one rule, checked by `check` on both, so a schema stays
  portable), or the adapter stores long keys as an indexed prefix, an overflow
  suffix and a hash, as Convex does. Measure the indexed text in existing
  schemas and choose; the counterexample test stays until then.
- Typed, natively indexed tables exist only as projections (§6.1).

### 4.4 One commit order

A watermark is a position in one total order of commits per store, and no
earlier commit may appear below a position a device has passed. Both stores
keep that order. A Postgres sequence allocation is not commit order; the
transactional head is (LLP 3000 §7).

Throughput comes from making each ordered commit cheaper — prefetched reads,
one write flight, group commit where durability settings allow — not from
concurrent writers. Concurrent execution with ordered validation is the next
step only when a named workload's measured commit rate needs it. Per-scope
logs are not proposed, because a commit must remain whole across scopes. An
infrastructure retry repeats the whole operation with its ids and
deterministic inputs, and rereads every fact.

### 4.5 What the abstraction gives up

The author asked what large wins an abstraction over SQLite and Postgres
loses. On this design there are two:

1. **Cost-based planning of Quarry.** Quarry reads are metered, bounded pages
   by design, where a batch recovers most of the round-trip cost. The read
   that needs a planner — an unbounded join or aggregate for a report — is
   written as SQL over a projection (§6.2) or computed by a job.
2. **Write parallelism beyond one committer.** One ordered committer on SQLite
   measured 14,000–15,000 commits per second in the experiment's longer
   four-writer run, and Convex serves general-purpose applications through
   a single committer. §4.4 names the path past it.

Operations, extensions and SQL tools survive the abstraction.

`dev` stays zero-install on SQLite unless the application requires Postgres
(§6.4). A store moves between SQLite and Postgres by an explicit export and
import of rows and log, never by a configuration change.

## 5. The server half

### 5.1 Declared actions and routes, typed handlers

Proposed spellings:

```quarry
action summarize(doc: documents) returns { summary: text <=4000 }
route billing: post "/hooks/billing" as service:billing   -- no session; the handler verifies the provider
```

```ts
// snapback/server.ts (proposed); model and billing are the application's provider SDKs
import { GiveUp } from "snapback4/worker";
import { api } from "./generated/api";
import { server } from "./generated/server"; // built by check and dev, never committed

export default server({
  actions: {
    async summarize({ doc }, ctx) {
      const read = await ctx.query(api.documentText, { doc }); // under the caller's rules
      if ("denied" in read) throw new GiveUp(read.denied.message);
      const summary = await model.summarize(read.data.text, { idempotencyKey: ctx.invocation.id });
      await ctx.mutate(api.saveSummary, { doc, revision: read.data.revision, summary }); // refuses a stale revision
      return { summary }; // checked against the declared result
    },
  },
  routes: {
    async billing(req, ctx) {
      const event = billing.verify(await req.rawBody(), req.headers, ctx.secrets.BILLING_SIGNING_KEY);
      await ctx.mutate(api.applyBillingEvent, { customer: event.customer, status: event.status },
        { id: ctx.writeIdFor(event.id) }); // at most one application per provider event
      return new Response(null, { status: 200 }); // acknowledged only after the commit
    },
  },
});
```

- **One declaration, three uses.** Quarry declares argument and result types.
  `check` generates the client's `Act<R>` and the handler's signature from
  that declaration; admission validates arguments and settlement validates the
  result. A result that fails validation fails the invocation terminally: its
  effects may already have happened, so it is never retried automatically.
- **The context.** `ctx.query` and `ctx.mutate` run under the invocation's
  authority and return the card's `Read` and `Write` states, replay-aware as
  LLP 3000.007 §8.1 requires; no transaction spans two calls. `ctx.principal`,
  `ctx.invocation` (id, attempt, deadline, cancellation), `ctx.secrets`,
  `ctx.files` (§7) and, for admitted database-owned tables only, `ctx.sql`
  (§6.3).
- **Authority.** An invocation runs as its caller, with a short-lived session
  fenced by its lease as today, or as a declared service seat. Queued work
  does not extend an expired caller's authority. Collecting a result later
  requires a live session of the same principal; a result holding protected
  rows returns ids for the client to read under current rules.
- **Routes.** A route is declared and bound to a handler; exporting a function
  never publishes one. It authenticates by session, or runs as a declared
  service seat whose handler verifies a provider's signature over the raw
  bytes. A provider is acknowledged only after durable admission bound to its
  event id through a deterministic write id, so a duplicate delivery is a
  replay, not new work. Handlers may stream; a stream is not a completion
  receipt, and a disconnect does not undo admitted work.

### 5.2 Schedules and durable work

- A schedule may name an action as well as a job. An effect `emit`ted by a
  mutation remains the transactional way to start external work.
- Actions, effects and scheduled actions share one lifecycle: a stable id
  bound to operation and payload, release version, authority, due time,
  attempts, a fenced lease, outcome, and inspection through `doctor` and
  `why`. Reusing an id for another operation or payload refuses. Retries,
  backoff, deadlines, concurrency limits and cancellation are per-operation
  settings. Retention and deduplication windows are documented; an expired id
  is never silently accepted again.
- A provider request uses a stable per-step idempotency key, never an attempt
  number. If a worker dies after a provider accepted a request and before
  settlement, the lease fences the old attempt and the successor reconciles
  through the key. Work whose provider can neither deduplicate nor be queried
  parks for an operator instead of repeating.
- Long workflows are persisted state and resumable steps, never checkpointed
  JavaScript stacks. Cancellation is cooperative for work in flight;
  compensation is application logic.
- A report too large for a request runs as a job or action that writes its
  result with the snapshot or cutoff it describes. Summing independent live
  pages is not an exact report.

### 5.3 Supervision and isolation

`serve` supervises the runtime as `dev` does today: start, restart with
backoff, correlated logs, stop with the server. A hosted worker pool may
implement the same claim protocol later. Application TypeScript is trusted
application code in its own process, isolated from the core and never a
sandbox for end-user programs; a declared capability list is not proof that it
cannot reach the network. It receives no credential for managed tables.

## 6. Database capabilities

### 6.1 Projections

```quarry
table places:
  name: text <=200
  latE6: int
  lngE6: int
  read <- public
  project places_geo { id, name, lat_e6: .latE6, lng_e6: .lngE6 }   -- proposed
```

```sql
-- snapback/sql/migrations/0001-places-geo.sql, applied at activation (Postgres with PostGIS)
ALTER TABLE places_geo ADD COLUMN location geometry
  GENERATED ALWAYS AS (ST_SetSRID(ST_MakePoint(lng_e6 / 1e6::float8, lat_e6 / 1e6::float8), 4326)) STORED;
CREATE INDEX places_geo_location ON places_geo USING gist (location);
```

- A projection maps each row of one managed table to one row of scalar
  columns computed by Quarry expressions of that row. The interpreter computes
  the values; the adapter writes them.
- The engine writes it inside every managed commit that changes the source —
  insert, update, delete, expiry sweep — and backfills it with a job when it is
  first declared. A projection write that fails aborts the commit. At every
  commit, a projection is exactly its source. Projection writes are charged to
  the mutation that causes them.
- Database migrations may add generated columns, indexes and extension types
  to a projection table. They may not add triggers, rules, foreign keys or
  write grants.
- A projection is server-only. It never syncs and changes nothing a device
  holds.
- It exists on both stores: a typed SQLite table (with FTS5 where wanted) or a
  typed Postgres table.

### 6.2 SQL reads

```quarry
query nearby(latE6: int, lngE6: int): sql reading places_geo returning places   -- candidates
query revenue(org: orgs): sql reading orders_facts returning list { month: time, cents: int }
  require exists memberships[org, viewer, 'admin'] else FORBIDDEN               -- a declared channel
```

```sql
-- snapback/sql/nearby.sql
SELECT id FROM places_geo
ORDER BY location <-> ST_SetSRID(ST_MakePoint(:lngE6 / 1e6::float8, :latE6 / 1e6::float8), 4326)
LIMIT 50;

-- snapback/sql/revenue.sql
SELECT date_trunc('month', placed_at) AS month, sum(cents) AS cents
FROM orders_facts WHERE org = :org GROUP BY 1 ORDER BY 1;
```

- **Scope.** A SQL read is a server-only query in the store's dialect. It
  reads projections and database-owned tables, never the managed row and entry
  tables, the log or receipts. It declares the relations it reads, and the
  store enforces the declaration: a per-operation grant on Postgres, SQLite's
  authorizer. It runs read-only, with bound parameters, a statement timeout
  and a row limit. Those are guardrails, labelled as such, not the meter
  (LLP 3000.002).
- **Authorization, in one of two declared forms.**
  1. *Candidates.* The SQL returns ids of one managed table. The engine reads
     those rows under that table's read rule in one prefetched batch and
     returns the visible ones in the SQL's order. Hidden and absent are one
     word, and the page is `complete: false`, since its extent is the SQL's
     rather than a prefix Snapback decides.
  2. *A declared channel.* The SQL returns computed values under a `require`
     prelude that decides who may see the whole result. `check` lists every
     channel beside readable maintains (LLP 3000.007 §8.7 (g)). The compiler
     cannot prove that the SQL stays within what the prelude guarded; the
     declaration names that responsibility for review.
- **Expiry.** A projection of a table with `expire at` is read through a view
  the engine regenerates at activation, which hides rows past their lifetime
  before the sweep. SQL reads are granted the view, never the table.
- **Liveness.** A read whose declared relations are all projections of tables
  without `expire at` is live at table granularity, because only managed
  commits write them and every commit names the tables it touched. Any other
  SQL read is one-shot, and the host refuses to observe it, whatever the
  generated types say.
- **Portability.** A Postgres-only function or extension requires §6.4's
  declaration. A SQLite-backed application writes SQLite's dialect. Moving an
  application between stores ports its SQL reads explicitly.

LLP 3000.007 §10.3 recommends application SQL reads for reporting and awaits
the author. Its §9.1 named three costs: generated views without the secondary
index, a second translation of authorization, and an approximate SQLite
instruction meter. Projections carry native indexes, candidates and declared
channels replace translation, and the limits are labelled guardrails. The
price is one `project` line per table a report reads, where §9.1's views
needed none; the brief measures whether agents pay it willingly. If the author
admits SQL reads, this is the proposed form on both stores. Translating simple
read rules into SQL predicates remains a later option.

### 6.3 Database-owned tables

- Created by database migrations in a separate schema, written only by actions
  through `ctx.sql` under a role that can write nothing else, and read by SQL
  reads.
- Never managed: no rules, sync, maintains or receipts. Whatever clients should
  see live or offline is published into a managed table by a mutation carrying
  a source version, eventually and explicitly.
- A database write followed by a mutation is two transactions. No bridge that
  writes managed rows from SQL is proposed; one would have to capture every
  trigger and cascade and enforce rules, maintains, receipts and whole-commit
  sync inside the database.
- For example, an action computes embeddings with a model provider and stores
  them in a pgvector table keyed by document id and revision; a SQL read
  returns candidate documents, authorized by §6.2's first form.

### 6.4 Requirements and credentials

```quarry
requires postgres >= 16 with postgis, vector   -- proposed
```

- `check` knows the declared target and refuses a Postgres-only construct
  against SQLite, naming the requirement. `dev` runs such an application
  against a configured local Postgres. `deploy` checks the server version,
  extensions, roles and migrations before activation.
- Only the core holds the role that writes managed tables and projections. SQL
  reads use per-operation read grants; `ctx.sql` uses the database-owned write
  role. The `sql` inspection verb (LLP 3000.007 §8.8) is never an application
  surface.

## 7. Services

The brief (§10.1) chooses among these and orders them. A service ships only
with a supported path through development, production, failure and recovery;
a test double is labelled, and a real-provider path qualifies each adapter.

| Service | Proposed baseline | Boundary |
| --- | --- | --- |
| Identity | OIDC and OAuth sign-in in the server runtime, minting sessions through the existing service-seat path; email verification and recovery through effects; an organizations-and-invitations recipe on existing rules | The engine stays out of provider protocols (`NOT-DOING.md`); membership is data under rules |
| Files | Arbitrary files beside typed media: a staged upload claimed once by a home row, as assets are; processing through actions; orphan expiry; object storage behind the adapter | Bytes are not in the transaction; deletion commits a cleanup intent; a signed URL's lifetime bounds revocation |
| Work | §5.2's lifecycle, inspectable | No exactly-once provider claim |
| Search | Word-prefix search stays portable; relevance, vector and geo search through projections and SQL reads (§6) | Rankings are not promised identical across stores; an external index states its lag |
| Realtime | Read-set invalidation for online observation (§7.1); authorized ephemeral channels | Ephemeral state never decides a durable invariant |
| Operations | Point-in-time recovery and failover through a managed Postgres; a first-class stopped backup and isolated restore for SQLite stores (LLP 3000.008.004 §8) | Restore creates a new store incarnation (§9) |

### 7.1 Observation narrower than a table

Today a watched online query re-runs whenever a commit touches a table it
read. That is correct and coarse: every write to `messages` re-runs every
watched query over `messages`. The interpreter knows each read's table, index
and key range, so the server can keep an observation's read set and notify a
client only when a commit's changed keys overlap it, as Convex's subscriptions
do. Key ranges stay on the server, because a key can name a hidden row.
Measure invalidation fan-out on the brief's workload before building it. With
more than one server process, commit notification and presence must also
cross processes (Postgres `LISTEN`/`NOTIFY`, or a polled commit table).

## 8. Locality stays optional

- A table without `sync` is online-only, and an online client loads no device
  runtime.
- A `sync` line requests an authorized replica with a horizon. `check
  --residency` computes where each operation runs and whether a mutation
  predicts (LLP 3000.007 §6); queueable, predicted and accepted remain
  distinct.
- Actions, routes, SQL reads, projections, database-owned tables and presence
  never run on a device. Nothing in §4–§7 changes what a device holds or how
  its writes are judged; the experiment's device already acquires, predicts
  and settles from Postgres pages (§2.3).
- A rule or capability change that would make an existing replica unsafe is
  refused or requires an explicit transition. A device learns of revocation
  on reconnect; retroactive secrecy is not promised.

## 9. One release, evolution and recovery

- One release carries the schema and programs, handlers and routes, SQL reads,
  database migrations and requirements; secrets are references. The candidate
  is validated before admission switches, and the stopped activation model
  remains the first target (LLP 3000.008.004 §4).
- Queued work records its handler contract. A deploy drains it, keeps a
  compatible executor, migrates it explicitly, or refuses; it never feeds an
  old payload to new code. Leases and credentials are fenced across
  activation.
- A projection added to an existing table backfills in a job before its SQL
  reads are admitted; a removed projection's table is dropped at activation.
- Backup and restore cover the database, release identity, database-owned
  schema, object bytes, durable work and deduplication state. Restoring an
  earlier point creates a new store incarnation: old device resumes are
  fenced, uncertain work is quarantined, and provider effects are reconciled
  before redelivery. Point-in-time recovery neither restores object bytes nor
  unsends an email.
- One correlated path runs from request to operation, commit, work attempt and
  delivery, without protected row contents by default; waits, contention and
  refusals are diagnosable.

## 11. Verification obligations

These carry forward LLP 3000.003's open cross-host questions. Its historical
defects are not reopened by being cited.

1. **One meaning on every host.** The corpus, simulator and device suites run
   on both stores. Prefetch is qualified differentially: results, refusals,
   cursors and meter observations are identical with it on and off.
2. **The access contract.** Every seek, scan, count and batch on Postgres
   returns SQLite's rows in key order at the snapshot, including long keys,
   nulls and word entries. A named unsupported case never counts as a pass.
3. **Atomic commits and ordered publication.** Fail after every durable
   write; contend on related and disjoint rows; repeat operation ids; delay an
   earlier commit while later ones finish. No change is skipped, duplicated or
   reordered, through a real database restart.
4. **Authorization across boundaries.** Hidden rows through candidates,
   channels, projections, expiry views and errors; SQL roles that cannot read
   managed tables or write projections; stale leases, revoked callers, and
   result collection after revocation.
5. **Durable external work.** Crash before and after provider acceptance;
   acknowledge webhooks only after admission; distinguish a retry from new
   intent; park what a provider cannot deduplicate.
6. **Real hosts.** Actual browser and native reopen, session replacement and
   persistence, as LLP 3000.008.004 requires. Simulation is not proof of a
   real host.
7. **Evolution and restore.** Deploy with pending work and old clients;
   migrations and projection backfills; an isolated restore with files,
   database-owned data, and fenced workers and devices.
8. **Generality.** The brief's records, not demos: workaround code,
   infrastructure the builders invented, correction loops, and the controls'
   results.

No new blocking gate, exact-HEAD battery or performance ratchet follows. The
Postgres suites run on a schedule, as `scripts/test-postgres.sh` runs today.

Revisit this design if the brief's builders still need a second backend for
ordinary features; if prefetch leaves Postgres page workloads outside a
multiple of SQLite the author accepts for a networked store; if routine
reporting keeps moving to SQL for want of Quarry forms rather than for
database facilities; or if one commit order limits a named workload.

## 13. Alternatives considered

- **Lower Quarry fragments to SQL** (the first draft). This gains planning for
  joins and aggregates. Each lowering reimplements rules, expressions, null,
  collation and overflow behavior, completeness and meter charges in two
  dialects, qualified against the interpreter or abandoned to the fallback.
  The meter's charges and cut are defined in interpreter order, which a
  cost-based planner does not follow. Snapback's reads are bounded pages by
  design, where batching recovers the round trips; the read that needs a
  planner is better written as SQL over a projection. Reconsider if prefetch
  fails on a measured workload.
- **A typed per-table layout for all managed data on Postgres.** Better for
  SQL tools and planning, at the cost of DDL for every schema successor and a
  dialect question for every index component. Projections provide it where an
  application asks.
- **Postgres as the only server store.** One server store, with the ecosystem
  by default. It gives up the zero-install binary behind `dev`, the loop bar
  and small deployments, and the author asked for both stores.
- **SQLite only, with Postgres as an external database the runtime calls.** The
  cheapest path. Specialist data stays outside the managed commit, and an
  operator who wants a managed database has no target. It is the fallback if
  increment C stalls.
- **TypeScript queries and mutations.** Familiar to agents, but it reopens
  JavaScript in the transaction and on the device, which the scope fence and
  the security review refuse. LLP 3000.007's relaxation is the measured answer;
  the brief will show whether data-program authoring is still the loss.
- **Build the platform, then an application.** This risks services no builder
  needed. The brief goes first.

## 14. The author's rulings (2026-09-15)

1. **Direction: accepted.** One executor over both stores; Postgres as a
   persistence target; projections as the only database-native form of
   managed data; no lowering of Quarry to SQL.
2. **The instrument: commissioned.** The online-only brief of §10.1, with
   Convex and Supabase controls.
3. **Promotion: delegated to the lead, who rules that the brief does not gate
   promotion.** LLP 3000 §3's decision rule was registered before the
   comparison and stays as registered; moving it now would change the bar
   mid-comparison, and the brief has no baseline from which to set a
   threshold. The brief is reported beside §3's gates, as the holistic score
   is. It is the bar for the claim this RFC exists to earn: Snapback is not
   described as a general-purpose backend, or as a choice over Convex and
   Supabase for online-only applications, until the brief's record supports
   it. Promotion itself remains the author's ruling.
4. **SQL reads: open.** In plain terms, LLP 3000.007 §10.3 asks whether an
   application may write read-only SQL for reports and search, beside Quarry;
   §6.2 is the proposed form. The question gates only increment D.
5. **Deployment targets: both.** A self-hosted binary (SQLite by default,
   Postgres optional) and a managed service. Nothing in increments A–C
   depends on the managed service. Its design — tenancy, isolation of
   application TypeScript, the stores it runs — is a later child of this RFC,
   with a Moves line in `NOT-DOING.md` when it is commissioned.
6. **Next: one panel round, then implementation.** Astra (max), Grok (xhigh)
   and Muse (xhigh) check direction and name major issues in one round.
   Implementation then begins with Astra (xhigh) coding lanes that the lead
   cuts, reviews and lands, as in LLP 3000.007's and 3000.008's programs.
   Increments A and C start together, and the lead writes the brief.

The increments, not this document, decide the long-key representation, group
commit settings, read-set granularity, the first identity and object-storage
providers, and the spellings `returns`, `route`, `project`, `requires` and
`sql … reading … returning`.
