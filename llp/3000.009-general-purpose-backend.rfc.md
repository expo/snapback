**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 product architecture; transactional core; Quarry and query planning; SQLite and Postgres backends; TypeScript server runtime; authorization; durable work; backend services; optional locality; native database capabilities; deployment and recovery
**Author:** Codex (for Charlie Cheever)
**Date:** 2026-09-15
**Revised:** 2026-09-15 (initial design, grounded in the current authoring surface and Postgres evaluation prototype)
**Related:** [LLP 3000](./3000-snapback4.explainer.md), [LLP 2000.000](./2000.000-keep-the-core-flip-two-substrates.rfc.md), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md), [LLP 3000.008](./3000.008-holistic-product-excellence.rfc.md), [LLP 3000.003](./3000.003-one-semantics-and-credible-verification.research.md), [LLP 3000.002](./3000.002-end-to-end-resource-bounds.research.md), [Postgres evaluation](../snapback4/experiments/postgres/README.md)

## Summary

Make Snapback a complete application backend whose data operations can also
run locally, rather than requiring every backend operation to fit a device.
The application has one schema, one managed-data authorization model, one
typed operation API and one deployment. Execution and physical storage may
differ without becoming separate application architectures.

The proposed architecture has five parts:

1. A compact Rust transactional core owns managed state and its invariants.
2. A first-class TypeScript server runtime owns general programming and I/O.
3. Integrated services compose through the same identity, operations and
   durable-work boundaries.
4. Local execution is an additional, checked capability of eligible data
   programs, backed by the existing partition replica and shared Rust runtime.
5. Explicit native capabilities expose specialist database facilities without
   silently claiming managed-data, reactive or offline guarantees for them.

Keep Quarry for the schema, policies and atomic data programs. Keep ordinary
TypeScript outside database transactions. Introduce plan-oriented execution
and backend-specific layouts beneath shared semantics. Do not add a JavaScript
interpreter twin, an ORM beside Quarry, or unrestricted SQL writes into managed
tables. Do not require Postgres for every application.

This is the author's requested design, **not an accepted implementation
program or a description of the shipped product**. The earlier Postgres
commission remains a bounded evaluation prototype. Proposed interfaces below
illustrate the target and are not copyable examples of today's SDK. No
production support, migration, performance or broad replacement claim follows
from this RFC's existence.

## 1. Motivation and current evidence

The product goal is a compelling default for most new application backends,
including online-only applications. Local-cloud continuity is a substantial
advantage when useful, not an infrastructure tax every application must pay.
Specialist systems should be able to use Postgres facilities without replacing
their entire application backend. This is not a promise of drop-in
compatibility with every existing Convex or Supabase application.

The current starting point is stronger than a storage engine:

| Evidence | What it establishes | What it does not establish |
| --- | --- | --- |
| [Current language and service cards](../snapback4/crates/snapback4-lang/src/guide.rs) | Quarry queries/mutations, rules, maintains, online-only tables, jobs, effects, assets, service identities and limited presence exist. | General server-runtime or service completeness. |
| [Actions card](../snapback4/crates/snapback4-lang/src/guide/actions.rs) | TypeScript actions already run in an external worker with request-principal sessions, durable admission and retries. | Typed public results, a ready-made server context, or integrated production worker deployment. Results currently default to `unknown`. |
| [Client contract](../snapback4/packages/snapback4/src/contract.ts) and LLP 3000.007 | Server/device classification, truthful read states, durable writes and execution-only replay are established contracts. | Every operation is local, predictable, or supported on every host. |
| [Postgres experiment](../snapback4/experiments/postgres/README.md), `72b182a8b` | Real Quarry queries/mutations and transactional sync records run against Postgres; the existing device can consume them. | A production Postgres target, complete portability, or a native application SQL interface. |

The experiment's 32-room inbox makes 68 database calls. Its separately seeded
native SQL comparison omits general authorization, metering and completeness;
it demonstrates planning headroom, not an optimized Snapback implementation.
The experiment also records a Postgres B-tree key-size counterexample and
contention on the global commit head. All three findings constrain this design.

LLP 3000.008's Implemented status covers its selected repair program, not the
architecture proposed here. Accepted .007 forms and later published fixes are
the baseline; old research descriptions of a TypeScript interpreter are
historical, not a proposal to restore it.

## 2. The application model and ownership boundaries

The public model stays small:

| Operation | Meaning | Additional capability |
| --- | --- | --- |
| Query | A read against a consistent application snapshot, with truthful completion and freshness. | Managed dependency tracking can make it live; eligible programs can run locally. |
| Mutation | An atomic managed-state change, authoritatively judged by the server. | A local client can durably queue it and may predict its row changes. |
| Action | Ordinary server code that may call services and perform I/O. | Durable invocation, scheduling, HTTP entry points and explicit native capabilities. |

Queries and mutations are not two spellings for arbitrary TypeScript handlers.
An action calling two mutations has performed two transactions, not one.
Scheduling does not create a fourth data language. Existing Quarry/native
chunk jobs remain atomic data-program invocations with durable continuation;
an action remains nontransactional even when it is run in the background.

The implementation has four owners:

| Owner | Owns | Does not own |
| --- | --- | --- |
| Transactional core | Values, managed schema/policies, program semantics, atomic commits, receipts, logical change records. | Network providers, arbitrary application JavaScript, object bytes. |
| Storage execution backend | Transactions, physical layout/indexes, qualified query plans, physical admission and commit publication. | Redefining application authorization or value semantics. |
| Server runtime and services | TypeScript handlers, invocation leases, provider adapters, files, HTTP and operational supervision. | A second route for untracked managed writes. |
| Device runtime | Authorized acquired state, the shared portable interpreter, durable pending operations and local observation. | Authoritative admission, external effects or server-only facilities. |

All participate in one application release. They need not share one process,
one connection, or one physical database schema. The core should be usable
without loading the Node runtime, and an online-only client should not acquire
the device runtime or its replication storage.

## 3. A compact transactional core

### 3.1 What must stay together

One successful managed mutation commits its row changes, indexes, constraints,
maintained values, logical sync changes, durable effect/task admissions and
operation receipt in one storage transaction. A data job also commits its
continuation there. A failed mutation never publishes a partial write or an
external-work intent. Application refusals and infrastructure failures retain
their existing distinct receipt behavior.

Administrative imports and migrations are not an untracked exception. They
either use managed write primitives or an explicit maintenance procedure that
validates/rebuilds derived state and transitions affected clients safely. A
direct database connection for inspection is not the application's write API.

The core receives a validated principal and execution context from its host;
accepting a trusted host context is not an authenticated public endpoint.
The Postgres prototype currently supplies only that trusted-host interface.
Public adapters must authenticate, bind operation identity, enforce admission,
and recheck current authority at authoritative execution.

The semantic contract includes canonical values and ordering, null behavior,
integer overflow, defaults, constraints, policy disclosure rules, mutation
results, replay, pagination and completeness. Database collation, JSON encoding
or exception messages must not accidentally become the application contract.
Ordinary portable types have defined meanings; specialist types require codecs
and a named capability rather than being silently coerced into that domain.

### 3.2 Execution, retries and the outside world

Retry a conflicting transaction as a whole, including authorization and
maintains, with bounded attempts. Preserve the logical operation's IDs and
deterministic program inputs across internal retries; reread mutable database
facts in each new transaction. Exhaustion is a typed retryable failure, not
a successful receipt. PostgreSQL likewise requires whole-transaction retry
for serialization failures. [Postgres retry guidance](https://www.postgresql.org/docs/16/mvcc-serialization-failure-handling.html)

The transaction never invokes a provider. It can commit an intent that becomes
claimable after commit. No provider request occurs for a rolled-back intent.
The provider call is not part of the database's atomicity or exactly-once
guarantee; §7 defines the uncertain-outcome case.

Preserve the accepted distinction between a fresh mutation result and a
replay confirming execution identity without historical values. A worker
convenience API must not resurrect withheld results. When it needs current
state after a replay, it performs a currently authorized query.

### 3.3 Storage and commit publication

Replace the assumption that `Rows` is the complete backend abstraction with
three internal responsibilities: execute admitted data plans in a transaction,
commit a managed change set, and expose committed changes through the existing
logical snapshot/stream contract. Retain the simple row interface as an
interpreter fallback and device-store boundary where useful.

SQLite may keep compact generic rows/indexes; Postgres should evaluate typed
per-table columns and native indexes where they provide a measured advantage.
The mapping is compiler/backend-owned, not a second schema the application
must keep synchronized. Schema evolution migrates that mapping explicitly.
Do not adopt one relational layout by assumption: qualify large keys, nullable
fields, unique constraints and canonical comparison before calling it portable.

The commit feed must never advance a consumer past an earlier transaction that
can later appear below its resume position. Preserve whole-commit visibility
across affected sync scopes. The initial correct implementation keeps the
transactional head; it makes no scalable multi-writer claim. Sequence allocation
alone is not commit order.

A later commit-ordered publication mechanism may remove that contention, but
must relate a receipt's commit identity to durable publication and snapshots.
It must handle delayed commits, publisher failure, restart and membership
changes. Per-scope logs are not automatically sufficient for cross-scope
transactions. Changing today's public sequence representation requires an
explicit wire/version decision; this RFC does not invent a replacement token.

## 4. Expressive data programs and backend-native plans

### 4.1 The authored program describes the answer

Make related-row selection, joins, filtered aggregation, grouping, nested
projections and stable ordered pagination ordinary data-program operations.
They should compose without a required hand-maintained projection for every
report. Maintains remain valuable for deliberately precomputed answers.
Keep index and plan diagnostics visible without requiring authors to encode
network round trips into the program.

Lower data-oriented fragments to a logical plan carrying their schema,
authorization context, ordering, dependencies, bounds and result shape.
Execute surrounding control flow with the shared Rust semantics. This is an
incremental compiler boundary, not a plan to translate every Quarry statement
into SQL or to ship a second language interpreter.

An indexed local lookup loop can be a sensible device/SQLite execution and a
poor client/server database execution. SQLite documents why its in-process
query calls differ from networked calls; Postgres can plan joins, aggregates
and sorts when it sees the combined operation.
[SQLite query-call costs](https://www.sqlite.org/np1queryprob.html),
[Postgres planning](https://www.postgresql.org/docs/16/using-explain.html)

### 4.2 Optimization is constrained by semantics

The first pushdown target is the measured inbox, on the actual managed data,
with its rules, maintained totals, dependency tracking and completion behavior.
Do not count the separate SQL fixture as this implementation. Batch related
reads or execute a joined fragment while preserving its observable behavior.

A legal optimization preserves authorized results, null/order/overflow
semantics, statement-visible failures, maintained changes, continuation and
the resource contract applicable to that operation. It cannot evaluate a
fallible expression on a hidden row before authorization, turn a page-local
group into a whole-relation aggregate, or move a cursor past unfinished work.
Fallback to the interpreter when an equivalence has not been established.

Portable pagination uses a defined total order and tie-breaker, not physical
row position. Cursors are opaque and bound to their operation, arguments,
authorization context and compatible schema/order definition. A backend
change may invalidate and restart a cursor; arbitrary native cursors are not
promised to survive migration or execute on a device.

### 4.3 Resource accounting is an explicit design boundary

Keep existing Quarry meter semantics for existing programs. For initial plan
pushdown, compute the same logical charges or use the fallback. A SQL call
count, returned row count or planner estimate is not a replacement for that
meter. Hidden physical work must not be exposed through a new public counter.

Broader exact server relational operators need a separately qualified execution
contract: an exact answer within the declared server resource profile, or a
typed failure. An interrupted aggregate never becomes a plausible exact total.
Do not silently insert a source `LIMIT` to make an aggregate fit. Long work has
an asynchronous report/job path with a declared snapshot or cutoff; summing
independent live pages is not an exact single-snapshot report.

The recommendation is to distinguish portable semantic bounds (result bytes,
admitted writes, canonical values) from backend physical admission (time,
concurrency, decoded buffers and database work). The latter can have different
failure thresholds on different backends. It must not change a successful
answer or permit a partial mutation. Existing deterministic meter cuts are
not silently replaced by this new profile.

Before shipping those broader operators, define their logical accounting and
the enforceable physical controls for each supported backend. SQL timeouts and
memory settings alone do not establish a process-wide hard resource bound.
This is a required design/measurement milestone, not a claim already established
by the prototype or permission to raise current ceilings.

## 5. Authorization and optional locality

### 5.1 One policy source, different execution capabilities

Use the managed schema's policies as the source of authority on both backends.
Backend SQL enforcement is generated/qualified from that policy representation,
not a second set of application-authored RLS rules. Policies apply before
aggregation, ranking and result shaping; policy-table changes are dependencies
of protected queries. Preserve hidden-versus-absent and protected-error behavior.

Server-only execution is not trusted execution. An operation runs as the caller
unless it is explicitly admitted to a scoped service capability. Internal-only
visibility prevents direct public invocation but does not itself grant authority.
Service reads that intentionally expose a derived result are declared read
channels, like separately readable maintains, not an accidental authorization
escape through a server wrapper.

Permit richer bounded server policy evaluation without requiring audience
inversion for every online table. Replication remains restricted to policies
whose audience and revocation behavior the delivery engine can establish.
General JavaScript with network I/O is not a row policy. Time-dependent rules
require clock-driven invalidation and an explicit local retention contract;
until qualified, keep them server-only and do not mark observations perpetually
fresh. Today's expiry and rule behavior remain unchanged.

### 5.2 Locality is requested and eligibility is derived

An ordinary table is online-only without `sync`, as it is today. A sync
declaration requests an authorized replica with a stated horizon/retention
policy; it does not request a second database owned by application code.
Server-only, backend-specific and observable are independent facts: a portable
report can be server-only on both engines, while a Postgres-specific read can
be either qualified for observation or explicitly one-shot.
Compiler classification and actual acquired coverage decide which calls can
execute or predict locally. A schema declaration is not proof of acquisition,
and a missing row beyond a horizon is not proof of absence.

Keep queueability, prediction and authoritative acceptance distinct. A local
client may durably queue an unpredicted mutation; a predicted mutation may
later fail server authorization or a global invariant. An action does not
become offline-queueable merely because it has a durable server invocation.
The existing `Read`, `Write` and `Act` truths remain the starting point.

If a policy or capability change makes existing replication unsafe, reject
the incompatible change or require explicit transition to an authorized
projection. Never silently broaden the audience or leave previously acquired
rows falsely fresh. Server sources may publish compact managed projections
for local use; their latency and completeness must be explicit.

An offline device cannot immediately learn remote revocation or erase facts
already delivered to a person. Apply the established retention contract on
reconnect and session changes. Do not promise retroactive secrecy.

## 6. A first-class general-purpose server runtime

### 6.1 Authoring and types

Use the application's normal supported Node/TypeScript toolchain and packages
outside the core. The supported release packages and supervises the runtime;
authors do not provision a second application server just to run an action.
Keep direct execution for deployment targets that supervise the process; a
hosted worker pool can implement the same invocation contract later.

Quarry owns public action argument and result shapes, as it owns the data
schema. Add an explicit result shape at this foreign-code boundary and generate
both client types and a server handler interface. TypeScript implements that
interface; runtime admission and result encoding validate against the same
contract. Do not separately hand-author a validator, client type and handler
signature, or infer a public serializable contract from arbitrary npm types.
A result-contract violation is a terminal program failure, not a reason to
automatically repeat external effects. Those effects may already have happened;
result validation cannot roll them back.

The intended application layout keeps the bodies near their declarations:

```text
snapback/
  workspace.q          # managed schema/policies, data programs, action contracts
  workspace.server.ts  # typed action implementations and HTTP adapters
  reports.sql          # optional, explicitly declared native read implementation
```

This is a proposed source layout, not today's module-discovery convention.
Binding to generated operation definitions determines identity; discovering
a file or exporting a TypeScript function does not make it publicly callable.

The generated operation catalog includes visibility, argument/result shapes,
required capabilities and execution facts. It is a build artifact, not a new
hand-maintained registry. Operation imports available to a public client are
not a bundle of server code, secrets or database credentials.

Proposed server context responsibilities (names are illustrative):

| Context facility | Contract |
| --- | --- |
| `ctx.query` / `ctx.mutate` | Typed calls under current caller authority, with explicit read completeness and replay-aware write outcomes. No transaction spans separate calls. |
| `ctx.principal` | Verified request identity; not a caller-supplied principal string. |
| `ctx.tasks` | Admit/inspect permitted durable invocations; transactional admission occurs through a mutation, not an ordinary action call. |
| `ctx.files` | Authorized file lifecycle operations, not unrestricted storage credentials. |
| `ctx.secrets` | Application deployment secrets available only in the server runtime. |
| `ctx.native` | Handles for the operation's admitted native capabilities. |
| Invocation metadata | Stable invocation ID, attempt/lease identity, cancellation/deadline and correlated logging. |

The host manages short-lived invocation credentials and fences stale leases.
It cannot renew an expired caller's authority indefinitely merely because work
is still queued. Caller-scoped work reauthorizes current access; service-scoped
work uses an explicit grant with a defined lifetime and purpose. Result retrieval
is authorized separately from having once admitted an invocation, especially
after revocation or an identity switch.

Retained action results need an explicit current result-access check. When no
safe such check is defined for protected content, return operation/resource
identifiers and read the data through a currently authorized query. The typed
contract must state collection/refusal behavior; it cannot smuggle historical
row access into a generic successful action receipt.

### 6.2 HTTP, webhooks and isolation

HTTP routes adapt verified requests into the same typed operations. Handlers
can use ordinary HTTP response/streaming facilities; they are not required to
pretend a stream is a single action result. Disconnection does not undo an
accepted durable command. A live stream is not a durable completion receipt.

Webhook adapters verify signatures over the required raw bytes, bind provider
event IDs, and durably admit work before acknowledging it. Duplicate delivery
does not create duplicate logical work. Public, internal and provider entry
points have explicit admission rules; importing a handler never publishes it.

Application TypeScript is trusted application code, not a sandbox for arbitrary
end-user programs. Run it in an application-isolated process/container with
bounded resources, separate from the core. A declared capability list is not
proof that ordinary Node code cannot access ambient networking or the filesystem.
Any multi-tenant isolation or enforced egress claim needs target-specific proof.
No database-owner credential is supplied merely to enable managed calls.

## 7. Durable work without fictional transactions

Unify the lifecycle plumbing for client actions, effect delivery and scheduled
invocations: stable identity, typed payload, admitted release/handler contract,
execution authority, due time, attempts, fenced leases, outcome and diagnostics.
Reuse existing action/effect machinery before inventing a separate workflow
engine. Their entry-point and result-disclosure rules remain distinct.
Admission binds an invocation ID to its application/store, submitting authority,
operation and payload. Reusing it for a different operation or payload refuses;
replay does not authorize that change. Accepted mutation replay still resolves
the original execution before judging a resend against a newer generation.

The supported policy surface includes bounded retries/backoff, deadlines,
concurrency limits, cancellation and inspectable terminal failures. Retries and
operator redrives preserve the original logical identity when they represent
the same intended effect. A deliberate new effect has a new identity. Retention
and deduplication windows are documented; expired identities are not silently
reaccepted under an unlimited at-most-once claim.

Managed transactions can atomically admit work. Outside them, admission is its
own transaction. Provider requests use stable per-logical-step idempotency keys,
not an attempt number or a fresh key after a timeout. Payload and provider-key
binding must remain stable across retries. Where a provider cannot deduplicate
or reconcile an uncertain outcome, park it for reconciliation rather than
blindly repeat a potentially destructive effect.

The failure case is explicit: a provider succeeds, then the worker dies before
recording success. Lease fencing prevents the old worker from settling local
state after a successor, but cannot retract the provider's action. Persisted
outcome inspection plus provider idempotency/reconciliation resolves this;
database exactly-once execution does not.

Long workflows use persisted application state and explicit resumable steps.
Do not checkpoint arbitrary JavaScript stacks or pretend an entire handler is
deterministically replayable. Cancellation prevents further admitted work and
is cooperative for work in flight; compensation is domain logic, not rollback
of external history. Existing chunk jobs keep their commit-bound cursor.

## 8. Integrated backend services

The baseline is a supported path through development, production and failure,
not merely the presence of a low-level primitive or adapter interface.

| Service | Proposed complete baseline | Boundary |
| --- | --- | --- |
| Identity and authorization | Built-in accounts plus a qualified external identity integration, session lifecycle, scoped services and tested revocation. Common sign-in flows have maintained adapters. | Provider verification stays outside row evaluation; identity does not replace application membership rules. |
| Files | Generic bounded files, typed references, resumable/streaming transfer where supported, authorized access, finalization and orphan cleanup. | Object bytes are not in the database transaction. Existing image/video conveniences remain. |
| Background work | Immediate/delayed/scheduled work, bounded retries, cancellation, failure inspection and safe redrive through §7. | No exactly-once provider claim or automatic distributed transaction. |
| Search | Existing portable word-prefix search plus qualified server full-text search; vector/geo through named capabilities when needed. | Analyzer/ranking/approximation contracts are explicit; native rankings are not promised identical across engines. |
| Realtime | Live managed queries plus authorized ephemeral channels for presence and transient application signals. | Ephemeral loss/TTL/reconnect differ from durable data. It cannot decide a durable invariant merely by being convenient. |
| Operations | Inspect data, files, work, capabilities, releases and correlated failures through existing tools and a coherent inspection surface. | No second administrative authorization universe or mandatory broad dashboard project. |

For files, preserve one explicit authorization home as the default. A completed
upload is initially unattached; a managed mutation attaches its verified
reference. A failed attachment leaves an expiring orphan. Deletion commits a
cleanup intent; physical cleanup retries and cannot delete an object still
referenced by live or retained recovery state. Sharing needs an explicit policy
model rather than guessing authority from possession of an object ID. A signed
URL's expiration bounds revocation; it is not immediate revocation of bytes.

Adapters may supply auth, object storage, email, payments and models. Snapback
owns their operation context, configuration, lifecycle and failure integration,
not the provider's implementation. Local test doubles are explicit, with a
qualified real-provider path before advertising the integration. No silent
production fallback to a different service or backend.

Search must authorize candidates and results, including aggregates and ranking
disclosures. An asynchronous external index has a lag/watermark contract and
current managed authorization checks; it is not transactionally fresh because
it returned quickly. A native approximate ranking states its approximation
separately from whether the available candidate set was completely searched.

## 9. Explicit native capabilities

### 9.1 Capability admission

A specialist module declares requirements such as Postgres plus a supported
PostGIS or vector-search extension/version and its result codecs. Build/deploy
checks the target, permissions, functions and schema version. A SQLite target
refuses a required Postgres capability with a useful diagnosis; it does not
silently emulate or remove it. Development of that module runs against the
required backend, even if unrelated portable modules can run on SQLite.

The requirement belongs to the module/operation and its generated metadata,
not every caller. The caller keeps a typed operation reference. Database
credentials and SQL bodies remain on the server. The ordinary application
does not author duplicate schemas or two implementations of every function.

### 9.2 Managed and native-owned data

| Data access | Allowed target design | Guarantees |
| --- | --- | --- |
| Managed mutation | Core-owned transaction and write primitives, including qualified compiled plans. | Full managed constraints, maintains, receipts and logical changes. |
| Native read of managed data | A qualified authorized read adapter over the managed mapping. | Only the policy, snapshot, resource and observation properties the adapter establishes. |
| Native-owned tables/functions | Explicit server-only namespace, restricted database role and tracked native migrations. | Native database semantics and explicit operation authorization; no automatic managed sync/maintains. |

Initially, deny direct SQL DML/DDL on managed tables to native worker roles.
Raw SQL is permitted on native-owned data. Publish local/live facts from it
through managed mutations; absent a qualified same-transaction bridge, that
projection is eventual and carries an explicit source version. A native SQL
transaction followed by a managed mutation is not atomic across the boundary.

A future native managed-write bridge would have to capture and validate every
affected change, including trigger/cascade consequences, and preserve policies,
maintains, receipts and whole-commit sync atomically. Ordinary CDC after commit
cannot retroactively enforce those invariants. Do not make that bridge a hidden
dependency of the first production Postgres release or claim it exists now.

This boundary is a deliberate trade: specialist database freedom is available,
but managed guarantees are not implied by sharing the same Postgres instance.
Most application data should remain managed; a second copy of ordinary tables
must not be the standard answer to a query-language limitation.

### 9.3 SQL, authorization and observation

SQL application reads are distinct from today's privileged developer `sql`
inspection command. Never expose the inspection connection as an application
query adapter. Use restricted roles, bound parameters, read-only transactions
and an admitted function/view surface; checking that text begins with `SELECT`
does not establish read-only or authorized execution.

Generated RLS or protected views can implement parts of policy enforcement,
but require equivalence tests. Postgres owners and bypass roles can bypass RLS;
constraints and database errors also have disclosure behavior that differs
from ordinary row filtering. [Postgres row security](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)

A service-native operation may intentionally read more than its caller. Its
output authorization is an explicit responsibility and reviewed read channel,
not an assertion that arbitrary SQL became policy-safe through a wrapper.

Live observation requires a sound invalidation source for all data and policy
dependencies. Conservative table-level invalidation is acceptable; missing
changes is not. Native-owned writes need a qualified committed change source
before they can drive automatic live queries. Views, functions, clock-sensitive
predicates and external data count as dependencies too.

Start opaque native reads as one-shot server queries unless these obligations
are met. Capability-aware generated types/diagnostics must reject unsupported
observation rather than let `observe` silently become a stale cache; the host
enforces that admission rule even for clients bypassing generated types. Never
promise local execution solely because a native result has a portable shape.

## 10. One development and operational lifecycle

One development command checks schema/policies, generates client and handler
types, starts the core and server runtime, provisions admitted local services,
and correlates their errors. Ordinary TypeScript tooling remains ordinary;
Snapback need not become a general frontend bundler. No generated projections
are committed merely to hold these pieces together.

One release packages compatible schema/programs, server handlers, native
artifacts/migrations and required capabilities. Secrets remain deployment
references, not embedded artifacts. Validate the candidate before switching
admission. The first target can use the existing stopped activation model;
one deployment does not imply a zero-downtime distributed switch.

Queued work records its admitted handler/contract version. A deployment must
drain, retain a compatible executor, explicitly migrate, or refuse incompatible
pending work. It cannot feed old payloads to new code and hope. Fence leases
and credential renewal across activation. Old clients and queued mutations
follow the existing compatible-generation and typed-refusal rules; schema
migration does not rewrite their intent silently.

Backups/recovery account for the database, release identity, native schema,
asset objects/references, durable work, deduplication state and external
provider outcomes. Database PITR alone does not restore object bytes or undo
emails/payments. The backup manifest names the recovery point and any service
limitations; immutable object retention must cover the promised restore window.

Restoring an older state creates a new store incarnation. Fence old resumes,
quarantine pending client/server work whose history is uncertain, and reconcile
provider effects before enabling redelivery. Do not transparently replay all
old device outboxes into a rewound deduplication ledger. A qualified initial
procedure may require fresh devices and stopped workers; seamless continuation
is a separate capability, not something implied by a restore button.

Expose a correlated path from request to operation, commit, work attempt and
delivery, without logging secrets or protected row contents by default. Plans,
waits, contention and resource refusals must be diagnosable. Performance and
recovery objectives are measured on the supported target, not inferred from
one deployment command or a microbenchmark.

## 11. Three concrete application journeys

### Workspace invitations: integrated ordinary backend

An authorized mutation creates an invitation and atomically admits email work.
The worker uses the invitation's stable delivery identity at the provider.
A crash after sending exercises provider reconciliation, not a new invitation.
Acceptance consumes the invitation and adds membership in one managed mutation;
membership changes invalidate protected queries and update sync audiences.
After revocation, old invocation IDs do not grant access to stored results.

The author writes membership/invitation rules and the provider call, not a
second queue, identity proxy or client synchronization protocol. Choosing a
new email provider does not change the data transaction's semantics.

### Documents and AI: general server programming

A generic file is uploaded, verified and attached through a managed mutation.
That commit admits extraction/model work. A TypeScript handler uses normal
libraries and provider SDKs. It stores output through a mutation that checks
the document/source version, so an old completion cannot overwrite a newer
revision. Progress is explicitly transient or persisted; the final outcome
is durable. Tokens streamed over HTTP are not a completion receipt.

A vector index is a server capability with an explicit index version and
freshness/approximation contract. An eligible document list or summary can
still be synced locally. The vector engine itself need not run on the device,
and obtaining a model result does not grant a caller new document authority.

### Booking and reporting: atomicity and native headroom

Two clients compete for the final available unit. A managed mutation owns
the invariant and receipt; local prediction never confirms allocation.
Payment intent and eventual provider settlement use §7 rather than a network
call inside the reservation transaction. Application-specific expiration and
compensation handle an abandoned payment.

A management report aggregates the authorized server population, not only
rows held by a device. It either returns an exact admitted answer or uses a
supported asynchronous snapshot/cutoff job. A geo-discovery operation may use
PostGIS behind the same typed API, with its server/native requirement visible
at development and deploy time. This does not make ordinary bookings depend
on native-owned SQL tables.

## 12. Proposed implementation sequence

These are bounded candidate increments, not permission to start all of them.
Each implementation commission names its owner, scope and acceptance date;
this RFC is not an undated binding Spec. Preserve one owner on core semantics.

| Increment | Deliverable | Evidence before advancing |
| --- | --- | --- |
| A: coherent server authoring | Typed action results, generated handler context, verified HTTP/webhook entry points and integrated supervision on the existing SQLite target. | One invitation journey, failure/retry/identity tests, one release containing handlers and schema. No Postgres dependency. |
| B: qualified execution boundary | Batched/plan-oriented inbox on the real managed stores; a layout solution for the large-key counterexample. | Interpreter/SQLite/Postgres comparisons of values, policies, bounds, cursors, receipts and sync, plus actual database-call/latency measurements. |
| C: complete everyday services | A qualified identity adapter, generic files, inspectable durable work and authorized ephemeral signals. | The workspace and document journeys through restart, revocation, provider ambiguity and cleanup, using maintained local and real-provider paths. |
| D: useful relational and native server reads | Exact server relational operators with an explicit resource contract; first read-only native capability and supported server search. | Reports beyond the old small-page fixture; authorization/error-channel tests; truthful one-shot/live capability admission and resource measurements. |
| E: production Postgres target | Authentication/session host, jobs/actions/effects, files, subscriptions, migration, pooling/admission and release/recovery integration. | All advertised services actually operate on this backend; isolated restore and actual clients qualify their boundaries. Keep serialized commits until a replacement is proven. |
| F: broaden and tune from applications | A substantial online-only application, then selected locality and a specialist capability without backend replacement. | Independent build experience, day-two change, measured operational/performance costs and a maintained failure journey. |

Prototype B can inform A without delaying the ergonomic improvements. D can
first run on a fenced evaluation host, but is not product support until E
qualifies the target. Search profiles and provider adapters have their own
qualified scope; C is not shorthand for every conceivable integration.

## 13. Acceptance, verification and falsification

Use the existing simulator and affected suites, with small actual-host
witnesses for their blind spots. Do not introduce a standing full-product
matrix, exact-HEAD battery, performance ratchet or new blocking gate.

The following obligations carry forward LLP 3000.003's unresolved verification
questions into the new architecture; its historical reproduced defects are
not presumed present or reopened merely because they appear in that research.

1. **One meaning across executors.** Differential tests cover value/tag
   boundaries, ordering, null/overflow, expression failures, rules, maintained
   values, completion and cursor ownership. Compare the shared Rust interpreter,
   each admitted plan backend and actual device execution for eligible programs.
   Named unsupported cases never count as passes. A common Rust implementation
   does not by itself qualify storage adapters or SQL lowering.
2. **Real admission and persistence.** Exercise argument/asset validation,
   durable acquisition, confirmed-base prediction, outbox persistence, session
   replacement and actual browser/native reopen. Schema presence and in-memory
   simulation are not proof of durable acquired state or real process recovery.
3. **Atomic commits and publication.** Fail after every relevant durable write;
   contend on related and disjoint rows; repeat operation IDs; delay an earlier
   transaction's commit while later work completes. Observe matching snapshots,
   receipts and whole-commit streams through actual database restart. No lost
   increment, duplicated effect admission or skipped committed change.
4. **Authorization across boundaries.** Test hidden rows in joins/aggregates,
   policy changes during observation, native roles, stale leases, revoked
   callers and result retrieval. Sanitized failures do not reveal protected
   facts. Never infer SQL authorization equivalence from the presence of RLS.
5. **Durable external work.** Crash before and after provider acceptance,
   acknowledge webhooks only after durable admission, distinguish retry from
   new intent, and show explicit recovery for an outcome a provider cannot
   deduplicate. A model fake does not qualify actual provider behavior.
6. **End-to-end resource behavior.** Measure acquisition, query/commit latency,
   concurrent-writer contention, live invalidation fanout, action startup,
   buffers/heap, slow clients and package costs on the supported hosts. SQL
   guardrails are labelled as such; do not claim a global bound from one meter.
7. **Evolution and restore.** Deploy with pending work and old clients; refuse
   incompatible artifacts before activation; restore an isolated earlier state
   with files/native data and fenced workers/devices. Distinguish supported
   fresh-device recovery from seamless continuation and from physical power loss.
8. **Generality and ergonomics.** Build the §11 journeys from public artifacts
   and perform a meaningful next change. Record workaround code, required
   infrastructure and correction loops. Then enable selected locality without
   duplicating business rules. Existing demos or a source-assisted regression
   do not substitute for this independent application evidence.

The architecture is not successful if ordinary features repeatedly need a
second application backend, routine data logic is labelled "specialist" to
avoid fixing Quarry, server programs inherit irrelevant device restrictions,
or native SQL silently creates another security/consistency model for ordinary
tables. Revisit it if the planner can only be fast by weakening the shared
contract, or if global publication serialization prevents the measured target
workload. No unmeasured "almost all applications" percentage is a success bar.

## 14. Scope changes proposed, not enacted

The [current scope fence](../snapback4/NOT-DOING.md) remains operative. An
implementation ruling must name the corresponding Moves entry and displaced
work; this design request is not that ruling.

| Current boundary | Proposed disposition |
| --- | --- |
| Quarry and one Rust interpreter | Retain; extend data expressiveness and add qualified execution plans, not a TypeScript data-plane twin. |
| No embedded JavaScript data plane | Retain. Strengthen the external TypeScript runtime and its release integration. |
| SQL is developer inspection only | Add an explicitly authorized application read capability; do not reuse the privileged inspection connection. |
| SQLite-only production target | Retain through evaluation; add Postgres only after increment E. Backend switching is an explicit migration, not a config-only promise. |
| No jobs framework, generic files, richer presence/search | Propose the bounded service contracts in §§7–8, one qualified increment at a time. |
| Restricted server-rule/audience forms | Preserve current forms; admit richer server policies only with qualified evaluation/invalidation. Replication keeps a checked subset. |
| Current resource ceilings and client card | Unchanged by this RFC. New exact server execution and capability-aware observation need explicit qualified contracts before shipping. |

Not proposed: arbitrary JavaScript transactions, a second ORM, transparent
distributed transactions, arbitrary native writes with managed guarantees,
automatic SQL-to-device execution, compatibility with every SQL extension,
multi-region/federated execution, device-to-device authority, instantaneous
offline revocation, or universal migration compatibility with other backends.

## 15. Alternatives, risks and decisions for the author

**Make all programs TypeScript.** Familiarity is valuable, but adding general
JavaScript transactions or a portable JavaScript data plane reopens execution,
retry and device-semantic boundaries. Recommend retaining the current split
and measuring ordinary atomic-data authoring. If common business invariants
still require contortions, fix the data language or revisit that choice with
evidence; an action around several mutations is not an equivalent workaround.

**Make Quarry do everything.** This would turn provider libraries, HTTP,
streaming and filesystem integration into language/runtime work. Recommend
ordinary TypeScript for those tasks and a deliberately small transactional core.

**Expose unrestricted Postgres everywhere.** This preserves maximum database
freedom but cannot automatically preserve Snapback maintains, replay and sync.
Recommend explicit native-owned namespaces plus qualified managed reads first.
Broader SQL write integration needs its own proof; do not sell opacity over a
generic `r`/`i` store as the full Postgres application experience either.

**Use only the intersection of SQLite and Postgres.** That would unnecessarily
limit both storage planning and specialist applications. Recommend rich shared
semantics with backend-owned physical execution and explicit nonportable modules.

**Build the entire platform before another app.** This risks architecture
without ergonomic evidence. Recommend increment A and the existing measured
query as the next bounded candidates, with the three journeys shaping the
service contracts. Do not start with an unlimited plugin framework or dashboard.

The recommendation is definite about ownership, operation semantics, public
action type ownership, native-write boundaries and deployment unity. Material
questions still needing a scoped implementation decision are:

- The admitted relational operator set and its exact/logical/physical resource
  contract; no optimizer change may choose this implicitly.
- The measured Postgres layout and eventual commit-publication design. Retain
  the correct serialized baseline until a replacement earns its guarantees.
- The first identity/object-storage/search integrations and supported deployment
  target. Choose concrete qualified implementations, not an abstract catalog.
- Operational recovery objectives and deduplication/retention windows, including
  how provider reconciliation and object retention support them.
- Final source spellings for typed action results and native capabilities.
  Examples here name contracts; parser/API syntax needs a small authoring trial.

The author can accept, revise or narrow this direction independently of
commissioning an increment. Focused review of authorization/SQL lowering,
resource semantics and replay/restore is recommended before those boundaries
are implemented. No independent review, implementation authorization, product
qualification, or replacement claim is recorded by this initial draft.
