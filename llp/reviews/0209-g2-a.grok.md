**M1 — (a) Root `window` proofs claim exhaustion after a take truncation.**  
`crates/snapback-engine/src/graph_evaluator.rs:593–623`

```593:623:crates/snapback-engine/src/graph_evaluator.rs
    let (label, class, evidence) = if has_more && unbounded(&window) {
        ( /* prefix, hasMore:true */ )
    } else if unbounded(&window) {
        ( /* complete, sourceExhausted:true */ )

            GraphCompletenessLabelV1::Window,

```

Named ends always take the `window` arm with **`hasMore: false`**, even when lookahead set `has_more`. LLP 0209 §4.1: a `window` proof “proves both named ends exhausted”; “reaching a cost or page bound is never terminal.” An admissible demand with a bounded root interval and `take` smaller than the interval therefore publishes a terminal `window` label for a truncated page.

The 12 executed cases all use unbounded roots, so the corpus is silent.

**Fix:** If `has_more && !unbounded`, do not mint `window`/`hasMore:false`. Use the closed root `unknown` arm (or refuse), never a terminal exhaustion proof.

**M3 — (d) Ledger charging and window-bound refusal diverge from §2.4 / §2.6.**  
`crates/snapback-engine/src/graph_evaluator.rs:1508–1536`, `1480–1506`

- Structural `scanned_rows` / `index_ranges` add **only** `state.work.examined/ranges[node_id]`, not the induced subtree. §2.4: the root lineage’s per-page structural counters “include every descendant consultation the root page triggers”; a child lineage includes that child and its descendants. Whole-result re-charge per lineage **is** implemented (`result_rows` / `result_bytes` on every demand-paged ledger).
- `ledger.pages += 1` is never compared to `maxWindowPages` (or `maxWindowScannedRows` / `maxWindowIndexRanges`). A second page against a `maxWindowPages: 1` plan still publishes. Corpus nodes declare `maxWindowPages: 1`.
- `enforce_execution_bounds` checks per-node examined/lookups/fanout/expansion and `maxPageResultBytes` only. It does not check `queryCost.maxScannedRows` / `maxIndexRanges` / `maxResultBytes` or any `maxWindow*`. For admitted plans the per-node examined sum is the analytical `maxScannedRows`, so that hole is redundant **if** plans stay consistent; window-page overflow is not.

The corpus test only asserts `windowLedgers` is an array (`graph_corpus_v1.rs:1819–1822`).

**Fix:** For each demand-paged `nodeId`, sum examined/ranges over that node and descendants; refuse `SNAPBACK_QUERY_COST_BOUND_EXCEEDED` when any lineage counter would exceed its `maxWindow*` (and when whole-query ceilings are exceeded).
