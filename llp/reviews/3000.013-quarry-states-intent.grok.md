# LLP 3000.013 design review — Grok 4.7, reasoning effort xhigh

**Date:** 2026-09-23. **Revision reviewed:** initial (6d9f3e001). **Mode:** blind, over the checkout (`--permission-mode auto`, instructed read-only). The narration preceding the first heading is omitted; the review below is verbatim.

## Verbatim review

## Blocker — Inbox reads disclose and then go incomplete (§4)

Unfollow deletes only the edge. Copies stay until a later purge, and the home read is a residual filter on one time-ordered inbox. Sync does not apply that filter. An inbox row is delivered to the reader when `read <- .readerId = viewer` passes (`schema.rs` audience binding; the recipe's `feed` rule). A conjunct such as `exists follows[viewer, .actor]` is rejected by that binder, because a conjunct it cannot invert would ship rows the rule denies. So the partition keeps shipping unfollowed copies, including a copy that loses the race below.

Cursors are unpadded base64url JSON (`cursor.rs`), not a sealed token. On a short page the continuation is `last_rule_visible`, which is updated before the residual filter (`read.rs` around the cut comment "a cut may pass filter rejects, never rule-hidden keys"). Those rows passed the inbox rule and failed only the follow filter, so the cursor carries their `at` and event id. A followers-only post the reader can no longer open is still named in `next`.

The cost line is wrong. The probe runs per examined row, not per returned row. The examined and rule-probe ceilings are 8,192 (`meter.rs`). `N_SPARSE_FILTER` already exists for this shape (`reads.rs`): an unscoped follow filter returns a short `complete: false` page. Without the old per-actor cap, unfollowing one busy author leaves more than 8,192 newest copies. The home page comes back empty or not a prefix of the readable feed, and a wide merge has no per-lane cursor (LLP 3000.007.000: a cut while any head is unknown stays terminal; windowed continuation was shelved).

Smallest fix: do not filter a mixed inbox. Serve one prefix lane per current follow plus the reader's own actor, so unfollowed copies are not in the scan. Make unfollow's commit revoke those lanes (edge delete is enough if sync is `exists follows[reader, actor]`). Physical purge is only reclamation.

## Blocker — Materialized copies skip the source read rule (§3.3, §4)

The recognizer materializes any union that looks like originals plus reposts, filtered by a follow edge. Delivery is unconditional. The inbox rule is "this reader", not "this reader may read the source row."

`posts` with `read <- .authorId = viewer or .audience = "public"` still matches the shape. A private row is copied into every follower's inbox and syncs to their device. The later join `posts[.post]` returns null, but the copy already showed the actor, time, and post id. The public tombstone does the same for a private id. That is safe in 0.3 only because the recipe's posts, reposts, and tombstones are all `public`.

Smallest fix: recognize the shape only when every branch is uniformly readable (`RuleExpr::Allow` or `Public`), or re-check the source rule for the recipient both at delivery and on read, and do not publish a tombstone the source row's readers could not already see.

## Blocker — Derived aggregates turn "absent" into an existence oracle (§3.2)

`followerCount[p]` is specified as 0 when absent. Point reads today return one null for hidden and absent ("Hidden and absent are the same word on purpose", `read.rs`). A maintained miss must not be coerced to zero (LLP 3000.007 §20.21).

If a miss returns 0 before the read rule is decided, and a hidden hit stays null:

- `follows` is `read <- .followerId = viewer` (private edges).
- `view followerCount: count follows by .followedId` uses only the group key, so the derived rule is `.followedId = viewer`.
- Alice has followers. `followerCount[alice]` finds a row and the rule returns null.
- An unknown person with no followers has no row and returns 0.

Null means "a positive total exists and you may not read it."

The four examples are not produced by either default. `revenue` and `receivedLikes` group by a shop or by `.postId.authorId`, which is not a bare column of a uniformly readable source. A compiler that accepts them has invented a third default. The default people will pick is world-readable, which publishes a shop's revenue and an author's likes, including rows the reader cannot open. The guide already treats that as a channel (`rules.md`: a filtered count discloses whether a hidden row matched; `N_MAINTAIN_DELTA` / `N_MAINTAINED_COLUMN_DISCLOSURE`).

Smallest fix: decide the read rule from the requested key first. An authorized miss is 0. An unauthorized miss and an unauthorized hit are the same null, with the same charge. Examples that the two defaults do not cover require an explicit `read <-` and still emit the existing disclosure note. Never default them to allow.

## Blocker — A streaming total is not a total (§5.1)

LLP 3000.011.001.000 measured this and stopped. Dropping the result vector does not drop the heap charge: the meter sums decoded row images, it does not track peak. The real digest shape (5,000 candidates, 50 recipient ids) still decoded to about 22.9 MB against a 16 MB ceiling. That LLP's rule is that a capped or unknown domain is not a scalar total.

§5.1 says the opposite twice: rows are examined under the meters, and this removes that ceiling. §7 says the ceilings stay. A job's examined ceiling is 16,384. One `count(R)` of a busy chat still stops. `exists` already answers false when a capped query finds nothing (LLP 3000.007 §20.22.4). Copying that onto `count` and `sum` returns a partial number that looks finished. Jobs run as the system principal and skip read rules (`jobs.rs` guide), so the same `count(R)` in a query is a disclosure channel if the implementer forgets the rule, and a full private total if they follow the job path.

Smallest fix: in a query, count, sum, and exists see only rows the read rule allows. A cut, an unread remainder, or an unknown device domain returns no number. Say plainly that the digest envelope is unchanged until a store cursor charges one live image at a time and the 5,000×50-recipient fixture is remeasured. Do not weaken the meter.

## High — Bucketed windows are not exact (§2.1)

`posts where .at > now - 1d last 10 by .likeCount, .at` becomes hour lanes plus a residual time filter. The feeds card already denies exactness for that plan: the oldest hour still charges rows the filter rejects, a crowded boundary returns `complete: false`, and a cursor across `likeCount` repeats or skips because the count moves (`feeds.md` trending; `maintains.md` on paging a moving ranking).

Counterexample: `now` is 12:30, so the window starts yesterday at 12:30. The bucket `hour(yesterday 12:00)` holds a half-hour of excluded posts. If those 8,192 highest `likeCount`s sit in the excluded half, the lane never reaches a qualifying row. Other hours fill `last 10`. The page is not the top 10. LLP 3000.007.000 cannot continue that merge: one cursor has no per-lane position, and a cut while a head is unknown has no `next`.

The bucket bounds are also unspecified. For a UTC epoch hour and a 24h window the inclusive set is `hour(now - D)` through `hour(now)` (25 buckets). The card uses `hour(now) - 24` through `hour(now) + 1` because of the upper bound. One missing endpoint drops an hour. `D > 92d` is not given a plan. Day buckets make the excluded slack a full boundary day, which hits the same meter.

Smallest fix: copy the card's contract into §2.1. The page is exact only when every lane exhausts or returns `take` qualifying rows inside the meter; otherwise return no winners, `complete: false`, and no cursor. State the inclusive UTC bucket formula. Say that paging a maintained order key is not a snapshot.

## High — `in` lanes drop a suffix and still look finished (§2.1)

`.conversationId in (members where .principal = viewer).conversationId` is one lane per value. That value read is itself a domain, capped by the schema cap or the examined meter (`prefix.rs`). Past the cap the rest of the memberships never become lanes. The outer merge can still fill `last 20` from the first lanes and look complete. A value list that changes between pages skips a newly included conversation's older rows, because the single cursor has no per-lane memory.

Duplicate values depend on the eager merge's `seen` set, which keys on id only (`merge_with_words`). That is not stated. Nulls are not stated. `exists` is not given this plan; it stays a residual, and a cut still answers false. An implementer who "optimizes" `exists follows[viewer, .author]` into lanes will invent the incomplete-list bug and may skip the branch read rule, which §2.1 never requires (only §3.1 does).

Smallest fix: each lane is an ordinary ruled scan. Dedupe values before opening lanes. If the value read caps, refuse the page. Do not report a full page from a prefix of the list.

## High — Cross-table pages dedupe the wrong identity (§3.1)

"Ids are globally unique, so no duplicates and no gaps" is false. Minted ids are 80 bits of entropy, but ids are caller-supplied too (`createPost` takes `postId`). Uniqueness is per table. The eager merge drops the second row with the same id string and keeps whichever projection it saw first. Two branches of one table with overlapping `where` clauses and different projections collapse the same way.

The cursor cannot express this plan yet. Translation requires the same columns and the same plain index (`program.rs` merge), then rewrites the table name and keeps one index descriptor (`read.rs`). `lazy_merge` is same-table, same-index only (`rules.rs`). A projected key read off the first lane's index components is null on a branch whose source column has another name. Exclusive resume on a non-unique suffix already skipped rows with `complete: true` until the merge position grew a row id (LLP 3000.007.000); that id is the store key inside one table, not a global identity.

Smallest fix: the merge identity is `(branch, source id)`. The cursor is the projected order values plus that pair, not one table's index token. Refuse overlapping branches of one table. A lane that does not establish its head fails the page.

## High — Follow, unfollow, and remove race the background worker (§4)

0.3's answer contract (LLP 3000.007.003 §3.3) is not what §4 specifies, and the non-claims only mention synchronous visibility.

A post enqueues one delivery record naming today's followers. Unfollow commits, cleanup runs and finds nothing, then the delivery chunk inserts the copy. The filter hides it until a later purge. If purge never runs again, the copy stays. Refollow inserts another. Nothing in §4 ties the copy to the follow epoch, and nothing makes the insert idempotent. Crash replay of a 256-row chunk doubles copies the same way. 0.3 closed the private-inbox existence probe by giving owned rows digest ids; a caller-chosen event id plus `FEED_EVENT_REMOVED` while the tombstone exists is not carried forward. Tombstones were deleted with the copies so the per-event cap fit one chunk. §4 does not say when the tombstone goes away or whether the id can be reused.

"Older events, chunked" has no stop. 0.3 examined the newest 865 and was explicitly not an unlimited archive. Full history times an uncapped follower set is the new storage and device-acquisition bound. Devices are told to hold the inbox and the public edges. The filter needs the viewer's outgoing edges, not the whole graph. 0.3 synced that graph publicly only under the caps §20.3 used to avoid an exhausted horizon (50,000 inbox rows, 100,000 edges). Those caps are gone and no horizon replaces them. Follow on a device that does not hold the author's posts cannot predict the same newest 50 the server copies; 0.3 queued that mutation with no predicted rows because slot state was online-only. That sentence disappeared with the slots.

Smallest fix: stamp every delivery and every copy with the follow epoch (edge generation). A chunk upserts by `digest(reader, event, epoch)` and no-ops if the edge epoch changed. Keep `FEED_EVENT_REMOVED` until the tombstone and its copies commit together. State the history window in the answer contract: either the newest 865, or full history with a device horizon. Sync the viewer's own edges only.

## High — A self-chunking `for` can skip or double-count (§5.2)

Today's `chunk` commits the cursor with the writes, captures an upper key when the sweep starts, and may only walk `id` or immutable columns (`jobs.rs` guide; `E_JOB_CURSOR_INDEX`). Otherwise a row whose order key moves is skipped or visited twice, and a row inserted under the cursor is either missed or repeated. §5.2 says "as `chunk` does today" and then does not require any of that. Halving K after a meter refusal is safe only if that attempt rolls back. A commit of the iterations that fit, then a retry, writes them twice. `emit … once` does not repair a doubled `sum` that already landed in a row.

Smallest fix: the failed K rolls back, then K shrinks. The sweep freezes its upper bound, resumes after the last committed key, and is refused unless every non-id key is immutable. `break` and `return` end the sweep the way `chunk` does.

## High — `emit … once` is only idempotent if the key commits with the outbox row (§5.3)

"At most one, forever, a repeat is a no-op" matches the digest marker (LLP 3000.011.001.000): same business key across restart, marker kept for the life of the store, provider retry is a separate at-least-once path. Two holes:

- The key is recorded and the transaction aborts, or two chunks insert the key concurrently. The retry is a no-op and the notification never exists, or both inserts exist. Needs a unique `(effect, canonical key)` in the same transaction as the outbox row.
- The key encoding is unspecified. A principal and a `periodEnd` that canonicalize differently across a rewrite double-send; two payloads under one key keep the first forever, including a partial one.

Smallest fix: one transaction inserts the outbox row and the unique key, or rolls both back. The key is the canonical JSON of the effect name and the value list. State that this dedupes enqueue, not the worker's external delivery.

## High — Synthesized index identity is the sync audience (§2.1, §2.3)

"Synthesis changes nothing at run time" is false. The partition delivers by the probe's exact index, not by column names, because two references of the same type would grant the wrong group (`schema.rs` `audience_binding`). The probe key has to be exactly the sync prefix plus `viewer`, and the principal has to sit at a fixed position in that index.

Canonical pin order is not defined. Alphabetical order serves `exists members[.conversationId, viewer]` (`conversationId` sorts before `principal`) and breaks `exists members[.roomId, viewer]` (`principal` sorts first). Adoption then fails closed, or someone "fixes" it by matching names and delivers the room to the wrong members. A synthesized name `byAuthorIdAt` also collides with a hand-written index of the same name and a different suffix. Two declared indexes with the same leading components are ambiguous; `select_index` already errors, and §2.1 does not say to keep that error.

Smallest fix: a synthesized index is reused only when the definition is identical, including direction and `hour`/`day`/`bucket` identity. Probe and sync indexes keep the audience order, never a sorted order. Any other same-leading-component index is a compile error. Put synthesized names in a reserved namespace.

## What is sound

Top-level conjuncts, with equality as a pin and everything else residual after the read rule, match `scan_prepared` (rule, then filter). Do not push predicates out of `or`. Refusing a positional read of a non-unique prefix fixes the real footgun; keeping explicit `by` for old programs is a compatible leftover and is stated. Planned unions that are not stored, with one ruled scan per branch, are the right visibility model once identity and cursors are fixed. The in-table `likeCount` form can keep today's semantics, including the disclosure note. Constant-time post acknowledgement, the author's own copy in that transaction, and deleting promotion, pull routes, and broadcast lanes are a coherent product cut. `emit … once` as an enqueue marker, not as exactly-once delivery, is the right reading of the digest work. Durations as milliseconds are fine.

§6 (the app object and the web shell) is outside this review.

## Verdict

**NOT READY.** The lanes can keep the surface (predicate reads, one `view`, background delivery, no author-facing caps) only after the inbox is lane-addressed and revoked on unfollow, copies obey the source rule, aggregate misses stay indistinguishable from hidden hits, and count/sum refuse a cut instead of returning one. Bucket, `in`, and union plans need the shelved merge-cursor limits written down so a partial lane cannot look exact.
