## Overall assessment

The main scan-based `{left, held}` case is implemented coherently, and coverage frames do not perturb whole-query evaluation. However, the stated eligibility and per-component routing contracts are not soundly enforced. A reading `require` can receive a plan and produce a composed record that violates its own guard; complete non-retained components are taken from the server even though their standalone query would remain local; retained point reads are not recognized. These are release-blocking correctness and authority defects.

## Findings

### High — reading guards are admitted and can produce a record that violates its own `require`

File: `snapback4/crates/snapback4-lang/src/bind/residency/components.rs:46-50`

A guard’s direct `facts.reads` is never checked; only transitive reads through bindings are. This is already exercised contrary to the stated boundary by `query guard()` and its expected component map at `snapback4/crates/snapback4-device/tests/components.rs:35-37,96-99`.

Concrete scenario:

- Local retained `a` and complete synced `b` each contain 25 rows, so `require count(a) = count(b)` passes locally.
- The server has zero readable `a` rows and zero current `b` rows, so the same guard passes there.
- A third unknown field triggers composition.
- The client keeps local `a` but server `b`, publishing `25 != 0` even though both executions individually satisfied the guard. BASELINE returned the whole server record and preserved the invariant.

Smallest fix: reject a guard when `guard.reads > 0` as well as when its binding dependencies read. Change the condition around line 49 to cover both, update the current `guard()` expectation to no component map, and add the paired race above.

### High — complete non-retained components come from the wrong host and can resurrect applied deletions

File: `snapback4/packages/snapback4/src/local.ts:880-887`

The contract says each component follows standalone routing, but the implementation copies the entire server record and overwrites only fields marked retained.

Concrete scenario:

- A query returns retained `left`, unknown `held`, and complete synced until-revoked `current`.
- The server reply is captured while `current` contains row `r`.
- Before releasing it, sync applies the deletion or scope tombstone for `r`.
- The second local observation correctly has `current=[]`.
- Composition overwrites only `left`, publishing the stale server `current=[r]` after the deletion has been applied.

Smallest fix: when composition remains necessary, copy every second-local component for which `wantsServer(c)` is false, not only `c.retained`. Use remote fields only for components that independently route to the server. Add a delayed deletion/revocation test with a third complete component.

### Medium — retained point reads are not classified as retained

File: `snapback4/crates/snapback4-core/src/engine/read.rs:281-328`

Scans use `Runner::retained_group`, but `Get`/`Exists` do not.

Concrete scenario:

```quarry
query both():
  return {
    left: messages[room = 'left', id = 'left-25'],
    held: messages['held'] last 50 by byTime
  }
```

With `byRoomId` unique and `left` marked delivered-history/left, the local point read finds the retained row. Its frame nevertheless says `retained:false`; since `held` needs the server and no component appears retained, `local.ts:889` performs whole-query fallback and replaces the row with the server’s inaccessible `null`.

Smallest fix: route point reads through retained-group detection. For hits whose addressed key does not expose the audience prefix, derive the retained group from the row. For retained misses under a horizon, record retained incompleteness rather than ordinary unknown coverage. Add hit, miss and `Exists` tests on both stores and both client tiers.

### Medium — nested locals can escape the ownership proof

File: `snapback4/crates/snapback4-lang/src/bind/residency/components.rs:83,125-129`

The analysis permits nested declarations, while the runner’s environment is flat and `Expr::Block` does not restore scope (`snapback4-core/src/engine/runner.rs:214-221,467-469`). A separate expression referring to that nested runtime name is treated as an unrelated free name.

Concrete serialized IR:

- Top-level `a = Block { let leak = scan(left); value = leak }`
- Top-level `held = scan(held)`
- Return `{a, held, z: leak}`

The plan assigns the retained read only to `a`. At runtime `z` sees the same leaked value. Composition can publish local retained `a` beside server `z=[]`, although `a` and `z` are aliases.

Smallest fix: reject any reference to a nested declaration outside the expression that declared it, or make runtime block scopes non-leaking. Add a serialized-IR regression asserting no plan.

### Low — documentation omits the pending-write exception

Files: `snapback4/packages/snapback4/README.md:1160-1162`; `snapback4/crates/snapback4-lang/src/guide/sync.rs:128-130`

Both say an unplanned mixed query returns the whole server answer online. With an unobserved predictable write, `local.ts:889-890` deliberately keeps the local answer.

Smallest fix: qualify the sentence with “when no predictable write is awaiting observation.”

### Low — several negative tests are vacuous without the feature

- `excluded_source_shapes_keep_no_plan` at `snapback4-lang/tests/components.rs:27-43`
- `inline_cross_read_aggregate_has_no_plan` at `:46-50`
- Client scenario `MQ ineligible` at `packages/snapback4/test/retained-history.test.mjs:127-141`

Each still passes if planning/composition is removed entirely. Keep them as negative controls, but add an eligible paired neighbor within each test.

The new `component-independent-record.json` also is not asserted by name to receive a plan: the corpus test only requires some program to be planned at `snapback4-device/tests/components.rs:140-161`. Assert that this specific case has two reading components and participates in the differential.

The delayed-reply tests do not have this defect: their initial composed-row assertion fails at BASELINE, and both delayed operations are proven to overlap the gate.

## Mandatory answers

**Did the change introduce a new problem?** Yes. BASELINE returned one server record for the guard/alias scenarios, so its fields remained mutually consistent. IMPL_COMMIT can combine local and server fields into a record that violates a successful `require` or makes two aliases disagree. It can also publish a complete non-retained field from the wrong host after the second local observation has applied a deletion.

**Is there a regression test that would also pass without the change it claims to test?** Yes: the two negative planner tests and `MQ ineligible` named above, plus the new corpus fixture unless it is asserted by name. They should each include or identify a positive eligible counterpart. The actual composition and delayed-reply tests do fail without the implementation.

Verdict: NOT READY
