## Specific findings

### P1 — Replay-result acceptance conflicts with the governing security decision

`.002 §2` and acceptance 1 require the same authoritative result after a lost acknowledgement. LLP .007 §17 deliberately withholds *all historical values*, including scalars. This is implemented in `snapback4-core/src/engine/receipt.rs:30–55`: the durable receipt strips `result` and `current`, and replays report execution identity. `test/write-authority.test.mjs:71` checks the exact wire shape across revocation.

The remaining client defect is real: `contract.ts:43` requires `result: R` on every sent write, while `client.ts:298` and `local.ts:772` synthesize `result: json.result` and discard `replayed`. A successful retry therefore presents `undefined` as a required result. The existing ticket is `issues/20260914-snapback4-write-result-type-omits-replay-state.md`.

**Action:** Preserve `state: "sent"` but distinguish fresh value-bearing success from an execution-only replay using a discriminated type; propagate that distinction through both clients, `onWrite`, and React `run`/`last`. An application must narrow before navigating from the result. Update `.002` to require stable execution identity and an explicit unavailable result on replay. Keep first-response `null` distinct from “no historical result.” Do not restore cached server values, rerun with a new ID, or suggest the original DM result is always recoverable.

### P1 — Static eligibility still needs an acquired-state boundary

`.001 §2` correctly distinguishes capability from current holdings, but its acceptance examples mostly cover horizons and server-only tables. The source reveals a more basic interruption case worth reproducing immediately:

- `snapback4-device/src/device.rs:214–233` persists backend/generation before acquisition; offline reopen accepts the presence of that backend.
- `local.ts:430–456` turns an initial sync transport failure into `false`, and its constructor at line 949 still returns the client.
- `device.rs:524` passes schema/rows to local evaluation without an acquired-state verdict. `snapback4-core/src/engine/local.rs:36` derives completeness from meter/coverage flags; an empty synced table without a horizon is not inherently unknown.

Thus `/schema` success followed by first `/sync` failure appears able to leave an empty, unacquired table reported as complete, including after offline reopen. `fresh: false` does not make that empty dataset a historically acquired answer. This is a source-derived finding, not an executed reproduction.

**Action:** Reproduce on actual wasm and process devices with a nonempty no-horizon server table. Persist a generation-scoped acquisition-complete fact at the same transaction boundary that publishes the snapshot/catch-up. Before it is established, return a truthful non-value/incomplete outcome and queue otherwise valid writes without fabricating missing-data refusals. Preserve stale, genuinely acquired data when a later refresh fails. Include interruption after schema installation, during a multi-page snapshot, and after a generation reset; an empty server at sequence zero must still be distinguishable from never acquired.

### P2 — Refresh superseded design choices before treating the family as executable

LLP .007 §§14/17 already decides these: predicates may read; `online only` is optional; `E_OFFLINE` is the offline non-value; no predicted result; row-based shapes preserve device metadata. `.008` also routes detailed residency amendments into .006 even though .006 is explicitly Superseded and .007 §6 is its accepted successor.

**Action:** Replace these open questions with current decisions and residual gaps. Keep `.000`’s disclosure requirement, but cite the implemented rule-visible cursor policy and uniform-prefix mutation restrictions rather than reopening last-examined hidden-row continuation. Keep S05/write-authority paired tests intact.

### P2 — Green ceremony evidence does not establish exact Trending

The current feeds card (`guide.rs:1173,1233`) improves the old 200-row illustration: it names an 8,192-candidate ceiling and incomplete results beyond it. That does not establish the builders’ implementations. The **0.2.12 ceremony record** explicitly shows two builders using `first 200` and one `first 1000`; all pass the small seed. A seek over the correct day still truncates the ranking domain before sorting. A full 200-row page can be complete as a page without being a complete day.

**Action:** Retain `.000` acceptance 5 and exercise it: put the winning post after candidate 200/1000 and check the required exact ID set. Add a case beyond the documented ceiling to verify honest partial status. For a materialized alternative, specify refresh lag and trailing-day expiry: the neighboring time-decay `ranked` recipe is not automatically an exact trailing-day likes ranking. Repair the relevant recipe/probe/application, not the shared language with a general ranking subsystem.

### P2 — The proposed acceptance milestone is too broad to be one deliverable

`.003` requires complete browser/native measurements, concurrency, churn and replay; `.004` adds six composed journeys, deploy/evolution, backup/restore and another application. Calling all of these the prerequisite for completing the small client/language improvements recreates the unbounded program the documents reject.

Current release tests explicitly require the server to stop before deploy/rollback (`test/release-activation.test.mjs:111`). “Real clients attached” must mean clients survive that supported interruption, not live zero-downtime activation. Restore of older state also needs a recovery policy for device watermarks and external effects; copying a SQLite file is insufficient.

**Action:** Define the first milestone as the concrete fixes plus their affected journeys. Keep stopped-server backup/restore as a bounded documented exercise; do not promise seamless replay after rollback of deduplication history. Keep broader operating targets and the second application as separately commissioned evidence, not gates for these repairs.
