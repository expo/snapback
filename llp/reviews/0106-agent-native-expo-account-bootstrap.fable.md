# Review of LLP 0106: Agent-native Expo account bootstrap

**Method.** Read the target RFC in full; read accepted siblings 0103 and governing 0089/0060 in full and 0104's header/metering-identity sections; grepped `/home/tuft/projects/universe` (AuthRouter, RobotEntity, AccessTokenEntity, AppTransferRecordEntity, StripeAuthRouter, firstPartyOAuthCodeConfig, PostHog) and `/home/tuft/projects/eas-hosting` (deployment-api, dispatcher, name/config schemas) to ground the "Universe already provides X" claims and the anonymous-preview feasibility. Standards checked against the cited RFCs from memory. No exposure to anything under `/llp/reviews/`.

## Overall assessment

This is a strong, unusually careful RFC that gets the hard decision right: it refuses to let an unknown model process manufacture a recoverable human identity, and instead invents a **provisional platform-escrow workspace** that is explicitly *not* a `UserEntity`/`AccountEntity`, that expires, that cannot incur paid overage, and that is *claimed* (an audited ownership transfer) rather than *merged*. The three-path structure (standing delegation / trusted-host federated assertion / universal claim link) is the correct decomposition, and the standards selection is largely idiomatic and correctly reasoned — device-flow-shaped decoupled completion, DPoP proof-of-possession so a leaked bearer is insufficient, RAR for budget/action constraints that don't fit flat scopes, token-exchange-style attenuation for child credentials, and webhook/API state (never redirect) as payment authority. The Universe-grounding is accurate: every specific claim in "Universe already has useful foundations" verified against the actual code, including the subtle PostHog `oauth`-vs-`requires_auth` behavior and its trusted-URL anti-phishing guard.

The RFC is correctly scoped as a *product/trust-boundary* RFC that defers wire/schema/policy to implementation specs, and it says so. That altitude is appropriate and I do not fault it for leaving endpoint names and numbers open. My concerns are about a small number of places where a **decision** (not a detail) is under-determined in a way that affects security or coherence, plus standards-precision notes. None rises to a blocking MATERIAL defect: the trust model's load-bearing decisions are made and made soundly.

## Strengths

- **The provisional-workspace-not-user decision is the crux and it is correct.** "An unknown model process must not be able to create a recoverable human identity or silently bind to an existing one" is stated as a non-goal and enforced structurally (escrow container, claim-as-transfer, discovery-before-creation, contact-hints-are-routing-hints-not-proof). This is the single most important call and the RFC nails it.
- **Proof-key binding as the spine.** Binding bootstrap and enrolled credentials to a locally generated key (DPoP-shaped) so "a leaked bearer string is insufficient by itself" is applied consistently across bootstrap, claim, enrollment, and child credentials, and shows up correctly in the abuse model (stolen claim URL cannot silently change the approved agent key or destination — acceptance scenario 10).
- **Anti-phishing of the in-agent (Flow C) UI is taken seriously.** "Expo — not model-provided text — supplies the request displayed by the host," assertion must be minted-for-Expo/fresh/nonce-bound/audience-bound/consent-receipted, and "an LLM-authored email string is not an identity assertion." This directly answers the review's Flow B phishing concern.
- **Payment separation is clean.** Stripe-hosted default, agent never receives PAN/wallet, URL payload is server-bound and agent-immutable, webhook-authoritative state, and "card is a payment instrument, not identity or recovery." Coheres with 0069's provider-fact rule (cited).
- **Duplicate-account avoidance is concrete and non-enumerating.** Discovery-before-creation, generic responses to contact hints, "reveal no account-existence fact to the unauthenticated agent," and the three-way disambiguation of "merge" (link logins / consolidate projects / merge records) with (1)+(2)-not-(3) as the paved recovery.
- **Idempotency and state machine are honest.** A caller-generated idempotency key scoped to actor+operation, "retries return the same resource," at-least-once completion events deduped by event id with authoritative refetch, and a small typed outcome vocabulary instead of prose. Acceptance scenario 7 tests the one-workspace/one-claim/one-subscription/one-credential-lineage invariant.
- **Grounding accuracy.** The Universe-foundations section is evidence, not aspiration, and it checks out precisely (see notes). The RFC also correctly flags the gap: today's access token has no expiry/audience/DPoP/scope/spend ceiling — verified in `AccessTokenEntity.ts`.

## Concerns

1. **[detail] The provisional workspace's billing identity is under-specified against 0104's owner-keyed metering, and "provisional/promotional pool" is asserted without an owner.** §"Provisional workspace contract" and §"EAS Hosting and Snapback" say usage before claim is "charged to the promotional/provisional pool" and after cutover "attributed to the destination Expo account," and that provisional resources are "mechanically unable to consume paid overage." But 0104's metering identity is *owner-independent durable id + a time-versioned ownership interval keyed on `expoAccountId`*, and every metering event carries the owning-account interval in force at `occurredAt`. The provisional workspace is explicitly *not* an `AccountEntity`, so it has no `expoAccountId` to be the owner-of-record for the pre-claim interval. The RFC needs to name what the pre-claim ownership interval attributes to (a platform/promotional pseudo-account? a null-owner interval that 0104's protocol must admit?) and confirm the "mechanically unable to consume paid overage" property is enforced by 0104's authoritative account-budget/lease protocol, not merely asserted here. *Resolves by:* one paragraph pinning the pre-claim owner-of-record and citing 0104's account-budget/lease + ownership-interval sections as the enforcement mechanism (and noting the amendment 0104 needs if a non-`AccountEntity` owner is required). This is altitude-appropriate to defer the mechanism, but the *coherence claim* to 0104 is currently unbacked — hence flagged, though not blocking.

2. **[detail] "Claiming preserves project/environment ids" needs to be reconciled with 0103's transfer protocol as a *required amendment*, not an assertion.** §"Avoiding duplicate accounts" and §"EAS Hosting and Snapback" state that claim is a transfer out of escrow that preserves `(expoAppId, snapbackEnvironmentId)` and deployment history. 0103's transfer machinery *opens a new ownership interval without rekeying the durable id* — which is exactly compatible — but 0103's app-wide transfer protocol is a two-phase multi-coordinator commit whose *source* owner is an existing `expoAccountId`. Claiming-from-escrow has a *non-account* source (platform escrow). The RFC should state whether claim reuses 0103's transfer boundary with an escrow-as-source special case (and thus amends 0103), or is a distinct first-run operation. `workspace.claim` and `project.transfer` are listed as separate ops, which suggests the former, but the relationship is not pinned. *Resolves by:* a sentence classifying `workspace.claim` as an escrow-source specialization of 0103's transfer boundary (or a distinct fenced operation) and noting the 0103 amendment if any.

3. **[detail] Flow A "identity.inspect" as an unauthenticated-discovery primitive risks becoming an account-enumeration oracle, and its authority posture is stated as "No" (not anonymous) — but discovery-before-bootstrap must sometimes run before authority exists.** §"Product flows / Flow A" step 1–2 and §"Avoiding duplicate accounts / Discovery before creation" both say all official clients call identity/project discovery *before* bootstrap, using signals including repository remote, bundle identifiers, and prior deployment metadata. The operation table marks `identity.inspect` as `Anonymous? No`. These are consistent only if discovery-before-creation for the *no-authority* case relies solely on locally held signals (credential broker, `.expo` linkage) and never queries Expo with an unauthenticated identifier. The RFC's "contact hints are routing hints / reveal no account-existence fact to the unauthenticated agent" covers the contact-hint channel, but bundle-id / repo-remote lookups against Expo could equally enumerate. *Resolves by:* stating that all pre-authority discovery is local-only, and any server-side match query requires either authenticated authority or returns a non-enumerating generic result.

4. **[detail] Bootstrap credential expiry/blast-radius and the anonymous-preview abuse budget are named as "recommended" without a pinned floor, and the "begin with a local artifact sandbox" fallback is load-bearing but unquantified.** §"Provisional workspace contract" lists TTL, per-bucket project caps, fixed ceilings, no paid overage — all "recommended launch limits." Grounding confirms eas-hosting has *no* existing TTL/escrow/anonymous-deploy notion and *no* deploy-time abuse controls (only request-time FREE-tier CPU/subrequest caps and a rate limiter), so this is genuinely new build, not a toggle. The RFC honestly acknowledges "if Expo cannot safely offer an anonymous deployed preview initially, the same state machine can begin with a local artifact/build sandbox." That is the right hedge, but the abuse-economics question (open question #1) is the one that determines whether Flow B is shippable at all. This is correctly an open question, not a defect — but Slice 2 depends on an unresolved abuse-budget answer, so the delivery plan's readiness hinges on it. *Resolves by:* keeping it an open question (as done) and having Slice 0's threat-model spike gate Slice 2 explicitly (the RFC nearly does this).

5. **[detail] Trusted-agent-host (Flow C) issuer trust is a standing high-value target; revocation latency and assertion replay window need a named bound.** §"Flow C" and §"Security and abuse model / Required defenses" require signature/issuer/audience/nonce/time validation, replay prevention, and "incident revocation for federated agent-host assertions." Open question 2 asks "how quickly can Expo revoke a compromised issuer." A compromised trusted host can mint identity assertions that *create or link human identities* — the highest-privilege operation in the system. The one-time + nonce-bound + short-expiry design bounds replay of a single assertion, but issuer-key compromise is the real blast radius. *Resolves by:* requiring (in the ratification checklist, which already lists trusted-host boundaries) a maximum issuer-revocation propagation bound and a rule that identity *creation* (not just linking) via federated assertion is gated behind an additional freshness/liveness check. Altitude-appropriate to defer the number; the *requirement* should be named.

6. **[detail] CIMD (client-id metadata document) is an IETF draft used for a security-relevant trust decision; the SSRF/caching/trust-policy mitigations are named but the "who may use CIMD directly" gate is deferred to an open question that Slice 4 depends on.** §"Relevant standards / CIMD" correctly notes it is a draft, requires SSRF/caching/metadata-trust policy, and offers an Expo-hosted client-metadata service for ephemeral agents. Open question 5 defers which client identities may use CIMD directly. This is fine as a decision to defer, but the RFC should be explicit that *client identity (CIMD) never by itself authorizes an account* — which it does state ("Client identity says which software is acting; it does not by itself authorize an Expo account"), so this is well-handled. Flagged only to confirm the SSRF surface is on the threat list (it is implicitly, via metadata-fetch rate limits in §Required defenses; making it explicit would help).

## Standards & Universe-grounding notes

- **Device flow (RFC 8628):** Used correctly as a *model/shape*, not claimed as literal 8628 conformance. The `verification_uri_complete` + short user code + polling interval + expiry mirror 8628's fields correctly. No misuse.
- **DPoP (RFC 9449):** Correctly invoked as token-to-key binding; the RFC does not over-claim ("a leaked bearer string is insufficient by itself"), consistent with 0060's C3 permanent rule that DPoP is a copied-credential/off-device-replay constraint, not XSS resistance. Coherent with 0060.
- **RAR (9396) / Token Exchange (8693):** RAR used for project/environment/action/budget constraints (idiomatic); 8693 invoked "as a model for attenuating a parent grant" (correctly hedged), with child-credential rules enforcing strict subset + delegation-depth + no-privilege-escalation.
- **RFC 9728 protected-resource metadata / MCP authorization:** Correctly tied to MCP's discovery model; MCP "does not itself decide who owns an Expo account." No misuse.
- **OIDC / CIBA:** OIDC used for the trusted-host assertion with the correct caveat that the assertion must be minted-for-Expo/fresh/nonce-bound and that an email hint is not an assertion. CIBA correctly deferred.
- **OAuth security BCP (9700):** Correctly cited for exact-redirect matching, PKCE, and rejection of password grants — and the RFC correctly declines to tunnel around Universe's reCAPTCHA-gated password signup.
- **Universe claims — all verified TRUE:** reCAPTCHA-gated password signup (`AuthRouter.ts`); OAuth dedup with verified-email linking, pending-identity creation, and SSO-conflict preservation (`_loginOrSignupUserWithOAuthAsync`, `OAuthLoginPendingSSOConflictEntity`, `PreventSSOUserOAuthIdentityValidator`); `RobotEntity` with account permissions; `AccessTokenEntity` with one-time return, SHA-256 storage, visible prefix, revocation, last-used, audit; `AppTransferRecordEntity` with transfer history; Stripe checkout/subscribe/customer-portal + `agent.expo.dev` return-URL allowlist (`CheckoutRedirectUrl.ts`); first-party OAuth clients for expo-agent/expo-mcp/eas-cli with S256 PKCE and allowlisted redirects (`firstPartyOAuthCodeConfig.ts`); access token has no expiry/audience/DPoP/scope/spend ceiling. PostHog claim precise: `PostHog.ts` implements the draft agentic-provisioning shape (`API-Version 0.1d`, `account_request` with CIMD `client_id`/S256/`configuration`/`scopes`, `oauth`-vs-`requires_auth` split, code exchange, rotating refresh, resource provisioning, credential rotation, trusted deep links with `assertTrustedPostHogUrl` anti-phishing guard).
- **eas-hosting feasibility:** Confirmed anonymous/TTL/escrow deployment does **not** exist today (`deployment-api` finalizes a pre-issued signed-token deployment; routes carry only `devDomainName`+`deploymentIdentifier`, no account/app id; dispatcher enforces FREE-tier CPU/subrequest + rate limiter at request time; no TTL/escrow/deploy-time quota). So the provisional-workspace preview and "add stable ids to the route" are real new builds — which 0103 independently flags.
- **Coherence with 0089:** Correctly "before 0089": unknown agent → Expo authority → account/project/environment → provision, with 0089's `app.provision`/`deployment.create` accepting the scoped credentials produced here. 0089 disclaims owning account creation/billing/tenant policy (verified), so 0106 fills a genuinely unowned layer.
- **Coherence with 0104:** owner-independent-id + admission-bound ownership-interval is the right substrate for usage before/after cutover — but see Concern 1: the pre-claim non-account owner-of-record is the one seam asserted without pinning to 0104's mechanism. 0104 lists `transfer` as non-chargeable, consistent with claim-as-transfer.

## Verdict

`0106: READY`

The load-bearing trust decisions — provisional-workspace-not-user, claim-as-audited-transfer, proof-key binding throughout, Expo-supplies-the-request anti-phishing, webhook-authoritative payment, discovery-before-creation with non-enumerating responses, and the child-credential strict-subset/attenuation rules — are all made and made soundly, and the standards use is idiomatic with no security-relevant misuse. The Universe-grounding claims are accurate against the actual code. The concerns are implementation-phase refinements and coherence-seams to pin against 0103/0104 (the pre-claim billing owner-of-record and the escrow-source transfer classification), plus open questions the RFC already surfaces. None identifies a defective decision that blocks acceptance.

**Overall assessment**

Revision 2 is a substantial, well-grounded improvement. The four round-1 MATERIAL concerns (stolen-claim-URL ownership hole, takeover-unsafe trusted-host linking, a single linear state machine that conflated payment with ownership, and an under-specified DPoP/replay contract) all now read as *substantively addressed*: the claim URL is explicitly modeled as an acknowledged bearer capability with five normative constraints; the trusted-host linking rule correctly forbids auto-link on asserted email and requires authentication under the existing Expo identity or an approved enterprise policy; the state model is decomposed into six orthogonal dimensions with the two key invariants pinned (payment failure does not roll back ownership; enrollment cancel does not delete a human project); and the RFC 9449 contract is normatively specified and *correctly* grounded against the real Universe validator, whose own follow-up note confirms exactly the `jti`-cache and nonce gaps the RFC flags as required new work. Cross-LLP citations (0103 transfer boundary, 0104 metering identity/lease, 0060 sender-constrained v2, 0069 provider-fact/idempotency, the OAuth-dedup/SSO-conflict code) were checked against source and are accurate, with the RFC honestly framing the 0103 and 0104 changes as amendments rather than existing behavior. What remains are coherence gaps in the *closure arguments* — one of which (notification/recovery in the no-contact-hint anonymous case) is close to material — and detail-level refinements. On balance no unresolved MATERIAL defect blocks graduation to implementation specs.

**Concerns**

1. **[MATERIAL] {IN-DELTA}** — The bearer-capability closure argument leaves the common anonymous (no-contact-hint) case without a working notification or an explicitly-named recovery principal. In §"The claim capability is an acknowledged bearer capability", the notification-on-claim constraint only reaches "any consented contact hint, and any channel already associated with a matched-but-not-authenticated existing identity." The RFC elsewhere deliberately supports a workspace created with no contact hint and no pre-existing identity — the URL lives only in chat/terminal/QR. In that case a stolen-URL claim notifies no one, so the hold window is never invoked, and after it clears the claim is durable. The design contains the material that closes this — the bootstrap credential is proof-key-bound to the agent installation key, which the thief lacks, and §Recovery says recovery "does not depend on the same claim capability" — but the RFC never affirmatively designates the agent-installation-key/bootstrap-request holder as the recovery principal for a contested claim, which is the only anchor in the no-hint case. Resolution: state normatively that the proof-of-possession holder of the bootstrap request is a first-class recovery/dispute principal (able to observe and contest a claim) and/or require that a claim of a no-contact-hint workspace either notify the originating agent channel or gate durable ownership on a stronger binding. Small addition, but the load-bearing step in the closure argument, currently missing.

2. **[MATERIAL] {IN-DELTA}** — Workspace-lifecycle `CLAIMED` (declared terminal) conflicts with ownership-transfer `CLAIM_HELD → REVERSED`, so the "orthogonal, non-conflating" claim is not fully met. The workspace-lifecycle dimension is "Terminal at `CLAIMED` (ownership left escrow)", while ownership-transfer can sit at reversible `CLAIM_HELD` and go to `REVERSED`. The RFC does not say when workspace-lifecycle advances to terminal `CLAIMED` relative to the hold: if at claim time, an in-window reversal must un-terminalize it (contradiction); if it stays `PROVISIONAL` through the hold, then "`CLAIMED` (ownership left escrow)" is premature and the escrow container's disposition during the hold and on `REVERSED` is undefined. Resolution: pin that workspace-lifecycle remains `PROVISIONAL` (escrow retained) until the ownership hold clears, and define the escrow container's fate on `REVERSED` (return to `PROVISIONAL`/`UNCLAIMED`).

3. **[detail] {IN-DELTA}** — "credential issuance/enrollment commits … independently of billing" reads as, but is not stated to be, independent of the hold. §Flow D and §Notifications list "credentials" among what must not become durable before the hold clears. Reconcilable (independent-of-billing ≠ independent-of-hold) but the state model should say so explicitly — e.g., `ENROLLED` may issue provisional-scoped credentials during `CLAIM_HELD` but durable/production credential authority is gated on hold-clear.

4. **[detail] {PRE-EXISTING}** — Escrow-source claim genuinely lacks 0103's old-owner lease, which "specialization" language slightly understates. 0103's prepare/commit/abort is built on old-owner leases frozen at prepare and revoked at commit; an escrow/null-owner source has no such lease, so prepare/abort semantics for the escrow case must be newly defined. The RFC already flags the required 0103 amendment and the fallback "distinct fenced first-run operation," so the decision is sound; "specialization" just shouldn't be read as "zero new mechanism."

5. **[detail] {IN-DELTA}** — Multiple deferred numeric/policy values are load-bearing for the security guarantees. Hold-window duration, `jti`/nonce cache sizing and retention (must cover at least the `iat` acceptance window), and the issuer-revocation propagation bound are deferred as open questions. Acceptable at RFC altitude, but the hold-window duration parametrizes concern #1's guarantee and the `jti` retention parametrizes scenario 10; the follow-on specs should treat these as security parameters with justified minimums, not free UX knobs.

**Standards & Universe-grounding notes**

- DPoP/RFC 9449 grounding is exact: `server/mcp/src/auth/dpop.ts` validates `typ: dpop+jwt`, an asymmetric-only allowlist (`ES256/ES384/RS256/PS256`, never `none`/HMAC), `htm`, normalized `htu`, `iat` with 60s skew, and `ath`, returns `jkt`, and its own `NOTE(follow-up)` states it lacks a `jti` replay cache + server nonces — precisely what the RFC marks as new work.
- RFC 8628 scoping correct (borrows UX/polling vocabulary; disclaims wire-compat). RFC 8693/9396 use disciplined (token-exchange as a model requiring server-side strict-subset checking; RAR carries structure but not a mandate; follow-on registration spec required).
- Trusted-host linking rule accurately grounded against `AuthRouter.ts` (`_loginOrSignupUserWithOAuthAsync`) + `PreventSSOUserOAuthIdentityValidator`: existing auto-link fires only after a real provider code-exchange with state+nonce and a provider-verified email + verified Expo user — never a bare asserted email. One precision nit: the RFC leans on `OAuthLoginPendingSSOConflict` as if it "blocks" silent linking, but in code that is a dismissible interactive *warning*; the genuine hard block for SSO users is `PreventSSOUserOAuthIdentityValidator`.
- 0103/0104 amendments honestly framed as required amendments, not existing behavior. Access-token gap claim accurate (`AccessTokenEntity` lacks intrinsic expiry/audience/PoP/scope/spend ceiling); `RobotEntity` with account permissions exists.

**Verdict**

`0106: READY`

Concerns 1 and 2 are real coherence gaps in delta material and should be tightened before implementation specs lean on them, but each is a small, additive normative clarification of mechanisms the RFC already contains rather than a defective decision, a broken security guarantee, or an infeasible design. The round-1 MATERIAL concerns are resolved, the standards use is correct, and the Universe grounding is accurate.

**Overall assessment**

Revision 3 of a mature, well-structured RFC. The two round-2 concerns are addressed substantively and correctly. The recovery-authority/evidence-hierarchy subsection closes the no-contact-hint stolen-URL hole by anchoring on the one secret a URL thief cannot intercept — the agent-installation key that created the bootstrap request — and does so without opening a contact-hint-reversal takeover (an unauthenticated hint can reverse nothing; reversal requires authenticating into an associated identity or a higher evidence tier). Scenario 10 now reads consistently. The workspace-lifecycle model is now internally coherent: the container stays `PROVISIONAL` through the hold, terminalizes to `CLAIMED` only at the single `CLAIM_COMMITTING` cutover, `REVERSED` returns it to `PROVISIONAL`/`UNCLAIMED` with no un-terminalization, and owner-of-record/permitted-principal/metering during `CLAIM_HELD` are pinned to the pre-claim escrow interval. The DPoP `(jkt+jti)`/nonce and opaque-continuation details are technically correct and accurately grounded in the real Universe code (verified directly). No unresolved MATERIAL defect; remaining items are detail/Gate-owned. Verdict: READY.

**Concerns**

1. **[detail] {IN-DELTA}** — Claimant evidence tier in the no-hint anonymous case is left implicit. The hierarchy is authenticated-associated-identity (1) > enterprise policy (2) > bootstrap-request PoP (3); in the no-hint case the first-time claimant authenticates as themselves but has no prior association to *this* workspace, so is not tier (1) w.r.t. it — the tie-breaker ("ties hold the workspace pending support adjudication") and "resolves toward reversibility" are what carry the guarantee. Sound (fail-safe), but the RFC never states which tier a self-authenticated-but-unassociated first claimant occupies. Resolves by the follow-on spec stating a first claimant with no independent binding does not out-rank the PoP holder, so a PoP-holder contest forces the "held / does-not-durably-commit" branch. Implementation-spec clarification, not a defective decision.

2. **[detail] {IN-DELTA}** — "Notify the originating agent channel" presumes the agent is still live and honest. If the originating agent is gone or is itself the adversary, the notify limb degrades to the "gate durable ownership on a stronger binding" disjunct, which the RFC allows. A malicious PoP holder cannot take over (only contest/freeze → fail-safe "held," never a destination it picks), so this is bounded to denial-of-completion, not takeover. Resolves by pinning the gate-limb as default when no live PoP-holder ack is observed in the window, and treating PoP-holder contest as freeze-only. Detail: takeover direction closed; only liveness/DoS framing under-specified.

3. **[detail] {IN-DELTA}** — Hold-window duration floor still an open question. §"Security and abuse model" reclassifies it as a security parameter with a justified minimum, but the RFC doesn't state the invariant the floor must satisfy (window must exceed max notification-delivery + human-reaction latency for the fastest-observing channel). Under-sized window degrades usefulness, not safety (default is reversibility, paid actions gated until clear), so Gate-owned. Resolves by Slice-0 threat model deriving the floor.

4. **[detail] {PRE-EXISTING}** — Escrow-source claim's newly-defined prepare/abort semantics are asserted but not specified. Verified against 0103 r5 / 0104 §"Authoritative account-budget protocol" that this is genuinely a gap in the accepted specs, correctly flagged and deferred to the 0103 amendment. Right altitude for an RFC.

5. **[detail] {IN-DELTA}** — `jti` cache retention floor pinned to the `iat` window, but eviction/store cost unbounded. The upper bound / eviction discipline and per-`jkt` cardinality bound (anti-memory-exhaustion under many valid-`iat` proofs) are unstated. Implementation-owned; resolves in the DPoP spec.

**Standards & Universe-grounding notes**

- DPoP grounding accurate (read `server/mcp/src/auth/dpop.ts`: validates `typ: dpop+jwt`, asymmetric-only allowlist, `htm`, normalized `htu`, `iat` 60s skew, `ath`, returns `jkt`; header comment states it lacks a `jti` replay cache + server nonces — exactly what the RFC marks as new work). The 9449 `use_dpop_nonce`/`DPoP-Nonce` challenge is the correct mechanism.
- SSO block correction accurate: `PreventSSOUserOAuthIdentityValidator` throws for `ActorType.SSO_USER` (hard block); `OAuthLoginPendingSSOConflict` is a dismissible warning (`result: 'action-required', reason: 'sso-conflict-warning'`, gated on `dismiss_oauth_sso_conflict_warning`).
- 0104 metering-identity amendment correctly scoped (ownership interval authoritative, `expoAccountId` derived; `transfer`/`preview-TTL` non-chargeable; the non-`AccountEntity` pre-claim owner is a real amendment point, and "cannot consume paid overage" correctly relocated into 0104's account-budget/lease).

- No standards misuse (8628 UX-only, 9449 DPoP+nonce, 9396 RAR w/ Expo types deferred, 8693 token-exchange attenuation w/ subset checking, CIMD-draft-with-SSRF-policy — all correct altitude).

The ownership model is now internally coherent: ownership is an immutable, append-only claim *attempt* (`UNCLAIMED → CLAIM_HELD → {REVERSED, CLAIM_COMMITTING → CLAIMED}`) plus a workspace-level current-claim pointer; `REVERSED` and `CLAIMED` are both terminal states of an attempt, a `REVERSED` attempt is an immutable idempotent reversal record, and re-claim is well-defined via a pointer reset to a fresh `UNCLAIMED` generation with a fresh idempotency scope. The lifecycle fence is now normative and genuinely closes the destroy-during-hold hole (entering `CLAIM_HELD`/`CLAIM_COMMITTING`/contested inhibits `EXPIRED` and cleanup; TTL suspended-or-bounded-extended over hold + dispute; TTL resumes on `REVERSED`; abandoned/timed-out adjudication yields a bounded held-not-destroyed terminal). The two-branch trusted-host contract (resolved `(issuer,subject)` in-agent; unresolved cases require an Expo-authored continuation driven by an opaque token that never reveals the collision classification) is internally consistent and reconciled across Summary, Goals, Flow C prose, and §"Trusted-host account-linking rule", with the no-detour promise explicitly narrowed to the resolved case. The DPoP nonce-overlap-window, per-`jkt` cardinality cap + eviction, and PoP-holder recovery-tier details are correct and well-grounded. No unresolved MATERIAL concern remains.

**Concerns**

1. **[detail] {IN-DELTA}** — Held-not-destroyed bounded cutoff vs. the safe-terminal default. §"State machine and idempotency" retains abandoned/timed-out adjudication "until a bounded safe cutoff (a security parameter), never silently erased," while §"Recovery authority…" says the container "either remains held pending support adjudication or falls back to the project-transfer/tombstone recovery." What happens *at* the bounded cutoff with no support adjudication (tombstone, hard-expire, hold) is left to the security parameter. A real open edge (an indefinitely-held escrow container is a mild resource-farming/cost surface), but a Slice-0 threat-model output, not a defective decision (the RFC forbids silent erasure and pins resolve-toward-reversibility). Resolves as a parameter-derivation item.

2. **[detail] {IN-DELTA}** — New idempotency generation vs. the caller's stable idempotency key. The pointer resets to a "fresh idempotency scope" on `REVERSED`, but every mutating request carries a caller-generated key scoped to actor+operation. A legitimate agent retrying `workspace.claim` with the same caller key across a generation boundary must land on the *new* generation, not replay-dedupe onto the terminal reversed attempt. Implied ("well-defined against the new generation") but the composition of caller-key + server-generation isn't spelled out; getting it wrong reopens a replay hole or a stuck claim. Implementation-spec mechanic; resolves by specifying the effective idempotency key as (caller-key, generation).

3. **[detail] {IN-DELTA}** — Host-rendered opaque-UI branch (b) non-enumeration timing. The unresolved continuation may be "Expo-authored opaque UI steps the host renders and returns signed results for." Sound in principle, but the anti-enumeration guarantee for branch (b) rests on rendered artifacts (step count, field shapes, latency, asset set) being indistinguishable across ceremonies — a side-channel a purely Expo-hosted branch (a) avoids. The RFC states the relay-only invariant but doesn't require constant-shape artifacts. Conformance/implementation obligation, not a broken contract; resolves by making shape-uniformity an explicit Flow C conformance requirement (or preferring branch (a) where the risk is unacceptable).

4. **[detail] {PRE-EXISTING}** — Hold-window floor invariant depends on an observable channel the anonymous gate-limb case lacks. The floor MUST exceed max notification+reaction latency "for the fastest-observing channel"; in the no-hint case the only observer is the PoP-holder (a polling machine quantity), and with no live PoP ack the design defaults to the gate limb. Floor-invariant and gate-limb are two mechanisms for two cases; the prose could be read as implying the floor always yields a human observer. Non-blocking wording refinement; the security outcome is already correct.

5. **[detail] {IN-DELTA}** — DPoP nonce overlap-window vs. `iat` coupling. A nonce accepted late in its overlap window must still fall inside `iat` for the replay store to remain the sole gate. Consistent as written (the `iat` check is independent and always applies), but the coupling deserves an explicit "nonce validity window derivable from / ≤ the `iat` window" note. Detail-level parameter coupling.
