## Findings

### MAJOR — §3.1 and §7: the first admission check is the final check on replay

§3.1 removes the after-body resolution and the first writer admission because "they decide nothing the final check does not decide again," and it places that final check inside the durable transaction. That is true only for a mutation that reaches `mutate`.

A keyed replay returns inside the first engine-lock section and never enters the durable transaction:

```1170:1194:snapback4/crates/snapback4/src/serve.rs
let (replay, metadata, signature) = {
    let mut engine = lock(&shared.engine);
    if let Err(refusal) = mutation_authority(&request, shared, &engine, &principal) {
        // ...
    }
    let replay = intent_store(&engine, &payload).and_then(|()| {
        let replay = id.map(|id| engine.replay_mutation(&principal, id, &op, &args_json))
        // ...
    });
    (replay, response_head(&mut engine), signature)
};
match replay {
    Ok(Some(outcome)) => { /* reply and return */ }
    Err(why) => { /* reply and return */ }
    Ok(None) => {}
}
```

The second `mutation_authority` is at `serve.rs:1407`, after this return. Ingress (`serve.rs:940`) ran before the body read and before the wait for the engine lock. `serve_identity.rs:58-60` is specifically this wait: write authentication stays behind the writer so time queued does not preserve a session that expired or was revoked. The tests named in §7 ("revoke while queued") fail on this path if the first admission check is deleted.

The same return is why §3.4 cannot be global. `serve.rs:804-805` says a replay's sequence is historical and the head is never that receipt. The head on that reply is the preflight `response_head`, a snapshot newer than the stored outcome. Carrying "the sequence this durable transaction just committed" does not apply, because no durable transaction ran.

Change: keep a fresh resolution in the snapshot that reads the receipt and the current head, and treat that as the final check for replay and for a replay-lookup failure. Delete the earlier duplicate only on the path that falls through to the in-transaction check.

### MAJOR — §4 and §6: B1's 6/8 is the unkeyed shape; the keyed receipt cost is the size of B1

The increment arithmetic for the measured unkeyed tiny mutation does check out. RT-A's 57 is 24 authority + 8 response-head + 14 durable + 11 post-commit. RT1 drops the post-commit 15 (57→42), RT2 drops the unused preflight 4 (42→38), RT3 removes two 6-exchange resolutions, collapses ingress 6→1, and moves the last resolution inside the durable transaction as one statement (38→16). The report's intermediate sum is then 8: ingress, guarded setup, in-transaction authority, three program flights, tail, COMMIT. The read side 23→19→7→6 matches the same report. SQLite's isolated 8+11+20 off 79 is 40, as §3.7 says.

That 57 excludes the production write key. RT-A sent no operation id. A keyed attempt opens a read transaction twice before the durable transaction, once in `serve.rs:1177` and again in `engine/postgres/mod.rs:300-301`. Each `transaction(None)` is BEGIN, the generation/head statement, the `_ops` lookup, and ROLLBACK (`store.rs:165-185`, `receipts.rs:54-58`): about four exchanges, twice. There is a third `replay_bound` inside `mutate_once` (`postgres/mod.rs:331`). Eight extra exchanges is the entire B1 mutation budget, and RT1/RT2 do not remove them.

§1's "a warm read waits on at most 6, a warm mutation on at most 8" is also wider than §4's derivation, which is ingress plus at most two dependent program reads, or three program flights. W3 and any program whose next address depends on a row are outside it. The measured tiny mutation is scan, update, scan (`counts.json` SQLite trace: the same index read before and after `UPDATE r`), so those three flights are real, not slack.

Change: scope B1 to the measured classes, add a keyed first-attempt class and a replay-hit class to §6, and collapse the two pre-transaction receipt snapshots into the receipt read that already runs inside the writer. Recompute 8 with that statement included.

### MAJOR — §3.5, §3.6, RT5, B2: the flight that reaches 4 is not the one S1b measured, and "joined" generation is the wrong statement

B1 can stay safe at 8 if the owner fence is waited on in Rust before the head lock is sent, and if COMMIT is sent only after the tail succeeds. That is the report's eight-term sum, and it preserves parent §5.1 (fence first) and the unknown-COMMIT split in `ownership.rs:127-147`.

RT5 and B2 do not describe that. RT5 "joins" the generation check to the head lock to save a flight. Writers are READ COMMITTED (`store.rs:98-101`). The generation statement is deliberately a second statement (`store.rs:179-185`) so an adoption this transaction waited on cannot be missed. Adoption holds `SELECT seq FROM _head … FOR UPDATE` and then publishes `_backend.generation` (`opening.rs:105-125`). A single statement that both locks `_head` and reads `_backend` takes its snapshot at statement start, before the lock wait; READ COMMITTED rechecks the locked row, not the other table. The writer then runs under the pre-activation generation. One ordered later command preserves the check. A join does not. Joining `_owner` and `_head` into one planner-ordered statement can also take the head lock first, which parent §5.1 changed because that order deadlocks with takeover (W10).

B2 then names tokio-postgres pipelining (`§3.6`) as the way to one flight. S1b already ran that experiment. Extended-protocol pipelines (k1, k3p) sat near 80 ms and failed the sizing rule at every connection count. The schedule that reached `k_exec = 2` was one SimpleQuery message per flight (k3), or one UNION statement (k2). k3p's flight count was also 2, so the budget's definition ("a pipelined flight is one wait") does not distinguish the mechanism that worked from the one that stalled (`postgres-commit-path/README.md` around the k1/k3/k3p table and the "k1 and k3p fail at every C" verdict).

§3.6 also forbids pipelining a data-dependent read. The measured mutation's second scan is after the update. With the client size gate kept, S1b's own floor for the read set was two flights, and the write cannot be in the first of them. Ingress, setup-plus-first-read, update, post-update read, and a finish that is not sent until that read succeeds is 5, not 4. Putting the interpreter's size gate or the post-update read into the same server statement is the B3 step §8 says it is not taking.

Folding COMMIT into that finish flight also makes §7's "outcome-unknown classification is unchanged" false. Today COMMIT is a separate message (`ownership.rs:129-131`); a failure before it is sent is a definite abort. Once COMMIT shares a payload with earlier statements, a lost finish flight is unknown even when the server never saw COMMIT.

Change: retarget B2 at ordered multi-statement SimpleQuery, which is what S1b cleared and which still gives each READ COMMITTED command its own snapshot. Keep the fence statement before the head-lock statement. Keep COMMIT as its own acknowledged flight until a server-side abort is specified and the widened unknown window is accepted in the parent's retry table. Set the mutation prediction from that schedule (5 for this program if the post-update read stays client-side). Move the raise-on-mismatch fence into the increment that first puts later statements in the same flight as the fence, and acquire `FOR KEY SHARE` before the raise.

### MAJOR — §1 and §9: K3/K4 is the right throughput tool and the wrong substitute for the execution-stage 2

The per-request claim is right. Seven framing flights are shareable (BEGIN, owner fence, head, generation, tail, SET, COMMIT). `57 / (50 + 7/16) ≈ 1.13×` at N=16, so batching the frame does not fix request latency. §10 is also right that each request still holds connections for the envelope.

§1 then says pre-execution "moves the envelope off the serial section." It moves the program's reads off the head lock (committer §1 and §4.2). The envelope is not in that section now: flights 1–28 and 43–57 are outside the durable transaction. The serial section today is the 14, of which 7 are the shared frame.

§9 tells the committer to size K3 with the B1/B2 request budgets instead of S1b's execution-stage 2. That 2 is `k_exec` for a captured read set. On that host the commit stage already binds at 4,256/s, and reducing execution from 10 to 2 did not raise the predicted ceiling further (committer §9; S1b re-size). The B1 mutation budget of 8 includes ingress and the commit flights. Substituting it for `k_exec` counts the commit stage twice and can un-clear a rule S1b cleared. Committer §7, which §9 cites, is the adaptive window, not that formula. The formula lives in the S1a/S1b notes and in LLP 3000.009.001.002 §8.

Change: keep K3/K4 as the serial-section win. Size the execution stage as S1b's program flights plus the authority statement this RFC moves inside snapshot S. Size the serial section from the §4 row once 3 and 1 are derived the way 6 and 8 are. Do not feed the full-request budget into `connections / (k·RTT)`.

### MAJOR — §8: deferring B3 is right; the trigger that reopens it is not

A server-side operation that includes rule checks, row changes, and the commit tail is a second executor. LLP 3000.009 §4.1 allows the store to take a batch of reads or a commit tail, and forbids it to evaluate a rule, an expression, or a filter. S1b says putting the client size gate into SQL is outside the experiment for the same reason. Declining B3 here is the right call.

The reopen rule is not the parent's. §8 closes B3 only if W1 p50 is within 2× of raw Postgres at 0.5 ms, and otherwise opens B3, reads first. It calls that "parent H2's rule." H2's 2× cell is the falsifier of the prediction `k = 5–8`, not a commission (LLP 3000.009.001.002 §3). The decision rule that governs this is §8 of that RFC: if W1–W3 p50 exceed 3× raw at 0.5 ms after prefetch, commission the next access-boundary step, and keep lowering declined unless that step also fails. B1's read count of 6 is already inside H2's predicted band. B2's 3 waits against raw's one statement is about 3× the network floor whenever RTT dominates, so §8 as written is likely to open the executor this RFC just rejected, and it skips the prefetch/batch step both 3000.009 §4.2 and S1b's k2/k3 results already point at.

Co-locating `serve` with Postgres is not the missing structural answer. The scale RFC treats the Unix-socket 0.05 ms cell as a reference only; the comparison hosts are separate. Say that under alternatives so it stays closed. The division of work to name instead is the one already commissioned: push access down in batches, keep semantics in the Rust executor.

Change: close B3 unless W1–W3 still exceed 3× raw at 0.5 ms after B2 and after the access-batch step. Do not cite H2's falsification threshold as the trigger.

### MINOR — §5: the ratchet holds the measured classes and will not see the holes above

A `cfg(test)` driver wrapper costs nothing in production, and an exact checked-in table is a real ratchet for whatever it drives. It has to count dependent flights (one Sync through ReadyForQuery), not `CommandComplete`, or B2's reduction never moves the table. As specified it drives the four unkeyed warm classes. Keyed first-attempt, replay-hit, action-claim sessions, and a refusal that still builds the preflight head can all grow outside it. Start the table with those classes, or the ratchet will certify the shape RT-A happened to send.

### MINOR — §3.2: one SELECT fits the guest resolution that was counted, not an action session

The measured guest resolution is the session UNION plus two worker-family reads (`identity.rs:219-232`, and the UNION already visible in `counts.json`). Those fields can be one statement, and on Postgres that statement is as consistent as today's REPEATABLE READ authority transaction. `live_session` then walks claims for `kind == "action"` (`authority.rs:237-238` into `family_authority_expiry`). That walk is data-dependent and is outside the 6. Keep it out of the guest statement, and do not let the B1 count be the action door's count.

### MINOR — §6: RT5's "one flight each" does not add up to the printed 8

Ingress + one setup flight + authority + three program flights + one finish flight is 7 for the measured program. §4 reaches 8 by charging setup as ≤2 or by splitting tail from COMMIT. The report's sum is the second of those. Make the row name the same eight terms the report does, so the ratchet's predicted count is one number.

### MINOR — §7 and §3.7: SQLite and §9.1 hold if the fence flight stays the Postgres adapter's

Removing duplicate snapshots and borrowing one snapshot is store-neutral, and §3.7 correctly leaves SQLite on `BEGIN IMMEDIATE` and WAL reads. Parent §5.1's first lock on Postgres is `FOR KEY SHARE`; on SQLite it is `BEGIN IMMEDIATE` (parent §6.2). §7 states the row fence as if it were both stores. The raise-on-mismatch statement belongs to the Postgres adapter. §9.1 rules 1–5 apply to the authority SELECT as §3.2 says; rule 6 is honored by resolving an absent `_read_sessions` at attach. No DDL and no signed arithmetic need to appear in that SELECT.
