## Material concerns

1. **§5 lacks replay-batch byte and owner-work bounds.** Sixteen eligible operations is a count bound, but each ordinary replay includes a transaction, actual effects, and `after_commit`; the owner audit says that the sole owner also services foreground work and timers. The query path explicitly has a between-execution work target and serialized-response budget. The replay path does not state their equivalents. Sixteen request envelopes may also exceed the existing 1 MiB HTTP request guard, and terminal effects are not necessarily small merely because event-ID count is limited.

   **Remedy:** Select replay prefixes by both count and encoded request bytes, preserving a legal ordinary single-intent fallback. Stop owner replay between complete intents on an explicit work target and response-byte policy; return a transport continuation separately from an execution failure. Since discovering a terminal's size may follow its durable execution, specify whether a final oversized terminal is returned alone or whether execution must be capped using an existing proven per-result bound. Never silently omit an already executed result as though it had not run. Keep ambiguity recoverable through identical replay bytes. Test request oversize, a large nonempty terminal, time-stop continuation, and a foreground operation queued behind a batch. Constants remain engineering choices, not latency guarantees.

2. **§4 gives competing atomicity boundaries when the journal forces smaller commit groups.** It first says to validate every frame and commit the chunk once, with a malformed frame rejecting that uncommitted chunk. It then permits splitting one transport batch into multiple local commits to stay under the 256 KiB changed-key history. Whether earlier subgroups may persist before discovering a later invalid frame is consequently unclear. Structural decoding alone does not discharge cross-frame same-sequence contradiction or authority checks.

   **Remedy:** Define “transport batch” and “local commit group” separately. State whether full transport preflight finishes before any subgroup commit, and which failures can still leave a durable subgroup prefix. Every subgroup must repeat the live commit-time fences, advance its own checkpoint atomically, and earn acknowledgements only for its persisted content. If whole-transport atomic rejection is required, choose transport bounds that permit one local commit or provide a concrete preflight design; do not imply that separate carrier commits are atomic together. Test failure and logout between subgroups, including a contradiction in the final subgroup. Specify the progress-preserving fallback when one legal page alone exceeds journal history; otherwise adaptive shrinking can become a non-advancing policy.

3. **§§5–7 need an explicit performance treatment of unresolved nonempty effects.** The plan correctly forbids using an unrelated application tail as evidence that receipt effects were observed. The audit also reports that such effects can leave terminal history unresolved and that `compactSuccesses` repeatedly scans that history and answers. Grouping commits reduces scan frequency but does not establish that this retained work or its growth is acceptable, especially for the fully initially-unreceived cohort. “All obligations settled” must not accidentally become “all effect-observation obligations discharged.”

   **Remedy:** Define the endpoint predicates separately: durable content, settled acknowledgement intent terminals, owner receipt truth, usable required queries, and any still-unresolved observation custody. Record unresolved terminal/effect count, retained bytes, and compaction work for both receipt cohorts. If the residual dominates, require an attributed follow-up design that either obtains genuine observation evidence or improves existing history processing without deleting custody; an application tail's sequence alone is insufficient. The plan need not solve that optimization before its first experiment, but it must name this as a possible blocker to the target rather than assuming one shared tail removes it.

4. **§7 should distinguish acquisition timing from validation-induced work and make foreground interference reproducible.** Exact never-opened thread/search readiness is appropriately required, but the timing endpoint does not explicitly say that the first invocation and any lazy index construction finish inside the measured interval. “Report foreground admission/commit” also lacks a defined injection point, so comparing runs could inadvertently compare different workloads.

   **Remedy:** Freeze a precise clock start and end predicate before candidate tuning. End only after required first-use thread/search results complete and match expected contents, alongside durable content and settled acknowledgements. Define whether foreground probes belong to the primary cohort or a separate matched responsiveness cohort, with a repeatable progress-triggered injection. Record physical reopen as a separate verification run unless its cost is explicitly included in the target. Ensure every timed sample starts from the same receipt and client-store state; receipt writes make fixture reset essential. Keep the ten alternating pairs as final qualification, preserving failures and both receipt cohorts.

## Simplification and deletion opportunities

- Prefer the audited persisted page-chain resume option over a new checkpoint metadata owner if its authority and cursor equivalence can be demonstrated. Conservative idempotent restart remains preferable to an unproved efficient resume.
- Keep prefetch out of the initial implementation. Sequential bounded batches already isolate transport, commit, admission, and settlement effects for attribution.
- Unify single/many admission and settlement preparation. Do not create a second replay state machine or carrier validation bypass.
- Deleting repeated decode/normalization passes through a private owned immutable prepared object is a stronger candidate than a speculative cache. Mutation-after-validation controls must cover this optimization.
- Preserve the audited 90,000 gzip-byte ceiling and 1,500-source-line constraint; name the latter in the plan alongside canonical size checks. The reported 976-byte runtime headroom is too small to treat factoring and deletion as optional cleanup.

With the boundary revisions above, proceed to bounded implementation and attributed measurement. Keep the 2–3-second objective open until qualifying results establish it; no reviewer verdict can substitute for that evidence.
