# Round 1 — Claude Fable 5

### 1. Position

**Conditional yes.** One closed language can be the only data-plane language and keep static read sets, retention, authorization, and local re-execution — *provided the restriction is on computational class and the operator set covers the LLP 0120 census, including per-viewer aggregates*. The mechanism my answer rests on is a **cardinality-typed plan whose closure is statically shaped and dynamically windowed**: the compiler proves the *shape* of every read (table, index, prefix arity, per-stage cardinality ceiling, rule dependencies) and the trusted executor records the *windows* actually touched (index ranges including empty ones, the rows in them, rule witnesses or opaque verdicts). Shape makes admission, prediction closures, and noninterference provable before execution; windows make the retained closure exact and invalidation precise. Neither half alone answers the founder: shape-only is Snapback's table-granular `reads:`; window-only is Convex. The conditions: (i) `with`/`maintain`/`recurse`/`when` are operators of one algebra, not profiles; (ii) the common one-hop membership rule costs one examined entry (hoisted), or `public` becomes the path of least resistance again; (iii) the dev loop is co-equal (0329.000 F-B) — the language cannot win Clique alone.

### 2. The crux question

Take `messages(conversation)` under `messages.read = exists(memberships[(conversation, viewer)])`, served at snapshot S with result R and recorded read set T = { `messages.byConversation[conv, +∞ … at₂₀₀]` with 200 rows plus the 201st boundary key; `memberships[(conv, V)]` present — own membership is viewer-readable, so the row ships, not a verdict }.

**Cold retention of unchanged data.** The claim is false here: a result cache already re-renders R; T only makes the closure checkable, and re-executing f over T reproduces R by construction.

**(a) Local optimistic `send` offline.** The client runs `send`: evaluates the `messages.insert` rule — the membership witness is in T. Inserts a row with `at = local clock`; its key lands at the *top* of the descending range, inside T's recorded window (the scan started at +∞). Re-executes f: 201 rows seen, 200 taken, `messages.read` on the new row uses the same witness. Prediction works. **But** suppose f also did `users[m.author]` per row (the Convex in-function join) and V has never posted here: re-execution issues a read T never recorded. Because T carries absence ranges, the client can tell *unknown* from *absent* and must answer `partial` — honest, but after the fact. A closed language answers *before* the fact: the compiler sees `send` writes `messages{author: viewer()}` and `messages` nests `users.byId(m.author)`, substitutes, and emits a **prediction closure** `users.byId(viewer())` for the pair (`messages`, `send`), hydrated at subscribe time. Static derivation knows the read pattern for rows that *do not exist yet*; a trace knows it for rows that did. That is the entire difference, and it sits on the prediction case.

**(b) Local delete of one held row.** The delete rule `old.author = viewer()` evaluates from the held row. Re-executing f yields 199 rows and a `take(200)` that on the server would pull the 201st row; T holds its key, not its content. Result: 199 rows, `partial` (window under-filled, boundary known). Static and dynamic give the identical answer; neither can do better without the row.

**(c) Membership revoked while offline.** Nothing on the device changes; no mechanism, static or dynamic, can inform it. It shows `stale`; the queued `send` stays `queued`. On reconnect the server re-authorizes the intent inside its transaction, rejects it, and the recorded local write set is inverted; the subscription for `(messages, conv, V)` carried `memberships[(conv,V)]` as a dependency key, so the server delivers the retraction — LLP 0053's "shrinking of the result set is the security event" obligation, unchanged — and the client purges. Equal on both sides, *provided the server keeps dependency keys*. The one divergence: if V locally **leaves** the conversation while offline, a closed rule re-evaluates locally (`exists` → false; messages vanish, matching what the server will do); an *opaque verdict* can only be marked invalidated, never recomputed. Verdicts serve rules whose inputs are hidden; for rules over viewer-readable inputs the rule must be a program the client can run — i.e. in the closed language.

**Three things "ship the read set" presupposes.** (1) *Row-level rules in the data.* A function's read set is not a disclosure boundary: a Convex-style function reads whatever the code reads (an email column to derive a display name) and returns less. Shipping T is safe only if every row in T passed the viewer's read rule or became a verdict — authorization must already be a property of rows, not of the function. Under "function = authorization," T is unshippable in general. (2) *Range extents leak.* A recorded range over a hidden table reveals how many entries were examined (LLP 0120 §Noninterference); redaction must be conservative — verdict only, no extents — which removes precisely what a local count would need. (3) *Closure ≠ result.* For `boardSummary` written as scan-and-count, T is every card on the board; the result is five integers. Tracing makes the aggregate offline-*possible* at closure = scanned population, unbounded; the closed language forces the choice between `Page.count` (closure = page) and `Maintained` (closure = one row).

**Verdict on the claim.** As stated — "cannot be re-executed" — it is false: with T, an arbitrary deterministic function can be replayed for unchanged data and re-run after local writes with honest miss detection. In the form that matters it is true: it cannot be re-executed **for prediction with completeness known in advance**, because a trace describes the read pattern for the data that was there, and control-flow-dependent reads on a predicted row are undecidable for arbitrary code and computable at `check` for a closed one.

**Where each wins, and composition.** Tracing beats static derivation on exact window contents, precise invalidation, and reactivity for *any* code. Static beats tracing on prediction closures, admission before execution, noninterference proofs, and knowing what to hydrate for args never yet executed. **They compose, and the composition is the design**: static shape from the closed language; dynamic windows recorded by the trusted Rust executor of that plan; the recorded windows doubling as a runtime assertion that the derived shape covered every read (0329.005's compiler-bug detector). What does *not* compose is the P2 hybrid — arbitrary-JS queries with traced closures beside closed-language mutations: offline prediction would work in dev (small data, traces cover everything) and go `partial` in production, which is capability-by-spelling with the discovery point moved from codegen to runtime. Worse than today.

### 3. Your proposal

**Proposal A (primary): a bound-carrying algebra with static shape, dynamic windows, and prediction closures.** Three kinds — `view`, `transition`, `effect`. One language for the first two; effects are JavaScript outside the data plane and change data only by applying a transition.

*Admitted.* `byId`/`byKey`, index-prefix `where`, `order`, `take`, `one`, `with` (bounded nest along a ref or index), `exists`, `when` (expression-level conditional over row values), `count`/`sum` over a `Page`, `countCapped`, `maintain` (same-commit count/sum by group key), `recurse(start, step, {depth})`, `map` with scalar expressions, `viewer()`, `commitTime`; transitions add `insert`/`update`/`delete` over key-bounded sets, `require`, `alloc` (LLP 0135's sequence primitive), `newId`. Cardinality is a type: `Unbound<T>` is a legal intermediate and an illegal result; `Page<T,N>`, `Row<T>`, `Maintained<T>` execute.

*Refused at `check`, at the span, with one rewrite that never weakens a rule:* JS control flow over row values (the builder runs at build time and constructs an immutable AST; row values are expression objects); `now()`/`random()`/I/O; dynamic table or column names; `count` on `Unbound`; a plan whose worst-case examined product exceeds the app ceiling `G` (default 10,240, loud override); an unconditional read rule without `public(reason)`; a table without rules; a filter not served by an index or ref (rewrite: the index); a `maintain` whose source's read rule depends on columns outside the group key (existence leak).

*Derivation artifacts.*

- `ReadShape(op)`: (table, index, prefix arity, take) tuples plus rule-dependency tables, computed by inlining rules into the plan. A rule whose predicate depends only on columns pinned by an equality filter is **hoisted** and evaluated once — this is what makes the membership rule cost 1.
- `Bound(op)`: examined ceiling and result cardinality (`with`: parent card × (n+1); `recurse`: Σ Fᵏ; `exists` over a `Row`: 1).
- `Certificate(op)`: `{shape, examined, resultCard, ruleDeps, closureCeiling, prediction, lowering}`, emitted as `snapback.certificates.json` beside the generated client and printed by `check`.
- `Closure(op, args, principal, S)`: recorded by the Rust executor per execution — windows with rows, absence ranges, rule witnesses (viewer-readable) or verdicts with dependency keys (hidden). Shipped with the result; stored client-side under `(PlanHash, args, principal)`.
- `PredictionClosure(view, transition)`: symbolic substitution of the transition's writes into the view's nested reads; windows depending only on `viewer()`, constants, or view args are hydrated at subscribe; anything else is an honest runtime `partial`.
- `Intent`: `(PlanHash, args, baseSnapshot, localWriteSet, inverse)` in the outbox; `predicted | queued | committed | rejected`. Reads: `hydrating | fresh | stale | partial`. The only states; no constructor changes them.
- Invalidation: each commit's write keys (rows, index keys, maintained rows) are intersected with subscribed windows and rule dependency keys; hits re-execute at the new snapshot and diff. Rerun-and-diff is the v1 lowering; `maintain` is v1's only incremental path.
- Revocation contract, once: the server authorizes at disclosure; a per-principal encrypted store whose key dies at sign-out; offline shows `stale`; reconnect presents `(keys, S)` and the server re-executes and retracts; queued intents are re-authorized in the commit transaction; `maxOfflineAge` is a uniform app policy. No leases as objects, no per-query custody class.

*Substrate.* Views and transitions execute in **Rust over the IR** inside the SQLite transaction; JavaScript is not in the authoritative data path. Effects run out of band in a sandbox — the DK-5 posture survives for effects only, and never holds the write lane. The **client is a closure cache + outbox + IR evaluator** in TypeScript, engine-agnostic (Hermes, V8, JSC): the operator set above over in-memory windows, a store adapter, sync, one React hook. It stays small because there is one code path per kind and no holes to implement — no retention classes, leases, custody modes, or completeness proofs; completeness is "did every read hit a recorded window." It cannot issue a query the model did not name; cross-closure row reuse is a later optimization, not v1.

*Postgres graduation.* Same IR, second lowering: `with` → `LATERAL … LIMIT`; `recurse` → `WITH RECURSIVE` with a depth column and the proven ceiling as `LIMIT`; `maintain` → engine-applied same-transaction updates; snapshots via `REPEATABLE READ`, transitions under `SERIALIZABLE` with retry. Admission is proven at `check`, so the engine's optimizer is never trusted for bounds. Invalidation uses the engine's own write sets; v1 requires the engine to be the only writer (no logical replication — LLP 0155's "do not import for parity").

**Proposal B (fallback, ranked second): same language, no client evaluator.** The compiler emits per-`(view, transition)` *patch programs* (insert-at-window-top, delete-from-window, update-in-place) the client applies to cached results; nested, maintained, and recursive views predict as `partial`. Smaller client, but predictability now varies by view shape — a matrix cell, visible in the certificate but a cell. Build A; fall back to B only if the evaluator measures too large on device.

### 4. Worked examples

Spelling: TypeScript build-time builder (P4a). The IR is the contract; a SQL front end (P6) is equivalent, and the choice should be a census bakeoff.

**Clique private chat**

```ts
import { table, id, text, time, ref, exists, viewer, view, transition, commitTime, public } from 'snapback'

export const profiles = table({ id: id(), handle: text().unique() })
  .read(public('handles are discoverable'))            // conspicuous; unlocks nothing
export const accounts = table({ id: id(), email: text() })
  .read(a => a.id.eq(viewer()))
export const conversations = table({ id: id(), title: text() })
  .read(c => memberOf(c.id))
export const memberships = table({ conversation: ref(conversations), user: ref(profiles), joinedAt: time() })
  .key(['conversation', 'user'])
  .read(m => memberOf(m.conversation))
  .write({ delete: m => m.user.eq(viewer()) })
export const messages = table({ id: id(), conversation: ref(conversations), author: ref(profiles), body: text(), at: time() })
  .index('byConversation', ['conversation', 'at'])
  .read(m => memberOf(m.conversation))
  .write({ insert: m => m.author.eq(viewer()).and(memberOf(m.conversation)),
           delete: m => m.author.eq(viewer()) })

const memberOf = (conversation) => exists(memberships.byKey({ conversation, user: viewer() }))  // Row → examined ≤ 1

export const thread = view({ conversation: ref(conversations) }, ({ conversation }) =>
  messages.where('byConversation', { conversation }).order('at', 'desc').take(200)
    .with({ author: m => profiles.byId(m.author) }))

export const send = transition({ conversation: ref(conversations), body: text() }, ({ conversation, body }, tx) =>
  tx.insert(messages, { id: tx.newId(), conversation, author: viewer(), body, at: commitTime() }))
```

Certificate for `thread`: shape `{messages.byConversation[conv,*] take 200; profiles.byId ×200; memberships.byKey[(conv,viewer)]}`; `messages.read` hoisted (pinned by `conversation`) → 1; examined ≤ 201 + 200 + 1 = **402**; result `Page<Message & {author: Row<Profile>}, 200>`; ruleDeps `{memberships}`; prediction closure for `send`: `profiles.byId(viewer())`. `send` predicts locally against the closure; `at` is provisional until the settlement delta.

**Relay `boardView`** (cards carry a denormalized `board` so their rule hoists):

```ts
export const boardView = view({ board: ref(boards) }, ({ board }) => ({
  board:    boards.byId(board),
  columns:  columns.where('byBoard', { board }).order('position').take(20)
              .with({ cards: c => cards.where('byColumn', { column: c.id }).order('position').take(100) }),
  activity: activity.where('byBoard', { board }).order('at', 'desc').take(50),
}))
```

One snapshot. Examined ≤ 1 + 21 + 20·101 + 51 = **2,093**; three rules hoisted on `board` → 3. Result type inferred as the nested object.

**Relay `boardSummary`**

```ts
export const cardCounts   = maintain(cards, { by: ['board', 'column'], count: true })   // same-commit ±1
export const boardSummary = view({ board: ref(boards) }, ({ board }) =>
  cardCounts.where('byBoard', { board }).take(20))
```

Read examined ≤ **21**, exact over an unbounded card population; write path +1/−1 (a column move is −1/+1); sum overflow refuses the write. Admitted because `cards.read` depends only on `board`, which is in the group key — otherwise refused as an existence leak.

**Split ledger** (participants, profiles, expenses, shares):

```ts
export const paid = maintain(expenses, { by: ['group', 'payer'], sum: 'amount' })
export const owed = maintain(shares,   { by: ['group', 'participant'], sum: 'amount' })
export const ledger = view({ group: ref(groups) }, ({ group }) =>
  participants.where('byGroup', { group }).order('joinedAt').take(64)
    .with({ user: p => profiles.byId(p.user),
            paid: p => paid.byKey({ group, payer: p.user }),
            owed: p => owed.byKey({ group, participant: p.user }) })
    .map(p => ({ ...p, balance: p.paid.sum.orElse(0).minus(p.owed.sum.orElse(0)) })))

export const addExpense = transition(
  { group: ref(groups), amount: int(), split: list({ participant: ref(profiles), amount: int() }, { max: 64 }) },
  ({ group, amount, split }, tx) => {
    const e = tx.insert(expenses, { id: tx.newId(), group, payer: viewer(), amount, at: commitTime() })
    tx.insertEach(split, s => tx.insert(shares, { expense: e.id, group, participant: s.participant, amount: s.amount }))
  })
```

Examined ≤ 65 + 64·3 = **257**; exact balances over unbounded history (LLP 0120 OQ8 answered by `maintain`). `addExpense` predicts through the maintained rows because maintenance is part of the transition IR the client also runs, and `paid`/`owed` rows are in the ledger's closure.

**Bounded traversal**

```ts
export const folderPath = view({ folder: ref(folders) }, ({ folder }) =>
  recurse(folders.byId(folder), f => folders.byId(f.parent), { depth: 32 }))     // examined ≤ 33, visited-set

export const friendsOfFriends = view({}, () =>
  recurse(follows.where('byFollower', { follower: viewer() }).take(50),
          e => follows.where('byFollower', { follower: e.followee }).take(50), { depth: 2 })
    .with({ profile: e => profiles.byId(e.followee) }))                          // ≤ 51 + 50·51 + 2,550 = 5,151
```

### 5. Evaluation of LLP 0329.005's P4

*Right.* Restriction as computational class, not operator poverty; cardinality as a type; `Maintained` as the only exact-over-unbounded aggregate; named operations as the sync unit with compile-time inlining; effects as a different kind; static shape + dynamic windows (its F1 is the crux answer in embryo); the P2 rejection. Its spike is the right falsification; run it first.

*Where it fails or costs.* (1) **Row-rule affordability is the first thing an agent hits, not a low-confidence tail.** Co-member visibility (`users.read = shares a conversation with viewer`) is a two-hop `exists` over an `Unbound`; the calculus refuses it or prices it at hundreds per row. Without hoisting and a paved template, `public` profiles become the path of least resistance — P18 with a different table. The diagnostic's templates must include the honest third: split public profile from private account, or a `maintain`ed contacts closure with a write-side fan-out cap. (2) **No prediction closure.** P4 says the client interprets the IR over the closure but not how the closure for a row that does not exist yet is obtained; §3's `(view, transition)` artifact fills it. (3) **One global ceiling with pessimistic products** refuses legitimate boards (50 columns × 200 cards), and agents will shrink `take` and ship silently truncated UIs. Continuation cursors must be first-class in the algebra so "bounded" never means "wrong." (4) `maintain` couples the write path to readers; fan-out maintenance (per-viewer unread) is bounded only by product caps (members ≤ 256) — a real spec: preimage, group move, overflow, idempotent replay. (5) Duplicate rows across overlapping closures — fine for v1, memory ×k.

*Is refusing row-level `if`/`for` necessary?* **Merely convenient** — for the P4a spelling. A build-time builder cannot evaluate a JS `if` on a row that does not exist at build time, so JS control flow must go; but the *guarantees* need only (i) statically known key domains, (ii) static cardinality bounds, (iii) no control flow the compiler cannot see. An expression-level `when(cond, a, b)` (SQL `CASE`) and iteration as `with`/`map` over a `Page` satisfy all three; a conditional nest's static closure is the union of branches and its dynamic window the branch taken — the composition again. Refuse the syntax, admit the semantics.

*Census score against Convex.* Relay `boardView`, `boardSummary`, and Split `ledger` each become one named view with an inferred type — **parity on terseness** with Convex's one function (LLP 0120's measured gap was contract verbosity plus refused shapes; both are gone). Snapback ahead on offline prediction, bounds, and inspection. Convex ahead wherever the agent wants a per-row computed field or a scan-count ("just loop"), and on **the first per-viewer aggregate** (§6). Net: P4 closes the composition loss; it does not touch the Clique losses that were lifecycle and media, and says so.

### 6. Refusals and objections

*Cannot express, honestly:* ranked-by-score feeds (an effect materializes `rank`); `now()`-relative windows (pass `since`); exact `min`/`max` under deletion (v1); full-text search (later operator or effect-maintained index); arbitrary per-row computation (UI or effect); dynamic table selection; client-invented joins with completeness; a global total over rows the viewer cannot see (existence leak — refused, not degraded); unbounded closures ("sync the table").

*Three strongest objections to my proposal.* (1) **It is a compiler and a planner**, and LLP 0120 measured ~700/~1,700 reviewed lines per shape. Answer: those were product specifications — cursor, live class, refusal grammar, maturity per shape; an operator's bound rule is a line in a calculus. That is a judgment; the spike falsifies it in a week. (2) **Effects-that-materialize-tables is a second class with staleness as the invisible capability.** Answer: the boundary is conceptual (a background job is not reactive), and the diagnostic never offers it as a repair for a query-shaped problem — but this is the residual risk, and I would instrument how often agents reach for it. (3) **The worst-case bound calculus is pessimistic**; real data is skewed, `G` refuses real boards, and hoisting is a heuristic that will miss rules agents write. Answer: app-level ceiling with a loud default, first-class cursors, and a certificate that prints the un-hoisted rule with the column that would pin it.

*Most likely way it loses Clique to Convex.* Not `boardView` — **the inbox's per-conversation unread count** (M2). `messages.where(conv).where(at.gt(lastRead)).count()` is `Unbound.count()` → type error. Convex just counts. The paved rewrite must be in the diagnostic and must be what real chat apps do: `.take(100).countCapped()` rendering "99+", with `maintain` per `(conversation, viewer)` (fan-out ≤ member cap) as the exact alternative. If that diagnostic is one word short, the agent writes an effect or makes something public. Second most likely: the dev loop, which no language fixes.

### 7. Confidence

- Capability-by-form is the root defect and one closed data-plane language is the fix — **high**; four attestations and three families.
- "Cannot be re-executed" is false as stated, true for prediction-with-completeness — **high**; it follows from determinism plus a trace's inability to describe reads on rows that do not exist.
- Static shape + dynamic windows compose and both are required — **high** for composition; **medium-high** that the composition covers the census without a thirteenth special case (the spike decides).
- Prediction-closure derivation covers the Clique/Relay/Split transitions — **medium-high**; symbolic substitution is mechanical for inserts and key-bounded updates; I have not worked `recurse` views under prediction.
- One-hop membership rules cost 1 via hoisting — **high**; two-hop rules affordable only via schema split or `maintain` — **medium**, unmeasured on SQLite.
- `maintain` is affordable at Clique scale — **medium**; hot-key contention is LLP 0120's named, unmeasured expectation.
- Refusing `if`/`for` is a spelling artifact — **high**.
- The client stays an order of magnitude below 212k lines — **medium-high**; the evaluator is small, but every past client started small; the discipline is "no holes to implement," not a line budget.
- P4a beats P6 on agent time-to-green — **low**; bakeoff.
- The language alone moves the Clique scoreboard — **low**; Diary 0114's losses were lifecycle and media (0329.000 F-B).
