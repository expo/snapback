NOT READY

This is a well-scoped proposal, but it is a proposal only. I found no live-through mechanism in this checkout to evaluate against it, and the RFC itself defers three load-bearing mechanisms to future design (§6). Per the RFC's own rule, that alone requires NOT READY.

What I checked: the parser accepts only `read through .ref` as `$readThrough` ([parser.rs](snapback4/crates/snapback4-lang/src/parser.rs)), with no `live` keyword. The binder implements captured-through only, including the immutability refusals this RFC wants to escape ([through.rs](snapback4/crates/snapback4-lang/src/bind/through.rs)). The engine stamps captures at insert and resolves parents live only at insert time ([through.rs](snapback4/crates/snapback4-core/src/engine/through.rs)). Device compat is keyed on `sync-generation-v1` plus per-schema capabilities ([device_protocol.rs](snapback4/crates/snapback4-core/src/device_protocol.rs), [capabilities.rs](snapback4/crates/snapback4-core/src/schema/capabilities.rs)), with no live-through capability. Partition grants are per-group logs with no epoch or scope registry ([partition.rs](snapback4/crates/snapback4-core/src/partition.rs)).

Blockers — each needs an executable mechanism, not prose, before READY:

- **No executable artifact.** There is no grammar, IR node, binder validation, engine evaluator, price function, wire format, or test for `read through live`. The instruction is to require a mechanism, not assume one. Status: missing.
- **Grant indexing and metering (§4) is asserted, not designed.** The "parent audience index" and "parent-to-child-scope registry" have no schema, durability, memory bound, or reservation price. Compare the existing `capture_price` path; nothing analogous exists for live scope admission. Action: specify the registry representation, its per-transaction charge, and the algorithm that maps a membership write to affected parent epochs without walking child rows.
- **Epoch bump fan-out is unspecified.** A roster change lives in a membership table, not the parent row. Which transaction increments which parent epochs, at what bounded cost, and what refuses when that budget is exceeded? Without this, "work proportional to grant changes plus schema edges" is a claim, not a bound.
- **Atomic delivery batch is unbounded and single-partition.** One batch carrying "descriptor + grants + revocations + watermark" has no size bound and no stated behavior under multi-partition polling — both flagged as open risks in §6. Action: give the batch encoding, its ceiling, and the multi-partition case, or narrow the claim.
- **Mutable expiry has no sweep or index design.** Today's sweep relies on the stored effective-deadline index. A live minimum over current ancestors has no stored column by design, so descendants are undiscoverable at sweep time. §6 admits this is unresolved. Action: specify how the sweep finds live descendants, or store something.
- **Device generation refusal has no token.** §4 says old devices "must refuse that generation," but names no capability or generation value. Action: add the capability string, wire it through `required_capabilities`, and show an old device refusing.
- **Dual-store atomicity is asserted.** "Persisted atomically in IndexedDB and SQLite" plus reorder/duplicate/crash safety needs a transaction protocol for each store. None is given. Action: specify the record layout and the crash-between-descriptor-and-data recovery.
- **Negation and redaction semantics are missing.** "Missing/dormant/expired/unknown parents never grant, including underneath negation" states a security property with no evaluation rule for a negated live edge. "Private parent field values never appear in outputs, cursors, or refusals" needs a redaction point; parent field values are the rule inputs being evaluated. Action: define both, with tests for negated and refused reads.
- **Fixed charges have no numbers.** "Fixed reservation per node and per syntactic probe; denied/missing restore the same charge" needs a price function and a meter test. Today that role is played by `capture_price` and the reservation plans; the live path has neither.
- **Cascade exception is undefined.** §2 permits parent delete under "an explicitly admitted cascade [that] deletes its complete closure." The reference-action pass currently restricts cascade on read-through children. Action: define "complete closure" for live children and the guard against partial cascades orphaning authority.
- **Completeness witnesses are unnamed.** Parent-keyed uniform scope needs a device-checkable coverage witness for the parent, the child range, and lifetimes. "Unknown yields unknown" is correct policy but not a representation. Same for aggregates across parent keys and the time witness deferred in §2.
- **Invalidation granularity is unbounded.** "Broad table dependencies are correct" concedes that any roster edit can invalidate every subscribed child read. That is safe but potentially unbounded work per membership write. Action: bound it or quantify the acceptance.
- **Adoption scan is unbounded.** Validating "all physical child links" and rebuilding the registry on activation needs a chunked, metered plan with a refusal path that publishes nothing. Currently prose.

High (not sufficient alone for READY, but must fix):

- Lane fit is unchecked. §4 restricts the initial case to a single public/principal/membership audience. Show that lanes 007, 032, and 085 parents actually qualify, or the first implementation serves no stated lane.
- held-watch and same-transaction policy visibility (§3) need executable tests, not just dependency prose.
- `sync ... last N by .index` bounds per-scope acquisition but not total scopes per viewer. State the global bound.
- Rollback "revalidates rather than trusting old captures" needs the revalidation algorithm; otherwise rollback is a second adoption with the same unbounded scan.

What would flip this to READY: a revision that (a) implements or pseudocodes to meter-and-test level the epoch registry, the atomic batch, and the sweep story — the three §6 risks — and (b) adds the grammar, IR node, price function, capability token, and redaction/negation rules with failing-then-passing tests. Until then the recipe fallback is the right path, with the unresolved questions above as its input.
