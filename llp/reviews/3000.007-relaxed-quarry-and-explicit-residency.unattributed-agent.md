## The review, verbatim

• Yes. I think LLP 3000.007 (llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md) points in the right direction, and I would push further on Quarry's expressiveness. But I would revise several technical claims before implementing it, and preserve more of 3000.006's work on projections and acquisition.

My preferred direction is: Quarry should comfortably express ordinary data processing, while Snapback makes authorization, execution location, completeness, and cost explicit. A small language is valuable when it makes the whole application smaller. Requiring a database work table to emulate a local accumulator defeats that purpose.

The diaries support that direction, although they also show that language restrictions are only one limiting factor.

| Limiting factor | Evidence | What I would change |
| --- | --- | --- |
| Ordinary computation takes unusual forms | The earlier Clique builder used a transactional work row to calculate digest totals and explicitly wanted familiar collection and arithmetic code. | Admit accumulators, reassignment, ordinary control flow, text concatenation, and arithmetic. These are justified additions. Builder essay (benchmarks/runs/2026-09-13-snapback4-clique-0003/builder-essay.md:19) |
| Operations compose poorly with client state | Builders needed an extra query to recover a mutation's return value, another to recover pending, and custom persistence for the WASM runtime. | Return typed mutation results, preserve pending state through supported projections, and make offline reopening a complete SDK responsibility. Current diary (benchmarks/runs/2026-09-13-snapback4-clique-0004/astra/diary.md), mutation-result audit (benchmarks/runs/2026-09-13-snapback4-clique-0004/grok-client-attribution-audit.md:12) |
| Concise declarations can replicate excessive data | Removing unnecessary counters reduced one snapshot from 45,719 to 22,099 events; observed startup fell from roughly 30 seconds to 14–15 seconds. | Show replica contents and measured bytes by table, including inherited maintains; make compact synced projections easy to build. The timings cover whole startup and do not isolate device application cost. Startup audit (benchmarks/runs/2026-09-13-snapback4-clique-0004/replica-startup-audit.md:13) |
| Predictability depends on facts builders cannot readily see | A seemingly harmless existence guard stopped message prediction because the replica could not establish absence beyond its horizon. | Explain prediction eligibility at compilation and explain the actual missing fact at runtime. Distinguish durable submission from successful prediction. Current essay (benchmarks/runs/2026-09-13-snapback4-clique-0004/astra/essay.md:9) |

Some of those client problems match the documented contract—the pending-shape and mutation-return audits establish that. That changes their classification, but does not make them good ergonomics. We should count the application work they cause even when the builder labels it "my mistake."

I would expand Quarry beyond the seven proposed conveniences in four specific ways:

- Composable collections. Make mapping, filtering, folding, grouping, and sorting work consistently on bounded collections. Preserve the distinction between a complete input and a page of a larger input. Developers should be able to calculate a digest without manufacturing durable scratch state.
- Reusable helpers with ordinary bodies and return values. Reconsider the fn/proc split and infer which helpers read, write, or emit. A query must remain read-only, but that does not require two different helper languages.
- Runtime-bounded ranges and a small standard library. An argument-dependent finite range should not require literal endpoints. Text normalization, joining, and date bucketing deserve supported forms where applications repeatedly need them. I would prioritize these ahead of unrestricted recursion or expanding Quarry into a numerical-computing language.
- More natural indexed queries. Support predicates and straightforward joins with visible access plans. Let the compiler translate suitable predicates into index ranges; a where implementation that merely examines and rejects rows leaves much of the reporting problem intact.

These additions should share types, dependency tracking, meters, and execution semantics. The native Rust facility remains useful for substantial numerical algorithms. Ordinary application arithmetic should be comfortable without reaching for it.

There are four places where I would correct 3000.007 before building it.

1. The meter needs work before it can justify the relaxations. The draft says the interpreter already supports the necessary operations and needs almost nothing. It does support them, but Concat (snapback4/crates/snapback4-core/src/engine/runner.rs:417) allocates without charging the heap meter, and variable evaluation clones strings and arrays. Reassignment plus repeated concatenation substantially changes the reachable allocation patterns. Reserve capacity before growth, account for copying, and test bounded failure. This is also an explicitly unresolved concern in 3000.002 (llp/3000.002-end-to-end-resource-bounds.research.md:66). These are code-inspection findings; I did not run new stress tests.

2. The proposed filtered cursor changes the disclosure contract. Section 5.1 resumes after the last examined row. That row may be hidden by authorization. Current cursors contain base64-encoded index values; they are not encrypted (snapback4/crates/snapback4-core/src/cursor.rs:51). Using that position could expose a hidden row's key. The proposed completeness rule also omits the existing non-uniform authorization class. I would initially support this continuation behavior for uniformly authorized ranges and separately design the non-uniform case.

3. The locality classification is too coarse. "Every table is synced" does not establish that a particular device holds the required rows—or can prove their absence. The draft's own failed-prediction example demonstrates this. Keep static capability information, plus runtime coverage checks. Also keep queueability independent: a command can be durably queued even when its eventual execution needs server reads. 3000.006's classification of individual read sites (llp/3000.006-explicit-data-residency-and-server-execution.rfc.md:176) is a better starting point, though I would simplify its vocabulary.

4. The Trending rewrite is not equivalent. Sorting the newest 200 posts by likes gives the top ten among those 200. It can omit the most popular post from the same day. Keep the maintained ranking, or establish that the entire candidate set was examined. More generally, aggregates and ranking must preserve information about incomplete inputs. Proposed rewrite (llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:352)

I would also reconsider the blanket requirement that every admitted form run on every device. Shared semantics are valuable; identical host capabilities are unnecessary. Native reads already have different availability across hosts. Similarly, an operation explicitly updating the first 50 authorized matches need not claim to update an entire population. We can support such server transactions with atomic rollback and metering while retaining stronger completeness requirements for operations that promise "all members" or "the exact total."

For functionality outside Quarry, I would prioritize worker actions ahead of SQL reads. Interview provides a useful second application for testing integrations, authentication providers, and model calls. Actions should use generated argument/result types, explicit caller authority, stable request identity, and recoverable settlement through the existing worker mechanism.

The SQL proposal needs more design. As drafted, its views cannot use Quarry's secondary indexes, and it introduces another authorization translation. SQLite's progress handler counts approximate virtual-machine instructions; it does not supply Snapback's complete resource contract. SQLite documentation I would first improve Quarry's collection/query facilities and measure what reporting still cannot express economically.

My implementation order would be:

1. Repair metering, land the ordinary language conveniences, and close the mutation-result, prediction, and offline-startup gaps.
2. Deliver residency explanations together with compact projections and acquisition measurements from 3000.006. Add an SDK-managed ordinary-media cache with explicit retention; exclude view-once media.
3. Add composable helpers and collections, then exercise worker actions in Interview and rerun Clique.

I would judge success by fewer work tables, fewer auxiliary queries, less client lifecycle code, correct complete answers, and faster acquisition. The existing runs identify those targets well. Their differing clocks, small samples, and pending independent grades do not yet establish that Snapback4 is broadly faster than the alternatives.
