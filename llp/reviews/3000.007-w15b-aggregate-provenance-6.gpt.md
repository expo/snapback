**Finding — Medium: special builtin contexts can acquire a helper’s unrelated provenance.**

Location: [aggregate_provenance.rs:580](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:580), reached from tuple bindings at line 292 and loop domains at line 340.

Concrete counterexample, traced through source:

```quarry
table posts:
  score: int
  public 'posts'
  update <- allow

fn divmod(a: int, b: int): 0

mutation setScore(amount: int):
  p = posts['seed'] ! else MISSING
  (q, r) = divmod(amount, 1)
  update posts[p.id] { score: p.score + q }
```

The catalog permits that helper name. The actual tuple binder bypasses helper lookup and emits builtin division, so `q = amount`: the caller supplies the increment. See [control.rs:230](snapback4/crates/snapback4-lang/src/bind/program/control.rs:230). Provenance instead calls the declared helper, obtains AMBIENT `0`, assigns that provenance to both tuple components, and records READ|AMBIENT for `p.score + q`. It therefore emits the derived-column note. `sorted` tuple bindings have the same mismatch.

The same defect bypasses L28/L29: declare `fn range(a: int, b: int): [0]`, then accumulate `delta = delta + 1` over `range(0, amount)` and write `p.score + delta`. The binder executes an argument-bounded range ([control.rs:368](snapback4/crates/snapback4-lang/src/bind/program/control.rs:368)); provenance sees the helper’s ambient literal list. L29 consequently adds the wrong cardinality.

**Smallest conservative fix:** classify a `range` loop domain, or `sorted`/`divmod` tuple result, as UNKNOWN when a same-named helper exists, while retaining traversal of relevant write effects. Add silence regressions for those three collisions. This changes only the optional analysis and requires no binder or engine change.

This is a behavioural finding, not merely wording.

Verdict: NOT READY
