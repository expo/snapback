## 1. The High

`index_key(current) != key` is not in `partition.rs`. The only remaining `index_key` uses are the current delivered key of a selected put (`664`), the join-time sort (`761`), and the historical locator in the walk (`701`). None compares a row’s current image or key with its own historical one.

Rule the code implements:

- Selection is still join-time: `group_at(join_seq)`, descending by the horizon index, first N delivered, tail kept as `unselected`, join seq stored on `JoinSelection` (`756–764`).
- `whole` (`rows.len() < last`) publishes `"whole"` with no probe (`694`).
- Otherwise K starts as the oldest *delivered current* selected key (`696`). If that set is empty, no completion (`696`, `646` drops the end marker).
- Candidate blockers are that unselected tail, walked descending. Historical `key < oldest` breaks before any log query or fetch (`704`) — the ordinary case.
- A remaining candidate is discharged iff `tx.written_after(&marker.table, id, selection.seq)` (`707`): `SELECT EXISTS(SELECT 1 FROM _log WHERE t = ?1 AND id = ?2 AND seq > ?3)` (Postgres `$1..$3`), answered from `_log_row_seq` on `(t, id, seq)` (`storage.rs` 36–39; `store.rs` 132; `postgres/log.rs` 29–31; `postgres/mod.rs` 99–100). Any later put, same-key rewrite, move, or del counts; the join commit itself does not (`tests/rows.rs` 148–157).
- Rare-path cost: one indexed existence probe per candidate still at or above K, O(log L), no image read; a hit continues without `fetch`. Only an unwritten candidate is fetched and checked for current presence, read rule, and group (`708–710`).
- The first such row is the greatest blocker. K becomes the next delivered key strictly above that historical key (`713`), which equals the current key because there was no later write. If none, `None` — no completion (`713`, `646`).

LLP 3000 §7 (`llp/3000-snapback4.explainer.md` 651–658) still holds: the wire carries current readable images or a deletion, never a withheld historical key as a published floor.

**Pre-existing, not this round.** If the withheld key would change the top N, the delivered *rows* differ. That is join-time selection (`JOURNAL.md` 32250–32251).

The journal’s leak argument (`32241–32251`) is sound as written: the decision is a function of delivered rows, current readable images, and the post-join event set; with no later write the join-time key *is* the current key, so there is no equality test between a row’s current and historical images. ## 3. Correctness

Join-time `p3=3000, p2=2000, p1=1500`, then `p3 → 1000`, p1 unwritten:

- Delivered `{1000, 2000}`, oldest 1000.
- p1@1500 is unselected, `written_after` false, current, same group → greatest blocker.
- Next delivered key above 1500 is 2000 (`713`). Never 1000 (`recheck.rs` 62; wasm `236`).
- Delete p2 as well: no delivered key above 1500 → no completion (`80–82`, wasm `236`).

Device coverage (`read.rs` 688–704): a descending page on the horizon index is known only for `Whole` or when it stays at/after `Key(floor)`. `newest` / `above` are complete iff a floor was published; `timeline` last-2 crosses and stays unknown (`64–70`; wasm `238–243`).

**Is “written after the join” the stream delivering it?** For a real `row_changed` mutation, yes after catch-up. Puts go to the row’s current partitions; dels go to partitions it left (`partition.rs` 139–151). A device catching up through this join holds the group from `join_seq`, so a same-group rewrite is a later put on that span; a deletion is a `del`; a move-out (`hide` to `'secret'`, or a group change) is a `del` on the old group plus a put on the new one. `changed_unselected` covers move-up, move-down, remove, and hide, including when the discharging write is on a later stream page (`98–104`). The device is not certified for a row it will not receive: a moved-out or deleted row is not a current readable member of this group, and a same-key rewrite is delivered as a put (current-image substitution still emits it). An unreadable put can be dropped at `658`; that row is not in the claim.

Paging can publish the end marker before the discharging put appears on a later page (`more` still true). That is the existing R2 behaviour the tests keep, not a new hole: after catch-up the device holds the row.
