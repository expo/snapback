### 1. The strongest objection to each proposal

**Fable.** Its load-bearing risk is the exact per-viewer aggregate it makes a condition of success. For an inbox of \(N\) conversations, exact unread either scans \(N\) independently growing ranges or maintains `(conversation, viewer)` state by touching every recipient on send. The first is unbounded; the second needs a schema-enforced membership cap plus measured contention, replay, deletion, and membership-change semantics. Capped “99+” changes the product contract. Fable survives if capped unread is acceptable or bounded maintenance measures well.

**codex.** `AllOrRefuse<T,N>` is an availability trap when presented alongside `Page<T,N>` as an ordinary collection type. Relay can pass every seed test with 900 cards and seal the entire board at card 1,001. LLP 0120 explicitly identifies that data-growth failure. The proposal survives by reserving `All<T,N>` for schema-enforced cardinality invariants and making runtime exact-or-refuse an explicit result union, never the first diagnostic repair.

**grok.** Refusing opaque verdicts leaves no general offline answer for valid rules over hidden billing, moderation, admin, or entitlement rows. The choices become disclosing the hidden row, refusing local prediction, or materializing a viewer-readable authorization fact—which is itself a witness under another name. Common Clique membership should be readable, but the proposal does not cover the general policy case. It survives by admitting narrowly scoped, non-authoritative policy facts.

**orchestrator/P9.** `Page<N>` bounds database fan-out, not “arbitrary pure computation.” A loop over 100 rows that repeatedly doubles a string, expands arrays, invokes an expensive comparator, or builds enormous output has a tiny trace and catastrophic CPU/heap cost. Examined-entry cardinality alone therefore does not protect scale-to-zero. P9 survives only with a closed call graph, bounded scalar/container sizes, and static plus fail-closed VM-step, heap, stack, output, closure-byte, and write-amplification budgets.

**0329.005/P4.** P4 defines current materialization closure but not future demand per `(view, transition)`. A locally inserted message may introduce `users[new.author]`, `mentions[new.target]`, or another dependent key absent from the existing closure. Algebra makes substitution tractable but cannot prefetch every value of an arbitrary future mutation argument. P4 does not provide complete private-offline prediction as written; it survives with conditional demand certificates and honest `partial`.

### 2. The crux, re-litigated

Fable and codex are right that the literal “cannot re-execute” claim is false. Grok is right that a previous trace is not a program closure for every counterfactual write. P9 overstates matters when it turns replayability into total prediction.

The shared fact should be:

> For deterministic, completely mediated code, an authorized trace is sufficient to replay the traced snapshot exactly and to re-execute after a local delta exactly while every requested read and policy obligation remains covered. Escaping coverage produces `partial` or queued-without-prediction, never invented completeness.

Formally:

```text
complete(P, D₀, Δ, T₀)
iff Reads(P, D₀ ⊕ Δ) ⊆ Coverage(T₀ ⊕ Δ)
    and each policy obligation is recomputable or has a valid scoped fact
```

Boundary conditions:

- A computed dependent read is complete only when the newly computed key is covered. Static analysis can prehydrate keys derived from the viewer, subscription arguments, constants, held rows, or modeled transition values; it cannot materialize all future argument-derived keys.
- Hidden rule rows and their range extents must not ship. Use a safe derived row, an opaque scoped policy fact, or decline prediction. The server retains the hidden dependency trace.
- Deleting from a full top-\(M\) page is complete if the trace says the range ended. If it stopped at the limit, the result is `partial` unless a refill row and subsequent boundary evidence were retained.
- Revocation while disconnected is unknowable. The result is `stale`, not `fresh`. Under the stated current-membership rule, reconnect reauthorizes queued writes, reruns the rule dependency, retracts the subscription, and purges no-longer-authorized closure rows.

Thus shipping the recorded read set provides genuine bounded offline execution, not universal advance-complete prediction.

### 3. Static vs. dynamic — the actual trade

Real `if` and `for (x of Page<N>)` do not inherently threaten shape, database-work bounds, authorization, tracing, or replay. “Arbitrary pure computation” does unless resource use and information flow are also typed and bounded.

| Property | Algebra | Bounded structured program | Year-one judgment |
|---|---|---|---|
| Shape and DB bound | Compositional closed predicates | Read-site families, branch unions, and loop products | Either suffices if rules and all resources are charged |
| Prediction closure | Symbolic demand is usually tractable | Exact only for a supported provenance fragment; otherwise `mayPartial` | Require a per-transition certificate, not universal completeness |
| Noninterference | Visibility-before-aggregation and hidden-flow proofs are natural | Needs taint/effect rules preventing hidden values from shaping output, exported traces, or observable refusals | Non-negotiable |
| Postgres | Often one set-oriented statement | Interpreter near DB; dynamic N+1 unless optimized | Correctness portability now; measure performance before graduation |
| IVM | Operators admit delta rules | General loops/helpers usually rerun-and-diff | Explicit maintained count/sum is enough initially |
| Semantic/compiler surface | Small value model and simpler compiler | Must specify sorting, strings, numeric overflow, Map/Set order, allocation, and helper calls | Keep the subset deliberately small |
| Agent prior | Expression-object callbacks look like JavaScript but reject normal JavaScript | Convex-shaped control flow and accumulators are familiar | This is the decisive year-one advantage |

The algebra therefore still buys proof precision, SQL lowering, IVM, and a smaller trusted semantics—not merely different spelling. Those are real, but the founder presently needs time-to-green, bounded work, private closure custody, and predictable chat operations more than general IVM or universal single-statement lowering.

### 4. Your updated position

I remain on the P9 side of the computational-class decision, but I would no longer call the admitted computation “arbitrary.” Build **bounded TypeScript-syntax data programs with an algebraic data-effect boundary**:

- Admit real `if`, acyclic helpers, bounded `Map`/`Set`/folds, and `for` only over `Page<N>` or fixed bounded values. `scan`, `nest`, `group`, `recurse`, and maintained aggregates are library forms normalized into the same IR.
- Refuse host imports, application JavaScript execution, dynamic schema names, unbounded recursion/allocation, ambient I/O/time/randomness, database effects inside comparators, and hidden-policy values escaping their policy type.
- Run application queries and mutations as bytecode in a Rust interpreter inside the authoritative transaction. Effects remain external workers calling named operations.

The minimal static certificate binds identity (`plan/schema/rule/value-model/evaluator` hashes); read sites with indexes, prefix provenance, maximum calls/examined entries, stop semantics, authorization dependencies, and hoisting proofs; write sites and maintained fan-out; result cardinality; VM steps, stack, heap, output and closure bytes; ordering/null/overflow semantics; noninterference class; halo and exact/page/capped/refusal semantics; per-`(view, transition)` prediction status; and physical lowering class. The dynamic receipt instantiates it with principal, canonical args, snapshot, authority epoch and deadline, concrete rows/ranges/absences/boundaries, stop reasons, actual meters, policy facts, and a trace digest.

Prediction status should be `closed`, `conditional(demandProgram)`, or `mayPartial`. For deletion-capable views, retain row \(M+1\) plus \(M+2\) boundary/stop evidence—not two full rows everywhere. That preserves one local refill. Its cost is one additional authorized projected row, its dependent reads, a boundary fact, and wider invalidation per realized page; select it from view-transition analysis rather than applying it uniformly.

Remove ordinary runtime `AllOrRefuse`. Keep schema-proven `All<T,N>` where writes enforce \(N\); any data-dependent exact-or-refuse operation must return an exhaustively handled sealed union.

Opaque policy facts are needed in v1 for hidden-input rules. The receipt is plan-bound; the fact is bound to `{deployment/schema/evaluator generation, normalized predicate hash, allowed consumer sites/effects, operation hash, principal, canonical resource and input digest, snapshot/authority epoch, decision, notAfter, dependency digest, MAC}`. A read-site verdict is not write authorization. Reuse for prediction is allowed only when the compiler proves the read and write obligations contain the identical normalized fact after substitution; otherwise issue a distinct write-prediction fact. The server trusts neither and always re-evaluates. Common Clique membership should ship as a readable row or absence.

The one-hop membership rule hoists to one probe when conversation equality pins its policy partition. For the two-hop co-member rule, `E_RULE_UNBOUNDED` should paste three repairs: split intentionally public `profiles` from owner-only `accounts`; maintain `visibleProfiles(viewer,user)` while printing its schema cap and write/storage fan-out; or query through an explicit bounded conversation. It must never suggest making the whole users/account table public.

Given Snapback’s protected-retention posture, a finite engine-owned `notAfter` is required; deployments may shorten the hard maximum, not disable it. This is lease-like cached evidence internally, but not an author-facing query class and not protection against copied plaintext.

Prefer one Rust semantic core compiled native for server/mobile and to WASM for web. However, LLP 0129’s older evaluator experiment measured 117,353 gzip bytes for Rust/WASM versus 7,615 for the shipped JavaScript evaluator, so size, startup, Expo integration, and storage-bridge cost are qualification gates—not assumptions. Hermetic QuickJS imports too much semantics. If the Rust core fails those gates, use a generated TypeScript evaluator only behind a frozen cross-engine result-and-trace corpus.

### 5. Convergence candidates

All four proposals—and P4—could sign today that:

- Named operations are the sync unit; effects are a visibly different, nonreactive kind.
- Row rules are the sole authorization boundary; public access is conspicuous and unlocks no capability.
- Read/write sets, indexes, retention, invalidation, and prediction behavior are derived.
- Executable collections are bounded or maintained.
- Static resource certificates and dynamic traces are complementary; traces include absences, boundaries, and stop reasons.
- The client is a closure store, evaluator, and outbox with the agreed eight states, not an ad-hoc replica query planner.
- Server settlement is authoritative; disconnected revocation is unknowable.
- Exact aggregates over growing populations require maintained state; page/capped semantics remain explicit.
- Application JavaScript does not execute in the authoritative query/mutation path.

The genuine disagreements and cheapest settling experiments are:

- **Algebra versus structured programs:** lower both front ends to one IR and run a counterbalanced agent bakeoff on private chat, `createOrGetDM`, Relay, Split, unread, and a branch-changing read. Measure time-to-green, effect-escape rate, certificate precision, and DB calls.
- **Prediction derivability:** property-test new-author, arbitrary-mentioned-user, computed-key, local-delete, and bounded-recursion cases. Require exact demand output or `mayPartial`.
- **Opaque facts:** implement one readable-membership case and one hidden-entitlement case; fuzz cross-rule, cross-resource, read-as-write, changed-input, expired-epoch, and plan-rebinding attacks.
- **Interpreter:** run one frozen semantic corpus through Rust native, web WASM, Expo carriers, and a TypeScript twin; compare result/trace bytes, compressed size, startup, and bridge overhead.
- **Halos and exactness:** replay realistic edits with halo 0/1/2 and grow `AllOrRefuse` fixtures past \(N\); measure partial incidence, closure growth, invalidations, and whether agents handle overflow.
- **IVM/Postgres:** compare `boardView` and Split under interpreter-near-Postgres versus set-oriented lowering; separately benchmark maintained unread under increasing membership and concurrent SQLite sends.

### 6. Benchmark failure mode

The most likely loss **[inferred]** is unread: a Convex-shaped exact `count()` works on seed data, while Snapback responds with a bound/maintenance decision and the agent routes around it through an effect.

The paved exact shape should use the per-membership counter and watermark already demonstrated by the current read-receipt recipe:

```ts
const inbox = db.scan(memberships.byUser, [ctx.viewer], { take: 50 });

return inbox.map(m => ({
  conversationId: m.conversationId,
  unread: m.unreadCount,
}));
// unread read bound: ≤51 examined
// send maintenance: ≤M recipient-counter writes; markRead: one watermark write
```

Here \(M\) is a schema-enforced maximum conversation membership, not runtime exact-or-refuse. The diagnostic for `Unbound<Message>.count()` should paste two runnable choices:

> Exact unread over a growing range has no examined-entry ceiling. Use the maintained membership counter (`inbox ≤ N+1`; `send ≤ M` counter writes), or use `countCapped(100)` for an always-available “99+” badge. `AllOrRefuse` and authorization weakening are not repairs.

The mitigation is to scaffold both variants, print their read/write costs, and make the bakeoff cross the membership and message caps while offline—not merely pass seed fixtures.
