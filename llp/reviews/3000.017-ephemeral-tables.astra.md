## Verbatim review

### Review of LLP 3000.017 revision 1 — GPT-6 Astra

**Verdict:** NOT READY

## Summary

The table modifier is a credible surface, and bypassing durable admission directly addresses the typing backlog. However, revision 1 has unresolved design defects in mutation coalescing, generation isolation, and watch invalidation. Several reuse claims also disagree with the code: pooled readers still require the writer’s mutex, `write_tables` misses executable writes, and `nextExpiry` does not cover every expiry-induced visibility change. Local probes reproduced the relevant transaction, authorization, expiry, and TypeScript failures. I would keep the table design, but resolve these mechanisms before handing it to the implementation and publication lane.

## Findings

### F1 (High) — An old-generation transaction can access the new incarnation’s memory

- **Where:** RFC §3.4 and §4.3; [store.rs:250](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/store.rs:250), [serve_adoption.rs:153](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4/src/serve_adoption.rs:153), [serve.rs:122](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4/src/serve.rs:122).
- **What is wrong:** Opening the durable transaction before locking the shared hub creates a generation race. A reader can establish a generation-1 snapshot, pause, then acquire the hub after adoption has cleared it for generation 2. It can subsequently populate the new hub using old rules, or read new-generation rows under old rules. Invalidating the reader pool does not revoke outstanding loans.
- **Evidence:** The SQLite probe held a reader transaction across adoption. Its generation remained `1` after the serving engine reached `2`. Only a *new* transaction on that reader returned `E_GENERATION`. The existing identity check therefore does not close this window.
- **Proposed change:** Specify one synchronization protocol for snapshot acquisition, hub access, and adoption. Bind each hub to store identity and generation; reject stale borrowers before memory access. Acquire the hub before establishing the durable snapshot, with adoption following a compatible lock order, or replace generation-specific hubs atomically. On clients, reject retired incarnations before comparing epochs.

### F2 (High) — The proposed mutation classifier misses executable writes

- **Where:** RFC §4.1 and §4.3; [ir.rs:729](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/ir.rs:729), [engine/read_only.rs:4](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/engine/read_only.rs:4).
- **What is wrong:** `ir::write_tables` is not an exhaustive effect analysis. It descends into statement-level `If` and `For` bodies but ignores expression-contained statements, including `Expr::Block`. Using it both for classification and runtime rechecking repeats the same blind spot.
- **Evidence:** A raw-IR probe wrapped a valid insertion inside `Return(Expr::Block { … })`. `write_tables` returned `[]`; executing the program returned `Sent` with `tables=["items"]`. The existing read-only checker explicitly warns that inlined helpers can hide writes in expressions. This was an IR probe, not a claim that the tested Quarry source emitted that form.
- **Proposed change:** Use an exhaustive shared effect visitor over statements, expressions, loop domains, and generated effects. Validate both durability directions independently of the operation fact. Add nested-expression and mixed-write tests, plus a runtime storage boundary that refuses durable writes from ephemeral execution.

### F3 (High) — Actual-byte capacity refusals create a private-data oracle

- **Where:** RFC §3.5 and §4.3; [rows/disclosed.rs:1](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/rows/disclosed.rs:1), [engine/write_target.rs:49](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/engine/write_target.rs:49), [LLP 3000.015:81](/Users/ccheever/projects/snapback-eph-review-astra/llp/3000.015-shared-baseline-for-snapback5.spec.md:81).
- **What is wrong:** If the global byte counter measures actual retained row images and keys, another principal’s private payload length can determine whether my unrelated write returns `Sent` or `E_EPHEMERAL_FULL`. Omitting row details does not remove that distinction. The existing law explicitly includes the refusal envelope.
- **Evidence:** The storage and write-target code deliberately reserves declared bounds for protected values instead of charging hidden lengths. Two worlds with identical row counts and public fields, but different private payload lengths, can cross the proposed global byte threshold differently.
- **Proposed change:** Define capacity accounting in terms of declared, visibility-independent reservations and specify how hidden occupancy affects admission. Add paired-world capacity tests with equal topology and different private values. Do not introduce an actual-size refusal oracle under the claim that existing disclosure laws remain unchanged.

### F4 (High) — Automatic coalescing changes the meaning of permitted mutations

- **Where:** RFC §2.2 and §2.4; [engine/write.rs:50](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/engine/write.rs:50), [engine/write.rs:223](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/engine/write.rs:223).
- **What is wrong:** Identical operation names and arguments do not imply an idempotent rewrite of the same row. Section 2.2 permits ordinary inserts and state-dependent updates. Two identical calls can legitimately create two rows or increment twice; the proposed sender silently collapses them and returns an earlier result. There is also a typing-specific ordering defect: `setTyping` can have a waiting call, `stopTyping` can execute under its different key, and the waiting `setTyping` can subsequently resurrect the row.
- **Evidence:** Inserts and upserts have distinct executable effects in the existing interpreter. The RFC provides neither an idempotence restriction nor ordering across related operation keys; closing the renewal window does not cancel a waiting call.
- **Proposed change:** Preserve ordinary ephemeral mutation semantics. Put suppression behind an explicit keyed state/heartbeat contract, with latest-value replacement and ordered cancellation/deletion, or restrict it to compiler-proven eligible operations. Supply the life and key metadata that the sender requires. Test delayed `set → set → stop` settlement, not just renewal-window closure.

### F5 (High) — Adding a watch can leave its table outside an outstanding 25-second poll

- **Where:** RFC §3.3 and §4.6; [changes.ts:27](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/changes.ts:27), [local.ts:819](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/local.ts:819), [local.ts:1118](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/local.ts:1118), [client.ts:450](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/client.ts:450).
- **What is wrong:** The RFC builds `ephTables` from live server-answered watches but does not specify how changing that set updates an outstanding poll. For example, a poll already subscribed to `viewing` remains outstanding while `typingIn` is mounted and initially returns empty. Subsequent typing writes are deliberately irrelevant to that poll. With no row, there is no expiry timer to rescue the watch.
- **Evidence:** The transport fixes URL parameters when issuing the request. Local polling defaults to 25 seconds; adding a watch only starts its query. Learning new dependencies does not restart the poll. Following these paths without another mechanism can miss the entire typing lifetime.
- **Proposed change:** Add a subscription revision: cancel/reissue polls when their dependency set expands, and catch up from the query’s observed epoch without a gap. Include `local-query.ts` in the publication-fencing work. Test mounting typing while another ephemeral-table poll is already held, using the actual local-first web tier.

### F6 (High) — Expiry can make a query readable without producing any notification

- **Where:** RFC §2.3 and §3.3; [engine/rules.rs:250](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/engine/rules.rs:250), [local.ts:911](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/local.ts:911).
- **What is wrong:** “Expiry does not bump the epoch because clients re-fetch at `nextExpiry`” is insufficient for the allowed rule language. A denied query can become readable when a negative rule witness expires, while its previous answer has no exported deadline.
- **Evidence:** Using the existing expiry mechanism, a probe with `read <- not exists silence[principal = viewer]` returned `[]`, `nextExpiry=None` at time 1500. After the silence row expired at 2000, the same query returned a hint at 2001. `evaluate_verdict` intentionally preserves a rule deadline only for `Readable` verdicts.
- **Proposed change:** Specify bounded, disclosure-safe expiry invalidation—for example, a table subscription tick independent of hidden row contents—or explicitly constrain these dependencies. Add denied-to-readable expiry tests. Exporting denied-witness deadlines indiscriminately would undermine the disclosure boundary.

### F7 (High) — The proposed pooled-reader path still takes the writer’s mutex

- **Where:** RFC §4.4 and §4.7; [serve.rs:995](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4/src/serve.rs:995), [serve.rs:696](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4/src/serve.rs:696), [serve_changes.rs:35](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4/src/serve_changes.rs:35).
- **What is wrong:** Taking a pooled reader “as `/q/` does” cannot satisfy the proposed test that an ephemeral mutation succeeds while another thread holds the engine’s writer lock. Reader checkout itself locks `shared.engine`. Bearer authentication also locks it. Peer `/changes` readiness checks and response-reader creation do likewise.
- **Evidence:** These are explicit mutex acquisitions in the cited paths. A SQLite read transaction avoids SQLite’s writer reservation; it does not avoid the serving engine mutex.
- **Proposed change:** Include reader checkout, authentication reads, and change-poll metadata access in the concurrency redesign. Test the complete authenticated HTTP path—including peer wake and query—while the serving engine mutex is held. A direct `mutate_ephemeral` test would miss this defect.

### F8 (Medium) — The recommended rules let departed members renew forever

- **Where:** RFC summary example and §3.2; [engine/field_authority.rs:70](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/engine/field_authority.rs:70), [guide/reads.rs:118](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-lang/src/guide/reads.rs:118).
- **What is wrong:** The sample checks membership on insertion but only ownership on update. Losing read access does not automatically revoke update permission. Therefore the claim that a departed member’s row outlives departure by at most its life is false.
- **Evidence:** A probe using those rules and the existing four-second expiry mechanism removed Alice’s membership at 1100. Renewals at 2000, 4000, 7000, and 10000 all succeeded. Bob still saw Alice at 10001, with expiry 14000. The existing guide already includes membership in the update rule.
- **Proposed change:** Retain `and exists members[.roomId, viewer]` on update. Test renewal after membership removal, alongside the proposed test that the departed member’s next read is empty.

### F9 (Medium) — The proposed TypeScript subtype makes the overload unsound

- **Where:** RFC §2.4 and §4.6; [contract.ts:119](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/contract.ts:119), [contract.ts:182](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/contract.ts:182), [react.tsx:279](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/react.tsx:279).
- **What is wrong:** Because `Ephemeral` extends `Mutation`, callers can widen it to `Mutation` and select the durable overload. TypeScript then promises a `Write` containing `seq`, while runtime dispatch returns a `Signal` without one. Passing durable mutation options can also select the wrong overload. Separately, the React recipe calls the hook result as a function, although `useMutation` returns `{ run, last, inFlight }`.
- **Evidence:** Strict TypeScript compilation accepted both erroneous durable-receipt expectations using the real contract types and the proposed overloads. The recipe also accesses `Read.data` without narrowing the union defined at [contract.ts:52](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/contract.ts:52).
- **Proposed change:** Define disjoint durable and ephemeral mutation types over a common base, with durable `ephemeral?: false`. Cover generic wrappers, options, and pending hooks with negative type tests. Preserve the hook object shape, use `.run`, and compile the complete React recipe.

### F10 (Medium) — Adding `engine_field` does not hide `$deadline` on ordinary rows

- **Where:** RFC §3.1 and §4.2; [engine/recorded.rs:20](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/engine/recorded.rs:20).
- **What is wrong:** The RFC says `public_image` already strips engine fields. Its fast path returns the row unchanged when there are no recorded fields, no `through`, and no timeline slots. A normal ephemeral table satisfies that condition, even after `engine_field("$deadline")` becomes true.
- **Evidence:** The early return precedes the field filter. Updating `schema/through.rs::engine_field`, as planned, does not change that branch.
- **Proposed change:** Update the fast-path predicate or centralize detection of hidden engine fields. Test unshaped point reads, scans, and mutation-returned rows on the wire; generated TypeScript row types alone cannot detect this leak.

## What the RFC gets right

The modifier and `typing` guide alias are a good fit for builders already using Quarry. Reusing queries, joins, and rules is a reasonable advantage over introducing a separate channel language tonight. The restrictions against durable dependencies, replay, prediction, and outbox admission are appropriate.

The simple disappearance path already has useful machinery: [local.ts:911](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/local.ts:911) retires an expired observation before asynchronous recovery, and [client.ts:419](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/client.ts:419) schedules online refreshes. Thus a correctly delivered ordinary typing row does not require an application timer.

Byte-identical defaults, an explicit capability fence, PostgreSQL refusal until support exists, and measured wasm-budget handling are sensible compatibility choices. The two-client burst test is useful, but should explicitly exercise local-first web publication and the deterministic races above.
