## Findings

### 1. High — Absence is proved for the key, but prediction inserts a different audience’s row

**Location:** [engine/write_target.rs:120](snapback4/crates/snapback4-core/src/engine/write_target.rs:120), with `engine/read.rs:234`.

**Scenario:** Use a fully synced table with `read <- .principal = viewer`, permissive insert authority, and unique `(postId, principal)`. Bob’s acquired partition is empty. Execute:

```quarry
r = upsert likes['p', viewer] { principal: other, on: true }
require r = null else WRONG
```

Pass Alice as `other`. The key proves Bob’s absence, but the patch’s `principal` wins over the key. The server inserts Alice’s row and returns `null` because Bob cannot read it. The device trusts the newly inserted synced row, returns it to the mutation, and predicts `WRONG`, preventing a write the server would accept. Without the `require`, it exposes a speculative row the server would withhold.

**Smallest fix:** Check the fully materialized insert image’s actual readable audience before predicting. Queue when that cannot be established; speculative insertion must not automatically confer delivered-row read authority.

### 2. High — Hidden unique collisions and cap populations invalidate insert prediction

**Location:** [engine/write_target.rs:94](snapback4/crates/snapback4-core/src/engine/write_target.rs:94); constraint checks at `engine/write.rs:299` and `:339`.

**Scenario:** Extend the private likes table with unique `alias`. Alice owns an unreadable row with alias `"taken"`. Bob has acquired his complete empty partition and upserts `('p', Bob)` with alias `"taken"`.

The device predicts an inserted row. The server finds Alice’s secondary-index collision and refuses with `E_RULE`. Similarly, with whole-table `cap 1` occupied by Alice, the device predicts insertion while the server refuses the cap.

These differences require neither concurrency nor stale acquisition.

**Smallest fix:** Require sufficient coverage for every uniqueness lookup and affected cap group before predicting insertion; otherwise queue without a row.

### 3. High — A cross-table merge continuation can permanently skip a readable row

**Location:** [engine/read.rs:717](snapback4/crates/snapback4-core/src/engine/read.rs:717), particularly continuation construction at `:756`.

**Scenario:** Merge two same-shaped tables descending by `(at, id)`, taking one row:

- First lane: a readable row at time 10.
- Second lane: more hidden rows than the examined-row ceiling, all above time 20, followed by a readable row at time 15.

The first lane contributes time 10. The second exhausts the meter before reaching time 15. The merge returns time 10 with a continuation after 10. That continuation is translated for the second table, positioning its next scan below 10 and permanently skipping the readable row at 15.

The hidden keys are not directly exposed. The failure is an invalid global continuation. The newly admitted cross-table form reaches the existing eager-merge behavior.

**Smallest fix:** Do not emit an advancing continuation unless every lane has established its position through that continuation. A conservative cut without a continuation is safer than returning a misleading one.

### 4. High — Exit transport dispatches durable mutations out of order

**Location:** [local-exit.ts:25](snapback4/packages/snapback4/src/local-exit.ts:25).

**Scenario:** Queue `setValue(1)` followed by `setValue(2)`. Both fetches start before either response. If the server processes the second first, the final value is 1 instead of the required submission-order value 2.

An in-memory reproduction importing this implementation produced:

```text
Outstanding before any response: [ 'first', 'second' ]
Reverse server execution final value: 1 ; required submission-order value: 2
Oversize head bypass: [ 'small-second' ]
```

Lines 33–34 also skip an oversized or quota-blocked predecessor and send smaller successors. An ordinary send already in flight is not coordinated with the exit sender. Stable IDs prevent duplicate execution but do not repair ordering.

**Smallest fix:** Share ordering state with ordinary flushing and dispatch only the oldest unconfirmed write unless the server has an explicit ordered-batch/predecessor protocol. Never bypass a blocked predecessor.

### 5. Medium — The left-group prediction guard is disconnected

**Location:** [device.rs:152](snapback4/crates/snapback4-device/src/device.rs:152), called by `engine/write_target.rs:62`.

**Scenario:** A delivered-history membership table reads through `exists members[.room, viewer]`, has immutable membership keys, and denies ordinary inserts. Bob leaves a room; his membership row disappears and the device records the group as Left. Bob upserts the now-missing `(room, Bob)` membership.

The self-witness analysis decides readability from that key. `Predicting` does not implement `retained_group`, so it inherits `false` from `Rows`. Prediction therefore reaches the denied insert and produces `NOT_FOUND`, rather than queueing without a row as §20.5 requires for a left group.

**Smallest fix:** Give the prediction adapter access to persisted history groups and implement the retained-group check used by the reading adapter, including admission and replay.

### 6. Medium — Publication can pack bytes that were never signature-verified

**Location:** [publish.mjs:58](snapback4/scripts/publish.mjs:58), followed by hashing/copying at `:67`.

**Scenario:** Signing and verification succeed on Cargo’s shared production executable. Before the subsequent hash and copy, another production build replaces that path with a same-version unsigned binary. Publication hashes and packs the replacement. The installed-consumer hash check passes because it compares against the replacement’s hash.

Configured notarization lengthens this exposure window.

**Smallest fix:** Copy the artifact into private publication staging first. Sign, verify, notarize, hash, and pack that staged file; validate the installed signature as well.

### 7. Medium — Releasing a hold can lose the next firing after a schedule edit

**Location:** [dev_replay.rs:9](snapback4/crates/snapback4/src/dev_replay.rs:9), interacting with `engine/job.rs:314`.

**Scenario:** A previously active 60-second schedule has a saved shape. While held, change it to 120 seconds. Release at time 119,999 ms. Release records boundary 0 but leaves the old shape. At the first tick, 120,000 ms, `fire_schedules` detects the shape mismatch, records boundary 120,000, and continues without enqueueing.

The first post-release boundary is lost; the next firing occurs at 240,000 ms.

**Smallest fix:** Update each schedule’s shape and release boundary together in the hold-release transaction. Add a changed-shape boundary test alongside the same-shape restart test.

### 8. Medium — Enum-to-text widening is not total over text’s accepted domain

**Location:** [types.rs:170](snapback4/crates/snapback4-lang/src/types.rs:170).

**Scenario:** Declare an enum containing an actual U+0001 character as a one-character variant. The parser accepts it, enum argument validation accepts the member, and widening to `text <=1` succeeds. Assigning that value to a text column then fails with `E_INPUT`, because text validation rejects the control character.

Thus a valid value of the source type is not a valid value of the advertised destination type.

**Smallest fix:** Check every variant against text’s character-domain restriction as well as its length, or consistently reject such enum variants at declaration time.

### 9. Medium — Merging package.json can destroy the original on write failure

**Location:** [init.rs:48](snapback4/crates/snapback4/src/verbs/init.rs:48).

**Scenario:** An existing valid package merges successfully in memory. `std::fs::write` truncates it, then disk exhaustion or interruption prevents completing the replacement. `init` returns an error, leaving a truncated or broken package and losing the original scripts/dependencies.

**Smallest fix:** Write the complete replacement to a temporary file in the same directory, then atomically rename it over the original.

### 10. Low — The writes card contradicts the new prediction contract

**Location:** [guide/writes.rs:15](snapback4/crates/snapback4-lang/src/guide/writes.rs:15).

The card categorically says missing-row upserts do not predict. Later guidance permits the §20.5 insert case. A builder following the earlier paragraph receives the obsolete rule.

**Smallest fix:** Replace the paragraph with the held-group and key-decides-readability conditions, linked to the prediction card.
