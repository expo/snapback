## 2. The lifetime rule

On one server commit boundary it holds for everything that does not rewrite the child's own deadline.

- **Delete.** A live child blocks the delete, including one inserted earlier in the same transaction, including a job or `seed_delete`, because the probe is after the delete rule and is not itself a rule. Deleting the child first, then the parent, succeeds. Read authority is required before the probe, with or without children.
- **Expiry at insert.** `deadline = min(authored, captured parent deadline)` is transitive. A middle table with no `expire at` still stores the grandparent's deadline. `lookup_live`'s `expire.is_none()` short-circuit (`read.rs`) and the sweep's expiry index are both named, so Tuesday's `exists projects[P]` is absent and the row is sweepable.
- **Reuse.** `insert_attempt` today deletes an expired predecessor and inserts the new id (`write.rs`). §3.3 forbids that while any physical child remains, and forbids the sweep from removing the parent first. A new id cannot meet an old child on the server.
- **Same mutation.** Insert parent, insert child, delete parent: the probe sees the child. Delete parent, then insert child: the parent is not live.
- **Seeds, imports, restores, activation.** Ancestor-first capture, refusal of a parent image whose captured fields differ, no recapture on restore, expiry judged under the previous schema before projection. A three-level chain copies stored captures and does not walk to a live grandparent.
- **Device, finite deadline.** Server time 110 applied to a device at 90 expires a child whose deadline is 100. A child whose deadline is never stays stored; the capture check, not the clock, keeps it out of the new parent's verdict.

It does not hold for a later write to the child's own `expire at` column. That column is not required to be immutable. `bind_expire` accepts a mutable `time`. §4.4 stamps the effective instant on insert, and §2.3 says an update does not restamp.

**High — §3.2, §2.3, §4.4.** Issue `X` expires Monday. Comment `C` is inserted with `until` next year, so the stored instant is Monday. The author then sets `until` to yesterday to kill `C`. Gates read the stored Monday instant, so `C` stays readable. The other natural implementation is worse: store that instant in `.until`, which updates already rewrite. The author then sets `.until` to next year. `C` is live after `X` is dead. `X` cannot be deleted or swept, because a live child still references it. That is a live child whose parent is gone, which is the rule §3 claims.

Smallest change: store the captured parent deadline as its own immutable field. The effective instant is `min(live authored column, that field)`, computed on every insert, update, import, and activation. A write cannot raise it above the captured parent deadline.

## 3. New defects

**Medium — §5.** `retain delivered-history` comments, viewer leaves org A, issue `X` stays in A, no reuse. §5's quantifier says the parent verdict applies only when every held child is current. The retained comments fail that, which is not one of the two mismatches the next sentence defines (tombstone lag, or retained captures that differ). A literal reading falls back to the server. The server serves current images only (`partition.rs`: retained history is device-held). The fallback erases history the leave policy keeps. The other reading keeps the retained rows in `X`'s current page, which §5 also forbids.

The reused-id disclosure probe in the table above is still closed either way. Bob in B does not receive A's bodies.

Smallest change: quantify only over live current children. If any of those captures differ, fall back. Retained-only rows stay on the existing retained path and are omitted from the current page, its count, and its completeness proof. Their presence is not itself a mismatch.

**Medium — §3.2.** Memberships `read through .org`, and the org expires Monday. Issues stay `exists members[.org, viewer]` and sync. The listed gates hide the membership row at Monday. `trust_synced_read` (`read.rs`) still trusts the issues, because it asks whether the audience table declares `expire at`, and that site is not in the list. The same omission is what lets a mutation page an expiring `read through` table (`admission.rs`) and what skips the hidden-maintain reservation (`write_target.rs`). Until the sweep revokes the grant, the device shows issues the server already denies.

Smallest change: one expiring classification, true when `expire at` is declared or a captured deadline can be finite. Every existing `expire.is_some()` / `is_none()` site uses it. Say that the bullet list is not the closed set.

Refusal codes, the fixed reservation, cursors, exact sync, `grant_guard` on the membership insert, and server activation do not reopen an oracle. Predicted child upserts stay non-predictable. A predicted parent delete still queues unless every child table is fully held.

## 4. Under-specified

The two Mediums above are the specification gaps a competent implementer would get wrong. The explicit adoption mapping has no syntax; a missing mapping refuses, so that fail-closed outcome is safe.

Nothing else rose above a preference. Cursor continuation across a later reuse is still ordinary pagination.

## What is sound

`read through .ref` as the whole read rule, over one required immutable id with no default, is the right cut. Parents that are ordinary application tables, service grants that live only on the parent, and copying the immediate parent's stored inputs without walking to a live grandparent are the right restrictions. Exact admission after the service strip matches LLP 3000.007 §6.6. The insert order — refuse a client value, reserve once before the upsert arm, require a live parent, stamp, then evaluate — is the right one. The four-outcome resolver, plus "authorization is not coverage," is the right device split for a parent the device actually holds. Keyed views and no scan are the right aggregate cut. On the server, at a commit boundary, a child that has not since changed its own deadline does live inside its parent, including through three levels, and a reused id does not meet an old child.

**Overall verdict: NOT READY.**
