## Material defect: the new regression's `generation == 2` is unreachable

Counterexample, using only code in this snapshot:

- `rolled()` performs three schema-changing activations. v1/v2 differ (enum `'recovering'` vs `'outer_covering'` plus alias), so deploy#1 → generation 1, deploy#2 → 2, rollback 2→1 → 3. The one-bump-per-changing-activation convention is proven in-snapshot by [surf4.rs:266](/tmp/rel3-evidence/review-round9-snapshot/snapback4/crates/snapback4/tests/surf4.rs:266) (`deploy, deploy, rollback, deploy` → generation 4). Bumping is driven solely by schema/activation-hash diff ([store/activation.rs:167-168,479-480](/tmp/rel3-evidence/review-round9-snapshot/snapback4/crates/snapback4-core/src/store/activation.rs:479)); nothing ever lowers `_meta generation`.
- The test then wipes `release` and `activation_hash` but keeps `_meta generation` (= 3).
- Re-deploy of identical OLD source: `schema_changed` is false, but staged `activation_hash=Some(h)` vs wiped `before.1=None` forces `changed=true` (line 168), so generation becomes `next_generation(3, true) = 4`.
- The test at [rel3.rs:100](/tmp/rel3-evidence/review-round9-snapshot/snapback4/crates/snapback4/tests/rel3.rs:100) asserts `2`. Generation never decreases and `rolled()` ends at 3, so `2` is unreachable; the static derivation predicts `4`. The test will fail as written. This also contradicts the amendment's own "generation advances" (from 3, advancing cannot land on 2).

Smallest fix: do not hard-code `2`. Capture generation from `releases` status before the SQL wipe and assert post-init equals that plus one (predicted `3 + 1 = 4`), then confirm by executing the suite, which this overlay has not yet had.
