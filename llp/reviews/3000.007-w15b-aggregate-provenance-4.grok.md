## Findings

### Medium — argument-bounded `range` accumulation is treated as control, so `score + amount` still qualifies

**Where:** `snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:204-210` and `:250-254`; pinned positive at `tests/aggregate_copies.rs:483-489`.

**What the code does.** Loop cardinality is control for every domain (`count_influence = self.selection(domain, …)`), while carried `n = n ± …` only picks up **READ** from `loop_reads` (`domain.data & READ`). For `for i in range(0, amount): delta = delta + 1`, `amount` never enters data bits. `p.score + delta` is therefore READ with ARGUMENT control and the column qualifies.

**Failing scenario.**

```quarry
mutation like(postId: posts, amount: int):
  p = posts[postId] ! else NOT_FOUND
  delta = 0
  for i in range(0, amount):
    delta = delta + 1
  update posts[p.id] { score: p.score + delta }
```

Under L26 this is `score + amount`: the caller supplies the increment and can set 999 in one mutation. P5’s footgun is a count the caller **cannot** set to 999 and can only nudge. The same file already silences the direct spelling (`p.score + amount` in `argument_or_ambient_writer_disqualifies_across_the_catalog`). Choosing `+1` vs `-1`, or summing a **read** page, is selection; a caller-sized ambient count is not.

A finite choice of ambient constants (`delta = 1 if choice else 2`, `slice([1,-1], offset, …)`, `choose` returning 1 or 2) is still selection and should keep firing.

**Smallest fix.** If a loop domain’s data includes ARGUMENT and not READ, influence ARGUMENT **data** onto a carried ambient accumulation (the iteration count is supplied). Keep today’s READ cardinality for read domains, and keep control-only treatment for `if` / ±1 / sort / slice picks.

### Medium — `update` result `id` is still minted, so F12’s mixed object still fires

**Where:** `aggregate_provenance.rs:541-542` (and the upsert-only fill at 493–512). Documented as upsert-only at `feeds.md:1313-1315`.

**What the code does.** Upsert copies a named/sole `id` key onto the returned row (ARGUMENT / READ / UNKNOWN). `update` skips that fill, then `values.entry("id").or_insert_with(|| AMBIENT)` always mints. Other omitted update fields inherit object READ (prior image); `id` does not.

**Failing scenario.** Same as F12, with `update` instead of `upsert`:

```quarry
mutation copy(requestId: id):
  r = update scratch[id = requestId] { n: 0 }
  require r != null else MISSING
  p = source['seed'] ! else MISSING
  insert copies { value: { requestId: r.id, n: p.n } }
```

`r.id` is AMBIENT, `p.n` is READ, the object is READ±AMBIENT with no ARGUMENT, and `copies.value` is noted. The caller supplied the id. The round-3 root fix was “returned id carries the key’s provenance”; it is implemented only on the upsert insert arm.

**Smallest fix.** For `Update` as well as `Upsert`, copy an `id` key onto the result without recording an `id` write fact. If an update has no id key, use prior-image READ, not a mint. Leave minting to insert/upsert with no id key.

### Low (wording) — a toggle whose arms name different arguments still prints one expression

**Where:** `aggregate_provenance.rs:603-608` (filter `selected.choice == first.choice`, cap 2 at 68–70).

**Scenario.** `if liked: score + 1` else `if unlike: score - 1` produces two choice witnesses. The message keeps only the first arm. F13 covers same-argument, different guards (`set` vs `not set`), which is fixed.

**Smallest fix.** Union stored expressions for the column and list unique argument names, instead of filtering on the first witness.
