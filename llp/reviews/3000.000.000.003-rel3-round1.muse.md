# REL3 amendment review — [LLP 3000.000.000.003](./llp/3000.000.000.003-day-two-release-repairs.rfc.md)

Read-only review. No files modified. Sources: the amendment text, governing [LLP 3000.000.000 §22](./llp/3000.000.000-retained-storage-and-hot-release.rfc.md) (§22, lines 2078–2245), and the in-progress working-tree diff (15 files, `git diff HEAD --stat`).

## Mechanism 1 — Idempotent selection and repair

What is implemented: CLI double-guard in `releases.rs` (`previous == active` before and after view resolution, returning `unchanged: true`), engine `validate()` refusal for same-id non-preview activation in `release.rs`, history `record_event` early-return for self-transitions except `prune`, `rename_accepts` widening, `temp._backfill_native_restored` restore path, reworded refusal/preimage strings.

Findings:

1. **View-resolution second guard is correct in shape but `live_identity` may misreport when the live release is itself a view.** The second `previous == active` check compares the resolved *bridge* release id against the live id. If live is a bridge release serving an older target, selecting that older target's logical id resolves to the same bridge and correctly no-ops; but if live is ordinary and the resolved view is a *different* bridge release that serves identical content, it will re-enter activation (new revision, receipt churn) instead of no-op. The amendment says "selecting the ordinary target already served by its registered view must not re-enter activation" — content-equivalence, not id-equality, is the test. Concrete repair: compare guarded-executable digest + hiding policy (the §22 equivalence sets, lines 2194–2195) rather than bare release ids in the second guard, or document that only exact-id equality no-ops.
2. **History guard exempts `prune` but the amendment says "pruning cannot reset" transform meaning (i.e. prune must not clear the fresh-name requirement).** The `record_event` early return skips *recording* self-transitions, which is right for previews, but nothing in the diff prevents `prune` from deleting the evidence that a transform name was already used/broken, letting a re-declared same-name transform pass. The backfill refusal rewording ("use a fresh declaration name") is advisory text only; there is no name-reuse gate keyed on pruned definitions. Concrete repair: add a pruned-definition tombstone check in `stage_downfills`/admit that refuses re-introducing a pruned transform name with different meaning, or narrow the amendment to say prune behavior is unchanged.
3. **Repair path (`_backfill_native_restored`) validates the column domain but I could not find re-validation of input/lifetime dependencies, authority, or visibility on the restored value.** The amendment requires "validates its complete older projection and input/lifetime dependencies" with "ordinary constraints, visibility and authority checks." The code checks `fields.get(c)==Some(&native)` plus `validate_column`, then marks the column `authored`/`native_preserved`. If the down receipt is stale relative to current guards/audience, restoring it bypasses the audience proof §22 demands (lines 2090–2100). Concrete repair: run the restored value through the same audience/input-closure check as a normal reverse projection before inserting into `desired`, and refuse (naming row + forward selection) otherwise.
4. **Refusal strings name row and table but not the forward selection.** E.g. `"forward selection refused for this row"` names no release id. The commissioned wording requires "refusals identify row, field, forward operation and repair". Concrete repair: interpolate the forward release id and operation name into both `bad.add` sites in `restore_downfills`/transition.
5. **Positive:** the `previous == active` pre-view guard correctly avoids migration preparation, and the engine-level refusal protects direct (non-CLI) callers. The `preimages retained` / "serves the retained predecessor representation" rewording matches §4 intent.

Verdict on mechanism 1: **NOT READY** — issues 1 (equivalence vs identity), 3 (unproved authority on repair), and 4 (missing forward-selection identity) are material to the "redundant rollback is no-op / wedged stores repairable" outcome. Issue 2 is a scoping gap.

## Mechanism 2 — Frozen result fields

What is implemented: `alias result` parser, `result_aliases::lower` (Spread + `old = Focal.current` shape wrap), `Bound.result_aliases` map, `client_contracts::result_fields` + `compare` "covered by alias" lines. **No changes** to `rollback_views.rs`, row-shape computation, codegen, or child-lookup paths in the diff.

Findings:

1. **Lowering is wrong for row collections and optional rows.** `walk` wraps the whole return value in one `Shape{base, Spread + alias fields}`. For an endpoint returning a collection/page of rows, the alias field lands on the array object, not on each row; for `Optional(row)` the shape wrap likely mis-handles null. The amendment requires "rows, optional rows and row collections keep their existing paging and row metadata". Concrete repair: lower per-row (map the projection over collection elements, propagate through optional) or refuse aliases on non-single-row returns at compilation until per-row lowering exists.
2. **"Source field evaluated once" is not guaranteed.** Each alias emits its own `Member(Focal, current)`; two aliases over the same `current` read it twice, and `value.clone()` as shape base plus per-field members re-traverses. If member access has metering/cut semantics, this double-counts against per-row budgets. Concrete repair: bind `current` to a fresh local once per row and project all aliases from it, or prove member reads are pure/unmetered and say so.
3. **Compilation-time refusals are missing.** The code refuses only `old == current` and duplicate old names, plus requires the operation to exist. It does not check: `current` exists in the endpoint's result; `old` collides with an existing result field; result is a non-row (scalar/native/action/job return). An unknown `current` lowers to a member access that fails at runtime or yields null — exactly the silent-drop the amendment forbids. Concrete repair: resolve `current` against the bound result type (using the new `result_fields` helper), refuse unknown/colliding/non-row cases with the `alias result …` usage string.
4. **Operation-alias inheritance is stored but not resolved.** `Bound.result_aliases` keys by qualified operation name only; nothing copies entries to `alias`-declared operation names (cf. `release_bridge.rs:700-701` which resolves alias→target for other purposes). Concrete repair: after collecting, propagate each entry to every operation alias pointing at the endpoint, or refuse aliases on aliased operations until inheritance is implemented.
5. **Guarded-rollback v1-photo retention (amendment ¶2, sentences 2–8) has no implementation in the diff.** `rollback_views.rs` is untouched: no canonical-child-id (`child id == parent id`) generation, no parent-reference-scoped child read, no missing-payload→null + changed-domain reporting, no "generated source is inspectable" artifact. The required user outcome "frozen clients receive … extracted v1 photos on rollback" therefore rests on unmodified §22 behavior, which per §22 lines 2141–2146 leaves unrepresented children to the view (i.e. hidden, not null-with-domain-change). If that half is intentionally deferred, the amendment must say so; as written it over-claims. Concrete repair: implement the canonical-child lookup in the guarded view path with the stated gates (matching parent ref, ordinary child/column authorization, no arbitrary followup, null + changed-domain on missing payload, qualification failure for unrepresented v1 payload), or split the mechanism and mark the photo half uncommissioned.
6. **Coverage wording overstates.** `compare` emits "covered by alias" whenever the alias's leaf name matches a frozen read path's last segment — a pure name fact, which the amendment correctly limits ("coverage is a field-presence fact"). But it also emits the line when `change==Changed` for *any* reason, including domain narrowing the alias cannot fix, adjacent to "missing fields […]" lists that may confuse presence-coverage with domain-safety. Minor: keep the line but ensure the `RESULT REVIEW` line still fires for the domain change (it does — verify ordering doesn't let readers stop at the coverage line).

Verdict on mechanism 2: **NOT READY** — findings 1, 3, and 5 are material correctness/safety gaps against the "frozen clients get old names + v1 photos" outcome. The `result_fields`/`compare` half is the strongest part of the diff and is close.

## Mechanism 3 — One-release evolution

What is implemented: `rename_accepts` (optional recursion, text-max, int-range, int→int widening, enum subset), two call-site swaps (forward `stage_downfills` rename check, reverse `transition` rename check), `extract` asset-only error rewording.

Findings:

1. **`rename_accepts` argument order is inconsistent between the two call sites — one may be backwards.** In `stage_downfills` the call is `rename_accepts(old=new?, …)` with `|(old,new)|` bound as `(target_kind, source_kind)` in one site and `(source_kind, target_kind)` in the other (diff lines: `target_kind.zip(source_kind)` vs `source_kind.zip(target_kind)` with the closure naming them `(old,new)` both times). Old-domain-inclusion is directional; if either site passes (new, old), it authorizes narrowing. Concrete repair: verify each site passes `(old_domain, new_domain)` in that order, name the bindings `old_domain`/`new_domain` (not `old`/`new`), and add a unit test with a narrowing case refused at each site.
2. **`rename_accepts` is silent on several kinds.** `Int`→`IntRange` returns false (correct — narrowing — but the refusal message should say so, else users will file "rename blocked" tickets); `Ref/Image/Video/File/List` kinds fall to `false`, meaning any rename touching them is refused even when identical kinds with equal bounds would be safe — but identical types already return true via `old == new`, so this is acceptable if deliberate. Missing: text minimum/bounds beyond `max`, enum *spelling* vs set semantics (ties to §22 lines 2166–2168 — confirm spelling changes don't need the old-signature veto). Concrete repair: document the kind matrix in the function comment and add refused-kind diagnostics naming the kinds.
3. **Reverse-projection value validation and "widened registered view" are asserted, not shown.** The diff has no change to reverse validation of actual values under the destination domain for widened renames, and no view-registration path for tightened column-write rules ("must register a view retaining the current rule"). The `live:` line requirement ("states that it still runs the registered workflow and current guards") has no `rollback_views.rs` change. These three are the load-bearing safety halves of "rename+widen in one release and current write-rule views". Concrete repair: implement or explicitly descope each: value-at-reverse check, write-rule view registration, `live:` wording.
4. **Positive:** the `extract` asset-only error now directs to named backfill/down + authored mutation, matching the amendment; the refusal rewordings pointing at "fresh declaration name" + bridge + `guide rename` are consistent with mechanism 1's repair story (modulo finding 1.4 about naming the forward selection).

Verdict on mechanism 3: **NOT READY** — finding 1 (possible swapped inclusion direction) is a must-fix safety item; finding 3 leaves the commissioned write-rule-view half unimplemented.

## Mechanism 4 — Preview wording

What is implemented: hidden-row refusal gains `sample row ids`; "dormant (restored…)" → "retained (restored…)"; "read stale" → "serves the retained predecessor representation"; `release_shape::print` condensed to one line per operation.

Findings:

1. **`release_shape::print` now prints *less* than the amendment requires.** It emits `op: result fields changed (inspect rowShape.differences with --json)` — no changed operation/property names in prose. The amendment requires "human shape advice lists changed operation/property names" and only permits *not repeating expanded JSON* ("full structured records remain available without repeating their expanded JSON in prose"). Operation + property names are short; the JSON pointer is not a substitute. Concrete repair: print `op: old.path → new.path` (or added/removed field paths) per difference, bounded (e.g. first N paths + "and K more"), keeping the --json pointer for the full record.
2. **"Print a row-shape JSON record once within each preview response" is satisfied in JSON (`rowShape` appears once in the preview payload, `release_preview.rs:241`) but not in text previews.** Text mode prints the condensed shape lines (now degraded per finding 1) and I found no single JSON-record print in the text path. If "preview response" means both `--json` and text, add one compact `rowShape: {...}` summary line in text mode. If it means JSON only, the amendment should say so.
3. **Hiding-refusal samples: table-qualified ids and exact count are present, boundedness/labeling is half-present.** The new `E_ADOPT` message includes per-table `table [id, …]` groups and the total count — good. But there is no stated bound (large hidden sets could flood stderr) and the samples are not explicitly labelled as samples/truncated. Concrete repair: cap per-table ids (e.g. 5) with `+K more`, and label `sample row ids (first N per table)`.
4. **`preimages retained` / `dormant` reservation: implemented in the two touched strings, but `dormant` still appears elsewhere in preview/adoption output** (e.g. `release_preview.rs:274` now says "retained", good — but check `adoption_report().summary()` and `estimate` strings for bare "dormant" describing retained preimages). Concrete repair: grep preview/adoption strings for `dormant` and confirm each remaining use refers to genuinely inactive rows/cells/indexes per the amendment.

Verdict on mechanism 4: **NOT READY (small)** — the closest of the four; findings 1 and 3 are concrete, bounded fixes.
