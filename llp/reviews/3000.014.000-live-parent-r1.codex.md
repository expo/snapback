NOT READY

Revision 1 leaves several security-critical algorithms unspecified. The test list is appropriate, but executable state transitions and bounded representations are needed before commissioning implementation.

1. **High — Grant resolution can move unbounded fanout from children to parents (§4).**  
   One roster revoke can affect arbitrarily many parents, each with child scopes. “Proportional to existing grant changes” provides neither a transaction bound nor protection against exposing hidden parent populations through charges or exhaustion. The existing [partition design](/home/ccheever/projects/sb4-w14-rules4/snapback4/crates/snapback4-core/src/partition.rs:1) deliberately logs membership changes without enumerating content populations.

   **Required:** Specify registry keys, forward/reverse indexes, and algorithms for parent transfers, roster changes, and ancestor changes. Identify which work happens during mutation versus polling. Give bounded pagination, durable progress, exhaustion behavior, and accounting independent of hidden populations.

2. **High — One atomic response batch does not specify incremental acquisition (§4).**  
   `last N` bounds rows per parent scope; it does not bound scopes per response. The RFC lacks a publication state machine for partially acquired grants. Consider acquisition under epoch E, a revoke/regrant, then a delayed acquisition page from E. Atomic persistence alone does not determine which staged rows, coverage markers, or continuations survive.

   **Required:** Define acquisition identity, authority cut, continuation validation, cancellation, terminal coverage, and watermark advancement. Explain how overlapping recipients move between epochs while preserving continuous coverage and already acquired horizons. Descriptor-only transitions must also invalidate dependent queries before observers run. Existing [snapshot staging](/home/ccheever/projects/sb4-w14-rules4/snapback4/crates/snapback4-device/src/device/snapshot.rs:1) and [deferred publication](/home/ccheever/projects/sb4-w14-rules4/snapback4/crates/snapback4-device/src/device/deferred.rs:1) require explicit integration.

3. **High — Mutable ancestor expiry has no bounded cleanup algorithm (§2).**  
   Current child expiry is a stored, indexed value. The [sweeper](/home/ccheever/projects/sb4-w14-rules4/snapback4/crates/snapback4-core/src/engine/through_activation.rs:465) discovers due children through that index. Shortening a live ancestor deadline makes descendants due without changing their indexed values. Extending it makes a previously derived deadline unsafe for physical deletion. “Children first” specifies ordering, not discovery or safe resumable retirement.

   **Required:** Define the authoritative expiry representation and bounded sweep traversal, including revalidation after deadline edits between chunks. Specify how aggregates and contribution indexes use current ancestry; the existing [expiry recount](/home/ccheever/projects/sb4-w14-rules4/snapback4/crates/snapback4-core/src/engine/aggregate_expiry.rs:1) relies on stored expiry ordering. Include shortening, extension before cleanup, and extension after partial cleanup.

4. **High — Inherited time authority is not covered by the proposed device protocol (§§2, 4).**  
   The finite-deadline restriction is ambiguous about inherited expiry and expiring membership witnesses. An ancestor or necessary roster witness can expire without a parent policy mutation. A matching descriptor could consequently remain installed after authority ends. Extending an unswept parent deadline may require reacquiring children previously removed from the device.

   **Required:** Either explicitly refuse all such compositions transitively, or define descriptor validity boundaries, clock handling, expiry revocation, and reacquisition. Specify parent `not before` admission as well. The existing [time publisher](/home/ccheever/projects/sb4-w14-rules4/snapback4/crates/snapback4-core/src/engine/time_audience.rs:87) publishes bounded row transitions; it supplies no inherited-scope algorithm automatically.

5. **High — Epoch identity is insufficiently defined across revocation, reuse, and rollback (§§2, 4, 5).**  
   The RFC explicitly increments epochs for parent policy changes, but does not establish an acquisition incarnation for roster revoke/regrant without a parent-row write. It also permits parent-id reuse after physical children disappear. A disconnected device can still retain those old children. No rule requires epoch identity to remain distinct across parent deletion/recreation, compaction, or rollback.

   **Required:** Define a durable monotonic authority/acquisition identity and retained revocation evidence. Bind descriptors, staged data, coverage, and continuations to it. State precisely what survives deletion, compaction, generation replacement, and rollback so an old child or acquisition cannot match newly created authority.

6. **High — Mixed captured/live chains and their adoption rules are unresolved (§§2, 5).**  
   Acyclicity does not establish compatibility with captured-through invariants. For example, a captured child of a live-through parent encounters an effective parent deadline that can change through an ancestor. Existing capture semantics depend on immutable parent inputs and deadlines, enforced by [through validation](/home/ccheever/projects/sb4-w14-rules4/snapback4/crates/snapback4-core/src/schema/through.rs:186). The RFC does not define which mixed chains remain admissible or how their authority and lifetime representations compose.

   **Required:** Provide an admission matrix for live-over-live, live-over-captured, and captured-over-live chains. Explicitly refuse unsupported combinations. For admitted combinations, define audience normalization, ancestor invalidation, expiry behavior, and adoption order. Adoption must also specify predecessor-lifetime retirement, dormant restoration, and capture removal/recapture before publishing the destination generation.

The conservative transitive table dependencies in §3 are a viable invalidation strategy. Their implementation must include authority metadata transitions as well as ordinary row writes.
