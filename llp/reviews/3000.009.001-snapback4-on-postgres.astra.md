## Verdict: SOUND WITH MAJOR ISSUES

The overall direction is sound: retain the interpreter, extract a semantic port covering all durable state, and measure the commit bottleneck before expanding the serving topology. However, the proposed failover, retention, and graduation mechanisms contain correctness holes, and the verification scheme cannot deliver the stated size-independent write pause as written. These require design changes before acceptance. This is a read-only review of `30384907ed`; runtime fault injection, managed-provider behavior, and current competitor capabilities are **UNVERIFIED**.

## Fundamental and major findings

### F1. Lost acknowledged history cannot safely retain the same incarnation — FUNDAMENTAL — store-port §5; parent §3.1

The store-port RFC permits asynchronous failover to lose acknowledged commits, relying on a head-regression check to refuse unsafe continuation ([RFC:158](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:158)). That check cannot establish history continuity.

For example, a device observes sequence 100, a replica is promoted at 98, and unrelated writes refill sequences 99–100 before that device reconnects. The identity and head now match its expectations, but its acknowledged history has been replaced. It can retain rows that no longer exist and skip replacement events. The actual device check detects only `head < floor`, not divergence at an equal or greater head ([store_identity.rs:102](../../snapback4/crates/snapback4-device/src/device/store_identity.rs:102)).

There is an even simpler case: acknowledged session revocation can disappear without any head regression, because revocation commits without advancing the public sequence ([identity.rs:732](../../snapback4/crates/snapback4-core/src/identity.rs:732)). A previously invalid token becomes valid again.

**Recommendation:** make history-preserving promotion an enforced prerequisite for transparent same-incarnation failover. Otherwise, refuse service until recovery creates a new incarnation and handles uncertain work. Reporting synchronous replication in `doctor` is insufficient; the promotion policy must actually guarantee preservation of acknowledged transactions. The accepted parent already requires a new incarnation and quarantined uncertain work when restoring an earlier point ([accepted parent:953](../../llp/3000.009-general-purpose-backend.rfc.md:953)).

### F2. The cutover is not a crash-safe ownership transfer, and reverse capture starts too late — FUNDAMENTAL — graduation §§5, 7

Step 5 makes Postgres live and **then** durably marks SQLite graduated. The only preceding source fence described is stopping admissions in the running process ([RFC:147](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:147)). A crash after the Postgres transaction commits but before the SQLite marker is written leaves the target eligible to serve while the source still lacks its durable write prohibition. A token stored in Postgres cannot fence a separately reopened SQLite database.

An ambiguous target commit is equally consequential: losing the connection during ownership transfer cannot authorize reopening source writes merely because the coordinator did not receive success.

There is also an explicit data-loss window in reversal: step 6 admits held writes against Postgres; step 7 arms reverse capture ([RFC:161](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:161)). Writes acknowledged between those steps never enter the reverse journal. Reverting would lose them while preserving the logical identity.

**Recommendation:** specify a durable cross-store handoff state machine. Persist a fail-closed source preparation before the target becomes eligible, bind both sides to one migration decision, and define recovery from every partially completed or ambiguously acknowledged transition. Install reverse capture before the first target application write. This protocol must govern process restart as well as the successful command path.

### F3. The “quick digest” is a full-store operation, and a replay position is not automatically a consistent snapshot — FUNDAMENTAL — graduation §§2, 4–6

The central promise is a write pause independent of store size ([RFC:48](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:48)). Yet the digest that gates the paused cutover hashes canonically ordered records across every durable family, including rows, indexes, and retained logs ([RFC:176](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:176)).

An ordered rolling SHA-256 is not an incrementally maintainable content root for arbitrary inserts, updates, and deletes. Computing it after the fence scales with store size. Computing it earlier does not establish equality at the final cut without an additional maintained verification structure. Calling a different comparison “complete” and excluding it from the pause does not remove this full-store work.

The proposed pre-cutover verification also lacks a consistent comparison point. Chunks come from different source snapshots, so the target can contain values newer than its replay position. Moreover, `jid` identifies individual trigger records, not transaction boundaries. Consequently, the claim that the target is consistent “at a replayed `jid`” is too strong ([RFC:104](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:104), [RFC:132](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:132)). Final convergence is plausible; arbitrary intermediate snapshots are not.

**Recommendation:** design transaction-aligned verification barriers and an incremental verification scheme—such as maintained chunk hashes with a composable root—before promising the pause bound. A valid replay barrier must follow every chunk’s source snapshot, and shadow queries need an actual matching source snapshot. Otherwise, explicitly weaken the pause or verification guarantee.

### F4. Retention deletes authority state needed by resumes above the floor — MAJOR — store-port §7.3; graduation §4.2

The proposal deletes all `_log` and `_commits` entries below the retention floor, while allowing devices at or above that floor to continue normally ([RFC:276](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:276)). In the current implementation, those old records are also authority state.

`memberships_before()` retrieves the last membership transition before the requested watermark. `intervals()` deliberately retains predecessor-only groups because an expired grant can still owe revocation even when no current membership or later transition exists ([store.rs:805](../../snapback4/crates/snapback4-core/src/store.rs:805), [partition.rs:1003](../../snapback4/crates/snapback4-core/src/partition.rs:1003)). The existing `undoing_a_replacement_keeps_the_predecessors_revocation` regression exercises this case and requires the device to discard its previously held row ([reviews.rs:502](../../snapback4/crates/snapback4-sim/tests/reviews.rs:502)).

Put the retention floor after that original grant but at or before the device’s watermark: the proposed pruning removes the predecessor needed to generate the owed revocation. The device is above the floor, so reacquisition does not repair it. Other paths walk earlier join chains and retrieve their commit times to distinguish previously live grants from grants never held live ([partition.rs:1197](../../snapback4/crates/snapback4-core/src/partition.rs:1197)).

**Recommendation:** separate disposable delivery history from retained authority facts. Before pruning, create a sufficient authority checkpoint at the floor, including the lifetime/history facts required by current sync semantics. Extend the shared partition contract and its oracles to consume that checkpoint. Graduation must copy it alongside the retained log window.

### F5. The durable-state inventory omits the worker completion ledger — MAJOR — store-port §§4, 9; graduation §§2, 4, 7

The proposed durable inventory covers the main store and asset bytes but omits the separate SQLite worker ledger ([RFC:101](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:101)).

This is consequential state. The worker commits a successful handler result to `completions` **before** settling the effect with the server ([worker-ledger.ts:54](../../snapback4/packages/snapback4/src/worker-ledger.ts:54), [worker.ts:195](../../snapback4/packages/snapback4/src/worker.ts:195)). The supervisor locates that ledger beside the SQLite store, namespaced by store identity ([dev_worker.rs:414](../../snapback4/crates/snapback4/src/dev_worker.rs:414)). The accepted design explicitly says that it must travel with backups and does not work as a distributed ledger across separate disks ([accepted parent:514](../../llp/3000.009-general-purpose-backend.rfc.md:514)).

Consider a completed provider call whose ledger commit succeeds but whose server settlement is interrupted. After takeover on another host, the copied `_outbox` still permits redelivery, while the new worker lacks the completion record. It invokes the handler again. This expands the existing ambiguity window beyond the documented crash-before-ledger-commit case.

**Recommendation:** include completion suppression and worker execution ownership in the port, graduation, backup, and standby contracts. Either provide shared durable completion state with appropriate coordination, or explicitly constrain supported worker placement and ledger transfer. Copying the main database’s work tables alone does not preserve this accepted behavior.

### F6. Public commit sequence is insufficient for the proposed fencing and optimistic validation — MAJOR — store-port §§5, 6.3

The fencing mechanism is attached to advancing `_head`; the optimistic validator checks write sets of public commits in `(S, head]` ([RFC:146](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:146), [RFC:199](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:199)). Neither mechanism, as specified, covers every durable transaction.

Session invalidation, work claims, and some receipt writes commit without advancing that sequence. The Postgres tail explicitly does nothing when no application commit was recorded ([tail.rs:24](../../snapback4/crates/snapback4-core/src/engine/postgres/tail.rs:24)); receipt-only mutations still persist their receipts and commit ([postgres/mod.rs:313](../../snapback4/crates/snapback4-core/src/engine/postgres/mod.rs:313)). The graduation RFC correctly acknowledges this distinction itself.

Thus a stale owner’s non-head-advancing transaction would never execute the proposed token predicate. Similarly, a speculative execution can span an authority change while `(S, head]` remains empty. Recording only the interpreter’s row/index reads also misses dependencies read outside `Runner`.

These are currently protected by broader serialization: Postgres authority invalidation explicitly requires the serialized head fence, and HTTP mutation authority is revalidated while holding the same engine lock used for mutation ([authority.rs:104](../../snapback4/crates/snapback4-core/src/engine/postgres/authority.rs:104), [serve.rs:1410](../../snapback4/crates/snapback4/src/serve.rs:1410)).

**Recommendation:** require ownership validation for every durable transaction, including those publishing no sequence. Define either an internal revision/order covering all relevant family writes or explicit final serialized validation of authority, receipts, leases, and other non-Runner dependencies. This belongs in the `StoreTx`/`Committer` contract before choosing candidate (a).

### F7. Waiting on a session advisory lock does not provide takeover from a paused owner — MAJOR — store-port §§5, 10

The standby waits to acquire the owner’s session-level advisory lock ([RFC:142](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:142)). Qualification nevertheless requires takeover while the old owner is `SIGSTOP`ped ([RFC:336](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:336)).

Pausing the application does not necessarily terminate its Postgres backend session or release that lock. The dedicated connection can remain alive indefinitely. Expiring the `_owner` lease does not release a session advisory lock, and the specified standby cannot reach token acquisition while waiting for it. The token addresses stale-writer safety only after takeover has occurred.

**Recommendation:** choose an explicit takeover mechanism: a database-clock lease protocol that can advance ownership after expiry, or database-enforced termination/timeouts that release the previous session and any transactions obstructing takeover. State the necessary privileges and connection behavior. The advisory lock cannot remain an unbounded prerequisite while paused-owner recovery is a P1 guarantee.

## What the documents get right that should not change

- Treating logical identity separately from a database file, connection string, or serving process.
- Keeping shared policy in Rust and making the port cover identity, work, evolution, assets, and time—not merely application rows.
- Preserving one interpreter and one commit order while measuring alternative commit implementations.
- Capturing all durable writes during graduation rather than treating the application commit log as sufficient change capture.
- Separating P1 from P2, with the reference implementation retained as a correctness oracle.
- The scale study’s equal-authorization controls, explicit durability, advocate review, RTT sweeps, open-loop load, and distinction between measured ceilings and public claims.
