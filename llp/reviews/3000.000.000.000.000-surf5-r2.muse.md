## Blocking / material issues

1. **Non-Unix build break in new code (`releases.rs:43-44,54`).** `inspect_current` unconditionally calls `private_fs::auxiliary_file`, `private_fs::owner_path`, and `private_fs::owner_is_named`, which are all `#[cfg(unix)]`-only with no `not(unix)` stubs (`private_fs.rs` gates at lines 72/92/100/119/128/148; only `directory`/`file`/`existing_file`/`database_file` have dual impls). The same file's pre-existing `command_lock` call site gates its `auxiliary_file` use under `#[cfg(unix)]` (`releases.rs:160`), and the neighboring `store_owner::acquire` and `release_control::request` both maintain `not(unix)` stubs — so this crate is expected to compile off-Unix and the new preflight breaks that. Fix: `not(unix)` early refusal (or stubs) for the preflight path. Blocking if off-Unix compilation is a supported configuration, which the surrounding stubs say it is.
2. **`releases` listing bypasses the live routing its own preflight just used (`releases.rs:492`).** Preflight honors §8 ("busy stores use Status, not SQLite"), but the verb body then opens the live store's SQLite directly via `Store::open_read_only` with no sidecar exclusion — and, on stopped checkpointed stores, without the `immutable=1` URI the preflight carefully constructed (`releases.rs:76`). A read-only SQLite snapshot of a live WAL database is consistent, so this is not corruption, but it contradicts §8 for the main read, can transiently disagree with the preflight's Status result (activation can commit between the two reads with no revision check on this path), and reintroduces the WAL-sidecar creation the preflight avoids (the file's own premise at `releases.rs:34-35`). The paged listing should either go through `status()` (host-routed when live, as `rollback`/`prune` do) or reuse the immutable URI under the held exclusion. Medium severity; the `deploy --check` preview at `releases.rs:294` shares the plain-open pattern but predates this wave.
3. **Recovery branches have no tests.** The WAL-without-SHM refusal (`releases.rs:73`) and the missing-sidecar error mapping (`releases.rs:43-45`) are headline §8 behaviors with zero coverage: the `.mjs` WAL test only exercises WAL+SHM success, and `release_consumers_refuse_a_development_store_without_new_sidecars` omits the `releases` verb itself (it would refuse cleanly — worth asserting). Given these branches exist to prevent destructive recovery mistakes, each deserves a positive test. Medium-low; test-only gap, code reads correct.
