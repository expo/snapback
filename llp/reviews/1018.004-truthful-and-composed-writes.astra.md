The durable inbox is viable, and it can eliminate the RPC’s uncertain-admission outcome. **The draft needs revision before implementation**, principally around database lifecycle, ordering, identity, observation, and liveness. I reviewed the actual checkout and ran small in-memory probes; I did not run a browser witness. The draft is already committed at `126a08e`, rather than uncommitted.

1. **REFUTED-RISK — A second IndexedDB connection does not require the Web Lock.** IndexedDB permits overlapping connections and serializes conflicting read/write transactions across them; a writer transaction spanning `inbox` and `outbox` can be atomic. The Web Lock is application policy. [IndexedDB specification](https://w3c.github.io/IndexedDB/#transaction-scheduling)

   However, the existing carrier’s `open()` cannot serve this purpose: it calls `closeDatabase()` and acquires the writer lock with `ifAvailable: true`. The proposed follower connection needs a separate lifecycle. Reusing `this.database` would also affect `giveBack()`, which refuses to release an acquired lock while that field is populated. These are integration requirements, not reasons the premise is unsound. 2. **MATERIAL — The wipe description is false on real IndexedDB.** Database deletion waits for existing connections to close; it does not delete the database underneath an ordinary live follower connection. Deletion, as well as upgrading, can be blocked. [IndexedDB specification](https://w3c.github.io/IndexedDB/)

   There is no `onversionchange` handler here. `wipe()` closes only its own connection, releases the Web Lock, and then requests deletion. Adding follower connections therefore introduces deletion blockers and a takeover window during wiping. Furthermore, rejecting the Promise in `onblocked` does not cancel the underlying open/delete request; a subsequently successful open can leave an unowned connection. The decision must specify connection invalidation, abandoned-request cleanup, and wipe/takeover ordering. Its “deleted database → transaction error” account is insufficient. 16. **REFUTED-RISK — Several expensive RPC scenarios really do disappear.** With immutable rows and atomic admission mapping, writer closure before admission leaves durable queued work; closure after admission or between commit and nudge leaves a durable mapping that prevents readmission. Lost or obsolete acknowledgments become harmless stale notifications because they no longer carry admission authority. Removing command retransmission also removes the reason receipts must survive ordinary terminal dismissal.

    The five-minute command lifetime and pruning clock floor can therefore disappear; clock rollback cannot resurrect a pruned RPC command once that command route is gone. Preserve byte-identical **server replay** and its server-governed expiry. Frozen-writer custody improves from unknown to durably queued, although liveness and honest status still require the fixes above. These conclusions address the old receipt scenarios, rather than assuming their tests were unnecessary.
