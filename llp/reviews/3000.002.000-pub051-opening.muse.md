## What I verified as correct

- **Progressive default untouched.** The diff changes no startup logic; `createApp` normalization in [app.ts](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/app.ts:169) still defaults to progressive, and the new test's `default` mode boots with no `startup` option and observes loading during the gated open.
- **Retryable opening `E_STORE` stays loading and retries.** First `client.asset` during progressive opening returns `localUnavailable()` (`E_STORE`, retryable true) via `assetUnavailable()` in [local.ts](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/local.ts:1597). The hook classifies it as `openingRefused`, publishes waiting (not denied), and `recover()` reloads only on `executable || acquired` ([react.tsx](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/react.tsx:695-699), ([react.tsx](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/react.tsx:714-719)). No polling loop: while still non-executable it waits for the next local notification.
- **Permanent failure surfaces.** Gated `device.open` throwing `E_STORE` retryable false lands as `coreFailure` + `localState` unavailable in `accelerate`'s catch ([local.ts](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/local.ts:1885-1889). The hook publishes that refusal, either directly (late first read, `retryable === false` fails the classifier) or via the `unavailable` branch of `recover()`. The `failed` test mode asserts exactly this.
- **No one-view replay on the covered paths.** Opening-denied attempts return before any fetch, so nothing consumable happens before the retry. After success, `openingRefused` is false and `recover()` ignores `url` reads, so acquisition notifications cannot refetch; the test asserts exactly one `url` outcome. `media.invalidate` on denied (local.ts:1618) is unreachable for opening denials since they return at entry. Unmount/signout modes assert zero downloads and `E_AUTH` respectively.
- **Other lifetimes preserved.** Success, non-`E_STORE` denied/error, `assetError` timed download retry, sign-out guards, and cleanup/revoke paths are byte-identical to base except for the additive branches.

## Actionable defects and gaps

1. **No dedicated regression test for the `useUpload` sibling change (should-fix before landing).** The `useUpload` effect now subscribes to `localStatus` ([react.tsx](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/react.tsx:820)), but [asset-opening.test.mjs](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/test/asset-opening.test.mjs) exercises only `useAsset`. `uploadIntent` returns `undefined` while `env.unavailable()` ([uploads.ts](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/uploads.ts:121-126)), so a kept id mounted before executable shows an empty card until a local notification — the exact race the comment claims to fix — and nothing asserts the card populates on executable without user action, or that no upload is auto-replayed. Existing [upload-hooks.test.mjs](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/test/upload-hooks.test.mjs) waits for executable before booting the hook, so it does not cover the pre-executable mount. Add a kept-id-before-executable case.
2. **No hook-level test that a *successful* read survives a later acquired toggle (coverage gap).** The single-`url` assertion covers refetch-during-opening only. A regression where a post-ready local notification re-runs `load()` would consume a second one-view grant; assert `client.asset` call count stays constant across a synthetic acquired toggle after `ready`.
3. **No hook-level download-retry preservation test.** [asset-retry.test.mjs](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/test/asset-retry.test.mjs) covers `fetchAsset`/`downloadAsset` only, not `useAsset`'s `assetError` timed-retry branch after this change. A short hook test (offline-then-online with `Retry-After`) would lock the "preserve download retry semantics" requirement.
4. **Fragile coupling: any `unavailable` local state is treated as terminal, even with a retryable `why` (low severity, harden or document).** Both `load()` ([react.tsx](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/react.tsx:698)) and `recover()` ([react.tsx](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/react.tsx:716)) publish terminal denied on `unavailable` without checking `status.why.retryable`. This is correct today only because `accelerate()` never retries once `coreFailure` is set ([local.ts](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/local.ts:1867)) — and note a plain `Error` open failure becomes `E_STORE` *retryable true* via `{ ...localUnavailable(), message: String(error) }` ([local.ts](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/local.ts:1885)). If any future path sets `unavailable` transiently with a retryable `why`, the hook dead-ends instead of staying loading. Either assert the terminal-unavailable invariant next to the branch or gate on `!status.why.retryable`.
5. **Classifier race (very low probability, suggestion).** `openingRefused` requires `wasOpening || post-load non-executable` ([react.tsx](/home/ccheever/sb4-pub-0441/snapback4/packages/snapback4/src/react.tsx:695-696)). A retryable `E_STORE` sampled from `client.asset` while both snapshots read executable (a transition straddling the two `getSnapshot` calls) publishes terminal denied with no retry, since `E_STORE` is excluded from `assetError`. The mutations are synchronous today so this is near-unreachable, but a single bounded re-read on retryable `E_STORE`-with-executable would close it.
6. **RFC wording overclaims in two places (nit).** The new §4 paragraph in [3000.002.000](llp/3000.002.000-progressive-web-startup.rfc.md) says "Asset hooks keep a retryable opening `E_STORE` in loading" — only `useAsset` does; `useUpload` keeps `undefined` until refresh. And "notifications retry only that unresolved opening read" is true of the local subscription but focus/online/visibility listeners also invoke `recover()` (harmlessly guarded). Tighten both sentences.
