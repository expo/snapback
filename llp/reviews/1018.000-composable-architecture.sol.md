## Required design corrections

### 1. Persistent and incremental query execution

The current owner path does more than globally rebuild indexes: `writer.rs::rerun_live` unsubscribes and resubscribes every affected client, creating new runtime IDs and triggering full index rebuilds twice. `Runtime::rerun` already supports stable IDs and trace replacement, but is bypassed.

Specify:

- Normalize each `AuthoritativeTrace` into an exact dependency set covering point reads, absence, indexed ranges, rule inputs, constraint tables, connection/clock facts, and search `scope_touches`.
- Replace global rebuilding with `attach(id, deps)`, `detach(id, deps)`, and set-difference-based `replace(id, old, new)`, pruning empty buckets.
- Rerun the existing runtime ID with a newly sampled execution context/read time. Do not detach before successful execution.
- A successful denied or partial result replaces the trace. A runtime error retains the old trace until the owner performs terminal cleanup; cleanup detaches once. Successor/missing-operation failure remains terminal.
- Verify insert, delete, key movement, absence, policy inputs, constraints, connection, clock, search scope, and removal.

The draft also promises progressive reuse of unaffected reads and enriched components. Either explicitly remove that from the commissioned scope or implement it as a bounded second slice. A sound version caches only certified leaf read results plus their trace/receipt fragments, keys them by generation, program, authority epoch, arguments, read site and operands, and execution context, dirties them on exact dependency overlap, and uses strict per-subscription/global memory caps with recomputation on eviction or uncertainty.

### 2. Coherent observed views

The proposed refinement from the orchestrator is valid and preferable: define the coherence boundary as **one named Quarry query**, composed from bounded reusable read/value functions.

A `conversationView` query returning `{messages, count, preview}` receives one certificate, execution context/read time, receipt, completeness state, continuation, delivery, and client snapshot. Separate named queries remain independently observed. This resolves bounded waiting structurally without introducing a cross-query barrier protocol or a public plan algebra.

The document must state the limitation: one composite view has one primary pagination/cursor contract. Independently paginated regions cannot also claim atomic coherence. If coherence between separately named queries remains a requirement, this refinement is insufficient and a new grouping protocol would be necessary.

On the client, make the snapshot concrete:

- Put reduction and the current `QueryView` in one per-key observed-query store.
- Expose stable `subscribe`/`getSnapshot`; React and Expo consume it through `useSyncExternalStore`.
- Publish one snapshot per server delivery or committed local store revision.
- Subscribe mounted offline views to range-store/outbox revisions so predictions and settlements trigger one atomic reevaluation. The current client has no general observed-query notification path for every local persistent-store change.

### 3. Derivation lifecycle

A “common framework” is too vague. Define a sealed internal catalog, rather than an extension or trigger language, for:

- Scalar indexes
- Word/prefix search indexes
- Maintained count/sum aggregates
- Scheduled timer derivations

Asset custody remains outside this abstraction.

Each derivation definition should own validation, bounded reservation, transactional apply, clean rebuild, dependency/touched disclosure, and successor diff behavior. All derivations run in the row-write pipeline before the next statement, inside the same SQLite transaction. Maintained target writes must re-enter index/search/timer derivation so same-mutation reads observe the complete result; transitive maintains remain refused.

Successor handling must compute added, removed, and changed definitions; validate surviving rows; clear or rebuild affected structures; and complete before generation publication. Order source-to-target edges topologically and refuse cycles.

The governing law should be: incremental final state, trace, and bounded-cost behavior equal a clean rebuild from the final authorized source state. The native engine and offline twin share this behavioral law, while the twin continues to derive only from authorized held rows.

### 4. Typed Quarry core and deletion

The “evidence insufficient” conclusion is now stale. Search WIP spans roughly 90 compiler files and adds repeated custody, provenance, ordering, binding, and type recovery. Not every changed line is accidental machinery, so the migration still needs a file-level deletion census, but there is enough evidence to commission a direct typed core.

Use this pipeline:

1. Parse Quarry syntax.
2. Resolve names to stable symbol IDs.
3. Elaborate into typed ANF/block IR with left-to-right, single-evaluation semantics.
4. Lower directly to existing executable schema/program IR.

Represent type, nullable/presence, collection cardinality and maximum, table/page/read origin, effects, and authored site stack as separate facts. Model branch joins explicitly. Do not recover semantics from generated TypeScript identifiers or strings.

Keep the Rust certifier independent and authoritative. Retain TypeScript generation only where needed for effects, seed code, journeys, and harnesses.

Require a dual-path migration over the existing corpus and integrated search cases, comparing results, state, receipts/traces/certificates, generated API types, and authored diagnostics. Name the generated query/schema printer, line remapping, and semantic recovery modules that will be deleted; otherwise this becomes an additional compiler layer rather than simplification.

### 5. Bounded Quarry functions

Functions should be built on the typed elaborator, not another string-level inliner.

A sound first version is:

- Module-local functions with explicit typed parameters and one inferred return type
- Read-only certified bodies: pure expressions, reads, `require`, bounded `if` and `for`
- No writes, emits, jobs, captures, closures, recursion, first-class values, generics, dynamic dispatch, or imports
- Acyclic call graph
- Maximum call depth 8 and expanded-node cap 4096
- Left-to-right, once-only argument evaluation into fresh symbols
- Alpha-renamed locals and helper-local `return`
- Compatible return type on every path
- Caller-owned certification, trace, receipt, and cost
- Diagnostics containing both definition and use-site stacks while preserving exact existing refusal codes

This is sufficient to compose the coherent named views above. List indexing remains a separate Quarry gap.

LLP 1011 and `rules/NOT-DOING.md` must record the explicit trade change because general `fn` behavior is currently deferred/refused.

### 6. Account session ownership and follower forwarding

The draft needs an exact idempotency and authority protocol.

Use a `BroadcastChannel` scoped to canonical backend identity and principal, with the Web Lock holder as sole writer. A forwarded command contains protocol version, random forwarding ID, principal/auth epoch, session incarnation, operation, and arguments. It never contains a bearer token.

The writer accepts only commands matching its exact current authority and session incarnation, serializes them through `OutboxLedger`, and persists the forwarding ID on the outbox entry. The acknowledgment is sent only after atomic grant consumption, intent creation, and prediction commit. Lost acknowledgments cause retry with the same ID; durable deduplication returns the existing intent and prevents duplicate server commits after takeover.

Define ordering as durable writer-admission order, with per-follower send order preserved. Broadcast arrival does not define cross-tab wall-clock order.

Add a bounded response protocol: for example, a two-second no-ack transition to a named `writer-unresponsive` state, followed by retry or lock takeover when Web Locks permit it. Do not steal ownership based only on a heartbeat. Account replacement, expiry, and sign-out fence pending commands by session incarnation; late acknowledgments are ignored.

The regression matrix must cover two offline writers, lost acknowledgments, retry, writer closure before and after durable commit, takeover, frozen writer, authority replacement/expiry, obsolete acknowledgments, FIFO admission, and exactly-once server ledger effects.

Two material corrections remain.

### 1. Define a recoverable follower-timeout result

Section 8 says that after two seconds the waiting API settles with a named uncertainty/refusal outcome that preserves the request identity for safe recovery. It also says to use the existing queued-mutation return contract. Those requirements do not yet compose.

The existing `MutationQueued` value requires a writer-allocated durable `intent` and `ids` and means the mutation is durably queued. At the timeout boundary the follower has received no acknowledgment, so it knows neither whether admission happened nor, if it did, the writer’s intent and IDs. It cannot truthfully return `queued`. A fresh call to `mutation()` creates a fresh request ID and can duplicate an earlier admission whose acknowledgment was lost. Merely placing the old request ID in a refusal is insufficient unless some operation accepts that identity for recovery.

Choose and specify one concrete contract:

- Add an `admission-unknown` result containing request ID, payload digest, expiration, and a public recovery operation that rediscovers the current writer and looks up/retries the same request ID and payload; return ordinary `queued` only after a durable receipt supplies intent and IDs; or
- Keep the original mutation promise pending while the coordinator retries the same request ID, expose `writer-unresponsive` only through readiness at two seconds, and settle by the finite request deadline after a final receipt lookup. If that lookup is still impossible, return a recovery token accepted by a named recovery operation.

Recovery must be limited to the same canonical backend, principal, and server auth epoch. Account replacement or expiry may invalidate publication, while an old durable receipt still prevents duplicate admission. State explicitly that callers must not convert an unknown outcome into a fresh request ID.

This is necessary to make lost-ack and takeover behavior implementable without weakening exactly-once admission.

### 2. Dispose all committed search component repairs, not only the named subset

Section 2 correctly treats `3eba7655b` as an unqualified integration starting point and excludes uncommitted active-lane bytes. However, it names only the survivor-uniqueness repair and browser/offline tests for reconciliation. There are also committed component changes after or outside that squashed candidate, including the compiler tip `d3e497acd` with literal-absence preservation and its preceding collection/capture/custody regressions, plus the separate twin tip `82c43ca45`.

Because the cohesive candidate is squashed, ancestry cannot prove which semantic repairs and regression cases it contains. Require an inventory and explicit disposition of every committed component delta relative to the candidate. A repair may be integrated, shown already equivalent, or superseded by the direct typed frontend, but its regression witness must enter the search qualification or typed-path parity corpus. Continue excluding uncommitted bytes. This prevents the prerequisite integration from silently dropping already-discovered correctness cases.

No further material design changes are required. The narrowed function subset is sound: helpers are expression-only, arguments evaluate once at the caller, expansion is statically bounded, and authorization/refusal stays with the caller. The row lifecycle correctly avoids timer generalization while ensuring maintained target writes take their normal index/search/timer path. The incremental/rebuild law appropriately requires observable equivalence without demanding identical internal work. The decision to omit read-result caching is explicit and does not drop the commissioned trace-index repair.

Conditions for readiness are therefore limited to:

1. Specify the timeout/recovery API and result state so the same forwarding request can be recovered without inventing a new ID.
2. Expand the search prerequisite to inventory and disposition all committed component repairs and retain their regression witnesses.

I verified the supplied SHA and reviewed the round-three changes. The design is now materially correct and implementable.

The follower timeout contract is closed. `admission-unknown` truthfully represents the state before a durable acknowledgment and cannot be confused with `queued`. Its opaque token binds the request, payload, expiration, backend/carrier scope, principal/auth epoch, and durable partition incarnation. `recoverMutation(ref, args, token)` supplies the missing safe operation: it verifies the same operation and payload, rediscovers the current writer, and retries or looks up the same identity. It returns `queued` only when the durable receipt can reproduce the writer-allocated intent and ID slice. The timeout retains its slot and request identity, and the text explicitly forbids retry under a fresh ID.

The adjacent lifetime fences are sufficient. Web Lock takeover preserves the durable partition incarnation, while wipe and relogin create a new one even when principal and auth epoch repeat. The persisted monotonic admission/pruning clock floor prevents wall-clock rollback from making a pruned request admissible again. Expired recovery can read a surviving receipt but cannot create new work. The bounded receipt and in-flight limits therefore remain compatible with lost acknowledgment, settlement dismissal, takeover, pruning, and account replacement.

The search prerequisite now has a finite, reviewable input set. It names the native, compiler, twin, and domain-repair tips and requires each committed delta to be integrated, demonstrated equivalent, or superseded while retaining its regression witness. This resolves the risk created by using a squashed cohesive candidate without turning active branches into an unbounded moving prerequisite.

The remaining closure edits are also sound:

- The composite record makes no pagination claim. It has no certified continuation or drain support; independently paginated messages remain a separate named observation without atomic grouping.
- Shapes and expression helpers instantiate exactly once in the bound elaborator, under one shared depth/node budget and one definition/use stack. The old AST expander and TypeScript helper inliner are replacement targets rather than hidden second expansion phases.
- Existing execution-context builtins are distinguished from caller-local captures, so the expression-only helper restriction remains precise.
- Newly legal Quarry names are tested directly rather than forced through an obsolete generated-TypeScript oracle.

The six commissioned moves, the search prerequisite, their boundaries, and their completion evidence are now concrete. I found no remaining material ambiguity that requires another design revision. Implementation should preserve the named witnesses and update the governing LLPs, public types, hooks, and guide where the design requires them.
