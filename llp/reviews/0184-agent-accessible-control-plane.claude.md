## MATERIAL concerns

1. **`mcp-control` cannot serve "build-matched Guide resources," so the RFC's central discovery fix is unbuildable as written.**
   §Design/4 states: "`snapback mcp-control` remains the explicit control server, but also re-serves the same build-matched Guide resources and the control catalog. One control registration is therefore enough for an operating agent to discover both documentation and tools." This is the load-bearing sentence for Phase 0 item 3 and for the Acceptance criterion "From a fresh MCP registration, an external agent discovers the network profile tools…". But:
   - The guide corpus is embedded into the **Rust binary** at compile time — `build.rs:22-27` (`cargo:rerun-if-changed=guide`, `emit_embedded_guide()`), `build.rs:102-119`, consumed by `src/guide.rs:18` (`include!(concat!(env!("OUT_DIR"), "/embedded_guide.rs"))`). "Build-matched" is specifically a property of that embedding: `guide/conventions.md` — "At server compile time, `build.rs` restamps the embedded manifest's `buildIdentity.commit` to the exact binary build."
   - `mcp-control` is **JS, in a separately versioned npm package** (LLP 0042's 2026-07-23 amendment: "the control-plane MCP server ships inside the `@snapback/cli` package as a `snapback mcp-control` command implemented in JS"). Its published `files` array (`packages/snapback-cli/package.json:20-36`) contains **no** guide corpus — no `guide/`, no `guide-flat.generated.md`, no `guide-manifest.generated.json`.
   - It also currently advertises no resources at all: `packages/snapback-cli/mcp-control.mjs:1031` — `capabilities: { tools: { listChanged: false } }`.

   So the JS server's only routes to build-matched guide content are (a) proxying a *running* server's `/_snapback/guide` (`src/server.rs:8638-8646`) — unavailable before `snapback_start`, which is exactly the cold-agent moment the RFC is trying to fix — or (b) reading the repo's `guide/` tree, which Phase 5 explicitly forbids ("Run the evaluation from outside the Snapback source tree against a packaged build"), or (c) shelling out to the Rust binary, which the RFC never names. **Resolution:** name the mechanism explicitly (most plausibly: the Rust binary gains a guide-resource export the JS server invokes, or the guide server moves/duplicates), and state how identity is bound when the `@snapback/cli` version and the Rust binary build differ — the RFC's own "Consumers refuse to combine mismatched catalog and instance identities" rule makes that a first-class question here.

2. **Acceptance depends on LLP 0146 typed remediations, which are unbuilt and whose contract is still an open question in 0146 — and 0182 quietly answers half of that open question.**
   §Design/4: "Every refusal carries the underlying structured diagnostic and LLP 0146 remediation projection." §Acceptance: "every structured refusal preserves the subsystem diagnostic plus typed remediations." §Acceptance is introduced as a conjunction — "The RFC is implemented only when all of the following hold."
   - `remediations` appears **nowhere** in `src/` (`grep -rn "remediations" src/` → zero hits). LLP 0146 is `Status: Draft`; D7 is verdict "**Build, narrowed — D7**" (`llp/0146:265`), i.e. not built.
   - LLP 0146's OQ6 is explicitly open and includes exactly the question 0182 answers: "**D7 remediation carrier and registry.** Do remediation kinds live in a registry keyed by refusal code? The carrier is an LLP 0094/0095 wire-contract decision, not LLP 0144's: envelope field, diagnostic-details member, or separate lookup — **and what is the disclosure behaviour across the CLI, HTTP, and MCP projections?**" (`llp/0146:1203-1207`).
   - 0182's §Authority-and-scope says "LLP 0146 owns typed remediation semantics." Requiring uniform remediation disclosure across CLI/MCP/HTTP *is* a ruling on 0146 OQ6's second half, and §Design/1 additionally requires the catalog schema to "represent … LLP 0146 remediation kinds," which presupposes the registry answer to OQ6's first half.

   **Resolution:** either (i) demote the remediation requirements to "when LLP 0146 D7 lands, catalog rows and refusals adopt its carrier," and remove them from the Acceptance conjunction, or (ii) declare the dependency explicitly, sequence it in the delivery plan, and record it as a proposed 0146 OQ6 amendment subject to that document's author. As written, the RFC can never be marked Implemented and covertly decides a neighbour's open question.

3. **The five-way `agentAccess` disposition is not mutually exclusive and not enforceable as defined, and the RFC's own OQ5 breaks it.**
   The enum mixes three different axes in one closed value:
   - `native` and `api` are defined by **frequency and composition** — `native` = "Common agent operation," `api` = "Rare or compositional specialist operation."
   - The CI rules that test them (§Design/3 rules 4 and 5) test only **projection presence** — "typed CLI command, typed control-MCP tool, … Guide anchor, … acceptance witness" vs "a stable typed API/client projection plus a complete invocation recipe." A checker cannot test "common" or "rare," so every contested row becomes an unenforceable judgement call, which is precisely the drift failure mode the RFC exists to eliminate.
   - OQ5 then repurposes `api` as a **risk** parking lot: "dangerous operations may remain cataloged `api` operations with named CLI projections rather than claiming incomplete `native` parity." A destructive-but-common operation with a named CLI is neither "rare" nor "compositional," so this row's disposition contradicts the disposition's own definition.

   The concrete casualty is assets, which the RFC itself flags: §Where-current-surface-falls-short — "Rich CLI and host operations | Agent-operable from a shell, but absent from MCP." I verified the shipped state: ten typed `snapback assets` subcommands (`src/cli.rs:1306+` — `Put`, `Inspect`, `List`, `Retry`, `GcSweep`, `RotateSigningKey`, `ExportCut`, `ImportCut`, `EnsureSeedFixture`, `Delete` at `:1416`), ten `host_ops.asset.*` registry identities, and zero MCP tools. That row is not `native` (no MCP tool), not `mediated`, not `internal`, not `unavailable` — and calling it `api` contradicts `api`'s definition. **There is no disposition for "has a full typed CLI, deliberately has no MCP tool,"** which is both the current state of the largest operation family and the state OQ5 wants to keep available.
   **Resolution:** split the axes. Make the closed disposition purely about *what surfaces are required* (`cliAndMcp` / `cliOnly` / `apiOnly` / `mediated` / `internal` / `unavailable`), and carry risk (`destructive`, `approvalPosture`) and frequency/promotion evidence as separate fields the checker can test independently. Then OQ5 becomes a question about the `approvalPosture` field rather than a question that corrupts the disposition enum.

4. **§Design/3 rule 2 is fail-open, so it cannot detect the failure mode the RFC exists to prevent.**
   Rule 2: "Every console button, form submission, and mutating action **exports** a stable operation identity that resolves to a catalog row. UI-local presentation actions such as changing tabs are excluded explicitly." Two gaps:
   - **Exclusion has no named mechanism.** "Excluded explicitly" — by whom, in what file, checked how? The RFC never says.
   - **Inclusion is voluntary.** If the console's compliance is "export an identity," then a new click-only button that exports nothing is invisible to the checker — silence is *not* a build failure, contradicting §Summary/2 ("An omission requires a reason; silence is a build failure"). §Design/2 forecloses the obvious fix: "the admin client and console export stable action identities **rather than relying on label scraping**."

   The boundary is genuinely hard here, not theoretical. The console is a declarative Contract app: `admin-ui/app.contract` declares `action cleanupNow` (`:162`), `action verifyEntry` (`:164`), `action openTable` (`:124`), `action pageTo` (`:128`). `openTable`/`pageTo` look like presentation but issue admin reads via `client.scanTable` (`admin-ui/admin-boundary.mjs:200-208`). A rule that cannot classify `pageTo` cannot be built.
   **Resolution:** name an *independent declared enumeration* the checker walks — `action` declarations in `admin-ui/app.contract` are declared, machine-readable, and not label scraping — and require each enumerated action to carry either a catalog operation id or an explicit `uiLocal` marker with a reason, so omission fails closed. This is the same shape as LLP 0061's existing route/host-op join (`scripts/guide-lib.mjs:425-438`), which does fail closed.

5. **§Design/3 rule 1's domain is under-specified, and the reading the RFC endorses collapses the app-data plane into the ControlCatalog.**
   Rule 1: "Every registered **host operation and admin route** has a catalog row or a closed `internal` classification with a reason." But §Design/3 closes with "The checker extends the useful LLP 0061 surface-map join rather than replacing it," and that join's domain is **every declared route and every registry operation**, not just admin ones (`guide/surface-map.md:19-22`; `scripts/guide-lib.mjs:329, 358, 425-438`). The two readings are both broken:
   - **Broad reading (the LLP 0061 join):** the registry I enumerated in `src/server.rs:14972-15641` contains app-data-plane entries — `live("ephemeral_publish")`, `live("ephemeral_delete")` (`:15071`), `live("ephemeral_subscribe")`, `direct_runner.{query,mutation,action,unknown}`, `app.ensure.{legacy,attest,provision}` — plus app-data routes such as `POST /ephemeral/delete` (`src/server.rs:8619`). Requiring a `ControlCatalog` row for each collapses exactly what the RFC forbids: "**No app-data/control-plane collapse.** Application calls and operator controls retain distinct namespaces, credentials, and audits," and undercuts the §Authority-and-scope promise that the catalog and LLP 0179's `AppDescriptor` "must never merge namespaces."
   - **Narrow reading ("admin route"):** `POST /_snapback/api/connections/{connection_id}/disconnect` is registered in the **system** lane in `src/server.rs:8737` (LLP 0031 D2 classifies it system/control), not in `src/admin.rs`. Under a literal "admin route" domain, the single control the RFC calls "the most hidden shipped control" escapes the rule written to catch it.

   **Resolution:** define the catalog's domain by a positive, code-checkable predicate — e.g. every registry entry whose `RouteClass` is not `AppData`, plus every `host_ops.*` identity — and state explicitly that app-data-plane operations are *out of domain* (owned by LLP 0042's app-data catalog and LLP 0179's `AppDescriptor`), so the two enumerations partition the registry rather than overlapping it.

6. **The "does not take semantic authority from" list omits LLP 0044, whose surface §P2 proposes to widen.**
   §Authority-and-scope enumerates eight neighbours as a closed boundary list. **LLP 0044 "Asset storage pipeline" (`Status: Accepted`) is absent** — from that list and from the `Related` header — yet §P2 proposes "**Asset delete/GC/key rotation/export/import:** catalog all existing CLI paths; add direct MCP tools only with exact destructive annotations, preconditions, and approval posture." Those are LLP 0044's operations; `src/cli.rs:746-748` says so in code — "asset.\* — **the LLP 0044 asset operator surface**: upload through a generated intent, inspect a complete lifecycle, list, re-drive generation-fenced work, delete." Adding MCP projections of key rotation and consistent-cut export/import, with new "approval posture," is precisely the kind of decision the RFC's discipline section exists to route to an owner. Similarly, §B's and §C's claims about `resync_required` emission and ephemeral store delete/notification mechanics touch the ephemeral/realtime and wire-contract owners, none of which is named in the boundary list (0094/0095 appear in `Related` but not in the disclaimer).
   **Resolution:** add LLP 0044 (and the ephemeral/wire owners relevant to §B/§C) to the disclaimer list with the same one-line ownership statement given the other eight, and say which of them Phase 3's "Amend the semantic owner documents as needed" is expected to touch.

**Claims I judged and found to HOLD:**

- **The `ControlCatalog` / `AppDescriptor` separation.** I read `llp/0179` §Summary, §Authority-and-scope, and §AppDescriptor-v1. The separation holds cleanly: 0179's descriptor is app-data vocabulary (`api.queries/mutations/assets/ephemeral`, `commands`, `surfaces`) explicitly scoped to what "an application consumes," and it disclaims exactly the neighbouring territory 0182 does not want. The one shared word is `capabilities` — 0179's `capabilities.required` is *app* requirements, 0182's is *instance*-enabled capabilities — which is a naming hazard worth a sentence but not a namespace merge. 0179's own naming note (on "manifest" vs "descriptor document") shows the authors are already alert to this class of collision. **Caveat:** this separation is what MATERIAL 5's broad reading of rule 1 would breach; the boundary is stated correctly and then endangered by the completeness rule.
- **`data.patch`'s `devImpersonation` vs `operatorBypass` split** does not duplicate an existing authority model. LLP 0042's five modes (`none`/`unauthenticated`/`devUser`/`devAdminBypass`/`servicePrincipal`, `llp/0042:100-115`) and LLP 0031's `InvocationAuthority` are adjacent but not the same axis: 0182's split is a *disclosure* obligation about whether application authorization was evaluated, which is a genuinely new fact. It should be spelled as a projection of `devUser`/`devAdminBypass` rather than as fresh vocabulary, but that is naming, not a conflict.
- **§D's rejection of simulated publish is well-reasoned.** Its two arguments — that a connection-less privileged write "would test a world actual clients cannot inhabit," and that it "would create a second publish implementation whose success says little about the application path" — are exactly right given `/ephemeral/delete`'s verified publish-parity + connection-bound + own-owner enforcement. A privileged bypass would have to skip all three, and passing tests against it would prove nothing about the real path. Naming a concrete successor (a real-connection scenario step, plausibly LLP 0146 D6) rather than leaving the gap silent is the right shape. I do not think this leaves an unaddressed gap.
- **OQ1 (compiler seam) is genuinely open and answerable, with an existing precedent the RFC could have cited.** `packages/snapback-cli/network-profile-authority.json` is exactly the "export Rust registry facts into a neutral artifact and join JS projections" pattern — a checked-in neutral artifact (`{"builtinNames": ["normal","optimistic","demo-slow"], "delayCeilingMs": 30000}`) consumed by `mcp-control.mjs:37` and cross-verified from Rust at `src/network_profile.rs:1008`. That satisfies OQ1's stated deciding criterion ("one cheap deterministic local-proof path without parsing source text for semantic facts") and would be worth naming.
