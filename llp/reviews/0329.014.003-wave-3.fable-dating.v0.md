# Paper archetype: dating app against LLP 0329.014.000 v0.1

**Respondent:** Claude Fable 5 · **Design:** wave-3 #2 (codex), fixed · **Target:** LLP 0329.014.000 v0.1, §9.1 rulings included.

Headline. The mutual match is expressible *in v0 as written* as a rule over one visible and one hidden row, and the swipe program's branch on it needs no new construct: the caller's own like, inserted in the same transaction, is what makes the hidden opposite like readable (§3 op 4). The design's mutable pair row dissolves into an append-only event table plus a hidden maintained count, which also removes a leak in the design (§8 #2). What the spec gets **wrong** here is §9.1 ruling 2: hidden rows consuming `take` make `hasMore` a count of who liked a free member — contract 6's paid secret, with a clean certificate (§4, L1). Block needs the retention dimension with a lease shorter than the store's (L2). Proximity is a prefix scan; the cost is the exclusions. L1–L9 are §6 items, **not** spec features.

### 2. Schema in v0

**There is no mutable pair row.** The design's `pair_state` becomes four derivations: `pairGeneration`, a hidden maintained count over append-only `pairEvents` (every pass, unmatch, block, unblock is one event its actor may read); `separations` current rows (creator-visible, otherwise hidden); `suppressions` flipped by schedule; `matches.byPairOpen`. A member never writes a row they cannot read; every fence is a rule. Sender-visible intent columns and hidden status columns are two tables, so a pass, expiry or consumption never touches a row the liker holds (§8 #2). Omitted, all owner-or-system rows with ordinary rules: `staffRoles`, `swipeEvents` (append-only audit), `discoveryPreferences`, `locationFixes` (append-only; unique `[deviceId, deviceSeq]`; coordinates owner/system only), `suppressions` (system-only), `entitlementEvents` (unique `providerEventId`), `entitlementsCurrent` (update rule `providerRevision >= old`), `verificationAttempts` (unique `providerRef`), `reports` (reporter and safety staff read), `reportEvidence` (`cap` 20; staff-only read; reporter may insert), `safetyActions`.

### 3. Operations in v0

Grouped by the design's §5; certificates in §1; audit inserts elided.

**§5.1 Publish a profile.** `publishProfile({ versionId, expectedVersion })` reads the draft, `require`s the expected version, then `db.scan(promptAnswers.byVersion, [v.id], { take: 3 }).all()` and photos `take: 6 … .all()` — `All<T,N>` is admitted because both children are `cap`ped — so `require(prompts.length === 3 && photos.length >= 2)` and `moderation === 'approved'` are exact over the owner's rows; flips old→`superseded`, draft→`published`, the current pointer, `badgeHash = null` when `photoSetHash` changed, `eligibilityVersion + 1`. First attempt `Date.now()` → **`E_AMBIENT_TIME`**. The `cap` is the sealed upper bound; the lower bound stays a `require` (§5). `createAccount` is one insert with `require(ageAt(birthDate, ctx.commitTime) >= 18)`.

**§5.2 Location and travel.** `updateLocation`: `unique('byDeviceSeq')` rejects replays sealed; `require(accuracyM ≤ 500 && ctx.now() − capturedAt ≤ 24 h)`; the previous fix (`byUserAt desc take 1`) gives the displacement threshold; `cell = geohash(latE6, lngE6, 5)` is pure; insert the fix, `upsert` the origin (skipped while travel is `active`), `eligibilityVersion + 1`. First attempt `encrypt(coords, keyId)` → **`E_OPAQUE`**; corrected: plaintext `latE6/lngE6` under `read: owner || system` (§7). `setTravel` `require`s ≤ 30 days; `exclusion` refuses overlap sealed; `activateTravel`/`expireTravel` rewrite the origin. No member reads another's origin; the band is a system-written item column.

**§5.13 Build recommendation queues** — a `schedule`, not an effect:

```ts
export const buildRecommendations = mutation({ userId: id(accounts) }, ({ db, ctx, args }) => {   // principal: system
  const me = db.get(accounts, args.userId), pref = db.get(discoveryPreferences, args.userId), origin = db.get(discoveryOrigins, args.userId)
  if (!me || me.status !== 'active' || !pref || !origin || (db.get(usableCards, [me.id])?.value ?? 0) >= 100) return
  const cells = neighborCells(origin.cell, pref.radiusMeters)                   // pure; ≤ 49 cells (3 rings)
  const cands = []
  for (let i = 0; i < 49; i++) { if (i >= cells.length) break
    for (const o of db.scan(discoveryOrigins.byCellActive, [cells[i]], { order: 'desc', take: 41 })) cands.push(o) }   // ≤ 2,009
  const scored = []
  for (const o of cands) {
    const k = pairOf(me.id, o.userId)
    if (o.userId === me.id || !open(k) || db.get(suppressions, k)?.state === 'active' || db.exists(matches.byPairOpen, [k, true])) continue
    if (like(k, me.id) !== null && like(k, me.id)?.generation === gen(k)) continue     // my intent only (I16)
    const a = db.get(accounts, o.userId), p = db.get(discoveryPreferences, o.userId), pv = db.get(profiles, o.userId)
    if (!a || a.status !== 'active' || !p || !pv || !mutual(me, pref, origin, a, p, o)) continue
    scored.push({ id: o.userId, gen: gen(k), score: score(me, pref, origin, a, p, o), band: band(origin.cell, o.cell), elig: a.eligibilityVersion }) }
  scored.sort((x, y) => y.score - x.score || (x.id < y.id ? -1 : 1))
  // then: delete the old queued items (take 1000, exact under the cap) and insert ≤ 500 rows stamped with pairGeneration, both eligibility versions, the band
})
```

`check`: examined ≤ 3 + 49×43 + 2,009×6 ≈ 14,170 > `G` 10,240 → **`E_BOUND`** *(shows the product; rewrite: fewer cells, smaller `take`, or raise the app ceiling)*; raised to 16,384. Under system visibility the exclusions and the rank are exact (§4). The geography is ≤ 49 *prefix* scans of one index with a shared order — range-decomposable; wave 1's `merge` scan would replace the loop. `like(k, me.id)` is the only `directedIntents` read, prefix `[pair, batchUser]`: I16 is reviewable from the certificate (L5). A served model makes `score` an `effect` calling a system mutation with ≤ 2,000 scores; with an arithmetic model the program is complete.

**§5.3 Serve a recommendation page.** First attempt did the recheck in the program — `db.get(discoveryPreferences, item.candidateId)`, `db.get(discoveryOrigins, …)` — **admitted**, and every read is `null` under the viewer's visibility, so every card is voided and the queue reads empty. Corrected: the recheck *is* `cardVisible`. `servePage(size ≤ 25)` scans `recommendationItems.byUserStateRank [viewer, 'queued'] take 25`; per item, `db.get(profiles, it.candidateId)` — `null` means some hidden rule failed: void the item without explanation (the design's "a short page reveals only exhaustion"); otherwise set `state: 'issued'` (the item row is the one-use swipe token) and return `{ itemId, userId, pairGeneration, distanceBand, travelCity }`. `viewCard(userId)` returns the current version, prompts (`take 3`), photo asset ids (`take 6`) and `badge: badgeHash === photoSetHash`; bytes are a grant (L4). Two devices claim by OCC on the item row: one `committed`, one `rejected`.

```ts
  const [lo, hi] = ctx.viewer < args.targetId ? [ctx.viewer, args.targetId] : [args.targetId, ctx.viewer]
  const matchId = ctx.newId()
  db.insert(matches, { id: matchId, pairKey: k, lowUserId: lo, highUserId: hi, generation: args.pairGeneration, open: true, closedAt: null, closeReason: null,
                       likeLowId: lo === ctx.viewer ? mine : theirs.id, likeHighId: hi === ctx.viewer ? mine : theirs.id })   // rule re-derives both live likes
  db.insert(conversations, { id: ctx.newId(), matchId, pairKey: k, generation: args.pairGeneration, open: true, lastAt: ctx.now() })
  return { matched: true, matchId } })
```

Exactly one match under simultaneous likes: the second commit's `matches.insert` sees `byPairOpen` occupied and the single writer serializes; a duplicate same-direction gesture dies on `unique('byPairActorGen')`; a stale offline like dies on the fence — every failure the same generic refusal. The `pass` path never writes the other person's row: the event advances `pairGeneration`, so their like is dead by rule at once; `applyPairEvent` flips its hidden status and writes the 30-day suppression within a period. Prediction: card removal `closed`; the match `partial` — `theirs` is not in the caller's closure — the design's "a match waits for confirmation".

**§5.5 Who Liked You.** First attempt:

```ts
const page = db.scan(directedIntents.byTargetDecisionAt, [ctx.viewer, 'like'], { order: 'desc', take: 25, before: args.cursor })
return { count: page.count(), likers: page.map(card), hasMore: page.hasMore }
```

`page.count()` → **`E_STRUCTURAL_COUNT`** *(a count over rows the caller may not read; rewrite: `maintain.count … readable`, or a caller-scoped count)*. `hasMore` → **nothing**, and it is a count of hidden likes (§4). Corrected:

```ts
export const whoLikedYou = query({ before: time() }, ({ db, ctx, args }) => {
  if (!paid(ctx.viewer)) return { locked: true }                                     // no scan is executed for a free or expired member
  const page = db.scan(directedIntents.byTargetDecisionAt, [ctx.viewer, 'like'], { order: 'desc', take: 25, before: args.before })
  return { locked: false, count: db.get(incomingLikeCount, [ctx.viewer])?.value ?? 0, likers: page.map(i => ({ likeId: i.id, ...viewCard(i.actorId) })),
           next: page.length === 0 ? null : page[page.length - 1].at } })          // paginate by key; never `hasMore` (L1)
```

The count is the declared disclosure (`E_DISCLOSURE` names `intentStatus`); the row rule supplies expiry, generation, separation, consumption and liker safety per row (four hidden-input probes, all verdicts); entitlement loss retracts every row live because `paid(viewer)` is in each row's trace; the 5-minute offline lease is L2. Free and expired members receive the identical `{ locked: true }` after one point read.

**§5.6 Entitlements.** `billingWebhook` is an `effect` calling `applyBillingEvent` (`callable: 'system'`, L6): insert the event (`unique('byProviderEvent')` makes replays no-ops), `upsert` `entitlementsCurrent` under the `(old, next)` rule `providerRevision >= old`, so an older webhook cannot reverse a newer refund; `expireEntitlement` flips `status` at `validUntil`.

**§5.7–5.9 Conversations.** `conversationPage(matchId, before)`: match, conversation, `messages.byConvAt take 100`, the other's current version; every row's rule re-derives `open`, participation and separation, so a concurrent block or unmatch retracts the page through the trace — the design's "ten-minute grant" is the receipt plus L2. `sendMessage` `require`s the match `open` and `conversation.generation === args.generation`, inserts, bumps `lastAt`; order is `at: commitTime` (ties by id), so concurrent sends never conflict; `conditional` because the hidden `open(k)` clause can refuse. `unmatch`: `pairEvents{unmatch}` + `open: false` on match and conversation — messages and profile become unreadable for both in that commit; `applyPairEvent` writes the 180-day suppression; an old unmatch fails the fence. `typing` is the channel.

**§5.10 Block, unblock, report.** `block`: `pairEvents{block}`, `separations{ source: 'block', creatorId: viewer }`, close the open match and conversation. The other person's cards, likes, messages and profile are unreadable at once because `open(k)` is in every rule; their queued items are voided by `applyPairEvent` for hygiene. Reverse blocks compose (per-creator rows); `unblock` updates only the actor's own row and appends `unblock` (fresh generation, 180-day suppression); `report_hold`/`safety` rows are staff-only by rule. `reportAndBlock` adds the report and ≤ 20 evidence references the reporter may write but never read; `messages.read`'s staff clause over `reportEvidence.byObject` is the segregated safety exception (I13). Nothing here writes a hidden row.

**§5.11 Sync** is the runtime: reconnect re-authorizes before outbox replay and evicts rows held by no range (§6) — the design's purge-before-additions ordering. Missing: the lease (L2) and a purge-before-render obligation.

**§5.12 Verification.** `startVerification` inserts an attempt bound to the current `photoSetHash` with a ten-minute `expiresAt`; the provider call is an `effect`; `recordVerificationResult` (system) dedups on `providerRef`, `require`s `pending` and `photoSetHash === current.photoSetHash`, sets `badgeHash`. A late callback for set 7 after set 8 fails the equality.

**§5.14 Expiry and bulk safety.** Every expiry is a `schedule` on its row's own timestamp. `suspendAccount` is one `accounts.update`; `okAcct` is in every rule, so everything concerning the user is unreadable in that commit — the immediate global deny is free. `closeAffectedPairs` scans `byLowOpen`/`byHighOpen` `take 500`, closes, and reschedules itself while `hasMore` (L8). The repair job has nothing to find: `matches.insert` requires both live likes and `immutable` fixes them.

### 6. Language delta

Prediction 2 held in outline and missed the two findings that matter. Held: the match is a rule over one visible and one hidden row whose existence is the disclosure; "who liked you" is a declared entitlement disclosure; block is retention with purge-on-block on both devices; proximity is a prefix scan, not a second read-site class. Refuted: a *card* must be independent of the other side's swipe (contract 6, I16), so the hidden input on every card is the pair, not the swipe; recommendations are a `schedule`, not an effect, unless the model is served. Missed: the `hasMore` oracle and the lease bound.

1. **L1 — the cardinality oracle.** *What:* ruling 2 makes `hasMore` and page length functions of hidden rows; a free member's `whoLikedYou`, certified clean, discloses the paid count's magnitude and its changes (trap 3's observation). *Smallest:* `hasMore` is an extent and ships only under ruling 3's condition; a program reading `hasMore` or `length` from a scan whose rule is not uniform for the running principal is refused `E_CARDINALITY_ORACLE` (*rewrite: gate on the hoistable clause; paginate by key until empty*); receipts carry no per-hidden-row artifact. *General* (health's SSN oracle; here a money secret). Amends §9.1(2–3), §4.2, §9.
2. **L2 — retention with a lease bound.** *What:* block must purge delivered rows on the other device within ten minutes while `maxOfflineAge` is 24 h and queued gestures live 24 h. *Smallest:* per-table `retain({ onDeny: 'purge' | 'keep', offlineLease: '10m' })`, lease ≤ store age; outbox age as a separate `maxIntentAge`; purge-before-render on the client. *General* (wave-1 F, sharpened as predicted). Amends §6, §10 D-D.
3. **L3 — notification outbox with recipient-scoped revalidation.** `notify(matches.insert, { to, revalidate: rule })`, the rule evaluated *as the recipient* at dispatch, so a block between commit and push withdraws it. *General* (wave-1 D). Amends §1, §7.
4. **L4 — asset grants bound to a rule.** `db.media.grant(assetId, { while: cardVisible(owner), ttlMs })`: an expiring viewer capability whose validity is the row's verdict. *General*. Amends §4.2.
5. **L5 — dependency assertions.** `independentOf: [directedIntents.byTargetDecisionAt]` on a program; `check` proves no read site touches that index or prefix. *General*. Amends §5.
6. **L6 — system-only callables and effect provenance** (`callable: 'system'`, `principal.via`). Wave-1 item 4. Amends §7.
7. **L7 — minimum cardinality at a transition** (`cap({ by, min, when })`) so "exactly three prompts" binds every writer. *Minor*. Amends §2.
8. **L8 — schedules at population scale:** `schedule` as a durable timer index (3×10⁸ pending) and a self-rescheduling chunk (wave-2 `job`). Amends §7.
9. **L9 — clarifications:** (a) reads in a transaction see the program's own writes and rules re-evaluate against them — the mutual match depends on it; (b) rules may `get` maintained rows; (c) `maintain … where` cannot probe other tables; (d) `?.` on probes. Amends §3, §4.2.

Not needed: hidden probes (wave-2 L), `tree`, `tokens`, `readTime`, column-level visibility, a second query class.

### 8. Where the design is wrong

1. **Contract 7 and op 14 contradict.** The paid count must "rejoin liker safety state" per like, yet suspension cleanup is eventual per-pair batches. With tens of thousands of likes on one profile no read can rejoin per row; the only exact number is over a state suspension flips later. *Observation:* suspend a liker holding 30,000 active likes; read a popular paid target's count in the next second — it includes the suspended liker, in the design's own backend as much as here.
2. **A pass is not declared secret, and the design leaks it.** Op 4 "terminates current intents" — it writes the liker's row, which the liker holds and watches. *Observation:* A likes B; B passes; A's sent-likes subscription receives a diff. The v0 form is the fix: a pass appends the passer's own event and advances a hidden count; the liker's row is never touched, and status lives in a table the liker cannot read.
3. **Op 13's "exclude … intents" is ambiguous, and one reading leaks.** Excluding the *user's own* intents is right; excluding candidates who hold an active like *toward* the user leaves stable holes (trap 3) and violates I16. *Observation:* controlled X likes free Y and retracts repeatedly; if X's presence in Y's queue tracks it, the secret is out. The certificate's read-site prefix (`[pair, batchUser]`) catches it; the design's prose does not.
