### Transactions, locks, clock

**Deferred snapshot + cleanup (SQLite-specific, not kernel policy).** `authority_transaction` is `unchecked_transaction` (deferred) plus the existing activation identity check (`store.rs:204-211`). `activation::identity` only SELECTs `_meta` (`store/activation.rs:13-16`) — no write, so this tx does not upgrade to a writer lock. `resolve` walks, **rollbacks**, then `DELETE FROM _sessions WHERE token_digest = ?1 AND expires_at <= ?2` on autocommit (`identity.rs:136-142`, `store/authority.rs:106-116`). That is the parent cleanup predicate; moving it outside the read tx is the lock-upgrade fix, not a change in which expired sessions are pruned. Action tokens that are unexpired but whose claim is dead still do **not** get deleted (parent was already that way).

Writer paths (`claim`, `settle`, `logout`, `bound_custom_session`, steps, jobs, route admit) still start with `store.transaction()` Immediate and reuse that `Tx`. Kernel invalidations are ordinary DELETEs on a lock already held. No new read-then-write upgrade.

**Labeled tightening, not a session-policy regression.** Parent `resolve` / `action_request_at` / `replay_action` / `route_service_generation` used autocommit `store.conn()` with **per-statement** snapshots and **no** identity fence. The new helper both (1) makes the documented one-transaction walk real and (2) applies the existing store-identity fence used by `transaction` / `read_transaction`. After successor activation, those reads now fail closed with `Generation` instead of walking a new database under a stale engine catalog. That is store-adoption fencing, not a change to session/claim rules.

**B1b clock (out of scope).** `logout_session` and `bound_custom_session` still take `now` from the caller and only then `store.transaction()?` (`identity.rs:154-156`, `539-559`). The kernel never calls `now_ms()`; every decision and `latest_live_family_member` already take `now: i64`. A later repair can sample once after the Immediate lock and pass that value through — no kernel change required. Do not treat the current pre-lock sample as an extraction defect.

### Adapter detail (not a production fail-open)

Parent family/claim lookups filtered live claim rows **in SQL**. The adapter loads `WHERE session_digest = ?1` with no state/lease filter (`store/authority.rs:77-88`); the kernel then applies `principal` + `claim_window_is_live`. For a unique digest this is the same fail-closed outcome. `_requests_session` is a non-unique index (`actions.rs:22`); `_sessions.token_digest` is unique. Duplicate `_requests.session_digest` values would make `query_row` error rather than pick the live row. Claim tokens are random and finish/requeue do not reuse them; this is a latent uniqueness assumption for a future adapter (UNIQUE / `LIMIT 1` + live filter), not a source-confirmed bug in this SQLite data model.

`actions::authority_expiry` now re-reads `work_by_id` instead of using the in-memory `ActionRequest` (`actions.rs:89-91`). Same Immediate/deferred snapshot as `request()`, same columns as `run.authority` / `run.service_generation`.
