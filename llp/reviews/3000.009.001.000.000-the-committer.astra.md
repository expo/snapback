## Verdict: SOUND WITH MAJOR ISSUES

The single-stream architecture is sound, and I would keep the direction. However, the specified read sets can miss a dependency, the overlay omits consequential durable state, and the clock and replay contracts need completion before implementation. Reviewed read-only at `21d2e6ec85`; no files were changed or tests/databases run. Runtime reproductions and proposed-committer throughput are **UNVERIFIED**.

## Fundamental and major findings

### F1. Index membership does not capture changes to the returned row — FUNDAMENTAL — Read sets and validation §§3–4

The read-set table records `lookup` as only `Key(table,index,key)`, conflicting with additions or removals of that index key. But `lookup` returns a row image, and changing that image need not change any index key. Both adapters deliberately leave unchanged index entries untouched. See [the RFC, lines 60–75](../../llp/3000.009.001.000.000.001-read-sets-and-validation.rfc.md:60), [SQLite lookup](../../snapback4/crates/snapback4-core/src/store.rs:610), and [SQLite update, lines 674–687](../../snapback4/crates/snapback4-core/src/store.rs:674).

A counterexample:

1. A looks up an account by its unique email, reads an unindexed `enabled=true`, and prepares an unrelated write.
2. B changes `enabled=false` and commits, leaving the account’s index keys unchanged.
3. B’s footprint contains `Row(account,id)`; A recorded only `Key(account,byEmail,email)`. The specified intersection accepts A.
4. Executing A after B would observe `false`, so the accepted history is not equivalent to revision order.

There is also a key-space mismatch: lookup searches the entire encoded prefix, while stored index keys append the row ID. An absent lookup cannot be protected by exact equality with a subsequently inserted full key. See [lookup’s prefix interval](../../snapback4/crates/snapback4-core/src/store.rs:614) and [stored key construction](../../snapback4/crates/snapback4-core/src/rows.rs:145).

**Recommended direction:** explicitly separate index-membership dependencies from row-content dependencies. A lookup needs its logical-key interval plus a `Row` dependency for the returned image. Scans likewise need dependencies for consumed row images, including hidden or filtered rows. Counting one recorder entry per adapter call cannot establish this semantic completeness.

### F2. The overlay loses durable effects of ordinary row transitions — MAJOR — Write overlay §§3–4, §6

The specified overlay keeps the latest row image and selected bookkeeping deltas. Ordinary `put` and `delete`, however, also participate in retained schema-evolution state:

- `put_indexed` checks dormant ID reservations and updates backfill provenance before writing the row.
- `delete` clears retained values and backfill state, invalidates dormant references, and can release retained assets.

These are existing mutation semantics, even when no administrative operation is running. See [store write preparation](../../snapback4/crates/snapback4-core/src/store.rs:664), [dormant reservation refusal](../../snapback4/crates/snapback4-core/src/store/narrowed.rs:224), [backfill write tracking](../../snapback4/crates/snapback4-core/src/store/backfills.rs:545), and [durable deletion effects](../../snapback4/crates/snapback4-core/src/store/dormant.rs:759).

For example, deleting a row and reinserting the same visible image ends with unchanged managed data, but must retire its previous retained lifetime. A latest-image write set cannot preserve that distinction without recording the additional transition effects. Preserving stale dormant state can change what a later activation restores.

The proposed differential’s enumerated final-state comparison omits dormant/backfill state, so it can miss precisely this divergence. See [overlay state](../../llp/3000.009.001.000.000.000-the-write-overlay.rfc.md:46) and [comparison scope](../../llp/3000.009.001.000.000.000-the-write-overlay.rfc.md:115).

**Recommended direction:** make shared write preparation cover every durable consequence of a row transition before qualifying the overlay. Preserve history-sensitive effects even when row/index changes cancel. Compare the complete logical durable state and include evolved-store fixtures followed by reactivation; otherwise keep those writes in place.

### F3. Rerunning cannot repair a permanently fixed stale clock — MAJOR — Committer §§4.2–4.3, §6

The RFC fixes `now` at admission, says it is never read from the store, and reruns a member when its time is below the committed pin. It does not define a transition that changes the stale time. See [execution inputs](../../llp/3000.009.001.000.000-the-committer.rfc.md:249) and [time rules](../../llp/3000.009.001.000.000-the-committer.rfc.md:307).

Suppose slow A executes at time 10 and faster B commits at time 11. Re-executing A at a newer snapshot with its fixed time 10 cannot make it eligible. Sampling a fresh host time alone also fails after a clock rewind below the durable floor. Today’s reference explicitly reads that floor and returns `max(requested, floor)` before running the program. See [writer pinning](../../snapback4/crates/snapback4-core/src/engine/mod.rs:946) and [the clock implementation](../../snapback4/crates/snapback4-core/src/store/time_audience.rs:27).

**Recommended direction:** distinguish request time from the effective time of an execution attempt. Define how retries obtain an effective time at least equal to the durable floor, validate against preceding accepted members’ times, and make time conflicts reach the bounded in-place fallback. Record the final effective time for replay. Applying a batch maximum can remain a storage optimization; it does not itself establish monotonic member execution.

### F4. The universal replay oracle lacks inputs needed to reproduce existing members — MAJOR — Committer §§3.5, §8; Read sets §2

Operation, arguments, principal, `now`, and sequence-placeholder resolutions do not determine today’s execution. Yet those are the inputs supporting the proposed byte-for-byte replay guarantee. See [the oracle contract](../../llp/3000.009.001.000.000-the-committer.rfc.md:212).

Concrete dependencies outside the recorded store-read boundary include:

- **Generated IDs:** `Context::mint` consumes supplied IDs or the shared mint stream, whose fresh entropy comes from `getrandom`; failed attempts also advance that stream. [Context minting](../../snapback4/crates/snapback4-core/src/engine/mod.rs:262), [mint implementation](../../snapback4/crates/snapback4-core/src/ids.rs:8).
- **Presence-dependent effects:** the evaluator samples the live presence registry directly. [Runner](../../snapback4/crates/snapback4-core/src/engine/runner.rs:1304).
- **Chunk boundaries:** job and timeline chunks stop according to elapsed wall time. Replaying the same operation and application clock can process a different number of rows and produce different cursors, meters and commits. [Job chunk](../../snapback4/crates/snapback4-core/src/engine/job.rs:142), [timeline walk](../../snapback4/crates/snapback4-core/src/engine/timeline/work.rs:48).

**Recommended direction:** define a replayable member and its complete external-input transcript before relying on this oracle. Capture consumed IDs, presence observations and scheduling/yield decisions, or inject deterministic equivalents during qualification. Continue rereading database facts during replay—recording and replaying those answers would conceal validation defects. If the oracle initially covers only a deterministic subset, state that limitation explicitly instead of claiming every member.

## What the documents get right that should not change

- One fenced stream for publishing and non-publishing writes, with internal revisions distinct from public sequences. This closes the authority-change ordering hole.
- Reading the snapshot revision inside the snapshot and validating against earlier members of the current batch.
- Keeping the reference executor, bounded fallback, and family-by-family overlay qualification.
- Treating hidden reads as dependencies and prefetch as physical speculation.
- Gating the expensive overlay work on execution-stage and full-write-set sizing, rather than treating the commit-only prototype as achieved throughput.

## Small notes

1. **Bounded counts cannot use the stated arithmetic directly.** `count_prefix` returns a count capped at `limit`. With two snapshot rows, limit 1, and one overlay deletion, “snapshot count − removed” gives zero although one row remains. This feeds live aggregate existence checks. See [bounded count](../../snapback4/crates/snapback4-core/src/store.rs:641) and [aggregate caller](../../snapback4/crates/snapback4-core/src/engine/maintains.rs:549).

2. **The adapter already charges the public meter.** Overlay §2’s prohibition on charging overlooks `scan_metered`: shared helpers charge row bytes, keys and vector growth before decoding. The merged view must preserve those charges and their ordering, including overlay-only entries. See [shared scan charging](../../snapback4/crates/snapback4-core/src/engine/word_heap.rs:276).

3. **Following has an engine-created global conflict.** Each enqueue reads the pending queue’s greatest position and writes its successor, even for unrelated actors. Correct validation therefore serializes otherwise independent posts for that timeline. Include this workload before extending disjoint-counter results to Following; quantitative impact is **UNVERIFIED**. See [enqueue](../../snapback4/crates/snapback4-core/src/engine/timeline.rs:185) and [queue-tail allocation](../../snapback4/crates/snapback4-core/src/engine/timeline/work.rs:25).
