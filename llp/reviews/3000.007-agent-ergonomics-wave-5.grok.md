## Findings

### 1. Medium — `insert if absent` with a caller-supplied (non-literal) id can still be headed `eligible` while the device queues

`snapback4/crates/snapback4-lang/src/bind/residency/inserts.rs` 52–58 only treats `id` as supplied when it is a **literal or `viewer`**. A parameter (`id: likeId`) is a variable, so the compile-time byId proof is skipped whenever another unique index exists.

Runtime (`write.rs` 56–60) treats any id **not** in `minted_ids` as `byId` and then `prove_upsert_insert`. On a viewer-keyed table, `byId` does not decide readability, so the device queues with 0 rows.

**Failing scenario.** `mutation like(postId: posts, likeId: id): insert likes { id: likeId, postId, principal: viewer } if absent` with `unique byPostPrincipal: postId, principal` and `read <- .principal = viewer`. `check` prints `predicts: eligible` (no insert-arm summary). Offline admit predicts 0 rows. Same shape W5b fixed for `id: 'chosen'`.

**Smallest fix.** In `failure()`, treat any non-`NewId` id image as supplied (variables, inputs other than `NewId`), matching runtime’s minted-id bypass.

### 2. Medium — `WriteHistory` grows without bound

`snapback4/packages/snapback4/src/writes.ts` 18–24: `values` Map never deletes. Local persistence (`local.ts` 208–213) writes `client:write:<id>` and never removes it after settlement. Every mutation leaves a durable meta row for the life of the device store.

**Failing scenario.** A Clique-scale device that sends tens of thousands of messages accumulates one JSON blob per mutation id in SQLite/IDB, including after receipts are no longer observed.

**Smallest fix.** Cap the in-memory map (same 256 pattern as `useTrackedMutation`’s `early` map) and delete `client:write:<id>` once the outbox entry is gone, or keep only the last N terminal ids.

### 3. Medium — `init --recipe feeds` does not refuse table-name clashes

`snapback4/crates/snapback4/src/verbs/init.rs` 52–63 only conflicts on `snapback/feed.q` and `src/following.ts`. The recipe declares `posts`, `follows`, `feed`, `broadcast`, … (`feeds.md` 33–116). Default/Expo starters do not use those names (`apps/chat/snapback/schema.q` has `profiles`/`conversations`/`memberships`/`messages`), so the packaged tests stay green.

**Failing scenario.** An app that already has `table posts` (or `follows`, `feed`, …) gets `feed.q` written, then `check` fails with a duplicate-table diagnostic. The write is not rolled back (atomicity is file-level only).

**Smallest fix.** Before writing, compile existing `snapback/*.q` plus the recipe and refuse with the colliding names if `check` would fail; leave destinations untouched.

### 4. Low — unparenthesized inner `by` after `where` now binds to the outer page

`parser/expr.rs` 264–285 puts `by`/`after`/`first`/`last`/`matching` in the `where` expression’s stop set. Previously those tokens were consumed by a nested read. Parentheses restore the old inner index (`spelling.rs` 86–92).

**Failing scenario.** A program that compiled as  
`posts['bob'] first 10 where exists follows[viewer, .author] by byPair`  
now either errors (repeated `by` if the outer page already has one) or, if the outer table also has `byPair` and had no `by`, silently pages posts by that index.

**Smallest fix.** Already the documented rule. Optional: if an inner indexed read is immediately followed by `by <name>` that matches only the inner table, refuse with “parenthesize the inner read” instead of rebinding.

### 5. Low — opener “close and throw” does not match ordinary transient failures

`chat-expo/src/client.ts` 32–35. `client.sync()` → `syncOnce()` (`local.ts` 514–523, 557–559) converts fetch failures to `link="offline"` and resolves `false`. The catch/close path only runs if `sync()` **rejects**.

**Failing scenario.** A 500/`TypeError` while `link` is still `"online"` after `createLocalClient`’s own `syncOnce` (1201–1205) does **not** prevent opening; the extra `await sync()` returns and the app proceeds, possibly unacquired. That is the better offline-first outcome. The advertised throw is for unexpected exceptions (e.g. `set_meta` denial inside `history.keep`), not a flaky network.

**Smallest fix.** Document that the opener waits for a successful or *failed* sync round, and only closes on thrown errors; or make `sync()` reject on a still-online unsuccessful round if blocking open is really required.

### 6. Low — missing acquisition tests for §18.2 replacement and restore halt

Device `w5c_sync_state_reports_durable_acquisition_after_snapshot_and_catchup` (`device.rs` 1461–1482) covers snapshot/catch-up/reopen/`clear_rows`. Client tests cover busy-online, empty partition, horizon invalidation. I did not find a client test that a **store_id replacement** or **`E_STORE_RESTORE` halt** keeps `client.acquired === false` until the new catch-up (or forever, for halt).

The code looks right (`store_identity.rs` 73–84; `local.ts` 339–344, 573–618). Still a gap against the brief’s checklist.

**Smallest fix.** Extend `acquisition.test.mjs` with a replaced `store_id` page and a restore-halt probe.
