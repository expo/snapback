### 1. Coverage table

Certificate shorthand: `exam≤N` includes halo (`take+2`). Prefixes: `a` arg, `v` viewer, `s` shape, `c` computed, `r` `ctx.replica` **[v1.1]**. `G` is unpublished. Shadow certificates are what a *single-engine* rewrite would emit; they are not admissions of the product.

**Premise (wave-4 #3, pre-registered):** one server authority; one acceptance order; `serialBy`. Prediction: *home authority per key, away-region escrow quotas; `serialBy`/`commitTime` per home; OCC at the home.* Tested, not confirmed: the *allocation* pattern matches; the *lowering* (`serialBy` on one engine) does not (see §6.1, §8).

**Totals (58 named; 4 seeds; 0 channels).** As specified: **plan 18** (single-home reads/writes, seeds, policy edits, O(1) book seal, payment-mark mutations, expire/selfFence *if* this engine is the home of that key) · **refused→rewrite 6** (list page, snapshot page, fork side table, O2 chunk, O14/demand window, book incremental) · **effect 3** · **schedule 3** (the ones that survive as local status flips) · **job [v1.1] 4** (O2, heal, demotion, rebalance) still not closing the premise · **product-change 1** (device queue already declared client-only) · **premise-violation 23** · **channel 0**.

Shadow (one engine, “region” a column, partitions impossible): most premise-violations collapse to plan/job and **promises 1, 4, 8, 9, 15 across a cut become false.** That collapse is the cheat boundary, not a plan.

No second query class appears. What appears is a **second evaluation site** (another engine applying a log) and a **second completeness axis** (frontier). Those are not queries.

### 2. Schema in v0

Sentinels: no `optional(t)` → `''` / `0` absent. No array columns → child tables. No `money` → `int()` minor units + `text({ max: 8 })` currency. No enum → `text({ max: 24 })`. `json` is opaque to rules and indexes — flattened wherever a program or rule must read it. `ctx.replica` / `serialBy` / `job` / `phase:'system'` / `callable:'system'` / `int({ sequence: by })` / increment constraints / `digest` / `insertIfAbsent` / `maintain.rank` / `maintain.rows` / effect outbox are **[v1.1]**, used as if in the spec and called out. They do **not** add a second live engine.

  table, id, text, int, bool, time, ref, json, unique, cap, appendOnly,
  maintain, viewer, public, never, immutable, immutableExcept,

// [v1.1] also: serialBy, digest, insertIfAbsent, principal, ctx.replica

const isOp = (regionId: string) => db.exists(operators.byRegionUser, [regionId, viewer])
const isAud = () => db.exists(auditors.byUser, [viewer])
const isSup = (supplierId: string) => {
  const s = db.get(suppliers, supplierId)
  return s !== null && s.userId === viewer
}

#### O3 Cancel

At origin (shadow plan): read hold, `require` owner, append `originLog(cancel)`, set `cancelled`, if `acceptedPoolId` is this region’s escrow then `release` in the same tx (`serialBy` that pool). Certificate exam≤6 writes≤5; prediction **closed** on Cancelled.

Away (`cancelIntent`): insert an `originLog` row *at S* addressed to R. **Two writers of two logs.** v0 has one insert path. **Premise-violation (one acceptance order / one server).** Product already tells the truth (“applied when R is reachable”) — that string is the honest UI, and it is **not** promise 9 as written (“always succeeds immediately … Cancelled at R is durable at the owner”). Promise 9 at S≠R during partition *is* the intent record, not Cancelled. Classifying cancel-at-S as a plan that returns Cancelled is the U2 cheat.

Release-on-apply at every pool that holds an assignment is an **apply program**, not O3.

#### O9 Heal

**First attempt:** `scan(foreignLog, { take: 9_000_000 })` — `E_BOUND`. Rewrite: **[v1.1] job** with `commitSeq` watermark, 10k-record batches, one O2 per batch. The *body* of each record is “the same handler as local” — there is no such kind. Simulating it as `db.run(applyOriginCreate, rec)` **[v1.1]** sums certificates × 10k and still assumes the records are *already in this SQLite*. **Premise: one store.** Broken look: a mesh. Outcome: **new kind `apply`** (deterministic program over a foreign append-only row, watermarked, term-checked, fork-aware). Jobs cover the bound; they do not cover the site.

#### O10 Lease, fence, transfer, demotion

`selfFence` as a schedule flipping a bool when `commitTime > expiresAt` is a K5 plan **on that region’s engine**. Renewal “ask every peer, ≥4 attestations” is not `exists` over a table the requester wrote; it is a **quorum of other engines**. Putting attestations in a table and counting them is a K2-looking count **and** a TOCTOU: a peer’s row does not mean the peer is reachable *at commit*. Wave-4 zero-trust prediction (mirrored row + freshness) is the closest v1.1 form, and it is explicitly a **product boundary** (TOCTOU labelled). Forced transfer needing 4/6 is the same. **Outcome: product boundary (host quorum), not a rule class.** Demotion review is O2 with a filtered candidate set — job, authority engine only.

#### O11 Book close

**First attempt:** `scan(bookEntries.byRegionDay, [R, D], { take: 5_000_000 }); hash; sum` — `E_UNBOUND_COUNT` / `E_BOUND`. Rewrite: running totals and `runningHash` updated on every `bookEntries` insert (the insert program is the constraint). Close is a point read + insert `bookDayCloses` + bump `openDay`. Certificate exam≤2. **I15 on apply:** a replicated `captured` arriving after close must not append with `bookDay = D`. That is a `require` in the *apply* program, not in the client mutation. If apply is outside the language, K6 is false and U5 stands. **v0 `appendOnly` does not take a predicate on `bookDay`.** Smallest addition: **[v1.1]** event-coupled / conditional insert, *binding apply*.

#### O13 Expiry

Schedule per hold at `expiresAt`, origin engine, flip `open → expired`. Plan (K5). Must not expire because an authority is unreachable — a first-attempt `if (!frontier of authority) expire` is the T6 product bug, and v0 correctly refuses clocks in rules. **The language prevents the wrong expiry; the runtime still has to run the schedule at the origin engine.**

#### O14 Rebalancer + partition reserve

**First attempt:** `holds_r(6h)` = scan origin logs where `createdAt > now-6h` — `E_AMBIENT_TIME` / v0.1 r11 (time-windowed maintain inexpressible). Rewrite: schedule flips samples into `demandSamples` every 15 min (status, not a window), then a job reads those rows and issues O7. Arithmetic is admitted. **Partition reserve** (“frontier stale > 30 s”) needs `replicationFrontiers.stale` as a scheduled flag (K5), then O7 into in-transit. The in-transit “destination cannot see until heal” is apply order, not a rule. Forecast as a number written by a job is a plan; the transfers are O7 premise-violations.

#### Payment effects

`authorizePayment` / `capturePayment` / `refundPayment`: effects, outbox **[v1.1]**, idempotency key `holdId`. Deferred auth on unreachable processor is an effect failure then `authState=deferred` — plan. Not a premise break.

#### Seeds

`seedRegion` ×6, `seedSku`, `seedCustomer`, `seedOperator`: system mutations, plans. Design did not name them.

### 8. Where the design is wrong

Not taste — exposed by writing the programs.

**1. 3+3 (or any majority-unobtainable) partition: zero global authorities.** Renewal and forced transfer both need ≥4 of 6 attestations. After 10 s both halves self-fence (O10.2); neither half can take the pool (O10.4). Escrow still works; the global pool is *nobody’s*. The design discusses 1-vs-5 fail-over, not a split without a majority. *Confirm:* run a 3+3 cut for 60 s on a global pool with `onHand>0` and no escrow; observe zero `assign` records and no legal forced transfer.

**2. O5’s “snapshot + locally-known newer holds ranked by the O2 key” is not defined.** `rankWithinOrigin` is 1-based position *inside snapshot C*. Newer holds are not in C; rotation uses `eventSeq` of the *next* event, not the snapshot’s. Two same-origin holds arriving after the snapshot can display in an order O2 will invert, or get a position that *improves* without a resync (promise 7). *Confirm:* after a snapshot, inject two `create`s from `eu` with consecutive `originSeq` and a `jp` hold that interleaves under rotation; compare O5 labels to the next O2 assignment order.

**3. `skippedCap` eligibility is unspecified, and I6 is therefore not a function.** I19 says skip, never delete. If skipped rows stay `eligible=true`, every O2 re-walks them (bound blow-up at 100k, promise 8 “progress is visible”). If they become ineligible, a later release that drops the customer under cap will not re-arm them unless a third state exists. Status `Held` is then not a pure function of request+assignment: it depends on a cap-skip bit O5 does not read. *Confirm:* a customer at cap in two regions after heal; one Confirmed; the other remains Held with no assignment and is either re-skipped forever or silently stranded off the queue.

**Verdict for the founder.** Ideal design for *a system like Snapback*: declare **authority placement** (home per key, engine per region), an **`apply` path that is still the language** (so K6 is not a lie), and **`atLeast(frontier)` completeness** (so K2 is not a lie). Do not pretend `merge`/`replica()`/`serialBy`-on-one-SQLite are that design. Majority lease stays a host boundary. With those, O1–O8, O11–O13 are programs; O2/O9/O14 are jobs; O5/O6 are plans whose certificate is allowed to say “lower bound.” Without them this is **not this system** for the product as specified — and a one-engine rewrite that keeps the promises is a cheat, not a plan.
