## 2. The lifetime rule

On a server commit it holds for every path that recomputes the stored instant.

- **Delete.** A live child blocks the delete, including one inserted earlier in the same transaction, including a job or seed delete. Read authority is checked first, with or without children. Deleting the child first, then the parent, succeeds.
- **Expiry.** `min(authored, captured parent deadline)` is transitive. A middle table with no `expire at` still stores the grandparent's deadline. After that instant, `lookup_live` misses the row and the sweep can see it.
- **Reuse and replacement.** Same-id replacement of an expired parent (`write.rs` deletes the expired predecessor, then inserts) is refused while any physical child remains. The sweep may not remove the parent first.
- **Same mutation.** Insert parent, insert child, delete parent: the probe sees the child. Delete parent, then insert child: the parent is not live. An upsert update keeps the captured deadline and recomputes the effective instant.
- **Seeds, imports, activation, three levels.** Ancestor-first capture, refusal of a parent image whose captured fields differ, expiry judged under the previous schema before recapture, and the child copies the parent's stored captures rather than walking to a live grandparent.
- **Devices, finite deadlines.** Server time 110 applied to a device at 90 expires a child whose effective deadline is 100. A deadline of never is not expired by that clock. A reused id whose old children are still current and live does not get one verdict.

It does not hold for a restored image.

**High — §3.2 and §7.1.** Comment `C` captures parent deadline Monday and has authored `until` next year. The image's stored effective instant is missing or next year. The parent is live and the captures match, so §7.1 accepts the restore. `LoadMode::Restore` keeps stored images verbatim (`engine/mod.rs`, `load_trusted`). §3.2 recomputes on insert, update, upsert, import, and activation, and §7.1 says a restore never recaptures, so the implementer will not recompute. After Monday the parent is expired and `C` is still live. The parent cannot be deleted or swept.

Smallest change: restore is one of the writes that recomputes the stored instant as `min(authored, captured parent deadline)`. Do not trust an instant in the image. The same sentence should say the instant is an engine column, so an activation projection cannot drop it.

## 4. Under-specified

**Medium — §4.5 and §10.** `view unread: count receipts by .message.chat` has no explicit `read`. The paved rule is that a reference path does not preserve a source rule field, so derivation fails with `E_MAINTAIN_READ_RULE` and the rewrite is an explicit aggregate read (`bind/maintains.rs`, `guide/maintains.md`). §4.5 says the path takes the capture's rule-field identity. It does not say that this identity satisfies that check, what the view column is named, or which rule is installed (`exists members[.chat, viewer]` copied onto a column named `message.chat` denies everyone). §10 still calls the path a recorded path. The safe failure is that the acceptance view does not compile. The escape the recorded-path fixtures teach is `read <- allow`, which publishes every chat's unread count.

Smallest change: a path that matches one inherited capture counts as that rule field and no other. The view column is that field, the derived rule is the parent's rule rewritten onto it, and a rule field the group key does not cover is still `E_MAINTAIN_READ_RULE`. Say it is not a historical recorded path. Sync is inherited only when that field is the audience key.

The explicit adoption mapping still has no syntax. A missing mapping refuses, so that fail-closed outcome is safe.

## What is sound

`read through .ref` as the whole read rule, over one required immutable id with no default, is the right cut. Ordinary application tables only, service grants only on the parent, and copying the immediate parent's stored inputs are the right restrictions. The captured parent deadline as its own immutable field, with the effective instant recomputed on update and capped by it, closes the revision-5 lifetime hole on the write path. One expiring classification, read by every gate including `trust_synced_read`, page admission, and the hidden-maintain reservation, is the right formulation, including through a middle table. The quantifier over live current children, and not over retained rows, is the right device rule when the parent is locally readable. Exact admission, the insert order, the four-outcome resolver, and keyed views remain sound. On the server, at a commit boundary, a child lives inside its parent through three levels, and a reused id does not meet an old child.

**Overall verdict: NOT READY.**
