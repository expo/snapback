The source-write reservation should cover all seven meter dimensions, including demonstrating that rule probes and output bytes gain no hidden-parent-dependent work. Insert needs reservation scope before its `if absent` early return; upsert, replacement, native calls and system calls must share it. The existing `target_attempt` restores prepaid state and refunds reserved heap (`C/engine/write_target.rs:12–20`), so this needs an explicit per-attempt lifetime, including consecutive writes in one mutation. A fixed reservation can cover different actual index costs; limbo’s “one write” is not itself the proof.

The dependency walk is otherwise a good repair. A ranking index such as `likeCount, at, id` remains usable for normal paging: `ReadMode::Range` is distinct from rule-probe resolution. Validation must inspect resolved index definitions, including raw-schema unique indexes, rather than only authored field references. The binder already calls core validation, providing a practical place to share the check.

**1. High — Generation discovery still depends on delivering row data**

**Design:** §3.11; §10’s activation disposition.  
**Evidence:** [partition.rs:567](snapback4/crates/snapback4-core/src/partition.rs:567), `C/partition.rs:587–618`; [serve.rs:641](snapback4/crates/snapback4/src/serve.rs:641); `P/local.ts:574–650,743–751`.

**Failing scenario:** A device is behind an ordinary pre-activation commit or join expansion whose response previously fitted the HTTP ceiling. Adding the maintained column enlarges the current parent images substituted into that old page. The response now exceeds 16 MiB.

The stream preserves whole commits, including at `limit = 1`. HTTP serialization replaces the response with `E_BOUND`, dropping its generation. The client shrinks the page before reaching generation adoption and eventually stops at one. `/changes` can report the new generation, but its handler merely triggers synchronization; it does not adopt it. Removing activation’s own row events therefore eliminates one oversized-commit case, not this remaining deadlock.

**Smallest design fix:** Require generation discovery and adoption to precede row-page delivery independently of whether that page fits. For example, provide a bounded generation-mismatch response before materializing a page, and handle it before page errors. Cover clients entering through `/sync` directly as well as `/changes`.

After that repair, the barrier is appropriate. Successful stream and snapshot replies carry generation; the client adopts before applying their rows, and `Device::apply` rejects mismatched generations (`D/device.rs:485–486`). Snapshot cursors themselves contain no generation (`C/partition.rs:253–262`), so “a crossing snapshot is already refused” should describe the client/page check accurately.

Server-run watches can rerun through the touched-table notification. The activation must record that notification even when all totals are zero or a column is removed: today’s rebuild commit is conditional on `written > 0` (`C/engine/mod.rs:447–449`).

I found no need for rebuild row events in `acknowledged`: it uses operation sequences and the watermark (`C/engine/mod.rs:738–749`). Generation reset also handles held images, including retained images; it does not promise to preserve all previously delivered history. The online client observes generation changes. Postgres has no activation API, as the design correctly states. Existing table-maintain rebuilds do emit events; changing delivery specifically for column activation is justified, provided that distinction is explicit.

**2. High — Split limbo arithmetic can refuse valid sums or poison the expiry sweep**

**Design:** §3.2–§3.3.  
**Evidence:** [maintains.rs:157](snapback4/crates/snapback4-core/src/engine/maintains.rs:157); [engine/mod.rs:629](snapback4/crates/snapback4-core/src/engine/mod.rs:629).

Let `M = 2^53 − 1`.

**Failing scenario:** An expired-unswept parent stores `M`. A new contribution of `1` updates limbo from zero to one. If the reused evaluator checks only that row, the source write succeeds. The sweep subsequently adds `M`, overflows, and rolls back. Since the sweep removes rows in one transaction, the same parent can repeatedly prevent other due rows from being swept.

The converse also matters: an expired parent stores `−M`, and two contributions of `M` arrive. The logical aggregate progresses from `−M` to zero to `M`, all valid. Limbo alone progresses to `2M`, which is not representable under the existing aggregate check.

Thus “overflow is the named exception” is insufficient: the design must define which aggregate is checked. Limbo is sometimes the aggregate and sometimes only its delta.

**Smallest design fix:** State an invariant for the combined stale-parent value and limbo delta. Check the final logical aggregate during source writes, permit a sufficiently wide internal delta, and make sweep transfer incapable of introducing a new overflow. Include both cancellation and endpoint tests, before and after sweeping.

This also closes a sweep-throughput channel caused by repeatable arithmetic failure.

**3. High — Redefinition and parent-lifetime changes do not reconcile expired stored values**

**Design:** §3.3 and §3.11.  
**Evidence:** `C/engine/mod.rs:432–435`; [successor.rs:111](snapback4/crates/snapback4-core/src/successor.rs:111); `C/schema.rs:276–277`.

**Failing scenario:** An expired-unswept parent stores count five. A predicate redefinition makes the correct total two. Rebuilding limbo to two while obeying §3.2’s prohibition on putting the expired parent leaves five in the physical parent. Its later sweep adds five, producing seven. Rewriting the expired parent to two while also rebuilding limbo to two would instead produce four.

There is a related revival path. An expired parent stores five and subsequent contributions have placed two in limbo. Removing or changing its expiry declaration can make the physical parent live again. The existing successor explicitly permits this. The stated rebuild triggers cover the maintain definition and source dependencies, not changes to the parent’s lifetime. The revived row can therefore expose five while two remains stranded in limbo.

**Smallest design fix:** Define exactly which location owns the total after rebuild and after every parent-lifetime transition. Rebuild must neutralize obsolete expired-parent debt or record that it has already been incorporated. Include parent expiry changes and relevant default changes in reconciliation triggers.

A simpler population-independent birth is an internal authoritative total for **every** parent id, including live parents. Birth reads it; death does not move it. That costs additional steady-state storage/work, but removes the stale-value transfer invariant. It is an alternative worth measuring, not a prerequisite to accepting limbo.

Ordinary delete/recreate, same-commit orders and self-reference can work with the current proposal, provided death transfer and the row’s own source contribution have a specified order and remain in the same transaction.

**4. High — `/changes` reveals whether the hidden parent was written**

**Design:** §3.2, §3.8 and §8’s paired observations.  
**Evidence:** [write.rs:497](snapback4/crates/snapback4-core/src/engine/write.rs:497); [serve_changes.rs:78](snapback4/crates/snapback4/src/serve_changes.rs:78).

**Failing scenario:** A principal may insert a source row but cannot read its parent. In one world the parent exists; in another it does not. The mutation body, receipt and logical meters are identical.

In the first world, `row_changed` records the parent table in `written_tables`. In the second, only limbo changes. `/changes` returns committed table names without filtering them through parent read authority. Polling from the preceding sequence distinguishes the worlds.

**Smallest design fix:** Make public invalidation metadata independent of hidden-parent state—for example, conservatively mark every statically possible maintained parent table touched for the source attempt. Never expose internal limbo table names. Add `/changes` to paired observations; identical stream and snapshot results do not test this path.

Limbo also needs structural exclusion from public schema enumeration, generated API, `data`, and SQL views. An internal-looking name alone is insufficient: these surfaces enumerate schema tables. This is enforceable without exposing a new query surface.

**5. High — “Device load ignores supplied values” conflicts with authoritative persistence restoration**

**Design:** §3.7, especially line 225.  
**Evidence:** [memory.rs:88](snapback4/crates/snapback4-device/src/memory.rs:88); `D/web.rs:27–37`; `D/device.rs:264–280`.

**Failing scenario:** A browser persists an acquired parent with server-confirmed count nine, then reopens offline. `MemoryStore::load` is the restoration of persisted rows, base images, staged images and metadata—not a fixture importer. Applying the design’s instruction there discards nine while retaining the same generation and acquired status. The parent now reads zero as an acquired fact. Its source may be online-only, so local recomputation cannot repair it.

**Smallest design fix:** Restrict sanitize-and-rebuild behavior to server fixture import. Device persistence restoration and replication must preserve authoritative maintained values. An untrusted device fixture-import API should refuse such imports or invalidate acquisition; it must not silently turn confirmed values into zero.

“No device writes the column” should mean no device **derives or accepts application assignments to it**. Applying and restoring server images necessarily writes those stored fields.

The first-build source-replay hazards are otherwise retired by skipping column maintenance on both initial prediction and replay. A predicted parent insert still reads zero, including recreation of an id with nonzero limbo. The existing row is marked pending (`D/device.rs:189–195`), so this is an explicit provisional prediction, not evidence of a known zero. The document should say that plainly. If the intended guarantee excludes that provisional value, move the freshly-minted-id restriction from the later increment into the first build.

The later increment’s listed replay, acknowledgement and watch obligations are appropriate; persistence reopen and interrupted catch-up must also be included.

**6. High — Valued inserts can return a missing or fabricated maintained value**

**Design:** §2, §3.3 and §3.11.  
**Evidence:** [bind/program.rs:713](snapback4/crates/snapback4-lang/src/bind/program.rs:713), `L/bind/program.rs:859–876`; `C/engine/runner.rs:286–295`; `C/engine/native.rs:660–699`.

**Failing scenario:** Limbo contains seven. A program binds the result of inserting its parent and returns that result’s maintained column.

The binder currently returns the insert expression prepared **before** the engine write, typed as the table row. `insert if absent` similarly returns the submitted row; native insert/upsert return their input JSON. The engine’s limbo-derived value is absent from those results. Merely injecting the implicit zero into the expression instead returns zero while the stored value is seven.

Blindly changing this to return the enriched stored image creates another problem: insert permission does not necessarily confer read permission. A creator forbidden from reading the parent could obtain the hidden aggregate through the insert result.

**Smallest design fix:** Specify the value contract for these insert forms. Either return a submission projection whose type excludes maintained fields, or obtain a final image through a read-authorized path with corresponding result semantics. Test full-row and scalar results, ordinary and `if absent` insert, native operations, and creators without read permission.

**7. Medium — Constant-time birth and death are not constant-meter birth and death**

**Design:** §3.3 and §8.  
**Evidence:** `C/engine/write.rs:62–72,497–501`; `C/engine/write_target.rs:287–305`.

**Failing scenario:** Two otherwise identical parent creations differ only in whether limbo contains a nonzero value. One deletes a limbo row; the other does not. Death likewise conditionally creates or updates limbo. Charging actual transfer work allows a just-insufficient budget to distinguish them. The parent need not itself be a source, so §3.2’s outgoing-source reservation does not cover these transfers.

The proposed creator test compares no sources with 100,000 **filtered-out** sources. Both produce zero limbo and therefore miss this case.

**Smallest design fix:** Prepay bounded incoming-column birth/death transfer work, including expired replacement, independently of whether limbo exists or is zero. Test zero versus nonzero limbo under creators who cannot read the aggregate, across every meter and budget boundary.

**8. Medium — Event suppression must be scoped to generation-backed activation**

**Design:** §3.2’s `Engine::load` rule and §3.11.  
**Evidence:** [engine/mod.rs:944](snapback4/crates/snapback4-core/src/engine/mod.rs:944).

**Failing scenario:** `Engine::load` loads additional source rows and invokes the prescribed rebuild. If it reuses an event-suppressed rebuild, existing parent values change without parent events or a generation change. Current `load` emits events for the explicitly loaded rows and does not publish a new generation. A device already holding the parent remains stale.

**Smallest design fix:** Give rebuild an explicit delivery mode. Only activation with its atomic generation barrier suppresses events. Fixture loading must emit affected parent events, establish its own barrier, or be explicitly restricted to a store that is not being served.

The in-place rebuild should likewise have a separate column-specific path that cannot invoke the whole-target delete loop. Final row counts and ordinary-field equality are useful tests, but do not prove that no parent delete occurred; instrument the row adapter to assert that property. Removal should atomically project the field out of stored images, remove its indexes as appropriate, and drop limbo so re-adding the declaration cannot recover stale totals.

“Accept and measure” for §3.6 is defensible. Full-parent updates and acquisition of older rows are an explicit first-build tradeoff; a device filter would introduce its own delivery semantics. However, §7 currently specifies measurements more clearly than acceptance criteria. Before briefing, record acceptable device growth, serialized bytes and activation behavior, and define what “material” growth means. Add the counterexamples above to §8, including an oversized **pre-barrier** commit, cold offline restoration, expired-parent redefinition/revival, and nonzero limbo birth.

The remaining findings are not limited to Low issues or implementation-only Medium details. Several require changes to the design’s behavior or observable contracts.

Verdict: NOT READY
