MATERIAL (§4.2, §4.4, §6 table; [app-online.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/app-online.ts:200), [writes.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/writes.ts:99)). Commit throws after capture → live call gets `E_STORE` "retry the same id", and §4.4 says K "is recovered before this runtime's next admission" via `client.mutate(op, args, {id})`. But `E_STORE` is not `E_ADMISSION`, so `MutationIds.run` takes the `finish(id)` branch and retains `seen`. Failing interleaving: capture K, IndexedDB `set` throws, caller retries the same id per the rewrite → `ids.run` takes the recover path ([writes.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/writes.ts:77)), `client.write(id)` finds no pending/receipt/retired ([app-online.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/app-online.ts:253)), returns `E_WRITE_RECEIPT_EXPIRED`. Same-runtime recovery replay through the custody client hits the identical wall. The write is not lost (K survives for a later different-id admission or reload), but the specified retry and replay are false. Resolve: specify that `E_STORE`-unknown deletes the reservation like `E_ADMISSION` ([writes.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/writes.ts:94)), define the replay resubmission path that re-runs `submit`, and test same-id retry after a commit failure.

2. MATERIAL (§4.4 ordering; [app-online.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/app-online.ts:219)). "A new call's dispatch additionally waits for the recovery replays to reach the transport" names no mechanism. Existing `start()` fires concurrent `client.mutate` promises ([app-online.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/app-online.ts:319)), and the `waitSeconds: 0` path dispatches detached. A zero-wait click after `start()` can reach the transport before a recovered replay: no double execution, but the stated recovered-before-new order is violated. Resolve: chain new submits and the detached dispatch behind the recovery promise, or weaken the claim to initiation order.

3. MINOR (§4.1; [writes.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/writes.ts:45)). "Ids the online journal already holds durably are not captured again" cannot be checked synchronously; IndexedDB is async, so only in-memory state (`seen`, restored ids) is testable at capture. Reload plus an explicit reused id re-captures and overwrites K. Harmless (admission's previous/receipt/retired/marker branches dedup), but reword to in-memory suppression plus admission-branch safety, and test cross-tab same-id overwrite (second caller must get `E_WRITE_ID_REUSE`, one server execution).

4. MINOR (§4.2 lock nesting; [app.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/app.ts:610), [app-storage.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/app-storage.ts:34)). Journal-then-session nesting is safe only with raw accessors inside: `onlineCustody` receives raw `storage`, not the per-key locking wrapper, and `storeLock` is non-reentrant (same-name `navigator.locks.request` reentry queues forever). State that all I/O under the nested locks must use the raw store and `authority.read`, never the locking `sessionStore`. I verified no existing session→journal nesting (session replacement, logout, revocation drain, and authority checks take the session lock alone and use direct store ops), so the order itself cannot deadlock.

5. MINOR (§4.5; G6). The runtime lock "held from creation" is granted asynchronously; a capture before grant lets a peer's `query()` miss it and adopt a live tab's K. Converges safely via journal-lock serialization, markers, and server dedup (duplicate dispatch at worst). Require the lock request before first capture and note the race. "Held or pending" is harmless (uncontended runtime names never pend).

6. MINOR (§2 G6; [identity-admission.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/identity-admission.ts:7)). G6's blanket "retrying the same id after repair is allowed" contradicts identity-timeout/store refusals, which finish (not clear) the reservation and whose rewrite demands a new id. Scope same-id retry to synchronous capture refusals.

7. MINOR (§1, §4.4). `start()` "replays in recorded order" overstates the existing concurrent `Promise.all`; strict seq-order recovery must be sequential. Clarify which the RFC requires.

8. MINOR (§5 residual). A server backup that lost receipts re-executes unless the head regresses below the dispatch floor ([client.ts](/home/ccheever/projects/sb4-ws-jr/snapback4/packages/snapback4/src/client.ts:472)); calling it "the existing `E_STORE_RESTORE` case" is glib. Reword as a shared known limitation.
