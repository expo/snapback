## What is sound

**§1, option A and rejecting C.** `infer_audience` accepts only `public`, `.col = viewer`, and `exists`, after `device_audience_rule` strips whole service disjuncts (`bind/schema.rs:357-376`, `schema.rs:691-701`). The guide states the two halves of the invariant (`guide/sync.rs:111-112`) and already says not to make private rows public (`guide/sync.rs:509-515`). The diagnostic does not: `RuleExpr::quarry` prints non-string literals with `canonical_json` (`schema.rs:716`), so `true` becomes `{"Bool":true}`, and the rewrite is only "one invertible read rule, or online only." Finding 8 in `reviews.rs:97-98` is exactly the second-disjunct refusal. `partitions` returns at most one partition (`partition.rs:118-130`). A `del` deletes by `(table, id)` (`deferred.rs:241-245`). A group `scope` leave deletes every row in the group (`device.rs:1279-1296`). Field-owner `del` suppression is special-cased (`partition.rs:958-965`). Union (option C) needs a reference count the device does not have. Waiting for an app that needs both disjuncts offline on one device matches `NOT-DOING.md:30`.

**§2.** The 2026-09-13 decision (`3000-snapback4.explainer.md:587-598`) is what the code does. `wire.rs:65` and `:115` accept any JSON string as an id. `identity_fits` bounds it at 144 canonical bytes (`value.rs:385-397`). Nothing checks 26-character Crockford form (`ids.rs:1-4` is minting only). `fits` treats any `Value::Id` as a reference (`validate.rs:152-153`). The guide is false: `codes.rs:206` and `guide/why/E_INPUT.md:4-5` say the id's shape is checked. Keeping existence explicit is right. An implicit probe would turn a reference into a visibility test and would make a write unpredictable when the target is outside the partition. That is the same cost the decision refused. Option B is unsafe alone, because caller-supplied ids are not canonical either.

**§3, rejecting a wire clause name.** `Refusal` for `Rule` and `AuthorizationBudget` shares one message and fills neither `site` nor `rule` (`error.rs:351-354`). A unique or cap collision with a hidden row is the same envelope. Filling `site` only when the rule evaluated false makes "no site" mean "hidden row or budget," which is still an oracle. The dev collector is real and opt-in (`engine/refusal_trace.rs:1-16`, `45-55`). `3000.015` around line 383 says the clause is developer evidence, separate from `Refusal`. Printing that trace from `run` and the dev console does not change the wire. Absent write rules are `RuleExpr::Deny` (`bind/schema.rs:200`). Jobs run as system and pass every rule (`guide/jobs.rs:90-91`, `read.rs:282-283`). Maintains write through the store, not through `check_rule`.

**§4.** The runtime check is `validate.rs:66-67` and `:199-200` via `contains_system_principal` (`schema.rs:1436-1444`). Neighboring refusals exist (`bind/actions.rs:117`, `parser.rs:1315-1318`, `bind/program/job_reads.rs:19`). `guide/jobs.rs:56-60` matches the prose the RFC quotes, and `72c600c478` is that guide commit (2026-10-08 02:07 -0700). `E_SYSTEM_PRINCIPAL` does not occur in the tree. A literal that can never succeed should be a `check` error. Values that flow through locals stay a runtime backstop. The doubled `E_INPUT:` is real in the ticket's doctor output: `RuntimeError::Input` displays as `E_INPUT: …` (`error.rs:98`) and `refusal()` copies that string into `message` (`error.rs:255`) while `code()` is also `E_INPUT`.

**§6 facts, and option A.** Vendored `tiny_http` keeps one parser thread per connection until the response finishes (`vendor/tiny_http/src/lib.rs:399-415`). The cap is 128 (`limits.rs:100`). Pools are 32 short, 32 mutation, 32 sync, 32 wait, 16 route, 4 registry, 4 verifier (`serve.rs:436-446`). `RequestAdmission` is the only budget (`explainer.md:1763-1769`). `GET /changes` and `POST /effects/claim`, `/actions/claim`, and `/a/*` share the wait class (`serve.rs:535-538`). A wait is capped at 25 seconds (`serve_changes.rs:13`), parks on `polls.wait_timeout` (`:85`), heartbeats every 2 seconds (`:8`, `:77-79`), and enters presence for a full session only (`:35`, `:89`). Grace is 35 seconds (`engine/mod.rs:122`). `publish_durable` calls `notify_all` (`serve_ephemeral.rs:90-92`). Each waiter then runs `check`, which is a read transaction (`serve_changes.rs:113-130`). Overload is `503` with `E_RATE_LIMIT`, `retryable`, `Retry-After: 1`, and `guide: assets` (`limits.rs:43-45`). The descriptor limit is reported at startup (`host_limits.rs`). Thirty-two idle `/changes` clients do fill the wait pool and starve claim polls. Configurable pools, a separate claim pool, a per-principal cap, and `E_STREAMS` are the right immediate change. Option D is not justified. "No broadcast event stream" (`NOT-DOING.md:38`) does not forbid a per-viewer cursor stream.

**§7.** One version across packages is `AGENTS.md:153-154`. The 0.4.16 ticket matches the RFC: release `d15ecba68f` from `6b588f4bce`, 24 failures in seven client files, 3112 seconds, an affected subset that omitted those files. Cutting a patch from the last published tag, without weakening qualification, and running the whole client suite before client or device changes land, matches that failure. Splitting the guide out of the binary fights the compiled-guide rule (`explainer.md:599-604`).

**§8, mostly.** Decision 4 gives the lead the engine, the store, and the client contract, and reserves a two-family review for partition inversion. §1 B is that review. §5's reply is the client contract. §2 A's text is periphery. Asking the lead whether a note or a refusal of a program that can never succeed may be lane work is the right question. Decision 4 does not name the binder.

## Findings

**1. High. §1 "Options" B and "Recommendation."** B is not the smallest admitted form, and the conditional-public half is not already implemented by `partitions`.

The smallest sound admission is one explicit `sync to` whose target is identical to one whole disjunct, and that disjunct is already one of the three invertible forms, with no extra conjunct. `sync to .claimant` on `read <- .claimant = viewer or .postedBy = viewer` is that form. The partition log does not change: `Audience::Column` and `Audience::Target` already return the one partition, and `account_row_change` already emits `del` plus `put` when the audience columns change.

`sync public where .approved` is a new audience. `Audience::Public` always returns the public partition (`partition.rs:119-120`). It does not consult a row predicate. §20.7 is the dual (a public read rule, a narrower sync), not this. §20.22.6 says that dual was never built. Calling B "§20.7 generalized from `public` to any rule" and saying `partitions()` already returns the conditional form will cause an implementer to ship a public partition for every row.

Leak if the named target is not the whole disjunct. `read <- (.claimant = viewer and .published) or .admin = viewer` with `sync to .claimant` delivers unpublished rows to the claimant. The guide already refuses an extra conjunct on a full audience (`guide/sync.rs:111-112`). B must apply that check to the named disjunct only. A viewer-free `exists flags[.id]` is not row-local either: the flags table changing would have to move the row, and `partitions` never sees that table.

Smallest change: split B. Admit the exact-disjunct `sync to` form first. Specify conditional public as a later audience arm whose predicate is a viewer-free, row-local comparison, evaluated inside `partitions`, with null not true. State that §20.6's "a second non-service disjunct is still refused" is amended only for an explicit named disjunct.

**2. High. §1 "What Snapback does today" and option B's completeness sentence.** A device under B still answers wrong unless completeness is defined, and the defined test can be cheaper than "the predicate implies the disjunct."

Scenario: `read <- .claimant = viewer or .postedBy = viewer`, `sync to .claimant`. Row R is claimant Alice and postedBy Alice, so Alice's device holds it. An update sets claimant to Bob and leaves postedBy Alice. `partitions` moves R from Alice's partition to Bob's. Alice's device applies `del` and drops R (`deferred.rs:241-245`). Alice may still read R. `claims where .id = R` and `claims where .postedBy = viewer` are then empty on the device. `trust_synced_read` (`read.rs:268-275`, used at `:290-291`) treats held rows as readable and does not re-evaluate the rule, so it will not notice the missing disjunct. The same delete happens on `until-revoked` group leave (`device.rs:1281-1291`): leaving the group drops rows the viewer can still read through `.owner = viewer`.

`DeliveredHistory` is the other edge. Leave keeps the rows, and `trust_synced_read` still returns true. That is today's retention policy, not a new leak, but B must not start re-checking the current rule against those retained rows.

The device can decide completeness without a general prover. It already knows the schema and the viewer. v1 should mark a read of this table device-complete only when the plan is the same shape `infer_audience` already recognizes for that one disjunct (the audience index probe, within the horizon). Any other read, including `where .id = ?`, a count, and an `exists`, sets the existing `unknown_fact` path. That errs toward the server. It is a scan-site check, not new partition machinery. The word "implies" commits to an entailment procedure the RFC never specifies. Extra filters such as `where .claimant = viewer and .status = 'open'` stay server-class under the coarse test even though they would be complete. That is the right v1 trade.

Field owners contradict "no row belongs to two partitions." `account_row_change` inserts the owner's partition when `field_owner_can_read` passes on the full rule (`partition.rs:216-222`). Those rows are still readable, so this is not a disclosure leak, but a `del` of the synced partition is rewritten to a `put` only for tables with private fields (`:958-965`). Tables without private fields lose the local row. Say that. Do not claim every row has one partition.

Writes are not "predict as usual" whenever the result lands in the synced disjunct. The author's pending row is not on the device. Approving it is an update of an unheld id. There is already a ticket for predicting an insert over an unheld id. That write is online-only unless the full prior image is held.

The existing inversion proofs still apply to the named disjunct: unique audience index (finding 7), recipient column (finding 2), aggregate not wider than its source (finding 5). `maintain_subset_unknown` (`maintain.rs:186-188`) is true only when a public read rule has a non-public sync. A disjunctive table needs the same "source is a subset" bit or a predicted aggregate is a partial count presented as complete.

Smallest change: add those four sentences (exact disjunct, coarse completeness, unheld writes online-only, existing proofs and `maintain_subset_unknown` still apply). Keep C rejected.

**3. High. §5 option B.** `answer` is not a function of the facts `wantsServer` reads, and the prediction fence is not on the device.

`wantsServer` is `unknown && !retained` (`local-query.ts:242`). The client's fence is separate (`local-query.ts:143-151`): `env.pending` is true when an admission is in flight or `pendingTables` says so (`local-reads.ts:285-287`, `:477-478`). `queuedPredictions` returns null, which fences every read, when any predictable queue entry has no predicted payload (`local-reads.ts:193-196`). `admitting()` increments that counter before the write reaches the device (`local-reads.ts:279-283`). Cold reads use a captured snapshot and skip the live queue (`local-query.ts:144`, `device-control.ts:78`). The device reply's `speculative` bit is set only when this evaluation observed a predicted row (`call.rs:181`). A query does not receive the client's footprint.

So the device can say "this result read a predicted row." It cannot say `server-after-settle` for the fence the first-party client actually applies. A host that trusts `answer` and skips `pendingTables` will replace a local page with a server page that does not contain the write still being admitted. `local-query.ts` cannot switch to the field and stay in agreement with today's procedure.

Smallest change: define `answer` from device facts only (`device` when `!unknown || retained`, with `complete` still meaning "more may exist"; `server` when `unknown && !retained`). State that the host still applies the admission fence, the cold snapshot, and `held`. Do not claim the device computes `server-after-settle`.

**4. High. §5 option B, omitting `data`.** Keyed the wrong way, this drops answers LLP 3000.020 and LLP 3000.028 keep.

`unknown_fact` sets `unknown` and does not set `speculative` (`local.rs:252-258`). Online-only scans set `speculative` themselves (`read.rs:422`, `:879`). A lower bound under LLP 3000.020 §3.3 is an unknown, non-speculative count `L`. Offline, the badge shows `L+`. Omitting `data` whenever `unknown` is set, or whenever `data` is `0` or `[]`, erases `L`.

A retained composition needs the device `data`. `routeLocal` merges with `keepRetainedRows` only when the device outcome still has `data` (`local-query.ts:330-334`). A row with one retained field and one online-only field is `answer: server` because a site is server-only. Omitting the whole `data` value drops the retained field. LLP 3000.028 §3.2 also refuses to replace history with a server page whose `seq` is ahead of the device watermark. The device does not know that `seq` when it builds the reply. One top-level `answer` cannot express per-component coverage. The reply already has `components`.

`local()` treats a missing `data` as `{loading: true}` (`local-query.ts:193`). Today's offline recovery of a server-only read depends on `data` being present and `speculative` being true (`placeholder` at `:122-123`). Published clients would show loading offline instead of a remembered answer or `E_OFFLINE`.

Read-through child coverage calls `unknown_fact` without setting `speculative` (`through_read.rs:64-66`). The RFC cites that `data: []` page as a case Exact2 renders as data. Omitting `data` only for server-only sites does not cover it.

Smallest change: omit `data` only when every site of the reply is server-only (online-only table or view, or `connected[p]`) and the reply is not retained and not a certified partial. Keep `data` for LLP 3000.020 `L` and for retained components. Say that `answer: server` with `data` present means "show this partial, and ask." Say that `answer: device` with `complete: false` means "do not ask" (meter cut, horizon, word cut). Point the contract at `components` for mixed rows, and at the watermark check in `local-query.ts:271-296`. Note the published-client offline change, or gate omission on the reply generation the backend already carries.

**5. High. §6 option B.** Evented parking inside `tiny_http` is not a sound design until the detach contract exists. The recommendation to measure before choosing it over a second listener is sound. The recommendation to adopt B as the design is not.

`ConnectionLimits` admits a socket with a lease, serializes the connection until the response finishes, and applies a 5-second write timeout (`vendor/tiny_http/src/limits.rs:88-105`, `SNAPBACK-PATCH.md:44-56`). One parking thread that writes the final bytes itself loses that timeout. One slow client blocks every other stream. Detaching the socket without keeping the lease either closes the fd or frees a connection slot while the fd is still open, so the 128 cap no longer counts live streams.

The bearer recheck is once, after the wait, on a poll of at most 25 seconds (`serve_changes.rs:90-101`). An SSE held for the life of a tab can outlive the session. "Per-viewer work is only the post-wait recheck" does not re-check before later events.

Presence is entered for the wait and left when the request function returns (`serve_changes.rs:35`, `:89`). A parker that never returns must leave on write failure, read-side close, and idle timeout, or `connected[p]` sticks. The 35-second grace exists because polls end. A long-lived stream changes that meaning. That is rule-visible, not an HTTP detail.

`check` is not a cursor compare. It reads up to 500 commits, preserved revocations, and settlement changes, and the table list is global (`serve_changes.rs:113-130`). Computing "the changed table set once" still wakes every viewer of a public table. Private delivery is per partition. Interest has to be the viewer's partitions, which the log already names.

The RFC does not mention proxy idle timeouts. The 25-second cap is what makes the current poll survivable behind a proxy that buffers.

Smallest change: keep A as the decision. Demote B to a sketch that is acceptable only with non-blocking writes and per-socket backpressure, lease accounting, a write timeout, auth recheck before each event, presence leave on a dead socket, partition-level interest, and a stated proxy config. Put that list in the RFC. Then measure, including a stalled client. A second listener remains reasonable if the detach patch cannot keep the lease and the timeout. "Two TLS stacks" is stronger than the code: TLS can stay at one proxy, with the second listener on loopback HTTP.

**6. Medium. §3 option C.** `N_WRITE_DENIED` is not well-defined for `upsert`, and "absent" is not visible on `RuleExpr`.

An `upsert` consults the insert rule and the update rule (`bind/residency.rs:132` and `:200`). `update <- deny` with an insert rule that admits callers refuses only the update arm. The sample sentence "refused for every caller" is false for that upsert. The note should say which arm.

After binding, an omitted rule and `update <- deny` are both `RuleExpr::Deny` (`bind/schema.rs:200`). A failed bind is also replaced with `Deny` (`:197`). Quoting `` `update <- deny` `` for an omitted rule is wrong. Read the AST. Do not emit the note when the only reason the rule is `Deny` is a bind error already reported.

The action exemption does not apply to v1. An action runs as its service seat, not as the system (`guide/jobs.rs:103`). A `deny` rule does not name that seat, so the write is unreachable for the action too. Apply the exemption only when the effect rule being checked admits the action's seat. Do not skip every write in an action because some other rule names the seat.

Smallest change: define the note over AST effects. An upsert has two. The message names the arm. Jobs and maintains are out. Actions are out only when that effect rule admits their seat.

**7. Medium. §6 "What it touches" and §8.** Idle-stream admission is periphery. Presence is not.

`connected[p]` is engine state (`engine/mod.rs:128-136`). LLP 3000's presence decision is that this is the server's own knowledge. Holding presence for the life of an SSE, or forgetting to leave it, changes what rules see. That part is lead-owned, not "periphery the lead reviews." The SSE event shape is a client-contract addition, which §8 already assigns to the lead. Split the row: pool sizes and `E_STREAMS` are periphery; presence lifetime and the event schema are core.

**8. Low. §1 recommendation.** The same sentence is repeated: "The evidence supports moving the NOT-DOING line, not deleting it." Delete one. Also, `RuleExpr::quarry` is the printer for every diagnostic, not a one-line `E_SYNC` tweak. Ownership as core is right. The size claim is not.

**9. Low. §2 option A.** Say "144 canonical bytes," matching `identity_fits`, not "144 bytes." The rest of A should land.

**10. Low. §4.** `contains_system_principal` walks arrays and objects. A list-of-principal literal can carry `'system'` and is refused only at runtime. The binder check should use the same walk, not only scalar `principal` and `principal?` columns.
