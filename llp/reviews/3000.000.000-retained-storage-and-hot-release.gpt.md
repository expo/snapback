## Round 1

**Verdict: NOT READY.**

The direction is implementable, and the transactional retention, enum refusal, monotone generations and ambiguous-reply handling are sound foundations. Six points need resolution before implementation.

1. **HIGH — Dormant children can cross an authorization boundary after parent ID reuse (§§2–4).**  
   Example: B adds comments that `read through` projects; rollback makes comments dormant; A deletes project `p` and recreates `p` for another tenant; forward restores the old comments. The existing activation code [recaptures parent authority](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4-core/src/engine/through_activation.rs:198) when the predecessor lacks the child declaration. Restored comments could consequently acquire the replacement parent’s audience. Dormancy removes the physical-child protection on which LLP 3000.014 relies.

   **Fix:** Specify how retained children remain bound to their original parent lifetime. Refuse restoration against a deleted/reused parent, and validate retained authorization captures before any recapture. Capture comparison alone cannot detect reuse with identical captured fields; preserve deletion/incarnation evidence or an equivalent safeguard. Test parent deletion, ID reuse, audience changes and inherited expiry.

2. **HIGH — Partial reactivation and changes of storage ownership are underspecified (§2).**  
   Consider B with `T(a,b)`, A without `T`, C reintroducing `T(a)`, then B again. C must restore `a` while retaining `b` separately. Simply validating the dormant whole-row image rejects its extra field; projecting it can lose `b`. Similarly, reusing a durable application name for a derived table or maintained column can let a builder overwrite authoritative retained values.

   **Fix:** Define the retention state transitions across active storage, dormant whole tables and dormant columns. Partial restoration must preserve omitted fields and their definitions, merge existing dormant cells, and consume only successfully restored entries. Explicitly refuse or define durable-to-derived ownership changes. Test repeated removal/restoration and partial table reintroduction.

3. **MEDIUM — Expected release alone does not detect A→B→A stale commands (§5).**  
   A command expecting release A can arrive after B and a rollback to A and pass its compare-and-swap. This contradicts the promise that out-of-band stale commands fail. The existing [release check](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4-core/src/engine/mod.rs:617) compares only release identity.

   **Fix:** Include an expected activation revision in the message and check it transactionally. Release plus semantic generation detects changed A→B→A transitions; a separate activation revision also covers equal-hash release activations that retain their generation.

4. **HIGH — The publication boundary must include native metadata and runtime source ownership (§5).**  
   Holding the engine writer guard does not exclude `/schema`, which independently reads [bound, generation and native metadata](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4/src/serve.rs:1122). Swapping native state outside that shared publication boundary permits a mixed backend description. Also, the current [worker supervisor](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4/src/dev_worker.rs:66) captures its original project, and declaration rediscovery is restricted to dev mode; incrementing worker revision cannot select a new release root.

   **Fix:** Specify a prepared runtime bundle containing bound programs, native module, reader factory, worker source root and desired declarations. Publish all observable backend components under a common lock boundary, with native included in the `/schema` lock order. Explicitly separate infallible publication from fallible worker spawning, and define post-commit restart failures as committed activation with degraded worker availability. Test mixed-schema/native races and worker addition, removal and source replacement.

5. **MEDIUM — Crash recovery needs a source-durability boundary (§5).**  
   Database authority is insufficient if its selected release source disappears after a host crash. Current staging [writes files and renames the directory](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4/src/verbs/releases.rs:104) without syncing the complete release tree and its directory entries.

   **Fix:** State the supported crash model. For power-loss recovery, durably flush all required source, native and worker artifacts and the release directory publication before committing the database pointer. Otherwise explicitly limit the guarantee to process crashes. Exercise crashes before commit and between commit, publication and reply.

6. **MEDIUM — Live prune and ambiguous-result inspection lack an operational path (§§4–5).**  
   `serve` owns the writer for its lifetime, but the described socket handler activates candidate releases. The RFC does not specify how prune runs against a live server or how an operator reads authoritative current/history after losing a reply.

   **Fix:** Define owner-mediated prune and status/history operations, or explicitly require stopping serve for prune. Prune must enumerate and delete the same transactionally selected dormant set and audit exactly that set. Recovery instructions must identify a concrete command that reads database authority despite stale convenience files.

Minor clarification: bound diagnostic **bytes and distinct values/keys**, as well as sampled IDs, so large values cannot produce unbounded refusal output.

This was a source-based blind review. I did not edit files or run tests.

## codex2 — 2026-10-12

**READY WITH CHANGES (minor only).** I found no blocking design defect. Transactional retention, parent-deletion evidence, activation revision, and prepared runtime publication provide a coherent design.

1. **Minor — bind activation history to activation revision (§§4–5).** The specified event fields omit the revision used by command CAS. Equal-hash activations can share release and generation identifiers, making lost-reply recovery harder to correlate. **Fix:** persist the committed activation revision in each activation event and expose it through `releases`. Include the operation and retained/restored summary.

2. **Minor — make the critical regression cases explicit acceptance requirements (§7).** Add:
   - `T(a,b) → absent T → T(a) → T(a,b)`, including another retirement between partial and full restoration.
   - Parent deletion and identical-id/value replacement while the referencing cell remains dormant.
   - A stale command after A→B→A, plus equal-hash activation.
   - An old reader checked out before activation but not yet pinned, including a native-only change.

   **Fix:** require assertions for retained values, invalidation evidence, command refusal, and reader retry—not merely successful deployment.

3. **Minor — test the stated crash guarantee at its boundaries (§§5, 7).** “Restart binds the committed release” does not explicitly cover interruption between commit, runtime publication, and convenience-copy updates. **Fix:** require fault injection immediately before and after database commit and during filesystem-copy updates. Recovery must select the database-authoritative release, preserve active/dormant consistency, and accurately distinguish committed activation from an ambiguous command result.

These changes clarify audit evidence and verification; they do not require redesign. No files edited.

## Round 3 — 2026-10-12

**NOT READY.** The transaction and crash-recovery model is coherent, but two correctness gaps need explicit fixes.

1. **§2: distinguish storage retirement from actual lifetime-ending deletion.**  
   “No schema retirement marks an edge deleted” is too broad. Existing activation [retires expired read-through rows](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4-core/src/engine/through_activation.rs:138). If such a parent disappears during activation, its id is later reused, and a dormant child restores, an unchanged `invalid` bit could attach that child to the replacement—even with identical audience values.

   **Fix:** exempt only moves into dormant storage and derived-cache replacement from deletion invalidation. Every actual deletion of an authoritative row, including expiry performed during activation, must invalidate matching dormant edges in the same transaction. Test dormant child → parent deleted by activation-time expiry → identical-id/value replacement → restoration refuses. A failed activation must roll back the invalidation too.

2. **§§5–6: bind worker preparation to the revision that authorizes it.**  
   Updating the desired root before incrementing revision does not close the race between worker preparation and engine acquisition. A supervisor can prepare B’s entry/declarations, activation C can commit, and then the supervisor can acquire the engine and mint a C-authorized session for B’s code. The existing [session-minting path reads the latest revision](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4/src/dev_worker.rs:306), so reusing it would preserve this race.

   **Fix:** prepare an immutable tuple containing release root, entry, declarations/environment and supervisor revision. Under the engine guard, compare its revision with the current revision before minting credentials; discard and retry obsolete preparation. Credentials must remain bound to that checked revision, so subsequent activation fences them even if spawning finishes later. Test rapid B→C activation with a barrier between B’s preparation and session minting, covering both conventional and named workers.

One minor clarification: define pagination for `releases` history and large dormant inventories. The 64 KiB response limit must still permit complete inspection and identification of every pruned item.

Review was independent and read-only, with small targeted code checks; no tests or full audit were run.

## Round 4 — 2026-10-12

**NOT READY**

One material defect remains in §§5–6: **native read implementation changes can retain the semantic generation**, because generation equality considers only schema/program hashes.

With unchanged native declarations, release B can change a native read’s body while retaining A’s generation. An already connected device still holds A’s backend descriptor and native module. The client’s [backend refresh condition](/home/ccheever/projects/sb4-ws-roll/snapback4/packages/snapback4/src/local.ts:668) does not detect that change, and its [native installer](/home/ccheever/projects/sb4-ws-roll/snapback4/packages/snapback4/src/local-native.ts:19) accepts the cached digest. Server reader replacement and poll wakes therefore leave the device executing A while the server executes B. Late results from A also carry the same generation, defeating the stated generation fence.

Require a changed native read module digest to advance the existing semantic generation, atomically with activation. Preserve generation for equal execution content; source-only changes can still advance activation revision independently. This uses the existing device protocol and adds no publication gate.

Add coverage with an already connected client holding module A: hot-activate B with unchanged declarations, verify backend/module reacquisition, and reject a delayed A result.

The retention, deletion evidence, partial restoration, pruning, and crash-recovery mechanisms otherwise present no material blocker in this review.

## Targeted confirmation — 2026-10-12 (coordinator authorized continuation)

**READY.** No material findings in the requested scope.

- **Native-only changes:** §§5–6 include the prepared module digest, including removal, in persisted execution identity. Generation advances within the activation transaction, and publication swaps bound programs/generation/native under the common guard. This also fences unpinned old readers.
- **Activation-time deletion:** §2 explicitly requires every actual authoritative deletion—including activation expiry—to invalidate dormant reference edges before id reuse. Failed activation rolls that evidence back. Retention moves and derived-cache replacement have narrow exemptions.
- **Worker preparation:** §5 binds prepared source/environment/declarations to a captured supervisor revision, compares it under the engine guard before credential minting, and discards stale preparation. Later activation fences credentials even if spawning finishes afterward.
- **Retention and hot activation:** Restoration precedes builders; omitted cells remain dormant; newly retired active values win collisions. Validation, consumption, deletion evidence and release identity share commit. Fallible runtime preparation precedes commit, while reader-opening and worker-spawn failures have explicit committed-result recovery.

The acceptance cases directly exercise these races and lifetime boundaries. This confirms the design’s readiness for implementation, not implementation correctness.
