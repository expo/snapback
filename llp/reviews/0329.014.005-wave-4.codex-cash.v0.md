Totals: **20 operations** — 1 plan, 5 refused→rewrite, 1 schedule, 1 effect, 1 product-change, 11 premise-violations, 0 maintained, 0 channel.

The violated premises are one server authority, trace-as-offline-closure, and the store-wide offline fence. A server mutation would make received cash merely `predicted`; a server receipt cannot cover peer-ingressed chains; and `replica` copies custody instead of moving it. The honest outcome is **not this system under v0/v1.1**. A successor could absorb it as a new **authority-placement dimension** plus a **peer-custody transaction kind**—not as a second query class.

The Wave-4 preregistration is only partly confirmed. Handnote softened “double-spend impossible” into two possible offline accepts followed by one settlement winner, punishment, and guarantees. Physics therefore does not dispose of this fixed product; authority placement does.

Required indexes/constraints:

- Unique: device public key; merchant/person; account/person; `(personId,clientOpId)`; `(deviceId,noteId)` locally; `(caseId,claimantDeviceId)`; `(personId,date,kind)`; `(extensionId,approver)`; `(deviceId,date)` day close.
- `handoff.bySession`, `handoff.byToTime`, `noteTip.byBearerExpiry`, notes by ancestry, receipts by payer/time and merchant/time, revocations by device/time, batches by device/time.
- Raw handoffs and splits deliberately have **no** unique consumption key. `consumption.unique(noteId,fromVersion)` chooses the winner while retaining every attempt.
- `appendOnly()` binds entries, handoffs, splits, receipts, refund events, revocations, bundles, batches, approvals, consumption, and evidence. Settlement stamps are sidecars rather than forbidden updates.
- `immutable(['denominationCents','ancestryRootId'])`; partial unique active pocket; conditional count/sum pocket caps; refund sum cap; event-coupled possession transitions; `sumEquals` for normalized split children; `balanced` for a normalized asset/liability ledger are v1.1.
- `interval` is used for possession history and extension validity. No `tree` is needed.

Rule macros expand to all four effects:

- Private mutable: `{read: owner(row)||system, insert: system, update: system, delete: never}`.
- Private append-only: same read, `{insert: authorizedNamedProgram, update: never, delete: never}`.
- Public signed: `{read: public(reason), insert: system, update: never, delete: never}`.
- Party evidence: `{read: bearerOf(from)||bearerOf(to)||system, insert: settlementSystem, update: never, delete: never}`.
- Mint-only registry/evidence: `{read: system, insert: system, update: system, delete: never}`.
- Claims/day sheets: claimant or merchant owner reads; named system mutations write; delete never.
- The apparent local rule `{read/insert/update: row.deviceId===viewer, delete:never}` does not solve `pocketNote`: the server remains authoritative. That table is unadmitted.

Protection splits are mandatory: publishing the original `deviceCerts` would publish `deviceId→personId`; mutable `receipts.refundedCents` contradicts append-only; and a single mutable/evidence `doubleSpendCases` table mixes protection and lifecycle classes.

### 3. Operations in v0

**5.1 ReadPocket.** The natural first attempt is wrong:

```ts
const rows = db.scan(pocketNote.byDevice, [args.deviceId], { take: 200 })
const liveCents = rows.reduce((n, r) =>
  n + (r.possessionState === 'live' ? r.denominationCents : 0), 0)
const stale = rows.filter(r => r.expireOfflineAt <= Date.now())
```

`Date.now()` is `E_AMBIENT_TIME`. More importantly, the 200 cap applies only to current live notes; `spent` history is unbounded. V0 can silently return a page sum as though it were total; v1.1 correctly refuses the population claim as structural incompleteness. The corrected shape splits capped current possession from append-only history, reads maintained `unsettledCents`, uses seven literal denomination buckets, and uses declared `ctx.readTime` for display. It remains a premise violation because the authoritative query must run locally.

**5.2–5.3 MintNotes and RedeemNotes.** Calling the partner inside a mutation is `E_OPAQUE`:

```ts
// Refused: await/fetch/I/O inside a data program.
const result = await partner.transfer(args.partnerKey, amount)
```

The corrected online flow is:

```ts
beginFunding = mutation(/* insertIfAbsent intent; online-only, predict:false */)
dispatchPartner = effect(/* immutable key; poll sent_unknown */)
applyPartnerResult = mutation(/* callable:system; bounded notes/entries/limits */)

redeem = mutation(/* db.run(settleBounded); redeem accepted notes; credit entry */)
```

This uses v1.1 transactional outbox, `insertIfAbsent`, `db.run`, system phases, and zoned mint-time limits. Mint delivery into, and redemption removal from, authoritative local custody still require the new authority dimension. Notes remain visible only after mint acknowledgement, so no optimistic prediction is appropriate.

**5.4 SplitNote.** A `while`-based splitter, ambient clock, CBOR encoder, and device signer produce `E_UNBOUND_LOOP`, `E_AMBIENT_TIME`, and `E_OPAQUE`. Rewriting the six denomination levels as a literal bounded loop and using modeled time makes the computation certifiable. Parent death, split evidence, and at most five child births are one local transaction. No v0 correction makes that transaction authoritative rather than predicted.

**5.5 SelectNotes, PayByHandoff, change, and fare.** `SelectNotes` can use `All<P>` over current possession, stable denomination/id order, and at most six canonical splits. The attempted payment cannot:

```ts
export const pay = mutation(args, async ({ db }) => {
  // lock, sign, BLE-send, let disconnected payee commit
})
// async/BLE/signing: E_OPAQUE
```

Moving BLE to `effect` yields `E_EFFECT_NOT_LIVE`; effects are server-side, never client-callable, and cannot make peer state final. A channel is transient server fan-out. The honest missing form is a `peerTransfer` kind whose payer transaction durably signs and kills notes before export and whose payee independently verifies and commits before acknowledgement. This is illustrative language delta, not v1.1.

Change is two such transfers, not cross-device atomicity. Fare uses the same kind with hop cap 8 and no reverse phase. The static bounds survive, but a 300 ms guarantee needs device/crypto latency metrology beyond `maxSteps`.

**5.6 RefundPurchase.** Scanning visible refund sessions and tallying them is `E_STRUCTURAL_COUNT`; another till’s hidden refund would overstate remaining value. The corrected server route is `refundTotal` with declared receipt-party readability plus a sum-cap constraint. The local check is only advisory; the cash movement remains a peer-transfer premise violation.

**5.7 MovePocket.** The whole current pocket is `All<P>`, followed by one peer transfer. Server finalization uses a partial unique active-pocket constraint. A v0 unique conflict is sealed `E_CONSTRAINT`; v1.1 can record an attempt and serialize the system continuation. It still cannot move authority between disconnected device stores.

**5.8 SettlePocket.** First attempts fail three ways: default-all is `E_UNBOUND_SCAN`; Ed25519/CBOR is `E_OPAQUE`; unique raw handoffs cause sealed `E_CONSTRAINT` and erase evidence. The server-side correction is:

```ts
for (const a of args.attempts /* max B */) {
  verifyBoundedSignedChain(a) // missing trusted crypto primitive
  db.insert(handoff, a)       // append evidence; no consumption unique here

  const won = db.insertIfAbsent(consumption, [a.noteId, a.fromVersion], {
    winnerEventId: a.handoffId, winningBatchId: args.batchId
  })
  if (won.already_acted) {
    const first = db.getHidden(consumption, [a.noteId, a.fromVersion])
    db.insert(doubleSpendEvidence, {
      firstHandoffId: first.winnerEventId, secondHandoffId: a.handoffId, ...
    })
  } else {
    // bounded registry, fee, velocity, tip, and result writes
  }
}
```

This borrows v1.1 `insertIfAbsent`, `getHidden`, `insertSoft`, `serialBy(pair)`, `callable:'host'`, and `predict:false`. The missing crypto verifier is still a runtime delta. Worst-case 5,000×128 verification also likely triggers `E_BOUND`; shrink batches by total chain events/bytes.

**5.9 GossipTrustBundle.** A server query for the latest available bundle is a point/page plan. Signature verification, durable local replacement, and offline forwarding are neither channel nor effect. They require signed peer import. “Latest” means latest this device received, not globally latest.

**5.10 ReportDeviceStolen.** The initial global patch is `E_UNBOUND_SCAN`, and `take:Q` followed by treating completion as exact yields `E_FANOUT`. Correct form: append revocation and disable the certificate in one mutation; enqueue HSM bundle signing; process stale registry tips with a v1.1 chunked job. Already-transferred notes are untouched.

**5.11 Sweeps.** Creating cases atomically during settlement makes the 30-second conflict scan a recovery audit. Otherwise use a per-case schedule/job cursor. Reclaim should be scheduled per session:

```ts
schedule(handleCase, { at:c => c.detectedAt, key:c => c.caseId,
  principal:'system' })
schedule(reclaimSession, { at:s => s.reclaimAfter, key:s => s.sessionId,
  principal:'system' })
```

These replace unbounded population scans. The stated late-payee-wins reclaim semantics require a product correction; no boundedness rewrite makes the resulting authority safe.

**5.12 CloseMerchantDay.** `while (unsettled)` is `E_UNBOUND_LOOP`; one 10,000-note transaction is `E_FANOUT`/`E_BOUND`. The honest form is a v1.1 job over a sealed `commitSeq` watermark, 5,000-or-smaller settlement chunks, then bounded redeem/remint. Day-sheet totals come from maintained merchant/day rows; page tallies are `E_STRUCTURAL_COUNT`.

**5.13 FileGuaranteeClaim.** Searching chains or existing claims is `E_UNBOUND_SCAN`/`E_NOT_ATOMIC`. Correct form point-reads the case, current eligible tip, stored acceptance evidence, note, account, and existing unique claim; a system continuation uses hidden data to write only `full|half|none`, payout, and clawback. The fixed schema omitted authenticated acceptance-time evidence.

**5.14 PublishEmergencyExtension.** Passing two operator IDs to one mutation does not prove dual control. Two distinct authenticated calls append unique approvals; a system mutation requires two, inserts the extension, and enqueues HSM signing/bundle publication. Direct signing or bloom construction is `E_OPAQUE`. Offline distribution then inherits GossipTrustBundle’s peer-kind gap.

Compared with the prose design, v0 makes serial uniqueness, append-only evidence, field immutability, idempotency keys, and protection splits binding across every admitted server writer. V1.1 additionally binds partial uniqueness, sum caps, conservation, balance, named writers, time zones, and jobs. Conversely, neither language enforces I5–I7, I10/I12 at acceptance, I13, I19/I21/I22 peer-side, or I24 without the new authority dimension.

### 8. Where the design is wrong

1. **The evidence schema contradicts the adjudication rule.** `handoffs` is globally unique on `(noteId,fromVersion)`, yet both competing handoffs must survive and `doubleSpendCases` names both. Confirmation: settle two valid forks; either the second insert is refused and no case exists, or the declared unique constraint is false.

2. **Seven-day reclaim is not reliable authority.** A later payee wins even after the mint tells the payer to reclaim and the payer spends again. Confirmation: B receives a signature, stays offline eight days; A reclaims and pays C; B then settles. A obeyed mint authority but is classified as the double-spender, while both B and C held “accepted cash.”

3. **The current/history bounds do not close.** The 200-note cap covers live possession, while ReadPocket also scans unbounded `spent` history and CloseMerchantDay expects thousands of unsettled items. Confirmation: let a till produce more than 200 unsettled spent rows before close; ReadPocket must truncate a claimed total or exceed its certificate. Current possession and maintained history totals must be separate.
