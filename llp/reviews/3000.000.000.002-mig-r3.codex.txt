1. **P1 — Backfills can overwrite row identity.** [Output admission](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/schema/backfill.rs:53) permits `id`. The compiler accepts `{id: replacement}`, but [patch application](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/store/backfills.rs:170) updates only the JSON image, retaining the original SQLite key and evidence identity. This can corrupt point lookup, indexing and deletion behavior. Reject `id` at the shared schema admission boundary and add a regression.

2. **P1 — Dropped historical references bypass lifetime invalidation.** [Narrowed restoration](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/store/narrowed.rs:303) checks an invalid reference only if its column remains in the candidate. Backfills retain access to dropped historical fields. A dormant child whose parent was deleted and recreated can therefore copy its dropped reference into a new reference column—or look up the replacement parent—and activate successfully. Validate lifetime evidence for consumed historical inputs before exposing them to backfills, regardless of candidate column visibility.

3. **P1 — Source expiry is not reliably enforced before transformation.** [Pre-backfill retirement](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/store/narrowed.rs:232) depends on `Retirement::affects`, whose [predicate](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/engine/through_activation.rs:187) excludes ordinary expiry changes when neither table uses read-through. An expired, unswept row can reach the transform; dropping expiry also makes its former deadline writable because admission checks only candidate lifetime fields. Rewriting that deadline can preserve an already-ended lifetime. Retire source-expired rows from their original images before evaluating patches, including restored sources.

4. **P1 — Pruned evidence permits double application and fabricated reversal.** [Re-entry](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/store/backfills.rs:109) treats missing evidence as a fresh row without consulting `_backfill_pruned`. Sequence: transform `n:3 → 6`, prune while active, remove the table, then restore the same declaration. It computes `6 → 12`, saves `6` as the preimage and clears the pruned marker; subsequent reversal returns `6`, falsely presenting it as the original value. Re-entry must honor pruned membership and refuse when required historical values are unavailable.

5. **P2 — Pruning deleted dormant lifetimes leaves evidence attached to reusable IDs.** [Prune](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/store/release_history.rs:323) deletes narrowed rows, then [converts all evidence into pruned markers](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/store/backfills.rs:196). Reusing a pruned row’s ID can inherit its active reversal-unavailable marker and incorrectly block rollback. Clear evidence and markers for lifetimes actually deleted by prune; preserve markers only for surviving lifetimes.
