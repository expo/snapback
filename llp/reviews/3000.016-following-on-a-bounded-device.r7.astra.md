1. **High — §2.1a: “same commit” does not establish source/event consistency during catch-up.**

   The requirement is clear, but the specified reuse of watermark catch-up leaves two concrete traps:

   - Insert P, then update its body in the **same mutation**. Birth accounting withdraws P’s earlier put and appends its final image, leaving P’s event **before P** in log order. A source-dependent filter added to the existing sequential applier rejects the event because P is not held yet, then accepts P. A subsequent repost treats the missing event as known absence and incorrectly refuses `FEED_POST_NOT_FOUND`. [Birth accounting](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/partition.rs:192>), [sequential application](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-device/src/device/deferred.rs:195>).
   - Ordinary stream puts are re-read at the serving transaction’s current state. A body-update put from commit A can therefore carry `removed: true` from later commit B, while B’s event delete remains on the next stream page. Merely preserving raw commit boundaries publishes a removed source beside its stale event. [Put normalization](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/partition.rs:867>).

   **Smallest design change:** explicitly require pairing against the **actual delivered source image**, including authoritative event absence, for ordinary sync and snapshot catch-up as well as snapshot acquisition. Obtain that pairing from the same server state, and apply source admission before its associated event effects; do not depend on raw event order. Preserve unconditional event deletes.

   Add both probes, with the second stream deliberately split between A and B. Atomic application alone does not repair either dependency.
