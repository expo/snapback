## Verdict: SOUND WITH MAJOR ISSUES

The direction holds: one interpreter over both stores, a store as a logical identity, Postgres as a production port of all durable state, a short fenced cutover, and a measurement before any commit-path redesign. Three mechanisms would fail as written. Log retention assumes a re-acquisition path the sync code does not have, so a device below the floor silently skips log. The cutover fence leaves read paths that still commit. Fencing waits on a session advisory lock a paused owner keeps, and checks the token only on the head update. The two committer candidates also need a protocol change before the scale rule commissions one. The umbrella — port, preserve identity, measure, then decide — should stay.

## Fundamental and major findings

### F1. Retention and the partial log copy assume a re-acquisition path that does not exist — FUNDAMENTAL — child A §7.3, child B §4.2

Child A §7.3 says a resume below the retention floor “gets the existing re-acquisition path, the same answer a device far behind would get.” Child B §4.2 copies only that window and says resumes below it “would re-acquire after graduation exactly as they would have before.” Nothing deletes `_log` or `_commits` today, and a device behind the head does not re-acquire. It replays the log.

`partition::stream` (`snapback4/crates/snapback4-core/src/partition.rs:1090-1137`) reads spans with `seq` above the device watermark and advances the watermark to whatever remains. The only snapshot path is a device with no watermark (`partition.rs:15`). `memberships_before` keeps the latest join at or below the watermark (`engine/postgres/log.rs:62-63`). If those rows were dropped, the join baseline is empty and later group events are calculated as if the device never held the group. The client cannot see the hole: a deleted span looks like “no events for you.”

`/changes` does not close this. `serve_changes.rs:220-224` invalidates every table only when the returned commit page fails to reach the head. A client whose watermark sits under a deleted prefix, with fewer than 500 commits left and the page reaching the head, is told only about the surviving commits.

Shipping §7.3, or graduating by copying the retained window, drops committed history for every device offline across the floor. That is new behavior, and it is silent. Retention needs an explicit floor in the stream and change paths: a watermark below the floor, or a gap in `seq`, is a refusal that forces a fresh snapshot. Until that refusal exists, keep the whole log, and have graduation copy the whole log.

### F2. The cutover fence does not make the source quiescent — FUNDAMENTAL — child B §5, §4.1, §6

§5 step 1 holds mutations, admissions, claims, mints, and uploads, and keeps reads, sync, and change polls on a source that “no longer changes.” Step 2 then fixes `final_jid`. Several paths that the fence calls reads still commit, and on a `not before` schema they commit on every such request:

- `serve.rs:1018-1024` calls `advance_time_audiences()` for `GET /changes`, `POST /sync`, `POST /q/…`, and `POST /m/…`. That opens a write transaction, pins `time_audience_clock` in `_meta` (`store/time_audience.rs:29-35`), and commits. If an opening is due it also `record_commit`s and appends to the partition log (`engine/time_audience.rs:114-188`).
- A held change poll does it again when the opening comes due (`serve_changes.rs:112-116`).
- A query that hits a pending opening commits through `materialize_time_audience_at` and then retries the query (`serve.rs:1302-1314`).
- A one-view `GET /assets/<id>` commits `_asset_views` after the bytes are sent (`crates/snapback4/src/assets.rs:225-228`, `engine/asset_uploads.rs:307-313`). The fence holds uploads and leaves this view write running, so a consumed one-view grant can be missing on the target.

Triggers will journal those writes. Replay will not apply them if `final_jid` was already fixed. The source is then marked read-only. The write exists only in SQLite. Parity requires `not before` before Postgres is a production target (child A §9), so this is in scope for the move the RFC allows. Stopping schedules does not cover these paths. They are not schedules.

The capture section rejects engine instrumentation because a missed write site is silent divergence (§4.1). The cutover fence is that same shape: an admission list, not a lock. Take SQLite’s reserved write lock after the drain and hold it through verify and the ownership transfer. `final_jid` is the maximum journal id observed while that lock is held. Read-triggered publications either finish before the lock or fail the request as retryable. While the lock is held, no later trigger can append.

Two related holes in the same move: the quick digest (§6) covers family rows and not blob bytes, so a ledger row can match while the `BlobStore` put failed. `graduate revert` and `data pull` replay rows onto SQLite, and SQLite serves bytes from `<store>/assets/<id>` (`store.rs:206-210`). Bytes written after cutover live only in the blob store. The reverse direction has to materialize those bytes, and cutover has to refuse while any ledger digest is absent from the blob store.

### F3. The fencing protocol cannot take over from a paused owner, and it does not cover non-head writes — FUNDAMENTAL — parent §3.4 and §6.3, child A §5 and §8

§5 has the standby wait on a session-level advisory lock, then increment `token`. It also says lease expiry is not trusted by itself. The P1b witness is SIGSTOP of the owner while the standby takes over, and the paused owner must commit nothing on resume (child A §10, parent §6 point 3).

A session advisory lock is held by the Postgres backend until unlock or disconnect. SIGSTOP of `serve` does not disconnect. The backend stays idle, or idle in a transaction, and keeps the lock. The standby’s `pg_advisory_lock` waits. A network partition that leaves the TCP session up does the same until keepalive fires, which is often hours. The successor never increments the token, so the resume path still commits. The witness cannot pass as specified.

The token check is only the head update: `UPDATE _head … WHERE owner_token = $token`. Graduation §4.1 correctly says some durable writes never advance the head (session mints, claims, lease renewals, sweeps). `claim_effects_inner` updates `_outbox` and commits with no `record_commit` (`engine/effects.rs:212-237`). `record_asset_view` does the same (`engine/asset_uploads.rs:307-313`). Child A §8 puts the advisory lock on a dedicated owner connection and commits on a different connection. When the owner connection drops, the committer connection does not die with it. After reconnect, those transactions commit with a stale token.

Every durable transaction has to include the token predicate in the same commit, not only the head update. Takeover should record the holder backend pid, and on a database-time lease expiry call `pg_terminate_backend` on it, then increment the token. The advisory lock can be a clean-shutdown fast path. It cannot be the gate. An in-flight transaction that already holds `FOR UPDATE` on `_head` is cleared only by terminating that backend. A paused client holds that row lock for the whole program (`engine/postgres/store.rs:113-117`).

### F4. Both committer candidates break an invariant they say stays fixed, and the scale rule commissions one anyway — MAJOR — parent §3.3, child A §6, child C §3, §8, §9

The reference path really does hold the serial section across the program. SQLite takes `BEGIN IMMEDIATE` before `Runner::run` (`store.rs:377-382`, `engine/mod.rs:934-998`). Postgres serialized mode takes `SELECT seq FROM _head … FOR UPDATE` at begin (`engine/postgres/store.rs:113-117`) and updates that row in the same transaction as the log and effects (`engine/postgres/tail.rs:33-48`). k≈15 for an increment is a real measurement (`experiments/postgres/README.md:277`, 18.002 → 15.002 calls). The H1 bound is the right shape. LLP 3000 already records why a sequence allocated before commit cannot be the watermark: an earlier sequence can commit after a later one was delivered (`3000-snapback4.explainer.md:1101-1103`). Head and body in one transaction is what makes “snapshot at W contains exactly the commits ≤ W” true.

Candidate (a) does not, as written. It validates each mutation against commits in `(S, head]`, then batches the ones that passed (§6.3 steps 3–4). Two mutations that both read the same counter at snapshot S both pass, both enter the batch, and both commit. The reference would have ordered them. The batch merges them. A single committer avoids that only if it folds each write set into an in-memory head before it validates the next mutation, and the batch is that serial image. The text never says so.

The read set (a) needs is also not what the Runner records. `Runner::read_tables` is a set of table names, “for live subscriptions and commits” (`engine/runner.rs:130-131`). Parent §7.1 says the interpreter knows table, index, and key range, and that recording them is increment E, after a measurement. Table-granular validation marks every concurrent reader of `messages` as a conflict, so the formula `batch / (2·RTT + flush)` does not apply to the chat and workspace cells. Precise ranges are a precondition of (a)’s throughput, and child C commissions E only if W6 later misses its SLO (§8).

Candidate (b) splits each mutation’s writes from “a short ordering stage” for the head and tail (§6.3). If the data transaction commits before that stage, readers see writes that have no sequence, or sequence N+1 before N. That is the failure the explainer already rejected. If the data transaction stays open until the stage flushes, the stated ceiling `1 / (tail RTT + flush)` follows, and the single `_head` row still serializes the flush. W9’s serializable cells already failed on that shared head (`W9-INTEGRATION-REPORT.md:113-116`). The version of (b) that group-commits and keeps exact snapshots is a different protocol: assign the order in a short critical section, commit data transactions without holding that section across fsync, publish only the contiguous committed prefix, and make a reader at W use a snapshot that excludes commits above W. That protocol is not in the document. §6.4 says exact snapshots stay fixed either way.

The decision rule does not wait to learn this. H1’s own formula at k≈15 and 0.5 ms RTT is at most about 1/7.5 ms ≈ 133 commits/s before flush, and 60–200/s in the 0.3–1 ms band. §8 commissions (a) when W4 on the reference committer is below 1,000/s at 0.5 ms, or below 25% of raw Postgres. S0 measures “reference committer only” (§9). The parent says to measure how much a cheaper serial section recovers before commissioning (§3.3). A serial batch inside one SQLite transaction amortizes `synchronous=FULL` without C2’s overlay, because SQLite already shows the transaction its own writes. That is the Linux 165/s problem (`store.rs:205`, W9 at 164.80–167.49/s). It does not remove k·RTT on Postgres. Qualifying (a) on SQLite first does not show that the RTT term is gone. Run a Postgres prototype of the in-memory serial batch at the swept RTTs before commissioning C2, and write the intra-batch rule and the contiguous-watermark rule into §6.3 before either candidate is eligible.

### F5. The durable inventory omits state the sync wire and exactly-once steps depend on — MAJOR — child A §4.1, child B §4 and §6

The 23-file / ~10,000-line `rusqlite` claim matches this tree (23 files under `snapback4-core/src`, 9,993 lines). Several live tables are absent from §4.1. Graduation exports families, and the quick digest is per family, so an omitted table is omitted from the move and from the gate.

- `_change_evidence` is written on every commit and pruned to the last 1,000 sequences (`store.rs:228`, `store.rs:726-731`). Sync and `/changes` call `preserved_between` on it (`serve_sync.rs:151`, `serve_changes.rs:227`). The function is SQLite-only (`revocation.rs:177-179`). An empty or missing `preserved` array makes `canRevoke` true (`packages/snapback4/src/change-evidence.ts:4-8`), so clients treat the interval as revocation. The Postgres evaluation schema has no equivalent table (`engine/postgres/store.rs:33-60`).
- `_action_steps` is the exactly-once ledger for external action steps (`engine/actions/steps.rs:11-16`). The work family lists `_effect_steps` and not this table. Dropping it on cutover re-runs provider steps whose results were already stored.
- `_cap_counts` is authoritative occupancy on both stores (`store/activation.rs:200-203`, `store/caps.rs:11-16`, `engine/postgres/caps.rs:22-37`). A row import that does not rebuild it over-admits cap constraints. Indexes are specified as recomputed and then digested. Caps need the same rule.
- `_dormant_narrow_rows` is created with the other dormant tables (`store/dormant.rs:20`) and is not in the evolution row of §4.1.

Add these to the family contracts. The change-evidence window has to move with the log or `/changes` and sync preservation change at cutover even when every listed digest matches.

## What the documents get right that should not change

- The product gap is outside `Rows`. The evaluation adapter already runs Quarry, and `serve` still reaches `engine.store().conn()` (`serve.rs:806`, `serve_changes.rs:214-219`). Extracting the seam before writing Postgres families is the right order.
- A logical `store_id` is already what sessions check (`store/authority.rs:137-141`). Keeping it across a move, and minting a new one on restore, matches parent §9.
- Refusing logical decoding as the commit order is the right call. Commit-LSN order is not snapshot order, and the head row exists because of that (`3000-snapback4.explainer.md:1101-1103`).
- Capture triggers, armed before the copy and generated from a registry checked against `sqlite_master`, fail closed on a missed table. Chunked reads plus idempotent full-image replay is the right copy shape, once quiescence is a real lock (F2) and the log copy is complete (F1).
- One interpreter, the generic layout, and no Quarry-to-SQL lowering should stand. Child C is the right place to reopen a typed layout, and only from a measured storage ratio.
- H1’s formula, open-loop load, separate hosts, fixed durability, and a ledger that separates semantic cost from a design choice are the right experiment. W9’s 446–461 and 165–167 commits/s figures match `W9-INTEGRATION-REPORT.md:92-96`.
- Mutations enqueue effects inside the commit (`engine/mod.rs:1029`). A speculative rerun must stay inside that boundary so a conflict retry does not perform the provider call.

## Small notes

- The parent’s 14,000–15,000 SQLite commits/s (`3000.009` §2.3 and §4.5) is the M5 run where `synchronous=FULL` is explicitly not macOS `fullfsync` (`experiments/postgres/README.md:247-252`). W9’s ~165/s is a Linux fsync. They are different ceilings.
- `_log.seq` references `_commits(seq)` (`engine/postgres/store.rs:40`). Deleting commit rows while log partitions remain will fail that foreign key. `seq` is already in the primary key, so range partitioning by `seq` is allowed.
- Seal the target schema so `serve` refuses it until the cutover transaction sets the graduation state live. Until then the partial copy already contains the production `store_id`.
- Reverse capture says “triggers, or the adapter’s family writers” (child B §7). The second option drops the missed-site guarantee §4.1 is built on. Use triggers on that window too.
- H3’s claim that Supabase Realtime authorizes each change on one thread, and H5’s claim that Convex’s Postgres backend uses the same generic shape as `sql.rs`, are UNVERIFIED from this checkout.
