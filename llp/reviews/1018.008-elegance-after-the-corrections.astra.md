## Final review (verbatim)

The useful next step is a smaller implementation batch: client-owned recovery, explicit empty effect grants, inexpensive presentation defaults, and measured acquisition optimizations. The broader mechanisms—automatic query slicing, collection provenance, and narrower policy identities—need stronger payoff evidence. The packet generally protects the right authority boundaries, but several proposals currently combine a modest ergonomic improvement with substantially more machinery.

For **LLP 1018.008, §§3–6**, the material concern is prioritization, with medium severity. Its central observation is sound: elegance comes from reusing established facts so applications stop reconstructing them. Its evidence also distinguishes historical failures from current behavior unusually well. Keep that discipline.

However, the proposed order places general presentation derivation ahead of acquisition work despite an almost exhausted client byte allocation. Generated companions bring programs, descriptors, selection logic, and lifecycle behavior. They may remove application code while increasing the platform’s total complexity. That trade can be worthwhile, but application lines removed alone cannot establish it.

Revise the near-term sequence around cheap, independently useful outcomes. Reconcile current orientation, remove the dummy-grant requirement, implement routine recovery, and profile acquisition before expanding presentation behavior. Measure table/order/selector defaults separately from generated history. A failed slicing experiment should not strand useful defaults behind it.

The parent should also distinguish an application responsibility from a product decision. Remembering to replenish platform IDs is platform work. Choosing which page of history to display, or where a pending draft belongs, can be product policy. Treating both as compiler inference risks hiding the latter rather than eliminating it. Nothing here requires reopening LLP 1019’s delivery/receipt work, LLP 1020’s successor and cost work, or LLP 1021’s effect lifecycle and witness work.

For **LLP 1018.008.000, §3**, there are two material integration gaps with high severity for the promised behavior.

First, capacity acquisition must work before there is any admitted work or held query. At the inspected baseline, `OfflineRuntime.resumeRequest` returns no request when there is no watermark, mounted answer, or queued intent. It also requires the relevant facts. Consequently, simply joining the existing resume flight does not establish a headless capacity-acquisition path. A client can need its next grant while having no observers and no pending outbox entry; the proposed call waits before creating that entry.

Make a validated capacity demand sufficient to construct the appropriate request through the existing resume route. Specify which authenticated program facts support it when there is no held coverage. Receiving capacity must not, by itself, clear a refused reset or establish renewed coverage trust. This is a concrete request-construction change, not a reason for another endpoint.

Second, demand must originate from every admission owner. In particular, an older follower inbox row can require more capacity than the writer’s selected operation. Renewing only for mounted mutation handles or the writer’s current call can leave that row blocking FIFO admission. The writer should derive demand from the oldest blocked inbox admission using the installed certificate. Apply the same principle to the actual internal consumers introduced by LLP 1019, without changing that work’s allocation policy.

There is also a medium-severity ambiguity in the three-attempt rule. “Per transition” needs an operational definition: a successful resume followed by another failed replay must not manufacture a new recovery transition and reset its own budget. Keep one attempt budget for the recovery episode across its resume and drain steps. Ordinary successful requests, notifications, and recovery-generated connection changes do not replenish it.

The proposal otherwise has the right design: one owner, immutable admitted envelopes, pure readiness projection, explicit offline intent, and finite pre-admission waiting. Include idle grant expiry with substantial unused capacity in the controls; exhaustion is not the only grant boundary. Resolve the cost of the ordinary renewal path before deleting the normal-capacity UI.

For **LLP 1018.008.001, §§3–4**, the material concern is behavioral equivalence, with medium-to-high severity. I did not find a definite disclosure bug in the stated snapshot law. Keeping every gating requirement and giving the companion independent authorization and receipts is the correct boundary.

There is, however, a concrete missing derivation: fallback argument policy. In the original `templates/chat/shared/thread.ts`, `withHistory` deliberately maps arguments to `{ conversationId, c: null }`. A slice of `conversationView` naturally preserves the primary’s cursor `c`. Those differ when the user has paginated. The existing fallback selects the history head; the generated slice would select the primary’s older page unless another rule intervenes.

Table identity, row lineage, and ordering do not tell the compiler which behavior the application wants. Keep a small explicit argument mapping initially, or specify a deliberate default with a demonstrated product rationale. Add a non-null primary cursor to the comparison against existing `withHistory`; testing independent continuation provenance alone does not cover this choice.

I would also leave `belongs` explicit in the first implementation. Matching a mutation’s inserted prefix to a query’s prefix does not automatically settle how a draft should appear in a bounded page. The current `c == null` condition already records such a presentation choice.

The simpler first slice is table/selector/order defaults plus reuse of an existing authored page function or query. One explicit fallback relation can remain. General slicing across branches and guards can follow only if that smaller version leaves meaningful duplication. Independent certification proves that a generated query is legal; preserving the primary’s authored restrictions is still a compiler-correctness obligation. A small supported syntactic shape makes that obligation easier to inspect.

For **LLP 1018.008.002, §§1–3 and §5**, the material concern is scope without surviving demand, with medium severity. Defer this feature until an actual application needs it after LLP 1019 lands. The RFC itself permits that outcome; exercise it.

The risky expansion is not the word `collect`. It is requiring provenance to survive aliases, records, helpers, branches, nested projections, and structural sinks across the compiler, certifier, and twin. That approaches a general completeness analysis for a feature whose motivating workaround is being removed elsewhere.

Before implementation, specify exactly where provenance ends. A returned list can subsequently arrive as ordinary mutation input; static source lineage cannot follow arbitrary application transport. Similarly, “storing it as a complete roster” is an application meaning, not something an ordinary list column necessarily declares. Storing a user-selected bounded shortlist can be valid without asserting population completeness.

Limit any eventual guarantee to what the engine can enforce: originating reads and their structural uses within a certified execution, existing mutation fan-out restrictions, and the query’s explicit capped result. Do not imply that an ordinary list carries a durable proof of completeness.

If a real need appears, begin with pure projection of one already bounded page, without nested reads or broader helper support. Expand only when the current IR demonstrably preserves the needed lineage. The proposed offset—deferring general list APIs and a `fn`/`proc` merger—does not remove work already being implemented, so it is not yet a concrete scope trade.

For **LLP 1018.008.003, §§2–3**, the material concern is actual effect lifetime, with high severity.

At the inspected baseline, `Ibex2Host` caches a runtime per effect source. `build_runtime` evaluates and installs the effect expression once; jobs reuse it. The host also recognizes a particular compiler-generated outer JSON-constant IIFE in `freeze_compiler_embedded_constants`. Therefore, hoisting imported helpers and captures into that outer expression does not make them freshly owned per job. Changing the generated shape can also bypass assumptions in the existing constant-freezing path.

This is a verified baseline integration fact, not a demonstrated exploit in an implementation that does not exist yet. Reconcile it with LLP 1021’s landed host before coding.

Specify placement and lifetime, not merely “one closed expression.” A straightforward compiler approach is to instantiate admitted helpers and mutable captures inside a generated invocation wrapper, so each invocation creates its own closure without reevaluating source dynamically. Alternatively, safely shared values must be deeply immutable, including any function objects exposed to authored code. Immutable constants need not be copied merely to satisfy a blanket freshness sentence; mutable state and job capabilities must not cross invocations.

Start with named function declarations and JSON constants. Supporting constant function expressions, broader initialization shapes, and sophisticated dependency forms simultaneously buys little for request construction and parsing. The proposed two-real-consumer criterion is good.

Separate `grants: []` and implement it first. It removes a misleading workaround without changing the module system or client runtime. Verify both successful provider-free execution and a refused fetch with the actual engine: compiler acceptance alone does not establish that the host accepts an empty grant set while enforcing zero network authority. Preserve private source identity and artifact separation as proposed.

For **LLP 1018.008.004, §§2–4 and §6**, the first optimization slice is the strongest cost proposal in the batch. I have no material architectural objection to §3. Its distinction between sharing immutable row values and sharing authority evidence is essential.

The medium-severity issue is leaving the batching contract partly undecided. Before prototyping a product protocol, choose one atomic accepted group for the first slice. Persist its facts and accepted continuation together; acknowledge only that durable group. Keeping partial-response acceptance as another open branch creates extra states without demonstrated benefit.

The writer-turn allowance also needs to identify the existing meter and its aggregate charge. A response below one MiB does not bound rule probes, execution time, or retained preparation work. “Several individually certified pages” is not itself an aggregate work budget. The proposal recognizes this conceptually; the implementation needs a concrete accounting rule before its cost can be assessed.

I would optimize immutable identity preparation, repeated materialization, and refresh coalescing first, then decide whether transport batching survives the comparison. The recorded operation counts justify investigation but do not identify the dominant cost.

Keep the paired experiment and separate instrumented runs. Use the proposed 20% threshold as an experiment decision rule, not a reason to reject a clear deletion with a smaller measured benefit. Under the byte ceiling, fewer representations and less code can be valuable even when host noise obscures a large latency claim.

For **LLP 1018.002, §§6–7**, the material concern is the current replay boundary, with high severity before any runtime identity change.

The older audit explicitly records that it found no predecessor-program equality check. At `c25b0ec98`, `writer_replay.rs` already accepts an optional `expected_generation` and calls `generation_rejection` before unsettled execution. Stable terminal lookup still occurs first, as required.

This does not establish that all ordinary queued writes carry that field, nor does it invalidate the historical audit. It does mean the follow-up cannot reuse its blanket absence claim. Establish which actual client envelopes carry the expectation and which successor cases it rejects before attributing an avoided conflict to narrower policy hashing. Never remove that check or omit an ordinarily present field to manufacture a successful experiment.

The proposed conservative closure is plausible, but its payoff remains weak: whole subject descriptors deliberately retain the witnessed optional-message-field conflict, while global descriptors and transitive relationships may exclude many realistic applications. The coordinated native/twin domain changes are substantial relative to a disconnected-table example.

Keep broad binding unless a common edit demonstrates useful unchanged-envelope replay with every other check intact. A smaller preliminary step is to compute candidate dependencies alongside the existing execution in a temporary diagnostic and report what would change. That can reject an unhelpful closure before adding experimental wire-domain handling. Only a convincing candidate warrants the full replay experiment. Dynamic revocation, actual row changes, coverage resets, and terminal recovery remain separate obligations.

My implementation order would be:

1. Correct orientation and permit explicit empty grants.
2. Complete demand-aware automatic recovery, including headless and follower admission.
3. Profile and remove acquisition duplication; measure the complete five-root runtime.
4. Add inexpensive presentation defaults while retaining explicit fallback cursor policy.
5. Add narrow effect-helper assembly only with two useful consumers and a resolved lifetime design.

Defer general query slicing, `collect`, narrower policy identities, and transport batching until their individual evidence earns the added machinery. None has demonstrated a byte cost yet. The 85,000-byte ceiling therefore remains a real selection constraint, not something these documents have already shown they can collectively satisfy.
