# LLP 0105 super-refine — Round 1 review

Target: `llp/0105-fly-completion-and-hosted-ephemeral.plan.md` (Status: Review, 2026-07-27), reviewed against LLP 0013, 0026, 0072, 0094, 0098, 0099 and the current code: `src/ephemeral.rs`, `src/deploy.rs`, `packages/snapback-cli/deployment-control.mjs`, `packages/snapback-cli/adapters/fly-machines-vm-driver.mjs`, the generated schemas, fixtures, guide, and the two named issue tickets.

## 1. Overall assessment

The plan's central move is correct and well-motivated: the existing process-memory ephemeral backend is already the reference implementation of LLP 0013's room-authority contract, and LLP 0013 itself states that process-local memory is correct exactly when all connections for a room are sticky to one process. Qualifying it as `single-instance-sticky-memory.v1` under the one-routed-Machine invariant — rather than building Redis/Durable Objects first — is the honest, smallest-claim answer to the design gate that `issues/shelved/20260727-hosted-ephemeral-parity.md` explicitly asked this document to decide. The authority-instance identity (`processBootId` + digest) closes a real, recorded hazard class: the LLP 0026 scope-epoch dead-code finding showed exactly how cross-incarnation version comparison misclassifies fresh entries as stale, and the plan makes that structurally impossible instead of incidentally avoided.

The lifecycle half is likewise well-grounded: the plan's observation/lease/idempotency/remote-evidence language matches the implemented closed protocol (19 operations across three schema families, `(operationId, planId, inputSha256)` idempotent replay, `remoteProviderAttestation`, and the structural noncanonical-base honesty already live in the driver). The claim boundary is disciplined throughout — `ephemeralHostedAdapter` stays false until all evidence commits, which matches all 20 committed capability manifests today.

However, the document has several material gaps: the single-routed-Machine invariant is asserted without pinning who mechanically enforces it at which plane and without recording the residual that LLP 0098 §7 records for the analogous single-instance auth invariant; §2.1 and §2.4 contradict each other on custody of `machineId`/`processBootId`; the TLS-custody claim conflates volume-preserving replacement with fresh-volume restore and collides with LLP 0072's secrets-excluded backup rule; the "old clients fail capability negotiation" claim has no mechanism under the current wire contract; the plan's operation names drift from the closed protocol enum it claims to implement verbatim; and the hosted-admission renewal posture — without which the "complete hosted target" cannot serve unattended for more than a bounded window — is never mentioned. These are document-level defects, fixable in one revision pass.

A cryptographically random per-boot identity carried in the grant and fenced per-frame makes cross-boot comparison impossible by construction, and the graceful path reuses the shipped `ResyncReason::Restarted` vocabulary (`src/ephemeral.rs:1037`, emitted at `:5202`) rather than minting new frames.

## 3. Concerns

**C1. Single-routed-Machine enforcement: undefined "routed," unassigned enforcement plane, unrecorded residual.** — Severity: High, MATERIAL.
Evidence: §1 requires "exactly one **routed** Machine" and §2.2 refuses on "zero or more than one routed Machine, ambiguous routing, an auto-scale policy capable of adding one," becoming false "before application ephemeral operations are admitted." Three gaps: (a) "routed" is never defined mechanically — on Fly, a *stopped* Machine whose config carries the production service mapping is auto-startable by fly-proxy on demand, so power state cannot be the discriminator; (b) the origin process holds no provider credentials (LLP 0072: application code has no credential capable of reading provider state), so it cannot evaluate the roster — only the control-plane driver can, and it only runs at operation time (`fly-machines-vm-driver.mjs` `observe()`), leaving the entire interval between control operations unenforced while a single `fly scale count 2` (or any out-of-band Machine creation) splits rooms across two processes mid-serving; (c) LLP 0098 §7 records this exact class honestly for the auth invariant ("A platform that silently starts a second instance during a deploy breaks the guarantee **without breaking any check in §3**... An operator MUST NOT configure rolling deploys") — LLP 0105 records no equivalent residual, yet its refusal language implies continuous mechanical enforcement.
Resolution criteria: define "routed Machine" as any Machine whose config carries the production service mapping regardless of power state, including autostart flags, and require the roster check to enforce zero such besides the active one; name the exact enforcement points (activation-time roster proof binding the capability fact to the activation generation; the cadence of control-plane re-witness, if any); and either add a data-plane binding that makes a second Machine refuse to serve (see Suggestion 1) or record the between-operations residual in §2.2/§Non-goals in 0098 §7's style.

**C2. §2.1 and §2.4 contradict each other on custody of `machineId`/`processBootId`.** — Severity: High, MATERIAL.
Evidence: §2.1 puts the full `ephemeralAuthority` object — including `machineId` and `processBootId` — into the served connection grant; §2.4 says "Machine ID, boot ID... require the gated developer/admin projection." Every client that can open a connection receives the grant, and on a public app that includes anonymous clients (`/connection/open` is a public-credential route per LLP 0094's route table), so the grant is effectively public custody for exactly the identifiers §2.4 gates. The existing custody discipline gates precisely this class ("Per-room identities, routing keys, scopes, and epochs stay on the gated admin endpoint," `inspect.public.schema.json:1467`). Additionally, UUIDv7 embeds a timestamp, so `processBootId` leaks boot wall-clock time to every connection. Note clients need only *equality* — §2.1's own rule is "Clients compare room versions only inside one exact authority instance" — so the members are not needed client-side.
Resolution criteria: the grant carries only the opaque `EphemeralAuthorityInstanceV1` digest (plus at most the profile id), with the member breakdown available only on the gated projection; or §2.4 is amended to state that grant recipients learn these identifiers, with justification. Either way §2.1 and §2.4 must agree.

**C3. TLS/Caddy custody claim conflates replacement classes and collides with 0072's secrets-excluded backups.** — Severity: High, MATERIAL.
Evidence: §3.5 claims acceptance "proves the production certificate/account/key state survives stop/start and Machine replacement without a new production issuance." That holds for volume-preserving replacement, but §3.4's restore path explicitly "creates/attaches a fresh encrypted volume" — and LLP 0072 §Backup and restore says "Provider/application secrets and control-plane credentials are excluded" from backup manifests, which Caddy's ACME account key and certificate private key are. So either Caddy key material is a backup component (contradicting 0072's exclusion unless a new encrypted-custody claim is written) or a fresh-volume restore requires a new production issuance (making §3.5's blanket claim false for the restore path). This matters concretely: the Let's Encrypt 5-per-168h duplicate-cert budget for this exact origin has already been burned once (real incident recorded in `issues/shelved/20260726-0072-fly-adapter-remaining-surface.md`: "Caddy's volume-backed cert storage evidently did not retain across the 2026-07-25 machine replacement"). Separately, the current deployment has cert state on a *cert-only* volume (`caddy_storage` mounted at `/data/caddy`, DB deliberately on rootfs per 0098 §8.4), while §1/§3.5 require one volume carrying both `/data/caddy` and `/data/app`; the transition to that layout is itself a Machine/volume replacement (0098 records that attaching a volume replaces the Machine) that must deliberately migrate the existing Caddy state or spend an issuance. §3.5's "separate directories and backup policies" leaves all of this ambiguous.
Resolution criteria: split the survival claim by replacement class (same-volume stop/start/update/replacement vs. fresh-volume restore incarnation); state explicitly whether Caddy state is a backup component and, if so, reconcile with 0072's secret-exclusion rule and name its encryption/custody; state the production-restore issuance posture and its rate-limit budget; and add the concrete migration step from the current `caddy_storage`-only layout to the single-volume layout.

**C4. "Old clients/servers fail capability negotiation" has no mechanism under the current wire contract.** — Severity: Medium, MATERIAL.
Evidence: amendment 4 asserts old clients/servers "fail capability negotiation rather than treating a new boot as the old room epoch." But `ConnectionGrant` is an *open* object where additive members are sanctioned and ignored by old decoders (LLP 0094 §0C:701); the hosted arm's decoders silently ignore unknown members — the recorded §0C hazard, live on `wireVersion` itself; and the ephemeral frame DTOs are closed shapes, so unconditionally adding a required per-frame digest member would fail old clients mid-stream with decode errors, not at negotiation. Nothing in the plan names the offer/refusal mechanics, the refusal code, whether failure is connection-scoped or ephemeral-capability-scoped (the repo's precedent — `authInvalidationProtocol`, LLP 0013's "Missing/unsupported negotiation still fails closed" — is capability-scoped), or the staged bootstrap across the local/hosted/Swift/kit arms that LLP 0094 §0B.5 shows this codebase requires for exactly this kind of change.
Resolution criteria: the LLP 0094 amendment must specify an explicit open-time offer (in the style of `authInvalidationProtocol`/`wireVersion`), the refusal code and its scope, conditional frame membership gated on the negotiated protocol, and the rollout staging across arms.

**C5. Operation names drift from the closed protocol the plan claims to implement verbatim.** — Severity: Medium, MATERIAL.
Evidence: §3 states the driver "implements every existing closed `snapback.vm-adapter-*.v1` operation. It may add no private lifecycle dialect" — but then uses `rollbackGeneration`, `restoreInactive`, and `restoreActivate`, none of which exist. The closed enum (`schemas/vm-adapter.lifecycle-request.schema.json:3-22`, `src/deploy.rs:388-406`) has `rollback`, `restoreBackupInactive`, `activateRestoredGeneration`, and the plan never names `verifyServedPath`, `fenceExternalEffects`, `verifyRestoredComponents`, or `verifyRestoredApplication` even though its prose describes their behavior. As written, an implementer cannot tell whether the plan renames the closed protocol (a schema amendment) or misnames it.
Resolution criteria: use the exact closed enum names throughout §3, enumerate the complete operation set once, and if any rename is intended, declare it as an explicit closed-schema amendment.

**C6. The hosted-admission lifecycle is absent from the journey, so "complete hosted target" overstates unattended serving.** — Severity: Medium, MATERIAL.
Evidence: the §1 target is the LLP 0098 loopback-terminated hosted-auth topology, so serving requires signed `HostedAdmission` snapshots with ≤5-minute lifetimes; the implemented renewal mode is `presignedWindow`, hard-capped at 24 hours, and `online` renewal is 0098's unresolved open question 1. LLP 0098 §8.5 records a deployment expiring by design when its window lapsed. Yet §4's eleven journey steps and §5.2's evidence rows never mention admission minting, delivery, rotation at activation/restore (each changes `deploymentId`/`configurationSha256` and so invalidates prior chains), or the serving-window boundary as a receipt fact. A "first complete hosted Snapback target" that stops serving within 24 hours absent operator re-minting is a material operational boundary the receipt and nonclaims must carry.
Resolution criteria: add admission production/delivery/rotation to the lifecycle mapping (who mints, at which steps, over which channel), state the renewal posture for the completed target, and surface the serving-window boundary in the receipt and nonclaims — or bring 0098 OQ1's online mode into scope explicitly.

**C7. `processBootId` duplicates an existing grant boot identity, and the digest construction is under-specified.** — Severity: Medium, DETAIL.
Evidence: the connection grant already carries `IssuerId { authorizationIncarnation, bootSequence, bootNonce }` — documented as "A boot identity is never reused, even when process-local counters restart" (`schemas/connection.grant.schema.json:87-109`, from the auth-invalidation subsystem). The plan introduces a second, unrelated per-boot identity without relating the two. Separately, "JCS digest" introduces a canonicalization standard the repo doesn't use — existing practice is domain-separated SHA-256 over repo-canonical JSON (e.g., `SHA256("snapback-release-manifest-v1" || 0x00 || canonical)`, LLP 0072; LLP 0098 §2.2 uses length-prefixed domain-separated input for exactly the boundary-shifting reason).
Resolution criteria: record the relationship between `EphemeralAuthorityInstanceV1` and the existing auth-plane boot identity (shared source, or why deliberately independent), and pin the digest as domain-separated over the repo's canonical-JSON convention rather than bare "JCS."

**C8. Cost-component vocabulary doesn't match the closed cost schema.** — Severity: Low, DETAIL.
Evidence: §3.5 requires "measured/declared compute, volume, artifact, backup, logs, DNS, and TLS costs"; the closed `RemoteDrillCostComponent` enum is `compute, persistentVolume, objectStorage, logs, dns, tls` (`schemas/remote-drill.plan.schema.json:38-49`) with exact-equality validation (`deployment-control.mjs:976-999`), and no receipt schema carries cost members today.
Resolution criteria: reconcile the vocabulary — either map artifact/backup onto `objectStorage` sub-facts or amend the closed enum — and name where measured cost/utilization lands (the journey receipt schema).

**C9. The "packaged" driver isn't packaged, and several journey commands don't exist.** — Severity: Low, DETAIL.
Evidence: `packages/snapback-cli/package.json` `files` omits `adapters/`, so the published package cannot run the Fly driver §3 calls "the packaged `fly-machines-vm-driver.mjs`"; no destroy/withdraw command, no cost print, no journey-receipt emission exists, and `inspectAdmin` is reachable only through the test harness while the driver refuses it in-protocol. ## 4. Suggestions

1. **Bind the LLP 0098 admission envelope to the exact `machineId`.** The control plane signs admission only for the Machine it just proved solely-routed; a second Machine then fails admission verification (`_FOREIGN`-class) and refuses hosted serving — converting C1's single-routed invariant from an observation-time check into a data-plane refusal, using machinery 0098 already ships. This also gives §2.2's "verify its new authority instance through the public TLS origin" a natural authenticated witness.
2. State in §2.2 how the driver's verification traffic traverses the public origin while "new connection admission" is stopped (health-nonce path vs. application admission), so the step ordering is executable as written.
3. Consider whether the per-frame authority digest is needed on every frame or once per drain batch/lane boundary; if per-frame is retained (defensible for fencing frames queued across a reconnect), say why, since it adds ~70 bytes to every coalesced ephemeral message.
4. Note that including `definitionGeneration` in the instance digest makes any single ephemeral-collection redefinition clear the *complete* overlay — coarser than LLP 0013's per-definition replacement barrier. Probably acceptable (hosted redefinition implies redeploy), but it should be a stated choice.
5. Add the data-durability boundary to the receipt facts: one host-pinned volume, backup-lagged RPO, restore as the recovery path — the honest counterpart to the HA nonclaim, matching 0072's "costs, downtime, retention... target limitations" receipt requirement.
6. Make the guide/capability-row endgame explicit: `realtime.ephemeral` gains exactly the qualified profile target (never `all`), with a GAP row until then per LLP 0061 §5 — §6 step 6's "guide/capability updates" is currently unspecific, and today's guide has no hosted-ephemeral GAP row at all.
