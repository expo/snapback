## 2. Language

A top-level declaration describes one table's historical input fields and its
simultaneous output patch:

```quarry
backfill bookings vehicleClass(weight: int, length: int):
  { vehicleClass: 'commercial' if weight > 3500 else 'van' if length >= 5 else 'car' }
```

The table and declaration name identify the transformation. Arguments are
typed predecessor fields, including fields removed in the candidate. Outputs
name candidate authoritative columns. Expressions use the existing interpreter:
literals, arithmetic, conditionals and deterministic string functions, plus
unique point lookups. No writes, scans, time, viewer, ids or external effects.
Inputs are read from the pre-adoption image, interpreted by the predecessor
schema. All output fields evaluate against that image before any patch applies.
Lookups read the same pre-adoption snapshot, independent of table walk order.
Missing/mistyped inputs or invalid outputs refuse the entire activation with
E_ADOPT, naming the table, backfill and row. New candidate-native writes do
not run historical backfills. Keep declarations in later releases.

## 3. Adoption and reversibility

Backfills execute inside the existing activation writer transaction, before
narrowing, projection, indexes, maintained data and generation publication.
The final ordinary validation remains mandatory. Failure at any phase rolls
back transformed rows, evidence and current release. Deploy --check executes
the same path on its private snapshot and reports exact affected counts.
Cold and hot receipts expose the same counts. Devices receive transformed
authoritative images after their ordinary generation reset, never run backfills.

Persist per-row input/output evidence keyed by declaration content and row
lifetime. Reopening unchanged source does nothing. Forward after rollback
preserves v2 edits when predecessor inputs are unchanged; older inserts and
changed predecessor inputs are caught up. Deletion clears evidence so id reuse
cannot inherit another lifetime's transformation. An edited declaration is a
new transformation, never a silent reuse of an old receipt.

When leaving a backfill, restore overwritten predecessor-visible fields from
the saved input only if the current value still equals the recorded output.
Otherwise refuse with an explicit changed-value reason; never overwrite a
post-backfill edit. Added/removed fields use ordinary dormant retention.
Rows created natively under v2 have no prior image: ordinary v1 validation
restores their view when representable and refuses otherwise. This is source
rollback, not a database snapshot or an inverse for arbitrary v2 edits.

## 4. Staging clock

Only a store durably classified staging by deploy --staging may serve with
--clock-offset. Missing/unknown classification is production. This setting
is process-local, with the same signed-duration parser and monotone elapsed
clock as dev. No source, public argument, environment variable or HTTP call
can classify a production store. Restart drops the offset unless explicitly
provided again; persisted timed-disclosure floors retain their existing law.

Staging exposes the existing /dev/clock/status and /dev/clock/advance only
with a full service session. Account, guest, read-only and unauthenticated
requests refuse. Recheck classification and session under the engine writer
before advancing. All fixture, reset, persona and dev-job doors remain closed.
Use the same advance implementation, schedule drain and ambiguous-reply law
as dev. CLI clock advance --release DIR mints its local service authority.
startServe accepts clockOffset and exposes now()/advance() through that
operator authority; it never changes store classification.
