**High — §2.1a: unconditional raw deletes rely on unenforced event-ID non-reuse.**

The RFC says an event ID is never reused. However, [`Context::mint`](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/mod.rs:173) consumes caller-supplied IDs without a lifetime-uniqueness check, and [purge retires the tombstone](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/timeline/work.rs:106). Reuse is therefore possible after purge.

Concrete probe, with horizoned reposts and an already acquired device:

1. An older, unheld repost owns event E. Commit A inserts newer repost S with event F.
2. Commit B deletes the older repost and E; let its purge finish.
3. Delete and recreate S under the same source ID, supplying E as its new event ID.
4. Serve A after all those commits. Its normalized source image is current S, paired with E. Then deliver B on a separate page.

B’s source deletion affects an unheld row, but its unconditional raw `del E` erases S’s newly paired event. S remains held with a missing event; unrepost now skips the event-removal/tombstone effects. This follows directly from [put normalization](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/partition.rs:867) and the [unconditional device delete](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-device/src/device/deferred.rs:230).

**Smallest change:** make raw deletion respect the paired image’s age. Carry its serving head through snapshot staging and deferred folding; an older raw delete must not erase an event installed from that newer paired state. Do not rely on lifetime ID uniqueness unless the design explicitly adds enforcement.

**Medium — §§2.1a–2.2: online-only event kinds fall outside the new coverage rule.**

“Partial” is explicitly assigned to a **floored** source. The ordinary-read restrictions and fourth withheld trigger activate only while either kind is partial.

**Probe:** fully sync posts; make reposts `online only`. Neither kind is “partial” under that definition. After omitting online-only repost events from acquisition, point-read an existing repost event by ID, scan `byTime`, and use the missing event in a negative mutation rule probe. The owned table remains horizonless `sync public`, so the existing [point-read logic](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/read.rs:325) supplies known absence unless the new mechanism explicitly overrides it. Implementing only the specified partial-kind override leaves false nulls, incomplete populations presented as complete, and incorrect local rule decisions.

The snapshot restriction likewise names partial kinds but leaves online-only kinds implicit.

**Smallest change:** apply conservative unscoped coverage and withholding whenever either kind is **not fully synced**, including online-only kinds. Explicitly exclude online-only kinds from snapshot delivery and raw-put application, and classify their dependencies accordingly. Preserve the exception for keys proving a fully synced kind.
