### 1c. The permission relation (`permissions/`)

- Row shape: `{ id, permission_id: number, grantee_id, grantor_id }` (`permissions/UserPermissionEntity.ts:43-48`) — scope = grantor **account**, principal = grantee **actor** (user / SSO user / robot / partner actor), role = `PermissionEnum` row (`OWN | ADMIN | PUBLISH | VIEW`, `constants.ts:14-19`). One row per (grantee, grantor, permission): the check filters the actor's rows to the named permission (`UserPermissionsUtils.ts:254-266`, `filterOnlyPermission`) and tests `p.getGrantorId() === accountId` (`:371`). **No role comparison anywhere**; implication (ADMIN ⇒ VIEW) is whatever rows the product wrote at grant time.
- Implicit grant: `if ((actor instanceof UserEntity || SSOUserEntity || PartnerProvisionedActorEntity) && actor.getPrimaryAccountId() === accountId) return true;` (`:355-362`) — a user's personal account grants everything via a column on the user row, not a relation row. "Robots can not be primary account owners" (`:412`).
- Policy on the relation itself (`permissions/UserPermissionPrivacyPolicy.ts`): create/update = omnipotent ∨ grant rule (`'permission_id', 'grantor_id'`); **read = `AlwaysAllowPrivacyPolicyRule`** (:24-25); delete = grant rule ∨ `AllowIfUserOwnerPrivacyPolicyRule('grantee_id')` ("allow a user to delete their own permissions (so they can leave an account or delete their user)", :47-48). `PermissionEnum`: read AlwaysAllow, C/U/D AlwaysDeny (`PermissionEnumPrivacyPolicy.ts:17-42`).
- Invariants outside the policy: last owner — `if (ownPermissionsGrantedByGrantorAccount.length === 1) throw` (`permissions/triggers/UserPermissionNoRemoveLastOwnerTrigger.ts:66`), skipped when `deleteCause.entity instanceof AccountEntity` (`:40`); per-actor membership cap — `if (accountIdsMutableSet.size > granteeAccountLimit) throw` (`permissions/validators/UserPermissionAccountMembershipLimitationValidator.ts:37`, limit from `grantee.getAccountLimit()` `:31`).

## 3. The five key questions

**Q1 — entities written only by the system.** Fewer than the names suggest. Omnipotent-only for *all* writes: `AppTransferRecord` (`projects/AppTransferRecordPrivacyPolicy.ts:16-38`), `DashboardChatMessage` (`:63-103`), `PermissionEnum` (AlwaysDeny). Omnipotent-only *create*: `Account`, `User`, `Session`, `InternalSession`, `SSOToken`, `Asset` (effect ingress from a GCS function), `EmbeddedUpdateAsset`, `DeviceRunSessionArtifact` (system ∨ scoped PUBLISH). Omnipotent-only *update*: `Session` (sudo flip), `EmbeddedUpdate`, `EmbeddedUpdateAsset`, `EchoTokenUsageLedger` (plus cascades). **Builds and job runs are not system-only**: created by PUBLISH viewers (`turtlebuild/TurtleBuildPrivacyPolicy.ts:31-67`), and their update rule is the same PUBLISH rule (`:148-159`) — the worker writes status as omnipotent, but nothing in the rule stops a PUBLISH viewer's program from writing `status`; EAS relies on the GraphQL mutation surface for that. **Ledger items** are omnipotent ∨ PUBLISH (`AccountBuildLedgerItemPrivacyPolicy.ts:24-61`). **Audit logs** are omnipotent ∨ PUBLISH ∨ actor, and update/delete = create (`auditlog/AuditLogPrivacyPolicy.ts:28-41, 70-71`) — mutable. Under the proposal's `update(old,next)` all four could be tightened (`next.status == old.status || viewer === system`; `appendOnly`) — a strengthening, not a gap.

**Q2 — longest association path on a read rule, and immutability.** Four directives plus the permission probe: `UpdateAssetEdge → update → branch → app → account` (`updates/UpdateAssetEdgePrivacyPolicy.ts:121-137`), `WorkflowJob/Approval/UpstreamEventPayload → run → workflow → app → account`, `WorkflowSchedule → revision → workflow → app → account` — the maximum the rule class's overloads type (`rules/AllowIfAccountActorHasPermissionOnAssociatedAccountPrivacyPolicyRule.ts:80-123`). Every intermediate link (`updateId`, `branchId`, `workflowRunId`, `workflowId`, `workflowRevisionId`, `parentBuildId`, `*_app_credentials_id`, `deviceRunSessionId`, `echoChatId`, `channelId`, and every child's `appId`) is immutable. **Exactly one link in every chain is mutable: `app.accountId`**, rewritten by transfer (`projects/AppUtils.ts:124-127`). So ruling 4's denormalization is sound for every hop but the last, and the last is the one every chain shares.

**Q3 — column-level redaction the proposal would force into a split.** One true in-row audience mix: `EnvironmentVariable` (`plaintext_value` / `encrypted_value` on one row; `SECRET` readable by no viewer, `SENSITIVE` by PUBLISH on request, metadata by VIEW/PUBLISH; redaction is done in GraphQL resolvers `graphql/types/EnvironmentVariable.ts:74-76` and `EnvironmentVariableWithSecret.ts:34-46`, decryption only in `EnvironmentVariableUtils.ts:90-97, 302-318`). Three more handled today as **public projections loaded under omniscient** rather than as row rules: build public data (`graphql/queries/BuildPublicDataQuery.ts:35-55`), Apple device registration public data (`credentials/AppleDeviceRegistrationRequestPrivacyPolicy.ts:43-44`), SSO configuration public data (`sso/AccountSSOConfigurationPrivacyPolicy.ts:14-20`). The device-facing update/asset projection (`middleware/serveUpdateResponse.ts:259-262`) is a fifth. **Credentials are not a split case**: the encrypted p12/p8/keystore/JSON columns share the row's single audience (PUBLISH) and are resolved in full through GraphQL (`graphql/types/credentials/ApplePushKey.ts:13,26`). Count: **≈5 tables** would split under E_SECRECY_MIX; ≈11 credential tables would not.

**Q4 — rules depending on a count, quota, plan tier, or time window.** **None inside any of the 171 privacy policies.** All four appear in validators/triggers/utilities on the write path: last-owner count (`permissions/triggers/UserPermissionNoRemoveLastOwnerTrigger.ts:66`), per-actor membership cap (`…AccountMembershipLimitationValidator.ts:37`), per-account app count vs `app_limit_override` (`user/AccountAppLimits.ts:102-110`), and the one that combines all three — plan tier + ledger sum over the billing period (`turtle-job-run/TurtleJobRunUtils.ts:383-405`). The first three are the proposal's constraint class (X17); the fourth needs an aggregate over a window and lowers honestly to a system-maintained counter reset by a schedule (R21).

**Q5 — NEW relative to the paper corpus.** Two things. (a) **A mutable parent scope under ruling 4's denormalization**: the corpus handled hierarchy *moves* only under Tier 2 (`nearest`/`inherits`) and snapshotted paths (`pathAtMint`); it never had "re-home a scope carrying an unbounded subtree of authorized rows" as a load-bearing, shipped operation with every child rule walking through it. Smallest bounded form: an engine `propagate`/rekey of one column along `app → *` (X13) or, as the honest interim, a transfer window (`AppTransferRecord`) during which a system job rewrites the copies in bounded batches and the app is frozen by a status column. (b) **A join of two relation probes on a free variable** (robot/token management, R19) — deeper than any Tier 2 form as written; droppable to a home-account column. Everything else is named by a tier: the system principal for effect ingress, builds, secret values, cascade nullification and metering (Tier 1); derived token-principal rows (X13) for scoped JWTs; session flags for staff/sudo/internal-read mode (X9); gated rule rollout (X16); pre-identity email invitations (events already had them); public projections keyed by unguessable ids (Coterie-style `public`).

## 4. Facet verdict

The proposal carries this facet. EAS's 171 policies are, almost line for line, the proposal's recipe: one `{grantor, grantee, permission}` relation row with independent permissions as independent rows and no role comparison anywhere; one-hop probes; literal compares; `public` reads; a reserved system principal in 164 of 171 tables — and its multi-hop chains collapse to one copied `accountId` column because every intermediate link is immutable. The single change that would flip the most rows is a ruling on the **mutable parent scope**: ≈140 rule sites walk `→ app → account`, and app transfer rewrites `app.accountId`, which is precisely the case ruling 4 does not cover; the bounded answers are an engine `propagate` of one column (Tier 2, X13) or a transfer-window system job as the interim, and EAS's own ledger tables show it already lives with the alternative (two scope columns, "app may have been transferred"). Beyond that, the tiers name everything: Tier 1 for effect ingress, worker writes, secret-value reads, deletion-cascade nullification and free-tier metering; X13 for scoped-JWT attenuation (droppable to explicit service grants); X9 for staff-mode, sudo and internal-read-mode session flags (droppable to a per-session principal or program-level gates); X16 for the unused gated-rollout rule. Genuinely NEW versus the 37 paper apps: the mutable-scope rehoming above, and one join-shaped rule (robot management) that no tier's probe form expresses and that reduces to a home-account column. Column-level secrecy is smaller than feared: one real in-row mix (environment variables) plus four public projections, while the eleven credential tables are single-audience rows that need no split.
