## Findings

### 1. Medium — D2.4 — `read.rs:840–875`

**Spelling of the record-time candidate is not a boolean, and a hurried `has_more \|\| drain_cut` is unsafe.**

The iff is `has_more` (glossed as uncut) **or** `opened_all ∧ drain_cut ∧ emitted ≥ 1`. The uncut requirement is only in the parenthetical. Concrete miss: a lazy merge of ≤ 8 lanes (`read.rs:840`, `batch = take+1`); the last lane’s opening read is meter-cut with no head (`opened_all` false); sibling lanes already hold a full buffer. Drain pops from those buffers, never refills, fills `take`, sets `has_more`, never sets `drain_cut`. The unknown lane can hold a row that belongs inside that page (lane A at 10,8; lane B’s unread 9). Publishing `next` after 8 skips 9 forever.

Today `merge_can_continue` (`:796–801`) withholds because `capped_at` is set. D must keep that conjunct on the `has_more` arm.

**Smallest change:** write the record-time predicate as

`(has_more ∧ capped_at.is_none() ∧ word_cut_at.is_none()) ∨ (opened_all ∧ drain_cut ∧ emitted ≥ 1 ∧ word_cut_at.is_none())`.

Outcome still applies only the non-uniform class, and only when the owner is a merge site.

### 2. Medium — D0.1 — `read.rs:466–468`, `:667`, `cursor.rs:107–123`

**Append-if-missing must not become a global `cursor_suffix` change.**

Direct pages over a unique index that does not end in `id` are legal (`bind/program.rs:274–277`). Their tokens use `suffix_after` only (`read.rs:466–467`, values from `take(components).skip(prefix)` at `:667`). If `cursor_suffix` grows an `id` for everyone, those tokens change length and `validate_values` / `decode_cursor_for` break; paved `…, id` merge tokens would still look fine, so the regression is easy to miss.

Merge lanes already go through `bounds()` with `scan.merge_site` set (`:547–552`, `:834`). That is the branch that should decode the longer descriptor. Eager cross-table translation (`:749–757`) keeps the encoded suffix; both tables already share columns (`bind/program.rs:528`).

**Smallest change:** one merge-position tuple — eager sort keys (`:766–767`), `MergeHead` / `key_of` (`:822`, `:31–39`), `Bounds.after`, recorded `next`, and the merge owner’s encode/decode descriptor. Direct `cursor_suffix` unchanged. Then: paved `…, id` JSON (version, table, index, order, suffix, values) is byte-identical (`cursor.rs:12, 60–78`); a pre-change v1 token whose suffix omitted `id` is `CursorError::Descriptor` once (`:116–123`).

### 3. Medium — D5.2 — `read.rs:636–638`

**The further-term path looks ahead to a second match; D5.1’s ~100 examined per one-head read does not carry over.**

D5.1 is right: filtered `take = 1` stops at the first match (`:642`), store batch is 2, every 100th ⇒ ~100 examined per opening/refill; 12×100 open, ~8,800 more to emit 100, 10,000 > 8,192; page 1 short with `next`.

D5.2 is unfiltered further terms (`:589–597`). After one match, the next match hits `visible.len() == take` and breaks (`:636–638`). Each opening and each refill examines until **two** further-term hits (or cut/end). Copying D5.1’s 12×100 (or “same assertions” without that factor) can either blow the opening budget (C1, no `next`) or never drain-cut at 8,192.

**Smallest change:** D5.2 states: > 8 word lanes; each one-head read costs ~2× the inter-match gap; opening stays under 8,192; filling `take` does not.
