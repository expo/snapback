## Round 1 — 2026-08-04

1. **[MATERIAL] Summary / evidence boundary — the prioritization overgeneralizes from one build.** “The whole gap,” “stronger on every axis,” “A is worth more than the other four combined,” “any domain … hits it on day one,” and “would have broken most games” exceed what one chess arm establishes. The evidence supports five concrete incidents in this build, not their prevalence or relative product value; D is explicitly unquantified and E was latent. Proposed fix: distinguish observed facts from hypotheses, scope comparative claims to this run, remove the minute-based global ranking, and require repeated workloads before using frequency claims to sequence large mechanisms.

2. **[MATERIAL] Whole document — this is an evidence report plus five independent RFCs.** A–E change separate authorities: guide/release metadata, CLI lifecycle, handler supply-chain policy, authenticated deployment identity, and job execution semantics. Accepting LLP 0171 would neither safely ratify those changes nor merely record evidence. Proposed fix: retype 0171 as Research or an LLP 0115 intake/plan update. Land actual decisions as amendments to LLP 0061, 0041, 0108/0009, 0058, and 0070 respectively.

3. **[MATERIAL] §A — `since:` does not provide the claimed closure proof as designed.** The existing checker knows repository witnesses, snippet sources, capability maturity, and published closure versions; it has no surface-to-package-version authority. Authored `since:` metadata can detect a stated version being newer than the closure, but cannot detect an omitted or incorrectly stated introduction version—the failure that motivated §A. Section-level “frontmatter” also conflicts with the guide’s flat page-frontmatter model, and the unit and comparison closure remain open questions. Proposed fix: decide the claim unit and authority before Review. Either describe `since:` honestly as a required authored fence, or introduce release-aware surface IDs whose package/version membership is generated from publication receipts. Acceptance needs a stale-closure fixture that demonstrably fails the checker.

4. **[MATERIAL] §B — a new lifecycle verb is not shown to be the cheapest adequate fix and creates a parallel readiness dialect.** The immediate defect is the non-TTY control channel’s `EOF → stop` behavior. `snapback dev` already owns generation, sessions provisioning, watching, structured events, signals, and the `HostReadyDescriptor`. A `--non-interactive`/`--no-control` mode that remains alive until a signal would address the observed failure with much less mechanism. The proposed stdout ready record duplicates the existing descriptor while omitting its nonce/ownership semantics, and stop behavior, stale-descriptor handling, and supervisor sharing are undecided. Proposed fix: extend the existing supervisor and emit/reference the existing descriptor; add a distinct `serve` verb only if a separately stated no-watch use case cannot be met that way.

5. **[MATERIAL] §C.2 — hashing bundler output does not preserve the existing handler properties.** LLP 0118 already explains why delegated `node_modules` resolution plus post-hoc output hashing loses deterministic regeneration, bounded reviewability, source-span diagnostics, and supply-chain admission. Final-byte scanning preserves a capability floor, not those properties. The proposal leaves lockfile custody, conditional exports, built-ins, package integrity, resolver semantics, initializer side effects, graph limits, source maps, and toolchain identity unspecified while claiming no trust-boundary widening. Proposed fix: land the documentation correction now, but move package support to a dedicated LLP 0108/0009 amendment. It must choose documented pre-bundling/vendoring or a clearly opt-in hermetic package profile with Snapback-owned resolution, lockfile and per-edge identity, strict bounds, final scanning, and cross-machine reproducibility tests.

6. **[MATERIAL] §D — the proposed “identity-bearing subset” weakens a deliberate executable-authority fence and names the wrong owner.** LLP 0058 defines deployment identity as the complete schema/function pair, including `bundleHash` and `inputsHash`; the startup carrier contains executable authority. Adding a function changes callable authority, not merely unrelated metadata. LLP 0160 explicitly owns migration experience without changing those semantics and already records watch reload as the safe sessions path. Proposed fix: retain complete-pair pinning and solve the observed loop through §B’s backgroundable live-provision path. Any cold-start successor mechanism must amend LLP 0058 and specify complete-pair preflight, atomic activation, admission fencing, and live-authority invalidation. Also correct the diagnostic claim: current guidance says expected and observed deployment identities are already carried; a field-level diff would be an incremental improvement.

7. **[MATERIAL] §E — the diagnosis is partly false and the alternatives have materially different safety semantics.** A successful product row exposes `attemptCount`, so a retry is visible; the operator surface already exposes complete append-only attempt history. What product code lacks is the prior diagnostic cause, not evidence that a retry occurred. Raising the generic default above one silently opts external-effect actions into replay, while making reservation contention “free” needs its own finite budget, authority-generation pin, jitter, and effect-safety rule. The existing client retry contract is deliberately mutation-only and retries only the exact `effectCommitted:false` refusal. Proposed fix: state the visibility gap accurately, then separately decide observability and execution policy. Prefer a bounded, stage-aware reservation retry only where the platform can prove the failed operation committed no effect; do not raise the generic job default based on this one push workflow.

8. **[MATERIAL] Acceptance — the cold-agent run is a benchmark, not conformance for the proposed designs.** It is model-, cache-, network-, and package-manager-dependent; “nothing written outside the app directory” is incompatible with ordinary package caches and temporary runtime state. It also cannot prove hermetic package resolution, deployment-authority preservation, retry bounds, or guide-checker completeness. Proposed fix: retain the cold run as periodic comparative evaluation, but add deterministic acceptance per owner: stale-closure fixtures for A; EOF/signal/descriptor lifecycle tests for B; reproducibility and adversarial package tests for C; same-database successor and negative authority cases for D; and bounded contention plus external-effect safety cases for E.

What is good: the RFC records unusually specific field evidence, names stable diagnostics, separates the immediate §C documentation fix from later mechanism, preserves the no-eval/determinism goals explicitly, routes work toward existing owners, and treats the end-to-end authoring loop as something worth measuring. Those parts should survive the split.
