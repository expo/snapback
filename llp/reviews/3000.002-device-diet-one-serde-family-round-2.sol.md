## Findings

### Medium — Owned-tree adapters now impose the text parser’s depth limit

**File:** `snapback4/crates/snapback4-core/src/json_codec.rs:48-68`

**Scenario:** A Rust caller supplies a programmatically constructed `serde_json::Value` nested beyond the text parser’s depth limit to the owned dispatcher. Baseline `serde_json::from_value` traversed that existing tree without the text parser limit; the new adapter stringifies it and calls `from_text`, returning a recursion-limit error. `to_value` has the analogous problem because it serializes and reparses.

The advertised depth test does not catch this: `tests/codec.rs:35-40,108-110` only encodes values that first survived `from_str`, and only calls `from_value` when the same text could already be parsed into a tree.

**Smallest fix:** Add tests using a programmatically constructed deep `Json`, then use a `StrRead` deserializer with recursion limiting disabled specifically for the rendered owned-value adapters. Keep ordinary `from_text` bounded.

### Medium — The route probe can report “Page” while the production path builds a whole tree

**Files:** `snapback4/crates/snapback4-device/src/call.rs:159-171`; `tests/codec/route.rs:8-13`

**Scenario:** Replace the fast return with:

```rust
#[cfg(test)]
ROUTE.set(Route::Page);
return Ok(call(device, json_codec::from_text(request)?));
```

All behavioral tests still agree, the route assertion still sees `Page`, and `--check-families` still sees only text-derived Snapback families because the owned dispatcher itself funnels back through text. Nevertheless, every large page is materialized as `Json` and rendered again, violating S1’s no-whole-page-tree requirement and reopening the acquisition-risk class.

**Smallest fix:** Couple observation to the costly adapter itself—for example, count test-only invocations of the owned-value conversion and assert zero for direct page calls and nonzero for duplicate-field fallback.

### Medium — `--check-families` enforces duplicate families per Snapback type, not one global typed family

**File:** `snapback4/scripts/attribute-wasm.mjs:31-40,47-83`

**Scenario:** Restore a direct owned-tree decoder only for `Vec<String>` at the `newIds` or `withdraw` call site. `derivedTypes` ignores it because the type does not start with `snapback4_core::` or `snapback4_device::`; all tests remain green and `--check-families` can also remain green. Likewise, a direct-only Snapback type with no text instantiation has one family for its key, so line 82 does not classify it as a duplicate.

Fully inlined family code is another unavoidable blind spot of the surviving-symbol approach.

**Smallest fix:** Aggregate recognized concrete families globally, include relevant standard/container instantiations, and reject any non-text decoder or nonstandard writer except the exact counting-writer exceptions. Add a single-owned-family and `Vec<String>` mutant test.

### Low — Dirty provenance omits the compiler pin and budget input

**Files:** `snapback4/scripts/measure-wasm.sh:8-12`; `snapback4/rust-toolchain.toml:1-6`; `snapback4/metrics/wasm-budget.json:1`

**Scenario:** Modify `rust-toolchain.toml` or `metrics/wasm-budget.json` without committing, then measure. The former changes the produced artifact; the latter changes the budget recorded in the metric. Neither path is queried by line 9, so the appended record says `dirty:false` and carries the HEAD SHA.

For paths currently included, `dirty:true` is unambiguous and cannot reasonably be mistaken for clean.

**Smallest fix:** Include both files in the status pathspec and exercise each in the stub test.

### Low — SQLite compatibility test does not prove raw row/outbox bytes were not rewritten

**File:** `snapback4/crates/snapback4-device/tests/codec/old_store.rs:120-149`

**Scenario:** Add SQLite-only open logic that decodes and canonically reserializes `r.data` and `_device_outbox.entry`. The query and `queued()` checks remain semantically equal; lines 146-147 inspect exact base and staged values, but no raw row or outbox value. The test can remain green despite those rewrites.

Memory is stronger: exact export plus the first-drain assertion at lines 39-52 catches record loss, resets and re-emission.

**Smallest fix:** Snapshot and compare the raw `r`, `_device_outbox`, `_device_base`, `_device_snapshot`, and relevant metadata rows before and after SQLite open.

## Required explicit answers

**Did a fix introduce a new problem?** Yes, in the evidence machinery: the route marker can be true while the fast-path property is false, the family checker permits some second families, and dirty provenance omits build/measurement inputs. I found no behavior regression caused by sharing `PageArgument` itself.

**Is there a regression test that would also pass without the change it claims to test?** Yes. The route test passes the marker-preserving parse-to-tree mutant; the synthetic family tests pass a production `Vec<String>` owned-tree regression; and the SQLite fixture passes semantic-preserving row/outbox rewrites. The compatibility fixture intentionally passing the baseline is appropriate—it tests preservation, not S1 wiring.

The fix adds roughly 3 seconds for the codec target and 3 seconds for the instrument tests according to `JOURNAL.md:29054-29058`. Device-target timings vary from 344 to 850 seconds, so there is no paired evidence isolating added `call_text` test overhead. The post-fix full blocking suite did not complete (`JOURNAL.md:29073-29075`), but I found no concrete new runtime regression from source inspection.
