**Finding 1 — High: exponential shape expansion remains outside loop widening.**

Location: [aggregate_provenance.rs:285](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:285), with owned recursive values at [line 12](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:12) and unconditional unused-helper analysis at [line 100](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:100).

Concrete scenario: declare an unused helper with `x0 = 0`, followed by 30 bindings of the form `xN = { a: xPrevious, b: xPrevious }`, then `return 0`; the only query returns `0`.

Every name lookup deeply clones its provenance tree. Consequently, `x30` contains `2^31 − 1` abstract nodes despite roughly thirty source statements. There is no loop to invoke widening, and helper caching cannot help the first interpretation. An otherwise trivial check can exhaust memory solely to produce optional diagnostics.

Smallest safe fix: bound abstract expansion and abandon affected all-writers proofs conservatively as UNKNOWN before allocating excessive trees. Structural sharing plus memoized operations is another solution. Add this unused branching-shape regression; the existing single-field-depth test does not exercise it.

**Finding 2 — Medium: statement branches lose caller control at write sites.**

Location: [aggregate_provenance.rs:174](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:174), [line 408](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:408).

Using the public `posts.score` schema and literal initializer from the existing `INCREMENT` fixture:

```quarry
mutation adjust(postId: posts, increase: bool):
  p = posts[postId] ! else NOT_FOUND
  if increase:
    update posts[p.id] { score: p.score + 1 }
  else:
    update posts[p.id] { score: p.score - 1 }
```

Both writes are recorded as READ plus AMBIENT. The argument condition influences merged local bindings and returns, but never these write facts. The note therefore fires although the caller chooses the resulting value. Rewriting the same operation as `p.score + (1 if increase else -1)` suppresses it, as the calibration rule requires.

Smallest fix: carry value-selecting control provenance into branch write facts, including helper writes, and ensure caching preserves that context. Add equivalent statement/expression regressions. A conservative UNKNOWN result is preferable to claiming read-only provenance.

**Finding 3 — Medium: sorting can hide argument-dependent element selection.**

Location: [aggregate_provenance.rs:350](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:350), with field extraction at [line 25](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:25).

With the same schema:

```quarry
mutation adjust(postId: posts, offset: int):
  p = posts[postId] ! else NOT_FOUND
  choices = [{ key: offset, delta: 1 }, { key: 0, delta: -1 }]
  selected = first(sort(choices, 'key')) ! else EMPTY
  update posts[p.id] { score: p.score + selected.delta }
```

Negative versus positive `offset` selects opposite deltas. However, `sort` simply returns the original provenance: ARGUMENT remains confined to `key`, while `selected.delta` is AMBIENT. Adding it to `p.score` produces a false note. This is the same selection-influence problem repaired for `slice`, through another supported operation.

Smallest fix: propagate the sort-key fields’ provenance into reordered elements and their nested fields, or conservatively return UNKNOWN where selection dependence cannot be represented. Add ascending/descending and nested-field controls.

These are behavioral and compile-cost findings, not wording-only changes.
