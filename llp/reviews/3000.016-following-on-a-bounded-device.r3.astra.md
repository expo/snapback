Three changes remain necessary:

1. **High — §2.2 and §7: the existing fallback still contradicts the withheld-page contract.**

   The desired outcome is stated, but delegating it to the “existing fallback” repeats the revision-2 mistake. [The client’s loading branch](../../snapback4/packages/snapback4/src/local.ts:991) calls the server before consulting pending predictions. Keeping `unknown` plus data instead publishes the local holes offline or while prediction blocks fallback. Queries classified as server-run take an earlier route again.

   **Scenario:** row 3 needs an unheld original; an own post has predicted. Converting the local result to `loading` and reusing the named fallback publishes a server page without the predicted post. An `online only` shaped query also currently uses remembered/offline-refusal behavior rather than the promised offline `loading`.

   **Smallest change:** explicitly specify one routing precedence for unavailable Following queries: no `data` or `next`; offline or any predictable, unobserved outbox entry → `loading`; otherwise retry original arguments, with transport failure returning `loading`. Apply it before the loading and server-run shortcuts. Preserve the existing [local-commit invalidation fence](../../snapback4/packages/snapback4/src/local-reads.ts:9), which already retires earlier in-flight answers. Add G1’s actual disposition to §7.

2. **Medium — §4, increment 1: the implementation plan reinstates the rejected owned-event floor.**

   §2.1 says owned events remain fully synced; §4 still directs implementation of “the derived floor on owned events.”

   **Scenario:** an implementer follows the increments and retains only the newest event. P’s card remains held, but its original event disappears from the device; reposting P queues instead of predicting. A missing event for an excluded reply likewise becomes undecidable instead of a local refusal. The [transition requires that original-event lookup](../../snapback4/crates/snapback4-core/src/engine/timeline.rs:116).

   **Smallest change:** delete the derived-event-floor instruction from §4. State there that owned events remain fully synced for every source residency.

3. **Medium — §2.2: meter cuts and horizon uncertainty are not cleanly separable as written.**

   The new text says meter cuts do not make a page unavailable. However, [the existing coverage calculation](../../snapback4/crates/snapback4-core/src/engine/read.rs:1040) can mark a short, capped scan unknown without reaching the floor.

   **Scenario:** hold the newest 1,000 copies, request 40, and exhaust the examination meter after ten candidates well above the floor. The page is short and its nominal range extends below the floor, so current coverage becomes unknown. Converting every such unknown to unavailable loses the partial-page behavior §2.2 promises. Conversely, heap/scalar exhaustion already legitimately makes an answer [unavailable](../../snapback4/crates/snapback4-core/src/engine/runner.rs:276); the blanket sentence must not reverse that.

   **Smallest change:** distinguish a safely resumable, known prefix cut by the meter from actual missing coverage. Preserve partial data only for the former; preserve existing heap/scalar unavailability. Require coverage calculation to account for the actual cut position. Also retain the full boundary-page case: its `next` can lead outside coverage without making the current page unavailable.
