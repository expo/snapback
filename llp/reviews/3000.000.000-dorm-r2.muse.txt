This is a design-only review of the §19 snapshot `58176d6a...`. No code inspected, no tests run.

## Summary

The proposal correctly preserves several laws: atomic activation with projection, preimage-wins, refuse-don't-invent on missing/meter/authority failure, no inferred coercion, disjoint writers checked before adoption, prune/expiry clearing evidence, preview not mutating live state.

It is not yet implementable as written. There are material authorization, determinism, and merge ambiguities.

## Blocking findings

### 1. Cross-compiler source identity breaks immutable definitions — forward/release correctness

19.4:

> Compiler reports/metadata do not change source identity... Actual compiler semantic fixes can change execution without minting a new source id.

This contradicts the cited law: backfills use immutable definitions plus per-lifetime preimage/cohort evidence.

Counterexample: retained source S validated under compiler V1. V2 fixes `! else` missing-point semantics or point-index uniqueness. On reactivation, S recompiled under V2 either refuses previously-accepted data, stranding rollback, or computes a different reverse/backfill value for identical inputs, invalidating saved preimages and "exact retained native cells win."

Smallest correction: source identity must include compiler semantic version, or cross-compiler selection must require explicit re-derivation and re-validation proof. Do not permit silent execution change without a new source id.

### 2. Reverse synthesis can widen confidentiality — authorization

19.1 runs reverse under system authority before visibility closure, then materializes into the older view. 19.2 only warns on broader old rules and explicitly adds no confirmation.

Counterexample: `explanations.explanation` narrowed in the newer release. Declared `down extensions legacyReason` copies it to old `extensions.reason`, readable under the old broader predicate. 19.3 counts precede read rules and do not isolate synthesized exposure. Preserving captures does not help because exposure is via old read rules over newly written cells.

Smallest correction: previews must list reverse-synthesized cells as new exposure separately from pre-existing broader access, and rollback that increases user-visible exposure via synthesis must require an explicit acknowledgment flag. Alternatively, forbid projecting a cell narrowed in the newer source into a broader old view unless the declaration proves predicate containment.

### 3. Reverse outputs over references/authority/assets underspecified — authorization/lifetime

19.1 says identity, reference lifetime, captured authority, asset and engine-owned fields "retain their existing safety boundaries" without stating the rule.

Counterexample: a future reverse declaration outputs a reference-typed old cell derived from a newer row. What parent lifetime binds it? Is it invalidated on parent deletion per retained-ref law? The example uses text, so the gap is latent but general.

Smallest correction: state the closed rule. For example: reverse outputs must not create reference/asset/captured-authority/engine-owned cells, or must carry explicit parent-lifetime binding with deletion invalidation. "Retain boundaries" is not implementable.

### 4. Forward merge after reverse is ambiguous — data loss

19.1 says both:

> Compatible forward restores those cells... Unrelated edits under the older source survive.

Counterexample: row R has projected fields A,B and unrelated field C. Under the old source, operator edits C and also touches A'. On forward, "restores those cells" suggests overwriting A',B with retained newer images, while "unrelated edits survive" suggests keeping C. The retained set, merged set, and refusal predicate are not defined per cell.

Smallest correction: define per-cell merge: restored set equals exactly retained newer projected cells plus reverse result; all non-overlapping old-source writes preserved; any overlap with retained/projected cells refuses atomically. State it formally.

### 5. Predicate-only rollback conflates operator capability with user exposure — authorization

19.2 justifies no new confirmation because the operator is the same-UID filesystem owner.

Counterexample: operator narrows a predicate, then rolls back to the older broader predicate. All release-T users regain broader visibility. Filesystem edit capability does not authorize widening other users' reads via a supported operation.

Smallest correction: keep predicate-only non-refusal for captures, but require explicit broader-exposure acknowledgment, not only a warning, when target rules are broader.

### 6. Inspection cannot distinguish null from absent — implementability

19.4: retained-cell record contains id plus retained cells, "with unprovided columns null."

Counterexample: operator verifying 19.3's "originally null restored intact are not losses" cannot distinguish genuine null from dormant-absent in `--dormant` output.

Smallest correction: include per-column presence/status metadata in the generated inspection relations.

### 7. Disjointness and future-risk checks need per-activation scope

"Reject overlapping declarations before any adoption work" can be read as once-at-declaration. Target schemas evolve, so overlap must be rechecked every activation against the selected target.

"Conservative future-write risks" in 19.3 has no soundness bar.

Counterexample: widened enum domain with no old mapping is missed, then a later write silently becomes rollback-hidden.

Smallest correction: require per-activation disjointness validation, and define conservative as no false negatives for new tables, widened domains, and missing old fields; false positives allowed.

## Non-blocking notes

Alias `both-supplied refuses even if equal`, `deprecated`-as-rename repair forbidden, one-snapshot simultaneous projections, `renamed from` identical-types-only, and E_ADOPT for missing required cells are all correctly fail-closed.
