### Findings, most severe first

**1. Medium, executor (lifetime).** `snapback4/packages/snapback4/src/progressive-writes.ts:113-120` and `:139-141`. A sign-out or viewer retirement resolves the device-close promise only when the device's own `signOut()` reaches its internal `client.close()`. If `endSession` rejects first (`forgetSession` through the app's scoped store, or `media.clear()`, both storage failures the corpus treats as ordinary), `local.ts:1668-1678` throws before `client.close()`, so `endDevice` never runs, `ending` never settles, the `holdClose` taken at `:105` is never released, `openingWork` is never drained, and the lifetime stays in `retiring`. The base code used `Promise.allSettled([ending, recovering])` with `finish()` in a `finally`, so this is a problem the repair introduced. Scenario: app.ts cancels a scope during opening and calls `cleanupScope(scope, () => raw.signOut())` with no prior `pause()` (app.ts:736, 786, 861, 887), IndexedDB rejects the session delete, the response hold leaks and no later `close()` arrives to run the `cause === "close"` branch. For cause `viewer` the rejected `signingOut` is also never awaited. Smallest fix: when `signsOut`, chain `Promise.resolve(this.original?.signOut()).catch(report).finally(() => this.endDevice?.())` so a failed device sign-out still closes the device and lets the drain reach `cleaned`.

**2. Low, row (P3) against LLP 3000.013 §6.** `settlement-reducer.ts:117-118`. On `observed`, `state.outcome = state.certificate?.outcome ?? event.receipt`, so an own failed store refusal retained as the certificate outranks a peer-persisted `sent` receipt and the publication carries `cut: undefined`. §6 rules the opposite for unknown-outcome refusals: a success-qualified sequence proves success. The base executor took the cut from the observed receipt's `seq`. I could not construct a reachable journal case: the server checks the request store before idempotency, and the restore path fences reads. Record it as a row deviation or add the row: when the stored certificate is a failed store refusal and the observed receipt is `sent`, the receipt supplies outcome and cut.

**3. Low, executor.** `app-online.ts:335-350`. The caller does still receive a refusal, and the new check correctly stops an intent being pushed behind a completed retirement, so the change is net positive. Smallest fix: return a marker from the transaction and route it through `refusedCapture()` so retirement failure still keeps the record.
