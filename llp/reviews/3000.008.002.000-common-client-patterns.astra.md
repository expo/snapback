## Direction check of LLP 3000.008.002.000 — GPT-6 Astra (max)

**Verdict:** RIGHT WITH CORRECTIONS

### Summary

The RFC targets real client-composition problems and mostly assigns responsibility correctly. Its most consequential mistake is accepting a grader complaint that contradicts the benchmark’s explicit recipient policy. The first implementation target should be **the generated Expo starter running on web with `createApp` and `webDevice`**, matching the evidence run. Composition first remains the right default, but probes already establish a missing early admission boundary and show why lifting a media viewer is insufficient without explicit lifetime enforcement. Fold those corrections into the RFC and implement a small, demonstrated set of client patterns.

### Findings

#### F1 (High) — The proposed Clique receipt correction contradicts the brief

- **Where:** RFC §1, §5 and §8, especially [RFC:150](/Users/ccheever/projects/snapback-ccp-review-astra/llp/3000.008.002.000-common-client-patterns.rfc.md:150); [benchmark brief:500](/Users/ccheever/projects/snapback-ccp-review-astra/benchmarks/briefs/social-messenger.md:500).
- **What is wrong:** The RFC instructs implementation to follow the grader rather than the diary’s interpretation. Here, the grader is wrong. The brief defines membership at send time **with an explicit exclusion for members who leave or are removed before reaching a receipt state**. Keeping departed unread members permanently in the aggregate requirement would regress the requested product behavior.
- **Evidence:** The run’s frozen [instrument:500](/Users/ccheever/clique-sb4-20260925-astra-cal21/lanes/astra-snapback4/instrument/social-messenger.md:500) contains the same departure exclusion. [Grader d-01:804](/Users/ccheever/clique-sb4-20260925-astra-cal21/lanes/astra-snapback4/grading/grader-report.json:804) calls precisely that behavior a defect. The implementation filters out later joiners and computes progress over remaining eligible members at [schema.q:223](/Users/ccheever/clique-sb4-20260925-astra-cal21/lanes/astra-snapback4/snapback/schema.q:223). Its [recipient proof:35](/Users/ccheever/clique-sb4-20260925-astra-cal21/lanes/astra-snapback4/scripts/recipient-proof.mjs:35) deliberately verifies advancement after removing the unread member.
- **Proposed change:** Correct the ledger and acceptance wording to “send-time cohort with the brief’s departure exclusions.” Distinguish **removing someone from aggregate eligibility** from falsely recording that person as having read. Preserve tests for later joins, departures and monotonic progress. Do not build a different receipt policy to satisfy d-01.

#### F3 (Medium) — Durable admission exists, but the prompt admission-completion signal does not

- **Where:** RFC §3’s “after admission … allow another send”; [local.ts:1177](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/local.ts:1177), [local.ts:1194](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/local.ts:1194).
- **What is wrong:** Existing recovery APIs do not make `await mutate()` or `await useMutation.run()` an early admission boundary. When online, the local client waits for settlement or a four-second timeout **after** durable admission. A composer built around that await still stalls on a slow connection.
- **Evidence:** With the current TypeScript client and published process-device runtime, a held mutation response produced: durable admission at **2 ms**, `client.write(id)` reporting pending, but `mutate()` returning pending only at **4,002 ms**. `onWrite` reports terminal outcomes only ([contract.ts:203](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/contract.ts:203)). `MutationPromise` exposes immediate refusal fields, not successful admission ([contract.ts:166](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/contract.ts:166)). Synchronous web capture is internal, and native admission is asynchronous ([admission.ts:5](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/admission.ts:5)).
- **Proposed change:** Treat this as the reproduced gap permitting a **small SDK addition**: an explicit admission result/notification for clients offering durable custody. Preserve existing awaited mutation-result semantics and terminal recovery. Carry the signal through `createApp` wrappers and distinguish confirmed admission, definite rejection and uncertainty. Do not make applications poll `write(id)` or inspect private journals. The existing storage-error path itself warns that admission can be unknown ([local.ts:1189](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/local.ts:1189)).

#### F4 (Medium) — A surviving one-view handle is not an authority or expiry subscription

- **Where:** RFC §6; [RFC:171](/Users/ccheever/projects/snapback-ccp-review-astra/llp/3000.008.002.000-common-client-patterns.rfc.md:171), [AssetRead contract:158](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/contract.ts:158).
- **What is wrong:** Moving ownership above list rows solves premature disposal, but does not establish a legal viewer lifetime. “Expiry, revocation … continue to apply” needs a concrete mechanism. The existing transient handle is caller-owned; it does not notify the caller when its home becomes unavailable.
- **Evidence:** One-view responses bypass ordinary retention at [local-assets.ts:133](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/local-assets.ts:133); ordinary cache entries receive the tracked handles and reconciliation behavior. `useAsset` disposes on ID/client change or unmount, not an independent home-revocation event ([react.tsx:369](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/react.tsx:369)). My probe consumed a one-view asset, cleared its home column and synced: the server returned **404**, while the held blob still returned **200**. It remained readable after client close until explicit `revoke()`. The benchmark requires purge after synced revocation ([brief:65](/Users/ccheever/projects/snapback-ccp-review-astra/benchmarks/briefs/social-messenger.md:65)). The run’s lifted viewer renders its saved URL independently of the message list and cleans up only when replaced/unmounted ([Conversation.tsx:65](/Users/ccheever/clique-sb4-20260925-astra-cal21/lanes/astra-snapback4/src/Conversation.tsx:65), [Conversation.tsx:217](/Users/ccheever/clique-sb4-20260925-astra-cal21/lanes/astra-snapback4/src/Conversation.tsx:217)).
- **Proposed change:** Specify an interaction owner keyed to the account, message and asset, with independent authorized home/expiry observation. Preserve the interaction across list recycling; dispose handles and copied URLs on definitive deletion, clearing, expiry or account change. During uncertainty, rendering must follow the permitted read state. Do not refetch a one-view asset to validate its lifetime. First compose this explicitly; add narrow SDK invalidation support only if that composition cannot meet the witness. No new media cache is justified.

### Recommended implementation increment

Correct F1’s RFC policy and acceptance expectation before changing receipt code. Then implement in this order:

1. **A complete send/recovery flow in generated Expo-on-web.**  
   **Files:** `apps/chat-expo/src/Thread.tsx`, shared starter intent presentation, `apps/chat/src/Composer.tsx`, and the narrow admission surface in `contract.ts`, `local.ts`, `app-online.ts` and client wrappers. **Size:** Medium; one SDK boundary plus starter integration.  
   **Verify:** Three sends before settlement; A refused after B starts; storage refusal while typing another revision; hard reload; lost acknowledgement; unknown receipt; account switch. Preserve original IDs and correlate predicted/observed rows through an explicit application identity. The existing Vite reference storage is already backend/principal-scoped ([state.ts:6](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/apps/chat/src/state.ts:6)).

2. **Make that flow discoverable from the published entry points.**  
   **Files:** `crates/snapback4-lang/src/guide.rs`, the appropriate `guide/` card, package `README.md` and `CLIENT-AND-OPERATIONS.md`. **Size:** Small.  
   **Verify:** `guide client` resolves usefully; the documented code matches generated output; a cold builder can locate admission, settlement, observation and saved-ID recovery without reconstructing the client reference.

3. **Carry stable routing and independent decorative reads through the Expo example.**  
   **Files:** `verbs/init/expo-app.tsx`, Expo `Inbox.tsx`/`Thread.tsx`, corresponding web example and guide. **Size:** Small to medium; mostly composition.  
   **Verify:** Loading profile/query states do not destroy draft or route identity; an unavailable unread aggregate does not remove an authorized conversation; definitive revocation still hides protected content. Defer **background acknowledgement scans**, not navigation or composing, during initial acquisition. The late scale evidence directly supports this priority ([diary.md:31](/Users/ccheever/clique-sb4-20260925-astra-cal21/lanes/astra-snapback4/diary.md:31)). 4. **One policy-explicit acknowledgement recipe.**  
   **Files:** Starter schema, conversation/visibility component and guide; extract a reusable hook only after the recipe passes. **Size:** Medium.  
   **Verify:** Sparse visibility, pagination, remount, failed admission, lost response, multiple devices and membership changes. Record progress only after admission; the run currently adds IDs to `seen` before calling the acknowledgement operation ([Conversation.tsx:72](/Users/ccheever/clique-sb4-20260925-astra-cal21/lanes/astra-snapback4/src/Conversation.tsx:72)). Make conversation-view versus individual-message visibility policy explicit. Use existing `sequence by`; its positions are shared with membership insertions, so “contiguous messages” must not mean consecutive integers ([writes card:249](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/crates/snapback4-lang/src/guide/writes.rs:249)).

5. **A media interaction owner with an explicit disposal contract.**  
   **Files:** Starter thread/viewer components; `react.tsx` or `local-assets.ts` only if the demonstrated lifetime gap requires SDK support. **Size:** Medium.  
   **Verify:** A list refresh preserves the same consumption; clearing/deleting the home and syncing removes the viewer; known expiry works offline; account switch fences late fetches; copied native data URLs are dropped. Browser proof comes first; native viewer/background claims require an actual native witness.

**Do not build:**

- An immutable recipient requirement that keeps departed Clique members blocking receipts.
- Another outbox, application resend loop, protected-result cache or global acquisition gate.
- A generic maximum-visible-ID acknowledgement helper, replacement router, or global change to latest-write hook semantics.
- A new media-cache abstraction or another ephemeral transport implementation.

### What the RFC gets right

The SDK/starter/schema responsibility split is sound. The distinction between admission, settlement and authorized observation is essential, as are immutable retry arguments and honest unknown outcomes.

Stable component ownership must preserve permitted user state without preserving unauthorized query results. Existing `AppProvider` already remounts account-owned state on account changes ([react.tsx:17](/Users/ccheever/projects/snapback-ccp-review-astra/snapback4/packages/snapback4/src/react.tsx:17)); this work should compose with it.

The ephemeral hand-off is sound. Carry through LLP 3000.017’s explicit **separate-query rule**: joining typing into the inbox would move that whole read to the server and break cold-offline behavior ([3000.017:283](/Users/ccheever/projects/snapback-ccp-review-astra/llp/3000.017-ephemeral-tables.rfc.md:283)). Its transport already owns ordering and durable-queue bypass; this RFC should own only activity binding and presentation.

The qualification posture is also right: published cold-builder evidence, actual browser behavior, and separate native runtime proof.
