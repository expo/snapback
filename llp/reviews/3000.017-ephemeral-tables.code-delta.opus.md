## New findings

**N1 (Low): the online client can adopt stale `/schema` facts after a poll reports the new generation.**
- **Where:**
  - `adopt_at` rebinds the hub (`engine/mod.rs:513`). The publisher then sets `wake.generation` and wakes polls.
  - `shared.bound` and `shared.generation` are written only later (`serve_adoption.rs:174-191`). In between come the reader invalidation and, when `reopened || rebuilt`, `native::install`.
  - `/schema` (`serve.rs:922-930`) reads those two without the engine lock, and persona auth doesn't take it either.
  - The client's poll loop then calls `refreshBackend()` and sets `generation = backend?.generation ?? json.generation` (`client.ts:586-590`).
- **What goes wrong:**
  - A poll can report generation N+1 while `/schema` still serves generation N.
  - `refreshBackend()` then returns true with the old facts and matches the watch interests against the old operations. `generation` stays at N.
  - The server entered the next poll at N+1, so that poll holds. It answers only on a durable commit, a write to the stale table, or the 25 s wait.
  - Until then, a watch whose query moved from `typing` to `viewing` misses `viewing` writes, the same symptom as Astra's F1.
  - This is new in the fix diff: before it, the online tier never read `/schema`.
- **Exposure:** narrow, and I did not reproduce it.
  - Without a native install the window is microseconds. My probe ran 12 adoptions, switching `typingIn` between `typing` and `viewing`, and fetched `/schema` immediately after each poll answer. 0 of 12 were stale.
  - The window widens to the length of `native::install` when a dev adoption rebuilds or reopens a native module. It clears itself within 25 s.
- **Fix:**
  - Client: treat `next.generation < json.generation` as not yet adopted. Retry `/schema` with a short backoff, and don't accept its generation until it catches up.
  - Or server: publish `bound` and `generation` before the hub rebind.
  - Add a mock test with a delayed `/schema`, like the existing test that capability discovery cannot swallow a generation invalidation.

**Checked, no finding:**
- **Capability header:**
  - It is emitted only when the hub has ephemeral tables, and CORS-exposed (`serve.rs:597-603`).
  - Streaming polls write it at the first heartbeat, so it is discovered before any answer.
  - Non-streaming clients (React Native) drop the first header-bearing poll answer when the poll is reissued. A seq change is re-delivered immediately and a generation change within the 2 s short poll, so this costs only latency.
- **Renewal guard:** guards may point-read only durable tables (`renewal.rs:63-64`). An ephemeral write cannot change a durable guard's outcome.
- **Rate key:**
  - `bearer_token` strips `Bearer ` and trims the token, and tiny_http already trims header values.
  - So it yields exactly the token `principal_of` authenticated, and any accepted header parses here.
  - There is no fallback to the shared persona bucket.
- **Adoption reconciliation:** both tiers reconcile every mounted watch, removing stale interests and reissuing the poll when the set grows. The local tier retries its loop until `/sync` and `/schema` agree.
- **Route-verification sites:** tickets there live in memory, so the helper only adds one engine lock, two SQLite reads and a poll wake per idle 100 ms claim-loop iteration. Base already woke polls at that rate.
