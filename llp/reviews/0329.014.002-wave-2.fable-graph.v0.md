### 2. Schema in v0

Three v0 facts shape it. Column tiers become tables (row rules only). "At most one *current* row" becomes `interval` + `exclusion` or a keyed side table (`unique`/`cap` have no `where`). Reachability is written once, as `hop2`, which **v0.1 cannot spell** (§6 L1); the listing uses the L1 form `any(index, prefix, { take, where })`, admissible only because adjacency carries `cap 5000`, making the probe count a compile-time fact.

### 3. Operations in v0

#### §5 Ops 1–4, 11 — connections

Plans as written. Op 1: `db.get(memberCards, args.toMemberId)` is rule-mediated, so hidden and missing targets return the same `null` → `{ visibility: 'out_of_reach' }` with no branch in the program (I6 for free); `hop1` → `ALREADY_CONNECTED`; `pendingInvites.byPair` → `ALREADY_PENDING` / `THEY_INVITED_YOU`; two inserts. The caps are *constraints*, so the target's incoming count is never read (§4). Email is `effect sendInviteEmail` keyed by invite id. Op 2 (`ex≤9`): get invite (null unless `to` and pending → `INVITE_NOT_FOUND`), `blocked` (hidden-input probes → verdicts), `hop1` idempotent success, two edge inserts (`cap` refuses `DEGREE_CAP`), interval insert (`exclusion` is the one-open-spell check), invite `accepted`, pending delete, two `graphEvents` (generation +1 via `maintain`), two `pymkCandidates` deletes, `schedule(rebuildNeighborhood)` ×2. Op 3, Op 4 (Op 3 inline; ≤ 2 pending rows via the pair key, not `take 8`) and unblock are the same shape. Op 11 is a per-row `schedule` at `expiresAt`: no scan, no `hasMore` loop.

#### §5 Op 6 — listMutualConnections

First attempt scans the *subject's* list "as the design says, the smaller side": `db.scan(connectionAccepted.bySrc, [small], { take: 5000 })`. Admitted (`ex ≤ 5,002 + 5,000`). When `small` is the subject and the viewer is 2-hop, the read rule (`hop1(viewer, srcId)`) hoists to false, the page is empty, and `total = 0` — the number the design's promise 6 says must never appear. Corrected: always scan the **viewer's** list (tautologous rule) and probe `(n, S)`, readable because `n` is the viewer's 1-hop (§8.1):

```ts
  db.require(db.get(memberProfiles, args.subjectId) !== null, 'OUT_OF_REACH')   // hop2, sealed like the profile
  const mine = db.scan(connectionAccepted.bySrc, [ctx.viewer], { take: 5000 })
  const hits = mine.filter(e => e.dstId !== args.subjectId && db.exists(connectionAccepted.bySrc, [e.dstId, args.subjectId])
                             && !db.exists(blocks.byPair, [ctx.viewer, e.dstId]))
  hits.sort((a, b) => cmp(nameOf(a), nameOf(b)))            // stable, codepoint
  return { total: hits.length, page: pageAfter(hits, args.after, 20) }
```

`examined ≤ 10,002`, `rp ≤ 5,000`; `total` is a loop tally admitted under r8 (probe inputs pinned; scan over the caller's own rows). It is 238 entries under `G`: this query can contain nothing else. Sorting by name needs 5,000 card gets — refused; sort by `dstId`, or denormalize `displayName` onto the edge (≤ 5,000-row fan-out on rename).

#### §5 Op 7 and Op 13 — PYMK and the rebuild

Op 7's step 2 ("drop any row where `hopDistance ≠ 2` at read time") is `50 × 10,002` → `E_BOUND … product 500,100; rewrite: maintained relation or drop the per-row traversal`. Corrected: scan `pymkCandidates.byScore [viewer] desc take 50`, drop rows where `hop1` or `blocked` (150 probes), return `degree: '2nd'` as a claim the click re-verifies (Op 5). Distance becoming 3/∞ within 60 s survives in the list — inside I10's own tolerance (§7). Op 13 as one program: PYMK `5,000 × 502 = 2,510,000`, hints `5,000 × 202 × 52 ≈ 5.3×10⁷` → `E_BOUND`; a schedule is still one mutation, and the design's own sampling (500/200/50) does not fit either. Corrected form is a chunked, generation-fenced **job** (L7): one run per neighbor (`ex ≤ 202 + 200×52 = 10,602`, over `G` by 3.5% — `take 45` on the last level fits), merging into a scratch table, final 50-row replace in a last run. A degree-5,000 member is 5,000 runs; the 60 s SLO fails for hubs, which the design concedes.

#### §5 Ops 8, 9, 10, 14 — the DAG

Op 8, first attempt, maintains the closure in the program (design steps 6–13):

```ts
  db.require(!db.exists(issueClosure.byPair, [args.blockerIssueId, args.issueId]), 'CYCLE')
  const desc = db.scan(issueClosure.byAncestor, [A], { take: 256 }); const anc = db.scan(issueClosure.byDescendant, [B], { take: 256 })
  for (const d of [A, ...desc]) for (const a of [B, ...anc]) db.upsert(issueClosure, [d, a], …)   // ≤ 512 writes
```

`check` admits the reads (`ex ≤ 258 + 258`, rules pinned by prefix) but the `for`-`for` is `257 × 257 = 66,049` steps against the design's 512 cap — `E_BOUND` unless the loop is `All<T,256>` over a `cap({ by: 'ancestorIssueId', max: 256 })`; and at run time the upsert of a `(d, a)` pair where *both* issues are foreign to the caller fails `issueClosure.insert` — the caller cannot write rows it cannot read, so cross-project diamonds abort `E_CONSTRAINT`. The counts (step 13) are the same structural write. Corrected: `dag(...)` (L2) — the program inserts one edge; the engine refuses the cycle (sealed), refuses `CLOSURE_CAP`/`DEPTH_CAP`, writes ≤ 512 closure rows with `ancestorOpen` carried from the ancestor's status, and the two `maintain.count`s move. What stays in the program is I15:

```ts
  if (db.exists(issueClosure.byPair, [B, A])) {                     // readable: A is the caller's
    let path = [B], x = B
    for (const step of range(16)) {                                    // literal range; keys are traced-row fields
      const next = db.scan(issueDependencies.byIssue, [x], { take: 32 })
        .find(e => e.blockerIssueId === A || db.exists(issueClosure.byPair, [e.blockerIssueId, A]))
      if (!next || !db.get(issues, next.blockerIssueId)) return db.refuse('CYCLE')          // hidden node ⇒ no path (L5)
      path.push(next.blockerIssueId); x = next.blockerIssueId; if (x === A) break
    }
    return db.refuse('CYCLE', { path })                                // L5: payload ≤ 16 ids
  }
  db.insert(issueDependencies, { id: ctx.newId(), issueId: A, blockerIssueId: B, createdBy: ctx.viewer, createdAt: ctx.now() })
```

`ex ≤ 1 + 16 × (34 + 32 + 1) = 1,073` worst case (582 with the closure-depth shortcut). Concurrent `A→B` and `B→A` serialize on the single-writer store; the second's traced absence of `closure(B,A)` is now present → `CYCLE` (T5 by construction). Op 9: `db.update(issues, I, r => ({ ...r, status, closedAt }))` — the engine flips `ancestorOpen` on ≤ 256 closure rows (cap by ancestor) and decrements ≤ 256 counters; reopen is the inverse, no recount (each row flips once). Op 10: the issue `get` is the rule; the 32 blocker `get`s at the full rule are `32 × 5,003` probes → budget fails; stubs use `member || createdBy` (§7). `transitiveOpenBlockerCount` is a `db.get(transitiveOpenBlockerCount, [I])` point read with declared `readable`. Op 14 is a plan; the notification insert is arm-checked by `member`. `startIssue` is `db.update` with the rule of §2 carrying I12.

#### Op 12 — GitHub import

`effect importGitHub` verifies the signature and fetches, then calls `mutation applyDependencyDelivery` under **which principal the spec does not say** (L6; assumed `system`). Inside: receipt insert on the unique `deliveryId` (duplicate → `E_CONSTRAINT`, treated as no-op by the effect), ≤ 100 point reads, stub creation, edges applied one by one under `dag` — a cycle anywhere aborts the whole delivery, which *is* the design's batch semantics without its topological sort. Write amplification `100 × 512` closure rows exceeds any sane ceiling → the effect splits deliveries at 20 edges (§7).

#### Search and lists

`db.scan(memberCards.byToken, [term], { take: 20 })` is admitted at `ex ≤ 22` and fails at run time: 22 candidates × the card rule's 5,003-probe arm, and strangers (the negative case) are the common case — D-F's budget fails closed on every common name. Rewrite: the `reach` table (L3, `reach.byObserverToken [viewer, term] take 20`, `ex ≤ 42`) or index-served arms only (§7). The remaining list queries are page scans over the caller's own or project-pinned rows; `projectIssues` hoists `member(projectId)` to one probe.

### 6. Language delta

Ranked by app impact.

**L0 — r8's pinned-input admission returns a wrong integer.** *What:* a hoisted rule that evaluates false yields an empty page whose `count()`/tally is admitted as a resource fact (Op 5, Op 6, PYMK popularity). *Smallest addition:* when a hoisted non-tautologous rule is false at run time, any reduction over that page is `E_STRUCTURAL_COUNT` at run time (fail closed), and `check` marks the site `hoist-false-possible`. General. Amends §9.1 r8.

**L1 — bounded existential in rules.** *What:* `hop2` needs `∃n: edge(v,n) ∧ edge(n,s)`; §3 admits only single-index `exists`/`get`, so D-F's "index-served rule" has no spelling. *Smallest addition:* `any(index, prefix, { take: N, where })` in rule bodies, `N ≤` a schema `cap` on the prefix column so `maxRuleProbes` is a compile-time fact; arms evaluated cheapest-first with short-circuit **defined** (the spec never says rules short-circuit; affordability depends on it). Affordability here: one negative evaluation is 5,003 probes — affordable once per program (`viewIssue`, `viewProfile`), never per row of a page (search, blocker stubs, author cards, PYMK re-check all fail the budget). General. Amends §3, §5, §10 D-F.

**L2 — `dag` closure, the multi-parent `tree`.** *What:* engine-maintained transitive closure with per-edge cycle refusal, `maxDepth`, `maxClosureRowsPerEdge` (512), `maxDescendants` (256, which bounds status propagation), a `carry` column copied from the ancestor and re-propagated on its change, and `maintain` admitted over the closure. Fan-out cap is the design's I19 numbers; a delete recomputes ≤ 256 descendants × 32 direct blockers = 8,192 examined. Needed not for cost but because **the writer cannot see the rows it must write** (cross-project diamonds). General (prerequisites, package graphs). Amends §2 "Tree closure".

**L3 — join-maintained aggregate (2-path witness count).** *What:* `maintain.count` over a self-join `edge(a,n) ⋈ edge(n,b)` keyed `(a,b)` gives same-commit `hop2` as one probe, exact `mutualCount` as a point read, PYMK as `scan byObserverScore take 50`, and search over `reach`. Write amplification per accept `2·(deg A + deg B) ≤ 20,000` (the write ceiling must be app-level); storage ≈ Σ deg(v)·deg(n) ≈ 20× the edge table at year 4. The alternative to L1, not its complement; unpickable without measurement. General. Amends §2.

**L4 — receipt sealing of point-read absence.** *What:* r3 ships an absence fact when every examined candidate was readable — vacuously true for a missing handle, false for a hidden one, so the receipt distinguishes them and I6 leaks at the transport. *Smallest addition:* no absence fact for a point read on an index whose rule is not tautologous for the principal. General. Amends §6, §9.1 r3.

**L5 — `db.refuse(code, payload)`.** Bounded payload (≤ 16 ids here) computed under caller visibility. General. Amends §4.2, §9.

**L6 — effect principal.** `effect({ principal: 'system' | serviceId })`; mutations it calls see `principal.kind`. Runtime/policy. Amends §1, §7.

**L7 — `job` kind.** Chunked, resumable, generation-fenced bulk work with a per-run certificate (Op 13). Same as prediction 1's. Amends §7.

**L8 — `cap`/`unique` with a column predicate** (`where: leftAt === 0`). Convenience; closed here by `exclusion` and side tables. Low. Column visibility is closed by table splits and is not listed.

### 8. Where the design is wrong

1. **Adjacency read authority is unspecified, and every 2-hop computation forces a choice the promises never made.** Exact mutuals and any caller-visibility 2-hop test need V to read edges `(n, S)` that are not V's own. Either 1-hop connection lists are readable (then a 1st-degree can page all 5,000 of your connections — no promise grants that) or 2-hop runs under system visibility (L3 / verdicts). *Confirming observation:* with an own-rows-only edge rule, Op 6 returns `total = 0` for every 2-hop subject and `check` says nothing; with the 1-hop-lists rule, `listConnections(S)` — a query the design never lists — is admitted for every 1st-degree.
2. **§6 forbids the 2-hop index that I7 requires.** "No neighborhood firehose, so implementers cannot pretend a 2-hop index exists" and "search returns the distance ≤ 3 set" cannot both hold: name-filtering the 2-hop set is a walk of ~6,400 members per keystroke at degree 80, or the forbidden index. *Observation:* typeahead `jo` for a viewer whose only matches are 2-hop returns nothing under the budget and everything under `reach`.
3. **Promise 2 is false whenever sampling saturates.** Cards are "visible iff distance ≤ 3", but `neighborhood3` is written by a `take 200 × take 50` sample and `n3Partial` is a declared state; 3rd degree is a discovery tier wearing an authorization promise. *Observation:* two members at exact distance 3 through one bridge of degree > 200 never see each other's card, at any generation, while promise 2 says they must.
