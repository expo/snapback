### 2. Schema in v0

This is the maximal data-language schema. It deliberately does not invent auth, asset-service, search, or retention primitives. `R` is an ordinary schema-time helper expanding all four mandatory rules. `U`/`S` mean user/system principal. `member`, `admin`, `canReadMessage`, and `canConfigure` are inlined algebraic rule helpers using indexed point reads.

Representative natural refusals are:

Their diagnostics respectively require an auth runtime, a bounded/projection rewrite, `maintain.count`, `ctx.commitTime`, and a declared normalized prefix index. Only the count and clock cases have current-v0 repairs.

### 5. Integrity audit

| Fixed invariant | Enforcement |
|---|---|
| Unique email, adaptive password KDF | Not enforceable: auth runtime absent |
| Expiring/revocable session and API token | Not enforceable |
| Unique handle | Schema unique constraint; sealed `E_CONSTRAINT` |
| Handle/profile formats | Program `require`; not a schema-wide regex constraint |
| Media MIME/size/duration and contextual delivery | Metadata `require`; service enforcement missing |
| No self-follow; unique follow edge | `require` plus unique constraint |
| Implicit self-follow has no row/count | Feed construction only |
| Idempotent set-state follow/like/repost/reaction/vote | Unique keys plus desired-state mutation branches |
| Post media 0, 1–4 images, or one video; never mixed | Cap 4 plus `createPost.require`; cross-table shape is not constraint-sealed |
| Replies absent from feeds/direct only | Immutable `isReply`, parent relation, feed insertion branch |
| One DM per unordered pair | Canonical pair plus unique constraint |
| Group created with 2–50 members | Creation mutation plus active-membership cap |
| Admin add/remove/promote; anyone leaves | Rules and mutation `require`s |
| At least two continuing members / last-admin behavior | Not specified by product and not enforced |
| New members see history | Current membership read rule ignores join time |
| Removed member receives no new messages | Active membership required by send and message read |
| Removed member retains cached old history | Not expressible without widening server access or adding retention policy |
| Send-time recipient set | Immutable `messageRecipients` referencing immutable episodes |
| Departure drops receipt requirement permanently | Missing active episode is treated as satisfied/dropped; rejoin creates a new episode |

It regresses where the fixed app needs authentication, asset custody, search normalization, post-removal local retention, external-effect idempotency, or cross-table invariants stronger than trusted mutation code.

### 6. Language delta

1. **Client-callable identity and credentials.** Add a runtime-owned `identity` kind or typed intrinsics for password signup/signin, adaptive KDF custody, expiring sessions, logout-family revocation, API-token issuance, and `ctx.viewer` projection. General; amend §§1, 4.3, 6.

2. **A real asset sublanguage.** Specify upload intent/finalization, metadata validation, contextual carrier authorization, ordinary delivery, one-use delivery, revocation, processing status, offline-byte custody, and purge receipts. General; amend §§2, 4.2, 5, 6.

3. **Transactional effect outbox.** Add commit-triggered effects with durable job identity, connection-state-at-commit input, replay suppression, provider idempotency, and “log exactly once” qualification. General; amend §§1, 7 and add effect execution semantics after §8.

4. **Normalized prefix indexes.** Extend `tokens` with declared `normalization:"NFC"`, `caseFold:"unicode-simple"`, `boundaries:"unicode-word"`, and `match:"prefix"`, with identical local-store derivation. General; amend §§2, 4.2, 5, 6.

5. **Bounded relational maintenance.** Add compiler-owned maintained projections/joins with backfill and a declared hybrid fan-out policy. This is needed for an exact unbounded Following feed and digest without failing either celebrity write or follower read scaling. General; amend §§2, 4.4, 5.

6. **Authorization-distinct retention.** Add an explicit, reviewable policy for retaining already-delivered ordinary rows after membership ends while denying server refetch and all future rows. Content revocations must override it. General; amend §§3 and 6.

7. **Constraint-safe derived rows.** Permit a declared derived/indexed row whose value is transactionally tied to a source aggregate—for example post like count indexed for Trending—rather than relying on every future mutation to update `postRanks`. General; amend §2 constraints/maintenance.

8. **Finish modeled-input spelling and settlement.** Specify commit-time column syntax, configuration constants/tables, mutation-ID dedupe, and whether OCC retries to server-arrival LWW or rejects. General; amend §§4.3, 5, 6.

### 8. Where the design is wrong

1. **“There is no other kind” is false for a complete application.** Authenticated client calls, asset custody, and transactionally triggered external effects are neither data programs nor legal effects as specified. Confirming observation: a fresh implementation reaches M1 or the first upload only by inventing host APIs or reintroducing a handler surface.

2. **Per-operation boundedness does not solve bounded total work.** The exact Following feed and digest require an unbounded relationship projection, while naive read-time, fan-out-on-write, and celebrity hybrids each violate a different frozen requirement. Confirming observation: at the O5 envelope, an admitted implementation exceeds either the 500-vs-5 read rule or the 900-vs-5 celebrity write rule `[inferred]`.

3. **The language conflates server authorization with client retention.** Current membership should deny new/server reads, yet an expelled member must retain already-held ordinary history while later delete/expiry still purges it. Row rules alone cannot state that three-way policy. Confirming observation: the removal test yields either over-authorized server history or an incorrect purge of the former member’s local history.
