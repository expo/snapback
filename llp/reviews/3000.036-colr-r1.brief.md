## 22. COLR: column read rules (0.4.35 proposal)

**Commission:** Charlie Cheever, wave-19 COLR workstream, 2026-10-19.
This replaces §21's open column-read decision. DORM owns reverse projections,
renames, dormant inspection and rollback narration; COLR changes no dormancy policy.

### 22.1 Surface and authority

An ordinary stored column may append `read <- P` to its declaration, after
its type and default. A group uses `read (notes, photo) <- P` as a table line.
Both use the existing row-read expression grammar, including readable unique
`exists` probes. Duplicate column rules and undeclared names refuse
`E_COLUMN_READ`. `id` is always row identity, never a protected column.
For example `notes: text <= 500 ? read <- .owner = viewer`.

Effective payload authority is the conjunction of the row read rule, the
column rule and any existing owner-private field gate. It cannot broaden a
row's audience. No column rule grants write authority. System maintenance
keeps its existing bypass. A missing or unreadable probe is unknown under
negation exactly as in row rules. Column rules may not depend on protected
values, including via target probe keys or residual equalities: this prevents
recursive policy and value-guessing oracles.

A denied cell is absent from whole rows and spreads, not a stored null.
Explicit field selection returns null through the existing optional-field
instruction. The Quarry type is optional and the generated TypeScript property
is optional for every audience (including formerly required protected fields).
An allowed optional null remains present as null in a whole row. Hidden and
null need not be distinguished in explicit scalar expressions. Existing hooks,
including `useQueryData`, require no extra call or policy branching.

### 22.2 Observations, planning and derivations

Projection occurs before any value reaches the program environment, response
pricing, serialization or mutation return. Expressions, transient views,
computed shapes and scalar computations therefore operate on the disclosed
image. Row existence and a count independent of a protected value retain the
row audience. A predicate over the disclosed optional value sees null when
hidden; its result cannot depend on the stored hidden value.

A protected column cannot supply an index, cursor/order/search key, unique
constraint, row lifetime, sync scope, recorded attribution or a row-rule input.
Such structural uses refuse `E_COLUMN_READ`, with a repair naming an ordinary
public key or a separate data entity. This includes inferred indexes and raw
schema admission, not only authored indexes. Sorting/grouping an in-memory
already-projected list is safe and follows ordinary optional-value semantics.
Program `exists` with a protected residual equality is refused rather than
using a raw storage predicate. Rule probes may not inspect protected keys or
residuals. Mutation transition rules may not inspect protected values to test
an unauthorized guess. Ordinary writes of supplied values are still allowed
under the row's write authority; read protection is not immutability.

Maintained views/counts/sums and maintained columns cannot consume a protected
input in their filter, group, sum or computed keys. A plain row count remains
legal. This conservative, explicit refusal prevents independent aggregate
audiences declassifying a field. Derivation over protected inputs requires a
query over disclosed rows; independent aggregate declassification is outside
this change. An ordinary maintained output column can itself carry a read
rule; derived maintenance remains system work, with projection at disclosure.

`read through` and `read through live` inherit row authority, not payload
permissions. A child's own ordinary column may have its own column rule.
Protecting a parent authority/capture field refuses as a structural use. A
column policy change is absent from capture identity and does not trigger
`E_READ_THROUGH_ADOPT`: existing children continue to inherit the same row rule.

### 22.3 Sync, device envelopes and live updates

Device schema declares a mandatory `column-read-v1` semantic capability;
older devices refuse it before executing any plan. New schemas without column
rules retain their prior byte representation and capability set.

Rules containing only row fields, viewer, literals and Boolean/equality
operators are row-local. The same projection is applied to every snapshot and
log put for its recipient. A shared log image contains no protected cells;
serve-time delivery re-fetches and projects the current row for its viewer.
Changes to owner/selector fields therefore replace or redact cells atomically
with the row update. Devices never re-materialize a hidden default. A
row-local protected cell in delivered history remains subject to the same
stored row-local projection; copied data cannot be retroactively forgotten by
a client that is offline.

A rule with a probe or reference is evaluated by the authoritative engine.
Its cell is omitted from every replica image. Read sites on that table are
server-class and the ordinary SDK fallback answers them online; offline they
are explicitly unavailable, never a complete answer with fabricated hidden
cells. A `held` query cannot certify those reads. Writes whose return or
transition needs those cells queue without prediction. This is the same
residency boundary as non-invertible row rules, scoped to column payloads;
it does not require an application side table, a second query or a new hook.
It deliberately makes no offline availability claim for policies whose
witnesses the device does not hold.

Server live queries track every column-rule probe dependency, so a grant,
role or parent change invalidates the answer even if the data row is unchanged.
Existing policy reset/expiry/sign-out fences still apply. No cell rule adds a
new result cache, partition audience or unbounded write fanout.

### 22.4 Assets, writes and refusals

Asset downloads and read-once use require owning-row read authority AND the
asset column's effective authority, including asset-list columns. Hidden
assets retain the non-oracular `E_ASSET_UNKNOWN` response and meter. Upload
placement checks insert/update authority and input shape; it does not grant
read access, and attaching an asset never returns its protected value to an
unauthorized writer. Returning an insert/upsert/update row runs the same
projection as a query. Blind write outcomes keep their existing refusal
normalization. The new declaration/structural refusal is `E_COLUMN_READ`;
ordinary denied scalar access is optional null, not a distinct refusal.

### 22.5 Invariants, audit and releases

SEC3's `invariant table.column read only P` is proved against row read AND
column read AND owner-private authority. Declared policy and intent must agree:
a column rule does not automatically mark an independently stronger invariant
proved. Unsupported observer flows retain the SEC3 proof obligations. Audit
prints each effective column audience and its server/replica residency.
A narrow 1:1 side table with a parent reference and unique parent key receives
an advisory column-rule suggestion, never an automatic rewrite.

Adding, changing or removing a column rule is a normal schema adoption; existing
values remain stored and clients rebootstrap on changed schema generations.
Rollback to a schema lacking the rule restores that schema's audience and
warns of confidentiality changes under the existing release preview policy.
A v2-only protected column becomes a dormant cell on a visible v1 row, using
ordinary retained-column storage. Old clients calling the new server receive
omitted protected fields, and generated compatibility reports must identify
newly optional fields. The DORM lane owns forward catch-up and reverse projection.
