I'll review the Following RFC against the amended LLP sections and the timeline, device-read, and client code it depends on. Nothing will be changed.The RFC amends Following delivery and device reads. Next I’ll check those claims against admission, backfill, horizons, and the client fallback.**NOT READY.** The RFC's device-answer rule is not what a Following read does today, and the two changes it adds fight each other: a public horizon does not cover the reader's feed, and dropping the history window keeps every page `complete: false` until an unbounded copy finishes.

## Findings

### 1. High — §2.2, §3. A missing card is not how this page is read

The paved read (`bind/timeline.rs` `read`) returns inbox fields only: event id, post, actor, author, repost, time. It never loads `posts` or `reposts`. The guide's `home` query is that read. `{ *, card: posts[.post] }` is optional, and it does not load the repost row. The repost's event id is minted; it is not `reposts.id`.

`get_inner` marks a **miss** on a horizon table unknown and still returns null. The row stays in the page. `unknown` is whole-query, not per card.

- Online, with no predictable write queued, `local.ts` does replace that answer (`wantsServer`).
- Offline, or while any predictable write is unobserved, it publishes the local page: a null card, `complete: false`. The feeds card says to render an incomplete result. That is the hole §2.2 says never happens.
- One repost of an original outside the horizon poisons all twenty rows, so "the first page stays offline" is false for an ordinary repost.

**Smallest change.** Keep the paved page as the inbox projection (it already matches the server without post bodies). State that a card is a separate point read, that a miss is unknown for that query only, and that offline or pending-write reads withhold the page (`loading`) instead of returning a null card. If the engine must join cards, look reposts up by `(actorId, postId)`, and do not treat "skip the row" as success: skipping shortens the page and moves `next`.

### 2. High — §3 Removal. The tombstone sentence is the wrong mechanism

`followingRemovedEvents` is its own `sync public` table with no horizon. The page hides a copy with `not exists RemovedEvents[eventId]`, not with `posts.removed`. A tombstone is not attached to the post's log event.

An unheld put below the acquisition floor is dropped (`boundary.accept`). A `removed: true` update for a post the device never acquired never arrives. The tombstone still does, because that table has no floor.

Until the tombstone syncs, the inbox row is still visible and the miss is a **known** absence (`horizon.is_none()`), so the page is `complete: true` and differs from the server. That lag exists today. The fallback does not cover it. Implementing the sentence as written — deliver the tombstone only with the post event — makes the copy stick forever: the post event is dropped, the filter never fires, and the page stays complete.

**Smallest change.** Delete the sentence. Removal stays a fully synced public tombstone. A missing card does not decide membership.

### 3. High — §2.1 and the summary. `sync public last 5000` is not the reader's feed

For `sync public` the audience prefix is empty, so the horizon is one group: the newest N rows of the whole table (`schema.rs`, `group_of`). It does not follow who the reader follows. Nothing evicts and nothing moves the floor (`guide/sync`: the horizon bounds acquisition, not what the device keeps). After the snapshot, every newer public post is stored forever. A quiet reader's entire feed can sit below the floor, so every carded page is unknown, while the device holds 5,000 posts that reader never sees.

`followingPosts` stays `sync public` with no horizon (`timeline.q`), so a cold device still acquires every event projection, every tombstone, and the whole follow graph. "Holds only what it reads" is false at cold start and false in steady state. The 10× check can still pass if post bodies dominate; it does not measure the feed.

A public read rule cannot be rewritten to `sync to follows[.authorId]` (`bind_sync` requires the audience to match the read rule). Per-author horizons are not available while posts stay public, which Following requires.

The order rule is also unenforced. A public horizon index only has to be plain; `starts_with` of an empty prefix is true for every index. `last 5000 by byId` is legal and is not "newest by `at`".

**Smallest change.** Say the horizon is a global, non-sliding acquisition floor, and that the first page is local only when each of its cards is inside that floor. Refuse any posts or reposts horizon whose index is not `(at, id)`. Do not claim the device holds only the feed. Leave `followingPosts` full-sync and count it in the cold-start measurement.

### 4. High — §2.3. Removing the window makes `complete: false` unbounded, and the stop condition will be built wrong

`complete` is false for every page of a reader while any backfill or cleanup row exists (`timeline_read_pending` on `byReaderPage`). It is not "this page reaches past the copied prefix." The newest 20 were already copied in the follow transaction, but they stay `complete: false` until the walk finishes. `unknown` is not set, so the client does not fall back. With no window, a follow of a long author keeps the whole feed incomplete for the whole copy, including pages that will never change.

The cost sentence is wrong. New posts already fan out to current followers. The window is what stops a follow from copying that author's past. Dropping it makes server storage and the device inbox both grow with history × followers. The inbox has no horizon (`Feed` is `sync` to `readerId`). The 1,000 cap is the device inbox bound per author. The scale fixture hides this: authors have on the order of 50 posts, under the window.

Backfill's chunk limit is `DELIVERY_CHUNK.min(remaining as u32)`, and `limit == 0` is immediately exhausted (`work.rs`). Cleanup ignores `remaining` and walks until the index ends. Deleting `HISTORY_WINDOW` and enqueueing `remaining: 0`, which is what cleanup does, copies nothing and then deletes the task. The reader sees a 50-event feed with `complete: true`.

`copied == remaining` counts only rows that were copied, not rows visited. Events born after the edge are skipped (`delivery.admitted < epoch` is false) and do not decrement `remaining`. A precount taken in the follow transaction both reintroduces a synchronous scan and stops early or late.

Refollow itself is safe: the old task sees the new edge epoch and exhausts; cleanup is prefixed by the old epoch (`byReaderActor`). What it costs is two full histories until cleanup finishes. Epoch string order is fine (fixed-width admission tokens). Restart from the committed cursor is fine once termination is "the descending walk found no older row."

`READER_ACTOR_COPIES` is unused. `EVENT_COPIES` (1001) is the per-chunk purge **authority** budget in `timeline_authority.rs`, and it is inert today because `purge` is `""`. It is not a window bound, and the work queue does not have a "chunked equivalent." Cleanup and purge already walk to exhaustion at 256 rows. Do not delete `EVENT_COPIES` on the theory that it only existed for the window.

**Smallest change.** Keep the window, or replace it with a horizon on the private inbox (`byReaderPage` already leads with `readerId`, and a descending page already goes incomplete at the floor, cursor included). If history must be complete on the server, end backfill only on walk exhaustion, ignore `remaining`, and define `complete` as false only for a page whose cursor is still inside the uncopied suffix. State the cost as one inbox row per historical event per follower, on the server and on the device.

### 5. Medium — §2.2 Predictions. "Unchanged" is false for a repost of an unheld original

An own post still predicts: the local row is the card, and the own inbox copy is written. That page differs from the server until ack, with `complete: true`. That is the existing prediction contract, not a horizon bug.

A repost reads the original (`timeline_get` on `posts`). A horizon miss sets `beyond_horizon`, and prediction is refused. The mutation queues with no local row. `write_site` still labels that input `Held` whenever `sync` is `Some`, not `Horizon`, so `check` will not say it may queue.

Follow and unfollow already queue with no prediction. Pending backfill does not change that.

**Smallest change.** Say a repost predicts only when the original and the tombstone probe are held; otherwise it queues with no row. Classify that input as a horizon site.

### 6. Medium — §2, adoption is unspecified. The existing reset is safe; an in-place floor is not

A sync edit is not a literal-default image keep (`keeps_literal_default_images` compares `sync`). Server `adopt` advances the generation. The device clears acquisition, and `local.ts` sets `partitionCurrent` false until the replacement snapshot is acquired, so it will not serve the old partition as a complete feed. The server inbox is not a timeline redefinition (`same_declaration` ignores source sync).

What must not be built: keep the old rows and only start dropping new ones. A point **hit** never consults the floor, so every previously acquired card stays a complete answer, including after "horizon → full sync" if rows were deleted and the horizon flag is gone — a miss is then a known null, `complete: true`, for the whole re-snapshot. Going the other way without a replacement snapshot leaves the full corpus in place and calls it the horizon.

**Smallest change.** One sentence: full sync ↔ horizon is an ordinary generation change and a full device re-snapshot. Do not trim in place. Say the reverse direction re-acquires the whole public table.

### 7. Low — §2.4 and §4. `doctor` cannot show a remaining count it does not have

`timeline_work_counts` is pending and parked task counts. `remaining` is a copy budget, not "rows left," and it is wrong once termination is exhaustion. There is nothing to display until a walk counts.

**Smallest change.** `doctor` shows pending and parked tasks, plus the cursor. Drop "remaining counts," or define a count the chunk updates.

## What is sound

- Private inbox, private work, and private edge epochs are unchanged. A horizon on public posts does not reveal another reader's feed or follow state. Public follows and public tombstones were already public.
- Delivery chunking, per-chunk meters, and request-before-maintenance yielding still bound each transaction. Cleanup and purge already run to exhaustion and do not use the 1,000 window.
- Refollow versus an in-flight backfill is already epoch-scoped. An old task cannot delete the new edge's copies. A committed cursor survives restart.
- Online, with no predictable write queued, a horizon **miss** is `unknown` and the client replaces the whole answer. That path is real. It is not what `home` does, and it is not the offline path.
- Own-post prediction still materializes the card it just wrote.

## Verdict

**NOT READY.** The calibration fix is the admission change alone: allow a horizon on `posts` and `reposts`, keep the inbox window, and tell the truth about a global non-sliding floor and about card reads. Section 2.3 should not ship on this design.
