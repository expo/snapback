1. **Blocker — §2.3; §5.1: the live-suffix index still uses authored expiry rather than effective expiry.**

   Consider `items` with `read through .session`, where sessions expire. Give items a separate ordinary reference `bucket: buckets on delete cascade` and `cap 1 by bucket`. Items have no authored `expire at`.

   Successive sessions can leave many expired, unswept items naming the same bucket while its live population remains capped at one. §2.3 specifies `[bucket, id]` for this case: there is no authored expiry column to include. Deleting the bucket must therefore visit the expired backlog before determining its live closure. If items also declare an authored deadline later than their captured session deadline, indexing that authored deadline still includes effectively expired rows.

   This is existing language behavior: `Table::expiry_column()` selects `$deadline` for expiring read-through tables, and that deadline is the minimum of authored and captured deadlines. §6.1’s exclusion only forbids cascade **on the read-through reference**; it does not forbid the separate bucket reference.

   Consequently, the examined count cannot bound the physical visits. Continuing to draw during traversal restores hidden-backlog-dependent exhaustion; bypassing draws permits work beyond the admitted bound.

   **Smallest fix:** make §2.3 use the table’s **effective expiry column** for every expiring child, including ordinary references on read-through tables. Reuse only indexes beginning `[reference, effectiveDeadline]`; perform the never-expiring and future-deadline seeks against that column. Apply the two-seek price consistently.

2. **High — §2.2; §5.1: an exported source-write price does not include the row-keyed member recount allowance.**

   Add an optional filing reference `category: categories ? on delete set null` to the ordinary `members` table of a row-keyed count view. Cap it at one member per category. Keep members and source rows publicly readable; category participates in no rule, audience, predicate or maintained path.

   Suppose that member’s count is pending because its source group exceeds the writer’s recount limit. Deleting its category clears one reference, then ordinary member maintenance attempts another recount—even though the filing reference is unrelated to the count.

   The existing exported `ROW_MEMBER` price gives the one-recipient allowance: `row_price(..., 1)` reserves eight examined rows. The **additional** recount reservation is constructed separately in `maintain_row_views`, with `WRITER_RECOUNT = 1024`; `row_view_member` can execute it when the existing value is unsettled. LLP 3000.022 §14.3 likewise describes member writes as paying the one-recipient price **plus** the bounded recount allowance.

   §5.1 adds the exported plan but never adds that separate allowance. A cap-one set-null action can therefore examine roughly a thousand source rows outside its computed physical draw. Those rows are unrelated to the cascade closure, so `N(T)` does not cover them.

   **Smallest fix:** add a shared, schema-fixed member-recount allowance to `unit(C)`, including examined work, steps and scratch. Alternatively, conservatively refuse set-null targets that act as row-keyed-view members until that allowance is exported. When admitting those targets, also apply §4.2’s hook-refusal exclusion to their member-authority checks.

3. **High — §3 step 6; §6.2: “remove `p` as today” leaves the root outside the explicit current-image protection.**

   Let projects maintain `taskCount: count tasks by project`, with a plain index on `taskCount`, and let tasks cascade from projects. A project initially has count one. Deleting its task mirrors count zero onto the project before the project is removed, exactly as §6.2 requires.

   Step 6 expressly removes the other closure rows from current images, then says to remove `p` “as today.” Today’s `delete_authorized` retains the originally authorized root image across reference actions. Both SQLite and memory deletion derive index keys from the supplied old image. Removing this root with count one consequently leaves its current count-zero index entry behind.

   This is not the previously closed set-null-on-a-doomed-row case: the root changes through permitted maintained-column mirroring.

   **Smallest fix:** explicitly require every removal, **including `p`**, to fetch its current image after preceding action effects. Reserve that root fetch unconditionally and use the fetched image for indexes, maintenance and events. Authorization can remain the decision made in step 1.

4. **Low — §4.4: the recommended existence guard is incompatible with `set null`.**

   The suggested `insert <- … and exists parents[.parent]` reads the reference. Under §2.2, that makes `on delete set null` ineligible—even when the author only wants to prevent initially dangling filing pointers.

   **Smallest fix:** qualify the recipe: the guard works with eligible cascade/restrict/keep references; set-null references cannot use it under this revision’s conservative authority exclusion. Read-through also cannot substitute for set null.

The parent-delegation model in §4.1 is now sound: explicit actions confer the intended authority, and the strengthened set-null, field-owned and timeline exclusions close the reviewed authorization holes. Closure-first ordinary restriction, schema-order reporting, current-image non-root writes, and complete-group prediction requirements are sound. The derived touched-set and static footprint changes also close the reviewed metadata disclosure channels.

The remaining blockers concern whether execution actually fits the reservation and whether root deletion preserves storage correctness.

**Overall verdict: NOT READY.**
