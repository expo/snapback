## New fundamental and major findings

### N1. Reading “not live” does not safely authorize reopening SQLite — FUNDAMENTAL — child B §5

Recovery permits the source to return to `copying` after reading a target state other than `live` ([B:231](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:231)). That observation does not establish that the handoff cannot subsequently commit.

A permitted execution is:

1. SQLite durably enters `prepared`.
2. The target handoff transaction starts; its commit is delayed or ambiguously acknowledged.
3. Recovery reads the previous, non-`live` target row and reopens SQLite.
4. The handoff commits and Postgres becomes writable.

An ordinary MVCC read need not wait for the pending update. Even a locking read is insufficient if it merely releases the lock: a paused coordinator that has not yet entered step 5 can later execute the handoff. The timeout rule has the same problem ([B:223](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:223)).

**Recommended direction:** give each cutover attempt a durable, mutually exclusive **commit or abort decision**. Recovery must serialize with handoff and persist an abort that a delayed coordinator cannot override; handoff must conditionally commit against that exact attempt. SQLite may reopen only after that abort is established. An unavailable or unresolved target must leave the source fenced. Apply the same rule to reversal.

### N2. The unverified delta still grows during an O(store) scan — MAJOR — child B §§4.4, 6

The complete comparison reads the barrier snapshot over every family. Only afterwards does cutover compare everything changed since that barrier ([B:248](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:248), [B:260](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:260)).

Let full verification take `T(M)` for store size `M`, with `λ` newly changed keys per second. The paused comparison then contains approximately `λ × T(M)` keys. Append traffic supplies a straightforward counterexample; commits, receipts and log entries also accumulate even when application writes repeatedly touch the same rows.

Consequently, a nearly caught-up **replayer** can coexist with a very large **unverified delta**. Refusing excessive replay lag does not bound this work. The claim that write unavailability depends only on the capture tail remains unsupported ([B:50](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:50)).

**Recommended direction:** advance a verified barrier while writes continue. After the initial full comparison, compare successive deltas outside the pause until the remaining unverified keys and bytes fit its budget. Qualification must establish that verification, not just replay, outruns changes. Alternatively, maintain composable verification roots or weaken the pause guarantee. Account for WAL retained by the long verification snapshot as well.

### N3. Moving completed results does not preserve worker execution ownership — MAJOR — child A §4.3

The existing ledger holds its SQLite write transaction across **lookup, handler execution, and completion commit** ([worker-ledger.ts:40](../../snapback4/packages/snapback4/src/worker-ledger.ts:40)). This prevents another live worker sharing the ledger from invoking the same handler while the first remains active. The accepted contract explicitly distinguishes that protection from the unavoidable crash window ([LLP 3000.009:536](../../llp/3000.009-general-purpose-backend.rfc.md:536)).

The replacement describes only recording the result **after execution, under the effect’s lease** ([A:159](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:159)). Consider a healthy worker whose provider call outlasts its lease:

- Expiry makes the effect claimable again ([effects.rs:513](../../snapback4/crates/snapback4-core/src/engine/effects.rs:513)).
- A successor finds no completed result and invokes the handler.
- The original worker’s successful result cannot be recorded under its expired lease.

This adds duplicate execution without a worker crash or unrecoverable storage failure. The current ledger can preserve that original result despite lease expiry; its completion transaction does not depend on the server claim remaining valid.

**Recommended direction:** require the planned worker slice to define execution ownership and uncertain-attempt recovery, as well as completion storage. Separate recording an already-produced result from authorization to settle the current claim. Specify when successors wait, reconcile through provider idempotency, or park uncertain work. Database lease fencing alone cannot stop an external call already in progress.

### N4. The termination sweep does not close admission under the old token — MAJOR — child A §5

The standby first terminates the recorded backend PIDs and only afterwards acquires `_owner FOR UPDATE` to advance the token ([A:209](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:209)). Meanwhile, new writing transactions check only the token and take `FOR SHARE` ([A:192](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:192)).

Between those steps, the old process can reconnect, register a replacement connection, and start another transaction using the still-current token. If it pauses while holding that shared lock, the standby again waits indefinitely. Its completed PID sweep did not terminate this new backend. The statement that a reconnect necessarily sees a newer token assumes takeover has already succeeded ([A:224](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:224)).

The token remains a sound **post-takeover write fence**; this is a hole in takeover progress.

**Recommended direction:** define connection loss, registration, renewal and takeover as one epoch protocol. Replacement connections must not resume writes under an abandoned epoch while takeover drains it. Revalidate the observed holder/token and lease when claiming ownership, and provide bounded handling of newly appearing blockers rather than one termination sweep followed by an unbounded lock wait. The witness should pause the former owner during reconnection, not only before takeover begins.

### N5. Speculative execution already consumes its eventual commit sequence — MAJOR — child A §§6.3–6.4

Candidate (a) describes execution at snapshot S followed by validation and ordered batch commit ([A:316](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:316)). It does not specify how execution obtains—or later replaces—the public sequence embedded in its output.

This sequence is more than commit-tail bookkeeping:

- The adapter obtains `next_seq()` before constructing `Runner` ([postgres/mod.rs:293](../../snapback4/crates/snapback4-core/src/engine/postgres/mod.rs:293)).
- `emit` constructs durable effect identities from that sequence ([runner.rs:688](../../snapback4/crates/snapback4-core/src/engine/runner.rs:688)).
- Following stores sequence-derived admission tokens ([timeline.rs:158](../../snapback4/crates/snapback4-core/src/engine/timeline.rs:158)) and later compares them to distinguish delivery from backfill ([timeline/work.rs:100](../../snapback4/crates/snapback4-core/src/engine/timeline/work.rs:100)).

Two executions at the same snapshot obtain the same provisional next sequence. Accepting both unchanged can duplicate effect identities or stamp incorrect admission order. Treating that head read as an ordinary validation dependency instead makes otherwise disjoint mutations conflict whenever any preceding mutation commits, undermining the proposed concurrency.

**Recommended direction:** make sequence-dependent execution an explicit part of (a)’s design. Define commit-time resolution of provisional identities and ordering fields—including their overlay, index and read semantics—or design an early ordering protocol that handles refusals without publishing gaps. Qualify concurrent emitters and Following transitions, not only counters or precomputed write sets. This is an unchanged interpreter dependency I missed in round 1.

## Small notes

- **Actually pin both barrier snapshots.** In [B:161](../../llp/3000.009.001.001-graduating-a-live-store-to-postgres.rfc.md:161), opening a deferred SQLite transaction alone does not establish its snapshot; perform a read while the write lock remains held. Likewise, pin the target’s barrier snapshot before replay advances beyond it.
- **Execution digest versus artifact digest.** [A:123](../../llp/3000.009.001.000-the-postgres-store-port.rfc.md:123) includes provenance in the content-addressed release tree, but `release_files::digest` explicitly excludes `provenance.json` and `.pending-adoption` ([release_files.rs:45](../../snapback4/crates/snapback4/src/release_files.rs:45)). Preserve that execution identity, but use a separate exact artifact digest or manifest so distinct provenance-bearing trees cannot silently share one blob key.
