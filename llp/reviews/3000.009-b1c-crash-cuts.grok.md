## Material findings

### 1. After-step `oidc.mint/done` intercept is not single-shot

`qualify-b1c.mjs:330-337` (`startFaultProxy`):

```330:337:snapback4/packages/snapback4/test/fixtures/identity-recipe/qualify-b1c.mjs
      if (mode === "after-step" && request.url?.includes("/steps/oidc.mint/done")) {

        requireMintStepDoneCut({ invocation: invocation(), phase: state.phase, path: request.url, upstreamOk: upstream.ok, reply }, assert);
        state.stepDone = reply.step;
        await cutWorker(pid, registered, "after-mint-step-done-before-action-settlement");
        state.phase = "final-recovery";
        exchange.intentionalCut(); response.destroy(); return;
      }
```

`crash-cut-plan.mjs:6-10` then requires `phase === "await-step-done"` and the exact done path. That phase exists only after the recovered `/auth/session` (`qualify-b1c.mjs:325-327`) and is left at `final-recovery` immediately after this cut, then `done` on the third mint (`qualify-b1c.mjs:327`).

The `if` does not test phase, cut count, or “already cut.” Every later `oidc.mint/done` in this mode still enters the block. `requireMintStepDoneCut` fails, the proxy catch maps it to `proxy-proof-protocol`, and the acknowledgement is destroyed instead of forwarded.

That collides with the mode’s own contract:

- Journal: a third distinct worker must replay the completed step and replace the lost handoff.
- Primary already depends on post-mint `oidc.mint/done` to finish `completeOidc`. After-step worker 3 is that same public helper path, with the step already durable.

Expected after-step shape is two cuts and three mints, then `phase === "done"` (`qualify-b1c.mjs:426-429`). A third-worker done replay cannot reach the forward path at `qualify-b1c.mjs:338-341`. An actual after-step run should fail closed after burning primary and before-mint Keycloak exchanges; raw never runs.

Gate the intercept on `state.phase === "await-step-done"` (and the exact path), then forward any later done replay.

### 2. After-step never observes “done committed, action not settled” in the store

Before-mint is explicit: read-only SQL, then signal (`qualify-b1c.mjs:297-308`, `database()` at `qualify-b1c.mjs:372-374` with `{ readOnly: true }`).

After-step takes durability only from the upstream HTTP body (`qualify-b1c.mjs:331-333`, later `qualify-b1c.mjs:448`). There is no read-only check that `_action_steps` for `oidc.mint` is `done`, and none that `_requests` for the invocation is still pending, before `cutWorker`.

The task is specifically after recovered mint-step done commits and before action settlement. Without those two reads, a 200 with `minted: true` can be treated as the cut point even if the engine has already settled the action, or if the HTTP success is not yet the durable receipt the journal describes. That is a missing witness, not an extra nice-to-have.
