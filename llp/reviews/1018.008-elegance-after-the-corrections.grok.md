## Overall judgment

The parent diagnosis is right: Snapback 2’s core is already elegant (one IR, one receipt, uncertainty instead of invented fields). Remaining roughness is mostly the application reconstructing a fact the platform already has, or a conservative boundary whose blast radius is wider than the product edit. The batch is careful about 1019–1021 non-overlap, fail-closed authority, no new gates, and the 85k gzip ceiling.

It still proposes too much machinery for the roughness that will remain after those landings. Two items are worth implementing in reduced form (routine recovery; empty effect grants, maybe same-file helpers). One is a docs fix. The rest should be descoped or shelved: generated companion queries, a new `collect` form, a compiler-side module bundler, multi-page resume as part of the same performance RFC, and a new policy-evidence domain whose only proved win is a disconnected table.

Cure-worse-than-disease test: if a change needs a second certified program, a second retry counter, a new wire domain, or a frozen-word trade, it is not “elegance after the corrections.” It is another architecture program wearing 1018’s application-work badge.

## 1018.008.000 — client-owned recovery

This is the only child that clearly removes a builder/user ritual rather than a cleverness. It must be smaller than written.

**Verified (SHA unconfirmed):** `grant_if_low` mints iff client `remaining` is absent/null or `< 1024`; block is 8192 IDs / 30 days; `/api/resume` already carries `remaining?`; `performResume` already coalesces one cancellable flight and loops **three coverage-rebuild rounds**; enqueue demand is `1 + maxNewIds`; offline guide says reconnect never replays, retry `online()` / drain. The 352-ID / 23-send / 85-remaining story is **not re-verified**; it is consistent with a large certified slice (fan-out) plus explicit-only replenishment.

**Material concerns**

1. **High — shared-flight cost is a defect in the proposal, not a leftover question (§6).** If background renewal rides `performResume` and that path re-validates log + mounted + possible reset, low-watermark crossings become silent cold rebuilds. That is worse than a Sync button. **Resolution:** first slice may join the existing flight only when (a) transport/auth actually recovers with admitted work, or (b) resume is already running. Grant mint stays `grant_if_low` on that path. A demand-aware mint that does not re-drain the world requires proving that an existing resume with current validators is cheap. If it is not cheap, **do not** invent a grant-only route (correctly refused) and **do not** ship automatic renewal. Keep Sync.

2. **High — two different “three attempts.”** `resumeOffline` already stops after three *coverage* rounds. §3 adds three *transport* attempts per transition, not reset by rerenders. Merging those predicates will either starve mixed failures or revive retries whenever a later “real reconnect” resets the counter. **Resolution:** reuse the existing flight’s deadline/abort; do not add a second scheduler. If transport retry exists in current policy, name the function. Cap automatic joins at “one flight in flight,” not “three plus three.”

3. **Medium — observer demand registration is I/O dressed as purity.** “`can` never starts I/O” plus “preparing a mutation handle registers demand and schedules renewal” means mounting a composer is a network edge. Disabled-composer UX does not require that: admission-time join plus `can` waiting on the existing flight is enough. **Resolution:** delete handle registration from v1. Recheck demand only in the serialized admission transaction (already the capacity source of truth).

4. **Medium, not an auth bug — remaining is already a client integer.** Lying low already mints extra unused server blocks; the RFC correctly refuses a grant-recovery ledger. Demand-on-resume does not fix that and can mint when remaining ≥ watermark. Fine if capacity is not evidence (§4 is good). Do not pretend “cannot supply its own arithmetic” is a security property.

5. **Hypothesis — “background” on Expo is foreground next-tick.** Say so, or iOS will be treated as an implementation bug.

**§4 invariants stay.** No auto-resubmit of refused/conflicted work; no covering a reset with a live read; no network behind `offline()`; no hook-multiplied coordinators.

**Smaller replacement:** (1) authenticated, not-explicitly-offline client joins existing resume+drain when admitted work is waiting after a real reconnect; (2) successful admission that cannot cover `1+maxNewIds` waits on that same flight rather than failing into a Sync ritual; (3) leave `online()` as the explicit verdict. Delete demand metadata, operation-name-on-resume, and the extra retry state until (1)–(2) are measured.

## 1018.008.001 — derived query presentation

Whole-query truth, separate history receipt, no per-field `unheld`: keep those walls. The *mechanism* is too large.

**Verified:** `templates/chat/shared/thread.ts` repeats table, reverse order, `select`, `belongs` (`c == null` / `c === null`), draft, and `withHistory` around `conversationView`. That duplication is real.

**Material concerns**

1. **High — a second independently certified program is the expensive part, and the motivating case may vanish.** 1019 owns derived delivery/receipts and may change the chat query shape (parent F2/F4). If a post-1019 composite is complete, `withHistory` is dead code and this RFC should close. If it is still partial, authors already have a named `thread` query; generating an internal companion is compiler+metadata+subscription cost against a ceiling that is already near 85k. **Resolution:** prototype on the *landed* 1019 shape before any slice compiler. Kill criterion: no material deletion in the full React/Expo app, including observers.

2. **Definite inconsistency in §3.** Create membership is derived only from exact key/prefix proofs; unknown branch requires explicit `belongs`. The proposed snippet omits `belongs`, but the live `belongs` is cursor policy (`c == null`), not a graph identity. **Resolution:** first slice never infers `belongs`. Draft stays authored. Example must show `belongs` or drop `create`.

3. **Hypothesis / authority — “keep every `require`” can make the slice refuse for the exact composite you care about.** Necessary for not weakening authorization; also why derivation may not delete `withHistory`. Independent review of dropping guards is correctly out of scope — so treat refused derivation as the expected common case, not a surprise.

4. **Medium — internal names still need to be uncallable from app API surfaces.** Ordinary session admission is not the same as “not in the catalog.” If it appears in typed `api.*`, someone will subscribe unconditionally (the RFC forbids that).

**Smaller replacement:** certified *presentation descriptors* only (table, original-row path, order) consumed by `defineItems`. Keep `withHistory(threadItems, …)` authored. Do not lower a companion program unless descriptors-plus-existing-sibling-query still leave a duplicated executable query after 1019.

## 1018.008.002 — bounded collection composition

**Shelf. Do not implement in this batch.**

Demand gate in §1 is the right rule and is not met. The ticket’s original-recipient list is 1019’s problem; remaining examples (effect payload of accounts, display ids) are hypothetical. A frozen-word trade for `collect` without a pasted surviving schema is exactly the collection-language failure mode the brief forbids.

Lineage-through-projection (§3) is the real project: capped-only must not become a complete roster, helper/alias must not erase origin, empty authorized page ≠ hidden run. That is certifier work disguised as syntax. If IR cannot carry origin, the RFC says refuse — which means the feature is “a new node plus a lineage proof,” not a spelling.

**Alternative:** if, after 1019, a real mutation/effect still cannot form a bounded list without an auxiliary table, paste that schema and consider the ticket’s page-projection spelling (`page { .principal }`) as compiler-only lowering. Do not spend `collect` until that day. Do not merge `fn`/`proc`.

## 1018.008.003 — closed effect modules

Split it; one half is a one-line honesty fix.

**Verified (SHA unconfirmed):** `lowerEffect` rejects empty/`non-https` grants; `validateClosure` refuses import/require and escaped non-JSON identifiers; module JSON constants already inline; guide shows a dummy `https://api.example.com` grant.

1. **`grants: []` — implement.** Runtime fetch still grant-checks; empty list refuses before transport; no static “this doesn’t fetch” proof. Deletes the guide’s lie. Tiny, no loader, no twin change.

2. **Cross-file import assembly — defer.** §2 is a bundler: realpath, named imports, cycle refusal, scope-aware rename, deterministic identity, no `check`-time evaluation. Compiler size is not the 85k runtime, but this is how you get symlink/path bugs and spurious outbox identity breaks. §6 already offers the reduction; **make imported function declarations + JSON constants the *fallback*, and same-file closed helpers the first slice.** Today a sibling `function makeRequest()` next to `run` is an escaped capture; admitting same-file closed functions removes most copy-paste without a module graph.

**Medium:** effect identity must include *used* helper bytes after a specified normalization (comment strip, specifier canonicalization, binding order). Unspecified normalization will churn `then`/outbox compatibility. Reuse 1021’s effect-change rules; don’t add a second identity function.

**Kill criterion (already in §5):** if two real effects do not share a helper after 1021, don’t assemble modules. Empty grants still ship.

**Smaller replacement:** measurement plan + permission to delete duplicate work under existing swap/subscription contracts. No protocol change in the same commission.

## 1018.002 §7 — narrower invalidation

§1–§6 are a good authorization document. §6’s decision (retain whole-schema `rule_hash`; disconnected-table candidate does not solve `messages.category`) should have been the end.

**Material concerns**

1. **High — payoff is still the wrong edit.** The witnessed pain is an optional column on the *subject* table. The candidate that can be proved is an optional column on a *disconnected* table. If apps evolve `messages` and not `notifications`, the experiment’s green cell is contrived. The RFC already says close in that case; **make that the default**, not a hope after building dual-domain mint/replay/twin lookup.

2. **High — do not run the subject-field treatment in the same diagnostic.** Field-level “what the rule actually uses,” including unexecuted branches, is how revocation/disclosure is missed (optional materialization, row-digest encoding, certifier structural visibility, index descriptors). A row digest that changes must not be normalized away — agreed — so the two-write failure remains unsolved. Mixing treatments is how a field-level “win” contaminates the disconnected-table candidate. **Hard stop: whole subject descriptor stays in.**

3. **Medium — an “isolated experiment” with a new distinguishable evidence domain is production-shaped code** (native produce, native replay, twin lookup, old envelopes conservative). That is the implementation §6 deferred during closeout. Don’t smuggle it back as research tooling.

4. **Alternative with better security/cost:** keep broad binding. On successor, surface queued-write review (“N intents will conflict”) rather than a second hash. Coverage reset remains mandatory (producer table in §6 is the useful artifact: replay identity ≠ policy ≠ coverage). 1020 owns additive successor evolution; this RFC must not shadow it with a compatibility story.

**Verified in the RFC’s own audit, not re-traced here:** `Schema::rule_hash` / twin `scopedRuleHash` bind `(whole schema, enclosing rule)`; stable replay digest is `(op, args, envelope)` and is looked up before program/trace/grant; `E_OFFLINE_RESET` on generation/schema mismatch. Those separations are the elegance; a narrower digest is not.
