### 2. Schema in v0

Spellings v0 forces: enums are `S(n)` = `text({ max: n })` with transitions checked in `(old, next)` rules; "null" is `''`/`0` (no `optional`); an open interval is `validTo: 0` **[inferred]**; each "partial unique" becomes a pointer column on the parent (`matches.openDisputeId`) or a keyed side table (`currentReports`). `…tid` means the row carries `tournamentId: ref(tournaments)` so rules are one hop.

const isTO = tid => db.exists(tournamentTos.byTournamentUser, [tid, viewer]) || db.exists(orgTos.byOrgUser, [db.get(tournaments, tid).orgId, viewer])   // two-hop; cost reported, hoisted when tid is pinned

The first attempt with the design's "scan forward for the first non-rematch, 2,000 global attempts" certifies the inner loop at its literal 2,048 — `maxSteps ≈ 4M` — because a global attempt counter is a runtime meter the checker cannot credit; the window over a linked list is the static-bound form. No job: invariant 17 requires the round to be one transaction, and a `schedule` under the system principal is the timer.

**Money (5.8, 5.9, 5.13).** `contributeToPool` requires `poolState === 'open'` (or an overflow policy) and inserts one `pending` row; the effect `createPaymentIntent` runs after commit (outbox, §6 #11) and returns the client secret out of band; nothing on the page moves (`W ≤ 1`, closed). The webhook effect calls `settleContribution` as system: return if not `pending` (idempotent, plus the unique payment id); set `settled`, `feeCents`, `netCents`, `settledAt`, and `stranded: locked` so a late settlement never enters this snapshot; if locked and `overflowPolicy === 'next_event'`, insert a settled row on the overflow pool keyed `c.id + ':overflow'`; if open, for each `active` sponsor rule (`take: 8`) with `s.window.contains(args.settledAt)` add `net` to `eligibleNetCents` — per-sponsor windows are interval containment in a program (ruling 11), not a rule. `E ≤ 13, W ≤ 10`. `recordReversal` inserts the reversal (`afterLock = poolState !== 'open'`; a duplicate webhook is `E_CONSTRAINT` on the event id), flips `poolState` to `shortfall` when after lock — the shortfall itself is the maintained sum, so no snapshot row is edited (the design's 5.8 edits one, against its own invariant 24) — or subtracts from in-window sponsors when open.

`lockPool` (5.9; the `lockPrizePool` mutation and its schedule at `prizeLockAt`) returns if not `open`; computes `community = communityNet − reversedNet` from two maintained rows, `matched = Σ min(capCents, divmod(eligibleNetCents × matchBps, 10000).q)` over the ≤ 8 `active` sponsor rows, `total = guaranteed + community + matched`; requires percent rules to sum to 10000 (or none) and fixed rules `≤ total`; inserts the `poolSnapshots` row and sets `poolState: 'locked'`. `E ≤ 80; W ≤ 3` — the live formula is three maintained rows plus eight sponsor rows; no contribution is scanned.
`finalizePlacementsAndPayout` requires `poolState === 'locked'` and `shortfall === 0`; for each prize-bearing phase `nonTerminalCount === 0` and `protestOpenCount === 0`, and `openDisputeCount === 0`, unless `forceFinalizeReason` is set (invariant 25 over maintained resource facts); reads the final generation's matches (`take: 1024`) and slots; elim placement = f(loss round) from the losing slot's `playedAsEntryId`, ties within a round broken by seed order (the design leaves this open, §8), RR/Swiss from the final `rank`; inserts `placements` (unique per placement and per entry); allocates from the latest snapshot's `totalCents`: fixed rules first, then `divmod(pot × bps, 10000).q` per percent rule, remainder cents +1 to the best placements in order (ruling 10's deterministic sink); inserts a `pay` row `pending` iff `byIntent` is absent (idempotent re-run). `E ≈ 3,170; W ≤ 2,114`. The effect `sendTransfers` reads `payoutLedger.byTournamentState [t, 'pending']`, calls the processor with idempotency key = ledger id, and calls `markTransferSent` (system; unique transfer id; `poolState = 'paid'` when `unsentPayouts` reaches 0).

**Reads (5.12 and the page).** `bracketProjection(phaseId)`: generation → `matches.byGenRound [gen] take 1024` → two `matchSlots` point reads per match; spectators get `displayEntryId` (locked name if locked, derived name if clean, else a placeholder from `sourceType` + source code) and official scores only from terminal states, because those are the only public columns; the TO additionally reads `slotDerivations` (2,046 point reads, hidden to others) for dirty flags. `swissRoundView(phaseId, roundIndex)`: `matches.byGenRound [gen, round] take 1024`, slots, `swissStandings.byGenRank [gen] take 200`, my match via two `byGenEntry0/1` probes. `matchView(matchId)`: match, two slots, own current report, the opponent's under the §2 rule (a verdict; `partial` locally until it flips). `tournamentPage`: row, phases, pool, sponsors, `entryCount`/`checkedInCount`. `prizePoolWidget`: open ? `communityNet − reversedNet + Σ min(cap, bps × eligible)` : latest snapshot, plus `shortfall`. `registrants`: `entries.byTournamentStatus [t] take 2048`, rule hoisted on `registrantsPublic`. `checkInDashboard`, `toDisputeQueue` (`disputes.byTournamentState [t, 'open'] take 100` + matches), `auditLog`, `payoutStatus`, `contributorList` (a contributor-published `contributionNotes` table, omitted) are ordinary bounded scans.

### 8. Where the design is wrong

1. **Its DE construction produces the BYE-vs-BYE it forbids.** WB round-1 losers pair into LB round 1 in reverse order; with `n ≤ 3P/4` two adjacent WB-1 matches are both byes, so an LB-1 match has two BYE occupants and step 11 plus invariant 9 leave it `pending` forever or refuse the generation. *Observation:* 5-entry DE, P = 8: byes at positions 6–8; WB-3 (2 vs BYE) and WB-4 (3 vs BYE) feed LB-1's first match → BYE vs BYE; the drop rounds never fill. Every 5-, 9–12-, 17–24-entry double elimination hits it.
2. **"Random with a stored seed" is TO-choosable.** `random_salt = H(generation_id)` and ids are client-mintable (the design's idempotency story needs that), so the TO mints candidates offline, evaluates the draw for each, and submits the one it likes; "same spec bytes → same DAG" holds while fairness does not. *Observation:* mint 1,000 generation ids, run `generate(spec)` for each, submit the one that byes your friend; the audit row shows a valid salt.
3. **Swiss pairings consume results without an edge, so the reversal path has no lock to stop at.** Occupancy lock guards elim cones through `source_match_id`; round r+1's pairing is a derived consumer of round r's results with no pointer back. 5.5's "reverse official result only if no downstream occupancy lock" finds no downstream and reverses, leaving round r+1 paired on a result that no longer holds and Buchholz written under the old one. *Observation:* four-entry Swiss, round 2 paired; a round-1 reporter edits inside the protest window; the opponent's counter disagrees; TO `set_score` flips it; nothing marks round 2 dirty, and the round-2 standings snapshot now disagrees with the official graph it claims to summarize.
