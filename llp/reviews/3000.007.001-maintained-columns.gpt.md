The direction is justified, but the design is **not ready for implementation**. The important gaps concern hidden-data disclosure at birth, prediction over streamed images, and adoption—not the column syntax. Several protections attributed to existing machinery are narrower than the proposal requires.

I reviewed baseline `d2011343f0b4e34195155320b0e18fdac19964d0`. This is a static review; I ran no builds or tests, changed nothing, and did not consult other reviews.

**1. High — §3.2: the stated reservation does not establish hidden-parent noninterference.**

`maintain_scratch` reserves heap, not the complete meter. `reserve_maintains` returns early for uniformly readable sources and for sources without a filter, computed key, or expiry. Ordinary insertion does not call that reservation. Those conditions protect particular *hidden-source* cases; they say nothing about whether the independently governed parent is hidden.

Consider a public source with `count likes by postId`, and a parent unreadable to the writer. In one world the parent is absent; in another it exists. Following the proposed final step, only the second world writes and indexes a parent. Without additional prepayment, ample-budget meters differ; near a ceiling, success can become `E_BOUND`. Furthermore, partition charging currently selects the maintain meter by **table classification**, not `Origin::Maintained`, so changing only aggregate charging is insufficient.

Evidence: `engine/write_target.rs:287`, `engine/write.rs:30`, `engine/maintains.rs:29`, `partition.rs:152`.

**Smallest design change:** specify a separate, unconditional hidden-parent reservation for every relevant source-write path. Before resolving hidden state, prepay the schema-bounded maximum for old/new parent attempts, all affected indexes, row writes, partition work, and heap; suppress corresponding actual charges consistently. State the treatment of no-op and `if absent` arms explicitly.

The raw parent `get` and `expired` predicate do not themselves meter according to existence; the divergent downstream work is the problem. Different non-overflow values must remain indistinguishable. Near the endpoint, the explicitly admitted overflow bit is an exception, so §8’s equality assertion must exclude that case and test the exception separately.

**2. High — §§3.3, 3.7, 3.8: birth exposes hidden population work and cannot always predict from local sources.**

Let the declaration count only selected source rows. A principal creates a parent under a chosen id. Compare:

- No source rows have that id.
- 100,000 unreadable source rows have that id, all excluded by the predicate.

The declared aggregate is zero in both worlds. A scan through the required `by`-leading index nevertheless has different examined work, meters, and potentially `E_BOUND`. This reveals hidden information beyond the declared aggregate, even when the creator can read the new parent. An insert rule need not grant parent read access either, making the distinction more consequential.

Deletion and recreation repeat the experiment; “paid at most once per parent” is misleading when the same id can be recreated.

On a device, an empty local scan is not evidence that the group has no hidden or unacquired contributions. Creating the parent and displaying zero cannot inherit the “held parent means known base” argument: this is precisely the operation that must establish that base.

Evidence: RFC:140, RFC:150; the existing uncertainty mechanism is `engine/local.rs:126`, and the existing maintain device path distinguishes unknown aggregate bases at [maintains.rs:157](snapback4/crates/snapback4-core/src/engine/maintains.rs:157).

**Smallest design change:** settle birth as a separate contract. Require population-independent birth work, for example by retaining an internal per-key aggregate while the parent is absent, or explicitly declare and diagnose the additional birth-work disclosure. The current count-only disclosure statement cannot cover it. Device birth must require complete source-group evidence or a valid zero/base certificate; otherwise queue without prediction.

Refusing contributions to absent parents is not a free repair. It creates a parent-existence outcome channel unless coupled to readable-parent authority, and breaks forward references, source-before-parent seeding, and the proposed ability to predict a source write while its parent is unheld.

**3. High — §3.7: a streamed parent image may already include a prediction that replay applies again.**

The stream replaces a logged `put` with the **current** row image. Its watermark still describes the selected log page, and acknowledgements are restricted to that watermark.

Concrete sequence:

1. Commit 10 adds another user’s contribution.
2. Commit 11 accepts this device’s predicted contribution A.
3. The device receives a page ending at commit 10.
4. The parent image fetched for that event already contains both contributions: count 2.
5. A is not retired at watermark 10, so replay inserts its still-unreceived source row and increments the parent to 3.

A later page repairs this, but an interrupted connection leaves the device holding and displaying the wrong count. The JavaScript sync loop reruns affected watches in `finally`, including after interrupted catch-up.

Evidence: [partition.rs:617](snapback4/crates/snapback4-core/src/partition.rs:617), [engine/mod.rs:740](snapback4/crates/snapback4-core/src/engine/mod.rs:740), `device/predictions.rs:57`, [local.ts:678](snapback4/packages/snapback4/src/local.ts:678).

**Smallest design change:** require confirmed images and replay suppression to describe the same causal boundary before publishing the overlay. Staging ordinary catch-up until a suitable confirmed boundary is one possible resolution; version-aware image/acknowledgement handling is another. Merely sending historical payloads would conflict with the existing current-read-authority policy.

This is an existing protocol interaction, not an implemented maintained-column defect, but it invalidates the design’s claim that holding the streamed row is always sufficient evidence for exact prediction.

**4. High — §3.7: “skip unheld, then replay when held” changes the affected-row set, which the client does not track.**

A predicts a like while P is unheld, so its saved `predicted` list contains only the like. An unrelated server update later delivers P. Replay now increments P, and the UI displays that increment. A subsequently fails on the server.

Settlement restores P correctly in storage. However, successful replay discards the returned written-row list, and the client invalidates watches using A’s original `predicted` list. A watch over P can retain the provisional count after A has failed.

Evidence: `device/predictions.rs:73`, [device.rs:761](snapback4/crates/snapback4-device/src/device.rs:761), [local.ts:1011](snapback4/packages/snapback4/src/local.ts:1011).

**Smallest design change:** make replay’s affected rows part of the maintained-column contract. Refresh persisted prediction effects after successful replay and return the complete restored/applied/replayed table set for invalidation. Cover failed settlement and withdrawal, not just successful server convergence.

**5. High — §3.11: rebuilding only nonzero parents preserves stale values after redefinition.**

P currently contains `likeCount = 5`. Adoption changes the predicate so that P’s new aggregate is zero. The specified rebuild writes only nonzero totals, so P retains 5. Missing-field materialization cannot fix an existing field.

The current maintain rebuild avoids this by deleting its entire target before rebuilding. That algorithm cannot be reused for a parent table containing application data.

Evidence: RFC:232, `schema.rs:1264`, `engine/maintains.rs:77`.

**Smallest design change:** distinguish initial addition from redefinition. Skipping physical writes for zero is valid only when the previous image has no maintained value. Redefinition must replace every changed value, including nonzero-to-zero transitions, while preserving all ordinary fields and other maintained columns. Specify removal separately.

`Additive` is defensible for adding recomputable derived data; it must not mean “no parent rows change.” In particular, do not let a column target trigger `successor.rs:62`’s whole-maintain-table comparison bypass.

**6. High — §§3.5, 3.11: a large activation can create an undeliverable commit that prevents generation recovery.**

The current activation builds with unbounded ceilings and emits its rebuild events in one commit. Streaming preserves whole commits. Rewriting 100,000 publicly synced parents of roughly 500 bytes produces far more than the HTTP response ceiling.

The response encoder substitutes an `E_BOUND` body that contains no generation. The client responds by shrinking the page limit, eventually to one; that cannot split the commit. Because generation adoption occurs after successful page decoding, the client can remain unable to discover through this path that it should discard its images and snapshot instead.

Evidence: `engine/mod.rs:440`, [partition.rs:568](snapback4/crates/snapback4-core/src/partition.rs:568), [serve.rs:641](snapback4/crates/snapback4/src/serve.rs:641), [local.ts:574](snapback4/packages/snapback4/src/local.ts:574).

**Smallest design change:** define adoption as a generation barrier that can be delivered independently of rebuild row volume. Devices requiring reacquisition must learn that before attempting to consume the rebuild commit; ordinary full-image events can then be suppressed or replaced by an explicit invalidation/reacquisition mechanism. Measure that actual delivery path.

The existing SQLite transaction publishes the rebuilt data and generation together, and failed builds roll back; device generation checks reject crossed pages. Those are sound foundations against intermediate zeros. Postgres currently has **no activation/migration API**, so it supplies no adoption-parity evidence: [postgres/mod.rs:75](snapback4/crates/snapback4-core/src/engine/postgres/mod.rs:75).

**7. Medium — §§2, 3.9: define semantic dependencies, including generated-source existence.**

A declaration equivalent to:

```text
maintain likeGroups: count likes by postId
posts.groupCount: count likeGroups by postId
```

meets the column form’s stated reference/index/non-expiry conditions without reading an aggregate value. Nevertheless, changes to `likeGroups` use `Origin::Maintained` and do not fan out; `groupCount` becomes stale. The existing maintain binder rejects another maintain as its source, but the new form needs that restriction explicitly.

Likewise, “in any rule” must include positional index probes and target-side extra equalities, not just locally named fields. `RuleExpr::fields` does not enumerate those dependencies or `OldField`/`NextField`. A rule probing an index containing the column could otherwise change truth and indirectly change another table’s audience.

Evidence: `bind/schema.rs:548`, `schema.rs:539`, [write.rs:529](snapback4/crates/snapback4-core/src/engine/write.rs:529).

**Smallest design change:** define a resolved dependency walk shared by binder and core schema validation. Include index components, probe targets/equalities, old/next terms, constraints—including final-exists—and sync dependencies. Explicitly reject generated maintain sources while permitting ordinary source tables whose maintained columns are not dependencies.

A self-referential `replyCount` is not inherently a cascade and need not be refused. Test self-id insertion and reference cycles, with birth initialization ordered so the new source row contributes exactly once. A maintained column in a job chunk index is already excluded by the immutable-index rule; preserve that refusal.

**8. Medium — §3.7: unmarked engine writes must preserve an existing ordinary prediction marker.**

“Does not set `pending`” is sound for a count-only overlay on a confirmed parent. It must not mean “clears `pending`.”

`Predicting` strips the marker from runner reads and currently adds it on every write. An origin-aware replacement that simply writes the marker-free image would erase `pending` from an earlier predicted parent edit or parent birth. Restoration does not search by the marker, but other behavior does: `asset_home` rejects pending rows.

Evidence: `device.rs:178`, `device.rs:189`, [device/media.rs:102](snapback4/crates/snapback4-device/src/device/media.rs:102).

**Smallest design change:** specify that an engine-only prediction does not introduce the marker and preserves any marker already justified by an ordinary prediction. It must still call `remember` and record its affected row. Test both orderings of overlapping ordinary/aggregate predictions and withdrawal of either one. With that requirement, “first image kept wins” correctly restores the common confirmed base.

**9. Medium — §3.8: the disclosure note needs a different suppression proof.**

Private likes can have insert/update/delete rules implying their own read rule while public posts disclose their aggregate to everyone. The existing `N_MAINTAIN_DELTA` implementation suppresses its note when source writes imply source reads. That implication does not prove that **parent readers** can read the contributing source rows.

Evidence: `bind/residency.rs:293`.

**Smallest design change:** suppress the new note only when parent-reader access to the relevant contributions is proven; otherwise report conservatively. Describe sums as sums, filtered aggregates as predicate-dependent facts, and indexed order as an additional observation. Keep the overflow bit explicit, including for writers unable to read the parent. A missing parent is absence, not a readable zero-valued parent.

The rule-free restriction is appropriate for the first build. Allowing counts to determine audience would require a separate design for revocation and prediction.

On authority specifically, I found no need for a new privileged application write API. Native writes enter the ordinary runner, seeds call `upsert`, Postgres mutations use the same runner, and receipt replay returns execution identity without applying the write again. Field refusal must therefore remain unconditional under system context and operate on the **submitted** fields: an explicit zero is forbidden too, including an `insert if absent` that would otherwise do nothing. Internally materialized zeros and retained fields from `merge_patch` must not be mistaken for caller assignments. `Engine::load` and its Postgres counterpart deliberately accept precomputed fixture images; document them as trusted fixture exceptions, or require aggregate verification before such data is served. Device mutation requests submit operation arguments, not authoritative predicted row images.

For §3.6, accept and measure the existing acquisition behavior. A streamed `put` really does insert an unknown row. Costs are approximately one full parent image per changed parent, per commit, **per destination partition**, plus envelope/index work; multiple changes can coalesce within a commit, while successive commits remain separate. A device filter would need durable per-group acquisition boundaries, the complete ordering tuple, confirmed-held membership, snapshot/generation state, and rules for newly inserted or ordinarily updated rows. An aggregate-only filter would additionally need event provenance absent from the current ordinary `put` contract. A timestamp check alone is insufficient.

I would retain the column form after these repairs. `maintain … over posts` preserves table-level writer separation and could reduce replicated payloads, but it still needs parent-domain zeros, parent lifetime/audience behavior, tie-breaking fields, and a projection story. P2 supplies concrete reasons to put this fact on the parent. The corresponding obligation is to rewrite P5 precisely: ordinary fields retain their existing writer class; each maintained field has exactly one declared engine derivation. I would pursue total-unique parent addressing before cascades.

Finally, §8 needs more discriminating acceptance criteria:

- **Oracle:** use an independent model; include recreation, self-reference, zero transitions, multiple maintained columns, sums, rollback, and actual Postgres mutations. Device assertions must distinguish known bases from incomplete birth scans.
- **Refusals:** exercise every write arm, including existing/missing upsert targets, no-op `if absent`, native/system writes, raw IR, and raw schema dependency violations.
- **Paired observations:** compare every meter and public outcome at ample and just-insufficient budgets; include expired parents and filtered-out orphan populations. Test overflow as the declared exception.
- **Device:** inspect intermediate states after each page, interrupted catch-up, failure, withdrawal, generation change, and overlapping predictions—including watched results, not only stored rows.
- **Cursor:** assert the documented moving-key contract explicitly; eventual correct ordering alone does not test continuation behavior.
- **Notes:** include private-source/public-parent cases whose write rules imply source readability, plus filtered sums and indexed disclosure.
- **Published examples:** the ranking assertion is useful documentation protection, but it does not replace executable attempts to write the column or manipulate its source outside source authority.

The §7 measurements should include serialized HTTP bytes, peak rebuild memory, durable log growth, retry/contention behavior, and whether a real device completes adoption. Activation elapsed time alone would miss the undeliverable-commit failure.

Verdict: NOT READY
