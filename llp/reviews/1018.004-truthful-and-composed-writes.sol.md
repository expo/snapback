REVISE. The durable-inbox architecture is sound, but commit `c6e2cb02b` has material correctness gaps in follower observation, FIFO ordering, custody, and readiness. I pinned all citations to that commit because the shared worktree advanced to `8c7bdb2f` during review. LLP orientation treated 1018.004 as superseding 1018.000 §8 while retaining 1012 §7’s FIFO rules. `node build.mjs` and 26 selected tests were blocked by the read-only filesystem (`EPERM`); 28/54 tests completed successfully, including all six inbox tests and 21 client-session tests. Caps passed; the browser witness was not run, as requested.

1. **MATERIAL — Follower hydration is neither coherent nor ordered before network work.** `src/offline.ts:401-405` reads `inbox` and `outbox` in two separate readonly transactions. An admission swap between them produces the old unadmitted alias and the new ledger entry together, so `entries()` can list one write twice. Separately, `src/client.ts:1028-1030` returns immediately after `TabFollower.begin`, while `src/client-sessions.ts:470-481` fire-and-forgets `runtime.follow`; therefore the durable read is not ordered before later network activity as §2 requires. The test witness only checks that no `/api/mutation` occurred, not that the durable rows appeared before any network request.

2. **MATERIAL — An admitted-but-queued follower write disappears from status and settlement.** Both `ClientInbox.status` (`src/client-inbox.ts:170-179`) and `followerSettlement` (`src/client-outbox.ts:276-284`) count queued ledger entries only when `entry.inbox === undefined`. Every admitted follower entry has `inbox` set, while its row no longer contributes to `inboxPending`. Consequently a follower can report `remaining: 0`, and `outbox.settled()` can report `{ stopped: false, remaining: 0 }`, while that entry is still queued for server replay.

3. **MATERIAL — Durable dismiss commands bypass backend, principal, epoch, and custody checks.** `OfflineRuntime.admitInbox` consumes `kind === "dismiss"` at `src/offline.ts:445` before the identity checks at lines 447-450. `OutboxLedger.consumeDismiss` (`src/store/outbox.ts:433-447`) performs no equivalent validation. Because database and lock names omit backend URL, a follower on a foreign backend with the same prefix/principal can insert a dismiss row that deletes the first backend’s terminal entry. A runtime probe reproduced exactly that deletion.

4. **MATERIAL — A smaller writer-local mutation can overtake an older durable follower row.** `submitMutation` awaits `admitInbox` at `src/client-outbox.ts:96`, but `ClientInbox.admit` discards `outcome.stopped` (`src/client-inbox.ts:267-276`). When admission stops on `E_OFFLINE_ID_BLOCK` (`src/offline.ts:458-463`), the local enqueue proceeds. With 36 grant IDs remaining, an older follower mutation needing 52 IDs stayed as `inbox:1`, while a newer local mutation needing one ID entered the ledger. That violates §2/§4’s device-wide durable order.

5. **MATERIAL — Capacity readiness does not use the capacity predicate enforced by insertion.** `IndexedDbInbox.insert` counts every row whose state is `queued`, including admitted mirror rows and dismiss commands (`src/store/indexeddb.ts:144-154`). Follower status checks only `runtime.inboxPending`, meaning unadmitted mutation rows (`src/offline.ts:426-427`, `src/client-inbox.ts:176-179`). Thus status can remain ready with `forwarding` or `writer-unresponsive` while the next `run()` refuses `E_OFFLINE_INBOX_FULL`. A 256-row probe reproduced the contradiction.

6. **MATERIAL — Admission does not preserve the required operation-fence custody check through commit.** `OutboxLedger.admitInbox` calls `custody()` once at `src/store/outbox.ts:410`, then `enqueueNow` awaits grant, bounds, and prediction before committing (`src/store/outbox.ts:318-387`). Its caller at `src/offline.ts:459` supplies no `beforeCommit` fence check. Meanwhile an authority transition increments the fence and stops the inbox (`src/client.ts:1266-1282`), but `settleWrites()` does not await background inbox admissions (`src/client.ts:1405-1416`). A nudge- or poll-started admission may therefore commit after its captured authority was superseded. This is weaker than the predecessor’s before/after-prediction and before-commit checks that §2 explicitly preserves.

7. **MATERIAL — `detail.writer` is not exposed.** `ClientInbox.writer` exists internally (`src/client-inbox.ts:163-164`), but `OutboxSnapshot` contains only `{ entries, status }` (`src/types.ts:360-363`), and the hook types and implementation expose only `detail.status` (`src/react-core.tsx:186-205,213-225`). This misses the explicit §3 contract for the announced writer grant state.

8. **MATERIAL — The blocking Rust init tests still require the deleted recovery modules.** `crates/snapback2/tests/init.rs:790-865` asserts that `shared/recovery.ts` and `shared/send.ts` exist and that generated Composer/Thread files import them. Those files were deleted by this commit, so the repository’s blocking Rust suite has deterministic stale failures.

9. **MINOR — Recovery/forwarding residue remains after deletion.** `guide/offline.md:17-18` still says followers “forward replayable writes”; `src/client.ts:1025-1026` and `src/client-sessions.ts:441-443` retain forwarding terminology; and `tests/chat-screens-recovery.test.ts:19-21` still promises a pinned-ID bubble without remounting, contrary to §5’s accepted inbox-alias rekey.

10. **REFUTED-RISK — The write record itself is correctly reduced to three outcomes.** `MutationResult` is exactly committed, rejected, or queued (`src/types.ts:104-127`). `jsonArguments` validates before insertion and `inboxEntry` gives unadmitted rows the specified empty fields (`src/store/inbox.ts:57-99`). `queuedIntents()` reads only the ledger, and item attachment falls back to the alias intent; retirement still requires `committed`. No removed unknown/recovery public type or method remains.

11. **REFUTED-RISK — Writer-side storage atomicity and lifecycle are substantially correct.** Version 4 creates an auto-increment inbox; follower insertion uses `add` with count and insertion in one transaction; admission uses a per-key inbox delta in the same transaction as grant, outbox, and overlay; `versionchange`, bounded `onblocked`, and wipe-under-lock are present (`src/store/indexeddb.ts`, symbols `openDatabase`, `IndexedDbInbox.insert`, `replace`, and `wipe`). Idempotent re-read and `admitted` checks are present in `OutboxLedger.admitInbox`. The fake models scoped snapshots, overlapping readwrite scheduling, `add` versus `put`, connection closure, and blocking lifecycle; the overlapping writer-swap/follower-insert test passed. The separate cross-store follower reads are the exception reported in finding 1.

12. **REFUTED-RISK — Most liveness and template obligations hold.** Writer activation, inbox nudges, ledger-change retries, 30-second/5-second writer polls, and `admit()` coalescing are present; the no-change guard prevents a notification loop. `TabFollower.begin` places inherited admission after reauthentication and before the first resume, with cancellation checks around each step (`src/client-sessions.ts:480-499`). React and Expo composers preserve capture, in-flight suppression, exact-draft clearing, and thrown-refusal notes; the Expo composer contains no recovery custody. However, `ClientInbox.following` arms its follower poll before the asynchronous durable read, while `refresh()` never rearms it (`src/client-inbox.ts:109-122,241-248,315-335`), so a reloaded follower with BroadcastChannel and persisted rows gets neither its two-second fallback poll nor the five-second unresponsive timer.

13. **REFUTED-RISK — Budgets and production deletion are within the stated bounds.** `client.ts` is 1,496 lines and `range-store.ts` 1,499; `scripts/caps.mjs` passed. The recorded c6 bundle is 80,999 gzip bytes, below the 84,000 hard ceiling though above the 80,000 working target. The forwarding source modules and template recovery modules are deleted without compatibility shims; the remaining deletion problem is the stale blocking tests in finding 8.

VERDICT: REVISE

The architecture is viable, but `c6e2cb02b` violates core truthful-readiness, FIFO, custody, and follower-observation contracts and leaves the blocking init suite inconsistent.
