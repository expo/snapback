## Findings

### 1. High — §2.2. The withheld page is not a state this client has

§2.2 requires three things at once: no data and no `next` when a card misses, offline `loading`, and no server page while a predictable write is unobserved. It then says to use the existing fallback. Those are two different branches, and each one breaks one of the requirements.

A card miss is a normal point read. `get_inner` records `unknown_fact` and still returns null (`read.rs`). The row stays in the page. `call.rs` sends `data`, `next`, and `unknown`. `query_unavailable`, the flag that strips `data` and sets `loading`, is only set for a meter or scalar cut (`runner.rs`). A horizon miss does not set it.

- **Unknown, data kept** (what “the existing fallback” does). Online with nothing predictable pending, `wantsServer` retries the original `args` (`local.ts`, the `wantsServer` return). That part is right. Offline, or while a predictable write is pending, that same function returns `first.result`: the null card and the continuation. That is the revision-1 bug.
- **Loading, data stripped** (what “offline, the query is `loading`” does if implemented with `unavailable`). Online, the branch above the pending check fires first: `loading` and `link === "online"` calls `server()` immediately (`local.ts`, the `loading` return). It does not consult `pending()`. A predicted own post is then replaced by a server page that does not contain it. That fails the §5 test, and it is the trap the previous review named.

`pending()` is `(predictable ?? predicted.length > 0)`. A repost that already queued with no row has `predictable: false`, so it does not block fallback. The write that must block fallback is an own post that did predict.

**Scenario.** The shaped page is `following last 20 by .at { *, card: posts[.post] }`. Row 3 is a repost of a post outside the posts floor, so the card misses. The user has also inserted their own post, which predicted. Offline, the unknown path publishes twenty rows, a null card, and `next`. Online, the loading path publishes the server page and the own post is gone until the write is observed.

**Smallest change.** Stop citing the existing fallback. Specify one client result. A card point-read that is undecidable (horizon miss, or any read of an `online only` source — that one calls `unknown_fact` even on a hit) makes the query `{ loading: true }` with no `data` and no `next`. Online, call the server with the original args only when no outbox entry is still predictable and unobserved. Offline, or while one is, publish that loading result and do not take the current `loading && online → server` shortcut. Say the §5 bullet is this shaped query. The unshaped inbox page does not look at `posts` and is not withheld.

### 2. High — §2.1. `last N` on owned events makes a known absence undecidable

Owned events are not a second copy of `posts`. `@T@Posts` has one row per original and one per repost (`timeline_apply`). A point miss on a horizoned table always calls `unknown_fact` (`get_inner`), and `timeline_get` then aborts with `Prediction` before `require(FEED_POST_NOT_FOUND)`. Full sync is what makes “no event” a refusal instead of a queue.

**Scenario A.** Posts horizon 2. Posts at t=1 and t=2, plus a repost of the newer one at t=3. Newest 2 events are the repost and the t=2 post. The t=1 post is still inside the posts floor, so its card hits. Reposting it reads `posts` by id (hit) and `@T@Posts` by `byActorPost` (miss). Prediction queues with no row. §2.3 says it predicts, because the original is held.

**Scenario B.** A reply is inside the posts floor, but the originals filter never inserted an event. Today that repost refuses `FEED_POST_NOT_FOUND` on the device. With an events horizon the miss is undecidable, so the write queues and the server refuses later. The same split happens after removal: the post row is still held (`removed: true`), the event was deleted, the tombstone is fully synced, and the repost queues instead of refusing.

`write_site` would also keep `byActorPost` as `Held` unless told otherwise, so `check` would not say this queues. “The same N” cannot mean “every event whose post this device holds.” Repost events consume slots in `@T@Posts` and do not exist in `posts`.

**Smallest change.** Delete the derived events floor. `@T@Posts` stays `sync public` with no horizon, and it stays in the inventory. Do not horizon it in this RFC. A horizon has no way to say “absence is known because the row was deleted or never admitted.”

### 3. High — §2.1. The `(at, id)` rule rejects the inbox index the same section requires

A horizon page is locally known only when `horizon.by == scan.index` and the scan is descending (`read.rs`, `by_boundary`). Otherwise `known` is false and every page is `unknown`. The Following scan is `byReaderPage`: `readerId, at, eventId, epoch, id` (`timeline.q`). The inbox line correctly names that index.

The next bullet refuses every horizon index that is not `(at, id)`. `byReaderPage` is not that, even after the `readerId` prefix: `epoch` and `eventId` sit between `at` and `id`, on purpose, so a nullable epoch has a stable cursor. The schema check also requires a horizon index to lead with the audience columns. For a public table that is `(at, id)`. For `Feed` it must start with `readerId`. One refusal cannot apply to both.

**Scenario.** Admission applies the bullet as written, refuses `byReaderPage`, and the implementer points the inbox horizon at a synthesized `(readerId, at, id)` index. The page scan stays on `byReaderPage`, `by_boundary` is false, and every Following page is `unknown`. The device never answers the paved page offline, which is the opposite of §2.2.

**Smallest change.** Restrict the `(at, id)` refusal to public `posts` and `reposts`, using each table’s mapped time column plus `id`, not the spelling `at`. State that the inbox horizon index is `byReaderPage` and must be the scan index.

### 4. Medium — §2.3. `online only` does not predict, and §2.3 says it does

`online only` is a peer of the horizon in the §2.1 table. A write to a table with no `sync` is a `Server` site (`residency.rs`, the `sync.is_none()` arm), so the mutation is `predicts: never`. The client’s `predictable` flag is also false when any touched table has no `sync` (`local.ts`). Independently, a device read of an `online only` table calls `unknown_fact` before it looks at the row (`read.rs`), so a local post image would not make the shaped page known anyway.

**Scenario.** `posts` is `online only`, so owned events are too under §2.1. Alice publishes. There is no local post and no inbox copy. The shaped home goes to the server, which does not have the post yet. §2.3 says the local row is the card and the inbox copy is written.

**Smallest change.** Say §2.3 is the horizon case. `online only` posts or reposts do not predict. Shaped pages stay on the server, which §2.2 already says. The guide sentence is the one the previous review asked for: `online only` removes prediction eligibility.

## What is sound

- The paved read does not load `posts`. `feed_view::read` reshapes the inbox projection. A global posts horizon does not by itself punch a hole in that page.
- The per-reader inbox floor is a normal column horizon: one group, the viewer, newest M on `byReaderPage`, fixed at acquisition, no eviction. Default M = 1,000 means one merged suffix, not 1,000 per author. That is what the machinery will do if the index rule is scoped.
- Own-post prediction does not read the old event row. It inserts one and copies it into the author’s own inbox. A posts horizon does not stop that, as long as events stay fully synced.
- Full sync, horizon, and `online only` already re-snapshot the device. No new adoption mechanism is needed, and in-place trim remains forbidden by the current reset.
