# Panel review: LLP 3000.001.001

## 1. A materially simpler shape exists on the existing rails; the RFC builds a second replication protocol beside the first

**Issue.** Almost every load-bearing mechanism in §§5–6 already exists at coarser granularity. [`SnapshotCursor`](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/partition.rs:546) already carries a partial group (`after`, `taken`) under a pinned watermark. [`snapshot_page`](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/partition.rs:668) already emits per-group, server-named floor markers — and a floor at `taken = 50` is the same certificate as a floor at `taken = 500`, since the walk is descending and contiguous from the top. The device already keeps staged boundaries in a separate namespace from published ones in [`boundary.rs`](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-device/src/device/boundary.rs:5), and [`snapshot.rs`](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-device/src/device/snapshot.rs:67) already applies catch-up into staging. Repair A and Repair B in [LLP 3000.001](/Users/ccheever/projects/snapback/llp/3000.001-durable-replica-and-write-lifecycle.research.md:650) already paid the review cost (seventeen blind rounds) for exactly the correctness questions §§6.2–6.4 re-derive: server-named floors, current-image catch-up, deferral, replacement disposal.

**Why fundamental.** The RFC instead introduces private candidates with individual base cuts, a new exact-cut replay wire capability, candidate rebasing, and a certified group-discovery boundary — a parallel acquisition protocol whose interleavings with the existing snapshot/deferral/adoption machinery (§9, "separate those legacy staging domains") become the dominant correctness surface. That is the most expensive possible way to change *order* and *publication granularity*, which are the only two things the user-visible contract in §3 actually needs changed.

**Instead.** Priority-order the existing walk and publish at group/slice boundaries inside it: foreground group first, then round-robin `taken`-bounded slices; let the server emit its existing floor marker at partial `taken`; run the existing stream catch-up for that group's span from the pinned watermark to a drained head; publish that group's staged rows and boundary. §11 dismisses "publish each whole conversation" as insufficient because one conversation can be huge — but with sliced floors this is not whole-conversation publication, it is the RFC's own suffix idea on rails that already survived adversarial review.

## 2. The one common live cut couples every slice to whole-account traffic and contradicts the RFC's own acceptance test

**Issue.** §6.3 requires bringing a candidate *and all already-published domains* to the same finite cut P in one transaction, one publication at a time, rebasing any candidate another operation outruns. §6.3's own mitigation — "the scheduler must reserve publication turns so ordinary ongoing sync cannot repeatedly outrun and starve every candidate" — names the livelock without dissolving it. As more groups publish, each new slice's cost grows with the account's total write rate, not the slice size.

**Why fundamental.** §10.2 acceptance requires "bounded foreground work independent of unrelated backlog." The common cut makes foreground publication latency a function of unrelated *live* backlog by construction. It also defends a guarantee nothing else in the system makes: [LLP 3000.001](/Users/ccheever/projects/snapback/llp/3000.001-durable-replica-and-write-lifecycle.research.md:706) Repair B explicitly accepts that "rows a page touched running ahead of rows it did not — is inherent to applying a stream one page at a time, and it converges." History reads are pinned to one group; cross-group reads already carry partial/server semantics in the RFC's own §5.2 table. The common cut buys cross-conversation atomicity that no read in the target app claims.

**Instead.** Independent published cuts per group (the §11 alternative the RFC rejects). Per-read coverage frames and `fresh`/`since` already describe skew honestly. This also removes the need for candidate rebasing entirely.

## 3. Revision-qualified exact-cut replay reverses a deliberate disclosure decision, and is only needed because of issue 2

**Issue.** §6.2 requires "immutable, revision-qualified row images and tombstones for the replay interval," budgeted in one sentence as server storage and write costs. But the current stream's serve-current-image behavior — [`expand_joins`](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/partition.rs:1353) re-fetches and re-checks every put at serve time — is a stated LLP 3000 §7 decision: superseded or revoked content is *not redelivered*. Exact-cut replay ships precisely those intermediate versions: a message edited to remove text, a row revoked before P, crosses the wire into device staging because it existed between B and P. §7 of the RFC handles revocation of *published* rows; it never mentions that replay discloses version history today's protocol never sends. [LLP 3000.001](/Users/ccheever/projects/snapback/llp/3000.001-durable-replica-and-write-lifecycle.research.md:879) already parked this: a cross-row during-catch-up guarantee belongs to the staged-sync proposal "with its historical-image storage path reopened explicitly rather than adopted by implication."

**Why fundamental.** This is a disclosure-semantics reversal and a permanent server-storage obligation (every intermediate version of every dependency row must survive from any in-flight candidate's B to its P), purchased solely so publication can stop at an arbitrary finite P instead of a drained head — which is only necessary because the common cut makes draining expensive. The two costly choices prop each other up.

**Instead.** Publish at drained head, where current images are exact by definition. Repair B already proves a terminal page with `watermark == images_at` exists by construction and cannot defer. No historical images, no retention coupling, no version-history disclosure.

## 4. The publication unit is one table's suffix; the usable unit is a screen's dependency closure, which §9 scopes out

**Issue.** §9's first increment covers single-audience, horizon-indexed tables — `messages`. But §3's contract ("A works offline after restart," witness 1 in §10.1) requires finding conversation A in an inbox, rendering `threads[c]`, and evaluating the local read rule `exists participants[.conversation, viewer]`. In the RFC's own §4.1 schema, `participants` syncs `by .personId` (principal partition, no horizon) and `threads` syncs per-group with no horizon. Neither is in the supported unit; both remain on the legacy path that publishes only at full acquisition. §5.2 treats profiles/receipts/reactions as separable decorations, but the membership witness is not a decoration — without it the local interpreter cannot authorize the very history page being published.

**Why fundamental.** As scoped, the first increment can certify message suffixes that no real screen can reach or read offline. The §10.1 witnesses would pass only by querying `messages` in isolation, which is not the §1 scenario.

**Instead.** Make the scheduler two-tier and say so in §4: publish the small structural partitions (`participants`, `threads` — bounded by group count and `cap`, ~1,000 rows in the example account) whole and first, then per-group message suffixes. This is cheap, uses whole-partition publication that already exists, and is what makes a published suffix actually reachable.

## 5. The plan repairs offline reads for large accounts while leaving offline writes and the finish line anchored to the same barrier

**Issue.** §7 retains current prediction guards, and [`require_acquired`](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-device/src/device.rs:386) gates any program touching a synced table on *complete* acquisition. For the RFC's own example account — `last 500` × 1,000 conversations, which [the sync card](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-lang/src/guide/sync.rs:344) warns is 500,000 messages, against a measured 18.4 s and ~308 MB heap for 90,500 — full acquisition may effectively never finish on a phone. The scheduler's "eventual obligation to finish it" (§4.2) and the §10.2 budget (≤25% full-acquisition slowdown) keep that finish line as the definition of done. So on exactly the accounts that motivate the RFC, a user can read the open conversation offline but still cannot get a predicted send in it, and the device burns bandwidth and storage indefinitely chasing a 500-deep working set in conversations that will never be opened.

**Why fundamental.** Sending in the open thread is the core offline messaging action; its dependency closure (one membership witness, one insert) is far smaller than a history page's. An RFC whose thesis is "coverage is a property of the replica, proved per read" (§5) but which refuses to examine the same per-operation proof for the one write that matters has solved the easier half of its stated problem.

**Instead.** Either extend the §5.2 coverage table to writes — admit prediction when the mutation's proved read/insert-proof domains lie inside published coverage — or state plainly that large-account offline sending stays unrepaired and drop full acquisition as the acceptance anchor in favor of time-to-foreground-usable.

**Verdict: DIRECTION RIGHT WITH ONE CHANGE (build it as priority-ordered, per-group publication inside the existing snapshot/stream — per-group cuts at drained head with current images — not as a new exact-cut replay protocol under one common cut) — confidence 0.75**
