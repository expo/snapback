## Verdict: SOUND WITH MAJOR ISSUES

The direction holds: a store as a logical identity, a semantic port with no connection above it, extraction on SQLite first, the commit path named as the first scale risk, a fenced single owner before several processes, capture-before-copy graduation with a fenced cutover, and a predicted-ceilings-first scale program with fair controls. None of that should change. Five things must change before the children are accepted: the ownership fence as written has a safety hole and a liveness gap; the log-retention design would break sync authority reconstruction, which reads the whole membership history, and the corpus already has a retention proposal the children ignore; the SQLite commit-ceiling premise is a four-connection busy-handler artifact rather than the `serve` topology's bound; the committer space omits the cheapest correct option, which is also what "SQLite first" should mean; and the durable-state inventory omits the release tree and the on-disk half of activation, which the standby and P2 depend on.

## Fundamental and major findings

### F1. "Every commit is fenced" leaves every non-head write unfenced, and the standby cannot take over a paused owner as designed — MAJOR — 3000.009.001.000 §5, §10 (P1b witness); parent §3.1, §6.3

**Safety hole.** The fence is the `_head` update (`UPDATE _head SET seq = $next WHERE singleton AND owner_token = $token`). Only head-advancing commits touch `_head`. Writes that never advance the head commit without any token check, on today's adapter and under the contract as written:

- Refusal receipts: `mutate_once` rolls back the program savepoint, then `record_applied` inserts into `_ops` at `seq - 1` and commits (`snapback4-core/src/engine/postgres/mod.rs:324-349`). `record_applied` goes through `execute`, which calls `flush_tail`, which returns early because no commit is staged (`engine/postgres/store.rs:183-188`, `engine/postgres/tail.rs:24-26`).
- Receipt-only reports (`mod.rs:314-321`): `record_commit` is skipped, so no head update.
- Identity and work writes: session invalidation requires only `serialized_head`, the `FOR UPDATE` lock, not a token (`engine/postgres/authority.rs:86-94, 107-110`). The port's P1 adds mints, claims, lease renewals, steps, settlements and sweeps to this class.

Child B §4.1 itself enumerates "writes that never advance the commit head: session mints, claims, lease renewals, sweeps." A former owner that resumes after takeover can therefore keep minting sessions, claiming work, renewing leases and recording receipts until it notices its lease is gone. The §5 sentence "a former owner … commits nothing after a successor takes over" is false for exactly the writes child B says exist.

**Liveness gap.** "The standby waits on the advisory lock." A SIGSTOPped owner keeps its TCP sessions, so its session-level advisory lock stays held and Postgres sees nothing wrong until a keepalive fires. Worse, every serialized write transaction takes `SELECT seq FROM _head FOR UPDATE` as its first statement (`engine/postgres/store.rs:113-117`), so a paused owner with one transaction open holds the `_head` row lock, and the standby's own token-increment update on `_head` blocks behind it. The P1b witness "SIGSTOP of the owner while the standby takes over" cannot pass with the mechanism as written.

**Direction.** State the invariant as "every durable write is fenced": every writing `StoreTx` reads the owner token under the `_owner` row at begin and the adapter refuses to commit if it differs, or every write transaction touches an `_owner` row `WHERE token = $t`. Make takeover lease-driven, not lock-driven: on expiry the standby terminates the predecessor's backends (`pg_terminate_backend` is permitted for same-role sessions without superuser), then increments the token under the `_head` and `_owner` locks. The advisory lock remains a fast path, not the liveness signal. Lease expiry is then trusted for takeover and never for fencing, which is what §5 means to say.

### F2. Log retention by seq-range deletion breaks sync authority reconstruction, and graduation's "retained window only" inherits the break — MAJOR — 3000.009.001.000 §7.3, §4.1; 3000.009.001.001 §4.2, §6; parent §2 (10⁸–10⁹ rows), §7

The sync catch-up path does not read only the window above a device's watermark. `stream` calls `intervals` (`snapback4-core/src/partition.rs:1090-1099`), which calls `memberships_before(partition, watermark)` over every `join`/`scope` event at or below the watermark (`partition.rs:1004`; SQL at `store.rs:806-807` and `engine/postgres/log.rs:62-64`), then `membership_transitions(partition, 0)` from sequence zero for the expired-grant walk (`partition.rs:1208`), then `commit_times` for arbitrarily old joins (`partition.rs:1191, 1219`). The code's own annotation at `partition.rs:1003` reads: "@ref LLP 3000#7 — a content page cannot establish authority from a truncated ledger." A device resuming *above* the floor still depends on events *below* it. Deleting or detaching `_log` and `_commits` partitions below a floor therefore does not merely re-acquire devices below the floor; it changes answers for devices above it, failing closed for expiring audiences (`fallback_expiry`, `partition.rs:1017-1022`) and mis-timing silent expiry.

Two more facts bear on this. On SQLite the head *is* `MAX(seq) FROM _commits` (`store.rs:468, 711-712`), so `_commits` retention needs a persisted head there too. And the corpus already has a retention design: LLP 3000.002 "Proposal: coordinated history, receipt and principal retention" (lines 1065-1134) requires "Complete checkpoint plus committed resume floor" for partition events and commit times, and for membership transitions "Fold into an equivalent checkpoint before advancing the same floor; never prune independently of content history," with a crash-safe publication order. Neither child cites it, and `NOT-DOING.md` line 31 still says "the log never evicts," so retention also needs a Moves line that parent §7 does not list.

**Direction.** Retention is checkpoint-plus-floor, not deletion-below-floor: fold membership transitions and their commit times into a materialized state at floor `F`, publish `F` and the checkpoint atomically, then drop content events below `F`. Range partitioning of `_log` by `seq` is fine for the *content* kinds; `join`/`scope` events either live in a separate never-pruned table or are folded first. Child B copies checkpoint plus suffix, not "the retained window," and its digest covers the checkpoint. Child C's H7 and W9 should include a cell with the floor active, because the checkpoint read is a new O(memberships) cost on resume.

### F3. The SQLite "165 commits/s production ceiling" is a four-connection busy-handler measurement, not the `serve` topology's bound; the SQLite-first sequencing and the "same ceiling binds there" claim rest on it — MAJOR — parent §1, §3.3, §7 (question 2); 3000.009.001.002 §2, §4 (SQLite cell)

The cell behind that number opens four separate `Store`s on four threads, each its own SQLite connection (`experiments/postgres/src/main.rs:96-119`), with a five-second busy timeout (`store.rs:126, 195`). SQLite's busy handler sleeps in steps from 1 ms up to 100 ms between retries of `BEGIN IMMEDIATE`, so with four contending writers the cell measures sleep granularity, not flush time. The experiment record already says as much: "Two full 1,000-iteration attempts on that idle host stopped at SQLite's existing five-second busy timeout" (experiment README, fix-round section). In production there is no contention of this kind: `serve` holds one `FairMutex<Engine>` and every write goes through `producing_engine` on one connection (`crates/snapback4/src/serve.rs:92, 461`), so the busy handler never runs and the ceiling is roughly `1/(exec + fsync)`, likely several times the stated figure. UNVERIFIED how high, which is the point: nobody has measured the topology `serve` actually uses.

**Direction.** Child C adds a single-connection SQLite cell as the SQLite baseline (one engine, N request threads queued on the mutex, as `serve` runs) and retires the four-connection cell from any ceiling claim. Parent §3.3 and §7 question 2 restate: SQLite's flush bound is real but unmeasured; the SQLite-first argument should rest on qualification cost and on F4's serial-batch committer, not on 165/s.

### F4. The committer space omits the cheapest correct design, which is what "land on SQLite first" should mean; candidate (a) is C2 plus OCC and its correctness surface is larger than "read sets the interpreter already knows" — MAJOR — parent §3.3, §5 (steps 1–2); 3000.009.001.000 §6; 3000.009.001.002 §8 (first rule), §9 (S0)

**A missing candidate.** Run `N` queued mutations back-to-back inside *one* store transaction under the reference protocol: each program under its own savepoint, as the adapters already do (`engine/postgres/mod.rs:294, 312, 325`; `engine/mod.rs:997, 1019, 1034`), one head update to the batch's last sequence, one flush. It is correct by construction: same serial order as the reference, no read sets, no overlay, native read-your-writes, atomic visibility per batch, contiguous watermarks, and a database error retries the batch's members individually. On SQLite, where `k·RTT ≈ 0` and the flush dominates, it recovers nearly `batch×`. On Postgres it recovers only the flush's share because the sequential round trips remain, which is why (a) is still the Postgres path. So the serial batch is the right first `Committer` behind the seam, the natural hot-key fallback for (a), and the meaningful content of "SQLite first." As written, "the same committer group-commits SQLite" makes SQLite wait for C2's overlay for no gain.

**Candidate (a)'s true size.** It needs C2's read-your-writes overlay over point reads, index scans, counts, deletions and constraints with charge order preserved, which the parent RFC deferred until evidence; plus read-set recording; plus validation; plus batching. The read set must cover every read the program made, not only "points, index ranges with bounds, counts and absences": `sequence_value`, `cap_count`, `count_prefix`, `index_head`, `effect_once`, `_ops` lookups and authority facts (session validity, principal generation), or a mutation validated at snapshot S commits after a revocation at S+1. The reliable way to get completeness is to record at the `Rows`/`PartitionRows`/authority adapter boundary, through which every read already passes, not "in the `Runner`." Execution concurrency is also a separate bound the §6.3 formula omits: `batch/(2·RTT + F)` is the commit stage; the execution stage is `connections/(k·RTT + exec)`, so (a) is connection-bound before it is flush-bound.

**A sequencing point.** Child C's first decision rule fires with certainty: the measured 450/s at a Unix socket with `k ≈ 15` gives roughly 100/s at 0.5 ms RTT, far below 1,000. S0 calibrates, it does not decide. Gating all committer work on S0 delays the one piece of core work every Postgres production claim needs. Start the seam, the serial batch and (a)'s design at A-P0; let S0 run beside them and size the batch.

**One invariant missing from §6.4.** The authority clock must be monotone in *commit* order (`pin_writer_time`, `engine/mod.rs:944-948`; `_meta.time_audience_clock`). Under (a), a mutation executed with `now = t` must commit only if `t ≥` the last committed pin, else rerun; add it to the fixed list.

### F5. The inventory omits the release tree and the on-disk half of activation; P1's standby and P2's rolling deploy cannot work until they are in it — MAJOR — 3000.009.001.000 §2, §4.1, §4.2, §5 (activation fencing), §10 (P1b); parent §3.1, §3.4

The store holds only the release *history* and the selected release number (`_meta.release`, `store.rs:358-368`). Everything a host needs to *run* a release is on disk beside the SQLite file: the immutable release tree (source, generated runtime, `native.wasm`, provenance) digested by `release_files::digest` (`crates/snapback4/src/release_files.rs:39-72`), the `current` pointer file renamed only after the database commit (`release_files.rs:126-170`, "flush it before DB selection" at lines 1-2), the `releases.jsonl` ledger, the store symlinked into the release directory (`release_files.rs:95-124`), and the activation control transport, a Unix socket whose identity is the store's path, device and inode (`release_control.rs:1-2, 50-59`). `serve` opens a release through that layout (`serve_start.rs:86-92, 112-116`). The parent's logical-store list (§3.1) names "generation and release history," child A §4.1 names six tables, and §4.2 names no release item at all.

Consequences: a warm standby on another host cannot serve after promotion unless it already holds the exact release tree the store names; `deploy` from a second host has nowhere to put the tree the store will point at; and the two-phase disk-then-database activation protocol (LLP 3000.000.000 §5) assumes one host owns both halves.

**Direction.** Add a family: release artifacts, content-addressed by the digest `release_files` already computes, stored in `BlobStore` (or an equivalent the operator configures), with the store's activation record naming the digest. A serving host materializes the tree from the store's record and refuses to serve a release it cannot fetch. The activation protocol becomes: upload tree by digest, then one fenced store transaction selects it; the `current` file becomes a local cache hint, as `serve.lock` already is. Also inventory `_change_evidence` (`store.rs:227-228, 728`), a server-only durable table the 31-table count misses.

## What the documents get right that should not change

- A store is a logical identity; graduation moves it, restore creates a new incarnation, and exactly one physical store serves it at a time.
- The port is a semantic contract for all durable state with policy in Rust and only adapters touching a connection, extracted on SQLite first with no behavior change (the LLP 0046 lesson).
- The commit path is the first scale risk, the bound formula is right, the head lock is held across every call and the flush (`engine/postgres/store.rs:113-117`), and `nextval` and WAL decoding are correctly rejected as commit order.
- The committer invariants: one total order, no gap below a published watermark, exact snapshots, retry repeats the whole operation. Both (a) and (b) preserve snapshot exactness as analyzed; (b)'s absence problem is real.
- Graduation's shape: arm capture before the copy, chunked copy in short read transactions, idempotent full-image replay, a fenced cutover bounded by the capture tail, digest and shadow comparison through the store oracles, a revert window, and the reverse direction as a product. Triggers over engine instrumentation is the right call.
- P1 before P2, with every in-process coordination point named with its P2 mechanism, and no claim that Postgres is faster.
- Child C's method: ceilings predicted before measurement, controls built to the same semantics with advocate review, open-loop load with coordinated-omission correction, fixed durability, and a ledger that classifies each gap as semantic cost, design choice or implementation.

## Small notes

1. Capture is physical. Triggers journal SQLite's own tables (`r` keyed by catalog number `t INTEGER`, `i` by `ti INTEGER`, `store.rs:290-291`), while child A §4.1 lets the Postgres adapter use different tables and says graduation maps "through the family's logical export format, not through table copies." The replayer therefore needs a per-SQLite-table-to-family mapping, which is table translation for the capture path. State that, and run capture with `PRAGMA recursive_triggers=ON`: `INSERT OR REPLACE` resolving a non-key `UNIQUE` (`_credentials.email`, `store.rs:299`) otherwise deletes a different row without firing a `DELETE` trigger.
2. Cutover step 5 spans two stores. "Take the `_owner` token and set `_graduation.state='live'`" is one Postgres transaction; "mark the source graduated" is a separate SQLite transaction. Define the recovery rule for a crash between them (the target's live record wins; a source that finds a live target record refuses writes).
3. Parent §5 step 1 says child C "builds its harness and the three controls" in S0; child C §9 S0 builds only the raw Postgres control and defers Supabase and Convex to S1. Align them, and see F4 on what S0 can decide.
4. `tc netem` on the app host's interface delays all egress, including app-to-load-generator traffic, which inflates every system's measured latency by the same amount but shifts absolute SLO ceilings. Filter the delay to the database host's address.
5. Child A §4.2 lists the time-audience clock as P1 work "persisted"; it already is on SQLite (`_meta.time_audience_clock`). The P1 item is the Postgres copy and, under any reordering committer, F4's commit-order monotonicity.
