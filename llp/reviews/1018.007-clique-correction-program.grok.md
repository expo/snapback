# Sanity review of LLP 1018.007 Draft repair plans

**Provenance:** Grok 4.6, one reviewer, 2026-09-09. Method: read-only check of the six `llp/1018.007*.plan.md` drafts plus cited Snapback 2 code and governing LLPs/brief at that baseline. Not an implementation or benchmark certification. Not an acceptance.

## Overall assessment

The program correctly treats eight grader findings as eight behaviors, keeps frozen Clique lanes read-only, and does not invent a second store, scheduler, push service, or language. Causal claims for send/live and cold sync are still mostly open, which matches the evidence. Signup is a confirmed owner omission. Pagination, TwinStore coalescing, watermark cloning, and digest/preview semantics are real, but three of those plans still point an implementer at the wrong minimal patch or at a flight-sharing shape that can deadlock or apply the wrong fence.

Signup can be implemented as written. The other lanes need the MATERIAL items below resolved first. No proposal-acceptance ritual is implied.

## Concerns

### MATERIAL

**1. LLP 1018.007.003 Repair / Evidence — cursor loss is not only an injected twin partial**

`offlineView` does prefer a non-retained local answer over a held `capped` page (`offline.ts` `useLocal` is true whenever `held.retained` is unset). `summarize` then zeros `next` on a non-retained partial (`snapshot.ts` `receiptOf`). `ClientPages.hasMore` is `pages.at(-1)?.next != null`. That chain can turn 20 rows + `hasMore: true` into 20 rows + `hasMore: false`. The injected-partial seam is a valid laboratory.

It is not the only production path, and it is not what live `usePage` does after a store commit. Observed refresh goes through `answerOffline` → `offlineView` (`client.ts` `local`, `client-observed.ts` refresh). For a non-retained feed, **any** local answer replaces the owner page, including:

- local `complete`/`capped` with `next: null` when `lastReturnedSuffix` is missing (`twin.ts` next encoding)
- local `capped` with an `h1` cursor, which must not be forwarded to the server (LLP 1018.006 §7; this plan already says that)

Existing `usePage` coverage (`plain-tier.test.ts`) uses a persona client with no offline store, so it never hits this branch.

A patch that only does `if (local.state === "partial" && held.state === "capped") keep held` can pass the injected case and still drop continuation after the first owner page is stored and `subscribeInputs` refreshes.

**Resolution:** Before choosing reconstruction vs retention, record the actual local `state`, `next`, `sites`, and issuing-query coverage **after one real carrier input refresh** on Global / Following / author, with and without offline storage. Keep a still-valid owner `capped` continuation across that refresh. Do not mint `next` on a fresh non-retained partial (LLP 1018.006 §7). Add that refresh case to Acceptance beside the 20+20+5 walk.

**2. LLP 1018.007.002 Repair strategy — shared `TwinStore.sync()` flight can deadlock and can apply across a fence**

`TwinStore.sync()` has no in-flight coalescing. `Twin.evaluate` → `hydrate()` → `sync()` on every local refresh, and `SharedSubscriptions.refresh()` walks every mounted entry. Concurrent cold callers can each take a snapshot and rebuild `ClientStore`. That diagnosis is right.

The method already re-enters itself on a replaced root dictionary (`twin-store.ts`: `this.revision = undefined; return this.sync()`). A wrapper of the form “if `this.flight`, return `this.flight`” deadlocks on that path. “If `this.flight`, return `this.flight.then(() => this.sync())`” is the recheck shape, and it still deadlocks if the inner call waits on the outer promise.

The same `TwinStore` lives across `OfflineRuntime.open()` partition changes (`offline.ts` assigns `this.partition` on one runtime / one `Twin`). An in-flight snapshot for principal A must not be applied after the fence is `[B, …]`. Rechecking revision after a successful apply is not enough if the apply already mutated `this.store`.

Yielding inside the rebuild to avoid a long turn, without keeping the published store unpublished until the flight finishes, tears the twin: `sync()` currently `put`s into `this.store` incrementally.

**Resolution:** Split inner work from the public waiter. Inner generation-reset re-entry must not wait on the outer flight. Capture `{principal, generation, schemaHash, authEpoch}` at start; discard the result and retry if it differs at apply time. Publish a rebuilt `ClientStore` in one assignment after the flight succeeds. Tests already listed (concurrent cold snapshot, concurrent warm delta, later revision while blocked) plus: generation-reset re-entry, principal change during a blocked snapshot, and no observer/`evaluate` seeing a half-built store.

**3. LLP 1018.007.004 Following-post activity — calling `bumpNewPostForFollower` on create fights the celebrity write rule**

The unused helper is a real Grok M8 miss. The first repair sentence is “Invoke period accounting from every successful top-level post-creation path.” The brief’s celebrity rule is post-create p95 ≤ 3× a 5-follower author, with a 900-follower celebrity (`benchmarks/briefs/social-messenger.md` scale envelope). A per-follower bump at create is fan-out-on-write.

The later paragraph (indexed period query / existing bounded maintain, do not raise a for-loop cap) is the repair that can pass that rule. As written, an implementer can “fix” the helper by calling it and fail M8 write-path.

Digest already needs `newPostsInFollowing` for `[periodStart, periodEnd)` (`1018.007.004` Period digests; brief M8 payload). That is the consumer.

**Resolution:** Do not invoke a per-follower write-time bump. Count newly visible following posts at digest emission with an indexed period query (and the stated follow/visibility checks). If a maintained row is used, it must not scale the create path with follower count. Keep the “explicit-ID and ordinary-ID agree; replies/retries/reposts/rejects do not increment” tests on that digest-time count.

**4. LLP 1018.007.000 Repair / Acceptance — do not close live delivery on the sender watermark clone**

`logTail` does call `runtime.coverage()` and clone rows/ranges/absences/verdicts/watermarks to pick `tailWatermark` (`client-outbox.ts`, `range-store.ts` `coverage()`). That is whole-store work on the **sender settlement** path after owner commit (Pending → rows in the swap). It does not run on the recipient device.

Astra’s other-client visibility samples and Grok’s >60s live waits are recipient-side unless measurement ties them to this clone. Recipient delay is more likely the same twin rebuild / 50-query refresh the cold-sync lane already owns. Acceptance currently pairs “no whole-history clone” with “real browser recipient observes each unique send.” A sender-only watermark fix can clear Pending and leave live delivery red.

**Resolution:** Keep the instrumented intervals (click → admission → replay → owner commit → recipient frame → recipient store commit → render → sender terminal). Treat watermark lookup as the settlement clone; treat recipient materialization as the shared store-change lane. Do not pass live-delivery on “Pending got faster” or on a timeout that still does not show the message. `coverage()` in `loadFacts` / `resumeRequest` / `resumeSeed` is the same clone; change those only if they sit on the measured path.

### MINOR

**5. LLP 1018.007.000 Repair — dependency filtering is a Draft RFC, not this patch**

Coalesce-per-entry already exists (`client-sessions.ts` `scheduleRefresh`). LLP 1018.002 is Draft and authorizes no runtime change. “Dependency filtering is allowed only with evidence…” is a trapdoor into a new invalidation design.

**Resolution:** Coalesce duplicate hydrates/evaluations; do not filter by operation name; do not implement 1018.002 here.

**6. LLP 1018.007.002 Repair — `isolate()` of a cold snapshot is still a whole-history copy**

Sharing the flight removes *duplicate* snapshot installs, not the copy itself. `preparedChanges` already prepares images; `sync()` then `isolate()`s the change. Skipping `isolate` without another isolation story would share mutable evaluator state, which the plan correctly forbids.

**Resolution:** After profiling, drop redundant copies, not isolation. One installed snapshot/delta per revision remains the acceptance.

**7. LLP 1018.007.001 Repair — pending grant is not stamped with the session viewer**

Owner cause is confirmed: `Action::Signup` passes `None` into `session_json`; Login/Guest call `grant_if_low` (`writer.rs`). LLP 1012 §7 lists resume/login/guest only. `client.ts` `session()` already `captureGrant`s any session response. `grant_if_low(principal, None)` on success is the right owner patch. Fresh accounts have no `remaining` field on Signup; do not add one.

`noteGrant` / `decodeGrant` still say “login, guest, or resume.” `pendingGrant` is not cleared on partition wipe; `adopt()` does not check principal. Login already has this shape; signup makes a brand-new principal more likely to land a grant in the previous partition if install fails between capture and `openOffline`.

**Resolution:** Bind `pendingGrant` to `session.viewer` at capture; refuse adopt on mismatch (the plan’s cross-principal case). Update the signup-has-no-grant comment in `local-data-recovery.test.ts` and grant-mint counts that assumed the first grant came from drain. Failed signup must still omit `grant` (`session_json` only inserts when `Some`).

**8. LLP 1018.007.004 Push preview — no Quarry text slice exists at this baseline**

Builtins are `range` / `tokens` / `count` / `min` / `max` / `divmod` / `share` (`bound-builtins.ts`). The parent program forbids a new language profile. “Use the supported Quarry text operation when possible” is a dead branch. The brief is first 80 chars, or `"Photo"` / `"Video"` (`social-messenger.md` M6). Engine text counting is Unicode scalars (`scalarLength` in `evaluator/src/unicode.ts`), not UTF-16 `length` and not grapheme clusters.

**Resolution:** Truncate once on the effect-plus-then seam (or equivalent) **before** `pushLog.preview` and the provider payload diverge. Count with the engine scalar rule; document that. Do not add a Quarry builtin. Do not clip only the effect log. Keep view-once off the hidden body.

**9. LLP 1018.007.004 Period digests — payload field names vs eligibility**

Using lifetime `unreadMessageTotals` / `unreadChatCounts` as sweep eligibility is the Grok M8 miss; uniqueness only dedupes inside one period. The brief requires no digest for a following period with no new activity, and payload `{newFollowers, newPostsInFollowing, unreadMessages, unreadChats}` from activity since the previous period.

**Resolution:** Drive **eligibility** from period activity only (including newly visible following posts from the digest-time count in concern 3). If a digest does emit, define `unreadMessages` / `unreadChats` as period-authorized unread, not standing lifetime totals. Keep skip-all-zero, replay-mode off, user/period idempotency, and atomic record-plus-effect.

**10. LLP 1018.007 Execution step 1 vs commission**

The root program still talks about sealing drafts for a Grok loop and resolving material issues before implementation. The later instruction is: sanity-check these drafts, then straightforward fixes may land without a full LLP process; signup is fast-tracked.

**Resolution:** Treat this review as a sanity check, not an accept/reject ritual. Signup does not need a further document cycle. Do not skip the MATERIAL repairs on pagination, TwinStore, digest fanout, or live-delivery attribution.

## Suggestions

- Watermark: add a facts/watermarks-only read (in-memory `state.watermarks` / `state.facts`) instead of teaching `coverage()` to be cheap. `tailWatermark` already sorts a watermark list; it does not need rows.
- Twin publish: build the new `ClientStore` privately, then swap the pointer. That is simpler than yielding inside the live store.
- Pagination: one owner+IndexedDB `usePage` test that commits ≥45 Global rows, asserts `hasMore` after the first owner page **and** after the next `subscribeInputs` refresh, then loads 20+20+5 with exact ids. That is the whole defect if the owner continuation is kept.
- Following posts: delete or leave unused `bumpNewPostForFollower` rather than wiring it; the digest query is the product behavior.
- Send measurement: count logical subscriptions and queued receipt ops, but do not change Astra’s per-bubble receipt model unless that interval dominates. Receipts staying is an authority fence, not a performance knob.
- Byte cap: keep 85,000 gzip / 80,000 target. Flight handle + watermarks-only getter should fit; a second cache will not.

## Verdict

**REVISE**

Signup (`1018.007.001`) is correct as a grant-issuer alignment and can land in the fast path once the pending-grant principal stamp and the tests that assume “signup has no grant” are updated. Do not implement pagination, TwinStore coalescing, or following-post accounting from the current repair sentences until the MATERIAL items are fixed in the plans or in the first patch that those sentences would otherwise produce. Live-delivery must stay attributed to the interval that actually moves, not to the sender’s `coverage()` clone.
