# External technical review — LLP 0309.000, round 1

Target reviewed: `llp/0309.000-operator-delta-semantics.spec.md`, commit `fec7c118e`; SHA-256 verified as `c8a6e00998f74556f7f2a04d898793e0d205ee8fbc598e4d86cf98657e126023`.

The Spec is not ready. Its syntactic inventory is complete, and several central rulings are correct, but the normative semantics contain correctness, feasibility, and custody defects.

## MATERIAL concerns

### 1. The normative wire mapping can disclose unprojected retained-row fields

Section 1.5 requires root updates to carry `retained_row_patch`, explicitly including all changed and system fields (`llp/0309.000-operator-delta-semantics.spec.md:128-133`). The implementation unions every old/new physical-row field and returns every changed value (`crates/snapback-engine/src/graph_evaluator.rs:3328-3360`), places that object directly in the wire op (`crates/snapback-engine/src/graph_evaluator.rs:3589-3607`), and serializes it (`crates/snapback-engine/src/local/engine.rs:34284-34315`).

The apply oracle only consults fields named by the closed projection and silently ignores other patch fields (`crates/snapback-engine/src/graph_evaluator.rs:3363-3405`). Consequently, for a projection containing only `title`, an update changing only retained field `secret` can emit `{"secret": ...}` while both applied and freshly projected results remain unchanged; the comparator can pass because it compares projected results, not wire-field custody (`crates/snapback-engine/src/local/engine.rs:34206-34217`).

This contradicts the Spec’s claim that retained rows and physical keys are server-internal and that nothing in the Spec becomes eligible to cross the client boundary (`llp/0309.000-operator-delta-semantics.spec.md:491-504`). It also conflicts with the parent’s exact-plan/projection custody restriction (`llp/0309-derived-delta-semantics.rfc.md:246-260`).

The existing carrier and op vocabulary can remain, but the normative lowering must be projection-safe, and Stage B must classify the shipped full-diff behavior as a potential class-(b) defect rather than canonizing it.

### 2. E1/E2 are not functions of their declared carrier and cannot be “state-free” as written

`ΔApp` gives updates only a post-image and may give deletes only a key (`llp/0309.000-operator-delta-semantics.spec.md:61-84`). Nevertheless, E1 declares owner visibility state-free (`:160-169`), while E2 declares itself state-free and then explicitly reads prior result membership (`:184-203`).

Concrete counterexample for owner visibility, with principal Alice and identical input `update(r, post.owner="Bob")`:

- If the prior owner was Alice, the correct output is a removal.
- If the prior owner was Carol, the correct output is no-op.

The shipped classifier resolves exactly this ambiguity through `prior_ids` and `was_member` (`crates/snapback-kernel/src/live_matcher.rs:3541-3545`, `3600-3659`). Graph `roots`/`by_node` retain only the post-visibility, post-window population, not an independently specified pre-E1/E2 relation (`crates/snapback-engine/src/graph_evaluator.rs:1139-1213`).

E1/E2 can be state-free if typed over an already paired `ΔZ`, but the Spec does not define or ledger the required `ΔApp → ΔZ` image-completion adapter. This fails the parent’s requirement for an explicit type and state contract per form (`llp/0309-derived-delta-semantics.rfc.md:109-153`).

### 3. E3’s rules do not maintain completeness state, and admitted `take:0` is undefined

E3 declares completeness, boundary state, and next state normative, but assigns every outside/outside change a no-op (`llp/0309.000-operator-delta-semantics.spec.md:205-234`).

Consider ascending `take=2`:

- World A: `A1, B2, C3`.
- World B: `A1, B2, C3, D4`.

Both evaluations retain only `A,B`, record `has_more=true`, and discard the lookahead row body: the evaluator reads with lookahead, truncates before captures and retained state, and captures only the retained rows (`crates/snapback-engine/src/graph_evaluator.rs:1147-1157`, `1178-1213`). Deleting `C` is outside the retained window in both worlds. Fresh evaluation becomes `Complete` in A but remains `Prefix` in B (`crates/snapback-engine/src/graph_evaluator.rs:1230-1250`). E3’s no-op cannot produce the correct next state or completeness proof. A bounded tail probe or fallback condition is required for such proof-changing outside events.

Separately, zero is a valid demand `take`: validation rejects only values over the maximum (`crates/snapback-types/src/manifest/graph.rs:5302-5308`). The shipped evaluator has explicit zero-take behavior producing empty output with `Unknown/zero-take-unproved` for roots and children (`crates/snapback-engine/src/graph_evaluator.rs:1117-1137`, `1467-1474`). E3 instead treats `result_count == take` as a full window with a displaceable boundary, which is nonsensical at zero, and assigns neither a maintain rule nor named fallback.

### 4. E5’s parent-entry rule omits the read and demand-identity conditions needed to create a window

E5 says a parent entering creates a complete per-parent window, but requires an authorized range read only for a join-value re-key (`llp/0309.000-operator-delta-semantics.spec.md:290-305`).

Concrete counterexample: parent `p` enters the upstream result while children `c1,c2` already exist and no child-table rows changed in this commit. Retained E5 state contains no range or child rows for `p`. Full evaluation performs a bounded authorized range query for every parent (`crates/snapback-engine/src/graph_evaluator.rs:1454-1536`). Without that read, the form would create an empty array instead of `[c1,c2]`.

Demand pages have an additional issue: shipped validation requires the demand interval’s parent set to equal the evaluated physical parent set exactly (`crates/snapback-types/src/manifest/graph.rs:5273-5300`). An old demand vector cannot simply acquire an interval for a newly entering parent. Therefore “demand pages … are otherwise identical” is false; the form must define the demand-identity transition or fall back/refuse. E4 parent entry similarly needs its bounded point-read condition stated explicitly, not only the “join value changes” case (`llp/0309.000-operator-delta-semantics.spec.md:268-272`).

### 5. E6 omits the predicate-filtering semantics of `ExistsSemiJoin`

The Spec gives E6 only a `ΔBit` output and maps that only to a projected Boolean update (`llp/0309.000-operator-delta-semantics.spec.md:112-138`, `307-350`).

The shipped evaluator has two modes determined by whether the terminal projection references the exists node (`crates/snapback-engine/src/graph_evaluator.rs:1888-1898`, `2047-2049`). When it is not projected, the semi-join filters its parent relation, replacing root or child membership (`crates/snapback-engine/src/graph_evaluator.rs:2050-2081`). Admission permits this because the inert-node check does not require an `ExistsSemiJoin` to be projected (`crates/snapback-types/src/manifest/graph.rs:4315-4323`).

Thus an unprojected `0→1` transition may need to reinsert a parent row at the correct sequence position, while `1→0` removes it. There is no Boolean projection to update, no bit-to-`ΔZ`/`ΔSeq` selection form, and rejected parents have already been removed from retained roots/children. The closure rows mapping all semi-joins only to E6 therefore omit a shipped semantic component (`llp/0309.000-operator-delta-semantics.spec.md:437-439`).

Membership visibility has the same missing lift: a membership grant can reveal an application row that was never retained by the visibility-filtered query (`crates/snapback-engine/src/graph_evaluator.rs:1139-1213`). `EvaluationState.exists` does not store membership-visibility scopes; it is populated only by graph semi-join evaluation (`crates/snapback-engine/src/graph_evaluator.rs:455-464`, `2031-2038`).

The blanket statement that every relation read receives its declared E1 visibility also needs an authoritative-membership exception. Membership probes deliberately bypass the membership table’s own visibility (`crates/snapback-types/src/manifest/types.rs:10265-10269`; `crates/snapback-kernel/src/membership_rules.rs:138-179`, `228-241`).

### 6. OQ-2 is only partly resolved: the unconditional 0→1 ruling is unsound

The central OQ-2 diagnosis is correct: `matched_count` is not support multiplicity, and a possible 1→0 transition needs a bounded re-probe or fallback. Direct and target probes stop at one supporting row (`crates/snapback-engine/src/graph_evaluator.rs:1749-1770`, `1863-1884`), while `matched_count` records successful probes rather than support rows (`:1975-2022`).

However, the Spec’s claim that every 0→1 is decidable from the change alone (`llp/0309.000-operator-delta-semantics.spec.md:319-321`, `406-420`) is false in at least two shipped cases:

- For `mode:"all"`, the evaluator stops at the first failed canonical argument, captures only aggregate `matched_count`, and retains one aggregate Boolean per parent/node—not the per-element bits claimed by §6.3 (`crates/snapback-engine/src/graph_evaluator.rs:1942-1952`, `1970-2023`, `2031-2038`). With arguments `[a,b]`, prior failure at `a` leaves support for `b` unobserved. Inserting support for `a` flips the aggregate only if `b` was already supported; identical retained state and delta can therefore require different results.
- For a through edge, inserting a through row proves only the link. Whether the target exists and passes target visibility still requires the target point query. Shipped evaluation performs the edge range followed by target reads (`crates/snapback-engine/src/graph_evaluator.rs:1774-1885`). Worlds differing only in visible target existence have identical prior empty-range state and identical through-row insertion, but different new bits.

The §6.3 “all-mode element scopes: have” entry is therefore wrong (`llp/0309.000-operator-delta-semantics.spec.md:545-549`). It must be missing/partial unless the evaluator gains real per-element state. The bounded 1→0 re-probe decision remains sound.

### 7. The unchanged wire mapping is not total for valid nested and transition forms

The IR admits `BoundedToMany` beneath another `BoundedToMany` (`crates/snapback-types/src/manifest/graph.rs:4369-4377`), and projection validation admits the corresponding nested arrays (`crates/snapback-types/src/manifest/graph.rs:3258-3271`).

The Spec nevertheless maps to-many splices using only `node_id` and parent `root_key` (`llp/0309.000-operator-delta-semantics.spec.md:136-137`). On the actual wire, `root_key` is explicitly the top-level physical root; the op has no immediate-parent key or projection path, and `position` is defined as the root-window position (`crates/snapback-types/src/live_wire.rs:348-365`). With two instances of the same child node beneath one root, an array splice cannot identify which nested array to mutate, particularly when child IDs are not projected.

The current oracle’s categorical rejection of arrays confirms that the existing fields provide no implemented application rule (`crates/snapback-engine/src/graph_evaluator.rs:3411-3417`, `3446-3451`). Merely “extending the oracle” cannot recover an immediate-parent/path identity absent from the frame.

Other mappings are also incomplete:

- A `ΔBit` update has no defined physical changed-node `key` or `position`, although both fields are mandatory.
- Root removal does not define whether mandatory `position` is pre- or post-splice.
- Optional null↔object transitions are called `update`, but no payload/application rule constructs or nulls the object. The current oracle only descends through an already non-null object, and the current delta evaluator replaces on child presence/identity changes (`crates/snapback-engine/src/graph_evaluator.rs:3386-3391`, `3770-3777`).

The fixed carrier posture can be preserved, but unsupported shapes need an explicit fallback or an exact encoding using the existing fields.

### 8. Authorized-read maintain verdicts are absent from the reference evaluator’s type

E3, E4, E5, E6, and E7 permit maintain verdicts after bounded authorized reads (`llp/0309.000-operator-delta-semantics.spec.md:225-230`, `268-272`, `301-303`, `322-332`, `366-370`). Section 6 likewise treats authorized reads as state sources (`:506-522`, `537-549`).

Yet §7.1 specifies a pure function receiving only `(state, Δin)` (`llp/0309.000-operator-delta-semantics.spec.md:590-600`), and vectors contain only initial state and change batch (`:618-621`). Neither type contains a read oracle, same-cut read transcript, authorization context, returned rows, or charged read effect.

The shipped graph lane performs those reads through `DbRead` with request authority/evaluation-cut state (`crates/snapback-engine/src/graph_evaluator.rs:3619-3626`), inside a pinned view whose cut and authorization version are checked before evaluation (`crates/snapback-engine/src/local/engine.rs:34159-34176`). Without an equivalent modeled input/effect, two worlds with identical `state` and `Δin` but different authorized probe results are indistinguishable to the promised pure evaluator.

This is a feasibility defect in the executable semantics, not a request for implementation detail.

### 9. Stage B does not bind the outer lanes it promises to audit, and one recorded kill-switch claim is false

Section 8 names only the inner `compute_live_delta` and `evaluate_graph_delta_on` functions while promising to audit publication, proof, ledger, capture-freshness, and authorization effects (`llp/0309.000-operator-delta-semantics.spec.md:642-660`). Those effects live in the outer `try_live_delta_fanout` and `try_graph_delta_fanout` paths:

- Graph pinned reads, convergence, wire construction, publication, and stale-capture latch are in `crates/snapback-engine/src/local/engine.rs:34120-34365`.
- DK-3 authorization handling and captured-state maintenance are in `crates/snapback-engine/src/local/engine.rs:34392-34661`.

The Stage B plan needs an explicit harness or entrypoint for all four functions; comparing only the two inner cores cannot exercise the promised outer axes.

Section 5 also says both graph kill switches wrap the forms (`llp/0309.000-operator-delta-semantics.spec.md:479-486`). Graph delta candidacy checks only `SNAPBACK_GRAPH_DELTA_DISABLED` (`crates/snapback-engine/src/local/engine.rs:33498-33523`), and `try_graph_delta_fanout` has no execution-switch check (`:34120-34136`). `SNAPBACK_GRAPH_EXEC_DISABLED` is explicitly dynamic but is checked only at memo/fresh graph execution (`:9055-9069`, `41932-41951`). An already established eligible subscription can therefore still enter incremental evaluation after the execution switch is raised. That is a safety-relevant shipped divergence which Stage B should classify, not an existing gate the Spec may assume.

The nearby “auth-scoped subscriptions are excluded” statement is accurate for graph deltas (`:33498-33503`, `34132-34136`) but not for DK-3 generally: DK-3 permits authorized add/update deltas and only forces replace for removals (`:34449-34473`). Its scope should be made explicit.

## Confirmed sound decisions

- The `presence:"required"` correction is accurate at evaluator level. Null/omitted join keys and point misses set `GraphRequiredEdgeMissing` (`crates/snapback-engine/src/graph_evaluator.rs:1312-1330`, `1367-1372`), and the delta lane falls back when a fresh point evaluation becomes refused (`:3753-3760`) or cannot rebuild the proof (`:3789-3793`). These are not patch verdicts.
- The core OQ-2 finding—that `matched_count` is the wrong grain for support multiplicity and that uncertain 1→0 requires a bounded authorized re-probe—is sound, subject to the all-mode and through-edge 0→1 corrections above.
- Search-membership is correctly named-refused by admission and defense-in-depth evaluation (`crates/snapback-types/src/manifest/graph.rs:4485-4512`, `4935-4942`; `crates/snapback-engine/src/graph_evaluator.rs:2965-2975`).
- The “window ledger is cost-only” finding is correct: `GraphWindowLedgerV1` contains only cumulative pages/rows/bytes/ranges, not boundary or membership state (`crates/snapback-engine/src/graph_evaluator.rs:99-109`).
- The graph stale-capture latch and one-delta-per-refreshed-capture description is substantively correct: captures are copied forward and the outer lane sets `delta_requires_replace` (`crates/snapback-engine/src/graph_evaluator.rs:3887-3889`; `crates/snapback-engine/src/local/engine.rs:34353-34362`).
- The proposed corpus layout, determinism/freeze discipline, expected-next-state vectors, and comparator posture follow existing conformance patterns. The problem is the unresolved semantics and missing read-effect model, not the general testing methodology.

## Fresh MATERIAL concerns

### 1. The closed FALLBACK contract assigns two reasons to the same input

Section 1.0 says a required request absent from `R` returns exactly `FALLBACK(read-unavailable)` (`llp/0309.000-operator-delta-semantics.spec.md:69-76`), and §7.2 requires every read-requiring vector rerun with empty `R` to expect that reason (`:690-692`). The operator rules instead assign domain reasons on the same absence:

- missing E3 tail → `boundary-displacement` (`:290-295`) or `completeness-indeterminate` (`:296-302`);
- missing E4 point → `scope-unfilled` / `rekey-unread` (`:341-345`);
- missing E5 range → `scope-unfilled` (`:369-372`);
- missing E6 probe → `support-unproved` (`:398-414`);
- missing lift read → `scope-unresolved` (`:435-442`).

Thus identical `(state, Δin, R=[])` has two normative results. This is material even though all reasons select replace on the server: reasons belong to the promised pure evaluator, frozen vectors, amendment-controlled set, and other-consumer handling. The Spec must define precedence and when each domain reason remains reachable.

### 2. E3 returns the wrong window when a known candidate masks underfill

Use ascending `take=2` with retained `A1,B2`, `complete=false`, and unseen `C3`. In one commit, delete `A` and insert admitted `X4`.

E3 step 3 computes top-2 of known `{B2,X4}` and obtains `{B,X}` (`llp/0309.000-operator-delta-semantics.spec.md:281-289`). Because its size equals `take`, step 4 performs no tail read (`:290-295`). Fresh evaluation is `{B,C}`. This violates the defining equivalence, not merely a preferred optimization.

The shipped evaluator discards exactly this information: it reads one-row lookahead, computes `has_more`, truncates, and retains only requested rows (`crates/snapback-engine/src/graph_evaluator.rs:1147-1157`, `:1201-1216`; per-parent equivalent `:1525-1536`). A tail competitor must be considered after a retained leave/re-rank even when in-batch candidates keep known-set cardinality at `take`; underfill is not a sufficient trigger.

### 3. E3’s completeness transition is incomplete, and `R` cannot encode the exhaustion fact it consumes

There are three independent counterexamples:

1. Start with ascending `take=2`, retained `A1,B2`, `complete=true`. Insert admitted `C3`. Step 3 still returns `{A,B}` and there is no underfill. Step 5 says `complete' = complete` except for its listed cases, so it preserves `true` (`llp/0309.000-operator-delta-semantics.spec.md:287-304`). Fresh evaluation sees the lookahead row and sets `complete=false` (`crates/snapback-engine/src/graph_evaluator.rs:1147-1192`). A known discarded candidate proves incompleteness; r2 omits that transition.

2. For an incomplete full window whose sole unseen source row is `C`, an update making unretained `C` fail E0’s predicate can change fresh completeness to true. E0 reports only was-retained for window consumers (`llp/0309.000-operator-delta-semantics.spec.md:244-253`), but E3 step 5 re-proves only a **delete** of an unretained row (`:298-304`), not an update leaving admission or the interval.

3. After deleting one retained row from incomplete `{A,B}`, compare W1 with tail `{C}` and W2 with tail `{C,D}`. The prescribed `tail(window,k)` has `k=deficit=1`, and §1.0 defines responses as admitted rows only (`:58-66`). Both transcripts contain `[C]`, yet `complete'` is true in W1 and false in W2. Step 5’s “read’s exhaustion” is not a field in `R` (`:296-302`). Full evaluation obtains it through lookahead before truncation (`crates/snapback-engine/src/graph_evaluator.rs:1147-1157`, `:1525-1536`).

Unlike step 4, 5(c) never joins the returned row into the working map, and §9 expressly calls this request label-only (`:887`). Only an empty authenticated tail can prove this window complete; a nonempty response proves incompleteness regardless of its local exhausted bit.

   The request is also undefined when the new window is empty. R4 defines a synthetic near-end boundary only for an empty **retained** window’s `B_old` (`:352`), while 5(c) requests from the **final** boundary (`:378`). For old incomplete `A<B<C`, retained `A,B`, with all three deleted in one batch, step 4 can exhaust and leave the new window empty while the unretained delete of `C` meets the literal 5(c) trigger. The rule must either state that step 4’s proof suppresses 5(c) or define an empty-final-window origin. As written, the claimed executable trigger is not total.

3. **The added `op` tag preserves the last raw operation, not necessarily the net pre→post transition required by “inserts never trigger.”**

   The Spec normalizes by retaining the last change per key (`llp/0309.000-operator-delta-semantics.spec.md:124`) and ΔZ preserves that folded operation kind (`:140`). The shipped fold likewise stores the last `ChangedRow` (`crates/snapback-kernel/src/live_matcher.rs:3581`). Storage processes ordered explicit-ID writes and records their raw insert/delete entries (`crates/snapback-kernel/src/storage.rs:1503`, `:6756`, `:6918`, `:7069`); delete/recreate of an ID is supported with a fresh incarnation (`:19632`).

   Counterexample: retained `A,B`, with sole unseen admitted row `C` and `complete=false`. In one batch, delete `C`, then reinsert the same key with a final image outside admission or the interval. Last-change folding produces `op=insert, stay-out`. The working map remains `A,B`; neither tail competition nor 5(a) runs, and 5(c) expressly exempts inserts (`llp/0309.000-operator-delta-semantics.spec.md:380`). It therefore retains `complete=false`, while fresh evaluation has exhausted source `A,B` and is complete, violating the defining equivalence at `:94`. The carrier needs net removal potential, not merely the last raw tag.

## Material findings

1. **The normalized “last image” can be an intermediate image, not the net pre-image.**

   A patch from join scope A to B followed by a delete is a valid same-commit sequence. Storage emits the patch’s post-image B (`crates/snapback-kernel/src/storage.rs:5598-5613`) and then the delete’s immediate pre-image B (`:5656-5682`). Under r5, first `update` + last `delete` becomes a net delete whose “folded image is the last image” (`spec:124-134`), yielding `delete(pre=B)` even though the batch pre-image was A.

   This is observably unsound for E6. Scope attribution derives affected scopes from folded images (`spec:550-555`), while retained state holds support bits rather than support rows (`spec:783-791`). If the row was A’s sole support, the fold can re-probe B and leave A stale-true although fresh evaluation yields false, violating the equivalence requirement (`spec:91-99`). The repository already preserves first-touch pre-images where transient keys matter (`storage.rs:5023-5027`).

   The fold must preserve the true first pre-image when available; otherwise it must mark the pre-image missing and take the applicable fallback. The last delete’s intermediate pre-image cannot stand for the net pre-image.

2. **5(a) and 5(c) remain batch-overlapping.**

   Counterexample: `take=2`; old source `A@1, B@2, D@3`; retained `[A,B]`; `complete=false`. The batch deletes unretained D and inserts admitted `C@4`.

   Step 3 remains `[A,B]`, and step 4 does not run because the window is full and neither selected row ranks beyond `B_old` (`spec:363-375`). C is an admitted working-map row left unselected, so 5(a) proves `complete'=false` (`spec:377-385`). Independently, D is an unretained delete that never entered the map, so the literal 5(c) trigger requires a label read or `FALLBACK(completeness-indeterminate)` (`spec:385-402`).

   Thus r5’s “disjoint from (a)” assertion is false at whole-batch grain, where forms operate (`spec:135-137`, `:420-425`). It also leaves conflicting readings of the verdict, contrary to §1.0’s uniqueness requirement (`spec:79-84`). Any batch-level 5(a) witness must explicitly subsume 5(c), or 5(c) must be gated on the absence of 5(a).
