Revision 2 fixes the capture order, preserves whole parent rules, and replaces background adoption with atomic activation. It still has authorization defects and incomplete incarnation semantics. Nothing was changed; these are design probes, not executed implementation tests.

Here, **A1–A8** identify the Astra findings and **G1–G10** the Grok findings.

|---|---|

| **A2 — schema interpretation** | **Partial.** Changing a captured parent field’s default triggers atomic recapture. Changing the child reference’s default does not appear in the specified dependency identity; see 6. |

An online-only child now requires parent read authority before insertion. But §4’s explicit-sync exception can still deliver children and captures to unauthorized recipients; see 2. |

| **A5 — whole-rule derivations** | **Partial.** Intermediate parent restrictions survive substitution. Child-local restrictions still invalidate the blanket page-completeness claim; see 3. |

The remaining findings are:

1. **Blocker — §§3.1, 4 “Sync”, 5: incarnation does not protect id-keyed authorization.**

   Let a chat read under `exists members[.id, viewer]`. Its children capture chat id `X` and incarnation `k1`. Delete the chat and memberships, recreate `X` as `k2`, and legitimately grant Bob membership in the new chat.

   Old children still evaluate `exists members[X, Bob]`. Bob therefore receives them through sync or other reads, although the new chat’s pinned page excludes them. The incarnation is absent from both the authorization probe and the sync group. Current [partition routing](../../snapback4/crates/snapback4-core/src/partition.rs:114) uses those audience values directly.

   **Smallest fix:** prohibit id reuse for `readable` targets while retaining raw-id membership keys. Supporting isolated reuse requires incarnation-aware membership keys and sync inversion too. Merely adding incarnation to child indexes does not provide the claimed isolation.

2. **Blocker — §4 “Sync”: the explicit-audience exception permits unauthorized delivery.**

   Consider:

   ```quarry
   read <- readable issues[.issue] and .author = viewer
   sync to .author
   ```

   The read rule implies the named audience, satisfying the RFC’s wording. But after the author loses issue membership, `.author` still receives the child and its captured inputs. Implication runs in the wrong direction for safe delivery.

   This contradicts both [LLP 3000.007 §6.6](../../llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:787) and [validate_sync](../../snapback4/crates/snapback4-core/src/schema.rs:1076). The binder also applies exact inference to explicit declarations.

   **Smallest fix:** delete that exception. Explicit and inferred sync must pass the same existing exact-audience admission after substitution and service stripping.

3. **Blocker — §4 “Pages pinned by the parent”: parent inputs do not decide child narrowing conjuncts.**

   A public parent has children reading under:

   ```quarry
   read <- readable parents[.parent] and .author != viewer
   ```

   Pinning `.parent` leaves `.author` unknown. The specified single verdict cannot authorize every child. With the current evaluator, an omitted `.author` becomes null, and `null != viewer` evaluates true, exposing rows the rule denies. An equality restriction instead produces a falsely empty, complete page. See [prefix_verdict](../../snapback4/crates/snapback4-core/src/engine/read.rs:85) and [term evaluation](../../snapback4/crates/snapback4-core/src/engine/rules.rs:263).

   **Smallest fix:** the parent lookup determines only captured fields. Apply existing uniformity analysis to the *entire child rule* afterward. Unpinned residual fields retain per-row authorization and the non-uniform completeness class.

4. **High — §§2.4, 3.3: blanket `E_RULE` creates an upsert existence oracle.**

   Compare two worlds with the same unreadable parent `p`. In one, child `c` exists but is unreadable; in the other, `c` is absent. Upsert `c` with `issue: p`, with child insertion otherwise allowed and update denied.

   The existing-child branch returns `NOT_FOUND`. The absent branch reaches the new implicit parent guard and returns the RFC’s `E_RULE`. Their meter treatment differs too: [target_attempt](../../snapback4/crates/snapback4-core/src/engine/write_target.rs:12) restores `NOT_FOUND`, while [insert_upsert](../../snapback4/crates/snapback4-core/src/engine/write.rs:130) deliberately translates denied insert authority into that hidden-target shape.

   **Smallest fix:** specify an effect-specific refusal table. Plain insert/if-absent keep `E_RULE`; denied upsert-insert preserves `NOT_FOUND` and its meter normalization. Reserve possible capture work before choosing the hidden update/missing insert branch.

   Also spell the guard as **live parent exists AND its rule admits the writer**. Evaluating an `allow` parent rule over null captures cannot enforce existence.

5. **Blocker — §§3.4, 6: recapture can attach old children to a replacement parent.**

   Child `c` captures issue `p`, incarnation `k1`, org A. Delete `p`, recreate it as `k2` in org B, then adopt a change to the parent’s read-rule dependency identity.

   Section 6 resolves live parents and recaptures descendants. It finds `p`, so the missing-parent check passes. Copying `k2` and B moves A’s old child into B’s pages and audience. Preserving `k1` while copying B is also wrong: other reads disclose the child to B.

   Ordinary recorded attribution explicitly [preserves existing captures across rebuilds](../../snapback4/crates/snapback4-core/src/engine/recorded.rs:104); this extension needs its own precise migration rule.

   **Smallest fix:** never change an existing captured incarnation during recapture. Require the live parent to match it; a missing, expired **or mismatched-incarnation** parent aborts activation. Initial adoption and subsequent recapture must be distinct operations.

6. **High — §3.4: dependency identity omits the child’s reference interpretation.**

   An older child physically lacks `issue`. Activation adds required, immutable `issue default 'p'` and captures `p`. Later the default changes to `'q'`.

   The parent rule, captured field types/defaults, and parent captures are unchanged—the complete listed identity is unchanged. Yet the child now reads as `.issue = q` while retaining `p`’s incarnation and audience. This is possible because [activation leaves literal defaults unstored](../../snapback4/crates/snapback4-core/src/store/activation.rs:108).

   **Smallest fix:** include the child reference’s binding, target table, type, optionality and default in the capture descriptor. Materialize the immutable reference when first capturing it, or refuse interpretation changes that would retarget existing children. Include reference-path changes even when both parents have identical read rules.

7. **High — §4 “Pages”, “Aggregates”, “Devices”: unheld parents are not absent parents.**

   A device holds comments but lacks their issue because the issue table is online-only or has a shorter horizon. The issue still exists on the server. Applying “an absent parent gives an empty, complete page” locally yields a false answer; a scalar count can similarly become a false zero.

   The recorded-path coverage requirement applies to **inserts**, not automatically to these new reads. Existing [read authorization](../../snapback4/crates/snapback4-core/src/engine/read_auth.rs:57) distinguishes covered absence from unknown evidence.

   **Smallest fix:** define a shared parent resolver with explicit found, covered-absent, denied and unknown outcomes. Register its parent dependency in residency, subscriptions and expiry invalidation. Unknown prevents completeness and falls back to the server; child coverage must still be checked separately.

   For provisional parents, specify authorization through the provisional-read path, stable identity for the logical pending insertion, and dependent replay after settlement/refusal. “The server replaces both” is insufficient when parent and child belong to different pending mutations.

8. **Medium — §4 “Sync” and “Pages”: cursor confidentiality conflicts with incarnation-bound continuation.**

   Fetch page one under `p/k1`, then recreate `p` as `k2` without changing schema generation. A cursor containing only child sort keys/id can resume against `k2`, skipping its earlier children and mixing two parent relations.

   Conversely, reusing today’s cursor machinery serializes the actual prefix—including the newly inserted incarnation—into [CursorScope](../../snapback4/crates/snapback4-core/src/cursor.rs:33), contrary to the unconditional hidden-field prohibition.

   **Smallest fix:** bind continuation to the resolved parent incarnation through an opaque scope fingerprint, while excluding captured audience values. Specify rejection/restart on incarnation change, with authorization checked before any mismatch response that could reveal a hidden parent.

9. **High — §4 “Aggregates”: the motivating maintained column has no incarnation contract.**

   `issues.comments: count comments by issue` is a maintained column. Revision 2 specifies a maintained **view**, but does not change column birth, mirroring or old-contribution removal.

   Today [birth_columns](../../snapback4/crates/snapback4-core/src/engine/columns.rs:40) reads totals by parent id, and `mirror_column` updates whichever live parent has that id. After recreation, the new issue can inherit the old total; deleting an old orphan can subsequently modify the replacement issue’s count.

   **Smallest fix:** explicitly give maintained columns the same composite contribution key. Birth reads `(id, current incarnation)`; mirroring applies only when the contribution incarnation matches the live parent. Keep the disclosure note until that proof applies. For scalar views, also state the result table explicitly: authorized live empty group → zero; unavailable/denied parent → indistinguishable unavailable result; unknown device evidence → incomplete.

The sound core is small: copy the immediate parent’s full stored rule inputs transactionally, protect engine-owned fields, retain live membership evaluation, and preserve existing exact sync admission. Atomic publication and independently declared leave policies are appropriate.

A simpler first implementation would admit the inherited rule as the whole child read rule, retain exact sync checking, and defer reusable target ids. That handles the motivating tracker and Clique audience shapes without introducing residual-rule uniformity, general audience implication, or incarnation-aware membership machinery simultaneously.

**Overall verdict: NOT READY.**
