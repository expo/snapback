# Blind review: LLP 3000.000.000.001 (STAGE) at `bda003c332f5f36b85ecc70d4b4ddc491dde9b96`

**Verdict: NOT READY** — one material finding (stale guide contract contradicting the shipped default, inside this RFC's own deliverable). No material security or separation defect found. Details below.

Scope and method: read-only. I read the RFC, `snapback4/AGENTS.md` (plus the fence/LLP pointers it requires), the full STAGE diff (`e25de6ae10^..bda003c332`), and the surrounding implementation. I did not read `llp/reviews/`, `WORKSTREAM-REPORT.md`, or any author reasoning. I did not invoke Cargo and did not run `scripts/test.sh`, per instructions. I ran only `./ref-check` (read-only Python validator): **ok — 552 LLP docs, 12005 refs, 0 errors, 0 unchecked**.

## What verified clean

**Production/staging separation** (`snapback4/crates/snapback4/src/verbs/staging.rs`, `verbs/releases.rs:226-239`). Classification is store-bound (`deployment_environment` meta in `store.sqlite`), set only for a fresh store under the deployment command lock (`command_lock` acquired before the `existed` check, so no TOCTOU between concurrent deploys). Existing/legacy stores refuse relabelling fail-closed; `--check` never writes (early `Ok` on fresh, read-only verify on existing). Repeat `--staging` on a staging store is idempotent. Retention across deploy/rollback/restart/copy falls out of storing the marker in the store file itself, and `deploy`/`rollback` never touch it. `serve` reports `environment` from the same meta per request (`serve.rs:1054-1062`), defaulting unknown to `production`. The `staging.test.mjs` suite asserts relabel refusal, hot-upgrade/rollback retention, and repeat-while-serving. No defect.

**Auth and dev doors** (`serve.rs:878` fence, `serve_dev_doors.rs`, `serve_identity.rs`, `serve_maintenance.rs`, `latency.rs:292-308`, `serve_token.rs`). The design is sound and the coverage is complete:
- `/dev/token` (`ENDPOINT == "/dev/token"`) is routed before the doors fence and keeps its mutual file-proof (loopback + Host + no Origin + store secret + nonce challenge). Correctly exempt on password dev, per the RFC.
- The fence blocks `/dev/*` and `/seed` on password-only dev without the flag, before body intake; every privileged effect revalidates under the writer (`dev_authority` in seed/reset/clock-advance/job-enqueue), closing the slow-body and adoption-queue gaps the RFC claims.
- Writer revalidation (`mutation_authority`, i.e. re-resolve the exact credential under the writer) is present at **all** durable admission sites I enumerated: `/m/` preflight and execution (`serve.rs:1164,1410`), `/q/` + fallback engine path (`:1262,:1285`), `/sync` acquisition and stream pages (`serve_sync.rs`), `/changes` entry, asset serve/intent/declare/finish/cancel/intents, actions call/cancel, session-route ingress, ephemeral preflight/serve, following open. Persona read authority rechecks the declared cast without holding the publication mutex through I/O, with the engine transaction fencing schema replacement — matching the deadlock concern from the review record.
- Serve is bearer-only: personas refused, `/seed` and `/dev/reset` refused pre-body, `/dev/jobs` and `/dev/clock/*` refused, `GET /dev/latency` requires a live service token and its reset is dev-only. `dev_request` loopback fencing is dev-only, which is correct since serve binds beyond loopback with bearer auth.
- Persona semantics change (empty declaration admits none, `serve_identity.rs:42-55`) is consistent with the updated `cli_friction.rs` test expecting 401 for undeclared names.

**First-admin safety** (`verbs.rs:1283-1328` token verb, `serve_token.rs:113`, `dev_worker.rs:89,690`). Service sessions mint only via the local CLI (store command-lock or the file-proof live path) or the internal worker — no bearer-authenticated HTTP endpoint mints service tokens, so privileged password accounts cannot escalate to service minting. Signup takes email/password only (`auth.rs:237-249`); roles come solely from the operator-only `provision` mutation, itself double-guarded by the `require viewer = 'service:operator'` rule and the `roles` insert rule. No first-caller-wins, no client-selected role, no operator credential in the frontend recipe. The guide's first-admin script uses an explicit operator-chosen password plus local `operatorToken()`. No defect.

**Proof helpers and secret hygiene** (`packages/snapback4/src/proof.ts`, `proof-accounts.ts`, `proof-process.ts:99-113`). `startServe(deployDir, …)` validates its first argument (`E_PROOF_USAGE`, already covered by `wave13-surface.test.mjs:58`); `operatorToken()` validates service/days and captures the token over a pipe with stdout withheld from logs; `seedAccounts` validates shape (1–100 accounts, role/mutation-name patterns, timeout) and environment (`staging`, `development === false`, password identity) **before** minting or creating anything; only explicit HTTP 429 `E_RATE_LIMIT` retries signup, never ambiguous writes; partial failure is disclosed, not rolled back-by-claim; failed `seedUsers` stops its own host. The `staging.test.mjs` log-sweep for token absence matches the mechanism. No defect.

**Caller migration for persistent `startDev`** (the executable amendment). Complete in-tree: `frontend-proof.mjs:21` selects `--memory` + `--unsafe-dev-doors`; `proof.test.mjs` was converted to explicit `--memory` where isolation is asserted; all Rust fixtures that need doors either declare `use personas` (doors open by schema) or run through `with_default_doors` (flag off, `serve_refusals/mod.rs:109-114`) for the new closure tests, while legacy hosts keep `unsafe_dev_doors = dev` (`:115-125`) — a deliberate, sound split. `devServer`/`launch` in `witness/lib.mjs` default `unsafeDevDoors: false`, which preserves sb4-loop/loopbar/witness behavior since the chat schema is guest-based. Flag table (`bin/cli-commands.json`) registers `deploy --staging` and `dev --unsafe-dev-doors`, and `serve` correctly has no such flag (passing it errors). `--no-memory` was never a binary flag (kit-level alias only), so kit-side consumption is not a CLI regression. The 0.4.30/0.4.31 retained templates are digest references only — `proof.rs:190-195` emits the **current** template for adapted apps — so no stale proof is generated. No defect.

## Material finding (blocks READY)

**F1 — `guide/testing.md` still teaches the old `startDev` contract, contradicting the shipped default and this RFC's §4.** The workstream added a correct intro (`testing.md:3`: "startDev persists unless --memory is explicit") but left the body inverted:
- `testing.md:150`: ``const dev = await startDev(); // memory store`` — now a **persistent** project store.
- `testing.md:180-183`: "`startDev({args})` still adds --memory unless --store or --no-memory is explicit… choose --no-memory for its project store" — false on both clauses: the kit no longer injects `--memory` (`proof.ts:52-58`), and `--no-memory` is not a valid binary flag (absent from `cli-commands.json`; direct use fails validation with "dev takes no --no-memory").
- `testing.md:317`: "Each dev memory start is empty" — false by default now.

This is material, not style: the guide is the builder contract for the exact helper this RFC redefines, and the stale text produces inverted expectations (cross-run state where emptiness is assumed; a refused flag where the project store is advised). **Repair**: rewrite those spots to the persistent default, e.g. `const dev = await startDev(); // persistent project store; pass {args:['--memory']} for a disposable store`, replace the paragraph at :180-183 with the :3 contract plus the `--memory`/`--unsafe-dev-doors` opt-ins, and qualify :317 ("Each disposable (`--memory`) dev start is empty…; on a persistent dev, POST `/dev/reset`…"). Then re-run the guide checks.

## Non-blocking observations (do not affect the verdict)

- **O1 (minor, warning accuracy)**: `serve_start.rs:347-351` prints "WARNING … UNSAFE development doors enabled" for **every** non-password dev, i.e. the ordinary guest/persona default workflow, conflating it with explicit `--unsafe-dev-doors`. Suggest gating the UNSAFE wording on the explicit flag and using a neutral doors-open line otherwise; as-is it trains warning blindness.
- **O2 (minor, robustness)**: `seedAccounts` does not preflight that the named `provision` mutation exists before creating accounts; a typo'd name leaves partial accounts. The documented partial-failure handling covers it, but an authed `/schema` (or single dry provision-shape) check before the first signup would make "inputs are validated before effects" airtight.
- **O3 (not a finding — missing qualification, runs separately)**: I could not verify execution claims — full crate suites, affected client tests, Darwin-on-Mac-Studio runs, packed-tarball Linux qualification (`qualify-linux --consumer-only`), or the guide/client test suites — because Cargo/test execution was out of bounds for this review. The RFC correctly records packed/platform qualification as still to come (§6); only the "native suite passes" statement should be treated as unverified until the claim-relevant qualification digest exists. No overclaim beyond that.

## Bottom line

Implementation versus sb4-loop and versus the RFC text: separation, doors, first-admin, helpers, migration, and secret handling are correct as written, with revalidation at every durable admission site and fail-closed ordering in every adoption window I checked. The single blocker is the self-contradictory `testing.md` contract (F1). Fix F1 (small prose repair + guide checks), optionally address O1/O2, complete the separately-run packed/platform qualification, and this should be READY.

**Verdict: NOT READY** (sole blocker: F1, `snapback4/crates/snapback4-lang/src/guide/testing.md:150,180-183,317`).
