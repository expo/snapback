### Fast path (hosts and smuggling)

`try_call_text` (`call.rs:163-181`) deserializes `PageArgument { op, page, first }` from the **original** `&str`, then `validate_text(request)` on that same slice, then `apply`/`observe_store`. Duplicate envelope fields fail the derive (`if let Ok`), then `from_str::<Value>` last-wins — BASELINE dispatcher semantics. A second `page` key cannot be typed-decoded as one object and tree-decoded as another; only one branch runs.

Same text entry: `web.rs:42-44`, `ffi.rs:104-107`, `verbs.rs:925-927`. Rust `call()` (`call.rs:42`) and `ffi::call` (re-export, `ffi.rs:15`) skip the fast path. Device tests still use `call()` (`tests/device.rs:54-55`).

## Findings

### High — `differential` does not compare the new path to the old one

`snapback4/crates/snapback4-device/tests/codec.rs:9-16`

`from_text` is `serde_json::from_str` (`json_codec.rs:12-14`); `to_text` is `to_string` (`json_codec.rs:62-64`). The helper therefore asserts `from_str` equals `from_str` and `to_string` equals `to_string`. Corpus/backends/`#[serde(default)]`/`deserialize_text_format`/hex `Bytes` never exercise `from_value`’s re-render, `to_value`’s parse-back, `from_slice`’s UTF-8 gate, or `to_vec`’s `String::into_bytes`.

**Scenario:** `from_value` mishandles a `Queued.args` tree (number spelling, nested object) after `value.to_string()`. `differential::<Queued>` still passes. Product `admit`/`enqueue` go through `parse` → `from_value` (`call.rs:29-31, 102-105, 127-128`).

**Fix:** For each adapter, assert against the **pre-funnel** API: `from_value` vs `serde_json::from_value`, `to_value` vs `serde_json::to_value`, `to_vec` vs `serde_json::to_vec`, `from_slice` vs `serde_json::from_slice`, including duplicate keys, `u64` above `i64::MAX`, i53 edges, omitted `skip_serializing_if` fields, `"handle"`/`"url"`, uppercase hex, and error strings.

### High — `text_page_and_owned_dispatch_agree` cannot catch a shared decode change

`tests/codec.rs:164-182`

It compares `call_text` to `call()` after `from_str::<Value>`. Both are IMPL_COMMIT. Duplicate-key last-wins is checked only as “fast path falls back and matches owned,” not “matches BASELINE `serde_json::from_value`.”

**Scenario:** `from_value`’s re-render changes how `StreamEvent.data` numbers round-trip. Both arms use `from_value` on fallback and agree; wasm still mis-applies a hand-crafted page with duplicate nested keys.

**Fix:** On awkward inputs, compare `call_text` to `serde_json::from_value::<StreamPage>` / BASELINE `from_value` of the page subtree, not to `call()`.

### Medium — “Old store” bytes are not a BASELINE capture; SQLite and reverse open are absent

`tests/codec.rs:94-129`

Records are built with live `serde_json::to_string` (`108-120`), then `schema.hash()` is checked against `Sha256(to_string(schema))` (`100-101`) — true because `hash` → `canonical_json` → `to_text` → `to_string`. Only `MemoryStore`. No IMPL-written image opened by BASELINE `from_str`.

**Scenario:** A funnel change later writes stored backends/rows with a different encoder than `canonical_json`. This test still constructs “old” bytes with the same encoder `hash()` uses, so it stays green while a real BASELINE IDB/`*.sqlite` would reset or rewrite.

**Fix:** Embed a literal change list (and a SQLite file) captured from BASELINE `to_string`. Assert exact `k`/`v` bytes after open. Add the reverse: IMPL `to_text` bytes decoded with `serde_json::from_str` only.

### Medium — Product apply path is a second envelope the suite does not run

`call.rs:165-178` vs `call.rs:80-85`; tests: `tests/device.rs:54-55`

`PageArgument` knows `op`, `page`, `first`. The dispatcher’s `apply` arm is the same today. Wasm/FFI/process use `call_text`; almost all device tests use `call()`.

**Scenario:** A later apply field (for example `stage`) is read in `call()` and covered by `tests/device.rs`. Browser/FFI/CLI ignore it (`serde` default drop on `PageArgument`) and keep applying with `first` default false.

**Fix:** Drive apply/observe_store in the shared device suite through `call_text` on **both** stores, or deserialize `first`/`page` from one shared struct used by both arms.

### Medium — Metrics line attributes the diet wasm to the baseline commit

`snapback4/metrics/wasm.jsonl:5` — `"sha":"70a663c22"` with `gzip:462005`. `70a663c22` is BASELINE (journal’s 1 891 742 / 520 557). `measure-wasm.sh:21` uses `git rev-parse --short HEAD` at measurement time, before this commit.

**Scenario:** A later reader treats 70a663c22 as already 462 005 B and concludes S1 saved nothing, or that main at that SHA shipped the diet.

**Fix:** Record the implementation SHA (and the base SHA in a separate field). Do not leave the diet artifact under the baseline id.

### Medium — Plan-required Chromium acquisition is missing

`llp/3000.002-end-to-end-resource-bounds.research.md:447-459`: every rung, including no-format-change, needs actual Chromium acquisition and offline reopen; S1 also needs paired cold-open on the scale witness. Journal: witnesses not run; `diet_timing` is native debug (`tests/diet_timing.rs:9-11`).

**Scenario:** Same class as the reverted handwritten decoder: unit/codec green, IDB reopen or cold apply in Chromium regresses. This review cannot rule that out.

**Fix:** Run `witness/idb.mjs` (and the named scale timing) on this artifact before treating S1 as landed evidence.

### Low — Budget unit test does not prove the suite path

`packages/snapback4/test/wasm-budget.test.mjs:10-24` only spawns `wasm-budget.mjs` on temp files. It would pass if `build-wasm.sh` never called the helper.

**Fix:** Assert `scripts/build-wasm.sh` / `measure-wasm.sh` invoke the helper (or a dry-run of those scripts with a fake wasm).

### Low — LLP/ticket still describe S1 as an estimate

`llp/3000.002-end-to-end-resource-bounds.research.md:351` still “about 455 000”; `issues/20260913-snapback4-wasm-device-diet.md` has no S1 measured outcome. Journal has 462 005.

**Fix:** Write the measured gzip/budget/sha into the plan table and a dated ticket note.

## Questions (no concrete failing input)

- Does `Error::custom` after `argument_error` (`json_codec.rs:56-59`) stay stable if serde_json’s Display of positions changes (`at line N column M` vs a comma form)? Only two `from_value` errors are pinned (`tests/codec.rs:186-192`).
- Does cargo fingerprint `CARGO_PROFILE_WASM_STRIP=none` for `target/wasm-sym` so a previously stripped artifact cannot be twiggy’d as current? The script rebuilds then refuses empty/truncated tables (`attribute-wasm.mjs:22-24`); I did not run a fingerprint probe.
- `--families` uses `[^<>]*?` (`attribute-wasm.mjs:67`). I did not find a derived Snapback type whose rustc name contains `<>`; if one appears, the census can report a single family while a second survives.

## Did a change introduce a new problem?

Nothing I can name that is wrong, less durable, or less safe **on current inputs** relative to BASELINE: identities still `to_string`, apply text hosts share `call_text`+`validate_text`, meter still `to_writer`. New hazards: (1) a second apply envelope only product hosts use; (2) `from_value` now allocates a full JSON string of dispatcher trees; (3) every apply/observe_store walks JSON twice (`from_str::<PageArgument>` + `validate_text`). (2) and (3) are not charged as interpreter heap; native debug did not show a repeatable apply regression. A cached BASELINE runtime still parses IMPL text (no new loud refusal), which is correct **if** bytes are unchanged.
