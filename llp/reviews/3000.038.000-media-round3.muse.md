The design is substantially coherent and the implementation matches the text on most axes: single-outbox custody with atomic admission, `begin_send` refusal on unresolved uploads, FIFO head-hold (unready head returns out of `flushOnce`), id-stable duplicate admission via stored fingerprint, pin-qualified sweep and quota queries, retryable/nonretryable refusal taxonomy, viewer/store fencing, and the Exact/host API boundary. Two issues are MATERIAL:

1. Abandoned server pins are immortal and strand quota permanently. §3 pins pending intent bytes "until the matching owner + mutation-id has a durable execution outcome, or the intent is cancelled," and both the sweep (`assets.rs stale()`) and the 128 MiB quota query (`asset_uploads.rs:121`) honor the pin indefinitely. But §2 declares browser eviction and cleared app storage outside durability — exactly the cases that orphan a pin. Cancellation requires the id, and no API lists a viewer's pending server intents, so an orphaned pin has no release path: not timeout, not reclamation, not even store replacement (the quota query has no store predicate). Two abandoned 64 MiB captures permanently deny all future uploads with `E_UPLOAD_QUOTA`. A bounded pin lifetime or a documented recovery path is a design change, not a test gap.
2. `store_id` is not required on intent upload, contradicting §3. `cancel` and `finish` refuse on store mismatch (`assets.rs:286,304`), but `POST /assets?intent=` only checks the store "if let Some" (`assets.rs:68-72`). An intent upload omitting `store_id` commits to whatever store is live with no binding check, while the RFC claims it is "required on SDK intent transport and checked before replay." The SDK always sends it, so impact needs a non-conforming client, but the normative claim is unenforced at the trust boundary.

Non-blocking notes. `finish` after `cancel` still records an applied failure receipt (the `UPDATE ... != 'cancelled'` preserves the pin state but not receipt absence) — worth stating whether that is intended. `DeviceUploads.prepare()` throws `E_AUTH` on viewer mismatch instead of returning, pushing a permanently fenced head into the flush catch/backoff path. Device quota sums all viewers' bytes, not just the admitter's. Re-upload under a cancelled id admits locally then burns a full byte upload before the server's tombstone refusal — the "new id after cancel" rule should be explicit. Qualification exists (`upload_intents.rs` core/device, `upload-intents.test.mjs`, `upload-browser.test.mjs`, `upload-delivery-matrix.mjs`, expanded fault sites) but I did not run it, so browser reload/orphan-transfer, blocked exit send, uploaded-but-unplaced recovery, and the full fault census remain incomplete qualification, not blockers.
