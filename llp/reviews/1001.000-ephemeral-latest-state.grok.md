## Strengths

Latest-state rooms are the right replacement for the untyped `{ from, payload, at }` pipe. Scope stays the query; the room stays the result set; values stay closed, typed, and TTL-bounded. That matches the useful boundary you already chose.

The security skeleton is the right one: owner-minted key plus unguessable lease, principal/`from` assigned by the owner, subscribe to open, publish to `set`, `clear` still allowed after publish loss, no client-chosen keys, no lease resurrection, no Last-Event-ID replay, reconnect always mints a new lease. Stale-write control via per-lease strictly increasing versions, including consuming a version on a denied-but-valid `set`, is the correct antidote to delayed HTTP.

Owner serialization of admission, expiry, snapshot, and fanout, plus whole-snapshot coalescing with terminal refusals winning, avoids a delta protocol you do not need. Compiler and generation admission both checking `value`/`ttl`, with server-side argument validation and TypeScript treated as non-validation, is the right split.

LLP 1006.002 is correct: keep assets on the durable column. Channel values must not take asset, byte, or cursor types. Open asset GC tickets must not gate this work.

## Material concerns

These are definite holes in the written contract, not optional taste. Each fix is a few sentences.

### 1. Lease is not fully specified as the write locator

`POST /api/channel/<name>/set` and `/clear` repeat `args` while the lease already binds channel name, normalized args, principal, session epoch, and the live subscription. If the owner locates the row by lease and then applies the body `args`, a stolen or confused lease writes into another room. If it locates by name/args and only spot-checks the lease, a closed lease can be pointed at a live room.

**Minimal fix:** The lease is the sole locator. The URL name, body `args`, authenticated principal, and session epoch must equal the bound tuple or the command refuses as an invalid lease. The write is never relocated by body args. `set`/`clear` run on the same owner serialization as snapshot, expiry, and revocation; they re-check lease liveness on that turn. `set` re-checks publish on that turn. A closed, restarted, superseded, or session-fenced lease cannot write.

### 2. Version high-water vs validation order can reintroduce stale writes

The packet says a validated command consumes its version even when publish is denied. It does not say what happens for malformed values, name/args mismatch, invalid leases, or equal/older versions. The wrong order lets a repaired old request land after a newer `clear`.

**Minimal fix:** Check in this order: authenticate → lease identity/liveness → version (refuse `<=` high-water without bumping) → value/args well-formedness (do not bump) → publish admission for `set` (bump, then maybe refuse) → apply (bump). Only a well-formed command with a live matching lease and a fresh version raises high-water. A new lease starts at zero. Userland `set`/`clear` never take a version; the handle allocates from a local counter.

### 3. Wire frame vs public snapshot currently contradict each other

The frame literal includes `lease`. Later text says the public snapshot never exposes it. If the wire object is what `subscribe` callbacks or React state receive, the lease will be logged, copied, and XSS-harvested.

**Minimal fix:** Name two types. The owner→client transport frame may carry `lease`. `ChannelSnapshot` and user callbacks get `key`, `entries`, `status`, `reason`, refusal — never `lease`. The handle stores the lease in a private slot. `key` and `lease` are minted on open and survive value TTL; only the entry is removed on expiry. After TTL, a live lease `set` reinserts the same key.

### 4. Handle open/retain/close is internally inconsistent

Opening is “first observation or `set`.” `clear()` is not in that list, but it is a first-class API. Last observer “releases the stream,” yet a headless `set` “retains until `close`.” Those two rules collide after `set` → subscribe → unsubscribe, and they collide with React cleanup.

**Minimal fix:**
- Construct is inert.
- Observe or `set` opens. `clear()` on a handle with no live lease is a local idempotent success and **does not** open a connection.
- `client.channel()` stays open until `room.close()`, even with zero observers, once opened.
- `useChannel` owns that handle and must `close()` on cleanup, including Strict Mode and argument changes.
- A write bound to lease L is never redirected to lease L'. Reconnecting/offline writes fail locally. In-flight writes on L fail closed if L dies.

Without this, either React unmount leaks presence handles or `clear()` on a cold handle accidentally occupies one of the 64 room slots.

### 5. Auth on the new POST routes must not be a special case

The packet specifies bodies and refusal envelopes, not how the request is authenticated.

**Minimal fix:** These routes use the same session, CSRF, and principal/epoch binding as ordinary mutations. Cookie session without that binding is a cross-site `set`.

## Uncertain assumptions (not scored as holes)

- The existing commit-triggered subscribe fence is actually race-free, and publish traces are as complete as subscribe traces. If publish dependency recording is weaker, losing a membership can leave a value in the next frame. Reuse the same tracing machinery; do not invent a second fence.
- The owner is one serialized actor per room, so “before the next room frame” is a real total order covering HTTP `set`/`clear`, not only SSE.
- `expiresAt` is informational wall-clock; expiry decisions use a monotonic deadline so clock rollback cannot extend life. The packet already requires this; it is an implementation tripwire, not a new design.
- Same-tab `useChannel` twice is two handles and two entries unless the React helper explicitly shares a handle. That is acceptable if documented; UIs that want one indicator per user coalesce by `from`, not by `key`.

---

## Optional suggestions

- State that two tabs/handles for one principal are two entries on purpose, and that “is typing” UIs should reduce by `from`.
- Keep the 4 KiB / 1 KiB / 64 / 1024 limits as runtime bounds. Do not add authored knobs.
- Do not add publish-only handles, principal keys, offline queues, or delta frames in this landing.
- Client `set`/`clear` promise errors should reuse the named diagnostics (malformed, closed lease, stale version, capacity, refused, ambiguous network). Ambiguous is client-side; do not invent a fourth wire state.
- Asset custody/GC defects stay under LLP 1006. This landing only keeps the column boundary and the channel type exclusion.

---

## Asset boundary

**Remain stable.** Channels are ephemeral latest state. Assets are durable column custody with a separate upload/claim/GC life. Putting asset/byte/cursor types into channel values would attach byte authority to TTL rooms and reconnect loss. Keep `sendPhoto.run({ photo: file })`, explicit `client.upload` for two-phase UX, and no fake query/mutation/file-store wrapper. LLP 1006.002 should stay a decision record, not a second implementation.
