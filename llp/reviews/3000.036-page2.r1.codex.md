**PAGE2: NOT READY.** The uncapped discovery design is sound under §14’s all-or-nothing fence. I found one material compatibility gap.

1. **The existing capability does not distinguish the new execution semantics.**  
   A device implementing §§0–14 advertises `branch-membership-v1` and understands cursor versions 4/5. It can therefore pass the inherited handshake for a PAGE2 backend. But a new row-id lane must report the logical position `(.at, id)`, whereas the inherited executor derives positions from the physical index suffix. A pinned `byId` range does not supply that suffix. The proposal also changes the source admission condition from capped discovery to total-point-or-cap.

   **Recommended fix:** require a new PAGE2 capability, checked before backend installation or page application. Alternatively, establish that every previously admitted device safely refuses these new forms; cursor decoding compatibility alone does not establish execution compatibility. Test a device supporting §14 but lacking PAGE2 against both uncapped discovery and row-id lanes.

**Time audiences: NOT READY.** Four material gaps remain in the frozen design.

1. **Server clock rollback conflicts with the device’s monotonic authority floor (§§2, 4–5).**  
   Suppose a membership opens at `100`. Advancement publishes its join and removes its pending entry. The device applies the commit with server floor `100`. If the server clock then falls to `90`, the server’s specified `live` predicate makes that membership absent, while the device continues treating it as open. No write or boundary transition reconciles them. Recrossing `100` also finds no pending entry.

   This is relevant to the existing release clock, which reads wall time in [dev_clock.rs](/home/ccheever/projects/sb4-w10-page2/snapback4/crates/snapback4/src/dev_clock.rs).

   **Recommended fix:** specify a durable, monotonic authoritative lifetime clock across requests and restarts, and use it consistently for openings, expiry, partition accounting and response samples. If rollback is supported instead, define the required closing/reopening events and compatible device-clock behavior.

2. **Private openings remain observable through replies and backlog availability (§§1.1, 4–5).**  
   Omitting the next-opening timestamp does not hide its meaning. If Alice’s private row opens at `T`, Bob’s held `/changes` request can wake with a new sequence and table invalidation at `T`, despite Bob receiving no payload. The existing changes reply exposes global invalidations in [serve_changes.rs](/home/ccheever/projects/sb4-w10-page2/snapback4/crates/snapback4/src/serve_changes.rs).

   Backlog handling adds another channel: Bob’s otherwise empty query becomes unavailable when enough private rows become due. Even never-live rows with `expire < not_before` can cause this if they remain unswept and consume bounded advancement work.

   **Recommended fix:** explicitly define which opening metadata is permitted disclosure. If opening existence and timing must remain private, filter observable wake/invalidation evidence and prevent unauthorized pending populations from changing logical completeness. Include paired worlds differing only in private scheduled rows, comparing replies, availability and wake behavior.

3. **Future-row metering is unspecified (§§2, 6–7).**  
   Consider two worlds before `T`: one contains no rows; the other contains many future rows in an otherwise readable scan range. Their logical answers must match. If future candidates consume ordinary examined/index-entry allowances before lifetime filtering, the second world can return different meters, cuts or continuations. A device never received those candidates, so server/device agreement also fails.

   The governing expiry behavior already excludes expired candidates from public metering and bounds their traversal separately; see [read.rs](/home/ccheever/projects/sb4-w10-page2/snapback4/crates/snapback4-core/src/engine/read.rs:364).

   **Recommended fix:** specify future-row pricing for scans, points, search, probes and PAGE2 discovery. Separate bounded physical traversal from public logical meters, keep future positions out of continuations, and define the physical-guard exhaustion outcome. Test both stores against the server with substantial unopened populations.

4. **A row-count advancement limit does not bound work or guarantee streamable commits (§4).**  
   `advance_openings(now, limit)` bounds entries, but the proposal gives no byte, allocation, event or accounting-work bound. Individually valid scheduled rows can collectively produce a boundary commit larger than the wire ceiling. Existing sync streams whole commits, so reducing the sync page size cannot rescue such a commit; a device can become permanently unable to advance its watermark.

   **Recommended fix:** give advancement explicit work and serialized-event budgets. Commit a bounded prefix and leave the remainder pending, with guaranteed progress for an individually admissible transition. Define how these budgets relate to the triggering request’s meter, and ensure publication failure rolls back events and pending-entry removal together. Verify backlog recovery and maximum-size boundary commits.

**Overall: NOT READY.** These findings concern the frozen designs, not the incomplete implementation.
