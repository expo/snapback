### 1. `recoverOutbox` / `withAbort` — expired waiter still rejects later (unhandled)

**Path:** `recoverOutbox` in `snapback2/packages/snapback2/src/client-outbox-recover.ts` wrapping `withAbort` from `client-wire.ts`.

The inner run is raced against the per-caller waiter. On timeout, `stop()` records the `E_TRANSPORT` refusal and aborts the waiter, so the **public** `recover()` result is correct. The inner run is not cancelled. After `host.online()` / `host.settled()` later resume, the next `check()` throws `stopped`. That rejection belongs to the raced-off promise, which nobody handles.

This codebase already treats that as a bug on drain (`void verdict.catch(() => undefined)` in `drainOutbox`). The new waiter does the same shape of work without that guard.

**Counterexample:** the attached “independent deadlines” sequence.

1. `recoverOutbox(host)` with `online` blocked on a gate.
2. Waiter expires at 10s; caller already has `{ refusal: E_TRANSPORT }`.
3. Shared `online` then completes (second caller still joined).
4. First invocation’s inner `check()` throws the stored timeout refusal on a detached promise → `unhandledrejection` / `node:test` unhandled-rejection failure.

Same sequence on a real client: first `outbox.recover()` times out during `goOnline`/`performResume`; resume later succeeds or fails; the expired invocation still throws at `check()` after `host.online()`. Ledger/shared work can be fine; the expired call still injects a late rejection.

### 2. `observeOutbox.getSnapshot` — takeover identity hides live work as `initial`

**Path:** `Client` identity `() => \`${authGeneration}:${operationFence}:${recoveryOwnership}\`` passed into both `recoverOutbox` and `observeOutbox` (`client.ts` `createOutboxApi(...)`); `observeOutbox.getSnapshot` in `client-outbox-observed.ts`; `takeover()` increments `recoveryOwnership` then aborts `recoveryScope`.

`getSnapshot` returns `initial` (`entries: []`, `status.reason: "grant-missing"`, `can` not ready) unless `slot.identity === identity()`. That fence is right for auth/fence cuts. `recoveryOwnership` is only bumped on writer takeover of the **same** partition. Takeover is therefore treated like account departure for the read model.

Refresh is not driven by `recoveryScope`. `takeover()` itself does not notify outbox/status observers. `performResume` notifies only if it actually starts a flight; it no-ops when `forcedOffline` is true.

**Counterexample:**

1. Follower has `observe` subscribed; snapshot shows the inbox-queued row (`getWork("inbox:…")` defined, `can` from live status).
2. This tab calls `offline()` (`forcedOffline = true`). Identity string is unchanged; work remains visible.
3. Writer tab closes; this tab `takeover()`: `recoveryOwnership += 1` so identity changes; `performResume` returns immediately because the tab is offline; no `outbox.notify()`.
4. `getSnapshot()` / `useOutbox()` / `useMutation().can` now return `initial` (empty work, grant-missing) while durable entries still exist. They stay there until some later unrelated notify.

Recover waiters should still fail takeover with `E_AUTH_SUPERSEDED` (captured identity + aborted scope already do that). The work index should not.

## Follow-up review

**READY**

The unhandled-rejection finding does not hold. `Promise.race` calls `.then(raceResolve, raceReject)` on **every** input, so the inner `run()` always has a rejection reaction. After the waiter wins, a later `check()` throw still goes to that reaction; an already-settled race capability is a no-op, not an unhandled rejection. That matches the independent-deadline test completing the shared gate after the first expiry under `node:test` unhandled-rejection detection.

The accepted identity split is in the current source: observe uses `${authGeneration}:${operationFence}`; recover uses `recoveryIdentity` with `recoveryOwnership`. Takeover still aborts `recoveryScope` and bumps ownership for waiters, without treating the same-account lock transfer as a read-model account cut.

`onlineScoped` now takes `operationAuthority(false)` and `performResume` still joins an active `resumeFlight`. That is the concurrent explicit-recovery path, not a weakening of `online()` / `settled()` / automatic recovery.

No remaining material recovery defect in this follow-up source.
