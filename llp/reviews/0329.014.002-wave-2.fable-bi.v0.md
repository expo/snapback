# Paper archetype: analytics / BI against LLP 0329.014.000 v0.1

**Respondent:** Claude Fable 5 · **Design under test:** `arch/w2/design-bi.md` (codex), fixed · **Target:** LLP 0329.014.000 v0.1 incl. §9.1 and §11 · **Prediction under test:** LLP 0329.014.002 #7.

Headline. Prediction 7 holds in *class* — the app ends at a boundary, and the kind that replaces what the language refuses is a declared, append-only, schema-listed **export stream** — but it draws the line in the wrong place with the wrong instrument. The line is not "maintained versus ad-hoc"; it is **declared before the data arrives versus asked after it arrived**. Every object the design calls a *definition* (cohort, funnel, retention curve, histogram metric, distinct count, privacy budget) is maintainable *at ingest* by one ordinary mutation running a bounded interpreter over definition rows — none of it is "schedule-built" — and what leaves is *history*: backfill, reattribution, and every ad-hoc scan. `G` is not the wrong instrument for analytical reads; it is the instrument that draws the line, and here it bites hardest on the **write** side (a 250-event batch under 20 cohorts examines 11,067 entries). And K2's `readable` is necessary but not sufficient: a *live* maintained aggregate over hidden rows discloses the timing of every hidden contribution — the leak the design's release epochs exist to stop and the spec's `disclosures[]` cannot name. Independently: the design's exact/protected split *is* K2's caller-fact/resource-fact dichotomy found by another family, and its trap 2 is `E_STRUCTURAL_COUNT` in prose. L1–L9 refer to §6.

### 2. Schema in v0

Authorization rows, not payloads, name the org and dataset (op 1's rule). Row scope and aggregate scope are *different grant tables* keyed by a declared scope column (`scopeKey`, e.g. region) — I6. Roles are int ranks (1 viewer · 2 analyst · 3 dataAdmin · 4 securityAdmin · 5 owner); `// L…` marks §6 deltas, not spec features.

```ts
import { table, id, text, int, bool, time, ref, interval, json, maintain, schedule, effect, viewer, principal, never, public } from 'backend'
const role      = (org, r) => (db.get(orgMembers.byOrgPrincipal, [org, viewer])?.role ?? 0) >= r
const member    = org => role(org, 1)
const orgOf     = dsId => db.get(datasets, dsId).orgId
const rowScope  = e => db.exists(rowGrants.byPrincipalDsScope, [viewer, e.datasetId, e.scopeKey])   // row-read scope
const aggScope  = r => db.exists(aggGrants.byPrincipalDsScope, [viewer, r.datasetId, r.scopeKey])   // aggregate scope: a different row

#### §5.6–5.8 Funnels, cohorts, retention

`advanceFunnel` (inside op 1): `get(funnelProgress.byKey, [f.id, subject, journey])`; if the event matches `steps[p.step + 1]` within `windowMs` of `enteredAt`, patch `step`; if it matches step 0 and the re-entry rule allows, insert a new journey (cap 8). Late events that precede the recorded entry re-derive from `scan(events.bySubjectTime, [subject], { range: window, take: 500 })` and refuse at `hasMore` — the one place per-subject event volume is a bound. The query is point reads: `for (step ≤ 12) for (cohortDay ≤ 90) db.get(funnelSteps, [f, day, step, scope])` — ex ≤ 1,081; step counts are monotone by construction because each row holds its max step. The conversion-time summary is a `metricHistogram` over a derived `elapsedBucket` dimension written by `advanceFunnel` — approximate, declared.

`createCohortVersion`: `require(base === cohort.headVersion)`, insert version, CAS head; the *semantic-conflict* merge is the report merge (§5.10).   db.update(reports, r.id, x => ({ ...x, headVersion: x.headVersion + 1 })); db.insert(audit, { ... }) })
// examined ≤ 3 + 16; steps ≤ 64×40 + maxBytes-bounded traversal (L8b); prediction closed: reports[id], reportVersions[id, head] are held by the editor's subscription;
// on conflict the client shows base/current/proposed from rows it already holds (design's "fork" path). Offline edits: queued; a stale base is `rejected`, never merged.
```

`loadDashboard` reads `dashboardVersions[id, v]`, then per tile the pinned `reportVersions` row and its series (`exactSeries` logic inlined, ≤ 400 gets) or retention triangle (≤ 1,431): 13 × 402 + 2 × 1,432 + 1 = **8,091** — under `G` by 21%, and one more retention tile refuses. Cross-tile consistency is the transaction; the "late response cannot replace a newer run" rule is the subscription's identity, not code.

#### §5.13–5.14 Erasure and system

`eraseSubject`: for each identity key (≤ 1,000 by `cap`) insert a `tombstones` row (`unique(requestId)` makes concurrent requests coalesce) and one `purgeManifests` row; from this commit every read rule's `notErased` probe hides the subject — I20 without a fence. `purgeChunk` (`every: '10s'`, system): `scan(purgeManifests.byState, [0], { take: 10 })`, per manifest `scan(events.bySubjectTime, [subject], { take: 100 })` → delete rows and witnesses (maintained aggregates decrement in the same commit), advance `cursor`, flip state at exhaustion — bounded per run, unbounded in total, state on the manifest row: the `job` pattern needs no kind. It needs L8c (system reads unfiltered). `sealSnapshot` dissolves: the commit version is the snapshot, watermarks are `sources.watermarkAt`, and columnar partitions, sketches, and funnel indexes are the replica's accelerators — which the design itself calls "never authoritative facts."

### 6. Language delta

Ranked by operations unblocked and by how wrong the answer is without it.

1. **L1 — `exportStream`: the declared boundary kind.** *What:* 8 of 9 refusals are questions about history at a volume no `take` covers; effects cannot read tables, so today there is no admitted route at all. *Smallest addition:* a schema kind over **append-only** tables only — `exportStream(table, { to: <service principal>, columns, with, order: <sequence column>, disclosure: public(reason) })` — that the engine ships in `seq` order, resumable by `(generation, seq)`, at-least-once, and lists in the receipt as a disclosure of named columns to a named principal. *What makes it a kind and not a hatch:* it is static (the receipt names every column that leaves), one-directional (nothing reads *through* it — no query, rule, or effect can ask the replica a question), its consumer is a principal whose only read is the stream, and results re-enter solely as rows written by named mutations under their own rules with unique idempotency keys (`publishRelease`, `publishProjectionChunk`). A hatch is any of: `db.raw`, an effect that scans a table, a "server-only query" whose result is returned to a client. *General* (any OLAP, search, or ML consumer). Amends §1 (kinds), §2, §5 `disclosures[]`, §9.
2. **L2 — disclosure cadence and floor on `readable`.** *What:* `readable` discloses an exact, *live* number; over hidden rows its first derivative is a per-subject event log. *Smallest addition:* `readable: rule, disclose: { cadence: 'epoch' | 'live', minGroup: N }` — with `cadence: 'epoch'` the live row is readable only by system, and a compiler-generated schedule copies it to a release row on the declared period; `minGroup` returns `null` below N (deterministic suppression, labeled weaker than the design's noisy threshold). `disclosures[]` records both. *General* (leaderboards, occupancy, follower counts over blocked users). Amends §2, §5, §9 `E_DISCLOSURE`.
3. **L3 — `int({ sequence: 'groupCol' })`.** *What:* the log needs a dense monotone order per dataset for the EAV key, the stream cursor, and the design's `ingest_sequence`; `newId()` is unordered and `commitTime` ties within a batch. *Smallest addition:* an engine-assigned column at commit, provisional locally like `commitTime`. *General.* Amends §2, §4.3.
4. **L4 — `text({ hashed: true })`.** *What:* identity keys must be stored as keyed digests under a key no principal can read; there is no hash in the subset and the key row is invisible. *Smallest addition:* the engine digests the column on write and on point-read keys; equality only; no `scan` by prefix. *General* (emails, tokens, PII lookups). Amends §2, §4.2.
5. **L5 — indexes over maintained rows.** *What:* "top groups" over a maintained aggregate has no admitted route unless the group domain is `cap`ped. *Smallest addition:* `maintain.count(…).index('byValue', ['datasetId', 'day', 'value'])`, maintained in the same commit, readable under the aggregate's rule. *General* (the game archetype's leaderboard is the same shape). Amends §2, §4.4.
6. **L6 — sum-cap constraint.** *What:* the privacy budget is "sum, then refuse" as a `require`; a second mutation that inserts a ledger row can overspend. *Smallest addition:* `cap({ by: [...], sum: 'epsMicro', max: ref(privacyPolicies, 'epsCapMicro') })` evaluated at every write. *General* (quotas, rate limits, credit lines). Amends §2.
7. **L7 — schedule `at` live from a row, composite key** (wave-1 auction/booking #4/#16). Cron with timezone and DST needs no operator: `tzRules` rows plus a program-computed `nextAt`. *General.* Amends §7.
8. **L8 — clarifications.** (a) effects read through named queries as a service principal, never tables; (b) `json` is traversable in programs with steps bounded by `maxBytes` — the bounded interpreter over definition rows depends on it; (c) `principal.kind === 'system'` reads are unfiltered where the rule says so (purge, epoch flip); (d) `maintain.max` is named in §4.4 and absent from §2. Amends §2, §4, §7.
9. **L9 — the third rewrite in `E_BOUND`/`E_UNBOUND_SCAN`.** *What:* the diagnostic pastes `maintain`, which answers "count this from now on" to an agent asking "count this over history" — the most likely way an agent lands at a 10,000-row page labeled a result. *Smallest addition:* "declare it (maintain, forward) **or** export it (stream, history)", with the `exportStream` paste. Amends §9.

Not needed here, worth recording: `tree`, `exclusion`, `channel`, `readTime` (every "now" in this app is a row: watermark, epoch, `nextAt`). Calendar arithmetic (wave-1 #13) is *data*, not a construct.

### 8. Where the design is wrong

1. **Exact mode is trap 2 by construction, and the design never labels the population.** Promise 7 defines exact mode as "aggregates only rows the analyst may inspect"; promise 11 re-authorizes every viewer of a shared dashboard. So a full-scope author shares an exact dashboard and a one-region viewer sees regional numbers under company-wide titles — the design's own trap-2 observation, produced by two of its promises composed. Nothing in `QueryRun` records the *population* (the grant set) the exact number summarizes; `access-policy version` in promise 15 names the policy, not the caller's slice. *Confirming observation:* author (all regions) saves an exact DAU tile; viewer (EU only) opens it; the tile shows EU DAU titled "DAU" with no scope label and a matching result digest. v0's caller-scoped route returns `population` because the sum is visibly over the grant list.
2. **The privacy budget cannot sustain the design's own dashboard count, and the missing middle mode is the one the language's boundary creates.** ε = 4 over a 365-day horizon per audience, no per-release ε stated; at any plausible per-release cost (≥ 0.1) an audience gets ~40 distinct protected charts per year against §6's 2 M reports and 300 k dashboards, sticky reuse notwithstanding (it dedupes identical queries, not distinct ones). Meanwhile the design offers nothing between "exact over my rows" and "noisy over everything" because trap 1 (differencing) assumes *arbitrary filters*. Inside the v0 boundary the cell set is fixed in advance, so differencing is limited to declared cells and complements; an exact, epoch-released, floor-suppressed disclosure (L2) is defensible there in a way it is not over ad-hoc filters. *Confirming observation:* compute the budget arithmetic from §4's defaults and §6's counts; then attempt the "excluding Alice" query of trap 1 against a declared cube — it has no cell to ask.
3. **Promise 15 (reproducibility) contradicts invariants 13–14 (current grants only).** A result records the policy version "needed to reproduce it," but authorization is always evaluated under current grants and revoked authority is never preserved. After a revocation the recorded result is reproducible only under the revoked policy — forbidden — or not reproducible — falsifying the promise. The design does not say which. *Confirming observation:* revoke EU from an author; re-run the recorded `QueryRun` under its recorded policy version; either the digest matches (revoked authority reused) or it does not (promise 15 false for that run). In v0 there is no "reproduce under an old policy": result rows are re-authorized on every read, so the promise must be restated as "the definition and cutoff are recorded; the population is whatever current grants admit."
