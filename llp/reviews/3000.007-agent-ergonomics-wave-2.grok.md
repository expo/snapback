## Question answers

### 1. §20.5 upsert insert prediction (F)

A device **cannot** predict `NOT_FOUND` for an unheld target: that path is still `E_PREDICT` / queue-without-a-row.

It **can** predict an inserted `pending` row the server will not produce:

- **Secondary unique (new).** Proven miss → `insert_upsert` → local unique checks see only held rows → pending insert; server hits a hidden sibling → `E_RULE`.
- **Left group (bug).** `tx.retained_group` is always false on `Predicting`, so a `delivered-history` group marked Left is treated as a complete held group whenever `decided_true`.
- **Caps / `after insert`.** Same shape as the named §15 residuals, now on a predicting insert arm.

Worlds:

| World | Behavior |
|---|---|
| Hidden row, update admits, key unpinned | Queue, no row; alice/carol pair matches on the full helper, both stores. |
| Hidden row, key pins readability | Impossible under (b); not tested against absent. |
| Horizon | No insert prediction (`rules.rs:32`). |
| Key does not decide readability (non-viewer columns, extra conjuncts, foreign `exists`) | Static `uniform` fails, or evaluate returns false / `beyond_horizon`. Membership without a witness does not predict. |
| Left group | Intended `false` at `write_target.rs:62`; dead on predict. |
| Pending local delete | Untested; ordered outbox likely OK. |
| Defaults | Same `with_defaults` on both hosts. |
| Caps | Physical local count; hidden siblings undercount. |
| Secondary unique | Predicts insert; server `E_RULE`. |

### 2. §20.6 service disjuncts (F)

A service disjunct does **not** change a non-service viewer’s partition, snapshot, stream, residency facts, or admission. Stripping is confined to audience inference/validation; the live read rule still admits the service on `/q` (`lifecycle.rs:22–45`). An ordinary principal cannot mint `service:…`. Any extra disjunct that is not a whole service equality still `E_SYNC`.

### 3. §20.3 Following (C)

Header cursor is validated against the first lane’s table/index/order/suffix before discovery; other lanes only rewrite the table field of an already-valid token. Foreign tokens fail on empty lanes. The hybrid recipe keeps ordering fields and `eventId` consistent; merge dedups row ids. `cap N` is enforced on insert/seed/adopt; devices use the same constraint code. `N_SPARSE_FILTER` is not emitted for scoped/seek/prefix-pinned scans.

Gap: no test that a translated cursor over a non-uniform lane cannot sit past a hidden row. The paved Following tables do not have hidden rows in the scanned prefixes.

### 4. §20.4 web exit flush (E)

Keepalive sends only outbox entries already in the committed map, after `save` with `durability: "strict"`. Mutate does not resolve until that save. Failed save discards the in-memory device; pagehide sees nothing to send; the next call reopens from IndexedDB. Same mutation id; `seq` order; per-client headers; module-wide 64 KiB. Node tests cover this; the Chromium witness did not run in the sandbox.

### 5. §20.1 / §20.2 (A1, A2)

Aliases, nearest-3, `Write` replay typing, `Client.signOut`, init merge (conflict → no writes), Metro wasm `require()`, and independent effect/schedule holds match the spec. Schedule hold is persisted and skipped on release; effect hold is process-local and durable in the outbox.

### 6. Diagnostics (B1, B2)

Named shape-after-`where`, one error per failed binding, enum widening (including non-ASCII and over-long variants), syntax rewrites, always-on never-predict summary, and `predicts:` are sound. `N_MAINTAIN_SYNCED` / `E_STRUCTURAL_FANOUT` / `N_WIDE_MERGE` wording is not a false runtime claim. **False claim:** writes card still says a missing upsert never predicts (`writes.rs:15–17`).

### 7. §20.8 signing (S)

Signing, strict verify, Developer ID authority+team, and notary status all refuse before `npm pack`. Installed bytes are digest-checked against the signed artifact. No path publishes unsigned or post-sign-mutated darwin bytes.

### 8. Tests

Red-before/green-after is recorded per lane. Positive/negative coverage is good for service grants, sparse filter, holds, init merge, signing refusals, and the five public/owner/horizon/unpinned/online upsert cases on **both** device stores. Concrete holes are listed with the findings.

## Findings

### 1 — High — `snapback4/crates/snapback4-device/src/device.rs:152–178` (used from `write_target.rs:62`)

**Scenario.** Table `items` with `read <- .owner = viewer`, `sync`, `retain delivered-history`, unique `(owner, k)`. Viewer held the group; the server then sent a `scope` tombstone (`history.rs:35`). Device still has retained rows; `GROUPS` marks the group `Left`. Viewer `upsert items[viewer, k_new]`.

- Required: `retained_group` is true → queue without a row (§20.5 (a); journal: “retained groups cannot supply whole-group absence”).
- Observed: `Predicting` does not implement `retained_group` (default `Ok(false)`). Queries wrap `history::Reading`; predict does not (`device.rs:563` vs `594`; `predictions.rs:52`). If `decided_true`, the device plants a pending insert for a group it no longer holds. A post-leave row written by someone else at a key that is only *statically* decided (e.g. `exists members[.room, viewer] or .author = viewer` with `author` pinned, membership retained) is an update/`NOT_FOUND` on the server and an insert locally.

Both stores share `Predicting`; SQLite vs memory does not save this.

**Smallest fix.** Implement `retained_group` on `Predicting` by loading `history::GROUPS` the same way `Reading` does (or wrap the predictor in `Reading`). Add a both-store test: leave the group, upsert a never-held key, `predictable == false`, no pending row; pair with a still-held group that does predict.

### 2 — High — `snapback4/crates/snapback4-core/src/engine/write.rs:107–108` + `299–310`

**Scenario.**

```text
table likes:
  postId: text <=30
  principal: principal
  handle: text <=30
  unique byPostPrincipal: postId, principal
  unique byHandle: handle
  read <- .principal = viewer
  insert <- .principal = viewer
  update <- .principal = viewer
  sync
mutation vote(postId: text <=30, handle: text <=30):
  upsert likes[postId, viewer] { handle }
```

Alice holds `handle: "cool"`. Bob, with an empty likes group, `vote("p2", "cool")` offline.

- Required: §8.7 (e) / §20.5 — do not predict an insert the server would not produce. Server unique collision with a hidden sibling is generic `E_RULE` (§8.7 (f)).
- Observed: absence of `(p2, bob)` is provable → insert arm runs → local `byHandle` lookup misses Alice → pending row. Server `E_RULE`. The device predicted a row the server will not commit.

This channel did not exist while every miss queued without a row; §20.5 reopened the insert arm without proving other unique indexes.

**Smallest fix.** On the device insert arm, if any unique index has a column not pinned by the write key (or not implied by the deciding read fields), treat the miss as unproven and `write_miss`. Regression: hidden alice/carol handles, complete observation, both stores, `predictable == false`; a collision on the write key itself still predicts when (a)+(b) hold.

### 3 — Medium — `snapback4/crates/snapback4-lang/src/guide/writes.rs:15–17`

**Scenario.** Builder runs `snapback4 guide writes` after this landing, copies `upsert likes[postId, viewer]`.

- Required: cards whose recipes use `upsert` say how they predict (§20.1); §20.5 is first-like insert when absence is provable.
- Observed: “predict only updates of rows the device holds; a missing row queues without a prediction.” Lines 70–72 and the README state the opposite. The language-card `react` comment is fine (that table has `last 500`).

**Smallest fix.** Delete or rewrite lines 15–17 so they match lines 70–72 / `prediction.rs:92–96`.

### 4 — Medium — caps / `after insert` on the new insert arm (`write.rs:339–371`, `400–424`)

**Scenario.** Public-enough key so (a)+(b) hold; hidden physical rows in the same cap group, or an `after insert` probe whose witness is not on the device.

- Required: do not predict a success the server refuses (Q1). §15 listed these as disclosure residuals, not as license to predict the insert.
- Observed: local cap count / exists probe uses the device store only.

**Smallest fix.** Same gate as finding 2: if the insert arm can fail on a population the device does not fully hold (any table cap; any `after insert` probe), do not predict. Keep the server words as they are.

### 5 — Low — `snapback4/crates/snapback4-core/src/engine/admission.rs:208`

Two `for x in …` loops with the same binding now share site `for/{binding}` (the ordinal map was removed). `E_STRUCTURAL_FANOUT` can point at the first loop and rewrite the wrong page.

**Smallest fix.** Restore a per-loop ordinal (or use the IR scan `site`) in `Problem.site`.
