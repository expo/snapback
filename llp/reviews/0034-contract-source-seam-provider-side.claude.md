## Overall Assessment

This is a well-structured, honestly-scoped provider-side companion that does the most important thing right: it treats the work as a delta against a real, shipping subsystem rather than a greenfield design, and it maps each Exact 0284 §5 "Done means" item to a deliverable. The §1 obligations table is exactly the right spine, the non-goals correctly defer to owner docs, and most code citations are accurate to the line (a real strength given the 0032 review bar). The five-deliverable split is coherent and nothing in Exact 0284 §5 is left wholly unassigned.

But the document oversells how much of D1 is "wiring, not server work," and three of its central mechanisms rest on mischaracterizations of the shipped code: the connection axis needs a heartbeat that does not exist, D2 says durable deltas are "unnumbered" when they already carry a shared version, and D2's resume/version story does not match how `resume_live` actually works. These are fixable without redesign, but they are load-bearing enough that the deliverables can't be built from the current text. Revise-and-stay-Draft.

## Strengths

- **The honest starting position is real, not rhetorical.** `subscribe_live` genuinely returns `{subscription_id, snapshot, permission_epochs}` in one operation (`src/local.rs:596-600`), so D5's atomicity check has a true foundation. The idempotent inspect-first ephemeral path is real: `ensure_collections` inspects without clearing and returns preserved counts (`src/ephemeral.rs:716-770`), and `replace_collections` no-ops on identical definitions (`src/ephemeral.rs:706-708`). D4's mount-lifecycle tier is buildable on these.
- **The overflow-to-resync primitive D1 leans on exists and is well-built.** The per-connection outbox has *separate* bounded `durable` and `resync` lanes (`src/ephemeral.rs:517-518`), and `MAX_OUTBOX_BACKLOG` (`:191`) collapses the whole queue to a single sticky resync signal on overflow (`:558-563`). D1 §2.3's "never a prime race, re-snapshot on overflow" is grounded.
- **The first-proof deletion target is accurate.** All Aboard really does hand-roll the bridge: `client.liveQuery('liveTrainStatus', …)` (`demos/all-aboard/surfaces/contract/main.ts:118`) feeding a `setInterval` poll (`:125-127`) into `./store.mjs` (`:21`). Deleting it is a meaningful proof.
- **The manifest-extended-in-place discipline (non-goal 5) matches 0284's anti-parallel-path stance,** and the migration cross-check (D3: "codegen fails if old and new fields disagree") is the right enforcement shape. Codegen's current `subscription` emission is exactly as claimed (`demos/_kit/codegen.mjs:149,183`).

## Concerns

**[high] The connection axis (§2.2) and D5 check 3 require a heartbeat/keepalive that does not exist, contradicting "not a new server transport."** The live stream loop ticks every 25ms to drain the outbox but sends *nothing* on an idle-but-healthy socket, and it explicitly no-ops incoming Ping/Pong (`src/server.rs:625-660`, esp. `:641 Some(Ok(Message::Ping(_))) | Some(Ok(Message::Pong(_))) => {}`). There is no server-originated liveness signal and no Pong response, so a browser cannot distinguish `live` from a dead-but-open socket until OS TCP timeout (minutes). D1 §2.2 defines `live` as "heartbeat within budget" and `stale` as "heartbeat overdue," and the freshness budget as "heartbeat interval × k" — all referencing a mechanism that must be *built server-side*. This undercuts §2's "D1 is therefore kit/adapter wiring … not a new server transport" and hides a dependency of D5 check 3 (`live → stale → disconnected`). *What would resolve it:* add an explicit D0 precondition — a server-sent keepalive frame (or real Ping/Pong handling) — name it as server work, and define the freshness budget concretely as `(heartbeatIntervalMs, k, pollCadenceMs)` with defaults.

**[high] D2's version story is built on a false premise, and OQ3 is a blocker, not an open question.** "today updates are unnumbered" (§3) is wrong: every durable delta already carries `version: query.output.version` (`src/local.rs:1261`), which is the *global durable commit version* (`src/storage.rs:481-482` → `current_version()` reading `_snapback_version`, `:204-210`), and the snapshot carries the same field — so one coherent, monotonic version already spans snapshot and deltas. D2 nonetheless commits to inventing "a per-subscription monotonic delta sequence," which (a) duplicates the existing global version and (b) is precisely what OQ3 flags as unresolved. That is an internal contradiction: the deliverable commits to a design its own open question says is unsettled. The genuine reconciliation problem OQ3 *should* name is that ephemeral uses a compound `(scopeEpoch, entryVersion)` (`src/ephemeral.rs`, LLP 0013 §Stored entry shape) while the receipt wants a single `snapshotVersion: number` — OQ3 mentions only `schemaVersion`/`bundleHash` and misses this. *What would resolve it:* settle OQ3 into D2 before building — default to reusing the global commit version for durable receipts/resume, specify the ephemeral compound→scalar mapping, and drop the per-subscription sequence unless a concrete need survives.

**[high] Several normative receipt keys are structurally unknowable to the provider, but D2 says emit them "verbatim."** Exact 0284 §2.6's `MutationReceipt` includes `optimisticWaveId` ("the runtime flush that applied it"), `actionInvocationId` (LLP 0231 action log), `rootId` (mount/session), and `bindingIds` — all Exact-runtime concepts Snapback cannot originate. D2 maps only the provider-native keys (`mutationId`, `affectedTables`, `snapshotVersion`, `scope`, transport) yet frames the obligation as "emit both receipt families with §2.6's keys verbatim." Since LLP 0278's *deterministic* loop-closure depends on these join keys, an under-defined handoff means the join can't close. *What would resolve it:* split the receipt into a provider-populated core and an adapter-stitched runtime-join set (a small table in D2), and specify the inbound-correlation mechanism — does the Exact adapter pass `optimisticWaveId`/`actionInvocationId`/`rootId` *into* `mutate()` for the provider to echo, or stitch them onto the response? This is the same question as 0284 OQ2 / 0278 OQ2; D2 should be its home, not a third pointer.

**[medium] The document's proofs cite a demo that isn't in the tree.** "graffiti" exists only in `diaries/0006-graffiti-board.diary.md` and three LLP docs — not in `demos/` (which is `_kit`, `all-aboard`, `cursors-web`, `todo`, `todo-v2`), and `git ls-files demos/graffiti` is empty. So D5 check 5 ("the graffiti suite's cursor-flood check, promoted") and the summary's "demo acceptance (todo, todo-v2, graffiti)" reference code not present. The shipped presence demo is `cursors-web`, which does use the socket ephemeral lane (`demos/cursors-web/tests/acceptance/browser.mjs:227`, `demo.snapback.json` `ephemeralWebSocketPublish`). *What would resolve it:* re-ground the presence proofs on `cursors-web`; if graffiti is meant to return, mark it off-tree/planned rather than shipped.

**[medium] D3 mischaracterizes the migration's starting point.** There is no `boardCursors.query.ts` + `boardCursorsPublish.mutation.ts` pair: `renderContractModules` emits Contract descriptors *only for durable functions* (`demos/_kit/codegen.mjs:1059-1093`), and ephemeral collections project as a distinct `ephemeralCollectionReference` in `api.mjs`/`api.d.ts` (`:982-998`, `:1021-1036`) — never as query/mutation Contract modules. Even diary 0006 shows graffiti's presence codegen'd into `ephemeral.manifest.json`, not query/mutation modules. So D3 is "create the `*.ephemeral.ts` Contract descriptor from the existing `ephemeralCollectionReference`," not "migrate an existing query+mutation pair." *What would resolve it:* restate D3's baseline against `ephemeralCollectionReference`; note this is *simpler* (no dual-emit/cross-check needed for the ephemeral kind, since nothing Contract-facing exists to keep in sync).

**[medium] D4's gate story conflates an existing auth policy with a not-yet-built environment gate, and doesn't confront the destructive-reset-on-boot it forbids.** The system write routes are *already* behind `AdminWrite` (`src/server.rs:165-167`, LLP 0031) but are open on loopback without a token (`demos/_kit/client.mjs:68-69` "On loopback with no admin token these are open") — the demo boot works precisely because the gate is a no-op locally. Separately, All Aboard's boot calls a *destructive* `client.reset()` on every page load (`main.ts:113`, POSTing `/_snapback/api/app/reset`), which is exactly the "destructive reset in mount lifecycle" D4 says must never happen — and profile-gating to dev/demo/test does *not* fix the multi-window clobber (0284 §2.7 / LLP 0275 C4: a second window still resets the first). *What would resolve it:* (a) distinguish the existing `AdminWrite` auth policy from a new positive environment/profile capability; (b) require concrete boot changes — drop `reset()` from the mount path, replace with inspect-first provision + seed-if-empty; (c) decide whether loopback-open stays or is replaced by the explicit profile flag.

**[medium] D1 §2.3's resume claim doesn't match `resume_live`.** `LiveResumeInput` carries `{subscription_id, connection_id, auth, recorded_permission_epochs}` — no version field (`src/local.rs:200-211`). Resume re-points the stream and returns `mode: "retained"` or `mode: "resnapshot"` with `reason: "permission_epoch_changed"`, driven by *permission epochs*, with no version-based delta replay (`:650-690`). So "Reconnect resumes via `resume_live` with the last-seen versions" is inaccurate, and it omits the permission-epoch dimension entirely — which also interacts with D2's version story (there is no `lastDeltaVersion`-driven replay to reconcile). *What would resolve it:* rewrite D1 §2.3 around the actual retain/resnapshot-by-permission-epoch semantics, and state where (if anywhere) a delta version participates in resume.

**[medium] OQ1 (poke vs deltas) is mis-framed against the shipped transport.** The server already re-runs the query on mutation and pushes *full replacement rows* over the socket (`notify_live_subscriptions` → `invoke_query_with_dependencies` → `LiveUpdate{kind:"live_replace", rows}`, `src/local.rs:1247-1262`). So neither OQ1 option describes reality: a client-side "poke → re-fetch" would *add* a round trip the current code avoids, i.e. a regression, not the "simplest" option. *What would resolve it:* reframe OQ1 as "keep the shipped full-row-replace push vs. add row-level diffs (bandwidth only)"; the poke is off the table.

**[medium] The connection axis is defined only against the always-on local server; its Cloudflare (LLP 0014) semantics are unexamined.** LLP 0013 §Backend adapters says a Durable Object under WebSocket hibernation must force resnapshot when in-memory room state is uncertain. A hibernating DO has no 25ms drain loop and no heartbeat cadence, so `live`/`stale` as defined don't map. OQ2 asks only about SSE-vs-WS and misses that the connection axis's meaning must be defined for a hibernating hosted target — the stated production direction. *What would resolve it:* add an OQ (or fold into OQ2) defining `live/stale/disconnected` under DO hibernation and whether hibernation always surfaces as `stale`/resync.

**[low] Multi-tab / key-mode identity is under-defined.** D3 says `sourceClientId` = publishing connection and `self` = binding's own connection id. That is correct only for connection-keyed collections; LLP 0013's session- and user-keyed modes share a lease across multiple connections/tabs, making a connection id ambiguous as `sourceClientId` and as the `self` test. *What would resolve it:* define `self`/`sourceClientId` per key mode.

**[low] 0284 §5 completeness has two under-drawn cross-repo seams (nothing double-assigned).** Item 3 correctly notes the Exact-adapter dependency, but item 6 (degraded example) is mapped to "need D2" while its compiler-diagnostic half is Exact-side (0284 §2.8) and its loop-closure half is LLP 0278 — those out-of-repo dependencies aren't acknowledged. Also, 0284's migration table maps `subscription:'change-only'`, but Snapback codegen never emits that value (only `'initial-snapshot'|'none'`, `demos/_kit/codegen.mjs:149,183`). And `coalesced_updates` is at `src/ephemeral.rs:1278`, not `:1277`. *What would resolve it:* note item 6's Exact/0278 halves; drop the `change-only` row or mark it N/A for this provider.

## Suggestions

- Add a **D0 precondition**: minimal heartbeat/keepalive as explicit server work, with the freshness budget defined numerically. Everything in the connection axis and D5 check 3 hangs off it.
- **Collapse to one version**: adopt the existing global commit version as the durable receipt `snapshotVersion`/`lastDeltaVersion`, specify the ephemeral `(scopeEpoch, entryVersion)`→scalar mapping, and delete the per-subscription sequence. This turns OQ3 from a blocker into a decision.
- **Give receipts a two-column ownership table** in D2 (provider-populated vs adapter-stitched) and pin the inbound-correlation convention; make D2 the single home for 0284 OQ2 / 0278 OQ2.
- **Rewrite D4 as three concrete All Aboard boot edits** (remove `reset()` from mount; inspect-first provision; seed-if-empty) plus the environment/profile capability definition — and note the first-proof (deleting the poll pump) is entangled with this boot change, so sequence them together.
- **Promote OQ6 to a stated fact**: the code already answers it — `resume_live` operates only on live-query `self.subscriptions`; ephemeral has no resume path, so ephemeral reconnect always re-snapshots through the resync lane. Name it, don't ask it.
- Restate LLP 0013's **durable-over-ephemeral scheduling priority** as an invariant D1's single-socket merge must preserve, and specify/verify the drain order in `drain_outbox`.

## Open Questions

1. Heartbeat ownership and shape: server-sent app frame vs. protocol Ping/Pong, interval, and `k`?
2. The one true version: is the global commit version sufficient for durable receipts *and* resume, and what is the exact ephemeral compound→`snapshotVersion` mapping?
3. Receipt population handoff: which normative keys does the provider originate vs. echo vs. leave for the adapter — and by what inbound-correlation mechanism? (Pick one home for 0284 OQ2 / 0278 OQ2.)
4. Does merging durable + ephemeral onto one socket preserve LLP 0013's durable-priority scheduling, and what is the concrete drain order under a cursor flood?
5. Connection-axis semantics under Cloudflare DO hibernation.
6. `self`/`sourceClientId` semantics for session- and user-keyed collections with multiple connections.

## Recommended Next Step

**Revise-and-stay-Draft.** The deliverable frame is sound and the code grounding is largely accurate, so this is not a redesign. But three items block building from the current text: the missing heartbeat behind the connection axis (concern 1), the version-story contradiction / OQ3 (concern 2), and the receipt population boundary (concern 3). Fold those in, plus the grounding corrections (graffiti→cursors-web, D3's true baseline, D4's gate/reset reality, and the resume/OQ1 accuracy fixes).
