1. **High — §§2.1a, 2.3: suppressing owned-event writes also suppresses dependent aggregate updates during prediction.**

   Owned events can be the source of an application-maintained aggregate. This is already exercised by [the adoption tests](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4/tests/timeline_adoption.rs:69). Such an aggregate can inherit full public sync from the owned table.

   **Concrete probe:** add `view totals: count followingPosts by .actorId`, with inherited sync. Horizon posts. In one mutation, read the caller’s total, insert an ordinary original, then require that the total increased by one.

   On the server, inserting the owned event invokes maintenance and increments the total. Following revision 10 literally, prediction writes the source column and inbox copy but skips the owned-event insertion. Maintenance therefore never runs. The aggregate read remains known, so the device can issue a definitive local refusal for a mutation the server accepts. The relevant connection is [row-change maintenance](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/write.rs:617) and [device aggregate application](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/maintains.rs:16).

   Merely reconstructing temporary event rows is insufficient generally: an unrepost’s ID-only column lacks the original’s `authorId` when that original is unheld, but an aggregate may group by that field.

   **Smallest safe change:** make transitions affecting a non-fully-synced event kind nonpredicting when that owned table has a synced dependent aggregate; enforce this at runtime and report it in `check`. Preserving prediction instead requires an explicit contribution-delta design with enough captured event metadata.

2. **Medium — §2.1a, event-column definition and activation: the column must belong to a declaration, not just a source table.**

   Shared source tables are already admitted. The engine deliberately executes every matching timeline, and an existing test has two Following declarations over the same activity and follows. See [transition dispatch](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/timeline.rs:58).

   **Concrete probe:** two declarations share reposts. One repost creates event E in the first owned table and F in the second. Horizon reposts, acquire that source, then unrepost offline. A single event-ID column retains only E or F; it cannot supply both declarations’ correct tombstones. Shared posts with different originals filters likewise require different live-event flags.

   **Smallest change:** specify one hidden slot per **timeline declaration and source role**, with each transition and activation fill addressing its own slot. Removing one declaration must leave the others’ slots intact.

The remaining mechanism is implementable:

- **Same-row writes:** the current hook runs after the source has been stored and logged, so stamping requires restructuring that path. Prepare the column before the existing source write/accounting; retain the old image for removal and unrepost. This can avoid an additional source update and its write charge. Calling ordinary `update` from the existing hook would not satisfy that cost model. See [insert ordering](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/write.rs:87).
- **Activation:** filling from existing `byActorPost` entries preserves minted identities without reconstructing history. The specified atomic fill and forced reacquisition are sufficient. The implementation must exclude this change from literal-default image retention, which otherwise can preserve acquisition across a generation change.
- **Prediction:** apart from dependent aggregates, the generated Following path needs no partial owned-event rows. Insertion already constructs the event needed for its own inbox copy; removal needs the original ID; unrepost needs the stored event ID and source actor. Application reads of omitted events are explicitly withheld.
- **Cost:** folding the column into the source image adds a Boolean or ID plus encoding overhead to every delivered source image, without requiring another row write or event index. Server-owned event writes remain. Keeping the public log also means discarded partial-event entries can still consume live-stream bytes; smaller device storage does not itself establish a live-bandwidth reduction.
