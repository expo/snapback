# Review: LLP 3000.038

**Verdict: NOT READY**

## Findings

1. **High — §3 vs `lazy_merge` / `merge_lazy` single-index assumption.** `lazy_merge` requires all lanes same table, same index, same prefix length, same order (`rules.rs:429-444`). `merge_lazy` derives suffix, `merge_key`, and cursor descriptor from the first lane's index only (`word_merge.rs:53-68,137-140`), and validates/decodes against `first.table/index` (`word_merge.rs:33-44,70-81,1375-1377` in `read.rs`). A branch merge with different indexes per lane is not lazy-eligible today and has no per-lane suffix/key path. **Change:** specify the engine change normatively: new branch-merge eligibility (same table, each lane uniform, identical suffix descriptor, id-terminated, same direction), per-lane prefix + shared-suffix resume, per-lane `merge_key`; add an acceptance that a two-index merge is lazy-eligible.

2. **High — §5 version-4 token vs `cursor.rs` + `PagePosition`.** Current wire is `Tagged = (u8,String,String,Order,suffix,values)` (`cursor.rs:67-93`), versions 1–3 only (`cursor.rs:95-123`), `PagePosition{table,index,order,prefix_len,prefix,merge,…}` (`runner.rs:61-77`), merge record uses first index/prefix (`word_merge.rs:251-257`), encode via `CursorPosition` (`read.rs:1326`). `[4,table,"$or:…",order,suffix,values,scope]` is a new arity/shape, breaks the canonical re-encode check (`cursor.rs:119`), and has nowhere to store the branch set in `PagePosition`. Old-cursor claim is also wrong: descriptor mismatch maps to `E_INPUT` (`cursor.rs:59-61` → `read.rs:629`, `word_merge.rs:43-44,76-78`; `E_CURSOR_INDEX` is only `check_variant`, `cursor.rs:42-44`), not `E_CURSOR_INDEX`. **Change:** define v4 encoding/decoding, `PagePosition` extension, descriptor check (table + branch set + order + typed suffix), scope/generation handling for prefix-less merge cursors, token-size bound for 8 synthesized index names, and correct old→new (`Descriptor`/`E_INPUT`) vs variant error codes.

3. **High — §2 completeness: false-uniform and grant-false lanes have no code path.** `scan_consumed` latches `non_uniform` for non-uniform, non-admitted scans (`read.rs:934-936`), takes the grant path only when `!visibility.uniform && !device` (`read.rs:923-933`), and `grant_verdict` admits only when uncapped (`read.rs:203-212`). A grant lane over whole `W` is non-uniform by `scan_visibility`, so "returns no rows and is decided (does not mark non-uniform)" (§3) requires a new special case that is not specified. Case-1 "decided by pins" relies on `rule_true` (`rules.rs:523-555`), including Id-vs-text typing (cf. OPEN V1) — not stated. **Change:** define a decided-lane predicate (uniform or grant-covered), state where the `non_uniform` latch is suppressed, how `N_NEVER_COMPLETE` identifies `grant:true` lanes (`bind/mod.rs:685-764` iterates `ir::scans`, including merge lanes), and the binder type check for `viewer` pins.

4. **High — §2.1/§5 shared-position proof is incomplete.** "Equal positions are the same row" needs: identical suffix descriptor across lanes, id-terminated, same direction, and a total order over nullable order columns (null order is OPEN V2; heap uses `total_cmp`, `read.rs:109-118`). Planner text ("prefix then order+`id`", "party pin first", §3) does not guarantee identical suffixes when prefix lengths differ or pins overlap order columns; it also conflicts with `intent.rs:127-159` order-pin/seek handling. Resume is `bounds.after = head.key` with fixed per-lane prefix (`word_merge.rs:182-184`; `cursor.after` skips `prefix.len`, `read.rs:866,1065`) — state this explicitly. **Change:** require a binding check for byte-identical suffix columns+kinds, id-termination, direction, and null ordering; add tests for overlapping order values, null order keys, a row in both branches, and `last`/descending.

5. **High — §9 Lean C8 is not implementable as written.** Model has single-pin `uniform` (`Eval.lean:148-154`), single-walk `pageRead` (`Eval.lean:192-199`), no merge/dedup/union walk; C8 is "uniform iff all rule columns pinned" (`OPEN.md:276-284`). "Decided = (a) pins decide or (b) branch-decided without grants" has no Lean definition of branch-decided, no union/dedup/order/`next` lemma, and leaves `pageRead_complete` breakage unaddressed; grants are excluded from the model yet owner-or-staff is a headline case. **Change:** define branch-decided in `Syntax`/`Store` terms, add a merge walk + union lemma + shared-suffix `next`, specify emitter coverage (where-disjunction, two-party rule), or explicitly descope Lean to case 1 with the gap recorded.

6. **Medium — §4 disclosure overclaims.** The v4 branch-set string reveals arity/columns beyond one index name; per-lane opening (`take+1` per lane when ≤8 lanes, `word_merge.rs:140`; `read.rs:995`) and grant-dependent lane opening (§3 "grant first") are meter-observable (examined/steps/index-entries) and differ between grant held/not-held; grant flips across pages have no grant version in the cursor. `grant_decision` readability (`rules.rs:88-110,368-416`) covers the single-page grant signal, not these. **Change:** justify branch-set disclosure vs existing index disclosure (or hash it), declare lane-count/meter differences as intended signals, and add a cross-page grant-change contract (per-page completeness only; continuation stays sound).

7. **Medium — §6 metering/cut contract is inaccurate.** "One step per head pushed and popped" is false: initial push charges (`word_merge.rs:150`), pop charges (`word_merge.rs:168`), refill push does not (`word_merge.rs:191-194`, word-metered only). Opening `take+1` per lane makes opening cuts likely and terminal (per 3000.007.000 §2–§3; `opened_all`/`drain_cut`/`continues`, `word_merge.rs:161,200-202`); the §3 eager fallback ("sound and incomplete, no `next`") contradicts §4 "complete exactly when…" unless lazy-eligibility is guaranteed. Grant-charge-then-cut (`grant_verdict`, `read.rs:210`) is unspecified. **Change:** correct step accounting, state opening-cut terminality with expected rates (e.g. k=8, take=50), require post-check lazy-eligibility or downgrade the completeness claim, and specify grant-cut behavior.

8. **Medium — §7 device contract is missing the merge combination rule.** Per-scan coverage sets device flags (`read.rs:255-260,894-901,967-970,1038-1040`; `non_uniform`, unknown facts, horizons, `query_unavailable`), but `merge_lazy` (`word_merge.rs:50-204`) has no stated combination of per-lane coverage into page `complete`/unavailable/`cut`; "grant lane always unknown + returns no rows" needs an exact wire outcome. Two-party device coverage is currently untestable (`E_SYNC` union-audience refusal, 3000.036.000 §4). **Change:** specify merged completeness as AND over lanes + coverage + horizons, the exact outcome for unknown lanes (vs server fallback), and device acceptance (held + unheld lanes → unknown).

9. **Medium — §3 planning/binding and IR compat.** The gate in `intent.rs:360-388` uses `intent_lanes::expand` + `prefixes_decide_rules` (`intent_lanes.rs:110-136`, pins-only, no `rule_true`/grant-readability); the promised "AST subset + runtime re-check + farm-shape test" is not defined. "Party pin first … reuses a declared index with exactly those columns or synthesizes one" conflicts with order-pin handling and creates up to 8 indexes per page (digest/churn unstated). "8 is the lazy merge's per-lane-page threshold (`lanes.len() <= 8`)" misreads a batch-size threshold as eligibility (`word_merge.rs:140`; eligibility is `rules.rs:429-444`, unbounded). New `branches:true`/`grant:true` on `Merge`/`MergeLane` (`ir.rs:383-414`, no such fields) with "skipped when false so digests unchanged" ignores old binaries silently ignoring unknown fields and mis-executing. **Change:** define the AST check, index reuse/synthesis + digest impact, correct the 8 rationale, and specify IR versioning/old-engine refusal instead of silent compat.

10. **Medium — §8 interactions leave `exists` and exclusions underspecified.** `exists → exists(b1) or …` needs engine + Lean (`existsRead` is single-domain, `Eval.lean:210-216`; cf. OPEN C5 / 3000.036 §15.12 true-or-unavailable) + device semantics; grant-`exists` "keeps today's behaviour" contradicts §7 device-unknown grant lanes. `count` (`E_QUARRY_BOUND`), search/word merges, views, mutations/jobs, `check` lane-skipping, and `test.cases.jsonl` expectations each need a citation/exact value. Exclusions (explicit index/key, `matching`, views, ephemeral/timeline/read-through, computed/calendar keys per `word_merge.rs:62-65`, seeks/`before`, nullable order) are scattered across §2 and §8. **Change:** add one normative exclusion table with per-case tests, and specify `exists`/count/device behavior or descope them.

11. **Low — §5 compat wording and shaped/inclusive positions.** Name the old-engine version, the `Version(4)` → `E_INPUT` mapping (`cursor.rs:116` → `read.rs:618`, `word_merge.rs:36`; `error.rs:98,173`), and device decoder parity. "Never records inclusive" (v3, `cursor.rs:81-83`; `PagePosition.inclusive`, `runner.rs:74`) must address shaped rewinds (`word_merge.rs:213-260`). **Change:** fix codes/messages (do not promise a new `E_CURSOR_INDEX` string the engine does not emit) and state inclusive/shape behavior for branch merges.

12. **Low — §12 Q1–Q6 scope.** Single-party non-expansion (§2) changes teaching and plans; 9-branch fallback ("at most 8") should state the 9th branch falls back to single-index + `N_NEVER_COMPLETE` (which test in §10 covers it). **Change:** record Q1 impact and the >8 fallback explicitly.

- Grant readability gating via `self_disclosing`/`disclosing` (`rules.rs:368-416`) and static probe charging on either verdict (`read.rs:203-212,918-932`) is the right basis for the grant-branch disclosure claim.
- Case-2 grant-superset short-circuit ("grant holds → read it alone") is sound for the current request; the gap is only cross-page grant flips and meter observability (findings 6–7).
- `prefix_verdict` probe-row + `prefix_decision` + `non_uniform` latch placement (`read.rs:179-198,909-954`) supports the per-branch admission story; the missing piece is the grant-false decided lane (finding 3).
- Old-engine `Version(n)` → `E_INPUT` path exists (`cursor.rs:116`, `error.rs:98,173`); only the §5 code/message attribution is wrong (finding 2).
