# Fresh ranked Trending needs no new authority; it is expressible today

**2026-09-16, lead, during wave 11.** Verified by compiling every form below with
the wave-11 `snapback4` binary. This closes — or at least reframes — the
"system-owned write authority" decision that the 0.2.21, 0.2.22, 0.2.23, 0.2.24,
0.2.25 and 0.2.26 reviews have all carried.

## The claim

A fresh, windowed, ranked Trending is a four-line `maintain`. It is
engine-maintained, fresh at load with no schedule lag, bounded on read, and
**takes no writes from principals at all**:

```quarry
maintain trendScore: count likes where .isOriginal = true by postDay, postId
  read <- allow
  by byScore: postDay, value, id

query trending(c: cursor ?):
  return trendScore[day(now)] after c last 10 by byScore { postId, score: .value }
```

`check: ok — 3 tables (0 synced), 1 operations, no problems`.

The two ingredients that make it work are both already paved and both already on
the maintains card: a maintain may be **indexed by its own `value`** (the card
ships `by byCount: value, id` on `postLikes`, read as `last 10 by byCount`), and a
maintain may be **grouped by a time bucket** (`day(.at)`, `bucket(.at, 2m)`). Put
the window column first in the index and the ranking is scoped to it.

## What the 0.2.26 builder wrote instead

A 14-line public `trendingRows` table with `insert <- allow` **and
`update <- allow`**, `expire at .expiresAt`, two indexes, a `backfill` job, an
`insert` inside `createPost`, and a hand-maintained increment/decrement inside
`setLike` — about 25 lines across three files. The 0.2.25 builder wrote the same
shape.

That workaround is not merely longer. `update <- allow` on a public ranking table
means **any principal can set any post's score to any value.** The paved form has
no such surface, because principals never write the maintain at all. The
hand-rolled version is the less safe one, and nothing in the run flagged it.

## What the maintain genuinely cannot do, verified

Both of these are refused, with accurate diagnostics:

```
maintain recent: count likes where .at > now - 86400000 by postId
  → E_QUARRY_MAINTAIN: maintain cannot evaluate now - 86400000;
    predicates compare row-local scalar columns and literals
    rewrite: store this fact in a source field and compare .field with a
    literal, or use a bounded job

maintain orig: count likes where .postId.parentId = null by postId
  → E_QUARRY_MAINTAIN: maintain cannot evaluate .postId.parentId; …
```

So the author must denormalise two static facts onto the counted row —
`isOriginal` and `postDay`, both known at insert and neither time-varying. That is
the real cost, it is small, and **the diagnostic already tells you to do it**:
"store this fact in a source field and compare `.field` with a literal."

A rolling 24-hour window is still not expressible; `day(.at)` is a calendar bucket.
The 0.2.26 app's own semantics were "posts created in the last 24 h, ranked by
current likes", which `postDay` + `day(now)` approximates as "posts created today".
Whether that difference matters is a product question, not a platform one, and it
should be stated rather than glossed.

## Therefore

The recurring proposal — a `system update` spelling, or engine-authored derived
writes under a new authority — **is not needed for this use case**, which is the
only use case any review has actually produced evidence for. The review's own
instinct was right for the wrong reason: it recommended "a narrow declared
derivation… over an unrestricted privileged helper", and the narrow declared
derivation already exists and is called `maintain`.

This is a **discoverability failure**, which is the programme's standing theme: six
consecutive reviews escalated a design decision for a capability that shipped. Two
builders in a row hand-rolled a less safe substitute. Nothing refused them, and
nothing pointed them at the maintain.

## What to build

1. **The feeds card must show this form**, as the answer for a ranking that must be
   fresh — next to the scheduled recipe, which its own card admits "lag[s] by one
   schedule period". A builder reading about Trending must meet the maintain first.
2. **The maintains card must show a windowed ranking**, not only `postLikes`
   ranked globally. The `by <window>, value, id` index order is the whole trick and
   appears nowhere.
3. **Consider a note** when a public table with `update <- allow` carries a column
   that is a `count`/`sum` of another table — the shape of a hand-rolled maintain,
   and a principal-writable score. This one is speculative; the false-positive risk
   wants checking before it is built.
4. **Do not** build `system update`, and close the carried residual in §20.x with
   this finding rather than another deferral.
