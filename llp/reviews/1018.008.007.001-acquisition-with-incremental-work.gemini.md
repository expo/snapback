## Verdict: REVISE

The diagnosis in LLP 1018.008.007 is accurate, and the targeted areas in LLP 1018.008.007.001 address genuine work amplification. Specifically, eliminating 200 redundant `groups.mine` tail queries, removing the $O(N^2)$ candidate scan in delivery acknowledgements, and stopping full `programs()` cloning during admission will cut 18–22 seconds of CPU and GC overhead.

However, the implementation plan has several material gaps around:
1. State-machine semantics and epoch invalidation races between semantic and item-only query refreshes.
2. Store listener classification protocols (`inputListeners`).
3. Rollback staging and bulk-eviction handling for the private derived acknowledgement index.
4. Rigid gating against the 30-second ceiling given the fixed 50-event network page constraint.

These issues must be resolved before cutting code.

## Strengths

1. **Accurate Bottleneck Attribution:** The profile attribution correctly distinguishes between intrinsic protocol latency and unnecessary local amplification. Identifying that `drainQueued -> logTail` repeatedly fetches the completed `groups.mine` query (202 times!) during message catch-up is an insightful discovery that explains a major source of serial network and evaluation churn.
2. **Strict Architectural Integrity:** The plan respects LLP 1012 and LLP 1019 invariants. It rejects easy shortcuts (such as bypassing admission envelope validation, fabricating watermark progress, or relaxing durable carrier atomicity) in favor of private, transient derived indexes and bounded exceptions.
3. **Targeted State-Proportional Allocation:** The plan identifies and eliminates concrete quadratic allocations: deep-copying `programs()` on every admission, detaching all terminal outbox history in `OutboxLedger.queued()`, and scanning full `deliveryAcks` history during page commits.
4. **Principled Verification Protocol:** The measurement methodology (ten alternating pairs, fleet host, explicit separation between time-to-first-useful-data, durable completion, acknowledgement settlement, and foreground admission) prevents gaming total sync time at the expense of background backlogs.

## Material Concerns and Required Resolving Changes

### 1. Missing Store-to-Query Classification Protocol for Refresh
* **Location:** Plan §5 (`Avoid redundant query work without suppressing progress`) & `snapback2/src/store/range-store.ts:792`, `snapback2/src/store/query-inputs.ts:16`
* **Concern:** In `PersistentRangeStore`, observers are notified via:
  ```typescript
  if (changesQueryInputs(journal.changed)) for (const listener of [...this.inputListeners]) { listener(); }
  ```
  In `query-inputs.ts`, `RECORDS` explicitly includes `"outbox"`. Consequently, *every* outbox mutation, ack state transition, and compaction triggers `changesQueryInputs() === true`, invoking `listener()` with no arguments.
  
  The plan states that outbox/compaction bookkeeping without overlay changes should refresh item entries while preserving query data, but it does not specify how the store communicates this distinction through `inputListeners`. Without changing the notification signature or mechanism, `subscribeInputs -> queries.refresh` will continue to trigger full query re-evaluations on every acknowledgement state change, defeating the intended decoupling.
* **Resolving Change:**
  1. Update `changesQueryInputs` (or introduce `queryChangeClassification(journal.changed)`) to classify swaps into `'semantic'` vs `'item-only'`. A swap is `'semantic'` if it touches rows, answers, extent/negative records, or outbox entries that have active overlays or row targets; it is `'item-only'` if changes are restricted to terminal outbox status transitions without overlays and `compactedThrough`.
  2. Update `inputListeners` in `PersistentRangeStore` from `Set<() => void>` to `Set<(kind: 'semantic' | 'item-only') => void>`, passing the journal's classification.

---

### 2. Race Conditions and Epoch Cancellation in Semantic vs. Item-Only Refreshes
* **Location:** Plan §5 (`Avoid redundant query work`) & `snapback2/src/client-sessions.ts:174-192`
* **Concern:** In `client-sessions.ts`:
  ```typescript
  if (entry.refreshScheduled || entry.refreshing) return;
  ```
  If a semantic refresh is in flight (evaluating a large message query) and an item-only bookkeeping event commits:
  - If the item-only event bumps `entry.epoch`, line 183 (`if (epoch !== entry.epoch) return;`) drops the in-flight semantic result, stranding the query on an older state or forcing a redundant restart.
  - If the item-only event does *not* bump `epoch` but mutates `entry.snapshot` concurrently, the completing semantic refresh will overwrite `entry.snapshot` with an older post-compaction state.
  - If `scheduleRefresh` simply drops the item-only event because `entry.refreshing` is true, the item-only update will be lost unless latched.
* **Resolving Change:** Explicitly define the refresh latch state machine in `client-sessions.ts`:
  1. Add `refreshPendingKind: 'none' | 'item' | 'semantic'` to `Entry`.
  2. If an item-only notification arrives while `refreshing === true`, set `entry.refreshPendingKind = entry.refreshPendingKind === 'semantic' ? 'semantic' : 'item'`.
  3. Item-only updates must never bump the query's main evaluation `epoch`.
  4. In `finally` of an in-flight refresh: if `refreshPendingKind === 'semantic'`, schedule a full semantic re-evaluation; if `refreshPendingKind === 'item'`, perform an in-place metadata patch (updating `itemEntries`, `compactedThrough`) without re-evaluating the underlying query plan.

### 3. Derived Index Staging, Rollback Safety, and Bulk Eviction
* **Location:** Plan §3 (`Acknowledgements proportional to changed state`) & `snapback2/src/store/range-store.ts:778-784`, `snapback2/src/delivery-acknowledgements.ts:60`
* **Concern:**
  1. **Rollback Leakage:** In `PersistentRangeStore.commit()`, `applyDeliveryAcknowledgements` runs on `journal.draft` *before* `await this.replace()` persists to IndexedDB. If the derived pending/bound index in `PersistentRangeStore` is updated eagerly during `applyDeliveryAcknowledgements` and `replace()` rejects, `journal.rollback()` restores `this.state`, but the in-memory index would remain corrupted.
  2. **Bulk Eviction Invalidation:** The plan limits candidate evaluation to the union of changed ack keys, changed log row keys, and keys from changed outbox intents. However, during retention resets, coverage drops, or range evictions, individual log row keys are not always individually enumerated in `journal.changed.get('rows')` (e.g., table wipes or range drops). A strict key-intersection approach would fail to identify orphaned acks, causing retained ack marks to leak permanently in `deliveryAcks`.
* **Resolving Change:**
  1. Keep `applyDeliveryAcknowledgements` purely functional over state and candidate inputs: it must return candidate changes or mutated drafts without touching `PersistentRangeStore`'s index directly.
  2. Update the derived index in `PersistentRangeStore` strictly *post-durability*, immediately after `this.persisted = this.state` and inside the same try block as `this.updates.publish()`.
  3. In §3, specify that if a swap contains a bounds adoption, coverage reset, or bulk range eviction where row deletion is un-enumerated, candidate evaluation falls back to an explicit full sweep of `state.deliveryAcks`.

### 4. Strict Preconditions for Safe No-Tail Ack Settlement
* **Location:** Plan §5 (`Avoid redundant query work without suppressing progress`) & `snapback2/src/client-outbox.ts:285-320`
* **Concern:** Bypassing `logTail` in `drainQueued` for acknowledgement mutations removes 200 unnecessary network roundtrips. However, `logTail` also ensures that any server-side state generated by a mutation is merged atomically into the store alongside the committed intent. If an acknowledgement mutation accidentally generates server-side row effects, or if the server returns an unexpected schema/plan mismatch, skipping `logTail` will drop rows and violate LLP 1012 §7.
* **Resolving Change:** Specify in §5 that skipping `logTail` is permitted if and only if all of the following conditions hold:
  1. The mutation operation matches the schema's declared delivery ack (`d.log` receipt declaration), verified via `storedProgram`.
  2. The admitted entry has no predicted row effects (`entry.targets !== undefined && entry.targets.complete && entry.targets.rows.length === 0`).
  3. The server response confirms zero observable effects (`Array.isArray(result.response?.effects) && result.response.effects.length === 0`).
  4. The server response confirms schema/plan identity match (`result.response?.program?.schemaHash === held.schemaHash && result.response?.program?.planHash === held.programs[entry.op]?.planHash`).
  
  If *any* of these conditions is not satisfied, or if `result.state !== 'committed'`, the execution must fall back immediately to the standard `logTail` pipeline.

### 5. Reality Check on the 30-Second Target vs. Fixed Page Bounds
* **Location:** Research Doc §Why initial sync is still expensive & Plan §1, §6
* **Concern:** In the 53.6s profile, CPU time is 47.7s. Expected savings:
  - Acknowledgement cleanup: ~6.1s
  - Detached program/outbox reads: ~5.0s
  - Redundant React/query evaluations: ~2.5s
  - Associated GC reduction: ~5.0s
  - Eliminated `groups.mine` network roundtrips: ~2.0s
  
  Total savings are roughly 20–21 seconds, putting projected completion around 32–35 seconds.
  
  However, the client is strictly bound to draining at most 50 events per query page across 10,008 messages. That mandates at least 201 sequential HTTP query requests and 201 IndexedDB transaction commits. On typical browser IndexedDB implementations, 201 write transactions alone consume 6–12 seconds of non-subtractable overhead. Gating this sub-LLP on strictly achieving `<30 seconds` risks rejecting sound algorithmic improvements due to transport constraints that this plan explicitly leaves untouched.
* **Resolving Change:** In §6, formalize the acceptance criteria:
  - If clean median acquisition lands between 30 and 38 seconds with all quadratic CPU paths eliminated (renderer CPU < 25s), the implementation is accepted as fulfilling LLP 1018.008.007.001.
  - Formally record the residual latency as transport-bound (201 sequential 50-row network roundtrips and IndexedDB transaction commit ceilings), providing concrete evidence for whether a subsequent transport streaming/batching sub-LLP is necessary.

## Optional Suggestions

1. **Inner Queued Filter in `OutboxLedger.queued()`:**  
   In `client-outbox.ts`, `queued()` currently reads `all()` and filters in JS. In `PersistentRangeStore`, implement an internal selector `state => outboxOrder(filterQueued(state.outbox)).map(clone)` so that only the 0–2 currently queued entries are cloned, rather than cloning hundreds of historical entries.
2. **Bucket Pending Ack Identities:**  
   When grouping pending identities in `admitAcknowledgements()`, partition them into a `Map<logName, string[]>` first, then slice into 50-item chunks. This guarantees strict $O(N)$ execution without intermediate array concatenations.
3. **Compile-Time Gating for Diagnostic Timers:**  
   Ensure all selector instrumentation and candidate-count tracking introduced in §4 are wrapped in compile-time dead-code elimination flags (e.g., `if (__DEV__)`) so diagnostic bookkeeping does not skew benchmark runs.

### 1. Concessions and Disagreements Resolved

* **Gemini’s `complete: true` target filter was incorrect (Orchestrator Disposition 5):**  
  In Round 1, I proposed requiring `entry.targets.complete && entry.targets.rows.length === 0`. The orchestrator rightly notes that generated ack operations carry an unresolved receipt update target (`deliveriesReceipts`) with `complete: false`. Requiring `complete: true` at admission would have killed the skip-tail optimization entirely. The revised plan correctly shifts proof of empty observable effects to the authoritative wire response (`Array.isArray(response.effects) && response.effects.length === 0`), combined with matching admitted identity and zero predicted/active overlays. I fully concede this correction.

* **Rejection of speculative transport floors and loosened targets (Orchestrator Dispositions 7 & 2; Astra Concern 4; Grok Concern 8):**  
  My Round 1 review argued for accepting a 30–38s window and assuming a 6–12s IndexedDB floor. Grok, Astra, and the orchestrator correctly rejected this: summing overlapping profile categories to assert a synthetic floor is unempirical. Retaining `<30s` as the explicit product goal, establishing complete durable content *and* all earned acknowledgements settled as the sole primary endpoint, enforcing a 180s cutoff with honest censoring, and attributing any residual latency post-measurement is the methodologically sound posture.

* **Source misreads on `SwapJournal` and `referenceIndex` (Muse Concerns 1 & 9; Grok Concern 1; Orchestrator Disposition 3):**  
  The provided `SwapJournal` source confirms that path length < 2 records specific keys under category names (`journal.changed.get('rows')`, `get('outbox')`). Compacted intents and per-row deltas *are* individually tracked, disproving Muse's concern about coarse category tracking. Furthermore, `PersistentRangeStore` only resets `referenceIndex = undefined` on root replacement (`journal.changed.get('*')`), handling ordinary deltas via `referenceIndex.update`. There is no hidden quadratic `referenceIndex` rebuild, and commit order is already post-compaction (`applySwap` → `compactSuccesses` → `applyDeliveryAcknowledgements`). Muse’s call for a transport sub-LLP to address a non-existent index rebuild was unwarranted.

### 2. Panel Convergence on Material Improvements

* **Astra’s backlog drain amplification is defused (§3):**  
  Astra made the most perceptive algorithmic observation in Round 1: bounding a single pending projection to $O(P)$ does not prevent quadratic aggregate work if repeated admission under grant limits enumerates a stagnant backlog. Revised §3 elegantly solves this: pre-promotion pending admission now selects `next50` plus the count of remaining batches per log. Coupled with stable insertion-ordered pending queues where redeliveries append to the tail, blocked or empty status checks never enumerate held history or regroup backlogs. Muse’s concern regarding FIFO stability across redeliveries is satisfied without sorting overhead.

* **Transaction-bound skip-tail eligibility and race guards (§5; Astra Concern 2; Grok Concern 5; Muse Concern 6):**  
  Astra and Grok rightly demanded that skip-tail eligibility cannot rely on a transient pre-persistence check that could be invalidated by concurrent resets, coverage drops, or overlay mutations before the terminal commit. Revised §5 explicitly binds eligibility through the serial terminal swap: principal, cancellation, and coverage revision checks remain active; the governing program and overlays are validated in that exact turn; missing or malformed effects always force the safe `logTail` path; and `recordTerminal` is deferred strictly until after durable persistence.

* **Store classification and refresh latch state machine (§5, §6.4; Gemini Concerns 1 & 2; Grok Concerns 6 & 7; Astra Concern 3):**  
  The revision completely addresses the store-to-query notification ambiguity. By passing `'semantic' | 'items'` through `inputListeners` and treating deletion of an absent journal key as a no-op (Grok's insight), we avoid false-positive semantic flags during outbox compaction without deep-cloning prior overlays. In `client-sessions.ts`, semantic dominance is formally preserved: in-flight semantic refreshes are never cancelled by item nudges, item nudges latch their metadata updates for post-refresh application, item events never bump query evaluation epochs, and controlled-promise test cases in §6.4 explicitly verify deterministic interleavings.

* **Post-durability index updates and rollback safety (§3, §4; Grok Concern 4; Muse Concern 4; Gemini Concern 3):**  
  Updating the private derived index strictly *after* successful durable persistence (inside the serial `enqueue` chain before observers or queued readers run) completely eliminates rollback state corruption without requiring defensive index cloning. If durable replace fails, the transaction rolls back, and the in-memory index remains untouched at its prior valid state.

* **Queued selector comparator (§4; Grok Concern 8; Muse Concern 5; Astra Suggestion 1):**  
  The plan explicitly pins in-store queued filtering to `outboxOrder` (preserving `createdAt` and code-unit tie-break behavior) rather than `outboxFifo`, preserving exact custody order while eliminating terminal detachment copying.
