- **Medium — detached upload resurrects an unowned directory.** [assets.rs:38](snapback4/crates/snapback4-core/src/assets.rs:38). Concrete sequence: prepare an upload, save the directory path, drop the engine, call `upload.write(&bytes)`, then drop the upload. `Store::drop` has already run; `write` recreates the directory; `Upload::drop` removes only the two file paths (lines 53–58), leaving an empty directory permanently. This is permitted by the public API, which explicitly returns an upload without borrowing the engine ([engine/mod.rs:480](snapback4/crates/snapback4-core/src/engine/mod.rs:480)); current HTTP callers retain the engine and avoid it. Smallest robust fix: share an ephemeral-directory cleanup owner between `Store` and outstanding `Upload`s, removing the directory when the last owner drops. Add this destruction-order regression.

- **Low — cleanup completion is overstated.** [Ticket:3](issues/20260919-snapback4-memory-store-leaks-an-assets-directory-per-engine.md:3) says leaked directories were removed, while lines 44–45 say removal remains running. A reader cannot determine whether host cleanup finished. Smallest fix: distinguish the code fix from cleanup in progress, or record verified completion.
