## Question evidence

### 1. Copy safety

The digest job is not a client operation (`jobs.rs` 67–70; `job.rs` 170–171). It emits only `targetUserId: p.principal` from `profiles` (`jobs.rs` 181–191). `profiles` insert is `.principal = viewer` (129), so a caller cannot mint another principal’s profile. The inner loop is `members[p.principal] first 1000` (185); `unreadIn` is only applied to those rows. A chat the recipient is not in cannot contribute. That is the structural authority the card states (116–118), and it is required because a job runs as the system principal and **passes every rule** (`read.rs` 241–247; `job.rs` 4–5, 257).

`inbox` walks `members[viewer]` and passes `viewer` into `unreadIn` (`jobs.rs` 175–179). Alice’s period inbox has no `c3` (`digest/mod.rs` 76). Another principal’s unread is not a column `inbox` returns.

`conversations` `insert <- allow` with `after insert <- exists members[.id, viewer]` (`jobs.rs` 131–136) is the careful create-and-join form: an orphan conversation cannot commit. `members` insert is `exists members[.conversationId, viewer] or created conversations[.conversationId]` (148). That lets any current member add any principal (and lets the creating mutation add others). It is looser than README §2’s admin-gated memberships (157–158) and than `guide search`’s admin-or-created rule. It does **not** let the job disclose a non-member chat: adding someone makes them a member, then the digest is about a chat they are in. A careful private-chat builder should not copy that insert line blindly; the digest recipe does not depend on it (tests seed as system).

`digestTotals` is `read/insert/update/delete <- deny` (`jobs.rs` 313–316). Principals cannot write it; the job still can because the system principal bypasses rules. That is exactly the “job-written only” case the card describes (232–236).

Remind: `invites` insert/update/delete are `deny` (`jobs.rs` 41–43); only the job (system) flips `reminded`.

### 2. Engine honour of the card

- **Expiry.** `Runner::expired` treats a row past `expire at` as absent to every reader, including system, before the rule (`read.rs` 212–217). The scan still charges examined, then `continue`s (`read.rs` 588–591). The three-profile test keeps 12 physical messages, excludes the `expiresAt = 20_000` row at `now = 20_000`, then sweeps one row (`digest/mod.rs` 88–94).
- **Authorization is structural.** Jobs do not consult rules (`read.rs` 245–247). The published loop is the proof; the card says a non-membership path must re-prove by hand (`jobs.rs` 116–118).
- **Envelope.** Job ceilings: examined 16,384 (`meter.rs` 29–31). Aborting scans pay one examined unit before the verdict (`read.rs` 564–566) plus each row, including lookahead when a `take+1` row exists (`read.rs` 574, 582–585, 639–641). The suite’s 1,000×20 period seek is 7,003; ordinal attempts 16,385 (`digest/mod.rs` 141–155). At 1,000 memberships and no lookahead/expired candidates, 14,381 period messages + 1,000 members + 1,002 scan attempts + 1 profile row = 16,384 (`digest/mod.rs` 236–254; `jobs.rs` 208–211). One more parks with no new effect.
- **Park / re-queue.** A refused chunk rolls back its savepoint and parks (`job.rs` 303–308). `run_job` always enqueues a **new** row (`job.rs` 189–192). The parked test: two different ids, effects 1 → 2 for the small profile (`digest/mod.rs` 158–174).
- **Schedule and cursor.** `fire_schedules` commits the boundary with the job (`job.rs` 317–384). Restart test: first seen at 1s does not fire; fire at 60s; one chunk commits one effect; reopen; `fire_schedules(60_001)` is empty; remaining chunks finish at two effects; a manual `run` of the same period is a new id and four effects (`digest/mod.rs` 176–207). Successful chunks record outbox in the same commit as the cursor (`job.rs` 288–300; `effects.rs` 74–84).
- **Idempotency.** The card calls this durable emission, not exactly-once delivery, and names `(targetUserId, periodEnd)` or an `emitted` marker (`jobs.rs` 218–228). README 1008–1010 says the same. That matches the tests and does not overclaim.

No builder-actionable sentence on the jobs digest section was found that this engine does not honour. 0.2.27 timings are labelled as that run, not a promise (`jobs.rs` 195–199).

### 3. `remind`

`by bySentAt: sentAt, id` plus `immutable sentAt` (`jobs.rs` 38–39) is exactly `E_JOB_CURSOR_INDEX`’s requirement (`bind/program.rs` 948–951; `jobs.rs` 337–342). Updating `reminded` does not move the resume key. The sweep captures an upper key at start and will not visit inserts past it (`job.rs` 260–274, 139–141). The engine test seeds `a-future` first in id order at 30_000: a by-id `break` on `sentAt >= periodEnd` would write 0; the range seek writes 2 and leaves `d-end` at `periodEnd` unreminded (`digest/mod.rs` 257–270). Half-open `[periodStart, periodEnd)` matches schedule arguments (`job.rs` 358–362).

Prelude and `break` are still shown: language card `job nightly` (`language.rs` 350–354, prelude `end = periodEnd` and `break`); jobs-card prose still describes the prelude (`jobs.rs` 55–57); README still says `` `break` ends the sweep `` (684–685). The language-card suite still asserts `break` ended a sweep (`guide.rs` 602). They were not the only place those forms were shown.
