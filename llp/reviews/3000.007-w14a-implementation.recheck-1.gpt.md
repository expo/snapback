In the pinned SQLite 3.53.2 implementation, `OP_Column`’s page-resident branch calls `sqlite3VdbeMemGrow` and `memcpy` for TEXT **and BLOB**, without consulting P5. Only the subsequent overflow branch checks `OPFLAG_BYTELENARG`/`LENGTHARG` ([bundled sqlite3.c:99667](/Users/ccheever/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/libsqlite3-sys-0.38.2/sqlite3/sqlite3.c:99667)). Thus `octet_length(r.data)` fixes oversized overflow reads, but neither it nor `length(i.k)` is universally payload-free.

A freshly prepared preflight reading approximately 700 bytes of page-resident JSON with a 500-byte heap allowance can allocate/copy that JSON before line 816 rejects the allowance. The current 4,000-byte fixture exercises overflow storage; its P5 assertions remain green for this uncovered case.

The smallest correct repair is to precharge a conservative, page-size-based bound for resident column scratch **before executing the preflight**, retaining the later actual-length allowance for subsequent payload work. Extend the native allocation probe to cover both page-resident and overflow payloads, and qualify the comment/ledger accordingly.
