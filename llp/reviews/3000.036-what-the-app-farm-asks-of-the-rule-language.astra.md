**Date:** 2026-10-08. **Revision reviewed:** draft (`4ca7e726f8`). **Mode:** blind, read-only, over a detached worktree at that commit; `codex exec --skip-git-repo-check -m gpt-6-astra -c model_reasoning_effort=xhigh -s read-only`. **Provider/runtime:** OpenAI Codex CLI 0.160.1 on the Mac Studio (Mac17,15). **Redacted:** no. **Brief:** [`3000.036-what-the-app-farm-asks-of-the-rule-language.brief.md`](./3000.036-what-the-app-farm-asks-of-the-rule-language.brief.md), shared verbatim with the Grok reviewer. **Verdict: NOT READY.**

## Verbatim review

The motivation is sound, but §§1, 5 and 6 need further design work before acceptance.

I reviewed the checkout read-only at `4ca7e726f8`. Farm counts are treated as quoted evidence. The counterexamples below are derived from the code; I did not run new reproductions.

1. **High — §1, option B: define completeness per read site, independently of readability.**

   Alice holds claimant-synced claims. A claim with `claimant = Bob, postedBy = Alice` is readable by Alice but absent locally. An unrestricted scan or unsuccessful `exists claims[id]` must therefore remain unknown. Conversely, finding an authorized held row can prove existence without the query predicate implying `.claimant = viewer`. The RFC’s predicate test is neither a complete specification nor a necessary condition for every answer.

   A predicate implying the selected disjunct also does not establish acquisition or horizon coverage. Nested lookups, aggregates, authorization probes and branches need their own coverage decisions. Today, ordinary horizonless synced scans do not perform this additional subset check; see [read.rs](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/crates/snapback4-core/src/engine/read.rs:875).

   **Smallest fix:** specify a conservative rule for each read site: prove its addressed domain belongs to the selected sync audience, then apply existing acquisition, horizon, retention and meter checks. Unproved misses and populations remain unknown; valid positive witnesses remain usable. Prediction must use the same distinction, especially for upsert absence.

   This need not introduce a general implication solver or query-shaped receipts. Existing [prefix visibility analysis](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/crates/snapback4-core/src/engine/rules.rs:109) provides useful machinery, provided it analyzes the **selected disjunct**, not merely whether the full read rule admits the prefix. Start with explicit column audiences and recognized pinned-key forms. Adding target audiences and conditional public sync makes B broader than the smallest useful admission.

2. **High — §1, options B/C and recommendation: one `sync` line does not guarantee one delivery path.**

   The RFC identifies private-field owner delivery, then excludes it from B’s cost argument. Consider:

   - Read rule: group membership **or** authorship.
   - Selected sync audience: group membership.
   - A private field `written by .author`.
   - Alice is both author and member, then leaves the group.

   [Partition accounting](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/crates/snapback4-core/src/partition.rs:203) additionally delivers an authorized private-field owner image to Alice’s principal partition. The membership leave emits a scope tombstone, but [device `leave()`](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/crates/snapback4-device/src/device.rs:1279) deletes every row in that group without preserving that independent delivery.

   Mutable target-audience columns expose another inherited hazard: moving a row from group X to Y emits the Y `put` before the X `del`. A viewer holding both groups receives both; the unconditional device deletion removes the surviving Y image. “At most one partition per row” at a single instant does not settle transition ordering.

   **Smallest fix:** initially exclude private-owner delivery combinations and mutable content group keys from narrowed sync, or explicitly design their preservation and ordering. Add witnesses for owner/member overlap, group moves, scope leaves and audience-column changes.

   Mere continued readability through an **unsynced** alternative is different: removing that row locally is correct under B. It does not itself require reference counting.

3. **High — §1, conditional public audience: the proposed reuse of audience-update accounting can disclose a never-public row ID.**

   Take an existing private photo with `approved = false`. In one transaction, set approval true and then false. With the proposed conditional partition selection, existing accounting produces a public `put`, then public `del`; [append coalescing](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/crates/snapback4-core/src/partition.rs:693) retains the `del`. Ordinary deletions are not read-rule filtered. Every public subscriber learns the ID of a row that was private at both commit boundaries.

   The born-row protection does not cover this case: the row existed before the transaction.

   **Smallest fix:** require commit-boundary audience accounting that suppresses transient grants and their tombstones, with a specific false→true→false regression. Conditional filtering must also govern snapshots, join acquisition, horizon selection and replayed current images—not only `partitions()`.

   This is a reason to separate conditional public sync from the first narrowed-column implementation.

4. **Medium — §3, option C: `N_WRITE_DENIED` needs branch-specific wording and no action-seat exemption.**

   An upsert with `insert <- allow` and absent/denied update succeeds when the target is absent. Saying its write “is refused for every caller” is false. The converse applies to an allowed update with denied insert.

   Actions also have no Quarry write body: [their bound program contains admission only](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/crates/snapback4-lang/src/bind/actions.rs:48). TypeScript handlers call separate mutations under invocation authority. Consequently, “inside an action whose seat a rule names” is not a schema-local property of the mutation. A service seat is an ordinary rule-governed principal; it cannot bypass literal `deny`.

   **Smallest fix:** define the note over bound mutation write sites. Missing rules normalize to `Deny`; report their absence using the table site rather than inventing a clause site. For upsert, name the denied insert or update **branch**. Exempt system job execution, but remove the action exemption. Say “this effect/branch cannot pass its rule for a non-system caller,” not that the entire operation is unreachable.

   Rejecting option A **as written** is sound: conditionally identifying evaluated-false rules distinguishes them from hidden collisions. That does not prohibit uniformly attached, schema-derived information that makes no such distinction.

5. **High — §5, option B and recommendation: the device cannot replace the host’s prediction fence using its present inputs.**

   `wantsServer` does not contain the prediction fence. The client separately checks queued prediction footprints, conservative read dependencies and host-side admissions in progress. [LocalReads.pending()](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/packages/snapback4/src/local-reads.ts:285) includes `admissions > 0`, which is not part of the device query request.

   More fundamentally, a device can answer `server`, then a write can begin while the HTTP read is in flight. Publishing that response based on the earlier instruction overwrites intersecting optimistic state. The first-party client checks again at delivery.

   “Keep the device answer marked pending” is also unsafe when that answer is a speculative zero or Boolean. Existing client behavior withholds such placeholders.

   **Smallest fix:** make the device field describe routing/coverage at its observation, while the host contract retains admission and publication fences. Define “settled” by the relevant prediction/observation state, not “a round” completing. Preserve checks before dispatch and publication, conservative dependencies for unknown branches, and withholding of speculative values. Moving those responsibilities into the device would require an additional protocol, not a field computed from `wantsServer`.

6. **High — §5, option B: omitting `data` requires a coordinated recovery and composition change.**

   There is a concrete compatibility failure. After remembering a valid server answer, the client goes offline and queries an online-only table. Removing device `data` makes `local()` construct loading. But [remembered-answer recovery](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/packages/snapback4/src/local-query.ts:122) currently requires a speculative placeholder whose result is **not** loading. The remembered answer is no longer recovered. Keeping the old booleans does not preserve this behavior.

   Furthermore, `answer: server` encompasses both unusable placeholders and useful non-speculative unknown values. LLP 3000.020’s lower bounds must remain available offline. LLP 3000.028’s retained components and row provenance may require composition rather than replacement by a whole server answer.

   **Smallest fix:** distinguish routing from local-value validity. Restrict omission to genuinely unusable speculative results; preserve supported partial and retained values. Update recovery and composition alongside the device change, and specify version negotiation or coordinated host/device requirements.

   The documented contract must include `held` queries, known cuts, authoritative versus speculative refusals, component/row retention, transaction-bound watermarks, expiry deadlines, identity/generation changes, and remembered-answer invalidation. A three-value routing field cannot replace those obligations.

7. **High — §6, option B: “changed tables once per commit” is not yet a resumable stream contract.**

   A disconnected or slow client misses commit 8 changing X, then receives commit 9 changing Y and advances its cursor to 9. If the event contains only Y, X remains stale indefinitely. Current [`check()`](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/crates/snapback4/src/serve_changes.rs:112) gathers the interval since the caller’s cursor, conservatively invalidates all tables on saturation, and includes store identity, preservation and settlement evidence.

   Durable commits are also not the only wake source. Ephemeral changes have their own incarnation and epoch. Presence can change without either stream producing a durable-table event; the core explicitly supplies a five-second presence refresh. Replacing all timers with durable SSE would leave presence displays stale.

   An indefinitely held stream additionally removes the existing ≤25-second opportunity to recheck credentials. An expired or revoked full session must not remain connected indefinitely merely because no data changed.

   **Smallest fix:** choose explicitly between:
   
   - SSE as a wake hint that causes the client to fetch the existing cursor-based contract; or
   - SSE carrying that contract, with interval aggregation, bounded-history fallback, store/generation reset handling and ephemeral cursors.

   In either case specify atomic registration versus commit publication, periodic credential revalidation, disconnect detection, Full-versus-Reader presence eligibility, grace/confirmation behavior, and continued presence refresh or equivalent invalidation.

8. **Medium — §6, costs and recommendation: evented tiny_http parking is feasible, but its advantage over C is unproved.**

   The current threading facts are substantially correct: bounded connections have a parser thread waiting for response completion; held polls occupy a wait worker; there are 32 wait permits shared with claims and a default 128-connection cap. The condvar and `notify_all` descriptions agree with the code. The 33rd *simultaneously held* waiter can be refused; this is not an unconditional 32-viewer limit.

   Handing a socket to a parker must transfer parser/response ownership and release the connection thread without allowing a pipelined request to race it. Existing [`write_response_frame()`](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/vendor/tiny_http/src/request.rs:569) performs blocking writes and flushes. Using it on one parking thread lets one slow reader stall every stream. Idle polls also currently retain a detached reader engine, so “one descriptor and a small entry” is not an established accounting result.

   C need not introduce a separate admission policy or TLS contract: a second listener can share admission state and sit behind the same proxy.

   **Smallest fix:** retain B and C as measured alternatives. Require bounded nonblocking output, coalescing/backpressure policy, stream and ordinary-request reservations, complete cleanup, proxy buffering/timeout behavior and terminal authentication signaling. Benchmark slow readers, reconnect bursts, credential expiry and ephemeral-only changes alongside idle capacity. Treat “low thousands” and the week estimates as unvalidated estimates. A is a reasonable bounded mitigation, not fulfillment of the thread-free requirement.

9. **Medium — §7, option B and recommendation: the proposed landing gate conflicts with the adopted loop budget, and its causal evidence is overstated.**

   A 25–55-minute mandatory gate for every client/device change conflicts with `rules/RULES.md`’s “Nothing blocks on anything slower than 60 seconds,” explicitly adopted by Snapback 4. Limiting the gate to those directories does not resolve that conflict.

   The cited qualification ticket says **several** failures match SN’s changes and attribution is in progress. It does not establish that all 24 failures were caused by that change, as §7 states.

   **Smallest fix:** recommend A, measure C, and propose broader client qualification outside the landing gate—or explicitly request an author ruling changing the budget. Correct the attribution to match the ticket.

   A is sound: qualify a clean patch cut from the actual published source with dependency-complete cherry-picks and unchanged artifact checks. The scripts bind source and artifact integrity rather than requiring `main`. Recording downstream pins is also necessary.

10. **Low — §2, option A: the replacement text still states the bound incorrectly.**

    “Any string id up to 144 bytes” is not the implemented rule. [`identity_fits()`](/Users/ccheever/projects/snapback-wt-laneE-review/snapback4/crates/snapback4-core/src/value.rs:390) limits the canonical **tagged JSON representation** to 144 UTF-8 bytes, including nine bytes of tag overhead and escaping. A 136-character ASCII ID already fails. Reserved `system` identities are rejected too.

    **Smallest fix:** say “a string identity within the canonical identity-size limit; no target-existence check,” and link the exact limit. Keeping existence explicit is consistent with the recorded reference decision and is the right recommendation here.

§4’s proposed literal/job-viewer diagnostic is sound within its stated scope. Keep runtime validation as the backstop. An `as` block is already read-only; the text should not imply that writing inside it is an alternative repair.

Deferring C is justified by its unresolved delivery and revocation work. B can be a useful smaller feature after the restrictions and proofs above; the RFC has not established that its entire proposed B is the smallest form. The diagnostic improvements in §1A and request-correlated development traces in §3B can proceed independently.

Ownership is mostly consistent with LLP 3000 decision 4:

**Low — §8, final paragraph:** §4 does narrow accepted programs: even a never-invoked job containing the prohibited write would newly fail `check`. Replace “changes no admitted semantics” with “preserves the runtime refusal and successful-write behavior”; use that narrower claim when deciding delegation.

**Overall verdict: NOT READY.**
