## Material concerns (each with concrete counterexample)

1. **useAppReady ordering/identity underspecified (§2).** "Successfully opened after this App's initial ready settled" does not decide the case where the account opens before initial ready settles, or where a remount reuses a cached account. Counterexample: `AppProvider` remounts for viewer B while account A's async open resolves late — does A flip B's lifetime true? The "new App or viewer starts a new lifetime" rule says no, but the late-resolution path has no fence described beyond "session revocation/store replacement retain synchronous identity fences."
2. **Protected-copy MUST-clear is unenforceable (§2).** "An application that copies protected data into editable state MUST clear that copy when its source authority withdraws" names no trigger, subscription, or re-render obligation. Counterexample: `const [draft,setDraft]=useState(role.name)` on first authorized render; role withdraws while the component does not re-render (memoized shell, blank draft retained "above all branches"). Blank-initialization plus "examples offer no prefill path" does not cover this later copy. No implementer can pass/fail this MUST.
3. **Authority-gate conjunction + race delegation (§2).** `isPresent && complete && fresh && !revalidating && initial-readiness && api.myRole.available(release) && availability of each protected operation` leaves "availability of each protected operation" undefined (which ops, empty-set vacuously true?) and then delegates races to "SDK/server admission handles races." Counterexample: gate passes, role revoked before submit, SDK refuses — UI already asserted authority. If that is acceptable, say so; if not, the gate is a TOCTOU check with no generation/lease.
4. **Discovery cache + missing-cache rule contradicts H9 (§2/§5).** Cache keyed "defensively by backend URL" with "missing cache selects accounts" and "failed refresh/cache writes never gate opening" means a reused URL with stale discovery opens wrong, and a cleared cache forces account selection. Counterexample for H9: clear only auth-config cache + refuse all backend including `/auth/config` → missing cache → §2 says select accounts (signed out), but H9 requires held signed-in data, `useAppReady` true, no alert. Both cannot hold without an unstated session-custody bypass.
5. **Preview/apply exactness and partial-application recovery (§3).** "ONLY --apply writes the exact displayed, compiled schema plan" has no locking/display-completeness rule; "individual writes are atomic, not a multi-file transaction" plus "filesystem failure can report a partial application" has no recovery. Counterexample: preview displays plan, file changes before `--apply`, or write 1 of 3 succeeds then disk fills — re-apply must distinguish "already applied, idempotent" from "partial, resume." "Repeated apply is idempotent after the new writer is reachable" (§3) conflicts with "fresh-named" mutations per variant: two applies mint `ops_insert_admin_<fresh1>` vs `<fresh2>` duplicates unless naming is deterministic, which is unstated.
6. **Guest→password principal switch leaks/overpromises (§3).** "Neither dropped nor transferred," "only reopening that principal with its still-valid credential can resume original IDs," "recovery after loss of the old guest credential is not promised," "no new credential archive/GC/flush owner." Counterexample: guest creates offline intents, signs up (persisted current credential replaced), old guest credential ephemeral and lost → old intents permanently orphaned, never syncable, never GC'd — silent storage leak with no owner. "New-account views and delayed old facades cannot observe/admit/send the guest's intents as the new principal" is stated as fact with no SDK guarantee vs app obligation, so a delayed facade holding the old handle is unaddressed.
7. **Bare-identity predicate ambiguous (§3).** "Add bare `use identity` only if no module declares identity" does not define declaration (bare vs `guests` vs `password` forms, commented code, fixtures?). Counterexample: module has `use identity guests`; second module bare — blocked or duplicate? "Bare allows passwords and guests; `guests` is guests-only; `password` removes guests" leaves combined/ordered forms (`guests password`?) undefined.
8. **Roster/writer predicates overbroad and unscoped (§3).** (a) "At least one `ColumnType::Principal` in a unique index's columns" qualifies non-identity composites. Counterexample: audit log `UNIQUE(principal, timestamp)` becomes a "roster" and gains per-role provisioning inserts. (b) "No compiled mutation OR job insert/upsert path" is not scoped to the target table; literally, an insert writer for unrelated table B disqualifies table A from literal-per-role. (c) "Native opaque writers disable additional absence inference" is undetectable by definition — a raw-SQL/native inserter is invisible to the planner, so the planner will over-provision. (d) Multi-principal tables: "explicit target-principal input even when its column defaults to viewer" does not say which column when two principals share a composite unique (`owner`, `reviewer`).
9. **Literal-per-role heuristic admits known-wrong provisioning (§3).** "Role is a syntactic heuristic," "even typed preferences can receive a preview of literal attribute insertion," plus `CHECK`-constrained tables. Counterexamples: `user_preferences(role enum('admin','user'), UNIQUE(principal))` gets an operator `admin`-insert for any principal — privilege escalation relabeled provisioning; `CHECK(role!='admin')` with enum containing `admin` gets a generated `admin` insert that can never succeed yet appears in preview as a grant ("preview shows every grant; apply explicitly authorizes them") with no required unsafe-heuristic warning. "Never an invented role grant" for `user_role`/`roles`/text owners does not save the `role`-named non-roster.
10. **Generic bootstrap widening + uninterpretable Bearer boundary (§3).** Adding a generic enum-argument bootstrap "including variants a narrow application writer does not insert" bypasses application guards by design, while "constraints are never bypassed" covers only DB constraints — the distinction is not stated, inviting misreading. "The trusted service:ops Bearer [REDACTED] the existing boundary" is a sentence fragment (missing verb); the prohibition "exposing its generic provisioning authority to untrusted input is not authorized by this recipe" has no enforcement point. Counterexample: `onSignup(role: clientInput) → service:ops.bootstrap(role)` — forbidden by prose but not prevented, detected, or error-coded. "Already reachable tables receive no additional branch" leaves "reachable" (readable? writable? by whom?) undefined.
11. **Principal scan precision/recall + checkpoint gap (§3/§5).** Skip-all-symlinks misses monorepo-linked sources; stem-component exclusion (`proof`, `spec`, `fixture`, …) excludes production files like `proof-of-delivery.ts`; `?as=` and `persona\s*:` match non-persona code (acknowledged "comments/strings may match" but still drives "Upgrade's project action line … for persona-only modules," with "persona-only" undefined). §5's "packed scan retains checkpoint/scratch/test files … and must report only runtime findings" has no checkpoint/scratch exclusion in §3's list, so a checkpoint containing `usePersonaApp` deterministically false-positives H9.
12. **Declaration inference gaps (§4).** (a) Literal–literal with no enum arm (`'a' if c else 'b'`) unspecified — "ONLY alongside an existing enum arm" leaves the else-case result (text? singleton union?) open. (b) "Dynamic text widens to text only when every enum variant totally fits the existing text domain" — "totally fits" (charset? length? U+0001?) and the non-fitting outcome (REFUSE vs Unknown vs text) unspecified; link to the value-join REFUSE rule unstated. (c) "N is configured since_release, not inferred" — missing-attribute default and display when unconfigured unspecified. (d) "Compatibility codegen subsequently merges baseline domains" risks leaking new values into old releases that "lack this column" — no guard stated.
13. **Text-builtin gate is breaking and incomplete (§4).** Refusing `count`/`sha256` on domains containing U+0001 "even operations such as count/hash that could produce safe outputs," and requiring "every enum variant to pass text's existing forbidden-control check" for ALL listed ops, newly breaks previously working safe ops on values that "remain valid enum values." Counterexample: existing `count(mode)` with a U+0001 variant now `E_QUARRY_TYPE`. `upper is not a builtin` names no error code; "nullable values/elements/separators still need non-null proof" names no static-vs-runtime rule or error; per-op result-type mapping (`tokens`→list, etc.) unstated; precedence between the builtin gate and the value-join REFUSE rule (e.g. unsafe separator in `join`) unstated.
14. **Leaf-compatibility unsound for rebinding; row/leaf conflict (§4).** The same "corresponding value leaves … including explicitly disjoint domains (intentional broader comparison admission)" rule is applied to both comparison and "inferred-local compatibility." Counterexample for rebinding: `let x: enum('a') = <enum('b') value>` — disjoint yet "compatible," letting `'b'` inhabit `x: enum('a')`. "Comparison grants no assignment authority" does not retract the local-join admission. Separately, "objects must have EXACTLY equal key sets, including optional-valued keys" breaks `{a,b?}` vs `{a}` comparisons/rebindings with no migration note, and "nominal rows/references retain bidirectional assignability" contradicts leaf-recursion for rows differing only in one enum field's domain — both rules claim the case.
15. **Value-join REFUSE scope gaps (§4).** "Enum variant outside text's character domain" covers characters, not length/bounds. Counterexample: variant `'toolongvalue'` vs `text(max=5)` — REFUSE or Unknown? Enum/enum disjoint value joins (not enum/text) unspecified — Unknown or refuse? Explicit argument/column violations ("uses actual enum constraints") name no error code; "negative controls place each unsafe selection before explicit helpers" is test placement, not precedence between overlapping gates.
16. **Ordering/min-max + container semantics (§4).** "Require present OUTER operands" does not say static-reject (nullable outer always rejected even when runtime-present — over-strict) vs runtime-trap, and names no error. Counterexample: `min(nullableEnum, 'a')` with runtime-present value. Row/map ordering ("field counts then sorted keys/values") permits ordering values with differing key sets (e.g. `{a:1}` vs `{b:2}` decided by key-name comparison) while §4 compatibility forbids those shapes from acquiring fields — ordering and compatibility disagree on cross-shape values.
17. **Device-less/createApp, empty-lists, PDF helper (§4).** "Must produce a type error naming sessionStore" is type-level only — JS callers with no check get no stated runtime guard. "Complete empty lists already classify absent" conflates `[]` with absent (`null`/missing) with no stated consequence for blank-draft overwrite. `Client.upload(bytes,{file:{type,name}})` leaves `bytes` type and missing `type`/`name` errors unstated, and "the app places the returned asset id through its authorized file-column mutation" assumes a mutation the recipe does not generate.
18. **Normative vehicle and scope contradictions (§§1/5).** The document as an RFC in `Review` status declares §§1–5 "the complete CURRENT rules" that "deliberately supersede[] client §6.11," while "no version bump/publication belongs to this lane" — permanent split-brain between the RFC and the specs it amends; normative amendment belongs in a spec/decision update, not a Review RFC. "No new … authorization or runtime protocol" contradicts "deliberately adds operator provisioning authority," new `service:ops` mutations/branches, and new `E_INPUT`/`E_QUARRY_TYPE`/`E_UNIQUE` behavior. The KIT4/DAY5/RULES5/EX10 ownership split is asserted while the text normatively touches each (guest/account switching, starter advice, rules, proof/wire-adjacent codegen).
