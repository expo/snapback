## Direction check of LLP 3000.008.002.000 — Claude Opus 5.5 (max)

**Verdict:** RIGHT WITH CORRECTIONS

### Summary

The RFC's principles hold up: never retain protected results, loading is not empty, decorative reads split from required data, the authentication boundary follows the session, admit-and-continue, honest unknown receipts, and typing handed to LLP 3000.017.

But it misreads the evidence in three places that would misdirect tonight's work:
- **Receipts:** its only concrete Clique receipt rule contradicts the brief. Grader d-01 is itself a misreading.
- **Read gaps:** most of the "temporary read gaps" were produced by Snapback's own pending-write fence. It turns any query the device can't answer completely into `loading` while one of the app's own typing, acknowledgement or send writes is pending. The `reads` card states the opposite of the code, and `check` names no affected query. The main lever is query completeness plus diagnostics; UI ownership comes second.
- **Target starter:** the run used the Expo starter (`init --expo`, also the README's first path), not the web starter the RFC recommends. The web starter already implements most of §3/§4; the Expo starter implements almost none of it.

The one SDK primitive the evidence does justify — a read-only view of pending and failed intents — is missing from the RFC. The builder's 105-line localStorage journal exists only to supply it, and that journal is absent from the §1 ledger. The §5 acknowledgement helper should not be built as an SDK visibility hook.

### Findings

#### F1 (High) — The Clique receipt rule inverts the brief; d-01 is a grader error
- **Where:**
  - RFC §1 ledger row 6 (`:47`), §5 last paragraph (`:150-154`), §8 row "Recipient leaves without reading" (`:216`).
  - Brief: `benchmarks/briefs/social-messenger.md:504-507`.
  - Grader: `grading/grader-report.json` d-01; `grading/trace.md:577-595`.
  - Builder: `snapback/schema.q:223-229`; `diary.md:10`.
- **What is wrong:**
  - The brief says the recipient set is "membership at send time, and members who leave or are removed before reaching a state **drop out of the aggregate requirement**."
  - The builder implemented exactly that: `receipt()` excludes later joiners via `joinedOrdinal`, and leavers drop out. The diary records the same design.
  - The grader quoted only the first clause and filed the behaviour the second clause mandates as a defect.
  - The RFC adopts the grader's reading and explicitly overrides the diary ("leaving must not magically count as reading … follows the grader's finding, not the earlier diary's provisional interpretation"). The "provisional" note (`run-log.md:34`) was about what a *removed member* sees in retained history, which is a different question.
- **Evidence:** `diff` of the packet's frozen `instrument/social-messenger.md` against the checkout's brief is empty; the clause sits at `:505-507` in both.
- **Proposed change:**
  - Delete the Clique-specific rule.
  - Change the §8 row to "leavers drop out (brief:505-507); later joiners never count".
  - Keep the generic "the schema declares its recipient policy".
  - Record d-01 as a grader misreading in the calibration record; O2's 86 was docked for it.

#### F2 (High) — The read gaps came from the platform's own write fence; the RFC treats them as external and fixes only the symptom
- **Where:** RFC §1 row 2 (`:43`), §4 (`:107-128`), §8 row 4 (`:214`).
- **How the fence works (code):**
  - `local-query.ts:82-94`: `pending()`/`blocked()` fence fallback whenever a predictable pending write's predicted tables intersect the query's tables.
  - `:167-174`: a withheld read that is also fenced goes to `recover()`, which yields `loading`.
  - `:213`: before the partition is current, `possible = null`, so *any* predictable pending write fences.
  - `read-observation.ts:47-52` and `contract.ts:46-49`: retention of the previous answer ends at "any local commit".
  - `react.tsx:175-179`: `usePage` returns `items: []` while the first page is loading.
- **What happened in the run:**
  - The loops happened "while local mutations settled" (`run-log.md:29,31`).
  - The diary names the cause: "a thread sorted on a different index from its sync horizon produced transient loading" (`diary.md:23`). Receipt shaping over horizon-limited `deliveries` "caused local unavailability" (`run-log.md:46`).
  - `inbox`/`inboxLocal` composed `typing: typingFor(.chat)` (`schema.q:234-236`), and `acknowledge` writes `members`, which `messageCard.receipt()` reads (`schema.q:223-230, 289-302`).
  - So every throttled keystroke, acknowledgement and send fenced whichever of those queries the device couldn't complete. `usePage` went to `[]`, rows unmounted, and per-row acknowledgement effects fired again — a self-feeding loop.
  - The builder's lasting fixes were query-side: ordinal alignment, bounded member progress, and the `inboxLocal`/`inbox` split (`src/useInbox.ts`).
- **What the docs and tools say:**
  - The card says the opposite of the code. `reads.rs:64-66`: "An unavailable ordinary device read asks the server while online even with pending writes." That holds only for writes to unrelated tables (`test/prediction-routing.test.mjs:125-132`); for intersecting writes the read stays `loading` (`:89-104`).
  - `check` summarizes mutations that can't predict (`bind/residency.rs:350-372`) but no queries whose whole answer is withheld.
- **Proposed change:** Name the mechanism in §4, and rank *preventing* gaps above *surviving* them:
  - (a) Correct `reads.rs:56-66` and `CLIENT-AND-OPERATIONS.md:1039-1043`.
  - (b) Add a `check` note for a device query whose whole answer needs the server because of one component or an order/horizon mismatch. Mirror LLP 3000.017's `N_EPHEMERAL_SERVER` (`3000.017:283-293`), with the rewrite "split it into its own query".
  - (c) In §6, record that 3000.017 removes the largest fence source, since ephemeral writes bypass the outbox and prediction (`3000.017:346-353`). Re-measure the §8 row after it lands.
  - Keep the §4 UI rules as written.

#### F4 (Medium) — §2/§3 miss the one reproduced SDK gap: nothing lets an app see its pending or failed intents
- **Where:** RFC §2 (`:60-63`), §3 (`:87-100`), §8 (`:227-229`, "no … settlement wiring").
- **Evidence:**
  - `src/Pending.ts` (105 lines; not in the ledger).
  - `essay.md:15`: "a durable pending-intent view … even when there was no predicted row".
  - `run-log.md:97`.
- **Code:**
  - `Queued` carries `op`, `args`, `new_ids` and `observed_seq` (`local-types.ts:3-17`), but `queued()` is internal (`local.ts:963`).
  - `App` exposes only `client/auth/ready/mutate/close` (`app.ts:38-47`).
  - `last` updates only for the latest run (`react.tsx:240`).
  - A refusal withdraws the predicted rows (`CLIENT-AND-OPERATIONS.md:842`).
  - The paved form tells apps to keep IDs themselves (`:886-889`).
  - The receipt window is 256 (`writes.ts:10`, `web.ts:623`).
- **What is wrong:**
  - Composition cannot meet §3 or §8. After reload, an app cannot list queued intents that have no predicted row.
  - A queued send refused on reconnect loses its text.
  - In both starters' composers, a refusal of any send other than the latest never surfaces.
  - The builder rebuilt the view in localStorage, and maps an unknown or evicted receipt to "failed … not queued" (`Pending.ts:42-48`). That invites the duplicate resend §2 warns about.
  - Correlating a pending item with its row is already solved for predicted rows: row IDs are minted at admission (`C&O:924`). The builder's duplicates came from rendering its journal beside the predicted rows (`diary.md:33`).
- **Proposed change:** Add a read-only view over the existing outbox, e.g. `usePendingWrites(op?)` returning `{id, op, args, state, reason?, why?}[]` per account and backend.
  - Keep entries until `observed_seq`, so the hand-off to the replica row has no gap.
  - Keep a refused entry's args until the user dismisses it (session-scoped at first).
  - No new queue and no retries.
  - Relax the §8 "no settlement wiring" criterion only once this exists.

#### F5 (Medium) — Several "agent errors" were taught by the platform, and one is misattributed

- **What is wrong** (all present in the published 0.4.2 docs the builder installed):

- **Proposed change:** Re-attribute these in §1, and aim the fixes at those docs and aliases (increment 1).

#### F6 (Medium) — §5 targets read-visibility; the evidence's cost was delivery pumps, and its gap rule breaks the brief
- **Where:** RFC §5 (`:132-148`), §8 (`:215`).
- **Evidence:**
  - `src/Chat.tsx:39-63`: one live `usePage(api.thread)` per chat, just to send `delivered`.
  - `run-log.md:40`: the "seen" set was moved above the transient inbox rows to stop repeated acknowledgements.
  - `run-log.md:93` and `final-report.md:43`: deferring delivery acknowledgements until acquisition finished took cold acquisition from 69.9 s to 5.6 s at 100 conversations. The ledger omits this.
  - Brief `:500-502`: read means the recipient "viewed the conversation".
  - Brief `:769-772, 800-803`: opening a conversation clears unread on the other device.
- **What is wrong:**
  - "Do not advance across unloaded or unread gaps" (`:139-142`), as a default, would keep older unloaded messages unread after the user opens the conversation. That fails M8 acceptance 6.
  - Deduplication across remounts falls out of the schema if the acknowledgement writes only held per-member progress: the pending write then predicts the value the pump compares against. Writes to horizon-limited `deliveries` queue without a row, so they don't.
- **Proposed change:** Make §5 a schema-and-recipe section, with no SDK hook:
  - predictable per-member ordinal progress;
  - one delivery observation, started after `useAcquired()`;
  - "read" when the conversation is open and foregrounded;
  - gap-aware watermarks only for apps whose declared policy is per-message visibility.

#### F7 (Medium) — Lifting the view-once viewer drops the revocation coupling `useAsset` gave; the typing hand-off is sound
- **Where:**
  - RFC §6 (`:171-178`).
  - Code: `assets.ts:106-134` returns a once-view handle as a plain object URL. `local-assets.ts:69-75` revokes only *retained* handles on purge and sign-out.
  - Evidence: `src/Conversation.tsx:66,184,316-326` — the builder lifted `client.asset` + `revoke`, and the existing API was sufficient.
- **What is wrong:**
  - No media extension is needed, so §6's contingency and §9's open question can close.
  - But a viewer lifted above the list outlives its row. After a delete, expiry or membership loss, the bytes stay on screen. The brief's revocation ruling forbids rendering revoked content once the client has synced the revocation (`social-messenger.md:65-73`).
- **Proposed change:** The canonical viewer observes its message row.
  - It closes and revokes on `data: null`, `denied`, tombstone or expiry.
  - It does not close on `loading` (F2's gaps).
  - Sign-out is already covered by the account remount (`react.tsx:17-26`).
- **Typing:** 3000.017 already specifies outbox/prediction bypass, reads as their own query, and `N_EPHEMERAL_SERVER`. §6 needs nothing more.
- **Sequencing:** `origin/sb4/eph-integrate` rewrites `useTrackedMutation` and the fallback path, so land hook work after it.

#### F8 (Low) — Some proposals already exist
- **Where:** RFC §3 (`:94-96`), §4 (`:123-125`).
- **What is wrong:**
  - Same-ID/same-arguments retry is already enforced (`contract.ts:102-110`, `E_ID_REUSED`).
  - A missing aggregate is already `loading`, never zero (`reads.rs:175-176`); what's missing is the query split (F2).
  - The web starter's `markRead` is a deliberate wall-clock, non-predicting demo (`apps/chat/snapback/schema.q:116-131`). Don't present it as the receipt recipe.
- **Proposed change:** Remove these from the work list.
