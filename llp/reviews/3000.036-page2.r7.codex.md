The blocker is in [partition.rs:241](/home/ccheever/projects/sb4-w10-page2/snapback4/crates/snapback4-core/src/partition.rs:241): an old image is treated as previously disclosed whenever it is opened and has no pending entry. That does not establish that it ever became live.

**Concrete counterexample:** Insert a publicly synced row at time `0` with `opensAt = 100` and `expiresAt = 1`. It receives no pending entry because its lifetime is empty. A snapshot contains no row. Call `sweep_expired(100, 10)`: `opened` now returns true, partition accounting logs a public `del` containing its id, and incremental sync delivers that deletion. This violates §§1.1 and 6’s promise that never-opened rows produce no device event.

The same defect affects missed publication: insert with opening `100`, expiry `150`, then advance at `200`. [time_audience.rs:81](/home/ccheever/projects/sb4-w10-page2/snapback4/crates/snapback4-core/src/engine/time_audience.rs:81) removes the expired pending entry without publication. A subsequent sweep again misclassifies the row as previously disclosed.

**Focused fix:** Preserve whether a timed row was actually published until physical removal, and use that evidence when constructing revocations. Exclude intrinsically empty lifetimes as well. Simply filtering old images with `live(now)` would break required revocations for previously delivered, now-expired rows.

Add regressions asserting no logged or delivered deletion for both counterexamples, while retaining deletion delivery for a row that opened successfully before expiry.
