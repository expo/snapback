**Fixed — Grok High / Astra Medium, §2.1a. `online only` is neither partial nor fully synced.** "Not fully synced" now covers both, the kind is left out of the horizonless walk, its raw puts are ignored, and a read is unknown even on a hit. The fully synced kind stays on that walk.

## 2. New defect

**High — §2.1a. A repost deleted before its insert page is served is not removed through the source.**

A repost event id is minted. It is not the repost id, and the repost row does not store it (`timeline.q`, `bind/timeline.q`). `log_events::del` and a put rewritten by `expand_joins` both deliver `data: None`. Snapshot catch-up deletes by `(table, id)` only (`snapshot.rs`: a `del` is `staged_delete`). Staging has no `byActorPost`. That index reads the published partition, which catch-up has not published.

Probe: reposts floored. The snapshot page after the insert stages repost `S` and event `F`. Unrepost `S` before the catch-up page that carries the insert is served (`head` is past the unrepost). `expand_joins` rewrites `S`'s put to `del S` and `F`'s put to `del F`. `del F` is the only entry that names `F`. Revision 9 ignores it. `del S` removes the staged repost and cannot name `F`. Publish holds `F` with no source. `feedPosts[F]` is a partial hit, which §2.1a says may be returned. Server-side, `F` is gone.

The same hole survives a full catch-up if the repost is recreated before that page, with a new event `G`. The normalized source image is a put of `S` paired with `G`, not a deletion. Putting `G` retargets `byActorPost` and leaves the old row (`memory.rs` `put`). The ignored `del F` was the only instruction to delete that id. After `S`'s later source delete and the recreate's put, `F` is still stored. `byId` returns it.

Snapshot omission works when the page's own transaction never sees `S`. The live stream works after publication, because `byActorPost` can see the held row. Catch-up, which is the path §2.1a assigns this repair to, does not.

**Smallest change:** state both of these, and no id-lifetime rule.

- A raw `del` carries no kind. If that id is held or staged, the stored `repost` flag decides: apply it when the kind is fully synced; do not apply it when the kind is not. A `del` of an id that is not held is a no-op. This keeps original removal working when reposts are floored (`posts` fully synced), and it keeps Astra's reused-id case from erasing the newer row.
- For a kind that is not fully synced, applying a source image makes the staged or held events for that source key exactly the paired row, or nothing. Match `(actor, post, repost)` in the store being written, including snapshot staging, and delete the previous id before putting the new one. Do that before `staged_delete` of the source. Absence at `head` does not remember a minted id; the device already has it on the staged row.
