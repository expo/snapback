## B. New findings introduced by round 4

1. **MATERIAL — the exact-source activation verdict is not bound to the authorization artifacts the host actually activates.** The observer's green `governedUpdateVerdict` binds the event's `after` OID, comparator/input versions, event-input digest, and quarantine head; activation then obtains a verdict for the bundle's “exact source OID” from target-owned configuration (`llp/0234-visibility-override-governance.rfc.md:531-547`). Nothing in the verdict or activation contract binds that OID to the staged schema hash, function-bundle hash, generation-input hash, or authorization-program digest. Saying that a bundle/request field cannot supply the OID protects input custody but does not prove that the staged bundle was derived from that OID. The current host already identifies the artifacts it activates by `schema_hash`, `bundle_hash`, and `inputs_hash`, recomputed from the schema/functions pair (`src/auth/mode.rs:67-118`, `:331-367`; `src/local.rs:4275-4303`). Without a signed OID → deployment-identity binding, a green verdict for benign commit C can be paired at the build/deploy boundary with a different but internally valid authorization bundle D carrying a remotely unobserved widening; all four stated activation checks can pass because the host has no predicate relating D to C. **Resolution:** have the protected observer or a separately custodied builder attest the exact `DeploymentIdentity` (and any separate visibility-authorization program digest) derived from the judged `after` OID, include those digests in the signed green verdict, and require the host to recompute and deep-match them from the staged artifacts before activation. Add an Acceptance 4/25 negative fixture that keeps the green OID/verdict fixed while swapping any staged schema, function bundle, governance baseline, or authorization-program input; every swap must refuse before activation.
