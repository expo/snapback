## 15. PAGE2: ordinary exact memberships, row ids and parent owners

Wave 10 showed that §14's cap requirement excluded the ordinary membership
schema it was meant to serve:

```quarry
table members:
  parent: parents
  principal: principal
  unique parent, principal
  read <- .principal = viewer

table documents:
  owner: principal
  parent: parents
  read <- .owner = viewer or exists members[.parent, viewer]
```

`unique parent, principal` proves that the rule's point probe has at most one
witness for one document and caller. It does **not** prove that a principal has
only finitely many membership rows: fixing `principal` leaves arbitrarily many
`parent` values. PAGE2 therefore does not call this source range statically
capped. It admits the exact total-unique witness and runs the inverted
`members where .principal = viewer` discovery under the ordinary read meter.
The §14 discovery fence already gives the required failure semantics: until
the source range is known complete, no owner or membership target row is
emitted; an `examined`, `index_entries`, `rule_probes` or discovery `steps`
cut, unknown device coverage or incomplete horizon returns an empty
`complete: false` page with no continuation. `heap_bytes` exhaustion retains
the existing `E_BOUND` read refusal. Every
distinct value, evaluated prefix and dynamic lane is sized and charged through
§14's heap ledger before allocation, so an uncapped population cannot allocate
past the request ceiling. Retrying a read-meter cut may complete under a larger
budget or smaller population. It cannot skip an undiscovered lane or turn
partial discovery into a negative authorization fact.

This admission proves a safe plan, not completion for every population size.
For a caller with `K` memberships, discovery and target-head work grow with
`K`; once a read ceiling is crossed the fenced result is empty and incomplete,
so a sufficiently large audience can be temporarily unavailable under the
ordinary budget. A cap is therefore optional for correctness and remains the
product's availability bound. If an app must guarantee that the page completes
within a chosen budget, the writer that grants memberships must enforce a cap
on the fixed enrollment group (for example `principal`). A writer allowed to
grant arbitrary memberships controls `K`; point uniqueness alone does not.

A declared cap is a separate static proof only when all of its grouping
columns are fixed by the discovery scan and null exemption cannot apply. Any
maximum is admissible: a cap above the request's examined ceiling may still
cut safely under the preceding rule. A cap grouped by `parent` does not bound a
scan that fixes only `principal`; a cap grouped by `principal` does. A fully
pinned total unique remains the one-row case. Planner, bound-IR validator and
Lean emitter use these same alternatives:

1. the rule probe selects the intrinsic `id` or one declared plain unique,
   and every other probe component is an exact necessary equality;
2. either that selected point is total, the discovery itself is a fully pinned
   total unique, or a declared cap covers the fixed discovery prefix;
3. the fixed pins decide the source read rule true, and all existing index,
   key, label, descriptor, total-predicate and shared-position checks pass.

A nullable unique is not a total point proof. It can still use PAGE when an
applicable cap bounds its discovery group; a null in the selected point keeps
the ordinary result of no witness. If that cap is the only missing condition,
`N_NEVER_COMPLETE` gives the exact declaration to add, using the source's
fixed non-null columns: for the usual shape, `cap 50 by principal`; with no
fixed group, `cap 50`. The note also says that a cap is a stored write
constraint: adding it can refuse existing adoption or later inserts once that
group holds 50 live rows (and physically retained rows where cap validation
requires them), so the author should add it only when it is a real product
limit. The note is withheld when a cap cannot repair the
shape, including multiple row-dependent components, a hidden source, a
non-exact or ambiguous probe, a multi-hop target, incompatible ordering, or a
physical key bound. It must not prescribe code that still cannot plan.

The varying target column may now be the target row's own `id`:


**Related:** [LLP 3000.036](./3000.036-what-the-app-farm-asks-of-the-rule-language.rfc.md) (app-farm rule-language findings), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) §§17–18 (logical lifetime, sync and acquisition), [LLP 3000.014](./3000.014-a-child-reads-through-its-parent.rfc.md) (captured parent lifetime), [LLP 3000.015](./3000.015-shared-baseline-for-snapback5.spec.md) §§1–3 (physical work, caps and expiry), [LLP 3000.019](./3000.019-what-the-builder-still-wrote.rfc.md) §3 (server clocks and read deadlines), [LLP 3000.035](./3000.035-quarry-semantics-in-lean.plan.md) §5.2 (executable semantics), wave-10 evidence 005, 015 and 070

## 0. Summary

Three wave-10 applications wanted a row to become readable at a server-time
boundary. Quarry correctly refused `now` in a table rule, so each builder kept
the deadline in mutations. That protects a write; it does not provide timed
disclosure. An application job which flips `published` is easy to forget and
briefly gives a device either the secret too early or a stale negative answer.

This RFC adds one row-lifetime declaration beside `expire at`:

```quarry
table teams:
  name: text <=80
  read <- exists members[.id, viewer]
  insert <- allow
  sync

table members:
  team: teams
  principal: principal
  unique team, principal
  immutable team, principal
  cap 200 by team
  read <- exists members[.team, viewer]
  insert <- created teams[.team] or exists members[.team, viewer]
  delete <- .principal = viewer
  sync

table announcements:
  team: teams
  opensAt: time ?
  closesAt: time ?
  secret: text <=4000
  by byOpening: opensAt
  by byExpiry: closesAt
  read <- exists members[.team, viewer]
  insert <- exists members[.team, viewer]
  update <- exists members[.team, viewer]
  delete <- exists members[.team, viewer]
  not before .opensAt
  expire at .closesAt
  sync
```

A null opening means immediately visible. A non-null opening makes the row
logically absent until the server clock reaches it. Before then, reads, rule
probes, membership witnesses, aggregates and sync see no row. The server stores
the row and caps count that physical occupant, but no secret payload crosses to
a device. At the boundary an ordinary request, query, sync, or held change poll
advances due openings transactionally and publishes an ordinary commit; no
application job exists. A device applies that commit and its server-clock sample
atomically. Its wall clock and estimated server clock can ask the server to
refresh, but can never authorize the payload.

`not before` is read lifetime only. A write deadline remains a `require` in the
server mutation. The compiled recipe says both facts and is tested as Quarry.

## 1. Language and schema

### 1.1 Declaration

```
not before .column
```

There is at most one declaration per table. The column must be a local `time`
or `time ?` column and the table must have an index leading with it. An optional
null means no lower lifetime bound. `not before .parent.opensAt`, arbitrary
expressions and `now` in read/write rules remain refused.

The checked schema stores the column as `not_before`, separately from `expire`.
It is part of schema equality, hashing, generated metadata and successor
classification. A schema using it requires device capability
`time-audiences-v1`; an older device is refused at the handshake before a page
is materialized or applied.

`not before` may be used with `expire at`. They form the half-open lifetime
`[not_before, expire)`. The compiler accepts an end before the opening: that row
never becomes live, and ordinary expiry cleanup may remove it after the end.
This is useful for a revoked scheduled item and does not disclose either time.

### 1.2 First supported composition

The first implementation covers ordinary stored tables and a stored table used
as a membership audience. It supports public, one principal, and one group sync
audiences, with or without a sync horizon. It rejects these combinations with a
located diagnostic and an `online only` or explicit-table recipe:

- union sync audiences, whose current proof already excludes lifetime scopes;
- `read through`, because a child would need the parent's opening captured and
  re-opened under the same boundary transaction;
- maintained aggregates or maintained columns whose source, target, or
  row-key member table has an opening, because their stored values would
  otherwise include a hidden source or require a boundary-time recount;
- private `written by` fields when the table's read rule performs a row probe.
  Opening-time owner projection runs as system work and cannot borrow an
  unbounded, data-dependent authorization walk. Keep that read rule to local
  field comparisons, declare the fields `readable by audience`, or move the
  probed grant into an ordinary disclosure table;
- timelines, row-keyed views, feeds and ephemeral tables.

These refusals preserve the completeness contract for every accepted program.
They are not silently
server-class forms. Later support must specify captured openings and boundary
recomputation before deleting a refusal.

## 2. One lifetime predicate

For a stored row `r` at authoritative server time `t`:

```
opened(r, t)  := r[not_before] is null or r[not_before] <= t
unexpired(r,t):= r[expire] is null or t < r[expire]
live(r, t)    := opened(r,t) and unexpired(r,t)
```

Every logical read uses `live`: point and unique lookups, scans, search,
existence and rule probes, count-like absence, reference checks, sync snapshot
selection, group acquisition and query completion. The system principal does
not bypass this read lifetime. Internal write resolution, cap accounting,
boundary advancement and physical cleanup may inspect stored rows explicitly.
If the private ledger still owes an overdue opening, that row remains logically
inactive until its publication transaction removes the entry. A query which
encounters such an entry is unavailable rather than certifying its absence.

A **future occupant** is a physical row which is unopened and unexpired at the
pinned clock. Storage may visit it under the existing bounded physical guard,
then refunds/excludes its row from the public examined, step, byte and heap
meters. Its key never becomes a public cursor position, authorization witness
or PAGE2 discovery/lane position. Points, searches, probes and scans therefore
produce the same public answer, cut and meter before the boundary in paired
worlds differing only by future occupants. A physical-guard refusal remains
the store-internal `E_STORE_MEMORY`, with no continuation containing a future
position. The same rule runs in both device stores, including across schema
adoption where a device may already hold a row which the new lower lifetime
makes future.

Only an unopened, unexpired witness receives the lower-lifetime refund from the
shared authorization allowance. An already expired rule witness keeps the
ordinary bounded authorization-walk treatment. This does not revise the upper
expiry contract: reads and scans may step over and refund expired candidates as
specified by LLP 3000.007 §20.24.6, while point and witness probes retain their
declared probe cost.

The implementation has one helper for this predicate in the checked schema.
The interpreter, device and Lean model use it; individual readers do not invent
their own comparison. `expired` continues to mean only the upper boundary.
A future row is not expired and must never be selected by `sweep_expired`.

## 3. Writes and boundary transitions

### 3.1 Write authority before opening

A future row is absent to application reads, including its author. Server write
target resolution may still find it without granting read authority, as hidden
target updates do today. Its update/delete rule decides the old and next stored
images. A returned value, conflict image or diagnostic never includes the row
unless the resulting row is live and its read rule admits the writer. Device
prediction never reads or writes a future row; a write targeting a `not before`
table is server-class and queues while offline. Device reads remain local over
the server-published subset.

This lets an organizer change, cancel or delete a scheduled secret. It does not
turn `not before` into write authorization. A deadline such as "picks close at
draftDeadline" remains:

```quarry
mutation setPick(event: events, team: teams, robot: text <=80):
  e = events[event] ! else NOT_FOUND
  require now < e.draftDeadline else PICKS_CLOSED
  upsert picks[event, team] { event, team, robot }
```

### 3.2 Image transitions

Partition accounting compares stored images under one server time pinned for the
whole writer transaction. The server derives it as the maximum of its current
clock reading and the durable lifetime floor left by prior transactions. A
backward host-clock step therefore cannot make a live row future again. The
same pinned value governs rule `now`, row liveness, event construction,
advancement and the response clock sample:

| old image | next image | delivery effect |
|---|---|---|
| absent/future | future | none; update the pending opening |
| absent/future | live | ordinary `put`/membership `join` |
| live | future | ordinary `del`/membership `scope` |
| live | live | ordinary changed-image accounting |
| future | deleted or expired | none |
| live | deleted or expired | ordinary revocation |

Changing audience columns while future changes only the eventual current
audience. Changing or deleting a future membership grants and revokes no group.
Moving a live membership into the future revokes the group immediately; when it
opens, a new join and acquisition establish authority from that boundary.
An ordinary future-to-future write can still advance the existing global commit
sequence and table invalidation at write time. That is the ordinary private
write timing channel; it carries no opening timestamp, row identity, audience,
or payload to an unauthorized device.

The log never receives a `put` containing a future payload. This is an invariant
at event construction, not only a serve-time filter. Serve-time re-fetch and
read-rule checks remain the second disclosure fence.

## 4. Advancing time without an application job

The store keeps a private pending-opening index keyed by `(at, table, id)` and
a durable monotonic lifetime floor. Both are engine metadata, never schema
rows. Ordinary insert/update/delete commits update the index transactionally
with the row and partition accounting. An insertion at or before the pinned
floor is live in that ordinary commit and never enters the pending index.
Consequently new work cannot sort ahead of an advancement cursor. Schema
adoption builds the index from stored rows under the writer lock. At every
committed publication boundary, the durable floor is at least the opening key
being removed. Rebuild preserves overdue unpublished entries unless the
generation barrier itself establishes those rows in a replacement snapshot.

`advance_openings(now)` runs under an ordinary writer transaction with the same
pinned monotonic time. The first implementation selects one due entry in key
order per invocation, re-reads its current row, and:

1. discards a stale entry when the row was deleted or its opening changed;
2. discards an entry whose upper expiry has already ended, without a put;
3. accounts a current due image as the transition `future -> live`, including a
   membership join and acquisition authority;
4. deletes the pending entry, advancing the durable cursor even when the entry
   is stale or never live; and
5. when any logical table changed, records one system `time` commit and appends
   its events atomically.

Each invocation uses the ordinary bounded request meter plus fixed event-count
and serialized-event-byte limits. These are internal limits, not public
`Ceilings` and not charged to the application query. Schema admission proves an
individual opening fits an empty invocation. Its static reservation includes
the base-row decode even when no event is emitted, plus the sync, owner-delivery
and membership-event steps, even though the original future write emitted
nothing. A timed table with private fields is admitted
only when its read rule is probe-free, so opening-time owner projection has no
witness scratch or shared authorization walk. Timed rows without private fields
may still use ordinary read witnesses. Membership publication emits at most one
join per dependent synced table. The audience's required unique
group-plus-principal key proves there is no distinct physical predecessor to
scan. Runtime accounting rechecks the event envelope. Any accounting,
serialization, log append or commit failure rolls back its events, floor and
pending-entry removal together. The compact logged boundary events therefore fit the opening publication
envelope. Expanded group acquisitions have a separate delivery bound and
recovery rule, below; this admission does not bound the current group contents.

Queries, mutations, sync and `/changes` invoke a fixed small number of bounded
advancements before or as they observe state. An exhausted system ledger cannot
turn a logical page into a partial prefix. A read which encounters a row whose
due ledger entry remains behind its pinned time is unavailable rather than
falsely complete; a subsequent request continues with the next ordered entry.
The insertion rule above guarantees that each invocation reduces the old
backlog even under continuous writes. Hosts may eagerly run more invocations,
but correctness never depends on an application job.

The held changes loop privately waits until the earlier of its ordinary
deadline and the next stored opening. On that wake it advances a bounded batch.
It returns only if the resulting commit changes something visible to that
subscriber; stale entries, revoked rows and rows with `expire <= not_before`
produce no event or invalidation, so their private wake resumes the same held
poll until its public deadline. The reply never includes the private
next-opening timestamp, count or table.

An opening that can change a watched result publishes the same ordinary table
revision invalidation as a writer commit. This applies to positive and negative
pages, existence probes, aggregates and sync; it is not a special negative-read
signal. The ordinary global changes sequence and table-revision invalidation
may therefore reveal, at or after the boundary, that this table published some
opening even to a subscriber who receives no payload. That table-level timing
channel is accepted, just as an ordinary private write advances the global
sequence; payload, row identity, audience, count and the scheduled timestamp
remain private. Before the boundary the client gets no timestamp, early
refresh hint or wake signal. `QueryOutcome.next_expiry` remains an
upper-lifetime/authority deadline and never carries a hidden row's opening. A
never-live or otherwise invisible pending entry produces no public commit,
sequence, invalidation, availability change or held-poll reply at its opening.
Removing stale private ledger metadata commits only the SQLite transaction; it
does not allocate an application sequence or table revision.

## 5. Sync, completeness and device clocks

A snapshot selects only rows live at its pinned server time. Incremental sync
receives the boundary commit like any writer commit. A membership opening's join
is expanded only from that commit, so content before the join cannot establish
premature authority. A revoke/change in the same boundary transaction is
accounted from the final stored image.

A compact join can acquire a horizon-free group whose current payload exceeds
the existing 16 MiB HTTP reply ceiling. Publication admission bounds the logged
join, not that expansion. Join expansion reads at most 64 rows per batch and
admits the schema's transient decode reservation before each batch. Across all
joins in the reply it retains at most 8,192 events and cumulatively accounts
actual row and key heap, event slots, and conservative serialized bytes under
the ordinary 16 MiB heap and wire ceilings. Delivery keeps the whole-commit
contract: a resource refusal discards the private reply and returns `E_BOUND`,
without events or an applied acquisition. Reducing a stream page to one event
cannot split that acquisition; at `limit: 1` the refusal preserves the request
watermark and sync identity and includes the existing `snapshot: true` repair.
The client then restarts a paged snapshot, which walks current rows individually
and stages them under the ordinary snapshot fence before publishing coverage.
A direct protocol caller follows the same repair.
No future payload, partial authority, or new completeness claim is published
from the refusal. A single row which itself exceeds the wire ceiling retains
its ordinary undeliverable-row refusal. This recovery uses the existing sync
protocol and requires no product cap or new wire message.

PAGE2 discovery and target reads use that same pinned predicate. A future
membership row is absent from discovery and cannot create a target lane or
group authority; a future target row is absent from an admitted lane. The
merged query watches both its source membership tables and target tables, so a
visible source or target opening invalidates it at the boundary. If relevant
advancement for either side still has due work, the merged page is unavailable
or `complete: false`; it never certifies absence from a partially advanced
source set. This is the lifetime composition rule for every admitted PAGE2
membership shape.

The server response's `now`, the boundary events and the watermark stage and
publish in one device transaction. The device keeps the existing monotonic
authoritative server floor for lifetime decisions. It must not use the supplied
request clock, the host wall clock, `issuedDeviceNow`, an offset estimate or a
timer to make a row appear. A timer may only initiate a request. Since future
payloads are absent from the device, there is no local bypass.

Before a boundary commit exists, a complete local negative answer is complete
at the device's applied server position. Once the device learns a later server
position, it applies the boundary events before publishing that position. A
partial page, missing acquisition, pending due batch, or learned-but-unapplied
boundary is `complete: false`/unavailable under the existing typed rules. No
clock estimate upgrades coverage.

Both memory and SQLite device stores must pass the same cases: no pre-boundary
payload bytes, opening delivery, restart, clock rollback/advance, group join,
reschedule later (revoke), reschedule earlier (put), and deletion before opening.

## 6. Caps, uniqueness, expiry and deletion

Caps retain their existing live-row rule for upper expiry: a saturated physical
counter may scan past unswept expired occupants and admit the freed slot. A
future, unexpired row is different: it consumes its whole-table and group caps
from insertion until it expires or is physically deleted.
This prevents scheduling unbounded secret payloads behind an invisible logical
population. Cap checks never reveal whether the occupant is future; an
unreadable collision keeps the ordinary generic refusal.

Uniqueness is also physical. A future row reserves its keys and may be targeted
by an authorized upsert without becoming readable. Logical existence/count
queries exclude it. A membership audience already requires a unique index over
its complete non-null group-plus-principal key. The opening row owns that key,
so predecessor absence is constant work without a new product cap. SQLite's
multiple-null unique behavior does not weaken this proof because a null group
or principal never forms an audience join.

`sweep_expired(now)` consults only `expire at`; it never treats unopened rows as
expired. When the expiry is due, deletion removes the row and pending-opening
entry in one transaction. Deleting or expiring a never-opened row creates no
device event, because no device could hold it. Deleting an opened row keeps the
ordinary revocation and retention semantics.
Expiry cleanup pins the authoritative floor but commits its physical removals
before attempting the next opening. A refused opening therefore cannot wedge
the cleanup that could make later progress possible.

## 7. Formal and generated semantics

The Lean table schema gains an optional lower-lifetime field. Its `opened`
projection filters every logical row lookup, scan, probe and write result at
the case clock, while physical write lookup and uniqueness remain over stored
rows. The emitter includes `not_before`; the unsupported-fragment report must
never silently erase it. The existing Lean harness strips `expire at`, so this
formal fragment does not prove lower/upper lifetime composition.

The difftest AST and generator produce null/past/future/equal-boundary openings,
opening plus expiry, membership witnesses and caps. Its first formal fragment
has no prelude or separately seeded clock: rows are seeded and evaluated under
one operation clock with openings at null, clock-minus-one, clock, and
clock-plus-one. That fragment proves the pure `live(now)` projection without
claiming to model the durable pending ledger or its bounded publication loop.
Native runtime, simulator and both device-store lifecycle suites cover
lower/upper composition, publication, rescheduling, restart, hostile device
clocks and server-floor rollback.

## 8. Compiled recipe

The `time` and `recipes` cards carry one executable timed-disclosure recipe. It
states separately:

- use `not before .opensAt` to withhold a row until server time;
- use a mutation `require now <|>= deadline else CODE` to authorize a timed
  write;
- a nullable opening means immediately readable, and `expire at` is the
  independent upper boundary;
- a device timer refreshes; it never unlocks secret data.

Every Quarry block compiles in the guide suite. There is no job/published-flag
workaround recipe for this admitted shape.
