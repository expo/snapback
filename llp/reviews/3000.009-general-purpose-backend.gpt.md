## Verdict: SOUND WITH MAJOR ISSUES

Reviewed commit `187d98b1f417d30db9693a74192e89fbe671ca15` read-only. Runtime reproduction and performance results are **UNVERIFIED independently**; the counterexamples below follow from the proposed contracts and source inspection.

## Direction assessment

I would retain one interpreter, backend-specific access batching, generic managed storage, and optional typed projections. This preserves Snapback’s central advantage: the same data semantics across server and device. The evidence justifies trying batching before SQL lowering. It does **not** establish that storage layout is irrelevant: the experiment uses small, warm workloads, and its relational comparison omits authorization, metering and completeness. ([Experiment:89](../../snapback4/experiments/postgres/README.md:89), [Experiment:102](../../snapback4/experiments/postgres/README.md:102))

The single commit order is sound as an initial protocol. The prototype locks the head before serialized execution, advances it transactionally, and commits the operation’s bookkeeping together. I found no reason to replace that protocol before measuring a realistic workload. Concurrent execution with ordered validation remains compatible with this direction. ([postgres/store.rs:52](../../snapback4/crates/snapback4-core/src/engine/postgres/store.rs:52), [postgres/store.rs:144](../../snapback4/crates/snapback4-core/src/engine/postgres/store.rs:144), [postgres/mod.rs:200](../../snapback4/crates/snapback4-core/src/engine/postgres/mod.rs:200))

The application-led comparison is the right instrument. The managed-service target is compatible with this architecture, but its isolation, operational feasibility and cost remain **UNVERIFIED**: §14.5 deliberately leaves those decisions to a child design. A–C can establish its foundations; they do not yet constitute its delivery plan.

## Major issues

### 1. Blocking — Candidate filtering does not establish SQL authorization
**RFC §6.2; blocks D’s proposed automatic candidate authorization.**

The contract says SQL returns managed IDs, then the engine returns the visible rows. But SQL has already read unfiltered projections before that check. ([RFC:431](../../llp/3000.009-general-purpose-backend.rfc.md:431))

A counterexample is a query that returns an always-visible marker row **only if a protected row satisfies a secret predicate**. Every returned row passes authorization; whether the marker appears discloses the secret. Ordering visible IDs by a hidden aggregate creates the same problem. `complete: false` does not prevent either disclosure.

This exceeds the acknowledged responsibility of the *declared-channel* form: candidates are presented as automatically authorized.

**Resolution:** Authorize every input that can influence candidate selection, ordering and errors before SQL evaluates it—for example, through a rule-proven partition or authorized input relation. Otherwise classify the operation as an explicitly reviewed disclosure channel. Automatic candidate authorization needs a restricted, demonstrably safe SQL surface.

### 2. Blocking — Durable action authority and protected result collection need explicit contracts
**RFC §§5.1–5.2; affects A.**

The existing request record retains a principal but no originating authorization expiry or revocation identity. Claiming queued work mints a new session from that principal; revoking a principal deletes current sessions. Thus queued work can recreate authority after session revocation unless A changes the durable model. ([engine/actions.rs:12](../../snapback4/crates/snapback4-core/src/engine/actions.rs:12), [engine/actions.rs:129](../../snapback4/crates/snapback4-core/src/engine/actions.rs:129), [identity.rs:458](../../snapback4/crates/snapback4-core/src/identity.rs:458))

Result collection has a related gap. Current lookup checks the original principal, and the HTTP response returns the stored result. Neither establishes current permission to its underlying data. ([engine/actions.rs:116](../../snapback4/crates/snapback4-core/src/engine/actions.rs:116), [host actions.rs:22](../../snapback4/crates/snapback4/src/actions.rs:22))

The RFC’s advice about results “holding protected rows” is too narrow for its own example: a document summary is protected derived content despite having type `text`. A live session of the same principal does not prove continued document access.

**Resolution:** Persist a revocable authority binding and deadline, with explicit service-authorized work distinguished from borrowed caller authority. Define result-collection authorization for derived content, or store protected results in managed rows and return IDs. These belong in A’s initial work-record design, before wrapping the existing implementation.

### 3. Blocking — “Pure keys” are insufficient for prefetch equivalence
**RFC §4.2; affects C.**

The claim that results and refusals remain unchanged “by construction” needs stronger preconditions. A pure expression can fail, allocate, or sit in an untaken branch.

Today, the interpreter short-circuits boolean expressions and evaluates scan filters after authorization. Arithmetic can overflow. A speculative key such as `.n + 1` can therefore fail for a row or branch the ordinary execution never evaluates. ([runner.rs:454](../../snapback4/crates/snapback4-core/src/engine/runner.rs:454), [read.rs:594](../../snapback4/crates/snapback4-core/src/engine/read.rs:594), [value.rs:108](../../snapback4/crates/snapback4-core/src/value.rs:108))

Using the ordinary expression evaluator during prefetch would also move its step and heap charges; it charges these while evaluating expressions. ([runner.rs:398](../../snapback4/crates/snapback4-core/src/engine/runner.rs:398))

Finally, “one page” is not a byte bound, and transaction-scoped retention can accumulate entries across many pages.

**Resolution:** Start with total field/literal key extraction. Speculation must neither expose language errors nor alter logical charges; unsupported or fallible cases should skip prefetch. Cache raw storage facts, retain ordinary authorization and expiry evaluation, and impose an independent byte budget with eviction or fallback. Qualify guarded reads, hidden rows, early cuts and large values—not just the inbox.

### 4. Blocking — One final write flight requires an indexed transaction overlay
**RFC §4.2; affects C.**

“All writes are known when the program ends” does not explain how the program obtains the state needed to calculate those writes.

Current execution writes the source before updating maintains; maintained updates read their current value from the transaction. Final-existence checks also query the resulting transaction state. ([write.rs:69](../../snapback4/crates/snapback4-core/src/engine/write.rs:69), [maintains.rs:157](../../snapback4/crates/snapback4-core/src/engine/maintains.rs:157), [write.rs:416](../../snapback4/crates/snapback4-core/src/engine/write.rs:416))

Deferring writes without replacing that visibility breaks ordinary programs: insert membership then perform an authorized write; update one maintained total twice; insert two rows competing for a unique key. Invalidating cached entries cannot make buffered writes visible.

**Resolution:** Specify an overlay that implements read-your-writes for point reads, indexes, scans, counts, deletions and constraints, while preserving execution-order errors and charges. Alternatively, flush at dependency boundaries and relax the one-flight promise. Read prefetch and deferred writes should be separate C milestones.

### 5. Major — SQL liveness must include authorization and clock dependencies
**RFC §§6.1–6.2; affects D.**

The proposed eligibility rule considers only declared SQL relations and whether their source tables expire. That is insufficient.

The revenue example also depends on `memberships` through its Quarry prelude. Candidate results depend on target-row rules. Those permissions can change—or expire—without changing any declared projection. Arbitrary SQL can additionally depend on time or volatile functions while reading only non-expiring projections.

Existing Quarry execution explicitly records rule-probe dependencies and expiration deadlines; the client uses both table invalidation and expiry timers. These are necessary parts of the existing observation contract. ([read.rs:60](../../snapback4/crates/snapback4-core/src/engine/read.rs:60), [read.rs:220](../../snapback4/crates/snapback4-core/src/engine/read.rs:220), [client.ts:273](../../snapback4/packages/snapback4/src/client.ts:273), [client.ts:360](../../snapback4/packages/snapback4/src/client.ts:360))

**Resolution:** Derive observation eligibility from the complete dependency set: SQL relations, returned managed rows, authorization preludes, rule probes and clock dependencies. Preserve expiration scheduling or classify the operation one-shot. Define the supported SQL function surface for live reads. Qualification must include permission removal and expiry with no projection write.

### 6. Major — Stable provider keys do not make a rerun a resumable workflow
**RFC §§5.1–5.2; affects A.**

The `summarize` example rereads the document on every attempt while using the same provider idempotency key. Consider:

1. Attempt one reads revision 1; the provider accepts the request.
2. The worker dies, and the document advances to revision 2.
3. Attempt two reads revision 2 and reconciles the same provider key.

If reconciliation returns the original summary, the example can save revision 1’s summary while presenting revision 2 as its source revision. If changed payloads are refused, retry cannot progress. Actual provider behavior is **UNVERIFIED**; the RFC must define what its adapter requires.

The current worker invokes the handler anew for each claimed request; it has no step-resumption mechanism in that execution path. ([worker.ts:129](../../snapback4/packages/snapback4/src/worker.ts:129))

**Resolution:** Bind each external step to immutable request data and source versions, with durable state sufficient to reconcile and resume. Persist outcomes or explicitly refuse changed inputs; derive mutation IDs per durable step. The example must inspect `ctx.mutate`’s outcome before declaring success. This needs a concrete A contract, even if implemented through a small helper rather than a general workflow framework.

### 7. Major — A and C share a larger persistence boundary than the increment table acknowledges
**RFC §§3, 9, 10.2; affects A/C integration.**

C promises `serve`, `deploy` and backup, but the prototype explicitly refuses assets, native modules, jobs, actions and schedules. A’s existing action persistence uses SQLite directly. ([postgres/mod.rs:297](../../snapback4/crates/snapback4-core/src/engine/postgres/mod.rs:297), [engine/actions.rs:5](../../snapback4/crates/snapback4-core/src/engine/actions.rs:5))

`Rows` and `PartitionRows` therefore do not cover the production backend’s whole durable state. A can otherwise deepen SQLite-specific work storage while C implements an incompatible replacement.

Activation also needs attention: today’s exclusion is a filesystem lock in a deployment directory. Separate hosts or directories targeting one Postgres store would not share it. ([releases.rs:11](../../snapback4/crates/snapback4/src/verbs/releases.rs:11))

**Resolution:** Agree on ownership and transactions for identity, work, effects, schedules, release metadata and recovery before both lanes establish their schemas. Split C into access/performance work that can proceed immediately and production host integration that consumes A’s shared contracts. C’s deployment scope needs database-scoped activation fencing and store-incarnation handling.

## Changes before increments A and C start

- **A:** Specify durable authority, protected-result collection and external-step replay first. Include them in invitation/webhook crash and revocation acceptance, alongside typed handlers and supervision.
- **C:** Separate read prefetch, write buffering and production host integration. Establish speculative-read and read-your-writes contracts before implementing their optimizations.
- **Joint:** Assign one owner to shared durable metadata and activation/recovery semantics. Preserve parallel work on independent parts.
- **Instrument:** Write the brief and capture its initial baseline immediately; use its failures to choose services and realistic performance targets.
- **Managed target:** Record the initial application isolation and credential boundary while leaving the full service design to its child LLP. A’s production launcher must deliberately construct the worker environment: the current development launcher inherits its parent environment, which must not accidentally pass future core database credentials to Node. ([dev_worker.rs:62](../../snapback4/crates/snapback4/src/dev_worker.rs:62))

These changes preserve the accepted direction and the parallel A/C start.

## Lesser concerns

- §4.3’s long-key decision must cover composite encoded keys, not just individual text-field lengths.
- §5.2’s exact-report path needs an actual snapshot strategy: existing jobs traverse pages across commits, which does not itself freeze mutable source data. ([job.rs:1](../../snapback4/crates/snapback4-core/src/engine/job.rs:1))
- §6.2’s expiry view needs engine-owned lifetime metadata even when the authored projection omits the expiry field.
- C’s performance target should include sustained mixed traffic and realistic database latency, alongside the recorded microbenchmarks.
