This is a semantic amendment to starter §14, client §6.11 and release-client §3. It is not ready to implement as written. The direction is sound, but several clauses are undefined, contradict governing text, or state untestable evidence.

## 1. Readiness lifetime contradicts §6.11 (readiness lifetimes, correctness)

Proposal §2: "Once true, it stays true for that App and signed-in viewer through release/catalog loading and later admission warnings."

Governing [§6.11](llp/3000.013-quarry-states-intent.rfc.md): `useAppReady()` "requires current auth signed-in without an E_ADMISSION-family refusal."

Counterexample: server revokes the session. SDK publishes an admission refusal while the React auth snapshot has not yet flipped to signed-out. Under §6.11 readiness is false. Under proposal §2 readiness "stays true" because this is a "later admission warning." The proposal then relies on the role gate to close, but leaves the readiness indicator true through revocation.

Minimal correction: define "admission warning" to exclude any E_ADMISSION-family publication or signed-out transition. Example: "Sticky-true covers only non-auth diagnostics (catalog loading, sparse-filter notes). Any E_ADMISSION-family refusal or signed-out viewer returns readiness to false; a replacement app or account starts a new lifetime." Also add the missing lifetime test: signed-out/restoring stays false after having been true.

## 2. Role-gate adjectives are undefined (authorization, testability)

Proposal §2: "present, complete, fresh, non-revalidating" gates; "Loading, partial, denied, absent, stale or revalidating role evidence never licenses" children or submission.

Governing §6.11 knows only `loading/denied/absent/partial/present` plus `isPresent`/`isReady`. There is no defined `stale`, `revalidating`, `fresh`, or `complete` predicate for role evidence.

Counterexample: a role read returns `present` with retained data across a release switch. One implementer calls it "fresh" (it rendered), another calls it "stale" (generation changed). Both satisfy the RFC text. The evidence clause "checking input identity and values" cannot distinguish them.

Minimal correction: bind each adjective to an existing observable. Example: "fresh means the role read is `present` from the current release generation with no pending refresh; stale/revalidating means `present` data rendered while `release` is loading or a refetch is in flight — both close the gate." Name the exact hook/field that exposes revalidation.

## 3. Guest-to-account replacement leaks the account boundary (authorization)

Proposal §3: "A guest session is a session: signup/login can replace it through app.auth, with the ordinary account boundary."

Governing starter §2: "Account B cannot see or submit A's intent, including through delayed callbacks."

Counterexample: guest creates pending `addTodo` offline, then signs up as Alice in the same `App` without replacement. If the SDK outbox is rebound to Alice, Alice submits the guest's intent. "Ordinary account boundary" does not say whether the guest outbox is isolated, discarded, or retained under the guest identity.

Minimal correction: require app replacement or explicit outbox isolation on guest→account transition, and add the test: guest pending write exists, signup as a distinct principal, prove the guest write never settles as the new principal and is not visible to the new viewer.

## 4. Planner role-shape change breaks the settled compatibility story (compatibility, authorization)

Proposal §3 extends planning to "a table with an enum column named role" and generates "one service:ops-guarded insert operation per declared role, with that role fixed as a literal, rather than a caller-supplied role argument."

Governing §14 and its review note settle the opposite split: "automatic adaptation uses one enum-typed mutation per roster" while "manual `why` proposals retain per-role literal mutations."

Counterexample: a wave-14 app already adapted with `provisionMember(role: RoleEnum)`. Re-running the new planner with "fresh names avoid collisions" either (a) adds N new literal mutations alongside the old enum mutation, doubling provisioning paths, or (b) is claimed "idempotent once writers exist" with no definition of "writer exists" that covers the old shape. "Keep existing blocked-roster bootstrap mutations for compatibility" then preserves a caller-supplied-role path with no statement of who may call it.

Minimal correction: state the migration rule explicitly. Example: "A table with any existing insert/upsert path counts as having a writer and gets no new mutation; old enum-arg mutations are retained as-is with their existing `service:ops` guard; new tables get N literal-fixed mutations." Define whether a job-internal or test-only insert counts, and whether principal-defaulted-to-viewer counts. Specify principal handling: the generated literal mutation must require an explicit target principal, not default to `viewer`, or an ops caller provisions a seat for itself.

## 5. Scan and entry-site patterns are untestable (testability, correctness)

Proposal §3: scan "excludes every dot-directory, test directories and known acceptance/fixture/proof/test scripts. Runtime source files under scripts still get scanned." Detection covers "`usePersonaApp`, `persona:` and `?as=` custom entry sites."

Counterexamples:

- `scripts/seed-admin.mjs` (dev seeding with `usePersonaApp`) is flagged as a production entry site. False positive.
- `persona:` matches any object key, comment, or CSS-adjacent text named `persona`. `?as=` matches any URL with that query key. Both overbroad with no AST/file-glob definition.
- "Known scripts" and "test directories" (`test` vs `tests` vs `__tests__`) are unnamed, so "only runtime findings appear" cannot be asserted.

Minimal correction: list exact excluded globs, define each entry pattern as a syntactic form (e.g., `usePersonaApp(` call in `src/**`, `openApp(persona)` / `createApp({ persona`, `?as=` in route parsing), and carve out `scripts/` dev tooling by filename list or annotation.

## 6. `--adapt --production` contradicts §7.2 (correctness)

Proposal §3: "Upgrade names init --adapt --production for a persona-only project."

Governing §7.2: "`--adapt` accepts only `--web`/`--expo` beside it and refuses without a `snapback/*.q`."

Under current CLI text, `init --adapt --production` is refused. The proposal neither amends the allowed flag set nor states the interaction with `--web`/`--expo`.

Minimal correction: amend §7.2 explicitly. Example: "`--adapt` accepts `--production` with exactly one of `--web`/`--expo` and requires `snapback/*.q`; otherwise it refuses as before." Add the refusal test.

## 7. Compatibility-dedup rule is underspecified (compatibility)

Proposal §4: "A literal string arm of a conditional joins as its singleton enum domain; enum arms retain their union, including nullable arms."

Release §3 scopes dedup to "compatibility output" merged enum domains with separate `BaselineRows` namespaces. The proposal gives no scoping or example.

Counterexample: `if c then "a" else someNullableEnum` — does the result become `"a" | Variants | null`, and does that collapsed domain leak into `BaselineRows` vs current rows, or into wire values? Proposal says "evaluation/laziness and wire values are unchanged," but without an input/output pair a checker cannot verify it.

Minimal correction: scope the rule to compatibility-union construction only, with one worked example (source conditional, baseline domain, emitted union, null placement), and state that baseline/current namespaces stay distinct.

## 8. H9 evidence as stated is unsatisfiable or unverifiable (testability, readiness lifetimes)

Proposal §5 H9: "execute the packed AccountEntry recipe with a real persisted password session and held data in a new browser realm, refusing all backend requests, including auth/config, with no metadata cache. Require signed-in held UI and no alert."

Problems:

- "New browser realm" with "real persisted session" and "no metadata cache" is contradictory unless realm means a new page/context sharing origin storage seeded online first. As written (new profile), no persisted session exists, so signed-in held UI is impossible.
- It assumes `ready` can settle offline with zero backend contact. Starter §15 says config fetch never gates restoration, but cites no SDK guarantee that initial `ready` settles with all backends refused. If `ready` needs the backend, H9 fails by design.
- "Three wave-15 custom apps" are unnamed; "exercise each new role mutation as service:ops and refuse outsiders" names no outsider (guest? authenticated non-ops?); "checking input identity" does not say value-preservation vs object-identity across unmount of protected children.

Minimal corrections:

- Define realm: "seed online, then open a new page in the same origin storage with every request refused and localStorage auth-config cache cleared; require held account UI, `useAppReady()===true`, no alert."
- Cite the SDK offline-ready guarantee or weaken H9 to allow the seeded-storage precondition.
- Name the three apps or give selection criteria plus byte-hash preservation check; enumerate outsider identities; assert preservation as "text-input values and selection persist while protected queries unmount and submission disables across release loss/restore and after explicit revocation."
