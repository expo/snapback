Quarry store testing (LLP 3000.035 §5.1): `SNAPBACK4_EVAL_POSTGRES` is an
explicit evaluation connection. The factory owns one physical schema per worker,
restores its rows and bookkeeping, installs the compiled fixture, then opens the
ordinary engine. Mutation attempts restore a seeded snapshot; shrinking reuses
that same factory. `Database::connect_fresh()` is an opt-in test mode. Fresh and
restored outcomes must serialize to identical bytes. The local wire observer
retains SQLSTATE, message, detail and SQL statement before the public query API
converts a driver error to a refusal; it never changes the traffic.

Reads sweep every public boundary. Mutations compare every discovered position
twice on SQLite, and compare up to eight seeded positions per dimension on
Postgres (including first/last), plus the case's original budget. Sampling
counters are in `store_stats`; each selected position runs prefetch on and off.
Physical prefetch counters are separate from the exact public outcome record.
The widened generator (`src/widen.rs`) emits prefetch-reachable reads: pages
projecting `tags[.tag]` and `tags[name = .label]` (a `Get` and a unique
`Lookup` whose keys vary across rows) and a loop reading `tags[row.tag]`, so
`store_stats` reports marked reads, transferred rows, cases with a transfer
and `prefetch_consumption_witness_probes` (fewer database calls with prefetch
on: cached answers were consumed). A planted cached-hit-to-miss fault is caught
by the random corpus (LLP 3000.035 §5.1; the closed
[coverage ticket](../issues/closed/20261007-quarry-store-oracle-prefetch-coverage-gap.md)).
Heap is charged identically on every store and the device (LLP 3000.007
§20.24.5); any disagreement is a ticket candidate, never normalized into a pass.
The cluster regression asserts it finds no signature and refuses any new one.

`run-stores --seconds N` stops each worker between cases after N seconds; a case
and any shrinking already underway finish. `cases` remains the requested count,
`generated` is actual completed generation, and `time_limited_workers` reports
the early stop. Slowest-case timing includes generation, comparisons, shrinking
and artifact saving. It does not silently claim the requested million. The scheduled
runner rejects incomplete reports; its own `--hours` option instead chooses a
case count from a 256-case calibration of both campaigns, with 20% headroom and
a million-case cap. This is a sizing estimate, not a hard deadline.

Generator widening (`src/widen.rs`, LLP 3000.035 §5.1): from a stream
independent of the base generator (`generate::base`; a seed it leaves alone is
the base case byte for byte), cases gain prefetch-reachable reads, mutation
blocks (lets, `require`, `if`, several writes to `key` and `k2`, reads after
writes), a prelude of mutations `prep0..` run in order on the same store before
`run` (`Case::steps`, sometimes as the other viewer; `observe` then reads both
keys), and expiry (`expire at .until`, a clock advancing from `seeded_at`
through each step to `clock`, sweeps, `until: now + ttl`). Every oracle runs the
prelude (`execute::world`) and compares its outcomes (`prelude-*` fields;
`store-postgres-prelude`); a device acquires at the seed clock and catches up by
one sync round after the server's prelude. The prelude is emitted first so no
rewrite moves its sites. `lean::generate` narrows half the cases outside the
model (projections, expiry) back into its fragment; the rest stay named
unsupported (`shape`, `loop`, `table-expiry`). The report's `coverage` counts
each new feature (`block/*`, `prelude/*`, `projection/*`, `expire/*`, `clock/*`).

# LLP 3000.036.004: Security invariants and exposure

**Type:** RFC
**Status:** Accepted (SEC design revisions 3/5 and SEC2 amendment/implementation round 5: Muse and fresh Codex READY; qualification in progress)

## 1. Contract

The wave-16 bakeoff found rules enforced correctly but policies encoded wrongly.
A declaration of intent is independent of the rules implementing it. `check`
reports each declaration as **proved**, **refuted**, or **unproved**. Refuted
means a concrete, replayed database/rule counterexample, never merely a Boolean
assignment. Unproved names the unsupported path or incomplete search. Neither
unproved nor a finite passing test campaign may be described as proved.

Implementer: SEC in this worktree, starting 2026-10-18. The author commissioned
this semantic extension and two independent design reviews. No version bump
or publication is part of this lane. STAGE owns provisioning/password dev doors;
RULES5 owns live-parent rule semantics; FRONT owns general diagnostic triage.

## 2. Surface

Use the existing rule vocabulary rather than invent a second policy language:

```
invariant notes.read only .patient = viewer or .clinician = viewer
invariant requests.update only .requester != viewer
invariant members.role write only exists roles[viewer, role = 'owner']
invariant photos always .image != null
```

The first target is a table, the second component an effect (`read`, `insert`,
`update`, `delete`) or a column followed by `write`. `write` checks insert and
update, including both images for ordinary updates; delete authority has its
own declaration. A column invariant only concerns writes to that column, but
must include every effective admission path. Owner-only field patches bypass
an ordinary table update rule; invariants affected by `written by` stay
unproved until that bypass is modeled. An implication from a denied table
rule must never prove such an owned-field claim.
`always` is a row-integrity assertion. Predicates parse as ordinary Quarry
expressions; unsupported policy expressions are reported unproved with the
reason. Unknown tables/columns/effects are authoring errors. Multiple source
files and multiple declarations are supported. For update intent `.field` means both old and next images for mutable
columns; named transitions require an explicit reviewed reduction or stay
unproved. Once-judged immutable/id rules need a proved equal-image reduction
or stay unproved. Both upsert arms and `insert if absent` are included, with
their own collision/refusal observations. `always` quantifies over every
committed row image from insert/update/upsert and trusted seed/import/restore/
activation, not merely mutation inserts. Constraint-based row proof must use
the actual validation on every ingress, including defaults and the exact
non-whitespace minimum function, or stay unproved.

No declaration changes runtime
authority or replaces a rule. No implicit service-seat exemption is added.

The proof fragment uses bound rule predicates. A row assertion can be proved
from its required column type/constraints (not an optional type), or otherwise
remains unproved. Aggregate/transition/temporal assertions outside that fragment
remain explicitly unproved, not syntactically discarded. Syntax with `now`,
counts, or other program expressions must retain that reason. This is a safe
extension point, not a claim of a complete solver for arbitrary Quarry.

## 3. Sound proof boundary

For a table effect, prove `admission => policy` for **every database snapshot**,
row image, ordinary authenticated viewer (including service seats) and clock.
The engine system principal is explicitly outside this quantification: it is
the trusted seed/import/job boundary, never an ordinary user or an implicit
service-seat exemption. Tables touched by system/native/job/worker paths remain
unproved absent a reviewed reduction, and audit lists those writers. This overapproximates every reachable history:
an old assignment and a changed current role are independent facts. Grant
creation never proves a current role. Required role predicates must be true at
the access boundary. No fixture-specific assumption enters a proof.

Translate Boolean connectives compositionally, retaining true/false/unknown
truth for atomic predicates. Unknown never admits and `not unknown` is unknown.
Atomic facts are keyed by their full bound structure, including table, index,
keys, named equalities and old/next image. Symmetric equality may canonicalize by operand reordering only, preserving
Value variants (Id is not Text), table, index, keys, image and predicate kind;
other equalities and probes stay independent. A finite exhaustive implication
check over this abstraction is sound because it includes every concrete
valuation, even impossible ones. Cap atoms/work; cap exhaustion is unproved.
Do not add database consistency axioms without a separate soundness argument.
Never drop, assume true/false, or simplify an unsupported admission atom;
keep it opaque with its full identity or report unproved. Concrete leaf
semantics are the current `evaluate_leaf`/`term`, not stale Lean open points:
null equals null, null differs from a non-null literal, Id differs from Text,
noninteger ordered comparison returns false, and a missing live reference
marks unknown (including under negation). Missing ordinary fields currently
load null; missing reference and missing image are not conflated. Any semantic
mismatch with the independent model is named, never normalized away. Runtime
errors do not establish an admitted result; probe/storage/schema failure
cannot be used as a successful counterexample or a proof fact.

The Lean addition proves a three-valued Kleene kernel with admission only
on Readable and the exact theorem: exhaustive checking implies that for every
valuation, eval(admission) = Readable implies eval(policy) = Readable; the Quarry-to-kernel translation and runtime boundary remain reviewed
Rust obligations, not a claim of whole-platform formal verification.

For read intent, admission includes the ordinary read rule and every bypass:
- point/list/view/filter/count/exists and live refetch use ruled reads;
- sync acquisition and publication authorize at their own server snapshot. An
  offline device cannot know a later server revocation, even with until-revoked.
  A synced read invariant therefore reports the device access path unproved
  for current-server-role intent, separately from its server proof. Delivered
  history has an additional explicit retained-history blocker. No stale local
  role is treated as a current server role;
- inherited read-through rules are checked in their bound form, including
  captures; live-parent semantics remain RULES5's responsibility;
- valued write targets already reread through `get` before returning, and
  generated insert results also use an ordinary ruled read. Verify those
  reductions against the bound IR; any escaping image without that reduction
  is a blocker or must satisfy the implication `effective write admission => read intent` for that image;
  otherwise the declaration stays unproved;
- maintained aggregates/columns and row views may expose source changes under
  different rules: report such source claims unproved unless a reviewed exact
  reduction proves them; projections narrow payload only; existence/count disclosure follows the
  derived path's own rules, so each derived path needs its own reduction or
  stays unproved;
- table-rule probes see raw target rows, unlike program `exists`. Follow
  reverse dependencies into every other table's read/write rules: the presence
  of a marker row or a successful write can disclose the protected target's
  existence or named fields without returning that target. Source privacy
  intent remains unproved for such raw-probe observations unless a reviewed
  reduction proves authorization or the policy explicitly permits disclosure;
- incoming `on delete cascade` and `on delete set null` effects bypass child
  delete/update rules. Report child delete/update/column-write invariants
  unproved when affected, including transitive cascades, until initiating
  authority and child-image policy are modeled. Enumerate these edges in audit;
- asset reads inherit their owning row privacy, while upload/write authority
  belongs to insert/update intent; applicable private-field authorities must be conjoined with owning-row
  admission for asset reads;
- jobs, schedules, native jobs, actions and external effects are trusted system
  or worker boundaries. Read claims affected by opaque outputs/side effects
  remain unproved. Job writes do not prove ordinary-user write authority;
- refusal codes are observations: an authored difference between an absent
  lookup and later denial is a reported exposure. A privacy proof must not
  ignore that path. Unmodeled constraint/refusal observations remain unproved.

Observer boundary: this verifies row payload and logical existence/refusal
observations, not physical timing, runtime cost or all resource side channels.
The platform's documented examined-count/meter-cut observations are explicitly
excluded and reported as exclusions, not full noninterference. Read intent
includes all logical exposures above. A component may be proved while the
whole declaration remains unproved because another path is blocked.

The implementation must build a closed-world census of bound IR read/write
forms and schema-triggered paths. An unclassified form is a blocker, never
silently omitted. Census includes sequence allocation/read admission, online
and device query paths, ephemeral paths, owner fields, maintained writes and
referential actions. System/job/action/native/external touched tables default
unproved without a reviewed reduction, and are listed as grant-column writers.
Every `read` declaration covers all enumerated logical paths, not just its
direct rule. Authenticated viewer classes use engine operations; signed-out
cases run only against HTTP/auth admission, never a fabricated principal.
Retained-history observations are classified by leave policy and reported
separately; they cannot refute the platform's retention contract or prove a
current-role declaration. Test output names unsupported device freshness.

The report enumerates the paths checked and blockers. A proof is never awarded
just because the direct table rule passed while an indirect path is unmodeled.
Conservative rejection/notes are acceptable; false proof is not.

## 4. Counterexamples and generated tests

Generate deterministic challenges from schema types, policy atoms and fixture
rows. Use in-memory stores; never leave SQLite sidecars under target. Vary the
viewer across owner/other-user/other-role/revoked-role/unauthenticated classes,
policy literals, principal arguments and absent optional values. Existing role
rows and retained grant rows form revoked-role snapshots. Do not call an
arbitrary consistent snapshot a *reachable* application-operation sequence.

Concrete counterexamples must replay the engine's actual rule admission and

path. The absence of a concrete witness when implication fails is **unproved**.
Generated tests are a separate executable check, run by default `test`, with
coverage counts and named unsupported cases. They use isolated state so they
cannot corrupt the fixture business tests. For operations, derive arguments
from fixtures and schema, substitute other principals and roles, and compare
admitted effects/observations against the declared intent. Merely succeeding
as another user is not a failure when policy permits that operation. Signed-out
network admission cannot be tested by inventing a signed-in principal: label
that boundary separately. No finite campaign promises arbitrary sequence
coverage. `test` fails on replayed violations; unproved coverage is explicit.

## Not building

- **A second authoring language.** Quarry, one spelling, copied from Snapback 2 (LLP 1004, LLP 1007 §4b). TypeScript is for seeds, journeys, effect bodies and the client.
- **Byte- and step-priced certification.** No closure, heap, output or step ceilings at `check`; the certificate certifies shape, uniformity, completeness class and prediction eligibility. Resources are metered at runtime (LLP 2000.000 §6).
- **A per-query result cache.** No range receipts, validators, halos, absence evidence, coverage spans, extent facts, held directories, fact integrity or swap journals. The client replicates declared partitions with one watermark each (LLP 2000.000 §7).
- **Engine-minted ids for client inserts, grants, ID slices.** Ids are client-minted, time-ordered, 128-bit; the engine mints for its own writes.
- **The `drain` protocol, follower-tab inbox rows, `defineItems`, `withHistory`, `mutationTarget`, `receipt.source`, `local.caughtUp`, `partial` reason codes.** The card (`packages/snapback4/src/contract.ts`) is the whole client vocabulary; `why` carries the rest.
- **`retain` as a receipt rule.** `until-revoked` and `delivered-history` survive as the client's leave policy on a scope tombstone.
- **JavaScript in the data plane.** Queries and mutations run in the Rust interpreter inside the SQLite transaction, and in the same interpreter on the client (host decided at week 3 by measurement, LLP 2000.000 §9). A *job* may be the app's own Rust, hosted as wasm through the interpreter's operations under the job's meter (LLP 3000.005, the Moves line below); a query or mutation may not.
- **An embedded JS engine for effects.** The data plane never calls out. `emit` writes the effect durably in the mutation's commit and an external worker holding a service token claims, performs and settles it over the wire (`snapback4/worker`); the four reference effects run on the builder's Node (LLP 2000.000 §10, decided 2026-09-13).
- **Committed generated code; an auth mode; a supervised bundler.** As Snapback 2 (`rules/NOT-DOING.md`): types by inference, personas not modes, `SNAPBACK_URL` is the client contract.
- **A TypeScript twin of the interpreter.** Retired by the author's ruling of 2026-09-13 (LLP 3000 §7): one implementation, in Rust, on every host — the core's SQLite under the native module, memory under wasm on the web with the host persisting each commit's changes. The web pays 312,924 B gzip before the diet where the twin's tier paid 16,842; the conformance obligation between two interpreters ends. Expo Go runs the online tier.
- **More than one hosted target, an admin console, media transcoding or thumbnails, push delivery itself (a worker's), cron syntax beyond `every N at HH:MM`, vector or relevance-ranked search (word-prefix search is in: `words(..)` and `matching`), federation, multi-region, device-to-device sync, at-rest encryption claims.** After the clock, on evidence.
- **General observability beyond `why`, `trace`, `logs`, `data`, `sql`, server operation latency, and bounded client subscription inspection.** The `sql` verb is read-only inspection of the developer's own store (LLP 3000.007 §8.8), never an application surface. Separately declared application SQL reads are admitted for increment D (LLP 3000.009 §6.2, §14.4; the 2026-09-16 Moves line below), not implemented by this inspection verb.
- **A guide corpus.** The compiler's facts, one language card and keyword cards, as Snapback 2; no freshness dates. Every card's Quarry is compiled by the suite and the language card is run, so a card cannot promise a form the parser refuses.

- **Partial union delivery, two group audiences, a public branch.** A union syncs principal-column branches and at most one group branch, each a whole disjunct of the read rule (LLP 3000.036.000.000); a branch with an extra condition, a second group or a `public` branch is refused with the rewrite, never partially delivered; service grants add no device audience (LLP 3000.007 §20.6). A union does not combine with delivered history, read-through children, synced or row-keyed views, owner keys, timelines, private field owners, acquisition windows or direct/inherited expiry on content or membership scopes.
- **Exact horizon maintenance.** The horizon bounds acquisition (a snapshot, a bootstrap); the log never evicts or back-fills to hold a device's group at exactly N rows. A local read past the acquired horizon by key says `complete: false`.

- **Clock expressions in rules.** A read rule compares with `=` and `!=` only; `.expiresAt > now` remains a mutation `require`. Stored lifetimes use `not before .col` for server-controlled opening and `expire at .col` for expiry. The engine publishes opening commits; devices receive no unopened payload. The supported compositions and explicit exclusions are in LLP 3000.036.003.
- **A jobs framework.** No priorities, worker pools or dead letters: one FIFO of runs, one chunk at a time, a refused chunk parked with its refusal. Actions, effects and scheduled actions carry per-operation retries, deadlines and cancellation, and a record per external step (LLP 3000.009 §5.2; the Moves line below). Missed period boundaries while a server is down fire once on return, not once per missed period.
- **Asset processing.** No transcoding, thumbnails, rungs or HEIC: the bytes are served as uploaded; JPEG, PNG, WebP and MP4 only; image dimensions and optional MP4 duration read from the header; MP4 dimensions are not extracted.
- **Search beyond word prefixes.** One tokenizer (NFC, lowercase, alphanumeric words), one index shape (`scope, words(cols), order.., id`), one read (`matching`): every term a prefix of some word, the first term's words merged as lanes, bounded by the meter in a uniform scope, at most 32 words in an admitted non-uniform scope. No stemming, no ranking by relevance, no phrase or mid-word matching, no per-language folding, no intersection index for the second term (it filters the page).
- **An identity provider.** Guests, password accounts, service seats, and sessions a service mints for accounts the application authenticated itself. No phone, OAuth, magic links or MFA in the engine: an application's worker verifies those and mints the session.
- **No multi-server presence, no presence history or last-seen storage, no broadcast event stream, no connection-bound rows.** `connected[p]` stays server-wide, counting held polls and their 35 s grace; a live query that may read it re-runs in the background about every 5 seconds to stay current (LLP 3000.018). Typing and viewing use short-lived, authorized ephemeral tables in one server process (LLP 3000.017); they never sync or decide durable invariants. A device does not know presence and says so.

# Rules

**Snapback 2 optimizes the edit-to-verified loop — the agent's building an app on it, and ours building it.**

Speed is the constraint. Everything below exists to keep the edit-to-verified loop short
and to stop this repository accreting apparatus faster than anyone can remove it. These
rules bind `snapback2/` and the LLPs numbered 1000 and up; Snapback 1 is baselined, not
exempt, and its numbers may only fall.

Each rule is **[check]** (enforced by `caps`) or **[review]** (enforced by a human).

- **59 documents in the working set** (`llp/current/`). Today's count. A 60th requires
  archiving one — which is just removing the link. Snapback 2 aims to leave this at 15;
  Snapback 1's links are archived at promotion. **[check]**

`caps` · `ref-check` · `snapback2/scripts/test.sh` · `snapback2/scripts/measure.mjs --check` · `check-inventories`

Writer-object coupling follows compiler Const/Let aliases (ordinary inserts
write a temporary, not an inline object). Unknown/reassigned object aliases are
not independent column worlds. Raw trusted row admission needs one witness per
declaration, not a full cloned initial snapshot for every row. Persisted evidence
deduplicates on the first write as well as later merges, keeping the complete
chosen initial world. A successfully stored matching refutation is never silently
ignored because its JSON exceeds a size threshold. The 600-row regression retains
all initial rows in a sub-megabyte record and check still fails on that evidence.

Guard dependence includes aliases of inserted rows and subsequent reads of the
written table, including post-insert require/check rollback. An argument's
single textual occurrence does not establish independence when a guard observes
its stored value through such an alias; unresolved guard aliases stay uncovered.
Packed qualification requires an actual policy or isolated HTTP challenge,
records the two counts separately, and retains explicit native campaign gaps
(e.g. the existing unsupported ephemeral-hub fork) rather than claiming native
mutation coverage from HTTP probes.

Packed social qualification exposed a complete native campaign skip when an
otherwise durable app merely declared an ephemeral table. Fixture-only forks
now copy the hub under its lock into independent memory, preserving row/index
state, deadlines, per-principal/global quota accounting and limits, epoch, ring
and generation binding. The copy never retains the live publisher or external
presence. A mismatched hub/store generation refuses. These are quiescent test
fixture copies, not live adoption or wire changes (LLP3000.017 §§3–4).
Durable generated initialization and histories then run normally in mixed apps.
Generated ephemeral populations and ephemeral mutation histories remain explicit
coverage gaps; their mutation programs are skipped rather than dispatched
through the durable mutation door. External presence still refuses a fixture
fork. Packed social must exercise actual native challenges, not a zero-work pass.

The unsupported ephemeral-program boundary applies in every dispatch phase,
including column/row paired observers and foreign-asset challenges, with a
central observer refusal as a backstop. No phase credits a skipped ephemeral
mutation as a reachable witness. Durable query controls still execute.
Column independence follows aliases into other written fields/tables as well
as guards. A creator copying an inserted private value into a related marker
constrains the alternate world; changing only the source value cannot turn
an always-public id list into a column disclosure. Alias-dependent operators
and opaque effects likewise stay conservatively uncovered.

Alias dependence is field-sensitive across compiler-owned object projections:
a copied row id does not couple an independently supplied private payload.
Unknown, defaulted or implicit upsert field sources remain uncovered. An
immutable-column alternate that must rebuild the SQL fixture declines when
the original hub has committed ephemeral state; it must not reset that state
and attribute the resulting public-presence difference to a protected column.
Actual typed disclosures and state-preserving forks remain available.

Roster discovery reuses the authority classifier's global principal/role index
relationship. A payload column merely named `role` does not bypass its authored
creator; drafts/final reports preserve creator constants and integrity checks.
The ephemeral exclusion also applies to operation-specific synthetic probes.
HTTP checks recognize existing route-specific authentication refusals: queries
and durable mutations use401 denied.E_AUTH; declared ephemeral mutations may
use200 failed/why.E_AUTH. Both require the auth family, no application-rule
marker and no successful data/result. Apply this equally to unsigned/forged
requests and actually retired credentials. Live wire semantics do not change.

The generated roster bootstrap exemption additionally requires an actual
viewer/role authority probe in a schema gate. A principal key alone does not
make a `role` or `kind` payload field an authority seat; such created tables
execute their authored creator. Program-only authority whose bootstrap cannot
be established within those creators is left explicitly unpopulated rather
than inventing payload states. Role actor proposals remain available.

Bootstrap proposals execute an ordinary insert in an isolated fixture fork,
including supplied-field ownership, sequence authority, defaults, recorded
fields, table gates and final constraints. A temporary private probe program
is removed after execution and never adopted or served. Rejected proposals
are uncovered; no system actor or trusted seeding bypass is used for admission.

## Summary

Snapback 4 is one of two parallel candidates for the successor to Snapback 2,
and the sibling of Snapback 3, not its successor. It builds
[LLP 2000.000](./2000.000-keep-the-core-flip-two-substrates.rfc.md) as
written: the Snapback 2 core kept verbatim, two substrates flipped up front —
resources metered at runtime instead of priced statically, and a client that
replicates the viewer's declared partition instead of caching receipted
results — proved first on the hub fixture, with a deterministic simulator as
the primary harness. Snapback 3 ([LLP 2000](./2000-snapback3.rfc.md), led by
Codex / GPT-6 Astra) keeps the same two questions open and discovers their
answers in its first slice. Snapback 2 ([LLP 1000](./1000-snapback2.explainer.md))
continues as the incumbent and the control. All three are judged by one
pre-registered comparison on one clock.

This document records the author's decisions of 2026-09-12 that created the
track, restates the bet on one page so a reader can orient without the brief,
fixes the bakeoff protocol, draws the fence, and plans the first four weeks.
The design argument and its evidence stay in LLP 2000.000. Only running code
will bind (`rules/RULES.md`).

## 1. Summary

LLP 2000 is right that the whole application is the unit of design, right
that ownership comes before abstraction, and right to ask for deterministic
simulation and an early real deployment. Its weakness is that it treats the
two structural choices that produced Snapback 2's costs as open research
questions, and then proposes a first experiment at exactly the scale where
those costs are invisible. This document takes a position on both, names
what to keep from Snapback 2 verbatim, and rewrites the first slice so it
can fail for the right reasons.

The position, in one paragraph. Snapback 2's *core* is excellent and should
be copied: the rule language and its uniformity analysis, the structural-fact
family, one data language, typed states with no silence, refusals that paste
a rewrite, personas, the successor classifier, the derived per-recipient
log, the loop verbs and their sub-second budgets. Two *substrates* under
that core are where the record shows the hours went, and both should be
flipped rather than re-investigated: (1) the static certificate should keep
certifying **authorization and shape** and stop pricing **bytes and steps**,
which move to a deterministic runtime meter with honest `capped`/abort
outcomes; and (2) the client should hold **a replica of the viewer's declared
partition** — the local-first shape every shipped sync engine and Snapback
2's own `deliver` log converge on — instead of a per-query result cache
proven by receipts. Those two flips dissolve most of the machinery that
leaked into the application (receipts, coverage, halos, validators, grants,
ID slices, drains, `withHistory`, follower inboxes, per-table retention
words) and turn the 28-second acquisition into a bulk stream whose floor is
the device's write speed. The first slice should be built on the **hub
fixture** (1,000 memberships, 500 follows, 100,000 messages), with the
day-two change designed before the day-one screen, a native client in the
first slice, and a deterministic simulator as the primary test harness.

Three claims this document makes that LLP 2000 does not:

1. **The costs have two named causes, and both are decisions, not
   mysteries.** Byte-priced static certification and the receipt-proven
   result cache account for every ergonomic residual in LLP 1018.008.009
   except documentation. §2 shows the mapping.
2. **The first experiment must include the hub.** Snapback 2 was "elegant on
   day one and hostile on day two" (LLP 1020) and broke at 1,000 memberships
   (LLPs 1023, 1024, 1025). A two-principal slice will pass and teach nothing.
3. **The process is part of the product.** Seventy-one LLPs, over two
   thousand commits, and seven ceiling raises in fourteen days produced a
   sound system nobody can hold in their head. Snapback 3 needs one owner on
   the core, a simulator instead of a test matrix, and budgets anchored to
   competitors so that raising one means admitting a loss.

## Reference

`invariant table.column read only P` protects a column value, derived values and value-dependent counts/existence/refusals. Mutation results, implicit final writes and explicit returned row objects are observers too. A query projection alone is not privacy: use column read rules to protect every operation. An authored projection excluding the column does not by itself disclose that value; filtering, ordering or copying it can. Audit JSON includes `column_audiences` (effective row rule plus private-owner gate). Unknown derived and opaque paths remain unproved.

`invariant table.read only P` protects read intent; insert, update and delete
name authority. `invariant table.column write only P` covers writes to a
column (insert, inserted insert-if-absent, update and both upsert arms).
Creation is not exempt from write intent; tests judge each executed write in
a committed mutation, including intermediate writes in a multi-write operation. `invariant table.column update only P` checks
only edits, retaining old-and-next-image semantics; use it when creation is permitted
to a different role (for example counter staff creating a ticket price). `invariant table always P` states row integrity.
An update policy over `.field` constrains **both old and next images**.
A policy saying status must not be override therefore also restricts editing
a row that was already override, even when changing it away from that status.
For the role authority of one named mutation, use operation-specific intent
(`invariant table.operation only P`) instead. General next-image-only and
cross-operation transition assertions still need a separate reduction.
Predicates use the existing rule vocabulary: `.field`, `viewer`, `exists`,
comparisons, `and`, `or`, `not`. For a role write use the complete roster probe,
for example `invariant members.role write only exists roles[viewer, role = 'owner']`
in a schema declaring those tables. A declaration never grants authority. Whole-row read intent also protects logical
existence: when occupancy totals are intentionally public but roster identities
are private, declare column read intent for those identities instead. Include
a service seat explicitly when the spec permits it; seats are ordinary checked
viewers, never implicitly exempt.

The implemented proof fragment exhaustively checks independent three-valued
rule predicates. A failed implication is unproved until an engine replay
establishes a counterexample. A schema-valid seeded snapshot is not a claim
that an application operation sequence reaches that state. Required-column
non-null assertions have a separate validation theorem. Read/count/sum/existence obligations are reported separately. A maintained aggregate with bare privacy keys can prove its contributor audience; a broader aggregate can yield a paired present/absent counterexample. Exact server `not before`/`expire at` bounds can prove a temporal read component independently of physical sweeps. General transitions and unsupported expressions remain unproved.
Read-through captures/live parents, complex derived aggregates, raw rule probes,
owned-field update bypasses, cascade/set-null and opaque jobs/workers need
separate reductions. An unresolved path blocks the whole declaration's proof.

Server delivery authorizes against the current server snapshot. A disconnected
device can retain an earlier snapshot until it receives a revocation; even
`until-revoked` cannot know a later server role. Synced current-role intent is
therefore unproved for device access. Retained history follows its leave policy.
These reports exclude physical timing and resource/meter side channels and
explicitly exclude the trusted system-principal boundary. Service seats remain
inside the ordinary-viewer check; there is no implicit seat exemption.

## Current roles and derived grants

A membership or assignment created while a user is an inspector can survive
their demotion. Conjoin the **current reader's role** with the assignment
branch, or revoke every derived grant transactionally whenever the role changes.
A grant writer's role does not establish the recipient's current authority.
With independent current-role intent, grant-lifetime advice points at this pattern; the argument-grant advice identifies
arguments written into reader-grant columns: validate the chosen principal's
role and relationship, even when the caller is privileged.
Global admin authority must come from a trusted operator or existing admin;
a group-creation `created` probe must remain scoped to that group everywhere.
`N_PRIVILEGE_ESCALATION` identifies role assignments trusted by later rules without independent delegation. Open enrollment may be intentional: compare each note with the specification. See `guide staging` for operator first-admin setup and `guide sharing` for parent authority.

## Required evidence and deadlines

If the spec requires a photo, use a required `image <=5000000` column or

Optional-evidence advice asks the builder to check intentional optionality.

the maximum counts all characters. Stored text is not trimmed or rewritten.

## Existence observations

A lookup that says NOT_FOUND on absence followed by a denial saying FORBIDDEN
can reveal existence to callers admitted by a broader read rule. Use the same
code **and message** for hidden/absent/denied cases when existence is private,
or tighten the table read rule. Program `exists` is caller-filtered; probes
inside table rules inspect raw rows and can disclose predicates indirectly.
Inspect both paths in `audit`; a payload-only read check is insufficient.

## When an observer remains unproved

The report names the edge that lacks a reduction. Preserve the specification
while changing its enforcement; weakening an invariant to match a leaking
rule does not repair privacy.

- Maintained counts/sums: retain privacy fields as ordinary bare group keys
  and protect the aggregate with the same audience predicate. Recorded
  reference paths, calendar keys, derived values, private columns and temporal
  contributors need their own reduction; their names are not source fields.
- Owner fields: declare column-write intent too. `written by` authorizes
  patches even when the ordinary update rule denies. To prove a particular
  mutation's role authority, use a dominating current-role requirement and
  operation-specific intent over a role table the mutation cannot change.
  This does not prove every owner-field or old/next-image path.
- Raw rule probes: inspect the observing table and its writers. A protected
  target's read rule does not protect predicates probed from another rule.
  Apply the intended audience at that observer, or remove the raw dependency;
  the report retains the unsupported edge until it can establish implication.
- Cascade/set-null: automatic child changes bypass child write rules. An
  explicit authorized child mutation with `restrict` removes that automatic
  writer, but parent refusal/existence and transitive references remain
  separate observations. Read-through/live-parent authority requires a separate reduction.
- Jobs/native workers/actions: the audit names the trusted or opaque writer.
  An ordinary mutation with stable role requirements can prove that mutation's
  authority; arbitrary native/worker output cannot acquire a proof from a
  caller's role or a passing finite test.
- Schedules: use a stored `not before`/`expire at` lifetime for exact read
  boundaries, or compare server `now` in the write itself. A scheduled status
  update leaves the old status visible between deadline and sweep.
