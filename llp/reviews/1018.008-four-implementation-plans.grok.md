## (2) Per-plan verdicts

### 1018.008.005.000 Composed page resources — **REVISE**

The outcome is right: one item loop for single-page and paginated chat, summary tied to the primary, no companion-query synthesis, no new wire cache. The switching table and the `usePage(conversationView)` shape do not yet specify that outcome.

**1. Blocking — Page and history lifecycle vs existing `composeHistory`.**
The table sends **Partial + readable history → history pages** and **Complete/capped → primary `next`, release history**. The same section says to apply **existing `composeHistory` once**. Those are different laws. Live-query already: unusable `data` is undefined; history grants no scalar; **usable composites** release history. Pagination already: a receipt-backed capped page can keep opaque `next` when a local refresh is partial only because computed projection fields cannot be rebuilt; missing count makes the **record** partial (`conversationView`).

If “partial” includes “count unknown, messages page present,” this plan **drops the live window and paginates original-recipient history instead**. If “complete/capped” includes the ordinary first-20 live page, releasing history is correct, but then **older messages are primary `next`, not history**—which is exactly the starter thread/search tickets.

**Resolution:** Eligibility is the existing composeHistory predicate (unusable primary → history; usable composite/denial/refusal/reset → release history). **Partial is not unusable.** Paginate the active source’s own certified `next`. A usable nested message page stays on the primary chain even when `head.data` count/preview is unavailable. History never certifies the summary.

**2. Blocking — Proposed public shape vs array `usePage`.**
Guides: `usePage` is for **arrays**; `ClientPages` flattens array `data`; one nested cursor-bearing page supplies root `next`. The snippet passes **record** `conversationView` and reads `head.data` plus `items`. That is a new extraction contract, not an overload of the array form.

**Resolution:** Keep array `usePage` unchanged. Define the composite form as: observe the record as `head`; bind items to the **named nested page** (`defineItems` `rows`); `loadMore`/`hasMore` follow that nested page’s `next` (or history’s, when history is the active **item** source). `pages` is the active item-source’s snapshots, not a union of ConversationView and `Message[]` that templates must switch on. Search continuation should use the array form only—no history machinery.

**3. High — Ordering and pending work (whole-collection, duplicates, drafts).**
Per-page `attachItems` then merge items will misplace drafts and invent a second pending-merge. Dedup-by-key is necessary; merging fields/receipts is correctly forbidden. “Seeing an ID elsewhere is not sufficient” for action retirement is correct and must not be weakened.

**Resolution (smaller):** At the resource boundary, (1) choose one active row source, (2) order **page blocks** (reverse acquisition for `order: "reverse"`, keep in-page item order), (3) dedup **whole rows** by table/key in that scan order—first whole item wins, (4) **`attachItems` once** on the concatenated rows so draft placement and pending FIFO are collection-scoped, identical to single-page. Pin with three reversed pages, a live boundary duplicate, a head create, and unrelated outbox work. Do not combine proofs. Pending retirement uses the **selected** item’s evidence only.

**4. Medium — C1 “settle precedence before aggregation” is still an open design.** Close it with the law above before C2 code, or C2 will guess.

**5. Medium — C4/C5.** Closing thread/search tickets only after client-arm acceptance is right. Do not hold search on C3. If `client-pages.ts` would exceed 1,500 lines, split rather than pack history into the array helper. Measure application files; if C1–C2 does not remove real observers/helpers, do not add a second public model to “finish” the parent.

**6. Low — Baseline.** Rebase to `bf845084…`. Reuse closed journey type-resolution for item types; do not synthesize selectors.

Stop condition already in the plan is good: land item-pagination without C3 if history paging cannot preserve authority.

### 1018.008.006.000 Shared recovery and presentation — **REVISE**

Direction is sound: one account-bound `recover()`, reuse `online()` + `settled()`, no second scheduler, no silent sign-in, no resubmit of refused writes, no new status machine, clique stalls stay correctness tickets. **1. High — Explicit recovery / 10s waiter vs `settled()`.**
“Complete attempt must be finite, including `settled()`, which can wait **beyond** the existing resume deadline” vs “proposed 10-second waiter.” Automatic recovery is already 10s. Unclear whether 10s is resume only, outer `recover()`, or a second clock on `settled()`.

**Resolution:** `recover()` captures account/session/writer generation. Step A: same resume/`online()` path as today’s explicit reconnect (existing 10s resume deadline). Step B: wait `settled()` with a **caller-only** wait budget (10s is fine if named). Expiry **cancels the waiter**, not custody, in-flight writes, or resume already running. Result:

- `{ ok: true, settlement }` — bounded attempt produced a real settlement; `stopped` still means paused
- `{ ok: false, refusal }` — existing transport/lifecycle/identity families
- Timeout uses an **existing** refusal family plus wording that it is wait expiry, not write failure. Do not add a scheduler or a new correctness bound.

Late success after logout, account replace, close, or explicit offline cut is `ok: false` for the **captured** identity, never account B’s counts. Recheck identity after every await.

**2. High — Followers.**
“Refresh inbox/writer state and report existing follower settlement; cannot take over an active writer or clear its offline state” is the right law; it is not a result shape.

**Resolution:** Follower `recover()` returns **follower** settlement (`forwarding` / `writer-unresponsive` / inbox-full / no route). Never a writer `remaining` count. No takeover, no lock steal, no silent auth. `work` lookup may use follower aliases; compacted/missing is `undefined`. In-flight follower recover + writer takeover: identity recheck, no aliased writer success.

**3. Medium — Work projection.**

Keep one eligibility predicate for bubbles and the device list; dismissal **rechecks** durable eligibility. `useMutation.last` stays last-call; `work` is present durable intent only. **Name `work`/`can` in R1** before R3.

**4. Medium — `recover()` vs `online()`.**
Clearing deliberate offline only on invoke is correct. Templates must call **one** of `recover()` or `online()`, not nest both. Mounting/display must not start recovery.

**5. Low — Copy.** No reason-order change without a truth table. Stale complete zero stays labeled stale.
