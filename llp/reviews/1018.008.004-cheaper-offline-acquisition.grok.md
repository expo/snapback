## schemaDigest / prepareSchema

`preparedSchemas` now stores `{ hash, rules }` only after `immutable(structuredClone(schema))` and a digest check. `schemaDigest` returns that stored hash iff the **same object** is the WeakMap key; otherwise it still `sha256(canonicalSchemaJson(schema))`.

That is safe for this write path:

- `prepareSchema` always clones first, so the `schemaDigest(owned) !== expected` check cannot hit a prior memo and skip verification.
- The WeakMap is module-private and only written after the check; `hash` is the just-verified `expected`.
- `scopedRuleHash` still prefers the prepared rule map; the fallback’s inner schema id is `schemaDigest(schema)`, which is the stored hash on prepared custody and a live digest otherwise — same bytes as `sha256(canonicalSchemaJson(...))` when immutability holds.

Mutable and shallow-frozen **caller** objects are different identities, so they rehash. The new tests actually exercise the security-relevant direction: nested mutation behind `Object.freeze`, fully mutable clones, successor vs predecessor, and `prepareSchema(successor, predecessorHash)` refusing admission.

Extending memoization to `schemaDigest` makes existing deep `immutable()` load-bearing for this API the same way precomputed rule hashes already were. That is not a new trust model; it is the same custody rule, now on the hasher the envelope re-exports.

Re-exporting from `offline-schema` does not introduce a second hasher **if** both paths resolve one `value-runtime` instance. Two instances would fail **open** (always rehash), not return a hash that was never validated.

## Sort

Both sites `.slice()` then in-place `.sort`. Held/caller arrays are not the sort target. `Sort` probes every `field(value, key)` before sorting, so a missing-field throw does not leave a native in-place sort half-done on a returned array.

ES2019 `Array.prototype.sort` is stable when the comparator is a consistent total order. `totalCompare` on validated IR, with `Desc` as `-compared` (and `0` staying `0`), matches the old merge (`<= 0` keeps left) for equal keys. `DeterministicShare` still uniqueness-checks after sort; with unique canonical recipients, stability does not affect the permutation.

New tests lock the regression that matters for this swap: lengths `0/1/32/1024`, Asc/Desc, `i % 7` ties (original index order), and canonical encoding of the source array unchanged. `1024` is past typical insertion-sort cutoffs.

## Missing tests / residual limits (not REVISE)

- **Engine contract, not algorithm.** Pre-ES2019 or a non-stable `sort` would change tie order. This delta documents ES2019 and you already smoked Hermes equal-key lengths; this Node test file does not itself prove Hermes.
- **Native vs userland diverge if the comparator returns `NaN` or is not a total order**, or if the array has holes/`undefined` (native sort moves those without `comparefn`). That is only a bug if `asArray` + `totalCompare` can produce those; the stated IR contract says they cannot.
- **`schemaDigest(prepared)` equality does not prove a WeakMap hit** (live hash of frozen content matches too). Security is covered by the mutation tests; reuse is not counted the way `preparedReads` counts rule-hash canonicalization.
- No new `DeterministicShare` non-mutation assert; the `.slice()` is the same pattern as `Sort`.

No material finding that should block this delta.
