**Finding — Medium: caller-supplied upsert IDs become AMBIENT.**

At [aggregate_provenance.rs:466](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:466), key propagation skips `id`; [line 503](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:503) then supplies AMBIENT provenance for the returned ID. But a `byId` upsert’s insert arm copies the supplied key directly into the row ID. [Runtime behavior](snapback4/crates/snapback4-core/src/engine/write_target.rs:154).

Concrete, code-traced counterexample, not executed:

```quarry
table source:
  n: int
  public 'source'

table scratch:
  n: int default 0
  public 'scratch'
  insert <- allow
  update <- allow

table copies:
  value: json <=1024
  public 'copies'
  insert <- allow

mutation copy(requestId: id):
  r = upsert scratch[id = requestId] {}
  require r != null else MISSING
  p = source['seed'] ! else MISSING
  insert copies { value: { requestId: r.id, n: p.n } }
```

With `source['seed']` present and the requested scratch ID absent, the caller **supplies** `value.requestId`. The pass nevertheless sees AMBIENT for `r.id` plus READ for `p.n`, so `copies.value` qualifies. This is not merely caller selection under L26.

The smallest fix is to preserve the `byId` key’s provenance in an upsert result’s `id`, retaining UNKNOWN when target resolution is ambiguous. Add this mixed-object regression and verify helper/cache propagation preserves the corrected provenance.

This requires a behavior change; it is not a wording-only finding.

Verdict: NOT READY
