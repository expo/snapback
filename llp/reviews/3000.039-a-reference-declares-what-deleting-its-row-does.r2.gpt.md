The remaining findings follow.

1. **Blocker — §3 steps 3–6; §5.1: the reservation does not bound closure storage or closure-excluding probes.**

   Closure-first evaluation needs persistent information about `S`: at least table/id membership, a traversal frontier or equivalent bookkeeping, and membership tests during restriction, nulling and deletion. §5.1 nevertheless prices heap as “the largest single row’s transient copy … since rows are processed one at a time.” Processing row images individually does not eliminate the retained closure.

   Concrete case: a project cascades 500 small task rows. All must remain identifiable in `S` while restriction probes run, even though the largest task image is small. A reservation containing only that image’s scratch does not cover the closure’s hundreds of identities and collection overhead.

   Closure exclusion also changes the probe bound. Suppose those tasks have an ordinary self-`restrict` reference, and 499 reference one task in `S`. Determining that no **outside** row references it requires skipping the 499 closure members before establishing absence. The advertised fixed one-seek `probe(r)` does not price that work. There is no store operation in the current `Rows` surface that receives `S` and returns an outside witness at that fixed price.

   Read-through adds another mismatch: `through.rs::refuse_live_children` reserves three seeks per child table, while §5.1 describes one seek, or two for an expiring child. Finally, written-row count is not a physical-visit bound: restrict probes can fetch rows without writing any, and maintenance can fetch additional witnesses.

   The exported source plan helps price ordinary write effects; it does not price these new traversal structures and probes.

   **Smallest fix:** define a complete shared delete-reservation calculation, still using the existing exported source prices. Add a schema-fixed maximum closure size, persistent closure/frontier scratch, traversal costs, and a closure-excluding probe allowance—conservatively bounded by possible closure members plus an outside witness. Specify the read-through seek constants and a separate physical-visit allowance. Admit these before traversal, with checked arithmetic. §5.2 must compare that complete reservation against ceilings.

2. **High — §4.2 “commit’s touched tables”: action-reachable tables do not include all derived writes.**

   Consider a readable project with a capped cascade to hidden tasks. Each task contributes to a maintained `profiles.taskCount` for a profile the caller cannot read.

   In the empty-child world, deleting the project does not write `profiles`. In the one-child world, deleting its task updates the profile count. `profiles` is reached through maintenance, not through a cascade or set-null reference.

   The current code makes this distinction observable: `engine/write.rs::row_changed` inserts a private maintain’s **owner table** into `written_tables`; public aggregate and row-view targets can also become touched. `serve_changes.rs::check` obtains `/changes.tables` from recorded commit tables independently of the footprint.

   Widening the footprint does work for the other two surfaces: `Footprint::preserved` returns no preservation certificates when `unknown`, and `settlement_changes` returns null. It does **not** make `/changes.tables` schema-fixed.

   **Smallest fix:** extend the touched-table envelope to every visible table that ordinary hooks of any potentially affected source can write: maintained-column owners, aggregate/view targets and other admitted derived destinations. Insert that envelope even when there are no children. State that footprint widening is triggered by a **statically reachable** writing action, rather than whether an actual child write occurred; suppress action-generated event counts transitively through those hooks.

3. **High — §2.2; §3 steps 5–6; §4.2: allowed maintained sums can disclose hidden data through overflow.**

   Append-only rejection removes one data-dependent refusal, but `server_only` is not a general “this write cannot refuse based on hidden data” flag. In `schema/reservations.rs`, an ordinary maintained sum receives a fixed price without becoming `server_only`.

   Let `M = I53_MAX`. Hidden tasks contribute to a hidden maintained sum:

   - In one world, the project being deleted has no tasks.
   - In another, it has one task contributing `-1`; other hidden tasks contribute `M` and `+1`, so the existing total is valid at `M`.

   The second world is reachable without overflowing during insertion: insert `M`, then `-1`, then `+1`. Deleting the project removes the `-1` contribution, producing `M + 1`. `engine/maintains.rs::apply_aggregate` explicitly refuses that value with aggregate overflow. The empty-child deletion succeeds.

   Both worlds have no occupied restrict reference. The caller nevertheless learns hidden information through success versus overflow, contrary to §4.2. A fixed work reservation cannot conceal a semantic refusal. Set-null moves into a null aggregate group can have the same problem.

   **Smallest fix:** reject writing actions whose maintenance effects can overflow without a static safety proof. Apply this eligibility check to the complete hook chain, not just the child table. Until such proofs exist, conservatively exclude affected sums. Netting a delete’s aggregate deltas can prevent intermediate-order overflow, but cannot fix the final-overflow example above.

4. **High — §6.4: `upsert_absence_proven` is not itself a complete held-group proof.**

   The helper checks uniform readability, absence of a horizon, and `retained_group`. For an ordinary membership rule it can then return true after evaluating the rule over the pinned key. It does not require `current_group` for that child range.

   These states are different in the device implementation. `device/history.rs::coverage_state` returns **Unknown** for a range in `Membership::Rejoined`; `retained_group` tests only whether the state is **Retained**. Consequently, an unknown range passes the “not retained” check.

   Concrete case: tasks sync to project members and use `read <- exists members[.project, viewer]`. The device has a current membership witness after rejoining, but the tasks range remains `Rejoined`/Unknown. `upsert_absence_proven` can return true for the project key because the membership rule evaluates true. That proves readability; it does not prove the complete child population. Any individually held rows can satisfy §6.4’s current-row checks while missing rows remain unproved.

   The read-through branch is stronger: `parent_verdict` calls `child_coverage`, which checks current group coverage. That protection is not present in the ordinary-rule branch. Both device stores use the same prediction wrapper, so choosing SQLite does not repair it.

   **Smallest fix:** specify an action-population proof requiring both key-decided read authority and positive coverage of the corresponding child group, including acquisition and `current_group` for delivered-history groups. Unknown or rejoined range coverage must queue. Reuse `upsert_absence_proven` only after strengthening it or pairing it with this coverage check.

5. **High — §2.2; §3 step 6; §6.1: separate acyclic graphs do not guarantee a valid removal order.**

   Consider these parent-to-child edges:

   ```text
   P --cascade--> B --cascade--> C
                       ^
                       |
                  read through
                       |
                       C
   ```

   More concretely, `B.p` cascades from `P`, `C.b` cascades from `B`, and `B.c` declares `read through .c` to `C`, with its default restrict action. Give both cascade edges caps and make all tables non-expiring.

   The cascade graph is acyclic. The read-through graph is also acyclic. The schema passes the stated cycle restrictions.

   The row state is legal: create `C` naming the future `B` id—ordinary references allow that—then create `B` through the existing `C`.

   Deleting `P` closes over `P`, `B` and `C`. Cascade children-first ordering requires deleting `C` before `B`; read-through’s physical-child protection requires deleting `B` before `C`. Removing `C` first invokes `E_PARENT_HAS_CHILDREN` because `B` still exists. There is no order satisfying both requirements.

   More generally, “the reference graph among their tables” cannot mean all references: the RFC deliberately permits ordinary self-restrict references and set-null cycles.

   **Smallest fix:** define the deletion precedence graph explicitly. Include cascade edges and read-through lifetime edges, reject cycles in their union, and use stable table/id tie-breaking. Ordinary restrict and set-null edges must not impose precedence. Also expressly exclude read-through references from the ordinary `E_REFERENCED` pass so their lifetime refusal remains `E_PARENT_HAS_CHILDREN`.

6. **Medium — §7; §8: the read-gate migration still has no `check` diagnostic.**

   The documentation now explains the gate, but the original diagnostic counterexample remains: a parent has `read <- deny`, `delete <- allow`, and an explicitly declared incoming `restrict` reference. Even with zero children, a direct-id delete changes from success to hidden-target refusal.

   §7 emits `N_DELETE_RESTRICTED` only for **undeclared** references, and declaring an action silences it. This delete site therefore receives no note. Reading `why E_REFERENCED` cannot help when the runtime outcome is `NOT_FOUND`.

   **Smallest fix:** add a separate read-gate migration note at affected delete sites, excluding existing read-through gates. It need not decide whether a particular caller has read authority; it can state the newly required prerequisite and identify the incoming references imposing it.

The proposed delegation, ordinary restrict closure semantics, explicit `keep`, null-exempt cap policy, scoped integrity guarantee and retained-history exceptions are now sound. The remaining implementation blockers concern resource admission, disclosure through derived effects, complete device coverage and mixed lifetime ordering.

**Overall verdict: NOT READY.**
