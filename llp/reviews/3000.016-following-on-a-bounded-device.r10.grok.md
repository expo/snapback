## 2. New defect

**High — §2.1a Activation. A literal default keeps the old device acquired, and a missing column is then known absence.**

The fill on the server is specified. What the device does with it is not, and the words "as for any sync change" point at the wrong gate. `adopt` drops images only when `keeps_literal_default_images` is false (`device.rs`). A sync change does that. A new column does not, if it has a literal default.

That spelling is the one successor offers for a new bool (`default false`). It is the natural type of "whether this post's event is live." On a populated store:

- `classify` calls a required column with no default `Narrowing`. `store/activation.rs` runs `assess` before any fill and refuses the adoption. The fill never runs.
- A literal default is `Additive`, so adoption proceeds. `keeps_literal_default_images` stays true. `adopt` keeps every row, sets `ACQUIRED` to the new generation immediately, and zeros the watermark. `refreshAcquired` then sets the partition current.
- A point read of an old post materializes the default. §2.1a treats that as "event absent" and refuses `FEED_POST_NOT_FOUND`. Offline, that refusal is the answer. The snapshot from watermark 0 does eventually overwrite each row, but the device is already serving. The window is the whole re-snapshot. A post whose page has not arrived yet still refuses.

Captures avoid this because they are optional and have no literal default, so `keeps_literal_default_images` is false and `ACQUIRED` stays clear until the snapshot finishes. The RFC does not say the event column has that shape. "Like maintained columns" is the other shape: required, missing reads as 0, and a missing id does not validate as 0 unless the fill happens before `validate_row`.

**Smallest change.** In §2.1a, replace "as for any sync change" with the gate that actually runs:

- No literal default. A column that is not yet filled is not event-absence.
- The fill is inside the adoption transaction, before `assess` and `validate_row`, at one pinned time, and it does not log (`event_free`, as maintained-column activation). Every post gets the live bit from `byActorPost`, every repost gets its event id, or null when the lookup misses.
- Say which stored shape adopts: optional, or required and activation-derived the way a maintained column is. A required column with no default, and no such exception, cannot be adopted on a populated store.
- The addition must make `keeps_literal_default_images` false. `adopt` clears source images and `ACQUIRED`. The device does not answer until the snapshot that contains the filled column is applied.

## 3. The places you asked about

**Same commit, same image.** A transition can set the column on the committed row before the mutation returns. `row_changed` logs the source image, then runs `timeline_transition`. A second put of the same id in that commit is what `append` keeps: one source image, with the column. Puts are not even served from that payload. `expand_joins` replaces every put with `fetch` at `head`, so a removal's image is the cleared column even when the event `del` is on the next page. Birth accounting is the same fact for an insert: the row is in `born_rows`, and the last image is the one that remains.

An unrepost cannot put the column in the `del`. `log_events::del` stores `data: None`, and `expand_joins` does not attach the old image. It does not need to. Deleting the source row deletes the column. The partial event was never a row. The tombstone, which is fully synced and carries the event id, is what hides the inbox copy. The server reads the id from the in-memory pre-delete image, which `fetch` materialized.

**Cost.** The streamed source row grows by a bool or an id, once, not as a second source event. The owned event put and delete are still logged, because `@T@Posts` stays `sync public`. The snapshot walk omits a kind that is not fully synced, which is what removes the 49,228 event rows from cold acquisition. A later catch-up still downloads those event records and the device drops them. That does not put them back into the cold inventory.

**Prediction.** The device hook already runs: `row_changed` calls `timeline_transition` on the device. `birth_columns` returns early there, so the stamp has to be in the transition, on the row just written, using the same `mint()` as the event id (`new_ids` is shared with the server). For a kind that is not fully synced it must not insert or delete an owned event row. A delete of a missing owned id is `NOT_FOUND` and would fail the unrepost. Tombstone the id from the column; do not touch the owned table.

**No device path still needs those rows.** The Following read is the inbox, the owned edges, and the tombstones (`bind/timeline.rs`). The three lookups read the column of a source row the device holds. Own-post delivery writes the inbox copy from the event value in memory. Rule probes and other reads of the owned table are withheld while either kind is not fully synced. A fully synced kind still has its rows, and prediction still writes them.

§2.3's "owned event row in `byActorPost`" is the old witness. The next sentence says that presence is known from the held source, which is the column. It is not a second lookup. Leaving the name there is confusing, not a second rule.
