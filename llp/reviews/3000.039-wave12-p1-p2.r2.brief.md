## Required behavior

P1: expiration is a server-authored delete trigger. Every scheduled sweep, born-expired row and same-id expired replacement applies declared cascade, set-null and restrict actions atomically. A logically expired root is unreadable even when restrict or a read-through descendant below the cascade closure retains its image. Expected physical blockers are decided before closure writes and scheduled sweeps advance beyond them. Repeated bounded calls, including `limit = 1`, must advance across rows and tables; a blocked earlier table cannot starve a later expiry table. Continuation state publishes only after commit and resets on activation. Unexpected late errors roll the whole transaction back. A child reached through two set-null references must accumulate both clears from its current image.

P2: maintained aggregate ids are lowercase 64-character SHA-256 hex over a versioned, domain-separated canonical logical group tuple at every check/read/write/rebuild site. Empty logical tuple `[]` is the identity input for ungrouped views while compiler-owned `$global = true` is only the physical discriminator. Existing SQLite and evaluation-PostgreSQL stores without the marker atomically rebuild ordinary aggregate targets, publish the marker and advance the semantic generation under their writer transaction. A real store written by frozen 0.4.28 must reopen with the same value under its digest id. Schemas require `maintained-id-sha256-v1`; an old device refuses before it can silently read a legacy address. SQLite adoption estimates and fast-open paths include the migration.

Lean evidence must state logical lifetime, sweep action/progress, fixed aggregate-id bound and atomic adoption invariants without claiming to prove SHA-256. The differential generator must retain and actually execute supported expiry sweep cases; maintained-view evaluation stays explicitly outside the full Lean oracle and gets a separate generated invariant. Simulator and both device stores exercise the relevant families.

1. Does the table cursor rotate after the last visited table, including bounded/time exits, and remain unpublished after rollback? Do row cursors still wrap so newly inserted lower keys become reachable?
2. Can any expected blocker be swallowed after a set-null/cascade write, or can an unexpected error commit a partial closure? Do born-expired and same-id inline paths keep their stricter transaction outcome?
3. Does cascade preflight inspect every reached row with physical read-through descendants without confusing ordinary restrict witnesses or expired logical witnesses?
4. Does the Lean current-image clear preserve prior clears when one child has multiple set-null columns into one or several retired parents?
5. On PostgreSQL, can any writer observe digest code with legacy target rows? Is rebuild+marker+generation one head-fenced transaction on reopen, create and later activation? Does generation conversion remain bounded?
6. Is every maintained-id caller based on the logical tuple, especially ungrouped `[]`, while point lookup uses physical `byGroup[$global=true]` and `$global` never leaks into authored results/types?
7. Does capability negotiation fence old devices before offline zero reads, and is the legacy schema decode lane one-time and stamped on serialization?
