## Round 1

Verdict: **NOT READY** — needs design changes, not wording.

I read the activation boundary, release verbs, ownership, successor and `private_fs` in this checkout. The direction (retain on rollback, hot activation without restart) is sound, but the RFC as written is not implementable safely.

## Blockers

**1. Dormant store is unspecified.**
No table/namespace is named. Active `r`/`i` must remain an exact projection ([activation.rs](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4-core/src/store/activation.rs:217)). Mandate separate `_dormant_*` tables, never hidden catalog numbers, or partition/sync/online reads will leak. Specify: catalog-number handling, legacy stores start with empty dormant state (already-deleted data cannot be resurrected), old binaries ignore new tables.

**2. Name reuse resurrects unrelated data.**
Reintroducing a name "deliberately reactivates its data, after validation" means a new `users` table inherits an old `users` table's rows if types happen to fit. That breaks deletion expectation and privacy (remove-PII-column then re-add must not bring values back). Fix: require explicit intent — fresh-create vs restore — or require `prune` first; type-fit alone is not consent. Same gap for `durable→ephemeral`: RFC says "refuses" with no path forward. Specify the two-step `prune` then convert.

**3. Row-identity and delete propagation incomplete.**
§3 handles dormant-column delete but not dormant whole-table images, and assumes ids are never reused without defining it. State: ids immutable, delete of an active row deletes both dormant-column values and any dormant-table image in the same txn, and reused explicit ids get defaults not resurrected values.

**4. Assets and expiry pin storage.**
Dormant asset homes "remain live but unreadable" with no active row to delete them, so bytes pin until `prune`. Bound this, define expiry on reactivation (rows past expiry vanish at once), and that dormant rows run no jobs/sweeps.

**5. Default-capture semantics ambiguous.**
"Capture interpreted defaults" then "restoration precedes builders" leaves which default wins unclear. State: rows with dormant values restore verbatim; rows without them (written under older release) get the candidate literal/optional-null; `now`/`viewer` defaults never backfill; required-without-default refuses with count plus ≤5 ids.

**6. Hot-control security and TOCTOU.**
Socket in deployment dir reuses 0700/0600 (`private_fs`), but RFC omits peer-credential check (same-UID only), `lstat`/`O_NOFOLLOW` stale-socket replacement rule, command-flock path, message bounds/timeouts, and the staging trust gap: today `deploy` stages then activates holding one owner ([verbs/releases.rs](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4/src/verbs/releases.rs:49)); hot splits staging (CLI) from compile (serve). Server must re-validate candidate id to an immutable `releases/N` dir, forbid path choice/traversal, and validate native `wasm`/worker artifacts (cargo-reported artifact, not lexicographic scan). Otherwise a same-UID attacker swaps staged source.

**7. Atomicity and lock order.**
RFC asks to hold "existing engine writer guard" across swap/generation, reader retirement, ephemeral rebind, change invalidation, sync wakeups and worker revision, while validation already holds `BEGIN IMMEDIATE`. Define order (fallible prep before commit; post-commit publication infallible assignments only) and degraded state when worker/native spawn fails after DB commit. Specify idempotency: timeout/EOF is ambiguous, inspect `current` plus durable history, retry reuses the same release id, never allocates `N+1`; CAS checks `expected current release` inside the txn (existing `check_selected_release` plus release check in [engine/mod.rs](/home/ccheever/projects/sb4-ws-roll/snapback4/crates/snapback4-core/src/engine/mod.rs:588)).

**8. Disclosure.**
`E_ADOPT` with "actual conflicting values/index keys" can leak PII through diagnostics. Bound byte sizes and restrict to operator channel, consistent with existing meter/cut privacy.

## Generation / clients

Fresh monotone generation on every changed activation including `A→B→A`, never release-number-as-generation, is correct and matches current `previous+1` logic. Clarify: identical schema/programs retains generation but still records a release event; `prune` never bumps generation; old watermarks/cursors refuse (`E_SYNC_GENERATION`-family) and queued intents are re-judged under new authority, never silently dropped or executed as old IR.

## Tests and docs

Acceptance list omits: socket perms/symlink/peer-cred, racing hot commands, writer-during-validation, `kill -9` mid-activation/prune, ambiguous-reply retry, legacy-store migration, and device-format stability. `SERVER.md` plus a security/OPS note is needed, not a one-line pointer.

Fix the storage schema, restore-vs-create intent, asset/expiry bounds, socket trust and lock-order sections, then re-review.


## muse3 — 2026-10-12

**Verdict: NOT READY** — the retention and hot-activation design is close, but several load-bearing rules are unimplementable or unsafe as written.

Reviewed [LLP 3000.000.000](llp/3000.000.000-retained-storage-and-hot-release.rfc.md) (round 2). Spot checks confirm no existing `_dormant_` / flag implementation in the tree, so this is greenfield; no code conflict found.

Concrete fixes required:

1. **Downgrade guard must be enforced, not documented.** "Old binaries must not operate" as prose does not prevent an old binary from opening a retention-enabled deployment and discarding or ignoring dormant tables. Add a durable format marker and a startup version check with its error code.
2. **Define the same-key dormant-cell merge rule.** Partial restoration says to merge prior dormant cells with newly retired cells "without overwriting their independent values," which is impossible when both hold `(t, id, column)`. State the winner (e.g., newly retired wins) or a refusal, with a test.
3. **Close the forward repair deadlock.** New rows legitimately written under the older schema have no dormant value; forward then refuses on a required default-less column, but the older release cannot backfill a column it lacks. Give the exact repair sequence (deploy-with-default first, delete-then-retry, or equivalent).
4. **Specify dormant isolation as mechanism.** State how app SQL projections are blocked from `_dormant_%` (prefix deny or equivalent) and how direct asset fetch by id is denied when the active schema has no home; add tests for both.
5. **Bound retention operationally.** Keep-forever plus keep-zero-row-definitions plus all-or-nothing prune is a disk-exhaustion path. Add dormant byte accounting to `prune`/`releases` previews and either per-item prune selection or an explicit rationale for all-or-nothing.
6. **Pin the hot-path commit boundary.** State that reader-factory preparation failure aborts before commit versus lazy-retry after, keep wake/sync work outside the writer guard or justify holding it, state the server continues after the 120-second client timeout, and expose degraded-worker state in `releases`.
7. **Publish the flag and error matrix.** Exact signatures and interactions for `deploy` / `rollback --to` (including forward-via-rollback), `--restore-dormant`, `--allow-destructive`, plus the `E_ADOPT` payload, repair/inspection commands, and the stop/retry string.

Minor: reconcile activation-revision bump on equal-hash redeploy with generation retention, and define catalog-number reuse precisely.
