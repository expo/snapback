## Where the panel stands (orchestrator's reading — dissent if wrong)

After round 2, Fable and grok both moved to the position codex and the
orchestrator held: **TS-syntax bounded data programs lowered to a small IR whose
relational operators are the algebra**. The orchestrator recants "static
analysis is an aid, not the gate": `check` on the static certificate (shape
families + examined bound + steps) **is** the gate; the trace **is** the closure.

The converged core, as the orchestrator will write it up:

1. **One language, two kinds of program** (`query`, `mutation`) plus a
   different kind (`effect`) outside the data plane. TypeScript syntax,
   type-checked against a custom `lib.d.ts` (no `Date`, `Math.random`, `fetch`,
   `while`, recursion, dynamic table access). Result types inferred by `tsc`.
2. **Reads only through the typed API** — `get`, `scan(index, prefix, {order, take})`,
   `exists`, `recurse({depth, fanout})` — every collection read bounded;
   `Unbound` is a legal intermediate and an illegal result.
3. **Three rules that keep static analysis alive under real control flow:**
   (i) loop domains carry static cardinality — pages, literals, and arrays
   derived from schema-bounded columns; (ii) read keys are *shape expressions*
   (args, `viewer`, literals, fields of rows from traced sites) or the site is
   marked `computed` in the certificate; (iii) rule bodies are algebraic
   predicates (single expressions), so they hoist and review.
4. **Row rules are the only authorization**, deny-by-default, `public(reason)`
   conspicuous and unlocking nothing. Maintained aggregates are schema
   constructs (`maintain.count/sum … by …`) with compiler-generated same-commit
   maintenance and declared overflow behavior. `AllOrRefuse` only on
   schema-capped domains.
5. **Static certificate at `check`**: `planHash, schemaHash, ruleHashes,
   evaluatorVersion; readSites[{index, prefixTemplate: arg|viewer|const|computed,
   take, maxCalls, hoist}]; writeSites; maintainedAmplification; maxExamined;
   maxRuleProbes; maxSteps; maxOutputBytes; resultType (cardinality-typed);
   completeness: page|capped|maintained; predictionSites[{transition, reads,
   mode: hydrate|partial}]; indexesRequired`. Refuse above the app ceiling `G`
   (loud default), never as a function of invisible-row counts.
6. **Dynamic trace per execution** — ranges with stop-reason (`limit`/`exhausted`)
   including absences; examined viewer-visible rows including a one-row halo;
   verdicts (bound to `ruleHash + pinned inputs + principal + authEpoch`) only
   for rules over hidden inputs; asserted `⊆` certificate. The trace is the
   invalidation predicate, the offline closure, the OCC set, and the
   completeness detector.
7. **Shared fact on the crux**: local re-execution is exact while
   `Reads(P, D₀ ⊕ Δ) ⊆ Coverage(trace)`, `partial` otherwise, never invented;
   the **prediction closure** `(query, mutation)` is derived at `check` for the
   substitution-closed subset (shape-keyed reads) and hydrated at subscribe;
   computed-key reads are `partial` under prediction, visibly. Revocation
   during a partition is unobservable in every design.
8. **Client = range-indexed store per (table, index) at one version + verdict
   cache + outbox + IR evaluator**; the eight runtime states
   (`hydrating|fresh|stale|partial`, `predicted|queued|committed|rejected`) are
   the whole offline contract; one engine-owned store-wide `maxOfflineAge`
   (mechanism required, value a ruling); sign-out destroys the store key.
9. **Server: one Rust IR interpreter inside the SQLite transaction; JS not in
   the authoritative path**; subscriptions indexed by range; rerun-and-diff is
   the v1 live lowering; `maintain` the only incremental path; Postgres is a
   second physical lowering, program-near-DB.
10. **The dev loop is co-equal** (one generation identity across schema, server,
    generated client, bundler, cache; `check`/`dev`/`verify`).

Remaining genuine disagreements (answer each with a verdict and a reason):

- **D-A Client evaluator**: TypeScript evaluator (Fable; runs everywhere, needs a
  conformance corpus + hydration replay check) vs Rust interpreter compiled to
  WASM (grok, orchestrator; same bytes, but mobile WASM availability is the
  question — the orchestrator is verifying Hermes v1 WASM status in RN 0.84).
  Note Fable's hydration replay check (re-execute over the shipped closure and
  compare to the shipped result) is a per-execution conformance test either way.
- **D-B Computed-key reads**: admit + mark `computed` + `partial` under prediction
  (grok, Fable) vs refuse (algebra purists) vs require a written row (mentions
  table). Verdict?
- **D-C Verdict binding**: `(ruleHash, pinned inputs, principal, epoch)` so a
  read verdict serves a compiler-equivalent write rule (Fable) vs codex's tuple
  with `planHash + args`. Which, and are verdicts in v1 at all?
- **D-D `maxOfflineAge` default**: 24 h (today's protected posture) vs 7 d.
- **D-E Halo**: content of row N+1 and the key of N+2 (grok) vs one examined
  row only (Fable).
