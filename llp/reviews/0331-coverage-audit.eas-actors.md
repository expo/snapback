- Flag tested: the engine's `evaluationContext.cascadingDeleteCause` (and `evaluationContext.previousValue` for the SET-NULL arm). From the public `@expo/entity` source: `const deleteCause = evaluationContext.cascadingDeleteCause;` … checks `parentEntityClasses.some((cls) => deleteCause.entity instanceof cls)`, then `valueInThisEntityReferencingParent === valueInParent` (delete arm) or `valueInPreviousValueOfThisEntityReferencingParent === valueInParent && valueInThisEntityReferencingParent === null` (set-null arm). The flag is set by the **engine's deleter** when walking declared edges, not by any Universe program.
- Program: `DeleteUserBackgroundJob` (`src/background-jobs/jobs/DeleteUserBackgroundJob.ts:58-154`) runs as the deserialized *dispatching viewer* (a sudo user session — `UserDeletionUtils.ts:44` `enforceSudoSessionUserViewerContext(user.getViewerContext())`); re-checks `getCanViewerDeleteResultAsync(UserEntity, userToDelete)` and the account's delete rules, throwing `'…indicates that the background job was dispatched erroneously or a cascading privacy policy is incorrect.'` (L74-94); refuses special accounts (L96-100); deletes apps sequentially "to preempt cascading deletion via account deletion" (L119-126); nullifies references; batch-deletes ledger items; final `deleteUserWithinTransactionAsync`, inside which the *account* delete runs under `withEndOfTransactionInvalidatingOmnipotentViewerContextAsync` (`UserDeletionUtils.ts:149-156`). `DeleteOrganizationAccountBackgroundJob` (`…:47-133`) is dispatched by an OWN holder (`AccountDeletionUtils.ts:27`). `DeleteSSOUserAsSSOAccountOwnerBackgroundJob` is the org-owner path (omnipotent, L21).

### 1.8 Anonymous / public

- Anonymous = absence of credentials (`middleware/viewerContext.ts:145`). Rules are allow-lists whose kind checks SKIP for anonymous, so the default is deny; `DenyIfAnonymousPrivacyPolicyRule` is unused.
- Public reads in this facet: `SnackPrivacyPolicy.ts` read = `AlwaysAllowPrivacyPolicyRule`; `AppPrivacyPolicy.ts` read rules are omniscient ∨ account permission ∨ scoped ∨ staff only (no public rule at the entity level — public project pages are another facet's concern); audit logs: `EvaluateIfNotStaffModeSessionPrivacyPolicyRule(new DenyIfSourceNotPublicPrivacyPolicyRule())` — "deny if not public but only if not expo admin with staff mode" (`AuditLogPrivacyPolicy.ts:52-55`).

### 1.9 In-process escalation (the structural metric)

Non-test call sites: `withOmniscientViewerContextAsync` 98, `withOmnipotentViewerContextAsync` 82, `withEndOfTransactionInvalidatingOmnipotentViewerContextAsync` 38 — **218** total (apiv2 80, data 48, internal 44, graphql 19, middleware 11, push 7, background-jobs 5, utils 4). Plus the four bare `new Omni*ViewerContext(...)` constructions in the middleware. EAS has **no system principal**; it has a scoped bypass used inside viewer programs, and 164/148 of 168 policies name it.

## 3. Answers to the five key questions

**(1) Is every actor kind an ordinary opaque principal + relation rows, with no `principal.kind` in rules?**

| Kind | Yes/No | Why |
|---|---|---|
| Anonymous | **Yes** | It is the absence of a viewer; EAS's own `DenyIfAnonymous` rule is unused (0 policies) because every allow-rule already SKIPs. Public reads are `public(reason)`. |
| Regular user | **Yes** | The principal. The implicit "primary account ⇒ all permissions" becomes an explicit owner row minted at registration. The 10 policies using `AllowIfRegularUserOwner` (passkeys, OAuth identities, sudo challenges) are identity-credential tables that leave the app plane. |
| SSO user | **Yes** | Login identity `(org SSO installation, subject)` is exactly the account model's binding; the org VIEW row is an ordinary relation row; IdP-refresh liveness is session policy inside the identity kind. The one program-level kind test ("SSO viewer is not permitted to accept an invitation") becomes `!exists(ssoMembers.byPrincipal,[viewer])` over a row the identity kind writes at mint — the ruling-2 pattern. |
| Robot | **Yes — the cleanest case** | An API-key principal with no login identity; the app's `createRobot` program minted it, so `robots {principal}` is an app fact and "humans only" is `CORE(neg)`. "Robots can't have sessions" is a credential-type fact in the identity layer. |
| Partner-provisioned actor | **Yes, by reduction** | The partner is the principal that calls; the provisioned user is a target. As built (partner token + user session on one request) it is the platform app's two-principal execution — dimension Q, OUT. |
| Scoped account actor | **Yes, as a separate principal** | See Q2. |
| Omniscient / Omnipotent | **Not actors** | In-process bypass, 218 sites, named by 164/148 policies. They are the thing the proposal refuses (an elevated bypass) and replace with Tier 1's one `system` disjunct per table plus Tier 2's `getHidden`. The mapping exists; the cost is that EAS uses it far more pervasively than any paper app. |
| Staff mode / internal session | **Yes, as a separate principal** | See Q3. |

Net: no EAS *actor* requires a `principal.kind` term. Every kind test in a rule (`is*ViewerContext()`, 8+5+4+3+2 policy files) is either redundant with an owner/role comparison or replaceable by a probe over an app-owned table that records who minted the principal.

**(2) The scoped account actor.** It is *attenuated delegation*: the same underlying user, a strict subset of permissions (`ScopedUserPermission = VIEW | PUBLISH`), opt-in per table (only rules that test `isScopedAccountActorViewerContext()` fire — 80 policies), live-linked to the user's current rows (the rule calls `doesViewerHavePermissionOnAccountAsync(viewerContext.underlyingViewerContext, …)`), and stateless with a 1–24 h TTL; the JWT payload naming a job/build is not verified (`verifyAsync` reads only `sub`). It is **not** a session attribute (that would be OUT:X9) and **not** a principal set (a binding would give the job the user's *full* role — sets union, they do not attenuate). It **is reducible to a separate principal with copied rows**: the identity layer mints job principal J at token mint; the mint program copies the user's `accountMembers` rows for the account(s) in scope into rows for J using a *distinct role enum* (`buildViewer`, `buildPublisher`), so each table's rule names explicitly whether it admits those roles — which reproduces today's per-table opt-in as reviewable schema. Live revocation is preserved by having `memberRemove` / `roleChange` delete J's rows for that (user, account) in the same transaction — a bounded, indexed delete (active job tokens per user per account), not the events design's unbounded closure. The engine-maintained form (`maintain.rows` from `accountMembers`, X13, Tier 2) is the lossless spelling if the app would rather not write the repair. Verdict: CORE with the repair; TIER2:X13 without it (loss: revocation lag ≤ token TTL — which, note, is already the case for the *token itself* in EAS today).

**(3) Staff mode / sudo.** Staff mode is a *session* fact (`staff_mode_expires_at`, 120 min) gated on a *principal* fact (2FA + ADMIN on `expo`), and it is overwhelmingly read-only (123 read lists; one write list, lint-guarded). Sudo is a session fact never consulted by a rule; it gates programs (9 sites). In the proposal a session carries no roles and there is no time or session term, so **as built both are OUT:X9** (and the time bound is REFUSED:X6-strong). Both reduce: staff mode → a *separate staff principal* S (`staff {principal, role: staffRead | staffWrite}` global role rows; `staffPersonas {staff, person}` for attribution) whose session the identity layer mints only after a step-up and with a short fixed TTL — `|| exists(staff.byPrincipal,[viewer])` on read rules is CORE, and the internal site's READ/WRITE distinction becomes two roles named explicitly on read vs write rules. The product loss is UX: a principal switch (the client holds a second session) instead of an in-session toggle. Sudo splits: the credential operations it guards (password, e-mail, passkeys, OAuth unlink) are identity-layer programs whose step-up lives inside the identity kind (CORE); the app-program uses (invitations on old accounts, self-deletion, SSO-user deletion) cannot be expressed and are dropped (OUT:X9, DR) — the honest reduced product has no re-auth step-up on those three programs.

**(4) Deletion cascades.** The flag is `evaluationContext.cascadingDeleteCause` (with `previousValue` for SET NULL), set by the `@expo/entity` deleter while walking edges declared as `EntityEdgeDeletionBehavior.CASCADE_DELETE_*` / `SET_NULL_*` on entity fields (174 + 75 edges) — **no Universe program sets it**. The rule reads "this child may be deleted/nulled because its declared parent (matching FK) is being deleted in this cascade", and it is evaluated under the *deleting viewer's* context (background jobs deserialize the dispatcher's viewer, `BackgroundJobRouter.ts:114-120`), so authority is transitive from the parent's delete rule to children the viewer's own rules would refuse (audit logs, ledger items, sessions). So yes: it is a viewer-invoked program writing rows the viewer cannot — Tier 1's continuation is the honest interim (viewer half: parent delete rule + attempt timestamp; system half: the cascade, with `|| viewer === system` on every child table's delete/update rule — ~40 tables in this facet). But the *shape* is more specific and cheaper than "system is total": it is a transaction-local **deletion provenance** — the exact mirror of Tier 0's creation provenance ("admissible only while a new scope incarnation is being inserted by the same derived viewer in the same transaction"). The ledger names the class (X19, event-coupled two-row write; RFC dimension C lists "cascade") but no tier admits a declared `ref(parent, { onDelete: 'cascade' | 'setNull' })` edge. Not `getHidden` (no hidden read is needed — the parent row is readable by the deleter). Verdict: TIER1 now; the strongest candidate in this facet for a *new schema primitive* that is nonetheless already named as a class.

**(5) Invitation by e-mail.** Two halves. The **token half** (`acceptUserInvitationByTokenAsViewer`) is the events-style contact/guest principal minted at link redemption — ruling 2's paved form — and the grant the viewer cannot make for themselves becomes a `where`-probe on the invitation row instead of an omnipotent write: CORE(where). The **e-mail-equality half** (`AllowIfViewerEmailMatchesInvitationEmailRule`: a regular user whose *verified login e-mail equals* `invitation.email` may read, accept, or decline without the link; the dashboard's pending-invitations list) is **not CORE** — the login e-mail is protected identity state, never a rule term. It is **TIER2:X3(sets)**: mint a contact principal C for the address at invitation time; at e-mail verification the identity kind binds C to the user (`existsAny(invitations.byPrincipal, {principalIn: viewer.bindings})`), with the closure interim being the identity kind pasting/rebinding the relation row at verification — ruling 2's write at a second lifecycle point. It is **not NEW** (events and Notion carried the set), but it does require the account model's sentence "mutable/shared email is never an automatic principal-link or merge key" to be carved out for the verified claim of a *contact* principal, which is precisely what the events design already assumed. Reduced product without it: token-only acceptance (the e-mail carries the link), no in-app pending-invitations list.

## 4. Facet verdict

The proposal, as ruled, carries this facet: every EAS actor kind — anonymous, password user, SSO user, robot, partner-provisioned actor, scoped worker token, GitHub-installation robot, staff — reduces to an ordinary principal plus relation rows the app or the identity layer writes at mint, and every kind test in EAS's rules is either redundant with an owner/role comparison or a probe over an app table that records who minted the principal; `principal.kind` is never needed. Two things EAS says that the rule language cannot are session-state elevation (staff mode, internal read/write mode, sudo) and verified-e-mail equality; both reduce (a separate staff principal with a short-TTL session and explicit `staffRead`/`staffWrite` roles; a contact principal bound at verification) with named losses (a principal switch instead of a toggle; no step-up on three app programs; token-only invitation acceptance in the interim). The single change that flips the most rows is not in the rule algebra at all but in the identity layer's contract: generalize ruling 2 so the identity kind may write ordinary relation rows at *every* lifecycle point where it alone knows the fact — mint (robot, SSO, partner, job token), e-mail verification, and step-up — which turns rows 6, 7, 9, 12, 13, 21 into CORE at once. Genuinely NEW versus the 37 paper apps: nothing that lacks a ledger name, but two things at a scale the corpus never reached — attenuated delegation (a principal acting with a strict subset of another's live authority, opt-in per table, 80 policies) and pervasive in-program escalation (218 omni sites; 164/148 policies name it), which the proposal absorbs into Tier 1's per-table `system` disjunct at a visible cost on essentially every table; and the cascade edge (174 + 75 edges) as transitive deletion authority, the deletion mirror of Tier 0's creation provenance, which the ledger names as a class (X19) but no tier admits as a schema primitive.
