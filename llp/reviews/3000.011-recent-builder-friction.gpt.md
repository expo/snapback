**1. Contextual compiler guidance — READY WITH CHANGES.**

The direction is sound, but the increment should be materially smaller than a diagnostic framework. `bind/program/control.rs::helper_arguments` already supplies the helper name, parameter, expected and actual types, and the argument's source site. It also deliberately accepts a row of the same table for a reference-shaped helper argument. The diary's cross-table app-post/feed-event confusion is therefore not evidence that all rows must be converted to IDs. `bind/mod.rs` already constructs `N_NEVER_COMPLETE` with the actual rule, missing deciding columns, and a proposed index order. `bind/residency.rs::change_notes` deduplicates root causes and sites, and `operation_lines` exposes them through the existing output. `bind/residency/presence.rs::reject` already tracks the presence origin and names a fallible or variable-cost arm. See the current prediction card as well as RFC §§1–2.

The useful missing pieces are precise: prefer an existing compatible index instead of suggesting a redundant declaration; connect the missing equality to an in-scope conversation argument when that relationship is established; and connect a presence origin/guard to the actual fallible consumer. An exact matching reference field can be named if the bound type proves it. None requires a new analyzer, a second guide, or language-specific feed casts.

Concrete resolution: record the existing output for the three reduced cases before changing it. Keep already sufficient cases unchanged. Add only the absent source/relationship detail through the current terminal/JSON paths. Prefer factual explanations and a tested card when a rewrite cannot be established. Do not recursively compile speculative whole-program repairs on ordinary `check`, or add generic fields merely to fill a proposed schema. Preserve RFC §3's prohibition on automatic hoisting or policy changes: moving a read can introduce refusal into a branch that previously did no work. Corrected snippets and deliberately ambiguous cases should be tested, with unchanged acceptance, prediction classification, and authority.

**2. Digest beyond one chunk — NOT READY as the proposed live-message remedy.**

The Research parent identifies a real, measured burden and correctly distinguishes same-run recovery, replacement-run deduplication, and provider delivery. The RFC also honestly disclaims an emission-time snapshot. That honesty exposes the unresolved product decision rather than resolving it.

High finding: RFC §2 admits a message contribution, then §3 retains eligibility as observed at that earlier read. Consider a live unread message counted in chunk A, which expires or is tombstoned before emission chunk B. The recipient remains a member, so the final membership check passes and the stored positive count is emitted. A read-cursor advance creates the same stale-unread problem. `benchmarks/briefs/social-messenger.md`, M8 (especially lines 752–764), requires correct digest counts and says expired/tombstoned content never contributes. Quiescent equivalence and membership rechecking cannot establish that contract for the intended live workload. A separate reconciliation pass only moves the race unless its consistency boundary is defined. Do not silently treat the latest builder's static proof as proof of this concurrent property.

High finding: replacement identity is still incomplete. The contribution key in §2 names policy/period/recipient/message, while §3 leaves membership incarnation and recomputation unresolved. A remove/rejoin can encounter old markers and totals, including when an application reuses its row identity. The example membership table has no declared public lifetime token. A policy version also must not accidentally create a second delivery for an already completed recipient/period. Define the business delivery key separately from an accumulation-policy/version identity, and make incompatible unfinished work fail or rebuild under an explicit decision. An immutable time index prevents row movement; it does not define what happens to late backdated inserts behind a cursor or to a replacement run with a different captured upper bound.

Medium finding: the algorithm's fanout and retained state are not yet bounded as an installable supported shape. One message chunk can still enumerate many recipients. Per-message/per-recipient markers are O(period messages × recipients), with no cleanup in the first increment. This may be an authoring improvement but can preserve the same large write/storage cost that motivated the proposal. State the supported membership cap, both inner and outer work, terminal-period behavior, and replay/retention horizon before claiming a reusable recipe. M8 also needs new followers and Following posts; this is only a message component unless the other aggregates and final one-payload boundary are explicitly composed.

The minimum useful replacement is a measured direct-count experiment, not another accumulator by default. The current binder lowers `count(page)` to `Builtin::Count`; `engine/runner.rs` evaluates an `Expr::Scan` into an array before taking its scalar length (around lines 588–607). `engine/read.rs::scan_prepared` already owns the difficult read semantics. Investigate one narrowly recognized count consumer that avoids retaining an otherwise unused full result array, using the existing scan machinery. This is a hypothesis, not a reviewed implementation or a claim that it removes the 16 MiB failure. A narrow projection already failed in the diary; a differently spelled projection is not sufficient evidence.

Qualify it on the exact busy-chat input against the existing direct recipe before expanding scope. It must preserve the transaction snapshot, expiry and tombstone checks, recipient authorization, filtering order, examined/rule/step charges, page limits, cut/refusal behavior, dependency/expiry tracking, and all applicable store/device semantics. Heap accounting must reflect actual work under the same ceiling; removing allocations is different from discounting rows. Do not silently convert `count(first N ...)` into a whole-domain count or emit a partial scalar when the domain did not finish. If the exact recipient computation fits, retain direct atomic read-and-emission, add a recipient/period emission marker in that transaction for replacement-run idempotence, and keep provider idempotence separate. Measure normal and worst-case bodies, not only tiny rows. If it still does not fit, record that boundary without manufacturing a successful fix.

A paged recipe is a second possible direction only for explicitly finalized immutable inputs and stable eligibility, or for a separately accepted contribution-time notification policy. Period membership, source completeness, lifecycle identity, and final delivery authority still need definition. That would not by itself satisfy Clique's mutable/expiring unread-message contract. For any live prototype, interleave actual scheduled chunks with expiry, deletion, reads, and leave/rejoin; a single `run_job` invocation passes its pinned `now` through all chunks and is not sufficient evidence of advancing-time behavior (`engine/job.rs::run_job`). Do not ship an installer before this semantic choice is settled.

**3. Feed integration and overflow — READY WITH CHANGES.**

There is a useful small bridge here. The current installer already compiles the combined program, renames declarations, handles collisions, produces typed client wrappers, and turns prefixed mutation entry points into helpers. The current feeds card's “Wire into an app” section (starting at line 609) already specifies the atomic manual bridge, distinct repost identity, and original media home. The new benefit is removing handwritten app-post/feed-event translation, not introducing those guarantees for the first time.

High finding: matching Quarry types cannot establish safe public disclosure. The installed recipe's source event rows publicly expose actor, author, post ID, repost attribution, and time; its graph is public too (`guide/feeds.md`, source-event/follow declarations and the sizing/acquisition table). An adapter that accepts an arbitrary private app post/follow relation can disclose that metadata even if joining the original media/card later refuses. Require an explicit supported public social model, or an explicit documented decision to publish those reference facts. Refuse unsupported private mappings by default. A table reference validates an identity value, not target existence or visibility (LLP 3000 §7, reference-ID decision); bridges must keep ordinary existence, ownership, and audience checks. Do not infer them from names or types.

Concrete resolution: start with the canonical published public-post/follow shape, with explicit mapped columns, and generate one understandable helper module for register/publish/remove/follow/unfollow and the explicitly supported repost mapping. Unsupported schemas get a named refusal and retain the manual path. Preserve same-transaction app/recipe writes, no public bypass operation, no rule widening, and collision/no-overwrite behavior. Specify what happens when source IDs differ, cards are deleted, events are removed then retried, and an existing app is backfilled. Backfill should reuse mapping invariants, not impersonate system-authority work as an ordinary viewer helper. Do not create a general schema-adaptation framework to save several lines of bridge code.

High scope finding: an online merge is not yet an overflow solution. `guide/feeds.md::addFollow` checks `tryPull` for every recipe follower during promotion. A dormant saturated follower still blocks the writer regardless of which read query the newcomer uses. To offer per-reader overflow, write admission, membership in the recipe graph, promotion accounting, old routes, and migration must change together. RFC §3 leaves that unspecified. Its wording should select either an entirely separate application serving model for measurement or a fully described per-reader mode; the latter is a larger design.

For this increment, retain the small bridge and run the alternative only as a separate experiment. Do not add automatic fallback or change cursors. Preselect its workload and latency/completeness criteria, including the saturated-existing-follower case, and report full traversal and the distinct history retained by each model. The earlier 500-follow measurement in LLP 3000.007 §21.3 is real counterevidence; a first-page win or a meter-cut prefix cannot establish a complete feed. Keep maintained-column work with LLP 3000.007.001 and outside this generator change.

**4. Offline-ready starters — READY WITH CHANGES.**

Cached-route-first navigation, explicit incomplete/stale display, and recovery of nonpredicting writes are worth demonstrating. The current Expo `Thread.tsx` already uses `usePendingWrite` and displays stale retained reads; the new work is not adding that hook. It does not pass a persisted mutation ID to the hook on reopen, so a complete durable-intent example is still useful. The known-room online-create trap was an application error, not proof that the current starter itself creates rooms before opening them.

Medium scope finding: there is no complete existing default web application starter to patch. `verbs/init.rs:28` emits the schema for plain `init`; `--online` emits a client/backend stub; `--expo` copies the Expo chat app. Its client chooses native versus online and does not itself select the web device. Select a concrete first deliverable, such as the Expo starter plus its explicitly supported production web output, or the existing Vite chat reference as a separate documented example. Do not silently turn a small starter correction into a multi-bundler scaffolding product.

High safety finding: keeping tokens/media/API bodies out of CacheStorage is necessary but insufficient. Cached route IDs, pending-write IDs and any displayed failed draft belong to the backend identity and principal that created them. A switch to B must not show A's held route, receipt, draft, or a delayed A callback, and must not replay A's intent under B. Follow the existing pending-write/sign-out policy instead of inventing automatic queue transfer. Test two accounts on the same origin with a pending nonpredicting write and delayed work, not only whether the service-worker cache contains an authenticated response. Session-expired and unavailable sessions must not become an unsigned cache route. These are proposed acceptance requirements, not a claim that the SDK currently leaks accounts.

The current hook tracks one write and its optional saved ID; `run(args)` mints the ID internally (`packages/snapback4/src/react.tsx`, around lines 166–241). For a crash-safe example that knows an ID before dispatch, mint and persist the minimal account-bound UI intent metadata first and use `client.mutate(..., { id })`; recover via `client.write(id)` or the hook's saved ID. This metadata must not become a competing outbox or resubmission loop. Decide how an unknown/evicted receipt is shown rather than inferring success, failure, or creating a new intent. Reuse the SDK's durable queue as the source of admission/settlement truth.

For the shell, cache only a build-known allowlist of immutable assets plus a generic non-personalized entry. A blanket same-origin fetch handler or caching arbitrary navigation HTML can capture personalized pages or cross app boundaries. Define the base path, deep-link fallback, worker scope, update activation and retention of assets required by an older open tab. Avoid forced activation that makes old code run against a new shell unexpectedly. Keep development uncached, and prove a fresh page realm opens offline. The RFC's old-tab upgrade and real-client residency exercises are good; no automatic blanket horizon changes or new read-state API is needed.

**5. Coordinated development commands — READY WITH CHANGES, retry/diagnostics first.**

The repeated CLI race is a worthwhile fix. The proposed shared advisory lock is not yet supported by evidence. SQLite already serializes writers and uses a five-second busy timeout (`snapback4-core/src/store.rs`). `serve_adoption.rs` retries typed BUSY/LOCKED errors at startup and BUSY/LOCKED/generation errors while watching, reports pending adoption, and reopens after an external adoption. `tests/check.rs` already covers startup lock release and watching-host recovery after CLI adoption. The remaining concrete asymmetry is that `verbs.rs::run` opens/adopts once and exits on error; the host and stopped-store commands need not acquire a new lock service to improve it.

Concrete resolution: reproduce both diary races and add a bounded pre-admission retry around the existing open/adoption path using typed SQLite lock errors, with elapsed wait, intended operation, available adoption/generation context, a deadline and a useful next step. Recompile or refuse if the intended source changed before admission. Preserve other I/O/schema errors. Do not use string matching on every `E_STORE`, change production behavior incidentally, or serialize read-only inspection.

High correctness boundary, already recognized but not solved by the RFC: do not wrap `run_job` or `mutate` in a general retry. `engine/job.rs::run_job` enqueues a freshly minted ID before running chunks; `verbs.rs` currently learns its final ID only from the returned run, and calls ordinary mutation execution with no supplied write ID. An error or interrupted caller after admission cannot be retried as a new invocation with an exactly-once claim. The first increment should stop at safe pre-admission retry; if later work exposes admission/observation separately, make the committed run identity recoverable first.

A second advisory primitive across normal mutations, job chunks, adoption, and host publication adds ordering, starvation, canonical-file identity and production-interaction responsibilities. An advisory lock also does not inherently guarantee fairness. Escalate to that design only if deterministic reproduction and latency evidence show the existing transaction/timeout path cannot meet the stated requirement. The current documents already allow this smaller alternative; revise §1 so the implementation does not start by building the larger mechanism.

**6. Qualify the built application — READY as an execution plan.**

This is the clearest useful proposal. The current `guide/witness.md` already describes installed Release execution, app-specific assertions, kill/relaunch with saved IDs, failure receipts, video and a run manifest. Implement the missing assertions in the actual Clique app and use that tool. The native acquisition exercise, realistic failure classes, stopped backup/restore, and separation of effect admission/provider acceptance/device receipt all follow existing owners. A second harness or new global evidence registry would make this worse.

Keep the package and app identity binding explicit. The existing witness manifest identifies installed bundle/build information and hashes its execution artifacts; record package pins and built app/native/backend artifact identities in the existing run record as well. A package-lock entry alone does not prove which native binary was installed. Missing Android, physical-device, peak-memory or power-loss results remain absent. Native, deployment and provider work complete as separate cells, and missing provider identity is not a reason to block independent native/browser work.

The Research parent's attribution needs one update. The local final report already says native exports were the proof permitted by its environment and that simulator assertions were not run. Root additionally supplied a primary-evidence quotation from the retained `prompts/astra-snapback4.md`: “Every milestone also produces an iOS Hermes bundle export as a build artifact; simulator proofs are not required.” Root reports `instrument/ENVIRONMENT.md` says simulators exist. I did not independently read those remote retained files. Treat that supplied fact as benchmark scope, not a demonstrated product discoverability failure or an unexplained missing capability. It does not turn an export into native execution, but it changes the causal interpretation of its absence.

The clean comparison is an unchanged frozen Clique authoring run plus a separately recorded application qualification extension using the produced app. If simulator proof is required from the builder during the timed run instead, version that instrument/environment change and disclose the additional work. Do not attribute a native-proof improvement solely to new product features when the instructions changed. Preserve failed runs and predeclared probes. Real provider delivery still requires the selected test account/device/recipient described in the RFC; prepare the adapter and labeled doubles first and report any unresolved provider ambiguity.

Keep the observations, their limited generality, and the distinction between observed refusal and product defect. **Minimum useful implementation scope for the authorized program.**

1. Reproduce the three diagnostic cases and improve only the missing existing-index or dependency information. Ship no second analyzer or broad autofix mechanism.
2. Reproduce the exact digest heap failure, then measure a narrow single-transaction count improvement with the established read/meter semantics. Ship it only if it proves useful. Keep live multi-chunk digest correctness unresolved if it does not; do not package a semantically weaker accumulator as success.
3. Generate a small, strictly typed, atomic feed bridge for the declared supported public model. Keep the hybrid recipe unchanged. Measure the online alternative separately; no unqualified fallback or cap increase.
4. Improve one actual starter/reference output with account-bound cached navigation, minimal persisted intent IDs, truthful read/write rendering, and narrowly scoped production shell caching. Exercise real offline reopen and account change.
5. Give local `run` bounded, typed pre-admission retry and actionable adoption diagnostics. Add no advisory writer coordinator unless the reproduced evidence requires it.
6. Publish the selected qualified changes using the existing publication path, rerun the comparable Clique instrument, and execute the actual application's installed native Release witness as an explicit additional coverage cell. Run isolated deployment/restore independently and complete provider delivery only on its selected authorized test identity.

This selection removes demonstrated authoring and lifecycle work while keeping the two open design problems visible: exact live digest accumulation across transactions, and feed admission beyond the hybrid pull envelope. They should not be hidden inside a generator or declared solved by a successful static fixture.
