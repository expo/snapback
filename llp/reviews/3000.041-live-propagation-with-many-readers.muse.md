## 2. W1 soundness — not yet sound; misses required wakes

**Touched-partition availability: half-true.** The partition log does name partitions per row event (`snapback4-core/src/partition.rs:200-221` `log_events::{put,del,scope,join}`, `runner.events`, `append(tx, seq, events)` at `:850`). But the commit publication path does **not** publish them: `committer.rs:353+` `continue_durable_publication` publishes only `(seq, store_id, generation)`; `member_store.rs:148` `record_commit(seq, at, source, touched: &[String], writes)` records **tables**, not partitions. Deriving partitions at commit time means threading `runner.events` (or a re-derivation from row images) through **every** `record_commit` site — mutations (`engine/mod.rs:1039`), seeds/loads/restores (`:1119,:1197,:1213,:1252,:1434`), expiry sweeps (`:695`), time-audience advances, jobs (`job.rs:506,655`), effects/actions settlement, activation rebuilds (`activation.rs:162`), dev reset (`dev_reset.rs:66`), expiry orphans. The RFC says "the log already names each row's partition … that is how devices acquire" — true of the sync log, not of the host wake path. Cost and plumbing are unscoped.

**Interest derivation gaps (each needs a stated rule):**

- *Online-only tables have no partition.* W1 registers "online-only tables the viewer's watched queries read (sent by client as `tables=`)" — so the commit footprint must be `(partitions ∪ tables)`, and the wake test is two-dimensional. The RFC never states the bipartite match explicitly.
- *`read through` parents (LLP 3000.014) and live-parent authority (LLP 3000.014.000).* A child readable exactly when its parent is readable depends on a parent row that may live in a **different** partition than the child's. Waking only on the child's partition interest can suppress a revocation caused by a parent-partition write. No analysis.
- *Presence-reading queries (LLP 3000.018).* `connected[p]` is not a partition; a query with `presence` re-runs on a 5 s refresh (`LLP 3000.018 §3.2`, `PRESENCE_REFRESH`). A partition-keyed registry must either always wake presence readers (defeating filtering for exactly the chat/typing workload) or state the carve-out. §6 says "W1 does not change when a poll enters or leaves presence" — entry/exit is not the issue; *waking presence-dependent polls on presence change* is.
- *Expiry / `not_before` openings.* The held poll already has an `opening` deadline path (`serve_changes.rs:70-73,101-117`). If W1 sleeps a poll whose only near-term event is a time-audience opening in another partition, the deadline logic must survive the registry. Unstated.
- *Revocation footprints / settlement changes / scope tombstones.* Partition-disjoint is not shown to imply scope-disjoint when rule inputs, `written_by` owner columns, or whole-table rule inputs (LLP 3000.023 §12 classifier inputs) are involved. The RFC leans on "membership commit touches that group's partition," which handles group add/remove but not rule-input-table changes that revoke without touching the read table's partition.
- *Missing fallback enumeration.* "Schema adoption, generation change, store identity reset, saturation, unattributable commits wake everyone" omits: physical store clears / `clear_rows` (unknown evidence per §12), dev reset (touched list exists but partition attribution unclear), effect/presence-obligation commits (see below), and Postgres-port null-preservation commits (LLP 3000.023 §12: Postgres emits no certificates).

**Hard miss: the `_effect_presence` obligation.** The cited 2026-09-17 ticket §§65-72 (lane W15a) explicitly requires: a filtered wake "must also wake the held polls of every principal a commit names as an unconfirmed presence dependency … otherwise a connected recipient of a row-less effect is pushed while connected." W1's "Membership changes" paragraph covers group add/remove but never mentions `_effect_presence`. Landing W1 without it regresses the deferred-push safety the ticket conditions the whole project on.

**Registry interactions understated.** (a) Per-viewer interest breaks the shared answer cache (`serve_changes.rs:172-188` `Answers` keyed by `(since, seq, generation, store_id)`, "one commit costs one read per distinct cursor"). Partition-filtered `tables` answers are per-viewer; the RFC keeps "the client re-polls, tables filtered" out of W1 but W1's wake filtering without answer filtering leaves the `tables` side channel (§"Side channel") half-fixed while multiplying `check` reads. State the cache redesign. (b) `connected[p]` counts held polls with 35 s grace (`serve.rs:246-307`); W1 doesn't change enter/leave, so no interaction — §6 is right — but the 5 s presence-refresh (§6 cites LLP 3000.018) *does* interact with partition-filtered wakes per above. (c) 100 ms ephemeral pacing shares the same condvar (`serve_ephemeral.rs:61-68` ephemeral publisher also `notify_all`s). Splitting durable-partition wakes from ephemeral-interest wakes needs two signals or a version-gated predicate; currently `eph_ready && now>=paced` is evaluated on every wakeup including durable ones.

**Multi-process.** Correctly scoped as payload-for-`LISTEN`/`NOTIFY` per LLP 3000.009 §7.1, but that transport doesn't exist; W1 on Postgres is single-process-only until it does. Fine as staging, should say so.

## 3. W2 soundness

**W2a disjointness test is sound only if both dimensions are checked and unknown stays conservative.** `partitions` (new, optional) + per-watch `scopes` (`ReadScopes`: table → group values) can soundly skip when *both* partition-interest and table-interest are disjoint — online tables have no partitions, synced rows' rule inputs may be tables outside scopes. The RFC says "partitions and, for online tables, the tables" (W2c) but W2a says only "footprint … disjoint from the watch's `scopes`." W2a must state the conjunction (partition-disjoint AND table-disjoint), with `scopes === undefined` (opaque/native/legacy) always re-running. Device-held vs online: both tiers populate `watch.tables`/`watch.scopes` (`client.ts:806,869`; `local.ts` watches share `LocalWatch`), so the test applies to both — but the RFC should cite that opaque watches stay conservative rather than implying all watches have scopes.

**W2c vs §12 RV: the RFC's own framing concedes the point.** W2c "does not relax the 'bound only possible row revocation' rule, it supplies a second proof" — that is a revision by definition, and §6/W2c correctly route it to author ruling Q2. Substantively, partition(+table) footprint disjointness is *coarser* than RV's row/column classifier (read rules incl. negative existentials, sync audiences, deadlines, aggregate sources, `written_by` owner columns). Using a coarse footprint to retain past the 1 s deadline extends visibility of possibly-stale data beyond what RV proved. It can be a valid second proof **only if** the certificate construction is shown to cover every RV classifier input for that watch — including parent-pinned reads (3000.014.000), presence inputs, and rule-input tables not in displayed scopes. The listed exclusions (unknown footprint, membership tombstone, key change, sign-out, §3.4 hard withdrawals) are the right shape but incomplete: add expiry/not-before, generation/store reset, opaque/native watches, and Postgres null-preservation. As written, W2c reopens a case RV closed for those inputs.

**W2d barrier: observability, not a fix.** The 2026-09-30 ticket's root cause is explicitly unresolved ("does not claim CPU scheduling or a particular SDK race caused it"). Recording `wantedSeq` and completing sync only at the watermark converts a silent loss into a visible stall (`wantedSeq` vs watermark in inspection — good), but T4's "always starts a sync" does not follow: if the swallow is in the poll loop's early-continues (`ephemeralReads.current`, `pauseRefusal`, `obsoleteRefusal`, `transportFailure` paths at `client.ts:949-1010`), the barrier waits forever. The RFC is honest ("If the lost notification has another cause the barrier makes it visible") — the target wording is not.

**Undeclared contract changes.** "No public API change" (W2) is false as stated: adding optional `partitions` to the `/changes` answer is an additive wire change (fine, but declare it, including the bound: at most N strings of at most M chars, mirroring §12's 256×128 publication fence), and W2c changes the *client contract* (retention past deadline on new evidence) — the RFC elsewhere calls W2c "a client-contract change and core," contradicting the "no change" line. Also undeclared: `tables=` poll parameter (Q4) is new client→server surface needing validation/intersection semantics.

## 5. Order and cost

Dependency order is right (W1 before W2-partitions before W4; W5 last; W5b conditional). Cost estimates are optimistic in exactly the places touching the core:

- Most likely wrong: **W1 "days."** Threading a partition set through every `record_commit` site plus adoption/dev-reset/jobs/effects/expiry, redesigning the shared answer cache per viewer, splitting the ephemeral/durable wake predicate, adding `_effect_presence` wakes, and Postgres payload design is core work through the lead session (§6 admits "one owner on the core") — expect a week+, not days, with the answer-cache and effect-presence items as the long tail.
- Next: **W4 "one to two weeks."** The B-vs-C measurement on "10,000 idle streams, reconnect burst, stalled client, credential expiry" plus the `tiny_http` detach patch's stated prerequisites (non-blocking writes with backpressure, lease accounting, parser ownership — LLP 3000.036 §6) is a multi-week build after the measurement, not including it.
- **W3 "about a week, exact2 lane"** for landing LLP 1110 understates a 20-release pin jump (0.4.16→0.4.36) plus the round-4 finding list (yield checks on every executor, forwarding-map growth, wasm leak on serialization failure, bake second-pass resolution — each "failing test first"). The pin raise ("hours") is the part most likely to surprise: device crate + TS driver + farm-app revalidation.
- W2d before root-causing 2026-09-30 puts instrumentation before diagnosis — acceptable explicitly as observability, but schedule the lost-notification reproduction first or W2d's assertion may just enshrine a hang.

## 6. W5

**W5a pinning: necessary, not sufficient as stated.** LLP 0009 DK-4 retired warm reuse because Ibex binds *evaluation, queue inspection, value release, and destruction* to the creating thread, with the no-eval constructor, rejection ledger, and `ex_hermes_interrupt_eval` nonce (2026-07-27 entry). Pinning live-scheduler evaluation to an owner thread (or one per module source) fixes the eval/destroy thread — but the RFC cites only "per-invocation baseline-restore reset." The full obligation from LLP 0009 includes: reset root-set (iterator/generator prototypes, all constructors), invocation-epoch stale-continuation guard, pool generation counter / read-lane check-in race, fail-closed burn on unhandled rejection, and local-only capability flagging (never hosted posture). None are named. Also, the expected win ("fixed cost falls from hundreds of ms to the query's own cost") assumes VM startup dominates the ~450 ms/turn; if query evaluation dominates (trivial tables suggest otherwise, but unproven), W5a under-delivers and W5b becomes load-bearing — which is exactly why T7 should be gated on W5a measurement before W5b, as the RFC stages it.

**W5b vs LLP 0200: directionally compatible, proof incomplete.** §2.2 requires the atomic cut (version + coverage drained under the pending-frame lock), eval against newest-committed-at-start with no pinned historical snapshot, delta-stamp ≤ coverage (re-cut or replace lane on race), and the enqueue-complete frontier. "Evaluate concurrently against a read snapshot at that cut" contradicts "no historical snapshot is pinned (no unbounded WAL retention)" unless the snapshot is bounded/short-lived — unstated. §2.5 requires per-subscription single-in-flight, monotonic delivery versions, latest-value collapse with age inheritance, refresh-signal priority, and the timeout→refresh→teardown terminal chain. Concurrent evaluators need all of that plus §2.4's witnessed-shrink transfer on every supersession path. The RFC names only "settlement isolation preserved" and "bounds get capacity proportional to evaluators." That's a correct intuition and a real spec revision — which is why it needs the LLP 0200 amendment, not a paragraph.

**Reclassification** of the contention ticket from "documented composition bound" to capacity defect is a product judgment; fine to propose, but it should wait for W5a measurement rather than ride this RFC.
