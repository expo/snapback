# Design review — frozen proposals of 2026-10-13

## Proposal 1 (PAGE2, §15 of 3000.036.001): NOT READY

The uncapped inverted-discovery idea (run `members where .principal = viewer` under the meter with §14's all-or-nothing fence) is sound in outline. Three material gaps remain.

1. **Row-`id` target lanes break the ordering/frontier accounting.** For `exists shares[document = .id, …]`, discovery yields ids and each lane pins `id`, but the page order is e.g. `.at, id`. A point lane's `.at` is unknown until the row is read, so an "ordinary per-range meter cut uses the §6 frontier" is undefined while point lanes are unread: there is no `through` to take the minimum over. Counterexample: viewer holds 10,000 shares; the meter cuts after 50 target reads. Which 50 rows may be emitted, and what is the frontier? Any emitted prefix requires knowing the unexamined lanes do not sort earlier, which requires reading them. Fix: specify point-lane `through` semantics (e.g. all point lanes must be read before any emission, making the target phase all-or-nothing too), with meter/heap bounds and tests, or restrict PAGE2 to lanes whose order columns are lane pins.
2. **Unbounded dynamic fanout has no stated heap/descriptor bound.** Static descriptors stay ≤8, but the distinct-parent/id set, per-parent descriptors, buffers and dedup state grow with the caller's whole membership population. `heap_bytes` elsewhere aborts the read, which would convert a large-but-legitimate membership into an abort rather than the promised empty `complete: false` page. Fix: state which meters cut (incomplete) versus abort during discovery and target expansion, and extend the §14 heap-ledger reservation to the uncapped distinct set.
3. **`N_NEVER_COMPLETE` cap advice has undisclosed write-side effects.** `cap 50 by principal` is not a planning hint; it is a write refusal once saturated. Advising it without saying existing inserts may start failing (and that the cap counts physically, per proposal 2's future-row rule) prescribes a semantic change. Fix: the note must disclose the enforcement consequence and when *not* to add it.

Also: the parent-owner form needs its source-index requirement stated (the inverted `baker = viewer` scan needs a supporting index and snapshot rules), and composition with timed lifetimes (proposal 2) must be explicit — discovery must exclude non-live source rows or a future membership opens target lanes early.

## Proposal 2 (3000.036.002, timed disclosure): NOT READY

The lifetime predicate, system-principal-no-bypass, physical-caps/uniqueness, and refusal list are the right shape. Four material gaps remain.

1. **The invalidation story contradicts itself and concedes an oracle.** §4 says `next_expiry` "never carries a hidden row's opening and cannot become an existence or timing oracle," then requires "a negative online query invalidates at the opening" and has the held-changes loop wake at the next stored opening. The invalidation time and the wake-up time *are* the opening: polling an empty `announcements where team = T` reveals exactly when a secret appears. Counterexample: embargoed announcement with `opensAt = Friday 9:00`; any team member learns the embargo time days early from refresh timing. Fix: name this as an accepted timing channel, bound what it reveals (earliest opening only? per-table? counts?), and say whether positive pages, aggregates and sync snapshots carry the same invalidation — currently only negative queries are specified.
2. **Never-live rows (`expire ≤ not_before`) leak under the same rule.** No boundary event ever fires (advancement discards without a put), yet the row sits in the pending index. Specify whether negative answers invalidate at its opening — either answer leaks or misleads, so the design must pick and justify.
3. **Server-clock behavior is underspecified.** No monotonicity requirement is stated. If the server clock steps backward, live rows become future again (flapping revocations); `advance_openings(now, …)` and commit-time liveness each need a pinned `now` source, and advancement work needs meter attribution (a triggering read paying for backlog drainage can itself cut). Fix: require a monotonic server floor for lifetime decisions, define `now` pinning per transaction, charge advancement explicitly, and bound backlog starvation ("reads unavailable" can become permanent under insert pressure).
4. **PAGE2 composition is claimed but not designed.** §1.2 supports a stored table as a membership audience, and §2 routes "rule probes" through `live` — but proposal 1's discovery never mentions lifetimes. Fix (in one of the two RFCs): future memberships excluded from discovery, future targets excluded from lanes, merged-page invalidation at the earliest relevant opening.

## Overall: NOT READY

Both proposals need revision. Neither finding asks for unrelated scope: each is the proposal's own stated end-game (disclosure, completeness, metering, clocks, caps, sync) applied to its new shapes.
