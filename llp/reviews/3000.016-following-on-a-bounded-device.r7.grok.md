## 1. Revision-6 findings

**Deletes after acquisition — fixed as an end state.** Section 2.1a now says a held source's event is held exactly while it exists, the delete is in the source's commit, and "never evicts" means never to keep a count. That matches the engine. `row_changed` logs the source change, then `timeline_apply` deletes the event (`timeline.rs` around the removal and unrepost arms). A stream page does not split a commit (`partition.rs`, the indivisible-commit cut). A `del` drops a local row unconditionally (`deferred.rs`); it does not consult the source. Probe: acquire post P and its event, remove P, sync, repost P. The event is gone and the device refuses `FEED_POST_NOT_FOUND`, including after the tombstone is purged. Second probe, already in §5: unrepost a held repost, sync, repost again. The stale `(actor, post, true)` row must be gone or the new insert fails the unique check while the server accepts.

**`sync to .<follower>` — fixed.** Section 2.1 now lists only `sync public`, a public horizon, or `online only`. Probe: `public` plus `sync to .followerId` is not a legal follows declaration; `bind_sync` rejects it because the read rule is public.

**One `byActorPost` input — fixed.** The §2.3 table matches the three reads. An own-post insert does not read `byActorPost` (it writes the event). Removal and repost insert read the original event through the post. Unrepost reads the repost event from the pre-delete image and does not read the original post (`timeline.rs` `(Some(row), None)` arm). Probe: posts horizon, reposts fully synced. `check` on a plain post insert stays `predicts: eligible` with no event site. Unrepost has no posts site and predicts. The reverse mix (posts `online only`, reposts fully synced) must not classify unrepost as Server.

**Other reads of a partial event table — only partly fixed.** Section 2.1a limits known absence to the three lookups and names queries, scans, and rule probes. That is the right rule for a kind-scoped key. It does not survive an unscoped key when the two kinds differ. See finding 1.

**Time boundary — fixed.** Acquisition is per source row, by `(author, post, false)` or `(actor, post, true)`, and the repost id is transferred, not rebuilt. A time or full-key floor is explicitly rejected. Probe: 50,000 originals at one timestamp, floor 1,000. The device holds 1,000 source rows and their events, not 50,000. A repost event whose minted id sorts below the floor repost's id is still held when its repost row is held.

Revision 2's scenario A and the reply/removal absence cases stay closed for those three lookups, as long as `@T@Posts` has no horizon and the event set for held sources is actually maintained.

## 2. New defects

**Medium — §2.1a. An unscoped read does not name the kind, so a mixed residency makes a miss look like absence.**

Posts fully synced, reposts `last 10`. Original events are a complete kind; repost events are not. They share one table. `byId`, `byTime`, and `byActorTime` do not carry `repost`. A miss of a minted repost-event id outside those 10 is indistinguishable from a missing original. `probe_witness` treats a horizonless miss as known absence (`read.rs`: known when `horizon` is `None`). A `byTime` page can likewise omit repost events and still look complete.

The kind-scoped reading of "a partial event kind" implements exactly that. The safe reading — only the three transition lookups may treat a miss as absent whenever either kind is not fully synced — is also in the section, but it is the one a kind-aware implementer will narrow away.

Smallest change: if either kind is not fully synced, known absence is only those three lookups. Every other miss is unknown, including `byId` and a rule probe. Any scan that can return a partial kind is withheld, not a complete page. A hit of a row the device actually holds may still be returned. A `byActorPost` key that names a fully synced kind may stay a known null.

**Medium — §2.1a and §2.2. "Unknown, as a read past a horizon" publishes the null, the false probe, and the short page. "Withheld" does not.**

A horizon miss still returns `null` or the rows, with `complete: false` (`get_inner`, scan coverage). `rule_probe_exists` returns the boolean and only then sets unknown. The client turns a payload that contains `data` into a published read (`local.ts` around the `outcome.loading || !("data" in outcome)` check). Offline, or online while an own post is still unobserved, that read is what the user sees (`wantsServer` is skipped). Section 2.2's trigger list is still only card misses, inbox coverage, and `online only` cards. An event-table query is none of those.

Probe: posts horizon 1, one event on the device, the rest on the server. Offline, `feedPosts first 100 by byId` must be `{ loading: true }` with no rows. A rule `exists feedPosts[thatUnheldId]` must not publish `false`. Same while a predicted own post is unobserved.

Smallest change: add that read as a withheld trigger in §2.2, and say it is not an ordinary horizon result. The engine marks the miss, scan, or rule probe unknown; the query result is the withheld value with no `data` and no `next`, then the existing four-step precedence.

**Medium — §2.1a. Partial events are not a residency the snapshot and the log can both express.**

`schema.synced()` is one switch. It both enumerates the horizonless snapshot (`snapshot_page`) and decides whether a mutation is logged (`account_row_change` logs only when `sync` is set). `boundary.accept` admits every put when there is no horizon.

"No horizon" leaves `@T@Posts` on that switch, so the snapshot walks every event and the live log stores every later put. Clearing `sync` so the walk skips the table also stops the log, so the unrepost `del` never arrives and finding 1's second probe fails. A horizon on `byActorPost` makes the three lookups unknown again. Those are the three mechanisms that exist today. The kind state the section describes is a fourth, and it is not spelled out against this switch.

Smallest change: a partial kind stays `sync public` with no horizon, so its puts and dels remain in the public log, and it is omitted from the horizonless snapshot walk. Snapshot pages attach each source row's event, found by key, in that same page. On apply, admit an event `put` only when that commit admits the source row or the source row is already held; always apply an event `del` if the event is local, including when the source `del` is earlier in the commit. Do not implement this by setting `sync.horizon` or clearing `sync`.

**Low — §2.1a. "At or above the floor" drops a row `whole` keeps.**

When the source has fewer than N rows, the recorded floor is `whole`, and `accept` admits every later row, including one whose `at` is older than every acquired row. The new sentence defines held rows as the acquired floor plus rows at or above it. A time compare against the oldest acquired `at` keeps the backdated source (the horizon put is accepted) and drops its event. Reposting that post then refuses `FEED_POST_NOT_FOUND` on the device and succeeds on the server. This is revision 2's scenario A for the steady state before the table reaches N.

Smallest change: events follow source rows the horizon admits, including every later row when the floor is `whole`. Do not re-derive that set with `at >= oldest`.

## 3. What is specified enough

**Same-commit deletes, for a logged event.** Source log entry, then event delete, one commit, one device transaction. Removal leaves repost events in place; the section says so, and the removal arm only deletes `repost = false`. No visible gap if finding 3's log rule is followed.

**Pages and interrupted acquisition, for mutations after the watermark.** Each snapshot page is one server transaction; staging stays invisible until catch-up publishes; a crashed page rolls back; resume uses the snapshot cursor. An insert or removal between pages is in the log after the pinned watermark, and catch-up can repair it. Catch-up cannot recreate a pre-watermark event that was never staged. The source row and its event image have to be the same staged page. The "each acquired source row brings its event" sentence already says that; finding 3 is what makes the log half true.

**The §2.3 table.** It matches the calls. Own-post also reads `@T@RemovedEvents` (`timeline_require_live_id`). Tombstones stay fully synced, so that read adds no horizon site and does not change `predicts: eligible`. Not a defect.

Section 2.2 still has the revision-5 precedence: `online only` cards are withheld, a `held` query does not fall back, and that order is ahead of the loading-to-server shortcut. No regression there.

## Verdict

**READY WITH CHANGES.** The revision-6 repairs are the right design. Before implementation, state the log-versus-snapshot split, treat every unscoped miss as unknown when either kind is partial, and put that read on the withheld-trigger list.
