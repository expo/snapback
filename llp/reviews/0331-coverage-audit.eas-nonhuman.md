# EAS audit — facet: non-human actors and the data-plane edges

Universe paths are relative to `server/www/` (so `src/...`). Proposal = LLP 0331 as ruled 2026-08-30 (Tier 0 core; Tier 1 one reserved `system` principal named by table rules; Tier 2 / Refused / Out as fixed). Extension codes X1–X20 from `llp/reviews/0331-coverage-audit.brief.md`.

## 0. The shape of EAS's non-human plane in one paragraph

Universe has eight viewer-context types (`src/data/entities/viewercontext/ExpoViewerContext.ts:28-37`: `ANONYMOUS, SCOPED, USER, SSO_USER, ROBOT, PARTNER_ACTOR, OMNISCIENT, OMNIPOTENT`). Two of them bypass rules entirely — `OmnipotentViewerContext.ts:11-14` "All-powerful viewer context ... bypassing all privacy rules", `OmniscientViewerContext.ts:11-15` the read-only bypass — and are vended in a scoped block that invalidates on exit (`ViewerContextUtils.ts:30-46, 53-69, 81-101`). **164 of 168 privacy policies carry `AllowIfOmnipotentPrivacyPolicyRule` and 148 carry `AllowIfOmniscientPrivacyPolicyRule`** (census below). That is the Tier 1 `|| viewer === system` disjunct, already paid on essentially every table. Non-human work then divides into: (a) background jobs that run **as the serialized dispatching principal** (not as system), (b) build/workflow workers that authenticate as **an attenuated re-mint of the initiating actor** (a scoped JWT), (c) inbound webhooks/crons that verify a signature or shared secret and then either **switch to a real robot principal** (GitHub, App Store Connect, Cloud Scheduler) or **run omnipotent** (Stripe, Cloudflare, Sentry, submission service, reapers, notifications cron), and (d) anonymous device/CDN reads (EAS Update manifests, artifacts, push, Snack) served **under omniscient with a hand-written access check**, not through the entity read rules.

## 3. Facet verdict

The proposal carries this facet's **write side** and most of its **ingress**: workers are ordinary principals (a re-mint of the initiating actor), webhooks are re-attributed to real robot principals, and everything that runs omnipotent in EAS today (Stripe, Cloudflare, Sentry, submission service, reapers, notification fan-out, waive-charges) is Tier 1 as ruled — with the sobering data point that EAS's "one disjunct per system-touched table" is 164 of 168 tables, i.e. Tier 1's one-trusted-domain is exactly what EAS is. The **device read side does not go through rules at all** in EAS (omniscient bypass + hand-written check + shared LRU cache); the proposal would carry it as a `public` served projection (#15) and gains safety, but the Expo Go gate (#16) is a caller-asserted-environment term the proposal rightly excludes — and EAS ships it as a dry run, so the loss is honest. **Two things would flip the most rows:** (1) letting the job/`schedule` kind name an *ordinary* principal to act as (a signed, expiring re-mint captured at dispatch) rather than only `system` — 31 of 35 jobs and the cron-triggered workflow run depend on acting-as-the-initiator for attribution and live re-check; and (2) a ruling on the *mutable* denormalized parent (app transfer), since every rule in this facet walks `row → app → account`. **Genuinely NEW versus the 37 paper apps:** (a) **deletion provenance** as a rule input (#23) — the mirror of creation provenance, used by 12 policies and 24 trigger sites; (b) the **attenuated principal** (#4) — same actor, capped ceiling, live-tracking the underlying grants — which EAS spells as a principal-kind test and the proposal must spell as a distinct minted principal; (c) at scale, the observation that the Tier 1 disjunct is universal. The paper corpus's service/webhook principals, bearer links, plan gating and schedule-flipped status all reappear here unchanged.

## 5. The five key questions, answered

1. **One system principal or a serialized context?** Serialized context. Jobs run as the dispatching principal (`BackgroundJobRouter.ts:115-120`), which can be a sudo user (deletions, exports), the installation robot (all GitHub/App Store Connect-derived jobs, scheduled workflow runs), the scoped worker (trigger-dispatched post-build jobs), or explicitly omnipotent (waive charges, internal admin dispatches). Only 4 of 35 job modules escalate inside. Under the proposal: the identity layer must be able to re-mint the *acting* principal for a deferred invocation (signed, expiring); `system` is right only for the four omnipotent/omniscient jobs and the crons.
2. **Workers: principals or shared secrets?** Ordinary principals for all state/log/artifact writes — a scoped ES512 JWT whose `sub` is the initiating user or robot (`utils/auth.ts:270-295`), 24 h, checked by the same table rules as a human with PUBLISH. Shared secrets exist only for side channels (queue positions, submission-service status, GCS asset creation, reapers, notifications cron, partner provisioning) and each of those runs omnipotent = Tier 1. The one non-trivial thing is the attenuation ceiling (#4).
3. **Device update fetch: `public(reason)`?** Not today — it is an omniscient bypass over tables whose rules deny anonymous, keyed by `(appId, channelName, runtimeVersion, platform)` from headers/query, with a plan-quota throw and a dry-run Expo Go check. No per-device or per-app key is required for standalone apps (the project id is public); code signing is integrity data on the row. So it lowers to a `public` served projection (CORE-split) plus a schedule-flipped quota status; the Expo Go gate is OUT:X9 and droppable. `bearerOf` is not needed.
4. **Non-human paths that read denied rows and return them?** Yes: (a) the manifest path returns Update/Channel/Branch-derived data to anonymous devices (#15) — fixed by making the served projection public by rule; (b) `EasArtifactsRouter` and `ProjectBuildsRouter` return build archive URLs/plists to anonymous callers by key (#19); (c) `PushRouter.getExpoPushToken` leaks app existence by name/id (#20); (d) notification fan-out writes rows for other users and the cron later loads builds under omni to compose email (#13, #14) — the system-domain taint claim must cover that the email body is composed from rows the *recipient* may read (EAS relies on membership at fan-out time, and the policy comment admits the recipient may have lost access by read time). The GitHub/ASC/scheduler omniscient lookups (#22) do not return data to a viewer.
5. **NEW relative to the paper corpus:** deletion provenance as a rule input (#23); the attenuated principal that tracks its parent's grants (#4); the mutable-parent denormalization (app transfer, #25) which ruling 4 explicitly does not cover; and, as an observation rather than a requirement, that at EAS scale the Tier 1 disjunct lands on essentially every table (164/168).
