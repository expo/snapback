## Finding 1 (verbatim)

Concrete recovery finding (read-only): client-outbox.ts submitMutation/enqueue checks admitInbox only before the new capacity wait. With an initially empty inbox + missing/exhausted grant, start a writer-local mutation; hold /api/resume; durably insert a follower mutation while renewal waits; release renewal. The local continuation calls outbox.enqueue without re-running inbox admission, while adoption's inbox retry is only a setTimeout(0). It can reserve/drain the local entry before the already-durable follower row, violating LLP 1018.004 §2/§4 FIFO. Recheck/admit oldest inbox work after each capacity wait and before local reservation (including contention retry). Add held-resume follower/local-order test. Sending owner same finding.

## Finding 2 (verbatim)

Second concrete finding: ClientRecovery.recover keys automatic attempts by grant.id/used/reason. If newly minted grants are unusable under the client's clock (e.g. device >30 days ahead of owner, so every returned expiresAt is already past), a selected observer or blocked inbox gets grant A -> status grant-expired -> renew B -> outbox.notify -> new key -> renew C indefinitely. Each HTTP response is fast/successful so the 10-second per-flight deadline does not bound this self-success loop. decodeGrant accepts these valid timestamps, and expired capacity always reports 0. Need suppress automatic reattempt when that flight's own replacement still fails its demand, until a genuine external opportunity/new consumption; test unique fresh grant IDs with past expiry and assert bounded requests + connect fallback.
