### 1. Capacity-only resume can run coverage reset/rebuild and then ordinary trust (blocking)

`performOfflineResume` sets `capacityOnly` and POSTs `/api/resume`, but `E_OFFLINE_RESET` is handled in the shared `catch` **before** the capacity-only success branch.

```javascript
if (candidate?.code === "E_OFFLINE_RESET") return rebuild();
```

`rebuild()` calls `reload()` and `resetCoverage(requestedEpoch)`, which persists `resetCoverage` / `facts` / `superseded`. `resumeOffline` may then loop (max 3). After that, `hasCoverageFacts` is true, so the next round is a normal resume: `commitMany`, bearer `reauthenticate`, `resumeSucceeded`, drain. `ClientRecovery` still treats the flight as success and runs `succeeded()` / `completed()` → `scheduleSupersessionReset`.

**Scenario.** Write-only partition (no query facts), installed program P1, user sends or a first `observe(op)` registers demand. Owner has deployed P2. Capacity-only resume carries P1, owner returns `E_OFFLINE_RESET`. This grant-only path now:

- **creates** coverage facts it never had,
- can **renew resume/fence trust** on the follow-up round,
- can **clear** the reset marker via `completeReset`,

all without a real coverage resume. That contradicts “capacity-only logless resume must not create coverage/resume trust or clear a real reset marker” and “a grant is capacity, not authority.”

With facts, `E_OFFLINE_RESET` → rebuild is the existing path and should stay. Capacity-only should fail closed (`E_GENERATION_CHANGED` / ordinary refusal), keep the draft, and leave reset/facts/trust untouched.

---

### 2. Capacity-only short-circuit steals queued replay and past-fence seeding (blocking)

Capacity-only is chosen when `!request && demand && !hasCoverageFacts` **before** the existing `queuedIntents` handling:

- inside fence → `drainOutbox`
- past fence → seed an authorized query, then a real resume  
  (“a fresh consumption grant alone never opens the fence”)

A manufactured `{ protocol: 1, generation, schemaHash, authEpoch, mounted: [] }` request skips both. On 200 it `noteGrant` + `adoptPendingGrant` and `return false` with no drain, no seed, no `resumeSucceeded`.

**Scenario A (inside fence).** Headless client logs in, admits writes, transport fails, intents stay `queued`. Composer/observer later `prepare("messages.send")`. Recovery takes capacity-only, maybe mints, returns. FIFO drain of already-admitted envelopes does not run unless some later `drainNow` happens to occur.

**Scenario B (expired fence).** Same queue, current grant expired (`remaining: 0`). Capacity-only adopts a new grant. If `outbox.fence()` follows current grant expiry, the fence becomes `inside` without validator/seed resume. A later serialized drain (new admission, inbox `admitted()`, or a joined replay waiter) replays **old** envelopes. Grant adoption has been treated as authority.

`adoptPendingGrant`’s extra check (`hasCoverageFacts` / `resetNeeded`) does not test queued intents or fence.

Capacity-only should run only when there is nothing already admitted that still needs drain or past-fence reauth. If `queuedIntents().length > 0`, use the existing drain/seed path.

---

### 3. Shared flight coalesces replay into a grant-only run (blocking)

`ClientRecovery.resume` joins any in-flight promise and **drops** the caller’s `demand` and purpose:

```javascript
if (this.flight) return this.flight.run;
```

`connection(true)` while `active` only stores `reachable`; it does not `opportunity()`. Auth restoration **does** call `opportunity()` during a flight (`publishAuthSnapshot`). `recover()` then:

```javascript
if (replay && (await runtime.queuedIntents()).length > 0) await this.resume(authority);
```

which **joins the capacity-only flight**. That flight’s `return false` is treated as replay success. `succeeded()` clears `resetRefusal` and `validated()`; queued work is not drained.

**Scenario.** Write-only client has queued envelopes. Capacity acquisition is in flight. Login/token restoration fires `opportunity()`. Replay waits on grant-only completion. Afterward `reachable` is already true, so a later `connection(true)` is not a new edge. Automatic FIFO replay is skipped until explicit `online()`.

Same-flight coalescing is fine when the in-flight work is a real validator resume (it already drains). A grant-only run must not count as the one reconnect/auth attempt.

---

These three are one design hole: the logless grant route is on the **same** cancellable resume flight and the **same** success/reset/fence machinery as coverage resume. Preference for “one flight” is fine; it cannot imply grant-only success.

## Not blocking (preference / already fenced)

- **Demand with facts still does a full `/api/resume`.** Matches “no separate grant-only route” and “existing facts use ordinary resume.” If that is routinely expensive, that is RFC §6, not a correctness break.
- **One automatic attempt per deficit/transition**, plus one pristine `E_OFFLINE_ID_BLOCK` retry in `submitMutation` (`!custody`), plus max-3 `resumeOffline` rounds, matches the narrowed slice. Residual “three-attempt backoff” in the broader RFC is deferred, not unimplemented by accident.
- **`remaining` is still client-reported.** Under-report mints extra 8192 blocks; over-report fails admission and retries once. Server still derives demand from the named mutation certificate, not client arithmetic. Same trust model as before, now less mint-on-every-resume.
- **Deadline `abort(RefusalError)`** plus `adopt`/`check` fencing is the right shape for fetch that ignores `AbortSignal`, as long as findings 1–3 do not treat that 200 as coverage success.
- **8192 / measured gzip.** Packet does not change `REPLAY_GRANT_COUNT` or the five-root gzip path. Owner test still expects `grant.count == 8192`. No measurement was in this packet.

## Orchestrator disposition

Finding 1 is material: the capacity-only request must not fall into ordinary generation-reset rebuilding. Preserve the existing reset path for partitions that already have facts, and add a no-facts successor control.

Findings 2A and 3 identify a real purpose-coalescing obligation: a capacity-only success is not a completed queued replay/reauthorization attempt. Cover a replay opportunity joining capacity acquisition, inside and outside the old intent's fence, with either actual bounded replay or visible refusal.

Finding 2B's proposed old-grant bypass is not established by the source. `OutboxLedger.canReplay(entry)` loads `entry.grant`, and `fence()` checks every queued entry before the current consumption grant. Adopting a fresh current grant alone therefore does not authorize old entries. Retain these controls; do not replace them based on the review's conditional premise.
