# LLP 3000.013.000 design review brief (round 1)

**Date:** 2026-10-12. Shared verbatim with both round-1 reviewers (GPT-6.1 Sol through codex, Muse Spark 1.3 through muse). The RFC was then numbered LLP 3000.038 (`llp/3000.038-a-browser-write-journal-without-the-device.rfc.md`, commit `f1c490be1c`); it was renumbered 3000.013.000 after four lanes claimed 3000.038 concurrently. The text is unchanged.

```text
You are an independent design reviewer. Review, rigorously and read-only, the RFC at
llp/3000.038-a-browser-write-journal-without-the-device.rfc.md in this repository
(revision: draft, commit f1c490be1c on branch sb4-ws-jr). Do NOT modify, create or delete any file;
do not run git commands that change state; do not run builds or tests. Read code freely.

Context: Snapback 4's TypeScript client lives in snapback4/packages/snapback4/src. The RFC proposes a
JavaScript-only synchronous localStorage write journal so a browser createApp without the wasm
device can admit writes durably, for schemas with no synced tables. The governing documents are
LLP 3000.013 §6, §6.2 and §13.3 (llp/3000.013-quarry-states-intent.rfc.md), LLP 3000.007 §17 and §20.4
(llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md), and the client reference
snapback4/packages/snapback4/CLIENT-AND-OPERATIONS.md (search E_ADMISSION, custody, journal, localStorage).
The relevant code: app.ts (createApp, admit(), open(), custody), app-online.ts (onlineCustody, the
existing online intent journal), app-journal.ts, app-storage.ts (storeLock), session-authority.ts
(IndexedDB session authority with a localStorage mirror), admission.ts, admission-authority.ts
(sameAdmissionAuthority), web-journal.ts (the device's synchronous localStorage journal this design
mirrors), writes.ts (MutationIds), app-client.ts (guardClient), client.ts (the online transport),
online-dispatch.ts, and the server's receipt record (snapback4/crates/snapback4-core/src/engine/receipt.rs).

Review for correctness above all:
1. The at-most-once argument (§5): can any interleaving of capture, IndexedDB commit, record removal,
   transfer-marker collection, recovery in this or another tab, dispatch, settlement, receipt eviction,
   store replacement, or journal damage cause the server to execute one user click twice, or the client
   to admit one record twice? Check the claims against the actual code paths it says it reuses.
2. The no-loss / custody argument (§2 G1-G2, §4): is there any window between mutate returning a
   non-failed promise and the intent being durable in localStorage or the IndexedDB journal? Any path
   that removes or cancels a captured record without either a live refusal or a recovery admission?
3. Locking: the proposed lock order (journal Web Lock, then session Web Lock) against every existing
   storeLock/persist path in app.ts, app-online.ts and app-revocations.ts — deadlock, starvation, or
   an authority check that is not actually under the lock.
4. Multi-tab behavior (§4.5): runtime liveness via navigator.locks.query, adoption races, a paused
   runtime with a commit in flight, two live tabs.
5. Session/epoch changes (§4.6), store changes (§4.7), and the failure-mode table (§6): storage full,
   private mode, IndexedDB failure, missing Web Locks — must refuse loudly, never silently drop.
6. Selection (§3): the /schema-based decision, the explicit `writes: "online"`, and whether the
   decision can be wrong in a way that harms correctness.
7. Anything the RFC claims about existing code that is false.

Output: an overall verdict on the first line, exactly one of READY, READY WITH CHANGES, NOT READY;
then numbered findings, each tagged MATERIAL or MINOR, with the RFC section, the code citation
(file:line) you checked, the concrete failing interleaving or false claim, and what would resolve it;
then a short list of what you found sound. Be concrete; do not pad.
```
