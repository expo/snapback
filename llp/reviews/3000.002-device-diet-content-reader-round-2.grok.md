## Questions

### 1. Mixed maps — FIXED

Every map that carries at least one discovered Scan name and one of `start` / `end_exclusive` / `value` / `max` is refused, independent of later interleaving.

- After a Scan commit, Replay reads **every** subsequent key as text and refuses the four domain keys before Scan’s visitor can treat them as unknown (`snapback4/crates/snapback4-core/src/ir/lane_source.rs` 69–75). That is the round-1 order bug.
- After a domain commit, `small()` refuses any key in Scan’s discovered set (85).
- Unknown keys are skipped first (55–60), so **unknown then small then Scan** still reaches `small()` and then line 85.
- **`max` alone then Scan keys:** `max` is in `SMALL_FIELDS` (37, 56), then a Scan name hits line 85.
- **Aliased Scan key:** today’s `Scan` has no `alias`/`rename` (`snapback4/crates/snapback4-core/src/ir.rs` 277–301). The probe includes aliases when they exist (`lane_source.rs` 147–154: fixture `alias = "max"` yields `["max", "renamed"]`). A future alias would be a Scan key on both paths.
- **Duplicate of the replayed first key:** not a domain key, so Replay hands it to Scan, which errors `duplicate_field` if it appears before a domain key, or MIXED if a domain key comes first. Either order is a refusal.
- Error **message** is not stable across those last two shapes (`duplicate_field` vs MIXED vs a typed Scan error such as `site: false`); **acceptance** is.

Canonical sources do not refuse: corpus, published Quarry, and compiler List round-trips still require `compare(text).same()` and byte identity (`snapback4/crates/snapback4-core/tests/lane_source.rs` 72–77, 91–97, 100–132, 222–231, 247–271). `Scan`’s serialized names do not overlap `SMALL_FIELDS`.

Values still use the original map (`lane_source.rs` 77). Value-error line/column through Replay matches a direct `Scan` decode (tests 205–210). Cost of reading Replay keys as text: journal/LLP **+327 B gzip**, replay visitor **3,951 → 4,306** shallow B (`llp/3000.002-end-to-end-resource-bounds.research.md` 434; `snapback4/metrics/wasm-budget.json` 1).

The mixed test rotates complete Scan+Range and Scan+List objects so every field is first (`tests/lane_source.rs` 292–300). It does not itself construct unknown-first, max-only, or duplicate-first mixed maps; those follow from 55–85, not from extra branches.

None of `SMALL_FIELDS`; the list is non-empty; the derive calls `deserialize_struct`.

Refusal is `de::Error::custom`, not a panic, on every host (`lane_source.rs` 13, 39–46). `unwrap_err()` is gone from the production path.

`scan_derive_fields_are_nonempty_and_disjoint_from_domain_discriminators` (128–132) probes the **real** `Scan` derive. Adding `#[serde(alias = "max")]` (or a colliding rename/field) fails that test. `unsupported_discovery_refuses_instead_of_panicking` (135–145) pins Ok / empty / overlap without panicking.

The guard runs **on every** `LaneSource::deserialize` (11–15), not once. That does not change the outcome: the slice is `'static`. It avoids a process-aborting `OnceLock` unwrap on wasm. Same per-decode probe as S1b, plus the three checks.

### 4. Unknown-field values — FIXED

The consistency claim is true for a derived **struct** reached without `LaneSource`. `Scan` is unchanged in this delta (`ir.rs` not in the diff). It has no `deny_unknown_fields`. `ordinary_ir_structs_already_skip_unknown_subtrees_without_validation` (320–328) decodes `Scan` with unknown `1e999`, `"\ud800"`, and 150 nested arrays and expects success; journal: that test was green on the unrepaired production decoder. `json_codec.rs` 16–20 already states that typed derives skip those subtrees.

Declining `validate_text` at `Engine::open` is defensible: stored programs are compiler JSON; `open` already `serde_json::from_str`s them (`snapback4/crates/snapback4-core/src/engine/mod.rs` 285–293); `validate_text` is the web command boundary (`snapback4/crates/snapback4-device/src/call.rs` 168–170); a full-text pass is CPU on every open. The narrowed contract is where a maintainer will look: `lane_source.rs` 1–4, `json_codec.rs` 16–20, LLP 3000.002 ¶434, JOURNAL 2026-09-17 S1b R1.

The test is `Scan` only, not every IR enum. Externally tagged enums are not the asked struct case.

### 5. Census evasions — FIXED (item 7 with it)

`decoderAliases` + `imports()` resolve grouped and nested use-trees (`wasm-codec-census.mjs` 88–125). Covered:

- `use serde::Deserialize as De` and `use serde::{Serialize, Deserialize as De}` — names set, refused with untagged (`wasm-codec-census.test.mjs` 190–207).
- `#[derive(serde::Deserialize)]` — `Deserialize` and `serde::Deserialize` are in the initial set (111).
- `use serde::{self, Deserialize as D}` — recursive group adds `D` (92–107). Not a separate test; the parser handles it.
- Glob `use serde::*` — does not hide `#[derive(Deserialize)]` (still in the default set).
- Re-export in another web-source file: `pub use serde::Deserialize as De` adds `De` to the **global** names set, so `#[derive(De)]` in a second file is still a decoder derive.
- `use crate::Foo as De` after `Deserialize as Foo` elsewhere: `De` is unknown and fail-closed (156–158).
- `macro_rules!` bodies with a decoder derive + `untagged`/`tag`/`flatten` are refused (143–150); no macro allowlist entries exist; no `macro_rules!` in web core/device sources.
- Unresolvable `…::Deserialize` that is not `serde::Deserialize` is a census error on the `use` (114–121, 215). `use elsewhere::Deserialize as De` and `use serde::{de::Deserialize as De}` are tested (204–207).
