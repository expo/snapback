Top finding: per-invocation discriminator rule is not implemented. A single-value caller-checked data field loses its derived freeze candidate as soon as any other mutation stages the same column, contrary to §12.

Concrete counterexample, reproduced by existing test `checked_caller_data_stays_an_input_when_other_operations_stage_its_column` in [security_wave28.rs](/home/ccheever/projects/sb4-b26-sec10/snapback4/crates/snapback4-lang/tests/security_wave28.rs):

```quarry
table docs:
  material: enum('steel','wood')
  approved: bool default false
mutation approve(doc: docs, material: enum('steel','wood')):
  require material = 'steel'
  update docs[doc] {material, approved:true}
mutation replace(doc: docs):
  require d.material = 'steel'
  update docs[doc] {material:'wood'}
mutation restore(doc: docs):
  require d.material = 'wood'
  update docs[doc] {material:'steel'}
```

`material` is a global discriminator (`steel`/`wood` across `replace`/`restore`), but `approve` itself only admits one literal state on that field plus a checked caller argument. §12 requires: omit only when this invocation admits/excludes multiple states, or a recorded subject approval governs same-subject data. Single-value caller data stays evidence.

- Same pattern hides the `text <=30` variant. This is loss of required capture / hidden false negative: an `approve` that checks replacement data would not get a paired `update` freeze, and `approval_checks::revalidated` would have no clause to enforce.

No semantic contract revision is required for this item. The §12 text is correct; the code must retain per-invocation caller checks when building `payload`/`inspected`, not global-stage exclusion.
