## Reading conventions used in every table

1. **Several independent one-hop probes joined by `&&`/`||` count as CORE.** 0331:251
   ("Independent permissions use independent relationship rows") and its
   "Hierarchy → explicit role sets / boolean composition" row admit boolean
   composition; what the brief forbids is *chaining* (a found row's field feeding a
   second probe's key). Chaining is marked X1 or CORE-with-denorm.
2. **Time-as-state ("K5 flip") is CORE for the rule** — the rule reads a `state`
   column that a schedule flips. But every such flip needs a *schedule running as
   some principal*, which is X11. X11 therefore recurs in all four apps; I count it
   once per app and say so.
3. **Server plane vs. outside.** Per the task, a requirement the RFC itself moved
   outside the server data plane — dimension P authority placement (RFC:258),
   dimension Q rule composition (RFC:259), device-plane evaluation (RFC:230), the
   `oblivious` kind (RFC:229), quorum as a host boundary (RFC:258), and the wave's
   explicit "not this system" verdicts (RFC:264; W4 "Verdict") — is reported in its
   own row and **not counted as a failure of 0331 core**. The row still names the X
   code so results merge, with the ruling beside it.
4. The **wave-4 v0 artifacts spell many rules with `principal.kind === 'system'`
   (and `'host'`, `'staff'`, `'anon'`, `'service'`)**. I do not treat the *spelling*
   as evidence for X3: where the same authority can be an ordinary seated principal
   with a role row, I say so and mark the actual need (usually X11: something must
   *run* as that principal).

### App verdict — **NEEDS: X9, X11, X19 (thin), X17 (thin)**

Authorization *was* the hard problem, but not its relational structure: roles, relationships, delegation, break-glass and audit audiences all lower to 0331's scoped-role and relationship-row recipe (rows 1–3, 7, 8, 11 are CORE or denorm the design already did). What core cannot say is that admissibility is a function of the **commit instant** over **evidence rows** scoped to a **session/device** (rows 4–5) — the archetype's axis (ZT-D:3 "authorization whose inputs are not rows — freshness, oracles at commit"). The RFC split that requirement: agreement *at the instant* is "not this system" (a product boundary, not a core failure); commit-fresh mirrored evidence is addition G/N — that is X9, the single extension that would flip this app to COVERED-WITH-DENORM once X11 (a seated system principal for schedules/effects) is granted, which every K5 lowering in the wave already presumes. The design did reach for something the RFC refuted: the pre-registered prediction-6 form "mirror the posture row" was shown insufficient (RFC §8 row "rule oracles are refused; mirror the posture row" → "freshness must be evaluated *at commit* and re-evaluated on retry"), and the design's own `session.establish` with budget zero "can never pass" (ZT-V:314).

Outside the server plane (not charged to core): remote-at-commit agreement (ZT-V:3, RFC:264); audited fenced delivery and padded execution (ZT-V:277, ZT-V:291; RFC:254); oracle I/O as effects (ZT-V:163 `E_OPAQUE`).

### Sprawl check

- **X9** — load-bearing. Promise 2 (ZT-D:36 "Freshness is measured against the commit instant") *is* the product. The design's own concession — handler-entry time plus a 500 ms skew allowance (ZT-D:218) — is marked a cheat "when the allowance exceeds the smallest budget in play" (5–10 s for restricted/order/admin/export, ZT-D:27–31). An honest reduced product keeps only the 60 s+ classes (`view.summary`, `view.chart`, `write.note`) and drops restricted/order/admin/export. The session/device half of X9 is load-bearing for promise 10 (ZT-D:44 "Stepping up on your phone does not freshen your laptop"); dropping it collapses all attestation scopes to the principal.
- **X11** — load-bearing. No human inserts attestations, revocations or leases; the 5 s sweeper (ZT-D:37) and every ingest effect write under it. Smallest form is a seated principal, not a kind.
- **X19** — droppable. With X11, the decision program is the only writer of chart/order rows (`insert: writeDecision|sys`, ZT-V:96–102) and `unique` on the consumption row gives one-use; X19 only upgrades "the program does it" into a constraint that binds a hypothetical raw writer. Loses nothing the product states.
- **X17** — droppable. Single-approver policy change loses the four-eyes rule (ZT-D:206) only; or keep it as program logic under X11.

### App verdict — **COVERED-WITH-DENORM on the server plane; NEEDS: X11 (and X1, droppable)**

Authorization was **incidental** here. The actor model is the plainest instance of 0331's recipe in the wave: `operators(regionId, userId, role)` with a unique `(region, user)` index is the canonical scoped-role table, auditors are a scope-less membership row, suppliers and customers are owner fields. The one true chain (row 5, operator-of-*current*-authority) is X1 because the intermediate is mutable, and it has an honest one-hop fallback the schema already carries. Everything the archetype was built to break — who may write which row *from which engine*, quorum, frontier-labelled completeness — is dimension P, which the RFC absorbed as authority placement and quorum-as-host-boundary (RFC:258); none of it is a rule-language gap, and none is charged to core. The single change that flips the app is the denormalisation the v0 skipped (row 4); X11 is the same seated-system-principal need as every other app. The design did reach for something the RFC refuted, but not in authorization: prediction 3's "`serialBy`/OCC on one engine" (RFC §8 last rows) and the wrong tools `merge: lww`, `sequence`, `replica`, `partitioned()` (MR-V:820).

### Sprawl check

- **X11** — load-bearing. Allocation events, heal, expiry, self-fence and rebalancing are the product; every one is a job or schedule.
- **X1** — droppable. Key operator reads on the region captured at write time (`poolLog.authorityRegion`, MR-V:333); the new authority's operators lose sight of pre-failover records of the pool they inherited — acceptable, and MR-D:216 already routes those records through demotion review under the new term.
- **P / quorum** (rows 6, 8) — load-bearing for promises 1, 4, 8, 9, 15 (MR-V:62), but outside the rule model by the RFC's own ruling; a one-engine product keeps all rules unchanged and loses those promises (MR-V:1117 "collapsing N engines into one SQLite and keeping promises 1, 2, 4, 8, 9, 15 in the marketing" is the cheat).

- **X11** — load-bearing. Host receipts, epoch publication, deletion finalisation, and the named-program write grant that makes an anonymous mix insert imply a spent token.
- **X5** — droppable (table split, row 6). **RFC N device-as-viewer** — droppable on the server plane (account principal + identity-layer sessions, row 1).

### App verdict — **NEEDS: X8 (with X16 inside it), X3 (install as principal), X11**

Authorization **was** the app's hard problem, by construction (PL-D:3 "Axis: rule ownership and composition across untrusted authors"), and the RFC agrees it is a language change (dimension Q, RFC:259; W4:117 "failed on 'no language change'"). The finding for 0331 is sharper than "needs Q": the *actors* and *relationships* of Concourse lower cleanly to core — tenant scope, staff permission rows, install scope-grant rows, field ownership, vault, refusal disclosure, live revocation are all CORE or a denorm the v0 skipped (rows 1–4, 8–10). What core cannot hold is (a) more than one **author** of rules per table (row 5–6), (b) more than one **principal** per execution (row 7), and (c) a non-human **principal origin** for installs (row 3). X8 alone flips rows 5–7, 9, 11; X3 (narrow) flips row 3; X11 is the shared system-principal need. The design reached for two things the wave refuted: app fields as columns on `orders` (refuted by `E_SECRECY_MIX`, PL-V:62, PL-V:1110) and `permissions set<text>` on the role row (split to `rolePermissions`, PL-V:102); and its numbers contradict its own posture (PL-V:1108 six gates × 5 ms against a 20 ms budget).

Outside the server plane (not charged to core): weighted-round-robin fairness (PL-V:995 "not in the language — job runtime"; RFC:259 "fairness is a job-scheduler policy"); webhook delivery and HMAC (PL-V:997); offline POS prediction (PL-V:1001).

### Sprawl check

- **X8** — load-bearing. Promises 3, 5, 11 and U1 (PL-D:606–617). The reduced product the v0 names — "Apps subscribe and cancel after commit; no in-commit rules" — is acceptable for "Marketing pixels, SMS (TextBlast)" and a cheat for "Sentinel as a required fraud gate; 'an app can enforce'" (PL-V:1088). A platform without Q is a webhook platform.
- **X3 (install as principal)** — load-bearing. Every app write must be attributed to the install (promise 2 PL-D:33, `write_audit.actor`); without a non-human principal every app write is a staff user's, which also destroys row 7 and autonomous jobs.
- **X11** — load-bearing (fan-out continuation, reactions, invoices).
- **X16** — droppable as a separate item: permission codes are closed (row 2); stored predicates live inside Q.
- **X1** (role→permission chain; install→merchant pin; share by app id) — droppable via the three denormalisations in rows 2–4.
- **`ctx.initiator`** (row 7) — load-bearing for the stated bar (inv 16 is a security invariant), but droppable to an honest, industry-standard reduced product: the design itself notes "Shopify apps act with app scopes regardless of the clicking staffer; Salesforce Apex runs in system mode by default — both the opposite of invariant 16" (PL-D:668–670).

**Codes by frequency.** X11 appears in **4/4** apps and is load-bearing in all four — but in its *smallest* form it is not a principal kind: it is "schedules, effects, continuations and jobs run as one declared, seated ordinary principal, and a table may grant inserts to named programs". Every K5 time-as-state lowering in the wave presumes it. X3 appears in **2/4** as load-bearing, each time in a narrow, different form: an anonymous invocation (Cove) and a non-human install principal (Concourse) — never `principal.kind` as a general rule term. X8 (dimension Q) appears in **1/4**, load-bearing, and is the only extension in this slice that changes the *rule model* itself (rules as owned, composed, stored data plus `ctx.initiator`); the RFC already ruled it a language change. X9 appears in **1/4**, load-bearing (commit-fresh evidence; session/device as terms). X4 appears in **1/4**, load-bearing with X3. X1 appears in **2/4**, droppable both times by denormalisation the designs skipped (the v0s leaned on v1's multi-probe budget instead of 0331's "denormalize the scope id"). X17 (2/4) and X19 (1/4) are thin and droppable — they reduce to program logic once X11 exists; the RFC's quorum ruling removes the only load-bearing X17 shape from the rule model entirely. X5 appeared twice and was replaced by a protection-class table split both times; X15 and X16 were not needed (nine roles with explicit sets; closed permission codes). X10 and X20 (P) appeared as *rulings*, not as gaps.

**What this slice says about 0331's core.** On the server data plane, the scoped-role recipe (`{scope, principal, role}` + unique `(scope, principal)` + one-hop `exists`) covered every human-actor relationship in all four premise-breakers, including a hospital's facility-scoped 9-role enum, a six-region operator roster, a marketplace's per-merchant staff permissions and per-install scope grants — with denormalisation, and without hierarchy, lattice, or multi-hop. The genuine gaps are all **about who is running**, not who may see what: something must run as a system principal (X11), something may run as nobody-with-a-proof (X3+X4), something may run as two principals at once (`ctx.initiator`), and something must know *when* it is running (X9, the commit instant). The one rule-model extension (X8/Q) is an RFC-ruled dimension for a product category, not a leak in the recipe.
