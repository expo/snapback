### 2. Schema in v0

v0.1 has no `optional`, enum, or `int({ max })`: absent money is `0`, absent ids `''`, enums `text({ max: 24 })` checked in rules. Drafts get a seller-only table so `listings` is world-readable without the `public()`-as-conjunct ambiguity; the reserve amount gets its own table because v0 has no column visibility (v1's `E_SECRECY_MIX` split). `proxyBids` carries `firstBidAtNeg` and `bidderIdInv` so one `desc` scan yields `maxCents DESC, firstBidAt ASC, bidderId ASC` (§6 #7). Abbreviations: `sys` = `principal.kind === 'system'`; `order(x)`/`listing(x)` = `db.get(orders|listings, x)!`; `noBids(l)` = `!any(proxyBids.byListingRank, [l], { take: 1 })`; `party(o)` = buyer or seller is `viewer`. Columns follow the design's §4 (Cents → `int()`, Time → `time()`); the two load-bearing tables are spelled in full.

### 3. Operations in v0

Pure helpers, inlined at `check` (`Math.*` avoided in case it is `E_OPAQUE`): `min`, `max`, `increment(p)` (the §4 table as a ternary chain), `nextMin(bids, start, price) = bids === 0 ? start : price + increment(price)`, `fvf(total) = min(divmod(total * 1325, 10_000).q, 75_000)`, `invertId`, `periodOf(ms)`, and

```ts
function recompute(start: number, reserve: number, top: { bidderId: string, maxCents: number }[]) {   // top = byListingRank desc take 2; reserve 0 = none
  if (top.length === 0) return { leader: '', price: start, met: reserve === 0 }
  const high = top[0], met = reserve === 0 || high.maxCents >= reserve
  if (top.length === 1) return { leader: high.bidderId, price: met && reserve > 0 ? reserve : start, met }
  let price = min(high.maxCents, top[1].maxCents + increment(top[1].maxCents))
  if (met && reserve > 0) price = max(price, min(reserve, high.maxCents))
  return { leader: high.bidderId, price, met }
}
```

`recompute` needs only the top two ranked rows: the design's "load all proxies" is a `take: 2` under system visibility, exact because the system read rule is uniform-true (ruling 8).

#### 5.1 `publishListing` — plan

Reads `users` (suspended), `any(invoices.bySellerState, [viewer, 'overdue'], { take: 1 })`, the draft; validates the §4 inequalities; inserts `listings` (`state: 'live'`, `publishedAt: ctx.commitTime`, `endsAt: publishedAt + days`), `listingReserves` if any, the 35¢ fee row, a `feePeriodActivity` row if absent; deletes the draft. The close timer is enqueued by the `schedule(closeListing, { at })` declaration in the same commit. `endsAt` is `commitTime`-derived: with `ctx.now()` a client could publish a window ending inside its skew allowance. Examined ≤ 6, writes ≤ 5, **closed**.

#### 5.2 `placeMaxBid` — the hot path

**First attempt**, one mutation from the design's step list: `(a) require(l.state === 'live' && ctx.now() < l.endsAt)`; `(b) scan(proxyBids.byListingRank, [id], { order: 'desc', take: 4096 })`; `(c) recompute` over the page written to `listings.currentPriceCents/highBidderId`; `(d) insert(bidEvents, { bidderId: prevLeader, kind: 'proxy_stand' })`; `(e) insert(notices, { userId: prevLeader, type: 'outbid' })`.

```
E_STRUCTURAL_COUNT (ruling 8) at (b)-(c): sort/[0] over proxyBids, whose read rule (bidderId === viewer) is not uniform-true
  for the caller, written as a listing fact. A bidder-visible fold sees one row — its own — and stands itself as leader at
  the start price. rewrite: compute under system visibility (phase: 'system' continuation) or declare a maintained
  aggregate with readable — the second rewrite is WRONG for this app (§4, §6 #1).
rule-denied write sites at (d),(e): bidEvents.insert / notices.insert require sys; the mutation is client-callable. No §9
  family names a statically denied write site.
E_BOUND at (b): 4,098 entries per bid; the fold needs 2.
ADMITTED, wrong, at (a): ctx.now() is the bidder's intent clock, validated within a skew window and reused. A device 20 s
  slow submits at endsAt − 5 s device time, commits at endsAt + 15 s, and the snipe sticks — Trap 2's cheat, no diagnostic. §6 #2.
```

**Corrected**: the viewer phase writes only the caller's rows and returns no standing; the fold is a system continuation keyed by the revision.

```ts
export const placeMaxBid = mutation({ listingId: id(listings), maxCents: int(), requestId: id() },
  { phase: 'system', continuation: r => foldStanding({ listingId: r.listingId, revisionId: r.revisionId }) },   // dimension L spelling
  ({ db, ctx, args }) => {
  if (db.get(proxyBidRevisions.byRequest, [args.listingId, ctx.viewer, args.requestId]) !== null) return { replay: true }   // idempotent ack
  const l = db.get(listings, args.listingId); db.require(l !== null && l.sellerId !== ctx.viewer, 'OWN_LISTING')
  db.require(l.state === 'live' && ctx.commitTime < l.endsAt, 'AUCTION_ENDED')        // hard close on the server clock
  const mine = db.get(proxyBids.byListingBidder, [args.listingId, ctx.viewer])
  if (mine === null) db.require((db.get(uniqueBidderCount, [args.listingId])?.value ?? 0) < 4096, 'LISTING_FULL')   // K2 route
  else { db.require(args.maxCents > mine.maxCents, 'MUST_RAISE'); db.require(mine.raiseCount < 64, 'MAX_RAISES') }
  const bids = db.get(bidCount, [args.listingId])?.value ?? 0
  if (l.highBidderId !== ctx.viewer) db.require(args.maxCents >= nextMin(bids, l.startPriceCents, l.currentPriceCents), 'TOO_LOW')
  const at = ctx.commitTime                                                             // firstBidAt is the tie-break: never intent time
  db.upsert(proxyBids.byListingBidder, [args.listingId, ctx.viewer], old => old
    ? { ...old, maxCents: args.maxCents, lastRaiseAt: at, raiseCount: old.raiseCount + 1 }
    : { id: ctx.newId(), listingId: args.listingId, bidderId: ctx.viewer, maxCents: args.maxCents, firstBidAt: at, firstBidAtNeg: -at, bidderIdInv: invertId(ctx.viewer), lastRaiseAt: at, raiseCount: 1 })
  const revisionId = ctx.newId()
  db.insert(proxyBidRevisions, { id: revisionId, listingId: args.listingId, bidderId: ctx.viewer, maxCents: args.maxCents, requestId: args.requestId, createdAt: at })
  return { accepted: true, revisionId, standing: 'pending' }          // never "you're winning": the fold decides (promise 20)
})

export const foldStanding = mutation({ listingId: id(listings), revisionId: id(proxyBidRevisions) }, { callable: 'system' }, ({ db, ctx, args }) => {
  const l = db.get(listings, args.listingId)
  if (l === null || l.state !== 'live') return { folded: false }       // BIN/close won; the close's own fold counted this row
  const rev = db.get(proxyBidRevisions, args.revisionId), reserve = db.get(listingReserves.byListing, [l.id])?.reservePriceCents ?? 0
  const next = recompute(l.startPriceCents, reserve, db.scan(proxyBids.byListingRank, [l.id], { order: 'desc', take: 2 }))
  const prev = { leader: l.highBidderId, price: l.currentPriceCents, met: l.reserveMet }
  if (next.leader === prev.leader && next.price === prev.price && next.met === prev.met) return { silent: true }   // no public write: R6 for free
  const at = ctx.commitTime, caller = rev.bidderId, events: { bidderId: string, price: number, kind: string }[] = []
  if (prev.leader === '') events.push({ bidderId: caller, price: next.price, kind: next.met && reserve > 0 ? 'reserve_meet' : 'first' })
  else if (next.leader === prev.leader) {
    events.push({ bidderId: caller, price: min(rev.maxCents, next.price), kind: 'challenge' })     // design step 10 verbatim — §8 #1
    events.push({ bidderId: prev.leader, price: next.price, kind: 'proxy_stand' })
  } else {
    const prevHigh = db.get(proxyBids.byListingBidder, [l.id, prev.leader])                       // hidden row: the system reads it
    events.push({ bidderId: prev.leader, price: prevHigh.maxCents, kind: 'exhausted' })
    events.push({ bidderId: caller, price: next.price, kind: next.met && !prev.met && reserve > 0 ? 'reserve_meet' : 'challenge' })
  }
  for (const e of events) db.insert(bidEvents, { id: ctx.newId(), listingId: l.id, bidderId: e.bidderId, stoodPriceCents: e.price, kind: e.kind, createdAt: at, causedByRevisionId: rev.id })
  db.update(listings, l.id, r => ({ ...r, currentPriceCents: next.price, highBidderId: next.leader, reserveMet: next.met, standingChangedAt: at }))
  if (prev.leader !== '' && next.leader !== prev.leader)                                          // the leadership edge, same commit as the fold
    db.insert(notices, { id: ctx.newId(), userId: prev.leader, listingId: l.id, orderId: '', type: 'outbid', payloadJson: `{"price":${next.price}}`, createdAt: at, deliveredAt: 0, dedupeKey: `outbid:${l.id}:${rev.id}` })
  return { isHighBidder: next.leader === caller }
})
```

**What serializes, exactly.** On the single-writer SQLite lowering every mutation is one serialized transaction: 80 bids/s on one listing queue FIFO, no retries, ≤ 7 entries per viewer phase. On a multi-writer lowering the viewer phase's trace is the listing row, two maintained rows, and its own unique key: it conflicts with BIN/close (listing-row writes) and with nothing another bidder writes except the maintained `uniqueBidderCount` row that every *first* bid bumps — the hot key. The design's "listing-scoped lock" reappears in the fold: continuations keyed by `revisionId` are idempotent but **not ordered per listing** by anything §7 says, and the close keyed by `listingId` is not ordered behind them. If fold(k+1) runs before fold(k), events and the outbid edge are computed against the wrong `prev` (the final price is still right: `recompute` is a function of the set). If the close runs before a pending fold, the bid is counted (the close refolds) but its event and outbid notice are never written — invariant 11 silently lost. The design's retry policy (16 waits, then `BUSY`) is engine policy with no stated bound and no intent state. §6 #3 names all three. Viewer phase examined ≤ 7, writes 2, **conditional** (cap, unique, OCC, provisional `commitTime`); fold ≤ 10, writes ≤ 4. The viewer phase never computes a standing, so `conditional` *is* the design's "Submitting…"; §6 #6 wants it declared rather than incidental.

#### 5.3 `buyItNow` — refused→rewrite

First attempt inserts the seller's `you_sold` notice and the FVF entry under the buyer: both sites rule-denied. Corrected: idempotency by `orders.byListing` + `requestId`; guards `!suspended`, `sellerId !== viewer`, `state === 'live' && ctx.commitTime < endsAt`, `binPriceCents > 0`, `uniqueBidderCount === 0` (**proxy rows, not events — §8 #3**); one `listings.update` to `sold_bin` and one `orders` insert (`source: 'bin'`, `paymentDueAt: commitTime + 4 d`); a `settleBin` continuation (`callable: 'system'`) writes the FVF entry, the activity row, and the `bin_bought`/`you_sold` notices, deduped by `dedupeKey`. The race: the buyer's `listings.update` rule carries `noBids(o.id)`, so its verdict depends on the proxy range; a concurrent first bid's insert overlaps that rule-dependency key and the maintained count BIN read — one commits, the other re-executes and refuses. `orders.byListing` unique is the backstop the design asked for. Prediction 5's "OCC on the item row" is **true in effect, wrong in locus**: the bid never writes the item row. Examined ≤ 8 + probe 3; **conditional** (the client replays against the cached verdict for `any`).

#### 5.4 `cancelLiveListing`, `reviseBeforeFirstBid`, `appendDescription` — plans

Cancel: seller check, `state === 'live' && commitTime < endsAt`, `uniqueBidderCount === 0` (the rule repeats it with `noBids`), one update. Revise: the four revisable fields; `immutableExcept … when noBids(o.id)` refuses after the first bid at the engine. Append: one insert. The design's fifth writer is serialized against bids by the same rule dependency. Cancel, revise **conditional**; append **closed**.

#### 5.5 Close, unpaid expiry, auto-release — per-row timers, not a 200 ms sweep

First attempt as designed, `schedule(sweep, { every: '200ms' })` over `byStateEnds ['live'] range lte now take 100` closing inline: `E_BOUND` (≈ 900 examined, ≈ 600 writes per run) and `E_FANOUT` on a minute burst over 100. The v0 form is the `at:` declaration in §2: one timer per listing, enqueued in the publish commit, no scan. `closeListing` (`callable: 'system'`): returns if `state !== 'live'` (BIN or cancel won — idempotent); `require(ctx.commitTime >= l.endsAt, 'WOKE_EARLY')` (a bid at `endsAt − 1 ms` already committed or never will); refolds `recompute` over the `take: 2` scan (the design's repair step); no leader or reserve unmet → `ended_unsold`; else `ended_sold` with `winnerId`, `hammerPriceCents = price`, one `orders` insert (`source: 'auction'`, `paymentDueAt + 4 d`), the FVF entry and activity row, `you_won`/`you_sold` notices deduped by `${type}:${orderId}`. Examined ≤ 9, writes ≤ 6.

`expireUnpaidOrder` (`at: paymentDueAt`): no-op unless `awaiting_payment`; `unpaid_cancelled`, an `orderEvents` row with `actorId: ''`, notices to both. `autoReleaseEscrow` (`at: autoReleaseAt`): no-op unless `shipped && !returnOpen && autoReleaseAt > 0`; then the §5.11 body, duplicated because v0.1 has no `db.run` (§6 #8). The expiry-versus-late-charge race is settled in `applyChargeResult`. `autoReleaseAt` is `0` until shipment; §7 enqueues "in the commit that creates or changes the trigger row", so shipment re-enqueues; whether the `0` enqueue fires-and-no-ops or is suppressed is **[inferred]**. Firing lateness after `endsAt` is unbounded by the text and does not matter: admission is `commitTime < endsAt`, so late settlement is late, never wrong — Trap 2's "liveness is a clock, `state` is a settlement fact" is v0's K5 verbatim.

#### 5.6–5.8 Reads — plans

`getListingLiveView` (public; `{ readTime: { granularityMs: 1000 } }`): `db.get(listings)` (drafts are another table, nothing to strip), `bidCount` and `uniqueBidderCount` maintained rows; returns the row plus `acceptingBids = state === 'live' && ctx.readTime < endsAt` (display; authority is `commitTime` in the writes), `binAvailable = binPriceCents > 0 && accepting && bidders === 0`, and `nextMinBid`. The countdown is client arithmetic on `endsAt`; `secondsRemaining` is not returned because `clock@1000` in the read set of 30,000 subscribers is 30,000 re-evaluations per second if the server reruns at every bucket rather than at the one boundary where a comparison flips — the text does not say which **[inferred]**. Examined ≤ 3. `getMyAuctionStanding`: listing, own unique proxy row, `bidCount`, the reserve row for the seller; `isHighBidder = l.highBidderId === viewer`, `headroomCents = max(0, myMax − price)` when leading — caller facts over visible rows, torn-proof by construction; ≤ 5. `getBidHistory`: `bidEvents.byListingTime [id] asc take 50 after cursor`, mapped through `db.get(users, e.bidderId).handle` (shape-keyed point reads); ≤ 102. `searchLiveListings`: `byToken [term] take 50`. The ten list/detail queries are prefix scans on `viewer` or an argument plus shape-keyed point reads.

#### 5.9 Payment capture — the effect seam

`captureBuyerPayment` (buyer): requires `awaiting_payment && commitTime < paymentDueAt`; returns `in_progress` if `payments.byIdempotency [order:{id}]` exists (second device); else inserts one `pending` row with `amountCents = totalCents`. `chargeProcessor = effect({ on: payments, when: p => p.status === 'pending', outbox: true })` calls the processor with `idempotency_key = order:{id}` and invokes `applyChargeResult` (`callable: 'system'`); a timeout leaves `sent_unknown` and the `processorWebhook` host-ingress effect completes it. `applyChargeResult`: no-op unless the payment is still `pending`; on success, if the order is no longer `awaiting_payment` (expiry won) it inserts a `refundRequests` row — compensation — else `paid_held`, `paidAt`, an order event, a `payment_received` notice. The processor call is never in the transaction; the unique key is the join; capture predicts **conditional** on it, and "Processing…" is the `pending` row, never a predicted `paid_held`. Identical in shape to wave 2's payments.

#### 5.10–5.13 Shipment, release, feedback, returns — plans

- `confirmShipment` (seller): idempotent on `shipped` + same tracking; requires `paid_held`; sets `shipped`, `shippedAt`, `autoReleaseAt = now + 3 d`, `returnWindowClosesAt = now + window` (from `shippedAt` until delivery is known); order event; a `shipped` notice to the buyer, granted for that type by the `notices.insert` rule. **closed.**
- `confirmDeliveryAndRelease` (buyer): no-op if `completed` (auto-release won); requires `shipped|delivered` and `!returnOpen`; sets `completed`, `deliveredAt` if unset, `completedAt`, `releasedAt`, `feedbackOpen`, `returnWindowClosesAt` from `deliveredAt`. The rule's `releasedAt 0 → > 0` transition is the single-release fact. **conditional.**
- `leaveFeedback`: party check; `completed && feedbackOpen && commitTime < completedAt + 60 d`; returns the existing row for a repeat `(orderId, role)`; one insert; two maintained sums move. **conditional.**
- `openReturn` (buyer): `returnWindowClosesAt > 0 && commitTime < returnWindowClosesAt`; allowed states; inserts `returns` with `openKey = orderId`; sets `returnOpen`, `autoReleaseAt = 0` (the timer re-enqueue is the hold extension); a `payoutClawbacks` row when already `completed`; a `return_opened` notice to the seller. **conditional.**
- `resolveReturn` (seller/support): state + `openKey = own id`; `refunded` → `refundRequests` → `refundProcessor` effect → `applyRefundResult`. `freezeOrderDisputed` (support): `disputed` + event. `closeReturnWindow`/`closeFeedbackWindow`: flip the flags. **closed.**

The two windows the design states as clock comparisons are schedule-flipped statuses in the *rules* (`feedbackOpen`, `returnWindowClosesAt`) and `commitTime` compares in the *programs*: ruling 11 twice.

#### 5.14 Monthly invoices — schedule, `job` missing

First attempt: one run over every active seller, inserting the invoice and patching all entries → `E_BOUND` (40k sellers × unbounded entries) and `E_FANOUT` at any `take`. Corrected: an hourly resumable schedule (`callable: 'system'`) over `feePeriodActivity.byPeriodStatus [previousPeriod, 'pending'] take 25`; per seller, read `uninvoicedFees`, insert the invoice if `invoices.bySellerPeriod` has none (plus an `invoice_ready` notice), patch `feeEntries.bySellerPeriodInvoice [seller, period, ''] take 200` to the invoice id, and mark the activity row `done` only when `!hasMore`. ≈ 5,127 examined, ≤ 5,025 writes per run — under a published `G` only if `G` is generous **[inferred]**. An entry arriving after the invoice exists re-flags the activity row `pending` (in `settleBin`/`closeListing`) and joins the open invoice with a total repair: "billed on a repair pass, never twice", enforced by the `invoiceId === ''` prefix. "First Monday 00:10 UTC" is inexpressible (`every` only). The honest form is v1's `job` with a `commitSeq` watermark (§6 #8).

#### Effects and the notice outbox

`deliverNotice = effect({ on: notices, when: n => n.deliveredAt === 0, outbox: true })` pushes with `dedupeKey` as the provider idempotency key, then invokes `markNoticeDelivered` (`callable: 'system'`). The outbid notice is a row in the fold's commit; a rolled-back fold leaves no row and no push (Trap 5); offline losers get the row on reconnect through `myNotices`. `coalesceWatcherAlerts = effect({ every: '10s' })` reads `listingsChangedSince(watermark, take 500)` over `byStandingChanged` and `watchesPage(listingId, cursor, take 500)` as a service principal and pushes per listing. Watcher alerts never enter the bid commit: 20,000 watches × 200 bids is `E_FANOUT` at any `take` — the spec refusing the design's own "cheat-to-death".

### 6. Language delta

Ranked by how wrong the answer is without it.

1. **Disclosure of a projection, not of an aggregate** — `maintain.top(proxyBids, { by: ['listingId'], order: rank, k: 2, project: (top, l) => recompute(...), readable: public })`. The K2 admit route as written discloses the aggregate's *value*; for `max`/`rank` over secret maxima that value is the secret. The spec admits `maintain.max(proxyBids.maxCents, readable: public)` with only an informational `E_DISCLOSURE`, and no spelling discloses `f(top-2)` while sealing the top-2. Smallest: a maintained top-k whose readable value is a declared pure projection; the engine keeps the k rows hidden, publishes the projection, diffs invalidation on it. *General* — top-of-book without order ids, surge from counts, brokerage last value. Amends §2, §4.4, §9. Also makes invariant 1 an engine fact and lets `placeMaxBid` be one commit.
2. **Deadline compares must use `commitTime`, and the checker must say so.** `E_AMBIENT_TIME` steers from `Date.now()` to `ctx.now()`, the *intent* clock, reused at settlement (§4.3, ruling 9): `require(ctx.now() < endsAt)` admits a snipe that commits after the close, and `firstBidAt: ctx.now()` lets a bidder backdate tie priority — both silent. Smallest: `ctx.commitTime` always available in mutations, plus `E_INTENT_TIME_WINDOW` refusing `ctx.now()` compared against a `time()` column or written into one an index orders by. *General*; re-found wave 2's payments finding independently, with the tie-break as a second instance. Amends §4.3, §9.
3. **Serialization of a viewer intent's system fold.** Dimension L's continuation is a second transaction with no per-key order; the design's lock needs (a) a **same-commit system segment** (`phase: 'system', sameCommit: true`, the certificate listing the elevated write sites and disclosure) or (b) FIFO of continuations and schedules sharing a key, plus a contention policy: an OCC retry budget and an `E_CONTENTION` intent state (the design's `BUSY`). Smallest: (b) + policy; (a) is what the design wrote. *General* (order-book fills attributed to resting orders, dispatch offers). Amends §6, §7, v1 §3.
4. **Coupled writes** — `coupled(notices, { when: n => n.type === 'outbid', to: listings, key: n => n.listingId, transition: (o, n) => o.highBidderId === n.userId && n.highBidderId !== n.userId })`: a row admitted only in a commit where a named transition occurred. Makes "notice only on the edge" and "event attributed to the incumbent only when the standing moved" engine facts, and lets a *viewer* program write them without system authority. *General* (dimension C, reversed). Amends §2.
5. **Broadcast subscription class** for uniform-true public reads: 30,000 subscribers × 200 folds/min is 6M per-subscriber reruns; the trace already knows the rule is `public`. Corroborates wave-3 predictions 1 and 8. Amends §6.
6. **`predict: false` and `delivery: 'online-only'`** on `placeMaxBid`, `buyItNow`, `captureBuyerPayment`: the design forbids local prediction and outbox replay after a network gap (promise 18). v1 §3 names both. Amends §4.3, §6.
7. **Mixed-direction composite indexes** (`['listingId', desc('maxCents'), 'firstBidAt', 'bidderId']`); every rank-with-time-tiebreak otherwise needs negated shadow columns. Wave 1 found it; v1 §4 still lacks it. Amends §2.
8. **`db.run(named)`** for the release body shared by the buyer's confirm and the auto-release timer (v1 has it). **`job`, indexes over maintained rows, cron `at`** for invoices (v1 dimension I). **Rules over maintained rows** so the BIN/cancel guard is a point read, not a range verdict (clarify §3).
9. **Invalidation must diff on the disclosed result; receipts must carry no version of hidden or maintained sources.** Otherwise a silent raise, which changes a hidden proxy row and (under #1) a maintained row, ships a "something changed" bit to 30,000 watchers — the design's R6 leak. Amends §6, ruling 3.
10. Type completeness this app tripped: `optional`, `int({ max })`, enums with transitions, partial `unique … where`, `appendOnly({ except })`, a named family for a statically rule-denied write site. All in v1 §4 or trivial.

App-specific, do not add: the increment table, second-price arithmetic, event kinds — pure helpers.

### 8. Where the design is wrong

Exposed by writing it strictly, not by taste.

1. **A leader who raises past a tie is charged with challenging themself, and `bidCount` double-counts.** Step 10's second branch ("same leader, price rose") emits `(caller, challenge)` and `(prev.highBidderId, proxy_stand)` without checking whether the caller *is* the leader. Reach it: start $1; Alice max $10 (leads at $1); Bob max $10 (tie — Alice keeps the lead at $10, her max; `beat` $10.50); Alice raises to $20 → price $10.50, leader unchanged, price up. The design writes two rows, both attributed to Alice at $10.50, and `bidCount` rises by 2 for one act — against invariant 3's spirit (events are stands; Alice stood once) and promise 5's framing (this raise is neither silent nor a challenge). Confirming observation: that sequence; expect two `bid_events` rows with `bidderId = Alice` and `bidCount += 2`; the correct history has one `proxy_stand`.
2. **"`reservePriceCents` is seller-only" is false whenever the reserve binds.** Invariant 10 stands the lone bidder *at the reserve* once their max meets it, and with two bidders sets `price = max(beat, min(reserve, high.max))`; in both cases the public price equals the reserve exactly while `reserveMet` flips in the same commit, telling everyone the number they see is the reserve. §2's secret-column split protects a number the product publishes by construction; the design should say "secret until met". Confirming observation: reserve $30, one bidder max $50 → public price $30.00 and `reserveMet: true`.
3. **The BIN/cancel guard is on `bidCount` (public events), but the fact that kills BIN is the existence of a proxy row.** The two coincide only inside the design's single lock, where a first accepted bid always writes an event in the same commit. Under any implementation where the proxy write and the fold are separate commits — v0.1's continuation, and what the design's own R1 says a row-level backend produces — a BIN guarded on `bidCount` commits over a committed proxy bid: a paid BIN and a live proxy on one listing, invariant 5 broken. Invariant 6 should be stated on `uniqueBidderCount`, which invariant 7 already keys on. Confirming observation: run a bid's proxy write, then BIN before the fold; with the guard as designed, `state = sold_bin`, `bidCount = 0`, `uniqueBidderCount = 1`.

Recorded, not ranked: the `exhausted` event publishes the loser's exact max even when `high.max < beat` and the price therefore did not (promise 4's "losing maxima are not secret" is broader than the second-price leak the design says it intends); and 8,192 events with 4,096 bidders × up to two events per accepted bid means a hot listing can hit the event cap while live, after which every bid is refused — a `LISTING_FULL` the product never named.
