Material findings:

1. Replay-created activity can emit after replay is disabled within the same period.

   `grok-app.patch:236-248` stamps follows and `:397-458` increments all post counters regardless of `replayMode`; only `digestSweep` checks replay at emission. A replay-on write followed by replay-off before the boundary therefore appears as fresh activity. The retained replay case at `owner-cases.test.ts:626-680` advances an entire period before disabling replay and misses this case. Guard or ineligibly stamp source writes, and test replay-on → write → replay-off → same-period sweep.

2. Digest time is per chunk, not per sweep.

   `grok-app.patch:95-104` and `digest-recipes.q:47-53` recompute the bucket from `now` inside one-profile chunks. LLP 1016 defines `now` as pinned per chunk. If a sweep crosses a two-minute boundary, later profiles inspect P+1 while earlier profiles inspect P; the following scheduled job also selects P+1, permanently skipping P for those later profiles. The independent prune job can compound this by advancing its deletion threshold before the corresponding profile sweep completes.

   The robust repair is a logical schedule-occurrence cutoff carried through one ordered profile→prune job. Current Quarry explicitly forbids arguments on `every` targets, so `digestSweep(now)` is not an existing supported remedy.
