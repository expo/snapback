## 2. New defect

**High — §2.1a. An `online only` kind is not the partial kind the mechanism and the read rule implement.**

The residency list has three states. Floored is **partial**. `online only` is a third state: “that kind is online only.” The mechanism that follows only leaves a **partial** kind out of the snapshot walk. The unknown-read rule fires only “while either kind is partial.” `timeline.q` still generates `@T@Posts` as one `sync public` table with no horizon, and `schema.synced()` walks and logs a table, not a kind. An `online only` source has no `sync`, so it is not walked and not logged. Its events have nowhere to ride.

Two readings, both wrong:

- Follow the mechanism. Posts are `online only`, reposts fully synced. Original events are not partial, so the horizonless walk still delivers all 50,228 of them. The device holds no posts and every original event. That is the corpus revision 6 exists to remove, and it falsifies “a device needs an event only when it holds the event’s source row.” The §5 list never acquires an `online only` source, so this passes every probe written there. Reads happen to be true only because the rows were kept. With posts `online only` and reposts floored, the partial guard fires and “a hit may be returned,” so a point read of a kept repost event returns data for a kind the same section calls `online only`. An `online only` read is unknown even on a hit (`get_inner` marks `sync` none before it looks at the row).
- Honor “that kind is online only” and omit the rows, but leave the guard as written. Posts `online only`, reposts fully synced: neither kind is partial, so `probe_witness` treats a horizonless miss as known absence. `feedPosts[originalEventId]` publishes null for an event that exists on the server. A rule can refuse locally. That is the revision-7 unscoped-read bug, moved to this residency.

**Smallest change.** An `online only` kind is omitted from the snapshot walk and is not retained. Its puts do not decide device state. Its deletes still apply. There is no paired image, because the source is not delivered. While either kind is not fully synced, partial or `online only`, the unscoped rule already stated for partial kinds applies, and a hit of an `online only` kind is unknown, not data. A `byActorPost` miss of a fully synced kind stays a known null.

## 3. The three places you asked about

**Paired event state is implementable, and ignoring a partial kind’s raw puts does not lose a committed event.**

`snapshot_page`, snapshot catch-up, and the ordinary stream are three deliveries of a source image. Catch-up and the ordinary stream are the same `stream` path: `expand_joins` already `fetch`es each put in the serving transaction at `head`. Reading the event there, by `(author, post, false)` or `(actor, post, true)`, is the same server state as the image that function delivers. `snapshot_page` is a separate transaction per page; the join belongs in that walk, next to the source row it emits. The device does not re-run `timeline_apply` on a streamed image. It stores rows. The paired row has to be written beside the source.

Event rows are inserted only in the source’s birth commit and deleted only in its removal or unrepost commit (`timeline.rs`). Fields are immutable (`timeline.q`). There is no later event update to lose. Birth accounting’s “event before the final post image” is covered because the final image carries the event and the earlier put is ignored. Commits are indivisible (`stream`’s cut), so that pair is one page.

A put of a row `fetch` cannot find is rewritten to a `del` before the device sees it. The device instruction is kind-scoped and talks about puts the device receives: ignore a served put of a partial kind, apply a served delete. For a repost unreposted before the page is served, the insert’s event put is already that `del` and still carries the minted id, which a source `del` does not. Applying it is what removes the event on that page. Do not drop partial event entries on the server before `expand_joins`. Snapshot pages cannot carry a `del` (`snapshot.rs` rejects anything but a put, and staging starts empty), so snapshot absence is omission. Catch-up and the live stream must delete. The §5 stream-split probe distinguishes those. I do not count the encoding as a second defect.

Original event ids are the post id, and the post row is never deleted. Repost event ids are minted. After purge removes the tombstone, a client-supplied `new_id` can collide with an old repost event id. Log order still applies the old delete before the later insert, so unconditional deletes do not need a stronger “never reused” claim than the code has. Not a defect.

**The log-versus-walk split is implementable for a floored kind.** Keeping `sync public` leaves puts and deletes in the log (`account_row_change` logs only when `sync` is set). Filtering `repost` inside the one public walk omits one kind without setting a horizon and without clearing `sync`. The fully synced kind stays on that walk, and its puts still apply. That is Grok’s revision-7 mechanism, and it matches the code. It has no third switch for `online only`, which is the High above.

**The withheld trigger is specified tightly enough.** §2.1a’s bullets, not its looser opening sentence, are the rule: miss versus hit, scan versus `byActorPost` of a fully synced kind, and the three transition lookups decided from the held source rather than from `get_inner`. §2.2 puts that unknown on the existing no-`data` result, ahead of server-run routing. `predict` already turns `beyond_horizon` into a queue, so a probe that returns false and sets unknown does not become a local refusal. A point hit of a held partial row staying local is intentional and consistent.

## Verdict

**NOT READY.** The revision-7 pairing, walk, unscoped-read, withheld-trigger, `whole`-floor, and tombstone edits are the right design. An `online only` kind still has no delivery and no read rule that can be implemented without either keeping the event corpus or publishing a known null.
