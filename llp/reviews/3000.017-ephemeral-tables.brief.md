## What to judge

Verify the RFC's claims against the code — cite `file:line` for every
finding. A finding that says "the RFC assumes X but the code does Y" with a
citation is worth far more than a general concern. Where a claim can be
settled by compiling or running something small, do it (see Rules).

1. **Does it solve the problem?** Would a builder agent following the guide
   get a typing indicator that appears within 2 s and disappears within 5 s
   of the last keystroke under the benchmark's measurement (a 25 ms-delay
   keystroke burst, peers on the local-first web tier)? Trace the full path:
   keystroke → client coalescing/renewal window → `POST /m/` → engine →
   epoch → peer's `/changes` wake → peer's watch re-run → server answer →
   render → `nextExpiry` re-fetch → disappearance. Name any step where the
   RFC's mechanism does not exist or does not work as described.
2. **Authoring ergonomics.** Is "a table with one modifier line" the right
   surface versus Snapback 2's `channel`? Will agents find it? Are the
   refusals (§2.1, §2.2) the right set — too many, too few? Is the client
   contract (`Ephemeral`, `Signal`, the overload) sound in TypeScript?
3. **Correctness and authorization.** Snapback 4 has strict laws about
   disclosure (rules, `NOT_FOUND` vs `E_RULE`, the meter's charges, hidden
   rows) — see `crates/snapback4-core/src/engine/` (read.rs, write.rs,
   authorized_scan.rs, rules.rs). Does routing reads and writes through a
   `Layered` row store over `MemoryRows` preserve them? Journal undo on
   refusal? Absent-before-rules expiry via a hidden `$deadline`? Stale-answer
   fencing by epoch/incarnation? Revocation? Anything a hidden row could leak
   through the new epoch, the `/changes` wake, `E_EPHEMERAL_FULL`, or the
   rate limit?
4. **Bounded work and memory.** Snapback 4 has a bounded-work law (the meter,
   walk limits, LLP 3000.002). Are §3.5's bounds sufficient and enforceable
   where the RFC says? Does the new wake path create unbounded work
   (every ephemeral write waking every poll; every poll re-running every
   watch)? Is taking a read transaction + the hub mutex (not the writer
   lock) sound under concurrency?
5. **Compatibility.** Byte-identical serialization for schemas without
   ephemeral tables; the published-0.2.33 capability fences; the device's
   wasm budget; day-two classification; generation adoption; Postgres.
6. **The implementation plan (§4).** Missing files, wrong citations, steps
   that cannot work as described, tests that would pass without the feature
   working (e.g. a latency test on loopback that cannot fail), and the order
   of work. Is it one lane's worth of work tonight?
7. **Alternatives (§7).** If you think a different design is clearly better,
   say so and sketch it concretely — but weigh it against the evidence in §1
   and the time box.

## Output

Write your review as Markdown, and make it your final message. Structure:

```
# Review of LLP 3000.017 revision 1 — <your model family>

**Verdict:** READY | READY WITH CHANGES | NOT READY

## Summary
(3–6 sentences: the design's soundness and the few things that matter most)

## Findings
### F1 (High|Medium|Low) — <title>
- Where: <RFC section> and <file:line> in the code
- What is wrong: ...
- Evidence: ... (what you read or ran)
- Proposed change: ... (concrete wording or mechanism)

(... more findings, most severe first ...)

## What the RFC gets right
(brief)

## Probes run
(each command and its result, or "none")
```

Severity: **High** = the feature will not work, leaks something a rule
hides, breaks an existing law/fence, or cannot be built as planned.
**Medium** = a real defect with a clear fix that the lane must fold.
**Low** = wording, docs, minor. Do not pad; three real findings beat twelve
speculative ones. READY WITH CHANGES means: fold these and implement, no
second design round needed.
