**NOT READY**

1. **Backfill eligibility and composition need a transition model** — [§§2–3](/home/ccheever/projects/sb4-b17-mig/llp/3000.000.000.002-declarative-backfills.rfc.md:29). Keeping declarations in later releases conflicts with binding arguments against the immediate predecessor: after v2 removes an input field, v3 still carries a declaration requiring it. A v2-native row also has no receipt, just like an unprocessed v1 row. Multiple declarations can overwrite the same column without defined precedence or reversal order. **Fix:** specify durable declaration membership and row eligibility across introduction, unchanged carry-forward, rollback, re-entry, skipped releases and edited declarations. Define historical schema binding. Reject overlapping output columns unless an explicit composition and reverse-order rule is specified.

2. **Declared inputs do not necessarily contain the rollback preimage** — [§3](/home/ccheever/projects/sb4-b17-mig/llp/3000.000.000.002-declarative-backfills.rfc.md:51). A constant backfill with no arguments can overwrite an existing `flag` column. Its saved argument input is empty, so “restore … from the saved input” cannot recover the previous flag. The same problem occurs whenever an output column is absent from the argument list. **Fix:** separately persist every overwritten column’s actual previous value, interpreted source type/default and physical absence where relevant. Specify field-by-field conflict checks and evidence replacement across repeated rollback/forward cycles.

3. **Receipt reuse ignores lookup dependencies** — [§2](/home/ccheever/projects/sb4-b17-mig/llp/3000.000.000.002-declarative-backfills.rfc.md:34), [§3](/home/ccheever/projects/sb4-b17-mig/llp/3000.000.000.002-declarative-backfills.rfc.md:53). Suppose a backfill derives a booking price from a uniquely looked-up tariff. During rollback, the tariff changes while the booking’s declared input fields remain unchanged. The stated reuse rule preserves the stale derived price. **Fix:** define lookup changes as input changes, recording and comparing the relevant lookup keys, projected values, absence and row lifetimes. Alternatively, explicitly specify frozen lookup semantics and their consequences. Also define lookup binding against predecessor tables/indexes and missing/non-unique outcomes.

4. **The activation population and phase order are incomplete and partly contradictory** — [§3](/home/ccheever/projects/sb4-b17-mig/llp/3000.000.000.002-declarative-backfills.rfc.md:43). The governing release RFC §§2, 9.1 and 10 restores whole rows/cells, preserves their source definitions and retires expired source lifetimes before projection. “Pre-adoption image, interpreted by the predecessor schema” does not cover dormant rows absent from that schema. It is unclear whether restored rows are transformed or whether a transformation can change an expiry before mandatory retirement. Additionally, “ordinary v1 validation … refuses otherwise” contradicts the existing rule that incompatible present values become dormant. **Fix:** give one ordered activation algorithm covering source-lifetime retirement, retained-image assembly, reversal, forward transformations, narrowing/reference closure and validation. Define eligibility for active and dormant rows. Explicitly choose refusal or dormancy for incompatible candidate-native rows and identify any override of the parent RFC.

5. **Saved rollback values need reference-lifetime and asset protection** — [§3](/home/ccheever/projects/sb4-b17-mig/llp/3000.000.000.002-declarative-backfills.rfc.md:58). “Candidate authoritative columns” does not exclude references or assets. If a reference is overwritten, its former parent can be deleted and its id reused while the saved input survives. Restoring that id can attach the row to another lifetime; ordinary nominal-reference validation does not prevent this. Likewise, an overwritten asset may be collected unless its saved preimage retains its home. **Fix:** either restrict supported input/output types explicitly, or integrate saved preimages with the existing deletion-invalidated reference ledger, capture/audience checks and asset retention. Cover parent deletion/reuse, expiry, pruning and rollback restoration.

6. **Persistent compatibility and generation rules are missing** — [§3](/home/ccheever/projects/sb4-b17-mig/llp/3000.000.000.002-declarative-backfills.rfc.md:48). Existing binaries accept `snapback4-release-store-3` but cannot maintain the new evidence. Opening an older source with such a binary could permit writes/deletions that invalidate future receipt decisions. Separately, the parent RFC §6 permits equal-execution-content activations to retain generation; changing backfill logic can change authoritative values without changing table population. Merely promising an “ordinary generation reset” does not establish one. **Fix:** introduce a store-format fence rejected by unaware binaries, transactionally installed with the evidence. Bind backfill semantics to activation identity and require a fresh generation whenever transformed values or their audiences change, including unchanged schema/program shapes. Test old-binary refusal and connected-client reacquisition.
