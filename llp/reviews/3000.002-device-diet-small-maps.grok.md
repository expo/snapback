# Blind review: Snapback 4 S2 — small ordered maps

**Overall.** The collection itself is a careful BTreeMap stand-in: last-value-wins, first-key-on-insert vs last-key-on-`FromIterator`, sorted serde, COW `ObjectFields`, and an unchanged heap formula. Memory-store B-trees, `created`/`created_rows`, merge `seen` sets, and server interval maps were left alone. Sort helpers were not landed. I did not find a wire, durable-format, or meter-number change.

The conversion still puts one **large, randomly mutated, unmetered** map on the sorted vector: the device’s per-group held/left image. That is slower than BASELINE for a viewer in thousands of groups, and it is the class of map the lane said it was not converting. The identity pin is the right *shape* of test, but the pin file is new in this commit, so this review cannot prove it was captured on the BTreeMap binary.

## Mandatory answers

**Did a change introduce a new problem?** Yes. At BASELINE, a device’s held/left group image was a B-tree (`BTreeMap<String, BTreeMap<String, Membership>>`). At IMPL it is `SmallMap<String, SmallMap<String, Membership>>` (`history.rs` 10). Applying *n* put/scope/join events in log order (not key order) is binary-insert + suffix shift per event (`history.rs` 32–45, `smallmap.rs` 61–72). That path is not the interpreter meter. Membership JSON is still a sorted object (no durability bug); the work is **slower**, ~4× at 1 024 shuffled inserts and ~11× at 4 096 on the lane’s own figures.

**Is there a regression test that would also pass without the change it claims to test?**

- `tests/smallmap.rs` `row_images_keep_sharing_order_and_meter_charges` (131–142) — `object()`, `shares_image`, `heap_bytes()==202`, and `total_cmp` all existed on BTreeMap-backed `ObjectFields` at BASELINE with the same formula. It does not fail if production maps are still B-trees. It should hash/serialize a row built from unsorted/duplicate JSON and compare to a **BASELINE-captured** digest, or differential-assert `SmallMap` vs `BTreeMap` on `String` keys.
- `tests/ordered_identity.rs` (22–56) vs `ordered_identity.json` — locks IMPL against a file introduced in this commit. If that file was emitted by IMPL, a silent serialization change vs BASELINE still passes. It should be produced only by a BTreeMap build of `70a663c22` (as the comment claims) and that capture command/binary hash should be in-tree, or the test should fail closed when it cannot prove that.

`seeded_operations_match_btree` / `equal_keys_preserve_the_btree_representative` / `serde_sorts_and_last_duplicate_wins` would **not** pass with a wrong `SmallMap`; they just do not cover production key types or `and_modify`.

## Findings

### 1. Medium — inner held/left groups are a large mutated SmallMap

**Where.** `snapback4/crates/snapback4-device/src/device/history.rs` 10, 28–46; insert engine `smallmap.rs` 61–72.

**Scenario.** Viewer holds 4 096 `DeliveredHistory` groups (4 096 conversations). A snapshot or stream delivers 4 096 `put`/`scope` events whose encoded group keys are not already sorted. Each `groups.entry(table).or_default().insert(key, Held|Left)` memmoves a growing suffix. Lane measurement: shuffled construction 5.23 ms vs 0.48 ms at n=4 096 (`crossover-final.txt` 19–20). Result image still round-trips as sorted JSON; apply CPU is quadratic and **unmetered**. Journal called g8 “small outer held/joined table maps”; `HeldGroups` is table-keyed and small (`wire.rs` 13), but this type alias converted the **inner** group map too. `snapshot.rs` 37 correctly uses `BTreeSet` for the incoming held set, then writes into the SmallMap (`snapshot.rs` 40–44).

**Smallest fix.** `pub(super) type Groups = SmallMap<String, BTreeMap<String, Membership>>` (or keep the whole `Groups` type a B-tree). Outer table map can stay a vector.

### 2. Low — identity pin cannot be independently shown to predate the change

**Where.** `snapback4/crates/snapback4-core/tests/ordered_identity.rs` 1–2, 22–56; `tests/ordered_identity.json` (new at IMPL).

**Scenario.** IMPL reserializes corpus Schema/Program/args/rows and Chat/Interview backends; hashes must equal the JSON file. If that file was written by IMPL, a key-order or skip_serializing_if delta vs BASELINE is green. The comment names `70a663c22`; this tree does not contain that capture binary or a hash of it.

**Smallest fix.** Check in the capture command plus the baseline executable’s digest (or regenerate the JSON in CI from a recorded BTreeMap artifact). Fail if `D2_IDENTITY_CAPTURE` is required and missing.

## Questions (not findings)

- Chromium acquisition, cold-open, and fresh-realm offline reopen were not run (plan 447–459; previous diet reverted on an acquisition regression). Native N=1 apply got faster; that does not replace the witness.
- `and_modify` on `SmallMap` is untested against BTreeMap.
- Presence `SmallMap<String, Option<i64>>` (`presence.rs` 6–16) under a mutation that `connected[]`-checks many principals: heap-capped, but shifts are unmetered. I did not construct a ceiling-legal input that is clearly worse than Groups.
- Action args remain `BTreeMap<String, Value>` (`actions.rs` 35) — leftover monomorphization, not a semantic miss.

Verdict: READY WITH CHANGES
