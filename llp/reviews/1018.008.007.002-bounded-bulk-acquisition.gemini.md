## 1. Technical Assessment & Feasibility of the 2–3s Target

The plan correctly identifies that serial lifecycle churn (613 local IndexedDB transactions across 201 page deliveries, 201 acknowledgement admissions, and 201 settlements, alongside 201 sequential HTTP turns) is untenable. However, **the plan as structured cannot achieve the 2–3 second target.**

### The Execution Budget Arithmetic
* **Baseline reality:** The prior 32.554s result was measured in development React with StrictMode. The first single production control ran at **30.689s** (an informal data point, not yet a qualified 10-pair median). Moving from development to production React shaved only ~1.86s, not the ~4.7s that raw React self-time (3.006s) and template render time (1.702s) might have suggested.
* **I/O and transport savings:**
  * Grouping 201 query pages into ~13 batches of 16 pages reduces HTTP round-trips from 201 to 13.
  * Grouping 201 acknowledgement replays reduces HTTP round-trips from 201 to 13.
  * Carrier transactions drop from 613 to ~40.
  * At ~10ms per IndexedDB transaction and ~5ms per local loopback round-trip, carrier and network coalescing saves approximately **7.0–8.5 seconds**.
* **The remaining CPU wall:**
  * Subtracting ~8.0s of I/O wait from 30.689s leaves **~22–23 seconds of single-threaded JavaScript CPU execution**.
  * From the frozen client profile:
    * Posting-tree AVL insertion + `HeldIndex.putPrepared`: **6.134s**
    * `imageCanonical`: **2.344s**
    * `compactSuccesses` (scanning committed history): **1.928s**
    * JSON detachment: **1.660s**
    * GC self-time: **2.721s**
    * Redundant `prepareClosureReceipt` + `decodeDeliveryEnvelope`: **1.529s**
* **Feasibility Conclusion:** Bounded transport batching (§3, §5) and single-commit chunks (§4) are necessary hygiene, but they leave the engine at roughly 22 seconds. Treating the ~20 seconds of pure renderer CPU work as an open-ended post-hoc diagnostic in §6 is fatal to the timeline. Indexing and normalization improvements must be specified architectural commitments, not an unbudgeted Phase 4 research item.

## 3. Material Concerns and Concrete Remedies

### Concern 1: Unresolved Nonempty Receipt Effects in Batched Settlement
* **Location:** §5, Paragraphs 5–6 (Lines 106–117).
* **Issue:** The audit reveals **112 nonempty receipt effect responses** in the 10,008 fixture. Under LLP 1019 §6 and LLP 1012 §7, the empty-effects no-tail proof is strictly forbidden for nonempty effects. The plan states: *"The chosen application tail may not contain receipt rows; their absence is not evidence that effects were empty or observed."* If the acquired tail omits receipt rows, the store cannot verify receipt effect observation. Consequently, those 112 entries remain permanently unresolved in observation custody. This will cause `compactSuccesses` (already consuming 1.928s) to re-scan every answer on every subsequent commit, degrading throughput and causing memory bloat.
* **Concrete Remedy:** Amend §5 to specify exact resolution semantics for nonempty receipt effects:
  1. The owner batch replay response must return either an application tail certified to cover the batch's receipt effects or an explicit certified receipt-observation marker.
  2. Forbid settling batched nonempty terminals under a tail that cannot prove effect observation. If coverage cannot be verified in the batch tail, those terminals must retain standard observation custody without stalling the outbox queue.

### Concern 2: The "Private Acquisition Checkpoint" Threatens the 976-Byte Budget and Dual-Watermark Semantics
* **Location:** §4, Paragraphs 4–5 (Lines 75–88).
* **Issue:** Introducing a new persisted metadata entity ("private acquisition checkpoint") distinct from the official watermark introduces new store records, serialization logic, and cold-reopen synchronization. With only **976 bytes of gzip headroom**, adding a secondary checkpoint system alongside existing watermark machinery risks an immediate budget breach. Furthermore, dual-watermark semantics create ambiguity regarding whether unexhausted checkpointed ranges participate in overlay retirement or outbox fencing.
* **Concrete Remedy:** Strike the private checkpoint entity. As noted in the client audit, reuse the **persisted delivery page chain itself**:
  1. Rely on the last durably committed delivery envelope's `next` cursor and arguments as the natural resume token.
  2. Maintain the invariant that the official watermark advances **only** upon complete acquisition exhaustion (`caughtUp`). A cold reopen reads the highest contiguous held cursor chain. This requires zero new storage schemas or wire DTOs.

### Concern 3: Lack of Architectural Commitment on the 20-Second CPU Bottleneck
* **Location:** §6 (Lines 120–133) and §8, Step 4.
* **Issue:** Section 6 delegates indexing and preparation optimizations to an open-ended diagnostic phase ("profile again... after chunk delivery/admission/settlement works"). Because single-threaded JavaScript execution accounts for ~22 seconds of the 30.689s baseline, transport batching alone will plateau near ~22s. Waiting until Step 4 to design index and normalization changes guarantees an architectural rewrite late in the cycle.
* **Concrete Remedy:** Promote two concrete CPU mitigations from "investigations" to explicit Phase 3 implementation requirements:
  1. **Private Immutable Prepared Delivery Object:** Eliminate duplicate envelope decoding and JSON normalization (saving ~1.53s across `prepareClosureReceipt` and `decodeDeliveryEnvelope`). Wire DTOs must be validated and frozen once upon intake.
  2. **Bulk Posting-Tree Insertion:** Rather than performing per-posting AVL tree balancing (2.871s) for every row in a chunk, buffer keys across the 16-page chunk and perform a single-pass sorted tree merge prior to carrier publication.

### Concern 4: Bundle Size Breach via Parallel Single/Batch Implementations
* **Location:** §1 (Lines 37–41), §3 (Lines 43–47), and §5 (Lines 94–101).
* **Issue:** The runtime has only **976 gzip bytes** of headroom. Implementing dedicated batch endpoints, batch decode loops, and batch outbox replay alongside existing single-page and single-mutation pathways will exceed the 90,000-byte hard limit.
* **Concrete Remedy:** Enforce a strict **"zero-net-branch"** design:
  1. The client drainer must not have separate `drainSingle` and `drainBatch` methods; `createOfflineDrain` must parameterize page consumption over an array of 1 to $N$ frames.
  2. `commitMany` already natively accepts an array of deliveries; no new carrier commit pathway is permitted.
  3. The outbox replay loop must operate on a slice of $1..N$ eligible intents. When $N=1$, it executes existing semantics; when $N>1$, it transmits the contiguous prefix.
  4. Explicitly fund the remaining bytes by deleting redundant wire normalizations and obsolete single-item wrappers.

## 4. Opportunities to Simplify and Delete

1. **Delete Private Checkpoint Entity (§4):** Completely eliminate the proposed private checkpoint table. Rely on the existing persisted log page frontier to determine resume position on restart.
2. **Delete Multi-Pass Envelope Decoding (§6):** Stop decoding envelopes in `accept()`, re-decoding in `expandRows()`, and re-normalizing in `prepareClosureReceipt()`. Parse and freeze the envelope into an immutable internal structure once.
3. **Avoid Streaming Abstractions (§2, §3):** Confirm the plan’s rejection of SSE and chunked-transfer streaming. Bounded HTTP JSON arrays reuse existing route parsers, connection pooling, and error boundaries without adding streaming worker dependencies.
4. **Unify Replay Reconciliation (§5):** Do not create distinct batch-terminal settlement logic. Feed the returned terminal array directly into `commitMany({ put: terminals })`, preserving existing identity checks and grant releases.

---

## 5. Experiment Design & Baseline Integrity

* **Baseline Qualification:** A single run of 30.689s does not establish a baseline. §8 Step 1 must explicitly require a **qualified 10-pair alternating median** in production React before any candidate code is tested.
* **Fixture Cohort Separation:** §7 correctly notes that the standard fixture contains 4,450 pre-received receipts. Testing against a fully unreceived fixture is essential, but results from the mixed fixture and the zero-receipt fixture must never be combined into a single statistical cohort.
* **Failure Injections:** The 6 failure controls in §7 are comprehensive. Prioritize verifying failure injection between carrier chunk persistence and acknowledgement admission to ensure queued intent IDs are never orphaned or double-allocated.

## 6. Final Verdict

**Verdict: REVISE.**

The plan is well-grounded in LLP 1012/1019 invariants and correctly identifies transport batching seams. However, it cannot be approved as **READY** until:
1. §5 defines precise reconciliation for the **112 nonempty receipt effects** to prevent permanent observation debt and `compactSuccesses` degradation.
2. §4 deletes the "private acquisition checkpoint" in favor of natural page-chain resumption to protect the **976-byte headroom**.
3. §6 commits to concrete **bulk index insertion** and **single-pass normalization** architectures rather than treating the decisive 20-second CPU bottleneck as a speculative post-hoc task.

## 2. Invariant and Contract Verification

The revised plan establishes solid invariants across all previously contentious seams:

* **Transport Batch vs. Commit Group Atomicity (§3, §4):** The plan explicitly decouples the wire batch (≤16 pages, 1 MiB budget) from the carrier commit group. By requiring full structural preflight before executing any commit group, and guaranteeing independent atomicity for each subgroup, partial failure semantics are preserved: prior committed groups remain durable, while invalid trailing frames reject only the pending group. Crucially, single legal pages exceeding journal capacity fall back to the cold snapshot path without wedging progress.
* **Bounded Replay and Terminal Overshoot (§5):** Replay requests are bounded by the 1 MiB body guard, and owner replay respects both the 20 ms work target and the 1 MiB serialized response limit. The bounded overshoot rule—requiring an executed terminal that breaches the response budget to be returned and halted rather than omitted—eliminates state divergence between owner SQLite transactions and client ledger state.
* **Natural Page-Chain Resumption (§4):** Deleting the private checkpoint metadata table preserves the 976-byte gzip headroom and prevents dual-watermark drift. Resuming from the durable page chain with strict root-to-next validation (exact argument, authority, and contiguous-cursor matching) safely reuses existing idempotent delivery mechanics.
* **Shared-Namespace Integrity in Lazy Indexing (§6, [`cpu-design.md`](file:///Users/ccheever/.gemini/antigravity-cli/scratch/runs/20260911-bulk-acquisition/cpu-design.md)):** Scoping lazy index construction strictly to [`FactIndex`](file:///Users/ccheever/.gemini/antigravity-cli/scratch/src/store/fact-index.ts) avoids degrading public search readiness. Populating both the `live` and `positives` namespaces (`l`/`p` posting prefixes) during on-demand materialization ensures that partial views never corrupt index seeks.
* **Strict Runtime and Qualification Gates (§1, §7):** The 90,000 gzip-byte ceiling and 1,500-line limit are hard gates funded by named deletions (wire decode/normalize consolidation, redundant wrapper removal). Qualification requires 20 uncensored alternating production samples, exact 10,008-message row hashes, settled receipts, and completion of first-use public queries before timing ends.
