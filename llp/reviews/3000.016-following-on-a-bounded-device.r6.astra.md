**Revision-2 objections**

Use fully synced reposts for the positive prediction cases, so their ordinary uniqueness proof does not independently prevent prediction.

| Objection | Concrete probe and required outcome |
|---|---|
| Grok scenario A | Posts horizon 2: P1 at 1, P2 at 2, repost of P2 at 3. Repost P1 offline. Its original event must accompany held P1, so the lookup succeeds and prediction remains eligible. Repost events cannot consume its acquisition slot. |
| Grok scenario B | Acquire a reply excluded by the originals filter. Reposting it must produce local `FEED_POST_NOT_FOUND`: the source is held and its event is genuinely absent. |
| Grok removal case | Acquire P, remove it, and synchronize the removal while retaining its source row. Reposting P must refuse locally, including after purge removes the tombstone. The absent original event remains decidable through held P. |
| Astra revision-2 finding 2 | Posts horizon 1: P at 10, repost event at 20. P’s original event must remain acquired alongside the repost event. Classify the original-event dependency from posts’ residency. Repeat with horizoned reposts: their independent `insert … if absent` proof may still queue. |

The committed-state existence invariants match [the transitions](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/timeline.rs:77>): filter fields are immutable except one-way removal; removing an original deletes its event while preserving independent repost events; deleting a repost deletes its corresponding event. Repost event IDs are minted, however, so acquisition must transfer the existing event rather than reconstruct its identity.

The three lookups have the necessary source witness: removal has the old post, repost insertion reads the original post, and unrepost has the old repost. For unrepost, that witness is the **pre-delete image**. Source-based decidability is new implementation work: ordinary `get_inner` does not infer it.

Four findings remain:

1. **High — §2.1a, “Nothing else on a device reads owned events.”**

   Ordinary application queries can read these tables. An [existing device test](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-device/tests/timeline/round2.rs:57>) compiles both `feedPosts['original'] by byId` and `feedPosts first 100 by byId`.

   **Scenario:** P and its event exist on the server but are excluded from device acquisition. An ordinary query reads P’s event directly. Filtering acquisition while retaining the existing horizonless table semantics produces a known null—or a complete shortened range—because [ordinary read coverage](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/read.rs:325>) recognizes table-level horizons and online-only residency, not this new containment relationship.

   **Smallest fix:** limit the special known-absence proof to source-backed transition reads. Explicitly classify all other event reads, including rule probes, conservatively as unknown/server whenever their required coverage is not established. Update ordinary `check` classification accordingly. Narrow the “nothing else” sentence to the generated Following page.

2. **Medium — §§2.3 and 5: implicit dependencies must distinguish insertion from deletion.**

   [`Timeline::inputs`](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/schema/timeline.rs:81>) ignores operation kind and adds an original-post read for every repost-table write.

   **Scenario:** originals are `online only`; reposts are fully synced. The device holds repost R and its event. Unrepost needs those two rows, but the existing dependency list still classifies its unnecessary original-post input as Server. That makes prediction `never`, contradicting §5’s new held-unrepost requirement.

   **Smallest fix:** specify dependencies by transition: repost insertion needs the original post and original event; repost deletion needs the old repost and repost event, without an original-post read. Also qualify §5’s “under every source residency” assertion by §2.3’s online-only and uniqueness-proof exceptions.

3. **Medium — §2.1, follows row: `public` plus `sync to .<follower>` is not admitted Quarry.**

   **Scenario:** retain the public follows rule and replace `sync public` with `sync to .followerId`. Even after relaxing timeline admission, [`bind_sync`](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-lang/src/bind/schema.rs:275>) compares that audience with the inferred Public audience and emits `E_SYNC`.

   **Smallest fix:** remove this example and promise the supported public-table choices: public sync, a public horizon, or online only. Supporting public tables with narrower delivery requires an explicit additional language change.

4. **Low — §2.1a, time-based acquisition: boundary overfetch is not necessarily “a few” events.**

   **Scenario:** 50,000 originals share timestamp T; posts acquire the newest 1,000 by `(at, id)`. Acquiring all original events with `at >= T` acquires all 50,000.

   **Smallest fix:** replace “a few more” with an explicit warning that timestamp ties can cause unbounded overfetch. If acquisition proportional to held sources is required, use per-source acquisition for boundary ties.

Both acquisition options otherwise satisfy **containment**: an existing event has its source’s immutable timestamp, and per-source acquisition transfers it directly. The recorded boundary must belong to the actual source acquisition. Existing [snapshot staging and catch-up](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-device/src/device.rs:728>) support publication of consistent source/event state.

Useful probes are an insertion and removal between source and event snapshot pages, interrupted acquisition followed by restart, and an empty or undersized `whole` source acquisition followed by a backdated insertion. `whole` accepts that insertion; its event must accompany it. The stated live-sync containment requirement already demands this.

The follows relaxation is otherwise sound for the generated view. Its [lowered read](</Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-lang/src/bind/timeline.rs:143>) uses owned edges and tombstones, while server delivery reads application follows. Supported residency changes introduce no new disclosure and do not change delivery. Application-authored queries or rules that read follows still inherit its changed residency.

Exercise each source independently through full sync → horizon → online only → full sync, interrupting acquisition.
