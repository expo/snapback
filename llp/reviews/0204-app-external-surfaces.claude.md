# Review — LLP 0204 "App external surfaces" (v0.2, revision 26c16b2eb, sha256 b3d39fad27a8aba8f9deb61a3b39647725cefc4ca39fa2d441755e81ca50aac6)

## Overall assessment

This is a strong synthesis at the right altitude. The keystone decisions are sound and well grounded: function-granularity exposure (P2) correctly applies the Hasura lesson and genuinely forecloses the forgot-RLS class because exposure adds no second authorization layer; "one authority, many projections" is a faithful application of LLP 0194's registry rule; and building authority acquisition as LLP 0150-verbatim with a generated OAuth 2.1 facade is the best available resolution of the ceremony-vs-interop tension. The grounding pass mostly checks out — the LLP 0062 citations (envelope routes, `code-mode.d.ts`, the surface-restriction OQ at 0062:1156/1829, the redact-`/inspect`-and-envelope-together warning), LLP 0093's "version carrier is its own proposal" (0093:292–294), LLP 0004's deferral (0004:463), LLP 0024's catalog and `snapback_fn_<functionId>` naming, LLP 0149 F3/F8/F9, LLP 0150's invariants and custody rules, LLP 0071's network-prefix admission substrate, and the LLP 0201 M6 grader language (benchmarks/briefs/social-messenger.md:563–592) are all accurately used. However, three defects rise to material: the headline hosted sequencing claim misstates LLP 0055's plane boundary (delegated reads *are* service-principal invocations and are refused on hosted); the trust argument for server-side code mode rests on an owner-code qualification while never engaging LLP 0009, which explicitly names comprehensive preemption a prerequisite for untrusted code; and the "automatic surface" pitch is unreachable under the default-closed `auth.agents.mode` knob the RFC itself reuses.

## Material concerns

**M1 — D2 "Reads first on hosted" misstates LLP 0055's plane boundary and contradicts itself within one bullet.** The bullet presents "user-delegated reads are v1" on hosted, and attaches the gate ("hosted service-principal invocation stays refused until LLP 0039's deployment-security contract and the durable audit log (LLP 0019 F8) land") only to *external mutations*. But in LLP 0055, delegated authority **is** `servicePrincipal` authority (§Resolved authority: `effectiveUserId?` present iff delegated), and the plane boundary refuses **every** hosted service-principal invocation — "query, live query, mutation, action, connection open, over HTTP, CLI, or MCP" (0055 §Plane boundary, "Hosted: refused wholesale"); the deployment-security contract gates *all* hosted invocation, with the audit log an *additional* gate for mutations only (0055 §Summary). LLP 0150 (v0.2 revision record) likewise has hosted targets "inherit 0055's wholesale refusal." As written, the same sentence asserts hosted delegated reads are v1 *and* that hosted service-principal invocation stays refused until gates land — and a reader implementing S1/S2 could ship hosted delegated reads believing them ungated. This is material because it is the RFC's central sequencing claim for surface 1 and it mischaracterizes a settled security invariant of its most load-bearing source. **Disposition:** restate the hosted ladder precisely — anonymous and declared lanes are the only gate-free hosted lanes; *granted* calls of any kind (delegated reads included) await the LLP 0039 deployment-security contract; mutations additionally await LLP 0019 F8 — or, if the intent is to un-refuse hosted delegated reads earlier, say so as a named dated LLP 0055 amendment with its own security argument rather than by implication.

**M2 — D6's trust argument for server-side third-party code execution is unsound as stated, and the RFC never engages LLP 0009.** D6 promotes code mode to a server-side primitive on every surface (`POST /api/v1/run`, MCP `run_code`, the `ask` inner loop), executing *stranger-authored* programs "in the restricted no-eval handler VM (the same VM class every JS handler already qualifies under — `snapback runtime-qualify`)." That qualification qualifies the VM for **owner-authored** app code; it says nothing about adversary-authored code, which is a different threat class. The corpus's governing code-execution-security document, LLP 0009 — absent from this RFC's Related list — states plainly that "comprehensive preemption remains a prerequisite for hosting untrusted code" and that ordinary Query and top-level Mutation preemption "remains honestly Missing" on the canonical engine, whose posture is "intentionally trusted-local"; LLP 0047 (which D6 cites for budgets) is Draft and is itself framed as the bar a target must meet "before it claims hosted or untrusted code execution." D2 grants local/trusted-local targets "the full surface immediately," and S4 ships `/api/v1/run` without distinguishing the untrusted-code posture per target or stating which invocation class submitted programs run in (action-class outer VMs have armed interruptible-eval deadlines per 0009; other classes do not). The authorization argument ("changes round trips, never reach") is correct but answers the wrong question — the new risk is engine escape and resource exhaustion by an adversarial author, not authority widening. **Disposition:** add LLP 0009 to Related; state the invocation class and engine regime code-mode programs execute under; make third-party code-mode availability per target explicitly conditional on 0009's untrusted-code prerequisites and 0047's enforced profile, distinct from owner-code runtime qualification.

**M3 — The "automatically, with every app" pitch is unreachable under the default-closed registration knob the RFC reuses.** D7 defines an integration as "an agent principal with a public face" whose registration policy knob is LLP 0055's `auth.agents.mode` — whose default is `"disabled"` (0055 §Registration), under which creation routes refuse. D8 makes the facade's DCR endpoint "subject to `auth.agents.mode`," and on `prod` 0055 additionally refuses operator-minted invitations (user-minted is the only production creation path). Consequently, an app that follows D1's example block and D10's recipe ("~ten `expose: true` lines and one budget block") gets **no** connectable MCP server, no mintable third-party token, and no CLI login — every credentialed lane dead-ends at principal creation — contradicting the Summary's "every Snapback app should come with four external surfaces, automatically" and D10's "remote MCP server any 2026 agent client can connect to with consent." This is a coherence defect in the keystone declaration, not a detail gap: the `api` block as specified is not sufficient to enable the product being pitched. **Disposition:** specify the interaction — e.g., `api.enabled` requires an explicit `auth.agents.mode` declaration (a manifest diagnostic when absent), or a stated, deliberate default for api-enabled apps — and correct D1's example and D10's recipe to include it, with the prod-path constraint (open or user-invited) named.

## Minor / implementation-phase notes

**m1 — D9.5's audit-gate sentence has it both ways.** "A candidate on-ramp for hosted external mutations ahead of the full audit-log gate — narrowing it, not replacing it: … the LLP 0019 F8 requirement stands." If F8 stands, there is no on-ramp ahead of it. Say what "narrowing" means concretely (e.g., approval-gated effects reduce the *scope* the audit log must cover at first landing) or drop the on-ramp claim.

**m2 — D1's "callability, disclosure, and documentation as one fact" is contradicted two bullets later by `disclosure: "full"`,** under which unexposed (externally uncallable) functions remain disclosed. The knob is fine; the "one fact" claim should be scoped to `exposed-only`.

**m3 — D9.3 watch authority needs grounding in LLP 0070's modes and an honest collision with LLP 0055's grant lifetime.** "Journaled under the owner's grant; revoking the grant kills the watch" presumes a grant that human owners don't have (their authority is session-shaped); LLP 0070's `revalidatePrincipal`/`capturedGrant` modes are the right substrate and should be cited. Where the anchor *is* a delegated grant, 0055's hard 90-day maximum with renewal-is-fresh-consent means integration-created watches die quarterly — materially shaping the "IFTTT for free" pitch; deserves an OQ alongside OQ10.

**m4 — D9.4 stretches LLP 0150's acknowledged-bearer category.** 0150's acknowledged exceptions are *ceremony* capabilities ("see and decide one request"); a capability link is bearer *invocation* authority. Per 0150's own discipline ("names the delta in §Named amendments rather than absorbing it silently"), this should be a named dated 0150 amendment, not an analogy.

**m5 — D10's "any 2026 agent client" claim silently depends on either DPoP adoption or the plain-bearer opt-in.** With sender-constrained tokens the default and bearer a per-app opt-in, the mainstream bearer-only MCP client population needs the opt-in; qualify the claim or state the intended disposition for bearer-only clients.

**m6 — The facade's route placement needs a dated LLP 0031 amendment**, particularly `/.well-known/oauth-authorization-server` (structurally required at origin root by the metadata RFCs) against the taxonomy's "no system route hides at the root" invariant; the `/auth/*` root family is the precedent to extend.

**m7 — Caller-key billing (D5) introduces a new secret class** — a caller-supplied model credential transiting and being used by the host — that LLP 0036's app-owned handles don't cover; name its custody posture (never persisted, never logged, request-scoped).

**m8 — Declared-tier ledger auto-creation is an anonymous storage-abuse channel** (mint unbounded ids → unbounded rows); the sybil paragraph bounds budget multiplication but not row creation. Bound ledger creation per network-evidence bucket (OQ8-adjacent).

**m9 — Motivation wording**: "scoped… tokens are designed and shipped on local targets (LLP 0055), with a consent ceremony that is materially better…" can be read as claiming the 0150 ceremony shipped; the capability index says `auth.agent-registration` is design-only with no user-reachable surface, which S0 itself acknowledges. Tighten to match S0.

**m10 — D5 v1 read-only vs D9.1 durable transcript settling**: settling a transcript "into app data" is a durable write; state where transcripts persist (reserved tables, like integration records) and under what authority, so read-only-`ask` remains an honest claim on gated targets.

**m11 — Exposure enforcement point**: D1's "not callable with an integration credential" invariant implies the bare finite routes (`/query/{name}` etc.) must refuse integration credentials for unexposed functions, not just the `/api/v1` family; worth one sentence so the invariant survives implementation.

**m12 — Standards nit (D8)**: OAuth 2.1 consolidates PKCE-required authorization-code (and drops implicit/password); the device-authorization grant remains RFC 8628, referenced but not consolidated. The sentence lists 8628 separately anyway; fix the parenthetical.
