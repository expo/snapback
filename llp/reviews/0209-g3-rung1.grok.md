3. Client did not negotiate `snapback.graph-live-delta.v1` → replace only.

8. After one delivered delta, `delta_requires_replace` forces the next wake to replace (stale captures).

If 1–5 are opened for a real graph subscriber, a wrong eligible delta is delivered with **no** shadow oracle.

## New findings (adversarial hunt on the new shape)

### (a) Eligibility unsoundness — **REFUTED-RISK**

On `issueSummary` the lane only emits `update` when physical root keys **and order** are identical (`graph_evaluator.rs:3683-3687`, `:3411-3416`). That catches:

- in-window reorder / boundary displacement (`issue-summary-order-key-move`, matched `n0`, replace);
- membership add/remove (same key-vector check; list membership-add remains replace);
- equality-to-one re-point (`descendant_join_may_have_changed` on `assigneeID` / `creatorID` / `projectID`, `:3689-3690`; frozen `issue-summary-assignee-repoint`);
- child identity replacement (`old_keys != new_keys` on the to-one, `:3753-3756`).

Assignee **rename** vs **re-point** is distinguished: rename matches user nodes `n1`/`n2` and patches `login` under the same physical user key (`delta-dispositions.v1.json:285-337`); re-point matches root `n0` because `assigneeID` is a join field and replaces. Position-unchanged at interval ends is untested on this corpus (the normal window is complete: 517 < take 1024, `graph_corpus_v1.rs:2107-2115`), but a prefix that actually moves a physical key cannot pass `old_keys == new_keys`. A row updated twice in one commit is folded as prior-state vs current-state (`graph_delta_ops` `:3556-3567`), not per-change. I did not find an eligible commit whose correct result differs from patch application.

### (b) Retained-state staleness — **REFUTED-RISK**

After a nonempty delta the serving owner stores the incremental `evaluation` and sets `delta_requires_replace = true` (`engine.rs:32466-32480`). The next matcher decision is `ConservativeFallback` (`:31560-31563`), so the following turn cannot skip on stale captures and cannot delta again. Replace then installs a fresh `GraphServingRegistration` with `delta_requires_replace: false` (`:41186-41199`, `:32067`). Resume/refresh is `force_replace: true` (`:29335-29342`). Empty-ops `NoChange` does not persist the tentative ledger (`:32367-32368`) — that under-counts work, it does not apply a delta against a client state the subscriber never received.

### (c) Coalescer — **REFUTED-RISK**

Data-lane coalescing concatenates `ChangedRow`s and evaluates once against the last delivered retained state (`engine.rs:29356-29359`, `:29785-29798`, `force_replace: false` on first Data enqueue `:29398`). That is cumulative latest-value, not a delta against a skipped intermediate. Join-field or membership changes in the merged bag fail closed to replace. After one delivered delta, `delta_requires_replace` is set on every nonempty publication path (`:32480`); Refresh/PermissionResync already force replace. The two-field case is last-change-per-row inside one mutation (`graph_corpus_v1.rs:1061-1075`), not two commits, and still converges.

## (j) Two Spec gaps — payload shape and replace-after-delta

**Not found** as labeled “Spec gap” text in this tree (no g3-pre-rebase reviews; no `replace-after-delta` / “payload shape” in `llp/0209` or engine comments). They are visible as **implementation choices**:

1. **Payload shape** — additive sibling `LiveEnvelope::LiveDelta.graph: Option<LiveGraphDeltaWireV1>` with **empty** DK-3 `ops` (`live_wire.rs:74-91`; `engine.rs:33657-33664`; asserted `graph_corpus_v1.rs:3574-3575`). Negotiation is fail-closed: `deltaFormat` must be exactly `snapback.graph-live-delta.v1` (`graph_evaluator.rs:44-53`).

2. **Replace-after-delta** — every successful graph delta sets `delta_requires_replace` (`engine.rs:33710-33713`) because “the attested capture belongs to the predecessor snapshot” (`:33710-33712`). Next wake is conservative-fallback replace (`:32769-32772`). The accumulation test *depends* on this: snapshot pages 1 → delta 2 → **forced** replace 3 (`graph_corpus_v1.rs:7010-7030`).

**Are they sound v0.10 note candidates?** **Yes**, if written as conservative, review-forced narrowings (same genre as G3-A’s four notes at `llp/0209-live-graph-profile.spec.md:3348-3360`):

- Sibling `graph` + empty `ops` keeps the DK-3 row-op contract byte-stable for non-opt-in subscribers; graph IVM is demand-negotiated, not a new `kind`.
- Pin-to-replace after one delta is weaker than consecutive IVM, but it is the only rule that keeps matcher captures honest without recapture. Consecutive deltas are a later widening, not v0.

Caveat to put in the note: empty `ops` + version advance is a **trap** for a DK-3-only client that somehow opted in; the demand default must stay fail-closed.

## 2. Memoization × delta

Delta sub-reads never consult the full-evaluation memo. The only `get_if`/`insert` is `invoke_live_subscription_query` (`engine.rs:8736`). `try_graph_delta_fanout` calls `evaluate_graph_delta_on` (and, if enabled, `evaluate_graph_query_on`) inside a pinned read (`:33536`). Matcher wake retires memo holders **before** lane selection (`:32813`). The two-sub test’s `evaluations_executed += 0` across two deltas holds.

**Compatibility precondition.** `get_if` compares the cached eval’s **input** ledgers to the receiver’s **output** ledgers. Window ledgers are cumulative counters, not cursors (`GraphWindowLedgerV1` at `graph_evaluator.rs:101`). Equal counters at the same §6 tuple ⇒ same remaining budget and same first-page result. Empty==empty is first-page only (a successful eval always emits one ledger per demand-cost node). Vec `PartialEq`, not a hash. Explicit continuations still miss via `graph_demand_is_root_first_page` on subscribe `input`.

**Oracle cannot be handed a memoized result.** Enabled oracle is a direct `evaluate_graph_query_on` in the same pin (`engine.rs:33557`). Debug memo oracle uses `invoke_query_with_dependencies_prepared_generation`, not `get_if` (`:8766`).

**Two-sub test, five claims — all hold** (`graph_corpus_v1.rs:7055`):

1. Two independent `live_delta` frames, pages 1→2, 2 deliveries / 2 oracle checks / 0 failures.
2. Delta + oracle do not increment `evaluations_executed`.
3. Shared replace: 1 exec, 1 miss, 1 hit; both pages→3.
4. Isolated refresh of holder 0 does not advance holder 1; mismatched prior is a miss.
5. Sibling hits once its ledger equals the cached prior (0 exec, pages→4).

Replace/fresh sharing is preserved, not destroyed: `graph_scheduler_case_same_key_memoizes_one_turn_and_delivers_three` still 1 eval / N−1 hits (now with a pages≥1 prior, which is the port’s point).

## Findings

### MINOR — eligibility is matched-node conjunction, not all-node (spec §7)

`rung1_delta_shape_is_eligible` (`graph_evaluator.rs:3140`) and the scheduler kind filter (`engine.rs:32884`) only constrain **Match** nodes, plus “no arrays in the projection.” LLP 0209 §7 says one ineligible **plan** node pins the graph.

Not reachable on this corpus: `issueSummary` is root + three to-ones + scalar projection; array-bearing graphs fail `projection_contains_array` even when only n0/n1 match. A later scalar graph with `Exists` / semi-join would need the all-node pin.

**Fix:** refuse delta if any plan node is `BoundedToMany | ExistsSemiJoin | PrincipalBound | SearchMembership`, or if the projection contains `Array` or `Exists`.

### MINOR — mismatch→replace is dead without the env (e)

```33517:33520:crates/snapback-engine/src/local/engine.rs
        let convergence_enabled = self.graph_delta_convergence_all
            || std::env::var("SNAPBACK_GRAPH_DELTA_CONVERGENCE")
                .ok()
                .is_some_and(|value| matches!(value.as_str(), "1" | "true"));
```

`graph_delta_convergence_all` defaults false (`:28305`). With the oracle off, `fresh` is `None` and `is_none_or` makes `convergence_matched == true`. `return Ok(None)` on mismatch is unreachable in production and in ordinary debug builds. This is **not** DK-3’s `cfg(debug_assertions)` assertion. Corpus tests force it on via `require_graph_delta_convergence_for_test`. `force_graph_delta_convergence_failure_for_test` is never called with `true`.

**What actually guards a wrong delta in production:** conservative identity checks (stable physical keys, join-field pin, label pin, in-window Update-only); opt-in `deltaFormat`; auth-scoped exclusion; cut/auth-version mismatch; **one** nonempty delta then mandatory replace (stale captures never used for a second skip); `SNAPBACK_GRAPH_DELTA_DISABLED`. Not a runtime apply-vs-fresh check.

**Fix:** `#[cfg(debug_assertions)]` run the apply-vs-fresh compare (keep the env as a release qualification opt-in).

### MINOR — G2-C memo-era `groupStateBytes` rewritten

`tests/conformance/graph/served-observations.g2-c.v1.json` original-graph **observations** are byte-identical. `normalServingGroupMeasurements.groupStateBytes` were copied up to the G3-A charging scale. v0.10 said those bytes live only in the G3-A file. `measure_widened_served_graph_groups` (`graph_corpus_v1.rs:2736`) writes both artifacts.

**Fix:** keep G2-C group-state frozen; put additive `issueSummary` + delta-field byte growth only in the G3-A (or a G3-B) file. Amend v0.10 item (1) for compatible-prior reuse.

### MINOR — comment drift on the memo key path

`execute_query_invocation` still says continuations never seed (`engine.rs:42428`); `live_subscription_rerun_input`’s `@ref` implies ledgers participate in identity (`:40880`). The key ignores rerun demand and uses subscribe `input`. Resume resnapshot bypasses `invoke_live_subscription_query` (`:23853`) and can stamp `memo_eligible_first_page` from injected non-empty ledgers — safety-preserving, sharing-reducing.

## Required answers

**(e)** Force-replace-on-mismatch is dead without `SNAPBACK_GRAPH_DELTA_CONVERGENCE` or the test helper. Production guard is eligibility + one-shot replace-after-delta, not an oracle.

**(j)** Both implementation choices are sound v0.10 note candidates.

- **Payload:** additive `LiveEnvelope::LiveDelta.graph` with empty DK-3 `ops` (`live_wire.rs:74`, `engine.rs:33662`). Negotiation is fail-closed (`deltaFormat == "snapback.graph-live-delta.v1"` only). Fixtures keep `graph: None`. LLP 0093 optional-field compatibility. Digest is SHA-256 of post-apply **result bytes**, not the whole frame.
- **Replace-after-delta:** after a nonempty graph delta, pin ConservativeFallback until a fresh eval rebuilds attested captures. Required because the delta path clones predecessor `captured_reads` (`graph_evaluator.rs:3867`). Consecutive IVM is a later widening, not this rung.
