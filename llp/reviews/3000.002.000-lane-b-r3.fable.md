## Findings

**1. High — `useMutation().run()` and every caller-supplied fresh id are refused while device custody is unlisted.**
`snapback4/packages/snapback4/src/progressive-writes.ts:172`, with `src/write-settlement.ts:21,45` and `src/admission.ts:34`.
The round-3 repair for Astra's item 2 refuses an explicit id whose device custody is unknown unless `freshlyMinted(options)`. That marker is set only when the facade itself mints (`options.id === undefined`). React's `useMutation(op).run(args)` goes through `settleMutation`, which mints its own id and calls `client.mutate(op, args, { ...options, id })`, so the facade sees an explicit id and never marks it.
Scenario: returning visit, custody `present`, journal holds one unsent intent from the last session (the "reload during send" case the RFC §9 requires). `decide` picks online-first; `deviceListed`/`deviceHistoryListed` stay false until the engine attaches (≥1.5 s plus the WASM download, forever on engine failure). The user clicks a button bound to `useMutation` → `settleMutation` mints `id` → `guardClient` → `mintedOptions` does not mark it → wrapper: `deviceKnown(id) === undefined && !freshlyMinted` → `E_ADMISSION "device write custody has not been listed"`. The click is not captured. RFC §5.1 ("no ordinary durable mutation may await WASM") and the §9 required case are violated on the primary authoring surface. Same for `app.mutate(op, args, { id: mintId() })`. No test covers an explicit fresh id during unlisted custody (the Chromium witness only uses explicit ids under `none` custody or after attach; the node tests use no id or a deliberate device-id retry).
Smallest fix: in `settleMutation`, pass `mintedOptions(options, id)` when it mints (or export the marking helper and use it there), and document that a caller-minted explicit id is refused until custody is listed. Alternative without provenance: treat an explicit id as fresh when its embedded mint time is later than this document's open time and `mutationIds` does not know it (a previous-session device id cannot be newer than this open; a same-session device id is always in `mutationIds`).

**2. High — a read that publishes during a journal-inspection window is parked at `loading` and never re-run.**
`src/local.ts:1148` (folds `journalWrites.uncertain` into the post-evaluation fence), `src/local.ts:1925-1926` (`changed(undefined)` only calls `pending.notify()`), `src/progressive-writes.ts:159-164`.
The round-3 repair for Astra's item 3 marks the snapshot invalid synchronously on every journal notification (capture, admission commit, dispatch bind, receipt — five or six per write, plus cross-tab broadcasts) until `inspect()` completes. Any watch whose evaluation finishes inside that window gets `read = { loading: true }, custodyWaiting = true`; with no displayed data it is published as `loading`. When inspection completes, only `pending.notify()` fires; nothing reschedules the watch. Intersecting watches are rescued later by the receipt's `scheduleRead`; a watch disjoint from the write (sidebar `rooms` while `messages` are being written) stays at `loading` until an unrelated `/changes` event touches its tables or the core attaches. Post-attach (document stays journal-owned) the local route hits the same fence at 1148 and the wait is unbounded. Pre-lane, `custodyWaiting` came only from device predictions, whose `settle`/`admit` commits re-run every touched watch.
Smallest fix: in the `changed` callback at `local.ts:1925`, when `op === undefined && !journalWrites.uncertain`, `scheduleRead` every watch whose snapshot is `loading` (or keep a set of custody-parked watches and re-run those).

**3. Medium (author ruling) — `present` custody plus a persistent engine-open failure wedges every table-reading query and all journal dispatch forever, with no typed refusal.**
