## New fundamental and major findings

### N1. Same-incarnation failover cannot see the promotion it has to refuse — FUNDAMENTAL — child A §5.4, parent §3.1

Parent §3.1 says `serve` refuses after a promotion until recovery mints a new incarnation, unless every acknowledged transaction survived and the old primary can accept no more writes. Child A §5.4 implements that as "a change in system identifier or timeline, on reconnect." A process that starts after the promotion has no baseline. It records the timeline it finds and serves the existing `store_id`. That is the ordinary path when the old host dies and `serve` is started on the promoted database. The warm standby's memory of the old timeline dies with that process. The record has to be written into the replicated store and compared on every acquisition, including the first one a process makes.

The guarantee that would justify keeping the incarnation has the same gap. `synchronous_commit = on` waits for a standby only while `synchronous_standby_names` names one; with an empty setting it commits locally. The RFC checks that name, or "the provider's documented quorum," at renewal (child A §5.4, lines 331–338), so a commit between renewals can be acknowledged without being on a standby. A documented quorum is not that wait. The fencing README's provider table is labelled documentation-only and UNVERIFIED (lines 400–412), no failover was run (lines 476–480), and W9 only shows a non-empty `synchronous_standby_names = 'phantom'`. Child A §5.4 then names RDS Multi-AZ and Cloud SQL HA as the configurations where the incarnation survives. Persist the timeline, compare it on every acquisition, and refuse the commit itself unless that transaction's quorum wait is in force.

### N2. Takeover terminates the owner before it knows the lease is still expired — MAJOR — child A §5.2

Steps 3 and 4 kill sessions while `FOR UPDATE` is waiting. Step 6 rechecks the lease and the token only after those kills. Step 5, on `55P03`, goes back to step 2 and kills again; it does not re-poll. A standby that sampled an expiry just as the owner renewed therefore aborts the live owner's fenced commits, then backs off once it finally sees the new `lease_until`. Under synchronous replication that abort is the W9 window: the commit can be durable while the client sees an error (fencing README, lines 334–360).

Step 3 is wider than the run that passed. It terminates every same-role owner tag `pg_blocking_pids()` reports. The prototype's watcher kills a blocker only when the tag generation is `<=` the expired token (`postgres-fencing/src/bin/node.rs`, lines 257–262). The RFC puts that bound on step 4 and calls it hygiene. A losing standby whose `FOR UPDATE` is blocked by the winner's `FOR KEY SHARE` thus kills the winner's commits until it gets the lock and notices the token moved. Two standbys racing were not run (fencing README, lines 481–484). Re-read the lease before any termination, and apply the token bound to blockers. If the only blockers are newer, abandon the attempt.

### N3. The interim worker fence misses the handler that outlived its lease — MAJOR — child A §4.3, child B §2

`expire_run` sets a leased effect back to `queued` and clears `claimed_by` (`effects.rs`, lines 513–517). The handler is still inside `ledger.run`: the completion row is inserted only after the handler returns (`worker-ledger.ts`, lines 54–61; `worker.ts`, lines 195–198). Child A §4.3 and child B §2 refuse promotion and graduation while an effect is `running` or a local completion exists for a non-terminal effect. In that window the effect is `queued` and no completion row exists, so the move is allowed. The target has a queued effect and no result; a worker there invokes the handler again. Same-host exclusion is the ledger's `BEGIN IMMEDIATE`, which the new host does not hold.

The attempt-record design is the right end state. The interim rule is what the RFC says makes standby promotion and graduation safe until that slice lands, and this is the case it was widened to catch. Refuse while any non-terminal effect has no stored completion and its latest attempt is unfinished, including an attempt whose lease has already expired.

### N4. The chunk's jid stamp makes verification defer keys the delta will not revisit — MAJOR — child B §4.3, §6

A chunk stamps every key with the journal's maximum `jid` in that read transaction (child B §4.3, lines 143–146), so an unchanged key copied at snapshot H carries jid H. Range verification defers any target row whose per-key jid is newer than the consistent point (child B §6, lines 263–264). A point J taken while the copier is still reading that range defers those quiet keys whenever H > J. The delta is "every key changed since its range was verified" (lines 274–276). The journal has no later entry for a key that was not modified, so nothing reads it again. Either those keys stay in the unverified tail and the tail cannot shrink to the budget, or they are dropped and never compared. Copy and verification overlap on a large store; that is the case this procedure is for.

Keep two numbers. Ordering needs the snapshot high-water mark. Verification needs the key's own last modification. A deferral has to remain in the unverified set and be retried at a later point even when the journal never names that key again.

## Small notes

- Renewal in the prototype is `UPDATE … WHERE token = $mine` (`node.rs`, lines 459–460). Child A §5.1 says a plain update of `lease_until`. Without the token predicate, a renewal that was waiting on the takeover's `FOR UPDATE` rewrites the successor's lease and the old owner still sees a successful renewal.
- Child C §8 records (0) at 150–200/s as the SLO-qualified result. At 0.5 ms the batches that reach that rate have write p99 of about 116 ms (N=8) to 850 ms (N=64); the best batch under the 100 ms write SLO is N=4 at about 130/s (`model-0.jsonl`). The rule still fires. The 15,744/s figure is the N=64 commit stage with execution, validation and the overlay omitted (commit-path README, lines 333–361). Same-counter (a) in that cell is 424/s before execution.
- Sequence placeholders are resolved "at commit," and the rewrite list is index entries, comparisons and outbox rows (child A §6.3 item 5). Following admission tokens are stored in the work row (`timeline.rs`, lines 161–206) and later compared as strings (`timeline/work.rs`, lines 101 and 115). Row images have to be rewritten too, and a key that contains the sequence has to be resolved before validation.
- Child B §6 step 4, inside the pause, says every asset and release-artifact digest must be present and re-hash. The following clause checks digests added since the last round. A re-hash of the whole blob set is again proportional to the store.
- The owner tag is `sb:<store>:<holder>:<token>` in at most 63 bytes (child A §5.2). A truncated tag drops the token the generation filter parses. The prototype's passing filter assumes the token is a complete colon field (`node.rs`, lines 257–261).
