## Verdict: SOUND WITH MAJOR ISSUES

The single serial stream, snapshot pre-execution, and in-place fallback are the right response to S0 and to the parent commission. The serializability argument does not hold for the reads this engine actually performs: an early-stopped descending scan validates the wrong side of its range, and an index lookup validates key presence while the value is a row image whose non-key updates never touch the index. On one snapshot, with no concurrency, the overlay's limited-count formula already diverges from `count_prefix` and can admit an over-cap write. Time-audience publication is a sequenced commit on the query path; the committer specifies it as a conflict-exempt pin. These are repairs inside this design. The stream, the batch, and K0 should stay.

## Fundamental and major findings

### F1. Early-stopped directional reads validate the unexamined side of the range — FUNDAMENTAL — read-sets §3–§4

Store scans are half-open in byte order and then ordered by direction: `k >= lo AND k < hi`, `ORDER BY k DESC LIMIT n` (`store.rs:110–118`, `rows.rs:92–143`). A descending page returns the largest keys. The last key examined, `k_stop`, is the smallest of those keys. Inserts and deletes that change the page lie at `k_stop` and above, up to the exclusive end. The same shape is `index_head` and every `LIMIT 1` descending read: the result moves when a key appears beyond the current extreme, in the gap the search just crossed.

The read set stores `Range(lo, hi')` and sets `hi'` to that last examined key (`3000.009.001.000.000.001` §3). For a descending early stop that interval is `[lo, k_stop]`. It includes keys the page did not depend on and excludes the keys it did. "Plus the next position that would have entered" extends the walk further downward, still on the side that cannot change a limited descending page. §4 then intersects only that interval. Ascending early stop happens to be the byte-order prefix, so the same notation looks right and the adversary's "just outside" case can pass while descending pages never conflict.

This is the chat and timeline order (`read.rs:1204–1206`, `timeline/work.rs:32`) and the job sweep's frozen upper key (`job.rs:336–341`, `Dir::Desc`, limit 1). Serial replay runs the later member on the post-image and returns a different page or a different upper key. The fix is a directional next-key span: the keys actually returned, the gap from the bound the walk started from through the extreme key, and one successor past the last key in the walk direction. `index_head`'s conflict sentence ("a key beyond the head") is that span; the stored range "from the head to the end" is the opposite side, and §4 implements the stored range.

### F2. An index read of a row image misses a payload update that keeps the key — FUNDAMENTAL — read-sets §3–§4

`lookup` and `scan` return `r.data`, the full row image (`store.rs:610–637`). `put` rewrites an index entry only when the encoded key changes (`store.rs:678–688`: `if before == after { continue; }`). A non-key update is a `Row` write and an unchanged key.

The conflict rule for `lookup` is "adds or removes that index key". The §4 probe for a range looks only at the add/remove map. A concurrent update of a column that is not in the index leaves that map untouched, validation succeeds, and replay shows the new image. Meter cuts make the same dependency stronger: `scan_metered` stops on cumulative payload size (`store.rs:1201–1216`), so a larger image for a row already on the page changes the cut and the cursor. The clause "or rewrites a row the scan returned" is the right idea and is absent from the §4 algorithm; `lookup` does not have it at all. Rows a rule or expiry check examines are in the same position: the runner pulls them with `scan(..., limit 1)` (`authorized_point.rs:149–164`) and then hides them. Their images decide the page.

Every observed image needs a `Row(table, id)` dependency, including filtered and meter-examined rows. Key intervals remain for phantoms and absences. Recording `get` by primary key already does this. Index reads do not.

### F3. Saturated `count_prefix` arithmetic diverges on one snapshot — FUNDAMENTAL — overlay §4

`count_prefix` is `COUNT(*)` of a `LIMIT` (`store.rs:642–647`). Callers pass the limit as the decision boundary: caps use `max + 1` and refuse when `count >= max` (`write.rs:733`, `767`); receipt membership counts stop at 50 and store `total - sender` (`receipts.rs:196–213`). The overlay answers "snapshot count + added − removed" (`3000.009.001.000.000.000` §4).

Once the snapshot count is capped, subtraction invents room. A group far past its cap returns `max + 1`. Deleting two overlay rows yields `max - 1`, the cap check allows an insert, and the true occupancy is still over the cap. Adding one member to a receipt population that already saturated at 50 yields 51; the store still returns 50. No other commit is required. The in-place path and the overlay path disagree on the outcome and the stored count. The differential would fail if a case hits the cap; the formula as specified is the defect. A limited count has to be re-derived from the merged key set under the same limit, or re-read after the write set is applied.

### F4. Time-audience publication is a sequenced commit on the read path — FUNDAMENTAL — committer §6

On SQLite, every `/q/`, `/m/`, `/sync`, and the changes poll calls `advance_time_audiences` before the operation (`serve.rs:1018–1024`, `serve_changes.rs:112–116`). That takes the writer, pins the clock, and may publish one due row as its own commit: `next_seq`, `record_commit`, `partition::append`, then `commit` (`time_audience.rs:96–189`, `serve.rs:178–188`). `Engine::mutate` and `query_reading` do it again (`engine/mod.rs:916`, `743`). The pin reads the store: `requested.max(time_audience_clock())` (`time_audience.rs:29–35`). The mutation then runs in a later transaction and can observe the published row. Postgres lacks this path; the committer calls that a parity item (`3000.009.001.000.000` §2.1, §6).

§6 assigns `now` at admission, says it is never read from the store, exempts pins from conflict detection, and applies one batch maximum. That reproduces the metadata `max`. It does not publish the due row, and it does not order that publication before the request that currently waits for it. A query on a reader connection cannot perform this write locally once the engine mutex is gone. The publication has to be a stream member that commits before the snapshot of the request that triggered it. The clock read has to be a recorded read, with `now` raised to the committed pin and the member re-executed. The batch maximum is a valid encoding of the final pin only after that order holds.

### F5. The byte-for-byte oracle does not test the claim — MAJOR — committer §3.5 and §8, overlay §6

§3.5 says replay of admission inputs (operation, arguments, principal, `now`, placeholder resolutions) through the reference reproduces every outcome and the final state. Server ids come from a process-wide cryptographic `Mint` (`ids.rs:8–40`), cloned into the context (`engine/mod.rs:262–267`) and advanced by discarded attempts as well as committed ones. Timeline chunks also stop on a wall-clock budget (`timeline/work.rs:59–65`), so the same inputs visit a different number of rows when the machine speed changes. Two fresh stores running the overlay differential mint different ids. The oracle and the differential fail on the reference itself, which means a red run does not identify an overlay or validation defect. Record every minted id and every other non-store decision (visit count, chunk cursor) in the admission record and inject them on replay, the way `Context::with_ids` already can. Compare logical outcomes only after that.

## What the documents get right that should not change

- One committer per store, revisions for every durable write, public sequences only for publishing members, and the ownership-lease renewal kept off the stream. That is the parent's §6.3 item 4, and it is what makes a snapshot a prefix.
- Pre-execution outside the serial section, with in-place members as the hot-key and eligibility fallback, and one flush per batch. S0's serial batch at about 160/s versus the commit-stage bound of 15,744/s at 0.5 ms is the right evidence for that split (`experiments/postgres-commit-path/README.md`).
- Acknowledge only after commit, and split a failed batch into single-member reruns. Receipts then keep exactly-once on crash, which matches `record_applied` in the same transaction as the writes.
- Read recording at `Rows` / `PartitionRows` / family operations, with a method census, and coarsening as a safe size bound. `Runner::read_tables` is table names only (`runner.rs:131`).
- The overlay as a `Rows` implementation beside `Layered`, qualified family by family, with writes staying off reader connections. Executing in a real write transaction would take SQLite's writer lock or Postgres row locks and give the serial section back.
- K0 and K1 shipping before S1a, and K2–K5 waiting on the sizing rule. The seam is useful even if pre-execution never becomes the default.
- Keeping (b) and "cut `k`" as named alternatives. (b) still has no contiguous-prefix snapshot protocol. Cutting round trips inside the lock is worth doing on the in-place path and still misses 1,000 commits/s at 0.5 ms.

## Small notes (optional, at most five)

1. Meter cuts happen inside `Rows::scan_metered` (`store.rs:1173–1216` reserves `2 * page_size` and charges each examined image). Overlay §2 says the interpreter charges from answers and identical answers imply identical charges. §4's requirement that examination counts and cut sites match is the one that matches the store.
2. The receipt check is raw SQL on `_ops` (`store.rs:1299–1308`) and is not a read-set kind, though parent §6.3 item 2 names `_ops` lookups. A duplicate read-only effect conflicts only when `INSERT INTO _ops` (`store.rs:747–749`) aborts the whole batch. Record the absence.
3. Ephemeral mutations already drop the engine guard (`serve.rs:1416–1418`) and serialize on the hub lock (`ephemeral.rs:446`). They are not in §2.2. K0's removal of `FairMutex<Engine>` has to leave that lock as their order, and keep the shared `Mint` on one thread.
4. Delivery-versus-backfill compares sequence-derived admission tokens in the engine (`timeline/work.rs:101`, `115`), which Quarry `check --cost` never sees. Those paths need the parent §6.3 taint rule, or a follow pre-executes a branch on a sequence it does not have yet.
5. `record_commit` stores each member's `at` (`store.rs:728`). A batch that only checks `now` against the pin from before the batch, then writes the maximum, can commit a later revision with an earlier `now` when enqueue order and admission time disagree. The check belongs on a pin that advances in revision order.
