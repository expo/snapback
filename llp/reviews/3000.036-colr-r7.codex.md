**[P1] Projecting an insert result can roll back an authorized blind insert.** [program.rs:1357](/home/ccheever/projects/sb4-b19-colr/snapback4/crates/snapback4-lang/src/bind/program.rs:1357) now routes consumed column-bearing inserts through `ProjectFields`. That calls [project_row](/home/ccheever/projects/sb4-b19-colr/snapback4/crates/snapback4-core/src/engine/field_authority.rs:126), which converts row-read denial into `NOT_FOUND`. The mutation then rolls back.

Concrete reachable case, called as `bob` with a fresh id:

```quarry
table records:
  owner: principal
  secret: text <=80 read <- deny
  read <- .owner = viewer
  insert <- allow
  online only

mutation add(id: id):
  return insert records { id, owner: 'alice', secret: 'x' }
```

The insert rule permits this write, but consuming its result makes it fail. Discarding the insert result allows it to commit. Successful `insert … if absent` bindings have the same problem.

This contradicts §22’s separation of write and read authority. It also diverges from [the Lean model](/home/ccheever/projects/sb4-b19-colr/snapback4/lean/Quarry/Write.lean:113), which commits and returns null for an unreadable inserted row. The new insert regressions use public rows, so they miss this case.

Use a nullable disclosure path for insert results and align their generated types.
