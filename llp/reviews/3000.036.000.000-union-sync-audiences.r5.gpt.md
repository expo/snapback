1. **High — §3 commit-boundary accounting still discloses ids when an existing row expires while entering a new arm.**  
   Start with `buyer = Bob`, `seller = Bob`, and a future `until`, under `read <- .buyer = viewer or .seller = viewer`, `expire at .until`, and `sync`. With `update <- allow`, run one mutation that sets `buyer = Mallory` and `until = now`, then returns `null`. Mallory could read the row at neither commit boundary.

   The existing-row branch nevertheless logs a `put` to Mallory: [`partition.rs:273`](snapback4/crates/snapback4-core/src/partition.rs:273) does not apply the lifetime check used for births at line 256. [`retire_expired_births`](snapback4/crates/snapback4-core/src/engine/write.rs:367) only examines `born_rows`, so this row survives physically. At delivery, `fetch` treats it as absent (`engine/read.rs:346`), and `expand_joins` converts the put into a `del` (`partition.rs:1146`). That reveals its id to Mallory, violating D2. A later sweep can repeat the disclosure.

   Account an already-expired final image as absent, preserving revocations to the commit-start partitions, and ensure physical retirement cannot later announce the uncommitted recipient. Extend the two-party world with content expiry and this mutation, checking both immediate delivery and delivery after sweeping at both page sizes. §8.8 excludes expiring **membership tables**, so this input is admitted. The round-1 transient-accounting disposition is therefore incomplete.

2. **Low — §4.3 and §10 overstate when predictions are withdrawn.**

Thus “every apply path withdraws predictions … before it applies a page” is inaccurate.

   The retention argument remains sound here: snapshot R2 inspects private staged server images (`device/snapshot.rs:108`), rather than the prediction overlay. Rewrite the disposition to distinguish snapshot staging from ordinary and deferred stream application.
