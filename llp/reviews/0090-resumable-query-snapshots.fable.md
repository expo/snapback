## 2. Overall assessment

This is a well-motivated, mostly well-grounded RFC that identifies a real and valuable unification: the wire already speaks version-stamped snapshots and deltas, and the server already retains a prunable change journal with a resume floor, so "snapshot + cursor through other channels" is a genuinely small protocol delta with a large product payoff. I verified the load-bearing code claims and almost all of them hold precisely: the `LiveEnvelope` shapes and `snapshotVersion` receipts are exactly as described (`src/live_wire.rs`), the boot waterfall is real (`demos/cursors-web/surfaces/react/index.html` is a bare shell; `main.tsx` awaits `health()` then `ensureApp()` before mount; `getServerSnapshot` in `packages/snapback-client/external-store.mjs` line 311 is indeed a stub returning the same client snapshot), no `resumeFromVersion`/`resume_from` exists anywhere in `src/` or `packages/`, and the `_snapback_changes` journal (`src/storage.rs` line 3507, storing `row_json`; `journal_resume_requires_resnapshot` in `src/local.rs` line 9578) is exactly the "hard part already exists" substrate the RFC leans on — LLP 0008's L3 note even says the missing piece is a delta-resume consumer, which is what this RFC proposes.

However, the RFC has a serious blind spot around authorization. It does not cite LLP 0053 (Accepted) at all, and LLP 0053 — echoed in LLP 0008's amended §Authorization text — mandates that **every auth-scoped resumption from a non-live state fresh-snapshots**, explicitly including "any resume-from-retained path," page reloads, and process restarts. Channels A and B, applied to auth-scoped queries, are precisely that path, so the claim that "this RFC adds no new failure semantics" (lines 126–129) is wrong for the auth-scoped case: the RFC either contradicts an Accepted decision or silently renegotiates it. Relatedly, the browser auth architecture (LLP 0060/0077: bearer + sender-constrained custody in IndexedDB, cookies explicitly avoided) leaves the initial HTML navigation request with no credential, so auth-scoped Channel A has no authentication mechanism as specified. Both are fixable — mostly by scoping v1 to non-auth-scoped queries and adding an explicit renegotiation path — but they must be fixed in the document before it can be accepted.

## 4. Concerns

**1. (Major) Auth-scoped resume contradicts Accepted LLP 0053, which the RFC does not cite.** LLP 0053 (Status: Accepted) mandates "a mandatory resnapshot on reconnect for every auth-scoped subscription" and defines reconnect maximally: "'Reconnect' means every resumption from a non-live state, and it must cover every materialized copy… process restart, page reload, tab close-and-reopen… and any resume-from-retained path" (LLP 0053 lines 296–320). LLP 0008's amended §Authorization repeats it: "every non-live auth-scoped resume fresh-snapshots regardless of epoch equality" (line 523). Channel B relaunch and Channel A subscribe-from-embedded-version are exactly non-live auth-scoped resumes, and D3's "render the first frame from the persisted snapshot" collides with 0053's rule that no materialized copy may render an auth-scoped result without a live subscription or a signed lease (the item-8 lease machinery in LLP 0043/0053, which the RFC never mentions). The claim at lines 126–129 that "this RFC adds no new failure semantics" is therefore false for the auth-scoped case — honoring `resumeFromVersion` there *is* a renegotiation of an Accepted decision, and replaying journal deltas across a permission change under current-time classification is precisely the staleness hole 0053's composite-witness machinery exists to close. **Resolution:** either (a) scope v1 `resumeFromVersion` and first-frame-from-persisted rendering to non-auth-scoped/public subscriptions, with auth-scoped subscriptions taking today's fresh-snapshot path (and lease-gated rendering per 0053 where retained display is wanted), stated explicitly in D1/D3; or (b) add a section that explicitly renegotiates 0053's mandatory-resnapshot rule with the obligation/lease machinery and an epoch-carrying cursor, flagged as requiring 0053 amendment. Either way, add LLP 0053 and LLP 0043 to Related.

**2. (Major) Auth-scoped Channel A has no authentication mechanism under the landed browser-auth architecture.** D2 (lines 167–169) says "Auth-scoped inlining means the HTML response becomes per-identity and must be marked uncacheable," presenting auth-scoped inlining as workable. But the hosted browser auth model is bearer tokens with sender-constrained custody held in IndexedDB (LLP 0077 — key material explicitly kept out of URLs/localStorage; LLP 0060 line 1098 lists cookie adoption without a full Origin/CSRF analysis as a hazard). The initial document navigation therefore carries no credential the gateway can evaluate, and D1.2's requirement that snapshot fetch "run under the requester's authenticated identity exactly like a subscription (LLP 0011)" cannot be met for the HTML-serve case as specified. **Resolution:** state that Channel A v1 is anonymous/public-manifest-only (the document already gestures at this) and move authenticated inlining behind an explicit prerequisite — a cookie-or-equivalent document-request credential with its own LLP 0060-adjacent security analysis; alternatively re-shape authenticated Channel A as "shell + immediately-fetched Channel C bundle," which works under the existing token custody.

**3. (Moderate) The delta-resume value proposition is overstated relative to DK-3's actual coverage.** `live_delta` applies only to the analyzable unordered subset; ordered queries fall back to `live_replace`, and membership-gated plans are excluded fail-closed from `live_delta` at candidacy and inside `compute_live_delta` (LLP 0008 header, 2026-07-21 entry; `src/live_wire.rs` lines 51–53; `src/live_matcher.rs`). For every query outside that subset, a resume can at best answer with a fresh `LiveReplace` — and the wire has no "unchanged since version N" frame, so even a fully current client re-downloads full rows. The RFC's framing ("resumes deltas from that version rather than refetching," lines 22–24; Channel B "deltas instead of full snapshots on every relaunch," line 222) silently assumes universal delta coverage. **Resolution:** state the coverage boundary explicitly, and add an open question on whether a cheap "current-as-of-version" acknowledgment frame (or version-equality short-circuit) is in scope, since that is where much of Channel B's bandwidth win actually lives for non-analyzable queries.

**4. (Moderate) The resume cursor is underspecified: commit version alone is not enough.** `ResyncRequired` already carries an `epoch` field and a `permission_epoch_changed` reason (`src/live_wire.rs` lines 79–89), and the auth program's durable authorization version advances on writeless events that produce no journal rows. A resume admission check that consults only the journal floor (`journal_resume_requires_resnapshot`) would honor resumes across authorization-version changes it cannot see. Even under Concern 1's resolution (a) — non-auth-scoped-only v1 — the RFC should say what the cursor *is* (version only, or version + epoch/app-generation) and what the admission predicate checks, so the v1 scope doesn't fossilize a cursor shape that can't grow. **Resolution:** specify the cursor tuple and the server-side admission checks (journal floor, schema/app identity, authorization version where applicable) in D1.

**5. (Moderate) No interaction story with the offline mutation outbox (LLP 0043).** LLP 0043's landed milestone does **full-resync-before-replay** — a reconnecting client completes a full resync before queued mutations replay — and explicitly pinned "delta-resume with pending offline mutations" out of scope as its named third milestone. Channel B relaunch with a non-empty outbox is exactly that pinned case: the RFC's relaunch sequence (render persisted, resume deltas) and 0043's replay sequence (full resync first, then replay) cannot both hold without a stated ordering rule. The RFC never mentions the outbox, pending mutations, or optimistic layers. **Resolution:** add a section (or open question) stating the rule — e.g., v1: a non-empty replay queue disables `resumeFromVersion` and takes the 0043 path — and cite LLP 0043 as the co-owner of milestone 3.

**6. (Minor) Cloudflare read-path characterization is imprecise.** "The gateway already reads query results synchronously from the coordinator commit" (D2 lines 163–164) — the gateway itself reads nothing; it forwards `/query` POSTs to the coordinator DO (`cloudflare/src/gateway.js` lines 25, 110–112), and asset serving currently bypasses the coordinator entirely. Channel A adds a gateway→coordinator subrequest to every manifest-bearing pageload before HTML can be served. The conclusion stands, but the cost and the plumbing change (assets and coordinator must be composed per-request) should be stated accurately. **Resolution:** reword to "the coordinator answers request/response query reads against committed state, so the gateway can assemble the bundle with one DO subrequest per pageload."

**7. (Minor) Related list omissions.** Beyond 0053 and 0043 (Concerns 1/5): LLP 0051 governs the schema-governed wire (any new envelope field or frame must land through the `live_wire.rs` schema/drift-gate machinery — worth one sentence in D1), LLP 0034 owns the wire/client half of DK-3, and LLP 0022 is the corpus's existing Electric/PowerSync research that the prior-art table partially re-treads. **Resolution:** add them to Related and a sentence noting the 0051 drift-gate obligation for the protocol additions.

**8. (Minor) The `health()`/`ensureApp()` piggyback is arm-dependent.** On the deploy-time-compiled Cloudflare arm the server knows the app identity, so embedding handshake results is coherent; in the local packaged dev loop the *client* owns the schema manifest and drives `ensureApp` (`main.tsx` line 43), so the server cannot pre-answer an ensure it hasn't seen. **Resolution:** scope the piggyback claim (D2 lines 156–158) to arms where the served instance already owns the app identity, or note the dev-loop needs a manifest-hash echo instead.

## 4. Concerns

1. **[Moderate] The authority-independence classification mechanism is never bound.** The entire v1 security boundary — what may be inlined into anonymous HTML (D2), persisted-and-rendered (D3), and resume-admitted (D1.1) — rests on a query being "authority-independent," defined here only by property ("results do not depend on the requesting identity," line 54). LLP 0053 already supplies the mechanism: an explicit, declared, trusted `authorityIndependent: true` assertion, with "undeclared means auth-scoped" fail-closed (0053:289, 377). The RFC uses the vocabulary but never says D1.1/D1.4/D2 admission is keyed to that declared fact, and never discusses that Channel A **amplifies the blast radius of a false declaration**: today a false `authorityIndependent` assertion leaks over one subscription; under D2 it leaks into served (and per Q6, potentially CDN-cached) HTML. *Resolution:* one paragraph in Authorization scope / D1.4 binding v1 admission to LLP 0053's declared `authorityIndependent` fact as carried in the served functions manifest, stating the undeclared-means-refused default for manifest entries, acknowledging the amplification, and adding an acceptance check that a manifest entry naming an undeclared query is refused at admission.
2. **[Moderate] The normative serializer requirement specifies a no-op as written.** Line 268 reads, byte-for-byte: "escape HTML-significant sequences (`<` as `<`, plus U+2028/U+2029)" — escaping `<` as `<` does nothing. The intended escape is plainly `<` (and ` `/` ` as their `\uXXXX` forms), and it appears the escape sequence itself was eaten by an HTML-entity or serialization mishap during revision — an ironic instance of exactly the bug class the sentence guards against. The adversarial `</script>` acceptance fixture (line 433) would catch a broken implementation, but a security MUST should not be self-contradictory on its face. *Resolution:* fix the sentence to specify JSON-string unicode escaping (`<` → `<`, plus U+2028/U+2029), and consider also naming `-->` / `<!--` per the standard JSON-in-HTML embedding guidance.
3. **[Moderate] Channel B on the web says nothing about multi-tab/store-attach semantics.** The corpus already treats this as a hard problem: 0053's second-tab-attaches-to-a-store-it-did-not-populate rule (0053:316–322) and 0008's Web-Lock-serialized same-origin store (0008 Revised, 2026-07-12). Two tabs racing to persist snapshots/tokens, or a tab resuming from a token another tab has since advanced past, need a stated single-writer/ownership rule even for authority-independent data (correctness survives via rung 3, but the persisted state's integrity and the "higher version wins" rule of lines 330–332 need an owner). *Resolution:* a short D3 paragraph naming the web persistence owner (e.g., the existing Web-Lock-serialized store discipline) and the cross-tab token rule.
4. **[Minor] Rung 1's "all query classes" claim overreaches for opaque plans.** The "cheapest check: no journal rows for the query's table set" (line 232) presumes a known table read-set; 0053:500 records that opaque JavaScript use leaves read summaries incomplete, so per-table unchanged proofs cannot cover those queries. The claim survives via the even-cheaper global check (no commits at all since `version` — the idle-relaunch common case), but the text should say which check applies to which class. *Resolution:* qualify rung 1: global no-commit proof for all classes; table-set proof only where the read summary is complete.
5. **[Minor] Wire-frame naming imprecision.** The envelope variant is `AuthorizationInvalidation` (carrying an *optional* `AuthorizationInvalidationSnapshot` payload — `live_wire.rs:65–71, 106–114`). The RFC repeatedly names `AuthorizationInvalidationSnapshot` as if it were the frame/invalidation semantic itself (lines 102, 147, 179, 326–327); D3's purge trigger in particular should key on the `AuthorizationInvalidation` obligation frame, not the optional snapshot payload. *Resolution:* name the frame correctly in the three places.
6. **[Minor] The 0008 resume-scoping note needs a reconciling amendment.** 0008 (lines 603–611) says v1 should target delta-resume "only for the online-reconnect-with-no-pending-mutations case"; this RFC deliberately widens version-based resume to relaunch-from-disk (honoring the pending-mutations boundary via the outbox rule, and the retention warning via the journal floor — the *reasons* behind 0008's rule are respected). Per corpus practice, the widening should land with a dated 0008 amendment rather than by silent supersession. *Resolution:* add the 0008 amendment to rollout step 0's landing list.

Its factual spine survives adversarial checking against the repository: the wire-protocol characterization (`LiveEnvelope::{LiveReplace, LiveDelta, ResyncRequired, AuthorizationInvalidation}`, version stamping, `snapshotVersion` receipts, the `PORTABLE_STORAGE_VERSION_MAX` range cap) matches `src/live_wire.rs` exactly; the boot-waterfall claims match the bare shells (`demos/cursors-web/surfaces/react/index.html`, `demos/graffiti/surfaces/contract/index.html`), the `health() → ensureApp() → subscribe` sequence in `main.tsx`, and the unfed `initialRows`/pass-through `getServerSnapshot` in `packages/snapback-client/external-store.mjs`; the journal claims match `_snapback_changes` (nullable `row_json`, deletes carry no row body — `record_change`, `src/storage.rs:10346`), `journal_floor_version`, and `journal_resume_requires_resnapshot` (`src/local.rs:9578`); the reattach-route facts are correct (`POST /live/{name}/resume` is subscription-id reattach, `src/server.rs:6974/16308`; `live.resume.{input,output}` schemas are already exported and drift-gated in `tests/artifact_schemas_v0.rs`; the Cloudflare gateway forwards only `subscribe|unsubscribe` on the live POST path — `cloudflare/src/gateway.js:29` — so the route is local-arm-only as stated). The characterizations of LLPs 0008 (DK-3 scope with fail-closed membership-gated exclusion, the L3 delta-resume-consumer gap, DK-9, Web-Lock discipline, the online-reconnect-only resume scoping the 0F amendment reconciles, the 2026-07-23 bookmarkable-versions note), 0031 (Active; the verbatim "Socketless HTTP cannot arm demand" invariant; the `ResponseSensitivity` universe genuinely containing no class for declared-public arbitrary query rows), 0034 (socket-close disposes durable subscriptions; reattach is permission-epoch retain/resnapshot with no version replay), 0039 (`AuthorizationVersion { incarnation, epoch }` owned there), 0043 (milestone structure, verification locus, `versionStreamId` identity tuple, retained/stale display duty), 0053 (declared fail-closed `authorityIndependent`, mandatory resnapshot on every auth-scoped non-live resume including reload/restart/second-tab, complete-read-summary machinery), 0060/0077 (bearer + IndexedDB custody, cookies unadopted), 0063 (the no-duplicate-subscription/no-stale-flash seam, verbatim), 0076 (served-instance manifest admission), and 0082/0083 all check out. The design itself is coherent: one primitive, three channels, a fail-closed admission ladder, and a rollout with named separable contract clusters.

One soundness gap remains in the core admission ladder — rung 1's global proof (and rung 2's journal-replay premise) silently assume every query result is a pure function of database state and arguments, an assumption the corpus itself demonstrates is false and already has machinery to enforce (LLP 0053's closed-inputs protected-query profile) that this RFC never binds to. That is a correctness hole in the primitive's central proof rule, and it is cheap to fix.

## 4. Concerns

1. **[Major] Rungs 1–2 assume query purity that nothing in v1 eligibility guarantees.** The global unchanged proof "applies to every query class" (lines 420–423), including opaque JS plans, and rung 2 reconstructs results purely from journal ops. Both are sound only if a result is a pure function of `(database state, args)`. The sole v1 eligibility fact, `authorityIndependent`, asserts invariance under *caller-authority* dimensions only (LLP 0053: "invariant under every caller-authority dimension" — not input closure), and LLP 0053 refuses `RuntimeNow`/`RuntimeId` only for *protected* queries (auth-scoped live + retainable). An authority-independent query reading time or randomness (declarative `RuntimeNow`, or `Date.now()` in an opaque plan) that relaunches after an idle gap gets `CurrentAsOf` under the global proof — the server ratifies rows a fresh execution would not produce, a semantic regression versus today's always-re-execute boot, unbounded except by token expiry and deploy cadence. The corpus already owns the fix: 0053's closed-inputs protected-query profile applies to "every retainable query, including an `authorityIndependent` retainable query" — and Channel B persistence arguably *makes* these queries retainable in 0053's sense, but the RFC never says so. **Resolution:** condition resume/persist/rung-1/rung-2 eligibility on the LLP 0053 closed-inputs proof (or an equivalent declared-and-verified input-closure fact), refusing to rung 3 otherwise; state explicitly whether Channel B persistence places a query in 0053's retainable/protected class; add an acceptance fixture proving a time-dependent query re-executes on relaunch instead of receiving `CurrentAsOf`.
2. **[Moderate] Step 0F amends 0008 and 0031 but not 0034, whose reconnect policy this RFC changes.** Accepted LLP 0034 pins "reconnect is always a fresh `subscribe_live`" (also encoded as the load-bearing comment at `packages/snapback-client/index.mjs:81`), and step 0B's client dispatch (reattach vs token-resume vs fresh, lines 293–296, 730–731) revises exactly the freshness/reconnect policy 0034 §2.2 governs. **Resolution:** add a dated LLP 0034 amendment to 0F (or one sentence arguing the invariant survives because token-resume still enters through a fresh `subscribe_live` and the token only seeds — but then say it, since "snapshot-with-subscribe" becomes "maybe-`CurrentAsOf`-with-subscribe").
3. **[Moderate] Register-mode idempotency key can merge concurrent legitimate boots as written.** The key is "bound to (authority, generation, manifest entry, canonical args)" (lines 388–391) — a tuple containing nothing that distinguishes two simultaneous same-user boots of the same route (two tabs), yet a matching key "returns the same registration set (or atomically supersedes it)." Read literally, tab B's boot dedupes or supersedes tab A's registrations. **Resolution:** state that the client mints the key per boot attempt (the tuple scopes replay validity only); add a two-concurrent-boots fixture to step 2's acceptance; and say how Channel C register mode composes with LLP 0053's second-tab attach rule under the Web-Lock store discipline (D3 covers this for persisted tokens only).
4. **[Moderate] Channel B has no device-storage lifecycle.** D3 persists "the latest snapshot + resume per subscription" (lines 563–565) across every authority-independent subscription with no storage budget, eviction rule, or GC — bundle limits (lines 358–360) bound the wire, not the store, and Q4 covers at-rest *protection*, not growth or selection. Long-lived apps with many parameterized queries (`argsHash` per instance) accumulate unboundedly. **Resolution:** add a bounded persisted-store budget with an eviction rule (or an explicit persist opt-in/out knob per manifest/subscription) to D3 and step 0, with a fixture.
5. **[Minor] MAC key custody is unlocated.** Step 0A pins scheme, key id, rotation, expiry, size (lines 718–720) but not where the key lives per arm (Worker secret vs DO storage vs local SQLite), whether the local arm's key survives restart, and that key loss is availability-only (everything refuses to rung 3). **Resolution:** add custody location and key-loss posture to the 0A checklist.
6. **[Minor] Token expiry's role is never stated.** Expiry appears as a step-0 contract item (line 196) and implicitly among refusal causes, but the document never says whether it is a correctness knob (bounding staleness — load-bearing while concern 1 is open) or purely key hygiene. **Resolution:** one sentence pinning which, in D1 or 0A.
7. **[Minor] Channel B offline relaunch display.** A relaunching-offline client renders persisted rows retained/pending indefinitely with no way to check `generation` currency until connect (lines 567–571). This is defensible under 0043's "never presented as current" rule, but the alignment is unstated. **Resolution:** one sentence in D3 tying the offline-relaunch retained/pending display to 0043's rule and the connect-time refusal path.

### 0A.1 Token envelope, MAC, keys

```
tokenWire   = "sbrt1." keyId "." b64url(bodyBytes) "." b64url(mac)      // opaque to clients
keyId       = "sbrk_" <22-char base64url>                               // AuthKeyId-style (lease.rs precedent)
bodyBytes   = canonical JSON (sorted keys) of tokenBody
tokenBody   = { app, generation, versionStream, version,
                queryArtifact, argsHash, digestKind, contentDigest,
                issuedAtMs,                    // ADDED — see decision 4
                authPartition: null }          // reserved; MAC'd as absent-tag
mac         = HMAC-SHA256(key, transcript), 32 bytes, untruncated
transcript  = "snapback-resume-token-v1\0"
              || tag-length-prefixed fields in the fixed order above
              (put_string/put_u64/put_optional_string exactly as src/auth/lease.rs)
```

- Token is **self-contained**: the server decodes `bodyBytes` from the token itself; the clear `meta` copy is client convenience only and is never trusted at admission.
- **Keyring**: reuse the `AuthKeyringStore` pattern. Active key mints; the ring retains the previous 2 keys for verification during a 14-day overlap; a key absent from the ring refuses with `SNAPBACK_RESUME_KEY_UNKNOWN` (distinct from `SNAPBACK_RESUME_GENERATION_STALE`), always answering rung 3.
- **Expiry**: `now - issuedAtMs > maxTokenAgeMs` (default 30 days, server knob) refuses with `SNAPBACK_RESUME_TOKEN_EXPIRED` → rung 3. This is the staleness backstop for render-before-resume admission too.
- **Custody per arm**: local arm — a `resume-keyring.json` beside the auth keyring under `secure_file`, surviving restart; Cloudflare arm — coordinator DO storage (not a Worker env secret: the DO is the sole minter/verifier and rotation must not require a deploy). Key loss ⇒ all outstanding tokens refuse to rung 3; never a correctness event.
- **Size cap**: token ≤ 1 KiB (comfortable with a 32-byte compressed digest, decision 7).

### 0A.2 Canonical row encoding (shared Rust / JS-Worker / JS-client / native)

- **RFC 8785 (JCS)**: UTF-8, keys sorted by UTF-16 code units, ECMAScript shortest-round-trip number serialization, **no Unicode normalization** (bytes as stored), non-finite numbers refused at mint (mirrors `canonicalValue`'s refusal in `external-store.mjs`). Integers outside ±2^53−1 are refused at mint (they already cannot round-trip through JS clients).
- `rowHash = SHA-256("snapback-rqs-row-v1\0" || jcs(row))` — 32 bytes.
- `canonicalRowId` = the UTF-8 bytes of the wire row id (the same string as `LiveDeltaWireOp.id` / `_snapback_changes.row_id`).
- **Leaf** (making the RFC's `H(canonicalRowId || rowHash)` injective):
  `leaf = SHA-256("snapback-rqs-leaf-v1\0" || u64_be(len(idBytes)) || idBytes || rowHash)`.

### 0A.3 contentDigest (shape-split)

- `digestKind = "mset1"` (DK-3-analyzable unordered): LtHash-16 class — state = 1024 lanes × u16 little-endian (2048 bytes); each leaf expands to 2048 bytes via BLAKE3 XOF; add lanes mod 2^16 to insert, subtract to remove; update = remove(old) + add(new). Empty result = all-zero state. Security margin stated per the LtHash SIS reduction. Published form: `contentDigest = "mset1:" + hex(SHA-256(state))` — a **compressed root**; the full 2048-byte state is held privately by the server per live result (incremental maintenance) and recomputed by the client from persisted rows at verification time (O(n), acceptable at relaunch). Rung-2 witness verification recomputes the state from `(rowId, oldRowHash)` leaves and compares compressed roots.
- `digestKind = "seq1"` (ordered/limited/replace-only): `contentDigest = "seq1:" + hex(SHA-256("snapback-rqs-seq-v1\0" || jcs(rowsArrayInDeliveredOrder)))`, computed only at `LiveReplace` boundaries and carried through rung-1 global proofs unchanged.
- The kind prefix makes digests self-describing; the *authoritative* kind selection is the served manifest's delta class for the `queryArtifact`, and a kind/class mismatch at admission refuses to rung 3.

### 0A.4 Token refresh rule, persistence cadence, store budget

- Mint a fresh token on every result-changing durable envelope (`LiveReplace`, `LiveDelta`, replay completion, `CurrentAsOf`); one mint shared per `(queryArtifact, argsHash, version, contentDigest)` across fan-out; minting suppressed for auth-scoped subscriptions.
- Client persistence (Web-Lock holder only): atomic commit of `{rows, meta, token}` in one IndexedDB transaction, on a trailing debounce of 1 s capped at 10 s of continuous change, plus a flush on `pagehide`/visibility-hidden. Before applying a delta sequence the holder marks the entry in-progress; an entry found in-progress at relaunch is invalid → fresh subscribe.
- `meta = { version, contentDigest, generation, versionStream }` per the RFC, **plus `queryArtifact` and `argsHash`** (see decision 8 — D3's A-vs-B arbitration is otherwise uncheckable client-side).
- Store budget: default 32 MiB or 256 entries per app (whichever first), accounted as serialized `{rows, meta, token}` bytes; eviction least-recently-resumed; per-manifest-entry `persist: false` opt-out.

### 0A.5 `generation`

```
generation = "gen1:" + hex(SHA-256("snapback-generation-v1\0"
             || tag-length-prefixed: deploymentIdentity, schemaSha256,
                functionsSha256, capabilitySha256, resumeConfigSha256))
```

- Cloudflare arm: components from the deploy receipt (`ReleaseCompatibility`-style hashes, `src/deploy.rs`). Local arm: recomputed from the served instance's manifest hashes after every schema/functions ensure — **content-derived**, so a no-op ensure yields the same generation (see decision 10).
- `resumeConfigSha256` covers (enumerated): journal prune policy identity, auth mode, route→query manifest hash, and the 0A digest-contract version string.

### 0A.6 `versionStream` crosswalk

- Reuse the existing data version stream: UUIDv7 in `_snapback_meta` (`ensure_data_version_stream_in`), rotated inside the reset transaction (`rotate_data_version_stream_in`, `src/storage.rs:800`) and on import/declared restore per LLP 0043. It exists independently of auth-mode installation, so anonymous Channel A apps have one.
- Crosswalk (normative table in the contract): `versionStream` ≠ LLP 0039's `AuthorizationVersion { incarnation, epoch }`; the authorization identity is reachable only through the reserved `authPartition` v2 door; commit versions compare only within one `versionStream`.

## 3. Decision log

1. **Token self-containment.** Is the token `MAC(tokenBody)` literally (body reconstructed at admission from the subscribe request + `meta` + served-instance facts), or a self-describing envelope carrying the body? The RFC's grammar (`resume = { token: MAC(tokenBody) … }`) says the former; D1.1 ("verifies the MAC, then accepts the token only if `app`, `generation`, `versionStream` match") reads like decoding fields *from the token*. Candidates: (a) MAC-only, body rebuilt from context+meta — but then `meta` becomes trusted input, contradicting "the client never edits it; it stores the blob plus the clear meta copy"; (b) self-contained body+MAC. Picked (b): it keeps `meta` advisory and matches the `AuthorizedLease` shape. Divergence: the subscribe-request wire schema and admission trust model differ between the two readings — **Major**.
2. **Token envelope framing and MAC transcript.** JSON-canonical bytes MAC'd directly vs a length-prefixed field transcript (`put_string`/`put_u64`, `src/auth/lease.rs`); dotted string vs single base64 blob; where `keyId` sits ("a key id in the token envelope" — inside or outside the MAC'd body?). Picked lease-precedent transcript, dotted framing, keyId outside body but included in the transcript (as the lease does at `lease.rs:490`). Divergence: each arm is self-consistent (tokens are minted and verified by the same instance, and `generation` binding localizes them), but the Rust and JS-Worker arms would implement incompatible 0A "shared" contracts and the mandated cross-language parity tests could not be written once — **Moderate**.
3. **MAC algorithm.** HMAC-SHA256 vs KMAC vs keyed BLAKE3. Picked HMAC-SHA256 (repo precedent: `lease.rs`, `admin_secret_read.rs`; `hmac`/`sha2` already in `Cargo.toml`). The RFC delegates this to 0A explicitly, so a guess is expected — **Minor** (any sound choice works; it never crosses an implementation boundary un-negotiated).
4. **Expiry needs a field the pinned `tokenBody` schema lacks.** The RFC requires token expiry (key hygiene + staleness backstop) but pins `tokenBody = { app, generation, versionStream, version, queryArtifact, argsHash, contentDigest, authPartition? }` — no issued-at. Candidates: (a) add `issuedAtMs` to the body; (b) derive age from key-id epochs (coarse: expiry granularity = rotation period); (c) wall-clock side-table keyed by mint (reintroduces per-token server state). Picked (a). Divergence: the *pinned* token schema differs and the staleness-backstop admission behavior differs materially at edges — **Major** (a spec self-inconsistency: the schema as written cannot implement the RFC's own expiry requirement).
5. **Canonical row encoding.** "A canonical row encoding shared across Rust/JS/native — step-0 item" names the problem, not the answer. Candidates: RFC 8785 JCS; the repo's Rust `canonical_json` (key-sort only, no number normalization — `storage.rs:10802`); the client's `canonicalValue` (`external-store.mjs:63` — drops `undefined`, normalizes −0, refuses non-finite, no key-encoding rule for numbers). These three *already disagree* (−0, number formatting, undefined handling, large-integer behavior). Picked JCS with mint-time refusal of non-finite and >2^53−1 integers. Divergence: client-recomputed digests never match server-minted ones → every persisted-state verification fails → the entire Channel B/A verification surface is dead on arrival, and Rust-arm vs JS-arm digests differ — incompatible store artifacts — **Major**.
6. **Multiset digest construction.** "LtHash-class with a stated security margin" admits many incompatible instantiations: lane count/width (1024×16 vs 2048×16 vs 683×32), leaf-expansion XOF (BLAKE3 vs SHA-512-chain vs BLAKE2xb as in Facebook's LtHash), endianness. No crate is vendored; both a Rust and a JS implementation must be written to the same spec. Picked 1024×16-bit LE lanes + BLAKE3 XOF. Divergence: incompatible digests across every component pair — **Major**.
7. **Published digest form: full lattice state vs compressed root.** A 1024×16 state is 2048 bytes; carrying it in `tokenBody`/`meta` bloats every envelope and token (and collides with the token-bytes cap the RFC itself mandates); publishing `H(state)` keeps 32 bytes but means the client recomputes the state from rows at verify time and rung-2 witness checking must recompute-then-compare rather than algebraically subtract from the published value. The RFC says "incrementally maintainable" (suggests state) and "a digest of the snapshot's canonical serialization" (suggests compressed) without choosing. Picked compressed root, private state. Divergence: `meta`/token wire artifacts of different sizes and a structurally different witness-verification protocol — **Major**.
8. **Clear `meta` is too small for D3's arbitration.** D3: when Channels A and B supply the same subscription, "the higher `version` within matching token identity (`app`/`generation`/`versionStream`/`queryArtifact`/`argsHash`, digests verified) wins" — but `meta` is pinned as `{ version, contentDigest, generation, versionStream }`: the client cannot see `app`, `queryArtifact`, or `argsHash` in either candidate (the token is opaque to it). Candidates: (a) widen `meta`; (b) redefine the arbitration in terms of the external-store identity key (`externalStoreIdentity` already covers provider/query/authority/args) + `meta`'s four fields. Picked (a) (adds `queryArtifact`+`argsHash` to `meta`); (b) is defensible but `queryArtifact` (generation-scoped artifact identity) has no client-side equivalent. Divergence: incompatible persisted-store schemas and different winners in the A-vs-B race — **Major**.
9. **`argsHash` canonicalization and `queryArtifact` representation.** No `argsHash`/`args_hash` exists anywhere in the tree today; the RFC says "canonicalized args" without naming the canonicalization (same fork as decision 5, plus: is it `sha256:` hex per `mutation_input_fingerprint` precedent or bare?). `queryArtifact` — per-function generated-artifact hash vs (functions-manifest hash + function name). Picked: JCS + `sha256:`-hex; per-function artifact hash from the served functions manifest. Divergence: server-internal within one arm (mint and admission are the same instance) but contract-level across arms — **Moderate**.
10. **Local-arm `generation` semantics contradiction.** "One rotation rule: the digest changes exactly when any bound component changes" vs "on the local arm … rotating on every schema/functions ensure". A content-derived digest does *not* rotate on a no-op ensure; a per-ensure nonce rotates even when nothing changed (needlessly refusing every token across a dev-loop ensure). Picked content-derived (the "exactly when" sentence is the rule; "every ensure" read as "recomputed at every ensure"). Divergence: dev-loop resume hit-rate differs drastically and acceptance fixtures for step 5 pass/fail differently — **Moderate**.
11. **"Resume-relevant configuration" enumeration.** Which config participates in `generation`? Candidates range from nothing to journal policy + auth mode + route manifest + digest-contract version. Under-inclusion admits resumes against changed semantics (correctness); over-inclusion over-rotates (availability). Picked the four named in 0A.5. Divergence: differing rotation behavior, one direction correctness-relevant — **Moderate**.
12. **Key rotation overlap.** D1.1 gives retired keys a distinct refusal code, implying refusal — but a keyring normally verifies under recently-retired keys for an overlap window; a cliff rotation refuses the whole fleet's tokens on every key rotation (a `generation`-rotation-sized event the Scalability section never counts). Picked: 2 retained keys / 14-day overlap; the refusal code applies past the window. Divergence: fleet-wide behavioral difference at every rotation — **Moderate**.
13. **Key custody picks.** The RFC names the option set ("Worker secret vs DO storage vs local store") and defers the choice to 0A. Picked DO storage (Cloudflare) and a `secure_file` keyring (local). Divergence: rotation ergonomics and restart-survival semantics differ — **Moderate** (explicitly delegated, but the options are not equivalent).
14. **Sequence-sensitive digest construction.** "Computed over the full replacement" — over what bytes? Picked SHA-256 over JCS of the ordered rows array with a domain prefix. Any deterministic shared choice works; divergent choices are incompatible across the client/server boundary — **Major** by the parity argument of decision 5, though it is a smaller surface (verification only at relaunch).
15. **Leaf-encoding injectivity.** The RFC pins `H(canonicalRowId || rowHash)`; bare concatenation of a variable-length id with a fixed 32-byte hash is parseable-from-the-right and thus injective, but only if both sides agree there is no length prefix/domain tag; repo precedent (`auth_fingerprint`, lease transcript) length-prefixes everything. Picked length-prefixed + domain-tagged. Divergence: incompatible digests — **Major** (folds into the digest-parity cluster; listed separately because the RFC's own notation invites both readings).
16. **Persistence debounce bound, budget values, token size cap, refusal-code names, `authPartition` absent-encoding.** All knobs the RFC either names as knobs or leaves silent (the resume refusal codes get a namespace nowhere, unlike `SNAPBACK_BUNDLE_*`). Picked: 1 s/10 s, 32 MiB/256 entries, 1 KiB, `SNAPBACK_RESUME_*`, tagged-absent in the transcript. Divergence: cosmetic-to-edge-behavioral — **Minor** each.

## 4. Spec gaps the RFC should close

The subset of the log that belongs in the RFC text or the 0A checklist itself (the checklist currently names topic areas; these are the places where even the checklist doesn't name the question, or the RFC's own pinned text is self-inconsistent):

1. (Decision 4) Add an issued-at field to the pinned `tokenBody` schema — or state that expiry derives from key-id epochs — one sentence: "`tokenBody` additionally carries `issuedAtMs`, the expiry anchor."
2. (Decision 8) Widen `meta` to carry `queryArtifact` and `argsHash` (or restate D3's channel-arbitration rule in terms of the external-store identity key), since the client cannot read the opaque token: "`meta` repeats every identity field the D3 arbitration compares."
3. (Decision 1) State that the token is self-describing (body + keyId + MAC in one opaque envelope) and that `meta` is never an admission input: "the server decodes the body from the token; `meta` is client-advisory only."
4. (Decision 7) State the published `contentDigest` form: "the wire/store digest is a fixed 32-byte compression of the incremental state; the full state is held server-side (and recomputed client-side at verification)."
5. (Decisions 5/15) Name the canonical encoding and make the leaf injective in the RFC text: "canonical row encoding is RFC 8785 JCS; leaves are `H(domainTag || len(rowId) || rowId || rowHash)`."
6. (Decision 6/14) Pin the digest constructions by name and parameters in the 0A checklist ("LtHash-16, 1024×16-bit LE lanes, BLAKE3-XOF leaf expansion; ordered digest = SHA-256 over the JCS rows array"), not just "LtHash-class".
7. (Decision 10) Resolve the local-arm generation sentence: "the local arm recomputes the content-derived digest at every ensure (a no-op ensure preserves it)" — or explicitly choose per-ensure rotation and count its cost.
8. (Decision 12) State whether key rotation has a verification-overlap window, and that the retired-key refusal code applies only past it: "the keyring verifies under the N most recent keys; older keys refuse with the retired-key code."
9. (Decision 11) Enumerate (or explicitly delegate with a placeholder list) the "resume-relevant configuration" components of `generation`.
10. (Decision 16) Name the resume refusal-code namespace (`SNAPBACK_RESUME_*`) to parallel the already-named `SNAPBACK_BUNDLE_*`.

Not gaps: the `versionStream` crosswalk is fully dischargeable from code (`ensure_data_version_stream_in` exists independently of auth-mode installation, UUIDv7, rotated in the reset transaction), and the MAC-scheme/custody/expiry-value delegations are legitimately 0A's to decide — the checklist names them.
