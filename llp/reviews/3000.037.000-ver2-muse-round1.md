# VER2 review: NOT READY

One material functional defect makes the session-reuse cache inert, and it contradicts the amendment's own test. I did not edit files or run tests; all findings are from static reading of the diff, the two untracked files, and LLP 3000.037.000 §18.

## Material gap 1: hook records nothing — strict npm argv match can never hold

[snapback4/crates/snapback4/src/verbs/init/verify-cache.mjs:110](snapback4/crates/snapback4/src/verbs/init/verify-cache.mjs:110):

```js
if (npm.argv.join(' ').trim() !== `npm run ${phase}`) return;
```

This requires the npm ancestor's `/proc` cmdline to be exactly `npm run acceptance` (or `frontend:proof`). That is unreachable in practice:

- `argv[0]` is the resolved script path, never bare `npm`. Confirmed on this machine: `npm` resolves to a `#!/usr/bin/env node` JS file, so the cmdline is `<full-path>/npm run …` at best.
- Every invocation in the feature's own flows carries npm flags. [verify.mjs:42](snapback4/crates/snapback4/src/verbs/init/verify.mjs:42) spawns `npm run --silent <phase>`, and the new [test](snapback4/packages/snapback4/test/ver2-routing.test.mjs:26) runs every phase via `npm run --silent <phase>`. The joined cmdline is therefore `… run --silent acceptance`, which the strict equality rejects.

Consequence: `before` never saves a pending digest and `after` never mints a receipt, so `reusePhase` is always false. The Muse-lane test expecting `acceptance (reused), frontend:proof (reused)` ([test:36](snapback4/packages/snapback4/test/ver2-routing.test.mjs:36)), the corrupt-cache test expecting `frontend:proof (reused)` ([test:58](snapback4/packages/snapback4/test/ver2-routing.test.mjs:58)), and the slow-mutation test's reuse counts cannot pass. The amendment blesses this strictness in prose ("Extra script arguments do not record reusable passes", §18), but `--silent` is an npm flag, not a script argument — and the amendment's own lane evidence depends on `--silent` runs recording. Implementation, amendment prose, and test disagree; at least two of the three must change. Suggested direction: match argv modulo the npm executable prefix and known npm flags (or gate on `npm_lifecycle_event`), keeping the deliberate exclusion of real extra script arguments.

## Material gap 2 (consistency): amendment promises adapt behavior the code does not deliver

§18 says "Existing app-owned scripts are not rewritten by adaptation." That half holds — [proof.rs:211-222](snapback4/crates/snapback4/src/verbs/init/proof.rs:211) only copies allow-listed keys. But nothing in `plan()` ever *adds* the VER2 surface to an existing app: `preacceptance`/`postacceptance`/`prefrontend:proof` keys are not in the merge allowlist, `scripts/verify-cache.mjs` fails the additions filter when the file already exists or is unreferenced ([proof.rs:242-255](snapback4/crates/snapback4/src/verbs/init/proof.rs:242)), and the updated `verify.mjs` (progress heartbeat, `rerun:` naming) is likewise never delivered to an existing checkout. So the whole existing fleet stays on VER1 permanently with no path forward, while §18, the [CHANGELOG](snapback4/packages/snapback4/reference/CHANGELOG.md), and the [guides](snapback4/crates/snapback4-lang/src/guide/start.md) describe the new loop as *the* proof loop. Either scope §18 explicitly to fresh starters (and say the fleet stays VER1), or add an adapt path for the hook scripts plus the two `verify-*.mjs` files. The brief's "hooks survive business-command replacement" holds for fresh starters (hooks are separate script keys written by [verify.rs:22-25](snapback4/crates/snapback4/src/verbs/init/verify.rs:22)); this gap is about every other app.

## Checked and sound (no change requested)

- One proof route, refusal-first bounded summaries: `verify.mjs` preserves the CALLS1 ordering, six-line refusal cap, and 3/9-line summaries; the steps line gains `(reused)`/`rerun:` naming per §18.
- Five-second progress: per-phase `setInterval` with `clearInterval` in `finally`; fast phases correctly emit no heartbeat, matching the test's 3-line expectation.
- Check/probe always execute: only `acceptance`/`frontend:proof` have receipts; `phaseKey` returns undefined otherwise.
- Worker lifetime custody: spawn/IPC/`unwatch.check()`/signal handling untouched.
- Conservative invalidation: unknown files/dotfiles/locks hashed, root-only exclusions match §18 exactly, symlinks outside `node_modules` force misses, env/Node-version/project-path/owner-pid+birth+boot bound, 2h absolute expiry, corrupt/oversize receipts rejected, hook exceptions swallowed so cache I/O cannot flip a verdict to pass.
- Before/after pairing correctly rejects mid-proof source edits (pending-key comparison).
- `PREVIOUS_49_README_PROOFS` chaining preserves historical-README recognition; no runtime/binder files touched, per the authorization.

## Minor suggestions (not blockers)

- Pre/post hook commands have no `|| true` guard: a corrupted `verify-cache.mjs` (or future Node syntax break) would fail every proof via npm lifecycle semantics. Current `try/catch` covers runtime errors, not load-time failure. Fail-closed is the safe direction, but one guard word would keep it purely an optimization loss as §18 claims.
- `session()` depends on `uv_set_process_title` rewriting `/proc` cmdline for the test's `process.title = 'muse'` trick to work. It does on Linux, but that coupling is subtle and worth a one-line comment in the test.
- Pending files from failed runs linger (bounded, inside ignored `.snapback4/`); harmless.
- Reused phases are not revalidated at loop end, so a source edit landing *during* `verify` after a reuse decision is only caught on the next run. Same staleness class as VER1 mid-run edits; consider documenting the window or re-checking keys after the loop.
- Nested `dist/`/`target` trees are fully content-hashed (only root names are excluded). Correct but potentially slow on large trees; a depth-aware exclusion would be a pure perf win.

Verdict stands at **NOT READY** on gap 1 alone; gap 2 needs an author decision on fleet scope before landing.
