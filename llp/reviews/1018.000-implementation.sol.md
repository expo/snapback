### P1 — `sorted(a, b)` preserves authored order, so its canonical-pair contract is false

**Files:**

- `snapback2/packages/compiler/src/quarry/bound.ts:153-160,857-866`
- `snapback2/packages/compiler/src/quarry/direct.ts:84-86,155-168`
- Reachable caller: `snapback2/packages/compiler/fixtures/quarry-clique/snapback/chat.q:5-15`
- Constraint relied upon by the caller: `snapback2/packages/compiler/fixtures/quarry-clique/snapback/schema.q:120-126`
- Missing reversal witness: `snapback2/packages/compiler/src/quarry-direct-core-checks.ts:293-295,481-496`

The direct binder special-cases a two-name `sorted` binding, but `sortedPair()` only builds `{ first: left, second: right }`. The generic object lowering then preserves those positions. No comparison, `Min`/`Max`, or sort operation exists on this path.

This contradicts the language contract and its shipped use. The frozen Quarry specification defines `sorted(a, b)` as “a pair in order,” and the Clique design states that `sorted(viewer, u)` plus `unique lo, hi` is the canonical unordered DM identity. The public fixture uses exactly that construction. If Alice opens Bob and Bob later opens Alice, the current compiler emits `(alice,bob)` and `(bob,alice)`. The unique `(lo,hi)` constraint sees distinct keys, so two DM conversations can be created for the same user pair.

The direct regression does not exercise this behavior: it passes two already ascending generated IDs and asserts only that both operands execute once from left to right. Its “legacy” comparison is produced through the same current project route and therefore is not an independent semantic oracle. The deleted generated-TypeScript route also preserved operand order, but this review is assessing the documented Quarry contract; retaining that old defect is not conformance.

**Fix direction:** represent a sorted pair explicitly in the bound form. Lower by capturing the left operand and then the right operand exactly once, then derive the two outputs using the engine's total ordering (`Min` and `Max`, or an equivalent single sorted-pair IR operation). Validate compatible comparable operand types. Add a reversed-principal execution witness through native certification and the twin evaluator, while retaining a side-effecting operand-order witness.

### P1 — one timed-out status probe latches `writer-unresponsive` and prevents its own recovery

**Files:**

- `snapback2/packages/snapback2/src/client-forwarding.ts:311-331,524-536,595-616,691-693`
- Existing adjacent coverage: `snapback2/packages/snapback2/tests/client-sessions.test.ts:237-275,838-975`

`status()` returns immediately whenever `this.unresponsive` is true (`:316`). A two-second status timeout deletes its waiter and sets that same flag (`:322-324`). Because subsequent status calls return before `discover()` and before posting a new status request, the follower cannot prove that the same writer has recovered. A late answer cannot help because its waiter was deleted and the receive path ignores it (`:609-616`). Only an unrelated valid writer announcement or another lifecycle transition calls `updateUnresponsive()` and clears this status-only latch.

Reachable trigger: a writer remains current and healthy but its status answer is delayed or dropped past the timeout. The first readiness call reports `writer-unresponsive`; all later readiness checks return that result without probing. A Composer that gates mutation admission on readiness can remain disabled indefinitely even though no mutation has an unknown admission outcome and the writer is responsive again.

This is separate from the disclosed false-to-false notification loop. Making notification conditional removes repeated React invalidation but does not make a status-only timeout recoverable. It also differs from a mutation timeout: a mutation timeout must retain request ownership until acknowledgment/expiry, while a status probe has no durable admission ambiguity to retain.

The successor-writer test proves that a new writer announcement retires a predecessor waiter. The long recovery test correctly proves that an unknown mutation continues to report unresponsive until its own recovery. Neither test covers a dropped status answer followed by recovery of the same current writer with no timed-out command.

**Fix direction:** keep mutation-command unresponsiveness tied to its retained command, but give status-only unresponsiveness a bounded re-probe path. After a cooldown, allow discovery/status against the validated current writer and clear the status-only state only on a matching response or current-writer announcement. Add a fake-bus drop/restore test and an actual two-tab freeze/thaw witness showing that the same writer eventually returns to ready, without reintroducing notification churn.
