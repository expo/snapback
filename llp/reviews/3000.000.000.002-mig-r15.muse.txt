## Finding 1 — Same-name redefinition after a gap escapes refusal

RFC §2 requires that changing a declaration under the same name refuses with a bridge/new-name repair, and that a new name denotes a new transformation.

The store check in [backfills.rs](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/store/backfills.rs:64) compares only the immediately previous schema. A declaration removed for one or more releases, then re-added under the same name with a different body, is treated as fresh entering input. No refusal fires.

History to consult is already durable. Every known digest is retained in `_backfill_evidence`, `_backfill_pruned`, and `_backfill_definitions`. The fix is to refuse when any retained definition shares the table and name with a different digest, not just the immediate predecessor.

## Finding 2 — Re-entry silently overwrites same-column edits made while absent

RFC §3 step 4 requires recompute only when current outputs equal the saved result or the reversed preimage, and refusal otherwise.

In [backfills.rs](/home/ccheever/projects/sb4-b17-mig/snapback4/crates/snapback4-core/src/store/backfills.rs:196) the conflict branch fires only when dependencies changed. When arguments and recomputed outputs are unchanged but the current same-column value equals neither the saved result nor the preimage (edited while the declaration was absent, prior inactive), the code falls through and stages the recomputed patch. The manual edit is overwritten without refusal.

Added columns are safe. That branch preserves current cells when the preimage is absent. The hole is specific to overwritten (same-column) outputs with an inactive prior. The fix is to refuse in the unchanged-dependency branch when current equals neither saved result nor preimage, for columns with a recorded preimage.
