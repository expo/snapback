1. **High — Another live tab can take the reloaded tab’s terminal receipt permanently.**  
   Location: [web.ts:375](snapback4/packages/snapback4/src/web.ts:375).

   Concrete scenario: primary A remains open; secondary B commits a write and closes. Before replacement C opens, A applies a sync page and adopts B. Adoption copies B’s terminal history into A, then removes B’s store at line 385. C receives a fresh tab store. Orphan enumeration only visits `:tab-` stores, so A’s primary store is never considered; even another secondary adopter remains inaccessible while live. `client.write(id)` reads only its own history/outbox [local.ts:1104](snapback4/packages/snapback4/src/local.ts:1104).

   This is a concrete interleaving compatible with the failing test’s live primary, and a plausible explanation for its intermittent failure—not proof of that particular run’s cause.

   **Smallest fix:** preserve discoverable receipt-only custody after transferring the exclusive outbox, or put terminal receipts in bounded shared history accessible by ID. Add a deterministic test that forces A to adopt B before opening C; assert recovery and exactly one server application.

2. **Medium — The bounded lock wait still permits indefinite missed recovery.**  
   Location: [web.ts:313](snapback4/packages/snapback4/src/web.ts:313).

   Concrete scenario: a closing tab keeps its lock beyond all ten 20-ms retries during replacement startup/acquisition. Adoption skips it. The lock then releases, but the backend stays quiet. Unchanged heartbeat polls do not trigger another sync/apply [local.ts:722](snapback4/packages/snapback4/src/local.ts:722), and receipt polling does not retry adoption. The receipt remains unavailable until another qualifying event.

   The named test awaits `close()`, whose implementation awaits lock release; this mechanism alone should not explain that exact ordering. It nevertheless remains a real teardown window.

   **Smallest fix:** retain retry responsibility for busy orphan candidates independently of server changes, without blocking indefinitely or adopting a live owner. Test a controlled lock release after the final attempt with no subsequent backend writes.

3. **Medium — The maintain recommendation omits material ranking differences.**  
   Location: [feeds.md:949](snapback4/crates/snapback4-lang/src/guide/feeds.md:949).

   Concrete scenario: today has one original post and no likes. The surrounding recipe promises zero-like candidates, but `count likes` creates no group, so this maintain returns nothing. Removing a final contribution also removes the count row [maintains.rs:175](snapback4/crates/snapback4-core/src/engine/maintains.rs:175). Equal scores order by maintained ID, not the preceding recipe’s post-time tie-break. Consequently, “use the handwritten table … only” for rolling windows or non-count/sum scores is too restrictive.

   **Smallest fix:** explicitly describe this as a current-calendar-bucket ranking of positively liked originals with maintained-ID ties. Name zero-like candidates and post-time tie-breaking as additional requirements needing another design. Explain that app mutations must derive the denormalized facts from the authoritative post; the maintain cannot validate their truth. Add behavioral tests for zero likes, equal scores and immediate first/last-like transitions.
