## Findings

### 1. High — Deferred recovery reuses submission numbers and permits reordering

**Location:** [web.ts:164](snapback4/packages/snapback4/src/web.ts:164), [web-journal.ts:164](snapback4/packages/snapback4/src/web-journal.ts:164).

**Scenario:** Reopen a store with two journal records and `backend_required` set—for example, navigation interrupted replacement-backend adoption. Initial recovery skips them. `local.ts:272` caches `submissions = 0` before startup sync. Adoption then recovers A and B as submissions 1 and 2, but does not update that cached counter. The next `mutate`, C, also receives submission 1.

The memory outbox permits this duplicate sequence and sorts by sequence. The in-memory host probe produced **A:1, C:1, B:2**. If delivery is unavailable and the durable queue subsequently replays, C can apply before B.

**Smallest fix:** Reconcile submission allocation after deferred recovery and before accepting successors. Recovery and ordinary admission must share a monotonic allocator that cannot reuse queued sequence numbers.

**Missing test:** Start with two matching-store journals behind `backend_required`; complete adoption, admit a successor while transport is unavailable, then reconnect/reopen and assert application order **ABC**.

### 2. High — Lazy merge predicates use the last discovery row for every expanded lane

**Location:** [bind/program.rs:541](snapback4/crates/snapback4-lang/src/bind/program.rs:541), reaching [read.rs:825](snapback4/crates/snapback4-core/src/engine/read.rs:825).

**Scenario:** The binder accepts a header predicate referencing the lane’s loop binding:

```quarry
return merge items after c first 20 by byOwnerTime where .body = p.wanted:
  [p.owner] for p in selectors[viewer] first 2 by byReaderOwner
```

With uniform lanes, plain lexical prefixes and selectors `(owner A, wanted red)` then `(owner B, wanted blue)`, this qualifies for lazy merging. Lane discovery freezes each prefix but leaves `p` in one shared environment. All later predicate evaluations therefore see the **last selector**, B/blue.

An A/red item is incorrectly omitted; an A/blue item can be returned. The page can report complete and advance past the wrongly rejected match. The published Following recipe avoids this specific failure because its named-table lane selects the eager path.

**Smallest fix:** Exclude source-dependent filtered lanes from lazy merging, using the existing eager path until expanded lanes retain their own binding environment.

**Missing test:** The query above, with different selector predicates, on server and both device stores; include pagination and compare eager/lazy results.

### 3. High — A backend-required orphan journal has no recovery path

**Location:** [web.ts:309](snapback4/packages/snapback4/src/web.ts:309).

**Scenario:** A secondary tab observes replacement store S, captures a write, and closes before installing S’s backend. Its persisted state has S’s identity plus `backend_required`.

A healthy destination already using S reconstructs the orphan with its **kept backend only**. `recover` immediately returns because `backend_required` remains set. There is no outbox entry to transfer, and the surviving journal causes the orphan database to be retained. Every subsequent adoption repeats the same sequence; destination backend adoption never repairs the source.

The in-memory host probe remained at **destination queued=0, journal=1, source backend-required=true** after destination adoption and another apply.

**Smallest fix:** Under the orphan’s lock, install the authenticated matching backend before recovering its journal. Preserve separate mismatch retirement and same-store restore refusal handling.

**Missing test:** A journal-only orphan interrupted between store observation and backend adoption, recovered by a healthy client on that same store.

### 4. Medium — Failed refusal bookkeeping leaves an executable journal record

**Location:** [web-journal.ts:116](snapback4/packages/snapback4/src/web-journal.ts:116), [web.ts:163](snapback4/packages/snapback4/src/web.ts:163).

**Scenario:** Capture succeeds. Prediction subsequently returns an authored refusal. `removeItem` now throws, so `refused` requests an IDB transfer marker; that save also fails.

The host throws instead of returning the known refusal, and the original executable record survives without a marker. If the authored condition later changes, recovery can admit and send the previously refused write. The probe confirmed the known refusal becoming an IDB rejection with **one journal record remaining**.

The documented storage fallback discusses possible loss before admission, not resurrection after a known refusal.

**Smallest fix:** When removal fails, persist a bounded, non-executable cancellation marker synchronously where possible. If neither store can record cancellation, explicitly document an indeterminate outcome; do not promise preserved terminal refusal.

**Missing test:** Combined removal and IDB failure after a state-dependent refusal, followed by changed state and reopening.

### 5. Medium — Missing Web Locks permits recovery of a live tab’s journal

**Location:** [web.ts:57](snapback4/packages/snapback4/src/web.ts:57), with [web.ts:266](snapback4/packages/snapback4/src/web.ts:266).

**Scenario:** Without `navigator.locks`, both clients use the same store name. A captures a write and remains alive with its admission save blocked. B opens that store; its separate `admissions` set does not contain A’s ID, so initial recovery admits A’s journal.

The probe confirmed **B holding A’s queued write while A’s admission remained blocked**. Thus the “never a live tab’s” guarantee does not hold in this explicitly implemented fallback. Different local snapshots can also produce conflicting prediction/refusal outcomes.

**Smallest fix:** Require exclusive ownership for journal capture/recovery, and disclose best-effort navigation when Web Locks are unavailable.

**Missing test:** Two live owners without Web Locks, with the first admission held; verify the second cannot recover or send it.
