### Verbatim review body

Provenance note: an overbroad search accidentally surfaced matching lines from `llp/reviews/` despite an intended exclusion. I did not use those snippets. The findings below were independently re-established by context-isolated Codex-family passes that never accessed that directory. Assessment: the compression direction is credible, `contentHash` is unchanged, and the approximate 1:1 binary saving is real. The RFC is not ready because its recommended encoding/granularity, loader model, security contract, and Phase 2 composition do not currently agree.

1. `MATERIAL` — §2, §3, §6 — Phase 2 is not “indifferent” to compression.

   The frozen plan pins `guide/embedded-guide.v1.bin`, requires one deterministic encoder shared by build-time and pack-time callers, and authenticates the exact container through `artifactSha256` ([0314.000:305](/Users/ccheever/projects/snapback/llp/0314.000-reduce-shipped-runtime-size.plan.md:305), [0314.000:320](/Users/ccheever/projects/snapback/llp/0314.000-reduce-shipped-runtime-size.plan.md:320), [0314.000:358](/Users/ccheever/projects/snapback/llp/0314.000-reduce-shipped-runtime-size.plan.md:358)). Compression preserves logical `contentHash`, but necessarily changes `artifactSha256`.

   The RFC also says it retains the exact `...\x01` magic while bumping the format ([0314.002:104](/Users/ccheever/projects/snapback/llp/0314.002-compress-the-embedded-guide-artifact.rfc.md:104)); today `\x01` is the version byte ([guide.rs:20](/Users/ccheever/projects/snapback/crates/snapback-server/src/guide.rs:20), [build.rs:187](/Users/ccheever/projects/snapback/crates/snapback-server/build.rs:187)). Gzip headers can carry filename/mtime, and the RFC does not require canonical metadata, codec backend/version, or level.

   Suggested fix: choose landing order and v2 naming, reconcile the frozen v1 pin, state that `artifactSha256` rotates while `contentHash` does not, and require byte-identical canonical output from both Phase 2 encoder callers.

2. `MATERIAL` — §Summary and §4 OQ1/OQ2 — the recommendations compare unmatched compression granularities.

   Re-measurement over the same 187 files and 20,658,338 source bytes produced:

   | Encoding | Whole stream | Per-record payloads |
   |---|---:|---:|
   | gzip `-9 -n` | 3,452,614 | 3,608,417 |
   | zstd `-19` | 1,128,188 | 2,838,299 |

   Container framing adds roughly 8.4 KB before the proposed new fields. Under the recommended per-record design, zstd saves about 0.77 MB over gzip—not the stated 2.2 MB. Conversely, gzip’s whole-versus-per-record penalty is only about 0.16 MB, so OQ2’s “cross-record redundancy is large” claim is false for gzip. Comparing the top five per-record outputs with the entire whole-corpus output proves nothing ([0314.002:132](/Users/ccheever/projects/snapback/llp/0314.002-compress-the-embedded-guide-artifact.rfc.md:132)).

   Suggested fix: present a matched 2×2 matrix, include decoder/link cost, and decide encoding and granularity jointly after the OQ3/OQ4 measurements.

3. `MATERIAL` — §3.2, §4 OQ2, §6 — “no consumer migration” contradicts the proposed lazy LRU.

   The current API exposes `bytes: &'static [u8]`, a static corpus slice, and static records ([guide.rs:26](/Users/ccheever/projects/snapback/crates/snapback-server/src/guide.rs:26), [guide.rs:48](/Users/ccheever/projects/snapback/crates/snapback-server/src/guide.rs:48)). HTTP constructs bodies directly from those static bytes ([server.rs:10449](/Users/ccheever/projects/snapback/crates/snapback-server/src/server.rs:10449)); native Guide search scans every Markdown record ([guide_command.rs:46](/Users/ccheever/projects/snapback/crates/snapback-cli/src/cli/guide_command.rs:46)); MCP catalog construction calls `guide::file()` for every declared page/resource ([guide_mcp.rs:121](/Users/ccheever/projects/snapback/crates/snapback-cli/src/guide_mcp.rs:121)); reference lookup reads and retains both large registries ([guide_reference.rs:31](/Users/ccheever/projects/snapback/crates/snapback-server/src/guide_reference.rs:31)).

   An evicting LRU cannot safely back outstanding `'static` borrows. Eager decompression preserves the API but retains roughly the entire corpus; lazy decoding requires an owned/fallible accessor and internal consumer/test migration.

   Suggested fix: narrow “no migration” to external URLs, bodies, headers, MCP protocol, `check-guide`, and docs-site behavior. Explicitly choose eager retained bytes or an internal metadata/owned-byte API migration.

4. `MATERIAL` — §4 OQ4 and §6 — the security and resource model is missing.

   LLP 0284 requires canonical paths, minimum closure, UTF-8 validation of every Markdown/JSON record, manifest validation, and decoded core-hash agreement before exposing any record ([0284:629](/Users/ccheever/projects/snapback/llp/0284-workspace-security-gate-threat-model.spec.md:629)). Current parsing performs that all-record pass ([guide.rs:109](/Users/ccheever/projects/snapback/crates/snapback-server/src/guide.rs:109)). OQ4’s question about decompressing only eight required records therefore understates the contract.

   Phase 2 separately requires total-size and record-count/length ceilings for an externally loaded sidecar ([0314.000:358](/Users/ccheever/projects/snapback/llp/0314.000-reduce-shipped-runtime-size.plan.md:358)). An uncompressed-length field alone does not prevent expansion bombs, oversized allocation, concatenated members, or trailing compressed data, contradicting §6’s “no new failure mode” claim.

   Suggested fix: require bounded encoded, per-record decoded, and aggregate decoded sizes; exact decoded-length/EOF checks; rejection of unknown encodings/trailing members; and a streaming all-record validation pass before exposure. Measure first Guide initialization separately from process readiness.
