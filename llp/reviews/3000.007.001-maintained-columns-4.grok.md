## Findings

### 1 — Medium — §3.2 projection / §3.11 activation — `successor.rs:190–213`, `device.rs:377–393`

**Gap.** The derivation identity is the right artifact, but revision 4 does not pin it to a location `keeps_literal_default_images` actually compares, and §3.11 still explains snapshot re-acquisition as “`keeps_literal_default_images` is false when **maintains differ** and the column has no authored default.” On the public projection there are **no** private maintains (`from.maintains != to.maintains` is false for a redefinition). Addition still fails the function because the column is required and not a `ColumnDefault::Literal` (`successor.rs:195–196`). Redefinition of kind / source / predicate / `by` without a column-type change does not.

`Device::adopt` (`device.rs:377–393`): `keep_images = keeps_literal_default_images(...)`; `install_checked(..., reset && !keep_images)`. If `keep_images` is true on a generation change, rows are kept, watermark resets, and `keep_acquired` can stay true when table counts match. Activation is event-free, so parents that only ever arrived in a snapshot and never took a later put keep the **old** total. That is the case the identity exists to prevent.

**Failing scenario.** `likeCount: count likes by postId` is redefined to `count likes where .active = true by postId`. Server rebuilds and mirrors; generation advances; no row events. The projection still has `posts.likeCount: int`, no private maintain. A device that snapshot-acquired a post which was never liked again keeps the unfiltered count.

**Smallest design change.** State that the derivation identity is a field of the **projected table or column** (so `Table`’s `PartialEq`, and therefore the projection step at `successor.rs:200–211`, sees it) — not a sidecar on the `/schema` JSON envelope. Replace §3.11’s “because maintains differ” with “because the derivation identity changed, or the column has no authored default.” Add the §8 line: redefining kind / source / predicate / `by` does not satisfy `keeps_literal_default_images`.

### 2 — Medium — §3.2 “never synced” — `bind/schema.rs:33–47`, `device.rs:571`

**Gap.** The generated maintain is a `Maintain` in `Schema.maintains` with a source that, in the Clique case, is `sync public`. Today’s inherit loop copies that audience onto any generated target whose `by` matches (`bind/schema.rs:33–47`, `Audience::Public => true`). The RFC says the private maintain “has no read rule and is never synced,” but it does not name this loop. `Device::apply` errors `unknown table` on any stream event whose table is missing from the projection (`device.rs:571`).

**Failing scenario.** A lane reuses `bind_schema`’s inherit pass. The first like after adding `likeCount` appends `Put`s for the unspellable target to `public`. Every device on the public projection fails apply and cannot catch up.

**Smallest design change.** One sentence in §3.2: the generated maintain does **not** inherit the source’s `sync` (today’s `bind_schema` loop would copy `sync public` from likes); it is omitted from `Schema.synced()` on the server as well as from the projection.

### 3 — Low — §3.2 `visible` / doctor — `verbs.rs:559`

`doctor`’s compile-time “N tables” uses `bound.schema.tables.len()` on the complete schema. Physical row/byte totals are supposed to stay honest and say they include engine-internal storage; this line is a schema count, not that total, and would be off by one vs `check`. Filter it with `visible`, or have it say the same “includes engine-internal storage” sentence.
