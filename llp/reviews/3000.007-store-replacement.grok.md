The identity contract is the right one and is built in the device, both stores, the HTTP sync/change replies, and the JS client: a persistent 128-bit `store_id`, mismatch discards the partition in one transaction, unsent/unknown-receipt writes keep their ids without predicted images, known receipts do not replay, and generation-equal replacements still reload `/schema`. After a replacement **reply is processed**, local reads cannot publish the old partition as acquired. The remaining hole is live detection: `/changes` waits on sequence before it ever looks at identity, so a live web (and any streaming) client can keep answering the old rows as `fresh` and `complete` for the full long-poll wait after an equal-head `dev --fresh`.

## Findings

### 1 — High — `snapback4/crates/snapback4/src/serve_changes.rs:26` and `snapback4/packages/snapback4/src/local.ts:589`

**Gap.** Equal-head replacement on a live client is detected only when the long-poll **finishes**. The wait condition is `*seq > since || deadline` (`serve_changes.rs:26`). Identity is attached afterwards (`serve_changes.rs:46–59`). `/probe` does not carry `store_id` (`serve.rs:830–832`).

**Failing scenario.** Web (or any streaming) client is `caughtUp` on store A at watermark/seq 3. Operator runs `dev --fresh` and seeds three rows on B (head 3, new `store_id`). The in-flight poll to A dies (offline, `fresh` drops). Probe succeeds against B (`setLink("online")`). The next `/changes?since=3&wait=25` waits the full 25s because `seq` is not greater than `since`. Until that JSON arrives, `caughtUp` is still true, the device still holds A’s rows, and `client.query` / `observe().getSnapshot()` answer those rows as `{ fresh: true, complete: true }` (`local.ts:690–692`). Default wait is 25s (`local.ts:583`); chat-expo passes `waitSeconds: 20`. Non-streaming RN short-polls at 2s (`changes.ts:41–42`), which only shrinks the window. The live test uses `waitSeconds: 1` (`store-reset.test.mjs:59`) and only waits until B appears (`:129–132`), so it never asserts “A is not fresh while we are online to B.”

This is exactly the ticket’s live-app interleaving, bounded by `wait` instead of forever. §18.2 says long-poll replies compare identity so equal-watermark replacements converge without extra sync on an unchanged database — comparison happens, but not until the wait ends.

**Smallest fix.** Additive: accept `store_id` on `GET /changes`; if present and ≠ the engine’s id, break the wait immediately and return the new id (unchanged database still waits on `seq`). Client: pass `storeIdentity` when known, and after any reconnect issue one `wait=0` fetch (or put `store_id` on `/probe`) before resuming the long wait. Do not sync on every heartbeat when the id matches.

### 2 — Medium — `snapback4/packages/snapback4/src/local.ts:489`

**Gap.** On reset the client `void rerun(watch)` but does not synchronously replace `watch.snapshot`. `getSnapshot()` keeps the last successful object, including `fresh: true`, until the async rerun finishes. `serverAnswers` are cleared (`local.ts:480`); the watch cache is not.

**Failing scenario.** A React subscriber reads `getSnapshot()` in the same turn as the reset (or during finding 1’s wait). It still sees A’s 50 threads as fresh/complete. After observe, a device query would already be unacquired; the UI path does not.

**Smallest fix.** Before `void rerun`, set `watch.snapshot = { loading: true }` (or a coded non-value) and `notify(watch)`.

### 3 — Medium — `snapback4/crates/snapback4-device/src/device/store_identity.rs:23–25` and `snapback4/packages/snapback4/src/local.ts:520`

**Gap.** Backwards watermark resets only when `page.store_id.is_none()`. A legitimate older restore of the **same** SQLite file keeps `store_id` and lowers the head. Observe does not reset; apply/client then refuse a backwards watermark and retry forever. `query` is `fresh: false` once a sync round has started, but still `complete: true` on rows the restored server does not have; watches can remain on the previous fresh snapshot (finding 2). Restart of the same file, release activation and adoption do **not** false-trigger (finding table). This is not needless reacquisition; it is failed convergence (LLP 3000 §6.7) for a shrink of the same incarnation.

**Failing scenario.** Device applied through seq 100. Operator restores yesterday’s `store.sqlite` (same `_meta.store_id`, head 40). Stream returns watermark 40 with the same id. Client calls `observe_store`, `reset == false`, then `return false` at `local.ts:520`. Loop continues. User still reads the seq-100 partition.

**Smallest fix.** If `store_id` matches **and** `page.watermark < device watermark`, refuse with a stable coded message that names restore/shrink (do not silently keep `complete: true`), or treat same-id regression as reset — the latter is reacquisition of the same identity, which the brief asked not to do accidentally; a coded halt is the smaller change.

### 4 — Low — tests

Missing, concretely:

- Live replacement at equal head with **production** `wait` (25 / 20), asserting that no `query`/`observe` snapshot is `fresh && complete` with A’s rows after B is listening.
- Native/process `createLocalClient` (Expo `nativeDevice` / `native-e2e`) through a replaced backend — only wasm `webDevice` + in-process Rust stores are covered. The originating iOS witness was not rerun (journal).
- Client mid-paged-snapshot: `after` in flight, then `--fresh` (device staging is covered; the HTTP loop is not).
- Same-`store_id` lower head (finding 3).
- Watch `getSnapshot()` in the turn of `observe_store` (finding 2).
- `/changes?store_id=` early-return (after finding 1’s fix).

Red-before/green-after is documented in `snapback4/JOURNAL.md` (X1, 2026-09-14) for `replaced_backend` (0 pass / 2 fail → 2 pass) and `store-reset.test.mjs` (0/1 → 4/4) on both Rust stores and persisted wasm. This review did not re-execute those commands.

### 5 — Low — `snapback4/crates/snapback4/src/serve.rs:1018–1019`

Foreign snapshot `after` is cleared only when the request **echoes** a mismatched `store_id`. Additive story for old clients is otherwise right (omit request field; ignore unknown reply field). An old client still paging A’s `next` onto B can present a cursor the new server will try to decode (`E_INPUT` if opaque parse fails; skip if it happens to parse). New clients that have learned an id are fine. **Fix:** ignore `after` whenever `from == 0` and the cursor’s implied identity is unknown, not only on explicit mismatch — or document that mid-snapshot upgrade without `store_id` must restart at `after: null`.
