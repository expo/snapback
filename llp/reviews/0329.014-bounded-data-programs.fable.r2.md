# Round 2 — Claude Fable 5

### 1. The strongest objection to each proposal

**Fable (r1).** The per-op closure store. I keyed closures by `(PlanHash, args, principal)`, so a predicted `send` in a conversation whose `thread` is not currently subscribed — the inbox predicting its `lastMessage` — goes `partial` even when another op holds the rows, and every overlapping page is stored twice. P9's range-indexed store per `(table, index)` at one connection version makes coverage a property of *ranges*, not ops, and is sound because the server delivers all subscriptions on one monotone version stream. My TS evaluator also had no conformance story. The proposal survives with the store replaced and a conformance mechanism added (§4).

**codex.** `AllOrRefuse<T,N>` is an availability trap in the exact place the benchmark looks. `boardView` with `cards.allOrRefuse(1_000)` is green on seed data and seals the whole board — one snapshot, entire refusal — at card 1,001 in production; the agent's repair is to raise N until `check` refuses, after shipping. It is LLP 0120 variant 2 with its named weakness intact. It survives only re-paired: `AllOrRefuse` admitted solely when the schema enforces the cardinality on the write path (`columns.cap({ by: 'board', max: 64 })`, refused at insert), which turns it into variant 1 — exact over an admission-bounded domain — and makes the refusal a write-time invariant instead of a read-time surprise. Secondary: binding verdicts to `planHash + args` over-fragments them; `thread`'s membership verdict cannot serve `send`'s prediction.

**grok.** "Opaque verdicts are leases under another name; Clique must not need them" is right for membership and wrong as a rule. Any rule over a table the viewer may not read — `blocks[(author, viewer)]`, `mutes`, admin roles, "archived by an admin" — has no viewer-visible witness. Under grok's own "admitted ⇒ retainable," such a rule must either ship the hidden rows (a leak), refuse at `check` ("rule reads a table the viewer cannot read" — whose repair is to make `blocks` readable, P18 with a new table), or produce a verdict. A social app hits this at the first block feature. It survives by admitting verdicts for hidden-input rules, bound as in §2, with no deadline of their own.

**Orchestrator / P9.** "Pure computation cannot change the read shape or the bound because every read goes through the typed API" is false as stated. `for (const w of m.body.split(' ')) if (w.startsWith('@')) db.get(users.byHandle, w.slice(1))` keeps the read *family* static and makes the bound `200 × maxWords` — statically computable only if every derived collection carries a cardinality from a schema max (`text({max})`), and unbounded if `body` has none. And the key `w.slice(1)` is computed, so no prediction closure, no prefetch, no set-oriented lowering for that site. P9 needs two rules it does not state: loop domains must be typed-cardinality collections *including derived arrays*, and read keys must be shape expressions. Its substrate has a second hole: "one interpreter compiled twice" reaches Hermes only through a native module — Hermes does not execute WebAssembly **[inferred; verify]** — which is a custom dev client, i.e. the dev-loop cost that lost Clique milestones. It survives with the two rules and a TS client evaluator.

**P4 (0329.005).** On guarantees it is sound; on the benchmark axis it loses where Familiar lost. The B-half is 55 of 100 points; a builder in which `rows.filter(r => …)` is `LANG_OPAQUE` and Split's rounding write is a `Page.forEach` contortion spends the agent's first hour on the type system. P4 concedes this in its own "Bad" list. It also conflates the static family with the concrete closure (codex's point 2). It survives as the *IR*, not as the spelling.

### 2. The crux, re-litigated

All four answers agree in substance and differ in precision; codex's containment is the cleanest statement, grok's two artifacts name the objects, P9 is right that the claim is "true of the text, false of the execution" but understates prediction, and mine supplies the missing artifact. The shared fact I propose:

> A recorded execution trace — index ranges with stop-reason (`limit` / `exhausted`), including empty ranges; the viewer-visible rows examined, including one halo row past each window; and dependency-keyed verdicts for rules over hidden inputs — permits exact local replay of that execution at its snapshot, and permits local re-execution after client-local writes **exactly while `Reads(P, D₀ ⊕ Δ) ⊆ Coverage(trace)`**. A read outside coverage is detected and reported `partial`; nothing is invented. What a trace cannot supply is coverage for reads that a not-yet-existing row or a flipped branch would issue. That coverage is computable at `check` — the **prediction closure** — only for read sites whose keys are *shape expressions* (args, `viewer()`, literals, fields of rows read at a traced site, composed by total scalar functions), and is `partial` otherwise, visibly in the certificate.

Boundary conditions to adopt with it:

- *Dependent reads driven by computed values.* Admitted, traced, invalidated precisely, retained; excluded from prediction closure and prefetch; `partial` if a local write steers execution into them. The certificate marks each site `prefix: shape | computed`.
- *Rule reads over non-viewer-visible rows.* The server retains the hidden dependency for invalidation; the client receives a verdict bound to `(ruleHash, pinned input values, principal, authEpoch)` — not `planHash`, not `args`, so `thread`'s verdict serves `send` when the compiler proves both rules pin the same inputs (`conversation`, `viewer`). When the write rule is not provably the read rule ("may read but muted"), the prediction closure carries a separate *may-write* verdict evaluated at subscribe time for the view's args. A verdict has no deadline of its own; it dies with the epoch or the store fence. That is the difference from a lease, and it answers grok: Clique's membership witness is a row or an absence range, never a verdict.
- *`partial` after local deletes.* Ship examined-visible rows, not returned rows: `take+1` already examined row M+1, so a one-row halo is free in trace size and adds no invalidation fan-in beyond the has-more probe the server already made. One local delete stays complete with `hasMore: unknown`; a second goes `partial`. Codex's halo is worth it at exactly one row.
- *Revocation.* Unobservable during a partition in every design; on reconnect the server re-evaluates the rule dependencies before outbox replay, retracts, and the client evicts rows held by no range. Prediction against a stale witness is a UI claim; authority rejects it.

### 3. Static vs. dynamic — the actual trade

Once both sides have shape-plus-bound at `check` and windows at run time, what the algebra still buys, and whether year one needs it:

1. **Key provenance by construction.** `nest` along a ref *is* the statement "the child key is the parent's id." Prediction closure, prefetch for unexecuted args, and vectorized lowering fall out. A bounded program gets the same property only via a key-provenance rule plus dataflow over the (small, loop-bounded, recursion-free) program. Year one needs prediction closure for offline `send`; it needs the *rule*, not the algebra.
2. **IVM** for select/project/join/nest/group. Every proposal ships rerun-and-diff in v1 with `maintain` as the only incremental path. Year two.
3. **Single-statement SQL lowering.** Irrelevant on in-process SQLite; matters on Postgres (2,000 point reads at 0.5 ms is a second). Recoverable for shape-keyed loop reads by batching (`= ANY`); computed-key sites stay program-near-DB. Year two.
4. **Reviewable closed predicates.** Rules are "who can see this row"; the diaries praise ceremony that caught category errors, and hoisting (evaluate once when the predicate's columns are pinned by an equality filter) is trivial over a predicate and heuristic over a program. Year one needs this — *for rules*.
5. **Semantic corners.** The algebra has a closed value model; a program needs one pinned: integers as i53 (JS-exact, SQLite-safe), strings compared by codepoint (= UTF-8 byte order; JS `<` is UTF-16 units), stable sort, `Map` insertion order, no `NaN`/`-0` observable, overflow refused. About a dozen items in a conformance corpus; a spec cost, not a guarantee.
6. **Static compute bound.** The algebra's scalar work is constant per row; a program needs a per-operation cost model over schema maxes or a runtime step budget. A step budget fails closed inside the transaction (abort = rollback) and is acceptable in year one.
7. **Compiler size.** Builder library versus off-the-shelf TS parser + ~30-node lowering + dataflow + cost model. Larger, not large.
8. **Agent prior.** Convex-shaped TS is inside the bounded-program subset and outside the builder. The benchmark's B-half is the product metric. Year one needs this most.
9. **Noninterference.** No difference: the data API filters hidden rows before the program sees them; `get`/`exists` on a hidden row is sealed absence; the budget-refusal side channel exists in both and is closed by making the ceiling a compile-time fact.

Answer to the round's question: **admitting pure computation and structured control flow between bounded typed reads threatens no guarantee, given three rules** — loop domains carry static cardinality (pages, literals, arrays derived from bounded columns); read keys are shape expressions or the site is marked `computed`; rule bodies are expressions of the algebra. What it costs beyond the builder spelling is IVM and single-statement lowering, which year one does not need, and a value-model spec, which year one must write either way.

### 4. Your updated position

**I moved**, from "algebra spelled as a build-time builder with `when`" to **TS-syntax bounded data programs lowered to an IR whose relational operators are the algebra and whose residual pure computation is bounded bytecode**, with rules restricted to algebraic predicates. Three things moved me: P9's observation that control flow can only *select among lexically fixed read sites* once every read goes through the typed API, so shape families and the bound survive `if` and `for`; my own worked examples — Split's rounding write and the unread count are loops, and the builder made them worse; and the realization that everything I wanted from the algebra (prediction closure, hoisting) reduces to key provenance, a rule on keys I can impose on programs. I did not move on the client evaluator language, and I moved *toward* codex on the fence.

*Spelling.* A TypeScript subset type-checked against a custom `lib.d.ts` (no `Date`, `Math.random`, `fetch`, `while`, recursion, dynamic property access on tables); `db.get`/`db.scan(index, prefix, {take})`/`db.exists`/`recurse`; `for` over typed-cardinality collections; pure computation with the pinned value model. Rules: `read: m => db.exists(memberships.byConvUser, [m.conversationId, viewer])` — single expressions, refused if they contain statements. Maintained aggregates are schema constructs. `AllOrRefuse` only with a write-path cap.

*Substrate.* Server: Rust interpreter over the IR inside the SQLite transaction; JS not in the authoritative path; effects sandboxed out of band. Client: a **TypeScript evaluator** in v1 — it runs in Expo Go, Hermes, JSC, V8, Node with no native module — plus a range-indexed store per `(table, index)` at one version, a verdict cache, an outbox. Conformance is enforced three ways: a corpus over the value model; the trace-⊆-certificate assertion on the server; and a **hydration replay check** — on every hydration the client re-executes the op over the shipped closure and compares to the shipped result, so interpreter divergence is detected in production and degrades to a result cache with a diagnostic. A Rust-to-WASM core is a later *web* option if it measures smaller; a native mobile core is never a v1 requirement, because it costs the dev loop.

*Fence.* One engine-owned, store-wide `maxOfflineAge` with a default (today's protected posture ships a 24 h hard maximum per the guide's lease section; a rebuild should not regress below a fence), shortenable per app, never per query, never disable-able to infinity. Codex is right that "stale until reconnect" with no bound is weaker than what ships; grok is right that it must not be a per-query object. Mechanism required, value a knob.

*Rule affordability.* The two-hop co-member rule is refused with a diagnostic that pastes two complete repairs and no third: (1) schema split — `profiles` under `public('handles are discoverable')`, `accounts` under `a.id.eq(viewer)`; (2) a maintained `contacts(owner, user)` closure from `memberships` with a write-side member cap (`conversations.cap({ members: 256 })`), the rule becoming `exists(contacts.byKey([viewer, u.id]))` at cost 1. A fan-out-capped rule (`memberships.byUser(u).take(K)`) is refused: it is semantically wrong past K. A v2 optimization can specialize the rule in context (authors of `thread(conv)` are witnessed by `memberships[(conv, author)]`), but v1 pastes the split.

*Certificate, minimal fields.* `planHash, schemaHash, ruleHashes, evaluatorVersion; readSites[{table, index, prefix: shape(expr) | computed, take, maxCalls}]; maxExamined; maxRuleProbes; resultType (cardinality-typed); maxSteps; maxOutputBytes; writeSites[{table, maxRows}]; maintainedAmplification; completeness: page | capped | maintained; predictionClosure[{transition, sites, verdicts}]; indexesRequired; lowerings`. Codex's list plus provenance and prediction closure; cardinality alone is not a cost proof.

*Worked delta — the unread inbox in the recommended spelling:*

```ts
export const inbox = query({}, ({ db, ctx }) => {
  const mine = db.scan(memberships.byUserActivity, [ctx.viewer], { order: 'desc', take: 50 });
  return mine.map(m => ({
    conversation: db.get(conversations, m.conversationId),
    unread: db.scan(messages.byConvTime, [m.conversationId], { after: m.lastReadAt, take: 100 })
              .countCapped(),                         // exact to 100, then "100+"
  }));
});
// bound: 51 + 50 × (1 + 101) = 5,151 examined; every prefix is a shape expression;
// prediction closure for markRead: memberships.byKey([conv, viewer]) — already held
```

### 5. Convergence candidates

Signable today by all four: row rules in the language as the only authorization, deny-by-default, `public(reason)` conspicuous and unlocking nothing; read/write sets, indexes, retention, prediction derived and never authored; named operations as the sync unit, composition by inlining, no ad-hoc client queries; effects as a different kind that write tables through named mutations; a static certificate (shape families + examined bound) at `check` and a dynamic trace (ranges with stop-reason, absences, rows, verdicts) per execution, with trace ⊆ certificate asserted; cardinality as a type with `Unbound` an illegal result; `maintain` as the only exact-over-unbounded aggregate; `countCapped`/page-count as the paved bounded forms; rerun-and-diff as the v1 live lowering; the eight runtime states as the whole offline contract; JS out of the authoritative query/mutation path; the client as range store + evaluator + outbox; one store-wide fence; a one-row halo; the dev loop as co-equal.

Genuine disagreements, each with the cheapest settling experiment:

1. **Ops as algebra versus bounded programs.** One-week census bakeoff: same IR, two front ends, agents build private chat + `boardView` + `boardSummary` + Split; measure time-to-green, correction loops, `partial` incidence in the offline milestone, and how often the agent reaches for an effect.
2. **Client core: TS evaluator versus Rust-WASM/native.** Build the interpreter for the operator subset in both (days, not weeks); measure bundle size and cold start on Hermes/JSC/V8/web; confirm Hermes WASM status; run the conformance corpus. The dev-loop cost of a native module is the tiebreaker.
3. **Opaque verdicts in v1.** Write Clique's and one blocking/muting social app's complete rule sets; count rules over hidden inputs. Zero in Clique makes verdicts v1.1; nonzero in the social app makes the binding a v1 spec item.
4. **`AllOrRefuse` versus write-cap pairing.** Grow Relay's fixture past every declared N and count sealed refusals per design.
5. **Rules imperative versus algebraic.** Take the census rule sets; check every rule hoists as a predicate. If all do, algebraic rules win on simplicity and reviewability; the experiment is a grep.
6. **Per-viewer maintained fan-out (unread) versus `countCapped`.** Measure SQLite write latency for a send into a 256-member conversation with per-member maintenance versus none; decide whether fan-out `maintain` is v1.
7. **Fence default.** Not an experiment; an author ruling on the number.

### 6. Benchmark failure mode

The design I now favor loses Clique's offline milestone to Convex through the **`partial` surprise**, not through a missing operator: the agent's offline test deletes a message, or predicts a `send` from the inbox, sees a `partial` marker where it expected a list, and "fixes" it by widening `take` until `check` refuses — burning the milestone and scoring B4 low. Convex shows a stale cached list with no marker and scores higher for being wrong quietly **[inferred]**. Mitigations, all mechanisms: the halo row makes one delete complete; the range-indexed store makes cross-op coverage ordinary; the prediction closure hydrates `users[viewer]` and the may-write verdict at subscribe; and the `partial` diagnostic names the read that missed and the one repair (subscribe the op that holds it, or accept `partial` as UI state) — never "raise `take`." Second most likely, and outside the language: the dev loop, on which all four proposals already agree.
