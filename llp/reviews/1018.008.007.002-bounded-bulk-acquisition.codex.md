### P2: Preserve each public drain page instead of silently dropping all but a batch's last page

Location: `snapback2/packages/snapback2/src/drain.ts:159` (line after removal of the optional partial-position hook), with `client-query.ts` publication at the end of `commitQuery`.

The new inner batch loop advances the cursor for every complete/capped page, but calls `deliver` only when `index === pages.length - 1`; the exhausted page is delivered separately. Consequently a three-page batch containing rows only in pages 1 and 2 does not expose those rows through the public drain subscriber. A subscriber that accumulates page data now silently misses most acquired rows. Durable row custody does not repair this public event stream. The unchanged public API comment in `react-core.tsx:158` promises “emits each page, then its tail”; LLP 1012 section 6 also says each event remains one page. The plan's coalescing language does not explicitly reconcile this visible change.

Actual lightweight repro against the existing candidate test bundle:

```js
const seen = [];
const sub = new DrainSubscription({
  args: { c: null },
  query: async () => [
    { state: 'complete', data: ['page 1'], seq: 1, next: 'two' },
    { state: 'complete', data: ['page 2'], seq: 2, next: 'three' },
    { state: 'complete', data: ['page 3'], seq: 3, next: null },
  ],
  mark: async () => {},
  subscribe: () => ({ close() {}, until: async () => {} }),
  onEvent: event => seen.push(event.data),
});
await sub.until(event => event.caughtUp);
console.log(seen);
sub.close();
```

Observed output: `[["page 3"]]`. Expected under the existing page event contract: `[["page 1"], ["page 2"], ["page 3"]]`.

Remedy: preserve public per-page events after their group is durable while coalescing the internal store/twin refresh work. `commitQuery` currently attaches `withQueryItems` only to its last page, so restore exact per-page item observation inputs for any newly exposed pages too; reuse a single captured outbox snapshot if desired. Recheck the subscription generation/closed fence between callback emissions because a callback may synchronously close/reset/reconnect the drain. Add a regression that accumulates multiple batched pages, verifies each page's sequence/cursor/evidence, and stops on synchronous close. If page coalescing is instead an intentional API redesign, make that explicit in the governing contract and public docs with suitable replacement semantics; do not leave it as an invisible optimization.

## Final changes inspected

### Direct adoption of normalized rows, overlays, arguments and data

`PersistentRangeStore.commit` first deep-detaches and JSON-normalizes the entire non-byte swap before `applySwap` derives keys or publishes values. Consequently, storing a normalized row wrapper, overlay array, delivery argument or delivery data directly does not retain the original caller's mutable object. JSON normalization also breaks shared aliases between distinct ordinary input fields.

Prepared delivery row pools take a separate checked route: every row must carry the private nominal immutable `RowImage` custody, its wire representation must exactly equal the normalized delivery rows, and row wrappers are rebuilt before insertion. Only the immutable nominal image is shared. The caller's row wrapper and ordinary mutable row body are not adopted.

Later nested state writes still traverse `SwapJournal`. Nested records copy on first write, root/dictionary replacements record undo state, inserted journal proxies are unwrapped, and failed carrier replacement rolls the journal back. Coverage transformations that need changed output construct new data or copy prior retained data; they do not mutate an incoming delivery body behind the journal. Public outbox views still return detached JSON data, and public row/answer views keep their existing detachment/nominal-custody boundaries.
