I'll review the RFC against the rule engine, write path, device prediction, and the guides it cites, and I won't change anything. Starting with the RFC and the sections it depends on.The RFC is a draft that copies a parent's audience into hidden child columns. Next I'll check that claim against how rules, writes, sync, and prediction actually work.**NOT READY.** The local-copy idea matches how sync and pages actually work, but the RFC's meaning, chain rule, write order, and adoption story each authorize a viewer the parent rule would refuse.

## What is sound

A child rule has to stay a local rule. Sync admits only three read rules (`public`/`allow`, `.col = viewer`, or one `exists t[.cols, viewer]`), and `scan_visibility` will not call a page complete while a rule reads an unpinned column. A live parent probe would not be a partition audience. Copying the parent's rule inputs into the child is the right shape.

These parts match the engine:

- The reference column has to be immutable, or the stored copy names a different parent after an update.
- Parent audience columns have to be immutable, or the copy goes stale even with no delete. `validate_sync` already requires that for audience keys.
- Membership changes belong in the live `exists` probe, not in the copy. Both rows see the same membership table.
- The child's horizon stays its own. Maintained views already inherit an audience and drop the source horizon (`bind/schema.rs`).
- One immediate transaction per write, so a single insert cannot tear against a concurrent delete. The hole is sequential reuse and multi-commit adoption, not interleaved writes.
- `exists` does not check the target's read rule (`probe_witness` is raw data). Keeping that, and making `readable` a different term, is right.
- A parent the device does not hold is today's non-predictable insert. Do not fetch it from the server inside prediction.

`allow` and `public` already infer the same sync audience. That part of §3 is not a new collapse.

## Findings

### 1. Blocker — §2, §3, §4, §5 — the copy is not the parent

§2 says `readable` means the parent row exists now and its read rule admits the viewer. §5 says a deleted parent leaves the child readable. §3 says immutability makes the copy always equal the parent's current value, so pinning `.issue` is one verdict for the whole page.

Immutability does not say that. Row ids are client-supplied (`guide writes`: minted unless `id:` is given), and `insert_attempt` replaces an expired row that still has that id. A declared unique key can be deleted and inserted again. The maintains guide already records both: deleting or reusing an id does not change an existing capture, and an id reused before a capture takes the new value.

Scenario. Comments on issue `X` copy `org = A`. `X` is deleted or expires. A new issue is inserted with id `X` and `org = B` (`org` immutable after that insert). Old comments still say A; new ones say B.

- §5's equality claim is false, so "one verdict" is false.
- `prefix_verdict` builds one synthetic row for the prefix. If `.issue = X` is treated as uniform, every comment on `X` is admitted or denied together. Org B's members then receive org A's comment bodies, or the page is declared `complete` while those rows were skipped. `N_NEVER_COMPLETE` exists because that is the "no more" versus "more you may not read" distinction.
- A count grouped by `issue` mixes the two orgs into one value.

The §4 collapse of an id-valued audience onto the reference column is the same bug in another form. `exists members[.chat, viewer]` follows whoever currently owns that id. It is not a frozen copy.

Smallest fix. Pick one meaning and delete the other. For the flattened model (§5), bind the copy to a parent incarnation: the intrinsic id plus a generation bumped on delete and expiry, and reject reuse of that id. Resolve a unique-key `readable` to that id at insert; do not track a later row that reuses the key. State that a reused key does not inherit the old children. Use the functional dependency only inside one incarnation. If you would rather keep §2, the term is false when that incarnation is gone, and aggregates must not group across it.

### 2. Blocker — §3 "Chains" — collapse drops conjuncts

§3 first says the child copies every column the parent's read rule reads. It then says a chain's effective inputs are the root's audience columns, with `$message.$chat.id` collapsing to `$message.chat`.

Scenario.

```quarry
table issues:
  project: projects
  closed: bool
  immutable project, closed
  read <- readable projects[.project] and .closed = false

table comments:
  issue: issues
  immutable issue
  read <- readable issues[.issue]
```

A walk to the live project, or a collapse that keeps only `org`, evaluates comments as `exists members[org, viewer]`. Members read comments on closed issues, including `.issue`, while the issue rule refuses the issue. New comments also diverge from the issue's stored copy if the project id was reused and only the comment re-walks.

That sentence is also how a non-invertible rule gets forced into sync. The sync-admitting class is not "local rules". `infer_audience` and `audience_binding` accept only an exact probe, with no extra conjunct, no `!=`, and no second `exists`. Service disjuncts are stripped separately by `device_audience_rule`. A parent rule `exists members[.org, viewer] and .closed = false` does not sync today. Dropping `.closed` so the child will sync is the disclosure above.

Smallest fix. Copy one stored parent row, never walk to a live root. The substituted rule is the parent's full rule with those stored fields, including every conjunct. Collapse a name only when the copied value is defined to be the reference column. If that substituted rule is not one of the three invertible forms, the child is online-only. Do not drop conjuncts to make it sync.

### 3. Blocker — §2 — `or` and `not` widen the parent

§2 allows `readable` under `and`, `or`, and `not`. §4 then syncs and ships the hidden columns "like any column" so the device can evaluate the rule. Holders of the row therefore hold the audience keys. Recorded fields already travel on the sync wire and are only stripped from query rows and generated types.

Scenario. `read <- not readable issues[.issue]`, or `read <- readable issues[.issue] or .author = viewer`, or `read <- readable issues[.issue] or readable projects[.project]`. A viewer the issue rule refuses can read the comment. The comment's visible `.issue` is the parent id. The wire image also carries `$issue.org` (and, through a chain, a hidden org the issue type itself does not expose).

`insert <- .author = viewer` with `read <- readable issues[.issue]` is the integrity hole in the summary, reopened. The insert reads the parent with system authority, so a non-member attaches a comment the org can read. `grant_guard` stops that only for a synced table whose insert rule restates the audience probe. An online-only child has no such check.

Smallest fix. On a read rule, `readable` is a top-level conjunct, never under `not`, and not the only true branch of an `or`. Other conjuncts may only narrow. Every insert, upsert-insert, and `insert … if absent` branch must imply that same audience, including online-only tables. Hidden fields use the recorded split: present on the sync image, absent from query rows, `*` shapes, and generated types.

### 4. Blocker — §3 "Insert" — the payload is checked before the copy

`insert_attempt` runs `check_rule` and only then `record_insert`. Recorded fields are safe to stamp afterward because no rule reads them. This copy is the rule input. `term()` treats a missing field as null, and a present field as the payload value. Upsert and `insert … if absent` use that same insert path. Nothing in the RFC says a client value is rejected.

Scenario. The writer is in org A. The issue is in org B. The insert payload sets `$issue.org` to A. The insert rule sees A and passes. The engine then overwrites the stored copy with B. Org B receives the comment. The other order is also wrong: if the field is absent, the rule sees null, denies the insert, and the real copy is never consulted.

An update that re-resolves `next.issue` (the §2 wording "select which image names the parent") has a second outcome. The comment is readable, so a parent miss becomes `NOT_FOUND` and a readable new parent fails later as an immutable-column constraint. Those are different codes for an issue the writer only named in a patch. `authorize_update` runs before `check_constraints`.

Smallest fix. Reject any payload that names a hidden column (`E_RECORDED_FIELD` already does this for recorded fields). Load the live parent, stamp the copy, then evaluate the write rule on that image. Updates and upsert patches keep the stored copy and do not read a parent. A changed reference fails immutability with one code, whether or not the new parent exists.

### 5. Blocker — §6 — a §5.2 job publishes a half-filled audience

§5.2 commits every K rows and parks on a rule refusal. That is an application job on a schema that is already live. Column and recorded adoption do the opposite: one activation transaction, no row events, and devices re-acquire only when the generation publishes. The maintains guide also says an id reused before capture stores the new target's value.

Scenario. The new read rule is already installed. The job has filled comment 1 on issue `X` with `org = A` and not comment 2. Either:

- unfilled copies are null, so those comments disappear until the job finishes, or
- the planner trusts "`.issue` determines the copy", sees comment 1's org, and admits comment 2 under org A. If comment 2 was hand-tagged as org B, org A just received it.

A crash resumes the job and leaves that mix durable. Between chunks the parent can be deleted and reinserted, so one issue id is filled partly as A and partly as B. An orphan refusal stops the job after earlier chunks have committed. "Keep the old rule" does not say those copies are discarded. A chain (project, then issue, then comment) has no fill order, so a comment can copy an issue whose own copy is still null.

Smallest fix. Do not use a §5.2 job. Fill inside activation, parent tables before children, system scan, expired and missing parents both unresolved. If any row's parent incarnation is missing, roll the activation back and name the rows; do not publish the generation. New writes are not accepted under the new rule until that generation publishes. Discard a failed fill. A row whose existing hand-copied org disagrees with the parent is reported, not silently moved into the parent's audience.

### 6. High — §4 "Maintained readability" — the proof does not go through

`N_MAINTAINED_COLUMN_DISCLOSURE` fires for every private source. There is no proof to turn off, other than a uniformly readable source (`bind/columns.rs`). A maintained view is stricter: `derived_read` returns `E_MAINTAIN_READ_RULE` unless every field the source rule reads is a bare group key. Sync is inherited only when those audience columns are themselves group keys.

`count comments by issue` groups by `issue`. The substituted rule reads `$issue.org`, which is not that key, and the aggregate row is `{ id, issue, value }`. It has no org to test against `members`.

Scenario. An implementer silences the note because the source rule contains `readable`, or rewrites the view rule to `allow` because the copy is "determined". Every caller who can name an issue id then sees the count, the predicate filter, and (if the column is indexed) the parent order. That includes viewers the parent rule refuses, and it includes the private-likes-on-public-posts case LLP 3000.007.001 §3.8 still requires the note for. A narrower child rule (`readable and .published`) has the same shape and must keep the note: the count includes unpublished rows.

Smallest fix. Derive the aggregate rule only when every captured field is a function of the group key inside one incarnation, and store those captured fields on the aggregate row. Otherwise keep `E_MAINTAIN_READ_RULE` and the disclosure note. Say that this view does not inherit sync unless the stored audience columns are group keys. Do not treat "the source mentions `readable`" as the proof.

### 7. High — §3 "Insert", §4 "Devices" — liveness of the parent read

The parent read is specified as get-by-id with system authority. `tx.get` returns an expired row. `fetch` does not. Expiry is defined as absent to every reader before any rule, including the system principal.

Scenario. The issue is past `expire at` and not yet swept. Comment insert still copies its org. Members post new comments on an issue that point-reads as absent, which discloses the id and keeps a live thread. On a device, "the parent row it holds" also includes retained-history images and rows the sweep has not removed. Recorded prediction already refuses those: `recording_covered` requires a live row in the current partition, and retained-only or expired targets queue with no predicted row. A local insert against a retained membership then shows a comment the server will refuse.

Same-mutation inserts are the other half of this lookup. Clique receipts are inserted in the mutation that inserts the message. `tx.get` sees that uncommitted parent; a snapshot read would return `NOT_FOUND` and the §9 Clique claim would fail. `created` is also weaker than `readable`: it does not apply the parent's read rule, so replacing it changes who may insert.

Smallest fix. One helper, used by server insert and device prediction: same transaction, live, not expired, and on a device also partition-covered and not retained-only. Otherwise the insert is `NOT_FOUND` on the server and non-predictable on the device. State that this sees parents inserted earlier in the same mutation. Do not claim `created` and `readable` are interchangeable.

### 8. Medium — §3, §4 — upsert, `if absent`, and the grant check

`upsert_absence` requires the addressed key to pin every field of the device audience rule. The audience field is `$issue.org`. A reaction's unique key is `(issue, author)`. The absence proof fails, so upsert and `insert … if absent` queue even when the parent is held. §9's reactions are this shape. The functional dependency is only mentioned for the planner.

`grant_guard` also requires the insert probe's field name to equal the membership table's column name. A hidden `$issue.org` does not equal `members.org`, so the natural substitution does not sync. Weakening `grant_guard` to get the example compiling removes the check that stops a stranger from joining an audience.

The hidden-target table does not apply to a new insert. Insert-rule failure is `E_RULE`. Update of a missing or unreadable target is `NOT_FOUND`, and `target_attempt` restores the meter only for that code. Special-casing a missing parent as `NOT_FOUND` while `.author = viewer` still fails as `E_RULE` tells the writer which conjunct failed. A parent read that is not pre-reserved can also fail as `E_BOUND` only when the parent row exists.

Smallest fix. Teach `upsert_absence` the incarnation dependency, or state that these two writes stay non-predictable. Map the hidden field through `audience_binding`; do not relax `grant_guard`. Pre-reserve the parent point-read, treat expired as miss, and use one insert-rule refusal for every conjunct.

### 9. Medium — §4 "Sync", §5 — revocation is not one audience

§5 says a member who leaves stops reading issues and comments in the same instant, on the server and at the next sync, and that retained history applies to both as declared.

Leave policy is per table and is not inherited. `trust_synced_read` does not re-evaluate a `retain delivered-history` table. A child that retains history stays readable on the device after the parent table has withdrawn, and the retained comment still carries `.issue`. The parent's horizon is also not inherited, so the device can hold every comment of a group whose issues were capped at 500. That is not an authorization bypass of the read rule (a horizon is not an ACL), but it is not "the same instant", and it is larger than the parent the author bounded.

Smallest fix. Say revocation follows each table's own leave policy and horizon. "Same instant" is server evaluation of the substituted rule only. The next sync withdraws a child only when that child is `until revoked`.

### 10. Low — §3 — service grants

If the substituted rule is the parent's real `RuleExpr`, `device_audience_rule` already drops `or viewer = 'service:…'` from the device audience and leaves it on the server. Re-deriving sync from copied columns alone either drops the service or delivers it to devices. Say that the existing strip is reused unchanged.

## A smaller design

Extend the recorded-field path the maintains guide already has, from public targets to private audience inputs. It already refuses client values, stamps inside the writing transaction, splits wire from query types, activates inside the generation barrier, and will not predict from a retained or expired target.

Keep it that narrow:

- `readable t[.id]` is the whole read audience, plus conjuncts that only narrow.
- Stamp the parent's full substituted inputs, plus the parent incarnation, after rejecting client values, then check the rule.
- Sync only when that result is one of the three invertible forms.
- Aggregates store those inputs and derive a rule only when the inputs are a function of the group key.
- No live walk, no `not`, no extra disjunct, no §5.2 fill.

That is enough for the issue tracker, a four-level tenancy chain, and a same-mutation Clique receipt. Mutable audience columns, referential actions, and "the issue is open" can stay in §8.

## Verdict

**NOT READY.** Do not implement from this text. The copy-as-local-rule approach is sound only after findings 1–5 are specified the way the write path, sync checker, and activation barrier actually behave.
