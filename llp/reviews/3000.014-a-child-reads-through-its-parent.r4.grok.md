## 2. The lifetime rule

On one server commit boundary it holds. A live child’s parent is live, and its captures equal that parent’s fields.

- **Delete.** A live child blocks the delete, including a child inserted earlier in the same transaction, including a job or `seed_delete`. Deleting the child first, then the parent, succeeds.
- **Expiry.** `deadline(row) = min(authored, captured parent deadline)` is transitive. A middle table with no `expire at` still passes the grandparent’s deadline down.
- **Expired id reuse.** Replacement is refused while any physical child remains, so recapture cannot stamp B onto A’s child.
- **Same-mutation insert-then-delete.** Insert parent, insert child, delete parent: the probe sees the child. Delete parent, then insert child: the parent is not live, so the insert refuses.
- **Seeds, imports, restores, activation.** Covered by §7 and §7.1, as in the table above.
- **Three levels.** The child copies the parent’s stored captures and the parent’s effective deadline. It does not walk to a live grandparent. Server equality follows from immutability plus the two rules above.

It does not hold on a device for the audience this RFC is for.

`group_partition` includes the table name (`partition.rs`). Issues and comments for the same org are different logs. A device can apply the new issue before the comment tombstones. The monotone clock then expires a child only when that child’s effective deadline is finite. A child that does not expire stays live, still carrying org A, under the new issue in org B.

§5’s sentence “a device behind the server can therefore never hold a child live after applying its parent’s removal” is false for that child. §5 then applies one verdict from B to every local comment of that id and, once comment coverage is whole, calls the page complete. There is no server fallback.

Today that page is not uniform: the substituted rule reads `$issue.org`, which `.issue` does not pin (`scan_visibility` / `fields_pinned` in `rules.rs`). With `trust_synced_read` false — the membership table itself expires (`read.rs`) — the device re-evaluates and sets the page incomplete. The new verdict removes that protection.

**High — §5.** Bob was in org A and is now in org B; memberships expire, so the device does not trust delivered rows. Comments on issue `X` are deleted, `X` is deleted, `X` is inserted in B. The device applies B’s issue while A’s comments are still stored, and Bob’s membership in A is already expired locally. Per-row evaluation of the captures hides the bodies. The parent verdict shows them and says the page is complete. Keyed `commentCounts[X]` does the same.

Smallest change: one verdict only when every locally held child of that id is live and its captures equal the parent image. Any mismatch is incomplete and falls back to the server. Delete the claim that applying the parent’s removal expires children whose deadline is never.

## 3. New defects

The device verdict above is the new authorization defect. I did not find a new server-side way to keep a live child after its parent is gone, or to make a live child’s captures differ, at a commit boundary.

Refusal codes, the fixed reservation, cursors, and sync admission do not reopen the revision-3 oracles. `grant_guard` stays on the membership table’s insert, which is the right place. Service stripping still applies to an inherited disjunct. Predicted child upserts stay non-predictable. Activation still publishes one generation or nothing.

## 4. Under-specified

**Medium — §3.2.** “Wire it through `Table::expired`” does not reach the gates that never call it. `lookup_live` returns the physical row when `expire.is_none()` (`read.rs`). `sweep_expired` only walks tables that have an expiry index (`engine/mod.rs`). `retire_expired_births`, `live_aggregate`, cap deltas, and `note_expiry` all key off the authored column. A middle table with no `expire at` will still answer `exists projects[P]` on Tuesday, will never be swept, and will not invalidate a subscription until a later authored deadline.

Smallest change: a captured finite deadline makes the table expiring. Store that effective deadline and index it. `lookup_live`, the sweep, commit-end retirement, live aggregates, caps, subscription `next_expiry`, and partition grant lifetime must use that stored instant, not `table.expire.is_none()`.

Nothing else rose above a preference. Cursor continuation across a later reuse is ordinary pagination. “Retire” in activation is safe whether it deletes the expired row or only refuses to lengthen it.

## What is sound

`read through .ref` as the entire read rule, over one required immutable id with no default, is the right cut. Copying the immediate parent’s stored inputs, including every conjunct, and not walking to a live grandparent, matches a local rule. Exact admission after the service strip matches LLP 3000.007 §6.6, `infer_audience`, `validate_sync`, and `grant_guard`. The insert order — refuse a client value, reserve a fixed charge, require a live parent, stamp, then evaluate — is the right one, including before an upsert arm. Absent and unreadable parents both stop before `term()` sees null. Updates do not re-resolve the parent. The four-outcome resolver is the right device split once it is forbidden to authorize rows whose captures do not match. Keyed views, no scan, are the right aggregate cut. Per-table leave policy is the right revocation story. On the server, the lifetime rule is the right replacement for incarnations.

**Overall verdict: NOT READY.**
