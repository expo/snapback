## (b) Delight: what Snapback 2 must keep

1. **Diagnostics with code + span + rule + admitted alternative + build-bound guide anchor.** D0101: "The diagnostics are the best I have used. Not 'good for a young product' — best, full stop. … `snapback errors issues` gave me a `TypeError`, the exact spliced-helper stack frame, and a telemetry query … turning a would-be bisection into a ninety-second fix." D0100: "The error messages are a feature … When I restarted the server on a changed carrier, the refusal printed the pinned deployment, the observed deployment, *and* two exact repairs — one that keeps data and one that discards it … it is why three of my four hard redesigns took under half an hour." D0114: "the platform told me exactly what was wrong every time". D0087 (device run): "every mid-session recovery had a paved path." R:capstone: `SNAPBACK_CLIENT_MUTATION_RETENTION_FULL` "named the exact remedy … Recovery: 10 minutes end to end."
2. **Live queries with zero invalidation code.** L:opus-coterie (D0102): "Declaring `reads`/`writes` per function meant live invalidation was automatic: I never wrote a single 'refetch after mutate' line." D0103: "I wrote zero invalidation logic in this app. A follow edge lands and every subscribed feed re-projects." D0107: "zero hand-written subscription or cache-invalidation code across all four milestones" — and multi-device sync "fell out for free" in M8. D0109: "realtime is an outcome of data dependencies, not a separate socket layer."
3. **The ephemeral/presence primitive (explicit profile).** D0100: "the typing indicator was genuinely fifteen minutes … That is the single most pleasant thing in the whole run." D0101: "a category difference, not an increment … Convex has no equivalent." D0106: "Realtime typing, once generated, was the nicest hour." D0104: "no durable typing row, no cleanup mutation."
4. **Declarative membership/visibility.** D0101: "This is the single biggest architectural difference from every other backend I know, Convex and Firebase included … Snapback puts it in the schema and then refuses to let you write the roster any other way." D0100: "The membership declaration paid for itself within an hour." D0108: "more expressive than anything I'd hand-roll on top of Convex's row-level `ctx.auth.getUserIdentity()` checks."
5. **Fail-closed identity everywhere.** D0100: "If the bundle is stale relative to the server, the call fails closed with `SNAPBACK_ARTIFACT_IDENTITY_MISMATCH` rather than sending a plausible-looking request into a schema that moved." D0112 (familiar essay): "Snapback's novelty is not mainly in writing a query; it is in the disciplined chain from authored source to generated artifact, admitted runtime, live client, and identity-bound evidence." D0098: "I have implemented 'remember me' on every stack I have used. I have rarely been prevented from lying about it. Snapback prevented the lie."
6. **`ctx.auth.userId` as the only identity input; server-derived everything.** D0100: "there is no forgeable identity input to review." D0111: "Server-derived principals removed actor ids from every write interface."
7. **Built-in password auth + typed assets.** D0101: "Password auth was five lines of client code and no hashing decisions … Assets were the biggest positive surprise: one `v.assetRef` field, one `defineAssetUpload` … the fixture avatar rendered real bytes on the first try." D0087 (real iPhone): "the atomic multi-upload-plus-commit and the per-item residue honesty have no equivalent."
8. **Version-exact served guide.** D0101: "`snapback guide <query>` and `http://<origin>/_snapback/guide/...` return the docs compiled into *that build*. No version-skew guessing … That is a structural advantage over every backend I know." D0091: "one question produced one relevant page." D0113: "The 0.1.25 served Guide was usually exact enough to unblock unfamiliar surfaces."
9. **Additive schema successors keep accounts/sessions/data; day-2 evolution is routine.** D0108 (M7): "no special migration DSL, no separate migration file, just a schema edit and `bun run generate`." D0106: "Successor activation printed old and new schema/function hashes plus a continuity block that said accounts, sessions, and stores were preserved. That is more honest than Convex's 'just deploy'." L:grok-explicit essay: "closer to Convex's 'push a new schema, keep the data' than to a migration night with Postgres."
10. **Familiar profile's Convex-shaped inner loop.** D0101: "If you have written a Convex app, you can write the first 200 lines of a Snapback backend without opening a doc." D0093: "much less duplicative machinery: no controller/request-schema/DTO/client-wrapper chain."
11. **`_version` as monotonic server order; bounded batch reads with an N+1 advisory.** D0100: "`SNAPBACK_AUTHORING_N_PLUS_ONE_BATCH_READ` … found two loops of point reads I had written and told me to use `ctx.db.uniqueMany` before I ever ran them."
12. **Replay through the app's own write path; the done-oracle.** D0091: "`bun run prove` passed in under two seconds … a single receipt that binds runtime readiness, generated identity, capability resolution, and the live journey." D0106: "Replay through the app write path, not a SQL dump, is the right default for a messenger."
13. **The 0.1.27 caller-owned (URL-first) loop, when it exists, is the loop everyone asked for.** R:qb: scaffold 1 s, backend ready 22 s, authenticated live query green 547 ms after construct, backend kill → auto re-verify → live in 8.6 s, schema edit → Metro serves successor hot in 1 s with no restart. R:capstone: explicit M1 first-green −51% vs 0.1.25 (1,075 s vs 2,183 s).
14. **The published scale runner (0.1.27+).** L:sol-explicit essay: "far better than the custom client loop I began with: it bounded the actor pool, preserved ordered terminal receipts, projected settled identifiers into later actions, and resumed exactly across lifecycle rotations." R:capstone: "The replay machinery itself … required zero interventions once the adapter honored the ack contract."

### c.4 Mechanism-level comparisons the agents made

**vs Convex** — nearest cousin; loses on the first hour, wins on authority.
- Day-one: D0100: "Convex also wins on the day-one loop: `npx convex dev` and you are writing functions. Snapback's `snapback dev` is comparable *if* you let it own the ports." D0097: "For the function bodies, yes, interchangeably. For the first hour of bringing a web client up, no. Convex has already spent that hour for you."
- Reads declaration: D0100: "In Convex I have never once had to think about what a query reads; in Snapback I had to write `reads: [...]` … That felt like ceremony on day one and like documentation by the time the feed read-model existed."
- Authority: D0100: "Convex would have let me write the four-line join and move on; Snapback made me build the read model and, in exchange, made the authority relation unreadable by accident. On a messaging app I think Snapback's trade is right. On a weekend project I would resent it."
- Where Convex is weaker (from Convex lanes): no built-in password auth on anonymous local (B2 38/44); no unique indexes ("occupancy-checked in mutations"); no TTL/presence primitive; `throw new Error` redacted unless `ConvexError`; hidden `--local-cloud-port`, dashboard port 6790 patched in dist; no reset/clone verb ("`reset` is not a CLI verb"). L:grok-convex: "I like Convex more when I am already inside a `convex/` directory. I like Snapback more at minute zero of a cold machine."
- Predictability: L:sol-familiar essay: "Convex still has an advantage in how predictable that loop feels … a mutation of data read by a subscribed query normally implies that the query will update everywhere it is subscribed." D0101: "Convex's `useQuery` is famously boring here; boring is a feature."
- Verdict pattern (3 of 4 opus/sol essays): choose Convex for a weekend prototype, Snapback "the second time I built something, when I already know the rules and want them enforced rather than remembered" (D0100).

**vs Supabase** — relational leverage and maturity vs one-language authority.
- L:sol-supabase essay: "Supabase is several coordinated systems, not one uniform programming model. Auth, PostgREST, Realtime, Storage, and the Management API each have slightly different error behavior … A table notification is not a ready-to-render feed or message bubble … Supabase supplied the signals; Clique had to supply the synchronization semantics."
- Storage RLS: L:grok-supabase: authenticated upload denied despite `WITH CHECK (true)`; "There is no useful diagnostic in that error: not the role, not the policy name." Needed a service-role proxy on a second port.
- Hosted quota killed scale at 24–29 actions; Management API 429s on DDL; no offline; no scheduled jobs without a worker.
- Snapback's edge per Supabase lanes: "a *typed contract between the write and the read*" (D0100); membership visibility "sits on the table next to the fields it governs" vs "RLS is SQL in a migration". Snapback's loss: "I missed SQL badly for Insights-shaped aggregation" (L:sol-explicit); read-only analytics "had to masquerade as mutations with a declared table they did not write."

**vs PocketBase** — fastest to green, thinnest on coordination.
- L:grok-pocketbase: "Download, unzip, `serve --http` on a loopback port, `superuser upsert`, and there is an app … For a timed lane that must provision inside itself, the binary is the best five minutes I had all day." D0114: "the model spent its effort on product code, not backend wiring."
- Costs: stateless JWT logout ("not a row you delete"); JSVM hooks don't close over file scope ("`eval` a factory … a builder-experience wound"); typing/receipts as durable rows; no offline SDK; `sort=created` fails generic 400 without autodate; same-second migration filename ordering breaks; scale died at ~28k/167k for grok, 500-author feed predicate errored and search degraded 5.32× for sol. O3 (trust): "Authenticated collection rules allow cross-user private-record reads."
- L:sol-pocketbase: "PocketBase offers a good local server; it is not a client database with a sync protocol."

**vs Firebase** (from memory, no lane): consistently cited as the offline/mobile winner and the authorization loser. D0100: "Firebase's offline cache is easy and its guarantees are vague, while Snapback publishes exactly which store retains what … and refuses a write while the durable outbox is still proving authority, with a typed code instead of a silent stall."

**vs hand-rolled Postgres + Express**: D0100 is the canonical list of what Snapback gives "without asking" (server-derived identity, argon2id, structural uniqueness, batched reads, declared-read live queries, intent-based assets, named-rule diagnostics) versus "the absence of walls."

**vs Clerk** (D0111 social auth): "much more explicit custody, provider-registration, callback, and lifecycle work … Supabase's development experience is genuinely better on day one; its production graduation story for Apple's team-scoped subjects is not better, it is just quieter."
