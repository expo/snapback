## New findings

**N1 — High: Initial capability discovery can swallow a generation change.**

At [client.ts:174](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/client.ts:174), discovery seeds `generation` without invalidating existing answers. If a durable watch answers under generation 1, then adoption occurs while its first `/schema` request is pending, discovery installs generation 2; subsequent generation-2 polls never trigger `changedGeneration`.

The real-server [differential probe](</tmp/eph-delta-GPT-6 Astra (max)/capability-generation-ab.test.mjs>) passes with the archived `1d6325c86` client and fails with this tree: direct querying returns `2`, while the mounted watch retains `1`, `complete: true`, `fresh: true`, through three generation-2 poll responses.

**Fix:** Treat initial backend installation as an invalidation boundary for existing reads: advance the query epoch, discard earlier answers, and rerun mounted watches before treating the seeded generation as current.

**N2 — Medium: Failed initial schema discovery is permanently marked complete.**

At [client.ts:565](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/client.ts:565), `backendLoaded = true` executes even when `refreshBackend()` fails. With a handle lacking the backend’s new ephemeral facts, one injected `/schema` 503 leaves polling at `ephTables=` indefinitely: the [probe](</tmp/eph-delta-GPT-6 Astra (max)/capability-failure.test.mjs>) records exactly one schema request, healthy subsequent polls, and an empty fresh watch while direct querying returns the new row.

**Fix:** Mark discovery complete only after successful installation; retry transient failures with bounded backoff.

**N3 — Low: Savepoint rollback leaves the sequence-table cache stale.**

[sequences.rs:15](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/store/sequences.rs:15) caches successful creation, but `Tx::rollback_to` does not invalidate it. A [public Store/Tx probe](</tmp/eph-delta-GPT-6 Astra (max)/sequence-savepoint.rs>) creates `_sequences` inside a savepoint and rolls back; subsequent reads and allocations both fail with `no such table: _sequences`.

**Fix:** Clear the cached existence result after savepoint rollback. This is limited to lazy allocation; ordinary sequence-schema activation creates the table beforehand.
