## Verified sound (no finding)

- **Negative caller/raw witness distinction**: `caller_facts` drops non-monotone (negative) existence probes to `Allow`, and `implies` requires *every* arm of an `Or`-have to imply the need (`query_branches.rs:8-20`). Negative program results cannot establish raw absence. The helper-return path additionally gates on `raw_witness_monotone(have, true)`.
- **Helper calls must actually succeed**: the zero-arg-helper path in `lookup_advice_proved` (`read_diagnostics.rs:41-60`) requires `authorization_proved(&call, true)`, which holds only for facts recorded from dominating guards — a merely existing callable helper does not suppress. 32-level expansion with opaque effects/recursion matches the contract.
- **Later require cannot authorize earlier lookup**: lookup checks run at the binding site against dominating facts.
- **Upsert operator admission** (`lints.rs`): `Or(insert, update)` gate conjoined with path requirements via exhaustive `kernel::implies`; `safe()` filtering drops unsafe requirements (conservative direction). `service:clock` change is warning-only. No new authority, gates, or Analyzer staleness (every affected note changed message text, so decision IDs re-key; `ANALYZER` unchanged is safe).
- **Deadline transposition/equality math**: offset normalization (`time_shift − field_shift`), reversed-comparison bit transposition, and equality-overlap retention are all correct.

## Blocking findings

### B1. Job-side unknown/non-affine sweep comparisons now silence the deadline entirely (regression)

`sweep_deadline.rs:171`: `let Some((offset,_)) = time_comparison(comparison, …) else { continue; }`. When the *job's* sweep comparison is non-affine (duration from a call/argument rather than a literal), the whole `(deadline)` pairing is skipped — no advisory at all. The old code folded unknown masks to `due = 7` and therefore **asked**. The RFC requires: "Unknown/non-affine relationships remain conservative."

Example: job `require r.createdAt < periodEnd - policy()` (helper-supplied retention) sweeping `status → 'expired'`; mutation writes `status` on the same table with a status test but no deadline guard. Old code emitted `N_SWEEP_DEADLINE`; new code is silent. Fix: fall back to offset-agnostic masks (old behavior) when the job comparison yields no offset, instead of `continue`.

### B2. `lifecycle_guard` suppresses the edit question even when the guard pins the approved/post state (regression of the canonical hole)

`lifecycle.rs:31-50`: suppression fires when *any* domain value falsifies *any* guard. It never checks *which* state is excluded. A guard pinning the approving value itself therefore "answers" the question:

```
table items { photo: image?, approved: bool default false }
mutation replacePhoto(id, p):
  require items[id].approved = true     // edit happens UNDER approval
  update items[id] set photo = p        // evidence replacement after approval
```

Old `creation_state_guard` required equality to the *default* (`false`), so this asked. New code substitutes `false`, gets `false = true → false`, and stays silent. Parent §17.1 explicitly includes "evidence replacement after approval," and the amendment blesses only source-stage/null-stamp/coalesced/exclusive-branch guards — not approved-state pins. Same flaw in smaller form: `status`-equality pins and single-probe `Time` guards suppress without excluding the post state. Fix: require the excluded set to include the approving/post state (the guard must fail once approval holds), not merely any state.

### B3. `N_GUARD_NOT_CONSUMED` repeat-create/reuse question dropped for Upsert birth arms

`lifecycle.rs` (~line 398): the block now requires `(state && !source_restricted) || (Insert && self-ref-table)`. Old code covered `Insert|Upsert`. A non-state-changing upsert birth reusing a one-use guard is now silent:

```
mutation redeem(code):
  require consents[viewer].granted = true   // one-use consent, never consumed
  upsert redemptions[code] { by = viewer }  // no enum change → state() false
```

Old code asked; new code skips the block (op is `Upsert`, not `Insert`). The RFC retains both the approval/consent/payment-reuse question and the repeat-create question with no insert-only qualification ("None of these reductions infer a gate or prove safety"). Fix: include the upsert birth arm in the reuse/repeat-create check (existing-row arms stay under the edit rules).

### B4. Sweep/mutation pairing has no resource identity (contract sentence unimplemented)

`sweep_deadline.rs:165-180`: pairing is by `(table, deadline)` × `(table, status)` only. The job alias and mutation alias are used independently per-side and never cross-compared; read keys are never compared. The RFC requires: "Pair mutation and sweep reads by resource identity" (parent §18: "resolved read-key identity").

```
job expireOrders:
  require o.due < periodEnd - 1d; require o.status = 'pending'
  update orders[o.id] set status = 'expired'
mutation renew(oid, otherId):
  require (lookup orders[otherId]).due > now - 1d   // a DIFFERENT row, same offset
  require (lookup orders[oid]).status = 'pending'
  update orders[oid] set status = 'active'          // oid row may be past-due
```

`due = {<}`, `admitted = {>}`, disjoint → suppress, although the written row `oid` was never deadline-bounded. The state check that follows would have asked; the time-bit suppression fires first. Fix: compare resolved read keys (as `N_DEPENDENT_WINDOW` already does with `resource_key`) before letting one program's window discharge another row's question — or weaken the RFC sentence.

## Non-blocking notes

- `N_EDIT_AFTER_APPROVAL` now also fires on upsert birth arms (`op != Insert`) — over-asking, conservative, acceptable.
