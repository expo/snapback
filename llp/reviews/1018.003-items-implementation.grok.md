### 1. MATERIAL — Head-page drafts for every old successful create

`attachItems` retires a create only when the row is **currently selected** (or there is explicit absence). Otherwise it synthesizes a draft, including for `committed` entries whose pinned id is simply not on this page:

```160:168:snapback2/packages/snapback2/src/client-items.ts
    const contributing = key !== undefined && inputs.predicted.get(itemAddress(spec.table, key))?.some(mark => mark.intent === entry.intent);
    if (!contributing && (item || observation?.absent) && observed(entry, observation, binding.kind)) continue;
    if (!item && binding.kind !== "create") continue;
    if (!item) {
      const stableKey = key ?? `intent:${entry.intent}`;
      item = items.get(stableKey) ?? { key: stableKey, draft: binding.draft!(entry), predicted: false, pending: [] };
      items.set(stableKey, item);
    }
```

`ItemCapture` only writes **positive** observations for rows walked from this answer (`query-items.ts` `row()` / `references()`). Off-page messages therefore have no `item` and no positive observation, so the skip never fires.

`threadItems` scopes creates to the head page (`c === null`), not to “still waiting for first display”:

```9:12:snapback2/packages/snapback2/templates/chat/shared/thread.ts
    belongs: (args, query) => query.c === null && args.conversationId === query.conversationId,
    key: intent => intent.ids[0],
```

`conversationItems` is even wider (same conversation, no cursor). Combined with “scan the whole retained ledger” (`ItemCapture.inputs()` returns `Object.values(this.state.outbox)`), the product is:

- send N messages, they leave the newest page (or a composite window)
- each remains `committed` until explicit dismissal
- the head page grows N labeled drafts of already-delivered mail

The same hole covers remount (no `previous` memory), capped/tombstoned pages (`select` drops null, then the create binding fills the gap), and extent eviction (explicitly not modeled as absence).

The unit test **requires** this:

```60:61:snapback2/packages/snapback2/tests/client-items.test.ts
  assert.equal(attachItems(spec, args, [], inputs([committed], { observations }))[0]?.pending.length, 1,
    "a row absent from this page has not been displayed here");
```

That is the right rule for **pending-on-a-visible-row** (fan-out / sibling seq must not clear an indicator). It is the wrong rule for **whether to invent a create row**. “Not in `data`” is not “never displayed here,” and with retained history it is mostly “already scrolled off.”

This is the collision of the two goals: keep the intent until this view shows the row, and never auto-delete the ledger. The code uses “currently in `data`” for both.

**Fix (keep the ledger; change only fabrication):**

Distinguish the two questions.

- **Visible row:** keep the current rule. `observed()` plus `item` (identity-checked) or `absent`. Fan-out and sibling seq still cannot clear a displayed indicator.
- **Off-page create placeholder:** do **not** synthesize from “committed ∧ !item”. Show a draft only while the send is actually outstanding in this partition: `queued` / `rejected` / `expired`, or `committed` and the pinned `(table, id)` is **not** in `state.rows` at `rowSeq >= commit seq` (still waiting for any authoritative image). Once the pool has that image, omission from this page is pagination; recovery stays on the account outbox.

That needs a small pool fact on `ItemInputs` (or observations for create targets that exist in `state.rows`, even when this answer did not return them). Do **not** use overlay `arrived`, fan-out ids, or `contributing` for this — those are the false “delivery” proofs the plan already rejected.

Sibling-query consequence: a draft can disappear from thread a moment before this query returns the row. That is a gap; a wall of historical drafts is worse. Invert the test above so a positive observation of `messages/m` with `data: []` yields **no** item, and add: after a committed create whose row was selected, a later page that no longer contains it must not grow a draft.

`previous` alone is not enough — it dies on remount, which is when the wall comes back.

### 2. MATERIAL — Server path tears ledger from row proof

```240:247:snapback2/packages/snapback2/src/offline.ts
  async withQueryItems<T extends object>(accepted: AcceptedDelivery<unknown>, value: T): Promise<T> {
    const entries = this.partition === undefined ? [] : await this.outbox.entries();
    if (accepted.envelope) return withItemInputs(value, deliveredItemInputs(accepted.envelope, (value as { data?: unknown }).data, entries));
    return withItemInputs(value, { ...(itemInputs(accepted.result) ?? emptyItemInputs), entries });
  }
```

Local capture already took `entries` from the same `PersistedRangeState` as `rowSeq` / proofs (`ItemCapture.inputs()`, `query-items.ts` 84–86). This then overwrites them with a later `await outbox.entries()`. Envelope deliveries also force `predicted: new Map()` (`query-items.ts` 30).

So a published frame can mix T0 row witnesses with T1 ledger (or a live overlay-free predicted map). That is exactly the “publish once after value, overlay attribution, and outbox are consistent” rule, and it is how a fresh base can be joined to the wrong contributing set.

**Fix:** if `itemInputs(accepted.result)` exists, keep that `entries` / `predicted` / `observations` / `values` tuple. Call `outbox.entries()` only when there is no capture (pure envelope, no twin). Do not rebuild `ItemInputs` field-by-field across an await.

### 3. MATERIAL — Join and outbox observer cost is O(retained history) per publication

Retention is an accepted policy. Paying for it on every query publication is not.

- Every local frame sorts **all** outbox rows (`query-items.ts` 84–86).
- `attachItems` walks **all** of them for every items projection (`client-items.ts` 154).
- `observeOutbox` `structuredClone`s the full ledger, then `JSON.stringify`s each slot on every notify (`client-outbox-observed.ts` 37–44).

Finding 1 makes this user-visible (history re-enters the thread). Even after that fix, every keystroke-driven refresh still scans every successful send this device has kept.

**Fix:** do not put the raw ledger on the query frame. Index once per session by `op` (and create `ids[0]` / update target), and pass only bindings that `belongs` plus intents in `predicted`. Compare outbox snapshots by store revision, not by cloning and stringifying the array. Compaction can stay a later policy; this is just not using the ledger as a page-sized join input.

### Boundary

Keep it. `defineItems` as a frozen declaration, `attachItems` as a pure join, `ClientQueries.observe(..., { items })` as memoized projection, one `observeOutbox` — that is the elegant cut. Do not add a second collection lifecycle, and do not put dismissal back in the join.

Smaller contract notes, not the reason to revise:

- Projection memo key is the spec object (`client-observed.ts` 190–191). The exported `threadItems` const is required; an inline `defineItems(...)` in a component will churn slots and drop item identity. Document that, or intern on `query` + `table` + binding ops.
- `sameValue` via `JSON.stringify` (`client-items.ts` 189–191) is only an identity optimization; if `response` is ever non-JSON it will throw inside `project()` and fail the snapshot. Compare `pending` by length + intent/state/op.
- Gzip 83.5KB vs 82KB is already owned by the prerequisite; it does not decide this slice.
