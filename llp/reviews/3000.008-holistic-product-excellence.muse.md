## Severity-tagged findings (with evidence)

- **[S1 — correctness] Helper early-return drops page cursor, certifies truncated page `complete: true`.** Open P1 with 12-row CLI repro ([ticket](issues/20260914-snapback4-helper-early-return-drops-page-cursor.md)), charged in 0.2.12 calibration (queries_and_live, diagnostics 88→78). Suspected mechanism (`runner.rs:276-278` re-seating `self.page` from the inlined helper's return site) is explicitly unverified — lane N2 must verify first. This is the highest-value fix: small, within current architecture, with a crisp acceptance (cursor preserved on server + both device stores; lost continuation never reads `complete: true`). Built on `sb4/next-int` (commit `4b8db6f85`), **not** in snapshot HEAD or 0.2.12 — do not describe 0.2.12 as containing it.
- **[S1 — contract honesty] `Write<R>` promises `result` that replay deliberately withholds.** Open P2 ([ticket](issues/20260914-snapback4-write-result-type-omits-replay-state.md)): server behavior (withhold historic `result`/`current`, return execution identity + `replayed: true`) is the accepted §17 security contract; the client type + `send()` construction + README overstate availability. Callers can receive `undefined` under a required `R`. Fix is representation-only (explicit replay/receipt shape through client + hooks + README), no server disclosure change, existing revocation regressions must stay green.
- **[S2 — docs/behavior contradiction, recurring] Presence card vs. binder classification.** Open P3 ([ticket](issues/20260914-snapback4-guide-gap-presence-prediction-contradicts-residency.md)): card says prediction reads everyone as connected; `bind/residency.rs:117` marks `Builtin::Connected` as `SiteClass::Server` → `predicts: never`. Hit on 0.2.10 **and** 0.2.12 (two builders, same workaround). Ruling 18 option C (.007 §19.1: presence deciding only emits keeps prediction) is the settled direction; lane N1 (`5f4d859b9`) builds it but is not in HEAD/0.2.12. Land it; until then the card or the diagnostic rewrite ("remove connected from this query" — wrong for a mutation) must change.
- **[S2 — stale proposal risk] .008.000/.001/.002 re-propose settled .007 rulings.** Examples: .000 §4 sequencing vs. .007 §14 rulings 1–5 (all seven forms accepted, reads-in-`where` yes, inferred audience yes); .001 §3/§7 vs. .007 §6.1/§6.6/§7 (optional `online only`, inferred audience, paved online mode — all in README §1 "Two ways to run" and guide); .002 §§2–4 vs. .007 §8.1–8.4/§8.13 (result, pending, wasm cache, media cache — all landed). Executing the children literally would duplicate or contradict the implementation record. The program must cite .007 §§12–19 as the completed predecessor and scope itself to the residuals above.
- **[S2 — cross-document tension] Filtering/cursor and projection disclosure need the .007 disclosure contract, not new .008 language.** .000 §3 (filtering/completeness/cursors) and .001 §5 (derived disclosure) touch blind-review territory (LLP 3000 decision 4; .007 §§15/17). The children handle this correctly by deferring to the settled cursor rule (cut page continues after last **rule-visible** examined row, never after a hidden one) and to `N_MAINTAIN_DELTA` — hold that line: any future relaxation here re-enters blind review; the N1–N3 + replay-type landing does not.
- **[S3 — process] A standing "no panel" fence vs. this panel.** [NOT-DOING.md](snapback4/NOT-DOING.md) ("No panel except the two blind reviews LLP 3000 decision 4 names") is a slice-one process fence; Charlie's explicit request for this sanity-check panel overrides it for this purpose, but the family should note the exception rather than silently normalizing standing panels. Related: I agree with the umbrella's implied position — **the existing user authorization ("execute on the ones that are directionally right, use Astra") is sufficient for the lead to select and land the residuals; no redundant author-acceptance bureaucracy per RFC.** Disclosure-sensitive changes remain the only exception (blind review), per standing decision 4.
- **[S3 — evidence honesty] Replay results are calibration, not magnitude claims.** 0.2.12 Astra calibration: holistic 86 (vs 85), target categories 79/89/80 (vs 78/88/74; only the +6 queries_and_live move is clearly outside noise), grade 101/0/18 vs 101/9/9 — the pass count is unchanged; nine iOS assertions moved fail→not-run on identical absent evidence (grader classification, not product change). Ceremony fourth run: 3/3, zero Snapback loops, natural rule 3/3 — but online-only tables, so no proof of retained history/device sync, and it does not exercise the cross-group merge (§18.1) or adoption path (§18.3). The children are honest about N=1/agent-builder limits; keep every future claim in that register. No claim that Snapback is "holistically excellent" or promoted follows from this program.
- **[S3 — acceptance measures agents, not users.]** All "cold builder" acceptance cases (.000 §5.6, .002 §7.6) are agent runs (Astra/Grok/Muse) with same-family scoring. That is the right instrument for ceremony cost, but it does not measure actual users; the program should say so and should retain correction-loop cause analysis (agent vs. mechanism) rather than accepting self-attribution at face value — to the children's credit, .008.000 §5.6 already requires this.
- **[S3 — scope growth] .004 §§4–6 and .003 §4 must not smuggle a platform.** Backup/restore procedure, admin/observability surface, second reference app, server-heavy workflow, "bounded storage" promises — each is valuable, each is outside the slice-one fence ([NOT-DOING.md](snapback4/NOT-DOING.md), LLP 3000 §3). The umbrella's §4 constraint (no new blocking check/registry/hosted target/ratchet) is the guardrail: enforce it. Union audiences, exact-horizon maintenance, automatic projection synthesis stay out (the children correctly exclude them — keep it that way).
