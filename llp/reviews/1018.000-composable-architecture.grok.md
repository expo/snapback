## Material concerns

### 1. Incremental invalidation omits the API that already preserves identity — High

`Runtime::rerun` in `snapback2-core/src/live.rs` already keeps subscription IDs, replaces traces in place, rebuilds indexes **once** after the batch, and on execute error keeps the previous indexes so a later overlapping commit can retry. Tests in `snapback2-core/tests/live.rs` cover that, including recovery. `registry.rs` uses `rerun_all_subscriptions` on successor/reset.

The owner path does not use it. `Writer::rerun_live` (`writer.rs` ~1244) unsubscribes and resubscribes each affected query, so `rebuild_indexes` runs twice per query over **all** subscriptions. It does that because it must stamp `context.now` and `context.read_time` before re-execute (clock-dependent queries; clock advance reruns every live client). On subscribe error it **drops** the live client and sends a terminal frame — the opposite of `Runtime::rerun`’s keep-and-retry policy.

After the first rerun, owner map key and `runtime_id` diverge. Invalidation already maps through `client.runtime_id`. That split is accidental complexity, not a feature.

**Correction:** the first slice is not a new incremental-index design. It is: teach `Runtime::rerun` (or a sibling) to refresh `now`/`read_time` on the retained `Context`, have `rerun_live` call that, keep owner envelope framing (offline vs connected, drain admit, digest skip), and keep dropping the live client only for terminal session/auth refusals. Incremental patch of `ranges`/`exact`/`constraints` (O(old trace + new trace) instead of one full rebuild) is the second slice, and it must target the search-engine index shape, not today’s `Vec<Value>` prefixes.

A failed rerun “retains evidence to retry” is already `Runtime::rerun`. Do not specify it as if it were new, and do not silently change the owner’s terminal-drop policy.

### 3. Cross-query snapshot coherence has no protocol — High

§4 correctly says sharing a subscription is not cross-query consistency, React batching is not a boundary, and a durable seq cannot order clock-dependent observations. It then leaves the actual design as an open question.

What exists today:

- **Same query:** `SharedSubscriptions` one delivery.
- **Writer store:** `OfflineRuntime.commitMany` is one swap for deliveries, facts, settlement, coverage. Enqueue commits intent, grant consumption, and prediction together.
- **Per view:** `QueryView` already separates completeness, liveness, staleness, prediction, connection.
- **Same-query same-seq:** `readTime` orders deliveries in the range store.
- **Follower:** `commitMany` no-ops (`followingPrincipal`); live frames go straight to callbacks. Follower list vs count never share a store swap.
- **Live SSE:** each `subscribeRegular` decodes and publishes independently. A send can update the message list in one frame and the unread count in a later frame.

A first slice that “exercises list and count across one mutation using the existing atomic swap” is a test, not a contract. Without a publication barrier, unrelated views, refused views, and clock-dependent views have no specified behavior.

**Settle this (write it into the document):**

- **Scope = owner commit `seq` (plus `readTime` only to order same-seq frames of one query).** No public application-declared consistency scope in this round. No new hook API. `useQuery` stays.
- **Writer with a store:** after prediction enqueue and after settlement, re-answer every mounted query that the twin can evaluate against that swap, and publish those answers in the same `commitMany`. Queries that cannot be evaluated locally stay on their last view (`partial` / retained), they do not gain completeness by sitting next to a complete sibling.
- **Follower / no-store:** the client holds at most **one** pending seq bag of live frames for queries that `after_commit` invalidated. Publish the bag when (a) every expected invalidated subscription has a frame or a refusal, or (b) **16 ms** elapses, or (c) a later seq arrives. Unrelated queries (not in that seq’s invalidated set) publish immediately. A refused/slow view publishes into the bag as refused/unchanged; it never stalls unrelated views.
- **Bound:** one pending seq (coalesce if a second arrives). No retained extra partition. Buffer cost is in-memory frames already on the wire.
- **Clock:** clock-advance reruns remain a separate publication (existing `Action::Clock`); they must not wait on a mutation seq bag.
- **Reconnect / revocation:** existing reset/supersession paths; a cached result does not inherit a sibling’s authority or completeness. Followers still do not hold.

React/Expo already share `useQuery`. The work is in the client publication path (`subscribeRegular` / decode / `commitMany` notification), not a new snapshot object.

### 4. Follower forwarding does not specify grant/id custody or lost-ack — High

The ticket’s product witness is right. The frozen text does not make it buildable.

A follower has no partition, so it cannot `outbox.enqueue`, cannot consume a grant, and cannot mint intent ids (`client-outbox.ts` throws `E_OFFLINE_FOLLOWER` before any bytes leave). Forwarding **arguments** to the writer is the only legal path: the writer consumes `1 + maxNewIds`, assigns `intent`/`ids`, durably enqueues, and acks **that** envelope.

Unspecified today, and required:

- **Transport:** `BroadcastChannel` named by account partition/principal. Not a second IndexedDB. Web Locks stay lock-only.
- **Ack after durable enqueue**, never after server commit. Follower renders queued/predicted from the ack payload (intent, ids, op, args) in a small ephemeral map — not a retained partition copy.
- **Correlation:** every submit carries a follower `requestId`. The durable outbox row must store it (or equivalent) so **durable enqueue + writer crash before ack** is recoverable on takeover by matching `requestId`, not by guessing `op+args`.
- **Lost ack / unacked:** not admitted from the follower’s point of view. After takeover, if the row is in the inherited outbox, adopt it; if not, the new writer (ex-follower) submits locally as a normal enqueue. Same grant/id rules as a cold writer. No plain `/api/mutation` from a follower, ever.
- **Frozen writer:** new `outbox.status().reason: "writer-unresponsive"` (do not overload `follower`). `ready: false`, `action: "none"`. Bound wait ~2 s then surface that reason; keep retrying; never hang `useQuery`. A frozen writer still holds the lock (existing one-writer contract).
- **Fences:** requests carry `authGeneration` + `operationFence`; writer nacks stale. Sign-out/replacement wipes; expiry seals (LLP 1012). A late ack must not unfence a successor incarnation (`TabFollower` already uses wait-object identity; forwarding must use the same).
- **File cap:** `client.ts` is **1490** lines (limit 1500). Forwarding goes in a new file (`client-forward.ts` or similar), not `client.ts`. `writer.rs` is 1443; do not grow it for this.
- **Bytes:** measure the forwarding module against the LLP 1012 complete local-runtime roots. No second store.

Two-tab witness: both writes settle FIFO in the writer’s outbox order; replay exactly once across writer close; account change in either tab nacks in-flight forwards.

### 5. Derivation “framework” would wrap unlike implementations, and search already has one in WIP — High

On main:

- Ordinary indexes: `reindex_row` deletes all `index_entries` for the row and reinserts (`engine/index.rs`).
- Aggregates: `maintain` / `apply_aggregate` unapply old / apply new (`runner_ops.rs`). In-transaction exactness already holds (cap probes depend on it; LLP 1017).
- Search postings: **not on main**. In `clique-search-engine`, `search_index.rs` already defines `Derivation { steps, scratch }`, trie nodes, postings, and remove-without-re-tokenizing.

Those three share rollback/rebuild/successor-admission *obligations*, not an algorithm. Extracting a trait on current main abstracts two paths and then collides with the third.

**Settle:** no shared derivation type on current main. First slice after search-engine lands: one incremental=rebuild law in the existing conformance suite covering count/sum, ordinary indexes, and search postings (edits, deletes, group moves, rollback, successor). Extract a driver only if that landing still duplicates lifecycle/accounting. Do not add trigger syntax or materialized-view syntax. Client derivations stay twin-over-held-data; an unheld count is never zero; index presence grants no authority (already LLP 1018 cap-count + 1012 search).

### 6. Typed Quarry + reusable functions are investigations, not implementation moves — High if treated as build work

Parent LLP 1018 §5 cut the typed IR unanimously; reopen only on several demonstrated failure classes or a census of machinery deleted. §6 cites two **closed** repairs (nested shape aliases, conditional page provenance). Those are regression material, as the draft says; they do not meet the parent’s reopen bar.

The lowering path is still: Quarry AST (`ast.ts`) → in-memory TS (`program.ts` ~1415 lines, near cap) → executable IR. `lineMap` / `remapVirtualDiagnostic` / `__q_*` temporaries / generated-alias recognizers in checks are real machinery. A deletion census is the right first slice. A compiler replacement is not commissioned here.

`fn` stays deferred under LLP 1011 §0 until a census collapses duplication **without unifying distinct refusal codes**. Shapes already expand at AST. If the census earns a form, it is hygienic, acyclic, call-by-value fragment expansion charged to the caller (shape-like), not `fn`, recursion, or a plan algebra.

`clique-search-compiler` is already adding `value-type.ts` and expanding `type-analysis.ts`. A parallel typed-IR project would fork that lane.

## Bounded implementation decomposition (all six focus areas)

Do not staff this as one program. Each slice amends an existing spec (1001 or 1012), names an implementer and date when commissioned, and lands behind `snapback2/scripts/test.sh` + `caps`.

**Move A — Incremental invalidation (server)**  
1. Route `Writer::rerun_live` through `Runtime::rerun` with `now`/`read_time` refresh; preserve envelopes, drain admit, digest skip; drop live clients only on terminal auth/session errors. Witness: same invalidation/refusal/clock behavior; `rebuild_indexes` once per batch not twice per query. Stay out of search-engine’s `invalidated`/`scope_touches` until that lane lands.  
2. After search-engine lands: incremental add/remove of index entries per replaced trace; unsubscribe of last consumer leaves no entries. Measure rebuild work vs subscription count × affected count. Full re-execute remains the reference.

**Move B — Search integration (already commissioned; this child only fences)**  
Do not implement engine postings, Quarry `wordPrefixes`, held indexes, or `h1` cursors here. Consume them when they land. §5’s law tests attach to that landing. Until then the guide’s `words()` + `searchWords` path is current authoring.

**Move C — Session / follower forwarding (product, LLP 1012 §4 / 1018 §3)**  
1. `client-forward.ts`: BroadcastChannel, writer enqueue, durable-ack, `requestId` on the outbox row, generation/fence nack, `writer-unresponsive` readiness.  
2. Witness: two tabs, one offline write each, both settle FIFO; takeover reload before replay; lost ack; account replacement; frozen writer named reason. Measure bytes. Then, and only then, look for a deletion in `Client`/`TabFollower` coordination.

**Move D — Snapshot coherence and bounded waiting (client)**  
1. Writer-store path: after prediction/settlement swap, re-answer mounted twin-evaluable queries in that same `commitMany`; publish together. List + unread count is the witness.  
2. Follower/no-store path: seq bag with the bounds above.  
3. Reconnect/revocation: cached view cannot strengthen authority/completeness. No new public API.

**Move E — Derivation lifecycle**  
Investigation until search-engine maintain/rebuild is on main. Then law tests. Extract a driver only if duplication remains. Closed operator set stays.

**Move F — Typed Quarry semantics and bounded functions**  
1. Deletion census on nested shapes, consumed write results, conditional pages, short-circuit: printers, `lineMap`, generated-alias recognizers, remapping. Compare diagnostics at Quarry source, plus IR/certificate. Warm `check` budget. Historical repairs are regressions, not live bugs.  
2. Duplication census in real apps (chat/Clique) with refusal-code preservation. Specify a fragment form only if the census earns it. Neither slice replaces the compiler or adds `fn`.

## Concerns

### 1. MATERIAL — Composite `conversationView` continuation vs current page law (§4)

`certificate/page.rs` does not treat `Expr::Object` as a page origin. The compiler pins this: `ops.nested` (`return { rows: page }`) must have **no** `result_pages`. Resume already refuses a query that returns no page.

The witness wants a real composite with list/count/preview **and** “the existing single primary continuation contract” whose provenance the Rust certificate can derive, while forbidding “multiple cursors or [promoting] an unsupported shape.” Those three cannot hold together. `{ messages, count, preview }` is the nested-object shape that is defined to have no continuation.

**Resolution:** State the supported shape in one sentence. Recommended, no language change: `conversationView` returns a record; `messages` is a bounded collection **without** a certified `next`; paging stays on the existing named `thread` query; two mounted consumers still share one snapshot. Do not imply the composite owns `next`. Do not add a designated page-field in records in this slice.

### 2. MATERIAL — Follower timeout / in-flight / `MutationResult` / `ready()` (§8)

On this tree, a follower cannot write: `submitMutation` throws `followerRefusal()`, and `outbox.ready()` is `{ ready: false, reason: "follower" }`. `MutationResult` is only `committed | rejected | queued` (`queued` carries `intent`, allocated by the writer at admission). LLP 1002 documents that triad.

The revision adds BroadcastChannel forwarding, a 2s `writer-unresponsive` path, and receipts keyed by **request** id (exists before intent). It does not specify:

- The client-visible discriminant for uncertainty. Reusing `rejected` + `retryable` invites a fresh request id (forbidden). Reusing `queued` without an intent is a lie. Need a named state that carries the **request** id, not an intent.
- In-flight accounting across timeout. Settling the waiting promise must **not** free the 64-slot or the dedup identity; the writer may still admit. The cap counts unexpired unacked commands, not currently-waiting promises.
- `ready()`: with transport, `reason: "follower"` cannot remain a hard write block, or the two-tab enqueue witness is only reachable by bypassing the public gate. Keep today’s follower refusal **only** when BroadcastChannel is unavailable, as the last paragraph of §8 already says for assets/channels.

**Resolution:** Add one client contract paragraph: new `MutationResult` (or equivalent) for writer uncertainty carrying `requestId`; in-flight/dedup held until ack or command expiration; `ready()` reports `writer-unresponsive` / writer capacity, not `follower`, when forwarding exists; late acks cannot resolve a successor incarnation.

### 3. MATERIAL — `fn` elaboration site vs retained shape expansion (§6 vs §7)

§6 **retains** shape expansion (today `quarry/expand.ts`, AST, depth 8 / 4096 nodes, import/cycle machinery). §7 puts expression-only `fn` **on the bound tree** and says nested helper **and** shape expansion share **one** budget.

Those are different phases. A bound-tree expander cannot honestly share `expand.ts`’s counter unless that pass exports consumed nodes and never instantiates helpers. Two expanders will double-count, miss cycles, or charge the certificate twice. The work-order table also lists Typed Quarry and Bounded expressions as sibling compiler rows; `fn` on the doomed TS recovery path (`lower/helper-expansion.ts` is a different, TS-inliner) would be thrown away.

**Resolution:** Pick one site, in this document. Recommended: instantiate `fn` in the **retained** `expand.ts` pass beside shapes (same counters, same `from module` / cycle rules, same “no caller locals”). The bound tree and IR see already-expanded expressions; direct Quarry does not re-expand. Do not land `fn` on `lower/helper-expansion.ts`. If you instead move both to the bound tree, say that `expand.ts` is replaced in the §6 deletion, not retained.

The round-3 seams are closed in this text and are implementable against the existing Snapback 2 surfaces without material protocol holes. Existing `MutationResult` is already `committed | rejected | queued`; adding `admission-unknown` is an extension, not a redesign. Search stays over budget and unqualified; this revision does not claim it ready.

## Strengths (seam closure)

**Record composite vs pagination (§4).** `{ messages, count, preview }` has no certified continuation, no designated page field, no multiple cursors, and no drain. Pagination stays on a separately named top-level `thread` page with no joint atomicity. A slow/denied/partial/refused composite is one outcome. That matches the page law (`Expr::Object` does not yield a result page).

**One bound instantiation for shapes and `fn` (§6–7).** Both instantiate once in the bound elaborator, share one expansion budget and definition/use stack, and replace `quarry/expand.ts` after parity. Import/diagnostic behavior survives; production does not keep a second AST expander or the TS helper inliner. Sequencing is explicit: direct value/read core first, oracle comparison, then one production switch.

**`admission-unknown` and recovery (§8).** Fourth mutation outcome `{ state: "admission-unknown", recovery }` at two seconds without ack. `recovery` is a serializable opaque token bound to protocol version, request ID, payload digest, expiration, backend/carrier, principal/auth epoch, and durable partition incarnation; no bearer, query data, or argument copy. `client.recoverMutation(ref, args, recovery)` re-supplies operation and args, verifies scope, and returns `queued` only from a durable receipt’s intent/IDs. Mismatching account/epoch/partition refuses without a write. Discovery timeout before send stays ordinary follower refusal (known non-admission).

**Timeout retains slot/id (§8).** In-flight identity is kept until ack or expiration. Late acks may update only the still-current local session and release their own slot.

**Readiness with forwarding (§8).** With forwarding available, readiness is discovery / `ready` / capacity / `writer-unresponsive`. `follower` is the hard refusal only when forwarding is unavailable. Hint is rechecked atomically on admission. Uploads and ephemeral publish keep explicit follower refusal and do not become outbox commands.

**Partition incarnation (§8).** Writer announces writer incarnation, auth epoch, and durable partition incarnation. Init under the lock; takeover preserves it; wipe mints a new one even on same principal/epoch. Recovery against an old incarnation cannot admit. Wipe/relogin at the same epoch is a named witness.

**Persisted clock floor (§8).** Monotonic admission/pruning floor is persisted so wall-clock rollback cannot make a pruned command admissible. Prune only after the command can no longer be admitted; never evict a live dedup receipt to admit another. Clock rollback after pruning is a named witness.

**Finite search input inventory (§2).** Tips are native `26c9fd5e0`, compiler `d3e497acd`, twin `82c43ca45`, domain repair `0ecd6015a`, relative to cohesive candidate `3eba7655bf5737bc184a68c1144b729ab205f66a`. Each delta is integrated, shown equivalent, or superseded; regression witnesses are retained either way, including superseded implementations. Finite snapshot; no demand that every active branch freeze. Literal absence, collection/capture/custody, and maintained-address controls stay.

**Search not claimed ready (§2, §9–10).** Twin complete-runtime 75,815 gzip vs 66,000 ceiling / 64,000 target, failed. Existing native/web/Expo and warm/cold qualification remains required for any search capability claim. No implementation or performance claim follows from this text.
