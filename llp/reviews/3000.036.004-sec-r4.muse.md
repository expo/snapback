§8 authorizes two new soundness-relevant moves: (a) proving operation-specific authority from leading straight-line `require` facts, (b) refuting general `always` via a partial concrete evaluator over snapshots plus engine-backed operation challenges.

Material risks:

1. Snapshot-seeded "counterexamples" vs §1 refuted definition. §8 says general `always` "can still receive concrete counterexamples" from a "schema-valid snapshot", with violations "labeled as such, never reachable traces". A snapshot evaluation is not a replayed engine admission. §1 requires refuted = concrete, replayed database/rule counterexample. §8 does not explicitly downgrade snapshot-only witnesses to unproved, so a literal implementation can report refuted on a row no ingress could ever commit. False-refutation risk, not an allowed unproved case.

2. Snapshot validity under-specified. "Schema-valid" does not require actual validation/defaults/constraints on every ingress, including the exact non-whitespace minimum and defaults from §2. A schema-valid but validation-rejected row (e.g. null image validation would reject) can seed a false violation. Same for live vs retained-history rows and expiry: §8 blocks "unmodeled expiry/captures/derived tables" but never requires live-only, leave-policy-consistent, validation-consistent seeding. False refutation.

3. Partial evaluator leaf semantics not pinned to §3. §3 fixes null-equals-null, null-vs-literal, Id-vs-Text, noninteger ordered comparison false, missing ordinary field loads null, missing live reference unknown including under negation. §8's evaluator ("row-local values, Boolean connectives, comparisons, server clock, raw named-key existence") never references that table. A host-semantics implementation (null=null false/unknown, Id/Text conflated, missing field as unknown) both misses real violations and manufactures false ones. Since §8 authorizes refutation through it, divergence is false refutation.

4. Clock modeling for refutation. Evaluator may judge "server clock", while §2 keeps temporal assertions explicitly unproved. No clock model (commit time, arbitrariness, monotonicity) is given. Arbitrary-clock refutation of a temporal `always` is unsound if runtime clocks are constrained. Conflicts with the temporal-unproved rule.

5. Require-to-write soundness gaps. "Stability checked against every intervening write" on a literal reading excludes the covering writes themselves: a require observing table T followed by a write changing T (the very write being authorized) can still be counted as stable, proving new-image policy from old-image facts. Old/next image binding for require facts is never stated, unlike §3's full bound identity. Concurrent interleavings between require and write are also unaddressed; stability covers only intra-operation writes with no stated atomicity/isolation assumption. Each permits false proof.

6. Opaque writes in stability. Helper calls/prior writes are "unproved unless separately reduced", and the implementation uses "only leading straight-line requirements before any other statement". But stability is phrased as writes, not opaque effects: a later helper call with unknown write set can evade a direct-write-only stability check while invalidating require facts. Must be helper-conservative explicitly. As written, false proof.

Conservative choices noted and accepted (allowed): leading-only prefix, no negative probes, no live references, no branch/loop/alias/helper/changed-viewer credit, effective write rule plus owner-bypass and implicit effects still obligatory, unknown-not-false, existential over stored rows, no-op/rollback exclusion, multi-operation/HTTP/device left as coverage obligations.

The conservatism is good, but findings 1-6 each let a spec-compliant implementation falsely prove or falsely refute. They need tightening before implementation, not fix-forward notes.
