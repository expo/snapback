### Findings

#### F1 (High) — Web starter throws away the text of a send that fails after custody

- Where: `snapback4/apps/chat/src/Composer.tsx:39-44`, `snapback4/apps/chat/src/intents.ts:3`, `snapback4/apps/chat/src/Composer.tsx:74-78`. `snapback4 init --web` copies these files.
- What is wrong: The old composer cleared the field only when the awaited outcome was not `failed`, and the default wait did not return until settlement. With `{ waitSeconds: 0 }` the same `!== "failed"` check now runs on `pending`, so the submitted text leaves the field as soon as the write is admitted. The saved intent is `{ id, room, operation }` — no body. The receipt row then says "Compose a replacement" and does not show the text. A server refusal (not a member, validation, and so on) arrives later through `usePendingWrite` and has nothing to edit. Expo keeps `intent.body` and restores it with Edit. Pre-custody `failed` still leaves the web draft alone; this hole is only the post-custody path that `waitSeconds: 0` made the common one.
- Evidence: Read the composer, `Intent`, and the receipt row. `clearSubmitted` runs for every non-failed return, including `pending`. The React case "refusal preserves and explains the draft" resolves the mutate promise with `failed` directly, so it never takes this path and would stay green.
- Proposed fix: Store the submitted body on the web intent, as Expo does. On `failed`, show that text and put it back in the field on edit. Do not depend on the mutate return still being `failed` after `waitSeconds: 0`.

#### F2 (Medium) — Expo thread blanks messages that are already on screen when an older page is loading

- Where: `snapback4/apps/chat-expo/src/Thread.tsx:70`. `usePage` builds that `read` in `snapback4/packages/snapback4/src/react.tsx:175-192`.
- What is wrong: The list is `data={"data" in read ? items : []}`. `usePage` only pushes ready pages, then if a later page is loading it sets `read` to that loading snapshot while `items` still holds the earlier pages. The new gate throws those rows away. The previous starter passed `items` through. A page-1 gap is already empty `items`, so this gate does not add protection; it only blanks the thread when the user loads older history. The reads card says earlier pages stay visible.
- Evidence: Compared `Thread.tsx` with `git show 1d6325c868:snapback4/apps/chat-expo/src/Thread.tsx` (`data={items}`). The new React case sets every observation to `loading`, so `items` is empty either way and does not catch this.
- Proposed fix: Render `items`. Keep the loading / denied / incomplete lines tied to `read`. Page 1 loading already yields `items: []`.

#### F3 (Medium) — The reads-card fence says every incomplete query stays `loading`

- Where: `snapback4/crates/snapback4-lang/src/guide/reads.rs:65-68`.
- What is wrong: "A query the device cannot answer completely stays `loading` and asks no server while this device holds a predictable pending write to a table the query reads." The no-server half matches `blocked()` / `recover()` in `local-query.ts`: a predictable pending write whose footprint intersects the query (or a missing footprint, which blocks every query) does not fall through to the server. The "stays `loading`" half does not. An engine-withheld answer stays `loading`. A published partial page (`complete: false`, data present) stays that partial page under the same fence. The paragraph above already tells the reader to render "Results may be incomplete."
- Evidence: `local-query.ts` `pending` (lines 86–92), `blocked` (95–98), and `routeLocal` (172–181): non-withheld partial answers return `localCandidate()` when `blocked()` is true, not `{ loading: true }`.
- Proposed fix: Say that an engine-withheld answer stays `loading` and is not sent to the server, and that a partial page stays partial. Keep the unrelated-table sentence, and mention that a write with no predicted footprint still blocks every query.

#### F4 (Medium) — `PendingSend` observes a saved id and then submits a different one

- Where: `snapback4/packages/snapback4/CLIENT-AND-OPERATIONS.md:947-951`. The hook that makes this matter is `snapback4/packages/snapback4/src/react.tsx:240-255` and `264-291`.
- What is wrong: The example takes `savedId`, passes it to `usePendingWrite`, and the button calls `run(args, { waitSeconds: 0 })` without `{ id: savedId }`. That mints a new write. `last` updates only when the write's serial is `latest`, so the click replaces observation of the saved id. The paragraph under the example says to submit with `{ id }`, but the block agents compile does not.
- Evidence: Read the example and `useTrackedMutation`. The saved id is bound to serial 0; `run` advances `latest`, so a later settlement of `savedId` does not call `setLast`.
- Proposed fix: Either drop `savedId` from this snippet, or call `run(args, { id: savedId, waitSeconds: 0 })` and do not use that button as a second send. Point reload-safe observation at the client card's saved-intent form.
