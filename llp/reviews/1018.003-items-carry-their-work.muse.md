## 3. Ranked concerns

**1. Blocker — unpredicted-edit settlement has no evidence.** §10's table requires "current-authority target read/negative at or after commit, or existing terminal-progress proof" and admits the landed runtime may not supply it. Load-bearing: an edit mints no row id, `entry.arrived` is set by any pinned-ID row arrival including fan-out rows (Evidence `range-store.ts:1139-1142`), and overlay retirement uses custody-level arrival/misses (Evidence `range-store.ts:996-1033`; LLP 1012:936-948), explicitly not per-item proof — which §10 itself states. Failure: committed edit either sticks forever as "awaiting delivery" or retires on an unrelated delivery to the same conversation. Admitted risk is material. Smallest fix: before building, spike one question — what durable fact distinguishes "this edit's write is in the readable target" from "target readable for other reasons"? If none exists, scope v1 to "committed/unpredicted edits stay visible until dismissed" and defer auto-retirement; do not ship the table's last two rows on `arrived`/misses.

**2. Major — atomic collection publication over two independent sources is unspecified.** §9 promises one publication after query value, prediction attribution, and outbox inputs are consistent, fenced by account/session/program/revision. But the base is `ClientQueries.observe` with per-query keys, lazy shared entries, and first/last-subscriber lifecycle (Evidence `client-observed.ts:136-153,180-202`), and query-input tracking covers answers/rows/outbox/overlay (Evidence `query-inputs.ts:7-10`). No design shows how `observeCollection` derives from the ordinary query entry keyed additionally by descriptor identity, how it subscribes to both query and outbox revisions without tearing or a second cache/transport, or ordering vs reset. Failure: commit lands between query and outbox snapshots → duplicate preview+bubble or dropped pending for one frame or permanently under StrictMode remount. Smallest fix: specify the dependency graph — collection as pure derivation of `(queryEntry revision, outbox revision)` with a single fenced swap, reusing `SharedSubscriptions`, or drop the new observer (see §4).

**3. Major — missing targets, deletes, and denied/refused suppression leave visibility gaps.** §8 correctly refuses to resurrect bodies, parking target-less updates/removals in the shared outbox. But then a pending edit to a capped-out or null-body row is invisible in-thread; a page of 50 tombstoned messages displays zero items with `receipt.next` intact (§8) while its creates sit in an unsorted tail — the ordering contract with continuation is unclear. Predicted deletes (`OverlayRow.removed`, Evidence `range-store.ts:232`) have no item representation defined: does the row vanish pre-commit? §9 suppresses rows *and drafts* on denied/refused — check against LLP 1012 §5 rule 4 retained-history rendering, where a denied delivery presents prior history. Failure: `unsend` predicted offline makes the bubble disappear before authority; denied thread hides the user's own queued send with no path forward. Smallest fix: define per-case visibility explicitly, including delete-preview behavior, and make suppression preserve explicitly-dismissable failed/queued own-intents via the outbox path rather than hiding them.

**4. Major — multiple edits to one row are attached but not resolved.** Keeping several actions per row (§9) fixes today's `entries.find` first-match loss (Evidence `Thread.tsx:22-23`). But `item.pending` as an ordered list with `draft`/`predicted`/`data` coexisting leaves open: which body renders when two queued edits with different bodies pend? Does `predicted` mean any or all actions predicted? The twin's `local.predicted` is partition-wide triples (Evidence `twin.ts:247-264`), so per-row `predicted` must be re-derived by `(table,id)` address — stated but not mapped to the overlay's `(intent → rows)` shape. Failure: two edits show the older body with a "sending" badge, or a predicted flag from an unrelated intent marks the row. Smallest fix: specify render precedence (authoritative body + action list, never merged body) and define `predicted` as "contributing overlay at this address in this revision," with a test for two-edits-one-conflict already in §11 made normative.

**5. Moderate — fluent builder + two new observers cost more than the reducer they delete.** `collection(...).create/update/remove` with `select`/`belongs`/`key`/`draft`/`order`, descriptor identity, inferred op-arg types, plus `observeCollection` and `outbox.observe()`, is a mini-framework against a ~1,500-byte headroom concern (§6: lane at 80,524 vs 82,000 ceiling; NOT-DOING now 66,000 complete-runtime ceiling). Total app complexity must count binding + renderers + adapters (§11 says so), and §8's "if the binding grows into old `shared/log.ts`, reject" has no enforceable gate. Failure: three concepts replace one helper while byte budget and docs surface grow. Smallest fix: budget the addition now and make the builder optional — a pure join function covers chat; fluent/observer layers land only if measured re-render or duplication warrants.

**6. Moderate — stale/partial/held/reset semantics for items are incomplete.** §7 preserves `status`/`reason`, but per-item staleness is undefined: a stale page with predictions shows which badge first (§2 open question 1 carries over)? `held` data with no receipt plus drafts risks presenting unvetted rows as thread history. Account reset invalidation "before successor values publish" restates 1018.000 §4's reset rule (Evidence `client-observed.ts:194-202`) without an ordering mechanism across the two sources in concern 2. *Inference:* current text is consistent but underdetermined; missing evidence is the reset/refresh fencing design from the other lane. Smallest fix: state that item-level badges never override query `reason`, and tie collection invalidation explicitly to the same fence that retires the query entry.

## 4. Simpler alternative

Ship the join as a pure SDK function; add no descriptor, no collection observer, no outbox observer in v1:

```ts
type Item = { key: string; data?: Row; draft?: { body: string };
  pending: OutboxEntry[]; predicted: boolean };
function toItems(rows: Row[], entries: OutboxEntry[],
  predicted: PredictedRow[], isMine: (e: OutboxEntry) => string | null): Item[]
// screen:
const view = useQuery(api.deliveries.thread, args);
const { entries } = useOutbox();
const items = useMemo(() => toItems(view.data ?? [], entries,
  view.local.predicted, e => matchThread(e, args)), [view, entries]);
```

`isMine` is the honest app input (today's `postFor`/`editFor`/`unplaced` in `Thread.tsx:22-25`, generalized). SDK owns dedup, key stability, tail placement, and `predicted`-by-address; screens own the one-line memo. Tradeoff: two subscriptions can tear for a frame and per-screen memo repeats trivial work — bounded, visible, and durability-safe — versus a new resource graph, identity keys, lifecycle, and bytes. Graduate to `observeCollection` only with measured need. This preserves every honesty property in §7 while deleting the framework risk in §9–§10.
