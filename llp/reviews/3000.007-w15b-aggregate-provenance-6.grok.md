## Findings

### 1. Medium — `matching` and seek bounds do not enter cardinality

**Where.** `snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:395–404` (read) and `:558–562` (merge).

**What.** `where` unions the predicate into the page’s cardinality (`401–402`), so `count(posts[] first 50 by byScore where .score >= lo)` is silent when `lo` is an argument (`review_f17_text_length_and_filter_cardinality` `1108–1111`). `matching` and each seek value are evaluated for writes and then discarded. A seek is also the paved spelling: binding rewrites a next-column `where` into a seek and tells the author to write it in the key (`bind/program/reads.rs:89–98`).

**Failing program.**

```quarry
table posts:
  body: text <=200
  score: int
  by byBodyWords: words(body), id
  by byScore: score, id
  public 'posts'
  insert <- allow
  update <- allow
mutation setHits(q: text <=100, lo: int):
  update posts['seed'] { score: count(posts[] matching q first 50 by byBodyWords) }
  -- also: count(posts[score >= lo] first 50 by byScore)
```

Every write is a caller-determined hit count of a stored page, but the note fires because cardinality stays `READ`.

**Smallest conservative demotion.** Same as filter: `cardinality |= matching.all()` and `cardinality |= seek.value.all()` on reads; `bits |= matching.all()` on merges. Do **not** mix equality keys (`likes[postId]` must stay a read-group count — `1016–1018`).
