# Review: LLP 0234 — Visibility override governance

**Reviewer model:** gpt-5.6-sol (xhigh)

**Provider/runtime:** OpenAI / Codex

**Date:** 2026-08-15

**Document revision reviewed:** 2026-08-15 (distinguish LLP 0231 D7 call-local handler reads from governed invocation overrides)

**Redacted:** No

**Method:** Independent fresh review of LLP 0234 in full, with LLP 0231, LLP 0173, the current codegen warning paths, and the repository push-gate implementation as specified context. No other review artifact was consulted.

## Findings

1. **MATERIAL — G0 assigns predecessor separation to a gate that ordinary pushes do not execute.** D3 makes codegen intentionally accept a valid approval closure from the same current tree and assigns remote-predecessor enforcement exclusively to pre-push (`llp/0234-visibility-override-governance.rfc.md:351-382`); G0 and Acceptance 3/7 then assume that pre-push rejects the self-approved update (`llp/0234-visibility-override-governance.rfc.md:885-893`, `llp/0234-visibility-override-governance.rfc.md:1088-1093`, `llp/0234-visibility-override-governance.rfc.md:1112-1114`). The actual tracked hook delegates only to `drift-prone-gates.mjs` (`.githooks/pre-push:32-35`), whose default is non-strict and returns success without running selected commands (`scripts/drift-prone-gates.mjs:249-284`): `origin/main` commands are deferred and non-main commands are not run (`scripts/drift-prone-gates.mjs:877-919`), exactly as LLP 0232 requires (`llp/0232-green-pointer-development-model.rfc.md:277-303`). Therefore a same-tree approval plus widening can pass codegen and land through the ordinary repository path; the scheduled backstop can only report the violation after authority is live. A local hook is also not remote admission authority because `git push --no-verify` skips it. **Suggested resolution:** make G0 require a non-deferable, trusted admission mechanism for every updated ref (for example a protected remote check/pre-receive-equivalent or a remote-notarized predecessor witness verified by codegen/activation), explicitly outside LLP 0232's frozen-record deferral and without a local bypass as the authority. Add ordinary-mode, non-main, multi-ref, and hook-bypass fixtures; do not allow override generation/activation until that remote mechanism is proved.

2. **MATERIAL — D7's call-local boundary is not transitive across `action.runMutation`, leaving a governed-override bypass.** D1 says elevation cannot be activated by an action or schedule and that scheduled/no-principal work remains governed (`llp/0234-visibility-override-governance.rfc.md:167-178`), but Acceptance 1 tests only the immediate handler kind (`llp/0234-visibility-override-governance.rfc.md:1080-1083`). Today an action exposes `ctx.runMutation` (`packages/snapback-harness/ctx-bootstrap.js:997-998`), and the host invokes the nested mutation with cloned auth (`src/runtime.rs:4147-4166`) and `InvocationSource::NestedMutation` (`src/local.rs:3473-3483`). The Ibex context then chooses `Mutation` mode solely from writability (`src/runtime.rs:2018-2022`), while elevated reads are refused only when the *current* mode is `Action` (`src/runtime.rs:3196-3200`, `src/runtime.rs:3300-3304`). Thus a system cron/action can move its read into a nested mutation using `ctx.db.elevated` and obtain the Class-R bypass without any override declaration, expiry, approval, or ratchet. **Suggested resolution:** define the fence over root invocation provenance, not the currently executing function kind: `NestedMutation`, action, cron, job, `system`, and `capturedGrant` ancestry must never admit D7 elevation. Carry that trusted root provenance into every nested handler and reject elevated host calls before storage access. Add a G0 acceptance fixture in which a system action/cron calls a mutation containing each elevated read form and prove refusal, while a direct caller-backed named query/mutation remains admitted.

3. **MATERIAL — G1/G2 can close with restricted tables still read through uncomposed plan surfaces.** The current omission warning is accurately present at `packages/snapback-codegen/index.mjs:2869-2945`, but the same generator separately emits only a warning when relational, bounded-children, and snapshot-batch reads do not compose a restricted table policy (`packages/snapback-codegen/index.mjs:3815-3897`). Those surfaces retain their own visibility declarations, including `public-read` (`packages/snapback-codegen/define.mjs:3160-3183`, `packages/snapback-codegen/define.mjs:3253-3261`). G1 requires zero implicit tables and override defects but says nothing about `SNAPBACK_TABLE_VISIBILITY_UNCOMPOSED_READ_SURFACE` (`llp/0234-visibility-override-governance.rfc.md:895-909`), and G2 promotes only omitted table visibility (`llp/0234-visibility-override-governance.rfc.md:911-919`). An engineer can therefore leave the table restricted (so neither ordinary-policy nor override ratchets grow), route the read through one of these surfaces, and declare that surface public. That contradicts LLP 0231's every-read table locus (`llp/0231-entity-and-permissioning-recommendation.rfc.md:199-227`) and is a direct visibility-widening escape. **Suggested resolution:** make G1 require zero uncomposed restricted read surfaces across the required and packaged-consumer corpus, and make G2 either compose the table policy into every such plan class or fail generation for that use. Add negative fixtures for relational root/joined, bounded parent/child, and both snapshot-batch node classes; a surface-specific declaration must never be broader than the table policy without a governed override.

4. **MATERIAL — the required predecessor ordering for delegated approvers is stated but has no enforcement transition.** D2 requires a new/widened delegation and its author ruling to land before any grant that relies on it (`llp/0234-visibility-override-governance.rfc.md:250-255`). D3's merge-base check, however, runs when a later widening consumes an approval closure (`llp/0234-visibility-override-governance.rfc.md:351-400`); it does not require the owner-map delegation to predate creation of that approval. A first push can therefore co-land the owner-map addition, delegation ruling/record, and approval record; a second push can consume the now-remote closure and satisfy the specified comparator, even though the grant was issued in the delegation's own push. Acceptance 4 checks current-tree owner-map equality but has no same-push delegation/grant negative (`llp/0234-visibility-override-governance.rfc.md:1094-1100`). **Suggested resolution:** give owner-map additions/path widenings their own predecessor ratchet. When admitting a new approval record, pre-push/remote admission must validate its approver against the owner map at that update's merge-base and require any delegation closure there unchanged. Add a fixture proving that delegation plus dependent approval in one push is refused and that delegation push → approval push → widening push succeeds.

5. **MATERIAL — fixture activation custody is not bound into the approved or ratcheted authority.** D4 makes the matching committed fixture-profile record the reason a fixture override may be non-expiring and says changing app registration, target profile, or data/principal class is incomparable growth requiring a production grant (`llp/0234-visibility-override-governance.rfc.md:470-491`). But D1 has no fixture-profile identity/digest field (`llp/0234-visibility-override-governance.rfc.md:180-189`), D3's `scopeDigest` binds only a fixture sentinel rather than the profile record (`llp/0234-visibility-override-governance.rfc.md:329-335`), and D5's baseline/growth facts omit the profile binding (`llp/0234-visibility-override-governance.rfc.md:516-545`). Consequently the profile record can be rebound or broadened while the override's approved scope and exact-set baseline remain byte-identical. The host may bind a newly generated bundle to the edited record, but no remotely prior production grant is mechanically required as D4 promises. **Suggested resolution:** include stable fixture-profile id, canonical profile-record digest, target-class ceiling, and synthetic-principal/data classification in the override declaration, scope digest, approval, bundle, projection, and D5 baseline. Treat any profile rebind or incomparable/broader record change as growth, and add same-push mutation fixtures for app registration, hosted/production reach, credentials, and data class.

6. **MATERIAL — the 90-day maximum can be defeated with a future `issuedOn`.** The approval schema carries authored `issuedOn` and `expiresOn` (`llp/0234-visibility-override-governance.rfc.md:300-327`), while D4 limits only the interval from `issuedOn` to `expiresOn` and specifies runtime checks only for the expiry boundary (`llp/0234-visibility-override-governance.rfc.md:433-466`). It never makes `issuedOn` a not-before boundary or requires it to be no later than trusted approval/admission time. A record issued in 2099 and expiring 90 days later therefore satisfies the stated duration check yet is usable immediately under the specified runtime rules, turning a 90-day grant into decades of present authority. Acceptance 9 exercises warning/expiry but not future issuance (`llp/0234-visibility-override-governance.rfc.md:1120-1123`). **Suggested resolution:** define and enforce not-before semantics using trusted host time at generation, activation, and read, reject an `issuedOn` later than the remote-observed approval admission date (apart from a fixed clock-skew bound), and cap `expiresOn` at 90 days from that trusted admission/issuance bound. Add future-dated and clock-boundary acceptance cases with a stable refusal code.

7. **MATERIAL — the ordinary-policy baseline does not retain enough provenance for history-independent closure validation.** D5 defines the second baseline as each table's current normalized policy and digest, then says codegen in the current tree verifies the matching transition closure while Git-aware pre-push handles growth (`llp/0234-visibility-override-governance.rfc.md:556-604`). After a widening has landed, however, current-tree codegen cannot distinguish that state from an initial restricted policy or a narrowing: the table declaration has no transition pointer, and the baseline stores no predecessor digest, admission kind, approval path, or closure digest. Deleting or replacing a transition closure in a later policy-equal push causes no policy growth, while D6's required `tablePolicyTransitions[]` history can silently disappear (`llp/0234-visibility-override-governance.rfc.md:623-641`). Thus the claimed artifact-closed, durable, auditable second ratchet is not implementable from the specified records. **Suggested resolution:** make every table-baseline entry carry immutable admission provenance (initial/G1 receipt/new-restricted/transition), predecessor policy digest where applicable, transition approval path, and approval-closure digest, or introduce an append-only transition ledger bound by the baseline. Codegen must validate that provenance exactly without Git; remote admission must govern any removal/rebinding. Add a post-landing fixture that deletes or mutates a transition closure while leaving the policy unchanged and prove refusal.

VERDICT: MATERIAL
