# Paper archetype, wave 3: calendar against LLP 0329.014.000 v0.1

**Respondent:** Claude Fable 5 · **Design under test:** `design-calendar.md` (codex), fixed · **Target:** LLP 0329.014.000 v0.1 incl. §9.1 and §11; v1 constructs from LLP 0329.014.004 used where marked *(v1)* · **Prediction under test:** LLP 0329.014.003 #10.

Headline. Prediction 10 named five things. Three hold as stated (the seam is the largest gap; external principals extend the identity kind; detail levels are the protection-class split). One holds in a sharper form: the seam cannot be an effect-only producer, because three operations need zoned resolution *inside* a transaction (the first instant at create, expansion behind or beyond the projection at read, local-clock reminder due times), so it is a **value-model operator over a certificate-pinned tzdb version**. One is wrong in form: free/busy is not an `exists` over hidden rows — per-granule `exists` is 1.79 M probes and a maintained `count` discloses multiplicity — it is a **maintained interval coverage** with a declared `readable`, a kind the spec lacks. Reminders need the timer index *plus* batched firing *plus* a way for a system program to evaluate a recipient's rules (`visibleTo`). Two spec rules give wrong answers: **an empty page under a hoisted-false readable is returned as `[]`**, so an admitted free/busy program reports a denied or nonexistent subject as *free* (invariant 10); and **K5 prices invariant 3 at 1.5 B freeze timers** where a commit-time constraint costs nothing. L1–L9 refer to §6.

### 2. Schema in v0

Protection classes are tables — identity-and-time, titles, details, guests, responses, audit — so the design's matrix is five read rules, not column grants (`E_SECRECY_MIX`, v1). Detail levels are integers (1 free/busy, 2 titles, 3 full). A recurrence key is the original civil datetime as fixed-width ISO text: codepoint order *is* civil order. `head(s)` is `db.get(series, s)`; other helpers (`adminOf`, `memberOfGroup`, `resourceAdmin`, `autoApprove`, `ownerOf`, `myOrg`) are one-probe reads in the style of `inOrg`; every validity `interval` has a `state` flipped by two schedules per row (v1). v1 constructs used: `any`, `getHidden`, `partitioned()`, `unique`/`cap` `{ where }`, `hashed`, `bearer`, `int({ sequence })`, event-coupled transitions. *L·* marks §6 additions.

### 3. Operations in v0

Grouped by the design's §5. Certificates are in §1.

**Op 3 — createEvent.** First attempt resolves the first occurrence with `Intl`/`Date`: **`E_OPAQUE`** — *zone arithmetic is not in the subset; rewrite: accept resolved instants as arguments, or an effect computes them.* Both rewrites are admitted and wrong: the engine cannot check invariant 1 (a client may post 09:00 New York as 14:00 UTC in July), and every room claim, busy run, and reminder inherits the unverified instant. Corrected form under L1:

```ts
export const createEvent = mutation({ actionId: id(), calendarId: id(calendars), onBehalfOf: id(), uid: text({ max: 255 }), title: text({ max: 500 }), details: json({ maxBytes: 24_000 }), privacy: text({ max: 8 }),
    timing: json({ maxBytes: 2_048 }), rule: json({ maxBytes: 2_048 }), recipients: list({ address: text({ max: 320 }), role: text({ max: 8 }) }, { max: 100 }), resourceIds: list(id(), { max: 5 }) }, ({ db, ctx, args }) => {
  if (db.get(clientActions.byPrincipalAction, [ctx.viewer, args.actionId])) return replay(db, args.actionId)          // duplicate action ids return the original result
  const eff = args.onBehalfOf ?? ctx.viewer
  db.require(eff === ctx.viewer || db.exists(delegateGrants.byDelegateOwnerScopeState, [ctx.viewer, eff, 'edit_events', 'active']), 'E_NOT_DELEGATE')
  const seriesId = ctx.newId(), segId = ctx.newId(), t = args.timing
  const r = zoned.resolve(t.startLocal, t.tz)                    // L1: { instant, offsetSec, resolution: exact|gap_shifted|overlap_earlier } under ctx.tzdb; invariant 2 is r.resolution
  const ref = `${seriesId}:${segId}:${t.startLocal}`
  db.insert(series, { id: seriesId, calendarId: args.calendarId, organizerId: eff, externalUid: args.uid, state: 'active', scheduleGeneration: 1, contentRevision: 1, materialRevision: 1, privacy: args.privacy, /* … */ })
  db.insert(scheduleSegments, { id: segId, seriesId, generation: 1, ...t, rule: args.rule, createdAt: ctx.now() })
  // eventTitles and eventDetails revision 1: two inserts
  db.insert(occurrenceProjections, { id: ctx.newId(), ref, seriesId, calendarId: args.calendarId, privacy: args.privacy, generation: 1, key: t.startLocal, resolvedStart: r.instant, resolvedEnd: r.instant + t.durationMs, dstResolution: r.resolution, tzdbVersion: ctx.tzdb, state: 'active', frozen: false })
  for (const g of args.recipients) {
    const epoch = db.getHidden(addressEpochs.byNormalizedActive, [normalize(g.address)]) ?? newExternalContact(db, ctx, g.address)   // v1 getHidden: branch and write, never return (contract 6)
    const pid = ctx.newId()
    db.insert(participations, { id: pid, seriesId, role: g.role, addressEntered: g.address, invitedRevision: 1, state: 'invited', currentResponse: 'needs_action', responseRevision: 1 })
    db.insert(participationRecipients, { id: pid, seriesId, recipientId: epoch.principalId, addressEpochId: epoch.id })
  }
  // ≤ 5 resourceRequests { when: [r.instant, r.instant + t.durationMs), state: 'pending' }
  // … busySegments (organizer), authorityAudit { actorId: viewer, effectiveId: eff }, the clientActions receipt, and
  db.insert(outbox, { kind: 'series.created', aggregateId: seriesId, generation: 1 })      // → projection job, invitation mail (mints capabilities), fan-out > 100, OOO auto-declines, display names (L4)
```

`newExternalContact` is `insertIfAbsent` (v1), so a race never becomes a refusal revealing that the address exists. OOO auto-declines are the `phase: 'system'` continuation's writes (the organizer may not respond as the recipient); their `sequence` follows the participation's, which makes op 10's watermark exact. Tokens are minted by the mail effect and attached through `attachCapability`. Prediction: `partial` at the `getHidden` site.

**Op 2 — freeBusy.** First attempt scans `busySegments.bySubjectStart` and unions the page: **`E_STRUCTURAL_COUNT`** (§9.1.8) — *`union` reduces rows the caller cannot read into a fact about `subjectId`; rewrite: a maintained aggregate with `readable`, or a caller-scoped computation.* Neither paste fits: the fact is an interval set, and a maintained `count` per granule discloses multiplicity (invariant 9). The predicted form — an `exists` per 5-minute granule under a declared existence disclosure — is 17,856 probes per subject: `E_BOUND`. Corrected form under L2:

```ts
export const freeBusy = query({ subjectId: id(), from: time(), to: time() }, ({ db, ctx, args }) => {
  db.require(args.to - args.from <= 62 * 86_400_000, 'E_RANGE')
  const runs = db.scan(busyCoverage.bySubjectStart, [args.subjectId], { range: { gte: args.from - 60 * 86_400_000, lt: args.to }, take: 8_928 })   // All: ≤ 144 merged runs/day × 62; readable hoisted once on the prefix
  return { asOf: ctx.readTime, intervals: runs.filter(c => c.to > args.from).map(c => [Math.max(c.from, args.from), Math.min(c.to, args.to)]) }
})
```

This program is **admitted and wrong**. Under §9.1.3 and v1's "absence is indistinguishable from hidden", a subject who denies the caller and a subject id that does not exist both yield `[]` — *free* — trap 2 verbatim. L3 makes a hoisted-false prefix a sealed runtime refusal (`E_HIDDEN_PREFIX`); the client renders `unknown`, identically for missing and denied; a permitted subject with no runs is `[]`. Without L3 the author must first point-read a policy row, and `check` cannot require that. A hundred subjects are a hundred queries with their own `asOf`; working hours are `outside_hours` runs; room availability is the same query over the resource principal.

**Op 1 — calendarWindow.** First attempt scans `[calendarId, start]`: a titles reader's page spends its `take` on hidden private rows (§9.1.2), so page length counts private events — health's oracle. Corrected: `partitioned()` with `privacy` in the prefix and `db.merge` (v1) over `[cal, 'default']`, `[cal, 'private']` when `viewPrivate`, and `recipientOccurrences.byRecipientStart [viewer]`; per row, head and title are point reads keyed from traced rows. Private events reach the titles reader only as coverage runs (`shareCalendar` writes an `availabilityPolicies` row beside every grant). `searchMyEvents` is a `merge` over ≤ 20 per-calendar token scans, each partition uniform for the caller.

**Op 4 — edit or cancel.** `editOccurrence` appends an exception keyed by the original `ref` (invariant 4 is `immutable(['ref'])`), bumps `materialRevision` when timing changes, audits; OCC is the head's revision. `editSeries` first attempt fenced every claim, request, and intent inline — participants × occurrences × rules — **`E_FANOUT`**. Rewrite: bump `scheduleGeneration`, one write; every derived row carries `generation`, reads filter by the head's, `fireReminder`'s guard compares it, and stale rows are invisible and inert *without being written* — the design's own sentence. The program closes the predecessor segment at the split key, inserts the successor, migrates stateful exceptions by exact key or explicit mapping (≤ 50; `require` that each unmapped stateful occurrence is detached or cancelled — invariant 5), inserts aliases (`unique(oldRef)`, one hop per edit), marks pending proposals on moved refs stale, audits. `require(splitStart > ctx.now())` keeps started occurrences frozen until L8. Releases, re-requests, and intents are the continuation's job.

**Op 5 — RSVP.** `respond` returns the prior row when `[participationId, idempotencyKey]` exists; `require(viewedRevision === head.materialRevision)` (invariants 8, 17); appends the response with `actorId = viewer`, `effectiveId = onBehalfOf ?? viewer` (self, `respond_as`, or the bearer whose capability names this participation); updates `currentResponse` (event-coupled); upserts busy runs for one occurrence or the projected series (`bySeriesGenStart` from `now`, `take: 600`); a bearer's subject id is a `getHidden` on `participationRecipients`. A material reschedule need not write 10,000 participations back to `needs_action`: a response whose `eventRevision < materialRevision` *is* needs_action at read (§7).

**Ops 6, 7 — propose and accept.** `proposeTime` inserts a pending proposal carrying civil start and zone; timing validation waits for L1 and happens at accept. `acceptProposal`:

```ts
export const acceptProposal = mutation({ proposalId: id(), expectedRevision: int(), retainResources: bool() }, ({ db, ctx, args }) => {
  const p = db.get(timeProposals, args.proposalId), s = db.get(series, p.seriesId)
  db.require(p.state === 'pending' && p.baseRevision === s.materialRevision && s.materialRevision === args.expectedRevision, 'E_STALE_PROPOSAL')   // invariant 18
  const r = zoned.resolve(p.proposedLocal, p.tz), rev = s.materialRevision + 1, end = r.instant + p.durationMs
  db.insert(occurrenceExceptions, { id: ctx.newId(), seriesId: s.id, segmentId: segOf(p.ref), key: keyOf(p.ref), ref: p.ref, revision: rev, state: 'modified', overrides: { start: r.instant, end, dst: r.resolution }, baseGeneration: s.scheduleGeneration, createdBy: ctx.viewer, createdAt: ctx.now() })
  db.update(series, s.id, x => ({ ...x, materialRevision: rev, contentRevision: x.contentRevision + 1 }))
  if (args.retainResources) for (const c of db.scan(resourceClaims.bySeriesGen, [s.id, s.scheduleGeneration], { take: 5 })) if (c.ref === p.ref) {
    db.update(resourceClaims, c.id, x => ({ ...x, state: 'released' }))
    db.insert(resourceClaims, { id: ctx.newId(), resourceId: c.resourceId, seriesId: s.id, ref: p.ref, generation: s.scheduleGeneration, when: { from: r.instant, to: end }, state: 'active' })   // exclusion: a sealed E_CONSTRAINT aborts everything
  }
  // pending proposals on p.ref (scan byRefState, take 50): this one 'accepted', the rest 'stale', resultingRevision: rev
  // … authorityAudit and outbox { kind: 'occurrence.moved' }
})
```

The organizer inserts the claim directly: the `exclusion` constraint *is* the serializable range check over rows the organizer cannot read (K6), its sealed refusal is invariant 14, and the abort is the design's "leaves both event and proposal unchanged". The design's separate allocator partition is needed only for approval mode and for per-occurrence outcomes.

**Ops 8, 9, 10.** Grants: insert a version, CAS the head's `version`, audit; revocation is a state update and the receipt model evicts. `requestResource` inserts ≤ 730 pending requests in one commit; `allocateResource` decides one occurrence per commit because a refused insert aborts — `tryInsert` (L5; events' `insertSoft`) would decide 50. `setWorkingHours` appends a revision; its outside-hours runs need zoned windows (effect today). `setOutOfOffice` writes policy and event; the reconcile job scans `byRecipientSeq [me] range gt watermark take 200`, appends `auto_ooo` declines, advances the watermark, and CASes `generation` — invariant 23 with v1's `sequence`.

**Ops 11, 12, 14.** `expandRecurrence` is `zoned.expand(segment, { from, to, max: 100 })` per chunk writing projections with `generation` and `tzdbVersion`; `byRefActive` makes concurrent workers idempotent; it is an effect until L1. `generateIntents` joins the next 14 days of projections to reminder rules (600 per chunk); each insert enqueues its timer. `fireReminder` receives ≤ 500 due intents (L6), re-reads head and projection (the generation is the fence), and renders the recipient's *current* projection with `visibleTo` (L4) for mail and push; in-app reminders ship references the client renders under its own rules. Sweeps are jobs; offline replay is spec §6.

### 5. Integrity audit

By enforcement (design invariant numbers). **Constraints binding every write:** 4 (`immutable(['ref'])`), 6 (`unique byRefActive { where }`), 13 (`exclusion`), 14 (sealed `E_CONSTRAINT`), 9 (coverage rows have no source columns), 19's attribution (event-coupled transitions, v1: a response or generation change requires its audit row in the same commit), 22 (`unique` action id + spec §6). **Rules:** 12, 16 (a bearer's authority is one participation), 18 (only editors insert exceptions or claims; a proposal writes nothing else), 19's authority-at-commit. **`require` in a program:** 2 (whoever resolves records `dstResolution`), 5 (every stateful occurrence mapped or explicitly detached), 17 (viewed revision), 23 (watermark then CAS), 20 up to 100 recipients — beyond that the continuation is not atomic (§7). **Schedule or job:** 3 (the freeze timer, until L8), 8 and 11 (no cross-table constraint says every projection has its busy runs — *not enforced*), 21 (generation guard at fire; `visibleTo` for mail under L4). **Not enforced today:** 1 (unverifiable without L1), 7 (a cross-column check `timingKind === 'all_day' ⇒ resolvedStart === null`, v1, would close it), 10 (admitted-wrong until L3), 15 (holds by ref-to-epoch only if claim is capability-scoped — program discipline until L7), 21 for mail and push.

The design could not enforce and now can: 6, 13, 14 (partition protocols became schema facts), 19 (attribution coupled to the transition), 22. The design could and v0 cannot: 1, 2, 3 at reasonable cost, 10, 20 above 100 recipients, 21 for external channels.

### 6. Language delta

1. **L1 — zoned arithmetic as value model.** `zoned.resolve(local, tz)`, `zoned.expand(spec, { from, to, max })`, `zoned.localDate(instant, tz)`: pure over an engine-pinned `tzdbVersion` in the certificate beside `valueModelVersion`, exposed as `ctx.tzdb`, whose update is a generation re-validating pending schedules. `max` required; `maxSteps` counts buckets × candidates. The twin ships the same tables or marks zoned sites `partial`. *General* (booking, shifts; real estate's `civil` converges). Amends §4.1, §4.5, §5, §7. Without it nine operations are effects or admitted-wrong.
2. **L2 — `maintain.coverage(table, { by, over, granularityMs, readable, as })`.** Merged half-open runs per key, engine-maintained; a delete recomputes one run from ≤ `cap` source rows. *General* (occupancy, driver availability). Amends §2, §4.4, and the `E_STRUCTURAL_COUNT` rewrite list.
3. **L3 — hoisted-false prefix is a sealed refusal, not an empty page** (`E_HIDDEN_PREFIX`). *Policy, general*: any availability or existence read; the boolean cousin of §9.1.8. Amends §9.1.3.
4. **L4 — third-principal verdicts:** `db.visibleTo(principalId, table, key)` → row or `null` under *that* principal's read rule; admitted only when `principal.kind === 'system'`; certificate-marked. *General* (notifications, digests, directory-policy display names). Amends §4.2, §7.
5. **L5 — `db.tryInsert`**: a sealed constraint outcome as a value (events' `insertSoft`). *General*. Amends §4.2, §9.
6. **L6 — `schedule(…, { batch: B })`**: the mutation receives ≤ B due rows; certificate = B × per-row. *General* at population scale. Amends §7.
7. **L7 — identity kind:** external principals are *address-epoch rows* (an `interval` table the kind owns); `claim` binds one capability to one account; `merge` is refused across epochs; `bearer` composes with `hashed`. *General*. Amends v1 §6; converges with events' "the principal is a set".
8. **L8 — `immutable(fields, { after: column })`** evaluated against `commitTime` at the write. *General* (started, sealed, closed). Amends §2 and K5: constraints may see the commit clock even though rules may not.
9. **L9 — civil types** `date()`, `localTime()`, `zone()`; today day ordinals and fixed-width ISO text stand in. *General, small*. Amends §2.

### 8. Where the design is wrong

1. **Op 7 contradicts op 9.** Accepting a proposal with retained resources must "test and move claims through the authoritative allocator" atomically with the revision, while op 9 places allocation on the resource's own partition with "pending, never confirmed". Both cannot hold; in v0 they reconcile only because the `exclusion` constraint lets the organizer's transaction *be* the allocator. **Observation:** accept two competing proposals for the same room slot concurrently under the design's asynchronous allocator — both revisions commit, one request later declines, and "leaves both event and proposal unchanged" is false.
2. **Trap 4 protects history, not live series.** `immutable_delivery_snapshot` keeps sending updates and reminders for a running series to a mailbox after its address epoch closes, so the new owner learns the predecessor's confidential meetings through *updates*. Nothing fences participations bound to a closed epoch. **Observation:** invite `alex@` to a weekly series, reassign the address, edit the series — the new owner receives the update without any invitation capability.
3. **Room claims outlive both the projection and the tzdb.** Claims run to 24 months while projections roll 18; a tzdb change moves an occurrence but not the claim's instants, and op 11 never mentions claims. **Observation:** book a two-year weekly 09:00 São Paulo room; install a rule change; the room is held at the old instant and the meeting occurs at the new one, or the re-resolved claim now conflicts and no operation owns the decline.
