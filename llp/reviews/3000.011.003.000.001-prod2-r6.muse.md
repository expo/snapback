## Verdict: NOT READY

Two remaining material concerns. The §§7–10 type-compatibility machinery itself I verified as sound and faithfully implemented (details under "Checked and cleared"); the blocks are a false normative claim about CLI admission (confirmed by execution) and a self-contradictory norm governing new insert authority.

### MC1 (§3): "refuses those combinations" is false — `--web`/`--expo` are silently ignored

RFC text: production mode "is independent of --web/--expo and refuses those combinations under the existing CLI admission rules."

The existing admission does the opposite. `init` admits `web|expo` alongside `adapt+production` ([init.rs:24](/home/ccheever/projects/sb4-w15-prod2/snapback4/crates/snapback4/src/verbs/init.rs:24)), and when `production` is present routes to `production::adapt(root, apply)`, which never sees the flags ([init.rs:29-31](/home/ccheever/projects/sb4-w15-prod2/snapback4/crates/snapback4/src/verbs/init.rs:29), [production.rs:11](/home/ccheever/projects/sb4-w15-prod2/snapback4/crates/snapback4/src/verbs/init/production.rs:11)).

Concrete counterexample, observed (prebuilt binary, minimal app with `snapback/schema.q`):

- `snapback4 init --adapt --production --web` → **exit 0**, prints the production preview; `--web` silently dropped. Same for `--expo`. (`--day2` is dropped the same way; `--dry-run` without `--apply` is a no-op alias for the default preview.)

An operator who passes `--web` believing web adaptation is included gets only the schema plan with no diagnostic. Either the code must refuse `web|expo|day2` with `--production` (one-line gate plus a case in `malformed_schema_and_flags_write_nothing`, which currently covers only `--dry-run --apply`), or the sentence must be reworded — silent ignore of explicitly passed flags should not be enshrined. Normative falsehood on the production path blocks sign-off.

### MC2 (§3): "receives no new role operations, even if blocked" contradicts the implemented planner on its plain reading

RFC text: "A table with an enum column named role and principal identity in a unique key [gets literal-per-role ops] when no mutation/job inserts or upserts that table… A table with any existing compiled mutation or job insert/upsert path receives no new role operations, even if blocked: retain its existing bootstrap behavior and guards."

The code generates for blocked-with-writer tables: `roles=[None]` selects the wave-14 enum-argument shape, then emits a fresh `bootstrap{name}` service:ops-guarded insert mutation **and** appends `or viewer = 'service:ops'` branches to the table's read/insert rules ([production.rs:89-113](/home/ccheever/projects/sb4-w15-prod2/snapback4/crates/snapback4/src/verbs/init/production.rs:89)).

Concrete counterexample: roster `members { principal: principal, role: enum('member','moderator'), unique principal, … }` with an app-authored, owner-guarded `mutation inviteMember(seat_principal: principal)` insert path, where `members` is blocked (its writer is not production-admissible). The planner emits a new `bootstrapmembers(seat_principal, seat_role)` mutation plus service:ops read/insert branches — a new insert authority the application never authored — while the sentence says the table "receives no new role operations" and keeps "existing … guards". No test covers a pre-existing-writer roster (every `ROSTER` fixture in `init_production.rs` is writer-less), so nothing pins the intended reading.

I judge the code's behavior defensible: sentence 1 ("Keep existing blocked-roster bootstrap mutations"), "Add only the displayed independent service read and insert branches", and base §14's additive seat branch triangulate to "no new *literal-per-role* operations; writer tables keep the wave-14 enum-argument shape". But a norm governing new insert authority whose plain reading forbids what the code does cannot stand. Resolution: reword to state explicitly that blocked tables with existing writers keep the enum-argument bootstrap shape and gain only the displayed seat branches, and add a pre-existing-writer test. Blocking until disambiguated, because a reviewer cannot certify new insert authority against a contradictory spec.
