**1. Medium — `E_GENERATION` in the journal's terminal-refusal list retires never-executed intents and can wedge a pre-attach document.**
`snapback4/packages/snapback4/src/local.ts:1876` (the repair for round-1 item 5).
Scenario: journal-owned document, a `/m/` reply carries a non-retryable `E_GENERATION` (the sim host emits one for "not an operation of generation N", `snapback4/crates/snapback4-sim/src/host.rs:98`; the lane's own fixture sends one). The wrapper sets `partitionDenied`, forces `observeIncarnation(..., true)` (every watch reset), calls `answers.refuse`, and `journalWrites.refuseStore` retires every pending intent as "store changed; whether this write executed is unknown" with R6 retirement, so those ids are permanently `E_WRITE_RECEIPT_EXPIRED`. Neither the device outbox (`flushOnce` settles that one write) nor the shipped journal (`web-journal.ts:364` explicitly excludes `E_GENERATION` from write refusals) does this. Because `onStoreChange` is skipped for this code, nothing reopens; before attachment `attachCore` returns early on `partitionDenied` (`local.ts:1738`) and `attaching` stays set, so the engine never attaches and reads stay denied until reload. Reachability: the production server rewrites every `E_GENERATION` body to `retryable: true` (`serve.rs:700-705`), so this needs the sim host or a non-normalizing peer. The test at `test/progressive-writes.test.mjs:353` encodes the wrong behavior.
Smallest fix: drop `E_GENERATION` from the list and let the transport settle that write individually; keep the three store codes.

**2. Medium — journal receipt cuts survive an in-place store replacement and fence the new store's reads.**
`local.ts:240`, `:1077`, `:1096`, `:1143`; `observeIncarnation` at `:300-325` never clears `journalCuts`, and `LocalReads.clear(reset)` at `local-reads.ts:476` never clears `scopedCuts`/`scopedChanges`/`scopedBarriers`.
Scenario: journal-owned document, attached and acquired, journal commit at cut 50 on `items`. The backend store is replaced and the device sync path adopts it in place (`observe_store` reset at `:781-794`, no `onStoreChange`), so `seq` restarts near 0. Every read touching `items` now has `partitionCurrent` false, routes to the server, and the reply's small new-store seq fails `journalCovered`, so watches with data sit retained-revalidating indefinitely, fresh watches stay `loading`, and one-shots return `E_QUERY_RETRY` until the new store's seq passes 50 or the next journal write forces a reopen.
Smallest fix: clear `journalCuts` (and the scoped structures) when the store identity actually changes in `observeIncarnation`.

**3. Medium — going offline below an unapplied journal cut withdraws displayed intersecting answers to `loading`.**
`local.ts:1096` (forced server route) with `:1118` (offline marking limited to `!coreReady`).
Scenario: journal-owned, attached and acquired; a watch shows `items` data; a journal write commits at 21 and the link flips offline before sync applies it (a failed `/changes` poll is enough; `setLink("offline")` reschedules every watch). The rerun takes the server route because `journalCuts.current(seq)` is false, `blocked()` stops it before any fetch, `recover()` returns a plain `loading` with neither `custodyWaiting` nor `transportOffline`, and `rerun` publishes it over the data at `:1248-1251`. Pre-lane, the same watch stayed on the local route and was retained under the bounded episode. This breaks LLP 3000.023 §10 ("transport loss/offline ... never introduce `loading` after data"). The two retention tests cover the online and disjoint cases only.
Smallest fix: extend `:1118` to also set `transportOffline` when `link === "offline"` and the route was forced by an uncovered journal cut, so `watch.failed(true)` retains with `fresh: false`.

**4. Low — a journal inspection failure takes the online phase regardless of custody.**
`progressive-writes.ts:59-63` returns `true` from the catch. Fix: `return custody === "none"` in the catch; the test at `test/progressive-writes.test.mjs:276` would then expect `local` for present custody.
