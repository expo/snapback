## New fundamental and major findings

### N1. The cutover can leave both stores writable — FUNDAMENTAL — child B §5

`prepared` is what keeps the source from serving. Two different steps move it back to `copying` because a read of the target did not yet show `live`:

- the budget abort (child B §5, the paragraph after step 6) returns the source to `copying` when the budget expires “before step 5 commits”;
- recovery, which runs at every process start, does the same when a read of `_graduation` shows the target is not `live` (child B §5, recovery bullets).

Step 5 is a Postgres transaction on the other database. A transaction that has not committed is invisible to that read, and a lost reply is not an abort. The graduate process can be inside step 5 while `serve` restarts and applies the recovery rule, or the abort path can unfence on a second connection while the handoff session is still open. Either order ends in source `copying` and target `live`, both accepting writes, under the production `store_id`. The crash rule “target `live` wins” does not close this. It only runs when the read happens to see the commit.

Unfence the source only after the handoff session is closed and a later read still shows the target is not `live`. While a handoff transaction might be open, `prepared` stays fail-closed. A timeout is not knowledge that step 5 aborted.

### N2. The write pause is still proportional to store size — FUNDAMENTAL — child B §4.4 and §6

The promise is a pause of seconds, bounded by the capture tail at the fence (child B §2). The procedure does something else. A barrier takes `BEGIN IMMEDIATE`, opens a read transaction, and releases the write lock (child B §4.4). The complete digest then runs against that held snapshot, outside the pause (child B §6). Cutover, inside the pause, compares every key the journal names between that barrier and the final `jid`.

The digest is O(store). Writes continue during it. The “delta” is therefore the write rate times the digest time, and that comparison sits inside the pause budget (default 10 s). On a store large enough to graduate, this either blows the budget or the pause grows with the store. The same held read transaction also blocks a WAL checkpoint for the whole digest (`store.rs:202-205` uses WAL for new stores). Child B §4.2 dropped long-lived snapshots on the copy path for that reason. The barrier puts one back around the longest read.

Advance a verified position outside the pause: compare each journal batch against a short snapshot, and enter the fence only when the unverified tail fits the budget. Take the first consistent image with the backup API or a copied snapshot so the source checkpoint is not pinned for the whole digest.

### N3. The committer rule still cannot come out any other way — MAJOR — child C §8–§9, child A §6.3

(0)’s throughput is `N / (N·k·RTT + exec + flush)`, and on Postgres that only amortizes the flush (child A §6.3). The measured increment is about 15 calls (`experiments/postgres/README.md:277`, 18.002 → 15.002). At the rule’s 0.5 ms RTT the asymptote is `1/(15 × 0.5 ms) ≈ 133` commits/s, at any batch size, before execution and flush. The rule commissions (a) when (0) is below 1,000/s or below 25% of raw Postgres on W4 (child C §8). 133 is already below 1,000. W4 is disjoint writers. Raw Postgres scales with them. (0) does not, so the 25% clause is the same predetermined result.

S0 also runs a commit-stage prototype of (a) and is described as the thing that decides whether (a) is built (child C §9, parent §3.3). The rule never reads that result. It will commission C2’s overlay even when the prototype shows (a) cannot clear the bar either.

Commission (a) only when (0)’s measured ceiling misses the bar and (a)’s commit-stage prototype clears it by enough to pay for the overlay. If both miss, change the bar or the call shape before building C2. An absolute 1,000/s test of (0) at 0.5 ms and k≈15 is not a measurement.

### N4. (a)’s conflict check does not see the revisions added for it — MAJOR — child A §6.3

Step 3 validates a mutation against commits in `(S, head]` and against mutations already folded into the batch. `head` there is the public watermark: step 4 says public watermarks stay the head, and gives session invalidations, claims, and receipts an internal revision instead. Those writes commit with no public sequence today (`tail.rs:24-26` returns without a staged commit when there is no head advance). A revocation in an earlier batch leaves `head` unchanged, so `(S, head]` is empty. The mutation that read the session at S still passes step 3.

The snapshot claim has the same gap. A `REPEATABLE READ` snapshot is the database’s committed state, not “exactly the commits up to S”, once non-head writes exist outside `_commits`.

Make the internal revision the validation order. Every durable write, including those that do not move the public head, appends a record that serial validation intersects with the read set. The public head remains only the sync watermark.

### N5. Synchronous replication is not the incarnation guarantee — MAJOR — child A §5, parent §3.1

Same-incarnation failover is allowed when the store was “created under” synchronous replication, and that is defined as “every acknowledged transaction survives” (child A §5, “Database failover and incarnation”). That equation does not hold.

- `synchronous_commit` is a per-transaction setting. One transaction committed as `local` or `off` is acknowledged and not required to be on the standby. `synchronous_standby_names` empty makes `on` behave as local. The creation-time label does not track either change. (Postgres behavior, not re-checked in this checkout.)
- Promotion does not fence the old primary. Clients that still reach it keep committing under the same `store_id` and the same token, because the token lives inside each primary. Those commits are a second history.
- P1b requires both “database restart succeeds” and “async promotion refuses” (child A §10). The text correctly says a head regression cannot tell these apart, and it names no replacement signal. A restart and a promotion both look like the connection dropped and came back.

Record the timeline the store last served, and treat a timeline change as a promotion. Keep the incarnation only when every acknowledged transaction, head-advancing or not, was committed under a synchronous quorum and the old primary is fenced before the new one serves. Otherwise refuse and mint a new incarnation, which is the path already specified for the async case.

### N6. Completion suppression is tied to a lease that expiry has already cleared — MAJOR — child A §4.3, child B §2

The new completion write happens “under the effect’s lease”, and only then does the worker settle (child A §4.3). Lease expiry does not leave the effect claimed. `expire_run` sets it back to `queued` and clears `claimed_by` (`effects.rs:513-517`). The handler runs inside the local ledger transaction, and settle happens after that returns (`worker.ts:195-198`, `worker-ledger.ts:52-62`). A handler that outlives the lease has already performed the external call, can no longer store the server-side completion, and the effect is free for another worker. The successor has nothing to replay.

The interim graduation check has the same hole. It refuses only while an effect is “claimed but unsettled” (child B §2, child A §4.3). After expiry the effect is queued, so cutover is allowed while the only copy of the result is still the source host’s ledger file.

Key the completion by the stable delivery key and let that write win after the lease has expired. Claim and redelivery read it before invoking the handler. Until that slice is in, the fence is “a local completion whose effect is not terminal, or any effect in `running`”, not “currently claimed”.

## Small notes

- Lease renewal updates the same `_owner` row that every writing transaction holds `FOR SHARE` for its whole body (child A §5). A serial batch longer than the lease is terminated while healthy, and a stream of share locks can stall renewal. The lease clock needs its own row, and the lease has to be longer than the longest fenced transaction.
- `doctor` refuses transaction pooling for the owner connection only (child A §8). Any connection that takes `FOR SHARE` has to be in `backends` before it locks, in session mode. A pooled committer pid is not the backend takeover kills, and a paused transaction on that backend holds the share lock indefinitely.
- The in-pause comparison is key images plus head, `store_id`, generation, and family counters (child B §6). The barrier digest also covers index entries and cap occupancy. Derived state written by replay in the delta window is not gated.
- Graduation’s copy and preflight upload asset files and check those digests (child B §3–§4.2). An already deployed SQLite release tree lives on disk (`release_files.rs:39-71`) and is not in that upload. The new blob gate includes release-artifact digests, so cutover refuses until some unstated step uploads that tree.
- Parent §3.4 still lists (b)’s ordering stage as a P2 commit path. Child A §6.3 demoted (b) to a protocol that is not designed. P2’s specified path is the lease holder.
