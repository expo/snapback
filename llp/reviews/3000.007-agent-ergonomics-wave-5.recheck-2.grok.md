## Prior findings

### 1. Medium — closed-tab adoption can replace the live tab’s entire receipt window — **Repaired**

`keep_write` now treats a JSON array as an adopted older window and a single object as a new completion (`device.rs:801-821`). Adoption unions by id, keeps destination values on collisions, prepends only missing orphan ids, then trims from the front so the destination occupies the newest 256 (`device.rs:813-819`). The web host copies the orphan’s window in one call (`web.ts:370-373`).

With destination `A0…A255` and orphan `B0…B255`, the live window stays `A0…A255`. Spare capacity still fills from the newest missing orphan ids (Rust sizes 0/128/256 in `receipt_history/mod.rs:16-38`; web 256 and 128 in `acquisition.test.mjs:447-469`).

**Regression test would fail without the repair:** yes. Without destination-first union, the 256-destination web case keeps `surviving === 256` at 1 or 0, and the Rust `size=256` history would not equal `own`.

### 2. Low — `onWrite` can fire twice for a sent id still in the outbox — **Repaired**

Durable clients do not cap `emitted` (`writes.ts:62-66`). `queued()` pins those ids to the current outbox plus session values (`local.ts:887-892`, `writes.ts:56-60`). A later `flushOnce` on a `sent_seq` row does not `keep` (so it cannot refresh an evicted receipt) and skips `emitWrite` when the durable window still holds that id (`local.ts:934-941`). Pending is no longer cached beside that window (`writes.ts:27-29`, `local.ts:1074`).

**Regression test would fail without the repair:** yes. `W5R2a … a sent queued id emits once beyond 256 other emissions` (`acquisition.test.mjs:423-445`) still has `sent_seq`, evicts the receipt with 256 other `keep_write`s, then flushes. Without the emission pin, `events.filter(id === first.id).length` is 2; without the `sent_seq` keep skip, the post-catch-up `write(first.id)` is a sent receipt instead of `undefined`.
