## Material issue — draft fallback does not own status

**Affected functions:** `ClientPages.project` (status fold and `historyHead`); `ClientPages.refresh` (the same `?? this.initial` fallback into `select`).

`composeHistory` is the stated rule: complete/capped primary with data → query; else a **ready** history only while the primary receipt is `partial`; otherwise **draft-only**. Drafts stay draft-only “even if history is unavailable.” `select()` follows that for `itemsFrom` / `items`. The published **page** record does not.

When `itemsFrom === "drafts"`, `pages` is `[]`, so status is not taken from the selected source. It is taken from a synthetic list that always includes a history snapshot while the primary is partial:

```ts
const historyHead = eligible ? historyPages[0] ?? this.historyFailure ?? this.initial : undefined;
// ...
history = historyHead;
pages = from === "query" ? primaryPages : from === "history" ? historyPages : empty;
const states = pages.length ? pages : [head, ...(history ? [history] : [])];
const unavailable = states.find(page => page.status === "unavailable");
const loading = states.find(page => page.status === "loading");
const status = unavailable ? "unavailable" : loading ? "loading" : "ready";
```

`eligible` is `declared && rawHead.receipt?.state === "partial"`. In that state `historyHead` is never omitted: missing chain → `this.initial` (loading/reconnecting). A history that is actually ready is not drafts; `composeHistory` would have chosen `itemsFrom: "history"`. So every with-history draft fallback folds in a history snapshot whose status is loading or unavailable.

**Counterexample (unavailable).** `withHistory` items. Primary `status === "ready"`, `receipt.state === "partial"`. History snapshot (or `historyFailure`) `status === "unavailable"`.

- `composeHistory`: `itemsFrom: "drafts"`, `data: undefined`, items = `draftsOnly(primary.items)`, `history` carries the unavailable snapshot, status from `...primary` → **ready**.
- `ClientPages.project`: same draft items, `pages: []`, `states = [strippedHead, unavailableHistory]` → **`status === "unavailable"`**.

A UI that keys on `snapshot.status` will not present the draft-only source. That contradicts “otherwise draft-only” and “even if history is unavailable.” History becomes the active authority for the widget while drafts are the active item source.

**Counterexample (placeholder).** Same primary partial, history chain not yet populated, no `historyFailure`.

- `composeHistory` with `history === undefined`: drafts, no `history` key, primary status.
- Here `fallback` / `historyHead` is `this.initial`, so drafts are published with `history: this.initial` and **`status === "loading"`** until history exists. Draft-only is never `ready` while a history is declared and the primary is still partial.

**Correction.** Keep `composeHistory` as the source choice. Do not let a non-selected history page (and never `this.initial`) own composite `status` / `reason`.

1. History observation: `this.history?.snapshots()[0] ?? this.historyFailure` — drop `?? this.initial` in both `refresh` and `project`. Pass `undefined` into `composeHistory` until there is a real history snapshot or prepare failure.
2. Status fold: if `from === "drafts"` (empty `pages` because drafts, not because the chain is empty), use `[head]` only — the stripped primary head, which is `...rawHead` with `data: undefined`. Attach a real history snapshot on the `history` field when present; do not use it in `unavailable` / `loading` / `reason`.

`hasMore` is already false for empty `pages`; `loadMore` stays inert on drafts. When history later becomes `ready`, existing `select` / `reconcile` already switches the active chain.

## Author disposition

The status recommendation is declined under the user's delegated judgment.
The page resource has a collection acquisition status distinct from the
primary `head.status`. The plan's lifecycle table explicitly keeps truthful
primary/history reasons in draft-only mode, and says replacement acquisition
is loading while permitted content stays renderable. It applies
`composeHistory`'s eligibility law to item selection, not the single-query
record's primary-only status to a multi-query acquisition resource.

A loading or unavailable eligible history cannot supply rows; the code retains
only permitted drafts. Those drafts remain in `items` and both shipped Threads
render them irrespective of aggregate status. Calling this a blocked widget
assumes an application hides all items based on that status; the implementation
does not. The generic initial history record supplies no authority, cursor or
row. It represents pending observation/preparation honestly. Excluding it would
make the resource say ready while its selected fallback is still being acquired,
without improving draft visibility.

The plan and pagination guide now state this distinction explicitly. No source
or status truth table was changed to obtain a reviewer verdict. Existing
rendered partial-history/queued-send controls and the deterministic query/page
source-gap controls establish the intended behavior. Muse and Astra independently
found no material page-source issue; this record does not claim unanimous
reviewer agreement. Grok's locality/acquisition assessment found no material
issue, with the review's stated limits retained above.
