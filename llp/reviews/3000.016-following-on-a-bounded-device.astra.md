The horizon/fallback approach is sound, but the RFC relies on guarantees the current machinery does not provide.

1. **High — §§2.2, 3: “incomplete” does not prevent missing cards from becoming data.**

   A recent repost is held, but its original is outside the posts horizon. The point read returns `null` and records an unknown fact; it does **not** make the query unavailable. Offline, or online while a predictable write is pending, the client can return that local page—including the null card and a continuation past it. See [point reads](../../snapback4/crates/snapback4-core/src/engine/read.rs:357), [unknown facts](../../snapback4/crates/snapback4-core/src/engine/local.rs:170), and [fallback routing](../../snapback4/packages/snapback4/src/local.ts:991).

   **Smallest fix:** specify that a missing required card makes the whole local page unavailable, with no data or continuation. Retry the **original input cursor** on the server. Define pending-prediction behavior explicitly: simply setting `loading` takes a fallback branch that currently bypasses the pending-write check and can replace predicted results with server results.

   Also define what “card” means. Following currently returns event metadata; card reads are explicit application shapes. Keeping that form and making required shape dependencies unavailable is simpler than introducing implicit post-and-repost hydration.

2. **Medium — §§2.2, 2.4: a global source horizon does not guarantee the first Following pages offline.**

   Alice follows a quiet author whose newest post ranks 5,001st globally. Her first Following page already needs fallback. Likewise, today’s newest repost can reference a years-old original. Matching the horizon’s time column to event time does not establish a boundary between locally answerable and server-only Following pages.

   **Smallest fix:** promise offline answers only when every required dependency is held, and include both scenarios in acceptance. The guide should also say that `online only` removes prediction eligibility for writes to those sources; the existing [residency classifier](../../snapback4/crates/snapback4-lang/src/bind/residency.rs:68) already does this.

3. **High — §§2.2–2.3, 5: the proposed device remains unbounded, including during cold acquisition.**

   The inventory omits the generated public `FollowingPosts` table, which remains fully synced, plus owned work and edge records. The private `Feed` also has no horizon. Following an author with one million historical events therefore creates one million inbox copies that the reader acquires even with a 50-card horizon. Every device still acquires the global generated event metadata. See the [owned schemas](../../snapback4/crates/snapback4-lang/src/bind/timeline.q:1).

   This affects startup directly: [device reads wait for acquisition](../../snapback4/crates/snapback4-device/src/device.rs:285), not merely for the first screen’s cards. Existing horizons also do not evict newer arrivals to maintain exactly N rows.

   **Smallest fix:** narrow the claim to reduced **card acquisition**, inventory and measure the whole partition, and make the 10× target conditional on that measurement. Achieving the stated bounded-device goal additionally requires acquisition policies for owned event/inbox data, with explicit treatment of prediction and completeness dependencies. Per-chunk meters do not bound cumulative storage.

4. **High — §2.3: one long backfill can monopolize background work.**

   The worker selects the oldest pending task on every invocation, and advancing its cursor does not change its scheduling position. A million-event backfill therefore precedes later deliveries, purges and other readers’ backfills until it finishes. After unfollow/refollow, a large old-epoch cleanup can similarly delay the new backfill. Request fairness does not provide fairness between background tasks. See [task selection](../../snapback4/crates/snapback4-core/src/engine/timeline/work.rs:147).

   **Smallest fix:** rotate unfinished tasks after each chunk, including across timeline declarations. Keep scheduling order separate from immutable admission order, edge epochs and durable scan cursors. Exercise delivery and removal while a large backfill remains active.

5. **High — §2.3: unbounded backfill needs a fixed enumeration domain and a defined completion condition.**

   Backfill scans the mutable `byActorTime` index. Its admission check prevents copying events born after the follow, but does not prevent **visiting** them. An admitted mutation can insert backdated events continually below the cursor; the worker can keep skipping these without reaching exhaustion, leaving a finite pre-follow history permanently incomplete. See [backfill traversal](../../snapback4/crates/snapback4-core/src/engine/timeline/work.rs:83).

   Furthermore, today’s `remaining` field is a window quota, not a count of outstanding historical events. Removing the quota does not produce the promised `doctor` remaining count.

   **Smallest fix:** enumerate an indexed, finite domain bounded by the edge’s server admission epoch, independently of application timestamps. Persist that boundary and cursor together; restart must resume the same domain. Finish on exhaustion of that domain. Report processed progress and unknown remaining work unless an exact count has a separately bounded implementation.

6. **High — §§2.3, 4: existing follows never acquire their omitted history.**

   An existing reader followed an author with 5,000 events, completed the old 1,000-event backfill, and has no remaining backfill task. After upgrading—or changing full sync to a horizon—the unchanged timeline passes activation without reconstruction. Nothing schedules the missing 4,000 copies, yet the reader can report `complete: true`. Existing unfinished tasks also retain their old quota unless explicitly converted. See [unchanged-declaration activation](../../snapback4/crates/snapback4-core/src/engine/timeline/activation.rs:33).

   **Smallest fix:** define a durable, idempotent upgrade pass over existing edge epochs that fills missing history and establishes reader incompleteness before claiming the new contract. Preserve event identities and epochs; do not rebuild the timeline from application source rows.

What is sound:

- **Disclosure:** source horizons do not change authorization. Sources and follows are already public; inboxes, owned edge epochs and reader work remain private under the current rules. I found no new authorization leak from allowing horizons.
- **Removal and refollow:** the existing filter checks the copy’s **edge epoch**, and copy identity includes that epoch. This protects refollows from stale copies and cleanup. Removal evidence comes from the independently synced `RemovedEvents` table, even when an old post image is unheld. Original removal must continue to preserve independent reposts and their original card.
- **Chunk safety:** cleanup and purge already use 256-row chunks and meters. `READER_ACTOR_COPIES` is unused; `EVENT_COPIES` remains in the legacy purge-authority path, rather than bounding current background delivery. Removing the history window does not require granting unlimited deletes.
- **Sync-only adoption:** full sync ↔ horizon already triggers partition reacquisition through [successor classification](../../snapback4/crates/snapback4-core/src/successor.rs:117) and [device adoption](../../snapback4/crates/snapback4-device/src/device.rs:504). Preserve that path, including clearing old coverage boundaries; this change need not redefine the materialized view.

**Overall verdict: NOT READY.**
