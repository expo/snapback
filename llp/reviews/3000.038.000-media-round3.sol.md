Three MATERIAL issues remain:

1. **The 128 MiB device bound does not cover orphan recovery.** RFC §2 requires bounded unresolved byte custody and transfers whole upload entries between stores. Both browser recovery paths transfer through `enqueue`, while [Device::enqueue](/home/ccheever/projects/sb4-w9-media/snapback4/crates/snapback4-device/src/device.rs:1198) performs no upload-byte accounting. A destination holding 128 MiB can therefore adopt another orphan’s 128 MiB, with repeated adoption increasing it further. Specify transactional destination accounting and a capacity-deferral policy that preserves source custody. This is a recovery-design gap, not merely missing qualification.

2. **The public app boundary drops the upload capability.** RFC §4 promises React `useUpload` and access through the same client that owns ordinary mutations. `AppProvider` supplies `app.client`, constructed by [guardClient](/home/ccheever/projects/sb4-w9-media/snapback4/packages/snapback4/src/app-client.ts:287), which forwards immediate `upload` but none of the upload-intent methods. Consequently, `useUpload` throws even when `createApp` has a device. The RFC needs an explicit capability contract across the app facade, including session checks, subscription retirement, typed availability, and refusal on unsupported tiers. Exposing the private raw client would bypass that authority boundary.

3. **A terminal ordinary write can falsely satisfy an upload admission.** RFC §2 says an ordinary mutation already owning an id refuses later upload admission, and changed upload input produces `E_WRITE_ID_REUSE`. [DeviceUploads.uploadAndPlace](/home/ccheever/projects/sb4-w9-media/snapback4/packages/snapback4/src/uploads.ts:91) instead returns any terminal `write(id)` before comparing operation, dependency, metadata or bytes. Example: an ordinary mutation finishes under `x`; an upload placement submitted under `x` returns `sent` despite uploading and placing nothing. The same shortcut accepts changed input after a terminal upload. Preserve enough immutable identity to compare retained admissions, and distinguish ordinary-write ownership. This is an implementation contradiction of an already-clear design requirement.

The revised server custody design otherwise looks coherent: upload deduplication is transactional; pathname durability precedes ledger publication; pending uploads remain pinned throughout the uploaded-but-unplaced interval; collection preserves dedup receipts; cancellation tombstones fence staged uploads; and readiness precedes ordinary dispatch. Round 3’s finalization transaction checks the bound execution receipt before creating a terminal failure and releases the pin atomically. I found no additional design blocker in those mechanisms.

**Qualification remains separate.** I inspected relevant fixtures but did not execute them. Full fault-matrix, Chromium, numeric-bound, restart and native qualification remain unverified by this review. Missing execution evidence alone is not the reason for NOT READY.
