## Findings

### FUNDAMENTAL — The replay hit's only check is inside the fenced write transaction, and a hit rolls that transaction back

§3.1 deletes both pre-transaction replay checks and reads the receipt only after the authority statement in the durable transaction. A hit rolls back and returns the stored outcome. Three contracts that the current code and the parent require do not survive that placement.

**The receipt read has to happen before any gate that can re-judge a historical write, and it has to be a later command than the head lock.** The parent states both checks: bound replay runs before validation and again under the writer fence (LLP 3000.009.001.000, P1-MR receipt reader). The before-validation check is what returns `sent` for an operation that was renamed, had its arguments narrowed, or was converted to ephemeral (`engine/mod.rs:931–950`, `postgres/mod.rs:298–308`). The receipt is inserted in that same transaction only after the program, and other transactions see it at COMMIT (`postgres/mod.rs:395–402`). Deleting the early check leaves these gates in front of the only remaining lookup:

- `serve.rs:1178` runs `check_delivery` only when the preflight replay missed, then `serve.rs:1181` diverts a now-ephemeral operation, then `serve.rs:1205` returns unknown-operation before `mutate`.
- `Engine::mutate` resolves the program, and returns the ephemeral result, before the in-transaction `replay_bound` (`engine/mod.rs:950–963`, `postgres/mod.rs:305–331`).

A committed id then learns `failed` or runs the ephemeral operation. The device is supposed to learn `sent`.

The same READ COMMITTED hole §3.5 states for `_backend.generation` applies to `_ops`. A statement that locks `_head` and reads the receipt takes its snapshot before the lock wait; READ COMMITTED rechecks the locked row only. The waiter misses the receipt the holder just committed, runs the program, and dies on the primary key instead of returning the stored outcome. The B2 replay row groups that read with the head lock (`head + generation + authority + savepoints + receipt lookup`) and never says the receipt read is its own later command.

**A replay during ownership loss no longer sees the receipt.** Takeover changes the owner token and does not bump `_backend.generation` (`ownership.rs:362`, `opening.rs:120`). Today's hit uses `transaction(None)`, a read-only snapshot that does not take the fence (`postgres/mod.rs:284–289`, `store.rs:125–136` is under `mode.is_some()`). The revision's only read goes through `begin()`'s token check. A stale token raises `StoreOwnership` before `_ops` is read, so this process cannot return the committed outcome.

**A pre-executed member cannot roll back the batch.** Committer §3.6 reads receipt absence at snapshot S and re-checks it at batch admission. Committer §3.7 makes a replay an abort to the member savepoint, because a member `ROLLBACK` undoes earlier members. Only keyed members share a batch (committer §3.4), which is the class §9 tells K3 to size. §3.1's hit rule is an unqualified transaction rollback (§4's replay schedule ends in `ROLLBACK`). One replay in a batch discards the other members. §3.1's pre-executed bullet (snapshot S plus the serial authority re-check) never says where that member's receipt is read, or that a hit aborts only its savepoint.

What would resolve it: keep the before-validation read, on a snapshot that does not take the owner fence, and keep the fenced re-check as a separate command after the head lock. A hit aborts that member. Historical gates (unknown operation, delivery fingerprint, ephemeral conversion, schema validation) run only on a miss.

### MAJOR — The B2 schedules are not achievable under both §3.6 candidates while keeping rule 5 and §3.5

§4's counts are one packing: multi-command flights, with `BEGIN` joined to the fence, the dependent W1 membership read in a later flight of the same transaction, and `COMMIT` alone. §3.6 offers two mechanisms and §6 assigns those counts to whichever RT5 picks.

**(a) Ordered SimpleQuery** hits every listed schedule and keeps §3.5. Commands run in order, each READ COMMITTED command gets its own snapshot, an error skips the rest of the string, and the tail's row count comes back before `COMMIT` is sent. It does not keep §9.1 rule 5, "Typed arguments, not dialect-parsed text." `EXECUTE` literals are still parsed by the simple-query parser. Rule 1's pre-bind NUL guard (`Tx::query` / `Tx::execute`, before Bind/Execute) never runs. The tail is the sharp case: one CTE binds eighteen arrays (`tail.rs:62–78`). Those would have to be array literals.

**(b) Attach-installed functions** can use real Bind parameters, so rule 5 holds, and a function cannot contain `BEGIN`, `ROLLBACK`, or `COMMIT`. The synchronous driver cannot pipeline a typed call with those commands (`tail.rs:58`); extended-protocol pipelining is excluded. W1 needs one snapshot across a data-dependent membership read (§4; §7, snapshot consistency). With one typed call per command that is ingress, `BEGIN`, authority and message, membership, `ROLLBACK`: five flights, not the table's three. W2 can be one typed statement and does reach 2. A mutation can be reassembled to 8 only by a different packing (a `VOLATILE` PL/pgSQL open function and a tail function that raises on a count other than one).

§3.5's command boundaries hold inside (b) only for a non-inlined `VOLATILE` PL/pgSQL body whose fence, head lock, generation read and receipt read are separate statements. §3.6 also allows a SQL function. A SQL function shares the calling statement's snapshot, including across its own statements, so the generation read and the receipt read miss the adoption or the receipt committed while `FOR UPDATE` waited. That is the bug §3.5 exists to prevent. S1b's k3 result does not close this: k3 folded read-only `REPEATABLE READ` executions, not a READ COMMITTED writer whose later command must see a commit that happened during the lock wait.

What would resolve it: publish one schedule per candidate, or pick one mechanism. If (a) remains, amend rule 5 and the bind guard for that encoder, including the tail arrays. If (b) remains, restrict it to `VOLATILE` PL/pgSQL, and change the W1 count to the typed-call schedule.

### MAJOR — Metadata-bearing refusals still depend on the admission check §3.1 removes

§3.1 removes the route resolution and the first writer admission (`serve.rs:1172`) and says any outcome that carries a head, a store id, a replayed result, or an `intent_store` mismatch is produced behind the final check. The final check it specifies is the query snapshot, the durable transaction, or snapshot S.

These refusals publish `store_id`, `head` and `generation` and never enter that transaction:

- `operation_refusal` (`serve.rs:822–826`), including unknown-operation after the body.
- `argument_refusal` (`serve.rs:1511–1518`), which returns HTTP 200 with that head.
- `intent_store`'s `E_STORE_REPLACED` (`serve.rs:814–819`, returned at `serve.rs:1193` with the preflight head).

Their authority after the queue wait is the check at `serve.rs:1172`. Ingress runs before the body (§3.1). A session revoked during upload or while queued still receives the store head on these paths. The normative sentence names the obligation and does not give these paths a snapshot.

What would resolve it: read authority in the same snapshot that supplies the head for every metadata-bearing refusal, including argument, unknown-operation, delivery and `intent_store` failures.
