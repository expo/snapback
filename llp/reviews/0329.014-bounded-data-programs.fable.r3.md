**D-A — TypeScript evaluator in v1, everywhere.** Verified: Hermes has no runtime WASM; polygen is AOT wasm→C→native module (custom build, not Expo Go); LLP 0129 measured a bounded Rust-evaluator WASM PoC at 117,353 gzip against 7,615 gzip for the shipped JS evaluator and recommended pinning the browser to the IR evaluator. "One interpreter compiled twice" therefore costs a native module on mobile — the dev-loop tax that lost milestones — and 15× the bytes on web. The TS evaluator is safe because the value model is defined JS-exactly (i53 integers, explicit codepoint compare, its own stable sort, insertion-ordered maps) rather than borrowed from the engine, a frozen corpus runs on Node/JSC/Hermes in CI, and the hydration replay check compares every hydration to the shipped result in production. **14. Multi-device offline** — each device has its own encrypted store, outbox, and version cursor; intents carry client-minted ids and a base version. Both devices predict with the same bytecode, so they predict identically; the server serializes commits and both converge to the one version stream. Inserts never conflict (distinct ids); concurrent updates are last-write-wins in commit order (the 0201 ruling), except where the mutation is written monotone — `markRead` above uses `max(old.lastReadAt, upTo)`, so cross-device read state converges regardless of order. Queued writes survive restart because the outbox is durable. The language guarantees determinism and identical prediction; the runtime guarantees convergence to the server stream and honest `predicted|queued` until then.

**15. Scale replay** — every op's bound holds per execution (`send` ≤ 2 examined; `thread` ≤ 201; inbox ≤ 5,151 capped or ≤ 251 maintained). Rerun-and-diff hurts first at **inbox-shaped subscriptions**: one send touches `messages.byConvTime[C]`, which every member's inbox subscription holds, so 256 subscribers × 5,151 examined per send at 7 sends/s is 9M examined/s. Mitigations, in order: (1) subscription coalescing — at most one rerun per subscription per 250 ms, resyncs and authorization events exempt; (2) maintained `unread`/`lastMessage` rows, making the inbox 251 examined (20×); (3) site-memoized rerun — the trace records which read site owns each range, so a rerun re-executes the program with untouched ranges served from the subscription's cache and only the touched conversation's 101-entry site re-read; (4) IVM for recognized `scan`/`map` patterns, later. The write path is unaffected: per send, one `messageCounts` ±1 and ≤ 256 unread counters if the exact variant is chosen — the contention measurement the spike must produce.

### 3. The spike

One week, one Rust binary, one TS package, no product surface. Pass/fail per day:

1. **IR + value model on two pages; TS-subset lowering** (`if`, `for` over typed cardinality, Map/Set, helpers inlined, typed reads); certificate emitter. *Pass:* `thread`, `send`, `inbox` (both variants), `boardView`, `ledger` (maintained), `ancestors`, `startDm`, `mentionScan` all lower; `expenses take 500 × shares` is refused at G with the `maintain` rewrite; a helper wrapping `scan` still yields the bound; `body.split` inside a loop yields `maxSteps` from the column max and is refused when the column has none.
2. **Rust interpreter over SQLite** inside one transaction, rules inlined and hoisted, trace recorder (ranges, stop-reason, absences, N+1 halo), trace ⊆ certificate assertion. *Pass:* measured examined ≤ certificate on a 10k-message table; membership hoists to one probe; a rule over a hidden table emits a verdict and never a row or range extent.
3. **TS evaluator over a range-indexed store** + hydration replay check + value-model corpus on Node, JSC, and Hermes. *Pass:* 100 random `(op, args)` replay byte-identical; corpus green on all three engines; evaluator ≤ 30 KB gzip.
4. **Prediction:** local `send` → `predicted` with `users[viewer]` from the prediction closure; local delete → complete with halo, `partial` on the second; first `@mention` send → `partial` at the computed site only; local leave → messages vanish; server-side membership delete → reconnect → eviction before outbox replay; `thread`'s verdict reused by `send` under the normalized-predicate proof. *Fail:* any of these needs a per-op special case.
5. **Scale:** 100k-send replay at 7/s with 256-member conversations; coalescing on; inbox capped vs maintained. *Pass:* delta p95 under 500 ms, server CPU under one core, idle profile unchanged after the run; per-viewer counter p95 send latency recorded, not asserted.
6. **Postgres lowering** of the same bytecode for `boardView` and `ledger`; conformance corpus identical results and traces. *Pass:* identical; N+1 round trips counted and reported.
7. **Agents:** two agents × two spellings (TS subset vs builder) on private chat + inbox unread + `startDm`. *Pass:* TS subset reaches green faster with zero effect escapes and zero `public` on non-profile tables. Any day's failure that requires a thirteenth special case falsifies the design.

### 5. Residual risk

1. **The cost model regrows the code catalogue.** Every pure operation needs a static cost in terms of schema maxes; the first refusals agents meet may be about `split`, `repeat`, or `Map` growth rather than reads. *Observation:* count distinct diagnostic families emitted across the week-7 agent transcripts; more than 20, or any refusal an agent cannot repair from the paste alone, means the subset is too large or the diagnostics too thin.
2. **Fleet rerun cost under inbox-shaped subscriptions.** Per-op bounds hold and the system still burns a core at Clique scale because reruns multiply by subscribers. *Observation:* day-5 delta p95 and CPU with coalescing on; if maintained rows plus coalescing do not hold the budget, site-memoized rerun moves from v2 to v1 before any product surface is built.
3. **Agents route `partial` and the two-hop rule to `public`.** P18's incentive returns through a side door if the `partial` diagnostic or `E_RULE_UNBOUNDED` is one word short. *Observation:* in the first agent bakeoff, any `take` widening after a `partial`, any effect written to replace a query, or any `public(reason)` on a table other than `profiles` — each is a design failure to fix in the diagnostic before the next run, not an agent error.
