### Findings

#### F1 (High) — Journal save failure replaces a known successful outcome

- **Where:** [app-online.ts:129](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/packages/snapback4/src/app-online.ts:129), particularly the catch at line 143.
- **What is wrong:** `change()` rewrites the journal even when it merely finds an existing intent or terminal receipt. The new catch converts failure of that redundant save into `failed/E_STORE`, overriding the outcome already read. A caller can therefore receive “failed” for an executed write and compose a duplicate.
- **Evidence:** With two public `createApp` instances sharing a journal, A completed an ID. After injecting journal-save failure, B’s same-ID mutation returned `failed/E_STORE`, while B’s `write(id)` returned `sent`, sequence 1. There was exactly one server execution. A separate reopening probe produced the equivalent `failed` versus durable `pending` disagreement.
- **Proposed fix:** Recover existing receipts without requiring another save. Preserve known pending custody when a recovery-related save fails. Restrict the fresh-admission failure handling to cases where it does not replace an existing outcome.

#### F2 (High) — Prefix clearing deletes newly typed replacement text

- **Where:** [web intents.ts:35](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/apps/chat/src/intents.ts:35), [Expo intents.ts:67](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/apps/chat-expo/src/intents.ts:67).
- **What is wrong:** String-prefix equality does not establish that those characters still belong to the submitted revision. Submit `hello`, clear the field during admission, then type the new draft `hello again`: successful admission changes that new draft to ` again`. This disproves the lane report’s claim that replacement drafts survive.
- **Evidence:** Chromium probes against both actual starter components reproduced the deletion. Existing tests exercise appended text and an unrelated replacement, so they miss this case.
- **Proposed fix:** Track whether edits replaced the submitted revision; remove only characters still owned by that revision. Add the clear-and-retype sequence to both component tests. This is separate from the already-known card composer defect.

#### F3 (Medium) — Overlapping calls ignore the second caller’s wait bound

- **Where:** [writes.ts:73](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/packages/snapback4/src/writes.ts:73), interacting with [client.ts:711](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/packages/snapback4/src/client.ts:711), [local.ts:1226](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/packages/snapback4/src/local.ts:1226), and [app-online.ts:160](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/packages/snapback4/src/app-online.ts:160).
- **What is wrong:** `MutationIds.run()` returns the first caller’s entire running promise before evaluating the second caller’s options. Consequently, a same-ID call with `waitSeconds: 0` can wait for the original settlement deadline or response despite custody already being established.
- **Evidence:** Four real-backend probes—native, wasm web, raw online and `createApp` online—confirmed pending custody, then made the zero-wait call. All four remained unresolved until the first request’s held acknowledgement was released.
- **Proposed fix:** Share admission and execution ownership while applying the wait policy per invocation. A zero-wait caller must await admission, but must not inherit another caller’s settlement wait.

#### F4 (High) — The mock executes one supplied write ID twice

- **Where:** [mock.ts:144](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/packages/snapback4/src/mock.ts:144).
- **What is wrong:** The new explicit-ID handling attaches the supplied ID to every invocation without reserving or recovering it. Identical retries execute again and publish distinct terminal outcomes under one identity. This affects the labelled mock tier.
- **Evidence:** Two zero-wait increments using one ID incremented the counter twice and emitted two `sent` events with sequences 1 and 2. `write(id)` then reported sequence 2.
- **Proposed fix:** Reserve supplied IDs, compare operation and arguments, recover the original pending write or receipt, and reject conflicting input. Test one execution and one terminal emission for repeated IDs.

#### F5 (High) — The fence documentation still misdescribes incomplete reads

- **Where:** [reads.rs:65](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/crates/snapback4-lang/src/guide/reads.rs:65), [client.md:36](/Users/ccheever/projects/snapback-ccp-cr-astra/snapback4/crates/snapback4-lang/src/guide/client.md:36).
- **What is wrong:** The cards say a query the device cannot answer completely becomes `loading` under intersecting predictable writes. Ordinary non-speculative partial answers remain readable with `complete: false`; the fence prevents server fallback without necessarily withholding local data.
- **Evidence:** A probe through the actual `evaluateLocal()` returned the partial local rows, `complete: false`, and zero server calls with an intersecting pending prediction. Existing Rule 4 routing tests also establish this behavior.
- **Proposed fix:** Describe engine-withheld and speculative answers separately from valid partial answers. Correct the matching RFC wording while preserving Rules 1–5 unchanged.
