The residency boundary is coherent: row-local policies can project recipient-specific replica images; policies requiring server witnesses can keep cells entirely online. Classifying all reads of those tables as server-class is conservative but implementable. The acknowledged limits of offline revocation and delivered history are also consistent.

However, three material gaps prevent approval.

1. **Immutable protected fields remain a guessing oracle.** Consider a readable row with a hidden, immutable `secret` and an otherwise authorized update accepting a supplied guess. Setting `secret` to its existing value succeeds; setting another value refuses. The current constraint code compares stored values whenever the **row** is readable ([write.rs](/home/ccheever/projects/sb4-b19-colr/snapback4/crates/snapback4-core/src/engine/write.rs:674)). §22.2 prohibits guessing through transition rules but does not resolve immutable constraints. Explicitly reject this composition or define cell-aware handling that makes equal and unequal guesses indistinguishable in outcome and meter. Normalizing only the refusal message cannot hide success versus failure.

2. **Asset placement needs cell-level blind-write handling.** The existing placement path accepts an asset already present in the old cell without requiring uploader ownership; explicitly supplied assignments receive stricter treatment only when the **row** is unreadable ([asset_columns.rs](/home/ccheever/projects/sb4-b19-colr/snapback4/crates/snapback4-core/src/engine/asset_columns.rs:40), [write.rs](/home/ccheever/projects/sb4-b19-colr/snapback4/crates/snapback4-core/src/engine/write.rs:385)). On a readable row with a protected asset column, submitting a known, non-owned asset ID can therefore distinguish whether that ID occupies the hidden cell. Download authorization and projected mutation returns do not close this channel. Require the same ownership check for every explicit assignment to an unreadable cell, including asset-list elements, while preserving omitted cells.

3. **Row-local prediction lacks a newly-visible-but-unheld case.** Suppose Alice holds a public row whose `secret` is omitted because `owner = Bob`. An authorized offline mutation changes the public selector to `owner = Alice` without supplying `secret`. The new policy permits disclosure, but the device lacks the stored value. “Never re-materialize a hidden default” is necessary but insufficient: specify that this cell remains unknown, dependent queries cannot claim completeness, and affected predictions queue or withhold their result. The existing owner-private implementation explicitly queues ownership acquisition of omitted values ([field_authority.rs](/home/ccheever/projects/sb4-b19-colr/snapback4/crates/snapback4-core/src/engine/field_authority.rs:76)); arbitrary column policies need an equivalent rule.

The remaining commission is substantially covered: projection before expressions and pricing; protected-input planning and maintenance refusals; row-independent count/existence; read-through authority; server-live dependencies; optional generated properties; SEC3 proof limits and audit; and ordinary adoption/rollback with confidentiality warnings. These are credible design commitments, although the supported compositions above currently permit disclosure or incorrect completeness.

Add explicit acceptance cases for all three findings. Also make the evidence list expressly cover policy grant/revoke/expiry without a data-row edit, both directions of server/replica residency changes, outstanding predictions during adoption, and optionality through spreads, transient views and compatibility types. Distinguish absent protected properties from present nullable scalar results.
