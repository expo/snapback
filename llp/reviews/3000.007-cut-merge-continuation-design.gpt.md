**1. High — D’s proof assumes a tie-breaker that some admitted indexes do not contain.**

Design: §2, D:88–94. Code: `core/engine/rules.rs:90–95`, `core/schema.rs:442–443`, `core/engine/read.rs:31–38, 854–866`; strict resume bounds are in `core/rows.rs:103–110`.

Consider `unique byRoomAt: roomId, at`, with required columns. Nine lanes select different rooms, so the lazy path uses `batch = 1`. Rooms A and B each contain a different row at `at = 100`. The merged cursor suffix is only `[at]`; the physical appended row id is not included by `suffix_after`.

All heads open successfully. A’s row at 100 wins the lane tie. Its refill cuts. D returns `next = [100]`. Resuming every lane strictly after 100 skips B’s unreturned row at 100. The emission itself was in merge order; the claim that every unread row is *strictly after* its key was false. This is also an existing uncut-pagination weakness, not something D invented.

**Smallest fix:** admit D continuation only when the merged suffix uniquely identifies rows across the union—most simply, require the suffix to contain `id`. Uniqueness of `(pinned prefix, suffix)` is insufficient.

With that fix:

- Duplicate occurrences of the same id have the same suffix in this single-table model; skipping their remaining copies is safe.
- Expiry, further search terms, and a lane filter remove candidates without reordering surviving candidates.
- A short read caused by a cut must never establish exhaustion. D’s opening guard and immediate refill stop can prevent reliance on today’s `done = rows.len() < batch`.
- The ≤8-lane branch buffers `take + 1`, rather than one head. The proof and tests must cover that distinction.

The stopping rule is sufficient, but not necessary: a refill may return a known next head before cutting during lookahead. Conservatively stopping immediately is reasonable.

If every successful request emits one distinct row, a finite unchanged walk advances and eventually reaches an uncut terminal request. “It always can” is too strong: the next request must pay opening and lookahead again, and those can fail.

**2. High — shrink does not deliver the advertised concurrent-write no-skip guarantee.**

Design: §3.4, D:197–224. Code: `core/engine/read.rs:491, 862`; `core/rows.rs:103–110`.

A descending window covers source keys `(0, 100]` and has reached inner position `at = 50`. Between requests, insert membership 40 for a room containing an existing message at 90. The enlarged window still fits, so no shrink occurs.

The design opens that newly discovered lane **after 50**. Its message at 90 is excluded. Once this window ends, later windows start after source key 100. That message is never returned.

The same failure applies to a newly matching or reordered row ahead of the inner position. Shrink only restarts lanes it ejects into the following window; it does not repair new rows in retained lanes. Removing and re-adding membership behind the outer position creates another missed range.

**Smallest fix:** retain restart/invalidation on membership and ordering changes, and define the no-skip guarantee precisely for unchanged data. Remove the claim that membership restart becomes unnecessary. If the requirement truly covers arbitrary concurrent writes, the design needs a snapshot or an equivalent versioned traversal contract; shrink alone cannot provide it.

**3. High — O lacks representable progress states and a terminating transition rule.**

Design: §§3.1–3.4 and §6, D:124–174, 197–205, 212–224, 350–357. Code: `core/engine/read.rs:417–430, 828–843`; `core/rows.rs:103–110`.

Four cases need explicit transitions:

- **Fixed lanes before any generated lane.** `[viewer]` fits, but opening the first generated lane does not. The last completed fixed lane has no position. `end: null` already means “through the end of L”; using it here loses the generated remainder. Multiple fixed lanes, and word boundaries inside a fixed matching scope, have the same representation problem.
- **Discovery without word lanes.** Thousands of readable membership rows can contain no matching words before a later room contains a hit. Discovery can exhaust the meter without opening any word lane. There is then no “last lane opened” to encode, although advancing past readable source rows would be legitimate progress.
- **Resuming inside one scope’s words.** If the token ends at `(room R, word32)`, scanning the source strictly `after` R excludes R itself. Restricting “the two edge scopes” does not explain how the first scope is retrieved again. The store’s existing exclusive composite bound does not implement that operation automatically.
- **An opening attempt itself cuts.** Checking the reserve before starting a lane does not bound the lane’s cost. A lane costing 500 examinations can fit a fresh request but cut when started with 100 remaining. The design needs to say how that unfinished lane is excluded, how already opened lanes drain under a set meter flag, and how the unfinished lane is retried.

Rejecting only a token equal to its immediate input does not exclude cycles. For example, an exhausted reserve can permit:

`([], start=S, end="open") → ([], S, S) → ([], S, "open")`

Every adjacent token differs; no work progresses. The design rejects `end < start`, not equality.

**Smallest fix:** define a complete tagged progress model covering fixed-lane offsets, source progress without a produced lane, and in-scope word progress. Require strict outer progress on window transitions, and forbid zero-width shrink/reopen cycles. State behavior for a mid-opening cut separately from successful closure before a lane.

Putting `[viewer]` in the first window only is correct for a stable Following walk **provided that window fully drains it**. Repeating it in every window would create unnecessary duplicates. The missing fixed-lane boundary must nevertheless be solved.

**4. High — window tokens can disclose expired content, beyond the already disclosed cost.**

Design: §5 items 1–3, D:306–321, and word windows at D:226–240. Code: `core/engine/read.rs:417–430, 585–587`. Law: `llp/3000-snapback4.explainer.md:361–368`; expire card, `snapback4/crates/snapback4-lang/src/guide.rs:247–249`.

Keep the viewer’s readable membership identical in two stores. Give its room 33 distinct first-term words, all present only in unswept expired messages. Change the 32nd word between the stores while preserving word count, ordering position, and costs.

Both stores return no messages. Under O, the exhausted first window returns a continuation containing its 32nd word. Decoding the token reveals expired message content. The viewer may have joined only after those messages expired; “previously entitled to read” is not a valid premise.

There is an important distinction here: query examination cost already includes expired rows (`read.rs:579–587`), and §17 explicitly preserves capped queries’ existing cut contract (L007:1705–1707). That supports retaining the existing **cost dependence**; it does not authorize publishing an expired word as a cursor component.

**Smallest fix:** require every newly disclosed word boundary to have a live, authorized witness. Keep affected expiring matching walks terminal where that cannot be established safely within budget, until a suitable continuation is designed.

For the requested denied-lane pair, keep the readable source row fixed and vary only denied child rows. Prefix authorization precedes child scanning and charges a static probe allowance (`read.rs:73–82, 564–566`), so those child rows need not affect the edge. Removing the readable source row is a different pair: its existence was already readable, and its discovery/probe cost may legitimately differ.

**5. High — “the whole query withholds next” is not an existing finalization invariant.**

Design: §5 items 4 and paired worlds, D:322–343. Code: `core/engine/read.rs:796–801, 875–876, 687–695`; `core/engine/mod.rs:715–725`; `core/engine/runner.rs:111–115`.

A query first binds a uniform merge page with `next`, then executes an auxiliary non-uniform scan, then returns the bound merge page.

The merge recorded its continuation before `non_uniform` became true. Finalization computes `complete: false` and suppresses the server cut reason, but `next_cursor()` does not recheck the class. The saved merge continuation survives.

The current guard therefore cannot justify D:343’s assertion on every execution order. Interleaving discovery with opening also requires preserving classification for reads nested in source expressions, filters, and later query work.

**Smallest fix:** finalize merge continuation eligibility after the query’s relevant work, explicitly suppressing merge tokens for the non-uniform class. Preserve the existing direct filtered-page contract; do not indiscriminately disable every direct cursor.

Also correct the host qualification: current `read_cut()` deliberately reports precise device reasons even when `non_uniform` is set. “Non-uniform means `cut: null` on every host” is not §20.17’s rule.

**6. High — SDK discharge can erase a horizon or another independent loss.**

Design: §4 item 1, D:273–277. Code: `core/engine/local.rs:35–47`; `core/engine/read.rs:682–684`; `SDK/local.ts:849–856`; `SDK/react.tsx:127–140`.

On an offline device, let the initial request execute an auxiliary online-only lookup, then return a windowed merge page. It has both unknown coverage and a continuable meter cut:

`complete: false, cut: "meter", next: T`.

A later request, which does not execute that initial-only auxiliary read, finishes the walk with `complete: true`. The proposed hook discharges the first page and reports aggregate completeness, although following T never supplied the missing fact.

The same issue exists for an independent lost page or cursorless overflow. The wire tuple contains no proof that the cut is the **only** incompleteness being discharged.

Current `Pages.notify()` correctly drops and rebuilds successors when the predecessor’s cursor changes (`react.tsx:89–102`). Preserve that. But a held page can re-answer with the **same** token and acquire an independent incomplete cause; byte equality with an already opened successor does not resolve it.

**Smallest fix:** establish an engine invariant that a cut-bearing, dischargeable continuation repairs all incompleteness represented by that page. With no new `Read` field, the conservative repair is to withhold such a continuation when independent incompleteness remains. “Any other incompleteness is never discharged” needs an enforceable mechanism, not just prose.

**7. Medium — fill lacks required metadata and a complete request-budget definition.**

Design: §4 item 2, D:278–284. Code: `SDK/react.tsx:64–103, 145–157`; `SDK/contract.ts:114–127`.

The hook receives an operation and arbitrary arguments. It does not know that Quarry asked for, say, 20 rows. A literal `last 20` need not appear in the arguments, and `Query` exposes no page-size metadata. Therefore it cannot generally determine either “shorter than requested” or “one page accumulated.”

Eight also needs to bound actual continuation opens across the fill episode, not current held depth. Existing reconciliation can repeatedly drop and reopen successors as a live predecessor changes its token; those opens occur without another `loadMore()`.

**Smallest fix:** supply the effective page bound through generated metadata or an explicit hook parameter, and define an episode counter covering automatic opens and replacements. Preserve it across notifications and in-flight completions. Distinguish this limit from ordinary ongoing live-query re-evaluations.

Q2: eight is a reasonable initial policy only with those mechanics and tests; the number itself is not a correctness proof.

**8. Medium — unconditional `id` deduplication changes valid query results.**

Design: §4 item 3, D:285–287. Code: `SDK/react.tsx:64, 131`; shape lowering in `snapback4/crates/snapback4-lang/src/bind/program.rs:560–575`.

A valid projected page can return:

`{ id: .authorId, body: .body }`

for two different posts by the same author. Today both entries survive concatenation. Unconditional `id` deduplication silently removes one.

The inspected web and Expo chat consumers return raw message rows with stable ids (`snapback4/apps/chat/snapback/schema.q:73–75`), so I found no demonstrated break in those applications. The public hook nevertheless accepts arbitrary arrays, not exclusively identity-preserving row projections.

**Smallest fix:** deduplicate using proven preserved row identity, or an explicit key policy. Specify which image wins when overlapping live pages contain different versions of the same row.

Even without concurrent writes, one message can match word lanes on opposite sides of a window boundary. Thus matching-window duplicates are not merely a concurrency phenomenon; acceptance must distinguish raw occurrences from unique accumulated results.

**9. Medium — token identity and capacity are weaker than claimed.**

Design: §3.3 and acceptance 7, D:159–187, 380–382. Code: `core/cursor.rs:60–101, 107–123`; `snapback4/crates/snapback4-lang/src/bind/key_bound.rs:14–19, 48–55`.

Two concrete problems:

- Change the source index from `(principal, roomId, id)` to `(principal, otherRoomId, id)`, with the same column types, retaining its name and the merge’s target index. `src` and the target descriptor still match. Old positions now address a different source ordering. The promised source-index change detection is absent. Likewise, two different merges can share every listed token field.
- Legal indexes can carry roughly 1,600 UTF-8 bytes of text in their suffixes. Two source positions plus a merged position already exceed 4,096 bytes before descriptors and JSON overhead. “A handful of ids” is not the admitted scope.

**Smallest fix:** bind the source’s structural descriptor, direction, and relevant selection semantics; define the intended compatibility across different merges and adoption. Prove an encoded-size bound for admitted window cursors or narrow eligibility with an explicit outcome for oversized legitimate positions.

Unauthenticated tokens do not inherently bypass authorization: use the evaluated source prefix and current lane rules, never token values as authority. However, this does not prove bounded physical server work. Rule probes already call expiry walks with charging disabled (`read.rs:102–107, 146–161`) and can traverse arbitrarily many unswept rows for one logical probe. That is inherited behavior, not a demonstrated v3-created exploit. The design should qualify its work-bound claim and avoid new unmetered discovery/retry loops.

**10. Medium — reserve behavior and word reasons contradict stated guarantees.**

Design: fixed point 3 and §§3.2–3.4, D:21–23, 140–154, 207–243. Code: `core/meter.rs:152–172`; current cut selection at `core/engine/runner.rs:111–115`.

For `take = 20`, the examination reserve is 42. A request with 40 examinations remaining may need only two more to finish opening its final lane and return a short page. The proposed reserve closes a window anyway. Therefore “windows exist only when today’s answer would have been a dead end” and universal one-window invisibility do not follow.

Separately, D:237 requires `cut: "words"` on word-closed windows, whereas fixed point 3 requires `"meter"` on every intermediate page of a multi-window walk.

**Smallest fix:** state the conservative reserve’s observable consequences and resolve them against the author’s fixed point; do not promise byte-for-byte equivalence for every previously fitting request. Follow fixed point 3’s public reason unless the author explicitly changes it.

Q3/Q5: continuation beyond 32 on a later page is faithful to the current limit. A plain matching read needs its own representable scope/word position; it does not acquire that automatically from a token requiring a generated source. Keep 32 for now.

Q4: honor final `complete: true`, but document that it establishes coverage under the traversal’s consistency contract, not global ordering. A client using the final aggregate’s first 20 rows as the global newest 20 would be misled. Update the contract documentation even though no field is added.

**11. Medium — acceptance can certify the wrong behavior unless it asserts transitions and coverage together.**

Design: §§6–7, D:345–389. Relevant code: `core/engine/read.rs:840–866`; `core/meter.rs:166–172`; `SDK/react.tsx:89–103`.

Additional dead ends include opening lookahead that cannot finish despite having found a head, discovery cuts before any representable lane, fixed-lane boundary exhaustion, oversized legitimate tokens, and step exhaustion—which aborts rather than becoming an ordinary capped page.

Several proposed tests can pass without O working:

- Acceptance 4 is principally a preservation test and already passes before the feature.
- “No repeated token” passes trivially if every request returns no token.
- Paired-world equality can pass when both worlds return an empty terminal answer.
- Acceptance 3 names fixtures without specifying coverage assertions.
- Acceptance 10’s 1,000-chat half tests the lazy-matching prerequisite, not O.

Require, at minimum:

- D: cross-lane equal suffixes, overlapping ids, 8/9-lane branches, cut lookahead, rare further-term matches, and a walk advancing one emission at a time.
- O: no-hit discovery before a hit, fixed-only boundaries, 32/33-word edges, same-row word overlap, mid-opening failure, zero-width shrink, and multi-token cycles.
- Concurrent changes: insertions in both retained and deferred portions, membership removal/re-addition, and ordering changes.
- Disclosure: expired-only word boundaries; denied-child pairs with identical readable sources; non-uniform reads before and after the merge.
- SDK: changed-token reconciliation, same-token mixed incompleteness, offline coverage, loading/denied successors, and budget exhaustion during repeated boundary replacement.
- Tokens: source-index adoption, preserved source bounds/order, same-shaped different merges, and legitimate near-limit encodings.

Keep privileged dev meters distinct from viewer observations: §20.17 expressly allows dev counters to reflect hidden non-uniform work. Interleaving must preserve the existing static-probe allowance and denial-before-discovery guarantees; comparing only total cost in ample-budget cases will not establish that.

**D should be reviewed and landed separately from O**, with the globally unique suffix restriction and focused regressions. It should not inherit O’s unresolved token, window, or SDK claims, and it should not trigger deletion of the two-cursor card.

Verdict: NOT READY
