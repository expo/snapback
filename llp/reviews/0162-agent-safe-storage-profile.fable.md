## 1. Overall assessment

LLP 0162 is a genuinely useful document: it takes LLP 0161's nine derived properties and proposes a bounded profile that is, in most of its parts, honestly scoped, correctly subordinated to the corpus's standing rulings, and unusually well-grounded in the actual tree. Its foundation inventory (lines 74–79) checks out almost item for item — commit versions and the row journal exist with no principal column (`src/storage.rs:5600`–5617), server-captured read facts including missing-row and predicate dependencies exist (`src/storage.rs:778`–810), the ctx-answer ledger exists and is durably retained inside the mutation transaction via `MutationOutput.ctx_ledger` (`src/manifest.rs:6486`; `src/storage.rs:4816`), `ContentDigestV1` exists (`src/rqs.rs:878`–1090), scoped grants exist (`src/auth/invocation.rs:1579`), and LLP 0097's substrate is landed and genuinely unwired (`src/lib.rs:53` declares `pub mod branches`, and no `branches::` reference exists anywhere else in `src/`). The non-claims list (lines 101–120) and its closing rule — missing coverage is a declared absence, never a successful empty diff — is the corpus's honesty discipline applied correctly, and §4's import of LLP 0081 §5's inventory-vs-proof rule (lines 253–259) plus Acceptance 12 makes that discipline executable rather than rhetorical. The performance gate (lines 382–399) maps nearly one-to-one onto the shipped bench harness (`src/bench.rs:90`–114, 163), which is rare actionability for an RFC at this altitude. What holds it back is not sloppiness but three unresolved structural questions that the document's own vocabulary papers over: it describes its fork as an LLP 0158 derived deployment while giving it LLP 0097's promotion and LLP 0097's acceptance language, so the profile's centerpiece is presently two incompatible primitives under one name; it makes "named checkpoint" the load-bearing substitute for P4 without ever saying what a checkpoint physically *is*, which is the exact conflation LLP 0161's P4 warns overstates progress; and it claims server-captured read/write facts across a coverage set that includes the host-plan lane, where LLP 0007 pins the read set to a *client-supplied* baseline. Each is fix-quality at RFC altitude, but each currently affects what the profile can honestly claim.

## 2. Verdict — NOT READY

NOT READY, for a first review round on a Draft seeking convergence — with the qualification that none of the blocking findings require new design research, and all three are resolvable by decision plus text. C1 is the controlling one: §Design 3 (lines 208–212) defines the v1 fork as "a short-lived derived deployment of the same logical app" — LLP 0158's vocabulary, resting on an amendment to LLP 0018/0012 that is only *proposed-normative* in a Draft RFC — and then assigns it LLP 0097's promotion-by-re-execution, while Acceptance 5 (lines 434–435) is written in pure 0097 in-app-branch language ("materialized branch base", "sibling forks"). LLP 0158's own comparison table records these as different points on one isolation axis with opposite properties on the two facts promotion depends on: schema/function bundle "Shared with parent — a branch cannot diverge them" versus "Fully divergent — fork can run a different app version", and merge-back "Staged promotion by re-execution" versus "**None** (non-goal)". Until the RFC picks one, the reader cannot tell whether the promotable fork can carry the divergent schema and functions that LLP 0158's primary agent use case exists to serve, and the acceptance corpus cannot be written. C2 and C3 similarly change what the profile may advertise rather than merely how it is phrased. Everything else is MATERIAL or MINOR and would not by itself block.

## 4. Concerns

**C1 — MAJOR. The v1 fork conflates LLP 0097's in-app branch with LLP 0158's derived deployment, leaving promotion undefined for the fork's primary use case.**
The claim at issue: §Design 3 lines 208–212 ("a short-lived derived deployment of the same logical app… uses the existing LLP 0097 / LLP 0158 materialized-copy and overlay lineage") combined with the P1 row (line 126) and §5's "strict-CAS promotion by re-execution". Evidence: LLP 0158's §Relationship-to-0097 table records the two as incompatible on the two facts promotion depends on — bundle divergence ("Shared with parent — a branch cannot diverge them" vs "Fully divergent — fork can run a different app version") and merge-back ("Staged promotion by re-execution" vs "**None** (non-goal)"); LLP 0158's phasing states outright that "What F0 deliberately does *not* include: promotion/graduation of a fork", and its OQ7 leaves fork graduation open. LLP 0097 §5 defines promotion as re-executing a durable operation log against the *canonical* bundle in a staging overlay — an operation with no defined meaning if the fork loaded a different function manifest, which is LLP 0158's motivating case 0 and the whole of its residual set (1) "schema/function-divergent rehearsal". LLP 0162's own acceptance criteria are written in 0097's idiom (Acceptance 5, lines 434–435: "materialized branch base", "sibling forks"), while §Design 3's identity requirements (scrubbed identity, newly minted fork identity, no reusable canonical credential, lines 217–219) are 0158's scrub-and-mint. The RFC never states whether a fork may diverge its schema/bundle, and §5's only hook is revalidating "manifest" (line 268), whose consequence for a diverged fork is unstated. Compounding this, "derived deployment" is defined only by LLP 0158's OQ9 amendment, which is explicitly "proposed-normative here; effective when this RFC is accepted" in a document that is still Draft — so LLP 0162 builds normative vocabulary on an unaccepted amendment to LLP 0018 and LLP 0012, neither of which appears in its Related list (line 9). Resolution: decide which primitive the profile's `Promotable` fork class actually is. The cheapest honest landing is probably: the promotable fork is 0097-shaped (shared schema and bundle, in-app child stream), schema/function-divergent forks are 0158-shaped and remain `CaptureOnly`/non-promotable in v1, and §Design 3 says so in one sentence; then rewrite Acceptance 5 to state which substrate it tests, add LLP 0018/0012 to Related with the amendment dependency flagged, and reconcile explicitly with LLP 0158's promotion non-goal.

**C2 — MAJOR. "Named checkpoint" is the load-bearing substitution for P4 but its substrate is never specified, and the document contradicts itself about it.**
The claim at issue: the P4 row (line 129) offers "Named checkpoints, fork-pinned bases, bounded record-change history" as the realization of P4, with "General relational as-of and indefinite retention" as the deliberate remainder. Evidence: §6 lines 286–291 describe only what a checkpoint *records* (boundary, schema identity, commit version, coverage manifest, retention owner, expiry/pin policy, optional digest) and never what it *is*. LLP 0161's P4 explicitly warns that its three strengths "need materially different substrates (a file copy; a per-row version chain; a retained baseline or temporal representation), and conflating them overstates progress" — this document conflates them. Internally, §Performance line 373 says "checkpoint copying" is an explicit operation, implying a materialized copy; the P4 remainder's "indefinite retention" implies a journal/retention pin; §Design 3 line 209 allows a fork to be based on a named checkpoint, which under a pin reading requires retained history the profile disclaims and under a copy reading means a full database copy per checkpoint; and OQ6 (lines 534–535) asks whether *every* fork creates one, which is unanswerable without the substrate. The consequence is not cosmetic: it determines the storage cost line in the performance budget, whether checkpoints pin the resume replay floor (see C8), and whether the P4 substitution is honest at all. Resolution: state the substrate per checkpoint class in §6 — materialized copy, retained baseline, or receipt-only pin — with its cost and its replay-floor relationship, and make the P4 table row cite it.

**C3 — MAJOR. The envelope claims read/write-set facts on a lane where the read set is a client assertion, without labeling it as one.**
The claim at issue: Motivation line 75 lists "server-captured read/write facts" as an existing foundation; §1 Coverage lines 181–183 sets the initial target as "every ordinary paved application mutation, including Ibex query/mutation execution **and host-plan mutation settlement**"; §1 lines 154–157 require "normalized read-set and write-set digests" and retained detail; the P5 row (line 130) says "Public normalized captured sets on paved query/mutation and dry-run paths", and the non-claims (line 113–115) exclude only raw SQL and undeclared lanes. Evidence: LLP 0007 §Transactions pins the split — "a host-plan mutation is an unconditional write sequence whose reads and writes run in one commit transaction… so the deciding read is the *client's* optimistic read and the client supplies it as the mutation's `read_set` baseline" (`llp/0007-storage-portability.spec.md:466`–473), reiterated in the implementation-status callout at :487–490 (Option A, "pending Charlie's ratification"). LLP 0161's P5 row records the same fact. The shipped `CapturedReadDependency` (`src/storage.rs:778`–810) is the Ibex capture path. LLP 0155's authority table states that LLP 0133 owns settle-time trust and that "client-captured values are labeled claims, not authority". So on the host-plan lane, an envelope's read-set digest is a durable record of a client's declaration — which, by the RFC's own borrowed rule from LLP 0081 §5, is inventory, not proof, and an agent reading "what did this operation read" would be given a claim as if it were an observation. Resolution: add a per-fact provenance discriminator (server-captured vs client-declared) to the envelope's read-set facts and to the explanation surface, name the host-plan lane's provenance in the P5 row and non-claims, and cite LLP 0133's claim-labeling vocabulary rather than coining a parallel one.

**C4 — MATERIAL. Sequencing omits the effect-capture work that its own promotion acceptance depends on.**
§Sequencing (lines 464–478) runs: operationId → provenance record → fork with deny-all egress "coordinated with LLP 0158's F0a program" → envelope + diff → strict-CAS promotion "including provisional effect state and fenced settlement" → history/checkpoints → measure. But LLP 0158's F0a explicitly *cut* capture-ledger integration ("the capture *ledger* integration… is deliberately deferred out of F0a and built once, coordinated with LLP 0097's own mediation prerequisite"), LLP 0097 §Design 2 names exhaustive host-egress mediation "a **prerequisite this RFC defines**, not something that exists", and `capture_effect` (`src/branches.rs:685`) has no consumer. Under deny-all egress there are no captured intents, so Acceptance 10's "contingent effect state remains provisional through settlement" (lines 447–448) and Acceptance 6's "denied **or captured**" capture leg are unreachable at the end of the stated sequence. Resolution: insert the mediation/capture wiring as an explicit sequencing step with its LLP 0097 ownership named, or scope v1 promotion to effect-free forks and say so.

**C5 — MATERIAL. §8's capability vocabulary and the aggregate `AgentSafeV1` claim do not attach to the corpus's owning capability machinery.**
§8 (lines 324–342) invents a nine-axis capability vocabulary and an aggregate profile claim, and line 382 speaks of `AgentSafeV1` "advanc[ing] beyond Draft". LLP 0134 (Accepted, and implemented — see its 2026-08-02 implementation record) owns capability maturity promotion to stable with a promotion registry, soak record, and demotion machinery; the shipped substrate is `TargetCapabilityId` / `CapabilityMaturity` / `capability_maturity` (`src/manifest.rs:7023`, :7326, with per-capability assignment at :6728–6769 and non-stable acknowledgement gating at :8306, :8350). LLP 0162 cites LLP 0134 nowhere, and OQ5 (lines 531–533) offers only this RFC, LLP 0037, or a focused follow-on Spec as candidate owners of the capability-manifest extension — omitting the Accepted Spec that already owns exactly that question. Resolution: cite LLP 0134, add it to Related, and state in OQ5 whether `AgentSafeV1` and the nine axes register as `TargetCapabilityId` entries under 0134's maturity/soak machinery or are a separate reporting surface.

**C6 — MATERIAL. Program ownership is disclaimed but never named.**
§Sequencing line 462 says "This is dependency order, not implementation authorization" and §Summary lines 42–44 say "not a commission to implement" — both correct postures — but no owning authority is identified anywhere in the document. LLP 0161 §4, the parent, states it plainly: "LLP 0155/0130 own the actual roadmap." LLP 0155 is Accepted and reserves execution/admission authority to LLP 0129 with LLP 0130's standing decisions governing acceptance. **C7 — MATERIAL. Bounded record-change history is adopted without LLP 0088's gate or its declared-retention contract.**
§6 lines 279–284 propose bounded record-change history as a v1 component. LLP 0088 §1 recommends "pursue" for exactly this capability but conditions it on a design LLP 0162 does not reproduce: per-table opt-in in the schema (`history: true`) with declared bounded retention surfaced in the manifest, "No unbounded option in v1", and horizon-past-the-window as a *normal* condition returning a marker rather than an error. LLP 0088 is also still Draft and, per its own Status, gated on the LLP 0085 evidence review. Resolution: cite LLP 0088 §1/§5/§6 as the owning design, restate the opt-in and declared-retention requirements or explain the deviation, and record the 0088 gate as a dependency.

**C8 — MATERIAL. The replay-floor rule is weakened from absolute to bounded without flagging it as an amendment.**
§Design 3 lines 225–226: a fork "is disposed by default and is reaped on TTL without pinning the canonical replay floor **indefinitely**". LLP 0097 §4 states the rule absolutely — a branch is discarded "leaving no residue in the canonical app and **never** pinning the parent's replay floor (0088 §5)" — and LLP 0088 §5 makes the two-independent-retention-clocks constraint the named guard against the Valet change-log trap ("History retention must never pin the replay floor"). LLP 0162 never restates that constraint for its own retention machinery (detail retention, checkpoint roots, fork bases, operator pins — lines 202–204 and 298–301), and Acceptance 8's "without moving the canonical replay floor incorrectly" (lines 440–441) is not a testable predicate. Resolution: restate LLP 0088 §5's independent-clocks rule as a governing constraint on every retention primitive in §6, drop "indefinitely", and rewrite Acceptance 8's floor leg as an exact assertion (the floor after reap equals the floor before, or advances only under the resume rule).

**C9 — MINOR. The settlement/ctx-ledger foundations are real but conditional, and Motivation states them flatly.**
Lines 74–79 list "deterministic ctx-answer ledgers" and "specialized settlement receipts" as existing foundations. Both exist and are atomic with the data change — `record_client_mutation_result` runs inside the mutation transaction (`src/storage.rs:4816`, :5463), the retained payload is the full `MutationOutput` including `ctx_ledger` (`src/manifest.rs:6486`), and reuse-with-different-arguments already refuses stably via `SNAPBACK_CLIENT_MUTATION_ID_REUSED` (`src/storage.rs:2190`) — but the table is keyed on `client_mutation_id` (`src/storage.rs:5637`–5647), which LLP 0161's P8 row records as optional with the client defaulting it off. So the foundation's *coverage* today is opt-in. §Sequencing item 1 fixes this, so the document is internally sound; the Motivation sentence just needs the caveat LLP 0161 already carries.

**C12 — MINOR. Three slightly different claim boundaries, and one conflates document status with capability status.**

## 5. Suggestions (non-blocking)

## 1. Overall assessment

LLP 0162 v0.2 is a genuinely strong piece of design writing: it takes LLP 0161's nine ideal properties, refuses four of them at full strength with named reasons, and proposes a three-primitive profile (operation-keyed commit envelope, class-separated safe fork, bounded proof/history) whose non-claims are more precisely stated than most Accepted documents in this corpus. The v0.2 repairs are real and verifiable — the envelope is now keyed by operation identity with the commit version demoted to a stream-qualified association (§1), which is correct against the tree (`src/storage.rs:3148-3152` confirms a no-op retains `current_version`, so version-keying would collide); the promotable/capture-only fork split (§3) correctly assigns promotion to LLP 0097's in-app branch and leaves LLP 0158's derived deployment capture-only with its merge-back non-goal unamended; the landed `branches::promote` really does apply overlay post-images with a version-ordering over-approximation of effect dependence (`src/branches.rs:908-958`), so §5's supersession call is honest; the `ContentDigestV1` header really is migration-shaped (`plan_digest`, `generation`, `barrier_head`, `publication_version`, `qualified_table` — `src/rqs.rs:1076-1085`), so §4's demand that each new boundary define its own domain-separated preimage is exactly right; and the "existing foundations" inventory in §Motivation checks out (server-captured read-set validation at predicate granularity in `src/storage.rs:11746+`, dry-run in `src/host_ops.rs:1744-1909`, `MaterializedBase`/`EffectClass`/`capture_effect` in `src/branches.rs:344/582/685`, and the journal with no principal column at `src/storage.rs:5600-5608`). Where it falls short is not vision but normative precision at exactly the two seams that matter most for a document whose thesis is capability honesty: its import of LLP 0088's history authorization silently drops the per-version fail-closed rule 0088 explicitly refused to trade away, and its operation-identity contract is narrower than the shipped, Accepted `ClientMutationIdentity` it proposes to universalize — the "riding beside it" pattern LLP 0133 forbids by name. A cluster of MATERIAL items (an undefined load-bearing term, a class re-blurring in §Sequencing, a capability vocabulary that cannot express one of its own declared fork shapes, an undefined profile-off mode, no owner for the agent-facing read surface) are all cheap to fix but collectively mean the current bytes would let a conforming implementation ship weaker guarantees than the corpus already has.

## 2. Verdict — NOT READY

NOT READY, by a narrow and fixable margin. Under LLP 0005 the bar for a Draft RFC seeking review convergence is not completeness but that its normative claims neither weaken an existing accepted guarantee nor contradict the corpus they cite; this draft does both, twice, in the same direction. C1 restates LLP 0088 §6's authorization rule in a form that 0088 explicitly considered and rejected ("a cheaper current-row-only gate is rejected because it leaks formerly-visible field values"), while §6 of this RFC claims to adopt 0088 "as its owning design rather than restating a parallel one" — a restatement that drops the rule is the exact failure mode the sentence disclaims. C2 states an identity-mismatch refusal rule (arguments, artifact, audience, kind) strictly narrower than the shipped `ClientMutationIdentity` (function + auth fingerprint + authority-instance descriptor + input fingerprint over `{args, readSet, ctxLedger}`) that LLP 0133 §Exactly-once identity binds and extends — so a v1 implementation reading §1 literally would relax fail-closed behavior on the very lane §Sequencing step 1 proposes to make mandatory. Both are one-paragraph fixes, and neither touches the profile's architecture; the remaining nine MATERIAL items are ordinary Draft residue. I would expect a v0.3 with C1-C7 addressed to come back READY without another architectural round.

## 3. Strengths

- **The claim boundary is stated once, correctly, and routed to an owner.** §Summary (lines 46-50) separates document status from capability status and hands the latter to LLP 0134; §8 makes the aggregate `AgentSafeV1` claim conditional on every component passing. This is the discipline LLP 0097's own claim boundary established and it is applied more rigorously here than in 0097.
- **The fork-class split (§3, lines 249-266) is the single best repair in v0.2.** It is verifiable against both parents: LLP 0097's branch shares the parent's schema/function/auth bundle and cannot diverge them, so re-execution against the canonical bundle is well-defined; LLP 0158's derived deployment "may diverge schema and functions" and its §Non-goals keeps merge-back out. Pinning promotion to the first class is the only assignment that makes §5 coherent, and the RFC says so rather than asserting it.
- **§5's replay-sufficiency requirement is grounded in the actual defect.** "An argument digest alone is not replay-sufficient" is not rhetorical: `src/branches.rs:781-803` shows `BranchOp` is `Write(u64, OverlayWrite)` plus `CapturedEffect` — post-images and effects only, no function, args, principal, or ctx answers — and `promote` (`src/branches.rs:940-958`) partitions writes by "ordered at/after the first captured effect", a version-ordering over-approximation, not the transitive dependence LLP 0097 §5 requires. The negative conformance fixture in Acceptance 10 is the right artifact.
- **§4's proof discipline is correctly inherited and correctly extended.** LLP 0081 line 535 reads "A digest with no independent predecessor-derived expected value is inventory, not proof"; §4 both restates it and — the extension that earns its keep — observes that the shipped header binds migration-domain facts, so promotion/checkpoint/audit boundaries each owe their own domain-separated preimage and independent derivation before claiming proof. That is a real finding about the tree, not a citation.
- **The stream-qualification requirement (§1, lines 163-166) is empirically grounded.** LLP 0158 §Spike evidence 5 records parent and fork both minting version 5322 with different contents; requiring every version fact on the envelope, diff, and promotion surfaces to carry stream identity is the correct consequence, and Acceptance 2's "receipt-only operations sharing one snapshot version keep distinct envelopes" is the testable form.
- **The per-fact provenance discriminators (§1, lines 179-186) close a real honesty hole** and route to existing owners (LLP 0133's labeled-claims-never-authority rule, LLP 0146's declared-vs-captured vocabulary) rather than coining a parallel scheme. LLP 0007's Option A is genuinely ratification-pending (0007 line 490), and §Coverage's "until ratified, that lane advertises `clientSuppliedValidated` provenance explicitly" is the right interim posture.
- **§Non-goals' client-store exclusion is honest and correctly scoped** — it names LLP 0043/0053/0090 and LLP 0155's client arm as owners and leaves LLP 0161 OQ5 open rather than quietly absorbing it.
- **The Sequencing preamble (lines 588-596) respects program ownership** (LLP 0130's standing decisions, LLP 0129's admission machinery, LLP 0155's direction) and correctly characterizes LLP 0158's F0a as the sole live adjacent lane that "deliberately excludes capture-ledger integration and promotion" — verifiable at llp/0158 lines 861-877.

## 4. Concerns

**C1 — MAJOR. §6's normative import of LLP 0088 drops 0088 §6's per-version fail-closed authorization rule, which 0088 explicitly considered and rejected weakening.**

The claim at issue: §6 (lines 364-371) states "Bounded history adopts LLP 0088 §1/§5/§6 as its owning design rather than restating a parallel one," then at lines 392-395 gives the rule as "History reads authorize fail-closed. The caller must be permitted to inspect the relevant historical lane and record under the applicable history policy; possession of a commit, operation, or checkpoint identifier is not authority." Acceptance 11 (lines 573-575) tests only "authorize fail-closed."

The evidence: llp/0088-record-history-and-branching.rfc.md lines 226-235 specifies something strictly stronger — "the reader must be authorized for the record **now**, and the read policy is additionally evaluated against **each historical post-image**, dropping versions that fail — fail closed... Dropped versions are elided, not disclosed" — and closes with the explicit rejection: "a cheaper current-row-only gate is rejected because it leaks formerly-visible field values." §6 of this RFC's rule is exactly the current-row-only gate under a different name: authorization for "the relevant historical lane and record" is a present-tense record-level check with no per-post-image evaluation. This is not an omission of detail; it is the specific weakening 0088 priced and refused, presented under a sentence claiming the import is not a restatement.

What would resolve it: quote or cite 0088 §6's two-part rule verbatim in §6 (authorized-for-the-record-now **and** policy re-evaluated per retained post-image, failing versions elided not disclosed), and make Acceptance 11 test the elision — a fixture where a row's visibility changed between two retained versions must return the newer and elide the older without disclosing its existence.

**C2 — MAJOR. §1's identity-mismatch refusal rule is narrower than the shipped, Accepted `ClientMutationIdentity`, and the RFC never says whether `operationId` extends it or rides beside it — the pattern LLP 0133 forbids by name.**

The claim at issue: §1 (lines 202-205) — "Repeating an operation with the same canonical identity and audience returns the stored receipt without re-executing. Reusing the identity with different canonical arguments, artifact, principal audience, or operation kind refuses with a stable mismatch diagnostic." §Sequencing step 1 (lines 598-600) proposes to "unify their duplicate-suppression/receipt behavior with the existing settlement vocabulary."

The evidence: `src/storage.rs:621-627` defines `ClientMutationIdentity { id, function, auth_fingerprint, authority_instance_id, input_fingerprint }`, and llp/0133-local-settlement.spec.md lines 271-282 records that the shipped identity binds "the function, the auth fingerprint, the authority-instance descriptor, and an input fingerprint over `{args, readSet, ctxLedger}`," with `SNAPBACK_CLIENT_MUTATION_ID_REUSED` and the `SNAPBACK_AUTH_STALE_RESULT` family as the shipped fail-closed responses (`src/storage.rs:2190,2239`). LLP 0133 then extends that identity with lane, element-1/5 claims, bounded-skew declaration identity, and the lane-L claim set, and states the governing discipline at line 282: "This Spec extends that identity rather than riding beside it." §1's enumerated mismatch set omits `readSet`, `ctxLedger`, lane, activation, and the authority-instance descriptor. Two consequences: (a) an implementation conforming to §1 as written would refuse on fewer divergences than the shipped path already refuses on, relaxing an Accepted-and-implemented guarantee; (b) the RFC never states whether `operationId` *is* `clientMutationId` widened to server- and host-initiated callers, or a second identity beside it — and LLP 0133 §The protocol-identity carve-out (lines 379-390) explicitly pins `clientMutationId` as client-minted idempotency that "is never re-derived," which a server-minted `operationId` would collide with conceptually.

What would resolve it: state in §1 that the envelope's operation identity **extends** the shipped `ClientMutationIdentity` (naming it), that every semantics-affecting fact LLP 0133 already binds remains bound and refusal stays in the shipped reused/stale diagnostic families, and answer explicitly whether `operationId` is the widened `clientMutationId` or a distinct key — with the duplicate-suppression authority named as exactly one of them. Add an OQ or a §Sequencing note assigning the amendment to LLP 0133/0043 rather than deciding it here.

**C3 — MATERIAL. §3 assigns deny-all egress the `CaptureOnly` capability class, contradicting LLP 0097's definition of that class and LLP 0158's F0a scope cut.**

The claim at issue: §3 lines 286-288 — "The first safety slice may be **deny-all egress** rather than simulated effect success. That narrower slice is useful and honest if its capability class is `CaptureOnly`/host-mediated and every bypass test fails closed."

The evidence: llp/0097 line 101 defines the class as "`CaptureOnly` (branch + host-side capture, no real-effect promotion)" — the effect is *captured as a durable intent*, which is the whole point of the ledger at `src/branches.rs:685` (`capture_effect`). llp/0158 lines 867-875 describes F0a's scope cut in the opposite terms: "deny-all egress, fail-loud, as the v1 posture... The capture *ledger* integration (captured intents instead of bare refusal) is deliberately deferred out of F0a." A target that refuses egress and records nothing has no capture ledger; advertising it as `CaptureOnly` tells a consumer that intents exist and are inspectable when they do not. For a document whose §8 is titled "Capability honesty," this is the one place the vocabulary itself misreports. Note §Acceptance 6 (lines 556-558) gets this right — "denied or, where the class declares capture, captured" — so the defect is confined to §3's class name.

What would resolve it: name a distinct class for the deny-all slice (e.g. `DenyAll`/`RefuseOnly`, host-mediated) in §3 and add it to §8's fork-class enumeration, keeping `CaptureOnly` reserved for LLP 0097's ledger-backed meaning.

**C4 — MATERIAL. §Sequencing step 3 re-blurs the two fork classes §3 exists to separate.**

The claim at issue: §Sequencing step 3 (lines 603-605) — "Wire the current-head fork through identity scrub-and-mint, deny-all egress, publication recovery, registry/TTL, and resource bounds, coordinated with LLP 0158's F0a program."

The evidence: §3 (lines 249-259) pins the *promotable current-head* class to LLP 0097's in-app branch, which is "same process and trust boundary" and "carries branch-scoped authority no broader than its creator's current grant"; scrub-and-mint and publication recovery are LLP 0158 derived-deployment machinery (llp/0158 §Design sketch, the S0-S5 publication state machine at lines 436-490), applicable only to the capture-only class. Step 3 applies both to "the current-head fork" without saying which, and then step 6 promotes over that same fork. An implementer following the sequencing would build scrub-and-mint for a class that by construction shares the parent's trust boundary and must *not* have its credentials scrubbed. This reads as a v0.2 fix not propagated from §3 into §Sequencing.

What would resolve it: split step 3 into 3a (in-app branch: registry/TTL, branch-scoped grant, resource bounds, deny-all egress) and 3b (derived deployment: scrub-and-mint, publication recovery, TTL — coordinated with F0a), and make step 6's promotion explicitly consume 3a only.

**C5 — MATERIAL. §8's fork-class vocabulary cannot express the checkpoint-based capture-only fork that §3 declares.**

The claim at issue: §8 line 433-434 offers "fork class (`Missing`, current-head `CaptureOnly`, or current-head `Promotable`)".

The evidence: §3 lines 257-259 declares a third shape — "A fork based on a named checkpoint is always this class [derived deployment] — its base sits behind the canonical head" — and §6 lines 375-379 makes the materialized checkpoint "alone can base a (capture-only) fork" a load-bearing property of that substrate class. Both surviving §8 values are prefixed "current-head," so a target that supports checkpoint-based forks has no honest value to advertise: it must either misreport as `current-head CaptureOnly` (false about the base) or as `Missing` (false about the capability). Given that the §Summary's P1 row (line 140) explicitly enumerates "capture-only derived-deployment fork (LLP 0158, incl. checkpoint-based)," this is an internal inconsistency, not an ambiguity.

What would resolve it: make base class an orthogonal axis in §8 (`currentHead` | `namedCheckpoint`) crossed with the effect class, or add a third enumerated value.

**C6 — MATERIAL. "Covered" is undefined but carries the document's central crash invariant.**

The claim at issue: "covered" qualifies nearly every normative sentence — "covered durable state transition" (line 21), "covered durable operation" (line 174), "covered-lane journal" (line 141), "covered mutation" (Acceptance 1), "covered record" (line 358) — and most sharply at lines 196-198: "it may not leave a data change whose covered commit envelope is absent."

The evidence: §1 §Coverage (lines 213-222) gives an "initial coverage target" and §Non-goals (lines 122-124) lists exclusions, but no definition says what makes a lane covered, who declares it, or where the declaration lives. This matters because the atomicity invariant is conditional on coverage: whether a crash cut is a defect or conformant depends entirely on whether the write path was covered at the time, and §4's journal-completeness proof ("The implementation proves journal completeness for every covered write path," line 306) is likewise coverage-relative. OQ2 asks which lanes are mandatory for the aggregate claim, which is a different question from what "covered" means for a single lane. LLP 0158 §Diff surface documents concretely that auth state, sidecars, asset blob operations, telemetry, captured-effect attempts, and privileged/raw-SQL changes are outside the app journal, so the boundary is real and non-obvious.

What would resolve it: a short defined-term block early in §Design — a lane is covered iff it has a declared coverage manifest entry, journal completeness proof, and envelope mapping; coverage is declared per lane and surfaced in the capability manifest; adding or removing coverage is a dated change with a stated effect on retained proofs.

**C7 — MATERIAL. The operation-identity source is specified only for first-party clients; host-initiated and non-first-party covered mutations have none.**

The claim at issue: §1 lines 200-202 — "First-party clients mint an `operationId` before the first attempt and reuse it across transport retries" — against §1's opening requirement that *every* covered transition writes an envelope keyed by `operationId`, and §Coverage's initial target of "every ordinary paved application mutation, including Ibex mutation execution and host-plan mutation settlement, plus branch promotion."

The evidence: `src/manifest.rs:6165-6176` confirms `client_mutation_id` is `Option<String>`, and `packages/snapback-contract/index.mjs:2018` sends `clientMutationId: queued?.id ?? null` — so the immediate (non-queued) path sends nothing today, which the RFC correctly notes in §Motivation. But covered mutations also originate from cron ticks, durable jobs, actions, admin commands, and protocol clients governed by LLP 0093/0095 — none of which are "first-party clients minting before the first attempt." If the host mints per attempt, the envelope key is stable-per-attempt and P8's retry-addressability silently evaporates while Acceptance 2 still passes (it only tests identical-identity replay). Nothing in §1 forbids this.

What would resolve it: state the identity source per originator class — client-minted for client-originated, derived deterministically from a durable upstream identity (job id + attempt-invariant key, cron occurrence, migration `operationId`) for host-initiated — and add an acceptance fixture proving a host-initiated retry after a crash returns the stored receipt rather than re-executing.

**C8 — MATERIAL. The measurement gate requires a "profile-off" mode the design never defines.**

The claim at issue: §Measurement gate lines 488-491 — "the same binary and fixture must compare profile-off versus profile-on."

The evidence: §Design specifies the envelope as committing in the same physical transaction as every covered data change (lines 194-198), with no toggle; §8's capability axes have no "profile disabled" value; §9 says nothing about a two-mode build. A supported profile-off mode is a real product surface — two capability manifests, two crash-cut matrices, two conformance runs, and a migration question when a database written under profile-on is opened under profile-off — none of which appear anywhere in the document, while §Performance's guardrail also references "the named baseline artifact" per LLP 0035's dated-baseline protocol, which would not require a toggle at all.

What would resolve it: either measure against the dated pre-profile LLP 0035 baseline artifact (dropping the toggle), or state in §9 that a build/flag-level profile-off mode exists, with its capability-advertisement and reopen-compatibility consequences.

**C9 — MATERIAL. Explanation detail has an expiry disposition but no capture-time truncation disposition, and the structural budget does not bound write-side detail volume.**

The claim at issue: §2 (lines 231-242) defines exactly two forms and one honest failure — "a stable `detail-expired` disposition. It never fabricates an empty set." §Structural budget line 476-478: "Ordinary covered writes add a bounded number of metadata records plus detail proportional to the captured read/write/effect facts." §Security line 483: "Explanation payloads and effect observations are size-bounded."

The evidence: read sets are captured at row, missing-row, and predicate granularity (`src/storage.rs:11746-11800`, `CapturedReadKind::Row` / `MissingRow` / query dependencies), and a paved mutation that reads a wide predicate can produce a read set far larger than its write set — so "proportional to the captured facts" is not a bound, it is a restatement. If detail is truncated at capture time to honor "size-bounded" and the 15% write-latency guardrail, the resulting explanation is neither complete nor `detail-expired`, and §2's honesty rule has no vocabulary for it. This is the same class of defect §2 was written to prevent, one stage earlier in the pipeline.

What would resolve it: add a `detail-truncated` (or `detail-elided-at-capture`) disposition with the counts and digests still durable, state the truncation policy's owner and default bound, and add it to Acceptance 3 beside `detail-expired`.

**C10 — MATERIAL. No document owns the agent-facing read surface the profile exists to provide.**

The claim at issue: §Sequencing step 2 promises "the operation-level provenance record and public explanation surface"; §8 advertises explanation, diff, history, and proof classes; OQ5 asks who owns "the committed artifact schemas and capability-manifest extension."

The evidence: OQ5 covers the *artifact schemas* and the manifest extension, not the read API. Yet the entire value proposition — "proof over memory," an agent asking what an operation read, what a fork changed, how a record changed — is a query surface, and the corpus has established owners for exactly that: LLP 0004 (application data API surface conventions), LLP 0017 (admin/inspection surface), LLP 0024 (agent operating surface and envelope conventions), LLP 0042 (agent MCP surface). None of 0004, 0017, 0024, or 0042 appears in the §Related list (line 9). LLP 0088 §Open questions makes the same point for history reads ("API shape and naming — owned by LLP 0004's surface conventions"), so the corpus precedent is explicit.

What would resolve it: add 0004/0017/0024/0042 to Related, and either name the read-surface owner in §Sequencing step 2 or extend OQ5 to cover it.

**C11 — MATERIAL. §8's multi-valued class axes do not fit LLP 0134's `TargetCapabilityId` mechanism as described.**

The claim at issue: §8 lines 442-444 — "These axes register as `TargetCapabilityId` entries under LLP 0134's capability-maturity machinery — with its soak, promotion-registry, and demotion obligations."

The evidence: `TargetCapabilityId` is a closed, code-owned enum (`src/manifest.rs:6578`) whose per-id state is a *maturity* constant (`TargetCapabilityId::maturity`, llp/0134 lines 120, 143, 437 — `Experimental` vs `Stable` arms), consumed as set membership (`acknowledged_capability_ids`, `src/manifest.rs:1138`). §8's axes are not maturity levels and are not booleans: fork class is three-valued, isolation scope two-valued, proof class two-valued, history class three-valued. Registering "fork class" as one id loses the value; registering one id per value invites a target to acknowledge two mutually exclusive values. OQ5 asks how the registrations interact with soak windows, which acknowledges the timing question but not the shape mismatch.

What would resolve it: state in §8 that each axis value gets its own mutually exclusive `TargetCapabilityId` with a stated exclusivity rule enforced at manifest validation, or say plainly that the class values are a manifest extension *beside* the maturity registry and that only the maturity of the extension itself is 0134's business — and widen OQ5 accordingly.

**C12 — MINOR. "Superseded" misplaces ownership of the `branches::promote` defect.**

§5 lines 339-342 says the landed post-image path "is superseded, not wired," implying this RFC supersedes it. But LLP 0097 §5 already forbids the mechanism in terms at least as strong — "it is **not** a blind replay of row post-images — `_snapback_changes` is a changeset of committed post-images, not an invocation log, so it cannot on its own drive a safe promotion" — and 0097 is Accepted. The landed code is therefore a *deviation from an Accepted RFC*, not a design this Draft supersedes. The practical consequence is that the fix and its negative fixture belong to 0097's implementation lane and should be ticketed there, and this RFC absorbing it makes the correction hostage to 0162's own acceptance. Resolution: reframe as "the landed path deviates from Accepted LLP 0097 §5; this profile inherits 0097's rule and adds the negative conformance fixture," and note the ticket home.

**C13 — MINOR. Read-path explanation has no durable substrate, but §8 advertises an explanation axis that spans it.**

§1 line 216-218 correctly keeps queries out of the durable envelope ("Read-only query execution produces explanation facts, not a durable envelope write — only durable transitions write envelopes"), which is the right call for the idle/read budget. But §glance's P5 row (line 144) claims capture "on paved query/mutation and dry-run paths," and §8's "read/write explanation detail and retention class" axis does not distinguish mutation-durable from query-ephemeral. An agent asking "what did that query depend on" after the response is gone gets nothing, and the capability manifest does not say so. Resolution: state in §2 that query explanation is response-scoped and non-durable, and split the §8 axis accordingly.

**C14 — MINOR. The effect-classification taxonomy is invoked without naming its owner, and the effect owners are absent from Related.**

§1 line 190 requires "classified effect intents and settlement identities" and §7 lines 413-416 leans on "deny, capture, or declared simulation." LLP 0097 §2 is careful to attribute this vocabulary to LLP 0066 and to flag it as "a recommended vocabulary, not yet an owned/accepted taxonomy," and attributes the credential/egress seam to LLP 0036. Neither 0066 nor 0036 appears in §Related (line 9), and §1 gives no taxonomy citation — so a reader cannot tell whether "classified" means LLP 0066's five settlement capabilities, `EffectClass` as landed (`src/branches.rs:582-612`: fetch, notification, payment, cron, outbox, uses), or something new. Resolution: cite the taxonomy and its unsettled ownership status in §1, and add 0066/0036 to Related.

**C15 — MINOR. §6's "checkpoint" disambiguation misses a fourth in-corpus sense living in the same file as the digest primitive.**

§6 lines 385-388 disambiguates against LLP 0075's protocol checkpoints, LLP 0090's resumable query snapshots, and LLP 0081's rehearsal checkpoints. It omits `ContentDigestStream::checkpoint()` / `resume()` (`src/rqs.rs:1131-1142`), the accumulator checkpoint of the very `ContentDigestV1` primitive §6 invokes two sentences later for receipt-only checkpoints. Given that §6's whole substrate split turns on the word, the collision is worth one clause.

## 5. Suggestions (non-blocking)

- **Add a defined-terms block.** Beyond "covered" (C6), the document leans on *lane*, *paved path*, *durable transition*, *boundary*, and *stream identity* as if each were pinned elsewhere. ## 6. Open questions

1. Is `operationId` the shipped `clientMutationId` widened to every originator, or a second identity? If the latter, which one is the duplicate-suppression authority, and how does a mutation carrying both behave when they disagree? (C2; this is the question OQ7 gestures at but does not ask.)

3. 8. Does the profile intend the aggregate `AgentSafeV1` claim to be per-target only, or also per-app (an app whose schema declares no history opt-in cannot exercise §6)? §8's phrasing is target-indexed throughout; app-level coverage variation is not addressed.

## 1. Overall assessment

LLP 0162 v0.3 is a strong, unusually disciplined bounded-scope RFC: it takes LLP 0161's nine ideal properties and proposes three composable primitives (a universal commit envelope, safe current-head forks with effect quarantine and promotion by re-execution, and bounded proof/history) while explicitly declining the four expensive halves (maintained Merkle state, database-wide `AS OF`, general lenses, universal action replay), and its non-claims list is honest rather than decorative. Its corpus discipline is the best part: it routes the promotable fork class to LLP 0097's in-app branch and the capture-only class to LLP 0158's derived deployment rather than blurring them, imports LLP 0088 §6's two-part per-version authorization rule verbatim (matching `llp/0088-record-history-and-branching.rfc.md:218-234`), preserves LLP 0088 §4's merge rejection, inherits LLP 0081 §5's "a digest with no independent expected value is inventory, not proof" (`llp/0081-reviewed-storage-evolution-and-migrations.rfc.md:534-535`), and — impressively — self-reports that the landed `branches::promote` deviates from Accepted LLP 0097 §5 rather than claiming to supersede it, a claim I verified exactly (`src/branches.rs:908-980` applies overlay post-images via `apply_write`; the only recorded op payloads are post-images per `src/branches.rs:453-461`). ## 2. Verdict — NOT READY

Not ready, but close, and the gap is repair work rather than redesign. Two findings are blocking. C1 is an internal contradiction at the RFC's load-bearing joint: §1 fixes the envelope's physical key as `operationId` plus canonical audience bytes and rules that repeating that identity "returns the stored receipt without re-executing," while §3 has forks record their operations "with the same commit-envelope vocabulary" and §5 has promotion re-execute exactly those operations — so the profile's central keep-path is blocked by its own suppression rule, and the stream-qualification it does apply is scoped to *version* facts, not identity keys. ## 4. Concerns

**C1 — MAJOR: the envelope's identity key makes the profile's own promotion-by-re-execution unreachable.**
*Claim at issue.* §1 (blob 187-196, 243-247): the canonical identity extends `ClientMutationIdentity`, "the physical key is the composite of `operationId` and canonical audience bytes," "no two envelopes share an operation identity," and "Repeating an operation with the same canonical identity and audience returns the stored receipt without re-executing." §3 (blob 338): a conforming fork "records its durable operations with the same commit-envelope vocabulary." §5 (blob 440-442): promotion "revalidates current principal, grant, policy, manifest, operation identity, and fence; re-executes the operation log into staging."
*Evidence.* Stream qualification in this RFC is explicitly scoped to *version* facts only — §1 (blob 176-179): "Every version fact on the envelope, diff, and promotion surfaces is qualified by the stream identity it belongs to." The identity key is not stream-qualified. So a branch operation that wrote envelope `(opId=X, audience=A)` in the child stream, then re-executed canonically at promotion under the same principal/args/artifact, either (a) collides with the existing envelope, violating "no two envelopes share an operation identity," or (b) hits the suppression path and returns the *branch's* receipt instead of executing — silently turning promotion into a no-op. Neither outcome is stated. The shipped substrate makes this concrete: `ClientMutationIdentity` (`src/storage.rs:621-627`) has no stream or branch component, and `mutation_input_fingerprint` (`src/storage.rs:17153-17166`) digests only `{args, readSet, ctxLedger[, settlement]}` — nothing that would distinguish a branch execution from its canonical replay.
*What resolves it.* One added paragraph in §1 stating that the envelope/suppression key is stream-qualified (`(streamId, operationId, audience)`), or equivalently that branch envelopes live in a branch-local namespace discarded at teardown and that promotion mints canonical identities derived deterministically from `(branchId, childVersion, sourceOperationId)` — plus an Acceptance 10 clause proving that promoting a branch whose operations already carry envelopes actually re-executes rather than returning a stored branch receipt, and that a post-promotion retry of the *canonical* identity returns the canonical receipt.

**C2 — MAJOR: the suppression horizon contradicts LLP 0043's shipped eviction rule and can durably record a committed mutation as failed.**
*Claim at issue.* §1 (blob 249-259): duplicate suppression is bounded "adopting LLP 0043's settlement pattern rather than inventing one: a receipt is retained until consumed (acknowledged), until its declared per-audience retention horizon, or until an operator purge ... After reclamation, a late retry of the same identity refuses with a stable `identity-horizon-passed` diagnostic."
*Evidence.* LLP 0043's pattern has no time horizon and forbids one: `llp/0043-offline-replay-retention.rfc.md:255-259` — "Local ACK capacity is a correctness bound: at the cap, new settlement consumption refuses rather than discarding an old ACK ... Server retention pressure has the same shape: **it refuses a new identity rather than evicting an unacknowledged result**"; the header records the same rule as "no time-based eviction can break exactly-once replay" (`llp/0043-...rfc.md:43`). The RFC's horizon is therefore net-new, not adopted, and it evicts *unacknowledged* receipts. Worse, 0043 defines the client-side consequence: `llp/0043-...rfc.md:251-254` — "A typed server refusal becomes a visible terminal `failed` record and is never ACKed as the current id." An offline client replaying past the horizon under `identity-horizon-passed` would therefore durably record `failed` for a mutation that *did* commit — the exact false-negative 0043's lifecycle was built to prevent. The RFC anticipates only the double-apply hazard ("re-execution past the suppression horizon could double-apply") and not the mis-report.
*What resolves it.* Either (a) restrict horizon reclamation to receipts already in 0043's `acknowledged / removed` state (which is 0043's existing behaviour and needs no amendment), or (b) keep the horizon but classify `identity-horizon-passed` as an explicit *outcome-unknown / may-have-committed* disposition distinct from a typed refusal, name the dated LLP 0043/0012/0095 amendments that define the client's handling of it, and drop the "adopting rather than inventing" framing. Acceptance 14 should then include a fixture proving the post-horizon retry does not produce a client-side terminal `failed`.

**C3 — MATERIAL: the envelope's effect classification conflates two different vocabularies, one of which promotion depends on.**
*Claim at issue.* §1 (blob 218-222): "classified effect intents and settlement identities — classification per LLP 0066's recommended effect vocabulary (not yet an owned taxonomy) as landed in the branch substrate's closed effect classes."
*Evidence.* Those are not the same taxonomy. The branch substrate's `EffectClass` is an *egress family* enum — `{Fetch, Notification, Payment, Cron, Outbox, Uses}`, documented at `src/branches.rs:578-580` as "The closed set of host-mediated egress classes (LLP 0097 OQ3 exhaustiveness)". LLP 0066's vocabulary, as cited by LLP 0097, is the *settlement capability* — `llp/0097-...rfc.md:67`: "`transactional | provider-idempotent | provider-queryable | compensatable | inherently-ambiguous`", which "governs whether and how it settles on promotion (§5) and whether it may be *simulated*." `CapturedEffect` (`src/branches.rs:654-662`) carries `class`, `scope`, `target`, `payload`, `simulated_outcome` — and no settlement capability at all. §5's provisional-then-reconcile machinery (blob 438-442) cannot decide settlement behaviour from an egress family.
*What resolves it.* Name both facts as required envelope fields — the egress family (closed, per the landed enum) *and* the LLP 0066 settlement capability — and add the settlement capability to Acceptance 6 and 10 so the fixture set proves it is present before promotion settles anything.

**C4 — MATERIAL: the closed `AgentSafeV1` aggregate is hostage to a Draft, externally-gated LLP, and §Sequencing lands that component last.**
*Claim at issue.* §8 (blob 555-564): `AgentSafeV1` requires the Ibex lane, the host-plan settlement lane, and branch promotion, "each with envelope coverage, explanation, diff, a `DenyAll`-or-better fork effect class, **the bounded-history capability**, and boundary proof."
*Evidence.* §6 (blob 458-465) makes bounded history adopt LLP 0088 §1/§5/§6 as its owning design and concedes "LLP 0088 is Draft and gated on the LLP 0085 evidence review; that gate is a dependency of this component, not overridden here." OQ8 (blob 818-820) then asks whether 0088's eventual design supersedes §6 outright. §Sequencing puts bounded history at step 7 of 8 (blob 753-754). So the profile's headline aggregate cannot be advertised until an LLP this RFC does not own is accepted, after the last implementation step — which undercuts the incremental capability honesty §8 otherwise builds well, and makes the most agent-critical parts (envelope, explanation, fork diff) unadvertisable for reasons unrelated to them.
*What resolves it.* Either drop bounded history from the aggregate (§8 already has the mechanism: "Specialized lanes ... advertise individually"), or define `AgentSafeV1-core` (envelope + explanation + diff + fork class + boundary proof) with history as a named additive tier gated on 0088's acceptance.

**C5 — MATERIAL: §8's "fork effect class" axis conflates effect handling with promotion capability, defeating the section's own orthogonality goal.**
*Claim at issue.* §8 (blob 534-537): "fork effect class (`Missing`, `DenyAll`, `CaptureOnly`, or `Promotable`) crossed with an orthogonal base axis," with "manifest validation enforces mutual exclusion within each axis" (blob 550-551).
*Evidence.* `Promotable` is not an effect class. In LLP 0097 it is the *branch capability* ladder value: `llp/0097-...rfc.md:101` — "**Branch capability:** `Missing` ... `CaptureOnly` ... `Promotable` (data re-execution + staged effect settlement). **Isolation scope:** `HostMediated` vs `EndToEnd`." Renaming that ladder "effect class" and inserting `DenyAll` below `CaptureOnly` makes the states mutually exclusive, so a target cannot express "denies all egress *and* can promote a branch that never attempted egress" — which is exactly the state F0a produces (`llp/0158-...rfc.md:867-875`: deny-all egress is the v1 posture, capture ledger deliberately deferred) and exactly what §8's own aggregate asks for when it requires "branch promotion ... [and] a `DenyAll`-or-better fork effect class."
*What resolves it.* Split into two orthogonal axes — effect handling (`Missing | DenyAll | CaptureOnly`) and promotion (`NotPromotable | Promotable`) — keeping the base axis and the isolation-scope axis, and restate the aggregate against the split. This also removes the "or better" ambiguity.

**C6 — MATERIAL: the checkpoint proof class is asserted without a defined independent expected-value derivation.**
*Claim at issue.* §4 (blob 405-414): for promotion, "A promotion or audit may independently apply the expected operation/change facts to the base and compare the expected digest with the staged actual result," and then "A checkpoint digest without an independent derivation remains inventory." §8 advertises a "proof class (recorded inventory versus independent boundary proof)" (blob 540); Acceptance 12 (blob 706-709) requires "migration/promotion/checkpoint fixtures independently derive expected values."
*Evidence.* The RFC states a derivation for migration (LLP 0081's predecessor-derived expected value, `llp/0081-...rfc.md:533-535`) and for promotion (apply expected change facts to the base), but never for a checkpoint of arbitrary current state — where there is no plan, no predecessor, and no transformation from which to derive an independent expected value. `ContentDigestHeaderV1` makes the mismatch structural: `plan_digest`, `generation`, `barrier_head`, and `publication_version` are all required, non-optional, `deny_unknown_fields` (`src/rqs.rs:1074-1085`). Acceptance 12 therefore mandates a fixture that §4 gives no way to write, and §6's receipt-only checkpoint "with optional independently verified `ContentDigestV1`" (blob 471-474) inherits the same hole.
*What resolves it.* Either name a concrete derivation (e.g. digest of the materialized copy computed by the checkpoint path versus digest of the source at the same stream-qualified version computed by an independent scanner — two code paths, one expected value), or state plainly that checkpoint digests are inventory in v1, remove `checkpoint` from Acceptance 12, and mark the checkpoint proof class accordingly in §8.

**C7 — MATERIAL: the measurement gate contradicts itself and is scoped to the wrong unit.**
*Claim at issue.* §Performance, Measurement gate (blob 604-632).
*Evidence.* Two adjacent sentences disagree: "the **same binary** and fixture must compare profile-off versus profile-on" (blob 606-607) versus "the profile defines no supported profile-off mode, so profile-off numbers come from the **pre-profile baseline binary** re-measured under the same protocol" (blob 620-623). Separately, the gate is written per-*component* ("Before the local target may advertise **any** `AgentSafeV1` component above `Missing`") but its metric list includes "fork creation, diff, promotion, and TTL-reap latency" — none of which exist until §Sequencing steps 3-6 (blob 740-752). Steps 1-2 (automatic `operationId`, the explanation surface) therefore cannot publish any capability until promotion is built, inverting the RFC's own incremental sequencing.
*What resolves it.* Strike "the same binary" and say "the same fixture corpus and protocol, against the dated named baseline artifact"; then attach each metric to the component it gates (read/write/idle metrics gate envelope + explanation; fork/diff/promotion/reap metrics gate the fork and promotion components), leaving the full list as the gate for the aggregate only.

**C8 — MATERIAL: no rebase affordance after a refused promotion — the profile's most common everyday outcome has no paved path, despite one being free inside the stated boundary.**
*Claim at issue.* §5 (blob 444-447): "If canonical state has advanced, promotion refuses and the agent creates a new fork from the new head. This deliberately trades convenience for a small, provable protocol."
*Evidence.* Strict base equality is correct and inherited from `llp/0097-...rfc.md:85` ("v1 promotion requires the canonical head to equal `baseVersion`"), and I am not asking to relax it. But the RFC also mandates a *replay-sufficient* durable operation log (§5, blob 422-429) retaining canonical arguments, ctx answers, and effect outcomes in causal order. Re-running that log into a **fresh fork from the new head** — not into canonical — needs no merge, no advanced-head semantics, no LLP 0088 amendment, and no new machinery; it is the same re-execution the RFC already specifies, pointed at a different target. Without it, "create a new fork from the new head" means the agent discards its work and redoes it by hand, on a substrate whose whole premise is that speculation should be cheap. On any app with concurrent writers this is the modal outcome, so the profile's headline agent affordance degrades exactly where LLP 0161's concurrency pressure (`llp/0161-...research.md:94-100`) is strongest.
*What resolves it.* Name "replay the recorded operation log into a new fork based on the current head, then re-diff and re-attempt promotion" as an explicit v1 affordance in §5, note that divergent re-execution results are surfaced in the fork diff for human/agent review rather than auto-resolved (preserving the 0097 §5 rationale that clean re-execution is not meaning preservation), and add an Acceptance 10 clause for it.

**C9 — MINOR: "first-party clients default off" overstates the settlement gap.**
*Claim at issue.* §Motivation (blob 83-84): "specialized settlement receipts (today keyed by the optional `clientMutationId`, which first-party clients default off)."
*Evidence.* The core client does default it off — `packages/snapback-client/index.mjs:5733` (`clientMutationId = null`) and `:5770` (`if (clientMutationId) body.clientMutationId = clientMutationId`). But the first-party React optimistic-mutation path always supplies one: `packages/snapback-react/index.mjs:908-913` passes `clientMutationId: id` unconditionally. The claim is inherited verbatim from LLP 0161's P8 row (`llp/0161-...research.md:236`), which itself carries only Medium today-column confidence (`llp/0161-...research.md:289-292`).
*What resolves it.* Narrow to "the transport client defaults it off; the React optimistic path already mints one," which strengthens rather than weakens §1's migration story (the cutover is smaller than stated).

**C10 — MINOR: "LLP 0146's retention opt-ins" is a mis-citation.**
*Claim at issue.* §3 (blob 346-349): branch-operation replay inputs "are classified under LLP 0146's retention opt-ins and the protected-lane custody rules."
*Evidence.* LLP 0146's "retention" is offline/RQS *query* retention admission, and its verified disposition is that it has no effect today: `llp/0146-agentic-affordances.rfc.md:307-327` — "Offline/RQS retention has a verified current disposition, and it is 'no effect'," with `validate_retainable_query` refusing opaque JavaScript. It is not a data-retention classification opt-in for replay inputs. Data retention is owned by LLP 0043/0053/0090, which §Sequencing itself names correctly (blob 729-730).
*What resolves it.* Recite to LLP 0043/0053 (retention) plus LLP 0146 only for the dry-run/explanation vocabulary it actually owns.

**C11 — MINOR: §6's bounded history depends on a journal index the structural budget does not account for.**
*Claim at issue.* §Performance, Structural budget (blob 592-594): "Ordinary covered writes add a bounded number of metadata records plus detail proportional to the captured read/write/effect facts."
*Evidence.* Bounded per-record history requires a `(table_name, row_id, version)` journal index — LLP 0088 names it as required net-new work (`llp/0088-...rfc.md:106-108`) — and it does not exist today: `_snapback_changes` carries only `_snapback_changes_by_version (version, id)` and `_snapback_changes_by_table_version (table_name, version)` (`src/storage.rs:5609-5615`). A third index on the journal is per-row write amplification on the ordinary mutation path, which is precisely what the structural budget exists to bound.
*What resolves it.* Name the added index (and its per-write cost) explicitly in the structural budget and in the bytes-written metric of the measurement gate.

**C12 — MINOR: the glance table's P5 row reads as promising durable digests for queries, which §2 then denies.**
*Claim at issue.* Profile-at-a-glance P5 (blob 144): "Public normalized captured sets with per-fact provenance ... on paved query/mutation and dry-run paths; durable digest plus bounded detail." §2 (blob 298-300) then says "Query explanation is response-scoped and non-durable," and §1 Coverage (blob 269-271) says read-only query execution "produces explanation facts, not a durable envelope write."
*What resolves it.* Split the P5 cell to say "durable digest plus bounded detail on mutations; response-scoped explanation on queries and dry-run."

## 6. Open questions

1. Is the envelope/suppression identity namespace stream-qualified, branch-local, or globally flat (C1)? The answer changes §1's physical key, §3's fork requirements, and §5's promotion contract simultaneously, so it should be decided in-document rather than deferred to the schema follow-on.
2. If C2 is resolved by restricting reclamation to acknowledged receipts, does P8 still need a declared horizon at all — or does 0043's refuse-at-capacity bound suffice, making the horizon (and `identity-horizon-passed`) unnecessary v1 surface?
3. What is the promotion contract when a covered operation also wrote to an *uncovered* lane inside the same transaction? §Non-goals says "Missing coverage is a declared absence, not a successful empty diff or proof" (blob 133-134), but §1's atomicity rule and §5's "compares the resulting write/effect facts with the fork's approved facts" both read as if the covered lane is the whole write set.
4. Does the `DenyAll` slice admit a promotable branch (one that attempted no egress), or does F0a's deny-all posture make every fork non-promotable by construction (C5)? This determines whether §Sequencing step 6 can precede step 5 in practice.
5. For a materialized checkpoint, what is the independent expected-value derivation (C6) — and if there is none, does the profile advertise checkpoints under the history class only, with no proof-class claim?
6. Should the rebase affordance (C8) live in this RFC or as a dated amendment to LLP 0097, given that the operation log it replays is 0097's primitive and this profile only requires it?
7. OQ2 (blob 801-803) asks whether the aggregate keeps host-plan coverage mandatory while LLP 0007 Option A is unratified; C4 raises the symmetric question for bounded history under Draft LLP 0088. Are both better answered by one rule — "the aggregate contains only components whose owning documents are Accepted"?

## 1. Overall assessment

LLP 0162 v0.4 is a genuinely strong, unusually honest RFC: it takes LLP 0161's nine ideal properties and cuts a bounded profile that is explicit about what it does not claim, and nearly every load-bearing claim I spot-checked against the tree holds. The three hardest technical calls are correct and independently verifiable — that `branches::promote` today applies overlay post-images and is therefore a *deviation from* Accepted LLP 0097 §5 rather than a design this Draft supersedes (`src/branches.rs:908-980`, writes applied through `apply_write` over `OverlayWrite.payload`, which `src/branches.rs:441-447` shows is a post-image with no preimage); that a net base-to-head diff cannot be derived from post-image journals alone because the landed `MaterializedBase` *is* the writable fork and retains no immutable base (`src/branches.rs:341-378`, 403-410); and that the shipped `ContentDigestV1` header is migration-shaped and therefore cannot be reused at a promotion or checkpoint boundary without a fresh domain-separated preimage (`src/rqs.rs:1074-1085`). The §Performance call-out that bounded per-record history needs a new `(table, row, version)` journal index is likewise verified — `src/storage.rs:5609-5615` carries only `(version, id)` and `(table_name, version)` — and naming that write amplification instead of absorbing it is exactly the discipline LLP 0005 wants. Where the document is weaker is at three seams the v0.4 revisions opened: the stream-qualified composite identity key now contradicts both Accepted LLP 0133's normative collision behavior and the RFC's own refusal sentence in the same paragraph; the split of fork capability into orthogonal axes silently restructures Accepted LLP 0097's closed capability vocabulary without declaring the amendment the RFC declares everywhere else; and the profile claims P9 "strongly" while having no answer at all for the multi-agent promotion contention that LLP 0161 derives P9 from. The first two are corpus-consistency defects of the kind this RFC is otherwise scrupulous about; the third is a completeness gap against the profile's own pinned first consumer.

## 2. Verdict — NOT READY

NOT READY, but close, and the distance is smaller than the concern count suggests. Three findings are MAJOR by LLP 0005's own standards rather than by taste: C1 is a self-contradiction inside §1 that also reverses an Accepted Spec's normative fail-closed rule (LLP 0133 §Exactly-once identity, line 283 onward) on the single primitive the whole profile rests on, so it is not a wording problem — it changes what happens when a client reuses an identity under a different principal. C2 restructures the capability axis of Accepted LLP 0097 (`Missing | CaptureOnly | Promotable`) into four orthogonal axes and admits a combination (`DenyAll` + `Promotable`) that 0097's axis and Acceptance corpus cannot express, while the RFC scrupulously routes every other contract touch through a dated amendment — the omission is conspicuous rather than harmless. C3 is the completeness finding: the profile advertises P9 strongly, LLP 0161 derives P9 from "concurrency without coordination," LLP 0158 pins this repository's agent fleet as first consumer, and the RFC's promotion protocol gives N agents forked from one head an unbounded rebase-by-replay loop with no serialization, reservation, fairness, or retry bound. None of the three requires new research — C1 and C2 are resolvable by choosing one rule and naming one amendment, and C3 needs a paragraph plus an acceptance row or an explicit deferral with a named revisit trigger. The six MATERIALs are ordinary round-4 residue. A v0.5 addressing C1–C3 and C4–C5 should converge quickly.

## 3. Strengths

- **The tree claims are true, including the uncomfortable one.** §5's admission that the landed `branches::promote` deviates from Accepted LLP 0097 §5 — and the refusal to launder that into "this Draft supersedes it" — is verified at `src/branches.rs:908-980`: authority revalidation and base-equality CAS are real (`:919-931`), but the write path is `apply_write(&tx, w)` over post-images, with no re-execution. Ticketing the fix to 0097's implementation lane "independently of this RFC's fate" is the right ownership call.
- **§4's net-diff impossibility argument is derived, not asserted.** `MaterializedBase::materialize` backs up the source into the branch's own connection and that copy becomes the writable fork (`src/branches.rs:341-378`), and `_snapback_branch_overlay` stores `payload` for upserts and `NULL` for deletes with no preimage column (`src/branches.rs:451-464`). The requirement of "an immutable retained base or first-write preimages recorded per row" follows exactly, and the canonical folding rules (update-then-revert, insert-then-delete, delete-then-reinsert) are the right closure.
- **§1's identity extension is grounded in the shipped type, not invented beside it.** `ClientMutationIdentity` binds `{id, function, auth_fingerprint, authority_instance_id, input_fingerprint}` (`src/storage.rs:621-627`) and `mutation_input_fingerprint` digests `{args, readSet, ctxLedger}` (`src/storage.rs:17147-17172`) — precisely as §1 describes. The attributed discipline is real: LLP 0133 line 283 says in its own words "This Spec extends that identity rather than riding beside it."
- **§8's manifest-extension reasoning is mechanically correct.** `TargetCapabilityId` (`src/manifest.rs:6604`ff) is a closed enum consumed as boolean membership, so multi-valued class facts genuinely cannot be forced into it; registering the extension itself as a `TargetCapabilityId` while housing the class values beside it is the honest shape, and OQ5 correctly leaves the 0134 soak interaction open.
- **The measurement gate refuses to run on the evidence that exists.** LLP 0035 self-describes as single-run order-of-magnitude (`llp/0035-local-target-benchmarks.research.md:47-51`), and §Measurement gate requires a dated statistically controlled baseline artifact — fixed hardware class, declared warm-up, run count, median plus spread, per-metric equivalence bounds — before the gate can run at all. Scoping each metric to the component it measures (new in v0.4) is what makes early sequencing steps advertisable without waiting for promotion.
- **The duplicate-suppression lifecycle preserves LLP 0043 rather than weakening it.** 0043's rule is explicit — "At any cap the server refuses a new identity rather than evicting an unacknowledged result" (`llp/0043-offline-replay-retention.rfc.md:332-338`, restated at `:255-259`) — and §1 imports it verbatim including the operator-purge-forfeits-exactly-once carve-out. The authoritative version-zero case (`llp/0043:216`) is correctly recognized in the receipt-only envelope rule.
- **Provenance discriminators are target-honest.** `serverCaptured` / `clientSuppliedValidated` / `serverEvaluatedConditional` map exactly onto the three real cases: Ibex `CapturedReadDependency` capture (`src/runtime.rs:2718-2812`, including missing-row and predicate facts), LLP 0007's Option A client-supplied baseline still "pending Charlie's ratification" (`llp/0007-storage-portability.spec.md:487-490`), and 0007's generated standard-pattern update/delete carve-out (`llp/0007:472-475`).
- **P3's gap is stated at its true width.** `_snapback_changes` is `(version, table_name, row_id, op, row_json, changed_at_ms)` with no principal (`src/storage.rs:5600-5608`), which is why the envelope-joined-through-commit-version shape (rather than per-row principal duplication) is the right answer and matches LLP 0161 P3 and its OQ2.
- **Erasure is treated as an obligation, not a policy note.** §6's checkpoint custody registry — mark invalid, destroy reachable copies or shred keys, record destroyed-versus-unreachable on the receipt, "an unreachable copy is an honest open erasure obligation, not a silent success" — is the strongest passage in the document and has a matching acceptance row (11).

## 4. Concerns

**C1 — MAJOR. The stream-qualified composite identity key contradicts itself and reverses Accepted LLP 0133's fail-closed collision rule.**
§1 states the physical key is `(streamId, operationId, audience)` — "envelopes and suppression records live in the namespace of the stream that executed them" — and, thirty lines later, that "Reusing the identity with any divergence in the bound identity facts — arguments, read baseline, ctx ledger, artifact, **principal audience**, or operation kind — refuses with the shipped stable mismatch diagnostics." These cannot both hold: if audience is a key component, a reuse under a divergent audience does not collide, so there is nothing to compare and nothing to refuse — the operation executes as novel. That is not a hypothetical. Today the key is `client_mutation_id TEXT PRIMARY KEY` alone (`src/storage.rs:5637-5647`), and audience divergence is exactly what fails closed: `retained_auth != identity.auth_fingerprint` → `SNAPBACK_AUTH_STALE_RESULT`, and `retained_authority != identity.authority_instance_id` → `SNAPBACK_AUTH_STALE_RESULT` with `"automaticRetry": false` (`src/storage.rs:2200-2236`). LLP 0133 makes that normative: "a duplicate `clientMutationId` whose semantics-affecting facts changed — lane, hash, activation, claims, or declaration — **fails closed in the shipped reused/stale family**. It never receives the stored result under semantically different input, and it never silently re-executes" (`llp/0133-local-settlement.spec.md:294-300`), with gate ordering pinned at `:305-317`. The cited precedent does not transfer: in LLP 0081 the `operationId` is server-minted fresh per execution and the audience is a deployment target (`llp/0081-reviewed-storage-evolution-and-migrations.rfc.md:229-233`), so no untrusted originator ever re-presents one identity under two audiences. **Resolution:** pick one. Either audience stays a *bound compared fact* outside the key (preserving 0133 and the shipped diagnostics, with `streamId` alone as the added key component), or audience joins the key and the RFC states plainly that it is amending LLP 0133's collision rule, says what a cross-audience reuse now does, and carries the dated 0133/0043 amendment plus an acceptance row for the changed behavior. Acceptance 2 currently tests only the same-audience path, so neither reading is covered today.

**C2 — MAJOR. §8 restructures Accepted LLP 0097's capability vocabulary without declaring an amendment, and admits a combination 0097's corpus cannot prove.**
LLP 0097 §Capability classes defines a single ordered branch axis — `Missing` | `CaptureOnly` | `Promotable`, where `Promotable` means "data re-execution + staged effect settlement" — plus an orthogonal isolation scope, and rules that "a target **must not report a weaker class or scope as a stronger one**" (`llp/0097-ephemeral-data-branches-and-effect-isolation.rfc.md:101`). §8 replaces that with four orthogonal axes and introduces a new value `DenyAll` in an egress axis, then §5 licenses `DenyAll` + `Promotable` for a branch whose log contains no egress attempts. That combination is not expressible in 0097's axis, and 0097's Acceptance corpus gates `Promotable` on the staged effect-settlement fixtures (`llp/0097:119-121`), which presume a capture ledger. The RFC is meticulous about this mechanism everywhere else — dated amendments named for 0133/0043 (§1), 0012/0095 (§1), 0051/0129/0133, 0043/0053/0090, 0094/0095, 0012 (§Sequencing), and OQ10 explicitly asks whether rebase-by-replay should graduate into a dated 0097 amendment — which makes the silence here read as an oversight rather than a decision. It also matters for the claim boundary: 0097's own boundary bars any branch capability above `Missing` until *its* corpus passes, so a target advertising `DenyAll`/`Promotable` under `AgentSafeV1-core` is advertising against a document whose gate it has not addressed. **Resolution:** add a dated proposed-normative amendment to LLP 0097 §Capability classes recording the axis split and the `DenyAll` value, state how the new matrix maps onto 0097's three-value axis for targets that already report it, and say which of 0097's Acceptance rows a `DenyAll`+`Promotable` target must pass in place of the effect-settlement fixtures.

**C3 — MAJOR. No answer for concurrent promotion contention, while P9 is claimed strongly and the fleet is the pinned first consumer.**
LLP 0161 derives P9 from "concurrency without coordination" — "Fleets of agents share one substrate (this repo's own fleet memory documents the collision patterns). The engine, not etiquette, must make concurrent speculation safe" (`llp/0161-agent-optimized-storage-engine.research.md:88-100`) — and the §Profile-at-a-glance table claims the profile "intentionally implements P1, P3, P5, P8, and P9 strongly." But §5's contract is strict CAS on base equality with rebase-by-replay as the only recovery, and §3 caps forks per principal by count/bytes/TTL only. With k agents forked from one head, exactly one promotes; the other k−1 rebase into fresh forks based on the new head and race again, with no serialization primitive, no promotion reservation or queue, no fairness rule, no bound on rebase attempts, and no diagnostic distinguishing "your rebase lost again" from "your re-execution diverged." §9's resource bounds are per-principal, so they do not bound aggregate contention at all. The RFC's own §5 concedes clean re-execution is not meaning preservation, so each rebase also requires human or agent review of the re-diff — which makes an unbounded loop expensive rather than merely slow. LLP 0158 pins "this repository's agent fleet, fork-per-worktree on demo apps" as the first consumer (`llp/0158-instance-forking.rfc.md:12-14`), so this is the expected steady state, not a tail case. **Resolution:** either add a promotion-admission paragraph to §5 (a promotion reservation or serialized promotion lane against the canonical head, a bounded rebase-attempt budget with a stable exhaustion diagnostic, and an acceptance row exercising k concurrent forks) or state explicitly that v1 leaves contention to the caller, name the resulting failure mode, and add it to §Revisit triggers — but do not claim P9 "strongly" while the concurrency half is unaddressed.

**C4 — MATERIAL. `AgentSafeV1-core` claims Accepted-only provenance, but its explanation-detail authorization is imported from Draft LLP 0088.**
§8 states that for `AgentSafeV1-core` "every owning design behind the core is Accepted (LLP 0097) or this RFC itself," and puts bounded record history in a separate `AgentSafeV1-history` tier gated on 0088's acceptance. But §6 imports LLP 0088 §6's two-part per-version rule "verbatim" and then extends it: "The same per-version rule extends to retained explanation detail and fork-diff rows, which are historical row values by another name." Retained explanation detail (§2) and fork diff (§4) are *core* components, not history-tier components — so core's authorization semantics are governed by a rule the RFC sources from a Draft document that is itself gated on the LLP 0085 evidence review (`llp/0088-record-history-and-branching.rfc.md:277-283`). OQ8 confirms the import is unsettled by asking whether 0088's landed design supersedes §6's import or the profile keeps an independent restatement. Acceptance 3 already tests non-row fact authorization under changing principals, so the machinery is specified — only the ownership claim is wrong. **Resolution:** either state that this RFC *owns* the per-version authorization rule for explanation detail and fork-diff rows (restating it rather than importing it, and resolving OQ8 in that direction for the core tier), or move the layering claim's wording to acknowledge that core inherits one rule from Draft 0088 and say what happens to core if 0088 lands differently.

**C5 — MATERIAL. The epoch-bearing anti-replay floor can collide with the never-evict-unacknowledged rule.**
§1 pairs two rules: unacknowledged receipts are never reclaimed (LLP 0043's refuse-at-capacity bound, `llp/0043:332-338`), and "identities carry a structured issuance epoch and the store persists a **minimum accepted epoch per audience**: a retry bearing an epoch below the floor refuses with a stable `identity-horizon-passed` diagnostic." The advancement rule for that floor is unspecified, and the two obvious ones both break. If the floor advances when an acknowledged receipt at epoch E is reclaimed, then every *unacknowledged, never-settled, still-in-flight* identity from the same audience minted at epoch ≤ E now refuses with `identity-horizon-passed` — a first attempt reported as outcome-unknown, which is precisely the exactly-once damage 0043's never-evict rule exists to prevent, and it is worse than eviction because the client is told the outcome is unknown when nothing happened. If instead the floor advances only when *all* identities in an epoch are acknowledged, then a single long-lived unacknowledged identity pins the floor indefinitely and reclamation never runs, which defeats the bound. The epoch granularity, the source of monotonicity across a client that has lost its store, and the interaction with 0043's per-auth retention counters (`src/storage.rs:5648-5652`, `:17191-17201`) are all unstated. Acceptance 2 and 14 test the below-floor refusal but not the false-positive case. **Resolution:** specify the floor-advancement rule, prove it cannot strand a never-settled identity, and add an acceptance row where an in-flight lower-epoch first attempt from the same audience is admitted normally while a genuinely reclaimed identity is refused.

**C6 — MATERIAL. Forcing checkpoint-based forks into LLP 0158's derived-deployment class is a new ruling presented as an inherited one.**
§3 states "A fork based on a named checkpoint is always this class — its base sits behind the canonical head, so strict-CAS promotion could never accept it anyway," and §6 says a materialized checkpoint "alone can base a (capture-only) fork." The promotion rationale is sound, but the class assignment does not follow from it: non-promotable does not imply *separate instance*. LLP 0097 explicitly deferred historical-base forks rather than reassigning them — "v1 forks the current canonical head only; forking a *prior* captured state ('design against the bug') is a separate historical-snapshot capability, deferred" (`llp/0097:51`), with OQ4 keeping the base-choice UX open. Routing that capability through 0158's derived-deployment class imports whole-instance scrub-and-mint (`llp/0158:827`, `:861-873`), a separate canonical stream, a different trust boundary, and schema/function divergence the app never asked for — to serve a same-app, same-schema, read-later fork. It also inherits 0158's still-Draft OQ9 amendment to LLP 0018/0012, which §3 itself flags as "proposed-normative in a still-Draft RFC." **Resolution:** either justify the assignment on custody grounds explicitly (why a checkpoint-based in-app branch would be unsafe), or add a third declared class — non-promotable in-app branch at a checkpoint base — and record whether it needs a dated 0097 amendment.

**C7 — MATERIAL. The fork-diff digest can never be proof at runtime under the RFC's own §4 rule.**
§4 says the diff digest is "proof only where Acceptance 9's independent base/head comparison supplies the independently derived expected value, inventory otherwise," and §8 offers a proof class of "recorded inventory versus independent boundary proof." But Acceptance 9 is a *fixture-time* randomized comparison against an independent base/head logical comparison — it is a property of the test suite, not a derivation available at runtime, where §4 has already established that the base is not retained unless preimages or an immutable base were recorded. So a production diff digest is inventory in every case, and §8's proof class cannot advertise independent boundary proof for the diff surface. Contrast the checkpoint treatment in the same section, which *does* specify a runtime dual-path derivation ("the checkpoint path digests the copy it produced, an independent scanner digests the source at the same stream-qualified version, and the two must agree — two code paths, one expected value") — that is the shape §4 owes the diff. LLP 0081's rule is unambiguous: "a digest without an independently derived expected value is inventory, not proof" (`llp/0081:535`). **Resolution:** either define a runtime independent expected-value derivation for the diff boundary (the promotion staging comparison in §5 is a candidate) or state plainly that the diff digest is inventory in v1 and remove diff from the proof-class axis.

**C8 — MATERIAL. Sequencing step 5 is now stricter than the design requires, and the RFC does not say which is controlling.**
§Sequencing 5 wires "LLP 0097's host-egress mediation and capture-ledger integration — the prerequisite LLP 0097 defines and F0a deliberately cut — so branch effect capture exists before promotion depends on it," and step 6 (promotion) follows it. But v0.4's own §5 rule — "A branch whose log contains no egress attempts is promotable under a `DenyAll` egress policy" — and §8's core aggregate (which accepts `DenyAll` *or* `CaptureOnly`) mean promotion no longer depends on the capture ledger for the no-egress case. This is not cosmetic: it decides whether the profile's first genuinely useful slice can be built on top of LLP 0158's F0a deny-all posture alone, or must wait on the 0097 mediation program that F0a deliberately excluded (`llp/0158:868-874`). Since §Sequencing opens by calling itself "dependency order, not implementation authorization," an unnecessary dependency edge here has real cost. **Resolution:** split step 5 into the DenyAll mediation slice (a genuine prerequisite for any fork) and the capture-ledger slice (a prerequisite only for `CaptureOnly` and for promoting branches that attempted effects), and say which slice step 6 consumes.

**C9 — MATERIAL. §3's "F0a scope is exactly the `DenyAll` slice" blurs the two fork classes the same section forbids blurring.**
§3 opens by naming two classes and refusing to blur them, then closes with "The first safety slice may be **deny-all egress** ... LLP 0158's F0a scope is exactly the `DenyAll` slice — its implementation status is F0a's to report — and the capture ledger is deferred work," in a paragraph that is class-agnostic. But F0a is scoped entirely to the derived-deployment class: its deny-all posture covers "every enumerated op family plus manual cron tick, forced drain, provider adapters, and S3/provider asset I/O under inherited env credentials" in a *forked instance* (`llp/0158:861-873`), and 0158's phasing explicitly excludes "promotion/graduation of a fork" (`llp/0158:895-899`). The in-app branch's egress mediation — the class that actually promotes — is LLP 0097's §Design 2 prerequisite, is unbuilt, and appears in this RFC only as sequencing step 3(a) and step 5, neither of which any live lane owns. §Sequencing gets this right; §3 does not, and a reader taking §3 at face value would conclude the promotable class's safety plane is already green-lit work. **Resolution:** qualify the sentence to "F0a's deny-all posture is the derived-deployment class's `DenyAll` slice; the in-app branch's equivalent is unbuilt and is sequencing step 3(a)."

**C10 — MINOR. Acceptance 14's absolute "no authorization decision may be derived from envelope contents" is untestable as stated.**
§Security ends "The envelope is evidence, never a second authority: no authorization decision may be derived from envelope contents," and Acceptance 14 demands "a negative fixture proves no authorization decision can be derived from envelope contents." But §1 records grant/policy identity and "fencing token or epoch where the lane uses one" on the envelope, and §5's promotion "revalidates current principal, grant, policy, manifest, operation identity, and fence" — which necessarily reads those recorded identifiers as lookup keys into current authority state. The intended rule (a recorded grant is never itself a grant; only a fresh evaluation of current state authorizes) is right and matches LLP 0097 §3's "Recorded historical authority is never silently reused." **Resolution:** restate as "envelope-recorded authority identifiers may be used only as lookup keys into current authority state; no envelope field may supply an authorization *result*," and scope the acceptance fixture to that.

**C11 — MINOR. Disposition vocabulary has no owner, and §1 and Acceptance 2 disagree about what survives reclamation.**
The RFC coins or reclassifies four dispositions — `detail-expired`, `detail-truncated`, the horizon marker, and `identity-horizon-passed` (v0.4 reclassified the last as outcome-unknown rather than a typed failure) — without naming which document owns the vocabulary, while §Sequencing carefully names owners for settlement, retention, wire, and client conformance. Separately, §1 says "The compact envelope identity (§2) may outlive the suppression record," but Acceptance 2 tests the case "after **every envelope and suppression record** for an identity has been reclaimed" — leaving unstated whether a surviving envelope identity can answer a retry, and if so why the epoch floor is needed for that case. **Resolution:** name the owning document for the disposition vocabulary (OQ5 is the natural home) and reconcile the two reclamation statements.

**C12 — MINOR. The identity-facts description is under-inclusive against the shipped preimage.**
§1 says the canonical identity "continues to bind every semantics-affecting fact the shipped path binds — function, auth fingerprint, authority-instance descriptor, and the input fingerprint over `{args, readSet, ctxLedger}`." The shipped preimage also carries `settlement` whenever it differs from the default (`src/storage.rs:17153-17166`, with the all-default lane-Q carrier deliberately retaining the pre-0133 preimage so an additive server upgrade can republish stored settlements), and LLP 0133 §Exactly-once identity adds lane, element-1/5 identity claims, bounded-skew declaration identity, and the lane-L claim set to the retained identity (`llp/0133:284-292`). The "every semantics-affecting fact" claim is therefore slightly wrong as written, and the omitted legacy-preimage carve-out is exactly the kind of detail a widening to host originators must not break. **Resolution:** cite the settlement carrier and the 0133 additions, or soften to "the facts the shipped path binds today, enumerated in LLP 0133 §Exactly-once identity."

## 5. Suggestions (non-blocking)

- §Profile-at-a-glance is the document's best on-ramp but its P1 cell now carries four clauses of class detail. Consider moving the class distinction into §3 and letting the table cell say "two declared classes (§3)" — the table earns its keep as a remainder-honesty device, not as a spec.
- §1 has grown to roughly seven dense paragraphs covering identity, key shape, atomicity, per-originator sources, versioned transition, and the suppression lifecycle. A subsection break (identity / atomicity / lifecycle) would help without changing a word of substance.
- The `DenyAll` versus `CaptureOnly` distinction is load-bearing in four places (§3, §5, §8, §Sequencing) and each states it slightly differently. One sentence in §0 Defined terms would remove the drift risk — and §0 is already the right home, since it does this for *covered*, *lane*, *stream identity*, and *paved path*.
- §4's canonical folding rules are precise and testable; consider promoting them into acceptance row 9's text as an explicit enumerated list, since the current row folds them into a clause and the fixtures will need each case separately.
- Acceptance 13 ("the measurement gate above is published against the named baseline artifact and passes per metric") now depends on a baseline artifact that does not exist. Worth naming that artifact's creation as a numbered sequencing step (step 0) rather than leaving it inside the gate's prose, since it blocks every component's advertisement.
- OQ4 (the 15% budget) and §Measurement gate's "each judged individually" p50/p95 rule are well matched; consider recording in OQ4 that the initial instrumentation-only measurement it proposes is itself gated on the same baseline artifact, so the two open items resolve in a known order.
- The §Revisit-triggers section is strong and under-cross-referenced. The Merkle trigger's first bullet ("journal-derived fork diff misses its latency or memory target") is exactly what §Measurement gate's fork/diff metric measures — a pointer between them would let the gate double as the trigger's instrument.

## 6. Open questions

1. If C1 resolves toward audience-in-the-key, what is the intended behavior for a client-minted `operationId` re-presented under a different principal — and does that weaken or strengthen the cross-principal receipt isolation `SNAPBACK_AUTH_STALE_RESULT` provides today (`src/storage.rs:2224-2236`)?
2. Does `AgentSafeV1-core` intend to be reachable on a target that has passed LLP 0097's Acceptance corpus, or does the profile propose its own substitute corpus for the branch capability? §8 asserts core's owning designs are Accepted, but 0097 is Accepted *with an unpassed gate*, which is a different fact.
3. What is the promotion-contention policy for the pinned first consumer (fork-per-worktree over one demo app)? Even "first-come, unbounded retry, agent's problem" would be an answer; the absence of one is C3.
4. Is `streamId` for a *canonical* stream stable across LLP 0158's scrub-and-mint of a derived deployment, or does the mint produce a new stream identity that renders parent envelopes unjoinable? OQ9 asks the inheritance question for envelopes and explanations but not the identity-continuity question underneath it.
5. Does the per-audience epoch floor survive a client that has lost its local store and must mint a fresh identity family — i.e. is the epoch derived from server-issued state, client-local monotonic state, or the authority instance?
6. What does an agent do with a `NotPromotable` branch whose non-promotability arose *late* (an uncovered-lane co-write, or a non-retainable replay input, per §3)? The branch receipt records it, but the profile offers no salvage path other than discarding work — is that intended, and should there be a diagnostic naming the specific operation that foreclosed promotion?
7. Should the profile declare whether two forks of the same head may be diffed against *each other* (as opposed to base-to-head)? LLP 0161's Merkle revisit trigger names "agents frequently compare states without an ancestor/base relationship" as the escalation signal, which implies the profile expects the question to arise but never says what v1 answers.

## 7. Recommended next step

Produce v0.5 addressing C1–C3 first, since each is a single decision rather than a research task: (1) choose whether audience is a key component or a compared fact, make §1 internally consistent, and carry the 0133 consequence explicitly — with an acceptance row for whichever behavior is chosen; (2) add the dated proposed-normative amendment to LLP 0097 §Capability classes recording the axis split and the `DenyAll` value, plus the mapping from the new matrix onto 0097's three-value axis and which 0097 acceptance rows a `DenyAll`+`Promotable` target must pass; (3) either add a promotion-admission paragraph to §5 with a bounded rebase budget and a k-concurrent-fork acceptance row, or explicitly defer contention with a named revisit trigger and soften the P9 "strongly" claim in the §Profile-at-a-glance table accordingly. Then fold C4 (own the per-version rule for core, or state core's dependency on Draft 0088 honestly), C5 (specify epoch-floor advancement and add the false-positive fixture), and C7 (runtime expected-value derivation for the diff boundary, or drop diff from the proof-class axis) — these three are the remaining places where the document claims more discipline than it currently specifies. C6, C8, C9, and C10–C12 are paragraph-level repairs that can ride the same revision. After v0.5, this should go back through one more cross-family round rather than to acceptance, because C1 and C2 both change contracts owned by Accepted documents and a fresh reader should confirm the amendments land cleanly; the author's own note that acceptance "should follow a cross-family review because the RFC joins storage correctness, authority, effects, retention, and performance on the ordinary write path" is the right standard and is not yet met.

## 1. Overall assessment

LLP 0162 v0.5 is a genuinely strong, unusually disciplined bounded-profile RFC: it takes LLP 0161's P1–P9, refuses four of them by name, and builds the remainder out of foundations that I verified actually exist in the tree — server-captured read/query/predicate dependencies (`src/runtime.rs:2768-2808`), the `_snapback_changes` row journal with its `(version,id)` and `(table_name,version)` indexes (`src/storage.rs:5600-5615`), the durable `ClientMutationIdentity` with refuse-at-capacity retention (`src/storage.rs:621-627`, `src/storage.rs:182-192`), `ContentDigestV1`'s framed streaming digest (`src/rqs.rs:1076-1119`), the dry-run report (`src/host_ops.rs:1621-1700`), and LLP 0097's landed `MaterializedBase`/overlay/`EffectClass` substrate (`src/branches.rs:344-720`). Its corpus discipline is the best part: I found **no contradiction** with LLP 0088 §4, LLP 0097 §5 (the RFC correctly reports `branches::promote` as a *deviation from Accepted 0097* — and `src/branches.rs:956-958` does apply overlay post-images directly, exactly as claimed), LLP 0158 (F0a's deny-all cut and the merge-back non-goal preserved unamended), or LLP 0081 §5 (the inventory-not-proof rule is applied *against the RFC's own diff digest*, which is the single most credible move in the document). Add a §8 provenance claim that is checkably false against document statuses, an amendment whose declared scope is narrower than its reach, a contention answer that converts a race into deterministic starvation, and a duplicated sequencing step, and this is a document one focused revision away from convergence rather than at it.

## 2. Verdict — NOT READY

NOT READY. This is a Draft seeking review convergence and it has clearly earned four rounds of real repair — the identity model, the diff-substrate honesty, the capability layering, and the checkpoint dual-path proof are all materially better than what a first draft would carry. ## 4. Concerns

### C1 — MAJOR: universalizing `operationId` into a globally unpartitioned keyspace, with deterministic host-derived identities, creates an identity-squatting denial-of-service the Security section does not address

§1 fixes the physical key as `(streamId, operationId)` — a single canonical-stream namespace — then requires host-initiated operations to derive their identity **deterministically** from durable upstream identities. The shipped ledger is a single global keyspace: `src/storage.rs:2161` reads `FROM _snapback_client_mutations WHERE client_mutation_id = ?1` with no principal predicate, and divergence yields `SNAPBACK_CLIENT_MUTATION_ID_REUSED`. Today that is tolerable: the id space is populated only by clients, opting in, with opaque ids. This RFC changes both halves at once: identity becomes **mandatory on every covered lane**, and **predictable** identities enter the same space. A caller who can mint an arbitrary `operationId` can pre-claim the identity a future cron occurrence, job attempt, or migration step will deterministically derive; when that host operation runs, it presents a colliding identity whose bound facts diverge and — by the RFC's own rule — refuses permanently, since §1 forbids evicting the unacknowledged squatter. §Security's digest-oracle clause protects digests from disclosure; it does not prevent an attacker from **writing** a chosen identity into the ledger. No acceptance item covers attacker-presents-first. **Resolution:** namespace the physical key by originator class at minimum — `(streamId, originatorClass, operationId)`, with the host-derived namespace unwritable by client-originated admission — or require host-derived identities to be server-authenticated (MAC'd under the issuing authority, as §1 already does for epochs); state the rule in §1, add it to §Security, and add a negative acceptance fixture.

### C2 — MAJOR: the commit envelope's own retention is undefined; a third retention clock is introduced with no bound, no independence rule, and no relationship to the journal it joins

§2 gives only the *detail* an expiry; the compact identity's lifetime is never bounded anywhere. §Non-goals disclaims "indefinite history retention"; §6's GC preservation list does not include the compact envelope identity. Yet the document depends on its reclamation twice: §1 says "the epoch floor covers only the case where both records are gone," and §Acceptance 2 requires a fixture "after **every envelope and suppression record for an identity has been reclaimed**." So reclamation is presupposed by the acceptance corpus while being specified nowhere. Second, the join is unanchored: row journal records join through the stream-qualified commit version, but `_snapback_changes` is pruned by LLP 0008's max-versions/max-age rule on a clock the RFC never relates to envelope retention — a pruned journal with a surviving envelope leaves provenance with nothing to explain; a pruned envelope with a surviving journal row breaks §Acceptance 3's join. The RFC is careful about the *other* two clocks, which makes the omission of the third conspicuous. **Resolution:** give §2 a bounded retention rule for the compact envelope identity, with an explicit independence statement against both the resume replay floor and the journal prune predicate; define what an explanation returns when one side of the join survives the other; add the pair to §Acceptance 8; widen OQ1.

### C3 — MAJOR: §6's captured-policy-version evaluation requires a retained historical policy representation that no document owns, no substrate provides, and the §Non-goals disclaim

§6 requires non-row facts to be "evaluated **under the policy version it was captured under**; if that policy version cannot be loaded, the fact is withheld fail-closed." Nothing in the tree or the corpus supplies a retained, loadable historical read policy; LLP 0088 §6, which the RFC imports for row facts, evaluates the *current* read policy against each historical post-image — it does **not** require loading the historical policy. So §6 is strictly stronger than the design it claims to inherit, and it is a retained historical representation — exactly what §Non-goals disclaims and §Motivation prices as too expensive. With no policy-version store, **every** non-row explanation fact is withheld, making the core tier's explanation surface vacuous. **Resolution:** either (a) name the policy-version identifier, its owner, sequencing step, and budget line; or (b) drop to LLP 0088's actual rule — evaluate non-row facts under the *current* policy — and record the residual leak explicitly as an accepted bound with a revisit trigger. Option (b) is the 80/20 move and is consistent with everything else in the profile.

### C4 — MATERIAL: §8's provenance claim for the core tier is checkably false

§8: "every owning design behind the core is Accepted (LLP 0097 …) or this RFC itself." But the core requires the host-plan settlement lane (LLP 0007 — **Draft**); the identity-source contract lands as LLP 0012/0095 amendments (**Draft**); the explanation read API is shaped by LLP 0004 (**Draft**); the envelope requires LLP 0055 scoped grants (**Review**); effect classification is per LLP 0066 (**Review**, "not yet an owned taxonomy"). Several are Draft-but-shipped, a real distinction the corpus tolerates — but the sentence asserts a status fact, and the status fact is wrong for five documents. **Resolution:** restate as *no core component depends on an undecided design decision*, with a short per-component table naming each owning document, its status, and whether the dependency is decided or unratified.

### C5 — MATERIAL: the dated LLP 0097 amendment's declared scope is narrower than its actual reach

The amendment names §Capability classes, but the same paragraph edits 0097 §Acceptance (fixture substitution for `(DenyAll, Promotable)` targets), and §5 adds serialized admission, a bounded rebase budget, and rebase-by-replay — all additions to Accepted 0097 §5's promotion protocol, none carried by any amendment. OQ10 asks the question for rebase-by-replay only; if rebase needs an amendment, so do serialized admission and the fixture substitution. **Resolution:** widen the dated amendment's declared scope to enumerate every 0097 section it touches, or split it into named amendments; fold OQ10 into the same instrument.

### C6 — MATERIAL: the contention answer converts a race into deterministic starvation, and the acceptance corpus does not test progress

Serialized admission plus strict CAS means after the first promotion all k−1 remaining forks refuse and rebase; nothing defines admission *fairness* — a rebased fork re-enters with no reservation or priority, so a slow or large-log agent is deterministically outraced and exhausts its budget. The rebase budget bears no stated relation to k. §Acceptance 10 tests exactly the failure half and never tests that all k eventually promote. **Resolution:** state a fairness rule (FIFO admission tickets held across rebase, or a head reservation window), relate the rebase budget to observed concurrency, and add an acceptance item proving bounded eventual progress for all k under a steady arrival rate — or declare starvation an accepted v1 bound with a revisit trigger.

### C7 — MATERIAL: `DenyAll` egress mediation is assigned to two different sequencing steps, and §3 cross-references the wrong one

Step 3(a) lists "`DenyAll` egress" and step 5(a) declares the `DenyAll` mediation slice "a genuine prerequisite for any in-app branch"; §3 points at 3(a). If mediation is step 5, step 3(a) delivers an in-app branch with no proved mediation — which Accepted LLP 0097 §Design 2 forbids outright. The v0.5 revision note says this round "splits mediation from capture-ledger work," so the duplication is a repair that did not propagate to §3. **Resolution:** remove `DenyAll` egress from step 3(a), leave it solely as step 5(a), correct §3's cross-reference, and state that step 3(a) yields a branch that cannot execute egress-bearing paths until 5(a) lands.

### C8 — MATERIAL: LLP 0130 is not an available exception authority for this RFC, and the exception clause makes Acceptance 13 unfalsifiable

LLP 0130 is a closed set of pre-adjudicated rules; SD-4 is scoped to documents commissioned by the accepted programs, which this RFC — by its own §Sequencing — is not. 0130's only extension path is a dated revision adding a new SD, a different act than invoking an existing mechanism. Separately, the exception clause is unbounded (no ceiling, no aggregate envelope, ratifiable *after* measurement), so a gate whose every failure can be excepted post-hoc is not a gate. **Resolution:** name the actual authority (a dated 0130 revision adding an SD, or author ratification recorded in this RFC) and bound the exception: a hard ceiling, re-measurement after the next component lands, and a rule that an exception holds the affected capability below stable rather than passing it.

### C9 — MATERIAL: no discovery surface for envelopes — the "proof over memory" pressure is only half served

Every access path is a point lookup keyed by something the agent must already hold. An agent that loses its context loses its `operationId`s and therefore cannot ask what it did — precisely the failure LLP 0161 says the substrate must absorb. **Resolution:** state in §2 that the explanation surface supports bounded enumeration by principal/session/time within the retention window, subject to the same fail-closed authorization; add an acceptance item; record the index cost in the structural budget.

### C10 — MINOR: §4's description of the shipped `ContentDigestV1` header is incomplete

The header also binds `algorithm_version`, `schema_hash`, `qualified_table`, and `publication_timestamp` (`src/rqs.rs:1076-1085`) — the shipped preimage is migration-*instant*-bound, which strengthens the RFC's point but means a reader implementing §4 from this description will under-specify the new domains. **Resolution:** cite the full field list or `src/rqs.rs:1076-1085` directly.

### C11 — MINOR: the §4 substrate finding is a real divergence between Accepted LLP 0097 and the landed code, and should be flagged as such

Accepted LLP 0097 §Design 1 reads as an immutable base plus overlay; the code says the materialized base *is* a writable fork. A reader of 0097 will conclude an immutable base already exists and §4's preimage requirement is redundant. **Resolution:** name it as a doc/code divergence in 0097's lane, as §5 already does for `branches::promote`.

### C12 — MINOR: §4's checkpoint dual-path proof leans on unnamed WAL snapshot mechanics while a working precedent sits in the tree uncited

`MaterializedBase::materialize` already reads `base_version` back from the snapshot so it is atomically consistent with the copied pages (`src/branches.rs:362-377`). **Resolution:** cite that precedent and name the intended mechanism, since the declared resource budget and stable-refusal rule depend on which one is chosen.

## 4. Concerns

**C1 — MAJOR. The sealed `PromotionRequestV1` and the FIFO-ticket contention answer are mutually unreconciled; Acceptance 10's bounded-progress property is not established.**
§5 requires promotion to consume a `PromotionRequestV1` that "binds the exact reviewed child-stream head (sealed by a branch-head CAS — a branch write after review invalidates the request)", the operation-log digest, the diff digest, and "the approver's identity and authority." §5 then answers contention with serialized admission, rebase-by-replay into "a new fork based on the current head," and inherited FIFO tickets, concluding: "Bounded eventual progress for all k forks under a steady arrival rate is an acceptance property, not a hope." Acceptance 10 states both properties in one row. But a rebase produces a new fork with a new `childStreamId`, a new head, and a potentially different diff digest — so it necessarily invalidates the sealed request, and the RFC never says whether the approval is re-derivable mechanically, inherited with the ticket, or must be re-obtained. Under the only reading the text supports, every losing fork in a k-way contention needs a fresh approval per cycle, which makes the approver — not the admission queue — the rate limiter, and directly contradicts "contention is answered by the engine, not etiquette." **Resolution:** state explicitly whether `PromotionRequestV1` is re-mintable across rebase without a new human/agent approval (e.g. the approval binds the *approved facts* — write set, effect set, coverage manifest — and re-seals automatically when re-execution reproduces them, with a fresh approval required only on divergence), and make Acceptance 10's bounded-progress fixture run with approval issuance in the loop so the claimed property is actually the one tested.

**C2 — MATERIAL. Per-row provenance attribution is undefined at the promotion version, contradicting Acceptance 3.**
§1 makes the journal-to-envelope join go "through the stream-qualified commit version of the data-changing operation," and §4 advertises "operation and principal attribution by commit-envelope join." §5 then commits a promotion as "one canonical transaction and one canonical version ... writing one aggregate promotion envelope keyed by the promotion identity with per-source join records at that version." Every journal row written by a promotion therefore shares one version whose envelope is the aggregate — so the version join attributes all promoted rows to the promotion, not to the branch operation that produced them, and "per-source join records" is not specified at row granularity anywhere. Acceptance 3 nonetheless requires without carve-out that "a committed row change joins to its operation, principal, authority, artifact, and retained read/write facts." This is the one place the version-keyed join is provably many-to-one on data-changing operations, and it is the place agents most want the answer ("which of my branch's operations actually wrote this row?"). **Resolution:** require the per-source join records to carry row-level (or write-fact-level) granularity, or add an explicit disposition naming promotion-aggregated attribution and carve it into Acceptance 3.

**C3 — MATERIAL. The epoch-closure rule contradicts its own summary sentence, and the two readings differ in whether an audience can wedge.**
§1: "An epoch **closes** only when both hold: its issuer is terminated or revoked ... and every recorded minted identity under it is **admitted-and-settled**, expired by the issuer's declared mint-record window with an explicit outcome-unknown classification, or operator-purged" — followed eight lines later by "a single **unacknowledged** identity holds its epoch open (bounded by the refuse-at-capacity rule, not by eviction)." An unacknowledged-but-settled identity satisfies the first closure alternative, so either (a) "settled" silently means "acknowledged", in which case one crashed client holds its audience's epoch floor open indefinitely with only an operator purge as escape, or (b) "settled" excludes acknowledgement, in which case the quoted summary sentence is simply false and epochs close over live unacknowledged receipts. §1's earlier text distinguishes the terms deliberately ("an *unacknowledged* receipt is never evicted"), which makes the ambiguity load-bearing rather than cosmetic. Acceptance 2 and 14 test admission and reclamation but never the closure predicate itself. **Resolution:** define "settled" against LLP 0043's acknowledgement-driven vocabulary, pick one closure semantics, and add a fixture that advances a floor past an epoch with a live unacknowledged receipt (or proves it cannot).

**C4 — MATERIAL. The middle retention regime answers a retry with a disposition where LLP 0043 answers with the stored result, and no client-contract amendment covers it.**
§1: "The compact envelope identity (§2) may outlive the suppression record, and while it survives a retry matching it returns the durable receipt disposition from the envelope." But §2 defines the compact identity as digests, provenance classes, and counts — not the result payload — while LLP 0043's shipped contract republishes the stored settlement itself. So in this regime a retrying client gets a *disposition* where it contractually expects a *result*, which is a client-visible behavior change. The RFC carefully mints dated LLP 0043/0012/0095 amendments for `identity-horizon-passed` but not for this case, and Acceptance 2 tests the below-floor case and the reclaimed case but not the envelope-survives-suppression-record case. **Resolution:** name the disposition, state whether it is terminal or outcome-unknown for the client, and fold it into the same dated 0043/0012/0095 amendment and into Acceptance 2.

**C5 — MATERIAL. The checkpoint dual-path proof credits `MaterializedBase::materialize` with a snapshot-pinning mechanism it does not implement.**
§4: "the checkpoint operation holds a read transaction pinning the source snapshot (the mechanism `MaterializedBase::materialize` already uses — the backup API reads the version back from the copied pages so it is consistent even if the source advances), the backup and the independent scanner both read that snapshot." The landed code (`src/branches.rs:362-378`) opens no transaction on the source at all: it runs `rusqlite::backup::Backup::new(source, &mut conn)` and `run_to_completion(128, 1ms, None)`, then reads `current_version_on(&conn)` — i.e. off the *copy*. That gives the copy internal consistency, but it emphatically does not pin a source snapshot a second, independent scanner can read; the RFC's own next sentence concedes exactly this. The mechanism the design requires is therefore net-new, and whether SQLite's backup API can be driven from inside a held read transaction on the source without restart or deadlock is unverified anywhere in the tree. Relatedly, calling this an "independent derivation" stretches LLP 0081, which reserves that term for a *predecessor-derived* expected value; two scans of the same bytes prove copy fidelity, not content correctness. **Resolution:** drop the "already uses" credit, state the pinning mechanism as unbuilt work with its own spike, and re-scope the claim to "verified copy fidelity at a pinned source snapshot" rather than boundary proof in 0081's sense.

**C6 — MATERIAL. "Proves journal completeness" is asserted with no derivation, which is inventory by the RFC's own standard.**
§4: "The implementation proves journal completeness for every covered write path," and §0's definition of *covered* makes "a journal-completeness proof for every write path in the lane" a precondition of coverage — so the entire coverage vocabulary rests on this word. The only mechanism offered is Acceptance 4: "every declared lane has positive and bypass fixtures." Fixtures over an enumerated list prove the enumerated paths behave; they cannot establish that the enumeration is exhaustive, which is precisely the property "completeness" names — and LLP 0097 §Design 2 already records that the runtime has "at least four initiation families" that a single-seam assumption missed, as does LLP 0158. A document that demotes its own diff digest to inventory for lacking an independently derived expected value should not accept fixture enumeration as proof of exhaustiveness. **Resolution:** name the derivation (a code-owned closed write-path registry with a compile-time or schema-export exhaustiveness check, in the manner of `EffectClass::classify`'s closed set, plus a fixture that a newly added unregistered write path fails the build), or rename the requirement to "journal-coverage inventory" and let coverage refuse on any unregistered path.

**C7 — MATERIAL. The non-row-fact authorization rule is presented as an import from LLP 0088, which contains no such rule.**
§6: "Non-row facts follow LLP 0088's actual rule — the **current** read policy evaluates each retained fact; no historical policy version is loaded." LLP 0088 §6 states one rule and it is only about historical post-images: authorized-for-the-record-now *plus* per-post-image evaluation. It says nothing about missing-row, predicate, membership, ctx-answer, or effect facts — those categories do not exist in 0088's design. This RFC is therefore authoring a new, consequential decision (a fact captured under an older policy is disclosed per today's policy) and attributing it to a Draft document that never made it, in the same section where §8 correctly claims ownership of the *row* rule. The residual is named honestly, which is good; the attribution is not. **Resolution:** own the non-row rule here explicitly, as §8 already does for the per-version row rule, and cite 0088 only as the analogy it is.

**C8 — MATERIAL. Sequencing step 3(a) is not separable from 5(a) by any mechanism the RFC names.**
§3 and Sequencing 3(a) both assert "a step-3(a) branch cannot execute egress-bearing paths until [5(a)] lands," and the measurement gate leans on this separability. But enforcing "cannot execute egress-bearing paths" *is* mediation — the only alternatives are refusing all branch handler execution (which makes step 4 vacuous) or a static declared-egress analysis that the RFC never names. LLP 0097 §Design 2 sets the fail-closed posture — "refuse branch execution for any action, adapter, native module, or target lacking proved mediation" — but that posture argues for the conservative reading. **Resolution:** name the enforcement (e.g. admission refuses any handler whose declared `uses`/ctx surface can reach the enumerated egress families of LLP 0158, with the closed-set refusal proved by fixture), and state which fork operations a 3(a) branch can actually execute so step 4 has content.

**C9 — MATERIAL. The 0097 capability amendment defines only the forward map, and `(DenyAll, Promotable)` advertises a class whose defining half it never proves.**
§8 maps 0097's ordered `Missing | CaptureOnly | Promotable` onto the new axes and concludes "an existing three-value report translates losslessly" — true in that direction, but the reverse is unaddressed: a `(DenyAll, Promotable)` target has no point in 0097's three-value enum, and every existing consumer of that field will compute *something*. Worse, LLP 0097 defines `Promotable` as "data re-execution + staged effect settlement", and the amendment permits `Promotable` with "the effect-settlement fixtures replaced by negative fixtures proving its attempt markers are empty" — so a target advertises 0097's `Promotable` having never exercised the staged-settlement half that 0097's acceptance corpus makes the gate. The substitution is defensible on the merits but it is an evidence-boundary change to an **Accepted** RFC made by a Draft one, and LLP 0130 ER-2 treats evidence-boundary weakening as a reservation even where its standing rules apply. **Resolution:** define the reverse projection for legacy three-value consumers explicitly, and either rename the promotion axis value for the no-egress case or state in the amendment that `(DenyAll, Promotable)` is a strictly narrower claim than 0097's `Promotable` and cannot be reported as it.

**C10 — MINOR. OQ4 and §Measurement gate disagree on who may change the performance threshold.** The gate text correctly names the author-by-dated-revision; OQ4 still says "under LLP 0130's mechanism." A v0.6 repair that landed in one place and not the other. **Resolution:** restate OQ4 in the gate's terms.

**C11 — MINOR. "Capture-only class" collides with the reserved `CaptureOnly` egress value the RFC itself declares load-bearing.** §3 names the promotion-axis class "the capture-only class" for a fork whose actual v1 egress value is `DenyAll`. **Resolution:** rename the promotion-axis class (e.g. "the non-promotable class").

**C12 — MINOR. The enumeration index is charged as per-row amplification when it is per-operation.** Envelopes are per-operation by §1's own design; only the journal index is per-row. **Resolution:** split the two costs.

**C13 — MINOR. Only the mutation thresholds in Acceptance 13 are actually normative today.** The read-path equivalence bound is defined by the step-0 baseline artifact, so the read-path half is self-referential until the artifact exists. **Resolution:** state the read-path formula here or say plainly it is delegated to the step-0 artifact.

## 1. Overall assessment

LLP 0162 v0.7 is a mature, unusually honest RFC: the SHA verifies (`2145942d…`), the proposal boundary is stable, and the six prior rounds have left a document whose load-bearing claims about the tree are — where I checked them — accurate rather than aspirational. The `MaterializedBase` doc/code divergence §4 names is real (`src/branches.rs:403` says the copy *is* the writable fork against LLP 0097 §Design 1's immutable-base reading), the snapshot-pinning gap is correctly diagnosed (`MaterializedBase::materialize` reads `base_version` back off the copied pages at `src/branches.rs:371` and holds no source transaction), the `ContentDigestV1` header really is migration-instant-bound (`ContentDigestHeaderV1` at `src/rqs.rs:1075-1085` with `deny_unknown_fields`, all fields required), `TargetCapabilityId` really is a closed unit-variant enum that cannot carry multi-valued class facts (`src/manifest.rs:6604`), the landed `branches::promote` really does apply overlay post-images directly (`src/branches.rs:955-960`) in deviation from Accepted 0097 §5, and the v0.7 correction of OQ4's authority away from LLP 0130 is right (0130's SDs are scoped to the 0115/0129/0074 programs, `llp/0130:13-17`). The v0.7 deltas are mostly genuine improvements — the originator partition with server-authenticated host derivations, the acknowledgement-based epoch closure with the crashed-client wedge stated plainly, the checkpoint re-scope from "boundary proof" to "verified copy fidelity at the pinned snapshot," and the per-component owner/status table are all sharper than what they replace. But three of the v0.7 changes close their gaps by naming a mechanism rather than deriving one, and one of them — the automatic `PromotionRequestV1` re-seal across rebase — introduces a new authority defect that did not exist in v0.6: it can commit a materially different net change than the approver reviewed, which is the precise failure mode Accepted LLP 0097 §5 exists to forbid.

## 2. Verdict — NOT READY

Narrowly not ready, and not for architectural reasons: the boundary, the P1–P9 mapping, the merge posture, the two fork classes, and the layered aggregate are sound and I am not re-litigating them. The blocking issues are both fresh in v0.7 and therefore unreviewed by the other family: (C1) §5's re-seal rule enumerates write set, effect set, and coverage manifest as the "approved facts" while the request also binds a diff digest that re-seal pointedly does not require reproduced — so a rebase onto a base whose relevant rows changed can auto-re-seal on identical post-images and apply an unapproved net change, which is structurally 0097 §5's own price example; and (C2) §4's journal-completeness "build-time sweep" is the derivation on which the word *complete* — and hence §0's definition of *covered*, the exact-diff claim, and the core tier — now rests, but no such sweep exists, the cited `EffectClass::classify` pattern (`src/branches.rs:605-613`) is a runtime string-to-enum validator solving a different problem, and `build.rs` has no code-sweep precedent. Both are sentence-to-paragraph repairs, not redesigns; the remaining MATERIAL items are contract-consistency gaps of similar size. A v0.8 fixing C1–C2 and dispositioning C3–C11 should be READY without another full round.

## 3. Strengths

- The v0.7 checkpoint re-scope is the best change in the revision: §4 drops the boundary-proof claim to "verified copy fidelity at the pinned snapshot," names the pinning mechanism as net-new, and routes it to a spike (OQ13) instead of asserting it — exactly LLP 0081's "a digest without an independently derived expected value is inventory" discipline applied against the author's own interest.
- §1's epoch-closure protocol states its wedge rather than hiding it, and correctly grounds it in LLP 0043's actual posture — refuse-at-capacity, never evict an unacknowledged receipt.
- The per-component owner/status table is a real improvement over a blanket provenance claim and makes the 0007-Option-A and 0066 residuals inspectable.
- §8's `Promotable(noEffects)` naming — a strictly narrower claim that "must not be reported as 0097's `Promotable`" — is the right instinct, and the 0097 amendment's scope widening to every touched section is honest about what an amendment costs.
- Corpus fidelity is high throughout: the §1 identity widening matches 0133's extend-don't-ride-beside discipline and its collision families verbatim, and §6's per-version rule matches 0088 §6 including its explicit rejection of the current-row-only gate.

## 4. Concerns

**C1 — MAJOR. §5's automatic re-seal can promote an unapproved net change.** The claim is that reproducing "the write set, effect set, and coverage manifest digests" against a new head re-seals the request "without fresh approval." But `PromotionRequestV1` also binds "the diff digest", and the re-seal comparison omits it — necessarily, since §4 establishes that a net diff is base-relative. Consequence: an operation writing `order.status='shipped'` unconditionally produces an identical write-set digest whether the new base says `pending` or `cancelled`; the approver reviewed `pending→shipped` and the promotion applies `cancelled→shipped`, auto-re-sealed. This is 0097 §5's ruling that "a re-execution that merely runs without error on an advanced base is not evidence the selected future's meaning was preserved", which §5 itself cites four paragraphs later for the divergence case. Resolve by requiring re-seal to reproduce the *read set* (or the net-diff digest against the new base) in addition to the write/effect facts, and naming base-relative divergence as an approval-forcing condition; Acceptance 10's re-seal leg needs a matching negative fixture.

**C2 — MAJOR. Journal completeness is derived from a mechanism that does not exist and a pattern that does other work.** §4 replaces fixture enumeration with "a code-owned closed registry (the `EffectClass::classify` closed-set pattern), a build-time sweep [that] fails when a write path lands unregistered," and runtime refusal of unregistered paths. `EffectClass::classify` validates an inbound *string* against six egress families; it proves nothing about which code paths mutate tables. `build.rs` (396 lines: linking, guide embedding, build identity) contains no sweep precedent, and `src/storage.rs` writes the journal via direct SQL, so the runtime backstop depends on the same unproven exhaustiveness. Because §0 defines *covered* as requiring "a journal-completeness proof for every write path in the lane," this unearned closure propagates into the diff capability and the core aggregate. Resolve by naming a real mechanism (proc-macro/linker-section registration, a deny-listed `execute` lint, or a schema-generated write facade per LLP 0037) with its own acceptance row, or by reverting to enumerated fixtures and saying so.

**C3 — MATERIAL. Promotion provenance dangles after teardown.** Acceptance 3 requires a committed row change at a promotion version to join to "its operation, principal, authority, artifact, and retained read/write facts" through the per-source join records. But §1 says branch envelopes "are branch-local and are discarded at teardown", §3 disposes forks by default on TTL, and §5 binds only "the operation-log digest" — nothing retains the branch operation log post-promotion. Post-teardown the join record is an opaque `(childStreamId, sourceOperationId)` pair with no principal, artifact, or read set behind it, so the acceptance row is unsatisfiable in the steady state. Resolve by requiring the promotion transaction to durably copy the replay-sufficient log entries (or their envelope facts) into canonical alongside the join records, or by narrowing Acceptance 3's promotion leg to the aggregate's own facts plus an opaque source reference.

**C4 — MATERIAL. Promotion identity across re-seal is unspecified.** §5 re-seals "against the new `childStreamId`", while §1 makes the aggregate promotion identity "the sole key that participates in duplicate suppression, collision comparison, retention floors, and receipt lookup" and grounds promotion-record non-collision in `childStreamId`'s global non-reusability; the v0.5 revision note derives promotion identities from `childStreamId` outright. If the aggregate identity is childStreamId-derived, it changes on every rebase and Acceptance 10's "a post-promotion retry of the canonical identity returns the canonical receipt" is ambiguous about *which* identity survives; if it is not, §1 never says what it is derived from. Resolve by stating the aggregate identity's derivation explicitly and declaring that it is invariant across rebase and re-seal (the FIFO ticket already is), with a fixture retrying the pre-rebase identity.

**C5 — MATERIAL. The `Promotable(noEffects)` legacy projection is not the "weakest honest value"; it contradicts §8's own forward mapping.** §8 maps 0097's `Missing` to "(`Missing`, any)" on the new axes and then projects (`DenyAll`, `Promotable`) back to `Missing`. Those are not inverses: a legacy consumer is told the target has no branching at all, when it has branching, promotion, and a proved deny-all egress posture — and 0097's honesty rule forbids reporting a weaker class *as stronger*, not conservatism as such, so nothing compels this. It also makes the negotiated acceptance-fixture substitution moot for every legacy consumer. Resolve by projecting to `CaptureOnly`/`NotPromotable` with the narrowing recorded (branch exists, no ledger, no settled-effect promotion), or by declaring the combination legacy-unrepresentable and requiring consumers to read the extension.

**C6 — MATERIAL. The bounded head reservation is an unbudgeted, unquotaed availability lever.** §5 defers *ordinary* canonical mutation admission for a bounded interval to let a starved fork's promotion commit. That directly inflates ordinary-write tail latency, but the measurement gate lists only "p50/p95" with no p99 or worst-case-under-contention metric, and §Security's quota enumeration covers forks, bytes, history pins, digest work, effect captures, and explanation detail — not reservations, so a principal that can create forks and lose R cycles can repeatedly defer application traffic. Relatedly, the declared fairness conditions (arrival below service capacity; finite replay work) omit a third: ticket lifetime equals fork TTL, so bounded eventual progress for all k forks holds only while TTL exceeds k service cycles. Resolve by adding a reservation quota and a tail-latency metric to the gate, and adding TTL sufficiency to the declared conditions Acceptance 10 tests under.

**C7 — MATERIAL. The imported 0158 publication machine is both weakened by Acceptance 12 and contradicted by §6's registry authority.** §4 imports 0158's state machine "normatively" but omits the staging sentinel — the element that makes refusal predate the data and the one LLP 0161 itself names as the honest durability qualifier. Worse, Acceptance 12 encodes "crash cuts land on either side of the atomic rename … never in between", i.e. boundary sampling — precisely the corpus 0158 upgraded away from in its own converged loop ("F0a upgraded from boundary sampling to an intra-state crash-cut matrix"). Separately, 0158 deliberately demotes the registry to advisory bookkeeping so recovery works from local evidence alone, while §6 makes the registry the fail-closed authority for post-erasure checkpoint validity — under the imported machine a self-evident checkpoint would remain usable with the registry unreachable. Resolve by importing the sentinel and the intra-state matrix into Acceptance 12, and by stating that checkpoint validity (unlike fork bootability) is registry-authoritative, as a declared deviation from the imported machine.

**C8 — MATERIAL. §8's core provenance rule is violated by its own table.** The rule is "no core component depends on an undecided design decision", yet "Promotion proof domain | focused follow-on Spec | **not yet drafted**" is a core component whose canonical preimage, expected-state derivation, and golden vectors are all undecided; labeling the dependency "named prerequisite" restates the problem rather than satisfying the rule. Resolve by weakening the rule to "no core component depends on a decision owned by a document this RFC does not control," or by moving boundary proof out of core until the Spec exists.

**C9 — MATERIAL. Two different effect taxonomies are conflated.** §1 requires effect classification "per LLP 0066's recommended effect vocabulary … as landed in the branch substrate's closed effect classes". Those are orthogonal axes: `EffectClass` is a six-value *egress family* enum, while 0066's recommended vocabulary is *settlement capability* (`transactional | provider-idempotent | provider-queryable | compensatable | inherently-ambiguous`). §5's promotability and provisional-state rules turn on the latter; §3's `DenyAll` attempt marker records the former. Resolve by naming both axes separately in the envelope's effect facts and saying which one governs promotability.

**C10 — MATERIAL. Preallocated identity-range exhaustion while offline has no disposition.** §1 closes offline minting with a server-preallocated *finite* range persisted before use, but never says what an offline client does when the range is spent. Given the same section's rule that a covered-lane mutation "arriving on that lane without an identity refuses stably", the consequence is that offline write capacity is now capped by a parameter this RFC introduces and does not size — a client-visible behavior change on a lane §Non-goals assigns to LLP 0043/0053/0090 and 0155's client arm. Acceptance 2 covers crash cuts around preallocation and persistence but not exhaustion, and OQ1's window list omits the range size and window entirely. Resolve by naming the exhaustion disposition (stable refusal vs. degraded uncovered queueing), adding it to Acceptance 2, and adding range size/window to OQ1.

**C11 — MATERIAL. Reclamation and the anti-replay floor run at different granularities.** Reclamation is per-receipt on acknowledgement; the floor advances per-epoch on closure. An acknowledged-and-reclaimed identity whose epoch is still open (held by a sibling unacknowledged identity) sits above the floor with no suppression record — indistinguishable from novel, and it re-executes. The document's safety argument (a post-acknowledgement retry is a client-contract violation) is stated only for the *restamp* case, and Acceptance 2's reclamation leg tests only the below-floor path. Resolve by extending the restamp argument explicitly to same-epoch reclaimed identities and adding the at-or-above-floor fixture, or by gating reclamation on epoch closure.

**C12 — MINOR. §6's non-row residual names the wrong residual.** §6 says the non-row rule loads no historical policy version because "a retained policy series is exactly the historical representation this profile's non-goals decline". But 0088's row rule doesn't load historical policy versions either — it evaluates the *current* read policy against each historical post-image. So the named residual (today's policy applied to yesterday's facts) applies identically to row post-images and fork-diff rows, and is not a non-row concession. The actual non-row delta is the absence of the first gate — there is no current record to be "authorized for now." Resolve by restating the residual as the missing current-record gate and saying what stands in for it per fact class.

**C13 — MINOR. Cross-reference and granularity gaps.** (a) The §Acceptance preamble maps "rows 5–10" to the fork and promotion components without carrying §8's carve of the derived-deployment legs of rows 5 and 7 to the additive capability. (b) The as-of revisit trigger lists "fork-at-checkpoint" among the affordances that must fail before reopening P4(c), but §3 makes checkpoint-based forks the derived-deployment class, which §8 puts outside core — so a conforming core target may never have the affordance whose absence is supposed to trigger the revisit. (c) Rows 2 and 10 each bundle ~10 independent properties into one pass/fail gate that blocks a whole component; splitting them would make the tier mapping actionable.
