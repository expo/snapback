## Probe answers

### 1. Was compression “never considered”?

**Mostly true of LLP 0314 and LLP 0314.000; false as a program-wide claim.**

- LLP 0314 mentions compression only as npm tarball / comparables / crates.io’s 10 MB compressed limit, plus F7 “Compression is hiding stringy rodata and symbols” (`llp/0314-shipped-runtime-binary-size.research.md:24`, `:106`, `:120`, `:276–294`). It never proposes compressing the Guide artifact.
- LLP 0314.000 does not contain the word “compress” at all. It never proposes artifact compression.
- LLP 0314.001 **did** consider encoding compression and dismissed it: “Compression of the encoding is a marginal fix” (`llp/0314.001-derived-guide-bytes.rfc.md:134–137`). Its withdrawal then proposed container compression (`:28–35`). That is this RFC’s origin, which §7 admits.

The Summary’s “This was never considered” / “no document proposes compressing the artifact itself” (`llp/0314.002-compress-the-embedded-guide-artifact.rfc.md:35–37`) overreaches. Scope it to 0314 / 0314.000.

I found no LLP 0284 / 0123 / 0061 prohibition on compressing the blob. What exists is a *simplicity* design: a length-prefixed inert decoder (`llp/0284-workspace-security-gate-threat-model.spec.md:620–640`; `crates/snapback-server/src/guide.rs:63–72`). Compression was neglected, then dismissed in the wrong frame, not ruled out.

### 2. Is `contentHash` unaffected?

**Yes, if and only if the decoder hashes decompressed bytes.** The RFC’s domain statement is correct. That is the trap that killed 0314.001, and this document does not repeat it.

Generator (`scripts/guide-lib.mjs:1271–1281`):

```
SHA-256(wholeFlat || "\0guide-resource\0" || "guide/reference/registry.json" || "\0" || registryBytes || "\0guide-resource\0" || "guide/reference/diagnostics-registry.json" || "\0" || diagnosticsBytes)
```

Decoder (`crates/snapback-server/src/guide.rs:174–196`) mirrors that over `flat.bytes`, `registry.bytes`, `diagnostics.bytes`. Labels live in `crates/snapback-server/src/guide_artifact.rs:28–31`. Docs-site re-hashes the same three **source files** (`scripts/generate-docs-site.mjs:868–880`).

`contentHash` is **not** over the packed set and **not** over the artifact bytes. `build.rs` copies the already-computed hex into the artifact header (`crates/snapback-server/build.rs:152–194`) and does not hash payloads. Compressing after that copy cannot change the digest **unless** `file.bytes` fed to `validate_content_hash` are still gzip.

Today they are artifact-resident slices (`guide.rs:123–131`, `:187`). Gzip is not UTF-8, so the current UTF-8 check (`guide.rs:126–128`) would also fail on compressed payloads. The RFC’s invariant — “decoder returns identical bytes”; “compression happens after hashing” (`llp/0314.002:107–120`) — is the right construction. It is not automatic from “we compress in build.rs.”

The same uncompressed-bytes boundary is load-bearing at:

- `crates/snapback-server/src/guide_reference.rs:43–56` (manifest `sha256` of registry / diagnostics bytes)
- `crates/snapback/tests/served_guide_v1.rs:130–133`, `:158–160`, `:294`, `:317`, `:357–379`, `:424–429` (`include_bytes!` of **source** files, not the artifact)

Name that boundary. Do not treat it as “by construction” without saying the decoder must decompress before UTF-8, hashing, and `EmbeddedGuideFile.bytes`.

### 3. Does compression break a consumer?

**Not if the decoder presents today’s uncompressed record bytes.** The “no consumer migration” claim is then true for the surfaces named.

| Surface | What it actually reads | Migration? |
|---|---|---|
| HTTP `/_snapback/guide*` | `guide::file().bytes` vs source `include_bytes!` | No, if bytes are uncompressed |
| `snapback mcp` | Catalog from **manifest** `flatProjections.*.bytes`; listing is `guide::file(path).is_some()` (`crates/snapback-cli/src/guide_mcp.rs:129–132`, `:141–144`, `:208–210`) | No |
| CLI `snapback guide` | UTF-8 of `file.bytes` (`guide_command.rs:53–59`, `:119`) | No |
| `REQUIRED_GUIDE_PATHS` | Path presence (`guide_artifact.rs:17–26`; `guide.rs:158–164`) | No |
| `check-guide` / docs-site | Checkout `guide/` files | No — they never see the artifact |
| served-guide `include_bytes!` tests | Source files, not `embedded-guide.v1.bin` | No |

What **does** change, and is not a “consumer”:

- Artifact **format** (encoder, decoder, `test_artifact` in `guide.rs:322–338`)
- `EmbeddedGuideFile.bytes: &'static [u8]` currently aliases the `include_bytes!` blob (`guide.rs:27–31`, `:123–131`). After gzip those static slices are not UTF-8. The decoder must own/cache decompressed bytes. That is the cache in §6, not a URL/body change.

§5’s “no … migrating the generator, checker, docs-site, MCP, and `include_bytes!` tests that consume the committed files” is right for those files. Do not extend it to the in-crate artifact fixtures.

### 4. Is the size arithmetic right?

**Planning-grade yes for Mach-O file size; I could not re-measure the corpus.**

`include_bytes!` of `OUT_DIR/embedded-guide.v1.bin` (`guide.rs:22–23`) is one rodata blob. On the 0.1.27 Darwin binary LLP 0314 F2 puts `__const` at 38,058,440 bytes and the file at 159,336,256 (`llp/0314-shipped-runtime-binary-size.research.md:131–139`). There is no Mach-O compression of `__const`, and DWARF is already gone. Dropping ~17.2 MB of payload should drop the file and `__const` by ~17.2 MB plus alignment (16 bytes, negligible). `159 − 17.2 ≈ 141.8` matches the RFC’s ~141 MB gzip figure (`llp/0314.002:77–80`).

Caveats, not reversals:

- 20,658,338 is “packed corpus,” not isolated from path/length headers. Headers stay. The win is payload.
- I could not re-run `gzip -9` / `zstd -19`. The five-file raw sizes and the two registry gzip sizes are identical to LLP 0314.001’s 2026-08-27 table and withdrawal (`llp/0314.001:83–86`, `:29–30`). Treat “re-run independently” as unverified here.
- Download analysis is honest: npm tarball is already gzipped; gzip-precompressed payload is roughly tarball-neutral; zstd can save ~2 MB in transit. Do not sell npm install. That part is good.

### 5. Was compression deliberately avoided? Gzip timestamps?

**No explicit ban. The RFC still omits a real encoder constraint.**

LLP 0284 wants an inert length-prefixed blob and fail-closed UTF-8 / digest checks **before exposing any record** (`llp/0284:632–640`). That is a reason the decoder is simple, not a prohibition on a codec under the record boundary.

LLP 0123’s `runtime-qualify` path is Hermes/CV-2, not Guide parse. OQ4 is aimed at the wrong probe; first `LazyLock` Guide access is the real timing (`guide.rs:40–43`).

LLP 0314.000 Phase 2 **does** require a **shared deterministic encoder with two callers** and a compiled-in whole-artifact `artifactSha256` (`llp/0314.000:320–367`). Gzip as *measured* (`gzip -9`) is the CLI, which stamps MTIME. Gzip as *implied crate* (`flate2` 1.1.9) is bit-stable by default: `GzBuilder` mtime `0`, OS byte `255` “to have cross-platform reproducible streams” (`flate2-1.1.9/src/gz/mod.rs:313–320`, `:432–436`; `GzEncoder::new` uses that builder). The RFC never says which, and never requires bit-stability. Two encoder invocations with `gzip(1)` would desynchronize Phase 2’s compiled digest from the sidecar. That is a defective omission, not an implementation nit.

### 6. Are gzip-over-zstd and per-record-over-whole right?

**Per-record: yes. Gzip-first: acceptable sequencing, false rationale.**

**OQ1.** zstd is not in `Cargo.lock`. `flate2` **is**, but only as a transitive dep of `ureq` / `png` — **no workspace `Cargo.toml` names it**, and `crates/allowed-dependencies.v1.json` does not list it. `snapback-server`’s `build.rs` currently uses only std. Using gzip means a new **direct** dep plus a **build-dep**. LLP 0276: confinement is only for axum/rusqlite/clap/ibex/celld-ltx; “Other externals are review-governed, not confinement-gated” (`llp/0276-ideal-codebase-architecture.rfc.md:366–376`). Gzip is cheaper than zstd. It is not “no dependency at all” and not “no policy question” (`llp/0314.002:32–33`, `:135–140`).

**OQ2.** One-page HTTP and MCP-not-returning-bodies are real. Whole-artifact gzip of everything vs per-record gzip of the **top five** (`llp/0314.002:141–144`) is not a size comparison; 1.93 MB for five files vs 3.50 MB for the corpus does not show cross-record redundancy. Per-record is still the right call because after init you can keep ~3.5 MB compressed plus an LRU, while whole-artifact is 20 MB decompressed or decompress-all per request.

OQ2 oversells *laziness*. LLP 0284 requires UTF-8 of **every** Markdown/JSON record before exposing any (`llp/0284:632–634`). Today that is the `LazyLock` parse. MCP listing already forces that parse. First Guide access will decompress the text corpus unless 0284 is amended. Steady-state RSS is where per-record pays; first-access peak is not.

### 7. Does it compose with scope-frozen LLP 0314.000 Phase 2?

**Goals compose; the “indifferent” claim is false.**

Phase 2 moves the **same closed table** to a sidecar, gates `include_bytes!` on the public-package path, and compiles in `artifactSha256` from a **deterministic two-caller encoder** (`llp/0314.000:306–374`). A smaller sidecar is strictly better for disk; Phase 2’s own outcome table even says the unpacked package “barely moves” because the corpus still ships (`llp/0314.000:396–401`, `:471`) — compression is the missing package-byte win.

What is **not** indifferent:

- “The sidecar is the existing closed-table `embedded-guide.v1.bin` format” (`llp/0314.000:307–309`). A record-layout change is a format change. The plan is scope-frozen; this RFC cannot quietly rewrite that pin. Honest composition: this is a breaking container version of the same closed table; Phase 2 ships whatever the shared encoder emits; keep the member path.
- Two-caller `artifactSha256` is over **artifact bytes**, including compressed payloads. Encoding must be bit-stable or compile-time digest ≠ pack-time sidecar.
- Phase 2’s decoder faces an **external** sidecar: tamper, oversized, wrong-revision tests (`llp/0314.000:371–377`). Today `content length` is bounded by remaining artifact bytes (`guide.rs:105–107`, `:123`). An extra **uncompressed** length is not. That is a decompression bomb on the sidecar path. §6’s “no new failure mode that is not a decode error on a corrupt artifact” (`llp/0314.002:190`) is wrong for resource exhaustion.

Carriage (embed vs sidecar) and encoding (raw vs gzip) do compose. The RFC’s composition paragraph does not.

## Concerns

### MATERIAL — §3.1 and §6 — format version contradicts itself and the frozen Phase 2 pin

**Wrong:** “The artifact keeps its `SNAPBACK_EMBEDDED_GUIDE\0\x01` magic and gains a format version whose records carry an encoding tag plus the uncompressed length” (`llp/0314.002:104–106`). Cost says “One format-version bump” (`:187`). `\x01` **is** the version. `guide.rs:20` and `guide.rs:90` treat the whole slice as `magic/version`. Adding an encoding tag and uncompressed length under the same magic is a silent layout break: `test_artifact` (`guide.rs:322–338`) and any `\x01` decoder will misparse.

Phase 2 pins “the existing closed-table `embedded-guide.v1.bin` format” at member path `guide/embedded-guide.v1.bin` (`llp/0314.000:307–309`). That pin is frozen. This RFC cannot both keep `\x01` and change records, and cannot call that “indifferent.”

**Fix:** State a breaking container bump (`\x02`, or a version field that is not `\x01`). Keep the closed-table family and the Phase 2 member path. Say Phase 2 ships this encoder’s output; do not claim the frozen “existing format” sentence is unchanged. Require the stored length to bound the read, the uncompressed length to match decoded output, and a ceiling on uncompressed size so a hostile sidecar cannot OOM (Phase 2 already lists oversized tamper tests; LLP 0284 already has length ceilings).

### MATERIAL — §2, §4 OQ1, §6 — gzip is recommended without a bit-stable encoder, which falsifies Phase 2’s digest design

**Wrong:** gzip “lands with no policy question” / “adds no dependency at all” (`llp/0314.002:32–33`, `:135–140`), and Phase 2’s “bare-binary tuple” is “indifferent to whether a record’s bytes are compressed” (`:95–100`).

Evidence:

- Phase 2 compiles in whole-artifact `artifactSha256` from a **shared deterministic encoder with two callers** (`llp/0314.000:320–367`). Two invocations of a timestamped gzip do not match.
- RFC measurements are `gzip -9` (CLI MTIME). The implied crate, `flate2` 1.1.9, is bit-stable by default (mtime 0, OS 255). The RFC never picks, and never requires bit-stability.
- `flate2` is not a workspace direct dependency (no `Cargo.toml` hit; lockfile only). `build.rs` has no crate deps today (`crates/snapback-server/build.rs:1–7`). Gzip still adds `[dependencies]` and `[build-dependencies]`. LLP 0276 still review-governs that.

**Fix:** Require a bit-stable encoder as a normative constraint: no `gzip(1)` in `build.rs`; mtime/filename/OS fixed; same bytes from both Phase 2 callers. Correct “no dependency.” Gzip-first can stay as sequencing versus zstd; the rationale cannot.
