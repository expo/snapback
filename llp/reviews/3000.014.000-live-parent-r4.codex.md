1. **High — The bulk restore barrier lacks a bounded representation for before-images and final events (§§4.1, 7).**

   The proposed barrier installs endpoint rows, recaptures existing children, validates, then regenerates partition events using the existing collector. That collector retains events for the entire transaction: [`PendingEvents`](/home/ccheever/projects/sb4-w14-live/snapback4/crates/snapback4-core/src/partition/pending.rs:16) owns event images, slots and identity maps; [`partition::append`](/home/ccheever/projects/sb4-w14-live/snapback4/crates/snapback4-core/src/partition.rs:850) additionally constructs a transaction-wide coalescing map. Existing SQLite and Postgres restore paths use unbounded meters and retain the complete event vector.

   **Admitted counterexample:** Restore changed policy inputs for 100,000 parents, each with one live child and `cap 1 by parent`. Every edge satisfies its cap, every individual row fits the byte-admitted walker, and the final image is consistent. Nevertheless, regenerating the child moves retains 100,000 put images and their removal/bookkeeping metadata simultaneously. Page scratch can remain bounded while request heap grows with the entire population. Neither the per-source-write ledger nor activation page admission bounds this special bulk path.

   The barrier must also preserve each row’s original audience before installation overwrites it. Retaining those original boundaries creates another population-sized account that the RFC does not define.

   **Smallest precise repair:** Specify transaction-local database staging keyed by `(table,id)` that preserves the earliest required before-image or before-audience and final affected identity. After validation, enumerate it in byte-admitted pages and append final events with a monotonically continuing event ordinal inside the same transaction. Avoid the whole-request `PendingEvents` and coalescing vectors on this path. Alternatively, impose an explicit total restore reservation and refuse before exceeding it. State the corresponding Postgres mechanism.
