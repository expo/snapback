Inside `routeLocal`, Rule 2 already certified the same answer with the device's transaction watermark via `receiptCurrent` (`local-query.ts:264`). The two checks disagree during every sync round.

**2. Medium — A same-id retry of a journal-owned id is refused as `E_ADMISSION` while device custody is unlisted.**
`snapback4/packages/snapback4/src/progressive-writes.ts:199`.
Returning visit, custody present, journal holds unsent J1 from the last session, engine held or failed, so `deviceKnown` returns undefined. The app retries `app.mutate(op, args, { id: J1 })` (the documented same-id retry). The id is not facade-minted and predates `openedAt`, so the wrapper answers `failed / E_ADMISSION "device write custody has not been listed"`. Meanwhile `start()` replays J1 through the journal and it may become `sent`. The caller holds a `failed` receipt for an executing intent; `E_ADMISSION` means "not admitted, safe to resubmit", so a caller that mints a new id duplicates the write. RFC §7.2 rule 4 says a journal-admitted id settles through the journal's same-id mechanism. On permanent engine failure this lasts the whole session.
Smallest fix: before the refusal, if `this.current().some(w => w.id === options.id) || recorded(options.id)`, route to `journal.mutate`; a journal-known id can never be a device id, so the device-custody guard does not apply.
