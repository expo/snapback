## New MATERIAL findings

1. **Phase 2a's independence-from-Phase-3 rationale is contradicted by Phase 2a's own item 2, and by the dated evidence in the Plan's own baseline.**
   Phase 2a's preamble justifies landing before Phase 3 on a specific factual claim: "the lowest-risk shape first: one fork at a time, one owner, no concurrent contention. This slice does not need Phase 3's parallel-isolation, credential-matrix, or resource-limit evidence — F0a/F0b's single-fork guarantees already cover it." Its exit repeats "single-fork and single-owner".
   Item 2 of the same phase is "a fork-per-worktree helper with deterministic ownership metadata, **collision-free ports**, environment export, status discovery, and cleanup tied to an exact worktree". Fork-per-worktree is by construction a multi-fork, concurrently-running shape — that is what worktrees are for — and "collision-free ports" is a requirement that only exists because two forks run at once. A single developer with three worktrees satisfies "one owner" and violates "one fork at a time" and "no concurrent contention" simultaneously. The seam the revision drew is *multi-owner vs single-owner*, but the rationale it wrote is *concurrent vs non-concurrent*, and item 2 sits on the wrong side of the second one.
   This is not hypothetical: the Plan's own baseline bullet is "dated fleet evidence for **two simultaneous** function-divergent worktrees", and `tests/acceptance/instance-fork-fleet-dogfood.2026-08-03.v1.json` records two concurrent sessions with `sessionAWritesAbsentFromSessionB` — and records that session-b was `"disposedBy": "fork.drop after the first reap attempt exposed a teardown race"`. A teardown race is precisely Phase 3 item 5's subject matter ("create/drop/reap races, duplicate cleanup, process-exit boundaries"). So the single dated run of the exact workflow Phase 2a item 2 productizes already hit a defect class Phase 2a declares it does not need Phase 3 evidence for.
   Fix is a placement decision, not a redesign: either (a) keep item 2 in 2a but narrow it to one live fork at a time and move concurrent multi-worktree use into 2b, or (b) move item 2 to 2b and leave 2a as the harness slice (item 1) plus templates (item 3), which is the genuinely single-fork, single-owner core and is what closes the guide-gap ticket. Whichever is chosen, delete "no concurrent contention" or delete "collision-free ports" — the two cannot both stand.

2. **Phase 2b's exit attributes port evidence to Phase 3, and Phase 3 has no port item — the round-1 defect survives in the reworded exit for one of its four clauses.**
   Phase 2b's exit: "parallel consumers cannot trample data, ports, credentials, or cleanup ownership — **because Phase 3 already proved it**, not because this phase asserts it." Three of the four clauses now land: data → Phase 3 item 1, credentials → item 2, cleanup ownership → item 5. Ports land nowhere. Phase 3's nine items cover write isolation, credentials, egress families, the future-family rule, lifecycle races, renewal, byte/count/diff limits, disk pressure, and OS-isolation guidance — none of them allocate, bind, or contend for a port. The only port language in the whole Plan is Phase 2a item 2's "collision-free ports", which is a helper *feature*, not evidence, and which Phase 2a's own framing guarantees is never exercised under contention (see MATERIAL 1).
   This is verifiable in code as a real surface, not a wording nit: `ForkCommand::Create` takes no port argument (`src/cli.rs:1234`ff), so port assignment happens wherever the fork's server is started — i.e. exactly in the helper layer Phase 2a/2b build, with no substrate-level guarantee behind it. Either add a port-allocation/contention item to Phase 3 (alongside item 5's race corpus, where it naturally belongs), or drop "ports" from the 2b exit and assign it explicitly to 2a item 2 as a helper obligation with its own test. As written the exit is unsatisfiable by the phase it names.

## New DETAIL findings

1. **Phase 1 item 1's "boot-time/periodic sweep" has no named carrier, and the residual case is the one the invariant exists for.** Create-time reap-or-refuse bounds a *growing* fleet, and boot-time sweep bounds a *restarting* one, but a machine where nobody creates a fork and nobody restarts a server keeps expired forks — servers still running, copied data still on disk — indefinitely. There is no daemon in `src/` that could run the "periodic" half. The genuinely self-enforcing form is a fork server that refuses to serve past its own recorded expiry; consider naming that, or say plainly that enforcement is event-driven and bounded by create/boot events.
2. **Phase 2b item 3 conflates two different recovery mechanisms.** "leave either recoverable finite-TTL forks (recoverable via Phase 1's automatic reap and recovery verb, not manual sweep) or fully cleaned state" — `recover()` repairs a *quarantined incomplete publication cut*; reap *deletes an expired* fork. A killed test runner most often leaves a fully published, unexpired, orphaned fork, which is neither. Name the third disposition (ownership-metadata-driven cleanup, from item 1) rather than folding it into the other two.
3. **Phase 7 widens LLP 0158 OQ6's decided surface disposition without naming it.** OQ6 is DECIDED (2026-08-03): "CLI-only. The source `snapback fork` verb emits the LLP 0024 host-operation/ready envelopes; no handler or public app API may fork." Phase 7 projects create/inspect/diff/renew/drop/reap as typed control-plane operations. That is defensible (OQ6's decision is scoped "for local v1 F0b", and a control surface is not a handler or app API), but a Plan this scrupulous about "requests it from that owner instead of deciding unilaterally" should name OQ6 in Phase 7 and route the widening to 0158 rather than leaving it implicit.
