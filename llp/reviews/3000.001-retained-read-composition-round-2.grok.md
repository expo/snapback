## Overall assessment

The eight round-1 findings are addressed in product code. Composition now copies every second-local field that would not route to the server; entry still requires a retained component plus a server-needing component; found point hits mark only the frame; reading guards and escaped nested names have no plan; meter cuts are mirrored at the charge, the observing read, and a flip during a component. Tables equality does include rules, sync, and leave policy, so a rule change still drops images.

Two leftovers keep this from READY. LLP 3000.007 §18.2’s “lane MQ implementation” paragraph still states the round-1 contract (“composes retained components”). The fix-round `keep_images` predicate is broader than “program-only”: any generation whose `tables` and `maintains` match keeps delivered-history images, including an identity-mode change that at `b5a7ddde3` would have wiped them. `trust_synced_read` will then serve those rows to a later principal on the same store.

An all-held query (no retained component) keeping the whole, fresh server answer is the right design: composing two locally truncated held pages would be a worse snapshot than one server transaction. A declared `held` query also stays local, which is correct.

## Scope expansion 2(a) — `keep_images`

`open_store` 267–280 and `adopt_captured` 377–393 keep images and `GROUPS` when `tables` and `maintains` are equal **or** `keeps_literal_default_images`. `keep_acquired` is still the old narrower predicate (same table count **and** a literal-default addition **and** already acquired), so a program-only generation still clears `ACQUIRED`, resets the watermark, invalidates native, clears `STAGED_GROUPS`, and refuses synced reads with `E_PREDICT` until a snapshot finishes (209–221, 652–654; test 114–116).

`Table` derives `PartialEq` and includes `rules`, `sync`, `leave`, `expire`, indexes, constraints, columns, defaults, residency (`schema.rs` 212–236). `Maintain` includes filter, computed keys, source, `by`, target, and `readable` (669–682). A rule, sync, or leave change still drops images. Literal-default adoption is unchanged.

Sound for the intended program-only case:

| Concern | What happens |
|---|---|
| Confirmed images under predictions | `install(..., reset && !keep_images)` so `_device_base` is not deleted (`store/activation.rs` 40). `predictions::restore` then `replay` after the replacement snapshot (`device.rs` 541, 615; `predictions.rs` 57–93). Missing/changed programs skip or withdraw the prediction; they do not invent ids. |
| Staged snapshot / `STAGED_GROUPS` | Always `{}` on generation reset (278, 390). `snapshot_owner = None` (407). A continuation page cannot finish another snapshot (517–518). The next first snapshot page `staged_clear`s (510). |
| Maintained values | `maintains` must be equal, so the derived shape is the same; values are replaced with held groups on snapshot. |
| Memory schema-hash re-projection | `Schema::hash` digests the whole schema, including `operations` (`schema.rs` 22–47, 141–143). A program-only change re-projects; `project` only drops unknown columns and keeps `pending` (`memory.rs` 194–254). Same tables ⇒ no-op on images, indexes rebuilt. |
| Outbox | Never cleared on generation reset (same as before). Replay uses the **new** programs on the kept confirmed base. |
| Native | `invalidate_native` on every generation reset (276, 388); in-memory module dropped (394–399). |
| Store identity | Replacement still `observe()`-resets rows, base, staged, `GROUPS`, and `ACQUIRED` (`store_identity.rs` 77–85) **before** adopt. `backend_identity` includes schema, programs, and generation (17–21). |
| Replacement snapshot held vs left | `snapshot::retain` still stages delivered-history rows as not acquired and keeps groups the new audience does not hold (`snapshot.rs` 12–64; publish 553). Left history can survive; held groups are replaced. |

**New problem:** `Schema.auth` (and effects, schedules, routes, unique-refusals) are **not** in the predicate. `trust_synced_read` skips live read rules for `delivered-history` (`read.rs` 232–238). See finding below.

## Scope expansion 2(b) — `incarnation++` on adopt

`incarnation` is the client’s fence for store/backend identity (`local.ts` 310, 331–347, 639–640). It gates: `refreshAcquired` (320–322); each sync page (552, 576, 591); backend reload (630–635); `apply` (655–657); `/probe` going online (700–708); `/changes` (729–738); `runLocal` retry (790–792); accepting a server POST (820); composing after the second local (880); watch publish (929–932); `query()` return (1079–1081); new watches snapshot the current value (1088).

The outbox sender (`flushOnce` 991–1053), `mutate` (1118+), and `asset` / `assetSource` (1188–1206) do **not** read `incarnation`. They never did. Client-minted write ids still dedupe. This bump does not strand or duplicate sends.

It does not cause a rerun storm: `runLocal` retries until the revision matches; a running watch sets `dirty` and reruns once (921–943); `adoptedGeneration` already reruns every watch (681–682). In-flight `/q/*` after adopt hit 820 and become `{loading: true}`, then retry — that is the epoch-1 fix (`MQ adoption` 316–319). Same-store adopt does **not** go through `observeIncarnation`, so existing watch snapshots are not cleared to `loading` first; they stay on the previous generation until that rerun finishes. That is the same stale-until-rerun pattern as ordinary invalidation, not a new strand.

## Findings

### 1 — Medium — `llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:1844` and `snapback4/crates/snapback4-device/src/device.rs:377`

**`keep_images` keeps delivered-history rows across any tables/maintains-equal generation, including identity-mode changes that used to wipe the store.**

Scenario: device store holds guest G’s left-group messages (`retain delivered-history`). App ships `use identity password` (or drops guests) without touching tables or maintains; generation bumps. Adopt keeps images and `GROUPS`. G signs in as password principal P on the same store. Snapshot marks G’s rooms left (not in P’s audience) and **keeps** those rows (`snapshot.rs` 55–58). P’s `messages[leftRoom]` is trusted on the device (`read.rs` 252–253) and returns G’s history. At `b5a7ddde3` this generation change dropped every row.

Smallest fix: keep images only when `tables`, `maintains`, **and** `auth` match (or the existing literal-default helper). Optionally require `schema` equality except `operations`.

### 2 — Low — `llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:1844`

**The §18.2 implementation paragraph still describes round-1 composition.**

It says the client “composes retained components from a second local evaluation with the other fields from the original query's one server answer.” Implemented behavior, README 1159–1160, and the sync card 127–128 copy **every** locally kept component (`!wantsServer`), including a complete until-revoked field. A three-field `{left, held, current}` after `delete current` would be documented as taking `current` from the server (resurrected row) and implemented as taking it from the second local (empty).

Smallest fix: replace that sentence with the card/README wording (“every component that would stay local as its own query”).

### 3 — Low — `llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:1974` (§18.3)

**§18.3 is still true** (literal-default addition does not rewrite stored rows; hosts materialize the default). It does not mention the new keep-images case. Readers of 18.3 alone will still think “generation change drops rows unless a literal default was added.”

Smallest fix: one sentence in **§18.2** (not 18.3): a generation whose tables and maintains (and, if finding 1 is taken, auth) are unchanged keeps acquired images and left-group metadata, and still re-acquires.

## Questions

- Should `keep_images` also require equal `effects` / `schedules` / `routes`, or is operations-only the only generation the author wants to keep? Auth is the only mismatch I can turn into a concrete cross-viewer leak.
- IndexedDB composition in `witness/idb.mjs` 139–178 was not run (Chromium SIGABRT). That is remaining lead qualification, not a logic defect in the script.

## Did a fix introduce a new problem?

Yes. At `b5a7ddde3`, images survived a generation change only via `keeps_literal_default_images`. At IMPL_COMMIT, identical `tables`+`maintains` also keep every delivered-history row and the held/left map (`device.rs` 377–389). That is what makes program-only adoption preserve left history (intended) and what lets an identity-mode generation leave another principal’s retained rows readable (finding 1). The `incarnation++` on adopt is not a durability or safety regression: it only invalidates in-flight reads and remembered server answers.

## Regression tests that would also pass without the change they claim to test

- **`completeOnly` in `retained-history.test.mjs` 224–226.** It only checks that a query with no retained component does not enter composition (`fresh: true`). Reverting the copy-all-kept-fields change (886–888 back to copying only `c.retained`) still passes this assertion. The tests that actually fail without that fix are `MQ delete current` and `MQ revoke current` (351). `completeOnly` is a valid entry control; it should not be counted as coverage of finding 1.
- **Positive controls** (`require true` still has a plan, independent inline scans still have two fields, nested `leak` before `z: leak` still has a plan). They are meant to pass without the new negatives. The negatives themselves fail without the binder fixes (journal red-before). Not vacuous.
- **Named corpus participation** (`tests/components.rs` 153, 175) would pass at `b5a7ddde3` without the fix-round binder/runtime patches; it asserts the file is planned, and the differential then runs. It is not a false pass of an empty plan.

Cap, point, reading-guard, nested-leak, adoption, and delayed-delete/revoke tests would fail if their product change were reverted.

Documentation: README 1153–1167 and `guide/sync.rs` 121–135 state one read per field, no reading `require`, found point composition, entry needing a retained component, the pending-write exception (`local.ts` 870, 873, 881), second-local kept fields, completeness conjunction, `fresh: false`, no `since`, no continuation. LLP 3000.007 §18.3 remains true for literal defaults; it needs no correction, only a pointer in §18.2 to the new keep-images case.

Verdict: READY WITH CHANGES
