## What to judge, in priority order

1. **Does the feature work end to end?** A builder writes the `ephemeral`
   card's typing table and operations; peers on the local-first web tier see
   typing within 2 s of a 25 ms-delay keystroke burst and see it disappear
   within 5 s of the last keystroke. Run the end-to-end test
   (`packages/snapback4/test/ephemeral-e2e.test.mjs`) and read its numbers.
   Look for a step that silently does nothing (a poll that never re-issues,
   an interest set that is never sent, a watch that never re-runs).
2. **Durable behavior is unchanged.** A schema with no ephemeral table must
   serialize, emit and behave on the wire exactly as at the base. Any
   changed expectation in an existing test is suspect — find each and judge
   it.
3. **Authorization and disclosure** under Snapback 4's laws (rules,
   `NOT_FOUND` vs `E_RULE`, the meter, hidden rows): the renewal law, the
   exhaustive classifier + runtime boundary, `$deadline` never on the wire,
   declared-size capacity (no private-payload oracle), no rule probes of
   ephemeral tables, the generation fence.
4. **Concurrency:** the lock order (engine → hub → wake), wake publication
   under the hub lock, lost wakeups, the drop-guard undo, the ephemeral
   request revision and `(incarnation, epoch)` fencing on the client, the
   ordered client lane, `renews` coalescing and the renewal window.
5. **Bounds:** per-principal and global capacity, the per-session rate
   bucket, 100 ms pacing, the 256-call lane bound, no unbounded work per
   write or per poll.
6. **Tests that would pass without the feature working** — e.g. a latency
   test that cannot fail, an assertion on a code without the effect, a test
   skipped silently. Mutation-test the key guards where cheap (revert a
   guard, run the one test, confirm it fails).
7. **Docs:** the `ephemeral` card is correct, compiles, and teaches the
   separate chats-list query, the membership conjunct and `.run`.
