## MATERIAL

1. **Relative-origin admission is not the allowlisted relay.** `canonicalSupervisedRelayBase` accepts any path-absolute string that starts with `/`, is not `/`, has no trailing `/`, and survives `new URL(value, 'http://snapback-supervised-relay.invalid')` with `pathname === value` (`packages/snapback-client/app-client.mjs:134-148`). That is then enough, when `source === 'supervised-dev'` and `routing === 'loopback'`, to pass `validateBinding` (`app-client.mjs:234-272`) and become `new SnapbackClient(origin)` (`app-client.mjs:664`), which does `fetch(\`${baseUrl}${path}\`)` (`packages/snapback-client/index.mjs:5507`).

   Empirically admitted: `/__snapback` (intended), `/_snapback/admin`, `/admin`, `/@fs/etc/passwd`, `/%2e%2e%2fadmin`, `/__snapback%2f..%2fadmin`, `/http://evil.com`. Empirically rejected: `//evil.com`, `///evil.com`, `/\evil.com`, `/../x`, trailing `/`, query, hash. Release cannot use this branch (`supervisedRelayBase` is forced `null` unless `source === 'supervised-dev'`).

   **Failure:** a supervised binding with `origin: '/_snapback'` (the one-character lookalike LLP 0030 `#proxy-surface` warns about) is admitted and sends session/password traffic, including the bearer after signup, to `/_snapback/auth/session` on the page origin. On default Vite that 404s; if the SPA is ever same-origin with Snapback, those requests hit the reserved admin/control namespace. `/@fs/...` is likewise admitted as a transport base on the Vite origin.

   The `@ref LLP 0030#generated-app-facts` comment (`app-client.mjs:236-238`) says the starter keeps transport on “the stable relative allowlisted relay.” The code does not check `/__snapback` or `/__exact/snapback`. `routing === 'loopback'` is a caller-supplied label, not a host check. The only new test is the happy path (`app-client.test.mjs:302-318`). Protocol-relative host escape is blocked; the defect is an over-wide same-origin path allowlist on freshly-reviewed admission.

2. **Template live acceptances do not cover the auth journey.** React `acceptance.mjs` still expects only `managed-lifecycle`, `artifact-identity`, `query`, `mutation-and-observation` (`packages/snapback-cli/templates/react/acceptance.mjs:22-27`) and drives `new SnapbackClient(ready.serverUrl, { adminToken, custody: 'anonymous-public' })` plus `createSnapbackReactProvider` (`acceptance.mjs:160-182`) — not `createSnapbackAppClient`, not `useSnapbackAuth`, not signup/signin/sign-out. Expo-chat `acceptance.mjs` still uses `createExternalSessionClient` and `snapback session mint` (`packages/snapback-cli/templates/expo-chat/acceptance.mjs:15-19, 111-145`) and the pre-auth check list (`acceptance.mjs:32-42`). Auth coverage is static greps only (`acceptance.static.mjs` in both templates).

   **Failure:** `bun run prove` stays green if `createSnapbackAppClient` rejects `/__snapback`, if `signUpWithPassword` throws, if recovery codes never appear, or if Expo web never reaches anonymous `ready`. That is exactly the “static coherence vs journey” hole the Phase 3 remainders ticket called out. The start packets still say prove is the done-oracle for these starters.

## MINOR

3. **Guide overclaims binding fail-closed on the bootstrap capability.** `guide/auth/passwords.md:122-123` says generation and binding admission fail closed if the required capability or target offer does not match. `createSnapbackAppClient` only intersects `password-v1` with offered `auth.passwords` (`app-client.mjs:288-301`). It never requires offered `auth.application-bootstrap.v1`. That id is the Expo provider opt-in (`packages/snapback-expo/provider.mjs:80-87`), not an app-client binding check. A hand-built binding that offers only `auth.passwords` still boots (as the package tests do).

4. **First-read safety-fact lists were not extended.** React/expo-chat `AGENTS.md` now state ready-is-not-sign-in and recovery-shown-once, but `guide/start/first-read-profiles.json` `requiredSafetyFacts` still omit those traps (`first-read-profiles.json:24-30, 57-64`). A first-read checker that only scores the listed facts will not notice the new ones disappearing from the packet.

5. **Expo-chat still spoofs `senderId` after first-party sign-in.** `ApplicationAuth` and `TestPersonaProvider` sit side by side (`packages/snapback-cli/templates/expo-chat/App.tsx:177-184`). You can be `authenticated` as user A and still send as seeded persona B. The start packet warns this is demo-only; after adding a real password journey it is easier to misread as authorized identity.

No sessions program ⇒ no fact ⇒ no capability (`application-auth-bootstrap.test.mjs:189-193`). `SnapbackExpoProvider` still requires **both** fact and capability (`provider.mjs:80-87`; LLP 0181 amendment). Unregenerated descriptors stay on the 0181 legacy path. Regeneration is the admitted flip.

Adding the capability string to `capabilities.required` rotates descriptor identity (JCS digest includes that array) and is why the templates grew new content-addressed descriptor/binding files.
