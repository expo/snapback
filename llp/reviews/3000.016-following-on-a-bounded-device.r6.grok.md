## 1. Revision 2's objections

Grok's scenario A and Astra's N=1 case are answered. Grok's removal half of scenario B is not.

**Grok A, answered.** Posts horizon 2: originals at t=1 and t=2, and a repost of the newer one at t=3. A count floor on `@T@Posts` keeps the repost event and the t=2 event, so the t=1 post is held and its event is not. Here the posts floor holds both originals. Option 1 copies each held post's event. Option 2 keeps original events with `at >= 1`, and the t=1 event's `at` is the post's `at` (`timeline_apply` copies the mapped time). The repost event is the other kind, so it does not consume the original's slot. Reposting the t=1 post reads `posts` by id (hit) and `byActorPost` (hit). It must not queue for a missing original event.

**Astra finding 2, answered.** Posts N=1, original P at t=10, a repost event at t=20. P is the posts floor. P's event has `at = 10`, so both mechanisms hold it. The repost event is held because its own repost row is held, not because it won an event-count slot. Reposting P still requires the live original row; a reply or an already-removed original still has no row. That is the check Astra required, and it no longer depends on an event horizon with the same N.

**Grok B, only the "never admitted" half.** A reply inside the posts floor never inserts an event (`filter.matches` returns before `insert`). There is no row to miss. With no horizon on `@T@Posts`, `get_inner` returns a known null and the repost refuses `FEED_POST_NOT_FOUND` instead of queuing. Probe: hold the reply, repost it, and require that refusal on the device.

Removal is not that case. The post row stays (`delete` is denied); `timeline_remove` deletes the event. A known null refuses only if the device has actually dropped the event. Section 2.1a never says that. Probe: acquire P and its event, remove P on the server, sync, repost P. Full sync refuses. A device that still has the event predicts. Details under finding 1.

## 2. Are the §2.1a claims true of the code?

**Existence invariants: yes.** An original event is inserted only when the post is new, not removed, and passes the filter, with the post's id, author, and mapped time. Removal deletes that `byActorPost` row (`repost = false`) and leaves repost events in place. A repost event is minted (`context.mint`), keyed by `(actor, postId, true)`, and its `at` is the repost's time. It is inserted only after the original event is found; a miss refuses `FEED_POST_NOT_FOUND` and rolls the repost back. Deleting the repost removes that event if present. "Exists exactly while the repost row exists" matches the committed states.

**"Nothing else on a device reads owned events": no.** The paved read does not. `timeline::read` uses `@T@Feed`, `@T@Edges`, and `@T@RemovedEvents` only. `byActorTime` walks and delivery's `byId` get run in `timeline_follow` and `run_timeline_chunk`, which are server paths; a device follow returns `Prediction` before `timeline_apply`. But `@T@Posts` is an ordinary public table. `eventCoverage` in `snapback4-device/tests/timeline/round2.rs` already point-reads and scans `feedPosts`. Nothing in bind rejects that. Finding 4.

**The three lookups are decidable only while `@T@Posts` has no horizon and absence is real.** The control flow is as written:

- Repost insert reads the post by id first. A horizon miss or an `online only` read sets `beyond_horizon`, and `timeline_known` queues before `byActorPost`.
- Removal and unrepost go through `fetch` of the source row. An unheld id takes `write_miss` and queues before the transition.
- `byActorPost` is `(actorId, postId, repost)`. It has no time column, so a horizon on that index cannot mean "newest."

`get_inner` does not consult the source row. A miss is unknown only when `sync.horizon` is set; otherwise it is a known null. The sentence "the engine decides these three reads from the held source row" is not what the engine does. It is true only if the table stays horizonless and the device's event set matches the server for every held source. Setting `sync.horizon` to drive `snapshot_page` brings scenario B back, including for a reply.

**Containment: the one-shot inclusion claim is true; the lookup claim is not.** For a live event, `event.at` equals the source's mapped time, and that column is immutable.

- Option 1 holds the event because it holds the source.
- Option 2 holds it because a held source's time is at or above the floor's oldest time. `boundary.accept` keeps keys `>=` the floor key, so every held source has time `>= T`. Inclusive time comparison also keeps other events at exactly T. That is the "few more," and it is harmless: those sources are not held, so the write queues on the source read.

Original event id equals the post id. A repost event id does not equal the repost id. Option 1 has to find the repost event by `(actorId, postId, true)`. A same-id join drops every repost event. Do not implement option 2 with `accept`'s full-key compare either: the repost's minted id has independent entropy and can sort below the floor repost's id at the same timestamp, so the source is held and the event is dropped.

`snapshot_page` is not one server state. Each page is its own transaction, and the watermark log is what closes the gap. Queries wait until `ACQUIRED` is set, so the gap is not served. After catch-up, inclusion holds if event log entries are applied with that same filter. A stale copy of a deleted event still satisfies "every live event of a held source is held." It fails the lookup sentence. Finding 1.

## 3. The follows relaxation

For the view, the claim is true. The lowered page is the inbox scan plus `exists @T@Edges[readerId = viewer, actorId = .actorId, epoch = .epoch]` and `not exists @T@RemovedEvents`. It never names the application's follows table. Edge writes return `Prediction` before `timeline_follow`. The follower walk that does read follows is `timeline_work` on the server.

No new disclosure, if the table stays public. A horizon or `online only` changes what a device holds. The server still stores every follow and still authorizes the public read. `@T@Edges` stays private to the reader. Delivery does not change: the server walks the follower index under system authority, and `online only` does not delete server rows.

Adoption is the ordinary generation reset. `old.sync != new.sync` is `RuleChange`, `keeps_literal_default_images` fails, and the device drops the partition and re-snapshots. `same_declaration` ignores source sync, so server event ids, edge epochs, and work survive. The view's server state is unaffected.

`sync to .<follower>` is not part of that story. Finding 2.

## 4. What an implementer will build wrong

**High — §2.1a. The acquisition rules keep a deleted event, and the lookup rules require it to be gone.**

"Holds the event of every held source" is one direction, and both mechanisms can meet it. "Neither evicts" plus "a new source row's event arrives with it" is an append set. Removal is not a new source row. It updates the post and deletes the event in the same commit (`row_changed` logs the post, then `timeline_remove` logs the delete). Unrepost deletes both the repost and its event.

`boundary.accept` drops below-floor puts and applies every `del`. A derived copy that never subscribes to those deletes, or that treats "do not evict" as "do not delete," keeps the old event.

Probe. Acquire P and its event. Remove P. Sync. Repost P. The device finds `byActorPost` and predicts; the server refuses `FEED_POST_NOT_FOUND`. Second probe: acquire a repost and its event, unrepost on the server, sync, repost again. The repost row is gone, so the insert's pair check passes, and the stale `(actor, post, true)` event fails the unique check. Full sync predicts. Section 5's "removed post" bullet can be passed by removing before the snapshot, so it does not catch this.

Smallest change. For a held source, the device holds that event if and only if it exists. Apply the event's `del` in the same commit as the source update or source delete. "Does not evict" means do not drop a live event to keep a count of N. Leave `@T@Posts.sync.horizon` empty so `get_inner` keeps treating a miss as absence. Add the post-acquisition removal probe to §5.

**Medium — §2.1. `sync to .<follower>` is not a residency of a public table.**

`bind_sync` requires the sync audience to equal the audience implied by the read rule. A public read infers `Audience::Public`. `sync to .followerId` is `Audience::Column` and is refused with "the sync audience disagrees with the read rule." What a public follows table can be is `sync public`, `sync public last N`, or `online only`.

Probe. Keep `public` and write `sync to .followerId`. Bind fails before timeline admission. Forcing the column audience means changing the read rule to `.followerId = viewer`, which changes who may read follows. That contradicts the "public" cell and §3's "never who may read it."

Smallest change. Delete `sync to .<follower>` from the §2.1 list.

**Medium — §2.3. One `byActorPost` input is two reads, and an own-post insert is neither of them.**

`Timeline::inputs` returns a single `(Posts, byActorPost)` for every post and repost write. `kind` is ignored. Repost insert reads the original event, whose source is posts. Unrepost reads the repost event, whose source is reposts. An own-post insert does not read `byActorPost` at all; it writes a new event. Tombstone reads stay on `@T@RemovedEvents`, which remains fully synced.

Probe. Horizon on posts, full sync on reposts. `check` on an ordinary post insert must stay `predicts: eligible` with no event horizon site. Classifying that input with the posts class says the insert may queue past the horizon. It does not: a plain insert is not `inserts::blocked`, and the transition does not read the old event. The other split: posts fully synced, reposts horizoned, so unrepost's event is always held, while repost insert's event follows posts. One site cannot be both.

Do not implement the class by setting a horizon on `@T@Posts`. `site()` would then report Horizon, and `get_inner` would make the miss unknown.

Smallest change. In `write_site`, attach `byActorPost` only to removal, repost insert, and unrepost. Removal and repost insert take the posts class. Unrepost takes the reposts class. An own-post insert has no event site.

**Medium — §2.1a. A partial, horizonless `@T@Posts` is a complete table to every other read.**

`get_inner` and the scan-coverage check mark unknown only when `sync.horizon` is set or sync is absent. The compiler also skips the "no horizon" note for tables a timeline owns. So `feedPosts first 100 by byId`, which `eventCoverage` already compiles, returns the acquired subset with `complete: true`.

Probe. Posts horizon N=1, one acquired original event, then that query. The page must not be a complete answer. The Following page is unaffected; this is every other read.

Smallest change. Say the three transition lookups are the only device reads that may treat a missing event as absent. Any other device read of `@T@Posts` is unknown unless that kind is fully synced.

What is not a defect:

- Live inserts are specified, and the log order matches them. `row_changed` records the source put before `timeline_transition` inserts the event. A backdated row below the floor is not held: `accept` rejects `key < floor`. "Newer row synced since" means at or above that fixed key, which §2.1 already says.
- Event adoption does not need a new successor bit. A source sync change fails `keeps_literal_default_images`, bumps the generation, and the device wipes and re-snapshots. The new snapshot has to use the same §2.1a rule. `same_declaration` correctly leaves server event ids in place. The failure mode is the stale event in finding 1, not a missed generation.
- The restated 5× bar is the right denominator. It still counts events, the table that dominated lane U, and it drops only non-view tables such as profiles. Tombstones stay full and the fixture calls them small. Work and edges sync to the viewer, not the corpus. This is a measurement bar, not a hole.
