## Round 1 — 2026-09-07 (verbatim)

### 1. Overall Directional and Implementation Readiness Assessment

* **Directional Assessment: CHANGE.** The diagnosis of the existing prototype is accurate: hook-owned mutation dismissals using a local `retired` Set (`react-core.tsx:278–286`) are an anti-pattern that causes race conditions, StrictMode double-invocations, and divergences between headless and React runtimes. Elevating retirement to a pure read-model projection while preserving explicit durable dismissal (`§10`) is essential. However, the proposed remedy—introducing a fluent `collection()` DSL (`§8`) and a secondary `client.observeCollection()` subscription pipeline (`§7, §9`)—is an over-engineered abstraction. To eliminate roughly 10 lines of straightforward presentation mapping in `Thread.tsx` (lines 21–27), the proposal adds a mini-relational join engine to the client bundle, risking bundle ceilings and introducing new synchronization seams.
* **Implementation Readiness: REVISE.** Implementation should not start now. Beyond the author's own requirement to await Claude’s baseline landing of LLP 1018.003 and LLP 1018.000 §4 (`client-observed.ts`), the proposal acknowledges a critical runtime gap: the runtime currently lacks an authoritative arrival/supersession proof for unpredicted edits and updates (`§10`). Furthermore, the design has not been audited against the strict 66,000 gzip byte local-runtime ceiling (`rules/NOT-DOING.md:164–170`).

### 2. What to Keep

* **Read-Model Retirement vs. Durable Dismissal (`§10`):** Removing the `useEffect`/`Set` dismissal hack in `useOutboxState` (`react-core.tsx:278–286`) is completely correct. The UI must stop displaying completed actions based on read-model evidence without issuing silent, side-effecting `dismiss()` writes.
* **Preservation of Named-Query Truth (`§7`):** Maintaining the raw query's orthogonal axes (`receipt`, `freshness`, `local`, `refusal`, `status`, `reason`) ensures that collection-level projections never mask underlying query denials, transport stalls, or partial receipts.
* **Stable Key Continuity (`§7, §9`):** Binding unpredicted submitted drafts to their pre-allocated first pinned ID (`intent.ids[0]`, `outbox.ts:330`) preserves DOM node continuity as an item transitions from draft to predicted overlay to authoritative server row (`Thread.tsx:26–27`).
* **Shared Outbox Read Observer (`§10`):** Exposing `client.outbox.observe()` to provide an immutable, session-shared stream of outbox entries replaces redundant per-hook polls (`react-core.tsx:292`).

### 3. Ranked Concerns

#### Concern 1: Unpredicted Updates and Deletes Lack Arrival Evidence (The Admitted Design Risk)
* **Severity:** High / Blocker.
* **Failure Scenario:** `range-store.ts:1139–1142` sets `entry.arrived = true` only when a delivery row matches `entry.ids.includes(row.id)`. In `deliveries.q:27–35`, `edit` and `unsend` mutate or delete rows in place and return `null` without minting new IDs. If an edit was unpredicted (e.g., past the fence, missing local program, or uncovered read; `outbox.ts:336–354`), no overlay exists in `state.overlay` (`range-store.ts:987–997`). When that edit commits on the server, `entry.arrived` is never set. Under `§10`, the collection has no mechanism to determine whether a readable row reflects the post-commit state or a pre-commit stale view, causing unpredicted edits to hang indefinitely in `item.pending`.
* **Smallest Resolution:** Defer attaching unpredicted updates/removals to collection items. Confine unpredicted edits to the general outbox display (`useOutbox`) until the server/range-store protocol provides commit-sequence watermarks or read-version tracking for in-place modifications.

#### Concern 2: Violation of Gzip and Apparatus Budgets
* **Severity:** High.
* **Complexity Cost:** `rules/RULES.md:12–24` and `rules/NOT-DOING.md:78–87, 164–170` enforce strict size caps (66,000 bytes gzip for the complete local runtime; 64,000 target). LLP 1018.003 §6 already warns that headroom is roughly 1,500 bytes. Adding a fluent builder (`collection().create().update().remove()`), descriptor registry, `observeCollection` lifecycle management, index cache, and draft item synthesis will exceed this remaining margin.
* **Smallest Resolution:** Eliminate `collection()` and `observeCollection()`. Keep `client.observe()` as the sole subscription mechanism and implement item derivation as a pure, tree-shakeable selector function.

#### Concern 3: Brittle Coupling to Mutation AST Layout via `intent.ids[0]`
* **Severity:** Medium.
* **Failure Scenario:** The binding in `§8` relies on `key: intent => intent.ids[0]`. In `deliveries.q:13–15`, `post` inserts `messages` first. If a developer alters the mutation to insert an audit log, notification, or join record before `messages`, `intent.ids[0]` will bind to the auxiliary row while the query returns the message row (`intent.ids[1]`). The draft item and authoritative item will have mismatched keys, breaking element continuity and remounting the UI bubble.
* **Smallest Resolution:** Require the mutation or schema compiler to expose designated ID bindings, or key unpredicted drafts by `intent.intent` until confirmed by `local.predicted` row attribution.

#### Concern 4: Notification Skew and Torn Frames in Dual Observers
* **Severity:** Medium.
* **Failure Scenario:** `§9` specifies that `observeCollection` derives from query entries and indexed outbox entries. In `range-store.ts:907–945` and `client-observed.ts:180–203`, query updates and outbox swaps are notified via distinct listener queues. If an outbox swap resolves while an async local query re-evaluation (`this.host.local(...)`) is awaiting execution, an intermediate frame can render the committed outbox entry alongside an already-updated query snapshot, displaying duplicate items simultaneously.
* **Smallest Resolution:** Derive item projection synchronously inside the consumer hook (`useSyncExternalStore` selector or `useMemo`) from an atomically published `Snapshot<T>` and `OutboxState`.

#### Concern 5: Paging and Cursor Ambiguity on Filtered Collections
* **Severity:** Low.
* **Failure Scenario:** `§8` notes that `select` drops null bodies and `order: "reverse"` reverses the page. In `deliveries.q:6–9`, a thread query reads `last 50`. If all 50 items are tombstoned, `items` is empty, but `receipt.next` is present. An unsorted tail of unpredicted drafts appended to an empty page with an active pagination cursor creates confusion over whether new queries should fetch forward or backward.
* **Smallest Resolution:** Keep pagination controls strictly bound to the raw `Snapshot<T>`, and restrict collection item projections to the currently active page without altering cursor mechanics.

### 4. A Simpler, Better Alternative

Instead of introducing a fluent descriptor builder and a secondary subscription layer in the SDK runtime, provide a pure, lightweight selector helper: `projectCollection()`.

#### API Sketch
```ts
// Client helper (pure, zero runtime state, <50 lines)
export interface CollectionItem<T> {
  readonly key: string;
  readonly data?: T;
  readonly draft?: unknown;
  readonly pending: readonly OutboxEntry[];
  readonly predicted: boolean;
}

export function projectCollection<Row, Item>(
  snapshot: Snapshot<Row[]>,
  outbox: { entries: readonly OutboxEntry[] },
  config: {
    select: (row: Row) => Item | null | undefined;
    key: (item: Item) => string;
    reverse?: boolean;
    drafts?: {
      match: (entry: OutboxEntry) => boolean;
      toDraft: (entry: OutboxEntry) => { key: string; draft: unknown };
    };
  }
): readonly CollectionItem<Item>[] {
  // Pure projection:
  // 1. Filter and map snapshot.data via config.select
  // 2. Correlate with snapshot.local.predicted
  // 3. Attach matching unpredicted outbox entries
  // 4. Return stable, immutable item array
}
```

#### Screen Usage
```tsx
export function Thread({ conversationId }: { conversationId: string }) {
  const query = useQuery(api.deliveries.thread, { conversationId, c: null });
  const outbox = useOutbox();

  const items = useMemo(() => projectCollection(query, outbox, {
    select: delivery => delivery.message,
    key: message => message.id,
    reverse: true,
    drafts: {
      match: e => e.op === "deliveries.post" && (e.args as any).conversationId === conversationId,
      toDraft: e => ({ key: e.ids[0] ?? e.intent, draft: { body: (e.args as any).body } }),
    },
  }), [query.data, query.local.predicted, outbox.entries, conversationId]);

  return <BubbleList items={items} reason={query.reason} />;
}
```

#### Tradeoff
* **Gains:** Adds ~0.3 KB gzip instead of 2.5+ KB; introduces no new reactive plumbing or caching hazards; avoids tearing; keeps `client.observe` as the single coherence boundary.
* **Losses:** Computes projection on the UI thread inside `useMemo` rather than inside the shared client worker/session. Because thread pages are capped at 50 rows (`deliveries.q:8`), computing this projection takes <0.1 ms, making the overhead imperceptible.
