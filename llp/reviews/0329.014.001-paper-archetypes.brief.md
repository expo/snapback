# Paper-archetype exercise — falsify the v0 language against one application

You are writing one application, completely, in the language specified by
**LLP 0329.014.000** (`llp/0329.014.000-bounded-programs-language-v0.spec.md` —
read it first, all of it, including §11's rubric). The purpose is not to show the
language works; it is to find **where the language, the schema vocabulary, the
runtime, or the policy model must change** for a real application, and where the
*product* must change instead. The founder's question is "what does the ideal
design for a system like this look like" — your report is evidence toward that.

The application is assigned in the launcher. Its design already exists (schema,
invariants, hard operations, traps) in the input document the launcher names;
that design was produced by a *different* model family, so treat it as a fixed
product specification, not as something to improve — except where §11's
`product-change` class applies and you say so explicitly.

## Method

1. Read the spec (0329.014.000), then the application's design document in full.
2. Rewrite the application's **schema** in the v0 spelling: tables, column types,
   indexes, rules (all four effects, every table), constraints, maintained
   aggregates (with `readable` where K2 applies), `tree`, `interval`.
3. Rewrite **every operation** the design names (every query the UI needs and
   every mutation, including seed/fixture mutations if the design has them) as a
   v0 program. Real code, first attempt as an agent would write it, then the
   corrected form if `check` would refuse the first attempt — show both.
4. For each operation, apply §11 exactly: class; what is missing and of what
   kind; K2 check for every count/sum/rank; integrity check; prediction check.
   Give the certificate line (`examined ≤ …`, prefixes, prediction sites).
5. Produce the **language delta**: every item the spec lacks that this app needs,
   with the smallest addition that closes it, whether it is general or
   app-specific, and which spec section it amends.
6. Produce the **product-change list** with the "when this is a cheat" boundary,
   in the style of LLP 0329.015.003's table.
7. State the **three places the design is most likely wrong or under-specified**
   as exposed by this app (not by taste), and one observation each that would
   confirm it.

## Deliverable (≤ 6,000 words; exactly these headings)

### 1. Coverage table
One row per operation: `operation | kind (query/mutation/schedule/channel/effect) | class (plan / refused→rewrite / maintained / schedule / channel / effect / product-change) | missing (construct / schema / runtime / policy / product / —) | certificate | prediction (closed / conditional / partial / n/a)`. Then the totals.

### 2. Schema in v0
Complete listing.

### 3. Operations in v0
Complete listing, grouped by the design's own sections. For refused first
attempts, show the diagnostic text (family + rewrite) the spec's §9 implies.

### 4. K2 audit
Every count, sum, rank, or "is it full" question: about the caller or about the
resource; the route taken; whether a silent visibility-filtered version would
have returned a wrong number.

### 5. Integrity audit
Each invariant from the design's own invariant list: enforced by a constraint
binding every write, by a rule, by a `require` in a program, by a schedule, or
not enforced. Say which ones the original design could not enforce and now can,
and vice versa.

### 6. Language delta
Ranked. For each: what, smallest addition, general vs. app-specific, spec section.

### 7. Product changes
Table with the cheat boundary.

### 8. Where the design is wrong
Three items, with the confirming observation.

### 9. Confidence
Per section; mark unverifiable repository facts **[inferred]**.

## Rules
- Modify no repository file. Your final message is the deliverable.
- Do not soften: if an operation cannot be a plan, say so and classify what is
  missing. If a spec rule produces a wrong answer (K2-style), that is the most
  valuable finding you can report.
- Do not invent spec features. If you need something the spec lacks, it goes in
  §6, and the operation is classified `refused` (or `effect`/`product-change`)
  until then.
