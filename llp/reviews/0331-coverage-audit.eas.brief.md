## The question

The proposal was audited against 37 *paper* applications. EAS is a real product with a decade of accreted authorization. Would the proposal, **as ruled**, carry EAS? Where not, is the gap something the tiers already name (say which), a stated product loss, or something **NEW** that none of the 37 paper applications had? The founder wants to know this concretely; do not soften a gap and do not invent one.

## The proposal in one paragraph (as ruled 2026-08-30)

**Tier 0 (core):** per-table `read` / `insert` / `update(old, next)` / `delete` rules, default-deny; terms over the row, one opaque scalar `viewer`, literals; `==`, `!=`, comparisons, `&&`, `||`, `!`, `public(reason)`; ONE bounded probe of depth one — `exists(table.index, [key terms])` keyed by row fields / `viewer` / literals, optionally with a `where` that may compare the found row to the subject row, `viewer`, and literals (ruling 1); several independent one-hop probes may be composed; a scoped relation row `{ scope, principal, role }` with a unique `(scope, principal)` index and a closed enum; independent permissions as independent relation rows; scope-less `{ principal, role }` rows are global roles; named programs derive the viewer from the session; transaction-local creation provenance; constraints (unique / cap / immutable / appendOnly / transaction-final counts); every relationship read enters the trace so revocation is live; protection-class table splits for columns with different audiences; **two-hop rules are refused by `check` with the denormalized immutable scope column pasted** (ruling 4); the identity layer mints ordinary principals for services, webhooks, devices, guests, contacts, API keys (no `principal.kind` term in rules); a guest/contact principal is minted at link redemption (ruling 2).
**Tier 1 (admitted):** one reserved `system` principal under which schedules, jobs, effect ingress, and a same-commit continuation (`phase: 'system'`) of a viewer's program run; `callable: 'system'` refuses client invocation; **a table whose rows a system program must read or write names `system` in its own rule** (`|| viewer === system`) — no per-program grant view (ruling 0 as amended); system programs are one trusted domain isolated by reviewed certificate write/read sites and the RFC's taint claims.
**Tier 2 (each waits for a scheduled spec + measured lowering):** hierarchy (`nearest` / `inherits` over `tree` / `dag`); principal sets (`existsAny(index, { principalIn: viewer.bindings })`); bounded two-hop `any(index, prefix, { take ≤ cap, where })`; `getHidden` in a viewer-invoked program; `principal.bearerOf`; engine-maintained relation projections (`maintain.rows`, `propagate`); program-scoped write grants (listed, but a second locus — effectively refused).
**Refused:** a time term in rules (status flipped by a schedule instead); a role lattice / role comparison (explicit sets instead); a `principal.kind` term; permissions-as-data outside RFC dimension Q.
**Outside initial scope:** device-plane evaluation, tenant-installed rule composition, `ctx.session` / `ctx.device` / `fresh` as rule terms, multi-region quorum.
