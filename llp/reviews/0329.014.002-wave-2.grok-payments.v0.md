The original paper’s hard ops are not “11 plans.” v0’s `scan`+`if`+`maintain`+`appendOnly`+`schedule`+`effect` close **internal** money movement as programs. What remains is not missing `sum`. It is **a parent-hot-row that `maintain.sum` reintroduces, a journal the insert rule cannot balance, a close boundary the runtime does not issue, and an effect seam that is not an outbox.**

### 2. Schema in v0

Sentinels: no `optional(t)` (delta §6.9) → `0` / `''` means absent. `time({ commitTime: true })` is **[inferred]** from §4.3 (column spelling not in §2). `never` is the spec’s missing-effect. `range(256)` is **[inferred]** from “for over a literal range.” No `tree`. `bytes` → `text({ max })`. `decimal(38,0)` → `int()` (i53; overflow refuses — §6.7). Enums are `text({ max })`.

```ts
export const postings = table({
  id: id(),
  entryId: ref(journalEntries),
  lineNo: int(),
  accountId: ref(ledgerAccounts),
  segmentNo: int(),
  deltaMinor: int(),
  currency: text({ max: 3 }),
})
  .unique('byEntryLine', ['entryId', 'lineNo'])
  .index('byAccountTime', ['accountId', 'entryId']) // statement page; not seq
  .index('byEntry', ['entryId', 'lineNo'])
  .cap({ by: 'entryId', max: 260 })
  .appendOnly()
  .immutable(['entryId','accountId','segmentNo','deltaMinor','currency'])
  .rules({
    read:   p => canViewAcct(p.accountId) || sys(),
    // Chart-of-accounts, per row. Does NOT see sibling lines (no balanced).
    insert: p => {
      const e = db.get(journalEntries, p.entryId)
      if (e === null) return false
      const op = db.get(operations, e.operationId)
      const acct = db.get(ledgerAccounts, p.accountId)
      if (op === null || acct === null || acct.currency !== 'USD' || p.currency !== 'USD') return false
      if (sys()) return true
      if (op.actorUserId !== viewer) return false
      const debitOwnAvail =
        p.deltaMinor < 0 && acct.purpose === 'wallet_available'
        && acct.ownerWalletId === op.sourceWalletId && canSpend(op.sourceWalletId)
      const debitOwnHeld =
        p.deltaMinor < 0 && acct.purpose === 'wallet_held'
        && acct.ownerWalletId === op.sourceWalletId
        && (canSpend(op.sourceWalletId) || canCapture(op.destinationWalletId) || canPayout(op.sourceWalletId))
      const creditDest =
        p.deltaMinor > 0 && (acct.purpose === 'wallet_available' || acct.purpose === 'wallet_debt')
        && acct.ownerWalletId === op.destinationWalletId
      const creditOwnHeld =
        p.deltaMinor > 0 && acct.purpose === 'wallet_held' && acct.ownerWalletId === op.sourceWalletId
      const creditFee =
        p.deltaMinor > 0 && acct.purpose === 'fee_revenue'
      const creditPayer =
        p.deltaMinor > 0 && acct.purpose === 'wallet_available'
        && acct.ownerWalletId === op.sourceWalletId
      const debitMerch =
        p.deltaMinor < 0 && acct.purpose === 'wallet_available'
        && acct.ownerWalletId === op.sourceWalletId && (canRefund(op.sourceWalletId) || canPayout(op.sourceWalletId))
      return op.kind === 'hold' && (debitOwnAvail || creditOwnHeld)
          || op.kind === 'transfer' && (debitOwnAvail || creditDest)
          || op.kind === 'capture' && (debitOwnHeld || creditDest || creditFee || creditPayer)
          || op.kind === 'release' && ( /* held→avail on payer */ creditPayer || debitOwnHeld)
          || op.kind === 'refund' && (debitMerch || creditDest)
          || op.kind === 'fund' && creditDest
          || op.kind === 'payout' && (debitOwnAvail || creditOwnHeld || debitOwnHeld || creditFee)
          || op.kind === 'dispute' && (debitMerch || creditDest)
          || op.kind === 'chargeback' && (debitOwnAvail || /* debt */ p.deltaMinor < 0 && acct.purpose === 'wallet_debt'
              || p.deltaMinor > 0 && acct.purpose === 'wallet_debt')
    },
    update: never, delete: never,
  })
```

```ts
const SEG = 256
function feeOn(fixed, bp, x) {
  const { q, r } = divmod(x * bp, 10000)
  const varPart = r === 0 ? q : q + 1
  const raw = fixed + varPart
  return raw < x ? raw : x
}
function segSum(accountId) {
  const acct = db.get(ledgerAccounts, accountId)
  db.require(acct !== null, 'NO_ACCT')
  let sum = 0
  for (const i of range(SEG)) {
    if (i >= acct.segmentCount) continue
    const s = db.get(segmentBalance, [accountId, i])
    const v = s === null ? 0 : s.value
    sum += v
  }
  return sum
}
function gatherDebit(accountId, amount) {
  const acct = db.get(ledgerAccounts, accountId)
  db.require(acct !== null, 'NO_ACCT')
  const lines = []
  let left = amount
  for (const i of range(SEG)) {
    if (left === 0) break
    if (i >= acct.segmentCount) continue
    const s = db.get(segmentBalance, [accountId, i])
    const have = s === null ? 0 : s.value
    if (have <= 0) continue
    const take = have < left ? have : left
    lines.push({ accountId, segmentNo: i, deltaMinor: -take })
    left -= take
  }
  db.require(left === 0, 'INSUFFICIENT')
  return lines
}
function requireBalanced(lines) {
  let s = 0
  for (const ln of lines) s += ln.deltaMinor
  db.require(s === 0, 'UNBALANCED')
}
```

`segSum` is a loop tally over **point gets of a cap-bounded key set**. It is about the resource. For the spender the read rule on `segmentBalance` is tautologous (own postings). It is **not** `E_STRUCTURAL_COUNT` under ruling 8’s “scan whose read rule is not tautologous.” Using a **scan of postings** instead is the admitted-wrong program below.

```ts
export const captureHold = mutation({
  clientOperationId: text({ max: 64 }), requestHash: text({ max: 64 }),
  holdId: id(holds), amount: int(), finalFlag: bool(),
}, ({ db, ctx, args }) => {
  db.require(args.amount >= 1, 'AMOUNT')
  const h = db.get(holds, args.holdId)
  db.require(h !== null && h.status === 'open', 'NOT_OPEN')
  db.require(canCapture(h.merchantWalletId), 'FORBIDDEN')
  db.require(h.capturedMinor + h.releasedMinor + args.amount <= h.authorizedMinor, 'EXCESS')
  const feeBefore = feeOn(h.feeFixedMinor, h.feeBasisPoints, h.capturedMinor)
  const feeAfter  = feeOn(h.feeFixedMinor, h.feeBasisPoints, h.capturedMinor + args.amount)
  const feeThis = feeAfter - feeBefore
  const payerHeld = db.get(ledgerAccounts.byOwnerPurposeCcy, ['wallet', h.payerWalletId, 'wallet_held', 'USD'])
  const merchAvail = db.get(ledgerAccounts.byOwnerPurposeCcy, ['wallet', h.merchantWalletId, 'wallet_available', 'USD'])
  const merchDebt  = db.get(ledgerAccounts.byOwnerPurposeCcy, ['wallet', h.merchantWalletId, 'wallet_debt', 'USD'])
  const feeAcct = db.get(ledgerAccounts.byOwnerPurposeCcy, ['platform', 0, 'fee_revenue', 'USD'])
  db.require(payerHeld !== null && merchAvail !== null && merchDebt !== null && feeAcct !== null, 'NO_ACCT')
  const debtBal = segSum(merchDebt.id) // ≤ 0
  const recovery = (-debtBal) < (args.amount - feeThis) ? (-debtBal) : (args.amount - feeThis)
  const heldDebit = gatherDebit(payerHeld.id, args.amount)
  const lines = heldDebit.concat([
    { accountId: feeAcct.id, segmentNo: 0, deltaMinor: feeThis },
    { accountId: merchDebt.id, segmentNo: 0, deltaMinor: recovery },
    { accountId: merchAvail.id, segmentNo: 0, deltaMinor: args.amount - feeThis - recovery },
  ])
  if (args.finalFlag) {
    const rest = h.authorizedMinor - h.capturedMinor - args.amount - h.releasedMinor
    if (rest > 0) {
      const payerAvail = db.get(ledgerAccounts.byOwnerPurposeCcy, ['wallet', h.payerWalletId, 'wallet_available', 'USD'])
      lines.push({ accountId: payerHeld.id, segmentNo: 0, deltaMinor: -rest })
      lines.push({ accountId: payerAvail.id, segmentNo: 0, deltaMinor: rest })
    }
  }
  requireBalanced(lines)
  // insert operation, journal, postings, capture, captureFlags; patch hold counters
  db.update(holds, h.id, old => ({
    capturedMinor: old.capturedMinor + args.amount,
    remainingMinor: old.authorizedMinor - old.capturedMinor - args.amount - old.releasedMinor,
    status: args.finalFlag ? 'captured' : 'open',
    version: old.version + 1,
  }))
})
```

`segSum(merchDebt)` is a **resource fact about the merchant, computed by the operator**. Allowed (they have `canCapture` / view). Silent visibility sum of debt **postings** the operator cannot read would be **wrong-low debt** → skip recovery. `maintain` on the merchant’s debt segments is the route.

Prediction **partial**: payer held segments are not in the merchant’s receipt (non-uniform rules → no extent, ruling 3). Matches UI “capture processing, not received funds.”

`recovery > 0` on the merchant’s own journal is fine. The **payer** must not see the merchant’s recovery split — `postings.read` is per-account, so they don’t. Good.

### 6. Language delta

Ranked by whether Relay’s central invariants stay slogans.

1. **Decrease-only floor over a cap-bounded child group, with no parent OCC row.** `maintain.sum(postings, { by:['accountId','segmentNo'], of:'deltaMinor', floorOnDecrease: { groupBy:'accountId', min: 0 } })` so a negative posting examines sibling segments and refuses `sum < floor`, while a credit to one segment does **not** read or OCC the parent. *General* (wallets, inventory). Amends §2, §5 `constraintChecks`. Without this: overspend (hostile skip of `gatherDebit`) **or** trap-2 hot `maintain` by `accountId`.

2. **`balanced(postings, { by:'entryId', of:'deltaMinor' })`.** Transaction-scoped aggregate constraint. *General* (ledger already asked). Amends §2/§5. Chart-of-accounts **is** expressible as a fat insert rule (this app wrote one); **unbalanced credit is not**.

3. **Host `commitSeq` + sealable watermark vector.** Per-partition monotonic seq assigned at commit; `scan` by seq; a seal forbids later seq ≤ sealed; certificate records the vector. *General* for any deterministic as-of. Amends §4.2, §6, §7. Daily close is otherwise trap 4.

4. **Transactional effect outbox.** Durable `externalActions` already modeled; the missing runtime: lease, `sent_unknown`, host invokes named mutations as `system` on inbound webhook, **cannot client-call** result mutations, retry uses the row’s key. *General*. Amends §1, §7, §8-adjacent. `effect` as “JS with I/O” is not an outbox.

5. **`callable: 'system'`.** *General* (auction). Amends §1/§7. Chargeback/applyResult/freeze/close are client-callable holes.

6. **Mutation-hidden probes / non-returned reads.** A debit-fence program must read dest debt without the reduction escaping to the caller (ruling 8 fires today). Smallest: `db.getHidden(row)` usable in control flow and writes, forbidden in `return` and in any written caller-visible column; certificate lists the site as `hidden`; prediction `partial`. *General* for atomic cross-principal money. Amends §4.2, §9 ruling 8. App-specific trigger: I7+I23.

7. **Money width.** i53 overflow-refuse vs design’s i64 API and “exact wider integer” accumulators for close. Smallest: `int({ bits: 64 })` or `sum` registers wider than storage. *General*. Amends §2/§4.5. $90T is the i53 cliff; close debit_total of 80M postings is the practical one.

8. **`appendOnly` vs one schedule-flipped flag.** Cannot flip `captures.disputable` on an append-only table. Smallest: `immutableExcept` already exists — **do not** mark the parent appendOnly if a flag must move; or allow `appendOnly({ except: ['disputable'] })`. *General*. Amends §2. We split `captureFlags` as a workaround.

9. **`optional(t)`, `text({ enum })` with transitions, `int({ min, max })` on columns and args.** Sentinels collide with epoch and with `id()`. *General*. Amends §2, §4.3.

10. **Authenticated-but-not-public read** (`feeRules` for every viewer). `public` unlocks the world; `viewer !== 0` is not spelled. *General*. Amends §3. Workaround: denormalize fee onto the hold (I11 already wants that).

11. **Principal kinds beyond `system`/`viewer`.** Adjudicator, finance dual-control, processor-ingest. Workaround: tables of assignments + `sys()`. *General*. Amends §3/§4.3.

12. **`db.run(namedMutation)`** in the same tx with summed certificates. Sweep/close/capture otherwise duplicate bodies. *General*. Amends §4.2.

13. **Total scalar `idMod(id, n)` / `hashToInt`.** Partition 128 and credit-segment assignment. Without it, `partitionNo` is client-supplied (skewable) and credit segment is `0` or `E_OPAQUE`. *General*. Amends §4.2 shape functions.

14. **Literal `range(N)` and `int({ max })` args** as executable spelling (ledger #26). Used above; not actually in `lib.d.ts`. *General*. Amends §4.1/§4.4.

15. **Publish `G`.** 256-seg debit is exam≤264–780. If `G.examined=10^4` it passes; if 200 it `E_BOUND`s and the diagnostic will propose “fewer segments” — the §7 cheat. Amends §5.

Not missing: `maintain.sum`, `appendOnly`, `immutable`/`immutableExcept`, `(old,next)` update, unique, cap, schedule/`system`, `effect` as a kind, `ctx.now` in mutations, integer `divmod`, tokens, OCC on the trace, outbox-as-queued-not-sent, `public(reason)`.

Do **not** add `maintain.sum` by `accountId` as the sufficiency oracle — that is trap 2 with a nicer name.

### 8. Where the design is wrong

Not taste. Forced by v0 spelling.

1. **Derived mutable caches are a second ledger, and the design both calls the journal the source of truth and tells writers to update `balance_segments`, `holds.captured_minor`, and `capture_relief` in the same breath.** Under a language whose only authorization is table rules, those caches are ordinary rows. Confirming observation: admit `trimRelief(captureId, n)` that patches `captureFlags.finalReliefMinor += n` with no posting; two $70 refunds plus a $40 dispute then pass `CAPACITY` against a $100 capture, or fail it, independently of the journal. The same shape on `holds.capturedMinor` forges a full hold.

2. **I21 (“authority at server acceptance”) contradicts v0 `ctx.now` (bound at intent, reused) and the design’s own 60-day dispute and 24-hour payout-cooling checks if those are written as clock arithmetic in the client mutation.** Rules re-check grants (good). Time windows do not. Confirming observation: mint `openDispute` on day 59, stay offline 3 days, replay; the intent’s `now` is still day 59 and a `createdAt+60d` `require` passes. Conversely, mint `requestPayout` 23h after a dest change, replay at 25h; reused `now` still fails cooling. Only schedule-flipped flags match I21.

3. **Atomic dest-debt recovery is inconsistent with I23 under ruling 8.** The transfer program must `segSum` dest debt or write dest postings whose amounts depend on it. That reduction is a resource fact over rows the sender cannot read → `E_STRUCTURAL_COUNT`, or the sender’s own journal contains the recovery split and I23 is false. Confirming observation: transfer $100 to a wallet with $30 debt; if `check` admits the program, inspect the sender’s returned lines/activity for a $30 debt leg; if it refuses, the atomic I7 body is not a plan. A third outcome — hidden write, prediction `partial`, money “immediate and final” in the UI — is the design pretending a `partial` prediction is a settled transfer.
