## Overall assessment

**Not ready.** The reset transaction handles the ordinary replacement case well, but four gaps remain: recovery can reuse the old backend program, asynchronous reads can publish old data as fresh, orphan adoption can replay a known receipt into another store, and the legacy fallback can delete retained history without a replacement.

## Findings

### 1. High — A failed backend reload is forgotten after identity persistence

**Location:** [local.ts:474](snapback4/packages/snapback4/src/local.ts:474), [local.ts:498](snapback4/packages/snapback4/src/local.ts:498); identity persistence at [store_identity.rs:49](snapback4/crates/snapback4-device/src/device/store_identity.rs:49).

**Failing scenario:**

1. Device holds A. B has the same generation number but changed programs.
2. A B sync reply commits the reset and records B’s ID.
3. The following `/schema` fetch fails once.
4. On retry, B’s ID already matches and its generation equals the old generation. `replacedStore` is false, so backend loading is skipped.
5. B’s rows can complete acquisition under A’s programs. Reads then execute the wrong program with `fresh: true, complete: true`. An incompatible schema can instead prevent convergence indefinitely.

**Smallest fix:** Persist a “backend adoption required for this store ID” marker in the reset transaction. Require successful backend adoption before publishing acquisition, and clear the marker only with that adoption. Retry and offline reopening must preserve this obligation.

### 2. High — Replacement does not fence asynchronous read results

**Location:** [local.ts:480](snapback4/packages/snapback4/src/local.ts:480), [local.ts:589](snapback4/packages/snapback4/src/local.ts:589), [local.ts:656](snapback4/packages/snapback4/src/local.ts:656).

**Failing scenario:** Start a server-run query or horizon fallback against A and delay its response. Replace A with B and complete B’s reset/acquisition. Release A’s response. The server-read path unconditionally marks it fresh and inserts it into `serverAnswers`; clearing that map during reset does not invalidate outstanding requests. A running watch also publishes the old result before processing its dirty rerun.

There is another exposure window: a `/changes` reply identifying B only schedules sync. If a mutation occupies `networkTail`, `caughtUp` remains true until that sync starts, so a new local query can return A’s rows as fresh **after B’s identity was received**.

**Smallest fix:** Introduce a client incarnation revision. Invalidate freshness, cached watch snapshots and remembered answers immediately upon replacement observation; capture the revision for every asynchronous read and reject/retry results from an older revision before returning, caching or notifying.

### 3. High — Orphan adoption loses receipt store ownership

**Location:** [web.ts:279](snapback4/packages/snapback4/src/web.ts:279), [local.ts:789](snapback4/packages/snapback4/src/local.ts:789), [store_identity.rs:34](snapback4/crates/snapback4-device/src/device/store_identity.rs:34).

**Failing scenario:**

1. An orphan tab’s store belongs to A. A write has `observed_seq` from sync, but its full mutation response was lost, leaving `sent_seq` absent.
2. The primary device store has already acquired B.
3. On reopening the primary store, `adoptOrphans` copies the orphan’s outbox without examining its store identity.
4. Sync sees B → B, so no reset retires the imported known-A receipt.
5. Flush checks `sent_seq`, sends the operation to B, and B executes it.

This preserves at-most-once separately inside A and B, but violates the explicit prohibition on replaying a **known** receipt into the replacement.

**Smallest fix:** Compare the orphan’s persisted identity with the destination during import. Retire known receipts from another incarnation; import only unknown/unsent entries with predictions disabled. Preserve receipt provenance when identity cannot yet be resolved.

### 4. High — A delayed legacy page can falsely reset a healthy store and destroy history

**Location:** [store_identity.rs:15](snapback4/crates/snapback4-device/src/device/store_identity.rs:15), particularly line 25.

**Failing scenario:** Two supported native owners share a SQLite device store and sync with a legacy server that omits `store_id`. Both capture watermark 10 and the same send revision. One response advances the device to 12; the other, produced earlier, arrives with watermark 11. No mutation send occurred, so the send-revision check passes. The fallback interprets `11 < 12` as replacement and deletes the partition and held/left history.

A retained group already left cannot be reacquired from the unchanged server, so this causes permanent loss of delivered history. Shared native ownership is explicitly exercised by [native.rs:1](snapback4/crates/snapback4-device/tests/native.rs:1).

**Smallest fix:** Bind fallback detection to the watermark captured for that request. Reject stale responses when another owner has advanced acquisition; only infer regression when an authenticated response is behind its own requested watermark, with the relevant capture still current.

## Missing test cases

Add deterministic regressions for all four findings, plus:

- Replacement **during A’s paged snapshot and during catch-up**, with delayed A responses delivered after B reset.
- A real IndexedDB reset with an aborted save and process termination around commit, verifying rows, metadata, stages and outbox together.
- Legacy first-identification with retained left-group history, making the intentional migration loss explicit.
- Same-store release activation/adoption controls, backwards-clock controls, and watermark integer-boundary cases.
- Known and unknown receipts across replacement during ordinary and page-exit sends.

The existing interrupted-acquisition tests do not cover failure between persisting the new identity and loading its backend.
