## Verbatim review

The parent-authorized action is sound as an explicit schema delegation: declaring `cascade` authorizes deletion of that child regardless of its own delete rule. I found no arbitrary child-write authority outside the declared action graph. However, the set-null eligibility checks, disclosure contract, reservation, and mixed-action execution need changes.

This was a read-only source review; I changed nothing and ran no builds.

1. **High — §2.2, §4.1: set null can change another table’s audience.**

   The exclusions cover the child’s own read rule and sync audience, but not other rules that inspect the column.

   Concrete example: a hidden `grants` row has `folder: folders ? on delete set null`, `document`, and `principal`. Its own read rule depends only on `principal`. An online `documents` table reads through:

   ```quarry
   read <- exists grants[document = .id, principal = viewer, folder = null]
   ```

   Deleting the folder clears the grant’s folder and thereby grants document access. The folder’s deleter could neither update the grant nor otherwise change that document’s audience. All listed set-null exclusions can pass. The existing rule IR supports these extra probe equalities.

   **Smallest fix:** exclude a set-null column whenever it supplies authority to *any* rule, including another table’s probe key or extra equality. Apply the check across the schema rather than only within the child.

2. **High — §4.2, §6.3: public invalidation metadata reveals hidden child presence.**

   Suppose a readable, deletable project cascades hidden tasks. With no task, the commit touches only projects; with one task, it also touches tasks.

   `row_changed` records actual affected tables. HTTP mutation responses add `preserved` through `ack_preserved`, and `/changes` exports actual `tables` and write footprints. `Footprint::preserved` removes a table when an actual deletion occurs. Thus the caller can distinguish zero hidden tasks from nonzero hidden tasks without receiving their partition events.

   The HTTP mutation reply correctly omits event counts. Nevertheless, core outcomes and local CLI `run` additionally expose actual event counts; `disclosed_event_count` does not filter ordinary events by the caller’s readability.

   **Smallest fix:** publish conservative, schema-fixed invalidation footprints for the entire possible action closure, separately from actual internal changes. Cover `preserved`, `/changes`, core/CLI diagnostics, and derived tables. State explicitly that fixed logical charges do not conceal wall-clock execution time.

3. **High — §2.2, §3, §4.2: ordinary constraints introduce undeclared disclosure.**

   An ordinary hidden child may declare both `append only` and a capped cascade reference. Nothing in eligibility rejects this combination.

   With zero children, deleting the parent succeeds. With one hidden child, `delete_authorized` calls `check_constraints`, which refuses its deletion because the table is append-only. The same problem applies to set-null updates.

   This exposes hidden child existence through `E_CONSTRAINT`, despite the claimed absence of disclosure for these actions.

   **Smallest fix:** reject cascade and set null on append-only children at `check`. Audit remaining child-write hooks for data-dependent refusals; either exclude incompatible shapes or explicitly include their disclosure in the contract.

4. **High — §3 step 3, §4.2 “Transitivity”: nested refusal ordering reveals more than the advertised bits.**

   Let a project cascade two hidden tasks, `x < y`. Tasks have incoming restrict references `A.task` and `B.task`.

   In world one, `A` references `x` and `B` references `y`; in world two, those associations are reversed. Both worlds have identical counts and identical advertised aggregate bits: an `A` referencer exists somewhere in the cascade, and a `B` referencer exists somewhere in it.

   Processing tasks in reference-index order returns `A.task` in world one and `B.task` in world two. The refusal exposes which association belongs to the first hidden task.

   **Smallest fix:** use a generic root-site refusal for nested restriction, or select the reported restriction globally across the complete cascade closure in schema order. Do not select it through hidden child iteration order.

5. **Blocker — §5.1–§5.2: `R(P)` is not yet a defined upper bound on all supported work.**

   The cited `schema/reservations.rs` computes phase-specific source-write prices, not a complete delete/update price. It contains no timeline transition price.

   Concrete example: a capped cascaded child is a mapped repost source. Its ordinary deletion can invoke `timeline_remove_id`, which inserts a removal tombstone, enqueues purge work, and deletes the engine event, in addition to deleting the source row. These writes are absent from the stated one-row price and the cited reservation implementation.

   Likewise, a reservation’s written-row count does not bound physical authorization visits. Private-field delivery can evaluate recipient read rules and traverse expired witnesses outside the child-reference cap. The current `AUTHORIZATION_WALK_LIMIT` counts actual fetched candidates, not reserved rows.

   Finally, devices cannot rebuild prices identically from their projected schema: the existing reservation contract deliberately exports prices while omitting private formulas.

   **Smallest fix:** define and export a complete action reservation plan covering traversal, indexes—including word expansion—assets, maintenance, timelines, applicable receipt hooks, recipient authorization, and physical visits. Specify checked arithmetic and nested allowance ownership. Reject unsupported hooks until they have bounded prices. Compiler/server validation must rebuild from the full schema; devices must consume the validated exported plan.

6. **Medium — §1, §3, §7: the committed-delete postcondition is false.**

   This legal mutation defeats the stated invariant:

   ```quarry
   delete parents[p]
   insert children { id: c, parent: p }
   ```

   The delete’s action finds no children. The later insert performs no existence check. The transaction commits with a live child referencing the deleted parent.

   Consequently, “after a committed delete … no live row references `p`” and “no reference leaves orphans any more” are too strong. Excluded reference kinds also retain orphan-producing behavior.

   **Smallest fix:** narrow the guarantee to references present when the delete statement executes, and explicitly allow subsequent writes—even within the same mutation—to create dangling references. If a commit-end invariant is intended instead, specify transaction-final validation of references to deleted identities.

7. **High — §2.2, §8, §9: null-exempt caps invalidate existing population proofs.**

   With `cap 10 by assignee` and set-null semantics, arbitrarily many tasks may have null assignees.

   However, `Schema::group_bound`, the compiler’s `prefix_bound`, shape advice, and mutation admission derive a bound from pinned *column names*, without proving that their values are non-null. A mutation iterating `.assignee = null` can therefore receive a ten-row scan bound and a whole-population admission proof for an unbounded population.

   Activation and prediction also currently count/prove null cap groups. Changing from set null back to restrict restores the null-group limit, contradicting §8’s statement that changing an action affects only the next delete.

   **Smallest fix:** represent null exemption explicitly in cap metadata. Require non-null evidence wherever that cap establishes a population bound; skip exempt groups in cap enforcement, activation, occupancy bookkeeping, and device insert/move proofs. Validate existing null groups when an action change restores their limit.

8. **Medium — §6.3–§6.4: the device no-orphan promise includes history that receives no deletion.**

   A device can retain a task after leaving its group under delivered-history policy. Its parent remains in a public partition. Later, the server cascades the task and deletes the parent. The device receives the public parent deletion, but no longer receives the departed group’s task deletion. Its retained task remains.

   The same broad guarantee also overlooks pending inserts replayed after publication: ordinary references still permit those inserts to name a deleted parent.

   **Smallest fix:** scope §6.3 to confirmed, currently acquired child rows covered by the commit’s delivery. Explicitly preserve retained-history and pending-write exceptions. Complete coverage proves a snapshot population; it does not prove freshness against subsequent server writes or expiry, so device and server refusals may legitimately differ.

9. **High — §2.2 self-references, §3 ordering, §6.2: set null can invalidate the parent image awaiting deletion.**

   A permitted self-reference can contain `p.link = p`. Step 3 clears `p.link`; step 4 then deletes `p`.

   Implementing these steps with the current `delete_authorized(table, old)` tail uses the original image. Both SQLite and memory deletion remove index keys using that supplied image. The new null index key can remain, while maintained contributions are subtracted from the wrong group.

   Excluding self-null alone is insufficient. An acyclic cascade `P → C` can have a set-null edge back to `P`, changing an ancestor already awaiting deletion.

   **Smallest fix:** track deletion targets by table/id, make deletion dominate set null for those targets, and obtain the current image before each physical write. Specify handling of mixed-action back edges and converging paths; an acyclic cascade graph alone does not settle them.

10. **Medium — §7–§8: the migration note does not cover the complete behavior change accurately.**

   A parent with `read <- deny` and `delete <- allow` currently permits a direct-id delete when it has only ordinary references. Under §3, that delete becomes `NOT_FOUND` even when no child exists. This change is not an occupancy restriction.

   Conversely, an undeclared read-through reference already imposes read authority and `E_PARENT_HAS_CHILDREN`; it is not a delete site newly changed by the default.

   **Smallest fix:** have migration diagnostics explain the new read prerequisite separately, exempt existing read-through behavior from “what changed,” and retain an orphan advisory for excluded reference kinds where useful. `N_DELETE_RESTRICTED` is appropriate for the new default’s occupancy effect, but not as an exact description of every changed outcome.

11. **Medium — §9: the proposed Lean campaign can skip every valid cascade/set-null case.**

   Both actions require a cap. The current Lean emitter rejects capped tables as `table-cap`; the Lean README explicitly excludes caps. Adding `onDelete` decoding and changing the authority theorem alone does not make those schemas comparable.

   The current Lean harness also excludes meters, table sets, sequence metadata, expiry, and devices from comparison. Its case count cannot establish the disclosure or reservation claims above.

   **Smallest fix:** explicitly extend the model/emitter with the necessary capped fragment, or define a justified abstraction with enforced preconditions. Require counts of *supported action cases* by action and outcome. Add separate paired-world checks for all public metadata, nested refusal ordering, and physical-budget boundaries, plus raw state/index checks for mixed-action execution.

The remaining choices are coherent. Default restrict deliberately permits stranger pinning; §4.3 acknowledges that consequence. Dangling-id claiming is an explicit consequence of declaring cascade, rather than an undeclared authorization bypass, although it now has destructive consequences that deserve clearer wording. Keeping existing orphans legal and declining an adoption scan is defensible.

A cap on the exact reference is a suitable bound on live children when scans skip expired backlog. The stricter read-through physical-child rule, prohibition of expiring read-through cascades, expiry bypass, capability fence, atomic rollback, and rejection of an implicit background sweep are all sound directions. Existing at-most-once receipts also appropriately prevent action re-execution.

**Overall verdict: NOT READY.**
