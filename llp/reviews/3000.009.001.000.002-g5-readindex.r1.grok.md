## 1. Linearizability without clocks

For a write that this owner, a successor, or any other grant-unaware writer commits through `Tx::commit` before the read arrives, an RI-served HTTP read does not return an older cached value. The linearization point is the validating statement’s snapshot, taken after that reader’s batch has closed enrollment.

Enrollment order holds, including depth 2. `prepare_read_index` assigns `serial` only after a successful `try_lock` lookup, and overflow refuses instead of wrapping (`revision_cache_park.rs:35-40`). Park pushes only onto `pending` (`serve_read_index.rs:101-103`). `tick` `mem::take`s that pending batch under the queue mutex before `submit_until` (`serve_read_index.rs:44-54`). `validate_read_index` loads `cut` and only then runs SQL (`revision_cache_park.rs:43-46`). `complete` keeps the proof only when `serial <= cut` and the cache `Weak` matches (`revision_cache_park.rs:18-20`). A reader who arrives while a flight is in progress joins the new pending batch. Each of the two flights certifies only the waiters it detached.

The statement really starts a new snapshot. `Connection::independent` is one autocommit extended query and returns an error if this wrapper already holds a transaction lease (`pipeline.rs:560-571`). An open repeatable-read reader holds that lease, so the validation cannot run inside it. Read Committed takes the snapshot when the server executes the statement, which is after the cut. A commit acknowledged before arrival is visible in that snapshot. A commit that lands during the park and is missed by the snapshot linearizes before the read. An 8 ms budget and a delayed worker resume are outside that argument: a proof applied on resume is still the snapshot from after enrollment, and a late proof is dropped.

What the statement proves is the whole `Published` stamp plus fence and session settings. `PUBLICATION` is revision, head, backend generation, store id, schema hash, and activation hash (`read_grant.rs:64-77`). `read_index.rs:13-28` adds `_owner` store, token, and holder, `_meta.generation`, and `client_encoding = UTF8`, and `binary_read` appends the settings guard as a trailing column (`checks.rs:121-128`), so indexes 0–10 stay put. Token, holder, store, both generations, encoding, row count, or any error becomes `None` (`lifecycle.rs:79-82`) and the read falls through to ordinary G5. There is no new read-your-writes token. Same-transaction commits bump revision before acknowledgement (`store.rs:840-844`), so a later read’s snapshot misses the old fill.

The proof is narrower than per-read G5. **MATERIAL.** Per-read G5 re-reads the digest’s session projection in the same snapshot (`revision.rs:39-47`) and then resolves those fresh rows. RI compares the stamp and then calls `cached_authority_snapshot` with the fill-time `SessionFacts` (`revision_cache.rs:817-828`). `cached_read` is `cpu_only` (`store.rs:157`), so it sends no `BEGIN`, and `rollback` returns immediately because `done` is already set (`store.rs:891-892`). Concrete miss: a revision-less edit of `_sessions` (raw SQL, or any later writer that skips `Tx::commit`) leaves `_head` unchanged. G5’s resolver sees the deleted or replaced session and denies. RI serves the cached authorized body. In-contract authority writers do not do this. `invalidate_session` / `invalidate_family` (`authority.rs:169-183`), identity inserts, and `set_clock_session` call `require_serialized_head_fence` (`authority.rs:190-196`). Serving connects set `unified = true` (`opening.rs:66`). A unified durable commit with `revisions == 0` bumps the revision (`store.rs:840-844`), the stamp misses, and the fresh G5 path runs. Lease renewal is the documented out-of-stream exception and does not change these facts. I would not call the statements equal.

The rest of the hit path fails closed onto that same G5 path. The enrolled `Arc<Entry>` is immutable and is reinstalled only when the cache pointer and key still match (`revision_cache.rs:716-718`). A `try_lock` failure skips RI and consumes no serial. Uncertain grants clear the key before lookup (`revision_cache.rs:705-711`). Revoked or uncertain grants skip the proof (`revision_cache.rs:805-807`) and are checked again after the authority callback (`revision_cache.rs:821-822`). A token mismatch on takeover yields `None`, then G5. G5 itself does not read `_owner`, so the fallback is exactly today’s revision-equality hit. A successor commit that bumps revision changes the stamp. A latch that flips after that check and before bytes reach the socket is the same window G5 already has. RI does not clear the latch, retry the epoch, or block the ownership-loss exit.

Deadline and disconnect do not apply a stale proof. `until` is `min(now+8ms, the absolute deadline captured at dispatch)` (`serve_read_index.rs:97-100`). `complete` drops the proof when `now >= until`, refuses with the existing 503 when `now >= deadline` (`serve_read_index.rs:70-75`), and `submit_until` drops an expired job (`request_workers.rs:73`). `Request::is_aborted` is the server abort flag only (`request.rs:382-386`); a TCP half-close does not cancel a shared flight. The parked request is still released on the wait, resume, or abort path. `proof.take()` runs once (`serve_queries.rs:100`), so a generation or fallback retry cannot re-enter synchronous RI. `query_context` on resume runs after the enrolled key; a key mismatch ignores the proof.

Stage R is the hole that is not open yet. **MATERIAL.** RFC 003 §5.1 requires every reader to bind atomic W immediately before the snapshot and to use `V.r = GREATEST($w_r, head.revision)`. §5.2’s G5 row says the statement revision is `V.r` and installs only through published W (`llp/3000.009.001.000.000.003-concurrent-disjoint-commits.rfc.md:499-553`). The LLP already says reading H is not that proof (`llp/3000.009.001.000.002-beating-the-postgres-controls.rfc.md:1547-1560`). The code reads H (`read_index.rs:13`) and bypasses only when `early_release` is set (`read_index.rs:10`, `revision_cache.rs:806`). After Stage R, a cached fill at an unpublished head is reused because the coalesced statement still matches H, while a two-image reader must bind V from W first. Stage R is not in this checkout, so that execution is not available here.

## 2. Liveness and resources

Parked HTTP readers do not leak loans, wedge on ownership loss, or grow without the existing admission bound.

The park path returns the detached reader before waiting (`serve_queries.rs:62-63`), drops the publication lease via `executed()` (`serve_read_index.rs:85`), and keeps the socket permit inside `Resume`. Resume re-admits with `Scope::begin` / `Scope::admit` (`serve_queries.rs:71-72`). Waiters are the admitted short class: 30 workers plus the 258 queue. Cache bytes stay inside the existing budget. Two validator workers borrow a pool reader only around SQL and `put` it back before `complete` resumes anyone (`serve_read_index.rs:91-93`). The pool stays the existing 30 readers plus writer and lease. A stalled flight cannot stop the timer from expiring other waiters or opening the second flight (`serve_read_index.rs:44`).

There is no timer/validator deadlock. `tick` holds the queue mutex and then locks a running batch (`serve_read_index.rs:35-43`). The validator drops the batch guard at the end of the `mem::take` statement before it locks the queue (`serve_read_index.rs:56-57`). A missed wakeup is rechecked within 200 µs or 1 ms. Ownership loss returns `None` and resumes G5; it does not leave the waiter parked. Spawn failure completes the batch with `None` (`serve_read_index.rs:60-63`). Validator panic is `catch_unwind`’d (`serve_read_index.rs:55`).

The 8 ms fallback is safe under overload. Expiry resumes an ordinary G5 read with the original deadline, or refuses. It does not apply the shared proof. The five-second statement timeout still bounds the SQL.

The blocking engine API can hold readers. **MATERIAL.** `query_materialized_search_with_request` calls `query_cached_request(..., None, true)` (`engine/mod.rs:843-844`). With the flag on, that enters `ReadIndex::validate` for up to 1 second while the caller still owns its engine (`revision_cache.rs:811-813`, `revision_cache_read_index.rs:31-69`). Thirty concurrent callers — difftest, core tests, any embedder — sit on thirty reader loans. The HTTP success path does not: resume uses `allow_blocking=false` (`revision_cache_park.rs:53-61`). The memory fallback at `serve_queries.rs:148` is not a Postgres store. Personas and staging pass `with_revision_cache(false)` (`serve.rs:1201`), so `prepare_read_index` never parks.

**MINOR.** After the first park, the timer thread loops every 1 ms even when idle (`serve_read_index.rs:29-31`, `:67`). One thread, not an unbounded queue. A panic in that thread is not isolated; the validator path is. I did not find a panic in `tick`’s own critical section.

## 3. Default-on readiness

Flipping the flag does not change SQLite. `prepare_read_index` requires `AnyStore::Postgres` (`revision_cache_park.rs:28`). The SQLite hit returns before the RI block (`revision_cache.rs:721-738`). Non-Postgres builds never pass `allow_blocking`.

`commit=early` stays on gated G5. `durability().is_some()` and `early_release.is_some()` both skip RI.

G6 stays ahead of RI on the fast path. A matching grant hit returns before the RI block (`revision_cache.rs:742-786`). `locally_changed` forces a miss (`revision_cache.rs:790-799`). **MINOR:** if both flags are set, `store_config.rs:237` overwrites the RI tier string written at `:218`, so diagnostics name only G6. If `Grant::read` gives up after its 1 ms inflight wait without revocation (`read_grant.rs:173-191`), RI may still certify a stamp hit. That result is as fresh as G5; the tier line will not say so.

The flag is still default-off. `Cache.enabled` is true only when `SNAPBACK4_G5_READ_INDEX=1` (`revision_cache.rs:237`). Unset or `0` leaves it off. Any other value refuses Postgres config (`store_config.rs:41-44`). The guide still marks the feature experimental. The LLP is still Review and records no accepted default-on (`llp/3000.009.001.000.002-beating-the-postgres-controls.rfc.md:1477-1483`).

The vendored tiny_http change is safe. `set_parser_cpu_clock` is installed only when `SNAPBACK4_READ_TRACE_ALL` is set (`serve_trace.rs:147-148`, `request.rs:810-813`). With the clock unset, parse behavior is unchanged. `is_aborted` reads the server abort flag and does not treat peer half-close as cancellation (`request.rs:382-386`). No new `unsafe`.
