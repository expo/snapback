1. **Blocker — set-null pagination can miss a row moved behind its cursor.**

   **Location:** RFC §3 step 5; `crates/snapback4-core/src/engine/write_references.rs:97`, `:142`; `crates/snapback4-core/src/schema/references.rs:88`; `crates/snapback4-lang/src/bind/reference_actions.rs:35`.

   Reference-index reuse accepts arbitrary columns after the reference. Extend the existing set-null regression schema with `by byCategoryCount: category, filed, id`. Have five nodes `a,b,c,d,e` in category `k`; `a.parent = b`, so `b.filed = 1`, while the others have zero.

   The first page contains `a,c,d,e`; its cursor ends at `(k,0,e)`. Clearing `a.category` mirrors `b.filed` from one to zero, moving `b` to `(k,0,b)`, behind that cursor. The next page misses `b`. Deleting `k` commits with `b.category = k` still present. Rereading each selected identity fixes stale images but cannot recover an identity the scan missed.

   **Smallest fix:** use a stable index for set-null walks—`[reference,id]`, or `[reference,effectiveDeadline,id]`—and restrict reuse accordingly. Add this five-row variation to the regression.

2. **High — set-null evaluates child read rules and spends an unreserved authorization allowance.**

   **Location:** RFC §3 step 5, §4.2, §5.1; `crates/snapback4-core/src/engine/write.rs:455`; `crates/snapback4-core/src/engine/write_references.rs:190`; `crates/snapback4-core/src/engine/read.rs:330`.

   `clear_reference` passes `readable = true` into `replace_authorized`, but `check_constraints` independently calls the child’s read rule for every update.

   A permitted child can have an optional category with set-null and `read <- exists grants[.access]`; that rule does not read category, so eligibility admits it. Its write plan does not reserve this read-rule probe. The probe nevertheless traverses grants under the request’s shared physical authorization allowance.

   Arrange preceding work so `R(P)` consumes the remaining allowance. With no hidden child, the delete succeeds; with one child, its constraint-time read probe raises `AuthorizationBudget`. That is an undeclared, occupancy-dependent refusal despite §4.2. Larger witnesses also introduce unreserved examination and scratch.

   **Smallest fix:** pass the already-established readability decision into constraint checking, and make the engine-owned set-null path validate constraints without evaluating child rules.

3. **High — `unit(C)` takes a heap maximum over reservations that remain live together.**

   **Location:** RFC §5.1; `crates/snapback4-core/src/schema/references.rs:291`; `crates/snapback4-core/src/engine/columns.rs:94`, `:99`; `crates/snapback4-core/src/engine/write_target.rs:15`.

   `unit_write` reserves the largest plan-phase heap. Execution charges both `COLUMNS` and `ASSETS` and retains their sum until `target_attempt` ends; aggregate and row-view reservations can overlap them too.

   For example, cascade one child carrying `[file <=N] <=500` and contributing to a maintained count on a parent with `text <=110000`. The asset phase reserves 8,192,000 bytes; the column phase reserves over 8,800,000 bytes for the parent. Each fits individually, and the other reservation dimensions can fit default ceilings, but their simultaneous heap exceeds 16 MiB. `R(P)` selects their maximum. The replacement meter is unbounded, so execution proceeds without enforcing that larger peak.

   **Smallest fix:** calculate the peak from the reservations actually held concurrently, and update §5.1 accordingly. Alternatively, change reservation lifetimes so the phase maximum is valid.

4. **High — retained device history is absent from the page and examined reservation.**

   **Location:** RFC §5.1, §6.4; `crates/snapback4-core/src/engine/write_references.rs:140`, `:147`; `crates/snapback4-core/src/schema/references.rs:239`, `:254`.

   `each_child` permits four retained, noncurrent rows per invocation before queuing. Those rows consume fetches and page seeks but neither the live cap nor a reservation term.

   A concrete state is a cap-one read-through cascade whose parent ID has been reused across audience groups. The device retains four children from departed groups and holds one current child in the newly acquired group. Read-through references bypass `prove_reference_held`, so the cascade scans four retained images, then the current image, rereads that child, and rereads the root. With no other hooks, `R(P)` reserves five examined units—including the unused capture allowance—but these operations fetch seven images. The capped walk also requires two page seeks where `w` reserves one. Four skipped rows permit successful prediction, so the queue threshold does not prevent this overrun.

   **Smallest fix:** use a current-only scan, or execute retained-history traversal under a separate bounded device-work allowance that queues on exhaustion. If it belongs inside `R(P)`, add a schema-fixed history allowance on every host.

5. **Medium — reading a count view silently substitutes for proving a zero-count guard.**

   **Location:** RFC §7; `crates/snapback4-lang/src/bind/reference_actions.rs:162`, `:190`; `crates/snapback4-lang/src/bind/delete_guards.rs:29`.

   Any read of an unfiltered count view adds its child/reference pair to `counted`. Suppression checks only that pair: it does not require comparison with zero, matching the deleted key, or dominance over the delete.

   For example, `n = bookingsBySlot[other]` followed by `delete slots[slot]` silences `N_DELETE_RESTRICTED`, although bookings can still make that delete newly refuse. An unused read or a read inside an unrelated branch has the same effect. Count-like sums inherit this problem.

   **Smallest fix:** suppress only for a dominating zero-count requirement over the deleted identity, with no intervening write invalidating it. Until that proof exists, retain the note.
