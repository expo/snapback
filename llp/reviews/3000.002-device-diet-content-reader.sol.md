## Overall assessment

The measured size reduction and canonical serialization claims are credible, but the change is not ready. A mixed Scan/domain object can now decode successfully as a different variant solely because of key order, silently discarding the valid Scan fields. The blocking source guard is also bypassable by an aliased derive or generated type.

## Required explicit answers

- **Did the change introduce a new problem?** Yes. A valid Scan object augmented with valid Range fields decodes as Scan at BASELINE but as Range at IMPL_COMMIT when a Range key comes first; the new decoder silently drops the Scan fields. Direct decoders also became more permissive about malformed unknown subtrees on server/backend-open paths.

- **Is there a regression test that would also pass without the change it claims to test?** Yes. `mixed_scan_and_domain_fields_have_explicit_streaming_precedence`, the positional-Scan check, and `skipped_unknown_syntax_keeps_the_existing_web_validation_boundary` can pass with the old derived decoder because their `compare` results or value differences are not asserted ([lane_source.rs:38](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/tests/lane_source.rs:38), [lane_source.rs:290](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/tests/lane_source.rs:290), [lane_source.rs:306](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/tests/lane_source.rs:306)).

## Findings

### Medium — Mixed Scan/domain maps silently change variant according to key order

File: [snapback4-core/src/ir/lane_source.rs:39](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/src/ir/lane_source.rs:39)

Concrete scenario: take any valid corpus Scan and add valid `start`, `end_exclusive`, and `max` fields before `site`. BASELINE’s untagged order tries Scan first, ignores the extra domain fields, and returns `LaneSource::Scan`. IMPL_COMMIT sees `start`, enters `small`, ignores every Scan field at line 86, and returns `LaneSource::Range`. Put `site` first and the same object becomes Scan. This is a silent semantic change and field loss, not a safe refusal.

The test explicitly permits both implementations to return unequal successful values ([lane_source.rs:42](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/tests/lane_source.rs:42)).

Smallest fix: once a small variant is selected, reject any field in Scan’s discovered set; once Scan is selected, make the replay wrapper inspect subsequent string keys and reject any small-domain key. This preserves streaming while making every mixed map a deterministic refusal.

### Medium — The blocking census can be bypassed by an aliased derive or generated item

File: [wasm-codec-census.mjs:79](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/packages/snapback4/test/wasm-codec-census.mjs:79)

Concrete scenario:

```rust
use serde::Deserialize as De;

#[derive(De)]
#[serde(untagged)]
enum Added {
    Scan(Scan),
    Expr(Expr),
}
```

This compiles a normal serde untagged decoder, but the census requires the literal word `Deserialize` in the item attributes, so `representations` skips the item and the blocking suite remains green. A macro whose emitted item name is a metavariable similarly falls outside the textual item walk. The slower artifact check would catch many such cases only when somebody runs a measurement.

Smallest fix: at minimum resolve and test `serde::Deserialize as Alias` imports and reject unresolvable derive aliases. To make the guarantee apply to generated types, either prohibit type-generating macros/procedural output in these web-reachable modules or put a compiled-artifact family check on the blocking path.

### Low — Direct backend/server decodes no longer validate malformed unknown LaneSource subtrees

Files: [lane_source.rs:43](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/src/ir/lane_source.rs:43), [engine/mod.rs:285](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/src/engine/mod.rs:285)

Concrete scenario: store a canonical program with an extra LaneSource field whose value is an unpaired surrogate, an out-of-range JSON number, or nesting beyond the ordinary tree limit. BASELINE’s `Content` construction rejects it. IMPL_COMMIT skips it with `IgnoredAny` and `Engine::open` directly calls `serde_json::from_str`, so the server accepts the corrupted stored program. `WebDevice::new` and kept-backend reopen likewise decode directly ([web.rs:27](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-device/src/web.rs:27), [device.rs:255](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-device/src/device.rs:255)). The test’s validation argument applies only where `validate_text` is actually called.

Smallest fix: run the existing allocation-free `json_codec::validate_text` before typed decoding at the server program-open and web/backend-open boundaries, or explicitly narrow and document the corruption contract.

### Low — Scan-field collisions and the metadata probe have no loud compatibility guard

File: [snapback4-core/src/ir/lane_source.rs:37](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/src/ir/lane_source.rs:37)

Concrete scenario: add `#[serde(alias = "max")]` to a Scan field. Input using that supported alias with `max` first is routed to the small decoder before the discovered Scan fields are consulted; it rejects or, if complementary domain fields exist, becomes the wrong small variant. A later custom Scan deserializer that returns `Ok` for the probe makes `unwrap_err()` panic. The “new field” test covers `existence`, not a discriminator collision ([lane_source.rs:272](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/tests/lane_source.rs:272)).

Smallest fix: reject an empty discovered list and any intersection with `start`, `end_exclusive`, `value`, or `max`; replace `unwrap_err()` with an explicit match; add a test that pins field-set disjointness.

### Low — Several differential tests do not enforce their claimed behavior

File: [snapback4-core/tests/lane_source.rs:38](/Users/ccheever/projects/snapback-dm-review/D3-r1/repo/snapback4/crates/snapback4-core/tests/lane_source.rs:38)

Concrete scenario: restore the old derived decoder. For `SkippedUnknown`, both decoders now reject, `compare` returns `false`, and the caller ignores the result. For `MixedScan`, both decoders return the same Scan, but equality is deliberately skipped. The positional call also ignores whether the new side refused. Smallest fix: return a structured comparison result and assert the expected old/new outcome and exact new variant at every deliberate-difference call site. For Scan order, assert the actual branching invariant—each possible first recognized key plus representative remaining orders—rather than claiming exhaustive key-order coverage.
