## Overall assessment

S3 is the intended exception to “one implementation, in Rust”: on `wasm32` + `web` only, `words::fold` takes NFC from a guarded `String.prototype.normalize("NFC")` and then uses Rust `to_lowercase`. Server and native still use `unicode-normalization` 0.1.25 (Unicode 17.0.0). `Builtin::Lower`, `nfc-lower-alnum-1`, email, mentions, and cursor encoding are unchanged. The constructor refuses with `E_HOST_UNICODE` before backend parse, kept-row load, or index rebuild. The budget ratchet fails only the suite’s wasm-build step; `measure-wasm.sh` still records `over`. Composed reads report `since: lastSyncAt` on the one composition path that query and both watch observations share.

The landing matches the 2026-09-18 rulings with one real hole in the guard: canary 2 does not test canonical reordering. Node 24.18 / ICU 78.3 is recorded at 57,848 folds and zero differences; Chromium on this tree is honestly left to the lead. Server folding is not changed.

## Findings

### Medium — canary 2 does not detect compose-without-reorder

**Where:** `snapback4/crates/snapback4-device/src/web.rs` 29; same pairs in `unicode_fold.rs` 14 and `unicode.test.mjs` 30.

**Scenario:** Host `normalize("NFC")` composes adjacent starter+combining marks but does not reorder by combining class. Canary input `d` + U+0323 + U+0307 is already in canonical order, so that host returns U+1E0D U+0307 and the guard **opens**. A later apply of body `d\u{0307}\u{0323}` (dot-above then dot-below): Unicode NFC reorders then composes to U+1E0D U+0307; the broken host composes `d`+U+0307 to U+1E0B and leaves U+0323. Local word keys disagree with the server. `matching` on the NFC form misses the row on the web device.

Identity-normalize, missing `normalize`, and NFD still fail canary 1 (`A`+U+030A → U+00C5). The LLP already says the canaries are not an exhaustive proof; they are still not decisive for the reordering mode the brief names.

**Smallest fix:** Change canary 2’s input to `d\u{0307}\u{0323}` (U+0307 then U+0323); keep expected `U+1E0D U+0307`. Update the native oracle, the JS stubs, and the LLP pair in the same commit.

### Low — unguarded `JsString::normalize` after a successful open (and on `word_fold`)

**Where:** `words.rs` 34; `web.rs` 59–61; `Cargo.toml` 35.

**Scenario:** `WebDevice::new` succeeds. A script then deletes or replaces `String.prototype.normalize`. The next `apply` / `matching` / reopen rebuild calls `JsString::normalize` with no `catch`. That is a wasm-bindgen import into a `panic = "abort"` module. The constructor path cannot hit this; `word_fold` can without ever constructing a device.

Empirically the throwing-normalize test still folds ASCII afterward, so this is a loud JS throw rather than a proven instance abort. It is still a new failure mode: at BASELINE, deleting `normalize` did nothing because NFC was Rust.

**Smallest fix:** Call the same caught `Function::call1` used by the guard (or refuse with `E_HOST_UNICODE`) inside the web `fold` path; drop or gate `word_fold` so it is not a production export.

### Low — no suite check that NFC tables stay out of the web artifact

**Where:** `attribute-wasm.mjs` 123–136; core `Cargo.toml` still has `unicode-normalization = "0.1"` unconditionally.

**Scenario:** A later web-reachable `.nfc()` / `UnicodeNormalization` use links the tables again (~59 KB gzip historically). `--check-families` / `--check-absent` stay green. The diet regresses under a report-only measurement unless someone reads twiggy.

**Smallest fix:** Extend `--check-absent` (or the wasm-budget test) to fail on `unicode_normalization` symbols in the web artifact.

### Low — budget `why` need not describe this raise

**Where:** `wasm-budget.mjs` 8; `metrics/wasm-budget.json`.

**Scenario:** A landing sets `"gzip": 450000` and leaves the previous `why`. The helper accepts it. `build-wasm.sh` goes green. The ratchet’s “with the reason” rule is a diff the reviewer can see, not a check.

**Smallest fix:** None required if that visibility is the design. If not, refuse a `gzip` change whose `why` / `set` are unchanged.

## Did the change introduce a new problem?

Not on the server or native device: fold is still `nfc().collect::<String>().to_lowercase()`, `Builtin::Lower` is still Rust, durable/wire forms and `nfc-lower-alnum-1` are unchanged.

On the web, the new problems are the ones above: a compose-without-reorder host passes the guard (Medium); post-open / `word_fold` NFC is unguarded (Low). The host-NFC dependency, the ~1 KB guard, the blocking budget, and `since` on composed reads are the rulings, not regressions.

A composed read at BASELINE was `fresh: false` with no `since`. That was the bug C fixes. Clients that treated “non-fresh without `since`” as a composed-read signal will now see `since`; that is the contract.

## Is there a regression test that would also pass without the change it claims to test?

Yes, in part:

- `host_nfc_canaries_match_native_tables_and_ascii_lowercase` (`unicode_fold.rs` 13–21) never executes the web cfg; it would pass at BASELINE.
- Fold expected values in `unicode.test.mjs` 18 and 23 are JS `toLowerCase(NFC(text))`. On Unicode 17 that often equals Rust lowercase, so without the `lowered === 0` counter the equality would not catch a host-lowercase fold.
- MQ composed scenarios other than R2 still do not assert `since`; they would stay green if line 906 omitted it. R2 (`retained-history.test.mjs` 381–409) would go red.
- `composition_card_matches_readme_and_the_routing_boundary` only pins docs to each other.

Tests that would fail without the change: constructor `E_HOST_UNICODE` matrix (including delete and `{bad backend}`), `lowered === 0` plus ASCII `normalized` stuck at 6, page-apply host-call counts, `wasm-budget.test.mjs` overrun `status !== 0`, guide `E_HOST_UNICODE`, R2 `since`.

Verdict: READY WITH CHANGES
