A server-named newest suffix of one conversation should become durable before the rest of the account. The plan's exact-cut replay is the wrong way to get there, and the scheduler never acquires the screen a messaging app has to reopen.

## 1. Exact-cut historical replay fights the replica you already have

Publishing a suffix early is Repair A applied before the rest of the snapshot: the server already names `whole` or a floor key per group when that group's horizon walk finishes (`snapshot_page`), and the device already treats a descending page as complete only at or above that floor. The new requirement in §6.2 is a second image store so a candidate read at cut B can be replayed to a frozen cut P.

Catch-up is required to do the opposite. LLP 3000 §7 (2026-09-13) says sync catch-up re-evaluates the current row and emits only its current readable image, or a deletion when the row is gone or expired. `expand_joins` implements that by discarding the logged payload and fetching the live row. LLP 3000.007 §18.2 went further: join expansion delivers the current readable top-N, and the historical candidate set was deleted so no completion proof consults history. Repair B then makes an image ahead of the watermark the supported steady state. The case that makes that unsound is the device's own prediction, and §7 of this RFC leaves prediction eligibility unchanged.

A history page joins that same replica. It does not need a tighter cut than the one the live stream already publishes. Read the next suffix in one server transaction, keep the floor the server already emits, stage that group's pages until the floor and the ordinary catch-up through that watermark are durable, and publish only then. Advance the single published watermark across groups already installed, with Repair B's fences. If the log interval for that watermark is gone, read the suffix again. Unknown groups stay out of that cursor until their own base snapshot names a watermark. That is the whole protocol change: a group-scoped snapshot plus "apply the existing stream to published groups."

This is fundamental because §11 makes "is revision-qualified replay worth it?" the accept/or-reject question. The replay exists to freeze a cut the stream is forbidden to serve. It also reopens a security rule the current image was introduced to close: a historical payload is exactly the hidden or superseded row catch-up is not allowed to emit.

## 2. The open thread is not the offline screen

The shipped chat inbox is `memberships[viewer] first 50 by byPrincipalConversation`, composed with the conversation row and the maintained count. That is an ascending, cross-group read. The sync card says ascending reads and other indexes have unknown coverage, and a horizon-free group stays unknown until it is exhausted. §4.1 only mints a target when a query pins one audience group on its horizon index, so a mounted inbox neither becomes a local read nor names scheduling targets. §5.2 then keeps every cross-conversation read on the server until every required domain is covered.

Background work therefore walks declared groups fairly, in group-key order. §4.2 already says that is not account recency. The conversations on screen are the server inbox's ids. They never enter the queue. Memberships are the small domain (one row per member per conversation, no message horizon). Message bodies are the large one. The plan spends the first durable bytes on the large one.

On reopen offline, the honest inbox still cannot list a conversation, including one whose message suffix is already certified. A pinned route can show the thread the process happened to keep. A cold start cannot.

Exhaust the viewer's membership and conversation domain with today's whole-table acquisition before any deep `last 500`. Treat the conversation ids in the server inbox answer as the same internal hints §4.1 already allows for a mounted history query, and take a recent suffix of those groups before older history. Absence of a membership is the conversation list. A message floor cannot certify it.
