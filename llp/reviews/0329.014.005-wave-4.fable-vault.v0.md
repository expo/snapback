# Vault (1Password/Bitwarden-class) in v0.1 — paper archetype, wave 4 #2

Written against LLP 0329.014.000 v0.1 with the §9.1 rulings; constructs from LLP 0329.014.004 v1.1 are used as if in the spec and marked **(v1)**. Ceilings are unpublished; I assume **[inferred]** `G_examined = 10,240`. `exam≤N` counts index entries with halo (`take+2`); `W≤n` writes. Product caps: ≤ 64 field operations and parents per revision, ≤ 16 conflict domains per item, ≤ 256 recipient mailboxes per delivery, ≤ 32 devices per person, ≤ 32 group bindings per principal.

The design splits into two planes, and the split is the report. **S** is the server plane — accounts, mailboxes, blobs, receipts, one timer — an ordinary v0 data plane. **D** is the device plane — every table the design encrypts, which is every table with item semantics. `pv` = premise-violation, `nd` = new dimension; premises **F** store-wide offline fence · **R** rules the server evaluates · **A** one server authority · **O** trace as OCC/settlement · **C** trace as the offline closure.

### 2. Schema in v0

**S plane.** `authenticated()` is v1's authenticated-but-not-public spelling **[inferred name]**; `bytes({ maxBytes })` is v0's `json({ maxBytes })` — opaque to rules and indexes, which is the point.

```ts
// accounts { id, tier, quotaBytes } — read: member; insert: authenticated('signup'); update: admin, id immutable
// accountMembers { accountId, userId, role } unique byAccountUser, cap 65,536;  mailboxes { id, accountId, kind: device | group | recovery } cap 262,144
// mailboxGrants { mailboxId, principalId } unique — transport principals are devices; owner-written
// routeTokens { token: id() unique bearer (v1: possession is the rule input), mailboxId } — opaque delivery capability; read: never; owner-written
export const blobs = table({
  id: id({ contentAddressed: true }),                                                                    // §6 #4 — v0 has only random id()
  accountId: ref(accounts), ciphertext: bytes({ maxBytes: 4_194_304 }), paddedLen: int(), uploadedAt: time({ commitTime: true }), gcCapHash: text({ hashed, max: 64 }) })
  .rules({ read: b => db.exists(deliveries.byBlobPrincipal, [b.id, viewer]), insert: b => isAccountMember(b.accountId), update: never, delete: b => principal.kind === 'system' })
  .constraints(appendOnly({ except: 'gc' }), cap({ sum: 'paddedLen', by: 'accountId', maxFrom: accounts.quotaBytes }),
               check(b => b.paddedLen === b.ciphertext.byteLength && isPowerOfTwo(b.paddedLen)), rateLimit({ by: viewer, per: '1m', max: 600 }))
  .audited(into: fetchLog)                                                                               // v1: server-observed fetches — promise 7, not 19
export const deliveries = table({ id: id(), toMailboxId: ref(mailboxes), blobId: ref(blobs), pointer: bytes({ maxBytes: 256 }), routeToken: id(),
    deliverySeq: int({ sequence: by: 'toMailboxId' }) })                                                // v1 engine sequence — a TRANSPORT cursor; nothing on D reads it
  .index('byMailboxSeq', ['toMailboxId', 'deliverySeq'])                                                 // read: mailbox grant; insert: route-token possession
  .replica({ index: 'byMailboxSeq', order: 'asc', watermarkColumn: 'deliverySeq', maxBytes: 2 ** 34 })   // v1.1 — under the fence
maintain.sum(blobs, { by: ['accountId'], of: 'paddedLen', as: accountUsage, readable: b => isAccountAdmin(b.accountId) })   // K2 declared
// checkpointReceipts { mailboxId, root, receivedAt: commitTime } appendOnly;  releaseTokens { id (bearer unique), requestId } system-only insert
// releaseRequests { grantRef: hashed, delegateMailboxId, ownerMailboxId, requestedAt: commitTime, vetoMs, status: enum(waiting → vetoed | released) } — owner sets vetoed, system sets released
```

**What the server can and cannot evaluate over ciphertext rows — exactly.** It can evaluate (i) transport rules: mailbox grants and route-token possession — who may put bytes where and take bytes from where; (ii) plaintext-column constraints: content address equals digest (asset `verify`), padded length a power of two, per-account byte sum under quota, rate limits, append-only with system GC; (iii) time witnessing: `commitTime` receipts and one schedule; (iv) engine transport sequences per mailbox. It cannot evaluate any item-level rule — read, edit, share, delete, admin — nor head-ness, ancestry, authorship validity, epoch membership, tombstone state, or any per-item cardinality, because none of those is a column. Item-level rules are not `E_RULE_MISSING`; they are rules on tables that do not exist on this plane. If a designer materializes them (the `editItem` first attempt, §3), `check` admits every rule and program: **the language cannot state that the server is not in a table's audience**, because the server is in every column's audience by construction. That is the axis the schema cannot state (§6 #1).

**D plane** — declared inside the construct that does not exist:

```ts
export const vault = partition('vault', {                    // §6 #1
  authority: 'device',        // the running replica commits; no settlement, no OCC, no `rejected`
  horizon: 'unbounded',       // no maxOfflineAge for these tables; retention is causal (key epochs), never temporal
  serverProjection: 'blobs',  // the server holds this partition only as blobs/deliveries: opaque bytes
  transports: ['mailbox', 'peer', 'bundle'], merge: 'dag', ingest: ingestBlob })
// decrypted projections, all appendOnly: principals, identityCommits, governanceCommits, deviceCerts, principalEpochs, vaults, items { vaultId, itemAlias },
// policyCommits, policyGrants { itemId, subjectId, rights, historyFloor }, effectivePolicy { itemId, subjectId, rights, policyHeads, disputed }.versioned() (v1),
// removedSubjects, itemKeyEpochs, epochAncestry, envelopes, chunkRefs, branchBases { itemId, headId, baseId }, conflictDomains, purgeBarriers, recoveryPolicies,
// emergencyGrants, auditCheckpoints, deviceFrontiers, travelProfiles, siteReceipts, readEvents, ingestQueue { blobId, state, waitingOn }, outbox { revisionId, perPeer },
// fieldOps { revisionId, fieldId, domainId, op, ciphertext, tag } cap 64;  revisionParents { childId, parentId } cap 64;
// auditEvents { actorDeviceId, deviceSeq (device-authority), action, itemAlias, details, policyHead, mutationCommit, signature } chain on mutationCommit
export const revisions = table({
  id: id({ contentAddressed: true }), itemId: ref(items), kind: enum(['content', 'merge', 'tombstone', 'restore']),
  policyHead: ref(policyCommits), keyEpoch: ref(itemKeyEpochs), authorDeviceId: ref(deviceCerts), authorPrincipalId: ref(principals),
  authorSeq: int({ sequence: by: 'authorDeviceId', authority: 'device' }),                             // §6 #5
  previousDeviceEvent: optional(id()), claimedAt: time(), signature: bytes({ maxBytes: 128 }), state: enum(['accepted', 'conflicted', 'staleAuthority', 'invalid']) })
  .index('byItem', ['itemId', 'authorDeviceId', 'authorSeq']).unique('byAuthorSeq', ['authorDeviceId', 'authorSeq'])
  .rules({ read: r => hasRight(r.itemId, 'read'),
           insert: r => r.authorDeviceId === principal.device && r.authorPrincipalId === viewer && hasRight(r.itemId, 'edit'),
           update: (o, n) => principal.kind === 'ingest', delete: never })
  .constraints(appendOnly({ except: 'state' }), immutableExcept({ fields: ['state'], when: principal.kind === 'ingest' }), chain({ by: 'authorDeviceId', prev: 'previousDeviceEvent' }))
maintain.rows(heads, { from: revisions, key: ['itemId', 'id'], where: r => r.state === 'accepted' && !db.exists(revisionParents.byParent, [r.id]) })   // §6 #6
maintain.rows(headOpsByDomain, { from: fieldOps, join: heads, key: ['itemId', 'domainId', 'revisionId'] })
coupled(revisions, { onInsert: exactlyOne(auditEvents, e => e.mutationCommit === r.id) })                // v1 event-coupled: invariant 9
// externalChangeIntents { itemId, baseHeads, origin, oldCandidate, newCandidate, remoteReceiptHash?, state: enum(prepared → submitted → ambiguous | confirmed | abandoned) }
//   .constraints(coupledTransition({ to: 'confirmed', requires: exactlyOne(siteReceipts) }))            // v1 — invariant 20
```

`hasRight(item, right)` is `existsAny(effectivePolicy.byItemSubjectRight, { principalIn: viewer.bindings, key: [item, right] })` **(v1 N)** — the rule language fits device-side authorization exactly, once the rows it reads exist.

### 3. Operations in v0

**Server plane, common to every hard operation (transport).** `uploadBlob(accountId, ciphertext, to ≤ 256)`: `db.assets.verify(ciphertext)` **(v1)** returns digest, padded length and GC capability; insert the `blobs` row and one `deliveries` row per recipient carrying its route token. `exam≤262` (256 route-token probes + unique + halo); `W≤258`; prediction `conditional(cap, unique)` — honest, because the device cannot know the account total; `E_CONSTRAINT` is sealed.

`fetchMailboxSince` — first attempt `db.scan(deliveries.byMailboxSeq, [m], { take: 250000 })` for the design's 250,000 missing objects: `E_BOUND: examined 250,002 > G_examined 10,240 (product: take 250000 + 2). Rewrite: declare replica() on deliveries.byMailboxSeq and page after the watermark.` Corrected: `after: args.after, take: 500`, `exam≤502`, completeness `replica`; 250k objects are 500 admitted pages. `deliverySeq` is arrival order; invariant 4 holds only because no D-plane program reads it — §6 #8 would let the certificate say so.

`releaseAfterVeto` (op 11, delayed mode) — first attempt is a query returning `ctx.now() >= r.requestedAt + r.vetoMs`: `E_AMBIENT_TIME at ctx.now(): queries have no clock; "released after the veto window" is a durable transition. Rewrite: schedule(releaseAfterVeto, { at: r => r.requestedAt + r.vetoMs, key: r => r.id, principal: 'system' }) flipping status.` Corrected: a `callable: 'system'` mutation that returns if `status !== 'waiting'` (vetoed meanwhile — idempotent), otherwise sets `released` and mints a `releaseTokens` bearer row an effect delivers to the delegate's mailbox as a blob. The cleanest fit in the app: invariant 17's "named trusted time witness" *is* v0's system principal with `commitTime`; the design's insistence that delayed mode is not outage-independent is dimension B. Trustee mode never touches S.

**Hard op 1 — unlock, search, read, autofill offline.** `unlockKeyring` is a device seam. `searchItems` cannot be written honestly in v0: no `title` column exists anywhere the server can index. Written dishonestly — `items` with a plaintext `title` and `tokens('title')` — `check` admits it and promise 6 is gone. The honest form is the same query with `runsOn: 'device'`: `db.scan(items.byToken, [term], { take: 50 })` plus a `heads` point read per row, `exam≤52`, evaluated by the device over its own store (**[inferred]** whether the v0 client store maintains `tokens` locally; the server engine does — one reason the partition needs the server's storage engine on the device). `autofillCandidates` scans `items.byOrigin take 50`, reads `headOpsByDomain` for the credential domain, and returns `{ item, heads, conflicted: heads > 1 }`; the program cannot choose, because choosing is a `take 1` maximum — ruling 8's structural fact and invariant 4's violation at once.

**Hard op 2 — create or edit an item.** First attempt, on S, as an agent would write it: a server `revisions` table with plaintext `itemId`, `parents: json`, `authorDeviceId`, an encrypted `payload`, and `insert: r => db.exists(itemGrants.byItemSubjectRight, [r.itemId, viewer, 'edit'])`. `check` **admits** it — trap 2's cheat: the server now holds item ids, parents, authors, and evaluates `edit`. Nothing refuses it: `E_SECRECY_MIX` compares audiences among *principals*. Promises 6, 7 and 11 break silently (a member's page over `revisions.byItem` is an existence count). Classified product-change; boundary in §7. The honest `editItem(itemId, baseHeads ≤ 64, policyHead, ops ≤ 64, claimedAt)`, `runsOn: 'device'`: point-read the current item epoch; `require` every base head is in `heads`; `seq = ctx.deviceSeq()` (§6 #5); `record = canonical({ …args, keyEpoch, authorDeviceId: principal.device, authorSeq: seq })`; `revId = digest(record)` and `signature = device.sign(record)` (§6 #2); insert the `revisions` row with `previousDeviceEvent: ctx.previousDeviceEvent()`, one `revisionParents` row per base head (so `heads` moves in this commit), one `fieldOps` row per op, the `auditEvents` row with `mutationCommit: revId`, and the `outbox` row. `exam≤70`; `W≤131`; maintained amplification `heads −64/+1`. Invariant 9 — revision, dependencies, audit commitment, outbox in one transaction — is what a mutation *is*; the design states it as an obligation, the language makes it structural. Prediction is n/a: there is no `predicted`; the device commit is the commit.

**Hard op 3 — synchronize after any partition.** `ingestBlob(blobId, ciphertext)`, `runsOn: 'device', callable: 'ingest'`, per delivered object:

```ts
db.require(digest(args.ciphertext) === args.blobId, 'DIGEST')                                   // content address, verifiable on both planes
const env = device.open(args.ciphertext)                                                         // §6 #2 — null when no possessed envelope
if (env === null) { db.insert(ingestQueue, { blobId: args.blobId, state: 'locked' }); return }    // invariant 14: locked, never empty
const r = env.record
for (const p of r.parents) if (!db.exists(revisions.byId, [p])) { db.insert(ingestQueue, { blobId: args.blobId, state: 'pending', waitingOn: p }); return }
db.require(device.verify(r.signature, db.get(deviceCerts, r.authorDeviceId)?.signingKey), 'SIG')
// invariant 5: capability under the policy head THE REVISION NAMES, for THE AUTHOR — neither `viewer` nor the current head:
const ok = db.evaluate(revisions.rules.insert, { as: r.authorPrincipalId, asOf: r.policyHead, row: r })   // §6 #3 — does not exist
const stale = db.exists(removedSubjects.byItemSubject, [r.itemId, r.authorPrincipalId]) && !bridgedInto(r.keyEpoch, currentEpoch(r.itemId))
db.insert(revisions, { ...r, state: !ok ? 'invalid' : stale ? 'staleAuthority' : 'accepted' })  // promise 16; chain() refuses equivocation (sealed)
// then revisionParents and fieldOps rows; heads is maintained
```

`exam≤140`; `W≤130`. The 250k backlog is a device `job` over `ingestQueue` in 200-row chunks **(v1)** — the certificate bounds the program, the job bounds the backlog, and neither bounds a hostile peer's flood: that is quotas and rate limits on S, as the design's §6 says.

> **The eight-state machine at day 400, with local edits — exactly.** Under v0.1 + v1.1 as written, D-plane tables *never enter* the machine: the server holds no item row, so no certified query returns one; `readItem` is `hydrating` from day 0 with nothing to hydrate — unreached, not wrong. S-plane tables do enter it: `deliveries`/`blobs` reads are `stale`, offline uploads `queued`. At the fence — day 1 by the v0 default, day 7 or 30 by the hard maximum; `replica` and `retain` leases sit **under** it (RFC §2.1 F) — the store is sealed: reads become `hydrating`, pre-fence intents stay `queued` (v0 has no outbox age, §6 #9), and a post-fence edit cannot even be *predicted*, because the program's local reads are refused — there is no intent state for it. **Day 400 = reads `hydrating`, intents `queued`, and roughly 393 days of refused writes.** On reconnect the S plane recovers completely — every upload is an idempotent content-addressed append, so all `queued` become `committed`: *the blob plane survives an arbitrary partition under the ordinary contract*; only the item plane cannot. With §6 #1, D-plane reads are `local(frontier)` and D-plane writes are `committed` at the device, then carry a **per-peer vector** `queued → uploaded → delivered → accepted | conflicted | staleAuthority | invalid` — none `predicted`, none `rejected` (invariant 10 forbids rejection). Prediction 2's "gains an `authoritative-local` state" is wrong in shape: one added state cannot carry it, because the intent half of the machine presupposes a settling authority.

**Hard op 4 — resolve content conflicts.** First attempt finds the common ancestor by walking parents — `recurse(args.heads, id => db.scan(revisionParents.byChild, [id], { take: 64 }).map(e => e.parentId), { depth: 4096, fanout: 64 })` — and is refused: `E_BOUND: recurse bound 1 + 64 + … + 64^4096 (ruling 6) exceeds G_examined. Rewrite: the fork point is known when the branch is created — store it (branchBases) and point-read it.` The design already says a device "retains its own branch bases"; the strict language says why. Corrected `resolveConflict(itemId, heads ≤ 64, choices ≤ 16, preserve ≤ 16, ops ≤ 64)`, `runsOn: 'device'`: `require` every named head is in `heads` (invariant 11); point-read `branchBases`; per `conflictDomain` (≤ 16), scan `headOpsByDomain take 64` and `require` a choice or explicit preservation when more than one head touches it (promise 13); a tombstone head `require`s a choice too (invariant 13 — a decision, never a rule); then `editItem`'s tail with `kind: 'merge'`, `parents = heads`. `exam≤1,140`; `W≤131`. Determinism cuts both ways: two devices running the *automatic* disjoint-domain merge compute identical plaintext (the twin is byte-identical by construction), then each emits a differently keyed, differently signed revision — §8 #2.

**Hard op 5 — grant item-level access.** `grantAccess(itemId, subjectId, rights, history, historyEpochs ≤ 64, envelopes ≤ 256, newEpoch)`: `require(hasRight(itemId, 'share'))`; `require` no unresolved secret head (`take: 1` as an *existence* test, admitted); insert the policy child over the current policy heads (≤ 8), the grant with `historyFloor = newEpoch` for current-and-future (invariant 12), the rotated epoch, ≤ 256 envelopes, the audit event, the outbox intent — one commit, "granted locally; delivery pending". `exam≤300`; `W≤262`. Wrapping is `device.wrap`; the program never sees a key.

**Hard op 6 — revoke and bulk-rekey.** `revokePrincipal` signs the removal, inserts `removedSubjects` and a new root epoch: `W≤6`. `bulkRekey` first attempt loops `db.scan(items.byGroupAudience, [groupEpoch], { take: 100000 })` → `E_BOUND`; rewrite: a device `job` **(v1)** in 200-item chunks writing per-item checkpoints and a `rekeyCoverage` maintained count by epoch generation. "Removed from future policy" and "new epoch active" are immediate facts; coverage is the job's watermark — three facts, as the design asks.

**Hard op 7 — resolve concurrent policy changes.** `resolvePolicyConflict(itemId, headsA, headsB ≤ 8)` merges grant/removal operations from both branches (≤ 128 rows): apply every removal; apply a grant only if the other branch carries no removal of the *same subject*; demotion beats promotion by `min(rights)`; divergent group restructures are written `disputed: true` at the most restrictive rights; rotate the epoch if any reader was removed. `exam≤80`; `W≤3`. Nothing asks whether the op's *author* was removed in the other branch — §8 #1.

**Hard op 8 — delete, restore, purge.** Tombstone and restore are `editItem` with `kind: 'tombstone' | 'restore'` over every known head; "deleted here, edited there" is two heads in `headOpsByDomain`, one a tombstone — a decision by the `require` above, never a rule. `purgeItem`: tombstone if absent, `device.destroyKey(epochIds ≤ 1,024)`, insert `purgeBarriers` (append-only, kept forever), enqueue GC capabilities a job redeems against S's `forgetBlob`. `exam≤1,030`. The barrier is why an ancient device cannot resurrect: `ingestBlob` checks it before `accepted`.

**Hard op 9 — enroll a device.** QR/proximity is product code. Approving device: insert the non-expiring `deviceCerts` row, add the device to ≤ 32 principal epochs, governance child, audit, outbox: `exam≤40`; `W≤5`. New device: `fetchMailboxSince` pages plus `ingestBacklog`; "offline ready" is the replica watermark meeting the approving device's frontier — completeness `frontier`, never a page's `hasMore=false` (wave 3's completeness axis).

**Hard op 10 — recover.** Threshold reconstruction is a seam; then a recovery-generation governance commit, revocation of lost devices (op 6), personal-item checkpoints (a job). Two recoveries from one generation are two governance heads with `disputed: true`; `grantAccess` `require`s none — "pause privileged sharing" as a program fact.

**Hard op 11 — emergency access.** Trustee mode is entirely D: verify `emergencyCoverage`, collect ≤ 16 share rows, reconstruct via seam, install, write approvals and use events. Delayed mode is the S schedule above plus D redemption of the token blob. The design's asymmetry — outage-independent versus witness-dependent — is which plane each mode touches.

**Hard op 12 — travel mode.** Insert a travel `deviceCerts` row; the ≤ 1,000 item grants to it are a device job (inline would be `E_BOUND` at 1,000 × 262 writes); `require(exists(restorationReceipts.byCapsule, [digest]))` before the switch; one row (`activeProfile`) flips in the transaction and `device.destroyKey(ordinaryKeyring)` runs *after* it — physical erasure is best-effort, as the design says.

**Hard op 13 — audit checkpoints and maintenance.** A device job: per named device frontier (≤ 64), scan `auditEvents.byDeviceSeq` after the frontier `take 200` (`chain()` already refused equivocation at ingest; gaps are absences, reported), fold a Merkle root, insert `auditCheckpoints` with both parents when concurrent, then `recordCheckpointReceipt` on S. `auditReport(vaultId, frontiers ≤ 64, from, to)` scans the same index and returns `{ events, frontiers }`; its completeness must be `frontier(vector)` (§6 #7), because a page reported as "events in period" is the population fact wave 3 refused three times — promise 18 in the design's own words.

**Hard op 14 — change a password at an external website.** `prepareExternalChange` inserts the intent; the browser is a client-side effect the language does not have; `recordSiteReceipt` + `confirmExternalChange` run in one device mutation whose transition to `confirmed` is coupled to exactly one `siteReceipts` row **(v1)** — invariant 20 as a constraint; timeout writes `ambiguous` and both candidates stay. `exam≤6`; `W≤2` each.

**Read telemetry** (promise 19) is a device mutation labeled client-reported; no construct makes it stronger — product boundary. **Bundle and direct transfer** are `ingestBlob` fed by a transport other than S; the partition's `transports` is the only place this can be said.

Every item-plane number is not merely refused on S — it is *uncomputable* there. K2's machinery has nothing to declare over; the one server-side count a designer could write (anchors per vault) is the disclosure promise 11 forbids, and `check` would name it — given a plaintext anchor table the honest schema does not have.

### 6. Language delta

1. **`partition(name, { authority: 'device', horizon: 'unbounded', serverProjection: 'blobs', transports, merge: 'dag', ingest })`** with `runsOn: 'device'` on programs, `E_DEVICE_PLANE` (a server-plane program names a device-plane table) and `E_SERVER_AUDIENCE` (a device-plane table declares a plaintext server column). *Retracts, per covered table:* server execution, the trace as OCC and settlement, the closure receipt, `predicted`/`rejected`, and `maxOfflineAge`. *Keeps:* the language, the static certificate (now a device-evaluator bound), the schema vocabulary with constraints and `maintain`, the rule language, and local live queries (the trace as invalidation over the device's own store). *Cost:* the device needs the server's interpreter and storage engine (index maintenance, `tokens`, `maintain`), not the 7.8 KB twin — reversing D-A's "never a native module" for this partition. **General** (E2EE messenger, private-device agent, encrypted legal workspace). Amends §1, §5, §6, §10 D-A and D-D. **A new dimension, and not the same one as region or allocation**: those *delegate* a server's authority (the home region and the preallocated allowance still settle and can still refuse later); device authority is the *absence* of a settling authority, replaced by per-peer cryptographic verification. Authority placement has two regimes — delegated and cryptographic — and the wave's "one dimension, three faces" holds only for the first.
2. **Device crypto/keyring seam** — `device.open/sign/verify/wrap/unwrap/encrypt/destroyKey/random`, `ctx.deviceSeq()`, `ctx.previousDeviceEvent()` — the client-side mirror of v1's `seal/destroyKey/verifyMac/digest`. Runtime axis; without it every D program is `E_OPAQUE`. General. Amends §4.2.
3. **Rule evaluation under a named principal and policy version** — `db.evaluate(table.rules.insert, { as, asOf, row })` over `versioned()` policy rows: ingest evaluates the rule for *the author* at *the head the revision names* (invariant 5), not for `viewer` now. Construct; general (signed-log ingest, federation, wave 4 #8). Amends §3.
4. **Content-addressed ids** — `id({ contentAddressed: true })` with the engine check `id === digest(bytes)`; verifiable on both planes. Schema; general. Amends §2.
5. **Device-authority sequence and hash chain** — `int({ sequence: by, authority: 'device' })`, `chain({ by, prev })`; equivocation is a sealed `E_CONSTRAINT` at ingest. Schema; general to any signed log. Amends §2.
6. **Negated existence in `maintain.rows … where`** for derived heads; v0 `where` is field-only. Small; schema. Amends §2.
7. **Completeness `frontier(vector)`** beside `page|capped|maintained|all|replica`: a result labeled with the device frontiers it covers. General to DAG-replicated data; promise 18 and wave 3's completeness axis in one word. Amends §5.
8. **Column-level `independentOf('claimedAt')`** — v1 has table-level; invariant 4 wants the column. Small. Amends §5.
9. **`maxIntentAge` decoupled from `maxOfflineAge`** (dating asked first): S-plane uploads queued through a 400-day partition must never age out. Small. Amends §6, §10 D-D.

Not a language item: a client-side effect kind for the browser and the QR channel — product code. **Prediction 2, tested:** held on the fence being the wrong instrument, on client-side resolution, and on the server never evaluating item rules (stronger: it cannot hold an item row). Did not hold on "per-item vector clocks" — the right primitive is a hash-linked DAG with per-device sequence chains; vector clocks are infeasible at 150,000 devices with no dead-device assumption — nor on "gains an `authoritative-local` state" (op 3 box), nor on "device is one face of the region/allocation dimension" (item 1).

### 8. Where the design is wrong

1. **A concurrently removed grantor's grants merge in.** Op 7 step 1 merges "operations on unrelated subjects"; promise 14 orders removal over grant *for the same subject*. Alice (admin) grants Carol `edit` on device A while Bob removes Alice on device B, both from policy head P0. Carol is not Alice; the rule commutes them; Carol has `edit` from an actor the merged policy says was removed — invariant 8 ("never broaden by union") broken by the design's own commutation rule. *Observation:* two devices at P0; A grants Carol; B removes Alice; reunite; read Carol's rights. Fix: an op's author must hold the right in the *merged* policy, not the ancestor — policy merge is author-aware, and the strict program is where that was visible.
2. **Materialized auto-merges create equivalent sibling heads.** Op 2 says "only disjoint conflict domains may auto-merge" and op 4 step 5 creates a merge revision — never saying whether automatic merges are materialized. Every device computes the same plaintext (deterministic program), then wraps it under a fresh revision key and its own signature: N devices, N distinct content-addressed merge revisions with the same parents; `heads` holds N equivalent heads the next merge must name. *Observation:* two online devices, the same two disjoint heads, both auto-merge; count heads after sync. Fix: derive automatic merges at read and materialize only human resolutions — or coalesce heads by parent set, a rule the design does not state.
3. **Item discovery versus promise 11 is unspecified.** An authorized device must learn that item X exists. Either every delivery is per item-audience (fan-out proportional to item × audience-device — the design's most-feared cost, group mailboxes the only relief) or a vault-level index under the vault key tells every member about items they cannot read. The data model hedges ("inside encrypted records when hiding grouping matters"). *Observation:* enroll a vault member with no item grants and capture their mailbox; create ten items; count deliveries. More than zero is an existence leak to the client, which promise 7 does not cover.
