This proposal largely implements the authorized model. Activation stays over current data. No new exposure confirmation is added. Down synthesis stays explicitly authored.

Atomic selection: reverse reads the assembled newer source before visibility closure, on one snapshot, with simultaneous projections isolated from each other. Forward retains exact newer cells plus reverse result in the same transaction, then restores only verified fields. Previews use MAIN tables in a private disk snapshot. Inspection snapshots are read-only operator views. This matches the current-data baseline.

Authorization: predicate-only rollback preserves captures and does not recapture a broader grant. Preview warns about broader old rules but does not block. Down/rename are declared only. Types do not establish applicability. This matches the preserved same-UID owner model.

Three ambiguities block safe implementation.

1. Nullable down spelling is missing.

The text gives only asserted form: `(explanations[extension = id] ! else MISSING_REASON).explanation`.

It then relies on a second form: an ordinary nullable point may return null only where explicitly allowed. No nullable spelling is defined.

Counterexample: old `reason` is intentionally null and newer has no `explanations` row. With only `! else` defined, the author must write a refusal. Rollback aborts though null is truthful. If an implementer guesses a bare lookup means nullable, then a required `legacyReason` missing row silently becomes null. That is false absence.

Smallest correction: define both spellings or cite the existing nullable point-read form. Require admission to reject a down point read that specifies neither an asserted refusal nor explicit nullable. State that bare lookups are never admitted in `down`.

2. Reverse-writer disjointness scope is ambiguous.

The text says reject overlapping declarations before any adoption work. It also says a declaration applies only when the selected target contains its named output, rechecked at admission and every activation.

Counterexample: newer source `S` has `down A` writing `T.reason` for old release `R1`, and `down B` writing `T.reason` for old release `R2`. No activation ever applies both together. A global pre-adoption overlap check falsely rejects `S`. Conversely, static single-writer plus per-cell preimage/native precedence are conflated by: at most one reverse writer after saved forward-preimage/non-null-retained precedence. Precedence is runtime per-cell selection. It is not a second writer.

Smallest correction: define overlap per co-applicable triple of declaring source, target release, table and field. Check known retained targets at admission. Recheck the actual candidate/target pair at every activation. Name both declarations and the field. Clarify that preimage/native rules select the per-cell source at runtime and do not permit two declared writers for one co-applicable cell.

3. Rename identity and lifetime move are under-specified.

The text admits only identical cell types. It permits moving a legacy field to a related table. It says a rename moves lifetime evidence unchanged and cannot create a binding.

Counterexample A: `text 1..500` renamed to `text 1..100`. Same base type, different bound. If treated as identical, values truncate or fall into narrowed dormancy silently.

Counterexample B: field moves from a row under parent `P` to a related row under parent `Q`. Carrying `P` evidence unchanged into `Q` leaves expiry ambiguous. `P` expiry may no longer clear it. `Q` expiry may wrongly clear it.

Smallest correction: define identical as fully identical type expression including bounds, nullability, defaults and constraints. Any conversion needs a separate transformation. Require a rename to preserve the same lifetime parent identity, or refuse cross-parent moves unless a bridge proves preservation and expiry/deletion clearing stays bound to the original parent.

These are implementability and correctness gaps, not a request for a new approval gate.
