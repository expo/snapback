## Direction check of LLP 3000.008.002.000 — Grok 4.7 (xhigh)

**Verdict:** RIGHT WITH CORRECTIONS

### Summary

The RFC is aimed at the right class of problem: these failures are client lifetime and paved-recipe mistakes, not missing durability, and it correctly refuses a second outbox, a result cache, a media cache, and a private copy of ephemeral tables. Two corrections change what to build tonight. The Clique "leave still counts as unread" test follows the grader's half-sentence and contradicts the brief, so it must not be implemented. The web chat starter already contains most of the §3–§4 composition; the run that motivated the RFC followed the package README and the `reads` card on an Expo Router app, and those paved texts still teach the two patterns that broke.

### Findings

#### F1 (High) — Clique leave-receipt policy is the opposite of the brief

- Where: RFC §5 (lines 150–154) and the acceptance row "Recipient leaves without reading" (line 216); `benchmarks/briefs/social-messenger.md:500-507`; grader `grading/trace.md:577-588`; builder `snapback/schema.q:223-229`
- What is wrong: The RFC treats grader defect d-01 as the brief's send-time contract and says leaving must not count as reading. The brief's own sentence says both things: the recipient set starts as membership at send time, **and** members who leave or are removed before reaching a state drop out of the aggregate requirement. The builder's `receipt()` does that. It mins over current members and skips anyone whose `joined` / `joinedOrdinal` is after the message. Carol leaving unread raises the aggregate because she left the requirement, which is what the second clause specifies. The grader quoted only "membership at send time" and called the advance a false "read by all."
- Evidence: Diary M3 (`diary.md:10`) records the same rule the schema implements: removed members stop contributing to the minimum. Checklist assertion `m3-a09` stayed green; d-01 is an extra probe outside that scenario (`grader-report.json` note on `m3-a09`). Later joiners are already excluded, which is the send-time half.
- Proposed change: Keep "the schema states the recipient set; a client helper must not change it." Delete the instruction to pin leavers, and delete an acceptance expectation that an unread leaver still blocks "read by all." For Clique, the test is: a leaver who had not reached the state drops out; a member who joins after send never enters the set. Do not "fix" `receipt()` to min over frozen delivery rows.

#### F2 (High) — The run followed the README and the reads card, not `apps/chat`

- Where: RFC §1 (lines 49–51), §7.2, §9 (lines 242–244); published README still at `snapback4/packages/snapback4/README.md:147-172`; `snapback4/crates/snapback4-lang/src/guide/reads.rs:95-128`; evidence `app/_layout.tsx:41-54`, `src/Pending.ts:46-49`, `src/Conversation.tsx:77-89` versus `snapback4/apps/chat/src/Composer.tsx:23-47` and `App.tsx:94-110`; Expo starter `snapback4/apps/chat-expo/src/Thread.tsx:15-22` and `App.tsx:58`
- What is wrong: "The builder attributed most corrections to agent error" is true of the log, and it is the wrong premise for where to edit. Two paved texts are the pattern the builder executed.
  - `reads` on published 0.4.2, and the same card on this tree, presents a typing indicator as a durable `expire at` upsert of `now + 4500`, with no mention that a keystroke is an outbox write. The M3 loop (`run-log.md` epoch 1790387112) was throttling that recipe so a backlog could not extend the indicator past 5 seconds. LLP 3000.017 already calls this the repeated failure. It is a guide defect, not an agent invention.
  - The README profile sample sets `busy` from `inFlight || last?.state === "pending"` and disables the button for the whole pending interval, then `await place.run(...)` without reading the returned write. That is the M6 "composer waited for settlement" pattern (`Conversation.tsx` media path still does; the text path was later fixed). The sample also renders a profile query as "Loading…" with no warning that a transient not-ready read is not sign-out. The builder lifted that into a gate that unmounted `<Slot />` until `myProfile` had data (`app/_layout.tsx:41-54`; run log epoch 1790386882).
  - `apps/chat` already admits with a saved id, clears the draft on non-failure (including `pending`), shows unknown rather than inventing failure, and opens a room by held lookup instead of `createDM` (`App.tsx:97-98`). The evidence app did not start from it. It is Expo Router plus `AppProvider`, the README's shell. `init --expo` copies `chat-expo`, whose thread blocks while `send.inFlight`, does not pass a saved id to `usePendingWrite`, and is unmounted by Back. The web composer still has a real hole: keystrokes during `await mutate` bump `revision`, so the submitted text is left in the field (`Composer.tsx:43`).
- Evidence: Holistic 92 / queries 88 / client integration 86 are the same-family score in `scores/astra/FINAL.md`, whose setup note says no misleading documentation was established and whose deductions exclude agent error. The independent grader is O1 78, O2 86, O4 55 (`grader-report.json:850-864`), mostly for missing native proof and M7, not for these UI loops. The RFC is right that those numbers are not acceptance criteria. It is not right that the attribution log clears the paved docs. There is still no missing write API: `useMutation.last`, `usePendingWrite(op, id)`, and `client.write(id)` existed and the web starter uses them. The evidence app's own recovery then labels a missing receipt `failed` (`Pending.ts:46-49`). Do not copy that. The law in RFC §2 is the one the web receipt list already states.
- Proposed change: Treat §7.1 as "which of these still fail on the README sample and on `init --expo`," not as a reason to re-author `apps/chat`. Change the README busy expression and the route-gate warning. Label the durable typing example as the workaround with different semantics. Bring the Expo thread up to the web composer's saved-id and unknown-receipt behavior. Fix the revision snapshot in both composers. Do not add a submission primitive until that reproduction shows a lifecycle the existing pending-write id cannot cover.

#### F3 (Medium) — A client watermark cannot enforce the gap rule this schema already violates

- Where: RFC §5 (lines 138–142) and the "Sparse visible messages" acceptance row (line 215); evidence `snapback/schema.q:223-229` and `:289-302`; brief `social-messenger.md:500-502`; builder ack effects `src/Conversation.tsx:72-76` and `src/Chat.tsx:52-62`
- What is wrong: The reproduced bug was an effect re-firing when `usePage.items` went empty and came back (epoch 1790386760), plus the profile gate unmounting the reader. The brief's read event is "recipient viewed the conversation," not per-row visibility. The builder's server operation already gap-crosses: `acknowledge` writes `readOrdinal` to the max ordinal in the batch, and `receipt()` treats every earlier message by that member as read. A client helper that sends explicit ids, or one max id, cannot keep the RFC's promise. A visibility or IntersectionObserver helper is more machinery than the evidence needs, and a max-visible-id watermark would mark the unloaded prefix read on this schema.
- Evidence: `usePage` concatenates only ready pages and stops at the first not-ready page, so a not-ready first page publishes `items: []` (`snapback4/packages/snapback4/src/react.tsx:175-178`). The reads card only promises that earlier pages stay visible while a later page is unavailable (`guide/reads.rs:61`). That matches the flicker the builder deduped with an in-memory set. It is not proof that a new acknowledgement type is required.
- Proposed change: Ship one recipe: remember ids already submitted for this backend, viewer, and open conversation, above the list, and do not re-send them when `items` flickers. Leave contiguous-watermark legality in the mutation. Do not add a hook until that recipe is still repeated machinery. Do not build a visibility subsystem in this increment.

#### F4 (Medium) — The view-once fix is "hold the asset handle above the list," and `useAsset` will revoke a lifted URL

- Where: RFC §6 (lines 171–178); `snapback4/packages/snapback4/src/react.tsx:369-398`; evidence `src/Conversation.tsx:313-324` and `:217-227`
- What is wrong: The RFC is right that no new media cache is justified, and slightly easy to implement wrongly. `useAsset` revokes the blob when the hook unmounts or the id changes. Copying `url` up and letting the row unmount revokes the only legal view; a second `client.asset` of a one-view photo is the denial. The fix that actually passed M5 does not use `useAsset` for the one-view photo. `Bubble.open` calls `client.asset`, then `onOnce` stores that handle on `Conversation`, which stays mounted when the row drops.
- Evidence: Diary M5 (`diary.md:19`) and epoch 1790388135. The parent effect revokes that handle on viewer change and unmount (`Conversation.tsx:66`). Keeping the row mounted is not required. Keeping the `AssetRead` is.
- Proposed change: Document that recipe next to `useAsset`. Do not add a cache, a second fetch, or a sticky protected image. Sign-out, revocation, expiry, and consumption still revoke. Step 1 only proposes an SDK extension if a handle that outlives the row is impossible with `client.asset`; this run shows it is possible.

### Recommended implementation increment

1. **Label the durable typing recipe, and stop there.** `snapback4/crates/snapback4-lang/src/guide/reads.rs` (the "for example, this typing indicator" paragraph) and the pointer in `CLIENT-AND-OPERATIONS.md` around the same example. Small. Say that each keystroke is a durable outbox write, a backlog extends the indicator, offline calls must not replay as current typing, and LLP 3000.017 owns the replacement. Verify with the guide-card compile test and `snapback4 guide reads` showing the warning. Do not implement ephemeral tables, coalescing, or a typing primitive on this branch.
2. **Correct the paved README sample the run actually copied.** `snapback4/packages/snapback4/README.md` profile section. Small. `busy` must not include `last.state === "pending"`; show pending, sent, and failed from `.last`; say a loading or incomplete profile read is not sign-out and must not replace the router. Verify by inspection against `app/_layout.tsx:41-54` and the M1/M6 log lines: the sample no longer matches the failing patterns.
3. **Expo thread parity, plus the draft-snapshot hole in both composers.** `apps/chat-expo/src/Thread.tsx`, `apps/chat-expo/App.tsx`, `apps/chat/src/Composer.tsx`. Medium. Save the mutation id, clear only the submitted revision (keystrokes during admission stay, without the submitted sentence), keep an unknown receipt unknown, and do not unmount the draft because Back or a loading query ran. The web starter's held room lookup stays as it is. Verify the three §8 composer rows (storage rejection, three offline sends, navigation immediately after admission) against these two files. No new mutation API.
4. **One optional-badge recipe, not a split of the safe starter count.** A short addition to the reads card, pointing at the evidence split `schema.q:233-236` and `src/useInbox.ts:4-24`. Small. A coverage-sensitive unread total is a separate read, renders unknown rather than zero, and must not gate the conversation list. Do not hold the last protected total in a ref the way `useInbox` does. Do not split `apps/chat` `inbox()`'s `messageCounts` card: that schema already says the count is a local fact (`apps/chat/snapback/schema.q:70-80`). Verify the card text states both cases.
5. **Acknowledgement dedup recipe, and the view-once handle note, as docs next to the existing hooks.** Reads card or the chat README, plus the `useAsset` comment in `react.tsx`. Small. No new exports until a later reproduction still needs them.

Before any SDK change, one probe only: whether a current `observe()` of the first page still publishes not-ready and thus empties `usePage.items` (`react.tsx:177-178`). If the client already holds the previous answer with `fresh: false`, do nothing. If it flickers to loading for the same viewer, the narrow fix is a same-subscription last-ready hold that drops on denial, sign-out, or principal change. That is not a query-result cache, and it is not this increment unless the probe reproduces it.

**Do not build:**

- LLP 3000.017's ephemeral engine, renewal lane, or "coalesce mutations" helper. The §6 hand-off is sound; 3000.017 already cites this run (`llp/3000.017-ephemeral-tables.rfc.md:88-93`).
- A second outbox, or the evidence app's rule that a missing `client.write` result is `failed`.
- A protected-result cache, sticky unread counts, or a media-byte cache.
- An IntersectionObserver or watermark hook. Gap safety is not enforceable in the client for the evidence `acknowledge` mutation, and the leave test in F1 is the wrong oracle.
- A generic replacement for `useMutation`.
- A schema change that keeps an unread leaver inside the Clique aggregate.

### What the RFC gets right

The responsibility split is the right one: the SDK already admits, recovers, and reports `pending` / `sent` / `failed`; starters own presentation; the application schema owns who is in a receipt set. "Compose current APIs until a lifecycle cannot be owned safely" matches this packet. Predicted rows are labeled `pending` and are not a settlement receipt (`essay.md:31`; web `Thread.tsx` already says "Sending…"). Held navigation already exists and should not be reinvented. Loading is not authority loss, and preserving a component is not permission to keep its last protected result. The view-once bytes must not be copied into a general cache. No new readiness gate, router, or retry queue. The §6 refusal to duplicate ephemeral work is the correct boundary with the other branch.
