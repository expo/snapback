# Review: LLP 0107 — Generated query-group bundle adoption (round 1)

**Summary judgment:** The document has the right architecture — a narrow profile that composes codegen references, the LLP 0090/0092 register-mode bundle, and the LLP 0114 provider without inventing a transport, cache, or authority source — and its safety posture (never-downgrade on failure, capability honesty, successor-never-adopts) points the right direction. But it is not yet a contract two independent implementations would converge on: several of its pinned numbers and validation rules contradict the governing owners it cites, its only sanctioned fallback trigger has no defined mechanism anywhere in the corpus, its generated-identity derivations are named but not pinned (and the repository's own two implementations already disagree on the hash bytes), and its relationship to LLP 0114's normative "Post-bakeoff implementation extension" — which covers the same surface with conflicting details — is undeclared.

## 1. What holds under stress

- **Layering and capability honesty.** The profile claim (llp/0107:21–25) mostly holds: no new transport, cache, credential carrier, or authority source; registered boot framed as "a startup-consistency fact, not offline or local-first support" (llp/0107:181–182) is exactly consistent with LLP 0064's Online/Parity ladder (0064:212–221) and LLP 0012's no-silent-fallback rule (0012:532–533).
- **Single-commit, no-duplicate-snapshot adoption.** The core mechanism is soundly grounded: LLP 0090 D4 pins that the register-mode bundle *is* the LLP 0053-mandated fresh snapshot with subscriptions created at the same cut (0090:760–765), so publishing bundle rows as authoritative and attaching without a second snapshot-with-subscribe respects 0053's mandatory-resnapshot rule rather than evading it. The headless client genuinely implements this (`adoptRegisteredSubscription`, packages/snapback-client/index.mjs:7346–7414) with wire-level tests proving no `/subscribe` and no second `/connection/open` (packages/snapback-client/bundle.test.mjs:156–218).
- **One request, fresh idempotency key.** "At most one register-mode bundle request for one preparation" with a fresh bundle-boot key matches 0092 §0D.3's per-boot-attempt minting (0092:386–388); forgoing the retry affordance is a legitimate narrowing.
- **Pre-mount acquisition.** Preparation before provider creation matches 0102's rationale that effect-time register requests strand pending registrations (0102:406–411).
- **Authority-fencing intent.** The invariant "a successor authority never adopts predecessor rows, subscriptions, grants, or resume coordinates," with release through the existing connection owner, is the correct projection of LLP 0012's AuthCoordinator compare-before-publication model (0012:710–716) and LLP 0034's dispose/settle posture (0034:931–948).
- **Provenance honesty.** Refusing post-boot atomicity claims (llp/0107:47) matches 0102's boot-is-provenance rule (0102:398–404).
- **Evidence shape.** The six-item acceptance list is finite and nonvacuous in structure — notably requiring a real-adapter receipt distinct from package fixtures (llp/0107:221–223) and a packed cold install.
- **Rollout/rollback.** Additive rollout retaining name-based paths, and rollback preserving the 0090 endpoint with format-versioned artifacts, are coherent.

## 2. MATERIAL concerns

**M1. The child-count bound (64) contradicts the governing bundle contract (32).**
llp/0107:117 admits "one through 64 ordered children," but LLP 0092 pins **32 queries per bundle (= per route entry)**, refused with `SNAPBACK_BUNDLE_LIMIT_QUERIES` and *also refused at route-manifest ensure* (0092:345–355), deliberately below the 64-per-connection subscription ceiling "so a register-mode bundle can never arm more demand than its socket may hold." 64 is LLP 0114's *React object-map group* cap (0102:373, 878) — a different surface. Every implementation seam already enforces 1..32 (codegen `ROUTES_QUERY_COUNT_INVALID`, packages/snapback-codegen/index.mjs:3893–3894; binding, packages/snapback-client/react-binding.mjs:347–348; schemas/routes.manifest.schema.json).
*Failure scenario:* an implementation built from 0107 admits a 40-child group, sends the request, and the server atomically refuses — defeating 0107's own goal "refuse … oversized groups **before** a bundle request" (llp/0107:32–33) and breaching its non-goal "broaden LLP 0090's bundle bounds" (llp/0107:53); two implementations (one reading 0107, one reading 0092) disagree on admissibility.
*Resolution:* change to 1..32 citing 0092 §0D.2, or state the bound symbolically as the served target's bundle query cap (default 32).

**M2. The registered-response validation rules conflict with 0092's closed per-entry union.**
llp/0107:137–138 requires "one subscription id, exact result rows, version, and **resume coordinate per child**," and the goals list preserves "resume coordinates" (llp/0107:36–37). But 0092 pins `resume: null` for non-`rqsEligible` entries **and for all auth-scoped register-mode entries** (0092:302–316, restated in Conformance, 0092:937–940) — and auth-scoped children are the *normal* case for the authenticated boot register mode exists for. Three further gaps in the same rule set: (a) the per-child `version` in the inspection shape (llp/0107:151) has no response-level source for `resume: null` entries — version exists only inside the resume token body; the only guaranteed version is the bundle-level `commitVersion`; (b) 0092's dated amendment pins a mandatory `authorization: {scope, invalidation}` field on auth-scoped register entries (0092:709–713), which 0107 never mentions while requiring "no unknown … entry" (llp/0107:132) — a validator written from 0107 alone rejects conforming responses; (c) the response↔child **correlation rule** is undecided: 0092 returns entries "one per querySpec, manifest order" (0092:293), and since 0107 explicitly supports repeated functions via occurrence suffixes, identity-keyed matching (which the current code uses, react-binding.mjs:158–160) cannot distinguish two same-function-same-args children, while positional matching can.
*Failure scenario:* implementation A (strict per-0107) refuses every group containing an auth-scoped child or an `authorization` field; implementation B accepts them; a group with a repeated child at identical args validates under positional correlation and refuses under identity correlation.
*Resolution:* define "resume coordinate" as the per-child `resume` value present iff `rqsEligible` (else null is conforming); source per-child `version` from `commitVersion` or drop it; enumerate the `authorization` field as expected; pin manifest-order positional correlation.

**M3. The sole fallback trigger — "the target explicitly reports that register-mode bundles are unavailable" — has no defined mechanism, and the surrounding normative texts disagree three ways.**
No owner defines a register-capability report: 0092's error registry has no capability code (0092:359–375); on the one arm where register mode is genuinely absent, the wire signal is `SNAPBACK_BUNDLE_REGISTER_REQUIRES_CREDENTIAL` (0092:861–870) — the same authorization-class code 0107:175 forbids from ever downgrading; and the runtime contains no `SNAPBACK_BUNDLE_REGISTER_UNAVAILABLE` (it exists only as a fake code invented by packages/snapback-react/package.test.mjs:475). LLP 0012 pins the capability manifest as a **server-declared single source** with no bundle/register axis (0012:535–555), so adding one is a real owned contract change, not something a "narrow additive profile" gets for free. Meanwhile LLP 0114's normative extension blesses fallback on *any* "coded `SNAPBACK_BUNDLE_*` target refusals" (0102:1267–1268) — which is what the implementation does (prefix match, react-binding.mjs:537–543, recorded as intended in issues/closed/20260727-typed-live-query-groups.md) and what 0107:175–177 expressly forbids; and 0092 pins the client response to the credential refusal as "retries in read mode" (0092:368), a path 0107 does not model.
*Failure scenario:* against a register-incapable target with `fallbackToLive: true`, implementation A (0107-literal) finds no capability report, classifies the 403 as authorization, and hard-refuses — making `fallbackToLive` dead code; implementation B (0102-literal) falls back on `SNAPBACK_BUNDLE_QUERY_FAILED` and `_LIMIT_*` too, which 0107 calls forbidden downgrades.
*Resolution:* name the concrete capability channel (a declared axis on the LLP 0012 server-declared capability manifest, owned via a dated amendment) and/or pin the exact refusal code(s) that constitute the capability-absence signal, decide the classification of `REGISTER_REQUIRES_CREDENTIAL`, and declare precedence over 0102:1267–1268 (updating 0102 in the same change).

**M4. Generated-identity derivations are named but not pinned — and the repository's own two implementations already disagree.**
The definition hash is specified only as "the generator's framed canonical encoding" (llp/0107:78–80). No such pinned artifact exists: codegen hashes the domain line plus **pretty-printed 2-space `stableJson`** (packages/snapback-codegen/index.mjs:5596–5598, 6417–6428), the binding recomputes over **compact RFC 8785 JCS** (`canonicalizeClientValueV1`, react-binding.mjs:385–387), and the generator's actual framed encoder (`sha256Framed`) is used by neither. Different bytes → different digests → the binding's canonical-equality admission (react-binding.mjs:454–470) refuses every codegen-emitted group with `SNAPBACK_REACT_GROUP_REFERENCE_INVALID` — the exact documented usage (guide/clients/react.md:86–90; demos/signal-desk/src/backends/snapback.ts:51–55). The group-id derivation (`${appId}:query-group:${route}`) and the occurrence-suffix scheme (`feed`, `feed2`, …) are likewise unpinned even though child names are **public typed API** (result keys in `GeneratedQueryGroups` and the inspection map), and no rule addresses a suffix colliding with a real function named `feed2` — despite admission item 6 requiring unique child names.
*Failure scenario:* is already realized in-repo: two conforming-looking implementations of the same spec sentence produce artifacts that refuse each other; independently, two codegens produce incompatible typed surfaces from the same route source.
*Resolution:* pin the exact encoding (domain string, canonicalization, framing) by name with a shared cross-package parity fixture; pin the id derivation and the suffix rule; add a refusal for derived-name collisions.

**M5. The relationship to LLP 0114's normative "Post-bakeoff implementation extension" is undeclared, and the two documents disagree on the same seam.**
0107 presents itself as filling a gap "added after LLP 0114's terminal review" (llp/0107:22–25), but 0102:1234–1272 already normatively covers generated group references, `prepareQueryGroup`, register-mode adoption, and `fallbackToLive` — with conflicting details: signature and parameterization (`prepareQueryGroup(reference, params)` with "typed route parameters" and wrong-parameter refusal, 0102:1244–1255, versus 0107's canonical-empty-object V1 that refuses parameterization, llp/0107:107–109 — the implementation, declarations, and guide all follow 0102's parameterized form); unconsumed registrations ("remain owned by the same connection and are removed by provider disconnect," 0102:1264–1265, versus "partial consumption refuses," llp/0107:163–164); grant custody ("retains no returned grant secret," 0102:1258, versus 0107's "preserve … grant"/"not exposed by inspection," llp/0107:36–37, 155–156); and the fallback trigger (M3).
*Failure scenario:* two implementers each pick a document; they build incompatible public signatures and opposite unconsumed-registration behavior, both citing normative corpus text.
*Resolution:* one precedence paragraph — state exactly which 0102 sentences 0107 supersedes or narrows (and land the 0102 pointer in the same change), and resolve params-in-V1, partial-consumption semantics, and grant custody in one direction each.

**M6. The prepare→mount window against `attachDeadline` is unspecified, and the unscoped "expiry never downgrades" clause collides with owner-mandated attach behavior.**
0092 pins a 30 s default attach grace window, exact enforcement at attach, refusal with `SNAPBACK_CONNECTION_TOKEN_INVALID` (outside the bundle namespace), and — normatively — "the client falls back to an ordinary connection open + fresh subscribes" (0092:414–422, 714–719). 0107 never mentions `attachDeadline`; its only expiry check runs at response verification (llp/0107:137–138), and its blanket "expiry … never downgrade[s] to live fallback" (llp/0107:175–177) is unscoped, so it reads as contradicting the owner's mandated post-deadline fallback.
*Failure scenario:* a prepared capability sits 35 s before mount (slow route transition, breakpoint, HMR pause); implementation A follows 0092 and silently continues via fresh subscribes; implementation B follows 0107's never-downgrade wording and hard-fails the provider; the spec decides neither, and its evidence item "zero ordinary snapshot requests after adoption" is unsatisfiable in this legal case.
*Resolution:* scope the never-downgrade rule explicitly to preparation-time outcomes; adopt 0092's attach-time behavior by citation; state what the group's reported source/boot means when deadline lapse forces fresh subscribes.

**M7. The authorization-barrier participant is attributed to the wrong owner.**
llp/0107:193–195 registers "the existing LLP 0053 authorization-barrier participant," but the registerable client participant contract — `registerParticipant(participant: AuthBarrierParticipant)`, the quiesce/blank/resume phase obligations, and the unregistration-joins-completions rule — is LLP 0059's (0059:1872, 1953–1968, 2020–2024). LLP 0053's "barriers" are server-side commit-ordered room/dependency-ticket barriers (0053:44, 701–719), not a client registry. 0102 cites it correctly as "one LLP 0059 barrier participant" (0102:1139–1141, 1278–1279); 0107's Related line omits LLP 0059 entirely.
*Failure scenario:* an implementer following 0107 searches LLP 0053 for a client participant registry that does not exist, or wires the wrong mechanism, on exactly the seam that fences authority replacement.
*Resolution:* retarget the citation to LLP 0059's `AuthBarrierParticipant` seam, add 0059 to Related, keep 0053 cited for invalidation-fence authority.

**M8. The `userId` dev-identity option lacks the owner's gates and is not bound into the authority fence.**
0102 defines the dev seam as `devPrincipal` **at provider construction**, admitted only when the target reports the local-dev profile, refused on sessions/hosted targets, and synchronously blanked on custody transition (0102:942–947); hooks accept no identity (0102:108–109). 0107 moves identity to a per-preparation option on the request that mints registrations — a credentialed-only operation (0090:436–440) — with none of those gates, and never states that the principal participates in the prepared group's fence identity (the generation fence in llp/0107:185–187 sees only the client authority snapshot, which a per-request field bypasses).
*Failure scenario:* a group prepared with `userId: "alice"` (auth-scoped rows and subscriptions minted as alice) is adopted by a provider whose ambient dev principal is bob; no fence trips, and bob renders alice's registered rows — violating 0107's own "successor never adopts predecessor rows" invariant in the dev profile, and setting the seam pattern a hosted arm would inherit.
*Resolution:* copy 0102's three guards (local-dev-profile admission, hosted/session refusal, custody-transition blank) and state that the supplied principal binds into the prepared group's admission/fence identity, verified again at adoption.

## 3. DETAIL concerns

- **"Non-query" should be "non-live-query."** Codegen admits `Query`-kind route children (index.mjs:3901–3903); the binding refuses them at prepare (react-binding.mjs:489–496); 0102 pins "non-live child" refusal. 0107's word "non-query" (llp/0107:31) underspecifies this.
- **Sessions-arm scope.** 0092's step-7 note records that registered adoption under the negotiated auth-invalidation protocol currently falls back to an ordinary fresh subscribe (0092:822–825; implemented at index.mjs:7347). 0107 promises no-second-snapshot unconditionally; it should scope V1 targets or explicitly own wiring the `authorization` projection into the client fence path.
- **"Stable synchronous admission error"** (llp/0107:124) vs the `Promise`-returning signature: pin throw-vs-reject (the load-bearing part — stable code, no request — is right; the observable delivery mode should still be one thing).
- **"One positive common `commitVersion`"** (llp/0107:135): confirm a fresh store cannot legally report commit 0; if it can, "positive" wrongly refuses first-boot bundles (the implementation accepts ≥ 0).
- **Inspection-surface exactness.** The spec's flat inspection shape vs 0102's `boot`-nested vocabulary (and `"live-fallback"` absent from 0102's `boot.source` union) should be reconciled; also decide whether per-child registration objects (subscription ids, rows) are part of the public capability surface — the runtime currently exposes `entries[].registeredSubscription` while the declarations omit it.
- **Disposal/HMR ordering.** "Unregisters the barrier, stops all child handles, and releases the shared connection" reads as an order; the shipped order unregisters the barrier last (snapback-react/index.mjs:1511–1531), and 0102's HMR witness constructs the successor before disposing the predecessor. State that the sentence lists obligations, not an order — or pin the order.
- **Idempotency-code mapping.** 0107 maps no outcome for `_IDEMPOTENCY_SENDER_MISMATCH` / `_SCOPE_MISMATCH` / `_EXPIRED` / `_PENDING_CAPACITY` (0092:372–375); under M3's resolution these should land explicitly in the never-downgrade class.
- **Evidence list additions.** Make the codegen↔client hash-parity fixture explicit in item 1 (given M4), and add the guide/capability-row update obligation the corpus convention (LLP 0061; 0102's landing gate) expects.
- **Metadata.** Date/Revised are 2026-07-28 — one day in the future.
- **Rollout item 2** ("emit `groups` only when `defineRoutes` is present") vs the current unconditional empty-map emission — reconcile at landing.

## 4. Implementation/evidence assessment

A substantial real implementation exists on all four surfaces: the codegen emitter with runtime and declaration exports (`groups`/`api.groups`/`GeneratedQueryGroups`), `prepareReactBinding`/`prepareQueryGroup` with a genuine admission-and-validation pipeline, a provider-side one-shot registration map feeding the headless `registeredSubscription` adoption (which demonstrably issues no second snapshot, with wire-level tests), and a Signal Desk adapter in demos/signal-desk wired to the generated groups. However: the codegen artifact currently cannot pass the binding's admission (the M4 hash split — no test crosses that seam); preparation-time authority fencing is entirely unimplemented (`fetchBundle` is the one request that omits `expectedAuthorityCapture`); the fallback predicate is the broad 0102-style prefix; reuse/partial-consumption refusal does not exist; no receipt artifact records `source: "registered-bundle"` anywhere; and no `@ref LLP 0107` exists in the repository, so ref-check currently validates nothing about this Spec. Per the review instructions I do not count unmet named gates against readiness — but the gates for evidence items 2–4 cannot be *made* to pass until M2–M4 and M6 are decided one way, which is the mark of spec-level, not implementation-level, blockage.

All eight material concerns have bounded, mostly one-to-three-sentence resolutions; none requires redesigning the architecture, which is sound.

VERDICT: NOT READY

# Round-2 review — LLP 0107: Generated query-group bundle adoption

Fresh independent review, implementer lens, delta round. ## 1. Derived implementation contract and divergence points

The contract I could derive from the target alone:

**Codegen.** For each admitted `defineRoutes` entry whose 1..32 children are all `LiveQuery` (mixed routes ineligible as a whole), emit one frozen `QueryGroupReference` with `artifactKind:"queryGroupReference"`, `formatVersion:1`, `id = ${appId}:query-group:${route}`, and `definitionHash = "sha256:" + hex(SHA-256("snapback:query-group-reference:v1\n" + JCS({route,queries}[+persist:false when authored])))`. Child names allocate in route order from a route-local used-name set (`foo, foo2, foo → foo, foo2, foo3`). Export `groups` and `api.groups` plus a finite typed `GeneratedQueryGroups` declaration.

**Preparation.** `prepareReactBinding({generatedManifest})` cross-verifies manifest identities; `prepareQueryGroup(group, params, {fallbackToLive?, userId?})` rejects with `SNAPBACK_REACT_GROUP_*` codes on the nine admission checks before any network work; `userId` admits only on `local-dev-sqlite-ibex` + settled `dev` mode. At most one register-mode bundle request per preparation, with a fresh idempotency key (no in-preparation retry — the 0092 supersession machinery is deliberately unused), `authInvalidationProtocol:1` when configured, and one client-allocated LLP 0053 namespace triple (`clientStoreId`, canonical fn+args key, monotone instance allocator) per ordered child in a positional `authorizationNamespaces` array.

**Response validation.** Positional 1:1 entry match (function + client-materialized canonical args), one common `commitVersion` in `0..PORTABLE_STORAGE_VERSION_MAX`, complete connection/grant/attachDeadline, the negotiated invalidation descriptor when any child is auth-scoped, closed `resume`-or-null, closed `{scope,invalidation}` projections matching the child's subscription id and allocated namespace, unknown fields refuse. Authority is captured pre-request, compared in the transport publication gate, before resolution, and at transfer.

**Transfer and adoption.** One atomic owner transfer to one provider; bundle connection is the provider's single connection; each child registration is consumed exactly once at first store demand; the headless owner installs the auth fence, publishes bundle rows as authoritative registered state, attaches to the wire subscription, and issues no snapshot-with-subscribe. Capability absence (`registered_bundle_boot_v1` missing from the target-authored manifest) is the *only* live-fallback trigger; every request/response failure refuses. Deadline expiry after preparation becomes `source:"live-recovery"`, `reason:"attach-deadline-expired"`, `boot:null` at transfer. Terminal idempotent cleanup on every exit path; 0059 barrier participant registered before observability.

**Divergence points logged** (places two implementers could materially diverge from the target alone): (a) whether a response whose `attachDeadline` already elapsed refuses at validation or becomes a prepared capability (§3-M2 — the text says both); (b) what happens to wire frames for registered-but-unadopted children between socket attach and lazy adoption (§3-M1 — unstated); (c) whether the bundle request may legally carry the two new fields at all, reading 0092's closed request schema (§3-M3); (d) what "complete generation and version-stream identity" checks — presence vs cross-equality with each `resume.meta` (§4-D3); (e) the exact member shape of `queries` inside the hashed `definition` — authored `{function,args}` specs vs generated `{name,ref,args}` entries (§4-D1); (f) auth-scoped route + client not configured for `authInvalidationProtocol` — pre-request refusal vs post-response malformed refusal (§4-D2); (g) whether all positions of `authorizationNamespaces` are populated or authority-independent positions may be null (the wire schema admits nulls) (§4-D2); (h) whether `userId` must equal the provider/client dev principal at transfer, and where "settled" is measured (§4-D5); (i) the field shape and reason vocabulary of the `live-fallback` prepared object (§4-D6).

## 2. What holds under stress

Most of the delta is coherent with its owners and proven feasible end to end:

## 3. MATERIAL concerns

**M1 (IN-DELTA) — No rule for wire frames delivered to registered-but-unadopted children; adoption then publishes the bundle cut as current.** The delta's lazy-adoption text ("passes a child registration to the headless `liveQuery` owner only when that canonical store first gains demand… publishes the bundle snapshot as authoritative registered state, and attaches to the registered subscription"; "remain provider-owned pending registrations until later demand") never says who owns deltas that arrive between socket attach and adoption. The server's handoff at attach is atomic for the whole registration set (0090 D1.2), so all N subscriptions stream on the socket once any one child creates demand. *Failure scenario:* a 4-child group mounts two children; a mutation changes child 3's rows; minutes later a route renders child 3 — the reference implementation drops handle-less frames (`index.mjs:6736/6772/6807`, `update.subscription_id !== handle.subscriptionId → return`) and adoption then sets `freshness:'current'`, `kind:'registered'` on the bundle-cut rows (`index.mjs:7450-7464`): stale rows presented as current, violating the corpus's retained-vs-current honesty rule (LLP 0043), with no resync until the *next* delta for that child, which may never come. ## 1. Derived implementation contract and divergence points

Working from the target alone, the contract derives cleanly as one pipeline with a single authority at each seam:

**Codegen.** For each `defineRoutes` entry with 1–32 all-`LiveQuery` children (mixed or `Query`-only routes excluded as a whole), emit one frozen `queryGroupReference`: `artifactKind`, `formatVersion:1`, `schemaVersion`, `appId`, `id = ${appId}:query-group:${route}`, `definitionHash = sha256("snapback:query-group-reference:v1\n" + JCS({route,queries}[+persist:false only when authored false]))`, route-ordered children with deterministic names (bare exported name, then decimal suffixes from 2, route-local used-name set — `foo,foo2,foo → foo,foo2,foo3`), authored `{function,args}` mappings excluded from generated `name`/`ref` projections in hash input. **Preparation.** `prepareReactBinding({generatedManifest})` verifies the schema/function/capability/route manifest set's shared identity. `prepareQueryGroup(group, params, {fallbackToLive?, userId?})` runs ten admission checks before any I/O (kind/format, app+schema, route-manifest identity + route entry with same persistence, recomputed hash + id, 1–32 ordered LiveQuery children, unique names, complete child references, exact function/args/result-contract identities, exact string params, and — new — refusal of exact duplicate canonical `(function-reference id, args)` children with `SNAPBACK_REACT_GROUP_DUPLICATE_CHILD`), rejecting the returned promise with stable `SNAPBACK_REACT_GROUP_*` codes with throw/reject parity. `userId` admits only on `local-dev-sqlite-ibex` + settled `dev` mode and joins the authority/adoption identity.
