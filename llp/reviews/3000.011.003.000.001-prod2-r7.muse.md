## Material concern 1: `--day2` refusal and timing not in normative §3

§11 promises production adaptation refuses `--web`, `--expo` and `--day2` with `E_INPUT` before planning/writing.

§3 says only:

> it is independent of `--web`/`--expo` and refuses those combinations under the existing CLI admission rules.

Problems:

- `--day2` is absent from §3.
- Error code `E_INPUT` is absent from §3.
- Timing `before planning/writing` is absent from §3.
- `independent of --web/--expo and refuses those combinations` is self-contradictory. An implementer following §3 alone can read `independent` as `orthogonal/allowed`.

Counterexamples:

- `init --adapt --production --day2` is accepted under §3, silently ignored, then claims a production-ready preview while a day2 lane is active.
- `init --adapt --production --web` is refused after partial writes. That violates §3's own `whole plan must compile before any file write` and `failed proposed policy writes nothing`.

This is material. Admission, code, and timing must be in §3, not only in the §11 disposition.

## Material concern 2: blocked-writer rule is ambiguous and unsafe either way

§3:

> A table with any existing compiled mutation or job insert/upsert path receives no new literal-per-role operations. If blocked, it retains §14's enum-argument bootstrap shape plus only the displayed service read/insert branches; existing authored writer bodies and guards remain byte-identical.

Counterexample table:

```q
table roster(role enum('member','admin'), member principal, UNIQUE(member, role))
```

Existing app mutation `join()` inserts only `role='member'`.

Reading A — `retains` means add generic bootstrap:

- Planner adds generic `bootstrapRoster(role: enum)` alongside narrow `join()`.
- That new path can insert `admin`, widening authority beyond application policy.
- `service:ops`-guarded does not cure it. Service code fed by user input can now be driven to `admin`.

Reading B — `retains` means leave existing writers alone:

- `admin` has no provisioning path.
- No review message is required. Only non-roster and inherited-authority roots get explicit messages.
- The gap is silent. §3 even disclaims: `the planner does not claim their role coverage`.

Either reading is wrong. The text must state whether a blocked narrow writer gets no new insert at all, or a guarded generic insert, and what review/error covers the uncovered role.

Related overbreadth: `any existing compiled mutation` reads as any mutation kind blocks. An update-only or delete-only mutation would block literal inserts even though no insert path exists. If the intent is only insert/upsert paths block, the qualifier must scope both alternatives.

## Material concern 3: per-role inserts assume multi-role coexistence

Trigger: enum column named `role` plus principal identity in a unique key.

Counterexample:

```q
table preferences(role enum('light','dark'), owner principal, UNIQUE(owner))
```

It meets the syntactic trigger. One row per owner exists. Generating one insert per declared role means the second role insert for the same owner violates `UNIQUE(owner)`.

Exercising `each new role mutation as service:ops` would then fail on constraint, not on auth. The rule needs: role must participate in uniqueness, or multiple roles per principal must be able to coexist. As written it over-provisions single-row attribute tables.

## Material concern 4: preserved shell inputs can retain protected-derived values across release withdrawal

§2: a release switch `withdraws protected children while preserving the shell and its inputs`.

Counterexample:

- Release N grants read on `doc.title`.
- `EditDoc` input is initialized from protected `doc.title` and its state lives in the shell above the branch.
- Switch to release N+1 where the role loses access.
- Protected children withdraw, but the shell input still holds the protected `title` string.

The spec does not distinguish user-typed input from protected-derived initial values, nor require clearing derived state. That defeats withdrawal for pre-filled edit forms.

## Material concern 5: orphaned guest intent lifecycle is unspecified

§3: pending writes, replicas, and receipts stay scoped to the original guest principal, never rebound. New viewer must neither observe nor submit that intent.

Counterexample flow:

1. Guest creates offline `hold` intent.
2. Guest signs up through `app.auth`. New account boundary applies.
3. Device goes online under the new session with the guest intent still in the outbox.

The test forbids observation/submission by the new viewer, but the spec does not state whether the SDK must drop, quarantine, retain-for-old-principal, or garbage-collect the orphan. Retain-forever grows storage and risks later resubmission. Silent drop is data loss from the guest's view. Attempted flush under new credentials risks misattribution. This needs one normative outcome.

## Material concern 6: comparison compatibility is over-permissive and nested-null ordering is undefined

§§9/11: all text/enum domains compare as runtime strings without domain containment. Recursive bounded-text view extends this through lists/objects. Shape, nominal/reference, and null rules remain. Ordering still requires present operands.

Counterexample A — disjoint enums:

```q
modeA enum('a','b')
modeB enum('c','d')
if modeACond == modeBVal { ... }
```

Previously a domain error catching `modeA` versus `modeB` confusion. Now it compiles to always-false runtime string comparison. Overlapping-only compatibility was the stated need. Disjoint comparison should stay an error or at least be called out.

Counterexample B — nested nullable in ordering:

```q
a = [{ m: nullableEnumCond }]
b = [{ m: 'x' }]
if a < b { ... }
```

Top-level lists are present, but `a[0].m` may be null. `ordering still requires present operands` covers top-level presence only. It does not define whether nested null traps, is ordered, or is refused at compile time. The same gap applies to scalar `min`/`max` over collections containing nullable enum conditionals.

Each concern above has a concrete program or command that the current text decides differently under two reasonable readings, or leaves without a decision. Therefore the amendment is not yet precise enough to implement.
