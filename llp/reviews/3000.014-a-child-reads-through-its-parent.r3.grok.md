## Does the lifetime rule hold?

It holds for a **two-level, non-expiring** parent on the server write path. `issues.org` is immutable, comments store that value, and a program cannot delete the issue while a comment is live. Insert-then-delete in one mutation holds if the child probe uses that transaction: the comment inserted earlier is visible, and a comment inserted after the delete sees no live parent. A job that deletes comments and then the issue also holds, **if** the probe sits in `delete_attempt` after `check_rule`. It must not be part of the rule. Jobs and `seed_delete` run as the system principal, and `check_rule` returns true for the system.

It does not hold in the cases below.

### B1. Blocker — §3.2, §4.1 — a grandchild outlives its parent

The rule you want is transitive: a row's effective expiry is the earliest instant in its captured chain, and that instant is what `Table::expired` already is. Reads, unique checks, the sweep, snapshots (`partition.rs` skips `table.expired`), and `retire_expired_births` (only tables with `expire.is_some()`) all use that predicate.

The mechanism is not. §3.2 captures the parent's **declared** `expire at` column, and only when the parent table has one. The sweep removes a row through `remove`, which applies no rule and no child check.

```quarry
table orgs:
  end: time
  immutable end
  expire at .end
  read <- exists members[.id, viewer]

table projects:
  org: orgs
  until: time
  immutable until
  expire at .until          # next year
  read through .org

table tasks:
  project: projects
  read through .project     # projects declare expire at, so tasks capture .until
```

Org `O` ends Monday. Project `P` captures Monday and is dead Monday, because its effective life is the earlier of `.until` and the org. Task `T` captures `P.until` (next year). On Tuesday `T` is live, `P` is expired, and the sweep can `remove` `P` and then `O`. Insert org `O` again and grant Bob membership. `T` still evaluates `exists members[O, Bob]`. Bob reads Tuesday's task. A pinned page of `T`'s parent is worse: §5's one verdict uses the new org, not `T`'s stored captures.

The same split happens one level up if the middle table does not declare `expire at` at all. §4.1 says to copy "the parent's expiry instant, when the parent expires," but §3.2 never feeds a **captured** instant into the child's `expired()`.

**Smallest change.** Capture one value: the parent's effective expiry, already the min along the chain, or none if it never expires. The child's effective expiry is the earlier of that instant and its own column. Wire it through `Table::expired` so the sweep, snapshots, unique checks, retirement, and maintains all see it. Do not sweep-remove a row while any descendant is still live under that predicate.

### B2. Blocker — §3, §5, §7 — a reused id meets unswept children, and recapture revives them

§3 allows reuse as soon as children are **logically** expired: "old, expired children that the sweep has not yet removed are invisible." `insert_attempt` already replaces an expired row that still holds the id. Those children are not invisible to activation, to `birth_columns`, or to a device that has not yet applied the sweep.

Probe. Issue `X` in org A expires Monday; its comments capture Monday and have no earlier expiry of their own. Tuesday, insert issue `X` in org B (`insert_attempt` deletes the expired issue and puts the new one). Then change the issue read rule so the capture identity changes.

§7 scans child rows and fails only on a missing or expired parent, or a hand-copied column that disagrees. `X` is live, so the check passes. Engine captures are not the hand-copied column. Recapture is specified to override "a stored value is never re-resolved," so it stamps B and B's expiry onto Monday's comments. They are live again, in B's audience. The first adoption of `read through` does the same to pre-existing comments: activation's projection drops a hand-copied `org` before the builder runs (`activation.rs` keeps only columns of the new table), so the disagreement check has nothing left to read.

That is Astra's revision-2 blocker, without incarnations. It is also the id-keyed leak: until the sweep, a device that already holds the comments still has them. Device `now` is the caller's clock, not the server's. A behind clock has not expired them locally. Sync can deliver B's issue before the comment tombstones (the sweep limit is 2,000 rows, table name order, one commit). §5's shared resolver then applies one verdict from B to every local comment of `X`. A fresh snapshot does not hand those rows to a new member (`snapshot` skips server-expired rows). A device that already has them, including `retain delivered-history`, mixes the two lives.

**Smallest change.** An id is not reusable, and is not recaptured onto, while any **physical** child row still references it, expired or not. The sweep emits child tombstones before the parent id may be inserted again. Activation may restamp a child only when that same parent row is still the one it was captured from; a reused id aborts the generation. Initial adoption fails closed when the only evidence of the old audience was a column this generation drops, unless the author has deleted those rows first.

## New defects

### H1. High — §4.4, §6 — upsert and `if absent` still branch before the reservation

`target_attempt` restores the meter only for `NOT_FOUND`. `visible_collision` returns `E_RULE` for a hidden existing row.

Probe. Parent `P` is unreadable. Upsert child `C`.

- `C` exists: the update arm returns `NOT_FOUND` and the meter is restored. The parent read never runs.
- `C` is absent: §4.4 reserves the parent point-read and the probe allowance on the insert arm, then §6 returns `NOT_FOUND`. Under a tight ceiling that reservation is `E_BOUND` in only one world.

`insert … if absent` is the same split: the existing-row path returns `E_RULE` from `visible_collision` without the parent reservation; the missing-row path pays it. §6's "same charge whether the parent exists" does not cover whether the **child** exists, and §4.4 attaches the reserve to the insert path only.

**Smallest change.** Reserve the capture's fixed charge once, before choosing the update arm, the hidden collision, or the insert arm. Both worlds return the hidden-target `NOT_FOUND` (upsert) or `E_RULE` (`if absent`) and the same restored meter, including at a ceiling that can hold the reservation and at one that cannot.

### H2. High — §5 — "the page is complete" ignores the child partition

A device page is complete by its acquisition boundary (`read.rs`, LLP 3000.007 §20.22), not by an authorization verdict.

Probe. The issue is held and readable. Comments are `sync last 20`. There are 50 live comments. `comments where .issue = X first 20` is a full local page and is not the end of the server's answer. §5's table says found-and-readable means the page is complete, so the client will not fall back.

**Smallest change.** The resolver's verdict is only the audience. The page is complete only when that verdict is decided and the child's own coverage for that prefix is whole. A horizon, an online-only child table, or an unknown child probe stays incomplete and uses the server fallback. Keyed `commentCounts[x]` follows the same split: unknown is incomplete, not zero.

### H3. High — §5 — retiring the column note contradicts LLP 3000.007.001

The cite to LLP 3000.013 is wrong. The source ban is LLP 3000.007.001 §3.10: a maintained **column** source may not declare `expire at`, because the mirrored value would be stale until the sweep. §3.2 says an expiring **parent** is fine, the private total survives deletion and expiry, and birth is `tx.get` of that total. `birth_columns` does that `get`. "A re-created parent is born with the right total."

Probe. `issues` expires and has `comments: count comments by issue`. Comments use `read through` and do not declare `expire at`, so the binder allows the column. Issue `X` has five comments and expires. Insert `X` again. Birth reads five. §20.9.3 keeps the physical contributions until the sweep, so the new row shows 5 even if the old comments are logically dead. Retiring `N_MAINTAINED_COLUMN_DISCLOSURE` presents that 5 as authorized. If B1 is implemented by an effective expiry that is not `decl.expire`, the binder still allows the column.

**Smallest change.** Do not retire the note for an expiring parent. A `read through` source with an effective expiry is an expiring source and stays on the view form, which recomputes. For a parent that does not expire, the note can go away only for the unnarrowed shape, and only because deleting the children removes the private total before the id can be reused (B2). Birth keeps reading the private total; "born at zero" is that total being zero, not a new birth rule.

### M1. Medium — §2.1, §5 — a child service disjunct breaks the one verdict

`read through .issue or viewer = 'service:search'` is legal. The issue rule has no service disjunct. The resolver's "found, unreadable → empty and complete" uses the **parent** verdict. The service principal is not a member, so a pinned comment page is empty even though the child rule admits the service. Fail closed, but it is the wrong page. Devices are fine: `device_audience_rule` still strips the disjunct.

**Smallest change.** The one verdict is the substituted child rule over the parent's captured inputs, service disjunct included, on the server only. A service disjunct that does not appear in the parent rule cannot be decided by the parent verdict alone.

### M2. Medium — §4 — "the recorded-field path" is the wrong function to copy

`capture_recorded` stamps `Null` when the parent is missing or expired, then charges that image's heap only on a hit. Schema validation requires the target to be publicly readable and the stored column to be optional. `audience_binding` then refuses the optional prefix. Public attribution also refuses to re-resolve a stored value; §4.5 overrides that only for this capture.

**Smallest change.** Say this is a sibling of recorded fields, not that function. Required columns, private parent fields, refuse before stamp, no hit-only heap, recapture only under B2. Keep the public-target path unchanged.

### M3. Medium — §5, devices — a predicted parent delete is unspecified

`recording_covered` gates child inserts, not parent deletes. A device that holds the issue and not the comments can predict `delete issues[X]`: the delete rule passes locally, `remove` is not involved, and the local issue disappears while held comments remain. The server then answers `E_PARENT_HAS_CHILDREN`. Until refusal replay, a pinned local page treats the parent as covered-absent and returns empty and complete.

**Smallest change.** A parent delete is predictable only when every `read through` child table is fully held and the live-child probe is false. Otherwise queue with no local deletion.

## Under-specified

### M4. Medium — §10 — the chain fixture reads like narrowing

§10 requires a four-level chain with `and not .archived`. §2 and §9 forbid a conjunct on `read through`. The conjunct has to be written on a middle table that does **not** use `read through` (`read <- exists members[.org, viewer] and not .archived`, `archived` immutable). The child copies that stored rule by `read through`. As written, the acceptance test is how an implementer talks themselves back into the revision-2 page bug.

**Smallest change.** Show that middle table in full. State that `read through` never grows a conjunct in this revision.

### M5. Medium — §7, seeds and restores — the invariant is only on the program write path

`load_trusted` writes stored images as given and does not look at the parent. A partial restore, or a backup taken after the parent sweep and before the child sweep, installs a live child whose parent is gone or whose captures belong to a replacement. `load` of a new child goes through `record_insert`, so it picks up whatever the current id points at (B2). The RFC never says which of these must revalidate.

**Smallest change.** Program inserts, seeds, and imports use §4.4. A trusted restore either refuses a child whose parent is missing, expired, or different from its captures, or it is defined as a whole-store image that already satisfied B1 and B2. No restore recaptures.

## What is sound

`read through .ref` as the entire read rule, over a required immutable id with no default, is the right cut. Copying the immediate parent's stored inputs, including every conjunct of a parent that spells its own rule, and not walking to a live grandparent, matches how a local rule has to work. Exact admission after the service strip matches LLP 3000.007 §6.6, `infer_audience`, `validate_sync`, and `grant_guard` (the guard stays on the membership table's insert, using the membership columns, so `insert <- .author = viewer` does not have to restate the probe and does not weaken it). The implicit insert check — live parent, then the parent's rule admits the writer, then the child's insert rule — closes the "non-member attaches a comment" hole on the server. Absent and unreadable parents both stop before `term()` sees a null. The fixed parent-read reservation, with no hit-only heap, is the right meter for that plain insert. Updates do not re-resolve the parent. Cycles are refused. Keyed views only, no scan, avoids the group-count oracle. Predicted child upserts staying non-predictable avoids `upsert_absence` having to understand captures. Per-table leave policy is the right revocation story. Two levels, no expiry, same transaction: captures stay equal to the live parent's immutable fields.

**Overall verdict: NOT READY.**
