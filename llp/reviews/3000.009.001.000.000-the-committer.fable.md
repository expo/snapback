## Verdict: SOUND WITH MAJOR ISSUES

The core shape is right and I could not break it: one serial stream per store, members either validated-at-snapshot or run in place, batches that commit atomically so exact snapshots and contiguous watermarks fall out for free, and Kung–Robinson backward validation folded serially within a batch. The code supports the key premise that a program's reads cross one boundary: `Runner` holds `&'a dyn Rows` (`engine/runner.rs:312`), and every raw `conn()` read in `engine/` sits in an `impl Engine` block, not in the `Runner` (`engine/effects.rs:190`, `engine/job.rs:182`, `engine/asset_uploads.rs:3`, `engine/timeline/work.rs:166`). Three things are wrong at the design level, though. The member's admission-time inputs, including who the principal is, are read before the snapshot and declared fixed, which contradicts the parent RFC and an invariant the server keeps today. The schema features that create contention by construction (sequence columns, maintains, caps) are validated by value, so the target workload degrades to the in-place rate, and the sizing cell that gates the build cannot see it. And the replay oracle, the design's central correctness claim, is defined over a "reference" (`Engine::mutate`) that bundles a prelude the committer does not reproduce, so the oracle as written disagrees with a correct committer.

## Fundamental and major findings

### F1. The member's admission inputs are outside the validated snapshot — MAJOR — read sets §2 and §3; committer §4.2; overlay §2

The child says "the principal comes from admission" and lists it under inputs that are "fixed rather than recorded" (read sets §2), while its own §3 table has `Auth(kind, key)` entries and the parent (§6.3 items 2 and 4) requires session validity, principal generation and lease to be validated so "a revocation that landed after S is seen". These cannot both hold, and the design never says where the `Auth` entries come from.

Today the server resolves the bearer session and runs the mutation under the same engine lock (`crates/snapback4/src/serve.rs:1411–1422`, `mutation_authority` → `identity::resolve_supervised`, `serve_identity.rs:107`, `identity.rs:80–84`), with an explicit rule that write authentication stays behind the writer because "time queued for adoption must not preserve a session that expired or was revoked in that wait" (`serve_identity.rs:58–60`; the `@ref` cites LLP 3000.019 §3.6, whose heading no longer matches — UNVERIFIED which section it means). The committer's queue is exactly such a wait. Under the design, admission reads happen on a reader at some earlier snapshot, execution happens at S, and nothing re-reads the facts inside S. A revocation between admission and S is visible in S but never read; a revocation after S is caught only if an `Auth` entry labeled S exists, and under §2 it does not.

The same gap covers the rest of `Engine::mutate`'s prelude, which runs before the `Runner` and outside `Rows`: the bound receipt check on `_ops` (`engine/mod.rs:938`), the asset-intent placement check on `_asset_intents` (`engine/mod.rs:945` → `assets.rs:874`), and the clock pin on `_meta` (`engine/mod.rs:946–950`, `store/time_audience.rs:29–36`). None is a trait method, so the "static census of read methods on those traits" (read sets §6.1) cannot see them, and the instrumented count only counts trait crossings.

Direction: define a member as everything read at S. The execution re-reads every admission fact inside S through the recorder (session by digest, principal generation, the `_ops` receipt, the intent placement, the clock), each a point read, and the `Auth`/receipt/placement entries carry S's label. Make the pre-execution handle expose only `Rows`/`PartitionRows`/family calls so a raw-SQL read cannot compile into the pre-executed path; the `Runner` already has that shape. Drop the sentence that fixes the principal at admission.

### F2. Schema-level hot keys defeat pre-execution on the workloads it exists for, and the sizing rule cannot see them — MAJOR — committer §4.3, §2.3, §9; read sets §3

The design treats hot keys as an application accident absorbed by the conflict budget. In Snapback they are produced by schema features, and the validation table conflicts on them by value:

- Every insert into a table with a sequence column reads the parent's counter and writes `previous + 1` (`engine/sequences.rs:203–239`, `271–281`). Two concurrent inserts under one parent always conflict. A per-room message number is the canonical chat shape.
- Every write to a maintained aggregate's source reads the target row and puts the new total (`engine/maintains.rs:586–619`); a global maintain has one row for the whole table (`maintains.rs:616`), so every insert into that table conflicts with every other.
- `cap_count` conflicts with any occupancy change (read sets §3), although the store already applies caps as deltas (`store/caps.rs:11–17`).

After `c` conflicts the member runs in place, and the score routes new members straight to in-place. So for any group with a sequence, maintain or cap, the throughput is the reference's serial rate, and each in-place member also spends its `k·RTT` inside the batch's serial section, stretching latency for every pre-executed member in the same batch. That is the chat workload, and it is where S0's 424/s single-hot-counter floor applies, not the 15,744/s commit bound.

The gate cannot catch this. S1a sizes (a) with W4, "each writer increments its own counter" (LLP 3000.009.001.002 §9 S1a, W4 at its line 168), a disjoint workload with no shared sequence, maintain or cap. The rule can clear and the first real application can still run at the in-place rate.

Direction: add a commutative/allocating write class. Maintains and caps go into the overlay as deltas (the overlay already does this for caps) with validation by predicate rather than by value: if the program did not branch on the total, there is no `Row`/`Cap` read entry, and the committer applies `value + delta`. Sequence columns are allocations, not reads: treat them as placeholders allocated at commit from the committer's in-memory counter, resolved into the row image and the sequence index key by the same §5 machinery; the taint rule decides eligibility exactly as for public sequences. Then add one S1a cell with C writers under one parent sequence and one global maintain, so the rule measures contention the schema creates.

### F3. The replay oracle's "reference" is not one function, so the oracle as defined disagrees with a correct committer — MAJOR — committer §3.5, §6, §8.1

`Engine::mutate` is not only the program. Before its transaction it calls `advance_time_audience`, which commits at most one due row as a separate publication commit (`engine/mod.rs:916`, `engine/time_audience.rs:84–86`, `114–188`), and inside it pins `now` to `max(requested, clock)` (`mod.rs:946–950`). Reads of a due-but-unpublished row refuse or hide it (`engine/read.rs:379–397`), so a mutation's outcome depends on how far that publisher has advanced.

The committer lists time-audience publication as a member (§3.2) and gives Postgres the advance (§6), but never places publication in the stream relative to the members whose `now` makes rows due. Validation will catch the dependency (`Time` entries conflict with a later publication), so committed histories stay serializable. The oracle does not: replaying member M through `Engine::mutate` re-runs M's prelude, which publishes a row that in the committed history was published by a later member P. The replay then sees a live row where M saw a pending one, and §8.1 calls that disagreement a defect. K3 would chase it.

Direction: define the oracle's reference as the seam's `run` (the parent's `Committer::commit(op, run)`, §6.1): the program plus its post-program obligations, with every prelude input supplied from the member's recorded admission, and publication members replayed as members. State the ordering rule for publication: a member whose `now` is at or beyond the next opening is ordered after the publication member for that opening, or it reruns.

## What the documents get right that should not change

- One stream per store with in-place members as both fallback and reference. It is the only candidate that keeps every §6.4 invariant by construction and still removes `k·RTT` for the common member.
- Batch atomicity. One transaction per batch gives exact snapshots and gap-free watermarks without a publication protocol; a snapshot labeled by the revision read inside it is sound because batches become visible atomically in commit order.
- Revision versus public sequence. Non-publishing writes taking a revision and a footprint is what makes revocations and claims visible to validation; the head stays the sync watermark.
- Recording at the adapter boundary, not in the `Runner`. Confirmed: the `Runner` reaches the store only through `&dyn Rows` (`runner.rs:312`), and `read_tables` is table names only (`runner.rs:131`).
- Backward validation with in-batch folding, and coarsening as the safe direction. Correct as stated once F1's inputs are inside S.
- Placeholders for sequence-derived values. Rows carry no commit sequence (`r (t, id, data)`, `store.rs:292`); only effect ids (`runner.rs:688`), timeline admission tokens (`engine/timeline.rs:161–162`) and tail rows do, so resolution is confined to what §5 names.
- Lease renewal bypassing the stream; the replay oracle as the property rather than a proof; K0 and K1 being worth landing whatever S1a says; declining pure OCC and MVCC-labeled validation for store neutrality.

## Small notes (optional, at most five)

1. **`index_head` interval is on the wrong side** (read sets §3). The head is the first key in `[lo, hi)` in `dir` (`store.rs:1156–1160`); a new key between the bound's start and the head changes it, a key beyond the head does not. The entry should be `Range(bound start … head]`, not "from the head to the end".
2. **SSI "cannot see absences" is a wrong reason** (committer §10). Postgres SSI detects phantoms through predicate locks. The sibling's reasons stand: write connections during execution, no SQLite counterpart, physical versus logical ranges, prefetch over-reads.
3. **Replay-oracle inputs are incomplete** (committer §3.5). Programs read presence (`connected[p]`, `engine/mod.rs:435`) and effects record presence deadlines (`effects.rs:93–96`); ids are minted from OS entropy (`ids.rs:33–36`). Record presence and minted ids with the member, and make the `_ops` receipt a read-set kind rather than relying on the `PRIMARY KEY (principal, id)` violation to abort the batch.
4. **Direct operations in place by default is the wrong default** (committer §3.2, §11.1). Each effect is at least claim, step and settle, each 1–2 RTT inside the serial section, so an effect-heavy application is RTT-bound again. They have single-key read sets and typed writes, the easiest members to validate in memory and array-apply; S1a should include an effect-per-mutation cell.
5. **Long in-place members need the administrative rule** (committer §3.2, §7). Job chunks and timeline delivery run at `Ceilings::job()` (`engine/job.rs:313`, `engine/timeline/work.rs:198`); one 200 ms member in a batch breaks the write SLO regardless of N. Run them alone in their batch, as administrative members do.
