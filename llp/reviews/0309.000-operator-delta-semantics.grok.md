M1. Reference-evaluator type cannot express the Maintain paths the forms define.

D1.1 and §7.1 type ∂O as a pure function (state, Δin) → Maintain(Δout, state') | Fallback(reason). §7.2 vectors pin only initial state, batch, and that result. The same document’s maintain conditions *require* bounded authorized reads that are in neither input:

- E3 (iii): next row past the boundary
- E4/E5/E7: point or range read on re-key
- E6: 1→0 re-probe (edge range + target points)

Ledger entries for those rows are explicitly **missing** (authorized-read). There is no read-oracle parameter, no vector slot for read results/effects, and no ruling that the reference evaluator MUST FALLBACK whenever a read would be required.

Consequences: (a) the (iii)/re-key/re-probe Maintain paths are unrepresentable in the derivation artifact D4.1 demands; (b) §7.2’s required class “displacement with and without provable replacement” cannot pin condition (iii); (c) Stage B’s “bounded/authorized read effects” axis has no oracle to disagree with; (d) two implementers will not even agree whether those cases are Maintain or FALLBACK. This is a defective type-contract decision, not missing prose.

M2. E3 is specified per ΔZ entry; the document’s own batch examples do not have a defined algorithm.

E3 lists five per-entry cases (inside/patch, inside re-rank, enter+displace, leave+replacement, outside). It also requires whole-batch consumption and cites a boundary swap as the motivating multi-row commit. Those two do not compose.

Concrete misclassifications if entries are judged independently against pre-batch state:

- Boundary swap (delete of last + insert of a new last, two keys): leave on a full incomplete window → FALLBACK(boundary-displacement) (or a 1-row lookahead), while the insert is “outside” or a second enter that displaces the already-deleted boundary. The replacement the leave needs is *in the batch*. No rule says to fold the batch before classifying, to sequence state' mid-batch, or to treat in-batch outside rows as replacement candidates.
- Two enters into a full window (or into remaining capacity 1): each enter displaces the same boundary row → duplicate splice-out and an oversized window, a Maintain that violates the equivalence property.
- Two leaves from a full incomplete window: “exactly the next row” (singular) cannot prove two replacements; FALLBACK vs a range-2 read is unstated.
- Sequential vs simultaneous application changes who the boundary is, hence which later entries are inside/outside.

“Forms consume whole batches” is an obligation without an operator. ΔSeq composition is only “sequence splicing,” with no conflict rule (two splice-outs of one key, patch after splice-out, two splice-ins at one rank). Stage C’s headline beneficiary is this form. As written, two reference evaluators will not match on the window vectors the corpus is required to contain.

M3. Parent-enter / new-scope fill is unspecified; the zero-fill default is a silent wrong delta.

E4’s parent arm is only “join value changes → re-key read or FALLBACK(rekey-unread).” E5’s extra parent arm says enter/leave “creates/destroys a whole per-parent window” and requires a range read only on re-key.

A new parent (root splice-in, or parent becoming visible) is not a re-key of an existing lookupKey. Nothing requires the same point/range read full evaluation would do. The maintain that then succeeds assembles optional to-one as null and to-many as [] whenever children exist at the join key — a wrong Maintain, not a FALLBACK. Required-presence would sometimes trip refusal-transition; optional presence and arrays would not.

Destroy-on-leave can drop state without a read; create-on-enter cannot. This is a missing change term for the parent input the parent RFC forbids treating as covered by fiat.

M4. E4 (and E5/E6 by the same pattern) child-side Δin is raw ΔApp; the closure table wraps the child in E1∘E2.

E4: “Child-side arm (ΔApp on the child table): … insert/update whose join-field value matches a retained lookupKey with found:false is a missing→found transition.”
§4: equality-to-one = “E4 (child side = E1 ∘ E2 of the child relation)” (same wrapping on bounded-to-many and exists).

If the arm is implemented as written, a child insert that matches the join key but fails child visibility or FilterExpr is attached. That is a fail-open maintain. If the arm is meant to consume post-filter ΔZ, E4’s text is the wrong type and never applies E1/E2 on the incremental path (including join-key change, delete, missing→found). Two implementers, two behaviors; one of them ships unauthorized rows. Same hole for E6 probe predicates (“Filters on the semi-join apply E1/E2 inside the probe predicate” vs through/target “ΔApp”).

M5. E6 0→1 “Maintain from the change alone,” reused as E1 membership visibility, is not closed over rows the result can newly admit.

E6: 0→1 is decidable from an insert/entering update on a scope whose bit is already 0. That is sound for exists-bits on *already retained* parents (output cannot gain a new parent from an edge write). E1 membership visibility decomposes to the same E6 against the membership relation. There the “scope” is a carrier row. Invisible rows are not retained. A membership-table insert can make a non-retained carrier row visible; that row can then pass E2 and enter E3/E5. State does not contain it. Maintaining 0→1 only for known scopes omits the enter — a wrong Maintain.

“FALLBACK(scope-unresolved)” is available but defined as “cannot classify which parents’ probes could it affect?” An implementer who answers “the retained parents whose resourceField matches” will classify, maintain, and drop the newly-visible row. The fail-closed reading (prove the affected-scope set is complete, else FALLBACK) is not required. Reusing E6’s 0→1 rule for visibility is the defective decision; exists and visibility do not have the same closure over scopes.

Related batch hole, same form: two edge/membership rows in one batch for one scope (delete M1 + insert M2). §1.4 ΔBit composition is last-write-per-scope, and E6 never says to net support or re-probe when multiple same-scope facts share a batch. Last-write can emit 1→0 when support remains, or 0→1 when net is unchanged.

M6. Both-change / n-ary interaction terms are required and not defined.

§2 (and D1.1): binary Δin is a product — two unary arms plus a both-change arm; n-ary forms owe interaction terms. E4 specifies two unary arms only. E5 adds a parent arm without a parent×child batch rule (parent re-key + child displacement in one commit). E7 is three-input and points at “E4 parent-arm rules.” E6 names FALLBACK(interaction-unordered) “where composition order cannot be established within the batch” but never says when order *is* established. A multi-table atomic commit has no inter-table order; ΔApp is per table.

Implementer A always FALLBACK on product Δin (conservative, not equivalent to the unary-arm spec). Implementer B sequences unary arms and can mis-order re-key vs child delete (patch a parent that just re-keyed away; miss missing→found at the new key). The equivalence property does not substitute for the arm: the reference evaluator is local, not “run O(S⊕ΔS) and diff.”

M7. E2’s pre-image rule disagrees with the E1∘E2∘E3 decomposition it is supposed to participate in.

E2 is confirmed linear and state-free. Enter/leave uses “membership-in-state … the row was retained iff it was in the node’s result” (DK-3 was_member). In the closure table, root-window is E1∘E2∘E3 feeding ΔZ into the window. E3 retains only the window, not E2’s output relation. So:

- If E2 is truly elementary, was_member at “node result” is the window, and an outside row that still passes the filter is classified as a filter-enter (+1) rather than a filter-stay. Harmless only when E3 then no-ops; not harmless if fused classification later treats that +1 as “not previously in the filtered source.”
- If E2 retained its full output, it is not state-free and the E3 ledger is the wrong grain.
- If E1∘E2∘E3 is meant to be a fused classifier (DK-3’s unordered under-limit rule lifted to windows), §5’s “composition of elementary forms along the dataflow” is not the rule.

This is the composition story the parent RFC exists to pin, and it is not pinned. It also makes E3’s input carrier (ΔZ) only implicit: E1/E2 never declare Δin/Δout types, and E4’s output is not ΔZ, ΔSeq, or ΔBit. D1.1’s “Δin/Δout are typed per operator” is not met for E1, E2, E4, E7, E8.
