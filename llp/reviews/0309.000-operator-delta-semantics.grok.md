M2. E3 is specified per ΔZ entry; the document’s own batch examples do not have a defined algorithm.

E3 lists five per-entry cases (inside/patch, inside re-rank, enter+displace, leave+replacement, outside). It also requires whole-batch consumption and cites a boundary swap as the motivating multi-row commit. Those two do not compose.

- Boundary swap (delete of last + insert of a new last, two keys): leave on a full incomplete window → FALLBACK(boundary-displacement) (or a 1-row lookahead), while the insert is “outside” or a second enter that displaces the already-deleted boundary. The first/last table is the 2×2 of (existed-at-start? first is update|delete : insert) × (exists-at-end? last is insert|update : delete):

- insert…delete → fold away (phantom; never a source row)
- insert…insert|update → insert (new at start, present at end)
- update|delete…delete → delete
- update|delete…insert|update → update, last image

Single-op batches are first=last and land on the identity. Insert-then-delete-then-insert is net insert; delete-then-reinsert is net update, so E3 5(c) can see the source-row removal that last-write-wins-to-insert hid. Inadmissible net insert still cannot remove a pre-existing source row; that exclusion is now sound. No missing first/last pair, no wrong kind.

E3 5(c) (the round-4 MATERIAL)
------------------------------
Checked against the two cited counterexamples and nearby variants.

- take=5 [A..E] incomplete + Z beyond the window, label-only tail(window,1) from the final boundary returns Z: nonempty ⇒ complete'=false even if that tail’s exhausted bit is true. The r4 exhausted-only rule is gone.
- take=2 [A,B] + unretained admitted update Z unselected: Z entered the working map as admitted ⇒ uniquely 5(a), Maintain, complete'=false, no 5(c) read.
- Unretained delete, or update whose post is inadmissible / outside the interval, on an incomplete window: 5(c) only; label-only tail; empty∧exhausted ⇒ complete'=true (Z was the last unseen source row).
- 5(a) still does not require the old complete bit, so a complete window that newly discards a working-map row still drops to complete'=false.
- 5(c) still requires incomplete, so an unretained delete against a complete window does not spuriously re-proof.
- Step-4 subsumes (c) only; 5(a) still wins over 5(b). A joining tail from B_old that returns rows past the old boundary is a completeness fact about the post-fill source, which is what (b) needs; a label-only tail from the final boundary is the (c) fact and must not trust exhausted-with-a-row.

Empty-final-window origin in (c) is written and matches the punch list. For take>0 it is redundant with step 4’s underfill trigger (empty window ⇒ step 4 runs, (c) is subsumed). Redundant, not unsound.

§1.5 assembled-payload absorption
---------------------------------
Birth is no longer splice-in-only. A presence-transition update carrying the full new object absorbs descendant fills; remove and update-to-null absorb descendant departure; independent descendant ops only when no ancestor was added or presence-appeared. That closes the duplication hazard for optional to-one appearance/clear without pulling rank-unchanged patches (field diffs, not assembled payloads) into the rule. Child-key change on a still-found scope remains the existing §9 lowering obligation, not a new hole in this fold.
