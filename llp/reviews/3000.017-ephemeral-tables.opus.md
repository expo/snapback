## Verbatim review

### Review of LLP 3000.017 revision 1 — Claude (Opus 5.5)

**Verdict:** READY WITH CHANGES

## Summary

The core bet holds up against the code. The runner takes `&dyn Rows` (`crates/snapback4-core/src/engine/runner.rs:226`), and `MemoryRows` already implements what an expiring table needs: `cap_count`, `index_head` and `scan_metered` (`crates/snapback4-core/src/rows.rs:345-376`). Taking the outbox out of the typing path removes the cause of F1.

The biggest gap is the wake path. A peer's held `/changes` poll is issued before its new typing watch has answered, and the RFC never re-issues it. The online tier also has no way to tell which tables are ephemeral. As written, a peer may not wake for up to 25 s (F1).

The RFC's own example table also breaks its revocation claim. I ran a probe on 0.4.2: a removed member's upsert renewal is accepted and still shown to the room (F2).

The remaining findings are foldable:
- a generation fence on the shared hub;
- a lock scope that would serialize every query;
- a wake path that still reaches the engine mutex and SQLite's writer lock;
- gaps in the client sender contract;
- a status mapping that would flip clients offline;
- a chats-list recipe that would break M6 offline.

None of these needs a second design round.

On timing, once F1 is fixed the design meets the benchmark with about 1 s of margin. The choreography starts both clocks at the final keystroke (`benchmarks/tools/social-messenger/choreography/choreography.mjs:1754-1765`). With `ephemeral 4s`, the last renewal is sent at most 1 s before that keystroke, so the row's deadline is at most last keystroke + 4 s. The local tier resets the watch to loading at the deadline (`packages/snapback4/src/local.ts:911-926`), so the indicator hides before the re-fetch even returns.

## Findings

### F1 (High) — The peer's held poll never hears about a newly mounted ephemeral watch
- **Where:** §3.3, §4.6 (`changes.ts` "built from the ephemeral tables of live server-answered watches"). Code: `packages/snapback4/src/client.ts:620-623`, `client.ts:511`, `packages/snapback4/src/local.ts:819`, `local.ts:848-852`, `packages/snapback4/src/backend.ts:1-50`.
- **What is wrong:**
  - A poll's `ephTables` is fixed in the URL when the request is issued.
  - The online tier calls `void refresh(watch); void poll();` together in `observe()` (`client.ts:622-623`). The poll therefore starts before the first answer reveals `tables`.
  - The local tier's `follow()` loop keeps a 25 s poll held continuously, and it was issued long before the conversation screen mounts `typingIn`.
  - Nothing aborts and re-issues the held poll when the set of ephemeral tables grows. Bob's first `setTyping` therefore wakes nothing on Alice's side until her poll ends: after 25 s, or on some unrelated durable commit.
  - The online client also never loads `/schema` (`client.ts` has no backend or schema). It cannot tell `typing` apart from `members` in a query's `tables`.
- **Evidence:** read the code above. `read_tables` does record `typing` before any row is found (`crates/snapback4-core/src/engine/read.rs:819`), so the table set is available after the first answer — it just arrives too late.
- **Proposed change:**
  1. Emit each query's static ephemeral read set on the generated op and in `/schema` operation facts, for example `ephemeral: ["typing"]`. Take it from `ir::read_sites` plus the rule-probe closure. The client then knows at `observe()`, before any answer.
  2. Add this rule: "When the union of ephemeral tables over live watches grows, the client aborts the held `/changes` request and re-issues it at once. Shrinking never restarts."
  3. Alternatively, the client sends all of its watches' tables and the server intersects them with its ephemeral set. That needs no schema knowledge, but still needs the restart.
  4. Add a test where B's poll is already held before B mounts `typingIn`. Run B on the local-first tier, which is the benchmark's tier and has its own loop (`local.ts:806-845` versus `client.ts:505-540`).

### F2 (Medium) — The RFC's own table lets a removed member renew forever, so §3.2's revocation bound is false
- **Where:** Summary table (`update <- .principal = viewer`), §2.2 "Life", §3.2 "at most its life". Code: `crates/snapback4-core/src/engine/write.rs:227-246` (the upsert's update arm) and `crates/snapback4-core/src/engine/field_authority.rs:89` (only the update rule is checked).
- **What is wrong:**
  - Every update or upsert renewal restamps the deadline, but only the update rule gates it.
  - With the RFC's update rule, a member removed from the room keeps renewing.
  - Under the card's 10 s heartbeat, a removed Carol shows as "viewing" indefinitely. Removed members keep their history screen open per the brief.
  - The current durable `reads` card already has the conjunct (`crates/snapback4-lang/src/guide/reads.rs:120`: `update <- .principal = viewer and exists members[.roomId, viewer]`). The RFC's example drops it.
- **Evidence:** a probe on the 0.4.2 binary, using the same table with durable `expire at`:
  - Carol joins, types, leaves, then calls `setTyping` again. The result is `"state":"sent"` (seq 5).
  - Alice's `typingIn` then returns `[{"principal":"dev:carol"}]`.
  - With the card's update rule, the same renewal fails with `NOT_FOUND`.
- **Proposed change:**
  - Restore the membership conjunct in the example.
  - Make it an engine law for ephemeral tables: any write that stamps `$deadline` must also pass the insert rule on the new image. Then "at most its life" holds whatever the author writes.
  - If you choose not to add that law, reword §3.2 so the bound is conditional on the update rule.

### F3 (Medium) — The shared hub has no generation fence
- **Where:** §4.3 ("`Engine::reader` hands the same `Arc`"), §4.4 ("adoption clears the hub"). Code: `crates/snapback4/src/serve_adoption.rs:152-173`, `crates/snapback4-core/src/engine/mod.rs:318-323`.
- **What is wrong:**
  - Adoption either adopts in place or replaces the engine (`*engine = next`). It only invalidates future reader checkouts (`serve_adoption.rs:173`).
  - A reader checked out earlier, whose read transaction opened before the adoption commit, passes the store identity check. It can then lock the cleared hub and write a row under the old generation's indexes. Stale index entries follow: an added unique index is missing entries, and a table made durable leaves orphan memory rows.
- **Proposed change:**
  - The hub records the (store identity, generation) it serves.
  - Every hub access checks that pair under the lock. A mismatch refuses with the same retryable generation refusal the store uses (`crates/snapback4-core/src/store.rs:239-246`).
  - The first access at a new generation clears the hub and bumps the incarnation. This covers `dev` adoption, `open_engine_at` replacement and any other path.

### F4 (Medium) — Ephemeral wakes still reach the engine mutex and SQLite's writer lock
- **Where:** Summary ("does not take the store's writer lock"), §4.4 ("notifies `shared.committed`"), §4.7 ("succeeds while another thread holds the engine's writer lock").
- **What is wrong:**
  1. `shared.committed.notify_all()` also wakes the maintenance loop. It re-runs `delivery()` under the engine's background lock on every wake (`crates/snapback4/src/serve_maintenance.rs:116`, `:123`).
  2. Every poll iteration takes `lock(&shared.engine)` to read `store_id` and `seq` (`crates/snapback4/src/serve_changes.rs:33-39`). Any wake currently answers the poll (`serve_changes.rs:51-52`).
  3. Each ephemeral answer makes the client re-poll. Poll entry runs `presence_reconnected` under the engine mutex (`serve_changes.rs:21-28`), which opens an IMMEDIATE transaction (`crates/snapback4-core/src/engine/effects.rs:287-291`). So one typing write costs up to W writer-lock acquisitions, where W is the number of watching clients.
  4. The ephemeral `/m/` path itself takes `shared.engine` for bearer resolution (`crates/snapback4/src/serve.rs:697`) and for reader checkout (`serve.rs:995-999`). The §4.7 test therefore cannot pass if "writer lock" means the engine mutex.
- **Proposed change:**
  - Give polls their own wake counter and condvar, bumped by durable commits and ephemeral commits. Leave `committed` for maintenance.
  - On a wake where `shared.seq` is unchanged, check only the hub's ring, with no engine lock.
  - Skip `presence_reconnected` when a cheap read shows no pending `_effect_presence` deadline for the principal.
  - Reword the test to "while another connection holds a SQLite write transaction".
  - Optionally, coalesce ephemeral-only answers per poll to at least 100 ms apart. That bounds the amplification of a 20/s session into W re-runs.

### F5 (Medium) — Borrowing `&MemoryRows` in `Layered` serializes every query
- **Where:** §4.3 ("Every query runner … runs over a `Layered` whenever the schema has an ephemeral table"). Code: `crates/snapback4-core/src/rows.rs:291-296` (`RefCell` fields, so the type is `!Sync`), `crates/snapback4-core/src/engine/runner.rs:79`, `:226`.
- **What is wrong:**
  - `Layered { eph: &MemoryRows }` must keep the `MutexGuard` alive for the runner's lifetime.
  - Because `MemoryRows` is `!Sync`, an `RwLock` cannot share it across threads.
  - With the wrapper applied "whenever the schema has an ephemeral table", every query, including message pages, runs one at a time across the reader pool.
- **Proposed change:**
  - Wrap in `Layered` (and lock) only for programs whose static read closure includes an ephemeral table: read sites, rule probes, and native reads treated conservatively.
  - Hold the lock only for that metered run. Those programs are small.

### F6 (Medium) — The client sender cannot be built as specified, and it can reorder or silently drop calls
- **Where:** §2.4 rules 1–3; the generated op shape. Code: `packages/snapback4/src/client.ts` (no schema), `crates/snapback4-core/src/engine/write.rs` (delete, insert and upsert are independent requests).
- **What is wrong:**
  - **(a) The client cannot compute the window.** Rule 2 needs "the shortest life among the tables the operation writes". The generated op carries only `ephemeral: true`, and the online tier has no schema.
  - **(b) Calls can reorder across keys.** `stopTyping` has a different key, so it can be in flight at the same time as an earlier `setTyping`. If the server applies them in the opposite order, the row is resurrected for a full life after send.
  - **(c) The dequeue step is ambiguous.** It is unspecified whether rule 2 applies when a waiting call is dequeued.
  - **(d) The window can drop non-idempotent calls.** Rule 2 resolves a suppressed call "with the previous result". That silently drops calls that are not renewals, such as a toggle, a counter or an insert-new reaction. This contradicts §3.5's "never … a silent drop".
- **Proposed change:**
  - (a) Emit `renewMs = life/4` on the op fact and in `/schema` operations.
  - (b) Use one ephemeral lane per client: at most one request in flight, sent in call order. A newer same-key call replaces the older waiting call and moves to the end of the queue.
  - (c) Apply rule 2 both at call time and at dequeue.
  - (d) Apply the window only to ops the binder marks `renews`: writes are only upserts or updates of ephemeral rows keyed by arguments and viewer. All other ephemeral ops only coalesce.

### F7 (Medium) — The new retryable refusals would flip clients offline
- **Where:** §3.5 (`E_EPHEMERAL_FULL` and `E_RATE_LIMIT`, both retryable), §4.4. Code: `crates/snapback4/src/serve.rs:753-755` maps retryable errors to 503; `packages/snapback4/src/client.ts:378` does `if (response.status >= 500) { setLink("offline") …}`.
- **What is wrong:**
  - A capacity or rate refusal returned through the error arm becomes a 503.
  - The client then marks the whole link offline: watches, durable outbox and ephemeral sender.
  - Separately, `E_RATE_LIMIT` is family `auth` (`crates/snapback4-lang/src/guide/codes.rs:188`).
- **Proposed change:** return both as HTTP 200 with `{state:"failed", why}`, as rule refusals are. State that the ephemeral sender changes link state only on transport failure.

### F8 (Medium) — The chats-list typing hint must be a separate query, or M6 cold-offline regresses
- **Where:** §2.3 ("a compiled query for the chats list … in one read"), §2.5. Code: `crates/snapback4-lang/src/bind/residency.rs:209` (a table without `sync` gives a `Server` site) and `residency.rs:122` (any `Server` site makes the query `runs: "server"`).
- **What is wrong:**
  - Joining `typing` into the chats-list query makes the whole list server-answered.
  - The brief's M6 requires cold-start offline to show "all previously synced chats" (`benchmarks/briefs/social-messenger.md:615-620`).
  - Every typing write would also re-run every user's chats list on the server.
- **Proposed change:**
  - The card teaches a separate `typingInMyChats` query, rendered next to the device-held list. It says in one sentence never to join an ephemeral table into a list that must work offline.
  - Add a `check` note when a query becomes `runs: server` only because it reads an ephemeral table.

### F9 (Low) — Undo the journal on every exit, not just on refusal
- **Where:** §4.3 step 3. Code: `crates/snapback4-core/src/error.rs:234-236` (everything except store failures counts as a refusal).
- **Proposed change:** undo from a Drop guard unless the commit completes. That covers store errors and panics; `serve.rs` recovers poisoned locks, so a panic would otherwise leave partial writes and cap counts.

### F10 (Low) — `run`, `--fresh` and capacity edges
- **`run`:** `snapback4 run` opens the store in its own process (`crates/snapback4/src/verbs.rs:452`). `run setTyping` reports `sent`, but the dev server's clients never see the row. Print a note saying so.
- **`--fresh`:** in-memory stores have no reader (`store.rs:270-272`). The ephemeral `/m/` branch needs the same fallback to the serving engine that `/q/` has (`serve.rs:1010-1013`).
- **Capacity:**
  - The 100,000-row bound is global. One account with many rooms and `ephemeral 60s` heartbeats can starve everyone; add a per-principal share.
  - The maintenance sweep runs about once a second (`serve_maintenance.rs:105-116`). Count only live rows, or sweep before refusing, so that unswept expired rows do not cause spurious `E_EPHEMERAL_FULL` refusals.

### F11 (Low) — The React recipe calls the wrong shape
- **Where:** §2.4 recipe. Code: `packages/snapback4/src/react.tsx:283-285`; `packages/snapback4/CLIENT-AND-OPERATIONS.md:986`.
- **What is wrong:** `useMutation` returns `{ run, last, inFlight }`, so `setTyping({ roomId })` does not typecheck.
- **Proposed change:** use `setTyping.run({ roomId })` and `stopTyping.run({ roomId })`. Builders copy card code verbatim.

## What the RFC gets right

- **Table, not channel.** Rules, joins, generated types and hooks carry over. The engine really does run over a pluggable `Rows`.
- **Expiry reuses existing machinery.** Hanging expiry on `is_expiring()` and `$deadline` inherits absent-before-rules behaviour and expiry-aware caps (`crates/snapback4-core/src/engine/write.rs:569-577`). Same-id expired predecessors are removed before the put (`write.rs:180-186`), so `MemoryRows` index entries stay clean.
- **`nextExpiry` re-fetch already exists in both tiers.** See `client.ts:419-429` and `local.ts:911-926`. Only the wake is missing.
- **The capability fence works as claimed.** Unknown names are refused (`crates/snapback4-core/src/schema/capabilities.rs:99-101`).
- **The disclosure surface is not new.** Table-granular `/changes` already exposes per-table commit activity to any session (`serve_changes.rs:80-94`). The ephemeral epoch adds no new leak class.
- **The refusal set is sound.** It forbids durable→ephemeral dependencies.
- **The end-to-end test is a real test.** It is not a loopback no-op, it has a durable control, and it would catch F1.
- **Citations are accurate.** I checked them in §4.1, §4.4 and §4.6, and the wasm budget line (578,207 against 577,207) exactly.
