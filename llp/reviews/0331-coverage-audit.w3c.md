# Authorization coverage audit — Wave 3, part C (Uber, eBay, Events, Photos, Tournaments)

Tested against: LLP 0331 §"Snapback2 synthesis" core (llp/0331-scoped-roles-diary-feedback.research.md lines 104–420) as restated in the brief. Extension codes X1–X20 are the brief's fixed list (from llp/0329.014.004 §2–§6).

Citations: `D:n` = the `.design.md` artifact line n; `V:n` = the `.v0.md` artifact line n; `RFC:n` = 0329.014.004 line n; `W3:n` = 0329.014.003 line n; `0331:n` = LLP 0331 line n.

## Coding policy applied uniformly (read before merging)

1. **Two independent one-hop probes conjoined by `&&`/`||` are coded CORE**, as long as no found-row field feeds a second probe's key. 0331's restriction is stated as *one hop* (0331:115, 0331:274-277); the brief's X1 is defined by a found row feeding a further key. Rows that need two or three independent probes are noted as such so the merger can re-code if 0331 is read as "one probe per rule".
2. **`where` on the found row may compare found-row fields to the subject row's fields, `viewer`, and literals** using the core operators. Example in the corpus: eBay V:70 `listing(b.listingId).sellerId !== viewer`, V:80 `hammerCents === binPriceCents`. Coded CORE(where). A `where` that compares *two different found rows to each other* is beyond one probe and is flagged (Tournaments row 3).
3. **Time-bounded authority** (offer expiry, rating windows, check-in windows, refund windows) is coded CORE when the paper design or the v0 already lowered the window to a status column flipped by a schedule, so the rule term is a plain enum compare (RFC dimension B, RFC:169). It is coded X6 only when the *rule* must compare against a clock or a computed value no status column can carry. Every occurrence is noted "time-as-state" so the merger can count them.
4. **Public reads by a logged-out visitor** are coded CORE via `public(reason)` (0331 admits it in the operator list). If 0331's `public` turns out to require a session, every such row becomes X3(anon); those rows are noted "anon-read".
5. **System-only tables** (`insert: sys`, `rules(SYS)`) and schedules/effects that write under a system principal are coded **X11** on the row where the *product requirement* needs a writer that is not a human principal. 0331 has personas resolving to ordinary principals and no system/service principal; every v0 in this slice spells `sys = () => principal.kind === 'system'` as its first line.
6. **Hand-split audience tables** (the v0's "protection-class" views) are coded **CORE-with-denorm** naming the duplicated columns; X5 (engine-maintained projection with declared audience, RFC:200) is noted as the sugar, never as the requirement.
7. Capacity/count gates on writes (RSVP capacity, registration cap) are integrity constraints, not authority; they are coded CORE for the authority part with "(X17-shaped, integrity)" in the note, so they are visible but not counted as authorization extensions.

**App verdict: NEEDS: X11, X4 (X3-anon rides on X4).**
Authorization was incidental to this app; its hard problems were the timed exclusive lease, geo k-NN, the intent clock, and the visibility-filtered surge (V:667 "The most dangerous silent answer is marketplace surge"). Every human-facing rule is owner/party equality or a one-hop probe; the only denormalization is the audience split the v0 already performed by hand (row 5). X11 alone flips it to COVERED-WITH-DENORM once the anonymous share link is dropped to sign-in-only (V:732 lists that as an honest product change). The design reached for `ctx.now`-style clock authority in accept/cancel/quote (D:42, D:324), which the RFC refuted (RFC:477 "§4.3: `ctx.now` reused at settlement → security windows compare `commitTime`"); that is not an authorization extension but it is the reason none of the time windows above are rule terms.

**Sprawl check.**
- X11 — load-bearing. Without a system principal there is no dispatcher, no timeout closer, no surge publisher, and no settlement; D:459 "Polling is allowed as a transport … not as the arbiter of who holds the trip." The product's axis dies.
- X4 — droppable with a stated loss: share viewers must sign in (V:732); promise 11's "read-only map" survives for logged-in recipients only.
- X3(anon) — droppable; it exists here only as the principal of the share link.
- X9 (`ctx.device`) — not needed; noted in row 1 as the only way to bind the location write to the *device* rather than the account. Honest reduced product: same-account devices are trusted.
- X5 — not needed; the v0's five hand-maintained view tables are CORE-with-denorm.

**App verdict: NEEDS: X11, X19 (secondary; X6 trivially droppable).**
Authorization was not the hard problem — the design's traps are the fold-over-secret-maxima, the hard-close clock, five writers on one row, and commit-triggered alerts (D:67-119). Every party rule is a one-hop where, every secret is a table split, and the only negation is `noBids` whose truth is public. What core cannot do is the one thing the product is: a bid by Bob must rewrite Alice's public stand and Alice's notice (row 5). That is X11 (a system continuation, the RFC's dimension L) or X19 (the v0's `coupled` write, V:289). X11 alone flips it to COVERED-WITH-DENORM. The design itself reached for "OCC on the item row" as the BIN-vs-bid race, which the v0 shows is "true in effect, wrong in locus" (V:339; RFC:216-217): the conflict is on the proxy range the buyer's *rule* reads — i.e. 0331's rule-dependency tracing does the serialization, a point in core's favor.

**Sprawl check.**
- X11 — load-bearing. Without a system principal the fold cannot write Alice's row while serving Bob (D:504 R1 "A mutation that can only patch rows the caller owns cannot update Alice's public stand while serving Bob"), and close/expiry have no actor. D:506 names the only honest reduction: drop proxy bidding entirely ("each bid is a public English bid").
- X19 — droppable. With X11 the outbid edge and attributed events are program facts inside a trusted system continuation; X19 only makes "notice only on the edge" an *engine* fact (V:289). The product ships without it.
- X6 — droppable. Two arithmetic equalities (row 8) are columns the program writes; `immutable` on them (V:80 "immutable parties, amounts") gives the same guarantee.
