## Alias custody and recursion (the regression focus)

- Canonical source of truth is resolved, not assumed. `source` is canonicalized by `existing_deployment`, then `database = source.join("store.sqlite").canonicalize()` and `assets = <canonical-db-parent>/assets` ([promote.rs:29-30](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:29)). The snapshot comes from `VACUUM INTO` on a read-only open of the canonical DB (backup surface, not file bytes), and the asset tree copied is the canonical sibling — so deployment-local `staging/assets` shadow bytes are never read ([promote.rs:36-49](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:36)). `Store::open`/`open_read_only` both derive `assets_dir` from the canonicalized DB path, so the candidate-side ledger check in `promote_snapshot` validates the copied canonical bytes ([promotion.rs:9-34](/tmp/rel4/review6/snapback4/crates/snapback4-core/src/store/promotion.rs:9)). Same-length `good`/`evil` shadows therefore cannot survive: length checks pass either way, but the bytes copied are the canonical ones, which is exactly what the regression asserts.
- Recursion is refused on both axes before any candidate is created: destination inside/equal to source ([promote.rs:27](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:27)) and destination inside/equal to the resolved asset tree ([promote.rs:31](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:31)). Because the candidate is `parent.join(hidden-id)`, a candidate inside source/assets would imply the destination is there too, which is already refused — so the candidate cannot smuggle recursion past either check. Both directions (`starts_with` either way) are covered for source; the asset check covers destination-within-asset-tree, the direction that would cause recursive self-copy.
- Exclusion is held end to end. The blocking release-command lock ([promote.rs:28](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:28)) and the no-create owner `try_lock` on the canonical DB's sidecar ([promote.rs:34-35](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:34)) are both bound to locals live until `plan` returns, spanning snapshot, copies, attach, preflight, and rename. The owner file is the same canonical path the live host holds, so a running source deterministically fails with the named `stop` repair.

Credential hashes, account ids, row data, and generation-scoped fencing survive, so old tokens (full, read-narrowed, service) all resolve to nothing while password login returns the same principal — matching both the core and CLI assertions.

- Quiescent-work coverage matches the enumerated surfaces (`_jobs`, `_requests`, `_outbox` queued/running; `_action_steps`/`_effect_steps` started), each guarded by table-existence checks; step states are `started`/`done`/`parked`, so `started` is exactly the unsettled set.

## Backend/source binding, strict preflight, publish atomicity

- The startup-binding correction is real: attach goes through ordinary `Project::open_release_engine`, which rejects `release source differs from its activated backend`, plus `native::install`'s module-digest check — before either preview or publish ([promote.rs:66-76](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:66)). The mismatch regression's expected message comes from that layer, and both `--check` and publish reach it identically since the preview branch is after all checks.
- Strict security runs on a genuinely separate scratch project (`candidate/.promotion-check`, a full copy of the selected release), with caches applied there and the copy removed afterward; immutable releases are re-digested against source after preflight ([promote.rs:71-90](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:71)). Worker staging writes under `.snapback4` (digest-ignored) with `Drop` cleanup, so `prepare_release` cannot false-trigger the re-digest.
- Publication is no-replacement only (`renameat2(RENAME_NOREPLACE)` / `renamex_np(RENAME_EXCL)`), unsupported hosts refused up front; candidate cleanup is armed only after exclusive creation and disarmed immediately after rename, so allocation races keep the existing dir and parent-sync failure keeps the published destination with an honest message ([promote.rs:44-100](/tmp/rel4/review6/snapback4/crates/snapback4/src/verbs/promote.rs:44)). Preview returns before flush/rename with the candidate removed by `Drop` — it never publishes and leaves no destination.

## Non-blocking observations (not READY blockers)

- Released (`released_at NOT NULL`) asset bytes are copied if present but not individually ledger-validated; only unreleased rows get the missing/length check. Silent pass on a missing released byte is possible. The spec's "active/retained" language and the regression both center on the unreleased ledger, so this is noted, not charged.
- The guest read-session query assumes `cap_expires_at` exists whenever `_read_sessions` does; on a hypothetical older schema this fails closed (refusal), never corrupts.
- A killed run can leave hidden `.snapback4-promote-*` candidates; they are never implicitly served (explicit paths only) and retries mint fresh ids.
