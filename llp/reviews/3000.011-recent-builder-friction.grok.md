## 3000.011.000.000 — Contextual compiler guidance

**Verdict: READY WITH CHANGES.**

**Usefulness.** High for the three recurring shapes, and small if kept there. The 0.2.31 diary's feed-id bridge, reaction prefix, and presence-guard mistakes are real correction loops (`benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/astra/lane-diary.md` M2, M4, M6). The builder also says the diagnostics were right. Richer context is a hypothesis, which the RFC already treats as one.

**Material concerns.**

1. **Medium. The first increment can become a second analyzer.** The binder already explains these cases. A reference with a field access is `E_QUARRY_TYPE` with a same-table rewrite (`snapback4/crates/snapback4-lang/src/bind/program/expr.rs` 242–249). An unpinned membership rule is `N_NEVER_COMPLETE`, naming the rule columns and an index (`snapback4/crates/snapback4-lang/src/bind/mod.rs` 347–365). Presence that decides a fallible arm is a server site whose rewrite is already "decide only the emit with presence" (`snapback4/crates/snapback4-lang/src/bind/residency/presence.rs` 11–38, 80–86). `N_NOT_PREDICTABLE` already dedupes causes and sites (`residency.rs` 351–364). The prediction card already separates server data, horizon misses, and guarded fallibility (`guide/prediction.rs` 18–35, 117–120).
   **Fix.** Land the RFC's step 1 as the whole first change: three small programs copied from those diary shapes, with today's terminal and `--json` text checked in. Add a field only where that fixture shows the builder still has to infer a link. If today's text is enough, stop.

2. **Medium. The open question about helper paths invites a compiler rewrite.** §6 asks whether call sites survive inlining. The binder already keeps source sites, including expanded helpers (`bind/program.rs` 725–728).
   **Fix.** Close §6 in the revision: use those sites. If the only site is the helper body, name that file and link the card. Do not add an IR for inlined stacks in this increment. Put the short refusal on stderr and the longer path on the existing `why <op>` text. `--json` keeps the current codes; new detail is an additive field.

3. **Medium. A "working rewrite" can change behavior.** §3 correctly forbids hoisting a fallible read out of a guard, changing rules, dropping a horizon, raising a cap, or adding a unique index as `check --fix`. `check --fix` is already limited to mechanical spelling and index edits (`guide/language.rs` 477–483; `diag.rs` 49–54).
   **Fix.** A suggested expression is pasted into the user's names and must compile, and it is never marked `mechanical` unless it is one of today's mechanical repairs. Suggest `.id` only when that value's type is already a reference to the expected table. Never suggest casting one table's id to another. For feed post versus recipe event, do not add a conversion; that belongs to 3000.011.002.000.

**Already present, so do not rebuild.** `check`, `why <op>`, `check --json`, `check --fix`, the prediction and programs cards, and `N_NOT_PREDICTABLE` / `N_NEVER_COMPLETE` / `E_QUARRY_TYPE`.

**Smallest scope.** The three fixtures, plus at most the missing call-site or scan-site text they justify. No pilot harness is required to land that. A later descriptive pilot is optional and is not a score gate.

## 3000.011.001.000 — Digests beyond one chunk

**Verdict: READY WITH CHANGES.**

**Usefulness.** High, and this is the one proposal that removes a real design the current card still teaches. The direct digest is the right default inside its envelope (`guide/jobs.rs` 112–225; LLP 3000.007.002 §6). The 0.2.31 scale run then parked at the 16 MiB heap after a whole-chat count, and narrowing the projection did not help (`lane-final-report.md` lines 26 and 55–56; `benchmarks/runs/2026-09-20-snapback4-clique-astra-0.2.31/README.md` 83–85). The replacement, 33,949 chunks and 580,996 writes, then a zero-write rerun, is that app's cost, not a universal lower bound.

**Directional decision.** The paged recipe does not promise an exact snapshot. Message eligibility is fixed when the contribution commits. Emission rechecks only current recipient membership and drops conversations whose membership row is gone. On quiescent data it must match the direct recipe and an independent oracle. If a product needs counts that subtract reads, tombstones, and expirations that happen after admission, that is a different design and this recipe must not pretend to be it. That is the decision §3 asks for; do not leave it open in the helper.

**Material concerns.**

1. **High. The card's "complete" large-digest example is the bug the RFC means to replace.** `digestLarge` still calls `unreadIn`, which is `count(... first 100 ...)`, then deletes the total on emit (`guide/jobs.rs` 243–253 and 329–342). Deleting the total is explicitly not an emission marker, so a replacement run can count twice. A scan charges the full stored row, twice, before any projection (`snapback4/crates/snapback4-core/src/store.rs` 821–844). Job ceilings are 16,384 examined rows, 8,192 writes, and 16 MiB of heap (`meter.rs` 22–30). A smaller outer chunk around that inner count repeats the diary failure.
   **Fix.** Replace that example in place. Do not add a third recipe beside it. Size each chunk from stored-row bytes on the worst fixture body, not from the examined-row ceiling. One message that cannot fit fails that chunk closed. Do not raise the heap ceiling.

2. **High. Period close is unspecified for two live runs.** A schedule will not fire the same boundary twice, and a restart resumes a queued or running job at the committed cursor (`engine/job.rs` 212–216, 260–263, 317–322). A parked job is not in that set (`job.rs` 220). `snapback4 run` always enqueues a new id (`job.rs` 191–198). The host runs one chunk of the oldest queued or running job at a time, so a manual retry interleaves with a live scheduled run. Contribution identity stops a double add inside one transaction. It does not stop the first run to finish its sweep from emitting, after which "no duplicate emission" drops whatever the second run adds later.
   **Fix.** One server-only period row per policy version and period: `open`, `emitted`. Only the run that moves `open` to `emitted` may emit, and it does that only after its own accumulation sweep has finished. A second run that finds `open` owned by a still queued or running job writes nothing and emits nothing. A second run that finds the owner parked may adopt the existing contribution rows, rescan, and skip admitted messages. A second run that finds `emitted` emits nothing. Never clear an emission marker as part of retry. Missed schedule boundaries still coalesce to the latest period; this recipe does not backfill skipped days.

3. **Medium. "Membership incarnation" is not a primitive.** Membership continuity is the membership row id. A leave and rejoin inserts a new id unless the client reuses one. The RFC correctly says not to invent continuity from a reused id, then offers either an incarnation or a recompute.
   **Fix.** Store the membership row id on the contribution. At emission, if that row is absent, drop that conversation's contributions. Do not add an incarnation column. A recompute, if ever needed, is a later bounded rescan of that one conversation, not part of the first example.

4. **Medium. Cleanup and delivery identity.** Effect `meta.id` dedupes lease retries of that one effect row (`guide/effects.rs` 107–120). A new emit gets a new id. The jobs card already says a re-queued period can emit again unless the worker uses `(targetUserId, periodEnd)` or a marker (`guide/jobs.rs` 232–239).
   **Fix.** The provider key is the payload business key `(policy, recipient, period)`, not `meta.id` alone. Markers are `read <- deny`, not synced, and hold no message body. The first increment documents that they are kept for the life of the store. Do not delete them, and do not ship the installer, until a measured retry horizon exists. Deleting markers while still accepting old reruns breaks the idempotency the zero-write rerun depended on.

**Already present.** Direct period-seeking digest, chunk cursors, `E_JOB_GENERATION`, `E_BOUND`, `doctor` for a parked run, effect admission, and worker idempotency guidance. System jobs pass every rule, so the recipe must keep proving membership itself (`guide/jobs.rs` 122–125).

**Smallest scope.** One compiled jobs-card program and engine tests: quiescent oracle match, crash before and after contribution commit, crash before and after emission, same-run resume, parked-then-replacement, second live run, membership delete and rejoin, expiry during the run, empty period, and no emit of a zero total. Fixtures: many quiet chats, one 10,000-message chat with large bodies, and both. Record heap, examined rows, writes, chunks, and marker bytes. No generator and no new job syntax.

## 3000.011.002.000 — Simpler feed integration

**Verdict: READY WITH CHANGES.**

**Usefulness.** The bridge half is a direct hit on the 0.2.31 M2 correction loop. The overflow half is a justified experiment and a bad default. The recipe's 32 slots are pull lanes for shared authors, not a cap of 32 follows and not search's 32-word bound.

**Material concerns.**

1. **High. Do not treat "same Following" as something the online merge already is.** Promotion needs a free pull slot for every follower, including a dormant one. If any follower is at 32, the whole follow rolls back and that author can stay at 50 followers indefinitely (`guide/feeds.md` 398–415). That behavior is documented source, not a failure the latest Clique celebrity fixture hit (one such lane). A read-time merge of all follows was already measured slower at 500 follows than at 5 (LLP 3000.007 §21.3 P1: about 2.5–3.1× metered requests, 7.3–9.0× on bare clients, about +2.5 ms per 500-lane page). Query examined ceiling is 8,192 (`meter.rs` 23). A meter-cut merge is not a complete feed (`guide/feeds.md` 88–93).
   **Fix.** Ship bridges without the experiment. Before any overflow code, write the workload and the stop numbers: examined rows, heap, latency, and whether `complete` / `cut` / `next` match the recipe oracle. Mismatch, a higher meter, a second interpreter, or a result cache stops the experiment. No automatic fallback and no mixed cursors. Offline scope for that path must say what history is missing.

2. **Medium. The generated client file is not the bridge the diary needed.** `init --recipe feeds` already writes `snapback/feed.q` and `src/following.ts` (`verbs/init.rs` 29–45). With a prefix it removes the mutation wrappers and leaves comments telling the builder to insert a recipe event and call `feedDeliver` in their own mutation (`verbs/init/following.ts` 7–30). That is the row-versus-reference loop.
   **Fix.** Generate `fn` helpers typed to the selected app post table, author reference, event time, and follow relation. Resolve those against Quarry types. If the mapping is ambiguous, print what is missing and leave today's manual path. The app calls the helper inside its existing mutation. The installer must not edit that mutation, widen its rules, or overwrite `feed.q`. Follow, unfollow, publish, and remove stay one transaction, with today's rollback. Reposts keep a distinct actor. Media stays on the home row. Backfill stays an explicit resumable step.

3. **Low. Ranking must not grow a second aggregate.** LLP 3000.007.001 is accepted and is not this package's paved syntax; the feeds card still uses `maintain` tables (`guide/feeds.md` 1047, 1252). The 0.2.31 pin did not have the column mechanism.
   **Fix.** Leave ranking on the current maintained-table recipes. Consume maintained columns only after that design is in the published package. No device prediction of those columns in this work.

**Already present.** Atomic promotion refusal (`FEED_PULL_CAP`, `FEED_PROMOTION_PULL_CAP`), public `pullCounts` so a server query can name the saturated follower (`feeds.md` 416–421), collision checks, cap sizing, and `test --residency`. Search still allows at most 32 words only in an admitted non-uniform scope; uniform scopes are meter-bounded (`guide/search.rs` 67–70; `NOT-DOING.md` line 36).

**Smallest scope.** The bridge module, mismatch refusals, and the existing follow, unfollow, repost, delete, retry, backfill, and promotion-rollback cases. Measure its runtime against the same hand-bridged recipe. Leave 32 where it is.

## 3000.011.003.000 — Offline-ready starters

**Verdict: READY WITH CHANGES.**

**Usefulness.** Real, and it is application composition, not a missing replica. The 0.2.30 diary's DM route called an online pair-dedup mutation before showing a cached room, and the shell worker was added by hand (`0.2.30` diary, M6). The 0.2.31 web offline reload succeeded (`lane-final-report.md` line 30). Those are different facts. The README already assigns the shell to the app (`packages/snapback4/README.md` 263–266). No service worker exists in the starters.

**Material concerns.**

1. **High. The sign-out test can be implemented by deleting the wrong store.** The replica name is `snapback4-${server:viewer}` (`packages/snapback4/src/local.ts` 231). `signOut` calls logout, which ignores an offline network error (`auth.ts` 129–134), then `endSession` clears the session and the SDK media cache (`local.ts` 482–499, 1364–1368). It does not delete that viewer's replica or outbox. The README says account switching must settle the old account's pending writes (`README.md` 263).
   **Fix.** Switching accounts opens the other viewer's client. It never flushes A's outbox as B. Offline switch leaves A's pending writes in A's store and does not claim they settled; do not block sign-out on the network. Online switch waits for A's terminal states or shows that they are still pending for A. The shell cache test asserts that the Cache API has no API response, token, upload, or user bytes. It must not require deleting the replica. Dev hot reload must not register the production worker.

2. **Medium. A broad service worker recreates the privacy bug the RFC is trying to prevent.** Authenticated reads and media already live in the SDK store.
   **Fix.** One published web starter only. Cache the navigation shell and that build's immutable assets. Do not cache `/m`, `/q`, `/auth`, or media. A new deployment must not delete assets an open tab is still running. If the bundler already does this, configure it instead of adding a second worker. Prove it by opening a new page realm with the network down.

3. **Medium. Truthful local state is already specified and easy to violate in the example.** `complete`, `fresh`, `usePendingWrite(op, id)`, and terminal failure already exist (`guide/prediction.rs` 3–10). A horizon miss is not absence. The 0.2.29 unfollow case is replica freshness versus authoritative settlement, not a reason to call `sync()` before every navigation (`0.2.29` diary, M2; RFC §2).
   **Fix.** The example reads the held membership first and renders it without a create mutation. An unknown room offline stays uncertain: no create, and no "not found." A pending write with no predicted row uses the saved intent id across reload. A failed write stays visible with its code. Predicted rows keep `pending`. Do not add a shadow queue or a new read state.

**Already present.** Viewer-scoped stores, outbox, `client.acquired` / `useAcquired()`, pending-write hook, sign-out, and `test --residency`. Expo Go is already the online tier (`CLIENT-AND-OPERATIONS.md` 1319–1323). A Hermes export is not native execution; that evidence is 3000.011.005.000.

**Smallest scope.** The web starter's room route, pending and failed write display, and the shell worker, plus the acceptance journeys in RFC §5 except the Clique residency pair. That pair waits until both configurations have the same required offline answers. A smaller horizon is not an equivalent speedup. Expo work in this increment is limited to not relabeling Expo Go or a Hermes bundle.

## 3000.011.004.000 — Coordinated development commands

**Verdict: READY WITH CHANGES.**

**Usefulness.** The symptom is real and the proposed lock service is larger than the symptom. Both diaries got `E_STORE` / `database is locked` from an overlapping writer, then succeeded when run alone (`0.2.30` diary, final boundary; `0.2.31` diary, M8 follow-through; `0.2.31/README.md` 85–87). No lost data, torn activation, or corruption is shown.

**Material concerns.**

1. **High. A new advisory lock is not the first fix, and the existing exclusive lock cannot be reused as one.** SQLite already waits 5 seconds (`store.rs` 67 and 106). `dev` startup retries a lock forever and says so (`serve_adoption.rs` 14–28). Background adoption retries `E_STORE` and `E_GENERATION` (`serve_adoption.rs` 51–58). `dev` and `serve` hold `serve.lock` for their whole life (`verbs/releases.rs` 11–23). `run` does not take that lock. `run` opens the store and activates the working schema (`project.rs` 229–236; `engine/mod.rs` 255–262). A long maintain rebuild holds the writer for the whole transaction (LLP 3000.000, implementation follow-up: "Long changed-maintain rebuilds still hold the writer transaction"). Five seconds is shorter than that rebuild, which matches the 0.2.30 backfill race. An advisory lock taken for every host mutation would serialize work the diary never showed contending, and taking `serve.lock` inside `run` would make `run` impossible while `dev` is up.
   **Fix.** Reproduce both races with barriers. Then retry only `SQLITE_BUSY` / `SQLITE_LOCKED`, with elapsed time, the operation, and a typed timeout whose default comes from a measured rebuild. Do not relabel other `E_STORE` or I/O as contention. Do not copy `dev`'s infinite startup loop onto the CLI. Add a shared lock only if that retry cannot pass the reproduction. Do not extend either mechanism to `serve`, backups, or online migration.

2. **High. Retry does not stop `run` from adopting under a live host.** After the wait, `Engine::new` still activates whatever the CLI compiled. A `--no-watch` host keeps the old generation until restart (`CLIENT-AND-OPERATIONS.md` 998–999). Generation checks refuse a stale engine (`LLP 3000.000` follow-up); they do not stop the CLI from being the adopter.
   **Fix.** If `serve.lock` is held, `run` must not activate a different schema. It attaches to the persisted generation, or waits until the host publishes the source it compiled, and then executes. If no host holds the lock, keep today's adopt-and-run path. Recompile if source changed during the wait. Do not kill the holder.

3. **Medium. Do not retry a write that may have committed.** `run` prints the job id only after `run_job` returns (`verbs.rs` 406–418). A kill after enqueue leaves a queued job, and a naive retry enqueues another.
   **Fix.** This increment retries only failures known to happen before admission or after rollback. If the job id cannot be observed after an interrupted CLI, stop there. Do not invent exactly-once job admission. `sql` and `data` stay read-only. `doctor` already has adoption and parked-job lines (`guide/refusals.rs` 40–41); extend that report instead of replacing it.

**Already present.** `busy_timeout`, dev adoption retry, `doctor`, generation fences, read-only inspection, and the deployment lock.

**Smallest scope.** The two barrier tests, the bounded busy retry, the live-host non-adoption rule, and the operations-doc paragraph that describes the resulting sequence. Manual stop, run, restart stays documented for anything else.

## 3000.011.005.000 — Qualify the built application

**Verdict: READY.**

**Usefulness.** High as evidence, and it correctly refuses to turn missing evidence into a defect. The 0.2.31 report claims no simulator, device install, push delivery, or hosted deploy (`lane-final-report.md` 20 and 62). The grader marks `m6-a01` and the following native cells `not-run` because the simulator files are absent and Hermes exports do not count (`grader-report.json` 538–542). Web and server proofs in that run did happen. Earlier reference-app witnesses remain their own evidence.

**What to watch, without blocking.**

- The published witness already drives an installed Release app, owns `dev --no-watch`, records video, receipts, and a hashed manifest, and builds nothing (`guide/witness.md` 1–5, 78–88, 117–139). The sample runner covers primed history, two pending sends, relaunch, and ordered settlement. Search, media, view-once, and revocation are application assertions the card already allows, not a second harness. Assert the app's declared leave policy. Do not invent one in the runner.
- A queued or running job resumes after process restart. A parked job does not (`engine/job.rs` 220). The restart cell should use a queued job.
- The stopped-backup procedure already exists and already says fresh outbox, workers disconnected, rollback is source activation, and this is not power-loss proof (`CLIENT-AND-OPERATIONS.md` 1249–1277). The RFC matches that. Do not write a success into the LLP until those artifacts exist.
- The parent authorization to publish does not name a push account or recipient (`3000.011` §6). Test-double crashes can land first. A real send waits for an explicit account and recipient. No secrets in the run directory. If the provider cannot dedupe, record that ambiguity.
- Peak memory is recorded only where the host exposes it. JavaScript heap is not native or wasm memory. Server query timings are not acquisition timings (`lane-final-report.md` 67).
- Package pins, simulator availability, and any instrument change are recorded before the next Clique run. A new native pass is not comparable to 0.2.29–0.2.31 unless the report says the environment changed. LLP 3000.010 forbids reading the score series as the cause.

**Already present.** `snapback4 witness ios`, `snapback4-expo/witness`, `witness/expo.mjs`, `deploy` / `rollback` / `serve`, and the isolated restore procedure. No new registry, badge, or push gate.

**Smallest scope.** One Release install of the app under test, on a dedicated booted simulator, running the published prime / offline / relaunch / reconnect scenario, with the manifest and a fresh artifact directory kept. Deploy, restore, provider, acquisition, and the extra assertions are separate rows in the same coverage table. Unavailable simulator, signing identity, or provider account stays `not-run`.

## Cross-proposal concerns

- **Private digest state and public feed state are different residency problems.** Digest totals and markers stay unreadable and unsynced. The feed recipe's public posts, follows, and broadcast rows are acquired by every device (`guide/feeds.md` 503–515). Do not "speed up" startup by putting a horizon on the recipe inbox; the card says that makes an exhausted lane incomplete (`feeds.md` 464–465). Measure acquisition with the existing residency command. A smaller fixture is not a faster equivalent product.
- **CLI retry and digest idempotency solve different double-runs.** 3000.011.004.000 stops a locked `run` from being started twice before admission. It does not make two successful digest runs one emission. That is the marker and period row in 3000.011.001.000. Do not block the digest recipe on the coordinator.
- **Feed reference errors should be fixed in the bridge, not the type checker.** 3000.011.000.000 should not grow a cast from an app post id to a recipe event id.
- **Maintained columns, result caches, a jobs framework, and higher meters stay out.** NOT-DOING forbids a per-query result cache, a second interpreter, and a jobs framework. LLP 3000.007.001 owns maintained columns. None of these six RFCs should implement them or raise the 16 MiB heap, the 32 pull slots, or the non-uniform 32-word search bound.
- **Do not score the program with one Clique number.** These runs are one builder family. A pilot that counts correction loops is descriptive. Keep failed attempts and unrun cells.

## Sequencing

1. **Compiler fixtures and the narrow CLI retry, in parallel.** Both are small, both can falsify a larger design, and neither depends on the others.
2. **Replace `digestLarge` and prove the period row in engine tests.** This is the correctness-sensitive change. No installer until those tests exist.
3. **Feed bridges.** Independent of the digest once the compiler work is not also inventing feed casts.
4. **Web starter route, pending writes, and shell cache.** Then the native witness can assert behavior the starter actually teaches. The published witness scenario can still run on the current app before the shell worker exists; do not block 3000.011.005.000 on it.
5. **Native witness as soon as a simulator is available.** Deploy and provider only with a disposable deployment and an explicit recipient. Otherwise record `not-run`.
6. **Only after the above:** the feed overflow measurement, and only with thresholds written first; the paired residency configurations, and only where offline answers match; digest marker deletion; a CLI advisory lock, and only if busy-retry fails the barrier tests.
7. **Then publish and rerun Clique,** with pins and any instrument change stated. Existing publication qualification still applies. A green native witness does not qualify deploy or push.
