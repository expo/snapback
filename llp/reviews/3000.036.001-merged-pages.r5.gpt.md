Two material size-bound gaps remain. The revision-5 totality, recursive capability detection and lane-prefix digest fixes are present and appear sound under static review.

1. **MATERIAL — Branch descriptors can still exceed the cursor limit.**  
   RFC §5 and §13, round-4 finding 3. [ir.rs:477](/tmp/sb4-merge-confirm-r5/snapback4/crates/snapback4-core/src/ir.rs:477) concatenates every lane’s index name; [cursor.rs:93](/tmp/sb4-merge-confirm-r5/snapback4/crates/snapback4-core/src/cursor.rs:93) rejects encoded JSON exceeding 4,096 bytes.

   Concrete scenario: an online `cards` table has `read <- exists members[.board, viewer]` and a declared index on `board, at, id` whose name is 507 ASCII letters. The table/index labels total 512 bytes, which is permitted. A query with eight alternatives, `.board = 1 or … or .board = 8`, merges eight lanes reusing that index. With membership and matching cards in those boards, `last 1 by .at after c` needs continuation. Its descriptor alone occupies **4,067 bytes**; the 64-character scope digest and remaining fields necessarily exceed the limit. A representative canonical token is **4,273 bytes**. Encoding `next` therefore refuses the query with `E_INPUT`.

   **Smallest fix:** use a bounded digest of the ordered index identities and grant markers as the branch descriptor. Retain the separate prefix-scope digest and add a long-index-name continuation regression. Hashing prefixes fixes the reported wide-prefix case, but leaves this independent source of token growth.

2. **MATERIAL — Optional expansion can make a previously valid program fail compilation.**  
   RFC §3 promises fallback when branch planning raises diagnostics. [intent_branches.rs:43](/tmp/sb4-merge-confirm-r5/snapback4/crates/snapback4-lang/src/bind/intent_branches.rs:43) checks component count, then commits requests without checking encoded key bytes. The portable byte check runs later at [bind/mod.rs:137](/tmp/sb4-merge-confirm-r5/snapback4/crates/snapback4-lang/src/bind/mod.rs:137).

   Concrete scenario: use an online table with `owner: principal`, `assignee: principal ?`, `folder: text <=435`, `at: int`, and the two-party read rule. Query:

   ```quarry
   query mine(folder: text <=435, c: cursor ?):
     return tasks where .folder = folder last 1 by .at after c
   ```

   The original `[folder, at, id]` index has a declared encoded bound of **2,028 bytes**, within 2,048. Each generated party index adds a 138-byte principal component, producing **2,166 bytes**. Both pass the eight-component check, but [key_bound.rs:61](/tmp/sb4-merge-confirm-r5/snapback4/crates/snapback4-lang/src/bind/key_bound.rs:61) subsequently emits `E_INDEX_KEY_BYTES`. This is a compilation regression introduced by expansion.

   **Smallest fix:** validate prospective lane indexes against portable key and label bounds before committing the cloned requests. On failure, discard those requests and plan the original read. Add this boundary case alongside the existing 400-character-folder regression.

   Concrete scenario: the existing [nested-shape capability test:725](/tmp/sb4-merge-confirm-r5/snapback4/crates/snapback4-lang/tests/branch_merge.rs:725) returns a header containing `tasks last 1 …`. Its nested case-2 merge contains an unpinned grant lane. That lane escapes suppression and generates `N_NEVER_COMPLETE`, although runtime execution decides the merge.

   **Smallest fix:** gather grant lanes with `ir::body_merges`, as capability detection now does, and extend that test to assert absence of `N_NEVER_COMPLETE`.
