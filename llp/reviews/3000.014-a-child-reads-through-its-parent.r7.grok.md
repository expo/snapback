## 2. The lifetime rule

It holds for authoritative server state. I could not build a live child whose parent is gone, or whose captures differ from its live parent's fields.

- **Delete, jobs, same mutation.** A live child blocks the delete, including one inserted earlier in the same transaction and including a job or seed delete. Read authority is checked first. Inserting a child after the parent delete fails the live-parent check.
- **Expiry and three levels.** Grandparent deadline Monday, middle table with no `expire at`, leaf authored deadline next year: both descendants store Monday and are not live after it. The middle parent's authored expiry is immutable (§4.2), so it cannot move earlier under a child that already captured it.
- **Sweep and same-id replacement.** A physical child, expired or not, blocks parent-id reuse and blocks the sweep from removing the parent. Child deadlines are no later than the parent's, so the children are already expired when the parent is.
- **Upsert.** The update arm keeps the captured parent deadline and recomputes the effective instant, which cannot pass it. An expired target takes the insert arm and needs a live parent again.
- **Seeds, imports, activation.** Ancestor-first capture, refusal of a parent image whose captured fields differ while a physical child remains, and expiry judged under the previous schema before recapture. Activation fails closed if a live child has no live parent.
- **Restore.** A valid image recomputes the derived instant from the stamped capture. It does not retarget the child onto a different parent.
- **Devices.** Finite deadlines follow the monotone clock: server time 110 applied on a device at 90 expires a child whose effective deadline is 100. A deadline of never is not expired by that clock. A reused id whose current children do not match does not get one verdict. A disconnected device can be late together with its parent; that is the skew the text already declines to promise.

## 3. New defect

**Medium — §5, fallback versus retained rows.** Comments retain delivered history. Issue `X` is **unknown** (the issue table has a horizon and `X` is past it), or the id was reused and a current child on the device does not match. §5 sends that read to the server. The same paragraph says no parent outcome erases retained children, including when the parent is replaced.

Those two instructions do not survive the current client. The engine records an unknown fact. `only_retained_incomplete` is then false, so the wire `retained` flag is cleared even if retained rows were read (`device.rs`). Online, `wantsServer` is true and `local.ts` replaces the whole answer with the server page. The server has no retained history, so the comments disappear while online. Implementing "don't erase" by not reporting unknown does the opposite damage: the mismatch never reaches the server, and the new issue's current comments stay hidden.

Smallest change: a server fallback replaces the **current** page only. Retained rows stay in that same answer with `retained: true`, and an unknown current page does not clear the flag. Mismatched current rows stay out of the local page.

## What is sound

`read through .ref` as the whole read rule, on one required immutable id with no default, is the right cut. Ordinary application tables only, service grants only on the parent, and copying the immediate parent's stored inputs are the right restrictions. The captured parent deadline is a separate immutable field; the effective instant is recomputed on every write, including a trusted restore, and capped by that capture. One expiring classification, read at every gate, is the right formulation. Exact admission, the insert order, keyed views, and the four parent outcomes are sound. On a server commit, through three levels, a child lives inside its parent, and a reused id does not meet an old child.
