# Blind design review: LLP 3000.038 (reference `on delete` actions)

I read the RFC, the five cited LLPs at the cited sections, and the cited code (engine `write.rs`/`through.rs`/`write_target.rs`/`authorized_scan.rs`/`mod.rs`, schema `reservations.rs`/`capabilities.rs`, lang `bind/delete_children.rs`/`bind/schema.rs`/`parser.rs`, device `Rows` surface, Lean README). No files changed. What follows is the review.

## What is sound

- **`restrict` as the default** is the right call. It matches SQL, matches `read through`'s existing refusal posture, and answers the farm evidence (lane 081, the hand-written zero-count guards). The migration machinery (`N_DELETE_RESTRICTED` at delete sites, capability fence, "declare `restrict` to silence") is the honest way to land a behavior change.
- **Cap-bounded cascade/set-null under the 3000.015 reservation law** is the right bound. Reusing `cap N by column` (which the device proofs in 3000.007 §20.5 already understand) instead of inventing whole-group admission is coherent, and the three §5.3 recipes are real alternatives using machinery that exists.
- **No background sweep** is correctly justified: delayed tombstone semantics would reintroduce the bug with a timer, break atomicity authors expect from `ON DELETE CASCADE`, and require an id-lifetime rule ordinary references don't have.
- **Parent-authorizes-cascade as the base rule**, the read-gate generalization from 3000.014 §3.1, **queue-without-complete-proof** on devices, the **read-through cascade condition** (no finite effective deadline possible, so physical children = live children and §3.3 holds), **children-before-parent ordering**, expiry-is-not-delete, and the existing-orphans stance in §8 are all sound as far as they go. The defects below are gaps in the edges around them, not in this core.

## Findings

### 1. High — §2.2/§4.1: set-null eligibility misses rule hops and sync paths that traverse the column

§2.2 excludes a set-null column that is "read by the child's read rule or named by its `sync` audience". Read narrowly (direct field reads, direct audience columns), this misses traversal. Concrete scenario: `tasks` has nullable `project: projects ? on delete set null`, and its read rule is `read <- exists members[.project.org, viewer]` (a legal probe key traversing `.project`, cf. the membership-path spelling in 3000.014 §2). Nulling `.project` changes every future read/update/delete verdict on that row — the parent's deleter moves rows between audiences it was never authorized to move, through a column the exclusion does not name. The same holds for write-rule hops (`Reference`/`ReferenceChain` in `schema/reference.rs` explicitly allow up to three hops in write rules) and for `sync to members[.message.conversation]`-style audiences traversed through the column (nulling changes the group in `partition.rs:group_of`, emitting `del`/`put` partition moves).

Fix: define "read by" as *any probe key, equality, hop, or sync-audience path that traverses the column*, and refuse `E_REFERENCE_ACTION` for all of them. One sentence in §2.2 plus a binder test.

### 2. High — §2.1/§2.2: there is no `keep`, so the deliberate-orphan pattern becomes undeletable

`bind/delete_children.rs` today explicitly exempts children "counted through a recorded path (`count likes by .postId.authorId`) … kept on purpose", and the guide maintains that a contribution may outlive its target. Under this RFC every durable→durable reference carries an action, so that like (durable child, durable parent, no eligible exemption) defaults to `restrict`: deleting the post now refuses `E_REFERENCED` and **no declaration the RFC offers** restores today's behavior. `cascade` deletes the history the app wanted to keep; `set null` requires an optional column and still mutates rows.

Fix (smallest): exempt the root of a recorded path from carrying an action (keep today's semantics for exactly that pattern, keep the note's `recorded()` exception), or add explicit `on delete keep`. Either way §7's "no reference leaves orphans any more" must be re-scoped (see 12).

### 3. High — §3 steps 2–3: fixed-order interleaved restrict/cascade spuriously refuses valid deletes

Step 3 deletes cascade children one reference at a time in schema order, each "by this same procedure from step 2", so each child's own `restrict` probes see sibling rows that the same cascade is about to delete. Scenario A (diamond): `A` cascades to `B` and `C` (B-table sorts first); `C` has a `restrict` ref to `B`. Deleting `A` deletes `B` rows first while live `C` rows still reference them → `E_REFERENCED`, although deleting `C` first would leave no dangling reference — SQL and the RFC's own §1 integrity claim would both allow it. Scenario B: a cascade child table with a `restrict` self-reference whose siblings reference each other; outcome depends on scan order.

Fix: compute the cascade closure first (BFS over cascade edges only — bounded by the reservation's row count), probe every `restrict` reference of every closure member **excluding other closure members**, then delete closure members children-before-parent and apply set-nulls. Deterministic, same integrity claim, no spurious refusals.

### 4. High — §4.2/§5.1: the physical allowance is not pre-drawn, so mid-scan exhaustion discloses hidden counts

`AUTHORIZATION_WALK_LIMIT` (8192, `authorized_scan.rs`) is request-shared, never restored, and exhaustion fails closed mid-scan with a refusal distinct from success. §5.1 hand-waves this ("likewise drawn by the reservation's row count") without a rule. Scenario: a mutation pages ~8000 rows of its own work, then deletes a parent with 500 hidden cascade children. The cascade's per-row fetches exhaust the remaining physical allowance → `AuthorizationBudget`/generic refusal where a parent with few children would succeed. Hidden-child count selects a caller-visible outcome — exactly what "nothing for cascade/set null" denies. (The logical meter is fine: `R(P)` is charged upfront. The physical side has no equivalent admission.)

Fix: before the first seek of steps 2–3, check `remaining_physical >= reservation_rows(P)` and fail closed there if not. The refusal is then a function of schema + the caller's own prior work only. Also state the job-ceiling edge: job `rows_written` (8192) equals the walk limit, so deep job cascades need the same admission or they always fail closed.

### 5. Medium — §3 step 1 / §7 / §8: the read-gate behavior change is invisible to the migration

Step 1 requires read authority on `p` "for every delete attempt, with or without children" whenever *any* action-carrying reference names `P` — and since every durable→durable reference carries one, that is nearly every referenced table. A caller who can delete but not read a row succeeds today and gets a hidden-target refusal tomorrow, with zero children involved. `N_DELETE_RESTRICTED` (defined as firing at sites with *undeclared* references) does not fire for this, and §8's migration note mentions only `E_REFERENCED`.

Fix: extend the note (or add one) covering the read-gate change, and add one sentence to §8. The design itself (generalizing 3000.014 §3.1) is fine; the signalling is incomplete.

### 6. Medium — §5.1/§9: `R(P)` has no specified home, and devices cannot use a formula

"Computable identically on the server, the compiler and both device stores" is asserted, not specified. But `schema/reservations.rs` is explicit that a device never rebuilds prices from formulas — a missing plan is a prediction refusal — and `WriteReservation` has no per-table delete phase. As written, every device would queue every parent delete forever (or each host would hand-roll the seven-dimension arithmetic and drift).

Fix: specify that `R(P)` (plus the `probe(r)` constants and the physical row count for finding 4) is computed once, stored in the schema IR's reservation plan, covered by the `reference-actions` capability, and consumed identically by all hosts. Name the `unit_delete`/`unit_update` phase split precisely (per-row price must exclude the restrict probes that `R(C)` counts, or the bound double-counts — harmless for soundness, but check's worst-case printout should match the engine).

### 7. Medium — §2.2: "a cap on a set-null column does not count null" needs its site list

The semantic change is necessary (otherwise set-null writes into a full null group would self-block and break the bound) and the single-column restriction keeps it tractable, but the RFC names no implementation sites. `check_constraints` counts the destination group including nulls today (group built with `unwrap_or(Value::Null)`, no null skip unlike unique checks); the `count_prefix` fast path, the `cap_count` maintained-occupancy path, device `prove_upsert_insert`/cap-move proofs, and activation's new-cap group validation must all skip null **only for set-null columns**, while every other nullable cap keeps counting null. Also unstated: the null group becomes unbounded, so index-prefix scans over `[Null]` and maintained views grouped by the column need their ordinary ceiling/horizon handling — worth one guide sentence.

Fix: enumerate the sites in §9 and add the null-group reads note.

### 8. Medium — §4.4: "unchanged in kind" understates acquisition, and caller-supplied ids make it feasible

Reads through a claimed id disclose; cascade *destroys* through a claimed id — that is a change in kind, not degree. And claiming is feasible: ids are caller-suppliable (`write_target.rs` mints only for non-`byId` upserts; outbox-minted ids are the norm), inserts never check existence, so a stranger can park rows naming id `X`; if a parent with id `X` is ever created (predictable ids, imports, `insert … if absent` with a chosen key), a later parent delete cascade-deletes (or, under default `restrict`, is pinned by) rows that predate the parent.

Fix: guide warning beside the rule of thumb ("a cascade/restrict parent should use minted ids; a cascade reference without an insert-time `exists` guard acquires strangers' rows"), plus a `check` note where a cascade/set-null child lacks any `require exists` over the reference. Do not block the RFC on existence checks (3000.036 §2 decided that); just surface the coupling.

### 9. Medium — §6.6: receipt-family restrict + refused-cascade needs its recipe stated

"Receipt family tables keep their engine-ordered deletes (`cascade` into them is refused; `restrict` probes them)" combined with `refuse_receipt_scope_delete` (non-system scope deletes already refused) means: a system job deleting a receipt scope with live members gets `E_REFERENCED` naming the members ref, and no declaration can ever make that delete atomic. Explicit member-first cleanup works (jobs pass rules; members are deletable), but it is exactly the toil §5.3's recipes are supposed to name.

Fix: state the job recipe in §6.6 (delete members/runs first, then scope), and confirm `N_DELETE_RESTRICTED` fires at those job delete sites since their behavior changes.

### 10. Medium — §6.4: provisional rows and refusal settlement are unspecified

Two gaps against 3000.014 §5's standard: (a) the local live probe must count the device's own **provisional** rows as live (014's `current_children` does: `current || provisional`); otherwise a device predicts parent-delete success while its own outbox holds a child insert, churning a replay the local probe could have avoided. (b) It is unstated whether a predicted `E_REFERENCED` is terminal-local or also sent for settlement. If terminal-local, a stale held child (tombstone in flight) spuriously refuses a delete the server would allow, with no server round trip to correct it — fail-closed but a real availability wart the RFC should own explicitly.

Fix: count provisional as live; state the refusal-settlement path (sent vs. terminal, and what catch-up replays).

### 11. Medium — §9: the Lean work is underestimated in two places

Per `lean/README.md`, the model currently excludes caps, sequences, expiry, maintains, residency, sync, devices, and `read through`. This RFC's proofs need caps (finiteness of `R`), live-vs-expired (the whole §3 probe semantics), and maintains/partition events (the `unit_delete` price) — all currently out of scope — and `applyWrite_authorized`'s restatement is not enough: the **disclosure theorems** (`query_noninterference`) must gain the one-bit-per-restrict-reference allowance, else the proved property contradicts the shipped behavior.

Fix: sequence it — model caps (or bound recursion by fuel with the acyclicity lemma stated), restate the disclosure theorems with the allowed bit, then grow generators. The ≥100k-case and difftest goals are fine once the semantics exist in the model.

### 12. Low — §7: "no reference leaves orphans any more" is false

References that carry no action (ephemeral/engine-owned, §2.1) keep today's meaning — the row stays — and dangling inserts stay legal (§1, §4.4). Fix: scope the sentence to action-carrying references; `N_DELETE_ORPHANS`' retirement note should say the same.

### 13. Low — §7: `N_DELETE_RESTRICTED` must not inherit `delete_children.rs`' filters verbatim

That file's map skips self-references (`parent != name`) and recorded-path children — right for an orphans note, wrong here: siblings *do* pin through a self-`restrict` probe (which excludes only `p` itself), and recorded-path children *do* refuse unless finding 2 exempts them. It must also *exclude* `read through` references, which keep `E_PARENT_HAS_CHILDREN`, not `E_REFERENCED`.

Fix: one paragraph in §7 defining the note's exact reference set.

### 14. Low — §4.1/§6.2: cascade/set-null vs. private fields and deny-rules deserves one explicit paragraph

A cascade can delete rows containing another principal's private `written by` fields, and a set-null applies to rows whose `update <- deny` the schema also declares — bypasses the declaration technically allows. Consent-by-explicit-declaration is a defensible justification (the schema author sees the child table), but the RFC never says it, and the §4.3 rule of thumb doesn't warn. Fix: state the justification and extend the rule of thumb ("don't cascade into tables holding others' private fields unless you mean to destroy them").

### 15. Low — §4.2: state the timing boundary

The meter is fixed by reservation, but wall-clock time varies with actual cascade size (the design meters counts, never time — `meter.rs`). A timing caller learns approximate hidden-descendant magnitude. The whole corpus already treats timing as out of scope; this RFC, which makes unusually precise disclosure claims ("exactly one bit"), should say so in one sentence rather than leave the claim absolute.

Also noted but not findings: `seed_delete`'s "0 or 1" return contract should say whether it counts cascaded rows; cascade into `append-only` tables correctly fails closed via `check_constraints` (worth naming so no implementer "fixes" it by skipping constraints on cascade steps); activation adding `expire at` above a read-through cascade is fail-closed automatically by whole-schema bind (worth one sentence).

## Verdict

**READY WITH CHANGES.** The core — default `restrict`, cap-bounded reservation-charged cascade/set-null, parent authorizes, no sweep, queue-without-proof — is sound and well-evidenced. Findings 1–4 are the ones to fix before implementation: define set-null eligibility over traversals (1), decide the recorded-path orphan pattern's fate (2), specify closure-based cascade evaluation instead of interleaved order (3), and add physical-allowance admission (4). Findings 5–11 are specification debts that would otherwise become implementation drift; 12–15 are wording. None requires re-architecting the proposal.
