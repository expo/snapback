### 7.1 Wave 2 (0.4.17): a starter beside a project's own schema

Wave 2 of the app farm (100 agents on 0.4.17) mostly wrote the backend first
and ran `init --web/--expo --skip-existing` afterwards. The 0.4.17 starter then
wrote its `fixtures/todos.jsonl` and `test.cases.jsonl` beside a schema with no
`todos` table, and the fail-closed fixture loader turned a green project red
(19 lanes). The decisions:

- **Any `snapback/*.q` is the project's schema.** `init` reads them before
  writing. The starter's `schema.q` is a conflict (or, with `--skip-existing`,
  kept out) when another `.q` file exists, and the todo starter's fixtures and
  cases are written only beside the starter's own schema; init says which it
  skipped. A stray `todos.jsonl` that 0.4.17 wrote names the starter in the
  loader's refusal.
- **The screen follows the kept schema's sign-in.** With `use personas` and no
  `use identity`, nobody can sign in as a guest, so the web and Expo starters
  write a persona picker (`openApp(persona)` → `createApp({ url, persona,
  device })`, one app per persona, closed on switch) around the same `Todos`
  screen; a password-only or identity-less schema gets a one-line pointer.
- **Vite's config is `vite.config.mts`** (both the starter and the chat
  template). The package's `"type"` stays whatever the project chose, including
  `npm init -y`'s `"commonjs"`, and Vite still loads the config as ESM, with no
  CommonJS-API warning (17 lanes). This replaces rewriting the package type.
- **Ports move together.** `--web-port N` sets Vite's `server` and `preview`
  ports (strict); without it, `--port N` puts the page on N+1 so a project
  confined to a port range stays inside it. init prints both URLs.
- **Adapting the starter is the expected path.** `package.json` scripts compare
  as commands (option order is not a conflict); a caret range of the starter's
  own `snapback4` version, as `npm i snapback4` saves it, is pinned to the
  exact version rather than refused; `.gitignore` covers `dist/`; the page
  title and Expo app name come from the directory; the starter CSS lives in
  `src/styles.css`. The conflict's first line names `--skip-existing`.

### 7.2 Wave 3 (0.4.18): init first, schema second

Wave 3 of the app farm (100 agents on 0.4.18) showed that §7.1's fixes fire
only when the schema exists *before* `init`. The README and the brief lead
agents to `init --web/--expo` first; they then replace `snapback/schema.q` and
are left with the todo starter's `fixtures/todos.jsonl` and cases (`test` runs
nothing), a guest sign-in screen over a persona-only schema (`auth.guest()`
refuses `E_AUTH`), or, rerunning init to get the picker, `E_INIT_CONFLICT`
(21 lanes, 41 minutes). The decisions, which make the outcome independent of
the order:

- **Leftovers are judged by the starter's bytes.** A starter file is a
  leftover only while it is byte-identical to what init wrote (the screen
  and client compared after normalizing the backend port and the persona
  list, the two values init varies) *and* it no longer fits the schema: the
  fixtures and cases when no `todos` table with `list`/`add`/`toggle`/`remove`
  exists; the screen and client when the schema's sign-in wants the other
  screen (guest for `use identity` with guests, the persona picker for
  `use personas` without `use identity`, or a picker for a different cast).
  A file the project changed is never reported as a leftover and never
  touched. No manifest is written: the starter text embedded in the binary is
  the reference, so a project that has never run 0.4.19's init still qualifies.
- **`check` names them, `init --adapt` fits them.** A successful `check`
  ends with a `starter:` block listing each leftover and its reason, then
  one command, `snapback4 init --adapt` (`check --json`: `starterLeftovers`
  with `files`, `advice` and `fix`). It never changes the exit status.
  `init --adapt [dir]` removes the unmodified fixtures (0.4.19 also removed
  an emptied `fixtures/`; §7.4 reverses that), and rewrites the unmodified screen and client to exactly
  what schema-first init writes for the same schema and port. A password-only
  or identity-less schema, and an adapted screen whose `Todos` component still
  calls the starter's operations, get advice lines rather than a rewrite.
  `--adapt` accepts only `--web`/`--expo` beside it and refuses without a
  `snapback/*.q`.
- **A project's `snapback/*.q` is never a conflict.** With any `.q` present,
  init leaves the starter's `schema.q` out with or without `--skip-existing`,
  lists the project's `.q` files as kept, and never writes through a linked
  schema. This replaces §7.1's "a conflict (or, with `--skip-existing`, kept
  out)". When an `E_INIT_CONFLICT` lists the files of an earlier starter that
  `--adapt` would fit, its first line and its rewrite name `init --adapt`.
- `test`'s refusal of a stray `todos.jsonl` names `init --adapt` as well.

Not done: `test` does not silently skip starter fixtures; a run that
executes nothing stays a refusal, and the command to fix it is one line.
(§7.4 skips the unmodified starter rows loudly instead.)

### 7.4 Wave 4 (0.4.19): the starter path after the schema

Wave 4 of the app farm (100 agents on 0.4.19) put 33 lanes (45 minutes) on
the starter path after the schema. One cause was a 0.4.19 regression; the
others were §7.2 stopping short. The decisions:

- **Adapt removes files, never a directory** (17 lanes). 0.4.19's adapt
  removed the two todo fixtures and then the emptied `fixtures/`, while its
  output named only the files; the documented next step, writing
  `fixtures/<table>.jsonl`, failed with `ENOENT` (and `ls fixtures/` after
  adapt explained the "adapt exits 2" reports). Adapt now removes only the
  files it names and says `fixtures/` stays. A project's own fixture file
  beside the starter's is never touched.
- **`snapback/generated/` is never a conflict** (6 lanes). Schema first,
  `check`, then `init --web` refused `E_INIT_CONFLICT` on the
  `snapback/generated/package.json` that `check` had written. Everything under
  `snapback/generated/` is regenerable output: init replaces the file it
  writes there (only `package.json`) and never lists it as a conflict.
- **Script spellings that run the same command are the same command.** A
  leading `npx`, and tsc's default project (`-p`/`--project` naming
  `tsconfig.json`, `./tsconfig.json` or `.`), no longer differ from the
  starter's script; init keeps the project's spelling and says so
  (`kept your package.json scripts.typecheck "tsc --noEmit" (the same
  command as the starter's …)`). A different command, such as
  `tsc --noEmit -p other.json` or another `build`, still refuses: keeping it
  would leave the starter's README instructions running something else.
- **A screen that compiles against any schema** (8 lanes). After §7.2's
  adapt, the screen behind the sign-in still called `api.list`/`add`/
  `toggle`/`remove` and the app did not typecheck. The starter screen is now
  composed of a sign-in head (guest, or persona picker) and a body: the
  todo list, or a neutral `Home` that shows the signed-in viewer
  (`useSignedInViewer()`), the link state and `Object.keys(api)`, with a
  comment naming the hooks and `snapback/generated/api.ts`. The parts are
  whole files whose single-line named imports init merges per module. Both
  orders write the same bytes: schema-first init beside a schema without
  the todo operations writes `Home`, and adapt rewrites an unmodified
  starter screen of either body and either sign-in to the one the schema
  wants (restoring the operations brings `Todos` back). A password-only or
  identity-less schema still gets advice for the sign-in, but its body is
  adapted too, so the app typechecks. Leftover detection recognizes all four
  pairs by bytes; a changed file is never touched. Verified with real
  installs from the registry: web (`npm init -y` first) and Expo, init
  first → schema → `init --adapt` → `check` → typecheck → build, for the
  guest and persona sign-ins.
- **`test` skips the unmodified starter rows, loudly** (4 lanes). A
  `fixtures/todos.jsonl` byte-identical to the starter's, beside a schema
  with no `todos` table, is skipped with `test: WARNING: skipped
  fixtures/todos.jsonl — … snapback4 init --adapt removes it`; the rest of the
  run proceeds. Any other file for a missing table, including a changed
  `todos.jsonl`, still refuses the run. An unmodified starter
  `test.cases.jsonl` still fails on its first unknown operation, now with a
  hint naming `init --adapt`, so a project that has written nothing of its
  own does not pass vacuously.
- **The advisories before the install** (15 lanes). Neither remaining
  advisory has a patched release as of 2026-10-11 (`braces` ≤ 3.0.3 and
  `node-forge` ≤ 1.4.0 are the whole vulnerable range; 3.0.3 and 1.4.0 are
  the latest releases), so no further `overrides` is possible. `init --expo`
  now prints, before `npm install` runs, that the install takes minutes and
  reports about 15 expected high advisories and not to run
  `npm audit fix --force`; the starter README opens with the same notice
  above its first command, and the package README's Expo row carries it.

Not done: `init --expo` still writes the todo starter's `slug`, `scheme`
and bundle identifiers (067, 035, 038), and `check`'s `starter:` block still
lists reasons rather than a one-line plan; both are smaller than the items
above and stay open.

## 9. Wave 10: upgrade deltas and visible form proof

### Generic smoke, 2026-09-24

`witness ios --smoke` adds a no-app-code first rung to the existing driver.
On an explicit smoke launch the Expo device attaches to the application's
own local client (including `createApp`/`AppProvider`), installs the native
JS error handler and reads counts and sync identity from the kept device.
Ordinary launches do not load the runner. It does not sign in for the app.
Prime waits for online acquisition; a cold offline launch checks persisted
counts and all optional-argument queries from the kept generated program
metadata; restart requires online sync through the exact driver barrier. No query rows enter the
receipts. Screenshots/video still show the real app's visible content.

After backend readiness, the driver reads the committed compiler generation
and binds it to the owned host's reported generation/store identity. It sends
that generation and the complete eligible query facts in the launch payload.
Before any query, the helper requires every runs/held fact to agree with its
kept backend and both device/backend generations to match the launch. The
driver refuses generation/fact changes across restart and checks the receipt
generation; a separate compilation of live source cannot supply these facts. Each smoke receipt records those facts and each
executed query's classification and actual result. Missing facts or a different
eligible operation set fail; classification is never inferred from `loading`.
Device-answerable queries (`runs: device`, including held reads) require data
or an explained refusal offline. Loading, a throw or an uncaught error fails.
Compiler-declared server-only reads (`runs: server`, including ephemeral and
online-only tables) are recorded offline as `online-only: unavailable offline
(expected)`, with their actual `loading` or `E_OFFLINE`-style refusal. This is
expected unavailability, not an answer. Those same eligible server-only queries
must answer in both online prime and restart. Required-argument queries remain
outside generic smoke. Optional-argument native queries are also refused by
generic smoke: their compiler server bit describes conditional module residency,
not unconditional server-only behavior. Use an application witness for those
queries. The native client must still acquire and reopen its
partition; an online-only client fallback cannot satisfy smoke.


A quiet backend's commit watermark cannot advance from reads alone. While
its owned backend and app are stopped, the driver records one zero-write
commit, with no application row, schema, log event or outbox change. The
manifest names this sync marker and all three segment receipts, timings and
screenshots. This is lifecycle evidence, not a substitute for the deeper
application assertions above; empty partitions and required-argument queries
remain explicitly limited evidence.

Round-one review hardening binds restart to the barrier sequence in both the
launch configuration and driver validation, so a pre-barrier tail cannot
stand in for reconnect progress. A successful segment's owned PID must still

# What Snapback 4 Does Not Do

Longer than the doing-list on purpose. Moving something off it means writing one
line naming what it unblocks and taking something off the doing-list in the same
change. Nothing comes off during slice one (LLP 3000 §3: the clock is four weeks).

## The bars

The bakeoff gates in [LLP 3000 §3](../llp/3000-snapback4.explainer.md) are the
bars: the loop bar, hub acquisition within 2× the measured floor, client bytes
under the competitor-anchored budgets, the six scenarios green in the simulator
on the hub fixture. Everything not required to pass them does not exist yet.

## Not building

- **A second authoring language.** Quarry, one spelling, copied from Snapback 2 (LLP 1004, LLP 1007 §4b). TypeScript is for seeds, journeys, effect bodies and the client.
- **Byte- and step-priced certification.** No closure, heap, output or step ceilings at `check`; the certificate certifies shape, uniformity, completeness class and prediction eligibility. Resources are metered at runtime (LLP 2000.000 §6).
- **A per-query result cache.** No range receipts, validators, halos, absence evidence, coverage spans, extent facts, held directories, fact integrity or swap journals. The client replicates declared partitions with one watermark each (LLP 2000.000 §7).
- **Engine-minted ids for client inserts, grants, ID slices.** Ids are client-minted, time-ordered, 128-bit; the engine mints for its own writes.
- **The `drain` protocol, follower-tab inbox rows, `defineItems`, `withHistory`, `mutationTarget`, `receipt.source`, `local.caughtUp`, `partial` reason codes.** The card (`packages/snapback4/src/contract.ts`) is the whole client vocabulary; `why` carries the rest.
- **`retain` as a receipt rule.** `until-revoked` and `delivered-history` survive as the client's leave policy on a scope tombstone.
- **JavaScript in the data plane.** Queries and mutations run in the Rust interpreter inside the SQLite transaction, and in the same interpreter on the client (host decided at week 3 by measurement, LLP 2000.000 §9). A *job* may be the app's own Rust, hosted as wasm through the interpreter's operations under the job's meter (LLP 3000.005, the Moves line below); a query or mutation may not.
- **An embedded JS engine for effects.** The data plane never calls out. `emit` writes the effect durably in the mutation's commit and an external worker holding a service token claims, performs and settles it over the wire (`snapback4/worker`); the four reference effects run on the builder's Node (LLP 2000.000 §10, decided 2026-09-13).
- **Committed generated code; an auth mode; a supervised bundler.** As Snapback 2 (`rules/NOT-DOING.md`): types by inference, personas not modes, `SNAPBACK_URL` is the client contract.
- **A TypeScript twin of the interpreter.** Retired by the author's ruling of 2026-09-13 (LLP 3000 §7): one implementation, in Rust, on every host — the core's SQLite under the native module, memory under wasm on the web with the host persisting each commit's changes. The web pays 312,924 B gzip before the diet where the twin's tier paid 16,842; the conformance obligation between two interpreters ends. Expo Go runs the online tier.
- **More than one hosted target, an admin console, media transcoding or thumbnails, push delivery itself (a worker's), cron syntax beyond `every N at HH:MM`, vector or relevance-ranked search (word-prefix search is in: `words(..)` and `matching`), federation, multi-region, device-to-device sync, at-rest encryption claims.** After the clock, on evidence.
- **General observability beyond `why`, `trace`, `logs`, `data`, `sql`, server operation latency, and bounded client subscription inspection.** The `sql` verb is read-only inspection of the developer's own store (LLP 3000.007 §8.8), never an application surface. Separately declared application SQL reads are admitted for increment D (LLP 3000.009 §6.2, §14.4; the 2026-09-16 Moves line below), not implemented by this inspection verb.
- **A guide corpus.** The compiler's facts, one language card and keyword cards, as Snapback 2; no freshness dates. Every card's Quarry is compiled by the suite and the language card is run, so a card cannot promise a form the parser refuses.

- **Partial union delivery, two group audiences, a public branch.** A union syncs principal-column branches and at most one group branch, each a whole disjunct of the read rule (LLP 3000.036.000.000); a branch with an extra condition, a second group or a `public` branch is refused with the rewrite, never partially delivered; service grants add no device audience (LLP 3000.007 §20.6). A union does not combine with delivered history, read-through children, synced or row-keyed views, owner keys, timelines, private field owners, acquisition windows or direct/inherited expiry on content or membership scopes.
- **Exact horizon maintenance.** The horizon bounds acquisition (a snapshot, a bootstrap); the log never evicts or back-fills to hold a device's group at exactly N rows. A local read past the acquired horizon by key says `complete: false`.

- **Clock expressions in rules.** A read rule compares with `=` and `!=` only; `.expiresAt > now` remains a mutation `require`. Stored lifetimes use `not before .col` for server-controlled opening and `expire at .col` for expiry. The engine publishes opening commits; devices receive no unopened payload. The supported compositions and explicit exclusions are in LLP 3000.036.003.
- **A jobs framework.** No priorities, worker pools or dead letters: one FIFO of runs, one chunk at a time, a refused chunk parked with its refusal. Actions, effects and scheduled actions carry per-operation retries, deadlines and cancellation, and a record per external step (LLP 3000.009 §5.2; the Moves line below). Missed period boundaries while a server is down fire once on return, not once per missed period.
- **Asset processing.** No transcoding, thumbnails, rungs or HEIC: the bytes are served as uploaded; JPEG, PNG, WebP and MP4 only; image dimensions and optional MP4 duration read from the header; MP4 dimensions are not extracted.
- **Search beyond word prefixes.** One tokenizer (NFC, lowercase, alphanumeric words), one index shape (`scope, words(cols), order.., id`), one read (`matching`): every term a prefix of some word, the first term's words merged as lanes, bounded by the meter in a uniform scope, at most 32 words in an admitted non-uniform scope. No stemming, no ranking by relevance, no phrase or mid-word matching, no per-language folding, no intersection index for the second term (it filters the page).
- **An identity provider.** Guests, password accounts, service seats, and sessions a service mints for accounts the application authenticated itself. No phone, OAuth, magic links or MFA in the engine: an application's worker verifies those and mints the session.
- **No multi-server presence, no presence history or last-seen storage, no broadcast event stream, no connection-bound rows.** `connected[p]` stays server-wide, counting held polls and their 35 s grace; a live query that may read it re-runs in the background about every 5 seconds to stay current (LLP 3000.018). Typing and viewing use short-lived, authorized ephemeral tables in one server process (LLP 3000.017); they never sync or decide durable invariants. A device does not know presence and says so.

# LLP 3000.000.000: Retained storage and hot release activation

**Type:** RFC
**Status:** Implemented
**Systems:** Schema evolution, Storage, CLI, Deployment, Replica generations
**Author:** Codex for Charlie Cheever (Workstream ROLL)
**Date:** 2026-10-12
**Revised:** 2026-10-13 (§10: REL2 wave-10 release lifecycle); 2026-10-13 (MACFIX: explicit pre-retention compatibility boundary and canonical deployment/worker paths); 2026-10-12 (§5.1: path-independent control socket; implemented; dual-family confirmation, captured lifetimes, native generations, hot activation and complete qualification)
**Related:** [LLP 3000](./3000-snapback4.explainer.md), [LLP 3000.000](./3000.000-atomic-schema-and-release-activation.research.md), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md), [LLP 3000.019](./3000.019-what-the-builder-still-wrote.rfc.md)

## 1. Commission and scope

Charlie approved the ideal end-game release lifecycle and commissioned implementation on 2026-10-12. Implementer: this ROLL session, beginning that date. Wave 8 DT1 found additive rollback deletes new storage in all 50 day-two lanes; DT1a found unnamed enum conflicts; DT10 found deployment requires stopping serve. This supersedes the release-only removal semantics in LLP 3000.000's implementation follow-up. Development and device replacement keep their existing projection/reset semantics. No new publication authority or gate is introduced.

## 2. Retain by default

Every release activation (deploy and rollback) retains removed durable application tables, columns and index definitions in SQLite-owned dormant storage within the same activation transaction. The active r/i image remains an exact projection of the active schema. Dormant data is outside that namespace and unavailable to programs, rules, references, queries, sync, SQL application projections and clients. The Quarry/IR binder admits only declared application table names; it has no general application SQL evaluator. Dormant internal names are not added to Schema, and schema validation forbids declarations in the reserved `_dormant_` and `_release_` namespaces. Inspection `snapback4 sql` is owner-only and may enumerate it. A future application SQL adapter must keep its declared authorized input allow-list. Asset reads must resolve the home table, column and row in the active schema/r image and check the current read rule; a dormant home refuses E_ASSET_UNKNOWN even when a caller knows its id. Test the reserved-name/program boundary and direct fetch by id. Reintroducing a dormant name deliberately reactivates its data, after full validation under the candidate schema. A deployment that reuses any dormant name refuses unless --restore-dormant explicitly selects restoration; its refusal lists retained items/counts/samples and the alternatives `deploy <dir> --restore-dormant` or `prune <dir> --allow-destructive` before fresh creation. Rollback's selection of an immutable older release explicitly selects restoration; `rollback <dir> --to N` also selects an immutable release for deliberate roll forward. To convert durable to ephemeral, deploy a release without that table, prune it explicitly, then deploy the ephemeral definition. This applies to deployments as well as rollback; a rename remains two names, without an inferred data move.

Inventory and audit entries carry a stable typed key (`table:name`, `column:table.name`, or `index:table.name`); pagination uses the returned key, not a bare path that could collide between columns and indexes. The SQLite format is `_dormant_tables(table_name, definition)` for whole-table Table definitions, `_dormant_rows(t,id,data)` for their stored images, `_dormant_columns(table_name,column_name,definition)` for retired column type/default/ownership, `_dormant_values(t,id,column_name,data)` for their cells, `_dormant_indexes(table_name,index_name,definition)` for index definitions and `_dormant_refs(t,id,column_name,parent_t,parent_id,invalid)` for deletion evidence with a parent lookup index. Catalog numbers are reserved monotonically and reused for the same physical name, but dormant rows are never kept in r under a hidden catalog number. These tables are created only during successful release activation; legacy deployments start empty and cannot recover data previously deleted by older binaries. A successful release activation writes the release-only format marker `version=snapback4-release-store-3`. New Store open/version checks accept this, the prior snapback4-release-store-2 and the legacy snapback4-store-1; old binaries reject it with E_STORE rather than opening it. Development and device stores retain snapback4-store-1 and their formats are unchanged. The format marker rolls back with failed activation. On restore, omitted cells from whole-table images move to dormant column cells before projection, merging previous retired cells; full-table entries are consumed only on commit.

The compatibility boundary is the store format, independently of schema
capabilities. Published 0.2.33 refuses retained release-store versions 2 and 3
with `E_STORE: store version <version> is not snapback4-store-1; this data
directory belongs to another Snapback` (the read-only doctor form omits
the final data-directory explanation), including capability-free releases.
That refusal must preserve committed state and never interpret dormant data
under the old layout. Capability-free backend/schema bytes and unchanged
store-1 development/device fixtures retain their separate compatibility
controls (LLP 3000.022 §14.3); they do not establish old-server readability of
new release stores. The Darwin publication fence checks both boundaries.
The MACFIX compatibility/path amendment passed independent final
[Muse](./reviews/3000.000.000-macfix-r3.muse.md) and
[Codex](./reviews/3000.000.000-macfix-r3.codex.md) reviews at e9150bd171.
The required Darwin schema and worker files passed alone with default TMPDIR
(10 and 82 tests); whole-publication qualification is a separate claim.

Dormant whole tables store their row images; dormant columns store values keyed by table/column/row id and their definitions. Capture interpreted literal defaults and optional nulls when a column becomes dormant, preserving the value existing rows actually saw. Keep index definitions as history; preserve their data logically and rebuild physical keys on reactivation from current rows. Dormant indexes are never consulted for active writes, uniqueness or caps. Thus a new duplicate under the older release can precisely refuse forward activation. Derived rows are caches and are rebuilt, not authoritative history. Retention must precede existing derived-state retirement. An unsupported durable-to-ephemeral conversion refuses rather than silently discarding stored data.

Partial restoration consumes only candidate-visible cells: B's T(a,b) → absent T → C's T(a) restores a and moves b to dormant cells, with b's definition, then B restores b. For an identical (t,id,column) cell key, the newly retired active value wins: it is the most recent authoritative value. Preserve other dormant keys. Use transactional upsert and test retire → restore → update → retire → restore. Keep zero-row table/column/index definitions too. Whole-table restoration first restores its stored image, splits omitted cells into dormancy, then projects the active image. Consumption shares commit with validation. Refuse application-table to derived-table ownership changes, or authoritative-column to maintained/captured ownership changes, including when the application table/column was dormant. Derived caches never overwrite retained authoritative data. The refusal names the incompatible owner and directs a deliberate rename or prune while dormant.

At retirement record reference edges for dormant rows/cells (including optional/list references), bound to their current parent lifetime. An active delete transaction marks matching dormant edges invalid before the id can be reused, even for identical replacement values. Only a move into dormant storage or replacement of a derived cache is exempt from deletion invalidation. Actual authoritative-row deletion always invalidates matching dormant edges, including expiry during activation; failed activation rolls the invalidation back. Restoration refuses invalidated edges or missing parents with table/column/parent ids, counts and samples; it cannot silently recapture another parent's audience. For read-through rows, compare preserved captured audience and identity fields to the candidate parent before existing recapture work. A changed audience refuses restoration; inherited deadlines keep their original capture. Newly expired rows remain logically invisible and may be swept only under the reactivated schema. Test deletion/reuse, identical replacement, changed audience, nested references and expiry. This adds no device incarnation format.

Restoration, candidate validation, derived rebuild, catalog/generation/programs and current release commit together. Any error rolls all of them back. Retained values overwrite no explicit candidate writes: restoration precedes activation builders. Incompatible name reuse must pass candidate types and constraints; no flag bypasses validation.

## 3. Older writes and incompatible values

Updating an active row while its newer columns are dormant preserves those dormant values. Deleting that row deletes its dormant column values in the same transaction: forward never resurrects a deleted row, including when its id is reused. New rows written under the older schema have no dormant value. On forward they receive the candidate literal default or optional null; required columns without such a default refuse with exact missing-row counts and up to five ids. Repair by deploying a bridge schema with that column optional or a literal default using --restore-dormant, fill it through a bridge mutation, then deploy the desired required schema. Alternatively explicitly delete the named rows through the current release and retry. Never tell the older schema to write a field it lacks. Contextual now/viewer defaults do not invent historical values. Existing required-column backfill rules still apply.

Release activations retain incompatible existing values per row rather than refusing a type narrowing. Section 9 specifies the visibility, reference and restoration rules. Development adoption keeps its checked narrowing behavior. Missing newly required fields still need the bridge described above; retention applies to present historical values, not absent backfill. No implicit coercion or fallback is introduced.

For every data-dependent refusal, aggregate count and bounded samples (five distinct values/keys, 256 UTF-8 bytes each, plus truncation markers) at the failed column/index/constraint, without unbounded row retention. Include actual conflicting values for column failures, index name and conflicting keys for unique failures, and actionable command or schema repair. Detailed values are privileged operator diagnostics only, never ordinary application refusal payloads, query meter diagnostics or sync refusals. No claim that a green read-only preview freezes later writes: adoption rechecks under its transaction.

## 4. Explicit pruning and audit

snapback4 prune <dir> runs through the serving owner when live, otherwise the offline owner. It lists dormant tables, columns and indexes with row counts, logical serialized dormant bytes (including retained asset bytes separately) and at most five ids; it changes nothing without --allow-destructive. With that flag it permanently deletes exactly the currently dormant storage in one writer transaction, records a durable prune event, and leaves active rows/programs untouched. It releases dormant asset homes for the ordinary collector. Deploy/rollback --allow-destructive do not prune; direct users to the separate command. Prune intentionally deletes all dormant items as one reviewed storage boundary; per-item dependency-aware pruning is deferred because partial pruning can strand dormant references and asset homes. There is no implicit size or age collector: previews make storage growth visible without inventing a data-loss policy. After prune, reintroducing the schema gets empty tables and normal required-column/default behavior. Pruning is an irreversible operator action; the command output names every item dropped.

Release activation events live in the database transaction with activation revision, operation, release/previous/generation, timestamp and retained/restored summary. Prune records its item summary in that transaction. Existing releases.jsonl and current remain checked convenience copies; post-commit filesystem errors explicitly say activation succeeded. History is never edited or rewound. Rollback picks an earlier immutable source, not a historical data snapshot.

Dormant bytes have no automatic age-based deletion: retention lasts until explicit prune, and prune preview exposes populations so operators control disk use. Dormant asset homes remain live in the asset ledger but are unreadable because the active schema has no home. Active-row deletion also retires any associated dormant asset home. Dormant rows do not run old expiry or jobs while dormant; candidate liveness applies again upon reactivation. Explicit application deletion and ordinary active expiry still mean deletion, not an undo archive.

## 5. Hot activation and ownership

serve owns the database sidecar for its lifetime and publishes a Unix-domain release-control socket in the private per-user runtime directory (§5.1; directory 0700, socket 0600). Check peer credentials on both ends (Linux SO_PEERCRED, Darwin getpeereid), requiring the effective UID. Only the host filesystem owner has this capability; it is not an HTTP door, browser origin, bearer service seat or remote endpoint. Check filesystem objects before replacing a stale socket; never follow symlinks or replace a regular file. Use `.release-command` (a hardened private regular file, no-follow, single link) for the command flock and the deterministic runtime address (§5.1) for the control socket. lstat socket entries; only a same-owner socket may be removed while holding the exclusive store sidecar. Bound command JSON to 4096 bytes and response JSON to 64 KiB, with a 5-second input timeout and 120-second command response timeout. The trusted same-UID operator can directly edit source/database; malicious same-UID edits are outside the threat model, but ordinary source races are caught by a candidate content digest over source/native/worker files in the request and verified by the server. Numeric release id is the only source selector; never a caller path. Commands hold a separate private command flock while allocating/staging immutable release source. They acquire the store owner when stopped; E_STORE_BUSY with a running serve uses the local socket instead of opening another writer. Dev and an older/unreachable server continue to refuse with an exact stop/retry command.

snapback4 releases <dir> reads authoritative current release, activation revision, generation and durable events without adopting source, including while serve is live. This is the recovery command for an ambiguous result. A bounded command message identifies the owned database inode/canonical identity, candidate release id, expected current release and monotone activation revision, operation and explicit flags. The server compiles only its own immutable release directory, prepares native module/worker prerequisites before commit, then holds its existing engine writer guard for activation and in-memory publication. The server verifies both expected current release and activation revision inside the activation transaction. Increment activation revision on every successful release activation, including an equal-hash source change; A→B→A cannot satisfy an old command. Concurrent commands serialize on the command flock; out-of-band stale commands fail compare-and-swap. No request may choose arbitrary filesystem source. Compilation/validation failure leaves the previous engine, bound schema, native module, worker revision and reader factory unchanged.

A query already running in a pinned SQLite read transaction finishes on its old snapshot and reports that generation. A writer already executing finishes before activation obtains its engine guard. Queued HTTP operations are admitted under one release request guard covering signature lookup, argument decoding and execution. Activation acquires its exclusive side before taking the engine guard; admitted operations finish before activation, and later operations dispatch under the new generation. Internal detached readers still fence obsolete identities with E_GENERATION. Fresh requests after publication use the new engine; a stale pooled reader not yet pinned retries through the replacement factory. Prepare a runtime bundle containing bound programs, precompiled native module/metadata, worker root and validated named declarations; prepare the reader factory from the post-activation engine while its writer guard blocks new writers (reader opening failure after commit clears the old factory and uses existing lazy retry, never aborts a committed activation or advertises the old backend). Swap bound/generation/native under the common bound guard in the existing /schema guard order, retire pooled readers, rebind ephemeral state, invalidate change answers, wake sync/polls and update worker revision while holding the writer guard. The supervisor explicitly switches its immutable release project root and named declarations on revision, including addition/removal/replacement; externally supplied --worker stays an operator-owned entry. Worker preparation captures an immutable (root, entry, declarations/environment, supervisor revision) tuple. Under the engine guard it compares that captured revision to the current worker revision before minting credentials; stale preparation is discarded and rediscovered. Never relabel an old prepared source with the latest revision. Credentials bind that checked revision so later activation fences them even when spawn finishes later. Workers restart using the candidate packaged source and native continuation hashes keep the existing conservative parking policy. Long validation can pause writes; hot means no process restart, not an unbounded zero-pause latency promise.

The server continues an admitted activation even if the client hits its 120-second response timeout or closes the socket; failure to write the reply is not permission to roll back or exit the server. The database is authoritative at crash or lost socket reply. Timeout/EOF after sending a command reports an ambiguous result and instructs inspection of current and durable history; never silently resend as a new release or claim failure left the old release active. Before activation fsync required immutable source/native/worker files and their directories, then the published releases directory entry. The supported guarantee covers process crashes and filesystem/SQLite durability on hosts honoring fsync; no guarantee covers failing storage hardware. Restart attaches the database-selected release even if current's convenience copy is stale. After database commit, publication is infallible in-memory assignments and committed ephemeral rebind; fallible native compilation, declaration/environment/import validation happens before commit. Worker process spawn remains fallible after commit: failure reports committed activation with degraded worker availability and retries; it cannot undo a release or external effects. Filesystem-copy failures report the committed result.

### 9.1 Per-row narrowed-value dormancy

Each actual release activation, including roll-forward and equal-schema/program-only/native-only selection, runs the row-visibility closure. A visibility change advances generation even if execution hashes are equal, so devices replace their population; identical-source deploy no-ops do not activate. The closure removes authoritative rows whose **present** values do not fit the candidate column type or text constraint (asset leaves include ledger-backed kind, byte bound and file MIME allow-list, recursively through optionals/lists) into `_dormant_narrow_rows(t,id,data,definition,reason)`. Store format advances to `snapback4-release-store-3`; this binary opens format 2 and upgrades only during committed activation. Absent new required fields remain E_ADOPT. Engine metadata and maintained cache fields are not a narrowing trigger. Store the full authoritative image and its source table definition (merge restored whole-table and column definitions before classifying restored values), with interpreted old literal defaults and nulls, before projection. Restore any retained image that fits the candidate, splitting omitted columns into existing dormant cells. Restoration is automatic even on deploy; this is an existing row lifetime, not reuse of a removed schema name. No fallback syntax ships: the declared policy is hidden rows, never value substitution.

Visibility is a fixed point: a row with a non-null reference (including nested/list references) to a dormant narrowed row is also dormant. This covers authorization parents and memberships. Active programs, rules, point reads, lists, counts, caps, maintained views, assets and application SQL see only active r/i. Tentative restore-and-rehide work does not count as a visibility change; compute population change from newly hidden rows and successfully restored rows in the final closed population. All dependent physical indexes and aggregates rebuild when rows enter or leave dormancy, including otherwise unchanged tables. Sync generation replacement clears base/index images and acquisition, then reacquires only that same active population. This supersedes the device literal-default image-retention optimization: an additive default can restore a dormant cell whose actual value is incompatible, so schema shape alone cannot certify an old image. Same-generation attachment and identical-source no-ops preserve images; outbox custody survives generation replacement. HAND owns the shipped-device compatibility floor; DX owns updates to client/evolution guide text. A reference lookup to a dormant id is absent. Preserve LLP 3000.039 §1/§4.4: references validate a nominal id, not target existence. A new write may carry a dormant id just as it may carry an unknown/hidden id; read-through or explicit require/insert rules decide target admission. Such a write remains active under the old release until the next adoption's reference-closure pass, but grants no parent-derived authority. Never probe dormancy selectively at the reference write boundary, which would be an existence oracle. Dormant rows contribute neither to uniqueness nor caps. Restoration uses the same set-null cap exemption as ordinary writes; null-exempt groups are never counted by adoption or successor assessment. Their ids remain reserved: inserts cannot replace them and return the same E_RULE as a hidden live identity conflict, without row contents or a special dormant code. Updates/deletes by old programs see an absent row; active updates retain unrelated dormant cells. Dormant uniqueness keys are not reserved: old writes may cause a constraint conflict on forward, which E_ADOPT reports with executable application SQL; resolve that conflict under the current release when those rows are active. If both conflict rows are dormant, deploy a bridge with compatible widened types and the conflicting index non-unique/cap increased using --restore-dormant, restore both, repair with authorized mutations, then reinstate the constraint. Neither row silently wins; activation refuses atomically. Diagnostics include this bridge and application SQL, with values only in privileged operator output (§3). Type incompatibility alone never blocks switching.

At one pinned activation time, retire affected expired predecessor read-through rows under their old deadlines before narrowed hiding; retirement uses the ordinary authoritative delete to invalidate dependent evidence and remove dormant cells. Then restore candidate-compatible images, hide the incompatible/reference-dependent population, rebuild all physical r/i and _cap_counts/maintained caches, and validate before publication. Counts, sums and private parent-column mirrors all use this order. Reference closure removes at least one active row per iteration, terminates on the finite store even with nominal cycles, and any non-null element of a nested/list reference can hide its row. Null has no edge; a missing ordinary nominal target alone does not trigger hiding, while an absent target schema or narrowed-dormant target does. Capture dormant reference lifetime evidence before hiding; hiding is not deletion. Actual parent deletion invalidates evidence. Transferring a retained whole row or cell into narrowed dormancy preserves its existing bound/unbound/deleted evidence; it must never recapture a replacement parent. On candidate restoration, evidence invalidated by an actual deletion keeps a row dormant only if its reference/capture column is candidate-visible. An initially dangling nominal keep reference captures invalid=2 (unbound), distinct from invalid=1 (deleted captured lifetime); it may restore without inventing a lifetime. Deletion invalidates only bound (invalid=0) edges. Omitted reference cells and evidence stay retained for future restoration. A narrowed row never rebinds a deleted visible parent. Restored read-through images retain their historical captures and must pass the existing audience/deadline safety check. Whole-table restoration keeps the full source image through lifetime retirement and narrowed classification; ordinary candidate projection follows that boundary. Before projecting a narrowed image, evaluate retirement against its retained source definition/deadline, including direct expiry without read-through; removing read-through or expiry cannot revive an expired source lifetime. Actual retirement deletes the narrowed image, dependent captured evidence and its retained asset homes. Rows whose target table is absent stay dormant. Dormant rows run no jobs/expiry until reactivation. Assets remain retained but inaccessible. `prune --allow-destructive` drops narrowed images, associated dormant cells and lifetime evidence and releases only their asset homes; the preview names counts/bytes/sample ids. Inventory uses `rows:<table>` typed keys and audit items record before_rows, after_rows, restored_rows and bounded before_sample_ids in the activation transaction, including partial column/row restorations whose typed key remains. Per-table narrowed restoration counters distinguish restore-and-hide swaps with equal totals; summary restored_items includes partial restorations. Restoration identity sets are held transactionally and counted against final surviving r only after all read-through/cache activation phases. Column restored counts are recorded from cells actually consumed into surviving candidate rows, not inferred from inventory decreases; expiry/deletion may remove cells without restoring them. There is no automatic collection.

### 9.2 Exact preview and operator vocabulary

# What Snapback 4 Does Not Do

Longer than the doing-list on purpose. Moving something off it means writing one
line naming what it unblocks and taking something off the doing-list in the same
change. Nothing comes off during slice one (LLP 3000 §3: the clock is four weeks).

## The bars

The bakeoff gates in [LLP 3000 §3](../llp/3000-snapback4.explainer.md) are the
bars: the loop bar, hub acquisition within 2× the measured floor, client bytes
under the competitor-anchored budgets, the six scenarios green in the simulator
on the hub fixture. Everything not required to pass them does not exist yet.

## Not building

- **A second authoring language.** Quarry, one spelling, copied from Snapback 2 (LLP 1004, LLP 1007 §4b). TypeScript is for seeds, journeys, effect bodies and the client.
- **Byte- and step-priced certification.** No closure, heap, output or step ceilings at `check`; the certificate certifies shape, uniformity, completeness class and prediction eligibility. Resources are metered at runtime (LLP 2000.000 §6).
- **A per-query result cache.** No range receipts, validators, halos, absence evidence, coverage spans, extent facts, held directories, fact integrity or swap journals. The client replicates declared partitions with one watermark each (LLP 2000.000 §7).
- **Engine-minted ids for client inserts, grants, ID slices.** Ids are client-minted, time-ordered, 128-bit; the engine mints for its own writes.
- **The `drain` protocol, follower-tab inbox rows, `defineItems`, `withHistory`, `mutationTarget`, `receipt.source`, `local.caughtUp`, `partial` reason codes.** The card (`packages/snapback4/src/contract.ts`) is the whole client vocabulary; `why` carries the rest.
- **`retain` as a receipt rule.** `until-revoked` and `delivered-history` survive as the client's leave policy on a scope tombstone.
- **JavaScript in the data plane.** Queries and mutations run in the Rust interpreter inside the SQLite transaction, and in the same interpreter on the client (host decided at week 3 by measurement, LLP 2000.000 §9). A *job* may be the app's own Rust, hosted as wasm through the interpreter's operations under the job's meter (LLP 3000.005, the Moves line below); a query or mutation may not.
- **An embedded JS engine for effects.** The data plane never calls out. `emit` writes the effect durably in the mutation's commit and an external worker holding a service token claims, performs and settles it over the wire (`snapback4/worker`); the four reference effects run on the builder's Node (LLP 2000.000 §10, decided 2026-09-13).
- **Committed generated code; an auth mode; a supervised bundler.** As Snapback 2 (`rules/NOT-DOING.md`): types by inference, personas not modes, `SNAPBACK_URL` is the client contract.
- **A TypeScript twin of the interpreter.** Retired by the author's ruling of 2026-09-13 (LLP 3000 §7): one implementation, in Rust, on every host — the core's SQLite under the native module, memory under wasm on the web with the host persisting each commit's changes. The web pays 312,924 B gzip before the diet where the twin's tier paid 16,842; the conformance obligation between two interpreters ends. Expo Go runs the online tier.
- **More than one hosted target, an admin console, media transcoding or thumbnails, push delivery itself (a worker's), cron syntax beyond `every N at HH:MM`, vector or relevance-ranked search (word-prefix search is in: `words(..)` and `matching`), federation, multi-region, device-to-device sync, at-rest encryption claims.** After the clock, on evidence.
- **General observability beyond `why`, `trace`, `logs`, `data`, `sql`, server operation latency, and bounded client subscription inspection.** The `sql` verb is read-only inspection of the developer's own store (LLP 3000.007 §8.8), never an application surface. Separately declared application SQL reads are admitted for increment D (LLP 3000.009 §6.2, §14.4; the 2026-09-16 Moves line below), not implemented by this inspection verb.
- **A guide corpus.** The compiler's facts, one language card and keyword cards, as Snapback 2; no freshness dates. Every card's Quarry is compiled by the suite and the language card is run, so a card cannot promise a form the parser refuses.

- **Partial union delivery, two group audiences, a public branch.** A union syncs principal-column branches and at most one group branch, each a whole disjunct of the read rule (LLP 3000.036.000.000); a branch with an extra condition, a second group or a `public` branch is refused with the rewrite, never partially delivered; service grants add no device audience (LLP 3000.007 §20.6). A union does not combine with delivered history, read-through children, synced or row-keyed views, owner keys, timelines, private field owners, acquisition windows or direct/inherited expiry on content or membership scopes.
- **Exact horizon maintenance.** The horizon bounds acquisition (a snapshot, a bootstrap); the log never evicts or back-fills to hold a device's group at exactly N rows. A local read past the acquired horizon by key says `complete: false`.

- **Clock expressions in rules.** A read rule compares with `=` and `!=` only; `.expiresAt > now` remains a mutation `require`. Stored lifetimes use `not before .col` for server-controlled opening and `expire at .col` for expiry. The engine publishes opening commits; devices receive no unopened payload. The supported compositions and explicit exclusions are in LLP 3000.036.003.
- **A jobs framework.** No priorities, worker pools or dead letters: one FIFO of runs, one chunk at a time, a refused chunk parked with its refusal. Actions, effects and scheduled actions carry per-operation retries, deadlines and cancellation, and a record per external step (LLP 3000.009 §5.2; the Moves line below). Missed period boundaries while a server is down fire once on return, not once per missed period.
- **Asset processing.** No transcoding, thumbnails, rungs or HEIC: the bytes are served as uploaded; JPEG, PNG, WebP and MP4 only; image dimensions and optional MP4 duration read from the header; MP4 dimensions are not extracted.
- **Search beyond word prefixes.** One tokenizer (NFC, lowercase, alphanumeric words), one index shape (`scope, words(cols), order.., id`), one read (`matching`): every term a prefix of some word, the first term's words merged as lanes, bounded by the meter in a uniform scope, at most 32 words in an admitted non-uniform scope. No stemming, no ranking by relevance, no phrase or mid-word matching, no per-language folding, no intersection index for the second term (it filters the page).
- **An identity provider.** Guests, password accounts, service seats, and sessions a service mints for accounts the application authenticated itself. No phone, OAuth, magic links or MFA in the engine: an application's worker verifies those and mints the session.
- **No multi-server presence, no presence history or last-seen storage, no broadcast event stream, no connection-bound rows.** `connected[p]` stays server-wide, counting held polls and their 35 s grace; a live query that may read it re-runs in the background about every 5 seconds to stay current (LLP 3000.018). Typing and viewing use short-lived, authorized ephemeral tables in one server process (LLP 3000.017); they never sync or decide durable invariants. A device does not know presence and says so.

# Rules

**Snapback 2 optimizes the edit-to-verified loop — the agent's building an app on it, and ours building it.**

Speed is the constraint. Everything below exists to keep the edit-to-verified loop short
and to stop this repository accreting apparatus faster than anyone can remove it. These
rules bind `snapback2/` and the LLPs numbered 1000 and up; Snapback 1 is baselined, not
exempt, and its numbers may only fall.

Each rule is **[check]** (enforced by `caps`) or **[review]** (enforced by a human).

## Budgets — every budget is a trade, not a limit

- **5 blocking checks, 60s total.** A sixth requires deleting one, in the same PR. **[check]**
- **59 documents in the working set** (`llp/current/`). Today's count. A 60th requires
  archiving one — which is just removing the link. Snapback 2 aims to leave this at 15;
  Snapback 1's links are archived at promotion. **[check]**
- **12 documents in the foundation** (`llp/foundation/`). **[check]**
- **This file: 700 words.** If it grows, something becomes a check or stops being a rule. **[check]**
- **1,500 lines per source file, baseline 204.** Generated files exempt — and generated
  files are built, not committed; so are benchmark run records under `benchmarks/runs/`,
  which are evidence, not source. The baseline is Snapback 1's oversize count on the day
  the rule landed; it may not grow, and `snapback2/` contributes zero to it. **[check]**

## Blocking checks

`caps` · `ref-check` · `snapback2/scripts/test.sh` · `snapback2/scripts/measure.mjs --check` · `check-inventories`

## Loop shape

- **Every check reports all failures in one run.** Fail-fast is banned. **[check]**
- **Nothing blocks on anything slower than 60 seconds.** Slow verification runs on a
  schedule, attributed to the breaking commit, and files a bounded set of issues. **[review]**
- **Fix loops get 3 rounds.** Then stop: escalate to a human or descope. **[review]**

Tracked every run of `snapback2/scripts/measure.mjs` (appends `snapback2/metrics/loop.jsonl`).

## Scope

pre-registered comparison on one clock.

**Flip 1 — certify authorization, meter resources** (LLP 2000.000 §6). The
certificate keeps every read site's shape, uniformity, completeness class
and prediction eligibility, and stops pricing bytes and steps. A
deterministic meter charges examined rows, index entries, rule probes,
steps, heap, output and rows written as the program runs, on the server and
in the client interpreter alike. A query cut by the meter returns `capped`
with no continuation past the cut, the same observable outcome as a static
ceiling cut today; a mutation aborts with `E_BOUND` naming actual work; a
job is chunked. `check --cost` prints the structural cost class; `test`
prints measured meters on the hub fixture.

**Flip 2 — the viewer's partition is the unit of sync** (LLP 2000.000 §7).
`sync to <audience> last N by <index>` on a table makes the engine maintain,
per principal, the rows that principal may read, as a change log with a
horizon; a table without the word is online-only, and `check` says which
rule term prevented inversion. The client holds a replica of its partitions,
one watermark each, a durable outbox with client-minted ids, and the
interpreter; queries run locally and are `complete` inside the horizon.
Revocation is a scope tombstone; `until-revoked` and `delivered-history`
survive as the client's leave policy. Two client tiers — online-only
without a store, local-first with one — share one language and one server.

**The vocabulary is fixed before the mechanism** (LLP 2000.000 §8):

A screen that needs a word not on that card is a defect in the mechanism,
not a gap in the card.

## 1. Summary

LLP 2000 is right that the whole application is the unit of design, right
that ownership comes before abstraction, and right to ask for deterministic
simulation and an early real deployment. Its weakness is that it treats the
two structural choices that produced Snapback 2's costs as open research
questions, and then proposes a first experiment at exactly the scale where
those costs are invisible. This document takes a position on both, names
what to keep from Snapback 2 verbatim, and rewrites the first slice so it
can fail for the right reasons.

The position, in one paragraph. Snapback 2's *core* is excellent and should
be copied: the rule language and its uniformity analysis, the structural-fact
family, one data language, typed states with no silence, refusals that paste
a rewrite, personas, the successor classifier, the derived per-recipient
log, the loop verbs and their sub-second budgets. Two *substrates* under
that core are where the record shows the hours went, and both should be
flipped rather than re-investigated: (1) the static certificate should keep
certifying **authorization and shape** and stop pricing **bytes and steps**,
which move to a deterministic runtime meter with honest `capped`/abort
outcomes; and (2) the client should hold **a replica of the viewer's declared
partition** — the local-first shape every shipped sync engine and Snapback
2's own `deliver` log converge on — instead of a per-query result cache
proven by receipts. Those two flips dissolve most of the machinery that
leaked into the application (receipts, coverage, halos, validators, grants,
ID slices, drains, `withHistory`, follower inboxes, per-table retention
words) and turn the 28-second acquisition into a bulk stream whose floor is
the device's write speed. The first slice should be built on the **hub
fixture** (1,000 memberships, 500 follows, 100,000 messages), with the
day-two change designed before the day-one screen, a native client in the
first slice, and a deterministic simulator as the primary test harness.

Three claims this document makes that LLP 2000 does not:

1. **The costs have two named causes, and both are decisions, not
   mysteries.** Byte-priced static certification and the receipt-proven
   result cache account for every ergonomic residual in LLP 1018.008.009
   except documentation. §2 shows the mapping.
2. **The first experiment must include the hub.** Snapback 2 was "elegant on
   day one and hostile on day two" (LLP 1020) and broke at 1,000 memberships
   (LLPs 1023, 1024, 1025). A two-principal slice will pass and teach nothing.
3. **The process is part of the product.** Seventy-one LLPs, over two
   thousand commits, and seven ceiling raises in fourteen days produced a
   sound system nobody can hold in their head. Snapback 3 needs one owner on
   the core, a simulator instead of a test matrix, and budgets anchored to
   competitors so that raising one means admitting a loss.
