## 1. Commission and constraints

Wave-15 fix lists 6 and 8 commission production adaptation for custom apps,
offline entry and draft survival. This amends starter §14, client §6.11 and
release-client §3. This explicitly supersedes the earlier requirement that every later E_ADMISSION
warning makes useAppReady false. No storage, sync, session, expiry or authorization protocol
changes. Existing table rules and constraints decide each write. No version
bump or publication belongs to this lane.

## 2. Readiness and current authority

useAppReady means the current account's initial opening succeeded; it is not
permission, connectivity or continuing write admission. Once true, it stays
true for that App and signed-in viewer through release/catalog loading and
later admission warnings. An admission warning never grants permission; even
when readiness remains true the SDK may refuse the next write. Session revocation
and store replacement still use the existing synchronous auth/viewer fence;
this proposal does not retain signed-in identity after that fence. Initial admission failure stays false until a later
successful sign-in/opening; a replacement app or account starts a new readiness
lifetime. Signed-out/restoring auth remains false. AppProvider's existing
app/viewer boundary still resets account-owned drafts; no stale identity is
retained to conceal revocation or store replacement.

The compiled role shell owns drafts and selection above every readiness,
role and release branch. Sticky role is a label only. Protected reads and
submission require a present, complete, fresh, non-revalidating current role
and generated operation availability, as well as initial readiness. Precisely:
isPresent(role) && role.complete && role.fresh && !role.revalidating, plus
api.myRole.available(release) and the protected operations' available(release).
The SDK withdraws prior-generation observations on generation change; no new
per-read generation field or application cache is introduced. Loading,
partial, denied, absent, stale or revalidating role evidence never licenses
protected children or a submission. SDK/server admission still handles races.
A release switch withdraws protected children while preserving the shell and
its user-authored, initially blank drafts/selections. This is not retention of
protected query values: prefilled server-derived values belong to protected
query children and clear with source withdrawal. If an application copies
protected data into another owner, it must clear that derived copy on authority
withdrawal under LLP 3000.023; none of these examples prefill a shell draft. Explicit revocation withdraws authority immediately.

## 3. Custom production plans

Preview stays read-only; apply writes only the exact compiled schema shown.
Retain bare identity insertion only when identity is absent. Bare identity
allows passwords and guests; identity guests is guests-only; password removes
guests. A guest session is a session: when password identity is enabled, signup/login
can replace it through app.auth, with the ordinary account boundary; it is not a dev persona. Pending writes,
replicas and receipts stay scoped to the original guest principal, never rebound
to the new account. Delayed old-view callbacks stay fenced by existing SDK
custody. This is existing cross-account isolation, not guest-data conversion.
Old intents remain retained under the old principal, subject to existing
outbox/receipt/residency bounds; they are neither dropped nor transferred by
signup. Only reopening that exact principal with a still-valid credential can
resume them with their original IDs. Signup replaces the persisted current
credential, so recovery of an old guest whose credential the application no
longer holds is not promised. No new guest GC, credential archive or background
flush owner is introduced. A new owner never sends an old principal's intents.
Test a pending guest write followed by signup as a distinct principal:
the new viewer must neither observe nor submit that intent.

Keep existing blocked-roster bootstrap mutations for compatibility. Extend
planning to a table with an enum column named role and principal identity in
a unique key when no mutation/job inserts or upserts that table, even if the
advisory's approximate reachability misses it. Generate one service:ops-guarded
insert operation per declared role, with that role fixed as a literal, rather
than a caller-supplied role argument. Inputs retain all other writable required
columns and explicit principal defaults. Such provisioning is independent of
fixture values; all declared roles appear even when the current fixture uses
only one. A table with any existing compiled mutation or job insert/upsert path receives no new literal-per-role operations. If blocked, the planner ADDS §14's generic enum-argument bootstrap
mutation plus the displayed independent service read/insert branches; existing authored writer bodies and guards remain byte-identical.
An already reachable table receives no extra bootstrap or seat branch. This includes wave-14's enum-argument bootstrap, which stays untouched.
Saved fixture/test files are not compiled production programs. Each generated
target principal is an explicit argument even when its column defaults to viewer.
This supersedes §14's enum-argument shape only for new fixture-only role tables.
Existing writer paths remain application policy; the planner does
not claim their role coverage. Non-roster and inherited-authority roots stay
explicit review messages. Add only the displayed independent service read and
insert branches; never bypass constraints or rewrite an application's screens.
Fresh names avoid collisions; repeated apply is idempotent once writers exist.
These service-seat proposals deliberately add the displayed provisioning
authority, including enum variants not inserted by an existing narrow writer.
They are not automatically inferred end-user grants: only the trusted operator
seat can call them; apply explicitly authorizes the displayed branches. Keeping
that seat secret and not proxying its authority from untrusted input is the
existing service-seat boundary. Per-role operations insert ONE row each and do
not assume roles coexist for a principal: ordinary unique constraints may make
roles mutually exclusive. Test different target principals for each role and
require a second role for the same unique principal to fail E_UNIQUE. Column
name role is a documented heuristic; even a preferences(role) table is only a
preview of literal attribute insertions, not a claim of authorization meaning.
The whole plan must compile before any file write and retain full-source
preflight/symlink refusal. A failed proposed policy writes nothing.

The principal scan excludes every dot-directory and directories named test,
tests, __tests__ or acceptance, alongside §14's existing exclusions. For source
stems, lowercasing then splitting on dot, dash or underscore excludes components test, tests,
spec, acceptance, fixture, fixtures, proof or smoke. scripts/seed-admin.mjs
remains a runtime review hint; the scanner cannot infer intent from a filename. Runtime source files under scripts still
get scanned. Findings remain bounded review hints, never a proof of complete
migration. Report source lines containing usePersonaApp, persona followed by optional
whitespace and a colon, or ?as= as heuristic custom entry hints (comments and
strings can match). These are discovery pointers to guide production's
account/persona recipe, not an assertion that the line is an executable picker; do not rewrite arbitrary UI.
Upgrade names init --adapt --production for a persona-only project. Starter
§14 already supersedes §7.2's old flag restriction: production mode requires
snapback/*.q and accepts --apply or --dry-run; it is a schema-only mode and refuses --web, --expo and --day2 with E_INPUT
BEFORE planning or writing. This fixes previously ignored flags. --dry-run is
an explicit preview spelling, mutually exclusive with --apply.

## 4. Declaration and recipe corrections

Post-baseline row and projected fields explain their optionality with
“optional: releases before N lack this column”; N is the existing configured
since_release label, not an inferred server generation. Argument additions retain the existing “Since release N” label from release-client §3. In ordinary conditional inference (not only compatibility generation), a literal
string arm joins as its singleton enum domain only when the other arm already
has an enum domain (possibly nullable); enum arms retain their union. Two plain
text arms retain their existing text type and operations. Dynamic text still widens to text; evaluation/laziness and wire values
are unchanged. Example: mode: enum('standby','measure'); projecting
.mode if condition else 'standby' emits "standby" | "measure"; with a nullable
mode the result also includes null. Dynamic text in either arm still emits
string (and null if applicable). Compatibility generation subsequently joins
this precise result with the baseline domain using its existing deduplication;
BaselineRows/Rows namespaces stay separate. This is a precision correction, not a new syntax or IR feature.

Device-less identity createApp calls without sessionStore must produce a type
error naming sessionStore. Device/persona/readOnly forms remain valid. Complete
empty lists already classify as absent; pin that behavior in packed tests.
The client PDF recipe explicitly calls Client.upload(bytes, {file:{type,name}})
(the existing UploadOptions.file signature in contract.ts) and executes
against the packed SDK. Other lanes own the literal wire and proof API pages
(KIT4), ordinary starter advice (DAY5), rules recipes (RULES5), and compiler
notes (LANG4).

## 7. Revision 3 compatibility control

Implementation inspection identified a regression in applying singleton domains
to two plain string arms: ('a' if active else 'b') + 'c' must retain its text
concatenation. The finite-domain correction is therefore scoped to conditionals
whose other arm already has an enum domain, including nullable enum arms. This
still fixes wave-15 lane 071's .mode fallback projection without changing plain
text expressions. A compiled concatenation control accompanies the enum,
nullable, extra-literal and dynamic-text tests. Guest prose also distinguishes
SDK-owned intents/receipts from React drafts, which reset at a viewer change.

## 9. Revision 5: comparison compatibility

[Round 4 Muse](./reviews/3000.011.003.000.001-prod2-r4.muse.md) is READY;
[fresh Codex](./reviews/3000.011.003.000.001-prod2-r4.codex.md) is NOT READY:
equality/ordering of an enum conditional with an overlapping enum that is not
its subset must continue to compile. All text/enum domains compare as runtime
strings, without requiring domain containment (also in existing comparable key
contexts). Assignment to a declared enum still requires its existing domain
checks; comparison grants no assignment authority. Equality retains existing
null handling; ordering still requires present operands. Execution controls
cover all six comparison operators and refuse optional ordering.

The text-bound predicate in §8 is general: any operation accepting present text
via its bound accepts present enum text via that bound. The listed operations
are the current inventory. Existing per-operation adjustments remain unchanged:
lower triples its input bound for Unicode expansion, concatenation sums bounds,
and join multiplies by list cardinality and separator length. An enum+enum
concatenation control joins the existing text/enum orders. No budget or
runtime metering rule is changed.

## 12. Revision 8: corresponding leaves and text-domain soundness

Both [round 7 Muse](./reviews/3000.011.003.000.001-prod2-r7.muse.md) and
[fresh Codex](./reviews/3000.011.003.000.001-prod2-r7.codex.md) were NOT READY.
This section supersedes the conversion-plus-whole-shape-assignability mechanism
in §§10–11. Comparison and inferred-local compatibility recurse through
corresponding value leaves with the existing outer shapes/nominal kinds.
Text/enum string leaves are compatible regardless of which bound/domain is
larger, so opposing field-bound directions cannot reject an otherwise compatible
object. Optional/sequence/object structure remains checked. Actual joined and
flow types keep precise domains; explicit argument/column assignment still uses
ordinary assignable_to and enum constraints. Tests compile and execute both
comparison and local replacement of objects with opposing field-bound directions.

Text-producing operations accept an enum only when ALL its variants satisfy
existing text's disallowed-control-character check as well as scalar bounds.
U+0001 is a legal enum value but cannot be laundered through lower/trim/concat/
slice/join into a purported text result; those operations refuse that domain.
Length/per-op allocation bounds and nullable proofs remain as in §8. Tests prove
the raw enum is valid and each laundering expression is an E_QUARRY_TYPE.
Comparison compatibility is about runtime string representation and does not
constitute this text-domain proof, including for disjoint domains. Disjoint
enum comparison is intentionally admitted (false equality/lexical ordering),
with no assignment or permission implication.

Outer nullable operands of ordering/min/max still require present proof. Nulls
nested INSIDE comparable containers retain existing Value::total_cmp behavior:
null sorts before strings; arrays compare lexicographically; row/map values
first compare field counts then sorted keys and their values. This is existing
core behavior, unchanged here. A compiled/executed nested-null list-of-object
ordering/min control pins it; no new deep-null restriction or trap is invented.

Muse's remaining r7 questions are settled normatively in §§2–3: admission code
and timing are explicit; blocked existing writers receive the displayed generic
seat path, not silent role coverage; per-role inserts respect mutual exclusion;
only user-authored blank drafts are retained; guest intents stay with their old
principal under existing bounded storage with no recovery promise after loss of
that credential. These clarify existing protocols rather than creating new ones.
