**Finding — Medium: a conditional reset suppresses required loop-cardinality provenance.**

Location: [aggregate_provenance.rs:266](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:266), together with the [branch join at line 303](snapback4/crates/snapback4-lang/src/bind/aggregate_provenance.rs:303).

Concrete source-traced counterexample:

```quarry
table posts:
  score: int
  public 'posts'
  update <- allow

mutation setScore(amount: int, reset: bool):
  p = posts['seed'] ! else MISSING
  delta = 0
  for i in range(0, amount):
    if reset:
      delta = 0
    delta = delta + 1
  update posts[p.id] { score: p.score + delta }
```

With `reset = false` and positive `amount`, this writes `p.score + amount`: the caller supplies the accumulated count.

The branch join inserts `delta` into the current iteration scope even though the untouched arm preserves its incoming value. The subsequent addition therefore sees `overwritten = true` and skips the domain’s ARGUMENT cardinality. `delta` remains AMBIENT data with argument control; adding `p.score` produces READ|AMBIENT, so the note fires. Fixed-point iteration does not restore the missing cardinality.

The smallest sound repair is to distinguish a **definite reset on every continuing path** from a binding merely present after a branch join. Preserve possible incoming-iteration dependence, consuming domain cardinality—or falling back to UNKNOWN—when that dependence remains. Add this regression alongside read-domain and unconditional-reset controls; simply tainting every assignment would break the latter.

This is a behavioural finding, not a wording-only correction.

Verdict: NOT READY
