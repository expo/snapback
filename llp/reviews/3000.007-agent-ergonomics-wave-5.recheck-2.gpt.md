## New defect

### N3 — Medium: durable recovery suppresses the first completion notification

**Location:** [local.ts:941](snapback4/packages/snapback4/src/local.ts:941).

Client A submits a write and receives `pending`. Native owner B persists its successful receipt and marks the shared outbox entry sent; interrupted catch-up leaves that entry queued. A’s next flush reads the durable receipt and skips `emitWrite` because `known` is truthy—even though A has never emitted this completion.

Consequently, `client.write(id)` returns `sent`, but A’s mounted `usePendingWrite` remains pending: its subsequent updates depend on `onWrite` ([react.tsx:174](snapback4/packages/snapback4/src/react.tsx:174)).

**Reproduced with stub storage/transport:** the baseline emits one completion; this commit emits zero. Both recover `sent`.

**Smallest fix:** call `emitWrite(receipt)` regardless of `known`, letting the existing per-client emission tracking suppress duplicates. Add a regression where another owner settles an already-observed pending write and assert exactly one notification.
