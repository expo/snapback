# LLP 3000.007 §8.7 and §5.9 — blind disclosure review (grok)

**Verdict: READY WITH CHANGES**

The two proposals point at the right boundary: a write should disclose its outcome, a read should disclose rows the read rule admits, and a third channel should not appear (LLP 3000.007 §4 principle 7, lines 319–322). §8.7’s Postgres-shaped split — the update rule admits the write; the result, `old`, and `E_CONFLICT.current` stay off the author’s program — is the right *content* rule. §5.9’s split — a predicting mutation still needs a complete capped group; a non-predicting one may pass a bounded page — is the right *device* rule.

They are not yet the observer rule they claim. As written, §8.7 lets a writer distinguish *absence*, *hidden-and-refused*, and *hidden-and-admitted*, and lets immutable / conditional-update refusals probe fields the update rule did not admit. As written, §5.9 reopens the meter-cut review’s mutation abort-vs-success oracle on a non-uniform prefix, a bit a query of the same prefix no longer gives. Both close with named wording changes. Neither proposal is sound to implement from the RFC text as it stands.

## Overall assessment

**Proposal 1** is a real restatement removal (LLP 3000.007 §3.1 R, lines 203–213): Clique builders opened counter tables (`read <- allow` / `public`) because unique-key upserts and valued writes go through a read-rule `Get` (`bind/program.rs` 603–663) and because hidden unique collisions are generic `E_RULE` (`write.rs` 300–318; S05). The engine’s by-id `update` / `upsert` already `fetch`es *without* a read check (`read.rs` 177–186; `write.rs` 66–93) and then applies the **update** rule (`write.rs` 95–100). So “today every hidden target is `E_RULE` whatever the write rule says” is true of the **binder’s unique-key path and of collisions**, not of a bare `update t[id]`. The proposal needs to change the binder and the device, not only `replace`.

What “the update rule’s admission implies” can honestly mean, matching the Postgres analogue the RFC cites (§8.7, lines 905–906) and the RFC’s own sentence at 912–914, is:

> Success means: a row exists **and** the update rule admits this writer for that row (and, if the write was conditional, the condition held). That is existence of an *admitted* row, and the predicates of the rule/condition, and nothing else. Absence, hidden-and-not-admitted, and hidden-and-condition-false are one observer word.

The RFC currently says the opposite of the second sentence: “the outcome discloses success **or the write rule’s refusal**” (lines 906–907). That refusal, kept distinct from `NOT_FOUND` / `E_CONFLICT` / incomplete-upsert `E_INPUT`, is existence of a row the update rule did **not** admit.

**Proposal 2** is right that `E_STRUCTURAL_FANOUT` (`admission.rs` 61–75, 241–251) is a prediction constraint (D), not a meter constraint (M). Admitting the pass while the runner still uses `Cut::Abort` (`meter.rs` 117–129; `local.rs` 60; `mod.rs` 757) makes “the scan walked more than 8,192 candidates” a mutation outcome. Queries of the same non-uniform prefix no longer carry that bit (`reviews.rs` `h1_a_non_uniform_scan_is_capped_whatever_the_meter_found`, lines 160–176; JOURNAL disposition of H1). That is a new channel.

## Strengths

- **Principle 7 is the right test** (LLP 3000.007 §4.7, 319–322). Withholding the result row, withholding `E_CONFLICT`’s `current`, and keeping `old` out of the author’s environment are the correct content closures. They match how `get` already treats hidden and absent as one word (`read.rs` 188–230) and how `/m` already omits `metered` (`serve.rs` 855–861; JOURNAL H2/H3).
- **S05 is mostly preserved on purpose.** `visible_collision` (`write.rs` 300–318) still turns an unreadable unique/id clash into generic `E_RULE` with the write effect, and the message must not name the key (`security.rs` 34–48). Keeping `insert … if absent` on that path (`write.rs` 39–48; `ir.rs` 108–109: “a unique clash yields absence, never the conflicting row”) is consistent: `Ok(false)` / `null` is the *readable* clash. Giving hidden clashes `null` would be a new existence bit for a writer the update rule has not admitted — the RFC is right to refuse that (lines 910–911).
- **§5.9’s residency split is the right one** (§6.2, 642–674; principle 1, 298–303). A predicting mutation must still be an exact complete group (`admission.rs` `page_problem`, 241–251: uniform, schema cap, literal bound ≥ cap, no cursor). A device that does not predict should not be asked to. `check --cost` printing “a pass over the first N visible rows” is the honest claim, *if* the runtime matches it.
- **Delivery stays the read rule’s audience** (LLP 3000 §7, “delivery is bound to the rule’s probe”; partition inversion). `partition::row_changed` (`partition.rs` 123–144) emits `Put` only into the row’s sync partitions. The writer’s stream is the merge of `p:<writer>`, `public`, and groups they held (`partition.rs` 518–597). A counter synced to `.principal` (the recipient) does not put the row on the writer’s device. Stream catch-up with no events still advances to head (`partition.rs` 548–550), so an outbox `sent_seq` does not stall. That part of proposal 1 holds.
- **The `E_BOUND` envelope already names meter, ceiling, and site, never the count** (`error.rs` 205–216; `guide.rs` 1227; `reviews.rs` 239–246). Proposal 2 must not make *whether that envelope appears* the hidden-population bit the count was stripped to avoid.
- **Patching upsert (§5.4, 466–474) is the right write shape** and, if the merged image never leaves the engine, does not itself leak old columns. Replace-upsert of a partial object is what lost an avatar; patch is what builders mean.

## Concerns

### 1. High — Unreadable targeted writes still distinguish absence, refusal, and conflict (proposal 1)

Binder layer, which is what Clique actually hits:

- Unique-key `update` / `upsert` **Gets under the read rule first** (`bind/program.rs` 603–610, 637–641). Hidden looks absent: `NOT_FOUND` on alternate-key update; upsert mints a new id and **inserts**, then `visible_collision` → `E_RULE` (`security.rs` 38–43, the `put` case).
- Valued update/upsert **re-Gets** the row (`bind/program.rs` 630–632, 661–663). Hidden result is `null` even if `replace` applied. After LLP 3000.007 §8.1 puts `result` on `sent`, `sent + row` vs `sent + null` is readability, which a query already gives — **unless** the implementation returns the merged image instead of a `Get`. Patch merge **must not** be that result (concern 4).
- Conditional `update … if .status = 'open'` Gets `current`, then `Stmt::Check` (`bind/program.rs` 614–625; `runner.rs` 200–206). Field on `null` is `null` (`runner.rs` 325–329), so hidden and absent both fail the check today (`E_CONFLICT`). To *perform* a hidden conditional update, Check must see engine `old`. Then `E_CONFLICT` vs `NOT_FOUND` is “row exists and the condition failed” — content plus existence, not admission.

**What the update rule’s admission implies:** the predicates of that rule (and of an engine-evaluated condition) held of some live row at that key, so that row exists. It does **not** imply: a row exists that the rule rejects; the values of immutable columns not named in the rule; the pre-image of a maintain the writer can read, beyond the delta they chose.

**What would resolve it**

State in §8.7, and implement, for a row the writer **cannot read**:

1. **One failure word** for absence, update-rule false, and failed `Check` condition. Prefer `NOT_FOUND` for “no admitted row” (Postgres 0-row `UPDATE`) and keep `E_RULE` only when the writer **can** read the row and the update rule fails. Do not publish `E_CONFLICT` for an unreadable current; if the condition failed on a hidden row, that is the same word as absence.
2. **Immutable mismatch** on an unreadable row is that same word, or the binder refuses to mention immutable columns in a patch the writer cannot read. It must not be a named `E_CONSTRAINT` the writer can use to search `old`.
3. **Incomplete patch-upsert** (`E_INPUT` missing required columns on the insert path vs success on the update path) is existence even when the update rule would deny. Unreadable + not admitted + incomplete payload must match absence (`E_INPUT` both sides, or the generic failure word both sides).
4. Unique-key addressing is an engine lookup **without** the read rule, then the update rule. The binder `Get` at `bind/program.rs` 603–641 is the Clique bug; leaving it in place makes §8.7 a no-op for `upsert unreads[conversationId, principal]`.
5. Valued writes and `/m` `result` return a `Get` (null if hidden) or nothing, never the merged image. `E_CONFLICT.current` stays a `get` (read rule) or is omitted. Withholding happens **before** `record_applied` (`mod.rs` 803–808), so replay (`serve.rs` 763–772) cannot grow a row.

### 2. High — The device will predict `NOT_FOUND` or a pending insert unless §8.7 names a runtime class the code does not have (proposal 1, Q2)

§6.2’s “queued without a row” is a **read-site** class: a `server` site (online-only / `connected` / native-without-module) (`llp/3000.007` 664–668). The client’s twin is “every table the op touches is synced” (`local.ts` 788–789).

A Clique counter table `sync to .principal` is synced. The sender’s mutation that upserts the recipient’s row is **eligible to predict**. On the device:

- `fetch` of a no-horizon synced table that is simply **not held** does **not** set `beyond_horizon` (`read.rs` 177–181: `beyond_horizon` on miss only if `sync` is `None` or the table has a horizon).
- `update` then returns `NOT_FOUND` (`write.rs` 72–73).
- `local::predict` returns that refusal, not `E_PREDICT` (`local.rs` 58–69: `E_PREDICT` only if `beyond_horizon`).
- `Device::admit` treats `E_PREDICT` as “queue, `predictable = false`” but **any other error fails admit** (`device.rs` 560–574).
- The JS client then emits `failed` and **never POSTs `/m`** (`local.ts` 792–793).

So under the RFC as written, the local-first Clique write never reaches the server. If admit were patched to queue on `NOT_FOUND`, the local outcome would still be a predicted failure that the server later turns into `sent` — invariant 4’s typed conflict, and an existence bit (server applied a row this device does not hold).

Worse, **upsert** on a device miss takes the **insert** path (`write.rs` 89–92). If the insert rule admits the writer’s image, `Predicting::put` writes a `pending` row (`device.rs` 159–164). The device does not re-judge its partition (LLP 3000 §7): that pending row is now **held** and queryable. The server will update the real hidden row and will **not** put it on the writer’s stream. Until watermark passes `sent_seq`, `predictions::replay` (`predictions.rs` 54–82) keeps re-applying a predictable insert. That is a partition-inversion-shaped leak of a row the read rule never delivered (the writer’s own insert image, not the hidden old image — still a row they should not hold).

**Pending absence**, if they **do not** predict: outbox entry, no pending row. Hidden and absent look the same locally (neither is held). That does **not** distinguish them. That is the safe shape.

**Replay (`_ops`):** at-most-once returns the recorded outcome (`mod.rs` 686–706, 726–733). It discloses whatever the first apply stored. If the first apply withheld, retry does not grow a row. If `current` or a merged result was stored, replay is the leak. Failed writes are also recorded (`mod.rs` 803–807).

**What would resolve it**

- Runtime, not only §6.2: a device `fetch` miss (or unique-key miss) on a write is `E_PREDICT` / queued-without-a-row, never predicted `NOT_FOUND`, never predicted insert.
- `admit` must queue that class; the client must send `/m`.
- No `pending` row. Local queries do not show the write. The later stream does not `Put` it to the writer (already true if audience excludes them).
- `N_NOT_PREDICTABLE` / `predicts: "never"` when *every* call would miss is optional; the runtime miss is the obligation.
- Tests: sender device, recipient-synced row, upsert admitted by update rule → outbox without predicted keys; server `sent`; writer snapshot has no row; recipient snapshot has the patch; retry `/m` with the same id is `replayed` and still has no result row.

### 3. High — Abort vs success on a non-uniform pass is the meter-cut mutation oracle, and a query of the same prefix does not give it (proposal 2, Q3)

Today a mutation `for` over a page is admitted only if `page_problem` is `None`: schema cap, **uniform** read rule, literal bound ≥ cap, no cursor (`admission.rs` 241–251), and no sibling non-uniform scan (74–75, 250). That is why the meter-cut review’s mutation example (`notes[] last 100 by byTime`, non-uniform `.owner = viewer`) does not run as a loop.

§5.9 admits that loop when the mutation never predicts. The runner still uses `Cut::Abort` (`mod.rs` 757; `meter.rs` 117–129). `scan_with_keys` charges **every** candidate, hidden or visible, one examined (`read.rs` 450–453), the same miss cost as a hidden point read (JOURNAL H4). Hidden rows do not fill `take` (484–512). The `for` domain is the **full scan before the body** (`runner.rs` 265–267, 175–188). So:

| Store (writer can read none) | Mutation `for` over `first 50` | Query of the same prefix (after H1) |
|---|---|---|
| 0 rows | `sent`, 0 iterations | `[]`, `complete: false`, `next: null` |
| 100 hidden | `sent`, 0 iterations | same card |
| 8,193 hidden | `E_BOUND` examined, ceiling 8192, site = the scan | same card as empty (`reviews.rs` 172–176) |
| 3 visible, then a long hidden run | `E_BOUND` if examined blows before the scan returns; else `sent` with 3 | 3 visible, `complete: false`, `next` from last visible |

The author’s program can count iterations (visible only) — that is the same number a query returns. `rows_written` is not on `/m`. **Abort vs success** is not. JOURNAL’s H1 fix made non-uniform queries `complete: false` *whatever the meter found*; empty hidden and huge hidden are one card. Mutations abort. That was meter-cut **M3**. §5.9 reopens it for every non-predicting caller of the new pass.

`E_BOUND` no longer names `actual` (`error.rs` 205–209). It still names **kind, ceiling, and site**. Whether the envelope appears is a 1-bit lower bound on hidden+visible candidates at the examined ceiling. That is the oracle LLP 1001 §3 and the meter-cut review closed.

It is **new**, not “already available through a query over the same prefix.”

Charging hidden rows nothing would close the observer bit and reopen unbounded walk (the scan does not `step` per candidate). Refusing the pass when the read rule is non-uniform on the prefix closes it and keeps DoS off the mutation (jobs already chunk).

**What would resolve it**

Pick one, and write it in §5.9:

- **Preferred:** the admitted pass **ends the page as a query does** when examined/index/probes hit the ceiling (`Cut::Cap` for that scan, or treat overflow as end-of-page without `Err`). The mutation then `sent`s with the visible prefix (possibly fewer than N). Atomic: those writes or none. `E_BOUND` remains for `rows_written` (visible), steps, heap. `check --cost`: “a pass over at most N visible rows, ending at the examined ceiling the way a query of this prefix does; it does not abort on hidden candidates.”
- **Also sufficient:** refuse the pass unless `scan_visibility` is uniform (keep `page_problem`’s uniformity clause; drop only the schema-cap / complete-group clauses for non-predicting mutations). Uniform-false already restores the meter and stops (`read.rs` 504–509); abort vs success then matches empty vs empty.

A predicting mutation keeps `E_STRUCTURAL_FANOUT` as today. Do not let `: server` on a synced non-uniform scan buy the abort oracle.

### 4. Medium — Patching upsert creates a merge image replace never had (Q4)

Replace upsert validates a **complete** row before `fetch` (`write.rs` 84, 89–92). Missing required columns are `E_INPUT` whether or not the row exists. The written image is the author’s object; unnamed columns are not “kept,” they are absent/invalid.

Patch merge (`write.rs` `update` 75–78 already patches) reads `old` in the engine. Observables replace did not have:

- **Success on a partial object iff the row exists** (and the update rule admits). Absence is `E_INPUT` naming missing required columns. That is concern 1.3.
- **If anything returns the merged row** (`result`, `current`, a bound `old`, a pending device row), every unnamed column of `old` is disclosed. Replace could not do that. This is the one patch-specific content oracle.
- Immutable / unique fields *omitted* from the patch are not probed (good; less oracle than replace).
- `after insert` still only on the insert path (same as replace).

**What would resolve it:** §5.4 plus §8.7 must say the merged image is engine-only. Valued upsert of a hidden row is `sent` with `null`/omitted result. Device must not materialize the merge. Incomplete payload vs success is folded into concern 1.

### 5. Medium — S05 cases (Q5)

| S05 case (`security.rs` 34–48; remediation row S05) | Proposal |
|---|---|
| `insert` colliding on a unique index with an unreadable row | **Keep** `E_RULE`, no key in the message (`write.rs` 39–48 + 300–318; also the id path 52–56). |
| `insert` colliding on id with an unreadable live row | **Keep** `E_RULE` then, if they ever passed `visible_collision`, the named constraint. Hidden stays `E_RULE`. |
| `insert … if absent` (`quiet`) on a hidden unique clash | **Keep** `E_RULE` (does **not** become `null`). Readable clash stays `sent` + `null` (`security.rs` 46–47). |
| `upsert` (`put`) on a hidden unique clash | **Change:** today Get-miss → insert → `E_RULE`. Proposed: if the update rule admits, **perform** the update/patch, no row in the result. If the update rule does not admit, **keep** `E_RULE` (same word as today’s collision). |
| Readable unique clash | **Keep** `E_CONSTRAINT` naming the index (or `null` for if-absent). |

**Insert-if-absent vs upsert on the same hidden row.** A writer who is not update-admitted: both `E_RULE` (if-absent by policy; upsert because update denies or insert collides). A writer who **is** update-admitted: if-absent stays `E_RULE`; upsert `sent`. That is exactly “the update rule let you modify it, so you may learn it exists.” It is **not** a new S05 bypass: they still do not learn the hidden key’s *name* from if-absent, and they do not get `null` vs insert. Using upsert to learn what if-absent will not say is the disclosure §8.7 exists to grant. State that in the RFC so S05’s test is rewritten, not quietly inverted.

If upsert succeeds on hidden while if-absent is `E_RULE`, §8.6’s extra sentence (“or a unique key collided… use `upsert` under an `update` rule”) is the right builder hint — **after** concern 1’s collapse, so `E_RULE` on if-absent is not also the deny/absence word for update.

### 6. Medium — A readable maintain of a hidden source is a delta oracle (proposal 1)

Not a third `/m` field. `maintain` puts follow the **maintain table’s** read/sync rules (`write.rs` 395–424; partition inversion: a row reaches a device only through that table’s audience). If the writer can read the maintain and can set an absolute field on a hidden source, they learn `old` from the delta. Today they could not write that source.

This is allowed by principle 7’s second clause (“a read discloses rows the read rule admits”) and is the author’s schema. Clique unreads that sync to the **recipient** do not give the sender this read. World-readable aggregates over hidden counters would.

**What would resolve it:** one sentence in §8.7: a maintain (or other table) the writer may read is a declared read-rule channel; §8.7 does not make a hidden source’s pre-image visible *except* through such a row. Do not treat that as “existence only.” Optional `check` note when an update rule is wider than the read rule and a maintain the writer can read sits on that source.

## Suggestions

- Write the observer contract as a table in §8.7: for an unreadable target, `{sent, NOT_FOUND}` (or one generic failure) are the only codes; `E_CONFLICT` / named immutable / incomplete-upsert `E_INPUT` do not appear. For a readable target, today’s codes remain.
- Do not implement engine-internal `old` in **patch expressions** unless you bind `old` only inside the update statement and never in `return`, `require`, or a later assignment. Clique increments are the **maintain** (already §8.6). §8.7 unblocks SET/patch, not `count: old.count + 1` in the author’s program.
- `delete` is still `fetch` + delete rule (`write.rs` 108–115`) with no read check. Leave it out of §8.7 or apply the same collapse; do not silently widen it.
- Proposal 2: keep `E_STRUCTURAL_FANOUT` for merges and for `Unknown` origins (`admission.rs` 234–236). Only `Origin::Page` with a literal bound, in a `predicts: "never"` mutation, is in scope.
- `check --cost` should print the examined ceiling next to “first N visible,” so builders do not think they scanned the population.
- Strip `metered` / `tables` / `events` from the `_ops` payload or store the same body `/m` returns, so replay cannot grow fields.

## Answers to the six questions (compressed)

1. **Oracles.** Enumerated in concern 1. Under the RFC as written, `E_RULE` vs `NOT_FOUND` vs `E_CONFLICT` vs incomplete `E_INPUT`, named immutable `E_CONSTRAINT`, and a returned merge image tell the writer more than “an admitted row exists.” `seq`, `replayed`, stripped `metered`, the writer’s empty stream, and S05’s generic hidden clash do not, if withholding is applied before `_ops`.
2. **Device.** Yes, unless classified at **runtime miss**: predicted `NOT_FOUND` fails admit and never sends; predicted upsert insert plants a pending row. Pending **absence** (queue, no row) does not distinguish hidden from absent. Replay discloses only what `_ops` stored.
3. **Loop.** Yes: abort vs success is a hidden-population bit at the examined ceiling. It is **new** relative to a query of the same prefix (H1). Close it by capping the page like a query, or by refusing non-uniform prefixes. Charging hidden nothing without another bound is a DoS hole.
4. **Patch upsert.** Yes: partial success vs `E_INPUT`, and any leak of the merged image. Engine-only merge does not.
5. **S05.** Keep hidden insert, id, and if-absent clashes as `E_RULE`. Change hidden **upsert** to success iff the update rule admits. Upsert-to-learn-what-if-absent-hides is the admission disclosure, not a new uniqueness oracle, **provided** concern 1’s collapse holds.
6. **Tests.** Named above.
