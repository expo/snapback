I found these remaining issues:

1. **Medium — Raw schemas admit invalid integer-range metadata.**  
   Location: [schema/columns.rs:142](/home/ccheever/projects/sb4-ws-lang2/snapback4/crates/snapback4-core/src/schema/columns.rs:142), [ir.rs:102](/home/ccheever/projects/sb4-ws-lang2/snapback4/crates/snapback4-core/src/ir.rs:102).

   The recursive column-bound walk checks list lengths but never checks `IntRange`. I reproduced `schema::validate` returning no issues and `Engine::memory` successfully admitting a column with `IntRange { min: 5, max: 1 }`. An empty-table adoption can therefore install a type that no integer satisfies. Out-of-i53 endpoints also escape column admission; argument `bounds_valid` checks ordering only.

   This leaves Codex 10’s accepted raw-metadata concern unresolved. It does **not** bypass the value validator: writes into the reversed range refuse.

   **Smallest fix:** add recursive `IntRange` metadata validation through optionals and lists, requiring `I53_MIN <= min <= max <= I53_MAX`; apply the same rule to argument metadata.

2. **Medium — Calendar schedules fabricate boundaries at the i53 edges.**  
   Location: [schema/schedule.rs:46](/home/ccheever/projects/sb4-ws-lang2/snapback4/crates/snapback4-core/src/schema/schedule.rs:46).

   `month_boundary` checks the month start before adding the schedule offset, then substitutes `I53_MIN`/`I53_MAX` on overflow. That differs from the checked calendar semantics.

   Concrete reproduction: a valid monthly schedule at **day 28 00:00** has a representable boundary at `-9007198704000000` in month `-3425122`. At that instant, `boundary` incorrectly returns `-9007199254740991`; `next` skips to the following month. At the positive edge, `next(boundary(I53_MAX))` returns `9007200604800000`, outside i53.

   The server and dev clock inherit these results. The Lean builtin proofs do not establish schedule correctness.

   **Smallest fix:** compute the civil start plus offset in `i128`, check the completed boundary, and explicitly represent/refuse an unavailable previous or next boundary instead of substituting an endpoint.

3. **Medium — The oracle evidence lacks the promised coverage guarantee.**  
   Location: [lean.rs:487](/home/ccheever/projects/sb4-ws-lang2/snapback4/crates/snapback4-difftest/src/lean.rs:487), [ast.rs:428](/home/ccheever/projects/sb4-ws-lang2/snapback4/crates/snapback4-difftest/src/ast.rs:428), RFC §§2.5, 5, 8–9.

   Calendar coverage is counted **before** unsupported cases are excluded. The report has no supported-calendar comparison counts, and campaign failure does not depend on calendar coverage. I reproduced a successful one-case campaign with zero calendar coverage and its sole case unsupported.

   Also, the generator’s operation signatures remain unbounded: it generates bounded **columns**, but not the bounded **arguments** promised by §5. Dedicated argument tests exist, so this is an evidence gap rather than a demonstrated runtime defect.

   **Smallest fix:** report generated, supported, agreeing and disagreeing calendar cases separately; enforce the promised coverage condition for qualification campaigns; add bounded argument generation. Record those counts and qualify “every calendar case agrees” as “every supported calendar case agrees.”

4. **Low — §4 describes the wrong failure stage for the preceding decoder.**  
   Location: [RFC §4](/home/ccheever/projects/sb4-ws-lang2/llp/3000.040-bounded-ints-calendar-months-and-small-table-caps.rfc.md:459), `schema/capabilities.rs` at `9163cad9e8`.

   A newly serialized calendar-key or monthly-schedule schema carries `calendar-month` or `calendar-schedule`. The preceding decoder already rejects unknown capability names with `E_SCHEMA_CAPABILITY`, before reaching `CalendarKey::validate` or schedule admission. Thus the blanket claim that older binaries use their own validation message instead of the named capability error is false.

   **Smallest fix:** distinguish capability-aware prior binaries from older decoders, and pin the behavior with a preceding-decoder fixture. The actual fence remains sound.

5. **Low — The implementation record needs reconciliation with the final representation and guide placement.**  
   Location: RFC §§1.3, 6, 9; [guide/jobs.rs:25](/home/ccheever/projects/sb4-ws-lang2/snapback4/crates/snapback4-lang/src/guide/jobs.rs:25).

   §1.3 still specifies `Option<i64>` endpoints, while the final implementation uses `i64` endpoints with omitted i53 defaults. §9 also says the jobs card carries the calendar material “in full,” although its addition is an example comment without the anchor explanation required by §6.

   **Smallest fix:** document the compact endpoint representation and either add the jobs-card anchor explanation or explicitly route it to the time card.

The **most important missing test** is recursive malformed-range admission: reversed and out-of-i53 metadata at top level, inside an optional, and inside both list representations. It would expose finding 1 immediately. The next useful witnesses are populated whole-table-cap adoption and reopening billing after a partially completed multi-chunk run.
