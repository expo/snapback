# Round 1 brief — "one restricted-but-expressive language for both sides"

You are one of three model families (Claude Fable 5, codex gpt-5.6-sol, grok-4.6)
in a structured, multi-round design discussion orchestrated by Claude Fable 5 on
behalf of Snapback's founder. This is **round 1 and it is blind**: you have not
seen and must not guess at the other panelists' answers. In round 2 you will see
all three round-1 answers plus the orchestrator's own candidate, and be asked to
attack them. In round 3 the panel converges. Budget your effort for depth here.

## The question (founder's words, verbatim)

> So the real first question isn't whether to restrict the language. It's whether
> the restricted language can be made expressive enough to be the only language —
> bounded fan-out, grouped counts, multi-table derivation, bounded graph
> traversal. If yes, the agreed design works. If no, you're buying offline at a
> price the benchmark already shows you losing.
>
> Can we come up with something that solves both sides of this?

"Both sides" means: **server-side** (authority, serializable transactions,
reactivity/invalidation, row-level authorization, bounded work) **and
client-side** (cold retention of private data, local re-execution while offline,
optimistic prediction from the same definition, honest completeness) — served by
**a single language** with **no second query class** and **no capability that
depends on spelling**. If the answer is "start over," the founder will pursue it
directly, so the design must be one you would actually build.

## What to deliver

Write a single document, ≤ 3,500 words, with exactly these headings so the
orchestrator can compare panelists side by side:

### 1. Position
Can one restricted language be expressive enough to be the only language while
keeping static-or-derived read sets, retention, authorization, and local
re-execution? Yes / no / conditional — and the one mechanism your answer rests on.

### 2. The crux question (answer this explicitly)
LLP 0329.004 F3 and LLP 0329.005 P1 both assert that an arbitrary deterministic
function cannot be re-executed on a client because "the function does not
describe what data it needs." **Is that claim still true if the server ships the
*recorded* read set of the last execution — as index ranges (including
absence/empty ranges), the rows inside them, and opaque verdicts for rule
evaluations whose inputs the viewer may not read — alongside the result?** Work
it through concretely for the private-chat case: `messages(conversation)` with a
membership read rule, then (a) a local optimistic `send` while offline, (b) a
local delete of one held row, (c) a membership revocation that happens while the
device is offline. State where static derivation beats dynamic tracing, where
tracing beats static derivation, and whether they compose.

### 3. Your proposal
The language's core semantics — what is admitted, what is refused, and the
mechanism by which read sets, closures for offline, authorization dependencies,
indexes/cost bounds, and optimistic prediction are derived. Name the execution
substrate (does JS run in the authoritative data path? what interprets the
program on the client?). Say what the client *is* (result cache / closure cache /
engine) and why it stays small. Say how Postgres graduation works. If you have
two proposals, give both and rank them.

### 4. Worked examples (concrete code, in your proposed spelling)
- Clique private chat: schema + membership rule + `messages(conversation)` + `send` with prediction.
- Relay `boardView`: board + columns + cards (+ activity) at one snapshot.
- Relay `boardSummary`: card counts per column.
- Split ledger: per-participant balances across four tables.
- A bounded graph traversal (folder ancestors or 2-hop "friends of friends").
- Show the static bound / cost certificate (if any) the compiler reports for each.

### 5. Evaluation of LLP 0329.005's P4
Where it is right; where it fails or costs too much; whether refusing
row-level `if`/`for` is necessary for its guarantees or merely convenient; what it
would score on the Clique/Relay/Split census against Convex in an agent bakeoff.

### 6. Refusals and objections
What your design honestly cannot express; the three strongest objections to your
own proposal; the single most likely way it loses the Clique benchmark to Convex.

### 7. Confidence
Per major claim, high/medium/low, with the reason.
