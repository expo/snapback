## Verbatim review

### Code review — ephemeral tables — Claude Opus 5.5 (max)

**Verdict:** BLOCKED. There is one High finding. Its fix is small and contained.

## Summary

The feature works end to end on the local-first tier. With the real CLI and two wasm clients, typing is first seen 7.6–10.6 ms after the first call. It is gone 3,871–3,900 ms after the last call, and a burst sends 2 requests against the durable control's 45.

These pieces held up in code reading and probes:
- **Renewal law:** every deadline stamp re-checks the insert rule, and a refusal matches the update's own refusal.
- **`$deadline`:** it stays off the wire on returned rows, scans and point reads.
- **Generation fence:** the read-transaction identity check plus the hub binding compare.
- **Capacity:** declared-size accounting, checked before the epoch moves, with undo.
- **Rule probes:** none may reach an ephemeral table.
- **Lock order:** engine → hub → wake; I found no cycle.
- **Renewal proof:** conservative, as rev 3 asks.
- **Client lane:** ordering, `renews`-only coalescing, the renewal window, offline drop, the 256 bound, refusals that leave the link online, and facades that route before any durable admission.

The blocker is a change to durable behaviour. On any `dev` schema adoption, held polls now report the stale generation and then miss the change, and this happens on schemas with no ephemeral table too. The rest is a weakened wake contract for durable commits outside `/m/`, tests that cannot see a lost ephemeral wakeup, and two small items.

## Findings

### F1 (High) — Dev adoption: held polls answer with the old generation, then miss the new one (durable-only schemas too)

- **Where:**
  - `crates/snapback4-core/src/engine/mod.rs:513`: `adopt` calls `clear_and_rebind`, whose publisher wakes every poll (`serve_ephemeral.rs:45-52`).
  - `crates/snapback4/src/serve_changes.rs:58-64`: the answer on `reset` uses `wake.generation`, and the `durable` predicate at line 60 ignores generation.
  - `serve_adoption.rs:187,202`: `shared.generation` and `wake.generation` are published only after the rebind.
- **What is wrong:**
  - Every adoption changes the incarnation, whatever the schema.
  - The rebind publisher wakes every held poll, legacy ones included, before `publish_engine` has written the new generation. The poll answers at once with the old generation.
  - The next poll does not answer on a generation change. It waits for a durable commit or for its `wait` to run out, which is 25 s for streaming clients.
  - The local-first client treats `json.generation !== generation` as the adoption signal (`local.ts:841`). So after a schema edit it does not sync or refetch the backend for up to 25 s.
  - Base woke polls after `*generation = next`, so they answered with the new generation.
- **Evidence:** `/tmp/eph-code-…/probe-adopt/probe.mjs`, a durable-only schema, one held poll, then a table added to `schema.q`:
  - **Base `0badac987`** (built from `git archive`): answered 87 and 92 ms after the edit with `generation: 2`.
  - **Branch:** answered about 380 ms after the edit with `generation: 1`, both for legacy polls and for polls sending `ephTables=`. The next poll held its full 8 s `wait`, then reported `generation: 2`.
- **Proposed fix:**
  - Carry the hub's binding `(identity, generation)` in `Snapshot`, and have the publisher set `wake.store_id` and `wake.generation` together with `wake.eph`, under the same lock.
  - Also answer a poll when `wake.generation` differs from the generation it entered with.
  - Add a regression test: a held poll across a `dev` adoption of a durable-only schema reports the new generation.

### F2 (Medium) — Durable commits outside `/m/` and `/seed` no longer wake polls directly

- **Where:**
  - Commit sites that notify only `committed` and never touch `wake.seq`:
    - `actions.rs:87,153,184,219`
    - `effects.rs:190`
    - `serve_routes.rs:103,124`
    - `serve_route_verify.rs:45,87`
    - `serve_maintenance.rs:77`
  - Polls now wait on `polls` and answer only when `wake.seq` moves (`serve_changes.rs:50-60`).
- **What is wrong:**
  - Base polls woke on any `committed` notify. Now a poll learns of these commits only when maintenance next runs `engine_work` → `publish_engine`. That happens when maintenance wakes on `committed`, or within 100 ms otherwise. The delay is bounded, but the RFC §3.3 contract ("a durable commit updates seq under that mutex and notifies polls") no longer holds.
  - Two existing tests had to add `lock(&host.shared.wake).seq=1; polls.notify_all()` to their simulated commit (`serve_tests.rs:575,655`). The production sites got no such change.
  - `publish_engine` (`serve_ephemeral.rs:54-68`) now notifies both condvars on every maintenance `engine_work`, where base notified only when seq advanced. That is a steady stream of spurious wakeups.
  - `publish_engine` also takes the hub lock while holding the engine. So maintenance, and every request queued behind the engine, waits for any running ephemeral program.
  - That unconditional notify is also what hides a lost ephemeral wakeup in the JS tests (F3).
- **Proposed fix:**
  - One helper that updates `wake.seq` under the wake mutex and notifies both condvars, called at every commit site.
  - `publish_engine` should notify only on a change and should not take the hub. The publisher already keeps `wake.eph` current.

### F3 (Low) — The acceptance e2e and the client watch tests pass with the ephemeral wake removed

- **Where:**
  - `packages/snapback4/test/ephemeral-e2e.test.mjs:56`: durable writes are interleaved with the burst.
  - `ephemeral-watches.test.mjs:19-46`.
- **Evidence:** a mutant that drops `shared.polls.notify_all()` from the publisher (`serve_ephemeral.rs:50`):
  - **e2e:** 5/5 pass, first seen 6.5–10.5 ms, indistinguishable from the real build.
  - **Watch test:** passes on both tiers.
  - **Rust `ephemeral_tests`:** 4 of 12 fail (`wake took 1.008062208s`). So the Rust tests guard the wake; the JS tests do not.
  - **Why the JS tests pass:** each `setDurableTyping` commit wakes B's poll, and the answer carries `typing`. Maintenance's unconditional notify covers the rest.
  - **Not differential either:** here the durable control also met the 5 s bound (4.00–4.29 s).
- **Proposed fix:**
  - Run the durable control in its own phase or on its own server.
  - Assert the delivery path, for example that the `/changes` answer just before first sight named `typing` without moving seq.

### F4 (Low) — Lazy `_sequences` creation is a durable store change outside LLP 3000.017

- **Where:** `store.rs:166`, `store/sequences.rs`, `store/activation.rs:101-107`.
- **Judgment:** justified.
  - It fixes main's red published-0.2.33 capability fences, which E3 reproduced on base.
  - All `_sequences` access is in `store.rs`, and the new test covers rollback.
  - But it is unrelated to ephemeral tables. It also adds a `sqlite_master` probe to every `sequence_value` call and a `CREATE TABLE IF NOT EXISTS` to every `set_sequence`.
- **Proposed fix:** land it as its own commit with its own journal line, and cache the probe per transaction.

### F5 (Low) — The card's chats-list hint shows the viewer's own typing

- **Where:** `guide/ephemeral.md:39-40`. In `typingInMyRooms`, the nested read `typing[roomId = .roomId] { principal }` has no `.principal != viewer`, unlike `typingIn` and the example in RFC §2.3.
- **What is wrong:** a builder who copies it shows themselves typing in their own chats list.
- **Proposed fix:** filter out the viewer in the nested read.

## Tests and probes run

1. **Build:** `cargo build --workspace && bash scripts/build-wasm.sh && bun run --cwd packages/snapback4 build` succeeded: `wasm 2014270 B raw, 578894 B gzip (budget 579833: ok)`.
2. **`node --test packages/snapback4/test/ephemeral-e2e.test.mjs`:**
   - The first run failed with `timed out: server`. The freshly built binary's first launch stalled for 12 s, the host's known launch-scan trap, not this change.
   - After a `--version` warm-up it passed:
     - Ephemeral typing first seen after 7.6–10.6 ms, gone 3,871–3,900 ms after the last call.
     - 2 ephemeral requests against 45 durable ones per burst.
     - The durable control's typing was gone 4,004–4,283 ms after the last call.
3. **Adoption A/B probe:** base binary built from `git archive 0badac987` against the branch binary, in legacy and `ephTables=` modes. Results are in F1.
4. **Undo-order probe** (`probe-undo/`): delete, then insert the same unique key, then a `require` refusal. The row stayed intact and reachable through the unique index, with no duplicate after re-upsert. My hypothesis was wrong: index keys carry the row id, so undoing in key order is safe.
5. **Wire probe** (`probe-wire/`):
   - `$deadline` is absent from a mutation-returned row, a scan and a point read. `/schema` lists only the column definition, as it does for `through`.
   - The facts are right: `ephemeral`, `renewMs: 7500` and `ephemeralReads` are present, and `renews` is absent for a mutation that returns a value.
6. **Mutation test** (no poll notify from the publisher): the e2e passed 5/5; `ephemeral-watches` "mounting interest" passed on both tiers; `cargo test -p snapback4 --bin snapback4 ephemeral_tests` had 8 passed and 4 failed.
7. **Not run:**
   - The full `bash scripts/test.sh`. E3 reports it green at `d735389d6`.
   - Mutation tests of the core and lang guards; I read them only. The renewal-law test uses `update <- .principal = viewer` with no membership check, so the law is genuinely what refuses the write.
8. **Side effect:** checking whether the `clock advance` verb exists sent one POST to 127.0.0.1:4400. That port belongs to a node process (PID 1729), not a snapback4 dev server. It answered with non-JSON, so no Snapback clock moved.
