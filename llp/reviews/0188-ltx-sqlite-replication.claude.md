Review of LLP 0188 — Continuous SQLite replication via a vendored LTX replicator (super-refine round 1, capsule-r1)

External-fact verification performed: I fetched github.com/denoland/celld, the `crates/ltx` tree, and litestream.io. Confirmed: `crates/ltx` exists and is "celld's in-process SQLite-to-object-store replication engine"; seeded from rustyriver; replication behavior and test vectors ported from Litestream v0.5.11; format pinned to superfly/ltx v0.5.1; `differential_xtool` checks LTX read/write byte-for-byte against the real Litestream binary; Apache-2.0; README calls the runtime "still evolving". Litestream v0.5 uses LTX, takes over WAL checkpointing via a long-running read transaction, restores to any retained transaction boundary (at file/txid granularity), and compacts in tiered levels. The ~90 ms durable-write and ~20 s failover figures match LLP 0083's fetched record. The one celld claim I could NOT verify is whether the crate's object-store I/O is pluggable (see concern 5); reliance on the target's implicit assumption there is marked explicitly.

Concerns:

1. MATERIAL — correctness / coherence — §2 ("Integration point") and Open Question 2. The RFC scopes v1 to "the single per-instance data-plane DB" and frames auth as outside it, and OQ2 asks whether "the auth SQLite database (distinct from the keyring bytes)" should "join the replication set." Per the capsule's own context, no separate auth database exists: LLP 0057 places the `_auth_*` catalog and `_snapback_meta` marker inside the instance's one file-backed database (keyring is the `<db>.auth-keyring.json` sidecar), and `code/auth-backup.rs` confirms it — `create_backup` runs the online backup of `database.database_path()` into the single staged `database.sqlite3` image (`backup_auth_catalog_into`). Physical page-level replication cannot exclude tables, so replicating the data-plane DB necessarily replicates the auth catalog (session token digests, code digests, identities/addresses, agent-credential rows). The stated v1 scope is therefore not achievable as written, and OQ2 rests on a false premise. Fix: state that continuous replication of the instance database includes the auth catalog rows; recast OQ2 as the real question (keyring/catalog freshness pairing and what the replicated auth rows imply), or explicitly propose the architecture change that would make a separate auth DB true.

2. MATERIAL — safety / coherence — §5 ("Restore composes with LLP 0057"). Two defects. (a) "LTX restore composed with the latest LLP 0057 keyring/manifest artifacts" contradicts LLP 0057's boundary 4: the auth unit is valid only when database and keyring bytes were captured under one quiescence boundary. An arbitrary retained LTX position paired with "the latest" keyring is two different cuts: after rotation/pruning the keyring can lack a `key_id` that restored challenges reference (0057 restore explicitly checks this and fails closed), or a stale keyring can pair with fresher catalog rows. (b) §5 never binds 0057's declared-restore obligation (bulk session revocation, challenge purge, `--restored-from-backup` declaration) nor, on the hosted lane, 0072's restore-incarnation/identity-translation and session invalidation. A `snapback replicate restore`d database materializes live session rows at the restored position; "undeclared restore can resurrect backed-up sessions" is the residual 0057 pins for its own quiesced path, and this RFC would create a second restore surface that institutionalizes it. The "refuse to present data-plane-only restore as full instance restore" rule does not close either gap. Fix: require the replicate-restore output to be non-servable until the 0057 declared-restore composition (and 0072 translation on hosted targets) runs, and specify how a keyring consistent with the restored position is obtained or how the mismatch fails closed.

3. MATERIAL — safety — §2/§3 and the LLP 0072 composition claim. The RFC is silent on encryption of the LTX stream at rest. LLP 0072's backup posture — which the Summary and §3 claim the checkpoint artifact "composes with" and which LLP 0111 inherits — requires encrypted backup components with "encryption keys live outside the protected deployment; the profile declares who can decrypt and restore." celld's model (and the vendored crate's default) ships raw LTX segments to the operator bucket. A continuous plaintext copy of the entire database (including the auth catalog per concern 1) in an object store is a decided-by-default security posture regression relative to the verified-backup lane it claims to compose with. Fix: make the at-rest encryption/key-custody decision explicit per lane (provider-side bucket encryption sufficiency vs. client-side, and who can restore), or record the divergence from 0072's posture as a deliberate, reviewed exception.

4. MATERIAL — safety / feasibility — §4 ("Single-writer safety") with §5. (a) The v1 rule embeds "the LLP 0072 deployment identity" in the replication prefix, but 0072 identities exist only for registered hosted targets; the self-hosted/local operator lane — Motivation 1 and OQ5, the RFC's lead use case — has no deploymentId, so the fencing rule is unimplementable exactly where split-brain (two servers pointed at one prefix) is most likely. (b) Halt-on-observing-a-newer-generation is detection-lagged: during the async window a stale writer keeps appending segments under its own generation lineage, so the bucket can hold divergent lineages without any overwrite. §5's restore "at a chosen retained position" and §3's checkpoint consumers have no generation/lineage-selection or ambiguity-refusal rule, so a restore can silently select the stale lineage — split-brain materializes at restore time. OQ4 defers only the Fly-lane epoch question; the restore-side selection rule is deferred nowhere. Fix: define the fencing identity for non-0072 instances (e.g., databaseId/streamIncarnation or instance identity), and require restores and checkpoint proofs to bind an explicit generation lineage with refusal on multi-lineage ambiguity.

5. MATERIAL — correctness — Motivation 2 and §3 vs. LLP 0099. "An LTX stream whose replicated position is provably ≥ the admission's source position is exactly that artifact" overstates. 0099 requires the checkpoint be complete, content-addressed, integrity-checked, restored into isolation, and opened "at the exact source schema/durable version/replay floor," then exact-equality re-proved under the barrier. A ≥-position proof suffices only if (a) the exact captured source position is a retained, restorable LTX transaction boundary (Litestream restores at file/txid boundaries; compaction can erase intermediate boundaries), (b) a durable mapping from Snapback commit position P to LTX TXID exists, and (c) that boundary is pinned against compaction/retention for the life of the admission (and 0081's rollback-to-backup residual). OQ3 frames retention/compaction purely as cost and product surface; the 0099 binding makes boundary retention a correctness precondition. Fix: bind the checkpoint proof to an exact retained restorable boundary equal to the captured source position, pinned until the admission concludes, and move that constraint out of OQ3's cost framing.

6. MATERIAL — coherence — §1 vs. §2. §1 commits to a patch-clean vendored crate; §2 commits to routing object-store I/O "through the existing S3-compatible seam (`src/assets_s3.rs`) ... rather than a second S3 client." The upstream crate's own README says it writes LTX files to cloud storage — it contains object-store I/O. Unless upstream exposes a pluggable storage backend (which I could not verify, and the RFC does not establish), the two commitments conflict: routing through `assets_s3.rs` means patching the crate, and staying patch-clean means accepting the crate's embedded client. Fix: verify the crate's storage seam and condition one commitment on the finding (e.g., "patch-clean except a storage adapter" or "the vendored crate keeps its client; Snapback glue reuses `assets_s3.rs` for its own operations"). Note `assets_s3.rs` itself checks out as described (hand-rolled SigV4, MinIO-qualified 2026-08-03), so the citation is accurate; the conflict is between the RFC's own two rules.

7. [detail] — correctness — §"What this RFC deliberately does not take from celld": "LLP 0083 should gain a celld row beside Rivet" is already stale against the capsule — 0083 carries the celld addendum dated 2026-08-06, which itself cross-references LLP 0188. Reword to a pointer.

8. [detail] — coherence — Motivation 1 cites "LLP 0033/0083" but LLP 0033 (license posture) is absent from the Related list; add it or drop the citation.

9. [detail] — correctness — §6 attributes the "no capability manifest claims replication until an acceptance corpus passes" rule to LLP 0134. 0134 owns maturity introduction/promotion machinery (experimental-first records, promotion-to-stable gates); the claims-gated-on-acceptance honesty posture is the 0074/0109/0113-family rule that 0099 applies to itself. The gates G1–G3 are sound; the citation is loose, and a real capability id here will also owe a 0134 `MaturityIntroductionRecordV1`.

10. [detail] — correctness — §2 names the live data-plane database "`database.sqlite3`"; that constant is the 0057 backup's staged image name (`BACKUP_DATABASE_FILE` in `auth-backup.rs`), not necessarily the live basename. Cosmetic, but a spec-bound name should not be minted from the backup constant.

Decision quality. The document's core decisions are good ones, and its factual foundation is unusually solid: adopt a conformance-tested Rust LTX port rather than build replication from scratch; take only the replication lane and park celld's placement/lease/runtime machinery with 0083; invert celld's RPO=0 default into bounded-RPO async with a gated sync checkpoint (the right call for Snapback's local-first posture, with an honest "RPO ≤ observed lag" claim); fencing-not-placement for single-writer safety; and claim nothing until an acceptance ladder passes. The reading of 0099's unowned "streaming backup" gap is accurate, and every externally checkable celld/Litestream claim I tested verified against primary sources. The document's systematic blind spot is auth: it treats "the data-plane database" as separable from the auth catalog and keyring lifecycle that LLP 0057 binds to the same file, and concerns 1–3 are all projections of that one wrong premise into scope, restore safety, and at-rest posture. The second-order gap is that a durability lane inherits restore-side obligations from the governing corpus — declared restore, lineage selection, boundary retention, encryption custody — which the RFC leaves implicit, defers under a cost framing, or scopes to the wrong lane. These are fixable without disturbing the central adoption decision, but as written they are defective decisions and missing safety decisions, not implementation detail.

VERDICT: NOT READY

# LLP 0188 r2 — Delta-round formal review

External verification performed: I fetched github.com/denoland/celld and its `crates/ltx` tree. The repository exists (Apache-2.0, Rust), `crates/ltx` exists, and its README confirms the target's specific provenance claims verbatim in substance: seeded from a read-only snapshot of rustyriver, replication behavior pinned to Litestream v0.5.11, format pinned to superfly/ltx v0.5.1, and a `differential_xtool` differential test "byte-for-byte against the real Litestream binary." Motivation 3 and the celld prior-art claims are accurate as of this review. Claims about LLP 0033 and LLP 0022 could not be checked (those documents are not in the capsule); I rely on the target's characterization of them.

## Concerns

**1. MATERIAL — IN-DELTA — correctness — §2, §3, §6.**
The keyring lane is not integrated into the position/proof/pinning machinery with the rigor the database objects get. (a) §2/§6 claim "snapshot-on-change gives every position a governing keyring version," but no ordering invariant is stated between keyring-snapshot upload and shipment of the WAL frames whose `_auth_*` rows reference the new key: after a 0057 rotation (which publishes the keyring locally *before* computing any digest with the new key), the replicator can ship dependent frames while the keyring upload lags or fails, leaving a durable tail of positions with no governing keyring in the prefix. §6's fail-closed pairing then makes that tail unrestorable as a full instance, so the honest `async` claim "RPO ≤ observed lag" is silently false for full-instance recovery, and G2's "bounded loss ≤ observed lag" exit can pass or fail depending on an unstated race. (b) §3's checkpoint proof binds the content identities of "the immutable objects that materialize that boundary" and pins "the named boundary," but never names or pins the governing keyring snapshot — yet the proof is declared bindable into an LLP 0072 backup manifest and consumed by LLP 0081's rollback-to-backup residual, both of which require a full-instance-restorable artifact (0072 restore invalidates sessions but still restores the auth-bearing database; 0081 §6 restores "the exact pre-migration backup"). *Fix:* state the ordering/coverage invariant (e.g., a keyring snapshot must be durable in the prefix before any position that can reference its keys is treated as replicated/restorable, or define the restorable frontier as min(database position, keyring coverage) and make that the lag/RPO clock); and make the §3 proof name, digest-bind, and pin the governing keyring snapshot (or explicitly scope the proof to a database-only component and state how full-instance composition and its pinning happen).

**2. MATERIAL — IN-DELTA — coherence — §2, §6 vs LLP 0057.**
LLP 0057's security boundary #4 is normative: "A physical backup succeeds only when its SQLite snapshot and exact keyring bytes were captured under one quiescence boundary," and its backup section adds that a raw copy of database/WAL/keyring while the server runs "is explicitly not a Snapback backup." r2's whole-database decision plus keyring pairing deliberately constructs a second full-instance restore surface from a database/keyring pair that was *not* captured under one quiescence boundary (LTX boundary at position P paired with the "governing" snapshot taken at a different instant), and §6 presents the successfully paired result as a full instance restore — but the RFC never confronts 0057's invariant. The composition may in fact be sound (LTX restore is transactionally exact at a commit boundary, unlike a raw `cp`, and governing-version selection plus fail-closed `key_id` checking can substitute for quiescence *given* concern 1's ordering invariant), but that equivalence argument is nowhere made and 0057 as written forbids calling this pair a physical backup. *Fix:* either argue the consistency-equivalence explicitly and name the required LLP 0057 dated amendment recognizing the LTX-boundary + governing-keyring capture discipline as a second admissible one, or narrow §6's claims so the output is not presented as satisfying 0057's backup/restore contract.

**3. MATERIAL — IN-DELTA — safety/correctness — §4, §6.**
The fencing identity defeats itself under the very operations this RFC introduces. The stream incarnation is "minted when replication *first* attaches" and "recorded both inside the database and in the bucket" — so every backup, `snapback replicate restore` output, and LLP 0158 fork (SQLite backup API copy of the live parent) carries the source's incarnation inside its database. A restored (rewound) or forked copy that attaches is therefore indistinguishable from a legitimate crash-recovery resume: it reads the current head, wins its first CAS, and takes over the stream, halting the original (if still live) and silently making a rewound lineage authoritative — no "multiple live heads / divergent lineage" ambiguity ever arises, so the promised refusal never fires, and durable transactions between the restore point and the old head are orphaned without signal on the surviving lineage. §6's declared-restore composition rotates 0057's authorization-stream incarnation and, on hosted, 0072's identities — but nothing rotates the *replication* incarnation, and the self-hosted lane has no identity translation at all. Additionally, §4 never states when a new generation is minted (every attach? incarnation change? detected rewind?), which the "append only under its own generation prefix" containment story depends on. *Fix:* require the restore/fork composition (all lanes) to mint a fresh replication incarnation — or keep the attachment discriminator outside the replicated database, sidecar-style — and specify the attach protocol's resume-vs-new-generation decision: attach must verify that local database state is position-consistent with the head's lineage and must start a new generation (or refuse) on rewind/divergence rather than silently advancing.

**4. MATERIAL — IN-DELTA — safety — §5.**
The hosted custody rule's justification is incomplete as proposed. The stated reason LLP 0111 gives the application machine no provider credential is that backup custody must survive application compromise; the proposed write-only, prefix-scoped credential preserves that only if already-written replication history cannot be rewritten by the credential holder — but §2's "immutable keys" is asserted as a protocol convention, and nothing requires the store to *enforce* no-overwrite/no-delete against the replication credential. A compromised server process holding a plain write-scoped credential can re-PUT earlier segment keys (with internally consistent LTX checksums), retroactively falsifying the disaster-recovery history that is this lane's whole point — the exact property the supervisor-mediated byte path protected. Checkpoint proofs are digest-bound and survive this; the continuous `async` tail does not. *Fix:* the §5 rule must require store-enforced immutability of written objects under the app-held credential (deny overwrite and delete on the prefix — e.g., policy or object-lock — qualified per store in G2/G3 alongside the CAS primitive), or fall back to supervisor mediation where the store cannot enforce it; the LLP 0072/0111 review flag should present the rule in that enforceable form.

**5. [detail] — IN-DELTA — coherence — §4.**
"Stream incarnation" collides with LLP 0072's existing `streamIncarnation` (the application data/reset authority, which 0072's restore translation *does* rotate). The collision invites exactly the misreading concern 3 exposes — that §6's "LLP 0072 translation" already rotates the replication identity. Rename (e.g., "replication incarnation") or explicitly distinguish the two.

**6. [detail] — IN-DELTA — safety — §5, OQ2.**
OQ2 would be better-posed with the concrete consequence stated: the same prefix holds both the keyring's HMAC keys and the `_auth_verification_codes` keyed digests, so a self-hosted bucket compromise under provider-side-only encryption defeats 0057's keyed-digest protection for low-entropy codes (high-entropy session digests remain safe). This materially argues for client-side encryption of at least the keyring snapshot by default.

**7. [detail] — IN-DELTA — feasibility — §2.**
"Auto-checkpoint is disabled on every writer connection" is narrower than the following clause needs: SQLite also checkpoints/truncates from non-writer paths (last-connection-close truncation; the reader pool in `src/storage.rs` opens and retires connections). The governing sentence "all checkpoint/truncation paths are mediated by the replicator" is the right invariant; implementers must be pointed at the non-writer triggers. Implementation-phase.

## Decision quality of r2

r2 is a substantial, genuinely responsive revision rather than a patch job. The pivotal reversal — replicating the whole instance database because LTX physically cannot exclude the `_auth_*` catalog — is correct per LLP 0057, and r2 follows the consequence chain honestly into confidentiality (§5), auth-bearing restore (§6), and open questions (OQ2) instead of minimizing it. The §3 proof envelope now speaks LLP 0099's actual admission language (exact boundary, isolated restore, schema/durable version/replay floor, pinning through admission including the 0081 rollback residual), Motivation 2 no longer overclaims, the §5 credential divergence from 0111 is flagged for the owning documents' review rather than assumed, the honesty-rule attribution is fixed and 0134's introduction record correctly added, and §1/G1 gate adoption on provenance verification — which I was able to confirm externally is pointing at a real, accurately described upstream. The remaining defects are not regressions of judgment but the places where the new whole-database decision meets the auth machinery's two identity disciplines and were not carried to completion: the keyring sidecar lane lacks the ordering/binding rigor the database objects received (concerns 1–2), the fencing identity travels inside the very artifact restore and fork copy (concern 3), and the custody rule stops one sentence short of the enforcement that justifies it (concern 4). All four are fixable within the design's existing shape; none requires revisiting the reversal itself.

VERDICT: NOT READY

# LLP 0188 r3 — Delta-round formal review

**External facts checked (per instructions):** I verified against github.com/denoland/celld that the repository exists, is Apache-2.0, and contains `crates/ltx`; its README confirms the port from Litestream v0.5.11, the superfly/ltx v0.5.1 format pin, the rustyriver seeding, and the `differential_xtool` byte-for-byte differential test against the real Litestream binary. Two celld claims I could not confirm from the source: the "~90 ms durable-write cost" figure and the exact ack-after-bucket-write semantics (the README claims "zero RPO" but publishes no latency number) — reliance on the target's description is noted, and nothing in the design depends on the exact number. One verification finding feeds concern 7 below: upstream `differential_xtool` **self-skips when the Litestream binary is unavailable**.

## Concerns

1. **MATERIAL — IN-DELTA — correctness — §4 (resume clause).** Resume is "permitted only when the local sidecar carries the head's incarnation *and* the local durable database position is position-consistent with the head's lineage (equal position, checksum continuity verified)." In the default `async` mode the ordinary crash-or-restart state is a local database *ahead* of the head's recorded position by the unshipped WAL tail (commits ack locally; the head can only trail). Under the equality test that state fails resume, and the "anything else" bullet then mandates refusal until explicit operator/supervisor instruction mints a new incarnation and generation — i.e., every unclean restart (and any restart racing head-advancement lag) requires manual intervention and burns a succession, which defeats the operational premise of the lane. The two bullets also fail to partition the state space: ahead-but-checksum-continuous is neither "rewound" nor "divergent," yet cannot satisfy "equal position." A fix must (a) admit resume when the head lineage is a verified checksum-continuous *prefix* of the local durable state (local ≥ head position), reserving refusal/succession for genuine rewind, divergence, or sidecar mismatch; and (b) say which positions are compared (sidecar-recorded shipped position vs. database commit position vs. head position) and tolerate the crash windows between segment ship, sidecar update, and head advance, since exact three-way agreement at attach time is not achievable.

2. **MATERIAL — PRE-EXISTING (unchanged §5 first paragraph; sharpened by in-delta OQ2) — safety / decision quality — §5 + OQ2.** §5 still permits the self-hosted lane to accept provider-side-only bucket encryption as a "recorded weaker posture," while the in-delta OQ2 text itself demonstrates that this configuration defeats LLP 0057's boundary 2: the same prefix then holds the keyring's HMAC key material (snapshots) and the `_auth_verification_codes` keyed digests (segments), so one bucket-credential compromise enables offline recovery of live low-entropy codes — the exact attack the keyed digest exists to prevent, with no compensating control. The document now both proposes the allowance and proves it unsound, and defers the resolution to an open question while the §6 acceptance dependency (the 0057 amendment) does not cover this exposure. A fix must either decide OQ2 — at minimum, client-side encryption of keyring snapshots mandatory on every lane, or an equivalent rule barring co-location of plaintext-to-provider key material with the digests it protects — or make the disposition an explicit acceptance dependency alongside the 0057 amendment rather than an allowed default.

3. **[detail] — IN-DELTA — coherence — §2/§6.** "Keyring coverage" (a position quantity) and "the keyring snapshot governing that position" require a durable position→snapshot association, but content-addressed digest names carry no ordering; the document does not say where the mapping lives (head record, per-generation index, checkpoint proof only). The frontier decision itself is sound; the association mechanism is implementation-contract work that should be named there.

4. **[detail] — IN-DELTA — coherence — §4/OQ4 vs §5.** OQ4 says epoch representation is "owned by the LLP 0072 amendment §5 already requires," but §5 only calls the custody divergence out "for LLP 0072/0111 review" — no 0072 amendment is actually required anywhere, and the only acceptance-dependency amendment named is 0057's (§6). Align the two: either make the 0072 amendment an explicit dependency or soften OQ4's reference.

5. **[detail] — IN-DELTA — completeness/feasibility — §5.** The custody split assigns append (application) and head/proofs (supervisor) but never places LTX **compaction and retention deletion**, which require the overwrite/delete rights the immutability policy denies; presumably supervisor custody on hosted and a separate lifecycle credential on self-hosted, but this is unstated — as is the head object's necessary exemption from the immutability rule (it must remain CAS-overwritable while generation prefixes are immutable). No defective decision; the roles need naming.

6. **[detail] — IN-DELTA — correctness — §4 (succession record).** "Binds its exact predecessor (incarnation, generation, position)" does not say whether the bound position is the predecessor's last head position or the successor's divergence/fork point. After a restore-to-earlier-P succession the two differ, and the read-time refusal rule ("succession record conflicts with observed prefixes") needs the divergence point to be meaningful.

7. **[detail] — PRE-EXISTING — feasibility — §7 G1.** Upstream's `differential_xtool` self-skips when the reference Litestream binary is absent (verified against the celld repo). G1's "reproduction of the conformance results in our CI" should explicitly require the binary present so the differential leg runs rather than silently self-skipping green.

8. **[detail] — PRE-EXISTING — feasibility — §2/§3.** Replicator-owned checkpoint mediation plus a stalled bucket means unbounded local WAL growth; the stall language covers the RPO bound surfacing (doctor/status) but not the local disk-growth policy. Implementation-contract material.

## Decision quality of r3

r3 is a substantively strong revision. The restorable-frontier construction is the right shape: it converts the keyring-coverage problem from a procedural promise into a measured invariant that drives the RPO claim, the `async` metric, and G2's exit, and the ordering invariant correctly leans on LLP 0057's publish-before-first-digest rule (which I verified in 0057's keyring protocol; the prune-precondition direction also holds, backstopped by the fail-closed `key_id` check). The replication-incarnation rename and sidecar placement cleanly resolve the collision with LLP 0072's `streamIncarnation` and make "backups/forks never impersonate resume" true by construction, consistent with 0057's backup member set and 0158's fork materialization. The custody role split is a real security argument — it identifies store-enforced immutability as exactly the property 0111's supervisor-mediated path protected, and falls back honestly where a store cannot enforce it. The 0057 boundary-4 treatment is the correct posture: consistency-equivalence argued on the merits, with the claim explicitly withheld until a dated 0057 amendment lands. The two MATERIAL findings are, however, real: the new resume clause as written breaks the lane's default operating mode (a specification bug in freshly added text), and the self-hosted encryption default remains a configuration the document itself now proves defeats an Accepted spec's security boundary, with the decision still parked in an open question.

VERDICT: NOT READY
