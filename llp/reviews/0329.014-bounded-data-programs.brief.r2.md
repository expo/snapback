## State of play after round 1 (orchestrator's reading — check it)

All four proposals share: row rules in the language as the only authorization;
derived read/write sets, retention, indexes, prediction — never authored; named
operations as the sync unit; effects as a different kind; a static certificate
(shape + examined-entry bound) at `check` **and** a dynamic trace (ranges incl.
absences, rows, stop-reason) per execution; the eight runtime states; JS out of
the authoritative query/mutation path; a small closure cache + interpreter +
outbox as the client.

**The one genuine disagreement is the computational class of the query body
between bounded reads.** grok and Fable: an algebra — builder callbacks construct
an AST at build time; row-level branching only as relational `case`/`when`;
iteration only as `nest`/`map`/`forEach` over a `Page<N>`. codex and the
orchestrator: bounded structured programs — real `if` on row values, `for` over
`Page<N>` (cost N×B), pure computation (Map/Set accumulators, string ops, helper
functions) between typed reads, lowered from TypeScript *syntax* to bytecode.
grok's objection: sealed-trace JS "becomes Zero the first time an agent writes a
data-dependent `for`". codex/orchestrator's reply: a `for` over an `Unbound` is a
type error in both designs; pure computation cannot change the read shape or the
bound because every read goes through the typed API; what it changes is a VM
step budget and the value model.

So the question for this round, precisely: **is admitting arbitrary pure
computation and structured control flow between bounded typed reads a threat to
any guarantee (shape, bound, closure, noninterference, prediction closure,
Postgres lowering, IVM), or only to the builder spelling?** If only spelling, the
recommended language is TS-syntax bounded data programs lowered to IR with the
algebraic operators as library; if a guarantee is threatened, name it and the
program that breaks it.

Secondary: grok says opaque verdicts are "leases under another name" and Clique
must not need them; Fable and codex use them for rules over hidden inputs. Are
they needed at all in v1, and if so what binds them?

## Specific points the orchestrator wants adjudicated (address inside the headings above)

Round 1 produced more convergence than expected — at least two panelists and
the orchestrator landed on "static shape+bound certificate at `check`, dynamic
trace as the closure, bounded structured control flow admitted (`if` on rows;
`for` only over `Page<N>`)". Convergence can be shared priors. So attack the
*details* where the answers differ:

1. **Prediction closure** (Fable): derive, per `(view, transition)` pair, the
   dependent reads a *not-yet-existing* row would trigger (e.g. `users[viewer]`
   after `send`) by symbolic substitution, and hydrate them at subscribe time. Is
   this derivable over bounded imperative programs (P9/codex) or only over an
   algebra? Where does it fail?
2. **Halo rows** (codex): a uniform compiler-selected halo (rows M+1, M+2) so one
   local delete of a top-M page stays complete. Worth it? What does it cost in
   trace size and invalidation fan-in?
3. **Witness binding** (codex): opaque verdicts bound to
   `{ruleHash, ruleSite, planHash, viewer, args, epoch, notAfter}`; read-witness
   ≠ write-authorization. Is a separate write witness needed for the common
   membership rule, or is the compiler-proven equivalence enough?
4. **Offline expiry fence** (codex) vs **"stale until reconnect"** (grok's sketch,
   Fable): is an engine-owned deployment-wide `maxOfflineAge` a requirement for
   the protected-retention posture, or a policy knob with a sane default?
5. **Rule affordability**: one-hop membership rules hoist to cost 1 when the
   predicate is pinned by an equality filter. The two-hop co-member rule
   (`users.read = shares a conversation with viewer`) does not. What does the
   diagnostic paste so an agent does not make profiles `public`? Does this need
   a `Maintained` closure, a schema split (public profile / private account), or
   a fan-out-capped rule?
6. **The unread count** (Fable's predicted Clique loss): per-conversation unread
   for an inbox of N conversations. Show the paved code and its bound in your
   design, and the diagnostic that gets an agent there from `count()` on an
   unbounded range.
7. **`AllOrRefuse<T,N>`** (codex, = LLP 0120 variant 2) alongside `Page<T,N>`:
   is exact-or-sealed-refusal a type agents will use correctly, or an
   availability trap as data grows?
8. **One interpreter compiled twice** (orchestrator): Rust interpreter, native on
   the server, WASM on the client. Versus a TypeScript evaluator on the client
   (Fable) or "two conformant interpreters" (codex). Which, and why — size, JS
   engine parity on Hermes/JSC/V8, semantic corners.
9. **Certificate contents**: cardinality alone is not a cost proof (codex).
   Agree on the minimal certificate fields.
