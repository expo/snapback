1. **A non-tautological lifecycle guard does not necessarily answer either lifecycle question.**  
   [lifecycle_guard](/home/ccheever/projects/sb4-b31-secp/snapback4/crates/snapback4-lang/src/bind/security/creation_advice/lifecycle.rs:31) accepts any guard excluding one domain value. Consequently, `require row.approved = true` suppresses `N_EDIT_AFTER_APPROVAL` precisely when editing approved evidence. Likewise, `status != 'cancelled'` permits approved edits. For consumption advice, that same status guard suppresses the question around `require row.paid; update … {status:'done'}`, although another call remains admitted in `done`.

   Section 3 needs distinct criteria: edit suppression must establish the relevant preapproval restriction; a source-stage restriction must prevent repeating the governed transition. Merely excluding some state establishes neither. The parent’s §17.5 explicitly preserves the cancelled-state counterexample.

2. **Helper expansion can erase an effect and manufacture a stale read witness.**  
   [narrow](/home/ccheever/projects/sb4-b31-secp/snapback4/crates/snapback4-lang/src/bind/program/control.rs:473) checks the expanded expression’s safety, while [returned](/home/ccheever/projects/sb4-b31-secp/snapback4/crates/snapback4-lang/src/bind/security/authority_walk.rs:258) can discard unused arguments. Consider a helper `keep(ok, unused)` returning `ok`:

   ```quarry
   require keep(exists roles[principal = viewer, role = 'admin'], revokeMyRole()) else NO
   ```

   The first argument captures a positive witness; the second revokes it. Expansion retains only the existence expression, which is then recorded as current advisory authority. A subsequent admin-only lookup can lose its legitimate question. Preserve evaluation order and effects from the complete original call; unsupported cases must remain opaque.

3. **Any write to a guard’s column is treated as consumption, regardless of resource, path or assigned value.**  
   The [consumption check](/home/ccheever/projects/sb4-b31-secp/snapback4/crates/snapback4-lang/src/bind/security/creation_advice/lifecycle.rs:410) searches the whole mutation for the same table and column. After checking `receipts[r].paid`, a conditional write to `receipts[other].paid` suppresses the question even when that branch is skipped. Assigning `paid: true` also qualifies, although it preserves the reusable authorization.

   Consumption must concern the exact checked resource and invalidate the prerequisite on every relevant successful path. Otherwise retain the question at the unproved write site.

4. **Operator suppression checks declared row rules rather than effective write admission.**  
   [Operator classification](/home/ccheever/projects/sb4-b31-secp/snapback4/crates/snapback4-lang/src/bind/security/lints.rs:140) combines insert/update rules, including both upsert arms, but omits the owner-field bypass. A reader-grant column declared `written by .owner readable by audience` can be patched by its ordinary owner despite an unnamed operator-only update rule. An upsert supplying only that column can therefore grant a recipient on its existing-row arm while being classified operator-only.

   Section 4’s “effective write admission” requirement must include that bypass. The runtime explicitly implements it in [authorize_update_fields](/home/ccheever/projects/sb4-b31-secp/snapback4/crates/snapback4-core/src/engine/field_authority.rs:108).

5. **Inspecting a linked timestamp is mistaken for defining the written window.**  
   [Dependent-window pairing](/home/ccheever/projects/sb4-b31-secp/snapback4/crates/snapback4-lang/src/bind/security/creation_advice/lifecycle.rs:435) accepts any matching Time member anywhere in a dominating condition. For example:

   ```quarry
   require proposed > now else PAST
   require parent.approvedAt != null else NOT_APPROVED
   ```

   Writing `proposed` into a linked child deadline now suppresses `N_DEPENDENT_WINDOW`, although nothing bounds it against `approvedAt` or the parent’s stored deadline. Require an actual window relationship involving the written value; timestamp presence alone cannot answer the question.

6. **Dependent-window matching confuses a secondary reference key with row identity.**  
   The same pairing compares only the single supplied key value. Suppose `parents.predecessor` is a unique reference to `parents`. Reading `parents[predecessor = parent]` and bounding a deadline against that row’s timestamp suppresses the question for a child storing `{parent}`. The selected row is the successor of `parent`, not `parent`.

   Match the selected index/key meaning as well as its value. Normalize to row identity only for a proved primary selection; preserve secondary keys and reference hops.

7. **Negating an approximate deadline mask incorrectly suppresses real overlap, including equality.**  
   [time_mask](/home/ccheever/projects/sb4-b31-secp/snapback4/crates/snapback4-lang/src/bind/sweep_deadline.rs:133) treats an unknown conjunct as unrestricted, then complements the resulting mask under `not`. With a sweep using `createdAt <= periodEnd - 14d`, consider:

   ```quarry
   require not (row.createdAt <= now - 14d and flag) else CLOSED
   ```

   When `flag` is false, the mutation admits the due window—including equality. The analyzer instead derives a strict opposite window and suppresses the question. Complementing an overapproximation is unsound. Preserve conservative possibilities under negation, or leave this shape unsupported.
