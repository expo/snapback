# Panel review: LLP 3000.009 (revision at `187d98b1f`)

## Verdict: SOUND WITH MAJOR ISSUES

## Direction assessment

The revision's direction is right and better than the first draft (`2dedc63fc`), which proposed lowering Quarry fragments to backend-specific SQL plans with per-fragment qualification. The experiment record supports the change: the cost is a row-at-a-time loop over the `Rows` boundary (68 calls for the 32-room inbox, 5 for a 20-row page), not the storage format, and the hand-written join at 0.082 ms is a planning lower bound that omits rules, meter and completeness (`snapback4/experiments/postgres/README.md:10-15,93-109`). Reimplementing rules, expressions, null/collation/overflow behavior, completeness, cursors and meter charges in two SQL dialects to chase that bound would create a second executor of exactly the semantics Snapback wins on. The current interpreter charges all of that in program order today — `exists` charges `RuleProbes` before probing (`snapback4-core/src/engine/read.rs:46-51`), point reads use mark/restore so hidden and absent cost one examined row (`read.rs:300-323`), scans charge per candidate and per index entry (`read.rs:409-422,574`), and query completeness folds in `capped_at`, non-uniformity and lost pages (`snapback4-core/src/engine/postgres/mod.rs:114-119`; same shape in `snapback4-core/src/engine/mod.rs:659`). Keeping one Rust executor and pushing down only access (batches of seeks, scans, counts, point reads, rule probes, write flights) through `Rows` (`snapback4-core/src/rows.rs:130-161`) plus `PartitionRows` (`snapback4-core/src/partition/storage.rs:14-31`) is the correct division, and the generic row/index layout on both stores with typed tables only as projections correctly defers per-successor DDL and per-index dialect questions to where an application asks for them. The Convex design point (§2.4) is valid as an existence proof for one engine plus shared tables plus one committer, not as a performance claim, and the application-led sequence (online-only brief with Convex/Supabase controls first, Postgres as a parallel measured lane) is the right way to earn "chosen over convex and supabase."

None of that survives contact with implementation unless the issues below are fixed. The most dangerous ones are all places where the RFC replaces a known hard problem with a sentence: channel authorization (§6.2), prefetch equivalence (§4.2), commit ordering (§4.4), and synchronous projections with expiry/liveness (§6).

## Major issues

### 1. §6.2 "declared channel" authorization is unsound as specified — blocking

**Section:** RFC §6.2, second authorization form (lines 444-448: "The compiler cannot prove that the SQL stays within what the prelude guarded; the declaration names that responsibility for review").

**Evidence:** Today every read is judged row-by-row in the interpreter: `check_rule` evaluates the read rule per row (`read.rs:244-266`), scans hoist only prefix-decided rules and otherwise mark `non_uniform` (`read.rs:545-566`), and hidden/absent are deliberately one word (`read.rs:279-324`). There is no SQL application path: `sql` is read-only inspection of the developer's own store, "never an application surface" (`snapback4/NOT-DOING.md:27`), and the Postgres evaluation DDL has no row-level policy object at all — seven plain tables (`snapback4-core/src/engine/postgres/store.rs:18-28`). Per-operation grants are table-level by nature; they cannot enforce that a query reading `orders_facts` filtered by `:org` does not return other orgs' rows once the `require exists memberships[org, viewer,'admin']` prelude passes for one org. A handler authoring `SELECT … FROM orders_facts GROUP BY month` and forgetting `WHERE org = :org`, or joining a second projection, passes the prelude and the grant and leaks across tenants. This is exactly the "second translation of authorization" cost LLP 3000.007 §9.1 recorded (`llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:1037-1053`), now relabelled as a review responsibility with no gate, no mandatory reviewer, and no test named for it.

**Resolve:** Restrict increment D to the candidates form (ids returned, engine re-reads under the table's read rule in one prefetched batch) until a row-level enforcement or constrained-SQL proof exists. If channels survive, require: SQL text confined to a checkable subset (declared filters must syntactically bind every parameter the prelude guards); `check` rejects unbound parameters; and §11.4 gains an explicit cross-org/cross-principal leak test through channels, expiry views and errors, with stale-lease and post-revocation collection. UNVERIFIED: the exact Postgres grant/role-switching mechanism — no code exists yet, so the claim "the store enforces the declaration" has no implementation to cite.

### 2. §4.2 "unchanged by construction" overclaims; prefetch as specified can move meter, cursor and refusal boundaries — blocking

**Section:** RFC §4.2 lines 215-221.

**Evidence:** Meter observations are part of the outcome (`metered: runner.meter.used` in `engine/postgres/mod.rs:114-128` and `engine/mod.rs:129-165`), and completeness depends on `capped_at`, `word_cut_at`, `non_uniform` and page ownership (`engine/mod.rs:659`). Charging is interleaved with store calls and visibility: `get` restores the meter mark and re-charges one examined row for hidden rows (`read.rs:300-323`); scans charge per fetched candidate before the rule verdict (`read.rs:574`), attribute the cut site via `meter.at(&scan.site)` (`read.rs:536`) and mint cursors from the last *returned* row or last rule-visible key with cut-sensitive continuation logic (`read.rs:652-664`); filters add probe charges (`read.rs:289`); expiring tables add extra scans (`read.rs:146-163`) and live-aggregate rescans (`read.rs:177-210`). Prefetching "the key set for each marked read" after the page fetch but before per-row evaluation executes physical reads for rows whose visibility is not yet decided, for filters not yet evaluated, and for aggregates not yet reached. Those physical reads cannot be "rolled back" the way `meter.restore(mark)` rolls back probe charges, and their site attribution and timing change which `capped_at` site fires first. The "pure functions of the row" marking criterion also silently excludes the interesting cases: filter-embedded reads, word-lane reads (`scan_words`, `read.rs:346-399`), and chained reads whose keys come from an earlier read in the same row (admitted as "one level at a time" without a termination or blowup bound).

**Resolve:** Narrow §4.2 to a cache contract with no semantic side effects: prefetch populates a transaction-scoped key→row snapshot cache; hits return exactly what the uncached call would return at the same snapshot; misses fall through; prefetch performs no authorization, charges nothing, attributes nothing, and never suppresses or invents a store error (a prefetch failure must be invisible, not "an infrastructure failure of the operation"). Specify cut equivalence operationally and qualify it differentially with prefetch on/off **on Postgres**, including meter-site, `capped_at`, cursor, refusal and `next_expiry` equality — SQLite-off differential (§4.2: "SQLite and the device … may keep it off") cannot qualify the Postgres path. Forbid prefetching rule-probe inputs for rows whose visibility is undecided until hidden-indistinguishability (including timing) is shown, or prove the batch shape leaks nothing beyond today's `take+1`/`max(32)` fetch (`read.rs:571`).

### 3. §4.4 dismisses the commit-order scaling question with a non sequitur and no target — major (blocking for the managed-service goal)

**Section:** RFC §4.4 lines 254-260, especially "Per-scope logs are not proposed, because a commit must remain whole across scopes."

**Evidence:** Whole-commit atomicity and per-scope publication are compatible: the implementation already records one commit plus per-partition log rows through the shared `PartitionRows` interface (`partition/storage.rs:14-31`; Postgres `read_log_spans`/`group_at` in `engine/postgres/log.rs:64-93`). The experiment explicitly lists the single head as a limiter "including writers touching disjoint rows" (`experiments/postgres/README.md:10-15`), serializes on `SELECT … FOR UPDATE` (`engine/postgres/store.rs:61-64`) plus a conditional head advance (`store.rs:133-148`), and measures ~2.5k ops/s serialized Postgres vs 14-15k SQLite in the long run, with-halved numbers and different contention sensitivity in the short run (`README.md:111-125`, with non-identical durability settings). The RFC's own revisit trigger — "if one commit order limits a named workload" (§11) — can never fire from the brief, which is one ordinary application, while ruling 5 already admits a multi-tenant managed service whose many applications would share the Postgres store and its head row. Increment C's evidence clause ("commit rate against a target the author states", §10.2) names a target that does not exist.

**Resolve:** Before C finishes: the author states a commit-rate target including a shared-store multi-tenant shape; C measures serialized vs serializable against it with the brief's write mix plus a disjoint-writer mix; and §4.4 is reworded to keep ordered-publication/per-scope options open with an explicit trigger that is not the single-app brief. At minimum, C's isolated-restore evidence must include the §9 incarnation rule (new incarnation, fenced resumes, quarantined work) or the managed-service child inherits an unfenced store.

### 4. Projections: synchronous-everywhere maintenance, expiry-view clock skew, and one-shot embeddings — major

**Section:** RFC §6.1 lines 399-410, §6.2 expiry/liveness lines 449-459, §9 backfill line 555-556.

**Evidence:** "The engine writes it inside every managed commit that changes the source … A projection write that fails aborts the commit" means every managed write pays every projection's native-index cost (GIST, and later vector) synchronously, with no conditional-on-projected-columns-changed rule and no deferred option; backfill is a job, but steady-state is not. Expiry "through a view the engine regenerates at activation" cannot match interpreter semantics: expiry is per-run clock (`expired()` uses `context.now`, `read.rs:216-218`; `now` is set per operation, `engine/postgres/mod.rs:101-112`), so a view fixed at activation goes stale as time passes and a view using the database clock diverges from test/controlled clocks and breaks "one meaning on every host" (§11.1). Liveness ("live at table granularity … Any other SQL read is one-shot", §6.2) combined with "a database write followed by a mutation is two transactions" (§6.3) makes the flagship §6.3 embedding flow (model provider → pgvector table → candidate SQL read) one-shot by construction, since it touches a database-owned table — a real cost, undisclosed in §6.3. The touched-table mapping needed for invalidation is also unspecified: the runner tracks managed `read_tables`/`written_tables` (`engine/mod.rs:794-802`), the online client re-runs on table overlap (`packages/snapback4/src/client.ts:362-365`), but nothing maps a projection write back to its source table for notification, and cross-process notification is itself deferred to increment E (§7.1).

**Resolve:** Add conditional maintenance (skip when projected columns unchanged) or a declared staleness contract with an async option before D builds indexes everyone pays for; parameterize expiry filtering by the operation's clock rather than activation time, with a differential test against Quarry expiry reads including `live_aggregate` (`read.rs:177-210`); define SQL-read cursors and the projection→source invalidation mapping, including the one-shot consequence for database-owned tables, and disclose it in the vector/geo examples.

### 5. Increment A bakes single-tenant supervision, unscoped secrets, and an undefined route-settlement contract — major

**Section:** RFC §5.1-§5.3, §9.

**Evidence:** Today's action path is durable admission private to principal+operation with replay (`snapback4/src/actions.rs:50-66`; `engine/actions.rs:94-122` for request/claim structures), worker claim over a service token with a fenced lease (`guide/actions.rs:51-58`), and request-principal sessions that expire with the lease (`guide/actions.rs:31-39`). The RFC adds declared results, `ctx.query`/`ctx.mutate` under invocation authority, routes verified over raw bytes, `ctx.writeIdFor(event.id)` determinism, whole-secret-map `ctx.secrets`, streaming handlers, and "trusted application code … never a sandbox" isolated from the core with "no credential for managed tables" (§367-374). Three gaps: (a) `writeIdFor` has no implementation to cite (grep for `writeIdFor`/`write_id`/`deterministic` in core/engine finds only an unrelated seed comment — UNVERIFIED whether the primitive exists, its scope, or its behavior after the dedup window); refusal-before-commit vs acknowledge-only-after-admission for the billing route is therefore unspecified. (b) There is no per-route secret scope, rotation, or redaction rule, while §9 simultaneously promises a correlated request→commit→attempt→delivery path "without protected row contents by default" without assigning that path to any increment. (c) "The core holds the only write role; the runtime holds none" (§6.4) is unenforceable if `serve` hosts both in one process or one container; the hosted-pool escape ("may implement the same claim protocol later", §5.3) only works if A uses the claim protocol exclusively with no local shortcuts.

**Resolve:** Scope A explicitly: per-route secret references with least privilege; a route settlement contract (what 200 means on mutation refusal, replay, and disconnect mid-stream); claim-protocol-only coupling between core and workers (no in-process bypass) so the managed-service child can substitute a pool; deterministic id mapping with documented retention/dedup windows where "an expired id is never silently accepted again" is testable (§5.2, §11.5, §11.7); and put the §9 correlated path (with redaction) in A, since A owns requests, commits and attempts.

### 6. The sequence starts A and C correctly but leaves D ungated and C unfenced — major

**Section:** RFC §10-§11, §14 rulings 4 and 6.

**Evidence:** A-before-brief-evidence is actually fine: A's scope (declared results, context, routes/webhooks, scheduled actions, supervision, one work lifecycle) is what the brief's invitation and webhook journeys need "through crash, retry, duplicate delivery and revocation" (§10.2). The problems are boundaries: C "from now" is unfenced (it must exclude SQL reads, projections, extensions, pooling/async execution and multi-process support — all currently listed as not implemented in `experiments/postgres/README.md:153-162`, but not restated as C non-goals); D's "SQLite half can follow A once SQL reads are ruled on" splits a feature whose value is the conjunction (projections without admitted readers are write amplification with no query path — §6.1 vs §6.2); the long-key decision (§4.3: bound-every-indexed-text vs Convex-style prefix/suffix/hash, with the B-tree counterexample at `README.md:147-151` and the `54000` failure mode) must land in C before D indexes anything; and §11.1/§11.2/§11.5 as written permit vacuous passes (SQLite-off differential; access contract without explicit long-key/null/word-entry cases; provider-crash tests without a labelled double plus a real-provider path).

**Resolve:** Fence C to Rows-batching + head discipline + `serve`/`deploy`/backup on Postgres; decide the long-key representation in C with the counterexample test retained; gate all of D (not half) on the SQL-reads ruling with brief evidence; schedule that ruling before D is commissioned; and tighten §11 to require Postgres on/off differential, long-key/null/word cases, and labelled-double plus real-provider paths. One scoping note: scheduled actions in A are not obviously needed by the stated brief (§10.1 lists no schedule); confirm or defer to B.
