### 2. Schema in v0

Viewer is a principal id (staff user, install, customer, or `system`). Enums are `text({max})` checked in rules. v0 has no `set`/`optional`/`enum`/`cents`; sets are child tables; open intervals use `to=0`. **App-owned host fields are not columns on host tables** (v1.1 `E_SECRECY_MIX` refutes mixed-audience rows). They are `fieldValues` rows. PII is a second table. v1.1 marks: `optional`, `cap({where})`, `appendOnly({except})`, `rateLimit`, `any`, `partitioned`, `serialBy`, `int({sequence})`, `immutableExcept`, `retain`, `audited`.

**§9 diagnostic.** `E_OPAQUE` — `json` predicates and `sandbox(JS)` are outside the subset; rewrite: typed AST rows / certified `planHash`, never `eval`. `E_UNBOUND_SCAN` — `take: 10_000`; rewrite: `cap` 100 and `All`. `E_AMBIENT_TIME` — `Date.now`; rewrite: `ctx.now` / schedule. `E_STRUCTURAL_COUNT` if the writer is told how many rules ran. Hidden: **no rewrite in v0** for “run whichever programs this merchant installed.” `db.run(namedMutation)` (v1.1) names the callee at `check`. The callee here is a row.

**Premise.** *Rules the server can evaluate as one author-time artifact; the static certificate as the gate; JS never in the authoritative path; deterministic programs over traced bounded reads.*

**Broken.** `placeOrder` for Northwind and for a second merchant are different admitted programs: different `ruleHashes`, different plugin certificates, different maxExamined. The certificate of a *named* operation is the wrong instrument — admission is of `(plan, installGeneration)`. Nested gate `E_STEPS` today aborts the host transaction; the product needs per-plugin catchable fuel mapping to `unknown` then `open_flag`/`closed`. A required JS gate is a second evaluator inside SQLite.

**Honest outcome: new kind + new dimension, not “no language change.”** Kind = `plugin` (marketplace-`check`ed IR, stored by `planHash`, invoked as `db.runInstalled(hash, args)` with an isolated catchable ceiling). Dimension = **rule ownership and composition** (engine ruleset: N owned predicates per effect, deny-wins, trigger mask, bound on every write like `exclusion`). Certificate = host envelope ⊕ Σ installed plugins under the caps, keyed by `installGeneration`. Smallest addition that would make O2 a plan: those two, plus three-valued `unknown`, plus `independentOf` on writer-visible refusal codes (v1.1 taint).

**Not this system** only if the product insists on in-commit Turing-complete JS with wall-clock 5 ms. Shopify-Functions-as-IR is this system with a plugin kind.

Host verbs (`placeOrder`, `payOrder`, …) are the same envelope. They are not separately admissible.

#### O3 staff-initiated action — premise-violation (principal)

v0 `ctx.viewer` is one id. Intersection “install grant ∧ staff permission ∧ every inner write re-checks” is not a table rule. First attempt: run the plugin as the install (`viewer = installId`) because the button lives in ShipNimbus — T6, the junior refunds.

**Premise.** One principal per execution; rules closed over `viewer`.

**Broken.** A second authority axis (initiator) that rules must see. `principal.bearerOf` (v1.1) is the install token, not the clicking staffer.

**Honest outcome: new dimension** (principal combinators: `actor` × `initiator`; rules may mention both; absence of initiator requires `autonomous:` grant). Smallest addition: `ctx.initiator: Principal | null` as a modeled input, and table rules of the form `grant(actor, scope) && (initiator==null ? autonomous(scope) : perm(initiator, code))`. Until then O3 is not a plan; `require` in one wrapper is a cheat (another mutation bypasses it).

```ts
  { productId: id(products), qty: int(), orderId: id(), ttlMs: int() },
  { max: { ttlMs: 30 * 60 * 1000 } },
  ({ db, ctx, args }) => {
    db.require(db.exists(scopeGrants.byInstallScopeLive, [viewer, 'write:reservations']), 'AUTHZ_REFUSED')
    const p = db.get(products, args.productId)
    db.require(p !== null, 'NOT_FOUND')
    const held = db.get(reservedQtySum, args.productId) // MaintainedRow
    db.require(held !== null, 'COUNTER')
    const available = p.onHand - held.value
    db.require(args.qty <= available, 'INSUFFICIENT') // discloses the counter; grant is the readable
    const id_ = ctx.newId()
    db.insert(reservations, {
      id: id_, merchantId: p.merchantId, productId: args.productId, qty: args.qty,
      ownerInstallId: viewer, orderId: args.orderId, state: 'held',
      expiresAt: ctx.now() + args.ttlMs, createdAt: ctx.now(),

    // reservedQtySum maintained same-commit; products.reservedQty mirrored by system continuation

```

Certificate: `examined ≤ 4` (product, grant, aggregate, unique), `W≤2`, prefixes `arg|viewer`, `serialBy(productId)`, prediction `conditional(sum-cap, unique)`. Constraint that binds every writer: v1.1 `cap({ sum: qty, maxFrom: product.onHand })` on `held` rows — program `require` alone is not K6.

`sweepExpiredReservations`: `schedule` every 30s, scan `byExpires` `take: 100`, flip `held→expired` under system, maintenance decrements the sum. Never early (compare `expiresAt` to `commitTime` in the mutation, not in a rule).

#### O6–O7, O11–O12, O14

`revokeScope` first attempt: scan all rules, programs, subscriptions for the scope with no `take` → `E_UNBOUND_SCAN`. Rewrite: `ruleScopes.byScope` under cap 100; one transaction closes grant interval (`state='revoked'`), appends rule versions with `dark_choice`, disables programs. Re-grant is the inverse. Prediction `n/a`.

`overrideRefusal`: insert `overrides(status=live)`, caller resubmits the write. `schedule` flips `live→expired` at `expiresAt`. Plan. Closed.

`reportUsage`: `insertIfAbsent` (v1.1) on `(install, key)`; `require` `occurredAt` in `[ctx.now()-7d, ctx.now()]` and install `state=active` and acceptance `state=live`; compare `spendMonth + qty*price` to cap; write `billable` or `over_cap`. Conditional on unique+cap. Invoice/payout are v1.1 jobs over `usageDaily` (raw `usage` scan is `E_BOUND` at 1B rows — the design already says this).

`uninstall` first attempt: `patchWhere` every `tagAssignments` owned by the install → `E_FANOUT`. Rewrite: **authority is one transaction** (close intervals, drop pending queue with a gap, `state=retained`); tag re-own and `appRows` purge are jobs. `adoptRetainedData` is a job (50M rows). Never delete audit/usage/adjustments (`appendOnly`).

```ts
export const merchantAppLedger = query(
  { installId: id(installs), since: time() },
  ({ db, args }) => {
    const inst = db.get(installs, args.installId)
    db.require(inst !== null && staffOwner(inst.merchantId), 'AUTHZ_REFUSED')
    const grants = db.scan(scopeGrants.byInstall, [args.installId], { take: 64 })
    const fields = db.scan(fieldDefs.byMerchantTable, [inst.merchantId, 'orders'], { take: 64 })
    const rs = db.scan(rules.byMerchantTableState, [inst.merchantId, 'orders', 'active'], { take: 100 })
    const writes = db.scan(writeAudit.byInstallAt, [args.installId], { take: 50, after: args.since, order: 'desc' })
    const spend = db.get(spendMonth, args.installId)
    const lag = db.get(queueLag, args.installId)
    // … programs, subscriptions, readAuditDaily analogously; each take ≤ 50
    return { inst, grants, fields, rs, writes, spend, lag }
  },
)
```

No population `count` over `writeAudit` (completeness). Refusal counts: `refusalHourCount` (merchant-readable). App row counts: `appRowCount`.

#### O8–O10, O13, UI reads

`enqueueFanout`: v1.1 `phase:'system'` continuation of O2; scan subscriptions+react programs `take: 40`; skip when projected fields are empty (and not insert/delete); skip `cascadeDepth ≥ 4`; insert `queueItems` (cap 100k → gap). Plan under the install cap.

`runReaction`: v1.1 job. Each write is O2 with `initiator=null` (needs `autonomous:`). **WRR across merchants / RR across installs is not in the language** — job runtime. Quotas (`budgetWindows`, `rateLimit`) park an over-budget install; they do not stop a plus-tier merchant’s queue from starving a starter’s. Invariant 19 is **not a plan**.

`deliverWebhook`: effect (HTTP, HMAC from vault, 72h backoff). Payload is a named query at **delivery** scopes, not commit scopes. `skipped_unreadable` advances the cursor. `exportStream` (v1.1) is the honest catch-up pipe; the design’s POST is the product shape of the same disclosure.

`runJobSlot`: job, unique `(program, slot)` so missed crons run once; fencing token on each inner write; `STALE_LEASE` is a `require` comparing `jobRuns.leaseUntil` to `commitTime` (window is state, not a rule clock).

`syncOfflineIntent`: replay of O2 with `clientIntentId` unique. Classification follows O2 (**PV**). Local prediction is `partial` whenever a plugin or unreadable lookup is in the envelope; algebraic merchant-visible predicates can replay. `predict:false` on pluginful writes matches “pending check”; promise 9’s “pending badge” is the `queued` state, not a closed prediction.

UI reads (`listOrders`, `storefrontCatalog`, `searchProducts`, `getMe`) are ordinary bounded scans. `getOrder` first attempt returning `orders` plus app metafields in one row is `E_SECRECY_MIX`; rewrite: host row + `fieldValues.byRow take: 32`. `listOrders` for `read:orders.own` uses `byMerchantCreator`, not a mixed-visibility scan of `byMerchantCreated` (`E_CARDINALITY_ORACLE` / v0.1 r2: hidden rows consuming `take` would also yield a wrong page). `availability` is `db.get(reservedQtySum, productId)` — never `page.count`.

### 8. Where the design is wrong

1. **In-commit untrusted programs vs the numbers it wrote.** Six gates × 5 ms CPU = 30 ms, against a 20 ms CPU / 50 ms wall write budget, against “JS never in the authoritative path,” against a certificate of *named* operations. Confirming observation: compile five no-op contributors plus a required Sentinel gate; measure `place` p99 and whether `E_STEPS` in Sentinel rolls back a valid paid order or is caught. If it rolls back, required-gate merchants halt (T5). If it is caught, the design needed nested catchable programs and did not name them.

2. **Invariant 3 vs 24, and metafields on host rows.** “Owner reads every field in the store” and “vault is unreadable to the merchant” cannot both be table rules on one store. Mixed-audience `orders` rows are independently illegal under `E_SECRECY_MIX`. Confirming observation: as owner, `get(installVault)` and `get(order)` — does the order payload contain `app.sentinel.risk_score`? If yes, StockSync’s `read:orders` is a column oracle (T2b by another door). If no, the design’s “fields on host tables” is already the side-table model and should have said so.

3. **One-transaction revoke/uninstall over unbounded children.** Dependents of a scope and tag rows owned by an install are not `All` under a schema `cap` the design named (only “≤ ~100 rules per merchant,” not tags, not `app_rows`). Confirming observation: ShipNimbus tags 2M orders, uninstall, measure whether (1) waits on 2M updates (unavailability) or leaves `ownerId=dead-install` (T4: ledger says “(deleted)” / dead owner still in the attributed set). Authority close can be one transaction; row re-own cannot.
