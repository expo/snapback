## Findings

### F1 (High) — Schema adoption leaves mounted watches polling obsolete ephemeral tables

- **Where:** [local.ts:918](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/local.ts:918), backend adoption at [local.ts:702](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/local.ts:702).
- **What is wrong:** Interests are registered when an observation mounts or resubscribes. Adopting a backend changes query execution facts without updating existing interests. A query changed from reading `typing` to `viewing` continues polling `ephTables=typing`, so writes to `viewing` never invalidate it.
- **Evidence:** [Regression probe](</tmp/eph-code-GPT-6 Astra (max)/adoption-interest.test.mjs>) uses a real dev server and wasm client. After generation adoption and a write, direct HTTP querying returns one row; the mounted observation remains empty, complete, and fresh after **2.2 seconds**. Closing and remounting immediately retrieves the row and changes the poll interest to `viewing`.
- **Proposed fix:** Reconcile every mounted watch’s interests against the adopted backend, including additions and removals. Reissue the held poll when the union grows.

### F2 (High) — Durable-only clients no longer preserve the base wire contract

- **Where:** [client.ts:540](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/client.ts:540), [local.ts:828](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/packages/snapback4/src/local.ts:828).
- **What is wrong:** Both clients unconditionally supply ephemeral poll parameters, including for schemas containing no ephemeral tables. Requests gain `eph=0&ephi=&ephTables=`; responses gain `ephemeral`, and the initial poll follows the incarnation-reset path. This violates the explicit durable-only wire guarantee.
- **Evidence:** [Base-comparison probe](</tmp/eph-code-GPT-6 Astra (max)/durable-wire.test.mjs>) builds clients from `0badac987` and compares both tiers against the same durable-only server. Both comparisons fail: base requests and responses omit those fields; integrated clients include them.
- **Proposed fix:** Preserve legacy polling for durable-only clients and activate ephemeral polling through relevant capability/operation facts. E2 acknowledges unconditional parameters, but preserving the low-level unparameterized helper does not justify changing actual durable clients.

### F3 (Medium) — Renewal certification accepts a guard invalidated by its own write

- **Where:** [renewal.rs:62](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4-core/src/ir/effects/renewal.rs:62).
- **What is wrong:** Guard reads are accepted without checking whether the final write changes their outcome. A mutation that reads `old.n`, requires `old.n = 0`, then updates `n` from its argument receives `renews: true`. Calling it twice with `n: 1` does not have the same result as calling it once.
- **Evidence:** [Regression probe](</tmp/eph-code-GPT-6 Astra (max)/renewal-guard.test.mjs>) gets `sent`, then `ALREADY_CHANGED` through direct HTTP calls. After resetting the row, the generated-fact client returns **`sent`, `sent` with only one request**.
- **Proposed fix:** Refuse renewal certification when guard dependencies overlap the written table unless guard invariance is proven. Add this self-invalidating guard case beside the existing read-derived-patch negatives.

### F4 (Medium) — Equivalent bearer headers bypass the per-session rate bucket

- **Where:** [serve_ephemeral.rs:111](/Users/ccheever/projects/snapback-eph-review-astra/snapback4/crates/snapback4/src/serve_ephemeral.rs:111).
- **What is wrong:** The bucket hashes the entire Authorization header, while authentication trims whitespace around the bearer token. Different spacing therefore authenticates the same session but obtains different buckets.
- **Evidence:** [Regression probe](</tmp/eph-code-GPT-6 Astra (max)/rate-key.test.mjs>) exhausts the canonical header’s burst, then sends the same token with two through seven spaces after `Bearer`. All six writes succeed in **5.37 ms**; the canonical header still receives `E_RATE_LIMIT`.
- **Proposed fix:** Key the bucket by the normalized authenticated token/session identity, using the existing bearer parser. Test equivalent header formatting.
