### 1. Product contract

Mosaic is a collaborative workspace for teams that design their own databases while using the product. Every database record is also a page; pages may contain text, comments, files, and embedded database views. Workspace members, guests, administrators, and integrations use the same runtime-created structures.

1. Users can create databases and typed text, number, select, date, relation, rollup, formula, and files properties without a deployment or operator action.

2. Databases, properties, select options, relations, formulas, views, templates, and records have stable identities independent of their displayed names.

3. Users can relate records across databases; an optional reciprocal property shows the same edge from the other side rather than maintaining a second copy.

4. Every rollup declares its domain:
   - `viewer_visible`, the default, aggregates only related records and values the current viewer may read;
   - `published_structural`, an explicit, audited disclosure of an aggregate over all related records.

5. Formulas are restricted, typed expressions stored as data and interpreted at read time. They may use current-record properties, rollups, deterministic text/decimal/date functions, conditionals, and a query-wide `now`.

6. Formulas execute with the reader’s authority, never the formula author’s authority. A formula depending on viewer-relative input remains viewer-relative unless an administrator explicitly publishes its result.

7. Users can save private or shared views containing nested filters, typed operands, sorts, groupings, visible columns, and deterministic pagination.

8. Runtime-created indexes may accelerate properties, expressions, or views. An index that is absent, stale, or building may affect latency but never the rows or ordering returned.

9. A database, page, and database-record page may each have access rules for viewing, commenting, editing data, editing schema, sharing, exporting, and administering access.

10. An embedded database or relation does not grant access to its target. A reader needs permission on both the containing page and the referenced database or record.

11. Templates can create pages, records, default property values, block trees, and linked or copied embedded databases under the applying user’s authority.

12. Comments support stable page, block, record, or property anchors, mentions, resolution, and notification without granting access to mentioned people.

13. Files use resumable upload, malware quarantine, previews, short-lived downloads, retention, and reference-aware deletion.

14. Imports can create multiple runtime databases, properties, records, and relations; exports produce a coherent authorized snapshot including selected metadata, comments, and files.

15. Concurrent edits to different cells survive one another. Competing edits to the same scalar cell produce an explicit conflict with both versions; relation edits are edge additions and removals, not whole-list replacement.

16. Schema changes are ordered per database. An incompatible change cannot silently reinterpret existing values or stale offline writes.

17. Offline devices may edit known records and create temporary records using stable IDs. Reconnection reauthorizes and revalidates every operation; compatible work merges and incompatible work is quarantined for resolution.

18. Devices converge after receiving the same accepted operations. Acknowledged changes appear in causal order, and no device can erase another device’s unrelated edit by uploading an older whole record.

19. A query uses one committed data/schema snapshot and one server-selected evaluation instant. Time-dependent views refresh at their next boundary even if no record is edited.

20. Revocation blocks new reads, writes, syncs, searches, cursor continuations, exports, and downloads immediately after its access-control commit; previously downloaded information cannot be made unseen, but official clients purge it on their next connection.

### 2. Invariants, in plain language, before any code

1. **[OTHER PEOPLE’S DATA]** Once runtime creation is acknowledged, the new database and properties work through every normal product path without a deployment or predeclared host table.

2. A rename never changes identity, and a deleted identity is never reused by a later object with the same name.

3. **[TIME]** Every response can be explained by one schema revision, one data snapshot, one access-control epoch, and one evaluation instant.

4. Every committed writable value conforms to the property revision and storage epoch recorded with that value.

5. Formula and rollup properties cannot be written as ordinary cells, and every dependency cycle is rejected before publication.

6. A relation has one authoritative edge identity, so forward lookup, reciprocal lookup, and rollup input cannot disagree about whether the edge exists.

7. **[SECRECY] [OTHER PEOPLE’S DATA]** Every rollup states whether it means “records this viewer can see” or an intentionally published structural aggregate, and the UI never presents one as the other.

8. **[SECRECY]** A formula, cache, index, view, notification, export, or background worker never declassifies a hidden input unless an authorized administrator explicitly published that exact derived output.

9. **[SECRECY]** Two worlds differing only in undisclosed facts produce the same visible rows, ordinary counts, groups, sort positions, pagination behavior, errors, notifications, and exports unless a published aggregate intentionally distinguishes them.

10. **[SECRECY] [OTHER PEOPLE’S DATA]** An embed, relation, comment mention, template reference, or guessed object identifier never grants or proves access to its target.

11. **[OTHER PEOPLE’S DATA]** An edit made from a partial view preserves every row and relation edge the editor could not enumerate.

12. Runtime index readiness changes performance only, never query meaning, uniqueness decisions, totals, or pagination.

13. A broken filter, formula, rollup, view, template, or import mapping produces an explicit broken-definition state instead of dropping a predicate or rebinding by name.

14. **[OTHER PEOPLE’S DATA]** Concurrent changes to different cells or different relation edges survive one another, while a same-cell conflict preserves both proposed values and their authors.

15. **[TIME] [SECRECY]** A stale offline grant never authorizes a reconnecting operation, and a committed revocation invalidates every later continuation and download capability.

16. An offline edit automatically rebases only when every referenced database, property, option, and relation still has compatible meaning.

17. **[TIME]** `now`, relative dates, filters, formulas, sorting, grouping, and exports use one declared evaluation instant and timezone rather than device clocks.

18. An accepted mutation has one effect despite retries, and its direct data change and durable change record commit together.

19. **[SECRECY]** A file is not downloadable as a completed attachment until its bytes, hash, scan state, live reference, and current reader authorization all pass.

20. **[SECRECY] [OTHER PEOPLE’S DATA] [TIME]** An export contains exactly its authorized snapshot, while an import is either atomically published as a declared unit or visibly reports its partial progress and failures.

### 3. The traps, ranked

**1. Confusing viewer-visible and structural aggregates**

- **Wrong version:** Compute a rollup over all related records under service or owner authority, expose it to every source-record reader, or instead filter hidden inputs and still label the result as the total.
- **Why it is wrong:** The first version launders secrets through counts, sums, formula branches, filtering, ranks, group sizes, and pagination; the second returns a confident but semantically false “total.”
- **Observation:** Give Lee access to project A but not a related private task. Adding that task must not change Lee’s viewer-visible count, view membership, rank, export size, or notifications; a structural count may change only if an administrator explicitly published that aggregate.

**2. Treating a property name as its identity or its old bytes as its current type**

- **Wrong version:** Rename `Status` to `State`, create a numeric property also called `Status`, and let old views, indexes, or offline edits bind to the new property by name; alternatively reinterpret old text bytes as numbers after an in-place type change.
- **Why it is wrong:** Historical data changes meaning without a user action, stale devices write into unrelated fields, and an incomplete conversion can make one database simultaneously obey two schemas.
- **Observation:** Keep an old filtered view and an offline select edit while the original `Status` is renamed, retired, and replaced. The view must retain the original property ID or become explicitly broken, and the offline edit must be quarantined rather than reaching the replacement.

**3. Treating derived state as independent caches rather than a versioned dependency graph**

- **Wrong version:** Update formulas, rollups, reverse relations, view membership, groups, and indexes in unrelated jobs that overwrite one another whenever they finish.
- **Why it is wrong:** Runtime schema edits change the graph itself; cycles can appear through cross-database rollups, one target edit can fan out to hundreds of thousands of records, and an old worker can overwrite a newer result.
- **Observation:** Concurrently change a formula definition, move a relation edge, and edit the target value while an old recalculation is delayed. No readable snapshot may show the new edge with the old aggregate, and delayed work must fail its dependency fingerprint instead of publishing.

**4. Storing a relation as the array currently visible to one editor**

- **Wrong version:** Render only authorized targets, then interpret the submitted list as a replacement for the complete relation and maintain the reciprocal side separately.
- **Why it is wrong:** A partial viewer deletes hidden edges, concurrent additions disappear, and a crash can leave forward, reverse, and rollup state inconsistent.
- **Observation:** Alice sees edge X while an administrator also creates hidden edge Y; Alice removes X as Bob adds Z. The final relation must retain Y and Z, remove only X, and expose the same live edge set from both directions.

**5. Resolving multi-device work with whole-object last-write-wins**

- **Wrong version:** A reconnecting device uploads its old record, page, relation list, view, or schema and whichever upload arrives last replaces the current object.
- **Why it is wrong:** Unrelated edits disappear, deleted properties are resurrected, old ACLs become authority, and stale operations can erase hidden data.
- **Observation:** Device A edits text offline while device B edits a date, deletes the text property, adds a hidden relation, and revokes A. Reconnection may preserve B’s date and hidden edge, but A’s text must become a schema/access conflict rather than being dropped, resurrected, or remapped.

**6. Assuming time-dependent results change only when rows change**

- **Wrong version:** Cache `today`, `now`, expiring access, and relative-date view membership until some data write happens, with each worker or device choosing its own clock.
- **Why it is wrong:** An overdue item never enters its view at midnight, a formula and its filter can disagree, an expired share link can keep working, and pagination pages can use different temporal meanings.
- **Observation:** Open a grouped “due today” view across midnight while a share grant expires and no row changes. A continuation either retains its original declared instant under still-current authorization or is invalidated; a fresh query must use the new instant and deny the expired grant.

### 4. Data model

All IDs are opaque 128-bit values and all authoritative references use IDs, never names. Each workspace has a monotonically increasing `sequence`; one committed mutation receives one sequence and one `commit_id`. Revisions are append-only and become valid at `from_sequence`; the next revision implicitly ends the interval. Mutable “head” rows are disposable accelerators.

**Identity and access**

- `workspace(workspace_id PK, name, current_sequence, retention_policy)`
- `principal(principal_id PK, workspace_id, kind: user|group|share_link|system, state)`
- `group_membership_event(group_id, user_id, operation: add|remove, from_sequence, valid_from?, valid_until?)`
- `resource(resource_id PK, workspace_id, kind: page|database|record_page, parent_resource_id?)`
- `acl_policy_revision(resource_id, revision, break_inheritance, from_sequence, actor_id)`
- `acl_entry_revision(resource_id, entry_id, subject_id, action, effect: allow|deny, valid_from?, valid_until?, from_sequence)`
- `share_link(link_id PK, resource_id, token_hash, actions, expires_at?, revoked_sequence?)`

Actions are `view`, `comment`, `edit_data`, `edit_schema`, `manage_templates`, `share`, `export`, `history`, and `administer`. At evaluation time, active rules are collected through the resource ancestry until an inheritance break; deny wins over allow. A database-record page requires the intersection of database and page permission. An embed requires both container-page and target-database permission.

**Pages and databases**

- `page(page_id PK, resource_id, parent_page_id?, record_id?, created_sequence, created_by)`
- `page_revision(page_id, revision, title, state: live|archived|purged, from_sequence, actor_id)`
- `block(block_id PK, page_id)` and `block_revision(block_id, revision, parent_block_id?, ordinal_key, kind, payload, from_sequence)`
- `database(database_id PK, workspace_id, resource_id, owning_page_id?, schema_head_revision, created_sequence)`

An embed block stores `database_id`, optional `view_id`, and `mode: track_latest|pinned_revision`; it stores no copied authority.

**Runtime schema catalog**

- `schema_revision(schema_revision_id PK, database_id, revision_number, parent_revision_id?, from_sequence, actor_id)`
- `schema_member(schema_revision_id, property_id, property_revision_id, ordinal, PK(schema_revision_id, property_id))`
- `property(property_id PK, database_id, created_sequence)`
- `property_revision(property_revision_id PK, property_id, predecessor_id?, name, kind, storage_epoch, state, config, from_sequence)`
- `select_option_revision(option_id, property_id, revision, label, color, ordinal, state, from_sequence)`
- `relation_definition_revision(relation_id, revision, left_database_id, left_property_id, right_database_id, right_property_id?, left_cardinality, right_cardinality, from_sequence)`
- `dependency_edge(owner_property_revision_id, dependency_kind, referenced_property_id, through_relation_id?)`

Property `config` is a validated tagged structure:

- text: rich/plain mode and length limit;
- number: decimal precision, scale, display unit, and rounding;
- select: stable option IDs;
- date: date-only or instant/range rules and timezone policy;
- relation: relation ID, endpoint role, and cardinality;
- rollup: relation property ID, target property ID, aggregate, null/error rules, and `viewer_visible|published_structural`;
- formula: expression ID, result type, language version, and volatility;
- files: count, size, and media restrictions.

Rename, reorder, formatting, and option-color changes preserve `storage_epoch`. An incompatible type change creates a new epoch through a staged conversion. Retired options retain their historical label but reject new assignments. Retargeting a relation creates a new relation identity.

**Records and values**

- `record(record_id PK, database_id, page_id, created_sequence, created_by)`
- `record_revision(record_id, revision, schema_revision_id, base_revision?, tombstone_state, from_sequence, actor_id)`
- `cell_revision(cell_revision_id PK, record_id, property_id, property_revision_id, base_cell_revision?, operation: set|clear, typed_value, from_sequence, actor_id)`
- `relation_edge_event(relation_id, edge_id, left_record_id, right_record_id, operation: add|remove, ordinal?, from_sequence, actor_id)`
- `write_conflict(conflict_id PK, object_id, field_id?, base_revision, accepted_revision, proposed_value, actor_id, state)`
- `change(commit_id PK, workspace_id, sequence, actor_id, request_key, cause, recorded_at)`

`typed_value` is exactly one of null, text, decimal, boolean, `{start,end?,all_day,timezone}`, select-option ID, or ordered attachment IDs. Relations use edge events; formulas and rollups have no writable cell. Numbers are base-10 decimals, not binary floating point.

**Expressions, views, and runtime indexes**

- `expression(expression_id PK, language_version, canonical_typed_AST, result_type, volatility)`
- `view_revision(view_id, revision, database_id, schema_revision_id, owner_id?, sharing_mode, filter_expression_id?, presentation_kind, from_sequence)`
- `view_sort(view_id, revision, ordinal, property_id, direction, null_error_order)`
- `view_group(view_id, revision, ordinal, property_id, bucket_policy, timezone?)`
- `view_column(view_id, revision, ordinal, property_id, visibility, width?)`
- `index_revision(index_id, revision, database_id, schema_revision_id, key_expression_ids, directions, collation_version, partial_filter_expression_id?, state, build_snapshot, coverage_watermark)`
- `index_entry(index_id, revision, normalized_key, record_id, source_record_revision, operation, from_sequence)`
- `derived_result(record_id, property_id, property_revision_id, evaluator_version, snapshot_watermark, dependency_digest, authorization_scope, evaluation_time_bucket, typed_result)`

Formula ASTs permit typed literals, property references, arithmetic, comparison, boolean operators, lazy conditionals, bounded text/date functions, and `now`; they prohibit mutation, files, network calls, randomness, and unbounded recursion. Null and error are distinct. Errors are typed values such as `MISSING_DEPENDENCY`, `TYPE`, `CONVERSION`, `DIVIDE_BY_ZERO`, `PERMISSION`, `LIMIT`, and `TIMEOUT`.

A canonical read fixes `(snapshot S, evaluation time T, principal P, ACL epoch A, schema/view revisions, evaluator version)`. A viewer-visible rollup traverses edges and target values readable by P at S. A published structural rollup traverses every live structural edge at S and exposes only the declared output. Formula scope inherits its dependencies. The entire dependency graph is type-checked and cycle-checked at schema publication.

Filters are typed ASTs. Errors do not match unless tested with `is_error`. Sorts define collation, null/error order, and `record_id` as the final tie-breaker. A cursor binds S, T, A, the view revision, and the query digest.

Indexes and derived results are non-authoritative. An index is usable only when its schema/expression revision and watermark cover the requested snapshot, possibly with an authoritative delta tail; otherwise the system scans, computes, queues the query, or returns an explicit cost-limit result.

**Templates, comments, files, jobs, and history**

- `template_revision(template_id, revision, target_database_id?, required_schema_revision, initial_cells, block_manifest, placeholders, from_sequence)`
- `comment_event(thread_id, comment_id, anchor_kind, anchor_id, anchor_revision, operation, body, mentions, from_sequence, actor_id)`
- `file_asset(asset_id PK, object_key, hash, size, media_type, state: reserved|uploaded|quarantined|clean|rejected|purged)`
- `attachment_revision(attachment_id, revision, asset_id, filename, caption, ordinal, from_sequence)`
- `job(job_id PK, kind: migration|import|export|index|recompute, state, pinned_snapshot, pinned_schema, checkpoint, manifest, error_report)`
- `outbox_event(event_id PK, commit_id, topic, payload_digest, delivery_state)`
- `audit_event(event_id PK, resource_id, actor_id, action, commit_id, metadata)`

Schema, cell, relation, ACL, comment, and audit revisions are append-only. Current heads, inverse-relation projections, effective ACLs, indexes, search entries, and derived results are rebuildable. Memberships, grants, share links, signed downloads, upload reservations, archived objects, export artifacts, and time-dependent cache entries are time-bounded.

### 5. The hard operations

All mutations carry stable IDs, an idempotency key, the expected schema revision, and relevant object or cell revisions.

1. **Create a database.**  
   **Inputs:** parent page, name, initial property definitions, default view, optional relations, client-generated IDs. **Authorization:** create child and edit schema; read any relation targets. **Steps:** (1) authorize the parent; (2) validate type configurations and IDs; (3) type-check expressions and dependencies; (4) create the database resource, ACL, schema revision, properties, view, embed block, and index intents; (5) append the change and audit records. **Atomic:** all catalog objects and the visible default view. **Eventual:** indexes, statistics, search. **UI:** provisional database shell. **Conflict:** duplicate request returns its original result; deleted parent, stale parent revision, or lost permission rejects everything.

2. **Publish an ordinary schema change.**  
   **Inputs:** expected schema revision and additions, renames, reorders, option edits, property retirement, or relation metadata. **Authorization:** edit schema; reciprocal cross-database relations require schema authority on both databases. **Steps:** (1) load the current manifest; (2) classify changes by storage compatibility; (3) enumerate affected formulas, rollups, views, templates, and indexes; (4) require an explicit repair, disable, or cancel decision for each incompatible dependent; (5) type- and cycle-check the proposed graph; (6) append revisions and atomically advance the schema head. **Atomic:** schema manifest, dependency graph, invalidation epoch, and audit record. **Eventual:** index/cache rebuild. **UI:** editable draft, not an optimistic published schema. **Conflict:** same-property or dependency changes require rebase; disjoint additions may be resubmitted against the new head.

3. **Convert a property to an incompatible type.**  
   **Inputs:** source property, target kind, deterministic conversion rules, error policy, expected schema. **Authorization:** edit schema and read all affected data. **Steps:** (1) create a hidden target property/epoch and migration job pinned at S; (2) keep the source canonical while backfilling target values in idempotent chunks; (3) record source edits after S in a delta stream; (4) replay deltas and report every conversion error; (5) after approval, briefly fence source writes, revalidate dependents, replay the final delta, publish the target in the source ordinal, and retire the source. **Atomic:** migration initiation and final cutover are separate transactions. **Eventual:** backfill and indexes. **UI:** “converting,” with old values authoritative until cutover. **Conflict:** schema/dependency changes pause the job; unresolved errors prevent cutover.

4. **Create or edit a record, including an offline edit.**  
   **Inputs:** record ID, cell and block operations, base record/cell revisions, schema revision, client operation IDs. **Authorization:** create/edit the database-record page; computed properties are read-only. **Steps:** (1) reauthorize now; (2) resolve stable property IDs against the current schema; (3) reject or quarantine incompatible stale fields; (4) validate typed values and select options; (5) accept unchanged-base cells, retain conflicts for concurrently changed scalar cells, and apply stable block operations; (6) commit cells, blocks, record revision, conflicts, and change event. **Atomic:** all accepted direct edits and conflict records. **Eventual:** derived values, views, search, notifications. **UI:** pending local patch with rollback/conflict badges. **Conflict:** different cells merge; same cell preserves current and proposed values; edit-versus-delete requires explicit restore.

5. **Add or remove relations.**  
   **Inputs:** source record/property, target IDs, edge IDs to add or remove, expected cardinality revision. **Authorization:** edit source and read every named target; removing a hidden edge requires administration rather than guessing its ID. **Steps:** (1) resolve the relation revision; (2) validate endpoint databases, target existence, cardinality, uniqueness, and permission without distinguishable unauthorized/not-found errors; (3) append exact edge add/remove events; (4) advance the source revision; (5) enqueue affected rollups, formulas, and views. **Atomic:** edge events, both directional projections’ source event, record revision, and change record. **Eventual:** derived projections. **UI:** optimistic visible edge deltas. **Conflict:** independent additions commute; removal deletes only the observed edge; a concurrent remove and new add produce a new live edge; single-value cardinality races conflict.

6. **Define or revise a formula or rollup.**  
   **Inputs:** property ID, formula AST or relation/target/aggregate definition, exposure mode, expected schema. **Authorization:** edit schema and read referenced schema; `published_structural` additionally requires access-administration authority over both endpoint databases. **Steps:** (1) parse and canonicalize the typed AST or aggregate; (2) resolve references to IDs; (3) infer output type and volatility; (4) construct dependency edges; (5) reject cycles, incompatible aggregates, excessive depth, and nondeterminism; (6) verify that any publication covers every dependency; (7) publish the property/schema revision and invalidate old derived state. **Atomic:** definition, type, exposure mode, graph, and invalidation epoch. **Eventual:** caches and indexes. **UI:** draft preview labeled with its domain. **Conflict:** concurrent dependency deletion or retyping rejects publication; obsolete recomputation cannot write under the new revision.

7. **Save and execute a dynamic view.**  
   **Inputs:** filter AST, sorts, groups, columns, sharing mode, view revision, page size, cursor. **Authorization:** edit shared views to save; view the database and each returned record to query. **Steps:** (1) validate and save a typed view revision if requested; (2) choose S and T and capture ACL epoch A; (3) resolve current schema and compile the stored AST; (4) use only an index whose definition and watermark cover S, otherwise scan or queue; (5) authorize candidates and dereferences; (6) evaluate formula and rollup scopes; (7) filter, sort, group, count, and paginate visible results; (8) recheck A before response and issue a bound cursor. **Atomic:** view save; each read is one coherent snapshot. **Eventual:** adaptive index creation. **UI:** local edits may overlay the returned page as explicitly pending. **Conflict:** view revision changes require rebase; schema or ACL changes invalidate cursors; over-budget work returns a clear queued/limit state, never partial rows.

8. **Grant, inherit, move, or revoke access.**  
   **Inputs:** resource, subject, actions, allow/deny, inheritance mode, expiry, expected ACL revision. **Authorization:** share/administer access and never grant beyond the actor’s authority; the last administrator cannot be removed accidentally. **Steps:** (1) resolve the resource ancestry and database/page intersection; (2) validate the delegation and resulting administrator set; (3) append ACL revisions or atomically change parent/inheritance; (4) advance the ACL epoch; (5) invalidate cursors, sessions, share links, exports, and download capabilities using the prior epoch; (6) append an audit event. **Atomic:** new authorization decision and epoch. **Eventual:** physical cache/search purge and connected-client notification. **UI:** grants may appear pending; revocation is not shown complete before commit. **Conflict:** stale ACL revisions return a policy diff. Previously downloaded bytes remain outside enforceable revocation.

9. **Instantiate a template and render embeds.**  
   **Inputs:** template revision, target parent/database, variables, defaults, copy/link choices, ACL mode. **Authorization:** read template, create target content, edit schema for copied databases, and separately access linked embeds. **Steps:** (1) pin template and target schema revisions; (2) allocate new IDs and remap copied property/relation/formula/view references; (3) evaluate placeholders under the caller’s authority; (4) create cells, blocks, pages, and embed references; (5) apply target ACL inheritance; (6) publish the instance. **Atomic:** small instances, or the publication of a fully staged large instance. **Eventual:** indexes and previews. **UI:** provisioning placeholder. **Conflict:** schema changes require revalidation; template edits do not mutate pinned instances; inaccessible linked embeds render locked without revealing target metadata.

10. **Create or change a comment.**  
    **Inputs:** stable page/block/cell anchor, body, mentions, thread revision, action. **Authorization:** view and comment on the target; author or moderator authority for edit/delete. **Steps:** (1) resolve the anchor and current target access; (2) validate body and mentions; (3) append the comment/thread event; (4) enqueue notifications only for recipients currently able to view the target. **Atomic:** comment state, thread revision, and notification outbox. **Eventual:** delivery, unread counters, search. **UI:** optimistic own comment. **Conflict:** new comments append; edits compare revisions; deleting an anchor leaves an explicitly orphaned page-level thread rather than losing it.

11. **Upload and attach a file across external storage.**  
    **Inputs:** target cell/block, filename, size, media type, hash, base cell revision. **Authorization:** edit target, satisfy file policy and quota. **Steps:** (1) reserve quota and create a pending asset; (2) issue a short-lived, single-purpose upload capability; (3) receive an external completion event and verify size/hash; (4) scan or quarantine the object; (5) reauthorize the user and revalidate target/schema; (6) atomically mark the asset clean and attach it; (7) generate previews asynchronously. **Atomic:** no distributed transaction is claimed; only the final internal asset/attachment transition is atomic. **Eventual:** scanning, previews, OCR, garbage collection. **UI:** local pending preview. **Conflict:** stale replacement becomes a cell conflict; deleted targets or lost permission leave an unattached object for cleanup; retries reuse the reservation.

12. **Advance derived state and temporal boundaries in the background.**  
    **Inputs:** committed change range or scheduled time boundary, schema/dependency epoch, checkpoint. **Authorization:** a tenant-scoped system identity may compute structural inputs but gains no disclosure authority. **Steps:** (1) claim an idempotent work item; (2) load its dependency graph revision; (3) coalesce affected records; (4) evaluate topologically at a declared snapshot/time and authorization scope; (5) compare complete input fingerprints; (6) atomically write each derived result/index delta and advance its watermark; (7) schedule the next `now`/relative-date boundary and publish invalidations. **Atomic:** each result plus fingerprint and each checkpoint. **Eventual:** tenant-wide convergence. **UI:** stale cached results carry a watermark or are read through; they are never labeled current. **Conflict:** changed inputs make old work a no-op and requeue; a poison record records a bounded error without stopping the tenant.

13. **Bulk import data.**  
    **Inputs:** uploaded CSV/JSON/package, proposed schema mapping, new-or-merge mode, relation keys, duplicate policy, base schema. **Authorization:** bulk write; schema authority for new properties; access to referenced targets. **Steps:** (1) scan and parse in isolation; (2) infer a proposal but require confirmed typed mappings; (3) allocate all database, property, record, and external-key IDs before relations; (4) create a durable job; (5) validate and commit idempotent chunks; (6) resolve relations in a second pass; (7) parse imported formulas into the restricted AST rather than executing source text; (8) publish a new database only when complete, or expose an explicit committed watermark for a merge import. **Atomic:** job/schema initiation and each chunk; not an unbounded import. **Eventual:** derived state and indexes. **UI:** resumable progress and row errors. **Conflict:** incompatible schema changes pause the job; retries use stable source-row IDs.

14. **Export an authorized snapshot.**  
    **Inputs:** database/view/workspace scope, format, files/comments/history flags. **Authorization:** export plus current read access and organization policy. **Steps:** (1) authorize and pin S, T, schema/view revisions, and ACL epoch; (2) enumerate only authorized resources; (3) evaluate filters, formulas, and rollups in the requester’s scope; (4) serialize permitted schema metadata, rows, relations, comments, and file manifest; (5) assemble encrypted external artifacts with checksums; (6) reauthorize before every chunk publication and download; (7) expire the artifact. **Atomic:** job creation and cutoff, not multi-hour assembly. **Eventual:** packaging and file copying. **UI:** progress with snapshot time. **Conflict:** later edits are excluded; revocation cancels and purges the unfinished artifact; retry retains the same cutoff.

### 6. Scale and cost

A successful deployment has about 500,000 active workspaces, five million monthly active users, one billion records, 20 billion populated cell revisions, several billion relation edges, and petabytes of files.

A median active database has 2,000 records, 25 properties, and six views. A large database has 10 million records, 500 properties, 1,000 views, 50 formula/rollup properties, and relation cells with up to 10,000 edges. A large tenant has 10,000 members and 100 million records. A hot database may sustain 2,000 connected readers, 1,000 view queries per second, and 200 mutations per second. Imports reach one million rows; exports reach ten million rows.

Practical limits include 500 properties, formula depth 32, 500 AST nodes, ten sort keys, five grouping levels, 10,000 edges per relation cell, and 100 displayed rows per page. Crossing a limit yields an explicit error or asynchronous job, never truncation described as a complete answer.

The expensive operations are:

- Viewer-relative rollups used in filters or sorts, because arbitrary per-page ACLs prevent one global aggregate or index from serving every principal.
- Target edits with large reverse fan-out, because one change can invalidate hundreds of thousands of rollups and view memberships.
- Cold dynamic filters over high-cardinality EAV values, especially formulas or multiple sorts without a ready runtime index.
- Access revocation for a large group or moved page subtree, because cached query, search, derived, export, and sync state all change authorization epoch.
- Incompatible property conversion, million-row import, snapshot export, and runtime-index backfill.
- Volatile formulas such as `now()`, whose results and view memberships change without source writes.
- Index proliferation: materializing every property-by-view combination would grow approximately with records × properties × views and is not viable.

Adding or renaming a nullable property should be metadata-scale. Interactive write work should scale with changed cells, edge deltas, and distinct dependency nodes scheduled—not total records or saved views. Warm indexed first pages should complete within roughly 500 ms; direct mutations within roughly 300 ms. Ordinary derived maintenance should converge within five seconds, while bulk-induced lag may take minutes and must expose a watermark.

### 7. Where a backend would have to be unusual

1. **Transactional runtime schema and index catalog.** The backend must publish user-created properties, types, relations, formulas, views, migration states, and index definitions atomically while ordinary writes continue.  
   **Concession:** use a fixed set of property kinds, bounded schema size, and asynchronous incompatible conversions.  
   **Cheat boundary:** requiring deployment-time tables, generated endpoints, or operator-created indexes makes runtime schema cosmetic; storing opaque maps while validating and querying only in clients is also a cheat.

2. **Access-aware runtime query and expression evaluation.** Filters, formulas, sorts, groups, and pagination are typed AST data interpreted against stable property IDs, a snapshot, an evaluation clock, and current ACLs.  
   **Concession:** restrict functions, recursion, depth, and cost; queue cold queries or require an index to finish.  
   **Cheat boundary:** hard-code anticipated views, download entire databases for client filtering, silently omit inaccessible inputs while calling the result structural, or return partial results from an incomplete index.

3. **Authorization-safe derived values.** The backend must distinguish viewer-relative evaluation from intentional structural publication and prevent counts, ranks, groups, errors, cursors, caches, exports, and notifications from laundering hidden facts.  
   **Concession:** disallow viewer-relative rollups as large-view sort/filter keys unless an authorization-scoped index exists, or require an administrator to publish the aggregate.  
   **Cheat boundary:** forcing all related data public, computing everything as the owner, or withholding hidden cells only after their values affected observable query structure defeats the axis.

4. **A versioned, incremental dependency plane whose graph is itself data.** Relation edges, formulas, rollups, view membership, runtime indexes, ACL epochs, and temporal invalidations require cycle checks, input fingerprints, fan-out control, durable retries, and stale-write rejection.  
   **Concession:** allow explicit derived lag, bounded read-through, per-record errors, quotas, and chunked recomputation.  
   **Cheat boundary:** update rollups only when opened, rescan whole tables for every edit while claiming scale, ignore target-value changes, or present stale derived results as current.

5. **One canonical change history spanning transactions, offline merge, bulk jobs, and external systems.** The backend needs per-cell revisions, edge operations, idempotency, schema-aware rebasing, snapshot cursors, transactional outbox records, resumable jobs, and reauthorization at external delivery.  
   **Concession:** use explicit conflicts instead of semantic same-cell merging, finite offline history followed by full resync, chunk-atomic imports, and at-least-once external events with delivery IDs.  
   **Cheat boundary:** whole-record last-write-wins, one-request million-row jobs, lossy post-commit notifications, mocked file failure paths, or retries that duplicate records and edges.

### 8. Confidence

Stable IDs, immutable revisions, typed tagged values, restricted expression ASTs, dependency DAGs, optimistic concurrency, relation-edge events, hierarchical ACLs, idempotency keys, outboxes, object storage, resumable jobs, and snapshot exports are standard practice.

The two-domain rollup contract, explicit aggregate publication, authorization-scoped derived caches, staged incompatible-property cutover, and the exact limits and latency targets are designed for this exercise. They are deliberate product choices that make hidden-domain semantics, schema races, and stale derived state observable rather than leaving an implementer to guess.
