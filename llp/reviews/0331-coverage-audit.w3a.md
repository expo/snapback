# Authorization coverage audit — LLP 0331 core vs wave 3, part A (brokerage, calendar, dating, DoorDash, daily fantasy)

Inputs read in full: `llp/0331-scoped-roles-diary-feedback.research.md` §"Snapback2 synthesis" (lines 104–420); `llp/0329.014.004-bounded-data-programs-v1-design.rfc.md` §1–§8; `llp/0329.014.003-paper-archetypes-wave-3.research.md` §Findings; the ten artifacts under `llp/reviews/` named per app below. Line references are `file:line` against those files as they stand today.

## Reading conventions used in every table

- **"One hop."** I read 0331's bound as *depth*, not count: a rule may compose several independent `exists`/`get` probes with `&&`/`||`/`!` (0331 says "explicit role sets / boolean composition"; its own Clique recipe pairs a membership probe with a separate admin-role probe). A probe whose **key** comes from another probe's found row is two hops → X1. If the founder intends literally one probe per rule, the rows marked "multi-probe" below become an X20 ("probe composition") and I flag that in the rollup.
- **`get(parent)` with a `where`** on the found row (`get(orders,[row.orderId]) where customerId == viewer`) is one hop on a non-relationship row → CORE(where), the brief's X7 form. Comparing a found-row field to a field of the row under evaluation (`where generation == next.generation`) is also counted CORE(where); if 0331's `where` admits only literals, those rows become X6.
- **X6 is split**: `X6-rt` = the rule compares a plain status field that a *schedule* flips (time-as-state; the rule language is unchanged, the runtime needs the schedule kind under the system principal, which RFC §6 already lists); `X6-rule` = the rule needs a computed value or a cross-probe comparison. Only X6-rule is a rule-language extension.
- **X11 is split**: `X11-run` = a mutation/schedule/effect-ingress that must execute under the system principal (`callable:'system'`, schedule under system) — 0331's own text already assumes schedules run as system; `X11-read` = a *viewer-called* named mutation that must read or write rows the viewer cannot read (`getHidden`, `phase:'system'`, third-principal `visibleTo`). Only X11-read is a real addition to 0331's model of "programs derive the acting principal".
- **CORE-with-denorm** notes name the duplicated column and whether the design (D) or the v0 (V) already did it.
- Integrity constraints (caps, balanced ledgers, PDT counts, unique seals) are not authorization and are not counted, except where a *money/authority hole* exists only because a write is not coupled to another write (X19) — those are called out because the v0s named them as holes.

Authorization was *incidental* here: the design's six traps are generations, fan-out, PDT pairing, the venue saga, buying-power fences and lot freezing (design:57–85); only T6 touches authority ("membership is an interval", design:82). The account-party recipe is 0331's recipe verbatim. The one extension that flips the app to COVERED-WITH-DENORM is **X11-read** — a viewer-called mutation reading the sealed risk feed (B5); X6-rt is a runtime kind 0331/RFC §6 already assume, and X17 dual control is droppable. The design did not reach for anything §8 refuted on the authorization axis; it did reach for `COUNT(*)` watch counts and loop-tally PDT counts (design:64, 207), which §8 refutes on the completeness axis ("loop tallies included"; "completeness is the second axis"), and it put "at **now**" in the trade check (design:179), which the v0 first spelled `party.valid.contains(ctx.commitTime)` (v0:330) and then correctly moved to schedule-written active rows (v0:497) — the §8 row "`ctx.now` … → schedule-flipped state".

**Sprawl check.**
- X11-read (B5): load-bearing for promise 1/inv. 19 as stated — the reservation collar uses the live risk mark that delayed customers must not read. Reduced product: reserve against the customer-visible (delayed) mark with a wider collar; loses risk accuracy on fast markets, keeps every customer promise. Honest but weaker.
- X6-rt (B1, B2): load-bearing for "time-bounded limited power of attorney" (design:3) and entitlement expiry (design:104). Reduced product: manual revocation only (no automatic `valid_until`); loses automatic expiry, keeps live revocation via row deletion (core).
- X17 (B6): droppable — ship single-approver, logged break-glass grants; loses "dual-controlled".

**App verdict: NEEDS: X1 (C2, C9), X4 (C6; or X3-guest), X11-read (C8, C12), X6-rt (C1, C3, C6), X19 (C3 attribution, droppable)**; C5 is CORE-with-denorm (v0 partial, design no).

Authorization *was* one of this app's hard problems: two of six traps (4 "email is not permanent identity", 5 "actor, owner and offline authority collapsed") and invariants 12, 15, 16, 19 are authority statements, and the fixed field-projection matrix (design:121–129) is the product. No single extension flips it: group/org audiences (X1) and the accountless guest (X4/X3) are independent. The *largest* is X1 — it appears in both sharing (C2) and free/busy audience (C9), and its cheapest bounded form is an engine-maintained fan-out (X13) so the rule stays one hop. The design reached for `visibility_epoch` cursors (design:91, 155) which the v0 shows are subsumed by the receipt/trace model (v0:93); it also stated detail levels as a per-relationship *column* matrix (design:121–129), which §4 of the RFC refutes as column-level rules ("`E_SECRECY_MIX` … the protection-class split pasted") and the v0 re-expressed as tables per class (v0:56) — core, no X5 needed. §8's row "rules are point predicates over one principal id → principal closure over a bounded binding set" was forced by the events app; calendar hits the same wall in C2/C9.

**Sprawl check.**
- X1 (C2, C9): load-bearing for contract 6 ("invite … groups") and for org-wide free/busy policy (design:137). Reduced product: direct grants and per-principal availability policies only; loses group sharing and org-level availability — a real loss for an enterprise calendar but an honest one. The X13 fan-out form keeps rules core at the cost of an engine-maintained table with a certificate.
- X4 (C6): load-bearing for contract 7 and for design:3 "external guest is a first-class invitation recipient even without an account". Reduced product: guests must register before RSVP; loses contract 7. The X3-guest-principal form is the smaller extension because it changes the identity boundary, not the rule language.
- X11-read (C8): load-bearing for contract 6's non-disclosure of account existence across orgs; droppable inside one org whose directory already reveals membership (the contract's own escape clause).
- X11-read (C12 `visibleTo`): droppable for in-app reminders (reference-only, v0:265); load-bearing for mail/push carrying titles.
- X6-rt (C1, C3, C6): load-bearing for every "time-bounded" grant/scope/link in contracts 7, 12 and the data model's `valid_until`; reduced product is manual revocation only.
- X19 (C3): droppable — attribution as program discipline; loses the guarantee that no writer can change a schedule without an audit row.
