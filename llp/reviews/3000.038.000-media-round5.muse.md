Four concrete design gaps prevent acceptance. None is a test-only gap; each needs a design or code change.

1. Orphan transfer bypasses terminal admission identity. `Device::enqueue` ([device.rs](/home/ccheever/projects/sb4-w9-media/snapback4/crates/snapback4-device/src/device.rs:1204)) checks only quota via `upload::transfer` and inserts, skipping the `upload_terminal` identity comparison and `upload::validate` that `admit_upload` enforces. Both web adopters ([web-worker-orphans.ts](/home/ccheever/projects/sb4-w9-media/snapback4/packages/snapback4/src/web-worker-orphans.ts:62)) and ([web.ts](/home/ccheever/projects/sb4-w9-media/snapback4/packages/snapback4/src/web.ts:542)) use this path. A stale owner holding unresolved id X can plant it on a destination whose terminal history already owns X under different input, with no `E_WRITE_ID_REUSE`. JS dispatch-time receipt recovery masks this on one path, but the device invariant in §2 is broken, and `uploads()` and `uploadIntent()` disagree while it holds.

2. Early-refusal finalization binds unverified args. `finish_asset_intent` ([asset_uploads.rs](/home/ccheever/projects/sb4-w9-media/snapback4/crates/snapback4-core/src/engine/asset_uploads.rs:158)) records whatever `op`/`args` the caller sends as the bound receipt. Nothing checks them against the intent fingerprint, so a divergent first finalization permanently poisons the id and the correct placement later fails `replay_bound`. The "unchanged operation/args" promise is client-side only.

3. Cancel-vs-upload race surfaces the wrong error. `_asset_intents` is `PRIMARY KEY(owner, intent)`, so a tombstone committed between the upload transaction's `replay_intent` recheck and its plain `INSERT` yields a constraint error (`E_STORE`, retryable), not `E_UPLOAD_CANCELLED`. The race is not "decided under the same ledger transaction" as §3 claims; it costs a spurious backoff plus a full byte retransmit before the replay path reports cancelled. Use `ON CONFLICT`-aware insert with recheck.

4. Facade parity overclaimed. `guardUploads` ([app-uploads.ts](/home/ccheever/projects/sb4-w9-media/snapback4/packages/snapback4/src/app-uploads.ts:23)) rechecks scope after await for readers but not for `retryUpload`, `discardUpload`, or `cancelServerUpload`, unlike the ordinary app-client guard. §4's "same session authority checks as ordinary writes" does not hold for three of seven methods. Related: `begin_send_for(None)` never calls `require_ready`, so the "direct/native adapters cannot bypass" claim rests on every caller passing an id, not on device enforcement; all current sites do, so this is hardening, not an active bypass.
