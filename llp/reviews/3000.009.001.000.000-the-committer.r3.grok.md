## Verdict: SOUND WITH MAJOR ISSUES

Commit-time `at = max(T, pin)` does not by itself match serial execution at `at`. The boundary is only lifetime edges plus the session and claim deadlines, while the pin lifts `at` above the provisional `T` on every overtake, and ordinary `now` arithmetic changes results inside that gap. Monotone allocation is sound for the synthesized parent-prefixed sequence index, including deletes and gaps, and unsound for other indexes that contain the sequence. Dependency-directed publication matches the settle loop and stays one row wide, but the member table still requires a full drain, and dropping the per-request prelude changes which disclosure commits exist below a sync watermark. Value dependencies for totals and caps are safe.

## Findings

### N1. Execution at provisional `T` is not serial execution at `at` — FUNDAMENTAL — committer §6, §3.5; read-sets §3

`at = max(T, pin)` is strictly later than the `T` the program ran with whenever a later commit has moved the pin (`3000.009.001.000.000-the-committer.rfc.md` §6). That pin is schema-wide as soon as any table has `not before` (`time_audience.rs:12–16`). Acceptance is `at < B`, and `B` is only the next expiry of examined rows, the pending opening of examined or written rows, and the session and claim deadlines (§6; read-sets §3, the `Boundary` row).

That is not every input that can change the outcome on `[T, at)`:

- `require now - m.at <= 60000` compares elapsed time to a literal. The language treats `now - .at` as ordinary arithmetic (`snapback4-lang/src/guide/language.rs:537`). §6 taints only "a comparison of `now` against stored data," which this shape is not, and a require's boolean is not a placeholder. Take `m.at = 0`, `T = 0`, window `60000`, and a pin moved to `120000` by an unrelated commit. `at < B` holds if `B` is a later session expiry. The pre-executed edit is allowed. Serial execution at `120000` refuses.
- `hour(now)`, `day(now)`, and `bucket(now, …)` (`language.rs:537`) are the same class when they choose a branch or a bucket and are not stored through the placeholder rule.

Storing `at: time default now` is covered, because §6 rewrites values derived from `now` to `at`. Lifetime edges of rows the walk actually examined are covered. Parent §6.4 still says an execution at `t` commits only if `t` is at or after the last pin, and otherwise reruns (`3000.009.001.000-the-postgres-store-port.rfc.md` lines 723–726). §3.5 says the committer keeps that invariant. §6 commits the execution done at `T` anyway. Exact sequence snapshots and the monotone floor are intact. The outcome at the new `at` is not.

### N2. The monotone-allocation exception is false for any index that is not parent-prefixed — MAJOR — committer §4.1, §4.5

The synthesized index is `(parent, ordinal)` (`snapback4-lang/src/bind/schema.rs:289`; `schema.rs:1149`). Integers sort in numeric order (`key.rs:37–40`). The counter advances by `previous + 1` (`sequences.rs:233`, `commit_sequences` at `271–280`) and delete never calls `set_sequence`, so a resolved value stays strictly above every surviving key of that parent, gaps included. Within that index the order claim holds.

User indexes are copied onto the table with no such restriction (`bind/schema.rs:173–189`). A unique index on `(ordinal)` or `(status, ordinal)` is legal. The insert's unique probe uses the provisional image (`engine/write.rs:149–158`). Parent A's row can already hold ordinal `5` while parent B's counter is `4`, so B's provisional `5` collides and the member refuses. Concurrent commits on B assign `6` or later, and serial execution inserts. The refusal's probe still sees A's `5`, so validation keeps the refusal (§4.7). The same move reorders a non-parent-prefixed scan relative to keys the program already observed. "Sorts above every key under that parent" does not imply "no observed key changes order."

### N3. Publication states two schedules, and one of them drops the reference prelude — MAJOR — committer §3.2, §6

§3.2 still says a publication member is ordered before any member whose effective time makes that row due (line 160). That publishes every due opening before the member. `advance_time_audiences` publishes one row (`time_audience.rs:114–116`), and §6 says the backlog must not be drained ahead of unrelated members.

§6's own schedule admits the unrelated member while those openings stay behind it. Today every `/q/`, `/m/`, `/sync`, and `/changes` publishes one oldest opening first (`serve.rs:1018–1024`). LLP 3000.036.003 §4 (lines 298–305) depends on that: each request reduces the old backlog under continuous writes, and disclosure does not wait for an application job. §10 keeps that prelude and only then prioritizes the opening a query actually met (lines 590–612). The settle loop in §6 matches that second step. Without the prelude, a sync watermark advances on unrelated commits while the disclosure the reference would already have appended is still private. Sequence numbers stay contiguous. The log below the watermark does not.

### N4. Running presence in place does not keep the lock that orders it today — MAJOR — committer §4.6, §3.1

`connected[p]` is the in-process registry (`runner.rs:1304–1327`). A poll durably sets `_effect_presence.reconnected` and then `presence.enter`, both under `FairMutex<Engine>` (`serve_changes.rs:48–55`; `effects.rs:285–287` says the host calls this under the same lock as emission and claiming). No mutation can observe the map update before that mark commits.

§3.1 removes that lock from durable writes: request threads enqueue and the committer runs the member. §4.6 sends presence-reading members and presence-guarded effects in place and says this keeps today's order. In-place execution is a savepoint on the committer (`§3.4`). It does not hold the serving lock, and `presence.enter` is not specified to move onto the stream. An in-place member can therefore commit the connected branch at a revision before the reconnect mark. That history cannot occur under the lock §4.6 cites. The replay transcript will reproduce it, because presence is injected rather than re-read (`§3.5`), so the oracle does not catch the inversion.

Totals and caps are safe. `apply_aggregate` reads the target row before writing the absolute image (`maintains.rs:586–619`), and `mirror_column` reads the owner row (`columns.rs:78–85`). A later writer conflicts on that value and reruns. `cap_count` by value does the same. `index_head` with no head spanning the whole bound matches an empty walk.

## Small notes

1. `live_session` also kills a read session when `cap_expires_at <= now` (`authority.rs:219–220`). §3.6 names `expires_at` and the claim window only. Action leases are min'd into the action session's `expires_at` at claim (`actions.rs:279`); this cap is not.
2. `QueryOutcome.next_expiry` is an upper lifetime and never carries a hidden opening (LLP 3000.036.003 §4, the sentence before line 349). `B` is wrong if it is implemented as that field alone.
3. §3.4 resolves placeholders after validation; §5 resolves a placeholder that reaches a key before validation. Allocation footprints need one of those orders.
4. §8's adversary still says "predicates at the cap boundary." Caps are value reads now (read-sets §6).
5. A stale or never-live opening commits the private ledger and the clock and takes no public sequence (`time_audience.rs:136–140`). §6's publication member does not say that. UNVERIFIED: whether a query result is ever labeled with a pin later than the `T` it executed with. If it is not, sliding windows on read-only queries stay sound.
