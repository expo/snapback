# Orchestrator's candidate (Claude Fable 5, orchestrating session) — "P9: bounded, traced data programs"

Written blind to the round-1 answers, after reading LLP 0329, 0329.000–.005, 0120,
0155, 0157, 0320's withdrawal, and the retention guide. Attack it.

## 1. Thesis

The three sketches and LLP 0329.005 all assume the property that buys *uniform*
capability is **algebraic closure** — a language small enough that the compiler
can derive the read set from the text. That is sufficient but not necessary. The
properties that are actually necessary are three, and all are weaker:

1. **Deterministic** given `(snapshot, args, viewer)` — no clock, randomness, or I/O.
2. **Traced** — every data access goes through a narrow indexed API
   (`get`, `scan(index, prefix, take)`, `exists`) that records what it examined
   as *index ranges* (including empty/absent ranges), not just rows.
3. **Portable** — the same bytes execute on the server (authority) and the client
   (prediction / offline re-execution).

Given those three, **every** program in the language yields, on every execution,
one artifact — the **trace** — and that one artifact is simultaneously:

| Use | Who consumes it |
|---|---|
| the invalidation predicate (a committed write overlaps a traced range ⇒ rerun) | server |
| the offline closure (the exact rows + ranges the client needs to re-execute locally) | client |
| the authorization witness (rule evaluations' reads are traced like any other) | both |
| the completeness detector (local re-execution that reads outside held ranges is `partial`) | client |
| the OCC validation set for mutations on multi-writer stores | server |

Capability is total because tracing is total: there is no program in the language
that lacks a trace. So "admitted ⇒ live, retained, authorized, predicted" holds
without restricting the language to an algebra. **Static analysis is retained as
an aid, not the gate** — it produces the cost certificate, the index
requirements, and the edit-site consequences — and it works over this language
because of one rule (below): loops iterate only over bounded collections.

This is LLP 0329.004's "fourth architecture" (dynamic read-set recording) with
the piece 0329.004 and 0329.005 both say is missing — the closure — supplied by
shipping the trace to the client. 0329.005 P1's objection ("an arbitrary function
does not describe what data it needs") is true of the *text* and false of the
*execution*: the last execution describes exactly what it needed, and that is
sufficient to re-execute at that snapshot plus the client's own pending writes,
with honest `partial` when the re-execution diverges outside the held closure.
A static closure can do no better: it also cannot manufacture rows the client
never received.

## 2. The language

Spelling: **a TypeScript subset with real control flow**, type-checked by `tsc`
against a custom `lib.d.ts` that simply omits `Date`, `Math.random`, `fetch`,
`import` of anything but the data API, etc. Result types are inferred by TS
(Convex's CV-4/CV-6 win). The compiler (off-the-shelf parser + a lowering of
~30 AST node kinds) emits a small IR; anything that does not lower is a refusal
with a rewrite, never a degraded capability. There is no other semantics for
the IR to disagree with, which is why LLP 0320's failure does not recur: 0320
lifted opaque handlers that already had a *different* execution model
(client-supplied baseline vs. read-to-commit validation); here there is one model.

Admitted:
- `const/let`, `if/else`, `for (const x of <bounded collection>)`, object/array
  literals, destructuring, template strings, arithmetic on i64/f64, UTF-8
  strings with codepoint ordering, `Array` methods (`map/filter/reduce/sort(cmp)/find/…`),
  `Map/Set`, pure helper functions defined in the module (inlined — there is no
  FFI, so there is no opaque boundary for analysis to fail at).
- Data API: `db.get(t, id)`, `db.scan(t.byIndex, prefix, { order, take: N })`
  (`take` required, `N` a literal or an arg with a declared max),
  `db.exists(...)`, and `recurse(seed, step, { depth: D, fanout: F })` for graph
  walks (visited-set, cycles specified).
- Writes (mutations only): `db.insert/update/delete`; modeled values
  `ctx.viewer`, `ctx.now()`, `ctx.newId()` bound at intent time and carried in
  the envelope; the server validates (skew window, id format) and reuses them,
  so prediction and settlement agree on identity and timestamp.
- Row rules: `readable(row => …)`, `writable(...)` in the same language, evaluated
  by the data API on every row it returns and every row a mutation touches.
- Maintained aggregates as **schema constructs** — `count of cards by columnId`,
  `sum of expenses.amount by (groupId, payerId)` — with compiler-generated
  same-commit maintenance (preimage on delete, −1/+1 on group move, declared
  overflow refusal). Reading one is a `get`.

Refused (each with a rewrite): `while`, recursion, unbounded `scan`, ambient
time/random/I/O, aggregates computed by scanning an unbounded population
(→ `take` + count-over-page, or a maintained aggregate), locale-sensitive ops,
dynamic table names.

**The one rule that keeps static analysis alive:** loops iterate only over
`Page<T, N>` values (a `scan` result, or an array derived from one) or fixed
literals. Conditionals can only *reduce* work. Therefore the compiler computes,
lexically, the **shape** (which indexes, which prefixes are args vs. computed)
and the **worst-case examined-entry bound** (product of nested `take`s, plus
`recurse`'s geometric sum), exactly the bound calculus of LLP 0329.005 — but over
imperative code. Refuse at `check` if the bound exceeds the global ceiling `G`.
The *windows* actually touched are dynamic (the trace). That is the
static-shape/dynamic-window split 0329.005 F1 asks for, without giving up `if`.

## 3. The crux, worked

`messages(conversation)` with `messages.readable = m => db.exists(memberships.byConvUser, [m.conversationId, ctx.viewer])`.

Server execution trace for viewer V, conversation C:
- `memberships.byConvUser[C, V]` — point range, present (rule read, memoized once per execution)
- `messages.byConv[C]` desc — range `(+∞ … k50]`, 50 rows, `take` reached
- `users[author_i]` — point ranges for each distinct author (say 4)

Shipped to the client: result + those ranges + rows. Rows inside rule-evaluation
reads that the viewer may *not* read (a rule that consults an `admins` table, say)
are not shipped as rows; the rule's outcome is shipped as an opaque **verdict**
keyed by `(rule, args)`. The client's closure store holds rows, ranges, verdicts.

(a) **Offline `send`.** The client runs the mutation IR locally: insert rule
needs `memberships[C, V]` → held → prediction allowed; the new row's key is
> k50 in a desc index, i.e. *inside* the traced range `(+∞ … k50]` → local
re-execution of `messages(C)` includes it. State `predicted`. On reconnect the
server runs the same IR against current state and settles (same id, same
timestamp — bound at intent time).

(b) **Offline delete of one held row.** Re-execution scans desc from +∞, gets
49 rows, needs a 50th, the scan cursor passes k50 → outside the held range → the
data API returns "range exhausted, incomplete" → the result carries `partial`.
The UI shows 49 rows and a partial marker; on reconnect the server reruns and
ships the refreshed closure. Honest, not wrong.

(c) **Revocation while offline.** Not observable, by information theory; the
client shows `stale` (last authorized). On reconnect, the server's subscription
index has `memberships[C, V]` in this subscription's trace, the delete overlapped
it, so it re-ran → empty result → the closure shrinks → the client evicts rows
held by no closure. Revocation is a trace change, not a subsystem.

Where **static** derivation still wins: prefetching a closure for args the client
has not run yet (a static shape can be turned into a fetch plan without
executing) — but the server can simply execute the query, which is the same
cost; and IVM for algebraic terms. Where **tracing** wins: dependent reads driven
by computed values, arbitrary shaping, and — decisively — no expressiveness
ceiling imposed by the analysis. They **compose**: static shape+bound at
`check`, dynamic windows at run time, and a debug assertion that the windows fall
inside the static shape (0329.005's "cheap insurance" — here it is the same
machinery, not extra).

## 4. Execution substrate

- **One interpreter, written once in Rust**, compiled native for the server and
  to WASM for the client. Same code ⇒ same semantics; no conformance twin, no
  JS engine in the authoritative data path (F-A satisfied), no warm-VM pool. The
  IR is small enough that this is a few thousand lines.
- Effects (`action`s) are ordinary JS with I/O, run in a sandbox *outside* the
  data plane, and may call named mutations/queries. They are visibly a different
  kind.
- Server: subscriptions indexed per `(table, index)` in an interval structure;
  a commit overlapping a traced range reruns the subscription and diffs; rule
  evaluation memoized per execution; SQLite single-writer = trivially
  serializable; Postgres = repeatable-read snapshot + trace-validated OCC at
  commit (Convex's mechanism) — the program runs in the server process near the
  DB, not as one SQL statement (an honest cost vs. an algebra; acceptable for the
  SQLite-first target).
- **Client = closure store + interpreter + outbox**, and nothing else: an
  ordered map per `(table, index)` holding rows within held ranges; a verdict
  cache; the WASM core (interpreter + store + tracer + rebase loop); JS glue for
  transport, persistence (IndexedDB / SQLite / file), and React hooks. Cross-query
  row consistency is free because every query re-executes over one normalized
  store — Zero's outcome — while the store is bounded by traces, never a replica
  (DK-9's intent). Rebase after a local mutation = re-execute active queries
  against store + outbox; anything reading outside held ranges is `partial`.

Implementation alternative **H** (faster to prototype, worse product): skip the
lowering and run the same TS subset in a hermetic QuickJS-in-WASM on both sides,
with the static analyzer as a lint. Same semantics contract, ~1 MB WASM, JS
value-model quirks, "JS in the data plane" in name. I would use it only to test
the thesis in the benchmark, and only if the IR route is judged > 2× slower to a
prototype.

## 5. Worked examples (TS-subset spelling; `// bound:` is what `check` prints)

```ts
// chat
export const messages = query({ conversation: id(conversations) }, ({ db, ctx, args }) => {
  const page = db.scan(messages_t.byConv, [args.conversation], { order: 'desc', take: 50 });
  return page.map(m => ({ ...m, author: db.get(users, m.authorId) }));
});
// bound: 1 rule-read + 51 examined + ≤50 point reads = ≤102; shape: memberships.byConvUser[C,V], messages.byConv[C], users[*]

export const send = mutation({ conversation: id(conversations), body: text() }, ({ db, ctx, args }) => {
  db.insert(messages_t, { id: ctx.newId(), conversationId: args.conversation,
    authorId: ctx.viewer, body: args.body, at: ctx.now() });
});
// insert rule: writable = m => m.authorId === ctx.viewer && db.exists(memberships.byConvUser, [m.conversationId, ctx.viewer])

// Relay boardView — one snapshot, nested, real loops
export const boardView = query({ board: id(boards) }, ({ db, args }) => {
  const board = db.get(boards, args.board);
  const columns = db.scan(columns_t.byBoard, [args.board], { order: 'asc', take: 20 });
  return { board, columns: columns.map(c => ({
    ...c, cards: db.scan(cards_t.byColumn, [c.id], { order: 'asc', take: 100 }) })),
    activity: db.scan(activity_t.byBoard, [args.board], { order: 'desc', take: 30 }) };
});
// bound: 1 + 21 + 20×101 + 31 = 2,073 examined

// Relay boardSummary — exact over a page, or maintained
export const boardSummary = query({ board: id(boards) }, ({ db, args }) => {
  const columns = db.scan(columns_t.byBoard, [args.board], { order: 'asc', take: 20 });
  return columns.map(c => ({ column: c.id, cards: db.get(cardCountByColumn, c.id)?.count ?? 0 }));
});
// schema: maintained cardCountByColumn = count of cards by columnId   → bound: 21 + 20 point reads

// Split ledger — multi-table derivation with an if
export const ledger = query({ group: id(groups) }, ({ db, args }) => {
  const members = db.scan(members_t.byGroup, [args.group], { take: 50 });
  const expenses = db.scan(expenses_t.byGroup, [args.group], { order: 'desc', take: 500 });
  const balance = new Map<string, number>();
  for (const e of expenses) {
    const shares = db.scan(shares_t.byExpense, [e.id], { take: 50 });
    for (const s of shares) {
      balance.set(s.userId, (balance.get(s.userId) ?? 0) - s.amount);
      if (s.userId !== e.payerId) balance.set(e.payerId, (balance.get(e.payerId) ?? 0) + s.amount);
    }
  }
  return members.map(m => ({ user: db.get(users, m.userId), balance: balance.get(m.userId) ?? 0 }));
});
// bound: 51 + 501 + 500×51 + 50 = 26,102 examined — exceeds G=10,240 → check refuses at `expenses … take: 500`
// rewrite offered: maintained `sum of shares.amount by (groupId, userId)` → bound 51 + 50 point reads

// folder ancestors — bounded traversal
export const ancestors = query({ folder: id(folders) }, ({ db, args }) =>
  recurse(db.get(folders, args.folder), f => f.parentId ? [db.get(folders, f.parentId)] : [], { depth: 8, fanout: 1 }));
// bound: 9 point reads
```

Every one of these is live, retained, authorized, and predicted, with no flag.
The Split example shows the design's honesty: the natural code is *admitted by
the language* and *refused by the bound*, with the rewrite being the maintained
aggregate — the same choice 0329.005's type error forces, but the agent got to
write the loop it was going to write anyway and learned the cost at the edit site.

## 6. What this gives up, and the objections I expect

1. **Static reach is a per-program bound, not a closed predicate.** An algebra
   can state "reads exactly `messages.byConv[C]`"; this states "reads
   `messages.byConv[*]` with bound 51" statically and the exact window
   dynamically. Reviewability is slightly weaker; enforcement is identical
   (runtime budget fails closed).
2. **No IVM for loops** — rerun-and-diff bounded by `G`. Maintained aggregates
   carry the exact-over-unbounded cases. Same first lowering codex accepted.
3. **Two-target semantic corners** (number formatting, string order, NaN) —
   closed by the one-interpreter-compiled-twice rule and a deliberately small
   value model; any divergence is a bug in one binary, not a contract mismatch.
4. **Code ships to the client** (queries, mutations, rules) — as in Replicache
   and Zero; secrets cannot exist in the data plane, so nothing leaks but policy.
5. **Trace rows must be viewer-visible** — hence verdict witnesses for rule
   reads over non-visible rows; local prediction against a stale verdict is a
   UI claim, authority rejects it.
6. **Existence side channels via budget refusal** — the same problem 0120 names
   for every aggregate design; the ceiling is a compile-time fact of the plan,
   and refusal messages never carry counts.
7. **"Looks like TS but isn't"** — mitigated by `tsc` against the custom lib (a
   `Date` simply does not exist), and by every refusal carrying a rewrite; this
   is a *strictly smaller* hazard than a builder DSL's, because the agent's prior
   (Convex-shaped code) is mostly inside the subset.
8. **Postgres is program-near-DB, not one statement.** True. SQLite-first.

The most likely way it loses Clique to Convex: not the language — the dev loop
(F-B). Second: a `partial` state surfacing in the UI where an agent expected a
number, and the agent "fixing" it by widening a `take` until `check` refuses.

## 7. P4 vs P9

| | P4 (0329.005) | P9 (this) |
|---|---|---|
| Expressiveness | operator set (nest/group/recurse/maintain) | any deterministic bounded program + same operators as library |
| Row-level `if`/`for` | refused | admitted; loops over pages only |
| Static shape+bound | yes | yes (same calculus, over control flow) |
| Precise invalidation | dynamic windows | dynamic windows (same trace) |
| Offline closure | derived from static shape, then windows | the trace itself |
| IVM | possible for algebraic terms | maintained aggregates only |
| Agent prior | builder/SQL — new | Convex-shaped TS — existing |
| Compiler | builder library or SQL parser | TS-subset lowering (~30 nodes) |
| Postgres | can lower to one statement | program near DB |
| Client | closure cache + IR interpreter | closure store + same interpreter (WASM) |

My claim: P9 dominates P4 on the benchmark axis (authoring prior, composition
ergonomics, inferred types) and ties it on the guarantees that matter (static
bound, dynamic windows, uniform capability, small client), at the cost of
single-statement SQL lowering and algebraic IVM — neither of which the
scale-to-zero target needs first.

## 8. The spike that falsifies it

1. Write the IR (≤ 2 pages) and the data API with tracing.
2. One Rust interpreter; build native + wasm32.
3. Hand-lower `messages`, `send`, `boardView`, `ledger` (maintained), `ancestors`.
4. Run on the server over SQLite, ship trace + result to an in-process "client"
   running the WASM build; apply a local `send` and a local delete; assert
   `predicted` and `partial` respectively; delete a membership; assert eviction.
5. Measure: rerun latency on a 10k-message table; trace size; WASM size.
If step 4 needs a special case per query, P9 is wrong.
