The one material hole is the reverse direction. The RFC promises "Reverse projection validates each actual value under the destination domain," and the patch removes the old whole-domain identical check for `$rename:down` (`store/backfills.rs:296-303`) expressly because "reverse identity never requires a whole-domain inclusion in that direction" — but no per-value destination check replaces it. Concrete case: `amount int 10..100` renamed to `price int 0..1000`, row `price=500`, exact rollback writes `amount=500` into the `10..100` column silently (exact path skips `requires_view`; `check_change` for exact checks only write authority). The existing tests never exercise exact-reverse with a non-fitting actual (the widening CLI test rolls back via the widened view only).

Repair: in `stage_downfills` (or `apply_staged_downfills`), validate each staged patch value against the target table's column type and text constraints — mirroring forward `validate_output` (`store/backfills.rs:943-946`) with `target` — and refuse via `bad.add(id, …)` naming row/column/domain.
