## Verdict: SOUND WITH MAJOR ISSUES

The revision-3 fixes hold: token-fenced renewal, separate graduation stamps, constraint-safe staging, the abort's row check, the committer stream, and child C's fixed denominator of 32. Continuity by evidence is the right shape for the author's rejection of a new incarnation on every promotion. The checkpoint in child A §5.4 does not provide that evidence. It publishes a history it has not witnessed, so a lost suffix — including a revocation — stays in the same incarnation, and a second primary keeps serving when the conditional write does not finish. Takeover's re-read still rests on a queueing claim that §5.1 has already ruled out.

## Findings

### N1. The checkpoint canonizes a history it has not witnessed — FUNDAMENTAL — child A §5.4, parent §3.1

Parent §3.1 (lines 131–149) says a lost failover is dangerous because commits can be refilled under the same sequence numbers and a revocation can vanish without a trace, and that the chain, the asynchronous checkpoint, and device hashes prove continuity. The acquisition check only requires that the database still contain the checkpoint's position and hash (child A §5.4.3, lines 423–427). The owner then advances that checkpoint to the database's own head. Anything after the checkpoint is treated as this incarnation's history.

That suffix is exactly the acknowledged history the check does not cover. The checkpoint is off the commit path, and if the blob store is unavailable it stops advancing while the store keeps serving (lines 413–422). The next sentence, that the checkpoint is at most one interval behind the last acknowledgement, contradicts that paragraph. A promoted replica, or a restore newer than a stalled checkpoint, still contains the checkpoint, passes the check, and the conditional write publishes its head. Lost revisions are then refilled by ordinary new commits. §5.4.4 runs only when the head is behind the checkpoint or a device presents a watermark the chain lacks (lines 438–441). Server-only writes in the gap, which no device watermark covers, match neither test, so there is no loss report and no repair. The checkpoint stores a hash, not the records, so "claims, leases and steps in the lost window are re-derived" (lines 463–465) has no image to derive them from.

Revoked tokens do not stay dead. Revocations, logouts, generation bumps, and credential changes are journaled before acknowledgement (lines 455–462), but the journal is applied only after a detected loss. In the suffix case detection does not fire, so the journal is never read. A revocation at `r+1` after a checkpoint at `r`, lost on promotion, leaves the token usable. Application-level revocations such as removing a member are ordinary writes and are not in the journal at all (lines 466–471). The P1b witness requires this fail-open behavior: blob store unavailable, serving continues, and only authority operations fail as retryable (child A §10, line 824).

Two primaries can both serve. Each database fences processes with its own token; the token does not cross a fork. The only cross-database rule is the conditional checkpoint (line 382). That write is asynchronous, so both sides can acknowledge divergent commits until it lands. If the losing primary cannot reach the blob store, the stated rule is to keep serving, and it never learns that it lost. A failed conditional write and an unavailable blob store are not distinguished.

Device resubmission can apply a retained write once when the receipt survived in the same commit and the server dedupes on the operation id. That interaction with the receipt schema is UNVERIFIED here. It does not cover the refill: a later journal replay, or a resubmit, lands on a chain that has already continued. Exactly-once is not defined between the journal and the device operation id.

What would repair it: the checkpoint has to be a lease. A primary acknowledges a write only while it holds the latest generation, and it stops serving when it cannot refresh; blob unavailability stops serving. On acquisition, before serving, replay the authority journal unconditionally, and do not advance the checkpoint unless this database's chain extends the published hash. A chain that cannot extend it is a different history. A hash alone cannot be the source of the lost records.

### N2. Renewal does not queue behind a waiting takeover — MAJOR — child A §5.1–§5.2

§5.1 says Postgres does not queue a new `FOR KEY SHARE` behind a waiting `FOR UPDATE`, so new fences are granted while takeover waits (lines 253–254). It then says a live owner cannot renew, because a renewal is an update and therefore queues behind that same waiter (lines 261–263). §5.2's guarantee depends on the second claim: the re-read sees a renewal before any termination, so a standby that sampled an expiry as the owner renewed aborts nothing (lines 299–319).

The renewal is an update of a non-key column, so it takes `FOR NO KEY UPDATE`. W8 measured that this does not wait on a held `FOR KEY SHARE`: renewal completed in 0 ms, while `FOR UPDATE` stayed blocked (`experiments/postgres-fencing/README.md`, lines 303–309 and 324–327). A waiting `FOR UPDATE` is not a holder. Under the rule in lines 253–254, the renewal is granted. W8 did not run that interleaving itself (UNVERIFIED as a live trace); it measured the conflict matrix the interleaving follows from.

The race is: step 3's unlocked re-read still sees the expired lease, the owner renews, step 4 terminates token `T`. Step 7 then backs off, after the live owner's backends are gone. Under synchronous replication that abort is the W9 window: the commit can be durable while the client sees an error. The P1b witness that the standby "abandons once it sees the renewal" does not cover a renewal that commits after the re-read.

Before any `pg_terminate_backend`, take a lock the renewal actually conflicts with: a conditional update of `_owner` that changes no data, `WHERE token = T AND lease_until < clock_timestamp()`. Zero rows means abandon with no termination. One row means the owner cannot extend the lease until this transaction ends, and termination is then safe. The prototype's renewal already treats zero rows as loss (`node.rs`, lines 459–469).

## Small notes

- Child B §2 (line 49) still refuses graduation while an effect is `running` or a local completion exists for a non-terminal effect. That is the check round 3 showed misses a handler that outlived `expire_run`. Child A §4.3's drain-until-exit and park-if-ever-claimed is the replacement. `expire_run` clears `claimed_by` and does not clear `attempts` (`effects.rs`, lines 231 and 517), so "ever claimed" has to mean `attempts > 0`.
- Child B §4.3 leaves tombstones in the staging rows until `finalize`, then builds secondary unique constraints over that staging (lines 154–171). A tombstone that still carries `email` will make the `_credentials.email` case this staging exists for refuse a later legal insert. Project tombstones out before constraints are built and while the tail is applied.
- Child A §10's P1b line still requires "persisted database identity with refusal and recovery on promotion" (line 824). §5.4 no longer refuses on an identity change; the same line's later witnesses keep the incarnation. An implementer can satisfy one clause only by violating the other.
- A device can hide a lost suffix by presenting an older watermark than the highest position it has accepted (§5.4.3, lines 432–434). The repair also both re-acquires the device and resubmits retained writes (lines 447–453) without saying that re-acquisition keeps that queue.
