## Round 1 — received review

**Verdict: REVISE.** The selected work should materially help acquisition, and the packet supports implementing these optimizations before adding transport machinery. The revisions below strengthen the bounded plan; they do not require a new service, protocol, or test framework.

The strongest parts are the separation of measured evidence from inference, preserving durable acknowledgement marks as authority, using the existing journal for derived indexes, and recognizing that acknowledgement mutations can have maintained observable effects. The research correctly avoids adding overlapping CPU categories into a savings estimate or comparing unlike PowerSync and Snapback endpoints. The plan also preserves the unmet 30-second objective instead of treating earlier improvements as completion.

Four required changes follow.

1. **Plan §3 and §6.2: test accumulated pending work, not only retained completed history.**

   The proposed index removes repeated enumeration of successful acknowledgement history. However, “visiting pending keys only” and grouping “linear in pending work” specify the cost of one call, not the aggregate cost of draining a backlog. If a call examines all pending identities but grant/FIFO limits permit only a bounded subset to become bound, repeated admission can still visit a decreasing prefix quadratically. This is a risk the plan permits, not a demonstrated defect in the excerpts supplied.

   **Resolving change:** Add an algorithmic control with a large pending backlog and constrained acknowledgement admission/drain, recording identities visited across the complete drain. Include repeated calls while admission cannot advance. Require that unchanged pending work is not repeatedly regrouped or copied without useful progress, or explicitly attribute and bound any remaining repetition. Keep the existing large-retained-history/small-new-page test: it addresses a different failure mode.

   This can use existing diagnostic counters and test files. It does not justify an additional durable index or a general scheduler.

2. **Plan §5, no-tail settlement, and §6: make the eligibility proof and its race controls explicit.**

   The proposed eligibility conditions are appropriately conservative. The remaining gap is when those conditions are established relative to persistence. Matching held/admitted/committed identities is insufficient if the held program, principal, overlay, or coverage authority changes between the eligibility read and the terminal swap.

   The supplied ordinary path includes `coverageRevision`, cancellation, and `commitMany` guards. The new path must retain their force despite removing `logTail` and its intervening checks. It must also avoid treating an old program still retained in `state.programs` as the currently governing receipt declaration.

   **Resolving change:** State that no-tail eligibility is bound to the current partition and governing held program through the terminal swap, either by checking within the serialized owner or by carrying a revision that the swap validates. A failed or superseded swap must leave the same intent replayable and must not publish a durable terminal.

   Add explicit controls for:

   - Eligible empty-effects engine acknowledgement: no tail request and durable settlement.
   - Nonempty maintained effects, missing/malformed effects, missing/mismatched identity, or an authored lookalike operation: ordinary tail behavior.
   - Authority/program or overlay change after eligibility inspection but before settlement.
   - Persistence failure and physical reopen, followed by retry of the same envelope.

   Reuse existing settlement tests where they already cover these cases; make the new branch part of those tests. This is the change with the greatest correctness consequence because it removes an existing settlement prerequisite.

3. **Plan §5, local observers, and §6.4: require deterministic interleaving tests for refresh dominance.**

   “A pending or in-flight semantic refresh dominates an item-only nudge” and “a stale result … must not publish afterward” are good requirements, but the verification list currently tests observable categories rather than the scheduling races.

   The supplied `scheduleRefresh` has one scheduled/in-flight path, a pending flag, and an epoch publication check. Adding two refresh kinds can lose semantic work if an item-only event overwrites pending intent. Conversely, invalidating every semantic refresh on item traffic can repeatedly discard useful work during acquisition. An item-only refresh must also avoid republishing old query data after a newer semantic result.

   **Resolving change:** Add controlled-promise tests for semantic-then-item and item-then-semantic changes while both scheduled and in flight; also test a semantic change during a semantic refresh and an authority/reset transition during either refresh kind. Assert that the latest semantic change is eventually reflected, stale data never replaces newer data, and final item/compaction state is current. Assert progress under a finite burst of acknowledgement item updates.

   Implement this in the existing refresh owner. No separate notification system is warranted.

4. **Plan §6: define the endpoint to which both performance targets apply.**

   Separately reporting complete durable content and all acknowledgements settled is valuable. But “30% lower clean median full acquisition” and “ordinary completion below 30 seconds” still leave room to choose different endpoints when evaluating the result.

   **Resolving change:** Name one primary endpoint before collecting samples. Prefer complete durable content **and** all acknowledgements earned by that acquired fixture durably settled, with ordinary foreground work measured separately. If the intended primary endpoint is content-only, say so and give acknowledgement completion an explicit finite completion criterion. Apply identical definitions to baseline and candidate.

   Retain all attempted runs, failures, and cutoffs. Specify how censored pairs affect the reported comparison rather than silently computing a median over completed runs. The existing ten alternating pairs are sufficient for a scoped comparison; they do not establish p95.

Two suggestions are optional:

- **Plan §4:** The excerpts contain two distinct FIFO comparators: `outboxOrder` includes a `createdAt` tie-break, while `outboxFifo` does not. Pin the projected queued selector to the ordering actually used by the existing `OutboxLedger.queued()` path and include tied/legacy entries in its equivalence test. “Same FIFO comparator” should not be interpreted as permission to unify these functions casually.
- **Plan §§4, 6–7:** Filtering terminal entries before copying can remove substantial allocation while still enumerating terminal history. Likewise, the supplied `compactSuccesses` still enumerates the outbox. Report their residual visit counts if attribution shows them material; do not expand this implementation merely because those loops exist.

I would not request batching or native storage now. The acknowledged history scans, whole-program admission copies, and approximately one unrelated tail query per acknowledgement are concrete, repeated costs. Removing them is a credible substantial improvement. The packet does **not** establish that these changes will reach 30 seconds, and its existing commitment to measure and attribute the residual is the right disposition.

This review advises revision and implementation qualification; it does not accept the plan on the author’s behalf.
