# Round 3 — the Clique gauntlet (part of the round-3 brief)

The Clique benchmark (LLP 0201, M1–M8) is the instrument the founder scores
against. Below are the shapes in it that stress a data-plane language the most.
For each, in the design you now favor, give (a) the code an agent would write
on first attempt (real spelling), (b) the certificate / bound `check` prints,
(c) whether it is a query, a mutation, a maintained aggregate, an effect, an
ephemeral channel, or refused-with-rewrite — and (d) if the agent's *first*
attempt would be refused, the exact diagnostic text. Keep each to ~10–15 lines
of code plus a few lines of prose. Do not skip any; a gap here is a gap in the
design.

1. **M2 Following feed** — reverse-chronological posts from accounts the viewer
   follows, plus the viewer's own posts and reposts (implicit self-follow, not a
   stored edge). Fan-out-on-write vs read-time filtering is the agent's choice;
   show the one your design makes natural and what happens when the viewer
   follows 500 accounts.
2. **M2 Live follow counts** — followers/following counts on a profile, live.
3. **M3 Read receipts and typing indicators** — sent/delivered/read state per
   message per recipient, live; typing indicators (not persisted). Which parts
   are rows, which are an ephemeral channel, and how does the language treat the
   channel (is it in the language at all)?
4. **M3 Deduped DMs** — "start a DM with X" must find or create the unique
   1:1 conversation atomically.
5. **M4 Edit within 15 minutes / delete-for-everyone within 1 hour** — server-
   enforced time windows on a mutation. Where does the clock live?
6. **M5 Disappearing messages** — server-enforced expiry (off/24h/7d) so a
   message stops being readable after its window with no client cooperation.
   The read rule is time-dependent; the language forbids `now()` in reads. Show
   the honest design (rule with a `notAfter` column checked at commit time and
   an effect that sweeps? an authoritative "current time" input that is a
   modeled value with declared refresh?) and its offline/retention consequence.
7. **M5 View-once photos** — the second view is denied server-side; a view is a
   write. Show the mutation and the read rule interplay.
8. **M5 Global message search, available offline for synced messages** — what
   is the search primitive (index kind, operator, effect-maintained table?),
   what does the certificate say, what is retained locally.
9. **M6 Offline compose with queue-and-flush and correct receipt transitions** —
   the outbox, prediction, settlement, and the receipt rows' state machine.
10. **M6 Third-party API** — token auth, list conversations, paginated history,
    send, receive (stream or polling) for a headless client. Is this just the
    generated client over the same named operations, or a separate surface?
11. **M7 Backfilled field** — conversations gain a `messageCount` shown in
    settings, backfilled for all existing chats and maintained forward, with no
    data loss. Show the migration story (maintained aggregate with backfill? a
    one-shot effect? schema versioning?).
12. **M7 Group polls with live tallies and offline-queued votes** — a new
    message type; tallies live; votes queued offline and settled.
13. **M8 Insights** — six lifetime totals for the viewer (messages sent,
    received, media, reactions given/received, conversations) and a 7-day
    activity breakdown by day.
14. **M8 Multi-device offline** — the same account on two devices, both
    offline, both composing; reconnect; what the language and runtime guarantee.
15. **Scale replay (O5)** — a fixture replays ~100k messages across
    conversations through the public API; the certificate's bounds must hold
    and subscriptions must stay live. Where does rerun-and-diff hurt first and
    what is the mitigation (maintained rows, subscription coalescing, IVM)?
