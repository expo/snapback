## New defects

### A. High — An unfinished exit response can block flushing and closing indefinitely

The exit transport retains its active promise until the entire response body finishes, without a timeout or cancellation mechanism: [local-exit.ts:29](snapback4/packages/snapback4/src/local-exit.ts:29).

Ordinary flushing now awaits that promise before proceeding: [local.ts:757](snapback4/packages/snapback4/src/local.ts:757). `close()` aborts ordinary requests but then awaits the blocked flush; the exit request does not use that abort signal: [local.ts:940](snapback4/packages/snapback4/src/local.ts:940).

**Scenario:** A visibility-change send receives headers, but its response body stalls. The page becomes visible again and ordinary networking recovers. Every subsequent flush remains behind `exitDone`; awaiting `close()` also hangs.

The in-memory probe supplied exactly that response:

```text
requestCount: 1
released: false
repeatUsesSamePromise: true
```

Closing the response body released the wait. The write remains durable, but this client has no bounded recovery path. The new overlap regression explicitly releases its held response, so it misses this case.

**Required change:** Bound the exit wait and allow recovery by retrying the same durable head before advancing. Closing the client must not depend indefinitely on an uncancellable exit response.

### B. Medium — W1 terminates an app process it did not start

`execute()` calls `terminate()` before its first launch: [witness.rs:239](snapback4/crates/snapback4/src/verbs/witness.rs:239). That sends `simctl terminate <udid> <bundle>` even while `app_started` is false: [witness.rs:107](snapback4/crates/snapback4/src/verbs/witness.rs:107). Every launch also uses `--terminate-running-process`.

Thus an ordinary instance already running on the selected simulator is terminated. Cleanup likewise identifies the app by bundle, not the launched PID, so it can terminate a replacement instance.

Host-child handling is better: `Owned` retains and checks its `Child`, avoiding signals to a reused PID. The ownership defect concerns simulator app processes, not arbitrary host processes.

**Required change:** Refuse an existing instance and track the launched instance, or explicitly revise the published ownership contract to permit taking over the named app. The fake simulator’s terminate handler is a no-op, so existing tests do not establish this boundary: [witness-simctl.py:25](snapback4/crates/snapback4/tests/fixtures/witness-simctl.py:25).

### C. High — W1 can report success despite a recorded failed step

When `wait_step()` finds the expected milestone, it examines following rows only for another milestone, then sets `consumed = rows.len()`: [witness.rs:185](snapback4/crates/snapback4/src/verbs/witness.rs:185).

A batch containing:

```text
offline-done
check:failed
```

therefore consumes the failure without rejecting it. A later `done` can complete the run. The actual helper produced this sequence in my in-memory probe.

Final collection checks JSON syntax and object shape, but does not revalidate step failures or ordering: [witness.rs:281](snapback4/crates/snapback4/src/verbs/witness.rs:281). A failure or reordered milestone appended after terminal `done` can consequently escape validation too.

**Required change:** Validate every complete receipt, including trailing rows, and validate the complete protocol sequence again before recording success. Add regressions for failure immediately after an expected milestone and invalid steps after `done`.

There is also a smaller helper defect: the object check precedes `JSON.stringify`, so an own `toJSON()` method can replace the entire envelope, bypassing the reserved `witness` key. My probe produced `"not-an-object"\n` from an accepted `receipt()` call: [witness-core.ts:25](snapback4/packages/snapback4-expo/src/witness-core.ts:25). That particular line is rejected during final collection, but serialization can also replace the protocol fields with a JSON object. Validate the serialized envelope or reject custom serialization.

### D. Medium — W1 does not guarantee artifact preservation

The preflight list omits `backend-stdout.log` and `log-stderr.log`: [witness.rs:313](snapback4/crates/snapback4/src/verbs/witness.rs:313). Existing files at those paths are subsequently truncated by `File::create`: [witness.rs:89](snapback4/crates/snapback4/src/verbs/witness.rs:89).

More generally, the existence checks do not reserve the artifact namespace. Two runs using different simulators and ports but the same artifact directory and segment can both pass preflight and overwrite each other’s files. Backend restart also truncates the first backend logs, and app relaunch truncates the earlier launch log.

**Required change:** Exclusively reserve each run’s output namespace, cover every output, and preserve lifecycle logs across restart/relaunch. The added tests do not construct existing-output or concurrent-run scenarios.

## Requested compatibility and boundary probes

- **First-like prediction remains available.** Viewer-keyed likes satisfy the stricter proof. The feeds card’s vote also satisfies its viewer-scoped cap. Existing tests exercise both stores, including the actual feeds-card source: [upsert/mod.rs:80](snapback4/crates/snapback4-device/tests/upsert/mod.rs:80). New covered-constraint/default controls ensure the repair does not simply disable insertion prediction.
- **Following pagination remains available within its envelope.** The private lane pins the viewer, broadcasts are public, and pull discovery pins the reader: [feeds.md:172](snapback4/crates/snapback4-lang/src/guide/feeds.md:172). Existing server and both-store pagination tests cover that recipe.
- **Search across groups remains pageable within budget and the word limit.** The paved `everywhere` recipe pins each room’s rule. Existing tests traverse multiple pages and compare server/device cursors: [search_merge/mod.rs:7](snapback4/crates/snapback4-device/tests/search_merge/mod.rs:7). Non-uniform merges and meter/word-limit cuts now intentionally have no continuation; those cases require a narrower query. The cards disclose this limitation.
- **Publication preserves binary custody.** Copying precedes signing; verification, notarization, version probing, hashing and platform packing all use the private staged binary. Installation checks its digest and signature; publication uses that packed tarball: [publish.mjs:52](snapback4/scripts/publish.mjs:52). I found no recurrence of the shared-Cargo-path race.
- **Simulator selection is explicit and consistent.** An explicit UDID must match an available booted iOS simulator; otherwise exactly one must exist. Subsequent simulator commands use the resolved UDID: [protocol.rs:13](snapback4/crates/snapback4/src/verbs/witness/protocol.rs:13). I found no wrong-simulator fallback.
- **Backend cleanup covers handled exits.** Success, errors and handled interruptions stop the owned backend, with forced termination after the grace period. No handled-path backend leak found.
- **Ordinary launches and physical devices remain inactive.** The native launch constant is simulator-only; absent launch configuration makes the helper return null. Old receipt files alone cannot activate it: [WitnessContainer.swift:6](snapback4/packages/snapback4-expo/ios/WitnessContainer.swift:6).
- **Missing/empty principal artifacts fail.** Video, receipts and device logs require nonzero bytes; final receipts require newline-terminated JSON objects. Those checks are sufficient for missing/empty artifacts, but do not close finding C’s protocol-validation gap.
