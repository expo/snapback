The copy mechanism can work, but immutable columns alone do not establish the authorization invariant the RFC claims. I read the RFC in full and checked the requested code and documents. Nothing was changed.

1. **Blocker — §§2–5: parent lifetime and identity invalidate both readability and the functional dependency.**

   **Scenario:** Issue `p` belongs to org A; comment `c1` captures A. Delete `p`, recreate the same id in org B, then insert `c2`. Both comments have `.issue = p`, but different audiences. B’s recreated issue receives a maintained count including A’s comment. A page pinned by `p` cannot safely use one audience verdict. Current insertion permits reusing a deleted or expired id; maintained columns explicitly preserve totals across parent recreation. See [write.rs](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/engine/write.rs:68).

   Even without recreation, deletion contradicts §2’s “parent exists” semantics. Expiry has the same problem: a public, expiring parent produces a public child that remains available to **new readers** after the parent expires. This propagates through every level of a chain.

   Full unique keys introduce another route: a non-audience unique key can change, then identify another parent, without changing either immutable audience columns or child reference values.

   **Smallest fix:** Choose one lifetime contract. A conservative first version can restrict inheritance to required id references and engine-enforced nondeletable, nonexpiring parents. Supporting surviving orphans requires explicitly naming captured-audience semantics and preserving a permanent identity-to-audience binding; live `readable` semantics instead require ancestor liveness checks and descendant revocation. Do not authorize completeness or count proofs before resolving this.

2. **High — §§3,6: immutable values can change through schema interpretation.**

   **Scenario:** An existing parent physically lacks `visible`, later added as `bool default true`, immutable, with `read <- .visible = true`. A child captures `true`. Changing the default to `false` makes the parent unreadable while its child remains readable. No update violated immutability.

   This is an existing storage behavior: activation leaves defaults unstored, and [materialize_optional_fields](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/schema.rs:1337) interprets missing fields using the current schema. Changing a parent’s read rule to use another column similarly changes every descendant’s required captures, even when their `readable` declarations are unchanged.

   **Smallest fix:** Define a transitive dependency identity covering the expanded rule, referenced keys, input types, optionality and defaults. Refuse interpretation changes while descendants exist, or refill all affected descendants behind one atomic generation change. §6 must cover these changes, not only adding or removing `readable`.

3. **High — §§2–5: hidden copies can disclose private parent fields through sync and cursors.**

   **Scenario:** A child has `read <- allow`, `sync`, and `insert <- readable issues[.issue]`. Section 3 creates the copies for this write-rule term; §4 sends them in every child image. An authorized creator therefore publishes the issue’s private audience inputs to every device. Excluding `$issue.org` from generated types does not conceal it from someone inspecting the wire or device database.

   Boolean read rules can likewise admit a child through one branch while another branch’s copied parent inputs remain private. Putting those inputs in synthesized indexes adds another disclosure route: [cursor encoding](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/cursor.rs:62) is base64url JSON containing key values.

   Existing recorded attribution avoids this by requiring a [public target](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-lang/src/bind/maintains.rs:65).

   **Smallest fix:** Evaluate write-only `readable` terms against the parent without persisting their inputs. Persist and deliver private inputs only when every recipient is proven entitled to them. Define protection across query results, write results, sync and cursors, plus engine-only assignment enforcement; generated-type omission is insufficient.

4. **High — §§2,3,5: mandatory capture contradicts Boolean semantics and creates an existence oracle.**

   **Scenario:** Consider `insert <- not readable parents[.parent]`. For an existing but unreadable parent, capture succeeds and the negated rule admits insertion. For an absent parent, §3 refuses `NOT_FOUND` before evaluating the rule. The writer distinguishes hidden existence, although `readable` should be false in both worlds.

   Similarly, `.author = viewer or readable parents[.parent]` should succeed through its first branch even when the parent is absent. Mandatory capture makes it fail.

   Private lookup costs also need protection: “inside the meter” permits a present hidden parent to consume different heap/probe work from an absent one. The existing [write-target reservation](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/engine/write_target.rs:29) exists to prevent such refusal channels.

   **Smallest fix:** Specify missing/unreadable Boolean results separately from reference-integrity constraints, and give an effect-specific refusal table with uniform reservations before lookup. Define the insertion pipeline explicitly: capture before the first authorization/absence proof for ordinary insert, upsert-insert and if-absent; retain existing captures on update/upsert-patch, with `old`/`next` evaluated after hidden immutable patches are removed.

5. **High — §§3–4: the derivations require the complete rule, not merely an inherited audience.**

   **Scenario:** A comment reads under `readable issues[.issue] and .author = viewer`. Pinning `.issue` does not pin `.author`; issue readers cannot necessarily read every comment. Clearing the disclosure note or declaring the page uniform would be wrong.

   Across three levels, a middle parent might read under `readable orgs[.org] and .owner = viewer`, with immutable `owner`. A grandchild must inherit the middle restriction too. The statement that effective inputs are “the root’s audience columns” is insufficient.

   Also, the claimed local rule class is broader than the sync class. Two membership probes joined by `and`, or two ordinary audience disjuncts, are not invertible by [current sync inference](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-lang/src/bind/schema.rs:293). LLP 3000.007 §6.6 explicitly preserves that restriction.

   **Smallest fix:** Define recursive expansion of the entire rule, preserving every branch, intermediate field, probe key and residual equality. Run existing exact-audience admission afterward. Suppress the maintained-column note only when parent readability implies readability of every contribution; claim uniformity only when all deciding inputs are determined.

6. **High — §4: a functional dependency does not supply the value needed for a safe prefix verdict.**

   **Scenario:** A query pins `.issue = p`, but its prefix contains no `$issue.blocked`. The current [prefix evaluator](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/engine/read.rs:85) constructs its authorization image solely from actual prefix values. Merely treating the copy as “determined” cannot evaluate it correctly.

   For a parent rule `.blocked != viewer`, an omitted copy becomes `null` under [rule evaluation](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/engine/rules.rs:263), making the verdict true even for the blocked viewer. Discovering the value from a first child instead needs a new disclosure-safe protocol for empty groups, denied groups and meter cuts. An aggregate with zero contributions has no child image from which to obtain it.

   **Smallest fix:** Specify an authoritative audience lookup by stable parent identity, or a persisted binding, before selecting child rows. Reserve its costs independently of hidden populations and preserve unknown device coverage. Until that mechanism exists, retain existing non-uniform classification. Adding the hidden field after the reference in an index does not itself pin its value.

7. **Medium — §4: holding a parent is weaker than having current evidence for prediction.**

   **Scenario:** A device retains a parent after leaving its group, then rejoins with a horizon that does not reacquire that row. The parent remains stored but lacks current coverage. A locally expired grant or a provisional parent later refused by the server presents related cases.

   Existing [recorded capture coverage](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-device/src/device/recorded.rs:5) and [provisional authorization](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/engine/read_auth.rs:48) distinguish these states. Ordinary offline staleness is expected; retained or unknown evidence must not become fresh authority.

   **Smallest fix:** Require a live, currently covered parent or a supported provisional dependency, reauthorized on reads and withdrawn through replay when refused. Preserve Unknown under negation. Register the implicit parent read in residency analysis: an online-only parent prevents prediction; a horizon miss queues that call. Parent possession must not prove complete child coverage, secondary uniqueness or cap populations for upsert/if-absent.

8. **High — §6: self-chunking work does not define safe schema activation.**

   **Scenario:** The fill passes child id `m`; an old-generation writer inserts a child with an earlier id and no capture. Alternatively, the fill copies org A while the still-active parent schema permits moving it to B. The job completes with missing or stale captures. A crash, orphan refusal, or simultaneous addition of a maintained count can expose further mixtures of old rules, new indexes and partially filled data.

   LLP 3000.013 §5.2 supplies durable job chunks, not a schema publication protocol. Current [activation](/Users/ccheever/projects/snapback/snapback4/crates/snapback4-core/src/store/activation.rs:59) and LLP 3000.007.001 §3.11 publish derived state and generation atomically.

   **Smallest fix:** Use existing atomic activation initially: fill ancestors before descendants, validate orphans, rebuild affected indexes/aggregates, and publish one generation that forces device reacquisition. Failure leaves the old generation intact. Background adoption needs a separate staged protocol specifying concurrent-write capture, durable progress tied to the candidate schema, restart/abort behavior and atomic final publication.

What is sound: within one stable parent incarnation and schema interpretation, copying all immutable inputs inside the write transaction preserves their equality. Re-evaluating shared `exists` probes preserves membership changes. Immutable references, cycle rejection and independently declared child horizons are appropriate.

A smaller first version would admit one required id reference and one exactly invertible inherited read rule, under an explicit lifetime restriction, while reusing engine-owned capture, device coverage and atomic adoption. Write-rule readability can remain an authorized parent lookup.

**Overall verdict: NOT READY.**
