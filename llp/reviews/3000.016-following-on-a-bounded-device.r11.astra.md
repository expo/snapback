All three revision-10 findings are fixed as design requirements. I found no new material defect or ambiguity likely to make a competent implementation incorrect. This was a static, read-only review; the probes below were traced, not executed.

1. **High — §2.1a: dependent aggregates. Fixed.**

   The fence covers transitions that **write events of the non-fully-synced kind**, including deletions.

   **Probe:** horizon posts, fully sync reposts, and sync `count followingPosts by .actorId`. A mutation that reads its total, inserts an original, then requires an increment must queue wholly without predicted rows; `check` must name the aggregate. Original removal must likewise queue. Reposting a held original changes the fully synced repost kind, so this fence need not stop it: its event write still performs ordinary aggregate maintenance. Reverse the residencies and test unrepost. Making the aggregate `online only` removes this fence, subject to ordinary prediction eligibility.

   This is implementable through the existing [transition classification hook](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-lang/src/bind/timeline.rs:120), with runtime enforcement.

2. **High — §2.1a: activation and retained acquisition. Fixed.**

   Revision 11 explicitly requires transactional filling before assessment/validation, no literal default, and `keeps_literal_default_images == false`.

   **Probe:** upgrade an acquired device containing a live original, an excluded reply, and a repost. Interrupt replacement acquisition before their source pages arrive. Reads must remain unavailable and mutations must queue, rather than treating missing slots as event absence. After publication, their slots must respectively contain true, false, and the existing minted event ID.

   Include an unrelated literal-default column addition in the same upgrade: the slot addition must still force image retention off. The existing [adoption reset](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-device/src/device.rs:505) and acquisition guard support the specified result. The optional-versus-activation-derived representation choice is implementation latitude, not a remaining semantic gap.

3. **Medium — §2.1a: shared sources. Fixed.**

   Slots now belong to each declaration **and source role**, and retirement preserves surviving declarations’ slots.

   **Probe:** two declarations share repost R but mint E and F. Acquire R under a horizon, then unrepost offline: each declaration must tombstone its own ID. Also share posts between declarations with different originals filters; one row must support different live bits. Removing either declaration must preserve the other’s slot and behavior. This matches the existing [dispatch to every matching declaration](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/engine/timeline.rs:58).

The two additional revision-10 observations are also addressed. Preparing slots before the source write avoids a second source update; removal and unrepost retain the old image as their witness. Probe insert-then-body-update and delete/recreate in one mutation: the final source image must carry the correct slots without an extra stamping write. Section 2.3 now names the slot explicitly.

The earlier identity repairs remain sound: [stream serving fetches the current source image](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-core/src/partition.rs:867), and [deferred folding preserves whole row images](/Users/ccheever/projects/snapback-worktrees/review-3000.014-r2/snapback4/crates/snapback4-device/src/device/deferred.rs:116). Neither needs a separate event association that an older raw delete could invalidate.
