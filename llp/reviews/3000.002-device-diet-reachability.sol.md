## Overall assessment

The core S5 implementation is sound for ordinary supported builds: Postgres is the only store that can prefetch; partition accounting and refusal order are preserved while only discarded event allocation disappears; and compiler-produced backends cannot hit the web/native admission divergence because the binder invokes the same admission function.

Two changes are still needed. The supposedly test-only `web-device-check` feature can alter a production native device through Cargo feature unification, and the absence regression test does not examine a real artifact. I found no default-build correctness, durability, or server-authority regression.

### Build and cfg matrix

| Build | Structural admission | Prefetch planner | Partition events |
|---|---|---|---|
| Server CLI, SQLite | Retained per call | Not compiled | Constructed |
| Server CLI with Postgres | Retained per call | Compiled; active only when the Postgres transaction enables it | Constructed |
| Expo native device | Retained | Not compiled | Constructed, then discarded for predictions as before |
| Process device | Retained | Not compiled | Constructed, then discarded |
| Simulator | Retained for server and device | Not compiled | Constructed |
| Wasm web device (`wasm32 + web + !sqlite`) | Removed locally | Not compiled | Construction removed; accounting retained |
| Native `web-device-check` candidate | Server retains it; local devices skip it | Not compiled unless `postgres` is also enabled | Server constructs; local devices skip construction |
| Differential control | Retained | Compiled by explicitly enabling `snapback4-core/postgres` | Constructed |

The gates are at `engine/mod.rs:21-22`, `engine/validate.rs:117-127`, `engine/pages.rs:20-46`, and `engine/write.rs:529-535`. The shipped web command supplies exactly `web`, no defaults, on wasm32 (`scripts/build-wasm.sh:8-10`). Expo uses the default native feature (`snapback4-device/Cargo.toml:13-22`; `scripts/build-xcframework.sh:20-23`).

`target_arch = "wasm32"` does not accidentally select this path for native jobs: the guest SDK has no core dependency (`snapback4-native/Cargo.toml:9-11`), while wasmi is hosted in the native server process. Enabling `web` on a native target does not remove admission; with default features it also retains SQLite events. A native `--no-default-features --features web` build would be a logless memory build, so it retains admission but has no event construction.

### Obligations

| Obligation | Assessment and evidence |
|---|---|
| 1. Only the web artifact changes | **Not literally true.** Ordinary non-Postgres server, Expo, process-device, and simulator compilations also lose the prefetch module because it is now gated solely on `postgres` (`engine/pages.rs:20-46`). Their behavior is unchanged because their `Rows` implementations returned the default `false` (`rows.rs:183-187`). Admission and events remain unchanged in ordinary non-web builds. `web` feature unification alone is safe; `web-device-check` unification is not—see Finding 1. |
| 2. Prefetch | **Correct, with one evidence gap.** Only the Postgres `Tx` overrides `prefetch_enabled` (`engine/postgres/store.rs:229-231`); all other stores inherit `false`. The return/collector plans remain built identically, while only the physical prefetch field and fill calls are gated (`engine/pages.rs:27-46`; `engine/runner.rs:362-368,389-398`). Prefetch has no meter calls and logical reads still own errors/rules/charges. The real Postgres harness did not run successfully, so execution equivalence remains unqualified (`JOURNAL.md:30928`). |
| 3. Partition events | **Correct.** The common function still builds interpreted images and partition sets, validates the id, charges the same steps/maintain work, performs the same replacement scans with examined charges, and keeps the same early exits (`partition.rs:158-235,240-253`). Only `put/del/scope/join` allocation is under SQLite (`partition.rs:128-153,174-180,243-250`). `written`, `read`, `next_expiry`, assets, maintained overlays, effect outboxes, and persisted device changes do not consume `Runner.events`; assets and maintains still follow the accounting call (`engine/write.rs:529-539`). Event allocation itself was unmetered, so no heap/output charge disappeared. The exact public-insert success boundary remains 11 (`device_diet.rs:117-136`). |
| 4(a). Binder equivalence and adoption | **Yes for supported backends.** After residency is established, the binder directly calls `admission::check_detail` and removes every refused program (`snapback4-lang/src/bind/mod.rs:66-71,97-113`). `check`/`dev`/`deploy` therefore cannot emit a program the runtime check would refuse. A generation adopts a complete `Backend { schema, programs }`; it does not combine successor schema with old programs. Raw `Backend` JSON remains publicly deserializable and adoptable without admission, so hand-built, corrupted, or diagnostics-ignored library output is the explicit unsupported path (`snapback4-device/src/device.rs:28-34,255-280,365-407`). Actions do not execute locally; the web has no native-read host. |
| 4(b). Consequences of inadmissible IR | **Real but locally contained.** An unreachable bad scan can now return its valid branch (`packages/snapback4/test/device-diet.test.mjs:16-24`). An inadmissible mutation can spend its local meter, create predicted rows/base images, and commit an outbox entry (`snapback4-device/src/device.rs:684-703,728-769`). Those overlays can be observed by later calls—including another viewer sharing that same local store—but only locally. The server receives the operation and arguments, not predicted rows, and rechecks admission before execution (`engine/mod.rs:797-799`). A successful refusal settlement restores base images, deletes the refused entry, and atomically replays survivors (`snapback4-device/src/device.rs:772-790`); absent a response, the local speculative state can persist offline. It cannot reach another device or durable server state. |
| 4(c). Published behavior and docs | **Yes, the refusals are published.** `guide::CODES` documents both errors (`guide/codes.rs:109-110`), and the programs/bounds cards describe them (`guide/programs.rs:31-45`; `guide/bounds.rs:43-47`). The new prediction card and README accurately disclose the web trust boundary, retained checks, native divergence, and server recheck (`guide/prediction.rs:12-16`; `README.md:622-625`). |
| 4(d). LLP 3000 §7 | **Consistent; no additional author ruling is needed.** The same Rust `Runner`, rules, stores, meters, and value semantics remain. This removes a redundant validation pass for compiler-admitted IR; it does not introduce a host implementation of valid-program semantics. Host Unicode would change valid-program behavior according to the host and therefore needs the separate ruling. |
| 5. Guards and differential | **Useful, not proof-complete.** `checkAbsent` searches demangled symbol names only (`attribute-wasm.mjs:111-121`), so renamed, copied, or fully inlined logic can evade it. A different retaining path cannot evade it if the forbidden symbol survives—the census still finds it and the path is diagnostic. `measure-wasm.sh` fails under `set -e` when the checker detects a symbol or path failure (`measure-wasm.sh:5,14`), but passes on a false negative. The two differential builds are genuinely different: the control enables Postgres, while `web-device-check` changes local admission/events. The 3,452 records and 24 boundaries were compared byte-for-byte (`JOURNAL.md:30916`). However, the test only writes records; it does not compare them itself (`device_diet.rs:73-114`). |
| 6. Documentation and budget | **Accurate and minimal.** The card and README add only the trust-boundary qualification. The measured 444,964 B gzip is rounded upward to 445,000 (`JOURNAL.md:30887-30895`; `metrics/wasm-budget.json:1`). Overruns remain report-only because the helper prints `OVER` without failing (`scripts/wasm-budget.mjs:1-10`). |
| Did the change introduce a new problem? | **Yes:** a Cargo feature intended for the differential can remove admission and event construction from a native shipped device. See Finding 1. Under ordinary documented build commands, I found no new incorrect, slower, less durable, or less safe behavior. |
| Is there a regression test that would pass without its claimed production change? | **Yes.** Restoring the prefetch planner and device event constructors leaves `partition_accounting_keeps_the_step_refusal_boundary` green, and `wasm-absent.test.mjs` tests only synthetic names rather than the built artifact (`wasm-absent.test.mjs:5-18`). The external two-run differential would also remain equal if both modes accidentally compiled the same behavior. The wasm admission regression itself is genuine and was reported red on the baseline (`JOURNAL.md:30920`). |

## Findings

### Medium — `web-device-check` can change a shipped native device

Files: `snapback4-core/Cargo.toml:24-25`, `snapback4-device/Cargo.toml:21-22`, `engine/validate.rs:123-127`, `engine/write.rs:529-535`.

Concrete scenario: build the native process or XCFramework while enabling `snapback4-device/web-device-check`, directly or through workspace feature unification. Load the malformed backend used by `device_diet.rs:13-32`: an empty schema and a query with an unreachable scan of `missing.byId`, followed by `return 7`. An ordinary native device returns `E_UNBOUND_SCAN`; this feature-enabled native shipment returns `7`. A malformed mutation can likewise commit speculative rows and an outbox entry while skipping event construction. The server remains protected, but the native device no longer has its documented refusal behavior.

Smallest fix: do not let a Cargo feature alter production local entry points. Parameterize a differential-only harness or compile the alternate policy under a test-only cfg. At minimum, reject `web-device-check` in production/release profiles so it cannot enter an XCFramework or CLI binary.

### Low — the absence regression is synthetic and symbol-name dependent

Files: `scripts/attribute-wasm.mjs:111-125`, `packages/snapback4/test/wasm-absent.test.mjs:5-18`, `scripts/measure-wasm.sh:14`, `scripts/build-wasm.sh:8-10`.

Concrete scenario: reintroduce event construction under `partition::events` or prefetch under a renamed/inlined module. The web artifact grows and resumes useless work, but the regex sees none of `pages::prefetch`, `admission`, `row_changed`, or `log_events`. The synthetic test still passes, `measure-wasm` accepts the false negative, and the size overrun remains report-only. Restoring the original prefetch/event calls without renaming also leaves the ordinary regression tests green; only the separately invoked artifact measurement catches them.

Smallest fix: bind a real artifact absence check to the wasm qualification path, and supplement symbol matching with stable compile-time markers or source/feature assertions that cannot be defeated by routine renaming or inlining.

## Questions

- Is “only the web artifact changes” meant literally or behaviorally? Literally, it is unmet because every non-Postgres build now excludes the planner. If literal byte scope matters, the planner needs a web-specific exclusion rather than a `postgres`-only inclusion.
- Before landing, can the lead supply the missing real Postgres harness result? The implementation appears semantics-preserving, but the recorded run failed before exercising any Postgres query.
