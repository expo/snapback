## 3. Concerns

**1. MATERIAL — S4.1/S4.3/S6.2: the synthesized-query witness is circularly defined and cannot be constructed.**
`NormalizedDataQueryCoreV1` includes `resolution: {kind, functionId, exportedName}` (`llp/0255-tiny-data-surface-v1-api.spec.md:534-538`), the witness is defined as `normalizedDataQueryId = sha256("snapback:normalized-data-query:v1\n" || JCS(core))` over that core (`:377`), and the synthesized exported name is `<resource>.query_<first 16 lowercase hex digits of normalizedDataQueryId>` with `functionId = {appId}:{exportedName}` (`:852`, `:856-857`). For every `resolution.kind:"synthesized-generated"` template, the witness is a hash over bytes that embed 16 hex digits of the witness itself — a cryptographic fixed point no implementation can produce. The same impossible object is embedded in `semanticInput.dataSurface.queryCatalog` (`:657`) and sorted "by … query witness" (`:661`). The Spec's own no-drift posture ("closed, deterministic, and implementable") makes this a correctness defect, not a nit. **Resolution:** define the witness over the pre-resolution template (exclude `resolution` from the hashed core the way invocation facts are excluded, or move `resolution` into the `DataQueryV1` envelope beside `functionReference`), and state the construction order: template core → witness → synthesized name → resolution record.

**2. MATERIAL — S5.2/S1.2: two closed-grammar terms are undefined and ambiguous over ordinary foreign-key fields.**
The filter grammar refuses "structured or relation fields" (`:731-732`) and the eligibility matrix refuses tables with a "relation-incarnation field or relationship node requirement" (`:181`), but neither term is defined in the document, LLP 0110 (which owns the framework's relation-incarnation stamp — see `schemas/schema.manifest.schema.json:1099`) is not cited or in the Related list, and the corpus supports two readings of "relation fields": (a) only LLP 0110 relationship-declaration fields (stamp + paired FK), or (b) every `v.id(table)` field. The readings diverge materially: under (b), `where({projectId: id})` on an owner-leading index refuses and any table carrying a plain `v.id` field arguably fails eligibility — a large, silent product restriction; under (a) both admit. A contract-bearing admission grammar cannot leave this to implementer judgment, and the divergence would surface directly in the cross-arm byte-identical descriptor/refusal goldens S9 requires. **Resolution:** define both terms in S1.2/S5.2 (cite LLP 0110 for the incarnation stamp), and state explicitly whether bare `v.id` fields are (i) eligibility-neutral and (ii) admissible equality/`in` filter fields.

**3. DETAIL — S10: the familiar-format promotion consequence for predicted operations is left implicit.**
S10 both freezes "prediction/custody facts" on emission (`:1085-1091`) and refuses "unsupported familiar capability" before writing (`:1077-1080`), while separately contemplating semantic rotation ("The semantic id remains only if … byte-equal"). Generated-exact prediction derives from plan-backed generated IR (`generated-mutation-ir.mjs:34-48`; LLP 0155), and the familiar grammar is handler-only with `plan` unsupported (LLP 0253 Appendix A), so `--format familiar` can never preserve prediction for owner CRUD mutations — which all carry IR. The consistent completion (refuse) is derivable, but the Spec should say it, since it renders `--format familiar` effectively always-refusing for v1 owner writes and the day-two evaluation measures promotion. **Disposition:** one clarifying sentence in S10 (dated revision before Phase 1 promotion tooling); a note to the D9 evaluation Plan.

**4. DETAIL — S1.3/S11: the LLP 0253 `.sync()` disposition change rides outside the S3 amendment protocol.**
LLP 0253 Appendix A pins familiar `.sync()` as "profile default **on** … an authored `.sync()` call is admitted verbatim"; this Spec changes that for data tables (authored `.sync()` refuses `SNAPBACK_DATA_RESOURCE_SYNC_PER_TABLE_FORBIDDEN`, and familiar's automatic call must gain a `source:"profile-default"` provenance marker — `:209-215`). This is disclosed in S11 (`:1128-1129`), so it is not a *silent* amendment, and 0254 D11 delegates exactly this enumeration to the Spec; but the Summary's ratification gate covers only "S3 amendments," leaving the 0253/0252-owned adapter change as the one cross-LLP contract change without a dated proposed-pending block or ratification hook. **Disposition:** move the `.sync()` provenance/refusal change (and the shared `.data` table-vocabulary admission) into S3 as a proposed-pending LLP 0253 amendment, or add one sentence stating why S11 disposition suffices for the Draft sibling.

**5. DETAIL — S4.2/S5.4: the derivation of `capabilities.retained` is unspecified.**
The resource core carries `retained: boolean` (`:479`), and S5.4 admits protected retention "only when the exact generated plan/policy and authorized-lease facts satisfy LLP 0243" (`:810-812`), but LLP 0243 retention is an explicit per-query opt-in and the closed `.data` grammar has no retention key — so nothing in the Spec says what makes `retained` true for a tiny resource (presumably constant `false` in v1 absent an external 0243 declaration). LLP 0254 Phase 2 asks the Spec to name the LLP 0065-OQ5 retention admission; the fail-closed capability refusal keeps this safe, but the fact's derivation should be one sentence. **Disposition:** Phase 2 (or a dated S4.2 sentence: `retained` is false in v1 unless a named LLP 0243 admission exists).

**6. DETAIL — S5/S9: the generated `<table>.get` operation has no route from the tiny doorway.**
Every owner/public resource generates `get` (`:144-147`), but the descriptor grammar filters only schema fields on index prefixes (`_id` is a system field and never indexed), `db.tx` has only writes, and the React subpath exports only `db` — so a point-read by id is expressible only by leaving the tiny doorway for the canonical reference surface. That may be the intent (list rows carry `_id`; detail screens use the canonical hook), but the Spec generates the operation and never names its consumption route, which the D9 concept-count would feel. **Disposition:** Phase 1/Phase 4 guide text naming the route (or a dated builder addition); record the concept cost in the evaluation protocol.

**7. DETAIL — S3.2/S7.3: the `intentId` ↔ `clientMutationId` identity is implied, never stated.**
The S3.2 amendment's dispatch projection carries `clientMutationId` (`:320-323`) and keys the durable/observation records by "stable intent id"; the data-facade grammar (S7.3/S4.4) uses `intentId` throughout (`:958-964`, `:617-621`). **8. DETAIL — S4.2/S4.3/S4.4: appId enters the "profile-neutral" normalized cores via `functionId`.**
Core `operations[].functionId` (`:456`), `resolution.functionId` (`:536`), and `chunks[].functionId` (`:581`) embed `{appId}:{exportedName}` (`:856-857`), so the witnesses are app-scoped and the S4.1 exclusion list (`:381-386`) does not name appId. LLP 0253 S5.2 deliberately excluded appId from `NormalizedApplicationDefinitionV1` so equal definitions witness equal across deployments; here, cross-profile equality proofs (Acceptance: "equal explicit/familiar normalized witnesses") hold only at fixed appId. That condition is satisfiable (one app regenerated under each profile) but should be stated — or the appId-bearing ids moved to the envelope, which the M1 fix will touch anyway. **Disposition:** dated revision alongside the concern-1 repair, or a named fixture condition in Acceptance.

**9. DETAIL — S2: the new `public-read.v1` generated read profile's soundness ownership is unnamed.**
LLP 0065 §2 reserves public standard patterns as future profiles requiring their own explicit semantics and negative cases (its OQ2 asks whether they share 0065 "after a separate existence-leak review" or get a follow-on authority), and LLP 0080 owns the existing query-only public-read relation profile. Minor companion: `DataDiagnosticV1` (S7.3) is referenced but never typed (S12 pins the `snapback.client-diagnostic.v2` schema; the alias should be stated). **Disposition:** one sentence in S2/Related naming this Spec as the 0065-OQ2 disposition for read-only public resources, plus the alias sentence in S7.3 or S12.

**C3. DETAIL, IN-DELTA — S7.1b is expressible in the shipped plan machinery, but the worst case exactly saturates undisclosed shipped bounds; the Spec should name them and pin the per-chunk step budget.**
