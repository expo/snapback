**Verdict:** SOUND WITH MAJOR ISSUES

## Direction assessment

This is the right architecture for the stated goal. Snapback 4’s distinctive half is a single Rust interpreter with static authorization, a runtime meter, prediction, and partition sync. Convex already shows that a general-purpose backend can sit on Postgres as a persistence engine while keeping its own query engine, a generic document/index layout, and one committer. The evaluation measurements support the same split here: compiled Quarry, rules, maintains, receipts, and device sync already transfer to Postgres; the inbox’s 68 calls vs a 5-call page is a row-at-a-time access boundary, not a reason to reimplement Quarry in SQL.

Lowering Quarry fragments to SQL would be a worse main path. Meter cuts are defined in interpreter order (`meter.charge` in `read.rs` at the probe, examined-row, and index-entry sites). A cost-based plan that reorders work changes when a query caps, and therefore changes results. The device must run the same programs. A server-only SQL lowering would split the “one implementation, in Rust” bet. The large wins the abstraction gives up are real and correctly named: planner-quality unbounded reports, and write parallelism beyond one committer. The first belongs on projections plus SQL (increment D, still open). The second is deferred until a named workload needs it; the four-writer cells already show a single `_head` row makes disjoint writers irrelevant.

The server half as TypeScript outside the transaction is the right complementary shape. Worker actions already exist with durable admission, a viewer-fenced session, and at-least-once delivery; they lack declared results, routes, and a generated context. Building that on SQLite (A) while making Postgres access batched rather than chatty (C) matches both the goal and the evidence. Postgres is for operator trust, extensions, SQL tools, and later multi-process hosting — not for beating SQLite at 0.02 ms pages on a Unix socket.

What this revision does *not* yet do is earn “chosen consistently over Convex and Supabase.” That claim needs the brief, services, and a managed-service design. A and C can start without those, but they must not freeze contracts that those later pieces cannot live with, and they must not treat §4.2/§4.3 as already proven.

## Major issues

1. **Blocking — §4.2’s “unchanged by construction” is not true of the interpreter as written.**
   Prefetch is specified as filling a cache, then “the interpreter then evaluates exactly as today.” Several read paths are not point-gets of a stored image:
   - Expiring point lookup is a scan that charges `Examined` for expired siblings (`read.rs` 146–162).
   - Maintains over expiring sources recompute in `live_aggregate` / `rule_probe_exists` with further scans and charges (`read.rs` 102–137, 168–200).
   - Hidden rows restore the meter mark and charge one examined row (`read.rs` 300–323).
   - Word matching discovers lanes with repeated `scan(..., limit: 1)` (`read.rs` 412–417).

   A cache of semantic read results (the inbox’s `totals[.room]` and “the probe that totals’ read rule makes”) would skip those loops and change meters, caps, live aggregates, and sometimes results. A cache that `scan` consults could also drop stored keys and change cursors. SQLite’s page cache is not an analogue: it does not return hidden row images to the engine.

   **Resolve before C:** define prefetch as a transaction-scoped physical cache of `Rows::{get,lookup,scan}` tuples (row image plus stored key), filled speculatively after a page fetch. The interpreter still runs expiry walking, live maintains, rule checks, and every `meter.charge`. Qualify on/off as §11.1 says, including an `expire at` maintain and a non-uniform hidden row — not only the non-expiring inbox. Cap speculative keys to the marked sites of the fetched page; a meter cut must not be “implemented” by omitting cache fills that would change later charges (fills may be extra physical work; they must not be extra logical work).

2. **Blocking — §4.3’s long-key overflow is not shown to preserve key order.**
   The access contract is SQLite’s rows in key order (`§4.1`, `§11.2`). Postgres already rejects a 6,000-byte indexed text with SQLSTATE `54000` (`snapback4/experiments/postgres/README.md` 147–151). Indexing a prefix plus hash, as vaguely attributed to Convex, sorts by prefix then hash, not by the full encoded key. Indexing prefix plus suffix still has to fit a B-tree entry. Convex’s on-disk scheme was not readable here (**UNVERIFIED**). Devices already scan one key encoding; a server that returns a different order is a second semantics.

   **Resolve before C:** default to one portable bound, checked by `check` for both stores, and keep the counterexample test. An overflow representation is in-scope only if it is specified as order-preserving under the btree limit and proven against `MemoryRows`. Do not treat “prefix, suffix, and hash” as an equivalent alternative until that proof exists.

3. **Blocking — prefetch cache lifetime is a cross-principal disclosure hole if it rides the pooled client.**
   §4.2 reads hidden rows into process memory and says they are “never disclosed.” Today’s adapter caches prepared statements on `Store` (`store.rs` 41–50, 93–100) and rows only inside `Tx`. A row cache on the connection, or a Tx cache that survives `commit`/`rollback` and is reused for the next principal, leaks hidden images. Debug logs of `= ANY` results do the same.

   **Resolve before C:** cache lives on `Tx`, is dropped on commit and rollback, is never on the pooled client, and is never logged. Prefetch failures stay infrastructure failures.

4. **Major — §6.2 candidates apply authorization after SQL `LIMIT`/`ORDER`.**
   The nearby example takes 50 ids, then the engine returns the visible subset in SQL order, hidden=absent, `complete: false` (`§6.2`). For any table that is not uniformly readable, the 50 nearest projection rows need not contain the 50 nearest *visible* rows. That is the wrong contract for the geo/vector features D is supposed to ship, and it is weaker than LLP 3000.007 §9.1’s per-viewer views (`llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md` 1043–1053).

   **Resolve before D (record the constraint now):** candidates only on uniformly readable sources, or the engine over-fetches until `N` visible rows or a stated bound, or ranked SQL is a declared channel whose prelude is the whole authorization. Do not ship “ORDER BY dist LIMIT N” plus post-filter as nearby-search.

5. **Major — §6.1/§6.2 declared channels plus unfiltered projections are a second, unproven authorization surface.**
   A projection is “exactly its source” at every commit and is not rule-filtered. Channels then return computed values under a `require` the compiler “cannot prove” bounds the SQL. That is an intentional hole in the property Snapback claims against Convex/Supabase. A `project` of private columns plus a weak prelude is a disclosure. Expiry views that use SQL `now()` rather than the interpreter’s transaction clock will also disagree with Quarry on `expire at` tables (`NOT-DOING.md` 33; `§6.2` expiry). Unique indexes on projections are not in the forbidden-DDL list (`§6.1`) and would fail otherwise-valid mutations.

   **Resolve before D:** treat projection tables as sensitive as the source; default SQL reads to candidates; require review plus `check` listing for channels; forbid unique/exclusion constraints, and bind expiry views to the same `now` as the mutation/query. Keep SQL reads gated on the open §14.4 ruling.

6. **Major — increment C as written fights the live scope fence and can freeze a single-tenant layout.**
   `NOT-DOING.md` 56 and 60 still say the Postgres adapter is an evaluation prototype, not a hosted/deployable target, and that CLI/deploy stay off that increment. C nevertheless includes `serve`, `deploy`, and backup on Postgres (`§10.2`). The prototype schema is one namespace with global `_head` / `r` / `i` (`store.rs` 18–28). A managed service was ruled in (`§14.5`) but not designed; database-per-app isolation would let this layout stand, while shared-cluster tenancy would not.

   **Resolve before A/C start:** Moves lines that enact A and the storage slice of C, and a one-line isolation assumption (database-per-app unless a child LLP says otherwise). Do not freeze production `deploy` on Postgres in the same slice as prefetch.

## Changes before increments A and C start

1. Enact `NOT-DOING.md` Moves for A (declared results, generated context, routes/webhooks, schedules, `serve`, one work lifecycle on SQLite) and for C’s *storage* slice (prefetch, write flights, long-key decision, corpus/simulator/device on both stores). Leave projections, SQL reads, `ctx.sql`, and managed-service tenancy off both lanes.
2. Tighten §4.2 as in issues 1 and 3; make those tests part of C’s first evidence, including expiry and hidden rows.
3. Lock the long-key default (issue 2) before changing the Postgres layout.
4. A’s generated `ctx` must not grow `ctx.sql`. Specify the principal for scheduled actions (service seat; they must not inherit an expired caller). Keep the existing separate-process worker claim protocol (`actions.rs` 21–39, 51–58); do not pull TypeScript into the core process.
5. Narrow C’s first cut to the access boundary and dual-store suites. Measure inbox/page after prefetch against SQLite 0.138 / 0.0248 ms and the 0.082 ms join (`experiments/postgres/README.md` 96–109) before `serve`/`deploy`/backup. State the commit-rate number C is judged against; the experiment’s ~2.5k Postgres vs ~14–15k SQLite ops/s is the current cell, not a target.
6. The lead can write the brief in parallel, but the first brief *run* should be after A can execute invitation and webhook journeys, and **without** SQL reads — that is the measurement LLP 3000.007 §10.3 still needs. Pin the brief’s deployment shape (published `dev`/self-host vs Convex/Supabase cloud) so operations losses are not misread as data-plane failures.

Do not wait for D, for a managed-service LLP, or for lowering Quarry to SQL.

## Lesser concerns

- Residual Postgres cost is not only the 68-call loop: a rule-filtered point read is already 5 calls and ~20× SQLite (`experiments/postgres/README.md` 96–100); JSON `r`⋈`i` (`store.rs` 206–209) remains after prefetch.
- `Rows` has no batch/prefetch/write-flight (`rows.rs` 130–145); C must extend that contract and keep `put`’s per-key executes (`store.rs` 228–246) from becoming the new 18-call floor.
- Group commit does not remove `_head` `FOR UPDATE` (`store.rs` 61–64, 146–148); document that multi-process scale still serializes writers.
- Online invalidation is still whole-table (`client.ts` 362–364); do not build read-set overlap in A or C.
- Prefetch can physically read a full page of nested keys the meter later refuses; acceptable on self-host, not a resource model for a shared managed service (experiment README 161).
