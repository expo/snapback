## New fundamental and major findings

### N1. The continuity guarantee is defeated by the adapter's own statement timeout: a canceled synchronous-commit wait returns a successful COMMIT the standby may not have — MAJOR — child A §5.4 (`:330-345`), §5.2 (`:286-295`), §8; `engine/postgres/mod.rs:103,147`

The guarantee has three parts: `synchronous_commit = on` per transaction and refused if lowered, a verified synchronous standby at every renewal, and provider fencing (`:332-338`). None of them sees the failure that actually happens when a synchronous standby lags or is absent. In Postgres, a backend waiting for synchronous replication that receives a query cancel issues a WARNING, stops waiting, and completes the COMMIT successfully; the transaction is committed locally and visible, and the client gets a normal commit acknowledgement. The server's own comment on that branch says the client "is entitled to assume that an acknowledged commit is also replicated, which might not be true." `statement_timeout` raises exactly that cancel, and it governs the COMMIT statement. The adapter sets `statement_timeout = '5s'` at session level (`mod.rs:147`, and `SET LOCAL` at `:103`), so today every COMMIT that waits more than 5 s on a standby is canceled, acknowledged to the engine, and acknowledged by the engine to its HTTP client. The three-part check still passes throughout: `synchronous_commit` is still `on` and `synchronous_standby_names` is still non-empty, which is a configuration fact, not a liveness fact. A standby outage therefore silently converts the store to asynchronous replication for its duration, and a primary failure that follows loses acknowledged history under the same incarnation, which is the §3.1 hazard the guarantee exists to exclude. Under (0) or (a) one canceled wait covers a whole batch. The P1b witness "promotion on one synchronous managed provider, which keeps it" (`:652`) runs with a healthy standby and cannot expose this.

Evidence. The prototype's W9 recorded the termination twin of this message, `canceling the wait for synchronous replication and terminating connection`, with the detail that the transaction "has already committed locally, but might not have been replicated" (README `:342-344`, `:354-360`). The cancel twin, which keeps the connection and returns success, is from Postgres's `SyncRepWaitForLSN` query-cancel branch; UNVERIFIED by a run on this checkout, since the server binary lies outside the directory I may search.

Direction. Make COMMIT uncancellable by the adapter: `statement_timeout = 0` in effect for the COMMIT statement, with the per-statement timeout applied to the other statements. Treat the WARNING on COMMIT as "guarantee lost" and fail closed: stop acknowledging, wait until the standby's flush position passes the commit's LSN, or mint a new incarnation as §5.4 already does for a failed guarantee. Verify the standby's state, not its name: `pg_stat_replication.sync_state = 'sync'` and its lag, at every renewal (UNVERIFIED whether the serving role sees those columns without `pg_read_all_stats` on each provider; the fencing README `:385-391` says the role does not need it, but that was for fencing only). State why W9's termination case is safe for continuity: a commit terminated while waiting precedes the takeover in WAL order, and the takeover's own synchronous commit cannot be acknowledged until the standby has flushed everything before it, so nothing the new owner serves is unreplicated, provided the takeover commits synchronously and the new owner serves nothing before that acknowledgement. Finally, note which deployments this covers: Postgres-level synchronous replication (self-hosted, Patroni-style, RDS Multi-AZ clusters). Block-level replication (RDS Multi-AZ instances, Cloud SQL HA) has no such wait, and there `synchronous_standby_names` is empty, so the second bullet's configuration check would wrongly fail on the design's own first-class configuration; the "provider's documented quorum" branch is an attestation, not a check, and should be labelled as one.

### N2. (a)'s internal revision has no stated assignment; a commit-ordered one is another flush-spanning hot row for every non-head write, and a non-ordered one makes validation unsound — MAJOR — child A §6.3 items 1, 3, 4 (`:419-448`), §7.2 (`:551-556`); parent §3.3 (`:218-227`)

Item 3 validates a mutation "against every durable write with internal revision in (S, current]" and item 1 labels S "with the internal revision read inside that snapshot." That interval is only meaningful if revisions are assigned in commit order, so that everything at or below S is visible at S and nothing above it is. Today that order comes from every durable authority write taking `_head FOR UPDATE` and holding it through its flush (`engine/postgres/authority.rs:105-114`: "every durable authority mutation joins the shared commit order"). Revision 2 removes the head from non-head writes, since §7.2 updates `_head` "once per batch" under (a), and says instead that every durable write "takes the next internal revision" (`:441-444`). It does not say from what.

- If from a counter row locked until COMMIT, every mint, invalidation, claim, renewal, step, receipt-only report, asset view and time-audience pin holds that row across its own flush. The aggregate rate of non-head writes is then about `1/(RTT + flush)`, and batch commits queue behind them. Under synchronous replication the flush is milliseconds, so that is hundreds per second for all identity and work traffic combined. It is the `_head` hot row again under another name. The 15,700/s commit-stage bound (`:478-480`) was measured with no such contention (commit-path README `:333-361`).
- If from a sequence, revisions are not commit-ordered: revision 9 can be in flight while 10 is committed; a snapshot labelled 10 later never sees 9's footprint in (10, current], and the serial image is broken. §6.3 sets `nextval` aside for the public order on exactly this ground (`:505-510`).

Direction. Choose one of two designs and state it. (i) Every durable write goes through the committer's batch stream, as Convex does and as P2 already says ("commits go through one committer", parent `:252`): the revision is the batch position, the fence is taken once per batch, and mints and claims become committer-submitted operations with batch latency. (ii) Keep independent non-head transactions and validate by MVCC visibility instead of a counter: label S with `pg_current_snapshot()`, record `pg_current_xact_id()` in each footprint, and treat a footprint as a conflict when its xid is not visible in S. That needs no counter and no serial section, and commit order becomes irrelevant to validation; on SQLite the single writer makes the counter free, so the seam can differ per adapter. Either way, add the non-head write rate to S1a's cell; the "clock-row contention cell" (child C `:246`) is the nearest existing one.

## Small notes

1. **"`FOR KEY SHARE` … then blocks new ones" is not how Postgres queues** (child A `:234-236`). A `FOR KEY SHARE` request on a row locked only by other key-share holders does not sleep and does not join the tuple-lock queue, so a waiting takeover `FOR UPDATE` does not stop new fences from being granted; each new holder restarts the waiter. Safety is unaffected, since any fence granted before the token flips reads the old token and is ordered before the takeover. Liveness rests on steps 3 and 4's termination and on the owner's renewal, which does queue behind the waiter and so cannot extend the lease. Correct the sentence and add a witness with a live owner that keeps opening fenced transactions and reconnecting during takeover; W5's slow-clock owner was alive but did not reconnect.
2. **Step 3 drops the token bound the prototype has.** The RFC's step 3 terminates every same-role blocker "with an owner tag" (`:263-268`); the prototype's blocker watcher also requires the tag's token to be no newer than the one observed expired (`experiments/postgres-fencing/src/bin/node.rs:257-261`). Without the bound a slow standby kills a newer owner's in-flight transactions during a race. Carry the bound into step 3 as step 4 has it, and run the two-standbys witness the prototype left open (README `:482-484`).
3. **The control-data functions are PUBLIC on vanilla Postgres 16.** `pg_control_system()` and `pg_control_checkpoint()` are absent from the `REVOKE … FROM public` list in `~/tools/pg16/usr/share/postgresql/16/system_functions.sql:613-723`, so the UNVERIFIED at child A `:326-329` is resolved for vanilla, not for providers. `pg_walfile_name(pg_current_wal_lsn())` exposes the timeline with no privilege at all and is a fallback where a provider restricts the control functions.
4. **The production label effectively waits on P1c.** Parent §7 asks whether P1 is enough to call Postgres a production target (`:351-353`), while §3.3 rules out shipping on the lock-first reference (`:244-245`) and S0 puts (0) at 1.3× that reference. Say that the label depends on (a) landing, or on the author restating the bound, so P1b is not read as the production milestone.
5. **Two S0 numbers are over-read.** Parent `:192-194` calls H1 "the largest" structural limit, while child C `:108-109` names H3 as the one most likely to put Snapback below every control; drop "largest" until W6 runs. The fired rule row cites 150–200/s as the best batch size "meeting §6's write SLO" (child C `:226`), but at N=32 the measured p99 is 433 ms against a 100 ms SLO (README `:313-316`); the SLO-qualified N is smaller and the rule still fires. Parent `:201-203` gives SQLite's flush as 20 µs, which is Postgres's `fdatasync`; cell 5 measured SQLite's at 77–79 µs (`:436-437`, `:485`).
