## Major

**M1. The B1/B2 boundary is inconsistent, and B1 as stated already needs B2's mechanism (§1, §3.5, §4, §6; questions 3 and 4).** §1 and §3.5 say folding guarded setup and finish is B2. But §6's arithmetic reaches B1's 8 only through RT5, which is exactly that fold: after RT3 the mutation is 16 (1 ingress + BEGIN, fence, head, generation, authority, 2 SAVEPOINTs, 2 reads, 1 write, RELEASE, tail, RELEASE, SET+COMMIT = 15), and only folding 15 into 7 gives 8. So "B1 is reached by removing repeated work" is not true for mutations; the honest structural budget is 16 for a mutation and 6 for a read. Either move RT5 into B2 and set B1 = 16/6, or declare that B1 includes the guarded folds and move §3.5's correctness constraints into B1. As written, "B2 waits for B1 and for the S1 cells measured at B1" measures a B1 that does not exist.

**M2. §3.5/§3.6 name a transport mechanism the project's own evidence and driver decision rule out (questions 3, 4).** §3.6 relies on tokio-postgres extended-protocol pipelining. Three facts cut against it:
- Parent §8: "The synchronous `postgres` crate stays for P1" (`3000.009.001.000` line 2308), and the adapter depends on `postgres = "0.19.14"` only.
- The adapter's own comment at `engine/postgres/tail.rs:58`: "Synchronous postgres cannot pipeline independently prepared calls."
- S1b measured extended-protocol pipelining stalling over the real SSH path: k1 20/s and k3p 25/s against a 295/s baseline (`experiments/postgres-commit-path/README.md:968-978`). The k_exec = 2 result came only from the k3 form, one SimpleQuery message per flight containing BEGIN plus EXECUTE of prepared statements.

The RFC must choose the flight mechanism explicitly. Two viable ones: (a) SimpleQuery multi-statement messages, which the sync driver supports and whose "error stops the rest of the string" semantics give §3.5's guard for free if the fence raises, but which return text-mode rows and need SQL-literal or `EXECUTE`-literal arguments, colliding with §9.1 rule 5 (typed arguments); (b) attach-installed envelope functions (a plain SQL/PL/pgSQL `sb4_open(token, store_id, digest, now, revision)` returning seq, generation and authority facts), which is one typed extended-protocol exchange, satisfies rules 5 and 6, raises on token mismatch natively, and is not a second executor because it lowers no program. (b) is the better answer for setup; finish still needs (a) or stays at two waits (typed tail, then SET+COMMIT). Either way §3.5's "the fence is written to raise" needs a named construct, since `SELECT ... FOR KEY SHARE` returning zero rows raises nothing.

**M3. Keyed mutations are unmeasured and unbudgeted, and the replay-hit path loses its only authority check (§2, §3.1, §4, §6; questions 2 and 3).** RT-A sent no operation ids ("there is no keyed `_ops` receipt/replay cost in these measurements"). First-party clients send them (committer §11 question 4). A keyed mutation today adds: a preflight replay snapshot (`serve.rs:1177`), a second replay snapshot inside `Engine::mutate` (`engine/mod.rs:946`), the in-transaction recheck (`engine/mod.rs:963`), the receipt inserts before member release, and when `store_id` is sent, an `intent_store` snapshot at both `serve.rs:1176` and `:1417`. That is on the order of 10 more exchanges on the common path, two of them the kind of duplicate snapshot this RFC exists to remove. Add a keyed class to §4 and §5, and an increment that keeps exactly one replay check, inside the durable transaction after the authority statement. Also: a replay hit returns at `serve.rs:1192` and never reaches the executing writer, so today its freshness rests on the `serve.rs:1172` check §3.1 removes. §3.1 must say where a replay hit's final check lives; the clean answer is to drop both pre-transaction replay checks.

**M4. The Postgres ratchet is cluster-gated, so it does not guard landings (§5; question 5).** Parent convention: database-dependent cases are named ignores without a private cluster. The per-landing regression guard is therefore the SQLite statement ratchet, which §5 mentions in one line. Make that explicit and mandatory, record both tables, and extend the classes to keyed mutations and the refusal paths. Counting unit: once flights fold, count driver calls (with the sync driver one call is one flight), not statements; `Store.calls` (`engine/postgres/store.rs:81`, `:96`, `:357`) already counts exchanges that way and can seed RT0.

## Minor

- **§3.1/§7 undersell freshness.** Every Postgres identity write takes the head fence (`IdentitySource` → `WriteMode::Serialized` → `_head FOR UPDATE`, `lifecycle.rs:158`, `store.rs:173`; metadata writes `require_serialized_head_fence`). An authority statement after the head lock therefore cannot be overtaken by a revocation before COMMIT. "The same race as today" is pessimistic; the in-place race closes.
- **Ingress for `/m/` resolves on the writer.** `principal_with_owner` resolves non-detached requests on `lock(&shared.engine)` (`serve_identity.rs:86`), so today's ingress check is a queue wait too. §3.1 should put ingress on a reader connection.
- **§8 cites "parent H2's rule".** H2 lives in LLP 3000.009.001.002 §3, where falsification is 2× and the §8 decision rule is 3×. Cite the right document and pick one bound.
- **B2 read budget.** W2 can reach 2 flights without lowering (room is an argument, so membership and page addresses are known). W1 cannot: the membership address comes from the fetched row. §8's "scoped first to reads" should say the composed-query question is about data-dependent chains like W1. Open question 3 closes itself under folding: BEGIN and ROLLBACK ride in the flight.
- **RT3's dependency on K0-Q.** The queue slice is only ordered in committer §3.7, not designed. RT3 is the largest saving (38 → 16) and works under today's `FairMutex` with the check inside the durable transaction. Waiting costs more than doing the admission-point move twice.
- **§3.4 on Postgres.** The tail writes no `_change_evidence` (`tail.rs:62-76`), so the "exact evidence it wrote" is unknown today. Carrying is still right; name the parity item so the carried value is not mistaken for evidence.
- **Facade surface.** K0c's `MemberTx` exposes no authority reads; the in-transaction final check needs a typed authority method on the Program member's facade, as K0d added for Direct members. On SQLite, the `_read_sessions` flag cached at attach must update on lazy install (LLP 3000.033 §1.3).
- **§1/§10 "stay at 57 under K3/K4".** Committer §3.6 already reads admission facts inside S, so pre-execution would collapse the four resolutions on its own. The RFC's value under K3/K4 is the response heads, post-commit re-reads and folds. The conclusion stands; the sentence overstates.
- **Locality.** Say that the budget's value scales with RTT: a co-located Unix socket (0.05 ms) is the self-hosted lever, same-zone placement the managed one, and neither substitutes for the budget on managed Postgres, which is the target.

## What holds

- **Question 1.** The envelope is 43 of 57 and the program is 3. The K3 arithmetic (1.13×) is RT-A's and is right for in-place batching. The conclusion that the envelope needs its own work under both paths is correct.
- **Question 2.** Cutting four resolutions to two is sound. The ingress check never authorizes; the final check sits inside the snapshot the outcome depends on, which on Postgres is strictly fresher than today (today's route check precedes the query snapshot). Nothing semantic relies on the removed checks except the replay-hit path (M3); `release_requests::stamp` on failure is telemetry; the ephemeral path does its own checks and is out of the four classes.
- **Question 6.** The fence stays the first statement after BEGIN in every fold; SQLite's ownership and transaction modes are untouched; the single authority SELECT is bounded, totally ordered and NUL-safe (digests are hex). Rule 5 is the one §9.1 rule a chosen fold mechanism can break (M2).
