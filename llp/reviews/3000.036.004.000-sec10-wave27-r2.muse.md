## Material issue 1 (blocker): scoped role-grant exemption is probe-dependent, not structural

§11 is unconditional: "Positive approvals and scoped or global role grants are never exempted by this rule." But [write_intent.rs:55](/home/ccheever/projects/sb4-b26-sec10/snapback4/crates/snapback4-lang/src/bind/security/write_intent.rs) excludes a literal-default column only if `roles.contains(column)`, and `authority_fields` ([write_intent.rs:38-44](/home/ccheever/projects/sb4-b26-sec10/snapback4/crates/snapback4-lang/src/bind/security/write_intent.rs)) builds that set from `role_columns` — which [privilege.rs:125](/home/ccheever/projects/sb4-b26-sec10/snapback4/crates/snapback4-lang/src/bind/security/privilege.rs) deliberately clears for scoped (composite-key) tables — plus columns pinned by a `String`/`Bool(true)` literal in some `Exists` rule. A scoped roster whose role column is never probed with a literal (e.g. `read <- exists members[team=.team, principal=viewer]` with no role check, invariant `members.role write only`, `role: enum(...) default 'admin'`, hardcoded `insert members {role:'admin'}`) gets a `security_literal_defaults` entry, so [executed.rs:162-166](/home/ccheever/projects/sb4-b26-sec10/snapback4/crates/snapback4-lang/src/bind/security/challenges/executed.rs) exempts the exact-site insert and `policy()` admits it — a hardcoded admin grant passes with no static question either (no edit arm, no table-guard). The existing regression test only covers the probed shape, so it cannot catch this.

Fix: seed `authority_fields` structurally — include `role`/`kind`-named columns on tables carrying a composite unique key with a `Principal` member (the `named` set [privilege.rs:110](/home/ccheever/projects/sb4-b26-sec10/snapback4/crates/snapback4-lang/src/bind/security/privilege.rs) before the global-clear), rather than relying on literal probes. Add the unprobed-schema counterexample above as a second regression test next to `scoped_membership_authority_is_not_default_initialization`.
