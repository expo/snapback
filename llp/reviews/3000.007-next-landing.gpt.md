**1. High — presence-controlled effects consume IDs belonging to later rows.**

Locations: [presence.rs:130](snapback4/crates/snapback4-lang/src/bind/residency/presence.rs:130), [presence.rs:156](snapback4/crates/snapback4-lang/src/bind/residency/presence.rs:156), [runner.rs:270](snapback4/crates/snapback4-core/src/engine/runner.rs:270).

Using the synced, public `notes` table from the presence tests:

```quarry
mutation probe(p: principal):
  if not exists connected[p]:
    emit notify { p }
  row = insert notes { n: 1 }
  return row.id
```

Start with no notes and supply IDs `["A", "B"]`. In the server world where `p` has zero connections, the effect consumes `A`; the inserted row and result use `B`. The device reads `p` as connected, skips the effect, and predicts row/result `A`.

The classifier admits this: the presence-controlled arm contains only an emit. But emit calls the same [`Context::mint`]( snapback4/crates/snapback4-core/src/engine/mod.rs:111) used by `new`. Dropping the device’s effect outbox does not undo ID consumption. Prediction replay also reuses this ordered ID supply.

Smallest fix: separate effect ID allocation—including `new` inside effect payloads—from row/result allocation. Until that isolation exists, classify affected paths as `never`.

**2. High — emitted computations can cause presence-dependent refusals and roll back rows.**

Locations: [presence.rs:157](snapback4/crates/snapback4-lang/src/bind/residency/presence.rs:157), [runner.rs:576](snapback4/crates/snapback4-core/src/engine/runner.rs:576), [local.rs:69](snapback4/crates/snapback4-core/src/engine/local.rs:69).

```quarry
mutation probe(p: principal):
  insert notes { n: 1 }
  emit notify { ratio: 1 / connected[p] }
```

With an empty notes table and zero server connections for `p`, this is classified eligible. The device evaluates `1 / 1` and predicts the note. The server evaluates `1 / 0`, raises `E_DIV_ZERO`, and rolls back the note through [mod.rs:795](snapback4/crates/snapback4-core/src/engine/mod.rs:795).

The same omission covers overflow and other failing builtins. Presence-controlled execution also changes meter consumption: an additional emit/payload evaluation can cross a ceiling in one presence world while the device succeeds. The current analysis recognizes explicit `require`/`check`, but these implicit refusal paths are also sinks.

Smallest fix: treat potentially failing presence-dependent evaluation and resource consumption as refusal dependencies; retain `never` wherever safety cannot be established. Simply skipping payloads on the device would not prevent incorrect row predictions when the server rejects them.

**3. Medium — expression-block setup bypasses mutation population admission.**

Locations: [control.rs:115](snapback4/crates/snapback4-lang/src/bind/program/control.rs:115), [control.rs:122](snapback4/crates/snapback4-lang/src/bind/program/control.rs:122), [admission.rs:178](snapback4/crates/snapback4-core/src/engine/admission.rs:178).

Given public, synced notes with no population cap:

```quarry
fn visit():
  for r in notes first 1 by byN:
    update notes[r.id] { n: r.n }
  return true

mutation probe():
  if visit():
    return true
```

With two notes, the baseline rejects this predicting loop because the selected group has no schema cap. At IMPL_COMMIT, the helper expansion is inside the condition’s `Expr::Block`. Population admission visits the `if` arms, not its condition setup, so it misses the loop and accepts the program; execution updates one note.

The earlier scan traversal still enforces plain/uniform scans, but it does not replace the completeness check in [admission.rs:265](snapback4/crates/snapback4-core/src/engine/admission.rs:265). Putting `visit()` inside an emit payload has the same bypass.

Smallest fix: make both admission’s binding collection and execution traversal descend into expression setup, including conditions and payloads, before introducing these wrappers.

**4. High — a lost page still claims completeness when its scan is shorter than `take`.**

Location: [read.rs:646](snapback4/crates/snapback4-core/src/engine/read.rs:646).

Run the existing [`interrupted`]( snapback4/crates/snapback4-sim/tests/common/helper_pages.rs:76) query with `c = null` and **four** fixture rows:

```quarry
query interrupted(c: cursor ?):
  result = []
  for i in items[] after c last 5 by byN:
    result = result + [{ id: i.id, n: i.n }]
    break
  return result
```

The scan obtains four rows; the collector returns one. Ownership analysis correctly rejects the collector’s continuation, but `filled` is false and `next` is absent. Consequently, `page_position_lost()` returns false and both hosts report `complete: true`.

There is another escape: an owned page elsewhere in the returned record makes `self.page.is_none()` false, masking a lost sibling page. Unknown field origins are omitted by [pages.rs:113](snapback4/crates/snapback4-core/src/engine/pages.rs:113).

Smallest fix: track loss through each returned page’s collector/provenance, including interrupted short pages and lost siblings. The presence of one owned page cannot certify every returned page.

**5. Medium — an exhausted, fully consumed scan becomes spuriously incomplete.**

Locations: [read.rs:637](snapback4/crates/snapback4-core/src/engine/read.rs:637), [read.rs:646](snapback4/crates/snapback4-core/src/engine/read.rs:646).

```quarry
query total(c: cursor ?):
  rows = items[] after c last 5 by byN
  return count(rows)
```

With exactly five public synced rows and `c = null`, the scan exhausts the population and returns all five to `count`. There is no continuation to lose. Nevertheless, `filled = true`, the scalar result has no page owner, and the new predicate changes completeness to false. With four rows, it reports true.

Smallest fix: distinguish a completely consumed scan from an interrupted or untransported collector. A full scan alone is insufficient evidence of position loss.

**6. Medium — the binder wrapper changes meter outcomes and error sites.**

Locations: [control.rs:122](snapback4/crates/snapback4-lang/src/bind/program/control.rs:122), [runner.rs:369](snapback4/crates/snapback4-core/src/engine/runner.rs:369), [runner.rs:400](snapback4/crates/snapback4-core/src/engine/runner.rs:400).

```quarry
mutation probe():
  if true and true:
    return 1
```

With a steps ceiling of 10, the baseline’s lowered execution consumes 10 steps and succeeds. The new execution consumes 11 because the wrapper itself charges a step, producing `E_BOUND`.

Setup also now runs under the hard-coded `"where"` prefix. Errors arising in different mutation conditions or effect payloads can therefore acquire identical `where:…` sites instead of their former operation paths. Ordinary variable scope and setup ordering remain intact; meter/refusal semantics do not.

Smallest fix: make this analysis-only grouping transparent to metering and preserve setup-site identity, or retain the previous IR and communicate expression ownership separately.
