## Findings

### 1. High — A cut tombstone lookup exposes the removed event

**Location:** [snapback4/crates/snapback4-lang/src/guide/feeds.md:219](snapback4/crates/snapback4-lang/src/guide/feeds.md:219), also copied into the README.

**Failing scenario:** The existing removal test deletes the newest 20 events, then lowers the examined-row ceiling to 25. The merge consumes approximately 22 examinations. Subsequent tombstone probes exhaust the remaining allowance.

On exhaustion, [`get` returns null](snapback4/crates/snapback4-core/src/engine/read.rs:305), and [`Expr::Exists` converts that to false](snapback4/crates/snapback4-core/src/engine/runner.rs:492). The recipe consequently selects `else e`, returning the removed event’s body. `complete: false` does not prevent disclosure or rendering. The [existing test only checks completeness](snapback4/crates/snapback4-sim/tests/following/removal.rs:72), so it misses this.

**Smallest fix:** Make an indeterminate tombstone lookup fail closed: withhold the affected row and any unsafe continuation, or return an unavailable incomplete result. Extend the cut test to assert that no removed event/body appears, on both device stores as well as the server.

### 2. High — Failed admission drops an outstanding transport predecessor

**Location:** [snapback4/packages/snapback4/src/local.ts:1028](snapback4/packages/snapback4/src/local.ts:1028).

**Failing scenario:**

1. Submit A and hide the page before admission commits. Keepalive dispatches A, but delivery stalls.
2. A’s IndexedDB transaction aborts. The client removes its submission record and returns `failed`; no durable A remains.
3. Submit B after persistence recovers. B commits successfully.
4. The [one-second exit wait expires](snapback4/packages/snapback4/src/local-exit.ts:64). Ordinary flushing reads only the [durable queue](snapback4/packages/snapback4/src/local.ts:895), so B reaches the server.
5. The outstanding keepalive subsequently applies A.

Application order is B, A. A may also execute after its caller received a failure. Dedupe does not prevent this because these are different mutation IDs.

**Smallest fix:** Track exit-exposed submissions independently of admission success. Preserve unresolved predecessors and reconcile/retry their original IDs before permitting successors. If persistence cannot preserve that ordering obligation, stop subsequent sending rather than silently dropping it. Add a delayed-keepalive plus first-admission-abort regression.

### 3. Medium — Ordered mutation batches ignore the dev clock

**Location:** [snapback4/crates/snapback4/src/serve.rs:1208](snapback4/crates/snapback4/src/serve.rs:1208).

**Failing scenario:** Start `dev --clock-offset +25h`, then submit two immediate writes through the pre-admission batch. A mutation inserting `{ at: now, expiresAt: now + 180000 }` receives wall time because the batch constructs `Context::new(...).with_ids(...)` without `.at(shared.now())`. The engine [fills an absent time from wall time](snapback4/crates/snapback4-core/src/engine/mod.rs:739).

The new rows are already expired according to the same server’s queries and sweeper. Ordinary `/m/<op>` writes behave differently.

**Smallest fix:** Add `.at(shared.now())` to each batch mutation context. Test ordinary and batched writes under a nonzero offset, including expiry and same-ID replay.

### 4. Medium — A schema cap does not prove that a cursor is unnecessary

**Location:** [snapback4/crates/snapback4-lang/src/bind/mod.rs:213](snapback4/crates/snapback4-lang/src/bind/mod.rs:213).

**Failing scenario:** A public table has `cap 9000 by owner`, and a query returns `rows[viewer] first 9000` through an appropriate plain index. The new condition suppresses `N_NO_CURSOR`.

At 9,000 rows, the default 8,192 examined-row ceiling cuts the result. Without an opaque cursor there is no continuation. The [cursor-enabled scan can provide one after this cut](snapback4/crates/snapback4-core/src/engine/read.rs:657).

**Smallest fix:** Retain the advisory when the cap exceeds the read ceiling; do not treat cardinality bounds as general resource-completeness proofs. Add this large-cap control beside the current 49/50/51 tests.

### 5. Medium — `init` can change existing JavaScript’s module interpretation

**Location:** [snapback4/crates/snapback4/src/verbs/init.rs:33](snapback4/crates/snapback4/src/verbs/init.rs:33).

**Failing scenario:** An existing CommonJS project contains `snapback/seed.js` using `require` or `module.exports`, but has neither `snapback/schema.q` nor a nested package file. Default `init` passes preflight and writes `snapback/package.json` with `"type":"module"`. The existing seed now executes as ESM and fails.

Preflight protects conflicting destination files, but not existing files affected by a new package scope.

**Smallest fix:** Refuse the scope change when it would reinterpret existing scripts, or narrow the ESM boundary to generated artifacts. Add an existing-CommonJS-script preservation test.

### 6. Medium — Browser acceptance remains unverified after W3a2

**Location:** [snapback4/JOURNAL.md:15294](snapback4/JOURNAL.md:15294).

**Failing scenario:** The only recorded lead Chromium result is [8/10 at W3a](snapback4/JOURNAL.md:15209), with both zero-delay unawaited cases losing their writes. W3a2’s final entry explicitly says its Chromium after-result is unmeasured. Successful Node models do not establish real IndexedDB/navigation behavior—the preceding browser failure already demonstrated that distinction.

**Smallest fix:** Record the lead’s final real-browser witness results, including both zero-delay cases and the ten-second destination without a client. Add the failure interleaving from finding 2 to the deterministic suite.
