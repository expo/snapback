**NOT READY — MATERIAL: literal resets can still become approval gates.**

In [approval_effects.rs:30](/home/ccheever/projects/sb4-b26-sec10/snapback4/crates/snapback4-lang/src/bind/security/creation_advice/approval_effects.rs:30), the operation-name fallback bypasses the new false/null field exclusion.

Concrete counterexample: `jobs` has `withdrawalApproved` and `withdrawalDone`, both Boolean with default `false`, and allows updates:

```quarry
mutation decide(job: jobs):
  require viewer = 'service:manager' else NOT_MANAGER
  update jobs[job] {withdrawalApproved:true}

mutation performWithdrawal(job: jobs):
  update jobs[job] {withdrawalDone:false}
```

`withdrawalApproved` yields the cue `withdrawal`. Although `modeled()` excludes the false-valued field, its final OR returns true because `performWithdrawal` contains `withdrawal` and starts with `perform`. The scalar caller consequently emits `N_APPROVAL_NOT_ENFORCED`, despite the only downstream effect being a literal reset. Receipt approvals share this fallback.

This contradicts section 11’s explicit rule that false/null resets alone do not perform the named act. The supplied reset control uses `decide`, so it does not exercise this fallback.
