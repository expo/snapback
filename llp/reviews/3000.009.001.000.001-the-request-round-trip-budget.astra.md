The envelope diagnosis is supported for the measured fixtures: 43 of 57 mutation waits occur outside the durable transaction. Removing duplicate snapshots and carrying committed metadata are sound directions. I found six **MAJOR** issues that need resolution.

Reviewed read-only at `9ca924414b`; no builds, databases, edits or other reviewers were used.

1. **MAJOR — §3.1, §7: the removed preflight check protects receipt replay.**

   The assertion that both intermediate checks “decide nothing the final check does not decide again” is false for early returns. The first writer admission authenticates before looking up a receipt; a successful replay returns immediately, without reaching executing admission or the durable transaction. See [serve.rs:1172](snapback4/crates/snapback4/src/serve.rs:1172) and [serve.rs:1192](snapback4/crates/snapback4/src/serve.rs:1192).

   This is an existing security obligation: [serve_adoption/authority.rs:4](snapback4/crates/snapback4/tests/serve_adoption/authority.rs:4) explicitly tests expiry/revocation while a replay waits and requires 401.

   **Change:** define the final authority boundary for *every outcome*, including replay and metadata-bearing early refusals. Either route replay through final admission or authenticate within its receipt snapshot. Two boundaries remain viable; deleting the checks without relocating these paths does not.

2. **MAJOR — §3.2, §3.7: the proposed authority SELECT omits action-session dependencies.**

   Session, principal generation, expiry, read cap and supervisor metadata are insufficient for all currently supported credentials. `live_session` additionally validates action claims ([authority.rs:237](snapback4/crates/snapback4-core/src/authority.rs:237)). That validation checks work state, lease/deadline and admission authority, potentially walking multiple delegation families ([authority.rs:114](snapback4/crates/snapback4-core/src/authority.rs:114)).

   This particularly affects the promise to apply the same restructuring to SQLite, which supports these paths. A live session row can belong to work whose authority no longer stands.

   **Change:** specify the one-statement fast path’s supported credential kinds and retain the complete shared resolver, inside the borrowed snapshot, for other kinds. Alternatively, design a complete fact-fetch contract for delegation. Do not claim a universal bounded SELECT or move authority policy into separate SQL implementations.

3. **MAJOR — §3.5, §6: the combined finish needs server-side guards beyond the owner fence.**

   The RFC explicitly makes owner mismatch raise, but does not provide equivalent protection for the tail’s result-dependent validation. The tail can successfully execute SQL yet return a committed-row count other than one; Rust then rejects it ([tail.rs:62](snapback4/crates/snapback4-core/src/engine/postgres/tail.rs:62), [tail.rs:80](snapback4/crates/snapback4-core/src/engine/postgres/tail.rs:80)).

   Sending COMMIT before inspecting that result could durably retain program writes without the expected head/commit record. Checking whether COMMIT returned ROLLBACK does not help: a failed logical count check is not a PostgreSQL statement error. RT-A itself names affected-count checks as a condition of this optimization.

   **Change:** enumerate all validations that must precede COMMIT. Make those folded into the finish raise on the server, or retain a client validation boundary and count its additional wait. Require fault cases for zero-row tail results, statement failures and ambiguous COMMIT outcomes.

4. **MAJOR — §1, §4–§5, §9–§10: the measured mutation omits the ordinary keyed path used for batching.**

   RT-A explicitly excludes operation IDs and store bindings ([REPORT.md:74](snapback4/reports/20261022-rt-a-round-trips/REPORT.md:74)). Ordinary SDK mutations mint an ID and send a known store identity ([client.ts:1155](snapback4/packages/snapback4/src/client.ts:1155), [client.ts:610](snapback4/packages/snapback4/src/client.ts:610)). Those requests add store checks, receipt lookups and receipt writes.

   Moreover, the committer permits **only keyed members** to share a batch ([committer RFC:198](llp/3000.009.001.000.000-the-committer.rfc.md:198)). Thus the 1.13× calculation is a conditional illustration, not a sizing result for the actual batchable request. Pre-execution also changes the execution/write schedule; its connection occupancy cannot simply be asserted to remain 57 waits.

   **Change:** retain the four diagnostic fixtures, but add keyed/store-bound success, replay and refusal variants to RT0. Separate whole-request latency, reader connection occupancy and serial commit work when sizing K3/K4. Label the existing budgets narrowly until those paths are accounted for. A small warmed fixture suite remains a reasonable ratchet; the current coverage cannot protect the ordinary mutation path.

5. **MAJOR — §4, §6: the advertised counts lack a consistent flight schedule.**

   The early tiny-mutation arithmetic is sound: `57 − 15 − 4 − 22 = 16`. The later accounting is not:

   - RT5 says setup’s six waits become one and finish’s five become one. Applied to 16, that gives **7**, not the table’s tiny-mutation **8**. Eight would fit the checked mutation, or a retained extra boundary.
   - W1’s membership address depends on the fetched message’s room ([admitted-s1.q:32](snapback4/reports/20261022-rt-a-round-trips/admitted-s1.q:32)). The stated B2 grouping leaves ingress; BEGIN/authority/message; membership; ROLLBACK: **four** waits. Three additionally requires folding the terminal read with rollback.
   - The tiny mutation’s recorded program sequence is read → UPDATE → read. Even combining setup, authority and the first read leaves **five** waits including ingress and finish. Four requires another transformation, such as safely scheduling UPDATE with its terminal read or eliminating that read.

   These targets may be reachable, but not through the transformations currently specified alone.

   **Change:** provide an explicit flight schedule for each fixture, including terminal reads, client-side guards and failure handling. Distinguish predicted counts from conservative ceilings, then reconcile RT5 and B2.

6. **MAJOR — §8: the escalation rule skips a permitted structural alternative.**

   Two-wait reads do not necessarily require a second executor. For a bounded shape such as W2, one statement can fetch authority facts, membership facts, metadata and the page; the existing Rust interpreter can still evaluate rules, meter work and construct the outcome. That is access batching, expressly permitted by [LLP 3000.009 §4.1](llp/3000.009-general-purpose-backend.rfc.md:192).

   The scale study already requires trying a plan-oriented access boundary before lowering ([scale RFC:257](llp/3000.009.001.002-scale-limits-against-postgres-controls.rfc.md:257)). The proposed rule also opens a reads-first B3 RFC when **only W4 fails**, even if the cause is commit serialization or durability.

   **Change:** separate read access composition from mutation semantic lowering. Select follow-up work from the measured bottleneck across the relevant workloads. Include matched transport/locality comparisons where deployable before attributing latency to interpreter semantics. Deferring mutation lowering is justified; treating it as the next structural option for every B2 miss is not.

The ownership-first lock order, borrowed snapshots and post-durable-COMMIT metadata handoff can remain. Their implementation must preserve the complete authority contract and the validation boundaries above. The count ratchet should accompany, rather than replace, latency measurements: S1b already observed markedly different performance between protocols with the same nominal flight count.

VERDICT: NOT READY.
