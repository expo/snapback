## MATERIAL

**1. The first-1 delivery queue cannot retire a refused head row, so later chats never ack.**

- `snapback/messages.q` `markDelivered` (applied lines 177–183): `msg = messages[messageId] ! else NOT_FOUND`, then `require isMember(...)`, then maybe delete `pendingDelivered`.
- `lib/delivery-watcher.tsx` lines 9–15: `nextPendingDelivery` is `pendingDelivered[viewer] first 1`; the effect runs `markDelivered.run({ messageId })` only when `viewer`, `messageId`, and `markDelivered.can.send` change. `can.send` is grant/admission readiness, not `inFlight` and not `last`.
- `unsend` / `purgeMessage` (lines 145–175) log `removed`/`expired` then `delete messages[msg]`. `deliver()` in `access.q` clears pending only for **current** `conversationMembers`.
- Prior `grok-app.patch` clears pending on `memberLeave` only. `memberRemove` is unchanged and does not.

Causal path: an admin removes a member who still has `pendingDelivered`. That row remains and is a legal `first 1` result. `markDelivered` then returns `NOT_MEMBER` (message still there) or `NOT_FOUND` (later unsend/expiry already deleted the body). The effect does not re-run: `messageId` and `can.send` stay the same. Deletion never happens, so the query cannot advance. Delivery acks for every other conversation on that client stop.

Duplicate admission of the same id is safe (`pending == null` is a no-op). Queued/offline is also safe (one `run`, outbox retries). Permanent refusal is not.

Bounded remedy: make `markDelivered` delete `pendingDelivered[messageId, viewer]` first, without requiring the message row to still exist; keep membership only as a guard on a live body if you still want it. Optionally give `memberRemove` the same pending/period cleanup as `memberLeave`. The watcher cannot skip a head row the mutation cannot delete.
