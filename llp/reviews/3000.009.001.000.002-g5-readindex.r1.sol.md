## Review (verbatim answer text)

I found no stale-read counterexample in the implemented **synchronous G5-RI path**, assuming the complete-revision writer contract. I would require two material fixes before making it the default.

1. **MATERIAL — RI intercepts explicitly enabled G6 hits.**  
   [revision_cache_park.rs:25](snapback4/crates/snapback4-core/src/engine/revision_cache_park.rs:25) checks revocation and uncertainty but never excludes a live G6 grant. [serve_queries.rs:58](snapback4/crates/snapback4/src/serve_queries.rs:58) consequently parks the request before the engine attempts its G6 hit.

   **Scenario:** enable both settings and repeatedly read a warm entry without writes. Each successful candidate probe schedules RI validation and waits before eventually taking the G6 branch on resume. G6 therefore pays SQL and collection/resumption delay; stalled validation adds the proof-wait budget even while a valid zero-flight hit was available. This contradicts the documented precedence and invalidates G6’s existing performance characterization for the combined configuration.

   **Required:** attempt G6 before parking, or exclude explicitly configured G6 from RI enrollment. Add an HTTP witness with both settings enabled that verifies live G6 hits generate no RI rounds.

2. **MATERIAL — lazy timer creation can abort the serving process.**  
   [serve_read_index.rs:29](snapback4/crates/snapback4/src/serve_read_index.rs:29) ends thread creation with `.expect("read-index timer")`.

   **Scenario:** the first eligible cached request arrives while OS thread creation fails, such as under a process/thread limit. The newly introduced optimization panics instead of using ordinary G5. The shipped production profile uses `panic = "abort"`, so the request worker’s unwind boundary cannot preserve service; concurrent writes can also lose their acknowledgements.

   **Required:** make timer initialization fallible and resume ordinary G5 with the original admission permit and deadline. Validator submission failures already receive this treatment.

3. **MINOR — doctor reports an incorrect per-hit SQL contract for RI owners.**  
   [deployment.rs:22](snapback4/crates/snapback4-core/src/engine/postgres/deployment.rs:22) selects the description from [store_port.rs:143](snapback4/crates/snapback4-core/src/store_port.rs:143): “one validation statement per hit.”

   **Scenario:** inspect a running RI-enabled owner without G6. Doctor reports per-hit validation despite active batching. For default promotion, update startup, doctor, guide and flag semantics together. Doctor should distinguish what persisted state proves from owner-local batching status.

The clock-free freshness argument otherwise holds. Batch detachment occurs under the queue mutex before validator submission; later arrivals enter the next batch even with two validations running. The enrollment counter is captured before SQL and rejects completed proofs supplied to later candidates. The independent transport takes shared connection custody, rejects retained snapshot custody, and submits a separate statement ending in Sync.

The validation checks the expected owner claim, store identity, both generations, schema/activation identity, revision and head. Exact equality with the immutable entry certifies its frozen session facts under the complete revision stream; each caller then resolves authority and expiry afresh. A supported write acknowledged before invocation must appear in the subsequent snapshot and force a mismatch if it changed those facts. This covers same-owner, successor and grant-unaware writers admitted by G5. Concurrent fills cannot change the selected immutable entry. Observed uncertainty/revocation prevents RI reuse, including after authority resolution; failed proofs retain ordinary G5 policy.

I found no unbounded parked population or connection-cap expansion: continuations retain existing bounded socket admission and charged entries; validators share the capped physical pool. Expiry removes waiters independently of stalled validations, and resumed requests cannot re-enter blocking RI. The **8 ms bounds proof waiting**, excluding timer scheduling, worker queueing and subsequent database work. Disconnects may take that bounded path because TCP closure is not eagerly detected.
