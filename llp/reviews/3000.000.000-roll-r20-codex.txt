## 20. Visible rollback views (ROLL)

Implementer: Codex for Charlie Cheever, 2026-10-22; commissioned for 0.4.39.
This amendment replaces opt-in bridging for declared domain widenings and
relaxed unique keys. Existing retention, metering, authority, immutable source,
and atomic activation laws continue to apply. SEC7 owns ordinary check gates
and ranking; ROLL owns deploy presentation and release selection.

### 20.1 Prepared source and selection

Deploy compares every selectable ordinary predecessor, even without sampled
widened rows. A widening without an applicable authored down requires a compiled
rollback view. All needed views must prepare successfully or deploy refuses.
The compatible join is LLP 3000.000.000.002 §8: optional union, integer and text
bound union with identical format, enum union, recursively joined bounded lists,
and asset size-bound union with identical nominal kind, MIME and once policy.
Nullability and list cardinality join separately. This differs from extraction,
which requires full type equality, including size, optionality and cardinality.
References join only across explicit nominal identity renames. A mixed change
cannot enlarge any current shared-column domain with predecessor-only values:
current read/write predicates may rely on their schema-level impossibility.
The ordinary union view refuses even if that column is not the widening trigger.
A closed alternative may retain the complete current authored source closure
(schema, defaults, programs, helpers, jobs and authority), rather than synthesize
a union. It requires every predecessor table and column under the same spelling,
every predecessor operation name/kind, and current argument domains accepting
every predecessor input under the same closed compatibility rule below. It
retains the exact current domains and values, with no resurrection, translation
or old-only writes. Missing fields/names or incompatible inputs refuse. Current
result semantics are disclosed for old-UI review; current extra operations
remain current-authorized. Native/worker bundle qualification remains mandatory.
Otherwise author a compatible source and truthful migration before deploying. Enum order
and nominal rename spelling do not change this domain comparison. Domain
includes nullability, recursive list-element/cardinality bounds, text formats,
integer bounds, asset kind/size/MIME/once constraints; unsupported or incompatible
domain changes refuse rather than truncate or coerce. No conversion,
zero-money fallback, implicit business default or arbitrary row choice is inferred.

The view retains predecessor operation names and argument contracts. A current
require can be copied only with identical argument and entire transitive local
binding/helper meanings, lookup predicates and control-flow paths. A changed
unmodeled closure or guard depending on writes refuses. Canonical expression
comparison ignores source locations, never semantics. When a relaxed unique key invalidates an old lookup, or current guards require
an added field on a shared table, retain that field and its authored current
backfill. An affected operation whose current guard/workflow cannot be transported
unchanged may likewise reuse its current authored endpoint under the same closed
input-compatibility rule. Every current added field is retained on a shared table, even without a guard
mention; required fields retain their authored default/backfill and every old
write path must supply them through a compatible current authored endpoint or
refuse compilation. No missing-required-field write is permitted. All helpers in a reused workflow, including write,
return and system-scope dependencies, need identical transitive meanings. An already-authored current endpoint of the same name/kind whose
arguments accept every predecessor input may replace the affected old endpoint;
the initial comparison permits identical argument types, optional widening and
integer-bound widening and enum-superset widening, never narrowing or new required arguments. Retained
current backfill identity keeps its output custody active. This supplies authored
writes for the added required fields instead of inventing defaults; the generator never invents first-row
selection. The replacement's point/limited selection must retain the language's
deterministic total ordering, including its stable id tie-break; a source outside
that deterministic language fragment refuses. Missing or incompatible authored
endpoints refuse compilation.

A generated visible view retains the current forward-migration declaration set
for shared output columns. It does not resurrect a retired predecessor transform
whose outputs already remain current columns in the compiled union. Historical
source and receipts remain intact. This preserves current native values and
migration custody instead of reinterpreting them with a retired input domain.
Transforms needed for fields removed from current source remain subject to the
ordinary truthful-projection and complete-adoption checks.

A generated visible view omits a predecessor-only historical down declaration
when all its outputs remain current columns whose generated domains admit the
current native values. Its immutable original declaration and receipt evidence
remain historical; the view does not reenter that retired projection or restore
stale preimages over native values. Downs needed for removed fields remain.
Exact original-source selection retains its projection/conflict behavior. Writer
adoption still enforces full domains, lifetimes and zero-unacknowledged hiding.

Shared tables retain the **current authored authority**, including transition
bindings, read rules, payload guards and field ownership. The compiled bound IR
must equal current authority after declared identity alignment. A release switch
is a view over the same current authoritative rows, never restoration of a
historical database snapshot: deleted rows stay deleted and current values
stay current except declared truthful migrations. No resurrection or replay of
historical preimages over authored current images is authorized. With no
hiding and no domain enlarging beyond current, those row populations remain
the current populations; changing read visibility still follows exact current
authority.
For intentional hiding, IR equality alone is insufficient: §20.2 additionally
checks population-sensitive authority/guards under the actual writer. Removed old immutability/uniqueness
constraints follow explicitly relaxed current constraints. Newer-only tables
retain current rules without promising old clients expose new concepts. Native
or worker dependencies without a qualified authored bundle refuse. Undefined
fields, changed helper closures and incompatible workflows refuse rather than
weakening guards. Nullable result fields and carried/reused guards appear in
an action-focused checklist; successful mechanical adaptations are facts, not
11–42 mandatory decisions. The commissioning author's chosen visible-rollback
contract explicitly permits nullable/wider result domains; these are disclosed
as RESULT compatibility changes, never claimed to retain a nonnull v1 result
contract. Requiring nonnull results would contradict that requested end game.
Names and accepted input contracts remain preserved. Dormant restoration advice
names --restore-dormant.

Removing a defaulted predecessor column requires an authored truthful down.
The initial grammar has no acknowledged-absence escape for removed defaults.
Preview may suggest a cross-table expression from declared references/columns,
but it is advisory source for the author to review, never an inferred business
mapping. A false default is not a reversible representation.

Prepared source is immutable. Each parent manifest maps original target id to
numeric view id, executable digest, changed columns, carried guards and hiding
reason. The parent's full control digest includes the manifest; the view's full
control digest includes its metadata. Prepared views are usable only after the
parent's CAS activation commits and never count as ordinary latest or equal
forward source. Failed parents remove stages/views. Unknown admitted outcomes
retain them for history-authoritative recovery; uncommitted parents cannot
authorize selection. Bootstrap of an unchanged legacy deployment lacking needed
registrations creates an ordinary parent using the same complete adoption and
CAS validation; no view is selectable before that commit. Later equal source
is a no-op. Retained-source reactivation and rollback preserve the registry.

Resolve the newest committed manifest containing the original under the command
lock, then bind actual source digest, expected release and activation revision
to the existing CAS. ABA/equal-content switches change revision. Cold, hot,
preview and restart use that actual immutable source. Selection restores dormant
names implicitly, with full data/constraint/lifetime validation. Output and
releases identify original and actual source. --exact selects the original and
reports dormant hiding; it bypasses only default visible-view selection, never
applicable security/strict refusals, authority checks or migration validation.

### 20.2 Writer-enforced visibility

Default rollback, even without a registered view, admits zero unacknowledged
hidden predecessor-table rows. Candidate preview also refuses uncovered hiding
on reverse snapshots. Future bad projections refuse selection under the writer.
Preview populations are privileged retained-row counts, not viewer guarantees.

The initial intentional-hiding spelling is:
`rollback N hides TABLE where COLUMN = null because 'REASON'`.
The candidate column must be nullable, the predecessor column nonnullable, and
table/column spellings identical. N is the immutable original. No arbitrary
predicate, blanket exemption or rename combination is admitted. Its view keeps
the null restriction while joining the nonnull domain: nullable 0..1000 versus
required 0..100 becomes required 0..1000, preserving widened nonnull values.
The nonempty reason travels in immutable metadata and repeats on selection.

Under the actual writer transaction, capture the before image, run full adoption,
then compare every retained hidden predecessor row. Only acknowledged null rows
and the actual hidden-reference closure rooted in them are allowed; unrelated
hidden rows refuse atomically. The closure graph contains only scalar/optional
nominal Ref cells in before-image active rows, as typed by the source schema;
ids are aligned through the catalog identity. An edge qualifies only when its
parent was also active before, is actually retained-hidden after adoption, and
has no invalid reference-lifetime marker. No list, synthetic extraction anchor,
asset, dormant overlay, cascade or set-null declaration invents an edge. A
renamed identity uses its same catalog number. Before-hidden rows are outside
this newly-hidden population; newer-only tables are distinguished. The snapshot
preview is advisory; concurrent writes cannot bypass activation revalidation.
Acknowledgment never changes physical preservation or permits broader read/write
authority. After collecting the actual newly hidden table set, the writer rejects
negative existence authority, reference comparisons that can admit absence, or
population-tainted requirements/control flow. Positive existence requirements
may only become denials. A direct point assertion may discharge absence taint:
if its row is hidden it aborts before subsequent work; its surviving field values
remain unchanged. Writes to affected existing targets require that same exact
point-presence guard. Transitive bindings and compiler-expanded helper bodies
are followed; unknown paths refuse. Tainted branch/loop/conditional-write keys AND persisted write values,
negative/count-based guard dependencies, nested job-query scope and maintained
populations depending on hidden sources are conservatively outside this initial
acknowledgment form. This is a closed syntactic admission check, not an inferred
semantic implication or a finite-snapshot security proof. Explicit reasons do
not bypass it. Source may retain the safety witness in a visible bridge instead.
Ordinary hidden-row occupancy/retention laws remain explicit in the preview;
intentional hiding supplies no promise of automatic forward conflict resolution.

Point-presence proofs discharge taint only for subsequent work in program
order on that exact table/key. A guard cannot justify any earlier tainted read
or write. Mutations/jobs retain their existing atomic transaction law: a later
refusal rolls back all prior writes in the operation, including work before a
point assertion. The population checker does not weaken that transaction law.

### 20.3 Edited transformation outputs

An edited in-place migration output reverses through an applicable down on its
assembled current image, or stays exact if the compiled selected view's full
type/constraints accept that physical value. This never widens a schema per row,
coerces, truncates, null-fills or invents defaults. Otherwise selection refuses.
Original preimage, actual authored newer output, prior computation and physical
old-view presence are separate evidence; edited output never gains native birth.

Forward validates old-view field presence/null/default/lifetime evidence first.
Preserving authored output requires unchanged explicit arguments AND freshly
unchanged computation, including point/existence lookups. Changed inputs require
exact deterministic agreement with authored output or a real conflict printing
competing values. Unedited outputs retain preimage precedence; receipts state
when older views read stale until forward. Repeated and partially retired cycles,
invalid lifetimes, pruned evidence and meter cuts obey the same atomic laws.

### 20.4 Reference renames and asset extraction

Reference renamed-from transports the existing physical cell and reference
lifetime bindings, including retained/narrowed images. It never recaptures a
deleted/reused parent or captured/engine-owned field. Both aliases at once and
unequal destination cells refuse. After identity alignment, nominal target,
nullability, bounds, on-delete and capture shape must be exactly equal; widening
is a separate migration, not part of this rename.

`extract CHILD from PARENT via REFERENCE: {newField: oldField}` is a declarative
migration, not an operation or cross-table rename. It creates one receipt-owned
initial child per source row; child's deterministic id equals parent id in the
child namespace. The child has a required reference to parent with cascade or
restrict deletion; keep/set-null are outside the initial form. Independent active
or dormant destination history refuses. At least one mapped asset is required,
with identical full source/child type. Parent must remove that source asset
column. Other copied fields must be explicitly immutable scalar source fields;
mutable, captured, maintained and nominal-reference copies refuse. Copies must
continue to agree both directions. Other required child columns need authored
defaults. Receipt identity uses numeric parent/child catalog identities and declared column
origins, so table, asset-column and uncaptured reference-column aliases do not
create a new migration or recapture an anchor. Typed schema normalization updates
extraction table/reference slots and preserves source/destination column strings.
Destination admission inspects active rows, dormant rows/cells and competing
receipts. Reentry requires its existing receipt-owned child and valid anchor;
pruned/deleted child history is never recreated from metadata.

Future independent children with distinct ids are allowed; extraction is not
unique-parent. Existing durable id reservation and duplicate-key admission apply
to receipt-owned/dormant children exactly as to ordinary rows. The normal mint
never overwrites an occupied id; an explicitly forced collision refuses. Neither
rollback nor deleting receipt metadata frees a still-retained row id.

Asset ledger home and physical asset cell move together, without reuploading or
changing bytes. The former active cell and equal dormant overlay are removed;
a distinct overlay refuses rather than being discarded. Private displaced-cell
receipt evidence persists separately from active cells. Reverse removes the
child asset cell while retaining identity/scalars and newer-only children. Later
forward uses the current old-view asset, including replacement/optional clearing,
never reviving released receipt bytes or creating a second ledger home.

A native child without a receipt reverses only when exactly one total candidate child
exists for that parent, and that child has a valid private parent-lifetime anchor. Anchors are captured while
extraction is active, including absent-parent invalid anchors; unchanged writes
never recapture invalid evidence. Older independent relations cannot qualify
retroactively. Deletion/id reuse, reparenting and ambiguity refuse; no arbitrary
photo selection. Receipt-owned children likewise require valid lifetime evidence.

For row-dependent audiences the child must read through its parent with identical
parent policy; otherwise source/child read policies must be identical and row-
independent, or destination denies reads. Existing payload gates must match.
Reverse must preserve the current effective child/parent/column audience or
refuse with guarded-bridge advice. These are closed admission rules, not a
policy implication prover. Native/ref compatibility does not confer byte access.

Actual activation revalidates active AND dormant destination emptiness, regular
byte presence/ledger length, full types, scalar copies, parent binding, anchor
validity and reverse ambiguity inside adoption under command locking and CAS.
Preview runs this transaction on a private copy; its counts cannot authorize a
later activation. Failure rolls back evidence, format, homes, selection and
generation together. Devices execute no migration metadata or home authority:
authenticated serving resolves the current server ledger home and current row/
column policy. Existing device generation and media-retention receipts remain;
this introduces no retroactive cache-erasure claim.

Store format 9 fences edited-output/reference/extraction AND compiled-view
registry custody from older runtimes. Every successful release adoption upgrades

Every hot activation request from this CLI carries the explicit registry-custody

This prevents an older engine from executing any adoption without the new laws.
Unchanged no-op deployments without new custody can stay at 8. Format 8 opens;

## 9. Edited migrated outputs (ROLL)

Commissioned for 0.4.39, 2026-10-22. LLP 3000.000.000 §20 and its review

status. Format 9 fences this retained law, including after selecting old source;
format 8 remains readable and upgrades transactionally on successful adoption.
Repeated cycles, partially retired outputs and table-name changes preserve
that evidence. The implementation adds focused regressions for those paths.
