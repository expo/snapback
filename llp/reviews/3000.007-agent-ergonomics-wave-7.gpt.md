## Findings

### F1 — High: grace bookkeeping makes presence decide mutation success

**Location:** [engine/presence.rs:21](snapback4/crates/snapback4-core/src/engine/presence.rs:21), especially lines 26–28 and 52–65.

**Failing scenario:** Use an eligible mutation that inserts a note and conditionally emits when Bob is absent. Compare two otherwise identical worlds: Bob has no live poll in either, but one has grace remaining. Only the grace world pays for dependency allocation and copying. Set the heap ceiling between those two costs—or place ordinary work sufficiently near the default ceiling.

The no-grace mutation commits; the grace mutation returns `E_BOUND` and rolls back its note. Devices disable this bookkeeping, so their existing untaken-arm charge does not reserve it. Presence now affects committed rows and the caller’s refusal, contradicting ruling 18 and creating a response channel even without access to effects inspection.

**Smallest fix:** Reserve a presence-independent worst-case bookkeeping allowance on both server and device, including dependency propagation and emission copies. Keep the actual allocations metered.

### F2 — Medium: dependency tracking is mistaken for proof that reconnect satisfies an effect

**Location:** [engine/presence.rs:52](snapback4/crates/snapback4-core/src/engine/presence.rs:52), [engine/effects.rs:114](snapback4/crates/snapback4-core/src/engine/effects.rs:114).

**Failing scenario:** An eligible mutation unconditionally emits:

```quarry
emit audit { recipient: p, online: exists connected[p] }
```

If `p` is in grace, the payload read attaches a dependency. A brief reconnect makes the effect permanently `satisfied`, with zero handler attempts, although the application unconditionally requested the audit.

Similarly, `if not exists connected[p] or force` loses the effect after reconnect even when `force = true`. The implementation retains dependency identities, not the condition that would establish whether cancellation is valid.

**Smallest fix:** Restrict automatic cancellation to proven necessary absence guards. Preserve ordinary semantics for payload-only presence and other boolean forms unless their condition is retained and correctly re-evaluated. Update the broad “any dependency” wording accordingly.

### F3 — Medium: pull routing changes from reader-private to public

**Location:** [guide/feeds.md:79](snapback4/crates/snapback4-lang/src/guide/feeds.md:79).

**Failing scenario:** An unrelated account cold-syncs and receives another reader’s pull routes, including which shared authors have installed lanes and which are missing after saturation. Previously those rows were readable only by their reader.

The follow graph was already public, but exact installed routing is additional state; skipped promotions make it more than a straightforward copy of current follow edges. Describing this solely as synchronizing already-public metadata understates the change.

**Smallest fix:** Retain the reader-scoped pull audience and expose only public promotion metadata, accepting the resulting prediction boundary for operations requiring foreign routing state.
