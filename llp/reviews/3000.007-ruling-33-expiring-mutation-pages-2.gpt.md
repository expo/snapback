**1. High — §2(c), §3 A2′/A3: a stable verdict does not imply a stable examined population.**

Consider an expiring `records` table with:

- Read rule `.owner = viewer`, unrestricted update authority, and no relevant constraints or maintains.
- A plain index `(owner, secret, id)`.
- A known, live target owned by Alice, whose retained `secret` is either `"A"` or `"B"` in otherwise equivalent worlds.

A never-predicting mutation by Bob performs this sequence:

```text
Consume a fixed amount of examined budget using unrelated public reads.
Blindly update target: owner = viewer, expiry = a time before now.
Scan records[viewer, "A"] first 1 by (owner, secret, id).
Require false with code STOP.
```

Arrange one examined unit to remain at scan entry. The page attempt consumes it. If the retained secret is `"A"`, fetching the newly expired target causes `E_BOUND`; if it is `"B"`, the prefix is empty and execution reaches `STOP`. Both outcomes roll back. No row is returned, but the refusal distinguishes the secret.

The operation satisfies the proposed conditions: the prefix uniformly pins the owner to the viewer, the operation never predicts, and **D(page) is empty** because the read rule contains no probe. A snapshot query of Bob’s `"A"` prefix is empty in both worlds.

This follows from hidden-target updates being authorized independently of readability, the patch being installed transactionally, and examined charging preceding expiry rejection: [write_target.rs:129](snapback4/crates/snapback4-core/src/engine/write_target.rs:129), [write_target.rs:140](snapback4/crates/snapback4-core/src/engine/write_target.rs:140), [write.rs:155](snapback4/crates/snapback4-core/src/engine/write.rs:155), [read.rs:573](snapback4/crates/snapback4-core/src/engine/read.rs:573). Distinct failed outcomes remain distinct receipts after rollback: [engine/mod.rs:861](snapback4/crates/snapback4-core/src/engine/mod.rs:861).

**Smallest conservative fix:** protect `page.table` itself against preceding effective writes, regardless of self-probes, alongside the verdict dependencies. Include maintain sources capable of changing that table. Preserve writes after a materialized page, including its consuming loop body when that body does not reexecute the scan. Add this paired counterexample.

This changes admitted behavior and cannot be left to an implementing lane as an interpretation of “stable verdict.”

**2. High — §2(c): one-level maintain expansion does not cover every core-admitted schema.**

Quarry rejects maintains sourced from maintains at [bind/schema.rs:548](snapback4/crates/snapback4-lang/src/bind/schema.rs:548). Core schema validation does not impose that restriction: [schema.rs:925](snapback4/crates/snapback4-core/src/schema.rs:925). Raw schemas reach activation through that validation: [engine/mod.rs:385](snapback4/crates/snapback4-core/src/engine/mod.rs:385).

A concrete admitted-schema case is:

- `B` maintains a count of application table `C`, grouped by `(room, until)`. `B` expires at `until`.
- `A` maintains a count of `B`, grouped by `room`.
- The expiring page table’s rule probes `exists A[.room]`.
- At the snapshot, an `A` row exists, but its only physical `B` contributor is expired. This state is obtainable by rebuilding `A` over retained `B` rows; rebuild includes physical source rows without an expiry test at [maintains.rs:91](snapback4/crates/snapback4-core/src/engine/maintains.rs:91).

The snapshot probe is false: maintained existence checks for a live source witness when the source expires. Inserting a `C` row with a future `until` creates a live `B` row, making the probe true inside the transaction. See [read.rs:111](snapback4/crates/snapback4-core/src/engine/read.rs:111) and [maintains.rs:189](snapback4/crates/snapback4-core/src/engine/maintains.rs:189).

The specified D(page) is `{A, B}`. The explicit IR write names only `C`. Thus the stated direct-write check misses the engine’s write to `B`, reopening the gate scenario. This example does **not** assume cascading maintains: the probe directly examines `B`; [write.rs:530](snapback4/crates/snapback4-core/src/engine/write.rs:530) limits maintain propagation to source-origin writes.

**Smallest fix:** define dependencies as a fixed-point closure through incoming maintain sources, or explicitly expand each write’s engine-side effects before checking interference. Alternatively, require core validation to reject these schemas consistently with Quarry before relying on a one-level definition.

For ordinary Quarry schemas, I found no additional dependency through a probed table’s own read rule: probes inspect its rows directly. Extra equalities inspect that same target; `Created` is forbidden in read rules; deciding row fields must be pinned or eliminated by the uniformity proof. Evidence: [read.rs:102](snapback4/crates/snapback4-core/src/engine/read.rs:102), [rules.rs:109](snapback4/crates/snapback4-core/src/engine/rules.rs:109), [schema.rs:892](snapback4/crates/snapback4-core/src/schema.rs:892).

**3. Medium — §2(c), §5(e): specify an executable-effect walk, including implicit repetition.**

The IR is closed and table destinations are statically named, so conservative checking is feasible. It need not solve exact path feasibility: union branch effects and conservatively account for repeated regions.

However, `Flow` is a population-provenance analysis, not an exhaustive execution-order analysis. It treats blocks as unknown without traversing their statements, omits shape bases, and ignores several statement expressions. `write_tables` likewise misses writes inside expressions. Evidence: [admission.rs:120](snapback4/crates/snapback4-core/src/engine/admission.rs:120), [admission.rs:137](snapback4/crates/snapback4-core/src/engine/admission.rs:137), [ir.rs:610](snapback4/crates/snapback4-core/src/ir.rs:610).

A particularly important serialized-IR fixture is a scan filter containing:

```text
nested expiring page
write its gate
return true
```

The filter repeats for successive outer candidates. Its second nested page follows the first candidate’s gate write, although no `Stmt::For` encloses it. Runtime executes filter blocks at [read.rs:625](snapback4/crates/snapback4-core/src/engine/read.rs:625) and [runner.rs:452](snapback4/crates/snapback4-core/src/engine/runner.rs:452). Quarry’s filter purity restriction does not itself validate hand-serialized IR.

**Smallest fix:** explicitly require exhaustive traversal of statement operands, blocks, conditions, shape bases/fields, read keys, scan prefixes/bounds/filters, and loop-domain expressions. Model filters as repeated regions. Include all six write forms and both upsert arms. Conservatively retain effects across `break`/`continue` unless their exclusion is proved.

No current IR form intrinsically requires an “unknown” result if fully implemented. An unhandled executable form must refuse, rather than inherit an empty effect set. This is an implementing-lane clarification consistent with the intended condition.

**4. Medium — §5: strengthen tests so broken implementations cannot pass vacuously.**

The existing observation helper compares the important serialized and durable observations, but it explicitly does not exercise actual HTTP transport/status: [write_observation.rs:1](snapback4/crates/snapback4-sim/tests/common/write_observation.rs:1).

The required additions and controls are:

| Test | What makes it discriminating |
|---|---|
| **(a), (a′)** | Assert successful admission and the expected execution result as well as paired equality. Otherwise blanket expiry rejection passes the comparison. Include both exhausted and non-exhausted denied cases. |
| **(b)** | Use one simple scan, a successfully paid attempt, identical candidate state and clock, and give the query the mutation’s **remaining** examined allowance. Exercise both sides of the threshold and `take + 1` lookahead. Assert examined `E_BOUND` versus specifically `cut == "meter"`. This is now well defined and achievable. |
| **(c)** | Add the page-table counterexample and indirect-maintain counterexample above, plus deletion of a required probe row—true-to-false changes matter too. |
| **(d)** | Retain reason-specific assertions and independently verify the predicting fixture’s operation fact. Each fixture must isolate its intended refusal. |
| **(e)** | Cover writes inside operands and implicit filter repetition, not only differently located scans. Exercise runtime `validate_inputs`, not just direct calls to `check_detail`. |
| **(f)** | Assert `predictable == false` and use a body-execution canary. A scan-only body can execute while producing no predicted rows. Cover initial admission, reopen, replay after an image, and generation changes on both stores. |
| **(g)** | Assert that the fresh invocation succeeds, while the original receipt remains byte-for-byte unchanged and its retry remains failed. |

These strengthen the requested tests without changing behavior; the first two findings require additional proposal changes.

**5. Low — §A’s device disposition overstates what `predicts: "never"` guarantees.**

The normal path is sound: `local::predict` checks admission, then returns `Prediction` before constructing a runner; device admission queues it as nonpredictable, and replay skips it. Residency changes can change the fact, but compilation recomputes facts before admission, and execution rechecks admission against the current schema: [bind/mod.rs:64](snapback4/crates/snapback4-lang/src/bind/mod.rs:64), [local.rs:63](snapback4/crates/snapback4-core/src/engine/local.rs:63). The protection is invocation-time rechecking, not a universal admission pass on every activation.

The literal “not executed on a device at all” claim has exceptions:

- `Device::query_with_coverage` can select a mutation by name; the local query entry rejects actions but not mutations. A scan-only never-predicting mutation can consequently execute with capped query semantics. [device.rs:635](snapback4/crates/snapback4-device/src/device.rs:635), [local.rs:25](snapback4/crates/snapback4-core/src/engine/local.rs:25).
- `snapback4 run` uses the server `Engine::mutate` path. If a device database is supplied at the project store path, `open_engine` checks deployment ownership, not device ownership; the prediction guard is not involved. [project.rs:230](snapback4/crates/snapback4/src/project.rs:230), [verbs.rs:430](snapback4/crates/snapback4/src/verbs.rs:430).

**Smallest fix:** scope the claim to device mutation admission and prediction replay. If universal device-store nonexecution is intended, require operation-kind and store-role guards explicitly.

Finally, §1’s “at no charge” should say “without fetching candidates”: the attempt is charged even for a false verdict. That charge is population-independent and creates no additional hidden-population distinction by itself.

Verdict: NOT READY
