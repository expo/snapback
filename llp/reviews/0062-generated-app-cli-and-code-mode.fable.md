# Review: LLP 0062 — Generated Per-App CLI and Code Mode

**Reviewer:** independent review pass (Claude Fable 5), 2026-07-17
**Revision verified:** I computed sha256 of `llp/0062-generated-app-cli-and-code-mode.rfc.md` and it matches the stated hash `777a47c787e3e8d46cb8da5eae299dbb5d7e04ff2394a88683b54dcc8bc7e497`; repo HEAD is `dfd829e` and the file is new/untracked, as stated.

## 1. Overall assessment

This is a good proposal with the right instincts, and most of its load-bearing claims verify against the repository: `authRequirement`, read/write-set summaries, and stable `{appId}:{exportedName}` ids are real manifest facts (`demos/todo/snapback/generated/functions.manifest.json`); the operations schemas exist one-per-function; `api.mjs` entries are inert descriptors and `api.d.ts` is types-only; the headless client (`demos/_kit/client.mjs`) has the session flow (`authRequestCode`/`authExchange`), `query`/`action`/`liveQuery`, and ephemeral routes the design assumes; `sbac_`/`sbagt_`/`POST /auth/agents/token` exist in `src/auth/crypto.rs` and `src/server.rs`; custody is exactly as described (`agent-authority-filesystem.mjs`: 0600 files, advisory lock, scoped-token bearer never persisted); LLP 0024's dated amendment does pin "host operations never resolve scoped tokens"; LLP 0055 does refuse every hosted service-principal invocation in v1 with a 1-hour default token TTL; and the served-guide identity pattern (`x-snapback-guide-content-sha256`, `x-snapback-server-build-commit`, LLP 0031 registration) is implemented in `src/server.rs`. The ibex cross-references are reciprocal — ibex LLPs 0028 and 0029 each name Snapback LLP 0062 as their motivating consumer.

The core architectural decisions are correct: one engine consuming artifacts as data (never executing served program source), zero CLI-owned authority, the operator/application plane separation, the two-process credential split, and code mode as the answer to context economics. The scope cuts (`--arg`, `repl`) are the right ones.

However, the RFC's weakest section — §5's "Projection, not inventory dump" — and several specific normative sentences do not survive contact with the code. The anonymous model is built on a two-valued reading of a three-valued `AuthRequirement` vocabulary; "verbatim" manifest entries would ship the app's full handler source to any caller; the served envelope has no specified path onto the server; the "typechecks against the served `api.d.ts`" claim is false against the artifact as generated; and the server-advertised `npx` install line reintroduces the exact trust problem §1 closes for `api.mjs`. Each is fixable with bounded edits, and none invalidates the direction, but together they are material correctness/safety/feasibility gaps in the normative design.

## 2. Strengths (with section citations)

- **The plane boundary is exactly right and verified (§Position).** "The app CLI never accepts the admin token … it does not use the `function.run` host op — host operations do not resolve scoped tokens into authority" matches LLP 0024's 2026-07-16 dated amendment and LLP 0055 §Plane boundary verbatim. This is the discipline that keeps the CLI from becoming a fourth authority surface.
- **Artifacts-as-data, never served code (§1, §3).** Refusing to execute a served `api.mjs` — with the correct observation that a self-attested identity header cannot mitigate RCE — is the single most important security decision in the document, and it is stated plainly with its rationale. The local-checkout carve-out is correctly reasoned (the entries are inert descriptors; verified).
- **Honesty about hosted gating up front (§Motivation, §4).** "LLP 0055 v1 refuses every hosted service-principal invocation" is stated in the third paragraph rather than buried, and matches 0055 §Summary/§Plane boundary exactly. The "target capability, not a bug" presentation rule is good agent UX.
- **The subscribe contract is grounded in the real client (§2).** Content-comparison "change" semantics, resync-suppression after reconnect, and resubscribe-with-backoff correspond to the kit's actual reconnect-by-fresh-subscribe behavior documented at the top of `demos/_kit/client.mjs`. This is a spec written by someone who read the transport.
- **Frozen exit codes and non-TTY JSON/JSONL defaults (§2)** are the right agent contract, and extending the LLP 0010/0012 diagnostic discipline (codes, not prose) is the corpus-consistent move.
- **One-envelope atomicity (§1, §5)** dissolves both the staleness question and the mixed-artifact deploy race, and correctly reuses LLP 0012's identity machinery (`inputsHash`/`bundleHash` verified present in generated manifests).
- **The two-process credential split (§3, §4)** is a real improvement over handing scripts the `sbac_` credential, and the acceptance suite's "no `sbac_` material in the script host's environment" test (§7) makes it checkable.
- **The acceptance section (§7)** is unusually strong for a Draft RFC: forged-violation adapter conformance tests and the host-portable code-mode suite make the "moving hosts changes enforcement strength, not script semantics" claim falsifiable.
- **Motivation is honest to its sources.** LLP 0019 F1 ("one core, thin projections", manifest-as-catalog) and F8's context-pack idea are genuinely what this composes; LLP 0012's packaging bar ("real, typed, versioned packages") supports the phase-1 client lift out of `demos/_kit/`.

## 3. Concerns

**C1 (major — correctness of the auth model).** The RFC's anonymous model treats `authRequirement` as two-valued; it is three-valued, and the default is the one the RFC ignores. `src/manifest.rs` defines `Public | OptionalUser (default) | Authenticated`, and the invocation gate (`src/auth/invocation.rs:1418-1425`) refuses an anonymous caller **only** for `Authenticated` — `optional-user` functions are anonymously callable. Consequences, all in normative text: (a) §Summary/§4 "Anonymous callers reach `public` functions" is wrong as a boundary statement; (b) §2's "client-decidable refusal (anonymous principal vs. a non-`public` function)" would client-side-refuse calls the server allows — for the todo demo (every function `optional-user`) it would refuse *everything* while the server accepts everything — which is precisely the "second auth semantics" §2 forbids one sentence later; (c) §5's anonymous envelope ("the `public`-functions projection") hides from anonymous consumers the very functions they can call, making `--help`/`introspect` dishonest by construction. *Resolution:* restate the anonymous boundary as "public + optional-user are anonymously callable; only `authenticated` is client-decidably refusable," and redefine the anonymous projection subset accordingly (or explicitly justify a stricter subset and delete the client-decidable-refusal claim).

**C2 (major — safety: handler source disclosure).** The function manifest embeds the app's complete handler source (`runtime.IbexModule.source` in `functions.manifest.json` carries the full JavaScript). §2 pins `introspect` entries as "verbatim" manifest entries and §5 gives "any authenticated principal … the full envelope" containing "the function manifest." As written, any logged-in app user (or any local artifact consumer) receives the app's entire server-side implementation. The repo already decided this exact question the other way: LLP 0031 D3 (ENG-23441) introduced `PublicFunctionManifest` (`src/manifest.rs:1672-1760`), which strips `IbexModule.source`, `HandlerPlan` bodies, and `sourceSpan`, with "full handler source lives only on the gated twin" (admin-gated) and a whole-payload source-sentinel test. *Resolution:* specify that the envelope and `introspect` serve a source-stripped projection (the `PublicFunctionDefinition` shape or an app-api-specific equivalent) for every non-operator principal, and replace "verbatim" with "projection-faithful under LLP 0012's `schemaVersion`."

**C3 (major — feasibility: the envelope has no path onto the server).** The server today holds only the schema and function manifests, provisioned through `/app/ensure` — whose provision variant LLP 0012 pins as a **closed** DTO ("its only optional fields are `schema` …, `functions` …, and `seed`"; unknown fields rejected). The operations schemas and `api.d.ts` are codegen outputs that never reach the server (the loaded manifest carries no args-validator field — verified against `schemas/functions.manifest.schema.json` — and `src/server.rs` has no operations/`api.d.ts` surface). §5's "the server serves the artifact envelope" therefore requires either a new provisioning channel (a compatibility event on a deliberately closed contract, needing a dated LLP 0012 amendment) or server-side derivation of the schemas — and the RFC specifies neither. *Resolution:* add a subsection specifying how envelope bytes reach the server (extended provision intent, separate artifact upload, or derivation), and name the LLP 0012 amendment obligation explicitly.

**C4 (major — correctness: the code-mode typing claim is false against the artifact).** §3 says the injected `api` is "shaped to match the generated `api.mjs`/`api.d.ts`, so a script typechecks against the served `api.d.ts`," and the Summary calls `api.d.ts` "the contract the agent codes against." But the generated `FunctionReference` interface (`api.d.ts:7-15`) has **no call signature** — `await api.createTodo({ title })` is a type error ("expression is not callable") against the artifact as it exists — and it carries no result type, so even a corrected callable surface types every result as `unknown`. *Resolution:* specify the actual code-mode typing artifact — either codegen grows a `code-mode.d.ts` (callable signatures; async-iterable for `LiveQuery`; result types when known) or the engine synthesizes one from the manifest + operations schemas — and correct the §Summary/§3 claims. State explicitly whether v1 accepts `unknown` results.

**C5 (major — safety: the install line reintroduces the trust problem §1 closes).** §1 refuses served `api.mjs` because "download JavaScript from the target server and run it" is RCE that no self-attested header mitigates. §5 then has the same self-attested server advertise "install spellings (`npx @snapback/app-cli` …)" which the degraded-mode diagnostic carries to the agent — and `npx <server-chosen string>` is download-and-execute with the invoking user's OS authority. A malicious or compromised app server can hand an agent a typosquatted package. *Resolution:* pin the package name as engine-side/documentation constant knowledge; the server may advertise only a version (and, for binaries, a redirect to a pinned release host with checksums); name the residual trust assumption explicitly.

**C6 (minor — coherence: the route lane named cannot hold this route).** §5 registers the envelope in "LLP 0031's public system-static lane," but that lane is enforced (in `src/server.rs:3914-3928` and the registry test at 26128-26132) as "inert public console assets or guide projections" — build-embedded, `Public`-policy, principal-independent bytes. The proposed route is app-owned, deploy-varying, and must resolve the principal to choose between two projections — none of which is system-static or unconditionally public. *Resolution:* specify a new route class/policy registration in LLP 0031 (the RFC may keep "mirroring the served-guide *identity* pattern," which is accurate) rather than claiming the guide lane.

**C7 (minor — safety-claim precision in §3).** "A compromised run is thus bounded by the scoped token's grant and TTL" contradicts the same paragraph's premise: a script that escapes the Node vm "can do anything the invoking OS user can" — which includes reading the 0600 custody file, since the invoking user is its owner. The parent/child split defeats disclosure through the script's *legitimate* channels (env dumps, injected surface), not an OS-level escape. *Resolution:* reword the bound to name the threat it holds against and the vm-escape residual (which the section otherwise handles honestly).

**C8 (minor — versioning model misread).** §5's "the engine supports the current and previous `schemaVersion`" treats `schemaVersion` as a linear sequence. Under LLP 0012 the admissible set is the closed mode-paired tuples `(snapback.v0, dev)` and `(snapback.v1, sessions)` — both *current*, neither the other's predecessor. *Resolution:* restate the compatibility window against LLP 0012's closed tuple set (e.g., "the engine supports every tuple admissible at its release, plus one revision back once a successor exists").

**C9 (minor — vocabulary drift on the target boundary).** §Motivation's "local and self-hosted dev targets" is not LLP 0055's boundary: 0055 admits local and **trusted-local**, where trusted-local requires LLP 0060's target-authored deployment capability and "a reverse-proxied local process is not trusted-local" — i.e., much of what "self-hosted" colloquially means is *hosted* and refused. *Resolution:* use 0055's local/trusted-local vocabulary.

**C10 (minor — unsupported citation, and the precedent points the other way).** §5 justifies the anonymous projection with "LLP 0055 deliberately redacts non-public shape from anonymous callers elsewhere." I could not find that in 0055 — its nearest facts are non-enumerating grant denials and the sealed anonymous `ctx.auth` (no `kind` key), which concern grant/principal existence, not API shape. Meanwhile the ungated public `GET /inspect` already serves the **complete** function inventory (all functions, `authRequirement` included, source-stripped) to anonymous callers as a deliberate D3 decision — so the proposed redaction protects nothing while degrading the anonymous CLI, and it silently diverges from the instance's own public posture. Note also that in dev mode no authenticated principal exists, so the "full envelope" branch never fires on the tool's primary phase-1 target. *Resolution:* fix or drop the citation; reconcile the projection with `/inspect` (either both redact or neither), and specify the dev-mode behavior.

**C11 (nit).** The `SNAPBACK_APP_CLI_*` code family and the exit-code table must be registered in LLP 0012's shared diagnostic dialect (changing an emitted code is a compatibility event there); name that registration as a phase-1 deliverable. Also: the `capabilities.md` GAP row the RFC says it "ships with" is not yet in the tree; and §Open questions on ephemeral rooms should note LLP 0055 v1 already refuses `servicePrincipal` for ephemeral operations, so "v1 or follow-up" is effectively decided for the agent path.

## 4. Suggestions (non-blocking)

- **`--args -` (stdin JSON).** Agents mangle shell-quoted JSON constantly; reading args from stdin is a near-free ergonomic win that avoids the `--arg k=v` contract entirely.
- **`introspect --changed-since <identity>`.** The envelope identity makes "what changed since I last looked" a cheap diff — very high agent value per line of implementation.
- **A `run` wall-clock/call budget** (`--timeout`, `--max-calls`) with its own exit code. The table has timeout semantics only for `subscribe`; agent-generated scripts loop by construction, and a kill switch belongs in the frozen contract.
- **Flag-spelling alignment with LLP 0024.** The operator CLI pins `--args-json`; this RFC uses `--args`. Either align or state the divergence deliberately so agents that use both surfaces don't guess.
- **Call transcripts as acceptance seeds.** A `--transcript <file>` that records call/subscribe envelopes replayably would convert agent exploration directly into acceptance fixtures — a Snapback-flavored differentiator consistent with LLP 0010.
- **One-shot `eval` as named future work** beside `repl` — `<app> run` requires a file; a `-e '<expr>'` form is not a REPL (no session state, so none of ibex 0022's obligations) and agents will want it.
- **Bound code-mode stdout** (size cap with an explicit truncation diagnostic) — the whole point is result economy; an unbounded accidental dump defeats it.
- **State whether the anonymous envelope includes a projected `api.d.ts`** — the full `api.d.ts` embeds the entire `GeneratedDataModel`, which the projection story should address once C1/C10 settle the subset.

## 5. Open questions

1. **Envelope delivery (C3):** which channel moves operations schemas and `api.d.ts` to the server, and does `/app/ensure`'s closed union grow a variant (dated LLP 0012 amendment) or does the server derive schemas from validators it would then need to receive?
2. **Projection audience (C1/C10):** what exactly does each principal class see, per auth mode — and does the anonymous envelope match `/inspect`'s existing public posture or does `/inspect` change too? What does a dev-mode target serve?
3. **Result typing (C4):** does codegen grow return types on `FunctionReference`, or does v1 accept `unknown` results in code mode?
4. **Token refresh for long `--watch` (extends the RFC's own TTL question):** LLP 0055 pins re-poll as revoke-and-replace and token rotation terminates the ended family's carriers — so a mid-watch refresh forcibly drops the live connection and must resubscribe. Is dedupe-across-token-replacement (content comparison spanning a reconnect under a new token) the documented answer, or is a ceiling?
5. **Install-line trust (C5):** where does the engine's package-name pin live, and what does the standalone-binary redirect attest (host pinning, checksums, signature)?
6. **Anonymous-projection knob (kept from the RFC):** app config or deploy setting — and does it extend to `/inspect` for consistency?
7. **Multi-app engine state:** cache location, per-target keying, and concurrent-invocation behavior for the envelope cache (two CLIs racing a deploy).

## 6. Readiness verdict

The direction is right and unusually well-verified against the corpus, but five major concerns — the anonymous/`optional-user` model error (C1), handler-source disclosure through "verbatim"/"full envelope" (C2), the unspecified envelope delivery path against a closed contract (C3), the false code-mode typing claim (C4), and the install-line trust inconsistency (C5) — are material correctness, safety, and feasibility defects in normative text. All are resolvable with bounded revisions; none requires rethinking the architecture.

## 1. Overall assessment

This is a good proposal, and an unusually honest one. The two core moves are right: (a) one generic engine consuming served artifacts strictly as data — which simultaneously dissolves CLI staleness and closes the download-and-execute hole that a naive "serve the generated `api.mjs`" design would open; and (b) code mode as the answer to agent context economics, with a parent-brokered call ABI that keeps every bearer out of the script host and makes a future stronger host a drop-in. The auth section adds zero second semantics and I verified its claims against the actual invocation gate: the three-valued `authRequirement` is real (`src/manifest.rs:139`), the gate refuses anonymous callers only for `authenticated` with `SNAPBACK_AUTH_REQUIRED` (`src/auth/invocation.rs:1418-1425`), one-shot `call` on a LiveQuery is already admissible (`function_kind_matches` admits LiveQuery under the Query constraint), and hosted/ephemeral/rotation/attribution claims match LLP 0055 verbatim. The ibex phase-2 deferral is accurate against ibex 0029's actual text ("no REPL, no eval, no file-execution ingress — exactly one entry"; compile-time type erasure; embedded policy as the authority ceiling) and correctly non-normative.

The document is not quite ready. The §4 target matrix misstates dev mode — the default local tuple has client-asserted identity (`DevImpersonation`), not "everyone is anonymous" — and the RFC neither exposes nor explicitly declines that lane, which materially degrades the CLI on the target agents use most and quietly contradicts the "projection of the headless client" claim (the headless client has a `userId` parameter on dev targets). A few frozen-contract items (exit 7 semantics, the version-handshake enforcement direction, envelope ingestion on the v0-dev tuple) are underspecified for contracts declared frozen from phase 1. All are bounded revisions, not structural rework.

## 2. Strengths

- **Engine-plus-data, with the RCE argument stated plainly (§1).** "A served `api.mjs` will not be loaded into the engine process" is exactly right, and the follow-through is complete: the served envelope reuses LLP 0031 D3's `PublicFunctionManifest` posture (verified: it strips `IbexModule.source`, HostPlan bodies, `sourceSpan`; the build manifest really does embed full handler source — I confirmed it in `demos/todo/snapback/generated/functions.manifest.json`), the identity pattern copies the served guide's real headers (`x-snapback-guide-content-sha256` / `x-snapback-server-build-commit`, `src/server.rs:4321-4322`), and §5 even refuses to let the server name an install command — closing the same trust hole from the other direction. Defensive parsing bounds ("not code rules out RCE, not denial of service") is the right level of paranoia.
- **Boundary honesty in code mode (§3).** "Not a security boundary, and no hostile-code bound exists" is the correct claim for a Node vm, and it matches ibex 0013's own framing ("the honest name is supply-chain integrity, not sandbox", ibex 0013:221). The parent-brokered ABI is a genuinely good design: it defeats disclosure through the script's legitimate channels, keeps semantics host-independent, and the §7 bearer-absence test makes the property checkable.
- **Zero second auth semantics (§4), verified.** Exactly two client-decidable pre-flags, everything else "determined by the server at call time" — this respects LLP 0055/0056/0058's server-side evaluation and the sealed anonymous projection's fail-closed `kind` rules (LLP 0055:1693). The `AgentAuthorityFence`-vs-`sbac_` custody distinction is accurate (the filesystem store actively refuses bearer fields — `agent-authority-filesystem.mjs:256-257`), and "AuthCoordinator has memory and IndexedDB storage only" is true (`createMemoryAuthCustodyStorage`, `auth-custody-indexeddb.mjs`), so the Node session custody store is correctly identified as new work.
- **Plane discipline (§Position).** The no-`function.run` rule cites the real dated amendment (LLP 0024 §Dated amendment 2026-07-16: host operations "do not resolve scoped tokens"), the `--args-json` spelling matches LLP 0024's operator CLI, and the LLP 0042 relationship is stated without land-grabbing.
- **Honest hosted story (Motivation, §4).** Verified: the Cloudflare gateway's `/inspect` returns only the capability manifest (`cloudflare/src/gateway.js:63-65`), serves no `/_snapback/*` artifact routes, and LLP 0055 refuses hosted service principals wholesale — the matrix's hosted row is a fair statement of facts plus one named deliverable.
- **Acceptance section with teeth (§7).** Source sentinel extended to the new surface, served-bytes witness, three-way result-contract parity, host-portable code-mode fixtures, the "and only those two" negative test on pre-flags, and typechecking the RFC's own examples against the generated `code-mode.d.ts`. This is the LLP 0010 discipline applied for real.
- **The revision note shows the process worked.** Round 1 already fixed the things a reviewer would most likely flag (two-projection scheme collapsed to one public envelope; bearer-free script host; honest matrix; ibex made non-normative), and `code-mode.d.ts` as a new artifact is correctly motivated — I verified `api.d.ts`'s `FunctionReference` has no call signature.

## 3. Concerns

**C1 (major) — The dev-mode identity lane is misstated and the decision about it is missing (§4 matrix, §2, §7).**
Evidence: the matrix says local dev is "yes (dev mode has no sessions; everyone is anonymous) / n/a / n/a". But dev mode has client-asserted identity: `ResolvedAppAuthority::dev_from_auth` maps a request-supplied `user_id` to `DevImpersonation` which `carries_user()` (`src/auth/invocation.rs:384-400`), the headless client this engine projects sends it (`SnapbackClient.auth(userId)`, `demos/_kit/client.mjs:2174-2175`, threaded through `query`/`mutation` options), LLP 0031 re-scopes `AppAuth` to exactly "dev-mode client assertion", and LLP 0024/0042 expose the same fact as `devUser` on their planes. Consequences as written: on the default local development tuple, the app CLI can only ever invoke as anonymous — every `authenticated` function is unreachable, and per-user flows (e.g. todo's `ctx.auth.userId` scoping) are inaccessible — a silent semantic subtraction from the headless client that contradicts "it introduces no call semantics, identity, or caching behavior of its own" (§Position) in the other direction: it *removes* one. The matrix also presents a false capability fact ("everyone is anonymous") in a section titled "stated as capability facts", and §7's auth matrix would bake it in.
Resolution criteria: decide explicitly — either expose dev assertion behind a dev-only flag with LLP 0042's `devUser` posture (localDevOnly, audit fact emitted, refused under sessions), or refuse it deliberately and say so; correct the matrix parenthetical to describe the CLI's choice rather than the target's nature; reconcile §2's "exactly two client-decidable refusals" enumeration; update §7's matrix to the decided behavior.

**C2 (minor) — Envelope ingestion is specified only for the sessions provision intent; the v0-dev tuple and the envelope-absent case are unaddressed (§5).**
Evidence: LLP 0012 pins the closed `{intent: "provision"}` union for v1-sessions and keeps "legacy untagged ensure input... only a v0-dev compatibility form". The RFC's ingestion amendment extends "the provision intent" — so a dev-mode server provisioned via the legacy form has no envelope, yet the §4 matrix's phase-1 dev row includes served-envelope operation, and nothing says what `GET /_snapback/app-api/envelope` returns when no envelope was ever ingested (older deploys, legacy-provisioned apps). Also, "The envelope is a codegen output (listed in `artifacts.json`)" reads as a present-tense fact; I verified today's `artifacts.json` lists no envelope.
Resolution criteria: state which ensure forms carry the envelope (both tuples, or sessions-only with dev targets relying on the local `generated/` fallback — either is defensible if stated); pin a typed response (e.g. 404 + stable code) for envelope-absent servers; fix the artifacts.json tense.

**C3 (minor) — The version handshake's enforcement direction is ambiguous, and one reading is wrongheaded (§5).**
Evidence: "The version handshake is a contract, not advice, in both directions" followed by "Engine newer than the server expects: same code, `detail` distinguishes the direction." If the server-authored expected-engine range is *enforced* (exit 8 on engine-newer skew), every older server refuses every newer engine even when the envelope's `schemaVersion` tuple is fully admissible — recreating the coordination treadmill the data-driven envelope exists to dissolve, and engine-newer-than-server will be the *common* skew (npx pulls latest engine; server binaries move slowly). If instead the closed tuple set is the sole hard gate and the range is diagnostic detail, the paragraph's first sentence overstates.
Resolution criteria: name exactly which checks hard-fail with exit 8 in each direction; make the LLP 0012 tuple set the sole hard compatibility gate (or justify range enforcement explicitly); demote the server's expected range to the degraded-mode install hint it already powers.

**C4 (minor) — Exit 7's trigger predicate is underspecified while the exit table is frozen (§1, §2).**
Evidence: "on revalidation mismatch the engine refetches (bounded retries, then `SNAPBACK_APP_CLI_ARTIFACT_IDENTITY_MISMATCH`)". A deploy changing the envelope between revalidation and refetch is *normal* (adopt the new envelope), not an error; the genuine error is served bytes whose SHA-256 differs from the server's own advertised header. The text conflates the two, and the multi-process cache-write race is explicitly an open question while the code that reports its failure is already frozen.
Resolution criteria: define the mismatch predicate(s) — bytes-vs-advertised-hash (integrity) distinct from cache-vs-live drift (refresh) — and settle the concurrent-writer rule (the open question) before phase 1 freezes the table, or mark exit 7 provisional until then.

**C5 (minor) — "Change" is defined by canonical-JSON serialization with no canonicalization named (§2, inherited by §3's iterators).**
Evidence: dedupe correctness across resubscribes — and the host-portability claim for code-mode subscription semantics — depends on every host serializing identically (key order, number formatting). The repo has canonical-encoding precedents (LLP 0012's length-framed hashing domains) but the RFC doesn't bind one.
Resolution criteria: name the canonical form (the kit's existing canonical serialization or an RFC 8785-style spelling) as part of the frozen contract.

**C6 (nit) — Result-size ceiling behavior can emit truncated JSON (§3).**
"A stdout size cap with an explicit truncation diagnostic" plus "on any ceiling the parent kills the child" leaves open whether a truncated (unparseable) result reaches stdout. For machine consumers a refusal is strictly better than a truncated payload.
Resolution criteria: pin refuse-and-diagnose (no partial result on stdout), or spill-to-file; never truncated JSON as the result document.

**C7 (nit) — The disclosure sentence undersells one genuinely new public artifact class (§5).**
Verified: public `/inspect` already serves full table shapes (`PublicSchemaManifest.tables: Vec<TableManifest>`) and per-function `authRequirement`, so the d.ts claim holds — but `PublicFunctionDefinition` carries no args validator, so the per-function `operations/*.args.schema.json` files are a *new* public disclosure, not a re-serving of one `/inspect` already makes. Same class, yes; already-made, no.
Resolution criteria: one sentence naming the operations schemas as newly public under the same posture argument.

**C8 (nit) — The RFC's own §Guide obligation is not yet co-landed.**
`guide/capabilities.md` in the working tree has no `clients.app-cli` GAP row while the RFC says it "lands together with" one.
Resolution criteria: same-commit GAP row (working id, owner, review date) when this RFC lands.

## 4. Suggestions (non-blocking)

- **Hash-addressed immutable envelope.** Serve `GET /_snapback/app-api/envelope/<sha256>` (immutable, cache-forever) with `/_snapback/cli` as the tiny current-pointer. The mixed-set race and most of C4's revalidation ambiguity disappear structurally, and offline caches become trivially correct.
- **Stamp `envelopeHash` into every result envelope.** Cheap now, hard to retrofit; it makes `--transcript` replayable against a pinned surface generation and gives `introspect --changed-since` its anchor for free.
- **Runtime reflection in code mode** (`api.$meta` or similar: function list, kinds, arg-schema access) so agents can write app-generic scripts (dump/diff tools) without shelling back out to `introspect`. The static `code-mode.d.ts` covers the typed path; reflection covers the generic one.
- **A `--profile`/`--session <name>` namespace on the session custody store** — agents routinely need two identities against one target to test role behavior, and the custody key (target origin, app id) admits only one.
- **Say how `login` completes on local targets** where the auth provider is capture-only (dev mailbox): prompt-for-code with a pointer at the captured mailbox is fine, but one sentence prevents implementers guessing.
- **Consider `subscribe --count N`** (exit after N changes) alongside `--first-change` — same machinery, and it postpones the day someone asks for a predicate DSL, which the RFC rightly refuses.

## 5. Open questions

The RFC's own open-questions list is good (the surface-restriction knob correctly coupled to `/inspect`; the token-refresh-vs-`--watch` lifecycle; cache concurrency). To it I would add, from the concerns above: the dev-mode identity decision (C1 — the one that must be answered in-document); envelope carriage for v0-dev and the envelope-absent response (C2); the precise hard-fail set of the version handshake (C3); the canonical-JSON binding (C5); and whether `introspect --json` should embed the `/_snapback/cli` capability field so an agent's first contact is one fetch instead of two.

The proposal is sound in architecture, honest in scope, verified accurate in nearly every load-bearing citation, and the acceptance bar is real. It needs one material correction (C1 — a normative matrix stating a false capability fact plus an undecided identity lane on the primary phase-1 target) and precision passes on contracts it declares frozen (C2–C5) before implementation should start against it. These are days of revision, not a redesign.

Three consequences go unanalyzed: (a) LLP 0055 gives the mint route "its own throttle budget" — a hot agent loop is one mint per command, and nothing sizes the budget for that workload; (b) the per-grant cap of 10 live tokens evicts the oldest, so ten quick `call`s under a grant carrier-kill a concurrent `subscribe --watch` on the same grant (the remint/resubscribe machinery self-heals it, but it can thrash); (c) mint latency is added to every call. §7 tests expiry-remint and rotation mid-watch but not cap-eviction-by-sibling-invocation. *Resolution criteria:* state the token acquisition strategy per invocation explicitly (mint-per-command, with the custody rationale), note the throttle-sizing obligation against LLP 0055, and add the sibling-invocation eviction case to §7's subscribe goldens.

**C4. (minor) A sessions target whose active generation predates envelope ingestion has unspecified discovery semantics.** An app provisioned before the LLP 0012 amendment lands has no stored envelope; §5 defines `/app-api/current` as naming "the current envelope SHA-256" and defines behavior for a *garbage-collected* hash (typed 404 → refetch via discovery), but not for "this generation has no envelope at all." Exit 8 doesn't fit (the tuple is admissible); silent absence would strand the engine. *Resolution criteria:* pin the typed response for envelope-less active generations and the engine's degraded behavior (e.g. `--artifacts`-only with the pinned redeploy hint).

**C5. (nit) `--artifacts` pinned against a sessions target makes the specified recovery inapplicable.** §1's mismatch handling is "the engine refetches artifacts and the caller retries" — impossible when artifacts are explicitly pinned to a local directory. Obvious in practice (the refusal stands), but the frozen exit-7 contract should say so. *Resolution criteria:* one sentence on the terminal behavior under explicit `--artifacts`.

**C6. (minor) The source-stripping projection will exist twice, and the document does not name the single source of truth.** Rust owns `PublicFunctionManifest` (exhaustive destructure so new fields force a classification decision — verified); the envelope's nested projection will be emitted by TS codegen. LLP 0037 pins Rust-first single-source with drift gates for shared artifacts. §7's sentinels catch a *leak*, but a field added to `FunctionManifest` and classified in Rust could still silently diverge from what codegen's envelope emits. *Resolution criteria:* name the authority (e.g. the envelope's nested projection validates against the Rust-generated `PublicFunctionManifest` schema in CI, per LLP 0037's existing pattern) in §5 or §7.

**C7. (nit) `pair`'s direction is ambiguous against device-flow intuition.** In LLP 0055's inversion the *user* mints the code and hands it to the agent; `pair` therefore *takes* the code as input. "Present the pairing code" (§4) is accurate (present-to-server) but reads, to anyone primed by RFC 8628-style flows, as the CLI displaying a code. *Resolution criteria:* state the direction explicitly ("the user supplies the code; `pair` submits it with the requested scopes") or give the flag spelling.

# 4. Suggestions (non-blocking)

- **Stamp a script digest into the audit lane.** The §3 audit records carry call identity, function id, and envelope identity; adding the script's content hash (and `run -` vs. file provenance) makes every brokered call attributable to the exact script text at near-zero cost.
- **Design `--transcript` as broker-frame replay from day one.** Since the audit lane and the broker frames share framing, a recorded transcript could later drive a `run --replay` mode that executes a script against recorded results — turning agent exploration into hermetic acceptance fixtures, which is exactly LLP 0010's direction and would also test scripts without a server.
- **Consider a machine-distinguishable sub-code under exit 7.** Integrity failure (bytes ≠ requested hash — tamper/bug; do not blindly retry) and generation race (refetch and retry) demand opposite agent reactions; the diagnostic detail should make the branch trivial.
- **Permit the fixed codegen banner explicitly.** §5's "no comments" rule for served declarations collides with the existing static `// Generated by @snapback/codegen` banner; either strip it in the envelope or scope the rule to source-derived text so the sentinel tests have a precise target.
- **Have `pair` print the follow-up invocation.** With anonymous-as-default, the most predictable agent stumble is pairing successfully and then calling without `--principal agent`; `pair`'s success output should print the exact next command.
- **Landing checklist:** the `clients.app-cli` GAP row does not exist in `guide/capabilities.md` yet (verified); §Guide obligations requires it in the same commit as this RFC — don't let it slip.

# 5. Open questions

Beyond the RFC's own list (which is well-chosen — the surface-restriction knob governing `/inspect` and the envelope together is the right framing):

1. The C1 dev-tuple binding question — the one that must be answered before the exit-code table freezes.
2. Token acquisition economics (C3): is mint-per-invocation the contract, and does LLP 0055 need a dated note sizing the mint throttle for CLI workloads?
3. Server-side envelope retention: how many generations does a sessions target hold (current-only? current+previous for the race window)? The typed-404 path exists, but the retention policy determines how often agents hit it mid-deploy.
4. Is the whole engine POSIX-only, or only its credential-bearing paths? Anonymous `call`/`introspect` need no custody; refusing Windows outright is a fine v1 simplification, but the RFC should say which it intends so the refusal diagnostic is honest.
5. Two concurrent invocations sharing one credential profile: custody stores have advisory locks, but is concurrent mint-under-one-grant from parallel CLI processes a supported pattern or a documented hazard (given the cap-eviction behavior in C3)?

- **Failure semantics for writes (§2).** `outcome: "unknown"` with a durable `clientMutationId` and re-attested, authority-bound replay is grounded in the existing auth-fingerprint-keyed recorded-mutation store; refusing auto-retry and gating cross-generation replay behind an explicit flag is the right agent-safety posture.
- **Sequencing honesty (§6).** Stage (a) needing no server changes is *argued* (binding scoped to sessions tuples; no credentials presented), not asserted; the ibex phase-2 conflict with 0029's one-embedded-entry/no-ingress contract is real (verified) and correctly demoted to a direction with a filed-amendment landing obligation.
- **Acceptance (§7)** reads like it was derived from the failure modes rather than the happy path: forged activation correspondence with recomputed internal hashes, reverse-proxy credential sentinel, redirect sentinels per class, kill-after-mint lease expiry, the two-pre-flags-and-only-those test.

## 3. Concerns

1. **(minor) `code-mode.d.ts` names two different artifacts.** §5 lists the envelope containing "`api.d.ts`, and `code-mode.d.ts`"; §3 pins that the envelope carries "the **app-owned binding declarations** only" and that nothing engine-owned rides the envelope; §2's `types` pins `code-mode.d.ts` as "one merged file: the installed engine's ambient block plus the envelope's app-owned bindings." So the envelope member named `code-mode.d.ts` (bindings only) and the `types` output named `code-mode.d.ts` (merged) are distinct byte-contents under one name, in two frozen deliverables (the envelope member set and the `types` topology). An implementer reading §5 alone would serve the wrong thing or expect the merged file. **Resolution:** rename the envelope member (e.g. `bindings.d.ts` or a structured member key) or add one sentence stating the envelope member carries bindings only and the engine prepends its ambient block to produce the identically named local file.

2. **(minor) The envelope-less network-operation refusal has no exit class.** §5 specifies the envelope-less sessions generation precisely — typed marker on `current`, "not a 404, not exit 8," introspection-only from `--artifacts`, "any network operation is a typed redeploy-required refusal" with a pinned hint — but never assigns the refusal a row in the frozen exit table. Exit 7's three sub-causes (integrity, binding, generation race) don't obviously cover it, and §7 tests "the typed redeploy-required refusal" without naming its code. Since the table is a frozen phase-1 contract, leaving one specified refusal unassigned forces an implementer choice that then freezes. **Resolution:** assign it explicitly (a fourth machine-distinguished exit-7 sub-cause, or its own code) in the exit table or the frozen mapping-table deliverable, named from §5.

3. **(minor) Defensive parsing stops short of served declaration text.** §1 bounds envelope size/counts/depth/`$ref`; §5 has the *server* validate declaration and schema members against the closed permitted structure at admission ("the server checks the structure it will serve"). But the engine's primary threat model for served artifacts is a target that is hostile or compromised — where no honest admission ever ran. In v1 a hostile target can serve arbitrary (size-bounded) `.d.ts` text that `types --out` writes into the developer's editor/CI surface. Not RCE, but it is untrusted network text flowing into local tooling, and the engine already has the canonical declaration grammar to check against. **Resolution:** state that the engine validates declaration members against the same versioned canonical grammar before `types` materializes them (or pull the structured-IR successor into phase 1 for the served path); alternatively, record the residual as accepted with the same explicitness as the loopback decision.

4. **(minor) Phase-1 scope is very large, concentrated in sub-stage (b).** Phase 1 spans: envelope codegen + digest maps; server ingestion with canonicity and correspondence checks; two public routes; call-time generation binding; two attribution wire seams; the Node session custody store with the full POSIX contract; the credential profile DTO; the admission/lease ledger; the exact-token release primitive; the `app-cli.target` descriptor; the shared result core with parity gates; the client-core package lift; the full subcommand engine; code mode with broker, teardown state machine, and audit lane; dual JCS implementations; five dated amendments (0012/0024/0031/0055/0058) plus two ibex filings. The internal ordering of (b) ("each step independently landable") is the right mitigation, and stage (a)'s independent releasability is well-designed, but the coordination risk across five amendment texts — several in actively churning LLPs (0055 is in Review with near-daily revisions) — is the likeliest failure mode of this plan. **Resolution:** none required for Draft acceptance; at implementation kickoff, decompose into a tracked docket (LLP 0032-style or a Linear program) with the amendments as first-class items, so the RFC's prerequisite ordering ("the frozen surface never ships in a pre-shared form") is enforced by tracking rather than memory.

5. **(nit) Exit-9 row wording vs. per-call broker timeouts.** The frozen table's meaning for 9 is "`call`/`subscribe --timeout` or `run --timeout` expired," but §3 maps a *per-call* broker timeout inside a run (default 60s, distinct from `run`'s 120s wall clock) to "the exit-9 class." A frozen table should cover both spellings. **Resolution:** extend the row's meaning to include per-call broker timeouts within a run.

6. **(nit) Related-header gloss for LLP 0060 vs. §4.** The header says 0060 holds "the capability-manifest registry the target-eligibility capability lands in," while §4 pins the `app-cli.target` descriptor as "a dated amendment to LLP 0058 (which owns `supportedCapabilities`) following LLP 0060's structured-descriptor pattern." The header conflates the (0060-owned) future trusted-local capability with the (0058-amendment) eligibility descriptor. **Resolution:** tighten the header gloss to match §4.

7. **(nit) Two acceptance/matrix wordings invite misreading.** (a) §7's "a large intermediate value (the 500-row case) appears in **neither stdout nor stderr**" is true only for a script that does not `console.log` the rows — §3 deliberately passes script-authored console output through; name the fixture's shape so the test doesn't appear to contradict §3. (b) The remote-service row's "yes, once it advertises `app-cli.target`" leaves unstated whether that advertisement is in or out of phase 1 (the hosted row is explicit). **Resolution:** one clarifying clause each.

## 4. Suggestions (non-blocking)

- **Promote `contract --json` from future work into stage (a).** The exit table, per-kind mapping, strict-value profile, and default ceilings all freeze at (a); emitting them machine-readably is nearly free, gives §7 the drift gate the RFC itself notes, and is the single highest-leverage agent-DX item on the future list.
- **Reconsider the lease/admission ledger vs. pulling the token broker forward.** §4's cross-process admission bound, crash-safe leases, idempotent release, and reserved headroom are intricate scaffolding whose stated proper fix is the profile-local token broker; the 0055-amendment text already hedges ("or pulls the token broker forward instead"). If the broker is a few hundred lines behind the same custody lock, it may be *less* total machinery than the ledger it replaces — worth an explicit cost comparison before building the interim.
- **Consider envelope signatures as named future hardening.** The RFC already names pinned-server-key challenge for local listener identity; a served-envelope signature (key advertised via discovery, verified against the cached pin) would extend last-known-good offline trust and pre-build the hosted-distribution integrity story. Fits the existing content-addressing cleanly since it signs the hash.
- **`whoami --all` in phase 1.** Given `--principal auto`'s conflict-refusal, the natural next question an agent asks is "what sources are live?" — the conflict diagnostic can enumerate them, but a first-class listing verb is the cheaper discovery path and the open question already leans this way.
- **Name the guide/capability-index row in the landing checklist explicitly.** The RFC commits to landing "in the same commit as a `capabilities.md` GAP row (`clients.app-cli`)"; the row does not exist yet (correct, since the file is untracked) — make it un-forgettable at commit time.
- The audit lane's per-run commitment could optionally be derivable under a user-authorized `--transcript` session key, so equality claims in captured stderr become retroactively verifiable when the operator opts into full recording — a small bridge between the value-free default and the transcript future.
