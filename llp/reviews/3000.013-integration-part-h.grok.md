## Findings

**High** — `snapback4/packages/snapback4/src/app-journal.ts:21`

`bindIntentStore` applies the "first store this journal has seen" rule only when `dispatched !== false`. Admission writes `dispatched: false` and `storeId: null` before `probe()`, and `observe()` can commit `firstStore` before `before()` commits the binding (`client.ts:350`, `app-online.ts:80`).

Failing scenario: mutate is admitted, the probe records `firstStore: "A"`, then the process dies before `before()` saves. Reopen against store B. `storeId` is null and `dispatched` is false, so the intent is not retired. It is stamped with B and posted. B executes it. The server check does not help, because the client now sends B's id.

Smallest fix: drop the `intent.dispatched !== false &&` conjunct so a null `storeId` is retired whenever `changedStore` is set or `firstStore` is set and different. Same-store reopen still binds: `observeJournalStore` sets `firstStore` to the current store before the comparison, and a matching `firstStore` stays a match.

**High** — `snapback4/packages/snapback4/src/client.ts:778` and `snapback4/packages/snapback4/src/local.ts:1432`

Both `close()` barriers still include `refreshing`. `refreshSession` posts `/auth/refresh` with no abort signal (`auth.ts:47`), and `close()` never resolves `refreshStopped`. `app.close()` waits on that client close (`app.ts:699`).

Failing scenario: a refresh is in flight and the server holds the response. `close()` does not finish until that body arrives. Aborting the mutation does not unblock it. That contradicts Ruling 1 and the new sentence in `CLIENT-AND-OPERATIONS.md` that a later, unkept successor is retired rather than waited for.

Smallest fix: remove `refreshing` from both barriers. Let the refresh POST finish in the background. If it settles after `closed` and the successor was not installed, revoke it instead of adopting it.

Server precondition: a retry that sends the same `store_id` passes `intent_store` (`serve.rs:723`) and then the idempotency lookup, so it is not refused. A different id is rejected before `replay_mutation` / `replay_action` and does not reserve the id. Missing or JSON `null` `store_id` skips the check on purpose; the cross-store bug above sends the new id, so this skip is not what lets that write through.
