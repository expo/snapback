Revision 8 of [3000.011.003.000.001]( /home/ccheever/projects/sb4-w15-prod2/llp/3000.011.003.000.001-production-and-release-shells.rfc.md ) improves text-domain soundness and supersedes the whole-shape conversion. Remaining material concerns below. Each blocks READY.

1. Per-role insert test over-constrains valid schemas.

   §3 requires: test different principals for each role and require a second role for the same unique principal to fail `E_UNIQUE`.

   Counterexample: roster `membership(principal, role enum('member','admin'), UNIQUE(principal, role))` intentionally allows multi-role. Insert `admin` for `P1` after `member` for `P1` succeeds. The prescribed test fails on a correct schema. Counterexample in the other direction: roster with no unique constraint at all. Second insert succeeds. The test as written rejects both.

   The requirement must be conditional on an exclusive `UNIQUE(principal)` shape. As written it mandates mutual exclusion for all rosters.

2. Control-character gate inventory is incomplete.

   §8 inventories: concatenation, count, lower, trim, sha256, tokens, slice, join and matching. §12 gates only lower/trim/concat/slice/join against `U+0001`.

   Counterexample: `enum('a\x01b','c')` through `tokens()`, `sha256()`, `matching()`, `count()`, or `upper()` if that builtin exists. Spec does not say whether each refuses with `E_QUARRY_TYPE` or succeeds. `tokens()` returning a list containing the control character would launder exactly what the gate forbids. Tests pin only "each laundering expression" without enumerating the full set. All text-producing builtins need an explicit allow/refuse row.

3. Roster heuristic creates authority from a name.

   §3 triggers on a column literally named `role` plus "principal identity in a unique key". `principal identity` is undefined. Case, `user_role`, `roles`, and free-text owners are undefined.

   Counterexample: `preferences(role enum, owner TEXT, UNIQUE(owner, role))` where `owner` is a display name, not a principal. The planner still generates `service:ops`-guarded inserts with an explicit target-principal argument bound to free text. §3 calls this "only a preview, not a claim of authorization meaning", but it adds callable provisioning authority. Preview language does not remove the authority consequence. Needs a precise principal-column predicate and a no-op or explicit-review path for name-only matches.

4. Shell draft preservation leaks protected copies.

   §2 preserves "user-authored, initially blank drafts/selections" across release switch and withdrawal. It assigns cleanup of app-copied protected data to the application under LLP 3000.023.

   Counterexample: shell draft starts blank. App runs `draft.set(protectedQuery.value)` on load to allow editing. On authority withdrawal the protected child clears, but the shell draft retains the protected string and remains visible without authority. The spec's "none of these examples prefill" does not forbid this common edit-copy pattern. The shell needs a normative rule. Either drafts that ever received a protected copy clear on withdrawal, or the generated shell must not offer the copy pattern.

5. Corresponding-leaves compatibility leaves key-set variance undefined.

   §12 recurses "through corresponding value leaves" and admits opposing field-bound directions. It does not define correspondence for differing keys, missing optionals, or list element versus scalar.

   Counterexample A: `{a: enum('x')}` versus `{a: text, c: text}`. Counterexample B: `{a: enum('x'), b: text bound 10}` versus `{a: text bound 1}`. Admitting either as compatible for inferred-local rebinding lets a later `x.c` or `x.b` access trap or read unbound text. Rejecting them needs a stated key-set and arity rule. One compiled opposing-directions object test does not cover this.

6. Production-mode default write behavior is unspecified.

   §3 states production mode requires `snapback/*.q`, accepts `--apply` or `--dry-run`, refuses `--web/--expo/--day2` with `E_INPUT` before planning, and calls `--dry-run` mutually exclusive with `--apply`.

   Counterexample: `init --adapt --production` with neither flag. Preview "stays read-only", but the default is not stated. An implementer could default to writing without explicit `--apply`. State the no-flag default is preview with no writes, and state the error code for `--apply` plus `--dry-run` together.
