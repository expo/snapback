### Findings

#### F1 (High) — The fence paragraph says any incompletely answerable query goes `loading` during own pending writes; partial answers do not
- **Where:**
  - `crates/snapback4-lang/src/guide/reads.rs:65-68`: "A query the device cannot answer completely stays `loading` and asks no server while this device holds a predictable pending write…"
  - `crates/snapback4-lang/src/guide/client.md:36`: "A query the device cannot complete goes `loading` while your predictable writes to its tables are pending".
- **What is wrong:** only a *withheld* answer stays `loading`. That means the device answered `loading`, or the answer is a speculative placeholder such as a point read past the horizon. A *partial* answer (`unknown`, not speculative — for example an order that differs from the horizon's) is published as local partial data with `complete: false`. It also asks no server.
  - This is a separate problem from known item (e). F1's branch (`72d772dbb5`) keeps this sentence and appends "an order differing from the horizon's order alone gives partial data (`complete: false`)". After F1 the paragraph contradicts itself, because an order-mismatch query is exactly one "the device cannot answer completely".
  - The RFC's §4 states the mechanism correctly; the cards do not.
- **Evidence:**
  - Code path in `local-query.ts`: `routeLocal` has `withheld = false` and `wantsServer = true`, so it calls `blocked()`. That returns true while fenced, so it calls `recover()`. `placeholder()` is false for a non-speculative answer, so it returns `localCandidate()`, which yields `latest.result`: the partial `{ data, complete: false }`.
  - L3's 104 routing probes (`/tmp/ccp-l3/routing-results.json`) fed real device results through the unchanged `evaluateLocal` under an intersecting predictable write. For `mismatch`, `pageCount` and `thread-order`, all record `"outcome": "partial", "serverCalls": 0`.
- **Proposed fix (folds into F1):** replace the lead sentence in both cards with: "A query the device withholds — it answers `loading`: a total/extremum over input past the horizon, or a point read past it — stays `loading` and asks no server while this device holds a predictable pending write to a table it reads. A partial answer (`complete: false`, e.g. an order unlike the horizon's) is published as local partial data, and also asks no server until those writes settle."

#### F2 (Medium) — The Expo `Thread` hides page one while a later page loads, and the test would pass without the change
- **Where:** `apps/chat-expo/src/Thread.tsx:70`, `data={"data" in read ? items : []}`. `init --expo` copies this file verbatim.
- **What is wrong:**
  - `usePage` sets `read` from the last page. While page two is loading, `read` is `loading` but `items` still holds page one's *current* rows. So every `onEndReached → loadMore` blanks the whole inverted list and loses the user's scroll position until page two arrives.
  - This contradicts the `reads` card line this same change added (`reads.rs:61-62`: "earlier pages remain visible while a later page is unavailable").
  - The guard protects nothing. `Pages.getSnapshot` only takes items from currently-ready pages, and returns `items: []` while page one is loading, so no previous answer can ever be painted.
- **Evidence (Chromium probe, scratch copy of the React harness):**
  - Before `loadMore`, the text was `"Back newest body …"`.
  - While page two was loading it was `"BackUpdating…SendWrites"` (`pageOneVisibleDuringPageTwo: false`).
  - With the guard reverted to `data={items}`, page one stays visible. The official case "Expo read gaps … hiding protected rows" (`react.test.mjs:879`, "read gap hides all previous rows") still passes, so it does not exercise the guard.
- **Proposed fix:**
  - Use `data={items}`, or `data={"denied" in read ? [] : items}` to be conservative.
  - Add a pagination case: page one ready and page two loading must keep page one's rows.

#### F3 (Medium) — A pending intent is labelled "Outcome unknown", with Dismiss, during admission and while its receipt is looked up; the card teaches the same mistake
- **Where:**
  - `apps/chat-expo/src/Thread.tsx:44` saves the intent before `mutate`.
  - `Thread.tsx:89` computes `write = outcome ?? receipt.last`, and `Thread.tsx:95` shows Dismiss for anything that isn't `pending`.
  - `client.md:27`: "An `undefined` receipt is unknown".
  - `react.tsx:257`: `usePendingWrite(op, id).last` stays `undefined` until `client.write(id)` resolves.
- **What is wrong:**
  - `undefined` means two different things: "not looked up yet" and "unknown". Until the lookup resolves, a saved intent shows "Outcome unknown — check the conversation before sending again" plus Dismiss. That happens during admission (IndexedDB commit, or the `createApp` journal) and on reload (the device call queue can be busy during acquisition).
  - If the user dismisses in that window, the draft is still cleared at custody, and a later refusal is never shown. The text is gone. This is the same "earlier refusal disappears" defect this RFC set out to fix.
  - Following `client.md:27`, every app built from the card inherits it.
  - The web starter has had the same pattern since before this change (probe below).
- **Evidence (probe):**
  - During admission: `"…Outcome unknown — check the conversation before sending againDismiss"`, with `dismissOfferedDuringAdmission: true`.
  - After Dismiss → custody → refusal: `draftAfterCustody: ""`, `refusalShown: false`.
  - With the lookup held: the same "Outcome unknown … Dismiss", changing to "Queued on this device" once it resolved.
- **Proposed fix:**
  - In `Receipt`, track `checked` with its own `client.write(intent.id)` lookup, and show "Saving…" for the intent currently in admission.
  - Show "unknown" and Dismiss only when the lookup has completed and there is still no receipt. Show `intent.body` in the unknown state too.
  - Fix the card wording to match. Alternatively, the lead could add a `checked` flag to `usePendingWrite`.

#### F4 (Low) — Expo composer: Edit overwrites the current draft, and a pre-dispatch storage failure is mislabelled
- **Where:** `Thread.tsx:82` (`edit={setBody}`) and `Thread.tsx:51`.
- **What is wrong:**
  - Edit on a failed intent replaces whatever the user is typing, which is a small draft-loss path.
  - When `journal.remember` throws, nothing was dispatched. The message still says "Could not confirm this write … check the conversation before sending again", which implies it may have been sent.
- **Proposed fix:**
  - Fill only an empty draft, or append.
  - For the `remember` failure, say "Not sent: could not save it on this device; your draft is kept."

#### F5 (Low) — `waitSeconds` edge cases
- **Where:**
  - `writes.ts:13-15` against `actions.ts:15-16`.
  - `app-online.ts:125` → `client.ts:129-131` / `:506`.
- **What is wrong:**
  - `mutationWaitSeconds(null)` gives 25, while `act` treats `null` as the default. A device mutate called with `waitSeconds: null` therefore waits 25 s instead of 4 s.
  - In `createApp` online, the first fresh write of a runtime whose store identity is still unknown awaits `/probe` before custody. That fetch has no timeout, so a stalled link blocks `waitSeconds: 0` until the probe returns. The starter doesn't hit this, because the inbox read sets the identity first.
- **Proposed fix:**
  - Use `wait == null` in `mutationWaitSeconds`.
  - Either document "custody may wait for store identification", or bound the identification wait.

#### F6 (Low) — The admission tests cannot catch the key regression
- **Where:** `client-seams.test.mjs:1013-1090` (the native and web tiers).
- **What is wrong:** nothing forces an admission failure in the local tiers with `waitSeconds: 0`.
  - The only refusal checked is `E_WRITE_ID`, which happens in `MutationIds.run` before admission.
  - `client.write(id)` is serialized behind the admit call, so it passes either way.
  - The web tier runs on memory persistence, not IndexedDB.
  - So moving the zero-wait return above `await call(request)` — returning `pending` for a write whose durable admission then fails — would pass the suite. (F2 names the other weak test.)
- **Proposed fix:** add a zero-wait case per local tier where the device's admit call rejects or denies, and assert `failed` (not `pending`) and that nothing is dispatched.
