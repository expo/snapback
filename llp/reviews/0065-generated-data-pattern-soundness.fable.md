# Review: LLP 0065 — Generated data-pattern soundness and declaration floor

## 1. Overall assessment

This is a well-disciplined, honest RFC that does the single most important thing right: it draws a bright, closed line between what may be derived from schema shape (validators, types, ceilings) and what must never be inferred (authorization, visibility, tenancy, authority creation). The three-way fact-class taxonomy in §1 — schema-derived / explicit security declarations / runtime evidence, with runtime evidence bounded to "may prove containment, never widen" — is exactly the right frame and is coherent with LLP 0063 Workstream 6's language nearly verbatim. The deliberately narrow v1 (owner-only CRUD, owner-scoped unique lookup, owner-scoped keyset pages) is the right scope, and the §3 pagination analysis (the third-index-field hazard that would silently skip rows under a strict continuation filter) shows genuine adversarial thinking about its own generator. The document also correctly delineates its authority against the coupled Draft LLP 0080 (owner floor here, query-only `public-read` there), and its §5 posture — the shipped `packages/snapback-codegen/standard-patterns.mjs` is "an implementation candidate and unit-level witness," not a gate satisfier — respects LLP 0063's no-gate-by-assertion discipline.

The residual problems are spec-level, not directional: an existence-oracle default in the generated mutation path that the acceptance criteria cannot witness and that sits inconsistently with both the generated query surface and LLP 0080's pinned behavior; unstated obligations inherited from LLP 0053's `authScopeField` machinery; an acceptance/entry-gate ordering ambiguity with LLP 0063 Step 5; an unpinned interaction with the post-LLP 0055 principal universe; and an unpinned ordering totality for the generated list. All are fixable with pinning, not redesign.

## 2. Strengths

- **§1 Fact classes.** The cleanest statement in the corpus of why read/write sets bound effects but do not prove visibility, why observed executions are lower bounds, and why unique indexes are storage invariants rather than authorization predicates. The fail-closed subset check (observed ⊆ admitted ceiling) with authorization/invalidation consuming the ceiling, never a branch observation, is exactly right.
- **§2 Visibility floor.** Mandatory explicit declaration with a pre-output failure (`SNAPBACK_STANDARD_PATTERN_VISIBILITY_REQUIRED`), all four effects mandatory, owner field server-set and non-transferable, and the explicit note that `authScopeField` metadata "is not treated as enforcement" — which correctly tracks LLP 0053's rule that class metadata may never override a captured dependency's verdict.
- **§2/Revised header 0080 delineation.** The explicit statement that 0080's `public-read` is a separate query-only authority that neither creates public CRUD nor weakens this floor closes an otherwise easy cross-document laundering argument. 0080 §3 reciprocates ("V1 admits LLP 0065's owner profile"), so the two Drafts are mutually coherent.
- **§3 Pattern contracts.** Closed options objects (misspelled options fail rather than being ignored), the exact `[visibilityField, cursorField]` unique-index shape with the correct skipped-row justification, the refusal to synthesize offset pagination, complete-field updates instead of guessed partial-patch semantics, and `id` never admitted for principal or foreign-ID fields. The implementation at `packages/snapback-codegen/standard-patterns.mjs` matches these contracts closely.
- **§5 Gate honesty.** The RFC self-limits: while Draft, it satisfies nothing and promotes nothing. This matches LLP 0063 line 1479's entry-prerequisite row exactly.
- **Open questions** are the right ones, especially Q3's refusal to let undecidability become an optimistic fallback.

## 3. Concerns

1. **MEDIUM — Existence-oracle posture in generated mutations is unpinned and unwitnessed.** §2 says missing vs. invisible rows use distinct stable codes internally and "public targets **may** project them to a common refusal when existence secrecy requires it." The implementation makes the leaky posture the default (`SNAPBACK_ROW_NOT_FOUND` vs `SNAPBACK_ROW_NOT_VISIBLE` in `ownedRowGuard`): a caller probing update/delete with a known id learns whether another owner's row exists. Meanwhile the generated `get` query returns empty for both cases, so the pattern set's two surfaces have contradictory secrecy postures; and LLP 0080 §3 pinned the opposite default for the relational surface ("invisible joined row behaves as absent … a target may collapse … but the server's structured trace records which predicate refused"). No acceptance bullet witnesses any of this — "cannot observe or mutate another owner's row" does not cover observing its *existence*. **Resolve:** pin the default (collapse at the public boundary, distinct codes in the server trace, mirroring 0080 §3), name the codes in §4, specify who decides "requires it," and add an acceptance negative test that the public refusal is indistinguishable. (Severity is MEDIUM rather than HIGH only because document ids are ratified UUIDv7 and thus effectively unguessable; ids do leak via URLs and logs, so the oracle is real.)
2. **MEDIUM — LLP 0053's `authScopeField` obligations are not carried into acceptance.** 0053 pins that `authScopeField` is an explicit, never-inferred disjointness claim, that a **retainable** query using it must carry the LLP 0008 L4-style convergence fixture, and that test/dev profiles run convergence assertions for every authorization-sensitive skip. 0065 auto-emits `authScopeField: ownerField` on every generated query but (a) never states the retainability posture of generated queries, (b) never requires the convergence fixture, and (c) never argues why deriving `authScopeField` from the visibility declaration is "explicit" rather than the inference this RFC bans (it is sound — the declaration is mandatory and its semantics coincide — but the argument must be on the page, since this is the soundness authority). **Resolve:** add one paragraph pinning retainability and the derivation-soundness argument, and an acceptance bullet requiring the 0053 convergence fixture for any retainable generated query.
3. **MEDIUM — Acceptance/entry-gate ordering with LLP 0063 Step 5 is circular as written.** §5 requires "the Step 5 Partitime receipt proves the frozen backend-declaration reduction without relaxing its threshold" before Accepted; LLP 0063 (line 1479) makes 0065 acceptance an *entry* prerequisite for the very step that produces that receipt, and the reduction rule's number "freezes at the first attribution run" per §Product choice — an event outside this RFC. The intended resolution (run the receipt pre-entry as a witness, claim the gate only after acceptance) is plausible but nowhere stated; 0080's parallel bullet says "Partitime **or the admitted Step 5 fixture**," a formulation 0065 lacks. **Resolve:** either adopt 0080's fixture phrasing plus an explicit "the receipt run is a pre-acceptance witness, not a gate claim" sentence, or decouple: soundness acceptance = semantic witnesses only, with the declaration-reduction receipt remaining LLP 0063's `STEP5.DECLARATION_REDUCTION` gate.
4. **MEDIUM — The post-LLP-0055 principal universe is unaddressed.** The owner profile binds every read and guard to `ctx.auth.userId`, and generated functions "require authenticated authority." The corpus now includes sealed service principals, delegated agent authority, and a `kind`-keyed `ctx.auth` (0053 §Agent-auth protected-query inputs). 0065 never pins whether a non-user principal satisfies "authenticated" for generated operations, what `authUserId()` denotes for one, or whether a delegated agent acting for user X may exercise X's ownership. **Resolve:** pin admission explicitly (e.g., generated owner operations require a principal that projects a user id; any other principal is refused with a stable code — or state that delegation resolves to the delegating user's id under 0055's rules) and add a negative acceptance case.
5. **MEDIUM — Generated list ordering is not provably total.** `listOrder` defaults to a field on which ties are possible, with no `_id` tie-break pinned — in contrast to 0080 §1, which mandates "deterministic ordering ending in the root `_id` tie-break." Nothing in §5 witnesses cross-target result determinism for generated queries (the byte-identical bullet covers *artifacts*, not result bytes). If LLP 0007's portable query rules already totalize ordering, cite that; if not, this is exactly where SQLite vs. pure-evaluator row order diverges. **Resolve:** pin a tie-break (or restrict `listOrder` to unique-per-owner fields), and add a cross-target determinism acceptance case for at least one generated query with duplicate order-key values.
6. **LOW — Trusted `now` type is unpinned.** §3 says "their schema field type must match" without saying what type `runtime.now` yields; the implementation admits `Integer` *or* `Real`. Pin the portable timestamp representation (0007's JavaScript-safe integer profile suggests integer milliseconds; `Real` timestamps invite cross-target float trouble). **Resolve:** name the admitted field type(s) in the RFC.
7. **LOW — Ownership-transfer rejection has no named witness.** "Update cannot transfer ownership" rests on argument-schema omission plus `additionalProperties: false`. The acceptance bullets test client-supplied `now`/`id` rejection but never name the test that a client-supplied owner field is rejected on create *and* update. **Resolve:** add it explicitly; it is the floor's central promise.
8. **LOW — §3 refusals lack dedicated acceptance bullets.** The unique-index refusal, the pagination exact-shape refusal (the RFC's best hazard analysis), and the closed-options refusal each have diagnostics in §4 but ride on the broad "every claimed pattern has an executable receipt." Name the negative generation cases so the receipts are checkable against the list.
9. **LOW — Index-first tension for list/get.** 0007 pins "unbounded production queries must use indexes"; the generated owner list is limit-bounded but scans by an unindexed owner predicate, and unlike lookup/pagination the CRUD helper requires no owner index. Not a soundness hole, but note the scan characteristics or have the helper require (or emit) an owner index.

## 4. Suggestions

- Add a **posture-parity acceptance case**: a generated operation and a handwritten equivalent produce identical auth requirements, refusal codes, and read summaries. LLP 0063's Step 5 acceptance says "generated operations carry the same authorization posture as handwritten ones" — nothing in 0065's list witnesses that equivalence directly.
- State explicitly that the floor is **per-operation, not a table invariant**: a handwritten function on the same table may legitimately transfer ownership or read publicly; the generated guarantees survive because enforcement is predicate execution per operation. A future table-level visibility contract (all functions on a table must be consistent with a declared table visibility) would be a strong follow-on and would close the "one stray handwritten function undermines the tenant story" gap.
- A non-standard idea consistent with the inference ban: a **diagnostic-only visibility lint** that flags declared tables with fields named `ownerId`/`userId`/`tenantId` that carry *no* visibility declaration and are exposed through unauthenticated functions. It creates no authority and generates nothing — it only nags — so it converts the RFC's own "failure mode 1" into a detector instead of a generator.
- For open question 1, the cleanest shape is probably a generated shadow compound continuation `(sortKey, _id)` carried opaquely in the cursor (0080 §2 already pins that cursors may carry boundary keys the projection does not expose) — reusing that rule here would keep one cursor doctrine across both RFCs.
- Name the runtime refusal codes (`SNAPBACK_ROW_NOT_FOUND`, `SNAPBACK_ROW_NOT_VISIBLE`, `SNAPBACK_UNIQUE_CONSTRAINT_VIOLATION` on generated create) in §4 so the public surface is fully enumerated in the authority document, not only in the implementation.
- Mention optimistic-concurrency posture for complete-field updates (last-write-wins within read-set validation) so authors do not assume a version precondition exists.

## 5. Open questions

- What is the pinned public-boundary refusal posture for update/delete on a missing vs. invisible row, and who owns the per-target override (RFC open question 4 — it should be answered before acceptance, not left open, since the acceptance suite must test one behavior)?
- Are generated standard-pattern queries retainable/offline-capable under LLP 0053's lease rules, and if so, which acceptance artifact carries the mandatory `authScopeField` convergence fixture?
- What does `authUserId()` denote for a sealed service principal or delegated agent, and does "authenticated" admit them for generated owner operations?
- May the Step 5 Partitime declaration-reduction receipt be produced before Step 5 entry as an acceptance witness, and what happens if the reduction threshold has not yet frozen when 0065 is otherwise ready?
- What portable type does `runtime.now` bind to for trusted `now` defaults, and does 0007's ordering rule already totalize the generated list order or must this RFC pin an `_id` tie-break?

## 6. Verdict

Verdict: NOT READY

The direction, taxonomy, and scope discipline are right and the coupled-document coherence with 0080/0063 is largely sound, but five MEDIUM issues — the unwitnessed existence-oracle default, the uncarried 0053 `authScopeField`/convergence obligations, the Step 5 acceptance-ordering circularity, the unpinned principal-universe interaction, and non-total list ordering — are each pinning-level fixes that must land before this can serve as the accepted authorization/visibility floor Step 5 waits on.
