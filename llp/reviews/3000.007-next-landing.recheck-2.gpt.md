## New D — High: a direct return loses the collector registration

Using the public `items` fixture, four rows, and `c = null`:

```quarry
query directReturn(c: cursor ?):
  for i in items[] after c last 5 by byN:
    return [i]
  return []
```

This returns one row without a cursor but now reports `complete: true`.

The original analysis registers this exiting page loop. However, the new backward analysis handles `Return` by recording demanded variables and setting `relevant`; it **never adds the enclosing loops to `collectors`**. Only demanded assignments and pushes do that. Consequently, the new filter removes this loop’s registration. See [page_collectors.rs:23](snapback4/crates/snapback4-core/src/engine/page_collectors.rs:23) and [pages.rs:31](snapback4/crates/snapback4-core/src/engine/pages.rs:31).

At execution, the remaining three rows therefore do not set `interrupted`: [runner.rs:224](snapback4/crates/snapback4-core/src/engine/runner.rs:224). The short scan has no continuation, so neither term of the loss predicate detects it: [read.rs:651](snapback4/crates/snapback4-core/src/engine/read.rs:651).

**Introduced by round 2.** Removing the new collector filter restores the previous incomplete result.

**Regression gap:** the existing program-return fixture pushes into `result` before returning, which registers the loop and conceals this omission: [helper_pages.rs:107](snapback4/crates/snapback4-sim/tests/common/helper_pages.rs:107). The generated page programs likewise always push before exiting; they never generate a direct return from the loop.

## New E — Medium: discarded intermediate output permanently poisons the complete final output

Again with four public rows and `c = null`:

```quarry
query replacedResult(c: cursor ?):
  result = []
  for round in range(0, 2):
    result = []
    for i in items[] after c last 5 by byN:
      result = result + [i]
      if round = 0:
        break
  return result
```

The first iteration collects one row. The second **discards that collection**, executes the same scan site, and collects all four rows. The returned value contains the entire exhausted page, with no missing rows or necessary continuation.

Nevertheless:

1. Static returned-value flow registers the inner loop because its pushes contribute to the final iteration’s result: [page_collectors.rs:37](snapback4/crates/snapback4-core/src/engine/page_collectors.rs:37).
2. The first iteration’s break marks its page interrupted.
3. The second scan transfers that interruption into `discarded_page_loss`, without checking whether the earlier output still contributes: [read.rs:643](snapback4/crates/snapback4-core/src/engine/read.rs:643).
4. The permanent bit forces `complete: false` after the second iteration has returned everything.

**Introduced by round 2.** The previous replacement behavior reports this particular complete result correctly. Preserving A’s loss requires distinguishing contributing executions from overwritten intermediate results.

**Regression gap:** `overwrittenCollector` tests an overwrite after one loop, allowing static liveness to remove that loop entirely. It does not test different executions of the same loop: [page_loss.rs:68](snapback4/crates/snapback4-sim/tests/common/page_loss.rs:68). The generator neither resets its accumulator between executions nor changes whether it breaks between iterations: [page_loss.rs:135](snapback4/crates/snapback4-sim/tests/common/page_loss.rs:135).

Both D and E affect server and device queries through the shared loss predicate: [engine/mod.rs:661](snapback4/crates/snapback4-core/src/engine/mod.rs:661), [local.rs:35](snapback4/crates/snapback4-core/src/engine/local.rs:35).
