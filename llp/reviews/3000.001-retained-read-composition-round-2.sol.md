## Scope expansions

### Compatible backend adoption

Keeping images when `tables` and `maintains` are equal is sound.

`Table` equality includes residency, defaults, columns, indexes, rules, constraints, leave policy, sync policy and expiry (`snapback4/crates/snapback4-core/src/schema.rs:212-235`); `Sync` includes audience and horizon (`schema.rs:303-329`). The older literal-default alternative also projects each successor table back to exact old-table equality, including rules/sync/leave, and requires identical maintains (`snapback4/crates/snapback4-core/src/successor.rs:188-213`). Therefore an old row cannot survive this predicate if the successor changed the rules governing whether this viewer may read it.

The surrounding lifecycle remains coherent:

- `ACQUIRED` is cleared for identical-table program changes, so retained images are inaccessible until reacquisition (`device.rs:269-280,380-393`; `device.rs:209-221`).
- Confirmed bases beneath predictions are overlaid into the retained snapshot before publication (`snapback4/crates/snapback4-device/src/device/snapshot.rs:11-35`), then predictions are restored and replayed under the new programs (`device.rs:541-615`; `device/predictions.rs:57-93`).
- `STAGED_GROUPS` is cleared on adoption and the next first snapshot clears stale staged rows (`device.rs:390`; `device.rs:508-515`).
- Maintained definitions are required equal.
- Memory-store schema-hash projection and index rebuilding still run; with identical tables they cannot destructively alter a row (`snapback4/crates/snapback4-device/src/memory.rs:231-256`).
- Native metadata and the owner-local module are invalidated (`device.rs:388-400`).
- Backend identity includes schema, sorted programs and generation, so older owners become obsolete (`snapback4/crates/snapback4-device/src/device/store_identity.rs:15-32`).
- Replacement publication clears visible rows and publishes only newly acquired rows or rows classified left by the staged group map (`device.rs:541-565`).

The expansion deserves more direct cross-product tests for staged snapshots, predictions, native modules and maintained values, but inspection found no concrete failure.

### Client incarnation bump

The bump safely fences reads and does not gate or duplicate unrelated work.

It gates local read retries (`local.ts:787-820,879-880`), sync request/application captures (`local.ts:552-591,655-657`) and watch publication (`local.ts:921-943`). Adoption produces one finite bump, and the sync `finally` reruns watches once; `running`/`dirty` coalescing prevents a rerun storm (`local.ts:680-684,921-943`).

It does not gate the outbox sender or in-flight writes. Those remain serialized through the existing network/send-revision mechanisms (`local.ts:958-1053`), so the bump neither strands nor duplicates an entry. Asset reconciliation is awaited as part of the successful adoption call, and asset homes carry generation (`snapback4/packages/snapback4/src/local-assets.ts:14-16,73-92,120-136`). I found no unsafe interaction there.

## Findings

### Medium — LLP 3000.007 §18.2 describes the pre-fix algorithm

`llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:1844`

It still says the client “composes retained components” and that the contract card is unchanged. At IMPL_COMMIT, every component that would stay local is copied, and the card changed.

Concrete scenario: a delayed `three()` server reply contains the old `current` row; meanwhile that row is deleted locally. The implementation publishes `current: []`, but §18.2 says the non-retained field comes from the server, describing resurrection of the deleted row.

Smallest fix: rewrite the implementation paragraph to include the full current eligibility and routing contract: one read per field, no reading guard, point hits, retained-plus-server entry, all locally routed fields from the second observation, and pending-write suppression.

Section 18.3 remains literally true, but it now needs a sentence distinguishing the broader program-only case: identical tables/maintains retain images and group history but clear acquisition and reacquire; literal-default evolution retains its narrower acquisition behavior.

### Low — the pending-write exception is attached to the wrong case in public prose

`snapback4/packages/snapback4/README.md:1163-1167`  
`snapback4/crates/snapback4-lang/src/guide/sync.rs:131-135`

The pending-write phrase appears only in the sentence about a mixed query “without a component plan.” Actual code suppresses both composition and ordinary server fallback whenever a predictable write awaits observation (`local.ts:870-873,892-893`).

Concrete scenario: `both()` has a valid component plan and an unobserved predictable write. The whole local answer stands; the paragraph does not state that contract for a planned query.

Smallest fix: add the plan’s explicit sentence: “Composition is never entered while a predictable write is unobserved; the whole local answer stands until it settles.” Make the guide test require that sentence rather than only the substring at `snapback4/crates/snapback4-lang/tests/guide.rs:1192-1200`.

### Medium — the LLP claims an IndexedDB qualification that did not occur

`llp/3000.001-durable-replica-and-write-lifecycle.research.md:453`

“the IndexedDB composition witness qualify this round” conflicts with the journal: Chromium exited before the page existed and the run cannot be claimed (`snapback4/JOURNAL.md:29103,29143,29147`).

Concrete scenario: a browser-only transaction/reopen defect remains undetected, yet a later reader treats the LLP sentence as completed browser evidence.

Smallest fix: change line 453 to “the IndexedDB witness scenario was added and awaits browser execution,” or run it successfully and record the receipt.

### Low — `completeOnly` does not prove the server route named by its assertion

`snapback4/packages/snapback4/test/retained-history.test.mjs:223-227`

The test asserts `fresh: true` and the `current` field. A caught-up first local answer is also fresh (`snapback4/packages/snapback4/src/local.ts:859-863`) and contains the same `current` row, so a mutant that returns the local answer without requesting the server passes.

Smallest fix: also assert `held` contains all 26 server rows rather than the device’s 25, and assert that `/q/completeOnly` was requested exactly once.

## Required explicit answers

**Did a fix introduce a new problem?** Yes: the all-locally-routed-components fix made LLP 3000.007 §18.2’s formerly accurate “retained components” wording wrong, and the fix text newly overclaims an unexecuted IndexedDB qualification. I found no new product-code correctness, durability or safety regression. The added scenarios do increase test time, but that is intentional qualification cost.

**Is there a regression test that would also pass without the change it claims to test?** Yes.

- `completeOnly` at `retained-history.test.mjs:223-227` passes without proving server routing; it should assert 26 held rows and the `/q/completeOnly` request.

These are useful qualification cases, not fix regressions; they should be labeled as such. If intended to test the adoption fence, they need an epoch-changing adoption and an assertion that the old reply is retried, which `MQ adoption` already provides at `retained-history.test.mjs:245-249,316-319`.
- The positive planner controls, named corpus participation assertion, complete-only entry control, and point-miss subcase intentionally pass without their adjacent fixes. They are controls, not regression failures.
- Rotation, prediction and retained-snapshot scenarios have no recorded b5 red-before result. Their assertions are meaningful lifecycle qualification, but they should not be cited as evidence that a fix was killed.
