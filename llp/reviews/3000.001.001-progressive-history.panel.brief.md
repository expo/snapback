## 1. Proposal

A person opens a messaging app on a new phone. Their account has a thousand
conversations and years of messages. The inbox appears from the server, the
conversation they open becomes available offline first, recent history from
other conversations follows, and older selected history fills in behind it.
The app stays usable and says that offline history is still syncing. Losing
the connection halfway through preserves the history already made usable.

Make acquisition incremental in **what the device can safely read**, as well
as in what it downloads. Publish a server-certified newest-first suffix of a
conversation after its rows, authority dependencies and changes through a
finite server cut are durably installed. Extend that suffix toward the
declared sync horizon in later turns. Keep one interpreter, ordinary queries,
the declared replica and the existing write owner.

Schedule open conversations first; give every discovered conversation a
recent slice before spending all background capacity on one conversation's
older history. Priority changes order, never authorization, the declared
working set, or the eventual obligation to finish it.

This is a proposed extension, not implemented behavior or implementation
authorization. The user commissioned this RFC on 2026-11-02. Implementation
belongs to the Snapback 4 core owner under LLP 3000's ownership rule; acceptance
must name that implementer and a start date. No performance result or review
verdict is claimed here.

## 3. User-visible contract

For an ordinary newest-first history query:

1. Online, render the server answer as today while acquisition proceeds.
2. Once its requested range and dependencies are durably covered, the same
   query can answer locally even while `client.acquired` remains false.
3. Offline, that range remains readable, including after closing and reopening
   the app. Its answer is stale, with the existing `fresh` / `since` metadata.
4. Scrolling beyond the local floor returns known rows with incomplete
   coverage, or an unavailable/loading result where the query cannot safely
   produce a partial value. It does not claim the conversation has ended.
5. Online scrolling can still page older server history beyond the declared
   sync horizon. It does not silently enlarge the persistent working set.

“This page is complete” means this page is covered. “Offline history ready”
means the entire declared acquisition has completed. Neither means every
message ever sent is stored on this device.

An illustrative sequence, not a timing claim:

| Moment | What is usable | Indicator |
| --- | --- | --- |
| Signed in, device opening | Server inbox and server history | Preparing offline access |
| First foreground slice published | Latest 50 messages in the open conversation, locally | Syncing offline history… |
| Background slices published | Recent history in additional conversations | Syncing offline history…; optional received/usable counts |
| Connection lost | Published ranges; queued writes under existing custody rules | Offline · some history is not downloaded |
| Reopened offline | The same published ranges | Same incomplete-history indication |
| Declared acquisition finishes | All selected history and other declared synced data | Offline history ready |

Fifty is an example query page, not a new required batch size. Media bytes
retain their separate caching and authorization rules; message availability
does not promise that every attachment is downloaded.

## 4. Authoring and scheduling

### 4.1 Keep the existing declaration and query

No new Quarry spelling is required for the first increment. A representative
existing shape, assuming `threads` and `participants` are declared, is:

```quarry
table messages:
  conversation: threads
  body: text <=2000
  at: time
  read <- exists participants[.conversation, viewer]
  retain delivered-history
  sync to participants[.conversation] by .personId last 500 by .at, .id

query history(c: threads, page: cursor ?):
  return messages where .conversation = c last 50 by .at, .id after page
```

The binder derives an acquisition target when a query pins one audience group
and reads on that group's horizon index. A mounted `useQuery` / `usePage`
observation gives that target a foreground scheduling hint. The hint names
the existing table, group and requested frontier internally; it is not a row
list or an application-maintained sync queue. Multiple observations coalesce.
Unmounting removes the hint, not downloaded data or background responsibility.

A scalar count, global search, unsynced table or unsupported query shape does
not invent an acquisition plan. It retains ordinary routing. Headless query
calls may give a bounded one-turn hint; they do not create permanent priority.
No public manual-priority API is required initially.

### 4.2 Recent coverage across conversations

The scheduler has three obligations, in this order of urgency:

- Process identity, revocation, expiry and changes needed to keep published
  data valid. Background preference never delays a known authority fence.
- Serve interactive queries/writes and acquire foreground history targets.
- Discover the remaining declared groups and acquire their history fairly.

Use bounded work turns, sharing the existing request, byte and meter budgets.
As an initial internal policy, at least one of every four acquisition turns
goes to background work when background work is pending; foreground targets
rotate among themselves. This is a starting policy to measure, not a builder
configuration or a wall-clock guarantee under overload/offline conditions.

Background turns rotate between group discovery and data acquisition. Among
discovered groups, prefer groups with no published recent slice before
deepening already usable ones. Within each class, use recent head keys where
the same table's declared order supports that comparison, with aging to avoid
starvation. New groups cannot indefinitely displace an existing group's next
turn. Head discovery is paged, metered and authorized; do not synchronously
probe every conversation before serving a foreground one.

This promises **foreground first, recent slices broadly, then older history**.
It does not promise a strict global reverse-chronological merge. Knowing the
newest message across every conversation would require inspecting all their
heads or maintaining a separate account index. Unknown groups and unrelated
table orders cannot honestly participate in that guarantee. A timestamp order
expresses application recency; an arbitrary id order is not relabeled time.

Changing the foreground target takes effect at the next bounded scheduling
boundary. An active request may finish; it must not monopolize the pipeline.
A requested old page inside the declared horizon deepens a contiguous suffix
toward that page. It does not create a disconnected island of cached rows.

## 5. Coverage is a property of the replica

### 5.1 Publication unit

The first supported unit is a contiguous descending suffix on one
single-audience table's existing horizon index, plus the authority/structural
facts necessary to evaluate that history locally. A unit is identified by
store identity, authenticated principal, schema generation, membership epoch,
table, index and group. Its floor is a full encoded key including tie-breakers.
`whole` proves exhaustion; an empty payload alone does not.

For each such group persist:

- The published floor, or unknown if none has been established.
- The acquisition continuation and whether the declared target is finished.
- A private candidate's base cut and continuation while it is being prepared.

Keep one common applied cut for the currently published live image. A cursor
that has scanned the change stream does **not** certify coverage of an
unacquired group. Coverage and delivered position must remain separate facts.
Private candidates can have individual base cuts; application queries never
combine arbitrary per-group snapshot times as one complete live result.

The amount of durable coverage metadata grows with declared groups, not the
number of queries, screens, scroll positions or subscriptions. A query reuses
the table/group floor, including after every observer has unmounted.

### 5.2 A safe read before full acquisition

Replace the blanket full-acquisition gate only where the interpreter can
prove the actual read's coverage:

| Read | Required evidence |
| --- | --- |
| Descending history page | Its audience prefix, authority dependencies and scanned range lie inside a published suffix; ordinary page/meter rules still apply. |
| Found point row | Published row with valid authority and lifetime; existence does not establish the surrounding range. |
| Missing point / `exists = false` | The key's domain is covered; merely not finding a staged or unacquired row proves nothing. |
| Count, unread total, anti-join or other derived scalar | All required input domains and dependency facts are covered. A recent slice cannot supply a whole-history total. |
| Cross-conversation read | Every required domain is covered at the common live cut, or the existing partial/server-routing semantics apply. |
| Explicit `held` read | Stays device-only, with truthful coverage; it cannot silently fall back online. |

Use the existing runtime coverage frames and binder plans. A missing
dependency makes the result unknown; it is never replaced by an empty table,
zero count, false boolean or fabricated membership witness. Initially keep
profiles, receipts, reactions and quotes as separate queries beside history,
as the existing guide recommends.

The common cut applies to current live data. Retained history after leave
keeps its existing separate stale/composition semantics; this proposal does
not relabel retained rows as current live rows.

## 6. Acquiring and publishing a slice

### 6.1 Server selection and finite cuts

An acquisition request is a scheduling request against the declared replica.
The server authenticates it and derives/validates the group and index from the
served schema. It refuses arbitrary audiences, unsupported shapes and requests
outside the declared target. An opaque continuation binds the viewer, store,
generation, membership epoch and selection frontier; changing any of them
invalidates that continuation. Client-provided priority is never authority.

Select a bounded next range and its required authority facts in a consistent
server read transaction, recording its base cut B. The reply states the exact
range covered and the acquisition target's continuation. For an extension,
the range adjoins the previously certified floor without a gap. If budget
runs out, certify only a range whose entire selection and rule evaluation
completed, or return no certificate and a continuation/refusal. An output
truncation is not exhaustion.

Each range is a short snapshot operation; the proposal does not require one
database transaction or MVCC snapshot held open for the entire account
download. The bounded selection must fit the existing meter on SQLite and
Postgres. Dependencies that cannot fit keep the unit private until a supported
acquisition plan proves them; they do not justify raising a ceiling.

The per-group target uses the declared horizon and the existing snapshot's
finite traversal semantics. New traffic enters through the change stream;
it does not restart the target or continually demand a new exact top N.
Concurrent deletion or movement can leave fewer than N rows above a certified
floor, as it can today. At a quiescent server, completion must produce the same
selected working set as ordinary full acquisition. Whole-table acquisition
without a horizon retains its explicit exhaustion requirement.

### 6.2 Catch-up cannot silently contain future images

A candidate selected at B must be reconciled with all applicable changes
through a finite publication cut P, where P is at least B and the already
published live cut. P is fixed for that publication attempt; new writes above
P do not move its finish line. Replay includes deletions, key moves, grants,
revocations, expiry, structural dependencies and write acknowledgements.

This needs an explicit new wire capability. Existing log hydration can serve
a row's current image, which is not sufficient evidence that the image belongs
to a requested historical cut. Do not reuse it while silently asserting exact
cut semantics. For this protocol, require immutable, revision-qualified row
images and tombstones for the replay interval, including dependency changes.
The implementation must account for their server storage and write costs.
Older intervals lacking that evidence force a new consistent base selection;
they cannot authorize publication.

The replay endpoint stops at P and preserves complete commit boundaries.
Existing write-outcome fences remain necessary even with revision-qualified
images. A row image alone still does not acknowledge a pending write.
Control changes cannot be filtered out because their content group is not yet
downloaded. An unknown group's row changes need not be kept indefinitely on
the device: a later base selection at B includes its state, and replay covers
changes after B. This optimization must not skip authority or receipt handling.

Bound in-flight candidates and replay lag. If required replay evidence is no
longer available or a candidate exceeds its resource allowance, restart that
private candidate, retaining valid published history. Do not pin an unbounded
server log or buffer every account change in browser memory. Overload can
delay readiness and must be visible; it cannot justify a false coverage claim.

### 6.3 One durable publication transaction

Before publication, verify that the candidate still belongs to the current
identity, generation and membership epoch. Bring its range and the already
published live domains to the same P. Commit together:

1. Confirmed row changes and affected indexes, including authoritative
   removals within the newly certified range.
2. Authority/structural facts and any withdrawals through P.
3. The new floor, target continuation and common applied cut.
4. The existing prediction-base and write-outcome transitions required by
   those changes.

Only after durable success notify observations and progress listeners. A crash
before commit leaves the previous published floor and data intact. A crash
after commit reopens the new range as usable. A partially written range can
never be paired with its completed floor. On web this includes IndexedDB
durability before publication; on native it is the device-store transaction.

Only one publication advances the live image at a time. If another operation
advances it beyond a candidate's P, rebase that candidate to a new finite cut;
never regress the live image. The scheduler must reserve publication turns so
ordinary ongoing sync cannot repeatedly outrun and starve every candidate.

Later history extends coverage downward. Normal stream changes continue to
update published ranges during acquisition, so a busy account does not freeze
its newest messages until all old history arrives. Apply each stream commit
atomically over all affected published domains and authority facts.

### 6.4 Whole-partition completion

Group enumeration must itself have a resumable, server-certified completion
boundary plus membership changes through a finite cut. A count of groups seen
is not proof that discovery finished. Foreground requests can bypass discovery
for an authorized pinned group, but cannot mark enumeration finished.

Set `client.acquired = true` only when discovery is complete, every currently
required target is finished, and all required data/control changes through the
completion cut are durable. Reconcile joins/leaves through that cut; changes
after it follow ordinary live-sync semantics. Continuing writes do not require
the account to become quiet. Unsupported tables remain part of this obligation.

## 7. Authority, retention, writes and observation continuity

- **Revocation:** a scope tombstone invalidates candidates from that membership
  epoch. Until-revoked rows and floors withdraw together. Delivered-history
  keeps only history already published under the acquiring identity; private
  staging is not newly retained history. Rejoining needs new coverage proof.
- **Expiry and delayed disclosure:** reuse the persisted server-clock and
  lifetime rules. Never deliver unopened payloads. Expired rows cannot become
  visible because an older acquisition reply completes late.
- **Identity and schema:** replacement or sign-out retires old work before it
  can publish. Same-store regression keeps the existing restore refusal.
  Adoption decides retention and reacquisition using the successor classifier;
  it cannot blindly reuse an old floor under a new index or audience rule.
- **Writes:** durable admission does not require complete acquisition. Keep
  the existing dispatcher/journal/outbox owner. Initially, partial publication
  adds no new prediction eligibility: retain the current acquisition/prediction
  guards. Writes lacking the required facts queue or run online as today.
  Never grant prediction just because the visible history page is covered.
- **Predictions already present:** apply new confirmed images through the
  existing base/outcome fences. An in-flight mutation, ambiguous response or
  cross-tab receipt cannot be overwritten or replayed twice by a slice commit.
- **Observations:** local results compete with server results under the
  existing store/cut and own-write fences. Becoming locally covered is not
  permission to replace a newer server answer with an older one, reset a
  revocation deadline or remount a query. Existing page accumulation deduplicates
  by row identity. Online cursors are not reinterpreted as local cursors;
  retain validated continuation rules or explicitly restart the page chain.

Offline access has the same limitation as current offline replicas: a device
cannot learn a remote revocation while disconnected. Known revocation and
known expiry must still take effect immediately under existing policy.

## 8. Progress and UI

Preserve existing meanings:

- `app.ready`: usable client/custody, not acquisition completion.
- `useLocalStatus()`: the engine may be executable while state is `syncing`.
  `ready` / `acquired` retain their full-acquisition meaning.
- `useAcquisition().rows` / `.tables`: received snapshot row-image counts,
  not a percentage and not evidence that those rows are readable.
- `Read.complete`, `fresh`, `since`, loading and refusal: truth about the
  particular query, independent of the whole-account progress indicator.

Propose one additive acquisition field, `usableRows`, counting distinct
confirmed rows in currently published acquisition domains. It includes their
published dependencies, excludes private staging and speculative inserts, and
can decrease on deletion, revocation or expiry. Reopening restores it from
durable state; it is not reset merely because the process restarted. It is
neither a message count nor a total to sync. Maintain it transactionally rather
than rescanning the whole replica on every UI update.

This optional detail lets an app distinguish “downloaded” from “available
offline.” A simple app needs only the existing hooks:

```tsx
const acquisition = useAcquisition();
const link = useLink();
const history = useQuery(api.history, { c: conversation, page: null });
// Render history through the existing read handlers, independently of this label.
const syncLabel = acquisition.acquired
  ? null
  : link === 'online'
    ? 'Syncing offline history…'
    : 'Offline · some history is not downloaded';
```

This is an illustrative fragment inside the existing provider, not a new
loading gate. Applications with no local device do not show an offline-sync
indicator. Surface a typed storage, permission or unsupported-device failure
through local status rather than showing an endless active-sync message.
An interrupted connection pauses acquisition; already published reads remain.

Do not add an ETA or percentage without a measured denominator. Discovery,
concurrent writes and horizon changes make “rows downloaded / rows currently
known” a misleading completion percentage. Do not say all conversations are
available merely because some tables have published rows.

## 9. Scope, compatibility and costs

First implement newest-first history on single-audience, horizon-indexed
tables with immutable audience keys and a provable bounded authority dependency
plan. Include until-revoked and delivered-history, timestamp ties, expiry,
empty groups, restart and continued live writes in that increment.

Union audiences, inherited child families, timelines, owner-key coverage and
arbitrary aggregates retain their existing acquisition barriers until their
dependency and publication plans are separately proven. Their rows still sync;
they do not keep an independent supported history range from becoming usable.
The implementation must separate those legacy staging domains so completing
them cannot overwrite newer progressively published history. Full acquisition
still waits for all of them. If the implementation cannot preserve that
separation for a schema, negotiate whole-acquisition behavior for that schema
and report why; do not partially enable an unsound plan.

Negotiate the protocol and persisted format through the existing engine/device
handshake. Old clients keep the old full-acquisition path. New clients against
old servers retain existing server fallback and atomic full publication.
Partial floors must never be serialized as legacy whole-partition readiness.
Older engines must refuse an incompatible upgraded store before reading it.
Migration preserves published rows, retained history, pending writes and
outcomes transactionally; no storage-clearing upgrade recipe is acceptable.

The same coverage and persistence semantics apply to wasm/memory+IndexedDB
and native SQLite. Web startup's existing early-engine-loading behavior does
not automatically become a native startup promise. Worker mode may improve
responsiveness, but is not evidence of publication correctness or a latency
bound.

Costs to measure explicitly: more small transactions, dependency reads,
per-group metadata, immutable replay images, log retention pressure, disk
writes, network overhead, index maintenance, wasm bytes and foreground
contention. The design replaces the whole-history publication barrier for
supported domains; it must not leave two independent background acquisitions
downloading the same account. No new service, application-side sync database,
per-query receipt system, or general arbitrary-range offline cache is proposed.

## 10. Verification and delivery

### 10.1 Correctness witnesses

Extend the existing simulator and server/device differential tests. Observe
every publication boundary, not only the final converged state. For a read
claimed complete, compare its confirmed result to the authorized server model
at its cut, then apply only the predictions permitted by existing policy.
Retained history uses its existing retention oracle rather than current server
authorization after leave.

Required cases:

1. Publish a recent slice in conversation A while B is unacquired; disconnect
   and restart. A works, B is unknown, and global `acquired` is false.
2. Page exactly to the floor, across it, through timestamp ties and into a
   proven-empty group. No fabricated end-of-history or absent row.
3. Insert, edit, delete and move ordering keys during selection, replay and
   publication. No gaps certified by stale row counts; no image beyond P.
4. Revoke/rejoin between each protocol step, including a delayed old reply.
   Test both retention policies and the private-versus-published distinction.
5. Apply one commit touching two published groups and an unpublished group;
   no torn current read. Later acquisition cannot resurrect deleted state.
6. Crash or fail persistence before/after every staging, floor and cursor
   write; abort leaves the old readable image, successful commit survives.
7. Send and settle writes during acquisition, including predictions from an
   existing store, ambiguous receipts, cross-tab ownership and offline capture.
8. Switch foreground conversations repeatedly under continuous traffic;
   old replies stay harmless and each eligible background target gets turns.
9. Replace/restore the backend, adopt a generation, sign out and switch viewer
   during acquisition; no cross-identity publication or retained-data leak.
10. Resume discovery with joins/leaves, exhaust replay retention, hit a meter,
    encounter unsupported dependency shapes and negotiate old/new peers.
    Refusal or fallback preserves truthful coverage and valid usable ranges.

At quiescence, compare final rows, floors and query answers with the existing
full-acquisition oracle. Run the critical cases on both durable host adapters,
including actual browser close/reopen and native process restart. A server
answer displayed before disconnect is not an offline witness.

### 10.2 Performance acceptance

Use the existing heavy messaging fixture and a second account with ten times
the unrelated older backlog. Pin declarations, device, server, network and
hardware; include cold browser and native runs. Compare the current path with
the proposal using equal declared data and record individual runs and medians.

Measure time to first server screen, first durably usable foreground page,
first recent page in each sampled conversation, and full acquisition separately.
Also record interaction latency, maximum main-thread stalls, bytes transferred,
peak memory, server work, replay bytes, disk writes and resumed-download work.

Acceptance requires a disconnected-and-reopened foreground page **before**
full acquisition finishes, bounded foreground work independent of unrelated
backlog after a directly authorized target is known, and demonstrated background
progress under sustained foreground activity. Discovery work must be reported,
not hidden outside the clock. Full-sync throughput and first-screen latency
must be compared, not sacrificed without a recorded decision. The proposed
initial regression budget is at most 25% median full-acquisition slowdown on
the pinned heavy fixture; accepting a larger cost requires an explicit tradeoff.
Absolute latency targets should be set from measured transfer/storage floors
before implementation qualification, not invented by this RFC.

### 10.3 Delivery sequence

1. **Model the protocol.** Add scoped publication and exact-cut replay to the
   simulator model. Prove the counterexamples above, finite-cut progress and
   the persistence transaction before changing public readiness behavior.
2. **Build the engine/device seam.** Add capability negotiation, bounded group
   discovery/selection, revision-qualified replay and durable partial floors.
   Keep it opt-in while the single-group witnesses run on both adapters.
3. **Integrate queries and scheduling.** Admit supported partial reads, infer
   foreground hints, add fair background turns and preserve existing answer
   and write fences. Add progress reporting and the messaging example.
4. **Qualify and expose.** Measure the heavy accounts and host restart cases;
   reconcile the scope fence, parent and guide/reference with what is built.
   Change the default only after the scoped evidence supports it. Publication
   uses the existing qualified path; ordinary landings use affected checks.

No new complete-battery-at-exact-HEAD landing requirement is introduced.

## 11. Alternatives and decisions for review

**Only prioritize network download.** Helps transfer order, but provides no
offline value before the current publication barrier. It does not satisfy the
disconnect-halfway scenario.

**Only retain server query answers.** Can make a screen reopen, but lacks the
declared replica's range, deletion, query composition and write-base semantics.
It would reintroduce the result-cache architecture the project rejected.

**Publish each whole conversation.** Simpler than slices and a useful internal
milestone. A large or unbounded conversation still delays the very history the
person is looking at; it is insufficient as the final behavior.

**Strict global newest-first.** Adds a cross-group ordering/index obligation
before first useful data. Prefer foreground targets and fair recent slices;
revisit only if measured product behavior requires strict global ordering.

**Independent visible cuts per conversation.** Reduces replay coordination but
makes cross-conversation queries and multirow commits harder to describe.
Prefer one common cut for the published live image and private candidate cuts.

The principal review decision is whether earlier durable offline usefulness
justifies revision-qualified replay and per-group publication complexity. If
not, keep current online-first startup and describe its offline limitation
plainly; do not weaken the coverage proof. Remaining implementation choices
are the exact bounded dependency fragment, replay-image representation and
retention allowance, and measured scheduler batch sizes. Those choices must
preserve the contracts above, particularly finite progress, unchanged authority,
no false absence and durable reopening before full acquisition.
