## Ranked concerns

**1. Critical — settlement evidence cannot support the handoff the screen sketch needs.**  
§10 admits the principal risk; it is still material. `arrived` is set when any delivered row carries any reserved id (`range-store.ts:1139–1142`), including fan-out `deliveries` rows from `edit`/`unsend` (`deliveries.q:18–34`). Overlay retirement also treats any predicted id, negatives, cursor-chain progress, or two misses as custody facts (`range-store.ts:946–1032`), not “this query returned this message.”  
*Failure:* an unpredicted edit is hidden when a sibling delivery row lands, or it stays “committed / awaiting delivery” forever because no inserted id exists. §11 still lists that handoff as an acceptance test.  
*Smallest fix:* specify per-op retirement against landed evidence before any collection API: a selected target readable (or an authoritative negative/tombstone) at or after commit. If that cannot be derived, the collection may only show “committed / awaiting delivery” and must not claim seamless handoff. Repair the runtime seam in its own change.

**2. High — `observeCollection` plus fluent `.create/.update/.remove` is more apparatus than the honesty requires.**  
The query entry already reevaluates when outbox/overlay change (`query-inputs.ts:4–10` on the architecture snapshot). A second resource keyed by descriptor identity adds lifecycle, identity, and torn-read surface for what is a pure join. The fluent builder is a second TypeScript authoring dialect; `ids[0]`, `belongs`, and `draft` are easy to get wrong; Snapback 2’s rule is to add no apparatus (`RULES.md` Agents). Current join logic is ~6 obvious lines, not `shared/log.ts`.  
*Cost:* every list screen learns a mini-ORM; two components with accidentally distinct descriptors split snapshots or transports.  
*Smallest fix:* no new observer type. Optional join spec on the existing observe/useQuery path, or a pure `attachWork(snapshot, outbox, spec)` like `summarize`. Keep `client.outbox.observe()`.

**3. High — create `key: intent => intent.ids[0]` is an unconfirmed convention.**  
1012 §7: first id names the intent; the rest are the `new` envelope. The template uses `ids[0]` as `messageId` (`Thread.tsx:23–27`). Those can diverge.  
*Failure:* draft and server row get different keys; the pending bubble remounts; predicted creates duplicate as tail items.  
*Smallest fix:* pin the key against one queued and one committed `post` fixture before shipping the binding. Do not encode `ids[0]` as SDK vocabulary.

**4. Medium — §9 suppresses drafts on denied/refused queries, contradicting §7.**  
§7 says pending-only items must not flip status to `ready`. §9 then hides those items. Today `unplaced` still renders when `view.data` is empty (`Thread.tsx:21–27`).  
*Failure:* a denied thread hides the user’s own queued send; they only find it in a global outbox.  
*Smallest fix:* keep `status`/`receipt` as query truth; still attach scoped drafts. Suppress only on account reset/replacement, as 1018.000 §4 already requires.

**5. Medium — predicted `remove` has no in-list action.**  
A predicted unsend deletes the overlay row (`twin.ts:257–258`); `select` drops nulls; §8 will not resurrect a body.  
*Failure:* the message vanishes with no “Unsending…” and no in-thread dismiss if it later fails, until the row returns.  
*Smallest fix:* allow a body-less action item keyed by the target id for in-scope removes whose target is not readable, without inventing message fields. Otherwise document that predicted deletes are outbox-only.

**6. Medium — derived hide of committed work vs unbounded `entries()`.**  
Stopping hook `dismiss` is right (`react-core.tsx:278–286`), but `settledResult` also dismisses on online settle (`client-outbox.ts:139–141`). Leaving every committed intent in storage is honest; a default outbox view that lists them is not.  
*Cost:* outbox UI and tests grow without a retention decision the proposal defers.  
*Smallest fix:* define the default outbox projection as “still awaiting delivery or needs explicit dismiss.” Leave raw `entries()` and compaction as today.

## Smaller alternative

Keep shared `outbox.observe()`. Do not add `useCollection` / `observeCollection`. Attach a data spec (not a fluent builder) to the existing query observer, which already sees outbox/overlay:

```ts
export const threadMessages = {
  table: "messages",
  select: (d: Delivery) => d.message,
  order: "reverse" as const,
  create: { op: api.deliveries.post, belongs, key, draft },
  update: { op: api.deliveries.edit, key: a => a.messageId },
  remove: { op: api.deliveries.unsend, key: a => a.messageId },
};

const thread = useQuery(api.deliveries.thread, args, { attach: threadMessages });
// thread.data, status, receipt unchanged; thread.items is presentation
```

Headless: `attachWork(snapshot, outboxView, threadMessages)`.

Tradeoff: you lose a dedicated collection resource and fluent chaining. You keep one transport, one publication, one conceptual object (`summarize` + `attachWork`), and the same honesty.
