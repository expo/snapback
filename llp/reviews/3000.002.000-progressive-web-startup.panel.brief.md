# LLP 3000.002.000: Useful web data before the local runtime

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 web client, app identity and readiness, online and local observations, durable browser writes, WASM loading, React, SSR
**Author:** Codex, requested by Charlie Cheever
**Date:** 2026-10-29
**Revised:** 2026-10-29
**Related:** [LLP 3000.002](./3000.002-end-to-end-resource-bounds.research.md#browser-startup-loading), [LLP 3000.013](./3000.013-quarry-states-intent.rfc.md#6-a-paved-client), [LLP 3000.013.000](./3000.013.000-a-browser-write-journal-without-the-device.rfc.md), [LLP 3000.001](./3000.001-durable-replica-and-write-lifecycle.research.md), [LLP 3000.001.000](./3000.001.000-device-engine-handshake.rfc.md), [LLP 3000.023](./3000.023-answers-stay-on-screen.rfc.md), [LLP 3000.028](./3000.028-one-query-online-or-offline.rfc.md), [LLP 3000.038.000](./3000.038.000-durable-offline-media-intents.rfc.md)

## 1. Proposal

A local-first Snapback web app should show authorized data and accept durable
ordinary writes without downloading or initializing the local interpreter.
It should gain local execution, prediction and offline reads in the background,
through the same application object and hooks. A returning device with usable
local state should take the faster local path, including when offline.

The desired end state remains under 100 KB for all compressed SDK JavaScript
and WASM needed for full local operation, excluding the app and React. This
RFC uses a sub-100-KB initial gzip budget as a near-term fallback; deferred
bytes still count toward the full runtime, whose size remains separate work.

Make these three events independent:

1. The application has established its current identity and durable authority.
2. The application can serve useful data and own new writes.
3. The local runtime and replica can take over the relevant work.

Keep the shared Rust interpreter and the complete local feature set. Use the
existing online client and browser admission mechanisms for the first phase.
Add an app-owned coordinator for observations, pending writes and the transition
between execution paths. Do not construct two independent apps and swap them.

This RFC proposes a behavioral change, not another packaging-only optimization.
The author requested it after observing that roughly seven seconds to first
local data remained unacceptable. Writing this Draft does not commission its
implementation or establish that the proposed latency targets have been met.

## 3. Existing mechanisms and constraints

The current paved surface is recorded in
[`CLIENT-AND-OPERATIONS.md`](../snapback4/packages/snapback4/reference/CLIENT-AND-OPERATIONS.md).
The relevant implementation boundaries are:

- [`app.ts`](../snapback4/packages/snapback4/src/app.ts) opens a provisional
  local client before publishing its signed-in scope. Its `online` arm is
  attached to that published owner, so it is not an early-read escape hatch.
- [`client-start.ts`](../snapback4/packages/snapback4/src/client-start.ts)
  separates prepare, commit and activate. Extend that ownership model instead
  of letting two independently restoring clients race to own the session.
- [`app-online.ts`](../snapback4/packages/snapback4/src/app-online.ts) and
  [`online-capture.ts`](../snapback4/packages/snapback4/src/online-capture.ts)
  already support durable browser writes without the interpreter. The online
  journal and device outbox are distinct recovery owners today.
- [`react.tsx`](../snapback4/packages/snapback4/src/react.tsx) follows the app's
  client and auth publications. Keeping these identities stable matters for
  mounted observations, forms and pending-write handles.

The implemented authority, custody and observation rules remain binding:

- Durable session replacement, logout epochs, credential fencing and
  cross-tab checks follow [LLP 3000.013 §6](./3000.013-quarry-states-intent.rfc.md#6-a-paved-client).
  A localStorage credential mirror is not authority.
- A browser write needs synchronous capture and durable recovery under
  [LLP 3000.013.000](./3000.013.000-a-browser-write-journal-without-the-device.rfc.md).
  A promise queued only in memory is not a captured write.
- Read retention follows the current amendments in
  [LLP 3000.023](./3000.023-answers-stay-on-screen.rfc.md), including §12.
  A transition must not prolong stale authorization or restart a retention deadline.
- Local execution still needs the actual device's
  [engine handshake](./3000.001.000-device-engine-handshake.rfc.md).
  Server answers cannot stand in for a compatible local engine.
- [The scope fence](../snapback4/NOT-DOING.md) keeps one Rust interpreter,
  declared-partition replication and the existing read vocabulary. This
  proposal adds no persistent per-query result cache or second interpreter.

## 4. Readiness and the authoring surface

Introduce progressive startup as an explicit browser option during qualification.
The following spelling is a proposal, not a shipped API:

```ts
const app = createApp({
  url,
  sessionStore: localStorageSessionStore(),
  device: webDevice({ worker: true }),
  startup: "progressive",
});
```

`AppProvider`, `useQuery`, `usePage`, `useMutation`, `usePendingWrites` and the
ordinary app methods keep selecting the execution path internally. A builder
does not maintain duplicate online/local screens, subscriptions or mutation ids.

| Surface | Meaning in progressive mode |
|---|---|
| `auth.state` | Identity and authority state. Engine download alone does not keep a validated scope `restoring`. |
| `app.ready` | Initial restoration has established a usable client and the required write-custody gate, or returned a typed refusal. It does not promise a complete replica. |
| `Read<T>` | The existing data/loading/denied contract, with truthful completeness, freshness, expiry and revalidation metadata. |
| `client.acquired` | Its existing replica acquisition meaning. A server answer does not set it. |
| Proposed local-status observation | `loading`, `opening`, `syncing`, `ready` or `unavailable`, with a typed cause where relevant. Useful for an offline indicator, not required around every query. |

The local-status API must distinguish an executable engine from an acquired
replica and from safe local write ownership. It must not advertise full offline
readiness merely because compilation finished. The final shape is an API review
item; it may expose those dimensions separately rather than overloading `ready`.

The explicit option protects existing callers that currently use `app.ready`
as a local-opening barrier. Native clients keep their current behavior. After
qualification, make progressive startup the normal web starter path and
document the new readiness meanings in the same release. Do not silently
change the default while readiness assumptions remain unaudited.

## 5. Startup paths

### 5.1 First visit with a network

1. Load the small SDK and render the application.
2. Establish identity, authoritative session state, backend store identity and
   admission ownership using the online path. Reuse metadata on existing
   authenticated responses where possible. Do not require the full schema,
   partition snapshot or engine stamp to authorize a server read. If the
   existing replies lack sufficient bootstrap metadata, add a small validated
   envelope; do not substitute an unauthenticated local hint.
3. Publish the usable app and run foreground queries through the online client.
   Ordinary mutations use the durable host journal described in §7.
4. Load and prepare the complete local runtime in the background. Normally
   start the bulk download after the first foreground result, so it does not
   compete with that result for a slow connection. If there is no foreground
   read, begin after the initial render. Use a bounded scheduling policy so
   a stalled read or continuously busy page cannot starve local preparation;
   its timeout and bandwidth tradeoff must be measured, not assumed.
5. Restore and synchronize the device, then transition eligible observations
   and write ownership under §§6–7.

No first query, sign-in completion or ordinary durable mutation may await WASM
solely because `device: webDevice()` was configured. Network loss and missing
authority can still prevent those operations; those are separate conditions.

### 5.2 Returning visit, including offline

Race valid cached local restoration against online startup. Do not force a
working cached device through a server round trip or redownload its engine.
Use a small durable ownership record to discover existing device custody
before starting an online sender. Unknown or older ownership metadata invokes
the existing local recovery path; absence must be established, not guessed.

Existing local pending writes cannot disappear behind an online answer or be
overtaken by new online sends. Where their read footprint is not yet known,
withhold affected observations conservatively until recovery establishes it.
If that requires holding every query, do so and report the warm-start cost.
The cold-start target is not permission to weaken read-your-writes on reload.

| Condition | Behavior |
|---|---|
| Cached compatible engine and replica, offline | Restore local reads, predictions and pending writes under existing authority/expiry rules. No network is a prerequisite. |
| First-ever visit, offline | Report unavailable data honestly. There is no replica to invent. |
| Engine download, compilation or compatibility fails | Keep valid online operation available, report local unavailability, and preserve pending custody. Do not sign out merely because the engine failed. |
| Storage cannot own a write | Preserve the existing explicit admission refusal. Never fall back to an in-memory queue presented as durable. |
| Logout, replacement account, store replacement or rollback evidence | Apply the current fences to both paths immediately; discard or retire state only under the existing rules. |

The offline application shell must retain all deferred assets from the same
build. Cached WASM alone cannot boot a page whose required JavaScript is absent.

### 5.3 Scheduling and the worker

Use the existing worker device where supported. Move expensive preparation off
the UI thread where feasible, including cache conversion and compilation, while
keeping page-side synchronous admission and the engine handshake intact.
The current worker path still performs some preparation on the page; enabling
`worker: true` alone is not proof that startup cannot block input.

Interactive requests take priority over background acquisition. A foreground
operation that genuinely needs local state may explicitly accelerate preparation.
Do not use `window.onload` or an idle callback as an unbounded readiness gate.
Workers and HTTP caching improve execution and repeat visits; neither removes
the cold download or justifies putting it back before first data.

## 6. One observation across online and local execution

The app owns a stable observation whose internal producer may change. Warming
the engine must not remount the component, reset the form, flash `loading`,
drop a pending row or replace a newer result with an older replica image.

A local candidate can replace an online result only after the coordinator checks:

1. The same current authority source, session epoch, principal and credential
   revision authorize publication. Same principal alone is insufficient.
2. Backend/store identity and program generation match, and the local engine
   is compatible with that program.
3. The device has applied the committed server basis needed by the displayed
   answer and subsequent relevant evidence, and reconciled affected pending
   writes. `acquired` alone is insufficient.
4. The candidate belongs to the same query, arguments and observation lifetime,
   and has passed the existing expiry, scope-loss and final publication checks.

Use internal commit/head, generation and observation evidence already carried
by the wire and clients where it is sufficient. Exposing the required evidence
between the two producers is implementation work. If an existing reply cannot
prove the necessary ordering, keep that observation online until a suitable
fresh evaluation establishes it. Add narrowly scoped metadata only where needed.
**`Read.since` is a wall-clock freshness timestamp, not a commit barrier.**

Both producers feed the same invalidation and authority fences during overlap.
A revocation or expiry learned on one path cannot wait for the other path to
become ready. Retained results keep the existing deadlines; a handoff does not
renew them. Promotion installs a checked snapshot and its subscription together,
then retires the old producer. A late callback from the retired producer cannot
publish, but a known terminal write outcome must still reach its receipt owner.

Pagination keeps cursor affinity: an opaque server cursor stays with the server
producer that minted it. Do not pass it to the device or append local pages to
that chain. Transition at a checked first-page refresh or keep that page session
online. Existing mixed queries and online-only operations keep their current
execution/composition rules under LLP 3000.028; engine availability does not
make every operation local or every answer complete.

A successful local evaluation is not sufficient if it answers less of the
query than the current online/mixed route can. Preserve the required coverage
and pending-write presentation when promoting; legitimate new commits may of
course change the result. If offline fallback can supply only a partial or
stale answer, apply the existing explicit read contract rather than presenting
that loss of coverage as a seamless successful upgrade.

Only the existing bounded observation state is retained. This is not a new
durable query cache, permission receipt system or replica filled from arbitrary
query results. Declared partitions still supply the device's data.

## 7. Durable writes before and during the transition

### 7.1 One logical owner, existing physical stores

Reuse the synchronous capture and online journal from LLP 3000.013.000 for
initial ordinary writes. The coordinator remains the app's identity and custody
owner throughout startup. The device outbox remains the local executor's store;
this RFC does not pretend those two physical journals become one atomic database.

Every admitted id has one recorded recovery/dispatch owner. The record retains
its original operation, arguments, principal, authority source/epoch, backend
store binding, admission order and any already-fixed execution inputs such as
time or generated ids. An execution-path change never mints a replacement id.
Existing per-owner ordering and cross-tab rules remain; this proposal adds no
new global ordering guarantee across independent tabs.

Before identity and store binding exist, keep the existing explicit
identity/admission-wait behavior. Do not call an in-memory wait durable capture.
Once the scope is usable, a same-turn navigation after admission must leave the
write recoverable even if WASM has never been requested.

The first implementation need not predict startup writes in JavaScript.
`pendingIntents`, pending-write status and server acknowledgements remain usable
while prediction is unavailable. The proposal preserves the Rust prediction
semantics rather than implementing a second evaluator to animate the first click.

### 7.2 Ownership transition

The preferred mechanism is a durable coordinator record plus idempotent import,
building on the existing claim, journal and prepare/commit/activate machinery:

1. **Prepare.** Open the candidate device with delivery paused. Restore known
   custody, validate identity and synchronize. Opening the candidate does not
   authorize its sender or an independent session rotation loop.
2. **Fence the old dispatcher.** Serialize the transition under the current
   authority and queue locks. Record a transition generation. New captures
   remain durable in the host journal while their execution route is held.
3. **Reconcile.** Settle known outcomes and import eligible, never-dispatched
   intents idempotently with their original inputs. A copied device record is
   staged and cannot dispatch merely because it exists.
4. **Commit ownership.** After durable import acknowledgement, commit the new
   owner generation. Only that generation may activate local delivery. Retire
   the source record only after its destination ownership is recoverable.
5. **Publish.** Update pending-write views and eligible predictions without
   changing ids or losing receipt subscriptions. Accept late known outcomes
   through their receipt owner without reviving an old dispatcher.

A lost HTTP response is **not** proof that a mutation was never dispatched or
never committed. Initially, issued/unknown startup writes retain their original
owner and reconcile through the existing same-id retry/receipt mechanism.
They may delay local write cutover and dependent predictions; they must not
delay unrelated online reads. A deadline may abandon the attempted cutover
and continue online operation, preserving every record and ordering obligation.
If reconciliation requires retrying through the fenced dispatcher, abort the
transition and resume its original ownership before retrying; do not grant it
temporary sending authority alongside an activated device.
Cancellation of a fetch does not establish that server execution stopped.

This conservative treatment avoids claiming a solved migration of uncertain
requests. If it proves too restrictive, transferring an issued/unknown write
needs an explicit protocol for its original request identity, predictions,
ordering and late outcomes before it can be added. Server deduplication alone
does not prevent duplicate local predictions or lost result notifications.

Cross-database atomicity is not assumed. Recovery must distinguish intent to
transfer, durable destination import and committed ownership. After a crash
there may be two records, but only one authorized dispatcher. A worker restart,
orphan-tab adoption or older tab cannot bypass that owner generation. The
persistent format/version fence and exact lock order are acceptance blockers
to resolve before coding this transition; existing clients must fail closed
rather than ignore a new ownership record.

### 7.3 Scope that must survive

Known `sent`/`failed` outcomes stay known if receipt persistence fails. Logout,
account switching, global logout and store replacement apply to capture,
import, recovery and dispatch, including while initialization is held. A later
sign-in cannot revive an earlier epoch's intent. Receipt replay retains today's
limits on historical result values and server receipt retention.

Media intents keep their durable bytes, cancellation and placement ownership
under LLP 3000.038.000. Ephemeral signals and actions keep their existing
online semantics; they must not be promoted into durable ordinary mutations.
An intermediate read-only prototype is useful evidence, but disabling writes
or media until WASM opens does not complete this RFC.

## 8. SSR as an additional fast path

Support server-rendered initial results through the same observation coordinator
after the client-only progressive path works. SSR can put useful content in the
first HTML response, but does not by itself solve browser writes or local handoff.

A hydration record must bind the authorized identity/scope, backend/store,
program generation, query/arguments, response basis and expiry needed to decide
whether it can seed this observation. It contains no session bearer or privileged
server credential and grants no authority to execute a later request. Serve
private HTML/data with correct per-user isolation and caching behavior.

Reject a record that does not match the browser's current validated scope;
account change, expiry and newer invalidation evidence win. Use the existing
read freshness and retention semantics during revalidation. Do not silently
turn an SSR payload into IndexedDB replica rows or a persistent query cache.
The exact serialization and framework adapter API are a later increment, not
an additional prerequisite for fixing the ordinary client-rendered page.

## 9. Performance and correctness acceptance

These are **proposed targets**, not current measurements or new CI gates.
Extend the existing production-build and browser witnesses rather than creating
a separate benchmark framework. Keep first paint, first useful data, first
durable interaction and full local readiness as separate measurements.

| Check | Proposed acceptance |
|---|---|
| Initial SDK download | Less than 100,000 B gzip, compressing emitted resources individually; React and authored UI reported separately. Count resources actually fetched before first data, not only static imports. |
| Cold first useful data | On the same 1.6 Mbps / 150 ms / 4× CPU profile: median ≤1 s, p95 ≤1.5 s for the defined small populated screen. |
| Engine independence | Hold or fail WASM for 30 s. Authentication, authorized online reads and ordinary durable writes still work; no readiness promise for those operations waits on the held engine. |
| Warm offline first data | With a cached compatible shell, engine and small acquired replica: median ≤500 ms, p95 ≤1 s. Include restored pending writes as a separately reported case. |
| Interaction while preparing | Scripted input-to-next-paint p95 ≤100 ms and no preparation-induced stall above 200 ms in that fixture. |
| Steady local performance | Compare identical acquired data/workloads with the current local client; no material regression in query/mutation latency or retained memory. Investigate >5% median regression rather than trading it silently for first paint. |
| Full local readiness and total bytes | Report both from navigation, including background traffic and retries. Any regression must be explicit; deferral is not a total-byte saving. |

Use at least 20 fresh-context samples per cold variant, with alternating order
and disclosed host/browser/build, compression, response sizes and backend timings.
Use production authentication with a restorable session and a real nonempty
screen, such as 50 short messages, not an empty inbox or placeholder. Measure
first-ever sign-in separately from session restoration. Report the whole-page
transfer including React/UI as well as the SDK budget. Repeat on a physical
low-end device before making a mobile-performance claim.

The first-data target applies to this defined fixture, not arbitrary large
queries or slow application servers. Run the larger partition/hub fixtures too
and report their acquisition costs without letting them gate the small first
screen. If the target is missed, retain the trace and revise the design or the
proposed target explicitly. A shell painting quickly is not a substitute pass.

Required behavioral cases include:

- Cold start, cached online start, fully offline reopen, partial acquisition,
  blocked/missing WASM, incompatible engine and failed cache/storage commits.
- A write and same-turn navigation before engine download; crash/reload at
  each transfer step; response lost after commit; repeated import; late result;
  receipt persistence failure; continued typing and writes during cutover.
- Existing local debt on return, two tabs, orphan adoption, worker termination,
  old/new client versions sharing storage, account change and logout at each
  readiness/ownership boundary.
- Revocation, expiry, generation change, store replacement and backup rollback
  learned independently by either producer. No stale fallback or leaked data.
- Active observations, pending rows, pagination cursors, mixed queries, media
  intents and server-only operations across handoff. No duplicate rows or
  unjustified reset of the current screen.

Use the existing session/custody models and fault-injection tests as well as
Chromium. Passing a latency probe cannot waive any of these guarantees.

## 10. Delivery and decisions still needed

The proposed implementer is the Snapback 4 client/core lead; a single owner
should carry the app lifecycle and custody changes. The sequence is:

1. **Trace and specify.** Extend the existing populated/authenticated startup
   witness and finish the ownership and observation-basis protocols below.
2. **Progressive reads.** Add the explicit mode, independent readiness and stable
   observation coordinator. Hold WASM in the real browser witness. This is an
   intermediate result, not completion while writes still wait on the engine.
3. **Progressive writes and recovery.** Complete early durable custody, safe
   local cutover, return-visit recovery, version fencing and media behavior.
4. **Qualify the full path.** Test both worker/direct hosts where supported,
   performance, faults, docs and installed consumer builds. Only then change
   the web starter/default and publish the capability claim.
5. **Add SSR adapters and continue the device diet.** Neither blocks the first
   usable client-rendered screen. Reassess full-runtime size with attribution.

Before accepting implementation, resolve:

- The exact owner-record format, cross-database recovery table, lock ordering,
  old-client fence and authority for a late outcome after ownership changes.
- Which online and local response metadata proves a non-regressing handoff,
  including mixed queries, time-sensitive results and unknown pending footprints.
- The final readiness API and migration of `ready`, `SignedIn`, `useAppReady`
  and existing starter assumptions. Native/custom persistence behavior must be explicit.
- The bounded background-start policy, handling of long-lived unknown writes,
  and which workloads can legitimately delay full local write readiness.
- Acceptance of the proposed latency targets and a representative populated
  fixture. The previous three-run empty-inbox probe cannot establish them.

The author commissioned this RFC, not implementation or a new testing apparatus.
No independent review has been performed for this Draft. Review the identity,
write-ownership and read-publication changes before treating it as ready to build.

## 11. Alternatives

**Continue shrinking the initial JS only.** Useful headroom, but the measured
first-data path still downloads the full engine. Keep the landed split and
cache improvement; change the readiness dependency next.

**Compress or shrink the existing WASM until it fits.** Continue measured work,
but the current 742 KB gzip / 556 KB Brotli device is far from a 100 KB complete
SDK. Small linker or dependency wins cannot meet that target. A compact
execution format or application-specific artifact deserves a separate proposal
with feature, hot-release, byte and runtime evidence; it is not a prerequisite
for serving the first result online.

**Replace the interpreter with a small JavaScript or reduced WASM client.** A
second evaluator violates the current one-interpreter decision, and omitting
language, authorization, query or write behavior compromises the requested
functionality. A thinner host/journal is useful because it executes through the
existing server and full local engine, not because it reimplements them.

**Use a worker, preload everything, or rely on the cache.** These improve CPU
responsiveness, the waterfall or repeat visits. They do not make a slow first
download disappear; aggressive preload can delay the foreground data itself.

**Ship online-only or SSR-only.** Each is appropriate for some apps. Neither
provides the full local behavior requested here. The proposal preserves that
behavior while letting the page become useful before it is available.
