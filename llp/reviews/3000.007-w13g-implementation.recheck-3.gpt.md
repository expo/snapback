The implemented completion rule is:

- Retain descending unselected rows from `group_at(join_seq)`. Start K at the smallest current readable selected key actually delivered.
- Stop when the next historical candidate key is below K. Otherwise query whether `_log` contains **any** matching `(t, id)` with `seq > join_seq`.
- A query hit discharges the candidate. Without a hit, require a present, readable current row still in the group; the first such blocker is the greatest. Publish the smallest delivered key strictly above it, or omit completion if none exists.
- `whole` returns immediately when selection contained fewer than N rows.

The query reads no image. SQLite and Postgres implement the same predicate, backed by `(t,id,seq)` indexes: one O(log L) existence probe per examined candidate, with no additional query or fetch on the ordinary early-exit path. [SQLite query](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/partition/storage.rs:37), [Postgres query](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/engine/postgres/log.rs:29), [SQLite index](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/store.rs:132), [Postgres index](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/engine/postgres/mod.rs:100).

For genuine row writes, moving out of the group emits a deletion in the old partition; deletion likewise removes the row. Neither leaves a current row in the certified group requiring delivery. A surviving readable row’s put carries its current image, possibly on a later catch-up page. Thus “written” need not mean “receives a put”; the relevant distinction is a row transition versus a membership transition. [partition.rs:139](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/partition.rs:139), [partition.rs:655](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/partition.rs:655).

**High — Membership events falsely discharge row blockers.**

Locations: [storage.rs:37](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/partition/storage.rs:37) and [postgres/log.rs:30](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/engine/postgres/log.rs:30), consumed at [partition.rs:707](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/partition.rs:707).

`_log` multiplexes row and membership events. Membership events use the **content table** as `t` and `canonical_json(group)` as `id`, even though no content row changed. These records live in the affected principal’s partition. [partition.rs:212](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/partition.rs:212).

A content row can legally have that same ID: identity validation imposes a byte bound, not a namespace restriction. For text group `g`, use the literal row ID `[{"String":"g"}]`. [value.rs:348](/Users/ccheever/projects/snapback-w13-review/repo/snapback4/crates/snapback4-core/src/value.rs:348).
