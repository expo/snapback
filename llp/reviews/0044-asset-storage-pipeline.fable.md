## 1. Overall assessment

This v3 is a substantial, mostly well-executed redesign. The four-record model (asset / upload attempt / blob / rendition) genuinely dissolves the identity collisions the Revised header claims it dissolves: making physical keys opaque and the verified digest a blob metadata fact is the right resolution of the direct-upload / content-addressing / privacy-rewriting triangle, and the transport-integrity-versus-canonical-digest distinction (llp/0044-asset-storage-pipeline.rfc.md:378-382) is correct and unusually careful — multipart composite checksums really are not byte-sequence digests. The logical-quota-with-reservation design (:403-415) closes both the dedup-quota-oracle and the concurrent-preflight overrun. The corpus citations I verified are overwhelmingly accurate: the LLP 0124 manifest claim is true down to `src/manifest.rs:5818/6023`; the LLP 0070 reconciliation matches 0070's own anticipation of exactly this amendment (llp/0070-durable-background-work.rfc.md:384-388); the 0108, 0037, 0012, 0114, 0013, 0036, and 0099 characterizations all check out; and the TUS claims are externally accurate (all four named extensions exist in TUS 1.0.0, and the spec does leave authentication to the server, matching "TUS itself is not the authority model").

Two design gaps keep it from READY under the "no flaws" bar. First, the capability boundary for image-accepting intents is ambiguous at the exact point where the RFC's flagship use case lives: an image-accepting intent requires an unnamed "image-finalization capability" (:161), privacy-safe image publication is listed under `asset-image-pipeline-v1` (:762), yet `asset-lifecycle-v1` alone is claimed to retire the storage GAP (:757-758) — for a subsystem motivated by "photos and video especially," whether a lifecycle-only target can accept a photo at all is left undecidable. Second, the privacy story is asymmetric between images and video: image location metadata gets a mandatory declared policy, but video files (explicitly in v1 delivery scope via range acceptance, :865-866) carry location metadata too (QuickTime/MP4 location atoms on iPhone video), and the RFC neither strips it, requires a declared policy, nor declares the nonclaim.

Below those sit a cluster of material concurrency and consistency items — the blob-reuse-versus-blob-GC race, the unstated single-current-attempt invariant, an acceptance item that unconditionally commissions Kotlin and Python SDKs the corpus explicitly does not commit to, and a provenance misattribution of the revive-versus-supersede decision to LLP 0127 when 0127 itself routes it as an open author decision. All are fixable with bounded edits; none requires rearchitecting.

## 3. Concerns

1. **BLOCKING — The image-admission capability is unnamed and the slice boundary is undecidable for the flagship use case.** llp/0044-asset-storage-pipeline.rfc.md:159-163 requires an image-accepting intent to declare a privacy policy and requires the target to "advertise the required image-finalization capability before admitting the intent" — but that capability is never named, and privacy-safe image publication is listed under `asset-image-pipeline-v1` (:760-765), not `asset-lifecycle-v1` (:750-755). Meanwhile :757-758 claims lifecycle-v1 "retires the basic authenticated-storage GAP" for a subsystem whose motivation is "photos and video especially" (:32-33). As written, a reader cannot determine whether a lifecycle-v1-only target refuses every avatar intent (making the GAP-retirement claim hollow for the blocked app classes 0124 identified) or admits images without the privacy step (violating :159-163). Resolve: name the image-finalization capability fact, state which slice carries it, and state explicitly what a lifecycle-v1-only target does with an image-accepting intent.

2. **BLOCKING — Video location metadata is silently retained while image location metadata is mandatory-policy.** Video is in v1 scope: :555-556 requires range support on video-capable profiles and the acceptance item :865-866 tests stored video delivery. iPhone-recorded video carries GPS location metadata (QuickTime/MP4 location atoms), the same threat the RFC treats as mandatory declared policy for images (:159-163, :384-389). No text requires a location policy for video-accepting intents, strips video metadata, or declares the gap; "Generic file lifecycle support cannot silently accept images while omitting the declared privacy step" (:162-163) shows the class of problem was seen — for images only. Resolve: extend the declared-location-policy rule to media types known to carry location metadata, or refuse video-accepting intents until a video-metadata-rewriting capability exists, or add an explicit nonclaim to Non-goals plus a capability fact so the gap is declared rather than silent.

3. **MATERIAL — Blob dedup reuse can race blob GC with no stated fence.** :393-395 lets the finalizer "reuse an existing immutable blob with the same digest"; :681-682 lets mandatory blob GC delete a blob "only after all asset and rendition references are gone." Nothing prevents the classic race: finalizer matches digest against a zero-reference blob concurrently being reclaimed, publishes a rendition pointing at bytes GC then deletes. The RFC pins fencing everywhere else (pointer switches, runners, migration) but not here. Resolve: state that reuse acquires its reference transactionally against GC's deletion decision (refcount increment and GC eligibility check in one transaction, or an epoch/fence rule), and add an acceptance item for the reuse-vs-GC race.

4. **MATERIAL — The single-current-attempt invariant is implied but never stated.** The finalizer "proves the attempt is current" (:363) and retry "creates a successor upload attempt" (:216-217) with a recorded predecessor id (:301), but nothing states whether creating a successor terminates a still-open predecessor, whether two non-terminal attempts for one asset may coexist (two tabs, or resume racing retry), or which of two completing attempts wins. "Current" is doing load-bearing work with no definition. Resolve: state the invariant (at most one current attempt per asset; successor creation supersedes/cancels the predecessor, or define the multi-attempt race outcome) and cover it in the concurrent-conflicting-writers acceptance item (:838-840).

5. **MATERIAL — Acceptance unconditionally requires Kotlin and Python SDKs the corpus does not commit to.** :834-837 requires "Generated JavaScript, Swift, Kotlin, and Python clients" to pass the conformance vectors, unconditionally. The RFC's own conformance section is conditional ("Each published SDK must run… before the SDK claims `asset-lifecycle-v1`," :272-276), and LLP 0064 says "Swift is the only committed maintained protocol-native artifact. Kotlin and Dart clean-room implementations are reference evidence until their packaging, ownership, and CI surfaces land" (llp/0064-native-client-surfaces.rfc.md:103-105) — Python appears nowhere as a committed client. As written, this acceptance item smuggles two new SDK programs into the asset RFC's exit criteria. Resolve: reword to the conditional form ("every SDK that claims `asset-lifecycle-v1` passes…"), or explicitly commission the four-language set and reconcile LLP 0064 in the same change.

6. **MATERIAL — Is `private-strict` delivery mandatory for every `asset-lifecycle-v1` target?** The lifecycle-v1 slice includes "strict authorized delivery with ranges" (:753-754), yet :769-771 lists `private-strict` among "independent target facts," and :548-550 explicitly contemplates a deployment supporting public/signed while "reporting strict delivery missing." These cannot all hold: either a strict-missing target cannot claim lifecycle-v1 (then it isn't an independent fact), or it can (then the slice definition overstates). Resolve: pin whether strict delivery is required for the lifecycle-v1 claim on every target or only on the canonical local target, and adjust one of the two sections.

7. **MATERIAL — The revive-versus-supersede decision is misattributed to LLP 0127.** :922-923 says "LLP 0044 remains the owner selected by LLP 0127's revive-versus-supersede decision," and :90 presents 0127 as routing the work. But 0127 poses this as a proposal and routes the decision to the author: its §Open questions is introduced as "The author decisions this synthesis forces" (llp/0127-parity-and-local-first-synthesis.rfc.md:~730), and item 8 lists "revive versus supersede LLP 0044; … parallel start confirmed" (llp/0127:759-764); §Sequencing 4 likewise says "Revive LLP 0044 (or supersede it by a fresh Spec — 0124 OQ1)" (llp/0127:628). The selection was evidently made by Charlie's v3 direction (:916), which resolves 0127's routed question — but a corpus reader sent to 0127 for the decision will find it recorded as open. Resolve: reword §Status to attribute the adjudication to the author's 2026-07-31 direction resolving 0127's routed question, and (outside this document) record the closure against 0127 item 8.

8. **MATERIAL — Deferred-length uploads are implied but no lane admits them.** :410-412 defines reservation behavior "when a supported streaming source defers length," but the TUS lane's extension set (:497-498) excludes the `creation-defer-length` extension — which, per the TUS 1.0.0 spec (verified), is the mechanism required to create an upload of unknown length — and the S3 lane text never claims unknown-total-length multipart. Either some lane supports deferred length (then name it and, for TUS, add the extension) or none does in v1 (then mark the sentence future-conditional). As written, quota semantics are specified for a transfer mode no described lane provides.

9. **MATERIAL — The asset state machine has no `pending → deleted` transition, leaving pending-asset cleanup and user abort unreachable as modeled.** Availability is `pending | ready | rejected | deleted` (:291) but transitions are given as "`pending → ready | rejected`, then `ready | rejected → deleted`" (:635-636). Pending-asset GC "removes" pending/rejected assets (:678-680) — is removal a transit through `deleted` or a row purge? And can a user who cancels an upload explicitly delete the pending asset, or must it wait out the grace period? Explicit delete is only specified for referenced/ready cases (:692-701). Resolve: add the `pending → deleted` (and/or purge) transitions and state explicit-delete semantics for pending assets.

10. **DETAIL — The LLP 0129 routing is unreciprocated.** :779 routes "local-first asset-byte sync/migration under LLP 0129," but LLP 0129 contains no mention of assets, blobs, or byte sync (grep-verified). The non-goal at :821 ("LLP 0129 owns the local-first program") is accurate; the capability routing at :779 assigns 0129 work it does not carry. Resolve: soften :779 to "under the local-first program" or land a reciprocal pointer in 0129.

11. **DETAIL — Seed binary fixtures vs the trusted-finalization invariant.** :788-789 lets versioned seeds carry binary fixtures, but "Only trusted finalization can publish a deliverable blob" (:102-103). Unstated whether seed-installed assets pass the finalizer (privacy rewriting, detection, digest) — a seed injecting GPS-laden bytes directly as `ready` would bypass the privacy invariant — and LLP 0109's canonical-payload digest model does not address binary fixture identity. Resolve: one sentence stating seeded assets take the same trusted finalization path, and note the 0109 interaction.

12. **DETAIL — Undefined normative terms: "reference policy" and "policy generations."** The intent declaration fixes "reference policy" (:160) and attachment verifies "owner/reference policy" (:448), but reference policy is never defined anywhere. Similarly "policy and lifecycle generations" (:293) and "asset lifecycle generation" (:449) are used for fencing without stating what events bump a generation. Resolve: define both or remove the undefined term.

13. **DETAIL — Quota accounting boundaries are incomplete.** When logical usage is released on deletion is never stated (at tombstone? blob GC? retention expiry?) (:403-415, :692-696), and whether system-produced renditions count against the app's logical owned bytes is unstated — pre-materialized variants can multiply storage materially. Resolve: two sentences pinning release timing and rendition accounting.

14. **DETAIL — Nothing forbids new upload attempts against a `ready` asset.** Successor attempts are specified only "while the pending asset remains eligible" (:216-217), and attempts need not carry the same bytes. If a ready asset could accept a successor attempt, a stable attached id could change content post-publication. This is almost certainly unintended; state that ready/rejected/deleted assets admit no further attempts and replacement is a new asset.

15. **DETAIL — "Original connection/session lineage" (:663) reads as contradicting cross-restart resume (:213-214).** A web refresh or Expo restart cannot preserve a connection. Presumably lineage means authority/auth-session lineage per the LLP 0093-0096 client protocol, not the WebSocket. Clarify the term.

16. **DETAIL — Two normative commitments lack acceptance coverage.** The reference-GC deployment warning listing uncovered asset-bearing fields (:688-690) and the client's automatic signed-URL refresh before expiry (:229) appear in no acceptance item. Add coverage or accept the gap explicitly.

## 3. New concerns

1. **MATERIAL — `via-references` has no defined per-row read-decision procedure.** :188-191 and :443-448 rest the policy on "authorized to read at least one app row that holds a typed reference," decided by "the same authorization the row's queries use," and :449-451 requires capturing "the referencing row's authorization basis" as an invalidation dependency. But the corpus this section cites shows per-row read authorization is not one thing: LLP 0011 distinguishes pushdown-compilable row-visibility filters — "a pure function of `(document, resolved filter)`" — from function-level authorization that "is arbitrary code" (llp/0011-auth-and-permissions.rfc.md:440-455). For a row whose visibility only arbitrary handler code decides, "may principal P read row R" is not evaluable outside a query invocation; for a row returned by multiple queries with different authorization, "the row's queries" does not pick a basis. The decision runs on every governed metadata and byte boundary and feeds the LLP 0053 dependency set, so divergent implementations here are a security divergence. Resolve (one paragraph): pin the `via-references` row predicate to the declared analyzable row-visibility shape 0011 records, and state the posture for rows whose read authorization is not expressible that way — e.g., a typed reference on such a row confers no `via-references` read authority (owner-only fallback), or a `via-references` intent refuses attachment into such tables — plus one acceptance clause for the non-analyzable case.
2. **DETAIL — "Default spelling" vs mandatory declaration for the location policy.** :196-198 says location-bearing media "require a declared location policy" and calls `location: "strip"` "the default spelling"; the acceptance row says an intent "without a declared location policy refuses at generation" (:1232-1233).
