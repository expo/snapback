## The seven items

### 1. `compile_error!` guard — FIXED

`snapback4-core/src/lib.rs:8-9` refuses `web-device-check` when `debug_assertions` is off.

Profiles in `snapback4/Cargo.toml` that compile **without** debug assertions (Cargo defaults; none of these stanzas set `debug-assertions = true`):

| Profile | Lines | `debug-assertions` |
|---|---|---|
| `release` | 16–17 | false (default) |
| `wasm` (inherits `release`) | 30–37 | false |
| `production` (inherits `release`) | 41–48 | false |
| `test` / `test.package."snapback4-device"` | 22–27 | **true** (default) |

Ship/measure scripts all use a no-assertions profile and **do not** pass `web-device-check`:

- `scripts/publish.mjs:76-77` — `--profile production -p snapback4`
- `scripts/build-xcframework.sh:21` — `--profile production` on `snapback4-device` (default features = `native`)
- `scripts/build-wasm.sh:10`, `measure-wasm.sh:15`, `attribute-wasm.mjs:144` — `--no-default-features --features web --profile wasm`

`web-device-check` is optional and empty (`crates/snapback4-core/Cargo.toml:25`, `crates/snapback4-device/Cargo.toml:22`). It is not a default. Turning it on for `wasm` / `production` / `release` hits the `compile_error!`. No snapback4 script or `scripts/test.sh` / `scripts/run-rust-tests.mjs` uses `--all-features` or `--release`/`--profile production` together with that feature, so the guard does not break the ordinary suite (`cargo test` uses the `test` profile, assertions on).

Residual, not a ship path: `cargo build -p snapback4-device --features web-device-check` (dev profile) still produces a native library that skips device admission (`validate.rs:125-126`, `write.rs:529-535`). No official packager uses that. There is also no committed compile-fail test; deleting the guard would not fail `cargo test`.

### 3. `--check-absent` patterns — FIXED

`attribute-wasm.mjs:114-116`:

```javascript
const forbidden = /::(?:prefetch|admission|log_events)::|::partition::(?:[A-Za-z0-9_]+::)*(?:row_changed|put|del|scope|join)(?=$|::|[<> ])/;
```

Near-misses that **must** stay in a web artifact do not match: `prefetch_extra`, `admission_extra`, `other::store::put` (`wasm-absent.test.mjs:7`). Trait methods `Rows::prefetch` / `Rows::put` (`rows.rs:185-189`) are `::prefetch` / `::put` without a following `::`, so they do not match. The kept `partition::account_row_change` does not end in `put|del|scope|join|row_changed`.

On the current web build (`--features web`, no `postgres`/`sqlite`) the forbidden **modules** are compiled out (`engine/mod.rs:21-22`, `pages.rs:20-23`, `partition.rs:128-154`). A hit would mean those modules (or identically named ones) returned — a true failure, not a false one. Limits are documented in the comment at `attribute-wasm.mjs:114-115` (inlined/renamed logic out of reach; gzip budget is the backstop).

The expanded throws in `wasm-absent.test.mjs:8-11` (`engine::prefetch::walk`, `other::prefetch::walk`, `other::partition::put`, …) would **not** have thrown under the old `snapback4_core::engine::(pages::prefetch|admission)` matcher. That test actually locks the new patterns.

### 6. Clock test — FIXED

`clock.rs:321-327` in `clock_advance_preserves_a_live_action_claim_session_and_settlement`:

- Prior clock mutations in **this** test: `--clock-offset +25h` at start (`:297`, already inside `before`) and a denied `E_CLOCK_INPUT` max-ms advance (`:316-317`). No successful 120 s advance precedes the assertion.
- Dev clock is `base + Instant::elapsed` (`dev_clock.rs:49-52`). A refused advance clones, then `advance_worker_leases` fails on the trigger, then `*clock = next` is not reached (`serve_maintenance.rs:91-105`). Elapsed is therefore request-duration Instant, not 120 s.
- Applied 120 s: `elapsed ≈ 120_000 + ε > 60_000` — still fails.
- A correct run exceeding 60 s would need the failed POST plus two sqlite reads plus the second `/q/time` to take a minute of Instant. That is not a plausible scheduling delay; the old flake was ~5 ms of HTTP skew (`issues/20260917-…:18-20`).
- Successful retry still pins exact +120_000 / +240_000 deadline shifts (`clock.rs:336-339`). Leases are still compared exactly at `:324-325`.

Scenario: an engineer reads `why E_UNBOUND_SCAN` / `guide bounds` and treats “runs only a server-admitted backend” as a runtime guarantee, then feeds the wasm device a hand-built backend (as `device-diet.test.mjs:16-20` already does) and gets `7` instead of `E_UNBOUND_SCAN`. Native devices are also unnamed even though they still check. Smallest fix: reuse the prediction/README wording — compile and serve refuse; native devices still check; the web device does not repeat the check and a corrupted backend can still run locally.

## Mandatory answers

**Did this delta introduce a new problem?** No new execution-path or ship-script problem. The two Low items are a missing compile-fail pin and host-boundary prose that is narrower/stronger than README/prediction.

**Is there a regression test in this delta that would also pass without the change it claims to test?** Yes, in two places. (1) There is **no** committed test of the `compile_error!`; removing it would not fail the suite. (2) `cargo test -p snapback4-lang --test guide` does not pin the new host sentences (no assert on “server-admitted” / “does not repeat”), so those 46 tests would still pass without the doc edits. Counterexample that **does** lock its change: `wasm-absent.test.mjs:8-11` would fail on the old matcher. The clock assertion tests the real 120 s property and would fail if that advance were applied; it is a flake fix, not a product-behavior change.
