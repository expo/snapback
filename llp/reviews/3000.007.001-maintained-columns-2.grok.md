## Findings

### 1. High — §3.2 / §3.3 — `engine/mod.rs` 845–857, `serve_changes.rs` 84–88, `write.rs` 498

**Scenario.** Likes do not require `exists posts` (the forward-reference §3.3 admits). Alice likes id `P`. If `P` is a live post, `row_changed` inserts `"posts"` into `written_tables` and `record_commit` lists it. If `P` is absent, the write is a limbo row: `posts` is not touched. `/changes` returns `tables` from those commits, unfiltered by the viewer’s read rule. Every connected client, and any paired §17 observation that includes commit metadata, sees whether that like found a parent.

`MutationOutcome.tables` is not on the HTTP reply (`receipt.rs` 12–27), so the mutation body can still match. The change feed is a different wire.

**Smallest change.** A source write that fans out to a maintained column always records the **parent table** as touched — including when the aggregate lands in limbo, including when the value does not change enough to `put`. Do not put limbo’s name on the commit.

### 2. High — §3.11 / §6 — `successor.rs` 62–67, `schema.rs` 157–159

**Scenario.** The RFC stores the column as “a `Maintain` whose target is a column” and reuses the evaluator. The natural spelling is `Maintain { target: "posts", … }`. Then `maintain_for("posts")` is `Some`, `classify` skips every column / index / constraint / expiry step on `posts`, and a later narrowing of `body` or a unique index is adopted as a maintain-audience check only. `refuse_engine_owned` (`write.rs` 302–307) would also refuse **all** program writes to `posts`.

The RFC already says a column target must not enter that bypass. It does not give the identity that keeps `maintain_for(parent)` as `None`.

**Smallest change.** Column-form maintains are not identified by `target == parent_table`. Keep `maintain_for` for generated tables only (e.g. a `column: "likeCount"` on `Maintain`, or a target spelling that is not a table name). `refuse_engine_owned` stays table-level for generated targets; the column refusal stays on submitted fields.

### 3. High — §3.11 — `schema.rs` 1273–1286, `successor.rs` 190–213, `device.rs` 377–393

**Scenario.** The engine interpretation of missing `likeCount` is hooked through `materialize_optional_fields` by storing `ColumnDefault::Literal(0)`. `classify` can still say Additive via the named exception. `keeps_literal_default_images` then returns true (required column, literal default, and — if finding 2 is also missed — maintains compared equal as tables). Device `adopt` keeps rows, sets `ACQUIRED` to the new generation, and watches rerun **before** the snapshot publishes (`device.rs` 532–538: staged snapshots do not replace until the last page). Every held post reads **0** while the server holds the rebuilt nonzero values.

Generation change alone does not close Grok’s window. `keeps_literal_default_images` is the gate.

**Smallest change.** Implicit 0 is **not** `ColumnDefault::Literal`. `materialize_optional_fields` (and index build / old-image validation) special-case required maintained columns. Authors still cannot write `default`. `keeps_literal_default_images` remains false because the added column has no authored literal default and because `from.maintains != to.maintains`.

### 4. High — §8 (also §3.5) — `partition.rs` 143–147, `serve.rs` 1082–1101

**Scenario.** The paired observation requires identical stream and snapshot for absent vs present vs differently valued vs expired-unswept parents. For public `posts`, the present world streams a `Put` of the post (`§3.5` is explicit that this is the cost). The absent world does not. A literal reading of §8 fails on the motivating schema, or tempts an implementer to hide parent events from the writer.

**Smallest change.** Split the observation. HTTP body, receipt, retry, and every **meter field** match in all four parent worlds, at ample and just-insufficient budgets. Stream and snapshot match only when the parent is **outside the writer’s partition**. Readable parents may differ by the parent image; that is the feature.

### 5. Medium — §2 — `schema.rs` 305–310, `bind/schema.rs` 260–269

**Scenario.** `sync public last 2000 by byLikes` with `byLikes: likeCount, at, id` is an allowed `by` index **and** a delivery rule: which rows a new device acquires depends on the column. A like then changes another row’s membership in the horizon set. §2 lists “the `sync` line and its audience,” not the horizon index. Job cursors are already refused (`bind/program.rs` 944–951). Ordinary `posts last 10 by byLikes` is a scan, not a probe (`bind/schema.rs` 434–436 vs `bind/program.rs` reads) — that distinction holds.

**Smallest change.** Add the sync horizon’s index to the walk. First build: refuse a horizon ordered by a maintained column (delivery depends on the column; §3.6 is already the unfiltered extra-acquisition problem). Reads of that index stay allowed.

### 6. Medium — §3.2 — `write.rs` 30–74, 121–135; `write_target.rs` 25–37, 287–314; `partition.rs` 152–153

**Scenario.** Unconditional reservation is implementable, but stacking it on every arm double-charges the upsert insert path (`reserve_target_resolution` then `insert_mode`). `insert` / `insert_if_absent` / native `insert` (`native.rs` 660–676) currently reserve nothing. Partition steps for a parent `Put` use `meter.charge` unless `maintain_for(posts)` is set — which finding 2 forbids — so prepaid suppression never sees them. At just-insufficient budgets a present public parent then `E_BOUND`s on steps and an absent one commits.

**Smallest change.** Reserve **once** per source-write **attempt**, at the outermost boundary, including `insert_mode` and the if-absent no-op, before any parent `tx.get`. Pass `Origin` into `partition::row_changed` and run Origin::Maintained partition work through `charge_maintain`. Prepaid worst case is two parent attempts: lookups, copies, every index that **contains the column** (and `byId` if `put` always writes it), rows written, partition steps, heap. Actual charges on that path are suppressed. Overflow stays the named exception.

Limbo does **not** make the two worlds cost the same in SQLite: a parent updates indexes over the column; limbo has none. The meter matches because both pay the reserved ceiling. Say that on the card. Do not charge actual parent index entries on the prepaid path.

Missed arms after that: none that a viewer can meter. `remove` / sweep are parent death (unbounded system). `load` is a rebuild (`engine/mod.rs` 944–946; Postgres `postgres/mod.rs` 283–307). Seeds are system / unbounded (`write_target.rs` 288).

### 7. Medium — §3.3 — `partition.rs` 133, `emit.rs` 21–28, `sql.rs` 45–46, 143

**Scenario.** If limbo is a `Schema` table, `api.ts` gains a `Rows` entry, `sql` views it unless the name is `_…`, `created` / `inserted` bookkeeping in `row_changed` (`write.rs` 518–527) runs on it, and programs can write it unless separately refused. If it is **not** a schema table, `partition::row_changed` cannot be used.

**Smallest change.** Limbo is an engine-private store table (catalog name `_…`, not in `Schema.tables`). Same SQLite transaction as the source write; charged as Origin::Maintained; never synced; `sql` / `data` / `api.ts` never see it. Rebuild drops and refills it. Removal of the column drops it — otherwise a later re-add births stale totals.

No simpler population-independent birth: counting at insert is GPT 2; refusing missing parents is the channel both families rejected; an always-on maintain table is the form this RFC replaces.

Other limbo paths are sound: expired-unswept contributions go to limbo and the sweep adds the stale stored value (`write.rs` 62–68 then birth); same-commit either order; self-ref contributes once if birth `put`s the row before source `maintain` (today’s `insert_mode` order, `write.rs` 70–72); rollback is the write savepoint (`engine/mod.rs` 837–863). Overflow on an expired-unswept parent uses limbo’s value, not the stale stored max — a theoretical existence/expiry bit through `AggregateOverflow`, excluded by the named exception and impractical for `count`. Sweep duration depending on nonzero deaths is operator telemetry, not a viewer channel.

### 8. Medium — §3.7 / §3.11 — `maintains.rs` 16–19; `engine/mod.rs` 447–449; `client.ts` 389–396 vs `local.ts` 747–749

**Device overlay.** `Runner::maintain` already writes synced targets on a device. Reusing it for columns predicts `likeCount`, and replay over a stream page whose image is already newer than its watermark double-applies the delta. §3.7 says the device never writes the column; say the skip explicitly: on a device, column-form maintains are not run. `load` on a device store is covered. A post minted in that mutation reads implicit 0, which is the true limbo of a fresh id.

Later increment obligations in §3.7 match round 1 (ticket, skip-stays-skipped, replay’s affected set, `pending` preservation, birth-at-zero only for minted ids). Complete.

**All-zero activation.** Initial addition writes only nonzero parents. If every parent is 0, `written == 0` and today’s loop skips `record_commit` (`engine/mod.rs` 447–449). Generation still bumps (`store/activation.rs` 150–157). Dev adoption still wakes polls. Online `createClient` reruns every watch on generation. Local-first **server-run** watches in `waitForChange` rerun only on `json.tables` (`local.ts` 747–749) until `syncOnce` finishes. §3.11 already says the activation commit names the table; require that commit even when no parent row is rewritten, with **no** row events. History, `acknowledged`, retained rows and the online tier do not need rebuild events in the log: devices re-snapshot (`keeps_literal_default_images` is false when maintains differ); Postgres claims no adoption parity.

Suppressing events is **not** how a maintain rebuild is delivered today. The difference is justified: a 100 000-row `Put` of `posts` is not a decodeable generation signal (`§3.11`, GPT 6).

## §7 / §8

Gates 1, 2 and 5 are the right briefing gates. Gate 2 as “accept and measure” is defensible: the filter Grok wanted is a separate device design, and Clique is horizoned. Item 4 (limbo vs present on every meter) should stay a test in §8, not a briefing gate — equality is by construction once finding 6 is specified.

Add to §8, as discriminating tests, not prose:

- Paired hidden-parent worlds: `/changes` `tables` equal (always the parent table, never limbo); meters equal at the reservation ceiling.
- `classify(posts)` still reports an ordinary column narrowing after a maintained column exists; `maintain_for("posts")` is `None`.
- Adding the column does not satisfy `keeps_literal_default_images`; a device never serves implicit 0 from a pre-generation image (empty/unknown until snapshot, not 0).
- Device prediction of a like does not `put` the parent on either store.
- All-zero initial addition: activation commit has no row events, lists the parent table, a held device re-acquires, a server-run watch over the parent reruns.
- Horizon `last N by` an index containing the column is refused.
- Upsert insert arm reserves once, not twice.

Rebuild, oracle, overflow-separate, and “no device path writes the column” are already the right tests.

---

The six repairs are sound. They are not complete until parent-touch is constant, column maintains are not table targets, and implicit 0 is not a stored literal default. An implementing lane cannot “just be careful” about those three without changing behaviour.

Verdict: READY WITH CHANGES
