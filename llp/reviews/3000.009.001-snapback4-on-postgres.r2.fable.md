## New fundamental and major findings

### N1. The `FOR SHARE` fence makes lease renewal conflict with every in-flight fenced transaction, so a long transaction gets a healthy owner terminated — MAJOR — child A §5 (`:185-200`, `:209-216`)

The fence is `SELECT token FROM _owner FOR SHARE` held for the life of every writing transaction (`:192-194`). The lease lives in the same row, and the owner renews it by updating `lease_until` (`:185-188`); `backends` is updated in that row too whenever a connection is opened (`:187`). In Postgres a `FOR SHARE` lock blocks any `UPDATE` of the row, and an `UPDATE` holds a `FOR NO KEY UPDATE` lock that blocks new `FOR SHARE` takers until it commits. Two consequences follow. Every renewal waits for the longest in-flight fenced transaction, and every new fenced transaction waits for the renewal's flush, a periodic stall of all writers. Worse, a fenced transaction that runs longer than the lease minus the renewal period cannot be renewed past, so the lease expires while the owner is healthy, the standby runs step 1 and terminates the owner's backends mid-transaction (`:209-212`), and the owner exits and restarts as a standby. The transactions that can be that long are exactly the ones the documents place under the fence: the internal-migration runner (`:46`), index adoption or backfill at size (child C W12, `:150`), sweeps, and the serial batch at large N. None of the P1b witnesses (`:519`) exercises this; W12 at 10⁸ rows would.

Direction. Take the fence as `FOR KEY SHARE`, which blocks `SELECT ... FOR UPDATE` but not a non-key `UPDATE`, so renewal and `backends` updates proceed under in-flight writers while takeover's explicit `_owner FOR UPDATE` (`:215`) still waits for them and blocks new ones. Under `READ COMMITTED`, which the serialized mode already uses (`engine/postgres/store.rs:96`), a blocked `FOR KEY SHARE` re-reads the committed row and sees the new token. Alternatively keep the token in `_owner` and the lease in its own row that writers never lock. Either way, add a witness: a fenced transaction longer than the lease completes without takeover.

### N2. The copy-and-replay convergence claim is false when replay runs while chunks are still landing; the text implies it does — MAJOR — child B §4.3 (`:129-150`), §4.4 (`:152-169`), §4.2 (`:109-113`)

Section 4.3 states that applying the journal over the chunked copy "therefore converges, per key, to the source's latest state" (`:131-134`), and explains only the benign interleaving: "a target key can be newer than the replay position" (`:138-139`), so an older journal entry briefly regresses it and a later one restores it. The other interleaving is not handled. A chunk reads key K at source snapshot p; the source then writes K (journal entry j > p); the replayer, "close behind" as §1 step 3 and `:147-148` require, applies j to the target; then the chunk's `COPY` lands K's older image from p. The replayer has already passed j and nothing re-applies it. Chunk writes are full-image upserts through the put path (`:114-115`), so the stale image wins. The window is the chunk's read-to-`COPY` latency, and it is open for the last chunks of a copy under load, which is the case graduation exists for. The barrier comparison (`:167-169`, `:248-259`) catches the mismatch, so the failure is a refused cutover rather than silent divergence, but no repair path is named and the only recourse is to start over. G1's evidence (`:309`) would be flaky under write load for this reason.

Direction. State the ordering rule. The simplest is that no journal entry is applied until the last chunk has landed on the target, which is what §1's step list already reads as, with the rule that a copier restart after replay began resets the replay position to zero. The robust alternative is per-key ordering during graduation: every target write carries the `jid` it reflects (the chunk's snapshot `jid` for copies, the entry's for replays), applies only if its `jid` is at or above the stored one, and replayed deletes leave tombstones until `finalize`. Add a G1 witness that writes hot keys during the final chunks.

### N3. The revised committer rule still fires with certainty, so S0 cannot decide what the parent says it decides — MAJOR — child C §8 (`:205`), §9 (`:223`); parent §3.3 (`:210-212`, `:217-221`), §5 (`:272-274`); child A §10 P1c (`:520`)

The rule now triggers when the serial batch (0) on Postgres at 0.5 ms RTT is below 1,000 commits/s or 25% of raw Postgres. By child A's own formula for (0), `N / (N·k·RTT + exec + flush)` (`:303`), the rate is below `1/(k·RTT)` for every N; at the parent's k ≈ 15 (`:181-183`) that is 133/s, and at k = 5 it is 400/s. Only k ≤ 2 clears 1,000/s. Child A says as much: on Postgres (0) "recovers only the flush's share" (`:306-307`). The rule was moved off the reference because it fired with certainty there (`:255-258`); it fires with certainty on (0) for the same reason. Meanwhile the commit-stage prototype, the one number S0 adds (`:223`), has no role in the rule, and it too is predictable: `batch/(2·RTT + flush)` at batch 64 is tens of thousands per second. The open quantity is the execution stage, `connections/(k·RTT + exec)` (child A `:348`), at the connection budget P1 will allow, and S0 does not measure it. The parent and P1c still gate building (a) on this rule (`:210-212`, `:520`).

Direction. Say plainly that the formula already commissions a committer that removes `k·RTT` from the serial section, and that S0 sizes (a) rather than decides it. Give S0 an execution-stage cell: a pool of read-only `REPEATABLE READ` executions of the W4 program at swept RTT and connection counts, without the overlay. The rule then becomes: build (a) if its predicted ceiling from both stages at P1's connection budget clears the bound with margin; if the execution stage cannot, the work is C1's next step on k or the async driver (child A `:532-534`), not (a).

## Small notes

1. Child B `:223-225` says a budget expiry before step 5 commits returns the source to `copying`. A budget expiry after step 5's `COMMIT` was sent is the ambiguous case of `:231-236`, and must follow the same rule: read the target's row first; a `live` target wins. Otherwise a late-landing `live` target with `_owner` set is one a standby would open while the source serves.
2. The barrier holds a source read snapshot through the complete comparison (`:163-167`, `:248-259`), which is O(store); that is the long-lived reader §4.2 (`:110-112`) avoided for the copy. It pins the WAL for the duration. State the bound (write rate times comparison time) and have preflight estimate it.
3. Child A `:243-254` does not say how `serve` detects a promotion. The timeline identifier changes on every promotion; record it in `_owner` at lease acquisition and compare on reconnect (UNVERIFIED whether `pg_control_checkpoint()` is readable by the core role on each provider). Also terminate by `(pid, backend_start)` or `application_name` rather than bare pids (`:187`, `:210`), since pids are reused.
4. Child A `:336-340`: a bare internal revision makes every session mint a conflict for every in-flight mutation. Either the revision carries the keys each durable write touched, or the commit stage re-reads the batch's authority facts in one statement.
5. Child A `:215-216`: step 2 should recheck `lease_until < now()` under `FOR UPDATE`. Between steps 1 and 2 a resumed owner can renew, and two standbys can race; the loser should back off rather than fence a live owner.
