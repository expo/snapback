**Direction.** Serving authorized online reads and journaled writes before the interpreter is the right move, and the problem statement holds against the code. With a device configured, `createApp` awaits the wasm open inside its signed-in opening, and the online arm only exists after that owner is published, so there is no early-read path today. No diet gets a Rust interpreter plus sync and persistence near 100 KB, and even a 300 KB device would lose to one server read on a slow link. Three fundamental concerns, most serious first. The first is the change I would make.

1. **The coordinator sits one layer too high.** The RFC adds an app-owned coordinator that arbitrates between two producers, the online client and a later local client, and must extract commit evidence from each to decide replacement (§6). The local client already contains exactly that arbitration. Its query procedure publishes one observation from a local candidate, a server answer or a remembered answer, ordered by the server's store cut against the replica watermark, under the retention, expiry and scope-loss fences of LLP 3000.023 and 3000.028. Those rules are the handoff. What the local client lacks is only the ability to exist before its core: `createLocalClient` awaits the device open at construction and binds write history, generation, clock, media and the outbox to that core. Why fundamental: rebuilding the arbitration between two clients means two producers, two session lifetimes kept from racing (§5.2 proposes racing them, which §3 says not to do), two evidence formats to reconcile, and a new observation object between the client and the hooks. Instead, make the core late-bound inside the one local client. Before the core attaches, every local evaluation answers unavailable, so the existing server route runs and `acquired` stays false. When the core attaches, dirty every watch and let the existing publication rules decide whether a local answer may replace the remembered server answer. The prepare, commit and activate seam in `client-start.ts` is where the attach step belongs. Hook identities never change because the client object never changes.

2. **Drop the import step of the write transition.** §7.2 moves never-dispatched intents from the online journal into the device outbox with a durable ownership record, generations, a cross-database recovery table and an old-client fence, and §10 lists those as unresolved blockers. The outbox is stored through the engine, since `local-delivery.ts` reads and writes delivery state via device calls, so this is a genuine cross-store transfer. What it buys is predictions for the few writes made before the engine arrived and a single pending list. Instead, use one rule evaluated under the journal lock. The online journal owns admission while it holds any unsettled intent. The device outbox may admit only once that journal is empty and the core is ready, and the flip is monotonic per tab. Per-owner ordering holds because the two never admit concurrently, unknown outcomes settle through the existing same-id retry, and offline the online journal waits as it does today. The RFC already accepts no predictions for startup writes and a deadline that abandons cutover, so this gives up nothing the RFC promised. Add import later only if measurement shows the drain wait delays local write readiness.

3. **The cold first-data target is below the transfer floor.** At 1.6 Mbps the link moves 200 KB per second. The SDK, React with ReactDOM, and app code total at least 140 KB gzip, so transfer alone is about 0.7 s. Serial round trips at 150 ms add the HTML, the scripts, the schema and probe reads the online scope makes before signed-in, and the query. That floor is near 1.4 s before 4× throttled parse and execute. Why fundamental: §9 makes a 1 s median the acceptance bar, so a correct implementation would be judged a failure. Instead, derive the target from the fixture's measured bytes and round-trip count and report the gap to that floor. SSR is the only path under 1 s on this profile, which argues for not leaving it last.

No concerns with keeping one interpreter, the explicit opt-in mode, or the readiness split in §4.

Verdict: DIRECTION RIGHT WITH ONE CHANGE (put the progressive seam inside the existing local client as a late-bound core with drain-then-cutover writes, instead of a coordinator over two clients). Confidence 0.8.
