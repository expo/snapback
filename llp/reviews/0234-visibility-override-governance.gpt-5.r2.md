## New findings introduced by the revision

1. **MATERIAL — Quarantine is neither monotone nor compatible with the transition ledger's append-only rule.** D3 makes a newly committed quarantine file the only current-tree fact that prevents reuse of an affected id, but no baseline, ledger, or admission rule makes quarantine records append-only or refuses their deletion/rebinding (`llp/0234-visibility-override-governance.rfc.md:483-493`, `:1142-1149`). A later update can delete that file; after the widening has been removed, reintroducing the same id can reuse its still-remotely-prior approval closure. For a quarantined ordinary-policy transition, the prescribed remediation also says to remove the active “ledger head,” while D5 requires the ledger to retain every superseded head and makes historical removal/rebinding an audited violation (`llp/0234-visibility-override-governance.rfc.md:491-493`, `:760-775`, `:1435-1442`). **Suggested resolution:** make quarantine verdicts an append-only exact-set ledger governed by both admission comparators and consumed by codegen/activation; define a compensating `quarantined-reversal` transition that retains the bad head, links the verdict, installs a clean successor head, and cannot confer authority. Add negative fixtures for quarantine deletion/rebinding and old-id reuse, plus a successful policy-transition quarantine/reversal/reapproval chain that never deletes ledger history.

2. **MATERIAL — The server auditor lacks the cross-ref predecessor input required for a newly created governed ref.** The job's stated retained input is each updated ref's own true `before`/`after` pair, but a new governed ref must be compared to the configured anchor ref's **old** tip (`llp/0234-visibility-override-governance.rfc.md:450-471`). On this GitHub repository the existing push-event seam exposes only the current event's `github.event.before` (`.github/workflows/local-proof.yml:55`); a new-ref event has a null `before`, and after a same multi-ref update the anchor's live tip is already its successor. Thus a bypassed push can advance `main` with the approval while creating a governed ref with the widening, and an auditor that substitutes the now-current anchor can launder the same push. The simulated OID fixture in Acceptance 5 does not establish that production custody can obtain the missing old anchor OID. **Suggested resolution:** require an authenticated atomic push envelope that retains all ref commands and their old/new OIDs under one event id. If GitHub cannot supply that envelope, prohibit new governed-ref creation in a multi-ref update and require a remotely notarized anchor OID committed/configured before ref creation. Add the laundering case above as a real provider-contract fixture.

3. **MINOR — The new `principal` admission policy is digest-only on the one-page review surface.** D5 carries `authorityAdmissionPolicyDigest`, while D6 expands the alternate row scope but never requires the full normalized principal admission policy (`llp/0234-visibility-override-governance.rfc.md:678-698`, `:837-849`). A reviewer can see that the admission policy changed but not whether it is a moderator role, broad membership, or authentication-only without leaving the artifact. **Suggested resolution:** render the complete canonical principal admission policy and its membership-audience closure beside the digest in the approval/review record and projection; add a fixture that distinguishes authentication-only from the required role predicate in generated facts.
