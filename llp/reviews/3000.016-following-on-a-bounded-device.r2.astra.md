The remaining findings are:

1. **High — §2.2 and §4: withholding is specified for missing cards, but not for missing inbox coverage.**

   Give the server 1,020 live inbox copies, acquire the newest 1,000, and fully sync every card. Request 40 rows after the newest 980. The device has only 20 remaining copies; every card lookup succeeds.

   The current [scan coverage check](../../snapback4/crates/snapback4-core/src/engine/read.rs:1040) marks this unknown but still returns the short page, potentially without a continuation. Implementing only §2.2’s card-miss rule leaves that result publishable offline and during pending prediction. An entirely empty page can have the same problem.

   **Smallest change:** explicitly withhold when either the inbox scan’s required coverage **or** a shaping dependency is unknown. Apply the same original-cursor retry and pending-write rule to both. The [loading fallback](../../snapback4/packages/snapback4/src/local.ts:993) must respect that pending-write fence.

   Also replace “a page within the inbox floor is complete” with “has known inbox coverage.” Pending backfill/cleanup and meter cuts retain their existing `complete: false` semantics; they must not automatically become unavailable.

2. **Medium — §§2.1, 2.3: the derived event horizon does not supply the stated repost prerequisites.**

   Set N=1. Have one original post P at time 10 and a repost event at time 20. The posts acquisition holds P; the owned-event acquisition holds only the repost. Equal limits produce different boundaries.

   A new repost of P needs both the source post and its live original row in `@T@Posts.byActorPost`, as the [transition explicitly checks](../../snapback4/crates/snapback4-core/src/engine/timeline.rs:116). A held card and covered tombstone probe do not establish that fact. Moreover, §2.3 only calls for classifying the source-original read; the current [implicit-input classifier](../../snapback4/crates/snapback4-lang/src/bind/timeline.rs:120) would still label the newly horizoned owned-event input `Held`.

   **Smallest change:** state that owned events inherit the source’s **limit and ordering policy**, with an independently acquired boundary. Require all implicit timeline inputs to be known and classify each from its actual residency. Preserve the live-original-event check.

   The paved `insert … if absent` repost also retains its ordinary uniqueness proof: a new insertion into horizoned `reposts` can queue even with both original rows held. State these as necessary conditions, not a sufficient prediction recipe.

3. **Medium — Summary and §2.3: own-post prediction is not unchanged with `online only` posts.**

   Change `posts` to `online only`, acquire the resulting backend, disconnect, and invoke an ordinary post insertion. The mutation writes an online-only source; its owned event table is also online-only. The existing [residency classifier](../../snapback4/crates/snapback4-lang/src/bind/residency.rs:68) therefore makes it non-predicting. It queues without the promised local card or own-inbox copy.

   **Smallest change:** qualify the own-post guarantee to synced sources and ordinary prediction eligibility. Explicitly say that online-only source writes queue without predicted rows. Test the same mutation under full sync, a horizon, and online-only residency.

I found no additional adoption defect: the existing sync-change classification and device reset support §2.4 without reconstructing timeline history.
