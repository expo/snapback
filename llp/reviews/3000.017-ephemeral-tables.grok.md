## Verbatim review

### Review of LLP 3000.017 revision 1 — Grok

**Verdict:** READY WITH CHANGES

## Summary

A table modifier over the existing runner is the right shape, and the durable-outbox failure it is aimed at is real. The runner already treats expiry as absence before rules, `nextExpiry` already reschedules watches, and a deferred read transaction really does not take the writer lock. Three holes in the wake and fencing design still keep a typing row from showing up within 2 seconds, or from being believed after `dev` adoption. Fold the fixes below into the RFC and implement; they do not need another design round.

## Findings

### F1 (High) — The first `/changes` poll is deaf to typing, for up to 25 s

- Where: RFC §3.3 and §4.6; `packages/snapback4/src/client.ts:618-625`; `packages/snapback4/src/changes.ts:27-48`; `packages/snapback4/src/local.ts:807-819`; `crates/snapback4/src/serve_changes.rs:12-13`; `benchmarks/tools/social-messenger/choreography/choreography.mjs:1749-1759`
- What is wrong: A watch records tables only after its first answer, and the poll URL is fixed when the request starts. `observe` starts both at once, with an empty table set:

```622:625:snapback4/packages/snapback4/src/client.ts
        watch = Object.assign(new ReadObservation<unknown>(), { op: op as Query<unknown, unknown>, args, key, tables: new Set<string>(), subscribers: new Set<() => void>(), inFlight: false, dirty: false, expiryTimer: null });
        watches.set(key, watch);
        void refresh(watch);
        void poll();
```

  The poll then blocks in `changes(... wait=25 ...)` (`client.ts:511`, `local.ts:819`). Nothing aborts that request when a watch appears or gains tables (`changes.ts` aborts only on offline, close, or the 4 s silence timer). §3.3 says a poll with no `eph` parameters "behaves exactly as before," and a wake for a table outside `ephTables` keeps waiting. So the poll that is open while Alice is looking at the conversation does not wake for Bob's `setTyping`. The server caps `wait` at 25 s (`serve_changes.rs:13`). The benchmark allows 2 s (`choreography.mjs:1759`). Heartbeats do not end the poll; they are discarded whitespace (`changes.ts:62`).
- Evidence: Same structure on the local-first tier (`local.ts:807-837` only reruns watches when `seq` or generation moves). The §2.4 recipe mounts `useQuery(api.typingIn)` when the conversation mounts, which is exactly this race. §4.7's end-to-end test never holds a poll that was opened before `typing` was known, so it can pass while the browser benchmark fails.
- Proposed change: Two rules. (1) Omitting `ephTables` means "wake me for every ephemeral commit," not "ignore ephemeral." Old clients never see an ephemeral schema (the capability fence), and a same-`seq` answer does not refresh them (`client.ts:522`). (2) Put `readsEphemeral: ["typing"]` on the generated operation so the client knows the set before the first answer, and abort the in-flight `/changes` when that union changes so a poll that already sent a narrower filter cannot sit for 25 s. The server entry check (epoch already moved) then answers the new poll immediately.

### F2 (High) — The ephemeral wake is not on the condvar the poll actually waits on

- Where: RFC §3.3 and §4.3 step 3 / §4.4; `crates/snapback4/src/serve.rs:1075-1078`; `crates/snapback4/src/serve_changes.rs:8-52`
- What is wrong: Durable commits wake polls by updating state under the `shared.seq` mutex and then notifying `shared.committed`. The waiter holds that same mutex across the check and `wait_timeout`, so a commit cannot be lost:

```1075:1078:snapback4/crates/snapback4/src/serve.rs
                        if let WriteState::Sent { seq, .. } = &outcome.state {
                            let mut current = lock(&shared.seq);
                            *current = (*current).max(*seq);
                            shared.committed.notify_all();
```

  §3.3 puts the epoch in the hub and says "notify `shared.committed`" without that mutex. A notify that lands after the poll has read the epoch and before `wait_timeout` is dropped. Recovery is the next loop turn, which runs when the 2 s heartbeat fires (`serve_changes.rs:8`, `42-47`). The benchmark's visible-timeout is 2000 ms and starts at the last keystroke (`choreography.mjs:1756-1759`). A full heartbeat plus the follow-up `/q/` and render misses it. Holding the hub mutex and then taking `seq`, while the poll holds `seq` and then takes the hub to read the epoch, deadlocks.
- Evidence: The poll breaks out on any notify (`serve_changes.rs:51-52`) only if it was already inside `wait_timeout`. `Engine::query` already opens its read transaction before the runner (`engine/mod.rs:844`), so the safe order is: snapshot under the hub lock, release the hub, then publish under `seq`.
- Proposed change: After the hub lock is released, under `shared.seq` publish `(incarnation, epoch, ring tail)` and `notify_all`. The poll reads that snapshot under `seq` before `wait_timeout`, and never takes the hub while holding `seq`. Unrelated wakes re-wait only after re-reading that snapshot under the same mutex. Add the "answers within 100 ms" test only with the peer's poll already blocked inside `wait_timeout`.

### F3 (High) — Epoch fencing drops the answers incarnation change is supposed to deliver

- Where: RFC §3.3 and §3.4; `packages/snapback4/src/client.ts:413` and `518-529`; `crates/snapback4-core/src/engine/mod.rs:331-333`
- What is wrong: §3.3 says the client discards an answer whose epoch is older than the one the watch has already seen, "mirroring `minimumReadSeq`." The epoch is a process-local counter. `clear()` on restart, adoption, or generation change issues a new random incarnation and the counter starts again at 0. A numeric compare then treats the new epoch-1 answer as stale against the pre-restart epoch-50, and keeps discarding. `dev` adoption is the common case (`serve_adoption.rs:157-167` replaces the engine and notifies). After the first save, typing updates never land. The mirror is also per-store for durable reads: a generation change bumps `queryEpoch` (`client.ts:518-521`), it does not compare sequence numbers across identities. §4.6 never names this client check. The online accept path only knows durable `seq`:

```413:413:snapback4/packages/snapback4/src/client.ts
  const currentRead = (result: { seq: number; epoch: number }) => result.epoch === queryEpoch && result.seq >= minimumReadSeq;
```

  An expiry refetch and a renewal often share a `seq`. The empty answer can arrive last and clear a live indicator, because `seq` did not move.
- Evidence: Incarnation is specified as the restart signal (§3.4) but is not an ordered integer, so it cannot be a tie-break on the epoch. Do not fold `ephemeralEpoch` into `minimumReadSeq`; a low ephemeral counter would start discarding durable reads.
- Proposed change: Per watch, remember `(incarnation, epoch)`. A different incarnation replaces the floor and is always accepted. The same incarnation accepts only `epoch >= observed`. Apply that in `currentRead` / the local publish path, and to `/changes` before deciding the answer is stale. State this in §4.6, not only §3.3.

### F4 (Medium) — `$deadline` is not stripped for an ephemeral table

- Where: RFC §3.1 ("`recorded.rs`'s public image strips engine fields"); `crates/snapback4-core/src/engine/recorded.rs:20-23`; `crates/snapback4-core/src/value/disclosed.rs:152-159` and `219-233`; `crates/snapback4-core/src/engine/read.rs:1005-1007`
- What is wrong: `public_image` returns the row immediately when the table has no recorded fields, no `through`, and no timeline slots. An ephemeral table is exactly that shape (`through` is refused). `Disclosed::visible` hides `recorded` keys only, and `into_value` keeps every visible field. Query emission runs both (`read.rs:1007`, `read_point.rs:174`). `$deadline` is therefore on the JSON answer. Generated types omit engine fields (`emit.rs:24`) only if `engine_field` is updated; the wire still has the key. `nextExpiry` already exposes the earliest deadline; this additionally exposes every row's.
- Evidence: Through-tables do get stripped, because `through.is_some()` skips the fast path (`recorded.rs:21`). Copying that story without changing the fast path does not hide `$deadline`.
- Proposed change: Treat `$deadline` like a recorded field in `Disclosed::visible` when `public` is set, and drop the fast path when any engine field is present. Add a query test that the answer object has no `$deadline`. §4.2 should cite `value/disclosed.rs` and `recorded.rs`, not `recorded.rs` alone.

### F5 (Medium) — There is no per-session mutation rate bucket to extend

- Where: RFC §3.5 and §4.4 ("the per-session token bucket of §3.5", "E_RATE_LIMIT (the existing code)"); `crates/snapback4-lang/src/guide/codes.rs:188`; `crates/snapback4/src/auth.rs` and `serve.rs:813`; `crates/snapback4/src/serve.rs:344`
- What is wrong: `E_RATE_LIMIT` is the auth/upload/HTTP-admission code: 30 attempts per socket per minute and 10 per email, plus a concurrent-upload cap. `dev` loopback has neither minute counter (`serve.rs:344`). There is no 20/s per-session mutation bucket. Wiring typing to the login bucket refuses a 1/s heartbeat (60/min > 30) on `serve`, and does nothing on `dev`, which is where the benchmark runs.
- Evidence: Card text at `codes.rs:188` is "bounded identity, upload, or HTTP admission." §4.1 says to extend that sentence; the bucket itself still has to be new.
- Proposed change: Say so. A new per-session token bucket, checked before `mutate_ephemeral`, returns the existing `E_RATE_LIMIT` code and is retryable. Do not share it with login or uploads. State the `dev` behavior explicitly (on or off) so the lane does not inherit the loopback exemption by accident.

### F6 (Medium) — The capacity refusal is checked on the success path and does not undo

- Where: RFC §3.5 and §4.3 step 3; `crates/snapback4-core/src/rows.rs:377-402`
- What is wrong: "On refusal, undoes the journal; on success, checks §3.5's capacity, bumps the epoch." `MemoryRows::put` has already updated the row, its index entries, and the cap slot (`rows.rs:377-402`). A post-check that returns `E_EPHEMERAL_FULL` and still bumps the epoch publishes a row past 100,000 rows or 64 MiB. A test that only asserts the error code passes. The hub mutex serializes writers, so the check is race-free if it happens before publish and undoes.
- Evidence: The runner writes through `Rows::put` immediately; there is no SQLite savepoint on the memory store. The journal is the only undo.
- Proposed change: Under the hub lock, after the program and before the epoch bump, if the projected row count or byte count would exceed the cap, undo the journal and return `E_EPHEMERAL_FULL` with an empty detail. The §4.7 test must assert the row is absent and the epoch did not move.

### F7 (Medium) — One query that also reads `typing` stops answering from the device

- Where: RFC §2.3 (the chats-list "one read"); `crates/snapback4-core/src/engine/read.rs:822`; `crates/snapback4-device/src/call.rs:119-139`; `packages/snapback4/src/local-query.ts:161-177`
- What is wrong: A device scan of a table with no `sync` is `unknown` (`read.rs:822`). That bit is on the whole observation unless the result is a record with components (`call.rs:133`, `local-query.ts:168-177`). §2.3 then sends the whole query to the server. Offline, the fallback cannot run, and a chats-list query that also reads `typing` no longer renders the durable rooms from the device. The conversation recipe in §2.4 is safe because it is only `typing`. The chats-list card is the one that mixes them, and §2.3 tells the lane to pick "a nested read or a scan" without this constraint.
- Evidence: Composition keeps a durable component only when some components are `retained` and others `unknown` (`local-query.ts:169-177`). A single scan does not split.
- Proposed change: In §2.3, require the chats-list shape to be a record whose ephemeral reads are their own component (or a separate query). State that a component which touches an ephemeral table is server-only and the durable components stay on the device. Refuse `held` as already specified.

### F8 (Low) — Removing an ephemeral table stays Destructive

- Where: RFC §3.4; `crates/snapback4-core/src/successor.rs:65-69`
- What is wrong: Every missing table is "removed; its rows are lost," `Change::Destructive`. §3.4 says adding, removing, or changing an ephemeral table is Additive. A `dev` save that deletes `typing` would demand a destructive adoption. The new `$deadline` column is Additive only because `engine_field` says so (`successor.rs:100`); that branch must not be the only classification for durable→ephemeral, which has to stay Destructive and actually delete stored rows (`activation.rs:115-124` only drops catalog names that disappeared).
- Proposed change: If the old table is ephemeral and the new schema drops it, emit Additive. If a durable table gains `ephemeral`, emit Destructive and delete its `r`/`i` rows in activation even though the name remains. Do not let the `$deadline` engine-field branch be the sole step.

## What the RFC gets right

The table, not a second `channel`, matches how builders already write the durable recipe (`guide/reads.rs:112-128`) and avoids the hook they failed to find. Refusing mixed mutations, `sync`, `expire at`, maintains-as-source, and durable rules that probe ephemeral state is what keeps memory from deciding a durable commit.

Expiry-before-rules is already the law (`engine/read.rs:239-244`, `authorized_point.rs:54` and `:142`, `write.rs:629-644`). `live_lookup` skips expired unique-key hits (`witness.rs:179-209`), and index keys include the id (`rows.rs:170`), so a swept predecessor does not delete the live key. `nextExpiry` is already filled from `expiry_column` (`read.rs:247-253`) and both tiers reschedule on it (`client.ts:419-427`, `local.ts:911-926` via `serverExpiry`). Disappearance does not need a new timer. With `ephemeral 4s`, the renewal window (`life/4`) leaves the last keystroke inside a 4 s deadline, and the 5 s benchmark has about a second for the refetch. `clock.serverDelay` (`clock.ts:98`) is the right clock.

`read_transaction` is deferred and does not reserve the writer (`store.rs:250-256`); `Engine::query` already uses it (`engine/mod.rs:844`). WAL is on (`store.rs:120`). Running `mutate_ephemeral` on a pooled reader can proceed while `FairMutex<Engine>` is held, which is what the "writer lock held" test has to prove. Do not call `transaction()` (Immediate) or the read will block in the 5 s busy timeout. `next_seq` is a `SELECT` (`store.rs:503-505`), so it will not upgrade the snapshot. `partition::account_row_change` returns before logging when the table has no `sync` and nothing syncs to it (`partition.rs:196-260`); the §2.1 refusals are what keep that true.

Schema JSON stays byte-identical for tables without the new field: `Table` and `Execution` already use `skip_serializing_if` (`schema.rs:217-258`, `53-80`), and the capability carrier is added only when a predicate matches (`capabilities.rs:57-71`). Unknown capability names are refused (`capabilities.rs:99-102`), so a published 0.2.33 device will not queue these writes. The wasm numbers match `metrics/wasm-budget.json`: measured 577,207 B gzip, ratchet 578,207 B, 1,000 B of headroom. Expect to raise it in the same commit; the RFC already says that. `E_OFFLINE`'s card is the sentence at `codes.rs:193`, and the parser span for `ephemeral` (`parser.rs:188-268`) is right. `upsert typing[roomId, viewer]` is the mutation the current card already uses; spell that, not `insert`, in the new card. Stamp `$deadline` as its own assignment beside `write.rs:281`: `recompute_deadline` returns immediately when `through` is absent (`through.rs:47-49`), and `merge_patch` copies the old deadline (`write_target.rs:81-83`).

The line map in §4 matches this tree (mutate at `engine/mod.rs:946`, `/m/` at `serve.rs:930-1087`, reader pool at `serve.rs:102-127`, `write_tables` at `ir.rs:729`). It is one lane's worth of work once F1–F3 are in the text.
