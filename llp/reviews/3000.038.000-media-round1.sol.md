Model: **Codex / GPT-6**. Three MATERIAL issues:

1. **Readiness releases byte custody before placement has a durable home.** [RFC §3](/home/ccheever/projects/sb4-w9-media/llp/3000.038.000-durable-offline-media-intents.rfc.md:79) deletes the device’s byte copy when upload readiness commits. LLP 3000.038 §6 preserves the one-hour unclaimed-asset sweep. An upload can therefore commit, readiness can commit, and the client can restart offline for more than an hour before placement dispatches. Collection then removes the only bytes; placement fails with `E_ASSET_UNKNOWN`, and the immutable intent cannot recreate its asset. `retryUpload` cannot repair this ready dependency.

   Define custody through this interval: protect the upload until placement resolves, or specify an explicit expiration contract that preserves recoverable selected bytes and exposes an actionable typed outcome. Require a restart-and-collection fixture **after readiness commits but before placement dispatches**.

2. **Discard can manufacture a terminal failure for an unknown mutation outcome.** [RFC §4](/home/ccheever/projects/sb4-w9-media/llp/3000.038.000-durable-offline-media-intents.rfc.md:95) says discard durably fails and removes the intent, while acknowledging that it cannot undo a dispatched mutation. If the server commits placement but its response is lost, discard followed by restart can leave a durable `failed` state for a placement that actually succeeded, while dropping recovery custody.

   Make discard conditional on durable evidence that placement has never dispatched. After `begin_send`, retain ordinary receipt recovery and expose an unknown/pending outcome until settlement. Specify cancellation fencing against late upload-readiness callbacks. Require races covering discard versus readiness, `begin_send`, a held successful POST response, and failed discard persistence.

3. **The server’s file durability barrier does not cover the published pathname.** [RFC §3](/home/ccheever/projects/sb4-w9-media/llp/3000.038.000-durable-offline-media-intents.rfc.md:69) requires syncing the private file before committing its ledger row and receipt. File sync alone does not establish directory-entry durability. The current staging path also [syncs the file before renaming it](/home/ccheever/projects/sb4-w9-media/snapback4/crates/snapback4-core/src/assets.rs:61), without a directory durability barrier. A crash/power loss can therefore preserve the receipt while losing the asset pathname; readiness may already have deleted the device copy.

   Specify durable publication of the final pathname before ledger/receipt commit, including required directory synchronization and typed handling of its failure. Add fault obligations around file sync, rename/publication, directory sync, and database commit. If durability excludes power loss, state that boundary explicitly.

The atomic admission, owner-scoped deduplication, dependency barrier, and committed-reply rules provide a sound foundation. These findings concern the proposed lifecycle and proof contract; implementation being unfinished is not itself a finding. This verdict does **not** accept the RFC on the author’s behalf.
