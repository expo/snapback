### 3. Operations in v0

The accepted core queries are ordinary bounded programs:

```ts
export const readBook = query(
  {outcomeId:id(outcomes), depth:int({max:50})},
  ({db,args}) => ({
    outcome: db.get(outcomes,args.outcomeId),
    bids: db.scan(bookLevels.byBook,[args.outcomeId,"bid"],
                  {order:"desc",take:args.depth}),

export const readPortfolioPage = query(
  {accountId:id(accounts), take:int({max:100}), after:text({max:160})},
  ({db,args}) => {
    db.require(args.accountId===viewer,"NOT_OWNER");
    const ps=db.scan(positions.byAccount,[viewer],
                     {take:args.take,after:args.after});
    const rows=[];
    for (const p of ps) {
      const o=db.get(outcomes,p.outcomeId);
      let yes=o.lastPrice || 50;
      if (o.bestBid>0 && o.bestAsk>0 && o.bestAsk-o.bestBid<=10)
        yes=divmod(o.bestBid+o.bestAsk,2).quotient;
      const mark=p.token==="YES" ? yes : 100-yes;
      rows.push({...p,mark,unrealized:p.qty*mark-p.costBasis});
    }
    return {balance:db.get(cashTotal,[viewer]),positions:rows,
            hasMore:ps.hasMore};
  }
);

export const readTrades = query(
  {outcomeId:id(outcomes),take:int({max:100}),after:text({max:160})},
```

The fixed one-shot portfolio fails:

```ts
for (const p of db.scan(positions.byAccount,[viewer],{})) { ... }
// E_UNBOUND_SCAN: supply take; an exact whole result needs cap+All.
// Rewrite: cursor pages. Calling the pages one atomic snapshot is a product cheat.
```

**Op 1 — placement and fills.** The natural first attempt is:

```ts
const makers=db.scan(orders.byBookPriority,
  [args.outcomeId,opposite,"open"],
  {order:priorityOrder,args.priceRange,take:MISSING});

for (const m of makers) {
  if (m.accountId===viewer) { /* cancel self order */ continue; }
  const q=min(remaining,m.remaining);
  // Inline one branch:
  // yes_transfer: buyer cash -= q*x; buyer YES += q;
  //               seller YES -= q; seller cash += q*x
  // no_transfer:  buyer cash -= q*(100-x); buyer NO += q; ...
  // mint:          both cash legs; pool += 100*q; YES/NO += q
  // merge:         YES/NO -= q; pool -= 100*q; both cash legs
  db.update(orders,m.orderId,o=>({...o,remaining:o.remaining-q}));
  db.insert(fills,{...});
  db.insert(publicTrades,{...});
  // Inline zero-sum ledger and position writes.
}
```

It receives three refusals:

- `E_UNBOUND_SCAN/E_UNBOUND_LOOP`: no static maker bound. Rewrite with hard `M`.
- `E_STRUCTURAL_COUNT`: best-maker/FOK completeness is a rank over rows hidden from the caller. Rewrite under sealed system visibility, then disclose only authorized fill facts.
- `E_OPAQUE`: `serialBy(outcomeId)` and caller-to-system execution do not exist.

Even with `take:M`, `makers.hasMore && remaining>0` must atomically refuse `MATCH_FRAGMENTATION_LIMIT`; committing a prefix would violate FOK and leave a crossed book. There is therefore no corrected v0 program.

Cancel and replace have the same missing sequencer/system-projection problem. Replace additionally re-enters the refused matcher. Offline cancellation can be queued, but its predicted writes must not be surfaced as committed state.

**Ops 2–5 — lifecycle.** Once matching authority is set aside, the bounded forms are straightforward:

```ts
createMarket: require creator role; require outcomes.length in 1..20;
              insert market; insertEach outcomes; insert created event.
submitMarket: get market; require creator && state==="draft";
              update state="in_review"; insert submitted event.
reviewMarket: require reviewer && viewer!==creator && state==="in_review";
              update approved/rejected state; insert event/fence.
halt/resume:  require reviewer && viewer!==creator; update state; insert event.
cancelOrder:  get own order; if terminal return it; update terminal state,
              release maintained reserve inputs, increment book sequence.
```

Composite position/vote/level upserts may additionally hit `E_NOT_ATOMIC` unless v0 defines `upsert` over a unique-index tuple.

**Op 6 — time transitions.**

```ts
schedule(openMarket,  {at:m=>m.openAt,  key:m=>m.marketId, principal:"system"});
schedule(closeMarket, {at:m=>m.closeAt, key:m=>m.marketId, principal:"system"});
schedule(expireOrder, {at:o=>o.expiresAt,key:o=>o.orderId, principal:"system"});
```

`closeMarket` can flip state in O(1), immediately making trading rules false. The authored cancellation loop fails:

```ts
for (const o of db.scan(orders.byMarketState,[marketId,"open"],{}))
  close(o);
// E_UNBOUND_SCAN. Rewrite as Page<B> work items.
// Delayed reserve release is a product change.
```

**Op 7 — oracle.** Fetching is correctly an effect, and recording is a bounded mutation:

```ts
effect fetchOracle(feedId, marketId) {
  const response = await fetch(...);       // legal only in effect
  await recordObservation({marketId,...}); // named mutation
}
```

But schedules invoke mutations, not effects, and v0 specifies no outbox trigger, retry controller, or effect identity. The 15-minute/48-hour workflow is `E_OPAQUE`; no v0 rewrite is complete.

**Ops 8–10 — disputes and votes.** `fileDispute` is a bounded mutation over proposal, market, balance, one dispute, and fixed ledger legs. `castVote` performs indexed recusal `exists` probes and writes only the caller’s vote. This first attempt is refused:

```ts
const votes=db.scan(committeeVotes.byTally,[roundId],{take:5});
if (votes.count(v=>v.weight===1 && v.resultKey===choice)>=3)
  finalize(...);
// E_STRUCTURAL_COUNT: a resource count over secret peer votes escaped voter
// visibility. Rewrite: schedule maybeFinalize under system, with All<5>.
```

`finalizeResolution` may scan all five votes and all twenty outcomes under system authority, but its loop over every dispute is unbounded. Finalize the result first, then process bonds in bounded, idempotent chunks.

**Op 11 — settlement.**

```ts
    let paid=0;
    for (const p of ps) {
      const o=db.get(outcomes,p.outcomeId);
      const value=p.token==="YES" ? o.valueYes : o.valueNo;
      const amount=p.qty*value;
      db.require(p.settledRunKey==="","ALREADY_SETTLED");
      // Insert uniquely keyed payout ledger legs.
      db.update(positions,p.positionId,x=>({
        ...x,qty:0,costBasis:0,settledRunKey:run.runId,payout:amount
      }));
      paid+=amount;
    }
    db.update(settlementRuns,run.runId,r=>({...r,paidTotal:r.paidTotal+paid,
      cursor:ps.length ? ps[ps.length-1].positionId : r.cursor}));
    // On hasMore create a distinct next work key; otherwise finish.
  }
);
```

The chunk is a plan. Durable chaining of distinct work keys is not fully specified. Finalization reads ≤20 pools and refuses completion unless pools are zero and `paidTotal===expectedTotal`.

**Op 12 — withdrawal.** This first line is outside v0:

```ts
db.require(principal.secondFactor ||

// E_OPAQUE: MFA, bearer subject, and scoped API-key claims are absent.
```

After an authorized request, processor submission is an effect and success/failure is a constant mutation. Callback ingress and its authentication are unspecified runtime seams.

| invariant | enforcement in v0 | result |

| 1. YES/NO/VOID payout | immutable final values + settlement arithmetic | blocked by binary-NO design bug |

| 12. pay only after final/no reversal | state rules, fences, immutable values | mostly enforceable |
| 13. pay once/conserve | unique marker, immutable settled state, chunks | at-most-once strong; conservation only checked by program |

Compared with the original design, v0 newly makes locked funds, pending additions, public depth, holder counts, read secrecy, append-only records, and retry fences engine/schema facts. It still cannot enforce the original design’s central cross-row conservation equations. Conversely, v0 loses the assumed sealed matcher, FIFO book executor, unbounded sweep, and end-to-end job/effect runner.

### 6. Language delta

Ranked:

1. **Sealed operation authority:** user-authorized transition running with scoped system reads/writes, retaining an unforgeable subject and taint-safe outputs. General; amend §§3, 6, 7.
2. **Keyed FIFO sequencing:** `serialBy(outcomeId)` shared by place/cancel/replace/expiry/close, with engine-issued acceptance sequence and authoritative receipt time. General; §§4.2, 6.
3. **Transaction constraints:** `balanced(by ref)`, cross-table `sumEquals`, numeric sum caps, nonnegative/cross-column checks, and event-coupled transitions. General; §2.
4. **Durable bounded jobs:** cursor work items, distinct chunk idempotency keys, generation fences, self-continuation, and terminal state. General; §§1, 7.
5. **Effect orchestration:** transactional outbox, schedule→effect trigger, service identity, retry envelope, authenticated callback ingress, and completion mutation. General; §§1, 7.
6. **Maintained indexed projections:** indexes and sequence/version custody on maintained rows; `min/max/first/last/rank` with declared disclosure. General; §§2, 4.4.
7. **Principal claims:** API-key subject mapping, scopes, revocation epoch, MFA, and distinct scheduler/oracle/payment/admin identities. General; §§3, 4.3, 7.
8. **Invocation policy:** `onlineOnly`, `queueAllowed`, `predict:false`, plus server `receivedAt`/commit-time deadline decisions. General; §§4.3, 6.
9. **Complete value model:** `optional`, constrained enums/state transitions, tagged unions/principal refs, `int({min,max})`, hashed secrets. General; §§2, 4.5.
10. **Atomic composite upsert and partial uniqueness:** needed for positions, votes, levels, candles, event fences, and callback references. General; §§2, 4.2.
11. **Normative `ref` semantics:** existence, deletion, same-transaction deferral, hidden-conflict sealing, and composite targets. General; §2.
12. **Protection classes:** either field projections or checker-required table splits for public profile, internal depth count, oracle config, and closed-vote disclosure. General; §§2–3.
13. **Uniform-audience live fan-out:** evaluate one public book snapshot and fan it to 40,000 subscribers. General runtime optimization; §6.
14. **Deterministic monetary helpers/in-transaction composition:** widened `mulDivCeil` and named private transaction functions. General but lower priority; §§4.1–4.5.

A hard maker bound is deliberately not solved by admitting an unbounded construct: the product must impose it or externalize matching.

### 7. Product changes

| Product change | What it dodges | When acceptable | When it is a cheat |
|---|---|---|---|
| Hard `MAX_EXAMINED_MAKERS`; atomically refuse `MATCH_FRAGMENTATION_LIMIT` | unbounded sweep | documented exchange limit | filling a prefix, resting a crossed remainder, or calling it FOK |
| Define acceptance as entry into a durable per-book FIFO | ambiguous arrival order | queue position is acknowledged durably | assigning a sequence before retries then committing out of order |
| Make placement asynchronous: `pending` intake → system match | caller/system authority | UI says pending and depth excludes it | returning accepted sequence/immediate fill statement at intake |
| Put matching in a dedicated exchange sequencer | Snapback’s high-write-firehose non-goal (`LLP 0000#non-goals`) | Snapback remains system of record through an atomic integration | claiming the matcher is a v0 plan or asynchronously publishing “exact” depth |
| Page portfolio/orders with versioned cursors | unbounded whole-account read | large accounts see explicit pages | presenting mixed-version pages as one strong snapshot |
| Close immediately, release orders/reserves in chunks | unbounded cancellation | UI says “closing; release pending” | claiming cash returned instantly or orders no longer rest |
| Split finalization, bond disposition, and payout into fenced jobs | unbounded atomic work | states distinguish resolved/settling/settled | marking settled before exhaustion and conservation |
| Drop early committee close; finalize at deadline | hidden voter tally | deadline-only governance is intended | tallying under voter visibility while claiming secrecy |
| Grandfather each order’s fee schedule, cap at its quote, or cancel on schedule change | incompatible fee promises | policy is explicit before placement | claiming both arbitrary fill-time schedule and immutable max quote |
| Owner-session-only withdrawals or processor polling | missing MFA/webhook principal model | explicitly narrower security/API product | continuing to advertise scoped-key withdrawal/callback support |
| Move leaderboard to an analytics service or remove it | global time-window rank | leaderboard is non-core | publishing visibility-filtered or stale rank as exact |

### 8. Where the design is wrong

1. **Binary NO is unrepresentable.** A binary market has one outcome, while a proposal contains that outcome ID or `null=VOID`; neither means NO. Confirmation: attempt to finalize the sole-outcome binary as NO—no legal stored value produces `valueYes=0,valueNo=100`.

2. **Open NO positions use the YES mark.** Op 4 applies `bestBid`/`bestAsk`/`lastPrice` directly without `100−YES`. Confirmation: with YES midpoint 70 and one NO share costing 40, the authored formula reports +30¢ instead of −10¢.

3. **GTC fee promises conflict.** A resting order must use the schedule in force when filled while never exceeding its earlier quote, but stores neither a governing version nor a cap rule. Confirmation: place under schedule A, activate higher B, then fill—A violates “in force”; B may exceed the quote/reserve.
