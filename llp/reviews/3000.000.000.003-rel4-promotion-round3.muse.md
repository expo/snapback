## Assessment against commissioned boundaries

- Stopped-source snapshot: intent is coherent, ordering is not. See issue 1.
- Atomic no-replacement publication: sibling-candidate plus `NOREPLACE`/`EXCL` rename is the right shape. Refusal-before-copy plus rename-time `EEXIST` covers the raced-destination case.
- Account preservation with authority revoked: direction is right, enumeration is not. See issue 2.
- Fresh store identity and reacquisition: requirement is stated, enforcement contract is missing. See issue 3.
- Immutable history plus provenance: the two proof criteria contradict. See issue 4.
- Strict gate, zero-clock, quiescent queues: strict preflight on the candidate is right. The clock gate is under-specified. See issue 5.

## Material issues

### 1. Running-source check is not bound under the source lock

Counterexample: staging is stopped at check time. A `serve STAGING` starts before the snapshot begins. The backup-surface copy then reads a live writer. The result is a torn snapshot sold as coherent.

Minimum fix: acquire the source exclusive owner lock first with no wait-stealing, refuse if held with the `stop` repair, then re-verify no live owner under that held lock, then snapshot. Hold both the release-command lock and the owner lock through publication. State that order in the design.

### 2. Revocation enumerates kinds instead of closing authority

Counterexample: design revokes full/read sessions, refresh families, and service/operator tokens. A delegated action bearer, supervised service family entry, device credential, mint receipt, or read cap issued on staging survives the copy. It then authenticates against production. This repeats the round-one failure mode with a different table.

Minimum fix: define revocation as an allowlist over every authority-conferring table, not example kinds. Add a post-revocation assertion of zero live authority on the candidate. Bind session and token validation to the new store incarnation so any missed row still fails closed.

### 3. Fresh incarnation has no admission contract

Counterexample: a staging device holds a watermark plus pending writes. It points at production after promotion. Production accepts the old watermark as continuous history. Rows are skipped or duplicated across two independently writable stores.

Minimum fix: require the server to reject watermarks, device ids, and pending writes issued under a different incarnation with a reacquire repair. Invalidate or rebind copied device and watermark state on the candidate. Keep historical receipts readable without accepting old watermarks for new writes.

### 4. History equality contradicts the provenance event

Counterexample: the proof demands immutable release and history equality. The design also demands a new promotion provenance record. An implementer either omits provenance to pass equality or adds provenance and fails equality.

Minimum fix: define the check as strict prefix equality: production history equals staging history plus exactly one appended promotion event linking predecessor and new incarnations. Never define it as byte equality.

### 5. Clock gate misses retained future floors

Counterexample: staging runs unpaused with zero effective offset but retains a future schedule boundary or commit stamp. It passes the stated gate. Production startup then resumes at the maximum of the retained evidences per the durable-time rule and jumps into test future. Test time becomes production time despite the gate.

Minimum fix: refuse promotion when any retained time evidence exceeds wall time: effective offset, pause flag, checkpointed time, disclosure floor, commit-stamp maximum, and schedule boundary. Name the exact five-evidence comparison instead of one frontier.
