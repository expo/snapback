### 2. Schema in v0

This uses only v0 scalar types. `E(n)` expands to `text({max:n})`; enum membership is checked by every writer because v0 has no enum/check type. `O(name,T)` expands to `hasName: bool(), name: T`, avoiding an invented nullable type. Permissions are normalized booleans, not opaque JSON.

Constraints:

- `appendOnly()` on agreements, official closes, cash entries, fills, tax-lot events, lot allocations, order events, venue reports, account-session marks, statement/tax lines, and frozen manifests.
- `immutable(...)` freezes fill execution fields, allocation order/quantity/generation, outbox key/payload/hash, statement/form hashes and blobs. `immutableExcept` allows only the declared order, reservation, lease, account-fence, grant-revocation, and quote-snapshot transitions.
- `exclusion({on:['accountId','userId','role'], interval:'valid'})` and the analogous entitlement and identifier exclusions prevent overlapping authoritative intervals where the product requires one covering row.
- Partial uniqueness for optional execution IDs is not expressible; the valid v0 normalization is separate append-only `venueExecKeys` and `internalExecKeys` tables with unique non-null keys.
- No `tree` is warranted: the brokerage model has no recursive ownership hierarchy.
- No cap exists in the fixed product for holdings, lots/order, or fills/symbol-day. Therefore `All` cannot honestly be used for those collections.

```ts
export const quoteBootstrap = query(/* instrumentIds max 200 */, ({db,args}) => {
  const access = db.get(activeParties.byAccountUserView,

  return out
})
```

Current v0 refuses `E_OVERFLOW`, `E_UNBOUND_SCAN/E_UNBOUND_LOOP` (`L` is not declared), and the PDT loop-tally route with `E_STRUCTURAL_COUNT`. The accepted order, reservation, frozen allocations, event, outbox, and `bpVersion` update then fit one mutation. Prediction is `partial`: risk data and current authority must not be delivered, and the product forbids showing `accepted` before settlement.

5. `CancelOrder`

```ts
export const cancelOrder = mutation({orderId:id(orders)}, ({db,args}) => {
  const o = db.get(orders,args.orderId)
```

```ts
  [accountId,instrumentId,sessionDate], {order:'asc',take:F})
let opening = 0, closing = 0
for (const order of groupByOrder(fills)) { /* FIFO pairing and tallies */ }
return max(opening,closing)
```

`E_UNBOUND_SCAN/E_UNBOUND_LOOP`; `E_STRUCTURAL_COUNT` covers both loop tallies, `max`, and the five-session sum. `take:F` would merely truncate a regulatory answer. The honest rewrite is a host-maintained ordered reducer, or an explicit hard order cap plus `All`; ordinary `maintain.count/sum` cannot perform the pairing.

9. `SyncDevice`

A single data program cannot provide separately committed PlaceOrder/watchlist calls or “all events”:

### 8. Where the design is wrong

1. **PDT capacity is checked but not reserved at accept.** With current count 2, two serialized closing orders can each predict count 3 and route; after both fill, the second creates the prohibited fourth trade, which cannot be unfilled. Confirm by accepting two same-day-closing sells before either execution arrives. The design needs an accepted-closing PDT reservation, not only a fill-time fence.

2. **Frozen lot allocations do not subtract allocations already reserved by other open orders.** Aggregate share reservation prevents total oversell but not two orders choosing the same tax lot. Confirm with lots `L1=6`, `L2=6` and two six-share sells: both may allocate `L1` while aggregate availability still permits twelve shares. A per-lot reserved-allocation total is required.

3. **Wash sales have an invariant and a downstream assumption, but no producer.** `Generate1099B` merely assumes wash adjustments are already booked. Confirm with a loss sale on December 31, form generation January 5, and a replacement buy January 20: the frozen form is wrong and the stated immutability prevents correction.
