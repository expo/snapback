## New defects introduced by the repairs

### Medium — closed-tab adoption can replace the live tab’s entire receipt window

`web.ts:370-375` `keep_write`s every orphan `client:write-history` entry. `device.rs:807-810` appends a new id and `drain`s from the front once the list exceeds 256; an id already present is left in its old position.

**Scenario.** Primary tab has 256 terminal receipts `A1…A256` (the whole retained window). A secondary tab, later orphaned, has 256 different receipts `B1…B256`. Closing the secondary copies each `B*` into the primary. After 256 pushes, every `A*` has been drained. `client.write(A256)` on the live tab returns `undefined` even though that mutation was sent there.

**Smallest fix.** In `adoptOrphans`, union by id and keep destination entries as the newest 256 (only `keep_write` orphan ids that are missing, and stop once the destination is full); do not FIFO-append a full orphan window onto a full destination.

### Low — `onWrite` can fire twice for a sent id still in the outbox

`firstEmission` evicts from a 256-id set (`writes.ts:54-58`). `flushOnce` calls `emitWrite` on every queued row that already has `sent_seq` (`local.ts:933-937`), which is the path that persists a receipt before outbox retirement.

**Scenario.** Mutation `A` is sent and remains queued while catch-up finishes. The client then first-emits 256 other terminal ids. A later `flushOnce` sees `A` still in `queued()` with `sent_seq`; `firstEmission("A")` is true again and `onWrite` replays `A`.

**Smallest fix.** Do not cap `emitted` (it is only ids), or drop an id from `emitted` only when it leaves `terminal`, and skip `emitWrite` when `values` already holds a terminal receipt for that id.
