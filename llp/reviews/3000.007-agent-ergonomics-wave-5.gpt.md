## Findings

### F1 — High: a failed host startup changes a running host’s replay policy

**Location:** [serve.rs:236](snapback4/crates/snapback4/src/serve.rs:236), [dev_replay.rs:11](snapback4/crates/snapback4/src/dev_replay.rs:11).

Start `dev --replay`, then start ordinary `dev` against the same project and port. The second process writes `dev:replay=false` **before** attempting to bind the occupied port at line 251. It exits, but subsequent emissions from the original replay host now enter `_outbox` and are claimable.

Two hosts on different ports also overwrite each other’s policy. Moreover, `record` checks no release identity: a delayed dev startup that opened the store before deployment can subsequently set replay metadata on the now-deployed store.

**Smallest fix:** acquire exclusive host ownership of the store before changing replay/schedule policy; refuse competing starts without changing metadata. Independently prevent release transactions from honoring dev suppression metadata.

### F2 — High: an explicit inner index silently moves to the outer read

**Location:** [parser/expr.rs:264](snapback4/crates/snapback4-lang/src/parser/expr.rs:264).

Consider this previously valid query:

```quarry
return posts['bob'] first 1 where exists follows[viewer, .author] by byReverse
```

Let `posts.byReverse` be `(author, id)`, and let follows have unique `byPair: follower, followed` plus non-unique `byReverse: followed, follower`.

Previously, the explicit `byReverse` belonged to `follows`, asking whether Bob follows the viewer. Now it belongs to `posts`; the inner probe selects `byPair`, asking whether the viewer follows Bob. Both programs compile, but asymmetric follows produce different results.

**Smallest fix:** preserve the interpretation of previously accepted reads. Where modifier ownership would be ambiguous, require parentheses with a specific diagnostic instead of silently moving the modifier.

### F3 — High: unique preference overrides an existing exact-type choice

**Location:** [bind/program.rs:374](snapback4/crates/snapback4-lang/src/bind/program.rs:374).

For a table with:

```quarry
a: int
b: time
c: int
by byA: a, c
unique byB: b, c
```

`exists t[x, 0]`, where `x: int`, previously selected `byA` through the exact-type fallback. The new filtering selects unique `byB` before reaching that fallback, because int and time are comparable.

A row `{a: 1, b: 2, c: 0}` therefore makes the query with `x=1` change from true to false.

**Smallest fix:** retain the existing exact-type winner; apply unique preference only when the former selection would remain ambiguous.

### F4 — Medium: parameter-supplied IDs still receive misleading eligibility

**Location:** [residency/inserts.rs:52](snapback4/crates/snapback4-lang/src/bind/residency/inserts.rs:52).

`supplied_id` recognizes literals and `viewer`, but not an argument or other non-minted expression.

On a fully synced private likes table with `read <- .principal = viewer` and unique `(postId, principal)`:

```quarry
mutation add(id: id, postId: id):
  insert likes { id, postId, principal: viewer } if absent
```

The compiler reports eligible and omits the insert-arm summary. At runtime, that supplied ID was not minted by the operation, so [write.rs:56](snapback4/crates/snapback4-core/src/engine/write.rs:56) requires the `byId` proof, which cannot establish this private audience. Every absent insert queues.

**Smallest fix:** track whether the ID is provably minted; require the primary-key proof for other supplied expressions. Add matching diagnostic/runtime tests on both stores.

### F5 — Medium: every completed write is retained indefinitely

**Location:** [writes.ts:19](snapback4/packages/snapback4/src/writes.ts:19), [local.ts:171](snapback4/packages/snapback4/src/local.ts:171).

Each distinct mutation adds a permanent Map entry, persistent `client:write:<id>` metadata, and an `emittedWrites` Set entry. There is no eviction or cleanup policy. A long-running client grows continually even after its outbox empties; persistent growth survives reopen. Eventually receipt persistence can exhaust storage and obstruct settlement, since saving precedes retiring the outbox entry.

**Smallest fix:** introduce bounded terminal-receipt retention, prune the in-memory deduplication state, and document that expired IDs return undefined. Preserve unresolved writes independently.

### F6 — Medium: installing into an existing app can break its schema

**Location:** [init.rs:17](snapback4/crates/snapback4/src/verbs/init.rs:17).

An existing app already declaring `posts` or `follows` passes destination checks when `feed.q` and `following.ts` are absent. Init writes both files and reports success. The next compile fails because table names are global; [catalog.rs:43](snapback4/crates/snapback4-lang/src/bind/catalog.rs:43) rejects duplicates. Module-qualified operations do not namespace those tables.

**Smallest fix:** compile the proposed recipe with existing sources in memory before writing, and refuse name conflicts with the colliding declarations identified.

### F7 — Medium: a parent-path conflict leaves a partial recipe

**Location:** [init.rs:59](snapback4/crates/snapback4/src/verbs/init.rs:59).

With an existing `snapback/schema.q` and a regular file named `src`, checking `src/following.ts` returns an error that is treated as absence. Init writes `snapback/feed.q`, then fails creating the `src` directory. The command returns failure with the recipe half-installed.

**Smallest fix:** preflight non-directory ancestors and required auxiliary files before writing; remove newly created recipe files if a subsequent write fails.

### F8 — Medium: Trending’s final tie-breaker differs from its immediate alternative

**Location:** [feeds.md:462](snapback4/crates/snapback4-lang/src/guide/feeds.md:462), [feeds.md:487](snapback4/crates/snapback4-lang/src/guide/feeds.md:487).

`upsert ranked[p.id]` addresses `byPost`; its insert mints a separate ranked-row ID. Scheduled ordering uses that ID, while `trendingNow()` sorts by the post ID.

With eleven posts sharing the same timestamp and like count, the two top tens can disagree even after scoring fully converges. The existing 105-post test gives every post a distinct timestamp, so it does not exercise this tie.

**Smallest fix:** order ranked rows by `score, at, postId, id`, and test equal-score/equal-time pagination against the immediate result.

### F9 — Low: principal relationships are mislabeled as follows

**Location:** [bind/mod.rs:239](snapback4/crates/snapback4-lang/src/bind/mod.rs:239).

The detector checks only a pinned principal column and another principal column used for lane discovery. A manager-to-report, delegation, or account-access relationship has the same structure and receives “read cost grows with follow count” plus Following-specific guidance.

**Smallest fix:** describe relationship/lane-count growth neutrally and present Following as a conditional example unless explicit application semantics establish it.
