## Blocking findings

### 5. High — Ordinary maintain adoption can permanently halt a healthy client

Round 2 treats the notification counter as an authoritative database head at [serve_changes.rs:59](snapback4/crates/snapback4/src/serve_changes.rs:59).

A concrete, legitimate sequence:

1. The database and notification counter are at **N**.
2. Adding or changing a populated maintain records rebuild commit **N+1**. See [engine/mod.rs:390](snapback4/crates/snapback4-core/src/engine/mod.rs:390).
3. The source watcher publishes the new generation and notifies waiters, but does **not** advance `shared.seq`. See [serve.rs:348](snapback4/crates/snapback4/src/serve.rs:348).
4. The client successfully acquires through **N+1**.
5. Its next `/changes?since=N+1&store_id=<same ID>` returns immediately because `shared.seq != since`. There are no later commits, so the response reports **N**.
6. [local.ts:327](snapback4/packages/snapback4/src/local.ts:327) persists that apparent regression as `E_STORE_RESTORE`. Healthy reads and retries now remain refused across reopening.

The database never shrank. This is a **new round-2 defect**, directly exercised by the maintains integration. Out-of-order notification-counter assignments after concurrent mutation commits provide another route to the same problem.

**Required repair:** obtain the actual database head with the changes read; use the notification counter only for waking polls. Keep its updates monotonic and refresh it after activation.

**Regression:** none found constructs adoption → acquisition of the rebuild commit → the next idle poll. The existing restore test constructs an actual backup restore; it cannot distinguish this false positive.

### 6. High — A second native owner can execute A’s module after B is acquired

This is a **remaining boundary of finding 1’s repair**, rather than a demonstrated new regression.

The owner fingerprint hashes schema, Quarry programs and generation, but excludes the native module and store incarnation: [store_identity.rs:17](snapback4/crates/snapback4-device/src/device/store_identity.rs:17).

Construct two native owners sharing one device store:

1. Both have A’s native module loaded.
2. B has the same schema, Quarry declarations and generation, but different native-module bytes.
3. Owner 1 observes B, adopts its backend, installs B’s module and completes acquisition.
4. Owner 2’s backend fingerprint still matches. Its `sync_state` reports no adoption requirement: [device.rs:427](snapback4/crates/snapback4-device/src/device.rs:427).
5. Owner 2 passes the read guards and executes its existing `self.native`: [device.rs:617](snapback4/crates/snapback4-device/src/device.rs:617), [device.rs:631](snapback4/crates/snapback4-device/src/device.rs:631).

The JavaScript client can observe B and complete sync without reloading the backend, because persisted identity already equals B, generation matches, and `backend_required` is false. `nativeReady` remains true. A fresh query or watch can therefore publish A’s computation as fresh and complete; the asynchronous revision fence cannot help because the computation starts after the revision changed.

**Required repair:** bind each owner’s loaded native module to the adopted incarnation/module digest, and require owner-local adoption or reload when that binding changes.

**Regression:** [native.rs:297](snapback4/crates/snapback4-device/tests/native.rs:297) changes Quarry code, making the fingerprint differ. It does not construct identical Quarry declarations with different native bytes.

## Other requested probes

- **Asynchronous reads:** the original delayed server, horizon and device responses are checked before return; server caching and watch notification are fenced too. Same-incarnation results are accepted without an unconditional retry. The native-owner case above remains outside that protection.
- **Persisted adoption:** reset and the obligation commit together; checked backend installation clears the obligation atomically. Offline reopen, failed installation and acquisition-before-adoption are covered. The IndexedDB tests model transaction boundaries; they do not execute browser termination.
- **Polling/reconnect:** foreign identities return immediately. Matching idle identities retain the normal wait, and reconnect probes check identity before restoring local freshness. These controls have live wasm/process regressions, but finding 5 invalidates the lower-head handling.
- **Restart, release and boundaries:** ordinary reopen/release activation preserves store identity. The positive watermark tests reach `2^53−1`; clock movement does not itself trigger restore. A populated maintain’s rebuild is the legitimate adoption counterexample above.
- **Merge mechanics:** contribution indexes are prepared before fingerprinting and installation on both [device open:261](snapback4/crates/snapback4-device/src/device.rs:261) and [adopt_captured:357](snapback4/crates/snapback4-device/src/device.rs:357). Preparation is idempotent. I found no additional defect in that merge resolution.
