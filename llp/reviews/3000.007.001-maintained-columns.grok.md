# Review of LLP 3000.007.001 — maintained columns

The direction is right: if the group is a row, the aggregate belongs on that row. That is what three Clique builders reached for, and it is the only form that deletes `update <- allow` on `posts`, makes zero a real parent, and makes “holding the post” the same fact as “knowing the base.” The security model is also the right one — engine authority, no rule on the engine write, source rules as the only principal authority, overflow value-free, paired §17 observations.

It is not yet specified tightly enough to keep that promise. The text names `maintain_scratch` and “the formula `Runner::maintain` already uses” as the hidden-parent reservation; those paths do **not** equalize skip vs write. Adoption’s “read 0 through `materialize_optional_fields`” does not match that function. A lane that reused `rebuild_maintain`’s delete-all-targets loop would delete parent rows. Those are design holes, not lane taste. With the amendments below the form should be built.

## Findings

### 1 — High — RFC §3.2 — `write_target.rs:287–290`, `maintains.rs:29–35`, `maintains.rs:157–191`

**Reservation as written does not implement the paired method.**

`Runner::maintain`’s scratch is a heap lease that is subtracted after work, so net heap equals actual work (`maintains.rs:29–35`). The path that **equalizes** hidden vs absent is `reserve_maintains` + `charge_maintain` no-op, and that path returns immediately when the source is uniformly readable or the maintain has no filter/computed key/expiry (`write_target.rs:287–290`). A maintained column’s hidden fact is **parent existence / parent image**, not a filtered source contribution.

Failing worlds: `notes` public, `secrets` `read <- .owner = viewer`; `secretNoteCount: count notes by secretId`. Writer W inserts a note for secret S. World A: S absent. World B: S present (owned by someone else), count 0. World C: S present, count near `I53_MAX`. Without prepaid parent-write meters, A commits with one row written; B with two and a parent index update; C overflows. At a tight rows/index/heap ceiling, A is `sent` and B is `E_BOUND`. W is not in S’s audience, so stream/snapshot stay equal; the meter/E_BOUND channel is enough.

**Smallest design change:** For every maintained column, before the parent lookup, prepay the static worst case of one parent `get` + one parent `put` (copy ceiling × indexes, two index-key images, one examined, one rows-written, index-entry ceiling) using the `maintain_prepaid` / `charge_maintain` mechanism, **whether or not the source is uniformly readable and whether or not there is a filter.** Lookup is `tx.get` plus `Table::expired`, never `fetch`/`get`. Overflow stays the named residual; §8 must say so. Skip and write then share every meter field.

### 2 — High — RFC §3.11 / §2 — `schema.rs:1264–1277`, `successor.rs:80–94`

**Old images do not read 0.**

`materialize_optional_fields` only inserts null for optionals and a value for `ColumnDefault::Literal`. A required column with no default is left missing; `validate_row` then fails (`validate.rs:20–21`). §2 forbids an authored `default`. `classify` will mark that column `Narrowing` unless the maintain step is the only one the store consults.

Failing window: adopt `likeCount` onto a populated `posts` store. Activation’s validate walk (`store/activation.rs:120–128`) materializes, then `validate_row`s application tables. Missing `likeCount` refuses the generation, or a device that interprets a held pre-generation image (if anyone bypasses `keeps_literal_default_images`) serves a row without the field. Postgres has no adopt (`postgres/mod.rs:75–76`) — say so, and do not claim parity there.

**Smallest design change:** The engine treats a maintained column as having an implicit literal `0` for materialize, index build, and old-image validation. Authors still cannot write `default`. `classify` then has a named Additive exception for “required maintained column added.” `keeps_literal_default_images` staying false (devices re-acquire) is correct.

### 3 — High — RFC §3.11 / §6 — `maintains.rs:76–85`

**A column rebuild must not reuse `rebuild_maintain`.**

`rebuild_maintain_inner` scans the **target** table and deletes every row, then folds the source. For a maintain table that is correct. For `likeCount` the target is `posts`.

Failing scenario: lane calls `rebuild_maintain` on the column’s `Maintain`. Every post is deleted, then only nonzero groups are written back as `{id, value, postId}`-shaped rows. User posts disappear.

**Smallest design change:** Specify an in-place rebuild: walk source contributions grouped by parent id; `put` the existing parent image with the one field changed for nonzero groups; leave zero groups to implicit 0; **never `delete` a parent.** Say explicitly that `rebuild_maintain_inner`’s delete loop is forbidden reuse.

### 4 — High — RFC §3.9 / §2 — `schema.rs:540–557`, `bind/schema.rs:166`

**“In any rule of any table” is not what `RuleExpr::fields` walks.**

`fields()` collects `.column` terms on **this** row. Extra equalities of `exists`/`created` store the **probed** column in the pair’s key, which is not collected (`schema.rs:554–556`). `after insert` is a `FinalExistsOnInsert` constraint (`bind/schema.rs:166`).

Admitted declaration that must be refused:

```quarry
table highlights:
  postId: posts
  read <- exists posts[id = .postId, likeCount != 0]
```

A like is an engine write that changes whether `highlights` is readable. That is an audience/verdict change, contradicting §3.8.

**Smallest design change:** The static check is a corpus walk: every table’s read/insert/update/delete rules, every `exists`/`created` probe (keys **and** extra equalities), every `after insert`. If the probed table+column is a maintained column, refuse, naming the column and the rewrite (probe existence only, or count the source). Do not implement this as `parent.rules.read.fields().contains(column)`.

### 5 — High — RFC §3.7 — `predictions.rs:44–93`, `device.rs:189–196`, `partition.rs:435–452`

**Skip is re-evaluated on replay; that is safe only under an unstated delivery assumption.**

Admit with parent unheld: source row predicted, parent skipped, `predictable = true`. Replay runs the whole program on the confirmed image (`predictions.rs:44–54`). If a later apply has put the parent, replay will write the parent.

When the source row is in the same commit as the parent put, restore+apply then replay collides on the source id and rolls that overlay back (`predictions.rs:89`; commits are delivered whole). That is the common Clique like. It fails when the parent put is applied **without** the source row: online-only source, or §3.6 filtering the parent put while the like is already locally predicted and then a later unfiltered parent image arrives.

**Smallest design change:** State the invariant: a prediction that skipped the parent skips it on every replay of that outbox entry (sticky), **or** state the assumption “source is synced to the writer and delivered in the same commit as the parent put” and refuse an online-only source for this form. Add the acceptance case. Leaving `pending` unset stays right: restore is `_device_base` (`predictions.rs:21–37`); `media.rs:102` would hide the post’s image if the like marked the post pending.

### 6 — Medium — RFC §3.2 — `write.rs:181–188`, `schema.rs:265–268`, `read.rs:268–276`

**Expired parent.**

§3.4/§3.2 say skip if expired. `apply_aggregate` today does not call `expired`. A `put` of an expired parent would emit a live `Put` (`partition.rs:143–148`) and resurrect the row until the next sweep (`engine/mod.rs:628–648`). The expiry check is one field on the one looked-up image — population-independent, no hidden sibling walk. Specify `tx.get` + `Table::expired`, not `fetch` (which is a device unknown-fact).

### 7 — Medium — RFC §3.2 / §6 — `engine/mod.rs:940–956`, `native.rs:660–698`, `postgres/mod.rs:280–330`

**`load` and native jobs are writer classes the refusal list under-names.**

`load` is the fixture path that writes images as given and skips maintains. For columns it would persist a lying `likeCount`, or persist source rows without touching parents. Native jobs call `runner.update` with any declared column. Both must go through the same per-column engine refusal as hand-serialized IR, **except** `load` if it remains the “already-computed fixture” hatch — in which case the card must say fixtures carry the column and source+parent are the caller’s to keep in step.

### 8 — Medium — RFC §3.2 — `write.rs:336–338`

**Append-only parents.**

Engine writes skip `check_constraints`, so they would update an append-only `posts`. That is the behaviour you want (programs cannot edit body; the engine can bump the count). Name it: append-only continues to mean program updates; it does not refuse the engine’s column.

### 9 — Medium — RFC §3.6 / §9.1 — `device.rs:572–581`, `NOT-DOING.md:31`

**Pick filter-at-device, and write the predicate.**

Accepting growth under `sync public last 2000 by byTime` plus likes on old posts will acquire every liked old post. That fights the hub acquisition bar. Filter: ignore a `put` when the device does **not** hold the id **and** the row’s horizon key sorts strictly older than the acquired boundary of that group. Held rows always apply. Tables with no horizon never filter. That is not exact horizon maintenance. Ordinary program updates to unheld old rows are rare and correctly ignored; updates to held old rows still apply. §7 item 2 still gets measured, as a regression bound on the filter, not as a choice to accept the growth.

### 10 — Medium — RFC §8 / §7

**Acceptance over-claims; several guards are missing.**

Would not fail when broken: “identical outcome… every meter field” as written would fail the overflow residual and birth `E_BOUND` even when the design is right — either name those residuals or the test will teach the wrong contract. Missing: native/serialized/seed/`load` refusal; probe extra-equalities; expired-parent skip; rebuild does not delete parents; 0 is not served from a pre-generation held image or a snapshot page that crossed activation; skip-then-replay; two overlapping likes on one held parent (first base image wins, no `pending`); Postgres seed/upsert parity; writer HTTP body stays `sent` in the hidden-parent pair (it should; meters are the test helper).

§7’s five measurements are the right briefing gate. Do not brief a lane without 1, 2, and 5.

### 11 — Low — RFC §3.5 — `bind/residency.rs:263–277`

`N_MAINTAINED_COLUMN_STREAM` should fire on the **parent** table’s sync, not via `inherited_from` on a generated target. `N_MAINTAIN_SYNCED`’s grouping of many maintains into one envelope (`:279–283`) must not swallow it.

### 12 — Low — RFC §3.3

Same-commit birth vs maintain order should be stated (reply then parent: skip then birth; parent then reply: 0 then +1). Implementers will otherwise double-count the parent’s own source image on self-ref `replyCount`.

---

The High items change behaviour if a lane follows the RFC literally; they are small spec patches, not a different feature. No remaining issue after those patches is more than Medium, and the Medium items are implementable without changing the user-visible form (prepaid skip, implicit 0, in-place rebuild, sticky skip or a stated delivery assumption, filter predicate, named residuals).

I would build this form. I would not build `maintain … over posts` as the primary: it does not answer P2, and the bakeoff evidence is that builders write the column anyway.

Verdict: READY WITH CHANGES
