## Findings, most severe first

**1. High. `E_AUTH` and `E_CLOSED` failures are extracted as terminal certificates, and credential rotation is hidden behind `lifetime-ended`.**
`snapback4/packages/snapback4/src/settlement-extract.ts:87` (outcome) and `:104` (authority); `refusal-decision.ts:43-45`.
Both executors treat these codes as non-terminal today: `app-online.ts:118-119` excludes them from `terminal()`, so `dispatch()` at `:333-339` answers the caller `pending` and keeps the journal intent, which LLP 3000.013.000 §4.6 requires ("retained through sign-out, replaying at that account's next sign-in"; the client model at `test/helpers/online-client-model.mjs:135` encodes the same rule). The wrapper's retry at `local.ts:1939` also runs before any lifetime check, and `endSession` bumps `credentialRevision` (`local.ts:545`), so every `E_AUTH` that arrives after sign-out is a rotated-credential refusal the wrapper retries.
Scenario: sign-out or a scheduled rotation races an in-flight journal send; the server answers `E_AUTH` (non-retryable). Today: wrapper throws, intent stays pending, replays at next sign-in. S2a: extraction issues `outcome` + `certificate`; `authority` is `lifetime-ended` so `transport: settle`; the reducer emits `deliverOutcome(E_AUTH)` then `settle`/`publish` on `persisted`. Ported as written, the write is persisted as a failed receipt and never replays. The current-credential case is also wrong: the wrapper runs `refusedSession` (`local.ts:1943`) before `current()`, so a terminal `E_AUTH` never reaches `onlineEvidence`, yet `decideRefusal` returns `metadata: through-online-evidence` and test `S2a 5` asserts it; reducer test `S2a 4` asserts `deliverOutcome` for `E_AUTH`.
Fix: in `extract`, withhold `outcome`/`certificate` for non-retryable `E_AUTH`/`E_CLOSED` exactly as for retryable refusals (keep `refusal`); derive `authority` for `E_AUTH` as `credentialCurrent ? (lifetimeLive ? current : lifetime-ended) : obsolete` so rotation outranks lifetime end as at `local.ts:1939`; drop `E_AUTH` from `S2a 4`, change the "E_AUTH after rotation" extraction row to expect no certificate, and have `S2a 5` cover retryable `E_AUTH` only. Record in RFC §2.1 that auth/closed refusals are known non-terminal outcomes.

**2. High. The response pin can only be released by a terminal `response`, so repairs 6 and 13 together leak every retried write.**
`settlement-reducer.ts:39` (`initialState` default 1), `:86-88` (`dispatched`), `:97` (decrement only on `response`), `:118-120` (eviction).
Parent RFC §6 (`llp/3000.002.000-progressive-web-startup.rfc.md:341-343`) says the pin holds "until their receipt processing finishes, including transport failures", which is what `finishReceipt()` in the wrapper's `finally` (`local.ts:1934`, `:1995`) and `ProgressiveWrites.dispatch` (`progressive-writes.ts:60-67`) implement. S2a item 6 makes retryable refusals produce no `response` event, and item 13 makes `response` the only decrement.
Scenario: write W, fetch 1 answers `E_OVERLOADED`, transport retries, fetch 2 answers `sent`. With `initialState()` and one `dispatched` per fetch (the RFC §2.2 row says "one more fetch for this id"), the count goes 1→2→3→2 and `evicted` is refused forever; even if S2b emits no `dispatched` for the first fetch it ends at 1. A thrown fetch behaves the same. The evidence map then grows by one entry per retried or failed send for the tab's life. The RFC §7 defers "a transport-finished event", but the reducer as shipped has no release path at all for the common case.
Fix: add a `transportFinished` event that decrements (emitted where `finishReceipt()` runs today), stop decrementing on `response`, default `initialState(0)` with one `dispatched` per fetch, and rewrite witness `S2a 13` and the generated `outstanding` model accordingly.
