## Overall assessment

The design is coherent and narrowly implemented, but I found two Medium correctness issues: the supposed canonical-reordering canary does not exercise reordering, and a concurrent sync can make a composed read report a `since` newer than one of its components. No server/native regression was found. No Critical or High findings.

## Findings

### Medium — the “canonical reordering” canary is already canonically ordered

File: [web.rs:29](/Users/ccheever/projects/snapback-dm-review/S3-r1/repo/snapback4/crates/snapback4-device/src/web.rs:29)

`U+0323` has combining class 220 and `U+0307` has class 230, so `d U+0323 U+0307` is already ordered. A host implementation that composes but never reorders can therefore produce `U+1E0D U+0307` and pass all four canaries.

Concrete failure: such a host passes construction, but folding `d U+0307 U+0323` can produce `U+1E0B U+0323`; Rust NFC reorders it and produces `U+1E0D U+0307`. Row and query word keys can then disagree with the server without `E_HOST_UNICODE`.

Smallest fix: change the second canary input to `d U+0307 U+0323`, retaining expected `U+1E0D U+0307`, and add a stub normalizer that composes without reordering. The existing tests merely force a wrong answer for each exact canary and do not model this failure. [unicode.test.mjs:34](/Users/ccheever/projects/snapback-dm-review/S3-r1/repo/snapback4/packages/snapback4/test/unicode.test.mjs:34)

### Medium — concurrent sync can make composed `since` too new

File: [local.ts:906](/Users/ccheever/projects/snapback-dm-review/S3-r1/repo/snapback4/packages/snapback4/src/local.ts:906)

The composition path reads the mutable `lastSyncAt` only after awaiting the server reply, the second local observation, and another pending-write check. Background sync can advance it concurrently.

Concrete failure: the previous sync is at `t0`; `/q/both` computes its server component at `t1`; while its response is delayed, the change follower completes a sync at `t2` and sets `lastSyncAt = t2`; composition then returns the older `t1` server component with `since: t2`. The value is not wholly as recent as the reported lower bound.

Smallest fix: capture `const composedSince = lastSyncAt` immediately before issuing the server read and use that captured value in the composed result. Add a test that delays the query response, completes a sync meanwhile, and asserts the returned `since` remains the pre-query sync timestamp.
