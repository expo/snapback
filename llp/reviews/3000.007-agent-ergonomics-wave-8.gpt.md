**1. High — Public cut reasons reveal hidden-row populations.**

Location: [engine/runner.rs:109](snapback4/crates/snapback4-core/src/engine/runner.rs:109), exposed by [serve.rs:901](snapback4/crates/snapback4/src/serve.rs:901).

Consider two stores with equal commit counts and identical reader-visible rows. An unscoped non-uniform query sees no readable matches in either. One store has no matching hidden rows; the other has 8,193. Previously both could return `data: [], complete: false, next: null`. Now the first returns `cut: null`, the second `"meter"`. Likewise, 33 distinct hidden matching words can produce `"words"` without a visible result. This works through production serve without dev meters.

Smallest fix: withhold data-dependent cut reasons for the entire non-uniform server class, and document that `null` can mean an undisclosed reason. Keep precise reasons for device/uniform reads and operator diagnostics. The current unconditional truthfulness promise cannot coexist with the existing disclosure boundary.

**2. Medium — A point-read rule-probe cut can disappear, producing `cut: null` and `complete: true`.**

Location: [engine/read.rs:316](snapback4/crates/snapback4-core/src/engine/read.rs:316); the new field reads that restored state at [engine/runner.rs:111](snapback4/crates/snapback4-core/src/engine/runner.rs:111).

A query can spend 8,192 rule probes through 4,096 successful point reads whose rules each require two true probes, while retaining examined-row budget. Its next point lookup addresses a readable row. The exhausted probe returns `false`; `get()` treats that as a hidden-row verdict and restores the pre-read meter mark, erasing `capped_at`. The query can return null as a complete, uncut answer.

This is an **inherited execution defect**, but it invalidates W8a’s every-path guarantee.

Smallest fix: distinguish an exhausted authorization evaluation from a false verdict. Reserve the rule’s static probe allowance consistently across hit/miss/hidden cases, and preserve incompleteness when that allowance cannot be paid.

**3. Low — Persistent adoption failures can still flood background logs.**

Location: [serve_adoption.rs:52](snapback4/crates/snapback4/src/serve_adoption.rs:52).

After the first contextual “adoption still pending” message, `repeated` sends every subsequent failure into an unconditional `eprintln!`. A stale host whose source cannot be adopted continues printing expiry/job failures every maintenance tick, plus lease and asset failures. The new explanation is bounded; the repeated failure stream is not. This remains a residual of the original incident.

Smallest fix: deduplicate or rate-limit identical background failures while the same adoption failure remains pending, resetting after recovery and reporting suppressed counts.
