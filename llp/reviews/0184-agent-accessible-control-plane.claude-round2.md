## Round-1 concern resolution

1. **`mcp-control` cannot serve build-matched Guide resources — NOT RESOLVED.** The RFC now names a carrier (§Design/4:437-448): "the Rust build pipeline's existing generated artifacts (`guide-flat.generated.md`, `guide-manifest.generated.json`) are packaged alongside `@snapback/cli`'s published files, **each stamped with the Rust build's `buildIdentity.commit`**", plus a refusal rule: "refusing to serve either if the packaged snapshot's `buildIdentity.commit` and a reachable running server's disagree." Every load-bearing clause of that sentence is false against the code:

   - They are not the Rust build pipeline's artifacts. `guide/guide-manifest.generated.json:3` — `"generatedBy": "scripts/generate-guide-manifest.mjs"`. They are checked-in outputs of a Node script; `build.rs` only consumes them.
   - The checked-in copies are, by explicit design, **not** stamped with the Rust build's commit. `build.rs:132-146` reads the source manifest, extracts `manifest_commit`, computes `build_commit` from `SNAPBACK_BUILD_GIT_COMMIT` or `git rev-parse HEAD`, and writes the substitution to `OUT_DIR/embedded-guide-manifest.json`; `build.rs:163-168` embeds *that* file for the `guide-manifest.generated.json` path while every other page is embedded from `CARGO_MANIFEST_DIR`. `guide/conventions.md:154-156` states the invariant in terms: "At server compile time, `build.rs` restamps the embedded manifest's `buildIdentity.commit` to the exact binary build; **the checked source manifest remains the corpus-generation record**."
   - The two commits are *designed* to diverge. `scripts/check-guide.mjs:54` — `const strip = ({ buildIdentity, ...rest }) => rest;` — strips `buildIdentity` before the staleness comparison, so the checked-in commit is allowed to lag HEAD indefinitely; `scripts/guide-lib.mjs:505-514` sets it from `git rev-parse HEAD` at *corpus-generation* time.
   - `guide-flat.generated.md` carries no build-identity field at all (`guide/conventions.md:152-153`: "Its SHA-256 is the manifest's `contentHash`"), so "each stamped" is false for one of the two named artifacts.

   The consequence is worse than an inaccurate sentence: the new refusal rule inverts. A running server reports the restamped **build** commit; the packaged snapshot reports the **corpus-generation** commit; they agree only when the guide corpus happens to have been regenerated at the exact commit the binary was built from. Any commit that does not touch `guide/` breaks the match — and the repo's own workflow (a locally built `target/debug/snapback` against an installed CLI) breaks it permanently. So `mcp-control` would "refuse to serve either" guide path in the normal case, denying precisely the cold-agent discovery the RFC exists to deliver.

   There is a correct carrier the RFC does not use: `snapback mcp` is a **Rust** subcommand (`src/cli.rs:813` `Mcp`, dispatched at `src/cli.rs:1728` to `crate::guide_mcp::run_stdio()`) serving the embedded, restamped corpus. Having `mcp-control` shell out to the co-installed binary — which already ships as `optionalDependencies` `@expo/snapback-runtime-darwin-arm64` / `-linux-x64` (`packages/snapback-cli/package.json:87-90`) — is build-matched by construction and needs no new packaging step. **Resolution:** either invoke the binary's own guide surface, or state that the packaging step re-stamps the artifacts per Rust build (which contradicts calling them "existing"), and drop or re-found the commit-comparison rule so it cannot fail closed on the intended-divergence case.

## New MATERIAL concerns (not in round 1)

1. **The new domain predicate contradicts its own exclusion list, and mis-scopes rule 1 in both directions.**
   §Design/3:358-371 defines the domain as "every registry entry whose `RouteClass` is not `AppData`, plus every `host_ops.*` identity — this is a positive, code-checkable predicate", and then claims it "deliberately excludes app-data-plane operations — `ephemeral_publish`/`ephemeral_delete`/`ephemeral_subscribe`, **`direct_runner.*`**, `app.ensure.*`, and the app-data `POST /ephemeral/delete` route". Three problems, all verified:

   - **The predicate includes `direct_runner.*`.** The registry's `direct` closure is `RouteClass::SystemApi`, not `AppData` — `src/server.rs:14989-14994`: `let direct = |name, path_policy, effect_policy, session_overlay| { operation(name, "/_snapback/api/functions/{name}/run", DirectFunctionRunner, RouteClass::SystemApi, …` — for `direct_runner.query` (`:15097`), `.mutation` (`:15109`), `.action` (`:15122`), `.unknown` (`:15134`). So the predicate says "in domain" and the prose says "a domain error", for the same four entries. This is not academic: the RFC counts "function run" among its 17 control tools (:140), calls it "Strong and agent-native" in the shortfall table (:152), and rule 3 (:386-388) requires every MCP tool to "resolve back to a catalog row" — `snapback_run_function` exists (`packages/snapback-cli/mcp-control.mjs:414`, `operation: 'function.run'`). Under rule 1 as written, the row rule 3 demands is a CI failure.
   - **The predicate over-includes `SystemStatic`.** `RouteClass` has exactly three variants (`src/server.rs:7172-7180`): `AppData`, `SystemStatic`, `SystemApi`. "Not `AppData`" therefore pulls in the console shell and the served guide — `src/admin.rs:3694-3708` (four `system_static_route` registrations including `/_snapback/admin` and `/_snapback/admin/setup`) and `src/server.rs:8638-8647` (three `served_guide_route` registrations). None of the six dispositions fits a static asset route, and the only available escape (`internal`, defined at :232 as "Unsupported as an author/operator action … **No console affordance may invoke it**") is incoherent for the route that *is* the console.
   - **It excludes a registered AdminWrite/Operator control.** `app.ensure.provision` is `RouteClass::AppData` (`src/server.rs:15056-15067`) yet carries `RoutePolicy::AdminWrite`, `CredentialResolution::AdminCredential`, `InvocationAuthority::Operator`, `ResponseSensitivity::OperatorMetadata`. It is the only such entry I found in the registry, and the RFC names `app.ensure.*` as excluded — so an operator-authority provisioning operation escapes the catalog by route class, contradicting Summary/2's "every registered admin/host operation must be cataloged."

   **Resolution:** make the predicate `RouteClass == SystemApi` (plus `host_ops.*`, which is then redundant — all 12 `host_ops.*` entries I sampled are `SystemApi`), remove `direct_runner.*` from the exclusion list or give it an explicit in-domain classification, and handle `app.ensure.provision` by policy (AdminWrite + Operator) rather than by route class.

2. **Rule 3 requires catalog rows the domain rule cannot produce, and the RFC commits to one of them by name.**
   Rule 3 (:386-388): "Every CLI command, MCP tool, and method in `packages/snapback-admin-client`'s public export list resolves back to a catalog row"; §Acceptance:725-729 restates it as a CI failure. But the catalog's domain is registry-derived, and §Design/2:355-356 forbids the escape: "An operation with no governing owner is an error, not an invitation for the catalog to invent semantics." A large family of shipped operator CLI commands has no route and no host-op owner — `CLI_ONLY_HOST_OPS` is only three names (`src/host_ops.rs:58`: `["host.start", "host.stop", "host.restart"]`), so `snapback fork` (`src/cli.rs:807-810`, "Create and operate finite-TTL, non-promotable local derived deployments"), `snapback auth` (`:802`, "Offline physical auth backup and declared restore operations"), `snapback migrate`, `snapback build-identity` (`:819-820`, explicitly "without binding a server port"), `snapback runtime-qualify`, `snapback secret-read-mint`, `snapback composition-activation-prepare`, and `snapback admin approve`/`admin link` (`src/cli.rs:874-895`) all fall through: rule 3 demands a row, rule 1's domain never creates one, §Design/2 makes inventing one an error.

   The RFC contradicts itself explicitly on one of these. §D:658-664 says of the SQL hatch: "that operation gets its own catalog row like any other CLI command." I verified it is local-only with no server surface — `src/cli.rs:1000-1012`, `/// Local-only read-only SQL over the visibility views; never networked.` with `max_rows`/`max_steps`/`max_time_ms`/`max_bytes`. So the RFC promises a row for an operation its own domain rule cannot generate. **Resolution:** add a third domain leg — CLI-declared local operations whose owner is the CLI itself — with its own required fields, or state that local-only CLI commands are catalogued from a CLI-side declaration rather than joined from the registry.

3. **The six-value disposition still has no slot for MCP-without-CLI, and `mediated` overlaps the surface axis — so the enum is not yet mutually exclusive or exhaustive.**
   The revision's own strengthening created the first hole. `native` now requires *both* ("both a CLI command and an MCP tool exist, or the row is not `native`", :235-236); `cliOnly` requires a CLI; `api` requires "**no** direct CLI or MCP tool" (:230). `host.restart` is a registered host-op (`src/server.rs:15532` `host_ops.host.restart`), has an MCP tool (`packages/snapback-cli/mcp-control.mjs:209-215` `snapback_restart`, `operation: 'host.restart'`, implemented at `:817-823`), and has **no** typed CLI subcommand — `HostCommand` (`src/cli.rs:703-880`) has `Start`, `Stop`, `Inspect`, `Reset`, `Load`, `Run`, … and no `Restart`; the only `restart` is a `snapback dev` interactive-keybinding/stdin verb (`packages/snapback-cli/index.mjs:2351-2352, 2383, 2470`), which is not a typed direct CLI command. So `host.restart` holds none of the six values, while the RFC's own table (:152) calls lifecycle "Strong and agent-native." The old frequency-based `native` absorbed it; the new surface-based one cannot.

   Second, the claim that a disposition is "defined purely by **which surfaces it has**" (:219-220) is false for three of the six. `mediated` is defined by human involvement, `internal` and `unavailable` by build/support state — and `mediated` genuinely collides with the surface axis today: `snapback admin link` (`src/cli.rs:880-895`, "Mint, observe, reattach to, or revoke a one-time operator claim link", with `--no-wait` "Print the link and return instead of observing redemption/expiry") is a typed CLI command with no MCP tool *and* the archetypal human-redemption operation with initiate/poll/resume built in. It satisfies `cliOnly` and `mediated` simultaneously; rule 5 would demand an `mcpDeferralReason` and rule 6 plan/initiate/status/resume plus secret-nonleak negative tests, and the RFC gives no precedence rule for a field that must hold exactly one value (:730-731). **Resolution:** add `mcpOnly` (or relax `native` to "at least one typed direct projection" and carry the missing one as a deferral reason), and either move mediation to an independent `mediationPosture` field — the same move the revision already made correctly for risk — or state a precedence rule (e.g. `mediated` wins, and its rule-5 obligations are waived).

4. **OQ3 asserts a v1 security default that §A does not contain.**
   OQ3 (:858-861): "**Direct patch authority — widening, not the v1 default.** §A already fixes the v1 default: **bypass only on an LLP 0158 derived instance**, an impersonated patch on ordinary local dev." §A does not say that. Its target clause is undifferentiated — ":566" "local non-production and LLP 0158 derived instances only" — and its authority clause (:581-585) offers `devUser`/`devAdminBypass` "**or** under an unmistakable **operator bypass** … with approval and audit when application authorization cannot be evaluated", with no target restriction attached to the bypass branch. §Acceptance:752 only adds "It is refused on a primary hosted/production target." So the RFC's most security-sensitive v1 default — on which targets an operator may bypass the application's own authorization to write rows — is stated nowhere, while OQ3 declares it settled and moves on. This is the "describes a fix without the fix being coherent" pattern: the round-1 alignment edit updated the open question to point at a §A ruling that was never written.

   It matters concretely because `LLP 0158` derived instances are not necessarily local. `llp/0158-instance-forking.rfc.md:9-11` reserves `SNAPBACK_DERIVED_INSTANCE_ID` as "the Cloudflare arm['s]… fork-id carrier", and OQ9 is decided as "same-`appId` derived deployment" (`:37`). Under §Acceptance's "primary hosted/production" qualifier, a *hosted derived* deployment is permitted — so as written, operator bypass may be legal on a hosted instance. Separately, 0158 is `Status: Draft` (`llp/0158…:4`) and is the one neighbour §A leans on as a security boundary that is **absent from §Authority and scope's disclaimer list** (:69-92 names 0024, 0031, 0017, 0036/0058, 0042, 0044, 0061, 0094/0095, 0146, 0167 — not 0158). **Resolution:** write the default into §A explicitly (which targets permit `operatorBypass` vs `devUser`/`devAdminBypass`, and whether hosted-derived counts), add 0158 to the authority list with its ownership sentence, and reduce OQ3 to the widening question it claims to be.

5. **§B requires a per-subscription generation that the wire contract does not define per subscription and no shipped operator surface exposes.**
   §B:601-606: "**V1 targets a single subscription**, identified by connection and subscription id, and requires **that subscription's current generation** plus the startup nonce." Two gaps:
   - The generation in the wire contract is connection-scoped, not subscription-scoped. `llp/0095-client-lifecycle-and-conformance.spec.md:251-253` — "locate the exact held subscription by the complete bound `scopeId`, not `subscriptionId` alone, and require its **issuer/connection generation**". In `src/ephemeral.rs` the generations are the socket delivery-registration generation (`:40-42`, `:65`, `:196-214`) and `room_authority_generation` (`:2511-2543`); neither is a per-subscription revision counter. The one per-subscription generation that exists is a different thing — `src/local.rs:3195-3201`, `LiveSubscription { … expected_generation: Option<ArtifactGeneration>, // The asserted sessions artifact generation, pinned at establishment. None is the legacy unchecked subscription contract. }` — an auth-artifact pin that is `None` for legacy subscriptions, so requiring it would make the operation un-invocable for exactly the subscriptions most likely to need forced resync.
   - Even if a value existed, the agent cannot read it. The gated inspect projection exposes only three fields: `src/local.rs:378-382`, `pub struct LiveSubscriptionInfo { pub id: String, pub connection_id: String, pub function: String }`. So the RFC's required precondition is unobtainable through any shipped operator surface, and §Acceptance:753-755 ("Forced resync … drives an actual client through the protocol's existing resync-required/re-snapshot lifecycle") cannot be met without a discovery field the RFC never mentions.

   The rest of §B checks out and is worth keeping: `LiveEnvelope::ResyncRequired` (`src/live_wire.rs:132-147`) carries `subscription_id: Option<String>` and an independent `clear_retained: bool`, and LLP 0095 pins both shapes — T-RESYNC subscription-scoped (`:237-241`) and T-OVERFLOW connection-wide (`:230-236`) — so the v1 narrowing and the OQ4 deferral map cleanly onto real wire states. **Resolution:** name the actual fence (connection generation + subscription id, or the room/scope epoch the store already fences on), and require the inspect projection to expose it as part of the same slice.

6. **Rule 9 plus the narrowed domain would break LLP 0061's existing, currently-passing surface-map join.**
   §Design/3:409-411: "The checker extends the useful LLP 0061 surface-map join rather than replacing it. `guide/surface-map.md` can become a generated human projection of **the same closed join**", and rule 9 (:404-405): "Guide inventories, generated tables, and counts come from the catalog." But the surface map's domain is strictly larger than the catalog's: `scripts/guide-lib.mjs:425-438` enumerates **every** route and **every** host-op and errors on any unclassified one, and `guide/surface-map.md` accordingly classifies 113 route rows including app-data ones — `:124` `| /ephemeral/delete | realtime.ephemeral |`, `:89` `| /app/ensure | backend.provisioning |`, `:131` `| /live/{connection_id}/stream | realtime.durable-push |`. Generating the surface map from a join whose domain excludes `AppData` drops ~40 rows that `guide-lib.mjs` requires, turning a check that passes today (`./ref-check` → "183 LLP docs, 6001 refs in 18481 files, 0 errors"; `check-guide` green per the corpus state) red. **Resolution:** say that the catalog generates only the control half of the surface map and that LLP 0061's app-data classifications remain authored, or extend the generated projection with an explicit app-data leg sourced from LLP 0042/0179 rather than from the `ControlCatalog`.
