## MATERIAL

### 1. Any predicted outbox entry disables owner-page continuation for every query

**Where:** `snapback2/packages/snapback2/src/offline.ts` lines 1148–1158 (`exactOwnerAnswer`), using `ItemCapture.inputs().entries` from `snapback2/packages/snapback2/src/query-items.ts` lines 95–100 (the full partition outbox).

**Failing scenario:**
1. The reader has any predicted intent (queued send, like, or a committed overlay not yet retired). Clique’s still-open sender Pending window makes this the ordinary send path, not an edge case.
2. A projected feed (`carrier.global` / Following / author, with `likeCounts` / `exists likes`) is observed offline or after a carrier-input refresh.
3. The twin is `partial` with only `computed-key` sites, at the held owner seq, with the same `selection.through`.

**Consequence:** `exactOwnerAnswer` is false because `localInputs.entries.some(entry => entry.predicted)` walks **every** outbox row, not overlays that intersect this page. `offlineView` then publishes the twin partial **without** the receipt-backed `next`. React `usePage` reports `hasMore: false` at 20 rows — the Astra M2 symptom this repair was meant to close. The 45-row witness never has a predicted entry on the happy path, so it does not catch this.

LLP 1012’s 2026-09-09 owner-page rule says active overlay custody must win over the fallback; it does not say an unrelated chat overlay may discard a still-valid feed continuation.

**Minimum remedy:** Treat overlay as blocking only when it affects this answer: predicted rows/refs for this page, or a removal overlay on those keys (including an empty/removal-only overlay awaiting retirement). Do not let a foreign predicted outbox entry drop `next`.

### 2. Non-admin author unsend cannot delete other members’ pending rows

**Where:** `snapback2/packages/compiler/fixtures/quarry-clique/corrections/grok-app.patch`

- `access.q` `deliver()` (patch lines 4–16) now deletes `pendingRead`, `periodUnread`, and `pendingDelivered` for every member when `kind` is `removed` or `expired`.
- `schema.q` `pendingRead` / `pendingDelivered` delete (patch lines 569–597) is only `.recipient = viewer` or `exists memberships[.conversationId, viewer, 'admin']`.
- `periodUnread` delete (patch lines 618–622) correctly also allows the current author: `exists memberships[.conversationId, viewer] and exists messages[.messageId, viewer]`.

**Failing scenario:** A non-admin member sends a message (so `snapshotRecipients` wrote other members’ `pendingRead` / `pendingDelivered` / `periodUnread`), then calls `unsend`. Clique `unsend` follows the usual `deliver(..., 'removed')` shape; this patch does not change that caller, only `deliver()`.

**Consequence:** The transaction tries to delete other recipients’ `pendingRead` / `pendingDelivered` under the tightened rule. The author is neither recipient nor admin, so those deletes are denied and **unsend is rejected**. Recipients keep pending/unread rows for a message the author is not allowed to retract. Owner expiry still works (system bypasses rules). The retained unsend journey uses Alice on `conversation-1`, which does not prove a group member who is not admin.

`periodUnread` has the author arm this cleanup needs; the two pending tables do not, even though the same `deliver()` loop deletes all three.

**Minimum remedy:** Give `pendingRead` and `pendingDelivered` the same author arm as `periodUnread` (current membership **and** `messages[.messageId, viewer]`), or stop deleting those rows from `deliver()` and clean them in an authorized helper.

## MINOR

- **`sendPoll` never enters `storeWithExpiryPolicy`.** Text/photo/clip/once-photo take the shared expiry helper; polls still insert without a disappearing deadline. A poll in a 24h/7d chat will not expire with other messages.
- **Twin shared-flight `requested` counter misses the fulfill-to-`finally` window.** A reader that calls `sync()` after the loop has returned but before `this.flight` is cleared joins an already-resolved promise and skips the extra delta pass LLP 1012 describes. - **Startup drain omits `preserveOwner = !drain`.** `queryInternal`’s incomplete-startup `answerOffline(...)` call does not pass `drain`, so a drain during that window can keep an ordinary owner page. The forced-offline and hydrating-token paths do pass it.
