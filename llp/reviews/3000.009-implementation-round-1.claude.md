## Lane A1 — work records (authority, ids, `why <id>`, `serve --worker`)

**Verdict: no blocking finding.** The reviewer tried each security claim and
could not break it: every `identity::action_session` mint is gated by the
authority check; the legacy unbound collector is gone; revocation bumps a
generation and deletes sessions in one transaction; migration is additive
only (`ALTER TABLE ... ADD COLUMN`, NULL read as "no binding"); the worker's
environment is `env_clear()` plus a seven-name allowlist.

| Finding | Severity | Disposition |
| --- | --- | --- |
| `_ops` persisted full raw arguments and full results forever, re-storing what `engine/receipt.rs` strips so a resend never returns historical values, in a table with no read rules | Major | Fixed in round 1: `_ops` keeps `principal`, `id`, `seq`, `outcome`, `name`, `args_digest`, `at`. `why --values` reports a mutation's arguments and result as "not recorded" |
| `doctor`'s storage accounting under-counted the new `_ops` columns | Major | Fixed: the sum covers every remaining field |
| The action digest was asymmetric — admission hashed decoded, validated arguments while replay hashed raw JSON, reconciled by a stored `arg_defaults` list | Major | Fixed: admission hashes raw wire arguments, as mutations already did; `arg_defaults` removed |
| A 365-day `service:worker` session was minted per child restart, leaking a year-long credential per SIGKILL under `serve` | Major | Fixed: child credentials last at most a day, with transactional ownership markers for startup cleanup. Limitation recorded: pre-fix unmarked credentials cannot be distinguished from manually issued tokens |
| The Postgres executor replays through the unbound `replay()` | Major, out of lane scope | Ticketed: `issues/20260915-snapback4-postgres-replay-skips-the-id-binding.md` |
| Lease floor silently lowered from 1,000 ms to 1 ms; dead refusal branch; unguarded `sqlite`-feature test; a dropped `/q/alive` assertion; `dev --worker` silently ignored | Minor | All fixed in round 1 |

The lane also fixed a pre-existing fixture shutdown race (awaiting child exit
before store deletion and port reuse). All three cases named in
`issues/20260915-snapback4-navigation-model-fixture-server-econnrefused-under-load.md`
then passed in every client run, with no `ECONNREFUSED`. The ticket carries
the cause and fix and stays open pending a quiet-host confirmation.

## Lane C1 — the Postgres access boundary

**Verdict: two blocking findings, both fixed in round 1.** The reviewer
confirmed the prefetch core itself: the cache holds only exact `get`/`lookup`
answers including misses, its fill SQL is byte-identical in range, join order
and `LIMIT` to the ordinary path, key evaluation is a separate total function
that cannot charge or raise, and the commit tail preserves ordering,
atomicity and error behaviour.

| Finding | Severity | Disposition |
| --- | --- | --- |
| The guide claimed every host enforced the new key bound, but the browser device (`snapback4-device/src/memory.rs`) did not, so it would predict success where the server refuses — a false claim in tested text and a real divergence between the two device hosts | Blocking | Fixed: all four stores share one key computation and validation; browser/server parity test added |
| The write-time bound was an ungated admission change against existing stores, with no evolution path: the next update to a row already holding an over-long key would fail | Blocking | Fixed: adoption scans existing indexes and names table, index and count; fresh stores skip it; legacy oversized keys may remain, shrink or be deleted |
| The byte budget was checked after the rows were fetched and decoded, so an oversized fill still transferred | Major | Fixed: the SQL checks payload size before transfer; tests assert zero rows and bytes transferred |
| Cache invalidation on savepoint rollback rested on a `sql.contains("ROLLBACK TO")` substring match | Major | Fixed: an explicit rollback method clears the cache and `batch` rejects rollback SQL |
| The call-count guard was disabled on exactly the cases that would catch a regression, and nothing bounded the excess | Major | Fixed: every differential case asserts a bounded excess; largest observed excess 4 calls (15 against 11) |
| A 3.4× SQLite write regression had a cause in the diff: index keys recomputed for every index on every `put`, tokenizing text twice | Major | Fixed: writes reuse the keys `put` already computes. **The re-measurement is still owed on a quiet host** |
| The marking walk missed `Stmt::Check`, `Stmt::WriteTarget` and `WriteCondition.setup` | Major | Fixed: the walk covers them |
| Diagnostic routing, conditional declaration checking, saturating subtraction, an undocumented amortization constant, internal ordering surfaced as user-visible refusals | Minor | All fixed |

Measured: Postgres accepts a 2,672-byte encoded key and refuses 2,673; the
portable bound is 2,048 bytes plus a 512-byte table/index name limit, with
`E_INDEX_KEY_BYTES` explaining it. The inbox falls from 68 database calls to
8. All 22,082 forced-cut positions matched between prefetch on and off.
