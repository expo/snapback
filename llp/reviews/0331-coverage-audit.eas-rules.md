## 1. Inventory

### 1.1 Evaluator semantics (the thing the proposal's rule list is compared to)

`@expo/entity`'s policy is four ordered lists (`createRules` / `readRules` / `updateRules` / `deleteRules`), each rule returning `ALLOW` / `DENY` / `SKIP`. *(upstream main, `EntityPrivacyPolicy.ts`)*: "foreach rule in rules: return authorized if rule allows, return not authorized if rule denies, continue to next rule if rule skips, return not authorized if all rules skip" — all-SKIP throws `EntityNotAuthorizedError` with rule index `-1`. Default-deny, first-ALLOW-wins, DENY short-circuits. The same shape is restated for feature gates at `src/utils/gating/FeatureGate.ts:46-50`.

Lowering to the proposal: a list `[A1, D1, A2, A3]` is `A1 || (!D1 && (A2 || A3))` — ordinary boolean composition. Two evaluation *modes* exist that the proposal has no analogue for: `LoggingDryRunEntityPrivacyPolicy` (`rules/LoggingDryRunEntityPrivacyPolicy.ts:31` `mode: EntityPrivacyPolicyEvaluationMode.DRY_RUN` — log the deny, allow anyway, except in test or in `getEnforcingTiers()`) and `LoggingEnforcedPrivacyPolicy` (`:25` `ENFORCE_AND_LOG`), plus a rule-level wrapper `dryRunLogIfRuleDenies` (`rules/dryRunLogIfRuleDenies.ts:31-48`). These are migration tooling (1 and 2 policies use them), not authorization semantics.

Update rules see the old row: `EvaluateIfEntityFieldPredicate…`/rules receive `evaluationContext.previousValue` (`projects/AppDevDomainNamePrivacyPolicy.ts:43` `const previousAppId = evaluationContext.previousValue?.getField('appId');`) — the proposal's `update(old, next)`.

### 1.2 What `viewer` is in EAS

`ExpoViewerContext` (`viewercontext/ExpoViewerContext.ts:55-100`) is a class hierarchy, not an opaque scalar. Discriminators used by rules: `isAnonymousViewerContext`, `isMaybeScopedAccountActorViewerContext`, `isScopedAccountActorViewerContext`, `isAccountActorViewerContext`, `isPartnerProvisionedActorViewerContext`, `isRobotViewerContext`, `isUserViewerContext`, `isRegularUserViewerContext`, `isSSOUserViewerContext`, `isOmniscientViewerContext`, `isOmnipotentViewerContext`. On top of the actor id it carries:

- session flags: `isSudoModeSession` (`middleware/viewerContext.ts:229` `sudoExpiresAt != null && sudoExpiresAt >= new Date()`), `isStaffModeSession` (`:231-232` `staffModeExpiresAt >= new Date()`), `getInternalSessionInfo()` with `InternalSessionMode.READ | WRITE` (`user/InternalSessionMode.ts:1-4`);
- a **scoped** wrapper: `ScopedAccountActorViewerContext` holds an `underlyingViewerContext` (`viewercontext/ScopedAccountActorViewerContext.ts:20`) and is minted from a short-lived JWT (`middleware/viewerContext.ts:392-408`, `ScopedViewerContextJwtToken.createAsync(actor, { expiresInSeconds… })` issued at `turtle-job-run/TurtleJobRunUtils.ts:355,365` and `apiv2/EchoRouter.ts:43`). Scoped viewers may only ever satisfy `ScopedUserPermission = VIEW | PUBLISH` (`src/constants.ts:22-25` "We never want to even consider granting more permissions than this");
- the Koa request (`viewerContext.koaContext`) — read by gating rules, not by privacy rules;
- two synthetic contexts: **Omniscient** (read-everything) and **Omnipotent** (write-everything), nestable over an underlying viewer (`rules/AllowIfOmnipotentPrivacyPolicyRule.ts:33` `getInnermostUnderlyingViewerContextForOmni`).

Actor kinds are rows in one `users` table with an `ActorType` (`PERSON`, `SSO_USER`, `ROBOT`, partner-provisioned), so every `isXViewerContext()` guard is, in data terms, a predicate on the viewer's own actor row.

### 1.5 Mutability of the parent scope — can an app move between accounts?

**Yes; `apps.account_id` is mutable, by a product feature.**

- `projects/AppEntity.ts:215-226` `accountId: new UUIDField({ columnName: 'account_id', association: { associatedEntityClass: AccountEntity, … } })` — an ordinary updatable field.
- `projects/AppUtils.ts:126-129` `return await AppEntity.updater(app, queryContext).setField('fullName', newFullName).setField('accountId', destinationAccount.getID()).updateAsync();`
- Authorization of the transfer, `AppUtils.ts:144-172`: OWN on the source account **and** ADMIN on the destination (`:150-168`), with the comment `:145-149` "asymmetric permissions means that an actor won't be able to undo a transfer in all cases … a single user cannot be an owner on multiple personal accounts". The GraphQL mutation `transferApp(appId, destinationAccountId)` (`graphql/mutations/UserMutation.ts:155`) is gated by a sudo session (`:759` `transferApp: ensureSudoSession(transferAppAsync)`).
- Transfer side-effects are triggers on the `accountId` change (`projects/triggers/*UponTransferTrigger.ts`, each `:31-32` `if (currentAccountId !== mutationInfo.previousValue.getField('accountId'))`): delete app pins, **duplicate credentials into the destination account** (`DuplicateCredentialsUponTransferTrigger.ts:65-66`), remove the GitHub repository link, remove the LogRocket project, update the dev-domain tier, write an `AppTransferRecordEntity` (`projects/AppTransferRecordEntity.ts:12-18` `{accountId, appId, createdAt, endedAt}` — a history of which account held the app when).
- A second path: account rename re-issues every app's `fullName` through the same `checkAndTransferAppAsync` (`user/AccountEntities.ts:1068-1072`), account unchanged.

**Is `accountId` copied onto children?** No. Of the app-scoped entities, none carries the account: `TurtleBuildEntity` (`turtlebuild/TurtleBuildEntity.ts:684` `appId: new UUIDField`, no account column), `BranchEntity` (`updates/BranchEntity.ts:105`), `ChannelEntity` (`updates/ChannelEntity.ts:93`), `UpdateEntity` (`:155`), `SubmissionEntity` (`submissions/SubmissionEntity.ts:372`), `WebhookEntity` (`webhook/WebhookEntity.ts:73`), `WorkflowEntity` (`workflow/WorkflowEntity.ts:80`, with `getOwningAccountIdAsync` at `:146` computed through the app) — all reach the account only through `appId`. The two entities that carry both columns are not denormalizations: `EnvironmentVariableEntity` uses `accountId` *or* `appId` as alternative scopes (`environment-variable/EnvironmentVariableEntity.ts:100-107` `accountId?: never` when `appId` is set), and `AccountBuildLedgerItemEntity` is a billing ledger recording the account charged at the time (`account-build-ledger-item/…:37-38`).

So the dominant EAS rule shape — `row.appId → apps.accountId → user_permissions` — is a genuine two-hop through a **mutable** intermediate. Ruling 4's rewrite ("denormalize the immutable scope id … emit the cross-column constraint so the copy cannot drift") presupposes an immutable scope; here the copy would have to be rewritten on every child row on transfer (builds per app are unbounded; a large app has thousands), and the cross-column constraint would be violated mid-rewrite unless the rewrite is one transaction. This is the case ruling 4 explicitly does not cover. See requirement rows R3–R5.

### 1.6 The permission model

**Vocabulary — closed.** `src/constants.ts:14-19` `export enum UserPermission { OWN = 'OWN', ADMIN = 'ADMIN', PUBLISH = 'PUBLISH', VIEW = 'VIEW' }`. The `permissions` table (`permissions/PermissionEnumEntity.ts:36` `tableName: 'permissions'`, `:15-18` `{ id: number; name: UserPermission }`) is a lookup so `user_permissions.permission_id` can be an integer FK; its policy is `AlwaysDeny` for create/update/delete and `AlwaysAllow` for read (`permissions/PermissionEnumPrivacyPolicy.ts:17-48`). Loaded by name (`PermissionEnumEntity.ts:55-65` `fromUserPermissionAsync`). **Not X16**: nothing can add a permission at runtime; the TS enum is the authority.

**Grants — independent bits as independent rows.** `permissions/UserPermissionEntity.ts:43-48` `{ id, permission_id, grantee_id, grantor_id }`, table `user_permissions` (`:81`). `grantor_id` is the **account** (scope), not the granting actor (`:105-108` `association: { associatedEntityClass: AccountEntity …}`; `getOwningAccountIdAsync` returns `grantor_id` `:145-149`). `grantee_id` is any actor (user, SSO user, robot, partner actor). Four rows per full owner. No unique index on `(grantee, grantor, permission)`: `:271-273` "Used for deduplicating UserPermissionEntity since the table can contain duplicates"; the migrations create only `(grantor_id, experience_name)` and `(grantee_id)` and `(grantor_id)` indexes (`postgres-migrations/general/0017-project-permissions.ts:51-54`, `0130-account-deletion-indexes.ts:43-44`). The proposal's unique `(scope, principal)` index would require a dedupe at migration and — since EAS is one-row-per-bit — a unique `(scope, principal, role)` rather than `(scope, principal)`.

**Who has what — the probe.** `permissions/UserPermissionsUtils.ts:346-372` `doesViewerHavePermissionOnAccountAsync`: (a) `:355-361` if the actor is a user/SSO user/partner actor **and** `actor.getPrimaryAccountId() === accountId` → `true` (implicit owner of the personal account: every permission, no row); (b) otherwise load all rows for the grantee (`:256-259` `loadManyByFieldEqualingAsync('grantee_id', actorId)`), filter by permission, test `grantor_id === accountId`. Note the primary-account fact lives on the **user** row (`users.primary_account_id`), not on the account. Related helpers: `getAccountIDsWhereActorHasUserPermissionAsync` (`user/UserEntities.ts:477-480` `new Set([userActor.getPrimaryAccountId(), ...grantedPermissions.map(p => p.getGrantorId())])`); `doesActorHaveAnyOfProvidedPermissionsOnAccountAsync` (`:404-436`, an any-of over a permission set).

**Roles — derived, exact sets, not a lattice.** `graphql/utils/permissions.ts:105-128`: `Role { OWNER, ADMIN, DEVELOPER, VIEW_ONLY, CUSTOM }`; `getRole(perms)` = OWNER iff all four; ADMIN iff `!OWN && ADMIN && PUBLISH && VIEW`; DEVELOPER iff `!OWN && !ADMIN && PUBLISH && VIEW`; VIEW_ONLY iff only VIEW; else CUSTOM. `:130-132` "a role is the exact permission set a member holds, so consumers matching on it must assert absence too". `getExactPermissionsForRole` throws for CUSTOM (`:148-151`). No privacy rule anywhere tests a role or compares roles; every rule names one bit (`UserPermission.VIEW` etc.). Roles are presentation and invitation defaults.

**Grant authority.** `permissions/rules/AllowIfActorCanGrantOrRevokePermissionOnAccountRule.ts:52-53` `const requiredGrantorPermission = permission === UserPermission.OWN ? UserPermission.OWN : UserPermission.ADMIN;` then `:55-60` `doesViewerHavePermissionOnAccountAsync(… requiredGrantorPermission, accountId)`. So: to grant or revoke OWN you need OWN; anything else needs ADMIN. That is not "grant ≤ own": an ADMIN may grant ADMIN (equal), and an OWN holder may grant anything. Two explicit cases. Used in `UserPermissionPrivacyPolicy.ts:16-51` for create/update/delete, plus `:47-50` "allow a user to delete their own permissions (so they can leave an account or delete their user)" (`AllowIfUserOwner('grantee_id')`). Reads of grants are `AlwaysAllow` (`:24-31`) — the roster is public to any viewer that can reach the row.

**Invariants — validators and triggers, not rules.** `UserPermissionEntity.ts:119-141`: `beforeCreateAndUpdate` — no OWN for a robot (`validators/UserPermissionNoOwnPermissionForRobotValidator.ts:29-32`), no OWN on a personal account (`…NoOwnPermissionOnPrimaryAccountValidator.ts:29-35`), no explicit grant to the implicit owner (`…NoPermissionForImplicitOwnerOnPrimaryAccountValidator.ts:35-36`), membership count ≤ the grantee's `getAccountLimit()` (`…AccountMembershipLimitationValidator.ts:31-39`), 2FA required if `account.require_two_factor` and grantee is a PERSON without OTP (`…TwoFactorRequirementValidator.ts:40-57`), SSO users only on their SSO account (`…SSOUserCanOnlyHavePermissionOnTheirSSOAccountValidator.ts:29-31`); `beforeDelete` — **last-owner protection** (`triggers/UserPermissionNoRemoveLastOwnerTrigger.ts:66-68` `if (ownPermissionsGrantedByGrantorAccount.length === 1) throw`), last *human* owner (`…NoRemoveLastHumanOwnerTrigger.ts:89-96` filters grantees to `ActorType.PERSON`), last SSO permission (`…NoRemoveLastSSOUserPermission.ts:53-64`); the "leave account" path also refuses the sole owner (`UserPermissionsUtils.ts:142-147`). Cascade deletes skip the last-owner check (`NoRemoveLastOwnerTrigger.ts:40-41`).

**Grantor tracking.** No "granted by" column on `user_permissions`; the audit log records the actor (`UserPermissionEntity` extends `AccountAndUserAuditedEntity`, `:61`, metadata `:50-55`). The feature-gate override rows do carry `granted_by_actor_id` (`account-feature-gate-override/AccountFeatureGateOverrideEntity.ts:28`).

## 3. Facet verdict

The proposal carries EAS's *vocabulary*: the permission bits are a closed four-value enum stored one-row-per-bit (R23–R25), grant authority is two explicit cases rather than a lattice, last-owner protection is a count constraint, and every viewer-kind guard lowers to a `where` on the principal's own actor row — none of the REFUSED items (lattice, kind term, permissions-as-data) is load-bearing. What it does **not** carry as ruled is the shape that 68% of EAS's membership rule uses take: a probe through `apps.accountId`, which is **mutable by a shipped mutation** (`transferApp`, OWN-on-source + ADMIN-on-destination, sudo-gated), with no child table carrying the account. Ruling 4's "denormalize the immutable scope id" therefore does not apply; the honest lowerings are Tier 2's `inherits(apps, 'accountId')` (X2) or `any` (X1), or a Tier 1 system continuation that rewrites the denormalized column across an unbounded child set on transfer with the fan-out reported by `check`. The single change that flips the most rows (R3, R4, R18, R19, R21: ~280 uses) is admitting **one-column `inherits` over a mutable parent** — an engine-maintained scope copy rewritten in the parent's commit — which the admission rule already classifies as an engine-maintained relation. Second-ranked are two session-flag items the paper corpus marked OUT (staff mode, 122 uses; the scoped-token cap, 150 uses); both have a minted-principal interim (ruling 2's shape) with a stated product loss. Genuinely **NEW** relative to the 37 paper apps: (a) the *mutable-scope transfer* itself — no paper app moved a resource between tenants with a decade of children under it; (b) the *attenuated principal* (a session that is the same actor but capped at VIEW/PUBLISH, R12); (c) *cascade-delete provenance as a rule input* (R22) — the Tier 0 text names creation provenance only. Everything else is a named tier or a named refusal.

## 5. Answers to the five key questions

1. **Hop fractions.** Of ~1,184 rule instantiations, 435 probe membership: **32% one hop, 46% two hops, 16% three, 6% four**. Of the 294 path-rule uses: 22 / 176 / 69 / 27 by step count; 87% pass through `AppEntity`. The rest of the corpus is system disjuncts (33%), staff/session (11%), zero-hop compares (11%), cascade provenance (6%).
2. **Is `accountId` immutable on apps?** No. `AppUtils.checkAndTransferAppAsync` (`projects/AppUtils.ts:126-129`) updates it; `transferAppToAccountAsync` (`:150-172`) requires OWN on the source and ADMIN on the destination; the mutation is sudo-gated (`UserMutation.ts:759`). A transfer touches: `apps.account_id` and `full_name`; the `AppFullName` row; an `AppTransferRecord` row; app pins deleted; credentials **duplicated** into the destination account; GitHub repository and LogRocket project links removed; dev-domain tier updated. No child row carries `accountId`, so no child row is touched — which is exactly why a denormalized copy would turn transfer into an unbounded fan-out.
3. **Closed or open?** Closed: `UserPermission` is a four-value TS enum; the `permissions` table is a deny-all-writes integer lookup. Core, not X16.
4. **Lattice needed?** No. Rules test single bits; roles are a derived presentation function (`getRole`, CUSTOM = any other set, `getExactPermissionsForRole` refuses CUSTOM); grant authority is two explicit cases (OWN needs OWN, else ADMIN) — an ADMIN can grant ADMIN, so "≤ own" is not even the rule. Explicit sets suffice. Last-owner and last-human-owner are count constraints (the human variant needs an immutable `granteeKind` denorm on the grant row).
5. **Feature gates.** Not in table rules at all (0 policies). Their inputs are literals (tiers, id allowlists), one-hop override rows (`CORE(where)`), the actor's own row (SSO kind, expo-admin), and a plan type + standing **computed from a Stripe JSON blob** on the customer row — expressible as a one-hop `where` only after a system-maintained `planType`/`inGoodStanding` column exists (Tier 1 ingress). Gate composition is boolean (`AllowIfOtherFeatureGateAllows`, ordered ALLOW/DENY/SKIP) — nothing the grammar refuses. Rollout inputs (route regex, hashed buckets, process flags) are not authorization and stay in programs.
