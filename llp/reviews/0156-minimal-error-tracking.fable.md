**Hunk 1 — resolve-transaction `enqueue_high_water` advance + defensive boot seed: SOUND.**
The v0.4 hole was real: the live admission counter runs ahead of the flush-persisted high-water, so a barrier captured from the live counter and persisted only in `resolved_seq` could exceed the durable high-water; a crash before the next flush would re-seed below the barrier and re-issue sequences at or below it, letting genuinely-post-resolve failures land under the barrier and not regress. The v0.5 mechanism (llp/0156-minimal-error-tracking.rfc.md:865-882) closes it: the resolve transaction persists `enqueue_high_water` to the captured barrier value, so after any crash the boot seed is ≥ every barrier, and "no post-boot sequence can fall at or below any barrier captured before the restart" holds. Pre-crash admitted-but-unflushed records with sequences above the barrier are lost with the buffer (0154 D3 is in-memory, llp/0154-minimal-observability.rfc.md:639-663), so re-issuing those sequences post-boot is safe — they never persisted. The defensive boot seed `max(enqueue_high_water, max(resolved_seq))` (llp/0156:871-873) additionally covers the flush-writes-a-stale-smaller-high-water-after-resolve interleaving on the shared connection, so the design is belt-and-suspenders coherent. The bulk form correctly reuses one barrier capture with its high-water advance (llp/0156:906-907), and the pattern claim about 0154's observation clock is repo-true (persisted clock in `telemetry_meta`, high-water advanced at flush and boot — llp/0154:549-553). **1. Verdict: NOT READY**

Two MAJOR findings (a factual over-claim at the heart of motivation 4 / deliverable 1, and missing fingerprint-versioning semantics) plus a cluster of MATERIAL spec gaps. The direction itself is endorsed — this is revise-and-re-review territory, not redesign.

**2. Directional assessment**

**Q1 — Is this the right thing to build? Yes, in exactly this consumer-not-pipeline shape.** The landscape's "everyone delegates to Sentry" fact cuts differently for Snapback than for Convex/Cloudflare/Fly, for three reasons the RFC correctly identifies and one it underweights:

- *Zero-infrastructure local-first is the product.* "Go create a Sentry account" is a defensible answer for a platform whose users already operate cloud services; it breaks the story for a platform whose pitch is that a toy app gets a working backend with nothing else. GCP Error Reporting is the right existence proof that a deliberately small built-in loop is a complete product.
- *Snapback owns the runtime.* The delegating platforms delegate partly because they don't own capture — they'd need an SDK either way. In-process capture at seams that already exist (CE1) removes most of the cost that makes error tracking a big product.
- *Agents are the consumer.* The landscape's own finding — agents-as-consumers barely exist in this market — means Sentry delegation forfeits the one axis where Snapback is ahead. An agent debugging a deployed app needs `errors.issues` as a typed operation, not a Sentry account and an MCP bridge.
- *Underweighted:* the typed-Diagnostic head start (motivation 5) is genuinely the strongest argument and deserves top billing. Sentry's entire grouping-heuristics apparatus exists because arbitrary exceptions are all it has. Snapback's failure paths terminating in stable `code`s (verified: `Diagnostic { code, severity, subsystem, message, details }`, src/diagnostic.rs:22–29) means E1's grouping is mostly *bookkeeping*, not heuristics. That asymmetry is why building this in is cheap here and expensive everywhere else.

The scope line — consumer of rows 0154 already persists, nothing needing new observation machinery — is the right hedge, and the preserved Sentry escape valve (D9 forwarder) makes this a both/and, not either/or.

**Q2 — Stronger direction?** I considered the capsule's alternatives seriously and endorse the current shape against them:

- *Sentry-envelope ingestion everywhere:* the RFC's rejection for the server side is correct — Snapback needs no SDK, so ingest compatibility buys nothing there. For E3 the leaning to envelope-compat is right (see OQ-G below). One inversion worth adding: Sentry-envelope **egress** — see design proposal P1.
- *Fold into 0154:* no. 0154 is seven rounds converged on "fixed dashboards over pre-aggregated rollups"; issues/triage/alerting is authored-state machinery with a different write pattern (upserts, a mutating operation). The CE1 seam is clean and independently testable. Reopening a converging document to add a diverging concern is the wrong trade.
- *Agent-native, no human triage UI:* the RFC is already 90% there — three typed operations first, one fixed console page as a projection. The triage state machine is not "human UI"; it is what agents need too (resolve-then-detect-regression is the fix-verification loop, motivation 2). Deleting the one console page would save little and cost the operator story. Keep as is.
- *Issues as app-queryable data:* attractive for self-healing apps, but it would cross the C1/C5 boundary (telemetry surfacing into app-authority surfaces) and create the first app-facing read of operator-tier data. Rightly out of scope; the control-MCP projection already covers the agent case.

**Q3 — Phasing:** E1/E2/E3 is the right order and roughly the right cut. E1 is the substance; E2 genuinely depends on E1's groups; E3 blocks on nothing and may never ship (the Convex-posture fallback for client crashes specifically is honest and correct). Two cut critiques: (a) the E2 spike rule is specified normatively but has no data substrate in the E1 schema (finding 6) — either provision the substrate in E1's schema or soften rule 3 to a leaning; (b) stack capture is presented as E1's near-free enrichment, but the claim is only true for one of the two uncaught-exception paths (finding 1) — the cut is still right, the cost accounting is not.

**3. Findings**

**F1 — MAJOR — Stack capture claim is over-scoped: the common uncaught-exception path has no stack anywhere, and capturing one there is not "decode what is already returned."** (Summary bullet E1; Motivation 4; Deliverables 1.) The claim about `render_async_failure` verifies exactly: src/runtime.rs:2982–2995 fills a `stack: HermesOwnedBytes` out-param from `ex_hermes_value_safe_throw_metadata` (FFI decl src/runtime.rs:672–678) and frees it undecoded at src/runtime.rs:3010–3013. But that function serves only the **Ibex asynchronous-failure queue** (unhandled rejections detached from the invocation; caller `render_and_release_async_failure`, src/runtime.rs:2949). The overwhelming majority of uncaught handler exceptions terminate through the **settle path**: `snapbackSettle` (packages/snapback-harness/ctx-bootstrap.js:1195–1239) awaits the handler, catches everything at :1207, and serializes an envelope carrying only `code` and `message` (:1236–1238) — the host never sees the thrown value's handle, so no FFI stack extraction is possible there. As written, E1 would ship "stack capture for uncaught exceptions" that captures stacks only for the rare async-orphan class, while ordinary `throw new Error(...)` in a handler gets none. *Resolve:* either (a) scope the Summary/Motivation-4/E1.1 claims honestly to the async-failure seam and add a named deliverable for settle-envelope stack capture — a JS-harness change with real trust design (the envelope code deliberately avoids reading handler-controlled properties naively; `error.stack` can be a poisoned getter, so it needs the `__snapbackSafeString`-class treatment and the 16 KiB cap, and the stack string is C5 raw-tier by CE3); or (b) defer settle-path stacks explicitly and state that E1 v1 stacks exist only for async failures. Option (a) is worth it — without it, the "single highest-value error-tracking artifact" is absent from the highest-volume path.

**F2 — MAJOR — No fingerprint-scheme versioning; a normalizer or tuple change silently splits every existing issue.** (E1.1, E1.2 schema, OQ-A1.) The issue id is derived from the fingerprint hash (E1.1 "Issue identity"), and OQ-A1 already anticipates tuning the normalizer against a real corpus — i.e., the scheme *will* change. When it does, every re-fingerprinted failure mints a new `iss_` id: all open issues orphan, triage state strands on the old rows, regression detection breaks across the upgrade (a resolved issue's recurrence lands in a fresh `open` group, never flipping `regressed`). Sentry pins grouping-config versions per project for exactly this reason (the RFC's own landscape section cites its grouping docs). *Resolve:* add a `fingerprint_version` (or reuse the 0154 registry version) to the fingerprint tuple's identity, stamp it in `error_groups`, and state the upgrade policy — simplest honest v1: scheme changes start new groups and old ones age out via the last-seen horizon, documented; better: carry-forward migration is named future work.

**F3 — MATERIAL — CE2's "subject-free, so C5-clean" justification does not cover exemplar snapshots.** (CE2, E1.2.) The D7-rollups precedent 0154 uses for aggregates-outlive-raw-retention rests on aggregates being classification-only (0154 D1/D7). `error_groups.exemplars` holds stack heads and message snapshots — raw-tier handler-controlled content by the RFC's own CE3 — and the last-seen horizon defaults to the daily-tier horizon (730 days per 0154 D7), so raw-class content that `max_days` would delete at ~7 days persists two years. Access control (AdminSecretRead) is handled; **retention class** is not. *Resolve:* scope CE2's C5-clean claim to counters/titles explicitly, and give exemplar snapshots their own stated retention (e.g., ring entries expire at a bounded exemplar horizon, or on group-state transitions), or explicitly accept long-lived raw snapshots as a documented C5 decision.

**F4 — MATERIAL — No fingerprint branch for failures with neither Diagnostic code nor exception.** (E1.1.) A failed `http_request` row that maps to no logical call (0154's `_unmatched` sentinel, 4xx/5xx transport failures) has `code = NULL` and no `error_class`/message. E1.1's three branches don't cover it. *Resolve:* define the branch — `fp = (kind, name, status_class)` is the obvious cut — or state explicitly which 0154 failure predicate classes are excluded from grouping.

**F5 — MATERIAL — The `errors.transition` write mechanism is unspecified and in tension with CE1.** (CE1, E1.3, E1.4.) CE1 says this layer's writes "ride the existing flush transaction," but a transition is a synchronous admin operation that must confirm to its caller and be immediately readable. Does it enqueue into the D3 buffer (then it can shed, and read-your-writes fails until flush) or write directly on the telemetry connection (then CE1's wording is wrong and the contention/ordering story with a concurrent flusher-driven `resolved → regressed` needs stating)? *Resolve:* specify — a direct serialized write on the telemetry connection, outside the flush transaction, with the optimistic `state_ms` check, plus an explicit ordering rule for the resolve-vs-regress race (flusher regression after an admin resolve must win, which the write-path transition at E1.3 already implies).

**F6 — MATERIAL — E2's spike rule has no data substrate.** (E2 rule 3.) "Trailing hour ≥ N× trailing-7-day hourly mean" per issue requires per-issue hourly history. `error_groups` holds one total count; D7 rollups are keyed by `(kind, name)`, not fingerprint. Nothing in the E1 schema can evaluate this rule. *Resolve:* either add a bounded per-issue hourly ring (C8-capped) to the E1 schema, restate rule 3 over the approximation `count / hours_since_first_seen` and say so, or demote rule 3 to an OQ-E leaning decided at E2.

**F7 — MATERIAL — Shed-lane interaction with issue fidelity is unaddressed.** (CE1, E1.1, E2.) 0154 D3 gives failure records *reserved capacity*, not a no-shed guarantee (C7 is explicit: telemetry may shed). Therefore group counts are lossy, and a new issue whose first occurrences shed alerts late or never. Every comparable product treats error events as must-keep; Snapback's substrate deliberately doesn't. This is a defensible consequence of CE1 — but it must be said. *Resolve:* one paragraph stating that issue counts inherit telemetry's loss model, drop counters surface in the errors variance envelope, and new-issue/regression semantics are "at first *persisted* occurrence."

**F8 — MATERIAL — Uncaught-exception titles on the `OperatorMetadata` surface can carry residual handler-authored free text.** (CE3, E1.1, E1.4.) The normalizer strips digit/hex/quoted spans, but the remaining words of a handler-authored message (including email-shaped or name-shaped tokens — the landscape itself notes Better Stack strips emails) flow into `title`, which `errors.issues` serves on the closed surface under ordinary admin authority. CE3's "never a raw message" is not the same as "safe." *Resolve:* either extend the normalizer with the landscape's token classes (emails, long alphanumerics) and state that templates of handler-authored text are best-effort-scrubbed, or title uncaught-exception groups from `(error_class, name)` only on the closed surface with the template behind the raw tier.

**F9 — MATERIAL — Exemplar-ring byte budget and write amplification unbounded per group.** (E1.2, CE4.) Ring depth 5 × 16 KiB snapshots × 1,000 groups ≈ 80 MB worst case against the C8 file cap, and an error storm (the exact scenario this layer exists for) rewrites a large exemplars JSON blob per group per flush. *Resolve:* a per-group exemplar byte budget (with the smaller of ring-depth/byte-budget winning), at most ring-depth pushes per group per flush batch, both counted when they truncate.

**F10 — MINOR — `state_ms` as the optimistic-concurrency token can collide.** (E1.4.) 0154's observation clock issues per-flush-batch stamps; two transitions (or a transition and a flusher regression) can share a millisecond. *Resolve:* a per-row monotone `state_seq` incremented on every transition is a cheaper and collision-free token.

**F11 — MINOR — The 0154 cross-reference deliverable understates what 0154 needs.** (Deliverables 6.) One sentence in 0154 should also reserve the `details` allowlist key the fingerprint hash rides in (E1.1 stamps it into the allowlisted `details`, which 0154 D2 governs via redactor/allowlist — that's a registry-visible change to 0154's surface, not just a "see also").

**4. Design proposals**

**P1 — Sentry-envelope egress in the E2/D9 forwarder.** The landscape's real lesson about Sentry compatibility may be inverted for the server side: instead of *ingesting* Sentry format (rightly rejected), make the D9-pattern webhook able to *emit* it. An operator who outgrows the built-in layer points the forwarder at a Sentry DSN and gets real Sentry with zero app changes — the Convex-posture escape valve becomes one config knob instead of an integration project. Benefit: converts the RFC's biggest strategic risk ("you built a worse Sentry") into a graduation path. Cost: maintaining an envelope serializer against someone else's versioned format; mitigable by keeping the native HMAC webhook primary and the Sentry shape a secondary encoder. Decide at E2, but name it now.

**P2 — Deploy-integrated resolve.** Motivation 2 calls fix-verification a state machine, but the RFC leaves "resolve at deploy time" as a manual CLI act. Add a cheap verb/flag — `snapback errors resolve --open-before <release>` or a deploy-hook option — that bulk-resolves open issues at release activation, stamping `resolved_release`. Combined with regression-reopen this yields AppSignal's first-in-deploy economics without new notification machinery. Benefit: the loop the RFC exists for becomes one step. Cost: a bulk transition path and its audit story; small.

**P3 — A canned "what's new or back since release X" query.** The agent's first question after deploying is exactly `errors.issues` filtered to `state IN (open, regressed) AND first_seen_release ≥ X OR regressed since X`. Make it a named filter preset in the operation (and the CLI's default view) rather than leaving each agent to compose it.
