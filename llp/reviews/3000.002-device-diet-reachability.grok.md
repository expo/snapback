# Blind review: Snapback 4 device diet S5 (`57bdc2cbcc` vs `614898e9a7`)

The three `cfg` splits are real, and for **binder-produced** backends they preserve query/prediction results, meters, and durable device state. Prefetch was already a no-op on every non-Postgres store; partition **accounting** is kept; only log construction is dropped on logless builds. Structural admission is the actual contract change: the web device (and any native build that turns on `web-device-check`) will run programs the binder never admitted.

That last point is disclosed, but it is still an observable host split of published `E_UNBOUND_SCAN` / `E_STRUCTURAL_FANOUT` behavior. The native “3,452 observations” are not a regression test of the three gates, `web-device-check` is a production-reachable Cargo feature, and several new tests would pass without the product change. Not a silent semantics break on `check`/`dev`/`deploy` backends.

### 1. Which builds see which arm

Three independent switches:

**A. Structural admission module** — compiled unless `wasm32` ∧ `web` ∧ ¬`sqlite`:

```21:22:snapback4/crates/snapback4-core/src/engine/mod.rs
#[cfg(not(all(target_arch = "wasm32", feature = "web", not(feature = "sqlite"))))]
pub mod admission;
```

Server `validate_inputs` is under the same `cfg` and always calls `admission::check` (`validate.rs` 117–120). Device paths go through `validate_device_inputs` (`local.rs` 10, 36, 75, 103), which **skips** the check when that web triple holds **or** `web-device-check` is on (`validate.rs` 123–127).

**B. Prefetch planner** — compiled only with `postgres` (`pages.rs` 20–31; `runner.rs` 366–367, 390–397). `postgres = ["sqlite", "dep:postgres"]` (`Cargo.toml` 20–21).

**C. Partition event construction** — `log_events` + `row_changed` are `cfg(feature = "sqlite")` (`partition.rs` 128–154). `write.rs` 529–535:

| `sqlite` | `web-device-check` | Path |
|---|---|---|
| off | anything | `account_row_change::<false>` (no events) |
| on | off | `row_changed` → `account_row_change::<true>` |
| on | on | events iff `!runner.device` |

`runner.device = true` only in `local.rs` 37, 81, 109.

| Build | Features / target | Admission | Prefetch code | Event construction |
|---|---|---|---|---|
| Server CLI (`-p snapback4`, defaults) | core `sqlite+native`; device `native`; not wasm32 | **on** (`validate_inputs`) | **off** (no `postgres`) | **on** (sqlite, no `web-device-check`) |
| CLI + optional Postgres | not wired on the CLI crate; only `experiments/postgres` sets `features = ["postgres"]` | on | on, and `prefetch_enabled` can be true | on |
| Expo native device | `build-xcframework.sh` 21: default `native`, `aarch64-apple-ios{,-sim}`, production | **on** | **off** | **on** |
| Process device | CLI → `snapback4-device` default `native` (`verbs.rs` uses `Device::open`) | **on** | **off** | **on** |
| Simulator | `snapback4-sim` → core defaults; `Engine` is `cfg(sqlite)` | **on** | **off** | **on** |
| Wasm web device | `build-wasm.sh` 10: `--no-default-features --features web --target wasm32-unknown-unknown` | **off** | **off** | **off** (no sqlite) |
| Test feature `web-device-check` | empty feature (`core/Cargo.toml` 24–25; device forwards at 22) | device local **off**; server `validate_inputs` **on** | off unless `postgres` also unified | device local **off**; server `row_changed` **on** |
| Native job guest / wasmi host | `snapback4-native` has **no** core dep; wasmi is a native `wasm-host` | N/A / host keeps native cfgs | N/A | N/A |

**Workspace unification:** resolver 3 unifies features per package. No current workspace member enables `web`, `web-device-check`, or `postgres` by default (`Cargo.toml` members = `crates/*`; experiment crate is outside). Ordinary `cargo test --workspace` and `cargo build -p snapback4` do not leak the web arms.

**`target_arch = "wasm32"`:** native-job guests are the app crate + `snapback4-native`, not core. Wasmi does not recompile core for wasm32. A hypothetical `wasm32` core **without** `web` still **keeps** admission (all three conjuncts required). A native `--features web` build **without** wasm32 also keeps admission.

**`web-device-check` is not impossible in a shipped binary.** It is a normal optional feature, not `cfg(test)`, with no `compile_error` for production. Official scripts do not pass it (`build-wasm.sh` 10, `build-xcframework.sh` 21, CLI has no features). But `cargo build --workspace --all-features` or `cargo rustc -p snapback4-device --features web-device-check --profile production` would compile a native device that skips local admission and log events. Unification from current default members will not; an extra `--features` / `--all-features` will.

**“Only the web artifact changes” is false for linked prefetch.** At baseline the planner was compiled into CLI/Expo/process/sim and then skipped because `prefetch_enabled()` is false. After this commit those binaries no longer contain it. That is dead-code removal, not a behavior change, but it is not web-only.

### 2. Prefetch

`Rows::prefetch_enabled` defaults to `false` (`rows.rs` 183–187). The only override is the Postgres adapter (`postgres/store.rs` 231). SQLite and memory use the trait default.

`pages::plan` still builds return/collector maps for every query (`pages.rs` 39–46). Prefetch is `Plan::default()` when `!prefetch_enabled`, and `fill` returns immediately if the site is absent (`prefetch.rs` 250–251). On non-`postgres` builds `fill` is not even called. Heap charging of the page vector is unchanged and still **after** the (now gated) fill (`runner.rs` 365–368).

Postgres still does `prefetch::plan(program).admit(schema)` then `fill` → `tx.prefetch`. Same plans/meters/results for sqlite and memory as a baseline run that already took the `prefetch_enabled == false` branch.

Side effect: `prefetch.rs`’s `#[cfg(test)]` cases (`prefetch.rs` 269–374) now compile only with `postgres`, so they left `cargo test --workspace`. They do not need a database.

### 3. Partition events

Device apply consumes **server** `StreamEvent`s (`device.rs` 529–530, 569, 597), not `Runner.events`. `local::predict` returns `result` / `written` / `read` only (`local.rs` 66–71, 94) and never reads `runner.events`. Successful predict commits store changes (`device.rs` 694–697); refusals roll back (699–701). Assets and maintains still run after the partition call (`write.rs` 536–538). `next_expiry` is a read-side field.

So dropping constructors cannot change written/read tables, refusal codes from rules/meter/coverage, heap/output **meters**, `next_expiry`, asset placement, maintain overlays, or outbox contents **for a given successful predict**. A public-table insert still first succeeds at step ceiling 11 (`device_diet.rs` 117–135).

Accounting vs baseline `row_changed`: interpreted images, `id` validation (`field("id")?.as_str()?` still runs when not logging, `partition.rs` 169–173), audience sets, maintain-vs-plain step charges (182–183), dependent membership scans with `Examined` (226–235), `replaced`/`renewed` decisions, and the trailing `Steps` 1 (252) all run before/without constructors. Constructors are infallible pushes (`partition.rs` 128–147). Charge order is still “optional puts/dels → step charge” and “scans → optional scope/join → one step”. Early `continue` on unchanged membership+expiry (210–212) is unchanged. **Metered** amounts and exits match; unmetered `Value` clones into `Event.data` do not.

### 4. Admission

**(a)** Binder and runtime share `admission::check_detail` (`bind/mod.rs` 97–113`; `admission.rs` 71–108`). Bind also refuses unknown tables/indexes before that (`program.rs` 212, 388). A successful compile (empty `diagnostics`) cannot contain a program this check refuses.

`check_detail` walks **every** scan, including dead branches (`ir.rs` 507–521; `admission.rs` 103–107). Quarry cannot spell the diet fixture (`if false { return missing[]… }`); the test **patches IR after compile** (`device_diet.rs` 13–16).

Adoption does **not** re-run the binder or admission. `WebDevice::new` deserializes `Backend` from `/schema` JSON (`web.rs` 27–37); `adopt_captured` installs `backend.programs` as-is (`device.rs` 365–402). Successor adoption replaces programs as a unit; it keeps row images, not old IR. Native query programs are empty-body (`bind/program.rs` 108) — admission is a no-op; the web build has no `wasm-host` anyway. Actions/jobs are refused on the device (`local.rs` 35, 74).

So: no `check`/`dev`/`deploy` backend differs web vs native. A hand-built, corrupted, or buggy-server `Backend` can.

**(b)** With the check gone, that backend can: return a dead-branch result instead of `E_UNBOUND_SCAN` (`device-diet.test.mjs` 16–24); run an `E_STRUCTURAL_FANOUT` mutation until `E_FANOUT`/`E_BOUND`/row caps; persist predicted rows, base images, and outbox through the ordinary IDB commit (`device.rs` 694–697). It cannot read past held rows, skip remaining rule/coverage/meter checks, or acquire a partition. Submitted mutations still hit server `validate_inputs` (`engine/mod.rs` 797–798) and cannot commit. Local failed-write / predicted-row residue is real; it is not server corruption and is not visible to another principal. A hostile server already chooses the backend.

**(c)** `E_STRUCTURAL_FANOUT` and `E_UNBOUND_SCAN` are in `guide::CODES` (`codes.rs` 109–110), `why`, bounds/programs cards, and README. They are `RuntimeError::Structural` with family `schema` (`error.rs` 182, 233–237). README (`packages/snapback4/README.md` 622–625) states the new boundary, including queries. The prediction card (`guide/prediction.rs` 12–16) only mentions predictions. `why E_UNBOUND_SCAN` still says a compiled/schema-skew program is refused, with no web exception (`codes.rs` 110; `bounds.rs` 43–47).

**(d)** LLP 3000 §7’s 2026-09-13 ruling killed a **second interpreter**, not sqlite-style cfg of server-only modules (jobs/actions/effects already). S3 needs a ruling because it would change search for **every** program. S5 does not, for binder-produced backends. It **does** split published runtime refusals on malformed backends, and LLP 3000.002’s S5 row claimed “None on the device’s contract,” which this commit falsifies. That belongs as a dated §7 diet decision (the lane’s own journal already describes the trade). It is not an unannounced Unicode-class fork, but it is not “the same implementation observed the same way on every host” either.

The native differential (`device_diet.rs` 78–115, `#[ignore]`): two manual `DIET_RECORD` runs, compared **outside** the test. The test only asserts `programs > 100 && success > 50` and writes a file. Control (`snapback4-core/postgres`) vs `web-device-check` **are** different compiles, but inputs are binder-admitted programs on **empty MemoryStore**. That cannot move admission (already passed), cannot execute prefetch (`prefetch_enabled() == false`), and cannot see discarded `Runner.events` (drain is store changes). Identical bytes are expected even if all three gates were no-ops. The 24 step-ceiling records witness **retained accounting**, not “events gone.” This is not a build compared with itself, and it is also not a test of gated vs ungated behavior.

## Findings

### 1. Medium — `web-device-check` is a production-reachable native skip

`snapback4/crates/snapback4-core/Cargo.toml` 24–25; `snapback4-device/Cargo.toml` 22; `validate.rs` 125–126; `write.rs` 533–535.

**Scenario:** `cargo rustc -p snapback4-device --features web-device-check --profile production` (or `--workspace --all-features`). Native Expo/process device then: (1) answers `7` for the dead unbound scan instead of `E_UNBOUND_SCAN`; (2) skips partition event construction on `runner.device` (harmless for predictions, but it is no longer “native matches baseline”). Official scripts do not pass the feature; unification of **default** members does not enable it.

**Smallest fix:** `compile_error!` when `feature = "web-device-check" && !debug_assertions`, or confine the skip to `cfg(test)` so production profiles cannot take the arm.

### 2. Medium — the “3,452 observations” are not a regression test of the gates

`snapback4/crates/snapback4-device/tests/device_diet.rs` 73–115.

**Scenario:** restore `admission::check` inside `validate_device_inputs` under `web-device-check`, or re-enable `log_events` on that path. Re-run the ignored test with `DIET_RECORD`; both files still match; `assert!(programs > 100 && success > 50)` still passes. Default `cargo test` never compares the two builds.

**Smallest fix:** in the **non-ignored** test (already almost this), keep the IR-patched query as the admission witness; drop the claim that the fixture census compares gated vs ungated, or actually `assert_eq` two in-process records that include the patched program.

### 3. Medium — `--check-absent` can pass while the three paths return

`snapback4/scripts/attribute-wasm.mjs` 114; `packages/snapback4/test/wasm-absent.test.mjs` 6–12; `scripts/test.sh` 138 vs `measure-wasm.sh` 14.

**Scenario:** `mod prefetch` is lifted to `engine::prefetch` (regex requires `pages::prefetch`), or `admission::check` is copied into `validate.rs`. `wasm-absent.test.mjs` still passes. `test.sh` still passes. `measure-wasm.sh` would catch only names that still match.

**Smallest fix:** match `::prefetch::` and `::admission::` without requiring `pages`; add a blocking test that runs `checkAbsent` on a committed or build-produced census (or run `--check-absent` from `build-wasm.sh` if twiggy is available, skip-loud if not). Do not treat the synthetic unit test as artifact proof.

### 4. Low — documentation does not fully state the new boundary

`snapback4/crates/snapback4-lang/src/guide/prediction.rs` 12–16; `guide/codes.rs` 110; `guide/bounds.rs` 43–47. README 622–625 is fine.

**Scenario:** web query with unreachable unbound scan returns data (`device-diet.test.mjs`); `guide prediction` talks only about predictions; `snapback4 why E_UNBOUND_SCAN` still implies every runtime emits it.

**Smallest fix:** one sentence on the prediction card covering **queries**; one clause on the E_UNBOUND_SCAN card that the web device trusts the compiler and may not emit the code.

### 5. Low — “server still admits” is not what `server.query` exercises

`device_diet.rs` 14–20 mutates `backend.programs` then queries the **unmodified** `Engine`.

**Scenario:** a later edit stops calling `admission::check` from `validate_inputs` but leaves `Engine` programs clean; `server.query` still returns 7; the `validate_inputs(...)` line is the real witness.

**Smallest fix:** install the mutated program on the engine, or drop the `server.query` assertion and keep the `validate_inputs` one.

## The two required answers

**Did the change introduce a new problem?** On every host, **binder-produced** programs keep the same results, meters, and durable state. New problems: (1) web (only) will locally query/predict/persist for an inadmissible `Backend` that native still refuses — disclosed, server still blocks commits; (2) `web-device-check` can copy that skip onto a native binary if someone passes the feature; (3) prefetch object code and its default-suite unit tests disappear from non-Postgres builds (behavior of sqlite/memory unchanged).

**Is there a regression test that would also pass without the change it claims to test?** **Yes.** `wasm-absent.test.mjs` (linter, not artifact). `partition_accounting_keeps_the_step_refusal_boundary` (characterizes the old ceiling 11). `structural_admission_stays_on_the_server_and_native_device` **without** `web-device-check` (expects `E_UNBOUND_SCAN`, the baseline). Ignored `fixture_outcomes_and_query_meters` (`programs > 100`). **`packages/snapback4/test/device-diet.test.mjs` would fail at baseline** (journal: red against saved `00-baseline.wasm`) and is in the client suite after `build-wasm.sh`.

Verdict: READY WITH CHANGES
