**Discovered `doctor --latency --reset` never sends the instance nonce, so the server guard on that route never engages in the discovered path.**

- Concrete failure path: `doctor --latency --reset` validates host A via `GET /dev/status`; A restarts as B (same project, same store, new instance) before the reset POST; the POST carries no nonce so it is accepted, and the `store_id` query check in [latency.rs:302-303](/home/ccheever/projects/sb4-w13-surf3/snapback4/crates/snapback4/src/latency.rs) passes because the store is unchanged — B's latency window is reset on the basis of A's validation. This directly violates the commissioned rule that discovered controls be rejected before mutation if the live instance changed. Clock (`dev_clock.rs:108`) and reset (`dev_reset.rs:27`) both send the nonce; latency-reset is the odd one out, and no test covers it (contrast `stale_instance_control_is_refused_before_clock_or_reset_changes` in `tests/clock.rs`, which covers only the other two routes).
