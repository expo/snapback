# LLP 3000.007 blind review — write authority and the non-predicting page pass (gpt)

**Overall assessment**

The proposals do not preserve the stated “existence, and nothing more” boundary. Withholding returned rows closes direct content delivery, but success versus refusal can still disclose hidden values, secondary collisions, aggregate contributions, and hidden population thresholds.

Baseline: `4e8e3efefeac6e313d40e5556c45d378b4fdb807`. Every file-and-line citation below refers to that commit; the inspected working files match it. This was an independent, blind, read-only inspection. I read only the historical reviews explicitly designated by the brief. No tests were run or files changed; proposed counterexamples below are source-traced, not executed.

One material correction to the premise: **the baseline does not universally require read permission for updates or upserts.** Direct-ID writes already fetch the old row without a read check and evaluate the update rule. Quarry’s alternate-key update instead performs a read-filtered lookup and returns `NOT_FOUND` for a hidden target; alternate-key upsert treats that lookup’s `null` as absence and encounters S05 on insertion. The change therefore needs to address target resolution and document these distinct starting points. [engine/read.rs:177](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/read.rs:177), [engine/write.rs:66](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:66), [bind/program.rs:603](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-lang/src/bind/program.rs:603).

**Strengths**

- The separation of device execution, authorization, and resource bounds is useful. In particular, retaining complete-group prediction while considering a smaller server-side operation is a reasonable direction. Keeping all writes inside the engine preserves rules, constraints, maintains, transactions, and at-most-once execution. [LLP 3000.007:194](/Users/ccheever/projects/snapback-3000007-review/repo/llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:194), [LLP 3000.007:296](/Users/ccheever/projects/snapback-3000007-review/repo/llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:296).
- The proposal expressly keeps `old` private and withholds hidden result/current rows. Existing valued updates and upserts already re-read through `Expr::Get`; conflict recovery also uses the read-filtered `get`. Those boundaries should remain intact. [LLP 3000.007:898](/Users/ccheever/projects/snapback-3000007-review/repo/llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:898), [bind/program.rs:630](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-lang/src/bind/program.rs:630), [engine/mod.rs:786](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/mod.rs:786).
- The cursor correction is sound in direction: positioning after a hidden row would reveal its key because the token is encoded, not confidential. Retaining visible-row positions and the non-uniform completeness class avoids that direct disclosure. [LLP 3000.007:506](/Users/ccheever/projects/snapback-3000007-review/repo/llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:506), [cursor.rs:48](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/cursor.rs:48).
- Partition delivery does not automatically include the writer. It follows the declared audience, and catch-up checks current read permission before emitting a row. This is the correct boundary for hidden writes. [partition.rs:106](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/partition.rs:106), [partition.rs:563](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/partition.rs:563).

**Concerns**

**1. High — update admission and write success are different predicates; the latter can reveal hidden content.**

“Admission” must mean the result of evaluating the particular update rule against the principal and the exact old/new images. Success necessarily reveals that predicate’s truth, as well as existence. If the rule is `old.secret = next.guess`, admission itself reveals a hidden equality. An unrestricted old-dependent rule language therefore cannot promise literally “existence only.” The author must either accept disclosure of the rule predicate or restrict such predicates for hidden writes. The evaluator supports these comparisons directly. [engine/rules.rs:105](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/rules.rs:105).

There are additional channels **even when the update rule admits both compared worlds**:

- **Immutable columns:** let `read` deny the writer, `update` allow it, and `secret` be immutable. A mutation assigning a caller’s guess to `secret` succeeds exactly when the guess equals the stored value; otherwise it returns the named immutable-column refusal. Replacing that refusal with generic `E_RULE` still leaves the success/failure equality oracle. [engine/write.rs:247](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:247).
- **Conditional updates:** withholding `E_CONFLICT.current` does not hide the truth of a condition evaluated against hidden content. Today Quarry evaluates the condition through a read-filtered temporary before `Stmt::Update`. Making that temporary a raw old image would expose hidden data to arbitrary author expressions and would evaluate the condition before update authorization. [bind/program.rs:606](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-lang/src/bind/program.rs:606).
- **Unauthorized existence:** direct-ID absence returns `NOT_FOUND`, while an existing row rejected by the update rule returns `E_RULE`. This distinction already exists at the baseline and reveals existence without successful update admission. [engine/write.rs:72](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:72).

**Resolution:** define the permitted disclosure precisely. Preserve ordinary read-filtered author expressions; introduce engine-private write-target resolution instead of weakening `Get`. For an existence-only hidden-write contract, reject hidden-value comparisons such as immutable-field assignments independently of whether the guess matches, and make missing versus unauthorized targets indistinguishable unless separate authority permits the distinction.

**Required regressions:** `wa1_hidden_immutable_assignment_is_not_an_equality_oracle`, `wa1_hidden_update_condition_never_receives_old_image`, and `wa1_missing_and_unadmitted_targets_have_the_same_outcome`.

**2. High — constraints and maintained side effects expose facts beyond authority over the selected row.**

An admitted update to row A does not authorize learning about row B.

The unique-index check examines every unique index and calls `visible_collision` on a different conflicting row. Consider A, which the writer may update but cannot read, and B, which the writer may neither read nor update. Setting A’s unique value to a supplied guess succeeds when B does not occupy it and fails when B does. Keeping S05’s generic refusal preserves diagnostic privacy, but does not remove this success/failure oracle. A composite key containing an unnamed retained field can additionally carry A’s hidden value into the named constraint message when the conflicting row is readable. [engine/write.rs:222](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:222), [engine/write.rs:300](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:300).

Other engine work has the same problem:

- **Caps:** moving a row into a capped group succeeds or fails according to the group’s population. The check counts physical live rows, not rows readable by this writer. [engine/write.rs:262](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:262).
- **`after insert`:** the final existence check uses an engine lookup without a target read check. An upsert’s insert branch creates this obligation; its existing-row update branch does not. A refusal can therefore expose either that branch distinction or existence in the postcondition’s target table. This is an existing constraint channel, not something the patch merge invents. [engine/write.rs:320](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:320), [engine/write.rs:376](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:376).
- **Readable maintained sums:** two hidden contributions can total the same publicly readable sum before the call. Resetting one admitted hidden contribution to zero reveals its former value through the change in that sum. The core’s source-audience restriction applies when the maintained target is synced; it does not impose the same restriction on an online-only readable target. [engine/write.rs:395](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:395), [schema.rs:788](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/schema.rs:788).
- **Budget outcomes:** index work depends on which old keys change, and maintained writes depend on the old contribution. Near a ceiling, the same admitted update can succeed in one hidden state and abort in another. Neither meter marks nor exact counts need reach the wire. [store.rs:342](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/store.rs:342), [engine/write.rs:417](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:417).

**Resolution:** do not describe these failures as merely “the write rule’s refusal.” Either narrow hidden-write eligibility to operations whose constraints and observable side effects preserve the stated boundary, or explicitly approve a broader disclosure contract. Retain S05 for every *other* conflicting row. Redacting error text alone cannot resolve the binary outcomes.

**Required regressions:** `wa2_secondary_hidden_collision_does_not_borrow_target_authority`, `wa2_retained_composite_key_never_enters_refusal`, `wa2_hidden_group_cap_and_postcondition_disclosures`, `wa2_reset_cannot_reveal_hidden_sum_contribution`, and `wa2_hidden_index_and_maintain_work_cannot_flip_public_bounds`.

**3. High — patching can expose retained asset identifiers before update authorization.**

Patching does not inherently disclose more than replacement: replacement already reads the old row. The important difference is that patching feeds **unnamed old fields** into subsequent processing.

The proposed merge would use the existing update/replace path. `replace` calls `with_asset_facts` before checking the update rule. That helper examines every asset field in the merged row and includes the asset ID in `E_ASSET_UNKNOWN` when the upload belongs to someone else. Thus a harmless patch to a hidden row retaining another principal’s photo can reveal the photo’s ID—even before determining whether the writer may update the row. Replacement with caller-supplied fields did not require exposing that omitted old asset. [engine/write.rs:75](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:75), [engine/write.rs:95](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:95), [engine/write.rs:156](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/write.rs:156).

Patch semantics also deliberately introduce an insert/update distinction for omitted required columns: the existing-row branch can succeed while the absent-row branch returns `E_INPUT`. That is an existence observation, acceptable only within the disclosure authority actually granted. [LLP 3000.007:466](/Users/ccheever/projects/snapback-3000007-review/repo/llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:466).

**Resolution:** preserve already-established facts for unchanged assets; validate newly supplied placements separately. Keep retained values out of diagnostics and author-visible temporaries. Specify authorization and validation ordering for both branches, including denied updates.

**Required regressions:** `wa3_hidden_patch_preserves_foreign_asset_without_disclosing_id` and `wa3_patch_missing_required_fields_respects_disclosure_authority`.

**4. High — §5.9 exposes a hidden-population threshold through commit versus abort.**

Use a non-uniform prefix, an empty visible population, and a loop over `first 1`. Hold public state and sequence history equal between worlds.

| Hidden population under that prefix | Proposed mutation | Equivalent query |
|---|---|---|
| Empty, or below the examined ceiling | `sent`; loop visits zero rows | Empty data, `complete: false`, no cursor |
| Above the examined ceiling | `failed`, `E_BOUND` | Empty data, `complete: false`, no cursor |

Each hidden candidate consumes examined work. Mutations use `Cut::Abort`; queries use `Cut::Cap` and retain the non-uniform completeness class. The mutation therefore reveals a threshold which **the equivalent query does not reveal in this example**. Naming only the ceiling does not conceal whether it was reached. [engine/read.rs:426](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/read.rs:426), [engine/read.rs:449](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/read.rs:449), [meter.rs:120](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/meter.rs:120), [engine/mod.rs:646](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/mod.rs:646).

The baseline scan also looks for an additional visible row after collecting `take`. Consequently, even a hidden tail *after the requested N visible rows* can consume the remaining budget and prevent the mutation from committing. [engine/read.rs:498](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/read.rs:498).

This is not wholly a newly invented engine channel. Baseline admission rejects population loops and certain cap combinations, but does not categorically reject a mutation that merely binds or returns a non-uniform scan. Such a mutation can already encounter `Cut::Abort`. §5.9 expands access to that channel; it does not establish its safety. The historical meter review explicitly identified this mutation problem and suggested constant outcomes or structural refusal. The journal’s disposition removed counts while retaining a documented residual. [engine/admission.rs:61](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/admission.rs:61), [3000-meter-cut.grok.md:245](/Users/ccheever/projects/snapback-3000007-review/repo/llp/reviews/3000-meter-cut.grok.md:245), [JOURNAL.md:416](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/JOURNAL.md:416).

Mixed visible/hidden scans can already expose differences in which visible rows fit before a cut. That existing residual does not make the all-hidden query and mutation equivalent.

**Resolution:** the smallest defensible version admits server-only bounded passes over prefixes whose read rule is uniformly decided, while retaining the non-uniform refusal. Say “up to N authorized rows, atomically, subject to the mutation’s budgets.” If non-uniform passes remain desired, they need a separately specified disclosure policy.

Charging hidden rows nothing is not a complete solution: physical traversal still needs a bound. A timeout or separate physical-budget abort recreates the channel. Committing a partial scan also changes the promised semantics and needs its own analysis.

**Required regressions:** `np1_hidden_empty_and_hidden_over_budget_have_identical_public_outcomes`, `np1_hidden_tail_after_take_cannot_change_commit`, and `np1_nonuniform_read_without_loop_cannot_bypass_admission`. Keep `h1_a_non_uniform_scan_is_capped_whatever_the_meter_found`; the existing `m3_e_bound_names_the_ceiling_not_the_count` checks formatting, not this oracle. [tests/reviews.rs:165](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-sim/tests/reviews.rs:165), [tests/reviews.rs:241](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-sim/tests/reviews.rs:241).

**5. High — `_ops` can replay formerly readable content after access is revoked.**

A write that was hidden initially and records only an appropriately sanitized outcome need not disclose additional row data on retry. `replayed` identifies the caller’s recorded operation, and `_ops` is keyed by principal and operation ID.

However, the baseline records the entire `MutationOutcome`, including `result` and conflict `current`. Replay returns it without reevaluating read authority, and the HTTP replay branch serializes those values directly. A mutation result or conflict image readable at the original attempt can therefore be retrieved after revocation, including when the original response was lost. This is an existing replay gap, not caused by merging patches. [engine/mod.rs:683](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/mod.rs:683), [engine/mod.rs:803](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/mod.rs:803), [store.rs:416](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/store.rs:416), [serve.rs:759](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4/src/serve.rs:759).

**Resolution:** distinguish durable execution receipts from permission to retrieve cached content. Preserve `sent`/failure identity and sequence without reexecuting the mutation; separately constrain or reauthorize replayed data. Arbitrary shaped/scalar results require more than removing a top-level row. If historical result retrieval is intentional, explicitly declare that exception instead of claiming current read authority governs all returned content.

**Required regressions:** `wa5_hidden_write_replay_returns_only_sanitized_receipt` and `wa5_revoked_result_and_conflict_current_are_not_retrievable`, including a dropped original response and a different principal reusing the same operation ID.

**6. Medium — “held” does not establish the absence of a hidden write target.**

A device’s absence of a pending row reveals only its own execution/coverage decision, provided identical local state produces the same decision whether the server target is absent or hidden. It need not be a server existence oracle.

But §6.2’s read-site classification is insufficient for the new write semantics. A synced table without a horizon holds all rows the viewer may **read**, not all rows the viewer may **update**. Baseline `fetch` marks a missing synced target uncertain only when there is a horizon. A direct hidden update can therefore produce local `NOT_FOUND`; an upsert can speculate an insert. `Device::admit` converts only `RuntimeError::Prediction` into durable non-predicting queueing. [LLP 3000.007:652](/Users/ccheever/projects/snapback-3000007-review/repo/llp/3000.007-relaxed-quarry-and-explicit-residency.rfc.md:652), [engine/read.rs:177](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/engine/read.rs:177), [device.rs:557](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-device/src/device.rs:557).

**Resolution:** include implicit write-target, rule, and constraint reads in prediction eligibility. Missing targets whose global absence cannot be established must queue without speculative rows. Enforce `predicts: never` in device admission and replay, not only generated client metadata. A host-dependent native-read classification must not accidentally make a §5.9 operation eligible on another device.

The writer’s outbox must settle even when its stream contains no row event. Existing watermark advancement and acknowledgement support that; do not add writer delivery to solve settlement. [partition.rs:546](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-core/src/partition.rs:546), [tests/review_corrections.rs:206](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-sim/tests/review_corrections.rs:206).

**Required regressions:** `wa6_hidden_and_absent_targets_queue_without_rows_on_both_stores`, `wa6_hidden_write_settles_without_viewer_event`, and `np6_server_only_pass_never_predicts_after_reopen_or_rebase`.

**Suggestions**

Revise the S05 contract explicitly rather than describing the change as removal of a redundant read grant:

| Case | Required disposition |
|---|---|
| Ordinary insert collides with hidden ID or unique key | Keep generic `E_RULE`. |
| `insert … if absent` collides with hidden row | Keep generic `E_RULE`; readable collisions may return `null`. |
| Upsert resolves its designated existing target, and update rule admits | Proposed exception applies to this target only, subject to the concerns above. |
| Upsert resolves a target whose update rule denies | No successful write or target-content disclosure. Normalize unauthorized/absent distinctions where required. |
| Update/upsert collides with a different hidden row on another unique index | Keep S05 for that other row; target authorization does not transfer. |
| Upsert finds no target | Apply insert authority and insert constraints, including required fields and final postconditions. |
| Readable conflict | Preserve useful diagnostics only to the extent their contents are readable or caller-known. |

The kept insert-if-absent refusal and an admitted upsert are **permission-consistent**: the former does not invoke update authority; the latter does. Learning existence through an admitted upsert is the disclosure §8.7 proposes to permit.

Nevertheless, S05 never proved complete existence noninterference: under a known-permissive insert rule and otherwise fixed constraints, successful insertion versus generic collision refusal already distinguishes an occupied key. Its record expressly disclaims formal noninterference. The review should not credit generic `E_RULE` with hiding that binary distinction. [3000-security-remediation-20260913.md:17](/Users/ccheever/projects/snapback-3000007-review/repo/llp/reviews/3000-security-remediation-20260913.md:17), [3000-security-remediation-20260913.md:33](/Users/ccheever/projects/snapback-3000007-review/repo/llp/reviews/3000-security-remediation-20260913.md:33).

Split the existing S05 regression into admitted and denied update cases, covering both primary and alternate keys. Its current `.owner = viewer` update rule tests the **new** image: the proposed alternate-key behavior would admit changing the hidden row’s owner to the caller. Add an explicit old-owner guard fixture so that this policy distinction is intentional. [tests/security.rs:15](/Users/ccheever/projects/snapback-3000007-review/repo/snapback4/crates/snapback4-sim/tests/security.rs:15).

Implement the regressions named above as paired worlds with identical caller inputs and readable state. Compare complete viewer-facing envelopes, committed effects, retries, and device observations—not merely absence of a secret substring. Preserve atomic rollback checks for source rows, maintains, partition events, and effects. Timing requires a separate host measurement; a deterministic simulator can validate logical work and outcomes, not establish physical constant-time behavior.

**Open questions**

- Is the intended contract existence only, disclosure of the update predicate’s truth, or disclosure of all constraint/resource outcomes? These are materially different policies.
- Does “result row withheld” depend on pre-write or post-write read authority? A write may itself make the row readable; specify the authorization snapshot.
- Are readable aggregates over hidden sources intentional declassification, including the additional information obtainable by modifying one contribution?
- May `_ops` retrieve historically authorized content after revocation, or only the durable execution receipt?
- Will §5.9 exclude non-uniform scans, or explicitly accept their population-dependent commit behavior? The `check --cost` wording cannot decide this security question.

**Recommended next step**

Return §8.7 and §5.9 for a bounded revision. Narrow the first implementation to engine-private target resolution with a precisely stated disclosure allowance, and server-only bounded passes over uniformly authorized prefixes. Resolve retained-field diagnostics and replay retrieval, then implement the paired-world regressions before accepting either broader claim.

The blocking channels are hidden-value-dependent write outcomes, secondary-row and aggregate disclosures, retained asset diagnostics, non-uniform scan aborts, and cached content retrieval after revocation.
