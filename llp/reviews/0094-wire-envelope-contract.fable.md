# Review: LLP 0094 — Wire envelope contract (Round 1)

## 2. Overall assessment

This is a strong P-0 spec in the LLP 0091 tradition: it pins the wire envelope at file+symbol precision, and nearly everything I spot-checked against the worktree code held exactly. The §0A.5 drain contract is byte-accurate against `drain_outbox` (bare `Json(drained)` array, the `admitted.is_none()` single-element synthesized `ResyncRequired` with `reason: "unknown_or_reaped"`, `clear_retained: true`, no subscription id, no ack verb). The §0C closure matrix is correct in every row I verified against the serde attributes and schema roots. §0D is genuinely implemented as claimed (`Option<Receipt>` at `src/local.rs:676,778`, regenerated schemas referencing the `Receipt` union, typed test instances). The §0A.3 migration is real, alias-free, and the LLP 0031 dated amendment landed. All four referenced tickets exist on disk. The document is also unusually honest about per-arm asymmetries (§0C.3, §0B.6's hosted caveat), which is exactly the right posture for a contract native clients build against.

However, one row of the normative §0A matrix is contradicted by the code and by a sibling contract-bearing spec. The matrix says the hosted kit socket serves `ping` only; the coordinator's `webSocketMessage` handler demonstrably serves in-band `subscribe` and `unsubscribe` frames on kit-protocol sockets — with kit-dialect responses built specifically for that case — and LLP 0091's step-5 amendment explicitly contracts `resumeFromToken` as "accepted on both subscribe entry points (the kit HTTP subscribe and the live-socket subscribe frame)" on the hosted arm. Because §0A declares itself normative ("a route absent from an arm's column is not served"), this is not a courtesy-citation drift: a clean-room server implementer would refuse frames the real hosted arm serves, and a clean-room client author would treat a served surface as nonexistent. The related §0F item 2 rests part of its exclusion decision on a "frozen" characterization that the same shared frame grammar has already outgrown.

The negotiation design (§0B) is coherent and well-staged, and the B1–B4 gap is known state I do not count against the document. But §0B.6's load-bearing "decode-class rejection" trigger is never pinned to a wire-observable signal, and the first clean-room consumer (the Swift client, in this very worktree) has already implemented an over-broad guess for it — direct evidence the spec underdetermines a clean-room implementer at exactly the point it was written to serve.

## 4. Concerns

1. **(Major) The normative §0A.1 WS-kinds row misstates the hosted kit-socket surface, contradicting both the code and LLP 0091.** The row says hosted serves "`ping` only (kit socket); no ephemeral kinds." In `cloudflare/src/coordinator.js`, `webSocketMessage` (`:4671-4733`) routes `subscribe` and `unsubscribe` frames from kit-protocol sockets into full service: the subscribe branch computes a kit `socketSessionId` (`:4703-4707`), `subscribe()` responds in the kit dialect (`const isKit = this.socketProtocolFor(ws) === 'kit'`, `kind: 'current_as_of'` with snake_case members, `:4807-4821`), and the unsubscribe branch has an explicit kit-session-scoped delete (`:4710-4716`). This is deliberate, not vestigial. LLP 0091's step-5 amendment states the same fact as contract: "`resumeFromToken` is accepted on both subscribe entry points (the kit HTTP subscribe and the live-socket subscribe frame)" (`llp/0091-rqs-token-and-wire-contract.spec.md:843-844`). Under §0A's own rule ("a route absent from an arm's column is **not served**"), a clean-room server refuses frames the real arm serves and a clean-room client is told a served, sibling-spec-contracted surface does not exist. "No ephemeral kinds" is correct; "ping only" is not. **Resolution:** either (a) correct the row to `subscribe|unsubscribe|ping` for the hosted kit socket, pin the kit-dialect response frames (`kind: 'current_as_of'`/error frames) or cross-reference where they are pinned, and reconcile the row with LLP 0091; or (b) decide the in-band kit-socket subscribe surface is unwanted, spec its refusal, and ticket the server change — but the current text may not stand as-is.

2. **(Moderate) §0F item 2's "frozen" factual basis is inaccurate, and the exclusion sweeps in a kit-socket grammar that is squarely wire v1.** The spec says the proof socket "speaks its own frozen three-message protocol" and that schematizing it "would imply evolution support it does not have." But `validateLiveSocketFrame` (`coordinator.js:5311-5360`) — the single validator behind coordinator.js's cited lines — already evolved past LLP 0040: the subscribe frame gained `resumeFromToken` and tolerates `membershipWitness` under LLP 0091 (the in-code comment cites "LLP 0091 §0B.4" directly). And the same validator serves **kit** sockets (concern 1), so excluding this grammar from wire v1 and the gate inventory leaves a served kit-socket client→server family entirely ungoverned — the opposite of §0F's purpose. **Resolution:** restate item 2 honestly (the grammar has an LLP 0091-era extension; "frozen" applies, at most, to the proof protocol's response framing), scope the exemption to the proof socket only, and place the shared/kit in-band frame grammar explicitly inside §0C and the §0F inventory (or inside the refusal decision from concern 1).

3. **(Moderate) §0B.6's "decode-class rejection" is not pinned to a wire-observable signal, and the first clean-room consumer already guessed it wrong-shaped.** The actual local signal is `SNAPBACK_REQUEST_JSON_INVALID`, HTTP 400 (`ApiError::request_json_invalid`, `src/server.rs:19553-19556`, via `parse_optional_json`, `:15715`) — a code that also fires for missing `Content-Type` and non-object bodies. The spec never names it. The Swift client in this worktree implements decode-class as *any* HTTP 400 or 422 except `SNAPBACK_WIRE_VERSION_UNSUPPORTED` (`clients/swift/SnapbackClient/Sources/SnapbackClient/SnapbackClient.swift:108-110`) — an over-broad heuristic under which unrelated open-time 400s (e.g. the hosted `SNAPBACK_CONNECTION_ID_INVALID`, `coordinator.js:4204-4208`) trigger a spurious offerless retry. For a contract whose stated purpose is preventing clean-room guessing, the legacy-detection trigger must be exact. **Resolution:** pin the concrete signal — today, `SNAPBACK_REQUEST_JSON_INVALID` (400) plus the disappears-when-member-removed differential — and enumerate codes that MUST NOT trigger the fallback (`SNAPBACK_WIRE_VERSION_UNSUPPORTED` at minimum, per §0B.3's must-not-retry-lower rule).

4. **(Minor) The §0B.7 enumerations are stale at HEAD and B2's stage wording is kit-only.** `clients/swift` is both a kit-stream socket consumer and a `/connection/open` body constructor, absent from both populations (audited at `6fe11376`, before the Swift landing). It is compliant — offers `snapback.v1` (`SnapbackClient.swift:57,272-280`) — so the "none found" conclusion survives, but the B3/B4 gates re-run this enumeration and the recorded population should include it. Relatedly, §0B.5 B2 names only the JS kit, while the Swift client already sends `wireVersion` pre-B1 and leans on §0B.6 detection every fresh process against a pre-B1 local server. **Resolution:** add the Swift client to both §0B.7 populations at next revision, and state whether non-kit clients are bound by the B2 gate or sanctioned to offer-early-with-detection (the Swift client's current behavior).

5. **(Minor) Citation freshness.** Line-number drift throughout is expected (spec pins `6fe11376`; HEAD is later): e.g. `OpenConnectionRequest` now `src/server.rs:4081-4094` (cited 4070-4083), subprotocol constant `:5467` (cited :5456), upgrade `:16966`, `acceptKitSocket` echo `coordinator.js:4600` (cited 4598), `kitOpenConnection` `:4196` (cited 4194), `KIT_ROUTE` `gateway.js:67` (cited 64), `HandlerInput` `src/manifest.rs:3277` (cited 2937), proof-frame validator `coordinator.js:5311+` (cited 5318-5347). All symbols and facts still hold. **Resolution:** refresh the courtesy line numbers (or the pin commit) at next revision; no content change needed.

## 5. Suggestions (non-blocking)

1. §0A.1 could record HTTP statuses where the hosted arm's refusals differ from intuition — `SNAPBACK_CONNECTION_SOCKET_REQUIRED` is 409 (`coordinator.js:4400-4405`), which §0E's "existing codes" list doesn't surface; a clean-room client mapping refusals to states benefits from the status being pinned somewhere.
2. §0B.3's alias note ("`wire_version` accepted as alias, matching the DTO's existing alias convention") could cite the convention concretely (`#[serde(alias = ...)]` on every `OpenConnectionRequest` member) so B1's implementer doesn't have to infer it.
3. §0C.5 could note that because `authInvalidationProtocol` is `Option<u32>`, a *non-numeric* unknown value is already a decode failure on the closed local DTO — the aligned-refusal matrix only governs unknown *numbers* — to spare an implementer the type-versus-value refusal distinction.
4. Consider answering the doc's own OQ2 (echoing the bound `wireVersion` in the open response) affirmatively in B1: §0B.6's hosted caveat ("absence-of-echo... cannot distinguish") would largely dissolve, and it is additive.

## 6. Open questions for the author

1. Is the hosted kit-socket in-band subscribe/unsubscribe surface (concern 1) intended contract, tolerated accident, or a surface to be refused? The code invests in it (kit-dialect responses), LLP 0091 contracts it, and this spec denies it — three positions, one wire.
2. When the shared Cloudflare deployment redeploys (post-§0A.3), does anything re-verify that the old root system routes actually stopped answering (the "no aliases" claim as deployed, not just in-repo)?
3. For §0B.6, should a strict-configured client's refusal on decode-class rejection get its own client-side diagnostic code (the Swift client minted `SNAPBACK_CLIENT_WIRE_VERSION_DOWNGRADE` for the non-strict path — is client-side code minting inside the `SNAPBACK_*` namespace sanctioned?)

## 7. Verdict

**NOT READY.** The document is close — the drain contract, closure matrix, receipt typing, migration record, and refusal registry all verified cleanly against the worktree, and the known-state items (B1–B4 unimplemented, pending redeploy) play no part in this verdict. But §0A declares its matrix normative, and one row of it is contradicted by the served behavior of `coordinator.js` and by the sibling contract LLP 0091 (concern 1, Major): the hosted kit socket serves in-band subscribe/unsubscribe that this spec says is not served. For a P-0 wire contract whose consumers are clean-room native clients, a normative served/not-served misstatement — compounded by §0F item 2 excluding that same shared grammar from governance on an inaccurate "frozen" basis (concern 2) — is exactly the defect class this spec exists to eliminate. Resolving concern 1 (either direction: pin the surface or spec its refusal), restating §0F item 2, and pinning the §0B.6 decode-class signal would make this READY; nothing else found rises above Minor.
