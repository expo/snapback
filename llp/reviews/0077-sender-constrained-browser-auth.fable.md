2. **Overall assessment**

This is a strong, unusually disciplined piece of security engineering. The design lands squarely inside the slice LLP 0060 C3 delegates: every item C3 owes before a positive capability — issuance vs. resource proofs (with `ath` present only on resource proofs), explicit inclusion/exclusion of every credential class, HTTP and WebSocket transport, canonical URI reconstruction behind the provider-authenticated target (src/auth/deployment.rs:367–391), a closed ES256-only JOSE profile, time-window and nonce policy, replay-store dimensions and fail-closed behavior, downgrade refusal, and key persistence/deletion/recovery — is covered by a section of this Spec. The claim discipline C3 pins ("off-device replay constraint, never XSS-resistant") is restated correctly (llp 0077 lines 109–111, 302–304), and `SNAPBACK_AUTH_SENDER_PROOF_*` codes match LLP 0060's reservation (0060 lines 907–910) plus one new `AUTHORITY_UNAVAILABLE` code that fits the fail-closed posture.

The implementation checkpoint is, on the whole, an honest record. I verified nearly every load-bearing claim against the code: the hosted entrypoint structurally excludes bearer/admin/agent seams (hosted-browser.mjs:22–42), the Rust verifier closes header/payload/JWK/base64url/signature/jti axes with `deny_unknown_fields` and canonical re-encode checks (sender_proof.rs:30–69, 1196–1258), inclusive time boundaries are tested on both edges (1556–1573), the two-connection replay race exists and asserts exactly one success/one replay (1728–1760), the pre-body cut runs before an adversarial body that panics if polled (server.rs:23653, 18800), the outage/repair drill accepts the same proof and nonce only after repair (server.rs:23928–23993), the reset train refuses a correctly signed stale post-reset request (server.rs:24098–24133), declared-restore coverage exists (src/storage/auth.rs:2751–2809), and the reflected nonce/JWK/proof-segment sanitization gap the doc claims was closed is demonstrably closed (index.mjs:1951–1958; sender-transport.test.mjs:346–378). The closing paragraph ("remain unimplemented. No capability is positive") is accurate status discipline.

Two things keep this from READY. First, the nonce-challenge semantics are internally contradictory in the doc and, in the implemented form, hand the protocol's own adversary — a token thief — an unauthenticated lever to rotate a family's durable nonce and deny the legitimate client service. Second, the work amends LLP 0057's Accepted `/auth/exchange` wire contract (which explicitly reserved sender-binding as "not implementation latitude") without a corresponding 0057 revision note, while LLP 0059 did get one. Both are cheaply fixable, and neither undermines the core replay/custody design.

3. **Strengths**

- **Verification order is genuinely pre-body and pre-projection.** `admit_hosted_sender_request` runs in the registered-route middleware before `AdmittedBodyGuard` wrapping and before any session projection (server.rs:8497–8531), matching the eight-step order in "HTTP binding" (llp lines 157–166), and the test proves it with a body that panics on poll (server.rs:18800, 23653).
- **The atomic consume/rotate cut is real.** One `IMMEDIATE` SQLite transaction fences generation+nonce+expiry, inserts the replay row, and installs the successor with a guarded UPDATE; constraint violation maps to Replay; partial commits are impossible (sender_proof.rs:937–1082), with rollback coverage (test at 1830).
- **Closed codec discipline.** Duplicate JSON fields, unknown fields, padded/non-canonical base64url, non-16-byte jti, extra compact segments, `crit`, `use`, wrong curve/alg/typ/version each refused, and each tested (sender_proof.rs:1577–1641).
- **URI retargeting is structurally excluded.** Proof target = authenticated public origin + routed path with `%`, `\`, `//`, and dot-segment refusal; query and forwarding headers cannot participate (deployment.rs:370–391).
- **Custody claims verified end to end**: non-extractable key enforcement on both generate and sign (sender-proof.mjs:30–41, 53–57), structured-clone persistence, interrupted-transition recovery, deletion-only logout to a v3-shell-free anonymous `AuthCustodyV2` (auth-sender-custody.test.mjs:163–220, 245–276), and forbidden-carrier sentinels for broadcasts/hints/settled state (auth-sender-custody.test.mjs:81–132).
- **No bare-bearer seam found.** A hosted session bearer without a family binding gets a challenge without a proof and `Invalid` with one (sender_proof.rs:757–777); v1 upgrade-in-place does not exist (test at 2062); non-session credential classes bypass into their own independent authentication paths exactly as the "Credential classes" section states.
- **Live cross-language proof** (tests/sender_proof_cross_language.rs:21–48) executes Node WebCrypto against the Rust verifier, and RFC 7638 thumbprint construction is canonically ordered on both sides (sender-proof.mjs:19–26, 38–39; sender_proof.rs:1227–1231).

4. **Concerns**

1. **Major — Nonce-challenge semantics: internal contradiction plus an unauthenticated rotation/DoS lever.** The doc says a lost response is recovered by presenting the retired generation and receiving "the still-current nonce" (llp lines 186–189), but the code path for both a missing proof and a wrong-nonce proof calls `fresh_challenge` → `issue_sender_nonce`, which **overwrites** the family's durable current nonce with generation+1 (sender_proof.rs:765–773, 860–869, 606–625). Worse, `verify_sender_proof` checks nonce before signature (1299–1306), and the missing-proof path never verifies anything — so an attacker holding only a copied bearer (exactly this protocol's adversary) can send proof-less requests that each rotate the target family's nonce, racing the legitimate client's at-most-once retry (llp lines 178–179) into persistent lockout. Without this lever a token thief can disrupt nothing (logout needs a v2 proof; family alarm is revoke-only), so the challenge path itself introduces the family's only thief-reachable availability attack. Resolve by returning the still-current nonce without rotation on the missing/mismatch path (the doc's own lost-response wording), or by verifying the signature before treating a nonce mismatch as challenge-worthy — then make doc and code agree.
2. **Moderate — Diagnostics section contradicts the nonce protocol and the code.** "They expose no distinction between unknown token, wrong key, bad signature, wrong nonce, stale time, or wrong target" (llp lines 276–277) is false as written: wrong/retired nonce yields `SNAPBACK_AUTH_SENDER_PROOF_REQUIRED` plus a fresh `DPoP-Nonce`, distinct from `INVALID` and `REPLAYED` (sender_proof.rs:858–870; server.rs:8277–8293), and the nonce section itself mandates that distinction (llp lines 174–177). The nonce carve-out is necessary (it is RFC 9449's `use_dpop_nonce` pattern); the normative sentence just needs to scope the non-distinction to within `INVALID`.
3. **Moderate — LLP 0057's exchange wire surface is amended without a 0057 revision.** 0057 (Accepted) pins the `/auth/exchange` body as `{challengeId, code}` (0057 lines 972–973) and lists sender-binding among explicit later-version questions that are "not implementation latitude here" (0057 lines 1740–1746). The implementation adds a `senderConstraint` member and a `dpop-nonce` response header to that route (server.rs:9320–9360, 11034–11040). LLP 0059 carries a Revised note delegating to Draft 0077; LLP 0057 has none. Add a 0057 Revised/delta note (or an explicit amendment statement in 0077 naming the 0057 sections it extends and the version gate).
4. **Minor — Replay retention overstates its margin.** The doc claims retention "for at least the full accepted window plus clock skew" (llp lines 170–171), but retention is exactly `PAST+FUTURE = 35s` (sender_proof.rs:21–25, 874–876) with inclusive-boundary deletion (`expires_at_seconds <= now`, 1013), so at exactly T+35 a maximally future-dated proof is simultaneously time-valid (inclusive `iat+30 >= now`) and purged from the replay table. Mandatory nonce rotation closes the practical hole, but either add a skew margin to retention or correct the wording.
5. **Minor — Second-implementation completeness gaps.** Interop-required facts live only in code: the exact issuance payload JSON (camelCase `challengeId`, `protocol` member, no `ath` — sender-proof.mjs:120–128 / sender_proof.rs:59–69) where the doc gives only prose; the WebSocket subprotocol carrier name `snapback.sender-proof.<compact>` (index.mjs:1982; server.rs:4769) which the normative WebSocket section never names; the nonce value format (32-byte base64url) and TTL (120s, server.rs:8181). The resource-proof payload got exact JSON; these deserve the same.
6. **Minor — Historical and browser-environment claims are unverifiable as stated.** "The last check found and closed a gap" is a history claim with no committed history (all files untracked); the closed state is verified but the narrative is not. "Cross-reopen structured-clone persistence" and the "live WebCrypto" tests run in Node, not a real browser IndexedDB/WebCrypto stack — accurate as written if read carefully, but the checkpoint should say Node explicitly so "live" is not over-read.

5. **Suggestions**

- Split the document: keep the normative contract (Summary through Acceptance) as the Spec and move the 85-line implementation checkpoint to a dated appendix or the diary/Linear trail. Roughly 40% of the doc is implementation log, and the standard-review question "could a second implementation be tested against this?" is currently answerable only with the code open.
- Convert the key requirements to explicit MUST/MUST NOT sentences (RFC 2119 style), especially verification order, the one-retry rule, atomicity of consume/rotate, and fail-closed replay-store behavior. Most are already unambiguous declaratives; the upgrade is cheap.
- State the deliberate RFC 9449 deviations in one place: nonce mandatory on every protected surface (stricter than 9449), `version` claim, closed single-alg profile, fixed 128-bit `jti`, `ath` over the grant token (not access token) on upgrade proofs, and the issuance proof's `challengeId`-instead-of-`ath` shape. All are justifiable narrowings; naming them preempts reviewer re-derivation.
- Consider recording that a challenge issued to an unbound/unknown identity is deliberately untracked and unpersisted (sender_proof.rs test at 2027 proves it) — it is a nice anti-probing/anti-flooding property the doc never claims.
- The nonce table's capacity check applies only on first insert per family (issue_sender_nonce:594–604); note the bound is families-per-epoch, and confirm the admission-epoch dimension cannot grow unboundedly within one deployment.

6. **Open questions**

- The two the author already lists (page vs. service-worker signing posture; the shared nonce/replay provider for the first adapter) — both correctly framed.
- The Concern-1 decision: rotate-on-challenge vs. still-current-nonce vs. signature-before-challenge — this is the one semantic fork a second implementer cannot resolve from the current text.
- Whether nonce TTL (currently 120s in code) and the 30s/5s window are normative constants of the protocol or adapter-tunable within stated floors.
- How multi-replica adapters satisfy "one transaction" for consume/rotate when SQLite's serialized-single-process assumption (llp lines 305–307) no longer holds — the doc names the constraint but not the acceptance test a replacement store must pass.
- Whether the operator-console exclusion (llp lines 261–263) eventually gets its own sender-constraint spec or a permanent recorded exemption in LLP 0072.

7. **Verdict**

Verdict: NOT READY — the design and its implementation evidence are substantially sound and honestly reported, but the nonce-challenge contradiction (doc promises the still-current nonce while the code rotates on unauthenticated requests, creating a token-thief DoS lever) and the unrecorded amendment of LLP 0057's Accepted exchange contract must be resolved before this Spec can advance.
