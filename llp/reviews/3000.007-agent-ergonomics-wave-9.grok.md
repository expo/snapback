## Findings

### Medium — held completeness is not executed on either device store, and not on the Clique shape

**Where:** `snapback4/crates/snapback4-lang/src/bind/residency.rs:401–404`; `snapback4/crates/snapback4/tests/check.rs:709–727`.

**Scenario:** `check` prints `complete over held rows — all sources sync without a horizon…` for `query heldRows … held:` over `public`/`sync` tables. The Clique form is `messages` with `read <- exists members[.conversationId, viewer]`, `sync to members[.conversationId]`, unscoped `byWords`. That still classifies as `Held` and would print the line, and on a device `trust_synced_read` makes the replica scan completable — but no test runs that query on SQLite or the memory device store and asserts `complete: true` (and `false` past a horizon). A regression in device completeness class would leave `check` green.

**Smallest fix:** One `on_both` device test: horizon-free membership-held search → `complete: true` when the replica is fully scanned; same query with `sync … last N` → no check line and `complete: false`. Keep the public/allow CLI case as the uniform control.

### Low — `insert-if-absent` rule sites can cite the table header

**Where:** `snapback4/crates/snapback4-lang/src/bind/residency.rs:91–97`; `catalog.rs:166–178`.

**Scenario:** `insert … if absent` contributes `insert-if-absent <table> rule`. `locate_sites` treats the verb as the effect name. `site_for("tables.t.rules.insert-if-absent")` does not match `insert`/`update`/`delete`, so it returns `info.decl.site` (the `table` line). `why`/`check --residency` then point at the wrong line in the same file. The W9b fixture never used this kind, so “0 unlocated” did not catch it.

**Smallest fix:** Map `insert-if-absent` (and the `insert if absent` spelling) to the insert rule when resolving `tables.*.rules.*`.

### Low — `why N_WIDE_MERGE` always excerpts the search card

**Where:** `snapback4/crates/snapback4-lang/src/diag.rs:127`; `guide/codes.rs:116–121`.

**Scenario:** A Following merge emits `N_WIDE_MERGE` with `guide: feeds` (`bind/mod.rs:261–276`). `snapback4 why N_WIDE_MERGE` still opens `guide search` and the first paragraph that names the code (`guide/search.rs:67–70`), not the feeds recipe. The gloss in `codes.rs:99` mentions feeds, but the excerpt can still send the author to the wrong card.

**Smallest fix:** Prefer the diagnostic’s `guide` keyword when present, or mention `N_WIDE_MERGE` in the feeds card so a feeds-mapped `why` can hit it. (Platform `why` has no per-note guide today; this is the cheap routing fix.)

### Low — unique update / `if absent` not covered on device stores

**Where:** `snapback4/crates/snapback4-device/tests/papercuts/mod.rs:32–54` vs `snapback4/crates/snapback4-sim/tests/papercuts/mod.rs:34–55`.

**Scenario:** Server memory tests cover duplicate insert, update collision, `if absent` → null, and hidden `E_RULE`. Device `on_both` only predicts `create` duplicates. A SQLite-device prediction bug on `rename` or `tryCreate` would not fail W9c’s device tests. Authoritative execution is also always in-memory.

**Smallest fix:** Drive `rename` and `tryCreate` through `on_both` the same way as `create`; optionally run the server unique cases on a SQLite `Engine` as well.

### Low — expiry cards omit the client’s existing `nextExpiry` timer

**Where:** `snapback4/crates/snapback4-lang/src/guide/reads.rs:81–84`; `packages/snapback4/src/client.ts:278–287`.

**Scenario:** A builder using `observe`/`usePage` already refetches at `nextExpiry`. The new copy says the server will not push a removal at the deadline (true of the log) and to drop locally. That is still the right render rule for the current answer (the Clique ~900 ms RTT), but it reads as if live watches do nothing at the deadline.

**Smallest fix:** One clause: local clients already reschedule the watch at `Read.nextExpiry`; still filter the current rows by `.expiresAt` so hide time is the deadline, not the refetch.
