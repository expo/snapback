2. **Overall assessment**

This is a strong, unusually honest RFC. The narrow v1 profile — a pull-driven reader subset instead of a full `ReadableStream`, hard byte/time/rate ceilings, settlement as durable rows rather than streamed responses — is the right shape for Snapback's authority model, and the document is disciplined about what it is not (no client streaming, no exactly-once, no durable cursors). The `ambiguous` settlement state as a first-class, non-retryable outcome is the standout design decision: most systems collapse this into `failed` and silently double-fire non-idempotent effects.

Doc/code agreement is substantially real, not aspirational. The shared Ibex/Workerd reader surface exists (`packages/snapback-harness/ctx-bootstrap.js:804-890`), both hosts implement the bounds with identical constants (`src/server.rs:760-764`; `cloudflare/src/coordinator.js:74-79`), the capability predicate is exact and conjunctive (`src/manifest.rs:3031-3032`, matching LLP 0058:316), the claimed diagnostic codes exist and are emitted at the stated operations, and both witnesses run the real action → nested mutation → commit → native live-push path with a second observing client and a blocked negative actor (`demos/competitive-checkpoint/tests/acceptance/local-streaming.mjs:100-138`). Bounds match LLP 0075's frozen fixture exactly (`demos/competitive-checkpoint/acceptance/protocol.v0.json:69-78`; LLP 0075:251-263).

However, a document whose whole purpose is to be the exact semantic authority pinned by a frozen protocol cannot afford the handful of places where it states more than the code does. Three matter: the progress pattern is repeatedly called "generated" when it is authored per-app with no generator in the codebase; the target-contract section claims manifests "publish the exact enforced limits" when they publish only limit names with an Enforced/Advisory/Missing status; and the "v1 code families" list omits an emitted code (`SNAPBACK_ACTION_STREAM_UNSUPPORTED`) while mischaracterizing where `SNAPBACK_REPLY_PROGRESS_RATE_EXCEEDED` is enforced. Each is a small edit, but each would mislead a consumer of this authority — including the LLP 0075 runner — and so should be fixed before the document leaves Draft.

3. **Strengths**

- **Bounds are genuinely frozen and triple-consistent**: 1 MiB / 64 KiB / 30 s / 5 s / 10-per-second appear identically in the RFC (§Surface, lines 52-61), LLP 0075's stream gate (0075:251-263), the protocol JSON (`protocol.v0.json:69-78`), and both implementations (`src/server.rs:760-764`; `cloudflare/src/coordinator.js:74-79`).
- **Every open/read/cancel really is revalidated** (§Authority and lifecycle, lines 69-72): the action-mode dispatcher routes every host op through `validate_host_call` (`src/runtime.rs:1027-1032`), whose default arm checks abandonment, app generation, and watchdog deadline (`src/server.rs:865-881`); open additionally crosses the external-effect begin/initiated cut (`ctx-bootstrap.js:811-825`) and re-checks liveness after transport (`src/server.rs:1317`).
- **The cancellation model is coherent and witnessed**: durable cancel row rather than connection inference (lines 88-92); the witness proves the terminal row fences late patches and the action settles `cancelled` (`local-streaming.mjs:160-192`).
- **Settlement taxonomy is exercised end-to-end**, including the ambiguous/failed distinction driven by method idempotency (`local-streaming.mjs:210-237`; classification at `src/server.rs:1287-1315` and `coordinator.js:1839-1846`).
- **Exact-code evidence exists on both targets**: Rust unit tests assert `SNAPBACK_ACTION_STREAM_TIMEOUT`, `_IDLE_TIMEOUT`, `_LIMIT_EXCEEDED`, and `SNAPBACK_REPLY_PROGRESS_RATE_EXCEEDED` (`src/server.rs:29902-30121`); the Miniflare witness asserts the 1 MiB refusal code, the 16 KiB chunk ceiling, and idempotent cancel (`cloudflare/test/acceptance.egress.mjs:253-281`).
- **Backpressure is structural, not advisory**: both hosts read upstream only when the invocation asks and the carry-over buffer is empty (`coordinator.js:1931-1949`; `src/server.rs:1381-1388`), so the buffered-byte bound holds by construction.
- **Scope discipline is excellent**: the non-goals (lines 172-179) genuinely exclude what the body could be read to promise, and lines 63-65 explicitly deny that the v1 maxima are a general streaming API commitment.
- **Diagnostics carry operation, limit, safe received summary, and a real guide anchor** (`guide/backend/actions-and-fetch.md:96` "Stream a response"); `./ref-check` passes with 0 errors.

4. **Concerns**

1. **Moderate — "generated progress pattern" describes something that does not exist as generated code.** Lines 61 and 97 attribute the durable pattern to codegen ("the generated progress pattern"), but the fixture's `startReply`/`applyReplyProgress`/`streamReply` are authored handler source (`demos/competitive-checkpoint/snapback/handlers.mjs`, registered via `defineAction`/`defineJsMutation` in `functions.mjs:8-12`), no generator for this pattern exists anywhere in `src/` or `packages/`, and both LLP 0075 (lines 186-190: "may be authored explicitly under the streaming semantic authority") and the protocol JSON (`generatedPatterns` lists only owned-crud/lookup/pages, `protocol.v0.json:66-68`) say the pattern is authored. This matters beyond wording: the late-effect fence is carried by the pattern's in-transaction terminal check, so claiming the pattern is "generated" overstates who guarantees the fence. Resolve by rewording to "the durable progress pattern (authored today under this authority; a generated variant is future work)" or by shipping the generator.
2. **Moderate — the target-contract manifest claim overstates the implementation.** Lines 141-144 say capability manifests "publish the exact enforced limits." They publish availability (`bounded_response_stream_v1` in `supportedCapabilities`) and four named resource-limit rows with status only — `ResourceLimit` is `{name, status}` with no value field (`src/manifest.rs:3268-3272`, rows at 3396-3408), and the generated manifest confirms no numbers (`demos/competitive-checkpoint/snapback/generated/capability.manifest.json:44`). There is also no `bounded_response_stream_wall_clock` row at all. Resolve by adding limit values to the manifest rows (and a wall-clock row), or by weakening the sentence to "state whether the profile is available and which limits are enforced."
3. **Moderate — the diagnostic code registry in §Diagnostics is incomplete and misattributes one code.** (a) `SNAPBACK_ACTION_STREAM_UNSUPPORTED` is a real, emitted stream refusal (default `IbexActionHost` trait impls, `src/runtime.rs:142-160`) absent from the exhaustive-looking "v1 code families" list (lines 122-130). (b) The RFC says `SNAPBACK_REPLY_PROGRESS_RATE_EXCEEDED` "describes the application commit protocol rather than response-reader transport" (lines 132-134), but the host transport layer itself emits it for *every* nested mutation while any cursor is open (`src/server.rs:1048-1066`; `cloudflare/src/host-ops.js:275-286`) — a runtime-enforced rejection, broader than the RFC's "for the generated progress pattern" scoping at line 61, and a fixture-flavored name ("REPLY") baked into the generic runtime. Resolve by listing `_UNSUPPORTED`, stating that the host conservatively rate-fences all nested mutations while a cursor is open, and either renaming the host-emitted code or acknowledging the shared name deliberately.
4. **Minor — ambiguity classification is coarser than the prose.** Line 105 says failure "before request initiation is `failed`," but the local implementation classifies *any* pre-metadata transport error on an unkeyed non-GET as `ambiguous` (`src/server.rs:1287-1315`), including connection-refused, where the request demonstrably never initiated; Cloudflare mirrors this (`coordinator.js:1839-1846`). The direction is safe (ambiguous strictly over-approximates), but the authority should state the implementable rule: "a transport failure the host cannot prove preceded initiation is ambiguous for non-idempotent requests." Separately, mid-body transport loss after metadata settles `failed` even though the non-idempotent upstream effect did execute (`src/server.rs:1399-1407`); the RFC never classifies the mid-body case and should.
5. **Minor — several acceptance bullets have no witness yet, and one witness carries a known protocol-violating receipt.** Not yet mechanically witnessed as written: 64 KiB buffering under deliberately slow consumption (enforced in code, never measured by a test); byte non-duplication across an *actual* stream retry (check 3 proves start-idempotency only, `local-streaming.mjs:140-158`); stream-specific reload/authority-loss/watchdog cursor closure (generic fence tests exist, none through an open cursor); and secret/private-data scans over stream receipts. Also `local-streaming.mjs:243` still hardcodes `targetProfile: 'local-ibex-sqlite.v1'`, the noncanonical alias protocol amendment v0.1 prohibits (`protocol.v0.json` amendments; LLP 0075:358-364) — the required instrument correction has not landed, so the Revised header's "local … executable witnesses" claim should carry that caveat. Acceptable for Draft; must be closed or explicitly staged before gate 2 is called closed.
6. **Minor — undocumented and boundary-loose limits.** Both hosts cap concurrent open cursors at 4 (`ACTION_STREAM_OPEN_MAX`, `src/server.rs:764`, `coordinator.js:79`) — a real enforced v1 bound the RFC never states. The 30 s wall limit is checked only at read boundaries, so a blocking read can overshoot the wall by up to the 5 s idle window (`src/server.rs:1363-1371` checks before, not during, the read). Document both.

5. **Suggestions**

- State explicitly that the late-effect fence is layered: the host closes cursors and fences via generation/abandonment, while *terminal-settlement* fencing is the pattern's in-transaction responsibility — so an authored progress mutation that skips the terminal-row check forfeits that guarantee. This is currently implicit and is the single most important thing an app author must not get wrong.
- The Workerd open path does not visibly cross the external-effect begin/initiated cut the way the Ibex path does (`ctx-bootstrap.js:810-825` gates it on `hostCallFn === ibexHostCall`); a sentence on how the Cloudflare adapter satisfies §Authority's "crosses the existing service external-effect begin/initiated cut" would prevent a reviewer from having to reverse-engineer it.
- The Rust side returns `total_bytes: 0` for a read on an already-closed stream (`src/server.rs:1350-1354`) while Cloudflare returns the retained total (`coordinator.js:1903`); harmonize, since the RFC promises the same application surface.
- Consider quoting the enforced constants in one normative table (name, value, code on breach, operation) — the prose currently scatters them across §Surface and §Diagnostics.
- The `Idempotency-Key` header injection (`src/server.rs:1274-1281`) is worth one sentence in §Surface: the key is not merely metadata; it is forwarded to the provider unless the author set the header explicitly.

6. **Open questions**

The document's own three open questions (reader-surface width, machine-checkable provider idempotency declarations, durable-cursor persistence) are the right ones. In addition the author must decide:

- Is the progress pattern *going to be* generated (making "generated" a commitment with an owner and an LLP 0065 fact-class story), or is authored-under-authority the v1 answer? This decision resolves Concern 1 and determines who owns the fence guarantee.
- Should capability manifests carry exact limit values (Concern 2), given that a later profile "may widen them only prospectively" — without published values, a consumer cannot detect which profile a target enforces.
- Is `SNAPBACK_REPLY_PROGRESS_RATE_EXCEEDED` the permanent name for a host-level fence, or a v1 compromise to be renamed before the code becomes load-bearing in receipts?
- Does the 4-open-cursor cap become part of the frozen v1 profile (and the 0075 fixture), or stay an implementation detail free to change?

7. **Verdict**

Verdict: NOT READY — the implementations and witnesses are genuinely strong, but a semantic-authority document may not ship stating that the progress pattern is generated, that manifests publish exact limits, and that the diagnostic registry is complete when the code says otherwise (Concerns 1-3); all three are small, well-bounded edits after which this should be accepted.
