The narrow v1 profile — a pull-driven reader subset instead of a full `ReadableStream`, hard byte/time/rate ceilings, settlement as durable rows rather than streamed responses — is the right shape for Snapback's authority model, and the document is disciplined about what it is not (no client streaming, no exactly-once, no durable cursors). Doc/code agreement is substantially real, not aspirational. The shared Ibex/Workerd reader surface exists (`packages/snapback-harness/ctx-bootstrap.js:804-890`), both hosts implement the bounds with identical constants (`src/server.rs:760-764`; `cloudflare/src/coordinator.js:74-79`), the capability predicate is exact and conjunctive (`src/manifest.rs:3031-3032`, matching LLP 0058:316), the claimed diagnostic codes exist and are emitted at the stated operations, and both witnesses run the real action → nested mutation → commit → native live-push path with a second observing client and a blocked negative actor (`demos/competitive-checkpoint/tests/acceptance/local-streaming.mjs:100-138`). 5. **Suggestions**

- State explicitly that the late-effect fence is layered: the host closes cursors and fences via generation/abandonment, while *terminal-settlement* fencing is the pattern's in-transaction responsibility — so an authored progress mutation that skips the terminal-row check forfeits that guarantee. - The `Idempotency-Key` header injection (`src/server.rs:1274-1281`) is worth one sentence in §Surface: the key is not merely metadata; it is forwarded to the provider unless the author set the header explicitly.

The document's own three open questions (reader-surface width, machine-checkable provider idempotency declarations, durable-cursor persistence) are the right ones. In addition the author must decide:

- Is the progress pattern *going to be* generated (making "generated" a commitment with an owner and an LLP 0065 fact-class story), or is authored-under-authority the v1 answer? This decision resolves Concern 1 and determines who owns the fence guarantee.
- Should capability manifests carry exact limit values (Concern 2), given that a later profile "may widen them only prospectively" — without published values, a consumer cannot detect which profile a target enforces.
- Is `SNAPBACK_REPLY_PROGRESS_RATE_EXCEEDED` the permanent name for a host-level fence, or a v1 compromise to be renamed before the code becomes load-bearing in receipts?
- Does the 4-open-cursor cap become part of the frozen v1 profile (and the 0075 fixture), or stay an implementation detail free to change?

4. **Concerns**

1. **Major — the two-axis settlement is stated as fact but is unimplemented, untracked, and unwitnessed.** §Settlement (lines 159–168) says the durable row "records" the effect-may-have-executed fact; a repo-wide search finds no such field anywhere, the reference pattern's `settleReply`/`cancelReply` persist only the single cause enum (`handlers.mjs:105–125`), the fixture's `requiredSettlementKinds` is single-axis (`protocol.v0.json:78`), the acceptance section (lines 244–260) has no bullet requiring it, the author-obligations list (lines 154–157) enumerates exactly three obligations and omits this fourth non-host-enforced one, and the implementation-gaps section does not mention it. There is also no defined channel by which the pattern learns "host-provable initiation" for the timeout-before-metadata case (the host knows, the authored mutation does not). Resolve by: rephrasing to "must record" with a named gap entry, adding an acceptance bullet (e.g. cancelled-after-initiation and timed-out-after-initiation rows carry the fact; pre-initiation `failed` does not), adding it to the author obligations, and deciding whether the host exposes an `initiated` fact on stream diagnostics so the axis is host-derived rather than author-inferred.
2. **Moderate — keyed non-GET classification deviates from the stated rule.** The RFC (lines 171–175) says that for a non-idempotent request any transport failure not provably pre-initiation is `ambiguous`, and that ambiguity "strictly over-approximates"; open question 2 says provider recognition of a key is an authored assertion. But the local host classifies any transport failure on a request that merely *carries* an idempotency key as `UPSTREAM_FAILED`, never `AMBIGUOUS` (`src/server.rs:1296–1302`). An unrecognized key on a POST whose effect executed gets `failed`, silently dropping exactly the uncertainty this revision set out to preserve. Resolve by either documenting that supplying a key opts the request into idempotent-class classification on the author's assertion (and accepting the consequence), or emitting `AMBIGUOUS` and letting the keyed author retry per the retry rule.
3. **Moderate — the stated 10/s ceiling is enforced as a 100 ms minimum inter-commit gap, which is stricter than a rate.** Both the host fence (`src/server.rs:1056`) and the reference row throttle (`handlers.mjs:78`) refuse any commit within 100 ms of the previous one, so a burst-after-stall pattern well under 10/s is refused — a real authoring trap given the doc's own guidance to coalesce. The RFC should state the enforcement shape (minimum spacing, not a rolling-window budget) since authors must write `shouldFlush()` against it. Resolve with one sentence in §Diagnostics or §Surface defining the enforced form.
4. **Minor — "the frozen fixture (chunks every 80 ms)" (lines 69–70) attributes a witness-implementation cadence to the fixture.** The fixture pins 16 chunks over at least 800 ms (`protocol.v0.json:70–72`), i.e. a ≥50 ms mean; 80 ms is the witness server's choice (`local-streaming.mjs:333`). The substantive claim survives (even 50 ms cadence trips the fence harder), but the attribution should say "witness" or "at the fixture floor, up to 20 chunks/s."
5. **Minor — cancel idempotence is scoped to once-open cursors.** `cancel()` on a wholly unknown stream id errors `SNAPBACK_ACTION_STREAM_INVALID` (`src/server.rs:1445–1450`); the bridge reader makes this unreachable from application code, so the §Surface claim holds app-visibly, but the host-op contract wording would be exact with a one-clause caveat.
