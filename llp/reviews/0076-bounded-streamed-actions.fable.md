The narrow v1 profile — a pull-driven reader subset instead of a full `ReadableStream`, hard byte/time/rate ceilings, settlement as durable rows rather than streamed responses — is the right shape for Snapback's authority model, and the document is disciplined about what it is not (no client streaming, no exactly-once, no durable cursors). Doc/code agreement is substantially real, not aspirational. The shared Ibex/Workerd reader surface exists (`packages/snapback-harness/ctx-bootstrap.js:804-890`), both hosts implement the bounds with identical constants (`src/server.rs:760-764`; `cloudflare/src/coordinator.js:74-79`), the capability predicate is exact and conjunctive (`src/manifest.rs:3031-3032`, matching LLP 0058:316), the claimed diagnostic codes exist and are emitted at the stated operations, and both witnesses run the real action → nested mutation → commit → native live-push path with a second observing client and a blocked negative actor (`demos/competitive-checkpoint/tests/acceptance/local-streaming.mjs:100-138`). 5. **Suggestions**

- State explicitly that the late-effect fence is layered: the host closes cursors and fences via generation/abandonment, while *terminal-settlement* fencing is the pattern's in-transaction responsibility — so an authored progress mutation that skips the terminal-row check forfeits that guarantee. - The `Idempotency-Key` header injection (`src/server.rs:1274-1281`) is worth one sentence in §Surface: the key is not merely metadata; it is forwarded to the provider unless the author set the header explicitly.

The document's own three open questions (reader-surface width, machine-checkable provider idempotency declarations, durable-cursor persistence) are the right ones. In addition the author must decide:

- Is the progress pattern *going to be* generated (making "generated" a commitment with an owner and an LLP 0065 fact-class story), or is authored-under-authority the v1 answer? This decision resolves Concern 1 and determines who owns the fence guarantee.
- Should capability manifests carry exact limit values (Concern 2), given that a later profile "may widen them only prospectively" — without published values, a consumer cannot detect which profile a target enforces.
- Is `SNAPBACK_REPLY_PROGRESS_RATE_EXCEEDED` the permanent name for a host-level fence, or a v1 compromise to be renamed before the code becomes load-bearing in receipts?
- Does the 4-open-cursor cap become part of the frozen v1 profile (and the 0075 fixture), or stay an implementation detail free to change?
