## 1. Diagnosis

A lazy merge really is two phases (`read.rs:807–880`). Opening scans the lane source then `scan_prepared`s one batch per lane (`841–848`). Draining pops the heap, optionally refills, repeats (`854–871`).

**Emissions before the first failed refill, with opening uncut.** The heap invariant holds: every non-exhausted lane has a head, so each emit is the current merge-minimum. De-dup (`seen` at `856`), further `matching` terms (`591–597`), `filter` (`625–635`), and expiry (`585–588`) all happen **inside** `scan_prepared` before a row becomes a head, so they do not reorder drain emits. The `batch = take+1` branch (`840`) only prefetches; it does not emit.

**Emissions before the first failed refill, with opening cut.** The opening loop does **not** stop on `capped_at` (`841–848`). A cut lane gets a short buffer and `done = rows.len() < batch` (`843`) — `done` is then a lie (`865` is the same lie on refill). Drain still pops whatever heads exist. Those emits **can** be preceded, in merge order, by an unopened lane. That is exactly the comment on `merge_can_continue` (`796–801`). D is right to gate on `opened_all`.

**`done` from a cut short read.** `scan_prepared` returns fewer than `batch` visible rows when the meter cuts while skipping expired/filter-rejected/unmatched rows (`579–581`, `585–597`, `633–634`). `merge_lazy` treats that as exhaustion. Today that feeds the out-of-order drain. D must key off `capped_at`, not `done`.

**Equal keys.** `MergeHead` breaks ties by **lane index**, not `id` (`read.rs:31–40`). Resume is `Bounds.after` on the suffix only (`rows.rs:65, 103–110`), exclusive of that suffix. `lazy_merge` allows a total-unique index that does **not** end in `id` (`rules.rs:91–95`). Two live rows in different lanes can share a suffix; popping the higher lane and resuming `after` that suffix **skips** the other row. Paved `byAuthorTime: author, at, id` / `scope, words(..), order, id` hide this; the design’s sentence “ties are broken by `id` through the index suffix” is not what the code does. This already applies to **uncut** lazy `next` (`875–876`). D inherits it.

**Word cut is not a drain cut.** `word_cut_at` is set during discovery (`425–428`), i.e. opening. D correctly leaves it alone.

So: the diagnosis is right about *why* drain-cut is a dead end today — (a) the loop keeps popping after a failed refill (`863`: refill gated on `capped_at`, loop not), (b) `merge_can_continue` does not distinguish phases. It is wrong to treat “the uncut-page argument” as already watertight.

## Findings

### F1 — Critical — D §2 / O §3.3 — `read.rs:873–876`

**Scenario.** Fixture in acceptance 1: second term matches once in 2,000, meter cuts during a refill, page length `< take`. `has_more` is set only when a unique head is popped **and** `page.len() == take` (`856–857`). A drain-cut page therefore has `has_more == false`. Continuation is `merge_can_continue() && has_more` (`875`). Relaxing only `merge_can_continue` still yields `next: None`. D is a no-op on the case it exists for. The same conjunction blocks O’s “window exhausted → next window” token (`has_more` is false there too).

**Fix.** Replace `has_more` as the sole continuation bit. Mint `next` from §2.3 / §3.3 (last key, or next-window token) even on a short or empty-of-this-window page. Keep `has_more` only as “this window still has rows” for the inner-page case.

### F2 — Critical — O §3.3–3.4, §5 item 1 — `read.rs:841–848`, `rows.rs:103–110`

**Scenario.** Search walk, window `(start, end]`, inner `values = K` (newest-first). Viewer joins chat `M` with `start < M ≤ end`. Re-open discovers `M` and opens it `after K`. Every message in `M` newer than `K` — historical rows the viewer may now read — is excluded by exclusive `after`. They are not duplicates of anything already returned. The walk never yields them. Design text says “never a skip”; “restart after a membership change becomes unnecessary”; acceptance 5 asserts no skip. All three are false. This is not “a concurrent insert above a single-lane cursor”; joining **adds a lane of pre-existing rows**.

**Fix.** A lane that was not in the previous request’s opened set is opened **from the top**, not `after values`. Duplicates of already-returned ids are removed by `id`. State that membership change can disorder the window (it already can). Do not claim the search card’s restart rule is gone.

### F3 — High — O §3.5, ruling 3 — `engine/mod.rs:718–726`, `read.rs:796–802`, `runner.rs:111–116`

**Scenario.** 5,000 sparse lanes. Reserve closes the window after N lanes. Those N drain **inside** budget (`capped_at` is `None`, `word_cut_at` is `None`). Ruling 3 and §3.5 still want `complete: false, cut: 'meter'` and a v3 `next`.

`QueryOutcome.complete` is `capped_at.is_none() && word_cut_at.is_none() && !non_uniform && …` (`mod.rs:721`). `read_cut()` emits `Meter` only if `capped_at` is set (`runner.rs:113`). `merge_can_continue` is false if `capped_at` is set (`read.rs:801`). There is no window bit.

- Set `capped_at` synthetically → `merge_can_continue` withholds `next` → O is dead.
- Don’t set it → the page is `complete: true, cut: null` with a next-window token → ruling 3 is broken and `complete: true` plus `next` is a new shape.

The same fight exists for `word_cut_at` when the 32-word rule closes a window that should continue.

**Fix.** Add an internal “windowed / more windows” flag (not a new `Read` field). `complete` is false when it is set; `cut` is `'meter'` or `'words'` as §3.4; `next` is still minted. **Do not** reuse `capped_at` or `word_cut_at` as that flag. Write the new `merge_can_continue` predicate in the design: uniform, and (`has_more` in this window, or drain-cut with `opened_all`, or more windows), independent of a synthetic meter cut.

### F4 — High — Disclosure §5 item 4, mixed query — `read.rs:550–554, 796–802`, `mod.rs:717–726`

**Scenario.** `query q(): { feed: merge … after c last 20, other: t[k] }` where `t[k]` is non-uniform. If the merge runs **first**, it records `next` while `non_uniform` is still false (`read.rs:874–876`). The later scan sets `non_uniform` (`553`). `next_cursor()` still returns the merge token (`mod.rs:717`). Server `read_cut()` then withholds the reason (`runner.rs:112`). Observables: `complete: false, cut: null, next: present`. Presence of `next` is exactly the channel W2R1m closed (`llp/3000.007` §20.3, “review round 1, lane W2R1m”: non-uniform class withholds `next` even within budget so hidden rows cannot change cursor presence). Design §5 claims “no `next`, `cut: null` on every path.” That is true only if the non-uniform read runs first.

**Fix.** At `next_cursor` / outcome build, if `non_uniform && !device`, force `next: None` and `cut: null` regardless of what the merge recorded. Add the execution-order pair to §7.8.

### F5 — High — O §6, termination — design §6 bullet 3

**Scenario A (2-cycle).** Token `T1` opens a window, emits nothing, shrinks, returns `T2 ≠ T1`. `T2` emits nothing, must not return `T2`, returns `T1`. The rule “≠ the token this request was given” is satisfied; the walk does not terminate.

**Scenario B (skip the rest of L).** Window of one degenerate lane (expired/filter run longer than the examined ceiling). §6 says no `next`. Every later lane is dropped. That is a skip of readable rows, and it is not in the §6 list as a skip (it is listed as a dead end of **that** lane).

**Fix.** Give tokens a well-founded order and require progress in that order: source `start` strictly advances in L, or `end` strictly shrinks, or `values` strictly advances in merge order, or `next` is absent. On an empty page whose first opened lane produced no head, **advance `start` past that lane** and continue (new token, not a death of the walk), unless that lane is the last of L. Reserve “no `next`” for “this lane is the last of L and produced nothing.”

### F6 — High — D §2 correctness — `read.rs:31–40`, `rules.rs:91–95`, `rows.rs:103–110`

**Scenario.** Index `unique byRoomTime: roomId, at` (legal `lazy_merge`). Two rooms, messages at the same `at`. Drain emits room 1’s row (higher lane index wins), meter cuts on refill, `next = [at]`. Resume `after [at]` on every room skips room 2’s row at that `at`.

**Fix.** State D (and uncut merge `next`) only for a suffix that uniquely identifies a row (`id` in the suffix, which the paved indexes already have). Alternatively put the extra stored trailing `id` (`rows.rs:126–129`) in the merge token. Do not claim the uncut argument already handles ties.

### F7 — High — SDK §4 fill — `react.tsx:85–107`

**Scenario.** Fill follows `next` on short cut pages, cap 8. If that counter resets on every `notify()` (live re-answer of a still-short page, or a 2-cycle of tokens from F5), the hook issues another 8 requests, forever, without `loadMore()`. Design says “rows gathered since the last `loadMore()`” but does not bind that to a ref that **ignores** live snapshots.

**Fix.** Arm fill only from mount / `loadMore`. Live `notify` must not re-arm. Count **attempts**, not only row-producing responses. Keep the cap at 8.

### F8 — High — SDK §4 discharge + ruling 3 — `react.tsx:119–144`

**Scenario.** Multi-window walk finishes; discharged pages contribute nothing to `complete`; last page is `complete: true`. `getSnapshot` concatenates window A then window B (`131`). A newest-first screen renders older A rows above newer B rows with `read.complete === true`. LLP 3000 §7: `complete` is a class of the answer, not “the walk’s iterator is done.” Ruling 3 forces this. A second case: page 1 live-updates, same `next`, more / different rows; reconcile keeps the suffix (`99–102` only drops on `next` change); last page still `complete: true`; aggregate is `complete: true` with a stale tail.

**Fix (design, given the ruling).** Document that `complete: true` on this walk means “no further page,” **not** “the concatenated list is a complete ordered merge.” Advise Q4: prefer `complete: false` on every windowed page and end the walk by `next == null` only — that matches §7 and does not require `usePage` to lie. If the ruling stands, `usePage` should still expose a seam bit or keep `read.complete` false when more than one window was concatenated; otherwise every existing `complete` consumer is wrong.

### F9 — Medium — Disclosure §5.3 expired — `read.rs:585–588`, §17

Expired rows in a **uniformly readable** prefix are charged (`585–588`) and can move a reserve edge. They are absent to every reader (LLP 3000 §7 expire card; `read.rs:212–216`). That is sweep lag of the viewer’s own prefix, the same in both paired worlds that differ only on **hidden** rows. It is **not** the §17 mutation abort bit (hidden vs empty at `Cut::Abort`). The sentence “the count of unswept expired rows … is unprotected” is too broad for queries: it is not a cross-viewer channel. **Fix:** rephrase as sweep lag of a prefix the viewer could already read while the rows lived; keep the paired-world test; do not treat expire-count as a §17 hole.

### F10 — Medium — False lane vs absent at a probe ceiling — `read.rs:73–83, 564–566`, design §5 item 1

A uniformly **false** lane still runs `prefix_verdict`, which charges the full static `rule_probes` allowance (`82`) and can set `capped_at` on that axis. An absent lane-source row never opens. Reserve ignores probes (`§3.2`), but a real probe cut is `cut: 'meter'` for the uniform class (§20.17). Adjacent to a window edge, with the meter already near the probe ceiling (design’s own paired-world bullet), `end` / presence of `next` can differ between “source row present, lane denied” and “source row absent.” The source row itself is viewer-visible, so this is a **cost** channel on a visible membership, not a hidden membership. **Fix:** charge a false uniform lane the same examined/index/step attempt as an empty true open (the §17 “one examined before verdict” idea, for this path only), **or** include `rule_probes` in the reserve so the edge does not depend on an unreserved axis. Add this pair to §7.8.

### F11 — Medium — Forged / replayed v3 token — design §3.2, `cursor.rs:40–54, 80–104`

Unauthenticated tokens cannot widen the readable set: discovery still runs on the viewer’s lane source and each lane is still authorized. `src` bound to the evaluated prefix, refused with `Scope`, is the right analogue of v2 (`cursor.rs:50–51, 93–95`). Gaps: (1) a forged `start`/`end` inside the viewer’s source **skips or reorders the holder’s own rows** (wrong walk, not a leak); (2) `end: "open"` with a chosen `start` lets the client ask the server to re-choose a window every time — per request the meter bounds it; a non-React loop is unbounded in the same way any pager is; (3) not binding generation matches v1 merge tokens (§20.3) and is acceptable. **Fix:** refuse `end < start` and mistyped positions (already said); also refuse a token whose `src` table/index is not this merge’s lane source (not only the merge descriptor); state explicitly that a forged window is allowed to starve the forger and is not allowed to increase per-request work above the ordinary meter.

### F12 — Medium — `cut: 'meter'` / `'words'` vs §20.17

§20.17 already discloses the precise cut on uniform server reads. Forcing `cut: 'meter'` on a window page that still has budget (F3) discloses **windowing**, not a real cut. `cut: 'words'` plus `next` discloses the same 32-word fact as today, plus continuation. Neither is a hidden-row channel. The author-facing lie (“I was meter-cut at 200/8192”) is the cost. **Fix:** keep the ruling’s wire shape if it stands; in `dev` print `window` vs actual `capped_at` so the bar does not teach a false cut. Do not put a third `ReadCut` value on the card (ruling 2).

### F13 — Medium — Charge order §5.7

Interleaving discovery with opening changes which axis hits first when the meter is already near a ceiling (an earlier read in the same query — the design’s own pair). Totals when **one window suffices** match only if every lane is still opened; the **order** of charges does not. Pinned card counts (feeds “82 examinations and 21 probes”) will move. I do not see a paired-world **hidden-row** guarantee that depends on “scan the whole source, then open.” **Fix:** re-measure as planned; add the near-ceiling mixed-read pair; do not claim totals-and-order both unchanged.

### F14 — Medium — SDK de-dup — `react.tsx:131`, design §4.3

Unconditional de-dup by `id` across held pages is right for this walk and for overlapping live pages. It will collapse cross-table projection copies that **intentionally** share an id (§20.3: “IDs identify an item across projections”). `usePage` is typed as one `Query` returning `R[]`; those copies only appear if a single op returns both. **Fix:** de-dup only when `id` is present; document that a page op must not use one `id` for two list entries. Existing search/feed consumers should be fine.

### F15 — Medium — Device fallback dependency — `local.ts:852–853`

Every windowed page is `complete: false`. Today the device bounces to the server on `complete === false` (`local.ts:853`). The design assumes §20.22.1 item 3 (fallback on `unknown`). If O lands first, every windowed local page pays an extra RTT for the same answer; if remaining meter differs across hosts, windows can diverge. **Fix:** list A3 as a hard dependency in §1/§6, or key this path on `unknown` in the same landing.

### F16 — Low — `end: null` vs `"open"` vs position

JSON-distinguishable. Unreachable-as-v3: whole-L one window should stay v1 (`§3.2`) — good. Ambiguity: `end: null` (“later lanes still belong”) vs `end: last-key-of-current-L` disagree after a new source row **after** the old last key. Replay of a stored `end: null` last-window token with `values = K` then skips that new lane’s rows newer than `K` (same family as F2). **Fix:** treat a source row that sorts after a previously observed end of L as a **new lane** (F2 rule), even when `end` was `null`.

### F17 — Low — Fixed `[viewer]` + generated Following lanes — design §3.1, §3.5

Fixed lanes first, only in the window whose `start` is `null`, is correct. They stay in window 1 for every inner page (`start` stays `null` until that window is exhausted). Subsequent windows are later followees from their top — the intended seam. A feed that must be globally ordered must still fit one read. No change except to write that on the feeds card with the landing.

## 2. D stopping rule

**Necessary.** After a failed refill of lane A at key `K`, any later pop from lane B can sit **between** `K` and A’s unread head. Stop before that pop.

**Not sufficient to resume.**

- F1: no `next` on the short page.
- F6: resume `after K` skips an equal-suffix row in another lane.
- Re-open: “the first emission after opening needs no read” (`§2`) is true **inside** a request. The next HTTP/wasm call re-runs opening (`841–848`). ~2 examined per lane plus the source scan. If that does not fit, `opened_all` is false and D dies. Example: 4,000-lane window, request 1 drain-cuts after one emit; request 2 opening-cuts; no `next`. With O, shrink saves this; **D alone does not**.

**One emission per request.** If every continuation still `opened_all`, each request emits ≥1 unique row (empty `seen`, first unique always emits) and the walk ends in ≤ N_rows requests. If any continuation opening-cuts, it does **not** terminate as a complete walk. Acceptance 1’s sparse second-term case (few lanes, opening cheap, drain expensive) **does** terminate. State that as D’s scope.

## 3. Windows (remaining)

**Shrink** of `(start, end]` to `end'` when re-open breaches reserve: lanes moved out, re-opened from the top, duplicate rows already returned, no skip of those lanes’ unread-after-`K` rows. That half is sound. Combined with F2 it is not “never a skip.”

**32-word close** as a window boundary: one scope’s words 1–32 then 33+ next window, adjacent. Grouped-by-chat still keys by room. Faithful to “at most 32 words **a page**” (`NOT-DOING.md:36`). A 1-letter term over 1,000 wordy chats becoming ~1,000 requests is a product problem; it is not a disclosure bug.

**Single-scope `matching` continuation (Q3).** Advise **yes, continue**. `scan_words` is already a merge (`read.rs:437–448`). Leaving `cut: 'words'` terminal only for non-merge matching breaks the “every admitted read completes or continues” invariant for the first search a builder writes (`messages[room] matching q`). Per-request work stays ≤32 word lanes. Switch-off is a one-line policy; default-on is the one that matches ruling 26’s spirit.

**Q5.** Advise **no** in this design. Meter-bounding word lanes inside a merge is a NOT-DOING move and a different cost model (one page merging thousands of word lanes). File it as a later question; do not smuggle it in.

## 5. 32-word limit — advice

Keep the constant as a **per request / per window** cap, not a per walk cap. That is what NOT-DOING says. Continuing the walk is the feature. Do not raise or remove 32 here.
