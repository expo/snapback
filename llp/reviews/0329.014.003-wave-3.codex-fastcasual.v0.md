Required indexes are the obvious unique identities plus: store/item/active; menu window by `(store,item,from)`; availability by `(store,targetKind,targetId)`; slots by `(day,slotStart)`; cart lines by `(cart,state)` and reverse projection by `(store,targetKind,targetId,state)`; cart ops by `(device,seq)` and `(cart,resultVersion)`; orders by host/time, store/state/fire, and slot; station queue by `(store,station,isRemake,promisedAt,firedAt)`; exceptions by unresolved/deadline; outbox by `(store,state,nextAttemptAt,sequence)`; inbox by `(store,posSeq)`.

Rule macros below expand to all four effects. `Ø` means declared `never`.

- Public catalog/config tables: `{read: public(reason), insert: brand||system, update: brand||system, delete: Ø}`.
- Availability state: public read; staff-at-store or scoped system insert/update; delete `Ø`. Events expose only to staff/brand/system and are append-only.
- Customer/guest: self/support/system read; self/system insert; self/support/system update; delete `Ø`.
- Join target: public exact-get disclosure; host/system insert/update; delete `Ø`. Participant insert additionally proves `next.participantId===viewer` and `joinTarget(next.joinTokenId,next.cartId)`. Guest-principal issuance remains a runtime gap.
- Slot rows: public read; manager/brand/system writes. Holds are host/system-readable and writable.
- Cart, participant, line, modifier, op, cursor: active participant/system read; owner or host/system writes; delete `Ø`. `cartOp` is append-only. Freeze and field-level authority are repeated in update rules.
- Quote and children: host/system read and insert; update/delete `Ø`; `quotePayer` additionally permits only its payer.
- Orders/lines/exceptions: host, relevant payer, store staff, or system read. Writes are limited to the same authorized actors; immutable snapshot fields bind every update.
- Claims/stations/devices/queue projections: store device, manager, brand, or system read/write; claim history is append-only.
- Payment/refund: payer/support/system read; processor system writes payment status; authorized payer/manager/support may insert a refund request; only system updates refund status.
- Loyalty: owner/support/system read; append-only entries; direct writes to maintained balance are `Ø`.
- Promotions: public read; brand/system writes. Redemption is customer/brand/system-readable and append-only.
- POS tables/cursors/outcomes: scoped system only. Audit: store manager/brand/support/system read; actor/system insert; update/delete `Ø`.
- Generic notification insertion is system-only; otherwise opaque payload and recipient fields would allow confused-deputy writes.

**Ops 1–4.** `availableAt` uses only normalized, bounded rows:

```ts
function availableAt(db, storeId, itemId, t, selected) {
  const si = db.get(storeItem.byStoreItem, [storeId, itemId])
  if (si === null || !si.active) return false

  const windows = db.scan(menuWindow.byStoreItemFrom, [storeId, itemId],
    { order:'desc', take: W, range:{ lte:t } })
  db.require(!windows.hasMore, 'MENU_WINDOW_BOUND')
  let scheduled = false
  for (const w of windows) if (w.from <= t && t < w.to) scheduled = true
  if (!scheduled) return false

  const itemState = db.get(availabilityState.byStoreTarget,
    [storeId, 'item', itemId])
  if (itemState !== null && itemState.eightySixed &&
      (!itemState.hasUntil || t < itemState.until)) return false

  for (const optionId of selected) {
    const s = db.get(availabilityState.byStoreTarget,
      [storeId, 'option', optionId])
    if (s !== null && s.eightySixed && (!s.hasUntil || t < s.until)) return false
  }
  return true
}
```

`menuForPickup` declares `readTime:{granularityMs:5000}`, scans `storeItem.byStoreActive` with `take:I`, refuses `hasMore`, and calls the helper. UTC `menuWindow` expansion is required; v0 cannot calculate local weekday/time.

Direct join against private `cart` is refused. The closest plan exact-gets a public, unguessable `joinTarget`, inserts the participant with that token recorded, advances cart version, and appends `cartOp`. Guest issuance and online-only enforcement remain runtime gaps. `leaveGroup` flips `active=false`, advances version, and leaves lines intact.

`applyCartOps` takes a typed list with `max:A`, checks `deviceCursor`, and records rejection rows rather than aborting when the cart is frozen. Modifiers use `cartLineModifier.lastRemoveVersion`, so remove-wins is a point read, not a JSON-history scan. `setSlot` scans all `C` capped lines and re-runs `availableAt`. The fixed design never defines conflict rules for `setNote` or `setFulfillment`; those branches cannot be completed without a product ruling.

`slotsForDay` scans at most 56 slots and point-reads `heldUnits` and `committedUnits`. `spotsLeft=max(0,capacity-held-committed)` is returned under the explicit public disclosures.

**Ops 5–7.** `beginCheckout`:

1. Reads the cart and exact capped line/modifier set.
2. Branches to stored rejected results if unavailable; it does not use a visibility-filtered count.
3. Reads maintained slot sums, requires `units<=capacity-held-committed`, inserts `activeSlotHold`, and appends its event.
4. Scans at most 56 alternatives.
5. Evaluates only normalized, compile-time promotion variants. Arbitrary `rule:json` remains refused.
6. Uses `promoConsumed`, a bounded caller-scoped redemption scan, and `loyaltyPoints`.
7. Inserts normalized immutable quote rows and a durable payment-intent request.

`placeOrder` exact-reads normalized quote rows, compares `payerCount===authorizedPayerCount`, rechecks availability from sources, reads global promotion counts, inserts redemptions, inserts the order and immutable lines, deletes the active hold, sets `capacityCommitted=true`, and freezes the cart as placed—all in one mutation. Failure calls an inlined cancellation helper; named mutation-to-mutation composition is not specified.

```ts
  db.insert(availabilityEvent, supersededEvent)
  return
}
db.insert(availabilityEvent, event)
db.upsert(availabilityState, key, _ => nextState)
db.insert(propagationJob, { sourceId:event.id, cursor:'', state:'pending', ... })
```

The same-transaction reverse fan-out has no corrected v0 form. A scheduled continuation processes `take:200`, persists the directional cursor, and reschedules until exhausted. Checkout and placement continue to gate on `availabilityState`.

**Ops 8–10.** Periodic global scans are rewritten as row-triggered schedules:

```ts
schedule(expireHold, { at:h => h.expiresAt, key:h => h.holdId, principal:'system' })
schedule(abandonCart, { at:c => c.lastActivityAt + 7*86_400_000,
  key:c => c.cartId, principal:'system' })
schedule(resolveDeadline, { at:e => e.deadlineAt, key:e => e.exceptionId,
  principal:'system' })
schedule(fireOrder, { at:o => o.fireAt, key:o => o.orderId, principal:'system' })
schedule(expireDeviceClaims, { at:d => d.lastSeenAt + 60_000,
  key:d => d.deviceId, principal:'system' })
```

Each re-reads durable state before changing it. Hold expiry removes `activeSlotHold`, writes history, unfreezes the matching cart, and requests processor voids. Fire inserts capped station projections. Claim expiry scans at most `Q` active claims for the device and preserves notes.

The station queue reads `stationQueueEntry` in exact rank order, then reads maintained `queueCount` and `upcomingCount`. Upcoming is schedule-flipped state, not `fireAt<ctx.now()+15m` inside a maintain.

Claim/bump/unbump/can’t-make/handoff/force-release are point mutations against `activeClaim`, order, and line. Bump compares maintained `doneCount` to `lineCount`, increments `readyGeneration`, and inserts the unique notification. All transition helpers, including exception resolution, must call the same readiness routine.

**Ops 11–14.** A POS effect first calls `reservePosBatch(take:50)`, sends each typed payload with its idempotency key, then calls `ackPos` or `failPos`. Webhook/poll effects call `ingestPosInbox`; `applyNextPosEvent` reads exactly `lastAppliedSeq+1` and stops at a gap.

Availability delegates to the bounded propagation design; price is a point update. Inventory remains refused: `Σ usage of orders unposted at external countAt` is an historical cross-table sum, not the current maintained unposted sum.

Exception substitution scans `S` offers and rechecks availability. Refund paths use maintained `refundReserved`. Proportional clawback is cumulative to avoid order-dependent rounding:

```ts
const target = divmod(payment.earnedPoints * totalSucceededRefund,
                      payment.amountCents).q
const delta = target - alreadyClawedBack
```

Cancellation scans capped order lines/payers, clears `capacityCommitted`, returns redeemed points, and applies the product’s eventual ruling for promotion consumption. Remake copies at most `C` explicitly selected lines and touches no slot, payment, loyalty, or promotion rows.

Capacity change scans no more than 56 slots. Closed-cart marking is another durable projection, never a truncated same-TX fan-out. Slot seeding is scheduled from precomputed `businessDay.seedAt`; local-calendar computation is not expressible. Points use at most 366 active daily `loyaltyBucket` rows per customer; expiry is scheduled per bucket rather than reconstructing an unbounded ledger nightly.

Required but absent hard operations are: `createCart`, guest-principal issuance, `arriveCurbside`, and a runner queue. `createCart` and arrival are bounded point mutations; guest issuance needs auth runtime; runner queue uses an indexed bounded projection. Quote, order, exception, loyalty, receipt, and notification reads are the paginated plans listed in §1.

Effects remain specifications rather than executable v0 code: §1 names the kind, but no syntax defines transactional invocation, credentials, retry state, or typed completion mutation.

V0 newly binds immutable snapshots, append-only journals, row authorization, uniqueness, and maintained disclosures across every language write. Conversely, it cannot reproduce the original design’s unbounded atomic fan-out, partial unique indexes, `skip locked`, local-calendar arithmetic, or historical inventory sum. Neither design proves exactly-once behavior outside the database.

The fixed `refund★`, `notification★`, and `posInbox★` declarations are internally inconsistent with later state/sent/outcome updates; splitting immutable core rows from mutable status rows is required.

### 7. Product changes

| product change | acceptable boundary | when it is a cheat |
|---|---|---|
| Make 86/cart/order marks a durable ≤5 s projection; keep checkout/place source checks synchronous | preserves safety and the stated notification latency | enqueue can be lost, pagination truncates, or placement trusts marks |
| Treat POS/push “exactly once” as one logical event plus mandatory downstream dedupe | provider/client honors the stable key | claiming one outbox row proves one external delivery |
| Add hard maxima for lines, participants, modifiers, payers, claims, substitutes, and edit batches | limits are explicit and refused before state is accepted | `take N` silently ignores already accepted rows |
| Return promotion consumption after failed capture, or redefine the limit as attempted placements | either choice is explicit in product copy | retaining both “release everything” and permanent consumption |
| State 5 s/60 s/5 min guarantees as fault-scoped SLOs with durable safety fences | outages delay notification but never permit an invalid commit | client-open clocks, lossy timers, or expired state remains committable |
| Restrict promotions to a finite compiled campaign vocabulary | brand operations accepts those campaign types | arbitrary `rule:json` remains advertised |
| Require POS inventory events to carry an app/POS causal watermark | vendor protocol can supply it | calling the current pending-usage sum “as of countAt” |
| Optional: owner edits a line; host may remove but not mutate it | UX promise changes accordingly | continuing to promise host-can-edit-anything |
| Optional: app becomes sole 86 sequencer and POS calls it | register cannot mutate independently during outage | POS retains a local writer while cross-clock ordering is removed |
| Replace guest link with authenticated invitation | no-account bearer joining is dropped explicitly | using this merely to avoid adding capability authority |

### 8. Where the design is wrong

1. **Op 7 skips a second shortage while an order is already in `exception`.** Its order scan includes only `placed|scheduled`. Confirm by 86’ing avocado, then chicken in the same unresolved two-line order; chicken receives no exception, violating invariant 2.

2. **Op 12 can leave an all-done ticket permanently non-ready.** It voids/substitutes and restores `scheduled|fired|inProgress`, but never runs Op 10’s readiness transition. Confirm with line A ready and line B `cantMake`; refund B. Both lines are terminal, yet no ready generation or notification appears.

3. **Capture-failure compensation contradicts invariant 5.** Op 6 routes failure through Op 12, whose cancellation deliberately keeps promotion consumption. Confirm when the 500th placement fails capture: the next eligible paid order is rejected as #501 even though the failed order was never charged.
