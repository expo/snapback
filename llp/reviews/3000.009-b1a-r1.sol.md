2. **[P1] A lost token-endpoint response is recorded as a definitive failure instead of uncertain work.**

   `authorizationCodeGrant`, token validation, JWKS failures, and transport failures are all inside one catch-all that returns `{ok:false}` ([identity.ts:267](/Users/ccheever/projects/snapback-worktrees/sb4-b1a-review-20260917/snapback4/packages/snapback4/src/identity.ts:267)). Because the callback resolves successfully, `ctx.step` durably records that false result as `done` ([server-steps.ts:62](/Users/ccheever/projects/snapback-worktrees/sb4-b1a-review-20260917/snapback4/packages/snapback4/src/server-steps.ts:62)); the handler then fails terminally.

   Demonstrable path: the provider consumes the one-time code and writes its token response, but the response connection drops. `authorizationCodeGrant` throws, the helper records `{ok:false}`, and the invocation neither parks nor preserves uncertainty. This is fail-closed, but it contradicts the stated uncertain-exchange behavior and LLP 3000.009’s requirement to park unqueryable, non-deduplicable provider outcomes ([LLP 3000.009:864](/Users/ccheever/projects/snapback-worktrees/sb4-b1a-review-20260917/llp/3000.009-general-purpose-backend.rfc.md:864)).

   The test provider covers an explicit `invalid_grant` response, not a response loss after code consumption ([identity.test.mjs:74](/Users/ccheever/projects/snapback-worktrees/sb4-b1a-review-20260917/snapback4/packages/snapback4/test/identity.test.mjs:74)).

3. **[P2] Restart recovery unnecessarily depends on renewed provider discovery.**

   Completion performs discovery before asking `ctx.step` for its persisted exchange result ([identity.ts:266](/Users/ccheever/projects/snapback-worktrees/sb4-b1a-review-20260917/snapback4/packages/snapback4/src/identity.ts:266)). Therefore:

   1. Exchange claims are durably recorded.
   2. `identityVerified` commits, but its response is lost.
   3. The worker restarts while the IdP discovery endpoint is unavailable.
   4. Discovery throws before the completed step can replay, so no mint occurs; three short retries can exhaust after the authorization code was consumed.

   The restart test exercises the lost verified-mutation acknowledgement but keeps the provider available ([identity.test.mjs:320](/Users/ccheever/projects/snapback-worktrees/sb4-b1a-review-20260917/snapback4/packages/snapback4/test/identity.test.mjs:320)). Thus it does not discriminate the recovery claim under provider outage.
