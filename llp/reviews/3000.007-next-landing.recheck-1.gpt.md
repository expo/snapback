## Remaining and newly introduced defects

### A. High — another execution of the same scan site erases an earlier lost page

Using the existing `items` schema, seed four rows in scope `0` and one in scope `1`, then call with `c = null`:

```quarry
query interruptedTwice(c: cursor ?):
  result = []
  for scope in range(0, 2):
    for i in items[scope] after c last 5 by byScopeN:
      result = result + [{ id: i.id, n: i.n }]
      break
  return result
```

The first scan materializes four rows; its loop returns one and sets `interrupted = true`. The second invocation uses the **same static scan site**, overwrites that entry with `interrupted = false`, and exhausts its one-row iterator. The query returns two rows, no cursor, and `complete: true`, losing three rows from scope `0`.

Evidence:

- Pages are replaced by scan-site key, resetting interruption: [read.rs:637](snapback4/crates/snapback4-core/src/engine/read.rs:637).
- A break marks the currently stored page: [runner.rs:221](snapback4/crates/snapback4-core/src/engine/runner.rs:221).
- Completeness examines only the surviving entries: [read.rs:644](snapback4/crates/snapback4-core/src/engine/read.rs:644).

This is a **remaining finding-4 escape**, on the server and both device stores. The new regressions execute distinct scan sites or one invocation of a site; none constructs this scenario. Loss must survive subsequent executions without incorrectly transferring ownership between their page instances.

### C. Medium — restoring setup after helper-return lowering does not restore the original IR or charges

```quarry

    return 1
  if true and true:

  return 3
```
