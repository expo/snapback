2. **High — result recovery proposal conflicts with accepted disclosure policy.** .002 §2 and acceptance 1 imply a replay returns the same historical result. Core `engine/receipt.rs` intentionally records/replays execution identity without `result` or `current`, even for scalar results: execution identity grants no historical read authority. The README's security paragraph is accurate, but contract.ts requires `result: R`, both clients read `json.result` and drop `replayed`, and the card repeats the promise. The existing ticket `20260914-snapback4-write-result-type-omits-replay-state.md` correctly identifies this. Preserve the server policy and make the client, hooks, examples and types represent result availability. Test fresh value and legitimate null, commit/lost acknowledgement/same-ID replay, queued terminal notification and revocation. Never repair this by retaining private results indefinitely.

3. **High — browser persistence failure needs an actual-host regression before claiming composition.** In web.ts, `device.call` mutates the live wasm device, `settle` drains its change buffer and then calls `persist.save`. A save rejection currently leaves the live instance ahead of durable state, with the drained changes gone; the next call is permitted because the chain catches the rejection. Initial `settle` and orphan adoption also occur outside the constructor cleanup block, so failure can strand the device/store lock. `cachedWasm` writes a URL pointer and bytes before validating them with the wasm initializer. These are source-inspection findings, not reproduced failures. Reproduce each through the real wasm host, then repair with a small explicit failure/recovery boundary. Do not add a full-store copy to every successful call as an unmeasured fix. Verify prior durable outbox preservation and that failed initialization releases owned resources.

4. **Medium — exact ranking is an acceptance problem, not another arithmetic feature.** The feeds guide now traverses up to 8192 candidates; the README explicitly says a page aggregate covers that page. The .000 adversarial winner outside the first 200 remains useful. Retain it and check coverage propagation when sort/slice reduce a page. A green small-seed Trending screen is insufficient evidence of exact ranking. Keep large-domain ranking on the existing maintained/materialized/native recipe; do not create a universal SQL surface to satisfy an unbounded example.

The existing scale witness calls a warm online reopen a reopen and combines constructor/sync; extend it to distinguish durable acquisition, a fresh-realm offline reopen, local query and send/settle where these are measured. Record actual rows/bytes and build/host identity. No new benchmark gate or invented universal target. .004 should use the actual-client seams changed here and a bounded disposable release/recovery experiment. Full independent builder grading, physical-device coverage, a real second application and disaster recovery objectives remain separately identified work; a panel cannot confer promotion by producing artifacts.
