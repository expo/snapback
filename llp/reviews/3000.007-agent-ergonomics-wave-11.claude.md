## Findings

### 1 — Critical. The published maintain silently drops every zero-like post; the recipe it replaces explicitly includes them

`snapback4/crates/snapback4-lang/src/guide/feeds.md:919-953` (the new block), against `snapback4/crates/snapback4-core/src/engine/maintains.rs:171-182`.

`apply_aggregate` deletes the target row when the count reaches zero, and never creates one for a group with no contributions:

```rust
let keep_zero = next == 0 && self.live_sum(maintain) && …;
if next == 0 && !keep_zero { … delete … return Ok(()); }
```

`live_sum` (`maintains.rs:120-122`) is true only for `Sum` over an expiring source. `trendScore` is a `Count`, so a `(postDay, postId)` group with no qualifying like has no row at all.

The card puts this four lines below the sentence that describes the recipe it is replacing: "ranks posts younger than 24 hours by their non-expiring like count, then post time and post id, **including zero-like posts**" (`feeds.md:911-913`). The handwritten recipe achieves that by creating a `ranked` row at post creation (`feeds.md:1012-1015`). The maintain cannot.

**Failing scenario.** A builder reads "**Prefer a `maintain` to this recipe wherever it fits**" (`feeds.md:919`) and ships the maintain form. On launch day 40 posts are created and nobody has liked anything yet. `trending` returns `[]`. The handwritten recipe returns the ten newest. The builder's Trending tab is empty and no diagnostic, note or card sentence explains why.

**Smallest fix.** Add one sentence to the cost paragraph at `feeds.md:949-953`: "A `count` maintain has no row for a group with zero contributions, so a post nobody has liked never appears; the handwritten table below ranks zero-like posts too."

### 2 — Critical. "has no principal-writable score … a real exposure a maintain does not have" is false for the block as published

`snapback4/crates/snapback4-lang/src/guide/feeds.md:949` and `:960`, against `feeds.md:931-941` and `feeds.md:975-984`.

The target is genuinely unwritable — `bind/program.rs:704-705` refuses any write to a maintained aggregate at compile time. That part of the lead's claim holds. The score, however, is not.

The maintain's group key `postDay` and its predicate input `isOriginal` are ordinary source columns on `likes`, and the block's `likes` is *more* permissive than the handwritten recipe's `likes` forty lines below:

| | maintain block (`feeds.md:931-939`) | handwritten block (`feeds.md:975-984`) |
|---|---|---|
| insert rule | `insert <- allow` | `insert <- .principal = viewer` |
| delete rule | *(absent → deny, `schema.rs:473-475`)* | `delete <- .principal = viewer` |
| cap | *(none)* | `cap 1000 by principal` |

`principal: principal` is an ordinary column; nothing ties it to `viewer` except a rule, and this block has none. `unique byPair: postId, principal` therefore bounds nothing an attacker controls.

**Failing scenario.** Following the card's own instruction that these facts "must be denormalised onto the counted row at insert" (`feeds.md:950-953`), the builder writes the obvious mutation `mutation like(postId: posts, principal: principal, isOriginal: bool, postDay: int)`. `insert <- allow` admits it. Mallory now calls it 5,000 times against a rival's reply with fabricated principal ids and `isOriginal: true, postDay: day(now)`. `maintain_one` (`maintains.rs:37-56`) charges `+1` per row; `trendScore[day(now)]` puts the reply at the top of Trending. Mallory can equally inject any old post into today's bucket by supplying today's ordinal. The handwritten recipe the card warns about cannot be attacked this way at all: `refreshRank` recomputes `score: likeCounts[p.id]` server-side from a table whose insert rule pins `principal = viewer`.

Note also that this is exactly the H4 requirement the lead claims to satisfy — "callers cannot supply arbitrary target keys or scores" (`benchmarks/runs/2026-09-16-snapback4-clique-astra-0.2.26/friction-review.md:310`). This form puts the target key *in caller-written data*.

For balance: the card's symmetric claim about the handwritten table ("`update <- allow` … lets any principal set any score", `feeds.md:957-960`) is also overstated. The client surface is queries/mutations/actions only (`contract.ts:119-171`), and no declared mutation in that block accepts a caller-supplied score. Both are latent permissions, not reachable exposures — but the card presents one as real and the other as absent.

**Smallest fix.** In the maintain block, change `likes`' rule to `insert <- .principal = viewer` and add `delete <- .principal = viewer`; replace "That is a real exposure a maintain does not have" (`feeds.md:960`) with: "A maintain's *target* cannot be written by a principal, but its score is only as trustworthy as the source rows' insert rule — pin `principal = viewer` and compute `isOriginal` and `postDay` from the post inside the mutation, never from a caller argument."

### 3 — High. A single saturated follower permanently caps a popular author at 50 followers, and the refusal is shown to someone who cannot fix it

`snapback4/crates/snapback4-lang/src/guide/feeds.md:245-268` (`addFollow`), `:354-368` (the card), `snapback4/crates/snapback4-lang/src/guide/codes.rs:18` (`why`).

Promotion fires only when `count(near) > 50` (`feeds.md:254-255`), and the refusal rolls the whole transaction back — including the `follows` insert. So after a refusal the author is back at 50 followers and still `shared: false`. The *next* follower re-triggers the identical promotion over the identical follower set and is refused identically.

**Failing scenario.** Author Q has 50 followers, one of whom is a dormant account at 32 pulls. Carol follows Q → `FEED_PROMOTION_PULL_CAP`. Dave follows Q → the same. Erin, Frank, every subsequent user → the same, forever, until that dormant third party unfollows a shared author. Q cannot exceed 50 followers. Previously this promotion succeeded and one reader missed broadcasts.

The refusal text handed to Carol says: "Have each saturated follower unfollow a shared author, then retry the refused follow with a new write ID" (`codes.rs:18`). Carol has no relationship with, and no authority over, the dormant account. The card (`feeds.md:361-366`) repeats the same remedy and never says that the author is now capped, or that the refusal will hit every future follower rather than only this one.

There *is* a discovery path the cards never mention: `follows` is `public` (`feeds.md:120`) and `pullCounts` is `public 'only the number of installed pulls is public'` (`feeds.md:141`), so a server-run query can enumerate the author's followers and read each one's `used`. Fifty-one reads identify the blocker.

**Smallest fix.** Add two sentences at `feeds.md:366`: "Until that follower frees a slot, every later follow of this author refuses the same way and the author gains no new followers. `follows` and `pullCounts` are both public, so the app can name the saturated followers to the author." Mirror the first sentence into `codes.rs:18`.

### 4 — High. When the caller *is* the saturated follower, the refusal gives the exact opposite of the correct repair — and no test covers it

`snapback4/crates/snapback4-lang/src/guide/feeds.md:250-259` and `snapback4/crates/snapback4-lang/src/guide/codes.rs:18`.

For an unshared author there is no pre-check on the caller: `require tryPull(viewer, authorId) else FEED_PULL_CAP` (`feeds.md:251`) runs only under `if a.shared`. The caller's own edge is inserted at `feeds.md:252` and is therefore one of the 51 edges the promotion loop walks at `:258-259`.

**Failing scenario.** Bob already pulls 32 shared authors. Author Q has exactly 50 followers and is unshared. Bob follows Q. The loop reaches Bob's own edge, `tryPull(bob, Q)` returns `false` (`feeds.md:237-238`), and the write fails with `FEED_PROMOTION_PULL_CAP`. The app shows Bob: "*Freeing only the caller's slot cannot fix another follower's full slots*". For Bob, freeing his own slot is precisely and solely the fix. Had Q been already shared, the identical state would have produced `FEED_PULL_CAP` with the correct advice.

The three new scenarios all seed the saturated reader as `reader00` or `reader49` and always trigger from `reader50` (`following_promotion.rs:9-28`), so this branch is untested on either store.

**Smallest fix.** In `addFollow`, hoist the caller's own lane out of the loop: after `insert follows …`, inside the `if not a.shared` / `count(near) > 50` arm, add `require tryPull(viewer, authorId) else FEED_PULL_CAP` before the `for f in …` loop (`tryPull` is idempotent for `readerId = viewer`, `feeds.md:230-232`, so the loop's later call costs nothing). Add a fourth scenario `scenario(case::TRIGGER, 32)` asserting `FEED_PULL_CAP`.

### 5 — High (pre-existing; wave 11 changed no client source). The bounded lock wait is not sufficient: it lets a *live sibling tab* adopt a just-closed tab's store and destroy the receipt the reloading tab needs

`snapback4/packages/snapback4/src/web.ts:305-318`, `:377-385`, `:100`, `:173`; `snapback4/packages/snapback4/src/local.ts:739-755`, `:1239`; the failing test is `snapback4/packages/snapback4/test/navigation-model.test.mjs:670-688`.

You asked me not to conclude flake from the reproduction attempts. I did not. Here is the gap, on the code.

`adoptOrphans` enumerates *every* `${name}:tab-` store (`web.ts:308`) — it cannot distinguish a dead orphan from a live sibling tab, because the only signal is the lock. For each, it polls the lock eleven times over ~220 ms (`web.ts:313-317`). Every open client runs an autonomous long-poll loop (`local.ts:1239` → `:739-755`), and every successful `apply` re-enters `adoptOrphans` (`web.ts:173`). When adoption succeeds, the write-history is *moved*: `keep_write` copies it into the adopting device (`web.ts:377-381`) and the source store is then deleted (`web.ts:385`).

**Failing scenario (matches the observed failure exactly).**
1. `t=0` the secondary tab's `send` lands on the server (`navigation-model.test.mjs:673`).
2. `t≈5 ms` the **primary** tab's long-poll returns, `apply` succeeds, `adoptOrphans` runs. It sees the secondary's live store `name:tab-S`, fails to take its lock, and enters the 220 ms poll.
3. `t≈15 ms` `secondary.close()` (`:676`) → `store.release()` → `name:tab-S` is free.
4. `t≈20 ms` the **primary's** next retry tick acquires `name:tab-S`, copies `client:write-history` into the *primary's* device, and calls `persist.remove("name:tab-S")`.
5. `t≈25 ms` the reloaded tab opens (`:677`). `persist.others` returns nothing. There is no orphan left.
6. `reloaded.write(sent.id)` → `history.read` miss, not queued, miss again (`local.ts:1104-1115`) → `undefined`. The test's own 2-second retry loop (`:682`) cannot help, because the receipt is not late — it is in another store.

This explains every observed property: intermittent (the primary's poll window must straddle the close), passes in isolation and under the same glob (timing shifts), fails under a loaded 1,229-second suite (scheduling delays push the retry ticks across the close). In production it is worse than a test failure: a user reloads a tab, and the write they just made reads back as unknown in that tab while a different open tab silently holds the receipt.

Note the direction of causation. Before the wave-9 fix, a live tab took one shot at a sibling's lock and skipped immediately; it could never straddle a close. **The bounded wait is what created this window.** Lengthening it makes this failure *more* likely, not less.

**Smallest fix.** Stop *moving* terminal receipts. At `web.ts:384-385`, when removing an adopted orphan, first persist its `client:write-history` changes to a shared `${name}:receipts` store that every opener copies from at `web.ts:100` (bounded by the existing `WRITE_HISTORY_LIMIT = 256`, `writes.ts:9`). Receipt recovery then no longer depends on which tab wins a lock race. Outbox adoption can stay exactly as it is — that one genuinely must be exclusive.

### 6 — Medium. The maintain's stated costs are incomplete in four further ways

`snapback4/crates/snapback4-lang/src/guide/feeds.md:949-956`.

- **No retention bound.** `maintain_target` sets `expire: None` (`bind/schema.rs:590`) and the parser accepts only `read`, `by` and `online only` on a maintain (`parser.rs:459-503`), so a maintain target can never expire or be capped. `trendScore` keeps one row per `(postDay, postId)` that ever got a like, forever, while `trending` reads only `day(now)`. *Scenario:* after a year a mid-size app carries ~365 days of dead, publicly readable score rows that no query can reach. The `ranked` table this replaces expires at `post.at + 24h` (`feeds.md:1003`).
- **The window is the *post's* calendar day, and the query reads only today's bucket.** "`day()` is a calendar bucket, not a rolling 24 hours" understates this. *Scenario:* at 00:00:01 UTC, `trendScore[day(now)]` contains only posts created in the preceding second — Trending is empty every midnight. A post made at 23:50 that collects 400 likes at 00:10 is in yesterday's bucket and is unreachable by the query forever. The handwritten recipe's `p.at > now - 86400000` (`feeds.md:1008`) is a genuine trailing 24 hours. "Use the handwritten table below only when the window truly must roll" therefore mis-scopes the choice: for a trending feed the window essentially always must roll.
- **No unlike, and no offline/`complete` story.** `likes` in the maintain block declares no `delete` rule, so it defaults to deny (`schema.rs:473-475`) — the score is monotonic and a user cannot un-like. The section also says nothing about `complete`, `fresh: false` or `E_OFFLINE`, all of which the handwritten section covers carefully at `feeds.md:1040-1048`.
- **The bucket offset is unenforced.** `calendar()` supports `day(.at, 8h)` (`bind/maintains.rs:40-52`), which a real app wants for a local-time boundary. Because the app writes `postDay` itself, nothing ties the writer's offset to the query's. *Scenario:* the client writes `Math.floor(at/86400000)` (UTC) while the query later becomes `day(now, 8h)`; every bucket is off by one and Trending is permanently empty, with no diagnostic.

**Smallest fix.** Extend the cost paragraph to name the four: unbounded retention, the calendar-day-of-post window and what the query can therefore never show, the missing delete path, and that the denormalised bucket must use the same offset as the query.
