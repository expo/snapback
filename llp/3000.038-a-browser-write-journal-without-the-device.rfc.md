**Author:** Claude Opus 5.5 (for Charlie Cheever)
**Date:** 2026-10-12
**Revised:** 2026-10-12 (draft)
**Related:** [LLP 3000](./3000-snapback4.explainer.md), [LLP 3000.013](./3000.013-quarry-states-intent.rfc.md) §6 (custody), §6.2 (why this was deferred), §13.3 (a web client that never loses a click), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) §17 (receipts carry no history), §20.4 (W4a's synchronous journal; EA round 3, wait before admission), [LLP 3000.019](./3000.019-what-the-builder-still-wrote.rfc.md) §3.3 (pending intent presentation), [LLP 3000.023](./3000.023-answers-stay-on-screen.rfc.md) §3.4 (custody lifetimes), [LLP 3000.033](./3000.033-read-only-client-mode.rfc.md) (the read-only app)

## 0. Evidence and the author's ruling

Every app-farm wave since 0.4.16 has asked for a browser app that writes
without the device. LLP 3000.013 §6.2 records four waves: ten lanes in wave 1,
twelve in wave 2, twenty-one in wave 3 (twelve "fix first" votes, the largest
group), and 26–29 lanes per wave since. A bare browser `createClient()` and a
device-less `createApp` refuse every mutation with `E_ADMISSION`, so an app
with no synced table ships `webDevice()`: 2,147,888 B of wasm (648,672 B
gzip, measured on this branch's `scripts/build-wasm.sh`), a 24 KB worker and
56.7 KB of device glue, to hold no rows.

§6.2 assessed four paths and named path 2, "a synchronous online journal with
its own replay, held to §20.4's navigation witness and §6's epoch and store
fences", as the real fix. The author ruled on 2026-10-12:

> (b) a small JS-only write journal for schemas with no synced tables — same
> at-most-once guarantee, no offline queries — as a reviewed design.

This RFC is that design. It adds no wire form, no server change and no new
web artifact. The device path (`createApp({ device: webDevice() })`) is
unchanged.

## 1. What exists, and the one gap

A device-less `createApp` already owns a durable **online intent journal**
(`app-online.ts`, `app-journal.ts`): one JSON value per (backend, account),
`storeKey("writes", url, viewer)`, kept in the app's `sessionStore`. In a
browser with `localStorageSessionStore()` that store is IndexedDB (the session
authority, `session-authority.ts`) with a localStorage mirror, and every journal
transaction runs under a Web Lock on the journal key (`storeLock`). The journal
already provides, and this RFC keeps unchanged:

- **Admission before dispatch.** An intent (id, operation, JSON arguments,
  owner, store identity) is committed before the online transport may send it
  (`ownDispatch.before` binds and marks it dispatched first).
- **Same-id replay.** Reopening replays every pending intent of this account
  with its original id, in recorded order (`start()`); the server returns
  `replayed: true` for an id it already executed and never re-executes it
  (LLP 3000.007 §17; `engine/receipt.rs`).
- **Store binding.** Each intent is bound to the store identity it was
  admitted under; every mutation request carries `store_id`, and the server
  refuses a replaced store with `E_STORE_REPLACED` before execution or
  idempotency lookup. A journal that saw a replacement retires its unbound
  intents with an unknown-outcome refusal.
- **One known outcome per id** (I13), receipts without historical values,
  retirement ids that are never admitted again, damaged-record preservation.
- **Waiting before identity.** A call on an unidentified client waits in
  memory (15 s of identity I/O) before admission, as on the device
  (LLP 3000.007 §20.4, EA round 3). No intent exists before identity.

The gap is the commit. The journal transaction is asynchronous: a Web Lock,
then IndexedDB. `mutate` returns its promise before that commit, so a
same-turn navigation, a tab close or a renderer crash in that window loses the
click. Losing it never duplicates it, but "a web client never loses a click"
(LLP 3000.013 §13.3) is a stated guarantee, so a device-less browser app
refuses instead (`app.ts` `admit()`, `client.ts`'s `!dispatch.owner` refusal).

The device closes the same window with W4a's synchronous localStorage
journal (`web-journal.ts`), whose recovery admits into the device's IndexedDB
outbox. This RFC gives the online journal the same front end: a synchronous
localStorage capture whose recovery admits into the online journal.

## 2. The guarantee

For a `createApp` in a browser, without a device, whose writes this journal
admits (§3):

- **G1 — capture before return.** When `mutate` returns a promise whose
  `state` is not `"failed"`, the id, operation, arguments, account, store
  identity and session authority stamp are already in localStorage, written
  synchronously in the calling stack. (A call made before store
  identification waits in memory first, exactly as today and as on the
  device; G1 applies from the moment that wait ends.)
- **G2 — no loss across page loss.** After G1, a same-origin navigation, a
  reload, a tab close, or a renderer crash after the write reached the
  browser's storage service, leaves the intent recoverable. The next app that opens the same backend and
  account in this origin, in this tab or another, admits it into the online
  journal and sends it with its original id, unless the session that captured
  it has ended (G5).
- **G3 — at most once.** Every send of an intent uses its captured id and its
  captured store identity. The server executes an id at most once per store
  and answers a repeat with the stored receipt (`replayed: true`, no result
  values). A localStorage record is admitted into the online journal at most
  once: an IndexedDB transfer marker, committed in the same transaction as the
  admission, outlives the record.
- **G4 — same replay semantics as the device path.** A recovered intent
  settles as `sent` with `replayed: true` (or the stored refusal), without
  historical result values; `write(id)`, `onWrite`, `usePendingWrites` and
  `pendingIntents` see it exactly as an intent the online journal admitted
  directly.
- **G5 — session fences.** A record is admitted only if, under the session
  lock, the IndexedDB session authority still names the capturing principal in
  the capturing epoch from the same authority source. Otherwise it is
  cancelled. A live caller receives `E_AUTH`; a recovered record from an ended
  session is cancelled and counted in a console warning. A later sign-in
  never revives it (the same rule as the device, LLP 3000.013 §13.3).
- **G6 — refuse loudly.** If custody cannot be acquired synchronously the
  call is refused with `E_ADMISSION` in the calling stack (a fulfilled failed
  promise that also exposes `state`, `id` and `why`), with a site and a
  rewrite; nothing was admitted and nothing was sent; retrying the same id
  after repair is allowed. No path drops a captured intent without either a
  refusal to its live caller or a recovery admission.

G2's limits are the device's limits, because the capture mechanism is the
same: localStorage survives navigation, close and renderer crash once the
browser's storage service has the write (Chromium's renderer forwards
`setItem` to it without waiting for a reply); it does not survive clearing site data, and it
gives no promise across an operating-system crash or power loss before the
browser flushes its storage. Private windows keep localStorage for the life of
the private session only.

## 3. Selection

`AppOptions` gains one field:

```ts
/** Browser writes without a device: journal each click in localStorage and
 * send it through the server (no offline reads, no predictions). Chosen
 * automatically when the backend syncs no table; "online" also chooses it when
 * tables sync. Requires sessionStore: localStorageSessionStore(). */
readonly writes?: "online";
```

A browser `createApp` without `device` and without `readOnly` decides, once
per signed-in scope, before it publishes `signed-in`:

1. `writes: "online"` → the journal. No extra request.
2. Otherwise the scope reads `GET /schema` once with its own bearer. A schema
   in which no table has a `sync` clause → the journal. One or more synced
   tables → **refuse writes** with `E_ADMISSION` naming the synced tables and
   both rewrites: `device: webDevice()` for offline reads and predictions, or
   `writes: "online"` to write through the server only.
3. If that read fails (offline, refused), the decision is unknown: writes
   refuse `E_ADMISSION` with `retryable: true` ("the backend has not said
   whether tables sync"), and each such refusal starts one new read (single
   flight). The decision is not cached across reloads; `writes: "online"`
   avoids the read entirely.

The decision binds the scope. A schema that starts syncing while the scope is
open keeps the journal: the server stays authoritative, and the only thing the
app lacks is what it chose not to ship.

Preconditions, each refused synchronously with `E_ADMISSION` and a rewrite
when missing at the call: a session store with a synchronous reader and an
IndexedDB session authority (`localStorageSessionStore()`; the memory default
and custom asynchronous stores refuse, as on the device), and
`navigator.locks` (the journal's cross-tab serialization). `writes: "online"`
together with `device` or `readOnly` is a configuration error (`E_CLIENT` at
`app.writes`, through `ready`, like invalid `assets`).

Unchanged: the device path; Node and native online apps (no capture, their
existing journal); a bare browser `createClient()` (still refuses: it has no
session authority or journal; its refusal now names both `createApp` forms);
persona apps (§8).

## 4. Mechanism

### 4.1 Capture (synchronous)

`mutate` on the app's client reaches, synchronously and in order:

1. the app facade's existing synchronous session check (`app.ts` `admit()`:
   the mirror's epoch and principal, the scope's validity), now also the
   selection decision of §3;
2. `MutationIds.run` (id shape, JSON snapshot, input reuse);
3. if the store is identified (the ordinary case after opening; otherwise the
   §20.4 wait runs first and the capture happens when it ends), **capture**.

Capture writes one localStorage record and returns:

```
key:   snapback4-online-admission:<hex url>:<id>
value: { v: 1, key, runtime, seq, id, op, args, viewer, url, storeId,
         authority: { key, epoch, principal, source }, at }
```

`runtime` names this custody lifetime (§4.5). `seq` is one more than the
largest `seq` among this backend's records and this runtime's last capture.
`authority` is the same stamp the device journal records
(`AdmissionAuthority`: session key, epoch, principal, authority source).
Before writing, capture enforces the device journal's bounds over this
backend's records: at most 32 records, 256 KiB of UTF-8 keys and values, and
64 KiB for one record. Any exception (`localStorage` unavailable or throwing,
`QuotaExceededError`) or bound refuses the call with `E_ADMISSION` (G6).
Ids the online journal already holds durably (restored or recovered intents
being replayed) are not captured again.

### 4.2 Admission (asynchronous, under both locks)

The existing journal transaction becomes, for a captured call:

```
storeLock(journalKey):              // Web Lock, as today
  storeLock(sessionKey):            // Web Lock on the session custody key
    if !sameAdmissionAuthority(stamp, authority, viewer): cancel record; E_AUTH
    journal = read(journalKey)      // IndexedDB
    ...the existing admission body (previous intent, receipt, retired id,
       store observation, push pending)...
    journal.captured += id          // transfer marker, same transaction
    set(journalKey, journal)        // one IndexedDB commit, strict durability
remove record                       // after the commit
```

The authority check is the device's (`sameAdmissionAuthority`: a fresh
IndexedDB read of the session and epoch under the session lock; the mirror is
never authority). Lock order is always journal, then session; no existing path
takes the session lock and then the journal lock (session replacement,
logout, revocation and authority checks take the session lock alone), so the
order cannot deadlock across tabs. The commit sees the same branches as
today: an id already pending continues to dispatch (the server deduplicates),
an id with a receipt or a retirement id returns it. In every branch the
marker is added, so a surviving record can never become a second admission.

After the commit the record is removed. Markers are collected by any later
journal transaction once `localStorage.getItem(key)` is confirmed `null`, so a
failed removal keeps both the record and its marker, and the marker keeps
recovery from admitting it (G3).

If the commit throws (IndexedDB refused or aborted), the record stays. The
live call returns the existing `E_STORE` "admission outcome is unknown" with a
rewrite to retry the **same** id; the record is recovered before this
runtime's next admission and at the next open (§4.4). If the authority check
fails, the record is removed, or replaced by a non-executable cancellation if
removal fails (`{ key, cancelled: true }`), and the caller gets `E_AUTH`; the
app then rechecks its scope after the locks release, as the device path does.

### 4.3 Dispatch and settlement

Unchanged. Once admitted, the intent belongs to the online journal: dispatch
binds it to its store, the raw online client sends it with its id and
`store_id`, and settlement commits a receipt (no historical values) and
retires the pending entry. The capture adds no transport and no settlement
path.

### 4.4 Recovery

When a scope starts (`custody.start()`, after the session commit and the
`signed-in` publication), and before this runtime's next admission after a
failed commit, recovery runs:

```
storeLock(journalKey):
  records = this backend's records, valid shape, not cancelled,
            whose runtime is not live (§4.5) and not this runtime's in-flight ids,
            in seq order
  storeLock(sessionKey):
    journal = read(journalKey); collect markers whose records are gone
    for each record:
      if the journal knows the id (pending, receipt, retired id, marker):
        ensure a marker; remove the record                 // a stale copy
      else if record.viewer != this account:
        if sameAdmissionAuthority(stamp, authority, record.viewer) fails: cancel
        else leave it                                      // not ours to admit
      else if sameAdmissionAuthority(stamp, authority, viewer) fails: cancel
      else if the journal's retirement ids are saturated: cancel, report
      else: push pending { owner, id, op, args, storeId: record.storeId,
                           dispatched: false }; add marker
    commit once
  remove admitted and stale records
replay recovered intents with client.mutate(op, args, { id }), in seq order,
before this runtime admits new intent
```

A record from another account of the same backend can be cancelled by anyone:
epochs only increase and every account change advances the epoch, so a failed
stamp check never becomes true again. Authority read errors (IndexedDB
unavailable) cancel nothing; they are reported through `auth.why` and the
records wait for a later open.

Ordering: the recovered replays reach the online transport before any intent
this runtime admits after `start()`: new admissions wait on recovery's journal
lock, and a new call's dispatch additionally waits for the recovery replays to
reach the transport. Recovered intents keep capture order among themselves.
There is no cross-owner ordering promise between two live tabs, as today.

### 4.5 Many tabs

Each custody lifetime holds a Web Lock named
`snapback4-online-runtime:<runtime>` from its creation until it pauses (sign-out,
account change, close, store refusal). Recovery treats a record as live, and
skips it, while `navigator.locks.query()` lists its runtime's lock as held or
pending. A closed, crashed or reloaded tab releases its lock with the
document, so its records become adoptable by the next tab or reload that opens
this backend and account. Two live tabs never adopt each other's in-flight
clicks.

All journal and recovery transactions in every tab serialize on the journal's
Web Lock, so at most one transaction can observe a record as unknown and admit
it. If a runtime pauses with a commit in flight, another runtime may adopt the
same record concurrently; the journal lock orders them, the second sees the
intent or its marker, and both dispatch paths use the same id (the server
deduplicates; the journal's existing `previous` branch keeps one pending
entry).

### 4.6 Session and epoch changes

- **Logout or account change after capture, before commit.** The commit's
  locked check fails; the record is cancelled; the caller gets `E_AUTH`. This
  is the device's rule (a logout cancels an unadmitted record).
- **Logout after commit.** The intent is in the account's online journal and
  is retained through sign-out, replaying at that account's next sign-in, as
  online intents always have (CLIENT-AND-OPERATIONS, "Online `app.mutate` …
  retains uncertain writes through restart and sign-out").
- **A stale mirror** (Chromium can show a stale localStorage mirror after
  granting a Web Lock): the synchronous check may pass and the click be
  captured; the locked IndexedDB check refuses it before admission or
  transport.
- **Rotation** keeps the epoch, so it never cancels a record.

### 4.7 Store changes

Capture records the store identity the call saw (G1 needs an identified
store). Recovery admits the intent bound to that identity; the existing
dispatch guard retires it with `E_STORE_REPLACED` (unknown outcome, never
retried automatically) if the server now has another store. A record is never
rebound.

## 5. Why at most once holds

Write K for the localStorage record, P/R/T/M for the journal's pending
intents, receipts, retirement ids and markers (one IndexedDB value, one atomic
commit), S for the server's per-store receipt table. The life of one id:
(1) K written; (2) commit {P += id, M += id}; (3) K removed; (4) dispatch
binds P[id] to its store; (5) the server executes once and records S[id];
(6) settle {R += id, P −= id}; (7) a later commit drops M[id] once K is
confirmed absent.

- **Loss.** From (1) the intent is in K or P until (6), which requires a
  server terminal outcome. K is removed only after (2) committed or after a
  locked authority refusal (G5, reported). A crash at any point leaves K, P,
  or both; recovery admits K only when P/R/T/M do not know the id, and
  replays P.
- **Duplicate admission.** K is admitted only under the journal lock when
  P/R/T/M do not know the id. M is added in the same commit that adds P and is
  dropped only after K is gone, so after (2) no copy of K can be admitted
  again, even after R evicts the receipt (the online journal keeps 256
  receipts) or T saturates.
- **Duplicate execution.** Every send of the id, from the live call, the
  journal's replay or a peer tab, carries the same id and the store identity
  captured at (1). The server checks the store before execution or lookup and
  executes an id at most once per store. This is the primary guarantee; the
  local markers keep the client from presenting a settled id as new.
- **Residual cases**, unchanged from today's online journal and the device:
  a damaged online journal is preserved aside and replaced with an empty one,
  after which a surviving K could be admitted again, and the server answers
  its replay with `replayed: true`; a server restored from a backup that lost
  S is the existing `E_STORE_RESTORE` case.

## 6. Failure modes

| Condition | When | Result |
|---|---|---|
| `localStorage` getter or `setItem` throws (blocked storage, `QuotaExceededError`) | capture | `E_ADMISSION` in the calling stack; nothing admitted or sent; retry the same id after repair |
| 32 records, 256 KiB, or a 64 KiB record | capture | `E_ADMISSION` naming the bound |
| memory or asynchronous-only `sessionStore` | call | `E_ADMISSION` naming `localStorageSessionStore()`; construction also warns once |
| no `navigator.locks` | call | `E_ADMISSION` (no cross-tab serialization) |
| schema syncs tables, no `writes: "online"` | call | `E_ADMISSION` naming the tables and both rewrites |
| sync decision unknown (offline at opening) | call | `E_ADMISSION`, `retryable: true`; a new read starts |
| IndexedDB unavailable or failing (some private modes, quota) | sign-in | sign-in fails with `auth.why`; the signed-out client refuses writes |
| IndexedDB commit fails after capture | commit | `E_STORE` "outcome unknown; retry the same id"; K stays; recovered before the next admission and at the next open |
| record removal fails after commit | cleanup | marker kept; record never admitted again; collected later |
| session ended between capture and commit | commit | `E_AUTH`; record cancelled; scope rechecked |
| session ended before a recovery | recovery | record cancelled; one console warning with the count |
| authority read fails during recovery | recovery | nothing cancelled; `auth.why`; retried at the next open |
| site data cleared, OS crash before flush | — | out of scope (G2's limits; same as the device) |

## 7. What is not supported

- **Offline reads and predictions.** Reads are the online client's: live
  queries over `/changes`, one-shots over `/q`, with its existing offline
  behavior (`loading`/`E_OFFLINE`). There is no replica, no prediction, no
  local interpreter and no `sync` behavior. A write is visible when the server
  confirms it.
- **Offline queuing across reloads beyond the journal.** Admitted intents wait
  for the link as they do today; a reload while offline keeps them, but a new
  write after an offline reload refuses until the sync decision is known,
  unless `writes: "online"`.
- **Page-hide keepalive sends.** The device sends its outbox head on
  `pagehide`; this journal does not. A click recovers at the next open
  instead.
- **Personas** (§8), **custom asynchronous session stores**, and **bare
  `createClient()`** writes in a browser.

## 8. Deferred

- **Persona apps.** A device-less `createApp({ url, persona })` has no session
  store, so it has neither the online journal nor an authority stamp. It keeps
  refusing browser writes, naming the device. A persona journal would bind
  records to (url, persona) with no epoch; it is a separate, small change.
- **Expo web.** The Expo starter selects `webDevice()` on web; an online-only
  Expo schema could omit it there too. The starter is unchanged here.
- **A cached sync decision** across offline reloads.

## 9. Testing

- **Unit (Node, a simulated window with real `localStorage` semantics and a
  Web Locks shim):** capture order and bounds; refusal on throwing and full
  storage; selection by schema (zero, some, unknown, explicit); transfer
  markers survive a failed removal; recovery admits once across two runtimes;
  cancelled and other-account records; ordering of recovered before new
  intents; unchanged behavior with no window.
- **Browser (the Chromium witness, `witness/lib.mjs` `launch`):** a click
  followed by a same-turn `location.assign`, and a click followed by a
  reload while the mutation POST is held, each recover with one server
  execution; a reload after commit but before removal does not re-admit; two
  tabs: a live tab's records are never adopted, a closed tab's are adopted
  once; storage refusal (full localStorage) refuses synchronously and sends
  nothing; logout between capture and commit cancels; the page fetches no
  `.wasm`.
- **Fault instrumentation:** the journal's new awaits are classified in the
  delivery await census (`delivery-await-boundary.json`,
  `delivery-fault-instrument.mjs`); none of them is on the device's delivery
  path, so the census records them with this RFC's tests as their coverage.
- **Bytes:** a Vite production build of the same online-only page with and
  without `webDevice()`, recorded here.

## 10. Alternatives

- **Path 1 (journal through the session store only):** the gap itself.
- **Path 3 (lazy wasm on the first write):** defers custody past the click.
- **Path 4 (a journal-only wasm):** a second web artifact with its own budget,
  census and qualification, to do what 300 lines of JavaScript over the
  existing journal do.
- **Capture before identity:** withdrawn in EA round 3 (LLP 3000.007 §20.4)
  after three review rounds; this design keeps the wait.
- **Automatic selection regardless of `sync`:** an app whose schema syncs and
  forgets the device would silently lose offline reads; the author scoped the
  journal to schemas with no synced tables, with `writes: "online"` as the
  explicit choice.
