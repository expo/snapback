## 1. Decision and claim

Build a **Release, arm64 iOS-simulator host**, published with a fixed native
dependency closure, which launches a builder's local exported Hermes bundle
and assets. Extend the existing witness driver; keep its process ownership,
offline boundaries, native smoke and application scenario protocol. The builder
does no CocoaPods, prebuild or Xcode compilation. The publisher does that work.

The intended command, from a project containing both the app and backend, is:

```sh
npx snapback4 witness ios --export dist --smoke
```

This is a proposal, not an available flag. It proves the builder's exported
application **in the published host**. It does not prove the builder's own
Release executable. Both proof kinds must remain distinguishable in receipts,
manifests, publication records and benchmark reporting. The installed-app path
remains `witness ios --bundle-id ...`; unsupported native configurations take
that path, with an explicit reason and build command.

**About two minutes is a warm-toolchain target, not a result.** Measure from
CLI invocation through finalized, validated artifacts with the host package
cached, an available booted supported simulator, dependencies installed, a
compatible export already present, and a fixture plus an unattended normal
test-login flow ready. Include host verification, first installation on that
simulator, copying the export,
all three smoke segments, recording finalization and hashing. Exclude neither
installation nor failed attempts from the reported measurements. Separately
report first npm download, simulator boot, fixture/auth setup and JS export
times. Installing Xcode or an iOS runtime is not a two-minute operation.

There is one qualification to “the export they already make”: stock Expo
`metadata.json` does not identify the native closure, export-time public config
or compiler, and does not map hash-named assets back to RN's local paths. The
paved export will add provenance and an asset map in the **same JS export**
(§4). Old exports without that evidence are refused with a JS-only re-export
instruction; they are not relabelled compatible by looking at today's
`package.json`. No native build is required to make that replacement export.

Round 0 commissions only this RFC. Implementation owner: the subsequent
macOS NP lane; proposed start is its first round after design acceptance.
No iOS artifact, new runtime behavior, publication or benchmark score is
claimed by this Linux round.

## 3. Host composition and version custody

Choose one host cohort for the scaffold's supported toolchain, initially Expo
**57.0.22**, React Native **0.86.3**, React **19.2.3**, Hermes and the New
Architecture (Fabric/TurboModules). Build with `Release`, `__DEV__ = false`,
without a development launcher, Metro lookup or OTA selection at startup.
`expo-dev-client` may be installed in the native dependency closure, just as
in chat-expo, but its Debug launcher/menu is not an alternate loading path.
Verify the resulting Release module inventory rather than assuming the npm
package name means a dev launcher is active.

The [Expo scaffold](../snapback4/crates/snapback4/src/verbs/init.rs) inherits
[`apps/chat-expo/package.json`](../snapback4/apps/chat-expo/package.json).
The [social scaffold](../snapback4/crates/snapback4/src/verbs/init/social.rs)
adds Router, image picker, linking, screens and safe area. The host includes
that union plus **expo-video**, which the reported cal25 application needs.
Do not ship a chat-only host and advertise support for the calibration app.

Initial pin candidates below are exact resolved entries in
[`snapback4/bun.lock`](../snapback4/bun.lock), except the explicitly identified
video candidate. They are inputs to macOS qualification, not an already
qualified compatibility matrix.

The table is not the complete pod list. Freeze **the entire iOS autolinking
closure**, its package integrity hashes, `Podfile.lock`, pod source checksums,
codegen inputs and registered Expo/TurboModule/Fabric names in the manifest.
For example the current Router lock brings `expo-glass-effect@57.0.4`,
`expo-symbols@57.0.3`, `@expo/ui@57.0.20` and masked view `0.3.2`; installed
optional peers include gesture handler `3.3.0`, reanimated `4.7.0` and worklets
`0.13.0`. Include and record those actually linked by the chosen graph;
do not discard transitive native packages because they were absent from the
builder's direct-dependency list. Never replace an unavailable optional module
with a stub. Reanimated/worklets require their matching JS and compiler plugin
versions when used.

Deduplicate native packages before qualification. This lock has nested
`expo-constants@57.0.18` as well as root `57.0.19`; the host cannot honestly
claim to link both as interchangeable native implementations. Resolve the
cohort to one copy, align scaffold pins and its lock, and test the resulting
graph. An export with multiple conflicting native resolutions is refused.
SDK-compatible semver ranges are not proof of identical native bytes.

Generate scaffold pins and the host manifest from one checked-in cohort input
at implementation time, retaining chat-expo as the reference consumer. Pin
native versions exactly on the paved path; allow arbitrary pure-JS packages.
A new native dependency, SDK/RN upgrade, native config change or Snapback
device change creates a new host artifact/cohort. No floating `latest` lookup
or “same SDK major” admission. Initial policy is exact resolved versions plus
integrities; future patch compatibility needs an explicit tested pair, never
a broad range added to make preflight green.

Hermes is a separate admission axis. The lock pins `hermes-compiler` at
`250829098.0.17`; the host manifest records the actually linked Hermes engine
identity, compiler version/digest, bytecode version and build flags. Read
the exported file's HBC magic and bytecode-version header, independently of
its filename; compare compiler provenance, RN version and architecture mode.
Matching a bytecode header alone does not prove RN or native-module ABI
compatibility. Refuse JSC, plain JS mislabeled HBC, unsupported multi-bundle
formats, wrong HBC version and legacy architecture. Never compile or downgrade
the bytecode silently at launch. Expo documents that Hermes bytecode can
change with Hermes/RN versions; a manually equal `runtimeVersion` is not an
independent compatibility check. [Expo Hermes guidance](https://docs.expo.dev/guides/using-hermes/),
[runtime compatibility](https://docs.expo.dev/eas-update/runtime-versions/).

## 4. The export and admission manifest

Add a proposed JS-only export wrapper, wired into the generated M1 script:

```sh
# Proposed build:ios-hermes script; also works on Linux.
npx snapback4 witness export ios --out dist
# Internally: the project's pinned Expo export -p ios --dump-assetmap,
# plus an export-time sidecar. No native build, Metro server or package install.
```

The wrapper uses the **project's** Expo/Metro/Hermes, not its own copy. Capture
resolved public Expo config and relevant environment in the same export
process, using a versioned adapter to that pinned Expo CLI. Do not evaluate a
dynamic `app.config` again after export and assume the answer is identical.
Snapshot input hashes before export and verify them after; a changing lock,
native graph, config or bundler input invalidates the sidecar. The sidecar is
a reproducibility record for local trusted code, not a cryptographic assertion
that an adversarial builder cannot lie.

Write `snapback4-export.json` only after a successful export. Record:

- Format version, iOS/production/Hermes/New Architecture, entry module name
  (`main` for registerRootComponent/Router), export CLI/Metro/Babel/Hermes
  identities and runtimeVersion if present.
- Root `package.json`, lockfile type/hash, resolved native dependency graph
  with reasons/paths, package integrities and local native/codegen/config
  fingerprints. Include autolinking settings, config plugins and options,
  patches/overrides, workspace modules and any custom `ios/` content.
- Export-time public config including `extra`, plus the chosen backend
  origin. Record only public values needed by the app, not ambient environment
  or credentials. `EXPO_PUBLIC_*` used by the export remains in the bundle;
  record its public-value digest and the origin explicitly for comparison.
- Bundle path/hash, original `metadata.json` and `assetmap.json` hashes,
  and a normalized iOS asset map: each scale/file hash, type, RN relative
  destination, exported source path, byte count and **SHA-256**. Expo's asset
  hashes identify assets; they do not replace the SHA-256 evidence binding.

Inspecting local primary sources explains the extra map: Expo CLI
`createMetadataJson` emits version 0, bundler, platform bundle and flattened
`assets/<hash>`/extension records. `createAssetMap` retains the full Metro
asset objects when `--dump-assetmap` is used. RN's iOS `AssetSourceResolver`
uses `httpServerLocation/name@<scale>x.type` relative to the bundle directory.
Merely copying `dist/assets` beside the HBC file does not meet that contract.
The macOS lane must verify the pinned exporter uses these forms before its
adapter accepts them; unknown export formats are refused.

For `witness ios --export`, compare three independent inputs before launching
anything: current project declarations/resolutions, the sealed export record
and bytes, and the qualified host manifest. Resolve from `--app-project`
(default cwd), not accidentally from a parent monorepo's node_modules.
Check direct dependencies **and** the transitive iOS autolinking graph. Use
Expo's resolver for Expo modules and RN/codegen metadata for other modules;
inspect local modules, podspecs, `react-native.config.*`, Expo module configs,
patches and plugins. Unknown native-bearing/config-plugin input fails closed;
an unknown ordinary JS package does not require a global package whitelist.
Unclassifiable native content is a refusal, not an inferred JS-only package.

The project's required native set may be a subset of the host's. Every
required native package/version/build option must match. Compare the export's
native graph/config with current project inputs so a stale export cannot be
tested under a newly edited manifest. Host-only extra modules are disclosed;
they do not authorize undeclared native use (§6).

Missing provenance on a stock export gets `E_WITNESS_EXPORT` with the JS-only
export command above. No post-hoc seal of arbitrary HBC, no source-code grep
for native imports as a substitute, and no accepting a handwritten
`runtimeVersion` as the whole manifest. This is an explicit compatibility
boundary, and a cost of making the “already exported” fast path reliable.

## 5. Launching the local bundle and assets

Install the verified `.app` on the resolved dedicated UDID. Its immutable
bundle ID is `dev.snapback4.witness`; its own scheme is `snapback4-witness`.
Do not rewrite its Info.plist, sign it as the builder's app, or replace its
embedded resources for each export. Verify the installed payload against the
package before using an existing installation.

With the host stopped, copy the validated export into a private directory
under its data container, e.g. `Library/Application Support/Snapback4Host/`
`exports/<export-sha256>/`. Materialize a `main.jsbundle` copy of the **unchanged
HBC bytes**, public config and the normalized asset tree. Check all source
and destination digests and store a staging manifest. Atomically select that
directory for the run; never mutate it between prime/offline/restart. Receipt
files keep the existing separate `Documents/.snapback4-witness/<run>/` path.

Pass only a small validated launch description through simctl, for example:

```text
SIMCTL_CHILD_SNAPBACK4_HOST={"format":1,"run":"...","export":"<digest>","manifest":"exports/<digest>/launch.json"}
SIMCTL_CHILD_SNAPBACK4_WITNESS={existing run/segment/smoke/barrier configuration}
```

`AppDelegate` reads `SNAPBACK4_HOST` before constructing the RN runtime,
confirms a simulator build and validates the selection/digests against its
container root. Its `ExpoReactNativeFactoryDelegate.bundleURL()` returns
`URL(fileURLWithPath: validatedBundlePath)`. Retain Expo's normal factory and
dependency provider, including generated Fabric/TurboModule registration.
Do not implement this solely as `sourceURL(for:)`: inspected Expo 57 factory
source explicitly avoids that bridge-only route under the New Architecture.
Root component registration must match the export's `main`. Without valid
launch configuration the host shows its own inert “Run snapback4 witness”
screen; it never reopens the last export or discovers a network bundle.

**Config.** Add a small, host-target-only native adapter to the pinned
`EXConstantsService.appConfig` path so its manifest comes from the validated
export-time config before JS reads `expo-constants`. The inspected service
normally reads `EXConstants.bundle/app.config` in the app. Version and hash
this adapter as a native patch in the host manifest. Do not swizzle arbitrary
Bundle access or patch a live JS `Constants` object after module evaluation.
`Constants.expoConfig.extra`, name, slug and declared app config come from
the export; actual native constants such as build number, execution
environment and installation identity remain the host's. Record both project
and host identifiers. Expo explicitly distinguishes manifest config from
immutable native build fields. [Constants documentation](https://docs.expo.dev/versions/latest/sdk/constants/).

**Scheme and native config.** Reading a project's scheme in `expoConfig`
does not register it with iOS. In-app Router navigation can run, but launching
the project's URL scheme, associated domains, OAuth callbacks, push identity,
keychain access groups and extensions require the own-app build. Do not
silently translate a project URL into the host scheme. Ordinary name, slug,
bundle ID and scheme differences are declared proof limitations, not grounds
to reject every scaffold. Admit only the known default plugin configurations
and explicitly classified identity/UI differences; refuse custom native
plugins, entitlements, AppDelegate changes, SQLite extensions/SQLCipher,
background video modes and other configuration outside the host. Stock
image-picker permission strings are host strings and recorded as such; they
do not prove the project's privacy text or production permission behavior.
A requested identity-dependent scenario is refused even when smoke could run.

**Environment.** `EXPO_PUBLIC_*` is inlined by the export, not a runtime
simctl environment API. Setting `SIMCTL_CHILD_EXPO_PUBLIC_SNAPBACK_URL` cannot
change the compiled origin. Compare the export's declared origin with
`http://127.0.0.1:<port>` and the attached smoke client's actual origin; refuse
a mismatch. Re-export for a new origin. Do not substitute a new client, inject
a guest or rewrite the HBC. [Expo environment semantics](https://docs.expo.dev/guides/environment-variables/).

**Assets.** Materialize all declared scales under the relative layout that
the pinned RN resolver computes, including its documented `../` to `_`
normalization, then validate that the result remains inside the staging root.
This lets ordinary RN `Image`, `Asset.fromModule`, runtime font loading and
video resolve local files without changing JS or enabling expo-updates.
Reject path collisions with different bytes, missing scales, embedded-only
resources absent from the export, custom resolver forms and unresolved asset
URLs. Native-compiled asset catalogs/fonts are outside this route. Test images
at multiple scales, a font, a Router icon and a local MP4. An empty chat asset
set is insufficient qualification. Keep application media fetched from the
Snapback backend separate: only the app's actual media policy may retain it.
The host must not prefill its ordinary/view-once media cache from a fixture.

**Storage.** A host bundle ID shares Documents, SQLite locations and keychain
identity across loaded apps. A different export/project must not inherit a
previous app's credentials or replica. Initial design is one exclusively
leased host per dedicated simulator, with an explicit host-data reset at the
start of an independent run (including host keychain items; uninstall alone
is insufficient). The run retains that same data container/keychain across
all its segments and relaunches. No reinstall/reset/seed after prime.
The host and driver use a per-UDID lease in addition to artifact reservation;
refuse concurrent ownership or an already running host. Never reset another
app or all simulator keychain entries. A future reusable session must be
explicitly bound to project/export/native cohort/backend identity; it is not
part of the initial two-minute path.

Consequently an app needing interactive login must sign in through its own UI
during prime; the fixture/session setup time is visible and separately
reported as part of the full elapsed run, not subtracted to claim a two-minute
interactive run. Smoke still waits for the app's own published client. For
unattended acceptance, the test application supplies its ordinary test-login flow; the
host must not manufacture session/store files to accelerate it.

## 6. Refuse incompatible inputs and detect runtime misses

Preflight collects **all** independent mismatches in one structured report:
code, package/config field, expected, found, dependency path and fallback.
It returns nonzero before simulator launch/backend start for compatibility
failure, and retains a failed preparation manifest when an artifact directory
has been reserved. Existing input/platform refusals retain their semantics.

| Proposed stable code | Refusal and recovery |
| --- | --- |
| `E_WITNESS_HOST` | Missing/wrong-version host package, unsupported host format or target; install the exact matching optional package, or build your app. |
| `E_WITNESS_HOST_DIGEST` | Tarball, host inventory, installed payload or qualification binding differs; reinstall verified package bytes. Never launch the changed payload. |
| `E_WITNESS_EXPORT` | Missing/stale export provenance, unsupported export format, non-iOS or non-production export; name each missing field/file and run the JS-only export command. |
| `E_WITNESS_NATIVE_COMPAT` | Missing native dependency, version/integrity mismatch, conflicting duplicate, native patch/codegen mismatch; list every mismatch and use matching cohort pins or own Release build. |
| `E_WITNESS_HERMES` | HBC/compiler/engine mismatch or non-Hermes input; name expected/actual versions and re-export with the cohort, otherwise build your app. |
| `E_WITNESS_ARCH` | Legacy/New Architecture, CPU or simulator/device target mismatch; use the cohort or own Release build for that target. |
| `E_WITNESS_CONFIG` | Unsupported native/plugin configuration or identity-dependent scenario; name fields/plugins and build your app. |
| `E_WITNESS_ASSET` | Missing asset, hash mismatch, ambiguous destination or unsafe/custom mapping; name all affected paths and re-export or build your app. |
| `E_WITNESS_ORIGIN` | Export/actual client origin differs from owned backend; re-export for the printed origin or select its matching free port. |
| `E_WITNESS_NATIVE_MODULE` | Runtime requested native module/component unavailable or undeclared for this project; name module and requesting stack when available, fail the run and build your app. |
| `E_WITNESS_SCHEMA` | Requested application-receipt schema/coverage validation fails; retain raw evidence, repair the scenario and rerun. |

Every native incompatibility prints the concrete fallback, using the resolved
project bundle ID and UDID, not a generic “something went wrong”:

```sh
# In your Expo project, then quit the app:
npx expo run:ios --configuration Release --device "$UDID"
# In your backend project:
npx snapback4 witness ios --bundle-id com.example.app --udid "$UDID" \
  --smoke --artifacts artifacts/native-own-build
```

Existing `E_WITNESS_PLATFORM`, `SIMULATOR`, `PORT`, `APP`, `BACKEND`,
`PROCESS`, `ARTIFACT`, `RECEIPT`, `STEP`, `TIMEOUT` and `INTERRUPTED` remain
applicable with their full `E_WITNESS_` prefixes. Add new codes to the guide's
existing diagnostic registry/tests when implemented, not an unrelated gate.

Static dependency inspection cannot prove every dynamically computed native
lookup. Add host-side observation at the pinned Expo module registry,
TurboModule lookup and Fabric component registration/failure paths **before
evaluating app JS**. A required missing module/component writes a synchronous
host failure record even if app JS catches the error. Include native fatal
and JS startup/error channels; a crash or missing terminal handshake fails.
Keep the existing smoke error handler and final PID checks, and apply equivalent
liveness checks to host application scenarios after their last success receipt.

Optional probes need care: Expo itself probes absent `ExpoUpdates` and Expo Go
modules during normal Release startup. Record optional misses; permit only
the qualified standard optional probes with their semantics unchanged. A
missing required lookup or unrecognized optional probe is not silently
accepted. Host inventory is intersected with the project's admitted native
set for app lookups so a superset host cannot hide an undeclared dependency;
baseline host/Expo plumbing has an explicit manifest allowance. Do not stub
native methods, change application feature detection into success, or turn a
module exception into an online-only fallback. If this enforcement cannot be
made correct on the pinned RN/Expo APIs, publication remains blocked on that
implementation question; a diagnostic string grep alone is insufficient.

Only executed requests are observed. An unexecuted branch can still contain a
problem, and passing smoke never proves every module's behavior. Preflight,
runtime lookup checks and actual scenario coverage serve different purposes.

## 7. Packaging, publication and digest custody

Choose a sibling **`snapback4-witness-ios-darwin-arm64@V`**, with npm `os:
["darwin"]`, `cpu: ["arm64"]`, exact version V and no lifecycle download/build
script. Make it an exact optional dependency of `snapback4-darwin-arm64@V`.
An ordinary Mac install then has the host ready for the one-command path;
Linux does not fetch it. `--omit=optional` can omit it, so `E_WITNESS_HOST`
prints the exact `npm install --save-dev --save-exact` command. The witness
itself performs no implicit network installation. Publish third-party notices
with the simulator-only `.app`, compatibility manifest and qualification data.

Putting the app directly inside `snapback4-darwin-arm64` would give the same
default download cost and couple the CLI and native payload layouts. The
sibling isolates size/integrity and lets users omit it. A separate opt-in
manual download would save Mac CLI-only users the bytes, but breaks the paved
one-command experience; reconsider after actual size measurement. Optional
does not mean free: the default Mac install pays the download and unpack cost.

**Size is unmeasured.** Plan for roughly **40–100 MB compressed / 150–300 MB
unpacked** for one arm64 Release app with Hermes, RN, media modules and the
Snapback device. This is an engineering estimate, not a measurement derived
from the much smaller XCFramework tarball (0.4.0 was 4,809,589 bytes). Proposed
first-release review thresholds are 100 MB compressed and 300 MB unpacked;
measure `.app`, npm tarball, installed size and transfer time in stage 1. If
over, remove unused native closure/debug resources or revise the packaging
decision visibly before claiming the fast path. Strip distributable debug
symbols; keep dSYMs in publication evidence outside npm. No web wasm budget
change follows from a simulator host.

Extend the native half of publication in this order:

1. Freeze release source, cohort lock/config/codegen and exact client/Expo
   packages. Build the native device slices as today. Build the host Release
   for `iphonesimulator` arm64 with explicit deployment target. Retain build
   inputs and linker evidence showing the linked Snapback archive digest
   equals the packaged Expo simulator slice. Verify actual Hermes/architecture
   and module registration, not just build settings.
2. Export chat's own JS through the new export path from those exact staged
   client/Expo packages. Install the host and run smoke, then the existing chat
   offline/restart application runner. Add the broader native-module/asset
   fixture. Preserve the ordinary chat Release qualification as a separate
   proof kind, including the existing `witness/expo.mjs` path. The host must
   not replace evidence that the Expo package links into an actual app.
3. Produce a deterministic host inventory: sorted relative path, file type,
   relevant executable mode, length and SHA-256 of every payload file, plus
   validated relative symlink targets if any frameworks require them. Reject
   links escaping the app. Exclude only the inventory/receipt itself from its
   own digest. Include executable, framework/resources, Info.plist, native
   adapter and cohort metadata. Record archive, executable, bundle inventory,
   export and asset hashes in qualification. Installed verification uses the
   same normalized content inventory; it does not trust modification times.
4. Put a payload-bound qualification receipt into the package, then `npm pack`
   **once**. An outer publication receipt binds tarball SHA-512 SRI/SHA-256,
   host inventory/manifest digests and that qualification receipt's digest.
   This avoids a tarball hashing a receipt that must contain its own tarball
   hash. Install the packed candidate outside the repository with the staged
   CLI/client/Expo packages and qualify those exact unpacked bytes. Record this
   final consumer proof externally against the immutable tarball SRI.
5. Extend the existing publication stage/resume machinery to verify those
   associations. Host publishes before the Darwin package that requires it;
   platform packages and the exact Expo package precede the client release
   claim. Verify registry integrity against staged bytes. Resume reuses the
   qualified tarball and refuses changed/missing host evidence; it never
   rebuilds a host under an existing version. No independent publish path
   bypasses the current release qualification.

Bind the host inventory digest and export digest into a driver-created
`proof.json` in each run. Pass its hash in native launch configuration; the
native bridge reports the verified proof identity before app steps. Driver
validation requires that handshake on each launch, plus unchanged staged
inputs at collection. Hash `proof.json` and raw receipts in the run manifest.
Ordinary witness JSONL gains a versioned proof binding understood by the
updated helper/driver; installed-app receipts set the other proof kind too.
Do not overload today's strict two-field `witness: {at, step}` envelope without
versioning and updating both validators. Choreography's closed schema uses
the sidecar binding described in §8 instead of new top-level fields.

Minimum proof identity is:

```text
proofKind: exported-bundle-host | application-release
host: package/version, payload inventory sha256, cohort/manifest sha256,
      published qualification digest, package SRI when available
application: project bundle ID (declared), actual installed bundle ID,
             export/HBC/public-config/assets sha256, package/lock hashes
runtime: UDID, iOS version/build, simulator device type, arm64,
         RN/Expo/Hermes identities, newArchitecture, Release
adaptations: local bundle/asset staging, public-config adapter,
             host identity/scheme/permission differences
```

For `application-release`, host fields are null and the actual installed app
inventory, embedded JS and native build identifiers replace them. For a host
proof the run's `appBuild` remains the **host's** Info.plist; never put the
project's declared bundle ID there as though it were installed. Strengthen
the existing `installed` field, which currently hashes executable/JS for
smoke and is null for deeper scenarios, for both modes. Hashes bind evidence
to bytes; they do not independently validate assertions or create a trusted
remote-attestation boundary.

## 8. CLI, smoke and application artifacts

`--export` and `--bundle-id` select mutually exclusive launch modes. Host mode
selects its own fixed bundle ID; `--app-project` locates the JS project when
the command runs in a separate backend directory (as for chat-expo). Paths
are resolved relative to invocation cwd and recorded. `--artifacts` defaults
in host mode to a fresh `.snapback4/witness/<timestamp>-<run>/`; print that
path immediately. Keep explicit `--artifacts` and the no-overwrite marker.
An explicit `--udid` is required if selection is ambiguous; otherwise retain
the exactly-one-booted-simulator rule. Do not download runtimes, target
unresolved `booted`, kill an existing server or borrow a busy simulator.

Generic `--smoke` retains the three actual segments:

1. **Prime:** the app's own published native client is authenticated as its
   own flow requires, online and acquired. Record counts, store identity,
   generation, watermark, link and uncaught errors after the render pause.
2. **Offline:** terminate and verify absence, stop the owned backend and
   verify refusal, cold-launch the same export/store. Require matching held
   counts and identity, offline link, and ready or explained-refusal outcomes
   for every no-argument/all-optional-argument query. Loading, thrown queries
   or uncaught errors fail. An explained refusal is evidence of refusal,
   not a successful result for that query.
3. **Restart:** terminate again, advance only the stopped backend's commit
   clock with the existing zero-write barrier, restart it and cold-launch.
   Require online sync through **that exact barrier**. Preserve final-state
   reread, published-client replacement handling and PID-alive checks.

Artifacts remain `smoke-ios-screen.mp4`, `smoke-ios-receipts.jsonl`,
`smoke-ios-run.json`, the three segment PNGs and logs, with hashes and the new
proof identity. Empty partitions only prove lifecycle/opening. Required-arg
queries, writes, media, search correctness and final recipient read states
need the app's scenarios. A successful generic run prints “Host smoke passed:
prime, offline, restart”, never “M6/M8 passed” or “your Release build passed”.

An exported app mounts its own `WitnessRunner` using the existing
`snapback4-expo/witness` helper and its actual visible screen/client. The host
does not replace its entry point or inject a reference chat. With smoke false,
`witness()` returns the ordinary segment API; during smoke it remains null so
the existing runner and automatic smoke cannot compete. Exported scenario
code must already be present in the bundle. A missing runner times out/fails;
there is no host scenario that can invent the application's assertions.

For example, with app implementations of the two segments:

```sh
npx snapback4 witness ios --export dist --udid "$UDID" --segment m6 \
  --prime --artifacts artifacts/m6 --receipt-schema instrument/choreography/receipts.schema.json
npx snapback4 witness ios --export dist --udid "$UDID" --segment m8 \
  --prime --warm-offline --relaunch --artifacts artifacts/m8 \
  --receipt-schema instrument/choreography/receipts.schema.json
```

These schema options and artifact adaptation are proposed additions, not
existing capabilities. For M6 the runner's prime acquires the named history,
search token and viewed ordinary image, and consumes/revokes the view-once
asset through normal app behavior. Cold offline asserts actual rendered
history, ordinary media, consumed view-once refusal with no cache open,
search/open-conversation, and two uniquely named visible pending bubbles in
compose order. After `offline-done`/`waitFor("reconnect")`, it observes exactly
once ordered settlement and **Bob's actual open/read progression**, then
finishes `done`. Bob's observation must run through a real app/client fixture
and be recorded; a server-side forced `read` value is not that observation.

**M8 needs one driver extension beyond the current relaunch flag.** The frozen
spec starts with warm-offline composition; today's driver always terminates
prime and starts the segment cold. Add a versioned warm-to-offline handoff
(proposed `--warm-offline`, used with `--prime --relaunch`) that starts video
before stopping the backend, keeps the primed app PID alive, signals verified
backend-offline to the runner, and waits for its two pending sends and
`relaunch`. For this opt-in mode launch initially with `segment: "m8"` and
new helper field `launchPhase: "prime"`; the runner completes `primed`, then
awaits `waitFor("offline")` in the same process. The driver creates that
run-specific signal only after verifying backend refusal. Existing scenarios
keep their `segment: "prime"` behavior. Then terminate, verify absence and
relaunch with `segment: "m8", launchPhase: "offline"` and the same export still
offline. The runner reloads saved IDs/bodies without sending again, proves
each pending row once in order (`m8-a17`), signals `offline-done`, then proves
ordered flush and final `read` after reconnect (`m8-a18`). The M8 command above
includes `--warm-offline` for the frozen instrument; without it the result is
only the existing cold-start durable-queue scenario. No reset or reinstall
occurs during the recording. Warm handoff needs helper signaling but no new
engine/client semantics.

**Schema-valid artifacts require a separate projection.** Keep raw driver
protocol lines, including milestones, errors and proof bindings, as
`<segment>-ios-witness.jsonl`. Let the app emit schema-shaped assertion
objects under an agreed application field, e.g. `w.receipt({ assertionReceipt,
observation })`. The driver copies `assertionReceipt` unchanged into
`m6-ios-receipts.jsonl` or `m8-ios-receipts.jsonl`, validates **every** projected
line against the explicitly supplied local schema, and binds a line mapping
back to the hashed raw file. Never just strip `witness` from all rows: the
empty milestone rows would still fail the schema. Never put host metadata
into a schema that has `additionalProperties: false`.

The supplied schema requires version, UUID runId, timestamp, assertion,
implemented/required/status/pass, timings, bestOf and details; fields must be
truthful. Native continuous runs use one attempt (`bestOf: 1`), not a collage
of three successful moments. Exact fixture IDs, message bodies, media/cache
observations, ordering/counts and final states live in the hashed raw
observations/fixture manifest, with each schema assertion mapped to them.
The app also includes the assertion's observation as JSON text in the schema's
allowed `timings[0].note` string, with numeric counts/order metrics in `metrics`,
so the schema-valid JSONL itself carries the exact observed content. The
projector verifies that this observation agrees with its raw structured copy;
it never adds a forbidden top-level `bodies` or `observation` property.
The export of a schema-valid boolean alone is insufficient. A local
application coverage declaration names the expected assertion IDs and
required observations; the driver checks coverage, no duplicates, same run
and passing required assertions, as well as syntax and its milestone sequence.
For instrument use, the application-owned native validator must additionally
check the frozen M6 obligations and exact `m8-a17`/`m8-a18` coverage before
emitting a passing status. The existing `choreography.mjs` status loader only
checks the status object's shape and receipt pointer, then records it as
supplemental; it does not verify the native movie or those assertions. Do not
mistake ingestion for validation. The generic CLI does not embed benchmark
scoring policy or grant itself a pass.

Finalize uninterrupted `m6-ios-screen.mp4`/`m8-ios-screen.mp4` and matching
`*-ios-run.json` containing actual bundle/build identity, proof kind, UDID and
runtime/build, backend command/origin/store identity, fixture IDs, start/end,
termination/relaunch events, and SHA-256/lengths for video, raw/projected
receipts, schema, coverage/fixture/proof files. Validate after process stop
and movie finalization. Failure or missing observations yields nonzero and
preserved failure artifacts, never a passing status based only on filenames.

The status file may then use the instrument's `ios-simulator-m6`/`m8` objects
and manifest paths. However the frozen specification says the lane's
release-style build; a generic host is a different build kind. Record it as
a **host supplemental artifact** pending an explicit benchmark policy decision
to admit that kind. Do not silently change the frozen instrument, the prompt's
optional-native rule, web milestone green or historical scores. If the scorer
requires the application's own executable, this fast path cannot remove that
deduction by itself. It can provide native runtime evidence with honest scope.

## 10. Alternatives, risks and costs

| Alternative | Decision and reason |
| --- | --- |
| Every builder builds its own Release app | Keep as authoritative native-build fallback. Exact app integration, but the reported cold 40-minute build defeats this fast loop. |
| Cache DerivedData/prebuilds on the calibration Mac | Useful optimization for own builds, but cache misses and dependency changes still require Xcode; not a published reusable artifact contract. |
| Expo Go | Reject for local-device proof: it lacks the Snapback custom native module and selects the online tier. |
| A generic Debug development client / Metro bundle server | Reject as the qualifying fast path: different execution mode and a live bundle/asset server complicate cold-offline evidence. Expo describes development builds as Debug apps with the developer tools; that is not this Release host. [Development-build documentation](https://docs.expo.dev/develop/development-builds/introduction/) |
| expo-updates local update installation | Technically aligned with swappable JS/native layers and useful if the direct loader fails. Defer: adds update DB/selection/manifest and rollback semantics solely for local proof. Do not implement a fake `ExpoUpdates` module just to supply asset constants. |
| Rewrite the `.app` resources/config for each project | Avoid: changes the qualified payload/identity, complicates installed digests and hides the fixed-host limitation. Stage data outside the app instead. |
| A host for every dependency combination | Reject initially: unbounded build/storage/publication matrix. One current scaffold cohort with strict refusal is the bounded product. |
| Build the requested dependency automatically on mismatch | Reject: hides the native-build cost and violates the fast-path contract. Print the own-build fallback. |

**Per SDK release.** Expect one engineer lane to update the native dependency
closure and factory/config/asset adapters, rebuild on macOS, exercise every
supported native module and Router, run host and own-app comparisons, then
requalify package installation. Initial planning allowance: 1–3 engineer days
for an ordinary SDK bump, longer for RN/Hermes/architecture changes; unmeasured.
Patch/native changes also need a cohort qualification. Keep one active SDK
cohort initially; npm retains old immutable packages for pinned projects.
The adapters and module-request observer are maintenance commitments, not free
consequences of Expo supporting updates.

**OS/runtime.** arm64 Apple-silicon Macs only at first; no Intel simulator slice
exists in the current Expo device package. Distinguish the host's linked
minimum iOS deployment target from the iOS runtime actually qualified. Start
qualification with the publication lane's installed iOS 26.5 runtime, then
26.4 if maintained there; these are proposed matrix entries, not new proof.
The Snapback podspec's 16.4 minimum remains binding for its archive. Determine
the host minimum from the maximum required by RN and all host pods, inspect
Mach-O/object load commands, and publish it separately rather than claiming
all 16.4+ runtimes work. Initially admit only explicitly qualified runtime
version/build entries; unsupported runtimes get `E_WITNESS_SIMULATOR` with
installation/selection or own-build guidance. Runtime downloads/boot stay
visible costs; do not silently widen the claim after an Xcode update.

**Signing.** A simulator app needs no Apple distribution/development identity,
provisioning profile or signing service. Build for the simulator, with signing
requirements disabled; preserve any toolchain-created ad-hoc signatures in
the payload inventory. This does not change Developer ID qualification of
the macOS CLI or authorize an unsigned physical-device build.

**Security.** Dev-only, simulator-only loader; no network URL for code/config,
no OTA listener, no incoming download scheme, no host secret injection.
Reject absolute/traversing paths, escaping symlinks, malformed JSON, oversized
inventories and hash mismatches; bounded copying into a private run staging
area closes accidental source mutation races. The builder app can still use
its normal network APIs: “local code loading” does not mean a network sandbox.
Use disposable development credentials/data. Do not claim simulator isolation
protects the Mac from malicious local native-app code. Loaded app code can
forge its own assertions; driver-owned lifecycle evidence and hashes improve
traceability, not adversarial attestation. Keychain/storage reset and per-UDID
ownership are necessary to avoid cross-project contamination, not optional
cleanup polish. Video can contain visible private data just as today's witness.

## 11. Staged macOS implementation and acceptance

The macOS NP lane records actual timings/bytes and failed attempts in a dated
report and appends the journal. Implement in small stages; do not mark this
RFC Implemented until the scoped acceptance below passes. No fleet work,
native builds or publication is performed by the present Linux design round.

| Stage | Work and deliverable | Exit evidence |
| --- | --- | --- |
| 0 — pin and spike | Resolve/deduplicate the full cohort, confirm exact Expo factory/constants/exporter APIs, obtain actual HBC version and compiled native inventory. Set host deployment/runtime matrix. | Reproducible lock, source/adapter hashes, module/config inventory; any proposed pin that does not resolve is corrected here. |
| 1 — first vertical slice | Build one Release host; seal **apps/chat-expo's own export**, stage it unchanged, launch via `bundleURL`, attach the existing smoke to its ordinary app client and run prime/offline/restart. Arrange normal app sign-in and a nonempty fixture; no synthetic session/store injection. | Real simulator video, receipts, screenshots, host/export hashes, exact restart barrier and visible retained history; deliberately broken offline startup fails. Measure host sizes and complete CLI wall time. No benchmark pass claimed. |
| 2 — compatibility and broader app | Implement strict preflight and native-request observation, config adapter, safe asset layout, exclusive host lifecycle/keychain reset, all selected modules and Router. Run the social scaffold plus cal25-shaped dependency/media fixture. | Positive RN image/font/video/router/SQLite/SecureStore/module tests, config/extra read at initial import, persistence across relaunch; every negative case below fails for the intended reason. |
| 3 — packaging | Extend native publication kit/stage with immutable host pack, installed-consumer qualification, digest receipts and resume checks. Keep ordinary chat Release linkage/witness. | Exact packed bytes pass from outside checkout; unpack/install digests match; tampered payload/manifest and omitted optional package refuse. Dry-run only until separately authorized publication. |
| 4 — app scenarios and entry path | Exercise app-owned runners; implement warm-offline handoff and schema projection/coverage, bind m6/m8 artifacts; update starter/README/guide entry text together. | Complete instrument-format media/search/queue/read scenarios and an explicit host-proof scope label; no automatic change to benchmark admissibility. Agent starting at M1 finds and runs the command without being told the card name. |

Acceptance is the following set, not a new repository-wide blocking gate:

1. **Real native execution:** unchanged chat HBC SHA-256 is echoed by native
   startup; Release Hermes/New Architecture confirmed; Snapback native probe
   matches V; no Metro or remote JS/asset service. Actual nonempty prime,
   cold offline and barrier restart pass, with each PID observed until
   deliberate termination. Repeat with the installed-app path and explain
   any behavior difference. An online-only fallback must fail admission/smoke.
2. **Compatibility controls before launch:** wrong Expo/RN/native patch,
   missing `expo-video`, an unknown native module/plugin, duplicate native
   versions, changed lock, stale export, HBC version change, JSC/plain JS,
   legacy architecture, custom native configuration and missing/corrupt/path
   escaping assets all refuse with enumerated stable diagnostics. No owned
   backend or app starts. Changed public origin refuses rather than timing
   out against a different backend.
3. **Runtime controls:** a dynamically required missing Expo module, RN
   TurboModule and Fabric view each fail with the requested name, even when
   JS catches the lookup error; undeclared use cannot succeed just because
   the host has the module. Known optional probes do not cause false failures.
   Fatal JS/native startup failure and death after a success receipt cannot
   produce a pass. Unexecuted branches remain outside the claim.
4. **Data/config/assets:** public config/extra is correct on first import;
   inlined environment remains unchanged; declared versus actual identity is
   visible. Multi-scale image, local font/MP4 and Router assets render while
   the backend is stopped. Two independent projects cannot share keychain,
   SQLite or media state. The same run preserves all of those across process
   termination. A concurrent run refuses and cannot stop/reset the owner.
5. **Evidence and publication:** independently recompute all payload/export/
   asset/video/raw/projected receipt hashes; validate every projected receipt,
   line mapping, required assertion and continuous lifecycle event. Tamper a
   file/receipt, remove the movie, substitute another run, lose a required
   assertion or advance a milestone out of order: all fail. Publication
   receipt binds exact host SRI and qualification; resume cannot swap bytes.
   Linux never installs/launches the iOS host and reports the platform limit.
6. **Timing:** at least ten recorded runs on the calibration-class Apple-silicon
   Mac, cached host/export and booted qualified runtime, including a fresh host
   installation and bounded nonempty fixture. Report each run, median and p95
   (nearest-rank), phase timings and failures. Target **p95 ≤ 120 s** from CLI
   entry to finalized smoke artifacts. Also report cold package-download and
   simulator-boot cases. Auth waiting/export/fixture costs are visible and
   separately measured; exceeding the target changes the wording, not timeouts
   or assertions. M6/M8 scenario duration has its own measurements.
7. **Honest integration:** both run manifests and raw proof receipts explicitly
   distinguish `exported-bundle-host` from `application-release`. Generic smoke
   never supplies a benchmark assertion; missing scenarios stay not-recorded.
   Frozen benchmark host admissibility remains an explicit external decision.
   All guide claims correspond to qualified behavior; old installed-app
   commands and receipt failure handling continue to work.

Stage tests belong in existing witness/guide/package suites where possible;
real native qualification runs in the native publication lane. Use affected
checks while developing and preserve existing publication obligations. No
extra universal gate, unmeasured budget raise or full battery per edit is
created by this RFC.
