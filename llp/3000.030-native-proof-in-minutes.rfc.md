## 1. Decision and claim

Make **the builder's own Release simulator app, built and driven by the
witness**, the primary route. Reuse its native binary for JS-only edits through
fingerprint-checked repack **after repack qualifies**. A warm own-app rebuild
is the available mechanism to fall back to. Retain the prebuilt host and its
direct bundle loader as alternatives (§10), with no host package in this plan.

Proposed commands, run from the backend project with the Expo project here
shown as the same directory:

```sh
# First proof, or a native/config change. Build, install, then smoke.
npx snapback4 witness ios --build . --udid "$UDID" --smoke \
  --artifacts artifacts/native-base
# Later JS-only edit. Read the immutable base and its inputs from the receipt.
npx snapback4 witness ios --repack artifacts/native-base/build.json \
  --app-project . --udid "$UDID" --smoke --artifacts artifacts/native-edit
# If repack refuses, the first command with a fresh output directory rebuilds.
```

`--build`, `--repack` and `--app-project` are proposed additions. Today's
installed-app command, `witness ios --bundle-id ...`, remains available and
builds nothing. The new build preparation feeds that existing driver; it does
not introduce a second smoke protocol, synthetic client or backend.

The supervisor measured **359 s cold build/install, 138 s warm rebuild/install,
and 13 s repack preparation** on the real cal25 app. Repack launch, Hermes
bytecode and full smoke are still unverified. These measurements justify
choosing an own-app feasibility slice; they do not establish a two-minute
end-to-end proof. First use pays a native build. Subsequent reuse targets
**p95 ≤ 120 s** from repack invocation to finalized smoke evidence under the
conditions in §11. The title is an objective, not a measured product claim.

A repacked app is **the builder's native binary with new JS and bundled
resources**. Its receipt proves execution of that combination on the recorded
simulator; it does not prove that today's project was rebuilt by Xcode, that
the earlier `dist` export was executed, or that all app behavior is correct.
Proof kinds remain distinct everywhere. Neither host nor repack evidence may
become the frozen instrument's native `pass:true` without explicit benchmark
admission, even if its application assertions pass (§8).

This round revises the design on Linux only. Implementation owner: the next
macOS NP lane, beginning with §11's bounded slice after design acceptance.
No iOS execution by this lane, product flag, publication or benchmark result
is claimed here. `Status: Draft` remains appropriate.

## 3. Own Release build and native base custody

`--build <app-project>` uses that project's installed, locked Expo/RN/native
packages and its own identity, config plugins, generated providers and native
resources. It runs the necessary prebuild/pod preparation and `xcodebuild`
for **Release, iphonesimulator, arm64, Hermes, New Architecture**. Preserve
`ExpoModulesProvider`, `RCTAppDependencyProvider`, codegen and delegate
handlers generated for this application. No custom AppDelegate loader or
`expo-constants` adapter is needed. Prebuilt RN core and Hermes are already
used in stage 0; they are not a separate acceleration project.

The first supported shape is the cal25-like generated Expo application on the
stage-0 toolchain. Dependencies are already installed. Run prebuild in a
private snapshot when `ios/` must be generated; retain existing native inputs
when present. Never run destructive `prebuild --clean` over a builder's edited
`ios/`. Ambiguous workspace/scheme or unsupported custom native preparation
gets a named refusal and the manual installed-app route. Capture all local
workspace/native inputs needed by a snapshot, or refuse before building.

Use an explicit workspace, scheme, SDK/destination and private DerivedData
path; preserve warm intermediates per project/native fingerprint. Resolve
`TARGET_BUILD_DIR` plus `FULL_PRODUCT_NAME` from that invocation's build
settings and result, not the first matching app elsewhere in DerivedData.
Do not launch a stale prior app after build failure. Build processes have
their own finite, reported deadline (initial proposal: 15 minutes) separate
from the witness's 120 s **per step**. Save argv, phase timings, exit statuses
and logs. An exceeded deadline fails preparation; it does not relax assertions.

After successful preparation, copy the complete `.app` to
`<artifacts>/base.app` outside mutable DerivedData and write
`<artifacts>/build.json` beside it. Preserve both as an immutable local base.
A receipt made after the build records the resolved input snapshot, complete
native fingerprint, configuration/target, Xcode/SDK/runtime identities,
package/lock/pod digests, build log/result digests, and app inventory (§6).
Record actual Hermes engine/compiler versions and digests, HBC version,
`RCT_HERMES_V1_ENABLED`, prebuilt-core settings and architecture, rather than
assuming SDK-major compatibility. Retain the linked Snapback archive identity
where the toolchain exposes it, plus native probe/helper version.

A warm rebuild is still `application-release`: Xcode builds the current
application using valid intermediates. It creates a new immutable receipt,
even if no native compilation was necessary. Reuse of a prior native base
without that build is `application-release-repack`. A receipt-less installed
app remains usable by the legacy witness, but Info.plist alone cannot grant
it new build provenance or eligibility as a repack base.

## 4. Fingerprint-checked repack

`--repack <build.json>` selects a base built for this same project and native
identity. No cross-project reuse or published superset binary is admitted.
The witness verifies the base bytes and compares current native inputs with
the captured build inputs **before running repack or installing anything**.
A mismatch prints a field-by-field diff and the `--build` command. Never infer
compatibility solely from `package.json`, SDK major or `runtimeVersion`.

Use a pinned `@expo/fingerprint` implementation and record its version,
options and source list. Its API exposes hashes and source-level diffs;
its ignore/transform configuration can exclude native inputs, so equality
under arbitrary project overrides is insufficient. The first slice refuses
custom ignores/transforms that weaken coverage. [Expo Fingerprint API](https://docs.expo.dev/versions/latest/sdk/fingerprint/)

The witness's conservative native comparison also binds:

- The full resolved iOS autolinking closure, package integrities, native patches,
  local modules, pods/`Podfile.lock`, codegen inputs and architecture/Hermes
  settings. Include transitive modules and generated providers, not only the
  direct list in §2. Conflicting native resolutions or unclassified native
  inputs refuse reuse.
- Evaluated Expo config and plugin inputs/implementations, native source and
  resources, entitlements, bundle ID/schemes, permission strings, fonts and
  asset catalogs. Initially **any config change** requires `--build`; broad
  metadata rewriting is unnecessary for this JS-only slice.
- The recorded toolchain and native helper compatibility. Changing native
  Snapback/Expo/RN/helper inputs requires a build. Pure JS source/assets may
  change; full locks and JS/compiler/Metro/Babel inputs are still recorded as
  provenance. An unexplained fingerprint difference conservatively rebuilds.

Take the baseline after native generation/pod resolution has stabilized, and
compare equivalent input stages later. Generated timestamps/build outputs
must not become an excuse to ignore native source. Build/repack consume a
private snapshot with stable config/public environment; verify input hashes
before and after. A live edit or changed dynamic-config result invalidates
preparation. Record only public config and required public-value digests,
never ambient credentials. An origin change needs a newly bundled app for
`http://127.0.0.1:<port>`; simctl environment cannot rewrite inlined
`EXPO_PUBLIC_*` values.

Run an exact pinned `@expo/repack-app` from that project with an explicit
source/output, always writing a new `.app`. Expo documents that this normally
runs a fresh `expo export:embed`, then replaces JS, assets and metadata.
Therefore this path **does not consume the exact pre-existing `dist` HBC**.
Record the actual output bundle; retain the earlier export digest separately
if needed, with no assertion that they match. [Expo repack documentation](https://docs.expo.dev/build-reference/repack/)

After repack, compare inventories. Native Mach-O executables/frameworks must
be byte-identical to the base. Allow only enumerated JS/bundled-asset changes
and understood metadata serialization changes with identical native meaning;
record the complete changed-file list. Check bundle ID, schemes, entitlements,
permissions and public config against the base. Unknown resource/config
changes fail; neither a generic directory exclusion nor `--js-bundle-only`
is proof that the needed assets and identity were preserved.

Read `main.jsbundle` bytes: verify HBC magic/version and the recorded compiler
against the base's actual Hermes runtime, then verify real cold execution.
Hermes can execute JS source; “it launched in Hermes” alone is insufficient
for the Release/HBC claim. The measured 4.16 MB bundle remains **format unknown**
until inspected. If the pinned repack path emits plain JS, try only its
supported configuration with the project's matching compiler and record that
new experiment. If HBC or resource parity cannot be established, leave repack
unavailable and use warm `--build`. Do not quietly relabel source as HBC or
invent a bytecode-conversion/loader subsystem to preserve the 13 s claim.

Initially exclude linked `expo-updates` from repack support, including launch
selection/delegate behavior; an own build remains available. Keep the real
app's `expo-dev-client` dependency in the own-app experiment (§5). Cold-launch
must show embedded configuration, no non-empty dev-launcher/updates manifest
superseding it, and no Metro/OTA fetch. Failure is visible, not repaired by
silently removing a dependency and continuing under the same base receipt.

## 5. Non-GUI installation, launch and witness lifecycle

Separate preparation from execution. Prefer `expo prebuild`/pod preparation
plus direct `xcodebuild`, followed by `simctl install` and the existing witness's
`simctl launch <udid> <bundle-id>`. A pinned Expo CLI's
`expo run:ios --no-install --no-bundler --configuration Release` is an
implementation alternative **only if its installed version supports it and a
non-GUI test confirms it skips installation, URL opening and GUI activation**.
No `open -a Simulator`, AppleScript, GUI session or Accessibility permission
belongs in the required path. Do not blanket-ignore Expo exit 1 or use a log
substring as a replacement for a successful build process and verified output.

`expo-dev-client` explains stage 0's wrong launch URL even with Release. The
witness launches the **bundle ID directly**, never `exp+...` or a dev-server
URL. Keep the application's dependency/config unchanged for the comparison;
inspect resulting Release behavior. Verify `__DEV__ = false`, native Snapback
available, the intended bundle digest and visible JS marker, initial config,
and absence of a developer launcher/Metro dependency on every cold launch.
If direct launch still enters a launcher or selects another manifest, fail
with the observed behavior and rebuild after an explicit project correction.
A successfully installed app and a PID alone are not smoke evidence.

The existing process rules remain: explicit dedicated UDID, or exactly one
available booted simulator; no unresolved `booted` target; no stolen backend
port; stop only recorded owned PIDs. Add a per-UDID preparation/run lease so
parallel builds cannot install over another witness. Refuse a running app
before replacement. Preserve artifact reservations and failed preparation
logs/manifests. Do not clear a simulator or keychain belonging to another run.

Install once **before prime**. A fresh dedicated simulator and a disposable
nonempty fixture are the first-slice baseline. Authenticate through the app's
normal flow; no fabricated guest, session or replica. The base and repack
proofs are separate runs, each declaring fixture, authentication and reset
policy. If the second uses the first run's store, name that reuse explicitly;
it does not prove a fresh installation. Uninstall alone does not clear
SecureStore/keychain. No reset, reinstall, repack or data injection occurs
between a run's prime/offline/restart segments.

Reuse the existing smoke:

1. **Prime:** the app's own published native client authenticates and completes
   online acquisition. Record held counts, identity, generation, watermark,
   link and errors after the render pause; seed nonempty history for acceptance.
2. **Offline:** terminate and verify absence, stop the owned backend and verify
   connection refusal, then cold-launch the same installed app/store. Compare
   held counts/identity and offline link; run no-argument/all-optional queries.
   Loading, thrown queries or uncaught errors fail. An explained refusal stays
   a refusal, not a successful answer.
3. **Restart:** terminate, advance the stopped backend with the existing
   zero-write barrier, restart it and cold-launch. Require online progress
   through that exact sequence; reread final state and require the owned PID
   alive until deliberate termination.

An online-only fallback cannot pass native smoke. Empty partitions establish
opening/lifecycle only. Smoke does not assert required-argument queries,
writes, media, search correctness or recipient read states. The application's
own `WitnessRunner`, visible UI and normal client supply deeper assertions;
no supplied runner means missing evidence, not an invented scenario.

## 6. Receipts, proof identity and refusals

Keep an external `proof.json`, whose SHA-256 identifies the preparation for
one run, and a finalized run manifest that hashes that proof plus video,
screenshots, raw receipts and logs. No artifact hashes itself. Inventory
payloads with sorted relative paths, file types/modes, byte lengths, SHA-256
and bounded relative symlink targets; reject escaping links. Preserve all
base and output bytes; verify the installed app matches the selected output
before launch and again at collection.

Seal `proof.json` before the first launch. It contains prepared inputs and
expected execution identity, not future results. Observed runtime facts,
actual backend/store observations and execution timings go into startup/raw
receipts and the finalized run manifest, checked against that immutable proof.

| Proof field | Claim |
| --- | --- |
| `proofKind` | `application-release`, `application-release-repack`, or, for the deferred alternative, `exported-bundle-host`. Legacy receipt-less installs use `installed-application`, with preparation unknown. |
| `nativeBase` | Immutable source `.app` inventory digest, executable/framework digests, `build.json` digest and native input fingerprint; null for an install with unknown preparation. |
| `executedApp` | Actual installed `.app` inventory, bundle ID/build fields, target/configuration, native probe/helper identity. For an own build it is the base; for repack it is the separately hashed output. |
| `javascript` | Actual launched bundle digest, length, HBC/compiler identity, assets/public-config digests and current JS input provenance. A previous `dist` digest is only an optional distinct source reference. |
| `transformation` | Repack tool/version/integrity, argv, source and result inventories, fingerprint comparison and changed-file list, or null for an own build. |
| `runtime` | Selected UDID, simulator type, iOS version/build, Xcode/SDK, architecture and expected Hermes/New Architecture/Release configuration; startup must corroborate it. |
| `scope` | Requested scenario and limitations, fixture/auth/reset policy, intended backend origin/store and completed preparation timings. |

The proof and raw receipts bind **both the native base app digest and actual
JS bundle digest**, plus the repacked app digest when applicable. Recheck that
binding on every relaunch. Extend the native witness startup observation to
report the actual embedded bundle digest and native identity along with the
run/proof digest; require agreement before accepting steps. Do not merely
have JS echo environment strings. For a future direct host loader, distinguish
`embeddedJavascript` from `launchedExport`; the inert host JS is not the app.

Retain the strict `witness: {at, step}` envelope. Add proof observations in
an allowed application receipt field through the helper/driver contract, with
an explicit format version; changing the reserved envelope would require both
validators to change. Record failure and liveness after terminal receipts for
application scenarios as well as smoke. Hashes and lifecycle observation bind
local evidence to bytes; they do not independently attest app assertions.

Preflight reports all independent mismatches with expected/actual values,
paths and recovery. Proposed additional codes, registered with the existing
guide/tests only when implemented:

| Code | Refusal and recovery |
| --- | --- |
| `E_WITNESS_BUILD` | Prebuild/pods/Xcode failed, timed out or selected no unique product; preserve logs, correct the named input and rerun `--build`. Never launch a cached older app. |
| `E_WITNESS_NATIVE_COMPAT` | Missing base provenance or native fingerprint/config/toolchain mismatch; list the diff and use `--build`. |
| `E_WITNESS_REPACK` | Unsupported repack version/output, modified native bytes or unexpected metadata/resource changes; preserve output and use a warm build. |
| `E_WITNESS_HERMES` | Unknown bundle format, plain JS, wrong compiler/engine/HBC header or target/architecture; rebuild with the recorded Release toolchain. |
| `E_WITNESS_PROOF` | Base/output/installed/launch digest or proof binding differs; refuse execution/pass and rebuild/repack from verified inputs. |
| `E_WITNESS_ORIGIN` | Bundle or actual client origin differs from the owned backend; rebundle for the printed origin or select its matching free port. |
| `E_WITNESS_SCHEMA` | Later application-receipt projection/coverage failed; retain raw evidence and repair the scenario. |

Existing platform, simulator, input, app, backend, port, process, artifact,
receipt, step, timeout and interruption codes retain their meanings. Linux
refuses before invoking native preparation. No new repository-wide gate follows.

Withdraw round 0's universal “missing required module fails even if JS
catches it” guarantee. Native lookup cannot determine application intent:
Expo required and optional helpers share a lookup, and ordinary `expo-asset`
catches `requireNativeModule('ExpoGo')`. RN `get`/`getEnforcing` share a lookup
too; Fabric can fail at render. Optional misses are diagnostics; explicit
scenario requirements and actual assertions decide failure. An uncaught
startup error, missing native smoke attachment, fatal process exit or declared
required capability failure prevents pass. Unexecuted/caught application bugs
remain outside smoke's coverage. Own native closure equality avoids the host's
extra-module feature-detection problem; it does not prove every JS path.

## 7. What remains of packaging and publication

**No simulator host npm package is proposed for the chosen route.** Remove
round 0's sibling payload, default optional dependency, cohort publication
build, host size thresholds and host-first publish ordering. The builder's
`.app`, local base cache and run artifacts stay local. General Darwin CLI
users do not download a simulator application. There is no new export wrapper
or publisher-maintained constants/asset/native-lookup adapter.

The existing CLI/Expo packages carry build orchestration and witness support
when implemented, with the JS preparation helper and exact tool dependencies
placed through their existing package layout. The macOS slice resolves and
records those pins; no floating `npx --yes ...@latest` acquisition may be hidden
in a timed proof. Cold helper installation is reported separately. Measure
actual package delta before making a download-cost claim.

Preserve existing publication's own-app build, linked Snapback archive check
and deeper chat witness. Qualify the new helper through the existing native
lane and installed-consumer path when it ships; a repack fixture can supplement
that evidence, never replace the proof that the Expo package links into a
fresh own application. Resume continues to retain exact qualified tarballs.
No host qualification is added to every Snapback release.

Local reuse is keyed by complete native inputs and actual immutable base
bytes, not by current package version alone. Requalify each changed JS bundle
by execution. If a host later becomes justified (§10), choose distribution
after measuring it: an explicit opt-in, platform-filtered sibling is the
starting alternative, not a nested default dependency. `--omit=optional` also
omits the CLI's platform binary, so it is not a host-only escape hatch.
Unchanged host reuse would require a complete native-input key and explicit
compatible JS/helper-version mapping; rebuilt native inputs create a new
artifact, and publication resume may never substitute bytes.

## 8. Application artifacts and frozen-instrument honesty

The three preparation selectors are exclusive: `--build`, `--repack`, or
legacy `--bundle-id`. Build/repack derive the bundle ID from the verified app;
`--app-project` disambiguates the Expo root for repack. Backend cwd/port rules
remain unchanged. Preserve explicit `--artifacts`, a fresh output directory
per attempt and no-overwrite behavior.

Own-build smoke retains `smoke-ios-*`; repack smoke uses `repack-smoke-ios-*`.
Each has video, three segment PNGs, raw JSONL, logs and a manifest. Print
“Own Release smoke passed” or “Repacked own-app smoke passed”, with the actual
scope. Generic smoke never generates `m6-a*`/`m8-a*` claims.

Preparation kind is derived from verified provenance, not a caller-selected
label. The new application-artifact projector cannot emit a frozen native
pass from `installed-application` alone: it needs a validated own-build
receipt or equivalent independently checked build provenance. Re-entering
through legacy `--bundle-id` cannot turn a repack into an own-build result.

For app-defined `m6` and `m8` segments, names and status policy are explicit:

| Preparation | Artifact prefix | Frozen native status |
| --- | --- | --- |
| Own Release build and complete admitted application scenario | `m6-ios-*` / `m8-ios-*` | Eligible only after native scenario/schema/media validation under the instrument. Smoke alone is insufficient. |
| Own binary repacked with new JS | `repack-m6-ios-*` / `repack-m8-ios-*` | No `pass:true` until the benchmark explicitly admits this preparation kind. |
| Deferred published host | `host-m6-ios-*` / `host-m8-ios-*` | No `pass:true` until explicit host admission. |

Host/repack results may have their own external status records
`ios-repack-m6`/`ios-host-m6` (and m8), kept **outside** the frozen
`--simulator-status` input, which accepts only its two original IDs.
Do not rename files, alias IDs, attach a repack receipt to a native `pass:true`,
or rely on extra metadata surviving ingestion. With only this alternative
evidence available, the frozen `ios-simulator-m6`/`m8` entry stays `pass:null`,
`receipt:null`, with a reason naming the separately retained result. A genuine
separate own-build result keeps its own status. Record future admission with
its policy/instrument version; it never retroactively changes frozen scores.

This matters because [the status normalizer](../benchmarks/tools/social-messenger/choreography/choreography.mjs)
reconstructs a fixed object and, for `pass:true`, only requires a receipt
pointer. It drops extra proof-kind fields and does not validate the movie or
assertions. A manifest disclaimer is insufficient protection against that
path. Every standalone projected assertion must carry `proofKind` and the
full proof SHA-256 in an allowed `timings[].note` text field (or
`details.reason` where appropriate). Every host/repack video and screenshot
must visibly show the proof kind and a readable short proof digest, with the
full digest in its manifest/receipts. The witness-only label must not obscure
the tested UI; it is present during recording, not a replacement edited movie.

Application runners retain their visible screen and same client. Later schema
projection takes explicit assertion objects, preserves raw protocol JSONL
separately, validates **every** projected line against the supplied closed
schema, and binds line mapping and coverage declaration. Populate the allowed
proof note before projection and check it against the driver; never add a
forbidden top-level field or strip envelopes from empty milestone rows and
call them assertions. Bind exact fixture IDs, bodies, occurrence counts,
media/cache observations, ordering and final receipt states in raw observations
and schema-allowed notes/metrics. One continuous run uses `bestOf: 1`.

M6 still needs cold-offline held history, viewed ordinary media, consumed
view-once denial with no cached open, search/open, two visible pending sends,
ordered exactly-once flush and **Bob's actual app/client open/read progression**.
A forced server-side `read` value cannot replace that observation. Finalize
video before hashing and validate the complete artifact set and coverage.
Missing observations/artifacts, wrong run IDs or failed lifecycle steps fail.

M8 remains a later driver increment: the frozen scenario starts **warm**
offline, whereas today's `--prime --relaunch` starts its scenario cold. A
versioned warm handoff must start recording before the backend stops, signal
verified offline to the same primed PID, await two pending sends and
`relaunch`, then terminate and relaunch offline without resetting storage or
sending again. Prove those exact pending bodies once/in order (`m8-a17`),
then ordered flush and final read (`m8-a18`). Existing cold restart is useful
evidence but is not this sequence. Keep schema projection, warm handoff and
benchmark admission outside the first build/repack smoke slice.

## 10. Alternatives, risks and costs

| Mechanism | Measured evidence | Decision |
| --- | --- | --- |
| Own cold Release build plus witness | Cal25 build/install 359 s, dependencies 30 s separately; launch/smoke still pending. | Primary first use: actual native integration and identity, bounded measured preparation. |
| Warm own build plus witness | Cal25 build/install 138 s with no native compilation; reference chat 65.349/89.319 s on other runs. | Simple fallback and comparison control. Already exceeds 120 s before smoke on stage-0 cal25. |
| Same-project fingerprint-matched repack | Cal25 output 13 s / reported 49 MB; HBC/launch/assets unverified. | Selected fast-path candidate, conditional on §11. Retains actual app binary/identity; does not prove a fresh build. |
| Prebuilt published host with repack | **Unmeasured** build, pack, download, install and proof. A host is a choice of native base, not itself a JS loading mechanism. | Deferred: removes builder's first native build but adds native-cohort custody, identity differences and distribution cost. No present evidence that these costs buy a necessary improvement. |
| Prebuilt host with direct local HBC loader | **Unmeasured**. Both reviews find the factory hook feasible; no executed loader or asset/config parity proof. | Deferred: may consume the existing HBC, but custom factory/config/assets adapters are extra work. Reopen only if own-build/repack measurements leave a material unmet need. |
| Publish unchanged chat example | Existing chat build/witness measurements above; no cal25 host measurement. | Proves chat. Its smaller graph is not cal25 support, and another app still needs repack or a loader. |
| Dev-client/Metro host, Expo Go, module-only probe | No comparable complete Release/HBC proof. | Useful narrower development/probe evidence; none establishes the real app's cold-offline UI/storage integration. |
| Local expo-updates delivery | No measurement here. | Deferred launch-selection/manifest/rollback machinery; excluded from the first repack/direct-loader qualification. |

If reopened, compare a **narrow** direct-loader spike against these measured
own-app paths before building packaging or a broad cohort. Use two visibly
different exports, first-import config, Router entry, a multi-scale PNG, a
`../`/monorepo asset and a runtime font, with no bundle/asset server on cold
relaunch. Preserve `ExpoModulesProvider`, its subscribers/delegate handlers,
`RCTAppDependencyProvider` and generated Fabric/TurboModule providers. Return
the local URL through `ExpoReactNativeFactoryDelegate.bundleURL()` before
runtime creation, not just `sourceURL(for:)` or `RCTBundleURLProvider`.

Exclude linked **expo-updates and expo-dev-client** from this first generic
host, including their delegate/manifest precedence paths. That host therefore
does not claim exact cal25 closure compatibility. Initial host admission
requires equality of the application's supported native closure plus explicitly
enumerated loader adapters, not a superset made “equivalent” by hiding modules.
Resolve exact versions, integrities, codegen, HBC/compiler and
`RCT_HERMES_V1_ENABLED`; never broaden to SDK-major admission to accept a
historical app. Admission means eligibility to execute in the disclosed host
environment, not behavioral equivalence or comprehensive prelaunch refusal.

For that alternative, config adaptation must precede the first Constants
access. A non-empty updates/dev-launcher manifest is a refusal, not a fallback.
Asset destinations must match the **post-transform strings embedded in the
bundle**, checked against export provenance; the serializer's asset-map
objects alone are insufficient for `../`/baseUrl cases. Unknown mappings,
plugin-embedded fonts, asset catalogs and unsupported native config refuse.
Required/optional lookup collisions are an experiment, not a universal guard:
Grok's proposed hiding of superset modules does not remove initialization
side effects or solve Astra's shared-lookup counterexample (§6).

An explicit scenario requirement for application identity routes to own-build.
Include `Linking.openURL(Linking.createURL('/inbox'))` as a negative host
comparison: the host may fail or open a different installed app despite an
admitted graph. Undeclared identity dependence can still occur in ordinary
startup; no automatic detector is promised. Keep scheme/entitlement/permission
limitations visible in receipts and label every host artifact. Measure all
phases and maintenance changes; no host speed/size estimate is a result.

**Costs that remain:** native builds after dependency/config/toolchain changes,
Xcode/runtime installation, app/base storage, conservative fingerprint
mismatches that force rebuilds, and maintaining a pinned Expo preparation adapter per SDK.
Stage 0 qualifies neither all SDK 57 patches nor all iOS versions. Start the
next experiment on its iOS 27.0/Xcode 27.0 arm64 setup, recording exact builds
and deployment minimum separately; older 26.4/26.5 publication results do not
qualify this app there. No Intel, Android, device or production signing claim.
Simulator artifacts need no Apple developer provisioning credentials; retain
any ad-hoc signatures and inspect toolchain changes instead of conflating
them with a physical-device signing workflow. [Expo simulator repack signing](https://docs.expo.dev/build-reference/repack/#signing)

All preparation is local development work, with bounded paths, validated
inventories and owned processes. The app still has its ordinary network APIs;
this is not a code sandbox or adversarial attestation. Use test credentials,
retain no ambient secrets, and account for visible data in recordings.

## 11. First macOS slice and acceptance

**One cal25-like app, one native base, one visible JS change, two smoke runs.**
Do not first build a general host, full module matrix, publication package or
M6/M8 harness. Use the real cal25 project if retained; otherwise record the
fixture's differences and lock a generated app with the same native dependency
shape, including dev-client, Router and video. Include normal unattended test
authentication, nonempty retained history, initial-import config observation,
a visible A/B marker, a scaled image (including a `../` asset where applicable),
a runtime-loaded font and a small local media reference. Add probes before
the base build so later changes remain JS/assets only.

The macOS lane records a dated report with exact source/tool pins, raw commands,
logs, rounded and exact byte sizes, input/output hashes and every failed attempt;
append the journal. Its concrete sequence is:

1. **Build A without GUI access.** Capture the lock/native inputs, run the new
   `--build` preparation from SSH or equivalent, inspect Release target/HBC,
   resolve the exact product and write immutable `build.json`. Install with
   simctl, direct-launch by bundle ID, and complete all three smoke segments.
   Prove A, first-import config, embedded assets and a nonempty offline screen;
   verify the native probe and no dev launcher/Metro. Preserve finalized video,
   segment PNGs, raw receipts, startup binding and run manifest.
2. **Repack B.** Change a visible JS marker/rendered behavior and one bundled
   asset, leaving native/config inputs unchanged. Verify fingerprint equality;
   run the pinned repack, inspect its actual HBC/compiler and complete app diff.
   Require native Mach-O digest equality and different JS/output digests.
   Install the new output before prime, run the same full smoke, and observe B
   plus the new asset online and cold offline. Retain separate labeled evidence
   binding A's base and B's executed bundle/output. An exit-0 repack alone fails
   this acceptance.
3. **Run bounded controls.** Native dependency/plugin or scheme change must
   refuse repack before install, with `--build` recovery. Tampered base/output
   or HBC mismatch must refuse. An intentional cold-offline startup error or
   online-only fallback must fail smoke; death after success must not pass.
   A concurrent owner/busy port must be preserved. Restore inputs between
   controls and keep their failure artifacts.
4. **Compare a warm own build of B.** Same snapshot, simulator, fixture/auth
   policy and witness scenario; compare behavior and proof kind, and report
   phase timings. If repack cannot meet HBC/assets/config/launch acceptance,
   record that failure and retain warm build as the chosen implemented path.
   Do not claim step 2 passed, or mark the full repack increment complete.

The first slice passes only when A and B actually execute through native smoke,
base/native/JS/output digests independently recompute, config/assets resolve
without a bundle server, and the specified controls fail for their intended
reasons. No scheme rewriting, simulated successful response, synthetic store
or automatic benchmark pass may repair a failure. If repack stays unavailable,
the own-build slice can ship with that limit and this RFC stays Draft for the
remaining candidate work. M1 docs must advertise only qualified behavior.

Then, as separate increments:

| Increment | Acceptance |
| --- | --- |
| Productize build/repack preparation and M1 discovery | Existing driver/guide/helper affected tests pass; legacy installed-app mode preserved; an M1 builder finds the printed route without being told the card name. No new host package. |
| Measure repeatability | At least ten complete repack+smoke attempts, cached dependencies/base/tools and booted supported simulator, fixed nonempty fixture and unattended normal auth. Report all successes/failures, per-phase/total times, median and nearest-rank p95; first install and hashing/finalization included. Target p95 ≤ 120 s; any failures stay visible and block an unqualified timing claim. |
| Report cold costs | Separately time dependency/helper installation, simulator boot, cold pods/build and fixture setup; include authentication waits and all invoked preparation in full elapsed time. Xcode/runtime downloads are setup costs, never silently removed from a cold claim. |
| Application evidence | Implement/validate real M6 assertions and M8 warm handoff, schema projection, standalone labels and status fencing (§8). A passing repack scenario stays separate until admitted. |
| Publication of helper changes | Existing native package/linkage and installed-consumer qualification; exact bytes retained through resume. Publication requires its own authorization and is not part of this design round. |

Tests are scoped to changed witness/helper/guide behavior and these native
experiments. No exact-HEAD full battery, new universal gate or budget raise.
If speed misses, report it and adjust guide wording; do not weaken smoke,
increase its timeouts to hide failures or replace it with an install check.
