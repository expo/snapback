# LLP 1018.007.001: Signup supplies first-write replay authority

**Type:** Plan
**Status:** Draft
**Systems:** Snapback 2 identity, replay grants, client session installation
**Author:** Codex, commissioned by Charlie Cheever
**Date:** 2026-09-09
**Revised:** 2026-09-09
**Related:** LLP 1018.007, LLP 1012, LLP 1001, LLP 1002, LLP 1018.004

## Confirmed cause

Grok's three new users authenticated but profile creation refused with no replay
grant, including after a 20-second wait; reload recovered. Current
`crates/snapback2/src/writer.rs` passes `None` into `session_json` for Signup,
while Login and Guest call `grant_if_low`. LLP 1012#7-writes-offline currently
lists resume/login/guest as grant issuers and omits signup too.

`client.ts` already captures a response grant, opens the new principal's
partition, and installs metadata. Ordinary `ClientAuth.session` does not run
resume merely because signup succeeded. Reload does run initializeOffline and
resume. This explains the workaround without making reload part of onboarding.

## Repair and security contract

Implementer: Codex gpt-5.6-sol, starting 2026-09-09. Mint a grant for the newly
created principal through the same owner helper used by Login/Guest and include
it in the signup session response. A fresh account has no remaining-ID claim.
Adopt it through the existing client grant/install path; do not add a second
login, special profile-write bypass, or template-owned replay lifecycle.

The grant stays principal-bound and server-issued. Every replay still requires
a live matching session; new IDs, expiry, OCC trace validation, and the
same-envelope terminal lookup retain their existing contracts. A grant does
not release old queued work past a resume fence. Refused signup must not yield
usable new authority. Account-switch and startup races must not adopt a grant
into another principal's partition.

Authentication may succeed while metadata loading fails; do not reclassify
that bearer as invalid. Preserve the explicit readiness refusal and ordinary
metadata recovery. Document any distinct failure after account creation rather
than claiming account-plus-grant allocation is atomic without checking it.

## Acceptance and documentation

Through a real owner and persistent client, await ready, signup with a fresh
identity, immediately create the profile once, and verify committed data from
another authorized query. No reload, login, explicit resume, or drained query
may be required. Repeat with startup still pending and with a browser carrier.

Pin fresh-account grant ownership, no grant on duplicate/failed signup,
cross-principal rejection, failed metadata/readiness recovery, and existing
same-principal replay after renewed authentication. Exercise actual client
adoption; checking only the JSON response is insufficient.

Update LLP 1012's grant-issuer list and existing auth/offline guide text. Amend
the closed capability-discoverability ticket's historical workaround with a
pointer to this repair, without rewriting its original evidence.
