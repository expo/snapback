## 4. Proposed sequence

### A. Reproduce and explain lookup selection first

Reduce the reported lookup into paired programs in the existing binder tests:
point lookup by row ID, lookup by a typed parent reference, absent target,
nullable reference and conflicting compatible indexes. Run the current package
and current source first; record selected index, key bindings, result shape and
whether behavior is already clear in `why`/diagnostics.

Prefer an existing explicit spelling if it already distinguishes the cases.
Only if it cannot express the distinction clearly, propose a narrow syntax
change with examples and compatibility consequences. Do not invent that syntax
in this plan. Changing a variable's reference type must not silently change a
claimed point lookup into a collection lookup.

Reuse binder facts in existing `why` and diagnostic output: source site,
selected index, key prefix, point/page result and the reason for selection.
Show a correction only when it binds to the intended table and existing index.
No cast between table identities, no inferred authority, no automatic semantic
rewrite. Keep successful checks quiet and within existing latency budgets.

### B. Make attribution complete in one tested example

Extend the existing maintained-data card with originals, replies, nested
replies, likes and deletion. State what each total counts and the consequences
of optional or missing targets. Exercise absent targets, backfill of existing
rows, delete/recreate identity and the supported recorded-versus-live semantics.
Use the current compiler and engine tests; do not create a parallel guide.

Evaluate whether existing `doctor`/inspection can identify missing captures
well enough. Add contextual reporting only for a reproduced gap; legitimate
nullable references are not universal warnings. Do not automatically backfill
or infer author policy. A sum-type reference or unified content table is an
alternative to evaluate only if the smaller recipe cannot express the app.

### C. Explain composition without widening the language by default

Use the existing feed card to show Following and Global side by side, including
repost identity, removal and the atomic writes maintaining the Global projection.
Test duplicate retries and rollback. Do not advertise unsupported union/merge
syntax or change private audiences to public to make the recipe fit.

Recheck the M6 guard example against the already implemented guidance LLP.
Add detail only if still missing. A read hoisted out of a guard may now fail on
a path that previously did not read; keep it an author decision, never a
`check --fix` transformation. Preserve authority and prediction classifications.

## 5. Acceptance and stopping conditions

- Paired lookup examples establish the intended row/page result and selected
  index, including absent and nullable cases; generated types agree.
- The attribution example matches an independently enumerated oracle for
  original and nested engagement, including the supported deletion semantics.
- Every suggested rewrite compiles and preserves its stated policy. Any
  intentional behavioral change is explained, not called a safe fix.
- Existing guide and affected binder/engine tests pass. No extra blocking check,
  language synonym catalog or second analyzer is introduced.
- After implementation is separately commissioned, use a small fresh-builder
  comparison with fixed tasks and retained attempts. Measure correction cycles,
  reading and elapsed time alongside correctness. A higher holistic score is
  neither a prerequisite nor sufficient proof of improvement.

Start with A; B follows independently of whether syntax changes. C is a small
recipe/explanation pass. If current output already resolves a case, keep it.
After three unsuccessful correction rounds, record the unresolved case and stop
that increment. Do not broaden the language merely to rescue the experiment.

## 6. Decisions before implementation

Which existing spelling should carry explicit point intent? Can selected-index
facts already be exposed without a new diagnostic model? What deletion and
missing-reference policy does the example promise? Resolve these against current
code and the owning derived-data LLP, rather than inferring them from the diary.
