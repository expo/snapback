## Withdrawal (2026-08-27)

Both families found the document's central factual claim false: the
whole-corpus flat is **not** a concatenation of the fourteen section
flats but a separate nav-order projection (`scripts/guide-lib.mjs`), and
`contentHash` covers the regenerated whole flat plus the two JSON
registries — not the packed page set — so §2a's "the digest is over
content the server already has" and OQ3's "it currently covers the
packed set" are both wrong. Grok noted this is the same error
LLP 0314.000 r5 already spent a review round correcting.

Codex then measured the alternative this RFC dismissed in one sentence:
`gzip -9` takes `registry.json` from 5,162,043 to 395,845 bytes and
`diagnostics-registry.json` from 2,526,048 to 152,125 — a 92.9%
reduction — and `crates/snapback-server/build.rs` writes raw `fs::read`
bytes with no compression anywhere in the artifact path. Container
compression is capability-preserving, needs no LLP 0061 amendment, no
identity change, and no consumer migration, and it was never considered
in the size program.

**Successor:** [LLP 0314.002](./0314.002-compress-the-embedded-guide-artifact.rfc.md).

## Summary

[LLP 0314](./0314-shipped-runtime-binary-size.research.md) F4 measures
"~20 MB of embedded Guide" in the shipped server binary.
[LLP 0314.000](./0314.000-reduce-shipped-runtime-size.plan.md) Phase 2
relocates that corpus out of the binary — and says so plainly: "Phase 2
relocates the Guide, it does not delete it."

This RFC is the complementary move. Of the ~20 MB, roughly **2 MB is
hand-authored prose**. The rest is derived: 8.2 MB of flat projections
that are concatenations of pages already present, and 9.9 MB of
`guide/reference/` generated registries. The largest single file in the
corpus is a 4.08 MB whole-corpus flat that is a byte-for-byte
concatenation of the 4.09 MB of section flats sitting beside it.

Proposal: **do not ship derived bytes that a server holding the source
pages can produce on request.** This is orthogonal to Phase 2 — it
shrinks the corpus wherever the corpus lives — and it is much cheaper.

Confidence is **0.85** for the flat projections and **0.5** for the
reference registries, which have a real "must be build-bound" argument
(§4).

## 1. Measurement

`guide/` totals ~20 MB. Breakdown as of 2026-08-27:

| Group | Bytes | Nature |
|---|---|---|
| `guide-flat.generated.md` (whole corpus) | 4,084,811 | concatenation of the 14 section flats |
| `guide-flat.<section>.generated.md` × 14 | 4,086,223 | concatenation of that section's pages |
| `guide/reference/registry.json` | 5,162,043 | generated API registry, 1,461 symbols / 56 modules |
| `guide/reference/diagnostics-registry.json` | 2,526,048 | 3,575 codes / 9,597 sites |
| `guide/reference/diagnostics.md` | 755,033 | rendered form of the above |
| `guide/reference/expo-snapback-client.md` | 501,468 | generated per-package reference |
| `guide/reference/published-symbols.json` | 294,833 | 4,248 identities |
| `guide/reference/*` remainder | ~660,000 | generated per-package/per-module references |
| all hand-written pages (176 `.md`, all sections) | ~2,300,000 | source |

The whole-corpus flat (4,084,811) and the sum of the section flats
(4,086,223) differ by 1,412 bytes — separator framing. They are the same
content twice, and both are the same content as the source pages a third
time.

`crates/snapback-server/build.rs:139` *asserts* the section flats are
present before packing, so the redundancy is currently required by the
build rather than incidental.

## 2. Proposal

### 2a. Do not ship any flat projection (≈8.2 MB)

The server holds every page. Concatenation is a pure function of the
manifest plus the pages, and the manifest already carries `contentHash`
per `build.rs:152`.

- `GET /_snapback/guide/flat.md` and the per-section flats keep their
  URLs and their bytes, computed on request from the embedded pages.
- The `x-snapback-guide-content-sha256` and
  `x-snapback-server-build-commit` headers are unchanged — the digest is
  over content the server already has.
- The `.generated.md` files are removed from `guide/` and from the packed
  artifact. `build.rs`'s section-flat presence assertion is deleted.
- `GET /llms.txt` keeps listing the flats with approximate sizes; the
  sizes become computed rather than `stat`ed.

The one behavioral question is per-request cost. A 4 MB concatenation on
a rarely-hit bulk endpoint is a cache-on-first-use, not a hot path. `[inferred]`

### 2b. Ship the reference registries in one form, not two (≈1.3 MB)

`diagnostics.md` (755 KB) is the rendered form of
`diagnostics-registry.json` (2.5 MB). Both ship. Pick one as the shipped
artifact and render or parse the other at request time. The same question
applies to the per-package `expo-snapback-*.md` files versus
`registry.json`, which carry overlapping symbol data.

### 2c. Reference registries: reduce at the source, not the encoding

`registry.json` is 5.16 MB for 1,461 symbols — about 3.5 KB of JSON per
symbol. `diagnostics-registry.json` is 2.5 MB for 3,575 codes across
9,597 sites. Both are large because the *things they describe* are
large. Compression of the encoding is a marginal fix;
[LLP 0322](./0322-tiered-diagnostic-codes.rfc.md) (fewer public codes) and
[LLP 0323](./0323-tiered-public-surface.rfc.md) (fewer published symbols)
are the real reductions, and this RFC defers to them rather than
inventing a third answer.

## 3. What this does not do

- **It does not amend LLP 0061 §4a.** The Guide stays embedded, always
  served, one build-matched corpus, with the server as the structural
  version authority. Serving a projection computed from embedded pages is
  *more* faithful to "one build-matched corpus" than shipping a second
  copy that can skew.
- **It does not conflict with LLP 0314.000 Phase 2.** Phase 2 changes
  *where* the corpus lives; this changes *what is in it*. Both, together,
  are ~8 MB smaller than Phase 2 alone. Phase 2's three assembly modes,
  bare-binary tuple, and pack-time refusal are unaffected — they carry
  fewer bytes.
- **It does not change any Guide URL or response body.** That is the
  invariant. LLP 0314.000's standing constraint — layout may change,
  "ready-file, health, or Guide *URL* semantics" may not — is respected
  exactly.
- **It does not touch the hand-written corpus.** The ~2.3 MB of prose is
  the product. It is not the problem.

## 4. Open questions

- **OQ1 — Is on-demand concatenation acceptable at the served tier?**
  Needs a measured p99 for `GET /_snapback/guide/flat.md` computed
  versus served. If it is bad, the fallback is to compute once at server
  start and cache, which costs memory rather than artifact bytes and is
  still strictly better than shipping the file.
- **OQ2 — Does anything consume the flats from disk rather than HTTP?**
  `snapback mcp` exposes per-section flats and the whole-corpus flat as
  `snapback-guide://` resources. Those resolve through the same embedded
  corpus, so they should follow automatically, but the MCP resource
  listing must be checked — a listing that `stat`s files will need to
  compute sizes instead.
- **OQ3 — Does the guide manifest's `contentHash` need to change
  meaning?** It currently covers the packed set including the flats.
  Removing the flats changes the hashed set. LLP 0314.000 r5 already
  touches this area ("compiling in the whole-artifact digest"), so the two
  should be reconciled rather than solved twice.
- **OQ4 — Is `guide/reference/` a guide section at all?** It is 9.9 MB of
  machine output living in a corpus whose LLP 0259 read budget is
  measured in pages. Making it a sibling artifact rather than a section
  might be more honest than shrinking it. Out of scope here; noted
  because §2c defers the real reduction elsewhere and this is the third
  option.

## 5. Cost

For §2a: delete files, delete one build assertion, add a concatenation
handler with a cache, update `llms.txt` size computation, verify the MCP
resource listing. Small — a day, plus the OQ1 measurement.

§2b and §2c are progressively more entangled with LLP 0194, LLP 0322,
and LLP 0323 and should not be attempted in the same change.

## 6. Why it matters

LLP 0314 frames the embedded Guide as the cost of the LLP 0061 carriage
decision, and 0314.000 correctly treats changing that carriage as a
design amendment requiring care. But most of the 20 MB is not the
carriage decision — it is derived bytes that got packed because they were
sitting in the directory. Removing them requires no amendment to 0061 and
no argument about carriage. It is the cheapest large reduction available
in the size program, and it is currently not in it.
