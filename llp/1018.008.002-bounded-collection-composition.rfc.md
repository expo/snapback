# LLP 1018.008.002: Bounded collections that compose without losing proof

**Type:** RFC
**Status:** Draft
**Systems:** Quarry expressions and bound graph, IR collection lowering, certification and capped-source lineage, evaluator parity, authoring diagnostics
**Author:** Codex, commissioned by Charlie Cheever
**Date:** 2026-09-10
**Revised:** 2026-09-10 (initial proposal)
**Related:** LLP 1018.008, LLP 1010, LLP 1011, LLP 1018.005, LLP 1001 §3, LLP 1017, LLP 1017.000, LLP 1019, LLP 1020

## 1. Outcome and evidence gate

A builder should be able to turn an already bounded page into a bounded list
of values without an auxiliary table or duplicated literal construction. The
list must retain the source's completeness and authorization restrictions.
Finite cardinality does not prove that the source population was complete.

The [existing ticket](../issues/20260904-quarry-no-list-from-range.md) wanted
to store original recipients for later unsend. LLP 1019 now owns that problem,
so do not implement a parallel recipient log to demonstrate this proposal.
First reproduce a remaining app need after that work lands: for example, a
certified capped group of readable accounts projected into one bounded effect
payload, or bounded display identifiers passed to another expression helper.
If no real application needs the operation, leave this RFC Draft or shelve it.

Design author: Codex, 2026-09-10. Runtime implementer/date are unassigned.
The proposal is a narrow language extension, not permission to add arbitrary
filtering, general iteration, a new handler language, or a larger ceiling.

## 2. Proposed expression

The candidate spelling is `collect <page-expression> { <element-expression> }`.
Within the element expression, `.` is that page row, as in a shape. The braces
contain a single expression; a projected record uses a nested record literal.
This paragraph specifies proposed syntax; these examples do not compile today.

```q
members = memberships[conversationId] first 50 by byConversationPrincipal
recipients = collect members { .principal }
cards = collect members { { principal: .principal, role: .role } }
```

The page expression evaluates once. Element expressions evaluate exactly once
per returned row, in page order. The result's bound is the certified page bound,
and its element type is inferred from the projection; a page bounded at 50
produces `[principal] <=50` in the first example. No truncation is introduced.
An empty authorized page produces an empty list. Missing offline coverage
produces the current whole-query partial result, not an empty complete list.

The first slice accepts nonoptional pages and expression-only projections.
It supports a bound page variable or bounded read; it does not introduce a
callable closure value. Allocation, writes, `emit`, `require`, and new callback
effects in the projection are excluded. Ordinary permitted read expressions
keep their existing cost and authority. Optional inputs need explicit narrowing;
optional element values remain optional elements rather than disappearing.

Arrays remain values and have no page cursor. A query that returns `collect p`
alone does not obtain continuation just because `p` had one. An API needing
pagination should return the page or a certified shape using the existing
page law. This is a deliberate boundary of list materialization.

### Representation

Bind a finite projection node in Quarry, then lower it to the existing bounded
iteration and list construction IR where possible. Evaluate the input once
into a fresh symbol, allocate one result list, and append one projected value
per iteration. Use the current lexical hygiene and argument-evaluation rules.
The implementation must verify that existing native/twin IR supports this
semantics and proof lineage before committing to this representation; no new
runtime opcode is justified just by the surface spelling.

## 3. Completeness cannot be laundered through a list

LLP 1001's capped-only policy follows originating read sites, not the display
type of the value. The compiler/certifier must retain origin and bound through
projection, aliases, object fields, helper parameters, branches, and list
construction. In particular:

- Returning a display list from a nonuniform scan remains capped under the
  existing read policy; a short returned list does not prove exhaustion.
- Feeding such a list into mutation fan-out does not turn it into a complete
  bounded argument. Preserve the same structural refusal as looping over the
  source page. Storing it as a complete roster is likewise a structural sink.
- Projecting a schema-capped group can support complete fan-out only when the
  existing cap, covering bound, and uniform-rule proof already establish it.
- An ordinary field derived from an unreadable point read remains absent;
  missing offline authority remains partial. Projection introduces no zero
  fallback or new read authority. Existing maintained point-read semantics
  remain unchanged, including partial replay when the authority is unheld.
- Passing through a helper or returning from one cannot erase origin. If the
  existing IR cannot express the required lineage, refuse the unsupported
  lowering until the certifier can preserve it; do not rely on TypeScript's
  static type as the server's proof.

No hidden/examined-position cursor is added. No comparison between empty
physical storage and an exhausted run of unreadable rows becomes observable.
The privacy tradeoff of LLP 1001 §3 remains explicit.

### Pricing

Charge the input read once, projection work up to the source cardinality,
every nested point/rule probe, the maximum output width and escaped encoding,
and the result's retained list storage. A nested projection multiplies the
appropriate bounds; aliases do not re-execute the page. Price branches by the
existing analyzer's rule, not an example's observed row count.

Build on LLP 1020's actual recurrence/pricing repairs and `check --cost`
representation. This RFC neither repairs that estimator independently nor
raises its meters. Native execution and the twin must agree on order, optionals,
partial results, bounds, and resource refusal.

## 4. Explain the remaining access constraint

LLP 1017.000 has already repaired the general fan-out rewrite. LLP 1020 owns
priced-plan output. Extend those existing diagnostics only where this new
projection obscures an originating read: name the source scan and why its
lineage reaches the rejected sink. Use existing `bound`/`quarry` families and
the bounds guide; do not add a diagnostic registry or command.

Where the compiler can identify an equivalent viewer-pinned existing index,
show that concrete spelling. Otherwise explain the unsatisfied prefix/rule
dependency without fabricating a safe schema transformation. Never propose
making a table public, copying hidden rows into a readable table, or dropping
a policy conjunct to make a proof pass. Automatic authorization denormalization
and a stronger uniformity theorem are outside this proposal.

The successful experience should be: an already finite, permitted computation
has a direct spelling; a refused computation identifies the real missing proof.
It should not require learning that a list silently lost provenance at a helper.

## 5. Acceptance and deletion

Use current compiler fixtures and the shared Rust/twin corpus. Cover zero and
maximum rows, Unicode/escaped maximum-width values, nested record projection,
optional elements, aliases and imported `fn`, nested bounded projections,
one evaluation of an order-sensitive source, hidden joined rows, and partial
offline coverage. Include negative controls that route a capped-only source
through each supported alias/field/helper form into a structural mutation sink.
Each must still refuse; the covering-cap control must certify.

Exercise a real surviving application use case online and offline. Remove its
auxiliary storage or repeated list construction. Compare source, check latency,
certificate totals, and full local-runtime bytes. No per-recipient log rewrite
is credited here; that belongs to LLP 1019.

If the syntax is accepted, amend the frozen word inventory and NOT-DOING Moves
with the concrete use case and the named displaced work. The proposed trade is
this one projection instead of a general list API, filter/append methods, or
merging `fn` and `proc`. Their deferred status is unchanged. The current draft
does not itself authorize a word-inventory change; acceptance must confirm the
offset against the then-current doing-list.

## 6. Alternatives and open decisions

A generalized scalar page shape could avoid the word `collect`, but conflates
a cursor-bearing page with a materialized list. A list-comprehension language
is broader than the witnessed need. The proposed spelling makes the loss of
cursor capability visible. Review should compare those options on real examples
before fixing the grammar.

The other question is whether existing native lineage already survives the
proposed lowering. Establish that with positive and negative fixtures before
choosing a representation. This is not grounds to repeat LLP 1020's separate
soundness project or to weaken incomplete-fan-out refusal.
