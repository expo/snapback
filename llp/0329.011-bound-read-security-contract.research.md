## Summary

[LLP 0329.010](./0329.010-cost-of-a-mutation-step.research.md) H5 established that
the mechanism for a visibility-composed bound read already exists in the mutation
executor, and that the remaining open item is a **policy** question:

> Which visibility should a mutation's bound read compose, and what is the
> noninterference contract when a refusal depends on rows the caller cannot see?

This document answers it. It also contains a same-day self-correction worth reading
before the contract: I claimed `coterie` contained a live instance of LLP 0120's
predicted leak, and **withdrew it** on finding the counted table is `public-read`
(§S1). The larger finding that replaced it is §S4 — `coterie` declares *every*
private-messaging table `public-read`, which means the contract below was never
actually exercised against protected data.

**Recommended contract.** Caller visibility by default; elevated reads admitted only
under a *mechanized* form of the pattern `guide/auth/protecting-data.md` already
prescribes; and capacity/count refusals admitted only over a domain the caller is
authorized for, because otherwise the refusal itself is the disclosure.

## Findings

### S1 — WITHDRAWN: the mechanism is real, the disclosure is not

> **Withdrawn 2026-08-28, same day.** I claimed below that `CHAT_ENVELOPE_EXCEEDED`
> discloses a third party's private state. It does not, because `coterie` declares
> `conversationMembers` as **`public-read`** (see S4). A caller can enumerate any
> profile's memberships directly, so the refusal reveals nothing they could not
> already read.
>
> **What survives:** the *mechanism* — a declared refusal whose threshold is computed
> from a third party's row count — is exactly as described, and would be a disclosure
> under any schema where the counted table is protected. What fails is the claim that
> a disclosure occurs here.
>
> I did not check the counted table's visibility before making a security claim about
> it. The text is retained unrevised below as the record of the error; the ticket
> carries the same correction.

#### Original text (claim not corrected)


LLP 0120 §Noninterference states the general rule — "a count over rows the caller
cannot see discloses their existence even though no row is returned" — and names the
specific trap: "**the refusal threshold itself becomes a side channel** unless the
ceiling is stated so that refusing does not reveal invisible-row counts."

`coterie` does exactly this:

```js
export const openDm = defineJsMutation({
  auth: 'authenticated',
  args: { otherProfileId: v.id('profiles') },
  refusals: ['PROFILE_REQUIRED','PROFILE_NOT_FOUND','SELF_DM_FORBIDDEN','CHAT_ENVELOPE_EXCEEDED'],
  handler: async (ctx, args) => { … return openDmCore(ctx, creator, other, existing); },
});
```

`openDmCore` → `createConversationCore` → `requireChatEnvelopeCapacity(ctx, input.initialProfiles)`,
and that helper counts **each profile's** conversation memberships:

```js
async function requireChatEnvelopeCapacity(ctx, profiles) {
  for (const profile of profiles) {
    const chats = await ctx.db.query('conversationMembers')
      .withIndex('by_profile_latest_chat_page')
      .eq('profileId', profile._id).eq('isLatest', true)
      .take(chatHistoryEnvelopeLimit()).collect();
    if (chats.length >= chatHistoryEnvelopeLimit()) ctx.refuse('CHAT_ENVELOPE_EXCEEDED');
  }
}
```

`initialProfiles` includes the *other* party. `addGroupMemberCore` calls it as
`requireChatEnvelopeCapacity(ctx, [targetProfile])` — the target, not the caller.

So any authenticated principal can call `openDm` with any profile id and learn from
the declared refusal code whether that user is at their conversation limit. It is a
one-bit disclosure about another user's private state, and it is a *declared* refusal,
so it is part of the published API surface rather than an incidental error.

Filed as `issues/shelved/20260828-coterie-chat-envelope-refusal-discloses-other-profile-state.md`.

**What this is and is not.** It is an application-level defect in a benchmark
instrument, not a platform vulnerability, and the disclosure is small. Its
significance is evidential: capable agents wrote it, review did not catch it, and
**nothing could have caught it**, because in a JS handler no analysis relates a
refusal to the visibility of the rows that caused it. That is the argument for making
this class of read declarative — not that declarative is tidier, but that it is the
only form in which the platform can reason about disclosure at all.

### S2 — The existing elevated-read contract is the right shape, hand-executed

`guide/auth/protecting-data.md` already prescribes what a mutation must do when it
needs rows past caller visibility:

1. check the host-owned permission declaration on a **nominal resource argument**
   (`ctx.permissions.X.requireRole(...)`, which "derives the effective principal on
   the host and returns no roster data");
2. read via `ctx.db.elevated`, whose closed surface is `get`, `getMany`,
   `uniqueMany`, `query`, and which "bypass[es] only table row visibility" while
   keeping bounds, snapshot capture, and OCC validation;
3. **verify every resolved row belongs to the authorized resource** — the guide calls
   these post-read comparisons "load-bearing" and says they "prevent an authorized
   conversation id plus an unrelated message or quote id from becoming an
   object-reference bypass";
4. add negative identity tests for a non-member and for a foreign row id.

The contract is sound. What is unsound is its enforcement: the guide requires it "in
**every** named function" and calls the repetition "intentional." Steps 1 and 3 are
load-bearing and unenforced, so every omission is silent.

A declarative bound read can mechanize exactly these: the resource argument and its
permission are declared, and the scope predicate binding returned rows to that
resource is part of the step rather than an author-remembered `if`.

### S3 — Recommended contract

**Default: caller visibility.** A bound read composes the table's declared read
visibility for the effective principal, exactly as `build_query_sql` already does for
reads (LLP 0329.010 H5). No new authority; a mutation can read what its caller could
read. This covers rung A entirely — uniqueness checks against a table the caller can
read — and is the safe default an agent gets without deciding anything.

**Elevated: admitted only with a declared scope.** Reading past caller visibility
requires, in the plan and checkable at generate time:

- a nominal resource argument, and a declared permission over it (LLP 0240 authority
  profile, as the existing predicate already requires);
- a scope predicate on the read binding every returned row to that resource.

This is S2 steps 1 and 3 turned into structure. It grants nothing `ctx.db.elevated`
does not already grant a JS handler today — it removes the opportunity to forget.

**Counts: authorized-domain only.** A `count(binding)` may participate in a refusal
only when the counted domain is scoped to a resource the caller is authorized for.
`insertMessageCore`'s message-envelope check qualifies (the sender is a member of that
conversation). `setFollowCore`'s following-set check qualifies (the caller's own
follows). **`requireChatEnvelopeCapacity` does not** — it counts a third party's
memberships — and under this contract it would be refused at generate time, which is
precisely the outcome S1 wanted.

Of LLP 0120's five shapes this is **visibility-before-aggregation** for the default
and **sealed refusal** for the unprovable case, with public-only and
partition-by-authority left available as later widenings. It deliberately does not
adopt "weaker claims, declared," because a declared-weak aggregate re-creates the
capability-by-authoring-form problem this whole family exists to remove: two counts
that look alike with different disclosure properties.

**Corollary the S1 case makes concrete:** a refusal is an output. Any analysis that
classifies what a *returned value* may disclose must classify refusal codes the same
way, or the contract has a hole shaped exactly like `CHAT_ENVELOPE_EXCEEDED`.

### S4 — coterie has almost no protected tables, so it cannot test this contract

Every table in `demos/coterie/snapback/schema.mjs` and its declared visibility:

| Table | Visibility |
|---|---|
| profiles, posts, postImages, postVideos, feedEvents | `public-read` |
| follows, likes, reposts | `public-read` |
| **conversations, conversationMembers, messages, messageReceipts** | **`public-read`** |
| conversationCurrentMembers | `owner` |

Twelve `public-read`, one `owner`, **zero `membership`** — in an application whose
milestones are direct messages, group chats, read receipts, and disappearing
messages.

Privacy in `coterie` is therefore entirely **handler-side**: `requireMyProfile` (27
call sites), `chatAccessForProfileConversation` (13), `requireActiveChatAccess` (7).

**This is not a live exposure.** I audited the four read paths that touch messages or
conversations: `listMessages`, `getMyFixtureConversation`, and `getMyFixtureMessage`
call an access helper, and `listChats` is self-scoped by construction
(`.eq('profileId', viewer._id)`). All four are correctly scoped today. (My first pass
flagged `listChats` as ungated; that was a false alarm from a helper-name detector.)

What is true is that the property is **unenforced**. The tables grant public read, so
correctness rests on every present and future function remembering to scope. This is
LLP 0310 P18's posture — which that document dispositioned as a `snapback-defect`
under the pit-of-success standard — reproduced in the committed flagship instrument
rather than in one benchmark lane.

It is also the multi-hop finding (LLP 0329.006 §4.2 lineage) with its consequence made
visible: `coterie`'s model is profile → conversation → membership with active/historical
distinction and removal cutoffs, which is beyond the single-hop visibility grammar, so
the app fell back to `public-read` plus hand-rolled checks.

**Methodological consequence, and the reason this supersedes S1.** §S3's contract was
tested against `coterie` and appeared to pass — `profileStats`'s follower counts are
over `follows`, which is `public-read`, so the authorized-domain rule admits them. That
result is **vacuous**: an application with no protected tables cannot exercise a
noninterference contract. Rule 3 remains untested by evidence, not validated by it.

### S5 — Rule 3 tested against a properly protected app, and sharpened

S4 said rule 3 was untested because `coterie` has no protected tables to aggregate.
A corpus scan found the instrument that does: **`demos/messaging-snapback`** (922
function lines) declares real declarative authorization —

```js
export const conversationMembers = defineTable({ … })
  .visibility({ kind: 'membership', declaration: 'conversationMemberships',
                resourceField: 'conversationId', roles: ['member'] })

export const conversationMemberships = defineTable({ … })
  .visibility({ kind: 'owner', field: 'userHandle' })
  .membership({ id: 'conversationMemberships', principal: 'userHandle',
                resource: 'conversationId', role: 'role',
                roles: ['owner','moderator','member'], bootstrapRole: 'owner',
                lastHolder: { protect: 'owner' }, transitions: [ … ] })
  .authorityProfile({ name: 'conversationMemberships', hierarchy: { … },
                      roster: { visible: ['userHandle','role'] } });
```

— with the intent stated in the schema itself: *"Product-visible does not mean
public. Every ordinary read is scoped by current admission through the canonical
private membership declaration."*

**The positive case.** `sendMessage` counts the roster over that protected table:

```js
const currentRoster = await ctx.db.query('conversationMembers')
  .withIndex('by_conversation').eq('conversationId', args.conversationId)
  .take(501).collect();
if (currentRoster.length > 500) ctx.refuse('MESSAGE_RECIPIENT_LIMIT', { limit: 500 });
```

Rule 3 **admits** it: the domain is keyed to a conversation resource, and membership
visibility filters the rows to the caller's admitted subset before the count. A member
counting their own conversation's roster learns nothing they could not enumerate.

**The discriminating contrast.** The same rule **refuses** `coterie`'s
`requireChatEnvelopeCapacity`, whose domain is `eq('profileId', otherProfile._id)` —
keyed to a *third-party principal*, not to a resource the caller holds. So the rule
separates the two real cases in the corpus correctly, which is the test S4 said it had
not had.

**And the test sharpens the rule.** The danger is not "the table is protected." It is
the opposite: under declarative visibility the count is filtered to the caller's
subset *automatically*, so protection makes counting safer, not riskier. What made
`coterie`'s pattern dangerous-in-shape was counting a domain keyed to another
principal over a table with no visibility to filter it. The rule is better stated:

> A count may drive a refusal when the counted domain is **(a)** filtered by the
> caller's declared read visibility, and **(b)** keyed to a resource rather than to a
> third-party principal.

(a) is automatic wherever visibility is declared — which is another argument for
declaring it. (b) is the condition an analyzer must actually check, and it is
checkable from the plan: the read's key expression either resolves to an authorized
resource argument or to some other principal's id.

**Secondary finding, which corrects S4's causal guess.** S4 suggested `coterie` went
`public-read` because multi-hop authorization is undeclarable.
`messaging-snapback` shows the declarative path *is* usable for DMs and groups, so
that explanation is too broad. The narrower difference: `messaging-snapback`'s
membership is **current-only**, while `coterie` models active *and historical*
membership with removal cutoffs (`chatAccessForProfileConversation` returns
`{ active, cutoffPageKey }`). It is the historical dimension, not group messaging as
such, that exceeds the single-hop current-membership grammar.

## Consequences

1. The security question does not block the bounded read. The default (caller
   visibility) needs no new contract, closes rung A, and is what
   `build_query_sql` already computes.
2. The contract is needed for rungs C and D, where a count or a fan-out can summarize
   rows the caller cannot see. That is 11 of coterie's 25 mutations.
3. Making the read declarative is what makes the disclosure question *answerable*. S1
   is the demonstration: the imperative form gets it wrong invisibly.

## Confidence

S1 is **withdrawn** — see the box above. The error was making a security claim about
a count without checking the counted table's visibility. High confidence in the
mechanism it describes; none in the disclosure it asserted.

High on S4: every visibility declaration is parsed from the schema, and the four read
paths were individually inspected rather than pattern-matched.

High on S2, which is quotation.

Medium on S3. It is a design proposal, not a measured result. The authorized-domain
rule for counts is the part I would most want reviewed: it is clean on coterie's three
capacity checks, but I have not tested it against a case where the natural product
requirement genuinely needs a global count over protected rows — which LLP 0120 names
as "the unsolved, existence-leaking case" and which this contract simply refuses.

## Open questions

1. ~~Rule 3 needs an application with protected tables to be tested against at all.~~
   **Done in S5** against `messaging-snapback`, which admits the legitimate roster
   count and refuses coterie's third-party count. The rule is restated there.
2. Does the sharpened rule hold outside these two, or does some real product need a
   count keyed to another principal? LLP 0120's "global total over protected sources"
   remains the named unsolved case and this contract still refuses it.
3. Under membership visibility a **non-member** sees an empty roster, so
   `sendMessage`'s capacity check passes trivially for them. Enforcement presumably
   falls to the `ctx.authority.conversationMemberships.list(...)` call that follows.
   Worth confirming that visibility-filtered counts never turn a refusal into a
   silent pass.
2. Should the elevated form be admitted in v1 at all, or should the first bounded read
   ship caller-visibility-only? Rung A needs nothing more, and deferring elevation
   would halve the security surface of the first landing.
3. Is a refusal-code disclosure analysis feasible statically, or does it require the
   author to declare which refusals are caller-observable?
