## Summary

[LLP 0329.010](./0329.010-cost-of-a-mutation-step.research.md) H5 established that
the mechanism for a visibility-composed bound read already exists in the mutation
executor, and that the remaining open item is a **policy** question:

> Which visibility should a mutation's bound read compose, and what is the
> noninterference contract when a refusal depends on rows the caller cannot see?

This document answers it, and reports that the question is not academic: the
corpus's flagship application already contains a reachable instance of exactly the
leak LLP 0120 predicted analytically, in a shipped `defineJsMutation` handler.

**Recommended contract.** Caller visibility by default; elevated reads admitted only
under a *mechanized* form of the pattern `guide/auth/protecting-data.md` already
prescribes; and capacity/count refusals admitted only over a domain the caller is
authorized for, because otherwise the refusal itself is the disclosure.

## Findings

### S1 — The corpus predicted this leak, and the corpus's own app has it

LLP 0120 §Noninterference states the general rule — "a count over rows the caller
cannot see discloses their existence even though no row is returned" — and names the
specific trap: "**the refusal threshold itself becomes a side channel** unless the
ceiling is stated so that refusing does not reveal invisible-row counts."

`coterie` does exactly this:

```js
export const openDm = defineJsMutation({
  auth: 'authenticated',
  args: { otherProfileId: v.id('profiles') },
  refusals: ['PROFILE_REQUIRED','PROFILE_NOT_FOUND','SELF_DM_FORBIDDEN','CHAT_ENVELOPE_EXCEEDED'],
  handler: async (ctx, args) => { … return openDmCore(ctx, creator, other, existing); },
});
```

`openDmCore` → `createConversationCore` → `requireChatEnvelopeCapacity(ctx, input.initialProfiles)`,
and that helper counts **each profile's** conversation memberships:

```js
async function requireChatEnvelopeCapacity(ctx, profiles) {
  for (const profile of profiles) {
    const chats = await ctx.db.query('conversationMembers')
      .withIndex('by_profile_latest_chat_page')
      .eq('profileId', profile._id).eq('isLatest', true)
      .take(chatHistoryEnvelopeLimit()).collect();
    if (chats.length >= chatHistoryEnvelopeLimit()) ctx.refuse('CHAT_ENVELOPE_EXCEEDED');
  }
}
```

`initialProfiles` includes the *other* party. `addGroupMemberCore` calls it as
`requireChatEnvelopeCapacity(ctx, [targetProfile])` — the target, not the caller.

So any authenticated principal can call `openDm` with any profile id and learn from
the declared refusal code whether that user is at their conversation limit. It is a
one-bit disclosure about another user's private state, and it is a *declared* refusal,
so it is part of the published API surface rather than an incidental error.

Filed as `issues/20260828-coterie-chat-envelope-refusal-discloses-other-profile-state.md`.

**What this is and is not.** It is an application-level defect in a benchmark
instrument, not a platform vulnerability, and the disclosure is small. Its
significance is evidential: capable agents wrote it, review did not catch it, and
**nothing could have caught it**, because in a JS handler no analysis relates a
refusal to the visibility of the rows that caused it. That is the argument for making
this class of read declarative — not that declarative is tidier, but that it is the
only form in which the platform can reason about disclosure at all.

### S2 — The existing elevated-read contract is the right shape, hand-executed

`guide/auth/protecting-data.md` already prescribes what a mutation must do when it
needs rows past caller visibility:

1. check the host-owned permission declaration on a **nominal resource argument**
   (`ctx.permissions.X.requireRole(...)`, which "derives the effective principal on
   the host and returns no roster data");
2. read via `ctx.db.elevated`, whose closed surface is `get`, `getMany`,
   `uniqueMany`, `query`, and which "bypass[es] only table row visibility" while
   keeping bounds, snapshot capture, and OCC validation;
3. **verify every resolved row belongs to the authorized resource** — the guide calls
   these post-read comparisons "load-bearing" and says they "prevent an authorized
   conversation id plus an unrelated message or quote id from becoming an
   object-reference bypass";
4. add negative identity tests for a non-member and for a foreign row id.

The contract is sound. What is unsound is its enforcement: the guide requires it "in
**every** named function" and calls the repetition "intentional." Steps 1 and 3 are
load-bearing and unenforced, so every omission is silent.

A declarative bound read can mechanize exactly these: the resource argument and its
permission are declared, and the scope predicate binding returned rows to that
resource is part of the step rather than an author-remembered `if`.

### S3 — Recommended contract

**Default: caller visibility.** A bound read composes the table's declared read
visibility for the effective principal, exactly as `build_query_sql` already does for
reads (LLP 0329.010 H5). No new authority; a mutation can read what its caller could
read. This covers rung A entirely — uniqueness checks against a table the caller can
read — and is the safe default an agent gets without deciding anything.

**Elevated: admitted only with a declared scope.** Reading past caller visibility
requires, in the plan and checkable at generate time:

- a nominal resource argument, and a declared permission over it (LLP 0240 authority
  profile, as the existing predicate already requires);
- a scope predicate on the read binding every returned row to that resource.

This is S2 steps 1 and 3 turned into structure. It grants nothing `ctx.db.elevated`
does not already grant a JS handler today — it removes the opportunity to forget.

**Counts: authorized-domain only.** A `count(binding)` may participate in a refusal
only when the counted domain is scoped to a resource the caller is authorized for.
`insertMessageCore`'s message-envelope check qualifies (the sender is a member of that
conversation). `setFollowCore`'s following-set check qualifies (the caller's own
follows). **`requireChatEnvelopeCapacity` does not** — it counts a third party's
memberships — and under this contract it would be refused at generate time, which is
precisely the outcome S1 wanted.

Of LLP 0120's five shapes this is **visibility-before-aggregation** for the default
and **sealed refusal** for the unprovable case, with public-only and
partition-by-authority left available as later widenings. It deliberately does not
adopt "weaker claims, declared," because a declared-weak aggregate re-creates the
capability-by-authoring-form problem this whole family exists to remove: two counts
that look alike with different disclosure properties.

**Corollary the S1 case makes concrete:** a refusal is an output. Any analysis that
classifies what a *returned value* may disclose must classify refusal codes the same
way, or the contract has a hole shaped exactly like `CHAT_ENVELOPE_EXCEEDED`.

## Consequences

1. The security question does not block the bounded read. The default (caller
   visibility) needs no new contract, closes rung A, and is what
   `build_query_sql` already computes.
2. The contract is needed for rungs C and D, where a count or a fan-out can summarize
   rows the caller cannot see. That is 11 of coterie's 25 mutations.
3. Making the read declarative is what makes the disclosure question *answerable*. S1
   is the demonstration: the imperative form gets it wrong invisibly.

## Confidence

High on S1 — the call chain is quoted from source and `openDm`'s argument is a
caller-supplied `v.id('profiles')` with `CHAT_ENVELOPE_EXCEEDED` declared. I did not
execute the probe against a running server; the claim is that the path is reachable
by construction, not that I observed the disclosure.

High on S2, which is quotation.

Medium on S3. It is a design proposal, not a measured result. The authorized-domain
rule for counts is the part I would most want reviewed: it is clean on coterie's three
capacity checks, but I have not tested it against a case where the natural product
requirement genuinely needs a global count over protected rows — which LLP 0120 names
as "the unsolved, existence-leaking case" and which this contract simply refuses.

## Open questions

1. Does the authorized-domain rule for counts hold outside coterie, or does some real
   product need a count the contract refuses?
2. Should the elevated form be admitted in v1 at all, or should the first bounded read
   ship caller-visibility-only? Rung A needs nothing more, and deferring elevation
   would halve the security surface of the first landing.
3. Is a refusal-code disclosure analysis feasible statically, or does it require the
   author to declare which refusals are caller-observable?
