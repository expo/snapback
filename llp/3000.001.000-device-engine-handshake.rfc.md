## Problem

R6 found supervised workers resolving packages beside releases outside the app, and simulated dev time expiring their injected tokens.

## Protocol

A device engine reports `{format:1, version:"0.4.24", capabilities:[...]}` from Rust. Memory, SQLite, wasm and Expo native share the same source. The client sends this JSON as `x-snapback-device` on every `/sync` and `/changes`, also on `/schema` before opening/adopting any backend. CORS permits the header. Neither a JavaScript package version nor a server echo stands in for device identity. Native and wasm hosts expose `snapback4_device::engine::info()` and `engine::headers()` without opening a store; wrappers forward `engine_info` and `engine_headers` before partition dispatch. Exact's Rust Fetch constructors attach the crate-owned headers and both Rust and TypeScript transport drivers forward them after caller credentials, overriding any caller-supplied device header. An unmodified adapter can obtain it from the opened core but cannot protect initial schema decoding; the paved adapters all supply it before open.

Authentication precedes compatibility. `/sync` requires the header; an absent, malformed, unsupported-format or too-old engine receives HTTP 409 `{denied:{code:"E_DEVICE_VERSION",family:"device-version",message,...}}` before parsing the sync body or materializing a page. `/schema` and `/changes` check a supplied header; bare one-shot and online-only callers have no replica and need no engine handshake. A legacy device first reaches `/sync` and receives this same refusal instead of an input-field error. No retry drops a modern handshake to bypass the fence.

The server checks a release's declared minimum version and every schema-required capability plus `sync-generation-v1`. Capabilities are authoritative even for a version above the floor. Version components are unsigned decimal u32 integers on both preflights and the server; overflow or malformed components refuse. Minimum engine version starts at 0.4.24, the first generation-capable union/merged-page release; future semantic releases must raise the constant when existing capabilities cannot represent the change. `GET /` exposes the current public-projection compatibility record for Exact's pre-browser preflight (both dev and serve). Exact compares that floor and capabilities, not npm version equality. Each immutable release writes `device-compatibility.json` with `{server_version,minimum_version,capabilities}`; `/schema` returns the active equivalent as `device_compatibility`. Capabilities come from the public projection, so server-private semantics impose no device requirement. Refusals name device/server versions, the first missing capability (or the floor/handshake), and rebuild commands: Exact `bun exact.mjs snapback --rebuild`, Expo `npx expo run:ios`, web reinstall the server's package version and rebuild the web app. An unversioned legacy device is explicitly `unknown (unstamped)`; its version cannot be inferred honestly.

The JS local client exports `DeviceVersionError` with a typed incompatible status for initial refusal, and `deviceVersion()` / `onDeviceVersion` for a running client. Runtime sync/poll refusal stops replication, preserves queued writes, and makes affected reads denied. Compatibility is admission, not an authenticity or trust attestation; application servers still enforce every authority rule.

## Build stamp

The optimized wasm carries exactly one custom section named `snapback4.engine`, containing canonical UTF-8 JSON in the same engine format: compact JSON, the fields `format`, `version`, `capabilities` in that order, and no other fields. Both stamp readers require reserialization to those exact bytes; duplicate keys, float spellings of format, unknown fields, alternate whitespace/escaping, and invalid UTF-8 refuse. This lexical rule applies to the embedded section, not ordinary transport header JSON. The `snapback4-device` crate generates this from the core's `DeviceEngine::current()` during its build and emits it as a used Rust wasm custom section. Every producer linking the crate inherits it, including Exact's separate wrapper; no packaging script may manufacture or append identity. The package build verifies the section survives bindgen/optimization and matches runtime `engine_info`, then derives a diagnostic `.engine.json` sidecar. The embedded section is authoritative; Exact's `.wasm.json` is also derived diagnostic output and is not read for admission. Native exports `sb4_engine_info`, with JSON freed by `sb4_free`, and the process device exposes `device --engine-info`. Exact's build workstream must copy these wasm bytes intact; its preflight can read the custom section with `WebAssembly.Module.customSections` without instantiating or decoding a backend. Missing, malformed or duplicate sections are unknown and require rebuilding. A stamp is a compatibility statement, not a cryptographic signature.

`check` and `doctor` inspect app.json in the backend root and immediate child app directories and require `typescript.sources.backend` to resolve to this project's `snapback/generated`. That backend mount only declares generated operations; it does not declare a replica. An Exact device adapter declared in `typescript.sources` as `snapback4/ts` requires `assets/snapback4.wasm`. A relocated adapter is recognized from its runtime import or re-export of `./web.ts` together with that module's runtime import or re-export of `./generated/device.ts`. Named, namespace, default, side-effect, static dynamic imports, import-equals and re-exports are recognized. Erased type-only imports do not establish consumption. Exact's `snapback4/online` adapter and a generated-operations-only mount impose no device gate, even if an unused old default artifact remains on disk.

Custom artifacts are discovered from static string declarations in app.json, app.ts, and the mounted adapter entry (`snapback.ts`, or a mounted source file). Relative source declarations resolve beside that source; `/assets/` URLs resolve inside the app. Local asset URLs use URL-decoded filenames with query/fragment suffixes removed; an existing literal relative filename takes precedence. Oxc 0.154.0 parses the TypeScript AST in the CLI (without executing source); runtime literal expressions and value module references supply paths. Escapes and templates without substitutions use their decoded values. Comments, regex bodies, erased type/ambient/interface declarations, abstract/declared members, and type-only import/export specifiers do not declare paths. TypeScript declaration files supply no runtime paths. Invalid source is left to Exact's compiler and is not treated as a custom declaration. A wasm custom section named `snapback4.engine` identifies the artifact by content, regardless of filename extension. An identified artifact's missing, malformed, duplicate, noncanonical or incompatible identity refuses check before generated output and marks doctor unhealthy. Unrelated wasm, diagnostic sidecars, comments, and unreferenced artifacts do not declare a device consumer. Computed/remote URLs and declarations solely in transitive secondary modules are outside this static discovery; the runtime handshake still admits the actual device. Apps mounted to another backend are ignored. The Exact tooling and its docs belong to the Exact/DX lanes.

## Workers

An immutable release records its originating app package directory separately from immutable source. Launch snapshots copy source with the existing no-follow custody and reconstruct dependency/package lookup from that app installation, preserving schema-local precedence. Host-installed dependencies remain outside immutable source. A relocation to another host sets `SNAPBACK_WORKER_PACKAGE_DIR` to its app installation; an unavailable recorded location refuses worker preparation instead of crash-looping. No deployment copies node_modules or changes dependency versions.

On a dev clock change, the engine guard first shifts the expiration of live supervised token families by the same delta, retaining their real-time remaining lifetime during the supervisor's transition. Manual tokens and revoked/expired families are unchanged. The supervisor detects the clock revision and stops the old child, revokes its family, then mints a new token at the new dev time and launches one replacement. It never issues HTTP refresh successors. Forward advance shifts live expirations before publishing time. Clock reset moves time backwards; old tokens remain unexpired until the same clock-revision replacement stops and revokes them. Store reset retains its ordinary authority semantics. Child process waits remain outside the engine guard; the bounded old-family transition preserves claims until orderly stop. Production wall time is unchanged.
