# LLP 3000.011.002.000: Simpler feed integration and a measured overflow path

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 feed recipe generation, application references, Following delivery, ranking and residency
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (initial proposal)
**Related:** [Problem](./3000.011.002-feed-modeling-and-limits.research.md), [LLP 3000.004](./3000.004-feeds-and-the-interview-reference-app.rfc.md), [LLP 3000.007.001](./3000.007.001-maintained-columns.rfc.md), [LLP 3000.007.002](./3000.007.002-common-application-shapes.rfc.md)

## 1. Recommendation

Make the existing feed recipe easier to integrate by generating bridges typed
to the application's own post and follow model. Separately evaluate an
explicit online query path for readers outside the recipe's pull-lane envelope.
Do not raise 32 to a larger constant and call the serving problem solved.

The first part can ship without the second. The measured default remains the
current hybrid recipe until an alternative establishes the required behavior
and cost. This RFC is a proposal, not a new accepted feed contract.

## 2. Typed application bridges

Extend the existing installer, which already parses and checks the project,
to accept explicit selections of the application post table, author reference,
event time and follow relation. Resolve those selections against Quarry types;
do not infer them from names alone or introduce a parallel schema DSL.
The exact CLI spelling is an implementation choice, not a currently available
command documented by this RFC.

Generate a small bridge module alongside the existing recipe. The intended
application-facing operations are register author, publish/remove an event,
and set following. Each accepts the actual application's reference type.
The bridge owns the app-post-to-feed-event mapping and validates it, so a
builder cannot accidentally pass an application row as a recipe event id.

The application calls the generated helper inside its existing mutation.
Post creation and delivery, and follow-edge change and recipe change, stay in
one transaction. No client sequence of two mutations, delayed repair job or
unchecked cast substitutes for that atomicity. Failed promotion rolls back
the app edge as it does today. Reposts retain their distinct attribution and
identity; media remains referenced through the original authorized home row.

Generation must preserve current collision/no-overwrite behavior. If the
application's model cannot map unambiguously, show the missing mapping and
keep today's manual integration path. An installer must not silently edit an
existing mutation or widen its write rules. Backfill remains an explicit,
resumable adoption step that uses the same mapping invariants.

## 3. Saturated readers: a serving experiment

The candidate is an explicit **online Following query** over all authorized
followed-author lanes using the current merge machinery, without installing
the hybrid recipe's pull routes for that reader. Keep the same ordering,
repost identity and inclusion of the user's own posts. This is an alternative
model to measure, not a silent runtime fallback that mixes two cursor domains.

Test 5, 32, 33, 64, 128 and 500 followed popular authors, plus the ordinary
500-follow/one-celebrity fixture and the saturated-existing-follower promotion
case. Measure lane initialization, rows examined, first page, deep pages,
write cost and full traversal. Include sparse lanes and equal ordering keys.
Carry cut/completeness and continuation semantics exactly as the language
permits; a meter-cut prefix is never a complete Following feed.

The earlier merge cost in LLP 3000.007 remains counterevidence. This candidate
earns a supported role only if a specified workload fits existing meters with
acceptable measured latency and a clear product advantage over refusal at the
slot boundary. It need not beat the hybrid recipe on every workload. Select
that workload and its acceptance thresholds before measuring.

The online path has no automatic full-offline equivalence. Its offline view
must declare the acquired event/card horizon and report incomplete history
truthfully. If the application requires the hybrid path's exact offline
contract and the candidate cannot provide it affordably, retain the refusal
and record that requirement as unresolved. Switching an existing app needs an
explicit migration and cursor restart, with queued writes and old clients
tested; this experiment alone authorizes no automatic switch.

## 4. Ranking and public data

Consume LLP 3000.007.001's maintained columns only after their own qualification
and package availability. Use them to remove manual score copies for supported
non-expiring sources; do not promise device prediction or rolling activity
ranking outside that design. Until then the current maintained-table recipes
remain the control, including their tie and zero-count behavior.

Both alternatives must report which public source rows, event rows and app
cards a device acquires. A bounded query result does not bound acquisition.
Reducing replicated facts must preserve the application's required offline
answers; verify this with the starter/residency proposal rather than counting
only generated module lines.

## 5. Acceptance and risks

The typed bridge must remove handwritten identity translation from a fresh
builder's integration, reject mismatched reference kinds before runtime, and
pass follow/unfollow, self-repost, deletion, retry, backfill and promotion
rollback cases. Its runtime overhead should be measured against the same
manually integrated recipe, not assumed free because it is generated.

The overflow experiment needs an oracle for complete chronological pages,
honest cuts, no private-row disclosure and named online/offline scope. Stop if
it needs higher meters, a second interpreter or a result-cache protocol just
to pass the chosen fixture. A later asynchronous materialized-inbox design
would need its own delivery-lag and migration decision; it is not smuggled
into this proposal as a fallback.

The major risk is moving manual complexity into generator maintenance while
leaving the application's actual decisions unchanged. Retain the change only
if measured builder work falls and the installed code remains understandable
through the existing feeds card and diagnostics.
