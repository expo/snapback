# LLP 3000.011.002.000: Simpler feed integration and a measured overflow path

**Type:** RFC
**Status:** Implemented
**Systems:** Snapback 4 feed recipe generation, application references, Following delivery, ranking and residency
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (selected scope after independent reviews; parent §7)
**Related:** [Problem](./3000.011.002-feed-modeling-and-limits.research.md), [LLP 3000.004](./3000.004-feeds-and-the-interview-reference-app.rfc.md), [LLP 3000.007.001](./3000.007.001-maintained-columns.rfc.md), [LLP 3000.007.002](./3000.007.002-common-application-shapes.rfc.md)

## 1. Recommendation

Make the existing feed recipe easier to integrate by generating bridges typed
to the application's own post and follow model. Separately evaluate an
explicit online query path for readers outside the recipe's pull-lane envelope.
Do not raise 32 to a larger constant and call the serving problem solved.

The first part can ship without the second. The measured default remains the
current hybrid recipe until an alternative establishes the required behavior
and cost. Only the typed bridge is accepted in this increment; the serving contract stays unchanged.

## 2. Typed application bridges

Extend the existing installer, which already parses and checks the project,
to accept explicit selections of the application post table, author reference,
event time and follow relation. Resolve those selections against Quarry types;
do not infer them from names alone or introduce a parallel schema DSL.
The exact CLI spelling is an implementation choice, not a currently available
command documented by this RFC.

Support an explicitly selected public social model only. Recipe events and the
follow graph disclose metadata publicly; matching types does not authorize
that disclosure. Reject unsupported private mappings without widening rules.
Keep target-existence, ownership and audience checks explicit, since a table
reference is not a permanent foreign key or authority proof.

Generate a small bridge module alongside the existing recipe. The intended
application-facing operations are register author, publish/remove an event,
and set following. Each accepts the actual application's reference type.
The bridge owns the app-post-to-feed-event mapping and validates it, so a
builder cannot accidentally pass an application row as a recipe event id.

The application calls the generated helper inside its existing mutation.
Post creation and delivery, and follow-edge change and recipe change, stay in
one transaction. No client sequence of two mutations, delayed repair job or
unchecked cast substitutes for that atomicity. Failed promotion rolls back
the app edge as it does today. Reposts retain their distinct attribution and
identity; media remains referenced through the original authorized home row.

Generation must preserve current collision/no-overwrite behavior. If the
application's model cannot map unambiguously, show the missing mapping and
keep today's manual integration path. An installer must not silently edit an
existing mutation or widen its write rules. Backfill remains an explicit,
resumable adoption step that uses the same mapping invariants.

## 3. Saturated readers: deferred serving experiment

Both reviews defer this experiment from the selected implementation. A read
query alone cannot unblock promotion: the current writer checks every existing
follower, including dormant saturated readers. A future proposal must choose an
entirely separate model or define write admission and migration together.

The deferred candidate is an explicit **online Following query** over all authorized
followed-author lanes using the current merge machinery, without installing
the hybrid recipe's pull routes for that reader. Keep the same ordering,
repost identity and inclusion of the user's own posts. This is an alternative
model to measure, not a silent runtime fallback that mixes two cursor domains.

Test 5, 32, 33, 64, 128 and 500 followed popular authors, plus the ordinary
500-follow/one-celebrity fixture and the saturated-existing-follower promotion
case. Measure lane initialization, rows examined, first page, deep pages,
write cost and full traversal. Include sparse lanes and equal ordering keys.
Carry cut/completeness and continuation semantics exactly as the language
permits; a meter-cut prefix is never a complete Following feed.

The earlier merge cost in LLP 3000.007 remains counterevidence. This candidate
earns a supported role only if a specified workload fits existing meters with
acceptable measured latency and a clear product advantage over refusal at the
slot boundary. It need not beat the hybrid recipe on every workload. Select
that workload and its acceptance thresholds before measuring.

The online path has no automatic full-offline equivalence. Its offline view
must declare the acquired event/card horizon and report incomplete history
truthfully. If the application requires the hybrid path's exact offline
contract and the candidate cannot provide it affordably, retain the refusal
and record that requirement as unresolved. Switching an existing app needs an
explicit migration and cursor restart, with queued writes and old clients
tested; this experiment alone authorizes no automatic switch.

## 4. Ranking and public data

Consume LLP 3000.007.001's maintained columns only after their own qualification
and package availability. Use them to remove manual score copies for supported
non-expiring sources; do not promise device prediction or rolling activity
ranking outside that design. Until then the current maintained-table recipes
remain the control, including their tie and zero-count behavior.

Both alternatives must report which public source rows, event rows and app
cards a device acquires. A bounded query result does not bound acquisition.
Reducing replicated facts must preserve the application's required offline
answers; verify this with the starter/residency proposal rather than counting
only generated module lines.

## 5. Acceptance and risks

The typed bridge must remove handwritten identity translation from a fresh
builder's integration, reject mismatched reference kinds before runtime, and
pass follow/unfollow, self-repost, deletion, retry, backfill and promotion
rollback cases. Its runtime overhead should be measured against the same
manually integrated recipe, not assumed free because it is generated.

The overflow experiment needs an oracle for complete chronological pages,
honest cuts, no private-row disclosure and named online/offline scope. Stop if
it needs higher meters, a second interpreter or a result-cache protocol just
to pass the chosen fixture. A later asynchronous materialized-inbox design
would need its own delivery-lag and migration decision; it is not smuggled
into this proposal as a fallback.

The major risk is moving manual complexity into generator maintenance while
leaving the application's actual decisions unchanged. Retain the change only
if measured builder work falls and the installed code remains understandable
through the existing feeds card and diagnostics.

## 6. Selected implementation record — 2026-09-22

The selected public bridge uses four explicit CLI selectors alongside
`init --recipe feeds --prefix <name>` in an existing compilable app:
`--public-profiles table:principal`, `--public-posts table:author:time`,
`--public-follows table:follower:followed`, and
`--public-reposts table:actor:post:time`. All four are required. No starter
mode implicitly chooses this mapping; standalone and manual recipe installs
remain unchanged.

The validator accepts four distinct ordinary application tables with explicit
public reads, full public sync, no expiry and the required principal/time/post
reference types. Exact total unique keys establish profile and edge/attribution
identity. Insert ownership must be a required conjunction; an OR alternative
is not sufficient. Updates/deletes must deny or require the same owner, mapped
columns must be immutable if updates are allowed, and edge/attribution updates
are denied. Posts deny deletion so independent reposts retain their card.
Extra required follow columns without defaults refuse. These restrictions
select a supported existing model; the installer never edits rules to make a
model pass.

The generated `feed_bridge.q` contains seven ordinary Quarry `fn` helpers:
AppRegister, AppPublish, AppRemove, AppRepost, AppUnrepost, AppFollow and
AppUnfollow, each under the selected prefix. Registration, publication and
reposting take the app's actual reference types. Follow takes a principal and
checks both mapped profiles. The application calls the helper in its existing
mutation; the helpers do not become a second client write API. Publication and
reposting validate target existence, ownership and the existing event's author
and time before translating identity. Repost has a distinct event and uses the
app attribution time. Removal resolves the actual event ID, which may differ
from the card ID in a manually integrated app. The app still owns its card,
media, attribution creation and Following joins. Files are preflighted and the
combined project is compiled before any output is written.

No permanent mapping or publication-history table was added. Ordinary retries
use the original write ID. Repeated initial-backfill calls can reuse a matching
live source event without redelivery. Publication is explicitly restricted to a
new app card inserted in the same mutation, or the initial adoption backfill;
it must never republish a removed card, including after tombstone purge. An
older event ID's removal marker is not discoverable by card ID alone. This is
a stated app precondition, not an arbitrary post-removal replay guarantee.
Removal retains the original card. A later fresh repost after unrepost requires
a new attribution row and a live original; existing independent reposts survive
original removal.

Adoption pauses publishing, removals and graph changes, registers profiles as
their owners, backfills original events and then reposts, and finally applies
edges before switching Following. Bounded owner-context calls checkpoint only
successful work. The helper does not manufacture a viewer for a system job.
The initial pause prevents a removal racing a later backfill into resurrection.
The existing caps, follow backfill bound, 32 pull slots, promotion rollback,
cursor and acquisition behavior remain unchanged. Overflow serving and
maintained-column integration remain deferred.

The control is the manual integration in `guide feeds`; both test schemas add
an immutable profile principal to select the supported model, with the manual
mutation bodies unchanged. Dedicated installer/runtime tests in `snapback4/tests/feed_bridge.rs` compare that control
with generated wiring and exercise private/unsafe/ambiguous refusal,
no-overwrite and helper collisions, selected names, actual legacy event IDs,
existence and ownership, live-event retry, original write-ID replay, timestamped
backfill, self-repost, retained-card deletion and saturated promotion rollback.
The measurement fixture compares the eight corresponding app mutations and
prints warm publish latency plus examined/index/written units for both paths.
The affected remote run passed all nine bridge tests, 49 language guide tests
and 32 existing installer tests. The eight matching app mutations use 36
nonblank handwritten lines in the manual control and 28 with generated
helpers (22% fewer); recipe-specific app statements fall from 14 to eight.
The generated module is 74 readable Quarry lines and adds no tables. Measured
units are:

| Mutation/workload | Manual examined | Generated examined | Writes, both |
|---|---:|---:|---:|
| Follow one registered author | 5 | 7 | 2 |
| Publish to self plus one follower | 4 | 7 | 4 |
| Promotion after freeing the saturated follower's slot | 213 | 215 | 159 |

Both publish paths examined 26 index entries. The added reads check app
existence/ownership and a pre-existing event rather than create additional
copies. Saturated promotion refused atomically in both paths before recovery:
the app edge, recipe edge, mode, routes, counts, sequence and deliveries were
unchanged. The final nine-test run also passed repost-removal's event-author
match against the retained card: a mismatched legacy event refuses without
removing either event or attribution.

An isolated single-test debug run on the M5 host, with no competing heavy
process, measured 20 publishes after five warmups. Manual p50/p95 was
0.211/0.358 ms; generated p50/p95 was 0.355/0.459 ms. These are fixture timings,
not a deployment throughput claim. The invariant evidence is the unchanged
four writes/26 index entries and three additional examined rows. Logs are
`feed-bridge-final.log` and `feed-bridge-measurement.log` under the run's
`/tmp/sb4-3011-20260922` evidence directory. No ceiling, store or interpreter
change was required.
