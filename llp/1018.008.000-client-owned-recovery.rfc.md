# LLP 1018.008.000: Routine recovery belongs to the client

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 2 account lifecycle, replay grants, outbox admission and replay, follower inbox, React/Expo readiness
**Author:** Codex, commissioned by Charlie Cheever
**Date:** 2026-09-10
**Revised:** 2026-09-10 (initial proposal)
**Related:** LLP 1018.008, LLP 1012 §5 and §7–§8, LLP 1018.003.001 §1, LLP 1018.004, LLP 1018.007, LLP 1019, LLP 1020

## 1. Outcome and boundary

A durable client that remains authenticated and online should keep accepting
ordinary writes across grant boundaries. A brief transport interruption should
not leave already admitted work indefinitely paused after connectivity recovers.
The client owns routine recovery; the application displays progress and handles
authentication, conflicts, and explicit offline intent.

This proposes a deliberate amendment to today's explicit-only recovery contract
in `guide offline` and LLP 1018.003.001 §1. It is not a missing Sync button fix:
the button now works and is the baseline. No runtime change is commissioned by
this Draft. Design author: Codex, 2026-09-10; implementation owner/date await
commission. LLP 1019's receipt work may add consumers of grants; this RFC neither
implements those receipts nor assigns their allocation order.

## 2. Evidence and existing machinery

LLP 1018.007 records a 352-ID operation exhausting its usable grant after 23
sends in one stress workload. `writer_replay.rs::grant_if_low` mints on resume
when reported remaining IDs are below the low watermark; it does not know the
next operation's demand. `client.ts::performResume` already shares a cancellable
flight. `client-outbox.ts::drainOutbox` serializes replay. The durable inbox
already gives one writer responsibility for follower admission.

Extend these owners. Do not create a hook-owned coordinator, periodic
`online()` loop, second grant allocator, or plain-wire fallback for a client
whose durable admission is temporarily unavailable.

## 3. Proposed lifecycle

Separate two reasons to enter the existing recovery flight: acquire capacity
for future admission, and resume byte-identical admitted work. Neither creates
a new intent in place of a refused one.

| Event | Proposed action | Limit |
|---|---|---|
| Successful admission leaves capacity low | Schedule one background renewal through the account owner | No wait on the already admitted call |
| Preparing a selected mutation reveals insufficient capacity | Register its certified demand with the account owner and schedule renewal | Readiness projection itself stays pure |
| A new explicit call needs more IDs than remain | Join renewal before admission, then recheck once | No queued result before durable admission |
| Authentication or transport actually recovers with admitted work waiting | Join resume, then serialized drain | Exact existing envelopes only |
| Explicit `offline()` / `startOffline` | Stop automatic network recovery | Only explicit `online()` releases that cut |
| Session refusal, conflict, malformed protocol, or carrier failure | Publish the specific recovery/refusal | No automatic fresh-intent retry |
| Account replacement, logout, close, writer loss | Cancel stale work and prevent late installation | Queue custody follows existing account rules |

### Capacity acquisition

Use the certified operation demand, `1 + maxNewIds`, not the number of IDs the
last execution happened to consume. A demand is tied to the installed program
generation and captured account. Concurrent calls recheck capacity in the
serialized admission transaction; readiness is advisory and cannot reserve it.

Extend the existing resume request with an optional operation name and expected
generation for capacity demand. The owner derives the demand from its current
certificate. Mint when remaining capacity is below the existing low watermark
or cannot cover that validated demand. A client cannot ask for a larger grant
by supplying its own arithmetic, and must report the real remaining count.
Keep the existing block size and lifetime. An operation that cannot fit one
block refuses with a sourced bound explanation; renewal cannot spin forever.

Renew early on a low-watermark crossing and after admission when necessary.
Also register operation demand when a mutation handle is prepared, through the
existing operation-scoped observation/metadata path. A disabled composer must
not depend on an impossible send click to trigger its renewal. Many observers
of the same operation share the registration; reading `can` itself never starts
I/O. Headless calls use the same admission-time fallback with zero observers.
The admission-time path covers a sudden change from a cheap to an expensive
operation. An in-flight request made for a cheaper operation cannot satisfy a
more expensive waiter merely because it completed: recheck demand, and allow
at most one subsequent demand-specific request for that explicit call.

Persist replacement capacity through existing principal-bound grant custody.
Never recycle a used slice. Existing entries retain their original grant,
offset, trace, target identity, and bytes; an old grant is still meaningful to
its queued entries after new admission switches to the replacement. A crash
between server allocation and local persistence may leave an unused server
block, but cannot admit overlapping local slices. Prefer the existing bounded
grant lifetime over a new grant-recovery ledger for that unused block.

If recovery fails before admission, the call returns the ordinary refusal and
the application retains its draft. A resumed callback does not later submit it.
Do not display "saved" for a call still waiting on capacity in memory.

### Replay after transport recovery

Automatic replay applies only to entries already durably admitted. Run under
the current authenticated account, reacquire the existing fence/coverage trust
when required, then enter the existing serialized drain. A successful unrelated
query alone is not evidence that either prerequisite was met.

Trigger from meaningful transitions: successful auth restoration, offline-to-
reachable transport transition, low-watermark crossing, or writer takeover.
Coalesce them into the existing flight. A retryable recovery transport failure
may use one bounded backoff schedule owned by that flight, at most three
attempts per transition. Ordinary connected frames and rerenders do not reset
the counter. A later real reconnect or explicit Sync is a new opportunity;
nonretryable refusals remain visible. Reuse existing transport timing policy
where it supplies these semantics instead of adding another timer subsystem.

Manual `online()` joins the same work, returns its actual verdict, and remains
available after automatic attempts stop. It explicitly releases an offline
cut. Internal automatic recovery never calls a wrapper that clears that cut.

### Follower tabs and readiness

The writer alone renews capacity and admits inbox rows. Followers continue to
save their inbox rows durably and observe announced readiness. A new writer
reopens the authoritative persisted grant/offset before renewing; late work by
the old writer cannot install or allocate after lock loss.

Project the existing `can` surface from actual activity: waiting while a
recovery flight can make progress, an explicit action after it stops, and
sign-in for an authentication barrier. Do not report sendable until admission
can uphold its contract. A composer may temporarily wait for renewal; it should
not need a normal-user capacity-management button. Keep the explicit fallback
and all refusal details for real failures.

## 4. Required invariants and controls

- No automatic resubmission of a rejected/conflicting/non-durable mutation.
  A lost acknowledgement on a durable write retries exactly its envelope.
- No renewal changes principal, auth epoch, fence duration, old authority
  evidence, or expiry of old entries. Capacity is not authorization evidence.
- No successful write or live read clears a refused coverage reset.
- No network work behind an explicit offline cut, including after takeover,
  cold restore, a low-watermark event, or a late completion.
- No multiplication by mounted hooks or tabs; cancellation does not publish a
  stale success into another account. All waits have the existing transport
  deadline/cancellation, and no new indefinite pre-admission state is public.

## 5. Acceptance and deletion

Use existing real-owner, carrier, readiness, and browser/Expo journeys. Hold
the grant size fixed and cross at least three actual renewal boundaries with
cheap and expensive operations. A normal send click after waiting for readiness
commits exactly once, without a Sync click. Record renewal requests, grants,
unused capacity, and write latency. Renewal frequency must follow certified
capacity consumption, not the number of hook callbacks or successful reads;
the 352-ID workload must not renew once per message. Operations larger than
half a block may legitimately need a new block for each subsequent admission.

Cover zero hooks, many hooks, two tabs, writer death during renewal, account
switch, competing admissions, a dropped renewal response, an old queued grant,
a refused old intent, generation change during preflight, insufficient demand
above the low watermark, and an operation larger than a block. Cut transport
after the owner commits but before the response; recovery must return one
terminal and one effect emission. Explicit offline restart must make zero
network requests until `online()`. Confirm the three-attempt stopping rule.

Delete normal-capacity recovery branches from both composers only after the
runtime owns them; preserve draft/error/auth UI and manual failure recovery.
Amend LLP 1012 and the packaged offline guide in the implementation change.
Rebase onto the actual LLP 1019 allocation relation and LLP 1020 certificate
changes without altering their acceptance. Measure the unchanged complete
runtime allocation; no new gate, dependency, grant-size increase, or wire lane.

## 6. Decisions remaining for review

The proposed default is automatic routine recovery for durable clients, with
`offline()` as the explicit stop. Review must settle whether background grant
renewal should request a full resume every time or safely use existing resume
validators to make it cheap. A separate grant-only route is not proposed.
If renewal routinely repeats expensive cold work, resolve that shared-flight
cost before promising invisible connected operation; a timer around `online()`
does not satisfy this RFC.
