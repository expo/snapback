## 1. Summary

This RFC turns the Postgres evaluation adapter into a production store. The
data plane already transfers. The remaining work is everything around it:
the internal tables (31 at the first count, more after the panel's inventory), the on-disk release tree, the worker's completion ledger, and the SQLite connection that serving code reaches
directly. There is also the process-local coordination that assumes one
server, and asset bytes kept as local files. The decisions:

1. A three-layer port — access, durable state, host coordination — and the
   rule that only an adapter touches a connection (§3).
2. An inventory of every durable and in-process item, with its contract
   family and its P1 and P2 disposition (§4).
3. Ownership held by the store: every durable transaction fenced by the
   owner token, takeover driven by a database-clock lease that terminates
   a paused owner's sessions, and a declared HA mode that decides what a
   failover means: lossless modes keep the incarnation, and in `async` the
   operator chooses (§5).
4. A `Committer` seam with today's lock-first protocol as the reference, the
   serial batch as the first committer, every durable write going through
   the committer's stream, and an optimistic committer (a)
   designed beside it (§6). The sibling scale RFC decides whether (a) is
   built.
5. Layout v1: the generic layout kept and partitioned by table, with the hot
   head row addressed. Log retention is checkpoint plus floor and outside
   P1 (§7).
6. Roles, connections and the supported Postgres matrix (§8).
7. A parity rule, with no silent Postgres subset (§9).

## 3. The port

### 3.1 Three layers

```
            serve / deploy / dev / sql / doctor            (crates/snapback4)
 ───────────────────────────────────────────────────────────────────────────
  Host coordination: Notifier · Lease · EphemeralBus · BlobStore
  Durable state:     StoreTx { identity, work, assets, release, evolution,
                               receipts, sequences, time }  +  Committer
  Access:            Rows · PartitionRows  (+ prefetch, batched tail)
 ───────────────────────────────────────────────────────────────────────────
        SQLite adapter                     Postgres adapter        (only these touch a connection)
```

- **Access** keeps `Rows` and `PartitionRows` and C1's batching unchanged.
  The adapter contract stays: rows in key order at the transaction's snapshot.
- **Durable state** is a typed transaction handle (`StoreTx`) with one
  sub-interface per family (§4.1). Each operation is semantic, such as
  `claim_work(spec, now, lease)`, `mint_session(binding)`,
  `record_step(invocation, digest, outcome)` or
  `ledger_asset(intent, digest)`. None of them takes SQL. Policy stays in
  shared Rust above the handle: what a claim refuses, how a generation fence
  works, the order of refusals. The adapter does storage. This is the shape
  C3.2 already gave authority: one typed policy, a SQLite and a Postgres
  transaction adapter.
- **Host coordination** names what processes must share (§4.2). Each item has
  an in-process implementation, used by SQLite and by P1, and a P2
  implementation.

### 3.2 The rule

Only `store::sqlite` and `engine::postgres` (renamed `store::postgres`)
touch a database connection. A suite test greps `crates/snapback4` and the
non-adapter core for `rusqlite::`, `postgres::`, `.conn()` and
`.query_row(`, and refuses them. Each refusal names this section. The `sql`
inspection verb (LLP 3000.007 §8.8) becomes a port operation:

- on SQLite, generated views over a read-only connection, as today;
- on Postgres, generated views in the store's schema, under a read-only role.

`Engine` becomes `Engine<S: Store>`, or an enum over the two stores; the
lead chooses. The host never names a backend type outside its configuration.

### 3.3 Extraction first, with no behavior change

P0 moves the SQLite code behind the contract, with no change of behavior,
before any Postgres family is written. Its evidence is the existing suite
(`scripts/test.sh`), the corpus, the simulator and the device oracles, all
unchanged. The wasm budget does not move, because the device does not link
the server families. This is LLP 0046's lesson: plugging Postgres into an
unextracted seam produces a second engine, not a port.

**P0-S3a identity extraction (2026-10-20).** `identity.rs` owns the
`IdentityTransaction` and `IdentityStore` traits and plain records;
`store/identity.rs` implements them for SQLite `Tx` and `Store`. Credential
checks, token creation, lifetime bounds and mint refusal order stay above
the adapter. Composite store methods keep signup/login, full/read rotation,
principal revocation and supervised-worker mint/retirement inside their
original transaction modes and statement order; policy callbacks run at the
original point in those transactions. Host auth and worker code use identity
operations instead of identity-table SQL. The shared identity cases exercise
rollback, credential rechecks, read caps and worker-family isolation. The
existing Postgres authority adapter is unchanged; the new identity operations
wait for P1 family parity.

**P0-S2 receipts and head extraction (2026-10-20).** `receipts.rs` owns
plain receipt records, the `ReceiptReader` access trait and replay binding
policy; `store/receipts.rs` implements access for SQLite `Store` and `Tx`.
Acknowledgement limits, cuts, negative-sequence errors and asset refusal order
stay in the engine. Shared receipt cases run against both handles. Typed
store identity, read-only and memory queries replace host/engine connection
inspection; required and optional identity reads retain their distinct
missing-row behavior. `Tx::abandon` ends the read snapshot at the existing
point before ephemeral publication while its undo guard still borrows the
transaction. `RuntimeError::is_busy` classifies the same SQLite busy/locked
codes inside the adapter; retry policy stays in the host. SQL, transaction
boundaries and the evaluation Postgres adapter are unchanged.
**P0-S4a request extraction (2026-10-20).** `engine/actions/requests.rs`
defines the `RequestsTransaction` and `RequestsStore` access traits and plain
insertion/settlement records; `store/requests.rs` implements them for SQLite
`Tx` and `Store`. Request DDL/upgrades and row decoding move into that adapter.
Action and route callers use typed access; authority, claim selection bounds,
lease transitions, retry decisions, settlement validation and refusal order
stay in `engine/actions.rs`. The shared finish policy still invalidates the
delegated session before the adapter preserves the last claim fence, including
when an uncertain or oversized external step parks its parent. SQL text and
transaction boundaries are unchanged. Adapter-neutral cases cover that fence,
credential invalidation, settlement clearing, due ordering/name filters and
rollback; the existing action/route suites cover the public lifecycle. Host
request SQL is confined to inspection (`verbs/work_records.rs`), left for its
own slice. Postgres lifecycle parity remains P1 work.
**P0-S4b jobs and schedules extraction (2026-10-20).** `engine/job.rs`
exposes plain continuation, chunk-update and bounded-summary records, with
crate-private `JobTransaction` and `JobStore` capabilities. SQLite access
lives in `store/jobs.rs`; the engine still chooses queue admission, sweep
bounds, adaptive chunk sizes, retry and park decisions, native continuations,
and schedule coalescing. Typed schedule accessors own the `schedule:*` and
`schedule-shape:*` metadata keys. The caller's existing writer transaction
still commits each boundary with its admitted job or action, and each chunk
with its data writes. Host clock inspection uses bounded summaries and typed
schedule reads while retaining presentation and error-byte truncation. Shared
adapter-neutral cases cover FIFO ties, continuation bytes and accounting;
SQLite lifecycle tests cover admission/watermark rollback and savepoint
rollback before parking. Postgres implementations wait for P1.
**P0-S4c outbox extraction (2026-10-20).** `engine/effects.rs` owns
`OutboxTransaction`, `OutboxStore` and plain admission/expiry records;
`store/outbox.rs` implements SQLite access. Declaration checks, presence
satisfaction, attempt limits, retry decisions, expiry budgets and refusal
ordering remain in the engine. Strict and legacy updates retain their distinct
field-clearing behavior. The cross-family `shift_worker_leases` operation
updates outbox and request leases, supervised sessions and delegated request
sessions in the caller's original writer transaction. Host health reads return
one `EffectHealth` snapshot, including the separately fallible advisory grace
count with its original diagnostic text. Replay configuration keeps its release
check and policy write in one immediate transaction. Shared capability cases
cover expiry equality, declaration parking, deadline precedence, presence
windows and bounded-maintenance progress. Postgres implementations wait for P1.

**P0-S5 asset-upload ledger extraction (2026-10-20).** `assets.rs`
extends the plain-record `AssetTransaction` contract and adds
`AssetIntentReader` for transaction/store existence probes. `store/assets.rs`
owns declaration reads/insertion, upload publication, cancellation and
settlement, quota and recovery-list joins against receipts, and reset's asset
ID inventory. `engine/asset_uploads.rs` retains declaration limits, JSON
encoding/decoding, digest and placement comparisons, quota checks, pagination
and refusal order. SQL text, statement order and transaction boundaries stay
unchanged; reset's remaining SQL waits for the release/schema slice. Shared
adapter-neutral cases cover declaration preservation, cancellation tombstones,
owner isolation, quota/recovery filters and the 51-row recovery bound; SQLite
also checks rollback. New Postgres methods remain explicitly marked P1.

through the family's logical export format, not through table copies.

### 4.2 Host coordination (one process today)

| Item | Today | P1 (one server, warm standby) | P2 (several serving processes) |
| --- | --- | --- | --- |
| Ownership | Sidecar file lock | Store-held lease and fencing token (§5) | Same lease, held by the committer |
| Commit wakeup (`committed`, `seq`) | Condvar | Unchanged in-process | `Notifier`: `LISTEN`/`NOTIFY` carrying the new head, with a bounded poll of `_commits` as the floor. A missed notification delays an answer; it never loses one |
| Change answers and long waits | Process maps; a held wait costs a thread | Unchanged. A held wait must not hold a database connection | Per process; each process wakes from `Notifier` |
| Presence (`connected[p]`) | `Live` over held polls | Unchanged | Pinned to the committer or a shared table with leases; chosen at P2 from LLP 3000.009 §7.1's measurement |
| Ephemeral tables | One-process `Hub` (LLP 3000.017) | Unchanged; a standby starts empty, as after a restart | `EphemeralBus`, or pin ephemeral traffic to one process; LLP 3000.017's exclusions hold until P2 rules |
| Asset transfer serialization | `AssetTransfers` per process | Unchanged | A row lock on the grant inside the consuming transaction |
| Asset bytes | Local files | `BlobStore`: S3-compatible, content-addressed by the SHA-256 the ledger already records, written before the claiming commit; local directory stays the SQLite default | Same |
| Schedules and sweeps | The serving process | The lease holder only | The committer only |
| Following reader (`Shared.following`) | A process-local reader over Following history | Unchanged | Per process; it reads the store and wakes from `Notifier` like change polls |
| Dev clock, dev doors, personas | Process and store state | Unchanged; `dev` stays on SQLite unless the application requires Postgres | — |
| Release activation | `deploy` writes the tree and `current` on the serving host's disk, then commits the selection; the activation control socket is keyed by the store file | `deploy` uploads the tree by digest, then one fenced store transaction selects it (§5). Every host materializes and verifies the tree the store names, and refuses one it cannot fetch. The control transport is keyed by `store_id` and owner token, not by a file | Same; a rolling deploy materializes the new tree on each host before the selection commits |

A `BlobStore` write happens before the commit that claims it, and outside
any serial section: the commit claims bytes by digest. Two rules make the
blob store recoverable together with the database:

- **Retention matches the recovery horizon.** No bytes are hard-deleted
  while any state the operator can still return to references them. That
  covers the provider's PITR window and graduation's revert window (sibling
  B §7). `_asset_gc` marks bytes deletable with a not-before time at least
  that horizon away, or the operator configures a versioned bucket whose
  lifecycle covers it. `doctor` and preflight check that alignment: a
  widened PITR or revert window with an unchanged blob lifecycle silently
  breaks the rule.
  - Otherwise a PITR to before an asset's deletion revives a ledger row
    whose bytes were already collected. No refusal can recreate them.
  - A restore or cutover still refuses while any referenced digest is
    missing, but that is the fail-closed backstop, not the recovery plan.
- **Release artifacts are keyed by an exact artifact digest.** That digest
  covers every file, `provenance.json` included. `release_files::digest`
  deliberately excludes provenance and `.pending-adoption`, because it names
  the executable identity. So the store records both digests: the execution
  digest for compatibility and the artifact digest for the blob key. Two
  trees with different provenance then never share a blob.

### 4.3 Worker completions and execution ownership

Today a worker opens `BEGIN IMMEDIATE` on its local SQLite ledger, looks up
the delivery key, runs the handler, stores the result and commits, and only
then settles with the server (`worker-ledger.ts`; LLP 3000.009 §5.2). The
ledger therefore gives two guarantees:

- **completion suppression:** a redelivery replays the stored result;
- **execution exclusion:** while one worker sharing the ledger is running a
  handler, another cannot start it.

Both live on one host's disk. Moving only the stored result into the store
would break the second guarantee. Lease expiry returns the effect to
`queued` and clears its claim (`effects.rs`, `expire_run`). So a healthy
handler that outlives its lease would be re-invoked by a successor that
finds no result, and the original's result could no longer be recorded
under its lease.

The slice that moves this state into the store (P1b) must define both
halves:

- **Completion records.** A completion is keyed by the stable delivery key.
  It may be recorded by the attempt that produced it even after that
  attempt's lease has expired. Recording a result someone already produced
  is separate from authorization to settle the current claim. Claim and
  redelivery read the completion before invoking a handler.
- **Attempt records.** Starting a handler records the attempt, with its
  delivery key and lease, in a fenced store transaction. A successor that
  finds an attempt started, not completed, and expired has an *uncertain
  attempt*. Like A2's uncertain steps, it must do one of three things: wait
  out a grace period, reconcile through the provider's idempotency key or
  status query, or park the effect. It never silently re-invokes. Database
  fencing cannot stop an external call already in flight, so the protocol
  makes such a call visible instead of pretending it cannot happen.

Until that slice lands, placement is constrained, and a cross-host move
requires **quiescence**. Waiting for a lease to expire does not establish
quiescence. `expire_run` returns an effect to `queued` while its handler
may still be executing, and the local ledger writes its completion only
after the handler returns (round 3, Astra N3, Grok N3).

- Workers run on the serving host, under `serve`'s supervision.
- **Graduation** first drains workers: the supervisor stops them from
  claiming, then waits for every worker process to exit, so every in-flight
  handler has returned and its completion is in the ledger. The ledger's
  completions are then imported with the store. A worker that cannot be
  confirmed exited refuses the cutover.
- **Standby promotion** cannot drain a host that is stopped or partitioned.
  So promotion parks every non-terminal effect with `attempts > 0` (`expire_run`
  clears `claimed_by` but not `attempts`) and no imported completion, as an uncertain attempt. Such an effect
  is reconciled through the provider or by an operator, and is never
  silently re-queued.
- `doctor` names the ledger file as state that must travel with the store.

## 5. Ownership and fencing

One physical store serves a logical store at a time (parent §3.1). Postgres
can be reached from many hosts, so ownership belongs to the store. This
section has been through two review rounds and a real-Postgres prototype,
[`experiments/postgres-fencing`](../snapback4/experiments/postgres-fencing/README.md)
("the prototype", PostgreSQL 16.15, non-superuser roles). Its witness
numbers are cited as W1–W10. The design separates three jobs:

- **fencing** decides whether a write may commit, and never trusts a clock;
- **takeover** decides when a successor may begin, on the database's clock;
- **continuity** decides whether a database failover keeps the incarnation.

### 5.1 The owner record and the fence

`_owner(singleton, holder, token BIGINT, lease_until TIMESTAMPTZ, ...)`.

- **The fence is the first lock of every writing transaction:**
  `SELECT token FROM _owner FOR KEY SHARE`. The transaction refuses if the
  token differs from its process's token.
  - This covers writes that publish no sequence: refusal receipts,
    receipt-only reports, mints and invalidations, claims, renewals, steps,
    sweeps, asset views, and time-audience pins.
  - The fence comes before `_head … FOR UPDATE`. The adapter's current
    head-first order deadlocks with takeover (W10), so it changes.
- **The token changes only through an explicit `SELECT … FROM _owner FOR
  UPDATE` followed by an update.** `FOR KEY SHARE` conflicts with that
  lock, so takeover waits for every in-flight fenced transaction.
  - Postgres does not queue a new key-share request behind a waiting
    `FOR UPDATE`, so new fences can still be granted while takeover waits.
  - That does not affect safety. Any fence granted before the token
    changes is ordered before the takeover. Afterwards, under READ
    COMMITTED a waiting or new fence reads the new token and refuses; under
    REPEATABLE READ or SERIALIZABLE it raises `40001`, which a retry loop
    must surface as a refusal (W4).
  - Takeover's progress therefore rests on terminating blockers (§5.2), not
    on queueing.
  - **Renewal does not queue behind a waiting `FOR UPDATE` either** (W8;
    round 4, Grok N2). It is a non-key update and takes `FOR NO KEY UPDATE`,
    which neither a key-share holder nor a waiter blocks. Takeover therefore
    first claims the expired lease with an update that renewal does conflict
    with (§5.2 step 2).
- **Renewal is `UPDATE _owner SET lease_until = … WHERE token = $mine`,**
  an update of a non-key column, fenced by its own token. Without the token
  predicate, a renewal that waited on a takeover could rewrite the
  successor's lease and report success to the old owner.
  - Under `FOR KEY SHARE`, renewal never waits on fenced transactions
    (0 ms, W8).
  - The first draft's `FOR SHARE` made every renewal queue behind the
    longest in-flight transaction. In W8 a single 7-second transaction let
    the lease lapse, and the standby took over a live owner. A long
    migration, backfill or serial batch would do the same.
- **Times come from `clock_timestamp()`,** never from a host clock and never
  from `now()`, which is the transaction's start time.
  - A host clock drives only the cadence of renewals and polls.
  - A slow or skewed host clock costs availability, not safety (W5, at ±1 day
    and at 0.1× monotonic).
  - An owner whose renewal fails until its lease lapses stops writing and
    rejoins as a standby. It never assumes it still owns the store.

### 5.2 Takeover

Every connection a serving process opens is tagged
`application_name = sb:<store>:<holder>:<token>`.

- **Format.** `store` and `holder` are fixed-width hexadecimal ids and
  `token` is decimal, so a tag never exceeds Postgres's 63-byte limit. A
  process whose tag would not fit refuses to start rather than truncate,
  because a truncated tag loses the token that bounds termination.
- **Role.** Every process of a store runs as the store's one role. No
  process needs superuser or `pg_signal_backend` (W1).

A standby takes over in one transaction, in a bounded loop:

1. Poll until `lease_until < clock_timestamp()`. Note the token T.
2. **Claim the expired lease before anything else.** Run `UPDATE _owner
   SET lease_until = lease_until WHERE singleton AND token = T AND
   lease_until < clock_timestamp() RETURNING token`, under its own short
   `lock_timeout`.
   - It takes `FOR NO KEY UPDATE`. That does not conflict with in-flight
     fences, so it is granted at once. It does conflict with the owner's
     renewal, which also takes `FOR NO KEY UPDATE`.
   - This relies on the fence being `FOR KEY SHARE` (§5.1). Under
     `FOR SHARE`, the claim itself would wait on every in-flight fence.
   - **Zero rows, or a timed-out claim: abandon, having terminated
     nothing.** The owner renewed, or another standby is mid-takeover. A
     second standby's claim blocks behind the first one's whole takeover,
     then matches zero rows (W11f).
   - **One row:** from here on the owner cannot extend its lease. Its
     renewal waits behind this transaction. Once the token changes, the
     renewal matches zero rows, and the owner learns of the loss.
3. Set a savepoint and issue `SELECT … FROM _owner FOR UPDATE` with a short
   `lock_timeout`. It waits on in-flight fences. The row lock from step 2
   survives a rollback to the savepoint.
4. While it waits, terminate every backend `pg_blocking_pids()` reports that
   has the same role, this store's tag, and a tag token of T or less. This
   needs no registration, so it also catches connections opened late or
   while reconnecting: the prototype's unbounded-block case (W3), where
   blocker termination took over in 2.9 s. If the only blockers carry a
   newer token, abandon.
5. On `55P03`, roll back to the savepoint and go back to step 3. Never wait
   without a bound.
6. Increment the token, record the holder, set the lease, and commit.
7. **After the commit**, terminate every same-role session tagged with this
   store and a token of T or less. This is hygiene: it frees the stale
   fast-path advisory lock and connections. Blocker termination in step 4
   alone suffices for takeover (W3). If the sweep ran inside the loop, it
   would also terminate the owner's waiting renewal. The owner would then
   learn of the loss from a terminated connection (`57P01`) rather than
   zero rows, which is equally safe.

Step 2 precedes every termination and holds a lock that renewal must wait
for. So it either sees the renewal and abandons, or blocks it, and a
standby can never terminate a live owner that has renewed.

**Evidence** ([fencing prototype](../snapback4/experiments/postgres-fencing/README.md),
W11, three runs on PostgreSQL 16.15):

| Witness | Result |
| --- | --- |
| W11a: a renewal between poll and claim | The claim matched zero rows and nothing was terminated |
| W11b: claim first | The renewal blocked for about 1 s, then matched zero rows; no old-token commit landed after the takeover |
| W11c: the old re-read design, run as a control | It killed a live owner that had just renewed. This is the hazard the claim closes |
| W11d: fences while the claim is held | Still granted, in about 0.6 ms |
| W11e: forced `55P03`s | The claim's lock survived rollback to the savepoint |
| W11f: two standbys racing | The loser terminated nothing |
| W2, W3, W8, W10 rerun under the claim | Unchanged |

W8's matrix also showed something the design depends on. A fence granted
during the claim locks the row version the claim already replaced, and it
still blocks takeover's `FOR UPDATE` on the new version.

**Bound.** Takeover lands within lease + poll + one termination round +
the transaction: 3.0–3.3 s for a 3 s lease in the prototype. A clean
shutdown sets `lease_until = '-infinity'` and releases the advisory lock, so
a standby waiting on that lock takes over in milliseconds (W6a). The
advisory lock is that fast path only. Waiting on it as a gate blocks forever
against a stopped owner (W6b, the first draft).

**Backstop.** `idle_in_transaction_session_timeout` on the serving role.
It does not replace termination, because it cannot see a backend blocked
writing to a stopped client (W7). TCP keepalives do not detect a paused
process at all.

**Ambiguous commits.** A COMMIT that races termination can be durable
while its client sees an error. Under synchronous replication that window
is seconds wide (W9). Fencing still orders it before the takeover, and a new
owner treats whatever committed as committed. The claim that every write
path is retry-safe across owners is a P1a deliverable, not an assertion.
P1a produces a per-path table: each write path (mutation, mint, refresh,
invalidation, claim, renewal, step, settle, sweep, asset view,
time-audience pin, activation), its idempotency key, and what a retry
observes in each of three outcomes (rolled back, committed and
acknowledged, committed but unacknowledged). Any path without a key gets
one; a mint is keyed by its existing mint binding. P1b's witness forces a
commit to race termination during a synchronous wait, retries the same
operation under the new owner, and asserts a single visible effect for at
least mint, claim, receipt and step.

**Connections.** Owner and standby connect directly or through a pooler in
session mode, never transaction mode. Under transaction pooling, a backend
pid and its tag belong to whichever client is mid-transaction, so
termination cannot identify the old owner. `doctor` refuses transaction
pooling on every serving connection and verifies same-role termination on
the provider. The prototype found Supabase's documentation ambiguous on the
latter.

### 5.3 Activation

`deploy` and `rollback` run as fenced transactions. The release tree is
uploaded by digest first (§4.2), and selection is a single fenced commit.
Two hosts or directories targeting one store cannot activate at once.

### 5.4 Failover and continuity

**History.**

- Revision 3 made every promotion a new incarnation. The author rejected
  that.
- Revision 4 tried to keep the incarnation through any failover. It used an
  asynchronous chain checkpoint and narrow repair. Round 4 showed it
  unsound (§12):
  - commits acknowledged after the last checkpoint can be lost without
    detection, revocations among them;
  - two primaries can both serve until a checkpoint write lands;
  - a hash cannot reconstruct lost records, attempts or graduation
    decisions.

When the database loses acknowledged writes, no asynchronous mechanism can
recover them. Only a synchronous write somewhere else can. So this section
draws the line at the database's replication guarantee, where Supabase and
raw Postgres applications draw it too.

#### 5.4.1 The HA mode is declared, and decides what a failover means

The release declares the store's HA mode. `doctor` checks what it can.

| Mode | Examples | A failover |
| --- | --- | --- |
| `none` | A single instance | A restart: keeps the incarnation |
| `storage-sync` | RDS Multi-AZ instances, Cloud SQL HA, Aurora, AlloyDB, Neon: replication below Postgres, so a failover restarts Postgres on the same replicated storage | **Keeps the incarnation; clients see a reconnect** |
| `streaming-sync` | Postgres synchronous replication, where the HA manager promotes only a synchronous standby and fences the old primary (Patroni `synchronous_mode_strict`, CloudNativePG, an equivalent provider mode) | **Keeps the incarnation; clients see a reconnect** |
| `async` | Asynchronous streaming replicas, or any configuration that can promote a lagging replica | The operator chooses: `new-incarnation` (the default) or `continue` (§5.4.3) |

**What the lossless modes rely on.** In `storage-sync` and
`streaming-sync`, Snapback relies on the database and its HA manager for
two things:

- that acknowledged commits survive a failover;
- that the old primary is fenced.

That is the same contract every Postgres application relies on. Snapback
adds its own obligations:

- **Uncancellable COMMIT.** The adapter runs COMMIT with
  `statement_timeout = 0`. A COMMIT that returns the
  "canceling wait for synchronous replication" warning is treated as
  unacknowledged and fails closed until the standby's flush position passes
  its LSN.
- **Streaming check.** In `streaming-sync`, each renewal checks
  `pg_stat_replication` for a synchronous standby that is actually
  streaming, where the serving role can see it. If none is, the owner
  stops acknowledging writes and alerts.
- **Live qualification.** P1b qualifies each named provider and HA manager
  with live failover witnesses. One example: a revocation committed just
  before the failover must still hold after it. Documentation alone does
  not qualify a provider.

#### 5.4.2 Detection: a persisted identity and a tripwire

- **Identity.** At every ownership acquisition, the store compares the
  database's system identifier and timeline with a row in the store
  (`_owner.db_identity`), so a freshly started process detects a promotion
  too.
  - On vanilla Postgres 16, `pg_control_system()` and
    `pg_control_checkpoint()` are executable by PUBLIC.
    `pg_walfile_name(pg_current_wal_lsn())` exposes the timeline as a
    fallback.
  - Preflight requires both values to be readable.
  - A timeline change is expected in `streaming-sync`. It decides the
    outcome only in `async`.
- **Tripwire.** Every durable write extends a hash chain over the
  committer's stream (§6.3). The owner writes `(store_id, revision, hash)`
  to the blob store asynchronously. At acquisition, a database that lacks
  the last checkpointed revision, or has a different hash at it, has lost
  acknowledged history. In a lossless mode that means the declared contract
  was violated. The store then applies the `async` rule configured for it,
  `new-incarnation` unless set otherwise, and raises an alert.
  - **It detects gross violations; it does not prove continuity.** Losses
    newer than the last checkpoint are invisible to it.
  - It never blocks serving: a stalled checkpoint only weakens the
    tripwire.
- **Graduation pins the mode.** A graduation target must be in `none`,
  `storage-sync` or `streaming-sync`. A timeline change on the target
  during graduation or its revert window halts graduation with the source
  fenced until the operator resolves it. An acknowledged decision lost to a
  lagging promotion therefore cannot make both stores writable (sibling B
  §5).

#### 5.4.3 Asynchronous mode: the operator chooses

On a detected promotion in `async` mode, the operator chooses one of two
behaviors:

- **`new-incarnation`** (the default) is correct. Recovery mints a new
  incarnation, fences old device resumes and sessions, quarantines
  uncertain work, and reconciles blob and ledger state, as a restore does
  (LLP 3000.009 §9).
- **`continue`** has the semantics a Supabase or raw Postgres application
  gets. The store keeps its identity and serves. Acknowledged writes and
  revocations in the lost window may be gone. Every non-terminal effect
  with `attempts > 0`, or admitted within the configured window before the
  promotion, is parked as uncertain, because a rollback may have erased its
  attempt record. The loss report names what the tripwire saw. `doctor`
  states these consequences when the mode is chosen.

#### 5.4.4 Considered and not taken in P1

- **A synchronous external anchor.** Every acknowledged batch waits for a
  conditional write to an external store that holds the ownership lease and
  the authority journal, and the owner stops serving when it cannot write.
  This is sound for `async` databases. It puts the object store's latency
  and availability on every commit, and makes it a second availability
  dependency. It is the path if an application needs `async` replication
  with Snapback-level guarantees. It would get its own child RFC.
- **Revision 4's narrow repair.** That meant device-held chain hashes,
  retained acknowledged writes resubmitted after loss, and journal replay
  after detected loss. Round 4 showed it cannot cover the undetected
  suffix, forks, or erased attempts and decisions without the synchronous
  anchor above.

The cost of the P1 design is one hash per durable write, an asynchronous
checkpoint, a declared HA mode, and `doctor` checks. There is no
device-protocol change.


## 6. The commit path

### 6.1 The seam

```rust
trait Committer {
    /// Run one mutation to an outcome, publishing at most one commit.
    fn commit(&self, op: Admitted, run: impl FnMut(&mut StoreTx, &mut Runner) -> Outcome)
        -> Result<Committed, RuntimeError>;
}
```

The reference implementation is today's protocol: reserve the head under its
lock, run the program, send the batched tail, commit. It stays in the suites
as the oracle for any other implementation. The same seed gives the same
outcomes, and the store oracles compare them.

### 6.2 Why the reference cannot be the production path on Postgres

Parent §3.3 gives the bound. The reference holds the head through every
program call and the flush. The code confirms it:

- SQLite takes `BEGIN IMMEDIATE` before `Runner::run`;
- Postgres serialized mode takes `SELECT seq FROM _head … FOR UPDATE` when
  the transaction begins.

So the database's own group commit can never combine two Snapback commits.
Postgres flushes concurrent committers together, but serialized holders
arrive one at a time.

### 6.3 Candidates, in the order they are taken

**(0) The serial batch** (proposed by the panel; §12). The committer drains
up to N queued mutations and runs them back to back inside one store
transaction:

- each mutation runs under its own savepoint, as the adapters already
  isolate a program today;
- the transaction makes one head update, to the batch's last sequence, and
  one flush;
- each mutation is acknowledged after that flush.

The batch keeps the reference's properties. It has the same serial order,
needs no read sets and no overlay, and reads its own writes natively.
Visibility is atomic per batch, so watermarks stay contiguous. A database
error in the batch reruns its members one at a time under the reference.

Its throughput is about `N / (N·k·RTT + exec + flush)`. S0 measured it
([`experiments/postgres-commit-path`](../snapback4/experiments/postgres-commit-path/README.md),
a statement-level model):

- **On Postgres it barely helps.** The best batch reached about 150–200
  commits/s at 0.5 ms RTT, against the reference's 120. Each member still
  makes about 10 round trips inside the serial section, and the flush it
  saves cost 20 µs on that disk.
- **On SQLite its gain is the flush's share.** That is about 1.46× at N=16
  on a 20 µs-fdatasync disk (an estimate; the core cannot yet be driven in a
  batch from outside). The gain should be far larger on disks whose flush
  costs milliseconds, which is unmeasured.

So (0) is not the Postgres answer. It stays because it is cheap and correct
by construction. It is the hot-key fallback for (a), the reference for
qualifying (a), and a SQLite improvement on slow-flush disks. It lands at
P0.

**(a) An optimistic single committer.** Convex orders commits this way, and
it is the candidate for removing the `k·RTT` term on Postgres. The first
draft omitted three requirements, all now part of the candidate:

1. *Execution.* A mutation runs at a snapshot S. On Postgres this is a
   `REPEATABLE READ READ ONLY` transaction. S is labelled with the internal
   revision read inside that snapshot (item 4), not with the public head,
   because non-head writes are part of the snapshot too. Its writes are buffered in C2's read-your-writes overlay (LLP
   3000.009 §4.2): point reads, scans, counts, deletions and constraints over
   buffered writes, with error and charge order preserved.
2. *A complete read set, recorded at the adapter boundary.* Every read
   passes through `Rows`, `PartitionRows`, or a durable-state operation, and
   is recorded there rather than in the `Runner`. Today `Runner::read_tables`
   records table names only. That includes sequence values, cap counts,
   index heads, `emit … once` keys, `_ops` lookups, and the authority facts
   the operation was admitted under: session validity, principal
   generation, lease. Key ranges must be precise. Table granularity would
   make every concurrent reader of `messages` a conflict, so precise ranges
   are a precondition of (a), not increment E's later optimization.
3. *Serial validation within the batch.* The committer folds each validated
   mutation's write set into an in-memory image before it validates the next
   one. A mutation is checked against every durable write with internal
   revision in (S, current] **and** against the mutations already accepted
   into the current batch. The batch is
   therefore one serial image, and two mutations that read the same counter
   at S cannot both enter it.
4. *The internal revision is the validation order, and the committer
   assigns it.* Session invalidations, claims and receipts commit without a
   public sequence today. Under (a) every durable write, head-advancing or
   not, takes the next internal revision and records its key footprint: the
   keys and ranges it wrote, such as the principal for a mint or
   invalidation, or the effect for a claim. Validation intersects read sets
   with those footprints, so a revocation that landed after S is seen. A
   mint for another principal is not a conflict. The public head remains
   only the sync watermark.
   - **Assignment** (round 3, Fable N2, Muse N2). A revision must be
     commit-ordered, or validation is unsound. A counter row locked until
     commit would recreate the `_head` hot row for all identity and work
     traffic, and a sequence is not commit-ordered.
   - So **every durable write goes through the committer**, whichever
     committer runs: reference, (0) or (a). The one exception is
     ownership-lease renewal. It is fenced by its token (§5.1), is not
     application state, and must not wait behind a long batch. Mints, claims, renewals, steps
     and sweeps become operations submitted to the committer's stream. The
     revision is the position in that stream, and the fence is taken once
     per batch. All committers record footprints in one key space, so (a)
     sees conflicts with work that fell back to (0).
   - This is the shape the parent's P2 already assumes: commits go through
     one committer. Non-head writes then pay batch latency, and S1a measures
     that.
   - The rejected alternative is validating by MVCC visibility: label S with
     `pg_current_snapshot()`, and treat a footprint whose transaction id is
     invisible in S as a conflict. It needs no serial stream. It is set
     aside because it ties validation to Postgres internals the SQLite
     adapter cannot share. The seam permits it per adapter if S1a shows the
     stream costs too much.
   - **Monotone writes do not conflict.** A time-audience pin only ever
     advances `max(pin, now)`, and `now` is assigned at admission, not read
     from the store. So pins are exempt from conflict detection and are
     applied as a batch maximum. §6.4's monotone-clock rule then holds in
     batch order: a mutation whose `now` is below the batch's committed pin
     reruns.
5. *Sequence-dependent execution.* Today the adapter takes `next_seq()`
   before the `Runner` starts, and execution embeds it. Effect ids are
   `effect-<seq>-<n>` (`runner.rs`), and Following stores admission tokens
   derived from the sequence (`timeline.rs`) that it later compares to tell
   delivery from backfill. Two executions at one snapshot would read the
   same provisional sequence. Under (a), sequence-derived values are
   therefore provisional placeholders. The overlay carries them, and the
   committer resolves them at commit to the sequence the mutation actually
   receives. Row images, index entries, comparisons and outbox rows that
   contain them are rewritten in the same batch transaction. A key that
   contains a placeholder is resolved before validation, so footprints never
   hold placeholders. Eligibility is conservative, by taint: any flow of a
   placeholder into a branch, a comparison, a string operation, a read-back
   or a row round trip makes the program ineligible for (a), and it runs
   under (0). `check` classifies this statically. Qualification covers
   concurrent emitters and Following transitions, not only counters.
6. *Batch commit.* As in (0): one Postgres transaction per batch, writes and
   tails as `unnest` arrays, one head update, one flush. On a conflict the
   mutation reruns at a new snapshot. After a bounded number of conflicts it
   goes to (0), so hot keys make progress.

Two bounds apply:

- the execution stage, about `connections / (k·RTT + exec)`;
- the commit stage, about `batch / (2·RTT + flush)`.

So (a) is connection-bound before it is flush-bound. Its recorded read sets
also supply LLP 3000.009 §7.1's read-set invalidation.

**S0's evidence.** The reference committer's serial time fits
`2.05 ms + 11.98 × RTT`. Twelve is exactly the number of round trips the
head lock is held across. That gives 120 commits/s at 0.5 ms, against raw
Postgres's 5,700/s with four writers and 89,000/s with 64. The upper bound
of (a)'s commit stage, with execution, validation and the overlay omitted
by construction, is 15,700/s at 0.5 ms. Child C's first decision rule
therefore fires, and **the author commissioned (a)** (parent §7). What S0 did not measure is (a)'s execution
stage. Child C's S1 sizes it before C2's overlay is built (child C §8).

**(b) Database transactions with an ordering stage.** The first draft's
version cannot keep exact snapshots:

- If a mutation's data commits before its ordering stage, readers see writes
  without a sequence, or sequence N+1 before N. LLP 3000 §7 already rejects
  this.
- If the data stays open until the stage flushes, the single `_head` row
  serializes the flushes again. W9's serializable cells failed on exactly
  that.

A correct version is a different protocol:

1. Assign the order in a short critical section.
2. Commit data transactions without holding that section across the flush.
3. Publish only the contiguous committed prefix.
4. Make a reader at W use a snapshot that excludes every commit above W.

That protocol is not designed here. (b) stays a named alternative, to be
taken up only if (a)'s overlay fails its differential.

**Set aside: the database's WAL as the commit order.** Logical decoding
emits commits in commit-LSN order and needs no head row. Postgres does not
guarantee that snapshot visibility follows commit-LSN order. Snapback's
snapshot-plus-catch-up protocol needs exactly that equivalence, and so does
watermark exactness. Logical decoding would also make every deployment
depend on replication slots, which some managed tiers restrict.

### 6.4 What stays fixed

Whichever candidate wins, these stay fixed:

- one total order per store;
- no gap below a published watermark;
- exact snapshots;
- whole-commit atomicity of rows, indexes, maintains, log, outbox and receipt;
- receipts recorded once;
- the same outcome as the reference for the same admitted inputs, modulo
  which concurrent mutation won;
- the authority clock monotone in commit order: a mutation executed with
  `now = t` commits only if `t` is at or after the last committed pin
  (`pin_writer_time`, `_meta.time_audience_clock`), and otherwise reruns;
- effects admitted only inside the commit, so a conflict rerun never
  performs a provider call;
- every durable transaction fenced by the owner token (§5);
- the same wire.

The simulator's seven invariants and the store oracles qualify the new
committer on both stores before it serves traffic.

## 7. Layout v1

### 7.1 Managed data

The generic layout stays (LLP 3000.009 §4.3). In production:

- `r` and `i` are `LIST`-partitioned by `t`, one partition per logical table,
  created at adoption. Vacuum, `ANALYZE` and bloat then act per table, and
  dropping a table drops a partition. Internal tables stay unpartitioned.
- Row images move from `TEXT` canonical JSON to the existing canonical form
  in `BYTEA`, or stay as text if child C shows no measurable difference. The
  bytes must be identical across stores for graduation's digests (sibling B
  §6).
- The portable 2,048-byte key bound and the 512-byte label bound stay, with
  every index still checked on every store.
- `C` collation on every key column, as today.

### 7.2 The head

`_head` is one row updated by every commit: a hot tuple, and the fencing
check of §5. Under the reference committer it is updated once per commit;
under (a), once per batch. Its table sets `fillfactor` so updates stay HOT.
Child C measures it.

### 7.3 Log retention

`_log` and `_commits` grow without bound on both stores today. The first
draft proposed a simple floor below which log rows are deleted. The panel
showed that would be silently wrong, for two reasons (§12):

- **No re-acquisition path exists for a device behind the head.**
  `partition::stream` replays spans above a device's watermark. The only
  snapshot path is a device with no watermark at all. A deleted span looks
  like "no events for you", and `/changes` invalidates everything only when
  its page fails to reach the head.
- **The log below a watermark is also authority state.**
  `memberships_before` reads the latest join or scope event at or below the
  watermark, and the expired-grant walk reads membership transitions from
  sequence zero with their commit times. The code's own annotation (`@ref
  LLP 3000#7`, `partition.rs`) says a content page cannot establish authority
  from a truncated ledger. Deleting below a floor changes answers for
  devices *above* it: an owed revocation for an expired grant is skipped.

So retention is **checkpoint plus floor**, as LLP 3000.002's proposal
"coordinated history, receipt and principal retention" already requires,
and it is not part of P1:

1. Fold the membership transitions and their commit times at floor F into
   a materialized authority checkpoint that the partition contract reads.
   Extend the shared partition oracles to consume it.
2. Publish F and the checkpoint atomically, with LLP 3000.002's crash-safe
   publication order.
3. Only then drop **content** events below F. Join and scope events are
   folded first, or kept in a table that is never pruned.
4. A resume, a `/changes` page or a sync page whose watermark is below F,
   or that would span a gap in `seq`, is an explicit refusal. The refusal
   forces a fresh snapshot, so retention can never answer silently.
5. On SQLite the head is `MAX(seq) FROM _commits`, so retention there
   persists the head first. On Postgres, `_log` may be range-partitioned by
   `seq` once its foreign key to `_commits` is replaced by the floor's
   invariant.

Until that design is commissioned, with its own Moves line (parent §7), both
stores keep the whole log, and graduation copies the whole log (sibling B
§4.2). Child C measures the cost of keeping everything (H7) and, once it
exists, of the checkpoint read on resume.

## 8. Connections, roles and supported Postgres

- **Driver.** The synchronous `postgres` crate stays for P1. The host's
  request-thread model (32 request workers, held long waits) maps onto a
  bounded pool. A held change poll waits on the in-process wakeup, or on
  `Notifier` at P2, and borrows a connection only to answer.
- **Connections.** P1 uses one dedicated owner connection (advisory lock,
  then `LISTEN`), one committer connection, and a reader pool sized from the
  request workers. Transactions are short and statements prepared. The store
  works directly or through a pooler in session mode. Transaction pooling
  is unsupported for **every** serving connection. Takeover terminates
  backends by tag and blocker, and under transaction pooling a backend
  belongs to whichever client is mid-transaction (§5.2). `doctor` detects
  it from the client side: it reads `pg_backend_pid()` and the session's
  `application_name` in two separate transactions on one client
  connection. A change means the pooler reassigns backends, and `serve`
  refuses that connection string. The same check runs when each serving
  connection opens.
- **Read replicas.** Not in P1. A replica-served read would need a causal
  token so that a client reads its own writes. That belongs with P2.
- **Roles.** These come from LLP 3000.009 §6.4:
  - *owner*: DDL, internal migrations and partition management, used by
    `deploy` and adoption;
  - *core*: managed reads and writes, used by `serve`;
  - *inspect*: read-only over generated views, used by `sql`.

  Increment D later adds the per-operation read roles and the
  database-owned write role. P1 creates these roles even though D is not
  built, so D does not have to reshape privileges on a live store.
- **Supported Postgres.** 16 and 17. No extension and no superuser required.
  TLS by default for any host other than a Unix socket; credentials are
  secret references in the release, never values. The qualification matrix
  is vanilla Postgres plus at least two managed providers that child C uses
  (for example RDS and Supabase's Postgres). It records each provider's
  restrictions.
- **Isolation.** One Postgres schema per logical store, as the evaluation
  does. A managed service gives each application store its own database
  (LLP 3000.009 §9).

## 9. Parity

A schema `check` accepts on SQLite runs on Postgres with the same outcomes,
or `check` names the store requirement before deploy. The features refused
today — maintained columns, `not before`, assets, jobs, native jobs, actions,
schedules — must all reach parity before P1 is called a production target.
The store oracles in `snapback4-difftest` already compare exact outcomes.
P1 widens the generator so their prelude covers each family's operations, not
only queries and mutations.

## 11. Alternatives considered

- **A typed per-table layout on Postgres.** LLP 3000.009 §13 declined it.
  Nothing here changes that, and child C names the measurement that would
  reopen it: storage and WAL amplification beyond its stated bound.
- **Port by table translation**, giving each SQLite table a Postgres twin and
  translating statements one by one. This is faster to start, but it keeps
  policy in SQL in two dialects. The C3.2 pattern (policy in Rust, storage in
  the adapter) already showed the alternative works.
- **An async driver and runtime now.** It would change the host's
  concurrency model at the same time as its store. Child C will show whether
  threads or connections are a binding limit before this is taken up.
- **Postgres-only server storage.** LLP 3000.009 §13 declined it.

## 12. Panel revision

The one-round panel (Astra max, Fable xhigh, Grok 4.7 xhigh; parent §9)
judged this document sound with major issues. Revision 1 changes:

- **§5:** the head predicate alone left non-head writes unfenced, and a
  paused owner's advisory and row locks blocked takeover forever. Every
  durable transaction is now fenced; takeover is lease-driven with backend
  termination; same-incarnation failover requires a replication guarantee
  that keeps every acknowledged transaction.
- **§6:** the serial batch is added as the first committer. Candidate (a)
  now validates within its batch, records complete read sets at the adapter
  boundary, and gives every durable transaction an order. Candidate (b) is
  demoted to an unspecified alternative, because its first version broke
  exact snapshots.
- **§7.3:** retention by deletion would have skipped owed revocations. It
  becomes checkpoint plus floor under LLP 3000.002's proposal, with explicit
  refusals, and leaves P1.
- **§4:** release artifacts, worker completions, change evidence, action
  steps, cap occupancy and narrowed dormant rows join the inventory.

### Round 2 and the experiments (revision 2)

Round 2 (Astra, Fable and Grok as deltas; Muse fresh) and two experiments
drove these changes:

- **§5, rewritten from the fencing prototype.** Its witnesses W1–W10 ran on
  real PostgreSQL 16.15 as non-superuser roles. In every witness, nothing
  the old owner wrote committed after a takeover.
  - **The pid list blocked takeover forever** when a paused connection was
    unlisted (W3; round-2 Astra N4, Fable note 3). Replaced by tags and
    blocker termination.
  - **`FOR SHARE` starved lease renewal** and let a long transaction cause a
    takeover of a live owner (W8; Fable N1, Grok note). Now `FOR KEY SHARE`,
    with the token changed only under `FOR UPDATE`.
  - **The head-first lock order deadlocks with takeover** (W10). The fence
    is now the first lock.
  - **Ambiguous commits** are named, and writes are retry-safe across owners
    (W9).
  - **Failover continuity** is detected by system identifier and timeline,
    with a three-part guarantee (Grok N5, Muse F1).
- **§4.2.** Blob retention is matched to the recovery horizon (Muse F2). An
  exact artifact digest is used, because the execution digest omits
  provenance (Astra).
- **§4.3.** Execution ownership and uncertain attempts (Astra N3, Grok N6).
- **§6.3.** (a) validates against an internal revision with key footprints
  (Grok N4, Fable note 4). Sequence-derived values are placeholders (Astra
  N5). S0's measurements are recorded. The serial batch is not the Postgres
  answer, and (a) is proposed for commissioning.
- **§8.** Transaction pooling is refused for every serving connection
  (Grok note).

### Round 3 (revision 3)

- **§5.4.** Every reviewer found the continuity guarantee unsound, as
  FUNDAMENTAL (Astra N1, Grok N1) or MAJOR (Fable N1, Muse N1):
  - a lagging replica can be promoted;
  - a fresh process has no baseline to compare against;
  - checking the configuration is not checking liveness;
  - "the provider fences the old primary" is trust;
  - the adapter's `statement_timeout` acknowledges a commit whose
    replication wait was cancelled.

  In P1, every promotion is a new incarnation. Detection uses a replicated
  identity row. COMMIT is uncancellable. Keeping the incarnation becomes a
  later, per-provider mode that needs evidence.
- **§5.1–§5.2.** Renewal is token-fenced. The `FOR KEY SHARE` queueing claim
  is corrected (Fable). Takeover re-reads before every termination round and
  bounds blocker termination by token, restoring the prototype's bound
  (Grok N2, Astra and Fable notes). The tag format is specified. The
  retry-safety claim becomes a per-path table with a witness (Muse N3).
- **§4.3.** The interim worker fence missed a handler that had outlived its
  lease (Astra N3, Grok N3). It is now drain on graduation and park on
  promotion.
- **§6.3.** The committer assigns every revision through its stream, and
  all committers share one footprint key space (Fable N2, Muse N2).
  Monotone pins are exempt from conflict detection. Placeholders are
  resolved before validation and eligibility uses taint (Grok and Muse
  notes).
- **§4.2, §8.** The following reader's P2 disposition, the blob-window
  check, and the client-side detection of transaction pooling (Muse).

### Author rulings (revision 4)

- **Rejected: "every promotion is a new incarnation"** ("this seems silly.
  can you come up with a way to fix this?"). Revision 4's §5.4 (superseded in
  revision 5 after round 4) proved continuity from evidence:
  - a hash chain over the committer's stream;
  - an asynchronous checkpoint in the blob store, advanced by conditional
    write;
  - device-held hashes.

  Supported HA configurations lose nothing, so a failover is a reconnect.
  Detected loss is repaired narrowly. A new incarnation is reserved for a
  provably different history.
- **Commissioned: the optimistic committer (a)** ("yes unless there are
  realistic alternatives"). The alternatives considered are in parent §7.

### Round 4 (revision 5)

A narrow round (Astra and Grok) reviewed revisions 3–4. Both returned
SOUND WITH MAJOR ISSUES.

- **Revision 4's continuity design was unsound** (Astra N1, N2, N5, all
  FUNDAMENTAL; Grok N1, FUNDAMENTAL; Astra N3, N4):
  - an asynchronous checkpoint cannot detect losses newer than itself;
  - it cannot stop two primaries serving before it lands;
  - journal replay ran only after a detected loss;
  - a hash cannot reconstruct lost writes, attempt records or graduation
    decisions.

  §5.4 now draws the line at the database's replication guarantee: a
  declared HA mode, lossless modes keeping the incarnation, an operator
  choice in `async`, the checkpoint as a tripwire, and graduation pinned to
  a lossless mode. The synchronous external anchor that would make `async`
  safe is recorded as a separate path.
- **Renewal does not queue behind a waiting `FOR UPDATE`** (Grok N2,
  following W8). Takeover now claims the expired lease with a conflicting
  no-op update before any termination.
- **Smaller items** (Grok, Astra): the park predicate is `attempts > 0`;
  renewal is exempt from the committer stream; the P1b witness list no
  longer contradicts §5.4.
