## 1. Summary

This RFC turns the Postgres evaluation adapter into a production store. The
data plane already transfers. The remaining work is everything around it:
the internal tables (31 at the first count, more after the panel's inventory), the on-disk release tree, the worker's completion ledger, and the SQLite connection that serving code reaches
directly. There is also the process-local coordination that assumes one
server, and asset bytes kept as local files. The decisions:

1. A three-layer port — access, durable state, host coordination — and the
   rule that only an adapter touches a connection (§3).
2. An inventory of every durable and in-process item, with its contract
   family and its P1 and P2 disposition (§4).
3. Ownership held by the store: every durable transaction fenced by the
   owner token, takeover driven by a database-clock lease that terminates
   a paused owner's sessions, and a declared HA mode that decides what a
   failover means: lossless modes keep the incarnation, and in `async` the
   operator chooses (§5).
4. A `Committer` seam with today's lock-first protocol as the reference, the
   serial batch as the first committer, every durable write going through
   the committer's stream, and an optimistic committer (a)
   designed beside it (§6). The sibling scale RFC decides whether (a) is
   built.
5. Layout v1: the generic layout kept and partitioned by table, with the hot
   head row addressed. Log retention is checkpoint plus floor and outside
   P1 (§7).
6. Roles, connections and the supported Postgres matrix (§8).
7. A parity rule, with no silent Postgres subset (§9).

## 2. The coupling today

| Coupling | Where | Consequence |
| --- | --- | --- |
| Direct SQL in the core | 23 files of `snapback4-core`, about 10,000 lines using `rusqlite`; families like assets, release events, dormant state, credentials and time audiences exist only as SQLite statements | Each needs a contract and a Postgres implementation, not a translation |
| Serving code reaches the connection | `engine.store().conn()` in `serve_readers.rs`, `serve_changes.rs` and others; `Shared.engine: FairMutex<Engine>` names the SQLite `Engine` type | `serve` cannot be generic over a store until these calls go through the port |
| One owner by file lock | `store_owner.rs` locks a sidecar file and pins its inode; `serve.lock` is an address hint | Means nothing for a database two hosts can reach |
| In-process coordination | `Shared`: `committed: Condvar`, `seq`, `presence: Arc<Live>`, `ephemeral: Arc<Hub>`, `long_waits`, `change_answers`, `asset_transfers`, the following reader | Correct for one process. P2 needs each one shared or pinned |
| Asset bytes on disk | `assets.rs` writes `<store>/assets/<id>` with a rename and directory fsync | A standby or second host cannot see them, and database PITR does not cover them |
| Internal-table upgrades in `attach` | `ALTER TABLE … ADD COLUMN` guarded by catalog probes, on both stores | Needs a versioned internal-migration runner, applied under the ownership fence |
| No log retention | No non-test code deletes from `_log` or `_commits`, and sync reconstructs authority from the whole membership history | Unbounded growth on both stores; retention needs an authority checkpoint (§7.3) |
| State outside the store | The release tree and `current` pointer beside the store; the worker completion ledger beside the store | A standby or second host cannot serve the release or suppress redelivered effects (§4.1–§4.3) |

## 3. The port

### 3.1 Three layers

```
            serve / deploy / dev / sql / doctor            (crates/snapback4)
 ───────────────────────────────────────────────────────────────────────────
  Host coordination: Notifier · Lease · EphemeralBus · BlobStore
  Durable state:     StoreTx { identity, work, assets, release, evolution,
                               receipts, sequences, time }  +  Committer
  Access:            Rows · PartitionRows  (+ prefetch, batched tail)
 ───────────────────────────────────────────────────────────────────────────
        SQLite adapter                     Postgres adapter        (only these touch a connection)
```

- **Access** keeps `Rows` and `PartitionRows` and C1's batching unchanged.
  The adapter contract stays: rows in key order at the transaction's snapshot.
- **Durable state** is a typed transaction handle (`StoreTx`) with one
  sub-interface per family (§4.1). Each operation is semantic, such as
  `claim_work(spec, now, lease)`, `mint_session(binding)`,
  `record_step(invocation, digest, outcome)` or
  `ledger_asset(intent, digest)`. None of them takes SQL. Policy stays in
  shared Rust above the handle: what a claim refuses, how a generation fence
  works, the order of refusals. The adapter does storage. This is the shape
  C3.2 already gave authority: one typed policy, a SQLite and a Postgres
  transaction adapter.
- **Host coordination** names what processes must share (§4.2). Each item has
  an in-process implementation, used by SQLite and by P1, and a P2
  implementation.

### 3.2 The rule

Only `store::sqlite` and `engine::postgres` (renamed `store::postgres`)
touch a database connection. A suite test greps `crates/snapback4` and the
non-adapter core for `rusqlite::`, `postgres::`, `.conn()` and
`.query_row(`, and refuses them. Each refusal names this section. The `sql`
inspection verb (LLP 3000.007 §8.8) becomes a port operation:

- on SQLite, generated views over a read-only connection, as today;
- on Postgres, generated views in the store's schema, under a read-only role.

The lead chooses an enum over the two stores (§3.4). `Engine` owns `AnyStore`
and uses `AnyTx` concretely; it does not become generic. The host never names
a backend type outside its configuration.

### 3.3 Extraction first, with no behavior change

P0 moves the SQLite code behind the contract, with no change of behavior,
before any Postgres family is written. Its evidence is the existing suite
(`scripts/test.sh`), the corpus, the simulator and the device oracles, all
unchanged. The wasm budget does not move, because the device does not link
the server families. This is LLP 0046's lesson: plugging Postgres into an
unextracted seam produces a second engine, not a port.

**P1-CE implementation note (2026-10-23).** The unified Postgres adapter
now records the shared net-image recorder's footprint on every public commit.
`Rows::put`/`delete`, explicit widening and uncovered touched-table fallback
match SQLite. The buffered commit slot owns its encoded footprint; the existing
single tail CTE inserts `_change_evidence` and prunes sequences `<= seq - 1000`
with saturating subtraction. Both operations depend on the successful commit
row. They add no driver exchange, prepare, writer transaction or evidence DDL.
Head, log, effects, evidence and pruning roll back together. Each member resets
its recorder; savepoints checkpoint it with the tail/head. Recovery invalidates
the row cache and conservatively widens evidence, as SQLite does: rolled-back
interpreter work cannot regain certification. No new design decision is needed;
this applies LLP 3000.023 §12's rollback rule to the new adapter.

`/changes` already uses one enum read transaction for head, commits and evidence.
The SDK's `/sync` stream now calls `Engine::certified_stream_at`: partition
images/head, pending receipt acknowledgements and the bounded footprint share
one physical read transaction on both stores. Preservation and settlement change
classification use that same footprint. Postgres uses REPEATABLE READ; commits
forced after the head or evidence read cannot mix snapshots. Missing, pruned,
incomplete, malformed, oversized and explicitly unknown intervals still encode
unknown, including `preserved: null`; a known empty list still certifies possible
revocation. Exactly 500 commits remain the certification bound.

Certified `/changes` and ordinary admitted sync now enter the Postgres passed
denominator. This admits no additional schema composition or background producer:
union sync, `not before`/timed publication and every other §3.4 named refusal
remain unchanged. Shared writer/prune/rollback cases run through `AnyStore` on
both adapters, alongside the existing bounded reader and attach-shape cases.
The public configured deploy/serve witness exercises identified writes, a
program-only release, preserved and revoked changes, the SDK stream request and
a pruned window on both stores, comparing store-independent wire bytes. The
[P1-CE report](../snapback4/reports/20261023-p1-ce.md) records exact verification and both RT0 tables; SQLite's table is
unchanged and the tail's new CTE clauses require no exchange-table adjustment.

**P1-MR fix round 1 (2026-10-21).** `preserved_between` returns an
optional list: missing, pruned, incomplete, malformed, over-limit or explicitly
unknown evidence returns unknown, never a certified empty list. This is a
deliberate SQLite wire correction for those intervals: `/changes`, sync and
mutation acknowledgements encode unknown as `preserved: null`. Known
classification is unchanged; sync now explicitly carries even a known empty
list, which previously was omitted. The client treats null/absent preservation
evidence as unable to certify revocation, including opaque and protected reads;
it still refreshes the answer. A known empty list retains the withdrawal bound.
This supersedes the older unknown-evidence withdrawal wording in LLP 3000.023
§12. The shared evidence contract and SQLite HTTP missing/unknown-summary
witnesses pin the distinction. One shared relation checker also rejects
inheritance parents, inheritance children and partitioned ledgers in foundation,
identity, jobs, outbox, assets and requests, preserving each family's named
schema error. The `_ops` and asset-GC witnesses include duplicate logical keys
split across a parent and child; every family exercises all three refusals.

**P1-MR change-evidence reader (2026-10-21).** `ChangeEvidence` now runs
on Postgres transaction snapshots and the store reader. Attach installs
`_change_evidence` and validates both evidence and commit-table shapes;
operations perform no DDL. Both stores select explicit columns in total
commit-sequence order with the same 501-row lookahead. Shared policy checks
the signed sequence domain before adapter access and checks successor
arithmetic without wrapping; empty intervals remain valid at every unsigned
endpoint. Missing tables, missing evidence, missing commits, malformed or
oversized footprints and intervals beyond 500 commits all widen. Exactly
500 commits, exactly 256 KiB and sequences up to `i64::MAX` are covered by
one shared contract, along with the actual preserved-table classification.
At P1-MR's landing the Postgres commit tail recorded no footprints, so its
commits widened; the reader had no `PostgresEngine` host caller until S10.
P1-CE above supersedes that writer/serving limitation. P1-MR itself did not
manufacture evidence or wire `/changes`/`serve`.

**P1-MR receipt reader (2026-10-21).** Postgres `ReceiptReader` replaces
the inherent `applied`/`applied_bound` access paths. `PostgresEngine` unbound
replay reads the record; bound replay, before validation and again under the
writer fence, uses shared `receipts::replay_bound` with the original wire
arguments. Asset mutation-existence reads also use the trait. Legacy NULL
bindings retain SQLite's unbound policy; attach conditionally relaxes the
old Postgres binding-column NOT NULL constraints after validating the table.
Receipt state inspection now uses one Rust JSON decoder on both stores,
avoiding dialect differences for duplicate object keys and non-string
states. Malformed outcomes return a store error; a sequence outside the
acknowledgement cut is not decoded. Point lookups need no list ordering.
Shared cases cover bound/legacy/partial bindings, absent and NUL-key reads,
signed sequence cuts and state decoding; Postgres also covers recorded
receipt replay, snapshots, held-reader reopen, additive cached reads and
shape refusals. `sent_sequence` has no Postgres host caller until S10.

**P1-MR foundation metadata (2026-10-21).** `MetadataReader` and
`MetadataWriter` now run on Postgres transaction snapshots and a store handle
that opens the appropriate read snapshot or serialized writer. Shared key
mapping retains raw textual values and caller-owned malformed-value policy.
New metadata text and new keys refuse NUL at admission; legacy SQLite keys
remain readable and updateable, with no stored-value revalidation. Postgres
NUL-key reads return absent without querying. Attach validates `_meta` using
structured catalogs, including persistence, rewrite rules, primary/unique
shape, constraints (ignoring NOT NULL catalog rows), collations and defaults.
Request/outbox release reads, replay suppression/deployment predicates and
the outbox replay flag write use the typed methods as pure refactors.
Specialized schedule metadata, identity composite SQL and suppressed-counter
SQL retain their family-owned semantics. No host wiring is added. Shared
contracts cover missing/malformed/raw values, admission, rollback and an
observably contended writer; Postgres also covers repeatable snapshots,
reopen with a held reader, additive cached reads and incompatible shapes.
**P1-RL fix round 1 (2026-10-21).** Opening rebuilds legacy live-sum
candidates and missing/stale cap occupancy before publishing their completion

ACT-RC (2026-10-21): activation rechecks core and release ledger relations under

**P1-RL conformance (2026-10-21).** The shared cases run on SQLite and
Postgres: first generation, selected/exact-backend refusal, all opening
markers and clock/epoch facts, history pages and rollback, connection restart,
a program-only successor and executed-program reopen, equal-content revision,
rollback generation and two observably blocked activation races (changed and
unchanged generation). Generation, catalog and event identities share checked
exhaustion policy: they refuse rather than saturate onto an existing key.
Ordinary SQLite ordinals/event ids are unchanged; its catalog overflow/panic
and rowid random fallback at the signed limit are replaced by the refusal.
Release finalization and event recording now cross the neutral history
contract too. Postgres timeline counts decode streamed text JSON in Rust so
escaped NUL remains readable; metadata patterns fold ASCII explicitly to
match SQLite on locale databases. Structured attach checks preserve the
catalog's unique ordinal constraint. Default and `en_US.utf8` private-cluster
scripts pass; all owned clusters have confirmed shutdown. The complete
core/required checks, final affected cases, two inherited Clippy errors and
per-rule/dialect audit are recorded in
[the P1-RL report](../snapback4/reports/20261021-p1-rl-release-activation.md).
The standalone experiment's obsolete lock edge/private connection calls are

no raw access is reopened. Public serving and full evolution remain outside
this qualification.

**P1-RL release family (2026-10-21).** A neutral release-history contract
now owns event recording, pagination, previous-active selection and snapshot
status; SQLite's existing opening/tooling functions delegate to it. Both
adapters retain revision increments on equal-content activation, signed
identity exhaustion refusals, atomic selected-release/history writes and
explicit ordered, bounded pages. New operation/digest names refuse NUL in
shared admission; JSON summaries remain lossless. The evaluator exposes
`create_release`, `activate_release`, `open_selected` and `release_status`.
Program-only activations persist a second generation; schema-changing release
activation refuses pending the evolution family. First create records its
release in the same transaction as generation adoption. S10d must still bind
these facts to local immutable source and matching host metadata, wire the

### 3.4 One engine over both stores

**S10 design revision 2, 2026-10-21; proposed implementation, lead-owned slices.** The
lead chooses an **enum**, not `Engine<S>`. `Engine` continues to be a concrete
type, owning `AnyStore`; its transaction arguments become `AnyTx`. The HTTP
host keeps `FairMutex<Engine>` until the committer queue replaces that lock
under the child RFC. It chooses storage through configuration, never by
instantiating a second engine type. Monomorphizing the whole engine and
spreading type parameters across the host buys no useful benefit for this
I/O boundary. This is the chosen design rationale, not a new performance
measurement.

The snapshot and migration inventory is
[the S10 census](../snapback4/reports/20261021-s10-engine-census.md). At the
rebased source snapshot, production engine/host code contains **123 concrete
SQLite `Store`/`Tx` tokens in 37 files**; identity helpers and the public
SQLite re-export add **36 in four files** (159 total). K0c's explicit member
forwarding adds 30 tokens while removing four raw reset-callback tokens and
one committer token. The brief's approximate 257/48 is not reproducible under
that scope. There are **13 existing family traits with explicit Postgres
implementations and 12 without**. P1-AS now implements the asset ledger and
placement reader; P1-OB outbox access is present. These are adapter counts,
not claims that the Postgres host serves those features.

#### Handles and ownership

The intended shape, with names local to the port (not a new public backend
API), is:

```rust
// Shape only; the Postgres arm is feature-gated.
// Each wrapper has fields private to the port and no backend dereference.
struct SqliteStore(sqlite::Store);
struct PostgresStore(RefCell<postgres::Store>);
struct SqliteTx<'store>(sqlite::Tx<'store>);
struct PostgresTx<'store>(postgres::Tx<'store>);
enum AnyStore {
    Sqlite(SqliteStore),
    Postgres(PostgresStore),
}
enum AnyTx<'store> {
    Sqlite(SqliteTx<'store>),
    Postgres(PostgresTx<'store>),
}
struct ReadSnapshot<'store> { tx: AnyTx<'store> }
struct MemberTx<'member, 'store> { tx: &'member AnyTx<'store>, /* state */ }
enum AnyPreparation<'store> { /* each adapter's pre-activation handle */ }
enum AnyInspection { /* SQLite inspection, Postgres inspect-role session */ }
```

`AnyStore::transaction(&mut self)` takes the Postgres cell through `get_mut`;
`AnyTx` directly borrows the driver store. It never owns a `RefMut` alongside
a transaction borrowing that guard. Existing `IdentityStore` and
`OutboxStore` operations taking `&self` instead borrow the Postgres cell
only within that composite operation, reusing their scoped
`RefCell<&mut Store>` implementations. No transaction escapes that scope.
The six current `authority_transaction` callers become
`with_authority_snapshot` callbacks returning owned facts; this avoids
returning a driver transaction through a temporary mutable guard. Store
read conveniences with shared receivers use the same scoped view rather
than duplicating SQL or changing SQLite's original transaction boundaries.
Conflicting internal borrows become a typed store error, never a `RefCell`
panic.

`ReadSnapshot` uses the same transaction enum and forwards the read
capabilities, including `Rows` and `PartitionRows`; it is not a separate
catalog or cached answer. Preserve SQLite's existing DEFERRED transaction
and authority-snapshot behavior in the neutral slices. Postgres uses its
REPEATABLE READ read-only transaction, pinning generation and head together.
Detached `Engine::reader()` opens an independent same-backend store from a
connection factory that retains the validated store identity, generation
and role; it never switches to SQLite or a replica. The factory retains
connection configuration, not an outstanding transaction. The existing
memory-store fallback remains SQLite-specific through a capability query.

The committer alone owns the physical `AnyTx`. K0c's restricted `MemberTx`
continues to borrow it, with `complete(value)` releasing only `member`,
`rollback(value)`/`abort(value)` rolling back only that savepoint, opaque
Complete/Abort disposition, frame validation and rollback-on-drop. It exposes
neither an owning transaction nor `Deref`, raw connections or physical
transaction control. Its explicit `Rows` and typed forwarding surface moves
to `AnyTx`; rollback failures still propagate their original cause. Nested
`program`, `job_chunk`,
`timeline_chunk` and `seed_sequences` savepoints keep their semantics.
Replace the direct `tx.changes` reset with a semantic
`begin_member_evidence` operation. `CommitTransaction` consumes `AnyTx` only
in the committer/solo path. Activation's pre-upgrade checks and Following
launch stay one solo administrative transaction; `AnyPreparation` forwards
`ActivationPreparation` and `ReleaseTransaction` without exposing SQLite's
`ReleaseCheck`. Owned opening metadata and adoption reports move to the
neutral port, rather than retaining adapter types in engine signatures.

Post-commit continuations still run only after the physical commit succeeds,
in member order, and continuation failures remain distinguishable from
failed commits. The enum does not introduce a retry loop or move the queue
into `serve`; K0's command/queue/serial-batch slices retain their ownership.
The census also records direct producers still outside the member facade.
Converting their handle type is not evidence that they have joined the
committer. K0 keeps the remaining producer routing, queue, continuations and
serial batch. Only producers exercised by S10d's admitted profile must join
the committer before that serving milestone; excluded producers remain K0
work. For example, `fire_schedule_range` stays off the profile while schedules
are refused. S10c does not depend on completing the whole opener census.

#### S10d-2 implementation note — 2026-10-22

The common Postgres store now installs a shape-checked singleton
`_owner(singleton, store_id, holder, token, lease_until)` in its successful
attach/activation transaction. The logical id must match `_meta.store_id`.
Fresh creation installs and fences the row before the core/head writes. A
legacy attach serializes absent-relation DDL with a bootstrap-only transaction
advisory lock, then installs and fences the row before the head. A refused
opening rolls the installation back; an acquired positive token can never
bootstrap over a missing owner record. Subsequent common-engine durable
transactions acquire `FOR KEY SHARE` and compare the
process token and logical id before `_head FOR UPDATE`, generation checks,
or family writes. A stale token refuses with `E_STORE_OWNERSHIP` and writes
no receipt. Token zero is the internal bootstrap lane, never
public serving authorization; after acquisition a plain token-zero reopen
refuses. The retained `PostgresEngine` evaluator requires a separate
namespace: opening a namespace with `_owner`, including token zero, returns
`E_STORE_OWNERSHIP`. Its connection retains a shared session advisory lock
on the namespace bootstrap key. Legacy owner installation takes the exclusive
transaction counterpart before DDL, so it cannot adopt underneath an
already-open evaluator or its in-flight writes. This guard adds no per-write
evaluator calls and preserves its serialized/serializable oracle modes.

`store_port::{StoreLease, LeasePolicy, LeaseAcquisition}` owns dedicated lease
traffic outside the committer. The caller connects with an expected logical
id, acquires, then uses `AnyStore::open_postgres_owned` with that lease.
Renewal and release match store id, token and holder and use the database clock. Takeover
uses W11's conditional no-op expired-lease UPDATE under its own lock timeout,
then `FOR UPDATE` retries under a savepoint that preserves the claim. A
bounded watcher terminates only actual same-role, same-database blockers
whose exact store tag carries a token no newer than the claimed token.
Each complete observed blocker set is classified before any signal;
an unowned/newer blocker aborts that takeover without signalling any member
of the mixed set (§5.2), rather than skipping it as the early prototype did.
`claim_timeout` and `fence_timeout` are at most four seconds, leaving a
one-second margin below the lease session's five-second statement timeout.
A `57014` during the conditional claim abandons before any watcher exists.
After a successful claim, `statement_timeout` is disabled before the watcher
starts: bounded fence waits use `lock_timeout` and the finite attempt count,
so the adapter's statement timer cannot cancel a claim after signalling.
The hygiene sweep runs after COMMIT
and retains the same token bound, so a losing or delayed standby cannot
terminate a winner's sessions. Serving connections and readers carry
`sb:<32-hex-store-id>:<4-hex-holder>:<decimal-token>` (at most 60 bytes, even at
BIGINT max); oversized or malformed tag components refuse.

Fix round 1 replaces start barriers with observed blocking. The winning
standby pauses while holding its actual conditional-UPDATE lock; the loser
must appear in `pg_blocking_pids` before release. A hook inside `acquire`
renews after the expiry poll and before the conditional UPDATE, which must
return zero rows without starting a watcher. A gated watcher forces a real
`55P03`, followed by savepoint rollback; the old renewal is observed blocked
on the claimant both before and after that rollback. This fence wait also
outlives an injected 20 ms session statement timeout. The legacy opener
pauses after taking its advisory lock, and the second opener must be observed
waiting on it. A shared-advisory wait exposes a mixed blocker set while
both sessions retain owner key-shares; termination refuses while preserving
both sessions and the tagged transaction's staged write. (Postgres may expose
row multixact holders one at a time.) Evaluator refusal and a serializable
evaluator blocking legacy adoption have separate witnesses.

Physical COMMIT disables `statement_timeout`, including on lease traffic.
The adapter exposes `RuntimeError::CommitOutcomeUnknown`
(`E_COMMIT_OUTCOME_UNKNOWN`) for lost/uncertain COMMIT acknowledgements and
cancelled synchronous-replication waits. It is a store failure with automatic
retry disabled, not an execution refusal or an acknowledged success.
Explicit serialization/deadlock/constraint aborts retain their driver error.
The common engine propagates the unknown outcome without fabricating a
receipt or running a success continuation. Per-path key resolution/retry
policy remains P1a's responsibility.

`AnyStore::worker_ledger_path` preserves SQLite's adjacent completion file
and derives the Postgres completion filename from the logical store id in an
explicit absolute durable state directory. Missing identity refuses with
`E_WORKER_STORE_ID`; missing Postgres state location uses `E_WORKER_STATE`.
The existing supervisor calls this seam; configuring its Postgres location
and admission belongs to S10d-3. No URL or dummy SQLite database path is used.

Real-cluster witnesses and check results are recorded in
[the S10d-2 report](../snapback4/reports/20261022-s10d2-postgres-ownership.md).
This is a store-level slice: public StoreConfig, release/bootstrap/listener
integration, lease cadence and loss-driven admission shutdown, startup runner
policy, and worker-state configuration remain S10d-3. Declared HA modes,
provider failover qualification, database-identity/tripwire continuity and
full worker recovery remain the broader §5/P1b work; this slice claims none
of them.

#### Family dispatch and the remaining semantic boundary

Use ordinary Rust supertrait composites, with explicit implementations on
the appropriate enums. Do not construct `dyn StoreFamilies`: existing
callback methods are intentionally generic and need not be object-safe.
Each family method matches once and delegates to the corresponding adapter;
policy remains in the shared Rust above it.

- **`TransactionFamilies` on `AnyTx`:** `Rows`, `PartitionRows`,
  `AuthorityTransaction`, `IdentityTransaction`, `RequestsTransaction`,
  `JobTransaction`, `OutboxTransaction`, `ReceiptReader`, `AssetTransaction`
  (including `AssetIntentReader`), `MetadataReader`, `MetadataWriter`,
  `ActivationTransaction` (including `ActivationReader`), `ChangeEvidence`,
  and the new ledger, placement-read, time-publication, Following-history,
  release-history and evolution operations identified in the census.
- **`StoreFamilies` on `AnyStore`:** `IdentityStore`, `RequestsStore`,
  `JobStore`, `OutboxStore`, `AssetIntentReader`, `MetadataReader`,
  `MetadataWriter`, `TimelineWorkReader`, `DevResetStore`, `ReceiptReader`,
  `ChangeEvidence`, plus semantic opening, reader creation, inspection,
  release tooling and fixture operations. Preserve each method's receiver
  and original SQLite atomicity; a composite is not permission to open
  another writer inside an existing transaction.
- **Scoped facades:** `AnyPreparation` implements
  `ActivationPreparation: ReleaseTransaction`; action/effect owner views
  over `AnyTx` implement `StepTransaction`; `AnyInspection` implements
  `InspectionCatalog` and the typed inspection query interface. They stay
  distinct because their authority and lifetimes differ.

`Rows`/`PartitionRows` already have both adapters. The enum must forward
**every override**, including prefetch and its enabled flag, metered scans,
sequence migration, change footprints, restored-authority reads, asset
operations and audience epochs. Inheriting a default on the enum would
silently erase an adapter's implementation. Shared default algorithms can
remain shared only for admitted semantics; a successful trait default is
not evidence that a Postgres family exists. `next_seq` and partition
append already belong to `PartitionRows`; no third sequence allocator is
introduced. `record_commit` belongs on a new `LedgerTransaction`, receipt
writes extend the receipt family, and change-recorder mutation is an
explicit member-evidence capability, not a public `RefCell` field. Raw
`meta`/`set_meta` calls become existing typed metadata/job-family operations;
no unrestricted string-key metadata trait is added.

`LedgerTransaction::record_commit` preserves SQLite's durable evidence and
prune-to-1,000 policy; Postgres uses its buffered tail and supplies that evidence
only when the change-evidence family is admitted. `commits_after` joins its
read side. Savepoint operations belong on transaction control, not on `Rows`.
S10c must repair the evaluator's tail before reusing it:

- `execute` never implicitly calls `flush_tail`. Shared effect admission
  batches all records into the tail; `insert_effect` must not flush it or
  turn one tail flight into one network trip per effect.
- Each member owns at most one pending commit slot. A second `record_commit`
  refuses an occupied slot; it cannot overwrite unflushed records. Receipt-only
  and failed-program receipt paths retain their semantics, and flushing a tail
  without a commit must not silently discard effects.
- Finish the tail **inside `SAVEPOINT member`, before `RELEASE member`**.
  The same successful step advances or clears `next_seq`'s cached `head`,
  so the next member observes the new head and receipts and allocates its
  successor. Tail/receipt completion preserves the shared receipt protocol's
  insert-then-bind order; any staged receipt operations finish before release.
  A flush failure must still be able to roll back the member.
- Rollback restores member-local tail/head/evidence state and invalidates
  speculative `rows_cache` answers (a separate cache). It never discards an
  earlier member's completed tail or leaves the aborted member's effects queued.
  Nested savepoints snapshot the same bookkeeping. A terminal Postgres bind
  refusal remains terminal across savepoint recovery (§9.1).

Port K0b's two-member facade property to real Postgres in S10c: member two
sees member one's head, receipt and metadata, allocates the next sequence,
then rolls back or fails; member one alone survives the physical COMMIT.
Include a tail-flush failure before release, an occupied-slot refusal and
multiple-effect call counts. Production remains single-member under K0c.
This interim performs one CTE tail flight per completed member and one
physical COMMIT per transaction. §6.3's eventual single tail flight per
serial batch requires separate ordering/visibility evidence before K0 enables
multi-member production; it is not permission to flush after member release.

#### Explicit temporary refusals

Until a family is implemented and admitted, its Postgres dispatch arm returns
`E_STORE_UNSUPPORTED: <family> is not yet available on Postgres`, with a
stable semantic family name (for example `release-activation` or
`time-publication`). It is a structural refusal preserved through the HTTP
and CLI envelopes, not a generic SQL error, retryable contention, an empty
result or a no-op. Unsupported writes abort their member, publish no
sequence and run no continuation. Capability admission happens before
activation or admission writes; runtime dispatch also refuses defensively.
A refused composite must not leave earlier partial bookkeeping durable.
The engine handles this capability error before ordinary program-refusal
receipt handling: abort the member and return the named refusal without
consuming the operation id or recording a failed-program receipt. This
distinction needs an enum-dispatch regression case.

Re-home `PostgresEngine::supported()`'s semantic exclusions as named admission
refusals on the unified engine's Postgres profile: union sync; `not before`
and timed publication; asset columns/asset-typed arguments beyond the placement
lookup; jobs, actions, routes, schedules and native programs; row-keyed views
needing a recount runner and the maintained/private-column shapes its
`refuse_maintained_columns` rejects. Adapters for jobs, outbox or assets do
not alone admit those features. Keep normal shared schema validation. Drop
only the evaluator's ephemeral-table exclusion: process-local ephemeral hubs
remain allowed and never supply durable authority.

The Postgres arm must explicitly refuse unadmitted family methods rather than
inherit successful defaults: `audience_epoch = 0`, `audience_epoch_time = None`,
`time_audience_published = true`, no-op `track_time_audience`/`release_asset`
and `holds_assets = false` cannot stand in for support. Make such boundaries
fallible where necessary; schema admission and defensive runtime refusal
cover them even when the underlying trait has a Postgres implementation.

Some existing interfaces return `Option`, `bool`, `Vec` or `()` rather than
`Result` (`ChangeEvidence`, `Rows` evidence hints and some inspection
helpers). They cannot report this refusal by delegation. Give unsupported
family operations a fallible port boundary: for example, change
`ChangeEvidence` access to return `Result<Option<()>, RuntimeError>` and
operator list APIs to return `Result<Vec<_>, RuntimeError>`. Existing
evidence policy is **unknown certifies nothing**: it may explicitly turn an
unavailable-evidence refusal into unknown/no certification; the adapter must
still identify the missing family. Infallible `Rows` evidence hints may remain conservatively unknown;
feature admission must reject unsupported use at a fallible boundary. Do
not turn a missing family into false authority or a certified empty answer.
P1-MR fix round 1 changes `preserved_between`'s missing-footprint-to-empty-vector
mapping (`revocation.rs`) to explicit unknown; S10b must retain that policy
through enum dispatch. `/changes` must never certify revocation from absent
evidence. P1-CE (§3.3) now admits certified `/changes` and sync for the
existing Postgres schema profile through enum dispatch: the actual relation,
per-commit buffered recording, last-1,000-sequences pruning and coherent
head/evidence snapshots are implemented and witnessed. Missing, pruned or
incomplete evidence still maps to explicit unknown (`null` on these wire
surfaces), never a certified `preserved: []`. This removes only the evidence
exclusion; all named schema and runner refusals above remain in force.

Mandatory opening, identity, head, receipt and transaction
control operations cannot be stubbed if they are needed by the chosen HTTP
smoke profile: finish those adapters before enabling that profile. Optional
background runners start only when their required families are present;
a schema requesting such a family refuses before listener readiness.

In particular, `Engine::mutate` reaches `assets::require_placement` through
K0c's member facade for every operation id, even on a schema without assets.
Stubbing the whole asset contract would refuse ordinary mutations. Extract
that helper's `placement_record` dependency into a narrow `AssetPlacementReader`
as mandatory admission groundwork, with cancellation/id-binding parity.
The rebased P1-AS adapter already creates `_asset_intents` with `placement`,
`facts` and `state` (`engine/postgres/assets_schema.rs`) and implements the
real `placement_record` lookup (`engine/postgres/assets.rs`). S10c reuses that
initialized relation and reader; it does not create a parallel ledger. It may
prove no record exists from the store's actual initialized state; it may not invent
`None` on unsupported dispatch. The rest of the upload/asset family can
remain refused. Similarly, activation currently reads the time clock even
for untimed schemas: supply that metadata fact, and start the timed-wakeup
runner only when timed publication is supported. Neither workaround may
skip policy just because the current schema declares no asset or timed field.

This is an explicitly named transitional subset, consistent with §9's ban
on a **silent** subset. It is not complete P1 parity or a publication claim.
As each P1a family lands, replace its refusal and run the same family cases
through `AnyStore`, without adding a new host branch.
Family-contract tests admit each implemented family explicitly; they do not
expand the narrower S10d HTTP profile.

#### Initial HTTP profile and public release bootstrap

The adopted first Postgres HTTP profile admits ordinary queries, identified
data mutations with receipt replay/id binding, bearer session resolve/logout,
and process-local ephemeral hubs. It requires the opening subset actually
called by `open_selected_at`/`activate`, identity, every applicable `Rows` and
`PartitionRows` override, metadata including the time clock, receipts in
SQLite's insert-then-bind order, the member-safe ledger/tail, savepoints, and
the existing placement relation/reader. The named startup refusals above
exclude assets beyond placement, jobs, actions, routes, schedules, native,
union sync, timed publication and the rejected maintained shapes. SQL
inspection and release operations beyond the minimum below remain named
operator refusals. Certified changes/sync retain the explicit evidence
exclusion above. Worker execution/claims are not admitted merely because
job, request or outbox adapters exist.

`serve_start` must gate child-session/replay work on its admitted identity/
outbox families, and gate `fire_schedules`, native installation and
`advance_time_audiences_at` on their respective admitted runners. It cannot
invoke an unsupported runner on an otherwise admitted schema. This does not
remove activation's unconditional time-clock fact. Only admitted-profile
durable producers must have K0 routing before S10d; S10c's internal HTTP-host
witness neither qualifies public `serve` nor claims a production lease.

**Named S10d prerequisite: P1a release + activation.** Implement
`ReleaseTransaction`, `ActivationReader`/`ActivationTransaction`/
`ActivationPreparation` and the opening subset `open_selected_at`/`activate`
actually call, including selected-release/backend checks, schema markers,
the time-audience clock fact and required audience-epoch writes. S10c owns
the opening/activation foundation it needs; S10d also requires the minimum
deploy/history/selection path through those adapters. An evaluator attach
is not a substitute. Branches needing other unadmitted evolution families
refuse before activation writes. The first public deployment works as follows:

1. Existing release tooling resolves `StoreConfig` and prepares the immutable
   local `releases/N/` source tree plus the matching compiled host metadata.
   Deployment configuration holds credentials; the release binding records
   the expected logical store identity and non-secret configuration.
2. A fenced solo activation transaction in Postgres installs the first
   persisted generation and its schema/programs/catalog/markers, records
   release history and activation, and selects release N atomically. The
   selected release/generation and store identity live in Postgres; local
   `current` and `releases.jsonl` remain convenience copies. A failed activation
   publishes no selection; an ambiguous COMMIT is resolved from persisted
   activation/history before source cleanup or any retry.
3. Public `serve` reopens the deployment, reads the selected release from
   Postgres and loads that release's local immutable source directory. It
   attaches to the persisted activation with the expected release and
   logical store identity, then checks compiled host schema/program metadata
   against that backend (`verbs/releases.rs::serve_release`,
   `project.rs::open_release_engine`). Edited/missing source, a mismatched
   binding or a racing selection cannot activate caller source during startup;
   refuse or reopen against the persisted selection.

Immediately before enabling the listener in S10d, take the thin §5 host
slice: owner token and fenced/tagged transactions with lease policy,
uncancellable/ambiguous-COMMIT handling and an explicitly configured worker
completion ledger bound to the logical store id. Unadmitted work uses §4.3's
drain-and-park policy; it does not waive that binding. SQLite file locks
cannot authorize Postgres serving.
Full P1b HA/blob/artifact and optional-tooling claims keep their own evidence.

An empty `preserved` answer reads as revocation on the client (`change-evidence.ts`), so its window moves with the log |
| Action steps | `_action_steps` (the exactly-once ledger for external action steps) | None | In the work family beside `_effect_steps` |

| Narrowed dormant rows | `_dormant_narrow_rows` | None | In the evolution family |
| Release artifacts | Not in the store. The immutable release tree (source, generated runtime, `native.wasm`, provenance, digested by `release_files::digest`), the `current` pointer, `releases.jsonl`, and the activation control socket keyed by the store file's path and inode | None | A release-artifact family: trees content-addressed by that digest in `BlobStore`, the store's activation record naming the digest, hosts materializing a tree before serving it, `current` demoted to a local cache hint (§4.2) |

The SQLite table names in this table are SQLite's own. A Postgres adapter may use different tables. It
must answer the same operations, and graduation (sibling B) maps between them
through the family's logical export format, not through table copies.

### 4.2 Host coordination (one process today)

| Item | Today | P1 (one server, warm standby) | P2 (several serving processes) |
| --- | --- | --- | --- |
| Ownership | Sidecar file lock | Store-held lease and fencing token (§5) | Same lease, held by the committer |
| Commit wakeup (`committed`, `seq`) | Condvar | Unchanged in-process | `Notifier`: `LISTEN`/`NOTIFY` carrying the new head, with a bounded poll of `_commits` as the floor. A missed notification delays an answer; it never loses one |
| Change answers and long waits | Process maps; a held wait costs a thread | Unchanged. A held wait must not hold a database connection | Per process; each process wakes from `Notifier` |
| Presence (`connected[p]`) | `Live` over held polls | Unchanged | Pinned to the committer or a shared table with leases; chosen at P2 from LLP 3000.009 §7.1's measurement |
| Ephemeral tables | One-process `Hub` (LLP 3000.017) | Unchanged; a standby starts empty, as after a restart | `EphemeralBus`, or pin ephemeral traffic to one process; LLP 3000.017's exclusions hold until P2 rules |
| Asset transfer serialization | `AssetTransfers` per process | Unchanged | A row lock on the grant inside the consuming transaction |
| Asset bytes | Local files | `BlobStore`: S3-compatible, content-addressed by the SHA-256 the ledger already records, written before the claiming commit; local directory stays the SQLite default | Same |
| Schedules and sweeps | The serving process | The lease holder only | The committer only |
| Following reader (`Shared.following`) | A process-local reader over Following history | Unchanged | Per process; it reads the store and wakes from `Notifier` like change polls |

The control transport is keyed by `store_id` and owner token, not by a file | Same; a rolling deploy materializes the new tree on each host before the selection commits |

A `BlobStore` write happens before the commit that claims it, and outside
any serial section: the commit claims bytes by digest. Two rules make the
blob store recoverable together with the database:

- **Retention matches the recovery horizon.** No bytes are hard-deleted
  while any state the operator can still return to references them. That
  covers the provider's PITR window and graduation's revert window (sibling
  B §7). `_asset_gc` marks bytes deletable with a not-before time at least
  that horizon away, or the operator configures a versioned bucket whose
  lifecycle covers it. `doctor` and preflight check that alignment: a
  widened PITR or revert window with an unchanged blob lifecycle silently
  breaks the rule.
  - Otherwise a PITR to before an asset's deletion revives a ledger row
    whose bytes were already collected. No refusal can recreate them.
  - A restore or cutover still refuses while any referenced digest is
    missing, but that is the fail-closed backstop, not the recovery plan.
- **Release artifacts are keyed by an exact artifact digest.** That digest
  covers every file, `provenance.json` included. `release_files::digest`
  deliberately excludes provenance and `.pending-adoption`, because it names
  the executable identity. So the store records both digests: the execution
  digest for compatibility and the artifact digest for the blob key. Two
  trees with different provenance then never share a blob.

### 4.3 Worker completions and execution ownership

Today a worker opens `BEGIN IMMEDIATE` on its local SQLite ledger, looks up
the delivery key, runs the handler, stores the result and commits, and only
then settles with the server (`worker-ledger.ts`; LLP 3000.009 §5.2). The
ledger therefore gives two guarantees:

- **completion suppression:** a redelivery replays the stored result;
- **execution exclusion:** while one worker sharing the ledger is running a
  handler, another cannot start it.

Both live on one host's disk. Moving only the stored result into the store
would break the second guarantee. Lease expiry returns the effect to
`queued` and clears its claim (`effects.rs`, `expire_run`). So a healthy
handler that outlives its lease would be re-invoked by a successor that
finds no result, and the original's result could no longer be recorded
under its lease.

The slice that moves this state into the store (P1b) must define both
halves:

- **Completion records.** A completion is keyed by the stable delivery key.
  It may be recorded by the attempt that produced it even after that
  attempt's lease has expired. Recording a result someone already produced
  is separate from authorization to settle the current claim. Claim and
  redelivery read the completion before invoking a handler.
- **Attempt records.** Starting a handler records the attempt, with its
  delivery key and lease, in a fenced store transaction. A successor that
  finds an attempt started, not completed, and expired has an *uncertain
  attempt*. Like A2's uncertain steps, it must do one of three things: wait
  out a grace period, reconcile through the provider's idempotency key or
  status query, or park the effect. It never silently re-invokes. Database
  fencing cannot stop an external call already in flight, so the protocol
  makes such a call visible instead of pretending it cannot happen.

Until that slice lands, placement is constrained, and a cross-host move
requires **quiescence**. Waiting for a lease to expire does not establish
quiescence. `expire_run` returns an effect to `queued` while its handler
may still be executing, and the local ledger writes its completion only
after the handler returns (round 3, Astra N3, Grok N3).

- Workers run on the serving host, under `serve`'s supervision.
- **Graduation** first drains workers: the supervisor stops them from
  claiming, then waits for every worker process to exit, so every in-flight
  handler has returned and its completion is in the ledger. The ledger's
  completions are then imported with the store. A worker that cannot be
  confirmed exited refuses the cutover.
- **Standby promotion** cannot drain a host that is stopped or partitioned.
  So promotion parks every non-terminal effect with `attempts > 0` (`expire_run`
  clears `claimed_by` but not `attempts`) and no imported completion, as an uncertain attempt. Such an effect
  is reconciled through the provider or by an operator, and is never
  silently re-queued.
- `doctor` names the ledger file as state that must travel with the store.

## 5. Ownership and fencing

One physical store serves a logical store at a time (parent §3.1). Postgres
can be reached from many hosts, so ownership belongs to the store. This
section has been through two review rounds and a real-Postgres prototype,
[`experiments/postgres-fencing`](../snapback4/experiments/postgres-fencing/README.md)
("the prototype", PostgreSQL 16.15, non-superuser roles). Its witness
numbers are cited as W1–W10. The design separates three jobs:

- **fencing** decides whether a write may commit, and never trusts a clock;
- **takeover** decides when a successor may begin, on the database's clock;
- **continuity** decides whether a database failover keeps the incarnation.

### 5.1 The owner record and the fence

`_owner(singleton, holder, token BIGINT, lease_until TIMESTAMPTZ, ...)`.

- **The fence is the first lock of every writing transaction:**
  `SELECT token FROM _owner FOR KEY SHARE`. The transaction refuses if the
  token differs from its process's token.
  - This covers writes that publish no sequence: refusal receipts,
    receipt-only reports, mints and invalidations, claims, renewals, steps,
    sweeps, asset views, and time-audience pins.
  - The fence comes before `_head … FOR UPDATE`. The adapter's current
    head-first order deadlocks with takeover (W10), so it changes.
- **The token changes only through an explicit `SELECT … FROM _owner FOR
  UPDATE` followed by an update.** `FOR KEY SHARE` conflicts with that
  lock, so takeover waits for every in-flight fenced transaction.
  - Postgres does not queue a new key-share request behind a waiting
    `FOR UPDATE`, so new fences can still be granted while takeover waits.
  - That does not affect safety. Any fence granted before the token
    changes is ordered before the takeover. Afterwards, under READ
    COMMITTED a waiting or new fence reads the new token and refuses; under
    REPEATABLE READ or SERIALIZABLE it raises `40001`, which a retry loop
    must surface as a refusal (W4).
  - Takeover's progress therefore rests on terminating blockers (§5.2), not
    on queueing.
  - **Renewal does not queue behind a waiting `FOR UPDATE` either** (W8;
    round 4, Grok N2). It is a non-key update and takes `FOR NO KEY UPDATE`,
    which neither a key-share holder nor a waiter blocks. Takeover therefore
    first claims the expired lease with an update that renewal does conflict
    with (§5.2 step 2).
- **Renewal is `UPDATE _owner SET lease_until = … WHERE store_id = $store
  AND token = $mine AND holder = $holder`,** an update of a non-key column,
  identifying the complete claim. Release uses the same predicates. A known
  rolled-back claim is never eligible for cleanup. An unknown claim COMMIT
  retains cleanup identity without write authority until conditional release or
  expiry. Token alone is insufficient: a successor may reuse the token of a
  rolled-back claim. A renewal that waited on takeover must not rewrite that
  successor's lease and report success to the old owner.
  - Under `FOR KEY SHARE`, renewal never waits on fenced transactions
    (0 ms, W8).
  - The first draft's `FOR SHARE` made every renewal queue behind the
    longest in-flight transaction. In W8 a single 7-second transaction let
    the lease lapse, and the standby took over a live owner. A long
    migration, backfill or serial batch would do the same.
- **Times come from `clock_timestamp()`,** never from a host clock and never
  from `now()`, which is the transaction's start time.
  - A host clock drives only the cadence of renewals and polls.
  - A slow or skewed host clock costs availability, not safety (W5, at ±1 day
    and at 0.1× monotonic).
  - An owner whose renewal fails until its lease lapses stops writing and
    rejoins as a standby. It never assumes it still owns the store.

### 5.2 Takeover

Every connection a serving process opens is tagged
`application_name = sb:<store>:<holder>:<token>`.

- **Format.** `store` and `holder` are fixed-width hexadecimal ids and
  `token` is decimal, so a tag never exceeds Postgres's 63-byte limit. A
  process whose tag would not fit refuses to start rather than truncate,
  because a truncated tag loses the token that bounds termination.
- **Role.** Every process of a store runs as the store's one role. No
  process needs superuser or `pg_signal_backend` (W1).

A standby takes over in one transaction, in a bounded loop:

1. Poll until `lease_until < clock_timestamp()`. Note the token T.
2. **Claim the expired lease before anything else.** Run `UPDATE _owner
   SET lease_until = lease_until WHERE singleton AND token = T AND
   lease_until < clock_timestamp() RETURNING token`, under its own short
   `lock_timeout`, with a margin below the lease session's statement timeout.
   - It takes `FOR NO KEY UPDATE`. That does not conflict with in-flight
     fences, so it is granted at once. It does conflict with the owner's
     renewal, which also takes `FOR NO KEY UPDATE`.
   - This relies on the fence being `FOR KEY SHARE` (§5.1). Under
     `FOR SHARE`, the claim itself would wait on every in-flight fence.
   - **Zero rows, or a timed-out claim: abandon, having terminated
     nothing.** This includes a `57014` statement cancellation during the
     conditional claim, before a watcher can exist. The owner renewed, or
     another standby is mid-takeover. A second standby's claim blocks behind the first one's whole takeover,
     then matches zero rows (W11f).
   - **One row:** from here on the owner cannot extend its lease. Its
     renewal waits behind this transaction. Once the token changes, the
     renewal matches zero rows, and the owner learns of the loss.
3. Disable the adapter's statement timeout before starting the blocker
   watcher; fence waits remain bounded by `lock_timeout` and a finite attempt
   count. This prevents statement-timeout cancellation after a signal.
   Set a savepoint and issue `SELECT … FROM _owner FOR UPDATE` with a short
   `lock_timeout`. It waits on in-flight fences. The row lock from step 2
   survives a rollback to the savepoint.
4. While it waits, classify the **whole** blocker set from
   `pg_blocking_pids()` before signalling any member. If any blocker is
   unowned, of another role, or tagged with a newer token, abandon that
   takeover before signalling the set. Otherwise terminate every backend in
   the set with the same role, this store's tag, and a tag token of T or less.
   This needs no registration, so it also catches connections opened late or
   while reconnecting: the prototype's unbounded-block case (W3), where
   blocker termination took over in 2.9 s. The implementation chooses
   whole-set refusal for mixed blockers, not the prototype's skip-and-wait
   behavior; per-signal exact identity rechecks remain required.
5. On `55P03`, roll back to the savepoint and go back to step 3. Never wait
   without a bound.
6. Increment the token, record the holder, set the lease, and commit.
7. **After the commit**, terminate every same-role session tagged with this
   store and a token of T or less. This is hygiene: it frees the stale
   fast-path advisory lock and connections. Blocker termination in step 4
   alone suffices for takeover (W3). If the sweep ran inside the loop, it
   would also terminate the owner's waiting renewal. The owner would then
   learn of the loss from a terminated connection (`57P01`) rather than
   zero rows, which is equally safe.

Step 2 precedes every termination and holds a lock that renewal must wait
for. So it either sees the renewal and abandons, or blocks it, and a
standby can never terminate a live owner that has renewed.

**Evidence** ([fencing prototype](../snapback4/experiments/postgres-fencing/README.md),
W11, three runs on PostgreSQL 16.15):

| Witness | Result |
| --- | --- |
| W11a: a renewal between poll and claim | The claim matched zero rows and nothing was terminated |
| W11b: claim first | The renewal blocked for about 1 s, then matched zero rows; no old-token commit landed after the takeover |
| W11c: the old re-read design, run as a control | It killed a live owner that had just renewed. This is the hazard the claim closes |
| W11d: fences while the claim is held | Still granted, in about 0.6 ms |
| W11e: forced `55P03`s | The claim's lock survived rollback to the savepoint |
| W11f: two standbys racing | The loser terminated nothing |
| W2, W3, W8, W10 rerun under the claim | Unchanged |

W8's matrix also showed something the design depends on. A fence granted
during the claim locks the row version the claim already replaced, and it
still blocks takeover's `FOR UPDATE` on the new version.

**Bound.** Takeover lands within lease + poll + one termination round +
the transaction: 3.0–3.3 s for a 3 s lease in the prototype. A clean
shutdown sets `lease_until = '-infinity'` and releases the advisory lock, so
a standby waiting on that lock takes over in milliseconds (W6a). The
advisory lock is that fast path only. Waiting on it as a gate blocks forever
against a stopped owner (W6b, the first draft).

**Backstop.** `idle_in_transaction_session_timeout` on the serving role.
It does not replace termination, because it cannot see a backend blocked
writing to a stopped client (W7). TCP keepalives do not detect a paused
process at all.

**Ambiguous commits.** A COMMIT that races termination can be durable
while its client sees an error. Under synchronous replication that window
is seconds wide (W9). Fencing still orders it before the takeover, and a new
owner treats whatever committed as committed. The claim that every write
path is retry-safe across owners is a P1a deliverable, not an assertion.
P1a produces a per-path table: each write path (mutation, mint, refresh,
invalidation, claim, renewal, step, settle, sweep, asset view,
time-audience pin, activation), its idempotency key, and what a retry
observes in each of three outcomes (rolled back, committed and
acknowledged, committed but unacknowledged). Any path without a key gets
one; a mint is keyed by its existing mint binding. P1b's witness forces a
commit to race termination during a synchronous wait, retries the same
operation under the new owner, and asserts a single visible effect for at
least mint, claim, receipt and step.

**Connections.** Owner and standby connect directly or through a pooler in
session mode, never transaction mode. Under transaction pooling, a backend
pid and its tag belong to whichever client is mid-transaction, so
termination cannot identify the old owner. `doctor` refuses transaction
pooling on every serving connection and verifies same-role termination on
the provider. The prototype found Supabase's documentation ambiguous on the
latter.

### 5.3 Activation

`deploy` and `rollback` run as fenced transactions. The release tree is
uploaded by digest first (§4.2), and selection is a single fenced commit.
Two hosts or directories targeting one store cannot activate at once.

### 5.4 Failover and continuity

**History.**

- Revision 3 made every promotion a new incarnation. The author rejected
  that.
- Revision 4 tried to keep the incarnation through any failover. It used an
  asynchronous chain checkpoint and narrow repair. Round 4 showed it
  unsound (§12):
  - commits acknowledged after the last checkpoint can be lost without
    detection, revocations among them;
  - two primaries can both serve until a checkpoint write lands;
  - a hash cannot reconstruct lost records, attempts or graduation
    decisions.

When the database loses acknowledged writes, no asynchronous mechanism can
recover them. Only a synchronous write somewhere else can. So this section
draws the line at the database's replication guarantee, where Supabase and
raw Postgres applications draw it too.

#### 5.4.1 The HA mode is declared, and decides what a failover means

The release declares the store's HA mode. `doctor` checks what it can.

| Mode | Examples | A failover |
| --- | --- | --- |
| `none` | A single instance | A restart: keeps the incarnation |
| `storage-sync` | RDS Multi-AZ instances, Cloud SQL HA, Aurora, AlloyDB, Neon: replication below Postgres, so a failover restarts Postgres on the same replicated storage | **Keeps the incarnation; clients see a reconnect** |
| `streaming-sync` | Postgres synchronous replication, where the HA manager promotes only a synchronous standby and fences the old primary (Patroni `synchronous_mode_strict`, CloudNativePG, an equivalent provider mode) | **Keeps the incarnation; clients see a reconnect** |
| `async` | Asynchronous streaming replicas, or any configuration that can promote a lagging replica | The operator chooses: `new-incarnation` (the default) or `continue` (§5.4.3) |

**What the lossless modes rely on.** In `storage-sync` and
`streaming-sync`, Snapback relies on the database and its HA manager for
two things:

- that acknowledged commits survive a failover;
- that the old primary is fenced.

That is the same contract every Postgres application relies on. Snapback
adds its own obligations:

- **Uncancellable COMMIT.** The adapter runs COMMIT with
  `statement_timeout = 0`. A COMMIT that returns the
  "canceling wait for synchronous replication" warning is treated as
  unacknowledged and fails closed until the standby's flush position passes
  its LSN.
- **Streaming check.** In `streaming-sync`, each renewal checks
  `pg_stat_replication` for a synchronous standby that is actually
  streaming, where the serving role can see it. If none is, the owner
  stops acknowledging writes and alerts.
- **Live qualification.** P1b qualifies each named provider and HA manager
  with live failover witnesses. One example: a revocation committed just
  before the failover must still hold after it. Documentation alone does
  not qualify a provider.

#### 5.4.2 Detection: a persisted identity and a tripwire

- **Identity.** At every ownership acquisition, the store compares the
  database's system identifier and timeline with a row in the store
  (`_owner.db_identity`), so a freshly started process detects a promotion
  too.
  - On vanilla Postgres 16, `pg_control_system()` and
    `pg_control_checkpoint()` are executable by PUBLIC.
    `pg_walfile_name(pg_current_wal_lsn())` exposes the timeline as a
    fallback.
  - Preflight requires both values to be readable.
  - A timeline change is expected in `streaming-sync`. It decides the
    outcome only in `async`.
- **Tripwire.** Every durable write extends a hash chain over the
  committer's stream (§6.3). The owner writes `(store_id, revision, hash)`
  to the blob store asynchronously. At acquisition, a database that lacks
  the last checkpointed revision, or has a different hash at it, has lost
  acknowledged history. In a lossless mode that means the declared contract
  was violated. The store then applies the `async` rule configured for it,
  `new-incarnation` unless set otherwise, and raises an alert.
  - **It detects gross violations; it does not prove continuity.** Losses
    newer than the last checkpoint are invisible to it.
  - It never blocks serving: a stalled checkpoint only weakens the
    tripwire.
- **Graduation pins the mode.** A graduation target must be in `none`,
  `storage-sync` or `streaming-sync`. A timeline change on the target
  during graduation or its revert window halts graduation with the source
  fenced until the operator resolves it. An acknowledged decision lost to a
  lagging promotion therefore cannot make both stores writable (sibling B
  §5).

#### 5.4.3 Asynchronous mode: the operator chooses

On a detected promotion in `async` mode, the operator chooses one of two
behaviors:

- **`new-incarnation`** (the default) is correct. Recovery mints a new
  incarnation, fences old device resumes and sessions, quarantines
  uncertain work, and reconciles blob and ledger state, as a restore does
  (LLP 3000.009 §9).
- **`continue`** has the semantics a Supabase or raw Postgres application
  gets. The store keeps its identity and serves. Acknowledged writes and
  revocations in the lost window may be gone. Every non-terminal effect
  with `attempts > 0`, or admitted within the configured window before the
  promotion, is parked as uncertain, because a rollback may have erased its
  attempt record. The loss report names what the tripwire saw. `doctor`
  states these consequences when the mode is chosen.

#### 5.4.4 Considered and not taken in P1

- **A synchronous external anchor.** Every acknowledged batch waits for a
  conditional write to an external store that holds the ownership lease and
  the authority journal, and the owner stops serving when it cannot write.
  This is sound for `async` databases. It puts the object store's latency
  and availability on every commit, and makes it a second availability
  dependency. It is the path if an application needs `async` replication
  with Snapback-level guarantees. It would get its own child RFC.
- **Revision 4's narrow repair.** That meant device-held chain hashes,
  retained acknowledged writes resubmitted after loss, and journal replay
  after detected loss. Round 4 showed it cannot cover the undetected
  suffix, forks, or erased attempts and decisions without the synchronous
  anchor above.

The cost of the P1 design is one hash per durable write, an asynchronous
checkpoint, a declared HA mode, and `doctor` checks. There is no
device-protocol change.


## 6. The commit path

### 6.1 The seam

```rust
trait Committer {
    /// Run one mutation to an outcome, publishing at most one commit.
    fn commit(&self, op: Admitted, run: impl FnMut(&mut StoreTx, &mut Runner) -> Outcome)
        -> Result<Committed, RuntimeError>;
}
```

The reference implementation is today's protocol: reserve the head under its
lock, run the program, send the batched tail, commit. It stays in the suites
as the oracle for any other implementation. The same seed gives the same
outcomes, and the store oracles compare them.

### 6.2 Why the reference cannot be the production path on Postgres

Parent §3.3 gives the bound. The reference holds the head through every
program call and the flush. The code confirms it:

- SQLite takes `BEGIN IMMEDIATE` before `Runner::run`;
- Postgres serialized mode takes `SELECT seq FROM _head … FOR UPDATE` when
  the transaction begins.

So the database's own group commit can never combine two Snapback commits.
Postgres flushes concurrent committers together, but serialized holders
arrive one at a time.

### 6.3 Candidates, in the order they are taken

**(0) The serial batch** (proposed by the panel; §12). The committer drains
up to N queued mutations and runs them back to back inside one store
transaction:

- each mutation runs under its own savepoint, as the adapters already
  isolate a program today;
- the transaction makes one head update, to the batch's last sequence, and
  one flush;
- each mutation is acknowledged after that flush.

The batch keeps the reference's properties. It has the same serial order,
needs no read sets and no overlay, and reads its own writes natively.
Visibility is atomic per batch, so watermarks stay contiguous. A database
error in the batch reruns its members one at a time under the reference.

Its throughput is about `N / (N·k·RTT + exec + flush)`. S0 measured it
([`experiments/postgres-commit-path`](../snapback4/experiments/postgres-commit-path/README.md),
a statement-level model):

- **On Postgres it barely helps.** The best batch reached about 150–200
  commits/s at 0.5 ms RTT, against the reference's 120. Each member still
  makes about 10 round trips inside the serial section, and the flush it
  saves cost 20 µs on that disk.
- **On SQLite its gain is the flush's share.** That is about 1.46× at N=16
  on a 20 µs-fdatasync disk (an estimate; the core cannot yet be driven in a
  batch from outside). The gain should be far larger on disks whose flush
  costs milliseconds, which is unmeasured.

So (0) is not the Postgres answer. It stays because it is cheap and correct
by construction. It is the hot-key fallback for (a), the reference for
qualifying (a), and a SQLite improvement on slow-flush disks. It lands at
P0.

**(a) An optimistic single committer.** Convex orders commits this way, and
it is the candidate for removing the `k·RTT` term on Postgres. The first
draft omitted three requirements, all now part of the candidate:

1. *Execution.* A mutation runs at a snapshot S. On Postgres this is a
   `REPEATABLE READ READ ONLY` transaction. S is labelled with the internal
   revision read inside that snapshot (item 4), not with the public head,
   because non-head writes are part of the snapshot too. Its writes are buffered in C2's read-your-writes overlay (LLP
   3000.009 §4.2): point reads, scans, counts, deletions and constraints over
   buffered writes, with error and charge order preserved.
2. *A complete read set, recorded at the adapter boundary.* Every read
   passes through `Rows`, `PartitionRows`, or a durable-state operation, and
   is recorded there rather than in the `Runner`. Today `Runner::read_tables`
   records table names only. That includes sequence values, cap counts,
   index heads, `emit … once` keys, `_ops` lookups, and the authority facts
   the operation was admitted under: session validity, principal
   generation, lease. Key ranges must be precise. Table granularity would
   make every concurrent reader of `messages` a conflict, so precise ranges
   are a precondition of (a), not increment E's later optimization.
3. *Serial validation within the batch.* The committer folds each validated
   mutation's write set into an in-memory image before it validates the next
   one. A mutation is checked against every durable write with internal
   revision in (S, current] **and** against the mutations already accepted
   into the current batch. The batch is
   therefore one serial image, and two mutations that read the same counter
   at S cannot both enter it.
4. *The internal revision is the validation order, and the committer
   assigns it.* Session invalidations, claims and receipts commit without a
   public sequence today. Under (a) every durable write, head-advancing or
   not, takes the next internal revision and records its key footprint: the
   keys and ranges it wrote, such as the principal for a mint or
   invalidation, or the effect for a claim. Validation intersects read sets
   with those footprints, so a revocation that landed after S is seen. A
   mint for another principal is not a conflict. The public head remains
   only the sync watermark.
   - **Assignment** (round 3, Fable N2, Muse N2). A revision must be
     commit-ordered, or validation is unsound. A counter row locked until
     commit would recreate the `_head` hot row for all identity and work
     traffic, and a sequence is not commit-ordered.
   - So **every durable write goes through the committer**, whichever
     committer runs: reference, (0) or (a). The one exception is
     ownership-lease renewal. It is fenced by its token (§5.1), is not
     application state, and must not wait behind a long batch. Mints, claims, renewals, steps
     and sweeps become operations submitted to the committer's stream. The
     revision is the position in that stream, and the fence is taken once
     per batch. All committers record footprints in one key space, so (a)
     sees conflicts with work that fell back to (0).
   - This is the shape the parent's P2 already assumes: commits go through
     one committer. Non-head writes then pay batch latency, and S1a measures
     that.
   - The rejected alternative is validating by MVCC visibility: label S with
     `pg_current_snapshot()`, and treat a footprint whose transaction id is
     invisible in S as a conflict. It needs no serial stream. It is set
     aside because it ties validation to Postgres internals the SQLite
     adapter cannot share. The seam permits it per adapter if S1a shows the
     stream costs too much.
   - **Monotone writes do not conflict.** A time-audience pin only ever
     advances `max(pin, now)`, and `now` is assigned at admission, not read
     from the store. So pins are exempt from conflict detection and are
     applied as a batch maximum. §6.4's monotone-clock rule then holds in
     batch order: a mutation whose `now` is below the batch's committed pin
     reruns.
5. *Sequence-dependent execution.* Today the adapter takes `next_seq()`
   before the `Runner` starts, and execution embeds it. Effect ids are
   `effect-<seq>-<n>` (`runner.rs`), and Following stores admission tokens
   derived from the sequence (`timeline.rs`) that it later compares to tell
   delivery from backfill. Two executions at one snapshot would read the
   same provisional sequence. Under (a), sequence-derived values are
   therefore provisional placeholders. The overlay carries them, and the
   committer resolves them at commit to the sequence the mutation actually
   receives. Row images, index entries, comparisons and outbox rows that
   contain them are rewritten in the same batch transaction. A key that
   contains a placeholder is resolved before validation, so footprints never
   hold placeholders. Eligibility is conservative, by taint: any flow of a
   placeholder into a branch, a comparison, a string operation, a read-back
   or a row round trip makes the program ineligible for (a), and it runs
   under (0). `check` classifies this statically. Qualification covers
   concurrent emitters and Following transitions, not only counters.
6. *Batch commit.* As in (0): one Postgres transaction per batch, writes and
   tails as `unnest` arrays, one head update, one flush. On a conflict the
   mutation reruns at a new snapshot. After a bounded number of conflicts it
   goes to (0), so hot keys make progress.

Two bounds apply:

- the execution stage, about `connections / (k·RTT + exec)`;
- the commit stage, about `batch / (2·RTT + flush)`.

So (a) is connection-bound before it is flush-bound. Its recorded read sets
also supply LLP 3000.009 §7.1's read-set invalidation.

**S0's evidence.** The reference committer's serial time fits
`2.05 ms + 11.98 × RTT`. Twelve is exactly the number of round trips the
head lock is held across. That gives 120 commits/s at 0.5 ms, against raw
Postgres's 5,700/s with four writers and 89,000/s with 64. The upper bound
of (a)'s commit stage, with execution, validation and the overlay omitted
by construction, is 15,700/s at 0.5 ms. Child C's first decision rule
therefore fires, and **the author commissioned (a)** (parent §7). What S0 did not measure is (a)'s execution
stage. Child C's S1 sizes it before C2's overlay is built (child C §8).

**(b) Database transactions with an ordering stage.** The first draft's
version cannot keep exact snapshots:

- If a mutation's data commits before its ordering stage, readers see writes
  without a sequence, or sequence N+1 before N. LLP 3000 §7 already rejects
  this.
- If the data stays open until the stage flushes, the single `_head` row
  serializes the flushes again. W9's serializable cells failed on exactly
  that.

A correct version is a different protocol:

1. Assign the order in a short critical section.
2. Commit data transactions without holding that section across the flush.
3. Publish only the contiguous committed prefix.
4. Make a reader at W use a snapshot that excludes every commit above W.

That protocol is not designed here. (b) stays a named alternative, to be
taken up only if (a)'s overlay fails its differential.

**Set aside: the database's WAL as the commit order.** Logical decoding
emits commits in commit-LSN order and needs no head row. Postgres does not
guarantee that snapshot visibility follows commit-LSN order. Snapback's
snapshot-plus-catch-up protocol needs exactly that equivalence, and so does
watermark exactness. Logical decoding would also make every deployment
depend on replication slots, which some managed tiers restrict.

### 6.4 What stays fixed

Whichever candidate wins, these stay fixed:

- one total order per store;
- no gap below a published watermark;
- exact snapshots;
- whole-commit atomicity of rows, indexes, maintains, log, outbox and receipt;
- receipts recorded once;
- the same outcome as the reference for the same admitted inputs, modulo
  which concurrent mutation won;
- the authority clock monotone in commit order: a mutation executed with
  `now = t` commits only if `t` is at or after the last committed pin
  (`pin_writer_time`, `_meta.time_audience_clock`), and otherwise reruns;
- effects admitted only inside the commit, so a conflict rerun never
  performs a provider call;
- every durable transaction fenced by the owner token (§5);
- the same wire.

The simulator's seven invariants and the store oracles qualify the new
committer on both stores before it serves traffic.

## 7. Layout v1

### 7.1 Managed data

The generic layout stays (LLP 3000.009 §4.3). In production:

- `r` and `i` are `LIST`-partitioned by `t`, one partition per logical table,
  created at adoption. Vacuum, `ANALYZE` and bloat then act per table, and
  dropping a table drops a partition. Internal tables stay unpartitioned.
- Row images move from `TEXT` canonical JSON to the existing canonical form
  in `BYTEA`, or stay as text if child C shows no measurable difference. The
  bytes must be identical across stores for graduation's digests (sibling B
  §6).
- The portable 2,048-byte key bound and the 512-byte label bound stay, with
  every index still checked on every store.
- `C` collation on every key column, as today.

### 7.2 The head

`_head` is one row updated by every commit: a hot tuple, and the fencing
check of §5. Under the reference committer it is updated once per commit;
under (a), once per batch. Its table sets `fillfactor` so updates stay HOT.
Child C measures it.

### 7.3 Log retention

`_log` and `_commits` grow without bound on both stores today. The first
draft proposed a simple floor below which log rows are deleted. The panel
showed that would be silently wrong, for two reasons (§12):

- **No re-acquisition path exists for a device behind the head.**
  `partition::stream` replays spans above a device's watermark. The only
  snapshot path is a device with no watermark at all. A deleted span looks
  like "no events for you", and `/changes` invalidates everything only when
  its page fails to reach the head.
- **The log below a watermark is also authority state.**
  `memberships_before` reads the latest join or scope event at or below the
  watermark, and the expired-grant walk reads membership transitions from
  sequence zero with their commit times. The code's own annotation (`@ref
  LLP 3000#7`, `partition.rs`) says a content page cannot establish authority
  from a truncated ledger. Deleting below a floor changes answers for
  devices *above* it: an owed revocation for an expired grant is skipped.

So retention is **checkpoint plus floor**, as LLP 3000.002's proposal
"coordinated history, receipt and principal retention" already requires,
and it is not part of P1:

1. Fold the membership transitions and their commit times at floor F into
   a materialized authority checkpoint that the partition contract reads.
   Extend the shared partition oracles to consume it.
2. Publish F and the checkpoint atomically, with LLP 3000.002's crash-safe
   publication order.
3. Only then drop **content** events below F. Join and scope events are
   folded first, or kept in a table that is never pruned.
4. A resume, a `/changes` page or a sync page whose watermark is below F,
   or that would span a gap in `seq`, is an explicit refusal. The refusal
   forces a fresh snapshot, so retention can never answer silently.
5. On SQLite the head is `MAX(seq) FROM _commits`, so retention there
   persists the head first. On Postgres, `_log` may be range-partitioned by
   `seq` once its foreign key to `_commits` is replaced by the floor's
   invariant.

Until that design is commissioned, with its own Moves line (parent §7), both
stores keep the whole log, and graduation copies the whole log (sibling B
§4.2). Child C measures the cost of keeping everything (H7) and, once it
exists, of the checkpoint read on resume.

## 8. Connections, roles and supported Postgres

- **Driver.** The synchronous `postgres` crate stays for P1. The host's
  request-thread model (32 request workers, held long waits) maps onto a
  bounded pool. A held change poll waits on the in-process wakeup, or on
  `Notifier` at P2, and borrows a connection only to answer.
- **Connections.** P1 uses one dedicated owner connection (advisory lock,
  then `LISTEN`), one committer connection, and a reader pool sized from the
  request workers. Transactions are short and statements prepared. The store
  works directly or through a pooler in session mode. Transaction pooling
  is unsupported for **every** serving connection. Takeover terminates
  backends by tag and blocker, and under transaction pooling a backend
  belongs to whichever client is mid-transaction (§5.2). `doctor` detects
  it from the client side: it reads `pg_backend_pid()` and the session's
  `application_name` in two separate transactions on one client
  connection. A change means the pooler reassigns backends, and `serve`
  refuses that connection string. The same check runs when each serving
  connection opens.
- **Read replicas.** Not in P1. A replica-served read would need a causal
  token so that a client reads its own writes. That belongs with P2.
- **Roles.** These come from LLP 3000.009 §6.4:
  - *owner*: DDL, internal migrations and partition management, used by
    `deploy` and adoption;
  - *core*: managed reads and writes, used by `serve`;
  - *inspect*: read-only over generated views, used by `sql`.

  Increment D later adds the per-operation read roles and the
  database-owned write role. P1 creates these roles even though D is not
  built, so D does not have to reshape privileges on a live store.
- **Supported Postgres.** 16 and 17. No extension and no superuser required.
  TLS by default for any host other than a Unix socket; credentials are
  secret references in the release, never values. The qualification matrix
  is vanilla Postgres plus at least two managed providers that child C uses
  (for example RDS and Supabase's Postgres). It records each provider's
  restrictions.
- **Isolation.** One Postgres schema per logical store, as the evaluation
  does. A managed service gives each application store its own database
  (LLP 3000.009 §9).

## 9. Parity

A schema `check` accepts on SQLite runs on Postgres with the same outcomes,
or `check` names the store requirement before deploy. The features refused
today — row-keyed recounts, `not before`, assets, jobs, native jobs, actions,
schedules — must all reach parity before P1 is called a production target.
The store oracles in `snapback4-difftest` already compare exact outcomes.
P1 widens the generator so their prelude covers each family's operations, not
only queries and mutations.

**P1-MC, 2026-10-22.** Ordinary maintained count/sum columns and their private
maintains are admitted on the unified Postgres profile. The writing path needed
no aggregate SQL: `Runner` already maintains the authoritative private total and
mirrors the parent through `AnyTx`. The unified admission gate no longer delegates to the stale evaluator exclusion;
projected/orphaned column definitions still refuse schema validation. The retained
evaluator keeps its old exclusion until S10e: its fresh-store commit head differs
from the shared activation builder for columns, so it is not this parity oracle.
Postgres attach now admits only maintained-column additions, redefinitions and
removals (including indexes on those columns), with every other schema declaration
unchanged. It projects retired fields, clears retired private rows/indexes and
builds changed indexes under the head fence; the common activation builder
recounts and mirrors before publishing generation and release selection.
Backfill failure rolls the whole activation back. No hot-writer DDL is added.
General evolution and row-keyed background recounts remain refused.
Aggregate arithmetic retains checked i128 intermediates and E_OVERFLOW outside
the public 53-bit range; rule 8 does not silently saturate a Quarry aggregate.
Exact store oracles cover writes/moves/deletes, rollback/savepoint/member abort,
boundaries and observable same-parent contention. The existing public CLI witness
deploys the unchanged S1 app, seeds through the owned engine and compares every
room/user total with source recounts. Qualification and limits are recorded in
[the lane report](../snapback4/reports/20261022-p1mc-maintained-columns.md).

**P1-MC fix round 1, 2026-10-22.** Projection compares complete index
key definitions, including every ordinary key column, and validates affected
unique groups after the common recount/mirror builder and before publication.
The bounded key walk uses the same null-distinct rule and refusal wording as
SQLite. Public schema admission continues to forbid unique keys on maintained
columns; a physical-adapter regression independently exercises the sparse-zero
collision behind that admission boundary, alongside its public refusal.

Full-schema preparation derives receipt dependencies from an empty graph and
rebuilds source reservations, refusing supplied nonempty facts that disagree.
The reduced-declaration comparison derives that graph again after stripping
maintained fields, so receipt-enabled parents can evolve. For unchanged programs
and ordinary declarations, activation preserves previously admitted execution
declarations (including author-declared `held`) and derives the maintenance-dependent
receipt/reservation sites and prediction class from the candidate schema and IR.
Only diagnostic locations and site ordering are ignored in that comparison;
forged executable flags and prices refuse on both stores. Program changes retain
the existing program-admission path. Initial zero additions stay sparse;
redefinition from nonzero to zero writes an explicit zero (LLP 3000.007.001 §3.11).

A reopen that only refreshes the stored backend's derived layout and reservation structures preserves its already-admitted execution declarations. It does not reinterpret historical execution facts using a newer compiler's classification. Stored programs must be unchanged, and the candidate must equal the predecessor after the same deterministic contribution/index and delivery-lookup preparation used by open; this one-way comparison includes every operation fact and takes no value from the candidate as a derivation seed. Changed execution declarations, maintained-column definitions, programs or other schema content continue through the existing admission/evolution checks. Metadata forgeries do not acquire authority through a legacy layout repair.

Integration 23 received independent Muse and fresh Codex READY verdicts on
legacy-open revision 3. The actual common briefs, verbatim reviews and provenance
are preserved under `llp/reviews/3000.009.001.000-integ23-legacy-open-*`.
R1's program-equality concern added the unchanged-program gate. R2's claim
that an unrelated edit skipped every other program was checked against the
actual passing regression: unchanged historical `add` still reaches rederive.
R3 strengthens that control with a valid unrelated query-body edit and records
both READY verdicts. This records design readiness, not author acceptance or
complete native/Postgres qualification.

### 9.1 Adapter parity rules

Review of the first two P1 families (identity, requests) found the same
divergences in both. They are dialect facts, not family bugs, so every
Postgres family adapter follows these rules, and each family's shared
contract carries a case for each rule that applies to it:

1. **NUL in text.** Postgres `TEXT` cannot hold U+0000; SQLite stores it.
   Three reviews of drawing a "new versus existing identity" line each left
   a hole, so the rule is two-part (2026-10-21):
   - **Identity fails closed.** An identity string containing NUL
     (principal, email, kind, family, worker, invocation id) is refused at
     every identity entry point on both stores, and a stored session whose
     identity strings contain NUL **never authenticates**. A pre-upgrade
     SQLite identity containing NUL therefore stops working; nothing is left
     live but unrevocable. No current producer emits one: generated ids are
     base32, kinds pass `valid_name`, and tokens and digests are encoded.
   - **Other families validate at admission only.** New identifiers and
     names (request, job, effect and schedule keys) are refused in shared
     validation before any write. Acting on an existing stored row by its
     stored key never re-validates it, so a legacy SQLite row stays
     expirable, settleable, cancellable and claimable, and a bounded pass
     never fails on it. A **lookup or filter** by a key containing NUL returns
     absent/empty on Postgres without querying, since no such row can exist
     there; SQLite queries as before.
   - Diagnostic free text (settlement errors, park reasons, refusal
     detail) has U+0000 replaced by U+FFFD in shared policy, before
     truncation, on both stores.
   - JSON-encoded values (`r.data`, payloads, results, arguments) are
     already safe: the encoder escapes NUL as `\u0000`.
   Admission and binding have shared chokepoints (2026-10-21):
   - **Identity-shaped strings fail closed.** The main admission doors —
     mutate, actions, routes, claims, steps on first record, asset intents
     and identity — refuse NUL in identity-shaped strings on both stores.
     These checks sit above adapter access; this does not expand the engine
     families currently implemented on Postgres. `identity_fits` refuses NUL,
     as do service-seat validation (`is_service`) and name validation
     (`valid_name`). Every admission path using those checks inherits the
     refusal, including viewers, request/invocation ids and scheduled-action
     seats, with its existing refusal code. Mutation and asset-intent owner/id
     checks are NUL-only; direct effect-worker labels likewise retain their
     existing unbounded size allowance. Refuse before opening a writer,
     advancing the clock or running expiry whenever the input is available then.
     Stored session identities containing NUL **never authenticate**. This
     covers principal, kind and family, including family members considered
     during lost-delivery recovery. Recovery retains the original liveness
     rule: any live valid family member suffices, including an action-kind
     custom session or a surviving read member after the full member closes.
     Ordinary expiry may delete an expired stored NUL session: cleanup is
     not admission and does not authenticate the row (review finding P3).
   - **Other families validate at admission only.** Acting on an existing
     stored row by its stored key never re-validates it, so a legacy SQLite
     row stays expirable, settleable, cancellable and claimable, and a bounded
     pass never fails on it. Step names are stored keys, not identities:
     first record refuses NUL, but completion, parking, replay and
     reconciliation address the stored row as-is.
   - **Postgres guards every parameter bind.** `Tx::query` and `Tx::execute`
     inspect typed text parameters, including optional text and text arrays,
     before Bind/Execute is sent. Any residual NUL is a typed `E_INPUT`
     refusal, not `E_STORE` or a server encoding error, and poisons its
     transaction. Subsequent statements and commit return an error; the
     transaction rolls back even if the caller catches the refusal, including
     when a buffered commit tail caused it (rule 4). Optional lookups use one
     `absent_text_key` helper:
     a NUL key returns absent without querying because no matching row can
     exist there; SQLite queries its legacy keys normally. Each such lookup
     documents the absence behavior.
   - Diagnostic free text (settlement errors, park reasons, refusal detail)
     has U+0000 replaced by U+FFFD in shared policy before truncation on both
     stores. JSON-encoded values (`r.data`, payloads, results, arguments) are
     already safe: the encoder escapes NUL as `\\u0000`.
   - **Documented residual:** any remaining direct Rust-API path where SQLite
     stores a NUL string and Postgres refuses it with `E_INPUT` and rolls back.
     This includes direct adapter writes bypassing admission; it is not
     transparent storage parity for that input. The open
     [static census ticket](../issues/20261021-snapback4-nul-string-to-adapter-census.md)
     proposes listing every adapter write that binds a caller-supplied string,
     tagged admitted-through-chokepoint or residual, so tools find future doors.
2. **Every `LIMIT` has a total `ORDER BY`.** SQLite's unordered `LIMIT`
   returns whatever its plan visits first, and Postgres's returns something
   else. Where the limit can bind, the two stores would then commit
   different subsets. Both adapters order by a key that is unique within
   the selection (for example `at, id`). On SQLite this is a behavior
   change only in which of several equally valid subsets a bounded pass
   takes.
3. **Explicit column lists, never `SELECT *`,** in any statement an adapter
   prepares or caches. An attach-time `ADD COLUMN` on another connection
   changes `*`'s result type, and Postgres then refuses the cached plan
   until the connection reopens.
4. **A statement error ends the transaction on both stores.** Postgres
   aborts the transaction on any error; SQLite continues. The shared
   contract therefore treats an adapter error, including a Postgres pre-bind
   guard refusal, as terminal for its transaction. An adapter operation whose
   conflict the policy is meant to handle and continue past expresses that
   conflict in the statement
   (`ON CONFLICT`, a conditional `UPDATE` and its row count) or wraps itself
   in a savepoint, and returns a typed result rather than an error.
5. **Typed arguments, not dialect-parsed text.** A trait takes `&[String]`,
   not a JSON string that `json_each` and `json_array_elements_text` would
   parse differently. Limits and counts are unsigned in the trait, so
   SQLite's `LIMIT -1` meaning "all" cannot reach Postgres, which refuses
   it. Jobs inspection clamps unsigned row limits to `i64::MAX` and summary
   prefix lengths to `i32::MAX` on both adapters, an explicit finite bound
   portable across substring implementations; zero remains zero. Oversized
   limits therefore return every retained row that fits this explicit bound,
   and oversized prefixes return the whole diagnostic with no truncation flag.
6. **No DDL in per-operation writers.** Tables and columns are created or
   upgraded at attach, under the head lock. Shape validation also refuses
   inheritance, partitioning, `UNLOGGED` tables, rewrite rules and deferrable keys.
   A `CREATE … IF NOT EXISTS` or
   no-op `ALTER` inside a hot writer takes relation locks for the rest of
   that transaction.
7. **Races are witnessed through adapter operations.** A two-connection
   race test drives the adapter's own methods, not harness SQL. A race
   that can pass under sequential scheduling is not evidence. A barrier
   alone is not enough, because the holder can finish and commit before the
   contender reaches the fence. The holder keeps the fence until the
   contender is **observably waiting on it**: on Postgres,
   `pg_blocking_pids(contender)` includes the holder; on SQLite, the
   contender's busy handler has fired at least once. Only then does the
   holder proceed. One shared test helper provides this for every family.

8. **Signed-boundary arithmetic saturates in shared policy.** SQLite turns
   an `INTEGER` overflow into a `REAL` that later typed reads refuse;
   Postgres raises `22003` and aborts. Additions and subtractions on stored
   counters, lease and expiry times (job row counts, lease shifts, session
   expiry shifts and stale-asset cutoffs) saturate at the corresponding
   signed `i64` endpoint, identically on both stores (P1-JB, P1-OB and P1-AS
   reviews). This changes SQLite only at the boundary.
9. **Attach shape checks are locale-independent, and are tested on a
   locale database.** The evaluation test script creates its cluster with
   `initdb --no-locale`. Production databases usually carry a locale such
   as `en_US.UTF-8`, where catalog renderings (`pg_get_indexdef`, column
   collations) can differ. Shape checks compare structured catalog data or
   normalized collations, and the Postgres suite runs once with a real
   UTF-8 locale.

## 11. Alternatives considered

- **A typed per-table layout on Postgres.** LLP 3000.009 §13 declined it.
  Nothing here changes that, and child C names the measurement that would
  reopen it: storage and WAL amplification beyond its stated bound.
- **Port by table translation**, giving each SQLite table a Postgres twin and
  translating statements one by one. This is faster to start, but it keeps
  policy in SQL in two dialects. The C3.2 pattern (policy in Rust, storage in
  the adapter) already showed the alternative works.
- **An async driver and runtime now.** It would change the host's
  concurrency model at the same time as its store. Child C will show whether
  threads or connections are a binding limit before this is taken up.
- **Postgres-only server storage.** LLP 3000.009 §13 declined it.

## 12. Panel revision

The one-round panel (Astra max, Fable xhigh, Grok 4.7 xhigh; parent §9)
judged this document sound with major issues. Revision 1 changes:

- **§5:** the head predicate alone left non-head writes unfenced, and a
  paused owner's advisory and row locks blocked takeover forever. Every
  durable transaction is now fenced; takeover is lease-driven with backend
  termination; same-incarnation failover requires a replication guarantee
  that keeps every acknowledged transaction.
- **§6:** the serial batch is added as the first committer. Candidate (a)
  now validates within its batch, records complete read sets at the adapter
  boundary, and gives every durable transaction an order. Candidate (b) is
  demoted to an unspecified alternative, because its first version broke
  exact snapshots.
- **§7.3:** retention by deletion would have skipped owed revocations. It
  becomes checkpoint plus floor under LLP 3000.002's proposal, with explicit
  refusals, and leaves P1.
- **§4:** release artifacts, worker completions, change evidence, action
  steps, cap occupancy and narrowed dormant rows join the inventory.

### Round 2 and the experiments (revision 2)

Round 2 (Astra, Fable and Grok as deltas; Muse fresh) and two experiments
drove these changes:

- **§5, rewritten from the fencing prototype.** Its witnesses W1–W10 ran on
  real PostgreSQL 16.15 as non-superuser roles. In every witness, nothing
  the old owner wrote committed after a takeover.
  - **The pid list blocked takeover forever** when a paused connection was
    unlisted (W3; round-2 Astra N4, Fable note 3). Replaced by tags and
    blocker termination.
  - **`FOR SHARE` starved lease renewal** and let a long transaction cause a
    takeover of a live owner (W8; Fable N1, Grok note). Now `FOR KEY SHARE`,
    with the token changed only under `FOR UPDATE`.
  - **The head-first lock order deadlocks with takeover** (W10). The fence
    is now the first lock.
  - **Ambiguous commits** are named, and writes are retry-safe across owners
    (W9).
  - **Failover continuity** is detected by system identifier and timeline,
    with a three-part guarantee (Grok N5, Muse F1).
- **§4.2.** Blob retention is matched to the recovery horizon (Muse F2). An
  exact artifact digest is used, because the execution digest omits
  provenance (Astra).
- **§4.3.** Execution ownership and uncertain attempts (Astra N3, Grok N6).
- **§6.3.** (a) validates against an internal revision with key footprints
  (Grok N4, Fable note 4). Sequence-derived values are placeholders (Astra
  N5). S0's measurements are recorded. The serial batch is not the Postgres
  answer, and (a) is proposed for commissioning.
- **§8.** Transaction pooling is refused for every serving connection
  (Grok note).

### Round 3 (revision 3)

- **§5.4.** Every reviewer found the continuity guarantee unsound, as
  FUNDAMENTAL (Astra N1, Grok N1) or MAJOR (Fable N1, Muse N1):
  - a lagging replica can be promoted;
  - a fresh process has no baseline to compare against;
  - checking the configuration is not checking liveness;
  - "the provider fences the old primary" is trust;
  - the adapter's `statement_timeout` acknowledges a commit whose
    replication wait was cancelled.

  In P1, every promotion is a new incarnation. Detection uses a replicated
  identity row. COMMIT is uncancellable. Keeping the incarnation becomes a
  later, per-provider mode that needs evidence.
- **§5.1–§5.2.** Renewal is token-fenced. The `FOR KEY SHARE` queueing claim
  is corrected (Fable). Takeover re-reads before every termination round and
  bounds blocker termination by token, restoring the prototype's bound
  (Grok N2, Astra and Fable notes). The tag format is specified. The
  retry-safety claim becomes a per-path table with a witness (Muse N3).
- **§4.3.** The interim worker fence missed a handler that had outlived its
  lease (Astra N3, Grok N3). It is now drain on graduation and park on
  promotion.
- **§6.3.** The committer assigns every revision through its stream, and
  all committers share one footprint key space (Fable N2, Muse N2).
  Monotone pins are exempt from conflict detection. Placeholders are
  resolved before validation and eligibility uses taint (Grok and Muse
  notes).
- **§4.2, §8.** The following reader's P2 disposition, the blob-window
  check, and the client-side detection of transaction pooling (Muse).

### Author rulings (revision 4)

- **Rejected: "every promotion is a new incarnation"** ("this seems silly.
  can you come up with a way to fix this?"). Revision 4's §5.4 (superseded in
  revision 5 after round 4) proved continuity from evidence:
  - a hash chain over the committer's stream;
  - an asynchronous checkpoint in the blob store, advanced by conditional
    write;
  - device-held hashes.

  Supported HA configurations lose nothing, so a failover is a reconnect.
  Detected loss is repaired narrowly. A new incarnation is reserved for a
  provably different history.
- **Commissioned: the optimistic committer (a)** ("yes unless there are
  realistic alternatives"). The alternatives considered are in parent §7.

### Round 4 (revision 5)

A narrow round (Astra and Grok) reviewed revisions 3–4. Both returned
SOUND WITH MAJOR ISSUES.

- **Revision 4's continuity design was unsound** (Astra N1, N2, N5, all
  FUNDAMENTAL; Grok N1, FUNDAMENTAL; Astra N3, N4):
  - an asynchronous checkpoint cannot detect losses newer than itself;
  - it cannot stop two primaries serving before it lands;
  - journal replay ran only after a detected loss;
  - a hash cannot reconstruct lost writes, attempt records or graduation
    decisions.

  §5.4 now draws the line at the database's replication guarantee: a
  declared HA mode, lossless modes keeping the incarnation, an operator
  choice in `async`, the checkpoint as a tripwire, and graduation pinned to
  a lossless mode. The synchronous external anchor that would make `async`
  safe is recorded as a separate path.
- **Renewal does not queue behind a waiting `FOR UPDATE`** (Grok N2,
  following W8). Takeover now claims the expired lease with a conflicting
  no-op update before any termination.
- **Smaller items** (Grok, Astra): the park predicate is `attempts > 0`;
  renewal is exempt from the committer stream; the P1b witness list no
  longer contradicts §5.4.
