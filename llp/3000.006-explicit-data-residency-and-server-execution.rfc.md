## Summary

Snapback 4 already has the correct substrate for data an application does not
want on a device: `sync` is opt-in, a table without `sync` is online-only, and
rows older than a declared horizon remain on the server. The full-brief Clique
run nevertheless exposed an ergonomic gap. The residency choice is expressed
partly by absence, the execution consequence is not prominent in the generated
contract, an offline server-dependent read can look like an ordinary incomplete
read, and the efficient replacement for a large synced source — a compact
synced projection — is a design pattern rather than a first-class paved move.

This RFC proposes that Snapback 4 make **data residency and execution locality
explicit, statically classified and observable** while keeping one language,
one authorization model and one operation plane. It is not an escape hatch
from rules, metering, transactions or types. It is the supported way to say:

1. these source rows stay on the server;
2. this bounded projection belongs on the device;
3. this operation is locally complete, locally partial, server-required, or
   queueable without a local prediction; and
4. an offline caller receives a typed truth instead of plausible-looking empty
   data.

The proposal preserves the architectural beauty of a server-authoritative
system with local-first partitions. It aims to remove a false choice between
syncing too much data and leaving Snapback's coherent operation model.

## 1. Motivation: the edge where elegance broke

The Astra-medium builder's account of the full Clique run was positive about
Snapback 4's center and negative about its edges. Authorization and sync shared
one membership fact; expiry, typed assets, view-once access, the persisted
replica, predictions, the outbox and generated operation types removed whole
integration layers. The application needed no separate TypeScript server or
API routing layer.

The same compression made a poor residency choice consequential. The Clique
application declared several growing public tables without a horizon and
broadcast per-recipient receipt rows into large conversation partitions. At
the scale fixture, cold sync exceeded thirty seconds and consumed substantial
memory. The following feed merged a thousand lanes and examined 21,000 rows for
one page, producing a 19.2× ratio against the five-follow account. Snapback made
the policy concise; concision did not make the policy cheap.

The important diagnosis is not “local-first is too expensive.” It is:

- some facts belong on the device;
- some facts belong only on the server;
- some large or sensitive server facts should produce a small device fact;
- some operations can run locally, some can only run remotely, and some can do
  either depending on the requested horizon; and
- the author should know which case they wrote before running the hub fixture.

Today those truths exist across `sync`, horizons, completeness, the meter and
guide prose. They should become one legible model.

## 2. What exists today

LLP 2000.000 §7 and LLP 3000 §7 already establish:

- `sync` is explicit rather than default;
- a table without `sync` is online-only;
- `sync ... last N by index` places only a bounded horizon on a device;
- older rows remain readable online;
- a local read beyond its held horizon reports `complete: false`;
- the online-only client has no store or interpreter;
- the local-first client has a replica, interpreter and durable outbox; and
- the same authored queries and rules govern both hosts.

This RFC does not replace those mechanisms. It promotes their consequences
into syntax, generated metadata, runtime outcomes and diagnostics.

## 3. Goals and non-goals

### 3.1 Goals

1. Make every table's device-residency choice visible in its declaration.
2. Make every operation's possible execution locations visible at `check` and
   in generated artifacts.
3. Never return an empty or partial value that an ordinary application could
   mistake for a complete server answer.
4. Make server-only source plus compact synced projection a paved composition.
5. Preserve one set of authorization rules, one meter, one value model, one
   transaction model and one generated API.
6. Diagnose expensive partitions and remote dependencies before scale replay.
7. Keep the local-first path excellent for the data that genuinely belongs on
   a device.

### 3.2 Non-goals

- No arbitrary unmetered server function.
- No second REST, RPC or GraphQL authorization surface.
- No bypass around Quarry rules or operation argument/result types.
- No silent client/server join.
- No promise that every query can run offline.
- No attempt to make an intrinsically large partition inexpensive.
- No requirement to sync source rows merely because a derived value is synced.
- No automatic fan-out or denormalization whose write amplification is hidden
  from the author.

## 4. The proposed residency model

Every durable table chooses one residency form.

### 4.1 Synced tables

The existing forms remain:

```quarry
table messages:
  conversationId: conversations
  authorId: principal
  body: text <=4000
  at: time
  by byConversationTime: conversationId, at, id
  read <- exists memberships[.conversationId, viewer]
  sync to memberships[.conversationId] last 500 by byConversationTime
```

The row is available on an admitted device inside the declared horizon. The
server remains authoritative. The horizon is a residency and acquisition bound,
not a deletion policy.

### 4.2 Explicit online-only tables

Add a positive spelling for the state that today is represented by the absence
of `sync`:

```quarry
table auditEvents:
  actorId: principal
  action: text <=100
  at: time
  by byActorTime: actorId, at, id
  read <- exists admins[viewer]
  insert <- deny
  update <- deny
  delete <- deny
  online only
```

`online only` means:

- rows never enter a partition snapshot or change stream;
- rows never enter a device store;
- queries may read them on the server under the same rules and meter;
- a device cannot claim a locally complete answer from them; and
- server-side jobs and effects may consume them through their existing
  authorities.

The phrase is deliberately about residency, not secrecy. Authorization still
comes from the table rules. An online-only public table is possible; it is
simply not replicated.

### 4.3 Omission policy

The preferred end state is that every table spells either `sync ...` or
`online only`. Missing both should be an admission error with both rewrites.
During an experimental migration, the compiler may retain the current meaning
and emit `N_IMPLICIT_ONLINE_ONLY`; Snapback 4 has no stability obligation that
requires the omission to remain permanent.

Explicitness is worth the line. A security- and performance-significant data
placement decision should not be encoded only as absence.

### 4.4 Horizons are the mixed case

A bounded synced table is not wholly local or wholly remote. Its newest `N`
rows per group are local; older rows are online-only. The same query may be
locally complete for the first page and server-required for a deep page.

The compiler therefore classifies **read sites**, not merely tables. The
generated operation classification is the join of its sites and arguments.

## 5. Execution classification

`snapback4 check` computes and emits one or more capabilities for every
operation:

| Class | Meaning |
| --- | --- |
| `local-complete` | Every possible read is decided by rows the device holds inside a statically established horizon. |
| `local-bounded` | The device can return a truthful partial page; continuation or a wider request may require the server. |
| `server-required` | At least one necessary read site is online-only, or the device cannot evaluate the operation without inventing missing facts. |
| `queueable` | The mutation's arguments and client-minted ids are sufficient to durably submit it later. |
| `predictable` | In addition to being queueable, the device can run its reads and writes locally to produce a prediction. |
| `online-required` | The operation needs a server fact or immediate server result and cannot be truthfully admitted offline. |

These are not author-written promises. They are compiler results derived from
the program and schema, like uniformity and completeness today.

Example output:

```text
residency
  thread        local-complete inside messages.last(500); server after horizon
  globalSearch  local-bounded inside held rows; server completes older matches
  adminAudit    server-required: auditEvents is online only
  sendMessage   predictable, queueable
  rotateSecret  online-required: reads secrets online only
```

Generated TypeScript carries the classification as metadata available to the
client and developer tools. Ordinary application code should not need to copy
it into a second registry.

## 6. Read behavior

### 6.1 Connected execution

When the device can prove the requested query locally complete, it runs the
query locally. When a necessary read site is online-only or the request crosses
a horizon, the connected client sends the **whole operation** to the server.

The default must not splice a local prefix into a remote suffix. Whole-operation
routing preserves one snapshot, one authorization decision, one meter and one
result ordering. A future explicitly specified algebra may compose local and
remote pages, but implicit hybrid evaluation is out of scope.

### 6.2 Offline execution

The existing `{data, complete: false}` is appropriate when the device has a
useful, truthful prefix: for example, the newest 500 messages while older
history is unavailable.

It is not sufficient when the query depends on a wholly online-only fact. An
empty list in that case is syntactically plausible and operationally false. The
client needs a typed non-value outcome. This RFC proposes:

```ts
type Read<T> =
  | { data: T; complete: boolean; fresh: boolean; since?: number; next?: Cursor }
  | { loading: true }
  | { unavailable: "requires-online" }
  | { denied: Refusal };
```

`unavailable` is not `denied`: reconnecting may make the same authorized query
answerable. It is not `loading`: while offline, no progress is occurring. It is
not `{data: empty, complete: false}`: there is no honest partial value.

This addition revisits LLP 2000.000 §8's index card and therefore requires an
explicit author ruling before acceptance.

### 6.3 React behavior

A generated hook knows the same classification:

- locally complete reads render from the replica immediately;
- server-required reads preserve a prior confirmed value while refreshing if
  the application opts into stale display;
- a cold offline server-required read returns `requires-online`;
- a bounded local prefix returns its data with `complete: false`; and
- reconnection re-runs the whole server operation and replaces the prior state
  causally.

The hook must not guess that an empty array is an offline placeholder.

## 7. Mutation behavior

Server-only residency and offline admission are independent questions.

1. A mutation over synced data may be `predictable` and `queueable` as today.
2. A mutation that writes an online-only table but needs no server read may be
   `queueable` without prediction. Its durable local state is the intent, not a
   fabricated row.
3. A mutation that requires an online-only read to decide validity or compute a
   result is `online-required` unless the compiler can prove an equivalent
   local fact.
4. A mutation that performs an online-only byte transfer, such as upload, is
   `online-required`; the client does not imply that bytes are durably queued.

The generated mutation state should expose the distinction. An application may
promise “saved to send later” only for a queueable operation.

No mutation bypasses the server transaction or rules. A local prediction is
never authority.

## 8. Compact synced projections

The preferred escape from an expensive or sensitive source partition is not a
custom endpoint. It is a small table or maintained value with an audience of
its own.

### 8.1 Clique receipts

Instead of syncing every recipient's receipt event to every conversation
member:

```quarry
table receiptEvents:
  messageId: messages
  principal: principal
  state: text 1..20
  unique byMessagePrincipal: messageId, principal
  read <- exists messageMembers[.messageId, viewer]
  insert <- .principal = viewer
  update <- .principal = viewer
  delete <- deny
  online only

table receiptStates:
  messageId: messages
  state: text 1..20
  unique byMessage: messageId
  read <- exists messageMembers[.messageId, viewer]
  insert <- deny
  update <- deny
  delete <- deny
  sync to messageMembers[.messageId]
```

The exact maintained or job-backed computation is a separate design. The
residency principle is what matters: detailed source online, bounded answer on
the device.

### 8.2 Other ordinary shapes

- raw analytics events online-only; daily totals synced;
- moderation and audit history online-only; current enforcement state synced;
- global feed sources online-only; per-reader feed entries synced;
- full message history online-only beyond the horizon; recent messages synced;
- global search index online-only; the held horizon indexed locally;
- service credentials and provider state online-only; user-visible job state
  synced; and
- large ranking signals online-only; a bounded candidate list synced.

The projection remains an ordinary table with ordinary rules, indexes, meters,
transactions and tests. Snapback should provide recipes and diagnostics, not a
hidden projection subsystem.

## 9. Cost and residency visibility

The author should not need a failed cold sync to discover the partition they
declared. `check --cost` or a dedicated `check --residency` view should report:

```text
messages       synced: last 500 per conversation
receiptEvents  online only
receiptStates  synced: at most 1 per visible message
posts          WARNING unbounded public sync
               hub estimate: 227,699 rows for u0500
               rewrite: add a horizon or sync a per-reader projection
```

Static output distinguishes facts from estimates:

- declaration facts: audience, horizon, indexes, cap, operation classes;
- fixture measurements: rows, bytes, groups and acquisition time for named
  personas; and
- extrapolations: clearly labelled estimates, never admission claims.

`why <operation>` should show the read site that makes an operation remote and
the shortest supported rewrite that would make it local. `why <table>` should
show why each row reaches a principal and which operations consume it.

## 10. Safety and semantic invariants

1. A row enters a device only through a declared `sync` audience admitted by
   the corresponding read rule.
2. `online only` rows never appear in snapshot, partition log, replica export,
   prediction state or device diagnostics containing row values.
3. Server execution uses the same operation, rules, value model, meter and
   transaction semantics as local execution.
4. A connected remote fallback routes the whole operation unless an explicit
   composition contract exists.
5. An offline read never converts missing server-only facts into a complete
   value.
6. A queued non-predictable mutation displays no invented row result.
7. A synced projection has its own authorization and audience; authority does
   not transfer merely because its source was readable to the system.
8. Revocation removes synced projections under the same watermark and tombstone
   rules as ordinary synced rows.
9. Residency metadata in generated code is derived from the admitted schema and
   cannot drift from it.
10. No server-only facility becomes an unmetered or untyped escape hatch.

## 11. Why this is not arbitrary server code

An unrestricted server function would make edge cases easy by creating a
second, more powerful system. It would also recreate the costs Snapback 4 is
designed to remove: duplicated authorization, opaque invalidation, unbounded
work, bespoke wire types, and behavior a device cannot classify.

This RFC instead varies **where declared data resides and where the same typed
operation executes**. It allows more applications to stay within Snapback's
model without claiming that all application data should be replicated.

Native queries and jobs in LLP 3000.005 remain bounded computation over the
same governed store. They are complementary, not an alternative authority
plane. Network I/O remains outside the engine through effects and service
seats.

## 12. Alternatives considered

### 12.1 Keep omission as the only online-only spelling

Mechanically sufficient, ergonomically weak. A missing line is too subtle for
a decision that controls security exposure, offline behavior and acquisition
cost.

### 12.2 Sync everything and rely on horizons

Horizons solve bounded history, not server-only secrets, audit data, global
indexes or source tables whose useful device form is an aggregate. This also
encourages applications to treat `complete: false` as a universal escape from
data modeling.

### 12.3 Add custom server endpoints

Rejected. They create a second type, authorization, metering and observability
surface and make the local/remote boundary invisible to generated clients.

### 12.4 Let the client transparently merge local and remote results

Rejected as the default. It risks different snapshots, duplicate or missing
rows, unstable ordering and authorization changes between halves. Whole-query
server routing is simpler and more credible.

### 12.5 Automatically synthesize projections

Deferred. The compiler can recommend and eventually generate a candidate, but
fan-out and aggregate semantics are product decisions with write, storage and
revocation consequences. The committed schema must remain authoritative.

## 13. Implementation sequence

### Phase A — make the current truth explicit

1. Parse and bind `online only` as the positive spelling of no `sync`.
2. Require or warn on tables that declare neither residency form.
3. Emit table residency and operation execution classes into generated API
   metadata.
4. Add compiled guide examples and conformance cases.
5. Add `check --residency` and `why` explanations.

This phase changes no storage or wire behavior.

### Phase B — truthful routing and offline outcomes

1. Route a connected server-dependent read as one server operation.
2. Distinguish useful bounded partial data from no locally evaluable value.
3. Add the accepted typed `requires-online` representation to the client and
   React hooks.
4. Classify mutations as predictable, queueable or online-required.
5. Exercise transitions under disconnect, reconnect, logout and revocation in
   the simulator and browser/device witnesses.

### Phase C — pave projections

1. Add compiled recipes for receipts, analytics, feeds, search and moderation.
2. Make `N_NO_HORIZON` and `N_WIDE_MERGE` propose the relevant projection.
3. Show fixture-measured partition rows and bytes per persona.
4. Implement the compact Clique receipt shape and measure its acquisition,
   storage and live behavior against the retained full-brief application.

### Phase D — repeat the experience test

Run a fresh docs-only Astra-medium Clique cell on a published pin. The builder
must not inspect installed package source or add a custom transport/store guard.
Grade native behavior and the full hub acquisition path. Compare the exact
residency report produced before replay with the measured result.

## 14. Acceptance criteria

This RFC is successful when:

1. every table visibly declares synced or online-only residency;
2. `check` classifies every operation without running the application;
3. a server-only query works through the ordinary generated client while
   connected and returns a typed non-value while cold and offline;
4. a horizon query returns useful local data with `complete: false` and routes
   the whole operation to the server when the requested page is not held;
5. online-only rows are absent from every device persistence and stream witness;
6. a queueable, non-predictable mutation survives process death without showing
   a fabricated optimistic row;
7. the compact Clique receipt projection preserves membership revocation,
   ordering and aggregate receipt behavior while materially reducing the hub
   device's rows and acquisition time;
8. generated metadata, `why`, guide examples and runtime behavior agree on the
   installed published package; and
9. the repeat builder completes without source inspection or a parallel API
   plane.

## 15. Consequences

### Positive

- Applications can keep large or sensitive sources off devices without leaving
  Snapback's coherent operation model.
- Local-first becomes a per-dataset choice rather than an all-or-nothing app
  identity.
- Compiler output explains both offline capability and acquisition cost.
- Compact synced projections become the ordinary answer to scale cliffs.
- The constrained language retains its authorization and metering advantages.

### Negative

- Every table gains one explicit declaration.
- The client result vocabulary may gain an `unavailable` state.
- Query routing becomes more visible and therefore adds concepts authors must
  learn.
- A projection duplicates selected facts and moves some cost to writes or jobs.
- Honest server-only operations cannot pretend to work offline.

These costs are preferable to accidental replication, ambiguous empty data or
an ungoverned server escape hatch.

## 16. Open questions for the author

1. Is `online only` required on every unsynced table, or introduced first as a
   canonical spelling with `N_IMPLICIT_ONLINE_ONLY`?
2. Does the index-card `Read<T>` gain `{unavailable: "requires-online"}`, or can
   an equally unambiguous result fit the existing vocabulary?
3. May a query explicitly request `server` execution even when it is locally
   complete, for debugging or authoritative freshness, or is that a client call
   option rather than Quarry syntax?
4. Can a mutation over online-only data be durably queueable when it needs no
   server reads, or should all such writes be online-required in the first
   implementation?
5. Should `check --residency` be a separate view, or should the concise summary
   be part of ordinary `check --cost`?
6. Which compact projection proves the design first: Clique receipts, global
   search, analytics, or an Interview feed?

Until those questions are ruled and the implementation exists, the current
LLP 3000 / LLP 2000.000 semantics remain binding.
