## Summary

The author asked, after LLP 3000.004: *what if we let you write Rust programs
that could access the database and generate a feed that the normal Snapback
live query could serve — would that be crazy?* Not crazy. It is the open
effects-host question of LLP 2000.000 §10 with a Rust answer, and it fits
Snapback 4 better than the JavaScript options because the pieces exist: the
interpreter runs over a `Rows` trait, the engine already runs jobs as the
system principal one chunk per commit under a meter, and the device core
already compiles to wasm.

This document specifies **native jobs**: a job whose body is not Quarry but
the app's own Rust, compiled to wasm by `snapback4 check`, hosted by the
engine with the same words as any job. Four rules keep it a job rather than a
hole in the design:

1. **Quarry still declares the feed.** The table, its rules, its horizon and
   its `sync` line are in `schema.q`; the Rust fills it. The one-language
   principle holds: effect bodies were always allowed in another language.
2. **Writes go through the engine's write path, never raw SQL**, so rules'
   companions — validation, constraints, maintains, partition events, the
   log — fire, and the ordinary live query serves the result for free.
3. **Reads go through the engine's read path, so the meter counts them.**
   A native job gets a job's words: one chunk per commit, the job ceilings,
   parked on refusal, listed by `doctor`, run by `snapback4 run`.
4. **Pure over the store.** The module imports one host function and
   nothing else: no clock, no randomness, no network. It runs in the
   simulator. Network-bound ranking stays outside and writes into tables
   the native job then reads.

What it buys: floats, vectors, real loops and a typed schema for the scoring
half of a feed, none of which belong in Quarry; and, after the native module
landing, one Rust function over `Rows` that can run on the server as the job
and on the device as the personalizer. What it costs: `check` runs `cargo`
when `snapback/native/` exists (a warm no-op build is a few hundred
milliseconds), and the binary carries a wasm interpreter.

## 1. The question (author, 2026-09-13)

> What if we let you write Rust programs that could access the database and
> generate a feed that the normal Snapback live query could serve. Would
> that be crazy?

The lead answered with the four rules above and three hosting options, and
recommended wasm inside the stock binary. The author: "Write up an LLP about
this and then implement." This document is that LLP; §8 records what landed.

## 2. Where it sits

LLP 3000.004 §3 drew the line: candidate generation and learned scoring are
not in the data plane. That stays true of *Quarry*: no floats, no loops over
the corpus, no model. This document moves the line for *Rust*: a native job
computes over the store with the same access a Quarry job has, under the
same bounds, and no more. The external ranker of LLP 3000.004 §6.5 (a worker
with a service principal writing through mutations) remains the shape for
anything that needs the network; a native job is the shape for anything that
needs only the rows.

Hosting was the real decision. Three options were weighed:

- **Wasm inside the stock binary** — the app's Rust compiles to
  `wasm32-unknown-unknown`; the server hosts it with fuel metering and host
  functions that are exactly the engine's read and write paths; a release
  stays a stock binary plus one `.wasm` file. Sandboxed, portable, no
  per-app server build, no unsafe code in the core.
- **A cdylib over the existing JSON C ABI** — simpler, no wasm runtime; but
  a crash takes the server down and the ABI is fragile across toolchains.
- **The app owns the server binary, Exact2-style** — most natural for
  Interview; but it ends `npx snapback4` and the loop bar's fresh-agent
  assumption.

**Decision (lead): wasm, with `wasmi`.** `wasmi` is a small, pure-Rust
interpreter with fuel metering, already in the dependency cache; `wasmtime`
is the upgrade if throughput ever demands it. A native job is optional: an
app without `snapback/native/` never pays for it, and the loop bar and the
bakeoff are untouched.

## 3. The authoring surface

```q
job rescore(): native                    -- the body is snapback/native/, in Rust
schedule rescoreEvery every 5m: rescore  -- a schedule fires it like any job
```

`native` where a job's body would be. Arguments are allowed (`periodStart:
time, periodEnd: time` for a schedule). Only a job can be native; the word on
a query or mutation is refused with the rewrite.

`snapback/native/` is a Cargo package the app owns — its own `[workspace]`,
`crate-type = ["cdylib"]`, a dependency on `snapback4-native` (the guest
SDK) — and a file that names its jobs:

```rust
use snapback4_native::{Ctx, Chunk, Next, Order, Result, from_row, json};

mod schema { include!("../../generated/native.rs"); }   // written by `check`
use schema::*;

snapback4_native::jobs! { rescore }

fn rescore(ctx: &Ctx, chunk: &Chunk) -> Result<Next> {
    let page = ctx.scan(tables::POSTS, indexes::posts::BY_ID, &[], Order::Asc, 100, chunk.state.as_ref())?;
    for row in page.rows {
        let post: Posts = from_row(row)?;
        let votes = ctx.maintained(maintains::POST_SCORE, &[json!(post.id)])?;
        let age_hours = (chunk.now - post.at) as f64 / 3_600_000.0;
        let score = (votes as f64 * 10.0 - age_hours.powf(1.5)).round() as i64;
        ctx.upsert_by(tables::RANKED, indexes::ranked::BY_POST, &[json!(post.id)], row_of(&Ranked { id: String::new(), post_id: post.id, score, at: post.at })?)?;
    }
    Ok(match page.next { Some(state) => Next::Again(state), None => Next::Done })
}
```

`check` compiles `snapback/*.q`, writes `snapback/generated/native.rs` — a
constant per table, index and maintain, and a `serde` struct per table with
the columns as fields — then runs `cargo build --release --target
wasm32-unknown-unknown` on the package and copies the module to
`snapback/generated/native.wasm`. It then loads the module and refuses if a
native job the schema declares is not one the module implements. `dev`
rebuilds on every save under `snapback/`, `.q` or Rust. `deploy` copies the
module into the release beside the source; `serve` loads it. `run <job>`
runs it here and now, as the system.

## 4. The contract between the host and the module

**One import.** `env.sb4_call(ptr, len) -> i64`: a JSON request in the
module's memory; the host answers with JSON it writes into memory the module
allocates (`sb4_alloc`), packed as `(ptr << 32) | len`. Every request is
`{ "op": …, … }`; every answer is `{ "ok": … }` or `{ "error": <refusal> }`
in the engine's own envelope.

**Four exports.** `sb4_alloc(len) -> ptr`, `sb4_free(ptr, len)`,
`sb4_jobs() -> packed JSON array of names`, and `sb4_run(ptr, len) ->
packed JSON` taking `{ "job", "args", "state", "now" }` and returning
`{ "done": true }`, `{ "again": <state> }` or `{ "error": { "code",
"message" } }`. The SDK's `jobs!` macro writes all four into the app's
crate so the linker keeps them.

**The operations**, each the interpreter's own read or write on the
chunk's `Runner`:

| op | what it is in the interpreter |
| --- | --- |
| `get { table, id }` | a point read by id; null when absent or expired |
| `lookup { table, index, key }` | a point read by a unique key, or a maintain's group (`{ id, …by, value }`) |
| `scan { table, index, prefix, order, first, after }` | a page in index order, `after` a suffix position; `next` is the last row's suffix when the page filled |
| `mint {}` | an id from the chunk's context |
| `insert { table, row }`, `insert_if_absent { table, row }` | the write statements, rules passing for the system, validation, constraints, maintains and partition events applying |
| `update { table, id, patch }`, `upsert { table, id, row }`, `delete { table, id }` | the same |
| `log { message }` | a line the server prints with the job's name |

Values cross as plain JSON typed by the schema on the way in (`row_from_json`,
`column_from_json`), so a wrong-typed field is `E_INPUT` naming it.

**One chunk per call, one transaction per chunk.** `sb4_run` runs inside
one SQLite transaction under `Ceilings::job()` (16,384 rows examined, 8,192
rows written, the rest as a mutation). The module returns `again` with a
state of its own choosing — the last suffix of a scan, a phase name — and
the engine commits the chunk's rows and events, stores the state in the job
row, and calls again next turn with that state; `done` ends the job. This
is exactly how a Quarry `chunk` resumes by its cursor: a chunk is wholly
done or not started, a crash resumes at the next one, and the maintenance
thread interleaves other work between chunks.

**Refusals park the job.** The first refusal a host operation returns
(`E_BOUND`, `E_CONSTRAINT`, `E_INPUT`, …) is sticky: every later call in
that chunk returns it again, the chunk rolls back to its savepoint, and the
job parks with `CODE: message`, as a Quarry job does. Out of fuel is
`E_BOUND` on steps; a trap — a panic in the module, an unreachable — parks
the job as `E_NATIVE_TRAP` with the panic's text, which the SDK's panic
hook sends through `log` before the abort.

**Fuel.** A chunk gets 100,000,000 units of `wasmi` fuel, roughly
instructions; it is the native job's step ceiling.

**Determinism.** The module has no clock, no randomness and no I/O; `now`
comes from the host as it does for Quarry; the interpreter is deterministic.
A native job therefore runs under the simulator's virtual clock like any
job (`Engine::install_native`), and its first refusal is reproduced there.

**The program hash.** A native job's `Program` carries `native: true` and
an empty body; the digest a queued run is checked against covers the
declaration, not the module's bytes, so rebuilding the module does not park
runs queued before it — the chunk state's format is the module's own.

## 5. Diagnostics

| code | family | when |
| --- | --- | --- |
| `E_NATIVE` | schema | `native` on a query or mutation; a native job declared with no `snapback/native/Cargo.toml`; a job the module does not implement (the message lists what it does); a module that does not load |
| `E_NATIVE_TOOLCHAIN` | store | `cargo` is not on `PATH`, or the `wasm32-unknown-unknown` target is not installed; the rewrite is the `rustup` line |
| `E_NATIVE_BUILD` | schema | `cargo build` failed; the message is the tail of its output |
| `E_NATIVE_TRAP` | bound | the module trapped in a chunk (a panic, an unreachable, an out-of-bounds memory access); the job is parked with the reason |

`doctor` prints a `native` line: the jobs declared, whether the module is
built, and whether the toolchain is present. `check --cost` says of a native
job that its reads and writes are metered per chunk. `snapback4 guide native`
is the card.

## 6. What this does not do

- **No network from a native job.** An LLM ranker, a webhook, an email: the
  external worker of LLP 3000.004 §6.5, or the effects host once measured
  (LLP 2000.000 §10). A native job that needs a model's opinion reads it
  from a table the worker wrote.
- **No native queries or mutations.** Reads a client can call stay Quarry,
  because the certificate — shape, uniformity, completeness class,
  prediction eligibility — is computed from Quarry's structure and a
  device predicts Quarry, not wasm. A native job runs on the server only.
- **No device-side native jobs yet.** The same Rust over `Rows` on the
  device is the natural next step after the native module lands; it is not
  in this landing.
- **No `snapback4-native` on crates.io yet.** The SDK is a path dependency
  inside this repository; an app outside it needs the crate published. That
  is a publication step, not a design question.
- **No raw SQL, no `Rows` handle, no second transaction.** The module sees
  the store through the interpreter's own operations and nothing else.
- **Nothing off the not-doing list beyond the one Moves line.** Ranked and
  vector search, effects execution and an embedded JS engine stay where
  they are.

**The proof, as the tests state it.** The scores land as computed (marc's
post 20, the model's 2, bob's −10 at age 0) and the ordinary `home` query
serves them in order with the viewer's own vote beside each row; every
device holds the public `ranked` partition, and a second rescore after new
votes updates the three rows in place. Over 250 seeded posts the job runs
as three chunks — `running` after 100 and 200 rows written, `done` at 250 —
the state persisted in the job row between them, the oldest post scoring
`−round(249^1.5)`. A unique clash parks the job with `E_CONSTRAINT` and the
chunk's first row is rolled back with it; a panic parks it as
`E_NATIVE_TRAP: job boom trapped: … panics on purpose`; a schedule fires
it; without a module it parks saying `snapback4 check` builds one; `native`
on a mutation is refused at parse. The write past the ceiling — 9,000
inserts against 8,192 — parks with `E_BOUND` and rolls back too, ignored
by default because the debug host spends about twenty seconds on its JSON.

**Fuel, measured** (debug host build, `SNAPBACK4_FUEL_PROBE=1`): one host
call costs about 90,000 units — the JSON each way, interpreted; 8,192
inserts spent 750,585,308 in 22 s; a 100-post rescore chunk (five calls a
post) 46 M in 1.3 s; three posts 2 M in 58 ms. The ceiling is 2,000,000,000
per chunk so the row ceilings bind first. A binary protocol is the next
lever should the JSON per call ever be the cost.

**The CLI, on the LLP 3000.004 sketch with the job native.** `check` 13.1 s
cold (cargo compiling the guest's `serde_json`), 95 ms warm, a 105,000-byte
module; `run rescore` three rows; `home --as bob` in score order with
`seen` and `mine`; `doctor` naming the job, the module and `cargo 1.94.0`;
`deploy` copying `native.wasm` into `releases/1/snapback/generated/` and
`serve` loading it (the `/schema` answer carries `"native": true` on the
job).

**Costs, as stated in the summary.** `check` runs `cargo` only when the
schema declares a native job; the binary carries `wasmi` (the `native`
feature, default on, off for the device crate). Neither the loop bar nor
the bakeoff instrument sees either.

## Non-claims

- This document changes no Quarry semantics for queries, mutations or
  Quarry jobs; a schema without `native` compiles and runs exactly as before.
- It makes no performance claim; the fixture proves shape and bounds, and
  the Interview spike (LLP 3000.004 §8) measures.
- It does not decide the effects host; a native job is not an effect.
