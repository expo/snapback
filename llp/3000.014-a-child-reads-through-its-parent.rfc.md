## Summary

Most rows in an application belong to a parent. A comment belongs to an
issue, which belongs to a project, which belongs to an organization. A
reaction belongs to a message, which belongs to a chat. The question every
rule answers for such a row is the same: *may this viewer read the parent?*

Quarry cannot say that today. A read rule compares the row's own columns with
`viewer` and probes other tables for existence. A child therefore copies its
parent's audience key by hand (`comments.org`, `reactions.chat`), and the
application keeps the copy honest. That has three costs:

- **an integrity hole** when the author forgets the insert probe that ties the copy to the parent;
- **notes that cannot be fixed**, because the compiler cannot see that `.issue` determines `.org`;
- **a second spelling of the model**, when SQL and Convex put the relationship in the rule.

Two rounds of blind review cut the proposal down to this:

```quarry
table comments:
  issue: issues
  author: principal
  body: text
  read through .issue
  delete <- .author = viewer
```

`read through .issue` makes the comment readable exactly when its issue is.
It is the table's whole read rule.

It rests on one lifetime rule, the one SQL's foreign keys give by default:
**a child lives within its parent**. A parent with a live child cannot be
deleted, and a child expires no later than its parent. As a result:
- no child ever outlives its parent;
- a reused parent id never meets an old child;
- the parent's rule inputs, captured into the child when it is inserted, always equal the live parent's.

The capture uses the recorded-field path that maintained views already use.
Everything the engine derives from a local rule then derives from it: exact
sync, device evaluation, and readable counts.

## 1. Evidence

- **Hands-on, 2026-09-24.** An issue tracker (orgs, members, issues, comments, labels) on the 0.4.1 candidate. Every child carries `org`. `comments: count comments by issue` draws `N_MAINTAINED_COLUMN_DISCLOSURE`, which does not clear after adding the integrity probe and `immutable`. `issueLabels where .issue = id first 20 by .label` draws `N_NEVER_COMPLETE`, whose rewrite asks the author to add `.org = i.org`, a fact the engine could know.
- **Clique.** The target program and calibration #19's builder both carry `chat` on messages, members, receipts, typing and reactions. `receipts.chat` is justified only by `insert <- created messages[.message]`: the receipt is created in the same mutation as the message, and the mutation sets the chat. The integrity lives in application code. The builder also copied each message's deadline into its receipts by hand, so that they would expire together.
- **Workroom** (LLP 3000.009 §10.1). Organization → project → task → comment → attachment, with tenancy "enforced by the backend", is exactly this shape, four levels deep.

## 2. The form

```quarry
table issues:
  org: orgs
  title: text
  immutable org
  read <- exists members[.org, viewer]
  insert <- exists members[.org, viewer]

table comments:
  issue: issues
  author: principal
  body: text
  read through .issue
  insert <- .author = viewer
  delete <- .author = viewer
```

1. **`read through .ref` is the whole read rule.**
   - `.ref` is one required, immutable reference column naming the parent by id, with no default.
   - No other read rule may be declared. A narrower child (a private comment only its author reads) keeps today's hand-copied form. Narrowing conjuncts are not in this revision (§9).
   - A service disjunct is allowed: `read through .issue or viewer = 'service:search'`. It keeps its existing server-only meaning and is stripped from the device audience as today.
2. **The meaning.** The child is readable by exactly the viewers who can read its parent now. Given §3, that is the same as the parent's rule evaluated over the inputs the child captured at insert (§4).
3. **Writes inherit it.** An insert of a child requires two things of its parent: it is **live** (present and not expired), and its read rule **admits the writer**. That covers a plain insert, an upsert's insert arm, and `insert … if absent`. The requirement is implicit and stated on the rules card; the child's `insert` rule adds conditions to it. Updates and deletes do not read the parent, because the reference is immutable and the capture never changes.
4. **Chains.** A parent that itself declares `read through` passes on its own captured inputs: the child copies the parent's stored captures, never walking to a live grandparent. A cycle is refused.

`exists t[.ref]` and `created t[.ref]` keep their meanings.

## 3. A child lives within its parent

Two rules make every child's captured inputs equal to its live parent's:

1. **No delete under a live child.** Deleting a parent that some live child row references through `read through` is refused. The deletion's refusal table is in §6. The application deletes the children first (a bounded loop or a self-chunking job), then the parent. Cascading deletion is a referential action, not in this revision (§9).
2. **A child expires no later than its parent.** If the parent table declares `expire at .col`, then:
   - the parent's expiry column must be immutable;
   - the child captures it;
   - the child's effective lifetime ends at the earlier of its own expiry, if it declares one, and its parent's.

   When the parent's lifetime ends, its children's end at the same instant: on the server, on devices, and before any sweep. Expiry machinery treats the captured instant exactly as an authored `expire at` column: reads skip the row, unique checks skip it, the sweep removes it, and maintained views over it are expiring aggregates.

**What follows.**
- A parent that is gone, whether deleted or expired, has no live children.
- A new parent inserted with a reused id therefore starts with none. Old, expired children that the sweep has not yet removed are invisible to every read, rule, unique check and live aggregate.
- Because live children never belong to a dead parent, the incarnations of revision 2 are withdrawn.
- Captured inputs are immutable on the parent (§4), so a live child's captures equal its live parent's fields.

## 4. The capture

A table that declares `read through .ref` gets hidden, engine-owned fields on the existing recorded-field path. They are:
- stamped at insert;
- stored with the row image;
- stripped from query rows, `*` shapes and generated types;
- refused in any payload (`E_RECORDED_FIELD`).

1. **What is captured.**
   - Every parent field that the parent's read rule reads, with every conjunct included. Probes stay live: `exists members[.org, viewer]` becomes `exists members[.$issue.org, viewer]`, evaluated against the current `members`.
   - The parent's expiry instant, when the parent expires.
   - The parent's own captures, in a chain.
2. **Captured parent fields must be immutable** on the parent. That covers every column its read rule reads and its expiry column. Each missing `immutable` is a refusal whose rewrite is the line to add.
3. **Captures are total.** A committed child always has every capture, because an absent or expired parent refuses the insert before anything is stamped (§6). `audience_binding` therefore treats a captured prefix as a required group key, like an authored required column.
4. **Order in the writing transaction**, the same on every insert path and on server and device:
   1. refuse client values for hidden fields;
   2. reserve the capture's fixed charge: one parent point read, plus the parent rule's static probe allowance. It depends on nothing about the parent. No hit-only heap charge is added;
   3. resolve the parent **live**: same transaction, not expired, including a parent inserted earlier in the same mutation;
   4. if it is absent or expired, refuse (§6), and never evaluate the rule over nulls;
   5. stamp the captures;
   6. evaluate the parent's rule over them for the writer, then the child's `insert` rule.
5. **The dependency identity** is:
   - the parent's read rule, expanded;
   - the captured fields' types, optionality and defaults, and the parent's expiry column;
   - the parent's own captures;
   - the child's reference binding: its target table, its type, and the refusal of a default.

   `adopt` compares it between generations. When it changes, activation recaptures (§7). For this kind of capture only, recapture overrides the recorded path's "a stored value is never re-resolved". Public attribution paths keep that rule.

## 5. What derives from the capture

- **Sync.** Only exact admission applies. The child syncs when its substituted rule, after the service strip, is exactly one of the three invertible forms: `allow`/`public`, `.col = viewer`, or one `exists t[.cols, viewer]`, with `grant_guard` unchanged. A declared `sync to` must equal that inference. Otherwise the child is server-read, and `check` says why. Every recipient can read the parent, so the captures travel on the sync image to viewers entitled to them.
- **Cursors** carry the child's own sort keys and id, and the caller's parent id where the read pins it. They never carry captured inputs. Because a reused id meets no live child, continuation needs no incarnation.
- **Reads pinned by the parent.** `comments where .issue = x first 20 by .at` resolves the parent `x` once, at a fixed, reserved charge. The **parent resolver** has four outcomes. The server and the device share it:

  | Outcome | Page |
  |---|---|
  | **found, readable**: live, and the viewer's verdict on its rule is true | Every live child of `x` has captures equal to `x`'s fields, so one verdict decides every row. The page is complete |
  | **found, unreadable** | Empty and complete |
  | **covered absent**: the server; or a device that holds `x`'s partition fully | Empty and complete. The charge is the same as for unreadable |
  | **unknown**: a device horizon miss, an online-only parent, or an unknown membership probe | Not complete. The read takes the server fallback of LLP 3000.013 §12.2 |

  A predicted parent is a local hit that does not make the page complete: the server's children of the committed row are not held. The resolver registers the parent dependency in residency, subscriptions and expiry invalidation.
- **Reads not pinned by the parent** (`comments where .author = viewer`) evaluate the substituted rule per row over its captures. That is the ordinary path, with its existing completeness class.
- **Aggregates.**
  - A maintained view grouped by the reference (`count comments by issue`) derives its read rule from the parent's, because the captures are a function of the group key. It is served by key: `commentCounts[x]` uses the parent resolver, and an absent, expired, unreadable or unknown parent reads exactly as the page does. An unbounded scan of such a view is refused in this revision, because visiting other tenants' groups would disclose their number.
  - A maintained **column** on the parent (`issues.comments: count comments by issue`) needs no incarnation rule. Its source cannot expire (LLP 3000.013), so a child whose parent expires cannot feed it, and a parent with live children cannot be deleted. A new parent with a reused id is therefore born with a total of zero. `N_MAINTAINED_COLUMN_DISCLOSURE` is retired for exactly this shape: the column counts children whose read rule is the parent's own.
- **Devices and prediction.**
  - A device evaluates the substituted rule over the captures it received.
  - A predicted child insert captures through the recorded path's coverage check: a live, covered parent in the current partition, or a parent predicted in the same pending chain whose settlement or refusal replays the child. A retained-only, expired or unheld parent queues the call without a row.
  - Upsert and `insert … if absent` on such a child stay non-predictable in this revision.
- **Revocation** follows each table's own leave policy and horizon. "The same instant" is server evaluation only.

## 6. Refusals and costs

Every refusal below costs the same fixed, reserved charge, whether the parent exists or not.

| Write | Parent absent or expired | Parent present, writer cannot read it | Parent readable, child rule refuses |
|---|---|---|---|
| insert, `insert … if absent` | `E_RULE` | `E_RULE` | `E_RULE` |
| upsert (target row absent, so the insert arm runs) | the hidden-target shape, `NOT_FOUND`, with its meter normalization | `NOT_FOUND` | `NOT_FOUND` |
| delete of a parent with live children | not applicable | the parent's ordinary hidden-target refusal | `E_PARENT_HAS_CHILDREN`, naming the child table (the deleter can read the parent, and so every child) |

The delete check probes each child table's live index once, at a fixed charge per child table.

## 7. Activation

Adding `read through` to a table, or changing a capture's dependency identity, captures **inside activation**:
- scan **child rows**, never parents;
- resolve each row's parent live, in dependency order: parents before children, chains level by level;
- stamp or recapture;
- rebuild affected indexes and aggregates;
- publish one generation that makes devices reacquire.

Captures are engine columns, so the generation's projection keeps them. Activation fails by table and count, publishing nothing, when any child row:
- has a missing or expired parent;
- has a hand-copied audience column that disagrees with its parent's.

A child whose own expiry is later than its parent's is not an error: its effective lifetime is the earlier of the two. Activation reports how many rows that shortens.

Removing `read through` drops the captures the same way. No self-chunking job is involved.

## 8. Increments

1. **Server.** The form, the lifetime rules, the capture and its write order, the refusal table, and per-row evaluation. The parent resolver and parent-pinned pages. Activation.
2. **Sync and devices.** Exact admission. Captures on the sync image. The device resolver's four outcomes. Predicted inserts through recorded coverage.
3. **Aggregates.** Keyed views, and the retired maintained-column note for the unnarrowed shape.
4. **Chains and the guide.** The rules card leads multi-level apps with `read through`. The issue tracker and Clique's receipts become card examples.

## 9. Not in this revision

- **Narrowing** (`read through .issue and .author = viewer`). A child conjunct needs per-row verdicts inside a parent-pinned page, and its own sync analysis.
- **Referential actions**: cascading deletion, and setting a nullable reference to null.
- **Mutable captured fields.** Moving an issue between orgs would have to recapture every descendant.
- **Naming the parent by a non-id unique key**, and **nullable references**.
- **Scanning a view grouped by the reference.**
- **Predicted upsert and `insert … if absent`** on a child.

## 10. How we will know

- **The issue tracker.** It compiles with no audience notes and no `org` on children. Pages pinned by an issue are complete. `issues.comments` is readable by the issue's audience without a note. Absent and unreadable parents refuse identically in code and meter. Deleting an issue with comments refuses with `E_PARENT_HAS_CHILDREN`.
- **A four-level fixture** (org → project → task → comment). Chains carry a middle conjunct (`and not .archived`, with `archived` immutable). A device predicts a comment on a held, covered task, and queues one on an unheld task. A device page pinned by an unheld task is incomplete and falls back to the server.
- **Lifetime.**
  - A child of an expiring parent disappears at the parent's instant, on the server and on a device, before any sweep.
  - A reused parent id starts with no children, a zero count, and pages that show only its own children.
- **Clique.** Receipts and reactions declare `read through .message` and drop `chat` and their copied deadlines. Their partitions and answers match the flattened program's. The unread count groups by `.message.chat`, a recorded path.

## Non-claims

This RFC does not make Quarry's rules general joins. A rule still reads one
row and probes by key. The capture makes a parent's rule a child's rule
without making the rule non-local. The lifetime rule makes the capture true
for as long as the child lives.
