# LLP 3000.014: A child reads through its parent — inherited audiences

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 — Quarry rules (parser, binder, rule IR), the write path, sync audience inference, maintained-view readability, the planner's completeness classes, devices and prediction, adoption
**Author:** Claude Opus 5.5 (for Charlie Cheever)
**Date:** 2026-09-24
**Revised:** 2026-09-24 (both design reviews NOT READY; §10 records the narrower design for revision 2); 2026-09-24 (initial)
**Related:** [LLP 3000.013](./3000.013-quarry-states-intent.rfc.md) (§12 records the 0.4.1 forms), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) (§6.6: the audience is the read rule), [LLP 3000.007.001](./3000.007.001-maintained-columns.rfc.md), [LLP 3000.009](./3000.009-general-purpose-backend.rfc.md) (the Workroom brief)

## Summary

Most rows in an application belong to a parent. A comment belongs to an issue, which belongs to a project, which belongs to an organization. A reaction belongs to a message, which belongs to a chat. The question every rule answers for such a row is the same: *may this viewer read the parent?*

Quarry cannot say that today. A read rule compares the row's own columns with `viewer` and probes other tables for existence. A child therefore copies its parent's audience key by hand (`comments.org`, `reactions.chat`), and the application keeps the copy honest. Three costs follow:

1. **An integrity hole.** Nothing makes `comments.org` equal the issue's `org` unless the author adds an insert probe (`exists issues[id = .issue, org = .org]`) and `immutable` lines. Without it, a member of org A can file a comment against an org B issue that A's members read and B's issue count includes.
2. **Notes that cannot be fixed.** The compiler cannot see that a child's `org` is determined by its `issue`. A page pinned by `.issue` is `N_NEVER_COMPLETE`, and a maintained count of comments on issues carries `N_MAINTAINED_COLUMN_DISCLOSURE` even when the probe establishes the invariant. A hands-on issue tracker drew five notes in 40 lines.
3. **A second spelling of the model.** Supabase says `using (exists (select 1 from issues i where i.id = issue_id and is_member(i.org_id)))`. Convex checks the parent in each function. Both put the relationship in the rule. Quarry makes the author flatten it.

Proposal: one rule term, `readable t[.ref]`, meaning "the row `.ref` names in `t` is readable by this viewer now". The engine keeps rules local by **inheriting the parent's audience columns**: at insert it copies the parent's rule inputs into hidden, immutable columns of the child, and it evaluates the parent's rule over that copy. Sync audiences, maintained-view readability, completeness classes and device prediction all derive from the copy exactly as they derive from an authored column today. The child's audience is its parent's audience, with no probe and no note.

## 1. Evidence

- **Hands-on, 2026-09-24.** An issue tracker (orgs, members, issues, comments, labels) on the 0.4.1 candidate. Every child carries `org`. `comments: count comments by issue` draws `N_MAINTAINED_COLUMN_DISCLOSURE`, which does not clear after adding the integrity probe and `immutable`. `issueLabels where .issue = id first 20 by .label` draws `N_NEVER_COMPLETE`, whose rewrite asks the author to add `.org = i.org`, a fact the engine could know.
- **Clique.** The target program and calibration #19's builder both carry `chat` on messages, members, receipts, typing and reactions. `receipts.chat` is justified only by `insert <- created messages[.message]`: the receipt is created in the same mutation as the message, and the mutation sets the chat. The integrity lives in application code.
- **Workroom** (LLP 3000.009 §10.1). Organization → project → task → comment → attachment, with tenancy "enforced by the backend", is exactly this shape, four levels deep.

## 2. The term

```quarry
table issues:
  org: orgs
  title: text
  immutable org
  read <- exists members[.org, viewer]
  insert <- exists members[.org, viewer]

table comments:
  issue: issues
  author: principal
  body: text
  read <- readable issues[.issue]                         -- readable exactly when its issue is
  insert <- .author = viewer and readable issues[.issue]
  delete <- .author = viewer
```

- `readable t[.ref]` takes one reference column of the child whose type is `t`. `.ref` names `t` by id. A full declared unique key of `t` is accepted, following LLP 3000.013 §2.2.
- It may appear in `read`, `insert`, `update` and `delete` rules, combined with `and`, `or` and `not` like any other term. In an update rule, `old.` and `next.` select which image names the parent.
- Its meaning: the parent row exists, and its **read rule** admits the viewer. That is the parent's rule, not its existence (`exists t[..]` keeps its existence meaning).

## 3. Inherited audience columns

The parent's read rule reads some of its own columns: its **audience columns** (for `issues`, `org`). The term is realized by copying them:

1. **Declaration.** For each child reference used under `readable`, the binder adds hidden columns `$issue.org` (one per parent audience column, typed as in the parent). They are not in the child's generated type. They are immutable, and so is the reference column itself.
2. **Insert.** The write reads the parent by id, with system authority and inside the write's meter, and copies its audience columns into the child's hidden columns.
   - An absent parent refuses as the child's rule would: `NOT_FOUND` when the writer cannot see the parent, following the rules card's hidden-target table.
   - A write-rule `readable` term is evaluated over the copy, which is the same fact.
3. **Read.** The child's rule is the parent's rule with every parent column replaced by its copy. `read <- readable issues[.issue]` evaluates as `exists members[.$issue.org, viewer]`. It is a local rule over the child's own columns, so everything LLP 3000.007 and 3000.013 derive from a local rule applies unchanged.
4. **Chains.** A parent whose own rule uses `readable` has copies of its own. The child copies the parent's *effective* inputs, which are the root's audience columns (`$message.$chat.id` collapses to `$message.chat`). Cycles are refused.

**Requirements, each a refusal with a rewrite:**

- **The parent's audience columns are immutable.** A mutable audience column would leave stale copies. Rewrite: `immutable org` on the parent. The alternative, re-copying on update, is left out of this RFC (§8).
- **The child's reference column is immutable.** Moving a comment between issues is a delete and an insert.
- **The parent's read rule is local.** It is built from `=`/`!=` over columns, `viewer`, `exists` and `readable`. This is the rule class that already admits sync. A parent whose rule is `allow` or `public` makes the child public.

## 4. What derives from the copy

Each item below is the existing derivation, applied to hidden columns as it is to authored ones.

- **Sync.** `sync` with no target infers the audience from the effective rule (LLP 3000.007 §6.6). `comments` inherits `sync to members[.$issue.org]` when `issues` has `sync to members[.org]`. The horizon is the child's own.
- **Maintained readability.** `comments: count comments by issue` is readable by the parent's audience. The count is keyed by `issue`, the copy is a function of `issue`, and the source rows' audience equals the parent's by construction. `N_MAINTAINED_COLUMN_DISCLOSURE` no longer fires for this shape. A view grouped by a key that does not determine the copy keeps today's analysis.
- **Completeness.** The copy is functionally dependent on the reference column. So pinning `.issue` decides the rule with one verdict, and `comments where .issue = id first 20 by .at` is complete. The planner may add the copy to synthesized indexes after the reference column, or treat it as determined.
- **Devices.** Hidden columns travel in the row image like any column, so a device evaluates the rule locally.
  - A predicted insert copies from the parent row it holds.
  - A parent the device does not hold makes the insert non-predictable, which is today's "reads beyond the partition" class, with its existing `N_NOT_PREDICTABLE` wording.
- **Search, expiry, retained history.** No change. They see an ordinary local rule.

## 5. Semantics worth stating

- **Copy semantics.** A child keeps the audience it inherited at insert. Because the parent's audience columns are immutable, the copy is always equal to the parent's current value. If the parent is deleted, the child keeps its audience: an orphan comment stays readable by the org. That is the flattened model's behavior today. Removing children is a separate referential action (candidate in `issues/20260924-snapback4-sql-parity-candidates.md` §2).
- **Membership changes** act through the shared rule. A member who leaves the org stops reading its issues and their comments in the same instant, on the server and at the next sync on devices. Retained history applies to both, as declared.
- **Disclosure.** None beyond the parent's rule. The child is readable exactly by the parent's audience, and the copy is invisible. Probing: a writer learns whether a parent exists and is readable, exactly as `require exists` or an insert probe tells them today.

## 6. Adoption

- **A new table** with `readable` needs nothing.
- **An existing table gains `readable`.** Adoption fills the copies from each row's parent in engine-owned, self-chunking background work (LLP 3000.013 §5.2), and the table becomes readable under the new rule when the fill completes. A row whose parent is absent is refused by name, with the count, and adoption stops. The author deletes the orphans or keeps the old rule.
- **Removing `readable`** drops the hidden columns.

## 7. Increments

1. The rule term, hidden columns, the insert copy, local evaluation on the server and devices, and the requirement refusals.
2. Sync inference and maintained-view readability through the copy. Retire the notes the copy makes unnecessary.
3. Completeness and planner use of the functional dependency.
4. Chains, adoption fill, and the guide: the rules card leads multi-level apps with `readable`, and the issue tracker becomes a card example.

## 8. Not in this RFC

- **Mutable audience columns.** Moving an issue between orgs would have to re-copy every descendant: unbounded background work with an interim audience. Refused for now.
- **Rules that read a parent's non-audience columns** (`readable` plus "and the issue is open"). Write `readable issues[.issue]`, then state the extra fact on the child, or as a named probe on the parent.
- **Referential actions** (`on delete cascade`) and **existence checks without readability** (`exists t[.ref]` stays).

## 9. How we will know

- **The issue tracker.** The program compiles with no audience notes and no `org` on children. Its pages pinned by parent are complete, and its counts are readable by the parent's audience.
- **A four-level Workroom-shaped fixture** (org → project → task → comment). Tenancy probes across orgs are refused on the server and on devices, and a device predicts a comment on a held task.
- **The Clique target** drops `chat` from receipts and reactions with identical partitions and answers.

## 10. Review record

Both blind design reviews returned **NOT READY** (2026-09-24):
[Astra max](./reviews/3000.014-a-child-reads-through-its-parent.astra.md) and
[Grok 4.7 xhigh](./reviews/3000.014-a-child-reads-through-its-parent.grok.md).
They agree on the defects:
- **Parent lifetime and identity.** A deleted parent recreated with the same id, an expired parent, and a changed non-audience unique key all break both the readability claim and the functional dependency.
- **Schema interpretation.** Defaults and changed parent rules shift a parent's audience while the copies stay unchanged.
- **Disclosure.** Copied parent inputs travel to wider child audiences, through sync and cursors.
- **Boolean composition.** Mandatory capture creates an existence oracle.
- **Completeness.** Proof needs the whole rule, not only the audience columns. A functional dependency does not supply the value a prefix verdict evaluates.
- **Prediction.** It needs live, covered parents, not held ones.
- **Adoption.** Filling copies with a §5.2 job is not an activation protocol.

Both propose the same smaller first version:
- extend the recorded-field path that maintained columns already use;
- `readable t[.id]` as the whole read audience, plus conjuncts that only narrow;
- stamp the parent's substituted inputs and its incarnation inside the writing transaction;
- sync only for the three invertible forms;
- aggregates derive a rule only when the stored inputs are a function of the group key;
- fill inside activation, parents before children.

**Status: revision 2 pending on that narrower design.** Nothing is implemented from this text.

## Non-claims

This RFC does not make Quarry's rules general joins. A rule still reads one row and probes by key. The copy is what makes a parent's rule a child's rule without making the rule non-local.
