# LLP 3000.014: A child reads through its parent — captured audiences

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 — Quarry rules (parser, binder, rule IR), the write path and recorded fields, sync audience inference, maintained-view readability, the planner's completeness classes, devices and prediction, activation
**Author:** Claude Opus 5.5 (for Charlie Cheever)
**Date:** 2026-09-24
**Revised:** 2026-09-24 (revision 2: the narrower design both reviews proposed — a captured, incarnation-bound audience on the recorded-field path; `readable` only as a top-level read conjunct; sync only for the invertible forms; parent-pinned reads resolve the live parent; capture inside activation. §10 records each finding's disposition); 2026-09-24 (both design reviews NOT READY); 2026-09-24 (initial)
**Related:** [LLP 3000.013](./3000.013-quarry-states-intent.rfc.md) (§12 records the 0.4.1 forms), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) (§6.6: the audience is the read rule), [LLP 3000.007.001](./3000.007.001-maintained-columns.rfc.md), [LLP 3000.007.003](./3000.007.003-the-engine-writes-derived-data.rfc.md) (§3.2: recorded paths), [LLP 3000.009](./3000.009-general-purpose-backend.rfc.md) (the Workroom brief), [LLP 4000](./4000-snapback5.rfc.md) §3.3 (this revision is the design of record for `through`)

## Summary

Most rows in an application belong to a parent. A comment belongs to an
issue, which belongs to a project, which belongs to an organization. A
reaction belongs to a message, which belongs to a chat. The question every
rule answers for such a row is the same: *may this viewer read the parent?*

Quarry cannot say that today. A read rule compares the row's own columns with
`viewer` and probes other tables for existence. A child therefore copies its
parent's audience key by hand (`comments.org`, `reactions.chat`), and the
application keeps the copy honest. That has three costs:

- **an integrity hole**, when the author forgets the insert probe that ties the copy to the parent;
- **notes that cannot be fixed**, because the compiler cannot see that `.issue` determines `.org`;
- **a second spelling of the model**, where SQL and Convex put the relationship in the rule.

Proposal, narrowed after two NOT READY reviews:

```quarry
table comments:
  issue: issues
  author: principal
  body: text
  read <- readable issues[.issue]
  delete <- .author = viewer
```

`readable issues[.issue]` is the **whole read audience** of the row, plus
conjuncts that only narrow it. When a row is inserted, the engine **captures**
into hidden fields of the child, in the writing transaction:
- the parent's rule inputs;
- the parent's **incarnation**.

Capture uses the recorded-field path that maintained views already use. Reads
evaluate the parent's rule over the captured fields, so the child's rule stays
local. Everything the engine derives from a local rule (sync, device
evaluation, readable aggregates) derives from the capture. Where the capture is
not enough, the derivation is refused rather than guessed. A page pinned by a
parent's id resolves the live parent once and reads its current incarnation's
children, so it is complete.

## 1. Evidence

- **Hands-on, 2026-09-24.** An issue tracker (orgs, members, issues, comments, labels) on the 0.4.1 candidate. Every child carries `org`. `comments: count comments by issue` draws `N_MAINTAINED_COLUMN_DISCLOSURE`, which does not clear after adding the integrity probe and `immutable`. `issueLabels where .issue = id first 20 by .label` draws `N_NEVER_COMPLETE`, whose rewrite asks the author to add `.org = i.org`, a fact the engine could know.
- **Clique.** The target program and calibration #19's builder both carry `chat` on messages, members, receipts, typing and reactions. `receipts.chat` is justified only by `insert <- created messages[.message]`: the receipt is created in the same mutation as the message, and the mutation sets the chat. The integrity lives in application code.
- **Workroom** (LLP 3000.009 §10.1). Organization → project → task → comment → attachment, with tenancy "enforced by the backend", is exactly this shape, four levels deep.

## 2. The term

```quarry
table issues:
  org: orgs
  title: text
  closed: bool default false
  immutable org
  read <- exists members[.org, viewer]
  insert <- exists members[.org, viewer]

table comments:
  issue: issues
  author: principal
  body: text
  read <- readable issues[.issue]
  insert <- .author = viewer
  delete <- .author = viewer
```

1. **Where it may appear.** `readable t[.ref]` is a top-level conjunct of a
   table's `read` rule. It may be combined with `and` only.
   - The other conjuncts narrow: `read <- readable issues[.issue] and .author = viewer`.
   - It never appears under `not`, and it is never a branch of `or`. Both are refused with `E_READABLE_POSITION`, whose rewrite names the two tables.
   - A service disjunct (`or viewer = 'service:…'`) keeps its existing meaning. It is stripped from the device audience exactly as today.
2. **What `.ref` is.** One **required, immutable** reference column of the child, typed `t`, naming the parent by its id.
   - A nullable reference is refused: a child with no parent has no audience to inherit.
   - Naming by another unique key is not in this revision (§8).
3. **What it means.** The row is readable exactly by the viewers who could
   read the parent **at the instant the row was inserted**, evaluated now:
   captured inputs and live probes. Membership changes act through the live
   probes. The parent's own later deletion or expiry does not change the
   child's audience (§5).
4. **Writes inherit it.**
   - Inserting a child (plain insert, upsert's insert arm, `insert … if absent`) requires the writer to be able to read the **live** parent, in addition to the child's own `insert` rule. This is implicit, is stated on the rules card, and needs no second spelling.
   - Updates and deletes do not read the parent: the reference is immutable and the capture never changes.

`exists t[.ref]` keeps its meaning (the row exists, with no rule applied).
`created t[.ref]` keeps its own meaning and is not an alias for `readable`.

## 3. The capture

A child table whose read rule contains `readable t[.ref]` gets hidden,
engine-owned fields on the existing recorded-field path. They are stamped at
insert, stored with the row image, stripped from query rows, `*` shapes and
generated types, and refused in any payload (`E_RECORDED_FIELD`).

1. **What is captured.**
   - **Incarnation.** Every table that is ever the target of a `readable` term gets a hidden engine field `$incarnation`, unique to each insertion of a row: a replacement of an expired row with the same id, and a re-insert after a delete, get new values. The child captures its parent's `$incarnation` as `$ref.incarnation`.
   - **Rule inputs.** The child captures every parent field its **substituted rule** reads. That is the parent's entire read rule, every conjunct included, with every parent column replaced by its capture (`$ref.org`, `$ref.closed`, …). Probes stay live: `exists members[.org, viewer]` becomes `exists members[.$issue.org, viewer]`, evaluated against the current `members` at read time.
   - **Chains.** When the parent's own rule contains `readable`, the substituted rule includes the parent's captures, copied from the parent row as stored. The engine never walks to a live grandparent. A cycle is refused.
2. **Captured parent fields must be immutable** on the parent. That covers every column the substituted rule reads, not only probe keys. Each missing `immutable` is a refusal whose rewrite is the line to add.
3. **Order in the writing transaction** (every insert path, server and device):
   1. refuse client values for hidden fields;
   2. reserve the capture's cost, a fixed allowance computed from the parent's declared field bounds, charged whether or not the parent is present;
   3. read the parent **live**: same transaction, not expired, including a parent inserted earlier in the same mutation;
   4. stamp the captures; an absent or expired parent stamps nulls;
   5. evaluate the implicit parent readability over the stamped image, then the child's `insert` rule.

   The written image is exactly the image the rules saw. An absent, expired or unreadable parent all refuse with the same `E_RULE` and the same meter charge. This is the insert-rule refusal the author sees today.
4. **The dependency identity.** A capture depends on:
   - the parent's read rule, expanded;
   - the captured fields' types, optionality and defaults;
   - the parent's own captures.

   `adopt` compares this identity between generations. When it changes, every descendant is recaptured inside the activation (§6). Changing a default on a captured field therefore recaptures, because a stored default is interpreted by the current schema.

## 4. What derives from the capture

Each derivation below is the existing one, applied to the substituted rule
over hidden fields. Where it would need more than the capture holds, it is
refused, and the reason is named.

- **Sync.**
  - `sync` with no target infers the audience from the substituted rule, only when it is one of the three invertible forms: `allow`/`public`, `.col = viewer`, or exactly one `exists t[.cols, viewer]`. Hidden fields map through `audience_binding` like authored ones. `grant_guard` is unchanged.
  - Any other substituted rule syncs only if the author names an audience that the rule implies. Otherwise the child is server-read, and `check` says which conjunct prevents inference.
  - Captures travel on the sync image only when the child's audience is contained in the parent's: `readable` is a required top-level conjunct, and the other conjuncts only narrow. Every device that receives a child could read its parent's captured inputs at capture time.
  - Hidden fields never enter cursors: a cursor carries only the child's own sort keys and id.
- **Pages pinned by the parent.** A read that pins `.ref = x` (`comments where .issue = x first 20 by .at`):
  1. resolves the live parent `x` once, with a fixed, reserved charge whether present or not;
  2. takes its `$incarnation` and rule inputs;
  3. evaluates the substituted rule once with those inputs;
  4. scans the index `(ref, $ref.incarnation, …)` for that incarnation.

  The page is complete: one verdict decides every row it can contain. Children of a deleted or expired parent are not in this page, even though they are readable through other reads (§5). An absent parent gives an empty, complete page. The planner synthesizes the index, and the certificate states the parent lookup.
- **Other reads** (`comments where .author = viewer`) evaluate the substituted rule per row over its captures. This is the ordinary non-uniform path, with its existing completeness class.
- **Aggregates.**
  - A maintained view grouped by the reference column (`count comments by issue`) groups internally by `(issue, $issue.incarnation)`, and stores the captures on its row.
  - Its read rule is derived only when the captures are a function of that group key, which holds by construction, and when the source's substituted rule has no narrowing conjunct. A narrower source rule (`readable issues[.issue] and .published`) keeps `E_MAINTAIN_READ_RULE` and `N_MAINTAINED_COLUMN_DISCLOSURE`: the count includes rows some readers cannot see.
  - A read of `commentCounts[x]` resolves `x`'s live incarnation as a page does.
  - A scan of such a view returns only groups whose incarnation is live. Each group returned or skipped costs one charged point read of its parent. A dead incarnation's group is removed when its last contribution is.
  - A view grouped by anything else keeps today's analysis.
- **Devices and prediction.**
  - A device evaluates the substituted rule over the captures it received.
  - A predicted insert captures through the recorded path's existing coverage check: a **live, covered** parent in the current partition, never a retained-only, expired or provisional-refused one. Otherwise the call queues without a row.
  - A parent predicted on the device has a provisional incarnation, and so do its predicted children's captures. The server's capture replaces both at settlement, as every predicted image is replaced.
  - Upsert and `insert … if absent` on such a child stay non-predictable in this revision: their absence proofs do not yet understand incarnations.
- **Revocation** follows each table's own leave policy and horizon. "The same instant" holds for server evaluation only. A device withdraws a child at the next sync when the child's table is `until revoked`. A child that retains delivered history is kept on the device, as that table declares.

## 5. Semantics worth stating

- **Captured, not live.** A child keeps the audience it captured. Because captured parent fields are immutable, the capture equals the parent's current fields while that incarnation lives. When the parent is deleted or expires, its children become orphans: still readable by the captured audience through reads that do not pin the parent, and absent from pages pinned by the parent's id. That second half is new. It is how a join through the parent behaves in SQL: no parent, no row. Removing orphans is a referential action, not in this revision (§8).
- **Id reuse is harmless.** A new row with a dead parent's id is a new incarnation. Old children keep the old audience and never appear in the new parent's pages or counts.
- **Disclosure** is no wider than the parent's rule. The child's audience is contained in the parent's, captures travel only to that audience, and every refusal is uniform in code and cost. Probing, as today, tells a writer whether a parent is readable to them. It never tells them whether an unreadable parent exists.

## 6. Activation

A schema change that adds `readable` to a table, or changes a capture's
dependency identity, captures **inside activation**, the way recorded paths
are captured today:
- parent tables before children;
- a system scan over live parents, with expired or missing parents stamping nulls;
- every affected index and aggregate rebuilt;
- one generation published that makes devices reacquire.

Rows whose parent is missing or expired are counted. If there are any, activation rolls back and names the table and the count. The author deletes the orphans, or keeps the old rule. A child whose hand-copied audience column disagrees with its parent's is reported, never silently moved into the parent's audience. Removing `readable` drops the captures in the same way. No self-chunking job (LLP 3000.013 §5.2) is involved: a job publishes partial state, and an activation publishes none.

## 7. Increments

1. **Server.** The term and its position rule, `$incarnation`, the capture and its write order, the implicit insert requirement, the refusals, and per-row evaluation. The parent-pinned page with its resolved incarnation. Activation capture.
2. **Sync and devices.** Inference for the invertible forms. Captures on the sync image. Device evaluation and predicted inserts through the recorded coverage check.
3. **Aggregates.** Grouping by `(ref, incarnation)`, the derived rule and the retired note.
4. **Chains and the guide.** The rules card leads multi-level apps with `readable`, and the issue tracker becomes a card example.

## 8. Not in this revision

- **Mutable captured fields.** Moving an issue between orgs would have to recapture every descendant: unbounded work with an interim audience.
- **`readable` under `or` or `not`, or in a write rule by itself.** A write that needs "the writer can read that other row" states it as `require` in the mutation, where it is evaluated live and captures nothing.
- **Naming the parent by a non-id unique key**, and **nullable parent references**.
- **Referential actions**: removing orphans with their parent, and expiring with the parent. The candidate is `expire at .message.expiresAt`, an expiry read from a captured immutable parent field. Both are in `issues/20260924-snapback4-sql-parity-candidates.md`.
- **Predicted upsert and `insert … if absent`** on a child.

## 9. How we will know

- **The issue tracker.** It compiles with no audience notes and no `org` on children. Pages pinned by parent are complete. `count comments by issue` is readable by the issue's audience. Tenancy probes across orgs refuse uniformly, and the meters are identical for absent and unreadable parents.
- **A four-level fixture** (org → project → task → comment). Chains capture the full substituted rule, including a middle conjunct such as `and not .archived`. A device predicts a comment on a held, covered task, and queues one on an uncovered task.
- **Identity.** Delete and recreate a parent with the same id. The new parent's page and count show only its own children. The old children stay readable to the old audience and appear in no page of the new parent.
- **Clique.** Receipts and reactions declare `read <- readable messages[.message]` and drop `chat`. Their partitions and answers match the flattened program's. The unread count groups by `.message.chat`, a recorded path.

## Non-claims

This RFC does not make Quarry's rules general joins. A rule still reads one
row and probes by key. The capture is what makes a parent's rule a child's
rule without making the rule non-local, and the incarnation is what keeps a
reused id from joining two parents' children.
