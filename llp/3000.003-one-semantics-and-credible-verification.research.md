## Finding

The project promises one data language and value model on server and device,
but the Rust and TypeScript implementations disagree in observable results.
The existing conformance runner exercises the Rust engine, and the simulator
uses a different replica lifecycle from the published client. Green results
therefore leave the central cross-host contract substantially untested.

This research extends [LLP 3000 §9](./3000-snapback4.explainer.md#9-architecture-and-code-review-2026-09-12).
It retains the chosen substrates and the small card. It asks how their
meaning becomes executable and shared without adding a second apparatus.

## Reproduced disagreements

- **Value semantics:** the device returns an integer beyond i53 where the
  server refuses overflow. JavaScript string comparison orders U+10000 before
  U+E000, while the retained value/key order places it after. Predicted text
  aggregate groups receive an `Id` tag instead of `String`, producing two
  aggregate rows for one group.
- **Eligibility:** a table without `sync` is documented as online-only, but
  the local client evaluates its queries against an empty replica even while
  connected. Valid server-side writes can also be refused locally because a
  required row was never acquired.
- **Completeness:** a point miss beyond a declared count horizon returns
  `null, complete: true`. The client lacks durable evidence distinguishing an
  absent row from one omitted during acquisition.
- **Compiler semantics:** two calls to `identity(x)` in one expression return
  4 for `identity(1) + identity(2)`. A null assertion in the skipped right side
  of `true or ...` executes anyway. The binder's temporaries and bindings
  change the meaning of ordinary expression evaluation.
- **Wire values:** a JSON numeric value 1.25 is silently decoded as zero.

## What is structurally missing

### Runtime representation and admission

TypeScript collapses ids, text and principals to strings and rows/maps to
ordinary objects. That is a useful public wire form, but not sufficient to
reconstruct tagged canonical identities without type context. Numeric bounds,
text order, constraints, cursor validation and meter cuts are separately
implemented and incompletely shared. More examples will continue to diverge
unless the ownership of these semantics is explicit.

Decide between retaining tagged values internally, carrying schema/IR type
information into operations that need it, or executing a shared core on the
device. A shared core could cost more startup bytes and integration work;
fully tagged JavaScript could cost allocations and ergonomics inside the
implementation. A typed operation boundary is smaller but must cover nested
values and maintain keys, not only obvious scalar input conversion.

### Eligibility and negative knowledge

The source brief retained prediction eligibility when it removed static
resource pricing. The shipped client largely infers eligibility while
executing on whatever rows it holds. A local read refusal or absence is not
necessarily the server's answer. A horizon is an acquisition limit, not proof
of an entire table's contents, and counting currently held rows cannot recover
that proof after deletions.

Possible directions are a small compiler-produced operation eligibility
classification, conservative server execution for operations outside local
coverage, or explicit acquisition provenance consumed by local reads. These
can be combined. The question is how the existing `complete`, `fresh` and
write states express the distinction; adding a second query API or resuming
a per-query receipt cache is not assumed. Exact horizon maintenance remains
out of scope; honest incompleteness does not require exact maintenance.

### Verification hosts

[corpus.rs](../snapback4/crates/snapback4-core/tests/corpus.rs) does not decode
expected completeness or continuation into its expected-result structure.
It skips all `partial` and `certification-refused` cases by broad state, even
though structural refusals were retained, and classifies schema-validation
failures as skips. Those choices can hide regressions and do not demonstrate
client parity.

The deterministic world is useful for ordering faults, but its
[replica](../snapback4/crates/snapback4-sim/src/replica.rs) is bespoke. The
[host](../snapback4/crates/snapback4-sim/src/host.rs) retains the engine through
an `Rc`; killing a simulated host does not kill and reopen the actual SQLite
engine. Its model disk faults therefore do not prove real server commit
recovery. Model guarantees and implementation guarantees need separate names
and evidence, even when they share scenarios.

## A compact way forward

1. Decide the internal value/eligibility boundary, using the reproduced
   mismatches as acceptance examples. Do not wait for that decision to fix
   the clear lowering, input-decoding and canonical-key bugs.
2. Run the same supported serialized programs and expected states against
   Rust and the actual TypeScript interpreter. Classify intentional exclusions
   explicitly; a newly unsupported schema cannot silently become a skip.
3. Exercise the actual replica lifecycle with adapter fault injection and
   reordered transport responses, as described in
   [LLP 3000.001](./3000.001-durable-replica-and-write-lifecycle.research.md).
   Reuse the simulator's useful scenarios without requiring a second client
   implementation to supply missing production behavior.
4. Keep a small real-host witness for the boundaries a model cannot exercise:
   IndexedDB transaction lifetime, SQLite adapter isolation, React lifecycle,
   process restart and published-package loading.

These steps strengthen existing tests and measurements. They propose neither
an additional blocking check nor a complete-proof-at-HEAD landing rule. The
security review is separately assigned by the author and is not represented
by this document's findings or confidence statements.

## Implementation follow-up

The findings above describe the review baseline. The 2026-09-13 fixes address
the concrete disagreements without accepting this Draft Research as a design
for the broader runtime or verification boundary.

The Quarry binder now gives locals, helper parameters and procedure bindings
distinct runtime names. Helper arguments are evaluated once in source order
before entering their lexical scope. Boolean right-hand setup stays inside
the selected branch, and null refinements join only paths that continue;
returns and refusals can establish a refinement for the remaining path.
Named index keys are checked for duplicates in reads, ranges and rule probes;
numeric rule literals use the same checked i53 parser as expressions.
Operation uniqueness uses the qualified public name, and emitted TypeScript
escapes enum literals and property names, including `__proto__`. Nullable
asset facts (`width`, `height`, `duration`) now have nullable Quarry and
TypeScript types; `bytes` remains an integer. These changes resolve the
compiler examples in [R20](../issues/closed/20260912-snapback4-helper-binding-hygiene.md),
[R21](../issues/closed/20260912-snapback4-short-circuit-lowering.md),
[R22](../issues/closed/20260912-snapback4-duplicate-named-key-diagnostic.md),
[R23](../issues/closed/20260912-snapback4-module-operation-names.md),
[R24](../issues/closed/20260912-snapback4-typescript-literal-escaping.md),
[R32](../issues/closed/20260912-snapback4-numeric-rule-literal-decoding.md) and
[R33](../issues/closed/20260912-snapback4-branch-local-null-narrowing.md).

The shared core's [structural admission check](../snapback4/crates/snapback4-core/src/engine/admission.rs)
now follows population origins through bindings, assignments, shaping and
branches. A mutation that consumes a page as a complete group must preserve
one uniformly readable, schema-capped population; a caller-supplied list,
cursor, range, slice, merge or insufficient bound cannot stand in for that
population. Missing scan definitions remain structural refusals. Admission
runs before runtime argument evaluation, and a clean Quarry binding reports
the same refusal at the operation's source site. This retains the brief's
structural checks without restoring static pricing, certificates or repair
receipts; runtime meters still bound execution independently.

Rust wire decoding now refuses fractional and out-of-i53 numbers recursively
instead of substituting zero, and rejects non-string asset ids. The actual
TypeScript interpreter uses checked integer arithmetic, Unicode scalar text
ordering and schema types for maintained group keys. Differential tests run
the same authored IR and confirmed rows on Rust and the actual TypeScript
interpreter, including nested maps, shaped rows and lists, text/ref/composite
maintained identities, group moves, checked sums and rollback. List-valued
maintain groups remain unsupported: their required group index is rejected
at schema admission, which has its own authored regression. These are bounded
corrections to the existing representations; they do not settle whether all
internal values should carry tags or which implementation should own every
cross-host operation.

Those comparisons also exposed a cursor encoding disagreement: TypeScript
sorted descriptor fields as `kind,name`, while Rust's canonical serialized
struct requires `name,kind`. The TypeScript encoder now preserves that order;
the differential scan and merge cases compare exact opaque bytes and consume
Rust-produced cursors on later TypeScript pages.

The [Rust page analysis](../snapback4/crates/snapback4-core/src/engine/pages.rs)
and its [TypeScript mirror](../snapback4/packages/snapback4/src/replica/pages.ts)
attach continuation ownership to the executed return. Aliases and one-to-one
collectors preserve provenance; ambiguous multiple pages, modified collectors
and auxiliary reads cannot supply another result's cursor. The corpus adapter
also translates seven legacy cursor oracles to the existing
[LLP 3000 ruling](./3000-snapback4.explainer.md#7-decisions-during-execution):
five server capped results continue from the golden result's last visible row,
while two exhausted, underfilled uniform pages end despite a limited auxiliary
preview. These translations use the fixture's certificate, result, held rows
and range-stop evidence before executing SB4; they never derive an expected
cursor from the output under test. Device completeness remains about its
acquired partition, horizon and meter, as the ruling requires; server
nonuniform read-rule classification is not imposed on delivered device rows.

The [R27 adapter](../issues/closed/20260912-snapback4-corpus-state-and-skip-coverage.md)
requires and compares result state and continuation as well as canonical
values and refusal codes. It no longer has an arbitrary failure allowlist or
broad partial, certification or schema-failure skips. Compatibility conversion
supplies the old store's implicit intrinsic/maintain keys and types asset ids
at declared asset positions. Unsupported asset-record assertions are named
exclusions because SB4 accepts upload references and supplies server facts;
retained asset clearing, deletion, index refusal and metadata behavior execute.
Unsupported receipt custody, delivery, word search and static resource pricing
remain separate named exclusions, reported independently from passing cases.

Qualification observed on 2026-09-13:

- `CARGO_BUILD_JOBS=2 cargo test -p snapback4-core --test corpus -- --nocapture`:
  all 16 tests passed; the Rust server corpus ran **211 passing cases, 82 named
  exclusions and zero failures**. All 24 retained structural refusal cases
  execute. Compilation took 1.28 seconds and tests 0.85 seconds.
- `CARGO_BUILD_JOBS=2 cargo test -p snapback4-lang`: all **18 tests** passed,
  including 11 frontend regressions and a Rust/TypeScript page-plan comparison
  over 15 authored and corpus programs. Tests compile authored Quarry, run its
  emitted IR through the Rust engine and the actual TypeScript interpreter,
  and typecheck emitted API artifacts with the real contract. Compilation
  took 3.72 seconds and test execution approximately 0.28 seconds.
- After integration with version 0.1.14,
  `CARGO_BUILD_JOBS=2 cargo test -p snapback4-lang --test value_parity`:
  all **4 tests** passed, covering **24 differential execution cases** plus
  authored rejection of list maintain groups. This includes every page of a
  Unicode-ordered scan and merge, positive/negative maintained sum overflow
  with source/aggregate rollback, nested ordering, integer boundaries and
  negative divisors. Compilation took 0.37 seconds and tests 0.08 seconds.
- `CARGO_BUILD_JOBS=2 cargo test -p snapback4-device --test native online_only_final_insert_target_is_unknown_to_the_native_predictor`:
  the focused native regression passed (0.81 seconds compilation, 0.01 seconds
  execution). A valid server insert whose after-insert target is online-only
  remains unknown on the device: prediction returns `E_PREDICT`, rolls back
  its local insert, and the server accepts the same write. The final constraint
  probe contributes to local read coverage instead of asserting absence from
  an unacquired table.

The 211-case result is Rust server conformance only. The page-plan comparison
checks static ownership, and the authored frontend/value checks cover selected
behaviors; they do not establish complete JavaScript/Rust conformance, real
IndexedDB recovery or a simulator that hosts the published client lifecycle.
The internal representation decision, acquisition provenance, implementation
host coverage and the larger verification strategy above remain unresolved.
Asset argument byte-bound enforcement and canonical metadata for query or
nested/list arguments also remain separate correctness work; nullable result
typing does not establish those runtime guarantees.

The final compiler review also exercised thirteen compound-expression cases
on Rust and the actual TypeScript interpreter: arrays, objects, minted fields,
min/max, slice operands, sharing, shapes, write fields, computed read/write keys
and lazy containers. Earlier values are captured before later setup can write
or refuse. Immutable lexical row-field reads remain in their projection so the
TypeScript pending marker survives a helper-bearing shape. All 23 language
tests passed; the last field-provenance correction also passed its focused
cross-host regression.
