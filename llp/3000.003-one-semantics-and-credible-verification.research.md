## Finding

The project promises one data language and value model on server and device,
but the Rust and TypeScript implementations disagree in observable results.
The existing conformance runner exercises the Rust engine, and the simulator
uses a different replica lifecycle from the published client. Green results
therefore leave the central cross-host contract substantially untested.

This research extends [LLP 3000 §9](./3000-snapback4.explainer.md#9-architecture-and-code-review-2026-09-12).
It retains the chosen substrates and the small card. It asks how their
meaning becomes executable and shared without adding a second apparatus.

## Reproduced disagreements

- **Value semantics:** the device returns an integer beyond i53 where the
  server refuses overflow. JavaScript string comparison orders U+10000 before
  U+E000, while the retained value/key order places it after. Predicted text
  aggregate groups receive an `Id` tag instead of `String`, producing two
  aggregate rows for one group.
- **Eligibility:** a table without `sync` is documented as online-only, but
  the local client evaluates its queries against an empty replica even while
  connected. Valid server-side writes can also be refused locally because a
  required row was never acquired.
- **Completeness:** a point miss beyond a declared count horizon returns
  `null, complete: true`. The client lacks durable evidence distinguishing an
  absent row from one omitted during acquisition.
- **Compiler semantics:** two calls to `identity(x)` in one expression return
  4 for `identity(1) + identity(2)`. A null assertion in the skipped right side
  of `true or ...` executes anyway. The binder's temporaries and bindings
  change the meaning of ordinary expression evaluation.
- **Wire values:** a JSON numeric value 1.25 is silently decoded as zero.

## What is structurally missing

### Runtime representation and admission

TypeScript collapses ids, text and principals to strings and rows/maps to
ordinary objects. That is a useful public wire form, but not sufficient to
reconstruct tagged canonical identities without type context. Numeric bounds,
text order, constraints, cursor validation and meter cuts are separately
implemented and incompletely shared. More examples will continue to diverge
unless the ownership of these semantics is explicit.

Decide between retaining tagged values internally, carrying schema/IR type
information into operations that need it, or executing a shared core on the
device. A shared core could cost more startup bytes and integration work;
fully tagged JavaScript could cost allocations and ergonomics inside the
implementation. A typed operation boundary is smaller but must cover nested
values and maintain keys, not only obvious scalar input conversion.

### Eligibility and negative knowledge

The source brief retained prediction eligibility when it removed static
resource pricing. The shipped client largely infers eligibility while
executing on whatever rows it holds. A local read refusal or absence is not
necessarily the server's answer. A horizon is an acquisition limit, not proof
of an entire table's contents, and counting currently held rows cannot recover
that proof after deletions.

Possible directions are a small compiler-produced operation eligibility
classification, conservative server execution for operations outside local
coverage, or explicit acquisition provenance consumed by local reads. These
can be combined. The question is how the existing `complete`, `fresh` and
write states express the distinction; adding a second query API or resuming
a per-query receipt cache is not assumed. Exact horizon maintenance remains
out of scope; honest incompleteness does not require exact maintenance.

### Verification hosts

[corpus.rs](../snapback4/crates/snapback4-core/tests/corpus.rs) does not decode
expected completeness or continuation into its expected-result structure.
It skips all `partial` and `certification-refused` cases by broad state, even
though structural refusals were retained, and classifies schema-validation
failures as skips. Those choices can hide regressions and do not demonstrate
client parity.

The deterministic world is useful for ordering faults, but its
[replica](../snapback4/crates/snapback4-sim/src/replica.rs) is bespoke. The
[host](../snapback4/crates/snapback4-sim/src/host.rs) retains the engine through
an `Rc`; killing a simulated host does not kill and reopen the actual SQLite
engine. Its model disk faults therefore do not prove real server commit
recovery. Model guarantees and implementation guarantees need separate names
and evidence, even when they share scenarios.

## A compact way forward

1. Decide the internal value/eligibility boundary, using the reproduced
   mismatches as acceptance examples. Do not wait for that decision to fix
   the clear lowering, input-decoding and canonical-key bugs.
2. Run the same supported serialized programs and expected states against
   Rust and the actual TypeScript interpreter. Classify intentional exclusions
   explicitly; a newly unsupported schema cannot silently become a skip.
3. Exercise the actual replica lifecycle with adapter fault injection and
   reordered transport responses, as described in
   [LLP 3000.001](./3000.001-durable-replica-and-write-lifecycle.research.md).
   Reuse the simulator's useful scenarios without requiring a second client
   implementation to supply missing production behavior.
4. Keep a small real-host witness for the boundaries a model cannot exercise:
   IndexedDB transaction lifetime, SQLite adapter isolation, React lifecycle,
   process restart and published-package loading.

These steps strengthen existing tests and measurements. They propose neither
an additional blocking check nor a complete-proof-at-HEAD landing rule. The
security review is separately assigned by the author and is not represented
by this document's findings or confidence statements.
