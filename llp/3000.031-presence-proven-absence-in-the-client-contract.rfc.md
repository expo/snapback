## 0. Evidence

Three cold builds of Clique on published packages (calibrations #24 on 0.4.6,
#25 on 0.4.7, #26 on 0.4.8) name the same cost in their essays. The #26
essay states it most sharply: a missing local row can mean absence,
incomplete acquisition, a history boundary, a pending write, or an
unavailable server fact, and "treating those states as interchangeable
caused real defects: a transient lookup unmounted a composer; an unavailable
membership disabled an offline send; an online-only DM lookup prevented an
otherwise durable conversation". The #26 diary's M3 entry: "one-shot route
resolution mistook loading for absence"; its M6 entry: "offline membership
loading fought the composer until I stopped treating temporary uncertainty
as permission denial".

What the builder is handed. Every read is one of three arms
(`packages/snapback4/src/contract.ts:66`):

```ts
export type Read<T> =
  | { data: T; complete: boolean; cut: ReadCut; fresh: boolean; revalidating?: true; since?: number; next?: Cursor | null; meter?: ReadMeter }
  | { loading: true }
  | { denied: Refusal };
```

Point reads are generated as `Query<A, Rows["t"] | null>`
(the #26 app's `generated/api.ts:404`), so absence is `data: null` on the
first arm. The five meanings map onto the fields like this:

| meaning | how it shows up today |
|---|---|
| absent | `data` null or empty, `complete: true`, `fresh: true` |
| still acquiring | `loading`, or `complete: false` |
| history boundary | `complete: false` with a `cut` |
| pending write on the read's tables | the query holds and asks no server (`client.md:43`) |
| withheld server fact | stays `loading` (`client.md:44`; `local-query.ts:163`, "`loading` is the engine's unavailable bit") |

"Is this row absent?" is therefore a derivation every component makes. The
#26 app (95 TypeScript files) made it with `"denied" in x` twelve times,
`"loading" in x` four times, `x === null` four times, `.complete` four
times and `.revalidating` five times; it never called the SDK's exported
`isReady`, `isLoading` or `isDenied`, and it wrote its own
`ReadState` helper in the copied starter (`starter/src/ui.tsx:7`). The
client card already says "never on `loading`" in four places
(`guide/client.md:34–36, 44–45, 58`). Prose is not holding across three
builders.

The one diagnostics complaint in #26 is the same shape. Any empty query
answer without an instrumented rule cause is logged as `EMPTY_READ` with the
clause "cause not instrumented" (`crates/snapback4/src/dev_refusal_response.rs:55–66`).
The #26 app's `myProfile` point read, legitimately empty on a fresh account,
logged that line dozens of times with nothing to act on.

## 1. Decision

Three changes, ordered by leverage. None changes authorization, disclosure,
durability or a meter.

### 1.1 `existence`: one word per meaning, computed by the SDK

The read word is renamed to `existence` (revision note above); connection
state keeps its established guide card. The ready arm of `Read<T>` gains a
required discriminant, `existence`, with
three values the SDK computes from facts it already holds:

- **`present`**: the published value is not a top-level `null` or `[]`. A
  `false`, a `0` or `{ liked: false }` is a present answer; only the top
  level counts, never a nested null.
- **`absent`**: the published value is a top-level `null` or `[]`, the
  answer is complete (`complete === true`, `cut === null`,
  no continuation (`null` or omitted)), and this device's pending predicate
  is false for the read: no in-flight device admission, no pending prediction
  with an unknown footprint (which blocks every read), and no pending prediction whose footprint intersects the read's
  tables after the existing complete-local narrowing (`local-query.ts`,
  `LocalReads.pending`, shared by one-shot and observed reads). The
  classification is recomputed whenever the pending set changes, including while `revalidating`, so a retained `absent` never
  survives a prediction that inserts the row.
- **`partial`**: everything else that is ready: `complete === false`, a
  `cut`, a non-null `next`, or an empty value blocked by the pending
  predicate.

`fresh` keeps its meaning and does not demote: an offline `absent` is
absence at the acquired watermark, which the guide says in those words. The
client adds no owner-key or retained-answer proof of its own; the engine
already folds coverage into `complete` (an owner-key partition miss is
`complete`, another principal's key is unknown), and `Coverage` stays
internal. Precedence is total: present, then absent, then partial.

The `loading` and `denied` arms are unchanged. One exported helper covers the
whole union for code that does not narrow:

```ts
export function existence<T>(read: Read<T>): "loading" | "denied" | "present" | "absent" | "partial";
```

**Typed narrowing.** `Ready<T>` has named covariant arms, each carrying
`data: T`. The present arm intersects data with `{} | undefined` (only null
is excluded); absent intersects it with `null | []` and carries
`complete: true`, `cut: null`; partial leaves `T` unchanged. Thus a nullable
point's present arm carries the row, a nullable array's present arm carries
the array, and its absent arm carries `null | []` while retaining the array's
result type. A non-null array retains `T` on every arm, with absent further
refined to `T & []`. `isReady` preserves `data: T`; `emit.rs` is unchanged.
The conservative limit for structural point types is recorded in §3.
`usePage` exposes `existence` on `page.read`, never on `items`: `items` is
`[]` while page one loads, so emptiness there proves nothing; `absent` is
the combined read with no items, `complete`, no cut and no continuation (`null` or omitted).

**Disclosure law.** `existence` is computed from the disclosed answer only.
A row the viewer may not read is `absent` exactly as a row that does not
exist, at the same cost; the discriminant carries no bit the answer did not
already carry. This is the same rule LLP 3000.015 §1 states for the meter and
the point read (`client.md:58`).

**Retention.** Landed RL replacement semantics (LLP 3000.023 §10) stay.
A retained answer is reclassified when pending facts change. Every published
or replaced answer recomputes its own `existence`; it never inherits the
previous answer's discriminant. A withdrawal to `loading` clears it.
Existence adds no retention. LL’s landed live-cut rules (cea3b70436, LLP 3000.023 §10)
remain: held reads resume at sync publication; ordinary reads may obtain a
whole server fallback before sync; terminal refusals bypass parking. Each
resumed or fallback answer recomputes its own discriminant, and a refusal
replaces the ready arm without retaining an existence field.

**Pending-fact refresh after sync (IT, 2026-10-05).** Applying a page
invalidates the client's cached pending predicate even when the page changes
no rows. A successful sync refreshes that predicate through the existing
fenced queue read before returning. Otherwise an unchanged, complete empty
watch can become `partial` and wait for unrelated later work to discover that
its outbox is still empty. This refresh does not reevaluate unchanged queries,
accept overtaken queue snapshots, weaken admission fences, or infer absence
from failed storage. Process and wasm regressions cover the unchanged-page
case; the delivery fault matrix classifies the additional read as optional
to already durable write custody. Evidence is in
[IT's intermittent report](../snapback4/reports/20261005-it-intermittents/REPORT.md).

**Guide and starter.** The client card's "Honest read boundaries" section is
rewritten around the table above with one rule per UI decision: route and
mount on `present`/`absent`, never on `loading` or `partial`; keep
composers, headers and routes mounted through `loading`; show uncertain-empty
status for `partial` and incomplete coverage/cuts/continuations even for
`present` (the §7 presentation adapter); a durable action is disabled on `denied` and, where the
rule is a row the viewer must hold (membership), on that row's `absent` only when fresh and not revalidating,
never on its `loading` or `partial`; the one-view viewer keeps its own
loading and deadline safeguards (`client.md:58`) and closes on `absent`
only after a ready answer. An optional `reason` on the `loading` arm,
`"acquiring"` or `"pending"` (this device's own queue, unknown footprint
included), is information for a status line, never a control channel;
`speculative` and rule causes are never published. The social starter
replaces its `ReadState` helper with `existence` and branches on it in its
point reads, so the copied code teaches the rule.

### 1.2 Probe evidence inside DX's optional `EMPTY_READ` record

Lane DX (`7e9208f47f`, merged in `b7d05baff6`) owns the structure and default:
`dev --trace-empty` is the sole opt-in. Without it, ordinary empty answers
enter neither the console nor `why recent`. With it, top-level empty answers
enter `why recent` only, never the console. Its
[EMPTY_READ card](../snapback4/crates/snapback4-lang/src/guide/why/EMPTY_READ.md)
supplies rule, coverage and horizon investigation commands. Explicit
`require … else EMPTY_READ` remains a real refusal under either setting.
The DX amendment in LLP 3000.015 §2.1 remains unchanged.

Round-2 qualification also found that lifecycle diagnostics, which bypass
Rust's stderr lock, could split a counted refusal's formatting fragments at
shutdown. The console writer now prepares the complete line before writing
it. Aggregation windows, counts, shutdown acknowledgement and the quiet-empty
policy keep their existing meanings.

This branch adds evidence within that optional record and fixes emptiness:

- **`cause: no-candidate`** comes only from the real `live_lookup` /
  `scan_metered` storage miss in `authorized_point` where `point_miss` does
  not call `unknown_fact`. Horizon misses, maintained views over horizoned
  sources and exhausted allowances do not prove absence. It is never inferred
  from an empty `authorized_candidate` and never overwrites a recorded clause.
  The record includes the probe site. The key or prefix matched no stored row
  for this viewer at this generation; it proves nothing about another viewer
  or a device.
- **`cause: unrecorded`** has the clause "no probe miss and no rule cause
  were recorded" when neither was recorded.
- `empty()` counts only top-level `null` or `[]`; a nested null does not make
  a present composed answer empty.

An evaluated nonterminal rule-filtering cause still excludes the successful
answer from the stream, even with the flag (LLP 3000.015 §2.1). Device-side
withholding never reaches this server hook. No device cause or loading reason
is added by this reconciliation. The card gains the two causes' meanings.

Dev evidence adds no meter charge and no wire field; the probe trace remains
behind the `sqlite` feature, excluded from the web device. Measure wasm and
explain any movement, including source-location metadata after integration.

### 1.3 The guide says what the replica proves about the viewer's own rows

The M6 defect, an offline send disabled while the viewer's membership read
`loading`, is decidable only under a stated policy, not for every sync
policy: admission of a conversation is not replication of its authorization
witnesses, a `last N` membership window can leave the viewer's row outside
it (`point_miss` calls `unknown_fact` whenever a horizon exists), and
`retain delivered-history` keeps messages after the membership row is gone.
For the social shape, a membership table synced with no horizon within the
conversation's own group and the same audience as its messages, a wholly
acquired group holds every current readable member row, so after that
group's first acquisition the viewer's own membership is `present` or
`absent` unless a pending prediction blocks absence. The composer recipe on the client card and
`guide offline_interactions` say exactly that condition, show `existence`
reading it. SR’s landed decision (38abb89b8e, LLP 3000.028 §8) governs:
queueing a durable write needs no membership answer. Send is disabled on
`denied`, or `existence(member) === "absent"` when the answer is fresh and
not revalidating. A stale absent row offline still queues; the server
authorizes or refuses at sync. `loading` and `partial` never disable Send.
The guides say that
`loading` means acquisition or later withdrawal, not denial or absence. `with
own keys` is not widened to admin-written membership tables: a complete
own-key partition would then swear a membership absent that an admin wrote.

## 2. Rejected options, with their counterexamples

- **Engine-level retention across commits** (LLP 3000.029): reverted after
  twelve rounds; its round-12 review found a newer cut for one table
  suppressing removal evidence for another. Existence adds no retention.
- **A boolean `known`.** It collapses `partial` and `absent`. LLP 3000.028
  §2.3: a unique-key miss inside a 2,000-row window is not absence, and the
  builder that read it as absence rendered "not liked" for liked posts.
- **Suspense or throwing on `loading`.** It unmounts the composer, the exact
  #26 defect, and it cannot express `partial`.
- **Hiding absence inside `denied`.** Absence is not a refusal, and a denied
  reader must see a hidden row as absent, not as refused (LLP 3000.015 §1).
- **Prose only.** Four "never on `loading`" sentences on the client card did
  not hold across three builders.

## 3. Compatibility and cost

Additive for readers, breaking for constructors. B2 replaces conditional
union arms with named covariant interfaces containing fixed intersections.
For any assignable `T` to `U`, `Read<T>` remains assignable to `Read<U>`,
including unresolved generic readers and widening to nullable or unknown.
The ready discriminant stays mandatory; the other two arms and guards stay.

**Narrowing limit (B2 fallback).** TypeScript permits an array with a row's
properties: `Row & []` is a subtype of `Row`. Consequently exact `null` on
`Read<Row | null>`'s absent arm cannot coexist with universal covariance and
sound empty-array reads. That arm is conservatively `null | (Row & [])`;
a caller needing literal null tests `read.data === null`. Present still
narrows to `Row`, partial keeps `Row | null`, and `isReady` keeps `T`.
Scalar absent intersections can likewise remain syntactically expressible;
no extra runtime outcome is introduced. B3's nullable-array absent data is
`(Row[] | null) & (null | [])`, assignable to `null | []` but never to just
`null`. Plain arrays keep their full `T` identity in every arm, with the
additional empty-tuple refinement on absent. The alternative conditional
filter cannot promise these refinements while accepting every subtype.

Code that constructs ready `Read<T>` literals itself (mocks, tests, custom
clients over the contract) must add `existence`; the implementation updates
every constructor in the repository and the release note names the break. Guide examples and the starters must
compile with the new field, which the guide tests already enforce. 1.2 is
dev-only engine tracing behind the existing `sqlite` feature; the device wasm
should not change (a measured delta is part of acceptance). No wire format
changes: `existence` is computed on the client from the answer and the
device's own coverage state.

## 4. Acceptance

| Cell | Required evidence |
|---|---|
| One-shot and observed point during a successful insertion held at device admission | Both publish `partial` until admission releases; native and wasm regression fails without the shared predicate |
| Nullable array `Row[] | null` | Generated query returns absent `[]` and absent `null`, present non-null array; absent data is assignable to `null | []`, rejected as `null` alone; partial remains `T` |
| Generic reader `T extends U` | `Read<T>` passes to `Read<U>`, including Astra's `T extends Row` consumer; a ready literal without `existence` is rejected |
| Discovery | “what does a missing row mean” and “loading or absent” open client; “unknown membership offline” opens offline-interactions; the connection-state keyword retains its card |

- Contract tests: a total decision table over {nullable point, array,
  scalar} × {top-level null or empty, non-empty} × {complete, incomplete,
  cut, non-null next} × {fresh, stale} × {no pending, pending on the read's
  tables, pending with unknown footprint, pending on unrelated tables} with
  the expected `existence`; recomputation during `revalidating` when a
  prediction inserts the row; and the disclosure assertion that a hidden
  row and a missing row produce byte-identical answers and the same
  `existence`.
- Guide tests: the client card's existence table compiles; the starter has no
  `"loading" in` outside the SDK; the composer recipe reads membership
  through `existence`.
- `EMPTY_READ`: default empty answers advance no evidence and print nothing;
  `--trace-empty` records a proven miss as `no-candidate` with its probe site,
  and other empty answers as `unrecorded` with the exact clause above, without
  console output. Rule-filtered empty answers never record; explicit
  `require … else EMPTY_READ` records and prints under both settings. A nested
  null is not empty.
- Same-key replacement changes `existence` from absent to present when a row
  arrives and from present to absent after deletion, preserving RL's policy.
- The full `snapback4/scripts/test.sh` at `== 0 failure(s)`; wasm delta
  measured; two-family blind review of the implementation, one round plus
  fixes.

## 5. Questions the sanity check answered

1. `loading.reason` may name `acquiring` or `pending` (derived from local
   acquisition and outbox facts); `speculative` and rule causes are never
   published. Adopted in §1.1 as information only.
2. `with own keys` is not widened: own keys stay structurally caller-owned.
   §1.3 now states the exact membership policy under which the replica
   decides the question.
3. `partial` does not split; `fresh` and `complete`/`cut` remain for code
   that needs the distinction.
4. `existence` lives on `page.read`; `items` proves nothing.

## 7. Read presentation (Lane A, 2026-10-03)

Implemented under Charlie's 2026-10-02 full-implementation commission for
[LLP 3000.032 §4.1](./3000.032-client-contract-builder-costs.research.md#4.1).
`readPresentation<T>(read: Read<T>): ReadPresentation` is exported from
`snapback4/contract`. This is presentation of the existing public observation,
with no subscription, saved result, timer, data traversal or authorization bit.

| Field | Exact derivation |
|---|---|
| `existence` | `existence(read)`; no recomputation from data or new absence algorithm |
| `pending` | existence is `loading`; a readable answer is pending, not a write |
| `incomplete` | ready and (`existence === "partial"` or `!complete` or `cut !== null` or `next != null`) |
| `stale` | ready and `!fresh` |
| `revalidating` | ready and `revalidating === true` |
| `why?` | current denied arm's `Refusal`, unchanged |
| `since?` | ready timestamp when defined, unchanged, including zero |

`incomplete` adds the composition missing from the word alone: a nonempty
answer stays `present` but still needs a coverage/cut/continuation notice.
A partial empty answer with otherwise complete metadata stays incomplete when
§1.1's pending predicate blocks absence. The adapter does not access that private
predicate, guess pending writes from row fields, or expose it as `pending`.
An empty continuation cannot become absent. A completed offline empty read
stays absent at its acquired watermark. Staleness and revalidation are independent.
All ready-only flags are false on loading/denied, and those arms omit `since`.
`why` appears only on denied. No meter internals become presentation causes.

The original read remains the typed data-narrowing surface. Display flags never
mean safe to mutate: membership-dependent Send retains §1.3's rule and server
authorization. LLP 3000.023 §§3.4,12 own all withdrawal and retention behavior;
this helper consumes it. It cannot retain content across a hard withdrawal,
extend RV's possible-revocation bound, or change once-media behavior.

The [complete React/Expo screen](../snapback4/packages/snapback4/CLIENT-AND-OPERATIONS.md#a-stable-conversation-screen)
keys its interaction shell by backend/account/resource. Results read current
`usePage` items and the notice reads `page.read`. Neither read arm controls shell
mounting. Only the shell owns the draft; no profile, row, cursor or authorization
answer is latched. Submission clears the composer before waiting for admission;
the submitted text stays paired with its write ID, so identical later text is
an independent draft. The latest write's refusal offers Edit/Dismiss without
overwriting newer text. The social starter uses the same incomplete predicate.

Acceptance: unit cases cover nonempty incomplete pages, empty continuations,
intersecting/unknown pending insertions and unrelated predictions, stale absence
and stale nonempty incompleteness,
independent freshness/revalidation, refusal identity and hard withdrawal. A
1,010-case table checks agreement with `existence` and frozen-input purity;
an opaque data getter refuses data inspection. The published declarations keep
generic reads covariant and provide no data or permission field. Process/wasm
client tests consume real admission-to-retained-partial-to-present transitions
and close refusals; the browser runs the actual published recipe under Strict
Mode and read replacement with host-view stubs. Native UI layout is outside
that browser proof. Independent nonempty-ready → loading and → denied cases
require immediate protected-content removal with draft/focus preserved; a
last-ready-items cache fails both. Held admission followed by deleting/retyping
identical text preserves the new draft; admission and later settlement refusals
retain editable submitted text. Pilot counts and the keep/reject decision are recorded in
[the lane report](../snapback4/reports/20261003-a-read-presentation/REPORT.md).


**2026-10-04 — quoted-message recipe.** The social starter ships
`QuotedMessage`, embedded verbatim in `guide social` and compiled against its
existing whole-message point query. It now consumes §8’s `matchRead`: loading
keeps the stable placeholder; present renders current text; absent alone says

## 8. Exhaustive typed matching (Lane RM, 2026-10-06)

Implemented under Charlie's Lane RM commission after calibration #31 on 0.4.13.
`matchRead` is the paved rendering form from `snapback4/contract`, re-exported
by `snapback4/react`. It dispatches the existing read once, with no classifier,
subscription, result cache, timer, data traversal or semantic change.

The exhaustive handler object has `loading(read)`, `denied(why, read)`,
`absent(read)`, `partial(data, read)` and `present(data, read)`. Parameters
retain the original objects and §1.1's exact narrowed types: present excludes
null, partial preserves T, and absent retains the conservative structural
intersection from §3. Every ready handler keeps the original metadata. The
return type is the union of handler results; input inference comes from the
read, not a handler's parameter annotation.

An explicit `otherwise(read)` may cover omitted loading/absent/present handlers.
Denied and partial are required even with this fallback, so no broad fallback
silently erases refusal or uncertainty. Explicit handlers take precedence.
The fallback's type is the union of loading/absent/present; it conservatively
keeps all three even when one also has an explicit handler. Named
`ReadMatchHandlers<T, R>` and `ReadMatchFallbackHandlers<T, R>` are public for
reusable handler sets. This is a rendering helper, not an authorization check.

Point and page reads use the same handlers: §1.1 already gives them the same
five meanings. Pages pass `page.read`, never `page.items`. Nonempty incomplete
pages dispatch present; §7's `readPresentation` still provides independent
incomplete/stale/revalidating notices. No sixth state or page-only API is
needed. SettledRead also accepts this handler set; its loading handler cannot
run. The same renderer can therefore consume observations and one-shot results.

The social quote no longer needs a second guard to reach its text. Conversation
status lines, its send gate, feed, chats, profiles and search adopt the helper,
as do applicable web/Expo chat status lines and gates. Social keeps §1.3 and
LLP 3000.028 §8's send rule. Web/Expo chat preserve their existing gate on any
absent/denied membership; this lane deliberately changes no starter behavior.
The online-only starter has no read-rendering component. All shells, drafts,
receipt ownership and once-media lifetimes remain independent of matching.

The client card and package reference teach exhaustive matching and the
restricted fallback, within existing card budgets. Type tests reject each
missing state and denied/partial omissions with a fallback, and check narrowed
point/page/generic parameters and mixed result unions. Runtime tests cover
all states and independent freshness, revalidation, completeness, cut, cursor
and timestamp combinations, including otherwise-complete pending emptiness.
The [RM report](../snapback4/reports/20261006-rm-read-match/REPORT.md) records
source-level inventory, starter behavior checks and full-suite/wasm evidence.

Wave 5 of the app farm (2026-10-11, LLP 3000.013 §6.6) keeps this rule and
changes only its error: a handler set with `otherwise` but no `denied` or
`partial` fails with a property whose type is the fix ("otherwise skips
denied: add denied: why => …, or reuse a zero-argument fallback"), and the
documented way to send both to the fallback is to pass one zero-argument
function three times.

Wave 6 (0.4.21, 2026-10-11, LLP 3000.013 §6.7) found the rule's cost had
doubled: 14 lanes (60 minutes, six "fix first" votes) wrote that function
three times, because `partial` is the steady state of every page `check`
reports with `N_NEVER_COMPLETE` and the adapted Home now starts most screens
from `matchRead`. The rule stays: a bare `otherwise` still does not cover
`denied` or `partial`, and omitting them still fails with the sentence that
names the fix. What changes is the cost of choosing the fallback. The
exported `otherwiseAll(fallback)` returns the three handlers `otherwise`,
`denied` and `partial`, each calling `fallback(read)` with the read itself,
and the call spreads it: `matchRead(read, { present: rows => …,
...otherwiseAll(read => <Status read={read} />) })`. The decision is still
written at the call site, in a word that says "all"; a reader sees that
denial and uncertainty reach the fallback, and the fallback can still show a
refusal (`readPresentation(read).why`). Ordering is checked by the compiler:
a `denied` or `partial` written before the spread is TS2783 ("specified more
than once"), so a later spread cannot silently replace an explicit decision,
and one written after the spread wins. Rejected: letting `otherwise` cover
`partial` (option (a) of the wave-6 analysis), which changes what an existing
`otherwise` means for every caller and re-opens the silent-erasure case this
section exists to prevent; a `matchReadOr(read, present, fallback)` second
entry point, which is a second spelling of the five meanings; and a default
fallback inside `matchRead`. The fallback's parameter is `Read<unknown>`
because the helper is evaluated before `matchRead` knows T; rows keep their
type in the handlers the call writes. The adapted Home's first read uses the
helper, and the client card, the package reference and the TS error text
name it.

Wave 7 (0.4.22, 2026-10-12, LLP 3000.013 §6.8) found the spread made key
order load-bearing: 7 lanes (018 034 035 076 083 095 098, 26 minutes, three
fix-first) wrote `{ present, denied, ...otherwiseAll(f) }` or added a
`partial` before the starter's trailing spread and met TS2783, and four of
them gave up and spelled all five states. The docstring's "spread it after
the handlers you write" contradicted its own next clause. The decision stays
where it was: a bare `otherwise` still never covers `denied` or `partial`, and
omitting them still fails naming the fix. What changes is what the spread
carries. `otherwiseAll(fallback)` now returns only `otherwise`, a function
marked `otherwiseAll: true` (a plain property, so two copies of the package
agree), and `matchRead` sends a `denied` or `partial` that has no handler of
its own to `otherwise` only when it carries that mark. A named handler
therefore wins wherever it is written, the spread can go first or last, and
nothing is silently overwritten (an object spread copies only the keys it
has). A plain `otherwise` written after the spread replaces the marked one,
so the explicit decisions are required again, at compile time and at run time
(an untyped caller that reaches `denied`/`partial` with neither a handler nor
the mark gets a `TypeError` naming `otherwiseAll`, where it used to call
`undefined`). `otherwiseAll(fallback, overrides)` also carries `loading`,
`denied`, `absent` and `partial` handlers in one place; they are typed over
`Read<unknown>`, because TypeScript does not infer T from the spread's
contextual type through `matchRead`'s generic handler set (measured), so
`partial: rows => …` that needs typed rows belongs in the call. Rejected: a
third `matchRead(read, handlers, fallback)` argument (a second spelling the
marked spread makes unnecessary). `matchRead` also takes a `usePage` result
whole and matches its `read` (four lanes wrote `matchRead(page)`); guards
still take `page.read`. Docs and the starter Home put the spread first.

## 9. Wave 12 list matching

Implementer: Codex for Charlie Cheever, SURF, 2026-10-14, target 0.4.29.
This narrowly revises section 8's rejection of a list-specific helper under
the explicit wave-12 commission. matchRead itself stays unchanged.

matchReadList accepts only Read of a readonly array, or a page hook, and
requires denied and otherwise. Otherwise receives the original read and
covers omitted loading/absent/present/partial handlers. Named handlers always
win; denial remains mandatory and cannot silently reach otherwise. Calling
the list-specific function is the explicit decision to put uncertain empty

handler return unions. Nonempty incomplete lists remain present and still
need readPresentation for independent incompleteness. No classifier,
authorization, subscription or retention changes.

Runtime tests cover every state, page-hook dispatch and explicit partial
overrides. Type tests reject missing denial and point-read inputs and verify
data inference/mixed returns. The shared list component compiles against
published PageHook and WriteHook; existing matchRead tests remain unchanged.
