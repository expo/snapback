## 0. Evidence

Three cold builds of Clique on published packages (calibrations #24 on 0.4.6,
#25 on 0.4.7, #26 on 0.4.8) name the same cost in their essays. The #26
essay states it most sharply: a missing local row can mean absence,
incomplete acquisition, a history boundary, a pending write, or an
unavailable server fact, and "treating those states as interchangeable
caused real defects: a transient lookup unmounted a composer; an unavailable
membership disabled an offline send; an online-only DM lookup prevented an
otherwise durable conversation". The #26 diary's M3 entry: "one-shot route
resolution mistook loading for absence"; its M6 entry: "offline membership
loading fought the composer until I stopped treating temporary uncertainty
as permission denial".

What the builder is handed. Every read is one of three arms
(`packages/snapback4/src/contract.ts:66`):

```ts
export type Read<T> =
  | { data: T; complete: boolean; cut: ReadCut; fresh: boolean; revalidating?: true; since?: number; next?: Cursor | null; meter?: ReadMeter }
  | { loading: true }
  | { denied: Refusal };
```

Point reads are generated as `Query<A, Rows["t"] | null>`
(the #26 app's `generated/api.ts:404`), so absence is `data: null` on the
first arm. The five meanings map onto the fields like this:

| meaning | how it shows up today |
|---|---|
| absent | `data` null or empty, `complete: true`, `fresh: true` |
| still acquiring | `loading`, or `complete: false` |
| history boundary | `complete: false` with a `cut` |
| pending write on the read's tables | the query holds and asks no server (`client.md:43`) |
| withheld server fact | stays `loading` (`client.md:44`; `local-query.ts:163`, "`loading` is the engine's unavailable bit") |

"Is this row absent?" is therefore a derivation every component makes. The
#26 app (95 TypeScript files) made it with `"denied" in x` twelve times,
`"loading" in x` four times, `x === null` four times, `.complete` four
times and `.revalidating` five times; it never called the SDK's exported
`isReady`, `isLoading` or `isDenied`, and it wrote its own
`ReadState` helper in the copied starter (`starter/src/ui.tsx:7`). The
client card already says "never on `loading`" in four places
(`guide/client.md:34–36, 44–45, 58`). Prose is not holding across three
builders.

The one diagnostics complaint in #26 is the same shape. Any empty query
answer without an instrumented rule cause is logged as `EMPTY_READ` with the
clause "cause not instrumented" (`crates/snapback4/src/dev_refusal_response.rs:55–66`).
The #26 app's `myProfile` point read, legitimately empty on a fresh account,
logged that line dozens of times with nothing to act on.

## 1. Decision

Three changes, ordered by leverage. None changes authorization, disclosure,
durability or a meter.

### 1.1 `presence`: one word per meaning, computed by the SDK

The ready arm of `Read<T>` gains a required discriminant, `presence`, with
three values the SDK computes from facts it already holds:

- **`present`**: the answer holds at least one row (a non-null point value or
  a non-empty list).
- **`absent`**: the platform proves no row matches. All of: the answer is
  complete (`complete === true`, no `cut`); it is fresh against the server
  (`fresh === true`) **or** the device's coverage proves the key without a
  server (a whole-partition owner-key marker, LLP 3000.028 §3.4, or a
  retained complete answer inside its horizon); and no pending predicted
  write on this device touches the read's tables. The data is `null` or
  empty.
- **`partial`**: rows may be missing: `complete === false`, a `cut`, or a
  stale answer (`fresh === false`) with no device proof.

The `loading` and `denied` arms are unchanged. One exported helper covers the
whole union for code that does not narrow:

```ts
export function presence<T>(read: Read<T>): "loading" | "denied" | "present" | "absent" | "partial";
```

**Typed narrowing for point reads.** For a point query the ready arm is a
union on `presence`: under `presence === "present"` `data` narrows to the
row type (non-null); under `"absent"` to `null`; under `"partial"` to the
row type or `null`. For list queries `data` keeps its array type in every
arm and `absent` means "complete and empty". Reading `data` without
narrowing keeps today's type, so existing programs compile unchanged.
`usePage` exposes `presence` on `page.read`; `absent` on page one means the
list is provably empty.

**Disclosure law.** `presence` is computed from the disclosed answer only.
A row the viewer may not read is `absent` exactly as a row that does not
exist, at the same cost; the discriminant carries no bit the answer did not
already carry. This is the same rule LLP 3000.015 §1 states for the meter and
the point read (`client.md:58`).

**Retention.** `revalidating` keeps the last answer's `presence`; a
withdrawal to `loading` clears it. This follows LLP 3000.023 §3 as it stands
after LLP 3000.029's revert and adds no retention.

**Guide and starter.** The client card's "Honest read boundaries" section is
rewritten around the table above with one rule per UI decision: route and
mount on `present`/`absent`, never on `loading` or `partial`; disable an
action only on `denied`; keep composers, headers and routes mounted through
`loading`; show "partial" only for `partial`. The social starter replaces its
`ReadState` helper with `presence` and uses the narrowing in its point
reads, so the copied code teaches the rule.

### 1.2 `EMPTY_READ` says which of three things happened

The engine's refusal trace already records a filtered read clause
(`refusal_trace.rs:filtered_phase`, non-terminal). For an empty query answer
under dev, the trace additionally records one of:

- **`no-candidate`**: the plan's key or prefix probe found no stored
  candidate row, recorded at the probe site;
- **`filtered`**: candidates existed and a named rule removed them, at the
  table, clause and site already recorded today;
- **`withheld`**: the answer was withheld as speculative or past the horizon.

The dev refusal log prints one actionable line per cause with its site and
the `snapback4 why <query>` pointer, and `why` reports the last cause. A
proven `no-candidate` answer is not logged by default (`--log-empty-reads`
includes it). "Cause not instrumented" disappears for query answers; the test
corpus asserts every empty query answer carries a cause. `EMPTY_READ` stays
the code, so nothing keyed on it breaks; the record gains a `cause` field.

### 1.3 The guide says what the replica proves about the viewer's own rows

The M6 defect, an offline send disabled while the viewer's membership read
`loading`, is a case the replica can already decide: a conversation is held
on the device because a membership row admitted it, so for a held
conversation the viewer's own membership is `present` or `absent`, never
`partial`, once the first acquisition completes. The composer recipe on the
client card and `guide offline_interactions` state this, show `presence`
reading it, and say that `loading` there is only first acquisition and is
neither absence nor denial. Whether `with own keys` (LLP 3000.028 §3.4) should
also admit admin-written membership tables is an open question below; this
change is guide text over what the replica holds today.

## 2. Rejected options, with their counterexamples

- **Engine-level retention across commits** (LLP 3000.029): reverted after
  twelve rounds; its round-12 review found a newer cut for one table
  suppressing removal evidence for another. Presence adds no retention.
- **A boolean `known`.** It collapses `partial` and `absent`. LLP 3000.028
  §2.3: a unique-key miss inside a 2,000-row window is not absence, and the
  builder that read it as absence rendered "not liked" for liked posts.
- **Suspense or throwing on `loading`.** It unmounts the composer, the exact
  #26 defect, and it cannot express `partial`.
- **Hiding absence inside `denied`.** Absence is not a refusal, and a denied
  reader must see a hidden row as absent, not as refused (LLP 3000.015 §1).
- **Prose only.** Four "never on `loading`" sentences on the client card did
  not hold across three builders.

## 3. Compatibility and cost

Additive. The ready arm gains one required field that the SDK always fills;
the union's three arms keep their shapes; `isReady`, `isLoading` and
`isDenied` are unchanged; the generated types add a narrowing that only
code which branches on `presence` sees. Guide examples and the starters must
compile with the new field, which the guide tests already enforce. 1.2 is
dev-only engine tracing behind the existing `sqlite` feature; the device wasm
should not change (a measured delta is part of acceptance). No wire format
changes: `presence` is computed on the client from the answer and the
device's own coverage state.

## 4. Acceptance

- Contract tests: a derivation matrix over {point, list} × {complete,
  incomplete, cut, fresh, stale, pending write on the table, owner-key
  covered, hidden row} with the expected `presence`, and the disclosure
  assertion that a hidden row and a missing row produce byte-identical
  answers.
- Guide tests: the client card's presence table compiles; the starter has no
  `"loading" in` outside the SDK; the composer recipe reads membership
  through `presence`.
- `EMPTY_READ`: every empty query answer in the test corpus carries a cause;
  a fresh account's `myProfile` logs nothing by default; a rule-filtered
  empty answer logs `filtered` with its site; a speculative answer logs
  `withheld`.
- The full `snapback4/scripts/test.sh` at `== 0 failure(s)`; wasm delta
  measured; two-family blind review of the implementation, one round plus
  fixes.

## 5. Open questions for review

1. Can the SDK attribute `loading` to acquiring, withheld or pending without
   a disclosure cost? `Coverage.speculative` is internal
   (`local-query.ts:31`). If it can, `{ loading: true, reason }` is worth
   adding as information, never as control flow.
2. Should `with own keys` admit admin-written membership tables? LLP 3000.028
   §3.4 admits only structurally caller-owned writes today. If not, §1.3
   stands on the replica's admission fact alone; state whether that fact is
   guaranteed for every sync policy a membership table can carry.
3. Should `partial` split into stale versus incomplete? The recommendation is
   no: one word per decision the UI makes; the fields stay for code that
   needs the distinction.
4. Is `absent` on `usePage` page one the right place, or should `items`
   carry it?
