## Summary

A first-party programmatic replay surface — `defineReplay` / `runReplay` in
`@expo/snapback-acceptance`, wrapped by a thin JS-side `snapback replay` CLI
verb — that drives a large ordered volume of mutations at a Snapback app from
a headless process. The helper owns the five custody decisions the 0.1.25
pair paid for by hand (transport identity, client pooling/disposal,
live-query suppression, settle-before-next pacing, receipts/resume), respects
or pre-flight-names the real 1,024-family ceilings, surfaces every refusal's
`SNAPBACK_*` diagnostic verbatim with its replay position, and runs detached
behind a small status file so a supervising agent polls instead of babysits.
LLP 0043 continues to own replay/retention *semantics*; LLP 0275 D9 owns
the acceptance package's public API, lifecycle, and compatibility contract,
which these exports extend and must not fork; the CLI owner governs the
verb; the helper is a disciplined consumer of the documented client surface
and adds none. LLP 0201's benchmark is the first consumer, not the owner.

## Motivation

LLP 0306 §F2: Explicit's scale segment was 11,314s of an 18,766s session —
settle-before-next over 167,157 actions — with a first attempt dead at 8,873
on `SNAPBACK_CLIENT_MUTATION_RETENTION_FULL`; Familiar's failed outright at
2,620 actions under a growing synchronized public replica per actor (~759 MB
at ~116 retained clients). The ticket inventories the reinvented bug set:
retention-ceiling death, `SNAPBACK_AUTH_STALE_RESULT` from binding transport
ids to fixture identity, `SNAPBACK_OUTBOX_NOT_WRITER`
(`packages/snapback-client/outbox-shared.mjs:184`), the missed
`x-snapback-auth-client-protocol` header, and unsuppressed live queries. The
current guide answer (`guide/testing/large-fixtures.md`) is an app-authored
loader that addresses none of the custody questions. LLP 0307 ruling 5 binds
the packaging; this Spec binds the contract.

## Design

### D1. Packaging and naming

- **Helper:** `@expo/snapback-acceptance` root entry (the package's single
  export surface, `packages/snapback-acceptance/package.json:24-31`), following
  its `define*`/`run*` convention (`defineStarterAcceptance`
  `index.d.mts:228`, `runStarterAcceptance` `index.d.mts:255`): new exports
  `defineReplay(options): ReplayDefinition`,
  `runReplay(definition, options): Promise<{receipt, exitCode}>`, and
  `readReplayStatus(statusFile)`. `@expo/snapback-client` is already the
  package's peer dependency (`package.json:32-34`). New module files join the
  package's `files` allowlist.
- **CLI verb:** the installable `snapback` binary is the JS CLI
  (`packages/snapback-cli/cli.mjs` → `runCli`), whose owned orchestration
  verbs live in the `PACKAGED_CLI_COMMANDS` registry
  (`packages/snapback-cli/index.mjs:7081`, `@ref LLP 0041#cli-commands`);
  established host operations delegate to the native binary
  (`crates/snapback-cli/src/cli.rs:798` `HostCommand`), which has no
  replay/seed/bulk verb. `snapback replay` is therefore a **JS-owned verb**
  registered there — `@expo/snapback-cli` already depends on
  `@expo/snapback-acceptance` (`packages/snapback-cli/package.json`) — a
  thin argument parser over `defineReplay`/`runReplay` with no logic of its
  own. The native verb table is not touched.

### D2. The contract

One replay = one ordered action log driven through the app's own generated
mutation surface against one target, one action at a time.

1. **Clients: one, or a small LRU pool.** Clients are
   `createExternalSessionClient(baseUrl, {bearerToken, clientStoreId,
   rqsStore: null})` (`packages/snapback-client/index.d.mts:2170`; the shape
   the zerobugs loader already uses,
   `demos/zerobugs/control/scripts/load-fixture.mts:309-313`). The factory
   sets `authClientProtocol = 1` itself (`index.mjs:2541-2543`), so the
   auth-client protocol header (`AUTH_CLIENT_PROTOCOL_HEADER`,
   `index.mjs:1235`) can never be missed. `rqsStore: null` means no durable
   client store: no outbox, no writer custody, no
   `SNAPBACK_OUTBOX_NOT_WRITER` class. Pool is keyed by actor with a hard
   ceiling (default 8, max 64); eviction and end-of-run call `close()`
   (`index.d.mts:1676`). Minted bearers are cached per actor for the run,
   so re-entry after eviction re-creates a cheap client without re-minting.
2. **Actor identity.** Default: the helper mints per-actor dev sessions
   through the admin-gated `snapback session mint --email … --ready-file …`
   path, discovering the admin token from the readiness descriptor's
   `adminTokenFile` exactly as the guide documents
   (`guide/testing/large-fixtures.md:118-148`); `bearerFor(actorId)` is the
   caller-supplied escape hatch. Actor switch within the pool is a client
   switch; actor eviction is dispose-then-re-auth. **Session custody:**
   minted per-actor session material persists to a mode-0600
   session-custody file beside the receipts — the same trust domain as the
   `adminTokenFile` it derives from — so a resumed run re-attaches the
   *same authority*. Load-bearing for D7's exactly-once claim: settlement
   lookup rejects a different auth/authority as
   `SNAPBACK_AUTH_STALE_RESULT`
   (`crates/snapback-kernel/src/storage/settlement.rs:634`), and LLP 0043
   provides no exactly-once bridge across authorities, so a re-minted
   session cannot redeem a prior run's transport id. Callers on
   `bearerFor` own the same stability obligation.
3. **No live queries.** The helper never calls `liveQuery`/`subscribeLive`
   (`index.d.mts:2035,2084`). This is the Familiar-scale failure mode
   (per-actor synchronized replica) made structurally impossible.
4. **Reads are one-shot and paged.** Lookups run through `client.query`
   with caller-provided generated query references using keyset cursors;
   page size clamps to the `.take()` ceiling of 1,024
   (`guide/backend/queries.md:357`; batch take-sums share it,
   `crates/snapback-types/src/manifest/types.rs:6938`). The helper also
   maintains the intent→settlement receipt map from prior actions (D6), so
   most id resolution needs no read at all — the placeholder→minted-id map
   every loader hand-rolls today (`load-fixture.mts:316-343`).
5. **Settle-before-next.** Strictly sequential: action *n+1* dispatches
   only after action *n*'s settlement resolves — LLP 0201's frozen replay
   contract ("replay order authoritative with settle-before-next", §D2
   Performance at scale) adopted as the only v1 pacing mode. The pool
   exists for identity custody, not parallelism.

### D3. Transport identity custody

The load-bearing default, per the parent ruling: **the helper mints transport
`clientMutationId`s; application intent ids pass through as args/receipt
fields and never become transport identity.** That kills the
`SNAPBACK_AUTH_STALE_RESULT` rediscovery class (transport id bound to
fixture/session identity) at the contract level.

Two custody policies:

- **`transportCustody: 'minted'` (default).** The helper mints a fresh
  transport id per action (`mutate`'s `clientMutationId` option,
  `index.d.mts:1903`), records it in the JSONL receipt, and acknowledges
  settled ids in trailing batches via the storeless standalone path —
  `acknowledgeMutations({clientMutationIds})`
  (`index.d.mts:1980`, `index.mjs:8474`; LLP 0043 names standalone
  `POST /client-mutations/acknowledge` as exactly the one-shot caller's
  completion path). The acknowledge window is **count- and byte-aware**:
  a batch acknowledges when outstanding settled ids reach the count window
  (default 256) *or* outstanding retained bytes reach a byte budget
  (default 2 MiB) — where "retained bytes" must be a **proven conservative,
  client-computable bound** on the server's retained-row charge. The public
  response does not expose that charge, and storage meters the complete
  logical carrier including private settlement fields stripped from the
  public projection (`crates/snapback-kernel/src/storage.rs:22745` vs
  `crates/snapback-server/src/server/response_types.rs:267`), so raw
  result-byte length is *not* conservative: the bound is result bytes plus
  a fixed per-settlement overhead constant, parity-locked by a kernel test
  asserting retained-row bytes never exceed it across settlement shapes —
  or, if no such constant can be proven, the implementation must expose the
  exact charge (a small LLP 0043-owned server addition) before claiming
  this budget. Never the smaller D6 projection size. This matters because
  the
  per-auth ceiling is not only 1,024 records but 8 MiB of complete
  retained-row bytes (128 maximum-sized results;
  `crates/snapback-kernel/src/storage.rs:626-638`), so a count-only window
  is not safe by construction. This buys exactly-once resume for the
  crash-ambiguous action (D7).
- **`transportCustody: 'none'`.** No transport id is sent, so no server
  settlement is retained: `mutate` only attaches an id when one is present
  (`index.mjs:11949`, `if (clientMutationId) body.clientMutationId = …`).
  This is the throughput mode the corrected 0.1.25 Explicit adapter proved
  at 167,157/167,157
  (`benchmarks/runs/2026-08-23-clique-published-0125-sol-high/record.md:75-88`);
  delivery is at-most-once and resume relies on receipts alone.

**Generated-IR boundary (superseded by r4.1).** For a local-executable generated-IR mutation
reference (`ref.mutationIr.format === 'snapback.generated-mutation-ir.v1'`),
`mutate` auto-mints a transport id regardless of caller input — `null` is
overwritten (`index.mjs:11738-11745` `clientMutationId ??=
createClientMutationId()`; again in `store-runtime.mjs:1724-1725`), so
`'none'` custody is not reachable for those references on today's surface.
The helper handles this honestly by refusing IR-carrying steps at preflight
with `SNAPBACK_REPLAY_GENERATED_IR_UNSUPPORTED`. Re-preparing their fresh
speculative identity cannot be an exact retry; the public carrier needed to
close that gap is the non-blocking obligation in OQ1.

**Idea-13 ruling (client-layer default minting): no.** On the actual
surface, ordinary (non-IR) generated references send no id unless given one
— which is why a naive sequential driver survives at all. Making
`createExternalSessionClient` default-mint would enroll every headless
consumer in server settlement retention (1,024 records per auth fingerprint,
below) with no acknowledgement loop attached — recreating
`SNAPBACK_CLIENT_MUTATION_RETENTION_FULL` as the default experience.
Minting-by-default belongs in the layer that also owns the acknowledge loop:
this helper. The client's behavior is unchanged.

### D5. API sketch

```js
import {defineReplay, runReplay} from '@expo/snapback-acceptance';

const replay = defineReplay({
  readyFile: '.snapback/dev.ready.json',   // resolves baseUrl + adminTokenFile
  api: './snapback/generated/api.mjs',     // generated reference module
  actions: './fixtures/scale-log.jsonl',   // path or async iterable
  // Each action: {seq, actor, fn, args, intent?} — or a mapper function
  // (ctx) => ({fn, args}) with ctx.query(ref, opts) and ctx.settled(intent).
  actors: {mint: {emailFor: (id) => `${id}@replay.invalid`}},  // or {bearerFor}
  clientPool: 8,
  transportCustody: 'minted',              // 'minted' (default) | 'none'
  acknowledgeEvery: 256,
  receiptsFile: './replay-receipts.jsonl', // append-only
  statusFile: './replay-status.json',
});

const {receipt, exitCode} = await runReplay(replay, {
  resume: false,
  signal,                                  // AbortSignal, like runStarterAcceptance
});
```

Definitions are frozen and versioned
(`schemaVersion: 'snapback.replay-definition.v1'`); the run receipt is
`snapback.replay-receipt.v1`, mirroring the starter-acceptance shape
(`index.d.mts:138-155,163-193`). Option names reuse the client's real
vocabulary (`clientStoreId` derives per actor; `rqsStore` is pinned `null`
and not caller-configurable in v1).

### D6. Receipts: a write-ahead JSONL log, not an outcome journal

The receipts file is the run's durable source of truth for identity custody,
`ctx.settled`, and resume — which forces a **two-line write-ahead discipline
per action**, not a single terminal line:

1. **Dispatch line, flushed durably *before* the send:**

```json
{"v":"snapback.replay-dispatch.v1","seq":12,"intent":"m-000012",
 "actor":"u0007","function":"messages.send","selector":"messages.send",
 "args":{"body":"hello"},"carrierBytes":52,
 "custody":"minted",
 "transportId":"rp-8f2c…","at":1756000000000}
```

Under `'minted'` custody, the transport id exists on disk before the server
can ever see it — the precondition for the exactly-once resume claim in D7.
Under `'none'`, `transportId` is `null` and the line still marks the action
as attempted. The mapper-resolved `{function,args}` carrier is capped at 1 MiB;
overflow refuses before append/send with
`SNAPBACK_REPLAY_DISPATCH_CARRIER_TOO_LARGE`.

2. **Terminal line after settlement or refusal:**

```json
{"v":"snapback.replay-terminal.v1","seq":12,"intent":"m-000012",
 "outcome":"settled","code":null,"version":48211,
 "settled":{"ids":{"message":"m_9x2k…"}},"ms":64,"at":1756000000064}
```

**Durability order (normative):** the terminal line is flushed durably
*before* the next action's dispatch line is written. This is what keeps
"at most one dispatch-without-terminal" true — the invariant every resume
rule below leans on.

`version` is the settlement's authoritative commit version from
`MutationOutput` (`index.d.mts:406-422`). `settled` carries the **bounded
settlement projection** that `ctx.settled(intent)` serves: by default the
minted row ids from the mutation result, capped in bytes; a definition may
supply a projection function. A result whose projection exceeds the cap
**stops the run** with a named error *after* writing a terminal line that
records the settlement with a projection-overflow marker — the mutation
committed, so it is never recorded as `refused` and never re-executed;
the run cannot continue safely because a later action may need the map
entry the projection could not carry. This is what makes the
placeholder→id map rebuildable from the file after a crash — without it,
resume could skip the settled prefix but not *use* it. Application
refusals write `outcome: "refused"` with the verbatim `code`.

3. **Ack watermark lines** (minted custody): each auth-fingerprint-composed
acknowledge batch appends
`{"v":"snapback.replay-ack.v1","actor":"u0007","through":[…transportIds]}`
(the actor selects a client bearing that fingerprint) — **appended
only after the server acknowledge succeeds**, so a watermark never claims
a drop the server has not performed (D7 ack-drain).

The trailing summary receipt binds counts, the receipts digest, per-action
custody, and pool/ack configuration. Intent
ids are receipt fields only — never transport identity (D3).

### D7. Failure semantics and resume

- **Verbatim diagnostics.** Every refusal path surfaces the underlying
  `SNAPBACK_*` code and details unmodified, prefixed with replay position
  (`seq`, `intent`, `actor`, `fn`) — never rewritten or folded. Default
  disposition is stop-on-first-failure with a nonzero exit; refused actions
  are terminal and never retried (the receipts analog of LLP 0043's
  drop-and-mark-failed rule).
- **One runner per WAL (fence).** The runner holds an exclusive advisory
  lock (an `O_EXCL` lockfile beside the receipts carrying pid + a start
  token, released on graceful exit) for the life of the run; `resume`
  acquires the fence before reading the WAL and refuses with a named error
  while it is held by a live pid. A stale fence (pid gone) is broken
  under an O_EXCL reclamation lease by comparing the complete expected owner
  and atomically replacing the stale name; the break is recorded in the
  receipts. This makes overlapping runners —
  the torn-WAL / double-dispatch failure — structurally impossible rather
  than merely discouraged by the D8 status text.
- **Resume requires a re-readable action source.** A definition whose
  `actions` is a one-shot async iterable is not resume-eligible; preflight
  records that in the definition, and `resume: true` against it refuses
  with a named error. File-backed logs are always resume-eligible.
- **Resume.** `runReplay(def, {resume: true})` reads the receipts file,
  verifies dispatch/terminal prefix continuity against the action log,
  skips every `seq` whose terminal line says **settled** — a `refused`
  terminal is a *failed run*, and resume stops there rather than
  continuing past it — and rebuilds the `ctx.settled` map from the
  terminal lines' `settled` projections. The
  crash-ambiguous action is the one with a dispatch line and no terminal
  line — at most one under settle-before-next. **Its handling follows the
  custody recorded on its own dispatch line, never the run default**: with a
  recorded `transportId`, resume re-attaches the actor's authority — from
  the D2 session-custody file, or for `bearerFor` callers by calling
  `bearerFor(actorId)` again under its stated same-authority obligation —
  and re-sends exactly that id, so LLP 0043's
  settlement lookup republishes the retained result or executes exactly
  once — sound only because D6 persists the id before the send *and* the
  authority survives; if the session material is missing or expired,
  resume **stops at the ambiguous action** with a named error rather than
  silently downgrading to re-execution. With `transportId: null`, resume
  also **stops at the ambiguous action by default**, naming `seq`/`intent`
  — automatic re-execution would make `'none'` worse than at-most-once.
  Re-execution of the ambiguous action requires the definition to declare
  the affected actions idempotent (whole-log or per-action) or an explicit
  `resume: {ambiguous: 'reexecute'}`, and the receipt and summary then
  record duplicate-possible semantics for that action. A rerun never
  re-executes an action that has a terminal line.
- **Retention across runs (ack-drain).** On start with `resume: true`, and
  on every graceful exit, the runner acknowledges, in batches, the minted
  transport ids that **have a settled terminal line** and are not covered by an
  ack watermark. **A dispatch-only id — the crash-ambiguous action — is
  never in the drain set:** it is resolved first (re-send → republish or
  execute → terminal line) and only acknowledged after its terminal line
  lands. Draining it first would drop the retained settlement the re-send
  depends on and turn exactly-once into a second execution. Without the
  drain, repeated kill/resume cycles of `'minted'` runs on one auth
  fingerprint would accumulate retained settlements toward
  `SNAPBACK_CLIENT_MUTATION_RETENTION_FULL` — the ceiling this surface
  exists to make unreachable. The D4 "respected by construction" claim is
  scoped to include this cross-run drain, not only the in-run ack window.

### D8. Detached mode and status

`runReplay(def, {detach: true})` (CLI: `snapback replay … --detach`) spawns
the run as its own process group and returns with the status-file path only
after the child has acquired the WAL fence through the IPC barrier.
**Liveness predicate (normative):** a live `pid` is never `dead` —
`readReplayStatus` reports a live pid with a stale `updatedAt` as
`state: "stalled"` (a long settlement under settle-before-next legitimately
stalls the heartbeat), and synthesizes `state: "dead"` only when the
recorded pid is gone (heartbeat-only inference is reserved for hosts where
pid liveness cannot be observed). Recovery guidance points at
`resume: true` only from `dead` — starting a second runner against a live
run's WAL would tear the receipts and destroy exactly-once.
**Detach requires a serializable definition boundary:** closures,
in-memory async iterables, and `AbortSignal` cannot cross a process spawn,
so a detached definition carries only file paths, JSON options, and module
specifiers — a mapper, `bearerFor`, or settlement projection is given as
the path of a module exporting that function, never a closure.
`runReplay({detach: true})` on a closure-bearing definition refuses with a
named error naming the offending field; the CLI shape satisfies the
boundary by construction. A detached run is stopped with SIGTERM to the
status-file `pid`, honored at the next action boundary (`signal` applies
to attached runs only). The runner rewrites `statusFile` atomically on a checkpoint cadence:

```json
{"v":"snapback.replay-status.v1","state":"running","settled":12000,
 "failed":0,"total":167157,"lastSeq":12000,"pid":4242,
 "receiptsFile":"…","updatedAt":1756000000000}
```

`snapback replay --status [--status-file <path>]` (and `readReplayStatus`)
reads it — and **synthesizes liveness rather than trusting the file**: a
SIGKILLed runner never writes a terminal state, so only when the recorded
`pid` is gone does `readReplayStatus` report `state: "dead"` with the last
checkpoint's progress and recovery `resume: true`; a live pid with stale
`updatedAt` is `stalled`, never `dead` (D7). A supervising
agent polls a file instead of holding a process in context — the direct
answer to the 0.1.25 pattern of sitting in one turn polling the replay
process (LLP 0306 §F2 item 1).

### D9. CLI verb

```
snapback replay [<backend-dir>] --actions <file.jsonl> [--api <generated/api.mjs>]
  [--ready-file <path>] [--receipts <file>] [--custody minted|none]
  [--resume] [--detach] [--status] [--json]
```

Registered in `PACKAGED_CLI_COMMANDS` with the registry's standard
lifecycle/output/exits/recovery fields; `--json` emits the run receipt (or
status projection) as the only stdout document. The verb constructs a
`ReplayDefinition` and calls `runReplay` — nothing else lives in the verb.

## Dated r4 amendment (2026-08-24 — fix-round author rulings)

This block is self-contained and supersedes every conflicting r3 sentence,
example, acceptance cell, or open-question premise above or below.

1. **Generated IR refuses in v1.** Forced upgrade is withdrawn. Every step
   carrying `snapback.generated-mutation-ir.v1` refuses at preflight with
   `SNAPBACK_REPLAY_GENERATED_IR_UNSUPPORTED`; no dispatch line or request is
   emitted. Re-preparation mints fresh speculative identity into the server
   fingerprint, so current public surface cannot meet exactly-once. A public
   carrier that can resend the exact prepared identity is a non-blocking
   obligation, not an S1 implementation prerequisite.
2. **The dispatch line is the retry carrier.** Before send, WAL records the
   mapper-resolved function and exact JSON arguments, plus actor, intent,
   custody and transport id. The `{function,args}` JSON carrier is capped at
   1 MiB; overflow refuses with
   `SNAPBACK_REPLAY_DISPATCH_CARRIER_TOO_LARGE`. Resume never invokes a mapper
   or `ctx.query` for a dispatch-lined or terminal-lined action: terminal
   actions skip, and the sole ambiguous action re-sends the recorded carrier.
3. **Only settlements are ACK-eligible.** A refused terminal retains no server
   settlement under LLP 0043 and is never acknowledged. ACK-flush failure is
   outside action disposition: once a settled terminal exists, no later ACK
   failure may append a second terminal for that sequence. Watermarks remain
   post-success only.
4. **Windows compose by auth fingerprint.** Outstanding count/bytes and ACK
   batches are keyed by the bearer identity the server fingerprints, not by
   actor. Preflight composes actors that resolve to one bearer; a conservative
   global window is also conforming. No group may cross 1,024 records or 8 MiB
   by actor aliasing.
5. **Ceiling scope is honest.** Construction proves the retention bounds for
   replay-minted fresh authorities. `bearerFor` receives
   `SNAPBACK_REPLAY_BEARER_RETENTION_UNKNOWN`: pre-existing retained rows are
   invisible to v1. Mirrored constants are parity-locked to the kernel values;
   reading live diagnostic values remains a non-blocking obligation.
6. **Fence custody includes publication.** A detached child acquires the
   `O_EXCL` WAL fence before parent-written shared config/status and before the
   parent reports success, using the IPC barrier. Stale reclamation takes a
   separate O_EXCL lease, compares the complete previously read owner token,
   and atomically replaces the stale lock name, eliminating the read/unlink
   race. Attached and detached runners retain the fence through
   summary-receipt and final-status writes.
   A competing detached launch refuses before either shared artifact changes.
7. **WAL analysis is strict.** Malformed/blank lines, unknown record or
   terminal outcomes, sequence gaps, duplicate/open terminal violations, and
   ACK ids without a matching settled dispatch stop with
   `SNAPBACK_REPLAY_WAL_INVALID`; none is skipped. Each append fsyncs the WAL,
   and the first append also fsyncs its parent directory so persist-before-send
   includes the newly created directory entry.
8. **Liveness has one rule.** Observable live pid implies `running` or
   `stalled`, never `dead`; `dead` requires a gone pid. Heartbeat-only death is
   reserved for hosts without pid observation.
9. **Diagnostic and secret posture.** A resumed refused WAL republishes its
   original `{code,message,details}` unchanged with only replay `position`
   added. Session-mint failure never includes raw child stdout/stderr.
   `SNAPBACK_REPLAY_DETACH_CONFIG_INVALID` is written to the public status file
   after the child has fenced the WAL.
10. **Qualification mechanics.** Packed proof staging rewrites internal
    `workspace:`/`file:`/`link:` ranges to exact package versions before
    packing, and session mint consumes the CLI's native `ok/data.token`
    envelope without a nonexistent `--json` flag. The capability row remains
    `experimental` with packed 200k two-custody qualification pending.
11. **Session ACK wire authority.** LLP 0058 makes the session bearer header
    canonical and rejects body `auth` under sessions. Therefore
    `MutationAcknowledgementRequest.auth` is wire-optional: it remains admitted
    for legacy dev-mode body authority, while a session-header request without
    the field reaches the handler. Served proof is mint → explicit-id mutation
    → header-authenticated ACK → 2xx/one removed settlement.
12. **Required regression cells.** S1 includes three bounded kill/resume cycles
    on one fingerprint, competing detached runners, aliased-authority ACK
    pressure, verbatim refused-WAL resume, every strict-WAL rejection above,
    and the served session-ACK sequence. These are affected-scope gates; the
    packed 200k proof remains the capability-qualification gate.

## Non-goals

- **Not a migration tool.** Replays go through the app's own generated
  mutation surface under ordinary authorization; no system-field authoring,
  no schema work, no bypass of LLP 0160 ceremony.
- **Not a load-test framework.** No rate targets, no concurrency ramps, no
  latency SLOs: v1 is strictly settle-before-next sequential (D2.5), and
  LLP 0201's O5 stays a scale-safety gate, not a speed statistic.
- **No live-query assertions.** Observing delivered live state is acceptance
  choreography (`defineStarterAcceptance` journeys); the helper forbids live
  queries entirely.
- **No hosted-target claims in v1.** Local target first. Target-independent
  in principle: the helper speaks only documented client surface, so
  `'none'` custody has no local-only dependency — but `'minted'` custody is
  local-only by construction, because the hosted coordinator keeps no
  client-mutation settlement ledger and never echoes `clientMutationId`
  (LLP 0043, handler-visible settlement identity, hosted-twin note). v1
  proofs and claims are local; a hosted run is out of scope, not
  degraded-but-claimed.
- **No relaxation of the 1,024 ceilings** (LLP 0306 "no plan" list; LLP 0307
  non-goals). The helper routes around them by custody, not by widening them.

## Acceptance

Refined from the ticket's floor; each item is checkable:

1. **Packed-package scale proof.** A consumer using packed
   `@expo/snapback-acceptance` + `@expo/snapback-cli` (archives, not
   workspace links) replays ≥ 100k actions across ≥ 8 personas locally,
   only documented surface, under both custody policies: zero
   `SNAPBACK_CLIENT_MUTATION_RETENTION_FULL`, zero live-query
   registrations, pool never over its ceiling, RSS asserted against a
   fixed budget.
2. **Ceiling preflight.** Preflight names the retention, `.take()`,
   buffered-write, and seed ceilings with parity-locked kernel values; a plan
   engineered to breach the ack-window invariant refuses before dispatch.
3. **Refusal transparency.** An induced handler refusal and an induced auth
   refusal each surface their verbatim `SNAPBACK_*` code plus `seq`/`intent`
   position in the error, the receipt line, and the CLI `--json` output.
4. **Resume.** A run killed mid-flight (SIGKILL, no cleanup) resumes: the
   terminal-lined prefix is skipped, the `ctx.settled` map is rebuilt from
   the receipts file alone, and under `'minted'` custody the crash-ambiguous
   action settles exactly once and final
   per-table digests equal an uninterrupted run's (digests per
   `guide/testing/large-fixtures.md`). **The digest-equality claim is
   scoped to minted custody.** A `'none'` resume proves prefix-skip and
   that the run **stops at the ambiguous action by default** with the
   named error; only under declared idempotency or the explicit
   `resume: {ambiguous: 'reexecute'}` opt-in does it re-execute, with the
   duplicate-possible ambiguity recorded — and no digest-equality claim
   for non-idempotent logs.
5. **Detached watch.** A detached run's status reaches a terminal state on
   graceful completion; `readReplayStatus` synthesizes `"dead"` only for a
   gone pid (a SIGKILLed runner), and reports a live pid with a stale
   heartbeat as `"stalled"`, never `"dead"`; the watcher touches nothing
   but the status projection.
5b. **Cross-run retention.** Three kill/resume cycles of a `'minted'` run
   on one auth fingerprint stay bounded: ack-drain on each resume keeps
   retained settlements under the ack window, proven against the
   1,024-per-fingerprint ceiling.
6. **IR refusal.** A local-executable generated-IR step under either custody
   refuses at preflight with `SNAPBACK_REPLAY_GENERATED_IR_UNSUPPORTED`, with
   no dispatch line or mutation request (r4.1).
7. **Guide routing.** `guide/testing/large-fixtures.md` routes the bulk
   case to the helper (the app-authored loader remains documented for the
   gated bootstrap-window pattern); the capability index gains the row.
8. **First consumer.** The next Clique full pin's scale segment runs
   through `snapback replay` / `runReplay` — the lane consumes it as a
   customer, with no lane-authored transport adapter.

## Open questions

1. **Public exact-retry carrier for IR references (non-blocking obligation).**
   The client needs a public carrier that resends the exact prepared
   speculative identities, timestamps, and settlement identity inputs for a
   generated-IR mutation. Merely honoring `clientMutationId: null` would offer
   at-most-once dispatch but would not satisfy minted-custody exactly-once.
2. **Independent-actor parallelism post-v1.** Whether a pipelined mode
   (parallel across provably independent actors, sequential within) is
   admissible is an LLP 0201 instrument-law question; v1 does not build it.
3. **Hosted custody.** If a hosted target ever advertises a client-mutation
   settlement ledger (`offline_mutation_replay`, LLP 0043 capability gate),
   does `'minted'` custody extend unchanged? Deferred until one exists.
4. **(Obligation, non-blocking.)** The exact LLP 0201 checkpoint /
   action-grammar adapter — how the benchmark's frozen action log maps
   onto `defineReplay` actions — is implementation-phase work owned with
   the first consumer integration, not this contract.
5. **(Obligation, non-blocking.)** D7's resume prefix check compares
   receipts against the re-read action log; adding a per-action args
   digest to the dispatch line for tamper-evidence against a mutated log
   is an implementation hardening obligation, not contract.
