## Summary

Every Snapback lane in the 0.1.29 Clique matrix hit the same dark loop: a
write settled, a one-shot query saw the row, and an already-open live hook did
not change. Unable to tell *where* the chain broke — the query's dependency,
the authority fence, the transport, the client's applied revision, or the
renderer — the lanes spent hours on destructive guesses: refresh-argument
nonces, 250–400 ms polling, alternating `skip` cycles, revision rows,
presence hacks, reloads, and snapshot-mutating workarounds (LLP 0317 O15).
The L1 diagnosis later showed that every one of those cases had a precise,
different answer (LLP 0317 O14 r2.4–r2.6), and that every fact needed to reach
it was already observable — but only by an author who could read
`demos/_kit/tests/live-query-invalidation-e2e.mjs` and the engine.

This RFC commissions the **causal subscription receipt**: a bounded,
redacted, machine-readable explanation, computed on the client from facts the
protocol already delivers, that answers "did subscription *S* observe committed
version *V*, and if not, which link is responsible?" with one verdict from a
closed set, each verdict bound to one guide repair. It adds no server route.
It needs at most one optional wire field. Its automatic producer — an
own-write that a still-attached subscription has not covered inside the
convergence envelope — is the dark-loop detector LLP 0219 was built to host.

The claim being made: the receipt is *minimal* because LLP 0200 §2.1 already
guarantees the one fact that is not otherwise visible — for every registered
subscription, the server's watermark advancing to ≥ V means the client holds
every content ≤ V it is entitled to, with `current_as_of(V)` sent when the
evaluation skipped or found no change. Watermark ≥ V without content for V is
therefore a *server-witnessed* statement that the query does not depend on
the committed rows. That single fact is what separates "your predicate does
not match" from "fanout is broken", and it is the fact none of the lanes had.

## Motivation

The evidence is the matrix itself:

- `sol-snapback-familiar` `1787857038`: own settled write absent from the
  same client's hook for 3 s. Verdict, had the receipt existed: `converged`
  inside the LLP 0200 envelope (the Linux rerun measured 30–40 ms), i.e.
  nothing to fix; the lane instead added polling.
- `sol-snapback-explicit` `1787861040`: "neither the JS conversation query
  nor a dedicated declarative reactions subscription emitted an update" while
  a fresh one-shot read saw the row. Verdict: `not-dependent` or
  `shared-custody` — the receipt would have shown either watermark ≥ V without
  content (the query does not read that row) or two receipts with the same
  principal and `storagePartition` (LLP 0317 F2's Node/headless collision).
- `grok-snapback-explicit` M3: an unscoped query "went silent" on a large
  thread. Verdict: `refused` — `SNAPBACK_QUERY_IMPLICIT_LIMIT_REACHED`, bound
  1,024, repair `.take(n)` — which since `9f7eb7f5d` is exactly what
  `handle.refusal` carries.
- `sol-snapback-familiar` `1787857472`: cross-context staleness while the
  same client's projection updated. Verdict: whichever of `pending`,
  `not-attached` or `fenced` the second context was actually in — the point
  is that it was one of three, and the lane had no way to name it.

O15 is LLP 0317's highest-leverage row for a reason the priority synthesis
states: the missing causal observability turned *one* uncertainty into hours
of workaround exploration, and the workarounds themselves (subscription
churn, `SNAPBACK_SUBSCRIPTION_CONNECTION_LIMIT`) created new failures. LLP
0219 already holds the channel, the redaction rules, the active-condition map
and the dev-only reporter; what it lacks is a producer for this loop and the
receipt the producer would carry.

## Options considered

1. **A server-side explain route** (`GET /live/explain?subscription=…`)
   returning the engine's per-subscription evaluation ledger. Most complete —
   it could name the matcher's decision per version — but it adds an
   authenticated dev route, a new authority surface, and a second history to
   redact; LLP 0219 rules out channel-owned routes, and every fact the agent
   needs to *choose a repair* is already delivered to the client.
2. **A client-composed receipt from delivered facts** (chosen). Joins the
   settlement version, the subscription's watermark and last delivered frame,
   the authorization fence state, the typed refusal, the transport state and
   the renderer's applied revision into one verdict. At most one optional wire
   field sharpens one verdict. Cost: a versioned receipt contract and a
   detector with a tunable grace.
3. **Export the engine spike trace** (`SNAPBACK_SPIKE_TRACE` JSONL fences).
   Already exists; server-only, env-gated, and useless from inside an app or
   an agent's headless client. Stays as the engineer's tool.
4. **Log every frame to the console.** No verdict, unbounded noise, and the
   lanes had console access already; what they lacked was a *diagnosis*.

## Decision

Build option 2 as a producer into the LLP 0219 channel plus two explicit
query surfaces, with the verdict set and the guide ladder below as the
contract. The receipt is computed from held client state in constant time,
carries no rows, arguments, principals or credentials, and is available in
every client arm (headless, React, Expo) because the channel already is.

## Design

### The causal chain and where each link is observable today

| Link in the lanes' question | Fact the client already holds | Source |
|---|---|---|
| "Was my write committed, and at which version?" | mutation settlement `status: 'settled'`, `commitVersion`, `settledAt` | LLP 0043; `packages/snapback-client/index.d.mts` |
| "Is this subscription registered and attached?" | `handle.subscriptionId`, `handle.connection` (`live`/`polling`/`stale`/…), `handle.paused`, the `resubscribed` subscription event | LLP 0095 |
| "Did the server consider V for this subscription?" | last delivered content frame version, or the `current_as_of(V)` watermark | LLP 0200 §2.1 (watermark ≥ V ⇒ every content ≤ V held) |
| "Did the query depend on the committed rows?" | watermark ≥ V **without** a content frame at V ⇒ not dependent; a content frame at V ⇒ dependent | LLP 0200 §2.1; sharpened by §Server changes |
| "Is the authority fence holding the result?" | `handle.authorizationDisposition` (`retain`/`quarantine`/`delete`), pending obligation revision and retry episode, `handle.authorizationDenial` | LLP 0053 client fences |
| "Was the reevaluation refused?" | `handle.refusal` (typed diagnostic: code, bound, repair) | LLP 0053 2026-08-28 amendment; `9f7eb7f5d` |
| "Did the client apply it?" | `handle.authoritativeRevision`, `handle.lastDeliveryAtMs`, `handle.deliveryLagMs`, `handle.freshness`, `handle.answerClass` | client handle |
| "Did the renderer show it?" | React registry snapshot revision, `handle.suppressedEqualSnapshots`, the LLP 0219 churn detector's site record | `packages/snapback-react/implementation.mjs` |
| "Are my two clients actually two principals?" | principal pseudonym, `storagePartition` digest, custody kind (`indexeddb-web-locks`, …) | LLP 0059 custody; the harness's `partitions` witness |

Nothing in the first column requires a new server fact. The receipt is the
join.

### The receipt

```json
{
  "schemaVersion": "snapback.live-query-receipt.v1",
  "subscription": {
    "id": "sub_…", "function": "allMessages", "argsDigest": "sha256:…",
    "connectionId": "…", "connection": "live", "paused": false,
    "principal": "pseud:…", "storagePartition": "sha256:…", "custody": "indexeddb-web-locks"
  },
  "asked": { "commitVersion": 1025, "askedAtMs": 1787961800008 },
  "server": {
    "watermark": 1025, "watermarkKind": "current_as_of", "watermarkDisposition": "not-dependent",
    "lastContentVersion": 1023, "lastContentKind": "live_delta", "lastContentAtMs": 1787961799844
  },
  "fence": { "disposition": "retain", "pendingObligationRevision": null, "retryEpisodeId": null },
  "refusal": null,
  "client": { "authoritativeRevision": 1023, "lastDeliveryAtMs": 1787961799844, "deliveryLagMs": 17, "freshness": "current", "answerClass": "authoritative", "rowCount": 1023 },
  "renderer": { "arm": "react", "snapshotRevision": 1023, "suppressedEqualSnapshots": 0, "argsIdentityChurn": null },
  "verdict": "not-dependent",
  "explanation": "The server evaluated version 1025 for this subscription and found no change: the query does not read the rows committed at 1025. Check the predicate, the index, or a nested dependency.",
  "repair": { "guide": "realtime/live-queries#explain-a-live-query-that-did-not-update", "step": "not-dependent" }
}
```

Redaction is structural, as in LLP 0219: no rows, no arguments (only a
canonical digest), no raw principal or partition identifiers (pseudonym and
digest only), no credentials. `rowCount` is the only row-derived scalar.

### Verdict set (closed)

Exactly one verdict per receipt, evaluated in this order; every verdict binds
to one anchor in the guide ladder.

| Verdict | Condition | What the agent does |
|---|---|---|
| `refused` | `handle.refusal !== null` | Apply the refusal's repair (`.take(n)` for the implicit ceiling). |
| `paused` | `handle.paused` | Resume; nothing else is wrong. |
| `not-attached` | `connection` not `live`/`polling`, or `subscriptionId` null, or a `resubscribed` event after `askedAtMs` | Wait for reattachment; if it persists, custody or lifecycle — LLP 0095 ladder. |
| `fenced` | `authorizationDisposition` is `quarantine`/`delete`, or a pending obligation revision exists | Authority changed or is being re-proven; read the disposition, do not add a refresh argument. |
| `converged` | `server.watermark ≥ V` and `client.authoritativeRevision ≥ V` and a content frame at ≥ V was applied | Nothing is wrong at the client; if the UI disagrees, see `applied-not-rendered`. |
| `applied-not-rendered` | client applied ≥ V but the renderer snapshot is < V, or `suppressedEqualSnapshots` advanced, or the churn detector has a live site | Renderer/hook identity — LLP 0219's churn repair. |
| `not-dependent` | `server.watermark ≥ V` with no content frame at V | The query does not read those rows. Predicate, index, nested/child dependency, or the row is outside the declared window. |
| `shared-custody` | only from `compareReceipts(a, b)`: same principal pseudonym and partition digest across two clients | The two clients are one principal — assign distinct `storagePartition`s (guide `clients/headless`, `recipes/multi-persona-clients`). |
| `pending` | none of the above and `server.watermark < V` | Inside the LLP 0200 convergence envelope; the receipt reports the elapsed time and the envelope. Wait — never poll. |

`pending` is the only non-terminal verdict, and it is honest about its own
bound: LLP 0200 §2.5's `max_hold` means a standalone watermark cannot be
withheld indefinitely, so a `pending` that outlives the envelope plus grace
becomes the detector event below rather than staying silent.

### Surfaces

- **Headless:** `handle.explain({ commitVersion? })` returns the receipt
  synchronously from held state (no I/O). `await handle.explainAfter({
  commitVersion, timeoutMs })` resolves when the subscription's watermark
  reaches `commitVersion` or the timeout elapses, then returns the receipt; it
  never resubscribes, never polls and never issues a one-shot query.
  `compareReceipts(a, b)` (a pure function exported beside them) yields the
  `shared-custody` verdict.
- **React/Expo:** `useSnapbackQueryReceipt(reference, args)` projects the bound
  handle's receipt for the same descriptor `useSnapbackQuery` uses, adding the
  renderer section. It is a read of registry state, not a subscription of its
  own.
- **Channel producer (the dark-loop detector):**
  `SNAPBACK_LIVE_QUERY_UNCONVERGED`, an LLP 0219 *active condition* keyed by
  `(subscriptionIdentityPseudonym, commitVersion)`. Armed when this client's
  own mutation settles at `V` while a still-attached subscription's watermark
  is `< V`; fires when the watermark has not reached `V` within the LLP 0200
  within-capacity envelope plus a grace (`liveReceiptGraceMs`, default
  3,000 ms, tunable configuration); carries the receipt; clears when the
  watermark reaches `V` or the handle is disposed. Dev-positive only, per
  LLP 0219's `positiveDevelopmentEnvironment()` seam. Cross-client cases are
  not detected automatically — the client does not know the peer's `V` — and
  are covered by `explainAfter` with a version obtained out of band (the
  peer's settlement, or a bounded control query such as a `latestVersion`
  read), which the guide ladder names.
- **Not in v1:** a CLI/dev-loop projection and any overlay. Both are
  consumers of the channel and can follow without changing this contract.

### Server changes (additive, optional)

One optional field on the existing `current_as_of` envelope —
`disposition: "no-change" | "not-dependent" | "coalesced"` — lets the receipt
distinguish "evaluated, nothing changed for you" from "your read set does not
include the committed rows". It is compatible within wire v1 (LLP 0093 D1) and
absent from every other variant. Without it the verdict is still decisive
(`not-dependent` collapses to "evaluated, no content for V"); with it the
guide step can be sharper. Whether the engine can cheaply tell the two apart
is an implementation question the lane answers; the receipt schema reserves
the field either way.

No other server change. In particular this RFC relies on, and adds an
acceptance for, LLP 0200 §2.1's existing promise: a registered subscription
that the matcher skips still observes `current_as_of ≥ V` within the service
bound. The O14 harness's shape (a) control is the natural proof.

### Cost and hot-path posture

The receipt reads fields the handle and registry already maintain; the only
new bookkeeping is the last watermark version/kind/disposition per handle
(three scalars) and the detector's armed set, which is bounded by the number
of in-flight own mutations and cleared on coverage. No timers per frame; the
detector uses the channel owner's single deadline scheduler (LLP 0219).

### The diagnostic ladder (guide)

`guide/realtime/live-queries.md` gains "Explain a live query that did not
update": step 1 is always `handle.explain()` / `useSnapbackQueryReceipt`;
steps 2–9 are the verdict table's rows, one repair each. The section states
the rule O15 asked for in so many words: **do not add a refresh argument, a
nonce, a `skip` cycle or a poll before reading the receipt.** Retrieval-eval
cases use the lanes' own phrases ("live query didn't update after mutation",
"hook stale but query sees the row", "cross-client live update missing",
"is fanout broken").

## Non-goals

- A server explain route or any new authenticated surface.
- Backend telemetry or fleet aggregation (LLP 0154/0156 territory).
- Changing settlement, watermark, coalescing or fence semantics (LLP 0200,
  LLP 0053 own them; this receipt only reads their outcomes).
- Diagnosing the *server's* matcher internals beyond dependent/not-dependent.
- Production-default emission; the detector is dev-positive like every
  LLP 0219 producer.
- A visual overlay.

## Acceptance

1. **Harness parity.** Run under `demos/_kit/tests/live-query-invalidation-e2e.mjs`,
   the receipt alone yields: shapes (a), (b), (c) → `converged` with
   `deliveryLagMs` recorded; shape (d) past the ceiling → `refused` naming
   `SNAPBACK_QUERY_IMPLICIT_LIMIT_REACHED`, bound 1,024 and the `.take(n)`
   repair; a new non-dependent control (a subscription whose predicate
   excludes the committed row) → `not-dependent` by watermark, within the
   LLP 0200 service bound, ten consecutive runs.
2. **Shared custody.** Two headless clients on the default partition →
   `compareReceipts` yields `shared-custody`; with distinct partitions it does
   not.
3. **Renderer.** LLP 0219's churn fixture → `applied-not-rendered` with the
   detector's site record in the receipt.
4. **Detector.** In a test app, an own write whose subscription is deliberately
   held back (paused transport) raises `SNAPBACK_LIVE_QUERY_UNCONVERGED` after
   envelope + grace with the receipt attached, and the condition clears on
   coverage; a healthy app raises nothing across the harness shapes.
5. **Redaction.** A receipt serialized from a fixture with known rows,
   arguments and principals contains none of them (structural test, not a
   grep).
6. **Guide.** The ladder section lands with CI-verified snippets and
   retrieval-eval cases; every verdict has exactly one anchor.
7. **P6 scope.** Evidence names platform and client arm; the browser arm is
   proven through `issues/20260829-o14-real-browser-arm-harness.md`'s runner
   by reading the receipt from the page.

## Open questions

1. Can the engine tell "no change" from "not dependent" without cost on the
   scheduler path, or should v1 ship the collapsed verdict and reserve the
   field? (The lane answers; the receipt schema is stable either way.)
2. Default grace for the detector: 3,000 ms is chosen to sit above the
   Linux-measured 30–144 ms deliveries and the lanes' 3 s observation
   window; measure before shipping.
3. Should `explainAfter` accept a settlement receipt object directly
   (`{ mutation }`) in addition to a bare `commitVersion`? Ergonomic, no
   semantic change.
4. Whether a dev-loop CLI projection (`snapback explain-subscription`) is
   wanted before the overlay question in LLP 0219 OQ3 is settled.
