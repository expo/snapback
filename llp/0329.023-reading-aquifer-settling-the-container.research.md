## Summary

[LLP 0329.022](./0329.022-panel-closeout-and-the-data-story.research.md) open
question 2 recorded the one live panel disagreement — whether a receipt-backed
resource and a foreign-fetch resource may share a **parametric** cell container —
and said deciding it "needs someone who knows Exact's runtime."

Nobody needed to. **Aquifer is built.** `aquifer/` is roughly 7,000 lines of Rust
and `packages/exact-snapback-provider/` roughly 13,000. Reading them settles the
disagreement, refutes part of each panelist, and surfaces something neither was
arguing about.

> **Codex is right about the container, and the code satisfies his condition by
> construction. Grok is right about exactly one field — `empty: bool` — and that
> field is the precise place Snapback's coverage semantics cannot be expressed.**

## F1 — The container is parametric, and the engine cannot inspect the payload

`aquifer/src/cell.rs`:

```rust
pub enum CellDataState<Value> {
    Pending    { previous: Option<Value> },
    Ready      { value: Value, empty: bool },
    Error      { error: CellFailure, previous: Option<Value> },
    Refreshing { value: Value },
}
```

`CellState<Value>`, `ProviderNormalizationState<Value>`, `Cell<Value>` and
`ProviderEvent<Value>` are all generic. The **only** trait bound in `cell.rs` or
`normalization.rs` is `Value: Clone`, on `apply_provider_event`. Normalization
dispatches on event kind and current status; it never reads the value.

Codex's stated test was: *"A generic container is harmless if it carries
`SnapbackResourceState<T>` unchanged; a generic data API that projects both paths
into `Rows<T> + completeness` is not."* The first clause is not merely achievable —
**it is what exists.** The engine is structurally incapable of the projection grok
feared, because it has no capability with which to look inside `Value`.

Grok's formulation — *"separate axes on a shared cell are still cell state"* — is
therefore **false for the payload.** The data axis
(`pending | ready | error | refreshing`) is arrival lifecycle; LLP 0284's
connection axis (`connecting | live | polling | stale | disconnected`) is transport
liveness. Neither is a claim about the payload's relationship to the authoritative
dataset.

## F2 — One field leaks, and it is the load-bearing one

`empty` is not parametric. It is a `bool`, and it is derived by the engine's host
seam rather than authored by the provider. `normalization.rs`, on `ProviderEvent`:

> "The chunk-2 host seam owns hostile-object decoding, row/page admission, and
> deriving `value` plus `empty`; **providers do not author canonical cell state.**"

The full chain, traced:

| Step | Site |
|---|---|
| host seam inspects content | `boundary.rs:314` — `let empty = materializer.is_empty(&value);` |
| enters the event | `ProviderEvent::RowsArrived { value, empty, connection }` |
| enters canonical state | `CellDataState::Ready { value, empty }` |
| reaches the view grammar | `packages/exact-contract/src/runtime/readiness.ts:273` — `{ kind: 'empty' }` |

So a **content-derived claim, computed by the engine, becomes a user-visible
rendered state** — as one bit.

For a receipt-backed resource that bit is ambiguous between two claims that
[LLP 0329.021](./0329.021-where-the-snapback-server-sits.research.md) P5 proved are
issuable by different parties:

- **no row exists** — an assertion about the authoritative dataset, issuable only
  by an authority;
- **no row held** — an assertion about this store's coverage, issuable by the
  client.

`empty: bool` flattens them. That is exactly LLP 0329.015 K2's silent-wrongness
class — an empty result and an unheld range rendered identically.

**Precedent that this field is known to be delicate:** RFC 0498 §4.2 records that
RFC 0263's capability-shaped refusal had to be ruled *distinct from* `empty` at
boot. That is one conflation on this field already found and defended against. This
is a second, and it is undefended.

## F3 — The shipped provider has the `Predicted` half and none of the coverage half

`packages/exact-snapback-provider/` is not a thin fetch adapter. Its dependencies
include `rusqlite` (bundled) and `ureq`; `owner.rs` describes itself as "the owner,
cache, subscriptions, optimistic… a document/result cache plus a monotonic outbox;
SQLite is the reference store" (Exact LLP 0331 §5.2/§7.3), and
`mutation_runtime.rs` exercises optimistic replacement.

So it already serves reads from a local store while offline, and already runs an
optimistic overlay.

A word-boundary search of its ~13,000 lines for `coverage`, `absence`, `absences`,
`Fresh`, and `Predicted` returns **nothing**. The only `Receipt` type is the
write-side one from §4.6 (`http_transport.rs`'s `server_receipt`), not a closure
receipt.

**The distinction this whole arc exists to defend is the one the shipped provider
lacks, and `Ready { empty: bool }` is where its absence currently hides.**

## F4 — §4.7 contradicts the settled position, more directly than the container does

RFC 0498 §4.7 states: **"local-first is a provider choice plus policy, not an app
rewrite."**

[LLP 0329.022](./0329.022-panel-closeout-and-the-data-story.research.md)'s settled
position holds the opposite, in codex's words: *"There is no moment when the same
declaration silently acquires stronger meaning."*

These cannot both stand. §4.7 makes local-first reachable by swapping a provider and
a policy behind an unchanged declaration; the settled position requires a different
declaration with a non-coercible result type.

This matters more than the container question, and neither panelist raised it —
they were arguing about whether a shared container is safe *given* separate nominal
contracts. §4.7 is accepted text saying no separate contract is needed at all.
**Codex and grok are far closer to each other than either is to §4.7.**

## F5 — Two corrections to this family's own record

**Aquifer is Accepted, not Draft.** RFC 0498's header reads
`Status: Accepted (curation pass 2026-08-23)`, with AQ-A closed and AQ-D partly
landed. [LLP 0329.019](./0329.019-aquifer-amendments.research.md)'s Confidence
section says "it is Draft and moving," which is wrong and understates the cost:
amendments go through §8 against landed workstreams, not into a moving draft.
Corrected in that document.

**Rust HTTP on the no-JS tier is built, not planned.** LLP 0329.019 and this
author's earlier reasoning treated RFC 0498 §4.4's "Rust providers on
`native-total` — HTTP fetch" as a plan. `exact-snapback-provider` depends on
`contract-native` and adds `ureq`, with 973 lines of `http_transport.rs` carrying
typed receipts and bounded decoding. The error came from reading `contract-native`'s
own `Cargo.toml` — which indeed has no HTTP client — and concluding the capability
was absent from the tier, rather than checking what depends on it.

## Suggested fix

`is_empty` is a **trait method on `materializer`** — the single quarantined point
where anything in the engine inspects content. That makes the fix small and local:
give emptiness more than one bit for providers that carry coverage evidence
(`EmptyByAuthority | EmptyByCoverage | Unknown`), leaving fetch-shaped providers
exactly as they are.

This satisfies the panel's C3 without an A1-style completeness field: the engine
still does not author the distinction, and the provider still does not author
canonical cell state — the *materializer for a receipt-backed provider* reports what
its receipt already proves.

## Confidence

High on F1 and F2's type chain. Both were read directly from source, and the four
chain sites are cited above.

High on F3's absence result — but see the method caution below.

Medium-high on F4. The §4.7 sentence is quoted exactly; what is interpretation is
whether "provider choice plus policy" is meant as strongly as it reads. §4.1–4.3,
§4.5 and §5–7 remain unread, and one of them may qualify it.

**Not established: whether any of this is live rather than latent.** The type chain
and the missing vocabulary are proven. Whether the offline cache can actually serve
a partial result as `Ready` requires reading `owner.rs`'s cache read path, which was
not done. That is the difference between a latent design gap and a user-visible
defect, and it should decide how loudly the issue is filed.

## Method caution

A first pass searched the provider for `Partial` and found 25 hits in
`provider.rs` alone, which read as strong evidence that coverage vocabulary was
present. **Every one was a `PartialEq` or `PartialOrd` derive.** The re-check
(`grep -vE "PartialEq|PartialOrd"`) returned nothing.

This is the **fourth** substring false-positive in this arc, after the three
recorded in [LLP 0329.008](./0329.008-the-ladder.research.md). The pattern is
identical every time: a short token that is also a fragment of common boilerplate.
The habit that caught it — re-running any grep whose result would *change the
conclusion*, with the boilerplate excluded — is the one worth keeping.

## Open questions

1. Live or latent (see Confidence). Requires `owner.rs`'s cache read path.
2. F4 is the bigger conflict and is unaddressed by the panel. Does §4.7's
   "provider choice plus policy" survive the settled position, or does the settled
   position require amending accepted text?
3. Does the parametric container hold at the **wasm ABI** boundary?
   `aquifer/src/wasm_abi.rs` and `wasm_machine.rs` were not read, and a serialized
   crossing is where an opaque `Value` is most likely to get flattened.
