## Summary

[LLP 0329.004](./0329.004-composition-expressiveness-constraint.research.md)
put one question ahead of every other in the rebuild: *can an analyzable read
language express bounded fan-out, grouped counts, multi-table derivation, and
bounded graph traversal while preserving static read-set derivation, retention
eligibility, and local re-execution?* If not, the unanimous "refuse, do not
degrade" design of LLP 0329.000 buys offline at a price the benchmark has
already shown Snapback losing.

This document's answer is **yes — and the question is slightly wrong in a way
that matters.**

1. **Expressiveness was never lost to restriction. It was lost to a registry.**
   Snapback's analyzable surface was built one *admitted shape* at a time
   (two-source unique join, one-parent-one-child, snapshot-batch tuple), each
   with its own cursor identity, evidence model, noninterference proof, and
   maturity ceremony — ~700 reviewed lines for the join, ~1,700 for one parent
   and one child page (LLP 0120 finding 6). A registry of shapes cannot converge
   to expressiveness because every shape costs a Spec. A *general closed
   algebra* — non-recursive relational algebra with bounded windows and an
   admitted aggregate set, i.e. roughly SQL-92 without recursion — is fully
   analyzable and covers every shape in the LLP 0120 census and every read in
   the Clique brief (§2). The proof that such a language is expressive enough
   *for agents* is already in the scoreboard: the `sol-supabase` lane — plain
   SQL plus row-level security — reached 7/8 with the highest schema score in
   the matrix (B1 92) and tied Convex (record §2–3).
2. **The three capabilities do not all need the same thing from the language.**
   Reactivity needs a read set, which can be recorded dynamically (Convex) or
   derived statically. Retained reads need only determinism and a per-principal
   result cache. Only *local prediction* needs the program to be locally
   executable — and it needs that of **mutations and of each query node's
   predicate and order**, not of arbitrary read assembly (§1). So the
   restriction that actually buys offline is narrow and falls on a boundary
   authors already hold: "a write is a transaction; a read is a relation."
3. **The benchmark loss was caused by the escape hatch, not by restriction.**
   The deepest Snapback lane lost realtime custody on *custom JS projections*
   ("nested reaction reads committed correctly but did not wake the active JS
   live query"), had "no SQL-grade aggregate path", and had "read-only
   analytical handlers … masquerade as mutations" (lane essay/diary). Agents
   fell to the hatch because the registry refused their shapes; the hatch is
   then unretainable and unreliably live. A general algebra removes the reason
   the hatch exists, which is the only way to make "refuse" survivable.

The recommended design (**Proposal A**, §3.1) is a general closed algebra with
per-operator semantics (the LLP 0309 methodology, promoted from optimization to
the definition of the language), compiler-decided materialization for
aggregates, row rules as relational predicates in the read set, time as a
declared-granularity input relation rather than a forbidden ambient, restricted
DML mutations that are the optimistic predictor, JavaScript only in effects that
materialize tables, and a client that is **SQLite plus a sync protocol plus an
outbox** running the same plans against delivered rows for *named queries
only*. Four alternatives are analyzed and either folded into A, kept as a named
fallback, or rejected with reasons (§3.2–3.5).

This is a research answer with proposals; it ratifies nothing. Its cheapest
disconfirmation is a one-day paper exercise (§6, step 1), and it names four
decisions only the author can make (§7).

## 1. Reframing the question: what each capability needs from the language

LLP 0329.004's trilemma treats "the language" as one choice that fixes all
three cells. It is more useful to ask, capability by capability, what property
of *which part* of the program is load-bearing.

| Capability | What it needs | From which part of the program | Static or dynamic? |
|---|---|---|---|
| Server reactivity (live) | the read set, so a commit can wake dependents | queries **and rules** (LLP 0053: a membership-gated query joins its ACL, so an ACL write wakes it) | either — Convex records it dynamically; DK-3 derives it statically |
| Incremental maintenance (delta, not rerun) | an algebraic form with per-operator delta rules | queries | static — but this is a *cost* property, not a capability; rerun-and-diff is a correct lowering |
| Retained reads (cold open from disk) | determinism given `(query, args, viewer, snapshot)` plus a per-principal result cache | queries | either — any transactional read is deterministic; the current `rqsEligible` refusal of JS handlers is about *proving* closed inputs, not about executing them |
| Local prediction (optimistic + offline compose) | the mutation's write effect computable from args plus local rows; each affected query node's membership predicate and order evaluable locally | **mutations**, and the **predicate/order of each query node** | static — this is the one cell that forces restriction |
| Bounded work / declared reach | statically known cost dimensions | queries, rules | static — an *evidence* property the corpus prizes (LLP 0080, 0110), not a capability the app author feels |
| Authorization | deny-by-default row predicates, evaluable at the server and (for prediction) locally from witnesses | rules | static |

Three consequences:

- **Only prediction forces restriction, and only of mutations plus per-node
  predicates.** The *assembly* of a read — nesting, fan-out, derivation — does
  not need to be locally executable to be live or retained; it needs to be
  locally executable only if the client re-runs the whole query for
  prediction. But a client that re-runs an admitted plan over delivered rows
  (§3.1) gets that for free, so the constraint collapses to "the query is an
  admitted plan," which a general algebra satisfies by construction.
- **Static derivation is not required for reactivity.** All three sketches
  assumed it was (LLP 0329.004 F3). The v1 server can wake subscriptions by
  recorded read-set touch — Convex's mechanism — and adopt per-operator delta
  maintenance operator by operator (LLP 0309's "generic derivation, per-kind
  admission") as an optimization. That removes the LLP 0209 G0–G3 ladder from
  the critical path of shipping a *uniformly* live surface.
- **"Bounded" is where the corpus's values and expressiveness actually
  collide** — not in the algebra. A per-shape static examined-entry ceiling
  (LLP 0080's `take + 1`) does not survive a rule like "shares a conversation
  with the viewer," whose cost is `window × viewer's membership count`. Postgres
  RLS has the same cost and is affordable because the semi-join is
  index-served. The rebuild must decide whether "index-served everything, with
  reported cost dimensions" is an acceptable evidence model (§7, decision 1).
  If it is not, no general language is admissible and the registry returns.

## 2. Evidence that a closed algebra is expressive enough

### 2.1 The scoreboard already contains the experiment

The `sol-supabase` lane is SQL for reads, PL/pgSQL for writes, RLS for rules,
and a change feed for realtime. It scored 7/8, B1 (schema) 92 — the highest in
the matrix — and B3 (live queries) 78; its holistic self-rating tied Convex at
74 (record §2–4). Its weaknesses were hosted-auth rate limits and O5, not
expressiveness. Meanwhile the deepest Snapback lane's own essay says "I missed
SQL badly for Insights-shaped aggregation" and "Supabase SQL or a Postgres
view would be materially simpler for six totals, seven buckets, and top-ten
ranking." The agents told us which language they can write. It is SQL.

This is evidence about *reads*. For writes, PL/pgSQL is imperative-with-SQL;
the corresponding claim for a restricted DML language is tested in §2.3.

### 2.2 The Clique read census, mapped to algebra nodes

algebra with bounded windows, to-one and bounded to-many edges, semi-joins
(including two-hop "through" edges, which LLP 0209 §2.2 already admits), and a
small aggregate set (`count`, `sum`, `min`, `max`) that may be grouped, nested
under a parent, and ordered on. Rules are conjoined at every node.

### 2.3 The Clique write census, mapped to restricted DML

The mutation side is where LLP 0320's race argument lives and where a
restricted language is most likely to be too tight. The brief's writes:

| Write | Shape |
|---|---|
| profile edit, chat config, poll vote, mark delivered/read | single-row update/upsert with an `assert` (monotonic receipt state) |
| create post/reply, send message (+quote, +media ref), react, follow, like, repost | insert, some under a unique index (idempotent pair rows) |
| unlike, unfollow, unreact, leave/remove member | delete under rule |
| create-or-get DM | `let existing = (select …); if existing is null then insert conversation + two memberships; return coalesce(existing, new)` |
| create group, add member (admin rule) | multi-row insert in one transaction |
| edit within 15 min, delete-for-everyone within 1 h | update with `assert commitTime - created_at < …` — mutations *may* read authoritative time |
| view-once open | insert unique open row; the second insert fails the unique index and is the denial |
| sequence numbers, message counts (M7 backfill) | `allocateSequence` / maintained count — both already exist as IR primitives (LLP 0135; `define.mjs` `allocateSequence`) |
| daily digest, push emission | **effects**: scheduled or event-triggered JS that reads named queries and calls mutations |

Every write fits "DML + `let` + `if` + `assert` in one server transaction."
The corpus has already proved the core of this: the existing mutation IR
carries `guard`, `cond`, `letBind`, `allocateSequence`, and `runMutation`, the
client already evaluates it for prediction (`generated-mutation-ir.mjs`,
`optimistic-rebase.mjs`), and LLP 0155 Move 4 recorded that the generated IR
"proved sufficient … no Candidate B authoring extension was needed." What is
new is only that this becomes *the* mutation form rather than one of two.

### 2.4 What genuinely falls outside, and where it goes

- **Recursion** (folder trees, org charts, threaded replies of unbounded
  depth): refused; the diagnostic offers the closure-table pattern maintained
  by the mutation. Postgres teams do the same for reactive workloads.
- **Non-relational compute** (model scores, text processing, external data):
  an **effect** — JavaScript with I/O, at-least-once, never client-callable,
  never live — that writes a table through a mutation. A view then reads the
  table. This is LLP 0329.001's "materialize via effect," and it is the *only*
  hatch. It is a different kind with a different client API, so the capability
  boundary sits on a concept boundary the author already holds (a background
  job is not reactive), never on a spelling.
- **Ad-hoc client composition** over the local store (Zero's ZQL): not
  admitted in v1 (§3.1.6). The local engine is general; *admission* is named
  queries only, so completeness is one bit per `(query, args)`.

## 3. Proposals

### 3.1 Proposal A — a general closed algebra, per-operator semantics, SQLite-shaped client (recommended)

**One sentence:** the read language is a grammar, not a registry; everything
client-readable is an admitted plan; admitted implies live, retained, and
authorized; the client runs the same plans over delivered rows in SQLite.

#### 3.1.1 The language

- **Relations, rules, queries, mutations** in one expression language
  (LLP 0329.003's four sorts), plus **effects** outside it. Rules are
  predicates over `this` and `viewer()`; queries are non-recursive relational
  expressions with nested result shapes; mutations are DML with `let`, `if`,
  `assert`, and `return`.
- **Admission rules, all decidable at `check` time, each with exactly one
  repair that never weakens authorization:**
  1. every scan is an index range (filter and order must match a declared
     index prefix) — repair: "add index on (…)";
  2. every collection node has a window (`limit`, or is under a parent with a
     per-parent bound) — repair: "add `order by … limit N`";
  3. every table has rules for each effect; no default — repair: the three
     templates (owner / member / `public`);
  4. no recursion — repair: closure table;
  5. no ambient except `viewer()` and `now(granule)` (§3.1.4) — repair: pass
     `since` as an argument or declare a granule;
  6. every rule's semi-join is index-served — repair: "add index on (…)".
- **Everything else is admitted.** Joins, nested shapes, grouped aggregates,
  aggregates under parents, ordering on aggregates, two-hop `exists`,
  correlated scalar subqueries. The compiler does not decide whether a shape
  is "in the registry"; it decides whether the plan satisfies six rules.

#### 3.1.2 What is derived (and forbidden to declare)

Read set including rule tables; write set; witness closure for prediction
(the rows a client must hold to predict a mutation — derivable only because
rules, queries, and mutations share one expression language); required
indexes; result types; whether a result is viewer-independent (public rules,
no `viewer()`) and therefore shareable across principals; cost dimensions
(`window × fanout × rule fanout`) reported in the build receipt.

#### 3.1.3 Reactivity: dynamic first, incremental per operator

v1 wakes a subscription when a commit touches its read set, evaluated by the
existing DK-3 matcher discipline generalized to plan nodes, and re-runs the
plan (index-served, so cheap) and diffs. Per-operator delta rules
(LLP 0309) are adopted operator by operator where measured demand warrants —
single-table windows first (DK-3 measured ~5,200× cheaper than warm re-query),
then aggregates, then ordered windows with boundary displacement (the case
LLP 0209 §7 found hardest). "Uniformly live" ships before "incrementally
maintained."

#### 3.1.4 Time as an input relation with declared granularity

Every sketch banned `now()` and every Clique lane re-derived the
client-clock-argument workaround (Diary 0114: "no paved path"). Instead: `now(g)`
with `g ∈ {minute, hour, day}` is admitted in rules and queries, and the clock
is modeled as an input relation that "writes" once per granule. The read set of
a plan that reads `now(hour)` includes `clock@hour`; the server re-evaluates
such subscriptions at the granule boundary (a smart matcher keeps the
result's next boundary timestamp and skips granules that cannot change it).
The result is still a deterministic function of `(args, viewer, snapshot,
granule)`, so it retains; the client re-evaluates locally with its own clock
(expired rows disappear offline; the server re-checks on reconnect). Disappearing
messages, edit windows, 24 h Trending, and 7-day buckets all become ordinary
programs. Mutations read authoritative `commitTime` exactly (settled, as in
LLP 0329.002).

v1 may ship only the scheduled-tombstone form (an effect deletes expired
rows); the clock relation is the paved successor and should be designed in from
the start so the tombstone form is not the *only* answer that gets learned.

#### 3.1.5 Aggregates: compiler-decided maintenance, visibility before aggregation

- An aggregate node in a live query is **maintained state** by default
  (Materialize/DBSP posture; LLP 0120 option 5's variant 5 result semantics):
  reads are point lookups, the initial build is a one-time scan reported in the
  receipt at deploy or schema-successor time, and each write updates a
  statically known number of aggregate rows. Every *request* is therefore
  bounded without refusing any aggregate shape. This dissolves LLP 0120's
  five-variant result-semantics question for the default case; the capped
  variant (`count … limit 100`, rendered "99+") stays available as the
  product-honest spelling for unread-style counts.
- **Visibility before aggregation.** The rule is conjoined at the aggregated
  source, so a count never summarizes rows the viewer cannot see. The planner
  classifies each aggregate's rule as *group-invariant* (all members of a
  conversation see the same message count → maintained per group, checked per
  viewer), *viewer-keyed* (unread against a principal-bound `read_state` →
  maintained per `(group, viewer)`, or computed at read over an index range
  when the per-viewer population is small), or *neither* (computed at read).
  The existence-leaking global total over protected rows (LLP 0120
  §Noninterference) remains refused with the partition-by-authority repair.
  This is real design work, but it is one design for all aggregates instead of
  one per shape.

#### 3.1.6 The client: SQLite, sync, outbox — named queries only

- A per-principal encrypted local store (LLP 0329.002 D2 contract): SQLite on
  every arm (wasm on web, `expo-sqlite`, native), holding rows delivered for
  subscribed named queries, tagged by source subscription, with pending rows
  from the outbox overlaid.
- Rendering and prediction **re-run the admitted plan locally** over the store.
  Because the plan is the same IR the server ran, LLP 0209 §8's
  "byte-identical local evaluation" is a property of using one lowering, not
  a conformance twin to maintain. Search offline is local FTS over delivered
  rows — free, which closes an M5 requirement that cost lanes.
- **Completeness is one bit per `(query, args)`**, attested by the server at
  last sync. A locally re-run named query with attested args is `fresh` or
  `stale`; anything else is `partial`. There is no client permission engine:
  every stored row was delivered to this principal by the server, and
  optimistic rows carry `pending`. This is the half of Zero worth copying
  (query-driven partial materialization, useful local rows, shared mutators)
  without the half LLP 0329.003 correctly warned about (ad-hoc composition
  requiring client-side permissions and general completeness proofs).
- Revocation while disconnected is an **information limit, stated once**:
  the last authorized snapshot is shown as `stale`; an authorization epoch
  recheck on reconnect purges newly unauthorized rows before anything is
  presented as `fresh`; sign-out destroys the key; a deployment may set a
  maximum offline age. No leases, custody modes, witnesses, or eligibility
  classes.

#### 3.1.7 JavaScript out of the data plane

Mutations lower to an IR interpreted in Rust (server) and in the client
runtime; no JS engine sits in the authoritative request or transaction path.
Effects run JS, cold-started, with I/O, calling mutations. This is
LLP 0329.000 F-A, made concrete: the Hermes/Ibex runtime contract, the DK-4
warm-VM pool, and the LLP 0048 conformance twin leave the request path and
become an effect runner. It contradicts LLP 0009 DK-5's enduring
"device parity with Exact" posture for the data plane (§7, decision 2).

#### 3.1.8 Spelling

Semantics above; spelling is secondary and should be measured with the
benchmark loop in week one. The lean, with an argument none of the sketches
made: **SQL-shaped text** — a `model` file of `table` / `rule` / `query` /
`mutation` statements with a nested-select extension for result shapes
(EdgeQL and ZQL are the nearest precedents for nesting; the nested-shape
projection is the one thing plain SQL lacks) — because LLP 0329 F5 measures
surface size as a *retrieval tax*, and SQL is the one query language whose
retrieval cost for an agent is approximately zero. A novel builder DSL
(LLP 0329.001) or a build-time TypeScript AST (LLP 0329.002) is a retrieval
tax by construction, however small. The six admission rules are a small delta
from SQL an agent already knows, and each diagnostic contains the rewrite.
Types are generated from the model, so TypeScript stays where it belongs: in
the generated client.

#### 3.1.9 Good

- Answers the load-bearing question affirmatively with evidence the corpus
  already holds (§2), not with a promise.
- Removes the reason the escape hatch exists, which is the only way "refuse,
  do not degrade" survives contact with real apps (LLP 0329.004 F2).
- Collapses the capability matrix to one predicate — *admitted* — so
  `reads:`, `writes:`, `retainable`, `authorityIndependent`, `auth: 'public'`,
  and thirteen query flavors have nothing to select.
- One invalidation mechanism: LLP 0053's reframe ("a membership-gated query
  joins its ACL, so an ACL write wakes it") becomes the *whole* authorization
  story, and the "committed child insert did not wake the subscribed
  projection" bug class cannot occur because there are no opaque projections.
- The client becomes SQLite + sync + outbox — DK-9's target reached by
  refusing holes instead of proving around them.
- Reuses the corpus's real assets: the SQLite kernel, journal, and version
  stream; the DK-3 matcher; the mutation IR and its client evaluator
  (LLP 0133/0155); LLP 0309's methodology; the benchmark and diary loop; the
  diagnostic discipline (with ~30 families, not 3,934 codes).
- Genuinely differentiated: SQL-expressive, uniformly live, private data
  offline by default, on one scale-to-zero binary. Supabase has the first;
  Convex the first two; nobody in the matrix has all three.

#### 3.1.10 Bad

- **It is a compiler, planner, and (eventually) IVM engine over a general
  algebra with row rules.** That is a larger single program than any profile
  the corpus has shipped. Mitigation: rerun-on-touch v1 (§3.1.3) makes the
  planner the only day-one obligation; DBSP is the reference for the rest.
- **It relaxes the evidence model.** "Index-served everything with reported
  cost dimensions" is weaker than LLP 0080's per-shape static ceilings, and
  LLP 0115 constraint 1 ("no evidence regression") would forbid it as
  written. This is a values decision (§7, decision 1), and the honest
  statement is that the corpus prized a property that did not survive the
  benchmark.
- Aggregate maintenance under viewer-varying rules (§3.1.5) and ordered-window
  boundary deltas (LLP 0209 §7) are the hard engineering cores; both have
  rerun fallbacks but the fallbacks are what will ship first.
- The nested-shape SQL extension is unproven with agents; the spelling might
  need to be ZQL-like after measurement.
- Restricted DML may be too tight for a minority of writes (multi-step
  validation, retry loops). Proposal E is the named fallback.
- Recursion refusal will be hit by any hierarchy; the closure-table repair
  must be excellent or it becomes the next "no paved path."
- The clock relation is novel; if its semantics are wrong the failure is
  subtle. v1 can ship without it, at the cost of teaching the tombstone form.
- None of this touches the dev loop, identity binding, or generation protocol
  (LLP 0329.000 F-B). A perfect language with a Metro race still loses Clique.

### 3.2 Proposal B — the hybrid: dynamic read-set JS reads for reactivity, algebra for the retainable subset

This is LLP 0329.004's "fourth architecture" made into a design: keep
Convex-style `query` functions with recorded read sets (expressive, live, not
offline) beside algebraic views (live, offline). Analysis:

- **Good:** ships the most expressive read surface on day one; Convex proves
  the mechanism at scale; no planner needed for the JS form.
- **Bad, and disqualifying as a read form:** it is LLP 0329 F1 with better
  names. An agent asked for "unread count" reaches for whichever compiles
  first; if the JS read compiles and is live, the agent ships it and loses
  offline invisibly — exactly the current defect, exactly what LLP 0329.004
  OQ3 asked. Capability boundaries must fall on concept boundaries
  (LLP 0329.001 §2); "query (offline)" versus "computed query (online)" is a
  spelling boundary in a costume.
- **What survives:** the *mechanism* — recorded read-set wake — is exactly
  A's v1 server reactivity (§3.1.3). Dynamic recording is a fine way to be
  live; it is not a fine way to spell a second read kind. And JS compute that
  cannot be relational goes through an effect that materializes a table
  (§2.4), which is B's expressiveness with A's invariant intact.

**Verdict:** rejected as an authoring surface; adopted as an implementation
strategy.

### 3.3 Proposal C — read models only: materialize everything, single-table client

The Firestore/fan-out-on-write posture, and LLP 0329.003's named-query
position taken to its limit: every composed or aggregated shape is a declared
materialized view maintained on write; client-readable queries are
single-table windows over base tables and views. Analysis:

- **Good:** the client is exactly today's `rqsEligible` class, so DK-3 IVM,
  cold retention, and delivery all already exist for it; single-snapshot
  composition is trivial because the composite *is* a row; reads are O(1).
- **Bad:** write amplification is the author's problem (the M8 celebrity with
  900 followers is the brief's own stress case for exactly this); the author
  must think in read models before they have a product; a
  `conversation-with-members-latest-unread` row maintained per viewer is the
  per-viewer aggregate problem (§3.1.5) moved to the write path in full,
  with no planner to decide when it is unnecessary.
- **What survives:** the insight that *materialization is the right strategy
  for aggregates* and that the compiler, not the author, should choose it.
  A already folds this in (§3.1.5). Making the author write read models by
  hand is Proposal A with the planner deleted.

**Verdict:** folded into A as the aggregate strategy; rejected as the whole
design.

### 3.4 Proposal D — a Convex clone plus a result cache (no prediction)

The null hypothesis: dynamic read-set JS reads and writes, retained *results*
per `(query, args, principal)` shown as `stale` on cold open, no local
execution, optimistic updates app-authored. Analysis:

- **Good:** matches the backend that won the matrix, on the mechanism it won
  with; smallest build; retained reads come almost free.
- **Bad:** it is "not buying offline," not "buying offline cheaply." Offline
  compose, cross-device convergence, and pending/settled state — the M6/M8
  half the Convex lane itself called "application machinery … a backend whose
  central abstraction includes durable local state should make this feel more
  native" — stay application-owned. It also keeps JS in the authoritative
  path and keeps declared-reach evidence at zero.
- **When to choose it:** only if §6 step 1 shows the algebra cannot express
  the Clique census on paper. Given §2, that outcome is unlikely.

**Verdict:** the honest fallback if A's premise fails; not recommended.

### 3.5 Proposal E — A's reads with shared TypeScript mutators (Replicache/Zero)

Keep the algebra for reads and rules; write mutations as ordinary TypeScript
against a restricted `db` API, executed on the client for prediction and on
the server for authority — no lifting, so LLP 0320's race objection does not
apply (prediction is a guess; the server decides). Analysis:

- **Good:** mutation expressiveness is Convex-grade; the create-or-get and
  multi-step validation cases are trivial; agents write it fluently.
- **Bad:** JS returns to the authoritative path (contradicts F-A and
  LLP 0314); the witness closure is no longer statically derivable, so the
  compiler cannot tell an author at `check` time which rows the client must
  hold, and predictions are `partial` more often; the write set is dynamic, so
  invalidation must record it; client/server equivalence is by shared source,
  not by construction.
- **When to choose it:** if §6 step 1 finds the DML form contorts more than a
  small minority of the write census.

**Verdict:** the named fallback for the mutation side only. The read side
does not change.

## 4. Recommendation

Pursue **Proposal A**, with E as the mutation-side fallback and D as the null
hypothesis, and treat §7's four decisions as prerequisites.

The single most important framing change relative to the sketches and to the
corpus: **generality is cheaper than a census of shapes.** The corpus's
relational lineage — LLP 0080 → 0110 → 0135 → 0157 → 0209 — is a
monotonically growing registry, each entry reviewed to the same exacting
standard, and the registry still admits no aggregate. A grammar with six
admission rules and per-operator semantics admits every shape in §2.2 in one
Spec, because the evidence attaches to operators and composes.

What I am least sure about, in order: (1) that "index-served with reported
cost dimensions" will be accepted as the evidence model — if not, A is not
admissible and the question reverts to D; (2) the aggregate-under-rule planner
classification; (3) the spelling; (4) whether the clock relation should ship
in v1.

## 5. What a start-over keeps and drops

**Keep:** the Rust + SQLite authority with its journal and version stream; the

evaluator as the seed of the DML language; LLP 0309's methodology as the
*definition* of the algebra's semantics; the LLP 0201 instrument, the benchmark

**Drop:** two authoring profiles; the `define*` constructor zoo and thirteen

read or write form; leases, custody modes, completeness witnesses, and

generated reference forests; the 20 MB embedded guide.

## 6. Cheapest disconfirmations, in order

1. **Paper Clique (one day).** Write the complete M1–M8 model — every table,
   rule, query, and mutation — in A's language, with no implementation.
   Record every shape that needs contortion or refusal. This is the single
   cheapest way to falsify the Summary's claim 1, and it also decides E versus
   A for mutations. Do it before writing any code.
2. **Planner spike (one week).** Parse the paper model, enforce the six
   admission rules, lower to SQLite, derive read/write sets and witness
   closures, emit the build receipt with cost dimensions. Measure `check`
   latency (target: under 100 ms).
3. **Rerun-on-touch reactivity (one week).** Matcher over plan nodes with
   rule tables in the read set; two clients; the receipt/reaction/membership
   invalidation cases that failed in the 0.1.29 lanes.
4. **Local SQLite re-execution with outbox overlay (one week).** Cold open,
   offline compose, `partial`/`stale`/`fresh` states, epoch recheck on
   reconnect, sign-out key destruction.
5. **Maintained aggregates (two weeks).** Group-invariant and viewer-keyed
   classification; Insights and Trending under load with the celebrity case.
6. **Agents build Clique M1–M3 on it** against Convex/Supabase/PocketBase,
   private-chat-first, with the retrieval eval reset to zero seeds.

Steps 2–4 can proceed in parallel after step 1. None depends on IVM.

## 7. Decisions only the author can make

1. **Evidence model.** Accept "index-served everything, cost dimensions
   reported in the receipt" in place of per-shape static examined-entry
   ceilings, explicitly overruling LLP 0115 constraint 1 for the rebuild. Without
   this, no general language is admissible.
2. **JS out of the data plane.** Overrule LLP 0009 DK-5's device-parity
   posture for reads and writes; keep JS for effects only. This is
   LLP 0329.000 F-A, and it is the largest simplification available.
3. **Named queries only in v1**, with ad-hoc client composition explicitly
   unadmitted until demand is measured — LLP 0329.000 D3 resolved in
   LLP 0329.003's direction on the *admission* axis while keeping a general
   local engine underneath.
4. **Spelling to be measured, not chosen** — with SQL-shaped text as the
   default hypothesis and the benchmark loop as the instrument.

## 8. Relationship to LLP 0329.012

**Agreement (independently reached):** the answer is yes; the loss was to a
registry of products, not to restriction; one bound-carrying algebra with
rules in the same language; named operations as the sync unit with
compile-time composition rather than a client query engine; effects as a
different kind that writes tables; JS out of the data plane; no query/query
hybrid; the LLP 0157 growth rule is the thing not to repeat; aggregates over
growing groups are *maintained* rows; visibility before aggregation; runtime
states (`fresh`/`stale`/`partial`) as information, not constructors.

**Genuine disagreements, each worth an author call:**

1. **Static ceiling versus index-served cost.** LLP 0329.012 keeps a global
   examined-entry ceiling `G` with cardinality as a type (`Unbound<T>` cannot
   execute) and refuses plans whose worst-case bound product exceeds `G`.
   This document argues (§1, §7 decision 1) that rules break that model: the
   "users the viewer shares a conversation with" rule (LLP 0329.002's
   `sharesConversation`) is an `exists` over the viewer's memberships, which
   is `Unbound` in the type calculus — so the calculus either refuses a
   correct and ordinary rule or forces `.take(N)` inside it, which changes
   its meaning to "among the viewer's first N conversations." Postgres RLS
   runs exactly this rule affordably because it is index-served. The
   disagreement is about what "bounded" must mean for *rules*; it is the
   crux of decision 1 and the paper-Clique step (§6) will surface every
   instance.
2. **Who decides maintenance.** 0329.012 makes `maintainCount` an explicit
   author choice so write-path cost cannot be implicit; this document makes
   maintenance the compiler's default for aggregate nodes with the cost in the
   receipt (§3.1.5). Explicit is more honest; implicit is one fewer concept
   for an agent. Either is defensible; the retrieval-tax argument (§3.1.8)
   leans implicit.
3. **The client evaluator.** 0329.012: an IR interpreter over a per-operation
   materialization closure — "it is not SQL." This document: SQLite running the
   same lowering over delivered rows (§3.1.6), because SQLite is already on
   every arm, local FTS comes free, and one lowering eliminates the
   conformance-twin problem. The IR-interpreter route keeps the closure
   strictly per operation; the SQLite route shares rows across named queries
   and marks anything not attested as `partial`. The two are not far apart —
   both refuse ad-hoc queries — and the choice is an implementation bakeoff.
4. **Recursion and time.** 0329.012 admits `recurse(depth, fanout)` as an
   operator with a geometric bound and bans `now()` outright; this document
   refuses recursion (closure tables) and admits `now(granule)` as an input
   relation (§3.1.4). A bounded `recurse` is analyzable and is the better
   answer for hierarchies; this document concedes it. The clock relation is
   this document's addition, motivated by the measured "no paved path" for
   clock-dependent visibility (Diary 0114).

**What this document adds:** the capability decomposition showing that only
prediction forces restriction and static derivation is not required for
reactivity (§1); the Supabase lane as a measured existence proof for SQL
reads (§2.1); the complete Clique read and write census rather than the four
LLP 0120 shapes (§2.2–2.3); rerun-on-touch as the v1 server mechanism that
takes IVM off the critical path (§3.1.3); the clock relation (§3.1.4);
group-invariant/viewer-keyed rule classification for maintained aggregates
(§3.1.5); Proposal E as the mutation-side fallback (§3.5); the SQL
retrieval-tax argument for spelling (§3.1.8); the paper-Clique
disconfirmation as the first step, before any code (§6); and the four author
decisions (§7).

High that §1's decomposition is correct and that only prediction forces
restriction. High that a non-recursive algebra with bounded windows and a
