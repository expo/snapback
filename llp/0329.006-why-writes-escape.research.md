# LLP 0329.006: Why writes escape the plan language

**Type:** Research
**Status:** Draft

## Summary

[LLP 0329.005](./0329.005-authoring-shape-census.research.md) measured that 74% of
writes escape to `defineJsMutation` and left the cause open. This document answers
it, and the answer relocates the whole rebuild question.

> **A declarative mutation plan can only read rows by primary key. Every write whose
> correctness depends on a non-key lookup — a uniqueness check, a membership check,
> any relational invariant — must therefore be a JavaScript handler, and a JavaScript
> handler forfeits optimistic prediction and cold retention.**
>
> The capability loss in real applications is caused by the *write* path's read
> restriction, not by the query language.

Every design proposal in this family ([LLP 0329.000](./0329.000-three-family-design-sketches.research.md),
six sketches across two rounds and three model families) proposed reforming the
*read* language. The measured cause is elsewhere.

## Findings

### F1 — The escape rate rises with application complexity, sharply

Post-vocabulary demos (created on or after 2026-07-09), grouped by schema table
count:

| Application size | n | JS mutations | Plan mutations | Escape |
|---|---|---|---|---|
| ≤ 3 tables | 13 | 20 | 22 | **48%** |
| 4–6 tables | 13 | 50 | 10 | **83%** |
| ≥ 7 tables | 4 | 47 | 6 | **89%** |

Mean schema size: all-declarative backends **2.7 tables**, all-JS backends **4.9**.
**No demo with more than four tables uses declarative mutations exclusively.** The
flagship benchmark instrument, `coterie` (14 tables), uses 25 JS mutations and zero
plans.

### F2 — It is not a historical artifact

The plan-step vocabulary (`insertEach`, `deleteWhere`, `letBind`, `elseError`)
landed 2026-07-09; `defineMutation` and `runtimeNow` on 2026-07-03. If the escape
were legacy, it would fall after that date. It rises:

| Backend created | JS | Plan | Escape |
|---|---|---|---|
| 2026-06 | 9 | 8 | 53% |
| 2026-07 | 41 | 17 | 71% |
| 2026-08 | 76 | 23 | 77% |

Before 2026-07-09: 47% escape. After: 75%. **Widening the plan vocabulary did not
pull authors onto the paved path.**

### F3 — The choice is per-application, not per-mutation

Of 30 post-vocabulary demo backends, **20 never call `defineMutation` at all** and 8
never call `defineJsMutation`. Only 4 mix. If the driver were per-write shape, mixing
would dominate: a plan for the simple insert, a handler for the hard one. Instead
each application picks a lane and stays in it, which is an authoring-stance signal
rather than a per-operation capability signal.

### F4 — The wall: a mutation plan can only read by primary key

This is the finding. It is verified against the Rust manifest types, which LLP 0037
makes the single source of truth for shared artifact shapes.

`MutationStep` in `crates/snapback-types/src/manifest/types.rs` has exactly these
variants: `AssetCollection`, `AllocateSequence`, `Insert`, `Patch`, `Delete`, `Get`,
`Guard`, `AssertCurrentRelation`, `Let`, `DeleteWhere`, `InsertEach`,
`AssertSourceChanged`.

In the dependency walker (`handler_plan`), **every mutation step that binds rows for
later steps reads by primary key**:

```rust
MutationStep::Get    { table, id, .. } => { self.read(table, "point", None); … }
MutationStep::Patch  { table, id, .. } => { self.write(table, "patch");
                                            self.read(table, "point", None); … }
MutationStep::Delete { table, id }     => { … self.read(table, "point", None); … }
MutationStep::AssertCurrentRelation { table, scope_table, .. }
                                       => { self.read(table, "point", None);
                                            self.read(scope_table, "relationIncarnation", None); … }
```

> **Correction, 2026-08-28.** An earlier revision of this section said "every read a
> mutation step performs is classified `point`," naming `AssetCollection` as the sole
> exception. That is **wrong**. The same walker classifies `DeleteWhere` as a
> **query-kind** read carrying the full filter vocabulary:
>
> ```rust
> MutationStep::DeleteWhere { table, filter } => {
>     self.write(table, "deleteWhere");
>     self.read(table, "query", None);
>     self.filters(filter);
> }
> ```
>
> `FilterOp` is `Eq | In | Lt | Lte | Gt | Gte`, so **range and set predicates already
> execute inside mutations today** — they are simply only available to a delete.
>
> The conclusion is unchanged and the precise statement is cleaner: *the one step that
> reads by predicate consumes its rows immediately as deletions and binds nothing.*
> The defect is not that mutations cannot evaluate predicates; it is that no step
> **binds** the rows a predicate selects. This also means a bound read would need no
> new filter vocabulary — an interval overlap test
> (`ltFilter('startsAt', arg('end'))`, `gtFilter('endsAt', arg('start'))`) is already
> expressible in the filter type.
>
> `AssetCollection` remains a separate platform-owned case, reading its child table
> through a fixed `uniqueParentAsset` index.

Read plans are not so restricted, in the same file and the same walker:

```rust
HandlerPlan::Query(plan)        => self.read(&plan.table,  "query", plan.indexed_by.as_deref())
HandlerPlan::RelationalQuery(p) => { self.read(&p.root, "query", Some(&p.root_index));
                                     self.read(&p.joined, "query", Some(&p.joined_index)); }
GraphNodeV1::ExistsSemiJoin { edge, .. } => match edge {
    GraphEdgeV1::Through(edge) => { self.read(&edge.table,        "query", Some(&edge.parent_index));
                                    self.read(&edge.target_table, "point", Some(&edge.target_index)); }
```

`HandlerPlan::Query` even carries `membership_filters` and registers a
`membershipPredicate` authorization input.

**So the asymmetry is exact: a declarative read plan can scan an index and perform a
bounded existential semi-join; a declarative mutation plan can only fetch rows by
`_id`.**

Any write whose correctness depends on a non-key lookup therefore cannot be a
declarative mutation:

- a uniqueness check (`WHERE handle = ?`) — `coterie`'s `requireAvailableIdentity`;
- a membership check (`WHERE conversationId = ? AND userId = ?`) — the paved
  authorization shape;
- any relational invariant asserted before writing.

Concretely, `coterie`'s `editProfile` needs `get('profiles', arg('profileId'), …)`
(expressible), a `guard` on ownership (expressible), and then a lookup of `profiles`
**by the `by_handle` index** to reject a duplicate handle — which has no step. The
mutation cannot be a plan, and every mutation in that application that touches an
identity or membership invariant is in the same position.

This explains F1 without appeal to habit: schema table count is a proxy for the number
of non-key invariants a write must check, so the escape rate should climb with schema
size, and it does — 48% → 83% → 89%.

### F4b — Plans also have no abstraction mechanism

`packages/snapback-codegen/define.mjs` exports step constructors (`insert`, `patch`,
`del`, `get`, `guard`, `letBind`, `deleteWhere`, `insertEach`, `allocateSequence`)
and expression combinators (`arg`, `lit`, `field`, `and`, `cond`, `coalesce`, …). It
exports **no mechanism for naming and reusing a predicate or precondition across
plans.** A plan is a literal step list. `standardPattern: { helper, profile }`
(LLP 0065) is a registry of *platform-authored* patterns, not an app-authored
abstraction.

Real applications factor heavily. Shared local helpers with ≥2 call sites, measured
across the corpus:

| Application | Shared-helper call sites |
|---|---|
| coterie | **164** |
| partiful-matrix | 6 |
| triage-graph | 4 |
| latency-kanban | 3 |
| fleet-observatory-move1 | 2 |

Coterie's most-reused helpers are **authorization predicates**:

| Helper | Call sites |
|---|---|
| `requireMyProfile` | 27 |
| `chatAccessForProfileConversation` | 13 |
| `boundedCurrentMemberships` | 8 |
| `requireActiveChatAccess` | 7 |
| `requireGroupAdminAccess` | 4 |

`requireMyProfile` is 200 characters — a lookup of `profiles` **by the `by_owner`
index** plus `ctx.refuse('PROFILE_REQUIRED')`. Note that F4 already disqualifies it:
it is an index read, so it could not be expressed in a plan even if it were inlined
27 times. F4b is therefore a *second, independent* barrier rather than the primary
one — it is what would still bite after F4 was lifted.
`chatAccessForProfileConversation` is 721 characters and resolves
profile → conversation → membership, distinguishing active from historical
membership and deriving a removal cutoff.

### F5 — The causal chain, end to end

1. A realistic application guards writes with non-key invariants: handle uniqueness,
   conversation membership, group-admin authority (`coterie`:
   `requireAvailableIdentity`, `chatAccessForProfileConversation` ×13,
   `requireGroupAdminAccess` ×4).
2. **A mutation plan cannot express any of them** — F4, verified against
   `MutationStep`.
3. `guide/auth/protecting-data.md` independently records that multi-hop
   authorization is "deliberately undeclarable" in the visibility grammar and
   prescribes a hand-written permission pattern "in **every** named function,"
   calling the repetition "intentional."
4. **Therefore the function must be a JS handler.**
5. A JS handler has no generated IR.
6. No IR means no derived optimistic prediction (LLP 0329.005 F2: a 19% ceiling) and
   never `rqsEligible`, so no cold retention
   (`guide/sync/offline-and-retention.md`).

Step 2 is the binding constraint; step 3 compounds it. Both are platform decisions,
neither is an author mistake, and together they mean **the applications with the most
invariants — the ones whose users would most benefit from offline and optimistic
behaviour — are structurally the least able to get either.**

### F6 — `allocateSequence` is a microcosm of the whole defect

All three model families independently recommended shipping a monotonic sequence
primitive first, to replace Campfire's unbounded `max`-over-scan. **It already
exists.** `guide/backend/declarative-plans.md`:

> `allocateSequence(counter, scope, into)` — Allocate one value from a declared
> scoped sequence into a binding. **Admitted only inside
> `defineWriteWithActivity`-generated plans**; hand-authored `defineMutation` plans
> use the JS-tier `ctx.sequence.allocate` instead.

`defineWriteWithActivity` is Experimental (LLP 0110/0113), point-operations-only, and
first admits `existing-owner.v1` authority only. So a hand-authored mutation that
needs a sequence must drop to a JS handler — `guide/backend/sequences.md` shows
exactly that: `handler: async (ctx, args) => ctx.sequence.allocate('jobNumber', args.orgId)`.

Measured consequence: `allocateSequence` appears in **zero** demo backends, and
`demos/campfire/snapback/functions.mjs` still runs an unbounded
`.withIndex('by_room_sequence').eq(...).order('sequence','asc').collect()` with no
`take`.

The capability exists, is gated behind a profile real applications cannot adopt, is
therefore unused, and the application it was for still performs the scan it was meant
to remove.

## Consequences

1. **The read-language debate was aimed at the wrong subsystem.** Six sketches
   proposed query-language reform. F5 says the binding constraint is authorization
   expressiveness plus plan abstraction.
2. **Adding vocabulary does not move authors** (F2). Two of the three proposed
   remedies in this family — richer composition, richer aggregates — are more
   vocabulary. F2 is direct evidence that this alone will not change behavior.
3. **"Intentional repetition" has a measurable price.** The guide's decision that
   multi-hop checks repeat per function is what forces the handler, which forfeits
   optimistic prediction and retention. The repetition is not local; it costs two
   platform capabilities.
4. **Gating a primitive behind an experimental profile is equivalent to not shipping
   it** (F6).

## What this suggests, without proposing a design

The cheapest interventions implied by the measurement, in order of evidence strength:

1. **Let a mutation plan read by index.** Read plans already do it, with bounded
   ceilings and an existential semi-join (`ExistsSemiJoin`, `GraphEdgeV1::Through`).
   The machinery exists on the read side; the write side does not admit it. This is
   the smallest change that could move a 74% escape rate.
2. **Give plans an abstraction mechanism** — a named, reusable, analyzable
   precondition. F4b: `coterie` factors 164 helper call sites and a plan can name
   none of them.
3. **Make multi-hop authorization declarable**, or accept that multi-hop applications
   are permanently JS-tier and therefore permanently without prediction and
   retention. This is the LLP 0329.004 §4.2 obligation, now with a measured price.
4. **Ungate `allocateSequence`** from `defineWriteWithActivity` so hand-authored
   plans can use it.

None of these is a query-language change.

## Confidence

High on F1, F2, F3, F4, and F6: all are counts or direct quotations, reproducible
from the cited files and `git log`. The helper counts come from a regex over
locally-defined functions with ≥2 call sites and may undercount indirection through
imports.

High on F4 and F5. F4 is read directly off the `MutationStep` enum and the
dependency walker in `crates/snapback-types/src/manifest/types.rs` — the LLP 0037
source of truth — not inferred from the guide. The translation attempt on
`coterie`'s `editProfile` located the missing construct precisely: a `by_handle`
index lookup, for which no step exists.

Medium-low on generalization. This is one corpus of demo applications written largely
by agents building benchmark instruments. `coterie` dominates the helper measurement
(164 of 179 call sites), so F4's magnitude rests substantially on one application —
though it is the largest and most realistic one in the corpus.

## Open questions

1. **Why is the write path restricted to point reads?** The read side already proves
   bounded index access and semi-joins. Is the restriction a deliberate
   isolation/conflict-validation property of the atomic single-transaction host-plan
   model (LLP 0032 Phase 2, docket DK-1 leg E3), or is it simply unbuilt? That answer
   decides whether recommendation 1 is cheap or forbidden, and it is the single most
   valuable follow-up in this family.
2. Would an app-authored plan-fragment abstraction preserve the bounded-work and
   declared-reach proofs the profiles exist to provide, or does inlining exist
   precisely so the analyzer sees the whole plan?
3. Does the same abstraction gap explain the 45% gratuitous read escapes in
   LLP 0329.005 F3, or is that a separate discoverability effect?
