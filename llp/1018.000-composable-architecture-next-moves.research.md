queries, atomic row changes, and account sessions. Reuse a capability's
semantics across authorization, certification, live invalidation, offline
coverage, prediction, pagination, and diagnostics. Remove machinery that
reconstructs information another layer already established.

## 3. Persistent, incremental query execution

### Contract

`writer.rs::rerun_live` currently unsubscribes and resubscribes affected queries.
`Runtime::rerun` already preserves IDs, replaces successful traces, and retains
an old trace on execution error; the owner bypasses it to refresh execution
context. Fix this seam first. Add context-aware batched rerunning to the
existing API. Keep runtime IDs stable, update `now` and `read_time` exactly once
per run as the owner currently does, and preserve connected facts, offline
receipts, drain handling, digest suppression, and terminal refusal behavior.

Normalize each authoritative trace to dependency sets. The existing exact,
range-prefix, constraint, rule-input, absence, connection, clock, and search
scope semantics remain authoritative. Implement attach, detach, and replacement
by set difference. A replacement touches only that subscription's changed
dependencies; prune empty buckets. Avoid scanning all subscriptions even when
several invalidated queries rerun in one owner batch.

Only successful execution replaces the retained trace. Denied/partial query
results are successful executions and replace it with their actual evidence.
An execution error keeps the old dependencies for core retry. When the owner
sends a terminal error and removes its client, it detaches the runtime entry
once. Missing operations and incompatible successors remain terminal. Removal
must clear every dependency, including logical search scopes and constraints.

### Witness and boundary

Compare against full execution and a simple trace-scanning invalidation oracle
through insert/delete/key movement, missing-point insertion, rule changes,
constraints, connection changes, clock-only changes at the same commit sequence,
search-scope changes, failed rerun/retry, and unsubscribe. Exercise the actual
owner frame path as well as the core API.

Measure dependency insertions/removals and rerun latency with subscription
count and affected-query count varied independently. This run retains whole
query execution as the reference and unit of rerunning. The initial draft's
speculative caching of individual read results is not a second commissioned
implementation: consider it only if measurements still identify material
repeated read work after the global index rebuilding is gone. No read-result
cache is added without its authority/context key and memory bounds.

## 4. One observed query, one coherent snapshot

### Scope

The coherence boundary is **one named Quarry query**, composed from bounded
read/value functions (§7). A `conversationView` returning messages, count, and
preview executes in one transaction/context/read time and has one certificate,
trace, receipt, completeness outcome, and delivery. Different UI
components select fields from that same snapshot. Separately named queries
advance independently; matching durable sequence numbers do not make them an
atomic group, especially for clock-dependent observations.

The record `{ messages, count, preview }` has **no certified continuation**:
`messages` is a bounded nested collection, and `next` remains null. Rust's
existing page law does not derive a result page through `Expr::Object`. Keep
pagination on the existing named `thread` query returning a supported top-level
page; it is a separate observation without joint atomicity. Do not introduce a
designated page field, multiple cursors, or drain support for the record. A slow,
denied, partial, or refused composite has one corresponding outcome. Unrelated
queries keep progressing. No cross-query barrier, waiting timeout, or sequence
bag is introduced.

### Client ownership

Move current `QueryView` reduction into the existing shared query entry, keyed
by authority/program identity, operation, canonical arguments, and live/drain
mode. Preserve value identity with `reduceQueryState`. One immutable current
snapshot owns value, receipt-backed completeness, freshness, predictions,
continuation, and refusal; no second result cache or authority inference.

Expose this resource through `client.observe(query, args, options)`, returning
stable `getSnapshot()` and `subscribe(notify)` operations. Merely obtaining an
observer does not open transport or retain an inactive entry. First subscription
opens the existing shared entry; last detach releases it. `client.subscribe`
continues to deliver query events through that same entry. React and Expo's
common `useQuery` read it through `useSyncExternalStore`, deleting their separate
per-hook query reducer/ownership paths. Preserve one-shot `live: false` behavior.

Server delivery and a committed local input revision each produce one snapshot
per affected named query. Notify mounted offline observations after the range
store atomically changes effective facts, coverage, authority, or the prediction
overlay. Reevaluation reads the committed state; evaluation itself does not
write the store or notify it recursively. Receipt bookkeeping that does not
change evaluation inputs must not start a feedback loop. Coalesce overlapping
notifications with bounded per-entry work and fence old authority/program
completions. Reset forgets the old snapshot before successor delivery; closing
one consumer cannot detach another or retain a superseded observation.

### Witness

Use a real composite conversation query with list/count/preview and two mounted
consumers. Observe live send, offline prediction, settlement, reconnect,
revocation, slow/refused execution, and same-sequence clock change. Each consumer
sees internally coherent fields, never gains completeness from unheld counts,
and cannot read data from a retired account. Verify React StrictMode remount,
headless observation, Expo's shared core, and last-consumer cleanup.

## 5. A shared row-change lifecycle for derived data

The supported derivations are scalar indexes, Unicode search postings/prefix
structures, and maintained count/sum rows. Keep a sealed internal operator set,
not a public extension system. They share row transition, bounded reservation,
transactional apply, clean rebuild, successor reconciliation, and dependency
reporting. Asset custody and scheduled effects retain their existing semantics;
this work does not turn every row side effect into a generic derivation.

Consolidate the duplicated lifecycle where source inspection finds actual
shared work. Represent a row transition as old/new source images. Remove the
old contribution and add the new one, with type-specific key/token/group logic.
The driver owns ordering and transaction participation; each derivation owns
its physical representation, conservative cost accounting, and disclosure.
SQLite still maintains ordinary physical indexes where it already does so.
Do not replace SQLite index maintenance with a parallel implementation merely
to fit the abstraction.

Updates occur before the next mutation statement. A maintained target-row
write participates in the ordinary target index/search/timer machinery;
same-mutation reads see it. Keep transitive/cyclic maintains refused. Failure
rolls back source rows, target rows, postings, timers, and metadata together.
Successor application identifies changed definitions, independently validates
surviving source data, clears/rebuilds affected structures, and publishes the
new generation only after success. Preserve the survivor-uniqueness repair and
count-backed cap certification/rebuild obligations from LLP 1017.

The law is **incremental final derived state equals a clean rebuild from final
source state**. Observable query/refusal behavior agrees; each route stays
within its own certified work bounds. Their operation counts and internal
traces need not be equal: rebuild necessarily visits different input rows.
Aggregate rows have a canonical sparse representation: count and sum targets
exist only when their value is nonzero. This includes nonempty source groups
whose sum is zero. An absent target continues to read as zero through the
scalar aggregate operation; a direct target-row read observes absence. Apply
each affected group's old/new contribution together, then insert, update, or
delete the target through the maintained-row lifecycle. Zero removal must obey
target deletion constraints, remove postings and timers, and roll back with
the source mutation. Rebuild uses the same representation. This requires no
additional source grouping index or durable cardinality structure, and the
twin still needs authority for the starting target value or its absence.
Exercise insert/edit/delete/group movement, rollback, repeated writes in one
transaction, and successor changes across all three derivations. Native and
twin share conformance cases. The twin derives only from authorized held data;
unheld counts stay unknown, and an index never grants row authority.

Extract the smallest driver that removes duplicated obligations. If a proposed
wrapper does not delete such code, retain the concrete implementations and the
shared law/tests; a class or trait is not the completion criterion.

## 8. Account sessions and durable follower admission

### Ownership

Extend the existing session/follower/outbox lifecycle. Keep one persistent
partition owner under the existing Web Lock. Each async operation captures its
own client's authority/custody/fence and loses publication rights when that
incarnation ends. These local counters are not comparable between tabs.
Preserve expiry-seals versus sign-out/replacement-wipes and obsolete-takeover
fencing. Extract coordination where it deletes duplicated ownership logic;
do not introduce a parallel session-state framework.

Use `BroadcastChannel` scoped to canonical backend identity, carrier namespace,
and principal. The writer announces a fresh random writer incarnation, the
current server auth epoch, and a durable partition incarnation. Initialize that
partition incarnation while holding the lock; takeover preserves it, whereas a
wipe creates a new one even if a later login has the same principal/auth epoch.
Recovery against an old partition incarnation cannot admit a new command.
Commands include protocol version, random request ID,
principal/auth epoch, durable partition incarnation, target writer incarnation,
operation, arguments, and a
bounded expiration. Never send bearer tokens. Both ends capture/check their
own local session; the writer checks current principal/epoch and incarnation
before admission. Re-discovery after takeover changes the target incarnation,
not the request identity. A tab without matching established account authority
cannot borrow another tab's writer. No transport means the existing explicit
follower refusal, with no plain mutation or second retained partition.

### Admission, retry, and bounded receipts

The writer alone allocates grant/intent IDs and serializes local and forwarded
commands through `OutboxLedger`. Admission atomically commits grant use,
intent, prediction, and a durable request-to-intent receipt. Acknowledgment is
sent only after that commit. Preserve each follower's submission order; across
tabs the order is durable writer admission, not wall-clock send order.

A retry uses the same request ID and payload digest. A matching durable receipt
returns the original admission acknowledgment; a conflicting payload refuses.
The receipt must survive ordinary settled-entry dismissal: an acknowledgment
can be lost after the server committed and the outbox row was removed. It
records admission identity and a compact allocated-ID slice descriptor sufficient
to reproduce both `intent` and `ids`, not query data or the full result.
Acknowledgment reports durable admission, which is distinct from current
pending/settled status. Use the existing queued-mutation return contract with
that distinction documented; live query delivery still reports server state.

Bound forwarding to 64 unexpired unacknowledged commands per follower and 256 unexpired fixed
metadata receipts per partition. Command lifetime is at most five minutes.
Reject admission before consuming a grant if receipt capacity is full; never
evict a live deduplication receipt to admit another command. Prune only after
its command can no longer be admitted. An expired request may return an
existing receipt but cannot create a new intent; absent expired receipt means
unknown outcome, never automatic resubmission under a fresh ID. Validate future
expiration against the writer's clock so malformed peers cannot retain records
forever. Expiration is encoded in the request identity and cannot be extended
by a retry. Persist a monotonic admission/pruning clock floor, so wall-clock
rollback cannot make a pruned command admissible again. Account wipe removes
receipts with the partition; epoch and partition-incarnation checks prevent
old commands from creating writes in a successor account session.

At two seconds after sending without acknowledgment, expose
`writer-unresponsive` through readiness and return a new mutation-result
variant `{ state: "admission-unknown", recovery }`. `recovery` is a serializable
opaque token binding protocol version, request ID, payload digest, expiration,
backend/carrier scope, principal/auth epoch, and durable partition incarnation.
It grants no authority. It contains no bearer, query data, or argument copy.
Update LLP 1002, public types, hooks, and the guide to expose this fourth outcome.
It is neither `queued` nor `rejected`; callers must not retry it as a fresh write.

`client.recoverMutation(ref, args, recovery)` verifies the operation/payload and
exact scope, discovers the current writer, and looks up or retries the same
identity. Return ordinary `queued` only when the durable receipt supplies intent
and IDs. A still-unreachable writer returns the same unknown outcome; after
expiration recovery can only look up a surviving receipt, never admit. A missing
expired receipt remains an unknown outcome. A mismatching account/epoch/partition
refuses recovery without a write. Discovery timeout before sending any command
is known non-admission and keeps the ordinary follower refusal.

A timeout does not free an in-flight slot: retain request identity until its
acknowledgment or expiration. With forwarding available, mutation readiness
reports writer discovery, `ready`, writer capacity, or `writer-unresponsive`;
`follower` is the hard refusal only when forwarding is unavailable. Readiness is
a hint, rechecked atomically on admission. Do not steal a Web Lock on a heartbeat.
Takeover first reloads durable custody and deduplication records, then resumes
and replays. Late acknowledgments can update only their still-current local
session and release their own slot; they cannot settle a successor's call or
clear another request's unresponsive state.

Forward mutation arguments that the writer can durably admit. Asset
uploads and ephemeral channel publication keep their existing explicit
follower refusal; forwarding bytes or channel events is a separate protocol,
and must still refuse before any bytes leave. This implements the ticket's
two-offline-mutation witness without pretending those operations are outbox
commands.

### Witness

Two real browser tabs each enqueue an offline write, reconnect, and settle
through one queue without duplicate server ledger effects. Cover writer closure
before/after admission, lost acknowledgment before/after settlement dismissal,
retry, request payload conflict, expiry, bounded receipt saturation, FIFO,
frozen writer, account replacement/expiry, wipe and relogin at the same epoch,
clock rollback after receipt pruning, public unknown-outcome recovery,
obsolete acknowledgment, takeover,
and unavailable BroadcastChannel. Record runtime/client size deltas; the
transport exclusion from the five-root measure does not hide durable receipt
machinery that belongs in the measured store/outbox.
