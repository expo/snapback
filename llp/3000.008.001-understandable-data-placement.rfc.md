## Summary

An author should be able to explain which facts belong on a device, which stay
on the server, and what an operation can do when either is unavailable. The
same explanation should lead to affordable data placement at realistic scale.

[LLP 3000.006](./3000.006-explicit-data-residency-and-server-execution.rfc.md)
owns the detailed residency proposal. LLP 3000.007 offers a smaller vocabulary
for related classification. This child connects those proposals to the product
outcome and isolates choices they have not yet reconciled.

## 1. Current evidence

`sync` is already opt-in. A table without it remains online-only; older rows
beyond an acquisition horizon remain on the server. The local client examines
an operation's dependencies and may route the whole read to the server. The
[published sync and client reference](../snapback4/packages/snapback4/README.md)
describes these mechanisms, but their consequences are spread across the
schema, runtime behavior and prose.

The [Clique startup audit](../benchmarks/runs/2026-09-13-snapback4-clique-0004/replica-startup-audit.md)
records a snapshot with 24,616 unnecessary repost-count entries. Correcting the
application's counter shape materially reduced transferred events and bytes;
browser startup improved in the corresponding observations. This is an
application modeling result, not evidence that the retired JavaScript replica
implementation is still present.

The [builder essay](../benchmarks/runs/2026-09-13-snapback4-clique-0004/astra/essay.md)
also records an apparently harmless existence guard that stopped a send from
predicting beyond the device's horizon. Table residency alone did not explain
whether that specific mutation could predict with the data held.

## 2. Three facts to distinguish

| Fact | Known from the program | Known only at runtime |
| --- | --- | --- |
| Residency policy | Audience, acquisition horizon, online-only source, inherited maintain policy. | What this device has acquired, retained, evicted or lost. |
| Execution capability | Required read/write sites, server-only dependencies, required native module, structural prediction restrictions. | Connectivity, module availability, generation, credential state and actual local evidence. |
| Result coverage | Possible completeness class and the reasons it can weaken. | Coverage of this call's arguments and horizon, metered cut, freshness and pending predictions. |

`check` should explain static capabilities and reasons. It cannot promise that
a query will be complete on a device that has not acquired its data, or that
every argument to a potentially predictable mutation will predict.

Generated metadata must preserve that distinction. If `runs` or `predicts`
are used, their documentation and types must express capability, not a promise
that hides runtime preconditions. Native reads also depend on a compatible
module and its declared capabilities. Conservatively classify opaque
dependencies until the compiler has sufficient evidence to do better.

## 3. Proposed authoring experience

Provide one residency report through `check` and focused explanations through
`why`, with the same facts represented in generated operation metadata. Show
the responsible read or write site when an operation requires the server or
loses prediction eligibility. Changes to eligibility should be visible during
ordinary development, including the first run where no previous generated
artifact exists.

Add the explicit `online only` spelling proposed in LLP 3000.006. The
recommended introduction is optional syntax plus a report that lists every
table, including those relying on omission. This follows LLP 3000.007's lower
ceremony option; LLP 3000.006's mandatory declaration remains an alternative
for the author to resolve. Neither proposal has been accepted by this child.

Pave the online-only template through the same generated API, identity,
authorization and live-query model. An application should be able to keep
analytics or private source events on the server without creating another API
or authoring a different language. Online-only residency is not itself an
authorization rule or a permission to expose sensitive results.

## 4. Read and write outcomes

| Situation | Required behavior |
| --- | --- |
| Local data supports this call | Return the local result with its actual coverage and freshness. |
| A useful local page is held, but the requested extent is not complete | Preserve truthful partial data; when using the server, evaluate the operation there as a whole rather than silently joining two inconsistent results. |
| The value depends entirely on server-only facts and the link is unavailable | Return a typed non-value, not a plausible empty page, null or zero manufactured from missing source rows. |
| A mutation can be durably queued but lacks evidence for prediction | Admit the write with its stable ID and explain the prediction limitation; show no invented optimistic row. |
| An operation requires an online capability to be admitted | Return the explicit online requirement; do not pretend a transient in-memory request is a durable write. |

The current card's `denied` with `E_OFFLINE`, family `link`, may represent
the typed non-value. LLP 3000.006 also considers an unavailable variant. Settle
one representation with the client child and generated types; this document
requires truthful behavior without silently adding both variants.

Do not erase valid pending predictions by replacing a local observation with
a stale server result. Existing replay and authoritative-base ownership remain
in force. Missing evidence is not an authoritative validation failure.

## 5. Compact device facts from server sources

Make the source/projection pattern an ordinary compiled recipe:

- detailed receipt events on the server, compact per-conversation state on the
  device, with exactly the receipt semantics the product requires;
- private vote or activity facts on the server, a disclosed count or ranked
  card on the device under its own explicit rule;
- large audit or analytics sources online, an intentionally bounded user-facing
  summary synced where useful.

For each recipe state the source authority, derived disclosure, update owner,
atomicity or staleness policy, revocation behavior and write amplification.
Distinguish an engine-maintained aggregate from a job-maintained projection.
A job's lag does not become exact merely because the projection is synced.

Measure rows and bytes per representative principal using the real fixture.
Warnings about unbounded public tables or wide merges should point to the
relevant recipe. A horizon bounds acquisition, not total long-lived holdings:
LLP 3000's current policy does not evict a device back to exactly N rows.
Do not advertise it as a permanent storage quota.

## 6. Proposed sequence and acceptance

First reconcile the classification vocabulary in LLPs 3000.006 and 3000.007,
then emit metadata and explain it through the existing tools. Route reads and
admission through those facts with runtime coverage checks. Add the compiled
projection recipes and repeat the retained application measurement.

Acceptance is concrete:

1. From `check` and the generated API, a builder can identify every online-only
   table and explain the server dependency or prediction limit of each operation.
2. A fully server-dependent read fails truthfully offline; a horizon-limited
   read still exposes useful partial data. Reconnection restores the ordinary
   observation without a custom transport or a second query model.
3. A redundant beyond-horizon guard is discoverable as a prediction limitation.
   A queued unpredicted write survives reopening and retains its identity.
4. Online-only source rows are absent from snapshot, stream and device stores;
   their authorized derived facts may be present under the declared policy.
5. The compact Clique receipt/counter design preserves the full product's
   membership, ordering, receipt and offline-history requirements while reducing
   measured device work. Removing required history is not an optimization win.
6. Changes of rule, residency, generation and module availability produce the
   stated outcomes on both browser and native hosts. Static metadata and runtime
   behavior agree without treating static capability as current completeness.

## 7. Open decisions and limits

Resolve optional versus required residency spelling, the minimum useful
operation classification, explicit server execution hints, and the single
offline non-value representation. Recommend ordinary compiler inference and
clear reasons first; add overrides only for a demonstrated application need.

This work does not add automatic projection synthesis, union audiences,
arbitrary server code or exact horizon maintenance. Those remain separate
scope and design decisions under [LLP 3000](./3000-snapback4.explainer.md).
