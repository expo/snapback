## Summary

An author should understand what stays on the server, what a device may hold,
and what a call can truthfully do now. [LLP 3000.007 §6](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md#6-residency-and-execution-made-legible)
owns the accepted residency design. LLP 3000.006 remains Superseded.

The compiler reports and optional spelling already shipped. The selected
residual is to verify that actual acquisition, rather than possessing a
schema, establishes local knowledge.

## 1. Current evidence

The [current reference](../snapback4/packages/snapback4/README.md) and
[residency tests](../snapback4/packages/snapback4/test/residency.test.mjs)
cover optional `online only`, inferred audiences, `check --residency`, site
reasons, generated `runs`/`predicts`, online-query liveness and `E_OFFLINE`.
No alternative mandatory declaration or new unavailable variant is pending.

The historical [startup audit](../benchmarks/runs/2026-09-13-snapback4-clique-0004/replica-startup-audit.md)
shows the practical cost of unnecessary counter rows. It supports deliberate
source/projection modeling, not a claim about the current device implementation.

The panel identified a source-derived interruption case: schema installation
can succeed before first sync fails. A nonempty server's never-acquired table
must not then look like known empty data, including after offline reopen.
Reproduce this through actual clients before changing the device.

## 2. Three facts to distinguish

| Fact | Static | Runtime |
| --- | --- | --- |
| Residency | Audience, horizon, server-only source, inherited maintain policy | Acquired, retained, evicted or missing rows |
| Capability | Dependencies, module requirements, structural prediction limits | Current generation, credentials, connectivity, installed module and local evidence |
| Coverage | Possible completeness class | This call's actual coverage, meter cut, freshness and predictions |

`runs` and `predicts` are capabilities, never proof that this device has
acquired the needed facts. A schema/generation record and a watermark of zero
must distinguish a successfully acquired empty server from no acquisition.

## 3. Proposed authoring experience

Keep the delivered compiler report, generated metadata and focused `why`
explanations. Keep `online only` optional and the server-only template on the
same generated API and authorization model. Correct current-surface guidance
where a reproduced readiness boundary needs explanation; add no vocabulary.

## 4. Read and write outcomes

A held local answer carries actual coverage and freshness. A server-dependent
call without an answer uses the accepted `E_OFFLINE` refusal. A never-acquired
local store must not fabricate complete empty pages, negative existence or
zero totals. Useful acquired stale data survives a later network failure.

Durable admission without enough evidence for prediction queues the stable
write ID without invented optimistic rows. Missing membership facts before
acquisition are not an authoritative refusal. A generation reset invalidates
old acquisition knowledge until the new snapshot and catch-up are durably
published; interrupted staging cannot manufacture that publication.

Do not combine a server answer and retained local rows mechanically. The
[mixed left/held limitation](../issues/closed/20260914-snapback4-mixed-left-held-query-loses-retained-rows-online.md)
keeps its separate-query recipe; deeper provenance is deferred.

## 5. Compact device facts from server sources

Keep the accepted receipt/digest and ranked-feed recipes: source authority,
derived disclosure, update owner, atomicity or refresh lag, revocation and
write amplification must be explicit. A job projection is not exact merely
because it syncs. A horizon bounds acquisition, not lifetime storage.

Measure an actual excess before inventing additional projections. This
increment adds no automatic synthesis, union audience or exact horizon
maintenance. The presence/effects exception remains the separately owned
LLP 3000.007 §19.1 correction.

## 6. Proposed sequence and acceptance

1. Reproduce schema-success/sync-failure against a nonempty uncapped synced
   table on wasm and process devices, including offline reopen.
2. If reproduced, establish durable, generation-scoped readiness through the
   existing snapshot/catch-up transaction. Keep an acquired empty sequence-zero
   store distinguishable from never-acquired state.
3. Interrupt a multipage snapshot and catch-up; neither publishes false local
   authority. Previously durable outbox entries survive. Missing facts queue
   valid writes unpredicted and preserve submission identity.
4. After successful acquisition, a later failed refresh preserves useful stale
   state; after reset, the old generation cannot certify new completeness.
5. Existing residency/disclosure behavior and generated metadata still agree.
   Any source-only finding not reproduced gets precise counterevidence.

## 7. Open decisions and limits

No new classification words, execution override or offline variant is needed
for this increment. Module compatibility, result coverage and acquisition
remain separate facts. Broader mixed-query provenance and projection synthesis
wait for their own concrete requirement.

## 8. Implementation evidence

The wasm and process clients reproduced false complete empty lists, zero
counts and negative point reads after backend installation but failed first
sync, including offline reopen. Four defect cases failed before the repair;
two truly acquired empty-partition controls already passed.

The device now commits a generation-scoped acquisition marker with final
snapshot/catch-up publication. Reset invalidates it. An already acquired
partition survives literal-default-only widening when the existing image
compatibility rule holds and no table was added. A store created before this
marker needs one completed online sync; a watermark alone cannot distinguish
a prior complete acquisition from an interrupted reset. Queued identities are
preserved. The focused verification passed 76 device tests and 19 actual-client
acquisition/residency/retention tests; integrated verification is recorded by
the umbrella's execution record.
