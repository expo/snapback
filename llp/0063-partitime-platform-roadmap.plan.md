## Summary

The Partitime experiment built one Partiful-shaped product as React, Contract,
and vanilla browser JavaScript over Snapback, Supabase, Convex, and plain
SQLite — a 3×4 matrix whose twelve cells all production-built and passed the
browser suite; the Step 0 refresh is now retained at 43/43: 36 shared claims,
four vanilla subscription-disposal claims, and three fallback-disabled
Snapback push witnesses. A second same-day extension added an
Apple-native comparison — SwiftUI versus Exact+Contract on macOS and iOS,
two authoring systems by two platforms by the same four providers, all over
the shared polling gateway with no push claim. Shindig separately exercised
Partiful-shaped resource membership, invite/RSVP behavior, and both React and
Contract surfaces over Snapback.

Together, those builds establish a second-generation product program. Snapback
already has the strongest generated end-to-end contract in the matrix, and
Contract plus Snapback has the cleanest live data plane. They are not yet the
unqualified default for a polished consumer application: React remains easier
to style and navigate, Contract query scopes can reshape the product, Contract
packages were large in the measured build, Snapback asks for more handwritten
declarations, and the
external developer/deployment loop is heavier than the simplest alternatives.

This Plan defines the work required to change that result. Its north star is:

> Snapback plus Contract should own data correctness, live lifecycle, typed
> integration, and agent operability so completely that application authors
> spend their differentiated effort on product behavior and visual design.

The target is a dominant default path with excellent escape hatches, not a
literal win on every isolated metric. Plain SQLite will remain the shortest
path to a first local row; React will retain the broadest component ecosystem;
PostgreSQL will retain familiar relational vocabulary; hosted competitors can
hide infrastructure behind an account. Snapback and Exact should win the whole
application lifecycle rather than distort the product to win a line-count
contest.

## Evidence and limits

Diary 0016 and the Partitime report confirm:

1. Snapback generated typed refs, argument schemas, manifests, capability
   facts, Contract bindings, runtime links, and artifact identity from one
   backend. It supplied the matrix's only push-capable transport — but the
   evidence proves "stream configured," not "push carried the observed
   update" until Step 0: the client defaults to polling fallback on stream
   loss, and the old browser contract never asserted transport. The old RSVP
   oracle was also satisfiable by seeded guest content. The retained Step 0
   receipt closes both holes: all twelve cells observe Eve's actor-specific
   before/after transition, and each Snapback arm relaunches with polling
   fallback disabled, applies an out-of-band mutation, proves `guestList`
   push establishment, and retains two warmups plus seven latency samples.
2. Contract plus Snapback removed React's handwritten subscription lifecycle.
   Exact owned query cells, connection delivery, action correlation, and
   disposal.
3. React plus Snapback was the strongest cell *when bespoke web UI was the
   priority* — which this build's polished-clone goal made true — while the
   report names Contract × Snapback the most successful cell for coherent
   data authoring; there was no single universal winner. Snapback supplied
   correctness and stream-configured realtime; React supplied local
   navigation, authoring economy, and escape hatches (animation traveled
   with the shared stylesheet, which the vanilla row reused unchanged). The vanilla
   extension sharpened the CSS claim: the polished stylesheet ran unchanged

## Product choice at the start of the program

For a polished Partiful clone built from the matrix as it existed on
2026-07-19, the default ranking is:

1. React × Snapback;
2. Contract × Snapback;
3. React × Convex;
4. React × Supabase;
5. Contract × Convex;
6. React × SQLite;
7. Contract × Supabase;
8. Contract × SQLite.

The ordering weighs production completeness, live capability (stream
configuration as it stands — not a proven push witness until item 1's Step 0
instrument runs), generated correctness, visual product freedom, deployment
path, and app-owned infrastructure, in roughly that order of weight. It is the author's synthesis of the report's
conditional conclusions, not a measured composite: the report itself concludes
only that React × Snapback was strongest for this bespoke consumer build and
that Contract × Snapback was the cleanest data-authoring path. It is not a
universal benchmark, positions three through eight carry wide uncertainty, and
the native Supabase and Convex follow-up cells may change the middle ranks.

The ranking covers the React and Contract web product rows only. The
Apple-native extension cells are excluded as comparative instruments (all
polling, hand-written provider seam, no push claim). The four vanilla
cells are deliberately excluded: the extension's own conclusion is that
imperative vanilla authoring was not the economical path for this polished
product (522 handwritten lines with a hand-owned subscription scope), so the
vanilla row serves as this program's measurement instrument and Workstream
8's zero-framework attribution control, not as a competing default.

The program's success criterion is not merely moving Contract × Snapback to
number one on this list. It must become the choice an author would make without
accepting a meaningful loss in visual quality, interaction design, runtime
weight, diagnostics, or deployment ergonomics.

For this program, "clearly better" is operational, not impressionistic:
Contract × Snapback passes every per-workstream acceptance gate in this Plan,
meets the Workstream 8 budgets once open question 4 fixes their thresholds,
and matches or beats React × Snapback on the same executable product claims,
agent-authoring effort, and diagnostic quality for the same application — with
no gate waived. A "meaningful loss" is failing one of those gates.

That definition binds only once its instruments exist. At Sequence step 0 the
program preregisters its comparison protocol as a committed artifact whose
repository path is recorded in this Plan by amendment at step 0 exit: the
workload (the Partitime fixture and shared claims), environment pinning
(package versions and hardware class, extending the report's version-pinning
discipline), the cost-attribution method, sampling, repetition counts and
aggregation rules for stochastic measurements, tolerances, and — for every
promised dimension, including visual quality, interaction design, runtime
weight, diagnostics, and deployment ergonomics — a preregistered pass/fail or
non-inferiority rule. "Agent-authoring effort" is measured under a pinned
agent configuration as turns, interventions, and tool calls per cell build,
with the mixed-result adjudication rule fixed in the protocol; "diagnostic
quality" is scored by a preregistered rubric over the Workstream 5 diagnostic
acceptance set. Step 0 freezes the method: metric definitions, adjudication,
non-inferiority rules, and the fixed formulas that compute each numeric
threshold as a margin relative to the React × Snapback same-workload
baseline. The first complete cost-attribution run is itself part of Step 0's
exit — it executes before steps 1–3 can change lifecycle, client, provider,
or emitted-code costs — and the numeric thresholds it freezes are *computed*
by the preregistered formulas from that baseline, not chosen after seeing
it. The step 0 run covers a protocol-declared initial category set — the
categories measurable with instrumentation that exists — and the remaining
Workstream 8 categories join by prospective dated amendment as their
instruments land, no later than step 4's budget enforcement; step 0 does
not block lifecycle work on building a complete metrology suite. Step 0
also freezes, per named graduation outcome, the **mandatory claim IDs**
that outcome requires — including Exact 0373's phase-5 agent-operability
claims (action → mutation → receipt → affected query → render, structural
repair, stable interfaces), which the north star's "agent operability"
otherwise leaves ungated — so no later trajectory or gap label can quietly
discharge required work. Instrument corrections distinguish two cases. A
drifted-but-valid instrument re-derives through the same formulas and may
only tighten. A *provably invalid* baseline (an instrument bug that
misstated cost) is corrected by a ratified invalidation procedure: the
ratifying owner approves it on documented evidence, the original artifacts
are preserved, the method and threshold IDs version-bump, the impact is
documented, both comparison arms and controls re-run prospectively, and
the corrected threshold may move in either direction — a known-false gate
is never preserved for the sake of the ratchet. A third case covers an
instrument that becomes *unavailable* while still valid (a deprecated
pinned agent configuration, a lost hardware class): the replacement follows
the same discipline — documented cause, version-bumped method and threshold
IDs, prospective re-run of both comparison arms and controls. One rule,
stated once and binding everywhere:
frozen thresholds from **valid** baselines are never loosened or replaced —
the ratified invalidation and unavailability procedures above are the sole
exceptions, each retiring the old ID and minting a versioned replacement;
later changes may only tighten them or add new metrics, and any added
metric requires a dated amendment plus prospective validation on a holdout
rerun. Thresholds bind
per immutable workload version: when the governed workload grows (new
UI-parity claims, new cells), the baseline rolls over by declared,
prospective amendment — never retroactively. Baselines are captured before
optimization work changes either stack, and each Sequence step exit re-runs
the Partitime harness against the same fixture and commits a CI-diffable
delta of source volume, glue inventory, bundle, and check counts.

Two governance rules complete the definition. The ranking above is
re-synthesized only at named events — follow-up-matrix completion and
Sequence step exits — so interim rank drift cannot leak into product
decisions before risk R2's gate closes. And partial success is a named
outcome, not a reframing hazard: if step 4's Workstream 3/8 gates do not
close, React × Snapback remains the endorsed polished-web default and
Contract × Snapback remains the endorsed data-authoring choice — that
end-state is recorded as such, neither spun as full success nor reframed as
program failure.

Until the Expo/native gate in Workstream 2 and the production-web gate in
Workstream 3 pass, every "default" claim in this Plan is scoped to local
single-page web authoring — the environment the matrix actually proved.

## Workstream 1 — dynamic keyed live-query scopes

Contract components must bind query arguments from reactive state or props
without rebooting the surface. Exact and the provider must own subscription
replacement, cancellation, stale-result suppression, connection continuity,
disposal, and diagnostic attribution.

This must not be app-authored resubscription glue hidden in a helper.

Acceptance:

- Partitime event selection remains component state;
- repeated selection leaves at most one subscription per active keyed binding;
- simultaneous component instances of the same query with different arguments
  subscribe independently (removing LLP 0034 §10.4's one-scope-per-query-name
  constraint, per Exact 0265 §5.1), and instances deduplicate only within a
  logical key of provider-issued **opaque authority-partition identity**
  plus stable descriptor identity/version plus canonical arguments — not an
  enumerated user tuple, because LLP 0012 distinguishes `userId` from
  `authorityInstanceId` and LLP 0053 lets authorization depend on session
  and provider state. The partition identity rolls on every authority
  transition (same-user re-login, anonymous/authenticated transition,
  provider or session reconfiguration, tenant/root change), identical
  arguments never deduplicate across partitions (cross-context sharing is a
  data-isolation failure, with Exact 0373's adversarial cases imported as
  tests, including late results arriving from a predecessor authority),
  ref-counted dedup within the key produces no shared-disposal errors, and
  physical transport sharing is a declared capability, never an implicit
  merge;
- same-key same-partition siblings share one logical attempt — its data,
  error, and reconnect state reach all of them identically (Exact 0373's
  contract, which adopts this rule) — while each retains an independent
  binding lifecycle, refcount, and disposal; full delivery/error/reconnect
  isolation is guaranteed only across different keys or authority
  partitions, and instance unmount and HMR reset dispose independently;
- no stale event snapshot can replace the current selection;
- URL synchronization is optional product behavior, not a provider constraint;
- reconnect, permission loss, argument change, and unmount have deterministic
  tests, and reconnect/permission behavior conforms to LLP 0053's Accepted
  contract — unconditional resnapshot of auth-scoped subscriptions,
  obligation-backed negative delivery, and authorization leases — not the
  older stale-epoch story;
- landing this amends LLP 0034 §10.4 (the boot-bound multi-live surface
  constraint) in the same change, and the Exact-side subscription-replacement
  amendment is a step-1 **entry** prerequisite — it exists before
  implementation starts, per the authority map and phase-gate matrix below.

## Workstream 5 — structural mutation outcomes and excellent diagnostics

Contract mutations need typed pending, success, retryable failure, terminal
failure, and ambiguous-settlement states. A transport rejection must not become
a Vite overlay that looks like a compiler error. Optimistic and confirmed state
must remain distinguishable.

Ownership of this splits across the repository boundary, and both halves are
prerequisites. The states named above are required *outcomes*, not a single
new state machine: Exact 0373 specifies the model as a projection over three
independent fact families — effect attempt, optimistic presentation, and
evidence-join status — owned by Exact 0330/0342/0329, with Exact 0263's
deferred completion branching and Exact 0284's confirmed/rejected receipts
as the current raw surface; this workstream reconciles to that three-fact
model, and the Exact-side amendments must land before implementation begins.
Snapback owns only the raw provider receipt and settlement facts that make
the projection truthful: LLP 0034 §3.2 already assigns outcome, rollback
reason, version, degradation, and transport to the provider, and LLP 0043
defines receipt-less failures as ambiguous with retained queued work — so
provider outcome classification, idempotent settlement signals, replay
safety, and receipt population land as LLP 0034/0043 amendments. The
fault-injection gate below runs against Snapback plus at least one
non-Snapback provider, phrased in the projection's vocabulary, and verifies
that every UI state is justified by provider evidence.

The complete authoring loop also requires:

- exact parser and claim-error source locations;
- stable diagnostic codes and structured payloads;
- one root report rather than per-tick repetition;
- compile/boot refusal for statically knowable incompatibility;
- no swallowed helper or action errors;
- LSP completion, navigation, rename, formatting, and incremental checks.

Acceptance:

- the known grammar, non-live binding, wrong-handler-kind, helper-type, and
  action-rejection failures report the correct locus and stable code;
- mutation failure UI is expressible entirely in Contract source;
- the three-fact projection has transition and reducer coverage under fault
  injection — timeout, retry, duplicate delivery, idempotency, late
  confirmation, and ambiguous settlement each have a deterministic witness —
  run against Snapback and at least one non-Snapback provider;

### Cross-repository authority

(authorization invalidation), LLP 0009/0047 (execution envelope), LLP 0014

The Exact-side counterpart is Exact 0373 ("Contract and Exact After

required Exact amendment stalls under that sequencing, the affected step's

named review trigger rather than silently freezing the program.

Detailed subsystem RFCs and Exact-side LLPs own semantics. This Plan is not
complete until the cross-stack acceptance gates are executable.

## Risks

- **R1 — Broad roadmap without subsystem ownership.** This document can become
  a wishlist. Mitigation: every implementation phase requires a governing
  subsystem LLP and executable acceptance gate.
- **R2 — Optimizing against non-idiomatic competitors.** The current matrix
  understates native Supabase and Convex clients. Mitigation: the
  native-realtime follow-up matrix is a scheduled instrument experiment owned
  by Sequence step 3, and Workstream 8's acceptance gates any final
  comparative ranking on its completion.
- **R3 — Contract favoritism weakens other surfaces.** Deliberately awkward
  React or vanilla paths would produce false evidence. Mitigation: first-class
  generated projections and identical product acceptance claims.
- **R4 — Ergonomic inference hides authority.** Reducing declarations can make
  security facts implicit. Mitigation: generated, reviewable facts remain the
  authority; inference is deterministic and explicit overrides narrow it.
- **R5 — Demo breadth outruns platform depth.** Many shallow apps can conceal
  missing production semantics. Mitigation: each app is admitted for named
  pressure and cannot claim capabilities without executable witnesses.
- **R6 — Cross-repository stall.** Steps 1, 3, and 4 gate on Exact
  amendments whose priority is set by Exact's own sequencing authorities
  (Exact 0373 and its parents), so a stalled amendment blocks a step
  indefinitely. Mitigation: blocked entry gates fail safe and are surfaced
  as this named risk with a review trigger — by default, any blocked entry
  gate older than four weeks forces the named review, and the same
  four-week review applies to step 0's own exit regardless of which
  repository the stall is in (Exact 0373 carries the symmetric trigger) —
  and the program re-scopes, re-orders around the blocked step, or
  escalates to the ratifying owners; it never starts implementation ahead
  of the amendment to relieve the pressure.
