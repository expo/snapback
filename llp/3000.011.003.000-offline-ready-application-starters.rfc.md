## 1. Recommendation

Reuse the existing Vite chat reference as one supported production web output,
exposed through the existing init flow. Default init remains schema-only.
Demonstrate cached-route-first navigation, an offline-loadable shell and visible
pending writes that have no predicted row. Use existing client APIs. Add a complete application journey to
the existing starter/witness tests, rather than introduce another state API.

The current Expo starter already shows pending and stale reads. Do not claim
to add those APIs or expand into a multi-bundler framework. Native execution
is a separate actual-application witness in the evidence proposal.

This is an application composition change. Replica recovery and acquisition
semantics remain in their existing implementation and owning LLP.

## 2. Route and write behavior

For a route to a known conversation, read the held membership/conversation
first. Open a locally readable room without first issuing a canonical-DM
creation mutation. When the local answer is incomplete or unavailable, show
the existing read state and allow the online lookup if connected. A horizon
miss is not proof that the room does not exist. Creating a new DM remains an
explicit operation with its current online/eligibility requirements.

Keep `complete` and `fresh` visible through the example's rendering logic.
Do not equate stale with unusable, loading with empty, or mutation settlement
with a freshly observed replica. A navigation that specifically needs the
new authoritative projection can await that observation, but ordinary held
navigation must not become globally dependent on `sync()`.

Bind saved route and intent metadata to both backend identity and principal.
Persist the minimal ID metadata before dispatch when crash recovery requires
it, then observe the SDK receipt; never add a competing outbox or replay loop.
An unknown/evicted receipt remains unknown. Account B cannot see or submit A’s
intent, including through delayed callbacks. Offline sign-out must remain
possible and does not claim A’s pending writes settled or delete its replica.
Test account switch with pending nonpredicting writes and delayed work.
Completed sign-out means local credentials have been durably removed. A stalled
logout request or refresh response cannot gate local invalidation; a late
refresh or store write cannot restore the credential after completion. A
storage failure remains incomplete and retryable. Ordinary client close keeps
its existing session-preservation behavior; remote revocation is best effort.
A rotation already committed by the server must be allowed to return its
successor for best-effort logout, without adopting or persisting that result.

Use the existing pending-write hook and stable intent id when a mutation has
no predicted row. Reopen observes that same write; it does not mint a new id.
Predicted rows keep their existing `pending` indication. A failed write stays
visible and actionable instead of disappearing with a cleared composer.

## 3. Shell and platform behavior

For the supported production web starter, provide a build-known allowlist app-shell cache
for the build's immutable assets and navigation entry. Cache only immutable build assets and a generic nonpersonalized entry; do not
cache arbitrary same-origin responses or navigation HTML. Keep authenticated API
responses, tokens, uploaded media and user data out of that cache; the SDK
retains the data/media it owns. Scope the worker to the application and use a
versioned shell lifecycle so one deployment does not delete a still-running
tab's assets mid-session. Development hot reload should not use a stale
production cache.

If the starter's bundler already provides shell caching, configure that path
rather than install a competing worker. Make the supported output shape
explicit; do not promise arbitrary bundlers automatically acquire offline
reload. Test an actual new page realm with network unavailable.

Expo uses the installed bundle and published native device module. Expo Go's
online fallback remains explicit. No Hermes export is relabeled a durable
native execution result; the evidence proposal owns that execution.

## 4. Residency is a measured application choice

Connect the starter's instructions to the existing
`test --residency --fixture ... --as ...` command and actual client witnesses.
Show which tables supply the screen, which are fully acquired, and which use
a horizon. Reuse current diagnostics rather than add a new residency report
format. Do not infer real client memory from fixture row counts alone.

The paired residency experiment is deferred until two configurations prove
equivalent offline answers. It is not a required implementation deliverable.
For a future Clique measurement, retain two explicit configurations for a paired
experiment only when both meet the same required offline product scope: the
builder's broad public replication and a candidate using justified horizons
or server-only nonessential aggregates. Record transferred rows/bytes, first
useful content, completed durable acquisition, peak memory and offline reopen
on the real web and native clients. Report any reduction in offline history
or prediction separately; it cannot be claimed as an equivalent speedup.

## 5. Acceptance

Extend existing starter and witness scenarios to cover:

- Prime a room, terminate the app/page, stop the backend, and open its route
  with no attempted create mutation before rendering held history.
- Open an unknown room offline and preserve uncertainty instead of creating
  a duplicate or reporting authoritative absence.
- Persist two pending writes across process/page restart, then reconnect and
  verify ordered settlement with the original ids and no duplicate rows.
- Render a pending nonpredicting write, a failed write and a stale retained
  read through the existing card without an application shadow queue.
- Upgrade the web shell with an older tab open; sign out/switch accounts and
  verify the shell cache contains no authenticated response or media bytes.

Success is a fresh builder retaining those properties while replacing the
starter's business screens. Keep generated/example code volume, route
corrections and measured acquisition beside the result. No new push gate or
global cache service is proposed. If a generic shell solution expands into a
framework, limit the first increment to the one published starter and record
the unsupported build shapes.

## 6. Implementation record — 2026-09-22

The selected implementation adds `init --web`, embedding the maintained
`apps/chat` reference; ordinary init remains schema-only. `shell.ts` is one
Vite production plugin for a single generic entry and hashed emitted assets.
The supported base is `/` or an absolute directory such as `/chat/`; routes
use `#room=<id>`. No SSR or arbitrary navigation fallback is promised. The
worker precaches with credentials omitted, waits for older controlled tabs
to close, then retires that scope's previous shell cache.

The room query reads conversation and membership directly, independent of
the inbox's first page. Incomplete offline absence remains uncertain.
`state.ts` stores only backend/principal-bound route and write references;
`Composer.tsx` persists the mutation ID before SDK dispatch and observes it
with `usePendingWrite`. SDK outbox payloads and replay are unchanged. A
server-only `readMarkers` table and `markRead` operation provide a concrete
nonpredicting write. Receipt display remains reachable when room authority
changes; terminal failures and unknown receipts are explicit. References
contain no message body: editable failed drafts after a process restart
remain a product-specific draft-storage choice, not a second replay queue.

Account changes invalidate the prior view synchronously, before async close
or sign-out work. Offline sign-out leaves the account's replica/outbox
intact. The starter explicitly selects the existing browser session store
for guest continuity and documents that page scripts can read that token.
Shell caching never stores it. The public client contract is unchanged; the
sign-out repair below also applies to native hosts using the local client.

Validation added to existing init and React tests covers no-overwrite,
schema-only default, nonprediction, delayed old-account callbacks and saved
write identity. `witness/starter.mjs` drives actual generated production

### Integrated-review repair: local sign-out completion

The independent Astra code review found that the completion screen could
precede credential deletion when logout or refresh stalled. The local client
now fences refresh adoption immediately, including a delayed transport or
response body. It waits for a session-store
write already underway before deleting the credential, so that write cannot
restore a token after completion. Deletion precedes media cleanup; ordinary
close still preserves a successfully rotated session. Remote logout is bounded
best effort and does not gate the local boundary. Storage failure rejects
sign-out for retry; the starter displays progress or that failure, and shows
completed sign-out only after the SDK resolves. The replica/outbox is retained.

The initial repair's final verification on M5 passed: 25 auth regressions, including seven
new persistent-store/transport lifecycle cases; all 49 guide tests; all 15
React cases; package build/typecheck; starter check/typecheck; and the complete
production browser witness (8.429 seconds). The browser held a real logout
request open, observed completed sign-out with no persisted credential, closed
the page, and refused the previous account on a fresh offline page. The first
starter typecheck caught an `exactOptionalPropertyTypes` annotation mismatch;
it was corrected before the final run. Final logs are retained under
`/tmp/sb4-3011-20260922/signout-*-2.log`; the first-run logs remain alongside.
The shared SDK change requires a fresh native Release bundle and repeated
reference witness before final package binding; that result is recorded in
the separate application-evidence report.

The independent Grok follow-up found that aborting a committed rotation could
lose its successor: the retired bearer cannot revoke the server's live family.
The repair keeps the real rotation promise separate from locally cancellable
adoption work. Sign-out captures it before synchronous lifecycle callbacks,
tries the current bearer, and also logs out any returned successor, without
waiting for its response, adopting it, or writing it to storage. The promise
remains tracked through the resolved-but-not-adopted microtask boundary.
The durable deletion ordering and ordinary-close behavior are unchanged.
Focused regressions cover abort-aware and abort-ignoring delayed requests,
delayed body parsing, a forever-stalled rotation, the resolved microtask race,
and real server family revocation after local completion.

Final follow-up verification on M5 passed on `5554e9a24`: 28 auth regressions,
five real-server cases, 49 guide tests, 15 React cases, package and starter
checks/typechecks, and the complete production browser witness (8.856 s).
Logs are retained as `/tmp/sb4-3011-20260922/successor-*.log`.
The maintained native reference was rebuilt in Release, freshly installed on
the owned iPhone 17 Pro / iOS 26.5 simulator, and passed both witness segments
in 23.128 s: offline 8.600 s; process restart 11.993 s. Both original write IDs
survived the restart and settled once, in order. Four extracted video frames
show the pending and sent states. The native framework bytes match runs 1
and 2; the repaired JavaScript is embedded in the newly hashed app bundle.
Source, installed-app and framework manifests plus the summary are retained
as `native-reference-3-*.json`, with receipts, videos and frames under
`native-reference-3/` in the same artifact directory. The owned simulator was
shut down and port 49380 left free. This is qualification of the maintained
reference built from workspace artifacts; installed-package and new Clique
application proof remain separately scoped.


The exact staged 0.2.32 client/platform tarballs subsequently passed the same

## 7. Revision 2026-10-11: small default starters, chat as a template

Wave 1 of the app farm (100 agents, each building a new app on 0.4.16) found
the full chat reference a poor first scaffold: 31 lanes deleted chat routing,
intents, workers and screens before writing their own app, and its files
carried this repository's design history (LLP pointers, "nothing compiles it
until week 2"). The decision:

- `init --web` and `init --expo` write one screen over one table: a todo list
  with guest sign-in, a live `usePage` query and three `useMutation` writes,
  on the same `createApp` + device composition the chat uses. Toolchain pins
  still come from the maintained reference apps, so the two cannot drift.
- The chat reference stays the supported production output of §1 and its
  witnesses, reachable as `init --web --template chat` and
  `init --expo --template chat` (also `new <dir> --template chat --web`).
- Every starter is written without `@ref` pointers: init keeps each
  comment's gloss and drops the pointer into this repository's records.
- The Expo starters ship `expo-env.d.ts` (`/// <reference types="expo/types" />`).
  Without it `process.env` is typed only when some import happens to load
  `expo-modules-core`'s globals, so replacing `src/client.ts` broke the
  starter's own typecheck under TypeScript 6 (16 lanes).
- A starter `package.json` created where no package and no `.js` script
  exists above or below keeps the starter's `"type"` (Vite's ESM); otherwise
  the inherited interpretation rule above still applies.
- `init` still refuses all-or-nothing by default; `--skip-existing` keeps every
  existing file (never overwriting `snapback/*.q`) and writes only the missing
  ones, and `E_INIT_CONFLICT` names that recipe instead of leaving agents to
  init elsewhere and copy over their schema. `--port N` writes the backend URL
  the client calls; the Vite starters pin port 5173 with `strictPort`.

### 7.1 Wave 2 (0.4.17): a starter beside a project's own schema

Wave 2 of the app farm (100 agents on 0.4.17) mostly wrote the backend first
and ran `init --web/--expo --skip-existing` afterwards. The 0.4.17 starter then
wrote its `fixtures/todos.jsonl` and `test.cases.jsonl` beside a schema with no
`todos` table, and the fail-closed fixture loader turned a green project red
(19 lanes). The decisions:

- **Any `snapback/*.q` is the project's schema.** `init` reads them before
  writing. The starter's `schema.q` is a conflict (or, with `--skip-existing`,
  kept out) when another `.q` file exists, and the todo starter's fixtures and
  cases are written only beside the starter's own schema; init says which it
  skipped. A stray `todos.jsonl` that 0.4.17 wrote names the starter in the
  loader's refusal.
- **The screen follows the kept schema's sign-in.** With `use personas` and no
  `use identity`, nobody can sign in as a guest, so the web and Expo starters
  write a persona picker (`openApp(persona)` → `createApp({ url, persona,
  device })`, one app per persona, closed on switch) around the same `Todos`
  screen; a password-only or identity-less schema gets a one-line pointer.
- **Vite's config is `vite.config.mts`** (both the starter and the chat
  template). The package's `"type"` stays whatever the project chose, including
  `npm init -y`'s `"commonjs"`, and Vite still loads the config as ESM, with no
  CommonJS-API warning (17 lanes). This replaces rewriting the package type.
- **Ports move together.** `--web-port N` sets Vite's `server` and `preview`
  ports (strict); without it, `--port N` puts the page on N+1 so a project
  confined to a port range stays inside it. init prints both URLs.
- **Adapting the starter is the expected path.** `package.json` scripts compare
  as commands (option order is not a conflict); a caret range of the starter's
  own `snapback4` version, as `npm i snapback4` saves it, is pinned to the
  exact version rather than refused; `.gitignore` covers `dist/`; the page
  title and Expo app name come from the directory; the starter CSS lives in
  `src/styles.css`. The conflict's first line names `--skip-existing`.

### 7.2 Wave 3 (0.4.18): init first, schema second

Wave 3 of the app farm (100 agents on 0.4.18) showed that §7.1's fixes fire
only when the schema exists *before* `init`. The README and the brief lead
agents to `init --web/--expo` first; they then replace `snapback/schema.q` and
are left with the todo starter's `fixtures/todos.jsonl` and cases (`test` runs
nothing), a guest sign-in screen over a persona-only schema (`auth.guest()`
refuses `E_AUTH`), or, rerunning init to get the picker, `E_INIT_CONFLICT`
(21 lanes, 41 minutes). The decisions, which make the outcome independent of
the order:

- **Leftovers are judged by the starter's bytes.** A starter file is a
  leftover only while it is byte-identical to what init wrote (the screen
  and client compared after normalizing the backend port and the persona
  list, the two values init varies) *and* it no longer fits the schema: the
  fixtures and cases when no `todos` table with `list`/`add`/`toggle`/`remove`
  exists; the screen and client when the schema's sign-in wants the other
  screen (guest for `use identity` with guests, the persona picker for
  `use personas` without `use identity`, or a picker for a different cast).
  A file the project changed is never reported as a leftover and never
  touched. No manifest is written: the starter text embedded in the binary is
  the reference, so a project that has never run 0.4.19's init still qualifies.
- **`check` names them, `init --adapt` fits them.** A successful `check`
  ends with a `starter:` block listing each leftover and its reason, then
  one command, `snapback4 init --adapt` (`check --json`: `starterLeftovers`
  with `files`, `advice` and `fix`). It never changes the exit status.
  `init --adapt [dir]` removes the unmodified fixtures (0.4.19 also removed
  an emptied `fixtures/`; §7.4 reverses that), and rewrites the unmodified screen and client to exactly
  what schema-first init writes for the same schema and port. A password-only
  or identity-less schema, and an adapted screen whose `Todos` component still
  calls the starter's operations, get advice lines rather than a rewrite.
  `--adapt` accepts only `--web`/`--expo` beside it and refuses without a
  `snapback/*.q`.
- **A project's `snapback/*.q` is never a conflict.** With any `.q` present,
  init leaves the starter's `schema.q` out with or without `--skip-existing`,
  lists the project's `.q` files as kept, and never writes through a linked
  schema. This replaces §7.1's "a conflict (or, with `--skip-existing`, kept
  out)". When an `E_INIT_CONFLICT` lists the files of an earlier starter that
  `--adapt` would fit, its first line and its rewrite name `init --adapt`.
- `test`'s refusal of a stray `todos.jsonl` names `init --adapt` as well.

Not done: `test` does not silently skip starter fixtures; a run that
executes nothing stays a refusal, and the command to fix it is one line.
(§7.4 skips the unmodified starter rows loudly instead.)

### 7.3 Wave 3 (0.4.18): the Expo starter's audit findings

Seventeen of the thirty Expo lanes reported `npm install`'s 22 findings
(7 moderate, 15 high) and the deprecated `uuid@7`, and several read
`npm audit`'s "fix" (Expo 44) as advice. A real install of the 0.4.18
starter from the registry resolves three advisories, all under `expo`:

| Advisory | Package (path) | Patched release | Disposition |
|---|---|---|---|
| GHSA-w5hq-g745-h8pq (moderate, 7 findings) | `uuid@7.0.3` (`@expo/config-plugins` → `xcode@3.0.1`) | `uuid` ≥ 11.1.1 | **Overridden**: `"overrides": { "xcode": { "uuid": "11.1.1" } }`. `xcode` calls CommonJS `require('uuid').v4()`, which 11.x still exports (12+ is ESM-only), so the override is scoped to `xcode` and pinned to 11.1.1 |
| GHSA-vfj7-8cjw-p6xm (high) | `braces@3.0.3` (`@expo/metro` → `metro-file-map` → `micromatch`) | none: every release is in range | Accepted, documented: Metro's file watcher; nothing reaches it but the project's own globs |
| GHSA-86w9-cpqp-85rv (high) | `node-forge@1.4.0` (`@expo/cli`, `@expo/code-signing-certificates`) | none: every release is in range | Accepted, documented: the Expo CLI's update code signing, unused by the starter |

`expo_package()` adds the override, so `init --expo`, `--expo --template chat`
and `new --template social` all carry it; an existing `package.json`'s own
`overrides` is kept as written (init only adds absent keys). Measured with a
real install, `npm audit` (and `--omit=dev`, since `expo` is a runtime
dependency) report 15 high and no deprecation; `npm run typecheck` and
`npx expo export -p web` pass. The starter README names both remaining
advisories, why they do not reach the app bundle, and that `audit fix --force`
downgrades to SDK 44.

Re-pinning was measured and not taken: Expo 57.0.27 (the newest SDK 57 patch)
resolves the same `@expo/cli` and `@expo/metro`, so the same 15 findings, and
would also move `expo-sqlite` (~57.0.4), which the native device links; the
reference app `apps/chat-expo` and its witnesses own that pin (§7), and this
change does not move it.

### 7.4 Wave 4 (0.4.19): the starter path after the schema

Wave 4 of the app farm (100 agents on 0.4.19) put 33 lanes (45 minutes) on
the starter path after the schema. One cause was a 0.4.19 regression; the
others were §7.2 stopping short. The decisions:

- **Adapt removes files, never a directory** (17 lanes). 0.4.19's adapt
  removed the two todo fixtures and then the emptied `fixtures/`, while its
  output named only the files; the documented next step, writing
  `fixtures/<table>.jsonl`, failed with `ENOENT` (and `ls fixtures/` after
  adapt explained the "adapt exits 2" reports). Adapt now removes only the
  files it names and says `fixtures/` stays. A project's own fixture file
  beside the starter's is never touched.
- **`snapback/generated/` is never a conflict** (6 lanes). Schema first,
  `check`, then `init --web` refused `E_INIT_CONFLICT` on the
  `snapback/generated/package.json` that `check` had written. Everything under
  `snapback/generated/` is regenerable output: init replaces the file it
  writes there (only `package.json`) and never lists it as a conflict.
- **Script spellings that run the same command are the same command.** A
  leading `npx`, and tsc's default project (`-p`/`--project` naming
  `tsconfig.json`, `./tsconfig.json` or `.`), no longer differ from the
  starter's script; init keeps the project's spelling and says so
  (`kept your package.json scripts.typecheck "tsc --noEmit" (the same
  command as the starter's …)`). A different command, such as
  `tsc --noEmit -p other.json` or another `build`, still refuses: keeping it
  would leave the starter's README instructions running something else.
- **A screen that compiles against any schema** (8 lanes). After §7.2's
  adapt, the screen behind the sign-in still called `api.list`/`add`/
  `toggle`/`remove` and the app did not typecheck. The starter screen is now
  composed of a sign-in head (guest, or persona picker) and a body: the
  todo list, or a neutral `Home` that shows the signed-in viewer
  (`useSignedInViewer()`), the link state and `Object.keys(api)`, with a
  comment naming the hooks and `snapback/generated/api.ts`. The parts are
  whole files whose single-line named imports init merges per module. Both
  orders write the same bytes: schema-first init beside a schema without
  the todo operations writes `Home`, and adapt rewrites an unmodified
  starter screen of either body and either sign-in to the one the schema
  wants (restoring the operations brings `Todos` back). A password-only or
  identity-less schema still gets advice for the sign-in, but its body is
  adapted too, so the app typechecks. Leftover detection recognizes all four
  pairs by bytes; a changed file is never touched. Verified with real
  installs from the registry: web (`npm init -y` first) and Expo, init
  first → schema → `init --adapt` → `check` → typecheck → build, for the
  guest and persona sign-ins.
- **`test` skips the unmodified starter rows, loudly** (4 lanes). A
  `fixtures/todos.jsonl` byte-identical to the starter's, beside a schema
  with no `todos` table, is skipped with `test: WARNING: skipped
  fixtures/todos.jsonl — … snapback4 init --adapt removes it`; the rest of the
  run proceeds. Any other file for a missing table, including a changed
  `todos.jsonl`, still refuses the run. An unmodified starter
  `test.cases.jsonl` still fails on its first unknown operation, now with a
  hint naming `init --adapt`, so a project that has written nothing of its
  own does not pass vacuously.
- **The advisories before the install** (15 lanes). Neither remaining
  advisory has a patched release as of 2026-10-11 (`braces` ≤ 3.0.3 and
  `node-forge` ≤ 1.4.0 are the whole vulnerable range; 3.0.3 and 1.4.0 are
  the latest releases), so no further `overrides` is possible. `init --expo`
  now prints, before `npm install` runs, that the install takes minutes and
  reports about 15 expected high advisories and not to run
  `npm audit fix --force`; the starter README opens with the same notice
