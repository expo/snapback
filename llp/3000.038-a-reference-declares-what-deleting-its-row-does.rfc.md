# LLP 3000.038: A reference declares what deleting its row does

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 — Quarry column declarations (`on delete`), the binder (eligibility, bounds, index synthesis, `check` notes), the schema IR and its capability fence, the engine's delete path on the server SQLite store (and the evaluation Postgres store through the same runner), both device stores and prediction, partition events, the Lean model and its oracle, the difftest generators, the simulator, the guide cards and the wire refusal codes
**Author:** Claude Opus 5.5 (for Charlie Cheever)
**Date:** 2026-10-12
**Revised:** 2026-10-12 (draft)
**Related:** [LLP 3000](./3000-snapback4.explainer.md) (§7, 2026-09-13 "reference IDs have no implicit foreign-key check": this RFC amends its delete half), [LLP 3000.036](./3000.036-what-the-app-farm-asks-of-the-rule-language.rfc.md) (§15.8, the open question this answers; §16.2, the zero-count guard), [LLP 3000.014](./3000.014-a-child-reads-through-its-parent.rfc.md) (§3, a child lives within its parent; §6, `E_PARENT_HAS_CHILDREN`), [LLP 3000.015](./3000.015-shared-baseline-for-snapback5.spec.md) (§2, one authorization law: work whose shape depends on unreadable rows is charged from a fixed reservation), [LLP 3000.007](./3000.007-relaxed-quarry-and-explicit-residency.rfc.md) (§20.5, held-group proofs for device writes), [LLP 3000.035](./3000.035-quarry-semantics-in-lean.plan.md) (§5.2, the Lean model)

## Summary

Deleting a row today leaves every row that references it in place. The
children keep a typed id that names nothing, and reading the parent through
them gives `null`. Wave 5's lane 081 shipped exactly that bug (cancelling a
screening kept its RSVPs), `check` grew a note for it (`N_DELETE_ORPHANS`),
and LLP 3000.036 §15.8 left the design question to the author. The author's
answer: go straight to the end-game.

A reference column now says what deleting its target does:

```quarry
table tasks:
  project: projects on delete cascade     -- deleting the project deletes its tasks, in the same commit
  assignee: people ? on delete set null   -- deleting the person unassigns the task
  owner: principal
  title: text <=200
  cap 500 by project                      -- cascade and set null are bounded by a cap on the reference
  cap 500 by assignee
  read <- .owner = viewer
  insert <- .owner = viewer
  delete <- .owner = viewer

table comments:
  task: tasks                              -- undeclared: on delete restrict
  body: text
```

- **`restrict` is the default.** Deleting a row that a live row still
  references refuses `E_REFERENCED`, naming the referencing column
  (`tasks.project`). This is a deliberate behavior change; §8 is the
  migration note, and `check` names every delete site whose outcome it
  changes (`N_DELETE_RESTRICTED`, which replaces `N_DELETE_ORPHANS`).
- **`cascade`** deletes the referencing rows in the same transaction, and
  their own references act in turn. **`set null`** (optional references
  only) clears the column. Both are authorized by the parent's delete, and
  only because the schema declares them on the child's column.
- **Both are bounded statically.** A `cascade` or `set null` reference needs
  `cap N by <column>`; the delete charges a reservation fixed by the schema,
  never by how many children exist; `check` refuses a delete whose
  reservation cannot fit its program's ceilings (`E_CASCADE_BOUND`). There is
  no runtime overflow path and no background sweep (§5.3 says why).
- **A device predicts a parent delete only when it holds every referencing
  row** for that parent (the existing held-group proof). Otherwise the call
  queues and the server decides; a predicted delete never predicts half its
  cascade.

## 1. The problem and the decision being amended

- **Evidence.** Wave 5 lane 081 (`delete screenings[s]` kept RSVPs; the
  roster listed them and `screeningCard` was null). Wave 6 lanes 029, 032,
  036, 095 and 085 each wrote a zero-count guard or a cleanup loop by hand
  (LLP 3000.036 §16.2). The booking recipe's `removeSlot` exists only to
  refuse while bookings exist. SQL, Prisma, Rails and Django all give a
  per-relation `ON DELETE`; Convex and Firebase give nothing, and their
  users write the cleanup the farm wrote.
- **The decision of 2026-09-13** (LLP 3000 §7) says a reference validates the
  id's value; insert, update and upsert do not read the target; and
  "deleting it neither cascades nor refuses because references remain". This
  RFC replaces the last clause and keeps the rest: **a reference is still not
  an existence check at write time.** A row may be inserted naming an id that
  does not exist, is hidden, or lives in another partition, exactly as today;
  `require exists t[ref] else CODE` remains the explicit form (§4.4 says what
  this leaves open). What changes is what happens to the rows that reference
  a row **at the moment it is deleted**.

The integrity claim is therefore precise and modest: **after a committed
delete of row `p`, no live row references `p` through a reference with an
action** (restrict refused the delete, cascade deleted the referencers, set
null cleared them). It is not "no dangling reference ever exists".

## 2. The form

```
column: <table> [?] [on delete restrict | on delete cascade | on delete set null] [default …] [written by …]
```

`on delete` follows the type (and its `?`). One spelling; no `on update`
(ids are immutable).

### 2.1 Which references carry an action

A reference **carries an action** when both ends are ordinary durable
tables: the child (the table declaring the column) and the parent (the
table it names) are neither ephemeral nor engine-owned (maintained views,
timeline and receipt bookkeeping, private engine tables). Every reference
that carries an action has one: the declared one, or `restrict`.

A reference that does not carry an action keeps today's meaning (the row
stays) and declaring `on delete` on it is `E_REFERENCE_ACTION`:

| Child or parent | Why no action |
|---|---|
| ephemeral child | its rows live for seconds and are not durable rows; probing or cascading them would make durable deletes depend on presence |
| ephemeral parent | the engine retires its rows on its own clock, and no rule or constraint stands between the engine and its own retirement |
| engine-owned child or parent | the engine derives these rows; no program writes or deletes them |

### 2.2 Eligibility of each action

| Action | Requires | Refused (`E_REFERENCE_ACTION` unless named) |
|---|---|---|
| `restrict` | nothing | — |
| `cascade` | `cap N by <column>` on the child (exactly that column) | without the cap: `E_CASCADE_BOUND`. A cycle in the cascade graph, including a self-reference. A child that is a receipt family's table (its deletes are engine-ordered). A `read through` reference whose child can carry a finite effective deadline (§6.1). |
| `set null` | an optional (`?`) reference; `cap N by <column>` on the child | a required reference; a column that is `immutable`, `written by`, a `sequence` parent, read by the child's read rule or named by its `sync` audience, the root of a recorded path (`.column.field`) or a maintained path, or named by a `cap` other than `cap N by <column>`. Without the cap: `E_CASCADE_BOUND`. |

Rationale for the `set null` exclusions: each one is a place where a value
change has meaning beyond "this row no longer has a parent". An immutable or
field-owned column promises nobody else writes it. A column in the read rule
or sync audience would move the row between audiences, which the parent's
deleter was never authorized to do. A recorded or maintained path stores a
fact resolved through the reference; clearing the reference would leave the
fact describing a parent the row no longer has. A self-reference may be
`set null` (it does not recurse); it may not `cascade`.

**A cap on a `set null` column does not count null.** `cap N by assignee`
bounds each assignee's rows; rows whose `assignee` is null belong to no
parent and are not a group. This is new semantics only for a column that
declares `set null` (a cap on any other nullable column keeps counting its
null group as today), and it is what makes the cap a bound on the
reference's children rather than a limit that the set-null writes would
themselves overflow.

### 2.3 The reference index

Every reference that carries an action is probed by its column. The binder
reuses a plain index whose leading columns are the reference (then, for an
expiring child, its `expire at` column); otherwise it synthesizes an
engine-named one: `[column, id]`, or `[column, expireColumn, id]` for a child
with `expire at`, so one seek skips an expired backlog (as `read through`'s
child index does, LLP 3000.014 §6). A `read through` reference uses its
existing child index.

## 3. What a delete does

A delete of row `p` of table `P` — `delete P[id]`, `delete row`, a unique-key
`delete P[key = …]`, a job, `POST /seed`'s delete, or `snapback4 data` —
runs these steps in the deleting transaction, on every host:

1. **Find and authorize `p`**, as today, with one addition: when any
   reference that carries an action names `P`, the caller needs **read
   authority on `p`** as well as delete authority, for every delete attempt,
   with or without children. A caller who may delete but not read gets the
   ordinary hidden-target refusal. This is LLP 3000.014 §3.1's rule,
   generalized from `read through` children to every referenced table, and it
   is what keeps step 2 from probing a hidden row's children. The system
   principal passes both rules, as it does every rule.
2. **Restrict.** Reserve a fixed charge for every `restrict` reference into
   `P` (one or two index seeks each, §5.1), then probe each, in the schema's
   order of `(child table, column)`, for a **live** row other than `p`
   itself whose column equals `p.id`. The first occupied one refuses:

   `E_REFERENCED: projects at <site> is still referenced by comments.task (on delete restrict); delete or retarget those rows first, or declare the reference's action (guide writes)`

   "Live" means present and not expired. A child inserted earlier in the
   same transaction counts; one deleted earlier in it does not. A `read
   through` reference keeps its own refusal, `E_PARENT_HAS_CHILDREN`, and its
   stricter physical-child probe (LLP 3000.014 §3.3); nothing about it
   changes.
3. **Cascade and set null.** Charge the reservation of §5.1 for every
   `cascade` and `set null` reference into `P`. Then, per reference in the
   same order: scan the live children of `p` through the reference index;
   for `cascade`, delete each one by this same procedure **from step 2**
   (the child's own restrict, cascade and set-null references act; its rules
   are not consulted); for `set null`, write the child with the column set to
   null (its rules are not consulted; its constraints, maintains and
   partition events apply as for any write).
4. **Delete `p`**, as today (receipt membership, constraints, maintains, the
   partition `del`).

Children go before the parent so a maintained column on `p` and any
aggregate over the children see each step in a consistent order, and so a
nested refusal aborts before `p` is touched. Every step is inside the
mutation's transaction: a refusal anywhere (a grandchild's `restrict`, a
constraint, the meter) aborts the whole mutation, and nothing commits.

**Expiry is not a delete.** A parent whose `expire at` passes is absent from
that moment, and the sweep removes it physically; neither fires an action.
A child of an expiring parent outlives it unless the child declares the same
lifetime (`read through`, or its own `expire at`). The writes card says so.

## 4. Authorization and disclosure

### 4.1 Who may delete a child by cascade

**The parent's delete authorizes a declared cascade or set null, and nothing
else does.** The children's `delete` and `update` rules are not consulted.

- *Each child's rule must admit* was the alternative. It fails both ways: a
  project owner could never delete a project with a collaborator's task
  (the task's `delete <- .owner = viewer` refuses), so `cascade` would be
  unusable for the shared trees it exists for; and a refusal from a hidden
  child's rule would tell the caller that a child it cannot read exists and
  is not its own, which is more disclosure than `restrict`.
- *The parent authorizes* is what SQL, Prisma and Rails do. It is sound here
  because the schema says so explicitly, on the child's own column:
  `on delete cascade` is the schema author's statement that a child's
  existence is subordinate to its parent's. The default never writes a
  child. A cascade can never reach a row through a reference that does not
  declare `cascade`, and set null can never touch a column that does not
  declare `set null` or whose value carries authority (§2.2).
- The caller still needs read and delete authority on the parent (§3 step 1),
  so a cascade starts only from a row the caller could see and delete.

### 4.2 What a delete discloses

- **`restrict` discloses one bit per reference:** whether a live row
  references a parent the caller can read and delete. That bit is inherent
  in the meaning of `restrict` (a child that blocks a delete must be
  observable by the party it blocks), and SQL's foreign keys disclose the
  same bit under row-level security. It is not new authority to read the
  child: its id, columns, owner and count stay hidden. The refusal names the
  column, a schema fact, and every probe's charge is reserved before the
  first seek, so cost never says which or how many.
- **`cascade` and `set null` disclose nothing about the children.** Their
  charges are reserved from the schema (§5.1), the mutation's reply carries
  no count, and the caller's device receives `del` (or `put`) events only
  for rows already in its partitions.
- **Transitivity.** A cascade carries step 2 into the children: a hidden
  task's `restrict` comment refuses the project delete with
  `E_REFERENCED … comments.task`. The bit disclosed is then "some row in this
  project's cascade is referenced". The schema declared both edges; `check`
  names the chain in its note (§7).

`check` states the bit in `why E_REFERENCED` and the writes card. A schema
that must not disclose it declares `cascade` or `set null`, or makes the
child readable through its parent.

### 4.3 Who can pin a parent

Under `restrict`, anyone whose insert rule admits a child row naming `p` can
block `p`'s delete: a stranger's bookmark of a public post pins the post.
That is the price of the default, stated plainly:

- `check`'s note at each parent delete site names every undeclared reference
  that can now refuse it (§7), so the author decides per relation;
- the writes card's rule of thumb: **a reference that other principals create
  to your rows (likes, bookmarks, follows, RSVPs) should be `cascade`**;
  a reference that is part of the row's meaning to its own author
  (an invoice's customer) is `restrict`; an optional pointer is `set null`.

### 4.4 Dangling references stay legal

Because writes do not check existence (§1), a row can still name an id that
does not exist; and a parent created later with that id (an id supplied by a
program argument) acquires those rows as its children, including for
`cascade`. This is unchanged from today in kind (such rows already "belong"
to whoever creates the id, for every read through the reference), and it is
why the integrity claim in §1 is about deletes. A schema that needs a live
parent at insert writes `insert <- … and exists parents[.parent]`, or uses
`read through`, which checks it.

## 5. Bounds

### 5.1 The reservation

The work of a cascade depends on how many children exist, and the children
may be hidden from the caller. LLP 3000.015 §2's law applies: work whose
shape depends on unreadable rows is charged from a fixed reservation, so the
meter — and an `E_BOUND` abort — is a function of the schema and the
caller's own work, never of hidden rows.

For a delete of a row of `P`, the reservation is

```
R(P) = Σ restrict references r into P         : probe(r)
     + Σ cascade  references r = (C.col → P)   : cap(C, col) × (unit_delete(C) + R(C))
     + Σ set null references r = (C.col → P)   : cap(C, col) × unit_update(C, col)
```

over every meter kind (examined, index entries, steps, heap, rows written,
rule probes); `probe` is the fixed seek charge of §3 step 2; `unit_delete(C)`
and `unit_update(C, col)` are the static per-row price of the engine's own
delete or set-null write of one `C` row: one row written, its index entries,
one row copy of heap, and each maintained aggregate, maintained column and
partition event `C` sources (the same source-write price LLP 3000.022 §14.3
already computes for a write of `C`). `R` is finite because the cascade
graph is acyclic (§2.2). The engine charges `R(P)` before step 2 and then
runs steps 2–3 inside that allowance without charging per row; the
physical authorization allowance per request (`AUTHORIZATION_WALK_LIMIT`)
is likewise drawn by the reservation's row count, not by rows found.

### 5.2 `check` proves it fits

- A `cascade` or `set null` reference with no `cap N by <column>` is
  `E_CASCADE_BOUND` at the column, with the rewrite (`cap 500 by project`,
  "choose a product limit").
- At every delete site of `P` in a mutation, `check` compares `R(P)` with the
  default mutation ceilings, and in a job with the job ceilings. A
  reservation that cannot fit even alone is `E_CASCADE_BOUND` at the delete,
  naming the chain and its worst case (`deleting projects reserves 500 tasks
  × (1 + 100 comments) = 50,500 rows written; a mutation may write 1,024`),
  with the three recipes of §5.3.
- At run time the reservation is charged like any other work; a mutation
  whose own loop deletes many parents can still reach `E_BOUND`, exactly as a
  loop of inserts can, independent of hidden rows.

### 5.3 Beyond the bound: refuse, with recipes; no background sweep

A relation with no product bound (messages in a long-lived room, likes on a
viral post) cannot cascade atomically, and `check` says so. The recipes, in
the writes card and the `E_CASCADE_BOUND` rewrite:

1. **choose a product limit** (`cap 500 by project`) if the domain has one;
2. **mark, then sweep:** keep `restrict`, add `archived: bool` to the
   parent, have readers filter it, and delete children in a self-chunking
   `job` before deleting the parent (the job card's sweep recipe);
3. **delete children first** in the same mutation when they are few and the
   caller can read them all (a bounded loop with its own cap).

A durable background sweep — delete the parent now, tombstone its id, and
let an engine job delete children in chunks — was considered and is not in
this revision:

- **It reintroduces the bug it exists to fix**, with a delay: until the
  sweep reaches them, the children are live, readable and countable while
  their parent is gone. Hiding them would need every read of the child
  table, on server and device, to consult the tombstone set: a join on every
  read path, including the device's local reads and every maintained view.
- **Atomicity is what authors mean by `ON DELETE CASCADE`.** Every SQL
  database gives it, and the farm's bugs were about state that was visible
  after the delete.
- **Ids need a lifetime rule** (no reinsertion while the tombstone stands),
  which ordinary references do not have today; devices could not predict the
  delete; and the Lean model would need asynchronous semantics.
- The recipe (2) gives the author the same end state with a lifecycle the
  app can render ("archiving…"), using machinery that exists.

If the farm shows demand after this lands, the follow-up is a declared
lifecycle (`on delete cascade later`) whose parent is tombstoned and *read as
absent*, and whose children are read as absent by the same deadline machinery
`read through` uses; §10 records it.

## 6. Interactions

### 6.1 `read through` children

A `read through` reference already has a lifetime rule stricter than
`restrict` (no delete under a live child; no id reuse or removal under a
physical child; LLP 3000.014 §3). It keeps it: undeclared or `on delete
restrict`, it refuses `E_PARENT_HAS_CHILDREN` exactly as today. It may
declare `on delete cascade` when its child can never carry a finite
effective deadline (no `expire at` on the child, and no expiring ancestor in
its chain): then every physical child is live, the cascade (bounded by its
`cap`) deletes all of them, and §3.3's physical-child rule is satisfied
before the parent is removed. An expiring chain would leave expired,
unswept children that still block the parent's removal, and deleting those
too would be unbounded; that combination is `E_REFERENCE_ACTION` with the
recipe "delete live children, let the sweep take expired ones, then delete
the parent". `set null` is impossible (the reference is required and
immutable).

### 6.2 Maintained views, columns and counts

A cascaded delete or a set-null write is an ordinary row change to every
derived structure: aggregates and maintained columns over the children
decrement (or move to the null group), recorded paths are untouched (they
are not eligible for set null), and the parent's own maintained columns are
updated before the parent is removed (§3 ordering). `count tasks by .project`
reads 0 or absent for the deleted project, as it would after a hand-written
loop.

### 6.3 Sync and partitions

Every cascaded delete appends the same partition `del` an ordinary delete
does, and every set-null write the same `put`, in the parent delete's commit
(one `seq`). A device holding a child receives its deletion in the same
catch-up as the parent's, so partitions never hold a child of a parent the
commit deleted beyond that commit. A set-null write cannot move a row
between partitions (§2.2), so no device gains a row. No new audience or log
form is introduced.

### 6.4 Devices and prediction

A predicted delete must predict its whole effect or not predict. On a
device, before step 2, for every reference that carries an action into `P`,
the device must prove it holds the **complete** live population of
`C where .col = p.id` for its viewer: the held-group proof writes already
use for unique keys and caps (`upsert_absence_proven`, LLP 3000.007 §20.5):
the key decides the child's read rule for the viewer (a public child, a
`read through` child of a readable parent, or a rule pinned by the
reference), the group is not retained-only history, and no horizon cuts it.
Without that proof for every such reference, the call queues without a local
row (`E_PREDICT`), and the server decides. With it, the device runs the same
steps on its held rows: a held live child of a `restrict` reference refuses
`E_REFERENCED` locally; `cascade` deletes the held children; `set null`
clears them. Settlement is authoritative, and a refusal replays the
confirmed image (as for every prediction). A `read through` reference keeps
LLP 3000.014 §5's predicted-parent-delete rule.

This queues more parent deletes than today (every parent whose children are
private to other viewers). That is the sound behavior: today's local delete
is "predicted" only because orphans were the semantics.

### 6.5 Programs, jobs, tests, fixtures and seeds

- **Jobs** run as the system principal: rules pass, actions apply, under the
  job ceilings (`check` uses those for a delete in a job).
- **At-most-once.** A replayed mutation returns its recorded outcome and
  re-runs nothing; a cascade is part of that outcome.
- **`test`, fixtures and `POST /seed`.** Fixture rows load as inserts and do
  not check references (unchanged). A seed delete runs §3 as the system. A
  `test` case may `expect` `E_REFERENCED`.
- **Explicit cleanup still works.** A mutation that deletes the children
  first and the parent last commits under `restrict` when it reached every
  child; a zero-count guard (`require rsvpCount[night] = 0 else HAS_RSVPS`)
  still gives an app-specific code before the engine's.

### 6.6 Other row kinds

Receipt family tables keep their engine-ordered deletes (`cascade` into them
is refused; `restrict` probes them). Timeline and maintained tables are
engine-owned and carry no action. Asset columns on a cascaded row are
released exactly as on an ordinary delete.

## 7. `check`, diagnostics and the wire

| Code | Where | Meaning |
|---|---|---|
| `E_REFERENCED` | runtime refusal (not retryable) | a delete would leave a live row referencing the deleted one through a `restrict` reference; names `child.column` |
| `E_REFERENCE_ACTION` | `check` error | an `on delete` the column cannot carry (§2.1, §2.2, §6.1) |
| `E_CASCADE_BOUND` | `check` error | a `cascade`/`set null` without its cap, or a delete whose reservation cannot fit its program's ceilings (§5.2) |
| `N_DELETE_RESTRICTED` | `check` note, review tier | a mutation or job deletes a row of `P` and an **undeclared** reference into `P` (now `restrict`) can refuse it; names each such `child.column`, says this used to keep the children, and gives the three declarations. Declaring any action on the column silences it. Replaces `N_DELETE_ORPHANS`, which is retired: no reference leaves orphans any more. |

`N_DELETE_RESTRICTED` is the "what changed" printout the migration needs:
it fires exactly at the delete sites whose behavior the new default changes
(a delete whose parent has an undeclared, action-carrying reference), and
nowhere else. `guide writes` gains the rule of thumb (§4.3), the three
actions, the bound and its recipes; `why` pages exist for the four codes;
`E_REFERENCED` joins `guide::CODES` and the wire card's refusal table.

## 8. Schema evolution and the migration note

- **Capability fence.** A schema in which any reference carries an action
  requires the capability `reference-actions`; an older engine or device
  refuses it instead of deleting with the old semantics. Every schema the new
  compiler emits with a reference between ordinary durable tables carries it
  (restrict is explicit in the IR).
- **Adopting an action on a populated store** is a schema change that
  builds the reference index (activation builds new indexes today) and, for a
  new `cap`, validates every group as activation already does for caps
  (refusing with the group and count). Changing an action changes only what
  the next delete does; it rewrites no row. Changing a column to optional for
  `set null` follows the existing optional-column evolution.
- **Existing orphans are neither refused nor reported at adoption.** A
  dangling reference is a legal value (§1, §4.4): it can arise at any time
  from an insert, so it is not an invariant activation could establish, and
  an activation-time scan would be a per-row parent lookup over every child
  table on every adoption. An action governs deletes from adoption onward.
  The writes card gives the query that lists a table's dangling references
  for an author who wants to clean them up.
- **Migration note (0.5).** Deleting a row that other rows reference now
  refuses `E_REFERENCED` unless the reference declares `cascade` or
  `set null`. Run `check`: every `N_DELETE_RESTRICTED` is a delete whose
  behavior changed. For each, declare the action you meant; `on delete
  restrict` keeps the new default and silences the note.

## 9. Verification

- **Lean model.** References with actions enter the model's schema; delete
  implements §3 (restrict, cascade, set null; the system principal; the
  authority rule of §4.1). `applyWrite_authorized` is restated: a committed
  delete step is authorized by the parent's rules, and every cascaded or
  nulled row is reached through a declared action from it. Examples cite
  this RFC; the oracle decodes `onDelete`; `run-lean` compares ≥100,000
  generated cases.
- **Difftest.** The generators gain a parent/child pair whose reference
  carries a random action, rows that reference present and absent parents,
  and deletes of the parent (by owner and non-owner, by the system in a
  prelude); `run-devices` compares server against both device stores
  (seeds 0–2999), including predicted refusals, cascades and the queued
  case.
- **Simulator.** The chat world's room delete cascades its messages under
  faults; the exhaustive two-write test adds a cascading delete, so
  disclosure is checked against the model with deletes that cross
  partitions.
- **Unit and CLI tests** for every eligibility rule, the reservation, the
  notes and the codes.

## 10. Not in this revision

- `on delete cascade later` (§5.3's tombstoned lifecycle), if demanded.
- An existence check at insert as an implicit part of an action (§4.4; the
  2026-09-13 decision stands).
- Actions on expiry.
- A report of existing dangling references at adoption (§8).
