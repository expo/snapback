## Summary

Deleting a row today leaves every row that references it in place. The
children keep a typed id that names nothing, and reading the parent through
them gives `null`. Wave 5's lane 081 shipped exactly that bug (cancelling a
screening kept its RSVPs), `check` grew a note for it (`N_DELETE_ORPHANS`),
and LLP 3000.036 §15.8 left the design question to the author. The author's
answer: go straight to the end-game.

A reference column now says what deleting its target does:

```quarry
table tasks:
  project: projects on delete cascade     -- deleting the project deletes its tasks, in the same commit
  category: categories ? on delete set null   -- deleting the category uncategorizes the task
  owner: principal
  title: text <=200
  cap 500 by project                      -- cascade and set null are bounded by a cap on the reference
  cap 500 by category
  read <- .owner = viewer
  insert <- .owner = viewer
  delete <- .owner = viewer

table comments:
  task: tasks                              -- undeclared: on delete restrict
  body: text

table auditLog:
  task: tasks on delete keep               -- history outlives its subject, as every reference did before
  at: time
```

- **`restrict` is the default.** Deleting a row that a live row still
  references refuses `E_REFERENCED`, naming the referencing column
  (`comments.task`). This is a deliberate behavior change; §8 is the
  migration note, and `check` names every delete site whose outcome it
  changes (`N_DELETE_RESTRICTED`, which replaces `N_DELETE_ORPHANS`).
- **`cascade`** deletes the referencing rows in the same transaction, and
  their own references act in turn. **`set null`** (optional references that
  carry no authority) clears the column. **`keep`** is the old meaning, now
  declared: the row stays and names a deleted row. `cascade` and `set null`
  are authorized by the parent's delete, and only because the schema declares
  them on the child's column.
- **Both writing actions are bounded statically.** They need
  `cap N by <column>`; the delete charges a reservation fixed by the schema,
  never by how many children exist; `check` refuses a delete whose
  reservation cannot fit its program's ceilings (`E_CASCADE_BOUND`). There is
  no runtime overflow path and no background sweep (§5.3 says why).
- **What the caller can observe is fixed by the schema**, except the one
  bit `restrict` exists to give: the meter, the touched tables and change
  footprints a commit publishes, the reply's event count and the physical
  authorization allowance never depend on how many (possibly hidden) rows a
  cascade reached (§4.2).
- **A device predicts a parent delete only when it holds every referencing
  row** of the whole closure (the existing held-group proof). Otherwise the
  call queues and the server decides; a predicted delete never predicts half
  its cascade.

## 1. The problem and the decision being amended

- **Evidence.** Wave 5 lane 081 (`delete screenings[s]` kept RSVPs; the
  roster listed them and `screeningCard` was null). Wave 6 lanes 029, 032,
  036, 095 and 085 each wrote a zero-count guard or a cleanup loop by hand
  (LLP 3000.036 §16.2). The booking recipe's `removeSlot` exists only to
  refuse while bookings exist. SQL, Prisma, Rails and Django all give a
  per-relation `ON DELETE`; Convex and Firebase give nothing, and their
  users write the cleanup the farm wrote.
- **The decision of 2026-09-13** (LLP 3000 §7) says a reference validates the
  id's value; insert, update and upsert do not read the target; and
  "deleting it neither cascades nor refuses because references remain". This
  RFC replaces the last clause and keeps the rest: **a reference is still not
  an existence check at write time.** A row may be inserted naming an id that
  does not exist, is hidden, or lives in another partition, exactly as today;
  `require exists t[ref] else CODE` remains the explicit form (§4.4 says what
  this leaves open). What changes is what happens to the rows that reference
  a row **at the moment it is deleted**.

The integrity claim is therefore precise and modest: **when a delete of row
`p` executes, every live row that references `p` at that moment through a
`restrict`, `cascade` or `set null` reference is refused for, deleted, or
cleared.** It is not "no dangling reference ever exists": a later statement,
even in the same mutation, may insert a row naming `p`, and a `keep`
reference, an excluded reference kind (§2.1) or an expired parent still
leaves the referencing row in place.

## 2. The form

```
column: <table> [?] [on delete restrict | on delete cascade | on delete set null | on delete keep] [default …] [written by …]
```

`on delete` follows the type (and its `?`). One spelling; no `on update`
(ids are immutable).

### 2.1 Which references carry an action

A reference **carries an action** when both ends are ordinary durable
tables: the child (the table declaring the column) and the parent (the
table it names) are neither ephemeral nor engine-owned (maintained views,
private maintained state, timeline-owned tables, and a receipt family's
scope, members and runs tables). Every reference that carries an action has
one: the declared one, or `restrict`.

A reference that does not carry an action keeps today's meaning (the row
stays) and declaring `on delete` on it is `E_REFERENCE_ACTION`:

| Child or parent | Why no action |
|---|---|
| ephemeral child or parent | ephemeral rows live for seconds and are retired by the engine on its own clock; probing or cascading them would make durable deletes depend on presence |
| engine-owned child or parent | the engine derives or orders these rows; no program writes or deletes them on its own (a receipt scope is deletable only by the system) |
| a field-owned column (`written by`) | its value belongs to its writers' audience, not to the table's rules; probing, clearing or cascading through it would disclose or write a field only its owner may (LLP 3000.007's field authority), so the binder gives it no reference index |

The integrity of §1 and the migration of §8 therefore cover every reference
**that carries an action**. A field-owned reference keeps today's meaning,
as a reference into an ephemeral table does: it may name a deleted row, and a
read must treat its target as possibly absent.

### 2.2 Eligibility of each action

| Action | Requires | Refused |
|---|---|---|
| `restrict` | nothing | — |
| `keep` | nothing | — (no index, no probe, no read gate) |
| `cascade` | `cap N by <column>` on the child (exactly that column) | without the cap: `E_CASCADE_BOUND`. With `E_REFERENCE_ACTION`: a cycle in the cascade graph, including a self-reference, or in the union of cascade and `read through` edges (§3 step 6); a child that is `append only`, has any field-owned (`written by`) column, feeds a maintained `sum` (view or column), plays any role in a timeline (owned, mapped or authors), is a row-keyed view's member table (its writes may recount a group outside any fixed price), or whose source writes have no fixed price (a `server_only` reservation plan, LLP 3000.022 §14.3); a `read through` reference whose child can carry a finite effective deadline (§6.1). |
| `set null` | an optional (`?`) reference; `cap N by <column>` on the child | everything refused for `cascade` except the cycle rule (set null does not recurse), and a column that **carries authority or meaning anywhere in the schema**: `immutable`, `written by`, a `sequence` parent, the root of a recorded or maintained path (`.column.field`), read by **any** rule of **any** table — the child's own read and write rules (directly or as the first hop of `.column.field`), every other table's `exists`/`created` probe that keys or equates on it, and every rule's hop that passes through it (`.task.column`) — named by the child's `sync` audience or horizon index, or named by any `cap` other than `cap N by <column>` alone. (Another table's sync audience can depend on the column only through a `read through` capture of the child's read rule, which the read-rule exclusion already covers.) |

Rationale for the `set null` exclusions: each one is a place where the
column's value is more than "which parent this row has". Clearing a column a
rule reads can grant or remove authority (`update <- .assignee = null`, or
another table's `exists grants[document = .id, folder = null]`), and the
parent's deleter was never authorized to change anybody's authority. An
immutable or field-owned column promises nobody else writes it. A recorded
or maintained path stores a fact resolved through the reference. A sync
audience or horizon would move the row between partitions. What remains is
the column that only says where a row is filed (a category, a folder used for
display, a "related to"). A reference the author's rules read chooses
`cascade`, `restrict` or `keep` instead. A self-reference may be `set null`;
it does not recurse.

**A cap on a `set null` column does not count null.** `cap N by category`
bounds each category's rows; rows whose `category` is null belong to no
parent and are not a group. This is new semantics only for a column that
declares `set null` (a cap on any other nullable column keeps counting its
null group as today), and it is what makes the cap a bound on the
reference's children rather than a limit that the set-null writes would
themselves overflow. Because the null group is then unbounded, **such a cap
never proves a population bound** (a loop's bound, a page's completeness,
mutation admission): those proofs ignore it, as they ignore an index that is
not unique. (A proof that the pinned value is non-null could recover the bound
for one parent's group; §10 records it.) Cap enforcement, activation's group validation, and a device's
cap proofs skip the null group of that column; changing the action away from
`set null` re-validates the cap at activation, null group included.

### 2.3 The reference index

Every reference whose action probes or writes its children is probed by its
column. The binder reuses a plain index whose leading columns are the
reference (then, for an expiring child, its **effective** deadline column: a
`read through` child's captured `$deadline`, which is the earlier of its own
and its parents' deadlines, else its `expire at` column); otherwise it
synthesizes an engine-named one: `[column, id]`, or
`[column, deadlineColumn, id]` for an expiring child, so one seek skips
an expired backlog (as `read through`'s child index does, LLP 3000.014 §6):
the live rows are exactly `[id, null]` (never expires) and `[id]` with the
deadline after now, so both seeks start at the live suffix and no expired row
is ever visited.
A `read through` reference uses its existing child index. The same index
serves `cap N by <column>`. A `keep` reference gets none.

## 3. What a delete does

A delete of row `p` of table `P` — `delete P[id]`, `delete row`, a unique-key
`delete P[key = …]`, a job, `POST /seed`'s delete, or `snapback4 data` —
runs these steps in the deleting transaction, on every host:

1. **Find and authorize `p`**, as today, with one addition: when any
   `restrict`, `cascade` or `set null` reference names `P`, the caller needs
   **read authority on `p`** as well as delete authority, for every delete
   attempt, with or without children. A caller who may delete but not read
   gets the ordinary hidden-target refusal. This is LLP 3000.014 §3.1's
   rule, generalized from `read through` children to every referenced table,
   and it keeps step 3 from probing a hidden row's children. The system
   principal passes both rules, as it does every rule.
2. **Reserve.** Charge the reservation `R(P)` of §5.1 on every meter, draw
   its row count from the request's physical authorization allowance, and
   publish the schema-fixed trace of §4.2.
3. **Close.** Starting from `p`, follow every `cascade` reference to the
   live rows that reference a reached row, and repeat: the **closure** `S`
   is `p` plus every row reached. (`S` is finite: the cascade graph is
   acyclic and each edge is capped.) Steps 3–5 stream the referencing rows
   through the reference index (§2.3) a bounded page at a time and keep only
   identities; no image outlives its page.
4. **Restrict.** For every row `s` in `S` and every `restrict` reference
   into `s`'s table, look for a live row that references `s` **and is not
   itself in `S`**: the probe streams past the rows of `S` that name `s` —
   `p` included, which may name itself — to the first live row outside `S`
   (each row of `S` names one target per reference, so a delete's probes
   visit each row of `S` at most once, plus one witness per probe). Every
   such probe runs. If any is occupied, refuse with
   the **first occupied reference in schema order** of
   `(child table, column)` — never the first found while walking hidden
   rows:

   `E_REFERENCED: projects at <site> is still referenced through comments.task (on delete restrict); delete or retarget those rows first, or declare the reference's action (guide writes)`

   "Live" means present and not expired. A row inserted earlier in the same
   transaction counts; one deleted earlier in it does not. Because rows in
   `S` are excluded, a diamond (`A` cascades to `B` and `C`, and `C`
   restricts `B`) or a self-referencing child table deletes when the whole
   closure goes together, as SQL's statement-end `NO ACTION` does. A `read
   through` reference is not part of this pass: it keeps its own refusal,
   `E_PARENT_HAS_CHILDREN`, and its stricter physical-child probe (LLP
   3000.014 §3.3), evaluated as each row of `S` is removed in step 6. When
   both would refuse, `E_REFERENCED` comes first (step 4 runs before any
   removal).
5. **Set null.** For every row `s` in `S` and every `set null` reference into
   `s`'s table, clear the column of each live referencing row **not in
   `S`** (deletion dominates: a row that is going away is not rewritten).
   The write rereads the row's current image immediately before clearing it
   (an earlier clear's maintained write may have changed it), consults no
   rule, and applies its constraints, maintains and partition events as any
   write does.
6. **Delete.** Remove the rows of `S` other than `p`, each table before every
   table it must not outlive: its cascade parents and its `read through`
   parent. Only those edges order the removal (an ordinary `restrict` or
   `set null` reference between rows of `S` imposes none, since step 4
   already cleared them), `check` refuses a cycle in their union
   (`E_REFERENCE_ACTION`; e.g. `B` cascades from `P`, `C` cascades from `B`,
   and `B` reads through `C`), and ties keep discovery order. Each row is
   removed from its current image, consulting no rule and applying
   constraints, maintains and partition events as any delete does. Then
   remove `p` as today, **from its current image too**: the actions may have
   changed it (a maintained column on `p` mirrors its children's removal), and
   a store removes index entries from the image it is given. Authorization
   stays the decision of step 1.

Every step is inside the mutation's transaction: a refusal anywhere (a
`restrict`, a read-through child, the meter) aborts the whole mutation, and
nothing commits.

**Expiry is not a delete.** A parent whose `expire at` passes is absent from
that moment, and the sweep removes it physically; neither fires an action.
A child of an expiring parent outlives it unless the child declares the same
lifetime (`read through`, or its own `expire at`). The writes card says so.

## 4. Authorization and disclosure

### 4.1 Who may delete a child by cascade

**The parent's delete authorizes a declared cascade or set null, and nothing
else does.** The children's `delete` and `update` rules are not consulted.

- *Each child's rule must admit* was the alternative. It fails both ways: a
  project owner could never delete a project with a collaborator's task
  (the task's `delete <- .owner = viewer` refuses), so `cascade` would be
  unusable for the shared trees it exists for; and a refusal from a hidden
  child's rule would tell the caller that a child it cannot read exists and
  is not its own, which is more disclosure than `restrict`.
- *The parent authorizes* is what SQL, Prisma and Rails do. It is sound here
  because the schema says so explicitly, on the child's own column:
  `on delete cascade` is the schema author's statement that a child's
  existence is subordinate to its parent's. The default never writes a
  child. A cascade can never reach a row through a reference that does not
  declare `cascade`, and set null can never touch a column that does not
  declare `set null` or that carries authority (§2.2). A child table
  with any field-owned (`written by`) column cannot be a cascade or set-null
  target at all (§2.2), so a cascade never destroys a value whose owner the
  schema singled out.
- The caller still needs read and delete authority on the parent (§3 step 1),
  so a cascade starts only from a row the caller could see and delete.

### 4.2 What a delete discloses

- **`restrict` discloses, per `restrict` reference reachable in the
  closure, at most whether it is occupied** — and the refusal names only the
  first occupied one in schema order. That is inherent in the meaning of
  `restrict` (a row that blocks a delete must be observable by the party it
  blocks), and SQL's foreign keys disclose the same under row-level security.
  It is not authority to read the blocking row: its id, columns, owner, count
  and position stay hidden. Transitively, a cascade carries the bit through:
  a hidden task's `restrict` comment refuses the project delete. The schema
  declared both edges, and `check` names the chain (§7).
- **Everything else a delete with actions publishes is fixed by the schema:**
  - *the meter:* the reservation `R(P)` is charged in place of every per-row
    charge of steps 3–6 (§5.1), so an `E_BOUND` abort depends on the caller's
    own work and the schema, never on the closure;
  - *the physical authorization allowance:* the reservation's row count is
    drawn from the request's allowance (`AUTHORIZATION_WALK_LIMIT`) before
    step 3, and steps 3–6 do not draw from it, so later authorization work in
    the same request exhausts it at a point independent of the closure;
  - *the commit's touched tables:* every table the closure could write
    (reached through `cascade` or `set null`) **and every derived
    destination a write of those tables names** (aggregate and row-keyed
    view targets, maintained-column owners) is added to the commit's touched
    set whether or not a row there changed, so `/changes` invalidation is
    the same;
  - *the commit's change evidence:* a delete whose table statically reaches a
    writing action records an *unknown* change footprint (LLP 3000.023 §12's
    conservative widening) whether or not any row was reached, so `preserved`
    and settlement changes say nothing about which tables lost rows;
  - *the reply's event count* omits every event of a table in that touched
    envelope, whenever the deleted table reaches a writing action: which
    rows the actions happened to change (the root included, whose maintained
    column a cascade may mirror) never decides whether an event is counted;
  - *refusals:* the only data-dependent refusals a delete's actions can
    produce are the declared `restrict` and `read through` lifetime bits.
    Every other write hook a cascaded delete or set-null write runs either
    cannot refuse or is refused at `check`: an `append only` target, and a
    target that feeds a maintained `sum` (removing a hidden contribution
    could push a hidden total out of range: success against an overflow
    refusal would tell the caller about rows it cannot see). "Feeds" needs no
    transitive closure: a maintain's source is an application table and its
    target is engine-owned, so maintains never chain;
  - *partition events* reach only devices that hold the affected rows, as
    every event does: a device receives a `del` or `put` only for a row
    already in its partitions.
- **Timing is out of scope**, as it is for the whole engine (the meter counts
  work, never time): a larger cascade takes longer.

`check` states the restrict bit in `why E_REFERENCED` and the writes card. A
schema that must not disclose it declares `cascade`, `set null` or `keep`,
or makes the child readable through its parent.

### 4.3 Who can pin a parent

Under `restrict`, anyone whose insert rule admits a child row naming `p` can
block `p`'s delete: a stranger's bookmark of a public post pins the post.
That is the price of the default, stated plainly:

- `check`'s note at each parent delete site names every undeclared reference
  that can now refuse it (§7), so the author decides per relation;
- the writes card's rule of thumb: **a reference that other principals create
  to your rows (likes, bookmarks, follows, RSVPs) is `cascade`**; a
  reference that is part of the row's meaning to its own author (an
  invoice's customer) is `restrict`; history that must outlive its subject
  (an audit entry, a recorded contribution) is `keep`; an optional filing
  pointer is `set null`.

### 4.4 Dangling references stay legal

Because writes do not check existence (§1), a row can still name an id that
does not exist; and a parent created later with that id (an id supplied by a
program argument) acquires those rows as its children: under `cascade` its
delete then deletes them, under `restrict` they pin it. That is a destructive
consequence of declaring `cascade` together with caller-chosen ids, not an
undeclared authority, and the writes card says so: **a cascading parent
should be inserted with a minted id, and a child whose rows must name a live
parent writes `insert <- … and exists parents[.parent]`** (or uses `read
through`, which checks it). Such a guard reads the reference, so a reference
it guards cannot also be `set null` (§2.2): it chooses `cascade`, `restrict`
or `keep`.

## 5. Bounds

### 5.1 The reservation

The reservation is built from **closure bounds**: `N(P) = 1` for the root's
table, and for each `cascade` edge `C.col → T` reachable from it,
`N(C) += cap(C, col) × N(T)` (the cascade graph is acyclic and capped, so
this is finite; edges into one table add up). `N(T)` bounds how many rows of
`T` one delete can reach. Let `s(C)` be 2 when the child `C` has an effective
deadline (§2.3) and the reference is not its `read through` reference, else
1: the number of seeks one discovery or probe takes.

`unit(C)`, the fixed price of one engine write of a `C` row, is

| meter | `unit(C)` |
|---|---|
| steps | `4 + 2e(C)` plus the exported plan's steps |
| index entries | `2e(C)` plus the plan's index entries |
| examined | `1` plus the plan's examined |
| rows written | `1` plus the plan's rows written |
| rule probes, output | the plan's |
| heap | the larger of `4 ×` the row's copy ceiling and every plan phase's heap |

where `e(C)` counts `C`'s index entries per row (one per plain index; a
`words(..)` index at its token bound) and **the plan** is the source-write
reservation the engine already computes and exports for `C` (LLP 3000.022
§14.3: maintained aggregates and columns, row-keyed views, assets, captures),
summed over its phases. A child whose plan is `server_only` is refused as a
target (§2.2), as is one whose hooks could refuse on hidden data (§4.2) or
recount outside a fixed price.

`R(P)` sums, meter by meter, over every table `T` with `n = N(T)` and every
`restrict`, `cascade` or `set null` reference `r = (C.col → T)`:

| term | steps | index entries | examined | rows written, probes, output |
|---|---|---|---|---|
| each reached row of `T ≠ P` | `n × unit(T)` | `n × unit(T)` | `n × (unit(T) + 1)` (re-read current) | `n × unit(T)` |
| `restrict` `r` (ordinary) | `2·q` | `q` | `q` (one row per seek: seeks that end a range, skipped closure rows, one witness per probe) | — |
| `restrict` `r` (`read through`), `T ≠ P` | `3n` | — | `3n` (LLP 3000.014 §6's three seeks) | — |
| `cascade` `r` | `2·w` | `w` | `s(C)·n` | — |
| `set null` `r` | `2·w` plus `k × unit(C)` | `w` plus `k × unit(C)` | `s(C)·n` plus `k × (unit(C) + 1)` | `k × unit(C)` |
| the root `p` | — | — | `1` (re-read current before its removal) | — |

with `k = cap(C, col) × n` the rows a set-null reference can clear,
`q = s(C)·n + N(C) + n` a restrict reference's seeks (a probe reads one row
per seek, so it examines nothing past its witness), `w = s(C)·n +
⌊cap(C, col)·n / 4⌋` a cascade or set-null walk's seeks (it reads its capped
groups four rows per seek, with one short page ending each range), and
`N(C) = 0` when `C` is not in the closure. The skipped closure rows of a
`restrict` probe are charged once **per reference**: each closure row names
one target per reference, so one reference's probes visit it at most once.
**Heap** is a maximum, not a sum: the largest `unit` heap and child page
(four row copies) along the chain, plus the identities held (`Σ_{T ≠ P} N(T)`
for the closure, one for `p` and four for a page's ids, × a fixed 384 bytes
for a table, an id and the set and queue entries holding them). That holds
because the engine retains identities only: every scan streams its page and
drops its images before acting on them, and every write re-reads its row's
current image. **Output** is the plans' output (a cascade target that is a
row-keyed view's source mirrors into it); it is charged with the rest and
checked against the output ceiling. The **physical
authorization allowance** drawn before the first seek is the examined
total.

Every host computes `R(P)` from the same inputs: the caps, the reference
graph, each table's indexes and declared row size, and the exported
source-write plans. A device's schema projection keeps every table that can
carry an action (it drops only engine-private tables, which carry none) and
the exported plans, so it charges exactly what the server charges; a test
pins that the full schema and its device projection price every delete
alike, and the device difftest compares the two at meter boundaries. A
device that lacks a plan for a reached table cannot price the delete and
queues it.

The engine charges `R(P)` at step 2 and runs steps 3–6 inside it without a
per-row charge and without drawing the physical allowance again. The work it
stands for is bounded by the same terms: at most `N(T)` rows of each table,
probes that skip each closure row at most once per reference and stop at
their witness, pages of at most four rows, and seeks that never visit an
expired row (§2.3).

### 5.2 `check` proves it fits

- A `cascade` or `set null` reference with no `cap N by <column>` is
  `E_CASCADE_BOUND` at the column, with the rewrite (`cap 500 by project`,
  "choose a product limit").
- At every delete site of `P` in a mutation, `check` compares `R(P)` with the
  default mutation ceilings, and in a job with the job ceilings. A
  reservation that cannot fit even alone is `E_CASCADE_BOUND` at the delete,
  naming the chain and the meter it exceeds
  (`deleting projects reserves 50,500 rows written through tasks.project
  (cascade, cap 500), …; a mutation may write 1,024`), with the three recipes
  of §5.3.
- At run time the reservation is charged like any other work; a mutation
  whose own loop deletes many parents can still reach `E_BOUND`, exactly as a
  loop of inserts can, independent of hidden rows.

### 5.3 Beyond the bound: refuse, with recipes; no background sweep

A relation with no product bound (messages in a long-lived room, likes on a
viral post) cannot cascade atomically, and `check` says so. The recipes, in
the writes card and the `E_CASCADE_BOUND` rewrite:

1. **choose a product limit** (`cap 500 by project`) if the domain has one;
2. **mark, then sweep:** keep `restrict`, add `archived: bool` to the
   parent, have readers filter it, and delete children in a self-chunking
   `job` before deleting the parent (the job card's sweep recipe);
3. **delete children first** in the same mutation when they are few and the
   caller can read them all (a bounded loop with its own cap); or declare
   `keep` when the children should outlive the parent.

A durable background sweep — delete the parent now, tombstone its id, and
let an engine job delete children in chunks — was considered and is not in
this revision:

- **It reintroduces the bug it exists to fix**, with a delay: until the
  sweep reaches them, the children are live, readable and countable while
  their parent is gone. Hiding them would need every read of the child
  table, on server and device, to consult the tombstone set: a join on every
  read path, including the device's local reads and every maintained view.
- **Atomicity is what authors mean by `ON DELETE CASCADE`.** Every SQL
  database gives it, and the farm's bugs were about state that was visible
  after the delete.
- **Ids need a lifetime rule** (no reinsertion while the tombstone stands),
  which ordinary references do not have today; devices could not predict the
  delete; and the Lean model would need asynchronous semantics.
- The recipe (2) gives the author the same end state with a lifecycle the
  app can render ("archiving…"), using machinery that exists.

If the farm shows demand after this lands, the follow-up is a declared
lifecycle (`on delete cascade later`) whose parent is tombstoned and *read as
absent*, and whose children are read as absent by the same deadline machinery
`read through` uses; §10 records it.

## 6. Interactions

### 6.1 `read through` children

A `read through` reference already has a lifetime rule stricter than
`restrict` (no delete under a live child; no id reuse or removal under a
physical child; LLP 3000.014 §3). It keeps it: undeclared or `on delete
restrict`, it refuses `E_PARENT_HAS_CHILDREN` exactly as today, and it is not
named by `N_DELETE_RESTRICTED` (its behavior did not change). It may
declare `on delete cascade` when its child can never carry a finite
effective deadline (no `expire at` on the child, and no expiring ancestor in
its chain): then every physical child is live, the cascade (bounded by its
`cap`) deletes all of them, and §3.3's physical-child rule is satisfied
before the parent is removed. An expiring chain would leave expired,
unswept children that still block the parent's removal, and deleting those
too would be unbounded; that combination is `E_REFERENCE_ACTION` with the
recipe "delete live children, let the sweep take expired ones, then delete
the parent". `set null` is impossible (the reference is required and
immutable). `keep` is refused on a `read through` reference: a child that
outlives its parent would break §3.

### 6.2 Maintained views, columns and counts

A cascaded delete or a set-null write is an ordinary row change to every
derived structure: aggregates and maintained columns over the children
decrement (or move to the null group), recorded paths are untouched (they
are not eligible for set null), and the parent's own maintained columns are
updated before the parent is removed (§3 step 6). `count tasks by .project`
reads 0 or absent for the deleted project, as it would after a hand-written
loop. A `keep` reference counted through a recorded path
(`count likes by .postId.authorId`) keeps its contribution, as before.

### 6.3 Sync and partitions

Every cascaded delete appends the same partition `del` an ordinary delete
does, and every set-null write the same `put`, in the parent delete's commit
(one `seq`). A device that holds a confirmed, currently acquired child
receives its deletion in the same catch-up as the parent's. A set-null write
cannot move a row between partitions (§2.2), so no device gains a row. Two
existing exceptions remain, unchanged: a row a device keeps as delivered
history after leaving its group receives no later event (LLP 3000.014 §5),
and a pending local insert replayed after the delete may still name the
deleted parent (§1). No new audience or log form is introduced.

### 6.4 Devices and prediction

A predicted delete must predict its whole effect or not predict. On a
device, for every row of the closure and every `restrict`, `cascade` or
`set null` reference into its table, the device must prove it holds the
**complete** live population of `C where .col = s.id` for its viewer — the
held-group proof writes already use for unique keys and caps
(`upsert_absence_proven`, LLP 3000.007 §20.5): the key decides the child's
read rule for the viewer (a public child, a `read through` child of a
readable parent, or a rule pinned by the reference), the group is not
retained-only history, and no horizon cuts it — **and** the device's
coverage of that range is current (`current_group`: an acquired, synced
group; a rejoined delivered-history range or an online-only table is
unknown, however readable). Readability alone does not prove that every row
is held. Without that proof for every
such pair, the call queues without a local row (`E_PREDICT`), and the server
decides. With it, the device runs the same steps over its held rows, with
LLP 3000.014 §5's witness discipline:

- a referencing row held only as retained history is ignored;
- a held row proves occupancy (a terminal `E_REFERENCED`, or a row to cascade
  or clear) only when it is live and current or the device's own provisional
  write; an expired or non-current held row makes the outcome uncertain, and
  the call queues;
- a `read through` reference keeps LLP 3000.014 §5's predicted-parent-delete
  rule.

Settlement is authoritative and a refusal replays the confirmed image, as for
every prediction. A local refusal is only as fresh as the device's held
rows, exactly like a predicted unique or cap refusal today: a child the
server already deleted can refuse locally until its `del` arrives.

This queues more parent deletes than today (every parent whose children are
private to other viewers). That is the sound behavior: today's local delete
is "predicted" only because orphans were the semantics.

### 6.5 Programs, jobs, tests, fixtures and seeds

- **Jobs** run as the system principal: rules pass, actions apply, under the
  job ceilings (`check` uses those for a delete in a job). The system draws
  no physical authorization allowance, as for all its work.
- **At-most-once.** A replayed mutation returns its recorded outcome and
  re-runs nothing; a cascade is part of that outcome.
- **`test`, fixtures and `POST /seed`.** Fixture rows load as inserts and do
  not check references (unchanged). A seed delete runs §3 as the system; its
  returned count stays "0 or 1": the parent row it was asked to remove. A
  `test` case may `expect` `E_REFERENCED`.
- **Explicit cleanup still works.** A mutation that deletes the children
  first and the parent last commits under `restrict` when it reached every
  child; a zero-count guard (`require rsvpCount[night] = 0 else HAS_RSVPS`)
  still gives an app-specific code before the engine's.

### 6.6 Other row kinds

Receipt family bookkeeping (scope, members, runs) and timeline-owned tables
carry no action (§2.1): a system job that deletes a receipt scope deletes its
members and runs first, as today. A receipt family's messages table and a
timeline's member application tables (posts, reposts, edges, authors) are
ordinary children for `restrict` and `keep`; `cascade` and `set null` into
any timeline-member table are refused (a timeline orders their writes). Asset columns on a cascaded row
are released exactly as on an ordinary delete.

## 7. `check`, diagnostics and the wire

| Code | Where | Meaning |
|---|---|---|
| `E_REFERENCED` | runtime refusal (not retryable) | a delete would leave a live row referencing a deleted one through a `restrict` reference; names `child.column`, the first occupied in schema order |
| `E_REFERENCE_ACTION` | `check` error | an `on delete` the column cannot carry (§2.1, §2.2, §6.1), or a cascade cycle |
| `E_CASCADE_BOUND` | `check` error | a `cascade`/`set null` without its cap, or a delete whose reservation cannot fit its program's ceilings (§5.2) |
| `N_DELETE_NEEDS_READ` | `check` note, review tier | a mutation deletes a row of a table that `restrict`, `cascade` or `set null` references name, and the delete rule is not structurally a reader's (the read rule is not `allow`/`public`, and the delete rule neither is the read rule nor contains it as a conjunct): a caller the delete rule admits but the read rule does not now gets `NOT_FOUND`. Not named where a `read through` child already imposed the gate. The test is a conservative structural heuristic: it can name a delete whose admitted callers all read anyway (`read <- .owner = viewer or .public` with `delete <- .owner = viewer`). A denied delete, and a delete rule containing every conjunct of an `and` read rule, also suppress it. |
| `N_DELETE_RESTRICTED` | `check` note, review tier | a mutation or job deletes a row of `P`, and an **undeclared**, non-`read through` reference into `P` or into any table `P`'s cascades reach (now `restrict`) can refuse it; names each such `child.column`, says this used to keep the children, and gives the four declarations. Declaring any action on the column silences it. Replaces `N_DELETE_ORPHANS`, retired: no action-carrying reference leaves the rows present at a delete behind unless it says `keep`. |

`N_DELETE_RESTRICTED` is the "what changed" printout for the default's
occupancy effect: it fires exactly at the delete sites whose outcome the new
default can change, and nowhere else. The read prerequisite of §3 step 1 is
the other behavior change; `N_DELETE_NEEDS_READ` names the delete sites where
it can matter, and §8 and `why E_REFERENCED` say so. `guide writes` gains the
four actions, the rule of thumb (§4.3), the bound and its recipes, and §4.4's
guard; `why` pages exist for the four codes; `E_REFERENCED` joins
`guide::CODES` and the wire card's refusal table.

## 8. Schema evolution and the migration note

- **Capability fence.** A schema in which any reference carries an action
  requires the capability `reference-actions`; an older engine or device
  refuses it instead of deleting with the old semantics. Every schema the new
  compiler emits with a `restrict`, `cascade` or `set null` reference carries
  it (restrict is explicit in the IR). `keep` is spelled by absence, so a
  schema whose references all declare `keep` stays byte-identical to what
  earlier compilers emitted, and capability-free: older engines already run
  it exactly.
- **Adopting an action on a populated store** is a schema change that
  builds the reference index (activation builds new indexes today) and, for a
  new `cap`, validates every group as activation already does for caps
  (refusing with the group and count); a cap whose `set null` exemption is
  added or removed is re-validated. Changing an action otherwise changes only
  what the next delete does; it rewrites no row. Changing a column to
  optional for `set null` follows the existing optional-column evolution.
- **Existing orphans are neither refused nor reported at adoption.** A
  dangling reference is a legal value (§1, §4.4): it can arise at any time
  from an insert, so it is not an invariant activation could establish, and
  an activation-time scan would be a per-row parent lookup over every child
  table on every adoption. An action governs deletes from adoption onward.
  The writes card gives the query that lists a table's dangling references
  for an author who wants to clean them up.
- **Migration note (0.5).** Deleting a row that other rows reference now
  refuses `E_REFERENCED` unless the reference declares `cascade`, `set null`
  or `keep`. Run `check`: every `N_DELETE_RESTRICTED` is a delete whose
  behavior changed. For each, declare the action you meant; `on delete keep`
  restores the old behavior, and `on delete restrict` keeps the new default
  and silences the note. Separately, a table that other rows reference now
  needs its deleter to be able to read the row it deletes; a deleter that
  could not now gets the hidden-target refusal.

## 9. Verification

- **Lean model.** References with actions enter the model's schema; delete
  implements §3 (closure, restrict with closure exclusion, set null,
  cascade; the authority rule of §4.1). Which occupied reference the refusal
  names is an implementation property the oracle does not compare: the model
  decides only that a delete refuses `E_REFERENCED`. `applyWrite_authorized` is restated: a committed delete step is
  authorized by the parent's rules, and every cascaded or nulled row is
  reached through a declared action from it. Caps are carried by the emitter
  as declared bounds the model does not enforce, under a precondition the
  emitter checks: the case's programs do not insert into or move rows of a
  capped group (otherwise the case stays the named unsupported `table-cap`).
  `run-lean` reports supported action cases by action and outcome, and
  compares ≥100,000 generated cases. The model's query noninterference
  theorems are about queries and are unaffected; mutation refusals are not
  claimed noninterferent.
- **Difftest.** The generators gain a parent/child pair whose reference
  carries a random action (with its cap), rows that reference present and
  absent parents, a second child for diamonds and nested restrict, and
  deletes of the parent (by owner and non-owner, by the system in a
  prelude); `run-devices` compares server against both device stores
  (seeds 0–2999), including predicted refusals, cascades and the queued
  case.
- **Simulator.** A cascading delete under faults, and the exhaustive
  two-write test with a delete that crosses partitions, so disclosure is
  checked against the model with deletes.
- **Unit and CLI tests** for every eligibility rule, the closure (diamonds,
  self-references, set null versus deletion), the schema-fixed trace
  (touched tables, footprint, event count, physical draw) across worlds with
  zero and many hidden children, the reservation, the notes and the codes.

## 10. Not in this revision

- `on delete cascade later` (§5.3's tombstoned lifecycle), if demanded.
- An existence check at insert as an implicit part of an action (§4.4; the
  2026-09-13 decision stands).
- Actions on expiry.
- A report of existing dangling references at adoption (§8).
- `set null` on a column that carries authority, with a declared transfer
  rule.
- A null-exempt cap proving one parent's group bound from a non-null pin.
- Cascade and set null into a table feeding a maintained `sum`, with a
  static proof that its total stays in range.
