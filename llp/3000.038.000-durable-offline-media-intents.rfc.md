## 1. Motivation and scope

Wave 9 NA9/E4 required seven applications to build offline upload queues;
all seven voted this first. An asset selection and its placing mutation must
be one device-owned intent. Exact's adapter calls the contract below; its
implementation belongs to the Exact workstream. HAND owns general wire guide
wording, DX owns starter and guide integration, REL owns publication.

This increment adds durable upload-and-place on devices; the online-only
client still has immediate `upload`. There is no second application outbox.
Audio is a sniffed file (`audio/wav`, `audio/mpeg`, `audio/flac`), using file
bounds, allow-lists, one home and attachment delivery. No transcoding, new
Quarry type, thumbnail processing or audio duration claim is added.

## 2. Custody and admission

`uploadAndPlace(op, args, bytes, {argument, id?, file?})` copies the selected
bytes and normalizes the filename/type before any network I/O. `args` omits
one top-level asset argument, filled only by the upload receipt. The optional
id names both the upload intent and the stable mutation execution. The device
stores the byte copy (hex), metadata, original args, dependency, authenticated
viewer and captured server store identity in the same outbox value and the
same transaction as the queued placing mutation. No arbitrary callback is
persisted. One intent owns one upload; callers compose separate intents for
separate placements. File metadata is normalized before custody: the sanitized last filename
segment is at most 255 UTF-8 bytes and the lowercase MIME essence at most
128 ASCII bytes. Both device hosts validate these bounds too, including
unknown file-metadata fields. Complete encoded placement metadata is at most
96 KiB.
Placing args are limited to 64 KiB of encoded UTF-8 before admission; use row
references for large application data. Declaration/mutation/finalization
envelopes fit the existing 1 MiB HTTP ceiling, with finalization refusal text
bounded to 4,096 characters (code/family/guide to 128).
Admission bounds individual bytes at 64 MiB and total unresolved
upload bytes at 128 MiB (decoded byte counts, before hex expansion); quota/storage failure refuses admission, never reports queued.

The memory device's durable boundary is the host's committed change batch;
the web host uses its ordinary IndexedDB commit and exclusive tab ownership.
Admission is asynchronous and acknowledged only after that commit. It does
not put binary payloads into the synchronous localStorage mutation journal.
SQLite uses its ordinary FULL transaction; Expo's native module invokes that
same dispatcher, so a picker URI is copied into owned bytes before admission.
Memory without a persistence host survives device reopen only when its change
batch is retained. Web admission requires the existing exclusive persistence
claim (IndexedDB uses Web Locks); missing ownership refuses before commit.
Hex doubles storage and transport between the JS host and device; this is a
bounded IndexedDB value under its atomic transaction. Storage quota refusal
leaves no queued intent, and callers reduce/compress large captures before
admission. No successful admission is inferred from an in-memory wasm change. The public
app authority stamp is captured before host waits. Both default and Worker
web hosts hold its authoritative session Web Lock through the strict commit;
a peer logout/replacement denies admission even after the facade check or
while reading bytes. The binary capture never uses localStorage custody. Browser storage eviction and user-cleared app storage are
outside durability, as for ordinary queued writes.

Pending upload bytes, original metadata and placing args travel with orphan
outbox transfer. A crash during transfer leaves source custody until the
whole destination entry commits. `enqueue` accounts destination upload bytes
inside its writer transaction too. At capacity, both default and Worker web
adopters defer that entry and its entire source suffix without removing them, and retry when later
calls release capacity. Recovery cannot bypass the 128 MiB destination bound. Transfer also compares
retained terminal identity: a matching terminal receipt needs no executable
copy; conflicting source input stays at its source and is never dispatched
from a destination that owns another terminal input under the id. When the
destination already has an executable same-id entry, both adopters compare
immutable input through enqueue instead of silently deleting the source. A
matching copy is acknowledged without replacing its state/order; a conflict
defers the source suffix intact. Reload/restart never needs the caller's Blob,
file URI or JS callback. Admission of an existing id compares the original
input, including bytes/metadata/dependency and all non-asset placing arguments, and refuses changed
input with E_WRITE_ID_REUSE. Ordinary mutations and upload placements share
the local mutation id domain; an ordinary mutation already owning the id
refuses a later upload admission. The server asset domain is owner + intent
and independently compares its upload fingerprint; the SDK never advances a
second placing input under that id. Recovery
and duplicate admission never create another placing mutation. Terminal
write history retains the upload fingerprint, operation, viewer and store
identity beside its receipt, within the same 256-entry terminal window.
Upload admission compares this identity before returning an old outcome;
a bare ordinary Write is never proof of an admitted media selection. Changed
terminal input and an ordinary-write id refuse E_WRITE_ID_REUSE. Identity
evicts only with its terminal receipt and travels with shared/orphan history;
value-free cross-tab projections preserve it. Admission checks the applicable
shared receipt directly through the host/device boundary before retention
trimming can evict it; a full destination history cannot bypass shared ownership.
Capture admission uses the client's already identified store binding without
an earlier sync_state/device call that could trigger recovery. An authority-
checked preflight precedes opening/orphan recovery too, so that
recovery cannot first evict the applicable shared receipt. Both media transfer
paths snapshot the existing shared receipt window before sharing/trimming
source history, then compare that protected window and the current window
as well as local/live input before acknowledging transfer;
no byte copy or private identity field is exposed in the public Write.

## 3. Upload and placement

An upload at the FIFO head holds unrelated later mutations too; preserving
submission order avoids a later edit/delete overtaking its intended placement.
Cancellation of a never-dispatched placement releases this hold.

FIFO dispatch resolves the upload dependency before `begin_send` and before
any mutation POST. The device refuses `begin_send(id)` on a known unresolved upload, and an
unscoped begin_send refuses while any upload dependency is unresolved. Host
adapters use this dispatcher barrier; the server independently checks the
declared placement and uploaded asset facts before mutation execution. The web exit
transport cannot dispatch such a head or skip to its tail. No prediction is
published for the held mutation. Sync acknowledgements cannot settle or
release an unresolved upload: an old same-id ordinary receipt is not proof
that this placement dispatched. Readiness and the server declaration fence
precede receipt qualification for upload-dependent writes. The upload is bound to its admitting viewer
and store; replacement does not send it to a new store or reuse old asset
facts. Session rotation for the same viewer can retry; sign-out/close fences
continuations and leaves durable custody for a later matching session.

Before byte transport, `POST /assets/intent/<id>/declare?store_id=...`
atomically binds a SHA-256 byte digest, normalized file metadata and the
original placement (operation, args omitting the asset argument, argument
name). It is idempotent only for that exact declaration; changed bytes,
metadata or placement refuse E_ASSET_INTENT_REUSE before any upload. The
ordinary bounded JSON body carries the declaration, not an oversized header.
A cancelled id cannot be declared again. Byte upload requires this declaration
and checks its byte/metadata fingerprint. The server fills the declared asset
argument with its own authenticated facts for comparison at mutation execution
and early-refusal finalization. A divergent first finalization cannot poison
correct replay identity. A declared but not uploaded intent owns no pinned
bytes and is not an execution receipt; the device still owns its byte copy.

`POST /assets?intent=<id>` deduplicates by authenticated owner and intent id
inside the asset store. Image/video requests omit `as`; files, including
audio, use `as=file&name=...` and declared Content-Type, exactly as the parent
RFC. `store_id` is mandatory on every intent upload and checked both before replay
and again under the final ledger guard;
legacy immediate uploads remain unchanged. Its immutable fingerprint includes the exact bytes,
kind, declared type and normalized filename. Changed input refuses
`E_ASSET_INTENT_REUSE`. The first successful upload atomically commits its
asset ledger row and intent receipt after the private file has been synced, renamed, and its parent directory
has been synced. A receipt cannot precede that pathname durability barrier.
Every ledger writer uses SQLite BEGIN IMMEDIATE: no cancellation writer can
interleave between the in-transaction recheck and publication. Declared rows
are conflict-aware updates; cancelled rows cannot be overwritten.
Concurrent staged duplicates recheck within that transaction and discard
only their own files. A lost reply can retransmit bytes, but records at most
one asset. Physical request attempts are not claimed to occur at most once.
Pending intent assets are pinned against the ordinary unclaimed sweep until
the matching owner + mutation-id has a durable execution outcome, or the
intent is cancelled. A readiness commit followed by an offline restart longer
than an hour therefore still has server-owned bytes when placement resumes.
Device eviction/cleared storage does not make pins undiscoverable:
`GET /assets/intents?store_id=...&after=...` lists the authenticated owner's
pending unplaced pins, 50 per page with a continuation, under the identified
store. The public `serverUploads(after?)` exposes that connected inventory;
`cancelServerUpload(id)` acknowledges the same tombstone endpoint as local
cancellation. This recovery path needs no lost device metadata and releases
quota for abandoned captures. It is explicit because another offline device
may still own an active capture. Server cancellation cannot override a durable
placement receipt, and races are decided under the same ledger transaction.
These connected recovery operations own no second queue; an uncertain
cancellation acknowledgement can be retried under its same id. A later device
reopen treats the authenticated E_UPLOAD_CANCELLED tombstone as acknowledged
cancellation and settles through ordinary local receipt persistence; it does
not leave the bytes permanently blocked or require another manual discard. No pin timeout weakens an admitted offline capture's custody.

The server bounds unplaced pinned bytes to 128 MiB per viewer; exhausted
admission refuses E_UPLOAD_QUOTA. Successful placement gives the ordinary
home lifetime; a failed terminal placement removes the pin via its bound
mutation receipt and the normal unclaimed sweep may reclaim it. Released
home assets are never pinned. Receipts outlive asset garbage collection: if the original bytes were
collected, replay refuses `E_ASSET_INTENT_EXPIRED`; it never creates a new
asset under the same id. A replacement/restored server database follows the
existing store identity/restore refusal contract, not cross-database dedup.

Some nonretryable input, wire and unknown-operation refusals return before
ordinary `_ops` recording. Before settling such a failure for an upload
placement, the SDK calls `POST /assets/intent/<id>/finish?store_id=...` with
the unchanged operation/args and typed terminal refusal. The authenticated
owner's intent must exist. A writer transaction checks the bound ordinary
receipt first (an existing execution outcome always wins), then records a
replay-bound terminal failure and marks the pin settled atomically. Retryable
refusals cannot finalize. Cancellation tombstones stay cancelled and themselves prove terminal failure
for that id; finalization returns their canonical E_UPLOAD_CANCELLED outcome
without inventing a new execution or reviving byte custody. Finalization
never revives their bytes. A lost finalization reply retries the same bound
id; the device retains its executable entry until this receipt and local
settlement persist. Schema changes and early wire refusals therefore cannot
strand pin quota. This endpoint is upload-specific, not a new general ordinary
mutation protocol. HAND owns general receipt/protocol text.

After upload success the device atomically stores authenticated facts, fills
the placing argument, marks the dependency ready and releases its byte copy.
Failure of this commit retains bytes and the same upload id for replay.
Only after it commits does ordinary mutation delivery run, with its existing
at-most-once id, receipt persistence, FIFO and restore fences. Terminal
placement outcomes retain ordinary write history; retention of receipts does
not confer historical read authority or a media home.

## 4. Typed states and adapter contract

The optional upload capability is typed on Client and detected by
`hasUploads(client)`. Local clients provide the complete capability; the
public createApp facade forwards it through the same session authority checks,
input snapshots and subscription retirement as ordinary writes. Readers
recheck scope after asynchronous completion. Every facade mutating method
rechecks active scope after the authority wait and before invoking the raw
operation. An operation already committed under its original owner keeps its
real acknowledgement across retirement, as ordinary writes do; retirement
cannot manufacture failure for an acknowledged cancellation or admission.
A positive authenticated cancellation response for its original request is
returned even if the owner retires while its body completes; the explicit
remote cancellation command owns and consumes its original request through
body completion, independently of client retirement/abort. A real transport
failure is unknown and retryable under the same id; retirement alone cannot
turn a later positive acknowledgement into an unknown result. Admission results retain their
real committed outcome if the facade retires mid-call. AppProvider's React
hook therefore uses the guarded client, never a private raw-client escape.
`useUpload` exposes `available`; an unsupported online tier returns typed
E_UPLOAD_DEVICE when asked to admit, with no capture custody or transport.

`UploadIntent` distinguishes `queued`, `uploading`, `blocked` (typed refusal,
retryable or manual), `placing`, `cancelling`, and terminal `sent`/`failed`. The durable
outbox owns progress; `uploading` may be retried after a crash. Successful
upload is not successful placement. `uploads()` reads current intent states;
`onUploads` reports invalidation, never promises delivery. `retryUpload(id)`
clears a blocked upload's hold without changing its immutable input or id.
`discardUpload(id)` transactionally marks a cancelling dependency only if
`begin_send` has never persisted dispatch. It does not immediately remove the
outbox entry or manufacture failure for an unknown placement outcome. A late
readiness continuation refuses after cancellation wins that transaction.
The SDK retries `POST /assets/intent/<id>/cancel?store_id=...` under the same
viewer/store. The server atomically writes a cancellation tombstone before
releasing the pin; a concurrent staged upload cannot commit past it. Only its
acknowledged cancellation is durably settled as E_UPLOAD_CANCELLED and then
removed through ordinary receipt settlement. A lost cancellation reply retries
the same tombstone. Once begin_send committed, cancellation refuses
E_UPLOAD_DISPATCHED and the existing placement receipt owns recovery. No
retry or cancellation changes the id or abandons a dispatched mutation.

`uploading` after a crash is retryable under the same id; a permanent blocked
refusal requires explicit retry or cancellation. E_OFFLINE and retryable
transport/store/admission overload refusals automatically retry with ordinary
outbox backoff. E_ASSET_TYPE/TOO_LARGE, E_ASSET_INTENT_REUSE/EXPIRED, quota
and schema/argument refusals block without automatic upload retries; callers
may cancel or explicitly retry unchanged bytes after fixing the cause.
Viewer/store mismatches fence transport; replacement cannot be repaired by
changing the existing intent's binding. A failed admission has no custody and
returns failed; a terminal placement or acknowledged cancellation uses Write
sent/failed. `uploads()` lists unresolved dependency states only, oldest first;
`uploadIntent(id)` consults ordinary terminal write history before presenting
its unresolved state. Terminal receipt retention is unchanged; eviction can
return undefined and cannot evict unresolved upload custody. React `useUpload` uses these operations and
reads states again after subscription/reload. Expo uses the same local client.

Exact calls the public local-client API on the very same device client that
owns its ordinary mutations; it forwards DeviceCore committed callbacks and
symbol capabilities. It must await admission before acknowledging capture.
The documented JSON commands are an implementation boundary for platform
hosts, not a second adapter delivery API. An adapter must not dispatch these
placing mutations via its online tier or own another queue. The SDK owns
upload retries, readiness, placement and cancellation. Exact's integration
and its own platform witness belong to the separate Exact workstream.

Expo `saveAsset` fetches through `client.asset`, preserving its authorization
and offline retention behavior, and gives a private temporary copy to the
native share/save sheet. Its result means presentation, not that a user chose
a destination. Cancellation and failures are typed; temporary files and
asset handles are disposed after presentation completes. Filenames are one
sanitized segment; no bearer token is placed in a URL.

## 5. Proof obligations

Both stores must prove atomic admission, duplicate-input refusal, reopen with
owned bytes, blocked begin-send, atomic readiness, typed retry, bounds and
store/viewer fencing. The server must prove concurrent dedup, lost response,
restart, changed input, owner isolation and collection tombstones. The browser
must prove IndexedDB reload and orphan transfer of upload custody, failed
persistence, blocked exit send and recovery of uploaded-but-unplaced intents.

Extend the existing delivery-fault matrix and its conservative all-client
await boundary census (LLP 3000.019 §3.3). Each new reachable await gets an
explicit semantic classification and transient/persistent fault fixture;
pre-dispatch custody and uncommitted readiness remain required barriers.
Already committed replies survive later host failure, as ordinary admission
and receipt persistence do. Upload bytes cannot disappear until readiness
commits; mutation dispatch cannot precede it. Await additions outside the
matrix must explain reachability and point to dedicated tests.

Qualification: affected asset/client tests, `delivery-fault-matrix`, Chromium
`online-journal-browser`, core/device/CLI Cargo suites, wasm budget and
`ref-check`. Native host code is tested with host-independent fixtures where
Linux cannot execute the iOS save sheet; no simulator claim is inferred.

## 6. Audio verification

Audio uses the file allow-list `audio/wav`, `audio/mpeg`, `audio/flac`.
WAV requires RIFF/WAVE, bounded fmt/data chunks with nonzero channels/rate
and a nonempty data chunk. MP3 requires a complete MPEG layer III frame with
valid version/bitrate/sample rate; a bounded ID3 prefix is skipped. FLAC
requires fLaC and a complete first STREAMINFO block of length 34. Declared
mismatches and truncated headers refuse E_ASSET_TYPE. These verify format
headers, not decoded sound or metadata validity; no playback/duration claim.
Immediate upload is still connected-only; use uploadAndPlace for captures
that must survive offline/reload. DX owns the general guide/starter text.

Round 11 clarifies the complete recovery pass: retain its entering shared ownership window across every orphan, and compare live destination input before honoring any matching shared terminal receipt. A conflict holds the source and its suffix intact.

Round 12: after schema adoption an uploaded placing id must never run on the ephemeral path. Both the core and HTTP route refuse media-owned ids lacking an existing execution receipt before ephemeral effects. Existing bound receipts still replay first; the normal media finalization endpoint records the bound permanent refusal and releases the pin. A nonretryable device readiness refusal (including removed/narrowed asset arguments) commits blocked plus its typed reason without discarding bytes. Automatic preparations stop until explicit retry/discard; a failed blocked-state commit retains custody for recovery. HAND owns general durable/ephemeral protocol wording.
