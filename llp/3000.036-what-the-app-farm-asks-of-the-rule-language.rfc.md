## 1. Union sync audiences

### What the farm saw

Round 2's cluster 4 counts 12 v4 builds (5 GPT / 7 Muse, 21.9 adjusted
minutes) and 11 in v3; round 1 counted 6 (4 GPT / 2 Muse). Read by hand,
the cluster mixes shapes: in the v4 snapshot only 7 of the 12 are refusals
of an OR-shaped or mixed public/private read rule (5 GPT / 2 Muse; the other
5, all Muse, are horizon-index order and membership-grant refusals), and in
v3 8 of 11 are (2 GPT / 6 Muse). Across all arms, including builds that
finished after the round-2 snapshot (652 records at 04:35), about 48 builds
met an OR-shaped refusal. What they did instead:

| repair | builds (about) | examples |
|---|---|---|
| a membership or reader table (the paved form) | 24 | crate-return-credit-0930 (Muse, 2 min, three `check` cycles), seed-lineage-swap-0927 (Muse, 4 min + 6 min on an empty online-only read first), volunteer-hour-bank-0213 |
| `online only` (no offline for the table) | 17 | club-charter-approvals-0265, commission-finder-0794 (GPT), inscription-proof-0798, meteor-blanket-0137 (round 1) |
| **weakened privacy**: made the rows public | 5 | memory-quilt-0800 (Muse, 3 min, major), cert-expiry-tracker-0435, commission-balance-0705, brick-lot-split-0960, load-in-clock-0512 |
| **weakened function**: dropped a reader disjunct | 2 | fridge-first-0911 (Muse, 2 min), offcut-finder-0933 |

Minutes per build are small (median about 1–2); the cost is in what
shipped. Two diaries say it plainly:

> "Dropped the poster disjunct; claims are now claimant-private on device
> and the poster reads nothing" (fridge-first-0911, final rule
> `read <- .claimant = viewer`, `sync to .claimant`)

> "So a private-pending-queue + offline mosaic is inexpressible … I made
> photos public-read with strict write rules instead." (memory-quilt-0800,
> final rule `read <- allow`, `sync public last 500 by .at`)

seed-lineage-swap-0927 named the trade: "Snapback's sync-audience strictness
(read rule must *equal* the audience) is the price of offline partitions
that never over/under-hold." `E_SYNC` is also praised (bird-bingo-0527,
sandcastle-shift-0314, scope-queue-0172 and others: "caught a real
authorization design mistake before serving it"), but every such line is
about an open self-join membership, never about an OR rule.

### What Snapback does today

Reproduced on `34852dba1f` (both ticket shapes):

```
schema.q:8:3 — E_SYNC: sync cannot infer an audience from `.approved = {"Bool":true} or .author = viewer`; use public, `.column = viewer`, or `exists target[.columns, viewer]`
  rewrite: use one invertible read rule, or remove sync (online only)
schema.q:9:3 — E_SYNC: sync cannot infer an audience from `.claimant = viewer or .postedBy = viewer`; …
```

The refusal is `infer_audience` in `crates/snapback4-lang/src/bind/schema.rs:357-378`.
It accepts exactly three read-rule forms after removing whole service
disjuncts (`snapback4-core/src/schema.rs:680-702`, LLP 3000.007 §20.6):
`public`, `.col = viewer`, and `exists T[.a, .b, viewer]`. The guide states
why (`guide/sync.rs:111`): "so a device never holds a row it may not read and
never misses one it may". The partition-inversion review that LLP 3000
decision 4 requires pinned the refusal as finding 8
(`crates/snapback4-sim/tests/reviews.rs:98`: "a second disjunct admits viewers
the sync never delivers to"). `NOT-DOING.md:30` keeps it: "A read rule with a
second non-service disjunct is refused with the rewrite, never partially
delivered … Several `sync` lines per table wait for an app that needs them."

Two defects are independent of the design. The literal renders as internal
JSON (`RuleExpr::quarry()` prints non-string literals with
`canonical_json`, so `true` becomes `{"Bool":true}`), and the rewrite offers
only "one invertible read rule, or online only". The guide's E_SYNC
paragraph does say "do not make private rows public just to enable sync"
(`guide/sync.rs:509-517`), but the diagnostic does not, and it names no
split that keeps both readers.

Related positions:

- LLP 3000.007 §20.7 (ruled yes 2026-09-14, **never built**, §20.22.6): a
  `public` table may sync a subset to each device; "a read the subset
  cannot decide is server-class … `complete: false` on the device, answered
  by the server online", giving up the "never misses one it may" half of the
  invariant and keeping "never holds a row it may not read". §20.22.6 adds
  that building it "needs the partition-inversion blind review … and an
  answer for an author's own rows … a second inferred audience is NOT-DOING's
  'union audiences'".
- LLP 3000.028 §3.4 (`with own keys`) gives a public window a compiler-owned
  owner-key partition, but certifies existence only and requires a `public`
  read rule (NOT-DOING.md:59: "General union audiences, full own-row
  replication … remain excluded"). It does not cover public-or-owner rows.

What union would need in the partition log
(`snapback4-core/src/partition.rs`): a table has one `Sync` with one audience
(`schema.rs:387-391`), and `partitions()` returns zero or one partition per
row (:118-130). The log already writes one row to several partitions for
private field owners (`account_row_change`, :183-262), and the server
re-checks each `put` against the reader's rule at stream time (:994) and
suppresses a `del` only for field-owner tables (:958-965). The device keys
rows by (table, id) with no per-partition count: a `del` from any partition
deletes the row (`snapback4-device/src/device/deferred.rs:241-245`), and a
group `scope` leave deletes every row in the group (`device.rs:1279-1296`).
Held rows are trusted as readable without re-evaluating the rule
(`engine/read.rs:268-275`).

### Options

- **A. Keep NOT-DOING; fix the diagnostic.** Render literals in source form.
  Make the rewrite name the split for the two shapes the farm hit:
  public-or-owner ("a `public` table for approved rows, an owner-synced table
  for pending ones; an approval moves the row") and owner-or-counterparty
  ("an `exists` audience over a membership table both principals are in, or
  one row per reader"). Add "never make private rows public to enable sync"
  to the diagnostic itself, and an "owner or role" recipe to `guide sync`.
- **B1. Exact-disjunct narrowed sync (the smallest admitted form).** Admit a
  read rule with several disjuncts when an explicit `sync to` (never an
  inferred `sync`) names a target identical to **one whole disjunct**, and
  that disjunct is by itself one of the three invertible forms with no extra
  conjunct. `read <- .claimant = viewer or .postedBy = viewer` with
  `sync to .claimant` is the case. The named disjunct is checked exactly as a
  whole rule is today, so `read <- (.claimant = viewer and .published) or
  .admin = viewer` with `sync to .claimant` is refused (it would deliver
  unpublished rows). The partition log does not change: `Audience::Column`
  and `Audience::Target` already return the one partition, and
  `account_row_change` already moves a row between partitions when its
  audience columns change. The device holds a subset of what its viewer may
  read, so the disclosure half of the invariant stands. Its other half is
  given up for this table, and the following rules replace it:
  - **Completeness is decided per read site, conservatively.** A site is
    device-complete only when its plan has the shape `infer_audience`
    already recognizes for the named disjunct (the audience index probe,
    within the horizon), followed by the existing acquisition, horizon,
    retention and meter checks. Every other site over the table, including
    `where .id = ?`, a count, and an unsuccessful `exists`, takes the
    existing `unknown_fact` path and is answered by the server online. A held
    row that a site finds is still a valid positive witness. No implication
    solver is needed; `where .claimant = viewer and .status = 'open'` stays
    server-class in the first version, which errs toward the server.
  - **Writes.** An insert into the named disjunct predicts as usual. An
    update or upsert of a row the device does not hold is online-only (the
    same shape as `issues/closed/20261008-snapback4-device-predicts-insert-over-an-unheld-id.md`).
    Upsert absence is never proved from the subset.
  - **Aggregates.** A maintained aggregate over the table must carry the
    "source is a subset" bit that `maintain_subset_unknown`
    (`maintain.rs:186-188`) sets today only for a public read rule with a
    narrower sync, or a device count is a partial count presented as
    complete.
  - **Existing inversion proofs apply to the named disjunct:** a unique
    audience index (review finding 7), the recipient column (finding 2), an
    aggregate not wider than its source (finding 5).
  - **Excluded in the first version:** tables with private field owners
    (`account_row_change` adds the owner's partition, `partition.rs:203-222`,
    so a row is not in one partition, and a group `scope` leave,
    `device.rs:1279-1296`, deletes an image the owner path delivered), and
    `exists` targets whose content group key is mutable (a move from group X
    to Y emits the Y `put` before the X `del`, and the device's
    unconditional delete removes the surviving image for a viewer in both
    groups). Each needs its own preservation and ordering design.
  - A row that leaves the named disjunct but stays readable through another
    (claimant changes from Alice to Bob, `postedBy` stays Alice) is deleted
    from Alice's device. That is correct under B1: Alice's reads of it are
    server-class.

  `check --residency` lists the server-class disjuncts. LLP 3000.007 §20.6's
  "a second disjunct that is not a service principal is still refused" is
  amended only for an explicit, exact named disjunct.
- **B2. Conditional public audience.** A new audience arm,
  `sync public where .approved`, for public-or-owner: the device holds rows
  for which a viewer-free, row-local comparison holds (null is not true).
  This is new machinery, not existing behaviour: `Audience::Public` always
  returns the public partition (`partition.rs:119-120`), and it is not LLP
  3000.007 §20.7 (§20.7 narrows a public read rule; this conditions a public
  audience inside a private one). It needs **commit-boundary audience
  accounting**: today an existing private row set `approved = true` then
  `false` in one transaction would append a public `put` then a public
  `del`, coalescing keeps the `del` (`partition.rs:693`), and ordinary
  deletions are not read-rule filtered, so every public subscriber would
  learn the id of a row that was private at both commit boundaries. The
  predicate must also govern snapshots, join acquisition, horizon selection
  and replayed images. A viewer-free `exists flags[.id]` is not row-local
  and is out.
- **C. Union of partitions.** Several `sync` lines per table; a row is in
  every partition any line names. Needs a device reference count per row (or
  a server-side "delete only when no other partition still grants",
  generalizing the field-owner rule at partition.rs:958 to every table and
  to group `scope` leaves), audience moves on every disjunct's columns,
  horizons per line, duplicate acquisition, and a fresh partition-inversion
  review. It is what builders asked for literally.
- **D. Compiler-owned projections.** The compiler splits a disjunctive table
  into one synced projection per disjunct behind one name, as
  `with own keys` does for existence. Most ergonomic, most machinery; it is
  C with a different storage shape.

### Recommendation

**A now; B1 as the first admitted form, starting with column audiences
(`sync to .col`) and then `exists` targets with immutable group keys; B2 as
a separate, later design; C stays on NOT-DOING.** Confidence: high on A (the
diagnostic is wrong and led builders to the worst repair); medium on B1;
low on B2 until its commit-boundary accounting is designed.

The evidence supports moving part of the NOT-DOING line, not deleting it.
Half of the builds that met the refusal found the membership split
themselves, so A alone, by naming it, would have saved most of the minutes.
A would not have saved the 17 builds that gave up offline for the table, nor
the public-or-owner shape (memory-quilt-0800 and the four other builds that
went public), whose paved split is two tables and a move on approval. B1
covers owner-or-counterparty: each party keeps offline for the disjunct the
`sync` line names, the other disjunct is read online, and no private row
becomes public. B2 is what public-or-owner needs, and it is where the
disclosure risk is; it should not ride on B1.

B1 changes one sentence of NOT-DOING ("never partially delivered" becomes
"partially delivered only when an explicit `sync to` names one whole
invertible disjunct; the rest is answered by the server") and must take
something off the doing-list in the same change, per NOT-DOING's own rule.
C should wait for a build that needs **both** disjuncts offline on one
device.

Wave 1 of the `snapback4` builder loop (2026-10-11) met these shapes again;
[LLP 3000.036.000](./3000.036.000-sharing-shapes-at-sync-and-union-audiences.rfc.md)
records the per-shape rewrites, the roster and self-witness forms admitted
then, and the work list a union (option C) would take.

### What it touches

**Core** (lead), and one of the two disclosure-sensitive mechanisms LLP 3000
decision 4 reserves for a blind two-family review: partition inversion. B1
touches the binder (`infer_audience`, the agreement check at
`bind/schema.rs:335-338`), the residency classifier, per-site device
completeness, `maintain_subset_unknown`, prediction of unheld rows, and the
review test `reviews.rs:98` (an explicit exact-disjunct `sync to` admitted;
an inferred one, or one naming part of a disjunct, still refused). B2 adds a
partition-log change and its own review. A's message and guide text are
periphery; the literal rendering is `RuleExpr::quarry()`, the printer every
diagnostic uses, so it is core and needs a check that no other diagnostic
relied on the JSON form.

## 2. References and existence

### What the farm saw

Two builds, both Muse, in different arms.

- order-relay-hooks-0037 (v1, 5 min, self-blamed): "Placed 2 orders with
  restaurant id literally "EXISTS" … mutation accepted the dangling
  reference without complaint." Most-needed fix: "validate reference args
  at the mutation boundary."
- museum-loan-puzzle-0976 (v2, 4 min, major; not named by the round-1
  synthesis): "Reference-typed mutation args are NOT existence-checked:
  `placeLoan` with exhibit "x" returned `state:sent` and stored a dangling
  loan … No error, no warning." It asked that "`check` should warn when a
  reference arg has no existence guard."

Builders mostly guard already. Of 652 `schema.q` files, 557 (85%; GPT 317,
Muse 240) use a lookup-or-refuse (`n = nodes[node] ! else NOT_FOUND`) or a
`require exists`, and 81 (GPT 70, Muse 11) have a `require exists` whose
probe is a reference or argument check rather than a role gate.

### What Snapback does today

Reproduced on `34852dba1f` with the ticket's schema
(`issues/20261008-snapback4-references-not-checked-for-existence.md`): `snapback4
run placeOrder '{"restaurant":"EXISTS","items":"x"}'` answers `state: sent`
with `"restaurant": "EXISTS"` stored.

This is a decision, not an accident. LLP 3000's record of 2026-09-13
(explainer:587-598): "insert, update and upsert do not read the target, and
deleting it neither cascades nor refuses because references remain. This
preserves the existing value and replica model, where a target can be outside
the viewer's partition or retained history." The paved guard is explicit:
`require exists restaurants[restaurant] else NO_RESTAURANT`, one metered point
probe that treats absent and hidden targets alike (`guide writes`;
`guide/types.rs:22-27`). Validation is `validate.rs:152-153`
(`@ref LLP 3000#7-decisions-during-execution — typed references do not imply
target existence`); the wire decoder accepts any JSON string as a reference
(`wire.rs:65`, `:115`), bounded only at 144 canonical bytes
(`value.rs:386-405`). Minted ids are 26-character Crockford base32
(`ids.rs:3`), but a caller-supplied id is never checked against that form.

What is wrong is the text. `snapback4 why E_INPUT` says "A table reference
validates the id's shape, not the target's existence"
(`guide/codes.rs:206`; `why/E_INPUT.md:4-5`), and `guide writes` repeats "A
typed reference checks the id's shape". No shape is checked. The rule is
stated in a refusal explanation and in `guide types` under membership, not
beside the reference type a builder declares.

### Options

- **A. Keep existence explicit; make the text true.** Replace "validates the
  id's shape" with what happens ("a string identity within the canonical
  identity-size limit, 144 bytes of tagged canonical JSON
  (`value.rs:386-405`), never `system`; the target is not read") in `codes.rs`, `why/E_INPUT.md` and `guide writes`; put the
  `require exists` idiom beside the reference type in `guide types` and in
  `guide from-sql`'s `REFERENCES` row ("not a foreign key").
- **B. A: and validate the minted form.** Refuse a reference whose value is
  not 26 Crockford base32 characters. Catches probe-script garbage like
  `"EXISTS"`. But caller-supplied row ids are not checked either, so stores
  can hold rows whose ids a reference could then not name; B is only safe
  together with refusing non-canonical ids on insert and `/seed`, which is a
  breaking change for existing stores and seeds.
- **C. Check existence on every write of a reference.** One point probe per
  reference column per write, under the writer's visibility. It turns every
  reference into a visibility test (a reply to a row the writer cannot see
  is refused, where today it is admitted), and a device cannot predict such
  a write unless the target is in its partition, so mutations that write a
  reference to an unsynced or past-horizon row become online-only (the same
  cost spine-stamp-hunt-0071 hit with a `require` in a `maintain`). It still
  is not a foreign key: deletes neither cascade nor refuse.
- **D. A, plus a `check` note for an unguarded reference argument.** When a
  mutation writes a reference argument with no `require exists` over it,
  print a note under `check --verbose`. Cheap; noisy for apps that
  legitimately reference unseen rows.

### Recommendation

**A.** Confidence: high that the text must change (it is false today);
medium-high that existence should stay explicit, because C changes
prediction and visibility semantics for one reported build whose bad value
came in both builds from the builder's own probe script, and 85% of builds
already guard. Revisit C if a later round shows dangling references reaching
users. D answers museum-loan-puzzle-0976's ask directly; medium-low
confidence, because it will fire on legitimate references to rows the
writer cannot see, so it belongs under `check --verbose` first.

### What it touches

Periphery: guide text, the `why` explanation, `guide from-sql`. Nothing in
the core changes under A. B and C are core (lead).

## 3. `E_RULE` names its clause in development, and `check` flags a write no caller can make

### What the farm saw

Round 1 counted 8 builds (1 GPT / 7 Muse; 16.9 adjusted minutes, worst
major): remodel-change-orders-0084 (8 min), flashcard-duel-0225 (10, an
upsert with no update rule), late-bus-alerts-0243 (5), budget-tokens-0900
(5), bag-valet-0540, donor-thank-you-engine-0224, travel-approval-flow-0483,
driveway-route-0189. Round 2's v4 cluster has 4 Muse builds, of which 2 are
this shape by hand (catch-the-cursor-0399, 5 min, `update <- deny`;
annotation-throughput-board-0878, an upsert with no update rule); the other
two are a client write-state problem and a deliberately generic refusal.
Later arms add about eight more, all Muse, 2–5 minutes each. GPT hits are
0–1 minute and self-blamed.

> "The message lists five possible causes; nothing says "your mutation's own
> update goes through the table update rule". ~8 min." (remodel-change-orders-0084)

> "`update <- deny` on rooms made even the owning mutations fail with E_RULE
> (no require code reached)." (catch-the-cursor-0399, filed as a docs gap)

Five builds asked explicitly for a `check` warning or a named clause
(late-bus-alerts-0243: "compile-time "unreachable write" note for mutations
inserting into tables no caller can admit"; museum-loan-puzzle-0976,
desk-step-challenge-0660, ev-charger-queue-0888, socks-tribunal-0335).

### What Snapback does today

Reproduced on `34852dba1f`: a mutation `fix` updates a table whose rule is
`update <- deny`. `check` says `ok` with no note. `run fix` answers:

```
failed E_RULE: orders's update rule does not admit this viewer, or a sequence insert requires read authority independent of its ordinal, or a unique key or cap group contains a row you cannot read, or authorization cannot be established within its physical work allowance; to write into another principal's row use `upsert` under an `update` rule, or let a `maintain` keep the count
```

The message is composed at `crates/snapback4-core/src/error.rs:351-354`
under `@ref LLP 3000.007#8 — explain the hidden-collision idiom without
disclosing a row`. The four causes are listed together on purpose: a unique
key or cap group that collides with a row the caller cannot read must not be
distinguishable from a false rule, or the refusal becomes an existence
oracle. The envelope has `site` and `rule` fields (`error.rs:13-31`); E_RULE
fills neither.

**The clause is already known in development.** LLP 3000.015 §2.1
(spec:383-390) made "the exact refusing clause … developer evidence,
separate from `Refusal`", recorded by an opt-in, dev-only collector
(`refusal_trace.rs:1-16`, `45-55`; sites mapped in `bind/refusals.rs:7-27`).
With the same schema under `snapback4 dev`, `run fix --as alice` forwards to
the dev server and `snapback4 why recent` then prints:

```
"clause": "update rule", "code": "E_RULE", "executionSite": "fix:2",
"phase": "update rule", "readRuleSite": "schema.q:11:3",
"site": "schema.q:13:3", "table": "orders"
```

`schema.q:13:3` is the `update <- deny` line. The information exists; the
builder has to know to ask `why recent`, and `run` against a local store
with no dev server (the path `E_STORE_BUSY` used to force) prints only the
four-cause message and leaves nothing for `why recent` to show.

`check` has static notes of exactly this kind (`N_SEQUENCE_READ`,
`bind/refusals.rs:29-50`: a first insert "always refuses E_RULE"), but none
for a mutation writing a table whose effect rule is `deny` or absent. Jobs
must be exempt: the system principal passes every rule (`read.rs:282`,
`guide/jobs.rs:89-90`). No guide sentence says that a mutation's writes still
pass the table's insert/update/delete rule; the nearest is "Writes check the
rule, then unique indexes, caps…" in the E_INPUT explanation.

### Options

- **A. Name the clause on the wire when it evaluated false.** Fill `site`
  and `rule` on E_RULE only when the table rule itself evaluated false.
  Refused as written: "no site" would then mean "hidden row or budget", which
  is still an oracle. Information derived from the schema alone and attached
  uniformly to every E_RULE for that table and effect (for example, that the
  effect's rule is `deny`) makes no such distinction and is not excluded by
  this argument.
- **B. Print the dev trace where the refusal is printed.** `run` (forwarded
  to a live dev, or against the local store with the collector opted in)
  prints the recorded clause and its sites under the refusal:
  `refused by orders: update <- deny (schema.q:13:3), at fix:2 — mutation
  writes pass the table's rules; jobs run as the system`. The dev server's
  console does the same. Production refusals are unchanged.
- **C. A static `check` note for unreachable writes.** `N_WRITE_DENIED`,
  defined over the bound write sites of mutations, one per **effect**: an
  insert, update or delete, and for an `upsert` each arm separately (it
  consults both the insert and the update rule, `bind/residency.rs:132`,
  `:200`). The note fires when that effect's rule is `deny`. After binding,
  an omitted rule and `update <- deny` are both `RuleExpr::Deny`
  (`bind/schema.rs:200`), so the note reads the source: it quotes the clause
  and its site when the rule is written, and names the table site with "no
  `update` rule" when it is omitted. A rule that is `Deny` only because its
  bind failed (`:197`) gets no note; that error is already reported. Jobs
  and maintains are out (the system principal passes every rule). There is
  no action exemption: actions have no Quarry write body
  (`bind/actions.rs:48`), their TypeScript handlers call mutations, and a
  service seat is an ordinary principal that cannot pass `deny`. Wording
  names the effect, not the operation: "orders has `update <- deny`
  (schema.q:9); the update at schema.q:21 in `submit` cannot pass it for any
  caller but the system". For an upsert: "… the update arm of the upsert at
  … cannot pass it; the insert arm can". Decided from the schema alone, so
  it discloses nothing. Rules that are not literally `deny` but can never
  admit a non-system caller (for example `.owner = 'system'`) are out of the
  first version.
- **D. A guide sentence.** In `guide writes` and `guide rules`: "A mutation's
  writes pass the table's insert, update and delete rules as the caller;
  only a job runs as the system."

### Recommendation

**B, C and D together; not A as written.** Confidence: high. B reuses a
collector the lead already designed and opted dev into; C is the static
form of the most common case in the farm (`update <- deny`, or an upsert
with no update rule); D is one sentence.

### What it touches

B: the CLI and dev console (periphery), reading the existing collector; if
`run` against a non-dev local store should also collect, that is a
one-line opt-in in the host (periphery). C: a note in the binder
(`snapback4-lang`), which decision 4 does not name as core, but the tickets
assign binder changes to the lead; see §8. D: guide text (periphery). No
change to `Refusal` or the engine.

### What Snapback does today

Reproduced on `34852dba1f` with the ticket's schema
(`issues/20261008-snapback4-reserved-system-principal-compiles-then-parks.md`):

The refusal is at runtime only (`snapback4-core/src/engine/validate.rs:66-67`
and `:199-200`, `contains_system_principal`, `schema.rs:1436-1444`). The

(`E_JOB_VIEWER_PRINCIPAL`, `bind/program/job_reads.rs:18-19`). Since

exists (`git grep E_SYSTEM_PRINCIPAL` finds only the ticket).

### Options

- **A. Refuse in the binder.** At a write of any column whose value
  `contains_system_principal` would walk (a `principal`, a `principal?`,
  and principals inside list or object values), refuse (a) a literal
  `'system'` in any operation and (b) a job's `viewer` (a job's viewer is

  `E_SYSTEM_PRINCIPAL_WRITE: activity.actor cannot store the reserved

  guide already gives (`actor: principal?` and `null`, or
  `'service:reminders'`). Values that flow through locals or arguments

- **B. A note instead of an error.** Keeps the program admitted. There is no
  reason to: the write can never succeed.
- **C. A `check` pass over the bound IR.** Duplicates binder knowledge
  without source sites and is not reached by the language's own tests.

### Recommendation

**A.** Confidence: high. Add the code to `guide::CODES` and to `guide jobs`
beside the existing paragraph; fix the doubled `E_INPUT:` prefix in the
stored run error in the same change (`RuntimeError::Input` displays as
`E_INPUT: …`, `error.rs:98`, and `refusal()` copies that string into
`message`, `error.rs:255`). Note that A does narrow the admitted programs:
a never-invoked job containing the write now fails `check`. What it
preserves is every runtime outcome: the write could never succeed.

### What it touches

The binder (`snapback4-lang`) and the code list. No engine change: the
runtime refusal stays as the backstop. Ownership as in §3.

## 5. The device says "ask the server" in so many words

### What the farm saw

In v3 (Exact2's client before its fallback), online-only reads answered
empty in 5 Muse builds (memory-quilt-0800 4 min, seed-lineage-swap-0927 6,
book-spine-duel-0388 8, token-ticket-pool-0098 8, weed-front-0518 3) and a
view in one more (charger-share-meter-0953). In v4, after Exact2 routed
`online only` reads to the server, 8 builds (5 GPT / 3 Muse, about 18
minutes, all major or design-cost) still showed zeros, a permanent
`loading`, or speculative presence for aggregates, counts and presence over
synced tables: annotation-throughput-board-0878 (Muse, 8 min, four `count()`
reads all zero), editor-capacity-0761, receipt-router-0200,
senior-fall-detector-0664 (GPT, presence shown as connected),
api-latency-tracker-0852, paint-by-vote-0352, quote-bank-0762,
science-fair-judging-0203; 7 more GPT design-cost rows after the snapshot.
"Most needed fix" lines asking for a server fallback or a loud refusal: 12
in v3, 11 in v4 (hand count, strict).

> "a wrong number with no error is worse than a refusal."
> (annotation-throughput-board-0878)

> "the client never asks the server for reads of `online only` tables —
> answers come back `speculative:true, unknown:true, data:[]` with no error"
> (seed-lineage-swap-0927)

In v5, on Exact2 `f9cb33270` with the fallback from `8bc0a8f74`, no build
reported zeros or a permanent `loading`; the remaining rows are disclosed
partial coverage (shelf-locator-0154, cistern-refill-signal-0996,
scrap-scale-0582). The client-side fix worked. This section asks whether
the next host should have to rediscover it.

### What Snapback does today

Reproduced on `34852dba1f` with the ticket's schema (an `online only`
`swaps` table and an `online only` view `lotCount`), one row of each seeded
through `snapback4 dev`, the `/schema` reply as the backend, and a fresh
device store:

```
POST /q/mySwaps           → "data":[{"id":"01M4D5AESC…0002","note":"n","owner":"dev:alice"}]
POST /q/total {"k":"a"}   → "data":1
device query mySwaps      → {"ok":{"complete":false,"data":[],…,"retained":false,"speculative":true,"tables":["swaps"],"unknown":true,"watermark":0}}
device query total        → {"ok":{"complete":false,"data":0,…,"retained":false,"speculative":true,"tables":["lotCount"],"unknown":true,"watermark":0}}
```

The reply is built in `crates/snapback4-device/src/call.rs:135-183`. `data`
is whatever the program computed over the rows the device holds; it is
omitted only when the outcome is `unavailable` (a meter cap, an unheld
Following card), which sends `loading: true` instead (`call.rs:149-150`).
`unknown` "names server-only knowledge (missing facts or presence), not every
incomplete answer" (`call.rs:138`; set from `missing_fact.is_some() ||
presence_unknown`, `engine/local.rs:89`). `speculative` is present only when
true (`call.rs:180-181`, kept for the published 0.2.33 wire).

The first-party client's rule is one line: `const wantsServer = (coverage) =>
!!coverage.unknown && !coverage.retained;` (`packages/snapback4/src/local-query.ts:242`,
`@ref LLP 3000.007#20.22.1`), ordered against the applied watermark (LLP
3000.028 §3.2) and fenced by intersecting predictions; offline it recovers an
unexpired server answer or refuses `E_OFFLINE` (`local-query.ts:155-173`,
`CLIENT-AND-OPERATIONS.md:389-390`). LLP 3000.028 §1 states the invariant
("an unknown Boolean must not become false"); LLP 3000.020 §3.3 makes a
lower-bound count an *unknown, non-speculative* fact the client keeps
offline as `L+`.

None of that is a host contract. The C header
(`crates/snapback4-device/include/snapback4.h:1-18`) documents the envelope
and the `query` request, not one reply field. The Expo module is a
pass-through to the JS client (`packages/snapback4-expo/ios/Snapback4Module.swift:46`).
`guide residency` explains server-run sites and `check --residency`, not the
per-call bit. Exact2's client (commit `8bc0a8f74`, 2026-10-08 01:59) read
the protocol from behaviour and implemented a coarser rule: fall back when
`loading` or `speculative` is set and *nothing at all* is queued; it never
reads `unknown`, so a non-speculative unknown answer (the LLP 3000.020 lower
bound, a `read through` child page with `data: []`) is rendered as data, and
any queued write leaves a speculative `0` on screen.

### Options

- **A. Document the current bits.** Write the reply schema and the
  first-party client's procedure as a host contract in
  `CLIENT-AND-OPERATIONS.md` and the C header. No wire change. Every host
  still derives the action from several booleans, and the placeholder `data`
  still renders in a host that does not.
- **B. Add a routing field beside the bits, computed from device facts
  only.** The device knows whether this evaluation's coverage is unknown
  and whether it is retained; it does not know the host's prediction fence
  (admissions in flight, `pendingTables`, a queue entry with no predicted
  payload, the cold snapshot; `local-reads.ts:193-196`, `:279-287`,
  `local-query.ts:143-151`) and cannot, because a write can begin while the
  server read is in flight. So the field describes routing at the moment of
  observation, and the host keeps every fence it has today:
  - `"answer": "device"` when `!unknown || retained`. Render it; `complete:
    false` means more may exist and **not** "ask" (a meter cut, a horizon, a
    word cut).
  - `"answer": "server"` when `unknown && !retained`. Online, ask `POST
    /q/<op>` with the same arguments, subject to the host's fences before
    dispatch and again before publication. If `data` is present it is a
    usable partial (the LLP 3000.020 lower bound `L`, known non-speculative
    rows): show it as partial and ask. Offline, show `data` as partial when
    present, else a remembered server answer, else unavailable.
  - **`data` is omitted only when it is an unusable placeholder:** every
    site the reply read is server-only (an `online only` table or view,
    `connected[p]`), the reply is not retained, and no component is a
    certified partial. Placeholders of that kind are speculative today
    (`read.rs:422`, `:879`); unknown non-speculative values (`unknown_fact`,
    `local.rs:252-258`; read-through child coverage, `through_read.rs:64-66`)
    keep their `data`. Mixed rows are described per component through the
    existing `components` field, not by the one top-level value.
  - The first-party client's recovery must change in the same release: its
    remembered-answer path (`local-query.ts:122-123`) recognises a
    server-only read by a present, speculative placeholder, and a reply
    without `data` would become `loading` instead (`:193`). The change is
    gated on the backend generation the reply already carries, so a
    published client meeting a newer device keeps working.
- **C. The device refuses instead of answering.** Server-only reads return
  `{"denied": {"code": "E_SERVER_READ", …}}`. Simplest for a naive host, but
  it loses the partial-but-known answers (`L+`, retained history) that LLP
  3000.020 and 3000.028 §3.2 deliberately keep, and it turns an ordinary
  online read into an exception path.

Whatever is chosen, the documented host contract must cover more than
routing: `held` queries (never fall back), known cuts, authoritative versus
speculative refusals, component and row retention with the watermark order
of LLP 3000.028 §3.2 (`local-query.ts:271-296`), expiry deadlines
(`nextExpiry`, `decorationExpiry`), identity and generation changes, and
when a remembered server answer is invalidated.

### Recommendation

**B, with A's documentation as the contract text.** Confidence: high that
the contract must be written down and that a host must be told "ask the
server" without inferring it from placeholders (the one non-first-party
host so far rendered them for a day of builds; the first-party procedure
exists to be copied); medium on the field and the omission predicate, which
the lead should settle against `local-query.ts` before the wire changes.
The server-against-device oracle (`snapback4-difftest run-devices`, LLP
3000.035 §5.1 oracle 4) already counts these reads under `online-only-*`
reasons and can assert the field. The contract lives in
`CLIENT-AND-OPERATIONS.md` under a "Device reply" heading, with the C header
pointing at it.

### What it touches

**Core** (lead): the device reply (`snapback4-device/src/call.rs`), the
client contract (`local-query.ts`'s recovery and routing,
`contract.ts` if a type is exported), and the normative host contract
text, whose semantics are the lead's even if a lane writes it up. Exact2's
client is its owner's: it would switch `read()` to the field and keep its
own fence, today coarser ("anything queued").

## 6. Idle live clients must not cost a thread

### What the farm saw

No build in 652 receives pushed changes. A Contract timer drives freshness
in nearly every client-arm app (v4: 92 of 93 GPT, 69 of 82 Muse; v5: 63 of
63 and 76 of 76; median 5 s). Two v1 apps used `/changes` as a bounded short
poll. Builders declined the long poll up front, because a held answer stalls
Exact's test settlement:

> "A long-held poll would make clock-data test settlement wait, so periodic
> sync fits this slice." (quiet-tent-capacity-0966)

> "`poll()` is unused: Exact sources cannot hold timers, and a 20 s long-poll
> inside a resource would stall answers the test driver waits on"
> (studio-door-0755)

The farm did not hit the capacity limit: its apps never held streams, and a
farm build has one or two viewers. The demand is Exact2 LLP 1110 D1
(Draft; direction approved by Charlie on 2026-10-08: SSE, with the Snapback
endpoint designed by its lead session) and the ticket
`issues/20261008-snapback4-changes-event-stream.md`. LLP 1110 asks for "a
stated bound on open streams per principal and per host, with a refusal the
client can show", and says a stream that pins a worker while idle "would
exhaust them at 32 viewers".

### What Snapback does today

The HTTP host is vendored `tiny_http` 0.12.0 with local patches
(`vendor/tiny_http/SNAPBACK-PATCH.md`): one OS thread per connection
(`vendor/tiny_http/src/lib.rs:415`), at most 128 connections
(`limits.rs:100-105`), and a worker pool per request class with an atomic
permit (`crates/snapback4/src/serve.rs:436-446`, 480-484): 32 short, 32
mutation, 32 sync, **32 wait**, 16 route, 4 registry, 4 verifier. The wait
pool is shared by `GET /changes` and by service workers' claim polls
(`POST /effects/claim`, `/actions/claim`, `/a/*`; `is_waiter`, serve.rs:536-539).
LLP 3000's "Contended read serving" record (explainer:1761-1775) keeps
`RequestAdmission` as the only admission budget.

A held `/changes?wait` (capped at 25 s, `serve_changes.rs:13`) parks its
worker on a condvar (`serve_changes.rs:85`), with optional chunked
whitespace heartbeats every 2 s (:8, :75-79), and enters presence for its
duration (:35, :89; `connected[p]` counts held polls with a 35 s grace,
`engine/mod.rs:121-126`). An idle live client therefore costs about two OS
threads (its connection and its wait worker), one of 32 wait permits and one
of 128 connections. There is no per-principal bound. Exhaustion answers
`503` with `E_RATE_LIMIT`, `retryable`, `Retry-After: 1` and a `guide` that
names `assets` (`limits.rs:43-45`). A commit wakes every parked waiter
(`serve_ephemeral.rs:78-95`: `polls.notify_all()`), and each rechecks its own
cursor with a read transaction (`serve_changes.rs` `check`). There is no
event-stream code. No LLP chose the threading model; NOT-DOING says "no
broadcast event stream" (NOT-DOING.md:38), which a per-viewer cursor stream
is not, and nothing about async.

So the 33rd simultaneously held wait on one server is refused, and 32 held
live clients stop service workers from claiming effects. Each held poll
also keeps a detached reader engine (`serve_changes.rs:30-37`).

### Options

Costs are estimates from reading the code, not measurements.

- **A. Raise and split the pools.** Make `WAIT_WORKERS` and the connection
  cap configurable, give claim polls their own pool, add a per-principal
  bound on held waits, and refuse an exhausted bound with its own code
  (`E_STREAMS`, family `limit`, naming the bound and the principal's share)
  instead of the assets-guided `E_RATE_LIMIT`. Days of work, no new
  architecture. Each held wait still costs two threads, a detached reader
  engine, and a share of the `notify_all` herd (every commit wakes every
  waiter and each runs `check`'s read transaction). A mitigation, not a
  thread-free stream.
- **B. Evented parking of idle waits inside a patched `tiny_http`.** A parked
  `/changes` request hands its socket to a parking thread, woken from
  `publish_durable`. Acceptable only with all of:
  non-blocking writes with per-socket backpressure and a write timeout (one
  slow reader must not stall the rest; today's `write_response_frame` blocks
  and flushes, `vendor/tiny_http/src/request.rs:569`); the connection lease
  kept with the socket so the 128 cap still counts live streams
  (`limits.rs:88-105`, `SNAPBACK-PATCH.md:44-56`); parser ownership
  transferred without racing a pipelined request; no detached reader engine
  held while idle; and the stream contract below. One to two weeks is a
  guess until the detach patch exists.
- **C. A second listener for this route.** `hyper`/`tokio` on a loopback
  listener behind the same TLS proxy (one TLS contract), sharing the
  `RequestAdmission` state. Clean concurrency at the cost of a second HTTP
  stack and a dependency on a budgeted binary. It needs the same stream
  contract.
- **D. Move the whole host to async.** Rewrites about 5.2k lines of serving
  code and the admission model the overload diagnostics rest on. Not
  justified by this evidence.

**The stream contract any of B or C must meet** (this is what an SSE
`/changes` is, separate from how it is parked):

- **Wake hint or full contract.** Either each event carries only the new
  head cursor and the client fetches the existing `GET /changes?since`
  answer, or the event carries that answer: the interval since the client's
  cursor (not only the latest commit's tables; a client that missed commit
  8 changing X must not advance past it on commit 9 changing Y), the
  saturation rule that invalidates every table, store identity and
  generation resets, preserved revocations and settlement changes
  (`serve_changes.rs:112-130`), and ephemeral epochs and incarnations. The
  wake hint is the smaller contract and reuses everything that exists.
- **Interest by partition, not by table.** "The tables that changed" is
  global; a viewer's interest is their partitions, which the log already
  names.
- **Credentials.** Re-check the bearer before each event and at least as
  often as today's 25-second cap allows, and end the stream with a terminal
  authentication event when a session expires or is revoked.
- **Presence.** A held poll enters presence for a full session and leaves
  when the request returns (`serve_changes.rs:22`, `:35`, `:89`); the 35 s
  grace assumes polls end. A stream must leave on write failure, read-side
  close and idle timeout, keep Full-versus-Reader eligibility, and keep the
  five-second presence refresh (`engine/mod.rs:121-126`) or an equivalent
  invalidation, or presence displays go stale.
- **Proxies.** State the proxy configuration (idle timeout above the
  heartbeat, buffering off); today's 25-second cap is what makes a held
  poll survivable behind a buffering proxy.
- **Bounds.** Per principal and per host, with `E_STREAMS`.

### Recommendation

**A now, as the decision; then measure B against C before building
either.** Confidence: high that idle streams must not each hold a worker
before SSE ships (LLP 1110's own requirement) and that A is a sound bounded
mitigation; low on choosing between B and C before the detach patch is
sketched. The measurement: 10,000 idle streams, one commit per second, a
reconnect burst, a stalled client, credential expiry and ephemeral-only
changes, on the M5 host, reporting RSS, descriptors, commit latency and
wake-to-event latency.

### What it touches

Pool sizes, the claim-poll pool and `E_STREAMS` are **periphery** (the HTTP
host is not the engine, the store or the client contract). Presence
lifetime is **core**: `connected[p]` is engine state that rules read
(`engine/mod.rs:128-136`). The SSE event schema is a client-contract
addition and is **core**. B's `tiny_http` patch is periphery under the
author's earlier approval of minimal vendored fixes, reviewed by the lead
because it changes admission.

### Implemented: option A (2026-10-08, lane S3)

All four "now" items of A landed; B, C and SSE did not.

- **Configurable pool.** `dev` and `serve` take `--long-waits N`
  (`SNAPBACK4_LONG_WAITS`); the connection cap is derived as 128 plus the
  long-wait pools, and startup prints the sizes, the cap and the descriptor
  need. The default rose from 32 to **1,024** on measurement; the upper bound
  is 4,096 (two threads per wait against Darwin's 16,384 per process), and
  explicit sizes the raised NOFILE limit cannot carry (four descriptors per
  connection plus 512) refuse startup with `E_HTTP_LIMIT`; a default that does
  not fit is lowered and says so.
- **Per-principal share.** `--long-waits-per-principal` (default 16) bounds a
  principal's held change polls; the share is taken inside the wait permit
  after authentication and refused at once with 429 `E_STREAMS`
  (`Retry-After: 5`). `/a/<action>` waits stay in the viewer pool but are not
  counted against the share.
- **Separate claim pool.** `/effects/claim` and `/actions/claim` have their
  own class (`--claim-waits`, default 32).
- **`E_STREAMS`.** A full pool answers the dispatcher's nonblocking 503 with
  `E_STREAMS` (family `limit`, retryable, `Retry-After: 2`, `guide wire`)
  through a new vendored `refuse_overload_with`. `guide::CODES`, the wire
  card, CLIENT-AND-OPERATIONS.md and SERVER.md say how to treat it, and the
  published client's change feed degrades to unheld polls at the Retry-After
  pace for 30 s instead of going offline.

Raising the default exposed two quadratic herds that the estimates above did
not name, and both were fixed in the same landing: the engine's FIFO lock
woke every queued request on each release (now each ticket parks on its own
condvar), and every held poll reopened a reader under the engine lock on each
commit (now a parked poll holds no reader, and polls woken by the same
publication at the same cursor share one answer read on a pooled reader; a
new poll still reads the store). Measured on the M5 host with
`scripts/measure-long-waits.py` (SERVER.md, "Long-wait capacity"): each held
poll costs about 85 KiB RSS, two threads and four descriptors; at 4,096 held
polls the server is 339 MiB and 8,201 threads, an ordinary `/q` stays at
0.6 ms p50, one commit answers all 4,096 in 0.33 s (persona) or 1.5 s
(bearer, which rechecks each session), and all re-poll in 0.4–0.8 s. A thread per wait therefore reaches low thousands cheaply on one
host; **tens of thousands of idle streams remain the evented-parking step
(B measured against C above)**, which this landing does not change.

## 7. Release velocity

### What happened

- 0.4.15 was cut at `4e5ec141be` (2026-10-07 09:07 PDT) and published at
  23:53 PDT, **14.8 hours later**: a 1,948 s Linux suite, a first Darwin dry

  `cd2fa88d8b` (`run` forwards to a live dev; `/seed` says what is wrong)
  and `28fa5fb0bf` (`guide wire`) at 00:09 PDT, `ab74765288` at 00:15.
  Round 2 measured the first of these at 34 of 76 v4 builds (50 minutes).
- 0.4.16 was cut at `d15ecba68f` (00:16, from main `6b588f4bce`). Its Linux
  qualification failed 24 tests in seven client files after 3,112 s.
  Several of the failures match lane SN's one-shot settlement change, whose
  landing ran an affected subset that did not include those files;
  attribution of the rest is in progress
  (`issues/20261008-snapback4-main-client-regressions-in-0416-qualification.md`).
  It is unpublished; the periphery fixes wait behind a core regression they
  do not touch.
- Publishing is not the last hop. Exact2's client pinned `snapback4`
  0.4.13, so the farm ran 0.4.13 from v3 through v6 (`~/appfarm/CONDITIONS.log`,
  04:15: "snapback4 npm 0.4.13 (0.4.16 publication stalled after a failed
  Linux qualification …)"), two releases behind npm. Builds with an
  `E_STORE_BUSY` row while the fix waited: 57 of 82 Muse v4 builds and 44 of
  76 Muse v5 builds.
- Every package carries one version (`snapback4/AGENTS.md`, "Bump `version`
  … together; a test refuses a mismatch"); the client pins the binaries
  exactly; the guide, CLI and diagnostics are compiled into the binary. A
  guide sentence therefore needs a full two-platform qualification of
  whatever core is on `main` at the cut.

### Options

- **A. Patch releases from the last published tag.** When `main` is red for
  a reason a fix does not touch, cut `0.4.N+1` from the published commit
  plus dependency-complete cherry-picks of periphery commits, and qualify it
  with the same full Linux suite and Darwin proof. Qualification is not
  weakened: `publish.mjs` and `qualify-linux.mjs` bind source and artifact
  integrity, not `main`. Cost: a release branch per patch and a rule for
  what may be cherry-picked (periphery by decision 4's list, with no
  dependency on unreleased core).
- **B. Qualify client and device changes more completely, off the landing
  path.** The 0.4.16 failure came from an affected subset. A mandatory
  25–55-minute landing gate would conflict with `rules/RULES.md` ("Nothing
  blocks on anything slower than 60 seconds"), which Snapback 4 adopts.
  Inside that rule: run the complete client suite on a schedule frequent
  enough that a red main is known before the next cut, and before cutting.
  A landing gate would need the author's ruling.
- **C. Shorten the Darwin dry run.** At 8,000–11,400 s it is the long pole;
  the Linux suite takes 1,948–3,112 s. Warming the artifacts first (already
  in AGENTS.md) and finding what the Darwin proof repeats beyond the suite
  would help. Needs measurement first.
- **D. Split the guide out of the binary.** Ruled out here: the guide is
  tested text compiled with the language (`crates/snapback4-lang/tests/guide.rs`),
  and splitting it would add a version skew the single-version rule exists
  to prevent.

### Recommendation

**A; B as a scheduled run, not a landing gate; measure C.** Confidence:
medium-high. A needs no change to what qualification proves, only to what
is cut. Neither reaches a builder until the consuming client's pin moves
too, so a patch release should name its downstream pins (Exact2's
`snapback4` dependency) in the publication record. This is the lead
session's and the publisher's to adopt; it touches `scripts/publish.mjs`
only if the cut tooling must record the base tag.

## 11. Wave 1 rule-language friction (workstream B, 2026-10-11)

The 100-lane farm on `snapback4@0.4.16` (`~/sb4-loop/wave1/analysis/patterns.md`)
repeated several §1–§4 themes and added new ones. Workstream B landed these
changes in `snapback4-lang` and `snapback4-core`. Each one either names the
construct the author used or renders its repair from the author's own tables
and columns. The patterns are numbered as in the analysis.

**Decided (implemented):**

- **Ordered comparisons in insert rules (#15).** An insert rule may order the
  new row's own required `int`/`time` columns and integer literals, such as
  `.stars >= 1 and .stars <= 5` or `.endsAt > .startsAt`. This form judges one
  image and reads no clock, no hop and no null, so the device evaluates it as
  the server does. The core accepts `Compare` in an insert rule only for those
  terms. A schema that uses it requires the capability `insert-rule-order`, so
  an older decoder refuses it rather than misjudging it. The Lean emitter
  already names ordered rule comparisons as outside its fragment.

  Read rules stay `=`/`!=`: they are audiences (sync inversion and per-page
  uniformity) and must not change with time. Delete rules and unnamed update
  rules are unchanged. Every other use is refused with `E_QUARRY_RULE_OPERATOR`
  (the clock, arithmetic, helper calls and misplaced ordered comparisons). Its
  rewrite moves the author's comparison into the mutation as
  `require … else INVALID_<FIELD>`, or for an update into a named
  `update (old, next)` bound. `guide rules` opens with a table of what a rule
  may say.
- **`require … else CODE 'message'` (#21).** `require` and `x ! else CODE`
  accept the optional message `unique` already took. IR `Stmt::Require` gains
  an optional `message`, skipped when absent, so existing bytes are unchanged.
  The refusal's wire `message` carries it; the code remains the contract. An
  older engine ignores the field and returns the default text. A table rule's
  `else CODE` names E_RULE and moves the name into a mutation `require`.
- **Reserved words (#40).** `E_QUARRY_RESERVED` is reported at the declaration.
  A table-line keyword cannot name a column (`snapback4 why E_QUARRY_RESERVED` lists them; the language card is held at its tested word budget, so the list lives on the why page every such diagnostic shows),
  and a statement or expression keyword cannot name a parameter, local or loop
  variable. Table, function and view names are unaffected.
- **Row as key (#27).** `t[row]`, where `row` is a present row of `t`, reads as
  `t[row.id]`, as `update t[row]` already did. A probe key written as
  `.id = .ref` gets the positional rewrite `t[.ref, col = viewer]`. Named
  equalities that cover two total unique keys test the same row through either
  key, so the first declared key is chosen instead of `E_QUARRY_AMBIGUOUS`.
- **Pages in objects (#29).** In an order-key list, a comma followed by
  `name:` ends the page, so `{ notes: t where … by .at, votes: v }` parses. An
  undotted key (`by .at, id`) names the missing dot.
- **Read-rule hops (#33).** The `E_QUARRY_RULE_HOP` rewrite for a read rule is
  now a table-rule repair: copy the immutable deciding value onto the row,
  check it in the insert rule, and probe one hop, or use `read through`. It
  previously printed mutation syntax. Two-hop read probes are not added; they
  would change sync inversion.
- **Pins as code (#6, #19).** `N_NEVER_COMPLETE` prints the equality to add,
  the parent read that supplies it (`parent = cards[card] ! else NOT_FOUND`,
  `.board = parent.board`), or one query per party for a two-party rule. The
  constraint form of `E_STRUCTURAL_FANOUT` renders its count-view and
  unique-unit repairs against the author's table and pins. `guide indexes` gains
  "Private lists". Further rewrites are rendered from the author's own line:
  the sync window without dots, sum clause order, `1w`, `not a = b`, the
  nested-predicate `.` scope (#44), and a lookup ambiguity.
- **`N_READ_DENIED` (lane 008).** A query or mutation that looks up an
  aggregate by key whose read rule is `deny` gets a note; such a lookup used
  to read as a silent 0. Pages of denied sources stay empty, visibly, and
  the guide uses them on purpose.
- **Job sweep (lane 081).** The sweep's carried-local check ignores
  compiler-internal facts (`$pureCallConstants`). A schedule naming a job that
  failed to bind is a hidden cascade.

**Deferred: a role guard as a completeness proof (#28).** Pages such as
"staff see all" (`.owner = viewer or exists staff[viewer]`) stay
`complete: false` for staff. A sound proof exists: a row-independent disjunct
that is true for this viewer in this snapshot makes the rule uniformly true.
It would change the engine's page verdict on the server and both device
stores, the static probe charge (LLP 3000.007 §18.1), and the `complete` field
the Lean oracle compares (LLP 3000.035 §5.2). It therefore needs the lead
session and a Lean-model change, and is not a binder-side edit. Until then,
`N_NEVER_COMPLETE` names the unused grant, and `guide indexes` says what staff
receive. *(Superseded by §12.1: implemented on the server, for readable
grants only, with the Lean fragment narrowed by name.)*

The second 100-lane farm built on `snapback4@0.4.17`
(`~/sb4-loop/wave2/analysis/patterns.md`, 541 friction entries). This
workstream took the rule-language patterns. Numbers below are the analysis's
pattern numbers; lane counts are distinct lanes with an entry. Every changed

### 12.1 A readable grant decides a page for its holder (#3, 17 lanes)

**Rule.** A read rule `A or G`, where the disjunct `G` reads no column of the
row (`exists staff[viewer]`, `exists staff[principal = viewer, role =
'manager']`, `viewer = 'service:audit'`), is true for every row whenever `G`
holds for the caller. `rules::grant_decision` returns such disjuncts; the
server's page walk (`read.rs`, `scan_consumed`) evaluates them once, before
the walk, when the prefix does not decide the rule. If one holds, the page is
admitted exactly as an always-readable page is: one verdict, ordinary
lookahead, `complete` when the walk ends, the grant row's expiry carried as
the page's. If none holds, the walk is the per-row walk it was. A staff
console's list is therefore `complete: true` for staff and unchanged for
everyone else.

**Disclosure.** `complete` must not reveal a row the caller cannot read. A
grant is used only when the caller could read every fact it reads
(`self_disclosing`): literal and viewer comparisons, and probes whose target
row's own read rule is decided true by the probe's pins (`.principal =
viewer`, `public`, a self-probe on a total unique key) or carries a probe the
grant implies (`read <- exists staff[viewer]` for `exists staff[viewer]`, or
`exists employees[principal = viewer]` for the same probe plus `role =
'manager'`). A negated probe, a hidden roster (`read <- deny`), an expiring or
read-through target, and every disjunct that reads a row column are not
grants. With that condition the grant's verdict is a function of the caller's
visible rows, so the Lean model's noninterference statement
(`query_noninterference`) stays true of the new behaviour. The test
`a_grant_the_caller_cannot_read_is_not_used` pins the hidden-roster case.

**Meters.** The check charges the read rule's static probe count once, on
either verdict, and records no filtered clause; a false grant then pays the
existing private-page reservation as before. The charge depends only on the
program, so it reveals nothing about the verdict.

**Where it applies.** Ordinary scans on the server, for non-system callers.
Word (search) scans, read-through children and maintained-view parents keep
the per-row walk, and a table with private `written by` fields still refuses
an undecided scan with `E_FIELD_AUTHORITY`; `complete: false` is always the
sound fallback. Point reads are a separate path and unchanged. The device never takes the path: a synced table's rule names
one audience (`E_SYNC` refuses a union), so the device either trusts its held
partition or answers online-only, and both device stores are unchanged.

**Require dominance.** `rules::grant_dominated` holds when a top-level
`require` of the grant's probe precedes the statement holding the scan and the
program writes nothing to the grant's table (so the fact cannot change between
the guard and the walk). Then every caller who reaches the page holds the
grant: `N_NEVER_COMPLETE` is not printed for it, and mutation admission
(`admission.rs`, `decided`) treats the page as decided, which admits a
staff-only pass such as `require exists staff[viewer] … for row in pieces
where .firing = firing`. At run time the same grant check admits the walk. A
guard after the loop, or a program that can delete its own grant row, keeps
`E_STRUCTURAL_FANOUT`, whose rewrite now names the guard to add and says that
`: server` does not lift it.

**Notes and docs.** `N_NEVER_COMPLETE` says "never complete except for
callers `G` admits" and tells the author to run the case as staff in
`test.cases.jsonl` (expect `capped` for the others), or explains why an
unreadable grant is not used. `guide indexes`, `why N_NEVER_COMPLETE` and a
new "staff console, online" recipe in `guide sharing` state the rule.

**Lean.** The model's `uniform` has no per-caller arm. The emitter names a
read rule with a row-independent disjunct under a top-level `or` as
unsupported (`read-grant`), so `run-lean` never compares such a program;
the difftest generator emits no such rule (its rules are `Allow`, `Deny`,
`Owner`, `Witness`, `OwnerOrWitness`), so neither the device nor the Lean
campaign's coverage changes. Extending the model is a follow-up: add
`granted vw v t := (td.read.disjuncts).any (selfCols = [] ∧ eval over vw)` to
`pageRead`'s `markIf`; evaluating over the view keeps the noninterference
proof, and the self-disclosing condition makes it equal to the engine's
store evaluation. It was not written here because `lake` is not installed on
this host and the model must build before it lands.

### 12.2 Owner-or-X lists (#12, 12 lanes)

Not implemented as an engine union. A page over `.owner = viewer or .assignee
= viewer` would be two lanes over two indexes (`owner, at, id` and
`assignee, at, id`), merged by order with a row matching both emitted once.
Merges today share one index (`rules::lazy_merge`), and their positions,
continuation and device coverage assume it; a two-index merge with
de-duplication is a new cursor kind and a new device-coverage case, which
this lane did not take on. Instead `N_NEVER_COMPLETE` for a two-party rule
prints the author's own query once per party, ready to paste
(`mineAsOwner`, `mineAsAssignee`: the `or` of the parties dropped from
`where`, `.party = viewer` added, every other clause as written), and says
that an `or` of the pins in `where` is still one scan (lane 049). A test
pastes the printed declarations and requires them to compile complete.

### 12.3 References and rows in programs (#10, 13 lanes)

- **A required reference's field reads its row.** `x.ref.col` in a program,
  helper or shape binds as `t[x.ref].col`: the same authorized point read,
  null when the row is missing or hidden, bound once into a temporary. It is
  sugar for a form that already compiled, so the IR, the meters and the
  device behaviour are those of the explicit read. This reverses the "no form

### 12.4 Money and decimal in insert rules (R8, 4 lanes)

`insert-rule-order` covered `int`/`time`; `money` and `decimal` are integer
minor units on the wire and in programs, so an insert rule now orders them
too, against an integer literal in minor units or a column of the same type.
A schema that does so requires the new capability `insert-rule-order-units`,
so a 0.4.17 decoder refuses it by name. The core now also requires two
ordered columns to share one type. The refusal for a remaining mismatch no
longer suggests "a column with an integer literal" to an author who wrote
exactly that; `assert_not_identical` guards every rewrite the new tests reach
against repeating the source line.

### 12.5 Read-hop rewrites that compile (R9, 2 lanes)

The §11 rewrite copied the next reference and suggested `.ref.col = viewer`,
itself a refused hop. The rewrite now goes straight to a compiling form: on
an online-only table or a view, probe the row that decides
(`exists ministries[.ministry, coordinator = viewer]`), copying the last
reference first when the chain is longer than one hop; on a synced table
compared with `viewer`, copy the deciding principal (a column audience). A
view is told to group by the reference column instead of declaring one. When
a link the copy relies on is mutable, the rewrite says so. A test applies
each printed rewrite mechanically and compiles it.

### 13.1 `check` follows the guard the runtime honours (#3a, 12 lanes)

0.4.18 made a staff page `complete` for staff at run time (§12.1), but
`N_NEVER_COMPLETE` only recognised a top-level `require` of the grant. The
lanes guarded the staff page the other ways a program can: `if exists
staff[viewer]:` around it (027 035 054 062 068 093), or an early `if not
exists staff[viewer]: return []` before it (061 095), or `if viewer !=
'dev:board': return …` (077). Their runs answered `complete` and `check`
said "never complete"; check and runtime disagreed.

**Rule.** `rules::grant_dominated` now walks the program's control flow. A
scan is dominated when, on every path that reaches it, a condition that
implies one of the scan's grants has held: a preceding `require`, an
enclosing `if` (the `then` of `G`, the `else` of `not G`), or an earlier
`if` one of whose branches always leaves the block (`return`, `break`,
`continue`) and whose other branch is guarded. A condition implies a grant
through its conjuncts (and `not` of a disjunction): an `exists` probe with
the grant's key, the point read and field comparisons the compiler lowers
a named-equality probe to (`$probe != null and $probe.role = 'manager'`),
`viewer = '…'` (and `viewer != '…'` on the exit branch), and the
compiler's short-circuit temporaries (`$bool1 = a; if $bool1: $bool1 = b`).
Every structural copy of the scan must be dominated, and the program must
write nothing to a grant's table. This is the same per-caller verdict the
server's walk takes (`read.rs`), so the note and the run now agree; the
mutation admission that shares the function (`admission.rs`, `decided`)
admits an `if`-guarded staff pass for the same reason. No runtime path
changed.

**Not followed.** An `or` proves neither disjunct; a guard whose exit is
itself conditional keeps the note. Lane 014's `rides where .driver = null`
under `… or (.driver = null and exists people[viewer, role = 'driver'])` is
a different proof: the pinned prefix would make that disjunct
row-independent. The runtime does not take it (grants are disjuncts that
read no column), so the note is accurate there and stays; extending the
grant to prefix-decided disjuncts is a runtime and Lean change, deferred to
the lead session with §12.1's model follow-up.
