## 1. Commission and boundary

Implementer: STAGE, 2026-10-18, commissioned by Charlie's wave-16 bakeoff
fixes #1/#4. Ten Muse probes used dev because password-role provisioning
had no single recipe. This amendment supplies that recipe using the existing
signup and service-seat authority. No system seed door is added to serve.
SEC owns self-promotion lints and security invariants; KIT4 owns unrelated
proof helpers, PROD2 owns production starter adaptation.

`deploy <dir> --staging` classifies a **new deployment store**, under its
exclusive owner, with durable metadata `deployment_environment=staging`.
An existing store with no classification is production, including legacy stores;
it cannot be relabelled. A staging store remains staging through deploy,
rollback, restart, copying and source edits. There is no promote/relabel flag:
production requires a separate fresh deployment without --staging and real
operator provisioning. --check never creates the classification. Repeating
--staging on an already staging store is allowed, including while serve runs;
it verifies the existing classification without changing it. Malicious edits by
the filesystem/database owner are outside the threat model, as for service tokens.
This is a deployment-lifetime boundary stronger than a mutable per-release flag:
production source or a seed plan cannot opt a production store into test setup.

## 2. Real staging accounts

`GET /auth/config` reports `development` independently of door availability,
`devDoors`, and `environment` (`development`, `staging`, or `production`).
Missing/unknown environment metadata is production. serve remains bearer-only
in both environments, with the same password verifiers, session lifetimes,
rules, rate limits, clock and data plane. No password hashing or grant bypass.

`startServe(dir, options)` additionally returns `operatorToken(service =
"operator", days = 1)` and `seedAccounts(options)`. Minting uses the existing
local CLI proof protocol, captures secret stdout in memory and never writes
tokens into proof logs. It confers only that service seat's existing authority.
Tokens may also be requested on production for first-admin setup.

`seedAccounts({roles, provision, args?})` creates N real password accounts per
role, then calls the declared mutation as service:operator; `args(account)`
maps the account to application arguments (default `{principal, role}`).
`provision` is a generated mutation handle or `{name}`, including qualified names such as `accounts.provision`. The returned records
contain email, password, principal, token and expiresAt, grouped by role.
`startServe(dir, {seedUsers: options})` performs the same setup before returning
and exposes those records as `sessions`. Before minting or creating accounts,
the helper requires environment=staging and development=false. Production,
legacy and dev hosts refuse. Inputs are validated before effects; signup is
sequential, bounded, respects identity throttling, and never retries an ambiguous
write. A fresh call creates a fresh random email/password set. Partial failure
does not claim rollback: some accounts/grants may exist; discard the disposable
staging deployment or inspect it before retrying. Application data is created
through ordinary authenticated mutations after provisioning.

Credential records are returned to the operator, never logged by the helper.
The tested guide writes them to an exclusively created 0600 file. They must
not enter source control or reports. There is no public provisioning HTTP
endpoint beyond the application's declared rule-checked mutation.

## 3. First admin

The tested guide uses password signup (which grants no role), then the
filesystem owner's `operatorToken()` to invoke an operator-only mutation.
The roster's insert rule independently requires service:operator. No "first
caller wins", empty-roster bypass, client-selected signup role, or permanent
operator credential in the frontend. The same recipe works on production
with explicit operator-selected email/password; bulk seedAccounts refuses there.
Privileged account tokens cannot mint service tokens. SEC owns lints for
self-bootstrapped global authority; the guide points to this ownership.

## 4. Development doors

For password-only schemas (`auth.password && !auth.guests`), dev disables
`/seed`, every `/dev/*` door (except the existing cryptographically protected
local token protocol), and persona headers by default. The pre-existing serve
GET /dev/latency inspection remains service-authenticated; it never admits an
unauthenticated caller and its reset remains refused. `dev
--unsafe-dev-doors` is explicit opt-in with a prominent warning; serve accepts
no such flag. Host/Origin loopback fences still apply. Door availability is
computed from the current adopted schema, so hot adoption to password-only
also closes them. Seed/reset, clock advance and dev job enqueue revalidate
against the engine schema under the writer immediately before privileged effects;
slow request bodies and requests queued behind adoption cannot retain authority.
Action admission/replay, session-route admission, persona cancellation and upload
owner state transitions likewise revalidate under their actual writer. Previously
admitted durable work retains the existing work-record contract; a refused
new request creates no claimable work.
Persona reads also revalidate against the engine used to evaluate the query,
sync page or asset grant, checking the current declared cast at that read’s
admission. In-flight reads retain their existing snapshot semantics: cast
publication does not lock out concurrent ordinary writes, and the engine
transaction rejects a replaced execution schema.
Change-poll presence entry revalidates under its engine. A detached old
schema is fenced by the engine transaction; a replacement password-only reader
cannot inherit a pre-adoption persona capability. A persona header must name an explicitly declared persona;
an empty declaration admits none. Persona-based schemas retain their ordinary
development workflow. /auth/config always reports development=true on dev,
even with closed doors, so probe tooling can refuse it.

`startDev` follows native persistent storage by default, consuming the old
--no-memory alias; --memory/--fresh explicitly request disposable storage.
The returned now() refuses with guidance if the clock door is closed. Native
readiness plus the per-launch proof marker still establish host identity when
/dev/status is unavailable. Existing fixture/clock tests explicitly opt into
unsafe dev doors when their password schema requires those tools. Generated
frontend proofs explicitly select --memory and --unsafe-dev-doors, preserving
disposable fixture isolation and repeatability under the persistent helper
default. Exact 0.4.30/0.4.31 proof templates are retained and safely adapted
by digest; custom scripts remain untouched. DAY5 owns other starter custody.

## 9. Wave-19 identity retry and local production lifecycle

Commission: Charlie's day-two addendum, wave-19 fixes #6/#7 (2026-10-19).
This amends the SDK/proof and local release contracts; it grants no new auth
or filesystem authority. SEC4 and QRY keep their existing scopes.

Identity `guest`, `signup` and `login` share a portable request helper with
proof `seedAccounts` (including `startServe({seedUsers})`). Only a delivered
HTTP 429 containing a validated auth `E_RATE_LIMIT` refusal, not marked
`retryable:false`, may retry. The server refuses these requests before account
creation/authentication. Wait for nonnegative integer `retryAfterMs`, or a
valid Retry-After header on older servers (otherwise one second). Preserve the
same credentials and scope, without sending retry options on the wire. Up to
four attempts fit inside the whole request deadline (`timeoutMs`, default
180000); an AbortSignal cancels fetch and waiting. A wait that cannot fit
returns the original refusal with its delay; setup instead throws
E_STAGING_TIMEOUT, warning that partial accounts/grants may remain. Setup
passes its remaining overall budget (default five minutes). There is no
polling at a fixed short interval. Transport errors, malformed responses,
other status/family/codes, permanent refusals, session rotations and role
provisioning mutations never automatically replay. Account/role admission,
peer/email/KDF limits and the staging-before-mint boundary stay unchanged.
These deadlines rely on the fetch implementation honoring AbortSignal, as the
standard fetch does. Custom fetch adapters must honor that contract too.

Deploy and rollback may wait up to five seconds to acquire the actual owner
flock before admission. Missing/unreachable address hints select bounded
waiting; a responsive listener selects the existing authenticated control
status path. If that read-only status fails while shutdown is underway, use
only the remaining acquisition budget, then reread status under the acquired
owner. Neither status nor an address/PID hint admits activation. A subsequent
activation request or ambiguous reply is never replayed automatically. The
exclusive flock, canonical inode/hardlink checks, private auxiliary files,
revision CAS and immutable-source validation remain authoritative. Prune and
other offline command semantics are unchanged. A surviving owner still
refuses E_STORE_BUSY; no process is signalled based on a hint.

`serve DIR --wait-stopped` exposes a five-second lock-release barrier for
callers retaining their own process handle. It requires an existing database,
opens only its existing hardened private owner sidecar, obtains an exclusive
flock and validates the named sidecar/database inode. It does not open SQLite,
create a deployment/sidecar, clear address metadata or signal a PID. No owner
sidecar means no named ownership exclusion. The documented sidecar removal
boundary of LLP 3000.019 §3.4 remains; this is a point-in-time barrier, not a
reservation against a future owner. Other serve flags refuse before effects.

Proof `startServe().stop()` first terminates/reaps the retained native child
through the existing bounded TERM/KILL path, then awaits this barrier, including
any watchdog-held descriptor during worker cleanup. Concurrent/repeated stops
share the in-flight/successful operation. Failure rejects, clears the cached
failure and allows a later barrier retry; it cannot falsely claim cleanup.
No new PID lookup or automatic stop of another owner is introduced. The proof
host stop allowance includes the native child and five-second store barrier.

`data TABLE --json` returns `{rows, more, limit}` for empty and nonempty
snapshots, replacing the bare array. `more` reports the existing one-extra-row
probe in the same read transaction, including default 50-row truncation and
`--limit 0`. Text JSON-lines and the stderr notice are preserved. This operator
surface still bypasses application read rules and refuses private/ephemeral
storage as before; no query semantics change. Existing repository consumers
and the 0.4.35 guide changes are updated for the envelope.

Required evidence: SDK/seed refusal timing, bounded attempts, cancellation and
non-replay tests; actual owner wait/no-effect probes; real delayed worker stop;
deploy/rollback cleanup with a still-listening stale control hint; JSON default
and explicit limit boundaries. Fresh packed Linux qualification must include
real server throttles and public SDK/seedUsers retry, production shutdown and
stdout-only inspection; affected Mac Studio lifecycle tests cover platform
sensitivity. Final exact results, review provenance and scoped limitations are
recorded in WORKSTREAM-REPORT.md.

### Clock reports

Amend LLP 3000.000.000.002 §4's proof helper return: `advance(duration)`
returns `{now, fired, held}`. Each entry carries the schedule name, target,
reason, boundary/window metadata and bounded run summary from the existing
operator-only schedule report. `now()` still returns a number. The CLI and

succeeded; the run summary distinguishes parked or pending work. Every
non-fired schedule appears in held with a reason, including an already
processed boundary, a future saved boundary, initialization, a future window
or an explicit hold. Saved boundaries survive restart: one fire per boundary,
coalescing missed periods unless eachBoundary was explicitly requested.
The helper and CLI print saved-boundary holds and their recovery action on
stderr, including the equal-boundary case on a reused store. Advance never
rewinds markers or replays a completed boundary. Reply limits account for the
retained report plus its partition into fired/held. Staging's expiry notice
describes expiry/upload recovery without development-door instructions.
Ambiguous or failed advances are never retried; time may already have moved.
Maintenance failures return an explicitly incomplete schedule report with the
advanced time; the proof helper attaches this reply to its thrown error.

### Source diagnostics without an existence oracle

null/custom-refusal consequence; duplicate N_LOOKUP_HIDDEN notes at that

is refused. Program `exists` and rule-witness `exists` keep distinct semantics.

For private tables with secondary unique keys, source advice explains that
an unreadable conflicting row uses generic E_RULE (or an undisclosed write

and LLP 3000.036.002 §15.2. Public E_RULE repair text, if changed, is identical
for ordinary rule rejection and hidden collision. No row, key, actual hiding

### Session input and compatibility

Seeded records preserve the actual signup session's kind alongside its
principal, token and numeric expiresAt. They can be passed directly as Session.
Online createClient accepts a legacy incomplete session literal as token-only
transport credentials: its token must be nonempty; partial principal, kind and
expiry metadata never establishes identity, refresh timing or authority. The
server resolves the bearer; session() is null and there is no refresh timer,
as for the existing token option. Complete shapes remain strictly validated
and privately snapshotted. Local/device session input remains complete-only.
E_SESSION lists every missing/invalid field without values and gives the exact
one-line online repair createClient({ url, token }). An ISO expiry in a complete
shape refuses instead of creating a NaN timer. Restored full sessions retain
the existing restore validation and server expiry semantics.

### Advances, maintenance and retained boundaries

ClockAdvance remains an object reporting now/fired/held; valueOf returns now
for arithmetic, ordering and new Date(result). This is JavaScript numeric
coercion, not strict-equality compatibility; typed callers use result.now.

For classified staging, advance(duration) preserves remaining ordinary session
lifetimes by default. The core advances valid full/read session created/expiry
fields, read caps and recoverable mint receipts by the same checked delta,
in the same transaction as existing worker-lease preservation, before publishing
the new process clock. Expired, capped, revoked or superseded authority cannot
become live. Selection uses the authority kernel and bounded pages; overflow
refuses atomically. Existing action delegated sessions and supervised service
families remain owned by the worker-lease path, without double shifting.
Historical admission timestamps are evidence, not an ongoing cap; application
deadlines/backoffs remain business time.

Preservation includes SDK custody, not just raw HTTP credentials. A staging
response for the exact request bearer can publish authoritative session expiry
and read cap beside the same locked business-time/revision snapshot, obtained
through a detached store-identity/liveness-checked authority read. No bearer,
new authority, mint, rotation or refresh is exposed. Production publishes no
such metadata. A failed detached timing read suppresses the clock sample,
including streaming-final samples, instead of publishing advanced business
time with stale credential metadata. A client reconciles only its current
bearer's matching request URL/header and monotonically increases its live
expiry/cap before clock listeners run. Local/device clients await durable
credential custody before publishing or persisting their business clock.
Online clients keep a volatile clock; their existing session listeners may
persist custody asynchronously. Authenticated restoration still validates
expired metadata with the staging probe; no online durability barrier is implied.
Heartbeat final frames carry the same matching-bearer timing or unavailable
evidence as ordinary response headers. Reconciliation and the corresponding
local/device clock publication are serialized: durable credential saves are awaited
before publishing or persisting the advanced clock. A failed save leaves the
clock unchanged, retains dirty credential timing for retry, and surfaces as a
transport failure; rotation/close fences also suppress stale clock publication.
App preparation retains its existing private credential staging: prepared local
clock offsets remain non-durable, including on discard/close, until the actual
App credential commit succeeds. Only then may clock persistence activate before
the scope is published. A later clock-save failure reports a signed-in warning
and retries through ordinary device work; it cannot roll back durable identity.
The existing per-invocation response cutoff (LLP 3000.013 §6 and §12.7) also
spans implicit scope retirement's local credential cleanup. A scope-owned
reference count retains capture before teardown and through each scheduled
local credential task, releasing on rollback or close without waiting for an
auth operation or remote revocation queue.
Capture occurs synchronously when the response decoder validates a body,
before caller Promise continuations can cross that cutoff.
An invocation retains a body validated while live through settlement; a
completed capture owner cannot reopen its cutoff through another begin or hold.
Retention preserves a decoded body, not a stale authentication classification.
An E_AUTH refusal remains scoped to the bearer revision actually dispatched:
rotation supersedes prior and intermediate retiring-bearer revisions, including
