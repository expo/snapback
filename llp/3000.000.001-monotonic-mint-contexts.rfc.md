## 1. Commission

Wave 13 P11 showed two server-created rows in one millisecond sorting in an
arbitrary order. The 128-bit time-leading encoding promised mint order but
fresh random suffixes implemented only timestamp order. This amends LLP 3000
§7's minted-ID contract; IDs stay opaque nominal identities in Quarry.

## 2. Contract

A live **mint context** produces strictly increasing text IDs in allocation
order. Its first allocation, and every allocation with a timestamp strictly
greater than its previous logical timestamp, sample 80 random bits from the
operating system (native) or Web Crypto (WASM). Within the same millisecond,
or when the clock regresses, retain the greatest observed millisecond and
increment the suffix as an unsigned big-endian 80-bit integer. Refuse on
suffix exhaustion without changing state. An advanced valid timestamp can
resume allocation. Rust interpreter host samples are signed integer
milliseconds: preserve the existing normalization of negative samples to zero
before the monotonic comparison. This supports synthetic/backdated timelines;
it does not change the operation's signed `now` or its time-valued columns.
Refuse samples above 2^48−1 without changing state; never mask high bits.
Public JavaScript `mintId` keeps its existing unsigned integer validation
(0 through 2^48−1), including RangeError for negative inputs. Its API boundary
accepts an unsigned timestamp; the Rust native/WASM interpreter boundary
accepts a signed host sample.

The wire encoding stays 48 timestamp bits plus 80 suffix bits in 26 uppercase
Crockford base32 digits. Fixed-width base32 and its alphabet preserve unsigned
numeric order. During rollback the timestamp is a logical high-water mark,
not the wall-clock time of that allocation. Explicit IDs, stable `idFrom`
labels and fixture IDs carry no mint-order promise.

SQLite Engine and Postgres evaluation Engine each own a context; interpreter
requests, jobs, native job chunks and asset allocations use their host's
context. Detached readers and cloned execution contexts share that same
stream. Authentication principal allocations use the HTTP host's separate
authentication mint context. A Device owns a context for locally generated prediction IDs, shared
across direct prediction calls. JavaScript `mintId` retains its existing
module-instance stream (one loaded copy in one JS realm), shared by SDK
admissions. Separate workers, devices, engine instances, module copies and
processes have independent streams. Opening another instance, restarting,
restoring a backup or replacing an engine starts another stream. There is
no total mint-order guarantee across those contexts, nor a commit-order
claim: failed executions consume allocations and supplied replay IDs keep
their original values. Restarts do not persist a timestamp or counter.

Cross-context ordering is timestamp then arbitrary suffix. Applications that
need global order declare an explicit application order column and tie-break
with ID; fixture assertions that express membership use the order-insensitive
matcher from SURF3's fixture amendment. Independent contexts retain the
existing probabilistic collision properties; monotonicity does not introduce
a global coordination service or a cross-device sequence.

## 3. Security and ownership

Randomness initializes independent streams and each later timestamp, while
increments within a logical millisecond are deliberately predictable. IDs
are public row identities, never authentication/session secrets, bearer
capabilities or proof of authority. Session bearer-token generation remains
independent cryptographic randomness. Guessing a row ID still requires the
row's ordinary authorization checks. Existing JS hosts lacking Web Crypto
retain their pre-existing noncryptographic fallback; that limitation belongs
to LLP 3000.001's secure-client-entropy work and confers no security claim.

The Rust mint context is explicit owned state, shared only by deliberate
cloning. Execution-context clones share it across retries and refused writes
so allocations are never reused. No process-global address/seed registry or
thread-local map determines identity or context lifetime. Device prediction
replay consumes recorded IDs instead of regenerating them.

## 4. Verification

Core tests cover a same-millisecond burst, clone sharing, clock rollback,
advancement, timestamp boundaries, negative-host normalization and suffix overflow.
The shipped-WASM witness starts with negative host samples, then exercises
equal milliseconds, positive rollback and rollback below zero. A server/device
integration test creates two rows by two mutations at one frozen millisecond
and checks ascending IDs agree with their creation order on SQLite and memory.
The Lean supplemental mint model states bounded allocation and proves the
same/regressed-clock successor and advancing-clock allocation are greater; its examples cover rollback,
overflow and advancing-time branches. The row-language Lean oracle still
receives explicit IDs (OPEN W5); native allocator randomness is not modelled
as deterministic row-language semantics. Difftest regressions exercise the
new allocator order and retain the classified signature census. Rebuild and
remeasure the shipped WASM artifact against the existing byte budget.
