# A closed model, or a capability maze

**An agent-authored, server-authoritative, offline-capable backend has one writeable artifact — a closed relational model of tables, row rules, named queries, and named mutations — and admission to that model is the only capability switch: if the compiler accepts the program, it is live, realtime, and retainable; if the program needs something the model cannot guarantee, it is not a query.**

That is the whole design. Everything else is a corollary or a refusal.

---

## Assumptions and confidence

**Assumptions.** The author is a strong coding agent with a large finite context. It retrieves, it does not study. It will not read a 178-page guide. It validates by running a checker and a server. The product must stay server-authoritative, SQLite-first with a Postgres graduation that is a dialect swap not a rewrite, and locally idle at ~13 MiB with zero disk writes. Genuine offline for *private* data is a requirement, not a premium SKU. CRDTs are out.

**Confidence.** High that capability-as-authoring-form is the API root cause, and that authorization-as-query-flag is the security root cause. High that JS handlers cannot be lifted into a retainable plan IR without changing race outcomes — LLP 0320 already ran that experiment. High that the client is the complexity sink because it implements holes. Medium-high that the data plane should be SQL-shaped rather than TypeScript-shaped; Convex’s Clique win is evidence against the syntax choice and evidence for “zero wiring,” which I am taking from Convex without taking its query language. Medium that named queries (not ad-hoc client composition) are the right sync unit; that fights Zero and fights a reading of LLP 0155, and I am doing it on purpose. Medium that dropping offline authorization proofs is correct; I have not measured the user-visible cost of “cached, possibly revoked” against the client-size cost of proving otherwise.

**Where I am guessing.** That a SQL-subset model file plus instant `check` beats a Convex-like TS surface on time-to-first-green for *this* product (offline + RLS + SQLite/Postgres). That agents will write `exists (select 1 from memberships…)` when the error message contains that exact snippet. That idle cost survives a local row cache on the client because the *server* stays Rust+SQLite and the JS engine is not in the data plane.

## Part 1 — The theory

### 1. The core abstraction

The author writes **a model**. Not a query constructor, not a handler, not a profile, not a lease. A model is four closed sorts:

1. **Relations.** Ordinary tables. Keys, types, references, indexes. SQLite today, the same statements on Postgres later.
2. **Row rules.** For each table, predicates over `this` and `viewer()` that govern `read`, `insert`, `update`, `delete`. Rules are SQL booleans. They are the only authorization in the system.
3. **Named queries.** Parameterized `SELECT` in a restricted SQL. They are total in the data plane: every admitted query is subscribeable, live, realtime, and cold-retainable for the viewer it was admitted under.
4. **Named mutations.** Parameterized DML plus `assert`, in the same SQL. The mutation text is the optimistic predictor. The server runs the same text. There is no second function to keep in sync.

The semantics are boring on purpose. A query denotes a bounded bag of rows: the `SELECT` conjoined with every applicable row-level `read` rule, with `viewer()` bound to the authenticated principal, with every built-in (`now()`, `random()`) rejected as non-deterministic. A mutation denotes a transaction: evaluate asserts against the server’s committed state, apply DML, reject if any row rule fails. An optimistic prediction denotes that same transaction against the client’s last authorized snapshot; a mismatch at settlement is a conflict, not a second code path.

**What the system derives, and therefore what the author is forbidden to declare:**

- Read-set and write-set of every query and mutation, including tables touched only by row rules (this is how membership invalidates a messages query that never mentions `memberships`).
- Whether a query depends on `viewer()`. Almost all private queries do. That dependence is not a disqualifier.
- Retention eligibility. Admitted ⇒ eligible. There is no `retainable`.
- Indexes sufficient to serve the query under its `LIMIT`.
- The invalidation key: which writes recompute which live queries.
- The client subscription shape, the generated typed client, the local cache keys.

`reads:`, `writes:`, `authorityIndependent`, `retainable`, `auth: 'public'`, `AuthorizedLease`, completeness witnesses, membership proofs as authored objects — these are operational residues of an unanalyzable handler. They are not part of the language. If a future compiler cannot derive one of them, the program is refused, not annotated.

There is a fifth sort, and it is not in the model:

5. **Actions.** Arbitrary JS/TS with I/O. They are not queries. They are not mutations. They are not live, not retainable, not replayed offline, not optimistic. They may *call* named mutations. They exist so the data plane never grows an escape hatch.

This is the disagreement with “an escape hatch is fine if it is a strict superset or strict subset of capability.” A JS handler is neither. LLP 0320 showed it is not a superset: translation changes races, and failure to lift *loses capability*. It is not a useful subset: it is spelled like a query and silently is not. Escape hatches that share a kind are how mazes start. Actions are a different kind, with a different client API, with a compiler that will not let you `live()` them.

### 2. Avoiding the matrix with holes: refuse, do not degrade

**Every program in the data-plane language gets every data-plane capability. The language refuses to express programs that cannot.**

The other choice — totality by running everything, and degrading what you cannot analyze — is the current system. It produces 13 query flavors because each flavor is a cell in (syntax × engine × auth × retention × replay). Agents do not fill in matrices. They pick the cell that compiles and document the rest as a known issue. Clique already recorded the security version of this: `auth: 'public'` because that was the retainable cell.

Refusal is the only shape that keeps the mapping visible at the authoring site. The mapping is: *admitted ≡ live ≡ realtime ≡ offline-cached ≡ (for mutations) predictible.* There is nothing to look up.

**What becomes impossible, honestly:**

- Live queries that call out (HTTP, embeddings, Stripe). Those are actions. Poll them into a table with a mutation if you need them live.
- Live predicates that mention `now()` or `random()`. “Unread in the last five minutes” is not a live query. Pass `since` as a parameter from the client, or materialize with a mutation. Time-advancing queries are a different product (a timer + a re-query), and pretending they are retainable is how you get `authorityIndependent`.
- Per-row JS computed fields inside a query. Compute in a mutation and store a column, or compute in the UI from returned columns.
- Divergent client/server mutation logic. The predictor *is* the mutation. If you need a prettier pending UI than the mutation can produce, that is UI state, not a second mutator.
- Offline replay of side effects. You cannot enqueue “charge the card” and replay it against a local Stripe. Queue the action, show pending, run it once on the server.
- Ad-hoc joins over the local cache that the model never named, with a completeness guarantee. The client will not pretend a local `SELECT` you invented in a component is a retained query. Declare it in the model and subscribe. This is the expensive loss; I am accepting it (see below).
- Unbounded queries. No `LIMIT` (and no proven-finite aggregate) is a compile error. Partial sync is not “send the table.”

**What remains possible, including the case Snapback currently drops:** a membership-scoped messages query, with `viewer()` in the row rule, joins if you want them, cold retention of the last authorized snapshot, live invalidation when membership or messages change, optimistic inserts that the server settles.

The cost of refusal is paid once, at `check`, at the span that caused it, with a rewrite. The cost of degradation is paid forever, in the client, in the guide, in the security hole, in 54 correction causes.

I am not “making the analyzable form total” by lifting JS. That RFC is withdrawn because the premise was false. I am making the analyzable form *the data plane*, and putting JS outside it.

### 3. Authorization lives on the row, and public is the long way around

Authorization is a property of **tables**, not of queries, not of subscriptions, not of leases.

Every table has rules. Missing rules are a compile error, not a default. Defaults are how agents get `public-read` without meaning to. The error at the table span offers three complete templates and will not offer a fourth:

- owner: `this.user_id = viewer()`
- member: `exists (select 1 from memberships m where m.<group> = this.<group> and m.user_id = viewer())`
- world: `public` — a keyword, not `true`, not `auth: 'public'`, not omitted.

Queries have no `auth` parameter. They cannot buy retention, reachability, or live-ness by becoming public. They cannot skip a table rule by filtering in the `WHERE`. The `WHERE` is conjoined with the rule; it does not replace it. A world-readable messages table is a one-token, greppable, reviewable fact on the table, and `check` still emits a security diagnostic that CI treats as failure unless the project explicitly allows public tables. Membership does not require a second mechanism. Membership is the middle template in the error you get when you forget the rule.

This is the design against LLP 0310 P18. The agent set chat tables to `public-read` because that unlocked retention. In this language that trade does not exist. The private query retains. The public table retains too, but public is louder, longer, and CI-red. The paved path is the member template because that is the snippet in the diagnostic the agent hits first.

**Write rules are the same predicates, not a parallel ACL.** `insert` on messages is `this.sender_id = viewer() and <member predicate>`. The mutation does not restate them; the engine enforces them. An `assert` in the mutation is for *invariants the row rule cannot see* (rate limits, “body non-empty”), not for authorization. If you put authorization only in the mutation, `check` fails: *table `messages` is readable/writable only through procedural asserts; move the predicate to a row rule or the query planner cannot retain.*

**Identity.** `viewer()` is the only ambient. It is a bound principal id, stable for the life of a subscription. It is not a function that re-enters the database. Session issuance is outside the model (tokens in, principal out). Do not grow four auth systems.

**Offline authorization.** Last-known-authorized snapshot, marked `cached`. If you were kicked from a conversation while offline, you may still see cached messages until reconnect, at which point the rule re-evaluates and the rows vanish. This is the consistency model. It is not a bug. **Authorized leases, membership witnesses, and client-side completeness proofs of auth do not earn their keep.** They are how a result cache becomes 212k lines, and they still cannot make revoked data disappear from a device that is offline. Do not spend the differentiator on a proof you cannot finish.

### 4. The agent as author

Agents retrieve; they do not read. They cannot see consequences that are not at the edit site. They route around obstacles and document the compromise. Diary 0114 and LLP 0317 are not color. They are the user.

Implications, as design rules:

**Surface size is an architectural constraint, not a docs problem.** The author-facing vocabulary is the four sorts, about two dozen keywords, the generated names of *this* app, and three CLI verbs (`check`, `dev`, `verify`). Not 31 `define*`, not 4,248 published symbols, not 3,934 codes. A code family is allowed to have structured payloads; it is not allowed to be a separate concept. If you need a new `define`, you split the language. Stop.

**Retrieval is the compiler.** There is no 20 MB guide in the install. There is a grammar, a 40-line explainer, and diagnostics that contain the rewrite. `snapback check` is the index. An agent that greps the repo should find the model file in one shot; therefore there is one model file (or one directory with one entrypoint), not a profile pair and a contract arm and a familiar arm.

**Errors are at the span, before the process, with the program you should have written.** “The platform told me exactly what was wrong” is the best-loved property in the corpus and the one that must survive. It does not survive 3,934 codes. It survives thirty families, each with a `span`, a `rewrite`, and a `why`. Feedback that requires booting the server, binding identity, opening a websocket, and observing that a JS live query did not retain is not feedback; it is a maze with a receipt.

**Latency.** `check` parses, type-checks, analyzes, and emits the client in well under 100 ms on a laptop for the apps this thing is for. If you cannot know retainability without running the server, you have reintroduced the hole. `dev` loads the admitted model into Rust+SQLite and does not restart the world when the model changes: subscriptions rebind, identity does not, the web arm is the same app. The Clique milestones that died on Metro races and identity rebinding are in scope for this theory. A closed data plane with a flaky dev loop is still a loss.

**What the system refuses, because agents will not:**

- Two ways to do the same thing. One authoring profile. One client. One query kind. One mutation kind.
- A query or mutation whose body is not the SQL subset. No “we’ll run it and see.”
- A table without rules.
- A live subscription to an action.
- A second mutator “just for optimistic UI.”
- Schema edits that mint a new app identity.
- Features whose only purpose is to restore a capability the language just refused.

**The agent will lie in a diary and ship.** Ceremony that is not mechanically forced is decoration. Reviewable authority is worth ceremony *if the ceremony is the row rule you had to type to compile.* Function-level `reads:`/`writes:` declarations are ceremony that does not buy reviewability of the thing that matters (who can see the row) and should not return.

### 5. What earns its keep

**Keep, as substrate.**

- Rust + SQLite on the server, scale-to-zero idle, MIT. This is the actual product. The JS engine is for actions and is loaded when an action runs, not at idle.
- Server-authoritative settlement, ordered intent, prediction-versus-settlement as *states of a mutation*, not as a parallel API.
- Typed refusal at the authoring site. Collapse the code catalog; keep the honesty.
- Acceptance evidence as done. A green `verify` receipt is done; anything else is a claim. Start the benchmark/diary loop on day one, against Convex, Supabase, PocketBase, on the private-chat case, not on a public counter.
- Query-driven partial materialization. The client holds authorized rows for subscribed named queries, plus an outbox, plus watermarks. That is the local-first outcome worth copying from Zero.

**Keep, demoted.**

- Cron: an action on a timer, not a data-plane primitive. v1 can wait.
- Blobs: a column type under the same row rules. No parallel asset product.
- React/Expo: a hook that calls the generated client. Fifty lines, one package, not an arm.

**Do not keep, including beloved things.**

- **JS live queries, JS mutations as the data plane, and any lift-the-handler IR.** Withdrawn for cause.
- **Two authoring profiles.** Familiar lost 2/8. Explicit won 7/8 slowly. Neither is the closed model. One profile.
- **Contract/Exact-first plus React as a second client.** The client is already the complexity sink. Generate one TypeScript client from the model. Framework bindings are sugar.
- **Ad-hoc client query composition with completeness (Zero’s local ZQL, a strong reading of LLP 0155 move 1).** Named queries are the unit of sync. Composition is compile-time in the model. A local row store you can invent new joins against *and trust* is a second query engine, a second permissions evaluator, and the completeness-proof machine. That is architecture, not outcome. Copy Zero’s outcomes that do not require it: query-driven materialization, a useful local row cache, shared mutators, inspection of prediction vs settlement.
- **Offline auth proofs, authorized leases, membership witnesses as user-facing or client-mandatory machinery.** Last-known-authorized + `cached` is the product.
- **The 20 MB embedded guide, 1,645 generated reference files as the authoring surface, 185 scripts.** Install size is the first scale-to-zero the user feels. 187 MB unpacked is a contradiction. Diagnostics replace the book.
- **Function-level operational annotations** (`reads`, `writes`, `retainable`, `auth` on a query).
- **Admin clients, custody packages, dev-identity packages as separate products.** Identity rebinding is a `dev` bug to fix, not a package to publish.

**Ship small.** The server is a Rust binary talking SQLite. The authoring surface is a model file and a generated client. The JS engine is optional at runtime. If a crate or package exists to implement a capability hole, deleting the hole deletes the crate.

### 6. Where the diagnosis is incomplete or wrong

The central claim is right: **capability as a function of authoring form, invisible at the authoring site**, is the API bug, and it is the same bug as the `public-read` security failure.

It is incomplete in three ways that change the rebuild.

**First, the scoreboard is not an API scoreboard.** Diary 0114: the friction that costs milestones is behavioral — realtime custody, dev-loop stability, media limits — and PocketBase won because the model spent effort on product code. A closed query language with a Metro race and an identity rebind still loses Clique. The theory of the agent as author has to constrain `dev` and the client lifecycle as hard as it constrains `define*`. Section 4 of the thesis lists “the dev loop is the product” as a differentiator; I am promoting it to the same rank as the execution model. Part 1 without that is a language design that fails the metric the thesis itself names (time-to-first-green, correction-loop count).

**Second, “pick the analyzable form and make it total” is the wrong slogan, and 0320 is the proof.** You cannot totalize opaque handlers without changing races or dropping capability. The rebuild is not “plan IR as compiler output from JS.” The rebuild is “JS is not in the data plane.” The four withdrawn RFCs were correctly withdrawn as retrofits; their premises are also the wrong premises for a from-scratch substrate if they still treat handlers as a source language.

**Third, “copy Zero’s outcomes, not its architecture” is right as a slogan and easy to implement as Zero.** Zero’s local composable query engine *is* the architecture that forces client-side permissions and completeness. Snapback already tried to be more honest about authority than Zero, and then grew a 212k-line client implementing holes so it could approximate Zero anyway. The from-scratch move is to take the *server-authoritative* half of Snapback’s advantage (settlement, ordered intent, prediction-versus-settlement, small local operating surface) and the *named, admitted query* half of Replicache, not Zero’s ad-hoc local relational replica. DK-9’s “result cache, never a replica” was the right local operating surface and the wrong way to get there (holes + proofs). Do it by refusing ad-hoc completeness.

A smaller disagreement: **declared reviewable authority should not be kept in its current form.** The diaries like ceremony that caught category errors. Row rules are that ceremony. `reads:`/`writes:` on functions are a symptom, and keeping them because ceremony feels safe will re-grow the matrix.

## Part 2 — The concrete API

One file. One language. The agent writes this and runs `snapback check`.

### The model (group chat)

```sql
-- app.model.sql

table users (
  id          text primary key,
  handle      text not null unique,
  created_at  integer not null
);

rule users read   public;
rule users insert this.id = viewer();
rule users update this.id = viewer();
rule users delete never;

table conversations (
  id          text primary key,
  title       text not null,
  created_at  integer not null
);

rule conversations read
  exists (
    select 1 from memberships m
    where m.conversation_id = conversations.id
      and m.user_id = viewer()
  );
rule conversations insert true;   -- creator must also insert a membership in the same mutation
rule conversations update
  exists (
    select 1 from memberships m
    where m.conversation_id = conversations.id
      and m.user_id = viewer()
  );
rule conversations delete never;

table memberships (
  conversation_id text not null references conversations,
  user_id         text not null references users,
  joined_at       integer not null,
  primary key (conversation_id, user_id)
);

rule memberships read
  exists (
    select 1 from memberships mine
    where mine.conversation_id = memberships.conversation_id
      and mine.user_id = viewer()
  );
rule memberships insert
  this.user_id = viewer()
  or exists (
    select 1 from memberships mine
    where mine.conversation_id = this.conversation_id
      and mine.user_id = viewer()
  );
rule memberships delete
  this.user_id = viewer();
rule memberships update never;

table messages (
  id               text primary key,
  conversation_id  text not null references conversations,
  sender_id        text not null references users,
  body             text not null,
  created_at       integer not null
);

index messages_by_convo on messages (conversation_id, created_at desc);

rule messages read
  exists (
    select 1 from memberships m
    where m.conversation_id = messages.conversation_id
      and m.user_id = viewer()
  );
rule messages insert
  this.sender_id = viewer()
  and exists (
    select 1 from memberships m
    where m.conversation_id = this.conversation_id
      and m.user_id = viewer()
  );
rule messages update never;
rule messages delete
  this.sender_id = viewer();

-- The live query. Membership is not in the SELECT.
-- The compiler conjoins the messages read rule, derives a
-- read-set of {messages, memberships}, and admits it for
-- live + retain + realtime. No auth flag. No retainable.

query messagesInConvo(conversation_id text)
  select id, conversation_id, sender_id, body, created_at
  from messages
  where conversation_id = :conversation_id
  order by created_at desc
  limit 50;

query myMemberships()
  select conversation_id, user_id, joined_at
  from memberships
  where user_id = viewer();

query membersOf(conversation_id text)
  select user_id, joined_at
  from memberships
  where conversation_id = :conversation_id;

-- The mutation is the predictor. now() and id() bind at
-- intent time and travel in the envelope; the server
-- reuses those bindings so prediction and settlement
-- agree on identity and timestamp.

mutation sendMessage(conversation_id text, body text)
begin
  assert length(:body) > 0;
  insert into messages (id, conversation_id, sender_id, body, created_at)
  values (id(), :conversation_id, viewer(), :body, now());
end;

mutation createConversation(title text, first_peer text)
begin
  assert length(:title) > 0;
  let cid = id();
  let t   = now();
  insert into conversations (id, title, created_at)
  values (cid, :title, t);
  insert into memberships (conversation_id, user_id, joined_at)
  values (cid, viewer(), t);
  insert into memberships (conversation_id, user_id, joined_at)
  values (cid, :first_peer, t);
end;
```

That is the authorization declaration. There is not another one. `viewer()` never appears on a query as a capability mode. Public appears once, on `users.handle`, as the keyword `public`.

The messages query works offline because it was admitted. The local cache holds the last 50 authorized rows for each subscribed `conversation_id`, plus memberships from `myMemberships`. After a reconnect, membership changes recompute the derived read-set and the cache drops what the rule no longer admits. While disconnected, the UI reads `status: cached`.

### Generated client

```ts
import { createClient } from "./snapback.gen";

const db = createClient({ url, token });

// live ≡ retainable ≡ realtime. One method.
const q = db.live.messagesInConvo(
  { conversation_id },
  (row, meta) => {
    // meta.status: "live" | "cached" | "pending" | "rejected"
    // meta.complete: boolean  // true iff this named query was
    //                         // fully answered at last sync
  },
);

await db.mutate.sendMessage({ conversation_id, body: "hello" });
// local insert is visible when meta.status is "pending",
// settled when the server ack arrives, rolled back on reject.

q.unsubscribe();
```

React, if you want it:

```ts
const { rows, status } = useQuery(db.messagesInConvo, { conversation_id });
const send = useMutation(db.sendMessage);
```

There is no `db.query(...)` builder. There is no `defineJsLiveQuery`. There is no `useRetainable`. Adding a screen that needs a different slice means adding a named query to `app.model.sql` and running `check`.

### Names an author has to know

**Language (fixed, ~22):** `table`, `index`, `rule`, `read`, `insert`, `update`, `delete`, `public`, `never`, `true`, `query`, `mutation`, `begin`, `end`, `assert`, `let`, `viewer`, `id`, `now`, `this`, `references`, `primary key`.

**CLI (3):** `check`, `dev`, `verify`.

**Client (fixed, ~8):** `createClient`, `live`, `run`, `mutate`, `unsubscribe`, `status`, `complete`, and the optional `useQuery` / `useMutation`.

**App-defined:** table names, query names, mutation names. Those are the product.

No `defineLiveQuery`, `defineJsLiveQuery`, `defineMutation`, `defineQuery`, `retainable`, `AuthorizedLease`, `auth`, `reads`, `writes`, two profiles, or a second arm. An agent that has this file and `snapback check` does not need a guide to author the canonical case.
