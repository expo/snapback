## 1. Readiness actions

**Implemented on the durable inbox (2026-09-08).** The sentence and offered
action describe what queued work needs. `OutboxStatus.draining` records active
replay in the existing serialized owner. A writer with queued work offers
`wait` during replay and `connect` when paused. The templates interpret
`connect` as **Sync now**, calling `client.online()`; the method also
reauthorizes held data and resumes delivery.

Connection is insufficient: `performMutation` can return `queued` after a
stopped drain and then mark the client validated/connected. A successful query
can likewise restore the transport fact without replaying the queue. Removing
the action solely because `connection === "connected"` could strand writes.

Readiness follows the existing shared drain owner:

| Queued work | Presentation |
| --- | --- |
| Actively draining under the current account | Waiting for the server; `wait`, with no duplicate sync action |
| Paused or idle, delivery requires an explicit retry | Offer sync/resume, including while transport is connected; the sentence explains that action |
| Transport unavailable | Offer reconnect/sync under the existing policy |
| Fence or authority blocks replay | Preserve the specific connect/sign-in reason; a live read cannot override it |

The drain owner notifies when replay begins and ends, including a transport stop
that leaves durable entries unchanged. `ClientInbox` announces those changes
through its existing writer-only ledger subscription, after the carrier opens.
A follower keeps LLP 1018.004's inbox admission status and its sending-tab
sentence; the writer's activity remains separate in `detail.writer`. There is
no new timer, probe, retry loop, or hook-owned lifecycle.

The earlier readiness slice `a746de73f` passed its package build and **82/82**
affected tests (16.97 s, Node 24.18.0):
readiness, snapshot, durable inbox, client sessions/regressions and outbox.
The tests hold replay open with zero/one/four observers, recover a transport

## 3. Semantic mutation targets

Replace the recipe's dependency on the insertion position in `intent.ids`
with a named relation the compiler derives and the client can verify. Reuse
that relation across the paginated thread and composite item declarations.
This revises the original item's decision to defer compiler participation;
the positional binding is no longer an acceptable final application contract.

The bound Quarry graph knows which table each insert targets. That is the
starting point. Proving which reserved ID belongs to a semantic target also
requires allocation order, cardinality and control flow. Two inserts into
the same table, a conditional earlier insert, or repeated inserts cannot be
resolved by picking the first matching table. Edits and removals need a
target relation even when they allocate no IDs.

### Implemented relation and surface

The existing Rust checker derives `certificate.mutation_targets` from the
checked executable IR and schema. Each direct table/action pair has either a
source, `{ newId: offset }` or `{ argument: name }`, or an explicit unresolved
reason: `conditional`, `repeated`, `ambiguous`, or `computed`. This is separate
from `write_sites`: a branch-maximized write bound does not prove which calls
to `Input::NewId` precede a write. `complete` means the entire direct row-effect
relation is known. It excludes maintained/engine effects, which keep their
existing certificates and custody; it does not require a client to observe
every recipient's server-only fan-out row.

The bounded proof supports straight-line allocations, required Id/Ref arguments,
aliases, constructed row `id` fields, and the identity field of reads through
a schema-proven unique index on `id`. It follows actual expression evaluation
order, including unused allocations and the allocation performed by `Emit`.
Unknown collection execution poisons subsequent offsets. Conditional or repeated
writes and more than one direct write of the same table/action remain unresolved.
Every outer binding written anywhere in a loop loses its exact target fact after
the loop, even when a later assignment restores the entry value on the final
body path. An earlier `break` or `continue` can preserve an intermediate value;
nested branches and loops count as writes to that binding too. Untouched argument
and read aliases retain their facts. Conditional exits prevent later writes from
being called unconditional, including escaping `break`/`continue` in certified
raw IR. A nested loop consumes its own loop exits; only a return escapes it.
No new evaluator, application target registry, or arbitrary data search is added.

The bound Quarry declarations type the available table/action choices as a third
`Op<Args, Result, Targets>` phantom. `mutationTarget(op, table)` selects a named
table; the runtime address always comes from the certified durable facts:

```ts
export const messageWrites = {
  create: mutationTarget(api.deliveries.post, "messages"),
  update: mutationTarget(api.deliveries.edit, "messages"),
  remove: mutationTarget(api.deliveries.unsend, "messages"),
};

defineItems(api.deliveries.thread, {
  table: "messages", select: delivery => delivery.message, order: "reverse",
  create: {
    target: messageWrites.create,
    belongs: (args, query) => query.c === null
      && args.conversationId === query.conversationId,
    draft: args => ({ body: args.body }),
  },
  update: { target: messageWrites.update },
  remove: { target: messageWrites.remove },
});
```

The selected reference is also passed to `useMutation` or `client.mutation`;
chat composers and edit/unsend controls submit `messageWrites`. Admission pins
the selected table beside the certified relation. Changing a mounted hook to
another target of the same operation updates its next submission.

`target.id(entry)` exposes the same conservative correspondence to headless
callers. A missing certificate, unresolved relation, multiple effects for the
selected table, or identity mismatch returns `undefined`. `defineItems` resolves
the certificate facts itself; it does not trust a caller-supplied `id` callback.
Both chat projections share these targets while keeping their own membership
and selection. Neither application code nor the generated declaration assigns
meaning to `ids[0]`.

The loop/exit boundary is exercised at the certified IR seam: `Let`/`Assign`
with an intermediate alias followed by conditional `Break` or `Continue` and
a restoring assignment. Engine execution proves that the early exit can delete
the second argument's row, while the repaired certificate refuses an exact
target. Both exits, nested assignments, and conditional exits consumed by or
escaping a loop are covered. Quarry itself has immutable bindings and no
`break`/`continue` form; its compiled-source witness proves that an untouched
alias remains exact after a bounded loop.

### Admission and actual execution identity

Admission materializes addresses against the reserved slice and captured args
inside the existing outbox turn. The same atomic swap stores
`entry.targets = { generation, planHash, schemaHash, rows, unresolved, complete }`
beside its replay bytes, including when the trust fence suppresses prediction.
Replacing the held program, cold reopening, or loading another generated API
cannot reinterpret a previously admitted slice.

A successful replay terminal carries `program: { planHash, schemaHash }` for
the program that actually executed. The engine saves this identity in the same
transaction as the terminal and commit. The writer returns that same identity.
The existing dedup lookup still precedes current operation, schema and grant
checks: an already-settled matching replay returns its original terminal even
after the operation is removed. There is no changed replay request or new
admission refusal in this slice.

The actual-owner regression
`offline_replay_terminals_survive_operation_and_traced_schema_successors` also
pins a successful no-write mutation: its sequence and execution count each
advance once, and an immediate matching replay returns byte-identical terminal
data without advancing either. This covers the empty-effect case used by §4;
row delivery still requires that row's authority evidence.

For a committed entry, the target is usable only when both execution hashes
match the admission hashes. A genuinely unexecuted intent can run under a
successor program, but a changed program cannot reuse its old target proof.
Item attribution additionally requires the exact published frame's generation
and schema to match admission. Otherwise a create stays an intent-only draft,
and missing-target edits/removals stay in the account outbox. Fresh query
membership may still exclude a create without asserting row delivery. These
fallbacks preserve truthful work through incompatible deployment; they do not
promise stable row handoff across it. Entries from an older client/owner with
no target or execution identity remain explicit until dismissed.

The regression witnesses cover unrelated-insert reordering without an app edit;
multiple/conditional/repeated and non-write allocation; no-ID edits/removals;
unpredicted admission; immutable facts through replacement and cold reopen on
file, IndexedDB and SQLite; program/frame mismatch; and lost acknowledgement
followed by operation removal. The item suite also supplies a contributing
prediction beside absent/unresolved target facts and changed or missing execution
hashes for creates, updates and removals: declared targets cannot borrow that
address, while an undeclared operation retains prediction-only attribution.

unknown target table, query-as-mutation target, and wrong action kind. Exact
target and commit identities are the inputs to §4's separate compaction change.

## 4. Automatic compaction of successful history

### Implemented eligibility and handoff (2026-09-09)

The carrier compacts inside its existing atomic swap, without readers or a
second journal. The owner records a committed replay terminal's `effects` as
`[{table, id, removed?}]`: the complete set of actor-observable row effects.
Full read authorization is checked against final transaction state; deletions
use the first preimage, so temporary intermediate values cannot launder hidden
row identities. Server-only fan-out/effects remain in the owner's durable commit
custody and expose no row addresses. Inability to complete this bounded
projection omits `effects`, never truncates a completeness claim. Changed
addresses are bounded by the mutation certificate's write-site maxima; first
preimages share an 8 MiB ceiling, serialized effects share the existing 1 MiB
output ceiling, and fresh read checks share the default step/probe ceilings. Exceeding any projection bound leaves a successful commit
intact with unknown effects. An empty array proves that this account has no
row-echo obligation. Prediction and certified allocation do not prove actual
execution completeness; the owner supplies the actual obligations.

Eligibility requires committed state, an `effects` array, matching actual
execution/current held operation and schema hashes, and no coverage
supersession. Each observable address must acquire an authoritative row or
negative through the commit in matching coverage. A removal requires a
negative. Each discharge is persisted by shrinking the pending addresses in
the same entry; an overlay's disappearance, patience, a capped exclusion,
`arrived` and the global sequence never discharge an address. Complete
discharge removes the entry, overlay bookkeeping and its inbox alias in the
same carrier transaction. The existing bounded in-flight terminal slot still
answers the issuing call when its durable entry has already compacted.

**Presentation change:** the carrier retains one scalar `compactedThrough`,
the greatest sequence of a compacted success. It is not row-delivery evidence.
An older query image exposes `freshness.compactedThrough` and reason `changed`
("Changes committed after this snapshot. Refresh to see them."). Its data,
receipt and row evidence remain unchanged. This conservative signal can include
an unrelated write; it deliberately avoids retaining a per-frame action archive
or silently advancing a once-only query. The scalar travels on the existing
follower inbox read transaction too. Failures and queued entries remain intact.

The achieved bound is on **discharged successful history**, not total storage.
A success without a complete owner effects projection, an unobserved readable
row/maintained target, or replaced program/authority remains
an unresolved terminal until evidence arrives or the user dismisses it. Such
entries can remain indefinitely; no age policy discards them. One hundred
repeated discharged successes add zero outbox entries and no per-success
replacement markers; row/query storage remains independently governed.


The target default is client-owned compaction of delivered, successful work.
Routine online sends must not accumulate permanently or require the user to
dismiss every success. Rejected/expired entries retain explicit dismissal;
queued and admission-unknown work remain recoverable. The account surface
should emphasize outstanding or failed changes, with any retained recent
successes governed by an explicit bounded policy.

Fable's proposal correctly separates the actor from the hook: a runtime
compactor can run independently of readers. The missing step is the scope of
its evidence. Consider an edit committed at 41: the live query has a body read
through 42, while a once-only query still holds the body read through 40.
The live indicator can resolve. The old one cannot. Deleting the shared intent
because the live query resolved would otherwise remove the old frame's only
description of its unobserved edit. A fresh capped page omitting a create is
also membership evidence for that page, not proof that its target arrived.

Design the compactor against these distinct obligations:

1. **Settlement custody.** A durable committed result is available to any
   issuing call still waiting for its own result. Deletion cannot turn a
   successful online call back into `queued` or race its result handoff.
2. **Effect custody.** Prove the relevant targets have authoritative state or
   removal through the commit under matching authority/program identity.
   A message row alone may not discharge fan-out or maintained effects.
   Empty write sets need their own proven rule. Overlay disappearance,
   `arrived`, a global sequence and elapsed time are insufficient substitutes.
3. **Presentation custody.** Preserve the meaning of older live/once-only and
   stored query frames. The implementation must either retain their minimal
   needed action evidence or safely invalidate/advance the affected stored
   representation under its existing contract. A once-only public image must
   not silently become a newer query. Counting mounted consumers is not a
   substitute, and moving unbounded history into a second store is not compaction.
4. **Recovery custody.** *(Moot after LLP 1018.004: there are no forwarded
   admission receipts or recovery handles. Compaction must still not delete an
   entry an inbox row's alias names, and must remove that row with it.)*
5. **Crash custody.** Decide and persist the eligible removal through the
   existing atomic carrier mutation. A crash, reopen, takeover or account
   replacement cannot expose half of the handoff or make a compacted draft
   reappear. Run from runtime/store progress with zero observers; rendering
   never schedules a durable mutation.

These are requirements for a deletion design, not a claim that today's
per-frame proof already meets them. First trace the minimum retained fields
and their owners through the current item frames, settling calls, outbox and
forwarding receipts. Specify the exact eligibility predicate and atomic
transition before adding a deletion call. Prefer extending existing custody
over a new journal or collection cache. If preserving old frames proves to
require a semantic change, document that change explicitly before coding it.

Unobserved successful writes can remain unresolved for arbitrarily long.
A compactor triggered only by observation therefore cannot claim a hard
bound on all storage. State the limit being achieved: repeated successes
whose effects have been discharged leave bounded durable history. Name and
measure the remaining exceptional/unresolved set; do not label the whole
store bounded or discard those records under a time limit. An absolute store
cap would additionally need an admission/backpressure policy.

Acceptance includes long repeated online sends after delivery; zero readers;
the two-frame example above; capped exclusion without target delivery;
predicted and unpredicted edits/removals; multiple affected rows and maintained
values; active result waiters; loss of the follower acknowledgment before and
after compaction; file/IndexedDB/Expo carrier crash/reopen; program replacement;
and rejected/expired entries remaining explicitly dismissible. Measure bytes
and operation cost as successes accumulate, including any replacement markers.
Amend LLP 1012 §7 and the current item decision in this separate code change.

## 5. Common item presentation

After recovery and target declarations simplify the templates, derive the
common display decision from the existing item facts: readable row versus
submitted draft, prediction, queued work, committed awaiting this image, and
failure. Keep those source facts and refusal details accessible. A `pending`
collection that also contains failures should have wording that matches its
contents; improve the actual decision a screen makes before choosing names.

The helper must preserve authorization/composite handoff, stable keys, omitted
timestamps for predicted creates, and the difference between commit and
delivery. It may derive a label or display choice; it cannot fabricate a
message row, rerun an edit, or decide a draft's editor lifecycle. Keep platform
markup and product copy where they belong. Prototype it in both templates and
retain it only if total application decisions and code fall. If a derived
helper buys nothing, record that result and simplify the callers directly.
