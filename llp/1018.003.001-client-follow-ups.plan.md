## 1. Readiness actions

Make the sentence and offered action describe what queued work needs. Today
`readiness(status, connection, queued)` has no drain-activity input and always
offers `connect` for queued work inside the fence. The templates interpret
that as **Sync now**, calling `client.online()`; the method also reauthorizes
held data and resumes delivery.

Connection is insufficient: `performMutation` can return `queued` after a
stopped drain and then mark the client validated/connected. A successful query
can likewise restore the transport fact without replaying the queue. Removing
the action solely because `connection === "connected"` could strand writes.

Derive readiness from the existing shared drain owner and its current outcome:

| Queued work | Presentation |
| --- | --- |
| Actively draining under the current account | Waiting for the server; `wait`, with no duplicate sync action |
| Paused or idle, delivery requires an explicit retry | Offer sync/resume, including while transport is connected; the sentence explains that action |
| Transport unavailable | Offer reconnect/sync under the existing policy |
| Fence or authority blocks replay | Preserve the specific connect/sign-in reason; a live read cannot override it |

Use the existing flight/outcome facts and shared outbox observation. Do not
start another timer, network probe or retry loop to derive this field. Final
action spelling must match the actual template behavior; keep the pure summary
and full detail available. This is a separate small change before recovery.

Verify a held-open active replay, a transport-stopped queue followed by a
successful read, a fence-blocked queue, and the zero/one/four-observer cases.
Assert that the paused queue remains recoverable and the active drain is not
duplicated. The current action table changes only with that implementation.

## 2. Shared mutation recovery

> **Withdrawn by LLP 1018.004 (2026-09-08).** The outcome this section would
> have made observable, `admission-unknown` with a recovery handle, no longer
> exists: a follower tab's write is a durable inbox row in the partition's
> own database before `run()` resolves, and the writer admits it through the
> ledger. There is no forwarded command, no lost acknowledgment, and no
> recovery flight to share. The template deletion this section named is done.
> §1, §3, and §4 stand; §4's recovery-custody item is moot for the same reason.

Make one submitted mutation own its recovery in the headless client. React
and Expo observe it across navigation. Settle its contract before
implementation: request identity, account lifetime and the
meaning of a lost acknowledgment are behavior, even when the visible result
is deleting a template helper. Codex is the implementer. This section
is a scoped draft; it records neither completed code nor independent review.

### The friction and the existing foundation

At `e6c89816b`, `useMutation` keeps its flight count, last result and transport
refusal in a hook-local state machine. The chat template separately hoists
`useAccountRecoveryCustody` into its app roots. Its `begin`, `hold`, `finish`,
`beginRecovery` and `resolve` calls carry arguments, recovery tokens and account
checks through send, edit and unsend. The headless client already has the
forwarding command, immutable payload identity, receipt lookup, retry
coalescing and authority fences that these screens need.

The governing boundaries are [LLP 1018.000 §8](./1018.000-composable-architecture-next-moves.research.md#8-account-sessions-and-durable-follower-admission),
[LLP 1012 §7](./1012-local-first-v1.spec.md#7-writes-offline), and the current
[offline guide](../snapback2/packages/snapback2/guide/offline.md#recovery).
Reuse those owners and the durable outbox. This proposal adds an observable
application-facing lifetime to a submission; it creates no second admission
queue, persistent pre-admission log, wire protocol or retry scheduler.

### Proposed surface

Make `useMutation(ref)` an adapter over `client.observeMutation(ref)`, following
the existing `subscribe` / `getSnapshot` pattern. Keep `run(args)` and its
result contract. The shared snapshot retains the useful current fields and
adds a typed collection of submissions whose admission remains unknown:

```ts
const post = useMutation(api.deliveries.post);
await post.run({ conversationId, body });

// A later screen observing this operation sees the same unresolved submission.
for (const send of post.unconfirmed) {
  showSendToCheck(send.id, send.args.conversationId, send.args.body);
  // A user action calls send.recover(); no args or token reconstruction.
}
```

`unconfirmed` is a working name. Each record has a stable submission ID,
read-only captured arguments, recovery-in-progress state, the last recovery
failure when present, and a bound `recover()` action. Mechanism details remain
inspectable. The headless surface must support the same observation and
actions; sharing cannot depend on React being mounted.

The operation selects a collection. Each invocation remains distinct: two
calls with the same op and arguments are two submissions. An op name, route,
message ID or argument digest must not accidentally become an idempotency
key. Recovery belongs to a particular submission. Concurrent checks of that
submission join its existing recovery flight; unrelated submissions proceed
independently within the existing capacity limits.

Keep `can` truthful about admission readiness and capacity. Chat separately
keeps its interaction policy of checking an uncertain send before another
send, and grouping edit/unsend as one user interaction. Shared observations
make that policy a small composition of facts. Do not introduce a general
mutation-group registry or silently serialize every caller of the same op.

### Ownership and transitions

1. Capture the owning client/account incarnation and the same argument snapshot
   used for submission before an async continuation can change either. Caller
   mutation of its original object must not alter recovery bytes. Integrate
   with existing upload planning; follower uploads retain their pre-byte refusal.
2. The client retains active and uncertain submissions with zero observers.
   Mounting, unmounting, Strict Mode and subscriber count perform no settlement
   or recovery action. All consumers read immutable shared snapshots.
3. A known initial outcome completes the admission record. An unknown outcome
   retains its exact operation, arguments and request identity. `recover()`
   supplies those internally to the existing recovery path; it cannot allocate
   a fresh request identity or rewrite arguments.
4. A valid late acknowledgment updates this same record even if the original
   promise already returned `admission-unknown`. Publish that fact from the
   existing forwarding receive path before releasing its command. A stale
   acknowledgment cannot resolve a newer submission or another account.
5. An unreachable writer, recovery refusal, failed check or expired receipt
   leaves admission unknown. Clear a known admission from `unconfirmed` only
   on its durable receipt. `queued` proves admission; it does not prove that
   the intent is still queued or that a particular screen displays its row.
6. Client close and account replacement invalidate old handles before new
   state can publish. A stale `run` or `recover` action refuses; it cannot
   launch a write under the replacement account. Expiry/sealing retains the
   existing custody policy. Writer takeover within the same durable partition
   preserves the original recovery identity and authority checks.
7. Keep a bounded set of live admission records. Reuse the forwarding lane's
   existing 64-command capacity for unresolved forwarded work; terminal
   admission records release their retained payloads. Expiry must not silently
   evict uncertainty to make space: additional tracked work refuses when full,
   and readiness explains the capacity limit. Record this retention change
   explicitly in LLP 1018.000 §8 when implemented.

The lifetime guarantee is navigation and remounts within the same client.
Full process restart remains the existing durable outbox/receipt contract.
The opaque recovery token contains a payload digest, not the original args;
automatic reconstruction after restart would require a separate persistence
decision. Do not claim that guarantee from this in-memory move.

### Application responsibilities and the implementation spike

The application owns unsent text, prompts, navigation and which draft an
acknowledgment may clear. Recovery state must not overwrite a newer draft or
publish a notice into another conversation. Send arguments contain the
conversation ID; edit/unsend arguments contain only a message ID. The current
helper also remembers the originating conversation and untrimmed draft.

Resolve this concrete API question with both template witnesses before
freezing the public type: how should a submission retain optional, typed
presentation context for those two facts? Prefer a small per-call context
value if removing the helper requires one. Keep it separate from authority,
payload hashing and wire args, with the same account lifetime and no implicit
persistence. Do not hide the problem by dropping the original-conversation
or draft-preservation behavior. If the candidate needs a generic workflow
framework, revise the surface before implementing it.

The deletion target is the template's generic recovery-custody machine and
its hoisted recovery props, plus hook-local ownership duplicated by the
client. `shared/send.ts` may still hold authored draft and sync behavior.
Do not promise that every async UI guard disappears: updating the correct
draft and notice is still application behavior.

### Implementation order and evidence

First settle the small typed API using headless, React and Expo examples.
Then expose the existing command lifecycle through shared client observations,

Acceptance covers zero/one/four observers; route unmount/remount during send

## 3. Semantic mutation targets

Replace the recipe's dependency on the insertion position in `intent.ids`
with a named relation the compiler derives and the client can verify. Reuse
that relation across the paginated thread and composite item declarations.
This revises the original item's decision to defer compiler participation;
the positional binding is no longer an acceptable final application contract.

The bound Quarry graph knows which table each insert targets. That is the
starting point. Proving which reserved ID belongs to a semantic target also
requires allocation order, cardinality and control flow. Two inserts into
the same table, a conditional earlier insert, or repeated inserts cannot be
resolved by picking the first matching table. Edits and removals need a
target relation even when they allocate no IDs.

Derive metadata from the same checked program used for execution and bind it
to the program/schema/certificate identity already carried to the client.
Generated TypeScript declarations should expose the corresponding typed
names; declarations alone are erased and cannot supply the runtime relation.
Audit `bound-api.ts`, the existing certificate/write-bound path and the held
program carrier before selecting the smallest runtime representation. No
second compiler pipeline or hand-maintained application registry.

Start with relations the compiler proves exactly. Unsupported or ambiguous
allocation must be explicit and preserve an intent-only item without a
seamless-row-handoff claim. It must never guess an ID or broaden query
membership. If presentation requires an explicit semantic choice, type that
choice from the generated facts rather than an integer slice offset.

Witness: reordering an unrelated insert in the chat post leaves its message
binding correct without an application edit. Also exercise multiple inserts
into one table, conditional/repeated allocation, unpredicted writes, no-ID
edits/removals and program replacement. Both projections reuse one domain
binding while retaining their independent row selection and authorization.
Carry the resulting effect identities forward to the compaction proof.

## 4. Automatic compaction of successful history

The target default is client-owned compaction of delivered, successful work.
Routine online sends must not accumulate permanently or require the user to
dismiss every success. Rejected/expired entries retain explicit dismissal;
queued and admission-unknown work remain recoverable. The account surface
should emphasize outstanding or failed changes, with any retained recent
successes governed by an explicit bounded policy.

Fable's proposal correctly separates the actor from the hook: a runtime
compactor can run independently of readers. The missing step is the scope of
its evidence. Consider an edit committed at 41: the live query has a body read
through 42, while a once-only query still holds the body read through 40.
The live indicator can resolve. The old one cannot. Deleting the shared intent
because the live query resolved would otherwise remove the old frame's only
description of its unobserved edit. A fresh capped page omitting a create is
also membership evidence for that page, not proof that its target arrived.

Design the compactor against these distinct obligations:

1. **Settlement custody.** A durable committed result is available to any
   issuing call still waiting for its own result. Deletion cannot turn a
   successful online call back into `queued` or race its result handoff.
2. **Effect custody.** Prove the relevant targets have authoritative state or
   removal through the commit under matching authority/program identity.
   A message row alone may not discharge fan-out or maintained effects.
   Empty write sets need their own proven rule. Overlay disappearance,
   `arrived`, a global sequence and elapsed time are insufficient substitutes.
3. **Presentation custody.** Preserve the meaning of older live/once-only and
   stored query frames. The implementation must either retain their minimal
   needed action evidence or safely invalidate/advance the affected stored
   representation under its existing contract. A once-only public image must
   not silently become a newer query. Counting mounted consumers is not a
   substitute, and moving unbounded history into a second store is not compaction.
4. **Recovery custody.** *(Moot after LLP 1018.004: there are no forwarded
   admission receipts or recovery handles. Compaction must still not delete an
   entry an inbox row's alias names, and must remove that row with it.)*
5. **Crash custody.** Decide and persist the eligible removal through the
   existing atomic carrier mutation. A crash, reopen, takeover or account
   replacement cannot expose half of the handoff or make a compacted draft
   reappear. Run from runtime/store progress with zero observers; rendering
   never schedules a durable mutation.

These are requirements for a deletion design, not a claim that today's
per-frame proof already meets them. First trace the minimum retained fields
and their owners through the current item frames, settling calls, outbox and
forwarding receipts. Specify the exact eligibility predicate and atomic
transition before adding a deletion call. Prefer extending existing custody
over a new journal or collection cache. If preserving old frames proves to
require a semantic change, document that change explicitly before coding it.

Unobserved successful writes can remain unresolved for arbitrarily long.
A compactor triggered only by observation therefore cannot claim a hard
bound on all storage. State the limit being achieved: repeated successes
whose effects have been discharged leave bounded durable history. Name and
measure the remaining exceptional/unresolved set; do not label the whole
store bounded or discard those records under a time limit. An absolute store
cap would additionally need an admission/backpressure policy.

Acceptance includes long repeated online sends after delivery; zero readers;
the two-frame example above; capped exclusion without target delivery;
predicted and unpredicted edits/removals; multiple affected rows and maintained
values; active result waiters; loss of the follower acknowledgment before and
after compaction; file/IndexedDB/Expo carrier crash/reopen; program replacement;
and rejected/expired entries remaining explicitly dismissible. Measure bytes
and operation cost as successes accumulate, including any replacement markers.
Amend LLP 1012 §7 and the current item decision in this separate code change.

## 5. Common item presentation

After recovery and target declarations simplify the templates, derive the
common display decision from the existing item facts: readable row versus
submitted draft, prediction, queued work, committed awaiting this image, and
failure. Keep those source facts and refusal details accessible. A `pending`
collection that also contains failures should have wording that matches its
contents; improve the actual decision a screen makes before choosing names.

The helper must preserve authorization/composite handoff, stable keys, omitted
timestamps for predicted creates, and the difference between commit and
delivery. It may derive a label or display choice; it cannot fabricate a
message row, rerun an edit, or decide a draft's editor lifecycle. Keep platform
markup and product copy where they belong. Prototype it in both templates and
retain it only if total application decisions and code fall. If a derived
helper buys nothing, record that result and simplify the callers directly.
