# LLP 1018.008.003: Reusable effect helpers with a closed runtime

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 2 TypeScript effect compiler, closed source identity, Ibex effect isolation, grant admission, effect authoring guide
**Author:** Codex, commissioned by Charlie Cheever
**Date:** 2026-09-10
**Revised:** 2026-09-10 (implementation selection: empty grants only; helper assembly deferred); 2026-09-10 (initial proposal)
**Related:** LLP 1018.008, LLP 1003, LLP 1002, LLP 1004, LLP 1021

## 1. Outcome and non-overlap

Effect authors should be able to share a small request-building or response-
parsing function between effects using ordinary local TypeScript imports.
An effect that requires no network access should declare `grants: []`.
Neither change requires module loading or code generation in the runtime.

At the initial research baseline, `lower/effects.ts::validateClosure` admitted
local bindings, a fixed global set, and module JSON constants. An imported helper
was a non-JSON capture and refused. `lowerEffect` rejected an empty grant list
even for a no-fetch body. The [packaged guide](../snapback2/packages/snapback2/guide/effects.md)
consequently instructed a provider-free test body to retain a placeholder origin
grant. Section 7 selects the empty-grant fix; helper restrictions remain unchanged.

LLP 1021 already owns lifecycle logs, journey providers and witnesses, deadlines,
and related reset/asset repairs. This RFC uses that final implementation for
qualification and does not duplicate its routes, runner, retries, or tests.
Design author: Codex, 2026-09-10; implementer of the selected slice: Codex,
2026-09-10, under the user's commission to revise the LLPs and implement the
improvements. Sections 2–3 and their helper-specific verification remain
deferred proposals, not current package behavior. Review advice does not
constitute author acceptance.

## 2. Build-time closure assembly

Start with the effect's `run` expression and resolve its referenced bindings
using the existing TypeScript program/symbol graph, rather than matching names
or concatenating imported files. Follow named relative imports to local
TypeScript functions and statically JSON constants. Include only the reachable
bindings needed by the effect. Transpile the closed result at project build
time with the existing compiler, and put it in the same private effect source
field the runner already executes.

First-slice module contract:

- Relative imports resolved inside the project source boundary; resolve real
  paths so symlinks cannot silently pull in unrelated host files. Named imports
  and aliases are supported; type-only imports are erased normally.
- Function declarations and constant function expressions may call other
  admitted helpers, and use the current effect globals or explicitly passed
  tools. The same closure restrictions apply transitively.
- Constant captures are statically JSON. Arbitrary module initialization,
  mutable module state, runtime import/require, Node built-ins, package imports,
  classes with static initialization, and dynamic export selection refuse at
  their original source locations. Do not evaluate user modules in `check`.
- Helper import/call cycles refuse in the first slice with the dependency path.
  Local recursion already inside an admitted effect keeps its current runtime
  deadline semantics; this restriction concerns cross-binding assembly.
- Refuse unresolved or computed dependency edges; never interpret them as an
  empty closure. Scope-aware renaming preserves shadowing and single evaluation.

There is no general bundler configuration, runtime module resolver, npm SDK
compatibility promise, or new dependency. This finite local-module boundary is
the first supported increment. Extending it later requires measured demand and
an authority/cost review, not a runtime fallback to host Node.

Proposed example (the imported helper capture is unsupported today):

```ts
import { effect } from "snapback2";
import { makeRequest, providerId } from "./provider-helpers";

export const notify = effect({
  grants: ["https://api.example.com"],
  run: async (payload: { body: string }, { fetch, meta }) => {
    const response = await fetch("https://api.example.com/send", makeRequest(payload, meta.id));
    if (!response.ok) throw new Error(`provider ${response.status}`);
    return { providerId: providerId(await response.json()) };
  },
});
```

The helpers are ordinary closed functions. Request IDs and capabilities are
passed from the current job; no captured host request or session is reused.

## 3. Lifetime and identity

Closure assembly emits one closed effect expression, preserving the current
per-job isolation boundary. Captured objects, helper-local mutable values,
timers, and any job tools must be freshly owned for each job invocation; helpers
cannot introduce shared module singleton state across attempts or principals.
Use the actual LLP 1003 host lifecycle rather than assuming a familiar Node
module lifetime. Review initialization and teardown explicitly.

The private effect identity includes the reachable helper source and constant
values after deterministic normalization. Changing a used helper changes the
identity, and outbox execution/`then` compatibility follows the existing
effect-change rules. An unrelated helper edit should not change it simply
because it lives in the same file. Output order is deterministic and cannot
reorder effectful authored evaluation. Old queued source must not quietly run
new helper code under an old identity.

Keep original definition/call sites for diagnostics in ignored compiler output.
Do not publish private provider code, grants, constants, or source maps into
public client metadata merely to make a stack readable. Tests must inspect the
public artifact boundary as well as successful compilation.

## 4. Empty grants mean no network authority

Accept an explicit empty origin list. Any `fetch`, whether written in `run`,
reached through a helper, or reached by redirect, still passes the current host
grant check. With no grant it refuses before transport. No static inference
of "this code does not fetch" substitutes for runtime enforcement.

Existing nonempty grant validation remains unchanged. Imported helpers add no
capability: the same logical-origin check, redirect policy, credentials policy,
job deadline, and frozen tools apply. No wildcard/default origin is supplied.
The default engine-less build remains engine-less; this RFC does not claim an
effect ran when it was only compiled or durably emitted.

## 5. Verification and deletion

Extend current compiler fixtures and LLP 1021's real-engine journey witnesses.
Verify transitive helpers, same names in two modules, aliases and shadowing,
an unused helper edit, a used helper edit, deterministic rebuilds, type-only
imports, and precise refusals for cycles, dynamic loading, mutable captures,
top-level side effects, escaped paths, and unsupported globals. `check` must
perform no application module evaluation or external request.

Run two jobs using the same helper with different payloads and principals;
make the first fail after mutating a local object and arming a timer. The second
must see no state or capability from the first. Cover retries/restart and a
helper edit while a continuation is pending under the existing identity rules.
An empty-grant effect that returns data runs; one that attempts fetch, including
through an alias/helper, refuses before any socket. A granted redirect outside
the declared origins still refuses through the same host.

Delete duplicated request/parsing code from at least two real effects and the
guide's dummy-grant workaround. If there are not two useful consumers, record
that and defer module assembly; empty grants can be evaluated separately.
Measure compiler latency, private effect source size, package bytes and the
unchanged engine proof. No compiler or helper assembly code belongs in the
offline twin, whose only effect behavior remains emission prediction.

## 6. Implementation boundary and review

Land only after reconciling with LLP 1021's final host and witness interfaces.
The compiler extension should be isolated from its runner changes. Update
LLP 1003's authoring contract and the current effects guide in the same eventual
implementation commit. Reuse current diagnostics and scheduled Hermes tests;
add no gate, registry, helper manifest, or runtime loader.

The review must settle the exact admitted declaration shapes and demonstrate
per-job initialization with the actual host. If safe assembly needs a broad
module system, reduce the initial subset to imported function declarations and
JSON constants instead of recreating a general TypeScript runtime.

## 7. Implementation selection — 2026-09-10

Implement only the empty-grant contract in §4. The compiler accepts explicit
`grants: []`, retains validation of every nonempty origin, and offers a no-network
body in its rewrite instead of inventing a placeholder capability. The existing
host already parses the empty grant set and mediates every fetch; no runtime
loader, host authority, client bytes, or LLP 1021 witness machinery changes.
Update the current guide and LLP 1003's authoring contract in the same change.

The repository survey found one real application effect, the chat template's
`delivery.notify`, plus retained benchmark copies of that same notification
effect. Compiler and engine fixtures exercise language behavior but are not
independent helper consumers. Therefore defer imported and same-file helper
assembly, used-only constant closure work, and their identity/lifetime changes
until at least two real effects justify the extension. The original proposal
stays here as research; it does not create a production module-system obligation.

Verification covers compiler acceptance (including an export alias and fetch
spelled globally, through tools, or through a local helper), malformed-grant
refusals, a real-engine no-network result across two jobs, and real-engine grant
denial before any loopback socket for global, destructured, aliased, and
helper-mediated fetch. Existing redirect-denial tests retain the hop boundary.
Compiler success alone is not a claim that an effect executed, and a no-network
result is not a claim of provider delivery.

Implementation evidence (2026-09-10, reused effects lane): 21 focused effect
compiler checks and all 289 compiler checks passed; compiler typecheck and
package build passed. The real Hermes host's two `empty_grants` tests passed:
two successful no-network jobs and four denied fetch spellings with no accepted
loopback connection; the complete 66-test effects host/runner suite also passed
with Hermes. `ref-check --verbose` reported no errors. The package guide
uses 79,182 of its existing 98,304-byte allocation; this compiler/guide change
adds no code to the complete local runtime.
