## 1. Summary

Snapback 4 serializes writes by holding its store's head across the whole
of each mutation. On SQLite that means `BEGIN IMMEDIATE` before the
program runs; on Postgres it means `SELECT … FROM _head FOR UPDATE`.

S0 measured the cost:

- serial time is `2.05 ms + 11.98 × RTT`, because 12 round trips are made
  under the lock;
- that is 120 commits/s at a 0.5 ms round trip, against 5,700/s for raw
  Postgres with 4 writers and 89,000/s with 64;
- the serial batch recovers only the flush.

The author commissioned the optimistic committer on 2026-10-19. This RFC
designs it.

One idea organizes the design. **The committer owns one serial stream per
store. Every durable write enters that stream as a member, and each member
reaches it in one of two ways:**

- **pre-executed:** run elsewhere at a snapshot, with its writes buffered
  and its reads recorded, then validated against everything that committed
  since;
- **in place:** run inside the stream's batch transaction, exactly as the
  reference protocol runs it today.

The stream commits members in batches, one transaction per batch: one head
update, one flush, and acknowledgement after commit. That gives two
properties at once:

- **Pre-executed members take their round trips outside the serial
  section.** This is the throughput win.
- **In-place members keep today's semantics exactly.** They cover hot keys,
  programs that are not eligible to pre-execute, and operations that are
  cheap to run serially. They are the fallback and the correctness
  reference.

The two children specify the machinery that pre-execution needs:

- [the write overlay](./3000.009.001.000.000.000-the-write-overlay.rfc.md):
  read-your-writes over buffered writes, with the reference's error and
  charge order;
- [read sets and validation](./3000.009.001.000.000.001-read-sets-and-validation.rfc.md):
  what a pre-executed member read, what a committed member wrote, and how
  the two are intersected.

The committer is store-neutral. On Postgres it removes the round-trip term.
On SQLite it moves execution onto parallel reader connections, and batching
amortizes the flush. Its build is gated by child C's sizing rule (S1a),
which is running now.

## 2. What exists

### 2.1 The reference protocol, today

From the inventory of the current commit path (`origin/main`, 2026-10-20):

| Step | SQLite `Engine::mutate` | Postgres `mutate_once` |
| --- | --- | --- |
| Replay check | `replay_bound` before and inside the transaction (`engine/mod.rs:921, 938`) | Before validation, then re-checked (`postgres/mod.rs:247–251, 277–283`) |
| Begin, serialize | `BEGIN IMMEDIATE` (`store.rs:384`) | `SELECT seq FROM _head … FOR UPDATE` (`postgres/store.rs:115`) |
| Time | Time-audience advance (`mod.rs:916`); writer time pinned (`946–950`) | None, which is a parity gap |
| Sequence | `next_seq` = `MAX(seq)+1` from `_commits` under the writer lock (`store.rs:714`) | Cached head + 1 (`postgres/log.rs:29`) |
| Program | `SAVEPOINT program`; `Runner::run`; expiry retirement; final-existence check (`mod.rs:999–1009`) | The same (`postgres/mod.rs:294–302`) |
| Tail | `record_commit` (change evidence and `_commits`), `partition::append` (`_log`), `effects::record` (`_outbox`, `_effect_presence`) (`mod.rs:1029–1031`) | Buffered, then flushed as one CTE that updates the head, `_commits`, `_log` and `_outbox` (`postgres/tail.rs:24–50`) |
| Refusal | `ROLLBACK TO program`, then a refusal receipt | The same |
| Receipt | `record_applied` and `bind_applied` (`store.rs:747, 752`) | `record_applied` (`postgres/store.rs:254`) |
| Commit | `store.rs:566` | `postgres/store.rs:212` |

### 2.2 Other commit producers

Fifteen other producers follow the same begin, sequence, record, append,
commit pattern:

- `expire`, `seed`, `load`, `restore` and `seed_sequences` (`engine/mod.rs`);
- job chunks (`job.rs:308–373, 497–529`);
- time-audience publication (`time_audience.rs:114–187`);
- timeline delivery (`timeline/work.rs:194–231`);
- row views (`row_views.rs:1011–1075`);
- expiry orphans;
- activation rebuild;
- dev reset;
- the Following launch;
- the host's smoke witness (`verbs/witness/smoke.rs:206–209`).

Writes that publish no sequence form a further class. Session mints and
invalidations, claims, lease renewals, steps, sweeps, asset views and
receipt-only reports each run their own transaction today.

## 3. The stream

### 3.1 One committer per store

- The committer lives in the process that holds the store's ownership lease
  (parent RFC §5). On SQLite that is the one `serve` process. Other
  processes (P2) submit members to it; they never commit themselves.
- It owns the writer connection: SQLite's single writer, or one dedicated
  Postgres connection. Execution uses reader connections.
- `serve` stops holding `FairMutex<Engine>` around mutations. Request
  threads submit members to a bounded queue and wait for their
  acknowledgement. Reads keep using reader connections as today
  (`serve_readers.rs`).

### 3.2 Members

A **member** is one durable unit that commits atomically and receives a
**revision**, its position in the stream. There are three kinds:

| Kind | Examples | How it reaches the stream |
| --- | --- | --- |
| **Mutation** | A Quarry mutation, a job chunk, an expiry sweep, time-audience publication, timeline delivery | Pre-executed when eligible (§4), otherwise in place |
| **Direct operation** | Session mint, invalidation, claim, lease renewal of work, step record, settle, asset view, receipt-only report | Always in place. These are short, typed operations from the durable-state families (parent RFC §3.2), not Quarry |
| **Administrative** | Activation, adoption, dev reset, seed, load, restore | In place, alone in their batch |

The store's **ownership-lease renewal** is the one exception (parent RFC §5,
§6.3). It is fenced by its token and is not application state. It must
never wait behind a batch, so it bypasses the stream.

### 3.3 Revisions and the public sequence

- Every member takes the next **revision**. That is the order of the
  stream, and the serial order the store's history is equivalent to.
- A member that publishes a commit, meaning it changes synced data, also
  takes the next **public sequence**, the sync watermark, in revision order.
  Public sequences stay contiguous, and a published watermark never has a
  gap below it.
- Revisions are internal. They appear in footprints (child: read sets), in
  the chain hash (parent RFC §5.4.2), and in receipts.

### 3.4 Batches

The committer drains its queue into a **batch**: up to N members, or
whatever arrived within a short window, sized adaptively against the write
SLO (§7). A batch is one store transaction:

1. **Fence.** The first statement takes the owner fence: `FOR KEY SHARE` on
   `_owner` on Postgres; SQLite's sidecar ownership plus `_owner` check
   (parent RFC §5.1).
2. **Members in revision order.** For each member:
   - **Pre-executed:** validate it against the in-memory window (child: read
     sets) and the members already accepted into this batch. If it passes,
     apply its buffered writes: rows, index entries, sequences, caps, effect
     keys, outbox, receipt. If it fails, it is rerun, either in place now or
     re-executed for a later batch (§4.3).
   - **In place:** under `SAVEPOINT member`, run it exactly as the reference
     does today, reading the batch transaction's current state. That state
     already includes every earlier member's writes.
3. **Tail.** One head update to the batch's last public sequence, the
   commits, log and change-evidence rows for each publishing member, and
   the chain-hash entries. All of it goes in one flight, using the
   Postgres CTE that exists today, extended to arrays.
4. **Commit, then acknowledge.** One flush covers the batch. Members are
   acknowledged only after the commit returns. An uncancellable COMMIT
   (parent RFC §5.4.1) means a cancelled replication wait is never
   acknowledged.

**Batch failure.** A database error rolls back the whole batch. The
committer then reruns each member alone, in place, in its own batch. Each
member's receipt makes that retry exactly-once (parent RFC §5.2). A member
whose single-member batch also fails returns the error.

**Refusals.** A member that refuses records its refusal receipt in the
batch, like any write. A pre-executed refusal is validated like any other
result, because a refusal depends on what the program read.

### 3.5 What stays fixed

The committer keeps every invariant of the parent RFC's §6.4:

- one total order per store;
- no gap below a published watermark;
- exact snapshots;
- whole-commit atomicity per member;
- receipts recorded once;
- the authority clock monotone in commit order;
- effects admitted only inside the commit;
- every durable transaction fenced;
- the same wire.

One addition holds them together:

- **The committed history is serializable in revision order.** Replaying
  every committed member, in revision order, through the reference engine
  on a fresh store reproduces every outcome and the final state, byte for
  byte. Each member's admission inputs are recorded: operation, arguments,
  principal, `now`, and placeholder resolutions.

That property is the qualification oracle (§8).

## 4. Pre-execution

### 4.1 Eligibility

A mutation is eligible to pre-execute unless one of these holds:

- it reads a value derived from its own sequence and branches on it, or
  otherwise lets such a value flow (the taint rule: parent RFC §6.3 item 5);
- its program is administrative (§3.2);
- its key has exceeded the conflict budget (§4.3);
- the overlay does not support one of its operations yet. During rollout,
  operations the overlay has not qualified run in place (child: overlay
  §5).

`check` computes eligibility statically for each operation and prints it
with `check --cost`. Eligibility never changes an outcome, only where the
operation runs.

### 4.2 Execution

A worker thread:

1. takes a reader connection;
2. opens a snapshot S: `REPEATABLE READ READ ONLY` on Postgres, or a read
   transaction on SQLite WAL;
3. reads S's revision inside that snapshot;
4. runs the program through the **overlay** (child), which records the
   **read set** (child) and buffers writes.

Sequence-derived values are **placeholders** (parent RFC §6.3 item 5).
`now` is the admission time, fixed before execution.

The result is a **pre-executed member**:

- its outcome: data, or a refusal with its site;
- the meter observations;
- the read set;
- the buffered write set, with its footprint;
- the effects;
- the placeholder sites;
- `now`;
- S.

### 4.3 Conflicts and the conflict budget

A member fails validation when a revision in `(S, current]`, or a member
already accepted into this batch, wrote into its read set (child: read
sets). It is then **rerun**:

- It is re-executed at a new snapshot and submitted again.
- After `c` conflicts (default 2), it runs **in place** in the next batch,
  so a hot key makes progress at the reference's speed.
- The committer keeps a small decaying score per footprint key. A key
  whose score crosses a threshold routes new members that read it straight
  to in-place execution. Contention degrades gracefully to the serial
  protocol rather than into retry storms. S0's single-hot-counter cell,
  424/s, is the floor this protects.

A rerun discards the previous attempt's effects, overlay and meter
charges. The outcome reported is the final execution's, as it is under the
reference.

### 4.4 The window

The committer keeps the footprints of committed revisions newer than the
oldest live snapshot, in memory (child: read sets §4). A pre-executed
member whose snapshot is older than the window, bounded by age (default
2 s) and memory, is rerun rather than validated. Footprints never leave the
server: a key range can name a hidden row (LLP 3000.009 §7.1).

## 5. Placeholders and resolution

Sequence-derived values include:

- effect ids `effect-<seq>-<n>` (`runner.rs:688`);
- Following admission tokens (`timeline.rs`);
- any value a program builds from its sequence.

In a pre-executed member they are **placeholders** carried by the overlay.
At batch commit the committer resolves each one to the member's actual
public sequence. It rewrites every row image, index entry, outbox row and
comparison that contains a placeholder, in the same batch transaction.

A placeholder that reaches a key is resolved **before** validation, so
footprints are always concrete. Placeholders never reach a client: the
response is built after resolution.

## 6. Time

- `now` is assigned at admission and never read from the store.
- Time-audience pins are monotone. A batch applies the maximum pin of its
  members, and pins are exempt from conflict detection (parent RFC §6.3).
- The monotone-clock rule (§6.4) holds in batch order. A pre-executed
  member whose `now` is below the batch's committed pin is rerun.
- Postgres gains the time-audience advance and the writer-time pin it lacks
  today (§2.1). That is a parity item for P1.

## 7. Batch sizing and latency

The batch window adapts. The committer measures each batch's commit
latency and its members' queueing, then picks the largest N whose p99
member latency (queue + validation + commit) stays within the write SLO
(child C §6: 100 ms). It shrinks N when the SLO is at risk.

An idle store commits a lone member immediately. So single-writer latency
is one execution plus one commit, not a window. S1a's per-N curves seed the
defaults.

## 8. Qualification

1. **The replay oracle** (§3.5). Under randomized concurrent load, with
   seeded generators from `snapback4-difftest` widened to concurrency:
   - record the admission inputs of every committed member;
   - replay them in revision order through the reference engine on a fresh
     store;
   - compare every outcome and the final state, on both stores.

   One disagreement is a defect.
2. **The overlay differential** (child: overlay §6). The same program runs
   in place and pre-executed at the same snapshot with no concurrency, and
   must produce identical outcomes, meters and write sets.
3. **The validation adversary** (child: read sets §6). Generated pairs of
   conflicting mutations are injected between snapshot and validation for
   every kind of read: point, range, count, absence, sequence, cap, effect
   key, authority fact. Each must be caught.
4. **The simulator's seven invariants and the device suites,** unchanged,
   with the committer enabled.
5. **Faults.** Kill the committer mid-batch, fail a batch, roll back a
   batch, take over ownership mid-batch, and race commits against
   termination (W9). Receipts must make every retry exactly-once.
6. **Measurement.** Child C's commit-path cells, rerun with the real
   committer on the Hetzner pair (database on `expo-build-450a`, server on
   `expo-build-450b`), against the reference and raw Postgres.

## 10. Alternatives

- **Keep the reference and cut `k`.** Batch the reads inside the lock and
  send the tail in one statement. Plausibly about 4 round trips, so about
  500 commits/s at 0.5 ms. It is worth doing inside the in-place path, but
  it misses the bar (parent RFC §7).
- **Database-native concurrency with an ordering stage** ((b) in the parent
  RFC's §6.3). It needs a contiguous-prefix publication and snapshot
  protocol that no one has designed, and Postgres's SSI cannot see absences
  in Snapback's generic layout the way the interpreter can.
- **Run the interpreter inside Postgres.** Managed providers do not allow
  custom extensions.
- **Optimistic execution without in-place members.** Pure optimistic
  concurrency control, as Convex is commonly described. Hot keys would then
  degrade into retry storms, and administrative operations would need their
  own path. In-place members make the reference protocol the fallback for
  free.

## 11. Open questions

1. Whether direct operations, which are cheap but numerous, should
   pre-execute too. This RFC runs them in place, where they cost about 1–2
   round trips each inside the serial section. S1a's 30% non-head-write cell
   says whether that matters.
2. The conflict budget, the window, and the batch defaults. S1a and K3 set
   them.
3. Whether the SQLite build enables pre-execution by default, or only for
   write-heavy stores on many-core hosts. K3 measures it.
