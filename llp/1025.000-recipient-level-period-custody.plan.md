## 1. The invariant

A `periodUnread` row represents one live, unread, replay-eligible message for
one current recipient membership incarnation and source period. It contains
immutable message id, source author, recipient, conversation, membership id
and period start. A `periodChats` row exists exactly when at least one such
row shares its recipient/conversation/membership/period key; its positive
`total` equals that number of rows.

Source admission, read, unsend, expiry, leave and administrative removal all
pair their custody changes within their source transaction. Pruning uses the
same helper. The maintained recipient/period counts therefore stay exact at
each commit, including between job chunks. Their sum is not accumulated from
an earlier eligibility snapshot.

In Clique, `periodUnread` is also a subset of its existing `pendingRead` rows:
send creates both; read/removal deletes both; period pruning removes only
period custody. Administrative removal uses that already capped,
admin-readable `pendingRead` range to enumerate all corresponding private
period rows by point lookup. This avoids a nonuniform private range scan.
Any future writer must preserve the subset as well as the primary invariant.

## 2. Schema and authority

`periodUnread` keeps the existing unique message/recipient key and two caps:
50 by recipient/conversation/membership and 50 by message. Its immutable
`author` is copied from the actual message; Clique's insert rule requires that
shadow to equal the viewer and checks the actual message author and current
membership. Read/delete admit the recipient, a current admin, or the source
author while still a current member. The shadow avoids fetching a rich
message merely to authorize a period-row read; it cannot create authority.

```q
table periodChats:
  total: int
  recipient: principal
  conversationId: conversations
  membershipId: memberships
  periodStart: time
  unique byRecipientConversationMembershipPeriod: recipient, conversationId, membershipId, periodStart
  immutable recipient, conversationId, membershipId, periodStart
  read <- exists memberships[.conversationId, viewer]
  insert <- exists memberships[.conversationId, viewer]
  update <- exists memberships[.conversationId, viewer]
  delete <- exists memberships[.conversationId, viewer]

maintain periodUnreadByRecipientPeriod: count periodUnread by recipient, periodStart
  read <- deny

maintain periodChatsByRecipientPeriod: count periodChats by recipient, periodStart
  read <- deny

maintain membershipCountsByPrincipal: count memberships by principal
  read <- deny
```

The membership cap is `cap 1000 by principal`; its count maintain makes the
50-member group insertion constant work per membership rather than scanning
1,000 candidate memberships for each insertion. The separate per-conversation
cap remains 50. Follow and compact-follow-mirror caps remain 500.

**Explicit privacy decision.** Clique already makes `unreadCounts` readable to
current conversation members. The new chat total has that same audience and
additionally discloses the period split. Ordinary peers can read that scalar
while the underlying period rows stay private. Recipient-wide totals remain
owner-only. Current admins gain period-row visibility needed for removal,
aligned with their existing lifetime `pendingRead` access. Outsiders and
former members gain neither aggregate nor source access. The distilled
compiler fixture deliberately retains its mechanical public/allow rules;
production authority is tested against the copied correction.

**Refinement from the draft.** The draft read a membership-period maintain to
check zero transitions. On the production private schema, its client reads
expanded maintained-address custody to 63,051,476 closure bytes for a send.
An explicit chat `total` performs the same zero transitions without those
maintained point reads. The redundant membership-period maintain was deleted.
No receipt term or ceiling was removed to make the recipe fit.

## 3. Transitions

| Transition | Atomic custody work | Bound |
| --- | --- | --- |
| Send | If replay is off, insert one unique unread row per non-author recipient; create chat total 1 or increment it | 50 recipients |
| Read | Delete each selected unread row; decrement its chat or delete it at total 1 | 50 per recipient/chat/incarnation |
| Unsend / expiry / admin retraction | Clear eligible custody before deleting message and poll companion; native delivery emits removal metadata | 50 recipients |
| Leave | Enumerate the recipient's capped period rows; clear each chat/source pair before membership deletion | 50 |
| Admin removal | Enumerate capped `pendingRead`; point-read and clear each corresponding period row before lifetime/membership deletion | 50 |
| Rejoin | Insert a new membership id with no old custody | 0 custody writes |
| Post create / delete | Stamp replay eligibility; update author/period counter in the same transaction only for eligible original posts | 1 |
| Replay | No source-period activity admitted; current follow mirror still updates; sweep also checks replay mode | existing bounds |
| Old-period prune | Call the same paired source/chat helper | 50 per chunk |

`queuePeriodUnread` is idempotent for a message/recipient pair. Clearing a
source first reads its chat and requires a positive total; total 1 deletes the
chat, otherwise the total decrements. A missing chat or nonpositive total
rejects the transaction instead of committing a partial repair.

All four distilled send variants call the helper. Clique's shared text/photo/
clip/view-once/poll send path does too. All six original-post insertion
branches stamp `digestEligible`; deletion decrements only an eligible row,
so deleting replay content cannot subtract someone else's period activity.
Key fields are immutable. No unpaired delete or key-changing writer is added.
Conversation deletion remains refused: 50 members × 50 pending rows exceeds
the 2,048-write ceiling and requires its own authored job.

## 4. The job

The two-stage `periodDigestSweep(cutoff)`/Clique `digestSweep(cutoff)` retains
its single durable `.periodEnd` argument and `first 1` recipient chunk:

1. Floor the supplied cutoff by the configured period. Check replay and the
   unique recipient/period receipt. Read the new-follower count and the two
   recipient counters. Fold all 500 current follow edges through their compact
   author/period post counters into one transaction-local scratch row.
2. If any count is nonzero, insert the unique digest, push log and effect in
   that transaction. Delete scratch before committing. Quiet recipients write
   no receipt, log or effect.
3. Only after all recipient chunks, prune period rows strictly older than the
   just-completed bucket. Invoke the paired helper so removing the last old
   source removes its chat in the same chunk.

There is no independent chat-prune stage: that draft design temporarily left
orphan chat rows between chunks and duplicated cleanup logic. The cutoff and
strict age test preserve this job's completed period while it remains queued
or running at the FIFO head. Parking removes it from that queue: a newer
scheduled or manual digest may prune older buckets before an operator resumes
the parked job. Resuming an old cutoff then reads whatever currently eligible
custody remains; this recipe provides no retention lease across parking.
That unresolved failure-order case is why LLP 1025.005 remains shelved.

## 5. Correctness and limits at emission

Eligibility-changing commits and the final digest chunk serialize. The
recipient counters thus reflect every paired source transition committed
before that chunk. Membership loss cannot leave countable old-incarnation
rows; rejoin does not resurrect them. The current-follow recount similarly
excludes unfollowed or deleted posts at emission.

The receipt, log and effect share a transaction and the receipt is unique on
recipient/period. Resume, restart or manual replay rereads it before writing;
the effect's stable id is the provider idempotency key. This proves logical
emission once, not unconditionally exactly-once external I/O.

Expiry depends on successful synchronous timer cleanup. LLP 1025.001 pins a
turn clock and skips chunks while due timers remain. It cannot promise that
nothing past expiry exists after a rejected/skipped timer or a target that
merely enqueues asynchronous cleanup. The recipe uses a synchronous deletion
mutation and paired custody cleanup; inspection of timer rejection remains
necessary. No multi-chunk global snapshot or wall-clock catch-up claim is made.

## 8. Copied Clique correction and guides

`recipient-period-custody.patch` applies after the retained production
correction stages and before `owner-inspection.patch`. The benchmark app is
never edited. `recipient-period-inspection.patch` adds only test queries and
an adversarial author-forgery mutation; neither inspection patch ships as
application behavior. The correction README gives the exact application order.

The retained app also used a removed `tombstones` declaration. The patch
replaces that annotation with native `messageCustody` on `messages` and moves
its inbox drain to that generated log. Its authored delivery/read history
remains application state for existing thread and receipt operations; it no
longer claims engine tombstone semantics. Native custody captures the original
audience and emits removals, including to departed recipients. Every affected
writer is included in the complete certificate above.

The schedule, fanout and maintain cards now teach recipient counters and an
explicit positive chat-total row for distinctness, and state the aggregate
disclosure. Existing card prose is compressed to stay within the unchanged
package byte allocation. No alternate scheduler, cascade, defer or receipt
exemption was needed.
