# LLP 1018.003.000: Composed items and image-bound observation

**Type:** Decision
**Status:** Implemented (extracted from the qualified parent §§7–11; document transfer and references checked 2026-09-08)
**Systems:** Snapback 2 query item projection, selected-row and page-membership evidence, shared outbox observation, chat React/Expo templates
**Author:** Codex, under Charlie Cheever's client-shape commission; extracted following user-supplied Claude Fable feedback
**Date:** 2026-09-08
**Revised:** 2026-09-08 (current contract extracted from LLP 1018.003; no new product behavior or qualification)
**Related:** LLP 1018.003, LLP 1018.003.001, LLP 1018.000 §4 and §8, LLP 1012 §5 and §7, LLP 1002 §9

## Summary

A query optionally publishes one item list with its readable rows, submitted
drafts, prediction marks and attributed actions. The query entry owns the
join and immutable publication. Exact row-image evidence settles each item's
indicator; the durable outbox currently retains every terminal entry until
explicit dismissal.

This is the implemented contract extracted from parent §§7–11 at `dc0367b45`.
[Historical reviews and qualification](./reviews/1018.003-implementation-record.md) remain bound
to their original revisions. The [follow-up plan](./1018.003.001-client-follow-ups.plan.md) changes the
future retention default and removes remaining application work in separate
changes. Its proposals do not change the contract recorded here.

## Context

Screen joins duplicated outbox attribution and prediction matching. Moving
retirement into mounted hooks made subscriber count affect durable state.
The implemented design centralizes the join and binds observation to the
image each reader actually holds. This is useful for predicted as well as
unpredicted writes: global overlay progress cannot update an older query's
body or page membership.

## 1. One list

The item projection reads:

```tsx
const thread = useQuery(api.deliveries.thread,
  { conversationId, c: null }, { items: threadItems });

return <>
  {thread.reason && <p role="status">{thread.reason.message}</p>}
  {thread.items.map(item => <Message
    key={item.key}
    message={item.data}
    draft={item.draft}
    pending={item.pending}
    predicted={item.predicted}
  />)}
</>;
```

React and Expo use the existing `useQuery`; headless code uses
`client.observe(api.deliveries.thread, args, { items: threadItems })`.
The optional projection runs inside that query entry before its immutable
publication. There is no `useCollection`, `observeCollection`, or separate
collection subscription lifecycle. Both existing APIs accept this option. A pure internal `attachItems(spec, args, data, inputs)` performs the
join; calling a pure function over two independently changing hook results
would not establish this publication contract.

The result retains the underlying query's `data`, `status`, `reason`,
`receipt`, `freshness`, `local` and `refusal`, and adds `items`. `data` is still
the named query's result; the receipt describes that result. `items` is its
presentation with attributed intents, never a second certified result. A
pending-only item cannot turn an unavailable query into `ready`, count as a
server row, or grant completeness to a composite. An empty `items` list does
not mean the query is loaded or exhausted.

An item has one stable `key`, `data` when there is a readable selected row,
`draft` when there is a separately labeled submitted create payload,
`predicted` for a contributing local overlay, and `pending`, an ordered list
of its unresolved actions. Each action carries its intent ID, operation,
state, SDK label, optional refusal, and whether explicit dismissal is
available. The same action can be displayed by several observations;
dismissal addresses its durable intent, not a row or component instance.

Never construct a fake message to fill a row type. A submitted body is a
draft; it has no server timestamp, author assertion, media custody or read
permission. `Message` renders the readable row or the labeled draft and the
attached actions. It does not search another collection. The outer keyed
element persists when a draft becomes a predicted or server row. A predicted
create shows no timestamp; an existing message can keep its authoritative
timestamp while an edit is pending.

## 2. Correspondence

The current chat binding, shared by React and Expo:

```ts
export const threadItems = defineItems(api.deliveries.thread, {
  table: "messages",
  select: delivery => delivery.message,
  order: "reverse",
  create: {
    op: api.deliveries.post,
    belongs: (args, query) => query.c === null
      && args.conversationId === query.conversationId,
    key: intent => intent.ids[0],
    draft: args => ({ body: args.body }),
  },
  update: {
    op: api.deliveries.edit,
    key: args => args.messageId,
  },
  remove: {
    op: api.deliveries.unsend,
    key: args => args.messageId,
  },
});
```

`defineItems` is a type-inference helper for an inert, immutable data
declaration. It supplies no fluent builder, registration, transport or
arbitrary reducer. The query reference types the selector and query arguments;
each operation reference types its callbacks. Inference is checked against the
actual API declaration, without `any` casts in the app.
An object result adds `rows: view => view.messages` before the same selector;
the query still certifies its whole message/count/preview result. The shipped
`conversationItems` uses this form, and `threadItems` covers the independently
authorized paginated fallback. Both select the original message object.
`select` returns one existing row or null, with its intrinsic `id`; the
explicit table and that ID identify the
row for attribution. Its selected fields come only from the query. The first
slice handles this row-preserving projection, not arbitrary aggregates,
flattened multi-table records, or compiler-generated result-path provenance.

The create binding describes two app facts: which list a send belongs to,
and which pinned row it will become. `ids[0]` is explicit because this
recipe's mutation inserts the message first. It is not an SDK convention for
all mutations: conditional or multiple-create programs need an exact binding
or retain an intent-only key without a seamless-handoff claim. Confirm the
binding against the operation's queued and committed results in its existing
journey. Source checks after review confirm that `sliceIds` and the Rust
`replay_slice_ids` hand the entire range, starting at `from + offset`, to
`context.new_ids`; `intentName` is separately `grant:offset`. The existing
outbox tests assert the first result ID equals `entry.ids[0]`. That supports
this recipe binding, not a general first-created-row convention. Do not
infer it from an operation name, scan arbitrary JSON for
`messageId`, or call every reserved ID a row that was created.

For unpredicted writes there is no evaluator evidence from which to derive
that app relationship. A small typed declaration is the honest boundary.
Updates and removals attach to a selected row's key. If the target is not
readable in this view, their recovery stays in the shared outbox; do not
resurrect an old body to display a pending action. A predicted removal follows
the twin's result: the row disappears from the list. The first slice makes
that action outbox-only until its target is readable again, rather than
inventing a body-less row whose query membership is unknown. The chat app
must render an account-level pending/failed-changes surface on both platforms;
an accessible SDK method by itself is not a recovery affordance. The binding
may later name an explicit scope for an action with no visible target, but this slice adds
no inferred membership, inverse query, or extra read.

`select` drops null bodies. `order: "reverse"` reverses just the received
page for display; it never sorts on a client clock. The kind-scoped query
continues to own event selection and the bounded page. A page containing 50
tombstoned messages can display zero items and still have `receipt.next`.
Preserve that opaque continuation and its source unchanged. In this binding
only `c: null` owns create placeholders; older pages do not each append the
same pending sends. Updates still attach to their visible target on any page.
No automatic page filling, new cursor, count, or cross-query history merge is
introduced.

One small domain declaration replaces the original parent §6's
"no helper modules" rule. The SDK deletes the application reducer; the
declaration does not rehouse it. Count this file with both screens when
judging whether application complexity fell. If the binding grows into the
old `shared/log.ts`, reject the abstraction.

## 3. Shared publication

The client's existing account session owns one current outbox projection and
indexes its associations from the raw durable entries. Collection joins use
those entries, not an already filtered global pending list: an action that
is complete for another presentation may still lack this view's target
evidence. The existing query entry owns the optional item projections.
It retains at most one derived publication per attached spec identity, with
one shared underlying query/value/transport. Different specs add pure
projection work, not subscriptions to a second source or new query lifecycles,
with one declared exception: an items declaration's history (LLP 1018.006)
opens the named history query while the composite's receipt is partial and
releases it when it is not; the composite's own entry, value, and receipt are
untouched.
They leave when their last attachment leaves; an inactive spec keeps nothing
alive. The ordinary query's first/last-subscriber lifecycle stays LLP
1018.000 §4's. This is derived output memoization, not another authoritative
result cache or durable queue.

**Input-frame contract.** The architecture lane already has `StoreRevision`
(`incarnation`, `revision`), atomic `StoreChange` batches, `TwinStore.sync`,
and shared-entry epoch fencing. Reuse those. A private frame captures the
query value, exact selected-row evidence, effective overlay attribution, and
raw outbox entries. Local evaluation captures these synchronously from one
synchronized twin image. Actual immutable `RowImage` objects survive evaluator
aliases and nested point reads; a copied object with the same ID cannot borrow
their provenance. A private WeakMap binds the frame to its event. Publication
clones the public value and rebinds witnesses to the cloned row objects;
equality reuse rebinds them to the equal objects the reducer preserves. Immutable
captured ledger records are shared, not cloned afresh for every query. The twin
reuses its ordered ledger until outbox records change. A spec/ledger index maps
targets and intent IDs once and orders creates by their unresolved sequence cut.
Warm pages inspect their targets and unresolved creates, not every old send.
The outbox observer compares history once per client update, independently of
its distinct operation-status slots.

For a direct server delivery, only its own returned `$row` references inherit
its sequence. A later pool read cannot upgrade an older returned body. The
admitted delivery is joined with the current ledger under the existing authority
and entry fences. If a local evaluator is unavailable, or a one-shot query keeps
its original value, newer ledger entries may attach work to that value while its
original row witnesses stay fixed. This refines the first draft's unnecessarily
strict same-revision requirement: the value and its proof are inseparable;
ledger progress may only attach work or resolve it against that proof. It never
supplies a newer row observation.

The shared entry's publish operation replaces the base snapshot and all its
attached item projections together, then notifies readers. A refresh can
retain the previous publication while computing its successor. Reset invalidates both
immediately. Authority/program and entry-epoch fences reject obsolete
completions. Keep one refresh in flight and coalesce later requests as the
existing entry does; no cross-query barrier or global matching of commit
numbers. The required internal frame is not exposed as another public
snapshot type. The capture is qualified by the carrier and multiple-observer regressions;
an option on `observe` alone would not establish coherent inputs.

For each committed input revision, the SDK:

1. Selects readable rows, preserving their identity and specified display
   order, and indexes their `(table, id)` addresses.
2. Attaches contributing prediction references by that exact address, using
   the same local revision as the value. A partition-wide prediction list
   cannot mark unrelated query rows. `predicted` does not mean every pending
   action on the row was predicted, and its absence does not mean fresh or
   server-confirmed.
3. Attaches declared create/update/remove actions, in durable FIFO order.
   Several edits to one row remain several actions. A failed earlier edit
   does not hide a later queued edit. An overlay and a declared binding for
   the same intent produce one attachment, not two. The displayed body is
   exactly the selected query/twin value: the presenter never reapplies edit
   arguments or chooses an older draft over the twin's FIFO overlay result.
   The row's prediction mark denotes a contributing effective overlay, not
   that every attached action was predicted or confirmed. Masked overlays
   cannot supply that mark.
4. Adds matching creates with no readable row as explicitly labeled
   intent-only items, in an unsorted pending tail. Uses the bound pinned ID
   as their key when it is known. When that row becomes readable, publishes
   one item at its query-defined position under the same key.
5. Publishes once after the source query value, prediction attribution and
   outbox inputs are consistent. A row cannot appear once as a prediction
   and once as a pending bubble in the same publication.

No callback from a render, `getSnapshot`, selector, or subscriber writes the
outbox. Store changes arrive after their atomic swap, not from intermediate
reads. Fence async work by account/session, program and source revision;
matching server sequence numbers alone are insufficient. Preserve item and
array references when their values and attached work are unchanged. Do not
make every row scan every intent; index once and join in work proportional
to the page and relevant associations.

On a denied/refused query, the reducer clears query-origin data. A scoped
create may still display the current account's own submitted draft, explicitly
labeled, while `status` remains unavailable and the denial/refusal remains
visible. Unavailable/offline with no held answer can likewise show an owned
draft. This is not permission to retain a previously read body. Target-less
updates/removals remain reachable through the account outbox surface.
Account replacement/reset invalidates the derived snapshot before successor
values publish; none of the retired account's drafts escape that fence.
Delivered-history results retain exactly the reducer's existing permitted
data and retained/stale facts; do not reinterpret a permitted retained result
as a fresh denial. Item labels accompany the query's reason and never override
its completeness, provenance or freshness.

## 4. Observation and retention

**Implementation rule, 2026-09-07.** A mutation's terminal response proves
that it committed. A row observation proves that a particular readable
image includes that commit or a later state. These are separate facts:

```
committed(intent, s) + observed(table, id, through >= s)
    => this item's successful action no longer needs a pending indicator
```

`through` is the owner's read sequence for that exact row image, not the
row's last-change version and not the client's highest sequence. The
evidence travels with the query value that uses it. Matching requires the
declared target, the current partition and authority, and fresh evidence
beyond the intent's admission. A retained answer or an unchanged admission
baseline cannot acquire a newer stamp from another row's arrival. The
direct server path derives it from accepted row references; local reads use
the authoritative base actually used by the twin, beneath any still-valid
later prediction. Absence is explicit negative evidence, never a row
missing from a capped page or a local predicted deletion.

For example, an edit commits at 41. A message body still read through 40
keeps its "Sent" indicator even if an unrelated delivery advances the
client to 80. The message read through 42 resolves that edit. It need not
equal the submitted body: another authorized edit may already have
superseded it. A second local edit can still predict over that confirmed
base and keeps its own action attached. No minted ID or write-set inference
is required for an in-place edit that creates no rows.

The corresponding lifetime rule removes the online special case:
`run()` returns its terminal response without dismissing the durable entry.
Online and offline admission therefore share one ledger and one lifetime.
Item projection is read-only; neither a subscription nor rendering schedules
deletion. The same keyed publication replaces a draft with its readable row
and removes a resolved indicator. Zero, one, or four readers cause exactly
zero automatic dismissals. Explicit dismissal remains a user action, as in
LLP 1012 §7; failures remain recoverable after the issuing call returns or
the component unmounts.

This deliberately retains successful terminal history until explicit
dismissal, matching the existing queued-write contract. It makes no bounded
history or automatic storage-compaction claim, and does not add a second
queue, acknowledgment ledger, timer, or per-screen settlement effect. The
account recovery surface exposes dismissal, including committed entries.
Any later automatic compactor must be specified separately and must not
erase unresolved work or use mounted-reader count as delivery evidence.

The shared outbox snapshot comes from `client.outbox.observe()`. `useOutbox`
and `useMutation` read it; status is shared per distinct operation. No-store
writes retain their direct result contract. Store-backed online and offline
writes both retain terminal entries until explicit dismissal. Queued entries
cannot be dismissed; rejected and expired entries remain actionable.

Explicit dismissal may race the call waiting for its own terminal result.
The drain keeps that result in a bounded waiter slot so the call still answers
from its committed/rejected outcome. Slots exist only for waiting calls and
close on every exit and lifecycle reset; they are not another terminal history.

The shared outbox snapshot exposes the raw terminal history, with one status
projection per distinct operation and one source subscription per client.
The templates expose it in **Changes on this device**, including explicit
dismissal of committed records and changes whose target is absent. Only query
items hide resolved indicators. This replaces the initial proposal for a
globally filtered outbox: each view owns its own observation evidence, so the
ledger needs no second definition of successful presentation. Retained
terminal records are a storage cost, not a bounded-history claim. Automatic
successful-record compaction is a separate policy decision and cannot hide in
this read projection. The [commissioned compaction change](./1018.003.001-client-follow-ups.plan.md#4-automatic-compaction-of-successful-history)
must replace the indefinite-success default with a proved deletion rule.
Until then, the functional item boundary is implemented and the retention
default remains incomplete.

Distinguish settlement from visibility when deriving an item's presentation:

| Evidence | Item/action presentation |
| --- | --- |
| Queued, with a contributing preview | One preview and its pending action; no create timestamp |
| Queued, without a preview | One labeled submitted draft if scoped here |
| Committed, no sufficient arrival evidence | Committed / awaiting delivery; no second send and no invented row |
| Readable authoritative target supersedes the action | One readable row; the completed indicator leaves |
| Current-authority target absence/removal at or after the commit | No invented visible-row claim; the completed action can leave the projection |
| Overlay retirement by generic cursor progress or another reserved ID | Custody progress only; it cannot settle this item's delivery indicator |
| Patience alone drops a prediction | No proof of row arrival; preserve the committed outcome for recovery |
| Rejected or expired | Failed action remains, with explicit dismissal |

**Target-evidence rule.** For an in-place edit, delivery is resolved by the
selected target's authoritative base at or after the commit, or an explicit
current-authority negative/tombstone for that target at or after the commit.
For a removal, only the corresponding negative/removal resolves absence;
a still-present target does not. Match `(table, id)`, partition, authority
and program identity. The evidence must be bound to the image used by this
frame: a newer global `seq`, a halo row, an unrelated fan-out ID, equality of
body strings, or `receipt.source = twin` is insufficient. A subsequent queued
edit may still overlay that base; it remains attached after the older committed
edit's indicator retires. Successful writes need not leave their old value
unchanged forever to count as observed/superseded.

Use the store's existing row/negative sequence facts and the admitted query's
selected-row provenance where sufficient; a receipt's overall sequence must
not be assigned to each retained/overlaid row. The implementation uses a private selected-row evidence sidecar; it adds
no wire field or compiler declaration for observation proof.

**Page-membership rule.** Whether to synthesize an unplaced create is a
separate question from whether a displayed row reflects a write. A complete or
capped owner answer to this exact query, freshly observed through the commit,
can select a page that omits the target. That committed create then belongs only
in device history; it must not return as a draft when a page advances or the
store reopens. This is a membership decision, not a claim of row arrival or
absence. A newer pool, sibling-query delivery, or halo cannot advance the old
page. Partial, denied, retained, clock-only and invalidated held answers provide
no new membership proof. Identical envelope replay does not manufacture fresh
observation order. Each stored answer privately retains its last qualified
membership observation as `{ through, order }`. This constant-size metadata
advances within the existing carrier commit, survives a partial or denied
replacement and later coverage invalidation, and travels in the query's private
frame. It never enters the wire or public answer. A legacy complete answer
records its existing order before losing coverage; migration cannot mint a
new observation. Cold reopen therefore preserves the same decision without
per-intent retirement records or a read-side write. An owner partial frame may
carry this query's earlier membership observation, never a later concurrent
answer's evidence. Coverage reset clears it with the stored answer.
Retained, clock-only and invalidated answers likewise cannot upgrade an old
point absence with fresh observation order. In-place indicators still require the selected row's own
proof even when this query's membership sequence is newer.

A pending create also retains its submitted `draft` alongside a selected `data`
row. During a composite-to-history authorization transition the screen can show
that owned draft while the independent history observer reattaches; it renders
query-origin data only from a usable composite or authorized history. This
preserves the key without borrowing uncertain row contents, author, or time.
No new lifecycle or collection cache is needed for the handoff.

The current `arrived` flag is not a per-item proof. The existing overlay
retirement includes negatives and cursor-chain progress; the pinned-ID
arrival loop also recognizes any reserved ID, including a fan-out row. Do
not read those as "this displayed message was returned by this query."
Use them for their existing custody meaning and require the selected target
to be readable before a draft becomes a row. A negative must not resurrect
the submitted body; a committed unpredicted edit, which may mint no IDs,
must not wait for a nonexistent inserted ID.

The implemented private frame supplies that evidence without changing the
wire. The no-ID edit tests advance an unrelated row first, then the displayed
target, and retain a once-only view of the old image. The live item resolves
only on its target update; the once-only item keeps its action. Both retain
the terminal intent. Missing proof keeps the action visible.
## 5. Witness and limits

The functional item boundary is implemented and qualified. **The overall
client elegance target is not met.** The original 60-line screen goal was
missed; added responsibilities explain the count but do not satisfy the goal.

These five files total 536 lines; this is not the entire application. Include
composers, root props and any replacement helpers when comparing a change.
Show both actual line counts and responsibilities removed. Moving recovery
to another application helper or compressing JSX does not count as deletion.
The target-ID declaration still exposes `ids[0]`; successful history still
accumulates. The follow-up plan addresses both.

Required behavior includes predicted and unpredicted creates; no-ID edits;
removal and missing-target recovery; stable keys; denied/partial/composite
handoff; old once-only images alongside newer live ones; current-account
fencing; and zero/one/four observers without automatic dismissal. The item
and carrier tests pin these distinctions. Missing proof preserves the action.
