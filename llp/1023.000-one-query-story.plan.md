Insights loads and refreshes reflect owner state as required by Clique M8.
Offline it shows a qualified held value or explicit unavailability. The same
client can open an unconsumed once image when online; offline once media stays
null. These are different knowledge states, not three competing backends.

Implementer: Codex / Astra, existing Snapback 2 query lane, under the parent's
2026-09-12 implementation commission. The parent owns shared budgets,
integration and published-package qualification.

removed coverage stays partial, noncanonical surviving rows still win, and
queued removal does not revive an older row. Initial qualification below is

**Already landed at review baseline `3b7f51564a`:** the twin withholds the

## Contract

Agreement is evaluated for the same operation, canonical arguments, principal,
auth epoch, program identity, effective held/overlay state and applicable read
time. In a quiet owner fixture, the eventual authoritative live value and a
same-client one-shot owner read must agree. A later sequence or time-dependent
bucket is not comparable just because the query name matches.

| Knowledge | Public behavior |
| --- | --- |
| Never-held maintained input, including inside arithmetic, list or composite | No fabricated scalar or total; current `unavailable` / `partial` with absent data |
| Qualified held zero or nonzero | Readable with actual freshness; `ready` is allowed offline |
| Owner-proved absent **or unreadable** maintained value | Preserve the language's typed zero; unreadability does not grant physical absence for prediction |
| Exhausted empty maintained group plus canonical primary absence | Preserve complete zero and permitted `0 → 1` prediction under the existing cap |
| Connected load awaiting the required owner answer | No claim that a held value is current; show pending refresh or explicitly stale content |
| Mixed rows/totals or timed result lacking replay authority | Partial/unavailable as appropriate; history rows never authorize a scalar |

Do not infer coverage from `seq > 0`, server provenance alone, `live`, or
the numeric value. `seq === 0` is valid; unrelated reads can advance the
client's sequence. Keep `summarize` a pure projection under
[LLP 1018.003 §2](./1018.003-truthful-and-composed-client.decision.md#2-derive-never-add).
Do not add a numeric-zero exception or return `ready` with deliberately
erased data to conceal an invalid evaluator result.

The landed retention of an untimed literal container of totals requires its
checked owner selection and all LLP 1012 §6 guards. It grants no new held fact.
Do not extend it to timed results, pooled-row composites, missing authority,
eviction or active/removal-only overlays merely to keep a screen populated.

## B — Make the existing one-client freshness path sufficient

Clique M8 explicitly requires owner freshness on load and pull-to-refresh;
it does not require live updates. Ordinary offline-first screens may render
held content immediately. Preserve both uses.

First exercise the provider's existing client, its readiness lifecycle,
`useQuery` / `observe`, `{ live: false }`, and `client.query`.
A one-shot call can return held data during startup/auth restoration or
transport loss; its method name alone is not a server-fresh guarantee.
Do not invent a hook `refresh()` method: it is not in the current public API.

Ship one small example showing the actual supported load/refresh sequence and
state presentation on that client. A connected refresh finishes only after its
current owner response is accepted and available to the screen through its
chosen public consumption path, either the explicit one-shot result or the
existing shared observation. Transport completion alone cannot clear a refresh
while the screen displays an older answer. An unchanged answer can complete
without manufacturing a new snapshot identity. Refusal/offline fallback stays explicit.
No extra auth/token store, polling loop, synthetic cursor/argument, or
component-key remount trick should be necessary.

If existing public operations cannot express that sequence, record a failing
consumer test and propose the smallest refresh operation on the existing query
owner in this child before implementing it. Its specified lifecycle must cover
shared subscribers, a second refresh, account/generation changes, cancellation
and offline refusal. It must not change the default offline query contract or
introduce a second query cache. This is the remaining API decision; a new
surface is conditional on the demonstrated gap and must fit the byte budget.
The executed consumer below resolves this branch: existing public operations
express the sequence, so no new refresh API was selected.

Specify overlapping refresh settlement using existing query/session ownership.
An older response cannot overwrite or satisfy a later refresh merely because
their owner sequences match: a UTC rollover can change this query without a
write. An obsolete attempt settles as obsolete. The consumer witness starts
with held Insights, changes owner state or UTC time, accepts and displays the
refresh, then delivers an earlier delayed answer. Include account/generation
change, cancellation and offline fallback in that same public path.

## C — Separate live once publication from offline redaction

The original draft's cold-reopen descriptor requirement contradicted the
[implemented offline policy](./1012-local-first-v1.spec.md#9-asset-bytes-on-the-device).
`nullOnceMedia` and the offline guide deliberately null once media, including
aliases and projections. The interesting defect is an **online, unconsumed**
owner value disappearing from a durable client's hook.

Use a real owner with an optional `image <=N once` column. Trace the same
delivery through HTTP/SSE decoding, carrier acceptance, local refresh and the
hook. Compare live observation and a one-shot read on the **same durable
client**, with no asset fetch yet. Reproduce any change caused by an unrelated
store update. A token-only client is a diagnostic control, not the proposed UI.

If local redaction overwrites a still-valid live owner descriptor, repair
selection/publication at that boundary using existing query/session ownership.
Persisted custody and the public offline projection retain their policy.
Do not bypass a viewed/revoked guard or invent a durable live-answer cache.

| State | Required once behavior |
| --- | --- |
| Online, unconsumed, authorized owner delivery | Hook and same-client one-shot expose the descriptor; rendering a preview does not fetch bytes |
| Warm offline or cold offline reopen, even unconsumed | Media null; no offline fetch, byte lease or predicted view |
| Cold reopen then authenticated owner delivery | Descriptor may return if still authorized and unconsumed |
| Consume, then unrelated live update | Existing mounted viewing instance may finish; a new instance cannot reuse its allowance |
| Consumed reopen, deletion, expiry, revocation or account switch | No revival; existing terminal/refusal and row-visibility semantics apply |

Extend `offline-view-once.test.ts` and existing real-browser media witnesses.
Include aliases, nullable joins and list positions; distinguish consumed 410
from separately diagnosed missing/deleted responses. `video ... once` stays
outside the grammar. The guide's click-to-open instance lifecycle remains.

## Acceptance and stop conditions

1. The landed unheld-total regressions stay green, including proven zero,
   unreadable zero, nonzero stale data and predicted counts.
2. The exact timed Insights screen passes load, refresh, UTC boundary and
   warm/cold tests without manufacturing totals or opening a second client.
3. Once media passes the online/offline matrix without weakening custody.
4. Shared snapshot/receipt provenance and account fences survive every change;
   published examples use the existing owner and actual public API.
5. Existing affected tests and guide checks pass. Current byte limits are
   measured after integration; fund growth through deletion, not a new ceiling.

Deterministic tests control delivery boundaries rather than requiring a first
server sequence of at least one. Real IndexedDB/browser evidence qualifies that
carrier; a file-store test alone does not. Use the existing scheduled witness
path, and keep physical native performance separate.

Three unsuccessful repair rounds trigger the parent's bounded stop rule.
A passing old control closes that case as already fixed; it does not close the
unreproduced timed or media cases. No blanket `summarize` redesign, second
replica, history-derived totals, or new Insights-specific API is selected.
