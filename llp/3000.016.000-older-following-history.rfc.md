## 1. Question and recommendation for Charlie

**Should following an actor eventually include all their retained pre-follow
events, accepting the measured tens-of-seconds copy run, minutes-long
serving-slice stress, and about 300 MB more server storage for one reader
at 100,000 events?** Or is an older
history link to the actor's profile the intended product boundary?

Recommend **freeze all pre-follow history and materialize in chunks** when the
product requires older history in Following. This lane implements that choice
only as an explicit experiment. Keep the ordinary 1,000-event declaration as
the default pending Charlie's semantics and resource ruling. There is no
measured builder LOC saving: the Cal29 specimens already declare the view in
six lines / 402 bytes and contain zero history-cap workarounds.

The prototype trades time to the first complete page and per-edge storage for
small, ordinary indexed reads after copying. It does not introduce a persistent
multi-actor merge frontier. Existing immutable birth records provide the finite
enumeration domain; the Feed index supplies final display order.

All timings are individual shared-eb1000 samples, not latency guarantees or
statistical speedups. The four options are not equivalent contracts. In
particular, neither profile paging nor the current-membership plan recovers
historical delivery. The on-demand design remains an unmeasured alternative;
this RFC does not present a synthetic merge as product evidence.

## 2. Opt-in contract

Only this spelling selects the experiment:

```quarry
maintain feed: timeline experimental history all
  events posts where .parentId = null and not .removed by authorId, at removed by removed
  reposts reposts by actorId, postId, at
  edges follows by followerId, followedId

query home(c: cursor ?):
  return feed[viewer] after c last 20
```

Ordinary `maintain ...: timeline` and inferred `view following: ...` remain
version 2. The experiment is version 3, using the existing serialized version
field. Old engines and devices reject version 3. No extra serialized field,
owned table, column or index is added to an ordinary declaration. Version 3
alone adds `Work.byActorBirth: kind, actorId, admitted, id`.

A follow pins its existing engine epoch E. It retains the ordinary immediate
50-copy write. If more than 50 events exist, one server backfill task traverses
all surviving delivery/birth records strictly below E. If 50 or fewer exist,
the immediate transaction already contains the complete pre-follow domain;
no empty task is queued. Own copies and post-follow delivery retain their
existing semantics. This is not a rolling window or an eviction policy.

The logical domain is the event incarnations alive at admission, identified by
`(event id, birth token, edge epoch)`. The physical representation is the
existing retained birth record plus its index and the task's immutable E.
Timestamp ties, backdating and caller-chosen source ids do not determine
membership. Removed events disappear; a removed identity does not refill with
a newly born incarnation. A recreated repost's new birth lies above E and
belongs to ordinary live delivery, even when its timestamp is old.

Changing an existing declaration from version 2 to version 3, or back, refuses
with `E_TIMELINE_REDEFINE`. The explicit upgrade is a new declaration name and
atomic **start now** adoption, preserving the old declaration if retained
alongside it. Existing current follows then get all retained live events,
fresh edge epochs and declaration-specific repost identities; they do not
recover former deliveries or deleted events. Dev's existing automatic launch
and deploy's existing `--allow-feed-adoption` apply. Preflight now counts all
copies for version 3 and refuses above the unchanged aggregate 5,000,000-copy
ceiling before candidate writes. Same-name re-add remains refused. Adoption
still fills slots and publishes one complete generation, with reacquisition.

## 3. Finite work and fairness

Birth tokens are engine transaction sequence plus write ordinal. The initial
backfill cursor is the encoded `['delivery', actor, E]` prefix used as an
exclusive descending seek. Continuations record the last processed full key.
Continuous later births sort outside the range before any row is decoded.
Deletion removes or skips a member without replacement. A missing event or
present removal tombstone skips and advances; a missing/deleted edge cancels
only the old epoch. Copy identity still contains reader, event and epoch.

The walk uses the existing metered 32-row fetches, at most 256 processed
members per chunk, and the existing cooperative time allowance. Each chunk
commits copied rows and its cursor together. No meter ceiling changes. There
is no O(follows) heap frontier: a reader following 16,386 actors is represented
by ordinary edges and, only where needed, individual work rows. The final
ordered index costs O(page) to read. The price is withholding the reader's
entire Following result until history finishes, instead of promising a newest
prefix while actors are still being copied.

For schemas containing an opted-in declaration, the last selected declaration
is stored in `_meta['experimental-history-last']` in the chunk transaction,
including parking. Selection resumes at the following declaration after
restart. Within each version-3 declaration, `Work.at` is a scheduling sequence,
not a source/event timestamp: enqueue uses the current commit sequence and an
unfinished turn moves to the tail with the new sequence. Each runnable task
gets a turn after the finite set already ahead of it; newly arriving tasks
cannot overtake that turn. Backfill, live delivery, cleanup and purge share
that queue. Parked tasks leave the runnable queue but retain their reader's
pending witness. A zero cooperative allowance still processes one member.

The cursor metadata read/write is charged. Fairness is in granted turns, not
wall-clock latency, guaranteed throughput under overload, or independence from
the host's maintenance admission. Legacy-only schemas execute the existing
scheduler unchanged. A mixed schema gets declaration rotation, while a
version-2 declaration retains its existing internal task policy.

## 4. Publication and devices

A version-3 Feed read checks the current viewer's Work partition. Pending,
parked or insufficiently examined work makes the result unavailable, with no
published data or continuation. This covers point reads, scans and folds;
`require` after an unknown point must not become a false absence refusal.
Write-context probes and system-wide reads of the experimental inbox are refused;
maintained aggregates over it are unsupported. This restriction is explicit
prototype scope, not an authorization inference from partial data.

No slots, tombstone semantics, edge epochs, source/inbox floors, outbox
publication fences or stream normalization rules change. Version-3 device
backends additionally select the existing deferred-publication barrier for
every normalized stream page whose image head exceeds its applied watermark,
even without a local prediction. Retirement of Work can be normalized to its
future absence before the log suffix supplies all historical copies. Without
this selection, the scale witness found a falsely complete third page.
Staged rows, metadata and restart custody use the existing barrier; ordinary
version-2 backends retain their existing selection policy. This barrier
selection covers the opted-in backend's whole normalized stream, including
unrelated table changes. A device that cannot catch up to the image head can
remain unpublished; no finite wall-clock completion under overload is claimed.
Snapshots keep their existing staged publication.
The cold-halfway witness interleaves removal, refollow during old cleanup,
backdated births and a reopened server/device. A device may claim complete
only after its surviving above-floor copies are available. Pages below the
original fixed floor remain withheld. Acquired pages do not become a new
retained-results cache. Later stream rows above that floor can grow the device;
1,000 is an acquisition floor, not a live storage cap.

The ordinary pending-own-edge fence and pending-prediction fallback precedence
remain the SDK's. The new declaration does not make follows predict and does
not let a sent receipt stand for observed rows.

The main comparison uses optimized Rust **test profile**, one-second
cooperative slices so the existing 256-row chunk bound wins, and a serial
loop without HTTP or maintenance pacing. It is a work/storage measurement,
not the serving scheduler's time-to-complete promise. Cold device measurement
uses global 1,000-row source floors, online-only application follows, the
unchanged 1,000 merged-copy inbox floor and all 16,386 owned edges. Sources'
residencies are adopted after the copy/disk measurement. The two phases must
not be confused. Acquisition figures time replay of actual server pages,
not network transfer. Heap charge is a meter dimension, not RSS.

The first all-history pilot queued useless tasks for one-event actors:
16,776 chunks, 59,501 ms drain, 868,564,992 B database. The final implementation
omits those already-complete tasks. Both raw runs are retained; no timing
speedup is attributed statistically on this shared host.

Regressions cover ordinary-schema bytes and deterministic histories against
committed base; version and policy fencing; finite completion with continuous
backdated births; removal and edge epochs; declaration/reader fairness;
restart; first-use existing-follow adoption and the 5M ceiling; honest raw
reads; the >16,384 actor scale; and halfway cold acquisition on SQLite,
memory, process and actual wasm devices. The 2,500-event device witness holds
1,000 copies at acquisition and 1,591 after catch-up/refollow, illustrating
non-sliding floors. Final suite details, short-slice scale stress and artifact
size are recorded with the report. The 100k stress completes with 512
backdated births, two removals and 116,895 final copies: 32,815 two-millisecond
turns, 544.095 s including fixture observations. Its corrected device replay
checks all 100 complete above-floor pages; peak logical wasm storage is
6,686,113 B and process database pages occupy 24,600,576 B. Full details and
measurement limits are in the report.

## 6. Cost of making this the default

At this skew, 99,000 additional foreign copies cost 30,480,890 extra row-image
bytes and 285,855,744 extra settled database bytes, including the birth index,
indexes, commits and allocation effects. Do not extrapolate that physical
ratio as a universal bytes-per-row tariff. Server space is
O(events + edges + sum of retained events across admitted edges), with
uncapped own and later delivered history. A hundred readers following this
hot actor add about 9.9 million historical copies beyond the current window;
this is arithmetic, not a measured hundred-reader run. It also exceeds the
current atomic launch ceiling, so a default upgrade at that scale requires a
separately designed migration rather than a ceiling increase.

Bounded cold acquisition does not make catch-up traffic constant. The stress
trace transports 42,647,361 B of stream data after its halfway snapshot, even
though the final device keeps only 2,019 inbox rows. History copying can
therefore add network/decoding work for rows below the fixed retained floor,
and the publication barrier adds transient staging cost.

Default shipping would need Charlie to accept this membership contract, a
storage envelope and complete-page wait objective; qualify normal serving
load/pacing and disk reclamation; choose an explicit existing-store rollout;
and decide whether whole-feed withholding is acceptable for interactive
Following. Newest-prefix publication while copying would require the
persisted merge/discovery mechanism this prototype deliberately avoids.
Version-3 schemas require upgraded engines/devices. Existing schemas are not
silently rewritten, and this lane does not publish a package or pave the
experiment in guide cards or the package README.
