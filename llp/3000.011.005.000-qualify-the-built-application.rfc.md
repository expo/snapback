## 1. Recommendation

Use the existing published witness on the application the builder actually
produced, with its exact installed packages. Add the missing application
assertions and run them on an installed native Release build. Then perform
scoped deployment/restore and provider exercises using existing tools.
Record each boundary independently in the existing benchmark run directory.

This proposal adds execution and application integration rather than a second
harness, registry, certification badge or universal publication gate. A
successful native run does not automatically qualify deployment or providers.

## 2. Native application witness

Build and install the Expo app with the actual published native module on a
dedicated compatible simulator. Use the existing `snapback4-expo/witness`
helper and `snapback4 witness ios`; a Hermes export and the Expo Go online
fallback do not satisfy this step. Keep the real screen visible so receipts
and recorded UI refer to the same application behavior.

Prime authorized history, search and viewed ordinary media online. Terminate
the app, stop the backend and verify network failure. Cold-launch and assert
held history/search/media, incomplete horizons where applicable, and no
durable replay of consumed view-once media. Queue two messages and persist
their ids; terminate and relaunch offline, then verify those same pending
intents survived. Reconnect, observe ordered authoritative settlement and
receipt progression without duplicate rows. Learn a membership revocation,
relaunch offline and verify its retained-history/new-delivery boundary.

Use the driver's existing failure receipts, video, logs and run manifest.
The manifest must identify the installed app, native package, backend package,
simulator runtime, origin and exact artifacts. Missing artifacts remain
missing, and retries receive fresh directories. A simulator result is still
not a physical-device, Android or power-loss result.

## 3. Acquisition on the same app

Run the full retained fixture on the actual client, identifying the offline
content required before measuring. Record first useful render, completed
durable acquisition, transferred rows/bytes, disk size and peak memory where
the host exposes it, then prove offline reopen. If peak memory cannot be
measured, name the absent metric; do not substitute JavaScript heap for all
native or wasm memory.

Preserve LLP 3000's physical-floor comparison only for equivalent fixture,
host and persistence semantics. Smaller reference-app timings and server
query latencies do not substitute for this measurement. These observations
also evaluate the residency proposal, without making it responsible for
native module correctness.

## 4. Deployment, restore and provider boundaries

Use an isolated disposable deployment with the existing release commands.
Exercise password session recovery, an asset read, schema adoption, a queued
job across process restart and the documented stopped backup/restore path.
Keep restored workers and old production clients fenced; do not reconnect a
prior outbox and claim recovery merely because fresh reads work. Test rollback
as source activation, not database rewind. Record the storage mode and the
precise crash class; this is not physical-power-loss qualification.

For one real push-provider adapter, select a test account/device and explicit
recipient before sending. The user-authorized implementation, publication
and benchmark program does not by itself identify a provider account or a
message recipient. Prepare the adapter and test-double crash cases first;
execute actual external delivery only with that account/recipient authorization.
No secret values belong in artifacts or LLPs.

Distinguish effect admission, provider acceptance and device receipt. Inject
the acceptance-before-local-settlement failure using a labeled test double;
then verify the real provider's supported deduplication/outcome behavior.
If a provider cannot deduplicate or resolve an uncertain result, record the
remaining ambiguity instead of claiming exactly-once external delivery.

## 5. Benchmark integration and availability

Before launching the next comparable Clique run, record package pins, builder
and grader identities, required simulator availability and the committed
probe set, or explicitly declare any protocol deviation. Preserve the frozen
instrument and perform native qualification as an explicit extension after
the cold build and independent grading. The prior builder prompt expressly
made simulator proof optional. Do not change that timed task silently. Do not quietly count a new
native proof as though previous runs used the same environment.

Append a compact coverage table to the existing report: scenario, host,
artifact link, result and limitation. A missing credential, simulator or
signing identity is an execution prerequisite, not a passing product test.
Continue independent browser/server work while that cell remains unavailable;
do not manufacture its outcome or replace it with a compilation check.

## 6. Completion and limits

The native increment is complete when the actual application passes its
installed Release witness and every required artifact is retained. Deployment
and provider increments complete separately on their stated environments.
Any discovered defect receives a reproduction, an affected fix and a rerun
of that boundary before the claim changes.

Run slow host exercises outside the ordinary edit/push loop and on a machine
whose simulator use will not disrupt the user. Use the existing fleet and
owned-process rules. No full battery at an ever-moving main is required.
Do not spend time building more evidence infrastructure when an existing
witness can execute the missing scenario directly.

## 8. Actual-app qualification exposed a native media defect

The [post-grade native failure](../snapback4/reports/20260922-native-media-repair.md)
reached the installed Expo 57 Release app using the published 0.2.32 client
and 0.2.23 native package. After ordinary native acquisition, a successful
HTTP 200 image response produced a 2,062-byte React Native Blob without
`arrayBuffer()`. The ordinary cache calls that method unconditionally, so
the actual image/video hooks refused and no ordinary bytes reached the cache.
The failed `restart-3` attempt remains evidence against the original package;
earlier signing/entitlement setup failures are recorded separately.

The selected remedy stays in the shared asset implementation: use the host's
public `FileReader.readAsArrayBuffer` only when Blob lacks its direct method,
and explicitly own/release response Blobs through the host's available APIs.
Keep once responses outside durable byte extraction, retain caller ownership
of upload Blobs, and preserve browser URL behavior. Native handle release
does not promise instantaneous memory zeroization or removal of decoder copies.
No app shim, native ABI change, new dependency or resource ceiling is needed.
Astra xhigh implements the repair; both requested reviewer families and exact
installed-package native reruns must precede a success claim. The original
cal16 app, grade and score remain frozen across the corrective release.


The first candidate passed ordinary native rendering, then exposed a second
host incompatibility: Expo 57's object-URL polyfill threw while its expected
bridgeless native proxy was absent. A separate ordinary-Blob probe reproduced
the exception with the link online and without consuming another once grant.
The selected transient fallback is public `FileReader.readAsDataURL` when
object-URL creation fails. It copies response bytes into an in-memory base64
URI and never writes them to media storage or refetches the asset. Browser
object URLs remain preferred. Copied data strings cannot be revoked, so the
caller must drop them on screen close; SDK cleanup releases its owned
references and native Blob, not arbitrary copies. This documented tradeoff
preserves the server's single grant and the no-durable-once-storage contract;
it adds neither a private native dependency nor a native ABI. Review and
qualification must check once-file/manifest absence while the actual image is
open as well as after close and process death. The [repair record](../snapback4/reports/20260922-native-media-repair.md)
separates both failures, patches and pending qualification.


Once rendering then passed, including live-handle durable-storage exclusion,
but the actual video player exposed a separate native-cache contract defect.
The valid original MP4 and cached file were byte-identical. AVFoundation decoded
that content with a `.mp4` filename and refused its extensionless cache name.
The selected first-party Swift storage repair gives ordinary MP4 a real suffix,
resolves/migrates legacy extensionless MP4, and keeps atomic writes, reads and
purges coherent across owned variants. Existing device locking, ID validation,
image storage and once exclusion remain; no app display-copy workaround or
Rust/C ABI change is introduced. Expo advances to 0.2.24 and the consumer's
Swift is rebuilt, while the Rust frameworks remain unchanged. Actual native
video/restart/revocation and final published-pin evidence are still required.


The combined 0.2.33 SDK / 0.2.24 Expo candidate then passed the actual Clique
Release application's restart, revocation and full-acquisition scenarios.
Restart includes fresh native offline image/video rendering on both process
launches, the exact two pending intents surviving death, exactly two ordered
sent settlements, and delivered/read progression. Revocation retains authorized
text history but purges ordinary media and excludes later delivery offline
and after an explicit reconnect. Full acquisition enumerates all 10,000
required message IDs in 100 scopes across 299 actual local query pages while
offline, before reconnect, matching the frozen fixture's canonical ID hash.
The [native application report](../snapback4/reports/20260922-clique-native-extension.md)
retains exact timings, package/app custody and limitations. These are candidate
results with the original 0.2.32 CLI. At that candidate checkpoint the final
published 0.2.33/0.2.24 pair still required installed-package requalification;
§9 records its subsequent completion. These observations do not change cal16's
original grade or qualify a physical device, Android, power loss or real provider.
