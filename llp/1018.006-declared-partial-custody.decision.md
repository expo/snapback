# 1018.006 Declared partial custody: the thread's fallback behind `observe`

**Type:** Decision
**Status:** Implemented (revision 5)
**Systems:** Snapback 2 client SDK (`packages/snapback2/src/client-items.ts`, `client-observed.ts`, `client-pages.ts`, `react-core.tsx`), the chat recipe's thread screens (`templates/chat/{react,expo}`), the live-query guide
**Author:** Claude (Fable 5.1), with the author
**Date:** 2026-09-08
**Revised:** 2026-09-08 (round-two declaration timing follows cursor metadata); 2026-09-08 (declared cursor callback spelling reconciled); 2026-09-08 (the plain tier: composite-data and receipt vocabulary reconciled); 2026-09-08 (revision 4: commissioned composite continuation, typed usability and truthful retained projections); 2026-09-11 (revision 5: composed page resources and shipped continuation)
**Related:** LLP 1018.000 §4 (one observed query, one coherent snapshot; the fallback's rules), LLP 1018.003 §1–§2 (the snapshot record; derive, never add), LLP 1018.003 §8 (declare correspondence once, keep mechanics in the SDK), LLP 1018.003.000 §2 (items and correspondence), LLP 1012 §6 (partial custody), LLP 1018.005 (the previous move in this series), LLP 1018.008.005.000 (composed page resources)

## Summary

The chat thread reads one composite query, `deliveries.conversationView`,
for its list, count, and preview. When that composite's receipt is
`partial` the screen falls back to the independently authorized paginated
`deliveries.thread` for history and shows no count or preview. Before this
change each platform arm carried that fallback itself: a usability predicate on the
composite, an eligibility predicate, a hand-rolled second observation that
subscribes only while eligible, a readability predicate over the two
snapshots, and a three-way selection of which items to render. Twenty lines
each, twice, and every consumer of the same composite has to get it right
again.

This decision moves the mechanics into the SDK and leaves the app one
declaration. `withHistory(items, { items, args })` names the query whose
head page stands in for the composite's rows under partial custody. A
snapshot observed with such a declaration carries two more fields,
`itemsFrom` and `history`, and its `items` already follow custody. The
screens delete their predicates and their second observation. The plain tier
exposes usable `data`, selected `items`, and `partial`; `itemsFrom` and `history`
remain opt-in custody facts. Nothing about the rules in LLP 1018.000
§4 changes: eligibility is the composite's partial receipt, only a complete
or capped composite with data is usable, denial, refusal, and account reset
never enable the fallback, and history detaches as soon as a usable composite
arrives.

## Context

LLP 1018.000 §4 states the fallback's rules and assigns their mechanics to
"both platforms". LLP 1018.003 §8 says the app should declare correspondence
once and the SDK should keep the mechanics. The thread screens do the first
for their items through `shared/thread.ts` and then do the second for
custody by hand, in `usableConversationView`, `needsPartialHistory`,
`usePartialHistory`, `readable`, and the `items` selection, duplicated in
`react/src/Thread.tsx` and `expo/src/screens/Thread.tsx` with two different
spellings. The screen suites pin the React helpers by importing them from
the template, so the helpers are a de facto surface without being one.

The SDK already has everything the mechanics need: `client.observe` returns
a stable `getSnapshot`/`subscribe` pair whose first subscription opens
transport and whose last unsubscription retires the entry; `defineItems`
already declares where a query's rows come from and which mutations target
them; `Snapshot` already carries the receipt whose state decides
eligibility and usability.

## Options

- **A. Leave it in the app.** Two copies of one rule set, and the third
  consumer will write a third. Rejected.
- **B. An `observe` option.** `observe(ref, args, { items, history: {...} })`.
  A shared exported options object could declare it once too, so this is
  not a duplication argument; it is a placement one. The fallback is about
  where the composite's rows come from, which the items declaration
  already owns. Rejected on placement.
- **C. A declaration on the items (chosen).** The composite's items
  declaration already says where rows come from; under partial custody
  they come from somewhere else, and that is a property of the same
  declaration. One expression in `shared/thread.ts` serves both arms. The
  declaration is bounded: the history's arguments are a pure function of
  the composite's.
- **D. Fold the fallback into the composite query on the server.**
  Impossible by construction: the partial case is exactly the case where
  the client holds the thread's pages with their own receipts but has no
  authority for the count.

## Decision

### 1. The declaration

```ts
export const conversationItems = withHistory(
  defineItems(api.deliveries.conversationView, { table: "messages", rows: view => view.messages, select: delivery => delivery.message, order: "reverse", create: {...}, update: {...}, remove: {...} }),
  { items: threadItems, args: ({ conversationId }) => ({ conversationId, c: null }) },
);
```

`withHistory` takes a finished items declaration and returns
`ItemsWithHistory`, the same declaration with a required `history` member.
That member is the discriminator every custody overload matches on, so a
plain `Items` never widens into it and the custody return type is never
lost. `history.items` is an items declaration for the query that supplies
rows under partial custody. It must describe the same `table` and the same
row and draft types as the declaring items: the table is checked at
declaration time and refuses with a `TypeError`; the types are checked by
the compiler, with `NoInfer` on the history's row and draft so the
declaring items alone decide them and an incompatible history is an error
rather than a widening. `history.args` maps the composite's arguments to
the history's; it must be pure and deterministic, it runs once per
observation after declared cursor metadata is available (superseding immediate
`observe`-time execution), and its result is bound by copy against
later caller mutation like every observed argument. Declaring history on a
declaration that already has one, or naming a history that itself has one,
refuses: custody has one level.

### 2. The published record

An observation whose items declare history publishes `HistorySnapshot`,
which is `ItemSnapshot` plus two fields. `itemsFrom` is also the TypeScript
discriminator: its `query` branch requires `data: Result` and a complete/capped
receipt; the `history` branch requires the independent history snapshot.

```ts
type HistorySnapshot<Result, Row extends ItemRow, Draft, History> = ItemSnapshot<Result, Row, Draft> & {
  /** Where `items` come from: the usable query, its declared history, or only this device's drafts. */
  readonly itemsFrom: "query" | "history" | "drafts"; // discriminated branches in the SDK type
  /** The history's own snapshot, present exactly while the query's receipt is partial. */
  readonly history?: Snapshot<History>;
};
```

The earlier rule that kept raw composite `data` on every branch is superseded
by the plain tier (LLP 1018.003): `data` is undefined unless the composite is
usable. `receipt`, `freshness`, `local`, `refusal`, `status`, and `reason` remain
the composite's facts. Count and preview come only from usable composite data. `history` is the republication of an independent input, the
history query's own published record with its own provenance; `itemsFrom`
is a selection derived from the composite's receipt and data presence and
the history's readability. Neither invents authority (LLP 1018.003 §2):
each record keeps its own receipt, and nothing on the composite is
rewritten from the history. `itemsFrom` is a different axis from
`receipt.source`, which stays who evaluated a value.

The rules, restated as the derivation:

- **Eligible** iff `receipt.state === "partial"`, including a partial
  with no data whose summary is `unavailable`. `history` is present iff
  eligible, whatever its own state: loading, held, ready, denied, or
  refused history is still the fallback in force, and a screen says so
  from `history`'s presence, not from `itemsFrom`. Held composite data
  without a receipt, `denied`, a refusal, `loading`, and an account reset
  are not eligible and never were.
- **Usable** iff `receipt.state` is `complete` or `capped` and `data` is
  present. `itemsFrom` is `"query"` iff usable. The compiler gives a successful
  evaluation its declared shape; the wire decoder validates its envelope,
  not an arbitrary application result schema. The carrier must mark a
  retained mixture or purged projection partial (§7), so such a value cannot
  enter the usable branch. The screens need no duplicate field checks.
- Otherwise `itemsFrom` is `"history"` iff eligible and the history's
  `status` is `ready`; its items are the history's items. A held history
  page is readable history, as today.
- Otherwise `itemsFrom` is `"drafts"`: `items` are the composite's items
  that carry a `draft`, this device's own pending creates, republished
  with `data` absent and their keys, drafts, prediction flags, and pending
  actions intact. `attachItems` keeps a draft beside a row image once the
  row arrives; under custody that image is not readable, so it is not
  handed out. A partial composite's own rows are never rendered.

### 3. Mechanics

`ClientQueries.observe` builds the composite's observation as today and,
when the items declare a history, a second observation of it with the same
`live`/`drain` options and `history.items`, and returns one composed
`ObservedQuery`:

- **Acquisition.** A consumer's `subscribe` subscribes the composition to
  the composite on its first consumer, then reconciles eligibility at once:
  the shared entry registers a subscriber without an initial notification,
  so a composite that is already partial must acquire history in the same
  call, not on the next change. Reconciliation runs again on every
  composite notification and never requires a consumer to call
  `getSnapshot`. Eligible and not held: subscribe the composition's own
  history subscription. Not eligible and held: release it. Both are
  idempotent.
- **Retirement.** The composition releases only its own history
  subscription; an unrelated consumer of the same history entry keeps that
  entry alive, as the shared entry's reference count already says. The
  last consumer's unsubscribe releases the history subscription if held
  and then the composite subscription, and is idempotent. Obtaining a
  composition opens nothing, like any `observe`.
- **Sharing.** Compositions are shared per client while any consumer
  holds one, keyed by the items declaration's identity and the composite's
  full query identity (authority generation, operation fence, mode,
  operation, canonical arguments); the history's identity follows from
  those given a deterministic `history.args`. An `observe` call returns a
  handle; the first handle to subscribe registers its composition and
  later handles join it at their own subscribe, whatever order the handles
  were created in. A composition with no consumer is not registered, so an
  abandoned handle retains nothing. Each subscription is its own
  attachment: one callback subscribed twice has two, a listener that
  throws does not silence the others, and a listener removed during a
  broadcast does not run. `clear()` retires registered compositions with
  the shared entries; a retired handle keeps reading the underlying
  fallbacks and opens nothing. Two screens observing the same conversation
  read one record.
- **One snapshot per input pair.** `getSnapshot` rereads both inputs on
  every call, deriving the record from the composite's snapshot and, while
  eligible, the history's, and returns the same frozen object until either
  input changes identity, so `useSyncExternalStore` sees a stable value
  and an account reset or fence change shows through as the underlying
  observations' fallbacks do.
- **Types.** `withHistory` returns `ItemsWithHistory`; `Client.observe`,
  the `SnapbackClient` interface, `ClientQueries.observe`, and `useQuery`
  each gain one overload, placed before the plain-items overload, that
  matches `ItemsWithHistory` and returns `HistorySnapshot`. Plain items retain their custody; the plain tier adds `next` and `partial` to
  every snapshot.

### 4. The screens

The earlier screen-owned `itemsFrom === "query"` narrowing is superseded:
read `snapshot.data` for count and preview, render `snapshot.items`, and use
`snapshot.partial` for selected history. Opt-in `history` still records an
eligible fallback while loading, denied or refused; its own state is
`history.receipt?.state ?? history.status` and its sequence is
`history.receipt?.seq`. These facts never authorize composite scalars.
`usableConversationView`,
`authorizedHistoryRows`, `needsPartialHistory`, `usePartialHistory`,
`readable`, and the Expo `usable` are deleted; their tests move to the SDK
as tests of the derivation and the subscription lifetime.

### 5. Surface

The live-query guide's paragraph on the coherent composite names the
declaration and the two fields in place of the app-side rule; the review
supplied a text that fits the byte budget. `withHistory`,
`ItemsWithHistory`, and `HistorySnapshot` are exported from
`snapback2/client`. LLP 1018.003.000 §3's sentence that item declarations
add "not subscriptions to a second source or new query lifecycles" gains
the one exception this decision makes, with a pointer here. The Expo
witness's `state` command reports the composed observation's `itemsFrom`
and `history` beside its direct queries, and the witness script asserts
them in the cold partial-custody step, so the changed path is qualified
through the SDK it now runs through and not only through direct queries.

## Consequences

- The fallback exists once, in the SDK, under test, and the screens are
  the declaration plus rendering.
- A screen cannot render a partial composite's rows as history by mistake,
  because with a history declared the SDK never hands them out.
- The record grows by two fields for history-declared items only.
- `history.args` binds at `observe` time; a screen whose history arguments
  depend on something other than the composite's arguments cannot use this
  declaration and keeps a hand-written observation, as today. Neither the
  recipe nor the witnesses need more.
- Item declarations now own one source-and-lifecycle exception, the
  declared history, recorded in LLP 1018.003.000 §3.

### 7. Composite continuation and retained projections

The author's implementation commission covers a usable composite's ordinary
pagination as well as its partial-history fallback. LLP 1011 §B1 now derives
one unambiguous cursor-bearing page through a returned record. The chat
`conversationView(conversationId, c: cursor ?)` forwards `c` to its message
page; the maintained count and fixed latest preview stay in the same certified
query. `receipt.next` belongs to that returned message page. Passing it back
to the same query reads an older composite. Multiple competing cursor-bearing
pages yield no single continuation. Wrapping a page does not qualify it as
an ascending resumable log.

The single-query observation remains a live head with its optional cursor
omitted. Its declaration supplies the independently authorized history head
under partial custody. Each observation keeps its own continuation: a history
cursor is not a composite cursor, and operation-bound local cursors must never
be forwarded between the two queries. The shipped threads now accumulate pages
through the revision-5 resource below; single-query observations retain this law.

Retention permits keeping authorized historical row bodies. It cannot certify
the whole result after old bodies are restored beside newer scalars, or after
unproven scalar projections are cleared on eviction. Such stored answers are
partial, including array projections. Their rows remain readable; the composite
cannot supply count or preview until its complete evaluation can reconstruct
them. Independently retained history remains the fallback.

An altered retained answer may keep its previously certified positional
continuation, with its existing sequence custody. The offline partial record
and snapshot carry that boundary without claiming complete coverage. Fresh
partial evaluation creates no cursor, and authority invalidation clears the
old one. Server partial wire envelopes still have no continuation. Existing
carrier and history-observer tests cover restoration, scalar purge, reopen and
the distinct composite/history boundaries.

### 8. Composed page resources (2026-09-11)

`client.observePages` and `usePage` accept the existing item/history declaration.
The current recipe uses `messages.conversationView` and `messages.thread`.
Its `head` retains primary scalar authority; `items` accumulates the active
source, and `pages` preserves each original snapshot under the `itemsFrom`
discriminant. No collection-wide receipt or sequence is synthesized. Raw array
pagination keeps its original shape. The complete contract and implementation
record are in [LLP 1018.008.005.000](./1018.008.005.000-composed-page-resources.plan.md).

One chain implementation owns both sources. The primary head stays observed;
history exists only under the existing partial/ready selection law. Each source
resolves its own cursor metadata. Handover retains requested depth and rebuilds
valid links; changed boundaries release dependent suffixes before publication.
Consumers share the existing query subscriptions, with pure snapshot reads.

Selected row images win duplicates in scan order, retaining their own item
evidence. Reversal applies once to the unique combined row sequence. Distinct
draft-only candidates survive from all valid pages in durable FIFO order after
rows; a selected row beats its draft. The recipe's membership predicates name
the conversation, leaving page placement to the SDK. Both mounted client arms
pass a real-owner 105-message continuation witness and a cold original-recipient
history witness with unavailable summary and no transport; the latter also
pins one queued create across three pages. These are revision-5 controls, not
new claims about the earlier review records.

## Non-claims

No multi-level custody, cross-query atomicity, count derived from history,
multi-cursor result format, or persisted collection cache. The original
revision-3 implementation and review records below retain their own source
scope; they do not qualify the revision-4 amendment.

## The plain tier (2026-09-08)

Absent and explicit-null declared cursors share observation and delivery
identity. Item membership callbacks receive the declared cursor as
explicit `null`; only identity keys and fingerprints omit it. Auxiliary null
arguments retain their own meaning. This supersedes the first repair’s
callback-omission wording in LLP 1018.003.

LLP 1018.003's A3/A4 rulings govern the operative contract: receipt `state`
replaces the old `outcome` field; `data` is undefined whenever the observed
composite is unusable. `partial` is true only when selected items come from
history. `history` and `itemsFrom` remain independent opt-in facts. Historical
implementation/review counts below retain their original scope and do not
qualify these later product changes.
