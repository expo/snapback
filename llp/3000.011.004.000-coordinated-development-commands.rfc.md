# LLP 3000.011.004.000: Coordinate development commands at the store boundary

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 dev and run commands, SQLite transactions, adoption diagnostics
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (initial proposal)
**Related:** [Problem](./3000.011.004-cli-and-host-contention.research.md), [LLP 3000.000](./3000.000-atomic-schema-and-release-activation.research.md), [LLP 3000.009](./3000.009-general-purpose-backend.rfc.md)

## 1. Recommendation

Add a bounded coordination path for cooperating local development writers.
Adoption, command admission and job chunks should use the same store-scoped
ownership primitive, with progress and timeout diagnostics. Preserve SQLite
transactions and the existing generation checks as correctness enforcement.

First reproduce the diary race against the installed CLI. If an existing
retry primitive can supply this behavior, extend it instead of introducing
a lock service. This is a local development change, not a new hosted control
plane or online migration protocol.

## 2. Ownership and ordering

Use an OS-released advisory lock associated with the canonical store identity
for cooperating processes. A crash releases ownership; a stale pid file must
not be the correctness primitive. Canonicalization must ensure symlinked
project paths do not acquire different locks for the same SQLite store.
Do not reclaim a lock by killing a process or deleting its file based on age.

Acquire the coordination primitive before the SQLite writer transaction, in
one order everywhere. No path may hold the SQLite writer while waiting for
this primitive. Adoption holds it through activation and publication of the
new in-process generation. A job holds it only for admission or one chunk,
not its entire potentially long run. Normal host mutations must cooperate
with the same ordering if they can otherwise starve those commands.

On acquisition, reopen or revalidate the active schema/program identity. A
CLI must not adopt stale compiled input just because its lock wait finished.
Bind an invocation to its intended source/operation and arguments; if source
changes while waiting, report that fact or recompile before any admission.
A running host's existing generation fences remain mandatory even if it has
not yet observed another process's adoption.

This preserves a stopped-store `run` path and adds no public system-job HTTP
endpoint. Production `serve`, release activation and backups retain their
existing contracts; their interaction with a proposed shared primitive must
be reviewed before extending its scope beyond development.

## 3. Bounded waiting and truthful retry

Use an explicit wait deadline, with a documented default chosen from the
reproduction's startup times. Report the operation waiting, elapsed time,
observed adoption state and store generation through existing terminal/JSON
diagnostics. A deadline exits with a typed contention refusal and a recovery
step; it does not become an arbitrary engine error or an indefinite hang.

Retry only a failure known to occur before admission or after transaction
rollback. Do not resubmit a whole job or mutation after an uncertain commit.
Once admission commits, retain its run/write identity and collect that
outcome. An interrupted caller can resume observing the same identity.
If the existing job API cannot provide that distinction, the first increment
must stop at safe pre-admission retry rather than invent exactly-once behavior.

`doctor` should distinguish pending adoption, writer contention, invalid schema
and a parked product job using its existing report. File permissions and I/O
errors remain their original errors. Read-only `sql`, `data` and inspection
must not become writers merely to participate in coordination.

## 4. Alternatives

Increasing SQLite's busy timeout alone can help short races but cannot explain
which generation or operation a command will execute. It remains the smallest
candidate to measure before adding a broader primitive. A permanent host RPC
owner gives stronger serialization but needs authenticated local discovery,
system-job authorization and crash handoff; it is larger than the diary's
demonstrated problem. Manual stop/run/restart is the safe fallback and should
remain documented for unsupported combinations.

## 5. Implementation and acceptance if accepted

Reproduce startup adoption plus `run`, and changed-maintain rebuild plus a
backfill, in the existing CLI lifecycle tests. Add barriers so the tests prove
contention deterministically rather than hope to hit it with sleeps.
Evaluate bounded SQLite retry first; add shared advisory ownership only if
the reproduction or fairness requirements cannot be satisfied by that path.

Exercise two simultaneous CLIs, a busy host, caller interruption, owner crash,
timeout, invalid schema, alias paths, changed source while waiting and
`--no-watch`. Assert no duplicate job admission, no stale-generation write,
no partial activation and no execution after a reported pre-admission timeout.
After crash, a fresh command must recover without deleting persistent data.

Measure normal mutation throughput and command latency with and without the
candidate. Keep the fast uncontended path and bounded progress; a coordinator
that serializes harmless reads or holds ownership across the whole job fails.
Update the operations reference with the actual supported sequence and limits.

## 6. Open decisions

Which existing store timeout/retry behavior already meets most of the need?
Can job admission identity be collected after interruption through today's
CLI? What default wait is useful for a measured rebuild without hiding a
stalled one? Settle these from the reproduction before expanding ownership
across all host operations.
