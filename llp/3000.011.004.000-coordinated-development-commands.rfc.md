# LLP 3000.011.004.000: Bound development-command waits before admission

**Type:** RFC
**Status:** Accepted
**Systems:** Snapback 4 dev and run commands, SQLite transactions, adoption diagnostics
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (selected scope after independent reviews; parent §7)
**Related:** [Problem](./3000.011.004-cli-and-host-contention.research.md), [LLP 3000.000](./3000.000-atomic-schema-and-release-activation.research.md), [LLP 3000.009](./3000.009-general-purpose-backend.rfc.md)

## 1. Selected recommendation

Give local `run` a bounded, typed retry around its existing store-opening and
adoption path, before job or mutation admission. Capture the two diary races
with deterministic barriers. SQLite already has a five-second busy timeout;
the host already retries BUSY/LOCKED at startup and reopens after an external
adoption. The missing CLI symmetry is the first target.

This revision replaces the first draft's proposed shared advisory coordinator.
Both independent reviews prefer the existing path first. No new writer lock,
public system-job endpoint or production control plane is accepted here.

## 2. Admission boundary and source identity

Retry only typed SQLite BUSY/LOCKED outcomes known to precede admission or to
have rolled back. Other store, permission, schema and I/O errors retain their
meaning. Do not string-match all `E_STORE`, wrap `run_job`, resubmit a mutation,
or invent exactly-once behavior after an uncertain outcome. A new job invocation
currently mints a new ID; an interrupted caller does not thereby authorize a
second one. Read-only inspection stays read-only.

Bind the wait to its intended operation, arguments and source identity. If
source changes while waiting, recompile and revalidate safely or refuse before
admission. Preserve all existing generation fences and atomic activation.
Report elapsed wait, operation, relevant available host/adoption state and a
bounded timeout with an actionable recovery step. Choose the default from the
reproduction; do not copy the host's indefinite startup retry into the CLI.

## 3. Live-host compatibility

Grok proposes forbidding all different-schema adoption beneath a live host.
Astra notes that external CLI adoption and watcher reopen already have explicit
tests. Resolve this against the current contract, not a hypothetical new lock.
A held `serve.lock` is a lifetime host lock, not a per-chunk mutex and cannot
be taken by every command that must work beside the host.

Prefer waiting for an active watching host's already pending adoption when its
reported identity matches the requested source. A `--no-watch` host may require
restart after external adoption under the current contract; state that sequence
precisely. Do not silently introduce a permanent wait for a host that cannot
adopt, nor disable a deliberately supported external-adoption path without a
reproduced reason. A stale host may refuse through its generation fence; it
must never execute a stale-generation write.

## 4. Validation

Prove startup adoption plus `run`, and changed-maintain rebuild plus backfill,
with controlled writer locks/barriers rather than timing guesses. Cover release
before deadline, deadline exceeded, invalid schema, changed source during wait,
two CLIs, watched and `--no-watch` hosts, caller interruption and owner exit.
Assert no admission after a pre-admission timeout, no duplicate retry admission,
no partial activation and no stale-generation write. Recovery must not delete
persistent data or kill another process.

Measure uncontended latency and bounded waiting. Update the existing operations
paragraph and relevant diagnostic card with exactly the sequence implemented.
A broader advisory primitive remains rejected unless these reproductions show
that the existing transaction/retry approach cannot meet the requirement.

## 5. Implementation record — 2026-09-22

`run` now has one pre-admission loop around store opening and atomic schema
adoption. It recognizes only typed SQLite BUSY/LOCKED (including extended
BUSY codes), polls at 100 ms, and stops at a 15-second contention deadline.
Its store connection uses a zero SQLite busy timeout during that loop so
per-statement waits cannot extend the retry deadline; the ordinary five-second
policy is restored before execution. Other callers retain their five-second
policy. The deadline bounds contention retries, not cancellation of an atomic
activation already running or execution of an admitted operation. Activation
can complete after the deadline while the operation remains unadmitted. Thus
neither a total process duration of at most 15 seconds nor an unchanged
generation on every timeout is promised. The blocked-lock test below proves
no activation for that controlled case.

The invocation retains its compiled operation, typed arguments and Quarry
source contents. Compilation consumes those retained bytes rather than a
second read of mutable files; an intervening A → B → A edit cannot compile B
while validating A. It compares those contents and the existing native/server
source stamp before each attempt, after opening and after native installation.
An edit refuses `E_RUN_SOURCE_CHANGED`; it never silently substitutes a new
operation. The refusal promises no operation admission, not rollback of an
activation that committed before the edit was detected. A timeout reports
`E_RUN_BUSY`, the operation and elapsed wait, with `doctor`/adoption-log and
stop/run/restart recovery. Neither `run_job` nor `mutate` is retried.

The compatibility ruling retains external CLI adoption. The existing watching
host explicitly reopens after another process adopts; its lifecycle tests
cover that path. A `--no-watch` host refuses through its old-generation fence
and needs a restart. Forbidding every different-schema CLI activation beneath
`serve.lock` would remove this supported behavior without evidence of a broken
fence. No new advisory lock or host endpoint was added; read-only verbs are
unchanged.

The fleet's first affected test execution passed all eight new subprocess
cases. Actual activation is paused by a SQLite update hook before commit,
including a changed-maintain rebuild, so contention is established by barriers.
The uncommitted generation remains invisible. Observed on the warm M5 lane:

| Case | Elapsed | Result |
| --- | ---: | --- |
| Uncontended `run` | 4 ms | No retry message |
| Startup activation writer then mutation | 1,035 ms | One admitted row, generation 1 |
| Changed-maintain writer held beyond five seconds, then backfill | 5,628 ms | One job, one update, generation 2 |
| Writer held past deadline | 15,022 ms | `E_RUN_BUSY`, zero jobs, generation 1 |

The 15-second default covers the controlled 5.5-second release that exceeds
the former single five-second wait and leaves a finite three-window budget.
This is not a claim about all rebuild sizes or a measurement of production
rebuild latency. Source edits, two independent waiting CLIs, writer exit,
caller SIGINT, invalid source and a non-lock store error are also covered.
The ignored `update_hook` setup result found by that build was then corrected
to assert setup success. A fresh fleet execution passed the eight subprocess
cases, the typed-lock unit test and all four existing `w8c_` host lifecycle
cases (13 total). Its uncontended invocation took 5 ms, controlled long-writer
case 5,599 ms and deadline case 15,010 ms. The existing host cases include
watcher reopen after CLI adoption and generation refusal plus restart for
`--no-watch`.

Root source review then identified the separate compile read's A → B → A
race. The captured-byte compilation above and a deterministic regression that
restores both bytes and mtime address it. The final focused fleet rerun passed
both unit tests and all eight admission subprocess tests. It measured 5 ms
uncontended, 933 ms for startup contention, 5,642 ms for the changed-maintain
barrier (one job, generation 2), and 15,014 ms at the blocked-lock deadline
(zero jobs, generation 1). Logs: `cli-aba-unit.log` and
`cli-aba-admission.log` in the integration run's retained evidence directory.
No retry scope or host compatibility decision changed.
