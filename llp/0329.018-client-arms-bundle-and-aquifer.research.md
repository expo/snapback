## Summary

Three questions arising from the Contract front-end work in
[LLP 0329.017](./0329.017-contract-block-front-end.research.md), answered
together because they share one boundary — where Snapback 2 stops and Exact
starts.

1. **Which client evaluator runs on which arm?** LLP 0329.014's settled result
   is "ship the TypeScript twin on every arm; do not ship WASM." That is a
   correct *web* verdict being read as universal, and it collides with a no-JS
   native Contract tier.
2. **Does local-first require a substantial client bundle?** **No — 7,794 gzip
   bytes**, and that number changes several arguments.
3. **How does Snapback 2 meet Aquifer, and should Aquifer change?** Aquifer's
   provider seam is "rows and writes." Snapback 2's value is that the client
   *re-executes the program*, and the artifact that makes that sound — the
   closure receipt — has nowhere to cross that seam.

## F1 — The evaluator axis is "does this arm host a JS runtime," not native-vs-web

LLP 0329.014's spike lane S3 measured a hand-written TypeScript evaluator over a
receipt-seeded range-indexed store as byte-identical to Rust on a 75-case corpus
under Node 25 and JavaScriptCore, at **20,826 raw / 7,794 gzip bytes and 3.2 ms
median cold first replay**, against a size-optimised Rust→`wasm32` *read-only*
subset that was **14× larger and 1.8× slower**. Its conclusion: ship the twin
everywhere, ship no WASM.

Both measurements are about **web delivery** — bundle bytes and cold start from
the network. Neither applies to a native Contract tier:

- native compiles to `aarch64`/`x86_64`, **not `wasm32`**, so the 14×/1.8×
  penalty is not incurred at all;
- there is no bundle to download and no cold start from the network — the
  evaluator is a linked module inside a Rust binary already being shipped.

The artifacts exist. `spikes/bounded-programs/src/client.rs` is an in-process
Rust client store, hydrated from a closure receipt, using **the same interpreter**
as the server for local mutations and query replay. And Exact's
`contract-native/` crate — "Rust Contract execution tier" — already carries an
1,811-line Snapback data evaluator (`data_tier.rs`) with **no JS engine in its
dependency graph** (verified: `serde`, `serde_json`, `ryu-js`, `sha2`,
`exact-kernel`, `taffy`).

**The proposed rule:** each arm uses the evaluator whose runtime it already
hosts.

| Arm | Hosts a JS runtime? | Evaluator |
|---|---|---|
| Web | yes | TypeScript twin |
| React Native / Expo | yes (Hermes) | TypeScript twin |
| Contract-native macOS/iOS | **no** | **Rust (shared interpreter)** |
| Server | no | Rust |

Note this puts React Native on the TypeScript side *despite being a native app*,
which is why native-vs-web is the wrong axis to reason with.

The implementation count stays at **two** — Rust and TypeScript — which is
exactly what Snapback 1 already carries (`storage.rs` + `ir-evaluator.mjs`,
LLP 0329.010 H1). This adds no third implementation; it assigns the existing two
sensibly.

**And on the arm that matters most it is strictly better.** The TypeScript twin
is a second implementation held byte-identical by a frozen corpus plus a
hydration replay check that re-executes on every hydration and degrades to a
result cache on divergence. That machinery manages a divergence risk a
shared-interpreter Rust client **does not have**. On an arm where bundle size
does not bind, adopting the twin buys a permanent conformance obligation for
nothing.

**Recommended amendment to LLP 0329.014:** "ship the TypeScript twin on every
arm" → "on every arm that hosts a JS runtime."

### A detail that argues for the Snapback 2 value model

`contract-native` depends on **`ryu-js`** — a crate whose entire purpose is
formatting floats exactly as JavaScript's `Number.prototype.toString` does. That
is Snapback 1's JavaScript number semantics being emulated in Rust *with no JS
engine present*. Under Snapback 2's i53/no-floats model the dependency is
unnecessary, because integers format unambiguously. Removing the JS VM does not
remove JS semantics; **changing the value model does.**

## F2 — Local-first is not a substantial bundle

The measured artifact is **7,794 gzip bytes** and it is not only the evaluator:
LLP 0329.014 describes it as "a hand-written TypeScript evaluator **over a
receipt-seeded range-indexed store**." So the local execution core *and* its
store fit in under 8 KB gzip, cold-replaying in 3.2 ms.

For contrast, LLP 0329.010 measured Snapback 1's client at ~120k lines in
`snapback-client` plus a 714-line `ir-evaluator.mjs` and a 728-line
`derived-overlay.mjs`. Snapback 2's local-first core is not marginally smaller;
it is a different order of thing.

**What that changes:**

1. **It removes the standard argument against local-first by default.** At 8 KB
   there is no bundle-cost case for making offline opt-in. LLP 0329.015 F4 found
   the offline milestone needs *rendering plus an ordered queue*; both fit here.
2. **It is why WASM lost on web**, and only on web: 14× of 7.8 KB is ~110 KB,
   which is a real budget against a real alternative.
3. **It reframes F1.** Because the twin is small, "use Rust on native" is not a
   size argument at all — it is an argument about not maintaining a second
   implementation on an arm that never needed one.

A caveat worth stating: 7,794 bytes is the *evaluator and store*. Subscription
management, the outbox, and the sync protocol are not in that number, and
LLP 0329.014's own limits list effects, channels, scheduler, and outbox
settlement as unbuilt. The claim is that the execution core is small, not that
the whole client is.

## F3 — Aquifer's seam cannot carry the artifact that makes offline sound

Exact LLP 0498 defines **Aquifer** as Exact's data tier: data in **cells** with a
layered identity, one state machine, a **Rust cell engine** in the plan runner,
and a single edge — the **provider**, "a typed capability declaring how to
subscribe to rows and how to perform writes." Its position on backends is
explicit:

> **Snapback is a provider behind Aquifer — the default one if LLP 0179 is
> ratified — never the architecture itself; Exact's knowledge of any backend ends
> at rows and writes.**

Aquifer also already owns the concerns Snapback 2's client owns. §4.7:
"Persistence, offline, and restoration are **cell policies**… Offline is cells
served from the local store with **staleness stated truthfully**… local-first is
a provider choice plus policy, not an app rewrite." Its constraint 6 is "honesty
under degradation."

**The layering is right and the seam is too narrow.**

Right: a provider that encapsulates local re-execution and presents rows is clean,
and it keeps Exact ignorant of Snapback's internals, which is the stated goal.

Too narrow: a cell served from a local store can be stale **or incomplete**, and
those are different. "Rows and writes" can express the first and not the second.
Snapback 2 computes the second precisely — `client.rs` already carries
`LocalState::{Fresh, Predicted, Partial(Vec<String>)}`, where the `Vec<String>`
is the exact partial site ids, and the closure receipt carries coverage, halo,
and the N+2 key. **All of that is discarded at a rows-and-writes boundary.**

So Aquifer's constraint 6 — honesty under degradation — is unsatisfiable for a
local-first provider through the current seam, because only the backend knows
whether a local answer is complete, and the seam has no field for it.

**Recommended change to Aquifer: widen the provider seam from "rows and writes"
to "rows, writes, and a completeness receipt."**

- It is additive and backend-neutral: a provider with no receipt reports
  `unknown`, which is what every non-Snapback provider will do, and Aquifer's
  policy can treat `unknown` exactly as it treats today's cells.
- It is what makes `Partial` renderable honestly rather than as a silent empty
  list — the failure mode LLP 0329.015 K2 found three model families
  independently produce.
- It avoids the duplication risk: without it, Aquifer will build its own
  completeness/staleness notion at the cell layer while Snapback maintains one at
  the data layer, and the two will disagree — precisely the "four documents
  lawfully disagree" problem LLP 0498 exists to end.

**Second, smaller recommendation.** Aquifer's write side (§4.6) already emits
typed outcomes and receipts, and describes optimistic UI as "a cell overlay
pinned to a pending write receipt, reconciled on" settlement. Snapback 2 derives
its optimistic overlay from the mutation IR by re-execution. These should be the
same mechanism, not two: Aquifer's overlay should be *fed* by the provider's
prediction rather than computed beside it.

## Confidence

High on F1's factual basis: the measurements are quoted from LLP 0329.014, the
`contract-native` dependency graph was read directly, and `client.rs` exists.
Medium-high on the recommendation, which is an inference that a web-delivery
verdict should not bind a native tier — persuasive but not measured on native.

High on F2's number, which is quoted. Medium on its interpretation, since
subscription/outbox/sync are excluded and unbuilt.

Medium on F3. The Aquifer reading is from LLP 0498's own text, but that RFC is
large, Draft, and moving; I have read its summary and §4.6/§4.7 rather than all
of it, and it explicitly declines to make the Snapback-as-engine decision
(LLP 0179). The recommendation may already be contemplated in a section I did
not read.

## Open questions

1. Does "ship the TypeScript twin on every arm" intend to include a no-JS native
   tier? If yes, the no-JS premise fails and that should be stated; if no, the
   sentence needs the qualifier in F1.
2. Is `contract-native`'s existing `data_tier.rs` the intended home for a
   Snapback 2 evaluator, or does the bounded-program IR get its own crate?
3. Does Aquifer's provider seam already contemplate a completeness signal
   somewhere in LLP 0498 §4 that this document did not read?
4. Who owns the local store when both sides have one — Aquifer's cell
   persistence (`exact-sqlite`, per §4.7) or Snapback's receipt-seeded store?
   Two stores with two eviction policies is the concrete duplication risk.
