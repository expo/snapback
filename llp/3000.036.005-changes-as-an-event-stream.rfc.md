# LLP 3000.036.005: `/changes` as an event stream

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4's HTTP host (`crates/snapback4`: `serve_changes.rs`, the long-wait pools, vendored `tiny_http`), the wire contract (`SERVER.md`, `CLIENT-AND-OPERATIONS.md`, `guide wire`), presence (`connected[p]`, engine state), and through Exact2 the Snapback client's live reads (Exact2 LLP 1110 D9)
**Author:** Claude Opus 5.5 for Charlie Cheever
**Date:** 2026-10-21
**Related:** [LLP 3000.036](./3000.036-what-the-app-farm-asks-of-the-rule-language.rfc.md) §6 (idle live clients; the stream contract this RFC meets), [LLP 3000.036.004](./3000.036.004-security-invariants-and-exposure.rfc.md) (exposure), [`NOT-DOING.md`](../snapback4/NOT-DOING.md) ("no broadcast event stream"), the ticket [`issues/20261008-snapback4-changes-event-stream.md`](../issues/20261008-snapback4-changes-event-stream.md), Exact2 LLP 1110 (`llp/1110-live-snapback-reads.rfc.md`: D9, server-sent events behind `Snapback.changes()`), Exact2 LLP 1016.000 (answers that keep coming) and LLP 1069.004 (SSE as built), Exact2 `apps/harmony` (`f79dcad812`)

## 0. Summary

`GET /changes` asked with `Accept: text/event-stream` answers as server-sent
events instead of one JSON body. It takes the same parameters, credentials,
handshake and admission as a held poll. It sends an event exactly when a
held poll from the same cursor would have returned, and each event is a
**wake hint**: the new head as the event `id`, with the generation and store
identity. A client that needs the interval's invalidation asks the existing
unheld `GET /changes?since`; a client that only re-reads (most Exact apps)
needs nothing more.

It lands on today's thread-per-wait host. A stream is counted as one held
wait in the viewer pool and the principal's share for its whole life, and
refused with today's `E_STREAMS`. A live client already holds one wait
continuously, so a stream costs what a held poll costs and saves the
re-poll every 25 seconds. Evented parking (§6 B against C) stays the later
step for tens of thousands of idle viewers, unchanged by this RFC. That
means revising one sentence of §6's recommendation, and §2 asks for that
ruling.

## 1. Motivation

An Exact app cannot follow `/changes` directly today.

- **An Exact stream reads only SSE or WebSocket.** A `fetch` with
  `exactStream` reads an `http(s):` URL as server-sent events and a `ws(s):`
  URL as a WebSocket. A reply that is not an event stream ends the stream
  with `{type: 'error', kind: 'Response', status, …}` (Exact2
  `docs/reference.md`, "An answer that keeps coming").
- **An ordinary source cannot hold the long poll.** An Exact answer is
  bounded. An answer in flight holds `clock settle`, so a held
  `/changes?wait` stalls every test. Natively, the Snapback device serves
  one answer at a time. The farm's builders said so and polled on a timer
  instead (§6: 92 of 93 GPT and 69 of 82 Muse apps in v4, median 5 s).
- **So an app that wants live reads writes a proxy.** Harmony, the team chat
  in Exact2 `apps/harmony`, reads `${origin}/live?as=<persona>`: a front that
  holds one `/changes` long poll per persona and re-emits each answer as an
  event. The proxy is in neither repository. Without it the stream answers
  404 and the app falls back to a 10-second tick. Every app that wants this
  writes the same proxy again, and the server still pays a held wait per
  viewer behind it.
- **The Exact-side alternative is not on main.** LLP 1110's async-iterator
  answer, with `Snapback.changes()` over the long poll, stopped at review
  round 4 (NOT READY from both families) on a branch. Even when it lands,
  its D9 names server-sent events from Snapback as the transport behind the
  same call.

The ticket asked for this on 2026-10-08. §6 recorded the direction as
approved (SSE, with the endpoint designed by Snapback's lead session) and
deferred it behind measuring evented parking. This RFC is that design.

## 2. The gate, revisited

§6's recommendation says: "high that idle streams must not each hold a
worker before SSE ships". That was written against a wait pool of 32, where
"a stream that pins one while idle would exhaust them at 32 viewers" (the
ticket). Option A has since landed (§6, "Implemented: option A"; `SERVER.md`,
"Long-wait capacity"):

- 1,024 viewer waits by default, up to 4,096;
- a share of 16 per principal;
- claim polls in a pool of their own;
- `E_STREAMS` refusals;
- about 85 KiB, two threads and four descriptors per held wait, with `/q`
  at 0.21 ms p50 under 1,024 held.

A live client on the published client already holds one wait almost all
the time: it re-polls within moments of each answer or 25-second deadline.
A stream held on the same thread costs the same. It also removes, per
viewer per 25 seconds:

- a new request and its admission;
- the entry read of the store (LLP 3000 finding 5);
- a presence leave and re-enter (`serve_changes.rs:52-55`, `:121`);
- the burst of re-polls after every commit (the measured "all re-poll at
  once" column).

The capacity ceiling is identical with or without SSE, and so is the step
that raises it.

**Ruling asked:** option A meets the gate for an SSE `/changes` on the
thread-per-wait host, counted as a held wait. Evented parking (§6 B against
C, with its 10,000-stream measurement) remains the step for idle viewers
beyond 4,096 per host and is not a precondition for D1–D9.

## 3. Design

### D1. A stream is one held wait

Opening a stream takes a viewer long-wait permit and one unit of the
principal's share (`shared.long_waits.enter`, `serve_changes.rs:30-36`),
and holds both until the stream ends. A full pool or share is refused before
any byte of the stream, with today's JSON refusals:

- 503 `E_STREAMS` with `Retry-After: 2` when the pool is full;
- 429 `E_STREAMS` with `Retry-After: 5` when the principal's share is used.

An Exact app sees either as `kind: 'Response'` with the status and body, so
it can show the refusal. There is no new pool, knob or connection cap:
`--long-waits` and `--long-waits-per-principal` bound streams and held
polls together.

### D2. The request

`GET /changes` with an `Accept` header that names `text/event-stream`.
Exact's native SSE fetch sets that header when the app does not
(`host/apple/src/executor_stream.rs`, `accept: text/event-stream`), and so
does a browser's `EventSource`.

- **Parameters.** The parameters are the held poll's: `since`, `store_id`,
  `eph`, `ephi` and `ephTables` (`SERVER.md`). `wait` and `heartbeat` are
  ignored.
- **Resume cursor.** The `Last-Event-ID` header wins over `since`, and an
  absent cursor is 0.
- **Credentials.** The request goes through `principal_of`, the device
  handshake and `persona_read_authority`, as the poll does
  (`serve_changes.rs:20-51`). Exact's native SSE request forwards the app's
  headers, so `Authorization: Bearer` and `x-snapback-persona` work
  unchanged.
- **No credential in the URL.** `principal_of` reads credentials from
  headers only (`serve_identity.rs`), and a stream adds no query-string
  credential: URLs are logged. (`serve_following.rs` takes a `token`
  parameter for its own route; that route is untouched here.)

### D3. The response, and the first event at once

200 with these headers:

- `Content-Type: text/event-stream`;
- `Cache-Control: no-store, no-transform` and `X-Accel-Buffering: no`;
- chunked transfer;
- the CORS, connection, ephemeral and latency headers that the poll's
  heartbeat frame writes (`serve_changes.rs:243-247`).

**The first event is sent at once**, after the entry read. It carries the
current head even when that equals the cursor. An Exact stream resource is
`pending` until its first message, and until then it holds `clock settle`
(LLP 1110 Summary; LLP 1016.000 D5). A stream that stayed silent until the
next commit would stall every test, which is the failure that kept builders
off the long poll.

### D4. Events are wake hints, emitted when a poll would have returned

A durable event:

```
id: 1042
event: changes
data: {"seq":1042,"generation":3,"store_id":"st_…"}
```

When the request carried ephemeral parameters, an ephemeral event is sent
without an `id` (so `Last-Event-ID` stays a durable cursor):

```
event: ephemeral
data: {"epoch":17,"incarnation":"…","tables":["typing"]}
```

**When an event is sent.** The stream runs the poll's loop
(`serve_changes.rs:64-118`) without returning. It sends an event whenever
the loop would have answered, other than at the deadline:

- the durable head moved past the stream's cursor;
- the generation or the store identity changed;
- an interesting ephemeral table changed, or the incarnation reset, paced
  as today (100 ms);
- a time audience opened.

After sending, the stream's cursor is the sent head. A publication that
lands while an event is being written coalesces into the next event, so a
burst of commits costs one event per stream for each write it can take.

**Why hints and not answers.** There are three reasons:

1. **Exact coalesces.** Messages that arrive faster than they commit
   coalesce to the newest (Exact2 `docs/reference.md`). An event that
   carried an interval's invalidation could be dropped, and the client would
   advance past a commit it never invalidated: the failure §6's contract
   names. A hint is idempotent, and the newest one supersedes the rest.
2. **One encoding of the contract.** The interval answer stays the existing
   `/changes?since` reply, whole: interval tables, saturation, `preserved`,
   settlement `changes`, store identity and generation. Nothing is encoded
   twice.
3. **It is cheap to send.** A hint names no viewer, so one publication
   serializes one durable payload for every stream.

The cost is one unheld `/changes?since` per wake for a client that tracks
invalidation. An unheld poll is never counted against the share or the pool
(`SERVER.md`).

### D5. Heartbeats, write failure and lifetime

- **Heartbeats.** An SSE comment (`:` and a newline) every 15 seconds keeps
  proxies with an idle timeout above that from closing the stream.
  `SERVER.md` gains that requirement, and that buffering must be off.
- **Write failure.** A failed or timed-out write ends the stream and
  releases its permit, share and thread. The vendored host already bounds
  writes (`vendor/tiny_http/src/limits.rs:146`, `:172`), so a stalled reader
  is cut off rather than parking its thread. One slow reader affects only
  its own thread, which is §6 B's concern about a shared parking thread and
  does not arise here.
- **Lifetime.** A stream ends after 30 minutes with
  `event: end` / `data: {"reason":"lifetime"}`. The client reopens from its
  cursor. This bounds anything a long-lived connection could leak and lets
  a fronting balancer rebalance. Exact's host never reconnects on its own
  (`executor_stream.rs`, module comment), so the app refreshes its resource
  with the cursor as an argument, as Harmony's `live` already does after a
  drop.

### D6. Credentials stay live

A bearer stream rechecks the session:

- before an event, when its last check is more than a second old;
- and at least every 25 seconds while idle, today's poll cap, so a
  revocation is noticed no later than it is now.

The recheck uses the poll's pooled-reader recheck (`serve_changes.rs:122-148`).
A failed recheck sends `event: denied` with the refusal JSON
(`{"denied": …}`) and ends the stream. A client must not reopen with the
same credential. Persona and loopback-development credentials behave as
they do for polls.

The cost is bounded by what is measured: one commit rechecking 4,096 bearer
polls takes 1.5 s today, because each answered poll rechecks. The
one-second floor keeps a burst of commits from paying it more than once a
second.

### D7. Presence follows the stream

A Full-session stream enters presence on open, as a held poll does
(`serve_changes.rs:52-55`). It leaves when the stream ends for any reason:

- a failed or timed-out write;
- denial;
- the lifetime ending;
- shutdown.

A closed client is found at the next write, so a viewer who leaves is seen
within a heartbeat (15 s) plus the write timeout, inside the 35-second
grace that `connected[p]` already allows (`PRESENCE_GRACE`). The five-second presence refresh
(`PRESENCE_REFRESH`, `snapback4-core/src/engine/mod.rs`) is unchanged. Reader-scope sessions never enter
presence (LLP 3000.033 §1.2).

### D8. Interest is global, as for polls

A stream wakes on every publication, as a held poll does. A viewer whose
partitions did not change still receives a hint, and its `/changes?since`
answer names no table it holds. Interest by partition is the refinement
§6's contract names. It applies to polls and streams alike, and it is not
part of this RFC.

A hint reveals the global head and the timing of its movement. `/changes`
already returns both to any authenticated principal, so this adds no
exposure; LLP 3000.036.004's owner is asked to confirm (§5).

### D9. Not a broadcast stream

NOT-DOING excludes "a broadcast event stream" (`NOT-DOING.md:38`). This is
not one, as §6 already observed: each stream is a single viewer's cursor,
admitted under that viewer's credential and bounded by its share, and it
carries nothing a poll does not. NOT-DOING does not change.

## 4. Clients

- **Exact apps.** A stream resource fetches
  `${origin}/changes?since=<seq>` with its credential headers. Its mapper
  returns `{ seq }` from each `changes` event and the state from `end` or
  `denied`. The reading resources take `seq` as an argument, so a change
  asks them again. Harmony's `live()` points at `/changes`, and its proxy
  goes away. Snapback's lead session owns nothing on that side.
- **Exact2's Snapback client.** LLP 1110 D9: `Snapback.changes()` switches
  its transport to the stream when the server advertises one. The
  advertisement is a response header, `X-Snapback-Changes-Stream: 1`, on
  timed responses and poll heartbeats. It mirrors `X-Snapback-Ephemeral`
  and is exposed to browser JavaScript, so discovery costs no request.
- **The published JavaScript client.** It keeps the long poll in this RFC.
  Moving it to the stream is a later change, on its own measurement.
- **The device client** (`exact-snapback4-client`). Unchanged. It already
  turns `/changes?since` answers into invalidation.

## 5. Open questions

1. **The gate (§2).** Charlie's ruling: is option A enough for an SSE
   `/changes` on the threaded host?
2. **Browser `EventSource` credentials.** A browser's `EventSource` cannot
   set headers. Cookie sessions would serve same-origin pages, if Snapback
   wants them. Otherwise browser code uses `fetch` streaming (which can set
   headers) or the published client's long poll.
3. **Constants.** The 15-second heartbeat, the 30-minute lifetime and the
   one-second recheck floor are proposed, not measured.
4. **Exposure.** Does LLP 3000.036.004 agree that the hint adds no
   exposure beyond `/changes?since`?
5. **Postgres serving** (LLP 3000.009.001). A stream inherits whatever wake
   signal held polls use there. The adapter's owner should confirm that a
   permanently held wait does not hold a Postgres connection while idle,
   the way a parked poll holds no SQLite connection today.

## 6. Verification

Tests in `crates/snapback4`, each failing before the change:

- the first event arrives at once, at the cursor;
- `Last-Event-ID` resumes and wins over `since`;
- a commit sends exactly one event per stream, and a burst coalesces;
- generation, store-identity and incarnation changes each send one event;
- ephemeral events are paced at 100 ms and carry no `id`;
- the share and pool refusals (429, 503) arrive before any byte;
- a revoked bearer session ends with `denied` within 25 seconds;
- presence leaves on client close, write timeout, denial and lifetime;
- a stalled reader is cut off at the write timeout and its permit returns;
- a time audience that opens sends an event.

Measurement: `scripts/measure-long-waits.py` gains a stream mode and
repeats the `SERVER.md` table at 256, 1,024 and 4,096 streams on the M5
MacBook. It reports RSS, threads, descriptors, `/q` p50/p99 while held, and
commit-to-event latency (persona and bearer). Acceptance is no worse per
viewer than the held-poll rows. A second run adds one commit per second for
five minutes and compares total requests and CPU with held polls; the
saving is the claim of §2.

End to end: Harmony on Exact2 with no proxy. Its six web tests pass, and a
two-persona test sees B's write in A's view in under a second with no tick.

## 7. What it touches

- **Periphery:** the route, the framing, and the counting in the existing
  pools.
- **Core:** the event schema is a client-contract addition (§6, "What it
  touches"), and presence lifetime is engine state that rules read. Both
  need the lead's review.

The implementation order:

1. the host;
2. the stream mode of the measurement;
3. the advertisement header;
4. Exact2's client and Harmony, in that repository, by its owner.
