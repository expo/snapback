## Summary

The founder asked whether the Snapback 2 query language must be embedded in
Contract as TypeScript, or whether a different surface form could lower to the same
bounded-program IR — on the intuition that a language which *looks like* TypeScript
but is not one invites agents to write valid TypeScript that is not a valid program.

The intuition is correct and the project's own evidence already supports it. The S2
TypeScript front end (`frontend-ts/REPORT.md`) **failed its gate**: 18 of 27
code-bearing gauntlet shapes lower (66.7%, against a 70% bar), 17/27 under strict
one-line accounting.

This document reports a prototype of the alternative and what it measured.

**Result: a Contract-block surface lowers 17/17 S1 corpus programs to identical IR
— matching the TypeScript front end's equality result — and refuses 8/8 of that
front end's known-bad first attempts at parse time.**

Prototype: `spikes/bounded-programs/frontend-contract/`. Reproduce with
`node frontend-contract/check.mjs` and `node frontend-contract/first-attempts.mjs`.

## Findings

### C1 — Subtractive versus additive is the mechanism

The TypeScript front end fences the language by **subtraction**: a `noLib`
environment removing `Date`, `Math.random`, `fetch`, `setTimeout`, and `eval`, plus
an AST policy pass refusing `while`, ambient time, recursion, and `async`/`await`.
Every removal is a place where an author writes well-formed, type-checking
TypeScript that is then rejected.

A Contract-shaped grammar is **additive**: only what it names exists. The eight
known-bad attempts fail as parse errors:

| Attempt | Contract-surface outcome |
|---|---|
| `ambient-time` | `cannot parse expression: Date.now()` |
| `helper-scan` | `scan needs an explicit take=` |
| `split-loop` | `cannot parse loop domain: tokens split(body, " ")` |
| `structural-loop-tally` | `unknown statement "count++"` |
| `structural-rank` | `cannot parse expression: sort(…)[0]` |
| `unbound-count` | `scan needs an explicit take=` |
| `unbound-scan` | `scan needs an explicit take=` |
| `while-loop` | `unknown statement "while"` |

Both front ends refuse all eight. The difference is *where*: type-checks-then-refused
versus does-not-parse.

### C2 — Three grammar choices do the work

1. **Reads are keywords with the index inside the form** — `get users.byId [key]`,
   `scan cards.byParentOrder [key] take=50`. A read without an index does not parse.
   This is the shape that would have caught
   `issues/shelved/20260828-plan-get-accepts-untyped-id-expression.md`, where a TypeScript
   builder accepted a `v.string()` where a document id was required because the
   signature `get(table: string, id: ValueExpr, …)` had nowhere to relate them.
2. **Every read carries its bound.** `take=` is required; three of the eight
   attempts fail on exactly that. In the TypeScript surface a derived loop's bound is
   *invisible in the source*: `thread`'s mention loop carries
   `max: 85, bound_source: "messages.body max 256 / min whitespace mention 3"` in the
   IR, computed by the compiler and never written by the author.
3. **No type annotations**, so nothing implies TypeScript semantics and there are no
   TypeScript priors to misfire.

### C3 — Contract already has most of the shape

Exact's `.contract` grammar (Exact LLP 0216) is indentation-scoped labeled blocks
compiling to canonical JSON IR. Its `action` blocks are *already* a bounded
imperative statement language with `if`, assignment, and — notably — an explicit
declared effect set in the header (`action requestAdd writes draftText,
actionSequence`).

| Contract block | Bounded-program IR |
|---|---|
| `derive x = expr` | pure expression nodes |
| `resource x = …` (already has `.loading`/`.ready`) | a `query` program |
| `action f writes a, b` + `if`/assign | a `mutation` program, with its write set already declared |
| `contract` claims | the certificate layer |

What Contract lacks, and what this prototype had to add, is **the bounds**:
required `take=`, declared argument maxima, cursors, `require … else CODE`, the
modeled inputs (`viewer`, `now`, `newId`), and `recurse … depth= fanout=`. That is
additive syntax, which is the tractable direction, but it is not free.

### C4 — Building the front end exposed three IR facts

Independent of the surface question, authoring 17 programs against the IR surfaced:

- **`provenance` is not derivable from the source.** Three programs are
  syntactically identical — `return scan <table>.<index> [<theOnlyArg>]` — and
  disagree:

  | Program | prefix | provenance |
  |---|---|---|
  | `helperWrappedScan` | `[columnId]` (arg) | `Arg` |
  | `ledger` | `[groupId]` (arg) | `Arg` |
  | `mentionScan` | `[handle]` (arg) | **`Computed`** |

  Either a rule is undocumented or provenance is an authored fact. If authored,
  **both** front ends should require it rather than infer it, and the TypeScript
  front end's inference is a silent-wrongness surface of the kind LLP 0329.009 G2
  already found once.

- **`site` is an authored label, not derived.** Corpus sites are `board.columns`,
  `inbox.memberships`, `helper.cards`; they do not follow from program or binding
  names. A TypeScript surface must derive them from helper identifiers, which makes
  site identity depend on refactoring.

- **The corpus never uses `Upsert`.** `sendMaintainedUnread` spells insert-or-update
  as an explicit `if unread == null / else`, which is more analyzable and suggests
  the node may be unnecessary.

### C5 — Secondary measurements

| Measure | Contract | TypeScript |
|---|---|---|
| S1 equality | 17/17 | 17/17 |
| Bad first attempts refused | 8/8, at parse | 8/8, by policy pass |
| Surface, same 17 programs | 109 lines / 5.4 KB | 256 lines / 8.6 KB |
| Front-end implementation | 349 lines | 2,271 lines |

The implementation figures are **not** like-for-like: the TypeScript front end also
type-checks against a shipped environment, emits mechanical rewrites, and invokes
the Rust checker.

## What this does not show

- **No gauntlet number, and none is possible.** The gauntlet measures whether
  *naturally written TypeScript* lowers. A Contract front end scores ~0% by
  construction. The honest equivalent — Contract-shaped snippets authored by someone
  not implementing the lowerer — does not exist. This document does **not** claim to
  beat 66.7%.
- **I wrote both the grammar and the programs**, so 17/17 is partly a measure of the
  author's own consistency. It is a *feasibility* result, not an ergonomics one. The
  TypeScript front end faced code written by others; this did not.
- **Diagnostics are worse.** Two of the eight refusals produce a generic "cannot
  parse expression" where the TypeScript front end emits a family, a source span,
  and a rewritten source. Nothing about the additive approach prevents good
  diagnostics, but this prototype does not have them.
- **Nothing was run through the Rust `Checker`.** Equality is against committed
  corpus IR, not against a certificate.

## Consequences

1. **The surface question is separable from the IR gaps.** Of the nine gauntlet
   refusals, the composite-identity and async ones are IR and execution-model limits
   that a different surface does not fix. Changing surface addresses the *hazard*,
   not the *coverage*.
2. **If Contract is a target, the grammar is the natural embedding** — extend
   `resource` for reads and `action` for writes rather than inventing a third
   vocabulary. Contract's `action f writes a, b` is already the effect declaration a
   mutation program needs.
3. **Keep the IR as the contract.** Contract-the-language should be one front end
   among several, or a backend language becomes coupled to a UI framework and the
   React/Expo arms lose it.
4. **`provenance` and `site` should be settled first.** Both front ends infer things
   the corpus shows are not inferable.

## Open questions

1. Would an independently-authored Contract corpus reproduce 17/17? Until someone
   who did not build the lowerer writes programs in it, the ergonomics claim is
   untested.
2. Is `provenance` an authored fact? C4 says the corpus cannot be explained by a
   syntactic rule; if so both front ends have a silent-inference surface.
3. Does the additive grammar keep its advantage as the language grows to cover
   LLP 0329.015's missing constructs — `patchWhere`, `sum`, `argMax`, interval
   membership? An additive grammar that grows to 60 forms is a registry again, which
   is precisely what LLP 0329.013 warns against.
