## Summary

The embedded Guide artifact is stored uncompressed. `build.rs` writes
raw `fs::read` bytes for every record and `guide.rs` `include_bytes!`s
the result, so roughly **20.7 MB** of the shipped binary is Markdown and
JSON at full size. Nothing in the artifact path compresses.

Compressing it is the cheapest large capability-preserving reduction
available. Matched measurement over the 187 packed files
(20,658,338 payload bytes):

| Encoding | Whole stream | Per-record |
|---|---:|---:|
| raw | 20,658,338 | 20,658,338 |
| `gzip -9 -n` | 3,452,614 | 3,608,417 |
| `zstd -19` | 1,128,188 | 2,838,299 |

Every Guide URL, response body, and header is unchanged, `contentHash`
is unaffected by construction (§3.3), and no LLP 0061 carriage
amendment is needed.

**Neither LLP 0314 nor the frozen LLP 0314.000 proposes compressing the
artifact.** The withdrawn LLP 0314.001 §2c did consider encoding
compression and dismissed it as "a marginal fix"; its round-1 review
measured that dismissal to be false, and its withdrawal named this
document as successor (§7).

**The proposal settles on per-record `gzip`.** Encoding and granularity
are one coupled decision, not two — the matrix shows why (§4 OQ1) — and
§3.1's normative per-record container depends on it being settled. A
whole-stream container is a different outer envelope and is not what this
RFC specifies. Confidence in the direction is **0.9**; §4 OQ1 records the
revisit triggers.

## 1. What is actually uncompressed

`crates/snapback-server/build.rs` reads each packed path and writes its
bytes verbatim:

```rust
let bytes = if path == guide_artifact::MANIFEST_PATH {
    embedded_manifest.as_bytes().to_vec()
} else {
    fs::read(guide_dir.join(&path))
    ...
```

`crates/snapback-server/src/guide.rs` embeds the result with
`include_bytes!`. `grep` for `compress|gzip|zstd|flate` across
`build.rs`, `guide.rs`, and `guide_artifact.rs` returns nothing. The
artifact is 20,666,784 bytes for 20,658,338 of payload — about 8.4 KB of
path/length framing — and appears once in `__TEXT,__const`.

The five largest records under `gzip -9 -n` (canonical: no filename, no
mtime — the header this RFC requires in §3.2):

| Record | raw | gzip `-n` | ratio |
|---|---:|---:|---:|
| `reference/registry.json` | 5,162,043 | 395,831 | 13.0:1 |
| `guide-flat.generated.md` | 4,084,811 | 942,252 | 4.3:1 |
| `reference/diagnostics-registry.json` | 2,526,048 | 152,099 | 16.6:1 |
| `guide-flat.reference.generated.md` | 2,289,259 | 342,674 | 6.7:1 |
| `reference/diagnostics.md` | 755,033 | 100,712 | 7.5:1 |

The two JSON registries compress 13.0:1 and 16.6:1; the two Markdown flat
projections 4.3:1 and 6.7:1; the rendered diagnostics page 7.5:1. That is
the same redundancy the withdrawn LLP 0314.001 proposed to remove by
deleting records — compression captures it without removing anything.

## 2. What this is worth, stated honestly

**Binary and on-disk: a real win.** From the retained 159,336,256-byte
Darwin binary, per-record gzip projects to roughly **~142.3 MB** and
per-record zstd to roughly **~141.5 MB**, before decoder code and
alignment. The 186,720,037-byte unpacked package lands near **~169.7 MB**
under per-record gzip.

**Download: roughly neutral.** The npm tarball is already gzipped, so
these bytes are already compressed in transit. Do not sell this as
"npm install got smaller." It is a binary and on-disk reduction.

**It composes with LLP 0314.000 Phase 2 in goal, not in format.** Phase 2
relocates the same closed table to a sidecar and reports that the
unpacked package "barely moves" because the corpus still ships;
compression is the missing package-byte win. But Phase 2 is **not
indifferent** to this change, and §3 states the three couplings
explicitly.

## 3. Proposal

### 3.1 A breaking container version

`ARTIFACT_MAGIC` is `b"SNAPBACK_EMBEDDED_GUIDE\0\x01"`, consumed as one
unit labelled `"magic/version"`. **`\x01` is the version.** Adding an
encoding tag under the same magic would silently break every `\x01`
decoder, including `guide.rs`'s own `test_artifact` fixture.

Therefore: **bump the magic to `\x02`.** Keep the closed-table family and
the `guide/embedded-guide.v1.bin` member path Phase 2 pins. Each record
gains an encoding tag and a decoded length.

LLP 0314.000 §Phase 2 pins "the existing closed-table
`embedded-guide.v1.bin` format," and that plan is scope-frozen. This RFC
**requires a one-sentence amendment to that pin** — the sidecar carries
whatever the shared encoder emits, at the same member path. It does not
rewrite the pin silently.

### 3.2 A bit-stable encoder, normatively required

Phase 2 requires one deterministic encoder with two callers
(build-time and pack-time) and authenticates the container through a
compiled-in `artifactSha256`. Non-deterministic output desynchronizes
the compiled digest from the packed sidecar.

Default `gzip(1)` stamps MTIME and the source filename — that is the
trap. The measurements in §1 and the Summary use `-n`, which writes
neither, and the crate this RFC selects, `flate2`, is bit-stable by
default (`GzBuilder` mtime `0`, OS byte `255`, chosen "to have
cross-platform reproducible streams"). Both are already canonical, but
the property must be required rather than inherited:

- **No `gzip(1)` in `build.rs`.** The encoder is a library call.
- **Canonical metadata:** mtime `0`, no filename, fixed OS byte — or raw
  deflate, which has no header and sidesteps the question entirely.
- **Codec backend, version, and level are pinned** and recorded.
- **Both Phase 2 callers must emit byte-identical output** for identical
  input, with a test asserting it.

`artifactSha256` **rotates** with this change. `contentHash` does not.

### 3.3 `contentHash` is unaffected, but only if the decoder decompresses first

`contentHash` is computed over the whole flat plus the two labeled JSON
registries, all uncompressed (`scripts/guide-lib.mjs`, mirrored in
`guide.rs`). `build.rs` copies the already-computed hex into the header
and hashes no payload, so compressing after that copy cannot change the
digest or its domain.

That is the trap LLP 0314.001 fell into, and it is avoided here — but it
is **not automatic**. The decoder must decompress before UTF-8
validation, before hashing, and before populating record bytes. Gzip is
not UTF-8, so the existing validation would otherwise fail closed. Name
that boundary in the implementation; do not treat it as free.

`x-snapback-guide-content-sha256` and `x-snapback-server-build-commit`
are unchanged.

### 3.4 Bounded decoding

LLP 0284 requires canonical sorted paths, the minimum required closure,
UTF-8 for every Markdown/JSON record, manifest validation, and decoded
core-hash agreement **before exposing any record**. Compression adds
attack surface on Phase 2's externally-loaded sidecar path, where the
encoded length is no longer implicitly bounded by remaining artifact
bytes. Required:

- bounded **encoded** size, **per-record decoded** size, and
  **aggregate decoded** size;
- exact decoded-length and EOF agreement with the stored field;
- rejection of unknown encoding tags, trailing members, and concatenated
  streams;
- the all-record validation pass runs over decoded bytes.

### 3.5 No record is removed

The packed set is identical; only its encoding changes. LLP 0061 §4a's
embedded-in-binary, always-served, one-build-matched-corpus decision is
untouched. (Precisely: the **manifest** records each flat's path, byte
count, digest, served path, and MCP URI; the **container** stores path,
length, and bytes with no per-record digest. Compression changes
neither.) `REQUIRED_GUIDE_PATHS` remains a *minimum* required-corpus
check, not an exact closed-corpus check — extra canonical records stay
allowed.

## 4. Open questions

- **OQ1 — Settled: per-record `gzip` via `flate2`. Recorded here with
  its revisit triggers.** Encoding and granularity could not be decided
  separately. The matched matrix: under **per-record**, zstd beats gzip
  by only ~0.77 MB; under **whole-stream**, by ~2.32 MB. Conversely
  gzip's whole-vs-per-record penalty is ~0.16 MB while zstd's is
  ~1.71 MB, because zstd exploits cross-record redundancy that gzip's
  32 KiB window largely misses. Whole-stream favors zstd strongly;
  per-record makes the codec choice nearly free.

  Per-record gzip captures 17.05 MB of the available 19.53 MB, adds no
  new resolved package or version (both `flate2` and `miniz_oxide` are
  already in `Cargo.lock`), and avoids the whole-stream loader problems
  in OQ2. **Revisit triggers:** the OQ3 measurement shows per-record
  decode cost is unacceptable on a hot path; or the ~0.77 MB zstd
  advantage becomes worth a new package; or OQ2 selects eager-retain, at
  which point whole-stream's loader objection weakens and the ~2.32 MB
  zstd advantage should be re-costed. Any of those reopens §3.1's
  container shape and requires a revision, not an implementation choice.

  **Dependency honesty:** gzip is not free. `snapback-server` declares
  neither `flate2` nor `miniz_oxide`; neither appears in
  `crates/allowed-dependencies.v1.json`, and `build.rs` currently has no
  crate dependencies. This adds direct `[dependencies]` and
  `[build-dependencies]` edges, review-governed under LLP 0276 (not
  confinement-gated — that list covers axum, rusqlite, clap, ibex,
  celld-ltx). zstd would additionally add a new resolved package.

- **OQ2 — Eager-retained bytes, or an owned/fallible accessor?** The
  decisive constraint on the loader, and the reason the original "lazy
  LRU" sketch does not work. `EmbeddedGuideFile.bytes` is
  `&'static [u8]` aliasing the `include_bytes!` blob; HTTP builds bodies
  from those static slices, native Guide search scans every Markdown
  record, MCP catalog construction calls `guide::file()` for every
  declared page, and reference lookup retains both registries. **An
  evicting cache cannot back outstanding `'static` borrows.**

  Two honest options: decompress eagerly at first access and retain
  (~20 MB RSS, API unchanged, zero internal migration), or migrate the
  internal accessor to owned/fallible bytes (lower steady-state RSS,
  internal consumer and test migration). LLP 0284's all-record
  validation means **first access decompresses the whole text corpus
  either way** — per-record buys steady-state RSS, not laziness.

- **OQ3 — Decode cost on the real hot paths.** Measure first
  `guide::file()` / `LazyLock` initialization (the actual decode event),
  first cold `GET /_snapback/guide/<page>`, MCP catalog construction
  (which already forces the all-record pass), and `snapback guide
  <query>`, which walks every Markdown record except the whole flat.
  Note the 16 KiB `lookupBytes` budget is symbol-registry slicing, a
  different path.

- **OQ4 — Startup and readiness.** `snapback runtime-qualify` is the
  Hermes/CV-2 probe and does not parse the Guide, so it is the wrong
  gate to watch. The question is whether first Guide initialization
  regresses scale-to-zero cold start and cold RSS, and whether the
  LLP 0123 digest-bound readiness receipt is affected (it should not be).

- **OQ5 — Build-time cost.** This lands in `build.rs`, which runs on
  every clean build. Measure a mid compression level against the maximum;
  the corpus is compressible enough that the difference is likely small.

## 5. What this does not do

- **It does not delete any Guide content.** That was LLP 0314.001,
  withdrawn. Its deletion targets compress 4.3:1 to 7.5:1, so its goal is
  captured without removing records or amending LLP 0061's packed-set
  language.
- **It does not shrink the source corpus.** `guide/` on disk is
  unchanged.
- **It does not change any external contract.** Guide URLs, response
  bodies, response headers, the MCP protocol surface, `check-guide`, and
  the docs-site generator are unaffected — the last two consume committed
  source files and never see the artifact. This is narrower than the
  earlier revision's blanket "no consumer migration": the **internal**
  `guide.rs` accessor may migrate under OQ2, along with its in-crate
  fixtures.
- **It does not make the published surface or the code space smaller.**
  `registry.json` and `diagnostics-registry.json` are large because what
  they describe is large. Both proposals to reduce them were withdrawn
  and neither has a current owner.
- **It does not become a landing gate.** LLP 0189 and LLP 0232 govern.

## 6. Cost

A container version bump in `guide_artifact.rs`, a pinned bit-stable
encoder in `build.rs`, decompression plus the OQ2 loader decision in
`guide.rs`, the §3.4 bounds and their tamper tests, the one-sentence
LLP 0314.000 Phase 2 pin amendment, and the OQ3/OQ4 measurements.

New failure modes are real and must be designed for, not waved away:
resource exhaustion from a hostile or corrupt sidecar (§3.4), and digest
desynchronization from a non-deterministic encoder (§3.2).

## 7. Implementation (landed 2026-08-28)

Implemented at the author's instruction against revision (c). Four files
in `crates/snapback-server`:

| File | Change |
|---|---|
| `Cargo.toml` | `flate2` as a direct `[dependencies]` and new `[build-dependencies]` entry, pinned `default-features = false, features = ["rust_backend"]` |
| `src/guide_artifact.rs` | `ARTIFACT_MAGIC_V2`, encoding tags, `RECORD_HEADER_BYTES`, the two decoded-size ceilings, and the shared `encode_guide_record` |
| `build.rs` | writes v2 records through the shared encoder |
| `src/guide.rs` | v2 decode, `decode_guide_record`, `read_u8`, v2 test fixtures, three new tests |

**Measured result:** the artifact went **20,666,784 → 3,619,265 bytes**,
a **17.05 MB** reduction at **5.71:1** — within 0.3% of §2's projection.

Two choices inside what §3.2 and §4 OQ1/OQ2 authorize:

- **Raw deflate, not gzip.** §3.2 offered it explicitly, and it is the
  stronger option: with no mtime, filename, or OS byte, bit-stability is
  structural rather than a canonicalization step that can be forgotten.
  It is also ~18 bytes per record smaller. A record that would not shrink
  is stored verbatim, so nothing is inflated.
- **The encoder lives in `guide_artifact.rs`, not `build.rs`.** That file
  is already `#[path]`-included by the build script and compiled into the
  library, so LLP 0314.000 Phase 2's "one deterministic encoder shared by
  two callers" becomes true by construction, and the encoder is
  unit-testable. The Phase 2 pin obligation is recorded in
  [LLP 0314.000](./0314.000-reduce-shipped-runtime-size.plan.md) §Phase 2.

**OQ2 resolved as eager-retain.** Stored records remain zero-copy slices
of the embedded blob; deflated records are inflated once inside the
existing `LazyLock` and leaked, which gives them exactly the lifetime the
borrowed slice had. `EmbeddedGuideFile.bytes` stays `&'static [u8]` and
**no consumer migrated** — HTTP bodies, MCP resources, the CLI, and the
reference registries are untouched. The cost is that the decoded corpus
is retained; LLP 0284's all-record validation means first access
decompresses it regardless, so the owned-accessor variant would have
bought steady-state RSS only.

**Verification.** `cargo test -p snapback-server --lib guide` — 14
passed, including `record_encoder_is_bit_stable_and_round_trips` (the
§3.2 test obligation), `hostile_record_headers_are_refused` (all four
§3.4 shapes: unknown tag, lying stored length, over-ceiling declaration,
over-expanding stream), and the pre-existing
`stored_content_hash_must_match_decoded_records`, which is the §3.3
invariant. `cargo test -p snapback --test served_guide_v1` — 7 passed,
asserting HTTP bodies byte-match committed `include_bytes!` fixtures for
the whole flat and every section projection with manifest identity.
`ref-check` clean.

**Still open:** OQ3 (decode cost on first `LazyLock` initialization,
cold `GET`, MCP catalog construction, `snapback guide <query>`) and OQ4
(cold-start and RSS) are unmeasured. OQ1's revisit triggers stand.

## 8. Measurements (2026-08-28) — OQ3 and OQ4 closed

Measured on the canonical publish build,
`SNAPBACK_BUILD_DISTRIBUTION=public-package cargo build --release --bin
snapback`, Darwin arm64.

### Binary impact, now measured rather than projected

| | bytes |
|---|---:|
| Canonical publish binary, **with** compression | **157,178,768** |
| Embedded artifact in that binary | 3,696,607 |
| Same corpus uncompressed | 20,900,889 |
| Therefore the same binary without compression | **~174,383,050** |

The ~1:1 assumption is now verified rather than inferred: the artifact
appears **exactly once and verbatim** in the binary (a 512-byte probe
matches once; the full byte string is present), in `__TEXT,__const`.
Removing N artifact bytes removes N binary bytes.

**Compression is worth ~17.2 MB of shipped binary**, taking the publish
artifact from ~174.4 MB to 157.2 MB. Section detail after the change:
`__TEXT` 115,277,824 (`__text` 74,674,852, `__const` 23,351,560),
`__LINKEDIT` 38,912,000, 264,500 symbols.

### OQ3 — decode cost: not a revisit trigger

Five runs each, cold process, best/mean:

| Invocation | best | mean |
|---|---:|---:|
| `snapback --version` (never touches the Guide) | 33 ms | 36 ms |
| `snapback guide <query>` | 160 ms | 174 ms |
| `snapback guide <exact code>` | 207 ms | 265 ms |

Guide-touching work therefore costs ~127 ms over baseline process
start. Isolating the part this RFC introduced: inflating **all 187
records** takes **12.8 ms** (best of 5). So decompression is roughly
**10% of the guide cost and ~13 ms absolute**; the remaining ~114 ms is
the pre-existing LLP 0284 all-record UTF-8 validation and the Markdown
walk, both of which predate this change.

Every one of the 187 records compressed profitably — zero fell back to
`RECORD_ENCODING_STORED` — at 5.65:1 overall.

**OQ1's decode-cost revisit trigger does not fire.** 13 ms, once per
process, is not a hot-path problem, and it is paid inside the existing
`LazyLock` that already paid 114 ms.

### OQ4 — resident memory

Peak RSS: **12.1 MB** for `--version`, **80.0 MB** for a guide query.
The decoded corpus is 20.9 MB of that; the rest is the Markdown walk's
own allocations.

**Honest limit on this number.** It is the eager-retain cost *in
total*, not the delta this change introduced. Before compression the
corpus was file-backed `__const` that LLP 0284's all-record validation
touched anyway, so most of those pages were resident too; the true
delta is closer to the 3.7 MB compressed source now also being resident
alongside the decoded copy. Separating them exactly needs a
pre-compression binary at the same commit, which was not built. Recorded
as a limit rather than claimed as a result.

### Baseline re-measurement: LLP 0314's figure is confirmed

A local `target/release/snapback` measuring 105,046,880 bytes prompted a
concern that the parent's 159,336,256-byte baseline was stale. It was
not. That binary was a plain `cargo build --release` — not the canonical
publish command — and carried 93,721 symbols against the canonical
build's 264,500. It was never a comparable artifact.

The canonical command produces 157,178,768 bytes *with* compression and
~174.4 MB without, against LLP 0314's documented 159,336,256 for
published 0.1.27. The parent's diagnosis stands; the binary grew with
the code between 0.1.27 and now, and this change roughly offsets that
growth.

## 9. Provenance

This proposal originated as a review finding, not an author hypothesis.
The codex-family round-1 review of the withdrawn LLP 0314.001 measured
the gzip reductions and observed that the encoder writes raw bytes,
concluding that compression is "a credible capability-preserving
alternative, not a marginal encoding tweak" — against that document's own
dismissal of it. That review is the size-and-hygiene cluster artifact
reachable from
[`0314.001-derived-guide-bytes.cluster-pointer.md`](./reviews/0314.001-derived-guide-bytes.cluster-pointer.md);
the quoted sentence is in its LLP 0314.001 section. All measurements in
this document were re-run independently against this checkout.
