## 3. The concrete limitations

### One recipient can exceed a chunk

The delivered digest chunks profiles one at a time, but each recipient's result
is computed atomically. Its source loops over memberships with `first 1000`,
counts period messages with `first 10001`, and loops over follows with
`first 1000`. These are authored bounds, not newly discovered universal engine
limits. Verify their overflow/completeness behavior in a reduced reproduction;
never infer an exact whole-domain total from a bounded page count.

Large bodies and recipient fanout matter as well as row count. The earlier
[measured stop](./3000.011.001.000-digests-beyond-one-chunk.rfc.md#6-implementation-and-measured-stop-2026-09-22)
found that removing the result vector did not eliminate decoded store images.
The optimization did not ship. Its mixed 999-quiet-plus-one-busy fixtures still
exceeded the heap envelope with large bodies or recipient-heavy rows.

### Resuming a count is not enough to make it correct

The preceding chat suggested checkpointing within a recipient. That is a
candidate direction, not a selected implementation. The owning digest LLP
already [rejected a live accumulator](./3000.011.001.000-digests-beyond-one-chunk.rfc.md#4-rejected-live-accumulator):
expiry, tombstones or read-cursor advancement after an early chunk can make a
saved positive count stale. A final membership check does not repair it, and
another non-atomic reconciliation pass moves the race. This plan preserves
that rejection rather than reopening the same design under a new name.

### Ranking still requires query-planning expertise

Trending combines a maintained score and an hour-based index, merges 25 hourly
lanes and filters the exact trailing 24-hour window. It worked, including
zero-like posts. The observed cost is authoring complexity and an incompletely
measured envelope, not a demonstrated wrong answer or slow-query defect.

## 4. Plan A: establish the envelope before changing execution

Reuse existing `digest_count`, Clique simulator fixtures and current metering.
Run the retained matched-period recipient-heavy control plus the 0.3.0
delivered digest on disposable stores. The historical failing range had 5,000
candidates and 4,900 qualifying messages, approximately 31-byte bodies and
50 recipient IDs per row. Large-body fixtures are separate stress cases, not
the explanation of that original failure. Change one workload dimension at a time: unread messages in one chat,
chat count, stored body size, recipients per message and follow count. Include
boundary-minus-one, boundary and boundary-plus-one for authored bounds.
Record exact output/refusal, heap, examined rows, steps, writes, duration and
marker storage. Compare complete counts against an independent unbounded test
oracle, not another invocation of the same capped query.

Separate server query work from browser rendering, replica acquisition and
native lifecycle claims. Measure acquisition only in a labeled additional
scenario; it is not established by the successful authoritative replay.
Retain failed trials and host-load samples. Alternate control and candidate on
the same qualified host, with identical data, indexes, limits and semantics.
Use enough repeated samples to report meaningful tail statistics; declare the
sample count and percentile method before collection. Do not reuse ten maxima
as strong evidence of p95 behavior or rerun only unfavorable points.

Long stress runs stay asynchronous. Use existing tests and run records; add no
sixth gate or generic benchmark platform.

## 5. Plan B: select a correct capacity improvement

First investigate allocation at the store/read boundary, not merely the final
array consumer. A streaming or projected read must actually avoid materializing
unneeded bodies while retaining fields required for rules, expiry and filters.
Preserve dependency tracking, identical count semantics and all work charges.
This is an experiment, not a promise that streaming is compatible with every
adapter or that it solves total-work exhaustion.

If one-recipient work still cannot fit, choose a semantic design before code:

- Exact live output at admission remains the default requirement. A maintained
  summary or transactional validation mechanism must account for all relevant
  changes and fit bounded finalization itself; no such mechanism is selected here.
- Immutable finalized input could support resumable accumulation, but needs an
  explicit product decision about cutoff, late arrivals, expiry and revocation.
  It cannot silently replace Clique's live-at-emission contract.
- An explicit exact refusal remains valid when neither design is established.
  Publish the measured supported envelope and recovery path without emitting a
  truncated count as complete or increasing a constant to claim success.

For any selected resumable design, specify durable progress, restart behavior,
replacement runs, leave/rejoin incarnation, backdated insertion, changed schema,
and bounded cleanup. Final effect admission and the recipient/period marker
must be atomic. Business identity is independent of implementation version;
provider retries keep the same key. Temporary progress may be cleaned up only
after safe finalization; recipient/period emission markers remain for the life
of the store under the existing policy. Deleting a marker requires a separate
rule that prevents old periods from being admitted again. Do not claim
exactly-once external delivery.

Test expiry, deletion, read advance and membership changes between actual
transactions; a single invocation with a pinned clock cannot establish these
races. Add crashes before/after checkpoint and final emission, repeated periods,
empty periods, cap overflow and unknown device coverage where applicable.
A naive paged live sum fails acceptance even if it scales beautifully.

## 6. Plan C: make rolling ranking easier to author and inspect

Extend the existing compiled recipe with the current maintained-score approach:
explicit tie order, cursor continuation, exact window edges, zero scores,
score changes and deletion. Compare all pages with an independent sort/filter
oracle. Do not claim cross-request snapshot consistency unless supplied by the
existing query contract; document how concurrent changes affect pagination.

Use existing `why`/trace/meter surfaces to explain lane count, selected index,
examined work and the actual stopping reason. Distinguish measured consumption
from static guarantees. Add only missing facts; a dedicated rolling top-K
language form waits for repeated consumers that the recipe cannot serve.
Measure follow-graph growth and existing timeline limits in their own scenario,
including a hub and boundary failures; do not infer them from Trending timings.

## 7. Acceptance, order and stop

A precedes B. C can proceed without an engine change after implementation is
commissioned. Ship a capacity change only with equal answers/authority and a
measured improvement on a named previously failing workload under unchanged
ceilings. Record remaining work, memory and fanout bounds. Fresh Clique scoring
is a later broad check, not a substitute for these targeted comparisons.

If store allocations still dominate or correctness requires an unbounded final
pass, retain the measurements and stop that candidate. Three unsuccessful fix
rounds trigger a recorded stop or author decision. No new scheduler, worker
pool, database cache, second interpreter or relaxed authorization is implied.
