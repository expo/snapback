## Summary

LLP 0326 OQ1 is ruled: **Option A** — the committed registry stops
publishing `line`/`column` — with **Option C** (pre-push regeneration) as
a separate, independent landing.

This plan is the sequence. It exists because a survey of the actual code
found five things the parent RFC's landing checklist did not know, two of
which would have broken the build and one of which changes what the
change *means*.

The load-bearing design decision is in §2: **line and column stay in the
internal source-scan API and stop appearing in the published artifact.**
That split contains the blast radius, but it does **not** leave the tests
untouched: the generator's correctness tests index into source by line through
the *published* artifact, so §2a inventories every assertion coupled to
coordinates or raw-site cardinality and relocates the locator ones onto
`diagnosticSourceSites`.

## 1. What the survey found

Verified in this checkout on 2026-08-28. Each item is a correction or
addition to LLP 0326 §5.

### 1.1 There are two coordinate-pinned blocks, not one

The RFC discussed `diagnostics`. The registry also has an `environment`
block: **188 variables across 367 sites**, each with `file`, `line`,
`column`, **and `kind`**. It is separately served — `reference-lookup`
asserts a `diagnostic-environment-slice` match type. A change covering only
`diagnostics` would publish two site dialects in one file. Environment is 367
of 10,571 records (**3.5%**), so the reason to include it is artifact
**coherence**, not magnitude.

### 1.2 Site records are not one shape

Within `diagnostics`, sites come in three shapes:

| Shape | Count |
|---|---:|
| `{file, line, column}` | 9,586 |
| `{file, line, column, kind}` | 607 |
| `{file, line, column, synthetic}` | 11 |

In `diagnostics`, `kind` is absent on 9,597 records and otherwise one of
`received` (378), `declaration` (218), or `reserved` (11). `environment`
sites carry a different `kind` vocabulary with seven values (`read` 260,
`mention` 35, `write` 26, `indirect-read` 15, `declaration` 14,
`remove` 9, `table-entry` 8). The two vocabularies overlap only in
`declaration` and must not be merged.

**The dedupe key is therefore `(file, kind, synthetic)`, not `file`.**
A naive collapse on `file` alone silently merges a `read` with a `write`
and loses classification that the served surface exposes. LLP 0326's own
first estimate made exactly this error; the corrected numbers are in §6.

### 1.3 `schemaVersion` appears in three places but only two validate it

`snapback-diagnostics-registry.v1` is asserted at:

- `crates/snapback-server/src/guide_reference.rs:73` — a hard equality
  check inside the shipped binary;
- `scripts/generate-docs-site.mjs:828`;
- `packages/snapback-cli/reference-lookup.test.mjs:186`.

Round-1 correction: `reference-lookup.test.mjs:186` is **not** a third pin — it
merely constructs a synthetic v1 object (§1.4). There are **two validating
consumers** (`guide_reference.rs:73`, `generate-docs-site.mjs:828`); the fixture
is a Stage 2 update. A schema bump is still a coordinated Rust + JS landing.

### 1.4 Pagination is by record count — but nothing truncates today

`guide_reference.rs` paginates with `DIAGNOSTIC_PAGE_SIZE = 24` under a
`MAX_LOOKUP_BYTES = 16_384` budget.

**Round-1 correction.** An earlier draft claimed real codes truncate today and
that `reference-lookup.test.mjs:39` fixtures would stop truncating. Both are
false. The largest diagnostic record in the current artifact is
**6,255 bytes** as a raw record (`SNAPBACK_CLI_ARGUMENT_INVALID`; ~6,734 bytes
as a full CLI lookup payload) against a 16,384-byte budget,
so **no real code truncates**, and `tests/fixtures/guide-symbol-lookup-v1.json`
contains **no diagnostic cases** at all. The relevant coverage is the synthetic
combined diagnostic/environment fixture at `reference-lookup.test.mjs:169–279`,
which must be updated deliberately. Likewise `reference-lookup.test.mjs:186`
merely *constructs* a v1 object; `reference-lookup.mjs` asserts no registry
schema, so it is not a third schema pin.

The elision string still needs rewording, but **not to "files"**: with the
`(file, kind, synthetic)` key one file can yield several records, so the
paginated unit is a *site record*, not a file.

### 1.5 RETRACTED — the affordance loss is *not* contributor-only

An earlier draft claimed published consumers never receive sites, because
`diagnostic_for_distribution` strips them for
`BUILD_DISTRIBUTION_PUBLIC_PACKAGE`. **That inference was wrong**, and it was
the single most consequential error in the first draft.

That function strips sites only from the *exact diagnostic lookup* path. The
raw artifact is itself published:

- `scripts/guide-lib.mjs:1229–1240` — `projections: {http, mcp, llms}`,
  `servedPath: '/_snapback/guide/reference/diagnostics-registry.json'`;
- `crates/snapback/tests/served_guide_v1.rs:368–379` — the server returns the
  exact committed bytes;
- `scripts/generate-docs-site.mjs:961` — republished into the docs site.

**Consequences for this plan.** v2 is a **public schema change**. It needs
HTTP/MCP/docs-site qualification (acceptance 6), the A-versus-B rationale rests on the
packing contract rather than on unreachability, and LLP 0326 OQ4 is a real open
question about external parsers rather than a formality.

`diagnostic_for_distribution` itself still needs no edit — it removes whatever
`sites` is — and its test remains a useful leak canary.

### 1.5-bis Two formatters render coordinates and will regress

Missed by the first audit:

- `crates/snapback-server/src/guide_reference.rs:606–616` formats
  `"- {file}:{line}:{column}"` inside a `filter_map` with `?`. A record without
  `line` is **silently dropped** — the failure mode is an "Emitting sites:"
  heading with zero rows, which no test currently catches.
- `packages/snapback-cli/reference-lookup.mjs:449–472` renders the same for
  diagnostic and environment sites; it would print `:undefined:undefined`.

Both are in scope (Stage 1.5).

### 1.6 One hazard checked and cleared

`scripts/diagnostics-registry-removals.mjs` reads **historical** registry
blobs via `git show <rev>:<path>`, which looked like a v1/v2 migration
break. It is not: `:220` derives `previousCodes` as
`new Set(Object.keys(baselineRegistry.diagnostics))` — code keys only —
and `diagnosticEmitterEvidence` recomputes locations from live source
rather than from the registry. Its allowlist pins a different schema
(`snapback-diagnostics-code-removals.v1`). **No migration shim needed.**

### 1.7 `buildIdentity.sourceDigest` bounds what this plan can claim

`generate-diagnostics-registry.mjs:608–613` hashes the **raw bytes** of every
entry in `inputPaths` (`:730–747`) — all production sources plus guide Markdown
— and publishes the result as `buildIdentity.sourceDigest`. Removing
coordinates does not touch it. Measured: `sourceDigest` changed in **59 of 60**
sampled registry commits.

So this plan does **not** reduce how often the registry restamps. It reduces
what each restamp *contains*: median 734 changed lines → 8 (§6).

Making the committed identity a digest over the semantic projection would
recover the frequency benefit. That is **explicitly out of scope** here — it
touches build identity, which is load-bearing beyond this artifact, and it is
the same defect class as LLP 0194's 2026-08-28 amendment (a global digest
copied into local projections). Author ruling 2026-08-28: land the coordinate
removal on its own honest justification first, then take the digest fix as a
follow-on reusing 0194's `projectionIdentity` pattern once that lands.

## 2. The design decision: internal versus published

`diagnosticSourceSites` (in `scripts/diagnostics-registry-source.mjs`)
scans source and returns matches with offsets. The generator turns those
into `{file, line, column}` records. Generator tests then verify
correctness by indexing back into the source:

```
.split('\n')[sites[0].line - 1]
```

**Keep all of that.** The scan must still compute coordinates — it is how
a site is located. What changes is only the **projection step** that
writes records into the artifact: add one function, applied to both
blocks, that takes located sites and emits deduplicated
`{file, kind?, synthetic?, count}` records.

### 2a. The locator assertions must move, not merely pass

An earlier draft of this plan claimed the generator's locator tests would
pass unmodified. **They will not.** The four initially identified
coordinate-dependent
assertions in `generate-diagnostics-registry.test.mjs` — at lines 1809,
1867, 2031, and 2219 — read the *published* artifact
(`registry.diagnostics[code].sites`) and index into source with
`site.line`, for example:

```
readFileSync(...sites[0].file...).split('\n')[sites[0].line - 1]
```

They prove the locator is correct, but they prove it *through* the
artifact. Zero coordinate assertions currently go through
`diagnosticSourceSites` directly.

**Those four are not the whole set (round-1 correction).** Further
published-artifact assertions coupled to coordinates or to raw-site
*cardinality* occur at lines 1615/1622, 1631, 1695, 1725, 1822, and 1939 among
others; deduplication changes the cardinality ones even where they never read
`line`. Stage 1 therefore begins with an **inventory** of every assertion
coupled to coordinates or raw-site counts — not a fix of four known lines.

Relocate the locator assertions onto the internal API; that is where they
belong, since they test the scanner and only reach through the projection by
accident of history. Add separate tests for the v2 projection and its
deduplication. Do not let "the tests still pass" be the signal: passing them by
keeping coordinates published would defeat the change.

This is still what makes the change tractable. Framed as "remove line
numbers" it touches the scanner itself; framed as "stop publishing
coordinates" it touches one projection, its consumers, and the assertions the
§2a inventory identifies.

## 3. Stages

Stages 1–4 are one landing. Stage 0 and Stage 5 are independent and may
land in any order relative to it.

### Sequencing note — LLP 0314.002 is in flight (2026-08-28)

The working tree shows LLP 0314.002 under active implementation:
`crates/snapback-server/Cargo.toml`, `build.rs`, `guide.rs`, and
`guide_artifact.rs` are modified, adding `flate2` as both a build and
runtime dependency with a **bit-stable encoder** requirement
(`@ref LLP 0314.002#32-a-bit-stable-encoder-normatively-required`).

That work compresses the embedded guide artifact; this plan changes the
bytes going into it. They are complementary in outcome — Option A hands
the compressor a 31.3% smaller registry — but they collide in timing.
0314.002 is establishing byte-for-byte encoder parity, and this plan
would move its input mid-establishment.

**Land 0314.002 first, then this plan.** Re-measure §6's byte figures
after compression lands, since the interesting number becomes compressed
bytes, not raw. If both must proceed in parallel, the compression parity
fixtures must be regenerated after Stage 4, not before, and whoever lands
second owns that regeneration.

### Stage 0 — Option C, independent

**Status: implemented 2026-08-28.** **The design changed on measurement.** This stage originally said the hook
should *regenerate* projections. Measured on `origin/main`:
`node scripts/generate-diagnostics-registry.mjs` takes **60 seconds**. Adding a
minute to every push, on a repository where many agent sessions push around the
clock, is not viable — and it contradicted this plan's own requirement that the
hook never become a burden or a veto.

The replacement is **240× cheaper and strictly better**. `buildIdentity.sourceDigest`
is a sha256 over the generator's input *bytes*, so staleness can be decided by
hashing the inputs and comparing to the digest the committed artifact already
publishes. Hashing the 760-path input set takes **0.6s**.

Because it only reads, the hazard this stage previously had to reason about —
"regenerate against the pushed tip, not the ambient worktree" — **dissolves**:
nothing is written, so there is no half-regenerated tree to worry about. The
advisory instead states plainly that it evaluated the working tree, so a dirty
tree can report drift the push does not carry.

Implemented as:

1. `scripts/generate-diagnostics-registry.mjs --check-freshness` — the
   `inputPaths` block moved above the expensive scan; the mode emits a
   `snapback-diagnostics-registry-freshness.v1` JSON record
   (`fresh`, both digests, `inputCount`, `regenerateCommand`) and exits 0.
   Read-only; it never writes the artifact.
2. `.githooks/pre-push` — an advisory block that prints the regenerate command
   when `fresh` is false and **never blocks**. Verified: with the generator
   missing, with `node` absent from `PATH`, and with the generator emitting
   non-JSON, the block still completes and returns 0. Staleness stays
   fix-forward (LLP 0189 D-2, LLP 0232).

The check is run unconditionally rather than gated on "a generator input is in
the pushed range". At 0.6s the gating logic would cost more complexity than it
saves, and `inputPaths` spans essentially all production sources anyway, so the
gate would almost always pass.

This closes the *visibility* half of
`issues/20260821-diagnostics-registry-tracks-line-numbers.md`: the staleness
that was invisible in the worktree where the work happened is now named at push
time. It does not close the churn half, which is Stages 1–4.

Verified end to end: a clean `origin/main` checkout regenerates the registry
**byte-identically**, and editing any production source flips `fresh` to false.

### Stage 1 — projection and schema

1. Add the dedupe projection of §2, keyed `(file, kind, synthetic)`,
   applied to **both** `diagnostics` and `environment`.
2. Replace only the **`line`/`column` fallback terms** in the three
   comparators (`:321–325`, `:704`, `:726`). **`:321` keeps `sitePriority` as
   its primary term** — it feeds subsystem classification and is not equivalent
   to `:704`/`:726` (acceptance 7). Coordinates remain available internally, so
   a deterministic first-site choice is still possible; decide explicitly
   whether "first" means lowest computed coordinate or first file lexically,
   and test it.
3. Bump `schemaVersion` to `snapback-diagnostics-registry.v2` and update the
   **two validating pins** from §1.3 in the same commit. The
   `reference-lookup.test.mjs:186` fixture is Stage 2, not a pin.
4. Update `counts` to describe the new record population without losing
   the old totals — `emittingSites` should keep meaning *sites*, with
   published record counts reported separately.

### Stage 1.5 — formatters

Update both coordinate-rendering formatters (§1.5-bis) to the v2 record shape:

1. `guide_reference.rs:606–616` — render file, classification, and
   multiplicity. **Do not leave the `filter_map`/`?` shape**, which fails silent
   on a missing field; make an unexpected record shape loud.
2. `packages/snapback-cli/reference-lookup.mjs:449–472` — the same for both
   diagnostic and environment sites.
3. Add coverage for each: a rendered site list must be non-empty for a code
   with known sites. The current absence of such a test is why this regression
   was invisible.

### Stage 2 — served surface

1. Update the **synthetic** combined diagnostic/environment fixture at
   `reference-lookup.test.mjs:169–279` deliberately, and add coverage for
   diagnostic, environment, and combined grouping and paging. Per §1.4 there is
   no real-code truncation to re-derive; do not claim there was.
2. Reword the elision string from "sites" to **"site records"** — not "files",
   since one file can produce several records under the
   `(file, kind, synthetic)` key. Keep Stage 1.4's distinction:
   `counts.emittingSites` still means sites; published record counts are
   separate.
3. Re-check `DIAGNOSTIC_PAGE_SIZE = 24` against the new record population and
   say explicitly whether it moves.
4. Leave `diagnostic_for_distribution` alone — it strips whatever `sites` is.
   Its test should keep passing untouched; if it fails, the projection leaked.

### Stage 3 — the guide edit

Re-render `guide/reference/diagnostics.md`, whose **"First registered
site"** column becomes `file` without `:line`.

Per AGENTS.md the guide records the paved form, so this lands as a
**reviewed documentation change**, not a regeneration side effect. Resolve
LLP 0326 OQ5 here: render `file`, render `file` plus a site count, or drop
the column. Recommend `file` plus count — it stays a useful pointer and
the count is the fact that actually changed.

Sweep the **whole** of the registry's documented shape, not just this column:
`guide/reference/diagnostics.md` prose claiming the registry "carries every
emitting site", any schema documentation naming `line`/`column`, and the
served-surface description. All are paved forms under the same rule.

### Stage 4 — chain and inventories

Regenerate registry → guide manifest → flats, then run
`node scripts/check-inventories.mjs`. Per AGENTS.md this is the only step
that sees the whole chain; grepping the diff is explicitly not sufficient.

Expect one large mechanical diff. Land it in the same commit as Stages
1–3 so no intermediate commit has an incoherent artifact.

**Produce the real diff-volume number here.** §6's table is a bounded estimate;
this stage is the first point at which a v2 generator exists, so replay it:
regenerate the artifact at a sample of historical commits under the v2
projection and diff the actual committed representation. That result supersedes
§6 and is what acceptance 9 records — acceptance 9's two-week re-run then
validates it against live history rather than establishing it.

### Stage 5 — bookkeeping

Close `issues/20260821-...` recording Option A and the measured result;
drop the LLP 0325 §5c(6) caveat, which exists only to describe this tax.

## 4. Acceptance

1. Both blocks project through one function; no published record carries
   `line` or `column`; the key is `(file, kind, synthetic)` and all
   classifications survive — including the 169 code/file pairs that carry more
   than one.
2. The seven environment `kind` values and the three diagnostics `kind` values
   remain distinguishable, and the two vocabularies are not merged.
3. Every assertion in the §2a inventory is dispositioned: locator assertions
   relocated onto `diagnosticSourceSites`, cardinality assertions updated to
   the v2 population. Unexpected edits to the **scanner** are the smell;
   expected projection/fixture/schema updates are in scope.
4. Both formatters (§1.5-bis) render the **exact** v2 output — file,
   classification, and count — for a code with known sites, proven by a new
   test in each language. A non-emptiness assertion is insufficient: the
   existing CLI path stays non-empty while rendering `undefined`.
5. `public_package_diagnostic_projection_omits_repository_sites` passes
   unmodified.
6. The **published** surface is qualified as a schema change: the served
   `/_snapback/guide/reference/diagnostics-registry.json` bytes, the MCP
   projection, and the docs-site copy all carry v2 coherently, and
   `generate-docs-site.mjs:828`'s schema check is updated.
7. `sitePriority` ordering is preserved and tested — subsystem classification
   must not move.
8. `check-inventories` passes on a **clean checkout**, not only in the worktree
   that generated it.
9. Before/after recorded against §6, including a re-run of the diff-volume
   measurement on post-landing history after ~2 weeks. **Restamp frequency is
   not an acceptance criterion** (§1.7).

## 5. Rollback

Stage 0 is independently revertible. Stages 1–4 revert as one commit;
because the change is a projection plus a schema pin, reverting restores
v1 output exactly — there is no data migration to undo and no historical
artifact is rewritten. Retained v1 snapshots stay readable either way,
since §1.6 confirms nothing reads historical site shape.

## 6. Expected measurements

Simulated on this checkout with the `(file, kind, synthetic)` key. An earlier
draft published 5,215 / 1,698,742 — those came from deduplicating diagnostics
on `file` alone and are **superseded**.

| | Today | After |
|---|---:|---:|
| `diagnostics` site records | 10,204 | 5,385 |
| `environment` site records | 367 | 281 |
| Artifact bytes | 2,526,048 | 1,735,036 (**−31.3%**) |
| **Median changed lines / registry diff** | **734** | **8** |
| Mean changed lines / registry diff | 1,451 | 521 |
| Registry restamps per 30 days | 624 | **~624 (unchanged)** |

The diff-volume figures replay the 40 most recent registry diffs at
`--unified=0`, counting changed lines that are not
`line`/`column`/`sourceDigest`. The restamp count does **not** improve, for the
reason in §1.7.

**Method limit — these are a bounded estimate, not a measurement.** The
diff-volume figures filter `line`/`column`/`sourceDigest` out of *v1* diffs.
They do not replay a real v2 artifact, which additionally deduplicates, carries
`count`, and reorders. A direct replay of the stated projection lands nearby
but not identically (median 7 rather than 8; ~17,800 rather than 20,824 total
changed lines), which is the size of the error to expect. A trustworthy figure
requires generating historical v2 artifacts, which requires the generator to
exist — so acceptance 9 obtains the real before/after at Stage 4 rather than
trusting this table.

Further caveats: the sample is recent commits and may not represent the month;
LLP 0325's file-splitting work will move file paths more than usual while it
runs, which raises residual diff volume; and because `count` is published
(OQ2), edits that change only a multiplicity will restamp records that a
countless projection would not.

## 7. What this plan does not do

- It does not change which diagnostic codes exist, their subsystems, HTTP
  classification, or guide anchors.
- It does not alter any emitted `SNAPBACK_*` wire contract.
- It does not change the *exact diagnostic lookup* projection for the public
  package — but it **does** change the published raw registry, which is served
  over HTTP/MCP/llms and republished to the docs site (§1.5). This is a public
  schema change.
- It does not change `buildIdentity.sourceDigest`, and therefore does not
  reduce restamp frequency (§1.7). That is a sequenced follow-on.
- It does not make generated projections uncommitted, or introduce a
  custody model for this repository's own projections.
- It does not add a landing gate; staleness stays fix-forward.
- It does not touch the symbol-registry churn class — that is LLP 0194's
  2026-08-28 amendment, a good co-landing candidate so the guide
  regenerates once rather than twice.

## 8. Open questions

- **OQ1 — First-site ordering.** Lowest computed coordinate, or first
  file lexically? Affects the guide column's stability; the coordinate
  order is stabler across file splits, the lexical order is explainable
  from published data alone.
- **OQ2 — `count` is RULED KEPT** (2026-08-28), closing the contradiction the
  delta round found. Rationale retained: without it the artifact loses
  multiplicity that `diagnostics.md`'s "Sites" column and both formatters
  render today, and §6's projection assumes it. The cost is that a
  same-file multiplicity change restamps a record a countless projection would
  not — noted as a §6 caveat rather than left open. **Closed; no author
  action pending.**
- **OQ3 — Co-land with LLP 0194's amendment?** One regeneration instead
  of two, against a larger and harder-to-review diff.
- **OQ4 — Does `counts.emittingSites` have consumers** that would break
  if its meaning shifted? Stage 1.4 preserves it defensively; confirm
  whether that is necessary.
- **OQ5 — Follow-on shape.** When the `sourceDigest` fix (§1.7) is taken up,
  does it reuse LLP 0194's `projectionIdentity` naming and schema, or does the
  diagnostics registry need its own? Prefer reuse; decide in that document, not
  this one.
- **OQ6 — Line/path pins.** Every `file:line` pin in this plan was verified on
  2026-08-28, but pins are exactly the volatile fact this document is about.
  Re-verify at implement time rather than trusting them.
