# LLP 3000.011.001.000: A complete digest recipe beyond one chunk

**Type:** RFC
**Status:** Draft
**Systems:** Snapback 4 jobs guide, recipe generation, scheduled digests, progress and effect admission
**Author:** Codex / GPT-6 (for Charlie Cheever)
**Date:** 2026-09-22
**Revised:** 2026-09-22 (initial proposal)
**Related:** [Problem](./3000.011.001-reporting-and-job-complexity.research.md), [LLP 3000.007.002](./3000.007.002-common-application-shapes.rfc.md), [LLP 3000.009](./3000.009-general-purpose-backend.rfc.md)

## 1. Recommendation

Complete the current jobs card with one tested message-paged digest recipe,
then expose it through the existing recipe installer if the example removes
repeated application work. Keep the direct live-read recipe as the small-workload
default. This proposal adds a concrete composition of existing Quarry jobs,
tables and effects; it does not add a workflow engine or a new language form.

The recipe must page the messages of a busy chat as well as the memberships
of a busy principal. A smaller outer chunk around an unbounded inner count
does not solve the observed failure.

## 2. Proposed algorithm

Use the period's immutable time index and the existing job cursor. The
application supplies the period, message/membership mappings, unread predicate
and effect payload. The recipe owns the ordinary Quarry bookkeeping below.

1. Bind one logical digest to a versioned policy and period. A fresh scheduled
   run and a manually requested retry for that same logical digest share its
   business idempotency key. Do not generate a new business period on restart.
2. Sweep period messages in bounded chunks. For each candidate, exclude
   expired, tombstoned, own and read messages according to the declared
   policy, checking each eligible recipient's membership. Bound recipient
   fanout too; choose chunk sizes from measured worst-case work.
3. Atomically admit a contribution and update the corresponding recipient/chat
   total. A contribution identity contains policy, period, recipient and
   message, so replaying a replacement run cannot count it twice. The engine's
   existing cursor commits in that same chunk; no separate progress journal.
4. After accumulation completes, sweep recipient totals. Recheck recipient
   eligibility, exclude conversations whose membership no longer qualifies,
   and atomically write an emission marker with the effect. Emit nothing for
   zero qualifying activity.
5. Re-entering an already completed logical period performs no duplicate
   emission. The external worker uses the same business key with a provider
   that supports deduplication; effect admission alone is not exactly-once delivery.

Bookkeeping tables are job-written and non-readable to ordinary principals.
Totals and raw private message counts must not become a public projection.
Retain the asset and message lifetime rules without cloning message bodies.
Do not keep private bodies or previews in admission markers unnecessarily.

## 3. Consistency, policy changes and cleanup

Existing job chunks do not share one database snapshot. This proposed form
counts eligibility at each contribution's read and checks current recipient
membership again at emission. It does **not** promise an exact snapshot of
all read cursors, edits and expirations at emission time. The small direct
form retains its single-transaction advantage.

A removed-and-rejoined membership must not silently inherit the old lifetime's
contributions. Bind to an available stable membership incarnation, or discard
and recompute that conversation's contribution when continuity cannot be
established. Do not invent continuity from a reused row id. The first prototype
must settle this using the existing membership semantics before installation
is offered.

If the product requires exact emission-time counts over mutable/expiring rows,
this recipe is insufficient without a separate snapshot or reconciliation
design. That requirement must be decided explicitly, not hidden in a helper.
On quiescent data, both direct and paged forms must match the same exact oracle.

Changed policy or job generation must not resume an incompatible cursor.
The existing generation refusal stands. A replacement either uses compatible
contribution identities or explicitly rebuilds an unfinished period. Never
clear a completed emission marker as an incidental part of a retry.

The first increment makes no automatic history-retention deletion promise.
Measure marker storage and document a supported retry horizon before adding
cleanup. Deleting old markers while still allowing arbitrary old reruns would
undo the idempotency contract.

## 4. Delivery if accepted

First extend the existing compiled jobs example and its engine tests; prove
the business semantics before packaging a generator. A generated module may
use an application-selected prefix and typed helpers, following the existing
feed recipe's collision and refusal behavior. Proposed installer support is
unbuilt; existing `init` does not yet promise this digest option.

The recipe should expose only the business mappings and chunk settings an
application must decide. It must state its acquired data and server-only
behavior and show `doctor` output for a parked run. Use the existing meters
to explain an exceeded inner or outer bound.

## 5. Validation and success

Use the same three shapes on control and candidate: many quiet chats, one
10,000-message chat, and both together with large message bodies. Record heap,
examined rows, writes, chunks, total duration and retained marker bytes.
Compare with the 0.2.31 replacement's actual algorithm on identical fixtures;
do not compare its total writes with a smaller workload.

Exercise crash before/after contribution commit, before/after emission,
same-run resume, replacement run, repeated period, changed job definition,
membership removal/rejoin, expiry and deletion during the run, empty periods
and provider retry. On quiescent data, compare exact per-recipient counts to
an independent oracle. Concurrent cases must satisfy the declared consistency
contract and never emit to a currently unauthorized recipient.

Success removes handwritten progress/deduplication scaffolding from a fresh
builder's digest, completes the busy-chat fixture within existing chunk meters,
and gives predictable restart behavior. Any claimed reduction in runtime work
needs a separate paired measurement. Reject a larger generic jobs abstraction
if the tested recipe supplies the benefit; reject the recipe if its live-state
semantics cannot meet the intended product.
