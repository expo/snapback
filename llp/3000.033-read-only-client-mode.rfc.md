## 0. Evidence

The Phase-2 native pilot (2026-10-05) asked each builder for a **read-only
oracle**: a command that signs in as an ordinary user (Bob), pages through his
conversation with the documented API, and prints raw rows for the driver to
compare against the screen. The independent source audit refused the
Snapback 4 lane's oracle, `oracleReadOnly: false`:

> Its ordinary SDK client accepts query delivery manifests and schedules
> delivery-report mutations to /m/<mutation>… Closing afterward does not
> prevent reports during pagination.

The Convex lane's oracle, an ordinary Convex query, passed the same check.
The Snapback 4 builder did nothing unusual. It used `createClient` and a
generated query, as the guide teaches. **Snapback 4 has no way to read as a
user without acting as that user's device.**

Today a client read can change server state in five ways:

1. **Delivery reports.** Every `/q/` answer that reads a receipts-tracked
   table carries a delivery manifest (`snapback4/src/serve.rs:1273`, built by
   `engine/delivery.rs:460-505`). Nothing in the request can suppress it.
   The raw client accepts it as soon as the answer arrives
   (`src/delivery-acceptance.ts:12-19`). `createApp` accepts it at facade
   approval (`app-client.ts:83`, `read-approval.ts:117`). That approval runs
   whether or not anything renders. Either way, the delivery queue posts
   `POST /m/<delivered>` within about 250 ms (`delivery.ts:67-75`,
   `online-delivery.ts:22`). This covers one-shot `query()`, every
   live-watch publication, and every presence re-query.
2. **Presence.** A live `observe` opens `/changes`. The server marks the
   principal connected for as long as the poll lasts (`serve.rs:172-229`).
   When a presence-gated effect is pending, it also runs
   `UPDATE _effect_presence SET reconnected = 1`
   (`engine/effects.rs:287-294`). Either way, `connected[p]` and effect
   timing see a "present" user who is only being observed.
3. **View-once consumption.** A non-ranged `GET /assets/<id>` consumes a
   view-once asset (`engine/mod.rs:782-805`). Any later fetch gets
   `E_ASSET_VIEWED`.
4. **Session rotation.** A client given a `session` refreshes it within 24 h
   of expiry, through `POST /auth/refresh`, which rotates the token
   (`client.ts:437-448, 1222`).
5. **Seen and queued writes.** `useSeen` sends `seen` mutations. A device
   app flushes its durable outbox at start, and it collects delivery debt
   from synced rows without any query (`local-delivery.ts:95-127`).

The only workarounds are unsanctioned:
- a custom `fetch` that strips `delivery` from answers and drops `/m/` posts;
- raw HTTP to `/q/`;
- `snapback4 sql`, which ignores rules, so it cannot read as Bob.

None of them is documented, and none would satisfy an auditor, who must take
the SDK's word for it.

Oracles are the sharpest case, not the only one. The same need appears in:
- **dashboards and admin consoles** that show a user's view;
- **graders and acceptance tests** that verify state without disturbing it;
- **server-side rendering and link previews** fetched on a user's behalf;
- **support tools** that look at a conversation as its member;
- **notification extensions** that peek at a message before the user opens
  the app. A delivered tick here is arguably honest, but it should be the
  author's choice.

Each of these today either marks messages delivered that no device
received, or makes the user look online. Both are wrong facts, not merely
extra traffic.

## 1. The proposal

A **read-only session** is a session whose every request is limited to reads
that leave no trace attributable to the reader. **The server enforces it**,
and the SDK makes it the easy path.

### 1.1 What "read-only" promises

A request made with a read-only credential **never causes an
application-visible state change**. In particular:

- **No mutation** runs. `/m/*` is refused with `E_READ_ONLY` before any rule,
  argument decoding or effect.
- **No delivery is reported.** `/q/` answers carry no `delivery` manifest, so
  nothing can be accepted. A delivery mutation is a mutation, so it is
  refused anyway.
- **No presence.** `/changes` serves change notifications exactly as for a
  full session. It does not register the principal in the presence registry
  and does not touch `_effect_presence`. `connected[p]` is unaffected, and so
  is every presence-gated effect.
- **No consumption.** `/assets/<id>` serves ordinary assets normally, with
  ranges allowed. For a view-once asset it refuses `E_ASSET_READ_ONLY`
  without recording a view, and the refusal reveals nothing a full session's
  `E_ASSET_VIEWED` or `E_ASSET_UNKNOWN` would not.
  - The bytes stay unreadable. A read-only session is not a way to see
    view-once content without consuming it.
- **No session churn beyond its own.** A read-only session can be refreshed
  only into another read-only session (`/auth/refresh` keeps the scope), and
  it can be logged out. It cannot mint, widen or rotate any other session.

**What it does not promise.** Its own creation and expiry are writes to the
auth tables, exactly as for a full sign-in; Convex's oracle has the same
property, and the audit accepted it. Read meters still charge the reader.
Server logs still record the request. Reads see **exactly** what the same
principal's full session would see: same rules, same answers, same cursors,
same refusals. Read-only narrows effects, never visibility.

### 1.2 How a read-only session is obtained

Two ways, both returning an ordinary session object with `scope: "read"`:

1. **At sign-in.** `POST /auth/session` (and the password and persona
   sign-in routes) accept `"scope": "read"`. The SDK's sign-in helpers take
   `{ scope: "read" }`. An oracle signs in as Bob this way.
2. **By narrowing.** `POST /auth/narrow`, authorized with a full session,
   mints a read-only sibling session for the same principal. Its lifetime is
   no longer than the parent's remaining life, and logging out the parent
   does not revoke it.
   - The SDK exposes this as `session.narrow("read")`.
   - This serves dashboards and SSR running beside an interactive session,
     without a second password prompt.

Supervised worker and service sessions (`kind = "service"`) can narrow the
same way. Action sessions (`kind = "action"`) cannot narrow; they are
single-purpose already.

Storage: `_sessions` gains `scope TEXT NOT NULL DEFAULT 'full'`, an additive
migration. `scope` is part of the session's identity in `resolve`. Every
request handler reads it from the resolved session, never from a request
parameter.

### 1.3 The SDK

`createClient({ …, readOnly: true })` and `createApp({ …, readOnly: true })`:

- **Require a read-only credential.** With a full session or token, the
  client refuses at construction with `E_READ_ONLY_CREDENTIAL`. Silently
  degrading a full credential would leave an auditor trusting the flag
  instead of the server.
  - Passing a read-only credential *without* the flag is allowed. The server
    enforces the limits regardless; the client simply sees refusals.
- **Never accept a manifest.** There is none to accept. The delivery queue is
  not constructed, so no timer exists.
- **Refuse writes locally.** Generated mutations and `client.mutate` reject
  with `E_READ_ONLY` without network traffic. The outbox is not constructed.
- **`useSeen` throws** `E_READ_ONLY` on first render in a read-only app. It
  does not silently do nothing: a screen that reports seen state is a write
  path, and wiring it into a read-only app is a builder mistake that should
  be visible. (Open question Q1.)
- **No device.** `createApp({ readOnly: true, device })` is refused with
  `E_READ_ONLY_DEVICE` in this RFC. A local replica's sync, outbox and
  local delivery collection are a larger design (§4). Online `createApp`
  with read-only works fully, including live queries and the facade.
- **Assets.** `client.asset()`, `useAsset` and `assetSource` work. A
  view-once asset surfaces `E_ASSET_READ_ONLY` as an ordinary refusal arm.
- **Identity in answers.** `Read<T>` is unchanged. A read-only client's
  answers are byte-identical to a full client's except that `delivery` is
  absent. The schema-capabilities fence (`sameAnswer`) must keep holding;
  `delivery` is not part of the published answer surface.

### 1.4 Wire and server changes

| Route | Full session (today) | Read-only session |
|---|---|---|
| `POST /q/<op>` | answer + `delivery` manifest | same answer, no `delivery` |
| `POST /m/<op>` | runs | `E_READ_ONLY` (403), nothing runs |
| `GET /changes` | notifications + presence registration (+ `_effect_presence` write when pending) | notifications only |
| `GET /assets/<id>` (ordinary) | bytes | bytes |
| `GET /assets/<id>` (view-once, unconsumed) | bytes, consumes | `E_ASSET_READ_ONLY` (403), no view recorded |
| `POST /auth/refresh` | rotates, same scope | rotates, stays `read` |
| `POST /auth/narrow` | mints `read` sibling | `E_READ_ONLY` |
| ephemeral tables (typing, scoped presence) | read/write | read only; writes `E_READ_ONLY` |

Skipping the manifest for read-only sessions also skips the manifest's
construction cost (`delivery_manifest`'s walk), so read-only reads are
slightly cheaper. They must never be more expensive.

### 1.5 Diagnostics

New codes, each registered with its emitting sites per the inventory rules:
- `E_READ_ONLY`: a write on a read-only session, server or client side;
- `E_READ_ONLY_CREDENTIAL`: the read-only flag with a full credential;
- `E_READ_ONLY_DEVICE`: read-only with a device;
- `E_ASSET_READ_ONLY`: a view-once fetch on a read-only session.

Each `why` names the read-only session and points to `guide read-only`.

## 2. The guide

A new card, `guide read-only` (aliases `oracle`, `observer`, `dashboard`,
`preview`), owns the promise in §1.1 and shows three recipes: an oracle that
pages a conversation as Bob, a dashboard narrowing an interactive session,
and an SSR fetch. The receipts card gains one paragraph: delivery is
reported only by full sessions, and a read-only reader never marks a message
delivered. The client card lists the flag. The native contract's oracle
section (LLP 0201.000 §6, native.2) cites this mode as Snapback 4's way to
build the oracle; plain HTTP to the documented API stays admissible for every
backend.

## 3. Acceptance

The conformance test is a **state digest**. Before and after a scripted
read-only session, hash the application tables plus `_effect_presence`,
the delivery runs and watermarks, asset view records, the presence
registry's view of the principal, and every session row except the reader's
own. The digests must be equal. The session must:

1. sign in read-only as a member, then page a receipts-tracked history to
   exhaustion, including a gap;
2. `observe` it live while another member writes, and receive every change;
3. watch a presence-gated effect (§1.1) stay pending and `connected[p]` stay
   false while the read-only observer is attached;
4. fetch an ordinary asset (full and ranged) and attempt a view-once asset,
   which is refused, then consume it as a full session and verify the
   recipient still gets the bytes exactly once;
5. attempt a generated mutation, `client.mutate`, a raw `POST /m/`, an
   ephemeral write and `/auth/narrow`, and get each refusal with its code;
6. refresh the read-only session and verify it stays read-only.

Plus:
- **answer identity:** a full and a read-only client run the same queries, and
  the answers are equal except for `delivery`, under the `sameAnswer` fence;
- **narrowing:** lifetime capping, parent logout not revoking the sibling, and
  action-kind refusal;
- **construction refusals:** `E_READ_ONLY_CREDENTIAL` and `E_READ_ONLY_DEVICE`;
- **`useSeen`:** it throws in a read-only app;
- **the Phase-2 oracle:** the Snapback 4 lane's real `native-oracle.mjs`,
  changed only to sign in with `scope: "read"` and pass `readOnly: true`,
  leaves Bob's delivered watermark unchanged across a full pagination;
- **budgets:** the wasm device budget (410,000 gz) is not exceeded. Most of
  this is server and TypeScript client code; the device build should not
  grow.

## 4. Not in this RFC

- **Read-only devices** (offline replicas that never report delivery or flush
  an outbox). They need decisions about what a replica that never reports is
  owed, and whether its sync cursors count as reads of record. Revisit if a
  kiosk or offline dashboard asks for it.
- **Per-query opt-out** (`query(q, { deliver: false })` on a full session).
  This is finer-grained, but it makes "no trace" a property of each call, so
  it is easy to forget and impossible to audit. It also cannot cover presence
  or assets. A full session that wants an untracked peek can narrow.
- **Admin or raw reads.** Read-only narrows effects, never rules; `snapback4
  sql` remains the only rule-free read and stays dev or `--release` only.
- **Making notification extensions read-only by default.** Whether a
  notification preview should mark delivery is an app decision. Both choices
  are now expressible.

## 5. Open questions

- **Q1. `useSeen` in a read-only app: throw, or inert?** Throwing makes the
  mistake loud (§1.3). An inert hook would let one component tree serve both
  an interactive app and a read-only preview. The leaning is throw, plus a
  documented `useSeen({ enabled })` for shared trees.
- **Q2. Should `/changes` for a read-only session still feed `connected[p]`
  under a distinct "observer" state?** The leaning is no: observers are
  invisible, and apps that want "someone is watching" can declare it.
- **Q3. Is 403 the right status for `E_ASSET_READ_ONLY`?** Today
  `E_ASSET_VIEWED` uses 410, and the refusal must not distinguish "unviewed
  view-once" from anything a full session could learn. A full session can
  learn this by fetching, so 403 discloses nothing new. Confirm.
- **Q4. Narrowed-session revocation.** Should logging out a parent revoke its
  read-only siblings? The leaning is no (independent sessions, capped
  lifetime), but `logoutAll` must revoke them.
