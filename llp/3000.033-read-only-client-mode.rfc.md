## 0. Evidence

The Phase-2 native pilot (2026-10-05) asked each builder for a **read-only
oracle**: a command that signs in as an ordinary user (Bob), pages through his
conversation with the documented API, and prints raw rows for the driver to
compare against the screen. The independent source audit refused the
Snapback 4 lane's oracle, `oracleReadOnly: false`:

> Its ordinary SDK client accepts query delivery manifests and schedules
> delivery-report mutations to /m/<mutation>… Closing afterward does not
> prevent reports during pagination.

The Convex lane's oracle, an ordinary Convex query after a password login,
passed. The Snapback 4 builder did what the guide teaches: `createClient`
and a generated query. **Snapback 4 has no supported mode in which a client
reads as a user without acting as that user's device.** Raw `/q` over HTTP
is documented (`CLIENT-AND-OPERATIONS.md:2434`), but nothing enforces a
no-trace promise. An auditor must trust the caller's code, line by line.

Today a client read changes server state in five ways:

1. **Delivery reports.** Every non-loading `/q/` answer that reads a
   receipts-tracked table carries a delivery manifest (`serve.rs:1273`,
   built in `engine/delivery.rs:460-505`). Nothing in the request suppresses
   it.
   - The raw client accepts it on arrival (`delivery-acceptance.ts:12-19`).
   - `createApp` accepts it at facade approval (`app-client.ts:83`,
     `read-approval.ts:117`), which runs whether or not anything renders.
   - Either way, the delivery queue posts `POST /m/<delivered>` about 250 ms
     later (`delivery.ts:67-75`, `online-delivery.ts:22`). This covers
     one-shot `query()`, every live publication and every presence re-query.
2. **Presence.** A live `observe` holds `/changes`. On entry the server
   registers the principal as connected (`serve_changes.rs:30-33`). When a
   presence-gated effect is pending, it also writes
   `_effect_presence.reconnected` (`engine/effects.rs:287-294`).
3. **View-once consumption.** A non-ranged `GET /assets/<id>` on an unviewed
   view-once asset is granted by the engine. The HTTP host records the view
   after sending the bytes (`assets.rs:128-131`, `record_asset_view`).
   Later fetches get `E_ASSET_VIEWED`.
4. **Session rotation.** A client holding a `session` refreshes it within
   24 h of expiry through `POST /auth/refresh`, which rotates the token
   (`client.ts:437-448, 1222`).
5. **Seen and queued writes.** `useSeen` sends `seen` mutations. A device
   app flushes its durable outbox at start and collects delivery debt from
   synced rows without any query (`local-delivery.ts`). Online `createApp`
   recovers its own write journal at startup (`app-online.ts:312`).

Oracles are the sharpest case. The same need appears in dashboards and
admin consoles showing a user's view, graders and acceptance tests,
server-side rendering and link previews, support tools, and notification
extensions that peek at a message. Each of these today either marks messages
delivered that no device received, or makes the user look online. Both are
wrong facts, not merely extra traffic.

## 1. The proposal

A **read-only session** is a credential whose requests the server limits to
an explicit set of reads that leave no trace attributable to the reader.
**The server enforces this; the SDK makes it the easy path and verifies it.**

### 1.1 The promise

A request carrying a read-only credential **causes no application-visible
state change**:
- no mutation, action, upload, route handler, claim or settlement runs;
- no delivery is reported;
- the reader never appears in presence and never moves an effect deadline;
- no view-once asset is consumed;
- no other session is minted, widened, rotated or revoked.

**Visibility is unchanged.** Under identical inputs (the same data, clock
and presence state), a read-only request sees exactly what the same
principal's full session would see: same rules, same query semantics, same
cursors, same refusals. Read-only narrows effects, never visibility.

There are four named exceptions, and nothing else:
1. **Delivery.** The answer carries no delivery manifest, and in dev no
   `meter.delivery`.
2. **The viewer's own presence.** A full `observe` makes `connected[viewer]`
   true; a read-only one does not. So a query that reads `connected[viewer]`
   can differ from a full client that is itself polling.
3. **View-once grants** (§1.5).
4. **Writes,** which are refused.

**Outside the promise:**
- the read-only session's own creation, refresh, expiry and logout, which are
  auth-table writes as for any sign-in, plus the expired-session garbage
  collection that sign-in already performs;
- request logging;
- read meters, which still charge the reader;
- **unauthenticated** dev loopback requests to the dev-only doors (`/seed`,
  `/dev/clock/advance`), and dev personas (`x-snapback-persona`), which
  carry no session row and are not credentials this RFC can scope.
  `readOnly: true` with a persona is refused (§1.4). A dev-door request that
  *presents* a read credential is refused by the guard like any other
  non-allow-listed request.

### 1.2 The server guard: a closed allow-list before dispatch

Session resolution returns a **capability**, `(principal, kind, scope)`, not
a bare principal. One guard sits at the **first authenticated branch of
`handle`**. That places it ahead of:
- the declared-session-route return (today `serve.rs:918`, before the
  ordinary matrix);
- the `/m` replay short-circuit (`serve.rs:1136-1152`);
- every handler.

The request permit is taken earlier, in `dispatch`, and background
maintenance runs on its own thread; neither is a write by the reader. The
finalizers that matter, `action_status` and `effect_status_strict`, sit on
routes the guard refuses.

The guard also covers dev doors whenever a credential is present. The `Bearer`
scheme is case-insensitive everywhere credentials are parsed, including auth
operations and detached poll rechecks. Malformed credentials enter this guard.
Any credential presented to an otherwise public or development write door must
resolve before dispatch; it cannot fall through to an unauthenticated write.
Authenticated full-session handlers retain their input-validation and refusal
ordering. The private-proof `/dev/token` door keeps its uniform auth refusal. If the
scope is `read` and the request is not on the allow-list, the guard answers
`E_READ_ONLY` (403). No handler runs. The refusal carries no
`head` or `store_id`, so no client queue can treat it as an accepted write.

**The allow-list for `scope = read`, complete:**

| Request | Behavior for a read-only session |
|---|---|
| `POST /q/<op>` | Same evaluation; the HTTP layer never builds or attaches a delivery manifest (§1.6). |
| `GET /changes` | Change notifications only. No presence registration, no presence leave and no `_effect_presence` write. |
| `POST /sync` | Allowed (a read), for parity with full sessions. The SDK does not use it in read-only mode (no device). |
| `GET /assets/<id>` | The full session's access path; a view-once grant is replaced per §1.5. |
| `GET/POST /probe` | Allowed; reports the bearer's scope (§1.4). |
| `GET /schema` | Allowed: the public projection, programs and `store_id`, no writes. The online client discovers ephemeral support through it before `/changes` can run, on any backend that declares an ephemeral table. |
| `POST /auth/refresh` | Rotates within the read family, under the cap (§1.3). |
| `POST /auth/logout` | Logs out this read-only session's family only. |

**Everything else is refused**, whether or not it is listed here. That
includes:
- `/m/*`, durable and ephemeral;
- `/a/*` actions;
- `POST /assets` uploads;
- declared session routes;
- action and effect claim, settle and cancel;
- `/routes/verify/*`;
- `/auth/session`, `/auth/narrow`, `/auth/revoke` and `/auth/logout-all`;
- any route added later.

New routes are denied to read sessions until someone adds them to this list
deliberately.

### 1.3 Read sessions: storage, minting, refresh and logout

**Storage fails closed.** Read sessions live in a **new table**,
`_read_sessions(token_digest, principal, kind, family, created_at,
expires_at, cap_expires_at, principal_generation)`. They are never rows in
`_sessions`, so:
- an older executable, which knows nothing of `_read_sessions`, cannot
  resolve a read token and refuses it as unauthenticated rather than
  serving it as a full session;
- no insert path can silently default a read session to full.

**Opening and adoption leave no committed changes on refusal.** Opening a
store is not permission to install auth schema before deciding whether its
backend can be used. A refused open or adoption preserves the schema (every
table, index and column), every stored row including `_meta`, and database
integrity. On SQLite the freelist count also stays unchanged. This is a
**committed-state guarantee, not whole-file byte identity**: physical bytes may
differ only in pre-existing free-page contents and journal or WAL residue.
SQLite deliberately [does not journal freelist leaf contents][free-pages], so a
DELETE-mode migration can reuse and overwrite those pages before rollback
returns them to the freelist. Allocated schema/data pages are restored. A large
WAL migration may spill dirty pages before a later refusal; rollback leaves
those frames uncommitted and invisible to readers but can retain the enlarged
file. Committed, uncheckpointed frames remain readable. Existing journal mode
is retained. Pre-admission SQLite connections disable checkpoint-on-close
before reading the database and retain that setting on refusal, so closing a
refused opener does not checkpoint committed frames into the main file.
Accepted backend activation restores ordinary close-time checkpointing. This
applies to other physical upgrades as well as `_read_sessions`. It describes
the refused operation's effects; it cannot freeze writes or checkpoints
performed by concurrent accepted owners.

[free-pages]: https://www.sqlite.org/atomiccommit.html#_do_not_journal_freelist_pages

**Why permit physical residue:** keeping every dirty page until the final
decision would require memory proportional to an arbitrarily large migration.
Late constraints, SQLite errors and native recovery can still refuse after
writes; moving a few known checks earlier cannot eliminate all such failures.
Staging a second database would add disk/copy cost and a separate publication
protocol around live SQLite owners. Neither cost is justified to preserve
unallocated page contents or invisible uncommitted frames. Retain the existing
cache/spill policy (LLP 3000.002, implementation follow-up). Linux refusal tests
compare complete schema/table/row dumps, `integrity_check` and freelist count.
The spill regression uses 1,500 legacy receipt rows with 8 KiB payloads and
4 MiB of committed free space in WAL and DELETE modes. It additionally verifies
that any changed main-file page was already a free leaf, retains the committed
WAL prefix, and proves a later accepting open can migrate. Small no-spill tests
retain their stricter whole-WAL comparisons; the checkpoint-on-close fence
still compares main-file bytes. The Darwin fence's fixture-specific byte
comparisons remain stronger witnesses, not a whole-file migration contract.

SQLite creates `_read_sessions` and its family index lazily in the transaction
that first mints a read session. A missing table means no read sessions:
authority lookups return no read credential, cleanup/logout skip the absent
table, and full-session authority remains available. Reads never create the
table; malformed storage and other SQL errors still fail closed. The
mint-binding `scope` column is installed inside bound minting's transaction.
Existing stores defer their other physical upgrades until successful backend
activation (or validated server attachment); native device side tables join
that installation transaction. Native opening also completes capture recovery,
send-revision validation, cache validation/cleanup and final metadata reads
inside the installation transaction; none may refuse after its commit.
Server `Engine::open`, `new` and `new_release` likewise read the store identity
and release metadata inside the accepting transaction, after upgrades and
metadata writes, and carry validated construction values out. Missing identities
are generated and read there; malformed identities or releases roll back the
upgrades and release pointer together. In-place server adoption checks its
fallible ephemeral-hub lock before activation, then releases it for the entire
SQLite transaction. Readers take SQLite before the hub; holding the hub while
DELETE-mode commit or spill waits for those readers would invert that order.
After commit, adoption rebinds with the validated identity. If a concurrent
reader poisoned the hub after the initial check, rebind replaces all ephemeral
state and clears poison rather than returning a refusal after durable commit.
Existing poison still refuses before activation. WAL readers holding an old
snapshot fail closed against the rebound generation.

SQLite rechecks the stored version after acquiring the writer lock for either
attachment or activation. Fast attachment keeps decoded schema/programs,
selected release, catalog and upgrade markers in that one transaction through
completion. If attachment needs semantic repair, it rechecks the exact captured
generation/schema/program bytes under activation's writer lock before physical
upgrades; activation rereads its catalog, checks the selected release and
repeats key, timeline and derived-state admission under the same lock. A
low-level handle's earlier supported version or backend is not authority after
a wait. Concurrent-opener regressions exercise version changes through all
three server constructors and device installation, with paired successful
attachers and stored-schema/program/catalog changes.

PostgreSQL creates its read-session schema
inside the same transaction as the backend-column, cap-counter and
contribution-index upgrades, with the shared head locked and the captured
backend rechecked before commit. That protected decision includes the store
version, decoded schema and programs, their supported-surface checks and
portable index-key admission; the earlier preflight is not authority after a
lock wait. A late refusal rolls back all of them.
Neither path changes the SDK's no-refresh rule, read-family caps, revocation,
logout, or the no-trace promise for reader requests.

**Read tokens are recognizable.** Every read token is `ro.` followed by the
ordinary base64url random part. Full tokens are pure base64url, so they
never contain `.` and never start with `ro.`; the server never mints a full
token with the prefix. The prefix is not authority, since the server
resolves scope from storage. It lets the client refuse a read token
**offline**, from the token string the server receives, which caller-edited
`Session` fields cannot disguise.

**Round 7: one normalized SDK predicate.** Read-token prefix checks ignore
leading ASCII whitespace exactly as the server's `split_ascii_whitespace`
bearer parser does: tab, line feed, form feed, carriage return and space.
Vertical tab and Unicode whitespace are not separators; JavaScript `trim()`
would accept a different set. Device admission (including restore and startup),
expiry scheduling, startup refresh and explicit refresh use the same predicate,
including the standalone auth helper. The SDK preserves supplied credential
strings at intake, in custody and on requests; normalization is only for prefix
recognition, never a storage rewrite or a source of authority. Read tokens
expire at `expiresAt` even with `readOnly: false` and absent or forged scope.

Resolution checks `_sessions`, then `_read_sessions`, and returns the
capability. Both authority adapters (`store/authority.rs` and
`engine/postgres/authority.rs`) and `SessionRecord` carry the scope.

**Revocation survives downgrade.** `logoutAll` increments
`_principal_generations` (`revoke_principal`), and an older executable
running it deletes only `_sessions` rows. Each read family therefore records
the principal's generation at mint and keeps it through rotation. Resolution
refuses a read session whose generation is below the principal's current
one. A read token minted before a `logoutAll` stays dead even if that
`logoutAll` ran on an older binary and the store is upgraded again.

**Who may hold one.** Any session whose kind is **not** `service` or
`action`, and which is not a supervised-worker family member. That
includes `user`, `guest` and app-defined kinds minted through
`/auth/session` (`member`, `account`). A narrowed service or worker session
would escape supervisor family fencing, and action sessions are
single-purpose already.

**Two ways to get one:**
1. **At sign-in.** The password and guest doors (`POST /auth/login`,
   `/auth/signup`, `/auth/guest`) accept `"scope": "read"` and mint directly
   into `_read_sessions`, with an ordinary session lifetime and
   `cap_expires_at = expires_at`. The oracle signs Bob in this way.
2. **By narrowing.** `POST /auth/narrow`, authorized by an eligible full
   session, mints a read session for the same principal. The scope is always
   `read`; the request names no scope. It starts a **new family**, and
   `cap_expires_at` is the parent's `expires_at` at mint time.
   - Narrowing is **one writer transaction**: take the writer, sample the
     clock, resolve the parent, check eligibility and generation, capture
     the cap, insert the sibling. This is the pattern `logout_session`
     already uses.
   - A concurrent `logoutAll` either happens first, so narrowing is refused,
     or after, so it revokes the sibling through the generation. The SDK
   exposes this as a standalone helper, `narrowSession(url, session)`, since
   a `Session` is plain serializable data.

**Server refresh never extends the cap.** `cap_expires_at` is written once, at
mint, and never updated. `/auth/refresh` on a read session rotates within
its family, copies the cap and the generation, and sets `expires_at =
min(now + ordinary lifetime, cap_expires_at)`. The one-day floor and
duration restart used for full sessions do not apply.
- Read refresh deletes only rows of its own family. It never runs the
  `_sessions` expired-row sweep that full-session insertion performs.
- Every read credential response (sign-in, narrow, refresh) carries
  `capExpiresAt`. The server enforces the cap; the SDK does not schedule refresh from it.
- Refresh refuses `E_AUTH` only once `now >= cap_expires_at`. While the
  session is live, refresh at the cap rotates the token within the family
  and leaves both timestamps unchanged.

**Revision 4 (implementation simplification, lead ruling 2026-10-07).**
The SDK never refreshes or rotates a read session, automatically or explicitly.
A read client runs until `expiresAt`, then surfaces `E_AUTH`; the caller signs
in again or narrows a full session again. Explicit `refreshSession()` refuses
locally with `E_READ_ONLY_REFRESH` and that recovery instruction, including
through the app facade. The standalone SDK auth helper also refuses `ro.` tokens.
`capExpiresAt` never determines SDK renewal scheduling.

Sign-in sets the cap equal to expiry, and narrowing caps the sibling at the
parent's expiry. Rotation ordinarily extends no useful lifetime, while shared
SDK custody introduced repeated liveness failures: a peer became signed out
with a live successor still stored. Removing rotation removes that failure
class. Even a sibling whose expiry is below its cap gets no SDK renewal.
Raw HTTP callers retain `/auth/refresh` exactly as above: immutable cap,
own-family deletion, no foreign sweep and principal-generation checks. Its
server tests remain unchanged.

**Logout:**
- logging out a read session ends its family only;
- logging out a parent does not revoke a narrowed sibling, and logging out
  the sibling does not affect the parent;
- `logoutAll` from a full session revokes every session of the principal,
  read sessions included;
- `logoutAll` from a read session is refused (§1.2).

Bound or recoverable minting records, where they exist, include the scope.
An unknown scope value is refused, never defaulted.

### 1.4 The SDK

`createClient({ …, readOnly: true })` and online `createApp({ …, readOnly: true })`:

- **Verify scope with the server, before any other request.**
  - Construction validates options synchronously. It refuses `device`
    (`E_READ_ONLY_DEVICE`) and personas (`E_READ_ONLY_CREDENTIAL`).
  - The client then calls an authenticated, side-effect-free
    `/probe?scope=1`, which reports the bearer's scope. It sends nothing
    else until that answer says `read`. A full credential is refused
    (`E_READ_ONLY_CREDENTIAL`), as is a server whose probe lacks the
    capability (`E_READ_ONLY_UNSUPPORTED`).
  - The check reruns after every restore and store change, and is
    bound to the credential revision and store identity. The client never
    trusts a `scope` field in a `Session` object, which is caller-controlled
    data.
  - **`Session.scope` is optional.** Existing persisted sessions lack it,
    and `restoreSession` today deletes anything `isSession` rejects. A
    session without `scope` is a **legacy, unverified** session: it is
    preserved, never discarded or revoked for its shape. The read-only path
    probes regardless.
  - **Device admission checks the token, not the field.** Every device path
    refuses a token that starts with `ro.` (`E_READ_ONLY_DEVICE`), whatever
    its `scope` field says, before refresh, persistence or opening. That
    covers `createApp` with a device, `createLocalClient`, and restoring
    into a device app, including offline startup. This needs no probe, so
    offline device restoration of legacy full sessions keeps working
    unchanged.
  - **Nothing is exported before verification.** Until the probe has
    verified the exact current credential, `assetSource` returns no usable
    URI or headers, and it withdraws them during revalidation and after a
    failure. `assetSource` hands a bearer to a platform image loader outside
    the SDK's fetch gate, so a full token mistakenly passed to
    `readOnly: true` must not reach a loader while the probe is pending.
  - **Nothing before the probe.** Until the probe answers `read` for the
    exact current credential, `query`, `observe`, `asset` and `fetchAsset` send nothing.
    Explicit refresh refuses locally without waiting for the probe. The client builds no delivery queue, makes no
    startup refresh rotation, opens no `/changes` and accepts no manifest.
    A full token mistakenly passed to `readOnly: true` inside its refresh
    window is therefore never rotated or used, and its owner can still write
    with it.
  - The guarantee comes from the server: an auditor reads the probe result
    and the server guard, not the SDK.
- **Isolated custody.** Every key the SDK derives from `sessionKey(url)`
  has a read-only namespace, `sessionKey(url) + ".read"`, with `.epoch` and
  `.revocations` beneath it. The suffix stays inside the Expo SecureStore
  key alphabet (alphanumerics, `.`, `-`, `_`) that `storeKey` already
  guarantees. A read-only client has no write
  journal and never reads the interactive journal. Read sessions never
  enter the interactive session's slot. The read-only
  app uses only its `.read.revocations` queue for retirement, draining and
  opening-error cleanup, with scope checks before revocation. A failed
  read-only startup can never sign the interactive user out.
  **Shared app custody (Round 2).** Read-only apps use the same app state
  machine as full sessions: shared logout epochs, provisional openers, atomic
  replacement, conditional retirement, facade ownership and notifications after
  auth publication. The policy selects the `.read` key, read-scoped sign-in,
  exact-credential verification and fixed-lifetime client; it omits device and write
  owners and refuses global logout. Retirement probes each read-namespace
  credential before revoking it. **Round 4 lead ruling, superseding Round 3:**
  explicit logout means this user is signed out of this shared storage. In both
  modes it compares the last owned principal under the storage lock, after any
  already-admitted commit finishes. It tombstones and retires every credential
  of that principal in this custody, whatever its epoch: peer rotations, pending
  successors and a newer deliberate login by the same user. The tombstone fences
  same-principal logins still in flight. It never deletes or revokes a different
  principal's later login: a stale Bob facade cannot sign Alice out. If Alice is
  already stored, logout keeps her token and epoch while recording Bob's sign-out
  watermark in that same record (`snapback4SignOuts`). Sign-in snapshots these
  watermarks before dispatch and rechecks its returned principal before commit;
  same-epoch rotations carry them forward. An epoch advance discards them,
  since it already fences all openers that captured the old epoch. Thus Bob's already-pending
  login cannot replace Alice after Bob logs out; a new sign-in begun afterward
  remains allowed. Full-session
  same-user behavior on `origin/main` is preserved; the only logout behavior
  change for full sessions is different-principal protection.

  **Revision 4 (implementation simplification).** Read custody has no successor
  receipt, rotation lock, waiting-peer recovery, successor verification or
  successor retirement owner. Every read runtime uses its original verified
  bearer until expiry, logout or replacement; restart restores that same bearer.
  Shared principal/epoch fences, scope-checked retirement of displaced logins
  and the logout ruling above remain. Full sessions keep their existing rotation
  and retirement behavior, including late successors after logout.

- **No write machinery.**
  - The delivery queue, outbox, write history, mutation-ID owner, pending-write
    presentation, ephemeral write lane and online write journal are not
    constructed, and no write journal is recovered at startup. A construction
    counter test, with full-session controls, detects unused allocations too.
  - Generated mutations, `client.mutate`, actions and uploads reject
    `E_READ_ONLY` locally, without network traffic.
- **`useSeen`.** An active `useSeen` in a read-only app throws
  `E_READ_ONLY` during render, before it subscribes. With the existing
  `active: false`, it still observes the receipt row, which is a legal read,
  and never posts. Shared component trees pass `active: !readOnly`.
- **No device anywhere.** `createApp({ readOnly: true, device })`,
  `createLocalClient` with a read credential, and restoring a read credential
  into a device app are all refused with `E_READ_ONLY_DEVICE`.
- **Assets.**
  - `client.asset()` and `useAsset` surface `E_ASSET_READ_ONLY` as an
    ordinary refusal arm.
  - `assetSource` returns a URI plus headers for a platform image loader, so
    it cannot return a refusal arm. The loader receives the 403. The card
    says so.

### 1.5 View-once assets

The read-only path runs the **same access checks, in the same order, as a
full session**: authorization, placement, expiry, release. Then:

| Case | Full session | Read-only session |
|---|---|---|
| Unknown or not visible | `E_ASSET_UNKNOWN` 404 | same |
| View-once, ranged request | `E_ASSET_RANGE` 416, no view | same |
| View-once, already viewed | `E_ASSET_VIEWED` 410 | same |
| View-once, unviewed, non-ranged | bytes; view recorded after send | `E_ASSET_READ_ONLY` 403; no bytes opened or sent; no view |
| Ordinary asset | bytes | bytes (ranges as today) |

The disclosure is stated plainly. `E_ASSET_READ_ONLY` means "a full
non-ranged GET would have returned the bytes and consumed the view." A full
session can learn this only by consuming the view, so it is one bit the
reader gains. It is the minimum needed to report the refusal truthfully, and
it reveals nothing about hidden assets. The card says so.

### 1.6 Delivery manifests and cost

`Engine::query_reading` calls `delivery_manifest` unconditionally in both its
native and interpreted branches (`engine/mod.rs:972, 1004`), as does the
PostgreSQL path (`engine/postgres/mod.rs:164`), before anything returns to
HTTP. Suppression is therefore a **request-scoped engine query option**,
`DeliveryManifest::Skip`. The `/q` handler passes it for read sessions, and
every branch honors it by never calling construction.
- The delivery module and `Engine` are behind the `sqlite` feature, and the
  web build disables default features and selects `web`. So device
  execution is unchanged and the device wasm must not grow
  (`snapback4/metrics/wasm-budget.json`, currently 639,941 gzip bytes).
- A read-only `/q` body has no `delivery` field and no `meter.delivery`.
  Loading answers have none today either.
- Because the manifest walk uses its own ledger rather than the work meters,
  "not higher on `examined`, `steps` and `heap`" cannot prove it was
  skipped. §3 instruments construction directly.

### 1.7 Diagnostics

New codes are registered through Snapback 4's existing code and guide
mechanism (`guide/codes.rs`), not a line-pinned inventory:
- `E_READ_ONLY`: a request outside the allow-list, or a local write;
- `E_READ_ONLY_CREDENTIAL`: `readOnly` with a full credential or a persona;
- `E_READ_ONLY_DEVICE`: read-only with any device path;
- `E_READ_ONLY_UNSUPPORTED`: the server cannot report scope;
- `E_ASSET_READ_ONLY`: §1.5.

Each `why` names the read session and points to `guide read-only`. The
internal names must not collide with the existing `resolve_read_only`
(snapshot authentication without a writer lock) or `E_JOB_VIEWER_READ_ONLY`.

### 1.8 App-owned online arm (OA, 2026-10-07)

Calibration #31 on 0.4.13 scored client integration 86 (cal30: 92).
The builder borrowed the account owner's bearer for Insights and Trending;
the social starter duplicated that lifecycle in `useOnlineArm.ts`.
`createApp` now owns `app.online`, with `useOnline()` under AppProvider.
These names parallel `app.client`/`useClient`; explicit arm selection leaves
the existing replica read model and its bounded settlement unchanged.

`Online` projects query, observe, ephemeral mutate, act, viewer, now, link,
onLink and readOnly. The projection has no Session, bearer, assetSource,
refresh or lifecycle methods, at runtime as well as in types. Durable writes
continue through app.mutate. On first access a device runtime privately constructs the online
client with its current credential and the app's scoped transport. No second
session store or rotation owner exists. Every operation request from an arm
checks shared authority and then rechecks its originating arm/credential after
that asynchronous check, immediately before transport dispatch. This applies
equally to device and no-device arms: private operation copies carry an
in-memory fence through signal queues, action refresh waits, read scheduling
and retries; the request retains it through the scoped transport. It is never
serialized into the wire request. Retiring a facade immediately fences new requests and observed/one-shot
read publication. Dispatched signal/action calls retain their outcomes and
drain before the private client closes; retirement allows at most 30 seconds
(the one-shot read lifetime), then raw close returns an unresolved action as
pending with its original ID. Retiring it never calls signOut.
Rotation replaces the arm and notifies app.onOnlineChange/useOnline. Old
handles cannot follow a later account or dispatch with an old credential.
Failed account replacement may expose a new arm for the rollback owner; the
old exposed arm stays fenced. Screen unmount alone leaves the arm alive,
allowing stopTyping. Retirement cannot send stopTyping through a retired
credential or substitute the next account; the four-second schema expiry
handles this cleanup. Retirement never waits for an application callback or a
best-effort stop before fencing.

Without a device, the projection shares the existing raw online client.
In that shared client, observation and renewal identities include the arm, so a
new arm cannot inherit a retired arm's queued work or cached renewal outcome.
A local arm refusal never revokes the shared client's current credential.
Already-dispatched calls keep their outcomes; only subsequent attempts are
fenced. These rules fix the three OA round-0 no-device reproductions (queued
signal using a replacement credential, storage-awaited retired bearer, and an
old-account dispatch during provisional replacement).

In read-only mode there is no extra verifier, device, write owner, refresh or
rotation. §1.3–§1.4's fixed lifetime, exact-credential verification, shared
epochs, principal sign-out watermarks and independent `.read` namespace remain
unchanged. No persistent record or wire shape changes; a new published-downgrade
control is unnecessary for OA.

Server snapshots bypass replica acquisition and pending predictions, never
claiming those predictions are committed. Server completeness, meter cuts and
continuations still apply. Signed-out operations refuse E_AUTH; offline
one-shots/signals/actions refuse E_OFFLINE, with pending retaining uncertainty
for an already-dispatched action. Observations reconnect under existing read
retention rules; ephemeral signals never replay. Normal delivery reports and
presence remain active for full sessions, absent for read-only sessions.

The starter uses useOnline for unchanged typing renewal/cleanup behavior.
TrendingSnapshot shows a one-shot server feed read rendered with matchRead,
with explicit Refresh and identity-bound publication. Scope: TypeScript client,
React hook and starter/docs only; no engine or device-wasm inputs change.

## 2. The guide

A new card, `guide read-only` (aliases `oracle`, `observer`, `dashboard`,
`preview`). It owns §1.1's promise and its four exceptions, the allow-list,
and §1.5's disclosure, and it gives three recipes:
- an oracle that signs Bob in read-only and pages a conversation;
- a dashboard that narrows an interactive session;
- an SSR fetch.

The receipts card gains one paragraph: only full sessions report delivery,
so a read-only reader never marks a message delivered. The client card
lists the flag and `useSeen({ active })`.

The native contract's oracle section (native.2) may cite this mode as
Snapback 4's oracle path. Plain HTTP to the documented API stays admissible
for every backend.

## 3. Acceptance

**Paired deterministic runs.** Run the same script twice against fresh
stores with the same seed, external writes and clock advances. Run A has a
read-only observer active; run B is identical without it. The final
application digests must be equal. The digest covers:
- application tables;
- delivery runs and watermarks;
- asset view records;
- `_effect_presence`;
- effect and action state;
- every `_sessions` row;
- `_ops`, the idempotency record.

Auth-table differences are limited to the reader's own `_read_sessions`
family and sign-in's expired-session garbage collection. The observer's
script:

1. signs in read-only as a member, then pages a receipts-tracked history to
   exhaustion, including a gap;
2. observes it live while another member writes, and converges to the final
   state (`/changes` coalesces, so it need not deliver every intermediate
   state);
3. holds `/changes` while a presence-gated effect becomes due on its normal
   deadline; the effect is not deferred or fired early by the observer;
4. fetches an ordinary asset (full and ranged), then probes a view-once asset
   with a ranged and a non-ranged GET. The ranged GET gets
   `E_ASSET_RANGE` and the non-ranged gets `E_ASSET_READ_ONLY`; afterwards a
   full session consumes it exactly once;
5. is refused, before anything runs, at each of: a generated mutation, raw
   `POST /m` (including a replayed id), an ephemeral write, `POST /a/`,
   `POST /assets`, a declared session route, an action/effect claim, `/auth/session`,
   `/auth/narrow`, `/auth/revoke` and `/auth/logout-all`; no refusal carries
   `head`;
6. refreshes repeatedly. After each refresh it reads the stored row (it must
   be in `_read_sessions`, never in `_sessions`) and retries `POST /m` and
   `POST /a/` with the new token. Every row's `cap_expires_at` must equal the
   value recorded at mint. The clock then advances to that instant, and
   refresh must answer `E_AUTH`. Another principal's expired `_sessions` row,
   planted beforehand, must still be present: read refresh sweeps nothing
   outside its family. The SDK must not schedule a renewal that cannot move
   `expires_at`.

**Barrier checks.** Final digests cannot see a forbidden write that a TTL
or cleanup later erased. So immediately after each forbidden request in
step 5, and before any expiry, maintenance or clock advance, the test
checks four things:
- the application tables and `_ops` equal a snapshot taken just before the
  request. This catches a short-lived row a later sweep would remove;
- through a second full-session client, the ephemeral hub (for example, a
  typing row) shows no change;
- an external-effect witness, such as a stub provider endpoint, recorded no
  call;
- **idempotency is not poisoned.** The full sibling then submits the
  identical operation, arguments and id, and it executes fresh: exactly one
  successful write, with no replayed refusal.

**Nothing before the probe.** With the probe held, a read-only client that
was given a full token inside its refresh window issues `query`, `observe`,
`asset` and `fetchAsset`. None of them sends anything but the probe: no
rotation, no `/changes`, no manifest acceptance. After the probe refuses,
the full token still `POST /m`s.

**Device admission is offline and token-based.** A `ro.` token with
`scope` absent, `"full"` or forged is refused by every device path. That
covers direct construction, `createLocalClient` and restoration, including
an offline start, and it happens before refresh or persistence. A legacy
full session restores offline exactly as today.

**Custody keys are SecureStore-legal.** The success-path custody test runs
through a store double that rejects any key outside the SecureStore
alphabet.

**Overlap and alternation:**
- **Overlapping polls.** A full and a read-only `/changes` poll for the same
  principal overlap in both orders. Presence count, grace timestamp and
  effect behavior must be exactly those of the full poll alone when either
  closes. This catches an unconditional presence leave.
- **Alternation.** Full and read requests alternate through reused readers.
  Full sessions still receive manifests and still report delivery, which
  catches accidental global suppression.

**Narrowing:**
- the narrowed sibling's family is independent in both logout directions;
- `logoutAll` from a full session revokes it;
- service, supervised-worker and action narrowing are refused, while an
  app-defined `member` kind narrows;
- signing in read-only as a service is refused;
- narrowing that waits on the writer while a `logoutAll` or parent expiry
  commits is refused, or is revoked by it, never left live.

**SDK:**
- construction refusals: `E_READ_ONLY_DEVICE` (including `createLocalClient`
  and restore into a device app), and `E_READ_ONLY_CREDENTIAL` for a full
  token, a persona, and a hand-edited `{scope:"read"}` session holding a
  full token;
- `E_READ_ONLY_UNSUPPORTED` against a server without the probe capability;
- a failed read-only startup leaves the interactive session's stored
  credential intact and live;
- after a *successful* read-only client starts, refuses refresh and closes, the
  interactive session can still `POST /m`, and its pending journal entry was
  neither posted nor consumed by the read client;
- upgrading an SDK with a persisted legacy full session (no `scope`)
  preserves it;
- with the probe deliberately held, `assetSource` yields no usable URI or
  headers, so an external loader given them cannot fetch;
- an active `useSeen` throws before subscribing; `active: false` posts
  nothing;
- the asset matrix in §1.5 is covered in full: hidden, missing, expired,
  released, already viewed, ranged and unviewed.

**Live queries on an ephemeral backend.** On a backend that declares an
ephemeral table, a read-only live query adopts the schema through
`GET /schema` and converges.

**Manifest construction is never invoked.** A test counter in
`delivery_manifest` stays at zero across every read-only `/q`, in both
engine branches. The read-only body carries no `delivery` and no
`meter.delivery`.

**Answer parity, HTTP:**
- full and read-only clients run the same queries under the same snapshot;
- the answers are equal except for `delivery` and dev `meter`;
- a query reading `connected[viewer]` differs as §1.1 states;
- work meters are not higher for the read-only client;
- the device compatibility fence (`sameAnswer`) is unchanged and is not
  cited as evidence.

**Downgrade.** The previous published server binary, on a migrated store,
refuses a read token as unauthenticated. Then, still on the old binary, a
full session runs `logoutAll`. After re-upgrading, the read token is
refused through the generation check.

**The Phase-2 oracle.** The Snapback 4 lane's `native-oracle.mjs`, changed
only to sign in with `scope: "read"` and pass `readOnly: true`, leaves Bob's
delivered watermark unchanged across full pagination.

**Budgets.** The device wasm does not grow.

## 4. Not in this RFC

- **Read-only devices:** offline replicas that never report delivery or
  flush an outbox. They need a ruling on what a never-reporting replica is
  owed. Revisit if a kiosk or offline dashboard asks.
- **Per-query opt-out** on a full session. "No trace" would become a
  property of each call: easy to forget, impossible to audit, and blind to
  presence and assets. A full session that wants an untracked peek can
  narrow.
- **Admin or raw reads.** Read-only never relaxes rules. `snapback4 sql`
  stays the only rule-free read, dev or `--release` only.
- **Read-only service or worker credentials.** Supervision fences families,
  not principals. Revisit with a supervised-descendant design if a worker
  needs it.
- **Notification-extension defaults.** Whether a preview marks delivery is
  the app's decision; both choices are now expressible.

## 5. Resolved questions

- **Q1 (`useSeen`).** An active hook throws; `active: false` is inert.
  Astra and Grok agreed.
- **Q2 (observer presence).** No observer state. Observers are invisible,
  and `connected[viewer]` is §1.1's named exception.
- **Q3 (asset status).** 403 `E_ASSET_READ_ONLY` replaces only a successful
  non-ranged view-once grant, after the full access path (§1.5). The
  distinguisher is the code, and the one-bit disclosure is documented.
- **Q4 (revocation).** Narrowed siblings are independent families with an
  absolute cap. A full session's `logoutAll` revokes them, and a read
  session's `logoutAll` is refused.

## 7. Implementation (2026-10-06)

Implemented revision 3, with the wire additions listed below. Read capabilities
live only in `_read_sessions`, carry the principal generation and immutable cap,
and use `ro.` tokens. Resolution carries `(principal, kind, scope)` through the
SQLite and PostgreSQL adapters. Narrowing samples the clock after taking the
writer lock. The first authenticated read-token branch in `handle` resolves
stored authority before applying the closed allow-list; the prefix selects this
branch and never substitutes for authentication. Legacy full-token handlers keep
their operation validation order. Session JSON adds `scope` (and read sessions
add `capExpiresAt`); `GET /probe?scope=1` adds `kind` and `scope`. Without
`scope=1`, the legacy probe body remains `{ok, store_id, seq, viewer}`. The new
`POST /probe` has the same optional fields. Auth bodies now validate `scope`
before dispatch: only absent, `"full"` and `"read"` are accepted, including on
refresh/logout bodies. Stored authority still wins over a caller's scope claim. Read polls neither enter nor
leave presence; all query branches honor request-scoped `DeliveryManifest::Skip`.

The online SDK probes the exact credential before dispatch or asset credential
export, uses separate `.read` custody, constructs no write owners, and stops
automatic renewal at the immutable cap. Device admission checks the token prefix
before opening or persisting, including restored sessions and refresh successors.
The client card, receipts card, new read-only card and diagnostic registry describe
the implemented surface. No schema capability or device wire format changed.

Acceptance includes paired fresh stores with actual receipt rows and a history
gap, HTTP barriers and replay, overlapping polls, atomic narrowing races, the
previous published 0.4.13 binary, the generated-query Phase-2 oracle, custody and
startup barriers, and direct manifest-construction counters. The paired digest
(including `_ops`, full sessions, principals and credentials) is
`e15809273ad09307d18d1d0e443d46dd93a8a424aa9ceca31ab2b6bcb0930136`.
The wasm is byte-identical to the baseline: 2,117,335 bytes raw, 639,888 gzip,
under the unchanged 639,941-byte cap. The
[implementation report](../snapback4/reports/20261006-ro-read-only/REPORT.md)
records commands, passing reruns, initial suite failures and qualification limits.

### Round 1 code-review corrections (2026-10-06)

Logout fences pending openers and removes their credential conditionally under
its storage lock; openers recheck the revision after persistence and before
adoption. A custody mismatch permanently fences old observations and asset
sources, closes the raw client and publishes signed-out state. Before revision 4, a refresh
successor stayed private during a transient probe failure; later verification
completed persistence, session notification and scheduling before reads proceed.
Consumed predecessors left client custody after successor persistence. Revision 4
removes this read-rotation machinery entirely.

Sign-in's `insert_session` collects read rows when either `expires_at <= now`
or `cap_expires_at <= now`, alongside expired full rows. Full refresh uses this
mint path too; read refresh continues to delete only its own family. The
PostgreSQL evaluation adapter currently resolves/invalidates authority but has
no production session mint/sign-in or refresh path; its test fixtures insert
rows directly. No PostgreSQL mint-path parity is claimed.

Round 1 adds regressions for all four review reproductions, forbidden GET and
method combinations, forged body scope, overlapping asset refusals, detached
and memory HTTP query construction, revoked held polls, and failed narrowing
leaving no sibling. PostgreSQL runtime limits and commands are in the report.


## Following integration (FH round 3, 2026-10-07)

LLP 3000.026 §9.11 keeps `POST /following/<op>` outside this RFC's closed
allow-list: all history actions refuse `E_READ_ONLY` before frontier access.
An explicit read-only `useFollowing` consumer refuses without constructing an
observer; ordinary inbox queries remain allowed and render with `matchRead`.
This does not add an exception to the no-application-trace promise or extend the
read-session capability. Route and SDK regressions cover both explicit read-only
clients/facades and a raw read credential without that option.
