## 1. Summary

The question: **does Snapback 4 on Postgres hit scale limits that Supabase,
raw Postgres, or Convex self-hosted on Postgres would not hit for the same
application?** For each limit found we also want to know why, and whether it
can be fixed.

The program:

1. **States predicted ceilings first**, each with a formula from the design
   and a falsifying measurement (§3). The measurements are then read against
   predictions rather than mined for a story.
2. **Builds three controls** to the same application semantics, on the same
   hardware, Postgres version and durability settings (§4).
3. **Runs open-loop load** from a separate host against separate app and
   database hosts. It sweeps network RTT, data size, writers, contention,
   subscribers and app processes (§5–§6).
4. **Produces a limits ledger** (§7). Each row is a workload, a ceiling for
   every system, the bottleneck with its evidence, and a classification:
   - **semantic cost**: paid for something the controls do not do (rules in
     the interpreter, the meter, completeness, partition sync);
   - **design choice**: the single commit order, the generic layout, the
     interpreter over network calls, table-granular invalidation, one process;
   - **implementation**: fixable without a design change.
5. **Applies decision rules** written now (§8). A ceiling below a stated
   bound commissions a named fix or reopens a named LLP 3000.009 decision.

The first cells calibrate the committer (S0, §9). They measure the
reference, the serial batch and a commit-stage prototype of the optimistic
committer at swept RTTs, and decide whether the optimistic committer is
built. The parent rules out production Postgres on the reference committer.

## 2. What is already known

- **Engine-level, one host, Unix socket** (W9, PG 16.15, durable settings):
  - a 20-row page at 5.22× SQLite;
  - the 32-room inbox at 3.10× in eight calls;
  - serialized writes at 446–461 commits/s. The same run recorded SQLite at
    165–167/s with `synchronous=FULL`, but that cell opened four connections
    contending through SQLite's busy handler, which sleeps between retries
    (`experiments/postgres/src/main.rs`, `concurrent_sqlite`). `serve` writes
    through one connection behind its engine mutex, so the cell measured
    retry sleep, not `serve`'s ceiling. SQLite's real commit ceiling under
    `serve` is unmeasured;
  - serializable mode retrying on the shared head and failing its stress
    cells.

  There is no HTTP, TLS, network RTT, pooling, sustained load or data size
  in these numbers.
- **A hand-written relational inbox join**: 0.082 ms against the adapter's
  1.894 ms on the M5. It is a planning lower bound without rules, meter or
  completeness, not a Snapback query.
- **The earlier Clique wave** (Snapback 2, LLP 3000.007 §2.4) scored Convex
  80 on scale against Snapback 2's 62. That was a builder-scored dimension,
  not a load measurement.

Nothing yet measures any system under load at realistic RTT. This RFC
produces the first such numbers.

## 3. Predicted ceilings

Notation: `RTT` is the app-to-database round trip; `k` is database calls per
operation; `F` is commit flush time; `W` is watchers of a table; `q` is the
cost of one query execution.

| # | Limit | Prediction for Snapback 4 on Postgres | Controls | Falsified if |
| --- | --- | --- | --- | --- |
| H1 | **Serialized commit path** | Reference committer: `≤ 1/(k·RTT + exec + F)` per store. With k≈15 measured for an increment: about 450/s at a Unix socket, 60–200/s at 0.3–1 ms RTT, flat in writers and in disjointness | Raw PG and Supabase: concurrent writers limited by row conflicts, with the flush group-committed. Convex: one committer, functions outside it | Throughput rises with writers on disjoint keys, or stays above 1,000/s at 1 ms RTT |
| H2 | **Read latency from calls** | `≈ k·RTT + exec`, with k = 5–8 after prefetch: about 2–4 ms per page at 0.5 ms RTT, against about 1 RTT for one SQL statement | Raw PG: one statement. Supabase: one PostgREST request with RLS in the plan. Convex: its function runner over its own index reads | Snapback's p50 stays within 2× of raw PG at 0.5 ms RTT |
| H3 | **Live invalidation fan-out** | Table-granular: a commit touching `messages` re-runs every watched query over `messages` (clients re-issue on `/changes`). Server cost per commit is about `W·q`, and delivery p99 grows with W | Convex: read-set ranges re-run only overlapping subscriptions. Supabase: Postgres Changes authorizes each change for each subscriber and processes changes on one thread to keep their order (per Supabase's Realtime documentation); Broadcast avoids the database | The chat send cell with W = 10⁴ keeps p99 delivery under 1 s at the controls' rates |
| H4 | **Sync acquisition and reconnect storms** | Cold acquisition cost grows with partitions × rows per device; a storm of N devices resuming after an outage multiplies it. There is no control with replicas | None directly. Report absolute numbers; an optional sync control (ElectricSQL or PowerSync) is out of the first matrix | — (absolute ceiling, reported) |
| H5 | **Generic layout amplification** | Per row: a JSON image in `r` plus one `i` entry per index, each a B-tree tuple with labels and an encoded key. Predict 2–4× the storage and WAL bytes per write of a typed table with the same indexes, and vacuum pressure concentrated in `i` | Raw PG and Supabase: typed tables. Convex: the same generic shape ([`sql.rs`](https://github.com/get-convex/convex-backend/blob/main/crates/postgres/src/sql.rs)) | Ratio under 1.5× |
| H6 | **One serving process** | CPU for the interpreter, sync pages and polls is one host's (P1). 32 request workers; held waits cost a thread each (`SERVER.md`, long-wait capacity) | Raw PG and Supabase: stateless app tiers scale out. Convex self-hosted: one backend process | Read throughput is database-bound before it is app-bound |
| H7 | **Data size** | Bounded pages make most operations O(page), not O(data), which is a strength. Exceptions are the operations `check --cost` classes as `grows`, unbounded log growth (no retention today), adoption and backfill scans, and graduation time | Raw PG and Supabase: planner-dependent; an unindexed RLS predicate grows with data | Every operation's p99 is flat from 10⁶ to 10⁸ rows |
| H8 | **Database CPU per operation** | Low: seeks and point reads only, with rules and the meter in the app. This is a possible advantage over RLS-heavy SQL | Supabase: RLS predicates and their subqueries run in the database | Snapback's database CPU per operation exceeds Supabase's on the same workload |

H1 is the prediction the parent's committer decision turns on. H3 is the one
most likely to put Snapback below every control on a chat-shaped workload.

## 4. Controls

Every control implements the same application with the same visibility and
write rules, using the system's idiomatic tools. A control that skips
authorization gets a separate row labelled as such, as the evaluation's
native join was.

| Control | Shape | Authorization | Live |
| --- | --- | --- | --- |
| **Raw Postgres** | Typed tables and the indexes a competent engineer would add; a small Rust (or Go) HTTP service with a connection pool, prepared statements and hand-written SQL | Checks in application code, or `WHERE` predicates joined to memberships | `LISTEN`/`NOTIFY` with a per-subscriber filter in the service |
| **Supabase, self-hosted** | The official self-hosted stack (PostgREST, GoTrue, Realtime) against the shared database host | RLS policies equivalent to the Quarry rules, with the indexes Supabase's guidance recommends for policy predicates | Two rows: Postgres Changes, and Broadcast fed by the app |
| **Convex, self-hosted on Postgres** | The open-source backend with its Postgres persistence ([self-hosting guide](https://github.com/get-convex/convex-backend/tree/main/self-hosted)) against the shared database host | Checks inside query and mutation functions | Its subscriptions |
| **Snapback 4 on SQLite** | The same application, `serve` on the app host's local NVMe: one engine, N request threads queued on its mutex, as `serve` runs. The four-connection evaluation cell is retired from every ceiling claim | Quarry rules | `/changes` |
| **Snapback 4 on Postgres** | The same application; the evaluation adapter (engine cells) until child A's P1, then `serve` | Quarry rules | `/changes` |

**Fairness rules.**

- **Same hardware class and the same database host** for every
  Postgres-backed system: Postgres 17, the same `postgresql.conf` (durable:
  `fsync`, `synchronous_commit` and `full_page_writes` on), the same
  `shared_buffers` and the same storage.
- **Separate hosts** for load generator, app and database, drawn from the
  machine fleet. RTT is measured, then swept with `tc netem` on the app
  host's interface, filtered to the database host's address so that
  app-to-load-generator traffic is not delayed: 0.05 (Unix socket,
  co-located, as a reference cell only), 0.2, 0.5 and 1.0 ms.
- **Expert construction with advocate review.** The lead, or a lane, builds
  each control from that system's documentation. A reviewer then argues for
  that control: a fresh session from a different model family, asked to make
  it as fast as its documentation permits within the same semantics. Their
  changes are taken unless they break semantics. This is a measurement of
  systems, not of builders (parent §7, question 3). It differs from
  `benchmarks/protocol.md`'s fresh-builder cells, which keep measuring
  authoring.
- **Published configurations.** Every control's configuration, versions and
  source are committed beside its results. A result is reproducible from one
  command per cell.
- **Fixed durability for writes.** No cell may relax durability. A relaxed
  cell (for example `synchronous_commit=off`) is a separate, labelled row,
  never the headline.

## 6. Method and metrics

- **Open-loop load** at a fixed arrival rate (for example k6's
  constant-arrival-rate executor or wrk2), with latency measured from the
  intended send time so coordinated omission is corrected. Each cell steps
  the rate up to saturation: p99 above the SLO, or the error rate above 0.1%.
- **SLOs for "sustainable throughput":** reads p99 ≤ 50 ms, writes p99 ≤
  100 ms, live delivery p99 ≤ 1 s. A system's ceiling in a cell is the
  highest rate meeting all three.
- **Per cell**:
  - throughput–latency curves (p50, p99, p99.9);
  - the sustainable ceiling;
  - database CPU, I/O and WAL bytes per operation (`pg_stat_statements`,
    `pg_stat_wal`, `pg_stat_io`);
  - app CPU per operation;
  - lock and wait events sampled from `pg_stat_activity`;
  - connections in use;
  - storage bytes per row and per index entry after `VACUUM`;
  - Snapback's own counters: database calls, retries, prefetch transfers,
    meter charges.
- **Attribution.** At each ceiling the bottleneck is named from evidence:
  - a CPU profile of the app (`perf` or `samply`);
  - the database's wait events;
  - lock waits on `_head`;
  - a control experiment varying exactly one factor.

  For Snapback: RTT, prefetch, committer, process count and layout.
- **Repetition.** Three runs per cell on idle hosts, with `vmstat` before and
  after as in the W9 report. The report gives medians and the spread, and
  never the best run.

## 7. The limits ledger

The output is one table, kept in the program's report and summarized in the
parent:

| Workload | Snapback PG ceiling | Snapback SQLite | Raw PG | Supabase | Convex/PG | Bottleneck (evidence) | Class | Fix candidate and predicted ceiling |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

A row with Snapback at or above every control's ceiling says so. A row below
any control names its class. "Semantic cost" requires a control row that
pays the same cost: for example Supabase with equivalent RLS, or raw Postgres
with the same authorization. Otherwise the gap is a design choice until
shown otherwise.

## 8. Decision rules

These are written before measurement. The author may restate a bound before
S1 begins, not after.

| If | Then |
| --- | --- |
| W4 with the serial batch (0) on Postgres, at 0.5 ms RTT and its best measured batch size, is below 1,000 commits/s, or below 25% of raw Postgres | Commission committer (a) of LLP 3000.009.001.000 §6.3, with C2's overlay and adapter-boundary read sets (child A P1c). The reference committer is predicted to fail this bound by its own formula, so it is measured for calibration and not used as the trigger. If the overlay fails its differential, the parent revisits (b)'s protocol |
| W4 with (0) on SQLite under `serve`'s single connection gains less than 3× over the reference at batch 16 | Recheck (0)'s implementation before P1; the flush share should dominate there |
| W6's live delivery p99 exceeds the SLO at W = 10³ while a control meets it | Commission increment E's read-set invalidation (LLP 3000.009 §7.1). Under committer (a) it shares the recorded read sets |
| W1–W3 p50 exceed 3× raw Postgres at 0.5 ms RTT after prefetch | Commission C1's next step from the evaluation's "what to evaluate next" (a plan-oriented access boundary: bounded pages, related-row batches, aggregates). Lowering stays declined unless that also fails (LLP 3000.009 §13) |
| H5's storage or WAL ratio exceeds 3× typed tables | Reopen LLP 3000.009 §13's typed-layout alternative for Postgres, with projections as the comparison |
| W7 saturates the app host while the database is under 50% utilized | Commission P2 (several serving processes) |
| W8 or W9 exceeds 10× its single-device cost per device at K = 10⁴, or W9 overloads the store | Commission sync-side work: snapshot page sharing, a resume admission queue, retention-floor tuning |
| W11 shows any operation's p99 growing with size beyond its `check --cost` class | File it as a defect, or a missing certificate class |
| W13's cutover pause exceeds 10 s at the largest qualified size | Revisit sibling B's replay batching and fence protocol before graduation ships |
| None of the above fires | The ledger says so, and the parent may call P1 production-ready at the measured ceilings |

No rule turns a measurement into a public claim. The parent's §6 point 4
governs that.

## 10. Non-claims and risks

- Self-hosted Supabase and self-hosted Convex are not their managed services.
  The managed services may differ in hardware, pooling and tuning. Rows say
  "self-hosted", and no cell compares against a vendor's managed service
  unless the same conditions can be recorded.
- Convex self-hosted on Postgres is a supported configuration but not
  Convex's own production storage path. That limits what a Convex row says
  about Convex.
- Equivalent semantics are approximate where systems differ (for example
  completeness and the meter have no control equivalent). The ledger's class
  column carries this; it is not hidden in a ratio.
- A loaded or shared host invalidates a cell, as in the W9 report. Cells run
  on idle hosts, serially per host.
- The program measures; it does not tune Snapback beyond its committed
  configuration between S1 and the ledger. Fixes come after rules fire, and
  S3 reruns them.

## 11. Panel revision

The one-round panel (Astra max, Fable xhigh, Grok 4.7 xhigh; parent §9)
judged the program sound and changed four things:

- **The SQLite baseline.** The 165/s figure came from four connections
  contending through SQLite's busy handler, not from `serve`'s topology. A
  single-connection cell replaces it.
- **The committer rule.** As first written, the rule fired on the
  reference committer, which its own formula already predicts below 1,000/s
  at 0.5 ms. S0 now measures the serial batch and a commit-stage prototype
  of (a), and the rule triggers on the serial batch.
- **The RTT sweep.** `netem` is filtered to the database path, so
  app-to-load-generator traffic is not delayed.
- **External claims.** The claims about Supabase and Convex that H3 and H5
  rest on were unverified from the checkout. S0 now verifies them.
