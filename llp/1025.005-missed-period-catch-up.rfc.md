# LLP 1025.005: Missed-period catch-up — one job per skipped occurrence, bounded

**Type:** RFC
**Status:** Shelved
**Systems:** Quarry `schedule` grammar (`snapback2/packages/compiler/src/quarry/schedule.ts`), period timer firing (`snapback2-core/src/registry_timers.rs`, `snapback2/src/writer_timers.rs`), the schedule ledger, `dev --status`, packaged guide (`schedule.md`)
**Author:** Claude Fable 5.1, for Charlie Cheever
**Date:** 2026-09-12
**Revised:** 2026-09-12 (commission review: shelved pending retention and failure-order semantics)
**Related:** [LLP 1025](./1025-digest-final-emission-at-hub-scale.research.md) F8, [LLP 1025.000](./1025.000-recipient-level-period-custody.plan.md) §4 (prune order), LLP 1016 D3 (FIFO) and D5 ("Re-arm and missed periods"), `rules/NOT-DOING.md` (one duration on the one schedule kind; no cron service)

## Commission disposition — 2026-09-12

The user delegated evaluation, refinement and implementation of worthwhile
changes in this family. Catch-up is useful for a digest product, but this
version is **not selected for implementation** because its central pruning
proof does not hold under the implemented job driver.

`store_jobs.rs::job_head` selects only queued/running jobs, ordered by
`created_at, rowid`. This preserves insertion order for simultaneous runnable
jobs, but a parked older job leaves the queue head. A newer period may then
prune its source buckets before the operator resumes the older job. A
manually enqueued newer digest can have the same effect. FIFO alone is not
a retention lease. The current store also cannot reconstruct activity or
visibility that has already been deleted, read, revoked or pruned; this
feature must define catch-up over retained, currently eligible facts rather
than promise historical delivery.

A future revision must choose an explicit failure rule (for example,
abandon older periods durably, or retain their buckets until terminal
settlement), then qualify parked/resumed jobs and manual enqueue order.
The existing persisted row-clock recipe (`admin.armDailyDigest` and
`utcDigestSweep` in the schedules fixture) already advances its next cutoff
only in its final chunk. That serial form can preserve an outstanding period
when its job parks; it is the first option to evaluate before adding grammar.
Price mutation targets as individual firing transactions within the existing
64-firing turn budget: executing up to thirteen mutations in each of 64
nominal firings would silently multiply the turn's work. Bound the ledger
and select retained occurrences without work proportional to outage length.
Define the skipped count by a worked boundary example; the original
"five periods" acceptance is ambiguous about whether it includes the
latest occurrence.

No implementer or delivery date is assigned while shelved. The grammar and
design below remain proposals. The default continues to execute only the
latest missed period and to record skipped periods; the refined digest makes
no new missed-period promise.

## Summary

A period schedule may declare `catchup K`. After an outage it fires once per
missed period, oldest first, up to `K` occurrences beyond the latest, each
with its own `.periodStart` and `.periodEnd` and its own occurrence identity;
older missed periods are recorded as skipped exactly as today. `catchup 0`
is today's behavior and the default. For a digest this means a two-day
outage produces two digests per user, not one, and nothing older than the
declared bound is silently dropped.

## Motivation

LLP 1016 D5: "If the owner was down across several periods it fires once,
for the latest missed period, then re-arms; the ledger records the periods
skipped." That is the right default for a cleanup sweep and the wrong one
for a digest, whose value is the period's contents. The assessment lists it
as the `oldPeriods` obligation. A job-level loop over past periods is the
alternative, and it multiplies the job's read cost by the number of periods
(500 follow reads per period); a range digest that sums buckets across the
gap has the same multiplier. Firing one job per period keeps each job at its
single-period certificate.

## Design

### D1 — Grammar

```q
schedule dailyDigest every 24h catchup 3: periodDigestSweep(.periodEnd)
```

`catchup K` is admitted on `every` schedules only; `K` is an integer from 0
to 12 (`E_SCHEDULE_CATCHUP` otherwise). It stays inside the `NOT-DOING`
line: one duration on the one schedule kind, no calendar syntax, no service.

### D2 — Firing

When a period timer fires with `M` missed periods beyond the one it would
fire today, the firing transaction enqueues up to `K + 1` jobs, oldest
first, each under its own `(schedule, period_start)` occurrence identity
with the period's own bindings; the remaining `M − K` periods are recorded
as `skipped` in the ledger row, which lists both sets. Coalescing is
unchanged: a job still `queued` or `running` for an occurrence coalesces,
and the timer re-arms to the schedule's anchor as today. A crash re-fires
and the occurrence identities make the second attempt a no-op.

A mutation target fires once per catch-up occurrence too, with the same
idempotency expectation D5 already states.

### D3 — Order and prune

`_jobs` is FIFO (D3) and the firing enqueues oldest first, so an older
period's job runs, emits and prunes before a newer period's job. The
1025.000 prune deletes only buckets strictly older than *its own* completed
period, so a later job cannot remove a bucket an earlier queued job still
needs, and no retention change is required. Periods older than the catch-up
bound are the ones a job's prune may remove first; they are the periods the
ledger already calls skipped.

### D4 — Cost

`K + 1` jobs' total work, spread across background turns; no per-chunk
certificate changes. The ledger row and `dev --status` (`timers: {
caughtUp, skipped }`) make the work visible.

## Acceptance

1. Outage across five periods with `catchup 3`: four jobs enqueued oldest
   first with the right bindings, two periods skipped in the ledger; a user
   with activity in each period receives four digests, each receipted once.
2. Restart mid-catch-up: the queue and the occurrences survive; no period is
   emitted twice.
3. `catchup 0` and an absent clause behave exactly as today (existing
   tests unchanged).
4. A mutation target with `catchup 2` is called three times with distinct
   `.periodStart` values.
5. Guide `schedule.md`: one sentence and the example.

## Non-claims

No reconstruction of historical visibility (a catch-up job reads current
state, LLP 1016 D5); no promise about lateness; no change to row timers; no
change to the 64-firings-per-turn bound (the catch-up enqueues jobs, it does
not run them in the firing turn).

## Open questions

1. Whether `catchup` should be a property of the job rather than the
   schedule, so the same job scheduled twice can differ. The schedule is the
   occurrence's owner, which argues for the schedule.
2. The upper bound of 12.
