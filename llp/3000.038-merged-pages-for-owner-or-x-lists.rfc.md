## 0. Summary

A list such as

```quarry
query myTasks(c: cursor ?):
  return tasks where .owner = viewer or .assignee = viewer last 50 by .at after c
```

over `read <- .owner = viewer or .assignee = viewer` is never `complete`
today. The engine walks one index per page; neither `[owner, at, id]` nor
`[assignee, at, id]` holds every row the caller may read, so the page is
planned on `[at, id]`, checks the rule per row, and cannot tell "no more"
from "more you may not read". `check` prints `N_NEVER_COMPLETE` with a
verified per-party rewrite (§12.2, §13.2, §16.1 of LLP 3000.036): one query
per party, merged by the client. Across six farm waves, 12, 19 and 16 lanes
reported this shape (§12.2, §13.2, §14.2).

This RFC makes the one-query form complete. When a query page's predicate,
or its table's read rule, is a disjunction of branches each of which pins an
index prefix that decides the read rule, the planner reads it as a k-way
merge of the branch ranges in the page's order. A row that matches several
branches is emitted once. Each branch's rows are decided by its own pins, so
the merged page is `complete` exactly when every branch's walk finishes. The
cursor is one position in the shared order, which every branch resumes
strictly after; its token is a new version that names the branch set, so an
older cursor of the same read refuses cleanly and an older engine refuses
the new token by version. Devices run the same plan over the branches'
partitions with the existing per-scan coverage rules. The Lean model's C8
gains the rule, with its proofs.

Owner-or-staff (`.owner = viewer or exists staff[viewer]`) is the same plan
with one branch guarded by the readable grant of §12.1: held, that branch is
the whole page; not held, it contributes nothing and the owner branch is the
page. A staff page is complete for staff (as today) and an owner's page is
complete for everyone else (new).

## 1. What the builders met

LLP 3000.036 records the shape in waves 2–6: `#12` (12 lanes), `#3b`
(19 lanes) and the §14.2 and §16.1 notes (16 lanes). The lanes read the note
and either pasted the per-party rewrite (two queries, two cursors, a
client-side merge and de-duplication, two loading states) or kept the
one-query form and shipped a list that always says "there may be more". The
rewrite is correct and verified by `check`, but it moves an ordered merge
with de-duplication and a two-cursor continuation into every client. That is
the engine's job: it already merges ordered lanes (LLP 3000 §7, 2026-09-13)
and already has the position that makes a merge resumable (LLP 3000.007.000
§1).

## 2. The rule

Definitions, over the bound schema:

- An **equality pin** in a conjunction is a conjunct `.col = e` (or `e =
  .col`, or a bare boolean `.flag` / `not .flag`) where `e` reads no row
  column and `.col` is a plain column of the table. A pin on a nullable
  column counts only when `e` is `viewer` (a principal is never null), so a
  branch never seeks on a null that the original filter would have rejected.
- A **party disjunct** of a read rule is `.col = viewer` (either side) on a
  principal column of the row.
- A **grant disjunct** is a read-rule disjunct that reads no column of the
  row (§12.1: a role probe, a service seat). It is **readable** when
  `rules::grant_decision` admits it (every fact it reads is readable by the
  caller).
- A scan's prefix **decides** the read rule when the core's existing
  analysis says so: `scan_visibility(..).uniform` (every deciding column
  pinned, or the rule proven true by the pins' form, such as `.owner =
  viewer` pinned to `viewer`).

A **query page** (a `where … first|last N by … [after c]` read in a query
program, at a position where the planner already expands merge lanes) that
names no explicit index or key, does not search (`matching`), reads an
ordinary table (not a maintained view, a row view, an ephemeral table, a
timeline table or a `read through` child), and whose own pins do **not**
decide the read rule, is **branch-decided** in two cases:

1. **Branches in `where`.** Exactly one top-level conjunct of `where` is an
   `or` of 2–8 alternatives; each alternative is a conjunction holding at
   least one equality pin; and for each alternative, the page's other
   conjuncts plus the alternative decide the read rule. The branches are
   `alternative_j and rest`.
2. **Branches in the read rule.** The read rule is an `or` of at least two
   disjuncts, each a party disjunct or a grant disjunct, with at least one
   party, and every grant disjunct readable. Let the base branches be case
   1's alternatives when `where` has such an `or`, else the whole `where`.
   The branches are `base_j and .party_k = viewer` for every base branch and
   party, plus, when the rule has grants, one **grant branch**: the whole
   `where`, guarded by the grant. At most 8 branches.

Case 1 is tried first. A page that is neither keeps today's single-index
plan and `N_NEVER_COMPLETE`.

Why the bounds: 8 is the lazy merge's per-lane-page threshold (`word_merge.rs`,
`lanes.len() <= 8`), and every branch is an index the planner may
synthesize. A rule with one party (`.owner = viewer`) is not expanded: its
complete form is the pin the author writes, and expanding it would change
the plan of every unpinned owner page in every app. That is a separate
decision (§12, Q1).

### 2.1 Why the merged rows are exactly the readable matches

Write `W` for the page's predicate and `R` for the read rule. The page
returns, in order, the rows `r` with `W(r) ∧ R(r)`.

- Case 1: `W = rest ∧ (a_1 ∨ … ∨ a_k)`, so `W = ∨_j (a_j ∧ rest)`. Branch
  `j` reads the range its pins select and filters by the rest of `a_j ∧
  rest`; its prefix decides `R`, so every row of the branch is readable
  (verdict true) or none is (verdict false, the branch is empty). The union
  of the branches' readable rows is `∨_j (a_j ∧ rest ∧ R) = W ∧ R`.
- Case 2: `R = ∨_k (.p_k = viewer) ∨ G` with `G` row-independent, so for
  this caller `R(r) = ∨_k (r.p_k = viewer) ∨ g` with `g` one boolean. Then
  `W ∧ R = ∨_{j,k} (b_j ∧ .p_k = viewer) ∨ (g ∧ W)`. Each party branch is
  decided true by its pin; the grant branch is all of `W` when `g` holds and
  nothing otherwise. When `g` holds, the grant branch is a superset of every
  other branch, so the plan reads it alone.

A row in several branches has the same position in each (below), so the
merge emits it once. No branch reads a row the caller may not read, so no
such row reaches the merge, the filter, the lookahead or the cursor.

## 3. The plan

**Planning** (`bind/intent.rs`, a new `intent_branches.rs`). The expansion
runs where `intent_lanes::expand` runs: on reads inside query programs, never
in shared helpers, shapes, mutations or jobs. Each branch is an ordinary
planned read (`Requests::read` in lane mode): its pins form the prefix (a
party pin first, so the deciding pin is never left residual), the page's
order then `id` the suffix; the planner reuses a declared index with exactly
those columns or synthesizes one. Every branch therefore has the suffix
`order…, id`. The result is the existing `MergeExpr` with planned lanes,
marked as a branch merge, and lowers through the existing planned-merge
binding (`program/views.rs`) to an IR `Merge` with one lane per branch and
`branches: true`; a grant branch's lane carries `grant: true`. Both fields
are new and skipped when false, so every existing program's IR and its
pinned digests are unchanged.

**Binding check.** After binding, with the core schema in hand, the binder
re-checks each branch with the runtime's own functions: every non-grant lane
must be `scan_visibility(..).uniform`, every grant lane's
`grant_decision(..)` must cover every row-independent disjunct of the rule,
and every lane's merge suffix must be identical. The AST-level planning
check is written to be a subset of these; a test runs both over the farm
shapes. If a grant check fails (a hidden roster, §12.1), the read binds as
its grant branch alone, which is exactly today's single-index plan.

**Execution** (`engine/word_merge.rs`, `rules::lazy_merge`). A branch merge
is a lazy merge whose lanes may use different indexes of one table. The
merge position of LLP 3000.007.000 §1 is computed per lane from that lane's
own index (the components after its prefix, plus `id` when missing); the
binding check makes the positions comparable, and because they end in the
row id, equal positions are the same row. The heap pops in position order,
de-duplicates by id (as every lazy merge already does) and refills the
popped lane strictly after the popped position. Lanes open grant first:
when a grant lane's grant holds, the remaining lanes are not opened. A grant
lane whose grant does not hold returns no rows and is decided (it does not
mark the page non-uniform). On a device a grant lane is never decided (the
device does not evaluate grants, §12.1); it marks the read unknown and
returns no rows.

Other merges are unchanged: same-index lazy merges, the eager path, views,
word lanes and search memberships keep their code paths. A branch merge that
is not lazy-eligible (it cannot be, after the binding check, unless a lane
turns non-uniform under a schema the planner did not foresee) takes the
eager path with the same descriptor; it is then sound and incomplete, with
no `next`, as every non-uniform merge.

## 4. Completeness and disclosure

- **Exact.** The page is `complete` when no lane is non-uniform, the meter
  did not cut, and the existing query-level conditions hold (position loss,
  device coverage, horizons). By §2.1 the rows are then exactly the first N
  readable matches after the cursor.
- **Nothing outside the rule.** Every lane is admitted by its own prefix
  verdict (`prefix_verdict`) or its grant (`grant_verdict`) before any row
  is read; a false verdict reads nothing. This is the same admission a
  direct page on that prefix takes today.
- **What `complete: true` reveals.** For a party or where branch: the same
  as a direct page on that prefix, which is decided by facts the caller
  could read (the analysis that already lets those pages be complete). For a
  grant branch: whether the grant holds, which §12.1 already reveals through
  a staff page's `complete` and which `grant_decision` restricts to grants
  whose every fact the caller can read. The merged page's verdict is a
  function of its branches' verdicts, so it reveals nothing the branch pages
  would not.
- **Meters as signals.** A grant charges the rule's static probe count on
  either verdict (§12.1). A party or where branch charges its prefix verdict
  as a direct page does. The number of lanes opened depends on the grant's
  verdict (one lane when held), which is the same information `complete`
  already carries.

## 5. The cursor

The continuation is one position: the shared suffix values (`order…, id`)
of the last emitted row. Every lane resumes strictly after it on its own
index. One position suffices because the suffix ends in the row id, so it
totally orders the union; the first N rows after `p` in the union are the
first N after `p` merged from each branch's rows after `p`. No per-branch
state is needed, including for a row that matched several branches.

The token is a new **version 4**:

```
[4, table, "$or:<lane index 1>|<lane index 2>|…", order, suffix, values, scope]
```

where the index field names the branch set in lane order and `scope`
carries the argument-presence variant as other tokens do (nullable). The
descriptor check compares table, branch set, order and typed suffix.

- **Old cursors fail cleanly.** A token minted by this read's earlier plan
  (one index) is refused with `E_CURSOR_INDEX`, "this read now merges its
  branches; restart it with a null cursor", the code and wording the
  engine already uses for a cursor minted under another argument-presence
  variant of the same read.
- **Old engines fail cleanly.** A 0.4.22 engine or device decodes version 4
  as "cursor token version 4 is unsupported" (`E_INPUT`).
- A branch merge never records an inclusive position (merges never do), and
  its pages record the shared suffix explicitly (as views do), since no
  single index names it.

## 6. Metering and ceilings

The meter charges what the plan does, in the existing units:

- each lane's opening is an ordinary uniform scan: its prefix verdict (rule
  probes once), one `examined` per candidate read (a batch of `take + 1`
  per lane, as lazy merges with at most 8 lanes read today), index entries
  as the store reports;
- one `step` per head pushed and per head popped (the existing lazy-merge
  charge), including duplicate pops;
- a grant charges the read rule's static probe count once, before its lane
  opens, on either verdict.

A cut while **opening** (before every lane has its first batch) is terminal:
`complete: false`, `cut: 'meter'`, no `next`, as for every lazy merge
(LLP 3000.007.000 §2). A cut while **draining** returns the rows emitted so
far with `next` at the last emitted position: every head was known, so that
prefix is a true prefix of the merged order (LLP 3000.007.000 §3), and the
continuation from it equals the uncut page's remainder.

## 7. Devices

The device runs the same interpreter over both stores, so the plan is the
same. Each lane applies the existing per-scan coverage rules: a lane over a
held partition is trusted (`trust_synced_read`) and complete when its group
is acquired and its horizon allows; a lane over an online-only table, an
unacquired group or beyond an acquired horizon marks the read unknown, and
the client asks the server (LLP 3000.028). A grant lane on a device always
marks the read unknown. Today no synced table can have a two-party or
owner-or-staff read rule (`E_SYNC` refuses a union audience; LLP
3000.036.000 §4), so on devices the merge matters for case 1 over a synced
group (`cards where .board = a or .board = b`, two lanes, each decided by
its group's probe). If union audiences land, a party lane over its held
partition is covered by the same per-lane rule without further change.

## 8. Interactions

- **`first` / `last`.** Both directions; the heap orders by the shared
  position in the page's direction.
- **`after c`.** §5. A cursorless top-N branch merge is complete when it
  fills (LLP 3000.027 §1).
- **Returned shapes.** The page owns the merge site as other merges do; a
  shape's cursor positions use the shared suffix.
- **`exists`.** In a query, `exists t where W` with `W` branch-decided by
  case 1, or by case 2 without grants, lowers to `exists (branch 1) or … or
  exists (branch k)`; each is a decided existence scan, so the answer is
  `true` or `false`, never the §15.12 "true or unavailable". With a grant
  the `exists` keeps today's behaviour (grant holders decided, others `true`
  or unavailable); a guarded existence lane is §12 Q3.
- **`count`, `sum`, `min`, `max`.** Unchanged (`E_QUARRY_BOUND` for an
  undecided total). A decided count of a two-branch union is `count(a) +
  count(b) - count(a ∧ b)`; not proposed here (§12 Q4).
- **Search (`matching`).** Unchanged: the page keeps its word merge and
  `N_NEVER_COMPLETE` keeps the membership-search rewrite. A branch merge of
  word merges is a merge of merges (§12 Q5).
- **Maintained views and row views.** Unchanged (excluded in §2): a view's
  read is decided by its audience pin or refused (`E_VIEW_KEY`).
- **Mutations and jobs.** Unchanged: an undecided page in a mutation stays
  `E_STRUCTURAL_FANOUT`; a job reads as the system.
- **`check`.** `N_NEVER_COMPLETE` iterates the bound scans; a branch merge's
  lanes are uniform (or grant lanes, which the note skips), so the note and
  its per-party rewrite are not printed for a page the merge covers. They
  stay for every shape it does not (a membership branch, a single party, a
  search page, more than 8 branches, a hidden-roster grant, a mutation).
- **`test.cases.jsonl`.** A merged page expects `complete`; the default
  case already accepts it.

## 9. The Lean model

OPEN C8 says "a page is uniform exactly when every row column its read rule
reads is pinned; a non-uniform page is never complete". The engine already
differs on one point the generator does not reach (`.owner = viewer` pinned
to `viewer` decides `.owner = viewer or …`), and this RFC adds two. C8
becomes:

> A page is **decided** when (a) its pins decide the read rule: every row
> column the rule reads is pinned, or the rule is true by the pins' form (a
> `.col = viewer` disjunct whose column is pinned to `viewer`); or (b) it is
> branch-decided (§2, cases 1 and 2 without grants). A page that is not
> decided is never complete.

The model's page semantics (the visible rows, the order, `next`) do not
change; only `complete` does. The emitter keeps grants unsupported
(`read-grant`). The proofs change accordingly: `pageRead_complete` concludes
"decided" instead of "uniform", and a new lemma states the merge itself:
for a branch-decided page, the visible rows matching `W` are exactly the
union of the branch ranges' visible rows, so a merged walk over the branch
ranges returns the model's page. The generator gains a two-party read rule
(a `helper: principal ?` column) and where-disjunctions of pins
(`.bucket = bucket or .bucket = 1`, `.owner = viewer or .helper = viewer`),
for the engine-against-model, rewrite, meter and device oracles.

## 11. Alternatives

- **Keep the per-party rewrite** (status quo). Correct, but every client
  implements a two-cursor merge with de-duplication.
- **Per-branch cursors** (a vector of positions). Not needed: one shared
  position is exact (§5). It would grow the token with k and leak nothing
  more, but it buys nothing.
- **The eager merge** (`take + 1` from every lane, sort, truncate; the path
  same-table translated lanes take today). Simpler, but a cut cannot carry
  `next` and it reads `k (take + 1)` rows every page; the lazy merge is the
  existing efficient path.
- **Union sync audiences** (LLP 3000.036.000 §4). Orthogonal: it would let a
  device hold a two-party table; the server page would still need this
  plan to be complete.
- **A readers table** (one row per party). The current recipe for sync; it
  adds writes and a table the author maintains.
- **Expand single-party rules too.** Deferred (Q1).
