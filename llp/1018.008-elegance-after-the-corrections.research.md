## 1. Finding and scope

The original assessment below remains the evidence map. Section 8 records the
subsequent review and implementation selection; it supersedes the initial
implementation ordering, not the historical observations.

Snapback 2 has an elegant core. Its ergonomics remain uneven because too much
of the machinery needed to uphold its guarantees becomes application work.
The next improvements should reduce the decisions a builder must make to get
ordinary behavior, while preserving the meaning of the underlying facts.

This is the written assessment Charlie requested on 2026-09-10, followed by

## 2. What became more elegant

The strengths are structural, not just shorter syntax:

- Quarry binds directly to typed IR; the Rust authority and TypeScript twin
  interpret the same program model. There is no separate optimistic handler
  authored for each mutation (LLPs 1018.000 and 1018.001).
- Transactions, rules, traces, certificates, and maintained data give one
  account of what a computation read, changed, and was allowed to disclose
  (LLP 1001).
- One named composite query has one execution context and one receipt.
  The client exposes uncertainty instead of inventing missing values
  (LLPs 1018.000 §4 and 1018.003).
- Shared subscriptions, durable follower-tab admission, semantic mutation
  targets, and compaction of discharged successes remove independent copies
  of coordination and reconciliation (LLPs 1018.004 and 1018.003.001).
- LLP 1018.007's corrections preserve acquired pages across offline restart,
  recover explicit sending readiness, and repair the measured application
  receipt loops. The old failures are evidence of the path taken, not claims
  that the corrected behavior still fails.

The source of elegance is reuse of an established fact across several needs.
The remaining weaknesses mostly occur where another layer must reconstruct
that fact, or where a conservative boundary has consequences wider than the
product action that crossed it.

## 3. Findings and confidence

### F1. Sending exposes grant maintenance

In the recorded expiry/page-boundary stress, 23 sends committed; the next
submission could not be admitted with 85 IDs remaining against a certified
352-ID slice. The final correction exposed the existing Sync now action and
its browser witness passed. This is not an unfixed admission bug. It is
evidence that today's intended connected-use contract asks the user to
replenish a finite resource. Those counts describe that workload, not a
platform message limit.

Evidence: [correction completion](./1018.007-clique-correction-program.plan.md#completion-record),
[recovery contract](../snapback2/packages/snapback2/guide/offline.md#recovery),
`client.ts::performResume`, and `writer_replay.rs::grant_if_low`.
Confidence is high in the behavior; the payoff from proactive renewal is a
proposal, addressed by [.000](./1018.008.000-client-owned-recovery.rfc.md).

### F2. Richer query composition increases fallback work

The current pagination guide explicitly says missing count authority makes
`conversationView` partial. A declared `withHistory` observation preserves
downloaded rows without pretending that the composite's count is known.
This is correct and implemented. However, adding a count to a thread changes
what the author must declare to keep the existing messages visible offline.

The [shared thread bindings](../snapback2/packages/snapback2/templates/chat/shared/thread.ts)
describe table identity, row selection, order, create membership, draft fields,
mutation targets, and an independent history query. Some is product policy;
some is a second description of executable relationships. The exact overlap
must be proved before inferring it. Confidence is high in the friction and
medium in the proposed derivation boundary. [.001](./1018.008.001-derived-query-presentation.rfc.md)
preserves whole-query truth and the existing fallback rule.

### F3. Evolution has broad consequences

Enum widening and maintain regrouping belong to LLP 1020. They are not new
tasks here. Separately, `Schema::rule_hash` binds the complete schema;
LLP 1018.002 records two queued rule-verdict conflicts after an optional
message-column addition. Its audit found a conservative disconnected-table
candidate but did not solve that witnessed subject-table edit.

Confidence is high in the broad invalidation and limited in the safe useful
scope of any narrowing. The existing [invalidation RFC](./1018.002-dependency-scoped-invalidation.rfc.md#7-follow-up-after-the-elegance-assessment)
is extended with the next falsifiable experiment. No sibling hash framework,
automatic intent replacement, or claimed compatibility is introduced.

### F4. Proof boundaries shape product data modeling

LLP 1001 §3 deliberately gives a nonuniform scan one opaque capped outcome.
A sufficiently long hidden run can produce an empty capped page with no
continuation even when readable rows exist later. Indexing a uniform visible
scope is the documented escape. This protects disclosure and work bounds;
it also makes authorization structure part of physical query planning.

Quarry has a separate finite-composition gap: a bounded page cannot be
generally projected into a stored or passed list of values. The open
[page-to-list ticket](../issues/20260904-quarry-no-list-from-range.md)
records an original-recipient use case. LLP 1019 will remove that particular
workaround, so it is not enough by itself to commission a new language form.
[.002](./1018.008.002-bounded-collection-composition.rfc.md) requires an independent
use case and preserves capped-source lineage instead of laundering it into a
complete list. The `fn`/`proc` distinction is also friction, but has an explicit
rationale in LLP 1018.005; no merger is proposed without new evidence.

### F5. Delivery and effects still have adjacent costs

The authored delivery table, fan-out calls, tombstones, original-audience
semantics, and durable received acknowledgements belong to LLP 1019. Its
declaration can remove application responsibility without removing the
per-recipient writes and storage. Measure those costs after its implementation;
do not implement another delivery mechanism in this series.

Effect visibility, real execution witnesses, provider stand-ins, stopping,
unused staged-argument disposal, and reset/seed fixes belong to LLP 1021.
The remaining effect authoring issue is that ordinary imported helper
functions are rejected and no-network bodies still require a grant. The
[guide](../snapback2/packages/snapback2/guide/effects.md) and
`packages/compiler/src/lower/effects.ts::validateClosure` establish this.
[.003](./1018.008.003-closed-effect-modules.rfc.md) proposes build-time closure
assembly with the same runtime authority. It does not promise Node or npm SDK
compatibility. Confidence in the current restriction is high; implementation
and size benefits are unmeasured.

### F6. Correct incremental sync is still substantial work

The retained cold cohort covers 10,008 inbox rows in 201 responses, with
p95 22,465.823 ms and maximum 23,753.609 ms. It includes navigation, auth, and
sync on a contended BLACK host. A separate instrumented final diagnostic
completed in 16,737.659 ms and retained 127,619,872 JavaScript heap bytes after
GC. It recorded 207 carrier commits and 613 query evaluations, with one whole
twin snapshot installation. The delivered row images include message,
delivery, and other query images; they are not distinct message counts.

Evidence: [timing cohort](./1018.007.002-bounded-cold-sync.plan.md#current-black-cold-series-qualification)
and [final diagnostic](./1018.007.002-bounded-cold-sync.plan.md#final-candidate-operation-counts-and-post-gc-heap).
Neither is a controlled comparative heap result or proof of an asymptotic
bound. They justify profiling batching, materialization, and duplicate retained
representations, not asserting which dominates. [.004](./1018.008.004-cheaper-offline-acquisition.rfc.md)
continues that work without reopening the completed correction acceptance.

The total retained-data store still has no budget/eviction contract; the asset
byte cache's own limit does not establish one. A retention redesign is on
NOT-DOING and remains an explicit later decision, not an incidental optimization.

### F7. Orientation obscures implemented strengths

The README still describes the compiler as a TypeScript subset compiler. The
root explainer's dated inventory describes the retired lowering path and lists
implemented offline/Expo capabilities under "Not yet". The current packaged
guides are substantially more accurate. Confidence is high: these are direct
text disagreements with the implemented architecture.

This needs a small prose reconciliation, not another corpus or freshness
registry. Section 6 gives the task alongside the five mechanism proposals.

## 5. Priority, constraints, and acceptance

First finish the existing commissions under their own acceptance. These
drafts may be reviewed in parallel; their implementation must inspect the
landed interfaces rather than imposing guessed ones on the current agent.

The recommended next order is .000 (ordinary connected use), .001 (application
composition), then .004 (measured acquisition costs). The invalidation RFC's
bounded experiment can proceed independently after LLP 1020's changes are
available. .002 needs a use case that survives LLP 1019; .003 benefits from
LLP 1021's witnesses. This is a recommendation, not an implementation schedule.

Governing constraints are LLP 1001#3-read-and-write-states-no-silent-states,
LLP 1012#5-retention-revocation-and-the-fence,
LLP 1012#7-writes-offline, LLP 1018.006#2-the-published-record,
and `rules/RULES.md` / `rules/NOT-DOING.md`. Preserve the 85,000-byte complete
local-runtime ceiling, 80,000 target, fixed measurement roots, ordinary runtime
ceilings, fast affected checks, one data language, and no runtime code generation.
None of these Drafts changes those allocations or adds a gate or registry.

Success is measured in application responsibilities removed: normal sends
across multiple grants without a ritual, adding a count without hand-authoring
another fallback, shared effect code without copy-paste, and fewer operations
and bytes to acquire the same authorized offline behavior. Count the complete
React/Expo application, including shared bindings, root observers, and recovery
code. Moving work into a helper file is not a deletion. Keep product choices
such as draft contents, conflict resolution, and disclosure explicit.

Each implementation must name what it deletes, preserve its adversarial
controls, and report affected checks and measured costs. Negative findings may
close a proposed optimization without adding a replacement subsystem. Security
and custody proposals need independent design review before runtime commission;
this document records no review it has not received.

Two review suggestions are not adopted. Dropping selected-operation demand
entirely can leave a disabled composer unable to trigger admission-time renewal;
the implementation must distinguish subscribing a real operation from reading
its pure readiness projection, and renew only when capacity requires it. Nor
may a grant-only response reopen old coverage: partitions with facts require
the existing reauthorization path. No-facts headless capacity acquisition must
not mint authority, clear reset state, or rewrite admitted intent bytes.

Several reviewer claims are not treated as evidence. Gemini's 500-ID example
does not describe the fixed 8,192-ID grant; a 352-ID operation need not renew
per send. Its proposed larger blocks are not selected. The 613 evaluations are
an attribution lead, not proof that all notifications should be suspended across
a network drain. Re-deriving an admitted envelope's verdicts on reset is not
allowed. Compiler code is outside the five-root client allocation; its cost is
still real, but speculative byte estimates are not measured violations.

Astra's concrete integration findings are retained: headless resume can have
no request today; the oldest blocked follower admission also needs demand;
fallback `{ c: null }` is not equivalent to retaining a paginated primary cursor;
the effect VM caches its compiled closure across jobs; and optional expected
generation is already checked before unsettled replay. The relevant children
record these constraints rather than building around assumed interfaces.

Implementation uses the existing main checkout and the clean named `wave3-l16`,
`wave3-media`, and `wave3-guide` worktrees, with their old refs preserved. No fresh
worktree is cut. The dirty `wave3-grammar` lane and unrelated main changes are
left alone. The .002 working-set link is removed because no implementation is
selected; its document remains. Working-set count is now 58, below the unchanged
59-link allocation. Individual implementation/evidence records follow in the
children; a locally passing slice is not an npm publication or benchmark-bar claim.
