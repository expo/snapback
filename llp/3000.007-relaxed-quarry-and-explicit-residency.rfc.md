## Summary

This RFC is cross-referenced by
[LLP 3000.008](./3000.008-holistic-product-excellence.rfc.md). Its
[Quarry child](./3000.008.000-ordinary-quarry-programming.rfc.md) adds
product-level acceptance cases, while the residency and client children cover
the corresponding outcomes. LLP 3000.008 does not alter this RFC's accepted
rulings or implementation record.

The author, after building Clique on Snapback: *Quarry seems great except
too constraining. Its biggest value is describing data that is synced
locally and in the cloud and queried with one language. If you don't need
that, something like Convex or Supabase — more flexible, even if you lose
some nice properties — is probably easier for agents.* He asked for the
thesis to be analysed and, if it holds, for a more relaxed way to use
Snapback 4 where local data is not needed, or relaxed across other seams,
that makes it ergonomic for agents and lets the Clique benchmark run
smoothly. Then, seeing the residency draft he had already commissioned
(LLP 3000.006), he asked whether to push further.

The thesis is half right, and the half that is right points somewhere
more specific than "relax when offline is not needed."

**Right:** the constraints that cost builders time are constraints on the
*program* — a local binds once, no accumulators, no `continue`, no `else
if`, no `where`, no text `+`, no `/` — and every one of them is an
inheritance from Snapback 2's static byte-and-step pricing, not a
requirement of running on a device. LLP 2000.000 §4.1 said so when it
flipped the bound model: *"Decide the bound model, keep the language, and
re-derive its restrictions."* Snapback 4 copied the binder and never
re-derived them. The evidence that they are not device constraints is in
the code: the IR carries `Assign`, `Push`, `Continue`, `Concat` and a
scan `range`; the interpreter — one implementation on the server, in the
wasm and in the native module — runs them today; only the binder refuses
them.

**Not right:** the value that survives without local sync is larger than
"nice properties." Declarative rules that are the audience, typed
refusals with rewrites, the runtime meter, identity, typed assets with a
lifecycle, expiry, jobs on the server's clock and a process that embeds
no JavaScript are why the same builder was faster than Convex on five of
seven Clique milestones in the 0.2.6 run and why authorization is the
dimension Snapback wins. Those do not depend on `sync`. And where the
weaker builders stopped, the cause was not the program language at all:
it was two *model* frictions — spelling the audience twice (the read rule
and the `sync` line) and counters written by one principal into rows
another principal owns — which the mechanism can remove.

So the proposal is not a second, looser language for online-only apps.
It is: **one language, relaxed once for every host under the meter that
already bounds it; the sync audience inferred from the read rule; write
authority decided by the write rule; residency and prediction made
legible instead of inferred at runtime; the online-only mode paved; the
client and dev seams the lanes hit closed; two escape hatches specified
for the last ten percent; and a bar that measures exactly the ceremony
this document claims to remove.** §10 maps every correction loop the five
Clique lanes recorded to the item that removes it. A review received on
rev 1 corrected four claims; rev 3 carries the corrections in §5.0, §5.3,
§5.6, §5.9 and §6.2 and the dispositions beside the review.

## 3. Analysis

### 3.1 Quarry's constraints come from four sources, and only one is the device

| Source | Constraints it explains | Needed when |
| --- | --- | --- |
| **D — device execution and prediction.** A program may run on a device over the rows it holds and predict a mutation before the server judges it | reads over synced tables only for a local answer; `connected` unknown on a device; no clock beyond `now`, no randomness, no network; a mutation's fan-out must be a complete capped group so a prediction is exact | the program is meant to run locally |
| **A — authorization is static.** Rules are the audience a partition can hold; completeness is a class the prefix decides | index-prefixed reads; the rule/sync pairing; `exists` over an index; reads never raise a rule refusal | always: this is what Snapback wins on |
| **M — resources are metered.** Examined rows, probes, steps, heap, output and rows written have ceilings (LLP 2000.000 §6) | a mutation aborts `E_BOUND`, a query caps; jobs chunk | always: the process is scale-to-zero and shared |
| **S — Snapback 2's static pricing**, retired by LLP 2000.000 flip 1 but never removed from the binder | a local binds once; no accumulators; no `continue`; no `where`; `range` literals only; no text `+`; the `fn`/`proc` split; the page-to-list gap; `divmod` in place of `/` | never, under the meter |

The author's thesis attributes the constraints to D. The record attributes
the *costly* ones to S, and the ones that stopped the weaker builders to a
fifth thing: **R — restatement**, where the model asks the author to say
a fact twice (the audience, in the rule and in `sync`) or to restate an
authority it already granted (the write rule) as a read grant. LLP
2000.000 §6 named S's outcome in advance — "What it dissolves: … the
`fn`/`proc` split and the page-to-list gap, which existed to keep
collections priceable" — and §4.1 asked that the restrictions be
re-derived once the bound model was decided. They were not; the binder
came over with Snapback 2's refusals intact. R was not in the brief
because Snapback 2 had neither `sync` nor the hidden-collision ruling.

### 3.2 The interpreter already runs what the binder refuses

- `crates/snapback4-core/src/ir.rs`: `Stmt::Assign`, `Stmt::Push`,
  `Stmt::Continue`; `Builtin::Concat`, `Builtin::Len`; `Scan.range`
  with `gt`/`gte`/`lt`/`lte`.
- `crates/snapback4-core/src/engine/runner.rs`: `Assign` rebinds a local
  (line 149), `Push` appends to a list local under the heap meter (157),
  `Continue` flows (252), `Concat` joins text or lists (417).
- `crates/snapback4-core/src/engine/read.rs:381`: a scan's value range
  is evaluated and applied as bounds on the scan.
- `crates/snapback4-lang/src/bind/program/control.rs:38`: "duplicate
  local"; `parser/expr.rs:178`: "`where` is not a Quarry filter";
  `parser/programs.rs:73`: a job's body is chunks and nothing else; the
  language card's "left out on purpose" list.

Because the device is the same Rust (LLP 3000 §7, 2026-09-13, "one
implementation"), a form the server interpreter runs is a form every host
runs. The relaxations of §5 are binder changes over an interpreter that
already evaluates them, plus small additive IR fields — with one
prerequisite the received review found: the meter charges `Push` and the
construction of a literal list or object (`runner.rs:159, 334, 339`) but
not `Concat`'s result (`runner.rs:417`) and not the clone every variable
read makes (`runner.rs:323`), so the accumulation the new forms invite is
unmetered today. §5.0 lands before §5.1.

### 3.3 What "not needing local data" does and does not change

Without `sync` lines an application already runs online-only today: the
online tier (`createClient`) has no store, `observe` re-runs a query
when a commit touches its tables (`packages/snapback4/src/client.ts`),
and every query answers on the server. What that mode does *not* buy is
a looser program: the binder refuses the same forms. So relaxing "for
cases where you don't need the data locally" would mean a syntax that
varies by tier — and §3.2 says there is no reason for it to. The honest
design keeps the syntax one and lets residency be a fact about the data
an operation reads, computed and displayed, not a mode the author
selects.

Two things *are* genuinely server-only and should be spelled as such:
reads of online-only tables and of `connected`, which the client already
routes to the server (`packages/snapback4/src/local.ts:608`), and a
mutation that reads beyond the device's partition, which the device
already refuses to predict (`E_PREDICT`). Both decisions exist at
runtime; neither is visible at `check`. §6 lifts them.

### 3.4 Where the thesis undersells Snapback 4

Convex's own builders paid for what Snapback carries: password identity
(scrypt by hand), non-time-reactive queries (typing, expiry and presence
filtered on the client), fan-out as a read-time scan, a second project
directory for a second instance, and the whole durable offline layer.
Supabase's paid for four products' seams. Those are the "nice
properties" of the thesis, and they are the reason the Snapback 4 lane
was faster on M1, M2, M5, M6 and M8 at first green. The gap to close is
narrow and named: the last ten percent of a feature — an aggregate, a
ranking, a digest, a notification preview, a grouped result — where an
ordinary loop with a counter and a string is what every model reaches
for; and the two restatements of §3.1 R.

### 3.5 Verdict

Agree that Quarry is too constraining; disagree that the constraint is
the price of local sync, and disagree that the answer is a looser mode
for online-only apps. The constraint is Snapback 2's pricing model wearing
Quarry syntax, plus two places the model asks for restatement. The answer
is to finish the flip: relax the language once, everywhere, under the
meter; let the engine infer what it already knows; let the write rule
decide writes; make where a program runs legible; pave the online-only
choice; close the seams the runs hit; and specify — without yet building
— the two hatches that would remain wanted.

### 3.6 What pushing further means, and where it stops

Pushing further is admitting every form the one interpreter runs
deterministically under the meter, and deleting every restatement. It
stops at: loops the meter can only abort (`while`, data-bound ranges),
floats (the value model), a mutation's unbounded fan-out (prediction and
scale), reads outside the partition on a device (D), and anything that
leaves the engine's write path. The rest — composition, accumulation,
filtering, seeking, grouping, formatting, defaults, patching — is §5.

## 4. Principles

1. **One language, one interpreter, every host.** Every form has one
   semantics, evaluated by one interpreter, on the server, in the wasm and
   in the native module. Where a form cannot be *evaluated* on a host — a
   fact only the server holds, a pass that only a non-predicting mutation
   may make (§5.9) — that is a residency class of the operation, printed
   by `check`, never a second syntax.
2. **The meter is the bound.** A form is admitted if the runtime meter
   bounds its cost; no static byte, step or closure price is reintroduced
   (LLP 2000.000 §6). A loop the meter cannot bound stays refused.
3. **The engine never asks for a fact it already holds.** The audience is
   the read rule; the write rule decides writes; a default the schema
   states is not restated at every insert.
4. **Residency is a fact, not a mode.** Where an operation runs and
   whether a mutation predicts are computed from the tables it reads and
   printed by `check`, carried in `api.ts`, explained by `why`.
5. **No silent class change.** A change that moves an operation from
   device to server, or a mutation from predictable to queued-without-a-
   row, is a note at `check`, never a runtime surprise.
6. **Nothing leaves the engine's write path.** Every relaxation is a read
   or a computation; writes keep rules, constraints, maintains, the log
   and at-most-once (LLP 3000.005's rule 2).
7. **Disclosure is decided once.** A write discloses nothing but its
   outcome; a read discloses rows the read rule admits; no relaxation
   adds a third channel (the blind-review territory of LLP 3000 decision
   4).
8. **The card grows one word at most**, and only by the author's ruling
   (LLP 2000.000 §8).

## 5. The language, re-derived

### 5.0 The meter charges what the new forms allocate (prerequisite)

The runtime meter is the bound this document leans on, and today it does
not charge the two things accumulation does most: `Builtin::Concat`
returns a new string or list without charging its size
(`crates/snapback4-core/src/engine/runner.rs:417`), and every read of a
variable clones its value (`runner.rs:323`) without charging the copy,
while `Push` and literal construction do charge (`runner.rs:159, 334,
339`). A loop that rebinds `s = s + row.body` over 8,192 rows of 4,000
characters would allocate past the 16 MiB heap ceiling with only the step
meter watching. LLP 3000.002 lists interpreter heap among the boundaries
still needing an owner. Before any of §5.1 lands:

- `Concat` charges the result's `heap_bytes()`; `Let` and `Assign` charge
  the bound value's size when it is a string, list or object; a list or
  page produced by `group`, `sort`, `slice` or a shape charges its size,
  as scan results do today (`runner.rs:371, 376`);
- variable reads stop cloning large values, or charge the clone; the
  choice is measured on the fixture, and the cheaper one that keeps the
  ceiling honest wins;
- a stress test in the corpus: a concatenation loop and a list-growing
  loop each abort with `E_BOUND` naming the heap meter at the ceiling, on
  the server and on both device stores, and a query cut the same way
  reports `complete: false` with its `capped_at`.

This is a correction the received review made to rev 1's claim that the
interpreter "needs almost nothing"; it needs this.

### 5.2 Composition: helpers with bodies, jobs with preludes

**8. `fn` takes a body.** Today `fn` is one expression and `proc` is a
block that returns nothing, so the 0.1.0 builder wrote the receipt
fan-out three times (`send`, `sendMedia`, `sendPoll`) and the 0.2.6
builder wrote its receipt state as three nested one-line `fn`s. LLP
2000.000 §6 named the split as pricing residue. Proposed: one `fn`,
declared with an expression or with a block ending in `return`, callable
in expression position anywhere; expanded inline as helpers are today
(`bind/program/control.rs`), so a write inside a body is admitted exactly
when the caller may write (a query calling a writing `fn` is a placement
error at the call site, with the site named). `proc` is deleted with the
rewrite `fn` (rules: delete, don't deprecate).

```quarry
fn receiptState(cid: conversations, sender: principal, seq: int):
  unread = 0
  undelivered = 0
  for m in memberships[cid] first 50 by byConversationPrincipal:
    if m.principal = sender or m.joinedSequence >= seq:
      continue
    if m.readSequence < seq:
      unread = unread + 1
    if m.deliveredSequence < seq:
      undelivered = undelivered + 1
  return 'read' if unread = 0 else ('delivered' if undelivered = 0 else 'sent')
```

**9. A job may have a prelude.** Today a job's body is `chunk` sweeps and
nothing else (`parser/programs.rs:73`); both 0.2.6 builders hit it
("jobs must start with chunk"; "job-level binding outside a chunk").
Proposed: statements before the first `chunk` form a prelude that runs at
the start of every chunk under that chunk's meter — argument-derived
bindings, a config row, `divmod` of the period — with its bindings
visible in every chunk. Re-running it per chunk keeps a chunk wholly
done or not started; a prelude that writes is refused (a write belongs
to a chunk).

### 5.3 Data access: seeks, groups, a page is a list

**10. Range seeks in the key.** The IR and the runner already scan a
value range on the first unpinned index column (`Scan.range`,
`read.rs:381`); Quarry has no spelling for it, so a builder who needs
"messages at or after this one" or "posts in the trailing day" scans
from the start of the prefix and filters, examining everything older.
Proposed: a comparison on the first unpinned column inside the key
brackets is a seek — `t[prefix, col >= x]`, `t[prefix, col > a, col <=
b]` — priced as a prefix, continued by a cursor as any page is. A `where`
on that column alone is accepted and lowered to the same seek, with a
note naming the seek spelling so the cost is visible.

```quarry
query around(conversationId: conversations, messageId: messages):     -- M3: tapping a quote jumps to the original
  q = messages[messageId] ! else NOT_FOUND
  before = messages[conversationId, at < q.at] last 20 by byConvTime
  after = messages[conversationId, at >= q.at] first 21 by byConvTime
  return { before, after }

query trending():                                                     -- M8: the top ten of the trailing day
  day = posts[at > now - 86400000] first 8192 by byTime { id, at, likes: likeCounts[.id] }   -- the whole day, up to the examined ceiling
  return slice(sort(day, '-likes', '-at'), 0, 10)
```

A ranking is a ranking of the rows it examined. Rev 1 of this example
ranked `last 200` — the newest two hundred of the day — and the received
review caught that it could omit the day's most-liked post. The corrected
form seeks the whole day up to the examined ceiling; a day past the
ceiling is cut by the meter and the card says `complete: false`, so the
reader is told the top ten is of an incomplete set rather than shown a
plausible one. A `sort`, `group`, `sum` or `count` over a page with a
`next` cursor is over that page, and `check --cost` prints it as such.
For a population that outgrows the ceiling the maintained ranking on the
`feeds` card — `ranked`, scored by a job on a cadence — is the recipe, and
it is what the 0.2.6 lane built.

**11. `group`, `first`, `last`, `at`.** Grouping is the one shape neither
accumulators nor sorting give, and Clique asks for it three times
(global search grouped by chat, reactions counted per emoji, receipts by
stage); the value model has no dynamic map, so a builder groups on the
client. Proposed builtins, all over lists and pages, heap-metered:
`group(list, 'col')` → `[{ key, items }]` in first-seen order;
`first(list)`, `last(list)`, `at(list, i)` → the element or null;
`join(list, sep)` and `trim(text)` beside `lower(text)`, the small text
library the digest and the push preview keep asking for. A typed `map` is
considered and deferred (§11).

```quarry
query reactionCounts(messageId: messages):
  m = messages[messageId] ! else NOT_FOUND
  rows = reactions[m.conversationId, messageId] first 50 by byConvMessage
  return group(rows, 'emoji') { emoji: .key, count: count(.items), mine: exists reactions[messageId, viewer] }
```

**12. A page is a list.** `sort`, `slice`, `count`, `sum`, `group`,
`first`, `last`, `at` and `for` accept a page, a list, a shaped
collection and a list argument alike; the three types unify for every
list-valued builtin. This is LLP 2000.000 §6's page-to-list gap, closed.

### 5.4 Writes and schema: patching, defaults

**13. `upsert` patches.** Today `upsert t[key] { fields }` replaces the
row; the 0.2.6 builder lost an avatar to it, and every model expects
insert-or-update-these-fields (Postgres `ON CONFLICT DO UPDATE`,
Convex `patch`). Proposed: when the row exists, the fields are an
`update` patch and unnamed columns keep their values; when it does not,
the fields are an insert and a missing required column refuses `E_INPUT`
naming it. The card's "insert or replace" becomes "insert or patch".

**14. Column defaults.** `at: time default now`, `authorId: principal
default viewer`, `count: int default 0`, `role: enum('member', 'admin')
default 'member'`: an insert may omit a defaulted column; the engine
fills it on the host running the write, as it evaluates an explicit
`at: now` today, so a device's prediction and the server's judgement
agree as they do now. Defaults are literals, `now` and `viewer`; nothing
computed.

### 5.5 The guessed spellings

Every lane guessed at least one of these and paid a loop for the
diagnostic: `elif`; `cond ? a : b` for `a if cond else b`; `a?.b` for
`a.b if a != null else null`; `len(x)` for `count(x)`; `//` and `#` line
comments for `--`. Rev 2 proposed admitting them as aliases. **Ruled
(2026-09-13): the language keeps one spelling.** None is admitted; the
parser recognizes each guess and refuses it with the canonical form as
the rewrite, as `E_QUARRY_UNSUPPORTED` does for most of them today, and
`check --fix` (§8.9) applies the rewrite in place, so a guess costs a
command rather than a loop. The card stays one form per idea and
`NOT-DOING.md`'s "one spelling" stands.

### 5.6 `where`: completeness, the cursor, and reads inside it

A filtered page is `complete: true` when it holds N matches or the scan
reached the end of its range, and `complete: false` when the meter cut
it. `Scan` gains one field, `filter: Option<Expr>`; the runner applies it
inside the scan loop after the read rule; `pages.rs`'s page-plan analysis
and `N_NO_CURSOR` treat a filtered scan as a scan; on a device the same
code runs and `beyond_horizon` is unchanged.

**The cursor never positions after a hidden row.** Rev 1 said a cut page
continues after the last *examined* row, so a continuation could not
re-examine the rejected run; the received review pointed out that a
cursor is base64url over the index key values (`cursor.rs:51`) and that
the last examined row may be one the read rule hides, whose key the
viewer must not learn (LLP 3000 §7, "completeness is a class": the cut
site stays off the wire; a hidden row costs what a miss costs). The rule
is therefore: a filled page's `next` is after its last returned row; a
cut page's `next` is after the last **rule-visible** examined row —
returned or filter-rejected — and never after a hidden one. A visible
row's key is the viewer's to see whether or not the author's predicate
kept it, so nothing is disclosed, and a continuation still advances past
every filter-rejected run. On a uniformly authorized range (the rule
decided by the prefix) every examined row is visible and the two rules
coincide. On a non-uniform range the page keeps its existing class —
never `complete` (`N_NEVER_COMPLETE`), and a cut inside a hidden run ends
on an empty capped page as it does today — so `where` adds no channel
the non-uniform class did not already close.

Reads inside the predicate (`where exists likes[.id, viewer]`) are
proposed as admitted: each is a rule probe the probe meter already
counts, and `check --cost` prints the class as "probe × examined". Rev 1
deferred this; the Trending and grouped-search shapes want it, and the
meter bounds it.

### 5.7 What stays refused, and why it is not S

- `while` and recursion: a loop with no intended bound has only the step
  ceiling (1,000,000 steps, an abort) between it and a runtime failure
  for one user (LLP 0329.014.004 §3: "Refused, unchanged: `while`,
  recursion"). `range(a, b)` over int *expressions* is admitted in rev 3
  at the received review's suggestion — a range has an intended bound
  even when it is an argument's, and the step meter holds it; `check
  --cost` prints such a loop as "steps ≤ meter" rather than a literal
  count. `for` over a page, a list, a range or `tokens`, plus a job's
  `chunk`, cover the reference applications.
- A mutation's loop over a page that is not one complete capped group
  (`E_STRUCTURAL_FANOUT`): D, for a mutation that predicts. A prediction
  must be exact and a write's fan-out visible; the 0.2.6 builder called
  this refusal valuable. The rewrite already names the job. §5.9 admits
  the same pass in a mutation that does not predict.
- Index-prefixed reads outside `where` and seeks; `exists` over an
  index: A.
- Floats: the value model has none; a native job or read (LLP 3000.005)
  is the hatch, and a score is rounded to an `int`.
- A typed `map` with dynamic keys: deferred (§11); `group` is the first
  answer and the rerun says whether the second is needed.

### 5.8 The language card after the change

The "left out on purpose" list loses its S entries and gains none. The
card's program grows a counter, a filtered page, a seek, a grouped
result, a helper with a body, a job prelude, a default and a patching
upsert; the suite compiles and runs it as today. `E_QUARRY_UNSUPPORTED`
for `where`, `continue` and the aliases, "duplicate local", and the

### 5.9 A non-predicting mutation may pass over a bounded page of a uniformly authorized prefix (revised after the blind review, §15)

`E_STRUCTURAL_FANOUT` refuses a mutation's loop over a page unless the
page is one complete schema-capped group over a uniformly decided read
rule (`admission.rs:241–251`), because a prediction must be exact and
"for each member" must mean every member. The completeness reasons belong
to a mutation that predicts; the uniformity reason does not, and both
blind reviews showed why it must stay: a mutation runs under `Cut::Abort`,
so a pass over a non-uniform prefix whose hidden candidates exhaust the
examined ceiling aborts with `E_BOUND` where a query of the same prefix
answers one card whatever it found (`h1_a_non_uniform_scan_is_capped_
whatever_the_meter_found`). Abort versus success would be the
hidden-population bit the meter-cut review closed.

Proposed, as revised: in a mutation classified as never predicting
(§6.2 — a `server` site, or `: server` written by the author), a `for`
over a bounded page whose read rule is **uniformly decided by the
prefix** is admitted without the complete-group and cap clauses; rows
written are metered (1,024 per mutation); the pass is atomic; merges and
unknown origins keep today's refusal; a page over a non-uniform prefix
keeps `E_STRUCTURAL_FANOUT` whatever the mutation's class. `check --cost`
prints "a pass over the first N rows of <prefix>, examined ceiling
<n>", so the partial claim is on the record. A predicting mutation keeps
the complete-group requirement. The variant both reviews name — ending
the pass at the ceiling the way a query does and committing the visible
prefix — is not proposed; it changes the promised semantics and needs
its own analysis. Regressions: §15's `m3_*` and `p2_*` list. Awaits the
author's ruling (§14, 15).

## 6. Residency and execution, made legible

This section absorbs the author's residency draft (LLP 3000.006) and
reduces its vocabulary to what the code already decides; §6.10 records
what was kept and what was not.

### 6.1 `online only`

A positive spelling for the table line whose absence today means
online-only:

```quarry
table auditEvents:
  actorId: principal
  action: text <=100
  at: time
  by byActorTime: actorId, at, id
  read <- exists admins[viewer]
  insert <- deny
  online only                          -- rows never enter a partition or a device
```

Optional: a table with neither `sync` nor `online only` keeps today's
meaning with no note. `check --residency` (§6.3) shows every table
either way, so the line is documentation the author can choose, not a
tax on every table. Whether it becomes required is the author's (§14).
The same line on a `maintain` opts it out of inheriting its source's
`sync` (§6.7).

### 6.2 Two words per operation, from the classes of its read sites

`check` classifies every read site, then rolls the sites up to the
operation. The received review was right that rev 1's roll-up — "every
table is synced" — was too coarse: a synced table with a horizon does not
establish that a device holds a given row or can prove its absence, and
the 0.2.6 lane's `exists messages[id]` guard is exactly a read over a
synced table that no device could decide beyond its horizon. So the site
classes are:

| Site class | Meaning |
| --- | --- |
| `held` | a synced table with no horizon, or a maintain inherited into the partition: every row the viewer may read is on the device |
| `horizon` | a synced table with `last N`: held inside the horizon, decided by the server beyond it; a point read by a key the horizon does not order (an `id`) is `horizon` too, since absence cannot be proved locally |
| `server` | an online-only table, `connected`[^connected-effects], or a native read on a device without the module |

[^connected-effects]: `connected` in a mutation that decides only effects: §19.1.

and the operation's words are:

- a query **runs on the device** when every site is `held` or `horizon`
  (a `horizon` site past its horizon is `complete: false` and the client
  re-asks the server whole, `local.ts:617`, as today); otherwise it
  **runs on the server**;
- a mutation is **eligible to predict** when every read site is `held` or
  `horizon` and every write is to a synced table (LLP 2000.000 §7.3); it
  is **queued without a row** when a site is `server`. Eligibility is
  static; whether a given call *predicted* is the device's word at
  admission, and when a `horizon` site could not be decided the runtime
  refusal names the site and the key it could not establish (`E_PREDICT`
  today says only "a read it needs is not on the device"; it says which).
  `N_NOT_PREDICTABLE` (§6.4) fires when eligibility is lost, and `check`
  additionally marks each `horizon` site in an eligible mutation as "may
  queue without a row past the horizon", which is what the 0.2.6 builder
  needed to read before its offline probe.

Queueability is independent of both words: every mutation is durably
queued by the outbox whatever it reads; prediction is the only thing a
`server` site removes. A native read is `held`-class on a device with
the module and `server` on one without.

`api.ts` carries the words on `Op`: `runs: "device" | "server"` for a
query, `predicts: "eligible" | "never"` for a mutation with the `horizon`
sites listed, and a doc comment per operation with its arguments, result
and the `require` codes it can raise (§8.11). The card is unchanged;
these are facts about operations, not screen states.

### 6.3 `check --residency` and `why`

```text
residency
  profiles          public, no horizon (one row per principal)
  messages          to memberships[.conversationId] (from the read rule), last 500 by byConvTime
  auditEvents       online only
  receiptEvents     online only (no sync line)
  repostCounts      public (inherited from feedEntries) — N_MAINTAIN_SYNCED: one row per post reaches every device

operations
  thread            device; server past the horizon
  insights          server: reads activityTotals (online only)
  send              predicts
  createDm          queued without a row: reads dmPairs[other, viewer] beyond the partition
```

`why <op>` prints the site that makes an operation server-run or
non-predictable and the shortest rewrite that would change it. `why
<table>` prints its residency line and, for an inferred audience, the
rule it was inferred from.

### 6.4 Notes when a class moves

Two notes, in the family of `N_NO_HORIZON`:

- `N_NOW_SERVER` — a query that ran on the device in the previous
  generation now reads a site the device does not hold; the note names
  the site.
- `N_NOT_PREDICTABLE` — a mutation that predicted in the previous
  generation no longer does; the note names the read. This is the
  0.2.6 builder's hardest loop (a redundant `exists messages[id]` guard
  beyond the horizon) surfaced at `check` instead of in an offline probe.

`dev` compares against the generation it is serving; `check` alone
compares against `snapback/generated/` when present.

### 6.5 The offline outcome of a server-run read, and its liveness

Today a server-run read while offline is either `denied: E_OFFLINE`
(when the device refuses) or a plausible empty page (when it does not;
`local.ts:620` returns the device's data with `complete: false`). With
the class known at compile time the client does two things it cannot do
today:

- it keeps the last server answer of each observed server-run query for
  the client's lifetime, and offline returns it with `fresh: false` and
  `since` — the words already on the card — and returns `denied: {
  code: "E_OFFLINE", family: "link", retryable: true }` only when it has
  none. Never a plausible empty page;
- it re-runs an observed server-run query when a commit touches its
  tables, as the online tier does (`client.ts:276`), so a server-run
  query on the local-first client is as live as a device-run one. Whether
  the local-first client does this today is an acceptance item (§13),
  not a claim.

The residency draft's `{ unavailable: "requires-online" }` word is not
needed: `E_OFFLINE` on the card is that word.

### 6.6 The audience is the read rule

Today a synced table spells its audience twice: `read <- exists
memberships[.conversationId, viewer]` and `sync to
memberships[.conversationId]`, and `check` refuses any mismatch with a
rewrite (`E_SYNC`, `bind/schema.rs:51`). LLP 3000 §7 already binds
delivery to the rule's probe, so the second line adds no information the
engine does not derive. Muse spent six compile iterations here; Grok
named it its main friction. Proposed: `sync` with no `to` clause, with
or without a horizon, means *the audience my read rule states*:

```quarry
table messages:
  ...
  read <- exists memberships[.conversationId, viewer]
  sync last 500 by byConvTime           -- to memberships[.conversationId], from the rule

table todos:
  ...
  read <- .ownerId = viewer
  sync                                  -- to .ownerId

table notices:
  ...
  public 'notices are public'
  sync last 100 by byTime               -- public
```

The three invertible rule forms infer to the three sync forms; a target
with several principal columns still needs `by .col`, and `check` says
so; a rule that is not one of the three refuses `E_SYNC` with the rewrite
as today. `sync to …` remains valid and, when written, must equal what
the rule implies — the check that exists becomes a consistency check on
an optional clause rather than a requirement to restate.

### 6.7 A maintain that reaches every device says so

A `maintain` grouped by a public source's audience columns inherits
`sync public`: one value row per group on every device. The 0.2.6 Astra
lane's repost counter did exactly that — one row per post replicated to
every device, a cold-start timeout at the 50% checkpoint, and a
schema change mid-replay. Proposed: `N_MAINTAIN_SYNCED` names every
maintain whose inherited audience is public or a wide group, with the
row count it implies on the fixture when one is loaded, and `online
only` on the maintain opts it out of inheritance; `check --residency`
lists it (§6.3).

### 6.8 Measured residency on the fixture

`snapback4 test --residency [--fixture dir] [--as persona]` prints, per
synced table and per named persona, the rows and bytes the persona's
partition would acquire cold, and the total, beside the `N_NO_HORIZON`
and `N_MAINTAIN_SYNCED` notes. Facts (declared audiences, horizons,
caps) are printed as facts; fixture measurements as measurements; nothing
is extrapolated. This is LLP 3000.006 §9's "hub estimate," done as a
measurement on the fixture the suite already loads rather than an
estimate.

### 6.9 Two recipes, on cards, from the lanes

- **Receipts as high-water marks** (the `messages` card gains it). The
  0.1.0 lane broadcast one receipt row per message per recipient into
  the conversation partition and paid the cold sync; the 0.2.6 lane kept
  `joinedSequence`, `deliveredSequence` and `readSequence` on the
  membership row and computed the aggregate from the members page (§5.2
  shows the helper). One row per member per conversation, synced with
  the membership, a `fn` over fifty rows: the compact projection LLP
  3000.006 §8.1 asked for, in the shape a builder found.
- **Digest counters as period-bucketed maintains** (the `jobs` card
  gains it). `maintain activityPeriods: count activity by principal,
  period, kind` and `maintain unreadPeriods: count receipts by
  conversationId, principal, period, stage` are what the 0.1.0 lane
  wrote; the 0.2.6 Grok and Muse lanes hand-kept four and two counter

## 7. The online-only mode, paved

An application that wants no partition writes no `sync` line and opens
`createClient`. Both exist. What is missing is that nothing tells an
agent this is a first-class choice:

- `snapback4 init --online` writes a template with no `sync` lines, a
  `public`/`.col = viewer` schema, and a client on `createClient`;
  `init` (the default) keeps the local-first template; `init --expo`
  (§8.10) adds the native starter. The README's §1 gains a paragraph,
  "Two ways to run," and the language card's `sync` comments say "omit
  for an online-only table."
- `check --residency` on such a schema prints every operation as
  `server`, and `api.ts` says so; `useQuery` on the online tier is live
  through `/changes` as today.
- Nothing else changes: the same rules, meter, identity, assets, jobs,
  effects and diagnostics. A `sync` line added later moves an operation
  to the device and `N_NOW_SERVER`'s inverse is silent, because moving
  onto the device loses nothing.

This is the relaxed mode the author asked for, and it costs a template
and two paragraphs because the substrate already supports it.

## 8. The client, dev and rule seams the runs hit

Each item names the loop it removes (§2.2).

1. **A mutation's result reaches the client.** `Write` gains
   `result` on `sent` (the server already answers with it,
   `crates/snapback4/src/serve.rs`); `useMutation().run()` resolves with
   the `Write`. Ruled (2026-09-13): `result` on `sent` only — no
   `predicted` on `pending`; a prediction is visible as `pending` rows,
   not as an answer.
   Fresh replies remove Grok's DM-reuse lookup. **2026-09-14 correction
   under LLP 3000.008's delegated program:** §17 deliberately withholds
   historical values on replay. `Write<R>` therefore distinguishes fresh
   `sent` with `result: R` (including null) from `sent` with
   `replayed: true` and no result. Both clients and hooks preserve this
   distinction; a lost acknowledgement never grants historical read
   authority or justifies resubmission with a new ID. An application may
   make a newly authorized query when it receives execution identity only.
2. **A shape over a device row keeps `pending`.** `*` spreads device
   metadata through as it spreads columns; `api.ts` types a shaped
   object with `pending?: boolean` when its base is a row. Removes the
   0.2.6 M6 loop and the `historyRows` second query.
3. **`webDevice()` persists the wasm.** The opener keeps the module's
   bytes in IndexedDB by digest and opens on them with no network, so an
   offline reload does not depend on a URL. Removes the M3 loop the
   builder solved by hand and makes the cold-offline promise the
   opener's, not the app's.
4. **The `{ id }` asset argument predicts.** The device resolves the
   uploader's own upload facts onto the argument as the server does
   (`issues/20260913-snapback4-video-id-only-prediction-refuses.md`).
5. **Identity admission under `dev`.** Ruled (2026-09-13): on loopback,
   `snapback4 dev` lifts the per-peer and per-email minute counters to
   what the host can carry — the Argon2 slots and the connection caps,
   which are the physical bounds, remain — and prints the fact once;
   `serve` is unchanged. Removes two loops in each of the Astra and
   Grok lanes and the harness's backoff scaffolding.
6. **A hidden unique clash says what it is.** The refusal stays generic
   `E_RULE` where it must (§8.7), and its message adds the one sentence
   from `why E_RULE`: "or a unique key collided with a row you cannot
   read; to write into another principal's row use `upsert` under an
   `update` rule, or let a `maintain` keep the count."
7. **Write authority is the write rule (revised after the blind review,
   §15).** What Clique's counter tables hit is the binder: a unique-key
   `update` or `upsert` reads its target under the READ rule first
   (`bind/program.rs:603–641`), so a hidden target looks absent — an
   alternate-key update is `NOT_FOUND`, an upsert inserts and collides
   with generic `E_RULE` — while a by-id `update` already fetches without
   a read check and applies the update rule (`write.rs:66–100`). Two
   lanes opened their tables to get past it. The proposal, narrowed to
   what both reviews found defensible:
   (a) **target resolution is engine-private**: a unique-key or id write
   resolves its target without the read rule, then the table's `update`
   rule decides, as Postgres applies an `UPDATE` policy without a
   `SELECT` policy;
   (b) **one failure word for an unreadable target**: absence, an update
   rule that refuses, a failed `if` condition, an immutable-column
   mismatch and an incomplete patch on the insert path all answer
   `NOT_FOUND` — the zero-row update — with no `current`, no named index
   and no named column; a readable target keeps today's codes. The
   disclosure granted is exactly: a row the update rule let this writer
   modify exists, and the rule's predicates held of it;
   (c) **the merged image never leaves the engine**: a valued write's
   `result` and `E_CONFLICT`'s `current` are a read-rule `get` (null when
   hidden), never the merged row; `old` in `update (old, next)` is the
   engine's, bound nowhere in the author's program; asset facts on
   unchanged columns are preserved without re-validation, and the update
   rule is checked before any asset diagnostic (`write.rs:75–156`);
   (d) **withheld before recorded**: `_ops` stores exactly the body `/m`
   returns, so a replay cannot grow a row (the existing gap is
   `issues/20260913-snapback4-ops-replay-returns-cached-content-after-revocation.md`);
   (e) **the device never predicts against a target it does not hold**:
   a fetch miss on a write is queued without a row — no predicted
   `NOT_FOUND`, no predicted insert, no `pending` row — on both stores,
   and `admit` queues that class (today `local::predict` raises
   `E_PREDICT` only past a horizon, `admit` fails on any other refusal,
   and an upsert miss takes the insert path and plants a `pending` row);
   (f) **`insert … if absent` on a hidden collision stays `E_RULE`**
   (S05), and so does a collision with any *other* hidden row on another
   index: target authority does not transfer;
   (g) **a readable maintain over a hidden source is a declared read-rule
   channel** — a writer who may read the aggregate learns the delta they
   caused; `check` notes an update rule wider than the read rule under a
   maintain the writer can read;
   (h) `delete` is out of scope.
   Not claimed: constant time; that constraint outcomes disclose nothing
   — a cap counted over physical rows, `after insert` on the insert
   branch, a budget abort near a ceiling — which the GPT review lists and
   §15 records as residuals of the narrowed contract. Regressions: §15's
   `s05_*` and `w1_*` list. Awaits the author's ruling (§14, 15).
8. **`snapback4 sql "…"`, a fifth observability verb.** Read-only SQL
   over generated per-table views (`json_extract` over the store's
   `r(t, id, data)`, `crates/snapback4-core/src/store.rs:101`), as the
   developer over the dev store or a `--release` directory, bounded by a
   row limit; never an application surface and never rule-filtered,
   because it is the developer's own store. Answers the ground-truth
   complaint of two essays and the operations dimension (53 against 76);
   the 0.2.6 Astra lane backed up its SQLite by hand to get the same
   thing. Ruled (2026-09-13) as a fifth named verb beside `why`,
   `trace`, `logs` and `data`; the Moves line is in `NOT-DOING.md`.
9. **`snapback4 check --fix`.** Applies the spelling-class rewrites in
   place — an ambiguous key's `by`, a cursor index's missing `id`
   tie-break, an alias to its canonical form, `proc` to `fn` — and prints
   every other diagnostic as today. The diagnostic-and-rewrite loop
   exists so an agent can apply the rewrite; the tool applying the
   mechanical ones is the loop bar's cheapest win.
10. **`snapback4 init --expo`.** The `apps/chat-expo` starter with a
    Hermes-clean toolchain pin. Grok's seven failed iOS exports were an
    Expo/Babel version mismatch in the app, not Snapback; a starter
    removes the guess and the native artifact the grade wants.
11. **`api.ts` documents itself.** A doc comment per operation: the
    arguments, the result, `runs`/`predicts`, and the `require` codes
    the program can raise, which the binder knows statically. Agents
    read `api.ts` before the README.
12. **A server exit without a diagnostic.** The 0.2.6 Astra lane's scale
    instance exited twice during a schema change with a backfill and left
    nothing in its log; filed as
    `issues/20260913-snapback4-dev-exits-without-diagnostic-during-schema-change.md`.
    A defect, not a design item; listed because "sail through" includes
    not dying silently.
13. **An SDK-managed cache for ordinary media.** Asset responses are
    `private, no-store` by design, so every local-first builder — both
    Astra runs, and the Convex and Supabase builders for their own
    reasons — wrote a per-principal media cache by hand, with its own
    purge on revocation and its own view-once exclusion. Proposed: the
    local-first client keeps the bytes of ordinary `image`/`video`
    assets it has fetched, keyed by asset id and home row, in the
    device's own storage (IndexedDB on the web, the documents directory
    under the native module), with explicit retention (`assets: { keep:
    "viewed" | "none", maxBytes }`), purged when the home row leaves the
    partition, is cleared, expires or is deleted, and never for a `once`
    asset. `useAsset` reads the cache first offline. This is the
    residency draft's "ordinary media durability" gap and the received
    review's second-phase item; it makes the cold-offline promise the
    client's rather than the app's, as §8.3 does for the wasm. Ruled by
    the author on 2026-09-13: it lands with the language (§12, A).

## 9. Escape hatches for the last ten percent

Two hatches remain wanted after §5–§8, by the builders' own words:
ordinary code for integrations and SQL for reporting — in that order.
Worker actions (§9.2) are commissioned with the seams (§12, C2; ruled
2026-09-13), with Interview (LLP 3000.004), already on Snapback 4, as the
application that proves them: an
authentication provider, model calls and provider webhooks are exactly
the request-and-response integrations effects, service seats and minted
sessions stop short of, and Clique never needed one. SQL reads (§9.1)
stay specified and unbuilt until the reporting gap is measured after §5:
with seeks, `group` and the inspection SQL of §8.8 the case narrows to
familiarity, and the design as drafted has three costs the received
review named — the generated views cannot use the secondary index table,
the rule translation is a second authorization surface, and SQLite's
progress handler counts approximate virtual-machine instructions rather
than Snapback's resource contract — that a measured need has to justify.

### 9.1 SQL reads

```quarry
query insightsSql(): sql
```

with the body in `snapback/sql/insightsSql.sql`, read-only, over
per-viewer authorized views the compiler generates from the read rules
(`public` → `TRUE`; `.col = viewer` → `col = :viewer`; `exists t[.a,
viewer]` → a correlated `EXISTS`; `and`/`or`/`not` → the same). The
secondary index table is not usable by SQLite's planner, so a SQL read is
a scan bounded by SQLite's progress handler as the step meter, an
injected `LIMIT` as the output bound, and an authorizer that denies
writes, the internal tables and the raw `r`/`i`. Always server-run; typed
`unknown` in `api.ts` unless a shape is declared. It is a second query
language, which `NOT-DOING.md` refuses; it earns a Moves line only if the
rerun shows reporting still costs loops after §5.

### 9.2 Worker actions

```quarry
action sendInvite(to: text <=200, message: text <=2000)
```

An operation whose body is the application's own TypeScript in the
worker it already runs for effects (`snapback4/worker`): the client
calls `api.sendInvite` like a mutation; the server keeps the request,
a worker with a service token claims it over the wire (as it claims an
effect), performs it with a short-lived session the server minted for
the *viewer* — so its reads and writes run under the viewer's rules,
never the service's — and settles a result the server returns to the
waiting client. At-least-once, no transaction, never predicted, offline
is `E_OFFLINE`, and `dev` spawns `snapback/worker.ts` when it exists.
The engine still never calls out. This is Convex's action in Snapback's
shape and the answer to "there was no ordinary server function into
which I could move the awkward part" for the parts that need the
network.

### 9.3 Considered and not proposed

- **Native mutations** (`mutation x(): native`) for server-run
  mutations: consistent with §6 — a mutation that does not predict has
  no device twin to protect — but the Rust toolchain is the wrong
  weight for the ten percent; LLP 3000.005 stays the floats-and-vectors
  hatch.
- **A JavaScript engine in the process**: refused by `NOT-DOING.md`,
  the security review and the Snapback 2 record (Ibex's subset library
  was the effect runner's whole friction).
- **SQL writes**: bypass rules, constraints, maintains, the log and
  at-most-once. Never.

## 11. Alternatives considered

- **A relaxed grade by syntax** (`query x(): server` admits the relaxed
  forms; device programs keep the strict ones). Rejected: §3.2 shows the
  forms are device-safe, so the grade would exist only to preserve a
  restriction the meter already replaced, and every author would learn
  two languages to write one.
- **Online-only by default; `sync` as the opt-in exception.** Rejected:
  it is already the case (a table without `sync` is online-only) and the
  bet of LLP 2000.000 §7 is local-first; §7 paves the choice without
  moving the default.
- **Make the residency line mandatory now.** Deferred to the author; the
  table view gives the same legibility without a line on every table.
- **`{ unavailable: "requires-online" }` on the card.** Not needed:
  `denied: E_OFFLINE`, family `link`, retryable, is that word, and §6.5
  makes it the only offline outcome of a server-run read that has no
  last answer.
- **A typed `map`** (`m[k] = v`, `keys`, `has`; `Value::Map` exists in
  the value model). Deferred: it needs a typing rule and a `SetKey`
  statement in the IR; `group` covers every grouped shape Clique asks
  for; the ceremony bar says whether the general tool is still wanted.
- **Acquired history**: rows the server answered to a device-run query
  that fell back past its horizon are kept on the device as delivered
  history for that group, so "previously viewed" survives a cold start
  without a wide horizon. The 0.2.6 lane removed its horizons to satisfy
  the brief's "previously synced" and paid the cold sync. Deferred: the
  replica would hold a second kind of row, shaped queries cannot supply
  rows, and revocation must cover both kinds; a real feature for
  messengers, with a substrate cost this document does not price.
- **World-readable counters** as the idiom for cross-principal writes.
  Rejected: it is what two lanes did, and it is a disclosure; §8.7 is
  the mechanism.
- **A full `fn`/`proc` unification with recursion.** Recursion stays
  refused (an unbounded loop by another name); inline expansion with a
  depth of eight is kept.

### 18.1 Search across the viewer's groups is a merge of matching lanes

A `merge` over a words index is admitted when the merge reads `matching q`:
each lane is one scope prefix of the index, read as the matching scan already
reads a scoped search (the first term's words as ordered lanes, at most 32),
and the lanes merge into one page ordered by the index's order columns. Each
lane's rule is decided by its prefix, so a lane is one verdict and its page
is complete; the merged page is complete when every lane's is, and a merge
past 50 lanes carries N_WIDE_MERGE as a feed does. The spelling, on the
search card:

```quarry
query everywhere(q: text <=100, c: cursor ?):
  return merge messages matching q after c last 50 by byRoomWords:
    [m.roomId] for m in members[viewer] first 50 by byPrincipalRoom
```

The same code runs on the device over the held rows, where the partition
holds exactly what the viewer may read. N_NEVER_COMPLETE's rewrite for an
unscoped words scan under a per-scope rule names this form before "read it
on the device". Not admitted: a merge over a words index without `matching`;
relevance ranking (NOT-DOING stands). The binder owns the exact grammar
position of `matching` in a merge; if the parser needs it elsewhere than
above, the card and this section move together.

Built as written (lane CU1): the spelling above is the parser's. A
matching merge lowers to scoped matching scans in the existing lane IR, so
no corpus shape changed; a lane's rule is judged once against its scope
before its words are discovered, so a denied lane returns nothing and
costs nothing that depends on its rows; a rule that is not uniform over the
scope keeps per-row checks and the never-complete note.

**2026-09-15 — W7d, the 0.2.22 H5 envelope.** The search card's

### 18.2 Retained history survives revocation under a horizon

`retain delivered-history` keeps what a device was given whatever the
table's horizon; the horizon bounds acquisition (a snapshot, a join) and
nothing else. A membership removal delivers the scope tombstone and the
device leaves the acquired rows in place; a local read of the left group
answers from them and reports completeness by the same rule it used before
the leave. A snapshot or catch-up that replaces the device's rows keeps the
retained rows of groups the viewer no longer holds. The sync card says so in
one sentence; the device regression runs on both stores. The 0.2.9
evidence: `evidence/m3-retention-probe7.txt` (25 rows `complete: false`
before removal, 0 rows `complete: true` after) against
`m3-retention-unbounded.txt` (26 and 26); the ticket is
`issues/20260914-snapback4-retained-history-with-horizon-drops-rows-on-removal.md`.

Built (lanes CU2 and CU2b). Two losses, not one. The one the builders
saw was the client: a horizon makes the device's answer unknown or
incomplete, and `local.ts` then substituted the server's answer, which for
a revoked viewer is empty and complete (the real client, before: 0 rows
`complete: true`; after: 25 rows `complete: false`, wasm and process
devices). The second was the replacement snapshot, whose `clear_rows`
dropped what it did not re-acquire. The device now keeps a held/left map
per delivered-history table: a scope tombstone marks a group left, the
first snapshot page names the viewer's current audience groups for those
tables (audience prefixes only), and a stream page names the groups joined
in it. A read that pins a left group answers from the device, and the
client never falls back to the server for it, for reads and watches. A
replacement snapshot keeps confirmed rows only for groups the viewer no
longer holds, so a deletion the device missed while away stays deleted. A
read that does not pin a group keeps its old behaviour.


**2026-09-14 — lane X1, backend store replacement.** Acquisition and the
held/left map belong to a database incarnation, not merely its schema
generation. `_meta.store_id` is a random 128-bit identity written once on
writable store open, preserved across restarts; sync replies add `store_id`
and requests accept its optional echo; change notifications add the same ID. This is additive within the package
version: requests may omit it and older replies may omit it; clients send
it only after learning it. A mismatch drops confirmed and predicted rows,
staged pages and held/left groups atomically, resets acquisition and the
watermark, reloads the backend even when its generation number matches, and
restarts the snapshot and catch-up. A first identity on a
legacy acquired device requires that same reacquisition; without an identity,
a backwards watermark is the reset signal. The stream reports its actual
head when the supplied watermark is ahead. No old partition becomes fresh
or complete during reacquisition; ordinary online query fallback may still
answer from the current server. Long-poll replies compare
store identity too, so equal-watermark replacements converge on a live client
without extra sync requests on an unchanged database.

The durable outbox keeps unsent and unknown-receipt writes, with the same
operation and row IDs and no predicted images. Known sent or acknowledged
receipts retire their entries without replay to the replacement; an unknown
receipt still retries under the existing per-store at-most-once rule. The
device's existing send revision also invalidates responses captured before
replacement, and the client serializes receipt settlement with sync. These
are internal transport facts; the public read/write card is unchanged.

**2026-09-14 — X1 review round 1.** The reset transaction also persists
`device:backend-required`, naming the replacement store (or `legacy` for
an identity-free regression). Acquisition and device reads refuse until
successful backend installation clears that obligation in the installation
transaction. Retry, an offline reopen, and a process restart retain it;
same-number generations do not excuse adoption. Installation checks its
store/send capture atomically, so a delayed adoption cannot discharge a
newer store's obligation. Each native owner also checks the persisted backend
digest before acquisition or reads: another owner's successful adoption does
not make an old in-memory interpreter current at the same generation.

A client incarnation revision advances immediately when sync or a change

remembered server answers and watch snapshots are invalidated at observation.
Every asynchronous read is fenced through return, caching and notification;
an answer from the earlier revision is retried. New reruns use the current
server until the replacement partition has completed acquisition, so the
observation cannot relabel old local data as belonging to the new revision. Sync and change replies are
fenced too. Legacy regression inference compares a reply to that request's

stale response, never permission to delete retained history.

Orphan adoption compares the persisted source and destination identities.
Foreign known receipts retire without a send; unknown and unsent entries
transfer with their IDs and no predictions. If a known receipt's ownership
cannot be resolved, it remains in the orphan store with its identity; unknown
entries may transfer, and a later observation or reopen retries the deferred
receipt. Same-store known receipts keep their acknowledgement. An orphan
whose source identity was never recorded keeps unresolved known receipts;
it cannot safely assert ownership in an identified replacement.

First identification of a legacy acquired device deliberately loses its

The Node IndexedDB tests model abort before commit and loss of the response

### 18.3 A literal default fills the column wherever it is absent; `check` reads the store

A required column with a literal default is additive at adoption: no stored
row is rewritten, no partition event is logged, and every host materializes
the default when a stored row lacks the column, as optional columns
materialize null, before rules, indexes, validation and the wire see the
row. A `default now` or `default viewer` on a new required column is
narrowing unless the table is empty, because the value is the write's, not
the row's; the successor's message says so and its rewrite names the
literal-default and optional forms. `check` opens the project's dev store
when one exists (`.snapback4/store.sqlite`, or `--store <path>`) and prints
every narrowing step of the successor as a diagnostic at the column's or
table's site, with the rewrite, and exits 1, as `dev` would refuse the
save; a green `check` then means the running store adopts. README §5
carries the schema-evolution paragraph.

### 19.1 Presence that decides only effects does not cost prediction

A mutation is eligible to predict when every value derived from
`connected[...]` reaches only `emit` statements: an `if` whose condition
reads presence and whose taken arms contain only emits, or an emit's
payload. Effects are never predicted: on a device, `emit` fills the
runner's outbox and `local::predict` drops it. So for such a mutation the
prediction is exactly the server's row writes, whatever presence says, and
the server commits its effect decisions, including deferred grace rechecks
as specified below. A
value derived from `connected[...]` that reaches a write (its existence,
key or content), a `require` or refusal, the returned value, or control
flow that contains a write keeps the `server` site and `predicts: never`,
with a reason naming the use and the rewrite "decide only the emit with
presence". A device reads everyone as connected. Queries are unchanged:
a query that reads presence runs on
the server, and the device's answer is `complete: false`. The presence,
effects and residency cards say this in one sentence each, and LLP 3000's
decision of 2026-09-13 and §6.2's site table are reconciled to it.
Dispatch-time presence (an unconditional emit plus a service mutation that
reads `connected` when a worker claims it) stays a documented pattern for
apps that want the fresher answer.

**2026-09-15 — W5g development grace.** The registry shares the development
clock used by commits: `clock advance 36s` and `POST /dev/clock/advance`
expire an ended poll's 35-second grace, while open polls remain connected.
Production grace still measures elapsed real time. There is no additional
presence flag or stream; an online device query reads the updated server
answer and a local presence read remains unknown.


**2026-09-15 — W7b deferred grace effects.** When presence decides only
a mutation's effects, evaluate those decisions using live polls. A principal
with no live poll but an unexpired grace contributes an absence dependency:
an emitted effect depending on it is durable at commit, with `next_at` at the
latest dependent grace deadline (at most 35 seconds). Ordinary presence
queries and presence deciding rows or results still count grace as connected.
An unrelated emit is immediate. Presence dependencies follow local values and
branch control, including the lowered short-circuit setup; no device presence
knowledge or predicted row changes. The existing proof that presence reaches
only effects authorizes this different effect decision, not a second execution
of application writes.

A poll authenticated for a dependent principal during the waiting window
records reconnection durably with the queued effect. At first claim, either
that record or a currently live poll satisfies the effect: state `satisfied`,
result `{ outcome: 'presence_reconnected' }`, zero worker attempts. Even a
reconnect that ended before claim, or before restart, counts. Otherwise the
effect enters the existing worker lease protocol once; its presence condition
is then consumed, so retries remain that protocol's. Multiple grace dependencies
wait for all their deadlines and a reconnect of any satisfies the effect.
A reconnect after the window that has already ended does not satisfy it.
The authenticated poll entry and effect claims serialize under the engine lock.
Development deadlines use the development clock; production converts remaining
monotone grace to a wall-clock queue deadline. Restart retains queued deadlines
and reconnect records; the process-local development offset still resets as
documented. No live poll and no grace means an immediate emit; a live poll
still prevents an absence-conditioned emit. Mutation replay cannot emit twice.

**2026-09-14 — round 1 soundness rule.** Presence-derived values may reach
an emit through total comparisons, `exists`, boolean logic and field
construction. Arithmetic, fallible or variable-cost builtins, reads,
`new` and explicit refusals dependent on presence keep `never`, with the
use named; presence-selected variable-size values keep `never` too, since
later clones could cost more in another world. Prediction evaluates both
safe arms of each presence-dependent branch, restoring the untaken arm's
locals and discarding its effects; its meter therefore pays at least the
server's work, and may conservatively refuse when the server would fit.
If an untaken arm needs a combined guard's value refinement, prediction
queues without a row; putting the data guard outside presence avoids that.
Effect ids use the commit sequence and emission ordinal, independently of
row ids. The binder records condition and payload ownership beside the
baseline flat statements, remapping only that side map through helper-return
lowering. Only presence analysis reads ownership; no grouping enters lowering,
admission or execution, retaining the original IR, statement sites and server
charges (round 2, 2026-09-14).

### 19.2 A helper's `return` never moves its caller's page

A helper is inlined per call (§18.5). A `return` inside it ends the helper
and yields its value; it does not end, reposition or reclassify an
enclosing page. The 0.2.12 calibration's history page lost `next` and read
`complete: true` when its shape called a helper that returned early
(`issues/20260914-snapback4-helper-early-return-drops-page-cursor.md`,
reproduced in 12 rows). The suspected mechanism is `Stmt::Return` assigning
the runner's page position from the plan of the return's own site.
Acceptance: the ticket's reproduction keeps its cursor on the server and
on both device stores; an early return in a `for`, an `if`/`else if` and a
nested helper inside a page's shape pages through every row without
duplicates; and no page whose continuation was lost reads `complete: true`.

**2026-09-14 — R2g completeness correction.** Loss is monotone across
executions within one query: a later execution of a scan site cannot clear
an earlier interrupted collector or an earlier continuation that no returned
owner carries. The returned owner keeps the existing last-execution rule for
`next`; that cursor never acquires ownership of an earlier execution. An
exhausted execution needs no cursor owner. The same rule applies to plain,
matching and merged pages on the server and both device stores.

An exiting loop counts as a collector only when its writes flow to a returned
value, through aliases, records or enclosing loops. Traversing an intact
returned page for an auxiliary calculation does not interrupt that page,
even if the traversal breaks; a separate returned collector built from that
same page can still lose rows. The ordinary meter, rules and horizon continue
to determine the other reasons a query is incomplete.

**2026-09-14 — the third review round, settled by the lead.** A `return`
inside a loop exits every enclosing loop with the result, so each enclosing
loop is a collector even when no write precedes the return
(`for i in items[] after c last 5 by byN: return [i]` over four rows now reads
`complete: false`; it read `complete: true` after R2g). The flow analysis only
removes a registration for a loop it visited and proved auxiliary; a loop it
never reached (inside a merge lane's setup or an expression block) stays
registered. A page that never executes because an earlier return or break
left its enclosing loop lost nothing: its rows were never read. One
conservative case remains and is accepted: when the same scan site runs
again after its earlier interrupted output was discarded (an accumulator
reset between iterations), the earlier loss still holds, so a result that
re-collected the whole page reads `complete: false`. The error is always
toward `complete: false`, never toward a lost page reading complete;
distinguishing a discarded execution would need per-value provenance, which
this landing does not build.

### 20.4 A queued web write survives navigation (S29)

On the web, admission waits for the outbox's IndexedDB commit. `pagehide`
or becoming hidden sends the oldest durable unconfirmed write with an
authenticated keepalive request, including a retry of that same head when
an ordinary send is in flight. A blocked or oversized head is never skipped;
requests across clients share the browser's **64 KiB body budget**. Unsent
or unconfirmed writes stay durable for retry on reopen with the same mutation
ID, so replay cannot apply a write twice. If the exit response has not finished
after **one second**, ordinary flushing retries the same durable head before
advancing. `close()` stops waiting immediately without cancelling keepalive.

Admission that finishes while the page is suspended rechecks exit transport
after its commit. On reopen, a matching server store identity and
non-regressed head allow unknown writes to replay before the first sync
finishes; §18.2's replacement and restore rules still apply.

**2026-09-15 — W4a, synchronous pre-admission journal.** Before `mutate`
returns its promise, a web host holding its exclusive Web Lock captures the
mutation id, operation, arguments, minted row ids and submission order in
localStorage. That synchronous store survives same-origin navigation; no network request exposes an unadmitted write.
On open, its records enter the existing IDB outbox in order before new writes.
A failed admission save leaves the record recoverable before a surviving page's
next admission too. A closed tab's records use the existing Web Lock and orphan
adoption rule: the next device opening the store adopts them, never a live tab's.
Recovery and ordinary admission allocate queued submission numbers from the same
device counter in the serialized host chain, including recovery deferred until
backend adoption. Capture order also advances past the journal already held.
Already-queued primary writes precede recovered orphan records.

Under the orphan's lock, a matching healthy destination installs its authenticated
backend before recovering records left behind `backend_required`. An orphan with
no kept backend or store identity is skipped, leaving its journal intact for a
later matching open; no identity is guessed from its journal key. Malformed or
unusable orphans are isolated so healthy stores still open, and one malformed
journal key cannot hide other tabs. A failed destination commit still discards
its uncommitted VM. Skipping neither loses a record nor makes it executable: the
usual identity fence and transfer acknowledgement must succeed on a later open.

An IDB transfer marker shares the admission transaction and suppresses duplicate
admission by mutation id against queued writes and receipts, including after a
receipt leaves the outbox while localStorage removal is failing. It contains no
server result or terminal settlement. Successful transfer removes the synchronous
record; acknowledged markers are collected when that removal succeeds. A
write-specific prediction or validation refusal keeps the ordinary failed outcome
even if bookkeeping fails. It removes the journal record, replaces it with a
non-executable cancellation, or acknowledges it in IDB. If neither store can
persist cancellation, recovery is indeterminate: an executable record may remain
and later be admitted if the authored condition changes. A returned refusal does
not promise preserved cancellation when both stores fail. Original arguments
and minted ids survive recovery. Sends remain exclusively the outbox's, in its existing order, with the
original mutation id; there is no new exit ordering or settlement path.

Recovered, previously unadmitted records keep their source backend store identity
until they leave the outbox. An identity mismatch retires them without sending
them to the replacement, including after an offline reopen and orphan adoption.
This is stricter than §18.2's treatment of ordinary already-admitted unknown
writes, which is unchanged. Same-store restore refusal still halts sending.

The journal is bounded to **32 records and 256 KiB** of UTF-8 keys and values
per device store, and **64 KiB per serialized record**. Unavailable, throwing or
full localStorage, missing Web Locks, an unidentified backend, exceeded bounds, or
browser storage clearing leave that write's unawaited navigation **best-effort**:
the write can still be lost before IDB commits. A journal-only write needs another client to
open before it can be admitted and sent. Keepalive remains best-effort and sends
only admitted writes. These are navigation/reopen guarantees, not a claim about
physical power loss. Without Web Locks the host neither captures nor recovers
journal records; ordinary IDB admission remains available. For programmatic
navigation, `await client.mutate(...)` remains the strongest durable boundary; handle `failed` before leaving.
`pending` means IDB admission is durable and the server outcome is unconfirmed.
The writes card and README state these limits.

The Node model covers same-turn teardown and an unresolved admission save, one
and two writes, original row ids, order and at-most-once application, stale
journals with queued and retired receipts, refusal, storage failure and bounds,
closed/live tabs, and store replacement. W4R1a adds deferred backend recovery
followed by an offline successor (ABC), backend-required and unusable orphans,
independent cancellation-store failures, absent Web Locks, malformed-key
discovery, queued-primary-before-orphan order, and an unidentified backend.
The lead's real Chromium run of
`witness/navigation-immediate.mjs` (chromium-1243, outside the sandbox) passes
**10 of 10**, against the **8 of 10** residual at 0.2.19 recorded in §20.12;
both unawaited zero-delay cases apply exactly once.

### 20.5 `upsert` predicts its insert when absence is provable (ruling 19; S20)

On a device, `upsert t[key] { … }` whose target the device does not hold
predicts the insert arm when two conditions both hold:
- **(a) The group is held with no horizon.** `t` is synced, and the key's
  group has no horizon, so the device holds every row of that group this
  viewer may read.
- **(b) The key decides readability.** The key determines readability, so no
  row hidden from this viewer can exist at that key. Examples: a read rule
  `public`, or `.col = viewer` with `col` in the key.

Otherwise the device queues without a row, as §8.7 (e) requires, and never
predicts `NOT_FOUND` or an insert for an unheld target. `check --residency`
and `why <op>` say which applies; the prediction card states the rule. Likes
and reactions keyed by `(post, viewer)` predict their first write offline.

### 20.6 A read rule may name a service principal (ruling 20; S35)

A read rule may carry disjuncts `viewer = 'service:<name>'` beside its
audience rule. Services hold no partition, and the `service:` namespace is
reserved, so the sync audience is inferred from the rule with those
disjuncts removed; no device's partition changes. `check --residency` lists
the service grants. A second disjunct that is not a service principal is
still refused.

### 20.7 A public table may sync a subset to each device (ruling 21; S16)

A table whose read rule is `public` may declare a `sync` audience narrower
than the read rule (`sync to .followerId`, or an audience through another
table). A device then holds a subset of what its viewer may read. A read the
subset cannot decide is server-class, like a read past a horizon:
`complete: false` on the device, answered by the server online. A write to a
row inside the subset predicts as usual. `NOT-DOING.md` records the move in
the same change. The public-audience half of the exact-audience invariant
("never misses one it may") is given up deliberately for these tables; the
other half ("never holds a row it may not read") stands. The work lands
after wave 2.

### 20.8 The darwin binary is signed with Developer ID (ruling 22; S31)

It notarizes when a notarytool keychain profile is configured; otherwise it

#### 20.9.2 One grammar, and its row shape

Proposed grammar below uses the existing Quarry lexical classes,
indentation, rule grammar and page grammar. `Name` may be module-qualified
where table names already may; `Column` and generated field names are local.
There is one `read` property, at most one `online only`, and any number of
distinct named indexes. No implicit filter alias or second group spelling.

```ebnf
Maintain    = Head NEWLINE INDENT Property+ DEDENT ;
Head        = "maintain" Name ":" ("count" Name | "sum" Name "of" Column)
              ["where" Predicate] "by" GroupKey {"," GroupKey} ;
Property    = "read" "<-" Rule NEWLINE | "online" "only" NEWLINE
            | "by" Column ":" Column {"," Column} NEWLINE ;
GroupKey    = Column | ("day" | "hour") "(" "." Column ["," Duration] ")"
            | "bucket" "(" "." Column "," Duration ["," Duration] ")" ;
Predicate   = Or ;
Or          = And {"or" And} ;
And         = Not {"and" Not} ;
Not         = "not" Not | "(" Predicate ")" | BoolLiteral | "." BoolColumn
            | Operand Compare Operand ;
Operand     = "." Column | ScalarLiteral ;
Compare     = "=" | "!=" | "<" | "<=" | ">" | ">=" ;
```

Only total, typed scalar comparisons enter a maintain predicate. Equality
and inequality admit null as the value model already does; ordered
comparisons require non-optional, comparable operands. A bare boolean column
must be non-optional. No row reads, `exists`, helpers, parameters, `viewer`,
`now`, arithmetic, JSON access or effect can occur here. Ordinary query
`where` keeps its broader grammar (§5.6); a maintain is evaluated without a
viewer and must remain correct when another table changes. This restriction
is checked at the offending expression, with a rewrite naming a stored
source field or the existing bounded job recipe.

**(a) Filter the contribution.** Examples in the proposed language:

```quarry
maintain originalPostCounts: count posts where .kind = 'original' by authorId
  read <- allow
maintain authorPosts: count posts where .parentId = null by authorId
  read <- allow
maintain visibleMessages: count messages where not .tombstone by conversationId
  read <- exists members[.conversationId, viewer]
```

The first is the brief's illustrative schema: `kind` distinguishes original
posts there. In the actual L12 schema `kind` is text/images/video and
`parentId = null` distinguishes originals; the second is its replacement
for `sum posts of original`. A filter also applies to `sum` with the same
typed contribution as today. It never changes the source's read rule.

**(b) Compute a key, without storing it on every source row.** Admit `day`,
`hour`, and, because the run actually uses two-minute digest periods,
`bucket` with a positive literal duration. Omit `week`: no M8 consumer needs
a week boundary, and there is no locale/ISO-week policy to invent here.

```quarry
maintain dailyPosts: count posts where .parentId = null by authorId, day(.at)
  read <- .authorId = viewer
  online only
maintain hourlyMessages: count messages where not .tombstone by conversationId, hour(.at)
  read <- exists members[.conversationId, viewer]
maintain periodPosts: count posts where .parentId = null by authorId, bucket(.at, 2m)
  read <- allow
  online only
```

Each accepts a required `time` column, interpreted with its literal default
under §18.3. Output is an `int` ordinal: respectively
`floor(at / 86400000)`, `floor(at / 3600000)`, and
`floor(at / literal-duration-ms)`. Epoch is Unix UTC. Floor division is
Euclidean for negative timestamps: `day(-1 ms) = -1`, not zero. The output
fits the existing integer range for every admitted time value; no flooring
back to a millisecond timestamp can overflow at the negative endpoint.
Zero, negative and unrepresentable durations fail binding. No local timezone,
DST, wall clock or locale affects the key. Function,
input column, duration and literal offset participate in schema identity; a semantic change
rebuilds the maintain. The same functions are ordinary scalar builtins for
query arguments, so a daily scalar lookup uses `dailyPosts[viewer, day(now)]`.

**2026-09-15 — W5g calendar anchors (G7).** `day(time, 8h)`,
`hour(time, 30m)` and `bucket(time, 1d, 8h)` accept an optional literal
nonnegative offset strictly smaller than their period, in maintain keys and
ordinary expressions. The ordinal is `floor((time - offset) / period)`;
08:00 UTC starts the new day in the first and third examples. The same
integer key encoding and value forms apply on the server and both device
stores. A zero offset is omitted from serialized computed-key metadata;
old calendar calls keep their one-argument builtin IR, and nonzero offsets
use its existing argument list. Changing an offset rebuilds the maintain
without rewriting source rows. No local timezone or daylight-saving policy
is introduced, and join attribution remains a stored source field.

Computed columns on the target are named `day`, `hour` and `bucket`; bare
keys keep their source column names. Duplicate output names, including two
`day` calls or collision with `id`/`value`, are refused, never auto-renamed.
The target remains `{ id, <group columns>, value }`, with the canonical
ordered tuple as its existing maintained id. No value-model serialization
changes. `dailyPosts[viewer, day(now)]` is a scalar, zero for an absent group;
seven explicit scalar lookups still give seven days, including empty days.
An enumerated page lists existing groups only; it does not invent empty days.

**(c) Read a group as a bounded set.** An explicit page operator selects
row mode, using the existing `first`/`last`, `after`, index and shape syntax:

```ebnf
MaintainPage = Name ["[" PrefixArguments "]"] ["after" Expression]
               ("first" | "last") PositiveInteger "by" Column [Shape] ;
```

Without a page operator a maintain lookup requires its whole group key and
returns the scalar; a short key alone is a diagnostic, not an overloaded
array/scalar result. `byGroup` is generated over the complete group tuple.
An explicit page may pin any leading prefix, or scan globally with none.

```quarry
maintain reactionCounts: count reactions by messageId, emoji
  read <- allow
query chips(messageId: messages):
  return reactionCounts[messageId] first 50 by byGroup { emoji, count: .value }

maintain roomReactionCounts: count reactions by conversationId, messageId, emoji
  read <- exists members[.conversationId, viewer]
query roomChips(conversationId: conversations, messageId: messages):
  return roomReactionCounts[conversationId, messageId] first 50 by byGroup { emoji, count: .value }
```

The first needs a public source to inherit public sync. The second is L12's
membership audience and retains `conversationId` in the key; grouping by
`messageId` alone does not prove a conversation audience through a foreign
key. L12 already caps reactions at 50 per `(conversationId, messageId)`, so
there are at most 50 nonempty emoji groups. The binder propagates this
source cap as a bound on distinct target rows under that prefix; it adds no
runtime target cap and rejects no 51st distinct group independently of the
source constraint. Where no source cap proves the bound, `first 50` is just
a page: overflow has the ordinary cursor/completeness result. A finite enum
can also prove a distinct-key bound. The engine never silently truncates
chips and calls the set complete. Individual reactor lists and the viewer's
own reaction remain reads of `reactions` under its rule.
An expiring source's cap bounds live rows, not unswept physical candidates;
that proof never exempts its live group read from the meter.

**(d) Order by the maintained value.** Admit ordinary non-unique indexes on
target group fields, `value` and `id`, declared with the existing `by` line.
A value-order index consists of zero or more distinct group fields, `value`,
then `id`; its prefix determines a scoped ranking. No computed score or
cross-table order expression enters it. Other plain group indexes keep the
ordinary index rules. Examples:

```quarry
maintain postLikes: count likes by postId
  read <- allow
  by byCount: value, id
query mostLiked():
  return postLikes last 10 by byCount { postId, count: .value }

maintain authorPostLikes: count likes by authorId, postId
  read <- allow
  by byAuthorCount: authorId, value, id
query authorLeaders(authorId: principal):
  return authorPostLikes[authorId] last 10 by byAuthorCount { postId, count: .value }

maintain authorLikes: count likes by authorId
  read <- allow
  by byCount: value, id
query mostLikedAuthors():
  return authorLikes last 10 by byCount { authorId, count: .value }
```

`last` returns descending value and then descending canonical group id,
using the existing total key order on both stores. Ordinary cursors bind
the index, prefix and generation. Concurrent score changes can move rows
between pages, as with any mutable index; this is not a snapshot ranking.
Only existing nonzero groups participate (the existing zero-sum expiry
candidate exception is discussed below). Unliked posts do not acquire a
zero row just because `posts` contains them. `authorId` must still be a
validated field of `likes`; there is no automatic post-author join or
cascade when that attribution changes.

| Choice | Work and state | Decision |
| --- | --- | --- |
| Index every maintained value | Existing target rows and index insertion/removal; any N and prefix use the ordinary page reader | Recommend: the engine already maintains these indexes; only their authoring and row reads are missing |
| `maintain top N` | Must recover the next candidate after a winner decreases, moves or disappears; either keep the full value index anyway or rescan the losing groups; also needs membership transitions for each N | Do not add: an extra materialization and lifecycle for the same ordered read |

This ranks a maintained number, not relevance. It deliberately does not
claim to replace all of L12's Trending table: “original post created within
the last 24 hours, ordered by total likes, including zero-like posts” needs
post eligibility and time as well as a likes group. A query-time filter of
the first ten ranked groups is not its top ten. The exact existing
`ranked`/expiry recipe and LLP 3000.004's scheduled scoring remain the
forms for that request. A UTC-day group is not a rolling 24-hour window.

#### 20.9.3 Transactions, expiry, residency and disclosure

For an interpreted source image define its contribution as either absent
(predicate false), or `(computed tuple, count 1 / sum column)`. Insert adds
the new contribution; delete subtracts the old; update subtracts old and
adds new, coalescing equal keys before applying the result. False→false
writes no target row. False→true, true→false, and true→true with a changed
key have respectively one, one, and at most two affected groups. A change
to an unrelated field with the same contribution produces no target event.
Defaults are interpreted identically in ordinary writes, adoption, expiry,
sync and device execution. The source, target rows, value indexes and
partition events commit or roll back together. Replay applies once. A
target stays engine-owned; direct writes are refused.

Maintain totals use the current wide intermediate arithmetic and final
integer/decimal/money range check. A zero count removes its row; a zero sum
keeps today's semantics. Overflow refuses the source transaction with the
existing value-free maintain/column diagnostic. Maintains of maintains,
joins and custom reducers do not enter this design.

**Expiry is a live read, not a delayed truth.** Keep the physical
contribution until the server removes its source, so the sweep subtracts
it once. At a pinned read time, filter, key and sum are recomputed from
live source images; expired sources contribute nothing even before a
sweep. A physical zero-sum candidate must remain while any selected
physical source remains: +1 and −1 may expire separately. The same
predicate/key evaluator must serve writes, live reads, existence probes
and rebuilds. Changing a filter must not leave a stale expiry candidate.

For new computed keys on an expiring source, build an internal contribution
index `(computed group tuple, source id)` for selected physical rows. Reuse
it for live recomputation, candidate existence and the zero-sum test; do
not fall back to a source-wide scan per group. Its entries and backfill are
metered and included in adoption. It is internal index state, not a new
table on the card. Live scans can still hit the meter on a large group;
partial contributions have `complete: false` and preserve the source
dependency/next-expiry invalidation. Existence-only rule probes retain the
one-unit observable charge; the physical work remains visible to operator
measurement. Value comparisons in rules over expiring maintains remain
refused under `E_QUARRY_LIVE_MAINTAIN_PROBE`.

**Refuse a value-order index over an expiring source in this slice.** Its
stored ordering can become wrong without a commit, including sums rising
when negative contributions expire. Rechecking only the ten winners cannot
find the missing winner. `check` names the source and rewrites to a live
bounded query or the scheduled ranked-table recipe; the implementation must
register the diagnostic on the expiry card. No sweep-lag assumption and no
exact time horizon maintenance are introduced to make the index look exact.

| Situation | Read and prediction contract |
| --- | --- |
| Source syncs, all audience columns survive as bare group keys | Inherit the resolved audience and **no target horizon**, as today; filtered rows reveal no new audience. Non-expiring maintained scalars and pages are `held`, even when source acquisition has a horizon |
| Public source, many groups | All inherited target rows reach every device; ranking `last 10` does not replicate only ten. `N_MAINTAIN_SYNCED` and measured residency show that cost |
| `online only`, or a source audience column is lost | Target is `server`; no automatic public projection of private votes. Queries and mutations reading it follow §6's server/queue-without-a-row contract |
| Predict a source change | Eligible only when ordinary source authority/old-image/absence checks and the affected aggregate base are locally decidable. A new eligible count, computed bucket, chip and index move use the same Rust contribution code. No rebuild from the device's partial source history |
| Expiring source not fully held | A live aggregate cannot trust its stored total; recompute held contributions and remain incomplete. A mutation depending on that live answer queues without a row |
| Source retained after leave | Preserve §18.2 for source history. Today a maintain inherits sync, not the source's `retain delivered-history`; its generated target defaults to until-revoked. Keep that rule in this slice, disclose it on the maintains/sync cards, and do not present a retained source page's length as its former total |
| Public source with subset sync under §20.7 | Do not infer that an aggregate over all public sources is complete inside a narrower delivery subset. Inherit only a statically source-complete group; otherwise classify the target read as server/unknown locally |

Merely maintaining an online-only target as an engine side effect must not
turn an otherwise predictable source mutation into a server mutation; the
device omits that target's overlay. Explicitly reading it, or writing an
online-only application table such as L12's `ranked`, does. An inherited
target with a locally unknown old value must never be initialized from zero
as if absence were proved. §20.5's separate upsert ruling governs an absent
application source row; this section does not bypass it.

**A filtered count can reveal a hidden field.** If a writer can change one
hidden row and read its count of `.kind = 'original'`, the before/after
delta reveals whether that predicate held. Computed keys reveal bucket
membership; rank exposes relative values. These are the declared aggregate
read channels of §8.7(g), not anonymization. Extend `N_MAINTAIN_DELTA` to
name filter/key dependencies and the readable target, conservatively when
source visibility is not proved for its aggregate audience, including
insert/delete channels. Keep the existing wider-update note. Recommend a
filtered example on `guide rules` that explains the disclosure and a
restrictive-read example that closes it. Inherited sync still requires
the source audience proof; an online-only aggregate's own read rule can
deliberately grant the channel. The filter grants no source-row read.

When the aggregate itself is hidden, filter-dependent work must not add a
new success/`E_BOUND` oracle on hidden-target writes. Extend the existing
schema-derived write-attempt reservation to the new predicate/key work,
up to two aggregate groups and their indexes, with heap based on declared
types; reserve before inspecting the hidden old image. Denied aggregate
reads keep the uniform-prefix/point-miss behavior, value-free errors,
dependency tables and replay withholding of §17. Paired worlds must test
this, not just compare returned counts. Existing §8 residual constraint
channels are not claimed solved. In particular, a filtered/keyed maintained
sum at an integer endpoint can refuse an admitted hidden write with
`E_OVERFLOW` when the hidden predicate holds and commit when it does not,
even if the aggregate's read rule denies the writer. The reservation bounds
work, not the stored sum. This is the constraint-outcome residual of §8/§17;
the refusal remains value-free and the failing transaction rolls back.
There is no paired-world success/error equality claim for overflow.

**Meter:** charge predicate nodes and key evaluation to steps, group/target
lookups to examined, actual index work (including contribution indexes) to
index entries, and each changed target row to rows written, alongside the
source charge. Reserve transient rows, keys and buffers before allocation;
release temporary heap when done. Group pages pay normal examined, rule,
heap and output charges. A value index does not scan the sources. Backfill
pays the same work under job ceilings per chunk, including excluded rows'
examined and predicate work. Hidden attempts use the conservative
reservation instead of a secret-dependent charge, never both. No ceiling
in `meter.rs` moves.

#### 20.9.4 Adoption owns the backfill

At base `56cdedba6a8ff343c8d297b246b7431824ef0241`,
`engine/write.rs::rebuild_maintain` scans in pages of 256 but holds all group
totals in a `BTreeMap`; `engine/mod.rs::activate` supplies
`Ceilings::unbounded()`. `store/activation.rs` publishes everything in one
SQLite transaction. Neither a page loop nor that transaction is a durable
continuation. The successor classifier does not yet describe filter/key
changes. Reuse its generation identity, interpreted images, constraint
validation and single publication boundary; add resumable preparation,
rather than describing the current rebuild as bounded.

Recommended first implementation, subject to the availability ruling below:

1. Classify a new maintain or changed filter, key function/duration, source
   default dependency or aggregate expression as a derived rebuild. A changed
   index alone rebuilds its index; a changed audience re-derives delivery.
   Report each step at its declaration. A source rename is still drop/add.
2. Acquire a durable store-wide write fence at the predecessor generation
   and sequence. Finish the current writer first. All application writers,
   jobs, seeds and expiry sweeps honor it; other processes cannot bypass it.
   Old-generation reads and logical expiry continue. A write not yet
   executed receives a retryable store-availability response and stays
   queued; it must not acquire an at-most-once failure receipt. Use a
   specific registered `E_ADOPT_BUSY` message, “schema adoption is preparing
   derived rows; retry this write with the same id”, family `store`.
3. Allocate candidate catalog identities, never reuse the live target's
   rows. Scan source by stable id into shadow target/contribution indexes
   in job-metered transactions, with a small page buffer and disk-backed
   per-group wide accumulators. Persist the candidate hash, predecessor
   generation/sequence, phase, source and last committed id with each
   chunk. Row contributions and cursor commit together. Do not keep an
   all-groups map or generate one huge partition event list.
4. Start with at most 256 sources a chunk, but stop before the next complete
   source's reserved work would exceed a job ceiling; commit the completed
   prefix. If one source and all its affected maintains cannot fit an empty
   chunk, refuse/park `E_BOUND` with the declaration and dimension, not a
   larger ceiling. Finalize wide sums and validate target rows/indexes in
   separate bounded phases. Do not reject a temporary out-of-range sum
   that cancels into range by the end of its group.
5. Recheck the predecessor identity under the publication transaction and
   swap candidate catalog mappings, backend and generation atomically.
   Devices use the existing generation replacement/acquisition protocol;
   they never observe a partially built maintain. Do not stream a single
   enormous rebuild commit. Obsolete internal rows are reclaimed in bounded
   cleanup chunks. Unchanged retained tables keep §18.2's handling.
6. On crash, recover the fence before accepting writers and resume the same
   candidate from its committed cursor. On overflow, invalid data or an
   unfit single source, cancel candidate publication, release the fence
   atomically and keep the old generation available; retain the private
   failure for `dev` to explain, then clean up. A cancelled fence invalidates
   its candidate for reuse because writes may resume. A different saved
   candidate invalidates the old preparation. No generic jobs framework,
   dual-write protocol or application backfill job is added.

Physical expired source rows belong to the same unswept contribution ledger
as ordinary writes; candidate live reads exclude them at read time. A clock
tick during preparation therefore needs no new time snapshot. Any legacy
expiry-candidate repair that this maintain needs joins the bounded phases,
not an unbounded follow-up inside publication. Mixed source projections,
constraints and index changes must also prepare before publication, or be
refused as an unsupported combined adoption; the old all-table activation
walk cannot remain hidden inside the final short transaction.

**`check` against the dev store.** Keep §18.3's read-only source/store
assessment and its unreadable-store exit 2. Show source rows to examine,
affected maintains/indexes, the job ceilings, and whether data assessment
finished; zero source-row rewrites are needed for these new derived forms.
Count scans are measurements of that store, not estimates of target groups.
An exact group count requires actually evaluating the keys. A full successful
assessment says “adopts after derived backfill”; it does not say the new rows
already exist. Invalid data or an overflowing final group gives the same
`E_ADOPT` in `check` and adoption with the maintain's location and rewrite.
No source with no store is presented as a populated-store assessment.

Large data-dependent assessments need a ruling against the one-second
`check` budget: recommend a bounded read-only assessment, exit 2 with
“derived backfill assessment incomplete; dev will prepare it in bounded
chunks” when it cannot finish. Never green on partial assessment, and no
mutation of the dev store to finish `check`. `dev` does the durable work
above and can still refuse it. This preserves “green implies the assessed
store fits” while making incomplete assessment an explicit third outcome.
The status wording/exit is proposed, not today's behavior; §18.3 must be
reconciled when the author rules. Structural resource certification is not
added: runtime meters still decide whether each chunk fits.

#### 20.9.5 Measurements and the implementation experiment

The opt-in measurement is
[`maintain_measurement.rs`](../snapback4/crates/snapback4-sim/tests/maintain_measurement.rs).
It uses the existing engine at the base above, debug profile, SQLite
`:memory:`, no sync or network, 1,000 groups, 50,000 post-shaped rows,
100,000 message-shaped rows, and a separate 100,000-row reaction workload.
Rows contain fixed small fields; they are not the full Clique fixture.
The reaction workload has 50,000 item ids and 100,000 distinct
`(groupId, itemId, emoji)` groups; it is a high-cardinality stress case, not
a claim about the measured run's reaction distribution. All ceilings remain
unchanged. Each mode seeds its own store, then measures adoption once and
200 inserts, 200 key/filter moves and 200 deletes. Timing is N=1 on the
shared loaded host, partly alongside the blocking suite; no disk durability,
replication or production latency claim follows.

`filter_proxy` is the shipped sum of a stored 0/1 flag, true on 75% of seed
rows; `key_proxy` adds a stored day ordinal. They measure current target-row
work, **not** proposed predicate/function execution. `chips` is the shipped
multi-column count. `rank_index` adds one plain `(value, id)` index to the
compiled target schema inside the test only, proving which existing engine
path can carry the proposal. It does not implement a new parser or reader.
The journal records exact measured numbers and the command transcript.

Measured adoption: count/filter-proxy/key-proxy took respectively
2,337.643 / 2,360.927 / 4,716.384 ms over 50,000 posts and
4,967.736 / 5,272.848 / 9,678.313 ms over 100,000 messages. The computed-key
proxy produced 37,500 / 75,000 target rows; simple counts produced 1,000.
The 100,000-group chip control took 12,757.363 ms to adopt; adding the value
index took 12,120.141 ms in its separate trial. That reversal is noise,
not evidence that an extra index speeds adoption. Chip insert/move/delete
p50 were 145.500 / 211.000 / 94.625 µs; with the value index,
158.917 / 227.125 / 96.333 µs. The final samples charged respectively
4/6/4 index entries versus 5/8/5, and 2/3/2 total rows written in both.
These moves delete and create groups; in-place numeric rank changes remain
in the implementation measurement plan. Existing meters do not charge
every internal aggregate lookup/allocation, so their printed totals are
observations of the base, not certification of the new evaluator.

Before claiming the implementation at the envelope, extend this measurement
with the real accepted forms, holding source/index/rule layout constant:

- Paired 0%, 50% and 100% filters; unrelated update, filter entry/exit,
  key move, last-source delete, and ranked winner decrease. Report all

  Distinguish target index removal+insertion from a source row update.

  rows/bytes acquired by a representative 50-member room and public reader,
  extra database/index bytes, peak temporary heap, total adoption time,
  worst chunk time, publication pause and durable chunk count. Use native
  SQLite on disk and both device stores, not only this memory control.

#### 20.9.6 What stays out, and concrete acceptance

No arbitrary maintain expressions, cross-table joins, exact rolling-window
ranking, rank-by-relevance, time decay between commits, custom calendar,
empty-group synthesis, exact horizon eviction/refill, app SQL query surface,
JavaScript reducer, recursively maintained table, new jobs framework, meter
raise, value-model change or second language. Existing corpus cases stay
unchanged. These forms stay small enough for the card; README examples,
all cards and affected callers change only with their parser/runtime.

**S26 is only partly answered by buckets.** A digest can read per-author
period posts and per-author follower buckets without scanning their events.
“Unread since a member's moving read watermark, excluding their own and
tombstoned messages” depends on another row and cannot be a row-local
maintain predicate. The implementation must carry the existing bounded
receipt/unread-counter recipe or an application continuation keyed by
`(recipient, period, stage, room, source cursor)` across job chunks. Commit
partial totals and cursor together; emit and dedupe only after all rooms
finish. A heavy user spanning several chunks must finish or park with a
named refusal, never emit a capped total as exact. There is no claim here
that one user per chunk becomes safe, or that an arbitrary anchored digest
is a UTC-day bucket. A two-minute epoch-anchored period is supported by
`bucket(.at, 2m)`; another origin still needs an explicit source field.

### 20.10 A published simulator witness (S30)

**2026-09-14 — lane W1, commissioned by the author.** The native witness
capability is an app-builder surface: `snapback4 witness ios` in the binary,
`snapback4-expo/witness` in the Expo package. It replaces the repository-only
Metro witness. The deterministic simulator remains the primary harness;
this tool covers installed native process, durable storage and visible UI
boundaries that the deterministic engine harness cannot reach.

The driver builds nothing. It selects a booted iOS simulator by explicit
UDID, or requires exactly one available booted iOS simulator, verifies the
installed app and its Info.plist, and starts its own `dev --no-watch` in the
project. An already bound port is refused. `--prime` launches the app online
with segment `prime` until `primed`, then terminates it. The driver stops
its backend, verifies TCP connection refusal, starts video and device logs,
and launches the app cold with the requested segment. For `--relaunch` it
waits for `relaunch`, terminates the app, then relaunches the same segment
still offline. After `offline-done`, it restarts the same command on the
same port and project store, signals reconnect, and waits for `done`.
Each wait defaults to 120 seconds (`--timeout` overrides it). Only child
processes it started are signaled; every simulator command names its UDID.
An already running app is refused with `E_WITNESS_APP` and an instruction to
quit it; termination targets only the PID reported by the driver's launch,
leaving a replacement instance running.

The protocol is run-specific container files. The driver passes JSON in
`SIMCTL_CHILD_SNAPBACK4_WITNESS`; the native bridge reads the resulting
process environment only on an iOS simulator. Hermes cannot read runtime
launch environment through Expo's build-time `process.env` replacement, so
the bridge adds that constant and two small file operations. The helper
returns null without this environment, including ordinary subsequent
launches with old witness files still present. JavaScript owns the rest:
`segment`, sequential `step(name, fn)`, `receipt(object)` and
`waitFor(label)`. A successful step appends an empty application object
with `witness: { at, step }`; receipts inside its function use
`step: "name:running"`, and a thrown assertion emits `name:failed` and
rethrows. No application field is changed; the `witness` key is reserved.
Receipt append is synchronized to the Documents file before returning.
`waitFor('reconnect')` polls a file the driver creates only after its
restarted backend announces readiness. Files work without simulator network
entitlements or a separate control server. App assertions decide which
history, media, search, pending, settlement or recipient states to record.

The driver finalizes video before stopping logs, terminates the launched
app, copies the JSONL from its data container, and writes the run manifest
with installed build identifiers, simulator/runtime, backend command,
origin/port, millisecond start/end and lifecycle events, byte sizes, SHA-256
of video and receipts, and exit status. Missing/empty artifacts, malformed
JSON lines, failed or out-of-order steps, timeouts, and backend stop/restart
failures are coded, nonzero exits. A failed run retains available evidence
and a failed manifest; a retry cannot overwrite it. The reference wrapper
runs the published verb for both cold-offline and durable-relaunch scenarios,
and its chat app uses the published helper without a gated fetch or simulated
client reopen.

The manifest binds artifacts, not assertion truth. This does not establish
physical-device behavior, loss of every network path, read-receipt delivery,
media retention, search or view-once exclusion without the app's own asserted
and rendered observations. A mocked-simctl test is driver evidence only;
a Release app run on an actual dedicated simulator is the native witness.

**2026-09-14 — native runs and the ownership residual (lead).** The iOS
simulator runtime has no `kill`: the driver confirms through `launchctl list`
