## Summary

The author, after building Clique on Snapback: *Quarry seems great except
too constraining. Its biggest value is describing data that is synced
locally and in the cloud and queried with one language. If you don't need
that, something like Convex or Supabase — more flexible, even if you lose
some nice properties — is probably easier for agents.* He asked for the
thesis to be analysed and, if it holds, for a more relaxed way to use
Snapback 4 where local data is not needed, or relaxed across other seams,
that makes it ergonomic for agents and lets the Clique benchmark run
smoothly.

The thesis is half right, and the half that is right points somewhere
more specific than "relax when offline is not needed."

**Right:** the constraints that cost builders time are constraints on the
*program* — a local binds once, no accumulators, no `continue`, no `else
if`, no `where`, no text `+`, no `/` — and every one of them is an
inheritance from Snapback 2's static byte-and-step pricing, not a
requirement of running on a device. LLP 2000.000 §4.1 said so when it
flipped the bound model: *"Decide the bound model, keep the language, and
re-derive its restrictions."* Snapback 4 copied the binder and never
re-derived them. The evidence that they are not device constraints is in
the code: the IR carries `Assign`, `Push`, `Continue` and `Concat`, the
interpreter — one implementation on the server, in the wasm and in the
native module — runs them today, and only the binder refuses them.

**Not right:** the value that survives without local sync is larger than
"nice properties." Declarative rules that are the audience, typed
refusals with rewrites, the runtime meter, identity, typed assets with a
lifecycle, expiry, jobs on the server's clock and a process that embeds
no JavaScript are why the same builder was faster than Convex on five of
seven Clique milestones in the 0.2.6 run and why authorization is the
dimension Snapback wins. Those do not depend on `sync`. And the places
Snapback 4 lost time in the newest run — messaging's client lifecycle,
a prediction that silently stopped predicting, a mutation whose result
the client dropped — are seams, not the language.

So the proposal is not a second, looser language for online-only apps.
It is: **one language, relaxed once for every host, under the meter that
already bounds it; residency and execution made legible instead of
inferred at runtime; the online-only mode paved as a first-class choice;
five client seams closed; and two escape hatches specified for the last
ten percent, to be ruled on after a rerun.** §10 maps every correction
loop the four Clique lanes recorded to the item that removes it.

## 1. The question

> What I've noticed from using Snapback to build Clique is that Quarry
> seems great except too constraining. The biggest value it gives us is
> that it can describe data that is synced locally and in the cloud and
> queried with one language. If you don't need that, then it seems like
> something like Convex or possibly Supabase — just more flexible, even
> if you lose some nice properties — are probably easier for agents to
> deal with. Can you analyze this line of thinking, decide if you agree
> with it, and if so, design a way to use Snapback 4 in a more relaxed
> way for cases where you don't need the data to be available locally /
> offline, or more relaxed across other seams, that would make it more
> ergonomic and usable by agents and make it sail through the Clique
> benchmark totally smoothly.

## 3. Analysis

### 3.1 Quarry's constraints come from four sources, and only one is the device

| Source | Constraints it explains | Needed when |
| --- | --- | --- |
| **D — device execution and prediction.** A program may run on a device over the rows it holds and predict a mutation before the server judges it | reads over synced tables only for a local answer; `connected` unknown on a device; no clock beyond `now`, no randomness, no network; a mutation's fan-out must be a complete capped group so a prediction is exact | the program is meant to run locally |
| **A — authorization is static.** Rules are the audience a partition can hold; completeness is a class the prefix decides | index-prefixed reads; the rule/sync exact pairing; `exists` over an index; reads never raise a rule refusal | always: this is what Snapback wins on |
| **M — resources are metered.** Examined rows, probes, steps, heap, output and rows written have ceilings (LLP 2000.000 §6) | a mutation aborts `E_BOUND`, a query caps; jobs chunk | always: the process is scale-to-zero and shared |
| **S — Snapback 2's static pricing**, retired by LLP 2000.000 flip 1 but never removed from the binder | a local binds once; no accumulators; no `continue`; no `where`; `range` literals only; no text `+`; the `fn`/`proc` split; `divmod` in place of `/` | never, under the meter |

The author's thesis attributes the constraints to D. The record attributes
the *costly* ones to S. LLP 2000.000 §6 named this outcome in advance —
"What it dissolves: … the `fn`/`proc` split and the page-to-list gap,
which existed to keep collections priceable" — and §4.1 asked that the
restrictions be re-derived once the bound model was decided. They were
not; the binder came over with Snapback 2's refusals intact.

### 3.2 The interpreter already runs what the binder refuses

- `crates/snapback4-core/src/ir.rs`: `Stmt::Assign`, `Stmt::Push`,
  `Stmt::Continue`; `Builtin::Concat`, `Builtin::Len`; `Scan.range`
  with `gt`/`gte`/`lt`/`lte`.
- `crates/snapback4-core/src/engine/runner.rs`: `Assign` rebinds a local
  (line 149), `Push` appends to a list local under the heap meter (157),
  `Continue` flows (252), `Concat` joins text or lists (417).
- `crates/snapback4-core/src/engine/read.rs:381`: a scan's value range
  is evaluated and applied.
- `crates/snapback4-lang/src/bind/program/control.rs:38`: "duplicate
  local"; `parser/expr.rs:178`: "`where` is not a Quarry filter"; the
  language card's "left out on purpose" list.

Because the device is the same Rust (LLP 3000 §7, 2026-09-13, "one
implementation"), a form the server interpreter runs is a form every host
runs. The relaxations of §5 are binder changes over an interpreter that
needs almost nothing, plus one small IR field for filtered scans.

### 3.3 What "not needing local data" does and does not change

Without `sync` lines an application already runs online-only today: the
online tier (`createClient`) has no store, `observe` re-runs a query
when a commit touches its tables (`packages/snapback4/src/client.ts`),
and every query answers on the server. What that mode does *not* buy is
a looser program: the binder refuses the same forms. So relaxing "for
cases where you don't need the data locally" would mean a syntax that
varies by tier — and §3.2 says there is no reason for it to. The honest
design keeps the syntax one and lets residency be a fact about the data
an operation reads, computed and displayed, not a mode the author
selects.

Two things *are* genuinely server-only and should be spelled as such:
reads of online-only tables and of `connected`, which the client already
routes to the server (`packages/snapback4/src/local.ts:608`), and a
mutation that reads beyond the device's partition, which the device
already refuses to predict (`E_PREDICT`). Both decisions exist at
runtime; neither is visible at `check`. §6 lifts them.

### 3.4 Where the thesis undersells Snapback 4

Convex's own builders paid for what Snapback carries: password identity
(scrypt by hand), non-time-reactive queries (typing, expiry and presence
filtered on the client), fan-out as a read-time scan, a second project
directory for a second instance, and the whole durable offline layer.
Supabase's paid for four products' seams. Those are the "nice
properties" of the thesis, and they are the reason the Snapback 4 lane
was faster on M1, M2, M5, M6 and M8 at first green. The gap to close is
narrow and named: the last ten percent of a feature — an aggregate, a
ranking, a digest, a notification preview — where an ordinary loop with
a counter and a string is what every model reaches for.

### 3.5 Verdict

Agree that Quarry is too constraining; disagree that the constraint is
the price of local sync, and disagree that the answer is a looser mode
for online-only apps. The constraint is Snapback 2's pricing model wearing
Quarry syntax, and the answer is to finish the flip: relax the language
once, everywhere, under the meter; make where a program runs legible;
pave the online-only choice; close the seams the runs hit; and specify —
without yet building — the two hatches that would remain wanted.

## 4. Principles

1. **One language, one interpreter, every host.** No form is admitted on
   the server that the device cannot run; the wasm and the native module
   are the same Rust.
2. **The meter is the bound.** A form is admitted if the runtime meter
   bounds its cost; no static byte, step or closure price is reintroduced
   (LLP 2000.000 §6). A loop the meter cannot bound stays refused.
3. **Residency is a fact, not a mode.** Where an operation runs and
   whether a mutation predicts are computed from the tables it reads and
   printed by `check`, carried in `api.ts`, explained by `why`.
4. **No silent class change.** A change that moves an operation from
   device to server, or a mutation from predictable to queued-without-a-
   row, is a note at `check`, never a runtime surprise.
5. **Nothing leaves the engine's write path.** Every relaxation is a read
   or a computation; writes keep rules, constraints, maintains, the log
   and at-most-once (LLP 3000.005's rule 2).
6. **The card grows one word at most**, and only by the author's ruling
   (LLP 2000.000 §8).

## 5. The language, re-derived

Seven relaxations. Each names the constraint's source from §3.1 and the
mechanism that bounds it now.

| # | Today | Proposed | Source | Bound by |
| --- | --- | --- | --- | --- |
| 1 | A local binds once ("duplicate local") | `x = expr` rebinds a local of the same type; a `for` may carry a counter or a running sum | S | the step meter; `Stmt::Assign` exists |
| 2 | No accumulators (`count`/`sum` over a page, or a `maintain`) | `xs = []` then `xs = xs + [v]` (a list local grows; the binder emits `Push`); `s = s + n`; a list's static bound is the meter's heap ceiling, so `for x in xs` after the loop iterates a metered list | S | the heap meter (`Push` charges) and the step meter |
| 3 | `continue` refused ("wrap the rest in `if`") | `continue` | S (minimalism) | `Stmt::Continue` exists |
| 4 | `else if` refused ("nest an `if` under `else:`") | `else if cond:` as sugar for the nesting | S (minimalism) | nothing to bound |
| 5 | `where` refused ("index the predicate or check it in the read rule") | `t[prefix] [after c] first\|last N by idx where <row predicate>`: the scan proceeds in index order, a row passing the read rule and the predicate counts toward N; examined rows are metered as today | S + A's completeness class | the examined-rows meter; §5.1 fixes completeness and cursors |
| 6 | Text `+` refused ("store the parts; the client formats") | `text + text` → `Concat`; `slice`, `tokens` unchanged; no `format`, no case folding, no interpolation | S (bytes) and a product discipline | the output and heap meters |
| 7 | `/` and `%` refused ("`divmod` binds both") | `a / b` (integer quotient) and `a % b` beside `divmod`; zero refuses `E_DIV_ZERO` as `divmod` does | S (a semantic preference) | nothing to bound |

**What stays refused, and why it is not S.**

- `while` and non-literal `range` bounds: an unbounded loop's only bound
  would be the step ceiling (1,000,000 steps, an abort), which turns a
  program shape into a runtime failure for one user (LLP 0329.014.004
  §3: "Refused, unchanged: `while`, recursion"). `for` over a page, a
  list, a literal range or `tokens`, plus a job's `chunk`, cover the
  reference applications; the digest and Insights need neither.
- A mutation's loop over a page that is not one complete capped group
  (`E_STRUCTURAL_FANOUT`): D. A prediction must be exact and a write's
  fan-out visible; the 0.2.6 builder called this refusal valuable. The
  rewrite already names the job.
- The rule/sync exact pairing, index-prefixed reads outside `where`,
  `exists` over an index: A.
- Floats: the value model has none; a native job or read (LLP 3000.005)
  is the hatch, and a score is rounded to an `int`.
- Reads inside a `where` predicate: not in the first cut. A point read
  per examined row is a probe per row; `check --cost` would have to
  price it as "probe × examined". Row-local predicates first; the
  diagnostic names the guard-in-a-shape idiom.

### 5.1 `where`: completeness and the cursor

A filtered page is `complete: true` when it holds N matches or the scan
reached the end of its range, and `complete: false` when the meter cut
it. Its `next` cursor is the position after the last **returned** row
when the page filled, and after the last **examined** row when the meter
cut it — otherwise a continuation would re-examine the rejected run and,
if that run alone exceeds the examined ceiling, never advance. Hidden
rows are examined at miss cost as today (LLP 3000 §7, "completeness is a
class"); `where` never substitutes for the read rule and never sees a
row the rule hides. `Scan` gains one field, `filter: Option<Expr>`; the
runner applies it inside the scan loop after the rule; `pages.rs`'s
page-plan analysis and `N_NO_CURSOR` treat a filtered scan as a scan.
On a device the same code runs; `beyond_horizon` is unchanged.

### 5.2 The language card after the change

The "left out on purpose" list loses seven lines and gains none. The
card's program grows three forms (a counter, a filtered page, a preview
string); the suite compiles and runs it as today. `E_QUARRY_UNSUPPORTED`
for `where` and `continue`, and "duplicate local", are deleted with
their tests; `E_DIV_ZERO` gains `/`.

Clique, before and after, for the three places the 0.1.0 builder named:

```quarry
-- Insights' seven days: seven hand-written lines on 0.1.0; a loop now.
query insights():
  (dayNumber, dayRemainder) = divmod(now, 86400000)
  d = now - dayRemainder
  days = []
  for i in range(0, 7):
    day = d - i * 86400000
    days = days + [{ day, posts: activityDays[viewer, day, 'post'], likesReceived: activityDays[viewer, day, 'like'] }]
  return { posts: activityTotals[viewer, 'post'], followers: followers[viewer], following: following[viewer], days }

-- The digest's totals: a `digestWork` table and four updates on 0.1.0; two counters now.
job digest(periodStart: time, periodEnd: time):
  chunk p in profiles first 1 by byId:
    unread = 0
    chats = 0
    for m in memberships[p.principal] first 1000 by byPrincipal:
      n = unreadPeriods[m.conversationId, p.principal, periodStart, 0]
      if n > 0:
        unread = unread + n
        chats = chats + 1
    if unread > 0:
      emit digest { targetUserId: p.principal, periodStart, periodEnd, unreadMessages: unread, unreadChats: chats }

-- The push preview: `slice(body, 0, 80)` and the worker formats, on 0.1.0; one line now.
emit notify { targetUserId: m.principal, preview: profiles[viewer].displayName + ': ' + slice(body, 0, 80) }
```

Trending — the top ten of the trailing day by likes — becomes a filtered
page shaped with the maintained count and sorted, instead of a `hotPosts`
table kept by every like: `posts last 200 by byTime where .at > now -
86400000 { *, likes: likeCounts[.id] }` then `slice(sort(page, '-likes'),
0, 10)`. Its cost class is one page plus one probe per row, which
`check --cost` prints.

## 6. Residency and execution, made legible

This section adopts the direction of the author's draft on explicit
residency (LLP 3000.006, uncommitted in the author's checkout as of
2026-09-13) and reduces its vocabulary to what the code already decides.

### 6.1 `online only`

A positive spelling for the table line whose absence today means
online-only:

```quarry
table auditEvents:
  actorId: principal
  action: text <=100
  at: time
  by byActorTime: actorId, at, id
  read <- exists admins[viewer]
  insert <- deny
  online only                          -- rows never enter a partition or a device
```

Optional: a table with neither `sync` nor `online only` keeps today's
meaning with no note. `check --residency` (§6.3) shows every table
either way, so the line is documentation the author can choose, not a
tax on every table. Whether it becomes required is the author's (§14).

### 6.2 Two words per operation

`check` classifies every operation from its read sites:

- a query **runs on the device** when every read site is a synced table
  (or a maintain inherited into the partition) and it reads no
  `connected`; otherwise it **runs on the server**. This is the
  client's `onlineOnly` test at `local.ts:608`, moved to the compiler;
- a mutation **predicts** when every read site is a synced table and
  every write is to a synced table (LLP 2000.000 §7.3); otherwise it is
  **queued without a row**, and the reason is the first read site that
  is not held.

A horizon does not change the class: a device-run query past its horizon
is `complete: false` and the client already re-asks the server whole
(`local.ts:617`). A native read is the device class when the device has
the module.

`api.ts` carries the words on `Op`: `runs: "device" | "server"` for a
query, `predicts: boolean` for a mutation. The card is unchanged; these
are facts about operations, not screen states.

### 6.3 `check --residency` and `why`

```text
residency
  profiles          public, no horizon (one row per principal)
  messages          to memberships[.conversationId], last 500 by byConvTime
  auditEvents       online only
  receiptEvents     online only (no sync line)

operations
  thread            device; server past the horizon
  insights          server: reads activityTotals (online only)
  send              predicts
  createDm          queued without a row: reads dmPairs[other, viewer] beyond the partition
```

`why <op>` prints the site that makes an operation server-run or
non-predictable and the shortest rewrite that would change it. `why
<table>` prints its residency line.

### 6.4 Notes when a class moves

Two notes, in the family of `N_NO_HORIZON`:

- `N_NOW_SERVER` — a query that ran on the device in the previous
  generation now reads a site the device does not hold; the note names
  the site.
- `N_NOT_PREDICTABLE` — a mutation that predicted in the previous
  generation no longer does; the note names the read. This is the
  0.2.6 builder's hardest loop (a redundant `exists messages[id]` guard
  beyond the horizon) surfaced at `check` instead of in an offline probe.

`dev` compares against the generation it is serving; `check` alone
compares against `snapback/generated/` when present.

### 6.5 The offline outcome of a server-run read

Today a server-run read while offline is either `denied: E_OFFLINE`
(when the device refuses) or a plausible empty page (when it does not;
`local.ts:620` returns the device's data with `complete: false`). With
the class known at compile time the client short-circuits: a server-run
query with no link is `denied: { code: "E_OFFLINE", family: "link",
retryable: true }`, always. That is the typed non-value the residency
draft asked for, already on the card as family `link`; no `unavailable`
word is needed.

## 7. The online-only mode, paved

An application that wants no partition writes no `sync` line and opens
`createClient`. Both exist. What is missing is that nothing tells an
agent this is a first-class choice:

- `snapback4 init --online` writes a template with no `sync` lines, a
  `public`/`.col = viewer` schema, and a client on `createClient`;
  `init` (the default) keeps the local-first template. The README's §1
  gains a paragraph, "Two ways to run," and the language card's `sync`
  comments say "omit for an online-only table."
- `check --residency` on such a schema prints every operation as
  `server`, and `api.ts` says so; `useQuery` on the online tier is live
  through `/changes` as today.
- Nothing else changes: the same rules, meter, identity, assets, jobs,
  effects and diagnostics. A `sync` line added later moves an operation
  to the device and `N_NOW_SERVER`'s inverse is silent, because moving
  onto the device loses nothing.

This is the relaxed mode the author asked for, and it costs a template
and two paragraphs because the substrate already supports it.

## 8. The client seams the runs hit

Each item names the loop it removes (§2.2).

1. **A mutation's result reaches the client.** `Write` gains
   `result` on `sent` (the server already answers with it,
   `crates/snapback4/src/serve.rs`) and `predicted` on `pending` when the

## 9. Escape hatches for the last ten percent

Two hatches remain wanted after §5–§8, by the builders' own words: SQL
for reporting and ordinary code for integrations. Neither is proposed
for the first landing; both are specified so the rerun (§10.3) can say
whether they are still needed.

### 9.1 SQL reads

```quarry
query insightsSql(): sql
```

with the body in `snapback/sql/insightsSql.sql`, read-only, over
per-viewer authorized views the compiler generates from the read rules
(`public` → `TRUE`; `.col = viewer` → `col = :viewer`; `exists t[.a,
viewer]` → a correlated `EXISTS`; `and`/`or`/`not` → the same). The
store keeps rows as JSON text in one table (`r(t, id, data)`,
`crates/snapback4-core/src/store.rs:101`), so a view is `json_extract`
per column; the secondary index table is not usable by SQLite's planner,
so a SQL read is a scan bounded by SQLite's progress handler as the step
meter, an injected `LIMIT` as the output bound, and an authorizer that
denies writes, the internal tables and the raw `r`/`i`. Always
server-run; typed `unknown` in `api.ts` unless a shape is declared. It
is a second query language, which `NOT-DOING.md` refuses; it earns a
Moves line only if the rerun shows reporting still costs loops after §5.

### 9.2 Worker actions

```quarry
action sendInvite(to: text <=200, message: text <=2000)
```

An operation whose body is the application's own TypeScript in the
worker it already runs for effects (`snapback4/worker`): the client
calls `api.sendInvite` like a mutation; the server keeps the request,
a worker with a service token claims it over the wire (as it claims an
effect), performs it with a short-lived session the server minted for
the *viewer* — so its reads and writes run under the viewer's rules,
never the service's — and settles a result the server returns to the
waiting client. At-least-once, no transaction, never predicted, offline
is `E_OFFLINE`, and `dev` spawns `snapback/worker.ts` when it exists.
The engine still never calls out. This is Convex's action in Snapback's
shape and the answer to "there was no ordinary server function into
which I could move the awkward part" for the parts that need the
network. Proposed after the rerun, if integrations still cost loops.

### 9.3 Considered and not proposed

- **Native mutations** (`mutation x(): native`) for server-run
  mutations: consistent with §6 — a mutation that does not predict has
  no device twin to protect — but the Rust toolchain is the wrong
  weight for the ten percent; LLP 3000.005 stays the floats-and-vectors
  hatch.
- **A JavaScript engine in the process**: refused by `NOT-DOING.md`,
  the security review and the Snapback 2 record (Ibex's subset library
  was the effect runner's whole friction).
- **SQL writes**: bypass rules, constraints, maintains, the log and
  at-most-once. Never.

## 11. Alternatives considered

- **A relaxed grade by syntax** (`query x(): server` admits the relaxed
  forms; device programs keep the strict ones). Rejected: §3.2 shows the
  forms are device-safe, so the grade would exist only to preserve a
  restriction the meter already replaced, and every author would learn
  two languages to write one.
- **Online-only by default; `sync` as the opt-in exception.** Rejected:
  it is already the case (a table without `sync` is online-only) and the
  bet of LLP 2000.000 §7 is local-first; §7 paves the choice without
  moving the default.
- **Make the residency line mandatory now.** Deferred to the author; the
  table view gives the same legibility without a line on every table.
- **`{ unavailable: "requires-online" }` on the card.** Not needed:
  `denied: E_OFFLINE`, family `link`, retryable, is that word, and §6.5
  makes it the only offline outcome of a server-run read.
- **A full page-to-list conversion and `fn`/`proc` unification.** In
  scope of LLP 2000.000 §6's "dissolves" but not needed by any recorded
  loop; left for a later pass.
