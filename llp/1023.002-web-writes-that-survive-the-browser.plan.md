## Outcome and owner

One provider-owned durable web client is sufficient for sends, offline vote
replay, settings and member removal. Once it has admitted a write, document
reload and a lost response preserve the intent and allow exactly one server
effect after reconnect. The UI distinguishes saving, queued, committed and
refused using the existing result/work model.

Implementer: Codex / Astra, existing Snapback 2 client lane, under the parent's
2026-09-12 commission. Coordinate shared client changes with the query
lane and use the acquisition lane's existing performance controls.

## Evidence before mechanism

The 0.0.21 Grok diary reports a durable-client wait beyond 15 seconds versus
about 54 ms for a token-only client. Triage reproduced successful **online
first writes**, not the single-context m7-a05 offline-vote replay. Intentional
follower tests also passed; they do not explain every single-context failure.
Later Astra builders reported headless/keepalive navigation workarounds.

Current main includes foreground admission repairs:
[LLP 1018.008.007.002 §9](./1018.008.007.002-bounded-bulk-acquisition.plan.md#9-implementation-and-measured-outcome).
The final controls admitted in 596–686 ms and returned committed in
2.50–3.09 seconds during acquisition; one cleanup failed. These are limited
controls, not a new quiet-host SLA. Do not reproduce the already-fixed
general-recovery wait as if it were the remaining diagnosis.

The token-only client omits durable storage, prediction and replay preparation.
Its timing is a diagnostic lower bound, not a fair completion contract.
Measure the stages before concluding that IndexedDB itself is the bottleneck.

## Contract: admission, settlement, observation

The current durable path already enqueues before dispatching replay, including
online writes (`client-outbox.ts::submitMutation`). `client.mutation` is
already asynchronous. It returns `committed | queued | rejected`; awaiting
it is not a new durability feature.

| Cut | Obligation |
| --- | --- |
| Before carrier admission | No accepted-save claim. An interrupted document may lose its unadmitted action; preserve the draft while the document remains active |
| Carrier transaction committed; response not yet received | Stable intent bytes, reserved IDs and order survive reopen in the same account/store |
| Owner committed; response lost | Replaying the same intent obtains its terminal without a duplicate effect |
| Result returned `queued` | Show locally saved/pending and stable intent/work identity; do not claim server completion |
| Result returned `committed` | Server commit is known; a receiving query still needs its own observation before claiming visibility |
| Result returned `rejected` | Preserve input and expose the refusal; never treat a resolved promise as success |
| Sign-out, account/generation change or explicit offline cut | Existing fences and sealing/wipe rules apply; no old-account background send or new-intent retry |

IndexedDB request success is not transaction completion. Use the carrier's
completed atomic commit as the admission boundary, consistent with the
[IndexedDB transaction lifecycle](https://w3c.github.io/IndexedDB/#transaction-lifecycle).
This plan qualifies reload/process restart with intact browser storage, not
power-loss durability, storage eviction or execution while the browser is closed.

A route change inside a surviving document, provider/client teardown, full
document navigation, and browser process termination are distinct experiments.
A route unmount must release its observers, not close an app-owned client.
Full navigation cannot promise to complete JavaScript still awaiting admission.

## A — A small reproduction matrix on current source

Use the existing Chromium/IndexedDB witness path, one stable browser profile,
one persona and one app-owned client. Reopen creates the replacement client
for that document in the same account partition; it is not an auxiliary
concurrent client. Start with bearer auth and retain a dev-persona control.

1. **Ordinary online write:** fixed small send/settings payload, fresh and
   warm store. Capture call, durable admission, dispatch, owner commit,
   local terminal and sender/recipient observation separately.
   Pause fresh-store/bearer restoration before the runtime principal exists
   and call mutation. Trace the `submitMutation` plain-wire fallback: a client
   configured with durable storage must wait or refuse truthfully, never
   bypass custody because restoration is incomplete. Preserve intentional
   non-durable-client behavior.
2. **Route lifecycle:** navigate with the client/provider mounted, then a
   separate explicit provider-teardown control. Identify which cancellation
   the app actually triggers.
3. **Full reload:** pause before admission, after carrier commit/before
   dispatch, and after owner commit/before response. Reload the same profile,
   first offline to inspect durable work, then reconnect.
4. **Offline replay:** queue at least two ordered writes, including the
   original vote/update shape, reopen offline, then explicitly reconnect in
   that same context. A clean SDK-offline cut and a physical network cut
   exercise different paths; cover both.
5. **Pressure/control:** repeat foreground admission during bounded
   acquisition and with existing queued acknowledgements. Reuse the landed
   repair's fixture. Keep a follower control separately labeled.

Use barriers/fault injection at existing boundaries for correctness tests,
not sleep-based races or a mocked claim that unload happened. Correlate
intent/alias, account, auth epoch, generation, store partition, writer state,
queue order and actual owner row. Preserve failed attempts and host load.

Also expire authentication after carrier commit but before the call returns.
A refused wait can leave admitted work sealed for later replay; it is not
necessarily a terminal rejection of that intent. The public work/alias owner
must let the consumer retain that distinction and recover the original
identity. Preserving input must not encourage a new submission while the
original admitted action can still commit.

## B — Repair the failing boundary

- **Provider ownership defect:** keep the durable client above route screens;
  release per-screen observers only. Do not install another client in settings.
- **Preparation stalls:** trace auth, program/grant acquisition, inbox ordering
  and recovery. Reuse the repaired capacity path; current readiness is advisory
  and must still be checked atomically at reservation.
- **Carrier stalls or lost admission:** inspect the exact transaction and
  serialization/lock wait. Remove attributed redundant work without publishing
  before commit, skipping IndexedDB or overtaking older durable inbox rows.
- **Replay stalls:** distinguish a legitimate stopped head from a drain that
  cannot advance. Resume existing work with `online()` / explicit recovery,
  preserve FIFO and fixed intent bytes, and publish actionable stopped reasons.
- **Delayed presentation:** a committed intent may still await its target's
  observation. Repair the missing notification or observation input; do not
  label speculative data committed.

Already-passing cases need retained qualification, not speculative fixes.
After three unsuccessful repair rounds, follow the parent's bounded stop
rule and record the unresolved failure.

## C — Navigation and transport choice

The paved settings recipe awaits `run(args)`, handles rejection, then
navigates on `committed` or on `queued` with a visible pending state.
A flow that requires the server-side result must wait for its committed
terminal rather than proceeding on `queued`. Same-document navigation with
an app-owned client may let work continue, but does not establish custody by
itself. Do not advertise fire-and-unload before admission as supported.

Preserve current online mutation result semantics. If measurement demonstrates
that a navigation flow needs a separately observable admission milestone before
its terminal result, propose that minimal addition on the same work owner here
with explicit types/lifecycle and a byte trade; do not silently change
`mutation()` to resolve all online calls as queued.

**Keepalive is an optional measured optimization, not the primary repair.**
The Fetch standard allows a request to outlive its environment but retains
abort behavior and a shared in-flight body limit of 64 KiB in its fetch group.
It does not keep async preparation or response processing alive.
[Fetch Standard](https://fetch.spec.whatwg.org/#http-network-or-cache-fetch)

Only evaluate it after durable intent admission, using the same replay
identity and authority. If tried, test aggregate quota exhaustion, large
bodies, auth changes and loss of response; ordinary replay must still recover.
Do not apply it to every `/api/*` request, treat it as immune to cancellation,
or bypass the outbox when the body does not fit. No beacon, service worker,
background sync or second persistence system is selected.

## D — Acceptance and bounded timing

| Scenario | Required evidence |
| --- | --- |
| Reload before admission | No UI accepted-save claim; no partial intent or inconsistent reserved state |
| Reload after admission | Original intent/alias and FIFO order recover; one server effect after reconnect |
| Response lost after owner commit | Same-intent retry settles; no second insert, vote or membership effect |
| Offline vote/settings replay | Pending survives cold reopen and becomes the correct owner state using one client |
| Rejection/auth/lock/quota controls | No false success, no cross-account work; existing refusal/recovery state is usable |
| Navigation and observation | App-owned client survives route unmount; full reload respects custody; server commit and UI observation remain distinct |

Timing protocol: on a checked quiet host with a local owner and small payload,
retain ten samples per ordinary online/offline-reconnect case. Proposed
engineering targets are median admission at most 1 second and median terminal
at most 3 seconds for the two-intent queue; record every sample and maximum.
They are targets to validate, not established service guarantees or population
p95. A 15-second unresolved call is a failed diagnostic sample, never a timeout
to raise silently. A legitimate blocked head must instead expose its reason
and recoverable work; it cannot be counted as a successful latency sample.

During acquisition, run the matched existing foreground control and attribute
regressions at admission, replay or observation. Full acquisition's 2–3-second
objective remains owned elsewhere. Do not require these distinct clocks to
have the same threshold.

Extend existing deterministic lifecycle/outbox tests; use real browser
witnesses for unload and IndexedDB. Browser qualification stays in the
scheduled web class, not a sixth blocking gate. Expo native receives affected
shared-code regressions but no native performance claim from Chromium.
One-client guide/template examples and the published consumer must demonstrate
the same contract. Byte funding and integration follow the parent.

## Implementation findings — 2026-09-12

Current-source deterministic probes reproduced two defects through
`client.mutation`: a failed fresh, unbound bearer restoration released `ready`
without a principal and then sent plain mutation bytes; an expiry after durable
admission returned a refusal without this call's original intent. The repair
reserves plain transport for clients without a runtime, refuses an unopened
durable partition, and retains the original intent in the existing refused
result after carrier completion. That refusal concerns the caller's wait;
queued work remains authoritative, sealed on expiry and recoverable after
same-account sign-in. No new admission API or provider lifecycle mechanism.

The existing Chromium 151 single-context bearer/IndexedDB send control passed
on baseline: 54 ms admission, 181 ms reconnect settlement, one exact envelope.
Its first launch refused because the media helper had not been built; building
the existing helper resolved that preparation failure. The original vote/update
and lifecycle matrix is recorded below.

### Carrier boundary and refusal ownership

A tighter immediate-seal probe exposed one further gap: `enqueueNow` completed
its atomic swap, then re-read the same entry. A seal between those operations
made an admitted call lose its identity. The ledger lock already excludes
settlement, so enqueue now returns a detached copy of its committed entry.
There is no second carrier read. Post-admission observation also maps the
known raw sealed-store error through the existing `E_OFFLINE_LIFECYCLE`
refusal; typed refusals and unrelated errors retain their original boundaries.

`onCustody` remains the pre-commit/upload cleanup fence. A separate **internal**
post-enqueue callback captures intent only after commit. The public API is
unchanged: `rejected.intent` identifies a refused wait whose durable entry may
still be queued. Expiry seals that entry, and same-account sign-in restores its
existing `outbox.observe().getWork(intent)` lookup; no fresh submission is
needed. No admission milestone API, keepalive, beacon, second client, worker,
new carrier, cache, gate or registry was added. The provider hypothesis did not
reproduce as a defect and received no lifecycle repair.

### Review correction: cleanup failure after admission

The Sol review found that the catch path awaited terminal-session cleanup
before attaching the admitted intent. A failed seal or token clear could
escape to the outer plain-result boundary, returning a rejected wait without
its durable identity. The catch now retains the cleanup error and uses the
same admission-aware return. Typed cleanup refusals retain their fields;
unexpected errors keep the existing `E_CLIENT` boundary. Cleanup failure
does not convert an admitted intent into a terminal ledger rejection.

Four deterministic controls in the existing `outbox-custody.test.ts` inject
expiry at the drain boundary after a real file-carrier commit, then fail
token clearing, typed sealing, raw sealing, or cleanup with an unexpected
exception. All four fail against the preceding source with a missing intent
and pass after this repair. Each removes the fault, signs into the same
account, and observes the original entry committed with exactly one owner
effect, including another reconnect. These are bounded injection controls;
the existing HTTP 401 and typed HTTP 200 replay/tail expiry controls also pass.

Package build and 209 affected custody/auth/recovery tests pass. Evidence is

### Qualification correction: admission bytes and store-owned FIFO order

The full package pass found three delivery cases comparing the detached
admission return with the entire persisted entry. Their only difference was
`order`: the carrier assigns it atomically to its stored copy. The admission
return intentionally avoids a second read after commit, which could lose
identity if the partition seals. Public mutation results return intent/IDs;
public outbox entries and work still read the persisted FIFO entry.

The correction changes tests only: compare the admitted bytes, assert a valid
persisted order, and check that the acknowledgement follows the product write.
No carrier, ordering or public-result behavior changes. Package build and all
251 affected checks pass (the retained 209 custody/auth/recovery cases plus
42 delivery cases). Logs are under `web/publication/final-ade408/` in the
existing program scratch directory. Final package integration and publication
remain with the parent.
